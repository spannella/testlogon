# GAP-0126: Billing Atomicity Gap in `_write_private_chat_billing()` — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at
> `app/services/broadcast_private_chat.py`. No prior investigation doc exists.

## 1. Summary & Classification

**Bug**: The `_write_private_chat_billing()` function in the broadcast private-chat service
writes a viewer debit and a creator credit as two independent DynamoDB `put_item` calls,
each wrapped in its own `try/except`. If the credit write fails after the debit succeeds,
the viewer has been charged but the creator receives no payment — money disappears into a
ledger gap with no alerting.

- **Severity**: HIGH — financial integrity, silent money loss
- **Source ticket**: BCAST-012
- **Status**: Open
- **Owning area**: Broadcast / Billing
- **Claim verdict**: Confirmed. Code matches description exactly (lines 633–664 of
  `app/services/broadcast_private_chat.py`).
- **One-line impact**: Any transient DynamoDB error during the credit write silently
  leaves a viewer debited with no corresponding creator credit.
- **Related tickets**: GAP-0128 (same pattern in `_charge_entry_fee`), GAP-0129 (same
  pattern in `_write_chat_billing`), SECOPS-007 (dev/prod parity requirement).

## 2. Current-State Investigation (root cause)

### Code path

The affected function is at
`app/services/broadcast_private_chat.py:603–665`:

```python
def _write_private_chat_billing(
    viewer_id, creator_id, total_cents, creator_earnings_cents,
    chat_id, session_id, tier, duration_minutes, payment_method_id,
) -> Tuple[str, str]:
    ts = now_ts()
    debit_id = uuid.uuid4().hex
    credit_id = uuid.uuid4().hex
    ...

    try:                                      # line 633
        T.billing.put_item(Item={             # line 634 — DEBIT
            "pk": f"USER#{viewer_id}",
            "sk": f"LEDGER#{ts}#{debit_id}",
            "type": "debit",
            "amount_cents": total_cents,
            ...
        })
    except Exception:                        # line 646
        logger.warning("private_chat_billing_debit_failed ...")
        # ← execution CONTINUES; no re-raise

    try:                                     # line 649
        T.billing.put_item(Item={            # line 650 — CREDIT
            "pk": f"USER#{creator_id}",
            "sk": f"LEDGER#{ts}#{credit_id}",
            "type": "credit",
            "amount_cents": creator_earnings_cents,
            ...
        })
    except Exception:                        # line 662
        logger.warning("private_chat_billing_credit_failed ...")
        # ← execution CONTINUES; debit already written, irrecoverable

    return debit_id, credit_id               # line 665
```

### What is present vs missing

**Present**:
- Two separate `put_item` calls, each with an independent `try/except`.
- A `logger.warning` log on failure — but no re-raise, no rollback, no dead-letter.

**Missing**:
- Atomicity: there is no `TransactWriteItems` call that either commits both ledger entries
  or neither.
- Error propagation: neither exception is re-raised; the caller receives `(debit_id,
  credit_id)` as if billing succeeded even when one write failed.
- A compensating rollback or idempotency key that would allow replay of the failed credit.

### Callers

`_write_private_chat_billing` is called from three code paths in the same file:

1. `purchase_private_chat` — tier-1 purchase (line 97)
2. `purchase_private_chat` — tier-2 voyeur purchase (line 168)
3. `extend_private_chat` — extension billing (line 369)

All three paths are affected. The tier-2 voyeur path ignores the returned `(debit_id,
credit_id)` tuple entirely (line 168), meaning a debit failure there also goes undetected
by the caller.

### Dev vs prod behaviour

In dev mode (`DEV_MODE=1`) the moto/local-DDB stack is reliable, so the split rarely
fails. In production (AWS DynamoDB), transient `ProvisionedThroughputExceededException`,
`InternalServerError`, or network interruptions can cause one write to land and the other
to be lost. The `logger.warning` call is not connected to any alerting, so the
inconsistency could persist indefinitely.

## 3. Impact / Exploit / Blast Radius

### Who is affected

- **Viewers** paying for private chats: any individual who purchases or extends a
  private chat (tier-1 or tier-2) during a transient DynamoDB write failure is charged
  without the creator being credited.
- **Creators**: receive no payment for the session despite the viewer having been
  debited.
- **Platform**: ledger becomes permanently inconsistent; the debit row exists without
  a matching credit row, making reconciliation reports wrong and audit trails unreliable.

### Concrete exploit walkthrough

Scenario — infrastructure fault:

1. Viewer calls `POST /broadcast/{session}/private-chat/purchase`.
2. `purchase_private_chat` writes the chat session record to `broadcast_private_sessions`
   (line 95) — succeeds.
3. `_write_private_chat_billing` is called. The debit `put_item` at line 634 succeeds
   (viewer wallet debited).
4. DynamoDB returns a transient error on the credit `put_item` at line 650.
5. Exception is caught and **swallowed** at line 662. `logger.warning` fires but no
   alert escalates.
6. Function returns normally. Caller sees a successful response; API returns HTTP 200
   with `chat_id` set.
7. The creator's billing ledger has no credit entry. The viewer has been charged.

### Worst case

At a busy broadcast with 50 concurrent chat purchases, if a transient DDB fault hits
during the credit sweep, every purchase in the affected window results in viewer
charges with no creator credits. At a $5/min default rate for a 5-minute chat, each
lost credit is $4 net (after 20% platform fee). Fifty purchases = $200 in lost creator
earnings per incident with no automatic detection.

### Data integrity consequence

The ledger is also used for wallet balance queries. A missing credit will cause creator
balance reads to show a lower-than-real balance until manual remediation.

## 4. Fix Design (code-level)

### Strategy

Replace the two sequential `put_item` calls with a single `TransactWriteItems` call
across the shared `billing` table. This is the same pattern already used in
`app/routers/newsfeed.py:2958` and `app/services/filemanager.py:3285`.

### Primary change — `_write_private_chat_billing`

```python
# app/services/broadcast_private_chat.py

from app.core.aws import ddb                # add import

def _write_private_chat_billing(
    viewer_id: str,
    creator_id: str,
    total_cents: int,
    creator_earnings_cents: int,
    chat_id: str,
    session_id: str,
    tier: int,
    duration_minutes: int,
    payment_method_id: str,
) -> Tuple[str, str]:
    """Write paired debit/credit billing ledger entries atomically."""
    ts = now_ts()
    debit_id = uuid.uuid4().hex
    credit_id = uuid.uuid4().hex
    reason = f"Private chat: tier {tier}"
    meta: Dict[str, Any] = {
        "content_type": "private_chat",
        "chat_id": chat_id,
        "session_id": session_id,
        "tier": tier,
        "duration_minutes": duration_minutes,
        "viewer_id": viewer_id,
        "creator_id": creator_id,
        "payment_method_id": payment_method_id,
    }
    billing_table_name = T.billing.name

    debit_item = {
        "pk": f"USER#{viewer_id}",
        "sk": f"LEDGER#{ts}#{debit_id}",
        "entry_id": debit_id,
        "ts": ts,
        "type": "debit",
        "amount_cents": total_cents,
        "currency": "USD",
        "state": "settled",
        "reason": reason,
        "meta": meta,
    }
    credit_item = {
        "pk": f"USER#{creator_id}",
        "sk": f"LEDGER#{ts}#{credit_id}",
        "entry_id": credit_id,
        "ts": ts,
        "type": "credit",
        "amount_cents": creator_earnings_cents,
        "currency": "USD",
        "state": "settled",
        "reason": reason,
        "meta": meta,
    }

    # Atomic write: both entries land or neither does.
    ddb.meta.client.transact_write_items(
        TransactItems=[
            {"Put": {"TableName": billing_table_name, "Item": _ddb_av(debit_item)}},
            {"Put": {"TableName": billing_table_name, "Item": _ddb_av(credit_item)}},
        ]
    )

    return debit_id, credit_id
```

Where `_ddb_av` is a helper that converts Python values to DynamoDB `AttributeValue`
format. The existing `_ddb_av_map` helper in `app/routers/newsfeed.py` (or
`boto3.dynamodb.types.TypeSerializer`) provides this conversion. A shared
`_serialize_item` helper can be added to `app/services/billing_utils.py` (see GAP-0129
for the consolidation recommendation).

### Error propagation

Remove all `try/except` wrappers from the billing write. Let the `TransactionCanceledException`
propagate to the router, which will return HTTP 500 to the client. The viewer is **not**
debited in that case (the transaction is all-or-nothing), so the correct user-visible
outcome is a retriable error, not a silent success.

### Dev/prod parity (SECOPS-007)

Both local DynamoDB (`DDB_ENDPOINT_URL=http://localhost:8001`) and AWS DynamoDB support
`TransactWriteItems`. No feature flag is needed. The `ddb.meta.client` handle is
already used by `transact_write_items` callers elsewhere in the codebase (e.g.
`app/services/filemanager.py:3285`). No mock-specific code path is required.

moto v4+ supports `TransactWriteItems` on `DynamoDB.Client`. The existing test suite
runs against moto — no changes needed for the test infrastructure.

### Alternatives considered

1. **Saga / compensating transaction**: Write debit, then on credit failure write a
   reversal. Rejected — more complex, still leaves a window of inconsistency during
   the reversal attempt, and adds a second DDB round-trip.
2. **Outbox pattern**: Write both entries to a pending outbox table, have a background
   worker flush them transactionally. Rejected — significant architectural change for
   a high-severity fix that has a simpler DDB-native solution.
3. **Keep try/except but re-raise on credit failure**: Half-measure. Still leaves a
   non-atomic debit. Rejected.

### Backward compatibility / migration

Existing ledger rows written under the old pattern are already settled and do not need
migration. The fix is forward-only: new writes after deployment are atomic. No schema
change, no DynamoDB table update, no feature flag required.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to `tests/services/test_broadcast_private_chat_billing.py`:

```python
import pytest
from unittest.mock import patch, MagicMock
from botocore.exceptions import ClientError

def _make_cancel_error():
    """Simulate a TransactionCanceledException from DynamoDB."""
    err = ClientError(
        {"Error": {"Code": "TransactionCanceledException",
                   "Message": "Transaction cancelled"},
         "CancellationReasons": []},
        "TransactWriteItems",
    )
    return err

def test_billing_is_atomic_credit_failure_does_not_leave_orphan_debit(moto_billing_table):
    """
    BEFORE fix: credit exception swallowed; debit row exists with no matching credit.
    AFTER fix:  TransactWriteItems raises; both rows absent; exception propagates.
    """
    from app.services.broadcast_private_chat import _write_private_chat_billing
    from app.core.aws import ddb

    # Patch transact_write_items to simulate a credit-side failure
    original = ddb.meta.client.transact_write_items
    call_count = {"n": 0}

    def failing_transact(**kwargs):
        call_count["n"] += 1
        raise _make_cancel_error()

    with patch.object(ddb.meta.client, "transact_write_items", side_effect=failing_transact):
        with pytest.raises(ClientError, match="TransactionCanceledException"):
            _write_private_chat_billing(
                viewer_id="viewer_1",
                creator_id="creator_1",
                total_cents=500,
                creator_earnings_cents=400,
                chat_id="chat_abc",
                session_id="sess_abc",
                tier=1,
                duration_minutes=1,
                payment_method_id="pm_test",
            )

    # After the fix, no debit row should exist because the transaction was cancelled.
    resp = moto_billing_table.query(
        KeyConditionExpression="pk = :pk",
        ExpressionAttributeValues={":pk": "USER#viewer_1"},
    )
    assert resp["Count"] == 0, "Orphan debit row must not be written after atomic failure"
```

**Fails before fix**: the old code swallows the credit exception and returns normally;
the test's `pytest.raises` block is never entered, so the assertion that `Count == 0`
fails because a debit row was written.

**Passes after fix**: `transact_write_items` raises `TransactionCanceledException`,
which propagates; no rows are written; assertion passes.

### Manual QA steps

1. Start the local dev stack (`just up`).
2. Use the DynamoDB admin (`just status` → port 8001) to inject a conditional write
   failure by temporarily adding a provisioned-throughput limit of 0 to the billing table.
3. Trigger a tier-1 private chat purchase via the API.
4. Confirm the HTTP response is 500 (not 200).
5. Confirm the billing table has zero ledger rows for the viewer.
6. Remove the throughput limit and retry — confirm 200 and two matching ledger rows.

### Observability

- Add a structured log at ERROR level (not WARNING) when `transact_write_items` raises.
- Add a CloudWatch / Prometheus counter `billing.private_chat.transact_failed` to alert
  ops when the atomic write fails.
- Existing reconciliation queries (matching debit rows to credit rows by `meta.chat_id`)
  should continue to work — the fix does not change the ledger row schema.

### Rollback

The change is backward-compatible — revert to the previous `put_item` pair if the
atomic write causes unexpected issues. Risk of revert: reintroduces the atomicity gap.

### Effort

**S** (Small) — one function to rewrite, no schema changes, no migration. Estimated
1–2 hours implementation, 2–3 hours for test coverage including edge cases.
