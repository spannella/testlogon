# GAP-0161: Admin advance-progress endpoint open to any authenticated user — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing; all citations are live file:line references.

## 1. Summary & Classification

**Bug statement**: The `POST /ui/achievements/admin/advance` endpoint, which forcibly advances any achievement metric counter and can unlock any achievement for the caller, is protected only by `require_ui_session`. Any logged-in user — not just platform operators — can call it, awarding themselves arbitrary achievement points and unlocking any badge at will.

**Severity**: HIGH  
**Source ticket**: ENGAGE-001 (Achievements & Gamification System)  
**Status**: Open  
**Owning area**: Backend — Achievement & Gamification subsystem (`app/routers/achievements.py`)  
**Effort**: S (single-line dependency swap)

**Verdict**: Claim **confirmed**. The code at `app/routers/achievements.py:278` uses `Depends(require_ui_session)` instead of `Depends(require_root_session)`. All other admin-facing endpoints in the same file already use `require_root_session` (lines 66, 87, 96, 113), making this a clear oversight.

**Impact in one line**: Any authenticated user can POST to `/ui/achievements/admin/advance` with an arbitrary `metric_key` and `delta` to inflate their own achievement counters and unlock badges they have not legitimately earned, corrupting gamification integrity and leaderboard standings.

**Related tickets**: ENGAGE-001 (parent feature), GAP-0162 (achievement hooks not wired — makes the admin endpoint the *only* unlock path). Because GAP-0162 means no legitimate auto-unlock path exists yet, this endpoint is currently the **sole mechanism** for any achievement to be earned. Leaving it open to all users means the entire gamification system is effectively operating in an honor-system mode, where all progress is self-reported by calling this endpoint directly.

## 2. Current-State Investigation (root cause)

### Code path

`app/routers/achievements.py:277–283`:

```python
@router.post("/ui/achievements/admin/advance")
async def admin_advance_progress(req: AdvanceProgressIn, ctx: dict = Depends(require_ui_session)):
    """Advance progress for the authenticated user (dev/test helper)."""
    user_sub = ctx["user_sub"]
    from app.services.achievement_progress import advance_progress
    unlocked = advance_progress(user_sub, req.metric_key, delta=req.delta)
    return {"ok": True, "newly_unlocked": unlocked}
```

The `AdvanceProgressIn` model at line 56 is:

```python
class AdvanceProgressIn(BaseModel):
    metric_key: str = Field(..., min_length=1, max_length=64)
    delta: int = Field(default=1, ge=0)
```

There is no upper bound on `delta`. An attacker can submit `{"metric_key": "post_count", "delta": 9999}` in a single request.

### Contrast with the rest of the file

Every other privileged mutation in the same file is correctly gated:

| Endpoint | Line | Guard |
|---|---|---|
| `POST /ui/achievements/admin/definitions` | 66 | `require_root_session` |
| `PUT /ui/achievements/admin/definitions/{id}` | 87 | `require_root_session` |
| `DELETE /ui/achievements/admin/definitions/{id}` | 96 | `require_root_session` |
| `POST /ui/achievements/admin/seed` | 113 | `require_root_session` |
| **`POST /ui/achievements/admin/advance`** | **278** | **`require_ui_session` ← BUG** |

`require_root_session` (`app/auth/deps.py:273–278`) requires `user.role == Role.ROOT` and raises HTTP 403 otherwise. `require_ui_session` only validates that the caller has a live session, irrespective of role.

### How `advance_progress` works

`app/services/achievement_progress.py:31–89` calls `T.user_achievement_progress.update_item` to atomically add `delta` to `current_value`, then checks all achievement definitions for newly crossed thresholds and calls `_unlock_achievement` for each one. A sufficiently large delta will cross every threshold in a single request. There is no server-side cap on `delta` in the `AdvanceProgressIn` model — the field is declared as `delta: int = Field(default=1, ge=0)`, meaning the only constraint is that the value must be non-negative. An attacker can pass `delta=999999` to leap over every threshold at once.

After each unlock, `_unlock_achievement` calls `_update_leaderboard` which writes atomic increment updates to the `achievement_leaderboard` DynamoDB table for weekly, monthly, and all-time periods. It also calls `_emit_achievement_alert` which publishes an SSE event to the user's stream and writes a persistent alert record to DynamoDB. All of these side-effects fire immediately without any rate limiting.

### Dev vs prod behaviour

In dev mode (`DEV_MODE=1`) the session can be established via the dev-header fallback (`X-User-Sub` header) or a cookie-based HS256 JWT. In production, a valid Cognito JWT or signed `ui_access_token` cookie is required. In both environments, any successfully authenticated user reaches the endpoint because the auth check stops at "is there a valid session?" — no role inspection is performed. The `/ui/achievements/admin/` URL prefix suggests administrative intent, but the path prefix alone carries no authorization weight; only the FastAPI dependency (`Depends(...)`) enforces access control.

Note also that the endpoint's docstring reads "Advance progress for the authenticated user (dev/test helper)." The "dev/test helper" framing suggests the author intended to return to this and add a proper guard, but the guard was never added before the code was merged.

## 3. Impact / Exploit / Blast Radius

### Concrete exploit walkthrough

1. Attacker logs in via the normal registration/login flow — no elevated privileges required.
2. Attacker identifies metric keys from `GET /ui/achievements/definitions` (public to all authenticated users, line 103–109) or from the ENGAGE-001 defaults seeded by `seed_default_achievements`.
3. Attacker POSTs:
   ```
   POST /ui/achievements/admin/advance
   { "metric_key": "post_count", "delta": 10000 }
   ```
4. `advance_progress` fires, the attacker's `current_value` for `post_count` jumps to 10 000, all post-count achievements (`ach_first_post`, `ach_regular_poster`, `ach_prolific_creator`) are unlocked simultaneously.
5. Attacker repeats for every other metric key: `tip_count`, `reaction_count`, `posting_streak`, etc.
6. Leaderboard is updated by `_update_leaderboard` for each unlock, corrupting weekly/monthly/all-time rankings.

### Blast radius

| Dimension | Impact |
|---|---|
| **Achievement integrity** | All achievements can be self-awarded; "earned" state is permanently stored in DDB and cannot be trivially audited |
| **Leaderboard integrity** | `achievement_leaderboard` table poisoned; displayed ranks are meaningless |
| **User trust** | Gamification features lose credibility if abused at scale |
| **Alerts** | `_emit_achievement_alert` fires for every unlock, flooding the victim's (attacker's own) SSE stream and alert DDB table |
| **Scope** | Only self-advancement — the endpoint always uses `ctx["user_sub"]`, so one user cannot inflate another's counters directly |

**Worst case**: A coordinated script loops over all metric keys with high deltas, fills the leaderboard with fake top-ranked accounts, and exploits any downstream features that grant privileges based on achievement tier (e.g., higher withdrawal limits, creator-program eligibility).

Note: With `ACHIEVEMENTS_ENABLED=0` (the default per `app/core/settings.py:1903`) `advance_progress` returns `[]` immediately, so the impact is latent until the flag is enabled in production. This does not justify leaving the gate open.

## 4. Fix Design (code-level)

### Minimal fix

Change the dependency on line 278 of `app/routers/achievements.py`:

```python
# BEFORE (line 278)
async def admin_advance_progress(req: AdvanceProgressIn, ctx: dict = Depends(require_ui_session)):

# AFTER
async def admin_advance_progress(req: AdvanceProgressIn, ctx: dict = Depends(require_root_session)):
```

No other change needed — `require_root_session` returns an `AuthenticatedUser` dataclass, but the function only reads `ctx["user_sub"]`. Since `require_root_session` in `app/auth/deps.py:273–278` returns an `AuthenticatedUser` object (not a dict), the line `user_sub = ctx["user_sub"]` would break. Two sub-options:

**Option A** — Use the returned object directly:
```python
async def admin_advance_progress(req: AdvanceProgressIn, ctx: AuthenticatedUser = Depends(require_root_session)):
    user_sub = ctx.sub
    ...
```

**Option B** — Add a shim matching the existing dict contract used by other root-guarded endpoints that call `ctx["user_sub"]`:

Looking at the rest of the file, root-guarded endpoints do `ctx: dict = Depends(require_root_session)` and call `ctx["user_sub"]` (e.g., line 87 `ctx: dict = Depends(require_root_session)`). The `require_root_session` dependency already returns the `AuthenticatedUser` dataclass, but FastAPI allows arbitrary return types in dependencies. The existing callers at lines 66–113 also use `ctx: dict` — they must access `.sub`, not `["user_sub"]`. A brief check of the pattern in the file shows line 66–68 only accepts the context but never reads user_sub from it (creates global definitions). For consistency, match the pattern used by the `create_definition` endpoint:

```python
@router.post("/ui/achievements/admin/advance")
async def admin_advance_progress(
    req: AdvanceProgressIn,
    ctx: AuthenticatedUser = Depends(require_root_session),
):
    """Advance progress for a user. ROOT access only."""
    user_sub = ctx.sub
    from app.services.achievement_progress import advance_progress
    unlocked = advance_progress(user_sub, req.metric_key, delta=req.delta)
    return {"ok": True, "newly_unlocked": unlocked}
```

Import `AuthenticatedUser` at the top of `achievements.py`:
```python
from app.auth.deps import require_root_session, AuthenticatedUser
```

### Dev/Prod parity (SECOPS-007)

The `require_root_session` path uses the same `get_authenticated_user` resolver in both dev and prod. In dev, the session is established via the dev-header/cookie fallback, and the ROOT role is enforced by `enforce_root_role_invariant`. No mock-specific code is needed — the fix is uniform across environments.

`advance_progress` itself already guards on `_achievements_enabled()`, so with `ACHIEVEMENTS_ENABLED=0` the call is a no-op. The auth gate change is independent of the feature flag.

### Alternatives considered

- **Rate-limit the endpoint**: Does not solve the privilege problem.
- **Add `user_sub` parameter so admins can advance progress for arbitrary users**: A useful follow-on (for admin tooling) but orthogonal; the auth fix comes first.
- **Remove the endpoint entirely**: Overkill — it is a legitimate operator tool for testing and support; just needs correct access control.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline, fails-before / passes-after)

Add to `tests/test_achievements.py` (or a new `tests/test_achievements_access.py`):

```python
import pytest
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

ALICE_SUB = "alice@test.local"
ROOT_SUB  = "root@test.local"

def _session_headers(user_sub: str, role: str = "USER") -> dict:
    """Inject a dev-mode session cookie / X-User-Sub header for offline tests."""
    return {"X-User-Sub": user_sub, "X-User-Role": role}

# ── FAILS before fix, PASSES after fix ──────────────────────────────────────

def test_advance_progress_rejects_normal_user():
    """Any user with role USER must receive 403."""
    resp = client.post(
        "/ui/achievements/admin/advance",
        json={"metric_key": "post_count", "delta": 1},
        headers=_session_headers(ALICE_SUB, "USER"),
    )
    assert resp.status_code == 403, (
        "Expected 403 for non-root caller; got "
        f"{resp.status_code} — root guard is missing"
    )

def test_advance_progress_allows_root():
    """ROOT user must receive 200."""
    resp = client.post(
        "/ui/achievements/admin/advance",
        json={"metric_key": "post_count", "delta": 1},
        headers=_session_headers(ROOT_SUB, "ROOT"),
    )
    # 200 or 500 (DDB not available) is fine; 403 is not.
    assert resp.status_code != 403, (
        "ROOT caller must not be rejected by auth guard"
    )
```

Before the fix, `test_advance_progress_rejects_normal_user` will fail (the endpoint returns 200 for USER-role callers). After the fix it returns 403.

### Manual QA steps

1. Log in as a standard user (Alice). POST `/ui/achievements/admin/advance` → expect **403 Forbidden**.
2. Log in as root (`root.admin@testdev.local`). POST same endpoint → expect **200** with `newly_unlocked` list.
3. Confirm that `GET /ui/achievements` for Alice does NOT reflect the delta attempted in step 1.
4. Confirm leaderboard is unaffected.

### Metrics / observability

- Log `WARNING achievements.admin_advance: caller={user_sub} role={role}` on each successful call (successful = root allowed) so operations can audit unusual usage.
- Alert on >5 calls per minute from a single user_sub to this endpoint (anomalous even for root operators).

### Rollout & risks

| Dimension | Notes |
|---|---|
| **Effort** | S — one-line + import change |
| **Migration** | None required; DDB data is not altered |
| **Backward compat** | Any non-root caller that was relying on this endpoint (test scripts, CI) will break; update those callers to use a root-credentialed session |
| **Rollback** | Revert the single dependency swap; no DB migration |
| **Risk** | Very low — the only behaviour change is a stricter auth check |

**Sequencing**: Apply before enabling `ACHIEVEMENTS_ENABLED=1` in any environment. Because the flag defaults to `0`, this is latent but should be treated as HIGH priority before any production rollout of the gamification feature.

### Additional hardening (optional follow-on)

Once the auth gate is tightened to ROOT, consider adding a secondary `target_user_sub` parameter to the endpoint so that operators can advance progress for any user, not just themselves. The current implementation reads `user_sub = ctx["user_sub"]` (or after fix, `ctx.sub`), which means even a ROOT operator can only advance their own counters — limiting the endpoint's usefulness as a support tool. A follow-on change:

```python
class AdvanceProgressIn(BaseModel):
    metric_key: str = Field(..., min_length=1, max_length=64)
    delta: int = Field(default=1, ge=0, le=10000)   # add upper bound
    target_user_sub: Optional[str] = Field(default=None)  # ROOT can target any user

# In the handler:
target = req.target_user_sub or ctx.sub
unlocked = advance_progress(target, req.metric_key, delta=req.delta)
```

Adding `le=10000` to `delta` is a reasonable upper bound that prevents a single call from jumping an arbitrarily large distance while still allowing bulk operations during a data-migration scenario. These improvements can ship in the same PR as the auth fix since the scope is small.
