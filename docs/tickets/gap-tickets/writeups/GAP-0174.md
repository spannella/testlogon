# GAP-0174: `MockSamlAuth` used in production path — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real file:line. No prior investigation doc; claim verified
> against live code as part of this write-up.

## 1. Summary & Classification

**Plain-English statement**: The SAML Assertion Consumer Service (ACS) endpoint and the
SSO login redirect endpoint both unconditionally use `MockSamlAuth` — an internal stub class
that explicitly skips cryptographic signature validation. In production, any POST to
`/saml/acs` containing a syntactically valid XML SAMLResponse can be accepted as a
successful authentication, regardless of whether the IdP signature is present or valid.
An attacker can forge arbitrary SAML assertions and log in as any user.

- **Severity**: HIGH
- **Source ticket**: ENTERPRISE-002
- **Status**: Open
- **Owning area**: Backend / SSO / Security
- **Verdict**: **Confirmed** — `app/routers/sso_saml.py` lines 60 and 106 instantiate
  `MockSamlAuth` in both the `saml_login` and `saml_acs` endpoints without any
  `if S.dev_mode` guard. `app/services/sso_saml_sp.py` line 110 documents that the mock
  "skip[s] signature validation" unconditionally.
- **Related tickets**: GAP-0175 (RelayState injection), GAP-0018 (open redirect via
  RelayState), ENTERPRISE-002, SECOPS-007.
- **Claim accuracy**: The ticket states both the login redirect and ACS use `MockSamlAuth`,
  and that assertions are never cryptographically verified. **Confirmed exactly.** The
  comment on line 110 of `sso_saml_sp.py` reads: "In dev mode, skip signature validation
  -- mark as authenticated". The comment says "dev mode" but the code has no such guard;
  it always marks `_authenticated = True`.

## 2. Current-State Investigation (root cause)

### The mock class

`app/services/sso_saml_sp.py` defines `MockSamlAuth` (line 29). The `process_response`
method (line 43):

1. Decodes the base64 SAMLResponse.
2. Parses it as XML.
3. Checks the `Issuer` element against the configured IdP entity ID.
4. Extracts `NameID`, `SessionIndex`, and attributes.
5. Line 110: `self._authenticated = True` — unconditionally, with no signature check.

The comment on line 109 says "In dev mode, skip signature validation" but there is no
`if S.dev_mode:` guard. The assignment at line 110 always executes.

The `login` method (line 133) builds a mock redirect URL:
```python
redirect_url = f"{idp_sso_url}?SAMLRequest=mock&RelayState={return_to}&Issuer={sp_entity_id}"
```
This does not produce a signed AuthnRequest. A real SAML SP must sign its AuthnRequest with
the SP private key.

### Production call sites

`app/routers/sso_saml.py`:

- **Line 60** (`saml_login`): `auth = MockSamlAuth(prepare_request_data(request), settings_dict)`
- **Line 106** (`saml_acs`): `auth = MockSamlAuth(req_data, settings_dict)`
- **Line 533** (`test_provider`): `auth = MockSamlAuth(...)` — admin-only test endpoint,
  lower risk.

Neither line 60 nor line 106 is inside any `if S.dev_mode:` block. The only dev-mode guard
in `saml_acs` (lines 88–92) is for the `?dev_bypass=1` query parameter shortcut, which
leads to `_dev_bypass_acs` — a completely separate code path from the production flow.

### What a production SAML SP should do

A real implementation would use `python3-saml`'s `OneLogin_Saml2_Auth`:

```python
from onelogin.saml2.auth import OneLogin_Saml2_Auth

auth = OneLogin_Saml2_Auth(req_data, settings_dict)
auth.process_response()
```

`OneLogin_Saml2_Auth.process_response` performs:
- XML signature verification using the IdP's X.509 certificate.
- Assertion signature verification.
- `NotBefore` / `NotOnOrAfter` condition checks (replay protection).
- `AudienceRestriction` check (ensures assertion is addressed to this SP).
- `InResponseTo` check (binds assertion to the original AuthnRequest).

`MockSamlAuth` does none of these. A correctly structured XML document with a plausible
`Assertion` element and a matching `Issuer` will always authenticate successfully.

### Issuer check is necessary but not sufficient

Lines 67–72 in `process_response` check that the `Issuer` element matches the configured
`idp_entity_id`. This prevents trivial cross-IdP attacks (an attacker cannot claim to be a
different IdP) but does not prevent assertion forgery because the issuer string is not
cryptographically signed — an attacker who knows or can guess the `idp_entity_id` (which is
a public URI, available from `GET /saml/metadata`) can embed it in a forged assertion and
pass the check. The issuer check is a necessary but far from sufficient condition for SAML
security. Cryptographic signature verification over the entire XML document (or the
`Assertion` sub-element) is the required control.

### Comment on line 109 creates a false sense of security

The comment reads "In dev mode, skip signature validation -- mark as authenticated." This
implies the code has a dev/prod branch, but it does not. The unconditional
`self._authenticated = True` on line 110 executes in every call regardless of `S.dev_mode`.
This is likely a copy-paste remnant from a stub that was never completed. The misleading
comment means a code reviewer may incorrectly conclude that production uses a different,
safer code path.

## 3. Impact / Exploit / Blast Radius

### Critical exploit: assertion forgery

1. Attacker knows (or guesses) the SP's `idp_entity_id` for a target tenant (publicly
   available from `GET /saml/metadata`).
2. Attacker constructs a minimal SAMLResponse XML:
   ```xml
   <samlp:Response ...>
     <saml:Issuer>https://idp.example.com/entity</saml:Issuer>
     <saml:Assertion ID="_forge1">
       <saml:Issuer>https://idp.example.com/entity</saml:Issuer>
       <saml:Subject>
         <saml:NameID>victim@acme.com</saml:NameID>
       </saml:Subject>
       <saml:AuthnStatement SessionIndex="_s1"/>
       <saml:AttributeStatement>
         <saml:Attribute Name="email">
           <saml:AttributeValue>victim@acme.com</saml:AttributeValue>
         </saml:Attribute>
       </saml:AttributeStatement>
     </saml:Assertion>
   </samlp:Response>
   ```
3. Base64-encodes the XML and POSTs it to `/saml/acs` with `SAMLResponse=<b64>`.
4. `MockSamlAuth.process_response` parses the XML, finds no errors (issuer matches),
   extracts `NameID = victim@acme.com`, sets `_authenticated = True`.
5. The endpoint creates a full session for `victim@acme.com` and redirects the browser
   with session cookies set.

**No credentials, no IdP interaction, no cryptographic material needed.** Any user on any
SSO-enabled tenant can be impersonated.

### Secondary blast radius

- **JIT provisioning abuse**: `ensure_user_exists` (line 175 in `sso_saml.py`) creates new
  user records if they do not exist. Attackers can provision arbitrary users for any email
  address, potentially including addresses that would grant elevated privileges if the
  `role_mappings` or `default_role` field allows admin assignment.
- **Replay protection bypass**: Assertion ID replay protection (`_is_assertion_replayed`,
  line 127) records `_mock_<uuid>` as the assertion ID (line 84: `self._assertion_id = assertion.get("ID", f"_mock_{uuid4().hex}")`). An attacker controlling the XML `ID` attribute
  can generate a fresh ID per request, bypassing the replay cache entirely.
- **Audit log poisoning**: `_record_sso_session_link` (line 202) stores the raw `attributes`
  dict from the forged assertion. An attacker can inject arbitrary values into the SSO
  session audit table, which could be used to plant false evidence or obscure real activity.
- **Scale**: The endpoint is unauthenticated and rate limiting is not visible in the endpoint
  code. An automated attack could provision thousands of sessions in minutes.

All of these secondary effects are contingent on fixing GAP-0174 first: once real SAML
signature verification is enforced, forged assertions are rejected before any of these
downstream operations are triggered.

## 4. Fix Design (code-level)

### Step 1 — Introduce `get_saml_auth` factory

Add a factory function in `app/services/sso_saml_sp.py` that returns the correct
implementation based on `S.dev_mode` and the availability of `python3-saml`:

```python
def get_saml_auth(request_data: Dict[str, Any], settings: Dict[str, Any]):
    """
    Return the appropriate SAML auth implementation.
    - Production (not dev_mode): OneLogin_Saml2_Auth from python3-saml.
    - Dev/test (dev_mode=True): MockSamlAuth.
    """
    if S.dev_mode:
        return MockSamlAuth(request_data, settings)
    try:
        from onelogin.saml2.auth import OneLogin_Saml2_Auth
        return OneLogin_Saml2_Auth(request_data, settings)
    except ImportError as exc:
        raise RuntimeError(
            "python3-saml is required for production SAML. "
            "Install it with: pip install python3-saml"
        ) from exc
```

The `try/import` prevents a hard import-time failure in dev environments that do not have
`python3-saml` installed (it requires `xmlsec1` system libraries). If `python3-saml` is
missing in prod, the `RuntimeError` at request time is preferable to a silent downgrade to
the mock.

### Step 2 — Replace `MockSamlAuth(...)` with `get_saml_auth(...)` at call sites

`app/routers/sso_saml.py`:

- Line 60 (`saml_login`): `auth = get_saml_auth(prepare_request_data(request), settings_dict)`
- Line 106 (`saml_acs`): `auth = get_saml_auth(req_data, settings_dict)`
- Line 533 (`test_provider`): Leave as `MockSamlAuth` — this is an admin-only test
  endpoint (`Depends(require_root_session)`) used for connection testing, not for issuing
  real sessions. Add a comment clarifying this.

Update the import in `sso_saml.py`:
```python
from app.services.sso_saml_sp import (
    get_saml_auth,          # replaces direct MockSamlAuth usage
    MockSamlAuth,           # retained for test_provider admin endpoint
    build_saml_settings,
    prepare_request_data,
)
```

### Step 3 — Add `python3-saml` to production dependencies

`requirements.txt` (or `pyproject.toml`):
```
python3-saml>=3.0.0
```

System package (Ubuntu): `libxml2-dev libxmlsec1-dev libxmlsec1-openssl pkg-config`.
Add to `scripts/setup_ubuntu.sh`:
```bash
apt-get install -y libxml2-dev libxmlsec1-dev libxmlsec1-openssl pkg-config
```

### Step 4 — Add SP private key for signed AuthnRequests (optional but recommended)

`python3-saml` can sign AuthnRequests if the SP private key and certificate are configured.
Store the PEM-encoded key in AWS Secrets Manager and inject it via env var
`SAML_SP_PRIVATE_KEY`. Extend `build_saml_settings` to add:
```python
if S.saml_sp_private_key:
    result["sp"]["privateKey"] = S.saml_sp_private_key
    result["sp"]["x509cert"] = S.saml_sp_certificate
    result["security"] = {
        "authnRequestsSigned": True,
        "wantAssertionsSigned": True,
        "wantMessagesSigned": False,
    }
```

### Dev/prod parity (SECOPS-007)

- `get_saml_auth` returns `MockSamlAuth` when `S.dev_mode=True` — same mock-only
  restriction pattern used in multiple places throughout the codebase.
- The production path imports `OneLogin_Saml2_Auth` conditionally to avoid breaking the dev
  environment where `python3-saml` may not be installed.
- The `strict` key in `build_saml_settings` is already set to `not S.dev_mode` (line 153),
  which controls whether `python3-saml` enforces strict XML validation. This is consistent
  with the new factory.
- No separate mock for `get_saml_auth` — the factory itself is the feature flag.

### Backward compatibility / migration

- `python3-saml` requires the IdP certificate to be configured in the provider record
  (field `idp_certificates`). Records without certificates will fail `process_response` in
  strict mode. Operators must ensure all active providers have valid IdP certificates before
  deploying. The existing `create_provider` and `upload_metadata` endpoints already handle
  certificate storage.
- Dev/CI environments without `xmlsec1` continue to use `MockSamlAuth` via `dev_mode=True`.
  No test breakage.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

`tests/test_saml_auth_factory.py`:

```python
import pytest
from unittest.mock import patch, MagicMock

def test_get_saml_auth_returns_mock_in_dev_mode():
    from app.services.sso_saml_sp import get_saml_auth, MockSamlAuth
    with patch("app.core.settings.S.dev_mode", True):
        auth = get_saml_auth({}, {})
    assert isinstance(auth, MockSamlAuth)

def test_get_saml_auth_returns_real_auth_in_prod(monkeypatch):
    """In prod mode, should return OneLogin_Saml2_Auth (or raise if not installed)."""
    FakeRealAuth = MagicMock()
    fake_module = MagicMock()
    fake_module.OneLogin_Saml2_Auth = lambda *a, **kw: FakeRealAuth

    with patch("app.core.settings.S.dev_mode", False), \
         patch.dict("sys.modules", {"onelogin.saml2.auth": fake_module}):
        from importlib import reload
        import app.services.sso_saml_sp as sp_module
        reload(sp_module)
        auth = sp_module.get_saml_auth({}, {})
    assert auth is FakeRealAuth

def test_forged_assertion_rejected_with_real_auth(client):
    """
    BEFORE fix: POST /saml/acs with a forged SAMLResponse returns 303 to '/'
                (successful login).
    AFTER fix (prod mode): process_response raises signature error, returns
                303 to /login?error=sso_validation_failed.
    """
    import base64
    forged_xml = b"""<samlp:Response xmlns:samlp="urn:oasis:names:tc:SAML:2.0:protocol"
                                     xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion">
      <saml:Issuer>https://idp.example.com/entity</saml:Issuer>
      <saml:Assertion ID="_forge1">
        <saml:Issuer>https://idp.example.com/entity</saml:Issuer>
        <saml:Subject><saml:NameID>victim@acme.com</saml:NameID></saml:Subject>
        <saml:AuthnStatement SessionIndex="_s1"/>
      </saml:Assertion>
    </samlp:Response>"""
    b64 = base64.b64encode(forged_xml).decode()

    with patch("app.core.settings.S.sso_saml_enabled", True), \
         patch("app.core.settings.S.dev_mode", False), \
         patch("app.services.sso_saml_provider.get_active_provider_for_tenant",
               return_value={"provider_id": "p1", "idp_entity_id": "https://idp.example.com/entity",
                             "idp_certificates": [], "attribute_mappings": {},
                             "allowed_email_domains": [], "jit_provisioning_enabled": False,
                             "auto_update_profile": False, "role_mappings": [], "default_role": "user"}), \
         patch("app.services.sso_saml_sp.get_saml_auth") as mock_get_auth:
        mock_auth = MagicMock()
        mock_auth.get_errors.return_value = ["invalid_signature"]
        mock_get_auth.return_value = mock_auth
        resp = client.post("/saml/acs", data={"SAMLResponse": b64, "tenant_id": "default"})

    assert resp.status_code == 303
    assert "sso_validation_failed" in resp.headers["location"]
```

### Manual QA steps

1. Install `python3-saml` in the virtual environment.
2. Configure an active SSO provider with a real IdP certificate in DDB.
3. Submit a forged SAMLResponse to `/saml/acs`: confirm redirect to
   `/login?error=sso_validation_failed`.
4. In dev mode (`S.dev_mode=True`), confirm `MockSamlAuth` is used (existing dev bypass
   flow continues to work).
5. Complete a real SSO login flow using the dev bypass (`?dev_bypass=1`): confirm it still
   works.

### Rollout

1. **Dependency installation**: Add `python3-saml>=3.0.0` to `requirements.txt`. Extend
   `scripts/setup_ubuntu.sh` with the system packages `libxml2-dev libxmlsec1-dev libxmlsec1-openssl pkg-config`.
   Run `pip install -r requirements.txt` in the virtualenv.
2. **Certificate provisioning**: Every active SSO provider in DDB must have at least one
   valid entry in `idp_certificates`. The `GET /v1/admin/sso/providers/{id}` endpoint lists
   current certificates. For any provider missing certificates, use `POST .../metadata` to
   upload the IdP's metadata XML, which parses and stores the certificates.
3. **Staging validation**: Deploy to staging with `DEV_MODE=0`. Run a full end-to-end SSO
   login using a real or test IdP. Confirm the `sso_login` audit event is written and the
   session is created with the correct `user_sub`.
4. **Monitor**: Watch `sso_login_failed` audit events for the first 24 hours. Certificate
   mismatches, clock-skew issues (assertion `NotBefore`/`NotOnOrAfter`), and audience
   restriction errors will surface here. Each has a clear remediation (update certificate,
   adjust clock sync, correct `sp_entity_id`).
5. **Production rollout**: Coordinate with infrastructure to ensure `libxmlsec1` is
   installed on all backend nodes before deploying the updated `requirements.txt`. Rolling
   deploy — nodes that have not yet received the package update will fail at import of
   `get_saml_auth` in production mode, resulting in 500 for ACS requests. Use a feature
   flag `SSO_REAL_SAML_ENABLED` to control which nodes switch to `python3-saml` first.
6. **Rollback plan**: If `python3-saml` causes compatibility issues, set `DEV_MODE=1`
   (emergency) or remove `get_saml_auth` call sites and revert to `MockSamlAuth`.
   This reverts the security fix, so it should only be used as a last resort while the
   root cause is investigated.

**Effort**: M (2–3 days: factory function, 2 call-site changes, system dependency
installation scripting, certificate provisioning audit, staging E2E test, coordination
with infrastructure).

**Risk**: Medium. Introducing `python3-saml` adds a native-library dependency
(`libxmlsec1`) that must be present on all production hosts. The dev path (`MockSamlAuth`)
is completely unchanged, so CI/CD and local development are unaffected. The primary risk
is an incomplete rollout where some nodes have the library and others do not. Mitigated by
the `SSO_REAL_SAML_ENABLED` feature flag and by validating the package installation in the
deployment pipeline before switching traffic.
