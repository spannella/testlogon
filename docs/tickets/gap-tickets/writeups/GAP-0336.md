# GAP-0336: Refresh Endpoint Is Still a No-Op Placeholder — Remediation Write-up

> Source ticket: PLATFORM-019 · Severity: HIGH · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** `POST /ui/analytics/refresh` is a rate-limited no-op. It updates an in-memory timestamp, constructs a response string, and returns immediately without computing or writing any analytics data to DynamoDB. A creator who clicks the "Refresh analytics" button triggers no rollup whatsoever; the dashboards continue to show whatever stale data existed before the call.

**Claim verdict: Confirmed.** The endpoint at `app/routers/creator_analytics.py:303–329` contains an explicit comment — "In a production system this would trigger an async rollup job. For now it serves as a rate-limited placeholder." — and returns `AnalyticsRefreshOut` immediately on line 325 without invoking any computation.

**Severity and area.** HIGH / Analytics & Creator Monetisation. Affects every creator who attempts to refresh their analytics dashboard. The issue is compounded by two companion gaps (listed in `docs/tickets/gaps/PLATFORM-019.md`): the `analytics_events` raw event service does not exist and the `analytics_rollup_engine.py` computation engine is absent. GAP-0336 is the final linking piece: even if both underlying services are built, the refresh endpoint must call them or creator-triggered refreshes remain silent.

**Related tickets.** PLATFORM-019 (parent), GAP-0337 (zero event instrumentation — raw data source is missing), companion PLATFORM-019 gaps "analytics_events.py service not implemented" and "analytics_rollup_engine.py not implemented". GAP-0336 has a hard dependency on both those companion gaps being resolved first, because it calls `compute_daily_rollups()` which must exist before this endpoint can be wired.

## 2. Current-State Investigation (root cause)

### The no-op path in full

```python
# app/routers/creator_analytics.py:303–329
@router.post("/refresh", response_model=AnalyticsRefreshOut)
def analytics_refresh(session=Depends(require_ui_session)):
    user_id = session["user_sub"]
    now = now_ts()

    last_refresh = _refresh_timestamps.get(user_id, 0)
    if now - last_refresh < _REFRESH_COOLDOWN_SECONDS:
        raise HTTPException(
            status_code=429,
            detail="Analytics refresh rate limit exceeded. Try again in a few minutes.",
        )

    _refresh_timestamps[user_id] = now
    lookback = S.analytics_rollup_lookback_days

    # The refresh endpoint returns success immediately.
    # In a production system this would trigger an async rollup job.
    # For now it serves as a rate-limited placeholder.
    return AnalyticsRefreshOut(
        ok=True,
        message=f"Rollup refresh triggered for {lookback} days",
        days_refreshed=lookback,
    )
```

The endpoint:
1. Checks and updates an in-process dictionary `_refresh_timestamps` for rate-limiting (this dict is defined earlier in the file and is not persisted to DynamoDB — it resets on every backend restart, meaning a creator can bypass the rate limit by simply restarting the server in dev).
2. Reads `S.analytics_rollup_lookback_days` (defaults to `3` in `app/core/settings.py:1753` — another separate gap notes this should default to 90).
3. Returns a fabricated success response with `ok=True` and a message string that never reflects real work done.

### What is missing

The router imports `upsert_daily_rollup` and `upsert_summary_sentinel` from `app/services/creator_analytics.py` (line 49–50), but neither is called from the refresh handler. The refresh handler does not import or call any rollup computation function. The `app/services/` directory contains `creator_analytics.py` (which can write individual rollup rows) but no `analytics_rollup_engine.py` — there is no `compute_daily_rollups()` function anywhere in the codebase.

### Rate-limit state loss

`_refresh_timestamps` is an in-process dict. In production with multiple uvicorn workers, each worker has its own independent copy. A creator can call `/refresh` up to one time per worker per cooldown window — effectively multiplying the rate limit by the worker count. In dev this is harmless (single worker enforced by `--workers 1`), but documents another gap in the endpoint's design.

### Dev vs prod behaviour

The no-op manifests identically in both environments: the response always returns `200 OK` with `ok=True` and the analytics tables are never written to. No mock code path differs here; the placeholder comment is present unconditionally.

## 3. Impact / Exploit / Blast Radius

**User-facing impact.** Every creator who presses "Refresh" on their analytics dashboard receives a `200 OK` with `ok=true` indicating success, while the underlying analytics tables (`analytics_rollups`) remain unchanged. There is no error to investigate; the creator has no way to know the refresh did nothing.

**Dashboard data staleness.** The `GET /ui/analytics/overview`, `/revenue`, `/views`, `/subscribers`, `/top-content`, and `/engagement` endpoints all read from `T.analytics_rollups` via `_query_rollups()`. Since no real data is ever written into that table through normal operation (the `upsert_daily_rollup` function exists but is never called from any router — that is GAP-0337's scope), these endpoints return aggregations of zero or empty rows. The refresh endpoint was the intended mechanism for creators to pull fresh data on demand; it does nothing.

**Financial implications.** Creators cannot validate their revenue, subscriber, or tip metrics. Any creator relying on analytics to make pricing decisions (e.g., locked post price, subscription tier) is operating blind. This is a trust and retention risk rather than a direct financial exploit.

**Security.** No security exploit is possible through this endpoint. The rate-limit bypass via worker-count multiplication is negligible in dev; in production it is not a security issue but a correctness one.

## 4. Fix Design (code-level)

### Prerequisite: `analytics_rollup_engine.py` must exist

The fix for this endpoint depends on a `compute_daily_rollups(from_date: str, to_date: str)` function in `app/services/analytics_rollup_engine.py`. That function is the subject of a companion PLATFORM-019 gap. For this write-up we define its expected interface:

```python
# app/services/analytics_rollup_engine.py (to be created as part of companion gap)
from datetime import datetime, timedelta, timezone

def compute_daily_rollups(from_date: str, to_date: str) -> Dict[str, int]:
    """Recompute daily rollup rows for all creators with activity in [from_date, to_date].

    Each rollup row is written via upsert_daily_rollup(). Returns a summary
    dict with keys 'creators_refreshed' and 'rows_written'.
    """
    ...
```

### Change 1: Wire the refresh endpoint

Replace the placeholder body in `app/routers/creator_analytics.py:319–329`:

```python
# app/routers/creator_analytics.py (updated analytics_refresh handler)
from app.services.analytics_rollup_engine import compute_daily_rollups  # new import
from datetime import datetime, timedelta, timezone

@router.post("/refresh", response_model=AnalyticsRefreshOut)
def analytics_refresh(session=Depends(require_ui_session)):
    """Trigger an on-demand analytics refresh for the authenticated creator."""
    user_id = session["user_sub"]
    now = now_ts()

    last_refresh = _refresh_timestamps.get(user_id, 0)
    if now - last_refresh < _REFRESH_COOLDOWN_SECONDS:
        raise HTTPException(
            status_code=429,
            detail="Analytics refresh rate limit exceeded. Try again in a few minutes.",
        )

    _refresh_timestamps[user_id] = now
    lookback = S.analytics_rollup_lookback_days

    today = datetime.now(timezone.utc).date()
    dates = [
        (today - timedelta(days=i)).isoformat()
        for i in range(lookback)
    ]
    from_date = dates[-1]  # oldest
    to_date = dates[0]     # today

    try:
        summary = compute_daily_rollups(from_date, to_date)
        rows_written = summary.get("rows_written", 0)
    except Exception:
        logger.exception("analytics_refresh: rollup computation failed for %s", user_id)
        rows_written = 0

    return AnalyticsRefreshOut(
        ok=True,
        message=f"Rollup refreshed {lookback} days ({from_date} to {to_date}); {rows_written} rows written",
        days_refreshed=lookback,
    )
```

### Change 2: Persist rate-limit state to DynamoDB (optional, medium priority)

Replace the in-process `_refresh_timestamps` dict with a DynamoDB-backed record keyed by `USER#{user_sub}` in `T.account_state` (or a dedicated small table). This ensures the rate limit is honoured across workers and across restarts. The `_REFRESH_COOLDOWN_SECONDS` check becomes:

```python
# read last_refresh from DDB instead of in-process dict
item = T.account_state.get_item(Key={"user_sub": user_sub}).get("Item") or {}
last_refresh = int(item.get("analytics_last_refresh_ts", 0))
```

This change is independent of the core fix and can be deferred.

### Dev/Prod parity (SECOPS-007)

`compute_daily_rollups` will write to `T.analytics_rollups` (DynamoDB). In dev this is DynamoDB Local on port 8001; in production it is AWS DynamoDB. No AWS-specific path differs. The refresh endpoint itself requires no mock bypass or environment flag — the computation is pure DynamoDB read/write. The in-process rate-limit dict is a known limitation in both environments; the DDB-backed upgrade (Change 2) closes the multi-worker gap in production.

### Backward compatibility

`AnalyticsRefreshOut` already contains `ok`, `message`, and `days_refreshed` fields (`app/models.py`). No model changes are needed. The response contract is unchanged from the caller's perspective; only the message string becomes more informative.

### Alternatives considered

- **Queue to SQS / async worker:** Correct for large-scale production but introduces infrastructure not present in the dev stack. An in-process synchronous call to `compute_daily_rollups` is acceptable for the `lookback_days` range (3–90 days of data for one creator) and matches the project's existing pattern for on-demand compute. Can be upgraded to async task submission later.
- **No fix, document as known gap:** Unacceptable. The endpoint tells callers `ok=True`, establishing a false contract that will delay discovery of the deeper pipeline gaps.

## 5. Testing, Verification & Rollout

### Regression test (`tests/test_gap_0336_analytics_refresh.py`)

```python
# tests/test_gap_0336_analytics_refresh.py
"""
Fails BEFORE fix: endpoint returns ok=True but writes no rollup rows.
Passes AFTER fix: endpoint calls compute_daily_rollups and rows are written.
"""
from unittest.mock import patch, MagicMock
import pytest


def test_refresh_is_placeholder_before_fix(client, alice_session_headers):
    """BEFORE: endpoint returns ok=True with no computation side-effect."""
    with patch("app.services.creator_analytics.upsert_daily_rollup") as mock_upsert:
        resp = client.post("/ui/analytics/refresh", headers=alice_session_headers)
    assert resp.status_code == 200
    assert resp.json()["ok"] is True
    # Confirm no rollup was actually written — this is the broken state
    mock_upsert.assert_not_called()  # passes before fix (nothing called)


def test_refresh_calls_compute_daily_rollups_after_fix(client, alice_session_headers):
    """AFTER: endpoint invokes compute_daily_rollups and the result is reflected."""
    mock_summary = {"creators_refreshed": 1, "rows_written": 3}
    with patch(
        "app.routers.creator_analytics.compute_daily_rollups",
        return_value=mock_summary,
    ) as mock_compute:
        resp = client.post("/ui/analytics/refresh", headers=alice_session_headers)
    assert resp.status_code == 200
    data = resp.json()
    assert data["ok"] is True
    assert "3 rows written" in data["message"]
    mock_compute.assert_called_once()
    args = mock_compute.call_args
    from_date, to_date = args[0]
    assert from_date < to_date  # sanity: from is before to


def test_refresh_rate_limit_enforced(client, alice_session_headers):
    """Rate limit returns 429 on second call within cooldown."""
    with patch("app.routers.creator_analytics.compute_daily_rollups", return_value={}):
        resp1 = client.post("/ui/analytics/refresh", headers=alice_session_headers)
        resp2 = client.post("/ui/analytics/refresh", headers=alice_session_headers)
    assert resp1.status_code == 200
    assert resp2.status_code == 429
```

**Fails-before / passes-after contract:**
- `test_refresh_is_placeholder_before_fix` passes today (no `compute_daily_rollups` import exists, so `mock_upsert.assert_not_called()` is trivially true).
- `test_refresh_calls_compute_daily_rollups_after_fix` fails today with `AttributeError` because `app.routers.creator_analytics` has no attribute `compute_daily_rollups`; it passes after the fix imports and calls the function.
- `test_refresh_rate_limit_enforced` passes both before and after (rate-limiting logic already works).

### Observability

Add a structured log line in the refresh handler with `rows_written`, `from_date`, `to_date`, and `duration_ms`. Alert if `rows_written == 0` on a successful `200` response (indicates the rollup engine ran but found no data — likely an instrumentation gap from GAP-0337).

### Rollout & risks

- **Dependency risk:** This fix is inert until `compute_daily_rollups` exists. Deploy the rollup engine (companion gap) first, then deploy this wiring change.
- **Latency risk:** Synchronous rollup computation for 90 days of data could take several seconds. Add a 10-second timeout around the `compute_daily_rollups` call and return `ok=true` with `rows_written=0` on timeout (the task can be retried). Consider upgrading to async background task in a follow-up.
- **Rate-limit persistence:** If deploying to multi-worker production before Change 2 (DDB-backed rate limit), each worker enforces its own 5-minute window. Acceptable for initial rollout.
- **Rollback:** Reverting the import and restoring the placeholder comment returns to the current no-op state with no data loss.
- **Effort:** S — one import, one function call, updated message string, test file.
- **Sequence:** (1) Create `analytics_events.py` service, (2) create `analytics_rollup_engine.py`, (3) apply this fix, (4) add instrumentation (GAP-0337).
