# GAP-0282: `_scan_availability_items` Uses a Full-Table Scan with a `begins_with` Filter on PK — Remediation Write-up

## 1. Summary & Classification

**Ticket**: GAP-0282 | **Source**: KYC-019 | **Severity**: HIGH | **Status**: Open | **Effort**: M
**Owning area**: KYC — case assignment workload management (`app/services/kyc_case_assignment.py`)

`_scan_availability_items` in the `KycCaseAssignmentService` class (lines 161–176 of `app/services/kyc_case_assignment.py`) retrieves all admin availability records from the `kyc_cases` DynamoDB table. Because `begins_with` applied to a partition key can only be expressed as a `FilterExpression` rather than a `KeyConditionExpression`, the method issues a full-table `Scan`, reading every item in the table before DynamoDB applies the filter. On a live system the `kyc_cases` table contains thousands of case items (each with multiple sub-items: META, AUDIT, CONFIG, SLA, MPOLL rows). Every call to `list_admin_workloads`, `workload_dashboard`, `get_admin_availability`, or `auto_assign` triggers this expensive scan on the critical path.

The scan does loop `LastEvaluatedKey` correctly (the fix partially proposed in the ticket to loop until exhausted is already in place). The core problem is not incompleteness but the O(N-table) cost. The ticket states "returns incomplete results when more than one 1 MB page of non-ADMIN items exists" — with the loop in place that specific incompleteness risk is mitigated; however, the fundamental O(N) scan-of-entire-table problem, the latency cost, and the RCU consumption remain unacceptable in production.

**Verdict**: Confirmed with a correction. The original ticket claim that results can be incomplete is partially inaccurate today because the current code does correctly loop `LastEvaluatedKey` (line 169–175). The real deficiency is the O(N-table) full-scan on the critical path, not missing pages. The write-up corrects this.

**Related tickets**: GAP-0283 (companion scan in `_scan_active_cases`), GAP-0024 (full-table scan pattern in case listing).

## 2. Current-State Investigation (root cause)

### The offending method

`app/services/kyc_case_assignment.py` lines 161–176:

```python
def _scan_availability_items(self) -> list[dict[str, Any]]:
    out: list[dict[str, Any]] = []
    ekey: dict[str, Any] | None = None
    while True:
        kwargs: dict[str, Any] = {
            "FilterExpression": "begins_with(pk, :p) AND sk = :s",
            "ExpressionAttributeValues": {":p": "ADMIN#", ":s": "AVAILABILITY"},
        }
        if ekey:
            kwargs["ExclusiveStartKey"] = ekey
        resp = self._table.scan(**kwargs)   # ← full-table scan
        out.extend(resp.get("Items", []))
        ekey = resp.get("LastEvaluatedKey")
        if not ekey:
            break
    return out
```

DynamoDB `FilterExpression` is applied **after** reading up to 1 MB of items per page. Every page of the `kyc_cases` table — which includes `KYC#{case_id}#META`, `KYC#{case_id}#SUBMISSION`, `AUDIT#ASSIGN#{case_id}#{ts}#*`, `CONFIG#SLA#{tier}`, and all other items — must be read and transmitted before the filter discards non-`ADMIN#` rows. With thousands of cases in production each `list_admin_workloads` call will scan dozens of pages, consuming thousands of RCUs and adding seconds to response time.

### Why `begins_with` on PK cannot be a KeyCondition

DynamoDB `KeyConditionExpression` requires the full partition-key value to be specified with `=`. The `begins_with` function is only supported on sort keys within a `KeyConditionExpression`. Applying `begins_with` to a partition key forces the expression to be a `FilterExpression`, meaning DynamoDB reads all items before filtering. This is a fundamental DynamoDB constraint and not something the application can work around by tuning the query syntax.

### Call sites and frequency

`_scan_availability_items` is called by:
- `list_admin_workloads` (line 246) — called by `workload_dashboard` and `_eligible_admins`
- `_eligible_admins` (line 285) — called by both `auto_assign` and `escalate_case`

`auto_assign` is invoked on every new KYC submission. `escalate_case` is called by `run_sla_escalation_sweep` which fires every 5 minutes in production (line 730 of the same file). This means `_scan_availability_items` runs at minimum every 5 minutes regardless of submission volume. In a production system with 100+ admins and thousands of cases, each scan consumes significant RCUs: a table with 10,000 items at an average of 400 bytes each fits roughly 2,500 items per 1 MB page, meaning 4 full pages are read and discarded for every 20 `ADMIN#` availability records found. The ratio of wasted reads to useful reads is approximately 500:1.

### What is present vs missing

Present: correct `LastEvaluatedKey` pagination loop (the ticket's "returns incomplete results when more than one 1 MB page of non-ADMIN items exists" claim is therefore inaccurate for the current code). The loop was added, presumably at implementation time, ensuring all availability records are eventually returned regardless of table size.

Missing: a GSI or dedicated table that allows O(A) lookup of availability items (where A is the number of admin records, typically tens to hundreds) without performing an O(N) scan across all case items in the shared table.

## 3. Impact / Exploit / Blast Radius

**Availability**: Each `auto_assign` call (triggered on every KYC submission) scans the entire `kyc_cases` table. In a production environment with 10,000 case items (each case has at least a META row plus audit rows), a single auto-assign call may read 30–100 DynamoDB pages before collecting the ~20 `ADMIN#*` availability records. At 100 submissions/day this becomes 3,000–10,000 full-page reads per day just for availability lookups.

**Cost**: DynamoDB provisioned RCUs for scans are consumed at full item size. At scale this easily exceeds the provisioned throughput for the table and causes `ProvisionedThroughputExceededException` — all KYC submissions fail to be assigned, silently degrading the admin queue.

**Latency**: A table scan with 50+ pages takes 2–10 seconds in production. The `auto_assign` path is synchronous on the submission critical path, meaning each KYC submission is blocked for seconds.

**No security or data-integrity blast radius**: This is a performance/availability gap, not a confidentiality or integrity issue. All data returned is correct; the cost is purely computational. Admin availability records cannot be accessed by unauthorized users through this path — the API endpoint requires admin-role authentication before calling `list_admin_workloads`.

**Degraded admin experience**: When the auto-assign path times out due to scan overload, new KYC submissions arrive in the queue with no assigned reviewer. Admins must manually claim cases, increasing review latency and violating the SLA commitments tracked by the companion SLA checker (GAP-0283).

## 4. Fix Design (code-level)

### Approach 1 (Preferred): Add a sparse GSI keyed on `entity_type`

Admin availability items already have `entity_type = "kyc_admin_availability"` (set in `set_admin_availability` at line 219). Adding a GSI on `entity_type` + `admin_sub` allows a targeted `Query` operation. This avoids a dedicated secondary table while keeping the single-table design.

**DynamoDB change** (`scripts/local-ddb-init.py`, the `kyc_cases` table definition at line 114):

```python
TableDef(
    _resolve_table_name(S.kyc_cases_table_name, "kyc_cases"),
    "pk",
    "sk",
    gsi=[
        {"index_name": S.kyc_cases_owner_index_name, ...},
        {"index_name": S.kyc_cases_status_index_name, ...},
        {"index_name": S.kyc_pii_audit_accessor_index_name, ...},
        # NEW:
        {
            "index_name": "entity-type-index",
            "partition_key": "entity_type",
            "sort_key": "admin_sub",
        },
    ],
    attr_types={"gsi_pii_accessor_sk": "N"},
),
```

Add a settings key for the new index name (follows the existing pattern in `app/core/settings.py`):

```python
# app/core/settings.py, near line 1166
kyc_cases_entity_type_index_name: str = os.environ.get(
    "KYC_CASES_ENTITY_TYPE_INDEX_NAME", "entity-type-index"
)
```

**Service change** (`app/services/kyc_case_assignment.py`):

Replace `_scan_availability_items` (lines 161–176) with a targeted GSI query:

```python
def _scan_availability_items(self) -> list[dict[str, Any]]:
    """Query admin availability records via the entity-type GSI (O(1) page count)."""
    index_name = S.kyc_cases_entity_type_index_name
    out: list[dict[str, Any]] = []
    ekey: dict[str, Any] | None = None
    while True:
        kwargs: dict[str, Any] = {
            "IndexName": index_name,
            "KeyConditionExpression": "entity_type = :et",
            "ExpressionAttributeValues": {":et": "kyc_admin_availability"},
        }
        if ekey:
            kwargs["ExclusiveStartKey"] = ekey
        resp = self._table.query(**kwargs)
        out.extend(resp.get("Items", []))
        ekey = resp.get("LastEvaluatedKey")
        if not ekey:
            break
    return out
```

This transforms an O(N-table) scan into an O(A) query where A is the number of admin availability records (typically ~10–100, not thousands).

### Approach 2 (Minimal / fallback): Dedicated `kyc_admin_availability` table

If adding a GSI to the shared `kyc_cases` table is undesirable (e.g., table is already at its GSI limit of 20), create a standalone `kyc_admin_availability` table with PK = `admin_sub` and SK = `AVAILABILITY`. The `_scan_availability_items` method is then replaced with a full-table scan of the small dedicated table, which has a predictable, bounded size.

Approach 1 is preferred because it avoids adding a new table and migration of existing availability items.

### Dev/Prod parity (SECOPS-007)

GSI additions apply identically in dev (DynamoDB Local via `scripts/local-ddb-init.py`) and production (AWS DynamoDB via CloudFormation/CDK). The table re-creation on `just restart` will pick up the new GSI definition automatically. No mock-specific code path is needed.

### Migration

Existing `ADMIN#{sub}#AVAILABILITY` items already store `entity_type = "kyc_admin_availability"` (written by `set_admin_availability` since initial implementation). The new GSI will index them automatically once created; no item re-write is needed. For production, the GSI backfill is automatic (online index creation, no downtime). The service should treat a missing GSI gracefully by falling back to the scan approach during the backfill window — this can be gated on a feature flag `KYC_AVAILABILITY_GSI_ENABLED=true` that defaults to `false` until the backfill completes.

## 5. Testing, Verification & Rollout

import pytest
from unittest.mock import MagicMock, call, patch
from app.services.kyc_case_assignment import KycCaseAssignmentService

def test_scan_availability_items_paginates():
    """Ensure LastEvaluatedKey pagination is exhausted."""
    svc = KycCaseAssignmentService()
    mock_table = MagicMock()

        {"Items": [{"admin_sub": "a1"}], "LastEvaluatedKey": {"pk": "ADMIN#a1", "sk": "AVAILABILITY"}},

### Observability

- Add a log line at `INFO` level in `_scan_availability_items` counting how many items were returned per invocation and whether the GSI or scan path was used: `kyc.availability.fetch method=gsi|scan items={n} pages={p}`.
- Emit a Prometheus counter `kyc_availability_fetch_pages_total{method="gsi"}` and `kyc_availability_fetch_pages_total{method="scan"}` to track how many DDB pages are consumed per call. After the fix, the GSI path should consistently show 1 page for any realistic admin fleet size (< 200 admins).
- Add a CloudWatch alarm on the `kyc_cases` table's `ConsumedReadCapacityUnits` metric. After the fix, each call to `list_admin_workloads` should contribute only ~1–5 RCUs (the GSI query for `entity_type = "kyc_admin_availability"`) rather than the hundreds previously consumed by the full-table scan.
- During the rollout window where both paths exist (controlled by `KYC_AVAILABILITY_GSI_ENABLED`), log `method=scan` so production operators can confirm the flag toggle takes effect before the legacy scan path is removed.

### Rollout

- Add feature flag `KYC_AVAILABILITY_GSI_ENABLED` (default `false`); switch to `query` path only when set to `true`.
- Deploy to production with flag `false` → create GSI → wait for backfill completion (CloudWatch metric `ConsumedWriteCapacityUnits` on the GSI returns to 0) → set flag `true` → verify → remove flag.
- Rollback: set `KYC_AVAILABILITY_GSI_ENABLED=false` to revert to the existing scan.
- Risk: low. The correctness of returned data is unchanged; only the access pattern changes.

**Effort**: M — approximately 1–2 developer-days including schema change, service update, tests, and staged rollout. The most time-consuming step is the production GSI backfill window (30–60 minutes for large tables), during which the feature flag must remain at `false` and the legacy scan continues to serve requests. Coordination with the on-call team to monitor the backfill and execute the flag flip is recommended.
