# GAP-0039: No Max-5-Accounts-Per-User Rate Limit on Ad Account Creation — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: The `create_ad_account` service function at `app/services/ad_accounts.py:14` immediately performs a `put_item` without first checking how many ad accounts the requesting user already owns. Nothing in the router (`app/routers/ads.py:108`) adds a pre-check either. A single authenticated user can submit an unlimited number of account creation requests, flooding the admin review queue with `pending_review` entries.

- **Severity**: HIGH
- **Source ticket**: ADS-001
- **Status**: Open
- **Owning area**: Ads Platform / Ad Account Management
- **Effort**: S
- **Claim verdict**: CLAIM OK — confirmed. `create_ad_account` at `app/services/ad_accounts.py:14–32` calls `T.ad_accounts.put_item` with no prior count check. `list_accounts_by_owner` at line 40 exists and could be used for the check. Neither the service function nor the router endpoint at `app/routers/ads.py:107–109` adds a limit guard.

**One-line impact**: A malicious user or a buggy frontend can create thousands of ad accounts, saturating the admin review queue and preventing legitimate accounts from being reviewed promptly.

**Related tickets**: ADS-001 (source), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### The service function

`app/services/ad_accounts.py:14–32`:

```python
def create_ad_account(owner_sub: str, data: AdAccountCreateIn) -> dict:
    """Create a new advertiser account in pending_review status."""
    account_id = f"adacct_{uuid.uuid4().hex[:12]}"
    ts = now_ts()
    item = {
        "pk": f"ACCT#{account_id}",
        "sk": "META",
        "account_id": account_id,
        "owner_sub": owner_sub,
        "company_name": data.company_name,
        "billing_email": data.billing_email,
        "status": "pending_review",
        "balance_cents": 0,
        "lifetime_spend_cents": 0,
        "created_at": ts,
        "updated_at": ts,
    }
    T.ad_accounts.put_item(Item=item)
    return item
```

No count check. No limit guard. `put_item` writes immediately.

### The router endpoint

`app/routers/ads.py:107–109`:

```python
@router.post("/accounts", status_code=201)
async def create_account_endpoint(body: AdAccountCreateIn, ctx=Depends(require_ui_session)):
    return create_ad_account(ctx["user_sub"], body)
```

The endpoint enforces authentication (`require_ui_session`) but adds no per-user account limit.

### The available helper

`app/services/ad_accounts.py:40–46`:

```python
def list_accounts_by_owner(owner_sub: str) -> list[dict]:
    resp = T.ad_accounts.query(
        IndexName="ByOwner",
        KeyConditionExpression=Key("owner_sub").eq(owner_sub),
        ScanIndexForward=False,
    )
    return resp.get("Items", [])
```

`list_accounts_by_owner` returns all accounts owned by a given user via the `ByOwner` GSI. This function can be called before `put_item` to count existing accounts.

### Why the limit is 5

The source ticket ADS-001 specifies a maximum of 5 accounts per user. This aligns with common ad platform design: a user may legitimately manage multiple brands or legal entities, but the cardinality is naturally bounded. Five is sufficient for legitimate use and prevents queue flooding.

### Current behavior under abuse

A script running `POST /ui/ads/accounts` in a loop with different `company_name` values:
- Creates N accounts per iteration (N unlimited).
- Each account starts in `pending_review` status.
- Admin queue (`GET /ui/admin/ads/accounts?status=pending_review`) grows without bound.
- Legitimate accounts from other users are buried.
- Admin reviewers cannot efficiently process the queue.
- Pagination (`list_accounts_by_status`) must page through thousands of stale entries.

## 3. Impact / Exploit / Blast Radius

### Queue flooding / denial of service

The admin review queue is a key-value DynamoDB scan over a `ByStatus` GSI. DynamoDB has no built-in queue depth limit. An attacker creates 10,000 pending accounts. An admin list query returns up to 500 per page (assuming a `Limit` parameter in the service layer), requiring 20 paginated requests just to enumerate stale entries. Each review action is O(1), but the cognitive load and time to reach legitimate submissions grows unboundedly.

### Financial and operational impact

- **Admin throughput degradation**: If each account takes 2 minutes to review, 1,000 flood accounts waste 33 hours of admin time.
- **Legitimate advertiser delay**: A real advertiser who submitted an account the same day as a flood event may wait days for review because the queue depth prevents timely processing.
- **Platform revenue impact**: Delayed ad account approval = delayed campaign spending = lost platform revenue.

### Potential data storage concern

Each ad account record is small (~200 bytes in DynamoDB). 10,000 accounts × 200 bytes = ~2 MB in DynamoDB, negligible. The concern is operational, not storage.

### Who can exploit this

Any authenticated user. Account creation requires only a valid session. There is no additional permission or admin role required. A free-tier user, a trial account, or a compromised low-privilege account can all trigger the flood.

## 4. Fix Design (Code-Level)

### Change: add count check in create_ad_account

`app/services/ad_accounts.py`, updated `create_ad_account`:

```python
MAX_ACCOUNTS_PER_USER = 5

def create_ad_account(owner_sub: str, data: AdAccountCreateIn) -> dict:
    """Create a new advertiser account in pending_review status.

    Raises ValueError if the owner already has MAX_ACCOUNTS_PER_USER accounts.
    """
    existing = list_accounts_by_owner(owner_sub)
    if len(existing) >= MAX_ACCOUNTS_PER_USER:
        raise ValueError(
            f"Account limit reached: a user may own at most {MAX_ACCOUNTS_PER_USER} ad accounts"
        )

    account_id = f"adacct_{uuid.uuid4().hex[:12]}"
    ts = now_ts()
    item = {
        "pk": f"ACCT#{account_id}",
        "sk": "META",
        "account_id": account_id,
        "owner_sub": owner_sub,
        "company_name": data.company_name,
        "billing_email": data.billing_email,
        "status": "pending_review",
        "balance_cents": 0,
        "lifetime_spend_cents": 0,
        "created_at": ts,
        "updated_at": ts,
    }
    T.ad_accounts.put_item(Item=item)
    return item
```

### Router: convert ValueError to HTTP 422

`app/routers/ads.py`, updated `create_account_endpoint`:

```python
@router.post("/accounts", status_code=201)
async def create_account_endpoint(body: AdAccountCreateIn, ctx=Depends(require_ui_session)):
    try:
        return create_ad_account(ctx["user_sub"], body)
    except ValueError as exc:
        raise HTTPException(status_code=422, detail=str(exc))
```

HTTP 422 Unprocessable Entity is appropriate: the request is syntactically valid (passes model validation) but semantically rejected by business rules. HTTP 429 (Too Many Requests) would also be acceptable and is semantically clearer for a per-user limit. Either is acceptable; 422 is used here to match the FastAPI convention for business-rule rejections already seen in the codebase.

### Deleted accounts and the limit

When an ad account is deleted or suspended, it should not continue to count toward the limit if the owner wants to create a replacement. The current `list_accounts_by_owner` returns all accounts regardless of status. There are two options:

**Option A (recommended)**: Count only non-deleted accounts. Add a status filter:

```python
def _count_active_accounts_by_owner(owner_sub: str) -> int:
    """Count accounts that are not in a terminal state."""
    items = list_accounts_by_owner(owner_sub)
    terminal = {"deleted", "permanently_suspended"}
    return sum(1 for acct in items if acct.get("status") not in terminal)
```

Replace `len(existing) >= MAX_ACCOUNTS_PER_USER` with `_count_active_accounts_by_owner(owner_sub) >= MAX_ACCOUNTS_PER_USER`.

**Option B (simpler)**: Count all accounts regardless of status. This prevents a user from cycling through accounts to evade the limit, but may frustrate legitimate users who deleted old accounts. For an MVP fix, Option B is sufficient.

For the initial implementation, use Option A (active accounts only) to avoid UX friction for legitimate re-creation scenarios.

### TOCTOU consideration

There is a time-of-check/time-of-use (TOCTOU) race: two concurrent requests could both pass the count check and both create an account, temporarily exceeding the limit. Mitigations:

1. **DynamoDB conditional expression** (strong mitigation): Use a conditional `put_item` that fails if a counter exceeds N. Requires maintaining a separate per-user account counter item in DynamoDB, which adds complexity.
2. **Accept the race** (practical mitigation): The window is narrow (milliseconds), the limit is 5, and the worst case is 6–7 accounts instead of 5. For a rate-limit use case (not a security invariant), accepting a small race is appropriate. Add a note in the service docstring.

The recommended approach is to accept the race for the initial implementation (Option 2) and document it. A distributed counter (Option 1) can be added in a follow-up.

### Dev/Prod parity (SECOPS-007)

`list_accounts_by_owner` uses `T.ad_accounts.query` via `app/core/tables.py`, which routes to DynamoDB Local in dev and real DynamoDB in prod. The `ByOwner` GSI must be present in both environments:
- **Dev**: `scripts/local-ddb-init.py` must define the `ByOwner` GSI on the `ad_accounts` table.
- **Prod**: the table's CloudFormation/CDK template must define the same GSI.

Verify the GSI exists in `scripts/local-ddb-init.py`:

```bash
grep -A 20 "ad_accounts" /home/ubuntu/testlogon/scripts/local-ddb-init.py | grep "ByOwner"
```

If `ByOwner` is already defined (it is used by the existing `list_accounts_by_owner` function which is not under test), no infrastructure change is needed. The fix is pure Python — no new AWS resources, no environment-specific branching.

### Backward compatibility

Existing users with more than 5 accounts (possible in current state) are not affected. The check only applies to new account creation requests. Operators who need to grant a user more than 5 accounts can raise the limit via `MAX_ACCOUNTS_PER_USER` (which could also be made a configurable setting in `app/core/settings.py` for operational flexibility).

### Rollout

No schema or infrastructure change needed. The `ByOwner` GSI is already in use. The fix is a pure Python addition to the service layer. Deploy normally; no migration needed.

### Rollback

Remove the count check and the `try/except ValueError` in the router. All accounts created during the fix deployment period that exceed 5 are orphaned but not harmful. The admin queue returns to its pre-fix state.

### Risks

- **TOCTOU race**: As documented, two concurrent requests can exceed the limit by at most N-1 where N is the concurrency. Acceptable for an MVP.
- **Legitimate users with >5 accounts**: Any user who already has more than 5 accounts (possible in the current state) will not be blocked from their existing accounts but will not be able to create new ones. This is the desired behavior.
