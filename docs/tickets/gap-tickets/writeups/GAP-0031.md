# GAP-0031: No `POST /{packet_id}/signers` API Endpoint — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real code at file:line. Builds on investigation doc
> `docs/tickets/gap-tickets/investigations/GAP-0031.md`.

## 1. Summary & Classification

**GAP-0031** identifies a complete absence of the `POST /v1/signature-packets/{packet_id}/signers`
and `DELETE /v1/signature-packets/{packet_id}/signers/{signer_id}` API endpoints that are required
by the SIGN-001 e-signature feature specification (§2.1 "Add/Remove Signers").

- **Severity**: CRIT
- **Source ticket**: SIGN-001
- **Owning area**: Document signing (`app/routers/signature_packets.py`, `app/services/signature_packet_store.py`)
- **Status**: Open
- **Effort**: M (~2 hours implementation, ~1 hour tests)

**Verdict**: Confirmed. The two endpoints are wholly absent from the router. The service layer
exposes read-only signer helpers (`list_packet_signers`, `get_packet_signer`, etc.) but provides
no `add_packet_signer` or `remove_packet_signer` write functions. As a direct consequence the
`POST /{packet_id}/send` endpoint — which requires at least one signer — is permanently
unreachable for any real user: there is no API path to satisfy its precondition.

**Related tickets**: SIGN-001 (original spec), GAP-0035 (CSRF gap on a different admin router).
No dependency blockers; the fix is purely additive.

## 2. Current-State Investigation (Root Cause)

### 2.1 Router audit

`app/routers/signature_packets.py` defines nine route handlers. A grep-level audit shows
every decorated handler:

| Handler | Path |
|---|---|
| `create_signature_packet` | `POST ""` |
| `mutate_signature_packet_field` | `POST /{packet_id}/fields` |
| `send_signature_packet` | `POST /{packet_id}/send` |
| `get_signature_packet_detail` | `GET /{packet_id}` |
| `acknowledge_signature_packet_legal_notice` | `POST /{packet_id}/acknowledge-legal-notice` |
| `fill_signature_packet_field` | `POST /{packet_id}/fields/{field_id}/fill` |
| `mark_signature_packet_done` | `POST /{packet_id}/mark-done` |
| `get_signature_packet_events` | `GET /{packet_id}/events` |
| `get_signature_packet_final_pdf` | `GET /{packet_id}/final-pdf` |

There is no `POST /{packet_id}/signers` and no `DELETE /{packet_id}/signers/{signer_id}`.
The router import block (`app/routers/signature_packets.py:19-42`) imports
`list_packet_signers`, `get_packet_signer`, `signer_assignment_exists`, and a full set of
status-management helpers — but no write functions for signer creation or deletion.

### 2.2 Service layer audit

`app/services/signature_packet_store.py` exports these signer-related functions (confirmed
by reading the file):

- `list_packets_for_signer` (line 38) — query by signer_id/status
- `signer_assignment_exists` (line 125) — membership check
- `list_packet_signers` (line 175) — list all signers for a packet
- `get_packet_signer` (line 238) — fetch one signer record
- `signer_has_accepted_notice` (line 286)
- `mark_signer_notice_shown` (line 292)
- `mark_signer_notice_accepted` (line 315)
- `mark_signer_completed` (line 338)
- `are_required_signers_completed` (line 395)

**There is no `add_packet_signer()`, no `remove_packet_signer()`, and no function that calls
`T.signature_packet_signers.put_item()`** for new records. The table can be queried and
updated in-place but never populated through the API.

### 2.3 The `send` endpoint is a hard blocker

`app/routers/signature_packets.py:388-390`:

```python
signers = list_packet_signers(packet_id)
if not signers:
    raise HTTPException(status_code=400, detail={"code": "signature_packet_no_signers"})
```

This check fires before the fields validation and before the `mark_packet_sent` call.
With no API path to create a signer record, `list_packet_signers` always returns `[]`, so
`send` always returns `400 signature_packet_no_signers`. The entire e-signature send flow
is dead code for any user interacting through the API.

### 2.4 E2E test confirms the workaround

`frontend/e2e/signing.spec.ts` line 164-176 injects signer records by writing directly to
DynamoDB (the `injectSigner` helper function). Line 231 carries the comment:
"Inject a signer so the send endpoint is satisfied." This confirms the team already
knew the API path was missing and chose a DDB-injection workaround for tests only.

### 2.5 Why the gap exists

The SIGN-001 ticket specified the two-step "add signer → send" flow. The store read helpers
and route handlers for signing workflow steps were implemented, but the write path for
populating the `signature_packet_signers` table via the API was never written. The service
module grew incrementally; the mutation side of signer management was deferred and never
added.

## 3. Impact / Exploit / Blast Radius

This is a **complete functional blocker** for the document signing feature, not a security
vulnerability.

**Who is affected**: Every user who creates a signature packet through the normal UI or API.
No production user can successfully send a packet.

**User-facing failure mode**:
1. User creates a packet via `POST /v1/signature-packets` — succeeds, returns `packet_id`.
2. User adds fields via `POST /v1/signature-packets/{id}/fields` — succeeds.
3. User attempts to send via `POST /v1/signature-packets/{id}/send` — always returns
   `400 {"code": "signature_packet_no_signers"}`.
4. There is no UI or API affordance to escape this state.

**Workaround availability**: None for real users. Dev/E2E tests bypass this via direct
DynamoDB writes (`injectSigner`), which is not a production-viable pattern.

**Secondary effects**:
- The capabilities object in `GET /{packet_id}` reports `can_send: true` (owner + draft
  status), creating a false affordance in any frontend that renders a "Send" button based
  on capabilities.
- The E2E test suite masks the gap by using DDB injection, so CI passes even though the
  feature is broken.

**Security**: No exploit path. The missing endpoints are additive (new write capability),
not a bypass of existing access control.

## 4. Fix Design (Code-Level)

### 4.1 Service layer — `app/services/signature_packet_store.py`

Add two new exported functions after the existing signer read helpers (approximately
line 395, after `are_required_signers_completed`):

```python
def add_packet_signer(
    *,
    packet_id: str,
    signer_id: str,
    email: str | None = None,
    required: bool = True,
) -> Dict[str, Any]:
    """Add a signer record to a DRAFT packet."""
    require_signature_pdf_enabled()
    _ensure_packet_draft(packet_id)          # raises 409 if not in DRAFT status
    now = datetime.now(timezone.utc).isoformat()
    item: Dict[str, Any] = {
        "packet_id": packet_id,
        "signer_id": signer_id,
        "status": SignatureSignerStatus.PENDING.value,
        "status_key": signer_status_sort_key(SignatureSignerStatus.PENDING, packet_id),
        "required": required,
        "added_at": now,
        "updated_at": now,
    }
    if email:
        item["email"] = email
    T.signature_packet_signers.put_item(Item=item)
    return item


def remove_packet_signer(*, packet_id: str, signer_id: str) -> None:
    """Remove a signer record from a DRAFT packet."""
    require_signature_pdf_enabled()
    _ensure_packet_draft(packet_id)          # raises 409 if not in DRAFT status
    T.signature_packet_signers.delete_item(
        Key={"packet_id": packet_id, "signer_id": signer_id}
    )
```

The `_ensure_packet_draft` helper already exists in the store (used by field mutation
functions) and raises `ValueError("packet_immutable")` when the packet is not in DRAFT status.

### 4.2 Router — `app/routers/signature_packets.py`

**Step 1**: Add `add_packet_signer` and `remove_packet_signer` to the import block
(`app/routers/signature_packets.py:19-42`).

**Step 2**: Add two Pydantic models after `SignaturePacketEventsOut` (~line 202):

```python
class AddSignerIn(BaseModel):
    signer_id: str = Field(..., min_length=1, max_length=256)
    email: Optional[str] = Field(default=None, max_length=256)
    required: bool = True


class AddSignerOut(BaseModel):
    packet_id: str
    signer_id: str
    status: str
    required: bool
    added_at: str
```

**Step 3**: Add two route handlers after `create_signature_packet` (~line 274):

```python
@router.post("/{packet_id}/signers", response_model=AddSignerOut)
def add_signer(
    packet_id: str,
    inp: AddSignerIn,
    user_sub: str = Depends(_current_user),
) -> Dict[str, Any]:
    _validate_packet_owner_and_draft(packet_id, user_sub)
    signer = add_packet_signer(
        packet_id=packet_id,
        signer_id=inp.signer_id,
        email=inp.email,
        required=inp.required,
    )
    append_packet_event(
        packet_id=packet_id,
        actor_user_id=user_sub,
        event_type="signer_added",
        event_payload={"signer_id": inp.signer_id, "required": inp.required},
    )
    return {
        "packet_id": packet_id,
        "signer_id": inp.signer_id,
        "status": signer["status"],
        "required": inp.required,
        "added_at": signer["added_at"],
    }


@router.delete("/{packet_id}/signers/{signer_id}", status_code=204)
def remove_signer(
    packet_id: str,
    signer_id: str,
    user_sub: str = Depends(_current_user),
) -> None:
    _validate_packet_owner_and_draft(packet_id, user_sub)
    remove_packet_signer(packet_id=packet_id, signer_id=signer_id)
    append_packet_event(
        packet_id=packet_id,
        actor_user_id=user_sub,
        event_type="signer_removed",
        event_payload={"signer_id": signer_id},
    )
```

`_validate_packet_owner_and_draft` (line 277) handles both the 403 (not owner) and
409 (not DRAFT) cases, so the handlers above do not need additional guard logic.

### 4.3 E2E test cleanup

`frontend/e2e/signing.spec.ts` lines 164-176 (`injectSigner` helper) and line 231
(direct DDB call) must be replaced with real API calls:

```typescript
async function addSignerViaApi(
  page: Page,
  packetId: string,
  signerSub: string,
): Promise<void> {
  const r = await page.request.post(
    `/v1/signature-packets/${packetId}/signers`,
    {
      headers: { "x-csrf-token": sessions["alice"].csrf_token },
      data: { signer_id: signerSub, required: true },
    },
  );
  expect(r.status()).toBe(200);
}
```

### 4.4 Dev/Prod parity (SECOPS-007)

The `T.signature_packet_signers` table is defined in `scripts/local-ddb-init.py` with the
same schema in both dev and prod environments. The two new service functions use only
`put_item` and `delete_item` on that table — the same pattern used throughout the store.
No AWS-specific code path, no feature flag, no mock divergence. Behavior is identical in
both environments.

### 4.5 Alternatives considered

- **Inline signer list on packet create**: Rejected — breaks incremental field-assignment
  workflows; SIGN-001 §2.1 explicitly specifies separate signer management endpoints.
- **Batch-add signers on send**: Rejected — the send endpoint already validates field-to-signer
  assignments; adding signers as a side-effect of send would conflate two distinct
  operations and preclude pre-send signer validation.

## 5. Testing, Verification & Rollout

### 5.1 Regression tests (pytest offline)

These tests must **fail before** the fix and **pass after**:

```python
# tests/test_signature_signers.py

def test_add_signer_returns_200(client, alice_session, draft_packet_id):
    """POST /{packet_id}/signers succeeds for packet owner; before fix → 404."""
    r = client.post(
        f"/v1/signature-packets/{draft_packet_id}/signers",
        json={"signer_id": "bob_sub", "required": True},
        headers=alice_session.headers,
    )
    assert r.status_code == 200
    body = r.json()
    assert body["signer_id"] == "bob_sub"
    assert body["status"] == "pending"
    assert body["required"] is True


def test_add_signer_then_send_succeeds(client, alice_session, draft_packet_id_with_field):
    """After adding a signer and assigning the field, /send no longer returns 400."""
    # Add signer
    r = client.post(
        f"/v1/signature-packets/{draft_packet_id_with_field}/signers",
        json={"signer_id": "bob_sub", "required": True},
        headers=alice_session.headers,
    )
    assert r.status_code == 200
    # Send
    r = client.post(
        f"/v1/signature-packets/{draft_packet_id_with_field}/send",
        headers=alice_session.headers,
    )
    assert r.status_code == 200


def test_add_signer_requires_draft_status(client, alice_session, sent_packet_id):
    """Adding a signer to an already-sent packet returns 409."""
    r = client.post(
        f"/v1/signature-packets/{sent_packet_id}/signers",
        json={"signer_id": "charlie_sub"},
        headers=alice_session.headers,
    )
    assert r.status_code == 409
    assert r.json()["detail"]["code"] == "signature_packet_not_draft"


def test_remove_signer_returns_204(client, alice_session, draft_packet_id):
    """DELETE /{packet_id}/signers/{signer_id} returns 204."""
    # First add
    client.post(
        f"/v1/signature-packets/{draft_packet_id}/signers",
        json={"signer_id": "bob_sub"},
        headers=alice_session.headers,
    )
    # Then remove
    r = client.delete(
        f"/v1/signature-packets/{draft_packet_id}/signers/bob_sub",
        headers=alice_session.headers,
    )
    assert r.status_code == 204


def test_add_signer_non_owner_forbidden(client, bob_session, alice_draft_packet_id):
    """Non-owner cannot add signers; returns 403."""
    r = client.post(
        f"/v1/signature-packets/{alice_draft_packet_id}/signers",
        json={"signer_id": "charlie_sub"},
        headers=bob_session.headers,
    )
    assert r.status_code == 403
```

**Fails before**: `test_add_signer_returns_200` raises `AssertionError: 404 != 200` because
the route does not exist. `test_add_signer_then_send_succeeds` fails at the send step with
`400 signature_packet_no_signers`.

**Passes after**: All five tests pass.

### 5.4 Observability

The existing `append_packet_event` calls in the new handlers write `signer_added` and
`signer_removed` events to `T.signature_packet_events`, which are surfaced by
`GET /{packet_id}/events`. No new metrics are required; the existing
`record_signature_packet_event` instrumentation fires automatically.

### 5.5 Rollout and rollback

- No schema migration needed; `T.signature_packet_signers` already exists.
- No feature flag needed; the feature is gated by the existing `SIGNATURE_PDF_ENABLED`
  env var (enforced by `require_signature_pdf_enabled()` inside the service functions).
- Rollback: revert the two new route handlers and two service functions. No data
  migration required since the table is append-only.

### 5.6 Risk and effort

- **Risk**: Low. The change is purely additive; no existing routes are modified.
  The existing `_validate_packet_owner_and_draft` guard ensures only the owner
  can mutate a DRAFT packet.
- **Effort**: M — approximately 2 hours for implementation, 1 hour for tests.
- **Sequencing**: Can land independently; no upstream tickets need to merge first.
