# GAP-0211: No Accounting-Software Column Mapping — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: FIN-016. No prior investigation doc.
> Claim verified against actual code.

## 1. Summary & Classification

**Severity**: HIGH
**Source ticket**: FIN-016 (Financial Audit Log Export)
**Owning area**: Audit/Export pipeline (`app/services/audit_export_pipeline.py`, `app/routers/audit_export.py`)
**Status**: Open — no fix applied

**Claim verification**: CONFIRMED. The GAP-016 as-built notes describe a generic audit column set at `audit_export_pipeline.py:22` and the absence of any `column_format` / `accounting_format` parameter. Both deficiencies were verified in the live code.

The export system emits a single fixed CSV schema — 15 generic audit columns (event_id, actor_user_id, actor_role, etc.) defined in the `CSV_COLUMNS` constant at `app/services/audit_export_pipeline.py:22`. Finance teams at QuickBooks or Xero shops require a mapped column schema: `Date`, `Transaction Type`, `Num`, `Name`, `Memo`, `Account`, `Amount`, and similar fields. No mapping logic or `column_format` parameter exists anywhere in the pipeline, router, or request model. Any billing-category CSV export downloaded today cannot be auto-imported by any major accounting package.

**Related tickets**: GAP-0211 is one of five FIN-016 gaps. Companion gaps (PDF export, scheduled reports, billing-specific filters, BillingLedgerAdapter scan) are tracked separately. This gap has no security impact but blocks Finance's self-service reporting workflow.

## 2. Current-State Investigation (root cause)

### The column schema is a hard constant

`app/services/audit_export_pipeline.py`, lines 22–27:

```python
CSV_COLUMNS = [
    "event_id", "event_type", "event_action", "timestamp", "timestamp_unix",
    "actor_user_id", "actor_role", "actor_ip", "actor_user_agent",
    "target_user_id", "target_resource_type", "target_resource_id",
    "outcome", "metadata", "source_table",
]
```

These columns are designed for security/compliance audit readers, not for finance reconciliation. They are passed directly to `event.to_csv_row(CSV_COLUMNS)` at line 159 and `csv.writer(header_buf).writerow(CSV_COLUMNS)` at line 149 with no branching on export category or format variant.

### The router accepts no column-format parameter

`app/routers/audit_export.py`, lines 64–99 (`create_audit_export`): the request body is consumed as a raw `dict`, and only the keys `categories`, `format`, `from_date`, `to_date`, `actor_user_id`, `target_user_id`, and `event_actions` are extracted. There is no `column_format` field read or validated. Passing `column_format: "quickbooks"` today would be silently ignored.

### No accounting-specific adapter mapping exists

The adapter layer (`app/services/audit_adapters.py`) maps category names such as `"billing"` to a `BillingLedgerAdapter`. The adapter's `query()` method returns `UnifiedAuditEvent` objects (`app/services/audit_export.py`) which carry generic fields. There is no `to_quickbooks_row()` or `to_xero_row()` method on `UnifiedAuditEvent`, and no specialised event subclass for billing ledger rows that would carry the required financial fields (`transaction_type`, `account`, `name`, `amount`, etc.).

### Dev vs. prod divergence

In dev mode `_process_export_inline` writes content to DynamoDB inline (capped at 500 events). In production the same `_merge_sorted_events` / `CSV_COLUMNS` path would be used to write a file to S3. The column set is therefore identical across environments — the gap is not environment-specific.

### Runtime effect

An admin who requests `categories=["billing"], format="csv"` receives a file whose first row is:

```
event_id,event_type,event_action,timestamp,timestamp_unix,actor_user_id,actor_role,...
```

A QuickBooks Online CSV import expects headers: `Date,Transaction Type,Num,Name,Memo,Account,Debit,Credit`. The mismatch causes a hard parse failure in every major accounting import wizard. The export is unusable without manual column rearrangement in a spreadsheet — which defeats the purpose of a self-service export tool.

## 3. Impact / Exploit / Blast Radius

This is a **functional gap**, not a security vulnerability. There is no exploit surface; the issue is that the exported data is in the wrong shape.

**Finance workflow impact**: Every billing CSV export must be transformed manually before it can be imported into accounting software. For a platform with thousands of monthly transactions this adds hours of data-wrangling per reporting period and introduces transcription errors.

**Compliance risk**: Manual column remapping is not an auditable process. If the remapped file is submitted to a tax authority or auditor, the chain of provenance from raw ledger to submitted document is broken. There is no signed manifest for the remapped file, and the original signed export has a different schema — the two artefacts do not match.

**Blast radius**:
- All operators using the audit export UI for billing data.
- Any automated accounting integration that consumes download URLs from `GET /ui/admin/audit-exports/{id}/download`.
- No user-facing feature is broken. No financial data is lost or corrupted.

## 4. Fix Design (code-level)

### Overview

Add an optional `column_format` request field. When `column_format` is `"quickbooks"` or `"xero"` and `format` is `"csv"` and `categories` includes `"billing"`, the pipeline renders columns appropriate for that accounting package. For all other combinations (non-billing categories, NDJSON, or `column_format=None`) the existing generic schema is used unchanged — this is fully backward-compatible.

### Step 1 — Extend the router's request handling

In `app/routers/audit_export.py`, lines 71–78, add extraction and validation of `column_format`:

```python
column_format = body.get("column_format")  # Optional: None | "quickbooks" | "xero"
VALID_COLUMN_FORMATS = {None, "quickbooks", "xero"}
if column_format not in VALID_COLUMN_FORMATS:
    raise HTTPException(
        status_code=400,
        detail=f"column_format must be one of: quickbooks, xero (or omitted)"
    )
```

Pass `column_format` to `create_export_job(...)`.

### Step 2 — Thread the parameter through the pipeline

In `app/services/audit_export_pipeline.py`, update `create_export_job` signature:

```python
def create_export_job(
    ...,
    column_format: Optional[str] = None,
) -> dict[str, Any]:
```

Store `column_format` in the DDB item so the async processor (future S3 path) can read it. In `_process_export_inline`, pass `column_format` to the CSV rendering branch.

### Step 3 — Add accounting column definitions and row mapper

Add a new module `app/services/audit_export_accounting.py`:

```python
QUICKBOOKS_COLUMNS = [
    "Date", "Transaction Type", "Num", "Name", "Memo",
    "Account", "Debit", "Credit",
]

XERO_COLUMNS = [
    "Date", "Amount", "Payee", "Description", "Reference",
    "Cheque Number", "Account Code", "Tax Rate",
]

def billing_event_to_quickbooks_row(event: UnifiedAuditEvent) -> list:
    meta = event.metadata or {}
    entry_type = meta.get("entry_type", event.event_action or "")
    amount_cents = int(meta.get("amount_cents", 0))
    is_debit = "debit" in entry_type.lower() or amount_cents < 0
    amount_dollars = abs(amount_cents) / 100
    return [
        datetime.fromtimestamp(event.timestamp_unix, tz=timezone.utc).strftime("%m/%d/%Y"),
        _qb_transaction_type(entry_type),
        event.event_id[:8],
        meta.get("user_name") or event.actor_user_id or "",
        meta.get("description") or entry_type,
        "Platform Revenue",
        f"{amount_dollars:.2f}" if is_debit else "",
        f"{amount_dollars:.2f}" if not is_debit else "",
    ]

def billing_event_to_xero_row(event: UnifiedAuditEvent) -> list:
    meta = event.metadata or {}
    amount_cents = int(meta.get("amount_cents", 0))
    return [
        datetime.fromtimestamp(event.timestamp_unix, tz=timezone.utc).strftime("%d %b %Y"),
        f"{abs(amount_cents) / 100:.2f}",
        meta.get("user_name") or event.actor_user_id or "",
        meta.get("description") or event.event_action or "",
        event.event_id[:16],
        "",
        "200",  # default sales account code
        "Tax Exempt (0%)",
    ]

def _qb_transaction_type(entry_type: str) -> str:
    mapping = {
        "tip_debit": "Sales Receipt",
        "tip_credit": "Deposit",
        "unlock_debit": "Sales Receipt",
        "subscription_charge": "Invoice",
        "payout": "Check",
        "deposit": "Deposit",
    }
    return mapping.get(entry_type, "Journal Entry")
```

### Step 4 — Use the mapper in the pipeline CSV branch

In `_process_export_inline` (audit_export_pipeline.py), replace lines 144–163:

```python
if fmt == "csv":
    is_accounting = column_format in ("quickbooks", "xero") and "billing" in categories
    if is_accounting:
        from app.services.audit_export_accounting import (
            QUICKBOOKS_COLUMNS, XERO_COLUMNS,
            billing_event_to_quickbooks_row,
            billing_event_to_xero_row,
        )
        cols = QUICKBOOKS_COLUMNS if column_format == "quickbooks" else XERO_COLUMNS
        row_fn = billing_event_to_quickbooks_row if column_format == "quickbooks" \
            else billing_event_to_xero_row
    else:
        cols = CSV_COLUMNS
        row_fn = lambda ev: ev.to_csv_row(CSV_COLUMNS)

    bom = "﻿"
    content_parts.append(bom)
    sha256.update(bom.encode("utf-8"))
    header_buf = io.StringIO()
    csv.writer(header_buf).writerow(cols)
    header_line = header_buf.getvalue()
    content_parts.append(header_line)
    sha256.update(header_line.encode("utf-8"))

    for event in _merge_sorted_events(...):
        row_buf = io.StringIO()
        csv.writer(row_buf).writerow(row_fn(event))
        line = row_buf.getvalue()
        content_parts.append(line)
        sha256.update(line.encode("utf-8"))
        event_count += 1
```

### Step 5 — Store `column_format` in the manifest and job-to-out helper

Add `column_format` to the manifest dict (for audit trail) and to `_job_to_out` so the download response carries the correct `Content-Disposition` filename suffix (`...-quickbooks.csv`).

### Dev/Prod parity (SECOPS-007)

The CSV rendering path is identical in dev mode (`_process_export_inline`) and the production S3-write path (future). The `column_format` parameter is stored in the DDB item and forwarded to whichever processor handles the job. No mock-only branching is introduced. The accounting row mappers are pure functions with no AWS calls; they work identically in both environments.

### Alternatives considered

- **Client-side transformation**: The frontend could remap columns. Rejected — breaks the signed manifest guarantee and the chain of provenance required for audit-grade exports.
- **Separate accounting export endpoint**: Adding `/audit-exports/accounting` would duplicate significant pipeline code. The parameterised approach keeps a single job model with a variant rendering path.
