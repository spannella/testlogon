# GAP-0128: Entry Fee Billing Atomicity Gap — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at
> `app/services/broadcast_lottery.py:484–561`. No prior investigation doc exists.

## 1. Summary & Classification

**Bug**: `_charge_entry_fee()` in the broadcast lottery service writes a viewer debit
and a broadcaster credit as two independent DynamoDB `put_item` calls, each in its own
`try/except`. If the credit write fails after the debit succeeds, the lottery entrant
is charged the entry fee but the broadcaster receives no payment. The exception is
swallowed silently and the function returns as if billing succeeded.

- **Severity**: HIGH — financial integrity, silent money loss, third occurrence of this
  pattern (see also GAP-0126, GAP-0129)
- **Source ticket**: BCAST-014
- **Status**: Open
- **Owning area**: Broadcast / Lottery / Billing
- **Claim verdict**: Confirmed. Lines 517–559 of `app/services/broadcast_lottery.py`
  match the description exactly.
- **One-line impact**: A transient DynamoDB write error on the credit step silently
  leaves an entrant debited with no broadcaster credit.
- **Related tickets**: GAP-0126 (same pattern in private-chat billing), GAP-0129 (same
  pattern in chat rich-feature billing), GAP-0127 (self-entry guard — correctly placed,
  but shares the same function), SECOPS-007.

## 2. Current-State Investigation (root cause)

### Code path

`_charge_entry_fee` is at `app/services/broadcast_lottery.py:484–561`:

```python
def _charge_entry_fee(
    *, user_id, broadcaster_id, entry_fee_cents, lottery_id, session_id,
    payment_method_id=None,
) -> str:
    ...
    billing_tbl = ddb.Table(S.billing_table_name)        # line 500

    # Payment method validation (lines 501–515) ...

    try:                                                  # line 517
        debit_entry_id = uuid.uuid4().hex
        billing_tbl.put_item(Item={                       # line 519 — DEBIT
            "pk": f"USER#{user_id}",
            "sk": f"LEDGER#{ts}#{debit_entry_id}",
            "type": "debit",
            "amount_cents": entry_fee_cents,
            ...
        })
    except Exception:                                    # line 535
        logger.exception("Failed to write lottery entry fee debit ...")
        # ← no re-raise; execution continues

    try:                                                 # line 539
        credit_entry_id = uuid.uuid4().hex
        billing_tbl.put_item(Item={                      # line 541 — CREDIT
            "pk": f"USER#{broadcaster_id}",
            "sk": f"LEDGER#{ts}#{credit_entry_id}",
            "type": "credit",
            "amount_cents": entry_fee_cents,
            ...
        })
    except Exception:                                    # line 557
        logger.exception("Failed to write lottery entry fee credit ...")
        # ← no re-raise; debit already written, irrecoverable

    return fee_payment_id                                # line 561
```

### Key structural issues

1. **Independent try/except blocks** (lines 517 and 539): the two `put_item` calls are
   not atomic. An exception on line 541 does not roll back the write on line 519.

2. **Exceptions swallowed, not re-raised**: both `except Exception` blocks call
   `logger.exception` but do not `raise`. The caller (`enter_lottery`) sees a normal
   return value (`fee_payment_id`) regardless of whether either write succeeded.

3. **Inconsistent billing handle**: unlike `_write_private_chat_billing` (which uses
   `T.billing`, the table handle from `app/core/tables.py`), `_charge_entry_fee` uses
   `ddb.Table(S.billing_table_name)` (lines 496, 500) — a raw boto3 resource call.
   This means `T.billing` and the table object in this function may point to the same
   underlying table but are separate handles. The inconsistency is not itself a bug
   but complicates refactoring (see Fix section).

4. **Debit write may also silently fail**: if the debit `put_item` at line 519 fails
   (exception swallowed at line 535), the credit write still proceeds — the broadcaster
   would be credited for an entry fee the entrant was never actually charged. This is
   the mirror-image of the described bug and is equally broken.

### Caller

`_charge_entry_fee` is called from `enter_lottery` at lines 231–238, only when
`entry_fee_cents > 0`. The call is inside no try/except in the caller; however, because
the function swallows exceptions internally, the caller never sees a billing failure.

The returned `fee_payment_id` is stored in the `LENTRY#` item (line 249) as a receipt
reference. If either billing write failed silently, this ID is stored in the entry but
references a partial ledger.

## 3. Impact / Exploit / Blast Radius

### Who is affected

- **Lottery entrants**: a viewer who enters a paid lottery may be debited without the
  broadcaster receiving the credit.
- **Broadcasters**: may receive a credit for a fee that was never actually collected
  from the entrant (reverse scenario).
- **Finance / reconciliation**: the `fee_payment_id` stored on `LENTRY#` items will
  not match complete debit+credit pairs in the billing ledger.

### Concrete exploit walkthrough — infrastructure fault

1. Entrant calls `POST /broadcast/{session}/lottery/{id}/enter` with a valid payment
   method.
2. `enter_lottery` calls `_charge_entry_fee`.
3. Debit `put_item` (line 519) writes successfully — entrant's wallet is charged.
4. Transient DynamoDB error on credit `put_item` (line 541). Exception swallowed.
5. `_charge_entry_fee` returns `fee_payment_id` as if billing succeeded.
6. `enter_lottery` writes the `LENTRY#` item with `fee_payment_id` set.
7. Entry count incremented. Broadcaster sees new entrant.
8. Broadcaster never receives the entry fee credit. No alert fires.

### Worst case

A lottery with `entry_fee_cents=500` (£5) and 200 entries during a fault window loses
200 × $5 = $1,000 in broadcaster credits. With no alerting on the swallowed exception
(`logger.exception` is not wired to any monitoring alert channel), the loss is
discovered only during periodic reconciliation — potentially days or weeks later.

### Blast radius

Limited to paid lotteries (`entry_fee_cents > 0`) during DynamoDB write-error windows.
Free lotteries are unaffected. In a high-volume broadcast (5,000+ viewers) with a
paid lottery, the number of affected entries during a 30-second fault window could be
in the hundreds.

## 4. Fix Design (code-level)

### Strategy

Replace the two sequential `put_item` calls with `TransactWriteItems`. This is the
same fix pattern as GAP-0126 and GAP-0129. All three billing gaps should be fixed in
the same PR to avoid partial state.

### Primary change — `_charge_entry_fee`

```python
# app/services/broadcast_lottery.py

from boto3.dynamodb.types import TypeSerializer as _TS

_serializer = _TS()

def _ddb_av(item: dict) -> dict:
    """Convert Python dict to DDB AttributeValue map."""
    return {k: _serializer.serialize(v) for k, v in item.items()}

def _charge_entry_fee(
    *,
    user_id: str,
    broadcaster_id: str,
    entry_fee_cents: int,
    lottery_id: str,
    session_id: str,
    payment_method_id: Optional[str] = None,
) -> str:
    import uuid
    from app.core.aws import ddb

    ts = now_ts()
    fee_payment_id = "lotfee_" + uuid.uuid4().hex
    billing_table_name = S.billing_table_name

    billing_tbl = ddb.Table(billing_table_name)

    # Payment method validation (unchanged) ...

    debit_entry_id = uuid.uuid4().hex
    credit_entry_id = uuid.uuid4().hex

    debit_item = {
        "pk": f"USER#{user_id}",
        "sk": f"LEDGER#{ts}#{debit_entry_id}",
        "entry_id": debit_entry_id,
        "ts": ts,
        "type": "debit",
        "amount_cents": entry_fee_cents,
        "currency": "USD",
        "state": "settled",
        "reason": "Lottery entry fee",
        "meta": {
            "lottery_id": lottery_id,
            "session_id": session_id,
            "fee_payment_id": fee_payment_id,
            "payment_method_id": payment_method_id,
        },
    }
    credit_item = {
        "pk": f"USER#{broadcaster_id}",
        "sk": f"LEDGER#{ts}#{credit_entry_id}",
        "entry_id": credit_entry_id,
        "ts": ts,
        "type": "credit",
        "amount_cents": entry_fee_cents,
        "currency": "USD",
        "state": "settled",
        "reason": "Lottery entry fee received",
        "meta": {
            "lottery_id": lottery_id,
            "session_id": session_id,
            "fee_payment_id": fee_payment_id,
            "from_user_id": user_id,
        },
    }

    # Atomic: both rows land or neither does.
    ddb.meta.client.transact_write_items(
        TransactItems=[
            {"Put": {"TableName": billing_table_name, "Item": _ddb_av(debit_item)}},
            {"Put": {"TableName": billing_table_name, "Item": _ddb_av(credit_item)}},
        ]
    )

    return fee_payment_id
```

Remove all `try/except` from the billing writes. Allow `TransactionCanceledException`
to propagate to the `enter_lottery` caller, which propagates to the router, which
returns HTTP 500. The entrant is never debited (transaction atomicity), so the
correct user-visible outcome is a retriable 500, not a silent success with a lost
credit.

### Consolidation recommendation (GAP-0129 alignment)

Given this is the third occurrence of the pattern (GAP-0126, GAP-0128, GAP-0129), a
shared utility should be introduced:

```python
# app/services/billing_utils.py (new file)

def write_billing_pair(
    payer_id: str,
    recipient_id: str,
    debit_amount_cents: int,
    credit_amount_cents: int,
    reason: str,
    meta: dict,
) -> tuple[str, str]:
    """Write an atomic debit+credit billing pair via TransactWriteItems.
    Returns (debit_entry_id, credit_entry_id). Raises on failure.
    """
    ...
```

All three billing functions (`_write_private_chat_billing`, `_charge_entry_fee`,
`_write_chat_billing`) should delegate to this utility.

### Caller impact in `enter_lottery`

After the fix, `_charge_entry_fee` may raise `TransactionCanceledException`.
`enter_lottery` should not catch this — let it propagate. The `LENTRY#` item write
and `entry_count` increment at lines 254 and 267 will not execute, which is correct:
no entry is created for a failed payment.

### Dev/prod parity (SECOPS-007)

`TransactWriteItems` is supported by moto v4+ (used in tests) and by AWS DynamoDB.
The `ddb.meta.client` handle already used in this file (line 500 calls `ddb.Table`)
is the boto3 DynamoDB resource. `ddb.meta.client.transact_write_items` is the same
client used for atomic writes elsewhere in the codebase. No dev-mode flag needed.

### Backward compatibility / migration

The change is forward-only. Existing ledger rows are unaffected. No DynamoDB table
schema change required. The billing table schema (pk/sk composite key) supports the
transactional write without modification.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

```python
# tests/services/test_broadcast_lottery_entry_fee.py

def test_entry_fee_atomic_credit_failure_no_orphan_debit(
    moto_billing_table, moto_broadcast_chat_messages_table
):
    """
    BEFORE fix: credit exception swallowed; debit row exists, credit missing.
    AFTER fix:  TransactionCanceledException propagates; zero billing rows written.
    """
    from botocore.exceptions import ClientError
    from unittest.mock import patch
    from app.services.broadcast_lottery import _charge_entry_fee
    from app.core.aws import ddb
    import pytest

    def fail_transact(**kwargs):
        raise ClientError(
            {"Error": {"Code": "TransactionCanceledException",
                       "Message": "Cancelled"},
             "CancellationReasons": []},
            "TransactWriteItems",
        )

    with patch.object(ddb.meta.client, "transact_write_items", side_effect=fail_transact):
        with pytest.raises(ClientError, match="TransactionCanceledException"):
            _charge_entry_fee(
                user_id="viewer_x",
                broadcaster_id="broadcaster_y",
                entry_fee_cents=500,
                lottery_id="lot_test",
                session_id="sess_test",
                payment_method_id="pm_test",
            )

    for user in ("viewer_x", "broadcaster_y"):
        resp = moto_billing_table.query(
            KeyConditionExpression="pk = :pk",
            ExpressionAttributeValues={":pk": f"USER#{user}"},
        )
        assert resp["Count"] == 0, f"No ledger rows for {user} after atomic failure"


def test_entry_fee_writes_both_rows_on_success(
    moto_billing_table, moto_broadcast_chat_messages_table
):
    """Both debit and credit rows exist after a successful _charge_entry_fee call."""
    from app.services.broadcast_lottery import _charge_entry_fee

    _charge_entry_fee(
        user_id="viewer_ok",
        broadcaster_id="broadcaster_ok",
        entry_fee_cents=100,
        lottery_id="lot_ok",
        session_id="sess_ok",
        payment_method_id=None,
    )

    for user, expected_type in (("viewer_ok", "debit"), ("broadcaster_ok", "credit")):
        resp = moto_billing_table.query(
            KeyConditionExpression="pk = :pk",
            ExpressionAttributeValues={":pk": f"USER#{user}"},
        )
        assert resp["Count"] == 1
        assert resp["Items"][0]["type"] == expected_type
```

**Fails before fix**: old code swallows exception; `pytest.raises` not entered;
no assertion about row count is reached (or, if the debit was written before the
mock, `Count == 1` for the payer).

**Passes after fix**: transaction fails atomically; both counts are zero; propagation
is confirmed.

2. Create a lottery with `entry_fee_cents=200` via the broadcaster's session.
3. Have a viewer with a valid payment method enter the lottery.
4. Confirm HTTP 200 and two billing ledger rows (one debit, one credit) in DynamoDB.
5. Simulate failure: temporarily use a network-level intercept (e.g. `tc qdisc`) to
   drop the second DDB call, or patch the handler in a dev build.

### Observability

- Remove swallowed `except Exception` blocks; let errors propagate and be logged at
  ERROR level by the FastAPI exception handler with a full traceback.
- Add a structured metric `billing.lottery_entry_fee.transact_failed` for dashboards
  and PagerDuty.

### Rollout

No feature flag needed. Deploy with normal canary: monitor
`billing.lottery_entry_fee.transact_failed` and HTTP 500 rate on
`POST /broadcast/*/lottery/*/enter` for 30 minutes post-deploy.

### Effort

**S** (Small) — one function rewrite. Combined with GAP-0126 and GAP-0129 in a single
billing-atomicity PR, the total effort is **M** (Medium, 4–6 hours).

### Sequencing

1. Merge alongside GAP-0126 and GAP-0129 in a single PR.
2. Introduce `billing_utils.write_billing_pair()` helper (GAP-0129 recommendation)
