# GAP-0314: `message:viewed` SSE Handler Uses `invalidateQueries` Instead of `setQueriesData` — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `frontend/src/hooks/useMessagingStream.ts`.

## 1. Summary & Classification

**Bug statement**: The `message:viewed` SSE event handler in `useMessagingStream.ts` calls `queryClient.invalidateQueries({ queryKey: ["messages", conversationId] })` (line 125). This triggers a full network round-trip to re-fetch all messages in the conversation every time any participant marks any message as viewed. The MSG-005 ticket design explicitly required a synchronous in-cache mutation using `setQueriesData` to increment `read_by_count` / update `read_by_user_ids` on the matching message item, avoiding the network refetch entirely.

**Severity**: HIGH  
**Source ticket**: MSG-005 (GAP-0314)  
**Owning area**: Frontend / Messaging / SSE Events  
**Status**: Open — no fix deployed

**Verdict**: Claim **confirmed**. `frontend/src/hooks/useMessagingStream.ts:120–126` shows the exact `invalidateQueries` call described in the ticket. The SSE payload includes `message_id` and `viewer_id` (both extracted at lines 121–122), which are sufficient for a targeted cache update — but the code discards them and performs a full invalidation instead.

**Impact in one line**: Every read-receipt event triggers an unnecessary full message-list HTTP refetch, causing measurable traffic overhead and a visible content flicker in active conversations.

**Related tickets**: MSG-005, SECOPS-007 (dev/prod parity — no backend change required for this fix).

## 2. Current-State Investigation (Root Cause)

### SSE event handler — current code

```typescript
// frontend/src/hooks/useMessagingStream.ts:119-127
// Read receipts — update message delivery status in cache
if (eventType === "message:viewed" && conversationId) {
  const messageId = typeof data.message_id === "string" ? data.message_id : undefined;
  const viewerId = typeof data.viewer_id === "string" ? data.viewer_id : undefined;
  if (messageId && viewerId) {
    queryClient.invalidateQueries({ queryKey: ["message-views", conversationId, messageId] });
    queryClient.invalidateQueries({ queryKey: ["messages", conversationId] });  // <-- full refetch
  }
}
```

`queryClient.invalidateQueries({ queryKey: ["messages", conversationId] })` marks the entire infinite-query pages cache for `conversationId` as stale. React Query immediately re-fetches all pages that are currently rendered, issuing a `GET /messaging/conversations/{id}/messages` request even if the only change is a single `read_by_count` increment on one message out of potentially hundreds.

### What the SSE payload provides

The backend SSE event (`message:viewed`) carries:

```json
{
  "type": "message:viewed",
  "conversation_id": "<cid>",
  "message_id": "<mid>",
  "viewer_id": "<uid>",
  "viewed_at": 1234567890
}
```

This is sufficient to surgically update the cache: find the cached message with `message_id == mid`, increment its `read_by_count`, and add `viewer_id` to its `read_by_user_ids` array — without any network call.

### Why `invalidateQueries` is used instead

The `typing:update` event (lines 77–93) and `presence:update` event (lines 96–117) both use `setQueryData` / `setQueriesData` for surgical in-cache mutations. These were implemented first and demonstrate the correct pattern. The `message:viewed` handler was likely added in a later iteration and copied the simpler `invalidateQueries` pattern from the top of the file (lines 56–58) without realizing it would cause full refetches.

### Frequency and traffic impact

In a group chat with 10 participants where each message is viewed by 9 people, a single sent message generates 9 `message:viewed` SSE events, each causing a full message-list refetch. At a modest 30 messages per minute per conversation, this is 270 unnecessary HTTP requests per conversation per minute — plus the flicker from React Query replacing cached data with identical server data.

### Infinite-query cache structure

The messages cache uses `useInfiniteQuery` with key `["messages", conversationId]`. Each invalidation causes React Query to refetch from the first page, replacing the `pages[]` array entirely. This produces a visible layout shift in `ConversationView` as the message list momentarily shows loading state or re-renders from scratch.

## 3. Impact / Exploit / Blast Radius

**Traffic overhead**: In a conversation where 5 users are simultaneously active and exchanging 10 messages per minute, each user's client generates approximately:

- 10 `message:viewed` events/min per other participant = 40 total events/min for one user.
- Each event triggers 1 GET /messages request from that user's browser.
- 40 unnecessary HTTP GET requests per user per minute, purely for read receipts.

At 1,000 concurrent active conversations this is 40,000 unnecessary backend requests per minute, consuming both frontend-side React Query budget and backend-side DynamoDB read capacity.

**UI flicker**: `invalidateQueries` on an active infinite-query sets `isFetching: true`, which causes `ConversationView` to render loading spinners or re-mount message bubbles, perceptible as a 50–200ms flicker for each `message:viewed` event. In a conversation with high-frequency read receipts, this produces continuous flickering.

**Race conditions**: If a user is scrolled mid-conversation and a `message:viewed` invalidation triggers a full refetch, React Query may re-scroll the viewport or lose the current scroll position, depending on the `ConversationView` scroll-anchoring implementation.

**Blast radius**: Affects all conversations in the application whenever `useMessagingStream` is active (i.e., whenever `MessagesPage` or `ConversationView` is mounted). No security risk — this is a performance and UX gap, not an authorization or data-integrity issue.

## 4. Fix Design (Code-Level)

### Strategy

Replace the `invalidateQueries(["messages", conversationId])` call inside the `message:viewed` handler with a `setQueriesData` call that surgically patches the matching message item in the infinite-query cache. Retain the `invalidateQueries(["message-views", ...])` call, which is a separate narrower query used by the message detail panel.

### MessageOut type — expected read-receipt fields

From `frontend/src/api/types.ts`, `MessageOut` should include (or needs to be extended with):

```typescript
// Verify these fields exist on MessageOut in types.ts
read_by_count: number;
read_by_user_ids: string[];
```

If not present, add them (backend `_message_out_from_item` populates these — confirm field names from messaging.py).

### Cache update implementation

```typescript
// frontend/src/hooks/useMessagingStream.ts:119-127 — REPLACE with:

// Read receipts — surgically update the message in cache (no refetch)
if (eventType === "message:viewed" && conversationId) {
  const messageId = typeof data.message_id === "string" ? data.message_id : undefined;
  const viewerId = typeof data.viewer_id === "string" ? data.viewer_id : undefined;
  const viewedAt = typeof data.viewed_at === "number" ? data.viewed_at : Math.floor(Date.now() / 1000);

  if (messageId && viewerId) {
    // Update the fine-grained message-views query (unchanged)
    queryClient.invalidateQueries({
      queryKey: ["message-views", conversationId, messageId],
    });

    // Surgically patch the message in the infinite-query pages cache
    queryClient.setQueriesData<{
      pages: Array<{ messages: MessageOut[]; next_cursor?: string }>;
      pageParams: unknown[];
    }>(
      { queryKey: ["messages", conversationId] },
      (prev) => {
        if (!prev) return prev;
        return {
          ...prev,
          pages: prev.pages.map((page) => ({
            ...page,
            messages: page.messages.map((msg) => {
              if (msg.message_id !== messageId) return msg;
              // Deduplicate viewer IDs
              const existingIds: string[] = msg.read_by_user_ids ?? [];
              const updatedIds = existingIds.includes(viewerId)
                ? existingIds
                : [...existingIds, viewerId];
              return {
                ...msg,
                read_by_count: updatedIds.length,
                read_by_user_ids: updatedIds,
              };
            }),
          })),
        };
      },
    );
  }
}
```

### Type considerations

The `setQueriesData` type parameter must match the shape returned by `useInfiniteQuery` for the `["messages", conversationId]` key. Check `ConversationView.tsx` to confirm the exact response shape:

- If the API returns `{ messages: MessageOut[], next_cursor?: string }` per page, the generic above is correct.
- If the API returns a plain array (`MessageOut[]`) directly (as documented in MEMORY.md: "returns a plain array, NOT `{ messages: [...] }`"), adjust to:

```typescript
queryClient.setQueriesData<{
  pages: Array<MessageOut[]>;
  pageParams: unknown[];
}>(
  { queryKey: ["messages", conversationId] },
  (prev) => {
    if (!prev) return prev;
    return {
      ...prev,
      pages: prev.pages.map((page) =>
        page.map((msg) => {
          if (msg.message_id !== messageId) return msg;
          const existingIds: string[] = msg.read_by_user_ids ?? [];
          const updatedIds = existingIds.includes(viewerId)
            ? existingIds
            : [...existingIds, viewerId];
          return {
            ...msg,
            read_by_count: updatedIds.length,
            read_by_user_ids: updatedIds,
          };
        }),
      ),
    };
  },
);
```

### Stale-data fallback

The surgical cache update is optimistic with respect to the SSE payload. If the local cache does not contain the message (e.g., the message is on an un-fetched older page), the `setQueriesData` map finds no matching `message_id` and returns the pages unchanged — a no-op. This is safe: the read receipt count simply won't update for that page until the user scrolls to it and triggers a page fetch.

For the `["message-views", conversationId, messageId]` query (the detail view), the existing `invalidateQueries` call is retained — this is a narrow single-item query and the round-trip is acceptable for the detail panel.

### Dev/Prod parity (SECOPS-007)

This change is entirely in the frontend JavaScript bundle. There is no backend code change and no environment branching. The SSE payload structure is identical in dev and prod (both use `_sse_pack` in messaging.py). No feature flag required.

### Unit test — cache mutation logic

```typescript
// frontend/src/__tests__/useMessagingStream.read-receipts.test.ts

import { renderHook } from "@testing-library/react";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { useMessagingStream } from "../hooks/useMessagingStream";

test("message:viewed patches read_by_count without invalidating messages query", () => {
  const qc = new QueryClient();

  // Seed cache with a message
  qc.setQueryData(["messages", "conv_1"], {
    pages: [[{ message_id: "m_abc", text: "hello", read_by_count: 0, read_by_user_ids: [] }]],
    pageParams: [undefined],
  });

  // Simulate SSE event
  simulateSseEvent(qc, {
    type: "message:viewed",
    conversation_id: "conv_1",
    message_id: "m_abc",
    viewer_id: "user_bob",
    viewed_at: 1700000000,
  });

  const pages = qc.getQueryData<{ pages: any[][] }>(["messages", "conv_1"])?.pages;
  expect(pages?.[0][0].read_by_count).toBe(1);
  expect(pages?.[0][0].read_by_user_ids).toContain("user_bob");

  // Query should NOT be stale (no invalidation)
  expect(qc.getQueryState(["messages", "conv_1"])?.isInvalidated).toBe(false);
});
```

### Rollout

- Effort: **M** (0.5 day frontend change; 0.5 day test; TypeScript type verification).
- Feature flag: not needed for a pure frontend cache change. Can optionally gate with `REACT_APP_SSE_READ_RECEIPT_CACHE_PATCH_ENABLED` env var for A/B testing.
- Rollback: revert the `setQueriesData` block; restore the `invalidateQueries(["messages", ...])` call.
- Risk: low. The `setQueriesData` mutator is synchronous and idempotent; if the message is not found in cache, it is a safe no-op. Worst case: a user's read-count badge is briefly stale until the next natural invalidation (e.g., new message arrives). This is substantially better than the current continuous flicker.
- Sequencing: can be deployed independently of any backend change. No server-side migration required.
