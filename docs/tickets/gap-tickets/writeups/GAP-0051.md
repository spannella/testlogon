# GAP-0051: by_creative / by_surface / by_targeting Maps Written as Empty Dicts — Remediation Write-up

## 1. Summary & Classification

**Gap**: In `app/services/ad_analytics.py`, the `compute_hourly_rollup` function writes an
hourly analytics record to DynamoDB with the three breakdown maps (`by_creative`,
`by_surface`, `by_targeting`) hardcoded to empty dicts `{}`. As a result, the
`get_breakdown` endpoint — which aggregates these stored maps across daily rollup items —
always returns an empty array for every dimension (creative, surface, targeting).

**Severity**: HIGH  
**Source ticket**: ADS-008  
**Owning area**: Ad Analytics  
**Status**: Open — claim confirmed against live code.

**One-line impact**: All advertiser dimension-breakdown analytics (by creative, by placement
surface, by targeting segment) are non-functional; advertisers and admins see zero data for
every breakdown query.

**Related tickets**: GAP-0050 (compute_hourly_rollup never called), GAP-0049 (platform
revenue share not written), GAP-0054 (per-creator revenue share ignored in billing).

## 2. Current-State Investigation (root cause)

### compute_hourly_rollup writes empty maps

File: `app/services/ad_analytics.py`, lines 168–211.

```python
# lines 201–204 (the bug)
"by_creative": {},
"by_surface": {},
"by_targeting": {},
```

The function queries the `ad_billing` table for raw charge entries matching the
`campaign_id` (via `get_campaign_spending`, which calls the `ByCampaign` GSI), counts
total impressions and clicks, and then writes the rollup item — but it never decomposes
those entries by `creative_id`, `surface`, or targeting segment. All three breakdown maps
are unconditionally initialized to `{}` and written straight to DynamoDB (lines 208–210).

### get_breakdown reads those stored maps

The `get_breakdown` function (lines 96–140) calls `_fetch_daily_rollups` to load daily
rollup items from DynamoDB, then iterates over each item looking for `r.get(dim_key, {})`,
where `dim_key` is `"by_creative"`, `"by_surface"`, or `"by_targeting"`. Because
`compute_hourly_rollup` stored empty dicts, `dim_data.items()` always yields zero
entries and `aggregated` remains empty. The function returns `[]` for every call.

### The billing charge record does carry the needed metadata

Each billing ledger entry written by `_process_charge` (`app/services/ad_billing.py`,
lines 100–147) includes a `meta` dict containing `creative_id` and `content_id`
(line 70 for impression charges). The `surface` is available from the ad event tracking
context (passed into `track_ad_event` as a parameter and stored in the `ad_impressions`
table). This means the raw data is present in DynamoDB; it simply is never aggregated into
the rollup maps.

### The get_breakdown aggregation path is correct — the data source is empty

Looking at `get_breakdown` (lines 96–140) more carefully: the logic for extracting and
accumulating data from `by_creative` / `by_surface` / `by_targeting` is correctly written.
For example:

```python
dim_data = r.get(dim_key, {})
if isinstance(dim_data, dict):
    for key, metrics in dim_data.items():
        ...
        aggregated[key]["impressions"] += int(metrics.get("impressions", 0))
```

The aggregation loop would work correctly if the stored dicts were non-empty. The entire
breakdown feature is architecturally sound; only the write path in `compute_hourly_rollup`
is broken. This means the fix is entirely contained to one function with no changes to the
read path.

### Historical rollups also carry the same bug

Every rollup item ever written by `compute_hourly_rollup` since the system was deployed
contains empty breakdown maps. The `get_breakdown` endpoint has therefore never returned
meaningful data. Any advertiser who has called `GET /api/v1/ads/analytics/breakdown` has
received `{"data": [], "count": 0}` for every query since launch.

### Dev vs prod

The bug is identical in both environments. DynamoDB Local (dev) and DynamoDB in production
both receive the same empty rollup items. There is no env-specific codepath here.

## 3. Impact / Exploit / Blast Radius

**Advertisers** receive zero useful analytics: calling `GET /api/v1/ads/analytics/breakdown`
with `?dimension=creative`, `?dimension=surface`, or `?dimension=targeting` returns
`{"data": [], "count": 0}` for every campaign, regardless of actual ad spend. This is not a
slow degradation — it is a total failure from the first hour of rollup data onward.

**Business impact**:
- Advertisers cannot evaluate per-creative performance. Split-testing creatives is
  impossible without data, causing misallocation of ad budgets.
- Surface-level breakdowns ("which placement type drives CTR?") are completely dark.
- Targeting-segment analysis ("did the 25–34 demographic respond better?") cannot function.
- Platform credibility with advertisers depends on analytics quality; zero breakdown data
  risks advertiser churn and contract disputes.

**Financial risk**: Advertisers may demand refunds or clawbacks if they can demonstrate
that campaign optimization was impossible due to absent analytics. There is no security
exploit angle, but the functional failure is total and visible to all programmatic API
consumers.

## 4. Fix Design (code-level)

### Strategy

During `compute_hourly_rollup`, after fetching the billing ledger entries for the campaign
and hour, decompose each entry into its three dimensions and accumulate counters before
writing the rollup. Two data sources must be joined:

1. **`ad_billing` entries** (already fetched by `get_campaign_spending`): contain
   `creative_id` in `meta`, and `entry_type` to identify impressions vs clicks.
2. **`ad_impressions` entries** (query by `campaign_id`): contain `surface` and
   `creator_id`/`content_id` for surface and targeting breakdowns.

Because `compute_hourly_rollup` already has the campaign's billing entries, the simplest
approach is:

- Build `by_creative` from the billing `meta.creative_id` field.
- Build `by_surface` from the `ad_impressions` table, queried by campaign_id for the hour.
- Build `by_targeting` from the same `ad_impressions` table using the `geo_country` or
  targeting-segment attribute (whichever is stored; this is a "targeting group" dimension,
  not a hard user-segment — use `surface` + `slot_type` as a proxy if targeting segment
  is not stored on the impression record).

### Concrete change to `compute_hourly_rollup`

```python
def compute_hourly_rollup(campaign_id: str, account_id: str, hour: str) -> dict:
    from app.services.ad_billing import get_campaign_spending
    from boto3.dynamodb.conditions import Attr

    entries = get_campaign_spending(campaign_id, limit=1000)

    impressions = 0
    clicks = 0
    spend = 0
    by_creative: dict = {}
    by_surface: dict = {}
    by_targeting: dict = {}

    for e in entries:
        etype = e.get("entry_type", "")
        amt = int(e.get("amount_cents", 0))
        spend += amt
        meta = e.get("meta") or {}
        creative_id = meta.get("creative_id", "unknown")

        if etype == "impression_charge":
            impressions += 1
            _bump_dim(by_creative, creative_id, impressions=1, spend=amt)
        elif etype == "click_charge":
            clicks += 1
            _bump_dim(by_creative, creative_id, clicks=1, spend=amt)

    # Build by_surface from ad_impressions table for this campaign
    try:
        resp = T.ad_impressions.scan(
            FilterExpression=Attr("campaign_id").eq(campaign_id),
            Select="ALL_ATTRIBUTES",
        )
        for imp in resp.get("Items", []):
            surface = imp.get("surface", "unknown")
            slot_type = imp.get("slot_type", "unknown")
            surface_key = f"{surface}/{slot_type}"
            evt = imp.get("event_type", "")
            _bump_dim(
                by_surface, surface_key,
                impressions=1 if evt == "impression" else 0,
                clicks=1 if evt == "click" else 0,
                spend=0,
            )
            # Use geo_country as a targeting proxy dimension
            geo = imp.get("geo_country", "unknown")
            _bump_dim(
                by_targeting, geo,
                impressions=1 if evt == "impression" else 0,
                clicks=1 if evt == "click" else 0,
                spend=0,
            )
    except Exception:
        logger.warning("by_surface_build_failed campaign_id=%s hour=%s", campaign_id, hour)

    rollup = {
        # ... existing fields ...
        "by_creative": by_creative,
        "by_surface": by_surface,
        "by_targeting": by_targeting,
        # ...
    }
    T.ad_analytics_rollups.put_item(Item={k: v for k, v in rollup.items() if v is not None})
    return rollup


def _bump_dim(d: dict, key: str, *, impressions: int = 0, clicks: int = 0, spend: int = 0):
    entry = d.setdefault(key, {"impressions": 0, "clicks": 0, "spend_cents": 0})
    entry["impressions"] += impressions
    entry["clicks"] += clicks
    entry["spend_cents"] += spend
```

The `_bump_dim` helper is a pure function with no I/O; it is safe to unit-test in isolation.

### Performance note

The `T.ad_impressions.scan` call with a `FilterExpression` is a full-table scan and will
not scale. A GSI on `campaign_id` (e.g., `ByCampaign`) should be added to
`AdImpressions` in `scripts/local-ddb-init.py` to replace the scan with a targeted query.
This is flagged as a follow-on: the logic fix is independent of the GSI addition and the
scan is acceptable for low-volume dev/early prod.

### Dev / Prod parity (SECOPS-007)

`compute_hourly_rollup` only touches DynamoDB. In dev it reads DynamoDB Local (port 8001);
in prod it reads the real DynamoDB table. The boto3 client is already routed through
`app/core/tables.py`. No new AWS service is introduced; no `if dev_mode:` branches are
needed. The fix satisfies SECOPS-007 by construction: the same code path executes in both
environments with only the DynamoDB endpoint differing, controlled by `DDB_ENDPOINT_URL`.

### Backward compatibility

Existing rollup items already stored in DynamoDB have empty breakdown maps. The
`get_breakdown` aggregation path is additive — it simply won't return rows for
periods whose rollup records were computed under the old code. A one-time backfill
of historical rollup items is possible but optional; new rollups will immediately
produce correct data going forward.

### Manual QA

1. Run `just restart` to wipe DDB.
2. Create a test advertiser account, campaign, and creative via the API.
3. Send several `GET /ui/ads/serve` requests followed by `GET /ui/ads/track?event=impression&...` calls to generate billing entries.
4. Manually invoke `compute_hourly_rollup("campaign_id", "account_id", "2026-05-29T14")`.
5. Call `GET /api/v1/ads/analytics/breakdown?dimension=creative` — expect non-empty rows.
6. Repeat for `dimension=surface` and `dimension=targeting`.
7. Verify that `by_creative` keys are the `creative_id` strings that appeared in the impression events.
8. Verify that `by_surface` keys are `"feed/native_post"` (or whichever surface was used).

### Edge cases to validate

- **No impressions in the hour**: `compute_hourly_rollup` should write empty dicts (acceptable; the aggregation handles zero entries gracefully).
- **Multiple creatives in one campaign**: each creative ID should appear as a separate key in `by_creative` with its own impression/click/spend counters.
- **Unknown surface**: if an impression record has no `surface` field, the code should use `"unknown"` as the surface key rather than raising.
- **DynamoDB scan failure**: if the `ad_impressions.scan` call throws, the breakdown maps should fall back to `{}` (acceptable degradation) rather than failing the whole rollup write.

### Observability

Add a `logger.info("rollup computed by_creative=%d by_surface=%d by_targeting=%d", ...)` line after the rollup write so that the background job log shows dimension counts per execution. A count of zero after a period with known impressions indicates the scan is finding no matching records and warrants investigation.

### Rollout

- **Effort**: M (2–3 days including GSI addition and tests)
- **Risk**: Low — additive change; existing rollup records simply lack breakdowns for historical periods.
- **Sequencing**: Fix GAP-0050 (background job wiring) in the same PR so the rollup function is actually called; fixing the empty maps without fixing the caller provides no user-visible improvement. The `AdImpressions` GSI addition can be a follow-on PR.
- **Rollback**: Reverting the PR leaves the previous behavior (empty maps); no DynamoDB schema migration is required. The only observable difference is that `by_creative`, `by_surface`, `by_targeting` will contain populated data going forward instead of empty dicts.
