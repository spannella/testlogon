# GAP-0339: `process_deletion()` Does Not Delete Messages, Conversations, or Participants — Remediation Write-up

> Source ticket: PRIVACY-001 · Severity: HIGH · Effort: M · Status: Open

## 1. Summary & Classification

**Bug statement.** `process_deletion()` in `app/services/gdpr_service.py` executes a ten-step account deletion procedure covering billing records, profile, addresses, contacts, calendar events, subscriptions, account state, tickets, and video metadata. It does not delete any messaging data: the `Messages`, `Conversations`, or `Participants` tables are never queried during deletion. When a user's account is deleted, every direct message they sent or received, every group conversation they participated in, and their participant records in all conversations remain permanently in DynamoDB. This is a GDPR Article 17 (Right to Erasure) violation.

**Claim verdict: Confirmed.** Reading `process_deletion()` at lines 672–827 of `app/services/gdpr_service.py` shows ten deletion steps (Steps 1–10, lines 688–798). None of them reference `Messages`, `Conversations`, `Participants`, or any of the env-var-named messaging table names (`DDB_MESSAGES`, `DDB_CONVERSATIONS`, `DDB_PARTICIPANTS`). The messaging tables are only accessed inside `process_export()` at lines 455–481 (for data export), not in the deletion path.

**Severity and area.** HIGH / Privacy & GDPR Compliance. Article 17 of GDPR gives users the right to erasure of all personal data. Messages — which contain content, timestamps, sender identity, and recipient identity — are personal data. The platform's stated account deletion procedure claims to delete user data; the incomplete implementation silently fails to honour this claim.

**Related tickets.** PRIVACY-001 (parent), GAP-0338 (export runs synchronously — affects export path sharing the same service file), GAP-0340 (S3 files not deleted — companion deletion gap), companion PRIVACY-001 gaps "Newsfeed posts and comments not deleted" and "Cognito user not disabled/deleted on account deletion".

## 2. Current-State Investigation (root cause)

### The ten-step deletion path

`process_deletion()` starts at line 672 and defines steps 1–10. A complete audit of the steps:

- **Step 1 (lines 688–719):** Anonymises or deletes billing records from `T.billing`.
- **Step 2 (lines 722–728):** Calls `delete_user_data(user_sub)` from `app/services/account` (deletes sessions, TOTP, SMS, recovery, email records).
- **Step 3 (lines 730–735):** Deletes profile row from `T.profile`.
- **Step 4 (lines 737–744):** Deletes addresses from `T.addresses`.
- **Step 5 (lines 746–755):** Deletes contacts from `T.contacts`.
- **Step 6 (lines 757–764):** Deletes calendar events from `T.calendar` (key prefix `CAL#{user_sub}`).
- **Step 7 (lines 766–773):** Deletes subscriptions from `T.subscriptions` (key prefix `SUB#{user_sub}`).
- **Step 8 (lines 775–780):** Deletes account state from `T.account_state`.
- **Step 9 (lines 782–789):** Deletes tickets from `T.tickets`.
- **Step 10 (lines 791–798):** Deletes video metadata from `T.video_metadata`.

After Step 10, the function finalises the deletion request record (line 800) and sends a notification alert (line 815). No messaging-related step exists between Steps 1–10 or after Step 10.

### How the messaging tables are accessed elsewhere

The export path (`process_export()`, lines 455–481) does access messaging tables:

```python
# app/services/gdpr_service.py:457–481
try:
    from app.core.aws import ddb as _ddb
    msg_table = _ddb.Table("Messages")
    conv_table = _ddb.Table("Conversations")
    part_table = _ddb.Table("Participants")
    # Get all conversations the user participates in
    part_items = _query_all(part_table, Key("user_id").eq(user_sub))
    for p in part_items:
        cid = p.get("conversation_id")
        if cid:
            try:
                c_resp = conv_table.get_item(Key={"conversation_id": cid})
                c = c_resp.get("Item")
                if c:
                    conversations.append(c)
            except Exception:
                pass
            try:
                msgs = _query_all(msg_table, Key("conversation_id").eq(cid))
                messages_out.extend(msgs)
            except Exception:
                pass
except Exception:
    pass
```

This is the correct access pattern for the deletion path: query `Participants` by `user_id` GSI to find all `conversation_id` values, then iterate and delete. The deletion path must replicate this pattern and additionally delete the message items, participant items, and (where appropriate) the conversation record.

### Table naming convention

The messaging tables are referenced by string name rather than via the `T.*` table handle objects. Looking at `scripts/local-ddb-init.py`:

- `Messages` table: PK = `conversation_id`, SK = `message_id` (default name; overridable via `DDB_MESSAGES` env var)
- `Conversations` table: PK = `conversation_id` (no SK for the top-level record)
- `Participants` table: PK = `user_id`, SK = `conversation_id` with GSI `ByConversation` (PK = `conversation_id`)

The `Participants` table query for export uses `Key("user_id").eq(user_sub)`, which is the table's primary key. This is the correct index for "find all conversations this user is in" and requires no GSI.

### GDPR scope of deletion

For full compliance:
1. Delete all `Participants` rows where `user_id = user_sub` — removes the user's membership record from all conversations.
2. For each conversation where the user was the only participant (solo/DM where the other party also deleted), delete the `Conversations` row.
3. For DM conversations: decide whether to delete all messages in the conversation or only messages where `sender_id = user_sub`. GDPR Article 17 requires erasure of the requesting user's personal data. Messages from the other party remain their data and should be preserved. For practical purposes, `sender_id = user_sub` messages must be deleted; messages received are more nuanced.
4. For group conversations: delete only messages where `sender_id = user_sub`.

The most defensible minimum-viable compliance approach: delete all `Messages` items where `sender_id = user_sub` across all conversations, and delete all `Participants` items where `user_id = user_sub`.

## 3. Impact / Exploit / Blast Radius

**GDPR Article 17 non-compliance.** When a user submits a deletion request and it completes (status `"completed"`), the platform sends a "Your account has been deleted" notification (line 817). The user receives confirmation that their data was erased. In reality, every message they ever sent — including private DMs and group messages — remains in DynamoDB indefinitely. There is no expiry, no TTL on the `Messages` table records.

**Concrete scenario.**
1. User Alice sends private messages to Bob, including sensitive personal information.
2. Alice exercises her Article 17 right and submits a deletion request via the UI.
3. The platform confirms "Your account has been deleted."
4. An administrator can still read all of Alice's messages via DynamoDB console or any internal tooling that queries the `Messages` table.
5. If the platform suffers a data breach, Alice's message content is in the breach — despite Alice having an active deletion confirmation.

**Regulatory exposure.** Sending a false "deletion completed" confirmation while retaining personal data is an aggravating factor in GDPR enforcement proceedings. Supervisory authorities treat false notifications as evidence of bad faith, which can increase fines beyond the standard Article 83 percentages.

**Blast radius.** Affects every user who has ever sent a message and subsequently deleted their account. The gap is invisible to the deleted user (they can no longer log in to verify) and invisible to the platform (the deletion record shows `"completed"`).

## 4. Fix Design (code-level)

### New deletion step: messaging data

Insert a new "Step 11: Delete messaging data" between the existing Step 10 and the finalisation block:

```python
# app/services/gdpr_service.py — insert after line 798, before line 800

# Step 11: Delete messaging data (GDPR Article 17)
try:
    from app.core.aws import ddb as _ddb
    msg_table = _ddb.Table(os.environ.get("DDB_MESSAGES", "Messages"))
    conv_table = _ddb.Table(os.environ.get("DDB_CONVERSATIONS", "Conversations"))
    part_table = _ddb.Table(os.environ.get("DDB_PARTICIPANTS", "Participants"))

    # a) Find all conversations the user participates in
    part_items = _query_all(part_table, Key("user_id").eq(user_sub))
    deleted_messages = 0
    deleted_participants = 0
    deleted_conversations = 0

    for p in part_items:
        cid = p.get("conversation_id")
        if not cid:
            continue

        # b) Delete all messages in this conversation where sender = user_sub
        #    Use a GSI on sender_id if available; otherwise filter after query.
        try:
            all_msgs = _query_all(msg_table, Key("conversation_id").eq(cid))
            for msg in all_msgs:
                if msg.get("sender_id") == user_sub:
                    msg_table.delete_item(
                        Key={
                            "conversation_id": cid,
                            "message_id": msg["message_id"],
                        }
                    )
                    deleted_messages += 1
        except Exception as e:
            logger.warning("Deletion: message delete error for conv %s: %s", cid, e)

        # c) Delete the Participants row for this user in this conversation
        try:
            part_table.delete_item(
                Key={"user_id": user_sub, "conversation_id": cid}
            )
            deleted_participants += 1
        except Exception as e:
            logger.warning("Deletion: participant delete error for conv %s: %s", cid, e)

        # d) Check if conversation has any remaining participants;
        #    if none remain, delete the conversation record.
        try:
            remaining = part_table.query(
                IndexName="ByConversation",
                KeyConditionExpression=Key("conversation_id").eq(cid),
                Limit=1,
            )
            if not remaining.get("Items"):
                conv_table.delete_item(Key={"conversation_id": cid})
                deleted_conversations += 1
        except Exception as e:
            logger.warning("Deletion: conversation delete error for conv %s: %s", cid, e)

    summary["messages_deleted"] = deleted_messages
    summary["participants_deleted"] = deleted_participants
    summary["conversations_deleted"] = deleted_conversations

except Exception as e:
    logger.warning("Deletion messaging error: %s", e)
    summary["messaging_error"] = str(e)
```

The `import os` is already available in the module header area (standard library). The `os.environ.get("DDB_MESSAGES", "Messages")` pattern matches how `local-ddb-init.py` names the table.

### Dev/Prod parity (SECOPS-007)

All three messaging tables (`Messages`, `Conversations`, `Participants`) are present in both dev (DynamoDB Local port 8001) and production (AWS DynamoDB). The table names are configurable via environment variables, consistent between environments. The `_query_all` helper used throughout `process_deletion()` handles DynamoDB pagination transparently and works identically in both environments. No mock bypass, feature flag, or environment branch is needed.

The S3 endpoint (`S.s3_endpoint_url`) is respected in the export path; the deletion path does not touch S3 (that is GAP-0340), so no S3 parity concern arises here.

### Handling the "other party's messages" question

The fix above deletes only messages where `sender_id = user_sub`. Messages sent by other parties to the deleted user remain in the conversation for the other participants. This is the minimum required by GDPR Article 17: the deleted user's own authored messages (their personal data) are erased. The implementation matches the guidance in PRIVACY-001 ticket §7.

For an alternate interpretation (delete the entire conversation when one party deletes their account), the implementation would replace step (b) with a full batch-delete of all items for the `conversation_id`. This is more aggressive than legally required and would violate the other party's right to retain their own message history. The sender-only approach is correct.

### Backward compatibility

The `deletion_summary` dict returned by `process_deletion()` and stored in DDB gains three new keys: `messages_deleted`, `participants_deleted`, `conversations_deleted`. This is additive and backward-compatible.

### Rollout & risks

- **Irreversibility:** Deletion is permanent. Deploy behind a feature flag (`privacy_messaging_deletion_enabled`, defaulting to `False`) and validate in staging before enabling in production.
- **Large accounts:** A user with 1,000 conversations and 50,000 messages will require many DynamoDB round-trips. The deletion path is already synchronous (see GAP-0338 for the export async gap — the deletion path has a separate `start_deletion_scheduler_task` background loop that should absorb this latency). Confirm that the deletion scheduler runs this asynchronously.
- **GSI for sender_id:** The current approach queries all messages per conversation and filters by `sender_id` in Python. At high message volume, a `sender_id` GSI on the `Messages` table would allow a direct query. Defer as a follow-up optimisation.
- **Group conversations:** In group chats with many participants, the "are there remaining participants?" check fires once per conversation. This is acceptable at current scale.
- **Effort:** M — new deletion step (~60 lines), test file (~80 lines).
- **Rollback:** Remove Step 11 from `process_deletion()`. No data migration needed; already-deleted messages cannot be restored.
- **Sequence:** Deploy after GAP-0338 (async export/deletion architecture is foundational), independent of GAP-0340.
