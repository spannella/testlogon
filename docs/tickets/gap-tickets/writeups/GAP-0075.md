# GAP-0075: Withdrawal Endpoint Absent — Remediation Write-up

## 1. Summary & Classification

**Claim status: Confirmed.**

`app/routers/referrals.py` exposes endpoints for creating referral codes, listing them, viewing the dashboard, and listing commission history — but contains no `POST /ui/referrals/withdraw` endpoint. The service layer (`app/services/referrals.py`) similarly has no `withdraw` function. The dashboard response at `get_referral_dashboard` (lines 343–413) does compute `available_for_withdrawal_cents` (line 387) and surfaces it in the API response, making users aware they have a balance to redeem — but there is no mechanism to redeem it. The MON-004 payout integration (wallet credit or direct bank transfer) referenced in the AFFILIATE-001 ticket spec is entirely absent.

- **Severity**: HIGH (feature completeness + financial — users see real money balances with no redemption path)
- **Source ticket**: AFFILIATE-001
- **Owning area**: Referrals / Affiliate system / Billing
- **Status**: Open
- **Impact**: Users with earned commissions are shown an `available_for_withdrawal_cents` balance on the referral dashboard but cannot withdraw it. The balance is effectively locked. If the commission window expires, the earnings become permanently inaccessible.
- **Related tickets**: GAP-0074 (attribution race — must be fixed before withdrawal to prevent inflated balances), GAP-0008 (commission replay risk), MON-004 (payout pipeline integration).

The `available_for_withdrawal_cents` field is populated and served to the frontend. The commission `status` values in play are `pending`, `confirmed`, and `paid`. Nothing in the codebase ever sets a commission status to `paid` — the `record_affiliate_commission` function (line 238) always writes `status: "pending"`. No payout function transitions statuses. ### MON-004 payout integration absence

The AFFILIATE-001 ticket spec referenced a `withdraw(user_id, amount_cents)` function that would:
1. Validate the requested amount does not exceed `available_for_withdrawal_cents`.
2. Call the MON-004 payout service (wallet credit or payout account transfer).
3. Mark commission records as `paid` up to the withdrawn amount.
4. Write a `WITHDRAWAL#...` record to `app_single_table` for audit.

None of these components exist. The payout service (`app/services/` directory) contains no MON-004 implementation.

### Dev vs. prod behaviour

There is no functional difference between dev and prod for this gap: the endpoint simply does not exist in either environment. Any frontend call to `POST /ui/referrals/withdraw` returns 404 in both.


## 3. Impact / Exploit / Blast Radius

### User-facing experience

A creator or affiliate who has generated referral signups leading to confirmed purchases sees a nonzero `available_for_withdrawal_cents` on their dashboard. They have no way to redeem these funds. The dashboard is a dead end. This creates trust and legal exposure: users can argue they are owed money that the platform is withholding.

### Commission window expiry

`commission_window_ends_at` is set at attribution time (1 year by default, from `S.referral_commission_window_days=365`). `record_affiliate_commission` (line 257) checks `_now_iso() > attribution.get("commission_window_ends_at", "")` and returns `None` if the window has passed. However, commissions already recorded are not subject to expiry — they accumulate indefinitely as `pending` records. Without a withdrawal endpoint, these pending balances grow but can never be redeemed.

### Double-payment risk after fix (interaction with GAP-0074)

If GAP-0074 (attribution race) is not fixed before the withdrawal endpoint is added, inflated commission balances from duplicate attributions could be withdrawn. The fix ordering must be: GAP-0074 → GAP-0075.

### Blast radius

Every user who has earned referral commissions and cannot withdraw them. All commission records remain stuck in `pending` status, creating an ever-growing audit liability.

### Financial risk from incorrect withdrawal implementation

A naive implementation that does not use an atomic DDB condition check before marking commissions `paid` would be vulnerable to a double-withdrawal race (same pattern as GAP-0074 on the attribution side).


## 4. Fix Design (code-level)

### Service layer: app/services/referrals.py

Add a `withdraw` function that:
1. Reads the user's available balance.
2. Validates the requested amount.
3. Attempts an atomic write of a withdrawal record with a conditional expression to prevent double-withdrawal.
4. Marks commission records as `paid` up to the requested amount.
5. Credits the user's wallet via the billing service.

```python
from botocore.exceptions import ClientError


def withdraw(user_id: str, amount_cents: int) -> Dict[str, Any]:
    """Initiate a withdrawal of affiliate commission earnings.

    Atomically creates a withdrawal record, marks commission rows as paid,
    and credits the user's billing wallet.

    Raises:
        ValueError: if amount_cents <= 0, exceeds available balance, or
                    is below the minimum withdrawal threshold.
        RuntimeError: if a concurrent withdrawal is already in progress.
    """
    if amount_cents <= 0:
        raise ValueError("amount_cents must be positive")
    if amount_cents < S.referral_min_withdrawal_cents:
        raise ValueError(
            f"Minimum withdrawal is "
            f"${S.referral_min_withdrawal_cents / 100:.2f}"
        )

    tbl = _tbl()

    # 1. Compute current available balance
    commissions_resp = tbl.query(
        KeyConditionExpression=Key("pk").eq(f"AFFILIATE#{user_id}"),
    )
    commissions = commissions_resp.get("Items", [])

    paid = sum(
        _to_int(c.get("commission_cents", 0))
        for c in commissions
        if c.get("status") == "paid"
    )
    earned = sum(
        _to_int(c.get("commission_cents", 0))
        for c in commissions
        if c.get("status") in ("confirmed", "pending")
    )
    available = max(0, earned - paid)

    if amount_cents > available:
        raise ValueError(
            f"Requested {amount_cents} exceeds available "
            f"{available} cents"
        )

    # 2. Write withdrawal record atomically (prevents double-withdrawal)
    now = _now_iso()
    ts = now_ts()
    withdrawal_id = f"wd_{uuid.uuid4().hex[:12]}"
    withdrawal_pk = f"AFFILIATE#{user_id}"
    withdrawal_sk = f"WITHDRAWAL#{ts}#{withdrawal_id}"

    try:
        tbl.put_item(
            Item={
                "pk": withdrawal_pk,
                "sk": withdrawal_sk,
                "Entity": "AffiliateWithdrawal",
                "user_id": user_id,
                "withdrawal_id": withdrawal_id,
                "amount_cents": amount_cents,
                "status": "pending",
                "created_at": now,
            },
            ConditionExpression="attribute_not_exists(pk) AND attribute_not_exists(sk)",
        )
    except ClientError as exc:
        if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
            raise RuntimeError("Concurrent withdrawal detected; please retry")
        raise

    # 3. Mark commission rows as paid (up to amount_cents, oldest-first)
    to_mark = sorted(
        [c for c in commissions if c.get("status") in ("pending", "confirmed")],
        key=lambda c: c.get("created_at", ""),
    )
    remaining = amount_cents
    for comm in to_mark:
        if remaining <= 0:
            break
        comm_cents = _to_int(comm.get("commission_cents", 0))
        if comm_cents <= 0:
            continue
        try:
            tbl.update_item(
                Key={"pk": comm["pk"], "sk": comm["sk"]},
                UpdateExpression="SET #s = :paid, withdrawal_id = :wid",
                ExpressionAttributeNames={"#s": "status"},
                ExpressionAttributeValues={":paid": "paid", ":wid": withdrawal_id},
                ConditionExpression="attribute_exists(pk) AND #s IN (:p, :c)",
                ExpressionAttributeValues={
                    ":paid": "paid",
                    ":wid": withdrawal_id,
                    ":p": "pending",
                    ":c": "confirmed",
                },
            )
        except ClientError:
            pass  # already paid by concurrent run; skip
        remaining -= comm_cents

    # 4. Credit user wallet via billing service
    try:
        from app.services.billing_shared import new_ledger_entry, user_pk
        from app.core.tables import T
        _sk, credit_item = new_ledger_entry(
            key_name="pk",
            key_value=user_pk(user_id),
            entry_type="affiliate_withdrawal_credit",
            amount_cents=amount_cents,
            state="settled",
            reason="Affiliate commission withdrawal",
            meta={"withdrawal_id": withdrawal_id},
        )
        T.billing.put_item(Item=credit_item)
    except Exception:
        logger.error(
            "affiliate_withdrawal_billing_failed",
            extra={"user_id": user_id, "withdrawal_id": withdrawal_id},
        )
        # Mark withdrawal as failed so user can retry
        tbl.update_item(
            Key={"pk": withdrawal_pk, "sk": withdrawal_sk},
            UpdateExpression="SET #s = :f",
            ExpressionAttributeNames={"#s": "status"},
            ExpressionAttributeValues={":f": "failed"},
        )
        raise RuntimeError("Billing credit failed; withdrawal rolled back to pending")

    # 5. Mark withdrawal record as completed
    tbl.update_item(
        Key={"pk": withdrawal_pk, "sk": withdrawal_sk},
        UpdateExpression="SET #s = :c, completed_at = :t",
        ExpressionAttributeNames={"#s": "status"},
        ExpressionAttributeValues={":c": "completed", ":t": now},
    )

    return {
        "withdrawal_id": withdrawal_id,
        "amount_cents": amount_cents,
        "status": "completed",
        "created_at": now,
    }
```

### Router addition (app/routers/referrals.py)

```python
class WithdrawBody(BaseModel):
    amount_cents: int


@router.post("/withdraw", status_code=200)
def withdraw_commissions(body: WithdrawBody, ctx: dict = Depends(require_ui_session)):
    _require_referral_enabled()
    if not S.referral_withdrawal_enabled:
        raise HTTPException(503, "Withdrawal is temporarily disabled")
    user_id = ctx["user_sub"]
    try:
        result = withdraw(user_id, body.amount_cents)
    except ValueError as exc:
        raise HTTPException(400, str(exc))
    except RuntimeError as exc:
        raise HTTPException(409, str(exc))
    return result
```

### Dev/Prod parity (SECOPS-007)

All DynamoDB operations in `withdraw` use the same `_tbl()` handle that routes to `DDB_ENDPOINT_URL` (DynamoDB Local in dev, real DynamoDB in prod). The `T.billing` table write uses the same `billing_shared` helpers used throughout the billing stack. No mock-specific paths are introduced. The `referral_withdrawal_enabled` flag defaults to `False` in `.env.local.example`, matching the pattern for all other money-moving features. The flag should be set to `1` in production only after smoke testing.

### Minimum withdrawal floor

The `referral_min_withdrawal_cents` default of 1000 ($10) prevents micro-withdrawal spam. This is configurable per operator via env var.

### Alternatives considered

- **Payout to external bank account (MON-004 integration)**: The AFFILIATE-001 spec mentions MON-004 payout as the long-term target. Since MON-004 is not implemented, the immediate fix credits the user's in-platform wallet (same `T.billing` table used for all other credits). This is a complete, useful path. MON-004 integration can be wired in a follow-up without changing the withdrawal endpoint's contract.
- **Single-step: mark commissions paid + credit wallet in one DDB transaction**: `transact_write_items` could wrap step 3 and 4 atomically. Rejected because crediting the wallet requires a `billing_shared` helper that writes to a different table; `transact_write_items` across multiple tables works but adds complexity. The two-phase approach (withdrawal record → mark paid → credit wallet) with compensating status updates is simpler and consistent with how other billing flows work.
