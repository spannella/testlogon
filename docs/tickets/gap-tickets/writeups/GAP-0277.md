# GAP-0277: Profile Country/Name Change and Large Billing Transactions Never Create Trigger Events — Remediation Write-up

> Source ticket: KYC-016 · Severity: HIGH · Effort: M · Status: Open

## 1. Summary & Classification

**Gap**: The KYC ongoing-monitoring system defines a `create_trigger_event` function in `app/services/kyc_monitoring.py` that records events requiring ad-hoc review (supported types: `large_transaction`, `country_change`, `name_change`, `screening_hit`, `manual`). However, neither the profile update path nor the billing payment path ever calls this function. Profile nationality and name changes and large billing transactions are completely invisible to the monitoring layer.

**Claim verdict**: CONFIRMED with one precision correction. The ticket states the integration points are absent from "profile nationality/name updates." The profile model (`ProfileBase`, `app/models.py` lines 1370–1393) does not expose a `nationality` field; the profile service (`PROFILE_FIELDS`, `app/services/profile.py` lines 16–33) tracks `display_name`, `first_name`, `last_name`, `location`, and `mailing_address` — but not `nationality`. The correct tracked fields are `last_name`/`first_name` (for `name_change`) and `location` or `mailing_address.country` (for `country_change`). The ticket's language of "nationality" is slightly imprecise, but the core claim — that no trigger events are fired on profile update or large transaction — is correct.

**Severity**: HIGH. AML/KYC regulations require re-screening on material profile changes (name, country) and on large transactions. Without these hooks the monitoring system is partially blind even when its background loops are running (see GAP-0276).

**Owning area**: Profile — `app/services/profile.py`, `app/routers/profile.py`; Billing — `app/routers/billing.py`.

**Related tickets**: GAP-0276 (background loops not started), KYC-016.

### Which profile fields map to which trigger types

| PROFILE_FIELDS value | KYC trigger type | Rationale |
|---|---|---|
| `first_name`, `last_name` | `name_change` | Legal name change requires re-ID |
| `mailing_address` (specifically `.country` key) | `country_change` | Country-of-residence change triggers re-screening |
| `location` | `country_change` (secondary) | General location change, lower priority |

The `ProfileBase` model does not include a top-level `nationality` field; the ticket's reference to "nationality" most likely refers to the `mailing_address.country` sub-field, which controls the KYC jurisdiction.

## 3. Impact / Exploit / Blast Radius

### Profile change blindspot

A user who changes their legal surname (e.g., after marriage) or relocates to a sanctioned jurisdiction after KYC approval will never trigger a `name_change` or `country_change` review event. The monitoring dashboard will show `needs_review_count: 0` even though material changes have occurred. Combined with GAP-0276 (no background loops), the system would not catch this even in theory.

**Concrete scenario**: Alice holds Tier 2 KYC approved under a US address. She PATCH-updates her `mailing_address.country` to `"IR"` (Iran). No trigger event is created. The re-screening loop (once GAP-0276 is fixed) only re-checks the sanctions list; it does not re-evaluate jurisdiction eligibility. Alice retains full Tier 2 access indefinitely.

### Large-transaction blindspot

Any payment processed through the billing system, regardless of size, never fires a `large_transaction` trigger. The `kyc_large_transaction_threshold_cents` setting is essentially documentation-only code today. A user could process repeated $4 999 transactions under the de facto unlimited KYC monitoring blind spot.

### Combined blast radius

Both blindspots together mean the ongoing-monitoring system only ever fires on `manual` admin triggers or `screening_hit` events from re-screening. In practice, if GAP-0276 is not fixed either, even screening_hit never fires automatically. The monitoring system is entirely passive.

## 4. Fix Design (code-level)

### 4.1 Profile update hook in `app/services/profile.py`

Modify `apply_profile_update` to detect name and country/location changes and fire trigger events. The lazy import avoids a circular dependency (profile → kyc_monitoring; kyc_monitoring does not import profile):

```python
# app/services/profile.py — apply_profile_update (line 294)
def apply_profile_update(user_sub: str, updates: Dict[str, Any], *, replace: bool) -> Dict[str, Any]:
    current = get_profile(user_sub)
    base = empty_profile() if replace else current
    normalized = normalize_profile_payload(updates)
    updated = {**base, **normalized}

    audit_entries: List[Dict[str, Any]] = []
    ts = now_ts()
    changed_fields: set[str] = set()
    for field in PROFILE_FIELDS:
        if current.get(field) != updated.get(field):
            audit_entries.append({"ts": ts, "field": field,
                                   "from": current.get(field), "to": updated.get(field)})
            changed_fields.add(field)

    save_profile(user_sub, updated, audit_entries)

    # ── KYC trigger events (GAP-0277) ────────────────────────────────────
    _fire_profile_kyc_triggers(user_sub, current, updated, changed_fields)

    return updated


_NAME_FIELDS = frozenset({"first_name", "last_name"})
_COUNTRY_FIELDS = frozenset({"location"})


def _fire_profile_kyc_triggers(
    user_sub: str,
    current: Dict[str, Any],
    updated: Dict[str, Any],
    changed_fields: set[str],
) -> None:
    """Fire KYC monitoring trigger events for material profile changes."""
    try:
        from app.services.kyc_monitoring import create_trigger_event  # lazy import

        if changed_fields & _NAME_FIELDS:
            create_trigger_event(
                user_sub=user_sub,
                trigger_type="name_change",
                details={
                    "changed_fields": sorted(changed_fields & _NAME_FIELDS),
                    "from_name": f"{current.get('first_name','')} {current.get('last_name','')}".strip(),
                    "to_name": f"{updated.get('first_name','')} {updated.get('last_name','')}".strip(),
                },
                actor_sub="user",
            )

        old_addr = current.get("mailing_address") or {}
        new_addr = updated.get("mailing_address") or {}
        old_country = (old_addr.get("country") or "").strip().upper()
        new_country = (new_addr.get("country") or "").strip().upper()
        if new_country and new_country != old_country:
            create_trigger_event(
                user_sub=user_sub,
                trigger_type="country_change",
                details={"from_country": old_country, "to_country": new_country},
                actor_sub="user",
            )

    except Exception:  # pragma: no cover - never let monitoring failures break profile save
        import logging
        logging.getLogger(__name__).exception(
            "kyc.monitoring.profile_trigger_error user_sub=%s", user_sub
        )
```

The `except Exception` guard is intentional: a monitoring failure must never roll back a profile save.

### 4.2 Billing large-transaction hook in `app/routers/billing.py`

Identify every endpoint in `app/routers/billing.py` that processes a payment and add a post-write threshold check. The threshold is already in `S.kyc_large_transaction_threshold_cents`. Pattern:

```python
# After successfully writing a payment/charge record in billing.py
from app.services.kyc_monitoring import create_trigger_event as _kyc_trigger

def _maybe_fire_large_transaction_trigger(user_sub: str, amount_cents: int) -> None:
    """Fire a KYC large_transaction trigger if the amount exceeds the threshold."""
    try:
        from app.core.settings import S
        if amount_cents >= S.kyc_large_transaction_threshold_cents:
            create_trigger_event(
                user_sub=user_sub,
                trigger_type="large_transaction",
                details={"amount_cents": amount_cents,
                         "threshold_cents": S.kyc_large_transaction_threshold_cents},
                actor_sub="system",
            )
    except Exception:
        import logging
        logging.getLogger(__name__).exception(
            "kyc.monitoring.large_transaction_trigger_error user_sub=%s", user_sub
        )
```

This helper is called after each successful charge confirmation in the billing router (wallet deposit, tip, subscription charge, etc.).

### 4.3 Dev/Prod parity (SECOPS-007)

- `create_trigger_event` writes to `T.kyc_review_schedule` (DynamoDB) and calls `write_alert`. Both use the mocked DDB Local in dev and the real DynamoDB in prod — no branching needed.
- The profile update path is identical in dev and prod; the trigger fire is unconditional (not gated by `S.dev_mode`).
- The large-transaction threshold is configurable via `KYC_LARGE_TRANSACTION_THRESHOLD_CENTS` env-var; in dev the default `500_000` can be lowered for testing.

### 4.4 Backward compatibility

The `kyc_review_schedule` table must exist. In a fresh dev stack this table is created by `scripts/local-ddb-init.py` (line 154–162). Existing users with no schedule row are handled gracefully: `create_trigger_event` calls `get_review_schedule` and only upgrades the status if a `status=="active"` record exists (lines 209–211 of `kyc_monitoring.py`); it stores the trigger log regardless.

### Metrics / observability

Monitor the rate of `trigger_type=name_change` and `trigger_type=country_change` events in the audit log to detect anomalies (sudden spike may indicate account-takeover name changes).

### Rollout / risk

- **Risk profile**: LOW for the profile hook (a failed trigger is logged and swallowed, never breaking the profile save). MEDIUM for the billing hook (must ensure the trigger is added after the charge is confirmed, not before, to avoid spurious triggers on failed charges).
- **Sequencing**: Deploy after GAP-0276 (monitoring loops). Without the loops the triggers accumulate but no automatic action fires — the dashboard will still show them, which is useful for manual review.
- **Effort**: M (requires identifying every billing charge confirmation point and inserting the helper call; the profile side is straightforward).
