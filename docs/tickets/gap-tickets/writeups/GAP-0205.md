# GAP-0205: `check_and_alert` Returns Alert Details But Never Sends Email or Notification — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code in
> `app/services/payment_provider_health.py:569–592`,
> `app/services/alerts.py:458–479`, and related notification infrastructure.

## 1. Summary & Classification

**Claim status: Confirmed.** `check_and_alert` at
`app/services/payment_provider_health.py:569` constructs a dict with `alert_email`,
`breaches`, `provider`, `status`, `error_rate_bps`, and `avg_latency_ms`, and returns it
to the caller — but the function contains no call to any email service, push service, or
in-app notification service. The returned dict is discarded because `check_and_alert` has
no callers (see GAP-0204). Even after GAP-0204 is fixed and a background task begins
calling `check_and_alert`, the alert payload will be returned to that caller but nothing
will be delivered unless this gap is also fixed.

- **Severity**: HIGH
- **Source ticket**: FIN-014
- **Status**: Open
- **Owning area**: Payment Provider Health Monitoring / Alerts
- **One-line impact**: Configured payment-provider alert recipients never receive
  notifications when Stripe, PayPal, or CCBill degrades — the alert email address is read
  from config and placed into a return dict that nothing reads.

**Related tickets**: GAP-0204 (function never called — prerequisite); FIN-014 HIGH:
`toggle_provider` enforcement gap. GAP-0204 and GAP-0205 must be deployed together for
any end-to-end alert delivery to work. Cross-ref: `app/services/alerts.py` provides the
email delivery infrastructure used by the alert system elsewhere in the codebase.

## 2. Current-State Investigation (root cause)

### The function body

`app/services/payment_provider_health.py:569–592`:

```python
def check_and_alert(provider: str) -> Optional[Dict[str, Any]]:
    """Return alert details if the provider exceeds configured thresholds."""
    prov = normalize_provider(provider)
    status = get_provider_status(prov)
    config = get_provider_config(prov)
    if status["total_success"] + status["total_failure"] == 0:
        return None

    breaches: List[str] = []
    if status["error_rate_bps"] >= _to_int(config["alert_error_rate_threshold"]):
        breaches.append("error_rate")
    if status["avg_latency_ms"] >= _to_int(config["alert_latency_threshold_ms"]):
        breaches.append("latency")
    if not breaches:
        return None
    return {
        "provider": prov,
        "status": status["status"],
        "breaches": breaches,
        "error_rate_bps": status["error_rate_bps"],
        "avg_latency_ms": status["avg_latency_ms"],
        "alert_email": config["alert_email"],    # <-- email address collected
        "at": now_ts(),
    }
    # No send call. Function ends here.
```

The function terminates after building the dict. There is no import of `alerts.py`, no
`send_alert_email`, no `create_alert` call, no push notification, and no in-app
notification. The `alert_email` field is populated from `config["alert_email"]` — set by
the admin via the health config endpoint — but it is only passed back to the (non-existent)
caller where it is discarded.

### The config model

`get_provider_config` at `payment_provider_health.py:333` reads:
- `alert_email: str` — the email address for breach notifications.
- `alert_error_rate_threshold: int` — threshold in bps.
- `alert_latency_threshold_ms: int` — threshold in ms.

These fields are written by `update_provider_config` (line 360) via the admin REST
endpoint. The infrastructure to configure alerting is complete; only the delivery call is
missing.

## 3. Impact / Exploit / Blast Radius

- **Operational blind-spot**: When Stripe's error rate spikes to 30% (well above the 5%
  default threshold), the configured `alert_email` recipient receives nothing. The on-call
  engineer only discovers the outage when users report failed payments or when someone
  manually opens the health dashboard.
- **Mean time to detect (MTTD)**: Without proactive alerting, MTTD is bounded by human
  polling frequency. On a typical engineer schedule, a Saturday-night incident could go
  undetected for 8–12 hours.
- **Financial**: Failed payments during an undetected outage window result in lost revenue,
  chargebacks, and user churn. For a platform processing $50K/day through Stripe, a 6-hour
  outage at 30% failure rate = ~$9K in failed charges.
- **Cascading**: No in-app notification means ROOT/ADMIN users also see no alert badge in
  the UI during a provider incident, compounding the detection gap.
- **No security exposure**: The gap is operational, not a security vulnerability.
- **No data corruption**: `check_and_alert` is read-only.

## 4. Fix Design (code-level)

### `_dispatch_alert` — the delivery function

Add a `_dispatch_alert` function to `payment_provider_health.py` that handles both email
and in-app notification delivery. This function is called by the GAP-0204 background loop
whenever `check_and_alert` returns a non-`None` payload.

```python
# app/services/payment_provider_health.py — add after check_and_alert

def _dispatch_alert(alert: Dict[str, Any]) -> None:
    """Deliver a provider health alert via email and in-app notification.

    Called by the background health check task (GAP-0204) when a breach is
    detected. Handles dev/prod parity via send_alert_email (which writes to
    the dev email log in S.dev_mode instead of calling SES).

    Does nothing if ``alert_email`` is blank and the alerts table is not
    reachable — never raises so as not to kill the background loop.
    """
    from app.services.alerts import send_alert_email

    prov = alert.get("provider", "unknown")
    breaches = alert.get("breaches", [])
    status = alert.get("status", "unknown")
    err_bps = alert.get("error_rate_bps", 0)
    latency_ms = alert.get("avg_latency_ms", 0)
    alert_email = str(alert.get("alert_email") or "").strip()

    subject = (
        f"[ALERT] Payment provider {prov.upper()} is {status.upper()} "
        f"({', '.join(breaches)})"
    )
    body = (
        f"Payment provider alert\n"
        f"Provider : {prov}\n"
        f"Status   : {status}\n"
        f"Breaches : {', '.join(breaches)}\n"
        f"Error rate: {err_bps / 100:.1f}% ({err_bps} bps)\n"
        f"Avg latency: {latency_ms} ms\n"
        f"Detected at: {alert.get('at', '')}\n\n"
        f"Investigate at: /admin/payment-health/{prov}"
    )

    # Email delivery (SES in prod, dev log in dev mode).
    if alert_email:
        try:
            send_alert_email([alert_email], subject, body)
        except Exception:
            logger.exception("Failed to send provider health alert email for %s", prov)

    # In-app alert for ROOT/ADMIN users (best-effort).
    try:
        _create_system_alert_for_health(prov, status, breaches, err_bps, latency_ms)
    except Exception:
        logger.exception("Failed to create in-app alert for %s provider health", prov)


def _create_system_alert_for_health(
    provider: str,
    status: str,
    breaches: List[str],
    error_rate_bps: int,
    avg_latency_ms: int,
) -> None:
    """Write an in-app alert row to the alerts table for ROOT/ADMIN visibility."""
    # The alerts table uses user_sub as pk; use a sentinel for system-level alerts.
    # Adjust to match the actual schema used by app/services/alerts.py.
    try:
        T.alerts.put_item(Item={
            "user_sub": "SYSTEM",
            "alert_id": f"PPH#{provider}#{now_ts()}",
            "alert_type": "payment_provider_health",
            "severity": "high" if status == STATUS_DOWN else "medium",
            "provider": provider,
            "status": status,
            "breaches": breaches,
            "error_rate_bps": error_rate_bps,
            "avg_latency_ms": avg_latency_ms,
            "created_at": now_ts(),
            "read": False,
        })
    except Exception:
        logger.debug("Could not write system health alert for %s (alerts table may lack SYSTEM PK)", provider)
```

### Update `check_and_alert` to call `_dispatch_alert` internally

Alternatively, `check_and_alert` itself can call `_dispatch_alert` before returning,
eliminating the need for the background task caller to do so:

```python
def check_and_alert(provider: str) -> Optional[Dict[str, Any]]:
    """Check thresholds and dispatch alert if breached."""
    prov = normalize_provider(provider)
    status = get_provider_status(prov)
    config = get_provider_config(prov)
    if status["total_success"] + status["total_failure"] == 0:
        return None

    breaches: List[str] = []
    if status["error_rate_bps"] >= _to_int(config["alert_error_rate_threshold"]):
        breaches.append("error_rate")
    if status["avg_latency_ms"] >= _to_int(config["alert_latency_threshold_ms"]):
        breaches.append("latency")
    if not breaches:
        return None

    alert = {
        "provider": prov,
        "status": status["status"],
        "breaches": breaches,
        "error_rate_bps": status["error_rate_bps"],
        "avg_latency_ms": status["avg_latency_ms"],
        "alert_email": config["alert_email"],
        "at": now_ts(),
    }
    _dispatch_alert(alert)   # <-- NEW: deliver the alert before returning
    return alert
```

This design is simpler because the background task loop (`_provider_health_loop` from
GAP-0204) does not need to know about delivery — it can simply log the return value.

### Alert deduplication (rate-limiting)

Without deduplication, a sustained incident fires an alert email every 5 minutes for as
long as the provider is degraded. This floods the inbox. Add a cooldown sentinel row:

```python
_ALERT_COOLDOWN_SECONDS = 1800  # suppress repeat alerts for 30 min per provider

def _alert_cooldown_key(provider: str) -> str:
    return f"ALERT_COOLDOWN#{provider}"


def _is_alert_suppressed(provider: str) -> bool:
    """Return True if an alert was recently dispatched for this provider."""
    try:
        item = T.payment_provider_health.get_item(
            Key={"pk": _provider_pk(provider), "sk": "ALERT_COOLDOWN"}
        ).get("Item")
        if not item:
            return False
        last_sent = _to_int(item.get("last_sent_at", 0))
        return (now_ts() - last_sent) < _ALERT_COOLDOWN_SECONDS
    except Exception:
        return False


def _mark_alert_sent(provider: str) -> None:
    try:
        T.payment_provider_health.put_item(Item={
            "pk": _provider_pk(provider),
            "sk": "ALERT_COOLDOWN",
            "last_sent_at": now_ts(),
        })
    except Exception:
        pass
```

Call `_is_alert_suppressed` at the top of `_dispatch_alert`; call `_mark_alert_sent` after
a successful email delivery.

### Dev/Prod parity (SECOPS-007)

`send_alert_email` (imported from `app/services/alerts.py`) already handles dev/prod
parity: when `S.dev_mode` is `True` it writes the email to `S.dev_email_log`
(default `.logs/emails.log`) instead of calling SES. No additional branching is needed in
`_dispatch_alert`. The `T.alerts` table resolves to DynamoDB Local in dev and AWS DynamoDB
in prod via `app/core/tables.py`. The cooldown sentinel row is written to
`T.payment_provider_health`, the same table used for all other health data.

### Alternatives considered

- **PagerDuty / Slack webhook**: More operationally ergonomic than email for on-call.
  Appropriate as a follow-on; not blocked on this ticket. The `send_alert_webhook` function
  already exists in `alerts.py:536` for this pattern. Can be added as an additional
  delivery path in `_dispatch_alert` once a webhook URL is configured.
- **SQS/SNS fanout**: Decouples the alert delivery from the health-check loop. Correct at
  scale; over-engineered for the current architecture where all alert delivery uses synchronous
  SES calls. The swallowed-exception pattern in `_dispatch_alert` makes the sync path safe.
- **Only in-app notification, no email**: Insufficient — if the health dashboard is not
  being actively monitored, in-app alerts are not seen. Email is the minimal viable delivery
  channel for a critical alert.

### Rollout and risks

- **Effort**: S (approximately 60 lines: `_dispatch_alert`, `_is_alert_suppressed`,
  `_mark_alert_sent`, and the call insertion in `check_and_alert`).
- **Risk**: LOW. Email delivery uses the existing `send_alert_email` function which is
  battle-tested in the codebase. Exceptions are swallowed. The cooldown mechanism prevents
  email storms.
- **Risk (SES in production)**: Ensure `alerts_email_enabled=True` and `alerts_from_email`
  is set in the production `.env` before deploying, or the email path silently no-ops.
  Verify SES sending identity is verified for the `from` address.
- **Rollback**: Set `PAYMENT_PROVIDER_HEALTH_ENABLED=0` to disable the entire subsystem,
  or add a separate `PROVIDER_HEALTH_ALERTS_EMAIL_ENABLED` flag. In the worst case, remove
  the `_dispatch_alert` call from `check_and_alert` — the function reverts to the current
  behavior (return-only, no delivery).
- **Sequencing**: Deploy GAP-0204 first (background loop), then GAP-0205 (delivery). The
  interim state where the loop calls `check_and_alert` but delivery does nothing (stub
  `_dispatch_alert`) is safe and can persist briefly between deployments.
