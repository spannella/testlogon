# GAP-0307: Subscription revenue is invisible to the creator earnings dashboard — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/routers/subscription_server.py`,
> `app/services/creator_earnings.py`, and `app/services/creator_payouts.py`.

## 1. Summary & Classification

**Bug**: Creator subscription revenue — the largest revenue stream for most creators — is
completely invisible in the creator earnings dashboard and in the available-balance calculation
used by the payout system. Every time a subscriber is charged (new subscription, renewal,
upgrade/downgrade proration), the subscription server writes creator-facing ledger entries to
`T.subscriptions` under the partition key `CREATOR#{creator_id}`. The creator earnings service
(`app/services/creator_earnings.py`) queries exclusively under `USER#{creator_id}` in `T.billing`.
These are different tables with different partition key schemes: the two sets of records never
overlap, so subscription revenue is permanently invisible to the earnings dashboard and to payout
balance calculations.

- **Severity**: HIGH — direct financial integrity failure. Creators cannot see their subscription
  income; the payout system may refuse legitimate withdrawal requests or approve withdrawals only
  against non-subscription income (tips, unlocks), under-reporting the available balance.
- **Source ticket**: MON-003
- **Status**: Open
- **Owning area**: Monetisation / Creator Earnings & Subscription Server
- **Claim verdict**: CONFIRMED with precision correction. The ticket cites
  `app/routers/subscription_server.py:582,947`. Verified:
  - Line 582: `build_ledger_item` — stores under `pk = CREATOR#{creator_id}` in `T.subscriptions`.
  - Line 947: `save_ledger_entry(plan["creator_id"], charge_entry)` — one of many call sites.
  - `_query_credit_entries` at `app/services/creator_earnings.py:133` queries `T.billing` under
    `USER#{user_id}` with `Attr("type").eq("credit")`.
  - Subscription ledger entries use field `entry_type` (not `type`) and are stored in
    `T.subscriptions` (not `T.billing`). The mismatch is therefore two-dimensional: wrong table
    AND wrong field name.
- **Related tickets**: MON-003, MON-004 (GAP-0308, GAP-0309), SECOPS-007.


## 2. Current-State Investigation (root cause)

### Subscription server ledger writes

`save_ledger_entry` is defined at `app/routers/subscription_server.py:586`:

```python
# app/routers/subscription_server.py:580–587
def build_ledger_item(creator_id: str, entry: Dict[str, Any]) -> Dict[str, Any]:
    item = entry.copy()
    item.update({
        "pk": pk_creator(creator_id),          # "CREATOR#{creator_id}"
        "sk": f"LEDGER#{entry['created_at']}#{entry['entry_id']}",
        "entity": "ledger",
    })
    return item

def save_ledger_entry(creator_id: str, entry: Dict[str, Any]) -> None:
    ddb_put_item(build_ledger_item(creator_id, entry))  # writes to T.subscriptions
```

`pk_creator` at line 111 returns `f"CREATOR#{creator_id}"`. `ddb_put_item` (defined near the
top of the file) calls `T.subscriptions.put_item(...)`. The entry dict itself contains
`"entry_type": "charge"` or `"entry_type": "fee"` — never a `"type"` field.

Charge/fee entries for a new subscription (line 926–948):
```python

save_ledger_entry(plan["creator_id"], charge_entry)
```

### Creator earnings query

`_query_credit_entries` at `app/services/creator_earnings.py:133`:

```python
# creator_earnings.py:133–169
def _query_credit_entries(*, user_id: str, ...) -> List[Dict[str, Any]]:
    pk = f"USER#{user_id}"                       # wrong PK namespace

        resp = T.billing.query(                  # wrong table
            KeyConditionExpression=key_cond,
            FilterExpression=filter_expr, ...

```

Three mismatches:
| Dimension | Subscription server writes | Earnings service queries |
|-----------|---------------------------|--------------------------|
| Table | `T.subscriptions` | `T.billing` |
| PK | `CREATOR#{creator_id}` | `USER#{creator_id}` |
| Type field | `entry_type: "charge"` or `"fee"` | `type: "credit"` |

`get_available_balance` in `app/services/creator_payouts.py:55` has the same issue: it also
queries `T.billing` under `USER#{user_id}` with `Attr("type").eq("credit")`.

### Runtime manifestation

A creator with $500 in subscription revenue and $20 in tip revenue sees:
- Earnings dashboard total: **$20** (only tips, which are written to `T.billing` via the billing
  ledger path).
- Available balance: **$20**.
- Payout request for $200 rejected as "Insufficient balance".

In dev mode this manifests immediately because the dev stack uses DynamoDB Local for both
`T.subscriptions` and `T.billing`; there is no separate mock path.


## 3. Impact / Exploit / Blast Radius

### Financial integrity (creator-facing)

Creators are systematically under-reported. Every subscription payment — initial charge,
renewal, upgrade — is invisible. For a creator earning 95% of income from subscriptions, the
dashboard shows near-zero earnings and the payout system blocks all withdrawals beyond the
tip/unlock residual.

### Platform liability

Creators who cannot withdraw legitimately-earned subscription funds have contractual grounds
for dispute. In jurisdictions with prompt-payment regulations for platform creators (e.g. DSA
Article 29, various US state creator-payment statutes), systematic suppression of earned balance
constitutes a breach.

### Compound effect with GAP-0308

GAP-0308 (reversed credits not excluded from balance) and this gap interact: if the fix for
GAP-0307 is applied first, reversed/refunded subscription entries will suddenly appear in the
balance without the reversal filter, potentially inflating balances. Both fixes must be
coordinated (see sequencing in Section 5).

### No over-payment risk from this gap alone

Because subscription ledger entries are invisible, the balance is *under-reported*, not
over-reported. A creator cannot exploit this gap to withdraw more than they earned. The gap
causes under-withdrawal, not over-withdrawal.


## 4. Fix Design (code-level)

Two fix strategies exist. **Strategy A** (recommended) writes a `type: "credit"` LEDGER entry
to `T.billing` under `USER#{creator_id}` each time a subscription charge or renewal is recorded,
mirroring the existing pattern used by tips and unlocks. **Strategy B** adds a second query to
`_query_credit_entries` that reads from `T.subscriptions` under `CREATOR#`. Strategy A is
preferred because it consolidates all creator credit data in one table and one PK namespace,
which simplifies the payout balance calculation and keeps the query path single-table.

### Strategy A — Mirror subscription credits into T.billing

Add a helper function to `app/routers/subscription_server.py`:

```python
# app/routers/subscription_server.py — new helper
def _write_creator_billing_credit(
    creator_id: str,
    amount_cents: int,
    currency: str,
    reason: str,
    ts: int,
    subscription_id: str,
    subscriber_id: str,
) -> None:
    """Mirror a subscription creator credit into T.billing so that
    creator_earnings.py and creator_payouts.py can see it."""
    from app.core.time import now_ts as _now_ts
    entry_id = new_id("biled")
    T.billing.put_item(Item={
        "pk": f"USER#{creator_id}",
        "sk": f"LEDGER#{ts}#{entry_id}",
        "type": "credit",                      # matches creator_earnings filter
        "amount_cents": amount_cents,
        "currency": currency,
        "reason": f"subscription_{reason}",    # classified as "subscriptions" by classify_entry
        "ts": ts,
        "subscription_id": subscription_id,
        "subscriber_id": subscriber_id,
        "entry_id": entry_id,
        "created_at": ts,
        "meta": {
            "content_type": "subscription",
        },
    })
```

Call this immediately after each `save_ledger_entry` call for `entry_type="charge"`, passing
`amount_cents = invoice["amount_cents"] - fee_cents` (net amount after platform fee). The
platform fee entry should NOT be mirrored as a credit because it is platform revenue, not
creator revenue.

The four primary call sites in `subscription_server.py`:
- Line 947: new subscription charge
- Line 1331: renewal charge
- Line 1461: upgrade proration charge
- Line 1815: webhook-initiated charge

For refund/reversal entries (`entry_type="refund"` at line 1515), write a corresponding
`type: "debit"` or set `state: "reversed"` on the previously written billing credit — this
feeds into GAP-0308's fix and must be coordinated (see Section 5).

### Dev/Prod parity (SECOPS-007)

Both `T.billing` and `T.subscriptions` are backed by DynamoDB in prod and DynamoDB Local in
dev. The `_write_creator_billing_credit` helper uses only `T.billing.put_item`, which works
identically in both environments. There is no mock-only code path to maintain. No feature flag
is required, though a `SUBSCRIPTION_CREDIT_MIRROR_ENABLED` env-var flag is advisable during
rollout to allow emergency rollback without a code deploy.

### Backward compatibility and migration

Existing subscription charges already written to `T.subscriptions` under `CREATOR#` will not
automatically appear in `T.billing`. A one-time backfill script must:
1. Scan `T.subscriptions` for all `PK = CREATOR#*` + `SK begins_with LEDGER#` items with
   `entry_type = "charge"`.
2. For each, write the corresponding `T.billing` entry under `USER#{creator_id}`.

The backfill should be idempotent: use a conditional `put_item` with
`ConditionExpression="attribute_not_exists(pk)"` on each new entry to avoid double-counting.

### Alternative considered: dual-table query in creator_earnings.py

Rejected because it requires every read path (earnings summary, payout balance, paginated
transactions) to be updated separately, and the `T.subscriptions` ledger entries use a
different field schema (`entry_type` vs `type`), requiring normalization logic scattered across
multiple functions.


## 5. Testing, Verification & Rollout

### Regression test (pytest offline)

Add to `tests/test_subscription_server_charge_paths.py` or a new
`tests/test_creator_earnings_subscription_visibility.py`:

```python
import pytest
from unittest.mock import patch, MagicMock

def test_subscription_charge_is_visible_in_earnings(monkeypatch):
    """
    After a subscription charge, the creator earnings query must
    return a non-zero total including the subscription amount.

    Fails before fix: T.billing has no matching entry → total=0.
    Passes after fix: T.billing has mirrored credit entry → total > 0.
    """
    from app.services import creator_earnings

    # Simulate a billing credit that the fix writes
    fake_items = [{
        "pk": "USER#creator1",
        "sk": "LEDGER#1700000000#entry1",
        "type": "credit",
        "amount_cents": 900,    # $9.00 after 10% fee on $10 subscription
        "ts": 1700000000,
        "reason": "subscription_charge",
        "entry_id": "entry1",
    }]

    def fake_query(**kwargs):
        # Only return items if querying the right PK
        pk = kwargs["KeyConditionExpression"].get_expression()["format_map"].get(":pk", "")
        if "USER#creator1" in str(kwargs.get("KeyConditionExpression")):
            return {"Items": fake_items, "LastEvaluatedKey": None}
        return {"Items": [], "LastEvaluatedKey": None}

    with patch.object(creator_earnings.T.billing, "query", side_effect=fake_query):
        entries = creator_earnings._query_credit_entries(user_id="creator1")
        assert len(entries) == 1
        assert entries[0]["amount_cents"] == 900

    # Also test get_quick_stats returns non-zero
    with patch.object(creator_earnings.T.billing, "query", return_value={"Items": fake_items}):
        stats = creator_earnings.get_quick_stats(user_id="creator1")
        assert stats["all_time_cents"] == 900
```

**Before fix**: `_query_credit_entries` returns `[]` for any creator who only has subscription
revenue because `T.billing` has no `USER#{creator_id}` LEDGER entries. Both assertions fail.
**After fix**: `T.billing` receives mirrored credits; both assertions pass.

### Metrics / observability

Add a `logger.info("creator_billing_credit_written", extra={"creator_id": ..., "amount_cents": ...})`
in `_write_creator_billing_credit`. This allows ops to confirm backfill completion and monitor

### Rollout sequencing

1. Deploy backfill script in read-only mode (scan only, log what would be written).
2. Verify scan output matches expected subscription history.
3. Deploy production code change with `SUBSCRIPTION_CREDIT_MIRROR_ENABLED=1`.
4. Run backfill script in write mode during low-traffic window.
5. Validate earnings dashboard shows historical subscription revenue.
6. **Coordinate with GAP-0308 fix** — if reversal entries are not yet excluded from balance,
   apply GAP-0308 fix within the same release window to avoid a window where reversed
   subscription credits inflate balances.

### Metrics / observability

Add a counter `subscription_billing_credit_written_total` to `_write_creator_billing_credit`.
During rollout, compare this counter's rate against the `save_ledger_entry` call rate in
`subscription_server.py` — they should be equal (one billing credit per charge ledger entry).
A divergence indicates a code path was missed.

For the backfill, log `creator_billing_credit_backfilled` per creator processed, with the
total `amount_cents` migrated. After the backfill completes, sum up the new entries and
cross-validate against the existing `T.subscriptions` ledger totals per creator.

### Rollback

If the billing credit mirror causes unexpected side effects (e.g., double-counting from a
backfill bug), the `SUBSCRIPTION_CREDIT_MIRROR_ENABLED` feature flag allows the writes to be
disabled without a code deploy. To clean up incorrectly written billing entries, a targeted
DynamoDB scan on entries with `reason BEGINS_WITH "subscription_"` can identify and delete
them.

### Effort estimate: M (Medium)

Files changed: `subscription_server.py` (~30 lines across 4 call sites plus new helper),
`creator_payouts.py` (no change needed after Strategy A since it reads from `T.billing` which
will now have the data). New backfill script (~50 lines). Two new test functions. Estimated
3–4 hours implementation, 1 hour review, 0.5 hours backfill dry-run.

### Sequencing

Must be deployed before or in the same release as GAP-0308. If deployed alone first, new
subscription credits will appear in `T.billing` but reversed ones will not be filtered —
this is an acceptable intermediate state since it only inflates balance (not a chargeback
risk until GAP-0308 lands). The backfill must be run after the code deploy, during a
low-traffic window, to avoid racing with live subscription charge events.

### Risks

- Backfill double-counting if idempotency guard is omitted. Mitigate with conditional write.
- If a creator has very high subscription volume, the backfill may take several minutes on
  DynamoDB; use `Limit=100` batching with exponential back-off.
- The `T.billing` table's GSI capacity must be sufficient to handle the backfill write burst;
  consider throttling the backfill to 50 writes/second if capacity is constrained.
