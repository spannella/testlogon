# GAP-0356: `emit_mention_alerts()` Never Called from Post/Comment Creation — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code. Source ticket: SOC-004.

## 1. Summary & Classification

**Plain-English statement**: The platform has a fully-implemented `@mention` detection and alert pipeline
in `app/services/social_alerts.py`. However, neither the post-creation handler
(`create_post`, `newsfeed.py:3304`) nor the comment-creation handler (`create_comment`,
`newsfeed.py:5324`) ever calls `emit_mention_alerts()`. As a result, any `@username` string
embedded in a post body or comment body is silently ignored: the mentioned user never receives
an in-app notification.

**Claim verdict**: CONFIRMED. A `grep -rn "emit_mention_alerts"` across the entire `app/`
tree returns only the definition site and an internal helper call inside
`social_alerts.py:667-701`. No router, service, or background job ever invokes it.

- **Severity**: HIGH
- **Source ticket**: SOC-004 (second-pass as-built review)
- **Status**: Open
- **Owning area**: Newsfeed / Social Notifications
- **Impact**: Mention notifications are completely non-functional. Users who type `@alice`
  in a post or comment will generate no alert to Alice. Mention-driven engagement (key
  metric for social products) is zero. Trust in the notification system erodes once users
  observe missed mentions.
- **Related tickets**: SOC-004 (parent), GAP-0358 (repost notification — same notification
  pipeline, similar gap pattern), GAP-0357 (bookmark/collections overlap).
- **Dependencies**: None blocking. The fix is purely additive.

## 2. Current-State Investigation (root cause)

### 2.1 The implemented-but-wired-up pipeline

`app/services/social_alerts.py` contains three tightly-coupled helpers:

```
social_alerts.py:604  def extract_mentions(text: str) -> List[str]
social_alerts.py:621  def resolve_mentions_to_user_ids(mentions) -> List[Dict]
social_alerts.py:667  def emit_mention_alerts(*, text, author_user_id,
                           author_display_name, context_type, context_id, post_id) -> int
```

`extract_mentions` uses `MENTION_REGEX` to parse `@username` tokens (lowercase,
deduplicated). `resolve_mentions_to_user_ids` does a DynamoDB scan on the `T.profile` table
filtering `alias == username` (capped at 20 mentions). `emit_mention_alerts` calls
`emit_social_alert()` for each resolved user with `alert_type="mention"` and a details
payload containing `context_type`, `context_id`, `post_id`, and a 100-character text
preview.

The function is complete and internally correct.

### 2.2 The missing call sites

**`create_post`** (`newsfeed.py:3304–3658`):

After writing `post_item` to DynamoDB at line 3609 and completing fan-out at line 3634, the
function returns a `PostResponse` at line 3649. There is no invocation of
`emit_mention_alerts`. The body text is available as:

```python
body_plain_text = content.get("body_plain") or content.get("body") or ""
# content is built by _content_from_payload(req) at line 3530
```

**`create_comment`** (`newsfeed.py:5324–5449`):

After writing the comment item at line 5389 and the two optional
`put_notification` calls (comment-on-post at 5397, reply-to-comment at 5416), the function
returns a `CommentResponse` at line 5429. No mention alert call exists. Comment body text is
available from `content["body_plain"]` (line 5347 for text-kind comments).

### 2.3 Why the gap exists in production

The scheduled-post path is also affected: `create_post` also returns early without
mention alerts for scheduled posts. Mentions in draft/scheduled posts would fire at write
time rather than at publish time — this is a minor sequencing question that should be
considered in the fix (see Section 4).

For media comments (`kind="gif"` or `kind="sticker"`), `body_plain` is `None`
(`newsfeed.py:5349`). `extract_mentions(None)` safely returns `[]` (see `social_alerts.py:615`).
No special guard is needed for media comments.

The dev/prod divergence is solely about call presence. The alert pipeline itself works
identically in both environments — `emit_social_alert` ultimately calls
`put_notification` (which writes to DynamoDB) and `sse_hub.publish` (for live SSE delivery).

## 3. Impact / Exploit / Blast Radius

This is a **silent feature failure**, not a security vulnerability.

**Users affected**: All users who mention others in posts or comments since the mention
pipeline was introduced. The gap is 100% reproducible on every mention.

**Functional impact**:

1. Mentioned users receive zero in-app alerts. The notification bell never increments for
   `mention` events.
2. The alert type `"mention"` appears in `ALERT_EVENT_TYPES` (alerts.py:141) and has a
   registered SSE delivery path and a preference/filtering UI, all of which remain dead until
   this call site is added.
3. Resolved `@username` lookups are O(1) DynamoDB point-reads per mention. The cap of 20
   mentions per text (social_alerts.py:632) means at most 20 profile reads per post/comment.
   No DynamoDB write amplification risk.

**Secondary risk**: If this fix is applied and the notify pipeline is therefore exercised for
the first time, pre-existing posts with `@mentions` will not retroactively generate alerts.
That is expected and acceptable behavior.

## 4. Fix Design (code-level)

### 4.1 Post creation call site

Add the following block at the end of `create_post`, immediately before the `return
PostResponse(...)` at line 3649. Place it inside the `if not is_scheduled:` branch so
scheduled posts do not emit mention alerts at draft time (alerts should fire at publish
time, which is handled by the scheduler publishing path — see §4.3).

```python
    # GAP-0356: emit mention alerts for @mentions in post body
    if not is_scheduled:
        try:
            from app.services.social_alerts import emit_mention_alerts
            emit_mention_alerts(
                text=body_plain_text,
                author_user_id=user_id,
                author_display_name=_post_fadt_display_name(user_id),
                context_type="post",
                context_id=post_id,
                post_id=post_id,
            )
        except Exception:
            logger.warning("emit_mention_alerts failed for post %s", post_id)
```

`_post_fadt_display_name` is already defined at `newsfeed.py:4138`.

### 4.2 Comment creation call site

Add the following block immediately after the existing reply-to-comment
`put_notification` block (after line 5427), before the `return CommentResponse(...)`:

```python
    # GAP-0356: emit mention alerts for @mentions in comment body
    if req.kind == "text" and content.get("body_plain"):
        try:
            from app.services.social_alerts import emit_mention_alerts
            emit_mention_alerts(
                text=content["body_plain"],
                author_user_id=user_id,
                author_display_name=_post_fadt_display_name(user_id),
                context_type="comment",
                context_id=comment_id,
                post_id=post_id,
            )
        except Exception:
            logger.warning("emit_mention_alerts failed for comment %s", comment_id)
```

The `kind == "text"` guard is correct: gif and sticker comments have `body_plain=None`,
and `extract_mentions(None)` handles it safely, but the guard avoids the function call cost.

### 4.3 Scheduled post publish path

The background scheduler that publishes scheduled posts (wherever it calls the equivalent
of `create_post` or sets `status=published`) must also call `emit_mention_alerts`. The
body text is already stored in the DDB post item under `body_plain`. Add a similar lazy
call in the publish scheduler after the post is promoted to `published`.

### 4.4 Dev/Prod parity (SECOPS-007)

`emit_mention_alerts` calls `emit_social_alert` which ultimately calls `put_notification`
(newsfeed.py:2419). `put_notification` writes to DynamoDB and attempts an SSE push via
`sse_hub.publish`. Both paths are the same code in dev and prod — there are no mock forks.
DynamoDB local (port 8001) and the `T.profile` / `T.alerts` tables are always available
during backend startup. No feature flag is required for this fix; the function is
defensive (empty mentions → immediate return).

If a feature flag is desired for gradual rollout, add `mention_alerts_enabled: bool = True`
to `app/core/settings.py` and wrap both call sites in `if S.mention_alerts_enabled`.

### 4.5 Alternatives considered

- **Background task (asyncio.create_task)**: Mention resolution involves DDB scans per
  mention. Running this in a FastAPI background task is possible but unnecessary — the DDB
  scan is O(1) per username (profile table Scan with Limit=1 and a filter) and is already
  capped at 20 mentions. Synchronous in-request execution with a broad try/except is
  simpler and less error-prone under the single-worker dev mode constraint.
- **Defer to fanout service**: Over-engineered for this scale. The existing `put_notification`
  is synchronous and sufficient.

## 5. Testing, Verification & Rollout

### 5.1 Pytest regression test (offline, fails before / passes after)

File: `tests/test_mention_alerts.py`

```python
import pytest
from unittest.mock import patch, MagicMock
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def _auth_headers(user_id: str = "user_alice"):
    # Use dev-mode X-User-Id header (tests run with DEV_MODE=1, no Cognito)
    return {"X-User-Id": user_id}

@patch("app.services.social_alerts.emit_mention_alerts")
def test_create_post_emits_mention_alerts(mock_emit):
    """GAP-0356: emit_mention_alerts must be called when a post contains @mentions."""
    resp = client.post(
        "/ui/posts",
        json={"body": "Hello @bob, check this out!", "visibility": "public"},
        headers=_auth_headers("user_alice"),
    )
    assert resp.status_code == 201
    mock_emit.assert_called_once()
    call_kwargs = mock_emit.call_args.kwargs
    assert "bob" in call_kwargs["text"]
    assert call_kwargs["context_type"] == "post"

@patch("app.services.social_alerts.emit_mention_alerts")
def test_create_comment_emits_mention_alerts(mock_emit, existing_post_id):
    """GAP-0356: emit_mention_alerts must be called when a comment contains @mentions."""
    resp = client.post(
        f"/ui/posts/{existing_post_id}/comments",
        json={"body": "Great post @charlie!", "kind": "text"},
        headers=_auth_headers("user_alice"),
    )
    assert resp.status_code == 201
    mock_emit.assert_called_once()
    call_kwargs = mock_emit.call_args.kwargs
    assert call_kwargs["context_type"] == "comment"

@patch("app.services.social_alerts.emit_mention_alerts")
def test_post_without_mention_no_alert(mock_emit):
    """GAP-0356: no call if the post body has no @mention."""
    client.post(
        "/ui/posts",
        json={"body": "Hello world!", "visibility": "public"},
        headers=_auth_headers("user_alice"),
    )
    mock_emit.assert_not_called()
```

Before the fix: `mock_emit.assert_called_once()` fails (called 0 times).
After the fix: all three assertions pass.

### 5.4 Observability

The `emit_mention_alerts` return value is the count of mention alerts emitted. Log it at
`DEBUG` level:

```python
n = emit_mention_alerts(...)
logger.debug("Mention alerts emitted: %d for post %s", n, post_id)
```

No new metrics table changes required. The existing alert SSE delivery already emits events
to connected subscribers.

### 5.5 Rollout and risks

- **Effort**: S (< 1 hour of code change, < 2 hours of testing)
- **Risk**: LOW. `emit_mention_alerts` is already tested in isolation. The change is additive
  (try/except wrapping ensures no post creation failures from mention alert errors).
- **Rollback**: Remove the two call sites; no DDB schema change required.
- **Sequencing**: Can be merged independently. No dependency on other open tickets.
  If the scheduled-post publisher exists, add the third call site in the same PR.
