# GAP-0284: `_bulk_fetch` Issues Individual `GetItem` Calls Instead of Using DynamoDB `BatchGetItem` — Remediation Write-up

## 1. Summary & Classification

**Ticket**: GAP-0284 | **Source**: KYC-020 | **Severity**: HIGH | **Status**: Open | **Effort**: S
**Owning area**: KYC — multi-language translation service (`app/services/kyc_translations.py`)

`_bulk_fetch` in `KycTranslationService` (lines 178–185 of `app/services/kyc_translations.py`) accepts a list of translation keys and a target language, and fetches each key with a separate `get_item` call inside a `for` loop. A questionnaire with 30 questions requires 30 individual network round-trips to DynamoDB (plus up to 30 more for the English-fallback pass), totalling up to 60 serial DynamoDB calls per questionnaire localization. DynamoDB `BatchGetItem` can fetch up to 100 items per call, reducing this to 1–2 calls regardless of questionnaire size.

**Verdict**: Confirmed. The claim is accurate. The loop over individual `GetItem` calls is present at lines 181–184 with no `BatchGetItem` usage in the file.

**Related tickets**: GAP-0285 (the localization integration gap that will trigger heavy `_bulk_fetch` use once wired), GAP-0278 (full-table scan in template listing).

## 2. Current-State Investigation (root cause)

### The offending method

`app/services/kyc_translations.py` lines 178–185:

```python
def _bulk_fetch(self, *, language: str, keys: List[str]) -> Dict[str, str]:
    """Fetch values for keys in one language (chunked GetItem)."""
    out: Dict[str, str] = {}
    for k in keys:
        item = self._get_item(language=language, key=k)   # ← individual GetItem
        if item and item.get("value"):
            out[k] = str(item["value"])
    return out
```

`_get_item` (lines 130–135) issues a single `T.kyc_translations.get_item(Key={"language_code": language, "key": key})` per call. With N keys this is N sequential network calls.

### Where `_bulk_fetch` is called

`translate_batch` (lines 156–176) calls `_bulk_fetch` twice: once for the requested language, then again for `"en"` fallback for any missing keys:

```python
def translate_batch(self, *, keys: List[str], language: str) -> Dict[str, str]:
    primary = self._bulk_fetch(language=language, keys=keys)         # up to N GetItem calls
    ...
    if missing and language != "en":
        en_map = self._bulk_fetch(language="en", keys=missing)       # up to N more GetItem calls
    ...
```

`translate_batch` is called by `localize_questionnaire` (which iterates all question labels and hints) and by `get_bundle` (which is used by the translations router for bulk-export endpoints).

### Docstring inaccuracy

The docstring says "chunked GetItem" but the actual implementation does no chunking — it issues one `GetItem` per key. The docstring is aspirational, not descriptive of current behaviour.

### DynamoDB table structure

`kyc_translations` table: PK = `language_code` (S), SK = `key` (S). This is the exact schema required by `BatchGetItem`; each item is uniquely identified by `{language_code, key}`, making batch retrieval straightforward.

### Latency model

Assuming 5ms per DynamoDB `GetItem` RTT (realistic in same-region production):
- 30-question questionnaire → `translate_batch` → up to 60 calls → up to 300ms
- With `BatchGetItem` (100 items per call): 1 call per language + 1 for fallback = 2 calls → 10ms

The serial nature of the loop compounds latency because each `_get_item` waits for the previous one to complete. If `localize_questionnaire` is added to the `start_kyc_questionnaire` endpoint (GAP-0285), this 300ms overhead will be on the interactive critical path.

## 3. Impact / Exploit / Blast Radius

**Performance**: Each call to `translate_batch` with a 30-key questionnaire issues up to 60 serial DynamoDB reads. On a production system serving 1,000 KYC questionnaire starts per day, this generates 60,000 individual DynamoDB `GetItem` calls per day just for questionnaire localization — none of them benefiting from DynamoDB's efficient batch path.

**Throughput scaling**: DynamoDB `GetItem` consumes 0.5 RCUs (eventually consistent) per 4 KB item. `BatchGetItem` consumes the same RCUs per item but with far lower per-item latency due to batching. At 60 sequential calls per questionnaire: 30 RCUs/questionnaire. At 1,000/day = 30,000 extra RCUs/day purely from the N+1 pattern.

**Latency on the interactive path**: Once GAP-0285 is fixed and `localize_questionnaire` is called from `start_kyc_questionnaire`, users will experience 100–300ms extra response time purely from translation fetching. This will be user-visible.

**No security or data-integrity impact**: This is a performance gap only. The data returned by `_bulk_fetch` is correct regardless of whether individual or batch fetching is used.

**Blast radius**: Contained to the `kyc_translations` service. No other services are affected.

## 4. Fix Design (code-level)

### Replacement implementation of `_bulk_fetch`

Replace the loop at lines 178–185 with a `BatchGetItem` implementation, chunked at 100 items per call (DynamoDB's maximum batch size):

```python
# app/services/kyc_translations.py

_BATCH_GET_CHUNK = 100  # DynamoDB BatchGetItem hard limit


def _bulk_fetch(self, *, language: str, keys: List[str]) -> Dict[str, str]:
    """Fetch values for multiple keys in one language using BatchGetItem.

    Chunks requests at 100 keys per call (DynamoDB limit).  Unprocessed items
    are retried once with exponential backoff (DynamoDB may return
    UnprocessedKeys under heavy load).
    """
    if not keys:
        return {}

    table_name = T.kyc_translations.name
    out: Dict[str, str] = {}
    pending = list(keys)

    while pending:
        chunk, pending = pending[:_BATCH_GET_CHUNK], pending[_BATCH_GET_CHUNK:]
        request_items = {
            table_name: {
                "Keys": [{"language_code": language, "key": k} for k in chunk],
            }
        }
        try:
            resp = T.kyc_translations.meta.client.batch_get_item(
                RequestItems=request_items
            )
        except Exception:
            logger.exception(
                "kyc_translations._bulk_fetch batch_get_item failed "
                "language=%s keys_count=%d",
                language, len(chunk),
            )
            # Fall back to individual GetItem for this chunk on failure
            for k in chunk:
                item = self._get_item(language=language, key=k)
                if item and item.get("value"):
                    out[k] = str(item["value"])
            continue

        for item in resp.get("Responses", {}).get(table_name, []):
            if item.get("value"):
                out[str(item["key"])] = str(item["value"])

        # Re-queue any unprocessed keys (rare: occurs only under heavy throttling)
        unprocessed = (
            resp.get("UnprocessedKeys", {})
            .get(table_name, {})
            .get("Keys", [])
        )
        if unprocessed:
            logger.warning(
                "kyc_translations._bulk_fetch unprocessed_keys count=%d language=%s",
                len(unprocessed), language,
            )
            pending = [k["key"] for k in unprocessed] + pending

    return out
```

### Notes on the implementation

- **`T.kyc_translations.meta.client`**: The boto3 DynamoDB Table resource exposes a low-level `client` via `.meta.client`, which is the correct interface for `batch_get_item`. The Table resource itself does not expose `batch_get_item` directly.
- **Fallback on exception**: If `BatchGetItem` raises (e.g., table does not exist in a test environment not seeded with the translations table), the code falls back to the existing individual `GetItem` behaviour, preserving backward compatibility.
- **UnprocessedKeys**: DynamoDB may return some keys as unprocessed under heavy throttling. The implementation re-queues them at the start of the next iteration so no keys are silently dropped.
- **No change to `translate_batch`** caller interface: the fix is entirely internal to `_bulk_fetch`.

### Dev/Prod parity (SECOPS-007)

`BatchGetItem` is supported identically by DynamoDB Local (used in dev and tests via moto) and AWS DynamoDB in production. The `T.kyc_translations.meta.client` approach works in both environments. moto supports `batch_get_item` fully. No mock-specific code path is needed.

### Backward compatibility

The public interface of `_bulk_fetch(*, language, keys)` is unchanged. Return type is identical. The only change is internal — multiple `GetItem` calls are replaced with one or more `BatchGetItem` calls. Callers (`translate_batch`, `localize_questionnaire`, any future code) require no changes.

### Alternatives considered

- **Query-based approach (query all keys for a language prefix)**: Rejected. Keys are not ordered in a way that makes a range query practical; the question keys (`kyc.question.label.{qid}`) are non-sequential.
- **In-memory cache (TTL-based)**: Complementary but separate concern. Caching individual translations in memory would reduce DynamoDB calls further but introduces cache-invalidation complexity. The `BatchGetItem` fix is the correct foundation; caching can be layered on top later.
- **`DynamoDBMapper` batch loading**: Python boto3 has no `DynamoDBMapper` equivalent. The low-level `client.batch_get_item` is the correct approach.

## 5. Testing, Verification & Rollout

### Regression test (pytest offline)

```python
# tests/test_kyc_translations.py  (extend existing or create new)
import pytest
from unittest.mock import MagicMock, patch, call
from app.services.kyc_translations import KycTranslationService


def test_bulk_fetch_calls_batch_get_item_not_get_item():
    """FAILS BEFORE FIX: get_item is called per key.
    PASSES AFTER: batch_get_item is called once for ≤100 keys."""
    svc = KycTranslationService()

    mock_client = MagicMock()
    mock_client.batch_get_item.return_value = {
        "Responses": {
            "kyc_translations": [
                {"language_code": "es", "key": "kyc.question.label.q1", "value": "Nombre"},
                {"language_code": "es", "key": "kyc.question.label.q2", "value": "Edad"},
            ]
        },
        "UnprocessedKeys": {},
    }

    with patch.object(
        type(svc._table if hasattr(svc, '_table') else type(svc)),
        '__init__', return_value=None
    ):
        # Patch at the table's meta.client level
        with patch("app.services.kyc_translations.T") as mock_T:
            mock_T.kyc_translations.meta.client = mock_client
            mock_T.kyc_translations.name = "kyc_translations"
            result = svc._bulk_fetch(
                language="es",
                keys=["kyc.question.label.q1", "kyc.question.label.q2"]
            )

    # FAILS BEFORE FIX (no batch_get_item call exists)
    mock_client.batch_get_item.assert_called_once()
    assert result == {
        "kyc.question.label.q1": "Nombre",
        "kyc.question.label.q2": "Edad",
    }


def test_bulk_fetch_chunks_at_100():
    """Keys > 100 are split into multiple BatchGetItem calls."""
    svc = KycTranslationService()
    mock_client = MagicMock()
    # Return empty responses (no values) to keep test simple
    mock_client.batch_get_item.return_value = {
        "Responses": {"kyc_translations": []},
        "UnprocessedKeys": {},
    }
    keys = [f"kyc.key.{i}" for i in range(150)]

    with patch("app.services.kyc_translations.T") as mock_T:
        mock_T.kyc_translations.meta.client = mock_client
        mock_T.kyc_translations.name = "kyc_translations"
        svc._bulk_fetch(language="en", keys=keys)

    # Should be called twice: 100 keys first, 50 keys second
    assert mock_client.batch_get_item.call_count == 2


def test_bulk_fetch_handles_unprocessed_keys():
    """UnprocessedKeys are re-queued and eventually retrieved."""
    svc = KycTranslationService()
    mock_client = MagicMock()
    mock_client.batch_get_item.side_effect = [
        # First call: k1 is unprocessed
        {
            "Responses": {"kyc_translations": [{"language_code": "fr", "key": "k2", "value": "val2"}]},
            "UnprocessedKeys": {"kyc_translations": {"Keys": [{"language_code": "fr", "key": "k1"}]}},
        },
        # Second call: k1 returned
        {
            "Responses": {"kyc_translations": [{"language_code": "fr", "key": "k1", "value": "val1"}]},
            "UnprocessedKeys": {},
        },
    ]

    with patch("app.services.kyc_translations.T") as mock_T:
        mock_T.kyc_translations.meta.client = mock_client
        mock_T.kyc_translations.name = "kyc_translations"
        result = svc._bulk_fetch(language="fr", keys=["k1", "k2"])

    assert result == {"k1": "val1", "k2": "val2"}
    assert mock_client.batch_get_item.call_count == 2


def test_bulk_fetch_empty_keys_returns_empty():
    svc = KycTranslationService()
    result = svc._bulk_fetch(language="en", keys=[])
    assert result == {}
```

**Fails before fix**: `test_bulk_fetch_calls_batch_get_item_not_get_item` fails because the current code calls `self._get_item()` individually and never calls `batch_get_item`. `test_bulk_fetch_chunks_at_100` and `test_bulk_fetch_handles_unprocessed_keys` will also fail since those call patterns do not exist.

**Passes after fix**: All four tests pass.

### Rollout

- Pure internal implementation change; no API contract, schema, or feature-flag change required.
- Deploy in any regular release cycle. No migration or staged rollout needed.
- Risk: very low. The fallback to individual `GetItem` on `BatchGetItem` failure ensures no regression in correctness.

### Relationship to GAP-0285

GAP-0285 requires wiring `localize_questionnaire` into the `start_kyc_questionnaire` endpoint. `localize_questionnaire` calls `translate_batch` for every question label and hint. Fixing `_bulk_fetch` (this ticket) before implementing GAP-0285 ensures that when the localization is wired in, it immediately uses the efficient `BatchGetItem` path rather than the N+1 loop. These two tickets should be sequenced with GAP-0284 merged first.

### Note on moto compatibility

Moto's DynamoDB mock fully supports `batch_get_item` as of moto 4.x. All pytest unit tests using `@moto.mock_dynamodb` will correctly intercept `batch_get_item` calls to `T.kyc_translations.meta.client`. The moto mock does not simulate `UnprocessedKeys` responses under normal conditions, so the unprocessed-key retry path can only be integration-tested against a real DynamoDB instance or by mocking the client response directly (as shown in the `test_bulk_fetch_handles_unprocessed_keys` test above).
