# GAP-0233: SSH Terminal Does Not Hook Into Session Recorder — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code; file:line citations are from
> the live codebase at `/home/ubuntu/testlogon`.

## 1. Summary & Classification

**Gap**: The `ParamikoSshBridge` WebSocket output loop in
`app/routers/browser_ssh_terminal.py` streams SSH output chunks directly to the
browser but never calls `append_events()` from `app/services/ssh_session_recording`.
As a result, live terminal sessions produce zero-event recordings unless the browser
client explicitly POSTs event chunks to `POST /ui/compute/ssh-recordings/{id}/events`.
The INFRA-010 design requires server-side automatic event capture during the live
session.

**Severity**: HIGH. Owning area: Infrastructure / SSH Terminal (INFRA-010).
**Status**: Open. **Source ticket**: INFRA-010. **Effort**: M.

**Claim accuracy**: Confirmed. The WebSocket handler's output loop at lines 774–778
(browser_ssh_terminal.py) reads `ssh_bridge.poll_output()` and sends the data to
the browser, but makes no call to `append_events`. The string `append_events`,
`start_recording`, `recording_id`, and `session_record` do not appear anywhere in
`app/routers/browser_ssh_terminal.py`.

**Impact**: Session recordings cannot be populated from live sessions. The recording
infrastructure (`app/services/ssh_session_recording.py`, router
`app/routers/ssh_session_recording.py`) exists and is functional, but is completely
disconnected from the live terminal WebSocket path.

**Related tickets**: INFRA-010 (parent), GAP-0234 (per-host `record_sessions` flag,
same source ticket), SECOPS-007 (dev/prod parity).


## 2. Current-State Investigation (root cause)

### The output loop — data forwarded but never recorded

`app/routers/browser_ssh_terminal.py` lines 774–778 (inside the main WebSocket
`while True` loop):

```python
if ssh_bridge:
    output = ssh_bridge.poll_output()
    if output:
        session_last_activity_at = now
        await websocket.send_json({"type": "output", "payload": {"data": output}})
```

`output` is the decoded SSH channel data from the reader thread. It is sent to the
browser but nothing else happens. There is no reference to `recording_id`,
`start_recording`, or `append_events`.

### The connect handler — recording never started

The `msg_type == "connect"` branch (lines 828–965) sets up `ssh_bridge` and calls
`ssh_bridge.connect()`. After a successful connect (line 930), it writes a structured
log entry and dispatches a `status:connected` WebSocket message — but makes no call
to `start_recording()` from `app/services/ssh_session_recording`.

### The session recording service — complete but unwired

`app/services/ssh_session_recording.py` exposes:

- `start_recording(user_sub, *, hostname, port, username, terminal_cols,
  terminal_rows, host_id, session_id) → Dict` (line 123) — creates a DynamoDB
  `RECORDING#` item.
- `append_events(user_sub, recording_id, events) → Dict` (line 210) — appends
  asciicast-format `[elapsed, type, data]` triples to the recording.
- `finish_recording(user_sub, recording_id) → Dict` — finalises the recording.

None of these are imported or called from `browser_ssh_terminal.py`.

### `_create_ssh_bridge` — discards all necessary parameters

`_create_ssh_bridge` (line 202) constructs a `ParamikoSshBridge` and returns it.
The bridge's `__init__` accepts only connection parameters; it has no knowledge of
`recording_id`, `user_sub`, or `session_id`. The recording state must therefore be
managed at the WebSocket handler level, parallel to `ssh_bridge`.

### Recording router — only explicit API calls populate recordings

`app/routers/ssh_session_recording.py` exposes
`POST /ui/compute/ssh-recordings/{id}/events`, which lets a client manually upload
event batches in asciicast `[elapsed, type, data]` format. This is a valid
supplementary path for browser-side capture (e.g., from `xterm.js` `onData`), but
it cannot be the only path for three reasons:

1. **Browser disconnection**: If the tab is closed, the network is interrupted, or
   the user navigates away, no further event POSTs are sent. The recording is
   permanently empty.
2. **Non-cooperative clients**: An automation script or custom WebSocket client that
   connects but does not implement the event-POST flow produces a zero-event recording
   silently, with no error.
3. **Forensic integrity**: Server-side capture cannot be suppressed by the client.
   Browser-side capture is trivially disabled by a user who modifies frontend code
   or uses a custom client. Compliance-grade recording must originate from the server.

### `start_recording` signature — all needed parameters are already in scope

`ssh_session_recording.start_recording` (line 123) accepts `hostname`, `port`,
`username`, `terminal_cols`, `terminal_rows`, `host_id`, and `session_id`. All of
these values are available in the WebSocket handler at connect time: `session_host`
(line 739), `session_port` (line 740), `normalized["username"]`,
`session_size["cols"]` / `["rows"]`, and `ws_session_id`. No new state needs to be
threaded into the handler — the gap is purely a missing call.

### Dev vs prod parity (SECOPS-007)

`app/services/ssh_session_recording.py` writes to `T.ssh_session_recordings`
(tables.py line 529). In dev mode this resolves to DynamoDB Local (port 8001). There
is no mock/real branch inside the recording service. The WebSocket handler hook
therefore behaves identically in dev and production, satisfying SECOPS-007. The
`SSH_SESSION_RECORDING_ENABLED` flag (section 4.5) gates the feature uniformly on
both paths.


## 3. Impact / Exploit / Blast Radius

**Primary impact — compliance and audit**: Without server-side event capture, session
recordings exist only if the browser client voluntarily sends data. A user who simply
closes the browser tab or uses a non-cooperative client produces a zero-event
recording. Compliance requirements for privileged access monitoring (PAM) cannot be
met.

**Operational impact — debugging**: When a user reports a problem during an SSH
session (e.g., "something deleted my files"), operators have no playback capability.

**No security exploit**: This gap does not grant additional access or expose data.
It is a missing recording feature, not an access-control bypass.

**Blast radius**: All users of the browser SSH terminal feature who expect session
recordings to be automatically populated. Affects all instance types (EC2 and K8s
pods, both accessed via the same WebSocket handler).


## 4. Fix Design (code-level)

### 4.1 State variables added to the WebSocket handler

In the WebSocket handler function, alongside the existing `ssh_bridge` variable
(line 733), add:

```python
recording_id:          str | None = None
recording_start_time:  float | None = None
```

### 4.2 Start recording on successful connect

In the `msg_type == "connect"` success branch, after line 933
(`session_last_activity_at = now`) and before the `send_json` call at line 953:

```python
# Start server-side recording
if S.ssh_session_recording_enabled:
    from app.services.ssh_session_recording import start_recording
    try:
        rec = start_recording(
            session_user_sub,
            hostname=session_host,
            port=session_port,
            username=str(normalized.get("username", "")),
            terminal_cols=session_size.get("cols", 80),
            terminal_rows=session_size.get("rows", 24),
            session_id=ws_session_id,
        )
        recording_id = rec["recording_id"]
        recording_start_time = time.time()
        logger.info(
            "browser_ssh recording_started",
            extra=_session_log_context(
                session_id=ws_session_id,
                user_sub=session_user_sub,
                host=session_host,
                port=session_port,
            ),
        )
    except Exception:
        logger.exception(
            "browser_ssh recording_start_failed session_id=%s", ws_session_id
        )
        recording_id = None   # recording failure must not abort the session
```

### 4.3 Append events on each output chunk

Replace lines 774–778:

```python
if ssh_bridge:
    output = ssh_bridge.poll_output()
    if output:
        session_last_activity_at = now
        await websocket.send_json({"type": "output", "payload": {"data": output}})

        # Append to server-side recording
        if recording_id and recording_start_time is not None:
            elapsed = round(time.time() - recording_start_time, 6)
            try:
                from app.services.ssh_session_recording import append_events
                append_events(
                    session_user_sub,
                    recording_id,
                    [[elapsed, "o", output]],
                )
            except Exception:
                logger.exception(
                    "browser_ssh recording_append_failed recording_id=%s",
                    recording_id,
                )
```

The `try/except` ensures recording failures never interrupt the live terminal.

### 4.4 Finish recording on session end

In the `finally` block (line 1093), after `ssh_bridge.close()`:

```python
if recording_id:
    try:
        from app.services.ssh_session_recording import finish_recording
        finish_recording(session_user_sub, recording_id)
        logger.info(
            "browser_ssh recording_finished recording_id=%s", recording_id
        )
    except Exception:
        logger.exception(
            "browser_ssh recording_finish_failed recording_id=%s", recording_id
        )
```

### 4.5 `S.ssh_session_recording_enabled` flag

`app/core/settings.py` already contains `ssh_session_recording_retention_days`
and related fields (confirmed by the service file imports). Add:

```python
ssh_session_recording_enabled: bool = os.environ.get(
    "SSH_SESSION_RECORDING_ENABLED", "true"
).lower() not in ("0", "false", "no")
```

The flag defaults `True` in production and can be set `false` for environments
where recording is not desired (e.g., low-storage dev testing).

### 4.6 Dev/Prod parity (SECOPS-007)

`start_recording` and `append_events` write only to DynamoDB, which is always
present (DynamoDB Local in dev, real DynamoDB in production). The `S.ec2_mock_enabled`
/ `S.k8s_mock_enabled` flags do not affect the recording path. Setting
`SSH_SESSION_RECORDING_ENABLED=false` disables recording on both paths uniformly.
No environment-specific branching is added.

### Alternatives considered

- **Hooking inside `ParamikoSshBridge._reader_loop`**: The reader thread runs in a
  background thread and has no access to the async DynamoDB client or the user
  context. Injecting a callback would require thread-safe queuing and is more complex
  than wiring at the poll site where the data is already being consumed.
- **Browser-only recording (xterm.js `onData`)**: Already supported via the manual
  event POST endpoint. Server-side recording is additive, not a replacement, and is
  the only option for automated compliance capture.
- **Stream to S3 instead of DynamoDB**: Valid for high-volume sessions, but out of
  scope. The existing DynamoDB-based asciicast format (with configurable max_events
  and max_bytes) is the designed storage path.

2. Ensure `SSH_SESSION_RECORDING_ENABLED=1` is set in `.env.local` (add it if
   absent; the default in `.env.local.example` should be set to `1`).
3. Authenticate as Alice via the browser.
4. Open the browser SSH terminal at `/browser-ssh`.
5. Connect to a test host (the mock host in dev mode, or a real SSH server if
   available on the test machine).
6. Run two or three commands: `echo hello`, `ls -la`, `hostname`.

8. Call `GET /ui/compute/ssh-recordings` — a recording item should appear with:

   - `hostname` matching the connected host
9. Call `GET /ui/compute/ssh-recordings/{id}/events` — events should be a list of
   `[elapsed, "o", data]` triples. Verify that the output of the typed commands

10. Verify that a second session to a different host creates a separate recording
    with a different `recording_id`.
11. Verify that `SSH_SESSION_RECORDING_ENABLED=0` disables recording: no new items
    appear in the recordings list when `false`.

### Performance considerations

`append_events` is called once per poll cycle in which `poll_output()` returns a
non-empty string. In typical usage (human typing speed), this is infrequent. High-
bandwidth sessions (large file transfers, `dd`, log tailing) may produce large chunks
at every 50ms poll interval. The recording service enforces `S.ssh_session_recording_max_bytes`
(default configurable) and raises `RecordingLimitExceeded` — this is caught by the
`try/except` wrapper and logged, ensuring the session is not interrupted.

### Observability

Three new structured log events are added by the fix:
- `browser_ssh recording_started` at connect success
- `browser_ssh recording_append_failed recording_id=<id>` on DDB write error
- `browser_ssh recording_finished recording_id=<id>` in the `finally` block

For metrics, extend the existing `record_browser_ssh_session_lifecycle` helper with
a `recording` tag in the session-end event: `recording=started|skipped|failed`.
This enables a dashboard panel showing the fraction of sessions with successful
recordings.

### Rollout

- **Effort**: M (approximately 35–50 lines added to the WebSocket handler; no
  changes to the recording service API, which is already fully implemented).
- **Risk**: Low. All three recording calls (`start_recording`, `append_events`,
  `finish_recording`) are wrapped in `try/except Exception` blocks. A DynamoDB
  outage or a recording bug cannot propagate to the live SSH session — the worst
  failure mode is a silently empty recording, which is exactly the current behavior.
- **Sequencing**: Should be delivered together with or after GAP-0234 (per-host
  `record_sessions` flag) so that automatic recording can be gated per host. The
  WebSocket changes can be behind `SSH_SESSION_RECORDING_ENABLED` as a global
  switch while per-host granularity is developed.
- **Rollback**: Set `SSH_SESSION_RECORDING_ENABLED=false` in `.env.local` or the
  production environment — immediately disables all server-side recording without
  a code rollback or redeploy.
- **Data volume estimate**: Each terminal session typically generates
  kilobytes to a few megabytes of terminal output. At 1000 concurrent sessions, DDB
  write capacity should be sized for 1–10 WCU per session per second during active
  periods. The existing `ssh_session_recording_max_bytes` limit caps runaway growth.
