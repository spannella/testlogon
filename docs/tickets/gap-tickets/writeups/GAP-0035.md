# GAP-0035: Missing CSRF Protection on Template Mutation Endpoints — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real code at file:line. No investigation doc exists
> (HIGH-severity ticket); the claim is verified directly against source code below.

## 1. Summary & Classification

**GAP-0035** identifies three mutation endpoints in the admin notification template router
that use the `require_admin_or_root` dependency instead of the CSRF-enforcing variant
`require_admin_or_root_csrf`. Because these endpoints accept cookie-authenticated browser
sessions, they are exposed to cross-site request forgery attacks: a malicious third-party
page can make the admin's browser issue a state-changing request that the server will
accept without verifying the CSRF token.

- **Severity**: HIGH
- **Source ticket**: ADMIN-002
- **Owning area**: Admin notification template management (`app/routers/admin_notifications.py`)
- **Status**: Open
- **Effort**: S (~30 minutes)

**Verdict**: Confirmed by direct code inspection. Three endpoints use `require_admin_or_root`:

| Endpoint | Method | Handler |
|---|---|---|
| `/ui/admin/notifications/templates/{template_id}` | PATCH | `update_notification_template` |
| `/ui/admin/notifications/templates/{template_id}/preview` | POST | `preview_notification_template` |
| `/ui/admin/notifications/templates/{template_id}/test-send` | POST | `test_send_notification_template` |

None of these handlers pass through `enforce_cookie_csrf`. The `require_admin_or_root_csrf`
dependency exists in `app/auth/policy.py:100-106` and is used correctly in other admin
routers. The fix is a three-line import+dependency substitution.

**Related tickets**: ADMIN-002 (original spec), SECOPS-007 (dev/prod parity).
No dependency blockers.

## 2. Current-State Investigation (Root Cause)

### 2.2 What `require_admin_or_root_csrf` does (and why it is absent here)

`app/auth/policy.py:100-106`:

```python
async def require_admin_or_root_csrf(
    request: Request,
    user: AuthenticatedUser = Depends(get_authenticated_user),
) -> AuthenticatedUser:
    """require_admin_or_root plus CSRF enforcement for cookie-auth requests."""
    enforce_cookie_csrf(request)
    return require_roles(user, {Role.ADMIN, Role.ROOT})
```

`app/auth/policy.py:71-97` — `enforce_cookie_csrf`:

```python
def enforce_cookie_csrf(request: Request) -> None:
    method = getattr(request, "method", "GET")
    if method.upper() in ("GET", "HEAD", "OPTIONS"):
        return
    cookies = getattr(request, "cookies", {}) or {}
    headers = getattr(request, "headers", {}) or {}
    session_cookie = cookies.get(session_cookie_name)
    if not session_cookie:
        # No browser session cookie → Bearer/API-key client → CSRF not applicable.
        return
    csrf_header = headers.get(csrf_header_name, "")
    csrf_cookie = cookies.get(csrf_cookie_name, "")
    if not csrf_header or not csrf_cookie:
        raise HTTPException(403, "Missing CSRF token")
    if csrf_header != csrf_cookie:
        raise HTTPException(403, "CSRF validation failed")
```

Key behaviour: Bearer-authenticated clients (no browser session cookie) are explicitly
exempt. Only cookie-authenticated sessions must present the CSRF token. This means the
fix does not break existing API integrations that use Bearer auth.

### 2.3 Why the gap exists

The router was initially written with `require_admin_or_root`. The CSRF-enforcing variant
was presumably added to `app/auth/policy.py` later (as part of SECOPS-007 hardening) but
the admin_notifications router was not updated at the same time. Both dependencies are
available via the same import; the gap is a one-word substitution per endpoint.

### 2.4 Scope of the gap

- **Read-only endpoints** (`GET /templates`, `GET /templates/{id}`) use
  `require_admin_or_root` and are unaffected — `enforce_cookie_csrf` skips all
  `GET/HEAD/OPTIONS` requests regardless.
- **Three mutation endpoints** (PATCH update, POST preview, POST test-send) are
  affected.
- The preview endpoint (`POST /preview`) is technically read-only in its side effects
  (renders a template without saving), but it is still a POST that accepts a
  body-supplied `sample_vars` dict. An attacker could forge a preview request to probe
  the template system or trigger server-side rendering with attacker-controlled variables.
  It should be CSRF-protected as a matter of defence-in-depth.
- The test-send endpoint is the highest-risk target: it causes the server to send an
  actual notification to a recipient, and an attacker who can forge this request can
  trigger admin-impersonated notification sends to arbitrary addresses.

## 3. Impact / Exploit / Blast Radius

### 3.1 Concrete CSRF exploit against `test-send`

1. Attacker creates a malicious web page hosted at `https://attacker.example.com`.
2. Page contains a JavaScript `fetch` (or hidden form) that issues:
   ```
   POST https://app.example.com/ui/admin/notifications/templates/welcome_email/test-send
   Cookie: (admin's browser session cookies are sent automatically by the browser)
   Content-Type: application/json
   Body: {"recipient": "victim@example.com", "sample_vars": {"...": "..."}}
   ```
3. The admin visits the attacker's page while logged into the app in another tab.
4. The browser sends the request including the admin's session cookies.
5. The server verifies the admin's session and role, finds no CSRF header check
   in `require_admin_or_root`, and processes the request.
6. A test notification is sent to `victim@example.com` under the admin's identity.

### 3.2 Concrete CSRF exploit against `update`

The same pattern against PATCH `/templates/{id}` allows an attacker to:
- Modify notification template subject/body to insert phishing links that will be sent
  to all platform users on the next real notification event.
- Disable active templates (set `active: false`) to suppress notifications (e.g., disable
  "suspicious login" alerts).

### 3.3 Prerequisite

The attacker must trick an authenticated admin into visiting the malicious page while
their admin session is active. This is a moderate-difficulty social engineering vector
(e.g., phishing email with a link to a page that silently makes the forged request).
Cookie `SameSite=Lax` mitigates cross-site form-based attacks but does not block
`fetch`-based CSRF with a `Content-Type: application/json` body when `SameSite` is
absent or when the admin navigates to the attacker's site directly.

### 3.4 Compliance exposure

Platform notification templates may contain legally mandated language (unsubscribe links,
disclosure text). An attacker who can silently corrupt these templates creates regulatory
compliance risk (CAN-SPAM, GDPR Article 7/12 for consent language, etc.).

## 4. Fix Design (Code-Level)

### 4.1 Import change — `app/routers/admin_notifications.py:13`

Replace:

```python
from app.auth.policy import require_admin_or_root
```

With:

```python
from app.auth.policy import require_admin_or_root, require_admin_or_root_csrf
```

### 4.2 Endpoint dependency substitution

Three `Depends(require_admin_or_root)` calls on mutation endpoints must be changed to
`Depends(require_admin_or_root_csrf)`:

**PATCH update** — `app/routers/admin_notifications.py:54`:

```python
# Before:
actor: AuthenticatedUser = Depends(require_admin_or_root),
# After:
actor: AuthenticatedUser = Depends(require_admin_or_root_csrf),
```

**POST preview** — `app/routers/admin_notifications.py:78`:

```python
# Before:
_actor: AuthenticatedUser = Depends(require_admin_or_root),
# After:
_actor: AuthenticatedUser = Depends(require_admin_or_root_csrf),
```

**POST test-send** — `app/routers/admin_notifications.py:92`:

```python
# Before:
actor: AuthenticatedUser = Depends(require_admin_or_root),
# After:
actor: AuthenticatedUser = Depends(require_admin_or_root_csrf),
```

**Note**: `require_admin_or_root_csrf` accepts a `Request` parameter in addition to the
`AuthenticatedUser`. FastAPI's dependency injection resolves `Request` automatically and
does not need to appear in the handler signature explicitly — the `Depends()` call
handles it. Existing handler signatures do not need to change.

### 4.4 Dev/Prod parity (SECOPS-007)

`enforce_cookie_csrf` reads `S.ui_session_cookie_name`, `S.ui_csrf_header_name`, and
`S.ui_csrf_cookie_name` from the settings singleton. These settings are populated from
`.env.local` in dev and from the production environment config in prod. The CSRF check
logic is environment-agnostic: it examines the incoming request cookies and headers
and applies the same validation in both environments.

Bearer-token clients (used by the admin E2E tests in `frontend/e2e/admin-roles.spec.ts`)
send no session cookie, so `enforce_cookie_csrf` returns early without raising. No E2E
tests are broken by this fix. The `e2e_admin_session_setup.py` cookie-based sessions
must send the `x-csrf-token` header on POST/PATCH requests to these endpoints — the
same pattern already used for all other CSRF-protected admin routes.

### 4.5 Alternatives considered

- **Add `SameSite=Strict` to all session cookies**: Would break legitimate cross-origin
  OAuth flows (e.g., SSO redirects). `SameSite=Lax` provides some protection against
  top-level navigation-triggered CSRF but not against `fetch`-based attacks. The CSRF
  token check is the correct defence here.
- **Switch endpoints to API-key auth only**: Would prevent admin browser workflows.
  Rejected — these are admin UI endpoints that legitimately use cookie auth.
- **Require re-authentication for template mutation**: Excessive friction for the
  low-financial-impact `preview` endpoint; disproportionate to risk. The CSRF token
  check is the appropriate and proportionate control.

## 5. Testing, Verification & Rollout

### 5.1 Regression tests (pytest offline)

```python
# tests/test_admin_notifications_csrf.py

def test_patch_template_without_csrf_header_returns_403(
    client, charlie_admin_session_cookies
):
    """Cookie-auth PATCH without x-csrf-token is rejected.
    Before fix: returns 200 (or 403 role-error if not admin).
    After fix: returns 403 CSRF error.
    """
    r = client.patch(
        "/ui/admin/notifications/templates/welcome_email",
        json={"subject": "Injected Subject"},
        cookies=charlie_admin_session_cookies,
        # No x-csrf-token header
    )
    assert r.status_code == 403
    # Ensure it's a CSRF error, not a role error
    assert "CSRF" in r.text or r.json().get("detail") in (
        "Missing CSRF token", "CSRF validation failed"
    )


def test_patch_template_with_correct_csrf_header_returns_200(
    client, charlie_admin_session_cookies, charlie_csrf_token
):
    """Cookie-auth PATCH with correct x-csrf-token succeeds."""
    r = client.patch(
        "/ui/admin/notifications/templates/welcome_email",
        json={"subject": "Updated Subject"},
        cookies=charlie_admin_session_cookies,
        headers={"x-csrf-token": charlie_csrf_token},
    )
    assert r.status_code in (200, 404)  # 404 if template doesn't exist in test DB


def test_post_test_send_without_csrf_header_returns_403(
    client, charlie_admin_session_cookies
):
    """POST test-send without CSRF token is rejected."""
    r = client.post(
        "/ui/admin/notifications/templates/welcome_email/test-send",
        json={"recipient": "test@example.com"},
        cookies=charlie_admin_session_cookies,
    )
    assert r.status_code == 403


def test_post_preview_without_csrf_header_returns_403(
    client, charlie_admin_session_cookies
):
    """POST preview without CSRF token is rejected."""
    r = client.post(
        "/ui/admin/notifications/templates/welcome_email/preview",
        json={},
        cookies=charlie_admin_session_cookies,
    )
    assert r.status_code == 403


def test_bearer_auth_patch_skips_csrf(client, charlie_admin_bearer_token):
    """Bearer-auth PATCH (no session cookie) does NOT require CSRF header.
    CSRF bypass protection must not block non-browser API clients.
    """
    r = client.patch(
        "/ui/admin/notifications/templates/welcome_email",
        json={"subject": "Bearer update"},
        headers={"Authorization": f"Bearer {charlie_admin_bearer_token}"},
        # No x-csrf-token header — bearer clients are exempt
    )
    # 200 if template exists; 404 if not. Either way, NOT 403.
    assert r.status_code != 403


def test_get_template_does_not_require_csrf(client, charlie_admin_session_cookies):
    """GET requests are always exempt from CSRF regardless of fix."""
    r = client.get(
        "/ui/admin/notifications/templates",
        cookies=charlie_admin_session_cookies,
    )
    assert r.status_code == 200
```

**Fails before**:
- `test_patch_template_without_csrf_header_returns_403` gets `200` (or role error `403`
  with `"code": "role_required"`, not a CSRF 403) instead of a CSRF `403`.
- `test_post_test_send_without_csrf_header_returns_403` gets `200`/`429`/`404` rather
  than `403`.

**Passes after**: All six tests pass.

### 5.2 E2E (Playwright) impact

Existing Playwright tests that call these endpoints through the browser (cookie-auth)
must include the `x-csrf-token` header. The test helper `apiPost` in
`frontend/e2e/admin-roles.spec.ts` already sends the CSRF token:

```typescript
async function apiPost(page: Page, identity: string, path: string, body: object) {
  return page.request.post(path, {
    headers: { "x-csrf-token": sessions[identity].csrf_token },
    data: body,
  });
}
```

Any new tests that exercise the template mutation endpoints through cookie-auth must
follow this same pattern. Bearer-auth calls (via the global `request` fixture) do not
need the header.

### 5.3 Manual QA steps

1. Start dev stack (`just up`), log in as charlie_admin.
2. Open browser DevTools → Network tab.
3. Attempt `PATCH /ui/admin/notifications/templates/welcome_email` with no
   `x-csrf-token` header. Verify `403 Missing CSRF token`.
4. Repeat with `x-csrf-token: <correct_token>` from the `ui_csrf` cookie.
   Verify `200` (or `404` if template doesn't exist — either is not a `403`).
5. Attempt `POST .../test-send` without the CSRF header. Verify `403`.
6. Verify that admin `GET /ui/admin/notifications/templates` still returns `200` without
   a CSRF header (GET must remain unaffected).

### 5.4 Observability

No additional logging is required. The existing `enforce_cookie_csrf` raises
`HTTPException(403, ...)` which is logged by FastAPI's request middleware with the
response status. Monitoring CSRF rejection rate on `/ui/admin/notifications/*` endpoints
can be added to the existing metrics dashboard by filtering on `403` responses for
those paths.

### 5.5 Rollout and rollback

- No schema changes; no database migration.
- No feature flag; CSRF protection is a security invariant.
- Deployment: hot-reload or rolling restart. Change is three lines of Python.
- Rollback: revert to `require_admin_or_root`. No data migration needed.
- **Admin UX impact**: Any admin browser client that was calling these mutation
  endpoints without the `x-csrf-token` header will start receiving `403` after deploy.
  The frontend must send the header. If the template management UI exists and sends
  cookie-auth requests, verify the frontend includes the header (all other admin pages
  already do via the axios client CSRF interceptor in `frontend/src/api/client.ts`).

### 5.6 Risk and effort

- **Risk**: Near-zero for correctly implemented admin UIs (they already send the CSRF
  header). Risk is low — only affects callers that rely on the absence of CSRF
  enforcement, which should not exist in a properly built admin UI.
- **Effort**: S — 30 minutes: import addition (1 line), three dependency swaps
  (3 lines), six pytest cases (~60 lines).
- **Sequencing**: Can land independently; no upstream dependencies.
