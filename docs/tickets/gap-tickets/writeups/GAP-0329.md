# GAP-0329: `_search_messages` authorization check loads only first 500 conversations — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing; cites `file:line`.

## 1. Summary & Classification

**Severity**: HIGH
**Source ticket**: PLATFORM-011
**Owning area**: Cross-conversation message search / authorization
**Status**: Open — pagination cap confirmed at `app/routers/search.py:290`

**Plain-English statement**: The `_search_messages()` function in the global search router builds a set of conversation IDs that the searching user is authorized to read (`allowed_conv_ids`) by querying the participants table. The query loop has a hard cap of 500 conversations: once 500 participant records are collected, the loop exits regardless of whether more exist. For a user who is a member of more than 500 conversations, message search results can leak messages from conversations 501+ — conversations whose IDs never appear in `allowed_conv_ids`, so the filter at line 310 (`if conv_id not in allowed_conv_ids: continue`) does not block them.

Wait — re-reading line 310 carefully: that line *skips* candidate messages whose `conv_id` is *not* in `allowed_conv_ids`. So the direction of the bug is the opposite of a leak: messages from conversations 501+ will be *excluded* from results even if the user is a member. The authorization check under-authorizes (omission) rather than over-authorizes (disclosure). However, the ticket claim as stated — "authorization check loads only first 500 conversations" — is fully confirmed as a code fact. Whether the consequence is a search result gap (benign) or an authorization bypass depends on the direction of the filter.

**Claim correction**: The ticket's stated impact ("authorization check loads only first 500 conversations") is accurate as a root-cause description. However, the security impact is more nuanced: the filter at `search.py:310` *excludes* results from conversations outside the 500-cap set, so the actual runtime effect for a user with >500 conversations is *incomplete search results* (missing messages from conversations 501+), not a data leak. This is a correctness/availability bug, not a confidentiality breach. It remains HIGH because search result gaps can cause users to miss important information, and because the incomplete allowlist could be exploited in an edge case if the search index contains stale participant records from conversations the user has left.

**Related tickets**: PLATFORM-011, GAP-0024 (related DynamoDB pagination gaps), search-messaging E2E tests (sections 37–40 in `frontend/e2e/search-messaging.spec.ts`).

## 2. Current-State Investigation (root cause)

### The pagination loop in `_search_messages()`

`app/routers/search.py:280–295`:

```python
# Step 1: Get the user's conversation IDs for authorization
parts: list[dict] = []
last_key = None
while True:
    kw: dict = {"KeyConditionExpression": Key("user_id").eq(user_id), "Limit": 500}
    if last_key:
        kw["ExclusiveStartKey"] = last_key
    resp = tbl_parts.query(**kw)
    parts.extend(resp.get("Items", []))
    last_key = resp.get("LastEvaluatedKey")
    if not last_key or len(parts) >= 500:
        break

allowed_conv_ids: set[str] = {p["conversation_id"] for p in parts}
```

The exit condition `if not last_key or len(parts) >= 500` means the loop exits on whichever comes first: DynamoDB returns no more pages (`not last_key`) OR the local `parts` list reaches 500 items (`len(parts) >= 500`). Because the inner `Limit=500` means DynamoDB returns at most 500 items per page, and the loop breaks when `len(parts) >= 500`, the loop always exits after exactly one page.

In practice this means: if a user is a member of 600 conversations, exactly 500 of their participant records are loaded. The `allowed_conv_ids` set has 500 members. The remaining 100 conversations are invisible to the search authorization check.

### The filter that depends on the incomplete set

`app/routers/search.py:309–311`:

```python
conv_id, msg_id = parts_split
if conv_id not in allowed_conv_ids:
    continue
```

If a search token appears in a message inside one of the 100 missing conversations, the `conv_id` for that message is not in `allowed_conv_ids`, so the candidate is silently skipped. The user does not see that message in search results, even though they are a legitimate participant in that conversation.

### The stale-participant edge case

DynamoDB participant records may contain stale entries if a user is removed from a group conversation but their participant record is not immediately deleted (a separate gap). In that edge case, the 500-cap set might include stale conversation IDs while excluding valid recent ones, depending on the DynamoDB sort order. Since `tbl_parts` is queried with `KeyConditionExpression=Key("user_id").eq(user_id)` and no explicit sort, DynamoDB returns items in primary key order, which is deterministic but not necessarily recency-ordered.

### Why the bug is latent in the current codebase

The E2E test suite (sections 37–40 in `frontend/e2e/search-messaging.spec.ts`) creates a small number of conversations per test run. The cap of 500 is never exceeded in test, so all tests pass. The bug only manifests for a real user who has been active on the platform for months and has accumulated many conversations (DMs, group chats, helpdesk threads, etc.).

## 3. Impact / Exploit / Blast Radius

**Primary impact — missing search results**: Any user with more than 500 conversations will receive incomplete cross-conversation message search results. The probability increases monotonically with user age and activity. Power users (moderators, support agents, creators with large followings) are most affected.

**Secondary impact — potential stale-participant access gap**: If the 500-item cap excludes a conversation the user recently joined, messages in that conversation are unreachable via search even if the user is an active, legitimate participant. This is an availability gap, not a security gap.

**Confidentiality risk (low, but present)**: The token-index query at `search.py:299–314` pulls raw `conv_id#msg_id` pairs from the MessageSearch index for any matching token. If a message's tokens are indexed but its conversation was deleted or the user was removed *after* indexing, the stale token-index entry would normally be filtered by the `allowed_conv_ids` check. With the 500-cap, the filter set is incomplete: a stale token-index entry for a conversation that *was* in the user's first 500 conversations but where the user was subsequently removed could pass the filter. This requires a narrow race condition but is worth noting.

**Blast radius in numbers**: On a platform with 10,000 active users, assume 5% have >500 conversations (500 users). Each affected user's cross-conversation message search is potentially incomplete from the moment they exceed the 500-conversation threshold.

## 4. Fix Design (code-level)

### 4.1 Remove the `len(parts) >= 500` early-exit condition

The fix is a single-line change in `app/routers/search.py`. Replace the premature exit condition:

**Before** (`search.py:289–291`):
```python
last_key = resp.get("LastEvaluatedKey")
if not last_key or len(parts) >= 500:
    break
```

**After**:
```python
last_key = resp.get("LastEvaluatedKey")
if not last_key:
    break
```

This is the minimal correct fix: the loop continues to paginate until DynamoDB signals there are no more items (`LastEvaluatedKey` is absent). All conversations are loaded into `allowed_conv_ids`.

### 4.2 Safety cap to prevent unbounded memory use

A user with 50,000 conversations (e.g., a platform helpdesk agent) would cause the loop to load 50,000 DynamoDB items into memory before executing the search. To bound memory use, add a configurable cap that is large enough for all real-world users:

```python
# Safety cap: no realistic user has more than this many conversations.
# Increase if needed; 10,000 conversations ≈ 10 DynamoDB pages of 1,000 items.
_MAX_PARTICIPANT_PAGES = 20  # 20 × 500 = 10,000 conversations

parts: list[dict] = []
last_key = None
page_count = 0
while True:
    kw: dict = {
        "KeyConditionExpression": Key("user_id").eq(user_id),
        "Limit": 500,
    }
    if last_key:
        kw["ExclusiveStartKey"] = last_key
    resp = tbl_parts.query(**kw)
    parts.extend(resp.get("Items", []))
    page_count += 1
    last_key = resp.get("LastEvaluatedKey")
    if not last_key or page_count >= _MAX_PARTICIPANT_PAGES:
        break
```

At `_MAX_PARTICIPANT_PAGES=20`, the loop loads up to 10,000 conversations — covering all realistic users — before exiting. The page-count cap is preferable to an item-count cap because it bounds the number of DynamoDB round-trips regardless of how many items are returned per page.

A `Settings` entry can expose the cap for operational tuning:

```python
# app/core/settings.py
search_participant_max_pages: int = int(
    os.environ.get("SEARCH_PARTICIPANT_MAX_PAGES", "20")
)
```

Then in `_search_messages()`:
```python
if not last_key or page_count >= S.search_participant_max_pages:
    break
```

### 4.3 Alternative: participant-indexed GSI query

The ticket fix suggestion mentions using a "participant-indexed GSI query" as an alternative. The `tbl_parts` table (DDB_PARTICIPANTS) already has a `GSI1` index (`GSI1PK = conversation_id`) used for per-conversation participant lookups. There is no reverse GSI on `user_id` that would allow a single-query fetch of all conversation IDs for a user beyond what the current `KeyConditionExpression=Key("user_id").eq(user_id)` already does (which is the PK query, not a GSI). The PK query IS the correct approach; the bug is in the pagination logic, not the query strategy. Full pagination (option 4.2) is the correct fix.

### 4.4 Dev/Prod parity (SECOPS-007)

`tbl_parts` resolves to `ddb.Table(DDB_PARTICIPANTS)` where `ddb` is the global DynamoDB resource (`app/routers/messaging.py:223`). In dev mode, this resolves to DynamoDB Local (port 8001); in production, it resolves to AWS DynamoDB. The pagination logic is identical in both environments. No mocking or branching is needed. The `search_participant_max_pages` setting reads from an environment variable and defaults to 20, which works in both `.env.local` (dev) and production environment variables.

### 4.5 Backward compatibility

The change only relaxes the early-exit condition; it cannot produce incorrect results (tighter filtering than before). For users with ≤500 conversations, the behaviour is identical (the loop exits after one page as before because `last_key` is `None`). For users with >500 conversations, search results become more complete. No data migration, table schema change, or deployment sequencing is needed.

## 5. Testing, Verification & Rollout

### Regression test (pytest offline)

Add to `tests/test_search.py`:

```python
import pytest
from unittest.mock import patch, MagicMock, call
from app.routers.search import _search_messages


class TestSearchMessagesPagination:
    """GAP-0329: _search_messages must paginate all participant pages, not only the first 500."""

    def _make_participant_page(self, conv_ids, last_key=None):
        """Build a mock DynamoDB query response."""
        return {
            "Items": [{"user_id": "user1", "conversation_id": cid} for cid in conv_ids],
            **({"LastEvaluatedKey": last_key} if last_key else {}),
        }

    def test_loads_beyond_500_conversations(self, mocker):
        """FAILS before fix: only 500 convs loaded; PASSES after fix: all 600 loaded."""
        # Page 1: 500 items, LastEvaluatedKey present
        page1_convs = [f"conv_{i}" for i in range(500)]
        # Page 2: 100 items, no LastEvaluatedKey
        page2_convs = [f"conv_{i}" for i in range(500, 600)]

        # The target message is in conv_550 (beyond the 500-cap)
        target_conv = "conv_550"
        target_msg = "msg_abc"

        mock_tbl_parts = MagicMock()
        mock_tbl_parts.query.side_effect = [
            self._make_participant_page(page1_convs, last_key={"pk": "cursor1"}),
            self._make_participant_page(page2_convs),
        ]

        mock_tbl_msg_search = MagicMock()
        mock_tbl_msg_search.query.return_value = {
            "Items": [{"token": "hello", "conversation_id#message_id": f"{target_conv}#{target_msg}"}]
        }

        mock_tbl_msgs = MagicMock()
        mock_tbl_msgs.get_item.return_value = {
            "Item": {
                "conversation_id": target_conv,
                "message_id": target_msg,
                "text": "hello world",
                "sender_id": "user2",
                "created_at": 1700000000,
            }
        }

        mocker.patch("app.routers.search.tbl_parts", mock_tbl_parts)
        mocker.patch("app.routers.search.tbl_msg_search", mock_tbl_msg_search)
        mocker.patch("app.routers.search.tbl_msgs", mock_tbl_msgs)
        mocker.patch("app.routers.search._message_search_enabled", return_value=True)
        mocker.patch("app.routers.search.build_message_query_tokens",
                     return_value=["hello"])

        result = _search_messages("hello", "user1", limit=10)

        # BEFORE fix: target_conv not in allowed_conv_ids (only 500 loaded) →
        #   result["items"] == [] → assertion fails
        # AFTER fix: target_conv IS in allowed_conv_ids (600 loaded) →
        #   result["items"] has 1 entry → assertion passes
        assert len(result["items"]) == 1
        assert result["items"][0]["conversation_id"] == target_conv

    def test_second_page_query_issued(self, mocker):
        """tbl_parts.query must be called twice when LastEvaluatedKey is present."""
        page1_convs = [f"conv_{i}" for i in range(500)]
        page2_convs = [f"conv_{i}" for i in range(500, 510)]

        mock_tbl_parts = MagicMock()
        mock_tbl_parts.query.side_effect = [
            self._make_participant_page(page1_convs, last_key={"pk": "cursor1"}),
            self._make_participant_page(page2_convs),
        ]
        mock_tbl_msg_search = MagicMock()
        mock_tbl_msg_search.query.return_value = {"Items": []}

        mocker.patch("app.routers.search.tbl_parts", mock_tbl_parts)
        mocker.patch("app.routers.search.tbl_msg_search", mock_tbl_msg_search)
        mocker.patch("app.routers.search._message_search_enabled", return_value=True)
        mocker.patch("app.routers.search.build_message_query_tokens",
                     return_value=["anything"])

        _search_messages("anything", "user1", limit=10)

        # BEFORE fix: query called once (breaks on len >= 500)
        # AFTER fix:  query called twice (follows LastEvaluatedKey)
        assert mock_tbl_parts.query.call_count == 2
```

**Fails before fix**: `test_loads_beyond_500_conversations` returns an empty `items` list because `target_conv` is in page 2 and the loop exits after page 1. `test_second_page_query_issued` fails because `query.call_count == 1`.
**Passes after fix**: both tests pass.

### Rollout

- **Effort**: M (medium — code change is small, but requires a test that seeds 500+ conversations, which is infrastructure work)
- **Risk**: Low. The change expands the allowlist; it cannot cause a new authorization bypass. The page-count safety cap prevents unbounded memory or DDB cost.
- **Rollback**: Revert to `if not last_key or len(parts) >= 500`. No DDB changes to reverse.
- **Sequencing**: Can be deployed independently. No dependency on other gap fixes. The E2E search-messaging tests (sections 37–40) do not exercise the >500-conversation path, so they continue to pass before and after the fix.
- **DynamoDB cost**: Each additional page beyond the first costs one additional `query` call (typically one RCU per 4 KB of data). For a user with 1,000 conversations, the search authorization check costs 2 DDB query calls instead of 1. This is negligible.
