# GAP-0194: Admin TIN reveal endpoint missing — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code in
> `app/routers/tax_form_1099.py` (218 lines), `app/services/tax_form_1099.py`,
> `app/core/crypto.py`, and the FIN-008 writeup at
> `docs/tickets/writeups/FIN-008.md`.

## 1. Summary & Classification

**Bug / Gap**: There is no `GET /ui/tax-forms/admin/info/{user_sub}` endpoint (or
equivalent) that allows a compliance officer or platform admin to retrieve a creator's
full decrypted TIN. There is no IP-address-logged audit trail specifically for
TIN decryption events. Without this endpoint, compliance review of W-9 submissions
and 1099-NEC corrections is impossible when the IRS disputes a TIN.

**Claim verdict**: Confirmed. `app/routers/tax_form_1099.py` contains four
admin endpoints (`/admin/1099s/{year}/generate`, `/admin/1099s/{year}/correct`,
`/admin/batch`, `/admin/year/{year}`) but none that read, decrypt, or return a
creator's TIN. A full-text search of the file returns zero matches for `tin`,
`decrypt`, or `audit`. `app/core/crypto.py:22` provides `kms_decrypt` but it is
never imported into the tax router or tax service.

**Severity**: HIGH — FIN-008 source ticket; cross-ref SEC-004.
**Status**: Open.
**Owning area**: Tax / Creator Compliance / Admin.
**Impact**: Compliance teams cannot verify whether a creator's TIN on file matches
IRS records. In the event of a B-Notice (IRS CP2100), an admin must inspect the
exact TIN submitted to determine whether to apply backup withholding. Without
decryption capability and an audit trail, the platform cannot demonstrate it handled
TIN access responsibly — a regulatory exposure.

**Related tickets**: GAP-0193 (W-9 TIN collection — prerequisite), SECOPS-007
(dev/prod parity), SEC-004 (audit trail for high-privilege money-path operations).

## 2. Current-State Investigation (root cause)

### Admin endpoints that exist today

`app/routers/tax_form_1099.py` registers four admin paths under `tax_form_1099_router`
(prefix `/ui/tax-forms`):

| Endpoint | Lines | Purpose |
|---|---|---|
| `POST /admin/1099s/{tax_year}/generate` | 132–156 | Generate 1099 for any creator |
| `POST /admin/1099s/{tax_year}/correct` | 159–183 | Re-generate/correct 1099 |
| `POST /admin/batch` | 186–205 | Batch-generate all qualifying 1099s |
| `GET /admin/year/{tax_year}` | 208–217 | List all 1099s for a tax year |

None of these endpoints touches TIN data. The generate/correct paths call
`svc.generate_1099` → `svc._build_1099_item` which references only
`_PAYER_TIN_LAST4 = "0000"` (a hardcoded stub, never decrypted).

### Crypto module (present but unused for TINs)

`app/core/crypto.py:22–25`:
```python
def kms_decrypt(ct_b64: str) -> bytes:
    ct = base64.b64decode(ct_b64)
    r = kms.decrypt(CiphertextBlob=ct)
    return r["Plaintext"]
```

This function is used by `app/services/webhook_service.py` (line 510),
`app/services/provider_credentials.py` (lines 477, 522), and
`app/services/llm_provider_keys.py` (line 170). It is **not** imported or called
from any tax service or router.

### Audit mechanism (present but insufficient)

`app/services/alerts.py:631` provides `audit_event(event, user_sub, request, **fields)`.
The admin 1099 endpoints (`app/routers/tax_form_1099.py:149–155`, 176–182, 197–204)
call `audit_event(...)` for generate/correct/batch operations. However:

1. These calls use the generic `alerts` table, not a dedicated `TAX_AUDIT` record.
2. No existing audit call captures a "TIN viewed" / "TIN decrypted" event with the
   specific fields required by the FIN-008 spec (`action`, `actor`, `target`, `ip`,
   `ts`).
3. The IP address is available via `request.client.host` in FastAPI handlers but it
   is not passed to `audit_event` in any existing tax-related call.

### Dependency on GAP-0193

GAP-0194 (admin reveal) is a read-path counterpart to GAP-0193 (write path). Without
W-9 submission, there is nothing to decrypt. The admin TIN reveal endpoint should be
implemented in the same service module (`app/services/tax_w9.py`) introduced by
GAP-0193, since both share the W-9 DDB key schema and the `_write_tax_audit` helper.

## 3. Impact / Exploit / Blast Radius

**Compliance exposure**: IRS CP2100 (B-Notice) procedure requires the payer (the
platform) to solicit a correct TIN from the payee within 15 business days. Without an
admin TIN-reveal endpoint, a compliance officer cannot:
- Compare the submitted TIN against the IRS-provided mismatch list.
- Determine whether to apply 24 % backup withholding.
- Document the review for audit.

**Privilege escalation risk (if incorrectly built)**: A TIN reveal endpoint that is
accessible without `require_admin_or_root` would expose full SSNs/EINs to any
authenticated user — a catastrophic PII breach. The fix must enforce admin-only auth
and log every decryption event.

**Audit trail gap**: Without a dedicated audit record per TIN view, the platform cannot
prove to a regulator that TIN access was controlled and logged. The generic `audit_event`
call is insufficient: it goes to the same table as cart events and does not carry
`action="tin_viewed"` with IP address in a queryable format.

## 4. Fix Design (code-level)

### 4.1 Service layer (shared with GAP-0193: `app/services/tax_w9.py`)

The `get_tax_info_admin` and `_write_tax_audit` functions designed for GAP-0193 already
cover this gap's requirements. For completeness, the key function is:

```python
def get_tax_info_admin(
    *,
    user_sub: str,
    actor_sub: str,
    ip_address: str,
) -> Dict[str, Any]:
    """Return full (decrypted) TIN for admin compliance review.

    Every call writes a TAX_AUDIT entry with actor, target, IP, and timestamp
    (SEC-004 / GAP-0194 requirement).
    """
    resp = T.billing.get_item(Key={"pk": f"USER#{user_sub}", "sk": "W9#"})
    item = resp.get("Item")
    if not item:
        raise LookupError("no_tax_info:No W-9 submitted for this user")

    tin_ct = item.get("tin_encrypted", "")
    tin_full = kms_decrypt(tin_ct).decode("utf-8") if tin_ct else ""

    _write_tax_audit(
        action="tin_viewed",
        actor=actor_sub,
        target=user_sub,
        ip=ip_address,
    )

    out = _to_tax_info_out(item)   # base dict: masked view
    out["tin_full"] = tin_full     # appended only in admin response
    return out
```

`_write_tax_audit` (also in `app/services/tax_w9.py`):

```python
def _write_tax_audit(*, action: str, actor: str, target: str, ip: str) -> None:
    ts = now_ts()
    from app.services.billing_shared import ulidish
    T.billing.put_item(Item={
        "pk": f"TAX_AUDIT#{target}",
        "sk": f"AUDIT#{ts}#{ulidish()}",
        "action": action,    # "tin_viewed" | "w9_submitted" | "1099_generated"
        "actor": actor,
        "target": target,
        "ip": ip,
        "ts": ts,
    })
```

### 4.2 Router endpoint (`app/routers/tax_form_1099.py`)

This endpoint is partially described in GAP-0193's fix design. Full definition:

```python
from app.services import tax_w9 as w9_svc
from app.models import TaxInfoAdminOut

@tax_form_1099_router.get(
    "/admin/info/{target_user_sub}", response_model=TaxInfoAdminOut
)
def admin_get_tax_info(
    target_user_sub: str,
    request: Request,
    admin: Any = Depends(require_admin_or_root),
) -> TaxInfoAdminOut:
    """Admin: retrieve full decrypted TIN with mandatory IP-logged audit trail.

    Access restricted to ADMIN or ROOT role.  Every successful call writes a
    TAX_AUDIT record (action='tin_viewed') to the billing table.
    """
    _ensure_enabled()
    _ensure_target_exists(target_user_sub)   # existing helper, line 60–67
    ip = request.client.host if request.client else "unknown"
    try:
        result = w9_svc.get_tax_info_admin(
            user_sub=target_user_sub,
            actor_sub=admin.sub,
            ip_address=ip,
        )
    except LookupError as exc:
        code, _, message = str(exc).partition(":")
        raise HTTPException(
            status_code=404, detail={"code": code, "message": message or code}
        )
    return TaxInfoAdminOut(**result)
```

The `require_admin_or_root` dependency from `app/auth/policy.py` ensures that only
users with `role >= ADMIN` can reach this endpoint. Root and scoped-admin sessions
both satisfy this condition.

### 4.3 Admin audit-log query endpoint (optional, recommended)

A companion read endpoint for auditors:

```python
@tax_form_1099_router.get("/admin/audit/{target_user_sub}")
def admin_get_tax_audit(
    target_user_sub: str,
    limit: int = Query(default=50, ge=1, le=200),
    admin: Any = Depends(require_admin_or_root),
):
    """List TAX_AUDIT entries for a specific user (most-recent first)."""
    _ensure_enabled()
    resp = T.billing.query(
        KeyConditionExpression=Key("pk").eq(f"TAX_AUDIT#{target_user_sub}"),
        ScanIndexForward=False,
        Limit=limit,
    )
    return {"entries": resp.get("Items", []), "count": resp.get("Count", 0)}
```

### 4.4 Pydantic model (`app/models.py`)

```python
class TaxInfoAdminOut(TaxInfoOut):
    """TaxInfoOut extended with decrypted TIN — only returned to ADMIN/ROOT callers."""
    tin_full: str = Field(..., description="Decrypted full TIN (SSN/EIN). Never cached.")
```

`TaxInfoOut` is defined as part of GAP-0193's fix.

### 4.5 Dev/prod parity (SECOPS-007)

KMS in dev uses `scripts/mock_kms_server.py` at port 7999. The `kms_decrypt` call
in `get_tax_info_admin` reaches the mock KMS via `app/core/aws_clients.py` →
`_kms_endpoint_url()` which reads `S.kms_endpoint_url`. In prod, this points to
real AWS KMS. The code path is identical; no conditional branching needed. The mock
KMS handles the `Decrypt` API identically to real KMS (it returns the plaintext of
whatever was encrypted with the same mock key), so dev tests exercise the same code
as production.

**Important**: `app/core/crypto.py:16–18` checks `if not S.kms_key_id: raise RuntimeError`.
This guard prevents the endpoint from silently returning an empty TIN if KMS is
misconfigured. In dev, `KMS_KEY_ID` must be set in `.env.local` (populated by
`scripts/local-stack-up.sh` which starts the mock KMS server).

### 4.6 Response design — never expose tin_full to non-admins

`TaxInfoAdminOut` extends `TaxInfoOut`. The creator-facing `GET /ui/tax-forms/info`
endpoint returns `TaxInfoOut` (no `tin_full` field). FastAPI's response model
serialisation drops unknown fields, so even if `tin_full` is present on the dict
returned from the service, it will not appear in the creator-facing response. This
is a defence-in-depth measure in addition to the auth guard.

### Manual QA steps

1. `just up`.
2. Submit a W-9 as Alice (`POST /ui/tax-forms/w9`).
3. Log in as Charlie (admin) and `GET /ui/tax-forms/admin/info/<alice_sub>`.
4. Verify response includes `tin_full: "123456789"` and `tin_last4: "6789"`.
5. Query audit log: `GET /ui/tax-forms/admin/audit/<alice_sub>` — confirm one entry
   with `action: "tin_viewed"`, `actor: "<charlie_sub>"`, non-empty `ip`.
6. Attempt the same as Alice (USER role) → expect 403.
7. Disable KMS (`KMS_KEY_ID=` in `.env.local`) and restart backend; submit a W-9 and
   attempt the admin reveal → expect a 500 with `RuntimeError: KMS_KEY_ID not set`
   (logged, not exposed to client). This confirms the guard at `crypto.py:17` fires.

### Observability

- Log `WARNING` when `kms_decrypt` call takes >500 ms (KMS latency spike).
- Emit a Prometheus counter `tax.tin.viewed{admin_sub=..., env=...}` for each
  successful decrypt.
- Alert ops if more than 10 TIN reveals occur within 60 seconds (potential scraping).

### Rollout

- **Effort**: M (1–2 days, given GAP-0193 is completed first — the service function
  is shared).
- **Hard dependency**: GAP-0193 must be merged first; there is no TIN data to reveal
  until W-9 submission is working.
- **Migration**: None — new endpoint.
- **Rollback**: Remove or 403-stub the endpoint. Audit rows in DDB are harmless.
- **Risk**: HIGH if KMS is misconfigised in prod; LOW once verified. Add a startup
  check: if `TAX_FORM_1099_ENABLED` and `KMS_KEY_ID` is empty, fail fast.
- **Sequencing**: GAP-0193 → GAP-0194 → 1099 PDF TIN integration.
