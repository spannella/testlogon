# GAP-0370: No client-side forensic watermark overlay — Remediation Write-up

> ~5 pages. Fix-oriented. Claim verified against actual code (no investigation doc exists).

## 1. Summary & Classification

**Severity**: HIGH  
**Source ticket**: VOD-008  
**Owning area**: Frontend / VOD player  
**Status**: Open  
**Claim verdict**: CONFIRMED — the player container at `VideoPlayerPage.tsx:479-504` renders `<MediaPlayer>` with no overlay. No `WatermarkOverlay` component exists anywhere in the frontend codebase.

The VOD-008 spec requires a `WatermarkOverlay` component to be absolutely positioned over the video player surface, displaying a semi-transparent string derived from the viewer's session identity. This overlay serves as a secondary deterrent against screen recording: even if a viewer captures their screen, the watermark encodes enough identity information (session ID prefix + owner/tenant ID) to attribute the recording to a specific viewer session. The current implementation omits this overlay entirely. The `<MediaPlayer>` is rendered inside a plain `<div data-testid="video-player">` with no overlay sibling.

**Related tickets**: VOD-008, VOD-020 (server-side watermarked download — a separate, complementary control that is already present).

## 2. Current-State Investigation (root cause)

### Player render block

**`app/frontend/src/pages/videos/VideoPlayerPage.tsx`, lines 478–491**:

```tsx
{/* Active player */}
{!playerError && playbackUrl && (
  <div data-testid="video-player">
    <MediaPlayer
      src={playbackUrl}
      mode="vod"
      autoplay
      poster={video.thumbnail_url ?? undefined}
      title={video.title}
      onError={handleMediaError}
      subtitleTracks={subtitleTracksForPlayer.length > 0 ? subtitleTracksForPlayer : undefined}
    />
  </div>
)}
```

There is no overlay `<div>` positioned over the `<MediaPlayer>`. The outer `<div data-testid="video-player">` has no CSS positioning (`relative`, `absolute`) that would allow an absolutely positioned child to be clipped to the player boundary.

### No WatermarkOverlay component exists

A codebase-wide search for `WatermarkOverlay` returns zero results in `frontend/src/`. The component referenced in the ticket's fix suggestion does not exist and must be created.

### Available data for watermark text

`VideoPlayerPage` already has access to the two pieces of identity information the ticket specifies:

- `video.playback_token` (`frontend/src/api/endpoints/videos.ts:85`) — a per-viewer, per-session token minted by the backend. `video.playback_token?.slice(0, 12)` gives a 12-character session fingerprint.
- `video.owner_user_id` (`frontend/src/api/endpoints/videos.ts:67`) — the creator/tenant ID. This is not the viewer ID; the ticket calls this `tenantId`.

The viewer's own identity (`currentUserId`) is also available via `useAuthStore` (line 289 of `VideoPlayerPage.tsx`).

### Distinction from VOD-020 (server-side watermarked download)

`VodWatermarkDownloadButton.tsx` (`frontend/src/pages/videos/VodWatermarkDownloadButton.tsx`) implements per-viewer watermarked video downloads via `requestVodWatermarkDownload` — a backend process that burns the viewer ID into a separate copy of the video file for download. That is an offline-copy deterrent for the download pathway. GAP-0370 concerns the live-streaming playback surface: a CSS overlay visible while the video is playing, which deters real-time screen capture of the HLS stream in the browser. These are complementary controls and neither substitutes for the other. A viewer who never uses the download button and simply records their screen is entirely untracked by VOD-020; GAP-0370 addresses exactly that scenario.

### Why the `playback_token` is the right session identifier

`video.playback_token` is minted per-request by `mint_vod_playback_url` in `app/services/vod_playback_url.py` and is specific to the viewer's current playback session. It changes on each page load. Using its first 12 characters in the overlay text ensures the watermark is session-specific rather than account-specific — enabling attribution to a specific viewing event, not just a user account. In contrast, `currentUserId` (the user's account sub) would enable user-level attribution but would remain constant across all of a user's sessions, providing less granular forensic data.

## 3. Impact / Exploit / Blast Radius

### Primary risk: unattributable screen recording

Any authenticated viewer can open a pay-per-view or subscription-gated video and record their screen with zero forensic evidence linking the recording to their identity. Without the overlay:

- A viewer can screen-record and redistribute premium VOD content.
- There is no way to identify which viewer session produced a leaked recording.
- The server-side watermarked download (VOD-020) only covers the download path; a viewer can bypass it entirely by recording the in-browser stream.

### Regulatory / licensing consequence

Premium VOD platforms that license content from studios commonly have contractual obligations to implement "reasonable technical measures" against unauthorised redistribution. A missing client-side watermark overlay may constitute a breach of such licensing terms, particularly for any content flagged as requiring forensic identification.

### Business impact

- Creator trust: creators who rely on the platform to protect their monetised content have no forensic recourse against screen-capture leaks.
- Platform liability: if leaked content can be attributed to the platform's failure to implement a committed security control, the platform bears reputational and potentially legal exposure.

### Attacker model

The overlay is a deterrent, not a hard cryptographic barrier. A sophisticated attacker who inspects the page's DOM in browser DevTools can identify the overlay div, set its `display: none` via the console, and then screen-record without the visible text. However, the threat model for a client-side watermark overlay is primarily casual leakers, not technically sophisticated adversaries.

For the deterrence goal:

1. Most casual leakers will not bother removing the overlay; the visual text discourages "share this with friends" behaviour.
2. Even after post-processing (cropping, blurring the corner), the persistent alpha-composited repeated text is likely to leave statistical artefacts in the compressed video signal. Forensic analysis of such artefacts is an established technique in the anti-piracy industry.
3. The overlay creates a contractual and legal basis for attributing a recording to a specific viewer session. Even if the text cannot be read, the platform can assert "at the time of viewing, a watermark was present" and tie the session ID to an authenticated account.
4. Against the DOM-removal attack: a future hardening step could use a `<canvas>` element with the overlay painted at the compositing layer, making DOM manipulation less straightforward. This is out of scope for the initial remediation but should be considered if the platform serves high-value content.

The overlay's primary value is in raising the cost and visibility of leaking: a viewer who sees "abc123def456 · creator_789" overlaid on their screen knows the recording is traceable, and this knowledge alone is the primary deterrent.

## 4. Fix Design (code-level)

### New component: `WatermarkOverlay.tsx`

Create `frontend/src/components/shared/WatermarkOverlay.tsx`:

```tsx
/**
 * WatermarkOverlay — semi-transparent forensic identity overlay for the VOD player.
 *
 * Absolutely positioned over the player container; pointer-events: none so it
 * does not interfere with player controls. Renders the session fingerprint and
 * tenant ID in a repeating diagonal pattern.
 */

interface WatermarkOverlayProps {
  /** First 12 characters of the playback token — session fingerprint. */
  sessionId: string | undefined | null;
  /** Owner/tenant ID of the video (creator identifier). */
  tenantId: string | undefined | null;
}

export function WatermarkOverlay({ sessionId, tenantId }: WatermarkOverlayProps) {
  if (!sessionId && !tenantId) return null;

  const text = [sessionId, tenantId].filter(Boolean).join(" · ");

  return (
    <div
      aria-hidden="true"
      data-testid="watermark-overlay"
      style={{
        position: "absolute",
        inset: 0,
        pointerEvents: "none",
        overflow: "hidden",
        zIndex: 10,
        display: "flex",
        flexWrap: "wrap",
        alignContent: "space-around",
        justifyContent: "space-around",
        opacity: 0.18,
        userSelect: "none",
      }}
    >
      {Array.from({ length: 12 }).map((_, i) => (
        <span
          key={i}
          style={{
            color: "white",
            fontSize: "11px",
            fontFamily: "monospace",
            transform: `rotate(-25deg)`,
            whiteSpace: "nowrap",
            textShadow: "0 0 3px rgba(0,0,0,0.7)",
            letterSpacing: "0.05em",
          }}
        >
          {text}
        </span>
      ))}
    </div>
  );
}

export default WatermarkOverlay;
```

### Changes to `VideoPlayerPage.tsx`

**Step 1**: Import the new component near the top of the file (after existing imports):

```tsx
import WatermarkOverlay from "@/components/shared/WatermarkOverlay";
```

**Step 2**: Make the player container a CSS positioning context and add the overlay. Replace the existing player `<div>` (lines 479–491) with:

```tsx
{/* Active player */}
{!playerError && playbackUrl && (
  <div
    data-testid="video-player"
    style={{ position: "relative" }}
  >
    <MediaPlayer
      src={playbackUrl}
      mode="vod"
      autoplay
      poster={video.thumbnail_url ?? undefined}
      title={video.title}
      onError={handleMediaError}
      subtitleTracks={subtitleTracksForPlayer.length > 0 ? subtitleTracksForPlayer : undefined}
    />
    <WatermarkOverlay
      sessionId={video.playback_token?.slice(0, 12)}
      tenantId={video.owner_user_id}
    />
  </div>
)}
```

The `position: "relative"` on the outer `<div>` is essential: it establishes the containing block for `WatermarkOverlay`'s `position: absolute` children, confining the overlay to the player boundary.

### SECOPS-007 dev/prod parity

The overlay is a pure React component with no backend calls. It reads `video.playback_token` and `video.owner_user_id`, both of which are already present in the `VideoDetail` API response in dev and production alike (`GET /ui/videos/{video_id}/detail`). No feature flag, no AWS path, no dev-mode conditional needed.

### Backward compatibility

The overlay is rendered only when `video.playback_token` or `video.owner_user_id` is non-null and the player is shown. It has `pointer-events: none` and `aria-hidden="true"`, so it does not break keyboard navigation, player controls, subtitle tracks, or accessibility. It does not affect the player's download or screenshot APIs.

### Alternatives considered

- **Canvas overlay**: More tamper-resistant (harder to inspect/remove from DevTools) but requires a `<canvas>` element sized to the video and redrawn on every resize. Rejected as over-engineered for a deterrent layer; a CSS overlay is sufficient for the stated goal.
- **SVG overlay with embedded data URI**: Similar to CSS approach; negligible difference in deterrence value. Rejected in favour of simpler JSX.
- **Server-side frame burn-in during streaming**: Would require re-encoding the HLS stream per viewer, which is prohibitively expensive. VOD-020's download watermark does this for the download case; extending it to live streaming is out of scope.
- **Viewer's own `currentUserId` instead of `playback_token`**: `currentUserId` is a stable identifier that could be useful for attribution but would encode the user's internal ID in the overlay text. Using `playback_token.slice(0,12)` provides session-level granularity (tying the leak to a specific viewing session, not just an account) and does not expose the user's primary key to potential screen-capture analysis.

 * GAP-0370 regression: VideoPlayerPage must render a watermark overlay

import { test, expect } from "@playwright/test";
import { injectAuth } from "./helpers/auth";

test.describe("GAP-0370 — watermark overlay", () => {
  test("player renders WatermarkOverlay over <MediaPlayer>", async ({ page }) => {
    await injectAuth(page, "alice");
    // Navigate to any video detail page that has a playback token.

    await firstVideo.click();
    await page.waitForSelector('[data-testid="video-player"]', { timeout: 15000 });

    // Overlay must exist inside the player container
    const overlay = page.locator('[data-testid="video-player"] [data-testid="watermark-overlay"]');
    await expect(overlay).toBeAttached();

    // Must be aria-hidden (no effect on a11y tree)

    // Must not intercept pointer events

    const text = await overlay.textContent();
    expect(text?.trim().length).toBeGreaterThan(0);
  });
});

### Rollout

- **Risk**: Very low. The overlay is `pointer-events: none`, `aria-hidden`, and renders only when the player is active. The only visible change to end users is a faint diagonal text pattern over the video.
- **Sequencing**: Can ship independently of GAP-0366/0368/0369. The overlay is visible regardless of video status (it only renders when the player is shown, which requires `playback_token` and `hls_manifest_url` to be set — i.e., the video must already be published and entitled).
