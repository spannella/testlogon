# GAP-0236: `resolve_connection_chain` function missing — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. No prior
> investigation doc exists for this ticket.

## 1. Summary & Classification

**Bug**: The SSH bastion path infrastructure (INFRA-011) resolves a multi-hop chain into a
ProxyJump / ssh_config text representation suitable for end-users, but there is no programmatic
`resolve_connection_chain` function that returns each hop's decrypted SSH private key alongside
the resolved host/port/username. Downstream consumers — primarily the SSH terminal bridge and
any automated connection manager — have no single call they can make to get a fully resolved,
credential-populated hop list ready for real dial-out.

**Severity**: HIGH. Without this function the SSH bridge cannot programmatically walk a bastion
chain using per-hop keys stored in the key manager. Every real multi-hop SSH session either
silently falls back to no-key auth or fails with an authentication error. The gap is invisible
in dev mode because dev mode uses the mock terminal (no real SSH dial-out occurs).

**Source ticket**: INFRA-011. No prior investigation document.

**Owning area**: `app/services/ssh_bastion.py`, `app/services/ssh_key_manager.py`,
`app/services/connection_profiles.py`.

**Claim verdict**: Confirmed. `resolve_path` in `app/services/ssh_bastion.py:349` returns a
ProxyJump-oriented dict (chain hops, `proxy_jump`, `ssh_command`, `ssh_config`). There is no
companion function that augments each hop with a decrypted private key. The key manager exposes
`get_decrypted_private_key` (`app/services/ssh_key_manager.py:271`) but it is never called by
the bastion service.

**Related tickets**: GAP-0237 (ByGlobalStatus GSI absent — separate infra gap), INFRA-006
(connection profiles), INFRA-011 (bastion paths).

## 2. Current-State Investigation (root cause)

### 2.1 What exists today

`app/services/ssh_bastion.py:349` — `resolve_path(user_sub, path_id)` reads the stored bastion
path, re-validates the hop chain, builds the OpenSSH `ProxyJump` directive and an `ssh_config`
block, and returns:

```python
return {
    "path_id": ...,
    "chain": chain,          # list of hop dicts (hostname, port, username, ssh_key_id, ...)
    "jump_hops": jump_hops,
    "target": target,
    "total_hops": len(chain),
    "proxy_jump": proxy_jump,
    "ssh_command": ssh_command,
    "ssh_config": ssh_config,
}
```

Each hop dict carries `ssh_key_id` (the reference id into the key store), but the resolved
dict does NOT include the decrypted private key PEM. The function stops at the identifier.

`app/services/ssh_key_manager.py:271` — `get_decrypted_private_key(user_sub, key_id)` is
a fully functional, KMS-backed decrypt routine:

```python
def get_decrypted_private_key(user_sub: str, key_id: str) -> Optional[str]:
    """Decrypt and return private key PEM. INTERNAL USE ONLY ..."""
    resp = T.ssh_keys.get_item(Key={"user_sub": user_sub, "sk": f"KEY#{key_id}"})
    item = resp.get("Item")
    ...
    pem_bytes = kms_decrypt(encrypted_blob)
    ...
    return pem_str
```

It updates `last_used_at` / `use_count` on each call (line 287-292) and is clearly designed
for internal consumption by an SSH bridge. Despite this, nothing in the bastion or connection
profile service ever calls it.

`app/services/connection_profiles.py:462` — `quick_connect(user_sub, profile_id)` calls
`resolve_path` to get a `bastion` sub-dict but only extracts the text fields
(`proxy_jump`, `ssh_command`, `total_hops`) for the API response. No key material is fetched
or forwarded (lines 501-513).

### 2.2 Missing function

There is no `resolve_connection_chain` function anywhere in the codebase:

```
grep -rn "resolve_connection_chain" app/  →  (no output)
```

The ticket description in INFRA-011 section 3.2 specifies that a programmatic connection
helper should return a list of hop dicts each containing:
- `hostname`, `port`, `username` (resolved / validated)
- `private_key_pem` — the decrypted key for this hop (or `None` if none configured)

### 2.3 Runtime behaviour

**Dev mode**: The mock terminal (`app/routers/remote.py`) starts an in-browser terminal that
never initiates a real SSH connection. The missing function causes no runtime error in dev.

**Production**: Any real SSH bridge that calls `quick_connect` and needs to programmatically
proxy through each hop has no API to retrieve the per-hop private key. The bridge would either
skip key-based auth (causing `Permission denied`) or crash with `KeyError`.

---

## 3. Impact / Exploit / Blast Radius

**Availability**: Every multi-hop SSH session that relies on per-hop key auth fails silently or
with an authentication error. Users who have configured bastion paths with stored SSH keys see
connection failures that appear to be network or server-side.

**Security implication**: Because the missing function has never existed, downstream integrators
may have resorted to workarounds (e.g., exposing private key PEM via an API endpoint). Any such
workaround would be a critical secret-exposure vulnerability. The correct fix keeps key material
entirely server-side, injected into the SSH dial-out code and never returned to the browser.

**Scope**: All users who have created bastion paths and stored SSH keys for one or more hops.
In the current release that includes any tenant who onboarded INFRA-011 (bastion) + INFRA-002
(key manager) features together.

**Financial / compliance**: No direct financial impact. Compliance: logs must record
`key_decrypted` events (already emitted by `get_decrypted_private_key`) so audit trails are
complete once the function is wired in.

## 4. Fix Design (code-level)

### 4.1 Add `resolve_connection_chain` to `app/services/ssh_bastion.py`

Place after `resolve_path` (currently ending at line 415):

```python
def resolve_connection_chain(
    user_sub: str,
    path_id: str,
    *,
    include_keys: bool = True,
) -> List[Dict[str, Any]]:
    """Resolve a bastion path into a hop list ready for programmatic dial-out.

    Each hop dict extends the base hop fields with:
        ``private_key_pem``:  decrypted PEM string (str) if ``include_keys``
                              is True and a key is stored for this hop, else None.

    The function re-uses the validation logic of ``resolve_path`` and inherits
    its ``BastionPathNotFound`` / ``ChainValidationError`` error contract.

    Never return this dict to the API layer — ``private_key_pem`` is
    server-internal only.
    """
    resolved = resolve_path(user_sub, path_id)   # raises BastionPathNotFound / ChainValidationError
    chain: List[Dict[str, Any]] = []

    for hop in resolved["chain"]:
        hop_out = dict(hop)   # copy: hostname, port, username, ssh_key_id, label, ...
        pem: Optional[str] = None

        if include_keys and hop.get("ssh_key_id"):
            from app.services.ssh_key_manager import get_decrypted_private_key
            pem = get_decrypted_private_key(user_sub, hop["ssh_key_id"])
            if pem is None:
                logger.warning(
                    "ssh_bastion.key_not_found path_id=%s ssh_key_id=%s",
                    path_id, hop["ssh_key_id"],
                )

        hop_out["private_key_pem"] = pem
        chain.append(hop_out)

    logger.info(
        "ssh_bastion.chain_resolved path_id=%s user_sub=%s hops=%d",
        path_id, user_sub, len(chain),
    )
    return chain
```

### 4.2 Wire into `quick_connect` (connection_profiles.py)

`app/services/connection_profiles.py:493-513` currently builds a `bastion` dict from
`resolve_path`. Add the chain alongside the existing ProxyJump representation so the terminal
bridge has full credential access without a second call:

```python
# (inside quick_connect, replace the existing bastion resolution block)
if profile["bastion_path_id"]:
    from app.services.ssh_bastion import (
        BastionPathNotFound,
        ChainValidationError,
        resolve_path,
        resolve_connection_chain,
    )
    try:
        resolved = resolve_path(user_sub, profile["bastion_path_id"])
        chain = resolve_connection_chain(user_sub, profile["bastion_path_id"])
    except BastionPathNotFound:
        raise ReferenceNotFound(...)
    except ChainValidationError as exc:
        raise ProfileValidationError(str(exc))

    bastion = {
        "path_id": resolved["path_id"],
        "proxy_jump": resolved["proxy_jump"],
        "ssh_command": resolved["ssh_command"],
        "total_hops": resolved["total_hops"],
        # Internal-only field; stripped before serialisation in the router:
        "_chain": chain,
    }
```

The router (`app/routers/connection_profiles.py`) must strip `_chain` before serialising
the response to avoid leaking key material to the browser. In production the SSH bridge
consumes `_chain` in-process before the HTTP response is built.

### 4.3 Dev/Prod parity (SECOPS-007)

The function is unconditionally useful in both environments. In dev mode, `kms_decrypt` is
serviced by the mock KMS server (`scripts/mock_kms_server.py`). In production it calls real
AWS KMS. No feature flag is needed; the KMS abstraction (`app/core/crypto.py`) already
handles the path selection transparently.

The `include_keys=False` parameter allows callers (e.g., admin audit endpoints) to resolve
the chain topology without triggering KMS calls when key material is not needed.

### 4.4 Alternatives considered

- **Return key IDs only and let the bridge call `get_decrypted_private_key` per hop**: This
  works but requires callers to import `ssh_key_manager` and know the user_sub, which couples
  every bridge implementation to two service modules. A single `resolve_connection_chain` is
  simpler and auditable (one KMS call site per chain resolution).

- **Cache decrypted keys for the session lifetime**: Rejected — keeping plaintext key material
  in memory beyond the dial-out increases the blast radius of a memory dump. Keys should be
  fetched on demand and discarded immediately after use by the dial-out thread.

import pytest
from unittest.mock import patch

def test_resolve_connection_chain_returns_key_pem(mock_tables, mock_kms):

    assert chain[1]["hostname"] == "10.0.1.5"
