# GAP-0306: `enforcement_id` absent from warning and ban alert details — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/routers/admin_moderation.py`,
> `app/services/moderation_policy_engine.py`, and `app/services/alerts.py`.

## 1. Summary & Classification

**Bug**: When an admin resolves a moderation ticket with `enforcement_action="warn"` or
`enforcement_action="ban"`, the alert written to the offender's notification stream (`write_alert`)
does not include the `enforcement_id` that was generated and stored in the
`user_enforcement_history` table. The alert's `details` map is therefore incomplete: recipients
and downstream consumers (audit pipelines, support staff looking at alert records) cannot
cross-reference the alert to the enforcement record.

- **Severity**: HIGH — compliance gap; enforcement records and alert records are disconnected,
  frustrating appeals review and regulatory audit trails.
- **Source ticket**: MOD-003
- **Status**: Open
- **Owning area**: Content Moderation / Admin Moderation Router
- **Claim verdict**: CONFIRMED. The code path described in the ticket is accurate.
  `_persist_enforcement_if_needed` at `app/routers/admin_moderation.py:475` generates an
  `enforcement_id` but does not return it, and both `issue_warning_notification` and `apply_ban`
  in `app/services/moderation_policy_engine.py` are called without the `enforcement_id` kwarg.
- **Related tickets**: MOD-003, SECOPS-007 (dev/prod parity on notification paths).


## 2. Current-State Investigation (root cause)

### Code path for the "resolve" action (ban/warn)

`POST /moderation/tickets/{ticket_id}/resolve` is handled at
`app/routers/admin_moderation.py:757`. When `inp.enforcement_action` is `"warn"` or `"ban"`,
the execution sequence is:

1. **`_persist_enforcement_if_needed`** is NOT called from the resolve path (only from the
   separate "decide" path at line 707). The resolve path jumps straight to the notification
   helpers at lines 938–967.

2. **`issue_warning_notification`** (line 939) is called as:

   ```python
   # app/routers/admin_moderation.py:939–943
   issue_warning_notification(
       offender_user_id=str(offender_user_id or ""),
       ticket_id=ticket_id,
       note=note,
       policy_category=policy_category,
   )
   ```

3. **`apply_ban`** (line 953) is called as:

   ```python
   # app/routers/admin_moderation.py:953–960
   apply_ban(
       offender_user_id=str(offender_user_id or ""),
       ticket_id=ticket_id,
       admin_user_id=admin.sub,
       note=note,
       duration_days=inp.enforcement_duration_days,
       policy_category=policy_category,
   )
   ```

4. Inside `issue_warning_notification` (`app/services/moderation_policy_engine.py:20–34`) the
   `write_alert` call builds a `details` dict that contains `ticket_id`, `action`, `policy_category`,
   and `note` — but no `enforcement_id`.

5. Inside `apply_ban` (`app/services/moderation_policy_engine.py:59–110`) the `write_alert` call
   likewise omits `enforcement_id` from `details`.

### Where `enforcement_id` is generated

For the *decide* endpoint, `_persist_enforcement_if_needed` at line 475 generates
`enforcement_id = f"enf_{uuid.uuid4().hex[:20]}"` (line 482), writes it to
`T.user_enforcement_history`, but returns `None`. Neither the caller at line 707 nor the
downstream notification calls receive the generated ID.

For the *resolve* endpoint, `_persist_enforcement_if_needed` is not called at all. The resolve
path at line 861–868 (inside the `elif inp.enforcement_action == "ban"` block) also generates an
`enforcement_id` inline but that block is inside a nested if that is actually for the *direct-ban*
action, not the general resolve action. The resolver at line 938 calls the policy engine helpers
without ever generating or passing an `enforcement_id`.

### Net effect at runtime

An alert appears in the offender's notification inbox with fields:
```json
{ "ticket_id": "mod_...", "action": "warn", "policy_category": "...", "note": "..." }
```
The `enforcement_id` is stored in `UserEnforcementHistory` DynamoDB table but never linked to
the alert record. Support staff navigating alerts cannot find the originating enforcement entry
without an extra DynamoDB query by `ticket_id`.

The bug is identical in dev and prod because both code paths execute the same Python; the only
dev/prod split here would be if SNS notifications were gated by `S.dev_mode`, but the
`write_alert` path writes to the `T.alerts` DynamoDB table unconditionally (gated only by
`S.alerts_enabled`).


## 3. Impact / Exploit / Blast Radius

### Compliance / audit impact
Moderation alerts are the primary communication channel between enforcement actions and the
affected user. Appeals staff reviewing an alert record can only see `ticket_id`; they must
perform a separate query against `UserEnforcementHistory` (keyed by `user_id` + GSI on
`user_enforcement_history` DynamoDB table) to find the matching enforcement entry. This adds
manual lookup overhead and introduces risk of mis-matching when a user has multiple warnings
for the same ticket (e.g. a ticket that was re-opened after the original decision). The
operational cost is compounded at scale: if a platform processes 1,000 enforcement actions per
day, every appeal review requires a cross-table lookup that could be eliminated by surfacing
the `enforcement_id` directly in the alert.

### Regulatory exposure
GDPR Art. 12 and DSA Art. 17 require that "meaningful information" be provided about automated
decisions affecting users. An enforcement alert that carries no cross-reference to the
underlying enforcement record fails this bar in jurisdictions that audit notification content.
The DSA in particular requires platforms to provide users with a specific statement of reasons
for enforcement decisions; the `enforcement_id` is the handle that links the alert (user-visible)
to the reasons record (admin-visible). Omitting it breaks the traceability chain.

### User appeal friction
When a user receives a warning or ban alert and navigates to the appeals flow
(`POST /moderation/appeals`), the appeal must reference an `enforcement_id`. If the alert
does not carry that ID, the user must contact support separately to obtain it — or the
appeal form must perform a lookup by `ticket_id` to discover the `enforcement_id`. This
adds at least one extra HTTP round-trip and a potential point of failure if that lookup
returns multiple enforcement records for the same ticket.

### Downstream system impact
Any consumer that ingests the alert stream (analytics pipeline, compliance export, third-party
appeal tooling) expecting an `enforcement_id` field in moderation alerts will either silently
skip the link or produce null foreign-key references.

### Security / financial blast radius
No direct money or account-takeover risk. The gap is an audit trail deficiency, not an
authorization bypass. Severity remains HIGH because of compliance consequences but is not
critical from a financial standpoint.


## 4. Fix Design (code-level)

### Step 1 — Return `enforcement_id` from `_persist_enforcement_if_needed`

Change the function signature and return value:

```python
# app/routers/admin_moderation.py:475
def _persist_enforcement_if_needed(
    *, decision: str, ticket_id: str, offender_user_id: str | None,
    admin_user_id: str, note: str, now_ts: str
) -> str | None:          # <-- was implicitly None
    if decision not in {"warn", "ban"}:
        return None
    user_id = str(offender_user_id or "").strip()
    if not user_id:
        return None

    enforcement_id = f"enf_{uuid.uuid4().hex[:20]}"
    T.user_enforcement_history.put_item(Item={
        "user_id": user_id,
        "enforcement_id": enforcement_id,
        ...
    })
    return enforcement_id   # <-- NEW: caller receives the generated ID
```

### Step 2 — Thread `enforcement_id` into notification helpers

Add `enforcement_id: str | None = None` to both notification functions:

```python
# app/services/moderation_policy_engine.py:20
def issue_warning_notification(
    *, offender_user_id: str, ticket_id: str, note: str,
    policy_category: str = "unspecified",
    enforcement_id: str | None = None,   # NEW
) -> None:
    ...
    write_alert(
        offender_user_id,
        event="moderation_warning",
        outcome="warning",
        title="Account warning issued",
        details={
            "ticket_id": ticket_id,
            "action": "warn",
            "policy_category": str(policy_category or "unspecified"),
            "note": (note or "")[:500],
            **({"enforcement_id": enforcement_id} if enforcement_id else {}),  # NEW
        },
    )
```

```python
# app/services/moderation_policy_engine.py:59
def apply_ban(
    *, offender_user_id: str, ticket_id: str, admin_user_id: str,
    note: str, duration_days: int | None,
    policy_category: str = "unspecified",
    enforcement_id: str | None = None,   # NEW
) -> dict[str, Any]:
    ...
    write_alert(
        offender_user_id,
        event="moderation_ban",
        outcome="warning",
        title="Account restricted",
        details={
            "ticket_id": ticket_id,
            "action": "ban",
            "policy_category": str(policy_category or "unspecified"),
            "ban_duration_days": duration,
            "effective_duration": _ban_duration_label(duration),
            "ban_until": banned_until,
            "note": (note or "")[:500],
            **({"enforcement_id": enforcement_id} if enforcement_id else {}),  # NEW
        },
    )
```

### Step 3 — Call sites pass `enforcement_id`

In the *decide* path (`app/routers/admin_moderation.py:707`):

```python
eid = _persist_enforcement_if_needed(
    decision=inp.decision, ticket_id=ticket_id,
    offender_user_id=offender_user_id, admin_user_id=admin.sub,
    note=note, now_ts=now,
)
```

In the *resolve* path (`app/routers/admin_moderation.py:938–960`), add a call to
`_persist_enforcement_if_needed` for resolve actions (it is currently absent) and pass the
returned ID:

```python
# at the top of the warn/ban branches in the resolve handler:
eid = _persist_enforcement_if_needed(
    decision=inp.enforcement_action,
    ticket_id=ticket_id,
    offender_user_id=offender_user_id,
    admin_user_id=admin.sub,
    note=note,
    now_ts=str(now_ts()),
)

if inp.enforcement_action == "warn":
    issue_warning_notification(
        offender_user_id=..., ticket_id=..., note=...,
        policy_category=..., enforcement_id=eid,
    )
elif inp.enforcement_action == "ban":
    apply_ban(
        ..., enforcement_id=eid,
    )
```

### Dev/Prod parity (SECOPS-007)

`write_alert` writes to `T.alerts` in DynamoDB. In dev mode the same DynamoDB Local instance
is used. There is no mock-only code path for alert writes, and the `enforcement_id` field is a
plain string stored in the `details` map column, so no schema migration is needed. The fix
applies identically to dev and prod. No feature flag is required.

### Backward compatibility

`enforcement_id` is additive to the `details` JSON blob. Existing alert consumers that do not
read `enforcement_id` are unaffected. The field is optional (`str | None`) in the function
signatures so call sites that do not yet have an `enforcement_id` (legacy callers) continue to
work without modification.


## 5. Testing, Verification & Rollout

### Regression test (pytest offline)

The two new tests below target the `moderation_policy_engine` service layer directly. They
monkeypatch `write_alert` so no real DynamoDB or SNS calls are made, making them suitable for
the offline pytest suite. The tests deliberately do NOT mock `_persist_enforcement_if_needed`
because that function is in the router module and the service layer is the concern here; the
router-level integration test (described below) covers the full call chain.

Add to `tests/test_moderation_policy_engine.py`:

```python
def test_issue_warning_notification_includes_enforcement_id(monkeypatch) -> None:
    """Alert details must carry enforcement_id when supplied."""
    calls = []
    monkeypatch.setattr(
        moderation_policy_engine, "write_alert",
        lambda *a, **kw: calls.append(kw) or {"alert_id": "x"},
    )
    moderation_policy_engine.issue_warning_notification(
        offender_user_id="u10",
        ticket_id="t10",
        note="test",
        policy_category="spam",
        enforcement_id="enf_abc123",   # supplied
    )
    assert calls[0]["details"]["enforcement_id"] == "enf_abc123"


def test_apply_ban_alert_includes_enforcement_id(monkeypatch) -> None:
    """Ban alert details must carry enforcement_id when supplied."""
    calls = []
    monkeypatch.setattr(moderation_policy_engine.T.account_state, "put_item", lambda **kw: None)
    monkeypatch.setattr(
        moderation_policy_engine, "write_alert",
        lambda *a, **kw: calls.append(kw) or {"alert_id": "y"},
    )
    moderation_policy_engine.apply_ban(
        offender_user_id="u11",
        ticket_id="t11",
        admin_user_id="admin1",
        note="ban",
        duration_days=0,
        policy_category="criminal",
        enforcement_id="enf_xyz789",
    )
    assert calls[0]["details"]["enforcement_id"] == "enf_xyz789"
```

**Fails before fix**: both assertions raise `KeyError` because `enforcement_id` is absent from
`details`. **Passes after fix**: `enforcement_id` is conditionally merged into `details`.

Add an integration test to `tests/test_admin_moderation_tickets_router.py` that:
1. Creates a moderation ticket.
2. Calls the resolve endpoint with `enforcement_action="warn"`.
3. Queries `T.alerts` for the offender user and asserts `details["enforcement_id"]` is present
   and matches the `enforcement_id` in `T.user_enforcement_history`.

### Manual QA steps

1. Start the dev stack (`just up`).
2. Create a moderation ticket via the admin UI or directly via
   `POST /moderation/tickets` with a test user as the offender.
3. Resolve the ticket with `enforcement_action="warn"` using an admin-role session.
4. Check the offender's alert list (`GET /ui/alerts`); confirm the newest alert's `details`
   contains a non-empty `enforcement_id` string (format: `enf_` followed by 20 hex chars).
5. Query `GET /moderation/users/{user_id}/history`; confirm the top entry's `enforcement_id`
   matches the value in the alert's `details`.
6. Repeat with `enforcement_action="ban"` and verify the ban alert also carries `enforcement_id`.
7. Verify that the appeals form pre-populates the `enforcement_id` from the alert (front-end
   change, tracked separately) or that a user can copy it manually from the alert details view.

### Metrics / observability

Add a structured log line in `_persist_enforcement_if_needed` at the point the ID is returned:
```python
logger.info(
    "enforcement_created",
    extra={
        "enforcement_id": enforcement_id,
        "decision": decision,
        "ticket_id": ticket_id,
        "user_id": user_id,
    }
)
```
No new metrics counter is required for this gap alone; existing moderation KPI dashboards will
continue to function. A future enhancement could add an `enforcement_id_in_alert_rate` metric
to confirm 100% of enforcement actions have linked alerts.

### Rollback

The change is purely additive (new optional field in `details` dict). Rolling back means
removing the `enforcement_id` key from `details`, restoring the previous behavior. No data
migration is needed in either direction. Because `enforcement_id` is a string field in the
`details` DynamoDB map, DynamoDB does not require a schema change in either direction.
Existing alert records written before the fix will simply lack the field; those written after
the fix will have it. Both old and new records are read correctly by `GET /ui/alerts` because
the response model uses `dict` for `details` without requiring specific sub-keys.

`moderation_policy_engine.py` (~4 lines each in `issue_warning_notification` and `apply_ban`).
Two new unit tests in `test_moderation_policy_engine.py`. One integration test in
`test_admin_moderation_tickets_router.py`. Estimated 1–2 hours implementation, 0.5 hours review.

### Sequencing and dependencies

Can be deployed independently of all other GAP tickets in the backlog. No schema migrations,
no dependency on MON-003 or MON-004. However, this fix should be prioritized before the next
compliance audit cycle given the DSA traceability requirement. Coordinate with the frontend
team to update the appeals form to read and display `enforcement_id` from the alert record,
so users can copy it directly into appeal submissions rather than requiring support lookup.

### Observability note

The existing `write_moderation_audit_event` call in the decide and resolve paths already logs
the enforcement action with `ticket_id` and `target_user_id`. After this fix, the audit log
entry can also include `enforcement_id` (pass it as part of the `metadata` dict) to close
the audit event chain from ticket → enforcement record → alert → appeal.
