# GAP-0218: `_AUTO_CONFIRM_DONATIONS = True` is a hardcoded module-level constant, not gated on `S.dev_mode` — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing.

## 1. Summary & Classification

**Plain-English statement**: `app/services/group_fundraising.py` contains the module-level constant `_AUTO_CONFIRM_DONATIONS = True` at line 35. When this flag is `True`, every donation — including donations made with failed or unverified payment instruments — is immediately confirmed, the treasury is credited, and `raised_cents` is incremented, all synchronously in the request handler, without waiting for a real Stripe webhook confirming that money has actually moved. Because the flag is `True` unconditionally, this behaviour is active in production today, not just in dev/test.

**Severity**: HIGH — Financial integrity defect. A bad actor can create a donation with a card they know will decline (or with a stolen card number that passes Stripe's initial `PaymentIntent` creation but fails on capture) and the group treasury will be credited as if real money was received.

**Status**: Open. Source ticket: GROUP-003. Effort: M. Owning area: Group fundraising / Payments.

**Claim verdict**: Confirmed. `app/services/group_fundraising.py:35`:
```python
_AUTO_CONFIRM_DONATIONS = True
```
Line 305:
```python
if _AUTO_CONFIRM_DONATIONS:
    confirm_donation(fundraiser_id, donation_id, pi_id)
    donation["status"] = "completed"
```
There is no `S.dev_mode` guard, no feature flag, and no webhook handler. The claim is accurate with no corrections required.

**Related tickets**: GROUP-003 (source), GROUP-004 (treasury — dissolution atomicity, GAP-0219), SECOPS-007.

## 2. Current-State Investigation (root cause)

### The donation creation path

`create_donation` (`app/services/group_fundraising.py`) follows this sequence:

1. **Lines 272–293**: Validate fundraiser exists and is active; compute amount; generate `donation_id`; create a mock Stripe PaymentIntent (`pi_id = "pi_mock_" + uuid4().hex`).
2. **Lines 293–294**: Write the donation record to DDB with `status = "pending"`.
3. **Lines 305–307** (the gap):
   ```python
   if _AUTO_CONFIRM_DONATIONS:
       confirm_donation(fundraiser_id, donation_id, pi_id)
       donation["status"] = "completed"
   ```
4. **Line 309**: Return the donation response.

`confirm_donation` (line 313) does three things:
- Marks the donation `status = "completed"` in DDB.
- Increments `raised_cents` and `donation_count` on the fundraiser record atomically via `update_item`.
- Calls `group_treasury.credit_donation(group_id, amount_cents, ...)` which credits the group treasury wallet and writes a ledger entry.

### What "auto-confirm" means at runtime

With `_AUTO_CONFIRM_DONATIONS = True`, the entire payment confirmation lifecycle collapses into a synchronous side-effect of the POST request. The mock Stripe `pi_id` is never verified against any Stripe event or webhook. In a dev environment this is intentional: `stripe-mock` cannot complete off-session PaymentIntents (they always return `requires_payment_method`), so auto-confirming bypasses the Stripe mock limitation.

The problem is that this constant is `True` unconditionally. In production, real Stripe PaymentIntents pass through Stripe's charge pipeline. The PaymentIntent is created in `pending` state; Stripe's actual confirmation comes asynchronously via a `payment_intent.succeeded` webhook. The current code credits the treasury before that webhook fires — or even if it never fires (e.g., card declined after intent creation).

### Why there is no webhook handler

The module docstring (line 1–13) explicitly acknowledges the design:
> "Donations are deterministic in dev/test: a donation is created in `pending` status with a mock Stripe payment-intent id and an auto-confirm path so the treasury credit + `raised_cents` increment happen synchronously."

No `POST /internal/fundraisers/{id}/donations/{id}/confirm` webhook handler exists anywhere in the codebase. A search for `payment_intent.succeeded` in `app/routers/` returns zero results related to fundraising. The Stripe webhook infrastructure (`app/routers/billing.py`) handles subscription and one-time payment webhooks but has no fundraising handler.

### Dev vs prod divergence

| Environment | Stripe | `_AUTO_CONFIRM_DONATIONS` | Behaviour |
|---|---|---|---|
| Dev | stripe-mock (fake) | `True` | OK — no real money, determinism needed |
| Prod | Real Stripe | `True` (BUG) | Treasury credited before charge clears |

This is a SECOPS-007 violation: the dev shortcut is deployed to production.

## 3. Impact / Exploit / Blast Radius

**Exploit walkthrough**:

1. Attacker sends `POST /ui/groups/{group_id}/fundraisers/{fundraiser_id}/donations` with `amount_cents=100000` (100 USD) and a card number known to fail at capture (e.g., Stripe test card `4000000000000002` — declined).
2. Stripe creates a PaymentIntent in `requires_payment_method` state. The intent ID is returned.
3. `create_donation` writes `status = "pending"` to DDB, then immediately calls `confirm_donation` because `_AUTO_CONFIRM_DONATIONS = True`.
4. `confirm_donation` marks the donation `status = "completed"`, increments `raised_cents += 100000`, and credits the group treasury `balance_cents += 100000`.
5. No money actually moved. The group can now spend $100 from their treasury (e.g., on ad campaigns via `spend_treasury`).

**Scale**: The attack is limited only by rate limits. If no per-user donation rate limit exists, an attacker can inflate a treasury to any balance.

**Worst case**: Group treasury balance reflects entirely fictional donations. Group funds ad campaigns, purchases, or — via dissolution (GAP-0219) — the fake credits are distributed as refunds to contributors. Since `dissolve_treasury` applies pro-rata refunds from the `balance_cents` field, fraudulent credits could result in real wallet credits being paid out to real users from a platform-subsidised fund.

**Blast radius**: All active fundraisers are affected. Any group with a fundraiser is a potential target. The treasury ledger integrity is compromised for any group that has received fake donations.

## 4. Fix Design (code-level)

### Step 1 — Gate the constant on `S.dev_mode`

The minimal fix is one line:

```python
# app/services/group_fundraising.py:35
# Before:
_AUTO_CONFIRM_DONATIONS = True

# After:
_AUTO_CONFIRM_DONATIONS = S.dev_mode
```

Import `S` is already present (`from app.core.settings import S` — add if not present; verify with `grep -n "from app.core.settings" app/services/group_fundraising.py`). With `S.dev_mode` defaulting to `False` in production, the auto-confirm path becomes unreachable in prod.

**Important**: `S` is imported at module load time, so `_AUTO_CONFIRM_DONATIONS` becomes a module-level boolean computed from `S.dev_mode` at startup. This is safe — `S` is a singleton initialised before any router or service module is loaded.

### Step 2 — Implement the Stripe webhook handler

In production, confirmation must come from a Stripe `payment_intent.succeeded` event. Add a handler to the existing Stripe webhook router (`app/routers/billing.py` or a new `app/routers/fundraising_webhooks.py`):

```python
# In the Stripe webhook dispatcher (where event.type is matched):

elif event["type"] == "payment_intent.succeeded":
    pi = event["data"]["object"]
    pi_id = pi["id"]
    metadata = pi.get("metadata", {})
    fundraiser_id = metadata.get("fundraiser_id")
    donation_id = metadata.get("donation_id")
    if fundraiser_id and donation_id:
        try:
            from app.services.group_fundraising import confirm_donation
            confirm_donation(fundraiser_id, donation_id, stripe_pi_id=pi_id)
            logger.info("fundraising.donation_confirmed_via_webhook",
                        extra={"fundraiser_id": fundraiser_id, "donation_id": donation_id})
        except Exception as exc:
            logger.error("fundraising.donation_confirm_failed",
                         extra={"fundraiser_id": fundraiser_id, "donation_id": donation_id,
                                "error": str(exc)})
            raise  # re-raise so Stripe retries
```

For this to work, the PaymentIntent must be created with `metadata={"fundraiser_id": ..., "donation_id": ...}`. The current mock `pi_id = "pi_mock_" + uuid4().hex` must be replaced with a real Stripe PaymentIntent creation call (guarded by `not S.dev_mode`):

```python
if S.dev_mode:
    pi_id = f"pi_mock_{uuid4().hex}"
    checkout_url = None
else:
    stripe_pi = stripe.PaymentIntent.create(
        amount=amount_cents,
        currency="usd",
        metadata={"fundraiser_id": fundraiser_id, "donation_id": donation_id},
        confirm=False,
    )
    pi_id = stripe_pi["id"]
    checkout_url = stripe_pi.get("next_action", {}).get("redirect_to_url", {}).get("url")
```

### Step 3 — Idempotency guard in `confirm_donation`

`confirm_donation` (line 326) already guards against double-confirmation:
```python
if donation.get("status") == "completed":
    return {"ok": True, "already_confirmed": True}
```
This guard is sufficient for idempotent webhook retries. No additional work needed here.

### Step 4 — Admin webhook endpoint for manual confirmation

For cases where a Stripe webhook is missed (network failure, endpoint downtime), provide a ROOT-only manual confirmation endpoint:

```python
@router.post("/ui/root/fundraisers/{fundraiser_id}/donations/{donation_id}/confirm")
async def manual_confirm_donation(
    fundraiser_id: str, donation_id: str, ctx=Depends(require_root_session)
):
    """ROOT-only: manually confirm a pending donation (break-glass for missed webhooks)."""
    result = confirm_donation(fundraiser_id, donation_id)
    audit_event("fundraising.donation_manually_confirmed", ctx["user_sub"], request,
                outcome="success", fundraiser_id=fundraiser_id, donation_id=donation_id)
    return result
```

### Dev/Prod parity (SECOPS-007)

| Path | Dev | Prod |
|---|---|---|
| `_AUTO_CONFIRM_DONATIONS` | `True` (S.dev_mode=True) | `False` (S.dev_mode=False) |
| PaymentIntent creation | Mock `pi_mock_*` | Real Stripe PI with metadata |
| Confirmation trigger | Inline in `create_donation` | `payment_intent.succeeded` webhook |
| Manual override | ROOT endpoint | ROOT endpoint (same code) |

The ROOT manual endpoint is available in both environments (useful for dev debugging and prod break-glass). The auto-confirm shortcut is preserved for dev/test (stripe-mock limitation).

### Feature flag

The `_AUTO_CONFIRM_DONATIONS = S.dev_mode` assignment can optionally be overridden by a separate env var for staging environments where `DEV_MODE=0` but real Stripe webhooks are not configured:

```python
_AUTO_CONFIRM_DONATIONS = bool(
    os.environ.get("AUTO_CONFIRM_DONATIONS", "1" if S.dev_mode else "0") == "1"
)
```

This allows staging to use auto-confirm without setting `DEV_MODE=1`. For production, `AUTO_CONFIRM_DONATIONS` should never be set (defaults to `"0"`).

### Rollout

- **Effort**: M — Step 1 (one-line fix) is immediate. Step 2 (webhook handler + PI metadata) is the main work. Step 4 (ROOT endpoint) is ~20 lines.
- **Ordering**: Deploy step 1 first (stops the immediate bleeding). Deploy step 2 + webhook endpoint registration second. Deploy step 4 for operational comfort.
- **Migration**: Existing `completed` donations in prod are unaffected (they were confirmed under the auto-confirm regime; the data is already there). No DDB migration needed.
- **Rollback**: Set `AUTO_CONFIRM_DONATIONS=1` env var to restore auto-confirm behaviour temporarily while investigating webhook delivery issues.
- **Risk**: After step 1 deploys without step 2, all new donations stay `pending` in prod until webhooks arrive. Ensure Stripe webhook endpoint is registered and verified before deploying step 1 to a live fundraiser.

### Note on `confirm_donation` idempotency with real Stripe

When `_AUTO_CONFIRM_DONATIONS = False` and a real Stripe webhook fires, `confirm_donation` is the single confirmation path. The existing guard at line 326 (`if donation.get("status") == "completed": return {"ok": True, "already_confirmed": True}`) handles the case where Stripe retries a `payment_intent.succeeded` event. However, the treasury credit operation itself (`group_treasury.credit_donation`) does not have an idempotency guard of its own. If two concurrent webhook deliveries both read the donation as `"pending"` before either has written `"completed"`, both will attempt to credit the treasury (a TOCTOU race). This is a separate atomicity gap: the `update_item` that marks `status = "completed"` should use a conditional expression (`ConditionExpression="attribute_not_exists(status) OR #s <> :completed"`) so only one execution succeeds. This hardening is a follow-on to the core GAP-0218 fix, logged as a lower-severity item for the same GROUP-003 implementation cycle.
