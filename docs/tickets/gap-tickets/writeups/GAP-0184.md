# GAP-0184: No IP-based rate limiting on public download endpoint — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against real code before writing; cites `file:line`.

## 1. Summary & Classification

**Bug statement**: The public encrypted file-share download endpoints — `POST /public/files/share/{link_id}/download` and `GET /public/files/share/{link_id}/download` — accept anonymous requests with no rate limiting of any kind. Neither endpoint inspects `X-Forwarded-For`, accepts a `Request` object, nor calls any rate-limit helper. A single IP can attempt password guessing against password-protected links at unlimited speed, and can also enumerate link IDs or exhaust S3 decrypt operations without any back-pressure.

- **Severity**: HIGH
- **Source ticket**: FILES-001
- **Owning area**: File manager / Public share links
- **Status**: Open (confirmed gap)
- **Verdict**: **Confirmed**. The cited line `app/routers/file_share_links.py:96` is exactly the `POST /{link_id}/download` endpoint. Neither it nor the parallel GET endpoint at line 103 takes a `Request` dependency, imports `client_ip_from_request`, or calls any rate-limit function. The `app/services/file_share_links.py` service layer also has no IP rate-limit logic.
- **One-line impact**: Unlimited password brute-force against protected share links and unlimited unauthenticated download attempts; both are trivially automatable with no throttling.
- **Related tickets**: GAP-0185 (TOCTOU in the same service), FILES-001

## 2. Current-State Investigation (root cause)

### Endpoint code (file:line)

`app/routers/file_share_links.py:96–106`:

```python
@public_router.post("/{link_id}/download")
def download_share_link_endpoint(link_id: str, body: ShareLinkDownloadIn | None = None) -> Response:
    password = body.password if body else None
    result = svc.consume_share_link(link_id=link_id, password=password)
    return _download_response(result)


@public_router.get("/{link_id}/download")
def download_share_link_get_endpoint(link_id: str, password: str | None = None) -> Response:
    result = svc.consume_share_link(link_id=link_id, password=password)
    return _download_response(result)
```

Neither endpoint signature includes `req: Request` and neither calls `client_ip_from_request`. There are no `Depends(...)` decorators beyond the default FastAPI parameter injection.

### Service layer (file:line)

`app/services/file_share_links.py:291–330`, `consume_share_link`, performs:
1. A DynamoDB `get_item` for the link record (line 297).
2. Pre-checks: `is_revoked`, `is_expired`, `_is_used` (lines 299–307).
3. Password bcrypt verification (lines 309–313).
4. Atomic DynamoDB `update_item` with `ConditionExpression` (lines 317–326).
5. S3 key retrieval and AES-GCM decryption (lines 335–347).

No rate-limit check occurs anywhere in this flow. Critically, the password check at line 309 calls `bcrypt.checkpw`, which is intentionally slow (O(2^cost) CPU). A single-IP brute-force would exhaust backend CPU even before it succeeds.

### Existing rate-limit infrastructure

The rate-limit service at `app/services/rate_limit.py` provides `_bucket_limit(user_sub, sid, max_n, win)` (line 60), which uses DynamoDB's sessions table for counter storage. The helper at `app/core/normalize.py:9`, `client_ip_from_request(req)`, reads `X-Forwarded-For` (respecting proxy headers) or falls back to `req.client.host`. Both already work without authentication — `_ip_user(ip)` at line 81 of `rate_limit.py` constructs an IP-keyed pseudo-user-sub (`ip#{ip}`) that can be used as the `user_sub` parameter for anonymous IP bucketing.

### Ticket specification gap

The FILES-001 ticket design specifies:
- **10 req/min per IP**: General download rate limit (prevents enumeration/DoS).
- **5 password attempts per (link_id, IP) per minute**: Targeted brute-force protection for password-protected links.

Neither limit exists today.

### Dev vs prod behavior

In dev, `S.ddb_sessions_table` is set (DynamoDB Local at port 8001). `_sessions_table_enabled()` returns `True`. The existing `_bucket_limit` function works in dev. In prod, the same DynamoDB AWS table is used. There is no behavioral difference — the missing call sites are the only gap.

## 3. Impact / Exploit / Blast Radius

### Password brute force

A password-protected share link uses bcrypt hashing (line 311 of `file_share_links.py`). Without rate limiting, an attacker who obtains a `link_id` (128-bit entropy, but link IDs can be shared or discovered via phishing) can brute-force the password at the speed their network and the backend's CPU allow. A typical bcrypt cost of 12 allows ~20–50 checks/second per CPU core. A small botnet could attempt thousands of common passwords within seconds.

The impact is amplified because: (a) password guessing against the `is_revoked` check is frictionless (failed passwords don't count toward `download_count`), and (b) there is no lockout mechanism at any layer.

### Link ID enumeration

Even without a password, repeated requests against the public info endpoint (`GET /public/files/share/{link_id}/info`, line 76) and the download endpoint allow an attacker to probe for valid link IDs. The 128-bit UUIDs make guessing impractical, but the absence of rate limiting means:
- Scraping of shared link URLs from other surfaces (e.g., email forwards, social posts) enables bulk validation at high speed.
- Error response timing differences (revoked vs. expired vs. wrong password) provide an oracle at zero cost.

### S3 and KMS cost amplification

Each successful `consume_share_link` call invokes:
1. One DynamoDB `get_item` + one `update_item`.
2. One S3 `get_object`.
3. One KMS `Decrypt` (or local HMAC equivalent in dev).

Without rate limiting, a single IP can drain these operations at API throughput limits, generating unexpected AWS cost spikes in prod.

### Blast radius

- All public share links, across all users.
- No authentication required — fully exploitable by anonymous callers.
- Password-protected links are the highest-risk target (direct content exfiltration); non-password links are still subject to DoS/cost amplification.
- The authenticated owner endpoints (create/list/revoke) are not affected — they use `require_ui_session`.

## 4. Fix Design (code-level)

### Change 1: Add `Request` dependency to both public download endpoints

**File**: `app/routers/file_share_links.py`

```python
from fastapi import APIRouter, Depends, HTTPException, Request
from app.core.normalize import client_ip_from_request
from app.services.rate_limit import rate_limit_share_link_download  # new function

@public_router.post("/{link_id}/download")
def download_share_link_endpoint(
    link_id: str,
    req: Request,
    body: ShareLinkDownloadIn | None = None,
) -> Response:
    client_ip = client_ip_from_request(req)
    rate_limit_share_link_download(link_id, client_ip)
    password = body.password if body else None
    result = svc.consume_share_link(link_id=link_id, password=password)
    return _download_response(result)


@public_router.get("/{link_id}/download")
def download_share_link_get_endpoint(
    link_id: str,
    req: Request,
    password: str | None = None,
) -> Response:
    client_ip = client_ip_from_request(req)
    rate_limit_share_link_download(link_id, client_ip)
    result = svc.consume_share_link(link_id=link_id, password=password)
    return _download_response(result)
```

### Change 2: Add `rate_limit_share_link_download` to the rate_limit service

**File**: `app/services/rate_limit.py`

```python
def rate_limit_share_link_download(link_id: str, ip: str) -> None:
    """Enforce two limits on the public share-link download endpoint:
    1. 10 req/min per IP (general enumeration/DoS protection).
    2. 5 attempts per (link_id, IP) per minute (password brute-force protection).
    Both limits use the existing _bucket_limit DynamoDB counter.
    """
    global_win = _env_int("SHARE_LINK_DOWNLOAD_WINDOW_SECONDS", 60)
    global_max = _env_int("SHARE_LINK_DOWNLOAD_MAX_PER_WINDOW", 10)

    pwd_win = _env_int("SHARE_LINK_PASSWORD_WINDOW_SECONDS", 60)
    pwd_max = _env_int("SHARE_LINK_PASSWORD_MAX_PER_WINDOW", 5)

    # 1. Global IP rate limit
    ip_key = _ip_user(ip)
    if not _bucket_limit(ip_key, "rl#share_download", global_max, global_win):
        raise HTTPException(
            status_code=429,
            detail={
                "code": "download_rate_limited",
                "message": "Too many download requests; try again shortly",
                "retry_after_seconds": global_win,
            },
            headers={"Retry-After": str(global_win)},
        )

    # 2. Per-link-per-IP password attempt limit (hash link_id to keep key short)
    link_hash = sha256_str(link_id)[:16]
    link_ip_sid = f"rl#share_pwd#{link_hash}"
    if not _bucket_limit(ip_key, link_ip_sid, pwd_max, pwd_win):
        raise HTTPException(
            status_code=429,
            detail={
                "code": "password_attempt_rate_limited",
                "message": "Too many password attempts for this link; try again shortly",
                "retry_after_seconds": pwd_win,
            },
            headers={"Retry-After": str(pwd_win)},
        )
```

### SECOPS-007 dev/prod parity

- `_bucket_limit` uses `T.sessions` (DynamoDB Local in dev, AWS DynamoDB in prod). The same code path runs in both environments.
- `client_ip_from_request` correctly reads `X-Forwarded-For` (for prod deployments behind an ALB or Nginx reverse proxy) and falls back to `req.client.host` (for direct connections in dev).
- Environment variables `SHARE_LINK_DOWNLOAD_MAX_PER_WINDOW`, `SHARE_LINK_DOWNLOAD_WINDOW_SECONDS`, `SHARE_LINK_PASSWORD_MAX_PER_WINDOW`, `SHARE_LINK_PASSWORD_WINDOW_SECONDS` allow tuning per environment without code changes. Dev can set higher limits to avoid test friction.
- No `if S.dev_mode` bypass is introduced — limits apply in dev as well (just configurable).

### Backward compatibility

The endpoints remain unauthenticated. Existing clients that call `/public/files/share/{link_id}/download` will experience 429s only if they exceed the configured limits. Normal single-user download flows are unaffected (one download per link per IP).

### Alternatives considered

1. **Middleware-level rate limiting (e.g., `slowapi` / Redis)**: More robust for high-volume prod deployments, but introduces a new infrastructure dependency. The DynamoDB-backed `_bucket_limit` approach is consistent with every other rate-limit in the codebase and requires no new infrastructure.
2. **Limit exclusively in the service layer, not the router**: Possible, but the service layer lacks `Request` context. Passing the IP as a function parameter would work but changes the `consume_share_link` signature — a wider refactor. Adding the check at the router layer is minimal-impact.
3. **Account-level lockout (not IP-based)**: Not applicable here — these are public/anonymous endpoints with no account context.

### Metrics / observability

```python
logger.warning("share link rate limited", extra={"ip": ip, "link_id_prefix": link_id[:8]})
```

### Rollback

Remove the `Request` parameter and `rate_limit_share_link_download(link_id, client_ip)` call from both endpoints. No DynamoDB migration needed (rate-limit counters have a TTL and expire automatically via `with_ttl`).

### Risks

- **Shared-IP environments (NAT, corporate proxies)**: Multiple legitimate users behind the same NAT gateway will share the 10 req/min global cap. The `SHARE_LINK_DOWNLOAD_MAX_PER_WINDOW` env var allows raising this for environments where it causes false positives.
- **CDN/proxy IP spoofing**: `client_ip_from_request` trusts the first value in `X-Forwarded-For`. In a deployment without a trusted proxy, this can be spoofed. The fix should be paired with proper proxy-header trust configuration at the ingress layer (nginx/ALB).
- **DynamoDB cold-start**: In a first-request scenario (empty sessions table), `_bucket_limit` returns `True` (allows the request). This is the existing behavior for all rate-limited endpoints and is acceptable.

### Effort: M (Medium)

One new rate-limit function (~30 lines), four new env vars, two endpoint signature changes, and tests covering both limits. No schema changes.

### Sequencing

Apply after GAP-0185 (TOCTOU in the same service) so both fixes land together. Both touch `app/services/file_share_links.py` and `app/routers/file_share_links.py`; coordinating them in one PR avoids merge conflicts.
