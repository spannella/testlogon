# GAP-0032: Admin Can Disburse Treasury Funds to Their Own Wallet — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real code at file:line. Builds on investigation doc
> `docs/tickets/gap-tickets/investigations/GAP-0032.md`.

## 1. Summary & Classification

**GAP-0032** identifies a missing self-disbursement guard in the syndicate treasury
`disburse()` function. The SYND-004 design specifies a "no-admin-withdrawal" constraint:
the syndicate admin must not be able to receive treasury disbursements. This constraint was
documented in the ticket but the one-line guard was never implemented in code.

- **Severity**: CRIT (direct financial theft vector)
- **Source ticket**: SYND-004
- **Owning area**: Syndicate treasury (`app/services/syndicate_treasury.py`)
- **Status**: Open
- **Effort**: S (~30 minutes)

**Verdict**: Confirmed. `app/services/syndicate_treasury.py:240-339` — the `disburse()`
function validates admin identity and recipient membership but performs no check that
`admin_sub != recipient_user_id`. Because the admin is always a member of their own
syndicate (added at creation time), both guards pass silently when the admin disburses
to themselves.

**One-line impact**: A syndicate admin can drain the entire treasury balance to their own
personal wallet in a single authenticated API call, with no secondary approval or rate limit.

**Related tickets**: SYND-004 (original spec), GAP-0021 (`dissolve_group` missing
`dissolve_treasury` call — separate gap). No dependency blockers; the fix is a one-liner
in an existing function.

## 2. Current-State Investigation (Root Cause)

### 2.1 The `disburse()` function today

`app/services/syndicate_treasury.py:240-258`:

```python
def disburse(
    *,
    syndicate_id: str,
    admin_sub: str,
    recipient_user_id: str,
    amount_cents: int,
    note: str = "",
) -> Dict[str, Any]:
    """Admin disburses/withdraws treasury funds to a member's personal wallet."""
    # Admin-only.
    syndicate_svc._require_admin(syndicate_id, admin_sub)          # line 250

    if amount_cents <= 0:
        raise HTTPException(status_code=400, detail="Disbursement amount must be positive")

    # Recipient must be a member of the syndicate.
    syndicate = syndicate_svc._get_meta(syndicate_id)
    syndicate_svc._require_is_member(syndicate_id, recipient_user_id)  # line 257
```

There is no `if admin_sub == recipient_user_id` check anywhere in the function body or
in the calling router handler.

### 2.2 Why both guards always pass for the admin

`app/services/syndicates.py:560-571` defines the two guards:

```python
def _require_admin(syndicate_id: str, user_id: str) -> None:
    meta = _get_meta(syndicate_id)
    if meta["admin_user_id"] != user_id:
        raise HTTPException(403, "Only the syndicate admin can perform this action")

def _require_is_member(syndicate_id: str, user_id: str) -> None:
    resp = T.syndicates.get_item(
        Key={"pk": f"SYND#{syndicate_id}", "sk": f"MEMBER#{user_id}"}
    )
    if not resp.get("Item"):
        raise HTTPException(404, "User is not a member of this syndicate")
```

`app/services/syndicates.py:61-62` (inside `create_syndicate`):

```python
# Add creator as admin member
_add_member(syndicate_id, creator_sub, role="admin", ts=ts)
```

The creator is stored as both `admin_user_id` in the metadata record and as
`MEMBER#{admin_sub}` in the membership table. Therefore:

- `_require_admin(syndicate_id, admin_sub)` → passes (admin IS the admin).
- `_require_is_member(syndicate_id, admin_sub)` → passes (admin IS a member).

Both guards are satisfied when `recipient_user_id == admin_sub`. The missing check that
the investigation confirmed is specifically the **identity equality guard** between
the actor and the recipient.

### 2.3 Downstream side-effects when the exploit succeeds

When the guard is missing, `disburse()` continues through lines 259-339:
- Line 265-278: treasury balance is decremented by `amount_cents` (conditional, raises
  409 on overdraw — so the attack is limited to the available balance, not unlimited).
- Line 281: `apply_wallet_delta(T.billing, pk_recipient, amount_cents)` — credits the
  admin's personal wallet.
- Lines 285-339: treasury and member-side billing ledger entries are written, logging the
  action under `type="syndicate_treasury_disbursement"`.

The audit trail exists (ledger entries are written), but by the time any compliance review
catches it, the funds have already moved.

### 2.4 Root cause

The SYND-004 no-withdrawal constraint was included in the design document but the
implementing developer omitted the equality check. The existing guards (`_require_admin` +
`_require_is_member`) were designed for different purposes (role and membership validation)
and are insufficient as a self-dealing guard. No automated test covered the
admin-as-recipient case.

## 3. Impact / Exploit / Blast Radius

### 3.1 Concrete exploit walkthrough

1. Attacker creates a syndicate via `POST /ui/syndicates` and becomes `admin_user_id`.
2. Members join and contribute funds via `POST /ui/syndicates/{id}/treasury/contribute`,
   increasing `balance_cents`.
3. Attacker calls:
   ```
   POST /ui/syndicates/{id}/treasury/disburse
   Authorization: Bearer <attacker_token>
   {"recipient_user_id": "<attacker_sub>", "amount_cents": <full_balance>}
   ```
4. `_require_admin` passes (attacker is admin).
5. `_require_is_member` passes (attacker is a member).
6. Treasury is debited; attacker's wallet is credited.
7. Attacker repeats for any amount up to the current balance. Since `balance_cents >= amount`
   is checked, a single call drains exactly the full balance.

### 3.2 Worst case

- Financial theft: all contributed member funds are transferred to the admin's personal
  wallet in one request.
- No secondary approval required; no rate limit on the `disburse` endpoint.
- The attack is logged in ledger entries but those entries do not trigger any alerting.
- A compromised admin account (account takeover) enables the same attack against innocent
  members.

### 3.3 Severity justification

CRIT because: (a) direct and immediate financial impact, (b) requires only a normal
authenticated API call, (c) the design explicitly intended to prohibit this, (d) no
compensating control exists (no dual-approval, no withdrawal cooldown, no alert trigger).

### 3.4 Scope of other treasury operations

`spend_on_advertising` and `contribute` in `syndicate_treasury.py` are not affected — they
involve the treasury as a whole, not a personal-wallet recipient, so self-dealing via those
paths is not possible in the same way.

## 4. Fix Design (Code-Level)

### 4.1 The minimal fix

In `app/services/syndicate_treasury.py`, insert the self-disbursement guard immediately
after the `_require_admin` call at line 250 and before the `amount_cents` validation:

```python
def disburse(
    *,
    syndicate_id: str,
    admin_sub: str,
    recipient_user_id: str,
    amount_cents: int,
    note: str = "",
) -> Dict[str, Any]:
    """Admin disburses/withdraws treasury funds to a member's personal wallet."""
    # Admin-only.
    syndicate_svc._require_admin(syndicate_id, admin_sub)           # line 250

    # SECURITY: No-withdrawal constraint (SYND-004).
    # The admin must not be able to disburse treasury funds to themselves.
    if admin_sub == recipient_user_id:
        raise HTTPException(
            status_code=400,
            detail="Admin cannot disburse treasury funds to themselves",
        )

    if amount_cents <= 0:
        raise HTTPException(status_code=400, detail="Disbursement amount must be positive")

    # Recipient must be a member of the syndicate.
    syndicate = syndicate_svc._get_meta(syndicate_id)
    syndicate_svc._require_is_member(syndicate_id, recipient_user_id)
    ...
```

This is a single-expression string comparison: `O(1)`, no network calls, no schema changes.

### 4.2 Placement rationale

The guard is placed **after** `_require_admin` (which confirms the caller is the admin
and rejects non-admins early) and **before** `_require_is_member` (which makes a DynamoDB
`get_item` call). This ordering avoids the DDB round-trip in the self-dealing path and
fails fast with a clear error message.

### 4.3 Dev/Prod parity (SECOPS-007)

`app/services/syndicate_treasury.py` is pure Python business logic with no environment-
conditional code paths. The DynamoDB client used (`T.syndicate_treasury`) is provided by
`app/core/tables.py`, which points to DynamoDB Local in dev and AWS DynamoDB in prod via
`S.ddb_endpoint_url`. The inserted guard runs before any DynamoDB I/O, so its behavior is
identical in both environments. No feature flag is needed or appropriate for a security
invariant.

### 4.4 Alternatives considered

- **Block at the router level**: The router handler (`app/routers/syndicates.py`) could
  compare `actor.sub` against `recipient_user_id`. Rejected because the constraint belongs
  to the service layer, which is the authoritative boundary for financial invariants. A
  service-level check cannot be bypassed by future callers that do not go through the
  router.
- **Require a second admin for approval**: More robust long-term design (dual-control
  for large disbursements) but out of scope for this CRIT fix; requires new UX, new
  endpoints, and a new DDB schema. The one-liner fix addresses the immediate vulnerability.
- **Remove admin from membership**: Would break legitimate uses (admin views their own
  wallet balance via membership queries). Rejected.

## 5. Testing, Verification & Rollout

### 5.1 Regression tests (pytest offline)

```python
# tests/test_syndicate_treasury.py

def test_admin_cannot_disburse_to_self(client, syndicate_with_balance):
    """Before fix: returns 200. After fix: returns 400.

    syndicate_with_balance fixture: creates syndicate with admin_sub='admin',
    member_sub='member', seeds treasury balance of 1000 cents.
    """
    syndicate_id, admin_sub, _member_sub = syndicate_with_balance
    r = client.post(
        f"/ui/syndicates/{syndicate_id}/treasury/disburse",
        json={"recipient_user_id": admin_sub, "amount_cents": 500},
        headers={"x-user-id": admin_sub},  # dev-mode auth
    )
    assert r.status_code == 400
    assert r.json()["detail"] == "Admin cannot disburse treasury funds to themselves"


def test_admin_can_disburse_to_member(client, syndicate_with_balance):
    """Legitimate disbursement to a non-admin member still succeeds."""
    syndicate_id, admin_sub, member_sub = syndicate_with_balance
    r = client.post(
        f"/ui/syndicates/{syndicate_id}/treasury/disburse",
        json={"recipient_user_id": member_sub, "amount_cents": 200},
        headers={"x-user-id": admin_sub},
    )
    assert r.status_code == 200
    body = r.json()
    assert body["amount_cents"] == 200
    assert body["recipient_user_id"] == member_sub


def test_treasury_balance_not_changed_on_self_disburse(client, syndicate_with_balance):
    """Treasury balance must be unchanged after a rejected self-disbursement."""
    syndicate_id, admin_sub, _member_sub = syndicate_with_balance
    r_before = client.get(
        f"/ui/syndicates/{syndicate_id}/treasury",
        headers={"x-user-id": admin_sub},
    )
    balance_before = r_before.json()["balance_cents"]

    client.post(
        f"/ui/syndicates/{syndicate_id}/treasury/disburse",
        json={"recipient_user_id": admin_sub, "amount_cents": balance_before},
        headers={"x-user-id": admin_sub},
    )

    r_after = client.get(
        f"/ui/syndicates/{syndicate_id}/treasury",
        headers={"x-user-id": admin_sub},
    )
    assert r_after.json()["balance_cents"] == balance_before
```

**Fails before**: `test_admin_cannot_disburse_to_self` gets `200` instead of `400`.
`test_treasury_balance_not_changed_on_self_disburse` fails because the balance decrements.

**Passes after**: All three tests pass. The legitimate disbursement test verifies no
regression to valid workflows.

### 5.2 Manual QA steps

1. Start dev stack (`just up`), log in as Alice.
2. Create a syndicate, have Bob contribute funds (seed via DDB if needed).
3. As Alice (admin), call `POST /ui/syndicates/{id}/treasury/disburse` with
   `recipient_user_id = alice_sub`.
4. Verify response is `400` with message `"Admin cannot disburse treasury funds to themselves"`.
5. Verify Alice's wallet balance is unchanged.
6. Call the same endpoint with Bob's sub as `recipient_user_id`.
7. Verify response is `200` and Bob's balance increases.

### 5.3 Observability

The `disburse()` function writes treasury and member ledger entries only on success. The
rejected self-disbursement returns a 400 before any write occurs, so no phantom ledger
entries are created. No additional alerting is implemented by this fix; a future improvement
could add an audit event for rejected self-disbursement attempts (useful for detecting
abuse attempts).

### 5.4 Rollout and rollback

- No schema migration; no new DynamoDB tables or GSIs.
- No feature flag; this is a security invariant, not a toggleable feature.
- Deployment: hot-reload or rolling restart of the backend service is sufficient.
- Rollback: revert the two-line guard. No data migration needed.

### 5.5 Risk and effort

- **Risk**: Near-zero. The change is a single equality check that returns 400 for a
  previously-permitted but-should-never-be-permitted operation. No valid use cases are
  affected; legitimate disbursements to other members continue to work.
- **Effort**: S — 30 minutes: insert the guard, add three pytest cases, update any
  existing fixture-based disburse tests to use a non-admin recipient.
- **Sequencing**: Can land immediately; no upstream dependencies.
