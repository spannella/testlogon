# GAP-0074: Attribution Race Condition in attribute_referral — Remediation Write-up

## 1. Summary & Classification

**Claim status: Confirmed.**

`app/services/referrals.py::attribute_referral` (lines 156–204) uses a read-check-then-write pattern to prevent duplicate attributions: it calls `tbl.get_item` to check for an existing `REFERRAL#{referred_user_id}` record (line 179), and if none exists, calls `tbl.put_item` (line 203) without any conditional expression. Under concurrent signups (two simultaneous requests with the same `referred_user_id`), both `get_item` calls can return empty results before either `put_item` completes. Both writes succeed, creating two attribution records that name different referrers (if two codes were used) or two records with the same referrer, leading to duplicate commission entries.

- **Severity**: HIGH (financial integrity — double-credits referrer commission)
- **Source ticket**: AFFILIATE-001
- **Owning area**: Referrals / Affiliate system
- **Status**: Open
- **Impact**: Concurrent signups using the same referred user's ID (possible via registration race, retry storms, or deliberate abuse) can create multiple attribution records, each independently triggering `record_affiliate_commission` calls that credit the referrer multiple times.
- **Related tickets**: GAP-0075 (withdrawal endpoint absent), SEC-013 (duplicate-write race referenced in ticket), GAP-0008 (commission replay risk).


## 2. Current-State Investigation (root cause)

### The vulnerable function

`app/services/referrals.py`, lines 156–204:

```python
def attribute_referral(
    referred_user_id: str,
    referral_code: str,
    ip_address: str = "",
    source: str = "cookie",
) -> Optional[Dict[str, Any]]:
    tbl = _tbl()
    code_item = tbl.get_item(Key={"pk": f"REFCODE#{referral_code}", "sk": "META"}).get("Item")
    if not code_item or not code_item.get("active"):
        return None

    referrer_id = code_item["owner_user_id"]

    # Self-referral prevention
    if referrer_id == referred_user_id:
        logger.warning("Self-referral blocked: %s", referrer_id)
        return None

    # Check for existing attribution
    existing = tbl.get_item(
        Key={"pk": f"REFERRAL#{referred_user_id}", "sk": "META"}
    ).get("Item")
    if existing:
        return None

    # ... build item ...
    tbl.put_item(Item=item)   # ← line 203: NO ConditionExpression
    return item
```

### Race window

```
Time →
Thread A: get_item("REFERRAL#u1") → {} (not found)
Thread B: get_item("REFERRAL#u1") → {} (not found)
Thread A: put_item(item_A)  ← succeeds, writes attribution for code ABC
Thread B: put_item(item_B)  ← also succeeds, OVERWRITES attribution for code XYZ
                               (DynamoDB put_item replaces unconditionally)
```

With two different referral codes, whichever `put_item` lands second wins — the first attribution is silently overwritten. If the same code is used by both threads, both compute and write commissions against that single attribution record (via `record_affiliate_commission`) because both `get_item` calls in `record_affiliate_commission` (line 251–255) also have the same race.

### Compare with create_referral_code

The same file does use a conditional expression at line 102:

```python
tbl.put_item(Item=item, ConditionExpression="attribute_not_exists(pk)")
```

This pattern exists in `create_referral_code` but was not applied to `attribute_referral`. The gap was introduced when the two functions were written independently.

### DynamoDB consistency model

DynamoDB's default read consistency is eventually consistent. `get_item` with `ConsistentRead=False` (the default used here) can return stale data even in a single-region setup if a recent write has not propagated. Using `ConditionExpression="attribute_not_exists(pk)"` on `put_item` is the correct and only safe approach because it runs atomically in DynamoDB's write path — no separate read is needed and eventual-consistency gaps do not apply.

### Dev vs. prod behaviour

In dev (DynamoDB Local on port 8001), the race is harder to trigger because requests are typically sequential. In production with multiple uvicorn workers or concurrent browser requests (e.g., a user double-clicking a registration submit button, or a sign-up POST retried by a client-side timeout), the race window is real and exploitable with trivial timing.


## 3. Impact / Exploit / Blast Radius

### Worst-case financial exploit

1. Attacker controls both a referrer account (with referral code `ABC`) and a signup automation script.
2. The script fires 10 simultaneous `POST /api/register` requests for new user accounts, all carrying cookie `ref=ABC`.
3. The registration hook calls `attribute_referral(referred_user_id=new_uid, referral_code="ABC")`.
4. All 10 concurrent calls pass the `get_item` check (none see an existing attribution yet).
5. All 10 calls write attribution records. DynamoDB resolves last-writer-wins, so only one record persists.
6. But before the final write resolves, each of the 10 threads calls `record_affiliate_commission` for the first qualifying purchase by that user — resulting in up to 10 commission entries credited to the referrer.

More practically: with two simultaneous registrations, the referrer gets two `COMMISSION#...` rows for what should be a single attribution event.

### Data integrity consequence

`record_affiliate_commission` sums `commission_cents` into `available_for_withdrawal_cents` in `get_referral_dashboard` (line 387). A double commission inflates the referrer's reported balance. When GAP-0075 (withdrawal endpoint) is implemented, the referrer could withdraw funds that were never legitimately earned.

### Blast radius

The race window exists for every new user signup that carries a referral code. Volume: if the platform processes 1,000 signups/hour and 10% carry referral codes, that is ~100 potential race exposures per hour during peak load.


## 4. Fix Design (code-level)

### Minimal fix

Replace the unconditional `put_item` in `attribute_referral` with a conditional write, and handle `ConditionalCheckFailedException`:

```python
from botocore.exceptions import ClientError

def attribute_referral(
    referred_user_id: str,
    referral_code: str,
    ip_address: str = "",
    source: str = "cookie",
) -> Optional[Dict[str, Any]]:
    tbl = _tbl()
    code_item = tbl.get_item(
        Key={"pk": f"REFCODE#{referral_code}", "sk": "META"}
    ).get("Item")
    if not code_item or not code_item.get("active"):
        return None

    referrer_id = code_item["owner_user_id"]
    if referrer_id == referred_user_id:
        logger.warning("Self-referral blocked: %s", referrer_id)
        return None

    # Remove the get_item existence check — it is racy.
    # The put_item ConditionExpression provides the atomic guard.

    now = _now_iso()
    window_end = (
        datetime.now(timezone.utc) + timedelta(days=S.referral_commission_window_days)
    ).strftime("%Y-%m-%dT%H:%M:%SZ")

    item: Dict[str, Any] = {
        "pk": f"REFERRAL#{referred_user_id}",
        "sk": "META",
        "Entity": "ReferralAttribution",
        "referred_user_id": referred_user_id,
        "referrer_user_id": referrer_id,
        "referral_code": referral_code,
        "attributed_at": now,
        "attribution_source": source,
        "status": "pending",
        "commission_window_ends_at": window_end,
        "ip_address": ip_address,
        "GSI1PK": f"REFERRALS#{referrer_id}",
        "GSI1SK": f"{now}#REF#{referred_user_id}",
    }

    try:
        tbl.put_item(
            Item=item,
            ConditionExpression="attribute_not_exists(pk)",
        )
    except ClientError as exc:
        if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
            # Another concurrent request already wrote this attribution.
            # Return None to signal "already attributed" — same semantics as
            # the old get_item check, but now race-safe.
            logger.info(
                "attribute_referral: duplicate race blocked for %s", referred_user_id
            )
            return None
        raise  # unexpected DDB error — propagate

    return item
```

### Why remove the get_item check

The prior `get_item` → `put_item` pattern is a TOCTOU (time-of-check-time-of-use) race. Removing `get_item` and relying solely on `ConditionExpression` is both simpler and correct. It eliminates one DDB read per attribution call, reducing latency by ~1ms in the happy path. The conditional expression performs the equivalent check atomically at write time.

### record_affiliate_commission — secondary check

`record_affiliate_commission` (lines 238–289) also reads the attribution record before writing commission, but its `put_item` is also unconditional (line 289). For commission rows the primary key is `COMMISSION#{ts}#{transaction_id}` — the `ts` component makes collision unlikely but not impossible under high clock pressure. The safer fix is to add `ConditionExpression="attribute_not_exists(pk)"` there too:

```python
tbl.put_item(
    Item=entry,
    ConditionExpression="attribute_not_exists(pk)",
)
```

If a duplicate commission write races, the `ConditionalCheckFailedException` should be caught and logged (not re-raised), returning `None` to signal "already recorded." This is a secondary hardening that should accompany the primary fix.

### Dev/Prod parity (SECOPS-007)

DynamoDB Local (dev, port 8001) fully supports `ConditionExpression` including `attribute_not_exists`. Moto (used in pytest) also supports it. No mock-specific code path is needed. The `botocore.exceptions.ClientError` with code `ConditionalCheckFailedException` behaves identically in dev and production.

### Backward compatibility

Existing attribution records are unaffected. The key schema (`pk=REFERRAL#{id}`, `sk=META`) does not change. No migration is required.

### Alternatives considered

- **DynamoDB transactions (`transact_write_items`)**: Could wrap the existence check and the write atomically. Rejected because `transact_write_items` has a 25-item limit and higher per-request cost; the simpler conditional put achieves the same atomicity guarantee for this single-item write.
- **Application-level distributed lock (Redis/DDB-based)**: Rejected because DynamoDB's built-in conditional expressions are the correct and idiomatic tool for this exact pattern. An external lock would introduce a new infrastructure dependency.
- **Retain get_item + add ConditionExpression**: Keeping both the existence check and the conditional write is harmless but wasteful. The conditional write alone is sufficient and eliminates the extra read.


## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to `tests/test_referrals.py`:

```python
import threading
import pytest
from unittest.mock import patch, MagicMock
from botocore.exceptions import ClientError


def make_ccfe():
    """Build a ClientError simulating ConditionalCheckFailedException."""
    return ClientError(
        {"Error": {"Code": "ConditionalCheckFailedException", "Message": ""}},
        "PutItem",
    )


def test_attribute_referral_conditional_write(mocker):
    """attribute_referral must use ConditionExpression='attribute_not_exists(pk)'."""
    tbl_mock = MagicMock()
    tbl_mock.get_item.return_value = {
        "Item": {
            "pk": "REFCODE#ABC123",
            "sk": "META",
            "owner_user_id": "referrer1",
            "active": True,
        }
    }
    tbl_mock.put_item.return_value = {}

    with patch("app.services.referrals._tbl", return_value=tbl_mock):
        from app.services.referrals import attribute_referral
        result = attribute_referral("new_user", "ABC123")

    assert result is not None
    call_kwargs = tbl_mock.put_item.call_args
    assert "ConditionExpression" in call_kwargs.kwargs or (
        call_kwargs.args and "ConditionExpression" in str(call_kwargs)
    ), "put_item must include ConditionExpression"
    assert "attribute_not_exists(pk)" in str(call_kwargs)


def test_attribute_referral_race_returns_none(mocker):
    """When ConditionalCheckFailedException is raised, return None (not an exception)."""
    tbl_mock = MagicMock()
    tbl_mock.get_item.return_value = {
        "Item": {
            "pk": "REFCODE#ABC123",
            "sk": "META",
            "owner_user_id": "referrer1",
            "active": True,
        }
    }
    tbl_mock.put_item.side_effect = make_ccfe()

    with patch("app.services.referrals._tbl", return_value=tbl_mock):
        from app.services.referrals import attribute_referral
        result = attribute_referral("new_user", "ABC123")

    assert result is None, (
        "Concurrent duplicate write must return None, not raise"
    )


def test_attribute_referral_no_double_commission_on_race(mocker):
    """Under concurrent calls, only one attribution must be written."""
    put_count = {"n": 0}
    lock = threading.Lock()

    def fake_put_item(**kwargs):
        with lock:
            put_count["n"] += 1
            if put_count["n"] > 1:
                # Simulate DDB rejecting the second write
                raise make_ccfe()

    tbl_mock = MagicMock()
    tbl_mock.get_item.return_value = {
        "Item": {
            "pk": "REFCODE#XYZ",
            "sk": "META",
            "owner_user_id": "ref_user",
            "active": True,
        }
    }
    tbl_mock.put_item.side_effect = fake_put_item

    results = []
    def do_attribute():
        with patch("app.services.referrals._tbl", return_value=tbl_mock):
            from app.services import referrals as r
            results.append(r.attribute_referral("signup_user", "XYZ"))

    threads = [threading.Thread(target=do_attribute) for _ in range(5)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()

    successes = [r for r in results if r is not None]
    assert len(successes) == 1, f"Expected exactly 1 attribution, got {len(successes)}"
```

The first and third tests fail before the fix (no `ConditionExpression` on `put_item`). The second test fails before the fix because `ConditionalCheckFailedException` is not caught (it propagates as an unhandled exception). All three pass after.

### Manual QA steps

2. Inspect DDB `app_single_table` for `pk=REFERRAL#{new_user_id}` — expect exactly one item.
3. Inspect `pk=AFFILIATE#{referrer_id}` commission rows — expect at most one.

### Observability

- The `logger.info("attribute_referral: duplicate race blocked for ...")` log line provides production visibility into race occurrences. Alert if the rate exceeds 1% of attribution calls.
- Add a CloudWatch metric or Prometheus counter `referral_attribution_race_total` incremented on each `ConditionalCheckFailedException` catch.

### Rollout

No schema changes. No migrations. Drop-in Python change to `app/services/referrals.py`. Deploy with normal backend restart.

Rollback: revert the single function — the old code path has been in production unchanged, so rollback risk is minimal.

### Sequencing with GAP-0075

This ticket (GAP-0074) must be deployed before GAP-0075 (withdrawal endpoint). The reasoning: if duplicate attributions already exist in the DDB table for any `referred_user_id`, the withdrawal endpoint could allow a referrer to withdraw funds computed from inflated commission totals. A pre-deployment audit of `app_single_table` for duplicate `REFERRAL#` entries is recommended before enabling withdrawals.

### Pre-deployment audit query

Before merging GAP-0075, run the following scan to identify any users with duplicate attribution records (indicating the race has already fired in production):

```python
import boto3, os
tbl = boto3.resource("dynamodb").Table(os.environ.get("APP_TABLE", "app_single_table"))
resp = tbl.query(
    IndexName="GSI1",
    KeyConditionExpression="GSI1PK = :prefix",
    ExpressionAttributeValues={":prefix": "REFERRALS#<referrer_id>"},
)
# If any referred_user_id appears more than once, flag for manual review
```

A full table scan filtered on `Entity=ReferralAttribution` grouped by `referred_user_id` would find any duplicates. Any user found with duplicate attributions should have the extra commission records manually set to `status=revoked` before the withdrawal endpoint is enabled.

### SECOPS-007 parity note

`ConditionExpression="attribute_not_exists(pk)"` is supported identically by DynamoDB Local (dev, port 8001), moto (pytest), and real DynamoDB (production). The `botocore.exceptions.ClientError` with error code `ConditionalCheckFailedException` is raised in all three environments when the condition fails. No mock-specific handling is required. The fix is inherently dev/prod parity-compliant.

**Effort**: S (< 1 day: service change, add import, three new test cases, optional pre-deployment audit).

### Long-term hardening

After this fix is deployed, consider adding a secondary uniqueness guard: a periodic Lambda or background task that scans `REFERRAL#` records and alerts on any `referred_user_id` appearing more than once in the GSI1 index. The conditional write makes duplicates structurally impossible going forward, but historical records (if any) will not be cleaned up by this fix alone.
