# GAP-0359: No Rate Limiting on `GET /ui/search` — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code. Source ticket: SOCIAL-003.

## 1. Summary & Classification

**Plain-English statement**: The global search aggregator endpoint `GET /ui/search`
(defined in `app/routers/search.py:797`) fans out to up to 9 backend modules concurrently
using a `ThreadPoolExecutor` with up to 8 workers. Any authenticated user can issue this
endpoint at unlimited rate: there is no call to any rate-limiting function in the handler,
no per-user request counter, and no `429 Too Many Requests` response path in the search
router. A single authenticated attacker can continuously hammer the endpoint, triggering
parallel DynamoDB `Scan`/`Query` operations across users, posts, catalog, files, messages,
tickets, contacts, videos, and calendar tables — causing CPU and DDB read-capacity
exhaustion.

**Claim verdict**: CONFIRMED. A full read of `app/routers/search.py:797–815` shows the
`global_search` handler: sanitizes the query, validates types, calls `_search_aggregator`,
and returns the result. No rate-limit function is imported or called anywhere in
`search.py`. The platform's existing rate-limit infrastructure (`app/services/rate_limit.py`)
has a `_bucket_limit` helper and several named `rate_limit_*` functions that could trivially
be extended to cover search.

- **Severity**: HIGH (availability / resource exhaustion)
- **Source ticket**: SOCIAL-003 (second-pass as-built review)
- **Status**: Open
- **Owning area**: Global Search / Platform Security
- **Related tickets**: SOCIAL-003 (parent — also flags missing `GLOBAL_SEARCH_ENABLED` flag
  and missing blocked-user filter; those are separate sub-gaps), PLATFORM-011 (Unified Global
  Search, which documents overlapping backend gaps)
- **Dependencies**: None. The rate-limit infrastructure already exists.

## 2. Current-State Investigation (root cause)

### 2.1 The unprotected endpoint

`app/routers/search.py:797`:

```python
@router.get("")
def global_search(
    q: str = Query(..., min_length=1, max_length=500),
    types: str = Query(default=",".join(sorted(ALLOWED_TYPES))),
    limit: int = Query(default=5, ge=1, le=20),
    session=Depends(require_ui_session),
):
    user_id = session["user_sub"]
    q = _sanitize_query(q)
    if not q:
        raise HTTPException(status_code=400, detail="Query is empty")

    requested_types = [t.strip() for t in types.split(",") if t.strip()]
    invalid = set(requested_types) - ALLOWED_TYPES
    if invalid:
        raise HTTPException(status_code=400, detail=f"Invalid search types: {', '.join(invalid)}")

    result = _search_aggregator(q, user_id, requested_types, limit)
    return {"query": q, **result}
```

The handler requires a valid UI session (enforced by `Depends(require_ui_session)`), but
imposes no per-user or global request cap. There is no `rate_limit_*` call before or after
`_search_aggregator`.

### 2.2 The amplification surface

`_search_aggregator` (`search.py:618`) dispatches up to 9 concurrent search functions
using `ThreadPoolExecutor(max_workers=min(len(search_fns), 8))`. With `types` set to all
9 allowed types, each invocation launches 8 parallel threads. Each thread may:

- Perform a DynamoDB `Scan` (e.g. `_search_videos`, `_search_contacts`, `_search_catalog`)
- Perform a DynamoDB `Query` with a `FilterExpression` (e.g. `_search_posts`, `_search_messages`)
- Fan out to external services (Discovery service, tickets)

Worst-case read amplification per request: 8–9 DDB operations × unlimited request rate.
DynamoDB Local in dev is not subject to RCU throttling, but in prod this maps directly to
`read_capacity_units` consumption on provisioned tables or `OnDemand` billing.

### 2.3 The existing rate-limit infrastructure

`app/services/rate_limit.py:60` provides `_bucket_limit(user_sub, sid, max_n, win)`:

```python
def _bucket_limit(user_sub: str, sid: str, max_n: int, win: int) -> bool:
    if not _sessions_table_enabled():
        return True   # dev mode without sessions table: no limiting
    now = now_ts()
    it = T.sessions.get_item(Key={"user_sub": user_sub, "session_id": sid}).get("Item") or {}
    start = int(it.get("bucket_start", 0))
    count = int(it.get("bucket_count", 0))
    if start == 0 or (now - start) >= win:
        start = now; count = 0
    if count >= max_n:
        return False
    try:
        T.sessions.put_item(Item=with_ttl({
            "user_sub": user_sub, "session_id": sid,
            "bucket_start": start, "bucket_count": count + 1,
        }, ttl_epoch=now + win + 3600))
    except Exception:
        pass
    return True
```

Several named wrappers already use this: `rate_limit_feed_query` (rate_limit.py:227),
`rate_limit_login_attempt` (163), `rate_limit_admin_action` (170), etc. A new
`rate_limit_global_search` wrapper following the same pattern is straightforward.

### 2.4 The GAP ticket's suggested call — evaluation

The ticket suggests `check_rate_limit(user_id, "global_search", max=30, window=60)`.
There is no function named `check_rate_limit` in the codebase — the correct internal
function is `_bucket_limit` (private) or a new public named wrapper following the
`rate_limit_feed_query` pattern. The fix below uses the existing infrastructure correctly.

### 2.5 Dev mode behavior

`_bucket_limit` short-circuits with `return True` when
`not _sessions_table_enabled()` (i.e., when `S.ddb_sessions_table` is empty). In the local
dev stack `DDB_SESSIONS_TABLE` is always set (sessions are used for auth), so the rate
limiter is active in dev. This is correct: dev-mode behavior matches prod, satisfying
SECOPS-007.

## 3. Impact / Exploit / Blast Radius

### 3.1 Attack scenario

An authenticated user (requires a valid session, so this is a post-auth abuse vector)
executes the following in a tight loop:

```
GET /ui/search?q=a&types=users,posts,catalog,files,messages,tickets,contacts,videos,calendar&limit=20
```

Each request: 8 concurrent DDB operations, each scanning up to 200 items with filters.
At 10 requests/second: 80 concurrent DDB reads/second sustained. At 100 requests/second:
800 DDB reads/second — enough to exhaust a typical provisioned table's RCU allocation and
starve other application reads.

**CPU amplification**: Each request occupies 8 threads from a `ThreadPoolExecutor` for up to
5 seconds (the `as_completed` timeout). Under burst conditions this creates thread pool
saturation on the single-worker uvicorn process.

### 3.2 Blast radius

- **DynamoDB tables at risk**: `app_single_table` (posts, messages, tickets, contacts,
  calendar), `video_metadata`, and any table used by the Discovery service.
- **Other users impacted**: DDB throttling affects all users reading/writing those tables,
  not just the attacker. A coordinated burst from 5–10 accounts could cause platform-wide
  slowdowns.
- **Financial**: OnDemand DDB billing is per-RCU. An unthrottled search loop can generate
  unexpected billing spikes in production.
- **No data exfiltration risk**: search results are scoped to the requesting user's
  visibility permissions. This is a DoS/resource-exhaustion vector, not a data leak.

## 4. Fix Design (code-level)

### 4.1 Add `rate_limit_global_search` to `app/services/rate_limit.py`

Following the `rate_limit_feed_query` pattern exactly:

```python
def rate_limit_global_search(user_sub: str) -> None:
    """Enforce per-user rate limit on the global search aggregator.

    Default: 30 requests per 60-second window.  Configurable via settings:
      GLOBAL_SEARCH_RATE_MAX       (default 30)
      GLOBAL_SEARCH_RATE_WINDOW_S  (default 60)
    """
    cap = max(1, int(getattr(S, "global_search_rate_max", 30) or 30))
    window = max(1, int(getattr(S, "global_search_rate_window_seconds", 60) or 60))
    sid = "rl#global_search"
    if not _bucket_limit(user_sub, sid, cap, window):
        raise HTTPException(
            status_code=429,
            detail={
                "code": "search_rate_limited",
                "message": "Too many search requests; try again later",
                "limit": cap,
                "window_seconds": window,
            },
            headers={"Retry-After": str(window)},
        )
```

### 4.2 Add two new settings to `app/core/settings.py`

```python
global_search_rate_max: int = int(os.environ.get("GLOBAL_SEARCH_RATE_MAX", "30"))
global_search_rate_window_seconds: int = int(
    os.environ.get("GLOBAL_SEARCH_RATE_WINDOW_S", "60")
)
```

This makes the limit configurable via environment variables without a code deploy,
satisfying the SECOPS-007 requirement for tunable limits.

### 4.3 Call the rate limiter in `global_search`

In `app/routers/search.py:797`, add the call as the **first** line after extracting
`user_id`, before any DDB access:

```python
from app.services.rate_limit import rate_limit_global_search

@router.get("")
def global_search(
    q: str = Query(..., min_length=1, max_length=500),
    types: str = Query(default=",".join(sorted(ALLOWED_TYPES))),
    limit: int = Query(default=5, ge=1, le=20),
    session=Depends(require_ui_session),
):
    user_id = session["user_sub"]

    # GAP-0359: rate limit per user
    rate_limit_global_search(user_id)

    q = _sanitize_query(q)
    if not q:
        raise HTTPException(status_code=400, detail="Query is empty")
    ...
```

Placing the call before `_sanitize_query` ensures the rate limit fires even for empty or
malformed queries, avoiding a bypass via a 400-path that doesn't consume quota.

### 4.4 Add `Retry-After` to 429 response

The `Retry-After` header is already included in the `HTTPException` raised by
`rate_limit_global_search`. The frontend search implementation should respect this header
to implement exponential back-off in the search input debounce.

### 4.5 Dev/Prod parity (SECOPS-007)

- In dev: `T.sessions` is DynamoDB Local. `rate_limit_global_search` uses the same
  `_bucket_limit` call path as all other rate limiters, which are also active in dev.
  No mock fork. Dev and prod execute identical code.
- The two new `Settings` fields default to `30` / `60` if no env var is set. They can be
  overridden per environment in `.env.local` or the production secrets manager.
- `_sessions_table_enabled()` returns `False` only when `S.ddb_sessions_table == ""`.
  This is never the case in the standard dev stack or prod.

### 4.6 Alternatives considered

- **IP-based rate limiting via middleware**: More robust (covers unauthenticated probes)
  but requires extracting the client IP from the ASGI request. Adds middleware complexity
  and is not consistent with the existing user-sub-keyed pattern. Can be added later as
  a complementary layer.
- **Redis-backed counter**: More accurate under high concurrency (no race window in the
  DDB `put_item` approach). The existing `_bucket_limit` has a known race — two concurrent
  requests can both read `count < max_n` and both increment. For a 30-per-minute limit
  this race creates a small overrun headroom (~2 extra requests in burst), which is
  acceptable for this use case.
- **Limit at API gateway / CDN layer**: Correct for production hardening but out of scope
  for this fix (and doesn't protect DDB from internal calls or direct backend access).

## 5. Testing, Verification & Rollout

### 5.1 Pytest regression test (offline, fails before / passes after)

File: `tests/test_search_rate_limit.py`

```python
import pytest
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def _headers(uid="user_alice"):
    return {"X-User-Id": uid}

def test_search_rate_limit_enforced(monkeypatch):
    """
    GAP-0359: global_search must return 429 after exceeding the per-user cap.

    Before fix: all requests return 200.
    After fix: the (N+1)th request within the window returns 429.
    """
    from app.core.settings import S
    # Set a tiny limit for the test
    monkeypatch.setattr(S, "global_search_rate_max", 3)
    monkeypatch.setattr(S, "global_search_rate_window_seconds", 60)

    for i in range(3):
        resp = client.get("/ui/search", params={"q": f"test{i}"}, headers=_headers())
        assert resp.status_code == 200, f"Request {i} should succeed"

    # The 4th request should be rate-limited
    resp = client.get("/ui/search", params={"q": "overload"}, headers=_headers())
    assert resp.status_code == 429  # FAILS before fix
    body = resp.json()
    assert body["detail"]["code"] == "search_rate_limited"
    assert "Retry-After" in resp.headers

def test_search_rate_limit_per_user_isolated(monkeypatch):
    """GAP-0359: rate limit bucket is per-user; different users have independent buckets."""
    from app.core.settings import S
    monkeypatch.setattr(S, "global_search_rate_max", 1)
    monkeypatch.setattr(S, "global_search_rate_window_seconds", 60)

    # Alice exhausts her quota
    client.get("/ui/search", params={"q": "hi"}, headers=_headers("user_alice"))
    resp = client.get("/ui/search", params={"q": "hi"}, headers=_headers("user_alice"))
    assert resp.status_code == 429

    # Bob's quota is unaffected
    resp = client.get("/ui/search", params={"q": "hi"}, headers=_headers("user_bob"))
    assert resp.status_code == 200  # Bob still succeeds

def test_search_no_rate_limit_without_sessions_table(monkeypatch):
    """GAP-0359: when sessions table is empty (no-auth mode), rate limit is skipped."""
    from app.core.settings import S
    monkeypatch.setattr(S, "ddb_sessions_table", "")
    # Should succeed indefinitely
    for _ in range(5):
        resp = client.get("/ui/search", params={"q": "hi"}, headers=_headers())
        assert resp.status_code in (200, 400)  # 400 = no results, not 429
```

### 5.4 Metrics / observability

Log each rate-limit hit at `INFO` level for monitoring:

```python

logger.info("global_search rate limit hit for user %s", user_sub)
```

If Prometheus metrics are wired, increment a counter:
`search_rate_limited_total{user_id=...}`.

### 5.5 Frontend debounce alignment

The current frontend search implementation should debounce input to at most 1 request
per ~200 ms (5 requests/second), which is well within the 30/60s default limit for normal
usage. No frontend change is required for correctness, but adding `Retry-After` header
handling to the search API client (`api/endpoints/search.ts` or `api/client.ts`) would
allow graceful degradation when a user triggers a burst.

### 5.6 Rollout, risks, effort

- **Effort**: S (< 2 hours: 20 lines of code + tests)
- **Risk**: LOW. The rate limiter uses the same proven `_bucket_limit` mechanism as
  6+ other rate-limit functions. The default limit (30/min) is generous enough that
  normal interactive search usage will never hit it.
- **Backward compat**: Transparent to users under the default limit. Users exceeding the
  limit receive a clear `429` with a `Retry-After` header.
- **Rollback**: Remove the `rate_limit_global_search(user_id)` call and the two Settings
  fields. No DDB schema change.
- **Sequencing**: Independent of all other open GAP tickets. Can be merged as a standalone
  security hardening change in the same sprint.

### 5.7 Future hardening

- Add a global IP-level rate limit at the load balancer / reverse proxy (complements the
  per-user limit for pre-auth probing).
- Consider adding the `GLOBAL_SEARCH_ENABLED` feature flag (SOCIAL-003 sub-gap) in the
  same PR to enable emergency killswitch for search without a rollback deploy.
- Add filtered-user blocking to `_search_users` (SOCIAL-003 sub-gap 3) as a follow-on PR.
