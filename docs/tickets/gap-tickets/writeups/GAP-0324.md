# GAP-0324: `send_alert_email()` Still Uses Silent Bare Except — Remediation Write-up

> **Claim status**: CONFIRMED — `app/services/alerts.py:478` contains an unlogged
> `except Exception: pass` that silently swallows all SES errors.

---

## 1. Summary & Classification

**Source ticket**: PLATFORM-006 (alert email delivery hardening)
**Severity as filed**: HIGH
**Status**: Open
**Owning area**: Alert delivery / email subsystem

`send_alert_email()` in `app/services/alerts.py` sends security-critical alert emails (new device login, MFA changes, API-key events) via AWS SES. Its entire exception handler is `except Exception: pass` (line 478). Any SES error — domain verification failure, quota exhaustion, invalid recipient, IAM credential expiry, network timeout — is silently discarded. The function always returns `None` whether the email was delivered or not. No log entry is produced, no metric is incremented, no delivery-failure record is written to the `email_delivery` DynamoDB table, and no caller can distinguish success from failure.

The `email_delivery` service (`app/services/email_delivery.py`) already provides a `record_email_failure()` function (line 54) designed specifically for this purpose. It is never called from `send_alert_email()`.

**Verdict**: Confirmed. Line 478 matches the claim exactly. Related gap GAP-0325 describes a second, outer `except Exception: pass` at line 792 that wraps the entire email fanout section — both must be fixed together.

**Related tickets**: GAP-0325 (outer silent-except around the email fanout); SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (root cause)

### 2.1 Exact code path

`app/services/alerts.py:458-479`:

```python
def send_alert_email(to_emails: List[str], subject: str, body_text: str) -> None:
    if not to_emails:
        return
    if S.dev_mode:
        # … writes to dev log file, returns early …
        return
    if not S.alerts_email_enabled or not S.alerts_from_email:
        return
    try:
        import boto3
        ses = boto3.client("ses")
        ses.send_email(
            Source=S.alerts_from_email,
            Destination={"ToAddresses": to_emails},
            Message={
                "Subject": {"Data": subject[:120]},
                "Body": {"Text": {"Data": body_text[:8000]}},
            },
        )
    except Exception:        # ← line 478: SILENT CATCH
        pass
```

The `boto3.client("ses").send_email()` call raises a `botocore.exceptions.ClientError` for every SES-side failure. The bare `except Exception: pass` at line 478 discards all such exceptions without producing any observable side effect.

### 2.2 Failure modes silently swallowed

| SES error code | Condition | Consequence |
|---|---|---|
| `MessageRejected` | From address not verified | User never notified of new-device login |
| `MailFromDomainNotVerified` | Domain misconfiguration at deployment | All security alert emails lost |
| `SendingPausedException` | Account in sandbox or reputation alert | Emails stop silently across entire platform |
| `DailyMessageQuotaExceeded` | SES quota hit | All emails drop for rest of the day |
| `NoCredentialsError` | IAM role misconfiguration in production | All SES calls fail silently from startup |
| Network timeout | Intermittent AWS connectivity | Retries never attempted |

### 2.3 `record_email_failure()` is ready but unused

`app/services/email_delivery.py:54-72`:

```python
def record_email_failure(to_emails: List[str], subject: str, error: str) -> None:
    """Record a failed email send attempt."""
    ts = now_ts()
    for addr in to_emails:
        T.email_delivery.put_item(Item={
            "pk": f"EMAIL#{addr}",
            "sk": f"FAILED#{ts}",
            "to_email": addr,
            "subject": subject[:120],
            "error": error[:500],
            "status": "failed",
            "created_at": ts,
            "ttl_epoch": ts + 90 * 86400,
        })
```

This function already exists and is called by other email paths (e.g. `app/services/invoices.py:475`). It simply needs to be called from `send_alert_email()` on failure.

### 2.4 Dev mode is not affected

The dev-mode path (lines 461-467) writes to a local log file and returns before the SES call. The silent-except only applies in production mode (`S.dev_mode = False`). This creates a dev/prod parity gap: failures are detectable in dev (file is written) but invisible in production (silently discarded).

### 2.5 Return type and caller contract

The function signature is `-> None`. Callers at lines 753, 765, and 791 call it without capturing a return value — they fire-and-forget. Converting the bare except to a logged exception does not require a return-type change and does not alter the caller contract. If callers ever need to distinguish success from failure (e.g., to retry or show a system warning), the return type should become `Optional[str]` (returning `None` on failure, the SES `MessageId` on success), but that refactor is a separate concern and should not be bundled into this minimal fix.

### 2.6 Why `record_email_failure()` was never wired

The `app/services/email_delivery.py` module was introduced for the invoice and transactional email subsystems (see `app/services/invoices.py:475` for a working call-site). The alert email path (`send_alert_email`) predates it or was written without awareness of it. The function exists and is correct — it simply was never called from the alert path. This is a straightforward integration omission rather than a design gap.

## 3. Impact / Exploit / Blast Radius

**Security impact** (HIGH):

The emails silenced by this bug are primarily security-critical notifications:

- **New device login** (`device_new` alert type): user is not notified that an unrecognised device has logged in. An attacker who has obtained credentials gains a window of silence in which to operate.
- **MFA device added/removed** (`totp_device_confirm`, `totp_device_remove`): account takeover operations are not emailed to the victim.
- **API key created/revoked** (`api_key_created`, `api_key_revoked`): credential management events go unreported.
- **Session revocation events**: user may not be informed their sessions were force-revoked.

In a misconfigured SES environment (wrong `ALERTS_FROM_EMAIL`, unverified domain, sandbox mode) the entire security-alert email pipeline fails from first deployment and no operator is ever aware.

**Observability impact**: Prometheus metrics and DynamoDB `email_delivery` records for the alert email channel are absent, making it impossible to measure delivery rate, detect quota exhaustion, or alert on delivery degradation.

**Financial / availability impact**: Low direct impact, but indirect: undelivered device-login emails may delay users from detecting account compromise, leading to increased support burden and potential platform liability.

## 4. Fix Design (code-level)

### 4.1 Minimal fix — log + record failure

Replace the silent bare except with a version that:
1. Calls `logger.exception()` to emit a log record with full stack trace.
2. Calls `record_email_failure()` to persist the failure in the `email_delivery` DDB table.
3. Increments a `record_auth_event("alert_email_send_failed")` counter via the metrics module so Prometheus can alert.

```python
# app/services/alerts.py — replace lines 470-479

    try:
        import boto3
        ses = boto3.client("ses")
        response = ses.send_email(
            Source=S.alerts_from_email,
            Destination={"ToAddresses": to_emails},
            Message={
                "Subject": {"Data": subject[:120]},
                "Body": {"Text": {"Data": body_text[:8000]}},
            },
        )
        message_id = response.get("MessageId", "")
        # Record successful send for delivery tracking.
        try:
            from app.services.email_delivery import record_email_sent
            record_email_sent(to_emails, subject, message_id)
        except Exception:
            pass  # Delivery tracking must never block the happy path.
    except Exception as exc:
        logger.exception(
            "send_alert_email: SES send failed for %d recipients; subject=%r: %s",
            len(to_emails),
            subject[:60],
            exc,
        )
        try:
            from app.services.email_delivery import record_email_failure
            record_email_failure(to_emails, subject, str(exc)[:500])
        except Exception:
            pass  # DDB write failure must not mask the original error.
        record_auth_event("alert_email_send_failed")
```

The inner `try/except: pass` guards for DDB write failures in the error recording path to prevent an exception in the reporting path from hiding the original SES error in logs.

### 4.2 Dev/Prod parity (SECOPS-007)

In dev mode (`S.dev_mode = True`) the function returns at line 467 before reaching the SES block. After the fix:

- Dev: unchanged — file log write, returns early, no SES call.
- Production: SES call; on failure logs + DDB record + metric counter.

No mock path bypasses the fix. The `record_email_failure()` call uses `T.email_delivery` which is mocked by moto in test mode. Tests can assert failure records without a real SES endpoint.

### 4.3 Metrics module change

Add to `app/metrics.py` in `record_auth_event()`:

```python
elif alert_type == "alert_email_send_failed":
    ALERT_EMAIL_FAILURES.inc()
```

And declare the counter at module level:

```python
ALERT_EMAIL_FAILURES = _counter("alert_email_send_failed_total",
                                "Number of alert email SES send failures")
```

### 4.4 Optional: retry with exponential back-off

Transient failures (network timeout, throttling) would benefit from a retry wrapper. However, for security-alert emails the latency requirements are strict (the user expects near-real-time notification). A single synchronous retry with a short back-off is acceptable; a full async retry queue is out of scope for this ticket. If desired, wrap the `ses.send_email()` call with `tenacity.retry`:

```python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type
from botocore.exceptions import ClientError

@retry(
    stop=stop_after_attempt(2),
    wait=wait_exponential(multiplier=0.5, max=2),
    retry=retry_if_exception_type(ClientError),
    reraise=True,
)
def _ses_send(ses, **kwargs):
    return ses.send_email(**kwargs)
```

This is optional and should not block the minimal fix.

## 5. Testing, Verification & Rollout

### 5.1 Regression test — fails before / passes after

```python
# tests/test_send_alert_email.py
import pytest
from unittest.mock import patch, MagicMock
from botocore.exceptions import ClientError

from app.services.alerts import send_alert_email


def _ses_error(code: str = "MessageRejected") -> ClientError:

        {"Error": {"Code": code, "Message": "Test error"}},
        "SendEmail",
    )


def test_ses_failure_is_logged_not_swallowed(caplog, monkeypatch):
    """FAILS before fix (no log emitted); PASSES after (logger.exception called)."""

    monkeypatch.setattr("app.core.settings.S.alerts_email_enabled", True)

    mock_ses.send_email.side_effect = _ses_error("MessageRejected")

        with caplog.at_level("ERROR"):
            send_alert_email(["alice@example.com"], "Security Alert", "body text")

    # After fix: error must appear in log.
    assert any("SES send failed" in r.message for r in caplog.records), \
        "Expected error log record; silent failure still present"


def test_ses_failure_records_email_failure_in_ddb(monkeypatch, ddb_mock):
    """FAILS before fix (no DDB record); PASSES after."""
    monkeypatch.setattr("app.core.settings.S.dev_mode", False)
    monkeypatch.setattr("app.core.settings.S.alerts_email_enabled", True)
```

### 5.2 Manual QA steps

1. In a staging environment, set `ALERTS_FROM_EMAIL` to an unverified address (force SES `MessageRejected`).
2. Trigger a security alert: log in from a new device or revoke an API key.
3. Before fix: `grep "send_alert_email" .logs/uvicorn.log` → no lines.
4. After fix: `grep "SES send failed" .logs/uvicorn.log` → error line with recipient count and exception.
5. Query DynamoDB: `aws dynamodb query --table-name email_delivery --key-condition "pk = :pk"` → `FAILED#` record present.

### 5.3 Metrics / observability

- New Prometheus counter `alert_email_send_failed_total` — alert if rate > 0 for 5 minutes.
- Existing Grafana panel for email delivery rate: add `alert_email_send_failed_total` as a negative series.
- DynamoDB `email_delivery` table `FAILED#` records are already queryable via the admin email-delivery audit endpoint.

### 5.4 Rollout, risks, and effort

- **Effort**: S (approximately 30 lines of code change + 40 lines of test — the entire change fits in a single-function edit to `send_alert_email()`).
- **Risk**: Negligible. Adding logging and DDB writes on the exception path cannot affect the happy path. The inner guard `try/except: pass` around `record_email_failure()` ensures DDB write failures do not introduce new uncaught exceptions. The inner guard `try/except: pass` around `record_email_sent()` similarly protects the success path from DDB latency issues.
- **Rollback**: Revert the single function edit. The `ALERT_EMAIL_FAILURES` counter can be left in place if the metrics declaration does not break anything when unused.
- **Sequencing**: Fix this ticket (GAP-0324) together with GAP-0325 in the same PR. The outer silent-except in GAP-0325 is the first line of defence; this fix is the second. Both must be present for full observability. Deploy to staging first; verify the new log lines appear by intentionally misconfiguring `ALERTS_FROM_EMAIL` in a test run.

### 5.5 Notes on `record_email_sent()` addition

The fix in §4.1 also adds a call to `record_email_sent()` on the success path. This is a separate improvement not required by the gap ticket but logical to include: the `email_delivery` table currently has `FAILED#` records (from other delivery paths) but no `SENT#` records from alert emails, making delivery rate calculations unreliable. Adding the success record gives operators a complete picture of alert email delivery health through the admin email-delivery audit endpoint.

### 5.6 Interaction with the HTML template path

The `send_alert_email()` function is called from three locations in the email fanout block:
- Line 753: after `render_ticket_email_template()` succeeds (plaintext or ticket-style template).
- Line 765: after `render_alert_email_template()` succeeds (NOTIFY-001 HTML template).
- Line 791: fallback plaintext builder.

All three call sites pass `(to_emails, subject, body_text)`. The fix applies uniformly to all three paths because they all funnel through the single `send_alert_email()` function. No per-call-site changes are needed.
