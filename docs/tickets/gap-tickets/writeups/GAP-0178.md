# GAP-0178: Background Async Export Worker Not Implemented — Remediation Write-up

> Source ticket: ENTERPRISE-004 · Severity: HIGH · Effort: L · Status: Open

## 1. Summary & Classification

**Bug statement.** The audit log export system (`POST /ui/admin/audit-exports`) processes
export jobs synchronously in dev mode only, capped at 500 events and stored inline in a
DynamoDB item. When `S.dev_mode` is `False` (i.e., in every production-like deployment),
`create_export_job` writes a `status: "pending"` record to DynamoDB and returns immediately —
**no background worker ever picks it up**. The job remains `pending` indefinitely. Root
administrators requesting audit exports in production receive a `202`-style response but the
download link is never generated and the export never completes.

**Verdict:** Confirmed. `app/services/audit_export_pipeline.py:111–117` branches on `S.dev_mode`
and calls `_process_export_inline` only in that branch. No `audit_export_worker.py` file exists
under `app/services/`. Settings `audit_export_worker_enabled`, `audit_export_worker_poll_interval_seconds`,
and `audit_export_worker_max_concurrent` are declared in `app/core/settings.py:1924–1926` but
reference a worker that does not exist. No startup hook in `app/main.py` registers an audit
export background task.

**Severity and area.** HIGH / Enterprise Compliance & Audit (ENTERPRISE-004). The export
feature is root-only and part of the compliance toolkit. In production, audit exports are the
primary mechanism for root administrators to fulfill eDiscovery, GDPR data subject access, and
SOC 2 audit trail requests. A permanently-pending export is a silent compliance failure.

**Related tickets.** ENTERPRISE-004 (audit export feature), GAP-0179 (companion gap: S3 upload
path is also dead inside the pipeline). These two gaps are tightly coupled and should be fixed
together in the same PR.

## 2. Current-State Investigation (root cause)

### The dev-only code path: `create_export_job` at `audit_export_pipeline.py:74–117`

```python
def create_export_job(...) -> dict[str, Any]:
    """Create an export job record in DynamoDB and immediately process it (dev mode)."""
    ...
    T.audit_exports.put_item(Item=item)          # writes status="pending"

    # In dev mode, process the export synchronously and store content inline
    if S.dev_mode:
        _process_export_inline(export_id, item)
        resp = T.audit_exports.get_item(Key={"export_id": export_id, "sk": "META"})
        return resp.get("Item", item)

    return item                                  # ← production: returns pending, nothing happens
```

The function's own docstring says "and immediately process it (dev mode)" — the comment is
accurate. Production falls through to `return item` with `status="pending"`.

### The missing worker: settings without implementation

`app/core/settings.py:1924–1926` declares:

```python
audit_export_worker_enabled: bool = ...
audit_export_worker_poll_interval_seconds: int = ...
audit_export_worker_max_concurrent: int = ...
```

These three settings presuppose the existence of `app/services/audit_export_worker.py` and a
`run_audit_export_worker_loop()` coroutine. Neither exists. Running `ls app/services/ | grep
audit_export` returns only `audit_export.py`, `audit_export_pipeline.py`, and
`audit_adapters.py`.

### Startup hook gap in `app/main.py`

`app/main.py:521–527` registers a set of background tasks at startup:

```python
app.add_event_handler("startup", start_billing_dunning_task)
app.add_event_handler("startup", start_filemgr_purge_task)
app.add_event_handler("startup", start_scheduled_messages_task)
...
```

No `start_audit_export_worker_task` call appears anywhere in `main.py`. A grep of the full
`app/` tree for `audit_export_worker` returns only the three settings declarations — confirming
no code path exists that would start the worker.

### Dev vs prod impact

In dev (`S.dev_mode=True`): jobs are processed synchronously, inline, with a hard cap of 500
events. This is sufficient for development and most QA scenarios, but the 500-event cap means
even dev exports silently truncate for large date ranges.

In production (`S.dev_mode=False`): `POST /ui/admin/audit-exports` returns HTTP 201 with the
pending job record. The frontend polls `GET /ui/admin/audit-exports/{export_id}` waiting for
`status` to change from `"pending"` to `"completed"`. It never changes. After a browser timeout
(or user frustration), the export is abandoned. DynamoDB accumulates orphaned `pending` items.

## 3. Impact / Exploit / Blast Radius

**Compliance failure.** Root administrators cannot produce audit exports in any non-dev
deployment. GDPR Article 30 (Records of Processing) and SOC 2 CC7.2 (Incident Detection)
both require the ability to export audit logs on demand. A broken export silently fails
compliance obligations.

**eDiscovery and legal hold.** If a legal hold or investigation requires audit log extraction,
the only mechanism is broken. Engineering would need to perform a manual DynamoDB export — a
time-consuming, error-prone process.

**No direct security exploit.** The broken worker does not expose data or create an injection
surface. The risk is entirely compliance, availability, and trust.

**Blast radius.** All `POST /ui/admin/audit-exports` calls from root administrators in
production. All downstream tooling that polls `GET /ui/admin/audit-exports/{id}` for
completion. No end-user data is affected.

**Secondary impact.** The `audit_export_worker_*` settings exist but do nothing, creating
confusion for operators who enable or tune them expecting an effect.

## 4. Fix Design (code-level)

### Create `app/services/audit_export_worker.py`

```python
"""Background worker that processes pending audit export jobs (ENTERPRISE-004)."""
from __future__ import annotations

import asyncio
import logging
import time as _time
from typing import Any

from boto3.dynamodb.conditions import Attr

from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts
from app.services.audit_export_pipeline import process_export_job
from app.services.job_registry import register_task, report_error, report_poll

logger = logging.getLogger(__name__)

POLL_INTERVAL_SECONDS = 10
MAX_BATCH_SIZE = 10  # match S.audit_export_worker_max_concurrent default


async def run_audit_export_worker_loop() -> None:
    """Poll for pending export jobs and process them."""
    poll_interval = S.audit_export_worker_poll_interval_seconds or POLL_INTERVAL_SECONDS
    register_task(
        "audit_export_worker",
        poll_interval,
        enabled=True,
        description="Processes pending audit log export jobs and uploads results to S3",
    )

    while True:
        _poll_start = _time.perf_counter()
        _processed = 0
        _failed = 0
        try:
            due = _query_pending_jobs(limit=S.audit_export_worker_max_concurrent)
            for job in due:
                export_id = job["export_id"]
                try:
                    # Mark as processing to prevent duplicate pickup
                    _claim_job(export_id)
                    process_export_job(export_id, job)
                    _processed += 1
                except Exception:
                    _failed += 1
                    logger.exception("audit_export_worker: failed to process job %s", export_id)
                    _mark_failed(export_id, "worker exception")

            _duration_ms = (_time.perf_counter() - _poll_start) * 1000
            report_poll("audit_export_worker", items_processed=_processed,
                        items_failed=_failed, duration_ms=_duration_ms)
        except Exception as exc:
            report_error("audit_export_worker", str(exc))
            logger.exception("audit_export_worker: poll loop error")

        await asyncio.sleep(poll_interval)


def _query_pending_jobs(limit: int) -> list[dict[str, Any]]:
    resp = T.audit_exports.scan(
        FilterExpression=Attr("status").eq("pending"),
        Limit=limit * 10,  # over-fetch to account for DDB filter post-read
    )
    items = resp.get("Items", [])
    pending = [i for i in items if i.get("status") == "pending"]
    return pending[:limit]


def _claim_job(export_id: str) -> None:
    T.audit_exports.update_item(
        Key={"export_id": export_id, "sk": "META"},
        UpdateExpression="SET #st = :st, started_at = :now",
        ConditionExpression=Attr("status").eq("pending"),
        ExpressionAttributeNames={"#st": "status"},
        ExpressionAttributeValues={":st": "processing", ":now": now_ts()},
    )


def _mark_failed(export_id: str, reason: str) -> None:
    T.audit_exports.update_item(
        Key={"export_id": export_id, "sk": "META"},
        UpdateExpression="SET #st = :st, error_message = :em",
        ExpressionAttributeNames={"#st": "status"},
        ExpressionAttributeValues={":st": "failed", ":em": reason[:500]},
    )


async def start_audit_export_worker_task() -> None:
    """Start the audit export worker if enabled."""
    if S.audit_export_worker_enabled:
        asyncio.create_task(run_audit_export_worker_loop())
    else:
        register_task(
            "audit_export_worker",
            POLL_INTERVAL_SECONDS,
            enabled=False,
            description="Processes pending audit log export jobs",
        )
```

### Add `process_export_job` to `audit_export_pipeline.py`

GAP-0179 covers the S3 upload stub in detail; the function signature needed by the worker is:

```python
# app/services/audit_export_pipeline.py  (new public function)
def process_export_job(export_id: str, job: dict[str, Any]) -> None:
    """Process an export job: generate content and upload to S3 (or inline in dev)."""
    if S.dev_mode:
        _process_export_inline(export_id, job)
    else:
        _process_export_s3(export_id, job)   # see GAP-0179 for full implementation
```

### Register the worker in `app/main.py`

```python
# app/main.py  (after the existing webhook_dispatcher startup registration, ~line 805)
from app.services.audit_export_worker import start_audit_export_worker_task
...
app.add_event_handler("startup", start_audit_export_worker_task)
```

### Dev/prod parity (SECOPS-007)

The worker itself runs in both dev and production but forks on `S.dev_mode` inside
`process_export_job`: dev uses `_process_export_inline` (inline DDB storage, capped at 500
events); production calls `_process_export_s3` (full S3 upload, see GAP-0179). The worker
loop, polling logic, job claiming, and failure handling are identical in both environments.
`AUDIT_EXPORT_WORKER_ENABLED=0` can disable the worker in either environment without code
changes.

### Avoiding duplicate processing

The `_claim_job` function uses a `ConditionExpression=Attr("status").eq("pending")` to perform
a compare-and-swap before processing. If two worker instances (e.g., during a rolling deploy)
race on the same job, only one will successfully transition to `"processing"` — the other
receives `ConditionalCheckFailedException` which should be caught and treated as a skip.

```python
from botocore.exceptions import ClientError

def _claim_job(export_id: str) -> None:
    try:
        T.audit_exports.update_item(...)
    except ClientError as e:
        if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
            raise RuntimeError(f"Job {export_id} already claimed by another worker")
        raise
```

**Alternatives considered:**

- **SQS-based worker**: more reliable at scale but requires adding SQS to the infrastructure.
  The existing pattern (webhook_dispatcher, scheduled_messages, etc.) all use polling loops
  against DynamoDB; consistency with that pattern is preferred for now.
- **Process inline always (no worker)**: breaks for large exports (>500 events, >400 KB DDB
  limit) and blocks the HTTP request thread. Rejected.
