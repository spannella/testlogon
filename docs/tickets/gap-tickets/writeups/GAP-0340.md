# GAP-0340: S3 Files Not Deleted During Account Deletion — Remediation Write-up

> Source ticket: PRIVACY-001 · Severity: HIGH · Effort: M · Status: Open

## 1. Summary & Classification

**Bug statement.** When a user's account is deleted via `process_deletion()` in `app/services/gdpr_service.py`, none of the files the user uploaded to the file manager are deleted from S3. The `filemgr` DynamoDB table records for those files are also not deleted. After a "successful" account deletion, the user's uploaded files persist indefinitely in the `filemgr_bucket` S3 bucket, and the file-manager DDB records remain queryable. This violates GDPR Article 17 and creates ongoing storage cost for data belonging to deleted accounts.

**Claim verdict: Confirmed.** Reading `process_deletion()` at lines 672–827 of `app/services/gdpr_service.py` confirms that none of the ten deletion steps access `S.filemgr_table_name` or `S.filemgr_bucket`. The only S3 client instantiations in the file are in `process_export()` (lines 572–587, for uploading the export ZIP) and `get_export_download_url()` (lines 652–657, for presigned URL generation). There are no `delete_object`, `delete_objects`, or `delete_object_tagging` calls anywhere in `process_deletion()`. The file-manager DDB table (`S.filemgr_table_name`) is accessed in `process_export()` at line 538–546 (for generating the export manifest) but not during deletion.

**Severity and area.** HIGH / Privacy & GDPR Compliance. Files uploaded by users are personal data. They range from profile pictures and documents to private direct-message attachments. Retaining these files after account deletion violates GDPR Article 17 and also violates the platform's own stated deletion policy.

**Related tickets.** PRIVACY-001 (parent), GAP-0338 (synchronous export — deletion background model), GAP-0339 (messages not deleted — companion deletion gap), companion PRIVACY-001 gap "Newsfeed posts and comments not deleted". This gap is independent of GAP-0339 and can be implemented in parallel.

## 2. Current-State Investigation (root cause)

### Confirmed absence of S3 deletion

A complete audit of `process_deletion()` (lines 672–827):

```python
# app/services/gdpr_service.py:672–827 — annotated scan
def process_deletion(user_sub: str, request_id: str) -> Dict[str, Any]:
    # Steps 1–10 (billing, core tables, profile, addresses, contacts,
    # calendar, subscriptions, account_state, tickets, video_metadata)
    # ... (see GAP-0339 for full step list)

    # Finalize
    T.data_requests.update_item(...)   # line 802
    _write_audit(...)                  # line 813
    write_alert(...)                   # line 817
    return summary
```

Zero references to: `S.filemgr_table_name`, `S.filemgr_bucket`, `s3_client`, `delete_object`, `delete_objects`, `delete_node`, or any other filemanager function.

### What the export path does (correct template)

`process_export()` at lines 535–546 shows the correct DDB access pattern for the file manager:

```python
# app/services/gdpr_service.py:535–546
if categories.get("include_files", True):
    try:
        from app.core.aws import ddb as _ddb
        filemgr = _ddb.Table(S.filemgr_table_name) if S.filemgr_table_name else None
        if filemgr:
            file_items = _query_all(filemgr, Key("pk").eq(f"USER#{user_sub}"))
            zf.writestr(
                f"{export_dir}/files/manifest.json",
                json.dumps(_serialize_items(file_items, redact_keys={"s3_key"}), indent=2, default=str),
            )
    except Exception as e:
        logger.warning("Export files error: %s", e)
```

**Important discovery:** The export accesses `filemgr` using `Key("pk").eq(f"USER#{user_sub}")`. However, examining `app/services/filemanager.py:438–443`, the filemanager table's actual primary key is `PK` (uppercase) with values like `USER#{user_sub}`, and the sort key is `SK` with values like `NODE#{path}`. The export path uses lowercase `pk` — this is a key naming inconsistency that may cause the export to return zero items. The deletion path should use the correct casing from `filemanager.py`'s `pk_user()` function.

### File manager DDB key structure

From `app/services/filemanager.py`:
- PK: `PK = "USER#{user_sub}"` (uppercase `PK`)
- SK: `SK = "NODE#{path}"` (uppercase `SK`)
- S3 key stored in `s3_key` field on each node record
- S3 bucket stored in `s3_bucket` field on each node record (may differ per node if multi-bucket routing applies)
- `deleted_at` field marks soft-deleted nodes — these still have S3 objects and DDB records

The deletion path must handle both soft-deleted (`deleted_at` is set) and active nodes; both have S3 objects that must be deleted.

### S3 deletion mechanics

AWS S3 `delete_objects` accepts up to 1000 object keys per request in batch. For users with many files, the deletion must be chunked. The S3 endpoint is configurable via `S.s3_endpoint_url` (pointing to moto in dev, real S3 in prod). The bucket name is `S.filemgr_bucket`.

The correct boto3 pattern:

```python
s3 = boto3.client("s3", endpoint_url=S.s3_endpoint_url or None,
                   region_name=S.aws_region)
s3.delete_objects(
    Bucket=S.filemgr_bucket,
    Delete={"Objects": [{"Key": k} for k in batch]},
)
```

## 3. Impact / Exploit / Blast Radius

**GDPR Article 17 non-compliance.** User-uploaded files — documents, images, attachments — are personal data. Account deletion must erase them. The platform sends a "Your account has been deleted" confirmation (line 817 of `process_deletion()`), which is a false statement with respect to files.

**Storage cost accumulation.** Each deleted account's files remain in S3 indefinitely. At scale, this represents unbounded storage cost for data with no active owner. A user who uploaded 10 GB of files and then deleted their account costs the platform 10 GB/month in storage permanently.

**Concrete GDPR Article 17 exploit scenario:**
1. User uploads a document containing their national ID number (highly sensitive personal data under Article 9).
2. User requests account deletion to exercise Article 17 rights.
3. Platform confirms deletion.
4. The document remains in S3 indefinitely. Any data breach of the S3 bucket exposes this user's data — despite their having taken the correct legal step to protect it.

**Blast radius.** Every user account that has been deleted since the file manager feature was deployed. Files belonging to those accounts are still in S3. The number of affected objects grows with each new deletion.

**No active exploit pathway.** An external attacker cannot directly leverage this gap to read another user's files (S3 access is protected by IAM). The risk is a data breach scenario or a regulatory enforcement action.

## 4. Fix Design (code-level)

### New deletion step: file manager DDB + S3

Insert a new "Step 12: Delete file manager records and S3 objects" after the messaging deletion step (or after Step 10 if GAP-0339 is not yet deployed) and before the finalisation block:

```python
# app/services/gdpr_service.py — insert before the "Finalize" block at line 800

# Step 12: Delete file manager DDB records and S3 objects
import os as _os  # os is already imported at module level via other code; alias for clarity
try:
    import boto3 as _boto3
    from app.core.aws import ddb as _ddb

    if S.filemgr_table_name:
        filemgr_tbl = _ddb.Table(S.filemgr_table_name)
        # Query all node records for this user (PK = "USER#{user_sub}", SK begins with "NODE#")
        file_items = _query_all(filemgr_tbl, Key("PK").eq(f"USER#{user_sub}"))

        s3_keys_to_delete: List[str] = []
        ddb_keys_to_delete: List[Dict[str, str]] = []

        for node in file_items:
            # Collect S3 objects (both active and soft-deleted nodes have real S3 objects)
            s3_key = node.get("s3_key")
            s3_bucket = node.get("s3_bucket") or S.filemgr_bucket
            if s3_key and s3_bucket == S.filemgr_bucket:
                s3_keys_to_delete.append(s3_key)
            # Collect DDB keys for batch delete
            pk = node.get("PK")
            sk = node.get("SK")
            if pk and sk:
                ddb_keys_to_delete.append({"PK": pk, "SK": sk})

        # Delete S3 objects in batches of 1000 (S3 delete_objects limit)
        deleted_s3 = 0
        if s3_keys_to_delete and S.filemgr_bucket:
            try:
                s3_client = _boto3.client(
                    "s3",
                    endpoint_url=S.s3_endpoint_url or None,
                    region_name=S.aws_region,
                )
                chunk_size = 1000
                for i in range(0, len(s3_keys_to_delete), chunk_size):
                    batch = s3_keys_to_delete[i : i + chunk_size]
                    resp = s3_client.delete_objects(
                        Bucket=S.filemgr_bucket,
                        Delete={"Objects": [{"Key": k} for k in batch]},
                    )
                    deleted_s3 += len(resp.get("Deleted", []))
                    errors = resp.get("Errors", [])
                    if errors:
                        logger.warning("S3 delete_objects partial errors: %s", errors)
            except Exception as e:
                logger.warning("Deletion: S3 delete error: %s", e)
                summary["filemgr_s3_error"] = str(e)

        # Delete DDB file manager records
        deleted_ddb = 0
        for key in ddb_keys_to_delete:
            try:
                filemgr_tbl.delete_item(Key=key)
                deleted_ddb += 1
            except Exception as e:
                logger.warning("Deletion: filemgr DDB delete error for %s: %s", key, e)

        summary["filemgr_s3_objects_deleted"] = deleted_s3
        summary["filemgr_ddb_records_deleted"] = deleted_ddb
    else:
        summary["filemgr_skipped"] = "filemgr_table_name not configured"

except Exception as e:
    logger.warning("Deletion filemgr error: %s", e)
    summary["filemgr_error"] = str(e)
```

### Key naming correction

The export path at line 538 uses `Key("pk")` (lowercase), but filemanager uses `PK` (uppercase). The deletion step uses `Key("PK")` (uppercase) matching `filemanager.py:pk_user()`. This is also a latent bug in the export path that should be fixed in a companion PR — the export manifest for files may be silently empty.

### Multi-bucket files

Some node records may have `s3_bucket` set to a different bucket than `S.filemgr_bucket` (e.g., video thumbnails in a separate bucket). The step above skips objects where `s3_bucket != S.filemgr_bucket`. A follow-up should handle multi-bucket deletion by grouping objects by bucket and issuing a `delete_objects` call per bucket.

### Dev/Prod parity (SECOPS-007)

The S3 client is instantiated with `endpoint_url=S.s3_endpoint_url or None`. In dev, `S.s3_endpoint_url` points to the moto mock (port 4566), so `delete_objects` calls hit moto. In production, `S.s3_endpoint_url` is empty or `None`, so the real AWS S3 endpoint is used. The conditional `or None` pattern is already used in the export path (line 572–573) and is the project standard. The `S.filemgr_bucket` value is set in `.env.local` for dev and via the deployment environment in production — both environments use the same code path.

**Important dev caveat:** moto's `delete_objects` implementation is functionally correct and returns a `Deleted` list. The `S.filemgr_bucket` bucket must exist in moto before the deletion runs. The export path already creates the export bucket on demand (lines 581–584); the deletion path should ensure the filemgr bucket exists or gracefully handle `NoSuchBucket` errors.

### Backward compatibility

The `deletion_summary` dict gains two new keys: `filemgr_s3_objects_deleted` and `filemgr_ddb_records_deleted`. This is additive. When `filemgr_table_name` is not configured, `filemgr_skipped` is set instead, ensuring the deletion completes rather than failing.

### Alternatives considered

- **S3 lifecycle rule to auto-expire user objects:** Would require all objects to be tagged with `user_sub` at upload time. Retroactive tagging of existing objects is complex and adds per-upload overhead. Not implemented in the current codebase. Rejected for the initial fix; tag-at-upload + lifecycle rule is a good long-term addition.
- **Lazy deletion via S3 Object Lock / hold:** Adds compliance complexity without reducing the core gap. Rejected.

### Rollout & risks

- **Irreversibility:** S3 object deletion is permanent (unless S3 Versioning is enabled; confirm bucket versioning configuration in production before deploying). If versioning is enabled, "delete" creates a delete marker rather than permanently erasing the object — a follow-up must call `delete_objects` with `VersionId` to permanently purge versioned objects.
- **Multi-region / multi-bucket:** The current fix handles only `S.filemgr_bucket`. Profile images, video thumbnails, and broadcast assets may be in different buckets. Audit all S3 bucket references in `filemanager.py` and add bucket-grouped deletion in a follow-up.
- **Large accounts:** A user with 50,000 files requires 50 S3 batch calls (50,000 / 1,000) and 50,000 DDB `delete_item` calls. At AWS API rates this takes approximately 10–15 minutes. The deletion path runs inside the `deletion_scheduler` background loop, so this does not block HTTP requests. Confirm `deletion_scheduler` has a long enough timeout.
- **DDB `_query_all` key casing bug in export:** The export path uses `Key("pk")` (lowercase) for the filemanager query. The DDB table uses `PK` (uppercase). If the export has been returning empty file manifests, fix the casing there too in the same PR.
- **Effort:** M — new deletion step (~60 lines), test file (~100 lines), S3 client instantiation pattern (already exists in `process_export`).
- **Rollback:** Remove Step 12 from `process_deletion()`. Already-deleted S3 objects cannot be restored; rollback only prevents future deletions.
- **Sequence:** Deploy after confirming S3 bucket versioning policy. Independent of GAP-0339.
