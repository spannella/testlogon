# GAP-0281: `_readiness_for_case` Does Not Gate Tier-2/Tier-3 Cases on Address Verification — Remediation Write-up

## 1. Summary & Classification

**Ticket**: GAP-0281 | **Source**: KYC-018 | **Severity**: HIGH | **Status**: Open | **Effort**: M
**Owning area**: KYC — case submission gate (`app/routers/kyc_cases.py`)

The `_readiness_for_case` helper function (lines 244–307 of `app/routers/kyc_cases.py`) determines whether a KYC case is ready for final submission. According to KYC-018 §4.8, cases at tier_2 ("enhanced" intake profile) and tier_3 ("high_risk" intake profile) must not be submittable unless the applicant's address verification status is either `verified` or `partial_match`. The current implementation checks only three conditions — questionnaire submitted, required files attached, and signature packet completed — and has zero awareness of address verification. A tier_2 or tier_3 applicant whose address has never been verified, or whose verification returned `no_match` or `failed`, can proceed through the submission gate as if the address check had passed.

**Verdict**: Confirmed. The claim is accurate. `_readiness_for_case` makes no call to the address-verification store and no import of `app/services/kyc_address_verification` exists in the router.

**Related tickets**: GAP-0279 (separate readiness gap on the admin side), GAP-0280 (address-change hook not wired), SEC-010-series (IDOR on lifecycle routes).

## 2. Current-State Investigation (root cause)

### The readiness check today

`app/routers/kyc_cases.py` lines 244–307:

```python
def _readiness_for_case(case: dict) -> dict:
    questionnaire = _questionnaire_status_for_case(case, include_submit_gate=False)
    files = _validate_file_requirements(case)
    signature = _signature_status_for_case(case)

    checks = {
        "questionnaire_submitted": bool(questionnaire.get("submitted")),
        "required_files": bool(files.get("ready_for_submit_gate")),
        "signature_completed": bool(signature.get("ready_for_submit_gate")),
    }
    ...
    requirements: list[dict] = [
        { "key": "questionnaire_submitted", ... },
        { "key": "required_files", ... },
        { "key": "signature_completed", ... },
    ]
    missing_requirements = [item["key"] for item in requirements if not item["ready"]]
    ...
    return {
        "ready_to_submit": all(checks.values()),   # ← only 3 checks, no address check
        "missing_requirements": missing_requirements,
        ...
    }
```

The function never queries the address-verification sub-system. There is no import of `app/services/kyc_address_verification` anywhere in `kyc_cases.py` — confirmed by a full-file `grep` search returning zero results.

### The address-verification service

`app/services/kyc_address_verification.py` exposes `get_latest(case_id) -> dict | None` (line 605) which returns the most recent verification attempt item. Relevant fields on that item are `status` (one of `"verified"`, `"partial_match"`, `"no_match"`, `"failed"`, `"pending"`) and the controlling feature flag `S.kyc_address_verification_enabled` (settings line 1298, env var `KYC_ADDRESS_VERIFICATION_ENABLED`, default `true`).

The tier vocabulary used by the rest of the KYC system (`app/services/kyc_case_assignment.py` lines 43–47) maps `intake_profile` field values to tiers:

```
"enhanced"   → medium risk → tier_2
"high_risk"  → high risk   → tier_3
```

Standard-intake cases (`intake_profile` not in `{"enhanced", "high_risk"}`) map to tier_1 and do not require address verification by spec.

### How the bug manifests at runtime

1. User creates a KYC case with `intake_profile = "enhanced"` (tier_2).
2. User skips the address-verification step entirely, or submits a proof-of-address document that the verification engine rejects (`status = "no_match"`).
3. User completes questionnaire, attaches selfie/id_front/id_back, and finishes the signature packet.
4. `GET /v1/kyc/cases/{case_id}/readiness` returns `ready_to_submit: true` and zero `missing_requirements`.
5. `POST /v1/kyc/cases/{case_id}/submit` succeeds and routes the case to the admin review queue.

In production the admin reviewer may not notice the missing address verification and could approve a case that lacks a required verification step.

### The readiness endpoint usage in the application flow

The readiness endpoint is called from two contexts. First, the frontend calls it to determine whether to enable the Submit button — if `ready_to_submit` is `false` the button is grayed out and the user is shown the list of `missing_hints`. Second, the submit endpoint itself calls `_readiness_for_case` as a guard (or should; checking the submit handler confirms the same function is not independently called at submission time — the only gate is what the frontend enforces based on the readiness response). This makes the readiness function the single authoritative gate for submission eligibility, and its correctness is therefore critical.

## 3. Impact / Exploit / Blast Radius

**Regulatory / compliance**: KYC-018 §4.8 is a hard business requirement, not a performance concern. Allowing tier_2/tier_3 cases to be submitted without address verification violates the enhanced due-diligence requirement that applies to high-risk applicants.

**Exploit walkthrough**:
1. Attacker registers, chooses `intake_profile = "enhanced"` (or is automatically assigned "high_risk" via risk scoring).
2. Attacker deliberately avoids initiating address verification (never calls `POST /v1/kyc/address-verification/{case_id}/start`), or initiates it and receives `status = "no_match"`.
3. All other requirements satisfied → case submits → enters admin queue as if fully verified.
4. Admin reviewer, trusting the submission gate, may approve the case without noticing the verification gap, resulting in a fully KYC-verified account that bypassed a mandatory check.

**Who is affected**: All users with `intake_profile` set to `"enhanced"` or `"high_risk"`. Tier_1 standard cases are not affected because address verification is not required for them.

**Worst case**: Fraudulent high-risk applicant receives verified KYC status and proceeds to use features that should only be available to address-verified users. Financial and legal liability for the platform.

**Data integrity**: No data corruption. The harm is a missing enforcement gate, not a write-path bug.

## 4. Fix Design (code-level)

### Changes required

**File**: `app/routers/kyc_cases.py`

1. Add an import for the address-verification service and the tier-mapping helper at the top of the file:

```python
# Near existing imports, after line 67
from app.services.kyc_address_verification import KycAddressVerificationService as _AddrSvc
from app.services.kyc_case_assignment import risk_band_for_case
```

2. Extend `_readiness_for_case` (currently line 244) to add the address check when the feature flag is on and the case tier requires it:

```python
def _readiness_for_case(case: dict) -> dict:
    questionnaire = _questionnaire_status_for_case(case, include_submit_gate=False)
    files = _validate_file_requirements(case)
    signature = _signature_status_for_case(case)

    checks = {
        "questionnaire_submitted": bool(questionnaire.get("submitted")),
        "required_files": bool(files.get("ready_for_submit_gate")),
        "signature_completed": bool(signature.get("ready_for_submit_gate")),
    }
    hint_map = {
        "questionnaire_submitted": "Submit the linked questionnaire to continue.",
        "required_files": "Attach all required identity files: selfie, id_front, id_back.",
        "signature_completed": "Complete the consent signature packet and wait for final PDF generation.",
        "address_not_verified": "Address verification is required for your account type. "
                                "Please complete address verification before submitting.",
    }

    # --- NEW: address-verification gate for tier_2 and tier_3 ---
    _ADDRESS_REQUIRED_RISK_BANDS = {"medium", "high"}  # tier_2 / tier_3
    address_check_enabled = (
        S.kyc_address_verification_enabled
        and risk_band_for_case(case) in _ADDRESS_REQUIRED_RISK_BANDS
    )
    if address_check_enabled:
        _addr_svc = _AddrSvc()
        latest_av = _addr_svc.get_latest(str(case.get("kyc_case_id") or ""))
        av_status = str((latest_av or {}).get("status") or "")
        address_verified = av_status in {"verified", "partial_match"}
        checks["address_not_verified"] = address_verified   # True = ready
    # -----------------------------------------------------------

    requirements: list[dict] = [
        {
            "key": "questionnaire_submitted",
            "ready": checks["questionnaire_submitted"],
            "missing": ([] if checks["questionnaire_submitted"] else ["questionnaire_submission"]),
            "hint": hint_map["questionnaire_submitted"],
            "refs": {
                "questionnaire_id": questionnaire.get("questionnaire_id"),
                "response_session_id": questionnaire.get("response_session_id"),
                "response_pdf_ref": questionnaire.get("response_pdf_ref"),
            },
        },
        {
            "key": "required_files",
            "ready": checks["required_files"],
            "missing": list(files.get("missing_types") or []),
            "hint": hint_map["required_files"],
            "refs": {
                "present_types": ",".join(files.get("present_types") or []),
            },
        },
        {
            "key": "signature_completed",
            "ready": checks["signature_completed"],
            "missing": (
                []
                if checks["signature_completed"]
                else ["signature_completion", "signature_final_pdf"]
            ),
            "hint": hint_map["signature_completed"],
            "refs": {
                "packet_id": signature.get("packet_id"),
                "final_pdf_ref": signature.get("final_pdf_ref"),
            },
        },
    ]

    # Append address requirement only when the gate is active.
    if address_check_enabled:
        requirements.append({
            "key": "address_not_verified",
            "ready": checks.get("address_not_verified", False),
            "missing": ([] if checks.get("address_not_verified") else ["address_not_verified"]),
            "hint": hint_map["address_not_verified"],
            "refs": {},
        })

    missing_requirements = [item["key"] for item in requirements if not item["ready"]]
    missing_hints = [hint_map[key] for key in missing_requirements]

    return {
        "kyc_case_id": case.get("kyc_case_id"),
        "status": case.get("status"),
        "ready_to_submit": all(item["ready"] for item in requirements),
        "missing_requirements": missing_requirements,
        "missing_hints": missing_hints,
        "checks": checks,
        "requirements": requirements,
    }
```

### Dev/Prod parity (SECOPS-007)

The `KycAddressVerificationService` already uses `S.kyc_address_verification_enabled` internally before performing real verification (lines 397, 484, 528 of `app/services/kyc_address_verification.py`). However, the gate in `_readiness_for_case` is separate from whether verification runs — it is about whether a verified result is required for submission. The proposed fix adds its own `S.kyc_address_verification_enabled` guard so that dev environments with the flag set to `false` continue to behave as before (no gate, tier_2/tier_3 can submit freely). In all environments — dev, staging, production — the code path is identical; only the flag value differs.

The `_AddrSvc()` instantiation is cheap (it is a service class that wraps a DynamoDB table handle). No mock-only code path is needed because `T.kyc_cases` is already abstracted and moto intercepts DDB calls in dev/test.

### Backward compatibility

The `ready_to_submit` response field and `missing_requirements` array are already part of the public API contract (`KycReadinessEnvelope`). Adding a new entry to `requirements` and potentially to `missing_requirements` is backward-compatible for consumers that iterate the array. Any client that hard-codes an expected length of the `requirements` array would break, but no such client is in the codebase (the frontend reads `ready_to_submit` and `missing_requirements` only).

The feature flag `KYC_ADDRESS_VERIFICATION_ENABLED=false` in `.env.local.example` means all existing E2E tests using standard-intake (tier_1) cases continue to pass without changes, because the risk-band guard also excludes tier_1 independently.

### Alternatives considered

- **Check at the submit endpoint rather than readiness**: Rejected. The readiness check is the authoritative pre-flight gate used by the frontend to enable or disable the Submit button. Checking only at the submit endpoint would leave the UI in an inconsistent state and create a "surprise rejection" for users who followed the readiness response.
- **Store the verification status on the case record instead of querying the service**: Rejected. The case record does not currently denormalize verification status. Adding a denormalized field would require a write-path change with its own migration complexity and introduce synchronization bugs when verification is retried.

9. Repeat with `KYC_ADDRESS_VERIFICATION_ENABLED=false` in `.env.local`, restart backend, and verify that a tier_2 case can reach `ready_to_submit: true` without any address verification — confirming the feature-flag gate works correctly for environments that have disabled the feature.

### Metrics / observability

Add a `missing_requirement=address_not_verified` counter tag to the existing `kyc_funnel_transition` Prometheus metric (already emitted at the readiness endpoint) so that ops can track how often tier_2/tier_3 cases are blocked here.

### Rollout

- Deploy with `KYC_ADDRESS_VERIFICATION_ENABLED=true` (already default).
- No DynamoDB schema changes needed.
- No migration needed — existing draft cases that have not been submitted are simply re-evaluated against the new gate on next readiness call.
- Risk: low. Feature-flagged; any issue can be immediately mitigated by setting `KYC_ADDRESS_VERIFICATION_ENABLED=false`.

**Effort**: M — approximately 1 developer-day including test authoring and review.

### Sequencing with GAP-0279 and GAP-0280

GAP-0279 identifies a separate readiness gap on the admin-side case detail view. GAP-0280 identifies that the address-change hook is not wired into the profile update path (meaning a user who changes address after passing verification would not be re-verified). Both gaps interact with this ticket: implementing GAP-0281 without GAP-0280 means that a user who updates their address post-verification and receives a `no_match` on re-verification would be blocked from resubmitting correctly — the readiness check would permanently fail until the address is re-verified, which is the correct behaviour, but only if GAP-0280 is also implemented to trigger re-verification. Consider sequencing GAP-0281 (readiness gate) concurrently with GAP-0280 (re-verification trigger) to avoid user-visible friction where the gate blocks a user whose address changed but no re-verification was automatically triggered.
