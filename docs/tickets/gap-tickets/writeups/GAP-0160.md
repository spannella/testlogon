# GAP-0160: recordEngagement never called from frontend — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement.** The recommendation engine (DISC-001) relies on engagement
signals — watch percentage and like events — to compute personalised "For You"
video feeds. The backend endpoint `POST /ui/recommendations/engagement` is
correctly implemented and registered. The TypeScript API wrapper
`recordEngagement` is correctly defined in
`frontend/src/api/endpoints/recommendations.ts:88`. However,
`VideoPlayerPage` (`frontend/src/pages/videos/VideoPlayerPage.tsx`) never
calls `recordEngagement`. There are no `onEnded`, `onTimeUpdate`, or
equivalent event hooks in `VideoPlayerPage` that fire `recordEngagement`.
`compute_affinity_scores` therefore always processes empty signal input for
every user, and the collaborative-filtering algorithm has zero data to work
with.

**Severity:** HIGH — the signal-recording layer is the data intake for the
entire recommendation system; without it, every downstream component
(personalised feed, creator suggestions, similar videos) operates on zero
data.  
**Source ticket:** DISC-001  
**Status:** Open  
**Owning area:** `frontend/src/pages/videos/VideoPlayerPage.tsx`,
`frontend/src/components/shared/MediaPlayer.tsx`  
**Effort:** S

**Verdict from code investigation:** Claim confirmed. A search of
`frontend/src/pages/` for any call to `recordEngagement` returns no results.
`VideoPlayerPage` passes only `onError` to `<MediaPlayer>`; the `MediaPlayer`
component's `MediaPlayerProps` interface exposes `onError`, `onReady`, and
`onQualityChange` callbacks but **no `onEnded` or progress callback**.
Neither `recordEngagement` nor its import path is referenced anywhere in the
pages directory.

**Related tickets:** GAP-0159 (background refresh job not registered),
DISC-001.

### Why the gap exists

`VideoPlayerPage` was implemented as part of VOD-008 (video playback
infrastructure). The recommendation signal integration from DISC-001 was
designed as a separate concern. When DISC-001 implemented `recordEngagement`
and the backend endpoint, it was left to the frontend team to integrate the
call into `VideoPlayerPage`. That integration step was never done.

## 3. Impact / Exploit / Blast Radius

**Who is affected:** All users of the "For You" feed and any recommendation
surface driven by engagement signals. Because `compute_affinity_scores` reads
from `T.recommendations` signals that are never written, it returns empty
affinities → `compute_for_you` falls through to the trending/cold-start
fallback for 100 % of users.

**Compound effect with GAP-0159.** Even when GAP-0159 is fixed (background
refresh runs on a schedule), the refresh processes empty signal sets. Both
gaps must be closed for recommendations to work.

**Signal drift.** Every user who watches videos during the window that both
gaps are open is generating watch history that is **not** recorded.
This engagement history is permanently lost (there is no replay mechanism).
Personalisation quality for early users will be degraded until sufficient new
signals accumulate post-fix.

**Financial / business impact.** Creator discovery and monetisation through
the "For You" feed is entirely non-functional. Any creator who relies on
discovery to grow their audience receives no algorithmic benefit.

**Security / integrity.** No security risk. No data is corrupted; the
`T.recommendations` signal store is simply empty.

## 4. Fix Design (code-level)

### Step 1 — Add `onEnded` and `onProgress` callbacks to `MediaPlayer`

`frontend/src/components/shared/MediaPlayer.tsx` — extend `MediaPlayerProps`:

```typescript
export interface MediaPlayerProps {
  // ... existing props ...
  /** Called when video playback ends naturally */
  onEnded?: () => void;
  /** Called periodically during playback with watch percentage (0-100) */
  onProgress?: (watchPct: number) => void;
}
```

Inside the `useEffect` that wires the `<video>` element (around line 420),
add:

```typescript
// Notify parent when video ends
if (props.onEnded) {
  const handleEnded = () => props.onEnded?.();
  video.addEventListener("ended", handleEnded);
  cleanup.push(() => video.removeEventListener("ended", handleEnded));
}

// Report watch percentage every N seconds (throttled)
if (props.onProgress) {
  let lastReportedPct = -1;
  const REPORT_THRESHOLD_PCT = 5;  // only fire on ≥5% increments
  const handleTimeUpdate = () => {
    if (!video.duration || video.duration === 0) return;
    const pct = Math.floor((video.currentTime / video.duration) * 100);
    if (Math.abs(pct - lastReportedPct) >= REPORT_THRESHOLD_PCT) {
      lastReportedPct = pct;
      props.onProgress?.(pct);
    }
  };
  video.addEventListener("timeupdate", handleTimeUpdate);
  cleanup.push(() => video.removeEventListener("timeupdate", handleTimeUpdate));
}
```

### Step 2 — Call `recordEngagement` from `VideoPlayerPage`

`frontend/src/pages/videos/VideoPlayerPage.tsx`:

**Add import:**

```typescript
import { recordEngagement } from "@/api/endpoints/recommendations";
```

**Add ref for 30-second milestone tracking** (per the ticket's requirement):

```typescript
const thirtySecFiredRef = useRef(false);
```

Reset on `videoId` change:

```typescript
useEffect(() => {
  thirtySecFiredRef.current = false;
}, [videoId]);
```

**Add engagement callbacks:**

```typescript
const handleVideoEnded = useCallback(() => {
  if (!videoId) return;
  // Record full watch (100%) on natural end
  recordEngagement({ video_id: videoId, watch_pct: 100 }).catch(() => {
    // Fire-and-forget; errors should not affect UX
  });
}, [videoId]);

const handleVideoProgress = useCallback((watchPct: number) => {
  if (!videoId) return;
  // Record engagement at 30-second proxy: fire once when watch_pct hits 30%
  // (exact 30-second tracking requires duration; % is equivalent and simpler)
  if (watchPct >= 30 && !thirtySecFiredRef.current) {
    thirtySecFiredRef.current = true;
    recordEngagement({ video_id: videoId, watch_pct: watchPct }).catch(() => {});
  }
}, [videoId]);
```

**Wire into `<MediaPlayer>`:**

```tsx
<MediaPlayer
  src={playbackUrl}
  mode="vod"
  autoplay
  poster={video.thumbnail_url ?? undefined}
  title={video.title}
  onError={handleMediaError}
  onEnded={handleVideoEnded}
  onProgress={handleVideoProgress}
  subtitleTracks={subtitleTracksForPlayer.length > 0 ? subtitleTracksForPlayer : undefined}
/>
```

### Step 3 — Record engagement for "liked" signal

When a user likes a video (if a like button exists on `VideoPlayerPage`),
call `recordEngagement({ video_id: videoId, liked: true })`. This is a
follow-up if a like button is not yet present; the watch percentage signals
are the primary fix.

### Dev/Prod parity (SECOPS-007)

The `POST /ui/recommendations/engagement` endpoint requires `require_ui_session`,
which works identically in dev (cookie-based session) and prod (Cognito JWT or
cookie). No mock gating is needed. In dev the endpoint is always available;
`S.recommendations_enabled` is checked at the router-include level in
`app/main.py:594` but defaults to `true`.

The `MediaPlayer` `onEnded` / `onProgress` changes are pure browser events
with no environment-specific behaviour.

### Throttling / de-duplication

`record_signal` in `app/services/recommendations.py:91` uses DynamoDB
`update_item` with `if_not_exists` for `view_count` and `max()` logic for
`watch_pct`. Multiple calls per session for the same `video_id` are safe and
idempotent. No client-side deduplication is required beyond the `thirtySecFiredRef`
guard.

### Alternatives considered

- **Track exact 30-second mark using `currentTime`** — requires knowing
  `video.duration` at the `timeupdate` callback. This is more accurate but
  more complex (duration may not be available immediately). The percentage
  proxy (30%) fires at approximately the same point for a 100s video and is
  simpler to implement correctly.
- **Send engagement on page unload** (`beforeunload` / `visibilitychange`)** —
  catches abandonment but is unreliable in mobile browsers. The combination of
  `onEnded` (full watch) + `onProgress` (mid-watch) covers the primary signal
  types. Page-unload signals are a follow-up enhancement.
- **Batch signals from the frontend** — not needed at current scale;
  fire-and-forget individual `POST` calls are fine.

### Rollback

Remove the `onEnded` and `onProgress` props from `MediaPlayer.tsx` and remove
the `handleVideoEnded` / `handleVideoProgress` callbacks and import from
`VideoPlayerPage.tsx`. No schema changes; no DynamoDB migrations.

### Risk

**Very low.** `recordEngagement` calls are fire-and-forget (`catch(() => {})`);
failures do not surface to the user or affect playback. The additional
`onEnded` / `onProgress` event listeners on the `<video>` element are
lightweight and do not affect playback performance. The `timeupdate` handler
is throttled to fire only at ≥5% increments.

### Effort

**S** — approximately 45–60 minutes: `MediaPlayer` interface extension
(~15 min), `VideoPlayerPage` callback wiring (~20 min), E2E test (~20 min).

### Sequencing

This fix is the data-intake prerequisite for GAP-0159 (background refresh).
Deploy this fix first (or simultaneously with GAP-0159) so that the first
background refresh has signal data to process. Without GAP-0160, GAP-0159
produces no meaningful output.
