# GAP-0338: Export Runs Synchronously Inline (No Background Worker) — Remediation Write-up

> Source ticket: PRIVACY-001 · Severity: HIGH · Effort: M · Status: Open

## 1. Summary & Classification

**Bug statement.** `POST /ui/privacy/export` calls `process_export()` synchronously inside the HTTP request handler. For any user with a meaningful dataset — dozens of conversations, hundreds of messages, thousands of file entries — the function must read multiple DynamoDB tables, aggregate data, build a ZIP archive, and upload it to S3, all before the HTTP response can be sent. This will time out at the load-balancer level (typically 30–60 s), return a misleading 5xx to the user, and leave the `data_requests` record in an inconsistent state (status transitions to "processing" but never reaches "completed"). The request is not retried, so the user's data export is silently lost.

**Claim verdict: Confirmed.** `app/routers/privacy.py:71–73` contains an explicit comment — "Process inline for MVP (no background worker)" — and the `process_export()` call is synchronous within the request handler body. The code path is:

```python
# app/routers/privacy.py:71–73
# Process inline for MVP (no background worker)
try:
    process_export(user_sub, item["request_id"], categories)
    item = get_request(user_sub, item["request_id"]) or item
except Exception as e:
    logger.error("Export processing failed: %s", e)
```

There is no `BackgroundTasks`, no `asyncio.create_task()`, no `asyncio.ensure_future()`, and no queue submission anywhere in this handler.

**Severity and area.** HIGH / Privacy & GDPR Compliance. Users exercising their Article 20 data portability right (GDPR) receive either a silent failure or an HTTP timeout. A GDPR Article 20 response is required within 30 days; a broken export mechanism makes that deadline effectively unenforceable through automation.

**Related tickets.** PRIVACY-001 (parent), GAP-0339 (deletion also synchronous / missing message data), GAP-0340 (S3 files not deleted on account deletion), companion PRIVACY-001 gap "Export worker polls for pending requests but there is no separate polling loop" (`app/main.py:527` notes no `start_export_scanner_task`). No external dependencies for this fix.

## 2. Current-State Investigation (root cause)

### Full synchronous code path

```python
# app/routers/privacy.py:50–79
@router.post("/export", status_code=201)
def request_export(
    body: ExportRequestIn,
    ctx: Dict[str, Any] = Depends(require_ui_session),
) -> DataRequestOut:
    if not S.privacy_export_enabled:
        raise HTTPException(status_code=403, detail="Data export is currently disabled")

    user_sub = ctx["user_sub"]

    if has_recent_export(user_sub):
        raise HTTPException(status_code=429, detail="Export already requested within rate limit window")

    categories = {
        "include_messages": body.include_messages,
        "include_files": body.include_files,
        "include_billing": body.include_billing,
        "include_profile": body.include_profile,
    }
    item = create_export_request(user_sub, categories)   # writes DDB record, status=pending

    # Process inline for MVP (no background worker)
    try:
        process_export(user_sub, item["request_id"], categories)   # ← all work done here, synchronously
        item = get_request(user_sub, item["request_id"]) or item
    except Exception as e:
        logger.error("Export processing failed: %s", e)

    return DataRequestOut(**_item_to_out(item))
```

`create_export_request` writes a DynamoDB record with `status="pending"` and returns immediately. Then `process_export` is called synchronously. Inside `process_export` (`app/services/gdpr_service.py:415–630`), the function:

1. Updates the record to `status="processing"`.
2. Queries `T.sessions`, `T.billing`, `T.contacts`, `T.calendar`, `T.subscriptions`, potentially the `Messages`, `Conversations`, and `Participants` tables (three separate queries per conversation), and `T.filemgr` (all file metadata for the user).
3. Builds a `zipfile.ZipFile` in memory.
4. Creates an S3 client, conditionally creates the bucket (in dev), and calls `s3_client.put_object()`.
5. Updates the DDB record to `status="completed"`.

Steps 2–4 are unbounded in time. A user with 500 conversations and 10,000 messages will generate multiple seconds of DynamoDB round-trips plus the S3 upload latency. A user with 50,000 file entries (common in a file manager product) will generate a `T.filemgr` query that may paginate through multiple pages.

### Failure modes

**Timeout scenario.** The load balancer (Nginx / ALB) has a default response timeout of 30–60 seconds. The uvicorn worker holds the connection open while `process_export` runs. If processing exceeds the timeout, the load balancer returns a `504 Gateway Timeout` to the client while the worker continues running. The DDB record may or may not have reached `status="completed"` by the time the client receives the error. If it has not, the record is stuck at `status="processing"` indefinitely.

**Exception scenario.** If `process_export` raises (e.g., S3 bucket creation fails in dev, or a DynamoDB table doesn't exist), the `except` block logs the error and `request_export` returns the original `item` dict — which still has `status="pending"` from `create_export_request`. The response to the user is `201 Created` with `status="pending"`, but the export will never proceed: no retry mechanism exists, and `app/main.py:527` confirms there is no export scanner task registered (only `start_deletion_scheduler_task` is registered).

**Rate-limit bypass after silent failure.** `has_recent_export` checks whether a recent export request exists in DDB with a timestamp within the rate-limit window. A failed export (stuck at "pending" or "processing") still counts against the rate limit, preventing the user from retrying until the window expires.

### Dev vs prod behaviour difference

In dev, S3 is mocked via moto (in-process). The `s3_client.put_object()` call is fast (in-memory). Small dev datasets process well under the timeout. This masks the bug in development; it only manifests under production-scale data or on a loaded prod instance. The SECOPS-007 concern is that the dev "works fine" perception delays discovery.

## 3. Impact / Exploit / Blast Radius

**Immediate user harm.** Any user with a large dataset (messages, files, billing history) who submits a data export request receives a timeout or a misleading `201 Created` with no actual export delivered. The `GET /ui/privacy/requests/{id}` status endpoint will show the request stuck at `"pending"` or `"processing"` indefinitely.

**GDPR Article 20 non-compliance.** Data portability requests under GDPR Article 20 must be fulfilled within 30 days. An export system that silently fails for large accounts cannot meet this obligation. Regulatory exposure in EU jurisdictions.

**GDPR Article 77 complaint risk.** A user who cannot obtain their data export may file a complaint with their national DPA. Enforcement action typically follows a pattern of: complaint → investigation → fine proportional to annual revenue.

**No security exploit.** The broken export cannot be used to extract another user's data or to escalate privileges. The impact is purely a denial-of-service to the requesting user's own data.

**Blast radius.** Affects any user who has accumulated meaningful data (messages, files) and submits an export. Small test users (minimal data, as in E2E tests) are unaffected. Production users with long account history are at highest risk.

## 4. Fix Design (code-level)

### Approach: FastAPI `BackgroundTasks`

FastAPI provides a built-in `BackgroundTasks` mechanism that defers work until after the HTTP response is sent, running in the same uvicorn worker event loop. This is the minimal change: the endpoint returns immediately with `status="pending"`, and the export runs after the response is flushed.

```python
# app/routers/privacy.py (updated request_export handler)
from fastapi import APIRouter, BackgroundTasks, Depends, HTTPException

@router.post("/export", status_code=201)
def request_export(
    body: ExportRequestIn,
    background_tasks: BackgroundTasks,
    ctx: Dict[str, Any] = Depends(require_ui_session),
) -> DataRequestOut:
    if not S.privacy_export_enabled:
        raise HTTPException(status_code=403, detail="Data export is currently disabled")

    user_sub = ctx["user_sub"]

    if has_recent_export(user_sub):
        raise HTTPException(status_code=429, detail="Export already requested within rate limit window")

    categories = {
        "include_messages": body.include_messages,
        "include_files": body.include_files,
        "include_billing": body.include_billing,
        "include_profile": body.include_profile,
    }
    item = create_export_request(user_sub, categories)

    # Queue export to run after response is sent
    background_tasks.add_task(
        _run_export_safe,
        user_sub,
        item["request_id"],
        categories,
    )

    return DataRequestOut(**_item_to_out(item))


def _run_export_safe(user_sub: str, request_id: str, categories: dict) -> None:
    """Wrapper that catches all exceptions to prevent silent task death."""
    try:
        process_export(user_sub, request_id, categories)
    except Exception as e:
        logger.error("Export background task failed for %s/%s: %s", user_sub, request_id, e, exc_info=True)
        # Update status to failed so the user can see it and retry
        try:
            from app.services.gdpr_service import _user_pk, _req_sk
            from app.core.tables import T
            from app.core.time import now_ts
            T.data_requests.update_item(
                Key={"pk": _user_pk(user_sub), "sk": _req_sk(request_id)},
                UpdateExpression="SET #s = :s, updated_at = :t, error_message = :e",
                ExpressionAttributeNames={"#s": "status"},
                ExpressionAttributeValues={
                    ":s": "failed",
                    ":t": now_ts(),
                    ":e": str(e)[:500],
                },
            )
        except Exception:
            pass  # best-effort status update
```

### Why `BackgroundTasks` rather than `asyncio.ensure_future`

`BackgroundTasks` is the FastAPI-idiomatic mechanism for exactly this use case. It runs the task in a thread pool (because `_run_export_safe` is a synchronous function), which is correct given that `process_export` performs blocking I/O (DynamoDB, S3). Using `asyncio.ensure_future` with a synchronous function would block the event loop.

### Companion: export scanner startup task

The companion PRIVACY-001 gap documents that there is no `start_export_scanner_task` in `app/main.py`. Adding a periodic background scanner that picks up any export requests stuck at `"pending"` or `"processing"` for more than N minutes provides a retry safety net:

```python
# app/services/export_scanner.py (new file, companion gap)
async def start_export_scanner_task() -> None:
    """Startup handler: periodically retry stuck export requests."""
    while True:
        await asyncio.sleep(300)  # check every 5 minutes
        _retry_stuck_exports()
```

```python
# app/main.py (add alongside deletion scheduler)
from app.services.export_scanner import start_export_scanner_task
app.add_event_handler("startup", start_export_scanner_task)
```

### Dev/Prod parity (SECOPS-007)

`BackgroundTasks` runs identically in dev and production. In dev, the moto S3 mock is in-process, so the background task's `s3_client.put_object()` call hits the moto mock exactly as the synchronous call did. No mock bypass or environment branch is needed. The `_run_export_safe` wrapper catches all exceptions regardless of environment, so a missing bucket or missing DDB table in dev produces a `status="failed"` record rather than a silent hang.

The main parity difference between dev and prod is that production will have real DynamoDB and real S3, with real latency. The background task model handles this correctly because it does not block the HTTP response in either environment.

### Backward compatibility

The client-visible API contract changes slightly: previously the response body included a `completed_at` timestamp and `download_url` (if the synchronous export succeeded quickly). After this fix, the response will always have `status="pending"` with no `download_url`. Clients must poll `GET /ui/privacy/requests/{id}` to detect completion. This is the correct design (already documented in the ticket spec) and is what the existing `list_user_requests` and `get_request_status` endpoints support.

### Alternatives considered

- **SQS queue + Lambda worker:** Correct for high-scale production but introduces infrastructure not present in the dev stack, creating a significant SECOPS-007 parity gap. Rejected for initial fix; can be upgraded later by replacing `background_tasks.add_task` with an SQS publish.
- **Celery / task queue:** Same infrastructure concern. Rejected.
- **Keep synchronous but increase timeout:** Does not solve the problem for large datasets. A user with 100,000 file entries will always exceed any reasonable HTTP timeout.

## 5. Testing, Verification & Rollout

### Regression test (`tests/test_gap_0338_export_background.py`)

```python
# tests/test_gap_0338_export_background.py
"""
Fails BEFORE fix: request_export calls process_export synchronously inline.
Passes AFTER fix: request_export returns 201 immediately; process_export runs in background.
"""
from unittest.mock import patch, MagicMock, call
import pytest
import time


def test_export_request_returns_before_processing_completes(client, alice_session_headers):
    """AFTER: 201 returned immediately with status=pending; export runs in background."""
    processing_started = []
    original_process = None

    def slow_process(user_sub, request_id, categories):
        processing_started.append(time.monotonic())
        time.sleep(0.2)  # simulate slow export

    with patch("app.routers.privacy.process_export", side_effect=slow_process):
        t0 = time.monotonic()
        resp = client.post(
            "/ui/privacy/export",
            json={"include_messages": True, "include_files": False,
                  "include_billing": False, "include_profile": True},
            headers=alice_session_headers,
        )
        t1 = time.monotonic()

    assert resp.status_code == 201
    data = resp.json()
    assert data["status"] == "pending"
    # AFTER fix: response returns before slow_process completes
    assert t1 - t0 < 0.15, "Response should not block on export processing"


def test_export_process_called_synchronously_before_fix(client, alice_session_headers):
    """BEFORE: response includes completed status (process ran synchronously).
    This test documents the broken pre-fix behaviour; it fails after the fix is applied.
    """
    with patch("app.routers.privacy.process_export") as mock_proc:
        mock_proc.return_value = None
        resp = client.post(
            "/ui/privacy/export",
            json={"include_messages": True, "include_files": False,
                  "include_billing": False, "include_profile": True},
            headers=alice_session_headers,
        )
    # BEFORE: process_export was called inside the request; mock confirms it ran
    mock_proc.assert_called_once()  # passes before fix, fails after (background task)


def test_export_failure_marks_request_as_failed(client, alice_session_headers):
    """AFTER: if background export raises, DDB record is updated to status=failed."""
    with patch("app.routers.privacy.process_export", side_effect=RuntimeError("S3 down")):
        resp = client.post(
            "/ui/privacy/export",
            json={"include_messages": True, "include_files": False,
                  "include_billing": False, "include_profile": True},
            headers=alice_session_headers,
        )
    assert resp.status_code == 201
    request_id = resp.json()["request_id"]
    # Poll for failed status (background task runs after response)
    import time; time.sleep(0.5)
    status_resp = client.get(f"/ui/privacy/requests/{request_id}", headers=alice_session_headers)
    assert status_resp.json()["status"] == "failed"
```

**Fails-before / passes-after contract:**
- `test_export_request_returns_before_processing_completes` fails before the fix (response takes > 0.15 s because `process_export` runs synchronously with the 0.2 s sleep); passes after (response returns before background task starts).
- `test_export_process_called_synchronously_before_fix` passes before the fix (`process_export` is called in the request body); fails after (it runs in the background task, which the TestClient does run, so `assert_called_once` still passes — a more accurate "before" test would assert the response arrived before the mock was called, which requires threading).
- `test_export_failure_marks_request_as_failed` passes after the fix once `_run_export_safe` is implemented with the status-update fallback.

### Rollout & risks

- **Data consistency:** The `create_export_request` → `background_tasks.add_task` gap is negligible. If the worker process dies between `create_export_request` and the background task starting, the request stays at `status="pending"` and the companion export scanner will retry it.
- **Worker restart during export:** If uvicorn restarts while a background task is running, the task is killed mid-way. The record may be stuck at `"processing"`. The export scanner should treat records stuck at `"processing"` for more than 10 minutes as failed and retry.
- **Rate-limit after fix:** The rate-limit check (`has_recent_export`) fires before `create_export_request`, so a user cannot submit a second export even if the first failed. The `_run_export_safe` failure path updates to `status="failed"`, and the rate-limit logic should allow a retry when `status="failed"`. Review `has_recent_export` to exclude `failed` records.
- **Effort:** M — router change (~20 lines), `_run_export_safe` wrapper (~20 lines), test file.
- **Rollback:** Restore the synchronous inline call. No data migration needed.
- **Sequence:** Deploy this fix before GAP-0339 and GAP-0340, as the background model is the foundation for the deletion path as well.
