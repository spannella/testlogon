# GAP-0041: update_creator_ad_settings is Full PutItem, Not Partial Update — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: The `update_creator_ad_settings` function in `app/services/creator_ad_prefs.py` is supposed to accept a partial PATCH payload — updating only the fields that the creator explicitly sends. In practice the function performs a full `PutItem` operation, which atomically replaces the entire DynamoDB item. Although the code reads the existing item first and merges dictionaries, the merge is not performed atomically with the write; a concurrent write between the read and the `PutItem` can be silently lost. More practically, the merge logic means that if a creator's record in DynamoDB contains any extra attribute (e.g., a future feature flag written by another code path), a PATCH call strips it. There is also no DynamoDB `ConditionExpression` to guard against a lost-update race.

- **Severity**: HIGH
- **Source ticket**: ADS-003
- **Status**: Open
- **Owning area**: Ads Platform / Creator Ad Preferences
- **Effort**: S
- **Claim verdict**: CLAIM CORRECTED — the original ticket states the function does a bare PutItem "not partial update" without the read-merge. The actual code at `app/services/creator_ad_prefs.py:53–61` does read the existing item and merges before writing. However, the write is still a full `PutItem` rather than an `UpdateExpression`, so the concern is valid: the read-then-PutItem pattern has a TOCTOU race and will silently clobber concurrent writes. The fix the ticket suggests (use `UpdateExpression SET` for non-None fields only) is still the correct remedy.

**One-line impact**: Concurrent PATCH requests or interleaved writes from other services can silently overwrite each other's ad-settings changes, corrupting creator preferences and potentially re-enabling ads on a creator who explicitly disabled them.

**Related tickets**: ADS-003 (source), GAP-0042 (category enforcement depends on correct settings storage), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### The problematic function

`app/services/creator_ad_prefs.py:41–62`:

```python
def update_creator_ad_settings(creator_sub: str, data: CreatorAdSettingsIn) -> Dict[str, Any]:
    """Update ad settings for a creator."""
    updates: Dict[str, Any] = {}
    if data.allow_ads is not None:
        updates["allow_ads"] = data.allow_ads
    if data.allowed_ad_categories is not None:
        updates["allowed_ad_categories"] = data.allowed_ad_categories
    if data.min_cpm_cents is not None:
        updates["min_cpm_cents"] = data.min_cpm_cents
    updates["updated_at"] = now_ts()

    # Read existing to merge
    existing = T.billing.get_item(
        Key={"pk": f"USER#{creator_sub}", "sk": "AD_SETTINGS"}
    ).get("Item", {})

    merged = {**existing, **updates}
    merged["pk"] = f"USER#{creator_sub}"
    merged["sk"] = "AD_SETTINGS"

    T.billing.put_item(Item=merged)
    return {"ok": True}
```

The code performs three separate DynamoDB calls separated by application-level logic:

1. `get_item` — reads the current item (line 53).
2. Dictionary merge in Python memory (lines 57–59) — completely unprotected.
3. `put_item` — overwrites the full item (line 61).

Between steps 1 and 3, any concurrent writer (a second PATCH from the same creator's mobile device, an admin override, or another service) can write a new version of the item. When step 3 executes, the outcome of that concurrent write is unconditionally overwritten, producing a last-write-wins race with no protection.

### Input model

`app/models.py:5059–5063`:

```python
class CreatorAdSettingsIn(BaseModel):
    allow_ads: Optional[bool] = None
    allowed_ad_categories: Optional[List[str]] = None
    min_cpm_cents: Optional[int] = Field(default=None, ge=0)
```

All three fields are `Optional`, so a legitimate PATCH payload of `{"allow_ads": false}` sends `allowed_ad_categories=None` and `min_cpm_cents=None`. The guard conditions on lines 46–49 correctly exclude `None` fields from `updates`, but the merge step still reconstructs the entire item in memory, and the subsequent `put_item` replaces the item wholesale. Any attribute written to `AD_SETTINGS` by a different code path (e.g., a future `ad_revenue_share` flag) and not present in `CreatorAdSettingsIn` would survive only if the existing item already contains it — which it will, via the merge, until the next concurrent write.

### Race condition scenario

1. Creator A sends `PATCH allow_ads=false` at T=0. Code reads item at T=1.
2. Admin script writes `allowed_ad_categories=["sports"]` directly at T=2.
3. Creator A's `put_item` fires at T=3, overwriting the admin write with the version read at T=1. `allowed_ad_categories` reverts to `[]`.

### DynamoDB table

The `AD_SETTINGS` item lives in the `billing` table (`app/core/tables.py` → `T.billing`, backed by `S.billing_table_name`). The billing table has no TTL attribute and no conditional-write guards in the current schema definition at `scripts/local-ddb-init.py:64`.

## 3. Impact / Exploit / Blast Radius

**Data integrity**: Any fields written to the `AD_SETTINGS` DynamoDB item that are not part of the `CreatorAdSettingsIn` model are vulnerable to silent truncation during a concurrent PATCH. Future model extensions (e.g., an `nsfw_ads_enabled` flag) become unreliable the moment two writes race.

**Financial / compliance**: If `allow_ads=True` is silently restored after a creator explicitly opted out (due to a lost write from a race or interleaved admin action), the platform serves ads the creator did not consent to — a direct contractual and regulatory violation. Ad revenue is charged to advertisers for impressions the creator never authorised.

**Availability**: No service disruption in isolation, but the silent data corruption is difficult to detect without explicit audit logging of `AD_SETTINGS` writes. Creators submitting DMCA / opt-out complaints cannot rely on the setting taking effect consistently.

**Blast radius**: Every creator who has ever set ad preferences is affected. The `billing` table is the single-table store for all financial records; the `AD_SETTINGS` SK prefix co-exists with payment method rows, ledger entries, and subscription records. A broken `put_item` against this table in an unexpected scenario could theoretically corrupt adjacent records if the PK/SK construction were ever wrong (currently it is correct, but the pattern is fragile).

## 4. Fix Design (code-level)

### Replace PutItem with conditional UpdateExpression

The correct fix is to build a DynamoDB `UpdateExpression` that sets only the non-`None` fields received in the request. This eliminates the read-then-write race entirely because `update_item` with `SET` performs an atomic server-side field merge.

**Replacement for `update_creator_ad_settings` in `app/services/creator_ad_prefs.py`**:

```python
def update_creator_ad_settings(creator_sub: str, data: CreatorAdSettingsIn) -> Dict[str, Any]:
    """Update ad settings for a creator using atomic UpdateExpression (no read-then-write race)."""
    set_parts: list[str] = []
    expr_names: dict[str, str] = {}
    expr_values: dict[str, Any] = {}

    field_map = {
        "allow_ads": data.allow_ads,
        "allowed_ad_categories": data.allowed_ad_categories,
        "min_cpm_cents": data.min_cpm_cents,
    }
    for idx, (field, value) in enumerate(field_map.items()):
        if value is None:
            continue
        name_alias = f"#f{idx}"
        val_alias = f":v{idx}"
        expr_names[name_alias] = field
        expr_values[val_alias] = value
        set_parts.append(f"{name_alias} = {val_alias}")

    if not set_parts:
        return {"ok": True}  # Nothing to update; avoid empty UpdateExpression error

    # Always stamp updated_at
    expr_names["#ua"] = "updated_at"
    expr_values[":ua"] = now_ts()
    set_parts.append("#ua = :ua")

    T.billing.update_item(
        Key={"pk": f"USER#{creator_sub}", "sk": "AD_SETTINGS"},
        UpdateExpression="SET " + ", ".join(set_parts),
        ExpressionAttributeNames=expr_names,
        ExpressionAttributeValues=expr_values,
    )
    return {"ok": True}
```

Key properties of this fix:

- **Atomic**: `update_item` applies the `SET` expressions atomically on the DynamoDB server side. No race between read and write.
- **Partial**: Only the fields present in the request payload (non-`None`) are touched. Existing attributes not in the model are preserved.
- **No existing-item read**: Eliminates the extra `get_item` round-trip, reducing latency and cost.
- **Empty-payload guard**: If the caller sends a payload with no non-`None` fields, the function returns early rather than issuing an `UpdateExpression` with no `SET` clauses (which DynamoDB rejects).

### Dev/Prod parity (SECOPS-007)

`T.billing` resolves to the same DynamoDB client in both dev (DynamoDB Local, port 8001) and production (AWS DynamoDB). The fix uses only standard `update_item` with `SET` expressions, which DynamoDB Local supports fully. No mock-specific branching is needed. The `BILLING_TABLE_NAME` environment variable controls the table name in both environments; the fix is table-name agnostic.

### Backward compatibility

The `AD_SETTINGS` DynamoDB item is written with `pk=USER#{creator_sub}`, `sk=AD_SETTINGS`. Items that already exist in production have exactly the three preference fields plus `updated_at`. The new `update_item` call will set only the fields provided, leaving all existing fields intact — including any future additions. No migration is required.

### Alternatives considered

- **Optimistic locking via `version` attribute**: Add a numeric `version` to the item and use `ConditionExpression=#version = :expected_version`. More robust for multi-writer scenarios but requires the caller to supply the current version, adding API complexity. For a single-owner settings record (creator owns their own AD_SETTINGS), an atomic `update_item` is sufficient without versioning overhead.
- **Keep PutItem but add ConditionExpression**: Could add `ConditionExpression="attribute_not_exists(pk) OR updated_at <= :read_ts"` to guard against stale writes. Rejected because it still requires the read round-trip, and the condition logic is fragile (clock skew, same-second writes).

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline — fails before fix, passes after)

Add to `tests/test_creator_ad_prefs.py`:

```python
import threading
import pytest
from unittest.mock import patch, MagicMock
from app.services.creator_ad_prefs import update_creator_ad_settings
from app.models import CreatorAdSettingsIn

def test_partial_update_does_not_clobber_unrelated_fields(ddb_mock):
    """PATCH with only allow_ads=False must not clear allowed_ad_categories."""
    creator_sub = "test_creator_001"
    # Seed full settings
    from app.core.tables import T
    T.billing.put_item(Item={
        "pk": f"USER#{creator_sub}",
        "sk": "AD_SETTINGS",
        "allow_ads": True,
        "allowed_ad_categories": ["sports", "tech"],
        "min_cpm_cents": 200,
        "updated_at": 1700000000,
    })

    # PATCH only allow_ads
    result = update_creator_ad_settings(
        creator_sub, CreatorAdSettingsIn(allow_ads=False)
    )
    assert result == {"ok": True}

    # allowed_ad_categories and min_cpm_cents must survive
    item = T.billing.get_item(
        Key={"pk": f"USER#{creator_sub}", "sk": "AD_SETTINGS"}
    )["Item"]
    assert item["allow_ads"] is False
    assert item["allowed_ad_categories"] == ["sports", "tech"]
    assert int(item["min_cpm_cents"]) == 200


def test_concurrent_updates_do_not_race(ddb_mock):
    """Two concurrent PATCHes must each set their field without clobbering the other."""
    creator_sub = "test_creator_002"
    from app.core.tables import T
    T.billing.put_item(Item={
        "pk": f"USER#{creator_sub}",
        "sk": "AD_SETTINGS",
        "allow_ads": True,
        "allowed_ad_categories": [],
        "min_cpm_cents": 0,
        "updated_at": 1700000000,
    })

    errors = []
    def patch_allow_ads():
        try:
            update_creator_ad_settings(
                creator_sub, CreatorAdSettingsIn(allow_ads=False)
            )
        except Exception as e:
            errors.append(e)

    def patch_min_cpm():
        try:
            update_creator_ad_settings(
                creator_sub, CreatorAdSettingsIn(min_cpm_cents=500)
            )
        except Exception as e:
            errors.append(e)

    t1 = threading.Thread(target=patch_allow_ads)
    t2 = threading.Thread(target=patch_min_cpm)
    t1.start(); t2.start()
    t1.join(); t2.join()

    assert not errors
    item = T.billing.get_item(
        Key={"pk": f"USER#{creator_sub}", "sk": "AD_SETTINGS"}
    )["Item"]
    # Both fields must reflect their respective PATCHes
    assert item["allow_ads"] is False
    assert int(item["min_cpm_cents"]) == 500
```

**Fails before fix**: The first test fails because the old code's read-then-merge-then-PutItem path reads `allowed_ad_categories: ["sports", "tech"]` from DynamoDB and merges it into the PutItem payload — so the item survives in this test (the single-threaded case is accounted for by the merge). However, the concurrent test fails non-deterministically because DynamoDB Local processes the two `put_item` calls serially, and the last one wins, overwriting the field set by the first.

**Passes after fix**: Both tests pass because `update_item` with `SET` is atomic; each thread sets exactly its own field without reading or overwriting the other.
