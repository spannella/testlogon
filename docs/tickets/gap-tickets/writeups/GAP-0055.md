# GAP-0055: Webhook System Entirely Absent for Ad Events — Remediation Write-up

## 1. Summary & Classification

**Gap**: The advertiser API (ADS-011) has no webhook notification system. Advertisers
cannot register a callback URL to receive real-time notifications when campaign-lifecycle or
billing events occur (impressions, budget exhausted, campaign paused, creative approved,
etc.). The general-purpose webhook infrastructure in `app/services/webhook_service.py` is
fully implemented and already supports per-user endpoint registration, signed delivery, and
retry logic, but the ad platform has zero ad-specific event types registered in it and no
service layer connecting ad events to webhook dispatch.

**Severity**: HIGH  
**Source ticket**: ADS-011  
**Owning area**: Advertiser API / Ad Platform  
**Status**: Open — claim confirmed. `find app/services -name "ad_webhooks*"` returns
nothing. `grep -rn "ad\." webhook_service.py` shows no ad event types. The existing
`advertiser_api_router` has no webhook endpoints. The ticket's claim is accurate.

**Important clarification**: The ticket states "no ad_webhooks.py, no DDB table, no CRUD
endpoints, no delivery mechanism." The first three are correct: no `ad_webhooks.py`
service file exists, no ad-specific DDB table exists, and no webhook CRUD endpoints are
wired into the advertiser API router. However, the claim of "no delivery mechanism" is
partially inaccurate: a robust, general-purpose delivery mechanism already exists in
`app/services/webhook_service.py` (including DynamoDB-backed endpoint storage in
`webhook_endpoints` and `webhook_deliveries` tables, HMAC-SHA256 signature, exponential
backoff retry, and `dispatch_webhook_event` dispatch). The fix should reuse this
infrastructure rather than implement a parallel one from scratch.

**Related tickets**: GAP-0049 (platform revenue share not written), GAP-0054 (per-creator
revenue share broken), ADS-011 (advertiser programmatic API source ticket).

## 2. Current-State Investigation (root cause)

### The general webhook system is complete and operational

`app/services/webhook_service.py` contains:
- `WEBHOOK_EVENT_TYPES` / `WEBHOOK_EVENT_TYPES_V2` (lines 24–165): registry of all event
  types. No `ad.*` or `campaign.*` types are present.
- `create_webhook_endpoint`, `list_webhook_endpoints`, `delete_webhook_endpoint` (lines
  190–400): endpoint CRUD wired to the `webhook_endpoints` DDB table.
- `dispatch_webhook_event(event_type, user_sub, data)` (line 532): enqueues signed
  delivery records in `webhook_deliveries` for any subscribed endpoint.
- `deliver_webhook` (line 591): HTTP POST with v1/v2 HMAC signature.

The router that exposes these to UI users exists at `app/routers/webhooks.py`
(confirmed by `grep "webhooks" app/main.py`).

### Ad event types are absent from the registry

No `ad.*` event types are registered in either `WEBHOOK_EVENT_TYPES` or
`WEBHOOK_EVENT_TYPES_V2`. Running:
```
grep -n '"ad\.' app/services/webhook_service.py
grep -n '"campaign\.' app/services/webhook_service.py
```
Both return zero results. This means `dispatch_webhook_event` would simply return `[]`
even if called with an ad event type, because the `EVENT#{event_type}` GSI partition
would have no matching subscriptions.

### No CRUD endpoints in the advertiser API

`app/routers/advertiser_api.py` defines routes for account, campaigns, creatives, budget,
and analytics (lines 36–214). There are no routes for:
- `POST /api/v1/ads/webhooks` — register a webhook endpoint
- `GET /api/v1/ads/webhooks` — list webhook endpoints
- `DELETE /api/v1/ads/webhooks/{id}` — delete a webhook endpoint
- `POST /api/v1/ads/webhooks/{id}/test` — send a test event

### No ad service layer calling dispatch_webhook_event

`app/services/ad_billing.py` does not import or call `dispatch_webhook_event`. Neither
does `app/services/ad_campaigns.py`. The only other existing domain that wires events is
`app/services/kyc_webhooks.py`, which calls `dispatch_webhook_event` from `emit_kyc_event`
— this is the reference implementation pattern.

### No ad_webhooks service module

`find app/services -name "ad_webhooks*"` returns nothing. The service layer that would:
(a) define ad event types, (b) provide `emit_ad_event(event_type, user_sub, data)`, and
(c) be called from billing and campaign lifecycle functions — does not exist.

## 3. Impact / Exploit / Blast Radius

**Advertisers** using the programmatic API have no real-time visibility into campaign
events. This is a standard SaaS advertiser API requirement; all major ad platforms
(Google Ads, Meta Ads API, Twitter Ads) provide webhook/callback notifications for at
minimum budget exhaustion, campaign pause, and creative approval events.

**Specific missing notifications**:
- `ad.campaign.budget_exhausted` — advertiser must poll to detect budget exhaustion instead
  of receiving a push notification; this delays ad spend adjustment.
- `ad.campaign.paused` / `ad.campaign.completed` — advertiser's integration cannot react to
  automatic campaign state changes.
- `ad.creative.approved` / `ad.creative.rejected` — advertiser must poll moderation status.
- `ad.billing.invoice_ready` — monthly invoice generated; no push notification.
- `ad.impression.threshold` (milestone notifications) — advertiser cannot receive
  reach-milestone alerts.

**Operational impact**: Advertisers running automated bidding or campaign management
systems (which is the entire target audience of ADS-011's programmatic API) cannot build
reactive integrations. This is a table-stakes feature gap that directly limits the
enterprise advertiser segment.

**No security exploit**: The absence of a feature is not an exploitable vulnerability, but
the platform has a contract exposure if advertiser agreements reference real-time
notification SLAs.

## 4. Fix Design (code-level)

### Architecture decision: reuse the existing webhook infrastructure

The general-purpose `webhook_service.py` already provides everything needed. The fix
consists of:

1. Registering ad event types in the event registry.
2. Creating `app/services/ad_webhooks.py` as a thin dispatch adapter (same pattern as
   `kyc_webhooks.py`).
3. Adding webhook CRUD endpoints to `advertiser_api_router` (delegating to the existing
   `webhook_service` functions).
4. Wiring `emit_ad_event` calls from ad billing and campaign lifecycle service functions.

No new DynamoDB tables are needed: ad webhook endpoints and deliveries use the existing
`webhook_endpoints` and `webhook_deliveries` tables. The event-type namespace prefix
(`ad.`) provides adequate partition isolation.

### Step 2: Create app/services/ad_webhooks.py

```python
"""Ad platform webhook event dispatch (ADS-011 / GAP-0055).

Reuses the general webhook_service infrastructure. Callers import and call
emit_ad_event(); this module handles event-type validation and dispatch.
"""
from __future__ import annotations
import logging
from typing import Any, Dict

from app.services.webhook_service import AD_WEBHOOK_EVENT_TYPES, dispatch_webhook_event

logger = logging.getLogger(__name__)


def is_ad_event_type(event_type: str) -> bool:
    return event_type in AD_WEBHOOK_EVENT_TYPES


def emit_ad_event(event_type: str, account_owner_sub: str, data: Dict[str, Any]) -> None:
    """Dispatch an ad platform webhook event. Best-effort; never raises.

    account_owner_sub: the user_sub of the advertiser account owner.
    """
    if not is_ad_event_type(event_type):
        logger.warning("emit_ad_event: unknown event_type=%s", event_type)
        return
    try:
        ids = dispatch_webhook_event(event_type, account_owner_sub, data)
        if ids:
            logger.debug("ad_webhook_dispatched event=%s deliveries=%d", event_type, len(ids))
    except Exception:
        logger.warning("emit_ad_event_failed event_type=%s sub=%s",
                       event_type, account_owner_sub, exc_info=True)
```

### Step 4: Add webhook CRUD endpoints to advertiser_api_router

The `webhook_service` already has `create_webhook_endpoint`, `list_webhook_endpoints`,
`delete_webhook_endpoint`, and `send_test_event`. Expose them under
`/api/v1/ads/webhooks`:

```python
# In app/routers/advertiser_api.py

from app.models import WebhookEndpointCreate  # reuse existing model

@advertiser_api_router.post("/webhooks", status_code=201)
async def create_ad_webhook(
    body: WebhookEndpointCreate,
    principal: Dict[str, Any] = Depends(require_api_key_principal),
):
    svc.require_scope(principal, "ads:manage")
    account = svc.resolve_account(principal)
    from app.services.webhook_service import create_webhook_endpoint
    # Restrict subscriptions to ad.* event types only
    allowed_events = [e for e in (body.events or []) if e.startswith("ad.")]
    return create_webhook_endpoint(account["owner_sub"], body.url,
                                    allowed_events, body.description or "")


@advertiser_api_router.get("/webhooks")
async def list_ad_webhooks(principal: Dict[str, Any] = Depends(require_api_key_principal)):
    svc.require_scope(principal, "ads:read")
    account = svc.resolve_account(principal)
    from app.services.webhook_service import list_webhook_endpoints
    endpoints = list_webhook_endpoints(account["owner_sub"])
    ad_endpoints = [e for e in endpoints
                    if any(ev.startswith("ad.") for ev in e.get("events", []))]
    return {"data": ad_endpoints, "count": len(ad_endpoints)}


@advertiser_api_router.delete("/webhooks/{endpoint_id}", status_code=204)
async def delete_ad_webhook(
    endpoint_id: str,
    principal: Dict[str, Any] = Depends(require_api_key_principal),
):
    svc.require_scope(principal, "ads:manage")
    account = svc.resolve_account(principal)
    from app.services.webhook_service import delete_webhook_endpoint
    delete_webhook_endpoint(account["owner_sub"], endpoint_id)


@advertiser_api_router.post("/webhooks/{endpoint_id}/test", status_code=200)
async def test_ad_webhook(
    endpoint_id: str,
    principal: Dict[str, Any] = Depends(require_api_key_principal),
):
    svc.require_scope(principal, "ads:manage")
    account = svc.resolve_account(principal)
    from app.services.ad_webhooks import emit_ad_event
    emit_ad_event("ad.webhook.test", account["owner_sub"],
                  {"endpoint_id": endpoint_id, "message": "Test event from advertiser API"})
    return {"ok": True}
```

### Step 5: Add ads:webhook scope (optional)

The existing scope model (`ads:read`, `ads:manage`, `ads:serve`) does not include a
dedicated webhook scope. For consistency with the KYC pattern (`kyc:webhook`), add
`ads:webhook` to `CANONICAL_API_KEY_CAPABILITIES` in
`app/services/api_key_capabilities.py`. This allows advertisers to issue API keys with
webhook-only permissions (register/manage endpoints without campaign write access). This is
a nice-to-have and can be deferred.

### Dev / Prod parity (SECOPS-007)

The fix introduces no new AWS services. All DynamoDB access uses the existing
`T.webhook_endpoints` and `T.webhook_deliveries` table handles (via `app/core/tables.py`).
In dev, these resolve to DynamoDB Local. In prod, real DynamoDB is used. Outbound HTTP
delivery (`deliver_webhook`) uses `httpx` — in dev this is intercepted by the existing
webhook delivery worker. No `if dev_mode:` branches are needed. The `emit_ad_event`
function is best-effort and never raises, so it cannot break billing regardless of
environment. SECOPS-007 is satisfied.

### Manual QA steps

1. Create an advertiser account and obtain an API key with `ads:manage` scope.
2. Register a webhook via `POST /api/v1/ads/webhooks` with a local ngrok or requestbin URL
   for `ad.campaign.completed` and `ad.billing.budget_alert`.
3. Send a test event via `POST /api/v1/ads/webhooks/{endpoint_id}/test`. Verify the POST
   is received at the target URL with correct HMAC signature.
4. Create a campaign with a small budget (e.g., 1 cent). Trigger an impression charge that
   exceeds the budget. Verify `ad.billing.budget_alert` and `ad.campaign.completed` events
   are received at the target URL.
5. Verify that registering an endpoint with `events: ["message.created"]` (non-ad event)
   is rejected or silently filtered to only `ad.*` events.

### Observability

The existing webhook delivery infrastructure already emits structured log entries for
each delivery attempt (success/failure, HTTP status, latency). Add a
`Prometheus counter` `ad_webhook_events_dispatched_total{event_type}` in `emit_ad_event`
to track dispatch frequency per event type. Wire the webhook delivery worker health check
to emit a `webhook_delivery_queue_depth` gauge.

### Rollout

- **Effort**: L (3–5 days: event type registration + service module + CRUD endpoints +
  wiring into billing/campaign lifecycle + tests)
- **Risk**: LOW for existing functionality (the fix is purely additive; no existing
  behavior changes). Moderate risk for the billing wiring: `emit_ad_event` calls inside
  billing functions must be inside `try/except` to avoid breaking charge processing if
  dispatch fails.
- **Phased rollout**:
  - Phase 1: Register ad event types + create `ad_webhooks.py` + add CRUD endpoints (no
    billing wiring). Advertisers can register endpoints and receive test events.
  - Phase 2: Wire `emit_ad_event` into `_check_budget_and_alert` and campaign status
    transitions. Enables the two highest-value events: budget exhaustion and campaign
    pause/resume.
  - Phase 3: Wire creative approval/rejection and invoice-ready events.
- **Sequencing**: No dependency on GAP-0051, 0052, 0053, or 0054. Can be developed
  in parallel. The existing webhook delivery worker must be running (confirm via
  `just status`).
- **Rollback**: Remove the `ad_webhooks.py` module, remove the router endpoints, remove
  ad event types from `WEBHOOK_EVENT_TYPES_V2`. No DynamoDB schema changes are required
  since the existing webhook tables are shared. Any already-registered `ad.*` subscriptions
  will become non-functional after rollback but will not cause errors (delivery lookup
  would simply find no matching endpoints).
