# GAP-0253: `get_verified_docs_for_case` Helper Missing — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase; no prior investigation doc exists.

## 1. Summary & Classification

**Claim from ticket**: The helper method `get_verified_docs_for_case` is missing from the
KYC residency store. The fix is to add it, querying the ByStatus GSI with
`status=verified` and a `FilterExpression` on `case_id`.

**Verdict: Claim CONFIRMED.** Searching the entire `app/` directory tree for the string
`get_verified_docs_for_case` returns zero results. The method does not exist in
`app/services/kyc_residency.py` or anywhere else. The `KycResidencyStore` class (line 317)
does have `list_by_status` (line 454) and `list_documents_for_case` (line 440), but no
convenience method combining the two — i.e., no way to ask "does this case have at least
one verified residency document?" without either (a) fetching all documents for the case
and filtering client-side, or (b) scanning the entire `verified` partition of the ByStatus
GSI and filtering by `case_id`.

- **Severity**: HIGH — required by GAP-0252 (enhanced/high_risk readiness gate) and
  GAP-0254 (ResidencyVerificationTab). Without this helper, the readiness gate cannot be
  extended as required by AML/CDD compliance, and the admin tab cannot display per-case
  residency verification state.
- **Source ticket**: KYC-004
- **Owning area**: Backend / `app/services/kyc_residency.py`, `KycResidencyStore`
- **Related tickets**: GAP-0252 (readiness gate), GAP-0254 (admin UI tab), SECOPS-007
- **Claim accuracy**: Fully confirmed. The method is absent.

## 2. Current-State Investigation (root cause)

### Existing `KycResidencyStore` methods

`app/services/kyc_residency.py` lines 317–693 define `KycResidencyStore`. The relevant
existing lookup methods are:

```python
# line 440 — fetches all documents for a case (all statuses)
def list_documents_for_case(self, case_id: str) -> list[dict[str, Any]]:
    try:
        resp = self._table.query(
            IndexName="ByCase",
            KeyConditionExpression=Key("case_id").eq(case_id),
            ScanIndexForward=False,
        )
        return list(resp.get("Items", []))
    except Exception:
        resp = self._table.scan()
        items = [i for i in resp.get("Items", []) if i.get("case_id") == case_id]
        ...
        return items

# line 454 — fetches all documents of a given status globally (all cases)
def list_by_status(self, status: str, *, limit: int = 100) -> list[dict[str, Any]]:
    ...
    resp = self._table.query(
        IndexName=S.kyc_residency_documents_status_index_name,
        KeyConditionExpression=Key("status").eq(st),
        ...
    )
    ...
```

Neither method provides "all verified documents for case X". The caller must choose:

1. **Use `list_documents_for_case`** and filter by `status == "verified"` in Python: this
   is correct and efficient when the number of residency documents per case is small (which
   it typically is — a user uploads one or two documents per case). This is the recommended
   approach.

2. **Use `list_by_status("verified")`** and filter by `case_id` in Python: this scans all
   verified documents across all cases. For a large production system with tens of thousands
   of verified documents this is unacceptably expensive. The ticket proposes this approach
   ("query the ByStatus GSI with FilterExpression on case_id"), but the correct approach is
   option 1.

### ByCase GSI structure

The `kyc_residency_documents` table is keyed by `document_id` (PK). The `ByCase` GSI uses
`case_id` as the partition key (referenced at line 428–430). Querying by `case_id` is an
efficient O(documents per case) query — typically 1–3 documents. Filtering by
`status == "verified"` on the result set is a constant-time in-Python filter on a small
list.

### Why the ticket's proposed implementation is wrong

The ticket says: "add `get_verified_docs_for_case(case_id)` querying the ByStatus GSI with
`status=verified` and `FilterExpression: case_id`".

DynamoDB `FilterExpression` is applied _after_ the page is fetched (it does not reduce
read-capacity consumption). Querying `ByStatus GSI PK=verified` with a filter for
`case_id` on a production table with 50,000 verified documents would consume all those
read-capacity units on every readiness check, even though the desired result is 0 or 1
documents. This is the "DDB FilterExpression doesn't reduce page size" anti-pattern
documented in the project's CLAUDE.md.

The correct implementation queries `ByCase GSI PK=case_id` (O(docs per case), typically
1–3) and filters by `status == "verified"` in Python on the result.

## 3. Impact / Exploit / Blast Radius

**GAP-0252 dependency**: The enhanced/high_risk readiness gate (GAP-0252) cannot be
implemented without this helper. All `enhanced` and `high_risk` KYC users are currently
able to submit without residency verification — a compliance gap that persists until both
this helper and GAP-0252 are deployed.

**GAP-0254 dependency**: The `ResidencyVerificationTab` in the admin case detail page
(GAP-0254) needs to call this helper to populate the two-column address comparison UI.
Without it the tab has no data source.

**Test coverage gap**: `list_documents_for_case` is already tested indirectly through the
residency router. Adding `get_verified_docs_for_case` as a thin filter wrapper expands
that coverage.

**No security risk**: This is a missing read helper, not a missing auth or authorization
check.

## 4. Fix Design (code-level)

### 4a. Add `get_verified_docs_for_case` to `KycResidencyStore`

Insert the following method in `app/services/kyc_residency.py` after `list_documents_for_case`
(line 451, just before `list_by_status`):

```python
def get_verified_docs_for_case(self, case_id: str) -> list[dict[str, Any]]:
    """Return all residency documents with status=verified for the given case.

    Queries the ByCase GSI (O(docs per case), typically 1-3 items) and
    filters in Python for status=verified. This is intentionally NOT
    implemented via the ByStatus GSI + FilterExpression, which would scan
    the entire 'verified' partition (potentially tens of thousands of items)
    to find the one or two documents for a specific case.
    """
    docs = self.list_documents_for_case(case_id)
    return [d for d in docs if str(d.get("status") or "") == STATUS_VERIFIED]
```

This is a six-line addition that reuses the existing `list_documents_for_case` path and
requires no new DynamoDB access patterns, no new indices, and no changes to the table
schema.

### 4b. Optional: add `get_latest_verified_doc_for_case`

For the admin tab (GAP-0254) which needs to display the most recently verified document's
extracted address and match result, a convenience wrapper is useful:

```python
def get_latest_verified_doc_for_case(self, case_id: str) -> dict[str, Any] | None:
    """Return the most recently verified residency document for the case, or None."""
    docs = self.get_verified_docs_for_case(case_id)
    if not docs:
        return None
    # list_documents_for_case returns items sorted by created_at descending
    return docs[0]
```

### 4c. Dev/Prod parity (SECOPS-007)

`get_verified_docs_for_case` calls `list_documents_for_case`, which:

1. Queries `T.kyc_residency_documents` using the `ByCase` GSI.
2. Falls back to a full `scan()` filtered by `case_id` in Python when the GSI query
   raises an exception (the except block at line 449–452 of the existing code).

Both paths use the same boto3 table handle (`T.kyc_residency_documents`) which resolves to
DynamoDB Local in dev and AWS DynamoDB in production. No environment-specific branches are
introduced by this fix. The fallback `scan()` runs in both environments — in dev it is the
primary path when DynamoDB Local's GSI is not configured; in production it is a safety
valve for transient failures.

### Alternatives considered

- **Query ByStatus GSI with FilterExpression on case_id** (as the ticket proposes): Scans
  the entire `verified` partition on every readiness check. Rejected as O(total verified
  docs) per call — a read-capacity amplification attack surface and a scaling hazard.
- **Add a new DynamoDB secondary index `ByCaseAndStatus` (PK=case_id, SK=status)**: Would
  allow an efficient query but requires a DynamoDB schema change, table re-creation (since
  DynamoDB does not support adding GSIs with composite sort keys to existing tables without
  data migration), and updates to `scripts/local-ddb-init.py`. Rejected as overengineering
  for a dataset that averages 1–3 documents per case.
- **Store verified-doc-count on the case object**: Denormalize the count into the
  `kyc_cases` table. Rejected — introduces a consistency hazard (the denormalized count
  can diverge from the actual residency table) and requires updating `run_extraction` and
  `review_document` to maintain the counter.
