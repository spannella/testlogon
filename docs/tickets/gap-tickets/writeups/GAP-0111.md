# GAP-0111: Status-filter list exposes all creators' sessions — Remediation Write-up

## 1. Summary & Classification

**Bug statement**: The `GET /ui/broadcast/sessions?status=live` endpoint allows any authenticated
user — including non-admin broadcasters — to enumerate every session on the platform that matches a
given status value. A broadcaster querying `?status=live` receives a full cross-creator list,
leaking the session identifiers, titles, viewer counts, privacy settings, stream-key references,
and scheduling data of every other creator currently live.

- **Severity**: HIGH
- **Source ticket**: BCAST-001 (second-pass as-built review)
- **GAP ID**: GAP-0111
- **Owning area**: Broadcast router / session discovery
- **Status**: Open
- **Effort**: S

**Claim verdict**: Confirmed. The code at `app/routers/broadcast.py:315-316` branches on
`status_filter` and calls `list_sessions_by_status(status_filter, limit=limit)` with no caller
identity passed. The function queries the `ByStatusCreatedAt` GSI without a creator constraint,
returning records for every creator.

**Impact in one line**: Any authenticated broadcaster can trivially enumerate all live (or
scheduled/ended) sessions platform-wide, exposing creator identity, session metadata, and privacy
configuration to peers.

**Related tickets**: BCAST-001, SECOPS-007 (dev/prod parity), GAP-0112, GAP-0113, GAP-0115
(related broadcast access-control gaps in the same file).

## 2. Current-State Investigation (root cause)

### The faulty branch in the router

`app/routers/broadcast.py`, lines 309–320:

```python
@router.get("/sessions", response_model=BroadcastSessionListOut)
def list_sessions_route(
    status_filter: Optional[str] = Query(default=None, alias="status"),
    limit: int = Query(default=50, ge=1, le=200),
    ctx: dict = Depends(_ctx),
):
    if status_filter:
        result = list_sessions_by_status(status_filter, limit=limit)   # line 316 — no creator scope
    else:
        result = list_sessions_by_creator(ctx["user_sub"], limit=limit)  # correctly scoped
    items = [_to_session_out(s) for s in result["items"]]
    return BroadcastSessionListOut(items=items, has_more=bool(result.get("cursor")))
```

The `else` branch is correct: it calls `list_sessions_by_creator` with the authenticated caller's
`user_sub`. The `if status_filter` branch, however, calls `list_sessions_by_status` and passes
**only** the status string — the caller identity is not used at all.

### The service function

`app/services/broadcast_store.py`, lines 423–440:

```python
def list_sessions_by_status(status: str, *, limit: int = 50, ...) -> Dict[str, Any]:
    kwargs: Dict[str, Any] = {
        "IndexName": "ByStatusCreatedAt",
        "KeyConditionExpression": Key("status").eq(status),
        "Limit": limit,
        "ScanIndexForward": False,
    }
    resp = T.broadcast_sessions.query(**kwargs)
    items = [session_from_item(i) for i in resp.get("Items", [])]
    return {"items": items, "cursor": resp.get("LastEvaluatedKey")}
```

The `ByStatusCreatedAt` GSI is keyed on `status` (partition) + `created_at` (sort). Querying it
with only `Key("status").eq("live")` returns every live session across every creator. There is no
`FilterExpression` that restricts to the caller's `created_by` value, so the entire live feed is
returned.

### Why admin callers are fine, regular users are not

The `_require_operator_role` guard is used on other admin-only list endpoints (e.g. `/admin/audit`
at line 539). The `list_sessions_route` handler does not call that guard at all — there is no
distinction between a regular broadcaster and an admin here. The status-filter path was clearly
intended as an admin/discovery feed but was never gated.

### Dev vs prod behaviour

The DynamoDB query runs identically in dev (DynamoDB Local on port 8001) and production (AWS
DynamoDB). The `ByStatusCreatedAt` GSI must already exist in production (it is the designed
discovery mechanism). The bug is therefore live in production at full severity.

## 3. Impact / Exploit / Blast Radius

### Concrete exploit

1. Attacker creates any account and obtains a valid `ui_session` cookie.
2. Issues `GET /ui/broadcast/sessions?status=live` (or `?status=scheduled`, `?status=ended`).
3. Response body contains up to 200 `BroadcastSessionOut` records covering **all creators** on the
   platform. Each record includes:
   - `session_id`, `created_by` (creator's `user_sub`)
   - `title`, `description`
   - `broadcast_privacy_visibility` (public / private / unlisted) — exposes which sessions are
     private and therefore whose invite-only streams exist
   - `stream_key_ref` metadata
   - `viewer_count`, `health_status`, `scheduled_at`
4. Pagination via `cursor` allows the attacker to walk the entire session history.

### Who is affected

- **All creators** who have ever had a broadcast session, regardless of privacy setting. A creator
  who set a session to `visibility=private` to limit exposure is still listed.
- **High-profile / pseudonymous creators**: their `user_sub` (and any display information on the
  session) is linked to their live cadence and content metadata.
- **Business-intelligence leakage**: competitor broadcasters can map the full live schedule and
  popularity distribution of every creator on the platform.

### Compliance

The session record contains PII-adjacent fields (`created_by` = Cognito user sub, `title`,
`description`). Exposure to non-authorized peers without consent is inconsistent with GDPR Article
5 (data minimisation) and may trigger notification obligations depending on jurisdiction.

## 4. Fix Design (code-level)

### Guiding principle

For non-admin callers, the status filter should still return only sessions belonging to the calling
user. Admin and root callers may legitimately need the platform-wide view. The fix therefore adds
a role check before deciding whether to apply the creator scope.

### Router change (`app/routers/broadcast.py`, around line 315)

Replace the unconditional cross-creator call with a scoped version for non-operators:

```python
@router.get("/sessions", response_model=BroadcastSessionListOut)
def list_sessions_route(
    status_filter: Optional[str] = Query(default=None, alias="status"),
    limit: int = Query(default=50, ge=1, le=200),
    ctx: dict = Depends(_ctx),
):
    is_operator = ctx.get("role") in {"admin", "root"}
    if status_filter:
        if is_operator:
            # Admins/root may query platform-wide by status
            result = list_sessions_by_status(status_filter, limit=limit)
        else:
            # Regular callers see only their own sessions filtered by status
            result = list_sessions_by_creator_and_status(
                ctx["user_sub"], status_filter, limit=limit
            )
    else:
        result = list_sessions_by_creator(ctx["user_sub"], limit=limit)
    items = [_to_session_out(s) for s in result["items"]]
    return BroadcastSessionListOut(items=items, has_more=bool(result.get("cursor")))
```

### New service function (`app/services/broadcast_store.py`)

The `ByCreatorCreatedAt` GSI already has `created_by` as its partition key. Add a `FilterExpression`
to narrow by status, or — if a `ByCreatorStatus` GSI exists — use a compound key condition. The
safest approach against the existing GSI layout is a FilterExpression (DynamoDB evaluates it
server-side, which is acceptable for the bounded result sizes of the broadcast use case):

```python
def list_sessions_by_creator_and_status(
    created_by: str,
    status: str,
    *,
    limit: int = 50,
    cursor: Optional[Dict[str, Any]] = None,
) -> Dict[str, Any]:
    """List sessions for a specific creator filtered by status.

    Uses the ByCreatorCreatedAt GSI with a FilterExpression on status.
    This is safe for broadcast session volumes (creators rarely exceed hundreds
    of sessions); a dedicated GSI can be added later for scale.
    """
    if not created_by or not status:
        raise HTTPException(status_code=400, detail="created_by and status are required")
    kwargs: Dict[str, Any] = {
        "IndexName": "ByCreatorCreatedAt",
        "KeyConditionExpression": Key("created_by").eq(created_by),
        "FilterExpression": Attr("status").eq(status),
        "Limit": limit,
        "ScanIndexForward": False,
    }
    if cursor:
        kwargs["ExclusiveStartKey"] = cursor
    resp = T.broadcast_sessions.query(**kwargs)
    items = [session_from_item(i) for i in resp.get("Items", [])]
    return {"items": items, "cursor": resp.get("LastEvaluatedKey")}
```

Note: `Attr` must be imported from `boto3.dynamodb.conditions` alongside the existing `Key` import.

### Dev/Prod parity (SECOPS-007)

No AWS-specific path is involved. Both dev (DynamoDB Local) and prod (AWS DynamoDB) use the same
boto3 query API. The `ByCreatorCreatedAt` GSI is already declared in `scripts/local-ddb-init.py`
and is assumed to exist in production. The new `FilterExpression` keyword works identically on both.
The `is_operator` check reads from the decoded `ui_access_token` JWT (`ctx["role"]`), which is
populated by `require_ui_session` and is the same in dev (seeded sessions) and prod (Cognito JWT).
No feature flag is needed because the fix is pure tightening of access control, not a new feature.

### Migration / backward compatibility

Admins who relied on the platform-wide status-filter query retain that ability. Regular broadcasters
who were (incorrectly) using `?status=live` to watch the whole platform lose that capability — but
that capability was never a documented or intended feature.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to a new file `tests/test_broadcast_list_sessions_access.py`:

```python
import pytest
from fastapi.testclient import TestClient
from unittest.mock import patch, MagicMock

from app.main import app

# ── helpers ──────────────────────────────────────────────────────────
def _session_ctx(role: str = "user", sub: str = "alice") -> dict:
    return {"user_sub": sub, "role": role, "admin_profile": None}

def _make_session(creator: str, status: str = "live"):
    m = MagicMock()
    m.id = f"sess_{creator}"
    m.created_by = creator
    m.status = status
    m.broadcast_privacy_visibility = "public"
    m.stream_key_ref = None
    m.title = f"Session by {creator}"
    return m

# ── test: non-admin gets only own sessions when status_filter is set ─
def test_status_filter_scoped_to_caller(monkeypatch):
    """Before fix: alice sees bob's session. After fix: alice only sees her own."""
    alice_session = _make_session("alice")
    bob_session   = _make_session("bob")

    monkeypatch.setattr(
        "app.routers.broadcast.list_sessions_by_status",
        lambda *a, **kw: {"items": [alice_session, bob_session], "cursor": None},
    )
    # After fix, this path is taken for non-operators:
    monkeypatch.setattr(
        "app.routers.broadcast.list_sessions_by_creator_and_status",
        lambda created_by, status, **kw: {
            "items": [s for s in [alice_session, bob_session] if s.created_by == created_by],
            "cursor": None,
        },
    )
    with patch("app.routers.broadcast._ctx", return_value=_session_ctx("user", "alice")):
        client = TestClient(app)
        resp = client.get("/ui/broadcast/sessions?status=live")
    assert resp.status_code == 200
    ids = [s["session_id"] for s in resp.json()["items"]]
    assert "sess_alice" in ids
    assert "sess_bob" not in ids   # FAILS before fix, passes after

# ── test: admin gets all sessions ────────────────────────────────────
def test_status_filter_admin_sees_all(monkeypatch):
    alice_session = _make_session("alice")
    bob_session   = _make_session("bob")

    monkeypatch.setattr(
        "app.routers.broadcast.list_sessions_by_status",
        lambda *a, **kw: {"items": [alice_session, bob_session], "cursor": None},
    )
    with patch("app.routers.broadcast._ctx", return_value=_session_ctx("admin", "charlie")):
        client = TestClient(app)
        resp = client.get("/ui/broadcast/sessions?status=live")
    assert resp.status_code == 200
    ids = [s["session_id"] for s in resp.json()["items"]]
    assert "sess_alice" in ids
    assert "sess_bob" in ids
```

**Fails-before**: The first test fails before the fix because `list_sessions_by_status` returns both
sessions and the router returns both to Alice.
**Passes-after**: After the fix, the router calls `list_sessions_by_creator_and_status("alice", "live")`
which filters to only Alice's session.

### Test for `list_sessions_by_creator_and_status` (service layer)

In addition to the router-level test, add a unit test for the new service function:

```python
def test_list_sessions_by_creator_and_status_filters_correctly(monkeypatch):
    """Service function must only return sessions matching both creator and status."""
    from app.services.broadcast_store import list_sessions_by_creator_and_status
    from boto3.dynamodb.conditions import Key, Attr

    captured_kwargs = {}

    class FakeTable:
        def query(self, **kwargs):
            captured_kwargs.update(kwargs)
            return {"Items": []}

    monkeypatch.setattr("app.services.broadcast_store.T.broadcast_sessions", FakeTable())

    list_sessions_by_creator_and_status("alice", "live", limit=20)

    assert captured_kwargs["IndexName"] == "ByCreatorCreatedAt"
    # Key condition must scope to alice's creator ID
    assert "alice" in str(captured_kwargs["KeyConditionExpression"])
    # Filter expression must restrict by status
    assert "live" in str(captured_kwargs.get("FilterExpression", ""))
```

This test verifies that the new service function uses the correct GSI and applies both the key
condition (creator scope) and the filter expression (status restriction).

### Rollback

The fix is backwards-incompatible only for the unintended cross-creator use case. Rolling back
means reverting the router branch; no database migration is involved.

### Risks

- **FilterExpression performance**: For a creator with thousands of archived sessions, querying the
  `ByCreatorCreatedAt` GSI and filtering by status reads more items than needed. For the current
  scale this is acceptable; a `ByCreatorStatus` GSI (partition: `created_by`, sort: `status#created_at`)
  can be added later.
- **Pagination under FilterExpression**: DynamoDB applies `FilterExpression` after consuming `Limit`
  items. If a creator has many sessions in other statuses, the first page may return fewer than
  `limit` results even if more matching items exist. Callers should follow `cursor` pagination until
  exhausted. This is the same pattern used across the rest of the codebase (see CLAUDE.md note on
  `DDB FilterExpression`).

### GSI design note for future scale

The current fix uses a `FilterExpression` on the `ByCreatorCreatedAt` GSI. DynamoDB evaluates
`FilterExpression` after consuming up to `Limit` read capacity units per page; for a creator with
many sessions in other statuses the caller may need multiple paginated requests to collect `limit`
matching items. The existing pagination cursor (`LastEvaluatedKey`) already handles this correctly.
For a creator with hundreds of sessions across statuses this remains acceptable; at scale a
dedicated `ByCreatorStatus` GSI (partition key: `created_by`, sort key: `status#created_at`)
would eliminate the post-read filter entirely and is a straightforward DynamoDB table evolution.
Adding that GSI requires: (a) a new entry in `scripts/local-ddb-init.py` with
`attr_types={"status_created_at": "S"}`, (b) a write-path update to populate the composite sort
key on `create_session`, and (c) a data migration to backfill existing items. These steps are
out of scope for the current fix but should be in the medium-term roadmap.

### Sequencing

1. Add `list_sessions_by_creator_and_status` to `broadcast_store.py` (no router change yet; safe).
2. Update `list_sessions_route` in `broadcast.py` to use the new function for non-operators.
3. Deploy and monitor. Effort: **S** (~2 hours including test authoring).
