# GAP-0045: ad_feedback Records Accumulate Without TTL — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: Every time a user hides or negatively signals an ad via `record_ad_feedback` in `app/services/ad_feedback.py`, a new DynamoDB item is written to the `billing` table with no `expires_at` attribute and no TTL mechanism. The items are never deleted. At platform scale (10 million users each hiding 20 ads over their lifetime) this produces 200 million unbounded items in a table that is also used for payment methods, ledger entries, and subscription records. DynamoDB storage costs grow without bound, and the `get_hidden_ad_ids` query (a `begins_with("AD_FEEDBACK#")` per-user query) must scan an ever-growing list of feedback records per user.

- **Severity**: HIGH
- **Source ticket**: ADS-005
- **Status**: Open
- **Owning area**: Ads Platform / Ad Feedback
- **Effort**: S
- **Claim verdict**: CLAIM OK — confirmed. `app/services/ad_feedback.py:36–44` writes items to `T.billing` with keys `pk=USER#{user_id}`, `sk=AD_FEEDBACK#{creative_id}#{ts}`. The item dict contains no `expires_at`, `ttl`, or any other TTL attribute. `scripts/local-ddb-init.py:64` defines the billing table as `TableDef(_resolve_table_name(S.billing_table_name, "billing"), "pk", "sk")` — no TTL configuration. The `_enable_ttl_if_needed` function at line 2434 is only called for `api_usage_events` and `app_single_table` (lines 2467–2468), and for `shopping_cart` (lines 2469–2476). The billing table is not in the TTL enablement list.

**One-line impact**: Ad feedback items accumulate indefinitely in the billing table, growing storage costs without bound and degrading the performance of every per-user `AD_FEEDBACK#` query used by the serving engine to suppress hidden ads.

**Related tickets**: ADS-005 (source), GAP-0041 (billing table write patterns), GAP-0042 (get_hidden_ad_ids called in serve_ad — performance degrades as items accumulate), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### record_ad_feedback — no TTL attribute

`app/services/ad_feedback.py:22–53`:

```python
def record_ad_feedback(
    user_id: str,
    creative_id: str,
    campaign_id: str,
    feedback_type: str,
    reason: str = "",
) -> dict:
    if feedback_type not in VALID_FEEDBACK_TYPES:
        raise ValueError(...)

    ts = now_ts()
    T.billing.put_item(Item={
        "pk": f"USER#{user_id}",
        "sk": f"AD_FEEDBACK#{creative_id}#{ts}",
        "creative_id": creative_id,
        "campaign_id": campaign_id,
        "feedback_type": feedback_type,
        "reason": reason,
        "created_at": ts,
        # ← no expires_at, no ttl field
    })
    ...
    return {"ok": True}
```

The item has `created_at` (Unix timestamp) but no expiry attribute. DynamoDB's TTL feature requires a numeric attribute whose value is a Unix epoch time; when TTL fires, DynamoDB deletes the item automatically within 48 hours of the expiry time.

### billing table — no TTL enabled

`scripts/local-ddb-init.py:64`:

```python

```

The `TableDef` call has no `ttl_attr` parameter. The `_enable_ttl_if_needed` helper is not called for this table in the TTL-enablement section (lines 2467–2476).

`app/core/settings.py:323`:


### get_hidden_ad_ids — per-user GSI query

`app/services/ad_feedback.py:56–72`:

```python
def get_hidden_ad_ids(user_id: str) -> Set[str]:
    try:
        resp = T.billing.query(
            KeyConditionExpression=(
                Key("pk").eq(f"USER#{user_id}")
                & Key("sk").begins_with("AD_FEEDBACK#")
            ),
        )
        return {
            item["creative_id"]
            for item in resp.get("Items", [])
            if item.get("feedback_type") == "hide"
        }
    except Exception:
        ...
        return set()
```

This query uses the billing table's primary key (`pk` = `USER#{user_id}`, `sk begins_with "AD_FEEDBACK#"`). It returns all feedback records for the user, then filters in Python for `feedback_type == "hide"`. Without TTL expiry, a user who has hidden 1,000 ads over 3 years will cause this query to read and deserialise 1,000 DynamoDB items on every single serve request. Since `get_hidden_ad_ids` is not called in `serve_ad` (confirmed: `serve_ad` calls `is_advertiser_blocked` but does not call `get_hidden_ad_ids`), this is a deferred performance issue — but the unbounded growth still affects the newsfeed ad-injection path that does call it (the feed serving pipeline calls `get_hidden_ad_ids` to filter the post feed).

### serve_ad — is_advertiser_blocked, not get_hidden_ad_ids

`app/services/ad_serving.py:91–92`:

```python
if is_advertiser_blocked(creator_id, account_id):
    continue
```

`serve_ad` calls `is_advertiser_blocked` (which queries `AD_BLOCK#` records), not `get_hidden_ad_ids` (which queries `AD_FEEDBACK#` records). The feedback items are used by the feed-post injection path, not by the per-slot serve path. However, the storage growth and billing table pollution still apply.

### Billing table co-mingling

The `billing` table stores a heterogeneous mix of record types, distinguished by `sk` prefix:

- `PM#*` — payment methods
- `BILLING` — billing configuration
- `LEDGER#*` — financial transactions
- `SUBSCRIPTION#*` — subscription state
- `AD_SETTINGS` — creator ad preferences
- `AD_BLOCK#*` — advertiser block list
- `AD_FEEDBACK#*` — ad feedback (subject of this gap)

Without TTL, `AD_FEEDBACK#` records become the dominant record type by item count over time. DynamoDB does not partition table capacity by SK prefix; hot partitions caused by frequent `AD_FEEDBACK#` writes for popular users can throttle reads/writes for `LEDGER#` and `PM#` records on the same partition — directly affecting payment reliability.

## 3. Impact / Exploit / Blast Radius

**Storage cost**: At 250 bytes per item, 200 million items = 50 GB of DynamoDB storage, billed at approximately $12.50/month in us-east-1 (on-demand). This grows linearly with the user base and engagement rate. At 100M users it reaches $62.50/month just for feedback records.

**Performance degradation**: `get_hidden_ad_ids` reads all `AD_FEEDBACK#` items for a user. A power user who has hidden 5,000 ads accumulates 5,000 DynamoDB items; the query reads all of them on every feed-load, consuming DynamoDB read capacity units proportional to item count. Without pagination this silently returns only the first 1 MB worth of records (approximately 4,000 items), meaning very active users' older feedback is ignored and previously hidden ads re-appear.

**Partition hotspot**: The billing table's partition key is `USER#{user_id}`. Users with high ad interaction frequency have large partitions, creating potential hotspots under DynamoDB's 3,000 RCU / 1,000 WCU per-partition limits.

**Compliance / GDPR**: Ad feedback signals (what a user hid and why) are personal data under GDPR Article 4. Without a retention policy (implemented via TTL), the platform cannot demonstrate compliance with GDPR's data minimisation and storage limitation principles. A 90-day TTL matches typical ad-signal data retention policies and gives the platform a defensible retention schedule.

## 4. Fix Design (code-level)

### Step 1 — Add expires_at to record_ad_feedback

In `app/services/ad_feedback.py`, add the TTL attribute to every feedback write:

```python
_FEEDBACK_TTL_DAYS = 90  # 90-day retention for ad feedback signals

def record_ad_feedback(
    user_id: str,
    creative_id: str,
    campaign_id: str,
    feedback_type: str,
    reason: str = "",
) -> dict:
    if feedback_type not in VALID_FEEDBACK_TYPES:
        raise ValueError(
            f"Invalid feedback type: {feedback_type}. Must be one of {VALID_FEEDBACK_TYPES}"
        )

    ts = now_ts()
    expires_at = ts + _FEEDBACK_TTL_DAYS * 86400  # NEW
    T.billing.put_item(Item={
        "pk": f"USER#{user_id}",
        "sk": f"AD_FEEDBACK#{creative_id}#{ts}",
        "creative_id": creative_id,
        "campaign_id": campaign_id,
        "feedback_type": feedback_type,
        "reason": reason,
        "created_at": ts,
        "expires_at": expires_at,  # NEW — DynamoDB TTL attribute
    })
    logger.info(
        "sponsored_hidden",
        extra={
            "viewer_id": user_id,
            "creative_id": creative_id,
            "feedback_type": feedback_type,
        },
    )
    return {"ok": True}
```

### Step 2 — Enable TTL on the billing table

In `scripts/local-ddb-init.py`, add the billing table to the TTL enablement section. Locate the `_enable_ttl_if_needed` call block (lines 2467–2476) and add:

```python
# ADS-005: Enable TTL on billing table for ad_feedback record expiry
# The TTL attribute is "expires_at" (Unix epoch seconds), written only on
# AD_FEEDBACK# items. Other billing table item types do not write expires_at
# and are unaffected by TTL enablement.
try:
    ddb.update_time_to_live(
        TableName=_resolve_table_name(S.billing_table_name, "billing"),
        TimeToLiveSpecification={
            "Enabled": True,
            "AttributeName": "expires_at",
        },
    )
except Exception as e:
    logger.warning("billing_ttl_enable_failed: %s", e)
```

Alternatively, call the existing helper:

```python
_enable_ttl_if_needed(ddb, _resolve_table_name(S.billing_table_name, "billing"))
```

However, the existing `_enable_ttl_if_needed` at line 2434 uses `S.ddb_ttl_attr` (defaulting to `"ttl_epoch"`) as the TTL attribute name. The feedback records use `"expires_at"` (consistent with other tables like `ad_frequency_caps`). Either rename the feedback attribute to `"ttl_epoch"` (the global standard) or add an explicit TTL call with `"expires_at"`. Recommended: use `"expires_at"` to match the platform-wide convention for ad-related tables, and add an explicit `update_time_to_live` call specifically for the billing table.

**Important**: Enabling TTL on an existing production table is a non-destructive operation. DynamoDB evaluates the `expires_at` attribute only on items that have it. Items without `expires_at` (all existing billing, payment, and ledger records) are never expired. There is no risk of deleting financial data.

### Step 3 — Add pagination to get_hidden_ad_ids

While not strictly required for the TTL fix, `get_hidden_ad_ids` should be updated to paginate, since without pagination it silently returns only the first 1 MB of results:

```python
def get_hidden_ad_ids(user_id: str) -> Set[str]:
    hidden: Set[str] = set()
    kwargs = {
        "KeyConditionExpression": (
            Key("pk").eq(f"USER#{user_id}")
            & Key("sk").begins_with("AD_FEEDBACK#")
        ),
    }
    try:
        while True:
            resp = T.billing.query(**kwargs)
            for item in resp.get("Items", []):
                if item.get("feedback_type") == "hide":
                    hidden.add(item["creative_id"])
            last_key = resp.get("LastEvaluatedKey")
            if not last_key:
                break
            kwargs["ExclusiveStartKey"] = last_key
    except Exception:
        logger.warning("ad_feedback_read_failed user=%s", user_id)
        return set()
    return hidden
```

### Dev/Prod parity (SECOPS-007)

DynamoDB Local (port 8001) supports the TTL API call (`update_time_to_live`) but does not actually expire items based on TTL in the local mock — this is documented DynamoDB Local behaviour. Items written with `expires_at` in dev will not be auto-deleted, but the attribute is present and can be inspected. Unit tests use moto, which also supports the TTL API without auto-deleting items. Both environments are consistent: the TTL attribute is written, and tests can assert its presence and correct value. Production AWS DynamoDB will delete items within 48 hours of `expires_at`.

No feature flag is needed. The TTL attribute is a passive cleanup mechanism — writing it to new records produces no observable change in behaviour until AWS TTL fires.

### Backward compatibility

- Existing `AD_FEEDBACK#` items in DynamoDB have no `expires_at`. They are never expired by TTL (TTL ignores items without the attribute). They will accumulate until manually cleaned up.
- A one-time back-fill script can scan `sk begins_with "AD_FEEDBACK#"` and add `expires_at = created_at + 90*86400` to existing items, triggering eventual cleanup. This is optional and can be deferred.
- The 90-day TTL window is configurable via `_FEEDBACK_TTL_DAYS`. Business requirements may dictate a shorter or longer window.

### Rollout

- **Effort**: S (< 1 day including tests and migration script).
- **Risk**: Low. Adding `expires_at` to new feedback items is a purely additive change. Existing items are unaffected. Enabling TTL on the billing table is non-destructive — AWS processes TTL asynchronously and never expires items lacking the TTL attribute.
- **Production deployment**: After code deploy, enable TTL on the production billing table via the AWS console or CLI: `aws dynamodb update-time-to-live --table-name billing --time-to-live-specification Enabled=true,AttributeName=expires_at`. The `scripts/local-ddb-init.py` change handles dev/test environments automatically.
- **Rollback**: Remove `expires_at` from `record_ad_feedback`. Items already written with `expires_at` in production will continue to be expired by AWS TTL, but new items will no longer have the attribute. Disabling TTL on the table stops future expirations.
- **Sequencing**: This fix is self-contained and can be deployed independently of GAP-0041 through GAP-0044. It should be deployed before any campaign volume milestone that generates significant ad feedback data.
