# GAP-0151: Feature Flag Not Enforced at Router Level — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at app/routers/fan_club.py.

## 1. Summary & Classification

**Plain-English statement:** The `FAN_CLUBS_ENABLED` feature flag (stored as `S.fan_clubs_enabled` in `app/core/settings.py:1885`) is silently ignored by the fan club router. Every endpoint — tier management, channel CRUD, badge resolution, and early access — remains live and accessible even when the flag is explicitly set to `FAN_CLUBS_ENABLED=0`. Setting the environment variable to disable the feature has zero runtime effect.

- **Severity:** HIGH
- **Source ticket:** CREATOR-002
- **Status:** Open
- **Owning area:** Fan Club / Creator Features backend
- **Claim verdict:** Confirmed. `app/routers/fan_club.py` contains zero references to `fan_clubs_enabled` or any `_check_enabled()` guard. Confirmed by `grep -n "fan_clubs_enabled\|FAN_CLUBS_ENABLED" app/routers/fan_club.py` returning no output.

**Related tickets:** CREATOR-002, SECOPS-007 (dev/prod parity), GAP-0152 (dashboard SSE), GAP-0153 (milestone detection).

## 2. Current-State Investigation (Root Cause)

### The flag exists — it just has no effect

`app/core/settings.py:1885`:
```python
fan_clubs_enabled: bool = os.environ.get("FAN_CLUBS_ENABLED", "1") not in ("0", "false", "False")
```

The setting is correctly defined and defaults to `True`. The corresponding `S.fan_clubs_enabled` attribute is available on the singleton `S` instance throughout the application.

### The pattern exists in a neighbouring router — but was never ported

`app/routers/collaborations.py:88–90` implements the exact enforcement pattern that fan_club.py is missing:

```python
def _check_enabled():
    if not S.collaborations_enabled:
        raise HTTPException(503, "Collaborations feature is disabled")
```

This helper is called at the top of every handler in `collaborations.py` (lines 99, 148, 159, 166, 174, 186, 202, 218, 242, 256, 270, 299, 370, 394, 411, 430, 457, 475, 501, 516 — exhaustively applied). The fan club router was presumably written after collaborations.py, or at the same time, but the guard was never added.

### Runtime behaviour

In dev mode (`DEV_MODE=1`) and in production, when `FAN_CLUBS_ENABLED=0`:
- All 15+ endpoints continue to return `200 OK` (or auth-gated `401/403` as expected).
- Tier and channel data continues to be written to and read from DynamoDB.
- No `503 Service Unavailable` is ever returned.
- The flag has zero operational meaning.

## 3. Impact / Exploit / Blast Radius

### Availability / product control risk

Fan clubs represent a monetisation surface. A platform operator setting `FAN_CLUBS_ENABLED=0` for a maintenance window, billing dispute, regulatory pause, or staged rollout would expect the feature to be fully inaccessible. Because the guard is absent, operators cannot enforce downtime through environment configuration alone; they would need to take a full deployment down or re-route at the load balancer.

### Staged rollout failure

The flag is designed to support phased feature launches (enable for internal users first, public later). Without the guard, the flag cannot be used for per-environment progressive rollout, making A/B gating via environment variable impossible.

### Data consistency risk during maintenance

If the platform operator attempts to migrate fan club data (tier restructure, channel re-keying) while setting `FAN_CLUBS_ENABLED=0` to prevent concurrent writes, that intent is ignored. Writers continue mutating DynamoDB during the "disabled" window, creating potential data integrity issues.

### Blast radius

- Every authenticated user can still create, read, update, and delete tiers and channels.
- The public endpoint (`GET /api/creators/{creator_id}/tiers`) has no authentication, so un-gated exposure is not limited to logged-in users.
- No financial or security exploit is directly possible through this gap alone (the endpoints themselves are correctly auth-protected). The risk is operational control and staged-rollout integrity.

## 4. Fix Design (Code-Level)

### Minimal change: add `_check_enabled()` guard

Add a private guard function at the top of `app/routers/fan_club.py`, immediately after the imports and before the router definitions, following the exact pattern established in `app/routers/collaborations.py:88–90`:

```python
# app/routers/fan_club.py — add after imports, before router = APIRouter(...)

from app.core.settings import S

def _check_enabled() -> None:
    """Enforce FAN_CLUBS_ENABLED feature flag."""
    if not S.fan_clubs_enabled:
        raise HTTPException(status_code=503, detail="Fan club feature is disabled")
```

Note: `S` must be imported. Check whether `from app.core.settings import S` is already present; if not, add it alongside the existing imports.

### Apply the guard to every handler

Add `_check_enabled()` as the first statement in each of the 15+ handler functions in `app/routers/fan_club.py`. Example for the tier creation handler (`fan_club.py:54–69`):

```python
@router.post("/ui/fan-club/tiers", status_code=201)
def api_create_tier(body: TierCreateIn, session=Depends(require_ui_session)):
    _check_enabled()                          # <-- ADD THIS
    user_id = session["user_sub"]
    tier = create_tier(
        creator_id=user_id,
        ...
    )
    return _tier_out(tier)
```

Apply the identical one-liner `_check_enabled()` to all other handlers. The public tier endpoint at line 280 should also be guarded — if the feature is disabled, the public-facing tier listing page should 404/503, not return stale tier data.

### Dev/Prod parity (SECOPS-007)

The `S.fan_clubs_enabled` setting is read purely from the `FAN_CLUBS_ENABLED` environment variable (`app/core/settings.py:1885`). No dev-mode bypass or mock path is involved. The same code path runs in both local dev and production.

In `.env.local` (dev), the default is `FAN_CLUBS_ENABLED=1` (enabled), so local development is unaffected by this fix. Setting `FAN_CLUBS_ENABLED=0` in `.env.local` will correctly disable all fan club endpoints in the local stack after the fix is applied, matching production behaviour. No separate mock or dev code path is required.

The fix is fully flag-selected: toggling `FAN_CLUBS_ENABLED` in either environment will immediately enable or disable all fan club endpoints without a code deploy.

### Backward compatibility

- **No migration required.** Existing DynamoDB data is unaffected.
- **No API contract change.** When `FAN_CLUBS_ENABLED=1` (the default), behaviour is identical to today. Only the previously-ignored `=0` case changes.
- **No frontend change required.** The frontend should already handle `503` responses gracefully (React Query will surface the error state). If it doesn't, that is a separate concern.

### Alternatives considered

1. **Middleware-level flag** — intercept `/ui/fan-club/*` paths in a middleware and return 503. Rejected: harder to test, less explicit, can accidentally block unrelated paths sharing the prefix, and departs from the pattern established in collaborations.py.
2. **Single router-level Depends** — inject a dependency on every route via `router = APIRouter(dependencies=[Depends(_check_enabled)])`. This is cleaner than per-handler calls and avoids omission bugs on future handlers. This is the preferred approach and slightly better than the collaborations.py per-handler pattern. Implementation:

```python
def _check_enabled() -> None:
    if not S.fan_clubs_enabled:
        raise HTTPException(status_code=503, detail="Fan club feature is disabled")

router = APIRouter(tags=["fan-club"], dependencies=[Depends(_check_enabled)])
public_router = APIRouter(tags=["fan-club-public"], dependencies=[Depends(_check_enabled)])
```

This single change automatically applies the guard to all current and future endpoints on both routers without requiring per-handler additions. This is the recommended implementation.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to `tests/test_fan_club_feature_flag.py`:

```python
"""Regression test for GAP-0151: FAN_CLUBS_ENABLED=0 must block all fan club endpoints."""
import pytest
from unittest.mock import patch
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

GUARDED_ENDPOINTS = [
    ("GET",    "/ui/fan-club/tiers"),
    ("POST",   "/ui/fan-club/tiers"),
    ("GET",    "/ui/fan-club/channels"),
    ("POST",   "/ui/fan-club/channels"),
    ("GET",    "/api/creators/test_creator/tiers"),
]

@pytest.mark.parametrize("method,path", GUARDED_ENDPOINTS)
def test_fan_club_disabled_returns_503(method, path, monkeypatch):
    """FAILS before fix (returns 200/401/404); PASSES after fix (returns 503)."""
    from app.core.settings import S
    monkeypatch.setattr(S, "fan_clubs_enabled", False)

    response = client.request(method, path)
    assert response.status_code == 503, (
        f"{method} {path} returned {response.status_code}, expected 503 when fan clubs disabled"
    )
    assert "disabled" in response.json().get("detail", "").lower()


def test_fan_club_enabled_passes_through(monkeypatch):
    """Confirm normal (401) behaviour when flag is True — guards don't block when enabled."""
    from app.core.settings import S
    monkeypatch.setattr(S, "fan_clubs_enabled", True)

    response = client.get("/ui/fan-club/tiers")
    # 401 because no auth cookie — but NOT 503
    assert response.status_code == 401
```

**Fails before fix:** `GET /ui/fan-club/tiers` without a session returns `401` (not `503`), so the parametrized assertion `== 503` fails.
**Passes after fix:** The `_check_enabled()` guard (or router-level dependency) raises `HTTPException(503)` before auth is checked, so `503` is returned.
