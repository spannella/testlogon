# GAP-0299: DRM support reduced to AES-128 flag only — Remediation Write-up

> ~5 pages. Fix-oriented. No investigation doc exists; the claim is verified directly against the codebase.

## 1. Summary & Classification

**Bug statement:** `MediaPlayer` accepts a `drmKeyUrl` prop for AES-128 HLS key delivery but does nothing with it beyond setting `hlsConfig.emeEnabled = true`. No `drmSystems` configuration is provided to HLS.js, no `licenseXhrSetup` callback for Widevine/PlayReady CDM token injection, and no Safari native FairPlay path is implemented. Content requiring Widevine (Chrome/Firefox), PlayReady (Edge), or FairPlay (Safari) DRM will fail silently or fall back to unencrypted playback.

- **Severity:** HIGH
- **Source ticket:** MEDIA-001
- **Status:** Open — only the AES-128 stub exists
- **Owning area:** Frontend / MediaPlayer / DRM
- **Claim verdict:** CONFIRMED. `frontend/src/components/shared/MediaPlayer.tsx:321-323` shows the complete DRM implementation is `if (drmKeyUrl) { hlsConfig.emeEnabled = true; }`. No `drmSystems`, no `licenseXhrSetup`, no FairPlay certificate fetch path. The ticket's characterisation is accurate.

**Related tickets:** MEDIA-001 (parent); GAP-0300 (token refresh, same file); SECOPS-007 (dev/prod parity).


## 2. Current-State Investigation (root cause)

**File:** `frontend/src/components/shared/MediaPlayer.tsx:55-82` (props), `310-325` (HLS config), `288-301` (Safari fallback)

The `MediaPlayerProps` interface (line 55-82) declares:

```typescript
/** Key server URL for AES-128 HLS encryption */
drmKeyUrl?: string;
```

This is the only DRM-related prop. There is no `drmConfig` object, no `licenseUrl`, no `fairplayCertificateUrl`, and no `token` field for license-server authentication.

The HLS.js setup block (line 310-325) uses `drmKeyUrl` only as a boolean signal:

```typescript
const hlsConfig: Partial<ConstructorParameters<typeof Hls>[0]> = {
  startLevel: -1,
  enableWorker: true,
  lowLatencyMode: mode === "live",
  maxBufferLength: mode === "live" ? 6 : 30,
  maxMaxBufferLength: mode === "live" ? 12 : 60,
  fragLoadingMaxRetry: 6,
  manifestLoadingMaxRetry: 4,
  levelLoadingMaxRetry: 4,
};

if (drmKeyUrl) {
  hlsConfig.emeEnabled = true;   // <-- entire DRM implementation
}
```

`emeEnabled: true` alone tells HLS.js to expect EME (Encrypted Media Extensions) but provides no system-specific key session parameters. HLS.js requires `drmSystems` to list Widevine (`com.widevine.alpha`), PlayReady (`com.microsoft.playready`), or FairPlay (`com.apple.fps.1_0`) key systems with their respective `licenseUrl` and optional header/callback configuration. Without `drmSystems`, HLS.js will attempt to negotiate key sessions but fail immediately because no key system is configured.

The Safari native fallback path (line 288-301) sets `video.src = src` and calls `video.play()` but implements no FairPlay key request handling:

```typescript
if (!Hls.isSupported()) {
  if (video.canPlayType("application/vnd.apple.mpegurl")) {
    video.src = src;
    if (autoplay) {
      video.play().catch(() => {});
    }
    setPlayerState("ready");
    onReady?.();
    return;
  }
  ...
}
```

For FairPlay-encrypted content in Safari, playback would start, the browser would issue a `webkitNeedKey` event (Safari 12-) or an EME `encrypted` event (Safari 14+), and neither handler is registered. The video will stall at the beginning waiting for a license that never arrives.

**HLS.js version context:** The project uses `hls.js@^1.6.16` (`frontend/package.json:49`). HLS.js 1.x has full EME support when `drmSystems` is configured correctly. The capability is present in the library; only the configuration is absent.

**Why `emeEnabled = true` alone is insufficient:** HLS.js's EME integration requires both `emeEnabled: true` and a populated `drmSystems` map. The `drmSystems` map tells HLS.js which CDM key systems to negotiate (Widevine: `com.widevine.alpha`, PlayReady: `com.microsoft.playready`, FairPlay: `com.apple.fps.1_0`), what license acquisition URL to call for each system, and optionally an `xhrSetup` callback to inject auth headers into license requests. Without `drmSystems`, HLS.js sets `emeEnabled` internally but never calls `navigator.requestMediaKeySystemAccess`, so no CDM is initialised. The encrypted content plays as if unencrypted — the browser may either block rendering or display visual corruption depending on whether the CDN strips the encryption or serves the encrypted segments unmodified.

## 3. Impact / Exploit / Blast Radius

**Who is affected:** Any user attempting to play DRM-protected content (Widevine, PlayReady, or FairPlay). Currently zero production callers pass `drmKeyUrl`, so there is no live impact today. However:

1. When a DRM-encrypted video is served and a caller passes `drmKeyUrl`, playback fails silently in all browsers (Chrome/Firefox/Edge/Safari). Users see an error or an infinite loading spinner.
2. Content stored with DRM keys on the server cannot be monetised if the client cannot decrypt it.
3. Safari users with FairPlay-required content are completely unserved — Safari does not support Widevine.

**Security posture:** The gap means DRM-protected content could potentially be served without DRM enforcement in degraded circumstances (e.g., CDN misconfiguration strips the encryption). The fix reduces the attack surface by correctly enforcing key sessions.

**Financial/compliance:** Premium or pay-per-view content relying on DRM for copy protection is unprotected if the DRM path is silently bypassed.

**Blast radius:** HIGH severity but currently LOW immediate impact because no production callers use the prop. The risk is forward-looking — the moment any DRM-protected content is served, the entire user base is affected.


## 4. Fix Design (code-level)

### 4.1 New `DrmConfig` interface

```typescript
// frontend/src/components/shared/MediaPlayer.tsx — add to Types section

export interface DrmConfig {
  /** Widevine/PlayReady CDM license acquisition URL */
  licenseUrl?: string;
  /** Bearer token or DRM-system-specific auth token for the license server */
  token?: string;
  /** FairPlay certificate URL (Safari only; fetched once per page load) */
  fairplayCertificateUrl?: string;
  /** Override the key system; defaults to auto-detect from browser capabilities */
  keySystem?: "com.widevine.alpha" | "com.microsoft.playready" | "com.apple.fps.1_0";
}
```

### 4.2 Updated `MediaPlayerProps`

Replace the `drmKeyUrl?: string` prop (AES-128 only) with a richer union:

```typescript
export interface MediaPlayerProps {
  // ... existing props ...

  /** AES-128 HLS key server URL (basic HLS encryption; no CDM required) */
  drmKeyUrl?: string;

  /** Full DRM configuration for Widevine / PlayReady / FairPlay content */
  drmConfig?: DrmConfig;
}
```

Keeping `drmKeyUrl` preserves backward compatibility for any existing callers.

### 4.3 HLS.js config with `drmSystems`

```typescript
// Inside the HLS setup useEffect, replace the `if (drmKeyUrl)` block:

if (drmKeyUrl) {
  hlsConfig.emeEnabled = true;
  // AES-128: HLS.js handles key fetch natively; no drmSystems needed
}

if (drmConfig?.licenseUrl) {
  hlsConfig.emeEnabled = true;
  hlsConfig.drmSystems = {
    "com.widevine.alpha": {
      licenseUrl: drmConfig.licenseUrl,
      ...(drmConfig.token ? {
        licenseXhrSetup: (xhr: XMLHttpRequest) => {
          xhr.setRequestHeader("Authorization", `Bearer ${drmConfig.token}`);
        },
      } : {}),
    },
    "com.microsoft.playready": {
      licenseUrl: drmConfig.licenseUrl,
      ...(drmConfig.token ? {
        licenseXhrSetup: (xhr: XMLHttpRequest) => {
          xhr.setRequestHeader("Authorization", `Bearer ${drmConfig.token}`);
        },
      } : {}),
    },
  };
}
```

### 4.4 Safari / FairPlay native path

Safari does not support HLS.js and uses the native video element. For FairPlay-protected content, the browser issues an EME `encrypted` event. A handler must fetch the FairPlay certificate and initiate a license key session:

```typescript
// After `video.src = src` in the native Safari fallback:

if (drmConfig?.fairplayCertificateUrl && drmConfig.licenseUrl) {
  let fpsCert: ArrayBuffer | null = null;

  video.addEventListener("encrypted", async (evt) => {
    if (!fpsCert) {
      const certResp = await fetch(drmConfig.fairplayCertificateUrl!);
      fpsCert = await certResp.arrayBuffer();
    }
    const ks = await (video as HTMLVideoElement & {
      webkitKeys?: MediaKeys;
    }).mediaKeys?.createSession("persistent-license");
    // initData contains the content ID bytes for FairPlay
    const initDataType = evt.initDataType;
    const initData = evt.initData;
    await ks?.generateRequest(initDataType, initData!);
    ks?.addEventListener("message", async (msgEvt: MediaKeyMessageEvent) => {
      const licenseResp = await fetch(drmConfig!.licenseUrl!, {
        method: "POST",
        headers: {
          "Content-Type": "application/octet-stream",
          ...(drmConfig!.token
            ? { Authorization: `Bearer ${drmConfig!.token}` }
            : {}),
        },
        body: msgEvt.message,
      });
      const license = await licenseResp.arrayBuffer();
      await ks.update(license);
    });
  });
}
```

### 4.5 Dev/prod parity (SECOPS-007)

The fix introduces no mock-specific code paths. DRM license servers are external services; in dev mode, the license URL would point to a mock DRM server or test FairPlay certificate endpoint. The same React component code runs in both environments. If no `drmConfig` is passed (current state of all callers), behaviour is unchanged.

### Backward compatibility note on `drmKeyUrl`

The existing `drmKeyUrl` prop is used for AES-128 HLS key delivery (also called "HLS encryption" or "basic DRM"). AES-128 does not use a CDM — it relies on the browser's built-in AES decryption after fetching the key from a key server URL embedded in the HLS manifest. HLS.js handles this natively without `drmSystems`. The `emeEnabled = true` on the AES-128 path (line 322) is technically redundant for pure AES-128 but harmless. It should be retained as-is to preserve the existing `drmKeyUrl` contract.

The new `drmConfig` prop is distinct and handles Widevine/PlayReady/FairPlay (EME-based DRM). The two props serve different encryption schemes and can coexist without conflict.
