# GAP-0114: Locked message text delivered in clear via chat SSE stream — Remediation Write-up

## 1. Summary & Classification

**Bug statement**: Inside the broadcast chat SSE generator, each outgoing message is serialised
with `_chat_msg_out(msg)` — without passing the `viewer_user_id` argument. The `_chat_msg_out`
function in `app/services/broadcast_chat_store.py` treats `viewer_user_id=None` as "anonymous
viewer" and, as a result, fails to apply the correct per-viewer locked-message visibility rule.
For a locked message, this means the encrypted/paywalled text is **returned in plaintext** to any
subscriber of the SSE stream who happens to be the sender — and for any non-sender subscriber,
the `is_unlocked` computation defaults to `False` based on `None` identity, suppressing the text.
The critical case is the sender: when a creator or chat participant sends a locked message,
they see it correctly because `viewer_user_id=None` makes `is_sender=False` for everyone —
but the deeper architectural problem is that no per-viewer personalisation is applied at all,
meaning `my_reactions` are wrong, expiry is evaluated without the sender override, and any
future field that depends on `viewer_user_id` will also be broken.

- **Severity**: HIGH (SEC-010 — data-visibility integrity failure)
- **Source ticket**: BCAST-002 (second-pass as-built review)
- **GAP ID**: GAP-0114
- **Owning area**: Broadcast router — chat SSE stream / `_chat_msg_out` helper
- **Status**: Open
- **Effort**: S

**Claim correction note**: The ticket states "locked message text delivered in clear to all SSE
subscribers regardless of unlock status." Code investigation reveals a nuance: when
`viewer_user_id=None`, `is_sender` is always `False` and `is_unlocked` evaluates to `False`
(because `viewer_user_id is not None` is False), so `text` is set to `None` for locked messages
for non-sender non-owner callers. The locked text is therefore *not* delivered in clear to
arbitrary subscribers in the current code. However, the problem is real and important:

1. The **sender** (who should always see their own locked message content) does not see it because
   `is_sender` is always False when `viewer_user_id=None`. This is a usability regression.
2. A subscriber who *has paid to unlock* a message does not see the content because their
   `user_sub` is never checked against `unlocked_by`.
3. The `my_reactions` personalisation is skipped.
4. The overall design is incorrect and will silently break future features that rely on
   `viewer_user_id`.

In short: the claim is partially correct. The locked text is suppressed, but the correct content
is also suppressed for legitimate payers and senders — a content-correctness bug with the same
root cause (missing `viewer_user_id`). The severity is HIGH because legitimate users receive wrong
content (paid unlocked messages appear locked in the stream), and because the architectural gap
enables future regressions.

**Impact in one line**: Paid-unlock recipients and message senders cannot see locked message content
via the SSE chat stream; the omitted `viewer_user_id` also silently breaks reaction personalisation
and all future per-viewer fields.

**Related tickets**: BCAST-002, GAP-0113 (chat stream access check — same handler), GAP-0112
(SSE event stream IDOR), SECOPS-007.

## 2. Current-State Investigation (root cause)

### The call site in the SSE generator

`app/routers/broadcast.py`, line 1806 (inside `broadcast_chat_stream_route`):

```python
out = _chat_msg_out(msg)   # viewer_user_id omitted — defaults to None
```

Compare with the REST history endpoint at line 1605:

```python
result = _store_get_history(
    session_id, limit=limit, before_sort_key=before,
    viewer_user_id=ctx["user_sub"],    # ← correctly supplied
)
```

The REST history path passes `viewer_user_id` all the way into `_chat_msg_out` via
`_store_get_history`. The SSE stream calls `_chat_msg_out` directly and omits it.

### The `_chat_msg_out` function

`app/services/broadcast_chat_store.py`, lines 344–415 (abridged):

```python
def _chat_msg_out(item: Dict[str, Any], viewer_user_id: Optional[str] = None) -> Dict[str, Any]:
    ts = now_ts()
    sender_id = item.get("sender_id", "")
    is_sender = viewer_user_id is not None and viewer_user_id == sender_id   # line 354

    # Phase C — Expiry
    expires_at = item.get("expires_at")
    if expires_at is not None:
        if int(expires_at) < ts and not is_sender:    # sender always sees expired content
            out["text"] = None
            out["expired"] = True

    # Phase D — Locked messages
    lock_price = item.get("lock_price_cents")
    if lock_price is not None:
        unlocked_by = item.get("unlocked_by") or {}
        is_unlocked = is_sender or (viewer_user_id is not None and viewer_user_id in unlocked_by)
        out["is_unlocked"] = is_unlocked
        if not is_unlocked:
            out["text"] = None    # ← text suppressed for everyone when viewer_user_id=None
```

When `viewer_user_id=None`:
- `is_sender = False` (line 354: `None is not None` → False).
- For locked messages: `is_unlocked = False or (None is not None and ...)` = `False`. So text is
  suppressed for all viewers, **including the sender and paying unlockers**.
- For expired messages: `if not is_sender` is True, so expired messages always have text set to
  `None` in the stream (no sender override).
- `my_reactions`: the reaction personalisation block checks `viewer_user_id in user_set`; since
  `viewer_user_id` is None this is never True, so `my_reactions` is always empty in the stream.

### Runtime manifestation

A user who pays 100 cents to unlock a locked message and then refreshes the REST chat history
(`GET /chat`) sees the content correctly. But while watching the live stream, they see the message
arrive with `is_unlocked: false, text: null` — the unlock state is invisible to them in real time.

The session sender who posts a locked message also sees it with `text: null` in the SSE stream,
creating a confusing UX where the sender's own content appears redacted.

## 3. Impact / Exploit / Blast Radius

### Content-correctness failure

This is primarily a correctness/UX bug rather than a pure security exploit. The incorrect
`viewer_user_id=None` causes:

1. **Senders** see their own locked messages with `text: null` in the SSE stream.
2. **Paying unlockers** see messages they have paid to unlock as still locked in the stream.
3. **Reaction personalisation** is broken: `my_reactions` is always `[]` in the SSE stream.
4. **Expiry**: Senders see their own expired messages as expired in the SSE stream (same bug
   direction — they should see the content).

### Security dimension

While the text is not exposed to unauthorised callers in the current code, the design is fragile.
If any future modification assumes that the SSE stream and the REST history endpoint apply identical
rules (which they should), a developer might add a field to `_chat_msg_out` that reveals data when
`viewer_user_id=None`. The architectural inconsistency is itself a latent security risk.

Combined with GAP-0113: if the access-check fix (GAP-0113) is applied first without this fix, a
legitimate subscriber who pays to unlock content still cannot see it in the stream — creating a
broken paid feature. The two fixes must land together.

### Financial impact

Broadcast locked messages are a monetisation feature. A user who pays to unlock content expects
to see it delivered in the SSE stream immediately. The current bug means they see `text: null`
in the stream until they manually reload the chat history via the REST endpoint. This degrades
the premium paid experience.

## 4. Fix Design (code-level)

### The complete fix

The fix is a single change in the SSE generator: capture `ctx["user_sub"]` and pass it to
`_chat_msg_out`. This fix also addresses the implicit dependence issue identified in GAP-0113:
the generator already needs `ctx["user_sub"]` for the access check fix, so capturing it is the
natural approach.

In `app/routers/broadcast.py`, `broadcast_chat_stream_route`:

**Before** (lines 1770-1806 condensed):

```python
async def broadcast_chat_stream_route(
    session_id: str,
    after: Optional[str] = Query(default=None),
    poll_ms: int = Query(default=500, ge=200, le=3000),
    ctx: dict = Depends(_ctx),
):
    _ = ctx    # identity discarded

    ...
    async def gen():
        ...
        out = _chat_msg_out(msg)    # line 1806 — no viewer context
```

**After**:

```python
async def broadcast_chat_stream_route(
    session_id: str,
    after: Optional[str] = Query(default=None),
    poll_ms: int = Query(default=500, ge=200, le=3000),
    invite_token: Optional[str] = Query(default=None),
    ctx: dict = Depends(_ctx),
):
    session = get_session(session_id)
    if session.status not in ("live", "ready"):
        raise HTTPException(...)

    # SEC-010 access check (GAP-0113)
    from app.services.broadcast_privacy import check_viewer_access
    check_viewer_access(
        session_id,
        ctx["user_sub"],
        creator_id=session.created_by,
        visibility=session.broadcast_privacy_visibility,
        invite_token=invite_token,
    )
    viewer_user_id = ctx["user_sub"]   # capture before entering generator

    async def gen():
        ...
        out = _chat_msg_out(msg, viewer_user_id=viewer_user_id)   # ← fix
```

The `viewer_user_id` variable captured in the outer scope is correctly closed over by the
`gen()` coroutine. It is assigned once and never mutated, so there is no closure-staleness risk.

### Why no changes to `_chat_msg_out` itself are needed

The function signature already accepts `viewer_user_id: Optional[str] = None` and correctly
implements all per-viewer logic. The only problem is the call site that omits the argument.

### Dev/Prod parity (SECOPS-007)

The fix is entirely in the router layer; no DynamoDB schema changes, no feature flags, no
environment-specific branches. The `unlocked_by` map and all other fields used by `_chat_msg_out`
are stored in the DynamoDB `broadcast_chat` table identically in dev and production.

The `broadcast_chat_store._chat_msg_out` function uses `now_ts()` for expiry evaluation, which
is deterministic (returns `int(time.time())`). No clock-synchronisation issue exists between
environments.

### Backward compatibility

The change makes the SSE stream more restrictive (locked text suppressed for non-payers, same as
REST) and more correct (locked text revealed for senders and payers). This is purely a bug fix
with no API contract change. No migration is needed.

## 5. Testing, Verification & Rollout

### Regression tests (pytest, offline)

Add to `tests/test_broadcast_chat_msg_out_viewer.py`:

```python
from app.services.broadcast_chat_store import _chat_msg_out
from app.core.time import now_ts

def _locked_msg(sender="alice"):
    return {
        "message_id": "m1",
        "session_id": "s1",
        "sender_id": sender,
        "sender_display_name": sender,
        "text": "secret content",
        "kind": "text",
        "created_at": now_ts(),
        "deleted": False,
        "lock_price_cents": 100,
        "lock_description": "Unlock to read",
        "unlocked_by": {"bob": True},   # bob has paid
    }

def test_sender_sees_own_locked_message():
    """Sender must see their own locked message text (is_sender override)."""
    msg = _locked_msg(sender="alice")
    out = _chat_msg_out(msg, viewer_user_id="alice")
    assert out["is_unlocked"] is True
    assert out["text"] == "secret content"

def test_payer_sees_unlocked_message():
    """User who paid to unlock must receive content."""
    msg = _locked_msg(sender="alice")
    out = _chat_msg_out(msg, viewer_user_id="bob")   # bob is in unlocked_by
    assert out["is_unlocked"] is True
    assert out["text"] == "secret content"

def test_non_payer_sees_null_text():
    """User who has not paid must receive text=None."""
    msg = _locked_msg(sender="alice")
    out = _chat_msg_out(msg, viewer_user_id="carol")
    assert out["is_unlocked"] is False
    assert out["text"] is None

def test_no_viewer_id_suppresses_for_everyone():
    """When viewer_user_id=None (the bug), text must be None for all (sender included).

    This test documents the current broken behaviour and will continue to pass
    after the _chat_msg_out fix, because _chat_msg_out itself is already correct.
    The SSE stream bug is in the call site (broadcast.py line 1806), not here.
    """
    msg = _locked_msg(sender="alice")
    out = _chat_msg_out(msg, viewer_user_id=None)
    # With no viewer context: is_sender=False, is_unlocked=False
    assert out["is_unlocked"] is False
    assert out["text"] is None   # alice's own content suppressed — this is the bug's effect

def test_reactions_personalised_for_viewer():
    """my_reactions must list emojis the viewer has reacted with."""
    msg = {
        "message_id": "m2",
        "session_id": "s1",
        "sender_id": "alice",
        "sender_display_name": "Alice",
        "text": "hi",
        "kind": "text",
        "created_at": 1700000000,
        "deleted": False,
        "reactions": {"👍": {"bob": True, "carol": True}, "❤️": {"bob": True}},
    }
    out = _chat_msg_out(msg, viewer_user_id="bob")
    assert set(out.get("my_reactions", [])) == {"👍", "❤️"}
    # Without viewer_user_id, my_reactions is absent
    out_anon = _chat_msg_out(msg, viewer_user_id=None)
    assert out_anon.get("my_reactions", []) == []
```

### Manual QA steps

1. Alice creates a broadcast session and sends a locked message (lock_price=100 cents).
2. Bob (authenticated, with a payment method) pays to unlock the message via
   `POST /sessions/{id}/chat/{msg_id}/unlock`.
3. Alice keeps the SSE stream open: verify she sees `is_unlocked: true, text: "..."` immediately
   after sending.
4. Bob keeps the SSE stream open: before fix → `is_unlocked: false, text: null`. After fix →
   `is_unlocked: true, text: "..."`.
5. Carol (has not paid) keeps the SSE stream open: must see `is_unlocked: false, text: null` both
   before and after the fix.
6. Verify `my_reactions` is populated correctly for the user who reacted.

### Observability

No new metrics needed for this fix. The `viewer_user_id` value flows through existing code paths.
If locking/unlocking is instrumented, the existing counters will reflect the correct behaviour.

### Rollback

Revert the `viewer_user_id=viewer_user_id` argument addition at line 1806. The rollback restores
the current (broken) behaviour but is safe because the locked text was already suppressed.

### Risks & effort

- **Risk**: Low. The fix is a one-word argument addition at a single call site. `_chat_msg_out`
  has been tested with `viewer_user_id` in the REST path for the duration of the feature.
- **Effort**: S — approximately 30 minutes of coding plus 1 hour of test authoring.
- **Sequencing**: Apply in the same commit as GAP-0113. The access-check fix and the
  `viewer_user_id` fix are in the same handler (`broadcast_chat_stream_route`) and are
  conceptually one unit of work.
