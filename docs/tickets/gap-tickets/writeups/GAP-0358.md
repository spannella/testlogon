# GAP-0358: No `post_shared` Notification Emitted to Original Author on Repost — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code. Source ticket: SOCIAL-002.

## 1. Summary & Classification

**Plain-English statement**: When user B reposts a post authored by user A, user A never
receives a notification. The `post_shared` alert type is registered in `ALERT_EVENT_TYPES`
(`app/services/alerts.py:142`) and has a complete delivery path through `put_notification`
and SSE, but the repost handler (`create_repost`, `newsfeed.py:6050–6164`) never calls
either `put_notification` or `emit_social_alert`. As a result, original authors are unaware
when their content is shared.

**Claim verdict**: CONFIRMED. A full read of `create_repost` (lines 6050–6164) shows the
function: verifies the post exists (6052), checks for self-repost (6060), checks block
(6069), checks duplicate (6077), writes the repost entity to DDB (6093), atomically
increments `repost_count` (6110), writes a FEEDREF for the reposter (6119), and fans out to
the reposter's followers (6138). It then returns `{"ok": True, "repost_id": ...,
"repost_count": ...}` at line 6164. There is no `put_notification` call anywhere in the
function, and `post_shared` appears in the codebase only in `alerts.py` and as a string in
`alerts.py:492` (a preference-handler switch).

- **Severity**: HIGH
- **Source ticket**: SOCIAL-002 (second-pass as-built review)
- **Status**: Open
- **Owning area**: Newsfeed / Social Notifications
- **Related tickets**: GAP-0356 (mention alerts — same missing-call-site pattern),
  SOCIAL-002 (repost fan-out cap gap also documented there), GAP-0357
- **Dependencies**: None. `put_notification` is already defined and callable from
  `newsfeed.py`. The `post_shared` alert type is already registered.

At no point does the function notify `author_id` (the original post's owner, extracted at
line 6061 as `author_id = post.get("user_id", "")`). The `author_id` variable is available
throughout the function but is only used for the self-repost guard (line 6062) and
the block check (line 6072).

### 2.2 The `put_notification` function

`put_notification` is defined at `newsfeed.py:2419`:


It is already called 6 times in `newsfeed.py` for other notification events
(comment_on_post at 5398, reply_to_comment at 5417, etc.).

### 2.3 The `post_shared` alert type

`ALERT_EVENT_TYPES` in `app/services/alerts.py:133–147` includes `"post_shared"` at line 142.
The alert preference system at `alerts.py:492` handles `post_shared` in a `elif event_type
== "post_shared"` branch, meaning user-level notification preferences for this event type
are already implemented and registered. The SSE delivery path and the notification inbox both
correctly handle `post_shared` events once they are written to DDB. The sole missing
piece is the call site in `create_repost`.

### 2.4 Self-repost guard already in place

The handler already raises `400` for self-reposts (`user_id == author_id`, line 6062). This
means the notification call site can be added without a self-notification guard — the
self-repost case never reaches the notification code.

### 2.5 Dev vs prod behavior

The notification pipeline is the same in both dev and prod. DynamoDB Local on port 8001
stores notifications in the same schema. The SSE hub is in-process and operational in dev.
No mock fork exists for `put_notification`.

## 3. Impact / Exploit / Blast Radius

This is a **silent feature omission**, not a security vulnerability.

**Users affected**: Every original post author on the platform. Each time any other user
reposts their content, the author receives no notification.

**Functional consequences**:

1. The `repost_count` on the post is correctly incremented, meaning the author can *see*
   their repost count increase in the feed, but receives no real-time alert and nothing in
   the notification inbox.
2. The notification preference UI exposes a `post_shared` toggle that can be configured but
   never fires, which may confuse users testing notification settings.
3. Analytics and engagement metrics that depend on notification-driven revisits
   (`post_shared` click-through) are perpetually zero.

**Volume**: Every repost operation is affected. There is no partial mitigation in place.

**Financial / compliance**: No direct financial impact. No PII exposure.

## 4. Fix Design (code-level)

### 4.1 The required change

Add a single `put_notification` call in `create_repost` immediately after the repost entity
is written to DDB (after line 6108, before the `repost_count` increment at 6110). The
`author_id` variable holding the original post owner's user sub is already in scope from
line 6061.

```python
    # GAP-0358: notify original author that their post was reposted
    if author_id and author_id != user_id:
        try:
            put_notification(
                recipient_user_id=author_id,
                notif_type="post_shared",
                payload={
                    "post_id": post_id,
                    "repost_id": repost_id,
                    "from_user_id": user_id,
                    "created_at": created_at,
                },
            )
        except Exception:
            logger.warning(
                "Failed to send post_shared notification for repost %s", repost_id
            )
```

The `author_id != user_id` guard is technically redundant (the self-repost check at line
6062 prevents reaching this code), but it is a defensive belt-and-suspenders measure that
avoids self-notifications if the guard logic is ever changed.

The `try/except` wrapping ensures that a notification write failure (e.g. DDB temporarily
unavailable) does not roll back the repost operation itself, which has already been
committed.

### 4.2 Payload fields

The `payload` dict mirrors the convention used by other `put_notification` calls in
`newsfeed.py` and matches the `post_shared` handling branch in `alerts.py:492`. The fields
needed for proper navigation link construction (`/feed?post={post_id}`) are `post_id` (see
`alerts.py:72: "post_shared": f"/feed?post={post_id}" if post_id else None`).

### 4.3 Optional: include reposter display name for richer notification copy

The notification payload could optionally include `from_display_name` for use in the
notification inbox rendering, fetched via `_post_fadt_display_name(user_id)` (already
defined at `newsfeed.py:4138`). This is low-cost but purely cosmetic:

```python
"from_display_name": _post_fadt_display_name(user_id),
```

### 4.4 Dev/Prod parity (SECOPS-007)

`put_notification` is a single code path for both dev and prod. There is no mock fork, no
feature flag gating the notification write, and no AWS-specific path. The DynamoDB write
target is determined by `APP_TABLE` (the same table in both environments). SSE delivery in
dev uses the in-process `sse_hub`; in prod it uses the same hub on a single-worker uvicorn.
No additional parity work is required.

**Optional feature flag**: If gradual rollout is desired, add
`repost_notification_enabled: bool = True` to `app/core/settings.py` and wrap the
notification call:

```python
if getattr(S, "repost_notification_enabled", True):
    put_notification(...)
```

This allows disabling via an environment variable without a code deploy.

### 4.5 Undo-repost path

The `undo_repost` handler (`newsfeed.py:6167`) does not need a corresponding "notification
retracted" event. The notification inbox does not support retraction, and the existing
comment/like notification flows do not retract on unlike/delete either. This is consistent
behavior.

### 4.6 Alternatives considered

- **`emit_social_alert` instead of `put_notification`**: Both ultimately write to DDB and
  push SSE. `put_notification` is the lower-level and more direct function, consistent with
  comment/reply notification calls already in the same file.
- **Async background task**: Unnecessary. `put_notification` is already fast (single DDB
  `put_item`). No fan-out or external HTTP call involved.

## 5. Testing, Verification & Rollout

### 5.1 Pytest regression test (offline, fails before / passes after)

File: `tests/test_repost_notification.py`

```python
import pytest
from fastapi.testclient import TestClient
from app.main import app
from unittest.mock import patch

client = TestClient(app)

def _headers(uid: str):
    return {"X-User-Id": uid}

def test_repost_sends_post_shared_notification(moto_ddb, alice_user_id, bob_user_id, alice_post_id):
    """
    GAP-0358: create_repost must emit a put_notification(notif_type="post_shared")
    to the original post author.

    Before fix: no notification written, assertion fails.
    After fix: notification item found in DDB, assertion passes.
    """
    # Bob reposts Alice's post
    resp = client.post(f"/ui/posts/{alice_post_id}/repost",
                       json={}, headers=_headers(bob_user_id))
    assert resp.status_code == 201

    # Check Alice has a post_shared notification in DDB
    from app.core.tables import T
    notifs = T.newsfeed.query(
        KeyConditionExpression="pk = :pk",
        ExpressionAttributeValues={":pk": f"NOTIF#{alice_user_id}"},
    ).get("Items", [])

    shared_notifs = [n for n in notifs if n.get("type") == "post_shared"]
    assert len(shared_notifs) == 1  # FAILS before fix
    payload = shared_notifs[0]["payload"]
    assert payload["post_id"] == alice_post_id
    assert payload["from_user_id"] == bob_user_id


def test_self_repost_no_notification(client, alice_user_id, alice_post_id):
    """GAP-0358: self-repost is rejected before any notification is attempted."""
    resp = client.post(f"/ui/posts/{alice_post_id}/repost",
                       json={}, headers=_headers(alice_user_id))
    # Self-repost returns 400, no notification
    assert resp.status_code == 400


@patch("app.routers.newsfeed.put_notification", side_effect=Exception("DDB unavailable"))
def test_repost_succeeds_even_if_notification_fails(mock_notif, client, alice_user_id,
                                                     bob_user_id, alice_post_id):
    """GAP-0358: notification failure must not roll back the repost operation."""
    resp = client.post(f"/ui/posts/{alice_post_id}/repost",
                       json={}, headers=_headers(bob_user_id))
    # Repost still created successfully despite notification error
    assert resp.status_code == 201
    assert resp.json()["ok"] is True
```

### 5.5 Rollout, risks, and effort

- **Effort**: XS (< 30 minutes of code change, < 1 hour of testing)
- **Risk**: VERY LOW. The change is entirely additive. The `try/except` wrapper ensures zero
  regression risk for the repost operation itself.
- **Backward compat**: Existing reposts will not retroactively notify authors. This is
  acceptable and expected.
- **Rollback**: Remove the 10-line `try` block. No DDB schema migration needed.
- **Sequencing**: Can be shipped in the same PR as GAP-0356 (mention alerts), since both
  are additive `put_notification` call site additions in the same file.
