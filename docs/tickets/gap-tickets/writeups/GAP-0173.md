# GAP-0173: SSO-only enforcement not wired into login endpoint — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real file:line. No prior investigation doc; claim verified
> against live code as part of this write-up.

## 1. Summary & Classification

**Plain-English statement**: The `is_sso_only_tenant()` helper is fully implemented in
`app/services/sso_saml_provider.py` (line 152–157). It checks whether the tenant's active
SSO provider has `sso_only = True` and returns a boolean. However, the `POST /session/start`
endpoint in `app/routers/ui_session.py` never calls it. Users belonging to tenants that have
been configured to require SSO-only login can still authenticate with a username and password,
defeating the enterprise SSO policy enforcement that ENTERPRISE-002 section 3.5 requires.

- **Severity**: HIGH
- **Source ticket**: ENTERPRISE-002
- **Status**: Open
- **Owning area**: Backend / Auth / SSO
- **Verdict**: **Confirmed** — `app/routers/ui_session.py` `ui_session_start` (line 63)
  contains no call to `is_sso_only_tenant`. The function is imported in `app/routers/sso_saml.py`
  (line 33) but is only used for the informational `GET /ui/sso/info` endpoint — not for
  enforcement. Password login proceeds regardless of the `sso_only` flag.
- **Related tickets**: ENTERPRISE-002, GAP-0174 (MockSamlAuth in production), SECOPS-007.

## 2. Current-State Investigation (root cause)

### The helper that is never called

`app/services/sso_saml_provider.py` lines 152–157:

```python
def is_sso_only_tenant(tenant_id: str) -> bool:
    """Check if the tenant requires SSO-only login."""
    provider = get_active_provider_for_tenant(tenant_id)
    if not provider:
        return False
    return bool(provider.get("sso_only", False))
```

The function is complete and correct. It queries `get_active_provider_for_tenant` (which
itself queries the `sso_providers` DynamoDB table via `list_providers`, line 87–93), filters
for `status in ("active", "testing")`, and checks the `sso_only` field.

### The login endpoint that ignores it

`app/routers/ui_session.py` lines 63–170 define `ui_session_start`. The function:

1. Resolves `user_sub` via `resolve_dev_or_authenticated_user_sub` (line 68) — which uses
   either a Cognito JWT or local password verification.
2. Checks rate limiting and anomaly detection (lines 74–119).
3. Calls `compute_required_factors(user_sub)` (line 86) for MFA.
4. Creates or challenges the session.

At no point between steps 1 and 4 is the tenant's SSO-only policy checked. The function
does not import `is_sso_only_tenant` and does not read `request.state.tenant_id`.

### The informational endpoint that does use `is_sso_only_tenant`

`app/routers/sso_saml.py` `sso_info` (line 278) returns `"sso_only": bool(provider.get("sso_only", False))` to the frontend. This is advisory: the frontend is expected to show the SSO
login button and hide the password form. But it is **not** enforced server-side. A direct
API call bypasses the UI entirely.

### Where `tenant_id` comes from

When `MULTI_TENANCY_ENABLED=1`, `TenantMiddleware` sets `request.state.tenant_id` per
request based on the Host header domain lookup. When disabled, `TenantMiddleware` sets it
to `S.default_tenant_id` (`"default"`) unconditionally (line 99 of `app/middleware/tenant.py`).
Either value is available inside the endpoint via `req.state.tenant_id`.

When `MULTI_TENANCY_ENABLED=0` and `sso_only=True` on the default tenant's active provider,
the call `is_sso_only_tenant("default")` would still return `True` (since it queries DDB
directly, not via the middleware). The fix therefore works correctly regardless of whether
multi-tenancy is enabled — it is not a multi-tenancy-only feature.

### The frontend SSO info endpoint does not constitute enforcement

`GET /ui/sso/info` returns `"sso_only": true` to the React frontend, which hides the
password form when this is set. However, this is purely a UX hint. The frontend renders on
the client and its behaviour can be overridden by any browser extension, developer tool, or
direct API call. Server-side enforcement is the only reliable control. The gap is precisely
that the server never enforces what the frontend advertises.

## 3. Impact / Exploit / Blast Radius

### Policy bypass

An enterprise customer that has:
- Configured `sso_only = True` on their SSO provider to enforce centralised IdP policy
  (MFA, group membership, conditional access, etc.)
- Disabled or not set passwords for their users (relying on JIT provisioning)

…still has the password login endpoint open. If a user's DDB record happens to have a
`password_hash` (e.g., set before SSO was configured, or via an admin seeding script),
the user can authenticate with the old password and bypass all IdP-enforced controls.

### Compliance implications

SSO-only enforcement is often mandated by compliance frameworks (SOC 2, ISO 27001, HIPAA)
or customer contractual obligations. A documented bypass means audit findings and potential
contract violations.

### Concrete attack path

1. Tenant admin enables `sso_only = True` on provider `sso_abc123` for tenant `acmecorp`.
   They believe this disables password login.
2. Employee Alice's account has an old `password_hash` from before SSO migration. This is
   common: when tenants migrate to SSO via JIT provisioning, the JIT path does not delete
   existing `password_hash` fields.
3. Alice (or an attacker who obtained her old password via phishing, credential stuffing, or
   a prior breach) calls `POST /ui/session/start` directly — not via the browser UI, which
   would show the SSO redirect — with Alice's email/password in `challenge_context`.
4. `resolve_dev_or_authenticated_user_sub` calls `_verify_local_password` (line 304 in
   `ui_session.py`), finds the matching `password_hash` in DDB, and returns
   `alice@acme.com` as the resolved `user_sub`.
5. A full session is created. The tenant's IdP conditional access policies — device
   compliance checks, geofencing, MFA enforcement, real-time account revocation — are
   bypassed entirely. Even if the tenant revoked Alice's IdP account, her local password
   still works on the platform.
6. The attacker has a valid `ui_session` cookie. All session-gated API endpoints are now
   accessible, including messaging, file manager, and billing — the same scope as a
   legitimate login via SSO.

The attack requires only Alice's email and password, both of which may be available from
prior breach databases for large-scale credential stuffing campaigns.

### Blast radius

All tenants with `sso_only = True` in the `sso_providers` DDB table. Does not affect
tenants without an active SSO provider (those get `False` from `is_sso_only_tenant`).
For each affected tenant, every user who retains a valid `password_hash` in DDB can
bypass the SSO policy — potentially including service accounts, test users, and accounts
created before SSO migration. A thorough remediation should also include a post-deploy
cleanup step that removes or nullifies `password_hash` fields for users on `sso_only`
tenants, though this is outside the scope of the code fix itself.

## 4. Fix Design (code-level)

### Change to `app/routers/ui_session.py`

Add a single guard at the top of `ui_session_start`, immediately after the root-user check,
before any session-creation logic runs:

```python
# app/routers/ui_session.py

from app.services.sso_saml_provider import is_sso_only_tenant  # add import

@router.post("/session/start", response_model=UiSessionStartResp)
async def ui_session_start(
    req: Request,
    body: UiSessionStartReq,
    response: Response = None,
    user_sub: str = Depends(resolve_dev_or_authenticated_user_sub),
):
    if response is None:
        response = Response()
    if user_sub == (S.root_user_sub or "").strip():
        raise HTTPException(status_code=403, detail="Root login must use /auth/root/login")

    # ── SSO-only enforcement ────────────────────────────────────────────
    if S.sso_saml_enabled:
        tenant_id = getattr(getattr(req, "state", None), "tenant_id", None) or S.default_tenant_id
        if is_sso_only_tenant(tenant_id):
            raise HTTPException(
                status_code=403,
                detail={
                    "code": "sso_only",
                    "message": "Password login is disabled for this tenant. Use SSO.",
                    "sso_login_url": f"/saml/login?tenant={tenant_id}",
                },
            )
    # ── End SSO-only enforcement ────────────────────────────────────────

    rate_limit_login_attempt(user_sub, client_ip_from_request(req))
    ...
```

Key design decisions:

- The check is placed **after** `user_sub` is resolved so the dependency is already called
  (allows consistent error handling), but before any session is written.
- The guard is wrapped in `if S.sso_saml_enabled` so it is completely skipped when SSO is
  not configured — zero overhead for non-SSO deployments.
- Returning 403 (not 401) because the user is identifiable but forbidden by policy.
- The error body includes `sso_login_url` so the frontend can redirect without a separate
  `GET /ui/sso/info` round trip.

### No change needed in `app/services/sso_saml_provider.py`

`is_sso_only_tenant` is already correct. No signature changes.

### Dev/prod parity (SECOPS-007)

- `is_sso_only_tenant` queries DynamoDB. In dev, DynamoDB Local (port 8001) is used; in
  prod, real DynamoDB. The code path is identical.
- The `S.sso_saml_enabled` guard mirrors the pattern used in `app/routers/sso_saml.py`
  (e.g., line 51, line 84) — same flag, same semantics.
- No mock implementation is added. In dev tests, the DDB mock (moto) returns the seeded
  provider record, enabling full offline testing.

### Backward compatibility

- Tenants without a SSO provider configured: `is_sso_only_tenant` returns `False` because
  `get_active_provider_for_tenant` returns `None`. No change in behaviour.
- Tenants with `sso_only = False` (the default): function returns `False`. No change.
- Tenants with `sso_only = True`: password login now correctly blocked. This is a
  **breaking change for misconfigured tenants** — intentional, as it enforces the configured
  policy. Operators should audit active `sso_only` flags before deploying.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

`tests/test_sso_only_enforcement.py`:

```python
import pytest
from unittest.mock import patch
from fastapi.testclient import TestClient
from app.main import app

SSO_ONLY_PROVIDER = {
    "provider_id": "sso_test01",
    "tenant_id": "default",
    "status": "active",
    "sso_only": True,
    "sso_login_url": "/saml/login?tenant=default",
}

NON_SSO_ONLY_PROVIDER = {
    "provider_id": "sso_test02",
    "tenant_id": "default",
    "status": "active",
    "sso_only": False,
}

@pytest.fixture
def client():
    return TestClient(app)

def test_password_login_blocked_for_sso_only_tenant(client):
    """
    BEFORE fix: POST /session/start returns 200 (or 401 for wrong credentials)
                for an sso_only tenant — policy bypass.
    AFTER fix:  POST /session/start returns 403 with code='sso_only'.
    """
    with patch("app.services.sso_saml_provider.get_active_provider_for_tenant",
               return_value=SSO_ONLY_PROVIDER), \
         patch("app.core.settings.S.sso_saml_enabled", True), \
         patch("app.auth.deps._verify_local_password", return_value="alice@test.local"), \
         patch("app.core.settings.S.dev_mode", True):
        resp = client.post("/ui/session/start", json={
            "challenge_context": {"username": "alice@test.local", "password": "secret"}
        })
    assert resp.status_code == 403
    body = resp.json()
    assert body["detail"]["code"] == "sso_only"
    assert "sso_login_url" in body["detail"]

def test_password_login_allowed_for_non_sso_only_tenant(client):
    """Tenants without sso_only=True must not be affected."""
    with patch("app.services.sso_saml_provider.get_active_provider_for_tenant",
               return_value=NON_SSO_ONLY_PROVIDER), \
         patch("app.core.settings.S.sso_saml_enabled", True), \
         patch("app.auth.deps._verify_local_password", return_value="bob@test.local"), \
         patch("app.core.settings.S.dev_mode", True):
        resp = client.post("/ui/session/start", json={
            "challenge_context": {"username": "bob@test.local", "password": "secret"}
        })
    # Should proceed past the sso_only check (may fail for other reasons,
    # but must NOT be 403 with code=sso_only)
    if resp.status_code == 403:
        assert resp.json().get("detail", {}).get("code") != "sso_only"

def test_password_login_allowed_when_sso_disabled(client):
    """When SSO feature flag is off, sso_only check must be skipped entirely."""
    with patch("app.core.settings.S.sso_saml_enabled", False), \
         patch("app.auth.deps._verify_local_password", return_value="carol@test.local"), \
         patch("app.core.settings.S.dev_mode", True):
        resp = client.post("/ui/session/start", json={
            "challenge_context": {"username": "carol@test.local", "password": "secret"}
        })
    if resp.status_code == 403:
        assert resp.json().get("detail", {}).get("code") != "sso_only"
```

### Manual QA steps

1. Seed an SSO provider record in DynamoDB with `sso_only = True` for `tenant_id = "default"`.
2. Start the stack.
3. Attempt to log in via the UI login form with email/password: confirm the response is
   HTTP 403 and the UI shows the "Use SSO login" redirect link.
4. Navigate to `/saml/login?tenant=default` (the SSO flow) and confirm login succeeds.
5. Change the provider record to `sso_only = False`: confirm password login works again.

### Metrics / observability

Add `sso_only_password_login_rejected_total{tenant_id}` counter at the 403 point. Alert
if this spikes — could indicate users confused about migration or automated credential
stuffing bypassing the frontend.

### Rollout

1. **Pre-deploy audit**: Scan DDB `sso_providers` table for all records with `sso_only = true`
   and `status in ("active", "testing")`. For each tenant, verify that the SSO flow is
   operational (can complete a test login via `/saml/acs?dev_bypass=1`). If the SSO flow is
   broken for a tenant with `sso_only = true`, all users of that tenant would be locked out
   after the fix — resolve SSO issues first.
2. **Communication**: Notify affected tenants 48 hours in advance via in-app announcement
   or email. The message should explain that password login is being disabled in accordance
   with their SSO-only configuration.
3. **Deploy**: The guard is wrapped in `if S.sso_saml_enabled` and checks DDB only for
   tenants that have SSO configured. The code adds a single DDB `query()` call per login
   attempt for SSO-enabled tenants. This is acceptable overhead (~1–2ms) given that login
   is not a high-frequency hot path.
4. **Monitor**: Watch `sso_only_password_login_rejected_total` for the first 24 hours.
   Unexpected spikes (e.g., hundreds of rejections for a tenant) indicate a misconfigured
   `sso_only` flag or a broken SSO flow that users are trying to work around.
5. **Rollback**: Remove the guard block if a rollback is needed. The `sso_only` flag in
   DDB remains unchanged — the feature can be re-enabled by redeploying.

**Effort**: S (1 day: one import, one 10-line guard block, three test cases, one metrics
counter).

**Risk**: Low for tenants with `sso_only = False` (zero code path change — `is_sso_only_tenant`
returns `False` in constant time for providers without the flag). For tenants with
`sso_only = True`, this is an intentional breaking change that enforces the configured
policy. The `sso_login_url` in the 403 error body allows the frontend to display a helpful
redirect button rather than an opaque error message. One edge case: a tenant can have
`sso_only = true` with no active SSO provider — in this configuration `is_sso_only_tenant`
returns `False` (line 154 of `sso_saml_provider.py`: `if not provider: return False`), so
users are not accidentally locked out by a misconfigured or deleted provider.
