# GAP-0132: Marketplace refund missing seller-side debit — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. Build on the
> investigation doc (docs/tickets/gap-tickets/investigations/GAP-0132.md) if it exists.

## 1. Summary & Classification

**Bug statement**: When an admin approves a marketplace refund request, the approval path credits
the buyer's billing ledger but does not write a corresponding debit entry under the seller (or
content creator) who originally received the funds. The seller retains the credit earned from a
tipped message, unlocked post, or other paid content even after the buyer is made whole, enabling
double-enrichment.

**Claim accuracy**: The GAP ticket cites `app/routers/billing.py:1164–1179` as the location, but
after reading the code, the actual marketplace refund approve path lives in a separate service:
`app/services/refund_requests.py`, specifically `approve_request()` at lines 172–241. The line
numbers in `billing.py:1164–1179` correspond to the Stripe stripe-direct refund endpoint
(`refund_payment()`), which handles a different flow (admin-initiated Stripe refund, not the
user-submitted BILLING-001 refund-request flow). The gap claim is accurate in substance — the
seller-side debit is indeed missing — but the cited location is partially wrong. Claim corrected
for location; claim confirmed for the bug.

- **Severity**: HIGH — financial double-enrichment
- **Source ticket**: BILLING-001
- **Status**: Open
- **Owning area**: Billing / Marketplace / Refund lifecycle
- **Related tickets**: BILLING-001, SECOPS-007, GAP-0026 (revenue split hooks absent)

## 2. Current-State Investigation (root cause)

### Two distinct refund flows

The codebase has two refund mechanisms:

| Flow | Trigger | Location |
|---|---|---|
| Stripe direct refund | Admin POSTs `/ui/billing/refund` | `billing.py:1144–1202` |
| BILLING-001 request/approve | User submits → Admin approves `/ui/admin/refund-requests/{id}/approve` | `refund_requests.py:172–241` |

The gap is in the second flow. The first flow (`billing.py:1164`) also has no explicit seller debit,
but that path calls `mark_reverted()` on the purchase transaction and adjusts Stripe state — it
does not model a tip/unlock revenue transfer in the first place because the Stripe path is for
direct payment reversals rather than peer-to-peer content purchases.

### The BILLING-001 approve path

`app/services/refund_requests.py:172–241` (`approve_request()`):

```python
# refund_requests.py:196-210  (buyer credit — present)
pk = user_pk(user_id)
led_sk, led_item = new_ledger_entry(
    key_name="pk",
    key_value=pk,
    entry_type="refund_credit",
    amount_cents=amount,
    state="settled",
    reason="Refund approved",
    meta={"refund_request_id": request_id, "admin_notes": notes or ""},
)
ddb_put(T.billing, led_item)

# refund_requests.py:212-213  (buyer balance delta — present)
apply_balance_delta(
    T.billing, pk, {"payments_settled_cents": -amount},
    currency=item.get("currency", "usd").lower()
)
```

**What is absent**: after crediting the buyer there is no lookup of the original tip/unlock
recipient (seller / creator) and no corresponding debit written under `USER#{seller_id}`.

### How the original purchase was recorded

When `write_tip_ledger()` executes (`app/services/tip_ledger.py:88–174`), it writes:
- `pk = USER#{tipper_user_id}`, `sk = LEDGER#{ts}#{debit_id}`, `type = "debit"` — buyer pays
- `pk = USER#{recipient_user_id}`, `sk = LEDGER#{ts}#{credit_id}`, `type = "credit"` — seller earns

The refund path reverses only the first entry (restoring buyer balance) without touching the second
(seller credit remains `state=settled`).

### Missing fields on the refund request record

The `create_refund_request()` function stores `transaction_entry_id` (the buyer's `LEDGER#` sk) and
`requester_user_id`, but does **not** store the paired `recipient_user_id` / `seller_user_id` at
creation time. This means `approve_request()` cannot trivially look up the seller's ledger entry
without re-reading the billing table.

The `meta` field on the original buyer-debit entry does contain `recipient_user_id` (set by
`_build_meta()` at `tip_ledger.py:73–87`), so the approve path can recover the seller by fetching
the original ledger item.

### Runtime manifestation

1. User Alice buys a $5.00 tip on a message.
2. Tip ledger writes: Alice −$5.00, Creator Bob +$5.00.
3. Alice submits a refund request citing her debit ledger entry.
4. Admin approves. Alice receives +$5.00 credit.
5. Bob's +$5.00 credit ledger entry remains; Bob retains $5.00.
6. Platform has dispensed $10.00 of value from a single $5.00 transaction.

## 3. Impact / Exploit / Blast Radius

### Who is affected

- **Platform**: Net financial loss equal to the approved refund amount for every tip/unlock refund.
- **Sellers / Creators**: No direct harm; they retain revenue they are not entitled to after a
  reversal. This creates audit discrepancies and incorrect earnings dashboards.
- **Buyers**: No direct harm; they receive correct refunds. However, if the platform absorbs losses
  indefinitely the viability of the refund programme is at risk.

### Concrete exploit walkthrough

An adversarial user who controls both a buyer account and a creator account can:

1. Creator account lists a message unlock at $50.
2. Buyer account purchases the unlock via `POST /ui/messaging/messages/{id}/unlock` or similar.
   Tip ledger writes buyer −$50, creator +$50.
3. Buyer account submits a refund request within the refund window.
4. Platform admin (or automated policy) approves: buyer +$50.
5. Creator account withdraws the $50 credit (via payout endpoint).
6. Net effect: buyer spent $0, creator received $50 — platform absorbs $50 loss per cycle.

This is a double-spend / chargeback-equivalent exploit with no technical friction; it requires only
that the user can reach admin approval for the refund request.

### Blast radius

- Financial impact scales with the refund window (`S.refund_request_window_days`) and the number of
  tip/unlock transactions.
- At 1 000 monthly refund-request approvals averaging $10 each, the monthly exposure is $10,000.
- No DynamoDB constraints prevent the ledger from going negative; balance deltas are applied
  unconditionally.

### Compliance note

Unmatched debit/credit pairs cause the bilateral ledger to fail internal reconciliation. Audit
reports will show inflated creator earnings vs. buyer spend, which may violate accounting standards
if the platform operates in a regulated jurisdiction.

## 4. Fix Design (code-level)

### Principle

When approving a refund for a transaction that originated from `write_tip_ledger()` or
`unlock_message()`, the approve path must:

1. Look up the original buyer-debit ledger entry.
2. Determine the `recipient_user_id` from its `meta` field.
3. Write a matching debit entry under the seller's `USER#{seller_id}` pk.
4. Apply a corresponding negative balance delta to the seller.

### Proposed change to `approve_request()` in `app/services/refund_requests.py`

```python
def approve_request(
    request_id: str,
    admin_id: str,
    notes: Optional[str] = None,
    override_amount_cents: Optional[int] = None,
    request_obj: Any = None,
) -> Dict[str, Any]:
    item = get_request(request_id)
    if not item:
        raise HTTPException(404, "Refund request not found")
    if item.get("status") != "pending":
        raise HTTPException(400, f"Request is not pending (status={item.get('status')})")

    amount = override_amount_cents or int(item.get("amount_cents", 0))
    if amount <= 0:
        raise HTTPException(400, "Invalid refund amount")

    ts = now_ts()
    user_id = item["requester_user_id"]
    pk = user_pk(user_id)

    # --- NEW: Look up the original ledger entry to find the seller ---
    transaction_entry_id = item.get("transaction_entry_id", "")
    original_entry = None
    seller_user_id = None
    if transaction_entry_id:
        # Re-fetch the buyer's original debit ledger entry by entry_id
        scan_resp = T.billing.query(
            KeyConditionExpression="pk = :pk AND sk BEGINS_WITH :prefix",
            ExpressionAttributeValues={":pk": pk, ":prefix": "LEDGER#"},
        )
        for entry in scan_resp.get("Items", []):
            if entry.get("entry_id") == transaction_entry_id:
                original_entry = entry
                break
        if original_entry:
            meta = original_entry.get("meta") or {}
            seller_user_id = meta.get("recipient_user_id")

    # --- Existing: Credit the buyer ---
    led_sk, led_item = new_ledger_entry(
        key_name="pk",
        key_value=pk,
        entry_type="refund_credit",
        amount_cents=amount,
        state="settled",
        reason="Refund approved",
        meta={
            "refund_request_id": request_id,
            "admin_notes": notes or "",
            "original_entry_id": transaction_entry_id,
        },
    )
    ddb_put(T.billing, led_item)
    apply_balance_delta(
        T.billing, pk, {"payments_settled_cents": -amount},
        currency=item.get("currency", "usd").lower()
    )

    # --- NEW: Debit the seller if identifiable ---
    if seller_user_id:
        seller_pk = user_pk(seller_user_id)
        _, seller_debit_item = new_ledger_entry(
            key_name="pk",
            key_value=seller_pk,
            entry_type="refund_debit",
            amount_cents=amount,
            state="settled",
            reason="Refund clawback",
            meta={
                "refund_request_id": request_id,
                "buyer_user_id": user_id,
                "original_entry_id": transaction_entry_id,
            },
        )
        ddb_put(T.billing, seller_debit_item)
        apply_balance_delta(
            T.billing, seller_pk,
            {"payments_settled_cents": -amount},
            currency=item.get("currency", "usd").lower(),
        )
        logger.info(
            "refund_seller_debit_written",
            extra={
                "refund_request_id": request_id,
                "seller_user_id": seller_user_id,
                "amount_cents": amount,
            },
        )
    else:
        logger.warning(
            "refund_seller_not_found; skipping seller debit",
            extra={"refund_request_id": request_id, "transaction_entry_id": transaction_entry_id},
        )

    # ... (rest of function unchanged: status update, write_alert, audit_event) ...
```

### Handling transactions where no seller exists

Not all buyer-debit ledger entries have a peer credit (e.g., a Stripe checkout deposit). The code
uses a defensive `if seller_user_id:` guard and logs a warning rather than raising an exception.
This prevents a refund approval failure for non-tip/unlock transactions while still producing a
visible log signal for investigation.

### Atomicity consideration

DynamoDB does not support cross-partition transactions larger than 100 items, but a two-item write
(buyer credit + seller debit) fits comfortably within `transact_write_items()`. Using a
`TransactWriteItems` call would guarantee either both writes succeed or neither does, preventing a
half-applied refund. The implementation above uses two separate `ddb_put()` calls for simplicity;
production hardening should migrate to `transact_write_items()`.

### Dev/Prod parity (SECOPS-007)

`new_ledger_entry()` and `apply_balance_delta()` are provider-agnostic DynamoDB writes that behave
identically in dev (DynamoDB Local port 8001) and prod (DynamoDB in AWS). There are no
mock-specific code paths in `approve_request()`. No feature flag is needed; the seller-debit logic
should be unconditionally active.

### Backward-compatibility / migration

Existing approved-but-unmatched refunds are historical data. A migration script can identify them
by scanning `T.refund_requests` for `status=approved` items created before this fix and reconciling
them manually or via a one-time correction job. The correction job is low urgency; the fix prevents
future divergence.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline — moto-mocked DynamoDB)

```python
# tests/test_refund_requests.py
import pytest
from moto import mock_aws
from app.services.refund_requests import approve_request, create_refund_request
from app.services.tip_ledger import TipLedgerEntry, write_tip_ledger
from app.services.billing_shared import user_pk
from app.core.tables import T


@mock_aws
class TestRefundApproveSellerDebit:
    """GAP-0132: seller debit written on refund approve."""

    def setup_method(self):
        # Create billing table (simplified; real setup uses conftest fixtures)
        T.billing.create_table(...)
        T.refund_requests.create_table(...)

    def test_seller_debit_written_on_tip_refund(self):
        """
        FAILS BEFORE FIX: seller ledger entry is absent after approve.
        PASSES AFTER FIX: seller carries a 'refund_debit' entry.
        """
        buyer_id = "buyer_001"
        seller_id = "seller_001"
        amount = 500  # $5.00

        # 1. Write a tip from buyer to seller
        entry_ids = write_tip_ledger(TipLedgerEntry(
            tipper_user_id=buyer_id,
            recipient_user_id=seller_id,
            amount_cents=amount,
            content_type="message",
            content_id="msg_001",
        ))
        buyer_debit_id = entry_ids["debit_entry_id"]

        # 2. Buyer submits refund request
        rr = create_refund_request(
            user_id=buyer_id,
            transaction_entry_id=buyer_debit_id,
            reason="I regret this tip",
        )
        request_id = rr["refund_request_id"]

        # 3. Admin approves
        approve_request(request_id=request_id, admin_id="admin_001")

        # 4. Verify buyer credit ledger entry exists
        buyer_entries = T.billing.query(
            KeyConditionExpression="pk = :pk",
            ExpressionAttributeValues={":pk": f"USER#{buyer_id}"},
        )["Items"]
        refund_credits = [e for e in buyer_entries if e.get("type") == "refund_credit"]
        assert len(refund_credits) == 1
        assert int(refund_credits[0]["amount_cents"]) == amount

        # 5. Verify seller DEBIT entry exists  <-- fails before fix
        seller_entries = T.billing.query(
            KeyConditionExpression="pk = :pk",
            ExpressionAttributeValues={":pk": f"USER#{seller_id}"},
        )["Items"]
        refund_debits = [e for e in seller_entries if e.get("type") == "refund_debit"]
        assert len(refund_debits) == 1, "Seller debit entry must be written on refund approval"
        assert int(refund_debits[0]["amount_cents"]) == amount
```

### Manual QA steps

1. Create two accounts: Buyer and Seller.
2. Buyer sends a $10.00 tip to a Seller message via API.
3. Confirm Seller ledger shows `+$10.00` credit entry.
4. Buyer submits refund request.
5. Admin approves via `/ui/admin/refund-requests/{id}/approve`.
6. Confirm Buyer ledger shows `+$10.00` refund credit.
7. **Before fix**: Seller ledger still shows only the original `+$10.00` credit; no debit entry.
8. **After fix**: Seller ledger shows a `−$10.00` refund debit entry.
9. Net seller balance should return to zero for the transaction.

### Metrics / observability

- Add counter metric `refund_seller_debit_written_total` incremented on success.
- Add counter metric `refund_seller_not_found_total` incremented when `seller_user_id` is None
  (to track non-tip refunds vs. potential data loss).
- Alert if `refund_seller_not_found_total / refund_seller_debit_written_total > 0.10` (more than
  10% of approved refunds cannot find a seller), which would suggest a metadata schema change.

### Rollback

Because the fix only adds new ledger writes and does not modify any existing record, rollback is
safe: deploying the previous version will simply stop writing seller debit entries; existing
historical debit entries are inert (they reduce seller balance; reversing them requires a
subsequent credit, which a rollback would not generate automatically — manual intervention needed).

### Effort / Sequencing

- **Effort**: M (service change + test + migration script)
- **Risk**: Low for new transactions; Medium for migration of historical records (requires audit)
- **Sequencing**: Block on confirming `new_ledger_entry()` `entry_type` field is indexed/visible
  in creator earnings dashboards so `"refund_debit"` entries render correctly in the UI.
