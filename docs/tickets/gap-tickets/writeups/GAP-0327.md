# GAP-0327: No rate limiting on `GET /ui/export/csv` (SEC-007 cross-ref) — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing; cites `file:line`.

## 1. Summary & Classification

**Severity**: HIGH
**Source ticket**: PLATFORM-009
**Owning area**: Data export / API rate-limiting
**Status**: Open — no rate-limiting call present in the endpoint handler

**Plain-English statement**: The `GET /ui/export/csv` endpoint performs unbounded DynamoDB pagination across up to three large tables (billing ledger, contacts, questionnaire responses) on every call. Any authenticated user can invoke it in rapid succession to bulk-exfiltrate data and to drive excessive DynamoDB read capacity. The ticket specification (PLATFORM-009, section 9.5) required a 5-requests-per-minute-per-user rate limit wired through the existing `_bucket_limit` / `can_send_alert_channel` pattern; that wiring was never added.

**Verdict**: Claim confirmed. `app/routers/csv_export.py:22–101` contains the complete handler. There is no call to any rate-limit function — no `_bucket_limit`, no `rate_limit_or_429`, no `can_send_alert_channel`, and no HTTP 429 response anywhere in the file. The `rate_limit.py` service has a fully-functional `_bucket_limit` primitive that can enforce this limit without additional infrastructure.

**Related tickets**: SEC-007 (rate-limiting policy), PLATFORM-009 (CSV export feature), GAP-0003 (other unprotected endpoints).

## 2. Current-State Investigation (root cause)

### Handler — no rate-limit guard

`app/routers/csv_export.py:22–56` (full handler preamble):

```python
@router.get("/export/csv")
async def export_csv(
    source: str = Query(..., pattern=r"^(billing_ledger|contacts|questionnaire_responses)$"),
    from_date: Optional[int] = Query(None, ge=0),
    to_date:   Optional[int] = Query(None, ge=0),
    questionnaire_id: Optional[str] = Query(None, min_length=1, max_length=120),
    ctx=Depends(require_ui_session),
):
    user_sub = ctx["user_sub"]
    # Validate questionnaire ownership if needed
    ...
    rows = generate_csv_rows(source, user_sub, ...)
    return StreamingResponse(rows, media_type="text/csv; charset=utf-8", ...)
```

After extracting `user_sub`, the handler immediately delegates to `generate_csv_rows()`. There is no check against any rate-limit store before this call.

### What the rate-limit infrastructure provides

`app/services/rate_limit.py:60–79` provides `_bucket_limit(user_sub, sid, max_n, win) -> bool`:

- On first call in the window: writes a token-bucket record to the `sessions` table (`bucket_start=now, bucket_count=1`) and returns `True`.
- On subsequent calls: increments `bucket_count` and returns `True` while `count < max_n`; returns `False` once exhausted.
- Window resets when `(now - bucket_start) >= win`.
- The `sid` (session-ID discriminator) is an arbitrary string key, so adding a new limit type requires no schema change.

`app/services/rate_limit.py:321–332` (`can_send_alert_channel`) uses the same primitive with alert-channel-specific settings; the pattern for a new `"csv_export"` channel is identical.

### DynamoDB cost of one unguarded call

`app/services/csv_export.py` (not shown in detail but inferred from endpoint contract): each call to `generate_csv_rows` for `source="contacts"` paginates `T.contacts` with `Limit` up to 50,000 rows per user, consuming multiple RCUs per page. For `billing_ledger`, the same applies to the billing table. At 60 calls/minute, a single user can sustain a DynamoDB read storm large enough to impact other users on a provisioned-capacity table.

### Data exfiltration angle

Because each call returns a full CSV download, 60 rapid calls download 60 complete snapshots of the user's billing history and contacts. For a compromised account (or for an insider threat), this provides a mechanism to exfiltrate data faster than any audit or anomaly detection system tuned for human-paced exports.

## 3. Impact / Exploit / Blast Radius

**Who is affected**: All users (availability via DDB read exhaustion), plus individual users whose accounts may be scraped by an attacker with session access.

**Concrete exploit walkthrough**:
1. Attacker obtains a valid authenticated session (phished cookie, compromised account).
2. Attacker runs a loop: `for i in range(1000): GET /ui/export/csv?source=billing_ledger`
3. Each request paginates the user's complete billing ledger from DynamoDB.
4. No 429 response is ever returned; all 1,000 requests succeed.
5. Attacker receives 1,000 CSV files in seconds; total data exfiltration is limited only by network bandwidth.
6. Side effect: DDB table read throughput is exhausted or, on on-demand billing, AWS charges spike.

**Data sensitivity**: Billing ledger rows contain transaction amounts, payment method references, and timestamps. Contacts rows contain names, email addresses, and phone numbers. In a GDPR context, unrestricted programmatic bulk export of a user's contact list may also violate data minimisation principles if the export is not expected to be automated.

**Availability impact**: On DynamoDB provisioned capacity: a single user at 60 requests/minute can consume all allocated RCUs for the contacts table, causing `ProvisionedThroughputExceededException` for all other users querying the same table.

## 4. Fix Design (code-level)

### 4.1 Wire the rate-limit check into the handler

`app/routers/csv_export.py` — add two imports and one guard block at the top of the handler body:

```python
# Add to existing imports
from fastapi import APIRouter, Depends, HTTPException, Query
# (already present — add the rate_limit import)
from app.services.rate_limit import _bucket_limit
```

Inside `export_csv()`, immediately after `user_sub = ctx["user_sub"]`:

```python
# Rate limit: 5 exports per 60 seconds per user (PLATFORM-009 §9.5, SEC-007).
_CSV_EXPORT_MAX = 5
_CSV_EXPORT_WINDOW = 60  # seconds

if not _bucket_limit(user_sub, "rl#csv_export", _CSV_EXPORT_MAX, _CSV_EXPORT_WINDOW):
    raise HTTPException(
        status_code=429,
        detail="Export rate limit exceeded; maximum 5 exports per minute.",
        headers={"Retry-After": str(_CSV_EXPORT_WINDOW)},
    )
```

The constants `_CSV_EXPORT_MAX` and `_CSV_EXPORT_WINDOW` can optionally be promoted to `Settings` if operational teams need to tune them without a code deploy:

```python
# In app/core/settings.py
csv_export_max_per_window: int = int(os.environ.get("CSV_EXPORT_MAX_PER_WINDOW", "5"))
csv_export_window_seconds: int = int(os.environ.get("CSV_EXPORT_WINDOW_SECONDS", "60"))
```

Then in `csv_export.py`:
```python
if not _bucket_limit(user_sub, "rl#csv_export",
                     S.csv_export_max_per_window,
                     S.csv_export_window_seconds):
    raise HTTPException(status_code=429, detail="Export rate limit exceeded.",
                        headers={"Retry-After": str(S.csv_export_window_seconds)})
```

### 4.2 `_bucket_limit` no-op in dev mode

`_bucket_limit` calls `_sessions_table_enabled()` (`rate_limit.py:13–14`), which returns `False` when `S.ddb_sessions_table` is empty. In dev mode, `ddb_sessions_table` is always set (it is populated by `local-ddb-init.py`), so the bucket logic runs against DynamoDB Local. This is the correct dev/prod parity behaviour: rate limits fire in dev, ensuring E2E tests can observe a 429 without requiring production AWS.

The `Retry-After` header conforms to RFC 6585 and ensures clients (including the React frontend) can implement correct back-off logic rather than hammering the endpoint.

### 4.3 Retry-After header in the frontend client

`frontend/src/api/client.ts` currently handles HTTP 401 by calling `logout()`. The 429 status should be handled gracefully. Add a response interceptor for 429 that surfaces a user-visible toast message:

```typescript
// In the axios response error interceptor (client.ts)
if (error.response?.status === 429) {
  const retryAfter = error.response.headers['retry-after'] ?? '60';
  throw new Error(`Export rate limit exceeded. Please wait ${retryAfter} seconds.`);
}
```

This prevents a confusing UI where the download silently fails with no feedback.

### 4.4 Dev/Prod parity (SECOPS-007)

The `_bucket_limit` function's DynamoDB backend is the same `sessions` table in both dev (DynamoDB Local on port 8001) and production (AWS DynamoDB). No mock or conditional path is needed. The rate-limit counter persists across backend restarts within the same session table, matching production behaviour. The only difference is that DynamoDB Local does not enforce per-table throughput limits, so the rate-limit guard in dev is enforced at the application layer (counter check), which is the correct layer.

### 4.5 Alternatives considered

**Middleware-level rate limiting** (e.g., SlowAPI / fastapi-limiter): rejected because the project has no existing middleware-based rate limiter and introducing a new dependency for a single endpoint is disproportionate. The `_bucket_limit` primitive already handles all other rate-limited endpoints in the system and uses the same DynamoDB table, so no new infrastructure is required.

**IP-based limiting in addition to user-based**: worthwhile for anonymous protection, but `GET /ui/export/csv` requires authentication (`Depends(require_ui_session)`), so a per-user limit is sufficient. An IP check could be added as a second layer if the threat model expands.

## 5. Testing, Verification & Rollout

### Regression test (pytest offline)

Add to `tests/test_csv_export.py` (new file) or to an existing endpoint test file:

```python
import pytest
from fastapi.testclient import TestClient
from unittest.mock import patch, MagicMock

# Assumes conftest.py provides `client` (TestClient) and `alice_session_headers`


class TestCsvExportRateLimit:
    """GAP-0327: GET /ui/export/csv must return 429 after 5 requests per minute."""

    def _make_request(self, client, headers):
        return client.get(
            "/ui/export/csv",
            params={"source": "contacts"},
            headers=headers,
        )

    def test_first_five_succeed(self, client, alice_session_headers):
        """First 5 requests in a window must succeed (2xx or start streaming)."""
        # BEFORE fix: all succeed; AFTER fix: first 5 still succeed
        for i in range(5):
            resp = self._make_request(client, alice_session_headers)
            assert resp.status_code != 429, f"Request {i+1} unexpectedly rate-limited"

    def test_sixth_request_is_429(self, client, alice_session_headers):
        """FAILS before fix: 6th request returns 200; PASSES after fix: returns 429."""
        for _ in range(5):
            self._make_request(client, alice_session_headers)
        resp = self._make_request(client, alice_session_headers)
        # BEFORE fix: status_code=200 → assertion fails
        # AFTER fix:  status_code=429 → assertion passes
        assert resp.status_code == 429
        assert "retry-after" in resp.headers or "Retry-After" in resp.headers

    def test_retry_after_header_present(self, client, alice_session_headers):
        """429 response must include a Retry-After header."""
        for _ in range(5):
            self._make_request(client, alice_session_headers)
        resp = self._make_request(client, alice_session_headers)
        assert resp.status_code == 429
        retry_after = resp.headers.get("retry-after") or resp.headers.get("Retry-After")
        assert retry_after is not None
        assert int(retry_after) > 0

    def test_different_users_independent_buckets(
        self, client, alice_session_headers, bob_session_headers
    ):
        """Rate limit is per-user; Bob's limit is unaffected by Alice's exhaustion."""
        for _ in range(6):
            self._make_request(client, alice_session_headers)
        # Bob should still get a non-429 on his first request
        resp = self._make_request(client, bob_session_headers)
        assert resp.status_code != 429
```

**Fails before fix**: `test_sixth_request_is_429` receives `200 OK` because no rate-limit guard is present.
**Passes after fix**: the `_bucket_limit` call returns `False` on the 6th request and the handler raises `HTTPException(429)`.

### Rollout

- **Effort**: S (small — ~10 lines of code, no schema changes)
- **Risk**: Very low. The change only adds a 429 path that previously did not exist; existing successful paths are unchanged.
- **Rollback**: Remove the `_bucket_limit` call and redeploy; the endpoint reverts to unguarded behaviour instantly.
- **Sequencing**: Can deploy independently of any other gap fix. No database migration required; the `sessions` table already exists.
- **Frontend work**: The `Retry-After` header handling in `client.ts` is a small enhancement; it can be deferred to a follow-up PR without blocking the backend fix.
