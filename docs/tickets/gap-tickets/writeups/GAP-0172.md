# GAP-0172: `TenantMiddleware` blocks root admin from accessing suspended tenants — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real file:line. No prior investigation doc; claim verified
> against live code as part of this write-up.

## 1. Summary & Classification

**Plain-English statement**: `TenantMiddleware` returns an HTTP 503 whenever a resolved
tenant record has `status == "suspended"`. There is no escape hatch for ROOT-role sessions.
A suspended default tenant therefore locks every operator out of the platform permanently,
including the root admin whose job is to investigate and remediate the suspension. An
adversary with write access to DynamoDB (or a billing engine misconfiguration) could weaponise
this to stage a denial-of-service against the operator.

- **Severity**: HIGH
- **Source ticket**: ENTERPRISE-001
- **Status**: Open
- **Owning area**: Backend / Multi-tenancy / Auth
- **Verdict**: **Confirmed** — `app/middleware/tenant.py` lines 131–136 return 503
  unconditionally for `status == "suspended"` with no role-based bypass. The ticket design
  (ENTERPRISE-001 section 3.4) explicitly requires root admin bypass.
- **Related tickets**: GAP-0171 (tenant_id in AuthenticatedUser), ENTERPRISE-001, SECOPS-007.

## 2. Current-State Investigation (root cause)

### The blocking code

`app/middleware/tenant.py` lines 131–141:

```python
# Check tenant status
status = str(tenant_record.get("status", "active")).lower()
if status == "suspended":
    return JSONResponse(
        status_code=503,
        content={"detail": "Tenant is suspended"},
    )
if status == "deleted":
    return JSONResponse(
        status_code=410,
        content={"detail": "Tenant has been deleted"},
    )
```

These two checks execute **before** `call_next` — i.e., before any auth dependency runs.
FastAPI/Starlette middleware cannot call `Depends(require_root_session)` because middleware
executes outside the DI framework. The request object at this point contains raw cookies and
headers that have not yet been processed by any auth layer.

### What is present

- `request.cookies` is available: the `ui_access_token` cookie, if present, contains a
  signed HS256 JWT with a `role` claim.
- `request.headers` is available: the `Authorization` header with a Bearer token would
  be present for API clients.
- The `S.ui_access_token_secret` signing key is available at module import time via the
  settings singleton.

### What is missing

No code in `TenantMiddleware` inspects the incoming credentials before returning 503. The
function `_decode_jwt_payload` in `app/auth/deps.py` (line 94) is a lightweight,
dependency-free helper that can be called without the DI framework.

### How the bug manifests

1. A root-admin session exists (`role: "root"` encoded in `ui_access_token` cookie).
2. An operator calls `PATCH /v1/tenants/{id}` with `{ "status": "active" }` to lift a
   suspension — but the middleware returns 503 first, before the router is reached.
3. The root admin is locked out. The only recovery path is direct DynamoDB manipulation
   (`scripts/rootctl` or AWS console), which is a break-glass procedure requiring separate
   credentials.

Under `MULTI_TENANCY_ENABLED=0` (current dev default) the status check is never reached
(middleware short-circuits at line 97), so the lockout is a production-only risk.

## 3. Impact / Exploit / Blast Radius

### Availability / lockout scenario

- If DynamoDB is writable by a compromised service account or a rogue background job, an
  attacker can flip `tenants#{default}` to `status = "suspended"`.
- The entire platform returns 503 to every request, including root-admin requests.
- Even if operators have `rootctl`, that CLI manipulates DynamoDB directly and requires
  AWS credentials, which are a separate secret management concern.

### Denial of service as a persistence technique

After the initial compromise, the attacker flips the tenant status to prevent operator
investigation through the normal UI or API. Root admins should retain access precisely to
counter this scenario.

### Scope

With `MULTI_TENANCY_ENABLED=0` (dev default), no impact — the middleware short-circuits
at line 97 before the status check. With `MULTI_TENANCY_ENABLED=1` (prod multi-tenant),
every suspended tenant (or the default tenant if it is suspended) blocks all HTTP access,
including admin remediation. The `deleted` (410) path carries the same structural deficiency
but is intentionally permanent by design; for `suspended` it is operationally incorrect.

In a single-tenant deployment using the `default` tenant (the most common production
configuration), a suspended `default` tenant would be a catastrophic platform-wide outage
from which operators cannot recover via the normal API. They would be forced to use either
`scripts/rootctl` (requires direct AWS DynamoDB access and separate credentials) or a
manual DynamoDB update via the AWS console or CLI. Both are break-glass procedures with
elevated audit footprint and human-error risk. The fix eliminates the need for break-glass
access for this specific scenario.

## 4. Fix Design (code-level)

### Approach: lightweight cookie/header check before 503

Middleware cannot use FastAPI DI, but it can perform a minimal JWT decode inline. The fix
adds a `_is_root_from_request` helper that reads the `ui_access_token` cookie or `Authorization`
header and checks the `role` claim — **without** network I/O or full session validation.

**Security note**: This check does not replace full authentication (the request still passes
through `require_ui_session` / `get_authenticated_user` if it reaches a router). Its sole
purpose is to bypass the 503 wall so a genuine root session can reach the auth layer.
Replay/forgery of the cookie is mitigated because the HMAC signature is verified.

### Change to `app/middleware/tenant.py`

```python
# Add at top of file
import jwt as _jwt

def _request_is_root(request: Request) -> bool:
    """
    Lightweight check: does the incoming request carry a ROOT role credential?
    Used only to bypass the suspended-tenant 503 guard.
    Full auth still runs downstream in the router layer.
    """
    # 1. Cookie-based access token (browser session)
    access_secret = getattr(S, "ui_access_token_secret", "")
    access_cookie_name = getattr(S, "ui_access_token_cookie_name", "")
    if access_secret and access_cookie_name:
        cookie_val = request.cookies.get(access_cookie_name, "")
        if cookie_val:
            try:
                payload = _jwt.decode(
                    cookie_val, access_secret, algorithms=["HS256"],
                    options={"verify_exp": False},
                )
                if str(payload.get("role", "")).lower() == "root":
                    return True
            except _jwt.PyJWTError:
                pass

    # 2. Bearer token dev fallback (Cognito path decoded downstream, skip here)
    #    For dev mode, allow x-user-role: root header
    if S.dev_mode:
        if request.headers.get("x-user-role", "").lower() == "root":
            return True

    return False
```

The status-check block in `dispatch` becomes:

```python
status = str(tenant_record.get("status", "active")).lower()
if status == "suspended":
    if _request_is_root(request):
        # ROOT bypasses the suspension wall so operators can remediate
        pass
    else:
        return JSONResponse(
            status_code=503,
            content={"detail": "Tenant is suspended"},
        )
if status == "deleted":
    return JSONResponse(
        status_code=410,
        content={"detail": "Tenant has been deleted"},
    )
```

### Why not bypass `deleted` too?

A `deleted` tenant is an intentional permanent state reflecting that the tenant has been
offboarded. There is no operator remediation workflow that requires access to a deleted
tenant through the normal HTTP API; the `scripts/rootctl` CLI is the correct tool for
any exceptional data recovery. Suspended tenants, by contrast, represent a temporary
administrative hold — billing delinquency, policy review, abuse investigation — from which
recovery is expected and must be possible remotely without break-glass procedures.

### Audit logging

The bypass should be visible. Add an audit event at the bypass point:

```python
if _request_is_root(request):
    from app.services.alerts import audit_event as _ae
    _ae("tenant_suspended_root_bypass", "", request,
        tenant_id=tenant_id,
        note="root session bypassed suspended-tenant 503")
    # fall through to call_next
```

This creates an immutable record in the audit table every time a ROOT session accesses
a suspended tenant, supporting the compliance requirement that all privileged escalations
are logged.

### Dev/prod parity (SECOPS-007)

- `_request_is_root` uses the same `S.ui_access_token_secret` and cookie name as the main
  auth path. In dev the secret is set in `.env.local`; in prod it is injected via AWS
  Secrets Manager. The code path is identical — the helper is not mocked.
- The dev-mode `x-user-role` header fallback mirrors the existing dev-mode header fallback
  in `app/auth/deps.py` lines 254–260 and is gated on `S.dev_mode`. In production where
  `S.dev_mode=False`, only the HMAC-verified JWT cookie path is active.
- No separate mock implementation required: `MockSamlAuth`, dev header fallbacks, and
  the test client all work with the same cookie-based mechanism.

### Alternatives considered

- **Move the check inside a FastAPI dependency**: Not viable. `BaseHTTPMiddleware.dispatch`
  is called before any FastAPI DI graph resolves. There is no way to use `Depends(...)` in
  a middleware class.
- **Use a special bypass HTTP header** (e.g., `X-Root-Override: 1`): Rejected. Any client
  could set this header. It would need to be secret (effectively a second bearer token),
  which creates a new secret management burden with no advantage over the already-signed
  `ui_access_token` cookie.
- **IP allowlist for root bypass**: Rejected. Adds operational complexity (IP rotation,
  VPN, on-call access from home), and root sessions already carry cryptographic proof of
  identity via the HS256 HMAC.
- **Skip suspension check for all `/v1/admin/*` paths**: Rejected. Too broad — a suspended
  tenant should still block non-root admin sessions. The fix correctly scopes the bypass
  to ROOT role only.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

`tests/test_tenant_middleware_root_bypass.py`:

```python
import pytest
import jwt
from unittest.mock import patch, MagicMock
from fastapi.testclient import TestClient
from app.main import app
from app.core.settings import S

def _make_root_cookie():
    return jwt.encode(
        {"sub": "root@example.com", "role": "root"},
        S.ui_access_token_secret,
        algorithm="HS256",
    )

def _suspended_tenant_record():
    return {"tenant_id": "default", "status": "suspended", "settings_overrides": {}}

@pytest.fixture
def client():
    return TestClient(app)

def test_suspended_tenant_blocks_regular_user(client):
    """Regular user must receive 503 when tenant is suspended."""
    with patch("app.middleware.tenant._resolve_tenant_from_domain",
               return_value=("default", _suspended_tenant_record())), \
         patch("app.core.settings.S.multi_tenancy_enabled", True):
        resp = client.get("/ui/me")
    # BEFORE fix: 503 (correct for regular user -- unchanged after fix)
    # AFTER fix:  503 (unchanged)
    assert resp.status_code == 503

def test_suspended_tenant_allows_root(client):
    """ROOT-role session must bypass 503 and reach the auth layer."""
    root_cookie = _make_root_cookie()
    with patch("app.middleware.tenant._resolve_tenant_from_domain",
               return_value=("default", _suspended_tenant_record())), \
         patch("app.core.settings.S.multi_tenancy_enabled", True):
        resp = client.get(
            "/ui/me",
            cookies={S.ui_access_token_cookie_name: root_cookie},
        )
    # BEFORE fix: 503 (root locked out -- the bug)
    # AFTER fix:  401 or 200 (reaches the router; auth layer may still reject if no session)
    assert resp.status_code != 503

def test_deleted_tenant_always_blocked(client):
    """Even root must not bypass a deleted tenant."""
    deleted_record = {"tenant_id": "default", "status": "deleted"}
    root_cookie = _make_root_cookie()
    with patch("app.middleware.tenant._resolve_tenant_from_domain",
               return_value=("default", deleted_record)), \
         patch("app.core.settings.S.multi_tenancy_enabled", True):
        resp = client.get(
            "/ui/me",
            cookies={S.ui_access_token_cookie_name: root_cookie},
        )
    assert resp.status_code == 410
```

### Manual QA steps

1. Seed a tenant record in DynamoDB with `status = "suspended"`:
   ```bash
   python3 -c "
   import boto3, os
   ddb = boto3.resource('dynamodb', endpoint_url='http://localhost:8001',
                        region_name='us-east-1',
                        aws_access_key_id='test', aws_secret_access_key='test')
   ddb.Table('tenants').put_item(Item={'tenant_id': 'default', 'status': 'suspended'})
   "
   ```
2. Start the stack with `MULTI_TENANCY_ENABLED=1` (`export MULTI_TENANCY_ENABLED=1` before
   `just restart`).
3. As a regular user (Alice): confirm `GET /ui/me` returns 503 and the body is
   `{"detail": "Tenant is suspended"}`.
4. Obtain a root `ui_access_token` cookie. In dev mode: use `e2e_admin_session_setup.py`
   which seeds the root session directly into DDB and returns the JWT. Alternatively, use
   `scripts/rootctl` to generate one.
5. Make a request with the root cookie: confirm the response is 401 (auth layer reached,
   session not found in DDB) or 200 (if the root session is fully seeded) — either outcome
   proves that the 503 wall was bypassed.
6. Use the root session to `PATCH /v1/tenants/default` with `{ "status": "active" }` and
   confirm the tenant is unsuspended.
7. Verify subsequent regular-user requests return 200 again.
8. Check the audit log in DynamoDB for the `tenant_suspended_root_bypass` event.

### Metrics / observability

Add `tenant_suspended_bypass_total{role="root"}` counter to `app/metrics.py` at the bypass
point so unexpected root bypass attempts are visible in dashboards. Also add a Grafana alert
that fires if more than 5 `tenant_suspended_root_bypass` events occur within 10 minutes
(could indicate automated probing with a stolen root cookie, or a bug in the JWT validation
that is incorrectly granting root-role bypass).

### Rollout

- Feature-flagged behind `MULTI_TENANCY_ENABLED` (no impact in dev, where the middleware
  short-circuits to `"default"` at line 97 before reaching the status check).
- Zero migration required — no DDB schema change. The new `_request_is_root` helper is
  pure Python with no new dependencies beyond `PyJWT`, which is already a dependency.
- Deploy to staging, manually trigger a tenant suspension, verify root bypass works, then
  verify normal users are still blocked.
- For production rollout, coordinate with on-call ops to ensure a root session is ready
  to test the bypass immediately after deploy.

**Effort**: S (1–2 days: one new helper function ~25 lines, one guarded check, two tests,
audit event wiring).

**Risk**: Low. The bypass only applies to credentials that are cryptographically verified
(HMAC signature over the `ui_access_token` cookie with `S.ui_access_token_secret`). A
forged root cookie without knowledge of the secret will fail `jwt.decode` and the
`_request_is_root` helper will return `False`. The existing full auth stack then
re-validates the same credential downstream, so there is defence-in-depth: the middleware
bypass merely allows the request to proceed to the FastAPI router; `require_root_session`
still enforces the role constraint before any endpoint logic executes.
