# GAP-0319: SNS Notification Endpoint Unauthenticated and Reachable Without Network Restriction — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase; no prior investigation doc exists.

## 1. Summary & Classification

**Bug statement**: `POST /internal/ses/notifications` (implemented in
`app/routers/ses_notifications.py`) accepts SNS HTTPS push notifications from AWS for SES
bounce and complaint events. The endpoint performs no cryptographic verification of the SNS
message signature and relies solely on network isolation to prevent abuse. In the current
deployment, the `/internal` path is proxied by Vite in the dev environment
(`frontend/vite.config.ts:66`) and is therefore accessible from the browser — the path is not
restricted to intra-VPC traffic only. Any network peer that can reach the FastAPI process can
send arbitrary bounce and complaint notifications, causing the application to mark any email
address as hard-bounced or spam-complained, silently disabling all outbound email to that
address.

**Claim verdict**: CONFIRMED. `ses_notification()` at `app/routers/ses_notifications.py:24`
contains no signature verification. The function processes `SubscriptionConfirmation`,
`UnsubscribeConfirmation`, and `Notification` message types based solely on the `Type` field in
the JSON body — no `x-amz-sns-message-type`, `x-amz-sns-message-id`, or `x-amz-sns-signature`
headers are checked. SNS does include an RSA signature on every message; the endpoint ignores
it entirely.

**Severity**: HIGH (unauthenticated write to email suppression list; denial of notification
service)  
**Source ticket**: PLATFORM-002  
**Owning area**: Infrastructure / Email  
**Related tickets**: SECOPS-007 (dev/prod parity), GAP-0009 (SSRF via custom base URL for
comparison).

## 2. Current-State Investigation (root cause)

### Endpoint — `app/routers/ses_notifications.py:23`

```python
@router.post("/internal/ses/notifications")
async def ses_notification(request: Request) -> Response:
    try:
        body = await request.json()
    except Exception:
        logger.warning("SES notification: invalid JSON body")
        return Response(status_code=400)

    msg_type = body.get("Type", "")

    if msg_type == "SubscriptionConfirmation":
        subscribe_url = body.get("SubscribeURL", "")
        ...
        return Response(status_code=200)   # ← auto-confirms ANY subscription request

    if msg_type == "Notification":
        message = json.loads(body.get("Message", "{}"))
        _process_ses_notification(message)
        return Response(status_code=200)
```

**Three distinct unauthenticated actions**:

1. **`SubscriptionConfirmation`**: The endpoint logs the `SubscribeURL` and returns 200. In a
   real production deployment this would be wired to auto-confirm the subscription by fetching
   `SubscribeURL`. Even as-is, an attacker can subscribe arbitrary SNS topics to this endpoint,
   and the 200 response encourages SNS to retry.

2. **`Notification`**: Calls `_process_ses_notification(message)`, which calls
   `record_email_bounce()` or `record_email_complaint()` with attacker-controlled data. These
   functions write to the email suppression store.

3. **`UnsubscribeConfirmation`**: Returns 200 unconditionally; could be used to silently
   acknowledge an SNS unsubscribe that was not legitimately initiated.

### Email suppression effects — `app/services/email_delivery.py`

`record_email_bounce()` and `record_email_complaint()` write records that prevent future email
delivery to the affected addresses. An attacker who can forge bounce/complaint notifications can
permanently suppress email to any user, preventing password reset, MFA challenge delivery, and
alert emails.

### Network exposure — `frontend/vite.config.ts:66`

```typescript
"/internal": "http://localhost:8000",
```

In the dev environment, Vite proxies `/internal/*` to the backend, making the endpoint
accessible from `http://localhost:3000/internal/ses/notifications`. While this is a dev-only
proxy, it demonstrates that no network-layer restriction is in place at the application layer;
the application assumes that `/internal` will be blocked upstream.

### Registration — `app/main.py:629`

```python
app.include_router(ses_notifications_router)
```

No path prefix or middleware is applied to isolate this router from authenticated user traffic.
The router uses its own prefix-less `APIRouter` with the path baked in as `/internal/ses/notifications`.

### Missing SNS signature verification

AWS SNS sends a `SigningCertURL` and `Signature` field on every message. The correct
verification procedure is:
1. Fetch the certificate from `SigningCertURL` (must be `https://*.amazonaws.com/...`).
2. Reconstruct the canonical string from the message fields.
3. Verify the RSA-SHA1 signature with the certificate's public key.

AWS publishes an official Python reference at `boto3/sns` and several third-party libraries
implement this (`aws-sns-message-validator`). The endpoint skips all of this.

## 3. Impact / Exploit / Blast Radius

**Exploit 1 — Email suppression of any user**

```http
POST /internal/ses/notifications HTTP/1.1
Content-Type: application/json

{
  "Type": "Notification",
  "Message": "{\"notificationType\":\"Bounce\",\"bounce\":{\"bounceType\":\"Permanent\",\"bounceSubType\":\"General\",\"bouncedRecipients\":[{\"emailAddress\":\"victim@example.com\"}]},\"mail\":{\"messageId\":\"abc\",\"source\":\"no-reply@app.com\",\"destination\":[\"victim@example.com\"]}}"
}
```

This call — which requires no authentication, no CSRF, no API key — marks `victim@example.com`
as permanently bounced. All subsequent password reset, MFA, and notification emails to that
address are silently dropped. The attacker can lock any user out of account recovery.

**Exploit 2 — Mass suppression via scripted attack**

A script iterating over registered email addresses (obtainable from other leaks or brute-force)
and posting forged bounce notifications can suppress the entire user base's email delivery in
minutes. Recovery requires manually clearing suppression records from DynamoDB.

**Exploit 3 — Subscription hijacking**

By sending a `SubscriptionConfirmation` with an attacker-controlled `TopicArn` and
`SubscribeURL`, an attacker can probe which SNS topics the application is monitoring, and
potentially redirect notifications to their own endpoint by confirming a rogue subscription.

**Blast radius**: Any email address in the system; all auth flows that depend on email delivery
(password reset, MFA SMS fallback, account verification, compliance alerts).

## 4. Fix Design (code-level)

### 4.1 Cryptographic SNS message signature verification

**File**: `app/routers/ses_notifications.py`

Add a signature verification guard before any message processing. The `aws-sns-message-validator`
package provides a reference implementation; alternatively, a lightweight inline verifier can be
written using the `cryptography` package (already a dependency for FCM JWT signing).

```python
import hashlib
import re
import urllib.request
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import padding
from cryptography.x509 import load_pem_x509_certificate

_SNS_CERT_CACHE: dict = {}
_SNS_SIGNING_CERT_URL_PATTERN = re.compile(
    r"^https://sns\.[a-z0-9-]+\.amazonaws\.com/"
)

def _sns_canonical_message(body: dict, msg_type: str) -> bytes:
    """Build the canonical string that SNS signs (field order matters)."""
    fields_for_type = {
        "Notification": ["Message", "MessageId", "Subject", "Timestamp", "TopicArn", "Type"],
        "SubscriptionConfirmation": ["Message", "MessageId", "SubscribeURL", "Timestamp", "Token", "TopicArn", "Type"],
        "UnsubscribeConfirmation": ["Message", "MessageId", "SubscribeURL", "Timestamp", "Token", "TopicArn", "Type"],
    }
    fields = fields_for_type.get(msg_type, [])
    parts = []
    for field in fields:
        if field in body:
            parts.append(f"{field}\n{body[field]}\n")
    return "".join(parts).encode("utf-8")

def _verify_sns_signature(body: dict) -> bool:
    """Return True if the SNS message signature is valid. Returns False on any error."""
    try:
        cert_url = body.get("SigningCertURL", "")
        if not _SNS_SIGNING_CERT_URL_PATTERN.match(cert_url):
            logger.warning("SNS: rejected non-AWS cert URL: %s", cert_url[:80])
            return False
        if cert_url not in _SNS_CERT_CACHE:
            with urllib.request.urlopen(cert_url, timeout=5) as r:
                _SNS_CERT_CACHE[cert_url] = r.read()
        cert = load_pem_x509_certificate(_SNS_CERT_CACHE[cert_url])
        signature = body.get("Signature", "")
        import base64
        sig_bytes = base64.b64decode(signature)
        msg_type = body.get("Type", "")
        canonical = _sns_canonical_message(body, msg_type)
        cert.public_key().verify(sig_bytes, canonical, padding.PKCS1v15(), hashes.SHA1())
        return True
    except Exception:
        logger.warning("SNS: signature verification failed", exc_info=True)
        return False
```

Then gate the endpoint:

```python
@router.post("/internal/ses/notifications")
async def ses_notification(request: Request) -> Response:
    try:
        body = await request.json()
    except Exception:
        logger.warning("SES notification: invalid JSON body")
        return Response(status_code=400)

    # ── Signature verification (PLATFORM-002 / GAP-0319) ──────────────────
    if not S.dev_mode:
        if not _verify_sns_signature(body):
            logger.warning(
                "SNS: rejected unverified notification, type=%s, topic=%s",
                body.get("Type", "?"), body.get("TopicArn", "?")[:80],
            )
            return Response(status_code=403)
    # ── Proceed with existing routing ─────────────────────────────────────
    ...
```

The `S.dev_mode` bypass allows the local dev stack to inject test bounce events via the
`/internal/ses/notifications` endpoint without requiring real SNS infrastructure. This is the
correct SECOPS-007 pattern: the bypass is gated on the same flag used throughout the app, not a
separate code path.

### 4.2 Network restriction (defence in depth)

The signature verification above is the primary fix. Network restriction is the secondary,
defence-in-depth layer. Document the required AWS infrastructure controls in the ops runbook:

1. **Application Load Balancer listener rule**: Add a condition that routes
   `/internal/*` only to a private target group that is not exposed on the public listener.
   Public requests to `/internal/ses/notifications` should receive 404 at the ALB.
2. **Security group**: The EC2/ECS task running FastAPI should accept traffic on port 8000 from:
   - The ALB's security group (for all other paths)
   - The SNS IP range (published at `https://ip-ranges.amazonaws.com/ip-ranges.json`,
     `service: SNS`) for direct SNS → app delivery
   No direct internet access to port 8000.
3. **Vite proxy**: Remove or gate the `/internal` proxy entry in `frontend/vite.config.ts` so
   the dev browser does not have a path to `/internal/*`. This does not affect backend-to-backend
   calls in the dev stack.

### 4.3 Dev mode behaviour (SECOPS-007)

In dev mode (`DEV_MODE=1`), signature verification is skipped. This allows:
- `just e2e` tests to post mock SNS events to the endpoint without a real SNS subscription.
- Developer tooling to manually test the bounce/complaint handling path.

Add an explicit log line when the bypass fires:

```python
if S.dev_mode:
    logger.debug("SNS signature verification skipped (dev_mode=True)")
```

This makes it visible in logs and easy to grep for in code review.

### 4.4 Alternatives considered

- **IP allowlist at application layer**: SNS IP ranges change over time and require ongoing
  maintenance. Cryptographic signature verification is self-contained and requires no IP list
  updates.
- **VPC-only routing without signature check**: Network controls are necessary but not
  sufficient — an insider or compromised internal service could still forge notifications.
  Both layers are required for defence in depth.
- **AWS SDK SNS message validator**: The `boto3` SDK does not include a built-in SNS message
  validator. The `aws-sns-message-validator` pip package exists but adds a dependency.
  The inline verifier above uses `cryptography` which is already a project dependency.
