# GAP-0176: `_find_invite` Does a Full Table Scan — Remediation Write-up

> Source ticket: ENTERPRISE-003 · Severity: HIGH · Effort: M · Status: Open

## 1. Summary & Classification

**Bug statement.** The `_find_invite` helper in `app/services/org_service.py` resolves an
invitation record by performing a full DynamoDB `Scan` on the `organizations` table, applying
a `FilterExpression` to match on `sk = INVITE#{invite_id}`. As the table grows — each
organization accumulating member records, invite records, and a meta record — every call to
accept or decline an invitation reads and discards the entire table before returning a single
item. The operation has O(N) cost relative to total item count across all organizations.

**Verdict:** Confirmed. `app/services/org_service.py:417` contains `T.organizations.scan(...)`.
No `invite-id-index` GSI exists in `scripts/local-ddb-init.py`; only three GSIs are declared
for the `organizations` table: `user-orgs-index`, `invite-email-index`, and `slug-index`.

**Severity and area.** HIGH / Enterprise Workspaces (ENTERPRISE-003). Affects every
unauthenticated invite acceptance and decline path. At modest scale (10,000 total items across
organizations) the scan consumes significant read capacity units; at enterprise scale it becomes
a latency and cost problem and can exhaust on-demand capacity on a shared table.

**Related tickets.** ENTERPRISE-003 (org/workspace feature), GAP-0177 (companion N+1 query gap
in `list_user_orgs`). No blocking dependencies; the DDB table and `invite_id` attribute are
already present.

---

## 2. Current-State Investigation (root cause)

### The broken path: `_find_invite` at `app/services/org_service.py:416–423`

```python
def _find_invite(invite_id: str) -> Optional[Dict[str, Any]]:
    resp = T.organizations.scan(
        FilterExpression="sk = :sk",
        ExpressionAttributeValues={":sk": f"INVITE#{invite_id}"},
        Limit=100,
    )
    items = resp.get("Items", [])
    return items[0] if items else None
```

There are two problems here:

1. **Full table scan.** `T.organizations.scan()` reads every item in the table, consuming one
   read capacity unit per 4 KB of data, before the filter narrows the result set. DynamoDB's
   `FilterExpression` is evaluated client-side by the service after reading, not server-side
   before reading. The `Limit=100` parameter limits the number of items read *before filtering*,
   not after. If the target invite item falls outside the first 100 items scanned, the scan
   returns an empty list and the function silently returns `None` even though the invite exists —
   this is a **correctness bug** as well as a performance bug.

2. **No `invite-id-index` GSI in DDB init.** `scripts/local-ddb-init.py:1486–1490` declares
   the `organizations` table with three GSIs, none of which keys on `invite_id`:

   ```python
   gsi=[
       {"index_name": "user-orgs-index", "partition_key": "user_sub", "sort_key": "org_id"},
       {"index_name": "invite-email-index", "partition_key": "email", "sort_key": "org_id"},
       {"index_name": "slug-index", "partition_key": "slug", "sort_key": "org_id"},
   ],
   ```

### Call sites

`_find_invite` is called from two places, both on unauthenticated-ish public paths:

- `accept_invite` at `app/services/org_service.py:237` — invoked from the email link accept flow.
- `decline_invite` at `app/services/org_service.py:295` — invoked from the decline link flow.

Both operations are called with only the `invite_id` supplied by the user in a URL token. There
is no organisation context available at call time, which is why the code scans globally rather
than doing a targeted `get_item` or `query`.

### Dev vs prod behaviour

In the local dev stack the `organizations` table is nearly empty (one or two test orgs), so the
scan completes quickly and the `Limit=100` bug is invisible. In a production table with hundreds
of organisations and thousands of invite/member records the scan is expensive, latency is
unpredictable, and the `Limit=100` cap means invitations belonging to large orgs can silently
disappear: `_find_invite` returns `None`, which causes `accept_invite` to raise HTTP 404, and
the invitee sees an unexplained "Invitation not found" error despite possessing a valid token.

## 3. Impact / Exploit / Blast Radius

**Performance / availability.** Every invite acceptance or decline performs a full scan. At
10 RCU per scan (400 items × 1 KB average), a burst of concurrent invite flows during an
enterprise onboarding event (100 employees accepting at once) produces 1 000 RCU spikes,
consuming provisioned capacity and causing latency spikes for all other table operations.

**Correctness (high severity).** The `Limit=100` cap silently breaks invite acceptance for
any organisation that shares table space with more than 100 other items before the target invite
item is encountered in scan order. Scan order in DynamoDB is by internal partition hash, not
insertion order, so the failure is non-deterministic. An enterprise customer accepting the 101st
invite in a live table gets HTTP 404 with no error log on the backend — the bug leaves no trace.

**No direct security exploit**, but the broken 404 is user-visible and affects customer trust.
If the DynamoDB table ever has TTL-expired items still waiting for tombstone propagation, the
Limit=100 cap makes the problem worse because tombstone items count towards the scanned limit.

**Blast radius.** All `POST /ui/orgs/invites/{invite_id}/accept` and
`POST /ui/orgs/invites/{invite_id}/decline` calls in production. Affects every new user
onboarded via email invite — a core enterprise workflow.

## 4. Fix Design (code-level)

### Step 1 — Add `invite-id-index` GSI to `scripts/local-ddb-init.py`

Add a fourth GSI to the `organizations` table definition. The `invite_id` attribute is already
stored on every invite item (see `org_service.py:224`). The GSI only needs a partition key;
no sort key is required because invite IDs are globally unique.

```python
# scripts/local-ddb-init.py  (around line 1486)
TableDef(
    _resolve_table_name(S.organizations_table_name, "organizations"),
    "org_id",
    "sk",
    gsi=[
        {"index_name": "user-orgs-index",  "partition_key": "user_sub",  "sort_key": "org_id"},
        {"index_name": "invite-email-index","partition_key": "email",     "sort_key": "org_id"},
        {"index_name": "slug-index",        "partition_key": "slug",      "sort_key": "org_id"},
        # NEW — enables O(1) invite lookup by invite_id
        {"index_name": "invite-id-index",   "partition_key": "invite_id", "sort_key": "org_id"},
    ],
),
```

`invite_id` is a string (e.g. `inv_<16-hex>`), so no `attr_types` override is needed.

### Step 2 — Replace the scan with a GSI query in `_find_invite`

```python
# app/services/org_service.py  (replace lines 416–423)
def _find_invite(invite_id: str) -> Optional[Dict[str, Any]]:
    """Look up an invite item by invite_id using the invite-id-index GSI."""
    resp = T.organizations.query(
        IndexName="invite-id-index",
        KeyConditionExpression=Key("invite_id").eq(invite_id),
        Limit=1,
    )
    items = resp.get("Items", [])
    return items[0] if items else None
```

The GSI projects all attributes by default (ALL projection in the local DDB init helper — check
that `_make_gsi` in `scripts/local-ddb-init.py` uses `ProjectionType=ALL`; if it uses KEYS_ONLY
or INCLUDE, add `invite_id` and all fields that `accept_invite` / `decline_invite` read:
`org_id`, `status`, `token_hash`, `expires_at`, `org_role`, `invited_by`, `email`).

The existing `_make_gsi` helper in `local-ddb-init.py` already uses `ProjectionType: "ALL"` for
all indexes, so the full item is projected and no projection change is required.

### Step 3 — Ensure new invite items write `invite_id` as a top-level attribute

`invite_member` at `org_service.py:220–231` already stores `invite_id` as a top-level attribute
in `invite_item`, so it is naturally projected to the new GSI. No schema migration is needed for
new items.

**Production migration.** Existing invite items in a live table that pre-date this change already
have `invite_id` written (the attribute was there from initial implementation), so the GSI
back-fill during `CreateGlobalSecondaryIndex` on the live table will index them correctly.
AWS charges the standard write cost to back-fill the GSI; for a typical invite table this is
negligible. Estimated back-fill time for 10 000 items: under 30 seconds.

**Dev/prod parity (SECOPS-007).** Both paths run through the same `T.organizations.query()`
call. The local DynamoDB Local instance used in dev is updated by re-running
`scripts/local-ddb-init.py` (or `just restart`). No flag-selected code paths are needed; the
fix is a straight replacement.

**Alternatives considered.**
- Storing `org_id` on the invite token itself and doing a targeted `get_item`: rejected because
  it leaks `org_id` in public URLs and requires URL-scheme changes.
- Keeping the scan but removing `Limit=100`: fixes the silent 404 but still performs full scans —
  rejected because the performance problem remains.

## 5. Testing, Verification & Rollout

### Regression test (pytest offline — fails before fix, passes after)

Add to `tests/test_org_service.py`:

```python
import pytest
from unittest.mock import patch, MagicMock
from app.services.org_service import _find_invite


def test_find_invite_uses_query_not_scan(mock_orgs_table):
    """_find_invite must use query() on invite-id-index, never scan()."""
    invite_id = "inv_testinvite123456"
    fake_item = {
        "org_id": "org_abc",
        "sk": f"INVITE#{invite_id}",
        "invite_id": invite_id,
        "status": "pending",
        "token_hash": "sha256:deadbeef",
        "expires_at": 9999999999,
        "org_role": "member",
        "invited_by": "user_xyz",
        "email": "invitee@example.com",
    }

    mock_orgs_table.query.return_value = {"Items": [fake_item]}

    result = _find_invite(invite_id)

    # Must call query, never scan
    mock_orgs_table.query.assert_called_once()
    mock_orgs_table.scan.assert_not_called()

    call_kwargs = mock_orgs_table.query.call_args[1]
    assert call_kwargs["IndexName"] == "invite-id-index"
    assert result == fake_item


def test_find_invite_returns_none_when_not_found(mock_orgs_table):
    mock_orgs_table.query.return_value = {"Items": []}
    result = _find_invite("inv_doesnotexist")
    assert result is None
```

**Before fix:** `mock_orgs_table.scan.assert_not_called()` fails because the current
implementation calls `scan`. `mock_orgs_table.query.assert_called_once()` also fails.

**After fix:** Both assertions pass; the mock returns the fake item and `_find_invite` returns it.

### Manual QA steps

1. Run `just restart` to wipe DynamoDB and recreate tables with the new GSI.
2. Seed at least 150 items in the organizations table to exceed the old `Limit=100` threshold.
3. Create an org, invite a member via `POST /ui/orgs/{org_id}/members/invite`.
4. Call `POST /ui/orgs/invites/{invite_id}/accept` — confirm 200 and membership created.
5. Confirm no scan appears in DynamoDB access logs (CloudWatch Metrics → `SuccessfulRequestLatency`
   on `Scan` operation should remain flat).

### Observability

In production, enable DynamoDB CloudWatch metrics and add an alarm on `SystemErrors` for Scan
operations on the `organizations` table. Post-fix, the Scan metric should drop to zero for
invite-related flows. If DDB Insights are enabled, the "Hot Key" report will confirm the new
GSI is serving the invite lookups.

### Rollout sequence

1. Deploy `scripts/local-ddb-init.py` change + run on dev stack — 2 minutes.
2. For production: run `aws dynamodb update-table` to add `invite-id-index` GSI; wait for
   back-fill (ACTIVE status, typically under 5 minutes for a small table).
3. Deploy the service code change. No downtime required; the old scan code works in parallel
   while the GSI back-fills because both are read-safe.
4. Verify invite acceptance in production, then monitor CloudWatch scan metrics for 24 hours.

**Effort estimate:** S (half day — DDB init change, one-line service fix, unit tests).
Sequenced after the GSI is confirmed ACTIVE in production before deploying code.

**Rollback.** Reverting the service code to `scan()` while the GSI exists is safe (the GSI is
never required by the rollback path). Dropping the GSI is optional cleanup.
