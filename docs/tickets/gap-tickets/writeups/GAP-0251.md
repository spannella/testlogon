# GAP-0251: No `GET /admin/case/{case_id}` endpoint — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase; no prior investigation doc exists.

## 1. Summary & Classification

**Claim from ticket**: There is no direct `GET /admin/case/{case_id}` endpoint for looking
up a liveness-call record by KYC case ID. Admins must iterate over all status partitions of
the ByStatus GSI and filter by `case_id` themselves. The proposed fix is to add the endpoint
backed by `STORE.get_call_for_case(case_id)`.

**Verdict: Claim PARTIALLY CONFIRMED (significant correction required).** The liveness-call
router at `app/routers/kyc_liveness_call.py` does **not** expose a `GET /admin/case/{case_id}`
endpoint for the admin path — confirmed: there is no route matching that pattern in the
file. However, the ticket's proposed service method name is wrong. The store already provides
`get_active_call_for_case(case_id)` (line 203) and `get_latest_call_for_case(case_id)` (line
210) in `app/services/kyc_liveness_call.py`. A method named `get_call_for_case` does not
exist and does not need to be created from scratch; the fix only requires adding a router
endpoint that calls the existing `get_latest_call_for_case`.

The KYC cases router (`app/routers/kyc_cases.py`) does have an admin case-detail endpoint
(`GET /v1/kyc/cases/admin/cases/{case_id}`, line 1062), but that endpoint returns the KYC
case document, not the liveness-call record. The two concepts live in different services and
are not interchangeable.

- **Severity**: HIGH — admin reviewers conducting liveness verification calls must find the
  call record for a case by scanning all status buckets (up to 600 records across six status
  partitions) rather than doing a direct lookup. For high-volume queues this delays the
  review workflow and can cause reviewers to open the wrong record.
- **Source ticket**: KYC-003
- **Owning area**: Backend / KYC liveness-call router
- **Related tickets**: GAP-0249 (liveness expiry task), GAP-0250 (VerificationCallPanel),
  SECOPS-007 (dev/prod parity)
- **Naming correction**: ticket says `STORE.get_call_for_case`; actual available methods are
  `get_active_call_for_case` and `get_latest_call_for_case`.

## 2. Current-State Investigation (root cause)

### Existing store methods

`app/services/kyc_liveness_call.py` already provides:

```python
# line 203
def get_active_call_for_case(self, case_id: str) -> dict[str, Any] | None:
    """Return the active (scheduled / in_progress) call for a case, if any."""
    for item in self.list_calls_for_case(case_id):
        if str(item.get("status") or "") in ACTIVE_STATUSES:
            return item
    return None

# line 210
def get_latest_call_for_case(self, case_id: str) -> dict[str, Any] | None:
    """Return the most recently created call for a case (any status)."""
    items = self.list_calls_for_case(case_id)
    return items[0] if items else None
```

Both delegate to `list_calls_for_case` (line 215), which queries the `ByCase` GSI:

```python
def list_calls_for_case(self, case_id: str) -> list[dict[str, Any]]:
    try:
        resp = self._table.query(
            IndexName="ByCase",
            KeyConditionExpression=Key("case_id").eq(case_id),
            ScanIndexForward=False,
        )
        return list(resp.get("Items", []))
    except Exception:
        resp = self._table.scan()
        items = [i for i in resp.get("Items", []) if i.get("case_id") == case_id]
        items.sort(key=lambda i: _coerce_int(i.get("created_at")), reverse=True)
        return items
```

This is an efficient GSI query on `PK=case_id`. The correct implementation already exists.

### What the router currently exposes (admin endpoints)

`app/routers/kyc_liveness_call.py` lines 139–233 define these admin endpoints:

```
GET  /ui/kyc/liveness-call/admin/by-status        -> list by status GSI
GET  /ui/kyc/liveness-call/admin/{call_id}         -> get one by call_id
POST /ui/kyc/liveness-call/admin/{call_id}/conduct -> mark in_progress
POST /ui/kyc/liveness-call/admin/{call_id}/result  -> record pass/fail
POST /ui/kyc/liveness-call/admin/{call_id}/cancel  -> cancel a call
```

No `GET /ui/kyc/liveness-call/admin/case/{case_id}` endpoint exists. The only way an admin
can currently find the call for a KYC case is to:

1. Call `GET /admin/by-status?status=scheduled` (up to 100 items)
2. Call `GET /admin/by-status?status=in_progress`
3. …and so on for `passed`, `failed`, `cancelled`, `expired`
4. Filter the combined result set client-side for the target `case_id`.

With default `limit=100` per status and six status values, this is up to 600 records
fetched to find one. The `VerificationCallPanel` component (GAP-0250) would need to
implement this scan itself, wasting bandwidth and making the panel fragile.

### Owner path contrast

A case owner can already call `GET /ui/kyc/liveness-call/case/{case_id}` (line 120–133)
to get the latest call for their own case. The admin equivalent is absent — the owner
endpoint enforces `_require_owner(item, session["user_sub"])` at line 130, which rejects
admin users who do not own the case.

### Why `get_call_for_case` does not exist

Grepping the entire `app/` tree for `get_call_for_case` returns no results. The ticket
author invented this method name. The semantically equivalent method is
`get_latest_call_for_case` (returns the most recently created call regardless of status),
which is the correct backing function for an admin endpoint that needs a full view of the
case's latest call state.

## 3. Impact / Exploit / Blast Radius

**Operational inefficiency**: Each admin reviewer who opens a KYC case verification panel
must trigger up to six separate list-by-status requests (or a full table scan fallback) to
find the call record associated with that case. On a queue of 500 active cases, this adds
seconds of latency per case and produces hundreds of unnecessary DynamoDB read-capacity
units.

**Reviewer error risk**: If an admin manually scans `by-status` across multiple status
buckets, they may mis-identify the call — for example, selecting an old `expired` record
rather than the current `scheduled` record for a case that has been rescheduled. The correct
endpoint unambiguously returns the most recent call (or active call), eliminating this risk.

**GAP-0250 dependency**: The `VerificationCallPanel` frontend component (GAP-0250) cannot
be correctly implemented without this backend endpoint. The panel must show the call status,
join URL, and recording reference for a specific case when a reviewer opens the KYC case
detail page. Without a direct lookup it must implement complex client-side GSI aggregation.

**No security risk**: The gap does not expose unauthorized access or data leakage. It is
purely a missing read path.

## 4. Fix Design (code-level)

### 4a. Add the admin case lookup endpoint in `app/routers/kyc_liveness_call.py`

Insert the following route in the admin section (after line 154, before `admin/{call_id}`):

```python
@kyc_liveness_call_router.get(
    "/admin/case/{case_id}", response_model=KycLivenessCallOut
)
async def admin_get_liveness_call_for_case(
    case_id: str,
    _user: AuthenticatedUser = Depends(require_admin_or_root),
) -> KycLivenessCallOut:
    """Return the most recently created liveness call for a KYC case (admin/root)."""
    item = STORE.get_latest_call_for_case(case_id)
    if not item:
        raise HTTPException(
            status_code=404,
            detail={
                "code": "kyc_call_not_found",
                "message": "No liveness call found for this case.",
            },
        )
    return _out(item)
```

The route **must be declared before** `/admin/{call_id}` to prevent FastAPI from matching
`case_id="case"` as a `call_id` value. The router already declares `/admin/by-status` before
`/admin/{call_id}` (lines 139 and 157 respectively), establishing the correct precedent.

### 4b. Optional: active-only variant

If callers need to distinguish "is there an active call right now" from "what was the last
call ever", a separate endpoint can be added:

```python
@kyc_liveness_call_router.get(
    "/admin/case/{case_id}/active", response_model=KycLivenessCallOut
)
async def admin_get_active_liveness_call_for_case(
    case_id: str,
    _user: AuthenticatedUser = Depends(require_admin_or_root),
) -> KycLivenessCallOut:
    """Return the active (scheduled/in_progress) liveness call for a case, if any."""
    item = STORE.get_active_call_for_case(case_id)
    if not item:
        raise HTTPException(
            status_code=404,
            detail={
                "code": "kyc_call_not_found",
                "message": "No active liveness call for this case.",
            },
        )
    return _out(item)
```

This secondary endpoint is optional; the primary endpoint covering the latest call is
sufficient for the GAP-0250 VerificationCallPanel use case.

### 4c. Dev/Prod parity (SECOPS-007)

`get_latest_call_for_case` and `get_active_call_for_case` both delegate to
`list_calls_for_case`, which queries `T.kyc_liveness_calls` using the `ByCase` GSI. The
table handle resolves to DynamoDB Local (`localhost:8001`) in dev (via `S.ddb_endpoint_url`)
and AWS DynamoDB in production. No environment-specific code paths are introduced. The
exception fallback (lines 223–227) provides a `scan()` alternative when the GSI is
unavailable — this executes on both environments but is only reached in degraded states.

The `require_admin_or_root` dependency (`app/auth/policy.py`) enforces ADMIN or ROOT role
via the same cookie-based JWT session check used throughout the admin KYC endpoints. No
mock fallback is needed.

### Alternatives considered

- **Use `get_active_call_for_case` only**: Returns `None` for terminal-status cases,
  breaking the panel when the last call is `passed`/`failed`. Rejected.
- **Filter the by-status GSI client-side**: Current workaround. Expensive (6 GSI queries)
  and error-prone. Rejected as a permanent solution.
- **Add a new DynamoDB service method `get_call_for_case`**: Unnecessary; existing
  `get_latest_call_for_case` provides the required semantics. Adding a wrapper would be
  pure indirection with no benefit.

## 5. Testing, Verification & Rollout

### Regression test — fails before / passes after

**pytest offline** (`tests/test_kyc_liveness_call_admin.py`):

```python
from fastapi.testclient import TestClient
from app.main import create_app

def test_admin_get_liveness_call_for_case_not_found(admin_client, kyc_liveness_ddb_table):
    """GET /admin/case/{case_id} returns 404 when no call exists."""
    # BEFORE fix: route does not exist -> 404/405 from FastAPI (method not allowed or 404)
    # AFTER fix: explicit 404 with code=kyc_call_not_found
    resp = admin_client.get("/ui/kyc/liveness-call/admin/case/case_missing")
    assert resp.status_code == 404
    assert resp.json()["detail"]["code"] == "kyc_call_not_found"

def test_admin_get_liveness_call_for_case_returns_latest(
    admin_client, kyc_liveness_ddb_table, now_fixed
):
    """GET /admin/case/{case_id} returns the most recent call for the case."""
    # Seed two calls for the same case (different status, different created_at)
    kyc_liveness_ddb_table.put_item(Item={
        "call_id": "kyccall_old", "case_id": "case_target",
        "user_sub": "user_x", "status": "passed",
        "created_at": now_fixed - 7200, "updated_at": now_fixed - 7200,
        "scheduled_at": now_fixed - 7200,
    })
    kyc_liveness_ddb_table.put_item(Item={
        "call_id": "kyccall_new", "case_id": "case_target",
        "user_sub": "user_x", "status": "scheduled",
        "created_at": now_fixed - 60, "updated_at": now_fixed - 60,
        "scheduled_at": now_fixed + 3600,
    })
    resp = admin_client.get("/ui/kyc/liveness-call/admin/case/case_target")
    assert resp.status_code == 200
    assert resp.json()["call_id"] == "kyccall_new"
    assert resp.json()["status"] == "scheduled"

def test_admin_get_liveness_call_for_case_requires_admin_role(user_client, kyc_liveness_ddb_table):
    """Regular users cannot call the admin endpoint."""
    resp = user_client.get("/ui/kyc/liveness-call/admin/case/case_target")
    assert resp.status_code == 403

def test_admin_case_route_does_not_shadow_call_id_route(admin_client, kyc_liveness_ddb_table, now_fixed):
    """Declaring /admin/case/{case_id} before /admin/{call_id} must not shadow call lookups."""
    kyc_liveness_ddb_table.put_item(Item={
        "call_id": "kyccall_direct", "case_id": "case_z",
        "user_sub": "user_z", "status": "in_progress",
        "created_at": now_fixed, "updated_at": now_fixed,
        "scheduled_at": now_fixed,
    })
    # Call by call_id must still work
    resp = admin_client.get("/ui/kyc/liveness-call/admin/kyccall_direct")
    assert resp.status_code == 200
    assert resp.json()["call_id"] == "kyccall_direct"
```

**Before fix**: `test_admin_get_liveness_call_for_case_returns_latest` returns 405 (Method Not
Allowed) or is routed to `admin_get_liveness_call` where `call_id="case"` never matches a
real record → 404 but with incorrect semantics. The routing test also fails because
`/admin/case/` hits `admin_get_liveness_call` with `call_id="case"`.

**After fix**: All four tests pass.

### Metrics / observability

No special metrics are required for a read-only GET endpoint. The existing auth audit events
from `require_admin_or_root` provide traceability. A 404 rate spike on this endpoint
indicates reviewers are opening case detail pages before any call has been scheduled.
