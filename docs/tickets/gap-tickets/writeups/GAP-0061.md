# GAP-0061: Brand Name Fallback Exposes Advertiser User-Sub as PII — Remediation Write-up

> ~5 pages. Fix-oriented. Claim verified directly against the code before writing; cites file:line.

## 1. Summary & Classification

**Claim status: Confirmed.** The code at `app/services/sponsorship_deals.py:521` does exactly what the ticket describes: it initialises `brand_name` to the raw advertiser Cognito sub (a UUID string) and only replaces it with the company name if the ad-account lookup succeeds. When the lookup fails for any reason — network blip, deleted account, exception — the sub value is written verbatim into the public-facing FTC disclosure text, producing a disclosure such as `"Paid partnership with b3f1c0de-1234-…"`.

- **Severity**: HIGH  
- **Source ticket**: ADS-013  
- **Owning area**: Sponsorship / Creator Monetisation  
- **One-line impact**: Any exception during ad-account lookup permanently embeds the advertiser's internal user identifier into publicly-visible sponsored-content metadata on posts, feed items, and videos.  
- **Related tickets**: ADS-013 (parent feature), GAP-0061 is self-contained; no blocking dependencies.

---

## 2. Current-State Investigation (root cause)

### Exact code path

`app/services/sponsorship_deals.py`, function `submit_content`, lines 509–531:

```python
# Line 520-521 — fallback is the raw sub
brand_name = deal["advertiser_sub"]          # ← PII leak if fallback used
try:
    from app.services.ad_accounts import get_ad_account
    acct = get_ad_account(deal["advertiser_account_id"])
    if acct and acct.get("company_name"):
        brand_name = acct["company_name"]    # only path that sets a safe name
except Exception:
    pass                                      # ← swallows any error silently
```

Then, a few lines later (line 531):

```python
_add_ftc_label(deal["content_type"], content_id, brand_name=brand_name, deal_id=deal_id)
```

Inside `_add_ftc_label` (lines 265–284), the label is written to the content record:

```python
disclosure = f"Paid partnership with {brand_name}"
# ... DynamoDB update sets  ftc_disclosure = disclosure
```

The `ftc_disclosure` field is part of the public content record that is returned to viewers via the feed router. The sub (`deal["advertiser_sub"]`) is a Cognito UUID, e.g. `b3f1c0de-8f44-4a1a-ab12-1234567890ab`, which is considered personal data under GDPR/CCPA because it uniquely identifies a natural person within the platform.

### Failure scenarios that trigger the leak

1. **DynamoDB transient error** — `get_ad_account` raises a `ClientError`; the `except Exception: pass` swallows it and `brand_name` remains the sub.
2. **Account deleted or never approved** — `get_ad_account` returns `None`; the `if acct and acct.get("company_name"):` branch is skipped; `brand_name` = sub.
3. **Account has no `company_name`** — advertiser left `company_name` empty; same branch skipped; sub used.
4. **Import error** — any import-time failure of `ad_accounts` module; same result.

### Why it is not just a dev issue

The fallback path is not gated on `S.dev_mode`. Both dev and prod execute identical logic. In production, scenario 3 (empty `company_name`) is reachable through normal user flows — an advertiser is only required to provide a billing e-mail to create an account; `company_name` is optional.

## 3. Impact / Exploit / Blast Radius

### PII exposure

The `advertiser_sub` is a UUID-form Cognito identity. Once written to the `ftc_disclosure` field, the value is:

- Persisted in DynamoDB on the content record (post, video, etc.) indefinitely.
- Returned in the public feed API response to any authenticated viewer.
- Potentially indexed by search, exported in moderation reports, or surfaced in admin dashboards.

Remediation requires not only fixing the code path but also back-filling every existing content record where `ftc_disclosure` contains a UUID-like value — a data-scrubbing migration task.

### Compliance risk

GDPR Article 4 treats pseudonymous identifiers (including platform-generated UUIDs that link to a natural person) as personal data. Embedding such an identifier in a field that is readable by other platform users constitutes an unauthorised disclosure to third parties, which can trigger Article 33 breach-notification obligations and Article 83 fines.

### Blast radius

- **Who**: All advertisers who have a sponsorship deal reach `content_submitted` status while their ad account has an empty or missing `company_name`.
- **What leaks**: Only the `advertiser_sub` UUID. No password, email, or financial data is directly exposed through this path.
- **Severity cap**: The leaked value is not directly actionable for account takeover. However it does allow a curious viewer to correlate the sub with the same UUID appearing in other API responses (e.g. notification sender fields), thereby building a partial identity graph.

## 4. Fix Design (code-level)

### Core change

Replace the bare `advertiser_sub` fallback with an anonymous sentinel string that is still FTC-compliant:

```python
# app/services/sponsorship_deals.py  — submit_content()
# BEFORE (lines 521-529):
brand_name = deal["advertiser_sub"]
try:
    from app.services.ad_accounts import get_ad_account
    acct = get_ad_account(deal["advertiser_account_id"])
    if acct and acct.get("company_name"):
        brand_name = acct["company_name"]
except Exception:
    pass

# AFTER:
brand_name = "a verified brand partner"   # safe sentinel — never contains PII
try:
    from app.services.ad_accounts import get_ad_account
    acct = get_ad_account(deal["advertiser_account_id"])
    company = (acct or {}).get("company_name", "").strip()
    if company:
        brand_name = company
except Exception:
    logger.warning(
        "submit_content: ad-account lookup failed for deal=%s account=%s; "
        "using anonymous brand fallback",
        deal_id,
        deal.get("advertiser_account_id", "unknown"),
    )
```

Key differences:

1. **Safe default** — `brand_name` is initialised to `"a verified brand partner"`, never to a user identifier.
2. **Explicit strip** — defends against a `company_name` that is whitespace-only.
3. **Logged warning** — the exception is no longer silently swallowed; operators can detect lookup failures in their log pipeline without leaking the sub to end-users.
4. **No behaviour change for happy path** — when `company_name` is populated the disclosure reads identically to today.

### Data-scrubbing migration

A one-time backfill script should query all content records where `ftc_disclosure` matches the regex pattern `^Paid partnership with [0-9a-f-]{36}$` (UUID format) and replace those values with `"Paid partnership with a verified brand partner"`. The script should be run under a feature flag / dry-run mode before applying writes. This is separate from the code fix but must accompany it for a complete remediation.

### Dev/Prod parity (SECOPS-007)

The bug and the fix are entirely in the Python service layer. No AWS-specific code path is involved — `get_ad_account` reads from DynamoDB which is mocked by DynamoDB Local in dev. The fix behaves identically in both environments because:

- The fallback string `"a verified brand partner"` is a constant, not sourced from an env var.
- The logger warning goes to the same `uvicorn` log stream in dev and to CloudWatch in prod.
- No feature flag is required; the change is safe to deploy directly.

### Alternatives considered

| Option | Rejection reason |
|--------|-----------------|
| Raise instead of fallback | Breaks `submit_content` if the account is temporarily unavailable; creators lose the ability to submit. Fragile. |
| Use `advertiser_account_id` as fallback | Still a platform-internal identifier; does not contain a name but could enable correlation. Not FTC-compliant as a meaningful disclosure. |
| Require `company_name` at account creation | Correct long-term, but requires a model/API change and migration. Should be a separate ticket. Does not fix existing records. |

### Schema and API model considerations

The `ftc_disclosure` field is written directly to the DynamoDB content record — it is not part of any validated Pydantic model at write time. The fix is entirely in service-layer logic. However, it is worth adding `ftc_disclosure` to the relevant `PostOut` / `VideoOut` Pydantic response models in `app/models.py` with a `str` type and a `field_validator` that raises if the value matches the UUID pattern — this would catch a future regression at the serialization layer rather than requiring a DynamoDB scan to detect it.

### Observability

The added `logger.warning(...)` call means any lookup failure will appear in the application log tagged with `deal_id` and `account_id`, enabling a CloudWatch Metric Filter or Datadog log alert to fire when this path is hit unexpectedly in production.

### Observability

In addition to the warning log, add a CloudWatch/Datadog metric filter on the pattern `"submit_content: ad-account lookup failed"`. Set an alarm if this fires more than 5 times per hour — that volume would indicate a systemic DynamoDB connectivity problem rather than isolated account-not-found events.

Also add a `ftc_disclosure_pii_leak` metric counter (incrementing whenever the old code path would have used the sub) by checking pre-fix whether the disclosure contains a UUID pattern. This metric can be used to size the backfill: if it has been incrementing for months, there may be thousands of records to fix.

### Compliance considerations

Under GDPR Article 17 (Right to Erasure), if an advertiser requests deletion of their account, the `advertiser_sub` embedded in `ftc_disclosure` fields on content records constitutes residual personal data that must be scrubbed as part of the deletion workflow. The current account-deletion procedure should be audited to ensure it sweeps `ftc_disclosure` fields on all content records linked to the deleted advertiser. The backfill script proposed in section 4 doubles as the erasure tool for this purpose.

### Rollout

- **Effort**: S (Small) — single-function change, ~5 lines of Python.
- **Risk**: Very low — the only observable behaviour change is that the FTC disclosure string is safer on failure paths. No API contract change; no schema migration.
- **Migration**: Run the backfill script in dry-run mode first; review the result set; apply writes with a feature flag (`FTC_DISCLOSURE_BACKFILL_ENABLED`); then disable the flag and archive the script.
- **Rollback**: Revert the single code change. The backfill script is idempotent — re-running it on already-fixed records is a no-op because the sentinel value does not match the UUID regex.
- **Sequencing**: (1) Code fix merged and deployed, (2) backfill script run against prod with dry-run first, (3) compliance team notified of the scope of historical records fixed, (4) account-deletion workflow updated to include `ftc_disclosure` scrubbing.
