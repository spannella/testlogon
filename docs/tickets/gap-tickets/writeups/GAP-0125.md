# GAP-0125: Private Chat Messages Exposed in Public Chat History — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase. No prior investigation doc exists.

## 1. Summary & Classification

**Claim verdict: Confirmed.** The ticket cites `broadcast_chat_store.py:296` as the location of the gap. The actual `get_chat_history` function begins at line 255; the `resp = T.broadcast_chat_messages.query(...)` call is at line 273 (not 296 — line 296 falls inside `fetch_chat_messages_after`). The underlying claim is accurate: `get_chat_history` queries the shared `broadcast_chat_messages` table without filtering on `kind`, and `send_private_chat_message` writes records with `kind="private_chat"` to that same table. Private chat messages are therefore returned to all viewers by the public chat history endpoint.

- **Severity**: HIGH (privacy violation / confidential message exposure)
- **Source ticket**: BCAST-012
- **Status**: Open
- **Owning area**: Broadcast Chat History (`app/services/broadcast_chat_store.py`), Broadcast Private Chat (`app/services/broadcast_private_chat.py`)
- **Impact**: Any broadcast viewer who calls `GET /sessions/{id}/chat` or receives SSE-delivered chat history sees the private, paid, 1-on-1 messages between the creator and a private chat tier-1 viewer. These messages are intended to be visible only to the private chat participants. Exposure is an immediate GDPR/privacy violation and undermines the paid private chat product.
- **Related tickets**: BCAST-012, BCAST-015 (private chat feature), SECOPS-007 (dev/prod parity)
- **Dependencies**: None external; the fix is purely within `broadcast_chat_store.py`.

## 2. Current-State Investigation (root cause)

### Table layout

Private chat messages are written by `send_private_chat_message` in `app/services/broadcast_private_chat.py` (lines 207–250). Per the docstring at line 217: "Messages are stored in the existing broadcast_chat_messages table with a `private_chat_id` field for scoping." The item written at line 231–244 includes:

```python
item = {
    "session_id": session_id,
    "sort_key": sort_key,
    "message_id": msg_id,
    "kind": "private_chat",        # discriminator field
    "private_chat_id": chat_id,    # chat scope identifier
    ...
}
T.broadcast_chat_messages.put_item(Item=item)
```

Public chat messages written by `send_chat_message` in `broadcast_chat_store.py` (lines 136–216) do NOT set a `kind` field by default. The `_chat_msg_out` helper (line 362) reads `kind` as `item.get("kind", "text")`, meaning the absence of `kind` implies `"text"`. Product link messages set `kind="product_link"` (line 241). Tip messages are inferred from `item.get("kind") == "tip"` (line 369).

Both public and private messages share the same DynamoDB partition key: `session_id`. The sort key is a timestamp-prefixed UUID string (`{ts_ms:016d}#{msg_id}`), meaning all messages for a session interleave in sort-key order regardless of kind.

### The exposure path

`get_chat_history` in `broadcast_chat_store.py:255–285`:

```python
def get_chat_history(
    session_id: str,
    limit: int = 100,
    before_sort_key: Optional[str] = None,
    viewer_user_id: Optional[str] = None,
) -> Dict[str, Any]:
    kwargs: Dict[str, Any] = {
        "KeyConditionExpression": Key("session_id").eq(session_id),
        "Limit": limit,
        "ScanIndexForward": False,
        "FilterExpression": Attr("deleted").ne(True),   # only filters soft-deleted items
    }
    ...
    resp = T.broadcast_chat_messages.query(**kwargs)
    items = resp.get("Items", [])
    # Filter out LOTTERY#/LENTRY# items (BCAST-014)
    items = [i for i in items if not (
        i.get("sort_key", "").startswith("LOTTERY#")
        or i.get("sort_key", "").startswith("LENTRY#")
    )]
    items.reverse()
    messages = [_chat_msg_out(item, viewer_user_id=viewer_user_id) for item in items]
    return {"messages": messages, ...}
```

The `FilterExpression` excludes only soft-deleted items (`deleted != True`). There is no filter on `kind`. A private chat message with `kind="private_chat"` and `deleted=False` passes the filter and is returned as a chat message.

The caller `get_chat_history_route` in `broadcast.py:1597–1613` does not perform any post-processing to exclude private messages. It maps all returned items through `BroadcastChatMessageOut(**m)`, which includes a `kind` field. The `kind="private_chat"` value is serialized directly into the JSON response.

### The scope of exposure

`get_private_chat_history` in `broadcast_private_chat.py:253–281` correctly scopes its query to a specific `private_chat_id` via `FilterExpression: Attr("private_chat_id").eq(chat_id)`. This function is only called by the private-chat-specific endpoint (`GET /sessions/{id}/private-chats/{chat_id}/history`). But the public chat history endpoint bypasses this scoping entirely.

Additionally, `fetch_chat_messages_after` in `broadcast_chat_store.py:288–305` (used by SSE polling for real-time message delivery) has no `FilterExpression` at all — not even the `deleted` check. It would also return live private chat messages to any SSE subscriber.

## 3. Impact / Exploit / Blast Radius

### Privacy violation

Private chat messages are paid, confidential 1-on-1 communications. The tier-1 viewer pays for exclusive access to the creator. If those messages are visible in the public chat history, the privacy expectation of both parties is violated. Depending on the message content (personal topics, financial discussions, intimate conversation), this could constitute a GDPR Article 5 violation (data minimization / purpose limitation).

### Concrete exploit

1. Viewer A pays for a private chat session with Creator B.
2. They exchange messages via `POST /sessions/{id}/private-chats/{chat_id}/messages`.
3. Any other authenticated user C calls `GET /sessions/{id}/chat?limit=200`.
4. The response includes all private chat messages from Viewer A and Creator B, in chronological order interleaved with public messages.
5. C can read the full private conversation without paying and without either party's knowledge.

The exploit requires no authentication bypass — only a valid broadcast viewer session. In an open broadcast, any viewer (or anonymous user if the endpoint permits unauthenticated access) can exploit this.

### Blast radius

All private chat sessions on all broadcast sessions in the table are affected. The `broadcast_chat_messages` table has a TTL of 7 days (`ts + 7 * 24 * 3600`), so messages up to 7 days old are exposed. The number of affected messages is bounded only by how many private chat sessions occurred in the past 7 days.

## 4. Fix Design (code-level)

### 4.1 Add `kind != "private_chat"` filter to `get_chat_history`

The minimal, correct fix is to add `Attr("kind").ne("private_chat")` to the `FilterExpression` in `get_chat_history`. Because public messages lack a `kind` attribute entirely (they don't set `kind` in the DDB item), DynamoDB evaluates `Attr("kind").ne("private_chat")` as `True` for items where `kind` is absent (DynamoDB's `<>` operator on a missing attribute returns `True` when using `ne` with a String value). This means the fix does not require migrating existing public chat records.

```python
def get_chat_history(
    session_id: str,
    limit: int = 100,
    before_sort_key: Optional[str] = None,
    viewer_user_id: Optional[str] = None,
) -> Dict[str, Any]:
    """Get recent chat history in chronological order (oldest first).

    Private-chat-kind messages (kind='private_chat') are always excluded
    from the public chat history.
    """
    kwargs: Dict[str, Any] = {
        "KeyConditionExpression": Key("session_id").eq(session_id),
        "Limit": limit,
        "ScanIndexForward": False,
        "FilterExpression": (
            Attr("deleted").ne(True)
            & Attr("kind").ne("private_chat")   # NEW: exclude private chat messages
        ),
    }
    if before_sort_key:
        kwargs["KeyConditionExpression"] = (
            Key("session_id").eq(session_id) & Key("sort_key").lt(before_sort_key)
        )
    ...
```

### 4.2 Apply the same fix to `fetch_chat_messages_after`

The SSE polling path at `broadcast_chat_store.py:288–305` also has no kind filter and no deleted filter. Both must be added:

```python
def fetch_chat_messages_after(
    session_id: str,
    after_sort_key: Optional[str],
    limit: int = 50,
) -> List[Dict[str, Any]]:
    """Fetch messages after a cursor (for SSE polling). Returns chronological order."""
    kce = Key("session_id").eq(session_id)
    if after_sort_key:
        kce = kce & Key("sort_key").gt(after_sort_key)

    resp = T.broadcast_chat_messages.query(
        KeyConditionExpression=kce,
        Limit=limit,
        ScanIndexForward=True,
        FilterExpression=(               # NEW
            Attr("deleted").ne(True)
            & Attr("kind").ne("private_chat")
        ),
    )
    return resp.get("Items", [])
```

### 4.3 Consider a separate table for private chat messages (long-term)

The root cause is co-locating public and private records in the same table with the same partition key. The `FilterExpression` fix is correct and immediately deployable, but it relies on all query paths correctly excluding `kind="private_chat"`. A more robust long-term solution is to write private chat messages to a dedicated `broadcast_private_chat_messages` table. This eliminates the class of bug entirely (private messages can never leak to a query on the public table). This is a larger refactor warranting its own ticket.

### 4.4 SECOPS-007 dev/prod parity

The fix is a `FilterExpression` addition to DynamoDB queries. DynamoDB Local (`localhost:8001`) and production AWS DynamoDB have identical filter semantics. No dev/prod divergence is introduced.

### 4.5 FilterExpression and page size

DynamoDB applies `FilterExpression` after fetching up to 1 MB of data (or the `Limit` number of items, whichever is smaller first). For `get_chat_history` with `Limit=100`, if private chat messages are numerous relative to public messages, the effective return count may be less than 100 after filtering. This is acceptable: the caller already handles partial pages via `has_more`. For `fetch_chat_messages_after` with `Limit=50`, the same consideration applies. The existing over-fetch pattern used in `get_private_chat_history` (fetching `limit * 3` items, line 267) should be considered here if private chat messages constitute a significant fraction of the table.

- Add a metrics event `broadcast/chat/private_message_leak_prevented` (counter) if an item with `kind="private_chat"` is detected in a context where it would previously have been returned — this can be done in a temporary audit log to measure historical exposure.

### Rollout

- **Effort**: S (2–3 line change to `FilterExpression`; 5 lines for SSE path; 15 lines for tests).
- **Feature flag**: None needed; this is a privacy fix that must be deployed unconditionally.
- **Backward compatibility**: Existing public chat clients will simply no longer see private messages interleaved in the history. This is the intended behavior. No client-side changes are needed.
- **Migration**: No DDB migration needed. The fix is read-path only; existing items are not modified.
- **Risk**: Low. The `FilterExpression` addition is purely subtractive — it removes items from a query result that should never have appeared. The only theoretical regression is a DynamoDB cost increase (FilterExpression on a `kind` attribute that is absent on most items adds a small filter evaluation cost), but this is negligible for a per-session query.
- **Priority**: This is the highest-urgency fix in this batch. It is a live privacy violation affecting any session with active private chats. Should be deployed before GAP-0121/GAP-0122/GAP-0123/GAP-0124.
- **Sequencing**: Independent of all other GAPs in this batch; deploy immediately.
