# GAP-0369: Worker completes job then tries illegal "published" transition — Remediation Write-up

> ~5 pages. Fix-oriented. Claim verified against actual code (no investigation doc exists).

## 1. Summary & Classification

**Severity**: HIGH  
**Source ticket**: VOD-003  
**Owning area**: VOD pipeline / transcode worker  
**Status**: Open  
**Claim verdict**: CONFIRMED — the illegal transition is at line 203 of `app/services/transcode_worker.py`, and the missing "encoding" transition after claim is also absent.

When the transcode worker successfully finishes processing a video, it attempts to advance the video's lifecycle status directly to `"published"` (`app/services/transcode_worker.py:203`). The full required state-machine path is `pending_encoding → encoding → pending_review → approved → published`. The worker jumps from whatever status the video is currently in (typically `"probing"` due to GAP-0366/0368) directly to `"published"`, which is an illegal transition at every plausible source status. The call is wrapped in a bare `except Exception`, so the failure is swallowed. The video is never published. Additionally, the worker never calls `transition_video_status(..., to_status="encoding")` after claiming a job, leaving the video's status unreflected in the metadata table during the encoding phase.

**Dependency**: GAP-0369 is partly masked by GAP-0366/0368. If those are fixed first, videos will reach `"pending_encoding"` before the worker claims them. After GAP-0369 is also fixed, the full state-machine path will be traversed correctly.

**Related tickets**: GAP-0366, GAP-0368, VOD-003.

## 2. Current-State Investigation (root cause)

### Defect 1 — illegal "published" transition at job completion

**`app/services/transcode_worker.py`, lines 199–205**:

```python
# Transition video to published if video_metadata store is available
try:
    from app.services.video_metadata_store import transition_video_status

    transition_video_status(video_id=job["video_id"], to_status="published")
except Exception:
    logger.warning("Could not transition video %s to published", job["video_id"])
```

The state machine (`app/services/video_state_machine.py`) requires `"published"` to be reached via `"approved"`:

```
approved → published   (the only legal predecessor to "published")
```

At the point this code runs, the video status is one of:
- `"probing"` (if GAP-0366/0368 are not yet fixed)
- `"pending_encoding"` (after GAP-0366/0368 fix, before encoding transition)

Neither is a legal predecessor to `"published"`. The call raises `HTTPException(409)`, which is caught silently.

### Defect 2 — no "encoding" transition after job claim

After `claim_job` succeeds (`transcode_worker.py:91`), the job-store row transitions to `status="running"`. The video-metadata row should simultaneously advance to `"encoding"` to signal to the player and dashboard that transcoding is actively in progress. There is no such call anywhere in `execute_transcode_job`.

The omission has two consequences:

1. The video-metadata `ByStatusCreatedAt` GSI partition for `"encoding"` is always empty, even while jobs are actively running.
2. The `VideoPlayerPage.tsx` treats `"pending_encoding"` and `"encoding"` identically (both show the processing spinner), so users see no differentiation. More critically, admin dashboards that track encoding progress by watching `status = "encoding"` are permanently dark.

### The correct full transition sequence

The worker must follow the state machine's prescribed path:

| Event | Video status after | Job status after |
|---|---|---|
| Job submitted (router) | `pending_encoding` | `queued` |
| Worker claims job | `encoding` | `running` |
| Worker completes job | `pending_review` | `completed` |
| Admin approves | `approved` | (job unchanged) |
| Admin publishes | `published` | (job unchanged) |

The fix addresses: job submission (GAP-0366/0368), the missing `encoding` transition, and the incorrect `published` transition.

### Dev vs prod parity

All calls to `transition_video_status` execute identically against DynamoDB Local in dev and AWS DynamoDB in production. There is no dev-mode fork. The bug fires in both environments.

## 3. Impact / Exploit / Blast Radius

### Videos are never published

Because the post-completion transition always fails, no video that goes through the worker ever becomes `"published"`. The video-metadata row stays in `"probing"` (or `"pending_encoding"` after GAP-0366/0368 fix), perpetually showing the "processing" spinner in the player page.

### Revenue impact

- Pay-per-view and subscription-gated videos can only be served once `status == "published"`. Videos locked in `"probing"` or `"pending_encoding"` are unreachable by the player entitlement check.
- Creator revenue from VOD is zero until this chain of bugs is corrected.

### Review workflow bypass attempt

The transition `encoding → pending_review` is the correct completion target. Jumping to `"published"` would also bypass the `pending_review → approved` human review step — if it had succeeded. In the current state the attempt fails silently, so the review bypass does not actually occur. However, the intent in the code is clearly to skip review entirely, which represents a latent compliance and moderation risk if the state machine's guard is ever relaxed.

### Admin/monitoring impact

- `status = "encoding"` GSI is never populated → encoding queue appears empty even during active jobs.
- `status = "pending_review"` GSI is never populated → review queue appears empty, blocking the moderation workflow.

## 4. Fix Design (code-level)

### Change 1: Add "encoding" transition immediately after job claim

**File**: `app/services/transcode_worker.py`, after line 95 (after `claim_job` succeeds and before processing begins)

Insert:

```python
# Advance video metadata status to "encoding"
try:
    from app.services.video_metadata_store import transition_video_status as _tsv
    _tsv(video_id=job["video_id"], to_status="encoding")
except Exception:
    logger.warning(
        "Could not transition video %s to encoding after claim", job["video_id"]
    )
```

This call goes after `logger.info("Claimed transcode job %s", job_id)` (line 95) and before `scratch_dir` creation on line 96.

Prerequisite: the video must be in `"pending_encoding"` when the worker claims it. This will be true once GAP-0366/0368 is fixed.

### Change 2: Replace "published" with "pending_review" at completion

**File**: `app/services/transcode_worker.py`, line 203

Change:
```python
transition_video_status(video_id=job["video_id"], to_status="published")
```
To:
```python
transition_video_status(video_id=job["video_id"], to_status="pending_review")
```

Update the comment on line 199:
```python
# Transition video to pending_review — awaits admin approval before publish
```

### SECOPS-007 dev/prod parity

No AWS-specific logic is involved. Both changes call `transition_video_status`, which is a DynamoDB write that executes identically in dev and production. No feature flag needed.

### Review-bypass concern

The fix to target `"pending_review"` (not `"published"`) enforces the mandatory human review step before a video is publicly accessible. Any future change that attempts to auto-approve or skip review must go through the state machine explicitly (e.g., `transition_video_status(..., to_status="approved")` followed by `transition_video_status(..., to_status="published")`), which will be visible in code review. The two-step explicit sequence also ensures the `published_at` timestamp is set correctly in `transition_video_status` (`app/services/video_metadata_store.py:394`), which sets `published_at` only when transitioning to `"published"` — not when transitioning to `"pending_review"`. If the worker had successfully jumped to `"published"` directly, `published_at` would have been set at encoding-completion time rather than at admin-approval time, producing misleading analytics about when videos were actually released.

### Interaction with VOD-005 outputs

After `complete_job_with_outputs` stores the HLS manifest URI and playback URL in the `TranscodeJobs` table, the video-metadata table needs to receive the `hls_manifest_s3_key`, `hls_manifest_url`, and `thumbnail_url` fields from the upload result. Currently these are not propagated to `VideoMetadataModel` in the worker. The correct place to do this is immediately before the `pending_review` transition:

```python
# After complete_job_with_outputs, update video metadata with output URIs
try:
    from app.services.video_metadata_store import update_video
    update_video(
        video_id=job["video_id"],
        updates={
            "hls_manifest_url": upload_result.hls_manifest_uri,
            "thumbnail_url": upload_result.thumbnail_url,
        },
    )
except Exception:
    logger.warning("Could not update video %s with output URIs", job["video_id"])
```

This is a follow-on improvement beyond the core GAP-0369 fix, but should be included in the same PR to avoid a second partial-fix cycle.

### Backward compatibility

- Videos currently stuck in `"probing"` or `"pending_encoding"` need manual status advancement via the admin API after all three GAPs (0366, 0368, 0369) are fixed.
- No DynamoDB schema changes required.

**Before fix (test 1)**: The worker makes no `transition_video_status` call with `to_status="encoding"` because no such call exists in the pre-fix code. The assertion `assert len(encoding_calls) >= 1` fails, correctly identifying the missing transition.

**Before fix (test 2)**: The worker calls `transition_video_status(video_id=..., to_status="published")`. The assertion `assert final_status == "pending_review"` fails, and the failure message explicitly names the review-bypass risk.

**After fix (test 1)**: The `"encoding"` call is present → passes.  
**After fix (test 2)**: The final call targets `"pending_review"` → passes.

These two tests together verify both the defects described in the GAP: the missing intermediate transition and the incorrect terminal transition. They are designed to be independent of each other so that if only one fix is applied, exactly one test fails, pinpointing the remaining gap.

### Rollout

- **Effort**: S (two-line change + tests).
- **Sequencing**: Deploy after GAP-0366/0368 fix. Without GAP-0366/0368, the `"encoding"` transition will fail because the video will be in `"probing"` or `"created"`, not `"pending_encoding"`. All three fixes — GAP-0366/0368 (router) and GAP-0369 (worker) — should ship in the same deployment for the end-to-end lifecycle to be correct.
- **Risk**: Low. Both changes tighten the worker into alignment with the documented state machine. The only observable difference from a user's perspective is that completed videos now enter the review queue rather than staying in `"probing"`. No external API contracts change.
- **Data repair**: Any video currently stuck in `"probing"` or `"pending_encoding"` with a `"completed"` job will need manual status advancement. An admin repair script should query `TranscodeJobs` for `status == "completed"` jobs, look up each corresponding video, and advance the video to `"pending_review"` if it is stuck in a pre-review state. See the data repair section in GAP-0368 for the detailed script design.
- **Rollback**: Revert the two-line changes. No schema migration.

### Compliance note: enforcing the review step

The fix to target `"pending_review"` (rather than `"published"`) is not merely a correctness fix — it enforces a compliance control. Many VOD platform licensing agreements and content moderation policies require that all uploaded content pass through a human or automated review step before public distribution. The original code, if it had succeeded, would have silently published every video without any review. The fix ensures that the human review gate (`pending_review → approved → published`) is always traversed, and that this invariant is visible in the state machine definition rather than depending on per-endpoint logic.
