# GAP-0270: Profile field name misalignment causes zero match score — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: KYC-010. Owning area: KYC ID scanner / profile cross-check.

## 1. Summary & Classification

**Bug**: `app/services/kyc_id_scanner.py`, `_load_crosscheck_profile` (line 433–454) builds
the dict used for document cross-checking using:

```python
out["first_name"] = profile.get("first_name") or ""
out["last_name"]  = profile.get("last_name") or ""
```

If a user registered with only a `display_name` (e.g. "Jane Smith") and did not separately
fill in the structured `first_name` / `last_name` profile fields, both values are `""`.
`cross_reference_profile` (line 334–380) then assembles `profile_name = ""`, skips the name
comparison block entirely (because both `extracted_name` and `profile_name` must be non-empty
to compare), and returns `match_score = 0`. A score below 50 triggers `STATUS_FLAGGED` in
`_derive_status` (line 597–599). Every user who registered with only a display name has their
ID scan flagged for manual review, irrespective of actual document accuracy.

**Claim accuracy**: **Confirmed correct.** `_load_crosscheck_profile` has no fallback to
split `display_name` into first/last name parts. The `get_profile` service returns a merged
dict from `profiles` DDB table; if `first_name` / `last_name` were never stored, both values
are `None` (see `empty_profile()` in `app/services/profile.py`, lines 199–217).

- **Severity**: HIGH
- **Source ticket**: KYC-010
- **Status**: Open
- **Owning area**: KYC ID scanner / profile service
- **One-line impact**: All users who registered without explicitly setting structured name
  fields receive a guaranteed "flagged" status on every ID scan, flooding the reviewer queue
  with false positives and blocking automated approvals.
- **Related tickets**: GAP-0266 (submission hook), KYC-010 (passport scanner spec),
  KYC-008 (risk scoring — also uses `first_name`/`last_name` for `profile_completeness` factor)

## 2. Current-State Investigation (root cause)

### Profile data layout

`app/services/profile.py`:

- `empty_profile()` (line 199–217): returns a dict with `"display_name": None`,
  `"first_name": None`, `"last_name": None`.
- `get_profile(user_sub)` (line 220–227): fetches the `profiles` DDB table row and merges
  `item["profile"]` into `empty_profile()`. A user who set only `display_name` has
  `first_name=None`, `last_name=None` in the merged result.
- `update_profile` (lines 148–155): updates only fields present in the request. Registration
  (`RegisterStartReq.full_name`) likely stores the full name in `display_name` without
  decomposing it into `first_name`/`last_name`.

### _load_crosscheck_profile — the bug

`app/services/kyc_id_scanner.py`, lines 433–454:

```python
def _load_crosscheck_profile(self, user_sub: str, case: dict[str, Any] | None) -> dict[str, Any]:
    out: dict[str, Any] = {}
    try:
        from app.services.profile import get_profile
        profile = get_profile(user_sub) or {}
    except Exception:
        profile = {}
    out["first_name"] = profile.get("first_name") or ""   # line 442
    out["last_name"]  = profile.get("last_name") or ""    # line 443
    out["date_of_birth"] = profile.get("birthday") or profile.get("date_of_birth") or ""
    out["nationality"] = profile.get("nationality") or profile.get("country") or ""
    # case META may carry overriding identity fields (lines 446–453)
    if case:
        ident = case.get("identity") or {}
        if isinstance(ident, dict):
            out["first_name"] = ident.get("first_name") or out["first_name"]
            out["last_name"]  = ident.get("last_name") or out["last_name"]
            ...
    return out
```

There is **no fallback** to `display_name` when `first_name` and `last_name` are absent.
The function returns `out["first_name"] = ""` and `out["last_name"] = ""`.

### cross_reference_profile — the consequence

`app/services/kyc_id_scanner.py`, lines 334–380:

```python
extracted_name = f"{extraction.get('given_names', '')} {extraction.get('surname', '')}".strip()
profile_name   = f"{profile.get('first_name', '')} {profile.get('last_name', '')}".strip()

if extracted_name and profile_name:     # <-- guard: skipped if profile_name == ""
    total += 1
    if _normalize_name(extracted_name) == _normalize_name(profile_name):
        matches["name"] = ...
        score += 1
    elif _normalize_name(extraction.get("surname", "")) == _normalize_name(profile.get("last_name", "")):
        matches["surname"] = ...
        score += 0.5
    else:
        mismatches["name"] = ...
```

When `profile_name = ""`, `total` remains 0. The final result:

```python
"match_score": round(score / max(total, 1) * 100)  # = round(0 / 1 * 100) = 0
```

`_derive_status` (line 597–599):

```python
if cross_reference is not None and int(cross_reference.get("match_score", 0)) < 50:
    return STATUS_FLAGGED
```

Score 0 < 50 → `STATUS_FLAGGED` for every scan.

### How widespread is the issue?

Any user whose profile was set up using the registration `full_name` field (which maps to
`display_name` in the profile service) without subsequently visiting the profile settings
to add structured `first_name` / `last_name` values will be affected. In a typical deployment,
this could be the majority of users, since structured names are not required at registration.

---

## 3. Impact / Exploit / Blast Radius

**False-positive flood**: Every ID scan for a `display_name`-only user is flagged. In a
production deployment with thousands of users, the reviewer queue is dominated by false
positives, obscuring genuine flags (check digit failures, expired documents, actual name
mismatches).

**Automated approval blocked**: `_derive_status` returns `STATUS_FLAGGED` rather than
`STATUS_MATCHED`. Flagged scans cannot auto-approve. The risk-scoring engine (via
`_feed_risk_scoring` → `compute_score`) will read `cross_reference.match_score=0` for the
scan, inflating the `document_quality` and implicitly the overall risk score.

**Compliance**: Incorrectly flagging users who provided valid documents degrades the
accuracy of the KYC audit trail and creates misleading reviewer notes.

**No security downside to the fix**: The fix adds a fallback that *increases* the match
score for valid name matches. It cannot permit a mismatch to pass — if the document name
does not match the display name, `mismatches["name"]` is still set and score remains low.

## 4. Fix Design (code-level)

### Change — add display_name fallback in `_load_crosscheck_profile`

In `app/services/kyc_id_scanner.py`, `_load_crosscheck_profile` (lines 441–443):

```python
out["first_name"] = profile.get("first_name") or ""
out["last_name"]  = profile.get("last_name") or ""

# GAP-0270: if structured name fields are absent, attempt to derive them from display_name.
if not out["first_name"] and not out["last_name"]:
    display_name = str(profile.get("display_name") or "").strip()
    if display_name:
        parts = display_name.split(None, 1)   # split on first whitespace, max 2 parts
        out["first_name"] = parts[0] if parts else ""
        out["last_name"]  = parts[1] if len(parts) > 1 else ""
```

**Logic**: Split `display_name` on the first whitespace. For "Jane Smith" this yields
`first_name="Jane"`, `last_name="Smith"`. For single-word names like "Cher", `first_name="Cher"`,
`last_name=""` — the name comparison will then compare `extracted_name = "CHER ..."` against
`profile_name = "CHER"` and compute a partial match using `SequenceMatcher`.

The split is intentionally simple. MRZ surnames map to `surname` and given names to
`given_names`; the composite `extracted_name` is `given_names + " " + surname`. Splitting
`display_name` on the first space into first/last is a best-effort approximation sufficient
for the purpose of avoiding a guaranteed zero score.

### Why not fix `cross_reference_profile` directly?

An alternative is to fall back to `display_name` inside `cross_reference_profile`. However,
`cross_reference_profile` is a stateless helper that receives a pre-built `profile` dict — it
has no access to the raw profile. Fixing at `_load_crosscheck_profile` is cleaner and keeps
the transformation in one place.

### Handling single-word display names

When `last_name=""` after the split, `cross_reference_profile` assembles `profile_name = "CHER"`.
The extracted name from a passport is typically `"CHER"` (given_names empty, surname "CHER").
The comparison `_normalize_name(extracted_name) == _normalize_name(profile_name)` would be
`"CHER" == "CHER"` → match. This is correct behaviour.

### Risk-scoring engine side-fix

`kyc_risk_scoring._compute_profile_completeness` (line 430–446) also checks
`profile.get("first_name")` and `profile.get("last_name")`. It uses `T.users.get_item` with
`Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"}` — which is the wrong key pattern for the
users table (see GAP-0267 residual issue). When that key-schema fix is applied, the
completeness factor may similarly need a `display_name` fallback. Recommend applying the
same fallback pattern in `_compute_profile_completeness` as part of the same PR.

### Dev/Prod parity (SECOPS-007)

The fix is in pure Python logic within `_load_crosscheck_profile`. No AWS-specific code paths
are touched. In dev, `get_profile` reads from DynamoDB Local via the moto mock, so the fix
exercises the same code path in dev and production. The `S.kyc_id_scanner_real_ocr_enabled`
flag gates MRZ extraction, not the cross-reference step; the fix applies regardless of OCR mode.

## 5. Testing, Verification & Rollout

### Regression test — display_name fallback prevents false flag (pytest offline)

```python
def test_display_name_fallback_prevents_false_flag(
    mocked_kyc_cases_table, mocked_profiles_table
):
    """A user with only display_name should not receive match_score=0 when document name matches."""
    from app.services.kyc_id_scanner import cross_reference_profile, _load_crosscheck_profile, KycIdScannerStore

    # Simulate a profile with only display_name set (no first_name/last_name)
    store = KycIdScannerStore()
    user_sub = "u_display_only"
    mocked_profiles_table.put_item(Item={
        "user_sub": user_sub,
        "profile": {"display_name": "Anna Eriksson"},
    })
    case = None  # no case-level identity override

    profile = store._load_crosscheck_profile(user_sub, case)

    assert profile["first_name"] == "Anna", (
        f"Expected first_name='Anna' from display_name split, got '{profile['first_name']}'"
    )
    assert profile["last_name"] == "Eriksson", (
        f"Expected last_name='Eriksson' from display_name split, got '{profile['last_name']}'"
    )

    # MRZ extraction for mock passport gives surname=ERIKSSON, given_names=ANNA MARIA
    extraction = {
        "given_names": "ANNA MARIA",
        "surname": "ERIKSSON",
        "date_of_birth": "1974-08-12",
        "nationality": "UTO",
    }
    result = cross_reference_profile(extraction, profile)

    assert result["match_score"] > 0, (
        f"Expected non-zero match_score but got {result['match_score']}. "
        "display_name fallback did not propagate into cross_reference_profile."
    )
```

**Fails before fix**: `profile["first_name"] = ""`, `profile["last_name"] = ""`,
`match_score = 0`.
**Passes after fix**: `profile["first_name"] = "Anna"`, surname partial match → score > 0.

### Regression test — genuine mismatch still flagged

```python
def test_genuine_name_mismatch_still_flagged(mocked_profiles_table):
    """A real name mismatch must not be cleared by the display_name fallback."""
    store = KycIdScannerStore()
    user_sub = "u_mismatch"
    mocked_profiles_table.put_item(Item={
        "user_sub": user_sub,
        "profile": {"display_name": "Jane Smith"},
    })

    extraction = {"given_names": "MARIA", "surname": "JOHNSON", "date_of_birth": None, "nationality": None}
    profile = store._load_crosscheck_profile(user_sub, None)
    result = cross_reference_profile(extraction, profile)

    # Smith vs JOHNSON — different surnames; score should be well below 50
    assert result["match_score"] < 50, (
        f"A name mismatch should still score < 50 but got {result['match_score']}"
    )
```

**Passes before and after fix**: The fallback improves true matches; it does not mask genuine
mismatches.

### End-to-end / manual QA steps

1. Register a user via the API with only `full_name` (no structured fields). Confirm via DDB
   that the `profiles` table row has `display_name` set but `first_name=null`.
2. Create a KYC case for that user and submit a mock passport scan.
3. Call `GET /ui/kyc/id-scanner/cases/{case_id}/scans`.
   - **Before fix**: `status="flagged"`, `cross_reference.match_score=0`,
     `cross_reference.total_fields_checked=0`.
   - **After fix**: `status="matched"`, `cross_reference.match_score≥50`,
     `cross_reference.total_fields_checked≥1`.
4. Verify a genuine mismatch still flags: use a user with `display_name="John Doe"`,
   scan with the mock `ERIKSSON` passport MRZ — expect `status="flagged"`, score < 50.
5. Verify a user with structured names set (`first_name="Anna"`, `last_name="Eriksson"`) is
   unaffected: fallback branch is not entered (both fields non-empty), outcome identical to
   current behavior for users who have structured names.

### Rollout

Single-function change, no schema or API changes. Deployable immediately. Effort: **S**
(< 1 hour including test). Recommend pairing with the GAP-0266 submission hook PR so the
improved cross-reference score is part of the first complete scoring run at submission time.

### Longer-term fix: structured names at registration

The root cause of this gap is that the registration flow stores the user's full name as
`display_name` without decomposing it into `first_name` / `last_name`. A longer-term fix
is to update `create_user_record` in `app/services/registration.py` to attempt a name split
at account creation time:

```python
parts = (full_name or "").strip().split(None, 1)
if len(parts) >= 2:
    profile_updates["first_name"] = parts[0]
    profile_updates["last_name"] = parts[1]
elif parts:
    profile_updates["display_name"] = parts[0]
```

This would ensure that new accounts always have structured names, making the fallback in
`_load_crosscheck_profile` a safety net for existing accounts only. This change is a
separate PR (touches registration + profile service) and should be coordinated with the
frontend `RegisterPage` to allow users to provide first/last separately.

### Retroactive data repair

Existing users at Tier 0 with `display_name` set but no structured names will benefit from
the `_load_crosscheck_profile` fallback immediately on their next scan. No data migration is
needed — the fix is purely a runtime computation. If the platform requires retroactive
structured-name data (e.g., for compliance exports), a one-time script can split existing
`display_name` values for users who lack `first_name` / `last_name`. This is out of scope
for the GAP fix but should be noted in the data team's backlog.

### Impact on reviewer queue backlog

If the system has been running in production with the bug active, the reviewer queue contains
a backlog of scans flagged solely due to this zero-score issue. Once the fix is deployed,
new scans for these users will correctly produce `STATUS_MATCHED`. However, historical flagged
scans remain in the `STATUS_FLAGGED` state and require a bulk adjudication pass. The
`adjudicate` method on `KycIdScannerStore` can be called programmatically to bulk-clear
false-positive flagged scans where `cross_reference.total_fields_checked=0` and
`cross_reference.match_score=0` (the signature of this specific bug), provided the reviewer
confirms the document MRZ itself was valid (no check-digit failures, no expiry). A one-time
admin tooling script to scan the `kyc_id_scans` table and batch-clear these records should
be prepared alongside the code fix. Estimated blast radius: potentially 100% of scans
submitted before the fix on a fresh deployment where all users registered without structured
names.
