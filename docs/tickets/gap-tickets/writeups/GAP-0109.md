# GAP-0109: frontend shows hard dead-end with no recovery UI — Remediation Write-up

> Claim verified against `frontend/src/pages/Register.tsx`. Claim is **confirmed**.
> Line 616 renders the `emailStatus === "unavailable"` branch. It displays only a static
> error message with no resend button or recovery link, and line 177-178 shows that
> `emailStatus === "unavailable"` disables the Next button. The cited line number (616) is
> exactly correct.

## 1. Summary & Classification

**Bug**: When `POST /ui/register/check` returns `available: false`, the Register page sets
`emailStatus = "unavailable"` and renders a hard dead-end: the error message "An account
with this email already exists" is shown, the Next button is disabled, and there is no way
for the user to recover from this state without leaving the page. Users with abandoned
(pending_verification) registrations are permanently stuck.

- **Severity**: HIGH (any user who abandons a registration and returns later cannot
  self-recover; effectively loses access to that email address for registration)
- **Source ticket**: AUTH-001
- **Status**: Open
- **Owning area**: Frontend registration page (`frontend/src/pages/Register.tsx`)
- **Verdict**: Confirmed. The single `"unavailable"` branch at line 616 handles all
  "email taken" cases without distinguishing verified vs unverified accounts.
- **Claim accuracy**: Fully accurate. Line 616 is the JSX rendering the dead-end message,
  and lines 177-178 confirm `isSubmitDisabled` is `true` when `emailStatus === "unavailable"`.
- **Related tickets**: GAP-0107 (backend must expose `unverified: bool` in `/check` response —
  prerequisite), GAP-0108 (backend must re-issue challenge on `/start` for pending accounts —
  makes resend actually work end-to-end). All three must ship together for a complete fix.

## 2. Current-State Investigation (root cause)

### High-level flow: where the dead-end is reached

1. User lands on `/register`.
2. User types an email address that belongs to a `pending_verification` account.
3. After a 400ms debounce, `registerEmailCheck` is called (`POST /ui/register/check`).
4. Backend returns `{"status": "ok", "available": false}` (current shape, no `unverified`).
5. `setEmailStatus("unavailable")` is called at Register.tsx:247.
6. React re-renders: the error paragraph at line 616 appears; `isSubmitDisabled` becomes
   `true` at line 178; the Next button is greyed out and unclickable.
7. There are no other controls rendered in this branch. The user is stuck.

The resend capability exists (`POST /ui/register/resend`, imported as `registerResend` at
line 17, used in the verify step's resend button at line 872), but it is only reachable after
`setStep("verify")` is called, which only happens after a successful submission. Since
submission is blocked, the user can never reach the verify step.

### emailStatus type definition — Register.tsx:90-91

```typescript
const [emailStatus, setEmailStatus] = React.useState<
  "idle" | "checking" | "available" | "unavailable" | "invalid" | "error" | "rate_limited"
>(...);
```

There is a single `"unavailable"` state that covers all cases where the backend returns
`available: false`. The type has no slot for `"unavailable_unverified"`.

### Check response consumption — Register.tsx:247

```typescript
setEmailStatus(data.available ? "available" : "unavailable");
```

The `data` object from `registerEmailCheck` is typed as `RegisterEmailCheckResp`. After the
GAP-0107 fix the response will include `unverified: bool`, but this line will still collapse
both cases into `"unavailable"` until this fix is applied.

### isSubmitDisabled — Register.tsx:174-179

```typescript
const isSubmitDisabled = startLoading
  || isEmailChecking
  || hasPasswordIssues
  || emailStatus === "invalid"
  || emailStatus === "unavailable"    // line 178 — blocks submit for ALL unavailable cases
  || emailStatus === "rate_limited";
```

`"unavailable"` unconditionally blocks submission regardless of whether the account is
verified or just pending.

### Dead-end JSX — Register.tsx:616-621

```tsx
{!form.formState.errors.email && emailStatus === "unavailable" && (
  <p className="flex items-center gap-1 text-xs text-destructive">
    <XCircle className="h-3.5 w-3.5" />
    An account with this email already exists.
  </p>
)}
```

No button, no link, no resend option. The user cannot proceed. The resend endpoint exists
(`POST /ui/register/resend`) and is already imported via `registerResend` at line 17, but it
is never exposed in this branch.

### The verify step has a resend button — Register.tsx:872-875

```tsx
<Button disabled={resendLoading}>
  {resendLoading ? "Resending..." : "Resend code"}
</Button>
```

This button is only visible on the `"verify"` step. If the user never reaches that step (because
the Next button is disabled), they never see this option.

### Dev vs prod

The bug is entirely frontend logic; it manifests identically in both dev and prod. It depends
on the API response shape, so it is only fully fixable once GAP-0107 ships the `unverified`
field.

## 3. Impact / Exploit / Blast Radius

### User experience

Any user who:
1. Started registration with email X
2. Closed the browser before verifying
3. Returns to the registration page and enters email X again

…sees "An account with this email already exists" with no further action possible. They must
either use a different email address or contact support. The platform loses that user.

### UX for active-account holders

Users with fully verified accounts who accidentally land on the registration page also see the
same dead-end message with no "sign in instead" link on the message itself (there is a sign-in
link at the top of the form but no contextual pointer near the error).

### Security

There is no security risk introduced by showing a resend button for unverified accounts: the
button calls `POST /ui/register/resend`, which is already rate-limited. An attacker who knows
an email address was used in an abandoned registration learns nothing beyond what `/check`
already tells them.

## 4. Fix Design (code-level)

### Step 1 — Update emailStatus type

In `frontend/src/pages/Register.tsx` at line 90:

```typescript
const [emailStatus, setEmailStatus] = React.useState<
  | "idle"
  | "checking"
  | "available"
  | "unavailable"
  | "unavailable_unverified"  // new: email taken but not yet verified
  | "invalid"
  | "error"
  | "rate_limited"
>("idle");
```

### Step 2 — Update check response consumption (line 247)

```typescript
if (data.available) {
  setEmailStatus("available");
} else if (data.unverified) {
  setEmailStatus("unavailable_unverified");
} else {
  setEmailStatus("unavailable");
}
```

This requires GAP-0107 to have added `unverified: boolean` to the `RegisterEmailCheckResp`
TypeScript type in `frontend/src/api/types.ts` (or the relevant endpoint types file).

### Step 3 — Update isSubmitDisabled (lines 174-179)

`"unavailable_unverified"` should NOT block submission, because we want the user to be able
to click "Resend code / Start over" instead of clicking the main Next button. The Next button
itself will not advance registration for unverified accounts; it will instead call the resend
flow. The simplest approach is a dedicated handler:

```typescript
const isSubmitDisabled = startLoading
  || isEmailChecking
  || hasPasswordIssues
  || emailStatus === "invalid"
  || emailStatus === "unavailable"         // verified account — still blocked
  // "unavailable_unverified" intentionally NOT blocked — user can click Resend
  || emailStatus === "rate_limited";
```

Alternatively, if you want to keep the Next button semantically accurate, keep it disabled
for `"unavailable_unverified"` too and rely solely on the inline resend button described below.

### Step 4 — Replace dead-end JSX with recovery UI (around line 616)

```tsx
{!form.formState.errors.email && emailStatus === "unavailable" && (
  <div className="flex items-start gap-2 text-xs text-destructive">
    <XCircle className="h-3.5 w-3.5 mt-0.5 shrink-0" />
    <span>
      An account with this email already exists.{" "}
      <Link to="/login" className="underline">Sign in instead?</Link>
    </span>
  </div>
)}
{!form.formState.errors.email && emailStatus === "unavailable_unverified" && (
  <div className="flex flex-col gap-2 rounded-md border border-amber-200 bg-amber-50 p-3 text-xs">
    <p className="flex items-center gap-1 text-amber-700 font-medium">
      <AlertCircle className="h-3.5 w-3.5" />
      A verification is pending for this email.
    </p>
    <p className="text-muted-foreground">
      We can resend the verification code, or you can start over with a different email.
    </p>
    <Button
      type="button"
      size="sm"
      variant="outline"
      disabled={resendLoading}
      onClick={handleResendFromCheck}
    >
      {resendLoading ? "Sending…" : "Resend verification code"}
    </Button>
  </div>
)}
```

`AlertCircle` must be added to the lucide-react import at line 6.

### Step 5 — Add handleResendFromCheck handler

```typescript
const handleResendFromCheck = React.useCallback(async () => {
  setResendLoading(true);
  try {
    await registerResend({ email: form.getValues("email") });
    // Navigate to verify step so the user can enter the code
    setRegisteredEmail(form.getValues("email"));
    setDeliveryInfo("We sent a new verification code to your email.");
    setStep("verify");
  } catch (err) {
    setError("Could not resend verification code. Please try again.");
  } finally {
    setResendLoading(false);
  }
}, [form]);
```

### Step 6 — Update API types

In `frontend/src/api/types.ts` (or wherever `RegisterEmailCheckResp` is defined), add:

```typescript
export interface RegisterEmailCheckResp {
  status: string;
  available: boolean;
  unverified?: boolean;   // present after GAP-0107 backend fix
}
```

### Dev/Prod parity (SECOPS-007)

This is a purely frontend change. The resend call (`POST /ui/register/resend`) works
identically in dev and prod. In dev mode the verification email is written to the mock mail
log rather than sent via SMTP; the frontend behaviour is unchanged.

### Backward compatibility

If the backend has not yet shipped the GAP-0107 `unverified` field, `data.unverified` is
`undefined` (falsy), and `setEmailStatus("unavailable")` is reached — identical to today's
behaviour. The frontend change is safe to ship before the backend change.

### Accessibility and i18n considerations

The amber recovery panel should use `role="alert"` so screen readers announce it
immediately when it appears. The "Resend verification code" button should have an explicit
`aria-label` that includes the email address for screen reader clarity. The text strings
should be added to the i18n resource bundle (if one exists) rather than hardcoded.

### Edge case: /check returns unverified but /start resume is disabled server-side

If GAP-0108's `REGISTRATION_ALLOW_RESUME_UNVERIFIED` flag is `false` in the environment,
`handleResendFromCheck` calls `POST /ui/register/resend` directly. The `/resend` endpoint
does not gate on that flag — it re-issues a challenge for any user who has a user record and
can pass the rate limiter. Therefore the frontend resend path works even if the `/start`
resume path is disabled. The two flags are independent.

### Rollout

- **Effort**: S (JSX additions, one callback handler, one type update; estimated 1-2 hours
  of implementation plus review)
- **Sequencing**: can ship after GAP-0107 backend fix is deployed; the frontend change is
  backward-compatible with the old response shape (`unverified` defaults to `undefined`/falsy
  which keeps the old `"unavailable"` branch); it is safe to deploy this frontend change
  before the backend change but the new recovery UI will never appear until GAP-0107 ships
- **Rollback**: revert Register.tsx; users return to the current dead-end — no data loss,
  no server-side state affected
- **Risk**: low — additive UI change; the only new API call (`/resend`) already exists and
  is rate-limited; no changes to authentication state or session management
