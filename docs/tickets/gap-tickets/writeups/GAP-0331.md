# GAP-0331: `finalize_deletion` does not anonymize messages or posts — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/services/account_deletion.py`.

## 1. Summary & Classification

**Gap**: When a user's deletion request passes the grace period and `finalize_deletion` fires, the cascade writes a `deletion_summary` stub with `messages_anonymized: 0` and `posts_anonymized: 0` — but neither counter ever increases because the corresponding anonymization logic is never called. Deleted-user messages remain in the `Messages` table with the real `sender_id` value, and newsfeed posts remain in the `Posts` DynamoDB table with the real `user_id` / `author_id` fields. Anyone who can enumerate messages or posts (participants in a conversation, or feed consumers) can still identify the deleted user by their sub or profile lookup.

**Claim status**: Confirmed exactly as written. The `finalize_deletion` function at `app/services/account_deletion.py:359` initialises `summary["messages_anonymized"] = 0` and `summary["posts_anonymized"] = 0` but takes no action to fill those values; there is no `_anonymize_messages` or `_anonymize_posts` helper anywhere in the codebase.

**Severity**: HIGH — violates GDPR Article 17 "right to erasure" and CCPA "right to delete". Once a user successfully completes account deletion, their identity is supposed to be purged. Continued presence of `sender_id` / `author_id` may also be an IDOR (broken-access-control) vector for deleted-user data.

**Source ticket**: PLATFORM-018. **Status**: Open. **Effort**: M. **Owning area**: Privacy / Account Lifecycle.

**Related tickets**: GAP-0332 (subscriptions not cancelled), GAP-0339 (gdpr_service process_deletion stub), GAP-0340 (S3 files not deleted), GAP-0341 (Cognito user not disabled). All five gaps share the same root: `finalize_deletion` is a scaffold with a `deletion_summary` dict that was intended to be populated but was never wired.


## 2. Current-State Investigation (root cause)

`app/services/account_deletion.py:359` defines `finalize_deletion(user_sub, request_id)`. The relevant portion (lines 386–404):

```python
summary: Dict[str, Any] = {
    "wallet_refunded_cents": _refund_wallet(user_sub),
    "destructive": bool(S.account_deletion_destructive),
    "profile_deleted": False,
    "messages_anonymized": 0,   # <- never updated
    "posts_anonymized": 0,      # <- never updated
    "files_deleted": 0,
    "push_devices_deleted": 0,
    "subscriptions_cancelled": 0,
}

if S.account_deletion_destructive:
    try:
        from app.services.account import delete_user_data
        delete_user_data(user_sub)
        summary["profile_deleted"] = True
        summary["core_tables_deleted"] = True
    except Exception:
        logger.exception("destructive delete_user_data failed for %s", user_sub)
```

There are two important structural observations:

1. **`S.account_deletion_destructive` defaults to `False`** (`app/core/settings.py:1673`). In both dev and default-prod this flag is off. The entire `if S.account_deletion_destructive:` block — which calls `delete_user_data` — never runs unless an operator explicitly sets `ACCOUNT_DELETION_DESTRUCTIVE=1`. This means, in practice, no data is ever deleted at all, not just messages and posts.

2. **No `_anonymize_messages` / `_anonymize_posts` helpers exist anywhere**. A global search across `app/` finds zero definitions or calls. The `messages_anonymized` / `posts_anonymized` fields in the summary dict are placeholders that document intent but lack any implementation.

The messaging data layout is: `Messages` DynamoDB table with PK `conversation_id`, SK `message_id`, and attribute `sender_id` containing the user sub. The `app/routers/messaging.py` message out-path reads `sender_id` directly to build `MessageOut`. Post data is stored in the `app_single_table` DynamoDB table (via `newsfeed.py`'s `APP_TABLE` variable) with PK `POST#{post_id}` and SK `META`, plus a `user_id` attribute containing the author sub. The `user_id` field is set at line 3552 of `app/routers/newsfeed.py` (main post creation). It is surfaced as `author_id` in `_post_to_dict` at line 2156 via `post.get("user_id", "")`. (The function `_post_to_dict` is defined at line 2093, not 2697 as originally noted.)

**Runtime behaviour**: `process_due_deletions` (line 421) calls `finalize_deletion` for all `pending` requests whose `scheduled_for` timestamp has passed. For a user with `ACCOUNT_DELETION_DESTRUCTIVE=0` (the default), the entire cascade is: refund wallet, set status to `completed`. The profile, sessions, messages, posts, files, push devices, and subscriptions are untouched. The `deletion_summary` that gets written to DynamoDB shows all zeros.

**Dev vs prod parity**: The `account_deletion_destructive` flag is the only protection. There is no separate dev-mode stub — the logic that is missing is missing identically in both environments.


## 3. Impact / Exploit / Blast Radius

**Who is affected**: Every user who successfully completes account deletion while the platform has `ACCOUNT_DELETION_DESTRUCTIVE=0` (the default). All such accounts — likely the entire production user base since launch — retain their message identity in the `Messages` table indefinitely.

**Privacy / legal impact**:
- GDPR Art. 17 requires erasure of personal data upon a valid deletion request. `sender_id` is personal data (it is the user's Cognito sub, used as their unique identifier across all tables). Failing to anonymise it is a reportable breach in GDPR-regulated jurisdictions.
- CCPA § 1798.105 similarly requires deletion of personal information.
- If a regulator audits the deletion pipeline, the `deletion_summary` fields (`messages_anonymized: 0`, `posts_anonymized: 0`) are written to the `account_deletion_requests` table and are themselves evidence that the deletion never occurred as advertised.

**Concrete exploit**: A creator or admin who retains read access to a conversation after a participant deletes their account can continue to query `GET /messaging/conversations/{id}/messages` and receive `sender_id` values belonging to the deleted user. A secondary profile lookup (`GET /ui/profiles/{sender_id}`) may return a 404 but the sub itself can be correlated with other records (billing, tickets, calendar) that were also not deleted.

**Blast radius**:
- All conversations involving a deleted user (potentially thousands of messages across hundreds of conversations).
- All posts authored by a deleted user in the newsfeed (could be millions for a high-volume content creator).
- Subscription records (covered by GAP-0332), payment ledger rows, and calendar entries also retain the user sub.


## 4. Fix Design (code-level)

### 4a. `_anonymize_messages(user_sub)` helper

Messages are keyed by `conversation_id` (PK) + `message_id` (SK); there is no direct GSI on `sender_id`. Two viable approaches exist:

**Option A — GSI on sender_id** (cleanest long-term): Add a sparse GSI `BySenderCreatedAt` (`sender_id` → `created_at`) to the `Messages` table. Query by `sender_id = user_sub`, page over all results, `update_item` each row. Requires a table migration.

**Option B — Scan each conversation the user participated in** (no migration, works immediately): Query `Participants` table for all `conversation_id` values where `user_id = user_sub`, then query `Messages` for each conversation filtering `sender_id = user_sub`. This is O(conversations × pages) but tolerable for an async background deletion.

The fix uses Option B because it requires no table schema change and is consistent with the existing pattern of building the conversation list from the `Participants` table.

```python
# app/services/account_deletion.py

def _anonymize_messages(user_sub: str) -> int:
    """Overwrite sender_id on every message authored by user_sub."""
    from boto3.dynamodb.conditions import Key, Attr
    from app.core.aws import ddb as _ddb
    import os

    participants_table = _ddb.Table(os.environ.get("DDB_PARTICIPANTS", "Participants"))
    messages_table = _ddb.Table(os.environ.get("DDB_MESSAGES", "Messages"))

    # Step 1: collect conversation_ids the user participated in
    conv_ids: list[str] = []
    last_key = None
    while True:
        kwargs: dict = {
            "KeyConditionExpression": Key("user_id").eq(user_sub),
            "ProjectionExpression": "conversation_id",
        }
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key
        resp = participants_table.query(**kwargs)
        conv_ids.extend(item["conversation_id"] for item in resp.get("Items", []))
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break

    # Step 2: for each conversation, find and overwrite this user's messages
    anonymized = 0
    for conv_id in conv_ids:
        last_key = None
        while True:
            kwargs = {
                "KeyConditionExpression": Key("conversation_id").eq(conv_id),
                "FilterExpression": Attr("sender_id").eq(user_sub),
                "ProjectionExpression": "conversation_id, message_id",
            }
            if last_key:
                kwargs["ExclusiveStartKey"] = last_key
            resp = messages_table.query(**kwargs)
            for item in resp.get("Items", []):
                messages_table.update_item(
                    Key={
                        "conversation_id": item["conversation_id"],
                        "message_id": item["message_id"],
                    },
                    UpdateExpression=(
                        "SET sender_id = :anon, #txt = :anon_txt, "
                        "anonymized = :t, anonymized_at = :ts"
                    ),
                    ExpressionAttributeNames={"#txt": "text"},
                    ExpressionAttributeValues={
                        ":anon": "deleted_user",
                        ":anon_txt": "[This message was deleted]",
                        ":t": True,
                        ":ts": now_ts(),
                    },
                )
                anonymized += 1
            last_key = resp.get("LastEvaluatedKey")
            if not last_key:
                break
    return anonymized
```

### 4b. `_anonymize_posts(user_sub)` helper

Posts are stored in `app_single_table` with PK `POST#{post_id}` and SK `META`. There is no base-table PK keyed on `user_id`; posts by a given author are accessible via GSI2 (`GSI2PK = POST_AUTHOR#{user_id}`, `GSI2SK = {created_at}#POST#{post_id}`). The helper must use this GSI (not a direct PK query) to enumerate all posts by the deleted user:

```python
def _anonymize_posts(user_sub: str) -> int:
    """Overwrite author identity fields on every post authored by user_sub."""
    import os
    from boto3.dynamodb.conditions import Key
    from app.core.aws import ddb as _ddb

    posts_table = _ddb.Table(os.environ.get("APP_TABLE", "app_single_table"))
    anonymized = 0
    last_key = None
    while True:
        kwargs: dict = {
            "IndexName": "GSI2",
            "KeyConditionExpression": Key("GSI2PK").eq(f"POST_AUTHOR#{user_sub}"),
            "ProjectionExpression": "pk, sk, post_id",
        }
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key
        resp = posts_table.query(**kwargs)
        for item in resp.get("Items", []):
            posts_table.update_item(
                Key={"pk": item["pk"], "sk": item["sk"]},
                UpdateExpression=(
                    "SET display_name = :anon, avatar_url = :n, "
                    "anonymized = :t, anonymized_at = :ts"
                ),
                ExpressionAttributeValues={
                    ":anon": "Deleted User",
                    ":n": None,
                    ":t": True,
                    ":ts": now_ts(),
                },
            )
            anonymized += 1
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
    return anonymized
```

### 4c. Wire into `finalize_deletion`

The two helpers must run unconditionally — not gated behind `account_deletion_destructive`. Anonymisation is a privacy obligation that must apply even in "soft delete" mode:

```python
# Replace the summary initialisation block at line 386
summary: Dict[str, Any] = {
    "wallet_refunded_cents": _refund_wallet(user_sub),
    "destructive": bool(S.account_deletion_destructive),
    "profile_deleted": False,
    "messages_anonymized": _anonymize_messages(user_sub),   # now populated
    "posts_anonymized":   _anonymize_posts(user_sub),       # now populated
    "files_deleted": 0,
    "push_devices_deleted": 0,
    "subscriptions_cancelled": 0,
}
```

Running anonymisation before the `account_deletion_destructive` block ensures that even if the destructive profile wipe fails, the identity fields in messages and posts have already been scrubbed.

### 4d. Dev/Prod parity (SECOPS-007)

Both helpers use the `DDB_PARTICIPANTS` and `DDB_MESSAGES` / `DDB_POSTS` env-var-backed table names, which resolve to DynamoDB Local (port 8001) in dev and real DynamoDB in prod via the same `boto3` endpoint abstraction. No new AWS service dependency is introduced. The helpers are pure DynamoDB operations and work identically offline.

The existing `ACCOUNT_DELETION_DESTRUCTIVE` guard is unchanged; the new anonymisation step is orthogonal to it. A new `ACCOUNT_DELETION_ANONYMIZE_ENABLED` flag (default `True`) may be added for testing convenience, but must default to enabled so that CI/CD pipelines exercise the real code path.

### 4e. Alternatives considered

- **Hard-delete messages**: More complete, but breaks conversation integrity for other participants (gaps in thread, broken reply chains). Industry norm is to tombstone rather than hard-delete. Rejected.
- **GSI-based message lookup (Option A)**: Cleaner O(1) lookup by sender; deferred because it requires a table migration and a backfill job. Should be the long-term approach but is out of scope for this gap fix.
- **Lazy anonymisation at read time**: Check `account_state` on every message read; if the user is deleted, return `"Deleted User"`. Rejected: leaks the sub to the storage layer and is inconsistent with GDPR erasure (the data must be overwritten, not just masked at presentation).

### Playwright E2E test (optional, medium effort)

2. Directly fast-forward the `scheduled_for` timestamp in DynamoDB Local.

### Observability

- Log line `privacy.anonymize_messages user={sub} count={n}` at INFO level inside `_anonymize_messages`.
- Log line `privacy.anonymize_posts user={sub} count={n}` at INFO level inside `_anonymize_posts`.
- The existing `deletion_summary` DynamoDB field captures the counts durably per request.

### Rollback

The anonymisation writes are non-reversible — once `sender_id` is overwritten with `"deleted_user"`, the original value cannot be recovered without a backup. This is by design (it is the privacy obligation). Rollback means disabling the anonymisation step, not undoing past writes.

### Risks

- **Performance**: A user with tens of thousands of messages in many conversations will take proportionally longer. The finalization runs in the background scheduler (`deletion_scheduler.py`) and is async; this is acceptable. For very large accounts (>500k messages) consider breaking the operation into a separate paginated background job.
- **Race with message reads**: Between the `update_item` calls, other processes may read un-anonymised messages. This window is unavoidable without a distributed lock. For a deletion pipeline with no SLA on instant erasure, the window is acceptable.
- **`anonymized` flag in `MessageOut`**: If the frontend renders `sender_id` from the `MessageOut` model, a follow-up ticket should ensure that messages with `anonymized=True` are rendered as "Deleted User" without a profile lookup, so stale caches don't re-expose the sub.

**Effort**: M (Medium). Core anonymisation helpers: 2–3 hours. Unit tests: 2 hours. E2E spec: 3 hours. Total: ~1 day. Should be sequenced alongside GAP-0332 (subscriptions) and GAP-0340 (S3 files) as part of a single "deletion cascade completeness" sprint.
