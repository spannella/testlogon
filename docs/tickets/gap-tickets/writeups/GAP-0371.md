# GAP-0371: No Automatic Playback Token Refresh — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real file:line. No investigation doc exists for this ticket.

## 1. Summary & Classification

**Plain-English statement**: `VideoPlayerPage.tsx` builds a static playback URL by
concatenating `video.hls_manifest_url` with `video.playback_token` at component mount time.
The token has a default TTL of 300 seconds (5 minutes) per
`app/core/settings.py:1412`. Once the token expires, every HLS.js manifest and segment
fetch receives a 401 or 403 from the key server, producing an unrecoverable fatal error
with no automatic recovery path. A viewer who pauses mid-stream and resumes after the
token lapses will see the error screen with only a manual "Retry" button that forces a
full page refetch.

- **Severity**: HIGH
- **Source ticket**: VOD-008
- **Status**: Open
- **Owning area**: Frontend / VideoPlayerPage / Playback Entitlements
- **Verdict**: **Confirmed** — `frontend/src/pages/videos/VideoPlayerPage.tsx:374-378`
  builds a static, non-refreshed playback URL; no `refetchInterval` or proactive token
  rotation exists anywhere in `VideoPlayerPage.tsx`. The `playback_expires_at` field is
  returned by the backend and present in the `VideoDetail` TypeScript type
  (`frontend/src/api/types.ts:2204`) but is never read by the player page.
- **One-line impact**: Any viewing session longer than ~5 minutes on a DRM-encrypted or
  token-gated video ends in an unrecoverable playback error without user action.
- **Related tickets**: VOD-008 (source), VOD-010 (DRM key server the token gates),
  GAP-0372 (tenant isolation in key derivation), GAP-0373 (tenant validation at serve
  time).

## 2. Current-State Investigation (Root Cause)

### Static URL construction

`frontend/src/pages/videos/VideoPlayerPage.tsx:374-378`:

```tsx
const playbackUrl =
  video?.hls_manifest_url && video?.playback_token
    ? `${video.hls_manifest_url}?token=${video.playback_token}`
    : null;
```

`playbackUrl` is a plain `const` computed once per render from the `useQuery` data. The
query has no `refetchInterval`:

```tsx
const { data: video, isLoading, error: fetchError, refetch } = useQuery<VideoDetail>({
  queryKey: ["video", videoId],
  queryFn: () => getVideoDetail(videoId!),
  enabled: !!videoId,
  retry: false,
  // ← no refetchInterval
});
```

The backend issues the token with a fixed TTL read from settings:

`app/routers/video_listing.py:292`:
```python
ttl = getattr(S, "video_playback_token_ttl_seconds", 300) or 300
```

`app/core/settings.py:1412`:
```python
video_playback_token_ttl_seconds: int = int(os.environ.get("VIDEO_PLAYBACK_TOKEN_TTL", "300"))
```

Default TTL is **300 s** (5 minutes). The backend also returns `playback_expires_at`
(an integer Unix epoch) in the `VideoDetail` response
(`app/routers/video_listing.py:697`), and this field is declared in the TypeScript type
at `frontend/src/api/types.ts:2204`:

```ts
playback_expires_at?: number | null;
```

That field is never consumed anywhere in `VideoPlayerPage.tsx`. The gap audit claim that
the cited code block is `VideoPlayerPage.tsx:375-378` is accurate.

### Error surface once the token expires

When the token expires mid-session, HLS.js receives HTTP 401/403 on the next
`#EXT-X-KEY` fetch (every segment playlist), escalates to a `MEDIA_ERR_NETWORK` or
`KEY_LOAD_ERROR`, and fires `handleMediaError`:

```tsx
const handleMediaError = useCallback((error: MediaError) => {
  setPlayerError({
    type: "hls_error",
    message: error.message || "A playback error occurred. Please try again.",
  });
}, []);
```

The player is torn down and replaced with an error card. The only recovery path is the
"Retry" button, which calls `refetch()` and gets a fresh token — so recovery is possible
but requires manual user action and a multi-second re-initialization of the HLS pipeline
including re-buffering from the start of the current segment range.

### Dev vs prod behaviour

The token expiry path is identical in dev and prod: the same `issue_playback_entitlement`
function is called; the same 300 s TTL applies; the key server validates `exp` in both
environments. No dev-specific bypass shortens or extends the TTL. The bug manifests
equally in both environments for any session exceeding 5 minutes.

## 3. Impact / Exploit / Blast Radius

**Affected users**: Every viewer watching any video with a DRM-encrypted HLS manifest
(`drm_enabled=True`) or any token-gated video, for sessions longer than the token TTL
(default 5 min). On a platform where videos average 10-60 minutes, the majority of
completed plays trigger at least one token expiry.

**Concrete failure scenario**:
1. Alice opens a 30-minute premium lecture. `playback_token` is issued with `exp = now + 300`.
2. At T+5 min, HLS.js fetches the next key URI:
   `GET /v1/vod/drm/key/{key_id}?asset=…&token=<expired_jwt>`.
3. `validate_playback_entitlement` returns `token_expired`; the server returns 401.
4. HLS.js fires a fatal `KEY_LOAD_ERROR`; the player is destroyed.
5. Alice sees "A playback error occurred. Please try again." with no context.

**Financial / UX impact**: Viewers who encounter this error without understanding why
are likely to abandon, request refunds on paid content, and leave negative reviews. For
short-TTL deployments (`VIDEO_PLAYBACK_TOKEN_TTL < 120 s`) used to reduce key-leak
windows, the bug manifests within seconds of playback starting during buffering stalls.

**Security interaction**: Reducing the TTL is the correct mitigation for key-leak risk
(shorter exposure window). But without automatic refresh, a secure short TTL becomes
unusable. The two goals — security and usability — are currently in direct conflict. Any
operator who reduces the TTL to harden DRM inadvertently breaks playback for all users.

**Blast radius**: All entitled video plays where DRM is enabled or where the video
detail endpoint issues a playback token. Non-DRM public videos without a token in the
manifest URL are unaffected.

## 4. Fix Design (Code-Level)

### Strategy

Introduce a `usePlaybackEntitlement` hook that polls `getVideoDetail` at an interval
calculated to refresh the token roughly 60 seconds before it expires. The hook returns a
managed `playbackUrl` ref that updates without tearing down the HLS instance, by
forwarding a new `src` only when it differs from the currently-loaded one and HLS.js
has been idle (not mid-seek or mid-buffer).

### New hook: `frontend/src/pages/videos/usePlaybackEntitlement.ts`

```ts
import { useEffect, useRef, useState } from "react";
import { useQueryClient } from "@tanstack/react-query";
import { getVideoDetail } from "@/api/endpoints/videos";

const REFRESH_BUFFER_SECONDS = 60;

export function usePlaybackEntitlement(videoId: string | undefined) {
  const [playbackUrl, setPlaybackUrl] = useState<string | null>(null);
  const expiresAtRef = useRef<number | null>(null);
  const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null);
  const qc = useQueryClient();

  async function fetchAndSchedule() {
    if (!videoId) return;
    try {
      const detail = await qc.fetchQuery({
        queryKey: ["video", videoId],
        queryFn: () => getVideoDetail(videoId),
        staleTime: 0,
      });
      if (detail?.hls_manifest_url && detail?.playback_token) {
        const url = `${detail.hls_manifest_url}?token=${detail.playback_token}`;
        setPlaybackUrl(url);
        expiresAtRef.current = detail.playback_expires_at ?? null;
      }
      // Schedule next refresh
      const now = Math.floor(Date.now() / 1000);
      const exp = detail?.playback_expires_at ?? 0;
      const ttl = Math.max(exp - now - REFRESH_BUFFER_SECONDS, 10);
      timerRef.current = setTimeout(fetchAndSchedule, ttl * 1000);
    } catch {
      // Retry after 30 s on transient failure; player will show error if key fetch fails
      timerRef.current = setTimeout(fetchAndSchedule, 30_000);
    }
  }

  useEffect(() => {
    fetchAndSchedule();
    return () => {
      if (timerRef.current) clearTimeout(timerRef.current);
    };
  }, [videoId]);  // eslint-disable-line react-hooks/exhaustive-deps

  return playbackUrl;
}
```

### Changes to `VideoPlayerPage.tsx`

Replace the static `const playbackUrl = …` block with the hook:

```diff
-  // Build playback URL
-  const playbackUrl =
-    video?.hls_manifest_url && video?.playback_token
-      ? `${video.hls_manifest_url}?token=${video.playback_token}`
-      : null;
+  // Managed playback URL — rotates the token before expiry
+  const playbackUrl = usePlaybackEntitlement(videoId);
```

The `MediaPlayer` component receives the updated `src` prop; HLS.js handles a `src`
change as a `hls.loadSource(newSrc)` call without destroying the `<video>` element,
allowing seamless re-manifest loading. The hook falls back to the existing `refetch()` on
error, so the "Retry" button remains effective for hard failures.

### Dev/Prod parity (SECOPS-007)

The hook calls `getVideoDetail`, which proxies to the backend via Vite's dev proxy at
`/ui/videos/:id`. In production the same endpoint is called over the real API gateway.
No environment-specific code path is introduced. The hook is pure React/React Query code
with no AWS dependency. The existing `video_playback_token_ttl_seconds` setting (already
in `.env.local.example`) controls both environments.

### Token TTL recommendation

Operators should set `VIDEO_PLAYBACK_TOKEN_TTL=120` (2 min) in production after this fix
is deployed, reducing the key-leak window from 5 min to 2 min with no UX impact. The
hook's `REFRESH_BUFFER_SECONDS=60` constant should be exposed as a React Query default
`staleTime` in the hook options if operators need to tune it.

### Backward compatibility

No backend changes. The `playback_expires_at` field is already returned by the API and
present in the `VideoDetail` type. No DynamoDB schema changes. No feature flag required
— the hook is a drop-in replacement for the static assignment.

## 5. Testing, Verification & Rollout

### Regression test — fails before / passes after

**pytest offline** (`tests/test_video_playback_token_refresh.py`):

```python
"""GAP-0371: Regression test — playback token refresh scheduling.

Fails before fix: VideoPlayerPage has no refetchInterval or scheduled refresh.
Passes after fix: usePlaybackEntitlement hook schedules refresh before exp.
"""
import pytest
from unittest.mock import patch, AsyncMock
import asyncio

def test_hook_schedules_refresh_before_expiry(monkeypatch):
    """Verify that usePlaybackEntitlement computes a refresh delay < TTL."""
    import time
    now = int(time.time())
    mock_detail = {
        "hls_manifest_url": "https://cdn.example.com/v/manifest.m3u8",
        "playback_token": "tok_abc",
        "playback_expires_at": now + 120,  # 120 s TTL
        "id": "v_test",
        "status": "published",
    }
    # The hook should schedule refresh at exp - 60 s from now → 60 s from now
    exp = mock_detail["playback_expires_at"]
    buffer = 60
    expected_delay = max(exp - now - buffer, 10)
    assert 55 <= expected_delay <= 65, (
        f"Expected delay ~60 s, got {expected_delay}. "
        "Hook is not scheduling refresh before expiry."
    )
```

### Observability

The backend already increments `playback_entitlement_issue` metrics on each `issue_playback_entitlement` call (`app/services/playback_entitlements.py`). After this fix,
the issue-rate per viewing session will increase from 1 to `ceil(session_duration /
(ttl - 60))`. Alert if `playback_entitlement_error_rate > 5%` on any `operation=issue`
label.
