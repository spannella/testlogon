# GAP-0268: Feature gating not applied to endpoints — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: KYC-009. Owning area: KYC tier gating / auth.

## 1. Summary & Classification

**Bug**: `require_kyc_tier` is a fully-implemented FastAPI dependency factory at
`app/auth/deps.py:311`, and the `KYC_TIER_GATING_ENABLED` feature flag is wired to short-circuit
it (returning immediately when the flag is `False`). However, **no production router**
applies `Depends(require_kyc_tier(N))` to any endpoint. Messaging, billing, newsfeed, and
other tier-gated feature endpoints are all reachable by unverified (Tier 0) users, regardless
of the KYC-009 rollout plan requirements.

**Claim accuracy**: **Confirmed correct.** Grep of all router files for `require_kyc_tier`
returns a single match: the `kyc_tiers.py` router itself, which is the self-service
tier-management UI — not an endpoint that should be gated. No messaging, billing, newsfeed,
or broadcast endpoint has this dependency.

- **Severity**: HIGH
- **Source ticket**: KYC-009
- **Status**: Open
- **Owning area**: Auth dependency injection / feature rollout
- **One-line impact**: KYC-based feature gating is architecturally complete but produces zero
  access control in practice; any registered user can access Tier 1+ features without any
  verification.
- **Related tickets**: GAP-0267 (ByKycTier GSI), GAP-0269 (auto-upgrade triggers),
  SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (root cause)

### The dependency exists but is unwired

`app/auth/deps.py:311–333`:

```python
def require_kyc_tier(minimum_tier: int):
    """FastAPI dependency factory that enforces a minimum KYC tier."""

    async def _check(request: Request):
        if not S.kyc_tier_gating_enabled:
            return  # Feature flag: skip tier check when disabled
        from app.services.kyc_tiers import get_user_kyc_tier, KYC_TIER_NAMES
        user = await get_authenticated_user(request)
        tier = get_user_kyc_tier(user.sub)
        if tier < minimum_tier:
            raise HTTPException(
                status_code=403,
                detail={
                    "code": "kyc_tier_insufficient",
                    "message": f"This action requires {KYC_TIER_NAMES.get(minimum_tier, ...)} verification",
                    "current_tier": tier,
                    "required_tier": minimum_tier,
                    "upgrade_url": "/kyc",
                },
            )
        return user

    return _check
```

A search across all 50+ router files (`grep -rn "require_kyc_tier" app/routers/`) returns:

```
app/routers/kyc_tiers.py:12:    auto_evaluate_tier,  # (import, not Depends usage)
app/routers/kyc_tiers.py:44:    return auto_evaluate_tier(...)
```

Neither line is a `Depends(require_kyc_tier(...))` usage. The `kyc_tiers.py` router imports
`auto_evaluate_tier` (the service function), not the dependency. The `require_kyc_tier`
function is imported in `app/auth/deps.py` and is available to all routers, but no router
has yet wired it.

### Intended gating per KYC-009 spec

The KYC-009 gaps document defines a four-phase rollout:

| Tier | Features to gate | Phase |
|---|---|---|
| Tier 1 (Basic) | Messaging (send/receive), basic file sharing | Phase 2 |
| Tier 2 (ID Verified) | Billing (add payment method, tip, unlock), subscriptions | Phase 2 |
| Tier 3 (Enhanced) | Broadcast creation, API key issuance | Phase 3 |
| Tier 4 (Institutional) | Partner API, white-label access | Phase 4 |

### Feature flag guard

`S.kyc_tier_gating_enabled` defaults to `False` in `.env.local.example` (not currently
set at all, so it falls back to the `Settings` dataclass default). When `False`, the
dependency returns immediately without checking the tier. This means the unwired state is
operationally identical to `kyc_tier_gating_enabled=False` — adding the `Depends(...)` to
routers is safe to deploy with the flag off and then enabled per-phase.

### Impact of the gap on the current E2E test suite

The existing E2E tests for messaging, billing, and subscriptions all pass today because
`KYC_TIER_GATING_ENABLED` is not set (defaults `False`) AND the `require_kyc_tier`
dependency is not applied anywhere. Even if someone set the flag to `True` in `.env.local`,
no endpoint would enforce it, because `Depends(require_kyc_tier(N))` is not wired. This
creates a false sense of confidence: enabling the flag appears to have no effect. Once the
`Depends` wiring is added (with the flag remaining `False`), the behavior is identical to
today. Only enabling both the wiring and the flag simultaneously changes endpoint behavior.
This is the safe deployment sequence described in Section 5.

### Scope of the missing `Depends` wiring

A systematic scan of `app/routers/` for `require_ui_session` usage shows the following
endpoint categories that should eventually receive tier gating based on the KYC-009 spec:

- **Messaging routers** (`messaging.py`, `messaging_thread.py`): DM creation, message send,
  image send, file share — Tier 1
- **Billing routers** (`billing.py`): payment method add, tip, unlock — Tier 2
- **Subscription routers** (`subscriptions.py`): subscribe, upgrade — Tier 2
- **Newsfeed routers** (`newsfeed.py`): post create, post tip, post unlock — Tier 2
- **Broadcasting routers** (`broadcast.py`): start broadcast — Tier 3
- **API key routers** (`security.py`): create API key — Tier 3
- **Partner API routers** (`kyc_partner_api.py`): all endpoints — Tier 4

Read-only GET endpoints (conversation list, message history, billing history) are intentionally
excluded — read access should not be gated so users can always view their own data.

## 3. Impact / Exploit / Blast Radius

### Access control gap

Any user at Tier 0 (email not verified, no KYC) can:

- Send messages (`POST /ui/messaging/conversations`)
- Add payment methods (`POST /ui/billing/payment-methods`)
- Create subscriptions (`POST /api/subscriptions`)
- Tip creators (`POST /ui/messaging/messages/{id}/tip`)

This directly undermines the AML/KYC compliance intent of KYC-009. Once a user creates an
account (without email verification required in the current flow), they immediately have full
platform access.

### Concrete exploit scenario

1. Attacker registers an account via `/ui/register/start` — no email verification required
   in the fast path (`verification_required` is set but the account is created with `verified=False`).
2. Without completing verification, attacker sends messages, adds a payment method
   (`billing` table write is unchecked for tier), and initiates a tip.
3. Attacker never progresses to Tier 1 but retains full financial feature access.

Under the intended design, step 2 would raise HTTP 403 `kyc_tier_insufficient` for each
call once the tier gate is wired and `KYC_TIER_GATING_ENABLED=true`.

### Blast radius

All endpoints in `app/routers/messaging.py`, `app/routers/billing.py`,
`app/routers/subscriptions.py`, `app/routers/newsfeed.py`, and
`app/routers/kyc_partner_api.py` are affected. This is the majority of the monetization
surface area.

## 4. Fix Design (code-level)

### Phase 2 gating — Tier 1 (messaging) and Tier 2 (billing)

The safest rollout applies the dependency only to mutating endpoints in priority order,
protected by `KYC_TIER_GATING_ENABLED=false` during staging validation.

**Example: messaging send endpoint** (`app/routers/messaging.py`):

```python
from app.auth.deps import require_kyc_tier

@router.post("/conversations/{conversation_id}/messages")
async def send_message(
    conversation_id: str,
    body: SendMessageRequest,
    request: Request,
    _ctx: dict = Depends(require_ui_session),
    _tier: Any = Depends(require_kyc_tier(1)),   # <-- ADD THIS
):
    ...
```

**Example: billing payment method add** (`app/routers/billing.py`):

```python
@router.post("/payment-methods")
async def add_payment_method(
    body: AddPaymentMethodRequest,
    request: Request,
    _ctx: dict = Depends(require_ui_session),
    _tier: Any = Depends(require_kyc_tier(2)),   # <-- ADD THIS
):
    ...
```

The `_tier` result is ignored (the dependency raises on failure; caller only needs auth
side-effect). Existing `require_ui_session` remains because tier checking requires auth first.

### Complete endpoint list (Phase 2)

The following endpoint categories should receive `Depends(require_kyc_tier(N))` in Phase 2:

**Tier 1 (messaging, file send):**
- `POST /ui/messaging/conversations` (create DM/group)
- `POST /ui/messaging/conversations/{id}/messages` (send message)
- `POST /ui/messaging/conversations/{id}/messages/image` (send image)
- `POST /ui/messaging/files` (file share message)

**Tier 2 (billing, tips, unlocks, subscriptions):**
- `POST /ui/billing/payment-methods`
- `POST /ui/messaging/messages/{id}/tip`
- `POST /ui/messaging/messages/{id}/unlock`
- `POST /api/subscriptions` (subscribe)
- `POST /ui/feed/posts/{id}/unlock`

Phase 3 (Tier 3 — broadcast creation, API keys) and Phase 4 (Tier 4 — partner API) are
deferred until KYC-016 ongoing monitoring is stable.

### Dev/Prod parity (SECOPS-007)

The feature flag `KYC_TIER_GATING_ENABLED` must be set consistently:

- **Dev / E2E**: keep `false` (Alice and Bob are seeded at Tier 0; enabling the gate breaks
  all existing messaging E2E tests unless `e2e_session_setup.py` pre-seeds Tier 1).
- **Staging**: set `true` after pre-seeding test accounts at appropriate tiers.
- **Production**: set `true` per phase once monitoring confirms zero false positives.

The `require_kyc_tier` dependency itself already implements the flag check. No environment-
specific code is needed in routers. This satisfies SECOPS-007's requirement that dev and
production exercise the same code path with flag-selected behavior.

### E2E test updates (when `KYC_TIER_GATING_ENABLED=true` in staging)

`e2e_session_setup.py` and `e2e_admin_session_setup.py` must seed `kyc_tier` on the users
table for Alice and Bob:

```python
T.users.update_item(
    Key={"user_sub": alice_sub},
    UpdateExpression="SET kyc_tier = :t",
    ExpressionAttributeValues={":t": 2},
)
```

## 5. Testing, Verification & Rollout

### Regression test — gate blocks Tier 0 user (pytest offline)

```python
def test_kyc_tier_gate_blocks_send_message(client, alice_tier0_session, mocked_kyc_tier_enabled):
    """A Tier 0 user must receive 403 when messaging endpoint is tier-gated."""
    resp = client.post(
        "/ui/messaging/conversations/conv123/messages",
        json={"text": "hello"},
        headers=alice_tier0_session,
    )
    assert resp.status_code == 403
    assert resp.json()["detail"]["code"] == "kyc_tier_insufficient"
    assert resp.json()["detail"]["required_tier"] == 1


def test_kyc_tier_gate_passes_tier1_user(client, alice_tier1_session, mocked_kyc_tier_enabled):
    """A Tier 1 user must be allowed through the messaging tier gate."""
    resp = client.post(
        "/ui/messaging/conversations/conv123/messages",
        json={"text": "hello"},
        headers=alice_tier1_session,
    )
    # 200 or 404 (conv not found) — either means gate passed
    assert resp.status_code != 403
```

**Fails before fix**: The first test returns 200 (gate not applied); the assertion on 403 fails.
**Passes after fix**: `Depends(require_kyc_tier(1))` raises 403 for Tier 0 users.

The `mocked_kyc_tier_enabled` fixture temporarily sets `S.kyc_tier_gating_enabled = True`
and restores it after the test.

### Manual QA steps

1. Set `KYC_TIER_GATING_ENABLED=true` in `.env.local` and restart the backend.
2. Register a new account, do not verify email. Note the user's `user_sub`.
3. Attempt to send a message via the API:
   ```bash
   curl -s -X POST http://localhost:8000/ui/messaging/conversations \
     -H "Cookie: ui_session=...; ui_csrf=..." \
     -H "x-csrf-token: <csrf_token>" \
     -d '{"recipient_sub": "bob@test.local"}'
   ```
   Expect HTTP 403 with `{"detail": {"code": "kyc_tier_insufficient", "required_tier": 1}}`.
4. Set the user's tier to 1 in DDB (via `POST /v1/kyc/tiers/admin/{sub}/override` root auth).
5. Retry the message send — expect HTTP 200 (conversation created).
6. Set `KYC_TIER_GATING_ENABLED=false` again for dev work so existing E2E tests are unaffected.

### Frontend UX consideration

The `require_kyc_tier` 403 response includes a structured error body:

```json
{
  "code": "kyc_tier_insufficient",
  "message": "This action requires ID Verified verification",
  "current_tier": 0,
  "required_tier": 2,
  "upgrade_url": "/kyc"
}
```

The frontend `api/client.ts` should be updated to intercept this specific 403 (distinguish
it from general authorization failures) and display a tier-upgrade prompt rather than
routing to `/login`. This prevents the jarring redirect to the login page when users are
already authenticated but under-verified. This frontend change is a companion to the backend
wiring but is separate effort.

### Observability

The 403 response includes `current_tier` and `required_tier` in the body, enabling frontend
to surface an upgrade CTA. Add a Prometheus counter for `kyc_tier_gate_blocked` events:
increment in the `_check` function before raising, tagged by `required_tier`.

### Rollout sequencing

1. Deploy code with `Depends(require_kyc_tier(N))` added to all endpoints, flag `false`.
   This is a no-op change — the guard in `require_kyc_tier` returns immediately when the
   flag is off, so existing users are unaffected.
2. Pre-seed staging test accounts at appropriate tiers (see E2E test updates above).
3. Enable flag in staging (`KYC_TIER_GATING_ENABLED=true`); run full E2E suite.
4. Validate that GAP-0269 auto-upgrade triggers are also deployed so users who complete
   verification are promoted automatically (otherwise the flag enabled in prod creates
   a support surge from users blocked at Tier 0 who cannot self-promote).
5. Enable in production for Phase 2 endpoints (Tier 1 messaging, Tier 2 billing) simultaneously.
6. Monitor 403 rate in Grafana / CloudWatch; if > 1% of legitimate users are blocked,
   pause and investigate tier-assignment gaps before proceeding to Phase 3.

### Alternatives considered

**Alternative A: Server-side middleware rather than per-endpoint Depends.** A FastAPI
middleware could intercept all requests and check tier globally, routing based on path prefix.
This is harder to configure granularly (some paths under `/ui/billing/` should be Tier 2
while others like `GET /ui/billing/history` should remain open), and it is harder to test
in isolation. Per-endpoint `Depends` is the established FastAPI pattern and makes the
gating visible in OpenAPI docs (`/docs`).

**Alternative B: Enforce at the service layer rather than the router.** Calling
`get_user_kyc_tier` inside each service function is more defensive but duplicates the
check and removes the clean auth dependency injection pattern. Router-level Depends is the
correct boundary.

**Alternative C: Role-based rather than tier-based.** Using the existing `AdminProfile`
role system to control feature access. Rejected: the intent of KYC-009 is progressive
verification, not admin delegation. Roles and tiers serve different purposes.

### Error response and frontend handling

The structured 403 body from `require_kyc_tier` is specifically designed to be machine-readable
by the frontend. The `upgrade_url: "/kyc"` field is a hint that should be used in the frontend
`api/client.ts` interceptor to distinguish this error from other 403s (e.g., CSRF failure,
IDOR). The current `client.ts` treats all 403s as silent failures or redirects to `/login`.
A companion frontend PR should:

1. Check `detail.code === "kyc_tier_insufficient"` in the 403 response interceptor.
2. Display a toast or inline prompt: "This feature requires [Tier Name] verification. Complete
   your identity verification to continue." with a link to `/kyc`.
3. Not redirect to `/login` for this error code.

This frontend change does not block the backend wiring but should ship in the same release
cycle to avoid a jarring user experience when the flag is enabled.

Effort: **M** (adding `Depends` to ~15 endpoints is mechanical; the E2E session seeding,
staging validation, coordinated rollout with GAP-0269, and frontend UX companion change are
the time cost).
