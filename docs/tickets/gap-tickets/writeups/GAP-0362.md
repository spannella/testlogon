# GAP-0362: execute_split uses Python `assert` for financial integrity invariant — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against real code; cites `file:line` throughout.

## 1. Summary & Classification

**Bug**: The `execute_split` function in `app/services/syndicate_revenue_split.py` uses two bare Python `assert` statements to validate that revenue distribution totals are self-consistent before writing to DynamoDB. Python's `-O` (optimized) and `-OO` flags — used in many production container build pipelines to reduce bytecode size — strip all `assert` statements at compile time. When assertions are stripped, a split calculation that produces an incorrect total silently passes both checks, credits members with wrong amounts, and leaves the platform-fee accounting inconsistent.

**Severity**: HIGH
**Source ticket**: SYND-003 (second-pass as-built review)
**Status**: Open
**Owning area**: Backend / syndicate revenue split service
**Effort**: S
**Related tickets**: GAP-0363 (wallet delta never applied), GAP-0008 (commission replay)

**Claim verification**: CONFIRMED. Lines 222–225 of `app/services/syndicate_revenue_split.py` contain:

```python
assert distributed == net_amount_cents, (
    f"split distribution mismatch: {distributed} != {net_amount_cents}"
)
assert platform_fee_cents + distributed == gross_amount_cents
```

Both are bare `assert` statements with no surrounding `if` guard and will be silently removed under `-O`.

**One-line impact**: Under production Python optimization flags, a buggy split calculation can silently credit members the wrong amount, leaving the platform-fee accounting permanently inconsistent with actual payments received.

## 2. Current-State Investigation (root cause)

### The two broken assertions

```
app/services/syndicate_revenue_split.py:220-225
```

```python
# Financial integrity invariant.
distributed = sum(d["amount_cents"] for d in distributions)
assert distributed == net_amount_cents, (
    f"split distribution mismatch: {distributed} != {net_amount_cents}"
)
assert platform_fee_cents + distributed == gross_amount_cents
```

These appear immediately before the per-member ledger-write loop and the final split-record write (lines 231–282). The intent is to guard against calculation bugs in `_calculate_equal`, `_calculate_weighted`, or `_calculate_performance` that would produce distributions whose sum does not equal `net_amount_cents`.

### Why `assert` is wrong here

Python's optimizer (invoked by `python -O` or by setting `PYTHONOPTIMIZE=1` or `PYTHONOPTIMIZE=2` in the environment) removes all `assert` statements from the bytecode before execution. This is documented behavior since Python 2. The Python 3.12 documentation states:

> "If this option is present, the __debug__ built-in variable is set to False. Augmented assignment statements containing assert are omitted."

Many Docker images used for production Python services pass `-O` as a standard optimization. The CPython `-OO` flag additionally strips docstrings. In either case, both asserts on lines 222–225 become no-ops at runtime.

### When would the invariant be violated?

The `_calculate_equal`, `_calculate_weighted`, and `_calculate_performance` helpers all use integer arithmetic with last-member remainder absorption to prevent drift. Under correct implementations the assertions always hold. However, future modifications to these helpers — or edge cases with very small gross amounts, unusual basis point configurations, or floating-point contamination if a future developer inadvertently introduces a float — could cause a mismatch. Without the guards, such a bug would:

1. Write incorrect per-member ledger credit entries.
2. Write an incorrect split execution record (with wrong `distributions` and `net_amount_cents`).
3. Leave no trace in error logs that anything went wrong.
4. Return a success response to the caller.

### The performance-mode calculation is the highest-risk path

The `_calculate_performance` helper at `app/services/syndicate_revenue_split.py:382-412` computes each member's share proportional to their `score / total_score`. The "last member absorbs remainder" pattern is used here too, but a subtle implementation error — such as iterating in an unstable order, or getting the `total_score` wrong due to an off-by-one in `_get_performance_scores` — could produce a mismatch that the current assertions would catch in dev (where `-O` is not used) but silently skip in prod (where it might be). The equal and weighted modes have simpler arithmetic and lower risk, but performance mode involves quotient computation across N members and is the most likely future regression site.

### Historical context: assert is forbidden in financial code by multiple style guides

The Google Python Style Guide, PEP 8 commentary, and numerous financial systems engineering standards explicitly prohibit `assert` for runtime invariant enforcement (as opposed to test assertions). The pattern `assert cond, msg` is appropriate only in test code (`tests/` directory) and developer-facing debug tooling, not in production service code where correctness must be guaranteed regardless of interpreter flags. A project-level lint rule (`no-assert-in-services`) should be added to `pyproject.toml` or `.flake8` as a follow-up to prevent this class of bug from reoccurring.

### Dev vs prod discrepancy

In the local development stack (`scripts/run_local_mock_backend.sh`) uvicorn is launched without `-O`, so the assertions execute and would catch a bug in testing. In production, if the container image is built with `python -O`, the assertions are stripped, the gap only exists in prod. This is a textbook dev/prod parity failure (SECOPS-007).

## 3. Impact / Exploit / Blast Radius

### Financial impact

`execute_split` is the sole entry point for distributing bundle-subscription and tip revenue across syndicate members. It is called by:

- The subscription payment flow whenever a syndicate bundle invoice is settled.
- E2E tests and manual admin triggers that force a split.

If a distribution mismatch of even 1 cent occurs per split, and the assertions are disabled, the error accumulates silently across every split event. On a platform with thousands of active syndicates and daily revenue events, this could produce material financial discrepancies between the platform's ledger totals and actual payments.

### Who is affected

- **Syndicate members** receive ledger credits for incorrect amounts. Their earnings dashboard shows wrong figures.
- **Platform** records inconsistent platform-fee accounting: `platform_fee_cents + sum(distributions) != gross_amount_cents` would not be caught, leading to balance sheet errors.
- **Compliance / audit**: Any financial reconciliation that assumes split records are internally consistent will produce incorrect results.

### Severity escalation

Because the split record is written to DynamoDB as an immutable record (there is no update path for a written split), correcting a silently-wrong split requires manual data surgery — there is no automated compensating transaction.

### Exploit

This is not an externally exploitable security vulnerability in the traditional sense — an attacker cannot force the invariant to fail without modifying the service code. The risk is an internal correctness bug that could be introduced through future code changes and would go undetected in production due to the assert stripping. The HIGH severity is justified by the financial integrity consequence.

## 4. Fix Design (code-level)

### Replace both `assert` statements with unconditional `if/raise` guards

```python
# app/services/syndicate_revenue_split.py:220-225 — AFTER FIX

# Financial integrity invariant — always enforced, even with -O.
distributed = sum(d["amount_cents"] for d in distributions)
if distributed != net_amount_cents:
    raise RuntimeError(
        f"GAP-0362: split distribution mismatch for syndicate {syndicate_id}: "
        f"distributed={distributed} != net_amount_cents={net_amount_cents} "
        f"(gross={gross_amount_cents}, fee={platform_fee_cents})"
    )
if platform_fee_cents + distributed != gross_amount_cents:
    raise RuntimeError(
        f"GAP-0362: split fee invariant violated for syndicate {syndicate_id}: "
        f"platform_fee={platform_fee_cents} + distributed={distributed} "
        f"!= gross={gross_amount_cents}"
    )
```

`RuntimeError` is used (rather than `HTTPException(500)`) because this is a programming invariant that should never fire under any valid inputs. A `RuntimeError` will propagate to FastAPI's default exception handler, which returns HTTP 500 with a generic error body. This is correct behavior — the caller should not receive a 2xx response when financial data integrity has failed.

If the preference is to return a structured JSON error body, `HTTPException(status_code=500, detail="Internal split integrity error")` is an acceptable alternative. Either choice is unconditionally executed regardless of Python optimization flags.

### Why not keep `assert` and add a CI lint rule?

One could add a CI flake8/pylint rule that forbids `assert` in financial services. However, this only prevents regressions if CI is always run and the lint rule covers all edge cases. The simpler and more robust fix is to replace the assertions with code that works correctly at runtime under all build configurations.

### Dev/Prod parity (SECOPS-007)

The `execute_split` function has no mock path, no `S.dev_mode` branch, and no feature flag. It runs identically in dev (DynamoDB Local) and prod (AWS DynamoDB). The fix is therefore fully parity-consistent — no additional environment-specific logic is needed. The only difference between environments is the Python optimization flag behavior, which this fix eliminates.

### Backward compatibility

No API contract changes. No DynamoDB schema changes. The function signature, return shape, and normal success path are identical. The only behavioral difference is that a previously-silent bug now raises a 500 error and writes nothing to DynamoDB, which is the correct behavior.

### Logging enhancement (recommended alongside the fix)

Add a structured log entry when the invariant raises, to ensure the event appears in observability dashboards:

```python
if distributed != net_amount_cents:
    logger.error(
        "syndicate_split_invariant_violated",
        extra={
            "syndicate_id": syndicate_id,
            "distributed": distributed,
            "net_amount_cents": net_amount_cents,
            "gross_amount_cents": gross_amount_cents,
        },
    )
    raise RuntimeError(...)
```

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline — fails before fix, passes after)

The test must verify that an invariant violation raises even under `-O`. In practice, since the test runner normally does not use `-O`, the most effective test is a unit test that directly patches the calculation helper to return a wrong total, then asserts that `execute_split` raises rather than silently succeeds:

```python
# tests/test_syndicate_revenue_split.py

import pytest
from unittest.mock import patch, MagicMock
from app.services import syndicate_revenue_split as svc

# Minimal stubs
SYNDICATE_ID = "test-synd-split"


def _fake_meta():
    return {"admin_user_id": "admin", "status": "active", "name": "Test"}


def _fake_members():
    return [{"user_id": "alice", "display_name": "Alice"}, {"user_id": "bob", "display_name": "Bob"}]


def _bad_equal_calc(net_amount_cents, member_ids):
    """Simulates a buggy equal-split that returns 1 cent less than the total."""
    half = net_amount_cents // 2
    return [
        {"user_id": "alice", "amount_cents": half, "percentage_bps": 5000},
        {"user_id": "bob",   "amount_cents": half - 1, "percentage_bps": 5000},  # off by 1
    ]


def test_execute_split_raises_on_distribution_mismatch():
    """Invariant check must raise RuntimeError (not silently pass) when totals disagree.

    This test FAILS before the fix (assert is a no-op or passes silently).
    This test PASSES after the fix (if/raise guard always executes).
    """
    with (
        patch.object(svc.syndicate_svc, "_get_meta", return_value=_fake_meta()),
        patch.object(svc, "get_split_config", return_value={"mode": "equal", "platform_fee_bps": 1500}),
        patch.object(svc.syndicate_svc, "list_members", return_value=_fake_members()),
        patch.object(svc, "_calculate_equal", side_effect=_bad_equal_calc),
        patch.object(svc.T, "billing", MagicMock()),
        patch.object(svc.T, "syndicate_revenue_split", MagicMock()),
    ):
        with pytest.raises(RuntimeError, match="split distribution mismatch"):
            svc.execute_split(
                syndicate_id=SYNDICATE_ID,
                gross_amount_cents=1000,
                source_type="subscription",
            )


def test_execute_split_no_ddb_write_on_mismatch():
    """DynamoDB put_item must NOT be called when the invariant fires."""
    mock_billing = MagicMock()
    mock_split_table = MagicMock()

    with (
        patch.object(svc.syndicate_svc, "_get_meta", return_value=_fake_meta()),
        patch.object(svc, "get_split_config", return_value={"mode": "equal", "platform_fee_bps": 1500}),
        patch.object(svc.syndicate_svc, "list_members", return_value=_fake_members()),
        patch.object(svc, "_calculate_equal", side_effect=_bad_equal_calc),
        patch.object(svc.T, "billing", mock_billing),
        patch.object(svc.T, "syndicate_revenue_split", mock_split_table),
    ):
        try:
            svc.execute_split(
                syndicate_id=SYNDICATE_ID,
                gross_amount_cents=1000,
                source_type="subscription",
            )
        except RuntimeError:
            pass

        # No ledger or split records must have been written
        mock_billing.put_item.assert_not_called()
        mock_split_table.put_item.assert_not_called()
```

The second test (`test_execute_split_no_ddb_write_on_mismatch`) also fails before the fix if the assertions are disabled, because `put_item` is called for each member before the assertions would have fired in the original code structure. Note: looking at the code, the assertions at lines 222–225 run BEFORE the per-member loop at line 231, so no writes occur before the invariant check. This means the second test actually passes even before the fix if assertions are enabled — its primary value is confirming no partial write occurs after the fix.

### Manual QA steps

1. Run `python -O -c "from app.services import syndicate_revenue_split as s; print('ok')"` to confirm imports work under `-O`.
2. Temporarily add a `return` after `distributions` is populated (to simulate a bad calc) and verify that `execute_split` now raises 500 rather than silently writing wrong records.
3. Remove the temporary change and confirm normal splits still produce correct 2xx responses.

### Metrics / observability

- Wire the `logger.error("syndicate_split_invariant_violated", ...)` call to a CloudWatch alarm (`ERROR` log line count > 0 in the split service). Paging on this alarm ensures any future regression is caught immediately.

### Rollback

Remove the two `if/raise` blocks and restore the original `assert` lines. This is a 4-line change with zero infrastructure dependency; rollback is instant.

### Risk

Very low. Under all valid calculation paths the invariant holds — the helpers are deterministic and integer-only. The `RuntimeError` path is a dead code path under normal operation. The only risk is a false alarm if the calculation helpers have a latent bug, which would correctly surface as a 500 error rather than silent data corruption.

### Effort

**S** — approximately 20 minutes of code change + 1 hour of test authoring.

### Sequencing

Deploy after GAP-0363 is fixed (wallet delta) so both financial correctness gaps are addressed in the same release. No schema migration needed; can be deployed with a simple service restart.
