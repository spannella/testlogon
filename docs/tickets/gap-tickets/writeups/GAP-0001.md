# GAP-0001: No Daily `spent_today_cents` Reset Task — Remediation Write-up

> Source ticket: ADS-004 · Severity: CRIT · Effort: M · Status: Open

## 1. Summary & Classification

**Bug statement.** Every ad campaign that uses `budget_type = "daily"` exhausts its daily cap on day one and is then permanently suppressed from serving. `spent_today_cents` accumulates indefinitely in DynamoDB and is never zeroed at UTC midnight; once a campaign's daily budget is consumed, `_has_budget()` at `app/services/ad_serving.py:310` returns `False` for every subsequent ad-selection call for that campaign—forever.

**Verdict (from investigation):** Confirmed. The field is written on every billing event (`app/services/ad_billing.py:136`) but has no corresponding reset anywhere in the codebase. A grep of the full `app/` tree for `"spent_today_cents"` returns exactly four files—`ad_serving.py` (read), `ad_billing.py` (write/increment), `ad_optimization.py` (read), and `ad_campaigns.py` (initial creation set to `0`)—with no reset, cron, or background task anywhere.

**Severity and area.** Critical / Advertising & Monetisation. Affects all daily-budget campaigns the moment they exhaust day-one spend. Because the platform's ad revenue depends on campaigns continuing to serve across multiple days, this is both a revenue and an advertiser-trust issue.

**Related tickets.** ADS-004 (ad serving engine), GAP-0048 (companion ticket describing the same symptom from a different angle — "no daily spent_today_cents reset background task"), GAP-0050 (compute-hourly-rollup never called). No blocking dependencies; the fix is self-contained within the ad-serving layer.

## 2. Current-State Investigation (root cause)

### The read path: `_has_budget()` in `ad_serving.py:310–320`

```python
# app/services/ad_serving.py:310–320
def _has_budget(campaign: dict) -> bool:
    budget = int(campaign.get("budget_cents", 0))
    spent = int(campaign.get("lifetime_spent_cents", 0))
    if campaign.get("budget_type") == "lifetime" and spent >= budget:
        return False
    if campaign.get("budget_type") == "daily":
        daily_spent = int(campaign.get("spent_today_cents", 0))
        daily_budget = int(campaign.get("daily_budget_cents", budget))
        if daily_spent >= daily_budget:
            return False
    return True
```

This function is called during every candidate-campaign evaluation in `serve_ad()`. When `daily_spent >= daily_budget`, the function short-circuits and the campaign is excluded from the auction for that request. There is no time-bounded TTL or date-awareness in this check; it operates purely on the raw integer stored in DynamoDB.

### The write path: `ad_billing.py:134–139`

```python
# app/services/ad_billing.py:134–139
T.ad_campaigns.update_item(
    Key={"pk": f"ACCT#{account_id}", "sk": f"CAMPAIGN#{campaign_id}"},
    UpdateExpression="SET spent_today_cents = if_not_exists(spent_today_cents, :z) + :amt, "
                     "lifetime_spent_cents = if_not_exists(lifetime_spent_cents, :z) + :amt",
    ExpressionAttributeValues={":z": 0, ":amt": charge_cents},
)
```

Every impression, click, and conversion charge atomically increments `spent_today_cents`. The DynamoDB `if_not_exists` guard handles first-write correctly, but there is no conditional logic to cap it to a calendar day or zero it at rollover.

### The missing reset path

`app/services/ad_campaigns.py:50` sets `spent_today_cents: 0` only at campaign creation time. There is no background task, scheduled job, startup handler, or EventBridge rule that resets the counter at midnight UTC.

`app/main.py` registers approximately 20 startup background tasks (lines 496–806). A complete audit of those registrations shows none that reference `spent_today_cents`, `daily_reset`, or any ad-budget rollover concept. The tasks that do exist cover: billing dunning, file manager purge, scheduled messages, broadcast scheduler, broadcast reminder, deletion scheduler, KYC SLA checker, carrier polling, KYC analytics precompute, bot scheduler, EC2 idle checker, K8s TTL checker, recording cleanup, unified scheduler, billing reconcile, projects reconcile, file-manager mount reconcile, broadcast reconciler, transcode worker, webhook dispatcher, and cart abandonment. The ad daily reset is absent from this list.

**The `spent_today_cents` field on initial creation.** `app/services/ad_campaigns.py:50` sets `spent_today_cents: 0` only when a new campaign record is first written to DynamoDB. No subsequent code ever writes `0` to this field again. The field is purely an accumulator with no rollover mechanism.

**Interaction with `ad_optimization.py`.** The investigation notes that `ad_optimization.py` also reads `spent_today_cents`. Specifically, the optimisation service uses the field to compute daily pacing — how quickly a campaign should be spending relative to its daily budget. Without a reset, the pacing calculation on day two onward operates on a cumulative lifetime figure rather than a true daily figure, producing completely wrong pacing recommendations even for campaigns that have not yet technically "exhausted" their daily cap (e.g., a campaign with `daily_budget_cents=10000` and `spent_today_cents=5000` at the end of day one will appear 50% spent on day two morning before any new spend occurs, causing it to pace aggressively when it should pace normally). This is a secondary impact of the same root cause.

**Dev vs prod behaviour.** The bug manifests identically in both environments because the DynamoDB table (`T.ad_campaigns`) is a real local DDB instance in dev (port 8001) and a real AWS DynamoDB table in production; neither environment has a reset mechanism. In dev the failure surface is limited to the E2E test run window; in production it is permanent and affects live advertisers from 00:00 UTC on day two of any campaign.

## 3. Impact / Exploit / Blast Radius

Any advertiser with a `budget_type = "daily"` campaign reaches the following state after day one:

1. All calls to `serve_ad()` that would have selected the campaign are silently skipped because `_has_budget()` returns `False`.
2. The campaign continues to appear as "active" in the advertiser dashboard (status field is not updated), so the advertiser sees an active campaign with zero delivery.
3. The advertiser is not charged after day one (no budget = no auction), but neither are they notified of the effective pause. They believe the campaign is running.
4. Platform revenue from that campaign drops to zero from day two onwards.
5. Creator revenue share derived from ad impressions on their content also drops to zero.

**Financial blast radius.** Every daily-budget campaign deployed since the feature launched is permanently suppressed after its first UTC day. The number of affected campaigns scales linearly with time since deployment. Advertisers may request full refunds for all days after day one on the grounds that the service was not delivered.

**No exploit required.** This is a silent logic bug; no attacker action is needed. Any advertiser who funds a daily-budget campaign and returns the next day will observe zero impressions.

**Compliance angle.** Charging an advertiser for a budget slot and then silently failing to deliver impressions may constitute breach of the advertising agreement and trigger chargebacks.

## 4. Fix Design (code-level)

### New service file: `app/services/ad_daily_reset.py`

Create a new async background task that:

1. Queries `T.ad_campaigns` for all items where `budget_type = "daily"` and `spent_today_cents > 0` (using a GSI scan or a filter expression on a table scan, depending on table size; a FilterExpression scan is acceptable at low campaign volume but should be replaced with a GSI on `budget_type` as volume grows).
2. Resets `spent_today_cents = 0` for each qualifying campaign using a conditional `update_item` to avoid resetting campaigns that were already zeroed by a concurrent call.
3. Sleeps until the next UTC midnight to avoid unnecessary polling.

```python
# app/services/ad_daily_reset.py (new file)
import asyncio
import logging
from datetime import datetime, timezone

from app.core.tables import T

logger = logging.getLogger(__name__)

_RESET_ATTR = "spent_today_cents"


def _seconds_until_midnight_utc() -> float:
    now = datetime.now(timezone.utc)
    midnight = now.replace(hour=0, minute=0, second=0, microsecond=0)
    next_midnight = midnight.replace(day=midnight.day + 1)  # safe; datetime handles month/year rollover
    return (next_midnight - now).total_seconds()


async def _reset_daily_spend_once() -> int:
    """Zero spent_today_cents for all daily-budget campaigns. Returns reset count."""
    from boto3.dynamodb.conditions import Attr
    count = 0
    last_key = None
    while True:
        kwargs: dict = {
            "FilterExpression": Attr("budget_type").eq("daily") & Attr(_RESET_ATTR).gt(0),
        }
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key
        resp = T.ad_campaigns.scan(**kwargs)
        for item in resp.get("Items", []):
            try:
                T.ad_campaigns.update_item(
                    Key={"pk": item["pk"], "sk": item["sk"]},
                    UpdateExpression=f"SET {_RESET_ATTR} = :zero",
                    ConditionExpression=Attr(_RESET_ATTR).gt(0),
                    ExpressionAttributeValues={":zero": 0},
                )
                count += 1
            except T.ad_campaigns.meta.client.exceptions.ConditionalCheckFailedException:
                pass  # concurrent reset already handled it
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
    return count


async def _daily_reset_loop() -> None:
    """Background loop: wait until UTC midnight, then reset all daily budgets."""
    while True:
        sleep_secs = _seconds_until_midnight_utc()
        logger.info("ad daily reset: sleeping %.0f s until next UTC midnight", sleep_secs)
        await asyncio.sleep(sleep_secs)
        try:
            n = await _reset_daily_spend_once()
            logger.info("ad daily reset: reset %d campaigns", n)
        except Exception:
            logger.exception("ad daily reset: unhandled error during reset")


def start_ad_daily_reset_task() -> None:
    """Startup handler: schedule the daily-reset background loop."""
    asyncio.ensure_future(_daily_reset_loop())
```

### Wire into `app/main.py`

Add the import and startup handler registration alongside the existing ad-related startup calls:

```python
# app/main.py (add near existing ad startup registrations)
from app.services.ad_daily_reset import start_ad_daily_reset_task
# ...
app.add_event_handler("startup", start_ad_daily_reset_task)
```

### Dev/Prod parity (SECOPS-007)

The reset task writes only to `T.ad_campaigns` (a DynamoDB table). In dev the table is DynamoDB Local on port 8001; in production it is AWS DynamoDB. No AWS-specific code path differs between the two environments. The background task runs identically in both. No mock bypass, feature flag, or environment branch is needed. The `asyncio.ensure_future` pattern is already used by all other background tasks in `main.py` (e.g., `start_billing_dunning_task`, `start_scheduled_messages_task`), so no new infrastructure is introduced.

**Conditional `update_item` guard.** The `ConditionExpression=Attr(_RESET_ATTR).gt(0)` ensures idempotency if the loop runs twice in rapid succession (e.g., if the process restarts near midnight). This is safe in both dev and prod.

### Backward compatibility

No schema migration is needed; `spent_today_cents` already exists on all campaign records (set to `0` at creation by `ad_campaigns.py:50`). The new task only writes `0` to an existing field.

### Alternatives considered

- **EventBridge scheduled rule (AWS-only):** Would introduce a dev/prod parity gap (EventBridge is not available in DDB Local). Rejected.
- **Cron external job (e.g., via the existing `CronCreate` hook):** Suitable for production but would require a separate deployment artefact. An in-process asyncio loop matches the project's existing pattern for all other scheduled tasks. Rejected in favour of in-process loop.
- **Reset lazily in `_has_budget()` based on a stored `last_reset_date`:** Would require a read-modify-write race condition and complicates the serving hot path. Rejected.

import pytest
from unittest.mock import AsyncMock, MagicMock, call, patch
from app.services.ad_serving import _has_budget

### Manual QA steps

1. Start the dev stack (`just up`).
2. Create a campaign with `budget_type=daily`, `daily_budget_cents=100`.
3. Trigger an impression via `POST /ui/ads/internal/charge-impression` until `spent_today_cents` reaches 100.
4. Confirm `GET /ui/ads/serve` no longer returns the campaign.
5. Manually call `_reset_daily_spend_once()` (via a test endpoint or the REPL).
6. Confirm `GET /ui/ads/serve` now returns the campaign again.
7. In the next integration run, confirm the background loop fires at UTC midnight and resets all qualifying campaigns without manual intervention.

### Observability

Add a counter metric `ad_daily_reset_campaigns_total` incremented by `_reset_daily_spend_once()` and a gauge `ad_daily_budget_campaigns_suppressed` (campaigns with `spent_today_cents >= daily_budget_cents`) polled hourly. Alert if `ad_daily_budget_campaigns_suppressed > 0` for more than 26 hours.

### Rollout & risks

- **Risk:** The reset loop could fire multiple times if the process restarts near midnight. Mitigated by the `ConditionExpression=Attr(_RESET_ATTR).gt(0)` guard on `update_item`.
- **Risk:** A full table scan on `T.ad_campaigns` at scale. Mitigate by adding a `budget_type` GSI once campaign count exceeds ~10k.
- **Rollback:** Removing `start_ad_daily_reset_task` from `main.py` reverts to the current (broken) state. No data migration needed for rollback.
- **Effort:** M — new service file (~80 lines), one `main.py` import + handler, and the test file.
- **Sequence:** Deploy before any daily-budget campaigns are activated in production.
