# GAP-0350: UPS Webhook Has No Timestamp-Tolerance or Replay-Protection Check — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. No investigation doc exists.

## 1. Summary & Classification

**Bug statement.** The UPS tracking webhook handler (`POST /api/ups/tracking/webhook`, `app/routers/ups.py:91`) validates the HMAC signature of the request body but performs no timestamp check and stores no record of processed event IDs. As a result, any legitimately signed webhook payload can be replayed indefinitely (minutes, hours, or days later), causing the order status update and seller delivery alert logic to re-fire for the same event. An attacker who captures a valid signed webhook body — or has transient access to UPS's outbound queue — can trigger repeated `delivered` status updates, spurious seller alerts, and potential business logic side-effects.

- **Severity**: HIGH — replay of a `delivered` event can trigger financial, fulfillment, or fraud workflows multiple times.
- **Source ticket**: SHOP-004 (carrier tracking); cross-ref SEC-002 (webhook signature integrity), SECOPS-007 (dev/prod parity)
- **Status**: Open
- **Owning area**: Shop / Carrier Integration / `app/routers/ups.py`
- **Claim verdict**: CONFIRMED. The webhook handler at lines 91–144 reads `x-ups-signature` (line 94) and verifies it via `verify_tracking_webhook_signature` (line 95). It then writes an audit row to `T.billing` (line 102), resolves the tracking number to an order, and calls `apply_tracking_result` (line 138). There is no `X-UPS-Timestamp` header check, no timestamp tolerance window, and no processed-event-ID dedup store. The `T.billing` audit row uses `pk="UPS_TRACKING"` and `sk=f"{now_ts()}#{tracking_number}"` (line 105) — `now_ts()` is the processing time, not a webhook event ID, so identical payloads processed twice get different SKs and are written as two distinct rows.
- **Related tickets**: SHOP-004, SEC-002, SECOPS-007

## 2. Current-State Investigation (root cause)

### Full webhook handler (ups.py:91–144)

```python
@router.post("/api/ups/tracking/webhook")
async def ups_tracking_webhook(req: Request) -> Dict[str, Any]:
    raw = await req.body()
    signature = req.headers.get("x-ups-signature", "")
    if not verify_tracking_webhook_signature(raw, signature):
        raise HTTPException(403, "Invalid UPS webhook signature")

    payload = await req.json() if raw else {}
    tracking_number = payload.get("tracking_number") or payload.get("trackingNumber") or "unknown"

    # 1. Audit log (existing behavior — preserved).
    T.billing.put_item(
        Item={
            "pk": "UPS_TRACKING",
            "sk": f"{now_ts()}#{tracking_number}",   # uses processing time, not event ID
            "payload": payload,
            "created_at": now_ts(),
        }
    )

    # 2. SHOP-004: resolve tracking number to order and update shipping status.
    order_updated = False
    try:
        ...
        order = find_transaction_by_tracking(tracking_number)
        if order:
            ...
            if apply_tracking_result(order, result) is not None:
                order_updated = True
    except Exception:
        pass

    return {"received": True, "order_updated": order_updated}
```

### What is missing

1. **No `X-UPS-Timestamp` header check**: UPS Real-Time Package Tracking webhooks include an `X-UPS-Timestamp` header (Unix epoch, seconds). The handler does not read this header. Without a tolerance window check (typically ±5 minutes), a replay attack using a valid signature can be submitted hours or days after the original event was delivered.

2. **No event ID dedup**: UPS webhooks include an event identifier (`eventId` or `messageId` field, depending on the UPS API version) in the payload. The handler does not read, store, or check this identifier. Multiple deliveries of the same event (which can occur from UPS's at-least-once delivery guarantee, not just malicious replays) all succeed.

3. **The audit row key is not idempotent**: The SK `f"{now_ts()}#{tracking_number}"` uses the server's current timestamp at processing time. Two identical payloads processed 1 second apart produce different SKs, so both are written to the audit log and both trigger `apply_tracking_result`. The billing table therefore accumulates duplicate event rows.

### `verify_tracking_webhook_signature` (services/ups.py:94–101)

```python
def verify_tracking_webhook_signature(raw_body: bytes, signature_header: str) -> bool:
    secret = (S.ups_webhook_secret or "").strip()
    if not secret:
        return True    # <-- dev-mode bypass when no secret configured
    if not signature_header:
        return False
    digest = hmac.new(secret.encode("utf-8"), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(digest, signature_header.strip())
```

The `if not secret: return True` branch is the dev-mode bypass (SECOPS-007 concern). In production, `S.ups_webhook_secret` is populated and signature verification is enforced. The signature covers the raw body but not the timestamp — a replay of the exact body with the exact signature passes signature verification.

## 3. Impact / Exploit / Blast Radius

### Replay attack scenario

1. Adversary captures a legitimate UPS webhook HTTP request (raw body + `x-ups-signature` header). This could happen via: a network tap on the webhook receiver (if TLS is terminated at a load balancer with shared logs), a compromised UPS account's webhook log, or a race condition in UPS's own at-least-once delivery.
2. Adversary replays the same request (same body, same signature) to `POST /api/ups/tracking/webhook` at will.
3. Each replay passes signature verification and re-executes `apply_tracking_result`.

### Business logic consequences of replay

`apply_tracking_result` in `app/services/carrier_tracking.py` updates the order's shipping status and fires the seller delivery alert when the status transitions to `"delivered"`. Depending on the idempotency of `apply_tracking_result`:

- If it is not idempotent (re-fires alerts on repeated calls): a seller receives N "Your item was delivered!" alerts for a single shipment — a significant UX failure and potential SMS/email cost amplification.
- If it transitions state machines (e.g., `pending → delivered → delivered`): repeated transitions may trigger post-delivery logic (auto-close order, release funds) multiple times, which in financial workflows could cause double-payouts or double-credits.

### At-least-once delivery (non-malicious scenario)

UPS's webhook system uses at-least-once delivery. For high-traffic tracking events, duplicate deliveries are normal. Without dedup, the current code incorrectly processes every duplicate as a new event, making the system functionally incorrect even without an adversary.

### Dev vs. production divergence (SECOPS-007)

In dev mode (`S.ups_webhook_secret = ""`), `verify_tracking_webhook_signature` returns `True` unconditionally for any body. This means replay and timestamp checks are even more important in dev testing — without them, dev tests cannot verify dedup behavior. The fix must apply in both environments, with the dedup store using `T.billing` or a new dedicated table that is available in DynamoDB Local.

## 4. Fix Design (code-level)

### 4a. Timestamp tolerance check

UPS includes the event timestamp in the `X-UPS-Timestamp` header (format: Unix seconds as a string). Reject requests where `|now - event_ts| > TOLERANCE_SECONDS`:

```python
_UPS_TIMESTAMP_TOLERANCE_SECONDS = 300  # 5 minutes

def _check_ups_timestamp_tolerance(req: Request) -> None:
    """Reject requests with an X-UPS-Timestamp outside the tolerance window."""
    ts_header = req.headers.get("x-ups-timestamp", "").strip()
    if not ts_header:
        # If UPS does not send the header, skip (backward-compatible for dev/mock)
        return
    try:
        event_ts = int(ts_header)
    except ValueError:
        raise HTTPException(403, "Invalid X-UPS-Timestamp header")
    drift = abs(now_ts() - event_ts)
    if drift > _UPS_TIMESTAMP_TOLERANCE_SECONDS:
        raise HTTPException(403, f"UPS webhook timestamp out of tolerance window ({drift}s)")
```

In dev mode when using `emit_ups_tracking_webhook` (ups.py:208), include the header: `headers={"x-ups-timestamp": str(now_ts()), ...}`.

### 4b. Event ID extraction

Read the event ID from the payload. UPS API v2 uses `eventId`; v1 may use `messageId` or `requestId`. Use a fallback chain:

```python
def _extract_ups_event_id(payload: dict) -> Optional[str]:
    return (
        payload.get("eventId")
        or payload.get("messageId")
        or payload.get("requestId")
        or None
    )
```

### 4c. Dedup via DynamoDB conditional write

Store processed event IDs in `T.billing` (reusing the existing table for simplicity) with a TTL of 24 hours. Use a conditional `put_item` with `attribute_not_exists` — if the event ID has already been processed, the condition fails and the webhook returns 200 (idempotent, not an error) without re-processing.

```python
_UPS_DEDUP_TTL_SECONDS = 86400  # 24 hours
_UPS_DEDUP_PK = "UPS_EVENT_PROCESSED"


def _check_and_mark_ups_event(event_id: str) -> bool:
    """
    Attempt to claim exclusive processing rights for this event_id.
    Returns True if this is the first time the event is seen (proceed).
    Returns False if the event was already processed (skip).
    """
    sk = f"EID#{event_id}"
    expires_at = now_ts() + _UPS_DEDUP_TTL_SECONDS
    try:
        T.billing.put_item(
            Item={
                "pk": _UPS_DEDUP_PK,
                "sk": sk,
                "event_id": event_id,
                "created_at": now_ts(),
                "ttl": expires_at,
            },
            ConditionExpression="attribute_not_exists(pk) AND attribute_not_exists(sk)",
        )
        return True  # First time seen — proceed
    except Exception as exc:
        if "ConditionalCheckFailed" in type(exc).__name__ or "ConditionalCheckFailed" in str(exc):
            return False  # Already processed
        raise  # Unexpected error — re-raise so the webhook returns 500
```

### 4d. Updated webhook handler

Replace the webhook function at ups.py:91–144:

```python
@router.post("/api/ups/tracking/webhook")
async def ups_tracking_webhook(req: Request) -> Dict[str, Any]:
    raw = await req.body()
    signature = req.headers.get("x-ups-signature", "")
    if not verify_tracking_webhook_signature(raw, signature):
        raise HTTPException(403, "Invalid UPS webhook signature")

    # Timestamp tolerance (replay prevention — window check)
    _check_ups_timestamp_tolerance(req)

    payload = await req.json() if raw else {}
    tracking_number = (
        payload.get("tracking_number") or payload.get("trackingNumber") or "unknown"
    )

    # Idempotency: dedup by event ID
    event_id = _extract_ups_event_id(payload)
    if event_id:
        if not _check_and_mark_ups_event(event_id):
            # Already processed — return 200 (idempotent, not an error)
            return {"received": True, "order_updated": False, "duplicate": True}
    else:
        # No event ID in payload — fall back to audit-row-only (no dedup possible)
        # Log a warning for observability
        pass

    # Audit log (existing behavior — preserved; SK now uses event_id if available)
    audit_sk = f"EID#{event_id}" if event_id else f"{now_ts()}#{tracking_number}"
    T.billing.put_item(
        Item={
            "pk": "UPS_TRACKING",
            "sk": audit_sk,
            "payload": payload,
            "event_id": event_id,
            "tracking_number": tracking_number,
            "created_at": now_ts(),
        }
    )

    # Order status update (existing SHOP-004 logic — unchanged)
    order_updated = False
    try:
        from app.services.carrier_tracking import apply_tracking_result, map_carrier_status
        from app.services.purchase_history import find_transaction_by_tracking

        order = find_transaction_by_tracking(tracking_number)
        if order:
            raw_status = (
                payload.get("status_description")
                or payload.get("statusDescription")
                or payload.get("status")
                or ""
            )
            new_status = map_carrier_status("ups", str(raw_status))
            result = {
                "status": new_status,
                "status_description": payload.get("status_description")
                or payload.get("statusDescription")
                or str(raw_status),
                "delivered_at": payload.get("delivered_at"),
                "events": payload.get("events"),
            }
            if apply_tracking_result(order, result) is not None:
                order_updated = True
    except Exception:
        pass

    return {"received": True, "order_updated": order_updated, "duplicate": False}
```

### 4e. Dev/prod parity (SECOPS-007)

- **Dev mode (`S.dev_mode = True`)**: `ups_webhook_secret` is empty, so `verify_tracking_webhook_signature` returns `True`. The timestamp tolerance check skips if `X-UPS-Timestamp` is absent — set it in `emit_ups_tracking_webhook` (ups.py:208). The dedup check uses `T.billing` via DynamoDB Local. Both paths use identical code.
- **Production**: `ups_webhook_secret` is populated. `X-UPS-Timestamp` is sent by UPS. Event IDs are present in UPS payloads. No divergence.
- **TTL**: DynamoDB Local supports the `ttl` attribute but does not auto-expire. In production, TTL must be enabled on `T.billing` in IaC (or the dedup check uses a separate `ups_events` table with TTL enabled).

### 4f. Alternatives considered

- **Nonce-based dedup in Redis**: Rejected. Redis is not in the dev stack and would require new infrastructure.
- **Dedup table in DynamoDB separate from `T.billing`**: Acceptable but adds a table. Reusing `T.billing` with a distinct `pk` prefix (`UPS_EVENT_PROCESSED`) is simpler and avoids new IaC resources.
- **Replay prevention via Stripe-style `Idempotency-Key` header**: UPS does not support custom response headers back from webhooks, so this pattern doesn't apply.

### Manual QA steps

1. Start dev stack (`just up`).
2. Set `UPS_WEBHOOK_SECRET=test-secret` in `.env.local` and restart backend.
3. Use `emit_ups_tracking_webhook` (or `curl`) to send a webhook with `X-UPS-Timestamp: <now>` and `eventId: "test-001"`.
4. Send again immediately (replay) — verify response `duplicate: true` and no duplicate audit row in `T.billing`.
5. Modify the timestamp to `<now - 400>` and resend — verify HTTP 403 response.
6. Delete the dedup record from DDB manually, resend — verify the event is processed again (TTL window reset).

### Observability

- Log a structured warning `ups.webhook.duplicate_suppressed: {event_id}` for every dedup hit.
- Log a warning `ups.webhook.no_event_id: {tracking_number}` when the payload lacks an event ID (so the dedup is unavailable for that payload type).
- Log an error `ups.webhook.timestamp_rejected: {drift_seconds}` for timestamp-out-of-window rejections.

These logs feed into the SECOPS-001 security event telemetry pipeline and can alert on replay attempts.

### Rollout and risks

- **Effort**: M (medium) — ~80 lines of new code, two new helper functions, updated `emit_ups_tracking_webhook` to include timestamp header, plus tests.
- **Risks**:
  - If UPS does not send `eventId` in some payload types, the dedup is bypassed and behavior reverts to pre-fix (duplicate processing possible but not worse than current state).
  - If UPS delivers payloads with significant clock skew (rare), legitimate events could be rejected by the timestamp check. The 5-minute window is standard for HMAC-timestamped webhooks (Stripe, Twilio, GitHub all use this value).
  - If `T.billing` TTL is not enabled in production, dedup records accumulate. They are small (one row per event) and bounded by the 24-hour business window — at 10,000 UPS events/day this is ~10,000 extra rows, which is negligible.
- **Sequencing**: Enable DynamoDB TTL on `T.billing` in IaC (or use a dedicated `ups_events` table) → deploy backend change → update `emit_ups_tracking_webhook` to include `X-UPS-Timestamp` in dev test helpers.
- **Rollback**: Remove `_check_ups_timestamp_tolerance` and `_check_and_mark_ups_event` calls from the handler. Dedup rows in DDB are harmless orphans.
