# GAP-0026: Revenue Split Hooks Absent from All Qualifying Billing Flows — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: The platform supports a content-licensing subsystem (`LICENSE-003`) where creators can register revenue-share agreements with licensors. Whenever a tip is sent, a locked message is unlocked, or a newsfeed post is tipped or unlocked, the licensor is contractually owed a percentage of that transaction. The function `process_revenue_split` exists and works correctly — but it is never called from any live billing event. Licensor accounts never receive their contractual revenue-share credits.

- **Severity**: Critical (CRIT)
- **Source ticket**: LICENSE-003
- **Status**: Open
- **Owning area**: Billing / License Revenue / Messaging / Newsfeed
- **Effort**: M

**Verdict**: Confirmed. The investigation (`docs/tickets/gap-tickets/investigations/GAP-0026.md`) verified that `process_revenue_split` at `app/services/license_revenue.py:82` is only reachable through a single debug/admin endpoint (`POST /process-split` at `app/routers/license_revenue.py:150`). It is never invoked automatically from any of the three primary revenue-generating billing flows.

**One-line impact**: Licensors lose all revenue-share credits on tips, unlocks, and post purchases; the financial discrepancy is silent and invisible to all parties.

**Related tickets**: LICENSE-003 (source), FIN-006 (per-content revenue breakdown), FIN-011 (collaboration revenue splitting), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### The revenue-split function

`app/services/license_revenue.py:82` defines `process_revenue_split(*, content_id, licensee_id, source_type, source_amount_cents, source_txn_id, currency)`. It queries the `license_revenue` DynamoDB table for all active licenses covering `content_id`, computes revenue-share and profit-share splits per license, enforces a safety cap (`SAFETY_CAP_PCT`), writes debit and credit ledger entries (`license_revenue_debit` / `license_revenue_credit`), and returns the list of splits created. The function is correct and complete.

### Where it is called today

A grep over `app/routers/*.py` finds exactly one call site:

```
app/routers/license_revenue.py:150 — splits = svc.process_revenue_split(...)
```

This call site is inside `POST /process-split`, an explicitly described test/debug endpoint:

```python
# app/routers/license_revenue.py:140–158
@router.post("/process-split")
async def process_split(body: dict, ctx: dict = Depends(require_ui_session)):
    """Trigger revenue split processing for a content item.
    This endpoint allows testing the split engine without going through
    the full tip/unlock flow.
    """
    splits = svc.process_revenue_split(
        content_id=body["content_id"],
        licensee_id=body.get("licensee_id", ctx["user_sub"]),
        ...
    )
```

There is no import of `license_revenue` in `app/routers/messaging.py`, `app/routers/newsfeed.py`, or any VOD purchase router.

### The three broken billing flows

**Flow 1 — Messaging tip** (`send_message_tip`, `app/routers/messaging.py:13461`):

The handler at lines 13516–13531 writes a `TipLedgerEntry` via `write_tip_ledger(...)` and generates an invoice. The ledger write ends at line 13531, followed by `create_invoice_safe(...)`. No `process_revenue_split` call follows. After the invoice, the function returns a `TipOut` response at approximately line 13560.

**Flow 2 — Messaging unlock** (`unlock_message`, `app/routers/messaging.py:13592`):

The handler writes raw DynamoDB ledger debit and credit entries at lines 13647–13687, inside a `try/except Exception: pass` block. After the `except`, at line 13691, an invoice is generated. No `process_revenue_split` call appears anywhere between lines 13592 and the end of the function.

**Flow 3 — Newsfeed post tip and unlock** (`app/routers/newsfeed.py`):

The grep `grep -n "process_revenue_split" app/routers/newsfeed.py` returns zero results. The newsfeed router has no import of the `license_revenue` service.

### Root cause summary

`process_revenue_split` was implemented as a standalone utility and tested via a dedicated debug endpoint (`POST /process-split` in `app/routers/license_revenue.py:140`). The integration step — inserting a best-effort hook call after each primary ledger write — was never performed. The `license_revenue` service is fully self-contained and nothing imports it at transaction time outside of the test endpoint.

### Scope verification

A comprehensive search confirms zero automatic call sites:

```
grep -rn "process_revenue_split" app/routers/messaging.py   → 0 results
grep -rn "process_revenue_split" app/routers/newsfeed.py    → 0 results
grep -rn "license_revenue" app/routers/messaging.py         → 0 results
grep -rn "license_revenue" app/routers/newsfeed.py          → 0 results
```

The only import of `license_revenue` outside the service's own module is in `app/routers/license_revenue.py` itself. This confirms that the integration was never started, not merely partially completed.

## 3. Impact / Exploit / Blast Radius

This is a **financial integrity bug**, not a security exploit.

**Licensor revenue loss**: Any creator who registered a content license with `register_content_license` (e.g., a music licensor whose track is used in a message or post) never receives the contractually agreed revenue-share credits. The license record exists in DynamoDB, the terms are set, but `process_revenue_split` is never called so no `license_revenue_credit` ledger entries are written.

**Silent discrepancy**: Because there is no error, no log warning, and no failed payment, neither the licensor, the licensee, nor the platform finance team has any signal that splits are not occurring. The audit trail shows tips and unlocks succeeding normally. Only a manual comparison of the `license_revenue` table against the billing ledger would reveal the gap.

**Quantified exposure**: Every tip and unlock transaction since the feature was deployed has under-credited licensors. In a high-volume environment the cumulative shortfall could be substantial. Because `process_revenue_split` also writes `license_revenue_debit` entries for the licensee, the licensee's contractual obligations are also untracked.

**Compliance exposure**: Revenue-sharing agreements are contractual obligations. Systematic non-payment is a breach of contract and, depending on jurisdiction and content type (music, artwork), may trigger additional IP-licensing liability.

**Scope**: All messaging tips, all messaging unlocks, all newsfeed post tips, all newsfeed post unlocks, and any VOD purchase revenue. The impact window begins at the deployment of LICENSE-003.

## 4. Fix Design (Code-Level)

### Principle

Insert a best-effort call to `process_revenue_split` immediately after the primary ledger write in each billing handler. Using a `try/except Exception` wrapper ensures that a failure in the revenue-split calculation does not roll back or block the primary transaction. Log the failure at `WARNING` level for observability.

### Fix 1 — `send_message_tip` (messaging.py ~line 13531)

After `write_tip_ledger(...)` completes (line 13531), insert:

```python
# Best-effort license revenue split for tipped message
try:
    from app.services import license_revenue as _lr_svc
    _lr_svc.process_revenue_split(
        content_id=message_id,
        licensee_id=user_id,
        source_type="tip",
        source_amount_cents=inp.amount_cents,
        source_txn_id=tip_payment_id,
        currency=str(inp.currency or "usd").lower(),
    )
except Exception:
    logger.warning(
        "license revenue split failed for tip on message %s", message_id
    )
```

### Fix 2 — `unlock_message` (messaging.py ~line 13689)

After the `except Exception: pass` block that ends the raw ledger writes (line 13689), before `create_invoice_safe(...)`, insert:

```python
# Best-effort license revenue split for unlocked message
try:
    from app.services import license_revenue as _lr_svc
    _lr_svc.process_revenue_split(
        content_id=message_id,
        licensee_id=user_id,
        source_type="unlock",
        source_amount_cents=amount_cents,
        source_txn_id=unlock_payment_id,
        currency="usd",
    )
except Exception:
    logger.warning(
        "license revenue split failed for unlock on message %s", message_id
    )
```

### Fix 3 — Newsfeed post tip handler (`app/routers/newsfeed.py`)

Locate the post tip billing write (the handler that processes `POST /posts/{post_id}/tip`). After the `write_tip_ledger` or raw ledger write, add:

```python
try:
    from app.services import license_revenue as _lr_svc
    _lr_svc.process_revenue_split(
        content_id=post_id,
        licensee_id=tipper_user_id,
        source_type="post_tip",
        source_amount_cents=inp.amount_cents,
        source_txn_id=tip_payment_id,
        currency=str(inp.currency or "usd").lower(),
    )
except Exception:
    logger.warning(
        "license revenue split failed for post tip on post %s", post_id
    )
```

Apply the equivalent pattern to the newsfeed post unlock billing path.

### Dev/Prod Parity (SECOPS-007)

`process_revenue_split` reads from and writes to the `license_revenue` DynamoDB table exclusively. This table is created by `scripts/local-ddb-init.py` and is present in both dev and production environments. The function uses `T.license_revenue` (the table handle from `app/core/tables.py`), which already follows the dev/prod parity rules — it resolves to DynamoDB Local on port 8001 in dev and to AWS DynamoDB in production via the `DDB_ENDPOINT_URL` setting. No mock paths, feature flags, or AWS-specific branches are needed for this fix.

### Backward compatibility

The fix is additive. Existing billing flows continue to run unchanged; the only difference is that a new best-effort call is appended after the ledger write. Existing `license_revenue` entries in production remain valid. There is no migration required because the table schema is not changing.

### Fix 4 — VOD purchase path

The investigation found no VOD purchase router that calls `process_revenue_split`. When VOD pay-per-view is implemented (`MON-001`), the same hook pattern must be applied in the purchase handler after the billing ledger write. This should be included in the MON-001 implementation spec to prevent the gap recurring.

### Fix 5 — Newsfeed post unlock (`unlock_post` handler, `app/routers/newsfeed.py`)

The `unlock_post` handler writes a `LEDGER` debit entry for the buyer and a credit entry for the seller. After the ledger writes, before returning `UnlockOut`, insert:

```python
try:
    from app.services import license_revenue as _lr_svc
    _lr_svc.process_revenue_split(
        content_id=post_id,
        licensee_id=buyer_user_id,
        source_type="post_unlock",
        source_amount_cents=unlock_price_cents,
        source_txn_id=unlock_payment_id,
        currency="usd",
    )
except Exception:
    logger.warning(
        "license revenue split failed for post unlock on post %s", post_id
    )
```

### Idempotency note

`process_revenue_split` generates a `TXN#<split_id>` record in the `license_revenue` table using a UUID generated at call time. If the caller retries on failure, a duplicate split entry may be created. A future enhancement should add an idempotency key derived from `source_txn_id` to prevent double-crediting licensors on retried transactions. For the initial fix, the best-effort `try/except` pattern means retries are unlikely in the common path.

### Alternative considered

Making the revenue split **synchronous and blocking** (removing `try/except`) was considered but rejected. The primary billing transaction (tip payment or unlock payment) must not fail because of a licensing table issue. A best-effort design with logged failure is consistent with how invoices are handled in the same handlers (`create_invoice_safe` at line 13533 uses the same pattern).

### Manual QA steps

1. Start the dev stack: `just up`.
2. Register a content license: `POST /ui/licenses/revenue/register` with `content_id=MSG1`, `licensor_id=<user_b>`, `revenue_share_pct=20`.
3. As user A, tip user B's message MSG1 for 500 cents.
4. Verify: `GET /ui/licenses/revenue/summary?role=licensor` with user B's session returns `total_cents >= 100` (20% of 500).
5. Repeat for the unlock flow and the newsfeed post tip flow.

### Metrics and observability

- Add a structured log line at `INFO` level when `process_revenue_split` runs with `processed_splits > 0`: `"license_split: processed N splits for {source_type} on {content_id}"`.
- The `WARNING` log in the `except` block provides observability for failures.
- In production, monitor CloudWatch for `license revenue split failed` log patterns.

### Rollback

The fix is additive and wrapped in `try/except`. Rollback is a code revert. No DynamoDB schema change is needed; the `license_revenue` table already exists.

### Risks

- **Performance**: `process_revenue_split` queries `license_revenue` for licenses on each billing event. If a content item has no licenses (the common case), `list_licenses_for_content` returns quickly. The performance impact is negligible for most content; content with many licensors adds a small DDB query overhead per transaction.
- **Retroactive splits**: Existing transactions before this fix will not be retroactively split. A backfill script querying the billing ledger for `content_type=message` or `post` entries and calling `process_revenue_split` would be needed if contractual obligations require retroactive credits. This is a separate workstream.

Extend `frontend/e2e/messaging-features.spec.ts` or add a new spec. After Alice sends a tip to Bob's message, query the license revenue summary endpoint with the licensor's session and assert `total_cents > 0`:

### Effort and sequencing
