# GAP-0164: Poll vote endpoint does not enforce post visibility/subscription gate — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing; all citations are live file:line references.

## 1. Summary & Classification

**Bug statement**: `POST /posts/{post_id}/vote` checks that the post exists and that it is a poll, but never checks whether the authenticated caller is allowed to see the post. A poll configured with `visibility: "followers"` or gated behind a subscription plan can be voted on by any authenticated user who knows or guesses the `post_id`, bypassing both the follower-gate and the subscription-entitlement gate.

**Severity**: HIGH  
**Source ticket**: ENGAGE-002 (Polls & Surveys)  
**Status**: Open  
**Owning area**: Backend — `app/routers/newsfeed.py:6659` (`vote_on_poll`)  
**Effort**: S (single guard insertion)

**Verdict**: Claim **confirmed**. The `vote_on_poll` handler at `app/routers/newsfeed.py:6659–6703` contains no call to `can_view_post`, `can_access_creator`, or any other visibility check. The `can_view_post` helper already exists at line 2557 and is used by every comparable read endpoint (`get_post` at line 4079, `create_comment` at line 5330, `tip_post` at line 4458, etc.), but was simply omitted from the ENGAGE-002 poll vote handler.

**Impact in one line**: Any authenticated user can vote on followers-only or subscription-gated polls, inflating counts and bypassing access-control decisions that creators rely on to restrict their content.

**Related tickets**: ENGAGE-002 (parent), GAP-0163 (SSE missing from the same endpoint — both should be fixed together).

## 2. Current-State Investigation (root cause)

### The missing guard

`app/routers/newsfeed.py:6659–6666`:

```python
@router.post("/posts/{post_id}/vote")
def vote_on_poll(post_id: str, body: VoteIn, user_id: UserIdDep):
    """Cast or change a vote on a poll/survey post."""
    post = ddb_get_item({"pk": pk_post(post_id), "sk": sk_post()})
    if not post:
        raise HTTPException(status_code=404, detail="Post not found")
    if post.get("post_type") not in ("poll", "survey"):
        raise HTTPException(status_code=400, detail="Post is not a poll")
    # ← NO visibility check before proceeding to cast_vote
```

### The existing visibility infrastructure

`app/routers/newsfeed.py:2557–2566`:

```python
def can_view_post(viewer_id: str, post: Dict[str, Any]) -> bool:
    author = str(post.get("user_id") or "").strip()
    if not author or author == viewer_id:
        return True
    if not can_access_creator(viewer_id, author):
        return False
    visibility = str(post.get("visibility") or "followers").strip().lower()
    if visibility == "public":
        return True
    return is_following(viewer_id, author)
```

`can_view_post` combines two gates:

1. **Subscription gate** (`can_access_creator`): checks `app/services/subscription_access.py` for active subscription entitlement.
2. **Follow gate**: checks the follow relationship in DynamoDB.

The function is called in every endpoint where post content is read:

| Endpoint | Line | Guard call |
|---|---|---|
| `get_post` | 4079 | `if … not can_view_post(user_id, post): raise 403` |
| `tip_post` | 4458 | `if … not can_view_post(user_id, post): raise 403` |
| `create_comment` | 5330 | `if … not can_view_post(user_id, post): raise 403` |
| `unlock_post` | 5261 | `if … not can_view_post(user_id, post): raise 403` |
| `vote_on_poll` | 6659 | **MISSING** |

The omission follows the same pattern as most mutation endpoints: the post is fetched, its type is validated, and then the mutation proceeds — but the visibility check step is absent.

### Why this is HIGH severity

The visibility system (`visibility: "followers"` and subscription plans) is part of the creator monetization and access control layer. Votes are a measurable form of engagement that affects poll results — creators publish followers-only polls expecting that the results reflect only their intended audience. Breaching this gate is not merely an information leak; it allows:

1. **Ballot stuffing**: Non-followers or non-subscribers can vote, corrupting the representative sample the creator intended.
2. **Post-ID enumeration**: An attacker who iterates `post_id` values can determine whether a post is a poll (via the 400 response vs. 403) and cast votes even for posts they cannot legally view.

### Interaction with the locked-post model

The `can_view_post` function only checks the follow/subscription gate. It does not check the locked-body paywall (`post["locked"]`). The design decision is that locked posts are viewable (the metadata is visible; only the body is paywalled) but only to subscribers/followers. This existing behavior is correct for voting — you can see a poll's question once you can view the post, so the `can_view_post` guard is the right level.

### Dev vs prod

The gap is identical in both environments. The `can_view_post` → `can_access_creator` chain calls `app/services/subscription_access.py`, which queries DynamoDB. In dev, that query goes to DynamoDB Local; in prod, to AWS DynamoDB. Same code path, no mock divergence.

## 3. Impact / Exploit / Blast Radius

### Exploit walkthrough

1. Alice creates a subscription-gated poll (`visibility: "followers"`), expecting only her followers to vote.
2. Attacker (Bob, a non-follower) guesses or discovers `post_id` (e.g., by noting the sequential-ish UUID pattern or observing public share links).
3. Bob POSTs to `/posts/{alice_poll_id}/vote` with a valid session.
4. `vote_on_poll` does not check `can_view_post(bob_id, post)` → reaches `cast_vote` → Bob's vote is persisted.
5. Alice sees inflated or skewed poll results from outside her intended audience.

### Severity dimensions

| Dimension | Impact |
|---|---|
| **Poll integrity** | Vote counts are permanently corrupted; no audit trail separates legitimate from illegitimate votes |
| **Creator trust** | Creators who relied on visibility gating for accurate audience polling lose confidence in the feature |
| **Subscription revenue** | Non-subscribers can interact with subscription-gated polls without paying, partially devaluing subscriptions |
| **Enumeration surface** | The missing check combined with the 400 "Post is not a poll" / 404 "Post not found" distinction leaks poll/non-poll classification to unauthenticated-but-logged-in attackers |

**Blast radius**: All polls and surveys created with non-public visibility. Creators who rely on visibility gating are most affected. Publicly-visible polls (`visibility: "public"`) are unaffected.

## 4. Fix Design (code-level)

### Minimal fix

Add the `can_view_post` guard immediately after the poll-type check, matching the pattern used by every other mutation endpoint. The post is already fetched, so no additional DDB read is required.

`app/routers/newsfeed.py:6664–6666` becomes:

```python
    if not post:
        raise HTTPException(status_code=404, detail="Post not found")
    if post.get("post_type") not in ("poll", "survey"):
        raise HTTPException(status_code=400, detail="Post is not a poll")

    # ── ENGAGE-002 fix: enforce visibility/subscription gate ────────────────
    post_author = str(post.get("user_id") or "").strip()
    if post_author and post_author != user_id and not can_view_post(user_id, post):
        raise HTTPException(status_code=403, detail="Not authorized to view this post")
    # ────────────────────────────────────────────────────────────────────────
```

`can_view_post` is already defined at line 2557 and available in scope — no import needed.

The three-part condition mirrors every other call site exactly:
- `post_author` — skip check if post has no author (data integrity edge case).
- `post_author != user_id` — post owners can always vote on their own polls (e.g., to test).
- `not can_view_post(user_id, post)` — combined follow + subscription gate.

### Security hardening: information-leak prevention

The current 400 "Post is not a poll" response leaks that the post exists but is not a poll, even to unauthorized users. After applying the guard, the order of checks should be:

```python
    post = ddb_get_item(...)
    if not post:
        raise HTTPException(status_code=404, detail="Post not found")
    # Check access BEFORE revealing post type
    post_author = str(post.get("user_id") or "").strip()
    if post_author and post_author != user_id and not can_view_post(user_id, post):
        raise HTTPException(status_code=403, detail="Not authorized to view this post")
    # Only now reveal post type to authorized callers
    if post.get("post_type") not in ("poll", "survey"):
        raise HTTPException(status_code=400, detail="Post is not a poll")
```

This eliminates the oracle that lets an attacker distinguish "post exists but is gated" from "post exists and is a poll."

### Dev/Prod parity (SECOPS-007)

`can_view_post` calls `can_access_creator` (subscription check, `app/services/subscription_access.py`) and `is_following` (follow check, also in `newsfeed.py:2492`). Both query DynamoDB. In dev, the DynamoDB Local instance at port 8001 serves both calls. In prod, AWS DynamoDB serves both. The code path is identical — no mock branching is required. The fix is uniformly effective in both environments.

### Backward compatibility

Callers that already have access to the post (followers, subscribers, or the author) will see no change. Only callers that were previously able to vote on restricted polls despite lacking access will receive a 403. No DynamoDB migration is needed.

### Alternatives considered

- **Extract `_check_post_access(post, user_id)` helper** (as suggested in the gap ticket): Good long-term refactor to centralize the pattern, but the inline guard is sufficient and safer for a point fix.
- **Validate at `cast_vote` level in the service**: The service layer should not own routing-level access control; the router is the right place.
- **Return 404 instead of 403 for access-denied**: Hides existence but makes UI error handling harder; 403 is consistent with every other endpoint in the file.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline, fails-before / passes-after)

```python
# tests/test_poll_access_gate.py
"""
Regression test for GAP-0164: vote_on_poll must enforce post visibility.
FAILS before the guard is added (returns 200), PASSES after (returns 403).
"""
import pytest
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

ALICE = "alice@test.local"
BOB   = "bob@test.local"  # not a follower of Alice in this test

def _h(sub: str) -> dict:
    return {"X-User-Sub": sub}


@pytest.fixture
def followers_only_poll(mock_ddb):
    """Seed a followers-only poll post owned by Alice."""
    post_id = "poll_test_gated_001"
    mock_ddb.put(post_item(
        post_id=post_id,
        user_id=ALICE,
        post_type="poll",
        visibility="followers",
        poll_data={"questions": [{"question_id": "q1", "options": [{"option_id": "opt_a"}]}]},
    ))
    return post_id


def test_non_follower_cannot_vote_on_gated_poll(followers_only_poll):
    """Bob (not a follower) must receive 403 when voting on Alice's gated poll.

    FAILS before the can_view_post guard is added (returns 200).
    PASSES after the guard is added (returns 403).
    """
    resp = client.post(
        f"/posts/{followers_only_poll}/vote",
        json={"question_id": "q1", "option_id": "opt_a"},
        headers=_h(BOB),
    )
    assert resp.status_code == 403, (
        f"Expected 403 for non-follower voter on gated poll; got {resp.status_code}. "
        "The can_view_post guard is missing from vote_on_poll."
    )


def test_owner_can_vote_on_own_poll(followers_only_poll):
    """Alice (owner) must be allowed to vote on her own poll."""
    resp = client.post(
        f"/posts/{followers_only_poll}/vote",
        json={"question_id": "q1", "option_id": "opt_a"},
        headers=_h(ALICE),
    )
    assert resp.status_code == 200


@pytest.fixture
def public_poll(mock_ddb):
    """Public poll — any authenticated user can vote."""
    post_id = "poll_test_public_001"
    mock_ddb.put(post_item(
        post_id=post_id,
        user_id=ALICE,
        post_type="poll",
        visibility="public",
        poll_data={"questions": [{"question_id": "q1", "options": [{"option_id": "opt_a"}]}]},
    ))
    return post_id


def test_anyone_can_vote_on_public_poll(public_poll):
    """Public polls must still accept votes from any authenticated user."""
    resp = client.post(
        f"/posts/{public_poll}/vote",
        json={"question_id": "q1", "option_id": "opt_a"},
        headers=_h(BOB),
    )
    assert resp.status_code == 200, (
        f"Public poll vote must not be blocked; got {resp.status_code}"
    )
```

### Manual QA steps

1. Log in as Alice. Create a poll with `visibility: followers`.
2. Log in as Bob (not following Alice). Attempt to vote via the API or UI on Alice's poll.
3. Confirm the response is **403 Not authorized**.
4. Alice follows Bob back; Bob now follows Alice. Bob votes → confirm **200 OK**.
5. Confirm vote counts are correctly updated only for the legitimate vote.

### Observability

- Log `WARNING poll_vote_access_denied: post={post_id} voter={user_id} visibility={visibility}` on each 403 rejection — this helps identify probing activity.
- Counter metric `newsfeed.poll.vote.access_denied` to alert on unexpected spikes.
