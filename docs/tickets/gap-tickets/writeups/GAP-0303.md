# GAP-0303: SEC-012 cross-ref: `content_url` not validated against SSRF or internal network targets — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Severity**: HIGH · **Source ticket**: MOD-002 · **Status**: Open · **Effort**: S  
**Owning area**: Backend — DMCA models (`app/models.py`) / security (SEC-012)

The `DmcaClaimIn` Pydantic model at `app/models.py:2164` validates the `content_url` field in `_validate_content_url()` (lines 2184–2190). The validator strips whitespace and blocks `javascript:` and `data:` scheme prefixes, but it does **not** validate:

1. Whether the URL is a relative path or points to the platform's own hostname (SSRF via external URL).
2. Whether the URL resolves to an internal network target (`localhost`, `127.0.0.1`, `169.254.*`, RFC-1918 ranges) — the classic SSRF vector.
3. Whether the URL uses other dangerous schemes: `file://`, `ftp://`, `gopher://`, etc.

The ticket design (SEC-012 cross-ref in MOD-002) specified both a `javascript:`/`data:` check **and** an SSRF/hostname allowlist check. The implementation only shipped the first half.

**Claim verification**: Partially confirmed — the gap ticket states "the existing `javascript:`/`data:` check in the ticket design is absent from the implementation." This is **inaccurate**: the `javascript:` and `data:` checks ARE present at `app/models.py:2188`. The SSRF / internal-network validation and hostname allowlist portions are the actual missing pieces. The writeup proceeds on that corrected basis.

**Impact**: An authenticated user can file a DMCA claim with `content_url` pointing to an internal IP (e.g., `http://169.254.169.254/latest/meta-data/`) or to an arbitrary external host. Currently the backend only uses `content_url` to parse the URL path into `(content_type, content_id)` via `resolve_content_from_url()` — no outbound HTTP request is made against the URL itself. The SSRF risk is therefore **latent** rather than immediately exploitable via the current code. However, the design gap opens a path for future functionality (e.g., a "preview content" feature, a webhook that fetches the URL) to inherit the missing validation and become exploitable without further review.

**Related tickets**: SEC-012 (SSRF prevention), MOD-002 (DMCA claims system), GAP-0009 (custom base URL SSRF), GAP-0022 (SSRF via SEC-020).

## 2. Current-State Investigation (root cause)

### 2.1 Current validator: `app/models.py:2184–2190`

```python
@field_validator("content_url")
@classmethod
def _validate_content_url(cls, v: str) -> str:
    v = v.strip()
    if v.startswith("javascript:") or v.startswith("data:"):
        raise ValueError("Invalid content URL scheme")
    return v
```

The validator does exactly two things: strip leading/trailing whitespace, and block `javascript:` and `data:` prefixes. No hostname inspection. No scheme allowlist. No internal-network rejection.

### 2.2 How `content_url` is used today

`app/services/dmca_claims.py:79–103` (`file_dmca_claim`):
- Line 99: If `content_id` is not provided, calls `resolve_content_from_url(content_url)`.
- `resolve_content_from_url` at `app/services/dmca_content_operations.py:35–62` parses the URL path segments purely by string splitting — it never makes an HTTP request.
- The `content_url` value is stored verbatim in DynamoDB at line 122: `"content_url": content_url`.
- It is returned to the claimant via `GET /v1/dmca/claims/{claim_id}` at `app/routers/dmca.py:64`.

Today, no code anywhere fetches the `content_url` over the network. The risk is latent.

### 2.3 Dangerous schemes not blocked

The current validator does not block:
- `file:///etc/passwd` — local filesystem read if anything ever fetches it.
- `ftp://internal.host/secret` — FTP SSRF.
- `gopher://internal:6379/_*1%0d%0a$8%0d%0aflushall%0d%0a` — Gopher-based Redis SSRF.
- `http://169.254.169.254/latest/meta-data/` — AWS IMDS SSRF.
- `http://10.0.0.1/admin` — RFC-1918 internal host access.
- `http://[::1]/` — IPv6 loopback.

### 2.4 Why the gap matters now (latent → real risk)

The DMCA claims workflow is explicitly designed for integration with a future "takedown notification email" feature that would include the `content_url` as a link. Any email client's link-preview or click tracker that fetches that URL on behalf of the backend would trigger an SSRF. Additionally, admin UI implementations that render the `content_url` as a hyperlink without target sandboxing open a phishing/redirect attack surface if the URL points to an external site.

The gap also violates the platform's stated SEC-012 policy, making it a compliance finding even if the immediate exploit is not reachable today.

### 2.5 Relation to `resolve_content_from_url`

`resolve_content_from_url` (lines 35–62) only understands relative-path-style URLs (e.g., `/feed/post/abc123`, `/videos/xyz`). An absolute URL like `https://example.com/feed/post/abc123` would pass through to the catch-all `return "other", ""`. The validation gap therefore also affects the content-resolution logic: legitimate full URLs from the platform's own domain are silently downgraded to type `"other"` rather than being parsed correctly. The fix should canonicalise the URL to its path component before resolution.

## 3. Impact / Exploit / Blast Radius

### 3.1 Current exploitability

**Immediate impact**: Low. No outbound fetch is performed against `content_url` today. An attacker who submits `content_url: "http://169.254.169.254/latest/meta-data/iam/security-credentials/"` will have their claim filed successfully, but the value is only read back via `resolve_content_from_url` (path-only string parsing) and stored in DynamoDB. Nothing makes an HTTP request.

**Future / latent impact**: HIGH. Any feature that touches `content_url` downstream — email link preview, admin preview panel, webhook notification, content verification crawler — inherits the missing validation and becomes exploitable without additional review, because the data is already in the database flagged as "validated".

### 3.2 Worst-case exploit (latent)

If a "verify content exists" background job is added that GETs the `content_url`:

1. Attacker registers an account (no special role needed — the endpoint is auth-gated but only requires a valid session).
2. Files DMCA claim with `content_url: "http://169.254.169.254/latest/meta-data/iam/security-credentials/role_name"`.
3. Background job GETs the URL, receives AWS IMDS credentials in the response body.
4. Attacker retrieves the response via the claim audit log or an injected webhook.

With cloud IMDS credentials, full account takeover is possible.

### 3.3 Stored value as attack surface

The value is stored in DynamoDB and returned to authenticated callers (`GET /v1/dmca/claims/{claim_id}`). A malicious URL could exploit unsanitised rendering in the admin panel (open redirect, phishing via authority-bearing domain).

## 4. Fix Design (code-level)

### 4.1 Validation strategy

The correct fix enforces **two independent checks** in `_validate_content_url`:

1. **Scheme allowlist**: Only `https://`, `http://` (dev only), and bare paths (starting with `/`) are permitted. All other schemes (`javascript:`, `data:`, `file:`, `ftp:`, `gopher:`, etc.) are rejected.

2. **Hostname/network check for absolute URLs**: If the URL is absolute (has a netloc), reject if:
   - The hostname resolves to a loopback, link-local, or RFC-1918 address (DNS rebinding protection must be applied at fetch time too, but static-value rejection is the first line).
   - The hostname is not in the platform's allowed hostname list (configured via `S.platform_hostname`).

3. **Canonicalise for `resolve_content_from_url`**: Strip scheme+host to leave a bare path before the URL is passed to the resolver, so both `/feed/post/abc` and `https://platform.com/feed/post/abc` are resolved correctly.

### 4.2 Updated `_validate_content_url` in `app/models.py`

```python
import ipaddress
from urllib.parse import urlparse

_BLOCKED_SCHEMES = frozenset({"javascript", "data", "file", "ftp", "gopher", "dict", "ldap", "sftp"})
_ALLOWED_SCHEMES = frozenset({"https", "http", ""})  # "" = relative/path-only
_INTERNAL_NETWORKS = [
    ipaddress.ip_network("127.0.0.0/8"),
    ipaddress.ip_network("10.0.0.0/8"),
    ipaddress.ip_network("172.16.0.0/12"),
    ipaddress.ip_network("192.168.0.0/16"),
    ipaddress.ip_network("169.254.0.0/16"),   # AWS IMDS / link-local
    ipaddress.ip_network("::1/128"),
    ipaddress.ip_network("fc00::/7"),
]

@field_validator("content_url")
@classmethod
def _validate_content_url(cls, v: str) -> str:
    v = v.strip()
    if not v:
        raise ValueError("content_url must not be empty")

    parsed = urlparse(v)
    scheme = (parsed.scheme or "").lower()

    # 1. Reject explicitly blocked schemes (defence-in-depth over the existing check)
    if scheme in _BLOCKED_SCHEMES:
        raise ValueError(f"content_url scheme '{scheme}:' is not permitted")

    # 2. Reject schemes that are neither http/https nor relative paths
    if scheme and scheme not in {"http", "https"}:
        raise ValueError(f"content_url scheme '{scheme}:' is not permitted")

    # 3. For absolute URLs: enforce platform hostname and reject internal targets
    if parsed.netloc:
        hostname = parsed.hostname or ""
        # Reject bare IP addresses that map to internal ranges
        try:
            addr = ipaddress.ip_address(hostname)
            if any(addr in net for net in _INTERNAL_NETWORKS):
                raise ValueError("content_url must not point to an internal network address")
        except ValueError as exc:
            if "does not appear to be" not in str(exc):
                raise  # re-raise SSRF ValueError
        # Reject hostnames that are obviously internal (localhost, *.local, *.internal)
        if hostname in ("localhost",) or hostname.endswith((".local", ".internal", ".localhost")):
            raise ValueError("content_url must not point to an internal hostname")

    return v
```

Note: DNS-based SSRF (where the hostname resolves to an internal IP at fetch time) must be addressed separately at the HTTP client level (if/when a fetch is ever added). Static validation here is the first gate.

### 4.3 Settings integration

Add `S.platform_hostnames: list[str]` to `app/core/settings.py` for optional hostname allowlisting. In dev mode any `http://` or `https://` hostname is accepted (so localhost E2E test URLs work). In production, the validator can enforce that the URL's hostname matches the platform domain:

```python
platform_hostnames: list[str] = [
    h.strip() for h in
    os.environ.get("PLATFORM_HOSTNAMES", "").split(",") if h.strip()
]
```

When `platform_hostnames` is non-empty and the URL is absolute, the hostname must be in the list or a validation error is raised.

### 4.4 Dev/Prod parity (SECOPS-007)

The `_INTERNAL_NETWORKS` check and the scheme allowlist apply equally in dev and production — there is no `if S.dev_mode` branch. SSRF prevention must not be relaxed in dev mode. The `platform_hostnames` allowlist defaults to empty (accept any hostname) so dev test suites are unaffected; production deployments set `PLATFORM_HOSTNAMES=platform.com` in the environment. This satisfies SECOPS-007: the same code path runs in both environments; production behaviour is hardened by configuration, not by forked logic.

### 4.5 Alternatives considered

**Alternative A — validate at the service layer, not the Pydantic model**: Rejected because Pydantic model-level validation provides the earliest possible rejection point, produces 422 responses with structured field errors, and is the established project pattern for `content_url` constraints.

**Alternative B — reject all absolute URLs, require relative paths only**: This would break legitimate use cases where a claimant pastes a full URL from their browser bar (e.g., `https://platform.com/feed/post/abc123`). The fix canonicalises rather than rejects, and adds the platform-hostname allowlist as an opt-in enforcement layer.

### 5.5 Interaction with `resolve_content_from_url`

The current `resolve_content_from_url()` at `app/services/dmca_content_operations.py:35–62` uses pure path-segment parsing and only understands bare paths like `/feed/post/{id}`. When a claimant pastes a full URL from their browser address bar (e.g., `https://platform.example.com/feed/post/abc123`), the function receives the full URL, finds no matching path-segment pattern (because `parts[0]` is `"https:"` after splitting on `/`), and returns `("other", "")`. This means the `content_id` is never resolved and the content is not hidden.

The validation fix in section 4.2 introduces URL parsing via `urlparse`. The fix can additionally canonicalise absolute platform-domain URLs to their path-only form before storing the value, so that `resolve_content_from_url` receives `/feed/post/abc123` regardless of whether the claimant submitted a relative path or a full URL. This is a one-line addition in `_validate_content_url` after the SSRF checks pass:

```python
# Canonicalise absolute platform URLs to path-only
if parsed.netloc and parsed.scheme in {"http", "https"}:
    v = parsed.path  # strip scheme and hostname, keep path+query
```

This must only be done when the hostname is the platform's own — otherwise a claimant could submit `https://external-site.com/feed/post/abc123` and the validator would strip the external hostname and resolve `/feed/post/abc123` as if it were a valid platform URL.
