# GAP-0038: CLI admin grant Produces Implicit Full Admin — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: The `rootctl admin grant` CLI command elevates a user to the `admin` role but writes no `admin_profile` to the user record and no `admin_capabilities` to the token. At runtime, `mint_access_token` does not write `admin_profile` into the JWT (see GAP-0037 for the token-minting gap), so the JWT emerges with no `admin_profile` claim. `normalize_admin_profile(None)` falls back to `AdminProfile(type=GENERAL)`. `admin_profile_has_scope` for `GENERAL` returns `True` for every scope check. The result: every admin user created by `rootctl admin grant` immediately has unrestricted access to all admin-scoped endpoints — billing, impersonation, content moderation, permanent bans — regardless of whether such access was intended.

- **Severity**: HIGH
- **Source ticket**: ADMIN-PERMS-001
- **Status**: Open
- **Owning area**: Admin Permissions / RBAC / rootctl CLI
- **Effort**: M
- **Claim verdict**: CLAIM OK — confirmed. `_admin_grant_command` at `app/cli/rootctl.py:1303` writes only `role=admin` with no `admin_profile` or `admin_capabilities` field. The fallback chain in `normalize_admin_profile` (line 91 of `app/auth/roles.py`) silently grants `GENERAL` profile to any admin whose JWT contains no `admin_profile` claim.

**One-line impact**: Every operator who runs `rootctl admin grant` creates a fully-privileged admin account with no scope boundaries, even if a more restricted profile was intended.

**Related tickets**: ADMIN-PERMS-001 (source), GAP-0037 (capabilities system disconnected), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### The grant command's DynamoDB write

`app/cli/rootctl.py:1347–1358` (within `_admin_grant_command`):

```python
ts = now_ts()
T.users.update_item(
    Key={"user_sub": target_user_sub},
    UpdateExpression="SET #role=:role, role_updated_at=:ts, role_updated_by=:by, role_reason=:reason",
    ExpressionAttributeNames={"#role": "role"},
    ExpressionAttributeValues={
        ":role": Role.ADMIN.value,
        ":ts": ts,
        ":by": actor_sub,
        ":reason": reason,
    },
)
```

The `UpdateExpression` sets four fields: `role`, `role_updated_at`, `role_updated_by`, `role_reason`. There is no `admin_profile`, no `admin_capabilities`, and no `admin_profile_type` field. The absence is intentional in the current code — the command was implemented to grant role only.

### The revoke command mirrors the gap

`app/cli/rootctl.py:1445–1456` (within `_admin_revoke_command`) also does not clear `admin_capabilities`:

```python
T.users.update_item(
    Key={"user_sub": target_user_sub},
    UpdateExpression="SET #role=:role, role_updated_at=:ts, role_updated_by=:by, role_reason=:reason",
    ...
)
```

If an admin user had `admin_capabilities` set, revoking their admin role does not clear `admin_capabilities`. If their role is later re-granted, the stale `admin_capabilities` from the previous tenure would be picked up. However, since `admin_capabilities` is currently not bridged to the JWT (GAP-0037), this is not an immediate exploitable issue.

### The fallback chain that produces GENERAL

`app/auth/roles.py:75–115`, `normalize_admin_profile`:

```python
def normalize_admin_profile(value: Any) -> AdminProfile:
    if not isinstance(value, dict):
        return AdminProfile(type=AdminProfileType.GENERAL)   # line 91: None → GENERAL
    ...
```

`mint_access_token` (before the GAP-0037 fix) emits no `admin_profile` claim. `_extract_admin_profile_from_claims` at `app/auth/deps.py:148` returns `normalize_admin_profile(claims.get("admin_profile"))` = `normalize_admin_profile(None)` = `AdminProfile(type=GENERAL)`.

`admin_profile_has_scope` for `GENERAL`:

```python
def admin_profile_has_scope(profile: AdminProfile, scope: AdminScope | str) -> bool:
    ...
    if profile.type is AdminProfileType.GENERAL:
        return True    # every scope check passes
```

The entire chain is deterministic: grant → no admin_profile written → JWT has no admin_profile → GENERAL fallback → all scope checks pass.

### Argparse interface of grant command

`app/cli/rootctl.py` around line 2265–2295, the argparse registration for the `grant` subcommand accepts:
- `--target-user-sub`
- `--actor-sub`
- `--reason`
- `--role` (currently only `admin` is accepted)
- `--request-id`
- `--correlation-id`
- `--output`
- `--dry-run`

There are no `--scope`, `--capabilities`, `--profile-type`, or similar arguments. The command interface provides no mechanism to specify what level of access the new admin should have.

## 3. Impact / Exploit / Blast Radius

### Privilege escalation via grant without scope restriction

Consider a use case where a first-tier support operator is granted admin role to handle password resets only. The intended workflow:

1. Root operator runs `rootctl admin grant --target-user-sub support@company.com`.
2. The operator believes "support@company.com" can now reset passwords but nothing else.
3. In reality, support@company.com can:
   - Start impersonation sessions for any user (including ROOT, if `S.impersonation_allow_privileged_targets` is True).
   - Approve financial refunds and manually adjust billing ledgers.
   - Issue permanent bans and content strikes.
   - Export all private message history via compliance query endpoints.
   - Approve/reject DMCA takedown requests.

### Concrete over-privilege scenario

1. Operator grants admin role to a contractor for content review support.
2. Contractor's intention: review and moderate flagged content.
3. Actual access: full billing, full impersonation, full compliance export.
4. Contractor is compromised or malicious: downloads compliance report of all private messages, adjusts billing records, impersonates high-value users.
5. No scope boundary exists to contain the damage.

### Blast radius

- Affects every admin account ever created via `rootctl admin grant` (which is the primary admin provisioning path).
- All admin accounts in production environments created before this fix are currently fully privileged.
- Scope enforcement endpoints exist and are correctly coded but are never triggered.
- Compliance posture: least-privilege requirement for PCI-DSS, SOC 2, and GDPR data access is not met for admin accounts.

## 4. Fix Design (Code-Level)

### Change 1: add `--capabilities` argument to the grant command

The `_admin_grant_command` function and its argparse registration must accept a list of capabilities:

```python
# app/cli/rootctl.py — in the argparse registration block for admin grant (~line 2265)

grant_parser.add_argument(
    "--capability",
    dest="capability",
    action="append",
    default=[],
    metavar="CAPABILITY",
    help=(
        "Admin capability to assign. Repeatable. "
        "Allowed values: " + ", ".join(sorted(ADMIN_CAPABILITIES)) + ". "
        "Omit to create a general (full-access) admin."
    ),
)
```

### Change 2: write capabilities in UpdateExpression

In `_admin_grant_command` at line 1347, extend the `UpdateExpression` to include `admin_capabilities`:

```python
ts = now_ts()
new_caps = _parse_capabilities(list(getattr(args, "capability", []) or []))

if new_caps:
    # Scoped admin: write capabilities list; token-minting will build admin_profile
    T.users.update_item(
        Key={"user_sub": target_user_sub},
        UpdateExpression=(
            "SET #role=:role, role_updated_at=:ts, role_updated_by=:by, "
            "role_reason=:reason, admin_capabilities=:caps"
        ),
        ExpressionAttributeNames={"#role": "role"},
        ExpressionAttributeValues={
            ":role": Role.ADMIN.value,
            ":ts": ts,
            ":by": actor_sub,
            ":reason": reason,
            ":caps": new_caps,
        },
    )
else:
    # General admin: write role only; capabilities absent = GENERAL profile
    T.users.update_item(
        Key={"user_sub": target_user_sub},
        UpdateExpression="SET #role=:role, role_updated_at=:ts, role_updated_by=:by, role_reason=:reason",
        ExpressionAttributeNames={"#role": "role"},
        ExpressionAttributeValues={
            ":role": Role.ADMIN.value,
            ":ts": ts,
            ":by": actor_sub,
            ":reason": reason,
        },
    )
```

### Change 3: include capabilities in dry-run output

```python
if bool(shared.dry_run):
    return {
        ...
        "new_capabilities": new_caps,
        "message": (
            "dry-run: user would be granted admin role (general)"
            if not new_caps else
            f"dry-run: user would be granted admin role (scoped: {new_caps})"
        ),
    }
```

### Change 4: clear admin_capabilities on revoke

`_admin_revoke_command` must clear `admin_capabilities` when removing the admin role:

```python
T.users.update_item(
    Key={"user_sub": target_user_sub},
    UpdateExpression=(
        "SET #role=:role, role_updated_at=:ts, role_updated_by=:by, role_reason=:reason "
        "REMOVE admin_capabilities"
    ),
    ExpressionAttributeNames={"#role": "role"},
    ExpressionAttributeValues={
        ":role": Role.USER.value,
        ":ts": ts,
        ":by": actor_sub,
        ":reason": reason,
    },
)
```

### Dependency on GAP-0037

This fix is only effective when combined with the GAP-0037 fix. The GAP-0037 fix bridges `admin_capabilities` in DynamoDB to `admin_profile` in the JWT. Without GAP-0037, writing `admin_capabilities` in the grant command still has no effect at runtime. Both fixes must be deployed together.

### Dev/Prod parity (SECOPS-007)

`T.users.update_item` uses the `app/core/tables.py` DynamoDB handle, which routes to DynamoDB Local in dev and real DynamoDB in prod. No environment-specific branching is needed. The `_parse_capabilities` function is pure Python with no AWS dependency. The argparse interface is a CLI concern, not an HTTP concern. SECOPS-007 is fully satisfied: the same code path runs in both environments.

### Backward compatibility

- Existing admin accounts have no `admin_capabilities` → behavior unchanged (GENERAL profile, full access).
- `rootctl admin grant` with no `--capability` flags → no `admin_capabilities` written → GENERAL profile, full access (current behavior preserved).
- `rootctl admin grant --capability auth_support` → scoped profile; admin is restricted.
- Operators must explicitly opt into restrictions; existing automation is not broken.

### Observability

- `audit_event("admin_role_granted", ...)` is already emitted. Add `new_capabilities=new_caps` to the kwargs to record the intended scope in the audit trail.
- In production, set a CloudWatch alarm on `admin_role_granted` events with `new_capabilities=[]` (implicit full admin grants) to flag any unscoped grant for review.

### Rollout sequence

1. Deploy GAP-0037 fix (admin_capabilities → admin_profile bridge in mint_access_token) first.
2. Deploy GAP-0038 fix (add `--capability` to grant command, update revoke to clear capabilities).
3. Audit existing admin users: query DynamoDB for all records with `role=admin` and no `admin_capabilities` field. Review whether they should be restricted.
4. For each admin user identified as over-privileged: run `rootctl admin permissions set` to assign appropriate capabilities.

### Rollback

Remove `--capability` argument and the conditional `UpdateExpression` from `_admin_grant_command`. The behavior before the fix (write role only, implicit GENERAL) is restored. `admin_capabilities` fields already written are orphaned but harmless until the GAP-0037 bridge is also deployed.

### Why the capability list should be mandatory for new grants

The current design allows `rootctl admin grant` to be called without `--capability` flags, defaulting to a general (fully privileged) admin. For a more secure default, consider making at least one `--capability` flag required:

```python
if not new_caps and not getattr(args, "allow_general", False):
    raise CliPolicyError(
        "at least one --capability is required; use --allow-general to explicitly grant full admin access",
        details={"code": "missing_capabilities"},
    )
```

This forces the operator to make an intentional choice between a scoped admin and a general admin, rather than accidentally granting full access by omission. The `--allow-general` escape hatch preserves backward compatibility for legitimate use cases where a fully privileged admin is truly needed (e.g., platform engineers). This approach mirrors the security principle of "explicit over implicit" for privilege assignment.

For the initial fix, the mandatory flag approach is noted as a future hardening step. The first deployment should retain backward compatibility (no flags = GENERAL) to avoid breaking existing automation. After the codebase is audited and all existing `rootctl admin grant` invocations are documented, the mandatory-capability requirement can be enforced in a subsequent release.
