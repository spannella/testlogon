# GAP-0332: `finalize_deletion` does not cancel active subscriptions before deletion — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/services/account_deletion.py` and `app/routers/subscription_server.py`.

## 1. Summary & Classification

**Gap**: `finalize_deletion` initialises `summary["subscriptions_cancelled"] = 0` in the deletion cascade but never calls any subscription cancellation service. When a user's account is deleted, all `active` / `trialing` / `past_due` subscriptions they hold — both as subscriber (paying for a creator's tier) and as creator (receiving recurring revenue from subscribers) — continue to persist in the `subscriptions` DynamoDB table in a live status. This can result in:
- Orphaned recurring billing attempts after the subscriber's payment method is gone.
- Continued entitlement access for a deleted subscriber.
- Continued revenue-stream records referencing a deleted creator.

**Claim status**: Confirmed. The subscription cancellation field is a stub counter at `app/services/account_deletion.py:392`; no call to any cancellation path exists in `finalize_deletion`.

**Severity**: HIGH — financial integrity issue (orphaned billing), compliance issue (deleted user's payment method may be charged for a subscription they legally terminated via account deletion), and data consistency issue (entitlement table references a non-existent user).

**Source ticket**: PLATFORM-018. **Status**: Open. **Effort**: S. **Owning area**: Privacy / Billing / Subscriptions.

**Related tickets**: GAP-0331 (messages/posts not anonymised), GAP-0340 (S3 files), GAP-0341 (Cognito not disabled). Also closely related to the subscription server (PLATFORM-018 source ticket).


## 2. Current-State Investigation (root cause)

### `finalize_deletion` — no subscription cancellation

`app/services/account_deletion.py:386–403`:

```python
summary: Dict[str, Any] = {
    "wallet_refunded_cents": _refund_wallet(user_sub),
    "destructive": bool(S.account_deletion_destructive),
    "profile_deleted": False,
    "messages_anonymized": 0,
    "posts_anonymized": 0,
    "files_deleted": 0,
    "push_devices_deleted": 0,
    "subscriptions_cancelled": 0,    # <- never incremented
}

if S.account_deletion_destructive:
    ...
```

There is no subscription-related import, no call to `cancel_subscription`, and no iteration over the user's active subscriptions anywhere in `finalize_deletion`. The `subscriptions_cancelled` field is a placeholder.

### Subscription data layout (`app/routers/subscription_server.py`)

The subscription server stores subscriptions in the `subscriptions` DynamoDB table with a fan-out pattern:

- **Per-subscription record**: PK `SUB#{subscription_id}`, SK `META`. Contains `subscriber_id`, `creator_id`, `status`, `plan_id`, `current_period_end`, `auto_renew`. (The `pk_subscription()` helper at `subscription_server.py:118` returns `f"SUB#{subscription_id}"`.)
- **Subscriber index**: PK `SUBSCRIBER#{subscriber_id}`, SK `SUB#{subscription_id}`. Used by `list_subscriptions` at line 985 (decorator `@router.get` is at line 984).
- **Creator index**: PK `CREATOR#{creator_id}`, SK `SUB#{subscription_id}`. Used by `list_creator_subscriptions` at line 1009 (decorator at line 1008).

An active subscription has `status` in `{"active", "trialing", "past_due"}`. The cancellation endpoint at line 1105 (`POST /api/subscriptions/{id}/cancel`; decorator at line 1104) sets `status` to either `"canceling"` (cancel at period end) or `"canceled"` (immediate) and sets `auto_renew = False`.

### Why the gap matters financially

The subscription cycle is driven by `subscription_cycle_orders.py`. When a renewal is due, the system queries active subscriptions and attempts to charge the subscriber's default payment method. If the subscriber has been deleted:
- The `billing` table row for the user is gone (assuming the destructive path ran).
- The charge attempt fails, generating payment failure noise and potentially retry attempts.
- But if the billing row was NOT deleted (default: `account_deletion_destructive=False`), the charge will succeed against a payment method attached to a deleted account — a compliance violation.

As creator: if a deleted creator still has `active` subscriber records pointing at their `plan_id`, those subscribers may continue being charged for a service that no longer exists.

### `S.account_deletion_destructive` default

`app/core/settings.py:1673`: defaults to `False`. This means `delete_user_data` is never called either. In the current state, deletion = wallet zeroed, status = `completed`, everything else unchanged. The subscriptions gap is therefore active in every default deployment.


## 3. Impact / Exploit / Blast Radius

**Financial impact**:
- A subscriber who deletes their account may continue to be billed for active subscriptions until the subscription's `current_period_end` lapses. If the billing table row is intact (destructive mode off), the charge succeeds and the user receives no service — a chargeback risk.
- A creator who deletes their account may have their subscribers unknowingly charged for a tier with no creator to deliver content.

**Compliance / legal**:
- GDPR Art. 17 erasure should include termination of contractual obligations tied to the account. Continued billing post-deletion is a breach of both privacy law and likely the platform's own terms of service.
- PCI-DSS scope: payment method tokens stored under the deleted user's `billing` PK remain live and may be charged.

**Entitlement access**:
- `subscription_access.py` checks `status in {"active", "trialing"}` to gate premium content. A deleted subscriber still passes this check and can access gated content indefinitely if their account row has not been invalidated.

**Blast radius**:
- Every user who uses the deletion flow (could be thousands/month on a large platform).
- Every creator whose subscribers delete their accounts without subscription cancellation.
- The `subscriptions_cancelled: 0` in `deletion_summary` is written to DynamoDB and is audit-trail evidence that the failure occurred — discoverable in any data-protection audit.


## 4. Fix Design (code-level)

### 4a. `_cancel_active_subscriptions(user_sub)` helper

The helper must cancel subscriptions from both perspectives: (a) subscriptions where `user_sub` is the subscriber, and (b) subscriptions where `user_sub` is the creator. For scenario (b), immediate cancellation is the appropriate behaviour because the creator is gone; no "cancel at period end" grace.

```python
# app/services/account_deletion.py

def _cancel_active_subscriptions(user_sub: str) -> int:
    """Cancel all active subscriptions as subscriber and as creator.

    Returns total count of subscriptions transitioned to 'canceled'.
    """
    from boto3.dynamodb.conditions import Key
    from app.core.time import now_ts

    ACTIVE_STATUSES = {"active", "trialing", "past_due", "canceling"}
    cancelled = 0
    ts = now_ts()

    def _fetch_subscription_ids_for_pk(pk_value: str) -> list[str]:
        ids: list[str] = []
        last_key = None
        while True:
            kwargs: dict = {
                "KeyConditionExpression": Key("pk").eq(pk_value),
            }
            if last_key:
                kwargs["ExclusiveStartKey"] = last_key
            resp = T.subscriptions.query(**kwargs)
            for item in resp.get("Items", []):
                sk = item.get("sk", "")
                if sk.startswith("SUB#"):
                    ids.append(sk[4:])  # strip "SUB#" prefix
            last_key = resp.get("LastEvaluatedKey")
            if not last_key:
                break
        return ids

    def _cancel_one(subscription_id: str) -> bool:
        meta = T.subscriptions.get_item(
            Key={"pk": f"SUB#{subscription_id}", "sk": "META"}  # pk_subscription() = "SUB#{id}"
        ).get("Item")
        if not meta:
            return False
        status = meta.get("status", "")
        if status not in ACTIVE_STATUSES:
            return False
        # Immediate cancellation — the user's account no longer exists
        T.subscriptions.update_item(
            Key={"pk": f"SUB#{subscription_id}", "sk": "META"},  # pk_subscription() = "SUB#{id}"
            UpdateExpression=(
                "SET #s = :canceled, auto_renew = :f, "
                "cancel_at_period_end = :f, updated_at = :t, "
                "cancelled_reason = :reason"
            ),
            ExpressionAttributeNames={"#s": "status"},
            ExpressionAttributeValues={
                ":canceled": "canceled",
                ":f": False,
                ":t": ts,
                ":reason": "account_deleted",
            },
        )
        logger.info(
            "privacy.subscription_cancelled subscription=%s user=%s",
            subscription_id, user_sub,
        )
        return True

    # Cancel as subscriber
    for sub_id in _fetch_subscription_ids_for_pk(f"SUBSCRIBER#{user_sub}"):
        if _cancel_one(sub_id):
            cancelled += 1

    # Cancel as creator
    for sub_id in _fetch_subscription_ids_for_pk(f"CREATOR#{user_sub}"):
        if _cancel_one(sub_id):
            cancelled += 1

    return cancelled
```

### 4b. Wire into `finalize_deletion` (before the destructive block)

Subscription cancellation, like message anonymisation, must run regardless of `account_deletion_destructive`. The user has a right to stop being billed even if full destructive wipe is disabled:

```python
summary: Dict[str, Any] = {
    "wallet_refunded_cents": _refund_wallet(user_sub),
    "destructive": bool(S.account_deletion_destructive),
    "profile_deleted": False,
    "messages_anonymized": 0,        # see GAP-0331
    "posts_anonymized": 0,           # see GAP-0331
    "files_deleted": 0,              # see GAP-0340
    "push_devices_deleted": 0,
    "subscriptions_cancelled": _cancel_active_subscriptions(user_sub),  # fixed
}
```

### 4c. Notification to subscribers when a creator account is deleted

When cancellation is triggered by creator deletion, active subscribers lose a service they paid for. A notification should be emitted:

```python
# Inside _cancel_one, after successful update_item, when user_sub == creator
if meta.get("creator_id") == user_sub:
    subscriber_id = meta.get("subscriber_id", "")
    if subscriber_id:
        try:
            from app.services.alerts import write_alert
            write_alert(
                subscriber_id,
                event="subscription_creator_deleted",
                outcome="info",
                title="Creator account closed",
                details={
                    "subscription_id": subscription_id,
                    "message": "The creator whose content you subscribed to has closed their account. Your subscription has been cancelled.",
                },
            )
        except Exception:
            logger.exception("creator-deleted subscription alert failed sub=%s", subscription_id)
```

### 4d. Dev/Prod parity (SECOPS-007)

The helper uses `T.subscriptions` from `app/core/tables.py`, which resolves to DynamoDB Local in dev (via `DDB_ENDPOINT_URL`) and real DynamoDB in prod — the same code path, no environment-specific branching required. The `T` table handles are already environment-aware through the settings layer. No new AWS service dependency is introduced. All operations (query, get_item, update_item) work identically with moto in unit tests.

### 4e. Alternatives considered

- **Delegate to `cancel_subscription` HTTP endpoint (internal call)**: Would trigger the full notification/audit trail of the endpoint, but creates an internal HTTP call from a service, which introduces latency, potential circular dependency, and complexity in testing. Rejected in favour of direct DynamoDB writes.
- **Soft-cancel only (cancel_at_period_end)**: Leaves the subscription `canceling` until period end, during which billing may still fire. Given the user has exercised a legal deletion right, immediate cancellation is appropriate. Rejected.
- **Skip creator-side cancellation**: Creator subscriptions could be handled by a separate cleanup job. But the atomicity benefit of handling both in `finalize_deletion` outweighs the added complexity of a separate job. Rejected.

### Observability

- `privacy.subscription_cancelled subscription={id} user={sub}` logged at INFO level per cancellation.
- `privacy.subscriptions_cancelled_total user={sub} count={n}` logged at INFO level at end of `_cancel_active_subscriptions`.
- `deletion_summary.subscriptions_cancelled` stored durably in DynamoDB per request.

### Rollback

Once subscriptions are cancelled, they cannot be automatically reinstated — this mirrors a user-initiated cancellation. If finalization is reversed (e.g. admin un-deletes an account), subscriptions must be manually or programmatically reactivated. Rollback of the code change itself (disabling `_cancel_active_subscriptions`) stops future deletion requests from cancelling subscriptions; it does not affect already-processed ones.

### Risks

- **Creator with many subscribers**: If a creator deletes their account, potentially thousands of subscriber `META` records must be updated. The loop is O(n) DDB operations. For large creators this could be slow. Mitigation: implement as a paginated background task with progress tracking, or cap per-deletion run and retry.
- **Race with in-flight renewals**: If a subscription renewal fires concurrently with `_cancel_one`, the renewal may succeed before the status is updated. Mitigation: use a DynamoDB conditional write (`ConditionExpression: attribute_not_exists(cancelled_reason)`) in `_cancel_one` to make the operation idempotent.
- **Subscriber notification spam**: If a popular creator deletes and has 10,000 subscribers, 10,000 alerts fire simultaneously. Mitigation: rate-limit alert emission or batch via the existing mass-notification pipeline.

### Effort & sequencing

**Effort**: S (Small) — the data model is already well-understood; the helper is a straightforward DDB query + update loop. Core implementation: ~2 hours. Tests: ~2 hours. Total: ~half a day. Should be sequenced in the same "deletion cascade completeness" sprint as GAP-0331, GAP-0340, and GAP-0341.

### Additional coverage — external subscriptions

The subscription system supports three billing providers: Stripe (native subscriptions), PayPal (external), and CCBill (external). `_cancel_active_subscriptions` above handles native subscriptions stored under the `SUBSCRIBER#` and `CREATOR#` PK prefixes in the `subscriptions` table. PayPal subscriptions stored in the `billing` table under a user-specific PK, and CCBill subscriptions stored via `_billing_query_by_user_sub`, are not addressed. A complete fix should extend `_cancel_active_subscriptions` to also call the provider-specific cancellation flows (or at minimum mark those records as `status=canceled` so the renewal cycle engine skips them).

For the MVP of this fix, native subscriptions are the critical path. External provider cancellations (PayPal, CCBill) are tracked under a follow-on ticket because they involve outbound API calls and must respect SECOPS-007 (dev/prod parity via mock providers in dev, real provider API in prod).

### Interaction with `subscription_cycle_orders.py`

The subscription renewal engine in `app/services/subscription_cycle_orders.py` queries active subscriptions by PK prefix. Once `_cancel_active_subscriptions` sets `status="canceled"` on all relevant META records, the renewal engine will skip them on subsequent runs. No additional change to the cycle engine is needed — it already gates renewal attempts on `status in {"active", "trialing", "past_due"}` and will see `"canceled"` and move on. This is an important correctness property: the fix is sufficient to stop future billing without any change to the billing cycle code.

### Idempotency

`_cancel_one` already checks `if status not in ACTIVE_STATUSES: return False` before writing. A `ConditionExpression` can strengthen this:

```python
T.subscriptions.update_item(
    Key={"pk": f"SUB#{subscription_id}", "sk": "META"},  # pk_subscription() = "SUB#{id}"
    UpdateExpression=...,
    ConditionExpression=Attr("status").is_in(["active", "trialing", "past_due", "canceling"]),
    ExpressionAttributeValues=...,
)
```

This makes re-entrant calls (e.g. if `finalize_deletion` is retried due to a transient error) safe: the second attempt sees `status="canceled"` and the condition fails, raising `ConditionalCheckFailedException`. Catch that exception and return `False` to treat it as a no-op rather than an error.
