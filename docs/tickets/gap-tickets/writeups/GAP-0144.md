# GAP-0144: No Automatic `call.end` Signal Sent to Remote Peer on `failure` Phase — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Gap statement**: When a WebRTC call enters the `failure` phase on one peer (all ICE restart attempts exhausted, `RECONNECT_ATTEMPT` transitions to `failure` in `callStateMachine.ts:116-119`), the local peer tears down its RTC resources and shows an error overlay. However, no `POST /messages/calls/{call_id}/end` request is sent to the backend, and no SSE `call.end` event is fanned out to the remote peer. The remote peer's overlay therefore remains stuck in `connected` or `reconnecting` indefinitely until the stale-session scan clears the DynamoDB record.

- **Severity**: HIGH
- **Source ticket**: CALL-008
- **Status**: Open — confirmed in production code.
- **Owning area**: `frontend/src/pages/messages/ConversationView.tsx`
- **Investigation verdict**: Claim is fully confirmed. The existing `useEffect` at `ConversationView.tsx:752-756` calls `teardownCallResources` when the phase reaches `failure`, but no API call is made. The `callActionMutation` at line 772-778 supports `action: "end"` but is never invoked for the `failure` phase. Every other terminal phase (`ended`, `declined`, `busy`, `timeout`) transitions through explicit user action or an SSE event from the backend; `failure` is the only machine-generated terminal phase that silently ends.
- **Related tickets**: CALL-008 parent, CALL-007 (related stale-invite cleanup), GAP-0143.

## 2. Current-State Investigation (root cause)

### 2.1 The `failure` phase transition

`callStateMachine.ts:115-120`:

```typescript
case "RECONNECT_ATTEMPT": {
    if (state.phase !== "reconnecting") return state;
    if (!state.isOnline || !state.isTabVisible || state.retryCount >= state.maxRetries) {
        return withPhase(state, "failure", { reasonMessage: "Call failed to reconnect." });
    }
    return withPhase(state, "outgoing_connecting", { retryCount: state.retryCount + 1, ... });
}
```

`failure` is also reachable via `FAIL` directly (`callStateMachine.ts:153-156`) when `useRtcPeerConnection` dispatches a fatal error.

### 2.2 What happens on `failure` today

`ConversationView.tsx:752-756`:

```typescript
React.useEffect(() => {
    if (["ended", "failed", "failure", "declined", "busy", "timeout", "idle"]
        .includes(callMachine.phase)) {
        teardownCallResources(callResourcesRef.current);
    }
}, [callMachine.phase]);
```

`teardownCallResources` closes the `RTCPeerConnection`, stops media tracks, and clears attached listeners (`callStateMachine.ts:199-222`). This is purely local cleanup. No HTTP request is made. No SSE event is dispatched.

### 2.3 `callActionMutation` exists but is not called for `failure`

`ConversationView.tsx:772-778`:

```typescript
const callActionMutation = useMutation({
    mutationFn: async (args: { action: "accept" | "decline" | "end"; callId: string }) => {
        if (args.action === "accept")  return acceptCallInvite(args.callId, ...);
        if (args.action === "decline") return declineCallInvite(args.callId, ...);
        return endCall(args.callId, { reason: "ended", ... });
    },
});
```

Calling `callActionMutation.mutate({ action: "end", callId: ..., reason: "reconnect_failed" })` is the correct mechanism to end the call on the backend. This mutation is already invoked when the user explicitly taps "End call" (line 1373 area). The gap is that it is never triggered automatically on `phase === "failure"`.

### 2.4 Backend behaviour without the signal

When the `failure` phase fires locally without a `POST /messages/calls/{call_id}/end`:
- The DynamoDB `MessageCallSessions` record remains in state `"connected"` (or `"reconnecting"` if the server received a `CONNECTION_LOST` signal — but no such signal exists from the client either).
- The remote peer receives no SSE `call.end` event.
- The remote peer's overlay shows `reconnecting` or `connected` indefinitely.
- Only the background `_expire_stale_invites` loop eventually clears the record — but that loop only handles `invited` state, not `connected`. A stale `connected` record is never cleaned up by the current backstop.

### 2.5 `callId` availability in the `failure` phase

When `failure` is reached, `callMachine.callId` is still populated — it was set in `OUTGOING_RINGING` (`callStateMachine.ts:81`) and never cleared. The `useEffect` can safely read `callMachine.callId`.

## 3. Impact / Exploit / Blast Radius

**Remote peer stuck**: The remote peer's call overlay stays open indefinitely. The user sees a ringing or connected overlay for a call that has already failed on the other side. There is no automatic resolution — the remote peer must close the conversation view or restart the app.

**DynamoDB record never closed**: The call session record in `MessageCallSessions` remains in a non-terminal state indefinitely. This skews call-duration analytics, prevents the billing timer (`app/services/call_billing_timer.py`) from finalising charges, and holds a DDB record open that would be counted as an "active call" by any monitoring query.

**Billing impact**: If the platform charges per-minute for calls, a call that ends in `failure` on the local peer but has no `call.end` signal to the backend causes the billing timer to continue accruing time against the remote peer indefinitely. Depending on the billing cutoff logic, this could result in overcharges.

**Stale session accumulation**: Over time, failed calls accumulate as non-terminal records. There is no cleanup backstop for `connected` state analogous to `_expire_stale_invites` for `invited`. This could cause the `list_call_sessions` scan to return stale records, inflating response sizes.

**Blast radius**: Any call in which the reconnection path exhausts retries (2 retries with 1-second debounce — approximately 3-4 seconds from connection loss to `failure`). Mobile clients on flaky networks are the primary affected population.

## 4. Fix Design (code-level)

### 4.1 New `useEffect` for `failure` phase

Add a new `useEffect` immediately after the teardown effect at `ConversationView.tsx:752-756`. It must fire after teardown (resources are already cleaned up) and should send the `call.end` signal best-effort:

```typescript
// GAP-0144: on failure, signal the backend so remote peer is notified
React.useEffect(() => {
    if (callMachine.phase !== "failure") return;
    const cid = callMachine.callId;
    if (!cid) return;

    callActionMutation.mutate(
        { action: "end", callId: cid },
        {
            onError: () => {
                // Best-effort — the stale-session backstop will eventually
                // clean up if this POST fails (e.g., the network is down).
            },
        },
    );
    // No onSuccess needed: END_REMOTE will arrive from SSE fanout on the
    // remote peer side; local peer is already in `failure` (terminal).
}, [callMachine.phase, callMachine.callId]);
// Note: callActionMutation is stable (useMutation returns stable ref)
// so it does not need to appear in deps to avoid re-firing.
```

### 4.2 Backend `end_call` endpoint

The backend endpoint `POST /messages/calls/{call_id}/end` (implemented by CALL-005/008) transitions the call to `ended`, writes a `call.end` timeline event, and fans out via `fanout_event_to_conversation`. The remote peer's SSE handler at `ConversationView.tsx:885-887` dispatches `END_REMOTE`:

```typescript
} else if (eventType === "call.end") {
    dispatchCall({ type: "END_REMOTE" });
}
```

This is the correct chain: `failure` → `POST call.end` → backend fans out `call.end` SSE → remote peer dispatches `END_REMOTE` → remote overlay closes.

### 4.3 `reason` field

The `endCall` API accepts a `reason` field. Pass `"reconnect_failed"` to distinguish programmatic failure-phase endings from explicit user "hang up" calls (which use `"ended"`). This allows call analytics to separate ICE failures from user-initiated ends.

The `mutationFn` at line 776 passes `reason: "ended"` for the `"end"` action unconditionally:

```typescript
return endCall(args.callId, { reason: "ended", idempotency_key: `ui-end-${Date.now()}` });
```

To preserve the reason, extend the `args` type:

```typescript
const callActionMutation = useMutation({
    mutationFn: async (args: {
        action: "accept" | "decline" | "end";
        callId: string;
        reason?: string;  // new optional field
    }) => {
        if (args.action === "accept")  return acceptCallInvite(args.callId, ...);
        if (args.action === "decline") return declineCallInvite(args.callId, ...);
        return endCall(args.callId, {
            reason: args.reason ?? "ended",
            idempotency_key: `ui-end-${Date.now()}`,
        });
    },
});
```

Then the `failure` effect calls:

```typescript
callActionMutation.mutate(
    { action: "end", callId: cid, reason: "reconnect_failed" },
    { onError: () => {} },
);
```

### 4.4 Stale-session backstop enhancement (separate follow-up)

The backend `_expire_stale_invites` at `messaging.py:13318` only handles `state = "invited"`. A companion backstop for `state = "connected"` with a max-call-duration guard (e.g., 4 hours) should be added, but that is a separate medium-effort ticket and is not in scope for this HIGH gap fix.

### 4.5 Dev/prod parity (SECOPS-007)

This is a pure frontend change calling an existing endpoint that already works in both dev and prod. No backend changes; no mock/flag differences.

### 4.6 Idempotency

The `endCall` mutation passes a unique idempotency key (`ui-end-${Date.now()}`). If the `failure` effect fires more than once (React strict mode renders effects twice in development), the second call will be rejected with `409 already_ended` by the backend, which is handled gracefully by the `onError` handler.

### 4.7 Alternatives considered

- **Add a dedicated `POST /messages/calls/{call_id}/failure` endpoint**: Semantically cleaner but requires a new backend endpoint, DDB state, and SSE event type. The existing `call.end` path already does everything needed. Rejected in favour of reuse.
- **Fire `END_LOCAL` and let the user-end flow handle it**: `END_LOCAL` transitions to `ended` (not `failure`). This hides the failure reason from analytics. Rejected.
- **Let the stale-session backstop clean up**: The existing backstop only handles `invited` state; `connected` sessions are never cleaned up by the current implementation. Even if a backstop for `connected` were added, the resolution delay would be minutes to hours versus sub-second with the explicit signal. Rejected as primary mechanism.

## 5. Testing, Verification & Rollout

### 5.1 Regression test — Jest / React Testing Library

```typescript
// src/pages/messages/__tests__/ConversationView.failureSignal.test.tsx
import { render, act } from "@testing-library/react";
import { rest } from "msw";
import { setupServer } from "msw/node";

const CALL_ID = "call_fail_test";
let endCallCalls: string[] = [];

const server = setupServer(
    rest.post(`/messages/calls/:callId/end`, (req, res, ctx) => {
        endCallCalls.push(req.params.callId as string);
        return res(ctx.json({ ok: true }));
    }),
);

beforeAll(() => server.listen());
afterAll(() => server.close());
beforeEach(() => { endCallCalls = []; });

test("failure phase triggers POST call.end to backend", async () => {
    // Render ConversationView in a connected call phase
    const { dispatchCall } = renderConversationViewInPhase("connected", CALL_ID);

    // Simulate connection lost → RECONNECT_ATTEMPT × 3 → failure
    act(() => { dispatchCall({ type: "CONNECTION_LOST" }); });
    act(() => { dispatchCall({ type: "RECONNECT_ATTEMPT" }); }); // retryCount=1
    act(() => { dispatchCall({ type: "RECONNECT_ATTEMPT" }); }); // retryCount=2
    act(() => { dispatchCall({ type: "RECONNECT_ATTEMPT" }); }); // retryCount=3 → failure

    // Allow async mutation to fire
    await act(async () => { await new Promise(r => setTimeout(r, 0)); });

    expect(endCallCalls).toContain(CALL_ID);

    // FAILS-BEFORE: endCallCalls is empty → assertion fails
    // PASSES-AFTER: useEffect fires callActionMutation on failure → POST sent
});

test("failure phase sends reason=reconnect_failed", async () => {
    let capturedBody: Record<string, unknown> = {};
    server.use(
        rest.post(`/messages/calls/:callId/end`, async (req, res, ctx) => {
            capturedBody = await req.json();
            return res(ctx.json({ ok: true }));
        }),
    );
    const { dispatchCall } = renderConversationViewInPhase("connected", CALL_ID);
    act(() => { dispatchCall({ type: "FAIL", message: "ICE failed" }); });
    await act(async () => { await new Promise(r => setTimeout(r, 0)); });
    expect(capturedBody.reason).toBe("reconnect_failed");
});
```

2. In Alice's tab, open DevTools → Application → Service Workers → simulate offline **or** use DevTools → Network → block `*.webrtc.*` to force ICE failure.
3. Wait for Alice's overlay to show the reconnecting spinner, then the failure banner.
4. Confirm Bob's overlay transitions from `connected` → `ended` (overlay closes or shows "Call ended") within 3 seconds.
5. Check DynamoDB: the call session record should have `state=ended`.
6. Check the conversation timeline: a "Call ended (reconnect_failed)" system message should appear for both parties.

### 5.4 Observability

- Add a telemetry event `call_failure_end_signal_sent` with `call_id` and `reason`.
- Add a backend counter `call_end_reason_reconnect_failed_total` to distinguish from user-initiated ends in metrics.
- Alert if `call_failure_end_signal_sent` events exist without corresponding `call_end` lifecycle events in DDB (indicating the POST is failing silently).

### 5.5 Rollout

- **Effort**: S (30-45 minutes — one new `useEffect`, one optional `args` type extension)
- **Risk**: Low. The `endCall` API is idempotent (idempotency key prevents double-end). The only edge case is if the call is already `ended` on the backend (remote peer hung up simultaneously) — the 409 response is swallowed by `onError`. The local peer is already in `failure` regardless.
- **Rollback**: Remove the new `useEffect`. Remote-peer overlay behaviour regresses to the prior indefinite-stuck state.
- **Sequencing**: Can ship independently. Coordinate with CALL-008 parent ticket which may introduce additional reconnection changes.
