# GAP-0286: Per-API-key rate limiting is completely absent from all partner API endpoints — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/routers/kyc_partner_api.py` and
> `app/services/rate_limit.py`.

## 1. Summary & Classification

**Plain-English statement**: Every endpoint in the KYC Partner API (`/api/v1/kyc/…`) is
reachable by any holder of a valid API key at unlimited throughput. There is no per-key hourly
cap on application creation, document uploads, GET reads, or webhook test requests. A partner
whose key is compromised — or a misbehaving integration — can generate unbounded KYC case
volume, saturate DynamoDB write capacity, or brute-force idempotency-key collisions.

- **Severity**: HIGH
- **Source ticket**: KYC-021
- **Owning area**: KYC Platform / Partner Integrations
- **Status**: Open — no rate-limiting code is present in the router or service layer
- **Claim accuracy**: Confirmed exactly. `app/routers/kyc_partner_api.py` has zero calls to
  any rate-limiting helper for all nine route handlers (lines 62–252).

**Impact in one line**: An unconstrained partner can create thousands of KYC cases per hour,
exhausting DynamoDB provisioned write capacity and inflating operational cost.

**Related tickets**: GAP-0287 (document bytes not stored), KYC-021 write-up,
`app/services/rate_limit.py` infrastructure (already used by MFA, login, admin-action flows).

## 2. Current-State Investigation (root cause)

### Router — zero rate-limiting calls

`app/routers/kyc_partner_api.py` defines nine route handlers:

| Handler | Line | Limit needed (per KYC-021 §4.7) |
|---|---|---|
| `create_application` | 62 | 100 / hour |
| `list_or_lookup_applications` | 114 | 1 000 / hour |
| `get_application` | 127 | 1 000 / hour |
| `get_application_result` | 136 | 1 000 / hour |
| `submit_application` | 145 | 100 / hour |
| `upload_document` | 175 | 200 / hour |
| `register_webhook` | 217 | 50 / hour (reasonable default) |
| `list_webhooks` | 228 | 1 000 / hour |
| `test_webhook` | 246 | **10 / hour** (most sensitive) |

None of these call any rate-limiting function. The only protection is scope checking
(`svc.require_scope`) which only validates _what_ the key can do, not _how often_.

### Rate-limiting infrastructure already exists

`app/services/rate_limit.py` contains two relevant helpers:

**`rate_limit_or_429(user_sub, factor)`** (line 17) — hard-coded to
`S.mfa_send_max_per_hour` and `S.mfa_send_min_interval_seconds`. These are MFA-tuned
values and are not appropriate for per-partner API caps.

**`_bucket_limit(user_sub, sid, max_n, win)`** (line 60) — generic sliding-window
counter keyed by `(user_sub, session_id)` with configurable `max_n` requests per `win`
seconds. This is the correct primitive to use. It is already used by login, MFA verify,
profile lookup, feed query, and file-manager mount flows.

**Claim note in the source GAP ticket**: The ticket recommends calling
`rate_limit_or_429(user_sub=f"apikey:{api_key_id}", ...)`. That helper hard-codes the
limit to `S.mfa_send_max_per_hour` (default 20/hour), which is far below the 100–1 000
targets specified in KYC-021 §4.7. The correct approach is a dedicated
`rate_limit_kyc_partner_api()` wrapper that calls `_bucket_limit` with endpoint-specific
caps, or direct `_bucket_limit` calls with named environment-variable caps.

### Runtime behaviour today

- A partner with `kyc:submit` scope can call `POST /api/v1/kyc/applications` in a tight
  loop, creating a KYC case and a DynamoDB write on every call.
- `POST /api/v1/kyc/webhooks/{id}/test` dispatches an outbound webhook delivery on every
  call — 10/hour is the spec limit; today it is unbounded.
- Idempotency guards only deduplicate identical requests (same key + same body fingerprint).
  A loop using a fresh `Idempotency-Key` per request bypasses them entirely.

## 3. Impact / Exploit / Blast Radius

### Financial / operational

1. A partner (or attacker who steals a partner key) issues 10 000 `POST /applications`
   requests in an hour. Each creates a real KYC case via `kyc_cases.STORE.create_case`,
   writing two DynamoDB items. At DynamoDB on-demand pricing, 20 000 writes per second is
   well within capacity but will spike costs and appear as real cases in the admin queue.
2. Webhook test spam: `POST /webhooks/{id}/test` calls `_emit_callback` which synchronously
   invokes the KYC webhook delivery path. Without a cap this can be used to flood a
   partner's own webhook receiver or trigger excessive outbound HTTP traffic from the
   platform.
3. `GET /applications` and `GET /applications/{id}/result` call
   `_refresh_status_from_case` which does an extra DynamoDB `get_item` per call. A burst
   of 10 000 GETs will spike read capacity.

### Security

A compromised or leaked partner API key with `kyc:submit` scope — which might be
extracted from a partner's CI secrets — can flood the KYC queue with fraudulent draft
applications until the key is revoked. Because idempotency records only live 24 hours,
a sustained attack spans multiple TTL windows.

### Blast radius

All partners sharing the `kyc_cases` DynamoDB table are affected. Provisioned capacity
exhaustion or throttling on that table degrades the internal KYC admin UI and reviewer
workflows simultaneously.

## 4. Fix Design (code-level)

### Step 1 — Add a dedicated rate-limit helper in `app/services/rate_limit.py`

```python
# KYC-021 §4.7 — per-API-key limits (env-var overridable)
_KYC_LIMITS: dict[str, tuple[int, int]] = {
    # factor_suffix: (max_per_window, window_seconds)
    "kyc_api:applications:write": (_env_int("KYC_API_APPLICATIONS_WRITE_MAX", 100), 3600),
    "kyc_api:applications:read":  (_env_int("KYC_API_APPLICATIONS_READ_MAX", 1000), 3600),
    "kyc_api:documents":          (_env_int("KYC_API_DOCUMENTS_MAX", 200), 3600),
    "kyc_api:webhooks:test":      (_env_int("KYC_API_WEBHOOKS_TEST_MAX", 10), 3600),
    "kyc_api:webhooks:write":     (_env_int("KYC_API_WEBHOOKS_WRITE_MAX", 50), 3600),
    "kyc_api:webhooks:read":      (_env_int("KYC_API_WEBHOOKS_READ_MAX", 1000), 3600),
}

def rate_limit_kyc_partner(api_key_id: str, factor: str) -> None:
    """Raise 429 if the API key has exceeded its per-hour quota for `factor`."""
    max_n, win = _KYC_LIMITS.get(factor, (200, 3600))
    sid = f"rl#{factor}"
    if not _bucket_limit(f"apikey:{api_key_id}", sid, max_n, win):
        raise HTTPException(
            status_code=429,
            detail={
                "code": "kyc_api_rate_limited",
                "message": f"Rate limit exceeded for {factor}",
                "retry_after_seconds": win,
            },
            headers={"Retry-After": str(win)},
        )
```

### Step 2 — Call the helper at the top of each handler in `app/routers/kyc_partner_api.py`

```python
from app.services.rate_limit import rate_limit_kyc_partner

@kyc_partner_api_router.post("/applications", status_code=201)
async def create_application(
    body: KycPartnerApplicationCreateIn,
    request: Request,
    principal: Dict[str, Any] = Depends(require_api_key_principal),
    idempotency_key: Optional[str] = Header(default=None, alias="Idempotency-Key"),
):
    svc.require_scope(principal, "kyc:submit")
    rate_limit_kyc_partner(str(principal.get("api_key_id") or ""), "kyc_api:applications:write")
    # ... rest unchanged

@kyc_partner_api_router.post("/applications/{application_id}/documents", status_code=201)
async def upload_document(...):
    svc.require_scope(principal, "kyc:upload")
    rate_limit_kyc_partner(str(principal.get("api_key_id") or ""), "kyc_api:documents")
    # ...

@kyc_partner_api_router.post("/webhooks/{webhook_id}/test")
async def test_webhook(...):
    svc.require_scope(principal, "kyc:webhook")
    rate_limit_kyc_partner(str(principal.get("api_key_id") or ""), "kyc_api:webhooks:test")
    # ...
```

The same pattern applies to all nine handlers using the factor names from `_KYC_LIMITS`.

### How `_bucket_limit` works at runtime

For each call, `_bucket_limit` reads the current bucket item from DynamoDB, compares
`bucket_start` + `bucket_count` against the window, and either resets (new window) or
increments. It uses `put_item` (not a conditional `update_item`), so there is a small
race window under high concurrency — two near-simultaneous calls could both read `count
= 99` (limit = 100) and both succeed. This is an acceptable approximation for
per-partner limits; the existing MFA and login flows have the same property. For strict
per-call accounting, a `ConditionalExpression` version like `rate_limit_or_429` would be
needed, but the soft counter is appropriate here given the high per-hour limits.

### Dev/Prod parity (SECOPS-007)

`_bucket_limit` already short-circuits to `return True` when
`_sessions_table_enabled()` returns `False` (i.e., when `S.ddb_sessions_table` is
empty). This means the rate-limiter is a no-op in test environments that do not configure
the sessions table. In the local dev stack, `S.ddb_sessions_table` is set (default
`"sessions"`) so the limiter is active — which is the correct behaviour for integration
testing.

No separate mock path is needed. The moto-backed DynamoDB in local dev accepts the same
`update_item` / `put_item` calls as production AWS DynamoDB.

The new `_KYC_LIMITS` constants are all driven by environment variables with sensible
production defaults. To raise limits for a high-volume partner in production, operators
set `KYC_API_APPLICATIONS_WRITE_MAX=500` etc. in the application's environment without
a code deployment.

### Alternatives considered

- **Using `rate_limit_or_429`**: Rejected. That function hard-codes `S.mfa_send_max_per_hour`
  (default 20/hour) and enforces a per-send minimum interval suited for OTP delivery, not
  for bulk API throughput.
- **Middleware-level rate limiting (e.g., slowapi)**: Would require a new library
  dependency and cannot be cleanly scoped per-API-key without significant plumbing. The
  existing `_bucket_limit` DynamoDB approach is already battle-tested on this platform.
- **API Gateway throttling in production**: A valid complementary layer, but not a
  substitute for application-level limits that are portable across deployment targets.

### Backward compatibility

No migration is needed. `_bucket_limit` creates new DynamoDB items on first use. Existing
partners will be subject to the new limit from the first call after deployment. For a
one-time grace period, `KYC_API_APPLICATIONS_WRITE_MAX` can be temporarily set high
during the rollout period.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline — fails before fix, passes after)

```python
# tests/test_kyc_partner_api_rate_limit.py
import pytest
from unittest.mock import patch, MagicMock

def _make_client(app):
    from fastapi.testclient import TestClient
    return TestClient(app)

def test_rate_limit_create_application_enforced(test_client, kyc_partner_principal):
    """POST /applications should 429 after exceeding per-key hourly limit."""
    call_count = 0
    def fake_bucket_limit(user_sub, sid, max_n, win):
        nonlocal call_count
        call_count += 1
        return call_count <= 1  # allow first, deny subsequent

    with patch("app.services.rate_limit._bucket_limit", side_effect=fake_bucket_limit):
        r1 = test_client.post(
            "/api/v1/kyc/applications",
            json={"external_id": "eid-1", "applicant": {"name": "A"}, "tier": "tier_1"},
            headers={"Authorization": "ApiKey testkey", "Idempotency-Key": "k1"},
        )
        assert r1.status_code != 429  # first call passes

        r2 = test_client.post(
            "/api/v1/kyc/applications",
            json={"external_id": "eid-2", "applicant": {"name": "B"}, "tier": "tier_1"},
            headers={"Authorization": "ApiKey testkey", "Idempotency-Key": "k2"},
        )
        assert r2.status_code == 429
        assert r2.json()["detail"]["code"] == "kyc_api_rate_limited"

def test_webhook_test_rate_limited(test_client, kyc_partner_principal):
    """POST /webhooks/{id}/test should 429 after 10 calls in an hour."""
    with patch("app.services.rate_limit._bucket_limit", return_value=False):
        r = test_client.post(
            "/api/v1/kyc/webhooks/wh_test/test",
            headers={"Authorization": "ApiKey testkey"},
        )
        assert r.status_code == 429
        body = r.json()
        assert body["detail"]["retry_after_seconds"] == 3600
```

**Before fix**: Both assertions on `status_code == 429` fail (responses are 404 or 200).
**After fix**: All assertions pass.

### Manual QA steps

1. Start the local dev stack (`just up`).
2. Create a partner API key with `kyc:submit` scope using the admin CLI
   (`scripts/rootctl apikey create --scope kyc:submit`).
3. Run a burst loop:
   ```bash
   for i in $(seq 1 105); do
     curl -s -o /dev/null -w "%{http_code}\n" \
       -X POST http://localhost:8000/api/v1/kyc/applications \
       -H "Authorization: ApiKey $KEY" \
       -H "Content-Type: application/json" \
       -H "Idempotency-Key: test-$i" \
       -d '{"external_id":"eid-'$i'","applicant":{"name":"A"},"tier":"tier_1"}'
   done
   ```
   Verify that requests 1–100 return 201, requests 101+ return 429.
4. Confirm the 429 response body is
   `{"detail":{"code":"kyc_api_rate_limited","retry_after_seconds":3600}}`.
5. Verify `Retry-After: 3600` header is present on 429 responses.
6. Test the `test_webhook` endpoint: send 11 requests within an hour; confirm the
   11th returns 429 (limit = 10).
7. Verify that different API key IDs each get their own independent counter — two keys
   can each send 100 applications without interfering with each other.

### Observability

- Add a `rate_limited_kyc_api_total` counter incremented in `rate_limit_kyc_partner` on
  rejection, labelled by `factor` and `api_key_id_prefix` (first 8 chars of hashed key).
- Alert when `rate_limited_kyc_api_total{factor="kyc_api:webhooks:test"}` exceeds 5
  distinct keys in a 5-minute window — indicates coordinated abuse.
- Log at `INFO` level when a partner crosses 80% of their hourly limit (i.e., `count ==
  int(0.8 * max_n)`) so the platform team can reach out proactively before the partner
  hits a hard wall. This requires adding an 80% threshold read after the `_bucket_limit`
  call, reading the current count from DynamoDB. Alternatively, expose a
  `GET /api/v1/kyc/quota` endpoint that returns current usage / limits per factor so
  partners can self-monitor.

### Rate-limit header response standard

Add `Retry-After` and `X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset`
headers to all 429 responses from `rate_limit_kyc_partner`. These headers follow
RFC 6585 and are expected by well-behaved HTTP clients with built-in retry logic:

```python
raise HTTPException(
    status_code=429,
    detail={
        "code": "kyc_api_rate_limited",
        "message": f"Rate limit exceeded for {factor}. Limit: {max_n}/hour.",
        "retry_after_seconds": win,
    },
    headers={
        "Retry-After": str(win),
        "X-RateLimit-Limit": str(max_n),
        "X-RateLimit-Remaining": "0",
        "X-RateLimit-Reset": str(now_ts() + win),
    },
)

### Rollout

1. Merge `rate_limit_kyc_partner` helper to `app/services/rate_limit.py`.
2. Merge router changes to `app/routers/kyc_partner_api.py`.
3. Deploy to staging; validate with the QA steps above.
4. Set `KYC_API_APPLICATIONS_WRITE_MAX` / `KYC_API_DOCUMENTS_MAX` etc. in production
   environment config before enabling the flag.
5. Monitor `429` rates for 24 hours post-deploy; adjust caps if any production partner
   is legitimately exceeding the defaults.

**Effort**: S (2–3 hours implementation + tests).
**Risk**: Low. New limits default to values above observed production traffic.
**Sequencing**: Can be shipped independently; no dependency on GAP-0287.
