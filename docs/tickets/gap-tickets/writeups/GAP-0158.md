# GAP-0158: Banned delegate bypasses account ban via API key path — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement.** The `authenticate_key` function in
`app/services/delegation_api.py:208` validates a delegation API key by
checking that the key is not revoked/expired, that the secret hash matches,
and that the underlying delegation relationship is still active. It does not
check whether the `owner_sub` (the delegate who holds the key) is subject
to a platform-wide account ban. As a result, a banned user can continue to
make authenticated API calls to every endpoint guarded by the delegation API
key auth path (`/ui/delegation-api/v1/…`) even after their account is
suspended.

**Severity:** HIGH — security enforcement bypass. Account bans are a critical
moderation and compliance tool; leaking through the API key auth path
undermines the ban entirely for technically capable users.  
**Source ticket:** DELEGATE-005  
**Status:** Open  
**Owning area:** Delegation API key authentication, `app/services/delegation_api.py`  
**Effort:** S

**Verdict from code investigation:** Claim confirmed. The ticket identifies
line 241 as the insertion point (after the delegation relationship check at
`get_delegate` on line 239); the code matches exactly. Neither
`is_user_currently_banned` nor any equivalent ban check appears anywhere in
`authenticate_key`.

**Note on the ban target.** The ticket says to check `item["owner_sub"]`
(the delegate/key holder). This is correct: `owner_sub` is the sub of the
delegate who created the key. The `creator_id` in the item is the creator
for whom the delegate acts. The ban being evaded is the delegate's *own*
account ban, not the creator's — confirming the ticket's phrasing.

**Related tickets:** GAP-0156 (missing delegates route), GAP-0157 (broadcast
chat ban bypass), DELEGATE-005.

## 2. Current-State Investigation (root cause)

### `authenticate_key` — full enforcement chain as it exists today

`app/services/delegation_api.py:208-252`:

```python
def authenticate_key(
    *,
    api_key: str,
    client_ip: str,
    required_permission: str,
) -> Dict[str, Any]:
    parsed = _parse_delegation_key(api_key)
    key_id, secret = parsed["key_id"], parsed["secret"]

    item = get_key_item(key_id)
    if not item or item.get("revoked"):
        raise HTTPException(401, "Invalid delegation API key")      # (1)

    expires_at = int(item.get("expires_at") or 0)
    if expires_at and now_ts() > expires_at:
        _do_revoke(key_id)
        raise HTTPException(401, "Delegation API key expired")      # (2)

    if api_key_hash(secret) != item.get("secret_hash"):
        raise HTTPException(401, "Invalid delegation API key")      # (3)

    # The underlying delegation relationship must still be active.
    delegate = get_delegate(item.get("creator_id", ""), item.get("owner_sub", ""))
    if not delegate or delegate.get("status") != "active":
        raise HTTPException(403, "Delegation relationship is no longer active")  # (4)

    if required_permission not in item.get("permissions", []):
        raise HTTPException(403, f"Key does not have permission: ...")   # (5)

    rpm = int(item.get("rate_limit_rpm") or _default_rate_limit_rpm())
    _enforce_key_rate_limit(key_id, rpm)
    _record_usage(key_id, client_ip)

    return item
```

The checks in order: key existence (1), key expiry (2), secret hash (3),
delegation relationship active (4), permission (5). **There is no check (6)
for whether `item["owner_sub"]` is currently banned.**

### Why this bypass exists

The delegation API key was implemented as a *programmatic* auth layer
(`DELEGATE-005`) that runs outside the normal `require_ui_session` path.
`require_ui_session` in `app/auth/deps.py:135` does call
`is_user_currently_banned(user_sub)`, but the delegation API key path uses a
separate dependency — the key is validated in `authenticate_key`, and the
result is injected into the endpoint handler directly. The `require_ui_session`
code is never called for API-key-authenticated requests.

### Where `is_user_currently_banned` lives

`app/services/moderation_policy_engine.py:113`:

```python
def is_user_currently_banned(user_sub: str) -> bool:
    if not user_sub:
        return False
    try:
        item = T.account_state.get_item(Key={"user_sub": user_sub}).get("Item") or {}
    except Exception:
        return False
    if str(item.get("status") or "") != BAN_STATUS:
        return False
    ban_until = _coerce_int(item.get("ban_until"), 0)
    if ban_until > 0 and now_ts() >= ban_until:
        return False
    return True
```

The function is already imported in `app/services/sessions.py`,
`app/auth/deps.py`, and `app/routers/sso_saml.py`. It is **not** imported in
`app/services/delegation_api.py`.

### Scope of API endpoints exposed via delegation key auth

The delegation API key grants access to a defined permission set mapped in
`app/services/delegation_api.py:48-71`:

- `GET /ui/delegation-api/v1/conversations` — read creator's DMs
- `POST /ui/delegation-api/v1/conversations/{cid}/messages` — send message as creator
- `GET /ui/delegation-api/v1/posts`, `POST /ui/delegation-api/v1/posts` — read/create posts
- `POST /ui/delegation-api/v1/posts/{pid}/comments/{cid}/moderate` — moderate content
- `POST /ui/delegation-api/v1/broadcast/{sid}/mute` — mute broadcast viewers
- `POST /ui/delegation-api/v1/broadcast/{sid}/start` — start a broadcast

A banned user retaining all of these capabilities is a severe gap:
they can continue to send messages as the creator, post content, start
broadcasts, and mute other users.

## 3. Impact / Exploit / Blast Radius

**Concrete exploit walkthrough:**

1. Delegate (Bob) has a delegation API key (`dak_<key_id>.<secret>`) issued by
   creator Alice.
2. Bob commits a policy violation; the platform bans his account. This writes
   `status = "banned"` to `T.account_state` for Bob's `user_sub`.
3. Bob's normal browser session (cookie-based) now correctly receives 403 on
   any `require_ui_session`-guarded endpoint.
4. Bob retains his delegation API key credentials (stored locally, not in the
   app). He sends `POST /ui/delegation-api/v1/conversations/{cid}/messages`
   with `Authorization: DelegationKey dak_<key>.<secret>`.
5. `authenticate_key` checks: key not revoked ✓, not expired ✓, hash matches ✓,
   delegation relationship active ✓ (the relationship is still active — only
   Bob's account is banned, not the delegation relationship), permission
   present ✓. The function returns `item`; the message is sent *as creator Alice*.
6. Bob can continue to impersonate Alice for the lifetime of the key.

**Worst-case scenarios:**

- Bob posts harmful content under Alice's account via the delegation API while
  his ban is in effect.
- Bob starts a broadcast session under Alice's name while banned.
- Bob mutes or moderates other users during the ban period.
- If the platform is liable for content posted via Alice's account (creator
  liability), Alice's reputation is harmed by a banned delegate's actions.

**Financial / compliance.** Delegation API keys are programmatic credentials;
they do not expire unless explicitly set. A banned user could retain access
indefinitely until the key is manually revoked. The gap effectively requires
administrators to remember to also revoke all delegation keys of a banned
user — a manual step that is not enforced by the platform and is easy to miss.

## 4. Fix Design (code-level)

### Step 1 — Import `is_user_currently_banned` in `delegation_api.py`

At the top of `app/services/delegation_api.py`, add:

```python
from app.services.moderation_policy_engine import is_user_currently_banned
```

### Step 2 — Insert ban check after delegation relationship check

After line 241 in `authenticate_key` (immediately after the delegation
relationship check):

```python
    delegate = get_delegate(item.get("creator_id", ""), item.get("owner_sub", ""))
    if not delegate or delegate.get("status") != "active":
        raise HTTPException(403, "Delegation relationship is no longer active")

    # GAP-0158: reject if the key holder (delegate) is platform-banned
    owner_sub = item.get("owner_sub", "")
    if is_user_currently_banned(owner_sub):
        raise HTTPException(
            403,
            "Delegation API key owner account is suspended",
        )
```

### Step 3 — Optionally auto-revoke on ban detection

For a stronger posture, revoke the key when a ban is detected, preventing
further lookups:

```python
    if is_user_currently_banned(owner_sub):
        _do_revoke(key_id)          # mark key revoked in DDB
        logger.info(
            "delegation_api: auto-revoked key %s for banned owner %s",
            key_id, owner_sub,
        )
        raise HTTPException(403, "Delegation API key owner account is suspended")
```

Auto-revocation is the recommended default. It means subsequent calls with
the same key return 401 (key revoked) rather than requiring a ban check on
every request. This also reduces the DynamoDB read on future attempts.

### Step 4 — Consider ban check on creator_id too

If a creator's account is banned, their delegates' keys should arguably also
be blocked. Add a symmetric check:

```python
    creator_id = item.get("creator_id", "")
    if is_user_currently_banned(creator_id):
        raise HTTPException(403, "Creator account is suspended")
```

This is lower-priority than the `owner_sub` fix and may have different policy
intent; treat it as a follow-up.

### Dev/Prod parity (SECOPS-007)

`T.account_state` is a DynamoDB table present in both dev (`DynamoDB Local`)
and prod (AWS DynamoDB). The `is_user_currently_banned` function is already
exercised on both paths. No mock/real bifurcation is required. The function
short-circuits safely when `T.account_state.get_item` raises (e.g., table
not found in a bare-minimum dev environment) by returning `False`.

### Backward compatibility

The change adds a new 403 rejection to an existing auth flow. Legitimate
non-banned delegates are unaffected. The only clients affected are those
whose `owner_sub` account is banned — by definition these should be blocked.

### Alternatives considered

- **Revoke all delegation keys at ban time (event-driven approach)** — when a
  user is banned via `moderation_policy_engine`, scan all their delegation API
  keys and revoke them. This is cleaner operationally but requires a
  DynamoDB GSI scan at ban time and is more complex to implement. Recommended
  as a follow-up hardening task (call `list_keys_for_owner(banned_sub)` and
  revoke each key). The inline check in `authenticate_key` is a necessary
  safety net even if event-driven revocation is added.
- **Check ban in a FastAPI dependency instead** — the delegation API router
  could have a dependency that extracts `owner_sub` from the authenticated key
  item and calls `is_user_currently_banned`. This is architecturally cleaner
  but requires touching every route definition. The inline check in the
  service is simpler and equally correct.

## 5. Testing, Verification & Rollout

### Regression test — pytest (offline)

```python
# tests/services/test_delegation_api_ban.py
from unittest.mock import patch, MagicMock
import pytest
from fastapi import HTTPException
from app.services.delegation_api import authenticate_key

FAKE_KEY = "dak_testkey123.secretabc"

@pytest.fixture
def valid_key_item():
    return {
        "key_id": "testkey123",
        "owner_sub": "banned_delegate_sub",
        "creator_id": "creator_alice",
        "secret_hash": "hashed_secret",  # will be patched
        "revoked": False,
        "permissions": ["messaging"],
        "rate_limit_rpm": 60,
    }

@pytest.fixture
def active_delegate():
    return {"status": "active", "creator_id": "creator_alice", "delegate_id": "banned_delegate_sub"}


def test_authenticate_key_blocked_for_banned_owner(valid_key_item, active_delegate):
    """GAP-0158: authenticate_key must reject keys held by a banned account."""
    with (
        patch("app.services.delegation_api.get_key_item", return_value=valid_key_item),
        patch("app.services.delegation_api.api_key_hash", return_value="hashed_secret"),
        patch("app.services.delegation_api._parse_delegation_key",
              return_value={"key_id": "testkey123", "secret": "secretabc"}),
        patch("app.services.delegation_api.get_delegate", return_value=active_delegate),
        patch("app.services.delegation_api.is_user_currently_banned", return_value=True),
    ):
        with pytest.raises(HTTPException) as exc_info:
            authenticate_key(
                api_key=FAKE_KEY,
                client_ip="1.2.3.4",
                required_permission="messaging",
            )
        assert exc_info.value.status_code == 403
        assert "suspended" in exc_info.value.detail.lower()


def test_authenticate_key_allowed_for_non_banned_owner(valid_key_item, active_delegate):
    """Non-banned delegates with valid keys are authenticated normally."""
    with (
        patch("app.services.delegation_api.get_key_item", return_value=valid_key_item),
        patch("app.services.delegation_api.api_key_hash", return_value="hashed_secret"),
        patch("app.services.delegation_api._parse_delegation_key",
              return_value={"key_id": "testkey123", "secret": "secretabc"}),
        patch("app.services.delegation_api.get_delegate", return_value=active_delegate),
        patch("app.services.delegation_api.is_user_currently_banned", return_value=False),
        patch("app.services.delegation_api._enforce_key_rate_limit"),
        patch("app.services.delegation_api._record_usage"),
    ):
        result = authenticate_key(
            api_key=FAKE_KEY,
            client_ip="1.2.3.4",
            required_permission="messaging",
        )
        assert result["owner_sub"] == "banned_delegate_sub"
```

**Fails before fix:** `is_user_currently_banned` is never imported or called;
even with `return_value=True` the mock has no effect and the function returns
the key item.

**Passes after fix:** `is_user_currently_banned(owner_sub)` is called;
mock returns `True`; `HTTPException(403)` is raised.

### Manual QA steps

1. `just up`.
2. Create a delegation relationship (Alice grants Bob the `messaging` permission).
3. As Bob, create a delegation API key.
4. Confirm the key works: `POST /ui/delegation-api/v1/conversations` returns 200.
5. Ban Bob via the moderation endpoint.
6. Re-attempt the same delegation API call as Bob.
7. **Before fix:** 200 or 201.  **After fix:** 403 with message "suspended".
8. Unban Bob and confirm the key works again.

### Observability

Log at `INFO` level whenever a ban check rejects a delegation key call
(already shown in Step 3 above). If auto-revocation is implemented, emit a
metric `delegation_api_key_auto_revoked_total{reason="owner_banned"}`.

### Rollback

Remove the `is_user_currently_banned` import and the two lines of ban check
from `authenticate_key`. No schema changes. If auto-revocation was enabled,
note that any keys revoked during the window cannot be un-revoked
automatically (a new key must be issued), but that is acceptable since the
owner was banned.

### Risk

**Low.** One additional DynamoDB `get_item` per delegation API call
(on `T.account_state`, keyed by `user_sub`). At normal delegation API volumes
this is negligible. If auto-revocation is added, a single additional
`update_item` on the first rejected call; subsequent calls return 401 with no
further DynamoDB reads.

### Effort

**S** — approximately 20 minutes of code change plus test authoring.

### Sequencing

This fix is independent of GAP-0156 and GAP-0157. It should be bundled into
the DELEGATE-005 ticket or a dedicated security hotfix PR. The auto-revocation
variant (Step 3) is recommended as the default but can be added in a follow-up
if the inline check alone is deemed sufficient for the immediate release.
