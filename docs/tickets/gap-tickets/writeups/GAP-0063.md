# GAP-0063: E2E Spec Absent for ADS-015 Affiliate/Promo Flows — Remediation Write-up

> ~5 pages. Fix-oriented. Claim verified directly against the code before writing; cites file:line.

## 1. Summary & Classification

**Claim status: CORRECTED.** The gap ticket states "no ad-affiliate-promo.spec.ts; redirect URL, cookie setting, and attribution recording are untested." This is inaccurate. The file `frontend/e2e/ad-creative-affiliate.spec.ts` exists (431 lines, 18 tests) and covers:

- Section 405: Discount config CRUD API (5 tests)
- Section 406: Click attribution + redirect URL + promo cookie (`set-cookie` header assertions, lines 268-302) (5 tests)
- Section 407: Redemption / checkout validation including attribution recording (4 tests)
- Section 408: Ownership + edge cases (5 tests — but note this collides with the section number claimed for ADS-016 scheduling tests, which use 408-410 in `ad-dayparting.spec.ts`)
- Section 409: Affiliate Discount management UI (2 tests)

All three specific capabilities mentioned in the gap — redirect URL, cookie setting, attribution recording — are tested in section 406 of the existing spec.

However, the investigation also surfaces a secondary real gap: the spec file was named `ad-creative-affiliate.spec.ts` rather than `ad-affiliate-promo.spec.ts`, creating a discoverability problem in documentation and in the gap audit. Additionally, section numbers 408-409 in `ad-creative-affiliate.spec.ts` conflict with the same numbers used in `ad-dayparting.spec.ts`, suggesting the spec was written without coordinating section numbering with the ADS-016 spec.

- **Severity**: HIGH (as filed) — downgraded to LOW on investigation; the coverage gap is superficial (naming/numbering) not substantive.
- **Source ticket**: ADS-015  
- **Owning area**: Ads / E2E Test Suite  
- **One-line impact**: No functional coverage gap exists; the gap is a documentation/naming inconsistency and a section-number collision between two spec files.  
- **Related tickets**: GAP-0062 (ROAS endpoint absent — the ROAS endpoint does need its own E2E coverage when GAP-0062 is resolved), GAP-0064 (ad-scheduling E2E — also claimed absent, also corrected).

## 2. Current-State Investigation (root cause)

### Verification of existing coverage

`frontend/e2e/ad-creative-affiliate.spec.ts:1-431` — confirmed present. Key test cases for the three claimed missing scenarios:

And in section 407, `test("407.1 Redeem validates promo via promo_codes and applies discount")` at line 315 tests the full redemption chain including the `record_conversion` path in `affiliate_links.py`.

### Root cause of the false gap

The gap audit appears to have searched for `ad-affiliate-promo.spec.ts` (the name suggested in the ADS-015 design doc) and found nothing, without checking for variant names. The actual file is `ad-creative-affiliate.spec.ts`, matching the service module name rather than the promo/affiliate marketing concept name.

### Section number collision

`frontend/e2e/ad-creative-affiliate.spec.ts` uses sections 408 and 409 for "Ownership edge cases" and "Affiliate Discount UI". `frontend/e2e/ad-dayparting.spec.ts` also uses sections 408, 409, and 410 for dayparting/flight/pacing endpoints. This collision means the section namespace is broken — any tooling that filters E2E reports by section number will produce ambiguous results.

### What is genuinely missing

The single genuine gap is: **no E2E test covers the `GET /ui/ads/campaigns/{id}/roas` endpoint** — because that endpoint does not yet exist (GAP-0062). When GAP-0062 is resolved by adding the ROAS service and endpoint, a corresponding E2E section (proposed: section 410 in `ad-creative-affiliate.spec.ts`, renumbered to avoid collision) should be added.

## 3. Impact / Exploit / Blast Radius

### Functional risk from the naming gap

None — the tests run and pass. The Playwright config (`frontend/playwright.config.ts`) discovers spec files by glob pattern (`e2e/*.spec.ts`); the filename mismatch does not prevent execution. The spec is currently part of the standard `just e2e` run and contributes its 18 tests to the overall suite count.

### Risk from section-number collision

Low operational risk today (no tooling enforces section uniqueness) but escalating as the test suite grows. The collision exists at two section numbers simultaneously:

- **Section 408** in `ad-creative-affiliate.spec.ts` tests "Non-owner cannot read discount config" — an ownership isolation test for affiliate promo.
- **Section 408** in `ad-dayparting.spec.ts` tests "Set dayparting schedule on campaign" — a mutation test for scheduling.

If a CI reporter is added that correlates failures to section numbers, a failure in either 408 will be indistinguishable from a failure in the other. Bug-tracking tickets that reference "section 408 failure" will route to the wrong team. As the test suite approaches the current count of ~1070+ tests, the probability of spurious collision-induced mis-triage increases.

The same ambiguity applies to section 409. Additionally, any future gap audit that counts sections will compute an incorrect total (appearing to have two fewer unique sections than actually exist).

### Risk from missing ROAS E2E coverage

When GAP-0062's endpoint ships without E2E tests, a regression in the ROAS calculation (e.g., returning `roas: null` after a DynamoDB schema change, or the endpoint returning stale cached data) would be invisible to the test suite. The affiliate conversion path (`record_conversion` in `affiliate_links.py:272`) accumulates `revenue_cents` on the link record, and the ROAS computation divides that by `spend_cents` from analytics rollups. Any bug in either of those two distinct DynamoDB reads — or in the division when `spend_cents = 0` — would go undetected without an E2E test covering the endpoint.

This is the actual substantive gap that GAP-0063 should be tracking, and it is blocked on GAP-0062 being resolved first.

### Summary of residual risk

| Risk | Severity before fix | Severity after fix |
|------|--------------------|--------------------|
| Gap audit false negative (spec not found) | Medium (causes mis-prioritisation) | None |
| Section-number collision in CI reports | Low (today) / Medium (at scale) | None |
| Missing ROAS E2E coverage | Medium (blocks on GAP-0062) | None (after GAP-0062 + 414) |

## 4. Fix Design

### Immediate action: resolve the naming confusion

Rename `frontend/e2e/ad-creative-affiliate.spec.ts` to `frontend/e2e/ad-affiliate-promo.spec.ts` to align with the ADS-015 documentation. This is a git `mv` plus one-line update to any import or documentation that references the old filename.

Alternatively (lower risk): keep the filename and update the gap audit documentation and any references to reflect the actual filename.

### Resolve the section-number collision

Renumber the `ad-creative-affiliate.spec.ts` sections. Current assignments:

| File | Sections |
|------|---------|
| `ad-creative-affiliate.spec.ts` | 405-409 (408, 409 collide) |
| `ad-dayparting.spec.ts` | 408-411 (408, 409 collide) |

Proposed renumbering for `ad-creative-affiliate.spec.ts`:

| Old section | New section | Description |
|-------------|-------------|-------------|
| 405 | 405 | Discount config CRUD API (no change) |
| 406 | 406 | Click attribution + redirect (no change) |
| 407 | 407 | Redemption API (no change) |
| 408 | 412 | Ownership + edge cases |
| 409 | 413 | Affiliate Discount management UI |

And reserve section 414 for the ROAS endpoint tests once GAP-0062 is resolved.

### Auth pattern note for section 414 tests

The planned ROAS tests (section 414) should use the same cookie-auth helpers as the rest of the spec. The `catGet` helper pattern already used in sections 405-407 sends the CSRF header and uses the alice-page context:

```typescript
async function catGet(page: Page, identity: string, path: string, params?: Record<string, string>) {
  const sessions = getAdminSessions();
  const qs = params ? "?" + new URLSearchParams(params).toString() : "";
  const resp = await page.request.get(`${BASE}${path}${qs}`, {
    headers: { "x-csrf-token": sessions[identity].csrf_token },
  });
  return resp.json();
}
```

Since `GET /ui/ads/campaigns/{id}/roas` is a GET request, CSRF is not enforced by the backend (only non-GET cookie-auth requests require CSRF). The `x-csrf-token` header can still be included for consistency with other helpers without causing errors.
