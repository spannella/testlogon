# GAP-0048: No Daily spent_today_cents Reset Background Task — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Claim (from ticket):** `app/services/ad_billing.py:_process_charge` increments `spent_today_cents` on every ad charge, but there is no background task that resets `spent_today_cents` to zero at midnight UTC. Daily-budget campaigns therefore accumulate spend indefinitely; once a campaign exhausts its daily budget it can never serve again.

**Verdict: Claim confirmed.** The increment at `ad_billing.py:136` is present and correctly accumulates into `spent_today_cents`. The `ad_serving.py:_has_budget` helper at line 316 reads `spent_today_cents` to gate serving for `budget_type="daily"` campaigns. There is no background task registered in `app/main.py` (confirmed by exhaustive grep) that ever resets this field. There is also no `last_reset_date` guard field written anywhere in the codebase. The gap is exactly as described.

- **Severity:** HIGH (billing correctness; active daily-budget campaigns stop serving permanently after day 1)
- **Source ticket:** ADS-007
- **Owning area:** Advertising / Ad Billing
- **Status:** Open
- **Effort:** M
- **Related tickets:** GAP-0049 (same service file), GAP-0001 (analogous wallet daily reset gap), GAP-0050 (analytics depends on correct campaign state)

### Background: The daily-budget model

The ad platform supports two `budget_type` values on campaigns: `"lifetime"` (spend up to `budget_cents` total, stop forever when exhausted) and `"daily"` (spend up to `daily_budget_cents` per calendar day, reset at midnight UTC, repeat until the campaign's end date or explicit pause). The daily-budget model is fundamental to advertiser expectations — they set a daily cap so they do not overspend in any single day. Implementing this requires both the accumulation logic (present, correct) and the reset logic (absent). Without the reset, the daily-budget model degrades to a lifetime model with a much smaller cap, and the advertiser receives no notification that the campaign is permanently stalled.

## 2. Current-State Investigation (root cause)

### The accumulation path

`app/services/ad_billing.py:100-147`, function `_process_charge`:

```python
# Step 3. Increment campaign spend
T.ad_campaigns.update_item(
    Key={"pk": f"ACCT#{account_id}", "sk": f"CAMPAIGN#{campaign_id}"},
    UpdateExpression="SET spent_today_cents = if_not_exists(spent_today_cents, :z) + :amt, "
                     "lifetime_spent_cents = if_not_exists(lifetime_spent_cents, :z) + :amt",
    ExpressionAttributeValues={":z": 0, ":amt": charge_cents},
)
```

Every impression, click, and conversion charge increments both `spent_today_cents` and `lifetime_spent_cents`. The two fields share one DynamoDB UpdateExpression; there is no date-stamp written alongside `spent_today_cents`.

### The serving gate that reads it

`app/services/ad_serving.py:310-320`, function `_has_budget`:

```python
def _has_budget(campaign: dict) -> bool:
    budget = int(campaign.get("budget_cents", 0))
    spent = int(campaign.get("lifetime_spent_cents", 0))
    if campaign.get("budget_type") == "lifetime" and spent >= budget:
        return False
    if campaign.get("budget_type") == "daily":
        daily_spent = int(campaign.get("spent_today_cents", 0))
        daily_budget = int(campaign.get("daily_budget_cents", budget))
        if daily_spent >= daily_budget:
            return False
    return True
```

For a campaign with `budget_type="daily"` and `daily_budget_cents=10000` ($100/day): once impressions accumulate $100 worth of charges, `_has_budget` returns `False` and the campaign stops serving. Without a reset, this state is permanent.

### No reset task exists

A full search of the codebase confirms:
- No file contains `last_reset_date` or any reference to resetting `spent_today_cents`.
- `app/main.py` registers no startup handler referencing `ad_billing` or `spent_today_cents`.
- The ad_billing module has no exported `reset_daily_spend` or similar function.
- The `ad_optimization.py:353` usage reads `spent_today_cents` for campaign pacing but does not write a reset.

### No `last_reset_date` guard

Without a `last_reset_date` field on the campaign record, it is not possible for the reset task to be idempotent across restarts. If the backend restarts at 00:01 UTC and the task runs at startup, it would reset spend even on a day where the reset already ran. The fix must write a `last_reset_date` (UTC date string) atomically with each reset to prevent double-reset. This same pattern is used in other daily reset tasks (e.g. wallet roll-over) and is the standard idempotency guard for DynamoDB-backed scheduled jobs in this codebase.

### Comparison with `ad_optimization.py` pacing

`app/services/ad_optimization.py:353` also reads `spent_today_cents` for campaign pacing decisions. Without a reset, pacing calculations on day 2+ will see a `spent_today_cents` value that is at least equal to the full daily budget, and the pacing algorithm will rate-limit delivery to zero from the very first impression of the new day — effectively compounding the serving failure before `_has_budget` even has a chance to block it. The reset task is therefore doubly important: it unblocks both the hard budget gate in `ad_serving.py` and the soft pacing gate in `ad_optimization.py`.

## 3. Impact / Exploit / Blast Radius

**Business impact — day 1 → day 2 transition:**
An advertiser creates a daily-budget campaign with `daily_budget_cents=20000` ($200/day). On day 1, the campaign spends its full budget and stops serving at, say, 18:00 UTC. On day 2 at 00:01 UTC, the campaign should have `spent_today_cents` reset to 0 and should start serving again. Without the reset, `_has_budget` permanently returns `False` for that campaign. The campaign appears "active" in the UI (status is not `"completed"`) but delivers zero impressions and zero revenue. The advertiser is charged nothing but receives no exposure — confusing and likely to generate advertiser support tickets.

**Financial impact (platform):**
Platform and creator ad revenue are both zeroed for affected campaigns from day 2 onwards. If a campaign has a 30-day flight and the budget is exhausted each day, the platform loses 29 days of revenue per campaign.

**Audit / integrity:**
`lifetime_spent_cents` continues to accumulate correctly (it is never reset) but `spent_today_cents` diverges from the true daily spend on day 2+. Any reporting that uses `spent_today_cents` as a daily metric (e.g. `ad_optimization.py:353`) will see inflated historical spend and produce incorrect pacing decisions.

**No security exploit possible.** This is a data-integrity/availability issue, not a security vulnerability.

**Blast radius:** All campaigns with `budget_type="daily"`. Campaigns with `budget_type="lifetime"` are unaffected (they use `lifetime_spent_cents` only).

## 4. Fix Design (code-level)

### New service function: `reset_daily_campaign_spend`

Add to `app/services/ad_billing.py`:

```python
import logging
from datetime import datetime, timezone

logger = logging.getLogger(__name__)

_UTC_DATE_FMT = "%Y-%m-%d"


def reset_daily_campaign_spend() -> dict:
    """Reset spent_today_cents=0 for all active daily-budget campaigns.

    Uses a last_reset_date guard so the reset is idempotent: if today's date is
    already written on the campaign, skip it. Returns counts of reset and skipped.

    Should be called once per day at midnight UTC by a background task.
    """
    today = datetime.now(timezone.utc).strftime(_UTC_DATE_FMT)
    reset_count = 0
    skip_count = 0

    try:
        from boto3.dynamodb.conditions import Attr
        # Scan for campaigns that have budget_type="daily" and status="active"
        # and whose last_reset_date is not today.
        # We use a FilterExpression scan rather than a GSI because this runs
        # once per day and campaign counts are expected to be in the thousands
        # at most; a full scan is acceptable.
        paginator_kwargs = {
            "FilterExpression": (
                Attr("budget_type").eq("daily") &
                Attr("status").eq("active") &
                (
                    Attr("last_reset_date").not_exists() |
                    Attr("last_reset_date").lt(today)
                )
            )
        }
        while True:
            resp = T.ad_campaigns.scan(**paginator_kwargs)
            for item in resp.get("Items", []):
                pk = item.get("pk", "")
                sk = item.get("sk", "")
                if not pk or not sk:
                    continue
                try:
                    T.ad_campaigns.update_item(
                        Key={"pk": pk, "sk": sk},
                        UpdateExpression="SET spent_today_cents = :zero, last_reset_date = :today",
                        ConditionExpression=(
                            Attr("last_reset_date").not_exists() |
                            Attr("last_reset_date").lt(today)
                        ),
                        ExpressionAttributeValues={":zero": 0, ":today": today},
                    )
                    reset_count += 1
                except Exception:
                    # ConditionalCheckFailedException = another worker already reset this item
                    skip_count += 1
            if "LastEvaluatedKey" not in resp:
                break
            paginator_kwargs["ExclusiveStartKey"] = resp["LastEvaluatedKey"]
    except Exception:
        logger.exception("reset_daily_campaign_spend_failed")

    logger.info(
        "ad_daily_spend_reset_complete",
        extra={"date": today, "reset": reset_count, "skipped": skip_count},
    )
    return {"date": today, "reset": reset_count, "skipped": skip_count}
```

### New background task: `start_ad_daily_reset_task`

Add to `app/services/ad_billing.py` (or a new `app/services/ad_tasks.py`):

```python
import asyncio
from datetime import datetime, timezone, timedelta


async def _ad_daily_reset_loop():
    """Runs reset_daily_campaign_spend once per day at midnight UTC."""
    while True:
        try:
            now = datetime.now(timezone.utc)
            # Compute seconds until next midnight UTC
            next_midnight = (now + timedelta(days=1)).replace(
                hour=0, minute=0, second=0, microsecond=0
            )
            sleep_seconds = (next_midnight - now).total_seconds()
            await asyncio.sleep(max(1.0, sleep_seconds))
            reset_daily_campaign_spend()
        except asyncio.CancelledError:
            break
        except Exception:
            logger.exception("ad_daily_reset_loop_error")
            await asyncio.sleep(60)  # back-off on unexpected error


def start_ad_daily_reset_task():
    """Register the daily ad spend reset background task at startup."""
    loop = asyncio.get_event_loop()
    loop.create_task(_ad_daily_reset_loop())
```

### Register in `app/main.py`

In the `create_app()` function alongside the other startup tasks (near line 806):

```python
from app.services.ad_billing import start_ad_daily_reset_task

app.add_event_handler("startup", start_ad_daily_reset_task)
```

### DynamoDB schema addendum

The `ad_campaigns` table gains a new non-key attribute `last_reset_date` (type `S`, format `"YYYY-MM-DD"`). No schema change is needed for DynamoDB Local because this is a non-key attribute. The field is absent on existing items, which is handled by the `not_exists()` condition expression. No migration script is required.

### Dev/Prod parity (SECOPS-007)

The reset reads from `T.ad_campaigns`, which maps to DynamoDB Local in dev (`DDB_ENDPOINT_URL=http://localhost:8001`) and to the real AWS DynamoDB in prod. The same code path is executed in both environments. No mock/dev bypass is needed. In dev, the reset can be tested by:
1. Seeding a daily-budget campaign with `spent_today_cents > 0` and `last_reset_date` absent.
2. Calling `reset_daily_campaign_spend()` directly from a test or the dev tools UI.
3. Confirming `spent_today_cents` is reset to 0 and `last_reset_date` is today's date.

The background task loop uses `asyncio.sleep` calibrated to wall-clock midnight UTC. In dev, operators may not want to wait until midnight; the function can be invoked directly via a test or an internal endpoint (not exposed in prod). An optional `RESET_AD_DAILY_SPEND_INTERVAL_SECONDS` env var can be added to settings to allow shorter intervals in dev without changing prod semantics, mirroring the pattern used by other background tasks (e.g. `billing_reconcile_interval_seconds`).

### Observability

The `logger.info("ad_daily_spend_reset_complete", ...)` log line at the end of `reset_daily_campaign_spend` emits the number of campaigns reset each day. Forward this to the platform's metrics system (Prometheus counter: `ad_daily_spend_resets_total{date="..."}`) for monitoring.
