# GAP-0311: Platform-Level Admin/Root Cannot Delete Any Message — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/routers/messaging.py`.

## 1. Summary & Classification

**Bug statement**: The `revoke_message_for_all` endpoint in the messaging router enforces a strict authz path that requires the requesting user to be an active participant of the conversation. Platform-level admins and ROOT-role operators are therefore unable to remove harmful, abusive, or legally problematic messages from conversations they are not a member of. This is a content-moderation gap, not a regression — the feature was never implemented.

**Severity**: HIGH  
**Source ticket**: MSG-001 (GAP-0311)  
**Owning area**: Messaging / Content Moderation  
**Status**: Open — no fix deployed

**Verdict**: Claim **confirmed**. The actual code at `messaging.py:10801–10809` and `messaging.py:5054–5062` demonstrates the exact gap described. The function `_ensure_can_revoke_message` permits revocation only if the caller is the original sender OR a conversation-level `admin` role participant. There is no bypass path for platform-level `Role.ADMIN` or `Role.ROOT` users.

**Impact in one line**: Any admin or root operator attempting to moderate a message they did not send, and are not a conversation participant of, receives HTTP 403 and cannot remove the content.

**Related tickets**: GAP-0038 (admin capabilities dead code), SECOPS-007 (dev/prod parity rule), GAP-0003 (internal charge endpoints lack access control — similar pattern).

## 2. Current-State Investigation (Root Cause)

### Auth dependency chain

`revoke_message_for_all` uses `Depends(get_messaging_user_id)`, which is defined at `messaging.py:1549`. This dependency returns only a `user_id: str` — it discards the richer `AuthenticatedUser` object (which carries `role: Role`) after extracting the subject. The platform role is therefore invisible to the endpoint body.

```python
# messaging.py:1549-1570
async def get_messaging_user_id(
    request: Request,
    ...
) -> str:
    ...
    ctx = await require_ui_session(request, user_sub=user_sub, x_session_id=x_session_id)
    uid = ctx["user_sub"]          # role is thrown away here
    _ensure_user_indexed(uid)
    return uid
```

### Participant check gates the endpoint

`revoke_message_for_all` (line 10801) immediately calls `require_participant_active(user_id, conversation_id)` (line 10807), which raises `403` if the user is not an active participant of that specific conversation:

```python
# messaging.py:4449-4453
def require_participant_active(user_id: str, conversation_id: str) -> dict:
    item = get_participant_any(user_id, conversation_id)
    if not item or item.get("status") != "active":
        raise HTTPException(status_code=403, detail="Not an active participant")
    return item
```

Platform admins are not participants in arbitrary user conversations, so this call always raises for them.

### _ensure_can_revoke_message provides no platform bypass

Even if the participant check were passed, `_ensure_can_revoke_message` (line 5054) only allows the message sender or a conversation-level "admin" participant to revoke:

```python
# messaging.py:5054-5062
def _ensure_can_revoke_message(user_id: str, conversation_id: str, message_item: dict) -> None:
    if message_item.get("revoked_at"):
        raise HTTPException(400, "Message already revoked")
    created_at = int(message_item.get("created_at", 0) or 0)
    if now_ts() - created_at > MESSAGE_REVOKE_WINDOW_SEC:
        raise HTTPException(400, "Revocation window has expired")
    if message_item.get("sender_id") == user_id:
        return
    require_participant_role(user_id, conversation_id, {"admin"})
```

The `MESSAGE_REVOKE_WINDOW_SEC` constant (line 216) defaults to 300 seconds (5 minutes), compounding the problem: a platform admin cannot remove a message even if they somehow gained participant access after the window has closed.

### Legal hold path exists but is separate

The compliance operator path (`require_legal_hold_operator` at line 1157) provides export and hold capabilities, but does **not** include a deletion or revocation endpoint. Legal hold preserves content; it does not remove it.

### Dev vs prod parity

In dev mode the same code path executes. The `get_messaging_user_id` dependency is identical in both modes — the gap is structural, not environment-specific.

## 3. Impact / Exploit / Blast Radius

**Who is affected**: Any platform admin or root user who needs to remove a harmful message from a conversation they are not a member of.

**Concrete scenarios**:

1. **CSAM / harmful content**: A user reports a message containing illegal content. A platform admin attempts to revoke it. The admin is not a participant → HTTP 403. Content remains visible to all conversation participants until the sender revokes it (within their 5-minute window) or until the TTL expires.

2. **Time-window bypass**: Even if an admin *were* a conversation participant, the 5-minute revocation window applies equally. A message reported after 10 minutes cannot be revoked by anyone, including admins — the `MESSAGE_REVOKE_WINDOW_SEC` check at line 5058 does not have a platform-role bypass.

3. **No parallel moderation endpoint**: There is no separate "admin delete message" endpoint. The compliance operator endpoints (lines 11970–12433) can export and legally hold conversations but cannot remove individual messages.

**Blast radius**: Content moderation is blocked for all conversations platform-wide. An adversarial user can post harmful content, survive the 5-minute self-revocation window, and the platform has no server-side mechanism to remove it.

**Financial/compliance consequence**: Depending on jurisdiction (e.g. DSA Article 17 in the EU, DMCA Section 512 in the US), a platform must demonstrate the technical capability to remove user-reported harmful content promptly. Absence of this capability is a regulatory compliance risk.

## 4. Fix Design (Code-Level)

### Strategy

Introduce a dedicated moderation endpoint with `require_content_moderation_admin` guard, bypassing both the participant check and the time-window restriction. This is analogous to the existing `require_legal_hold_operator` pattern but for active deletion rather than preservation.

Do **not** modify `revoke_message_for_all` itself — that endpoint carries user-facing semantics (5-minute window, sender-only permission) that must be preserved. A separate endpoint makes the intent explicit and auditable.

### New dependency (app/auth/deps.py or messaging.py)

```python
# Reuse existing pattern at messaging.py:1157-1165
async def require_content_moderation_operator(
    user: AuthenticatedUser = Depends(get_authenticated_user),
    request: Request = None,
) -> AuthenticatedUser:
    return await require_content_moderation_admin(request=request, user=user)
```

`require_content_moderation_admin` should be declared alongside `require_legal_hold_admin` at line 248, gating on `AdminScope.CONTENT_MODERATION`.

### New endpoint

```python
# app/routers/messaging.py — add after revoke_message_for_all (~line 10862)

@router.delete(
    "/conversations/{conversation_id}/messages/{message_id}/moderate",
    response_model=MessageOut,
    tags=["moderation"],
)
def admin_revoke_message(
    conversation_id: str,
    message_id: str,
    req: Request = None,
    actor: AuthenticatedUser = Depends(require_content_moderation_operator),
):
    """Platform-admin forced revocation — bypasses participant and time-window checks."""
    msg = _get_message_or_404(conversation_id, message_id)
    if msg.get("revoked_at"):
        raise HTTPException(400, "Message already revoked")

    ts = now_ts()
    tbl_msgs.update_item(
        Key={"conversation_id": conversation_id, "message_id": message_id},
        UpdateExpression="SET revoked_at = :ts, revoked_by = :uid, moderated_by = :uid",
        ExpressionAttributeValues={":ts": ts, ":uid": actor.sub},
    )
    if _is_searchable_kind(msg.get("kind")):
        remove_message_search(conversation_id, message_id, _message_search_text(msg))

    revoked_item = dict(msg)
    revoked_item["revoked_at"] = ts
    revoked_item["revoked_by"] = actor.sub
    _sync_gallery_index_message(revoked_item)

    fanout_event_to_conversation(
        conversation_id=conversation_id,
        sender_id=actor.sub,
        event_type="message:revoked",
        payload={"message_id": message_id, "revoked_at": ts, "revoked_by": actor.sub},
        respect_mute=False,
    )
    audit_event(
        "messaging_message_admin_revoked",
        actor.sub,
        req,
        outcome="success",
        conversation_id=conversation_id,
        message_id=message_id,
        revoked_at=ts,
        moderation=True,
    )
    _emit_message_lifecycle_archive_event_or_503(
        mutation="admin_revoke",
        event_ts=ts,
        conversation_id=conversation_id,
        message_id=message_id,
        actor_user_id=actor.sub,
        event_type="message.admin_revoked",
        payload={
            "mutation": "admin_revoke",
            "message": _serialize_message_event_payload(
                _get_message_or_404(conversation_id, message_id), actor.sub
            ),
        },
    )
    return _message_out_from_items(
        _get_message_or_404(conversation_id, message_id), actor.sub
    )
```

### DynamoDB schema note

The `moderated_by` attribute is a new non-key attribute on existing message items — no schema migration is required for DynamoDB (schemaless). Retrospective moderation logs are accessible through the audit_event stream.

### Dev/Prod parity (SECOPS-007)

The `require_content_moderation_operator` dependency uses `get_authenticated_user` (line 34), which already handles both cookie-session and Bearer JWT paths and is tested in both dev and prod. No new mock path is needed. In dev mode (`S.dev_mode = True`) the same `AdminScope.CONTENT_MODERATION` gate applies — the `e2e_admin_session_setup.py` script issues JWTs with scoped admin profiles, so Playwright tests can authenticate as a content-moderation admin.

### Backward compatibility

The existing `revoke_message_for_all` endpoint is unchanged. No migration needed — the new endpoint is additive. Old API clients are unaffected.
