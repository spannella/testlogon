# GAP-0361: list_pending_requests exposes join requests to any authenticated user — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against real code; cites `file:line` throughout.

## 1. Summary & Classification

**Bug**: The `GET /{syndicate_id}/requests` endpoint in the syndicates router is decorated with a comment claiming "Admin-only check done in service," but the underlying service function `list_pending_requests` performs no admin guard whatsoever. Any authenticated user — including non-members and users with no affiliation to the syndicate — can enumerate all pending join requests for any syndicate by sending a valid session cookie.

**Severity**: HIGH
**Source ticket**: SYND-001 (second-pass as-built review)
**Status**: Open
**Owning area**: Backend / Syndicates router + service
**Effort**: S (small — single guard line)
**Related tickets**: GAP-0032 (admin treasury self-disbursement), GAP-0038 (implicit full-admin via CLI grant)

**Claim verification**: CONFIRMED. The router handler at `app/routers/syndicates.py:268-280` calls `svc.list_pending_requests(syndicate_id)` directly after `Depends(require_ui_session)` with no further authorization. The service function at `app/services/syndicates.py:462-468` performs only a DynamoDB query — no admin check, no membership check. The comment on line 269 is factually false; the promised guard does not exist.

**One-line impact**: A low-privilege user can observe the email/user-ID and personal message of every person trying to join any syndicate on the platform, enabling competitive intelligence gathering, targeted harassment, and social engineering of applicants.

## 2. Current-State Investigation (root cause)

### Router handler

```
app/routers/syndicates.py:267-280
```

```python
@router.get("/{syndicate_id}/requests")
def list_requests(syndicate_id: str, session=Depends(require_ui_session)):
    # Admin-only check done in service          <-- THIS COMMENT IS FALSE
    items = svc.list_pending_requests(syndicate_id)
    return [
        SyndicateRequestOut(
            syndicate_id=r.get("syndicate_id", syndicate_id),
            user_id=r.get("user_id", ""),
            requested_at=int(r.get("requested_at", 0)),
            message=r.get("message", ""),
            status=r.get("status", "pending"),
        )
        for r in items
    ]
```

`require_ui_session` only validates that the caller holds a live session cookie — it does not check any relationship between the caller and the target syndicate. After that dependency resolves, the handler calls straight into the service with no additional gate.

### Service function

```
app/services/syndicates.py:462-468
```

```python
def list_pending_requests(syndicate_id: str) -> List[Dict[str, Any]]:
    """List pending join requests for a syndicate."""
    resp = T.syndicates.query(
        KeyConditionExpression=Key("pk").eq(f"SYND#{syndicate_id}") & Key("sk").begins_with("REQUEST#"),
    )
    items = resp.get("Items", [])
    return [i for i in items if i.get("status") == "pending"]
```

The function signature accepts only `syndicate_id` — there is no `caller_sub` or `admin_sub` parameter, so a caller's identity cannot be checked even if someone wanted to add the guard here. The DynamoDB query returns all `REQUEST#*` items for the syndicate unconditionally.

### Comparison: similar endpoints that do guard correctly

The helper `_require_admin` at `app/services/syndicates.py:560-564` raises HTTP 403 if the caller is not the syndicate admin:

```python
def _require_admin(syndicate_id: str, user_id: str) -> None:
    meta = _get_meta(syndicate_id)
    if meta["admin_user_id"] != user_id:
        raise HTTPException(status_code=403, detail="Only the syndicate admin can perform this action")
```

Other sensitive endpoints correctly invoke this guard before proceeding. For example:

- `app/services/syndicates.py:76` — `update_syndicate` calls `_require_admin`
- `app/services/syndicates.py:167` — `respond_to_request` calls `_require_admin`
- `app/services/syndicates.py:279` — `invite_member` calls `_require_admin`
- `app/services/syndicates.py:436` — `remove_member` calls `_require_admin`

`list_pending_requests` alone omits this call. The comment in the router was presumably left over from an early draft where the guard was intended to be in the service — it was never implemented.

### The audit log endpoint has the same structural pattern — but it's correctly different

For comparison, the adjacent `GET /{syndicate_id}/audit` handler at `app/routers/syndicates.py:283-300` also relies on the session dependency only:

```python
@router.get("/{syndicate_id}/audit")
def get_audit(syndicate_id: str, ...session=Depends(require_ui_session)):
    items = svc.get_audit_log(syndicate_id, limit=limit)
    ...
```

The audit log may intentionally be accessible to all members (not just the admin) — the spec does not restrict it to admin-only. By contrast, join requests contain personally identifiable applicant data and are explicitly admin-domain information. The two endpoints look identical in structure at the router level, which may be why `list_requests` did not receive scrutiny during initial review — the structural similarity masked the missing authorization difference.

### Scope: `list_pending_requests` takes no `caller_sub`

```python
# app/services/syndicates.py:462
def list_pending_requests(syndicate_id: str) -> List[Dict[str, Any]]:
```

The function signature makes it structurally impossible to perform an identity check inside the service: there is no parameter for the caller's identity. The router must be the enforcement point. This reinforces that the fix belongs in the router, not the service.

### Runtime manifestation

In dev mode with session cookies, an attacker with any valid session can call:

```
GET /ui/syndicates/{any_syndicate_id}/requests
```

and receive the full list of pending applicants, including `user_id`, `requested_at`, and the `message` field (which often contains personal information like "I'm a photographer focusing on …"). The attacker needs only to discover the `syndicate_id` (a UUID-style string exposed by the public `GET /ui/syndicates` listing).

## 3. Impact / Exploit / Blast Radius

### Who is affected

- **Applicants**: Any user who submitted a join request to any syndicate. Their user ID and free-form application message are visible to the entire authenticated user base.
- **Syndicates**: Competitive syndicate operators can observe which creators are trying to join rival syndicates and poach them or preemptively block them.
- **Platform**: Exposure of structured applicant metadata may constitute a privacy violation under applicable regulations (GDPR Art. 5, CCPA §1798.100) depending on what the `message` field contains.

### Concrete exploit walkthrough

1. Attacker creates or logs into any account — no special role needed.
2. Attacker calls `GET /ui/syndicates?limit=100` to enumerate all active syndicates and collect their `syndicate_id` values.
3. For each syndicate ID of interest, attacker calls `GET /ui/syndicates/{syndicate_id}/requests`.
4. Response lists every pending applicant's `user_id`, timestamp, and personal application message.
5. Attacker repeats indefinitely; no rate limit exists on this endpoint.

### Worst case

A malicious actor running an automated script could harvest the entire applicant pool across all syndicates in seconds, building a database of users who are actively seeking syndicate membership. This data could be used for targeted phishing, competitive recruiting, or social engineering attacks against applicants.

### Data integrity / financial consequence

None directly — this is an information-disclosure vulnerability, not a write path. However, the chilling effect on join requests (if applicants learn their messages are public) could reduce syndicate participation and harm platform revenue.

## 4. Fix Design (code-level)

### Minimal fix — add admin guard in the router handler

The correct change is a single call to `svc._require_admin` (already imported via `from app.services import syndicates as svc`) in the router handler, before the service call:

```python
# app/routers/syndicates.py:267-280 — AFTER FIX

@router.get("/{syndicate_id}/requests")
def list_requests(syndicate_id: str, session=Depends(require_ui_session)):
    svc._require_admin(syndicate_id, session["user_sub"])   # <-- ADD THIS LINE
    items = svc.list_pending_requests(syndicate_id)
    return [
        SyndicateRequestOut(
            syndicate_id=r.get("syndicate_id", syndicate_id),
            user_id=r.get("user_id", ""),
            requested_at=int(r.get("requested_at", 0)),
            message=r.get("message", ""),
            status=r.get("status", "pending"),
        )
        for r in items
    ]
```

The misleading comment on line 269 must also be removed to avoid repeating this confusion:

```python
# Remove: "# Admin-only check done in service"
```

### Alternative considered: move the guard into the service

Adding a `caller_sub` parameter to `list_pending_requests` and calling `_require_admin` from inside the service would also work, but is a larger change with more call-site impact and is inconsistent with the existing pattern where most service functions accept identity only when they need it for business logic. The router is the right enforcement layer for cross-cutting access control, consistent with how `respond_to_request`, `invite_member`, and `remove_member` all receive admin auth checks.

### Dev/Prod parity (SECOPS-007)

This endpoint is served by the same `require_ui_session` dependency in both dev and prod. There are no mock paths, feature flags, or `DEV_MODE` branches on this endpoint. The fix applies identically in both environments. No AWS-specific path is involved.

The `_require_admin` helper reads from DynamoDB (`T.syndicates`) to fetch the syndicate metadata record and compare `admin_user_id`. In dev the table is DynamoDB Local (port 8001). In prod it is a real DynamoDB table behind AWS IAM. The lookup is identical — no extra config needed.

### Backward compatibility / migration

No DynamoDB schema changes. No new tables. No migration needed. The change is a pure runtime access-control addition. The only behavioral difference is that non-admin callers now receive HTTP 403 instead of HTTP 200 with the applicant list. Any frontend code that depends on non-admin users accessing this endpoint is itself a bug and should be addressed.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline — fails before fix, passes after)

Add to `tests/test_syndicates.py` (or create `tests/test_syndicates_access.py`):

```python
import pytest
from fastapi.testclient import TestClient
from unittest.mock import patch
from app.main import app

client = TestClient(app)

SYNDICATE_ID = "test-synd-001"

def _make_session(user_sub: str, role: str = "USER"):
    """Return a minimal session dict (matches require_ui_session return shape)."""
    return {"user_sub": user_sub, "role": role, "admin_profile": None}

def test_list_requests_requires_admin():
    """Non-admin authenticated users MUST receive 403, not the request list.

    This test fails before the fix (returns 200) and passes after (returns 403).
    """
    non_admin_sub = "alice@test.local"
    admin_sub = "bob@test.local"

    with (
        patch("app.routers.syndicates.require_ui_session",
              return_value=_make_session(non_admin_sub)),
        patch("app.services.syndicates._get_meta",
              return_value={"admin_user_id": admin_sub, "status": "active", "name": "Test"}),
        patch("app.services.syndicates.list_pending_requests",
              return_value=[{"user_id": "carol", "requested_at": 1000, "message": "hi", "status": "pending"}]),
    ):
        resp = client.get(f"/ui/syndicates/{SYNDICATE_ID}/requests")
        assert resp.status_code == 403, (
            f"Expected 403 for non-admin caller, got {resp.status_code}. "
            "GAP-0361: _require_admin guard is missing."
        )


def test_list_requests_admin_succeeds():
    """Syndicate admin MUST receive 200 with the request list after the fix."""
    admin_sub = "bob@test.local"

    with (
        patch("app.routers.syndicates.require_ui_session",
              return_value=_make_session(admin_sub)),
        patch("app.services.syndicates._get_meta",
              return_value={"admin_user_id": admin_sub, "status": "active", "name": "Test"}),
        patch("app.services.syndicates.list_pending_requests",
              return_value=[{"user_id": "carol", "requested_at": 1000, "message": "hi",
                             "status": "pending", "syndicate_id": SYNDICATE_ID}]),
    ):
        resp = client.get(f"/ui/syndicates/{SYNDICATE_ID}/requests")
        assert resp.status_code == 200
        data = resp.json()
        assert len(data) == 1
        assert data[0]["user_id"] == "carol"
```

### Playwright E2E test addition

Add two scenarios to `frontend/e2e/syndicates.spec.ts` (or an equivalent spec):

1. **Non-admin user Alice tries to view Bob's syndicate requests** — expects network response with status 403 and the page shows no applicant data.
2. **Syndicate admin Bob views his own syndicate requests** — expects 200 and a correctly rendered requests list.

```typescript
// Fails before fix, passes after:
test("non-admin cannot list join requests for a syndicate they do not admin", async ({ page }) => {
  await injectAuth(page, "alice");
  const resp = await page.request.get(`/ui/syndicates/${syndicateId}/requests`);
  expect(resp.status()).toBe(403);
});

// Passes both before and after (smoke):
test("syndicate admin can list join requests", async ({ page }) => {
  await injectAuth(page, "bob"); // bob is admin of syndicateId
  const resp = await page.request.get(`/ui/syndicates/${syndicateId}/requests`);
  expect(resp.status()).toBe(200);
});
```

### Manual QA steps

1. Seed one syndicate with admin=Bob and one pending join request from Carol.
2. Log in as Alice (non-admin, non-member).
3. `curl -b <alice_cookies> http://localhost:8000/ui/syndicates/{syndicateId}/requests`
4. **Before fix**: 200 JSON with Carol's request.
5. **After fix**: 403 `{"detail": "Only the syndicate admin can perform this action"}`.
6. Repeat logged in as Bob (the admin): should still return 200.

### Observability / metrics

Log a `syndicates.list_requests.forbidden` counter (or rely on the existing 403 access log) to detect if legitimate admin tooling breaks after the fix.

### Rollback

Remove the single added line from the router handler. The change is self-contained with zero state side-effects.

### Risks

- Any existing frontend code or integration that calls this endpoint as a non-admin will start receiving 403. Audit the frontend for any `GET /{syndicate_id}/requests` call sites before deploying.
- If any automated background job queries this endpoint, it must run under admin credentials or be refactored to call the service layer directly.

### Effort

**S** — approximately 30 minutes of code change + 1–2 hours of test authoring and review. No schema or infrastructure changes needed.

### Sequencing

Can be deployed independently at any time. Recommended priority: high — the vulnerability is trivially exploitable by any authenticated user.
