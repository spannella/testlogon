# GAP-0057: Ads Scopes Not Surfaced in Frontend API Key Creation UI — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against live code at
> `frontend/src/pages/security/ApiKeys.tsx`,
> `app/services/api_key_capabilities.py`. No investigation doc exists.

## 1. Summary & Classification

**Gap**: The API Key creation dialog in `frontend/src/pages/security/ApiKeys.tsx` exposes
no capability/scope selector at all. It only allows users to set a label and expiry date.
The three advertiser API scopes (`ads:manage`, `ads:read`, `ads:serve`) — which are fully
defined in the backend canonical list (`app/services/api_key_capabilities.py:4–31`) and
enforced by every endpoint in `app/routers/advertiser_api.py` — are therefore
unreachable from the UI. An advertiser wanting programmatic access must make a raw
`POST /ui/account/api-keys` API call to specify these scopes.

- **Severity**: HIGH
- **Source ticket**: ADS-011
- **Owning area**: Security settings UI / API key management
- **Status**: Open
- **Related tickets**: GAP-0056 (per-key rate limiting); ADS-011 (advertiser API)
- **Verdict**: Claim confirmed and extended. No scope selector of any kind exists in the
  creation dialog — not only the `ads:*` scopes are missing, but all 25 canonical scopes
  are absent from the UI creation flow.

**One-line impact**: Advertisers and third-party integrations cannot mint capability-scoped
keys from the product UI, creating a usability gap and potential security risk (users
resort to full-capability keys created via raw API calls).

## 2. Current-State Investigation (root cause)

### API key creation dialog — no scope field

`frontend/src/pages/security/ApiKeys.tsx:511–543` renders the creation form:

```tsx
<form onSubmit={(e) => { e.preventDefault(); createMutation.mutate(); }} className="space-y-3">
  <div>
    <Label htmlFor="key-label">Label (optional)</Label>
    <Input id="key-label" value={label} ... />
  </div>
  <div>
    <Label htmlFor="key-expiry">Expiry</Label>
    <Select value={expiresInDays} ...>
      <SelectContent>
        <SelectItem value="none">No expiry</SelectItem>
        ...
      </SelectContent>
    </Select>
  </div>
  <DialogFooter>
    <Button type="submit" ...>Create Key</Button>
  </DialogFooter>
</form>
```

There is no `capabilities` state, no multi-select component, and no scope-related
UI element anywhere in the 601-line file.

### `createApiKey` call carries no capabilities

`ApiKeys.tsx:250–261`:

```tsx
const createMutation = useMutation({
  mutationFn: () => createApiKey({
    label: label || undefined,
    expires_in_days: expiresInDays === "none" ? undefined : Number(expiresInDays),
    // no capabilities field
  }),
```

The mutation function constructs the request body from component state. The `label`
and `expiresInDays` state variables are initialized at lines 232 and 233 respectively.
There is no `capabilities` state variable in the component at all — a `grep` for
`capabilities` in `ApiKeys.tsx` returns zero results. This confirms the UI has no
awareness of scopes.

### Backend `create_api_key` defaults to full capabilities

`app/services/api_keys.py` (referenced by `GET /ui/account/api-keys`) — when
`capabilities` is omitted or `null`, the service returns
`set(CANONICAL_API_KEY_CAPABILITIES)` (all 25 scopes):

```python
# api_keys.py — effective_api_key_capabilities:
if not allowed:
    return set(CANONICAL_API_KEY_CAPABILITIES)
```

This means keys created through the UI today always receive the maximum set of scopes,
including `ads:manage`, `ads:read`, `ads:serve`, `kyc:admin`, etc. — an over-privileged
default that violates the principle of least privilege.

### Canonical scope list is complete but not exposed

`app/services/api_key_capabilities.py:4–31` defines all 25 capabilities including the
three ads scopes, with implications (`ads:manage` implies `ads:read` and `ads:serve`).
The `normalize_api_key_capabilities` and `expand_api_key_capabilities` functions are
ready to accept a scoped list — they just are never called from the UI flow.

The implication table at `api_key_capabilities.py:37–44` means the UI must be careful
not to display implied scopes redundantly. For example, if a user checks `ads:manage`,
the backend will automatically expand this to `["ads:manage", "ads:read", "ads:serve"]`
via `expand_api_key_capabilities`. The UI should communicate this clearly (e.g.
"ads:manage also grants: ads:read, ads:serve") to avoid user confusion about what
they are actually authorizing.

### `createApiKey` endpoint wrapper

`frontend/src/api/endpoints/account.ts` — `createApiKey` must already accept a
`capabilities` field or the fix must add it. This needs verification (the field is a
known backend model parameter). The backend `POST /ui/account/api-keys` endpoint
processes a `CreateApiKeyIn` Pydantic model; that model includes a `capabilities`
field that accepts `Optional[List[str]]`. If the TypeScript type at
`frontend/src/api/types.ts` mirrors this model, the field already exists but was
never wired to state in the component.

### Missing scope display in key list

Even for keys that were already created with scopes via direct API calls, the current
key list view (ApiKeys.tsx:394–451) shows no scope information per key. A user who
previously created a scoped key via curl has no way to verify its scope assignment
through the UI. The `KeyDetailsDialog` similarly lacks a scope section (confirmed by
reading lines 92–224 — IP Rules, Usage, and Expiry are shown, but Scopes is absent).

## 3. Impact / Exploit / Blast Radius

**Who is affected**: All users who create API keys via the UI — they unknowingly
receive full-scope keys.

**Security consequence**: A key created by any user carries `ads:manage`, `kyc:admin`,
`kyc:upload`, `messager:manage`, etc. by default. If the key is compromised (e.g. leaked
in a client-side app), the attacker can:
- Create and manage ad campaigns on behalf of the key owner.
- Access KYC submission and webhook endpoints.
- Send messages as the user.

The intended security model from ADS-011 is that advertisers request only the scopes
their integration needs (principle of least privilege), but the UI defeats this
entirely by silently granting everything.

**Usability**: Advertisers must know to make a raw `curl` call with a
`{"capabilities": ["ads:read"]}` body; this is not documented in any in-product help
text, creating support burden.

**Audit trail**: With all-scope keys, the audit log (`last_used_at`, usage stats shown
in `KeyDetailsDialog`) cannot distinguish which capability domain was actually exercised.

## 4. Fix Design (code-level)

### Approach: add a capability multi-select to the creation dialog

The fix is a self-contained UI change. No backend changes are required — the backend
already supports scoped creation.

#### 4.1 Add capability state to `ApiKeys.tsx`

Add a `capabilities` state array and a grouped capability selector. Group the 25 scopes
into logical domains for readability:

```tsx
// At the top of the ApiKeys component:
const [capabilities, setCapabilities] = useState<string[]>([]);

const SCOPE_GROUPS = [
  {
    label: "Advertising",
    scopes: ["ads:manage", "ads:read", "ads:serve"],
  },
  {
    label: "File Manager",
    scopes: ["filemanager:admin", "filemanager:read", "filemanager:share", "filemanager:write"],
  },
  {
    label: "KYC",
    scopes: ["kyc:admin", "kyc:read", "kyc:submit", "kyc:upload", "kyc:webhook"],
  },
  {
    label: "Messaging",
    scopes: ["messager:manage", "messager:read", "messager:write"],
  },
  {
    label: "Newsfeed",
    scopes: ["newsfeed:moderate", "newsfeed:read", "newsfeed:write"],
  },
  {
    label: "Shopping",
    scopes: [
      "shopping:cart:write", "shopping:catalog:read",
      "shopping:checkout:write", "shopping:orders:read",
    ],
  },
  {
    label: "Tickets",
    scopes: ["tickets:admin", "tickets:read", "tickets:write"],
  },
];
```

#### 4.2 Render the capability selector in the creation form

Add below the expiry `<Select>`:

```tsx
<div>
  <Label>Scopes <span className="text-xs text-muted-foreground">(leave empty for full access)</span></Label>
  <div className="mt-1 space-y-3 rounded-md border p-3">
    {SCOPE_GROUPS.map((group) => (
      <div key={group.label}>
        <p className="mb-1 text-xs font-semibold text-muted-foreground">{group.label}</p>
        <div className="flex flex-wrap gap-2">
          {group.scopes.map((scope) => (
            <label key={scope} className="flex items-center gap-1.5 text-xs cursor-pointer">
              <input
                type="checkbox"
                checked={capabilities.includes(scope)}
                onChange={(e) => {
                  setCapabilities(prev =>
                    e.target.checked ? [...prev, scope] : prev.filter(s => s !== scope)
                  );
                }}
              />
              <code className="text-xs">{scope}</code>
            </label>
          ))}
        </div>
      </div>
    ))}
  </div>
  {capabilities.length > 0 && (
    <p className="mt-1 text-xs text-muted-foreground">
      {capabilities.length} scope{capabilities.length !== 1 ? "s" : ""} selected
    </p>
  )}
</div>
```

#### 4.3 Pass capabilities to the mutation

Update `createMutation` in `ApiKeys.tsx`:

```tsx
const createMutation = useMutation({
  mutationFn: () => createApiKey({
    label: label || undefined,
    expires_in_days: expiresInDays === "none" ? undefined : Number(expiresInDays),
    capabilities: capabilities.length > 0 ? capabilities : undefined,
  }),
  onSuccess: (data) => {
    queryClient.invalidateQueries({ queryKey: ["apiKeys"] });
    setCreatedKey({ key_id: data.key_id, key_secret: data.key_secret, label, expiresInDays });
    setLabel("");
    setExpiresInDays("none");
    setCapabilities([]);   // reset
  },
  ...
});
```

#### 4.4 Update `createApiKey` endpoint type in `frontend/src/api/endpoints/account.ts`

Ensure `CreateApiKeyParams` (or equivalent type) includes `capabilities?: string[]`.
The backend `POST /ui/account/api-keys` already accepts this field; confirm the type
matches and add it if missing.

#### 4.5 Display granted scopes in `KeyDetailsDialog`

In `KeyDetailsDialog` (ApiKeys.tsx:92–224), add a "Scopes" section below "IP Rules"
that lists `keyData.capabilities` (or falls back to "All scopes" if empty):

```tsx
<div>
  <div className="mb-2 flex items-center gap-1.5 text-sm font-medium">
    <Shield className="h-4 w-4 text-muted-foreground" />
    Scopes
  </div>
  {(keyData.capabilities ?? []).length === 0 ? (
    <p className="text-xs text-muted-foreground italic">All scopes (full access)</p>
  ) : (
    <div className="flex flex-wrap gap-1">
      {(keyData.capabilities ?? []).map((scope) => (
        <Badge key={scope} variant="outline" className="text-[10px] font-mono">
          {scope}
        </Badge>
      ))}
    </div>
  )}
</div>
```

Requires adding `capabilities?: string[]` to the `ApiKey` type in
`frontend/src/api/types.ts`.

### Dev/Prod parity (SECOPS-007)

This is a pure frontend change. The backend `create_api_key` service and
`require_api_key_principal` dependency are already production-identical in dev mode.
No flag gating is needed. The `capabilities` field has been accepted by the backend
since ADS-011 was merged.

### Backward compatibility

- Keys created without capabilities before this fix continue to work unchanged
  (backend treats missing/null capabilities as full access).
- No migration is needed.
- The `ApiKey` DDB item shape is unchanged; `capabilities` is an existing field.

### Alternatives considered

- **Separate "Scopes" settings page**: Over-engineered for a simple list of 25 fixed
  scopes; adds navigation friction.
- **Server-driven scope list endpoint**: Unnecessary — the 25 canonical scopes are
  stable and versioned with the backend. Hardcoding the grouped list in the frontend
  is acceptable; a backend `/ui/account/api-keys/capabilities` endpoint is not worth
  the extra surface area.

## 5. Testing, Verification & Rollout

### Regression test (Playwright E2E)

Add to `frontend/e2e/security.spec.ts` (or a new `api-keys.spec.ts`):

```typescript
test("can create an API key with ads scopes only", async ({ page }) => {
  await injectAuth(page, "alice");
  await page.goto("/settings/security");

  // Open create dialog
  await page.getByRole("button", { name: "Create Key" }).click();

  // Select only ads:read scope
  await page.getByRole("checkbox", { name: "ads:read" }).check();

  await page.getByRole("button", { name: "Create Key" }).last().click();
  await page.getByRole("button", { name: "Done" }).click();

  // Re-open the key and verify scope badge shown
  const keyRow = page.locator("li").last();
  await keyRow.getByRole("button", { name: "View key details" }).click();
  await expect(page.getByText("ads:read")).toBeVisible();
  await expect(page.getByText("ads:manage")).not.toBeVisible();
});
```

**Fails before fix**: The creation dialog has no scope checkboxes; `getByRole("checkbox",
{ name: "ads:read" })` throws an element-not-found error.

**Passes after fix**: The checkbox is present; the key is created with `["ads:read"]`;
the details dialog shows the scope badge.

### Scope display and UX considerations

The `KeyDetailsDialog` scope section (section 4.5 of the fix) is important for
transparency: users must be able to inspect the scopes on an existing key without
revoking it. This is especially important for keys created via the API before this fix
(which carry all 25 scopes). A user reviewing their security posture should see a
prominent "All scopes (full access)" warning rather than an empty badges section.

Additionally, the scope selector in the creation dialog should include a "Select all"
and "Clear all" affordance for power users who want full-scope keys intentionally.
The current proposed design (individual checkboxes grouped by domain) makes it easy
to select minimum required scopes, which is the primary goal. An explicit "grant all
scopes" checkbox (when checked, disables the individual pickers) prevents accidental
over-scoping while still supporting the existing full-scope workflow.

The `ads:manage` → `(ads:read, ads:serve)` implication means the backend will silently
expand a key that has only `ads:manage` checked into all three ads scopes. The UI should
visually show this by greying out `ads:read` and `ads:serve` checkboxes when `ads:manage`
is checked, with a tooltip "Included via ads:manage". This prevents confusion when a
user later views the key's scope list in `KeyDetailsDialog` and sees three badges instead
of the one they selected.
