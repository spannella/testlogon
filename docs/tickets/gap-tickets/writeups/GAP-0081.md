# GAP-0081: Double-Write Claim Race — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement**: `claim_ticket` in `app/services/agent_orchestrator.py` performs two sequential DynamoDB writes — first creating an `AGENT_CLAIM#` record, then updating the `TICKET#META` record — without wrapping them in a single atomic operation. A crash, process kill, or transient network failure between those two writes leaves an orphaned claim record that permanently blocks the ticket from being claimed by any other agent.

- **Severity**: HIGH
- **Source ticket**: AGENT-003
- **Status**: Open
- **Owning area**: Agent Orchestration / Agent Loop
- **Verdict**: Claim CONFIRMED. The two-write sequence exists at `app/services/agent_orchestrator.py:278-312`. A compensating rollback (delete_item) is attempted on write-2 failure but is itself a best-effort operation that can fail silently.
- **Impact**: A ticket whose claim record exists but whose `TICKET#META.agent_worker_id` is blank cannot be picked up again; it appears unclaimed to the worker fleet but rejects new claims. The queue depth counter (`_count_eligible_tickets`) will still count it as eligible, yet every actual claim attempt will fail.
- **Related tickets**: AGENT-003, GAP-0083 (pagination under-count amplifies this defect by hiding orphaned tickets from the dashboard).

## 2. Current-State Investigation (root cause)

### Exact code path

`app/services/agent_orchestrator.py:255-340` — `claim_ticket`:

```python
# Write 1 — line 278-285
T.tickets.put_item(
    Item=claim_item,
    ConditionExpression="attribute_not_exists(pk)",
)

# Write 2 — line 289-312
T.tickets.update_item(
    Key={"pk": f"TICKET#{ticket_id}", "sk": "META"},
    ...
    ConditionExpression=(
        "attribute_not_exists(agent_worker_id) OR agent_worker_id = :empty"
    ),
    ...
)
```

If write-1 succeeds and write-2 raises any exception (`ClientError`, network timeout, `ProvisionedThroughputExceededException`, process termination via SIGKILL), the compensating rollback at line 307-309 runs a best-effort `delete_item`:

```python
except ClientError as e:
    # Rollback claim if ticket update fails
    T.tickets.delete_item(
        Key={"pk": f"AGENT_CLAIM#{ticket_id}", "sk": f"CLAIM#{worker_id}"}
    )
```

This rollback is not atomic. Three things can go wrong:

1. **SIGKILL / OOM / crash between write-1 and write-2**: The `except` block never executes. The orphan persists.
2. **Rollback itself fails**: `delete_item` can raise `ProvisionedThroughputExceededException` or a transient network error; the outer `raise` re-raises the original exception without confirming the delete succeeded.
3. **Simultaneous second worker**: Two workers call `claim_ticket(ticket_id)` within milliseconds. Worker A succeeds on write-1 (conditional put). Worker B also succeeds because A's write-1 used `pk=AGENT_CLAIM#{ticket_id}, sk=CLAIM#{worker_A}` — the condition only checks that *this* PK/SK pair is absent. Both workers can proceed to write-2; write-2 has its own condition expression, so only one will win, but the losing worker's AGENT_CLAIM# record is now orphaned.

### Present vs. missing

- **Present**: conditional `put_item` on write-1 (prevents duplicate claim by the same worker).
- **Present**: compensating manual rollback on `ClientError`.
- **Missing**: atomic two-way rollback on process crash / SIGKILL.
- **Missing**: `TransactWriteItems` call that atomically commits both writes or neither.
- **Missing**: cleanup job for orphaned `AGENT_CLAIM#` records.

### Dev vs. prod

In dev, DynamoDB Local processes requests synchronously in a single Java process; crashes are rare. In production, multi-AZ DynamoDB with real network partitions makes the window between the two writes a real risk. Additionally, the agent loop background task (`_running_loops`) can be interrupted by a Kubernetes pod eviction mid-claim.

## 3. Impact / Exploit / Blast Radius

### Who is affected

Any agent-enabled user whose workers are actively pulling from the ticket queue, particularly under high concurrency (multiple workers fighting for the same ticket).

### Concrete failure scenario

1. Worker W1 calls `claim_ticket("TKT-99")`.
2. Write-1 succeeds: `AGENT_CLAIM#TKT-99 / CLAIM#W1` record now exists in DynamoDB.
3. The uvicorn process is OOM-killed mid-write.
4. Write-2 never executes: `TICKET#TKT-99 / META.agent_worker_id` remains `""`.
5. Worker W2 calls `claim_ticket("TKT-99")`:
   - Write-1 condition: `attribute_not_exists(pk)` — fails because W1's record still exists.
   - Raises `ValueError("Ticket TKT-99 already claimed by another agent")`.
6. W1 has been terminated; no worker ever holds the ticket.
7. `TKT-99` is permanently stuck: visible to `_count_eligible_tickets`, invisible to workers.

### Worst case

Under autoscaling with frequent pod recycling, a busy queue can accumulate dozens of ghost-claimed tickets within hours, bringing effective throughput to zero while the UI dashboard shows a healthy queue depth.

### Financial / data integrity

No monetary impact in the current implementation (claims do not debit wallets), but a stuck ticket means user work never gets done, degrading SLA and potentially causing missed deadlines for time-sensitive tickets.

## 4. Fix Design (code-level)

### Primary fix: `TransactWriteItems`

Replace the two sequential writes with a single `transact_write_items` call. DynamoDB transactions are all-or-nothing; a crash between the two logical operations simply means neither write is committed.

```python
# app/services/agent_orchestrator.py — replace lines 267-312

def claim_ticket(user_id: str, worker_id: str, ticket_id: str) -> Dict[str, Any]:
    ts = now_ts()
    claim_item = {
        "pk": {"S": f"AGENT_CLAIM#{ticket_id}"},
        "sk": {"S": f"CLAIM#{worker_id}"},
        "worker_id": {"S": worker_id},
        "user_id": {"S": user_id},
        "claimed_at": {"N": str(ts)},
        "status": {"S": "active"},
        "checkpoint": {"S": ""},
    }
    tickets_table = T.tickets.name   # resolved table name string

    try:
        T._client.transact_write_items(
            TransactItems=[
                {
                    "Put": {
                        "TableName": tickets_table,
                        "Item": claim_item,
                        "ConditionExpression": "attribute_not_exists(pk)",
                    }
                },
                {
                    "Update": {
                        "TableName": tickets_table,
                        "Key": {
                            "pk": {"S": f"TICKET#{ticket_id}"},
                            "sk": {"S": "META"},
                        },
                        "UpdateExpression": (
                            "SET agent_worker_id = :wid, agent_claimed_at = :ts, "
                            "agent_state = :as_val"
                        ),
                        "ConditionExpression": (
                            "attribute_not_exists(agent_worker_id) "
                            "OR agent_worker_id = :empty"
                        ),
                        "ExpressionAttributeValues": {
                            ":wid": {"S": worker_id},
                            ":ts": {"N": str(ts)},
                            ":as_val": {"S": "claimed"},
                            ":empty": {"S": ""},
                        },
                    }
                },
            ]
        )
    except ClientError as e:
        code = e.response["Error"]["Code"]
        if code == "TransactionCanceledException":
            reasons = e.response.get("CancellationReasons", [])
            # Item 0 = claim; Item 1 = ticket META
            if reasons and reasons[0].get("Code") == "ConditionalCheckFailed":
                raise ValueError(
                    f"Ticket {ticket_id} already claimed by another agent"
                )
            raise ValueError(
                f"Ticket {ticket_id} already claimed by another agent"
            )
        raise
    # … continue with steps 3-4 (worker update, logging) unchanged
```

Note: `T._client` is the underlying `boto3.DynamoDB` low-level client. If the project uses only the resource (`Table`) API, expose the client via `T.tickets.meta.client` and use `T.tickets.table_name` for the table name string. Both are available on any `boto3.resource("dynamodb").Table(...)` instance.

### Secondary fix: orphan reaper

Even after the transaction fix is in place, existing orphaned claim records from the current race can block tickets. Add a scheduled cleanup function:

```python
def _reap_orphaned_claims(user_id: str) -> int:
    """Delete AGENT_CLAIM# records where the corresponding TICKET#META
    has no agent_worker_id (orphaned by a previous crash)."""
    # Scan claim records, batch-get corresponding META, delete orphans.
    ...
```

Call this once on startup and hourly from the fleet heartbeat background task.

### Dev/Prod parity (SECOPS-007)

`TransactWriteItems` is supported by DynamoDB Local 2.x (Java bundle). The local stack uses DynamoDB Local at port 8001; verify the version supports transactions:

```bash
# scripts/local-ddb-init.py — add a startup check
import boto3
ddb = boto3.client("dynamodb", endpoint_url="http://localhost:8001", ...)
# transact_write_items with a trivially True condition validates support
```

No feature flag is required. Both dev and prod use the same code path through `T.tickets`; DynamoDB Local transparently supports `transact_write_items`. This satisfies SECOPS-007's requirement that dev and prod share identical code paths.

### Alternatives considered

- **Pessimistic lock (conditional attribute on ticket before claim)**: Adds a three-write sequence, not fewer.
- **Manual 2-phase commit with TTL-based cleanup**: Complex, slower, harder to reason about.
- **Idempotent retry only**: Doesn't solve the permanent orphan; retry eventually gives up.

```python
# BEFORE FIX: inject a failure on the second write to show orphan is created
def test_orphan_left_on_second_write_failure_before_fix(ddb_tables):
    """Demonstrates the bug: crash after write-1 leaves orphan."""
    tickets, workers = ddb_tables
    original_update = tickets.update_item

    call_count = [0]
    def fail_on_first_update(*args, **kwargs):
        call_count[0] += 1
        raise RuntimeError("Simulated process crash")

    tickets.update_item = fail_on_first_update

    with pytest.raises(RuntimeError):
        svc.claim_ticket("user1", "w1", "tkt1")

    # Orphan check: AGENT_CLAIM# record should NOT exist after failure
    # (This assertion FAILS before the fix — it finds the orphaned record)
    claim = tickets.get_item(
        Key={"pk": "AGENT_CLAIM#tkt1", "sk": "CLAIM#w1"}
    ).get("Item")
    assert claim is None, (
        "ORPHAN DETECTED: AGENT_CLAIM# record persists after write-2 crash. "
        "This test should fail before the TransactWriteItems fix is applied."
    )


# AFTER FIX: same scenario with transact_write_items must leave no orphan
def test_no_orphan_after_atomic_fix(ddb_tables):
    """After fix: a crash scenario leaves no orphaned claim record."""
    tickets, workers = ddb_tables
    # With TransactWriteItems the writes succeed atomically; if we simulate
    # a pre-transaction crash (before the call), neither write happens.
    claim_before = tickets.get_item(
        Key={"pk": "AGENT_CLAIM#tkt1", "sk": "CLAIM#w1"}
    ).get("Item")
    assert claim_before is None

    # Happy path succeeds atomically
    result = svc.claim_ticket("user1", "w1", "tkt1")
    assert result["status"] == "active"

    # Both records exist
    claim = tickets.get_item(
        Key={"pk": "AGENT_CLAIM#tkt1", "sk": "CLAIM#w1"}
    ).get("Item")
    meta = tickets.get_item(
        Key={"pk": "TICKET#tkt1", "sk": "META"}
    ).get("Item")
    assert claim is not None
    assert meta["agent_worker_id"] == "w1"


def test_double_claim_rejected(ddb_tables):
    """Second claim attempt after successful first is rejected."""
    tickets, workers = ddb_tables
    svc.claim_ticket("user1", "w1", "tkt1")
    with pytest.raises(ValueError, match="already claimed"):
        svc.claim_ticket("user1", "w2", "tkt1")
```

**Fails before fix**: `test_no_orphan_after_atomic_fix` will see `claim_before` is already populated if the pre-existing two-write sequence leaks during the happy path (it won't under normal conditions), but `test_orphan_left_on_second_write_failure_before_fix` asserts the orphan is absent — this fails with the current implementation because the `RuntimeError` is not a `ClientError`, so the compensating `delete_item` in the `except ClientError` block is never reached.

**Passes after fix**: `TransactWriteItems` is all-or-nothing; a simulated exception before the transaction call means neither write is committed.

### Rollback plan

The `TransactWriteItems` call is a drop-in replacement for the two-step sequence; rolling back means reverting the single function. No schema migration required.

### Effort & sequencing

- **Effort**: M (2-4 hours implementation + testing)
- **Sequence**: Implement fix first; deploy orphan reaper in the same release to clean up any existing orphans from the current code.
- **Risk**: Low — the transaction semantics are strictly stronger than the current best-effort rollback. DynamoDB Local 2.x supports transactions; verify with `describe_endpoints` or a no-op transaction on startup.
