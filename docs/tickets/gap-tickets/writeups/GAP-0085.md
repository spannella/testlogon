# GAP-0085: Summarization LLM Call Not Implemented for Prod — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement**: `_maybe_trigger_summarization` in `app/services/agent_memory.py` silently truncates memory entries to 200 characters in *all* environments. The docstring claims "In dev mode: simple truncation instead of LLM-based summarization," but there is no `dev_mode` check and no LLM call path — the truncation is unconditional and runs identically in production. Semantic information in long memory entries is discarded permanently once the token budget threshold is crossed, degrading agent performance in prod without any warning.

- **Severity**: HIGH (reliability / feature completeness — advertised behavior is absent in production)
- **Source ticket**: AGENT-005
- **Status**: Open
- **Owning area**: Agent Memory / Summarization
- **Verdict**: Claim CONFIRMED. `app/services/agent_memory.py:535-569` — the entire function is a single truncation path. There is no `if S.dev_mode` branch, no import of an LLM client, and no `AnthropicSummarizationClient` class anywhere in the codebase.
- **Impact**: In production, agents accumulate memories. Once total token count crosses `SUMMARIZE_THRESHOLD` (80,000), older memories are irreversibly truncated to 200 chars. The agent loses the semantic content of its accumulated knowledge, silently degrading performance on complex or long-running projects. Operators and users have no visibility into this happening.
- **Related tickets**: AGENT-005, GAP-0084 (memory content must be sanitized after summarization too — the summary field is also susceptible to injection if the LLM produces output containing signal tokens).

## 2. Current-State Investigation (root cause)

### Exact code path

`app/services/agent_memory.py:535-569` — `_maybe_trigger_summarization`:

```python
def _maybe_trigger_summarization(worker_id: str) -> None:
    """Check if total memory tokens exceed threshold and summarize old entries.

    In dev mode: simple truncation instead of LLM-based summarization.
    """
    memories = list_memories(worker_id, limit=MAX_MEMORY_ENTRIES)
    total_tokens = sum(int(m.get("token_count", 0)) for m in memories)

    if total_tokens <= SUMMARIZE_THRESHOLD:
        return

    # Sort by importance (ascending) then age (oldest first)
    candidates = sorted(
        memories,
        key=lambda m: (int(m.get("importance", 3)), int(m.get("created_at", 0))),
    )

    for mem in candidates:
        if total_tokens <= SUMMARIZE_THRESHOLD:
            break
        if mem.get("summarized"):
            continue

        # Simple summarization: truncate to first 200 chars
        content = mem.get("content", "")
        summary = content[:200] + "..." if len(content) > 200 else content
        old_tokens = int(mem.get("token_count", 0))
        new_tokens = len(summary) // 4

        T.agent_memory.update_item(
            Key={"pk": f"WORKER#{worker_id}", "sk": f"MEM#{mem['memory_id']}"},
            UpdateExpression="SET summarized = :s, summary = :sm, token_count = :tc",
            ExpressionAttributeValues={":s": True, ":sm": summary, ":tc": new_tokens},
        )
        total_tokens -= (old_tokens - new_tokens)
```

The docstring on line 537-538 says "In dev mode: simple truncation" — implying a prod path exists — but there is no `from app.core.settings import S` import in this file (let alone a `S.dev_mode` check) and no alternative code path. The truncation runs unconditionally everywhere.

### What is present vs. missing

- **Present**: Token accounting (`token_count`, `summarized` flag, `SUMMARIZE_THRESHOLD`).
- **Present**: Sort logic (least important, oldest first) for which entries to summarize.
- **Present**: DynamoDB update to mark an entry summarized and store the truncated text.
- **Missing**: Import of `S` (settings) in `agent_memory.py`.
- **Missing**: `if S.dev_mode:` branch to fork the dev truncation from a prod LLM call.
- **Missing**: Any LLM client (`AnthropicSummarizationClient` or similar).
- **Missing**: The original full `content` is overwritten (not preserved) — once truncated, the semantic information is gone.

### How it manifests at runtime

1. A worker processes 40+ tickets over several days.
2. Total memory tokens accumulate past 80,000.
3. `_maybe_trigger_summarization` is called on the next `add_memory` call.
4. The 10 oldest/least-important memories are each truncated to 200 chars.
5. The memories now contain only the first sentence or two of each entry.
6. On the next ticket, `assemble_full_context` includes these truncated stubs.
7. The agent has lost context about earlier decisions, patterns, and project-specific knowledge.
8. This is invisible to operators; the `summarized: True` flag just marks the entries as "processed".

## 3. Impact / Exploit / Blast Radius

### Who is affected

- All workers that accumulate memories over time (i.e., long-lived workers on complex projects).
- Agents working on large codebases where accumulated context (file structures, past decisions, style notes) is critical.

### Concrete failure scenario

1. An agent has 200 memory entries including:
   - `"The project uses snake_case for DB column names"` (truncates to `"The project uses snake_case f..."`)
   - `"Auth tests require calling injectAuth(page, 'alice') before page.goto()"` (truncated to 200 chars, losing the goto call detail)
2. After summarization, the agent creates a ticket fix that uses camelCase column names and fails auth setup.
3. The regression is attributed to "model quality" rather than the memory truncation.

### Compliance / quality assurance

The product documentation (docstring + AGENT-005 design) promises semantic summarization. Shipping truncation as a permanent implementation in production is a material gap between advertised and actual behavior. In a commercial SaaS context this represents an SLA risk.

### Security interaction with GAP-0084

If an LLM is used for summarization, its output must also be sanitized through `sanitize_agent_field` before being stored in the `summary` field — an LLM may reproduce signal tokens from the input content. This must be addressed in the same fix.

## 4. Fix Design (code-level)

### Architecture: Strategy pattern with dev/prod implementations

Introduce a `SummarizationClient` protocol with two concrete implementations and a factory gated by `S.dev_mode`. This satisfies SECOPS-007: same code path in both environments, with the environment-appropriate backend selected by a single flag.

```python
# app/services/agent_memory.py — additions near top

import re
from typing import Protocol
from app.core.settings import S   # add this import

class SummarizationClient(Protocol):
    """Protocol for memory summarization backends."""
    def summarize(self, content: str, title: str, category: str) -> str:
        """Return a concise summary of the content. Must be shorter than content."""
        ...


class MockSummarizationClient:
    """Dev-mode summarization: deterministic truncation for tests and local dev."""

    def summarize(self, content: str, title: str, category: str) -> str:
        if len(content) <= 200:
            return content
        return content[:200] + "..."


class AnthropicSummarizationClient:
    """Production summarization using the Anthropic Messages API.

    Requires ANTHROPIC_API_KEY in environment.
    Uses prompt caching on the system prompt for efficiency.
    """

    _SYSTEM = (
        "You are a memory summarizer for an AI coding agent. "
        "Summarize the provided memory entry into a concise, "
        "semantically complete summary of at most 150 words. "
        "Preserve key facts, decisions, file names, and instructions. "
        "Output only the summary text, no preamble."
    )

    def __init__(self):
        import anthropic
        self._client = anthropic.Anthropic()

    def summarize(self, content: str, title: str, category: str) -> str:
        import anthropic
        try:
            resp = self._client.messages.create(
                model="claude-haiku-4-5",   # fast + cheap for summarization
                max_tokens=256,
                system=[
                    {
                        "type": "text",
                        "text": self._SYSTEM,
                        "cache_control": {"type": "ephemeral"},
                    }
                ],
                messages=[
                    {
                        "role": "user",
                        "content": (
                            f"Category: {category}\nTitle: {title}\n\n"
                            f"Content:\n{content}"
                        ),
                    }
                ],
            )
            summary = resp.content[0].text.strip()
            # Sanitize the LLM output before storing — the LLM may reproduce
            # signal tokens from the content (see GAP-0084)
            from app.services.agent_utils import sanitize_agent_field
            return sanitize_agent_field(summary)
        except Exception as exc:
            logger.warning(
                "summarization.llm_failed worker=%s error=%s — falling back to truncation",
                "unknown", exc,
            )
            # Graceful fallback: truncation is always safe
            return content[:200] + "..." if len(content) > 200 else content


def _get_summarization_client() -> SummarizationClient:
    """Factory: return the appropriate summarization client for this environment."""
    if S.dev_mode:
        return MockSummarizationClient()
    return AnthropicSummarizationClient()
```

### Updated `_maybe_trigger_summarization`

```python
# app/services/agent_memory.py:535-569 — replace

def _maybe_trigger_summarization(worker_id: str) -> None:
    """Check if total memory tokens exceed threshold and summarize old entries.

    In dev mode (S.dev_mode=True): uses MockSummarizationClient (deterministic truncation).
    In production: uses AnthropicSummarizationClient (semantic LLM summarization).
    """
    memories = list_memories(worker_id, limit=MAX_MEMORY_ENTRIES)
    total_tokens = sum(int(m.get("token_count", 0)) for m in memories)

    if total_tokens <= SUMMARIZE_THRESHOLD:
        return

    client = _get_summarization_client()

    candidates = sorted(
        memories,
        key=lambda m: (int(m.get("importance", 3)), int(m.get("created_at", 0))),
    )

    for mem in candidates:
        if total_tokens <= SUMMARIZE_THRESHOLD:
            break
        if mem.get("summarized"):
            continue

        content = mem.get("content", "")
        title = mem.get("title", "")
        category = mem.get("category", "note")

        summary = client.summarize(content, title, category)
        old_tokens = int(mem.get("token_count", 0))
        new_tokens = max(len(summary) // 4, 1)

        T.agent_memory.update_item(
            Key={"pk": f"WORKER#{worker_id}", "sk": f"MEM#{mem['memory_id']}"},
            UpdateExpression=(
                "SET summarized = :s, summary = :sm, token_count = :tc"
            ),
            ExpressionAttributeValues={
                ":s": True,
                ":sm": summary,
                ":tc": new_tokens,
            },
        )
        total_tokens -= (old_tokens - new_tokens)
        logger.info(
            "memory.summarized worker_id=%s memory_id=%s old_tokens=%d new_tokens=%d",
            worker_id, mem["memory_id"], old_tokens, new_tokens,
        )
```

### Settings addition

Add `ANTHROPIC_API_KEY` to `app/core/settings.py` and `app/services/agent_memory.py` may import `S` directly:

```python
# app/core/settings.py — add field
anthropic_api_key: str = ""
```

The `AnthropicSummarizationClient` reads the key from the environment via the `anthropic` SDK's default env-var lookup (`ANTHROPIC_API_KEY`), so no explicit wiring is needed beyond ensuring the key is in the production environment.

### Dev/Prod parity (SECOPS-007)

Both `MockSummarizationClient` and `AnthropicSummarizationClient` implement the same `SummarizationClient` protocol. `_maybe_trigger_summarization` calls `client.summarize(...)` — the same function call regardless of environment. The only difference is *which object* is returned by `_get_summarization_client()`. This is the pattern prescribed by SECOPS-007: one code path, environment-selected implementation.

In dev, `S.dev_mode=True`, so `MockSummarizationClient` is used. Tests can inject `MockSummarizationClient` directly without any mocking of AWS/Anthropic APIs.

### Preserve original content

Consider storing the original `content` in a separate field (`content_original`) before overwriting with the summary, to allow recovery if the summary is inadequate. This is a recommended but optional enhancement.

### Alternatives considered

- **Always use LLM in dev**: Wasteful for unit tests; introduces a test dependency on the Anthropic API.
- **Cache summarization output in S3**: Avoids re-summarizing on export/import cycles; good optimization but not needed for correctness.
- **Use a smaller local model (Ollama)**: Avoids API dependency but introduces a new service dependency; out of scope.

### Rollback plan

Revert `_maybe_trigger_summarization` to the truncation-only version. No data migration needed (the `summarized` flag and `summary` fields remain compatible; truncated summaries are not distinguishable from the old behavior).

### Effort & sequencing

- **Effort**: M (4-8 hours: protocol + two client classes + factory + tests + settings + `ANTHROPIC_API_KEY` wiring)
- **Sequence**:
  1. Deploy `MockSummarizationClient` + `_get_summarization_client` factory first, still using truncation in both modes.
  2. Verify dev tests pass.
  3. Implement `AnthropicSummarizationClient` in a follow-up PR.
  4. Gate behind `S.dev_mode` check.
  5. Deploy to staging with `ANTHROPIC_API_KEY` set; run integration test.
  6. Deploy to production.
- **Risk**: Medium. The Anthropic API is an external dependency. The fallback-to-truncation path in `AnthropicSummarizationClient` ensures that an API outage degrades gracefully rather than crashing the memory system. Rate limits on the Anthropic API should be considered if many workers summarize simultaneously; a simple exponential-backoff retry (built into the `anthropic` SDK) is sufficient for this use case.
