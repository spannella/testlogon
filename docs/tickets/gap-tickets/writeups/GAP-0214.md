# GAP-0214: Fee BPS Settings Not Wired to Live Billing Fee Calculations — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: FIN-018. No prior investigation doc.
> Claim verified against actual code.

## 1. Summary & Classification

**Severity**: HIGH
**Source ticket**: FIN-018 (Billing Configuration UI)
**Owning area**: `app/services/billing_config.py`, `app/routers/billing.py`, `app/services/billing_shared.py`, `app/services/tip_ledger.py`, `app/routers/messaging.py`
**Status**: Open — no fix applied

**Claim verification**: CONFIRMED with precision correction. The as-built gap states that `get_fee_bps(entry_type)` at `billing_config.py:430` "is never imported by `app/routers/billing.py`, `app/services/billing_shared.py`, or any tip/unlock/deposit handler." This is accurate. A comprehensive `grep` across the entire `app/` directory shows `get_fee_bps` is defined only in `billing_config.py` and called from nowhere. The only billing_config function consumed elsewhere is `get_min_payout_cents`, which is imported by `app/services/creator_payouts.py:176`. The impact claim is correct: runtime fee changes via the BillingConfig UI have zero effect on actual transaction fees.

**Related tickets**: GAP-0215 is the companion gap from FIN-018 (call billing timer reads fee from env var). Together these two gaps mean the entire Billing Configuration UI is cosmetic — admin-set fee values are persisted to DDB but never influence any transaction.

## 2. Current-State Investigation (root cause)

### `get_fee_bps` is defined but never called

`app/services/billing_config.py`, lines 430–434:

```python
def get_fee_bps(entry_type: str) -> int:
    """Platform fee in basis points for a transaction type."""
    config = get_billing_config()
    field = _FEE_FIELD_BY_ENTRY_TYPE.get(entry_type, "fee_tips_bps")
    return int(config.get(field, _ALLOWLIST[field]["default"]()))
```

The `_FEE_FIELD_BY_ENTRY_TYPE` map (lines 419–427) covers all major transaction types:

```python
_FEE_FIELD_BY_ENTRY_TYPE = {
    "tip_debit": "fee_tips_bps",
    "tip_credit": "fee_tips_bps",
    "unlock_debit": "fee_unlocks_bps",
    "subscription_charge": "fee_subscriptions_bps",
    "subscription": "fee_subscriptions_bps",
    "catalog_purchase": "fee_catalog_bps",
    "ad_revenue": "fee_ad_revenue_bps",
}
```

A codebase-wide search for `from app.services.billing_config import` or `billing_config.get_fee_bps` finds only one consumer: `creator_payouts.py:176` imports `get_min_payout_cents`. No tip handler, unlock handler, deposit handler, or subscription handler imports `get_fee_bps`.

### Tip billing writes full amount without platform fee deduction

`app/services/tip_ledger.py`, lines 124–172 (`write_tip_ledger`):

```python
# 1. Write debit entry (charge to tipper)
T.billing.put_item(Item={
    ...
    "amount_cents": entry.amount_cents,   # ← full tip amount, no fee deducted
    ...
})
# 2. Write credit entry (income to recipient)
T.billing.put_item(Item={
    ...
    "amount_cents": entry.amount_cents,   # ← same full amount credited to creator
    ...
})
```

The platform takes zero fee on every tip transaction. An admin who sets `fee_tips_bps = 2000` (20%) via `PATCH /ui/admin/billing-config` sees the value stored in DDB and returned by `GET /ui/admin/billing-config`, but every tip still credits 100% of the tip amount to the creator.

### Unlock billing also writes full amount

`app/routers/messaging.py`, lines 13639–13689 (unlock ledger write path):

```python
billing_tbl_led.put_item(Item={
    "pk": f"USER#{user_id}",
    ...
    "amount_cents": amount_cents,   # ← full unlock price, no fee split
    ...
})
# Credit the seller (creator)
if _seller_id and _seller_id != user_id:
    billing_tbl_led.put_item(Item={
        "pk": f"USER#{_seller_id}",
        ...
        "amount_cents": amount_cents,   # ← full amount to creator, no deduction
        ...
    })
```

No platform fee deduction occurs. `get_fee_bps` is never called.

### There is no `platform_fee_bps` setting in `app/core/settings.py`

The FIN-018 ticket NOTE states: "There is NO `platform_fee_bps` setting — tip/unlock platform fees are not parameterized as a global BPS setting." This was verified: `grep "platform_fee_bps" app/core/settings.py` returns nothing. The billing config allowlist provides the canonical runtime value; there is no fallback env-var to compete with it. The fix therefore has a clean insertion point.

### The billing_config cache is correct and efficient

`get_billing_config()` (lines 230–272) uses an in-memory cache with a configurable TTL (`billing_config_cache_ttl_seconds`, default 60s) and is invalidated immediately on write. Calling `get_fee_bps` on every tip/unlock is safe: the first call per TTL window hits DDB; subsequent calls within the window are served from `_config_cache`. Performance impact is negligible.

### Dev vs. prod

The billing ledger writes in `tip_ledger.py` and `messaging.py` do not branch on `S.dev_mode`. The same no-fee path runs in both environments. Adding `get_fee_bps` calls will introduce the same correct behavior in both.

## 3. Impact / Exploit / Blast Radius

### Financial impact

Every tip and unlock transaction since the BillingConfig UI was deployed has incorrectly credited 100% of the transaction amount to creators instead of `(100% - fee%)`. At the default `fee_tips_bps = 2000` (20%), the platform has collected zero platform revenue on tip and unlock transactions.

**Concrete example**: A $10 tip at 20% fee should produce:
- Tipper debit: $10.00
- Creator credit: $8.00
- Platform revenue: $2.00

Current behavior:
- Tipper debit: $10.00
- Creator credit: $10.00
- Platform revenue: $0.00

Over time at scale this is a significant revenue leak. Additionally, for subscription and catalog transactions, the platform fee configured via the UI is similarly ignored (the subscription service and catalog service were checked via grep and also do not call `get_fee_bps`).

### No security exploit

This is a financial correctness gap, not a security vulnerability. No user can manipulate fee values (the BillingConfig endpoint requires ROOT role).

### Blast radius

All transaction types covered by `_FEE_FIELD_BY_ENTRY_TYPE`: tips, unlocks, subscriptions, catalog purchases, ad revenue. Only minimum-payout enforcement (`get_min_payout_cents`) is correctly wired. Call billing is a separate gap (GAP-0215).

## 4. Fix Design (code-level)

### Overview

For each billing handler that collects a platform fee, introduce a call to `get_fee_bps(entry_type)`, split the gross amount into `platform_fee_cents` and `net_cents`, write the buyer debit for the full gross amount, and write the creator credit for `net_cents` only. Optionally, write a platform revenue ledger entry for `platform_fee_cents`.

### Step 1 — Fix tip ledger (`app/services/tip_ledger.py`)

Replace the hardcoded `entry.amount_cents` credit with a fee-adjusted net amount:

```python
from app.services.billing_config import get_fee_bps

def write_tip_ledger(entry: TipLedgerEntry) -> Dict[str, str]:
    # ... collaboration split check (unchanged) ...

    ts = now_ts()
    debit_id = uuid.uuid4().hex
    credit_id = uuid.uuid4().hex
    reason = _reason_for_content_type(entry.content_type)
    meta = _build_meta(entry)

    # Compute platform fee
    fee_bps = get_fee_bps("tip_debit")
    platform_fee_cents = (entry.amount_cents * fee_bps) // 10000
    creator_net_cents = entry.amount_cents - platform_fee_cents

    result = {"debit_entry_id": debit_id, "credit_entry_id": credit_id}

    # 1. Debit tipper for the full gross amount (unchanged)
    try:
        T.billing.put_item(Item={
            "pk": f"USER#{entry.tipper_user_id}",
            "sk": f"LEDGER#{ts}#{debit_id}",
            "type": "debit",
            "amount_cents": entry.amount_cents,   # gross — tipper sees full charge
            "currency": entry.currency,
            "state": "settled",
            "reason": reason,
            "meta": {**meta, "platform_fee_bps": fee_bps, "platform_fee_cents": platform_fee_cents},
        })
    except Exception:
        logger.warning("tip_ledger_debit_write_failed", ...)

    # 2. Credit creator for net amount after platform fee
    try:
        T.billing.put_item(Item={
            "pk": f"USER#{entry.recipient_user_id}",
            "sk": f"LEDGER#{ts}#{credit_id}",
            "type": "credit",
            "amount_cents": creator_net_cents,   # net — was entry.amount_cents before fix
            "currency": entry.currency,
            "state": "settled",
            "reason": reason,
            "meta": {**meta, "platform_fee_bps": fee_bps, "platform_fee_cents": platform_fee_cents},
        })
    except Exception:
        logger.warning("tip_ledger_credit_write_failed", ...)

    return result
```

### Step 2 — Fix unlock billing (`app/routers/messaging.py`, unlock path ~line 13639)

```python
from app.services.billing_config import get_fee_bps

# Inside the unlock endpoint, replace the credit ledger write:
_fee_bps = get_fee_bps("unlock_debit")
_platform_fee_cents = (amount_cents * _fee_bps) // 10000
_creator_net_cents = amount_cents - _platform_fee_cents

# The buyer debit stays at amount_cents (full price)
# Replace creator credit:
if _seller_id and _seller_id != user_id:
    billing_tbl_led.put_item(Item={
        "pk": f"USER#{_seller_id}",
        "sk": f"LEDGER#{unlock_ts}#{credit_entry_id}",
        "amount_cents": _creator_net_cents,   # was amount_cents
        "meta": {
            ...,
            "platform_fee_bps": _fee_bps,
            "platform_fee_cents": _platform_fee_cents,
        },
    })
```

### Step 3 — Fix subscription and catalog fee handlers (follow-on, same pattern)

`app/services/subscription_billing.py` (if present) and catalog purchase handlers should import `get_fee_bps("subscription_charge")` / `get_fee_bps("catalog_purchase")` respectively. The pattern is identical: gross debit from buyer, net credit to creator.

### Step 4 — Optional: platform revenue ledger entry

For auditability, write a third entry to a platform revenue record on each fee-bearing transaction:

```python
platform_entry_id = uuid.uuid4().hex
T.billing.put_item(Item={
    "pk": "PLATFORM#REVENUE",
    "sk": f"LEDGER#{ts}#{platform_entry_id}",
    "type": "platform_fee",
    "amount_cents": platform_fee_cents,
    "source_entry_type": "tip_debit",
    "source_entry_id": debit_id,
})
```

This is optional for the initial fix but necessary for FIN-013 (platform financial dashboard).

### Dev/Prod parity (SECOPS-007)

`get_fee_bps` calls `get_billing_config()`, which reads from DDB (`T.billing_config`). In dev mode, DynamoDB Local is used. In production, the real DDB table is used. Both environments hit the same code path — the in-memory cache is per-process and works identically in both. No mock-specific branching is added. Dev mode does not override the config lookup.

If `billing_config_ddb_enabled = False` (an existing settings flag), `get_billing_config` falls back to env-backed defaults — the fix is still correct, just using the env-var-derived BPS value as the fallback, which matches current behavior.

### Backward compatibility

Existing transactions are unaffected (ledger entries are immutable). Going forward, creator net amounts will decrease by the configured fee percentage. This is the intended behavior of the billing config feature. Finance should be informed before deployment so they can set the correct BPS values in the config UI prior to the code change going live.

### Manual QA steps

1. Start dev stack (`just up`).
2. Set `fee_tips_bps = 2000` via `PATCH /ui/admin/billing-config` (if not already default).
3. Seed Alice with wallet balance via DDB.
4. Alice sends a $10 tip to Bob via `POST /ui/messaging/conversations/{id}/messages` with `tip_amount_cents=1000`.
5. Query Bob's billing ledger: expect a `credit` entry with `amount_cents=800`.
6. Query Alice's billing ledger: expect a `debit` entry with `amount_cents=1000`.
7. Confirm `meta.platform_fee_bps=2000` and `meta.platform_fee_cents=200` on both entries.
8. Change `fee_tips_bps` to 1000 (10%) via the billing-config UI. Wait 60 seconds for cache TTL.
9. Send another tip. Confirm new credit amount = 900.

### Rollout sequencing

The fee change will reduce creator net earnings on tips going forward. This is intentional but must be coordinated:

1. Finance confirms the correct BPS values to deploy with.
2. Set BPS values in billing config to `0` before deploying the code change (to avoid a surprise fee drop at deploy time).
3. Deploy the code change.
4. Finance sets the correct BPS values via the UI — fees take effect immediately (within 60s cache TTL).

**Effort**: M (2–3 days for tip + unlock; additional 2 days for subscription/catalog).
**Rollback**: Remove the `get_fee_bps` import and revert creator credit writes to `entry.amount_cents`. Fees return to 0 effectively.
**Risk**: Medium. The change affects financial settlement on every tip and unlock transaction. Staging/canary deployment with real transaction monitoring is strongly recommended.
