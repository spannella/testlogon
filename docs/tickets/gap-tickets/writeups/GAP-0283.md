# GAP-0283: `_active_case_counts` Loads All Active Cases Into Memory to Count Admin Assignments — Remediation Write-up

## 1. Summary & Classification

**Ticket**: GAP-0283 | **Source**: KYC-019 | **Severity**: HIGH | **Status**: Open | **Effort**: L
**Owning area**: KYC — case assignment workload management (`app/services/kyc_case_assignment.py`)

`_active_case_counts` in `KycCaseAssignmentService` (line 238) calls `_scan_active_cases` (lines 136–157), which issues three separate GSI queries — one each for `status=submitted`, `status=under_review`, and `status=needs_more_info` — and returns every matching case item in full. `_active_case_counts` then iterates all returned items in Python to build a `{admin_sub → count}` map. In a production environment with thousands of under-review cases this is an O(N-cases) in-memory aggregation on the critical path of every assignment-scoring and workload-display operation. Additionally, `_active_case_counts` is called from multiple contexts that only need a single admin's count (`get_admin_availability`, `set_admin_availability`) but still fetch the entire active-cases dataset.

**Verdict**: Confirmed. The claim is accurate. The code matches the ticket description exactly. The three-query scan with Python-side aggregation is present at `app/services/kyc_case_assignment.py` lines 136–244.

**Related tickets**: GAP-0282 (companion full-table scan in `_scan_availability_items`), GAP-0024 (full-table scan in case listing).

## 2. Current-State Investigation (root cause)

### The data-access chain today

#### `_scan_active_cases` (lines 136–157)

```python
def _scan_active_cases(self) -> list[dict[str, Any]]:
    statuses = ("submitted", "under_review", "needs_more_info")
    out: list[dict[str, Any]] = []
    for status in statuses:
        ekey: dict[str, Any] | None = None
        while True:
            kwargs: dict[str, Any] = {
                "IndexName": S.kyc_cases_status_index_name,
                "KeyConditionExpression": "gsi_status_pk = :pk",
                "ExpressionAttributeValues": {":pk": f"STATUS#{status}"},
            }
            if ekey:
                kwargs["ExclusiveStartKey"] = ekey
            resp = self._table.query(**kwargs)
            out.extend(
                row for row in resp.get("Items", [])
                if row.get("entity_type") == "kyc_case"
            )
            ekey = resp.get("LastEvaluatedKey")
            if not ekey:
                break
    return out
```

This performs 3 GSI queries (one per active status), each potentially returning thousands of full case items with pagination.

#### `_active_case_counts` (lines 238–244)

```python
def _active_case_counts(self) -> dict[str, int]:
    counts: dict[str, int] = {}
    for case in self._scan_active_cases():       # ← O(N) load
        assigned = str((case.get("review") or {}).get("assigned_admin_sub") or "").strip()
        if assigned:
            counts[assigned] = counts.get(assigned, 0) + 1
    return counts
```

Every call to any of the following invokes `_active_case_counts`:

The cumulative effect: with 2,000 active cases and 30 admins, every KYC submission triggers a network roundtrip fetching ~2,000 full case items (each potentially 2–5 KB in DynamoDB), serializing the full item set into Python memory, and counting assignments. At 100 submissions/day and a 5-minute SLA check loop: thousands of RCU-heavy page reads per day.

### What is present vs missing

Present: correct pagination of the three status-based GSI queries (no missing pages).

Missing: a dedicated assignment-count counter per admin, maintained at write time, so that reads can be O(1) or O(A) (where A is the number of admins) rather than O(N-cases).

## 3. Impact / Exploit / Blast Radius

**Latency on the assignment critical path**: `auto_assign` is called synchronously during KYC submission. If the active-case query takes 3 seconds (plausible at 2,000+ cases), every KYC submission is blocked for 3 seconds.

**DynamoDB throughput exhaustion**: Three GSI queries returning 2,000 items at ~3 KB each ≈ 6 MB per invocation. With DynamoDB returning a maximum of 1 MB per page, this is at least 6 pages × 3 statuses = 18 page reads. Each 4 KB costs 0.5 RCUs (eventually consistent) → ~750 RCUs per `auto_assign` call. At 100 submissions/day plus the 5-minute SLA sweep (288 sweeps/day): 288 × 750 = 216,000 extra RCUs/day. On a 100-RCU provisioned table this saturates provisioned capacity within 1 day of production load, causing `ProvisionedThroughputExceededException` and stalling all KYC submissions.

**No security or data-integrity impact**: This is a performance and availability gap. Data returned is correct.

**`list_my_assigned` compounds the problem**: `list_my_assigned` also calls `_scan_active_cases` independently (line 441), loading the full active-case list a second time for the same admin view request.

**SLA checker impact**: `run_sla_escalation_sweep` calls `check_sla_compliance` (line 615) which calls `_scan_active_cases` directly. Combined with the 5-minute interval timer in `kyc_sla_checker_loop` (line 730), this guarantees at least 288 full active-case scans per day from the background task alone, regardless of submission volume. As the active-case count grows from hundreds to thousands, the SLA checker itself becomes a DynamoDB-intensive background job that competes with real-time submission and review traffic.

**Cascading failure scenario**: At peak load — say a system with 3,000 active cases, 50 submissions/hour, and the 5-minute SLA sweep — the following DDB reads occur per hour: 50 submissions × 750 RCUs (auto-assign) + 12 SLA sweeps × 750 RCUs (compliance check) = 46,500 RCUs/hour purely for the case-count and SLA operations. With a provisioned capacity of 100 RCUs, the table exceeds burst capacity within minutes, and AWS DynamoDB rate-limits subsequent reads, causing cascading timeouts across all KYC operations including case creation, file attachment, and admin review — none of which use the active-case scan themselves but share the same table and provisioned capacity.

## 4. Fix Design (code-level)

### Approach A (Preferred): Per-Admin Assignment Counter

Maintain a live counter of assigned active cases per admin, updated atomically at write time. Since assignment is written via `_write_assignment` (line 462), the counter can be incremented/decremented there using DynamoDB's atomic `ADD` update expression.

#### Counter item schema (same `kyc_cases` table, single-table pattern)

```
PK: ADMIN#{admin_sub}
SK: ASSIGN_COUNT
count: N   (DynamoDB Number, atomic increment)
```

#### Changes to `_write_assignment` (lines 462–511)

After writing the case review update, atomically update the counter:

```python
# In _write_assignment, after self._table.update_item(...) on the case item:

# Decrement old admin's counter (if re-assigning away from an existing assignee)
if from_admin:
    try:
        self._table.update_item(
            Key={"pk": _admin_pk(from_admin), "sk": "ASSIGN_COUNT"},
            UpdateExpression="ADD #cnt :dec",
            ExpressionAttributeNames={"#cnt": "count"},
            ExpressionAttributeValues={":dec": -1, ":zero": 0},
            ConditionExpression="attribute_exists(pk) AND #cnt > :zero",
        )
    except ClientError:
        pass  # Counter row may not exist yet; safe to ignore

# Increment new admin's counter
if new_admin_sub:
    self._table.update_item(
        Key={"pk": _admin_pk(new_admin_sub), "sk": "ASSIGN_COUNT"},
        UpdateExpression="ADD #cnt :inc SET entity_type = if_not_exists(entity_type, :et)",
        ExpressionAttributeNames={"#cnt": "count"},
        ExpressionAttributeValues={":inc": 1, ":et": "kyc_admin_assign_count"},
    )
```

For unclaim (`new_admin_sub = None`), only the decrement applies.

#### Replace `_active_case_counts` with a counter read

```python
def _active_case_counts(self) -> dict[str, int]:
    """Return {admin_sub: count} from pre-computed counters (O(A), not O(N))."""
    # Fetch all ASSIGN_COUNT items for known admins via a GSI query on entity_type
    # or by batch-reading known admin PKs.  Fall back to the scan path if no counters
    # exist yet (e.g., fresh deploy before any assignments have been made).
    items = self._table.query(
        IndexName=S.kyc_cases_entity_type_index_name,   # entity-type-index from GAP-0282
        KeyConditionExpression="entity_type = :et",
        ExpressionAttributeValues={":et": "kyc_admin_assign_count"},
    ).get("Items", [])
    if not items:
        # Warm-up path: fall back to legacy scan on first deploy
        return self._legacy_active_case_counts()
    return {
        str(item.get("admin_sub") or str(item.get("pk") or "").removeprefix("ADMIN#")): max(0, int(item.get("count") or 0))
        for item in items
    }

def _legacy_active_case_counts(self) -> dict[str, int]:
    """Fallback: O(N) scan used only during warm-up or counter inconsistency recovery."""
    counts: dict[str, int] = {}
    for case in self._scan_active_cases():
        assigned = str((case.get("review") or {}).get("assigned_admin_sub") or "").strip()
        if assigned:
            counts[assigned] = counts.get(assigned, 0) + 1
    return counts
```

Note: the `entity-type-index` GSI from GAP-0282 is reused here, requiring only one new GSI to fix both issues.

### Approach B (Minimal, lower effort): Add `assigned_admin_sub` GSI to `kyc_cases`

Add a new GSI with `PK = assigned_admin_sub` on `kyc_cases`. Then, per-admin count = `Query(IndexName="...", KeyConditionExpression="assigned_admin_sub = :s", Select="COUNT")`. This avoids maintaining a counter but requires a GSI on a field that may be null for unassigned cases (DynamoDB does not index null/absent fields, which is correct behaviour here — only assigned cases appear in the index).

```python
def _count_for_admin(self, admin_sub: str) -> int:
    resp = self._table.query(
        IndexName=S.kyc_cases_assigned_admin_index_name,
        KeyConditionExpression="assigned_admin_sub = :a",
        ExpressionAttributeValues={":a": admin_sub},
        Select="COUNT",
        FilterExpression="gsi_status_pk IN (:s1,:s2,:s3)",
        ExpressionAttributeValues={
            ":a": admin_sub,
            ":s1": "STATUS#submitted",
            ":s2": "STATUS#under_review",
            ":s3": "STATUS#needs_more_info",
        },
    )
    return int(resp.get("Count") or 0)
```

Approach A is preferred because it eliminates per-call DDB queries entirely for the count aggregation step.

### Dev/Prod parity (SECOPS-007)

Counter updates are DynamoDB `update_item` operations using atomic `ADD`. These work identically under DynamoDB Local (dev) and AWS DynamoDB (prod). No mock-specific path is needed.

### Backward compatibility and migration

- Existing deployed systems with active assignments have no counter rows. The `_legacy_active_case_counts` fallback ensures a seamless transition.
- A one-time reconciliation job can be run to seed counters from the current assignment state. The job iterates `_scan_active_cases()` once and writes the initial counter values. This is a run-once operational task, not a schema migration.
- Feature flag `KYC_ASSIGNMENT_COUNTER_ENABLED` (default `false`) gates the counter path. Flip to `true` after reconciliation.

### Rollout

1. Deploy counter write path with `KYC_ASSIGNMENT_COUNTER_ENABLED=false` (writes counters but reads via legacy scan).
2. Let assignments warm counters organically, or run reconciliation job.
3. Switch `KYC_ASSIGNMENT_COUNTER_ENABLED=true`.
4. Monitor DynamoDB RCU consumption; expect 95%+ reduction in active-case-related reads.
5. Rollback: set flag back to `false` — read path reverts to legacy scan.
