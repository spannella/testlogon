# GAP-0106: top_content view attribution bug — Remediation Write-up

> Claim verified against `app/services/creator_analytics.py`. Claim is **partially correct** — the
> root bug exists in `get_top_content` at lines 438-441, but the ticket's cited line number (432)
> is the function definition, not the offending loop. Additionally, the identical attribution
> pattern exists in `get_overview` at lines 206-209, which the ticket does not mention.

## 1. Summary & Classification

**Bug**: `get_top_content` (and `get_overview`) attribute the entire day's `total_views` rollup
figure to every content ID that appears in that day's `top_content_ids` list. A creator whose
three videos collectively drove 500 views on a given day will see 500 views credited to each
of the three videos, yielding a combined "attributed" total of 1,500 views — triple the real
figure.

- **Severity**: HIGH (misleading financial/business metric; creators use top-content rankings to
  make monetisation decisions)
- **Source ticket**: ANALYTICS-001
- **Status**: Open
- **Owning area**: Backend analytics service (`app/services/creator_analytics.py`)
- **Verdict**: Confirmed. The offending accumulation loop is real and runs on every call to
  `GET /analytics/top-content`. The `get_overview` function contains a structurally identical
  bug (not mentioned in the ticket).
- **Claim accuracy note**: The ticket cites line 432 (the function's `def` statement). The actual
  defective lines are 438-441 (the accumulation loop inside the function body). Both functions
  (`get_top_content` and `get_overview`) are affected; the ticket only names `get_top_content`.
- **Related tickets**: ANALYTICS-002 (per-video live view counts via `_resolve_content_details`
  already implemented and can be used as the fix), GAP-0107 through GAP-0110 (unrelated).

## 2. Current-State Investigation (root cause)

### How rollup rows are produced

The analytics pipeline writes one `DAILY#<YYYY-MM-DD>` row per creator per day to the
`analytics_rollups` DynamoDB table. The rollup writer aggregates all view events for the
day and writes a single integer `total_views` — the combined count across all content items
the creator published that day. It also writes a `top_content_ids` list: the content IDs
that received the most activity that day, ranked by the rollup writer's own internal
heuristic. Crucially, the rollup writer does **not** store a per-content view breakdown; it
stores only the aggregate and the ID list.

This schema design is a space-efficiency trade-off: it avoids storing a potentially large
map of `{content_id: view_count}` pairs in every row. The expectation was that `get_top_content`
would resolve per-content counts from the source-of-truth metadata tables. That resolution
step exists in `_resolve_content_details` — but the sorting and scoring step runs before it,
on the wrong data.

### DynamoDB rollup schema

Each daily rollup row stored under `CREATOR#<user_id>` / `DAILY#<YYYY-MM-DD>` contains:

```
total_views       INT   — sum of ALL views for that creator on that day
top_content_ids   LIST  — content IDs with the most activity (no per-content view count)
```

There is no per-content view count stored in rollup rows. The rollup writer records only the
aggregate view total and the ranked list of busy content IDs.

### get_top_content — lines 424-475

`app/services/creator_analytics.py:432` (function definition)

```python
def get_top_content(user_id, from_date, to_date, sort_by="views", limit=20):
    items = _query_rollups(user_id, from_date, to_date)

    content_scores = defaultdict(lambda: {"views": 0, "revenue_cents": 0})
    for item in items:                                      # each daily rollup row
        for cid in (item.get("top_content_ids") or []):    # every content ID in the list
            content_scores[cid]["views"] += _to_int(item.get("total_views", 0))  # BUG: line 440
            content_scores[cid]["revenue_cents"] += _to_int(item.get("revenue_cents", 0))
```

`item.get("total_views", 0)` is the day's **aggregate** view count across all content, not the
views for `cid`. If three content IDs appear in `top_content_ids` for that day, each receives
a full copy of `total_views`. Over a seven-day range with three content IDs per day, the sum
reported for a content ID is `7 × daily_total`, which is meaningless.

The same pattern appears verbatim in `get_overview` at lines 206-209:

```python
for item in items:
    for cid in (item.get("top_content_ids") or []):
        content_scores[cid]["views"] += _to_int(item.get("total_views", 0))  # BUG: line 209
```

### _resolve_content_details — lines 357-421

The function `_resolve_content_details` **already** fetches live per-content view counts:
- For video IDs (`vid_*`) it calls `batch_get_item` on the `video_metadata` table, projecting
  `view_count, like_count, comment_count` (lines 374-388).
- For post IDs it fetches `POST#<id> / META` from `app_single_table` and reads `view_count`
  (lines 400-415).

In `get_top_content` the resolved details are consumed at line 458:

```python
views = d.get("views") if d.get("views") is not None else scores["views"]
```

This fallback is correct — when `_resolve_content_details` returns live data the per-content
count is used — but only for the **final output**. The sort ranking (lines 443-449) is still
performed on the inflated `content_scores["views"]` values, meaning the wrong content IDs can
appear in the top-N list before the live counts are applied.

### The view override at line 458 does not fix the sort

A superficially reassuring line appears in the output-building loop:

```python
views = d.get("views") if d.get("views") is not None else scores["views"]
```

This means the **displayed** view count in the response may be correct (when
`_resolve_content_details` returns data from `video_metadata`). However the **ranking** that
determined which content IDs are in `sorted_content[:limit]` was already computed on the
inflated `scores["views"]` values. So the top-N list can contain the wrong items even if the
view count shown for each item is accurate. A content ID that appeared in many days' rollup
lists (even if it had few actual views) can bubble to the top because its inflated aggregate
sum is larger than a genuinely popular item that appeared in fewer rollup rows.

### Dev vs prod behaviour

The bug is path-independent: both dev (DynamoDB Local) and prod (DynamoDB on AWS) execute
the same Python loop. The magnitude of the error scales with the number of content IDs in
`top_content_ids` per rollup row, which is controlled by the rollup writer. In a typical
production scenario with five to ten items per rollup row, every item's attributed views are
overstated by a factor of five to ten relative to the day's real per-item count.

## 3. Impact / Exploit / Blast Radius

### Data integrity

- **Creator dashboard** shows wildly inflated per-content view counts. A creator with three
  equally popular videos each getting 167 daily views (500 total) will see 500 attributed to
  each, suggesting the first is 3× more popular than it actually is.
- **Sort order is wrong**: the top-N ranking is computed on inflated scores. Content that
  appears in `top_content_ids` on more days wins unfairly regardless of true view count.
- **get_overview** is also corrupted: the "top content" card on the overview dashboard
  (`GET /analytics/overview`) suffers the same inflation, compounding confusion.

### Financial / business consequences

- Creators make pricing and promotion decisions (pay-per-view prices, subscription tiers,
  which content to boost) based on this metric. Incorrect data can lead to real revenue
  miscalculation.
- If the platform uses `top_content` rankings to drive recommendations or ad placements,
  campaigns target the wrong content.
- No direct financial exploit by an external attacker — this is an internal data-quality bug,
  not an authorisation gap.

### Scope

Affects every creator who has more than one content ID in any single rollup day's
`top_content_ids` list, which is the normal case. The bug has existed since ANALYTICS-001
was shipped.

## 4. Fix Design (code-level)

### Option A — Use live counts from _resolve_content_details for ranking (recommended)

The cleanest approach is to make the sort ranking consistent with the output already produced
at line 458. Instead of accumulating the broken `content_scores["views"]` from rollup rows,
collect the deduplicated content IDs first, resolve live counts upfront, and rank on those.

**Changes to `app/services/creator_analytics.py`:**

```python
def get_top_content(user_id, from_date, to_date, sort_by="views", limit=20):
    items = _query_rollups(user_id, from_date, to_date)

    # Collect deduplicated content IDs and aggregate revenue_cents per content.
    # Revenue is stored per-day in the rollup but NOT per-content; we keep the
    # aggregate as a best-effort attribution.  Views come from live metadata below.
    seen: set[str] = set()
    ordered_ids: list[str] = []
    revenue_by_cid: dict[str, int] = defaultdict(int)

    for item in items:
        for cid in (item.get("top_content_ids") or []):
            if cid not in seen:
                seen.add(cid)
                ordered_ids.append(cid)
            # Revenue attribution note: still a coarse approximation;
            # see Option B for a complete per-content revenue solution.
            revenue_by_cid[cid] += _to_int(item.get("revenue_cents", 0)) // max(1, len(item.get("top_content_ids") or [1]))

    total_items = len(ordered_ids)
    # Resolve live per-content counts BEFORE ranking
    details = _resolve_content_details(ordered_ids)

    sort_key = "revenue_cents" if sort_by == "revenue" else "views"

    def _score(cid):
        d = details.get(cid, {})
        if sort_key == "views":
            return d.get("views") or 0
        return revenue_by_cid.get(cid, 0)

    sorted_content = sorted(ordered_ids, key=_score, reverse=True)[:limit]

    result_items = []
    for cid in sorted_content:
        d = details.get(cid, {})
        views = d.get("views", 0)
        likes = d.get("likes", 0)
        comments = d.get("comments", 0)
        rev = revenue_by_cid.get(cid, 0)
        engagement = (likes + comments) / views if views > 0 else 0.0
        content_type = "vod" if cid.startswith("vid_") else "post"
        result_items.append({
            "content_id": cid,
            "content_type": content_type,
            "title": d.get("title", cid),
            "views": views,
            "revenue_cents": rev,
            "engagement_rate": round(engagement, 4),
        })

    return {"items": result_items, "total_items": total_items}
```

Apply the same deduplication-first approach to `get_overview` (lines 205-221): collect
`ordered_ids`, call `_resolve_content_details`, then rank and build `top_content` from live
counts rather than from accumulated `total_views`.

### Revenue attribution caveat

Revenue (`revenue_cents`) presents the same problem: the rollup stores the day's total
revenue, not a per-content breakdown. Option A's fix uses an evenly distributed approximation
(`total_revenue / count_of_top_content_ids`) to avoid the worst inflation, but this is still
an approximation. A comment in the code should call this out explicitly so future developers
do not mistake it for accurate per-content revenue data. Accurate per-content revenue
requires a schema change (Option B below).

### Option B — Store per-content view counts in rollup rows

The rollup writer (not in scope here but tracked under ANALYTICS-002) would store a
`content_views` DynamoDB map: `{"vid_abc": 120, "post_xyz": 47}` and a
`content_revenue` map. `get_top_content` would read from these maps instead of
`total_views`/`revenue_cents`. This is the long-term correct solution but requires a schema
migration for historical rows and a rollup-writer change; Option A is deployable immediately
with no schema change and no historical data impact. Old rows without per-content maps
naturally fall back to `_resolve_content_details` live counts, which is Option A's approach.

### Dev/Prod parity (SECOPS-007)

Option A touches only Python service logic and the DynamoDB read path. The DynamoDB table
and `_resolve_content_details` already work identically in dev (DynamoDB Local port 8001)
and prod (AWS DynamoDB). No mock/feature-flag branching is needed. The `video_metadata` and
`app_single_table` tables must both exist and be seeded before the test suite runs; both are
already created by `scripts/local-ddb-init.py`.

### Backward compatibility

The API response shape (`items`, `total_items`) is unchanged. View counts in the response
move from inflated aggregate values to accurate live counts — this is a data quality
improvement, not a breaking change.
