# GAP-0145: Missing Timeline System Message on Recording Completion — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Gap statement**: When a call recording upload is completed — transitioning the recording to `"ready"` status — no timeline system message is inserted into the conversation's Messages table. Users who did not actively open the recordings panel have no in-chat signal that a recording exists. The only discovery path is the separate `GET /messages/recordings` endpoint or the per-call `GET /messages/calls/{call_id}/recording` endpoint.

- **Severity**: HIGH
- **Source ticket**: CALL-009
- **Status**: Open — confirmed in production code. `app/routers/call_recording.py:322` (`complete_recording_upload`) does not call `emit_call_timeline_event` at any point.
- **Owning area**: `app/routers/call_recording.py:322-393`
- **Investigation verdict**: Claim is confirmed. The cited endpoint `app/routers/call_recording.py:322` does not call `emit_call_timeline_event`. The function `emit_call_timeline_event` is fully implemented in `app/services/messaging_call_timeline.py:45` and handles the `call.recording_available` event type — however, the `_preview_for_event` function at `messaging_call_timeline.py:21-42` does not yet include a case for `call.recording_available`, which means calling it today would return the generic fallback `"Call event: ready"`. The fix therefore requires changes to both files.
- **Additional note**: The CALL-009 gaps doc (`docs/tickets/gaps/CALL-009.md`) cites a self-consent guard as missing (`app/routers/call_recording.py:183`). In the current code, the guard is **already present** at lines 210-214 (`if recording.initiated_by == user_id: raise HTTPException(400, ...)`). That is a separate gap that has been resolved in the code and is not the subject of GAP-0145.
- **Related tickets**: CALL-009 parent, CALL-007 (call.missed fanout — same pattern), GAP-0142.

## 2. Current-State Investigation (root cause)

### 2.1 `complete_recording_upload` — no timeline event

`app/routers/call_recording.py:322-393` (the endpoint responsible for the fix location):

```python
@router.post("/messages/calls/{call_id}/recording/upload/complete", ...)
async def complete_recording_upload(call_id, body, request, user_id):
    ...
    updated = complete_upload(
        recording.recording_id,
        s3_key=s3_key,
        s3_bucket=bucket,
        file_size_bytes=recording.file_size_bytes or 0,
        duration_seconds=body.duration_seconds,
        mime_type=recording.mime_type,
    )

    download_url = None
    download_expires_at = None
    if updated and updated.status == "ready":
        download_url, download_expires_at = _make_download_url(updated)

    return RecordingUploadCompleteOut(
        recording_id=updated.recording_id if updated else body.recording_id,
        status=updated.status if updated else "failed",
        download_url=download_url,
        download_expires_at=download_expires_at,
    )
```

After `complete_upload` succeeds and `updated.status == "ready"`, the function generates a download URL and returns. There is no call to `emit_call_timeline_event` or `fanout_event_to_conversation`.

### 2.2 `emit_call_timeline_event` is fully operational

`app/services/messaging_call_timeline.py:45-126`: The function writes a system message to the Messages table and updates the conversation's `last_message_preview`. It is already used by `timeout_call`, `end_call`, `decline_invite`, and other lifecycle transitions. It accepts an `extra_payload` dict for additional metadata (e.g., `recording_id`, `download_url`).

### 2.3 `_preview_for_event` — missing case

`app/services/messaging_call_timeline.py:21-42`:

```python
def _preview_for_event(*, event_type: str, call_state: str, reason: Optional[str]) -> str:
    if event_type == "call.invite":    return "Started a call"
    if event_type == "call.accept":   return "Call accepted"
    if event_type == "call.decline":  return ...
    if event_type == "call.end":      return ...
    if event_type == "call.missed":   return "Missed call"
    if event_type == "call.voicemail_start":    return "Recording a voicemail"
    if event_type == "call.voicemail_complete": return "Left a voicemail"
    if call_state == "voicemail" or event_type == "voicemail": return "Voicemail"
    return f"Call event: {call_state}"  # fallback
```

There is no `call.recording_available` case. Without adding it, calling `emit_call_timeline_event(event_type="call.recording_available", call_state="ready", ...)` would produce the generic fallback `"Call event: ready"` — a confusing message that would not hint to users that a recording is available.

### 2.4 `call_state` value for recording

When `emit_call_timeline_event` is called from `complete_recording_upload`, the call itself is already in `ended` state (recordings are uploaded after the call ends). The appropriate `call_state` argument is `"ready"` (the recording status), not the call state, since the timeline event is about the recording — not a call phase transition. This is a minor misuse of the field but consistent with the existing `voicemail_complete` pattern. Alternatively, pass `call_state="ended"` and rely solely on `event_type` for preview text.

### 2.5 DDB idempotency

`emit_call_timeline_event` at `messaging_call_timeline.py:84`:

```python
tbl_msgs.put_item(Item=item, ConditionExpression="attribute_not_exists(message_id)")
```

The `message_id` is deterministic: `f"sys_call_{call_id}_{event_type.replace('.', '_')}_{ts}"`. If `complete_recording_upload` is retried (idempotent client re-POST), the second `put_item` silently no-ops. This is correct behaviour.

## 3. Impact / Exploit / Blast Radius

**Discoverability**: Both participants in a recorded call — typically a support agent and a customer, or two users who mutually consented to record — have no in-chat indication that the recording is available for download. They must know to check a dedicated recordings panel or call a separate REST endpoint. For infrequent users, this is a significant usability gap.

**Notification gap**: The SSE fanout (described in §4.1) is also missing from the current endpoint, meaning even the SSE `call.recording_available` event that the frontend would need to refresh the recordings UI is never sent.

**Compliance surface**: In regulated industries (legal, healthcare, finance), call recordings are material records. Users who do not know a recording exists cannot exercise their right to request deletion or access. The gap creates a compliance audit risk.

**No security impact**: This is a missing positive notification, not an information-disclosure or access-control gap. The recording itself is correctly access-controlled (participant-only download).

**Blast radius**: All completed call recordings where mutual consent was obtained. Scope is limited to the `call_recording` feature gated behind `S.call_recording_enabled`. No financial or data-integrity impact beyond discoverability.

## 4. Fix Design (code-level)

### 4.1 `app/services/messaging_call_timeline.py` — add preview case

Add a new case to `_preview_for_event` at `messaging_call_timeline.py:21-42`:

```python
def _preview_for_event(*, event_type: str, call_state: str, reason: Optional[str]) -> str:
    if event_type == "call.invite":              return "Started a call"
    if event_type == "call.accept":             return "Call accepted"
    if event_type == "call.decline":
        if reason == "busy":                    return "Call unavailable (busy)"
        return "Call declined"
    if event_type == "call.end":
        if reason:                              return f"Call ended ({reason})"
        return "Call ended"
    if event_type == "call.missed":             return "Missed call"
    if event_type == "call.voicemail_start":    return "Recording a voicemail"
    if event_type == "call.voicemail_complete": return "Left a voicemail"
    if event_type == "call.recording_available": return "Call recording available"  # new
    if call_state == "voicemail" or event_type == "voicemail": return "Voicemail"
    return f"Call event: {call_state}"
```

### 4.2 `app/routers/call_recording.py` — call `emit_call_timeline_event` and fanout

In `complete_recording_upload` at approximately line 385, immediately after `download_url` is resolved:

```python
if updated and updated.status == "ready":
    download_url, download_expires_at = _make_download_url(updated)

    # GAP-0145: insert timeline system message so participants see the recording
    try:
        from app.services.messaging_call_timeline import emit_call_timeline_event
        emit_call_timeline_event(
            call_id=updated.call_id,
            conversation_id=updated.conversation_id,
            actor_user_id=user_id,
            event_type="call.recording_available",
            call_state="ready",
            extra_payload={
                "recording_id": updated.recording_id,
                "duration_seconds": updated.duration_seconds,
                "initiated_by": updated.initiated_by,
            },
        )
    except Exception:
        # Timeline event is best-effort; do not fail the upload completion
        import logging
        logging.getLogger(__name__).warning(
            "call_recording_timeline_event_failed recording_id=%s",
            updated.recording_id,
        )

    # GAP-0145: SSE fanout so both peers refresh the recordings UI immediately
    try:
        from app.routers.messaging import fanout_event_to_conversation
        fanout_event_to_conversation(
            conversation_id=updated.conversation_id,
            sender_id=user_id,
            event_type="call.recording_available",
            payload={
                "call_id": updated.call_id,
                "recording_id": updated.recording_id,
                "duration_seconds": updated.duration_seconds,
                "download_url": download_url,
            },
            respect_mute=False,
        )
    except Exception:
        import logging
        logging.getLogger(__name__).warning(
            "call_recording_fanout_failed recording_id=%s",
            updated.recording_id,
        )
```

Both calls are wrapped in `try/except` to ensure that a failure in timeline or fanout does not prevent the upload completion response from reaching the client. The recording itself is already persisted by `complete_upload`.

### 4.3 Frontend SSE handler (CALL-009 follow-up)

The frontend's call-event SSE handler in `ConversationView.tsx:852-891` does not currently handle `call.recording_available`. As a companion change (same PR):

```typescript
} else if (eventType === "call.recording_available") {
    // Invalidate the recordings query so the UI refreshes
    queryClient.invalidateQueries({ queryKey: ["recordings", convoId] });
    toast.info("Call recording is now available.");
}
```

This is not strictly required by GAP-0145 (which focuses on the system message), but it completes the UX loop: the recording is discoverable both as a conversation timeline entry and via a live toast notification.

### 4.4 Dev/prod parity (SECOPS-007)

`emit_call_timeline_event` writes to DynamoDB via `_messages_table()` which uses the `DDB_MESSAGES` env var — pointing to DynamoDB Local (port 8001) in dev and real DynamoDB in prod. The same code path executes in both environments. No dev-mode short-circuit is needed or acceptable.

The `_make_download_url` helper at `call_recording.py:555-576` already branches on `S.dev_mode` for S3 URL generation — that branch is not affected by the timeline fix.

### 4.5 Alternatives considered

- **Push-notification only (no system message)**: Push notifications are opt-in and may not be available in the web client. Rejected in favour of the more reliable in-conversation system message.
- **Write the recording_id into the `call.end` system message**: The `call.end` event fires before the upload is complete (the call ends, then the client uploads). At the time of `call.end`, no recording ID is available. Rejected.
- **Return the download URL in the `complete_recording_upload` response and let the frontend show a toast**: Already done (download_url is in the response). This does not help the remote peer (who was not the uploader) discover the recording. Rejected as the sole mechanism.

### 5.4 Observability

- Counter: `call_recording_available_events_emitted_total`. Alert if `recordings_completed` (DDB state changes to `ready`) exceeds this counter by more than a few percent — indicates timeline emission is silently failing.

### 5.5 Rollout

- **Effort**: S (1-2 hours — three focused changes: preview text, timeline call, fanout call)
- **Risk**: Low. Both the timeline emit and the fanout are wrapped in `try/except`; any failure in those paths does not affect the primary recording completion response. The feature is already gated behind `S.call_recording_enabled`.
- **Rollback**: Remove the `emit_call_timeline_event` and `fanout_event_to_conversation` calls from `complete_recording_upload`. System messages and SSE notifications for recordings stop appearing; all other recording functionality is unaffected.
- **Sequencing**: Can ship independently. No dependency on other GAPs. Coordinate with any CALL-009 follow-up work (stale `uploading` cleanup, per-user GSI) to land in the same release.
