# GAP-0375: Download Rate Limiting Not Enforced — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real file:line. No investigation doc exists for this ticket.

## 1. Summary & Classification

**Plain-English statement**: `app/core/settings.py:1444` defines
`video_download_rate_limit_per_10m: int = 5` (configurable via
`VIDEO_DOWNLOAD_RATE_LIMIT_PER_10M`), but the download endpoint at
`app/routers/video_listing.py:772-824` never reads this setting, never writes or
checks a rate-limit counter, and never returns HTTP 429. Any authenticated user can
call `GET /{video_id}/download` in a tight loop, minting an unlimited number of
presigned download URLs. The spec (§1.4) requires a limit of 5 URL mints per 10 minutes
per user per video to prevent presigned URL farming and unauthorized redistribution.

- **Severity**: HIGH
- **Source ticket**: VOD-012
- **Status**: Open
- **Owning area**: Backend / `app/routers/video_listing.py` / VOD download
- **Verdict**: **Confirmed** — `app/routers/video_listing.py:772-824` contains no rate-
  limit logic. `video_download_rate_limit_per_10m` at settings line 1444 is defined but
  never referenced anywhere in the application except in its own definition (confirmed
  by `grep -rn "video_download_rate_limit" app/` returning only the settings line).
- **One-line impact**: Unlimited presigned URL generation per user per video enables
  download URL farming and large-scale piracy with no throttle or detection.
- **Related tickets**: VOD-012 (source), GAP-0374 (DRM key revocation — complementary
  post-compromise control).

### The orphaned setting

`grep -rn "video_download_rate_limit" app/` returns only this definition. The setting is

### `increment_download_count` is a metric only

`app/services/video_metadata_store.increment_download_count` increments a DynamoDB
attribute on the video metadata record. It does not count per-user, per-window
requests; it is a total cumulative counter for display purposes only and provides no
rate-limit functionality.

### Why the window-based counter needs DynamoDB

The dev stack uses DynamoDB Local, not Redis. All existing rate-limiting patterns in
the codebase (e.g., `filemgr_s3_mounts_download_rate_per_minute`) use DynamoDB counters.
For consistent dev/prod parity per SECOPS-007, the rate-limit counter must also use
DynamoDB, not Redis. The implementation uses a DynamoDB item with a TTL attribute set
to `now + 600` seconds (10 minutes); the counter is stored under key
`USER#{user_sub}#VIDEO#{video_id}#DOWNLOAD_RATE` in an existing table (or a dedicated
`VideoDownloadRateLimit` table), and a DynamoDB conditional update atomically increments
and checks it.

## 3. Impact / Exploit / Blast Radius

**Concrete exploit — URL farming**:

1. Attacker purchases a $1 PPV download entitlement for a premium video.
2. In a loop, the attacker calls `GET /v1/ui/videos/{video_id}/download` with their
   session cookie.
3. Each call returns a fresh presigned S3 URL with `video_download_url_ttl_seconds`
   (default 3600 s = 1 hour) validity.
4. The attacker distributes the presigned URLs to piracy groups. Each URL, once minted,
   is valid for 1 hour regardless of the account's subscription status.
5. With no rate limit, the attacker can mint thousands of URLs per second. Each URL can
   be used by a different downloader before expiry.

**Financial impact**: Each distributed URL enables one free download of purchased or
subscriber-gated content. A premium creator selling a $50 course can have its entire
library URL-farmed by a single attacker who paid $1 for one download entitlement.

**Storage / cost impact**: Each S3 presigned URL call triggers an S3 GET request
charged to the platform's AWS account. At scale, a farming attack generates direct
cloud egress costs.

**Detection gap**: `increment_download_count` only tracks the total across all users
and does not record who minted how many URLs within what window, making post-hoc
forensics difficult.

**Blast radius**: All videos with `allow_download=True`. The feature flag
`VIDEO_DOWNLOAD_ENABLED` can disable downloads platform-wide as an emergency brake, but
that also disables legitimate downloads.

## 4. Fix Design (Code-Level)

### Strategy: DynamoDB atomic counter with TTL

Use a DynamoDB `UpdateItem` with `ADD` + `ConditionExpression` to atomically increment
a per-user-per-video counter and reject requests once the limit is reached. The counter
item carries a DynamoDB TTL attribute so it auto-expires after the 10-minute window
without a background cleanup task.

### New service function: `app/services/video_download_ratelimit.py`

```python
"""Per-user per-video download URL rate limiting (GAP-0375 / VOD-012 §1.4).

Uses a DynamoDB item with a TTL of 10 minutes. The counter is incremented
atomically; if it exceeds the configured limit, RateLimitExceeded is raised.
"""
from __future__ import annotations

from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts


class RateLimitExceeded(Exception):
    """Raised when the per-user-per-video download rate limit is exceeded."""

    def __init__(self, limit: int, window_seconds: int = 600):
        self.limit = limit
        self.window_seconds = window_seconds
        super().__init__(
            f"Download rate limit of {limit} per {window_seconds}s exceeded"
        )


_WINDOW_SECONDS = 600  # 10 minutes


def check_and_increment_download_rate(
    *,
    user_sub: str,
    video_id: str,
    limit: int | None = None,
) -> int:
    """Atomically increment the download counter; raise if limit exceeded.

    Args:
        user_sub: Authenticated user's sub (PK component).
        video_id: Video being downloaded (SK component).
        limit: Override for testing; defaults to S.video_download_rate_limit_per_10m.

    Returns:
        The new counter value after this request.

    Raises:
        RateLimitExceeded: if the counter already equals or exceeds the limit.
    """
    effective_limit = limit if limit is not None else int(
        getattr(S, "video_download_rate_limit_per_10m", 5) or 5
    )
    if effective_limit <= 0:
        # Rate limiting disabled (set to 0 in config)
        return 0

    now = now_ts()
    expires_at = now + _WINDOW_SECONDS
    pk = f"DL_RATE#{user_sub}#{video_id}"

    try:
        result = T.video_download_rate.update_item(
            Key={"pk": pk},
            UpdateExpression=(
                "SET #cnt = if_not_exists(#cnt, :zero) + :one, "
                "#exp = if_not_exists(#exp, :exp_val)"
            ),
            ConditionExpression="#cnt < :limit OR attribute_not_exists(#cnt)",
            ExpressionAttributeNames={
                "#cnt": "count",
                "#exp": "expires_at",
            },
            ExpressionAttributeValues={
                ":zero": 0,
                ":one": 1,
                ":limit": effective_limit,
                ":exp_val": expires_at,
            },
            ReturnValues="UPDATED_NEW",
        )
        return int(result["Attributes"]["count"])
    except T.video_download_rate.meta.client.exceptions.ConditionalCheckFailedException:
        raise RateLimitExceeded(limit=effective_limit)
```

### Owner exemption

The spec (§1.4) does not exempt content owners, and owners could also farm URLs for
redistribution. Apply the rate limit uniformly to all callers including `is_owner`.

### Dev/Prod parity (SECOPS-007)

The counter uses DynamoDB Local in dev (same client factory as all other tables via
`app/core/tables.py`). In production it uses real DynamoDB with TTL enabled. No
`if dev:` branching. The `video_download_rate_limit_per_10m` setting (already present
in `settings.py`) is the single source of truth in both environments. Set to a high
value (e.g., 1000) in `.env.local.example` so E2E tests are not throttled.

### Regression test — fails before / passes after

**pytest offline** (`tests/test_video_download_ratelimit.py`):

```python
"""GAP-0375: Download rate limiting regression test.

BEFORE fix: calling the download endpoint > 5 times returns 200 every time.
AFTER fix: the 6th call within 10 minutes returns 429.
"""
import os
os.environ.setdefault("UI_ACCESS_TOKEN_SECRET", "test-secret")
os.environ.setdefault("DEV_MODE", "1")
os.environ.setdefault("VIDEO_DOWNLOAD_RATE_LIMIT_PER_10M", "3")
import pytest
from unittest.mock import patch, MagicMock

from app.services.video_download_ratelimit import (
    check_and_increment_download_rate,
    RateLimitExceeded,
)


class TestRateLimitService:
    def test_first_n_calls_succeed(self):
        """First N calls within the window must not raise."""
        for i in range(3):
            result = check_and_increment_download_rate(
                user_sub="user_a", video_id="vid_x", limit=3
            )
            assert result == i + 1

    def test_exceeding_limit_raises(self):
        """Call N+1 must raise RateLimitExceeded."""
        for _ in range(3):
            check_and_increment_download_rate(
                user_sub="user_b", video_id="vid_y", limit=3
            )
        with pytest.raises(RateLimitExceeded) as exc_info:
            check_and_increment_download_rate(
                user_sub="user_b", video_id="vid_y", limit=3
            )
        assert exc_info.value.limit == 3

    def test_different_users_independent(self):
        """Rate limit is per-user, not global."""
        for _ in range(3):
            check_and_increment_download_rate(
                user_sub="user_c", video_id="vid_z", limit=3
            )
        # user_d has independent counter
        result = check_and_increment_download_rate(
            user_sub="user_d", video_id="vid_z", limit=3
        )
        assert result == 1

    def test_zero_limit_disables_ratelimiting(self):
        """limit=0 means disabled; never raises."""
        for _ in range(100):
            check_and_increment_download_rate(
                user_sub="user_e", video_id="vid_w", limit=0
            )  # must not raise
```

### Rollout

- **Effort**: M (2 engineer-days: service, table, endpoint wiring, tests, frontend 429
  handling)
- **Risk**: Low. The change adds a DynamoDB read+write before minting the presigned URL.
  P99 latency impact: ~2-3 ms in production DynamoDB. The DDB call is not on the hot
  streaming path (not per-segment; only on URL mint). Feature flag via
  `VIDEO_DOWNLOAD_RATE_LIMIT_PER_10M=0` to disable.
- **Sequencing**: Can be deployed independently. Not blocked by GAP-0372, GAP-0373, or
  GAP-0374. Recommend deploying before major platform launches or creator promotions.
- **Rollback**: Set `VIDEO_DOWNLOAD_RATE_LIMIT_PER_10M=0` to disable enforcement
  immediately without code rollback. Full code rollback: remove the
  `check_and_increment_download_rate` call from the endpoint.
