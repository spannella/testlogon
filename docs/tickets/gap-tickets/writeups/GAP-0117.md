# GAP-0117: SEC-010 — Chat Send Endpoint Missing `check_viewer_access` — Remediation Write-up

> ~5 pages. Fix-oriented. Real code verified against the codebase; cite `file:line`.

## 1. Summary & Classification

**Gap**: The broadcast live-chat send endpoint (`POST /broadcast/sessions/{session_id}/chat`) does not call `check_viewer_access` before writing a message. Any authenticated user can post chat messages to a `private` broadcast session they are not authorised to view, and those messages will appear in the chat stream for all legitimate participants.

**Severity**: HIGH
**Source ticket**: BCAST-005
**Status**: Open
**Owning area**: `app/routers/broadcast.py` → `send_chat_message_route`
**Related tickets**: GAP-0116 (SSE stream missing the same guard), GAP-0118 (locked message paywall bypass), BCAST-011 (Go-Private feature)

**Verdict**: Claim confirmed. `send_chat_message_route` at `app/routers/broadcast.py:1553` checks only `session.status == "live"` before writing the message; it never invokes `check_viewer_access`.

**One-line impact**: An excluded user can inject arbitrary chat messages into a private broadcast, polluting the creator's moderated chat room and potentially impersonating legitimate viewers.


## 2. Current-State Investigation (root cause)

### Route handler (as-is)

`app/routers/broadcast.py:1548–1593`:

```python
@router.post(
    "/sessions/{session_id}/chat",
    response_model=BroadcastChatMessageOut,
    status_code=status.HTTP_201_CREATED,
)
def send_chat_message_route(session_id: str, body: BroadcastChatSendIn, ctx: dict = Depends(_ctx)):
    """Send a chat message to a live broadcast session."""
    session = get_session(session_id)
    if session.status != "live":
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail={"code": "BROADCAST_NOT_LIVE", ...},
        )

    user_id = ctx["user_sub"]

    # Broadcaster-only features (BCAST-015 Phase C + D)
    if body.expires_in_seconds is not None or body.lock_price_cents is not None:
        if user_id != session.created_by:
            raise HTTPException(403, ...)

    # ... display name resolution ...
    result = _store_send_chat(...)
    return BroadcastChatMessageOut(...)
```

After the `session.status` check the function proceeds immediately to service layer logic. There is no call to `check_viewer_access` anywhere in this function, and `session.broadcast_privacy_visibility` is never consulted.

### The ticket's fix suggestion

The ticket says: *"add `check_viewer_access` call after `session.status` check in `send_chat_message_route`"*. This is correct and sufficient. The broadcaster-only feature check that follows can remain in place — it is independent of the privacy gate.

### Contrast with guarded routes

`viewer_join_route` (`app/routers/broadcast.py:568`) shows the correct pattern:

```python
session = get_session(session_id)
if session.created_by != ctx["user_sub"]:
    from app.services.geo_check import check_geo_access
    ...
from app.services.broadcast_privacy import check_viewer_access
check_viewer_access(
    session_id,
    ctx["user_sub"],
    creator_id=session.created_by,
    visibility=session.broadcast_privacy_visibility,
    invite_token=invite_token,
)
```

The chat send endpoint should replicate this pattern. Since chat participation implicitly requires viewing the stream, the same access level should apply.

### Why the creator is exempt

`check_viewer_access` (`app/services/broadcast_privacy.py:241`) returns immediately when `viewer_id == creator_id`, so the broadcaster's own ability to send messages is unaffected.

### Interaction with mute enforcement

`_store_send_chat` (`app/services/broadcast_chat_store.py:157`) calls `_enforce_chat_mute` before writing. The mute check must remain — it fires after the privacy gate in the new ordering. Correct sequence:

1. `check_viewer_access` — exclude non-participants.
2. Broadcaster-only feature check — gate Phase C/D fields.
3. `_store_send_chat` → `_enforce_chat_mute` + rate-limit.

This order ensures excluded users see a 403 rather than a mute-specific error, which would reveal information about the session's chat state.

### Relationship to GAP-0116 (SSE stream gap)

GAP-0116 and GAP-0117 are sibling issues: one covers the read path (SSE stream subscription), the other covers the write path (message send). Both are in `app/routers/broadcast.py` and both require exactly the same one-line `check_viewer_access` call inserted at the top of the respective handler. They should be fixed in the same commit to avoid a window where one path is guarded and the other is not.

### Broadcaster-only enforcement is not a substitute

One might ask whether the broadcaster-only check already present (line 1565) provides equivalent protection. It does not. The broadcaster-only check gates Phase C/D fields (`expires_in_seconds`, `lock_price_cents`) on `user_id == session.created_by`. It does not prevent an unauthorised viewer from sending a plain text message. The two checks are orthogonal: the privacy gate is about session membership; the broadcaster-only gate is about feature capability within a session.

### SSE fan-out amplification

The `send_chat_message` function calls `broadcast_sse_publish(session_id, ...)` immediately after writing the DynamoDB row (line 213 of `broadcast_chat_store.py`). If an excluded user can write messages, those messages are instantly broadcast to all SSE subscribers via the in-memory queue. The privacy gate at the send endpoint is therefore a double protection: it prevents both the DynamoDB write and the SSE fan-out of the intruder's message.


## 3. Impact / Exploit / Blast Radius

### Exploit walkthrough

1. Bob is not on the allowlist for Alice's private session `sess_abc`.
2. Bob sends `POST /broadcast/sessions/sess_abc/chat` with body `{"text": "spam"}`.
3. The only check is `session.status == "live"` — which passes.
4. `send_chat_message` writes the row to DynamoDB and calls `broadcast_sse_publish`, pushing Bob's message to every SSE subscriber — including legitimate viewers Carol and Dave.
5. Bob can flood the chat, post abusive content, or impersonate another display name (display name is resolved from the profile table, so Bob cannot spoof an arbitrary name, but he can post under his own name in a room he should be excluded from).

### Escalation path — rate limit bypass

The broadcaster can mute individual users, but mute state is keyed on `session_id#user_id`. An excluded user who should never have had access cannot be muted in advance. The broadcaster must discover the intrusion, identify the user ID, then post a mute — a purely reactive defence.

Even the mute-based reactive defence is limited: the rate limit (`_enforce_chat_rate_limit`) is in-memory (`_CHAT_RATE_BUCKETS`, line 21 of `broadcast_chat_store.py`) and is keyed per-worker. In a multi-worker configuration (not used in dev but possible in production at high load), each worker maintains an independent bucket. An attacker can spray messages across workers up to the rate limit per worker, amplifying the effective message rate by the worker count.

### Information disclosure secondary effect

Every message written by an excluded user generates a DynamoDB write and an SSE `broadcast_sse_publish` event. The published event includes `sender_id` and `sender_display_name`. A platform operator examining SSE logs or DynamoDB records would see the excluded user's identity in the chat history, potentially creating a confusing support investigation: the user's ID appears in records for a session they were never granted access to.

### Worst case

- For subscription-gated or adult-content private sessions, allowing unsolicited participation violates the user contract and may breach payment processor terms.
- If a banned user was previously removed from the allowlist, they can continue to interact with the session — defeating the allowlist removal mechanism.
- Denial-of-service: an excluded attacker can drive up DynamoDB write cost and SSE fan-out load without any throttle beyond the in-memory rate limiter (which resets on worker restart).

### Blast radius

All sessions with `broadcast_privacy_visibility == "private"`. Public and unlisted sessions are unaffected.


## 4. Fix Design (code-level)

### Change — Insert `check_viewer_access` call

**File**: `app/routers/broadcast.py`, function `send_chat_message_route` (line ~1553).

After the `session.status` check and before the broadcaster-only feature gate, insert:

```python
def send_chat_message_route(session_id: str, body: BroadcastChatSendIn, ctx: dict = Depends(_ctx)):
    """Send a chat message to a live broadcast session."""
    session = get_session(session_id)
    if session.status != "live":
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail={"code": "BROADCAST_NOT_LIVE", "message": "Chat is only available while the broadcast is live"},
        )

    # Go-Private access gating (BCAST-011 / GAP-0117)
    from app.services.broadcast_privacy import check_viewer_access
    check_viewer_access(
        session_id,
        ctx["user_sub"],
        creator_id=session.created_by,
        visibility=session.broadcast_privacy_visibility,
    )

    user_id = ctx["user_sub"]
    # Broadcaster-only features (BCAST-015 Phase C + D)
    ...
```

No `invite_token` parameter is needed here. Chat send is a secondary action; the token is consumed at join time (`viewer_join_route`). By the time a viewer is sending messages they are already enrolled in the allowlist.

### Dev/Prod parity (SECOPS-007)

`check_viewer_access` reads from `T.broadcast_allowlist` (DynamoDB). In dev mode the table is served by DynamoDB Local on port 8001. In production it points to AWS DynamoDB. The `T.*` handle is wired identically in both environments via `app/core/tables.py`. No mocking or branching is involved. The fix is fully environment-neutral.

### Backward compatibility

- No schema changes.
- No migration.
- For public/unlisted sessions `check_viewer_access` returns immediately — zero behaviour change.
- For private sessions, only users on the allowlist or the creator can post. This is the intended behaviour per BCAST-011.
- Existing integration tests that test public-session chat remain unaffected.

### Alternatives considered

**Option A — Check at the service layer (`send_chat_message`)**: Moving the check into `_store_send_chat` would gate the DynamoDB write but would require passing `session.broadcast_privacy_visibility` and `creator_id` into a function that currently knows nothing about session-level privacy state. This would couple the chat storage service to the privacy service, violating the existing separation of concerns. The router is the correct place for cross-cutting access checks.

**Option B — Validate allowlist membership at register-viewer time and cache**: Caching allowlist membership in the session would reduce DynamoDB reads but introduces a staleness window where a removed viewer could still post. The current per-request DynamoDB read is a single `GetItem` (O(1)) and is acceptable given the infrequency of chat send operations relative to SSE poll frequency.


## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Extend `tests/test_broadcast_chat_privacy.py`:

```python
def test_send_chat_blocked_for_excluded_viewer():
    """GAP-0117: excluded viewer must receive 403 on chat send."""
    resp = client.post(
        f"/broadcast/sessions/{SESSION}/chat",
        json={"text": "hello from outside"},
        headers=_inject_session(BOB),
    )
    # Before fix: 201 Created (message is written).
    # After fix:  403 Forbidden with BROADCAST_PRIVATE_ACCESS_DENIED.
    assert resp.status_code == 403
    assert resp.json()["detail"]["code"] == "BROADCAST_PRIVATE_ACCESS_DENIED"

def test_send_chat_allowed_for_creator():
    resp = client.post(
        f"/broadcast/sessions/{SESSION}/chat",
        json={"text": "broadcaster message"},
        headers=_inject_session(ALICE),
    )
    assert resp.status_code == 201

def test_send_chat_allowed_for_allowlisted_viewer(mock_ddb):
    from app.services.broadcast_privacy import add_to_allowlist
    add_to_allowlist(SESSION, BOB, added_by=ALICE)
    resp = client.post(
        f"/broadcast/sessions/{SESSION}/chat",
        json={"text": "viewer message"},
        headers=_inject_session(BOB),
    )
    assert resp.status_code == 201

def test_send_chat_mute_still_enforced_for_allowlisted_viewer(mock_ddb):
    """Mute check runs after the privacy gate, not before."""
    from app.services.broadcast_privacy import add_to_allowlist
    from app.services.broadcast_chat_store import set_mute
    add_to_allowlist(SESSION, BOB, added_by=ALICE)
    set_mute(SESSION, BOB, duration_seconds=300, actor=ALICE)
    resp = client.post(
        f"/broadcast/sessions/{SESSION}/chat",
        json={"text": "muted message"},
        headers=_inject_session(BOB),
    )
    assert resp.status_code == 403
    assert resp.json()["detail"]["code"] == "BROADCAST_CHAT_MUTED"
```

**Fails before the fix**: `test_send_chat_blocked_for_excluded_viewer` gets 201 instead of 403.
**Passes after the fix**: all four assertions hold.

### Observability

The `raise HTTPException` in `check_viewer_access` is the single failure path. Add a structured log line at that site:

```python
logger.warning(
    "broadcast.privacy.chat_send_denied session=%s viewer=%s visibility=%s",
    session_id, viewer_id, visibility,
)
```

An alerting rule on `broadcast.privacy.chat_send_denied` with a threshold of >10 events per minute per session can surface active abuse.

### Rollout

- **Effort**: S (< 1 day, largely shared with GAP-0116 and GAP-0118 work).
- **Risk**: Low. Behaviour change is restricted to private sessions. Allowlisted viewers are unaffected.
- **Sequence**: Bundle with GAP-0116 and GAP-0118 into a single "BCAST-005 privacy hardening" release.
- **Rollback**: One-line revert of the inserted block. No state to undo.

### Audit trail consideration

Currently no audit record is written when a chat message is sent. Adding a structured log line after the `check_viewer_access` call (both on success and on denial) provides a lightweight audit trail:

```python
logger.info(
    "broadcast.chat.send session=%s sender=%s visibility=%s allowed=%s",
    session_id, ctx["user_sub"], session.broadcast_privacy_visibility, True,
)
```

For the denial path the exception in `check_viewer_access` will propagate before this line fires; the denial is logged inside `check_viewer_access` itself at `app/services/broadcast_privacy.py:248`. This is sufficient for the audit requirement without adding a secondary log call.

### Idempotency note

If a client retries a chat send (network timeout), the retry will also pass through `check_viewer_access`. Since the function is a pure read (no side-effects for `public`/`unlisted`, and allowlist enrollment happens at join time), retries are safe. There is no risk of the privacy gate being triggered differently on a second attempt.

### GDPR and data minimisation note

Chat messages stored in DynamoDB for private sessions that were accessible to excluded users constitute unintended data processing. Under GDPR Article 5(1)(c) (data minimisation), the system must not collect data from individuals who did not consent to participate. Any messages written by excluded users before the fix is deployed should be reviewed and potentially purged from the `broadcast_chat_messages` table. The `sender_id` field on each item enables identification of messages from users not on the allowlist. A targeted cleanup script can scan the table with `FilterExpression=Attr("session_id").eq(session_id)` and compare each `sender_id` against the allowlist. This is a compliance follow-on task outside the scope of the code fix itself.
