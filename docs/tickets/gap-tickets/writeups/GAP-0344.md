# GAP-0344: No Message Idempotency — Remediation Write-up

## 1. Summary & Classification

**Gap**: The send-text-message endpoint (`POST /ui/messaging/conversations/{id}/messages`)
in `app/routers/messaging.py` has no client-side idempotency key. When a mobile or PWA
client retries a failed POST (network timeout, 5xx, or offline-queue replay), the backend
creates a duplicate message. The frontend model `SendTextMessageReq`
(`frontend/src/api/types.ts:1249–1264`) similarly has no `client_request_id` field.
PWA offline queues (PWA-004) rely on stable action IDs; without idempotency, every
offline-queue replay during reconnection produces a duplicate in the conversation.

- **Severity**: HIGH
- **Source ticket**: PWA-004
- **Owning area**: Messaging / Backend + Frontend
- **Status**: Open

**Claim accuracy**: Confirmed. `SendTextMessageIn` at
`app/routers/messaging.py:1844–1879` has no `client_request_id` field. `send_text_message`
at line 7852 generates a new `mid = "m_" + new_id()` unconditionally on every call with
no duplicate-suppression check. `frontend/src/api/types.ts:1249–1264` confirms the
frontend type has no idempotency field. Note: other endpoints in `messaging.py` (mass
messages, helpdesk claim) do have idempotency logic; the single-message send path does not.

**One-line impact**: Every network retry by a mobile or PWA client produces a duplicate
message, degrading conversation quality and creating phantom message content.

**Related tickets**: PWA-004, GAP-0081 (double-write claim race)

## 2. Current-State Investigation (Root Cause)

### 2.1 The send-text-message path

`SendTextMessageIn` (`app/routers/messaging.py:1844`):

```python
class SendTextMessageIn(BaseModel):
    text: Optional[str] = Field(default=None, min_length=1, max_length=MESSAGE_TEXT_MAX_CHARS)
    body: Optional[str] = None
    reply_to_message_id: Optional[str] = None
    ...
    lock_price_cents: Optional[int] = ...
    lock_description: Optional[str] = ...
    # No client_request_id field
```

`send_text_message` (`app/routers/messaging.py:7852`):
```python
def send_text_message(conversation_id, inp, req=None, user_id=...):
    ...
    mid = "m_" + new_id()   # line 7907: always a fresh UUID, no idempotency check
    item = {
        "conversation_id": conversation_id,
        "message_id": mid,
        ...
    }
```

`new_id()` is defined at the top of the file as `uuid4().hex`, so every call produces a
unique `message_id`. There is no lookup of a prior write by `client_request_id` before
inserting.

### 2.2 Idempotency already works for other send paths

`app/routers/messaging.py:3156` defines `_lottery_dedupe_message_id` which hashes
`sender_id | conversation_id | idempotency_key` to produce a deterministic `message_id`.
The lottery-ticket send endpoint (`app/routers/messaging.py:12687`) reads an
`Idempotency-Key` header and uses this function. The helpdesk claim endpoint uses a
similar approach (`line 6509: _idempotent_success`). The pattern exists; it was simply
not applied to the main `send_text_message` path.

### 2.3 Frontend types

`frontend/src/api/types.ts:1249–1264`:
```typescript
export interface SendTextMessageReq {
  text?: string;
  encryption?: MessageEncryptionEnvelope;
  reply_to_message_id?: string;
  ...
  tip_amount_cents?: number;
  tip_payment_method_id?: string;
  // No client_request_id
}
```

The PWA-004 offline action queue stores actions with a stable client-generated `id`
(UUID). This id is available at send time but is never forwarded to the backend.

### 2.4 Dev vs. prod behaviour

The lack of idempotency manifests equally in dev and prod. In dev, retrying a `curl` or
test POST twice creates two messages. In prod, mobile clients on flaky connections routinely
retry 5xx or timeout responses, causing visible duplicate messages.

## 3. Impact / Exploit / Blast Radius

**User experience**: A user on a slow mobile connection sends a message. The POST times
out at the HTTP layer (backend processed it but the response was dropped). The PWA
offline queue replays the action. The backend creates a second message with a new UUID.
The user sees their message twice in the conversation view.

**Data integrity**: Tips attached to retried messages would be charged twice. The tip
billing path calls a stub payment processor in dev, but in prod would produce two billing
ledger entries and two payment processor charges.

**Encrypted messages**: An encrypted message uses a one-time IV. A retry with the same
`encryption` envelope (same IV and ciphertext) creates a second DynamoDB record. If a
different IV is used on retry (client regenerates), the recipient receives two distinct
ciphertexts for the same intended message.

**Scale**: Every user on mobile or PWA is affected whenever network conditions cause a
retry. High-volume conversations (helpdesk, group chats) amplify the problem.

## 4. Fix Design (Code-Level)

### 4.1 Add `client_request_id` to `SendTextMessageIn`

In `app/routers/messaging.py:1844`, add the field:

```python
class SendTextMessageIn(BaseModel):
    text: Optional[str] = Field(default=None, min_length=1, max_length=MESSAGE_TEXT_MAX_CHARS)
    body: Optional[str] = None
    ...
    lock_description: Optional[str] = Field(default=None, max_length=200)
    client_request_id: Optional[str] = Field(
        default=None,
        min_length=1,
        max_length=128,
        pattern=r"[A-Za-z0-9._:-]+",
        description="Client-generated idempotency key. Same key = deduplicated send.",
    )
```

The pattern `[A-Za-z0-9._:-]+` matches the same regex already enforced for the lottery
endpoint's `Idempotency-Key` header (`app/routers/messaging.py:12713`), ensuring
consistency.

### 4.2 Use deterministic `message_id` when `client_request_id` is provided

In `send_text_message`, replace the unconditional `mid = "m_" + new_id()` at line 7907
with:

```python
    if inp.client_request_id:
        # Deterministic message_id: same client_request_id always maps to the same
        # message_id for this sender/conversation pair, enabling safe retries.
        mid = _lottery_dedupe_message_id(
            sender_id=user_id,
            conversation_id=conversation_id,
            idempotency_key=inp.client_request_id,
        )
    else:
        mid = "m_" + new_id()
```

`_lottery_dedupe_message_id` (`messaging.py:3156`) already produces:
```python
def _lottery_dedupe_message_id(*, sender_id, conversation_id, idempotency_key):
    digest = hashlib.sha256(
        f"{sender_id}|{conversation_id}|{idempotency_key}".encode("utf-8")
    ).hexdigest()[:32]
    return f"m_{digest}"
```

### 4.3 Add a conditional-put guard in DynamoDB

Using a deterministic `message_id` as the DynamoDB sort key is necessary but not
sufficient. Two concurrent retries with the same `message_id` could both succeed if
the first write has not yet landed. Add a `ConditionExpression` to the DynamoDB
`put_item` call that creates the message:

```python
    try:
        T.messages.put_item(
            Item=item,
            ConditionExpression="attribute_not_exists(message_id)",
        )
    except ClientError as exc:
        if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
            # Message already written (idempotent retry) — return the existing message
            existing = T.messages.get_item(
                Key={"conversation_id": conversation_id, "message_id": mid}
            ).get("Item")
            if existing:
                return _message_out_from_item(existing)
            # Rare race: condition failed but item disappeared — treat as success
            raise HTTPException(409, "Duplicate message detected; please retry")
        raise
```

This makes the send operation idempotent at the storage layer: first write wins;
subsequent writes with the same `message_id` are silently reflected back.

### 4.4 Update the frontend type and send call

`frontend/src/api/types.ts:1249`:
```typescript
export interface SendTextMessageReq {
  text?: string;
  encryption?: MessageEncryptionEnvelope;
  ...
  tip_payment_method_id?: string;
  client_request_id?: string;  // NEW: stable per-action ID for idempotent retries
}
```

In the PWA offline queue's send action, pass the action's `id`:
```typescript
await sendTextMessage(conversationId, {
  text: action.payload.text,
  client_request_id: action.id,   // stable UUID from the offline queue
  ...action.payload,
});
```

### 4.5 Dev / Prod Parity (SECOPS-007)

The fix is pure DynamoDB and hashing logic. No AWS service boundary is crossed beyond
DynamoDB, which is mocked by DynamoDB Local in dev. The `ConditionExpression` on
`put_item` works identically in both environments. No feature flag is needed.

### 4.6 Backwards Compatibility

`client_request_id` is optional. Existing clients that do not send it continue to
receive fresh UUID-based `message_id`s and no idempotency guarantee (same behaviour as
today). Only clients that supply `client_request_id` get the deterministic path.

### 4.7 Alternatives Considered

- **Header-based idempotency key (like the lottery endpoint)**: Equally valid, but a
  request-body field is more naturally associated with offline queue replays where the
  same JSON body is retried. Header approach also requires frontend changes.
- **Server-side idempotency store (Redis / DDB TTL table)**: Heavier infrastructure.
  The hash-based deterministic `message_id` achieves the same result with zero extra
  storage, reusing the DDB `put_item` condition as the atomic gate.
- **Client-side deduplication only**: Not sufficient — the server must be the source
  of truth; client state can be lost on app restart.

## 5. Testing, Verification & Rollout

### 5.1 Pytest Regression Test (fails-before / passes-after)

Create `tests/test_message_idempotency.py`:

```python
"""Regression: duplicate POSTs with the same client_request_id must not create
two messages in the conversation."""
import pytest


def test_send_message_idempotent_retry(client, alice_session, bob_session, seed_dm):
    """Two identical send calls with the same client_request_id return the same
    message_id and only one message exists in the conversation."""
    conv_id = seed_dm["conversation_id"]
    payload = {
        "text": "Hello idempotent world",
        "client_request_id": "client-req-abc-123",
    }
    headers = alice_session["headers"]

    resp1 = client.post(
        f"/ui/messaging/conversations/{conv_id}/messages",
        json=payload,
        headers=headers,
    )
    assert resp1.status_code == 200
    mid1 = resp1.json()["message_id"]

    # Simulate network retry — same payload, same client_request_id
    resp2 = client.post(
        f"/ui/messaging/conversations/{conv_id}/messages",
        json=payload,
        headers=headers,
    )
    assert resp2.status_code == 200
    mid2 = resp2.json()["message_id"]

    # Must be the same message_id
    assert mid1 == mid2, "Retry produced a duplicate message"

    # Confirm only one message in conversation
    msgs_resp = client.get(
        f"/ui/messaging/conversations/{conv_id}/messages",
        headers=headers,
    )
    assert msgs_resp.status_code == 200
    matching = [m for m in msgs_resp.json() if m["text"] == "Hello idempotent world"]
    assert len(matching) == 1, f"Expected 1 message, got {len(matching)}"


def test_send_message_without_client_request_id_creates_distinct_messages(
    client, alice_session, seed_dm
):
    """Without client_request_id, two identical calls produce two distinct messages
    (existing behaviour preserved)."""
    conv_id = seed_dm["conversation_id"]
    payload = {"text": "Hello non-idempotent"}

    resp1 = client.post(
        f"/ui/messaging/conversations/{conv_id}/messages",
        json=payload,
        headers=alice_session["headers"],
    )
    resp2 = client.post(
        f"/ui/messaging/conversations/{conv_id}/messages",
        json=payload,
        headers=alice_session["headers"],
    )
    assert resp1.json()["message_id"] != resp2.json()["message_id"]
```

**Fails before fix**: `mid1 != mid2` because `send_text_message` generates a new UUID on
every call. The first assertion in `test_send_message_idempotent_retry` fails.

**Passes after fix**: The deterministic `mid` is computed from `sender_id |
conversation_id | client_request_id`, the second `put_item` hits the condition,
and the same `message_id` is returned.

### 5.4 Observability

- Add `logger.debug("idempotent_replay message_id=%s conv=%s", mid, conversation_id)`
  in the `ConditionalCheckFailedException` branch.
- Track metric `messaging.idempotent_replay` to monitor PWA retry frequency. High rates
  indicate network issues on the client side or backend latency causing spurious timeouts.
- On the frontend side, the PWA offline queue should log each send attempt and whether
  it was a replay (action already completed). This can be tracked with a `sent_at_count`
  on each action record; any action with `sent_at_count > 1` that received the same
  `message_id` on both attempts is a successful deduplication event.
- Add a `x-idempotent-replay: true` response header when the backend detects an idempotent
  replay, so the client can confirm the deduplication worked and avoid unnecessary UI updates.
  This header has no security implications and mirrors the pattern used by Stripe's API.

### 5.5 Rollout

- **Effort**: M (Medium) — ~50 lines of backend change, ~5 lines of frontend type/send
  change, one test file.
- **Backward compat**: Fully backward compatible; `client_request_id` is optional.
- **Rollback**: Remove the `if inp.client_request_id` block; revert to unconditional
  `new_id()`. No DDB schema change required.
- **Risk**: Low. The `ConditionExpression` on `put_item` is a proven DynamoDB pattern.
  The only new edge case is the race-condition `ConditionalCheckFailedException` on the
  first write — handled by returning the existing item.
- **Sequencing**: Implement before PWA offline-queue feature (PWA-004) ships to
  production. Can be deployed independently to any existing client.
