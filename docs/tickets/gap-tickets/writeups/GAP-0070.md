> ~5 pages. Fix-oriented. Verified against actual codebase 2026-06-05; claim is **inaccurate**

## 1. Summary & Classification

- **Severity**: HIGH (as filed) — downgraded to LOW for the core claim, but a **genuine
  medium-severity residual gap** exists (kill-switch UI absent from the dashboard).
- **Source ticket**: ADS-018 · **Status**: Filed as Open, partially false-positive.
- **Owning area**: Frontend / Admin Ad Platform (ADS-018)
- **GAP claim**: `AdminAdDashboard.tsx` and `frontend/src/api/endpoints/adminAds.ts` are both
  absent; admins have no UI access to the ad management backend.

**Verdict: CLAIM INACCURATE.** Both artifacts named in the gap ticket exist, though under
different names than the ticket specifies:

| Artifact claimed missing | Actual path | Status |
|---|---|---|
| `AdminAdDashboard.tsx` | `frontend/src/pages/admin/AdPlatformDashboard.tsx` | Present, 290+ lines |
| `frontend/src/api/endpoints/adminAds.ts` | `frontend/src/api/endpoints/adminAdPlatform.ts` | Present, 75 lines |

**What the ticket got wrong**: The gap audit looked for the exact names `AdminAdDashboard` and

toggle. The kill-switch backend (GAP-0068) is also absent, so both the backend service and the
corresponding UI are missing. Fixing GAP-0068 (backend) should be paired with a frontend
kill-switch panel in `AdPlatformDashboard`. This write-up documents the frontend portion of
that work.

**Related tickets**: GAP-0068 (kill switch backend — prerequisite), GAP-0069 (account
suspension cascade), ADS-018 source ticket, SECOPS-007.

## 2. Current-State Investigation (root cause of the false-positive)

### Dashboard component — `frontend/src/pages/admin/AdPlatformDashboard.tsx`

A full read of `AdPlatformDashboard.tsx` confirms a fully-functional admin dashboard:

- **Revenue tab**: `getPlatformMetrics()`, `getRevenueSeries()`, `getTopSpenders()` — shows
  total spend, platform revenue (30 % share), creator share, impressions, monthly revenue
  series table, and top-10 spending advertisers.
- **Moderation tab**: `getModerationQueue()` — lists accounts and creatives awaiting review
  with Approve/Reject action buttons backed by `moderateAccount` / `moderateCreative` mutations.
- **Accounts tab**: `listAdvertiserAccounts()` with status filter — shows account status,
  suspension actions (Suspend button → `moderate_account(action='suspend')`).
- **Creatives tab**: `listAdCreatives()` — shows creatives with status badges.

The component imports from `@/api/endpoints/adminAdPlatform` (lines 3–12), which is the file
the gap ticket named `adminAds.ts`.

### API wrapper — `frontend/src/api/endpoints/adminAdPlatform.ts`

All nine API functions cover the full backend surface:
`listAdvertiserAccounts`, `getAdvertiserAccount`, `listAdCampaigns`, `listAdCreatives`,
`getModerationQueue`, `getModerationHistory`, `moderateAccount`, `moderateCreative`,
`getPlatformMetrics`, `getRevenueSeries`, `getTopSpenders`.

### Route and sidebar wiring

```tsx
// frontend/src/App.tsx:120, 445
const AdPlatformDashboard = lazy(() => import("@/pages/admin/AdPlatformDashboard"));
// …
<Route path="admin/ad-platform" element={<AdPlatformDashboard />} />

// frontend/src/components/layout/Sidebar.tsx:235
{ label: "Ad Platform", path: "/admin/ad-platform", icon: <Megaphone …> }
```

The sidebar entry is gated by `showModerationBoard` (line 308), which is the same guard used
by other admin moderation features, ensuring it only appears for ADMIN/ROOT users.

### Real gap: no kill-switch panel in the dashboard

`AdPlatformDashboard.tsx` has four tabs: Revenue, Moderation, Accounts, Creatives. There is
no "Emergency Controls" or "Kill Switch" tab. The backend endpoint (`POST /ui/admin/ad-
platform/kill-switch`) doesn't exist yet (GAP-0068), but the frontend UI for it is also absent.
Both halves of the kill-switch feature need to land together.

### Why the audit produced a false-positive

The ADS-018 spec section described the component as `AdminAdDashboard.tsx`. The implementation
named it `AdPlatformDashboard.tsx` for consistency with `AdPlatformDashboard` (the naming
convention used throughout the admin section, e.g., `AdminComputeDashboard.tsx`,
`RateLimitDashboard.tsx`). Similarly, the spec called the API wrapper `adminAds.ts`, but the
implementation used `adminAdPlatform.ts` to match the backend module name
(`admin_ad_platform.py`). The audit script checked for the exact spec names and reported them
as missing.

## 3. Impact / Exploit / Blast Radius

### Current state (with the corrected understanding)

**Admins DO have UI access** to the ad management backend via `/admin/ad-platform`. The
"admins have no UI access" impact stated in the gap ticket is therefore not accurate. The
moderation queue, account suspension, creative review, and platform metrics are all functional.

### Real gap impact: missing kill-switch UI

Without a kill-switch panel, ROOT operators who need to halt all ad serving in an emergency
must use `curl` or the Swagger UI (`/docs`). This is acceptable for a technical operator but
suboptimal for:
- Speed of response during an incident (UI is faster than curl)
- Auditability in the UI (visual confirmation of current state before toggling)
- Error prevention (the UI can require a reason field and a confirmation dialog; raw curl
  does not)

The financial and compliance impact of a missing kill-switch UI mirrors GAP-0068's blast radius
— the UI just makes the operational control more ergonomic, not more correct. The backend gate
in `serve_ad` (once GAP-0068 is implemented) is the actual enforcement point.

## 4. Fix Design (code-level)

### Part A: Close the false-positive

No product code changes are required to address the originally-stated gap. The resolution is:

### Part B: Add kill-switch panel to `AdPlatformDashboard.tsx` (prerequisite: GAP-0068 backend)

Once GAP-0068 lands (backend kill-switch service + endpoint), add a fifth tab to the dashboard.

#### Step 1: Add API wrapper functions to `adminAdPlatform.ts`

```typescript
// frontend/src/api/endpoints/adminAdPlatform.ts — append

export interface KillSwitchState {
  active: boolean;
  toggled_by: string;
  reason: string;
  updated_at: number;
}

export interface KillSwitchToggleIn {
  enabled: boolean;
  reason: string;
}

export const getKillSwitchState = () =>
  api.get<KillSwitchState>(`${BASE}/kill-switch`);

export const toggleKillSwitch = (data: KillSwitchToggleIn) =>
  api.post<KillSwitchState>(`${BASE}/kill-switch`, data);
```

#### Step 4: Implement `KillSwitchPanel` (sub-component within the file or a shared component)

```tsx
function KillSwitchPanel() {
  const qc = useQueryClient();
  const [reason, setReason] = useState("");
  const [confirming, setConfirming] = useState(false);

  const ksQ = useQuery({
    queryKey: ["adPlatform", "kill-switch"],
    queryFn: () => getKillSwitchState(),
    refetchInterval: 10_000,  // poll every 10 s to show live state
  });

  const toggleMut = useMutation({
    mutationFn: (data: { enabled: boolean; reason: string }) => toggleKillSwitch(data),
    onSuccess: (r) => {
      toast[r.active ? "error" : "success"](
        r.active ? "Ad serving HALTED" : "Ad serving RESUMED",
      );
      qc.invalidateQueries({ queryKey: ["adPlatform", "kill-switch"] });
      setReason("");
      setConfirming(false);
    },
    onError: () => toast.error("Kill switch action failed"),
  });

  const ks = ksQ.data;
  const isActive = ks?.active ?? false;

  return (
    <Card className={isActive ? "border-destructive" : ""} data-testid="ks-panel">
      <CardHeader>
        <CardTitle className="flex items-center gap-2">
          <AlertTriangle className={`h-5 w-5 ${isActive ? "text-destructive" : "text-muted-foreground"}`} />
          Platform-Wide Ad Kill Switch
        </CardTitle>
      </CardHeader>
      <CardContent className="space-y-4">
        <div className="rounded border p-3 text-sm">
          <div className="flex justify-between">
            <span>Status</span>
            <Badge variant={isActive ? "destructive" : "default"} data-testid="ks-status">
              {isActive ? "ACTIVE — All serving halted" : "Inactive — Serving normally"}
            </Badge>
          </div>
          {ks?.toggled_by && (
            <div className="mt-2 flex justify-between text-muted-foreground">
              <span>Last toggled by</span>
              <span>{ks.toggled_by}</span>
            </div>
          )}
          {ks?.reason && (
            <div className="mt-1 flex justify-between text-muted-foreground">
              <span>Reason</span>
              <span className="max-w-xs text-right">{ks.reason}</span>
            </div>
          )}
        </div>

        {!confirming ? (
          <Button
            variant={isActive ? "default" : "destructive"}
            onClick={() => setConfirming(true)}
            data-testid="ks-toggle-btn"
          >
            <Power className="mr-2 h-4 w-4" />
            {isActive ? "Resume Ad Serving" : "Halt All Ad Serving"}
          </Button>
        ) : (
          <div className="space-y-2 rounded border border-destructive p-3">
            <p className="text-sm font-medium text-destructive">
              {isActive
                ? "Confirm: resume all ad serving?"
                : "Confirm: HALT ALL AD SERVING platform-wide?"}
            </p>
            {!isActive && (
              <div>
                <label htmlFor="ks-reason" className="text-sm">
                  Reason (required)
                </label>
                <input
                  id="ks-reason"
                  className="mt-1 w-full rounded border px-3 py-1.5 text-sm"
                  placeholder="Describe the reason for halting ad serving…"
                  value={reason}
                  onChange={(e) => setReason(e.target.value)}
                  data-testid="ks-reason-input"
                />
              </div>
            )}
            <div className="flex gap-2">
              <Button
                variant={isActive ? "default" : "destructive"}
                disabled={(!isActive && !reason.trim()) || toggleMut.isPending}
                onClick={() => toggleMut.mutate({ enabled: !isActive, reason })}
                data-testid="ks-confirm-btn"
              >
                Confirm
              </Button>
              <Button variant="outline" onClick={() => setConfirming(false)}>
                Cancel
              </Button>
            </div>
          </div>
        )}
      </CardContent>
    </Card>
  );
}
```

### Dev/Prod parity (SECOPS-007)

The kill-switch UI calls `POST /ui/admin/ad-platform/kill-switch` which requires ROOT session
auth (cookie-based JWT). The same endpoint and auth mechanism exist in both dev and prod — no
mock/real branching. The `getKillSwitchState` GET poll is also auth-gated (ADMIN or ROOT).

### Backward compatibility

The new tab is purely additive. Existing tabs (Revenue, Moderation, Accounts, Creatives) are
unchanged. The API wrapper additions to `adminAdPlatform.ts` are new exports that do not affect
existing imports.

### Observability

- The `getKillSwitchState` query polls every 10 seconds — this provides a live indicator in the
  dashboard without requiring a page reload. If the kill switch is enabled by another operator,
  the dashboard will reflect it within 10 seconds.
- Backend `logger.warning("ad_kill_switch_toggled ...")` (from GAP-0068) provides the
  server-side audit trail.

### Rollback

The kill-switch panel is an additive new tab. Rolling back means removing the "Controls" tab
from `AdPlatformDashboard.tsx` and the two new functions from `adminAdPlatform.ts`. The backend
kill-switch state in DynamoDB can be read and cleared by a ROOT operator via the backend API.

### Risks

- **GAP-0068 prerequisite**: the kill-switch UI is a no-op until the backend is implemented.
  The UI should be gated or hidden behind `S.dev_mode` until GAP-0068 lands, or both should
  land in the same PR.
- **ROOT-only action**: the kill-switch endpoint (GAP-0068) requires ROOT role. The UI should
  confirm the user's role client-side (read from `authStore`) and hide the panel for ADMIN
  users to avoid a confusing 403 response.
