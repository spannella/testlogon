# GAP-0169: `delete_clip` does not check admin/moderator role — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement.** The `delete_clip` service function
(`app/services/broadcast_clip.py:270-293`) authorises deletion only when the
calling actor matches the clip's `creator_user_id` (the user who created the
clip) or `broadcaster_user_id` (the owner of the broadcast session). The
function's own docstring states "Authorized for: clip creator, broadcaster,
**or admin**", but the code does not implement the admin/moderator arm of
that check. Platform administrators (role `ADMIN`) and root operators (role
`ROOT`) cannot delete clips from any broadcast, even when content-moderation
policy requires it. The router (`app/routers/broadcast_clips.py:93-96`) passes
only `ctx["user_sub"]` to `delete_clip` and does not forward the caller's
role.

**Severity:** HIGH — content moderation is unavailable to admins; harmful
clips posted on any broadcaster's stream cannot be removed by platform
operators without impersonating the broadcaster.  
**Source ticket:** ENGAGE-005  
**Status:** Open  
**Owning area:** `app/services/broadcast_clip.py:270-293`,
`app/routers/broadcast_clips.py:93-96`  
**Effort:** S

**Verdict from code investigation:** Claim confirmed exactly. The
authorization block at `app/services/broadcast_clip.py:280-285` is a
two-condition OR (`actor != creator_user_id and actor != broadcaster_user_id`)
with no role branch. The router at line 96 calls
`delete_clip(clip_id, actor=ctx["user_sub"])` without passing `ctx["role"]`.

**Related tickets:** GAP-0168, ENGAGE-005.

## 2. Current-State Investigation (root cause)

### `delete_clip` service — missing role branch

`app/services/broadcast_clip.py:270-293`:

```python
def delete_clip(clip_id: str, actor: str) -> Dict[str, Any]:
    """Delete a clip (soft delete).

    Authorized for: clip creator, broadcaster, or admin.
    """
    resp = T.broadcast_clips.get_item(Key={"clip_id": clip_id})
    item = resp.get("Item")
    if not item:
        raise HTTPException(404, "Clip not found")

    # Authorization
    if (
        actor != item.get("creator_user_id")
        and actor != item.get("broadcaster_user_id")
    ):
        raise HTTPException(403, "Not authorized to delete this clip")

    T.broadcast_clips.update_item(
        Key={"clip_id": clip_id},
        UpdateExpression="SET #s = :deleted",
        ExpressionAttributeNames={"#s": "status"},
        ExpressionAttributeValues={":deleted": "deleted"},
    )
    return {"ok": True, "clip_id": clip_id, "status": "deleted"}
```

The authorization check:

```python
if (
    actor != item.get("creator_user_id")
    and actor != item.get("broadcaster_user_id")
):
    raise HTTPException(403, ...)
```

is evaluated solely on string equality between `actor` (the caller's
`user_sub`) and the two stored IDs. The caller's role is never consulted.
An `ADMIN` or `ROOT` user calling this endpoint with their own `user_sub`
will always fail the check (their sub does not match either stored ID) and
receive a `403`.

The docstring "Authorized for: clip creator, broadcaster, or admin" is
misleading — it describes the intended design but not the actual behaviour.

### Router — role not forwarded

`app/routers/broadcast_clips.py:93-96`:

```python
@router.delete("/broadcast/clips/{clip_id}")
def delete_clip_route(clip_id: str, ctx: dict = Depends(_ctx)):
    """Delete a clip (creator or broadcaster)."""
    return delete_clip(clip_id, actor=ctx["user_sub"])
```

`ctx` is the dict returned by `require_ui_session`. It contains `user_sub`,
`role`, and `admin_profile`. Only `user_sub` is forwarded. The route docstring
("creator or broadcaster") also omits admin, confirming this was not
intentionally implemented.

### Role model in `require_ui_session`

`app/auth/deps.py` (per CLAUDE.md) returns a dict with keys `user_sub`,
`role`, and `admin_profile`. `role` is a `Role` enum (`USER`, `ADMIN`,
`ROOT`). The comparison `role >= Role.ADMIN` is the standard idiom used
elsewhere in the codebase for admin access gates.

## 3. Impact / Exploit / Blast Radius

**Who is affected:** Platform administrators and root operators who need to
moderate content on any broadcast.

**Content moderation blocked.** A clip containing harmful, illegal, or
policy-violating content can only be removed by the clip's creator or the
broadcaster of the originating session. If neither is cooperative (e.g.,
the broadcaster is offline, or the creator posted a clip of their own
misconduct), a platform admin has no API mechanism to remove it. The clip
remains visible in `list_gallery` and `list_clips_for_session` to all users.

**Impersonation workaround is itself a security concern.** The only current
workaround — an admin impersonating the broadcaster to call `delete_clip` —
is auditable but leaves an audit trail that obscures the real reason for
deletion (content moderation vs. broadcaster self-action). It also requires
the broadcaster to have an active session, which may not be the case.

**Admin direct-DynamoDB write bypass.** An admin could soft-delete the clip
by writing directly to DynamoDB via the root CLI (`scripts/rootctl`) or a
manual AWS console operation. This bypasses all business logic (SSE
notification of deletion, audit log) and is error-prone.

**Compliance exposure.** Platform-level CSAM, copyright, and DMCA response
workflows require rapid, automated takedown capability with an admin actor.
The absence of an admin delete path blocks compliant takedown within
statutory timeframes (24-hour CSAM; 72-hour GDPR; 14-day DMCA safe harbour).

**Blast radius:** Confined to `T.broadcast_clips` and content moderation
operations. No financial or authentication data is affected.

## 4. Fix Design (code-level)

### Step 1 — Add `role` parameter to `delete_clip`

`app/services/broadcast_clip.py:270`:

```python
from app.auth.roles import Role  # add this import at the top of the file

def delete_clip(clip_id: str, actor: str, role: Role = Role.USER) -> Dict[str, Any]:
    """Delete a clip (soft delete).

    Authorized for: clip creator, broadcaster, or platform admin/root.
    """
    resp = T.broadcast_clips.get_item(Key={"clip_id": clip_id})
    item = resp.get("Item")
    if not item:
        raise HTTPException(404, "Clip not found")

    # Authorization: creator, broadcaster, or platform admin/root
    is_admin = role >= Role.ADMIN
    if (
        not is_admin
        and actor != item.get("creator_user_id")
        and actor != item.get("broadcaster_user_id")
    ):
        raise HTTPException(403, "Not authorized to delete this clip")

    T.broadcast_clips.update_item(
        Key={"clip_id": clip_id},
        UpdateExpression="SET #s = :deleted",
        ExpressionAttributeNames={"#s": "status"},
        ExpressionAttributeValues={":deleted": "deleted"},
    )

    logger.info(
        "clip: deleted clip_id=%s actor=%s role=%s reason=moderation",
        clip_id, actor, role.value if hasattr(role, "value") else role,
    )

    return {"ok": True, "clip_id": clip_id, "status": "deleted"}
```

The `role` parameter defaults to `Role.USER` so all existing callers that do
not pass a role (e.g., internal/script callers) continue to be restricted to
creator/broadcaster, preserving the principle of least privilege.

### Step 2 — Forward `role` from the router

`app/routers/broadcast_clips.py:93-96`:

```python
@router.delete("/broadcast/clips/{clip_id}")
def delete_clip_route(clip_id: str, ctx: dict = Depends(_ctx)):
    """Delete a clip (creator, broadcaster, or platform admin/root)."""
    from app.auth.roles import Role
    role = ctx.get("role", Role.USER)
    return delete_clip(clip_id, actor=ctx["user_sub"], role=role)
```

### Step 3 — Audit log for admin-initiated deletions (optional but recommended)

Within `delete_clip`, after a successful soft-delete, if `is_admin` is `True`,
write a moderation audit record:

```python
if is_admin:
    from app.core.time import now_ts
    T.audit_log.put_item(Item={
        "pk": f"MOD#{clip_id}",
        "sk": str(now_ts()),
        "actor": actor,
        "role": role.value if hasattr(role, "value") else str(role),
        "action": "delete_clip",
        "clip_id": clip_id,
        "session_id": item.get("session_id", ""),
        "creator_user_id": item.get("creator_user_id", ""),
    })
```

This provides an immutable record linking the clip deletion to the admin
actor, separate from the application log, which satisfies DMCA
counter-notification evidence requirements.

### Dev/Prod parity (SECOPS-007)

`role` is populated from the `ui_access_token` JWT cookie in cookie-auth
mode, or from the Cognito JWT in bearer-auth mode (per `app/auth/deps.py`).
Both paths produce a `Role` enum value. The fix is identical in dev
(cookie-based admin sessions from `e2e_admin_session_setup.py`) and
production (Cognito JWT with role claim). No mock or feature-flag path is
required.

The `T.audit_log` write uses the same DynamoDB endpoint as all other writes
(`S.ddb_endpoint_url`), so it works in both dev (DynamoDB Local) and prod.

### Backward compatibility / feature flags

The `role` parameter defaults to `Role.USER`, so no existing caller is
broken. The authorization logic for non-admin callers is unchanged (creator
or broadcaster only). No DynamoDB schema change is required unless the
audit log table does not already exist.

### Alternatives considered

- **Separate admin endpoint** (`DELETE /admin/clips/{clip_id}`) — cleaner
  separation of concerns but doubles the endpoint surface and requires
  routing the session-auth middleware differently. Rejected: unnecessary
  complexity for a one-line authorization fix.
- **Require `require_admin_session` at the router level** — would gate the
  entire delete route behind ADMIN, preventing creators and broadcasters from
  using it. Rejected: too restrictive.
- **Role check in middleware** — not appropriate for a resource-level
  authorization decision. Rejected.

### Observability

The `logger.info` line added in Step 1 will produce log entries for every
admin-initiated deletion:

```
clip: deleted clip_id=bclip_abc actor=charlie_sub role=ADMIN reason=moderation
```

Alert on this log pattern in the production logging system to audit all

### Rollback

Remove the `role` parameter from `delete_clip` and revert the router to
pass only `actor`. No schema changes. The rollback restores the original
`403` behaviour for admins.

### Risk

**Low.** The change adds a new code path (`is_admin = role >= Role.ADMIN`)
that is reached only when the caller is authenticated as `ADMIN` or `ROOT`.
All existing behaviour for `USER` callers (creator and broadcaster) is
unchanged. The `role` parameter defaults to `Role.USER`, so no call site
breaks if the role is not provided.

The only risk is that an `ADMIN` or `ROOT` user could delete any clip. This
is the intended capability — it is a privilege explicitly granted to admins
and is no different from the other admin capabilities (ticket management,
user management, etc.) already implemented in the codebase.

### Effort

**S** — approximately 30 minutes: two-line code change in service + one-line
router change, import, and unit tests (~25 min).

### Sequencing

Deploy alongside GAP-0168 as part of the ENGAGE-005 clip service hardening
