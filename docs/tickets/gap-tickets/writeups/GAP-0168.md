# GAP-0168: `_count_user_clips_for_session` uses `FilterExpression` with no pagination — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement.** The broadcast clip service (ENGAGE-005) enforces a
per-user quota of at most `_MAX_CLIPS_PER_BROADCAST = 10` clips per broadcast
session via `_count_user_clips_for_session`. This helper queries the
`BySession` GSI with `Select="COUNT"` and a `FilterExpression` that restricts
to clips by the requesting user whose status is not `"deleted"`. Because
DynamoDB applies `FilterExpression` **after** reading up to 1 MB of raw items
per page, and because `_count_user_clips_for_session` issues exactly one
`query()` call with no `LastEvaluatedKey` loop, the function silently
under-counts on any session that has accumulated enough clips across all users
to exceed the 1 MB page boundary. The quota guard therefore fails to detect
that a user has already created 10 clips, allowing unlimited clip creation on
busy sessions.

**Severity:** HIGH  
**Source ticket:** ENGAGE-005  
**Status:** Open  
**Owning area:** `app/services/broadcast_clip.py:335-343`  
**Effort:** S

**Verdict from code investigation:** Claim confirmed exactly. The function at
`app/services/broadcast_clip.py:335-343` issues a single `T.broadcast_clips.query()`
with `Select="COUNT"` and a `FilterExpression` but has no `LastEvaluatedKey`
pagination loop.

**Related tickets:** ENGAGE-005, GAP-0169.

## 2. Current-State Investigation (root cause)

### The function — single-page query

`app/services/broadcast_clip.py:335-343`:

```python
def _count_user_clips_for_session(session_id: str, user_id: str) -> int:
    """Count clips created by a user for a specific session."""
    resp = T.broadcast_clips.query(
        IndexName="BySession",
        KeyConditionExpression=Key("GSI1PK").eq(f"SESSION#{session_id}"),
        FilterExpression=Attr("creator_user_id").eq(user_id) & Attr("status").ne("deleted"),
        Select="COUNT",
    )
    return resp.get("Count", 0)
```

A single `query()` call is issued. The response `resp["Count"]` reflects only
the items that (a) were read in the first page (up to 1 MB raw data) and (b)
passed the `FilterExpression`. If the first page contains 100 items for this
session belonging to other users, and our user's 10 clips are all in the
second page, `resp["Count"]` returns `0` — the user appears to have no clips
and can create more.

### DynamoDB pagination semantics

From the DynamoDB documentation and the CLAUDE.md "Common gotchas" section:

> DDB `FilterExpression` doesn't reduce page size: DynamoDB fetches up to
> 1 MB **before** applying `FilterExpression`. Any query that filters a sparse
> attribute must loop via `LastEvaluatedKey`.

`Select="COUNT"` does not change this behaviour. DynamoDB still reads up to
1 MB of raw items, applies the filter, and returns the count of matching items
within that page. `LastEvaluatedKey` in the response indicates whether more
items exist beyond the current page.

The existing code does not check `resp.get("LastEvaluatedKey")` and does not
loop.

### Quota enforcement call site

`app/services/broadcast_clip.py:104-110`:

```python
existing_clips = _count_user_clips_for_session(session_id, creator_user_id)
if existing_clips >= _MAX_CLIPS_PER_BROADCAST:
    raise HTTPException(429, {
        "code": "CLIP_QUOTA_EXCEEDED",
        "message": f"Maximum {_MAX_CLIPS_PER_BROADCAST} clips per broadcast.",
    })
```

The check fires only if `existing_clips >= 10`. If the count is silently
truncated to, say, `3` (because the user's other 7 clips are on the second
page), the guard passes and a new clip is created — raising the true count
to 11 (or more, if the session has enough other-user clips to fill many pages).

### When does the bug manifest?

The 1 MB page boundary is crossed when the `BySession` GSI contains enough
items for `SESSION#{session_id}` to exceed ~1 MB of raw DDB attribute data.
A single clip item is approximately 400–600 bytes. The boundary is crossed at
roughly 1,700–2,500 clip records per session. On a popular live stream where
many viewers are clipping simultaneously, this threshold is reachable in
minutes during a high-traffic event.

In dev and test environments with a low number of items the bug is invisible
— the first page always contains all clips — which is why the existing test
suite does not catch it.

### Comparison to other list functions

`list_clips_for_session` (`app/services/broadcast_clip.py:214-223`) uses a
`Limit=50` parameter and also does not paginate, but it is a display query
(under-listing is acceptable). `_count_user_clips_for_session` is a
**security/quota** function; under-counting is not acceptable.

## 3. Impact / Exploit / Blast Radius

**Who is affected:** Users of popular broadcast sessions with a high clip
volume.

**Quota bypass.** A user can create more than 10 clips per session by
ensuring that their existing clips are pushed past the 1 MB page boundary
by other users' activity. In practice, they do not need to manipulate
anything deliberately — on a busy session this happens naturally.

**Storage amplification.** Each clip creates a DynamoDB item, triggers
a background processing job (`_mark_clip_ready` in dev mode; a real
processing pipeline in prod), and stores a video segment in S3. Without
an effective quota, a single user can saturate the clip processing queue
and S3 storage for a session.

**Rate-limit bypass at scale.** `_enforce_clip_rate_limit` (line 35-49)
provides a 30-second per-user per-session rate limit, but this is in-memory
(`_CLIP_RATE_BUCKETS` dict). The per-broadcast quota (`_MAX_CLIPS_PER_BROADCAST`)
is the durable limit enforced via DynamoDB. Bypassing the DynamoDB quota
means only the in-memory rate limit applies — which resets on process
restart.

**Financial impact.** S3 storage and video processing compute costs are
incurred for each clip regardless of quota. Unlimited clipping on a busy
session translates directly to unbounded infrastructure cost.

**Blast radius:** `T.broadcast_clips` table, S3 bucket for clip video
segments, background processing queue. No messaging, billing, or auth
tables are affected.

## 4. Fix Design (code-level)

### Replace single query with paginated loop

`app/services/broadcast_clip.py:335-343` — replace entirely:

```python
def _count_user_clips_for_session(session_id: str, user_id: str) -> int:
    """Count non-deleted clips created by a user for a specific session.

    Paginates through all DDB pages so that FilterExpression never
    silently under-counts on high-volume sessions (GAP-0168).
    """
    total = 0
    kwargs = {
        "IndexName": "BySession",
        "KeyConditionExpression": Key("GSI1PK").eq(f"SESSION#{session_id}"),
        "FilterExpression": (
            Attr("creator_user_id").eq(user_id) & Attr("status").ne("deleted")
        ),
        "Select": "COUNT",
    }
    while True:
        resp = T.broadcast_clips.query(**kwargs)
        total += resp.get("Count", 0)
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
        kwargs["ExclusiveStartKey"] = last_key
    return total
```

The loop continues while `LastEvaluatedKey` is present, accumulating the
per-page `Count` into `total`. This is the standard DynamoDB pagination
pattern used throughout the codebase (e.g., `app/services/messaging.py`
conversation list logic noted in CLAUDE.md).

### Performance consideration

Each page read costs one DynamoDB `query` call. On a session with 2,000
clips across all users, this is approximately 1–2 extra round trips. For
quota-enforcement on create (a write path), this latency is acceptable.
The typical case (fewer than 1,000 clips per session) requires only one
page read, so the common-path performance is unchanged.

If profiling shows this is a bottleneck, an alternative is to maintain
a per-user per-session clip count in a separate DynamoDB item (a counter
record) updated atomically on every `create_broadcast_clip` and
`delete_clip`. That approach is more complex and introduces a two-table
write; the pagination fix is sufficient and simpler.

### Dev/Prod parity (SECOPS-007)

DynamoDB Local (port 8001) and production DynamoDB both return
`LastEvaluatedKey` when a page is exhausted under the 1 MB limit. The
pagination loop behaves identically in both environments. No mock or
feature-flag path is required.

In `S.dev_mode`, `_mark_clip_ready` fires synchronously
(`app/services/broadcast_clip.py:154-155`); the count function is not
affected by this flag.

### Backward compatibility / feature flags

No API surface change. The function signature is identical. No DynamoDB
schema change. The fix is fully backward compatible.

## 5. Testing, Verification & Rollout

### Regression test — pytest offline (moto)

The key challenge is triggering the second-page scenario in a unit test.
With moto, we can insert enough items to force a second page by setting a
low `Limit` hint — but `Select=COUNT` with moto respects `LastEvaluatedKey`
even for small datasets. A practical approach is to patch the DynamoDB
response to simulate pagination.

```python
# tests/services/test_clip_quota_pagination.py
"""GAP-0168: _count_user_clips_for_session must paginate fully."""
import pytest
from unittest.mock import patch, call


def test_count_paginates_across_pages():
    """
    Simulate a DDB response where the first page returns Count=3 for the
    target user (out of 200 items) but has a LastEvaluatedKey, and the
    second page returns Count=7 with no LastEvaluatedKey.
    Total must be 10 (quota reached), not 3 (under-count).

    Fails before fix: returns 3 (only first page).
    Passes after fix: returns 10 (both pages).
    """
    from app.services.broadcast_clip import _count_user_clips_for_session

    page1 = {"Count": 3, "LastEvaluatedKey": {"clip_id": {"S": "cursor_abc"}}}
    page2 = {"Count": 7}

    call_count = {"n": 0}

    def fake_query(**kwargs):
        n = call_count["n"]
        call_count["n"] += 1
        return [page1, page2][n]

    with patch.object(
        __import__("app.core.tables", fromlist=["T"]).T,
        "broadcast_clips",
    ) as mock_table:
        mock_table.query.side_effect = fake_query
        result = _count_user_clips_for_session("sess_001", "user_001")

    assert result == 10, (
        f"GAP-0168: expected 10 (paginated), got {result} (under-counted)"
    )
    assert call_count["n"] == 2, "Expected exactly 2 DDB query calls"
```

**Fails before fix:** `result == 3` (only the first page's `Count` is
returned; the loop is missing).  
**Passes after fix:** `result == 10` (both pages are accumulated).
