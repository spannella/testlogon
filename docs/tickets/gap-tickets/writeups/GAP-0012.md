# GAP-0012: WebSocket Hook Not Wired — SSH Terminal Output Bypasses Monitoring Pipeline — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: AGENT-006. Investigation: docs/tickets/gap-tickets/investigations/GAP-0012.md.

---

## 1. Summary & Classification

**Plain-English statement**: The SSH browser terminal WebSocket handler polls the SSH bridge for output and forwards it directly to the connected browser client. It never calls into the terminal monitoring pipeline — the output is not buffered, not pattern-matched, and no feedback requests or completion signals are ever automatically created. The entire AGENT-006 detection pipeline (`TerminalOutputBuffer` → `PatternMatcher` → `create_feedback_request` / `transition_agent_state`) is dead code for live SSH sessions.

## 2. Current-State Investigation (root cause)

### Confirmed absence of `process_terminal_output`

A grep for `process_terminal_output` across all Python files under `app/` returns zero matches. The function described in the gap ticket does not exist. The monitoring primitives exist as separate, unconnected building blocks:

- `app/services/terminal_monitor.py:147` — `get_or_create_buffer(worker_id)` → returns/creates a `TerminalOutputBuffer`
- `app/services/terminal_monitor.py:174` — `PatternMatcher.match(text)` → returns a signal dict or `None`
- `app/services/terminal_monitor.py:191` — `create_feedback_request(...)` → writes to `T.agent_feedback`

None of these are called from the WebSocket handler.

### The WebSocket forwarding loop

The SSH WebSocket handler lives in `app/routers/browser_ssh_terminal.py`, function `browser_ssh_terminal_ws` starting at line 715. The output-forwarding block is at lines 774–778:

```python
# app/routers/browser_ssh_terminal.py:774-778
if ssh_bridge:
    output = ssh_bridge.poll_output()
    if output:
        session_last_activity_at = now
        await websocket.send_json({"type": "output", "payload": {"data": output}})
```

The output chunk is sent directly to the browser with no intermediate processing. There is no call to `terminal_monitor` anywhere in this function (confirmed by reading the full function body from line 715 to the closing `except` block at ~line 900).

### Worker ID is not tracked in the WebSocket session

The WebSocket handler (line 715–end) maintains `session_user_sub` (extracted from the auth token at line 734) but has no `session_worker_id` variable. A `worker_id` is required to:
1. Look up the correct `TerminalOutputBuffer` via `get_or_create_buffer(worker_id)`
2. Create feedback requests against the correct worker in `T.agent_feedback`
3. Call `transition_agent_state(user_id, worker_id, ...)` on signal dispatch

The `connect` message payload (parsed in the WebSocket message handler, further down in the loop) currently accepts `host`, `port`, `username`, `password`, and `privateKey` fields. It does not accept or store a `worker_id`.

### Root cause summary

The monitoring service (`terminal_monitor.py`) was built as a standalone library of primitives. The integration layer — a composite `process_terminal_output` function that chains buffer append → pattern match → signal dispatch — was never written, and the WebSocket handler was never updated to call it. The `worker_id` linkage between an active SSH session and the agent orchestrator was also never established.

## 3. Impact / Exploit / Blast Radius

**Primary functional impact**: The entire AGENT-006 auto-feedback pipeline is non-functional for SSH-based agents:

- An agent that prints `[AGENT_FEEDBACK_NEEDED]` in the terminal will have that signal silently discarded. No feedback request is created. The operator sees nothing in the Agent Queue UI.
- An agent that prints `[AGENT_COMPLETE]` will remain in `working` state indefinitely; its ticket is never auto-closed.
- An agent that prints `[AGENT_ERROR]` stays in `working` state; no alert fires.

**Scope**: All live SSH agent sessions. Affects every workflow that relies on automatic signal detection rather than manual operator intervention.

**Operator workaround**: Operators can manually create feedback requests via `POST /agent-feedback/{worker_id}` and manually transition state via the orchestrator API. This is impractical at scale and defeats the purpose of the monitoring system.

**Security**: No security exploit. The monitoring pipeline bypass does not expose private data or allow privilege escalation.

**Availability risk**: Agents accumulate in `working` state indefinitely, consuming worker slot quota. If the quota is fixed (e.g., 5 concurrent workers per user), all slots will eventually be occupied by stalled agents with no automatic recovery.

## 4. Fix Design (code-level)

### Step 1 — Add `process_terminal_output` to `terminal_monitor.py`

Insert the integration function immediately after the `PatternMatcher` class definition (around line 186):

```python
# app/services/terminal_monitor.py — new function after PatternMatcher class

def get_default_patterns_for_worker(worker_id: str) -> Dict[str, List[str]]:
    """Return per-worker pattern config, falling back to defaults.
    Future: load from T.agent_workers item or a worker-config table.
    """
    return DEFAULT_FEEDBACK_PATTERNS


def process_terminal_output(
    worker_id: str,
    chunk: str,
) -> Optional[Dict[str, str]]:
    """Feed a chunk of terminal output through the buffer and pattern matcher.

    Appends *chunk* to the worker's ring buffer, then runs the PatternMatcher
    against the most recent 2000 characters.

    Returns a signal dict {"signal": <category>, "pattern": ..., "match": ...}
    if a pattern fires, else None.
    """
    buf = get_or_create_buffer(worker_id)
    buf.append(chunk)
    recent = buf.get_recent(2000)
    patterns = get_default_patterns_for_worker(worker_id)
    matcher = PatternMatcher(patterns)
    return matcher.match(recent)
```

### Step 2 — Accept `worker_id` in the WebSocket connect message

Extend the `connect` payload handler in `browser_ssh_terminal.py` to extract and store `worker_id`:

```python
# In browser_ssh_terminal_ws, near the top of the WebSocket session locals:
session_worker_id: str | None = None  # NEW

# In the "connect" message handler (where host/port/username are extracted):
session_worker_id = payload.get("worker_id") or None
```

The client (Worker Fleet UI) must pass `worker_id` in the `{"type": "connect", ...}` payload when launching an agent terminal.

### Step 3 — Tap output in the forwarding loop

Replace the output-forwarding block at `browser_ssh_terminal.py:774–778`:

```python
if ssh_bridge:
    output = ssh_bridge.poll_output()
    if output:
        session_last_activity_at = now
        await websocket.send_json({"type": "output", "payload": {"data": output}})
        # Tap into monitoring pipeline if this session is agent-tracked
        if session_worker_id:
            signal = terminal_monitor.process_terminal_output(session_worker_id, output)
            if signal:
                await _dispatch_terminal_signal(
                    signal=signal,
                    worker_id=session_worker_id,
                    user_id=session_user_sub,
                    websocket=websocket,
                )
```

### Step 4 — Implement `_dispatch_terminal_signal`

Add as a helper in `browser_ssh_terminal.py` (can also live in `terminal_monitor.py`):

```python
async def _dispatch_terminal_signal(
    signal: Dict[str, str],
    worker_id: str,
    user_id: str,
    websocket: WebSocket,
) -> None:
    """Dispatch an agent terminal signal to the appropriate handler."""
    category = signal.get("signal")
    match_text = signal.get("match", "")
    buf = terminal_monitor.get_or_create_buffer(worker_id)
    context = buf.get_recent(500)

    if category == "feedback_needed":
        try:
            req = terminal_monitor.create_feedback_request(
                user_id=user_id,
                worker_id=worker_id,
                ticket_id="",  # look up from worker record if available
                question=match_text,
                terminal_context=context,
                detected_pattern=signal.get("pattern", ""),
            )
            # Notify browser that a feedback request was created
            await websocket.send_json({
                "type": "feedback_request",
                "payload": {"request_id": req["request_id"], "question": match_text},
            })
            # Transition agent to awaiting_feedback
            from app.services import agent_orchestrator
            try:
                agent_orchestrator.transition_agent_state(user_id, worker_id, "awaiting_feedback")
            except (ValueError, LookupError):
                pass
        except Exception as exc:
            logger.error("Failed to create feedback request for worker %s: %s", worker_id, exc)

    elif category == "completion":
        from app.services import agent_orchestrator
        try:
            agent_orchestrator.transition_agent_state(user_id, worker_id, "completing")
        except (ValueError, LookupError):
            pass
        await websocket.send_json({"type": "agent_complete", "payload": {}})

    elif category == "error":
        from app.services import agent_orchestrator
        try:
            agent_orchestrator.transition_agent_state(user_id, worker_id, "error")
        except (ValueError, LookupError):
            pass
        await websocket.send_json({"type": "agent_error", "payload": {"match": match_text}})
```

### Dev/Prod parity (SECOPS-007)

- `T.agent_feedback.put_item` and `transition_agent_state` use the same boto3 paths in dev (DynamoDB Local, port 8001) and production (AWS DynamoDB). No divergence.
- `TerminalOutputBuffer` is in-process memory. In production with a single uvicorn worker (required by the moto S3 constraint documented in CLAUDE.md), the buffer is shared across all WebSocket connections in the same process. This is consistent.
- The `process_terminal_output` call is synchronous and runs in the asyncio event loop's thread. Terminal output processing (regex matching) is CPU-bound but fast enough (~1 ms for typical chunks) to be safe inline. If large chunks become a concern, offload to `asyncio.get_event_loop().run_in_executor(None, ...)`.
- No feature flag is required; the monitoring tap is gated by `if session_worker_id` — non-agent SSH sessions (without a `worker_id` in the connect payload) are unaffected.

### Backward compatibility

Existing SSH terminal connections that do not send `worker_id` in the connect payload will have `session_worker_id = None` and will skip the monitoring tap entirely. No existing functionality is broken.

### Manual QA steps

1. `just up` — start the dev stack.
2. Create a worker, seed it into `working` state via the agent orchestrator API.
3. Open a browser SSH terminal session and include `worker_id` in the `connect` message payload.
4. In the SSH session, type `echo "[AGENT_FEEDBACK_NEEDED] test question"`.
5. Verify in the Agent Queue UI that a new feedback request appears for the worker.
6. Also verify the worker's `agent_state` transitions to `awaiting_feedback`.
7. Repeat with `echo "[AGENT_COMPLETE]"` and verify state transitions to `completing`.

### Observability

- Log at `INFO` level whenever `process_terminal_output` fires a signal: `logger.info("Terminal signal '%s' detected for worker %s", signal['signal'], worker_id)`.
- Log at `DEBUG` level when no signal fires (to avoid log spam on every output chunk).
- Add a CloudWatch metric `TerminalSignalDetected` with dimension `signal_type` for monitoring detection rates in production.

### Rollback

The monitoring tap is guarded by `if session_worker_id`. Reverting to the pre-fix state requires removing the monitoring tap block and the `process_terminal_output` function. The `T.agent_feedback` DDB table is unaffected — no schema migration needed.

### Risks

- **Pattern false-positive rate**: The default patterns include broad English phrases (e.g., `"(?i)please confirm"`). A verbose agent that routinely prints such phrases in normal output will trigger spurious feedback requests. Mitigation: tighten patterns or add a minimum-context requirement before firing.
- **CPU overhead**: Pattern matching runs on every output chunk. For very high-throughput terminals (e.g., build logs at thousands of lines/second), this adds latency to the WebSocket forwarding loop. Mitigation: batch chunks or use `run_in_executor` for the matching step.
- **Worker ID spoofing**: If the client sends a `worker_id` belonging to another user, the feedback request is created under the wrong worker. Mitigation: validate that `worker_id` belongs to `session_user_sub` before using it (lookup from `T.agent_workers` at connect time).

### Sequencing

1. **GAP-0012 (this ticket)** — adds the integration layer and WebSocket tap. Workers can now auto-create feedback requests.
2. **GAP-0011** — ensures `respond_to_feedback` actually unblocks the agent state machine when a response is submitted.
3. Both fixes should be deployed together; individually they are each incomplete halves of the feedback loop.

**Effort**: M — approximately 3–5 hours of development: ~50 lines for `process_terminal_output` + dispatch, ~15 lines to wire the WebSocket tap, plus tests and the `worker_id` connect payload change.
