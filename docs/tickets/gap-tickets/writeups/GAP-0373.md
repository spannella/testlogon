# GAP-0373: Tenant ID Not Validated at Key Serve Time — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real file:line. No investigation doc exists for this ticket.

## 1. Summary & Classification

**Plain-English statement**: The DRM key server endpoint
`GET /v1/vod/drm/key/{key_id}` validates that the playback entitlement token's
`asset_id` claim matches the `asset` query parameter, but never reads or validates
the `tenant_id` claim embedded in the same token. An attacker can supply any
`tenant_id` value in the URL while presenting a valid token issued for a completely
different tenant, and the server will silently accept the request and derive a key for
the attacker-supplied tenant. The spec (§6.1) requires `tenant_id` to be validated
at key serve time.

- **Severity**: HIGH
- **Source ticket**: VOD-010
- **Status**: Open
- **Owning area**: Backend / DRM Router / `app/routers/vod_drm.py`
- **Verdict**: **Confirmed** — `app/routers/vod_drm.py:66-72` extracts and compares
  `asset_id` from the token claims but there is no corresponding `tenant_id` extraction
  or comparison. The `claims` dict returned by `validate_playback_entitlement` does
  contain `tenant_id` (the JWT payload includes it at `app/services/playback_entitlements.py:237`), but the router never reads `claims["tenant_id"]`.
- **One-line impact**: A valid playback token for Tenant A can be used to request keys
  scoped to any other tenant, bypassing the intended tenant isolation at the key server.
- **Related tickets**: VOD-010 (source), GAP-0372 (tenant_id missing from HKDF
  derivation — companion fix; both must ship together), GAP-0371 (token refresh).

## 2. Current-State Investigation (Root Cause)

### Endpoint validation logic

`app/routers/vod_drm.py:33-103` — the full `get_decryption_key` handler:

```python
@router.get("/key/{key_id}")
def get_decryption_key(
    key_id: str,
    asset: str = Query(..., min_length=1, ...),
    token: str = Query(..., min_length=1, ...),
):
    # 1. Validate entitlement token
    try:
        claims = validate_playback_entitlement(
            token=token,
            expected_audience=S.playback_entitlement_expected_audience or "playback",
        )
    except PlaybackEntitlementError as exc:
        ...

    # 2. Verify asset_id in token matches the requested asset
    token_asset_id = (claims.get("asset_id") or "").strip()
    if token_asset_id != asset.strip():
        raise HTTPException(
            status_code=403,
            detail={"code": "asset_mismatch", ...},
        )

    # 3. Validate key_id matches expected derivation
    if not validate_key_id(key_id, asset):
        ...

    # 4. Derive and return the content key
    content_key = derive_content_key(asset)
    ...
```

**Line 67**: `token_asset_id = (claims.get("asset_id") or "").strip()` — asset ID is
read from the token and compared against the `asset` query param.

**Missing**: There is no equivalent `token_tenant_id = (claims.get("tenant_id") or "").strip()` extraction, no `tenant` query parameter accepted on the endpoint, and no
comparison between token's tenant and a request-supplied tenant.

### What the JWT actually contains

`app/services/playback_entitlements.py:234-245`:

```python
payload = {
    "tenant_id": tenant,   # ← tenant_id IS in the JWT
    "asset_id": asset,
    "session_id": session,
    "device_id": device,
    "profile": selected_profile,
    "aud": aud,
    "iat": now,
    "exp": now + ttl,
    "jti": uuid4().hex,
}
```

The `tenant_id` claim is present in every issued token, but the key server router never
reads `claims["tenant_id"]`. This means the token's tenant binding is completely
unenforced at key serve time.

### The attack surface without the companion GAP-0372 fix

Even in the current codebase (where `derive_content_key` does not accept a
`tenant_id`), failing to validate the tenant at serve time means:

- An attacker with a valid token for `(tenant=alice, asset=vid_001)` can request the
  key server with `?asset=vid_001&token=<alice_token>` and receive the key.
- Because the derivation is also not tenant-scoped (GAP-0372), that key decrypts any
  co-named asset across all tenants.
- After GAP-0372 is fixed, the derivation will be tenant-scoped, but **without this
  fix (GAP-0373)**, an attacker could still:
  1. Present Alice's valid token (`tenant=alice`, `asset=vid_001`).
  2. Append `&tenant=bob` in the request URL.
  3. The server reads `tenant=bob` from the URL, derives the key for
     `(tenant=bob, asset=vid_001)`, and returns Bob's content key.
  Alice's token gives access to Bob's key, defeating the tenant scoping added by
  GAP-0372.

The two gaps are therefore **mutually dependent**: GAP-0372 scopes the derivation; this
gap (GAP-0373) enforces that only the token's own tenant can trigger that derivation.

### Dev vs prod behaviour

Identical code path in both environments. No mock or flag alters the token validation
logic. The gap exists in all deployments.

## 3. Impact / Exploit / Blast Radius

**Exploit walkthrough (post-GAP-0372 fix, pre-GAP-0373 fix)**:

1. Alice is a subscriber to her own creator account; she has a valid playback
   entitlement token: `{tenant_id: "alice", asset_id: "vid_001", …}`.
2. Alice knows (via the public `/v1/vod/drm/info/{asset_id}` endpoint) the `key_id`
   for Bob's video `vid_001`: `key_id=<derived_from_bob_vid_001>`.
3. Alice requests:
   `GET /v1/vod/drm/key/<bob_key_id>?asset=vid_001&tenant=bob&token=<alice_token>`
4. The server validates Alice's token signature ✓, validates `token.asset_id ==
   asset` ✓ (`vid_001 == vid_001`), but never checks that `token.tenant_id == tenant`.
   It proceeds to derive `derive_content_key("vid_001", tenant_id="bob")`.
5. Bob's AES-128 key is returned to Alice. Alice decrypts Bob's premium content.

**Without GAP-0372 fix**: Even simpler — no `tenant` param needed; the derivation is
already the same for all tenants.

**Blast radius**: All DRM-protected content where an attacker holds any valid playback
token. On a platform that allows free-tier or cheap subscription, any user can obtain
a token for their own content and leverage it against any other creator's content with
the same `asset_id`.

**GDPR / compliance**: DRM is the contractual mechanism by which creators license their
content to the platform. A bypass enables unlicensed distribution of creator content,
creating potential liability under the platform's creator agreements and DRM
circumvention laws (DMCA § 1201, EU Copyright Directive Article 6).

## 4. Fix Design (Code-Level)

### Add `tenant` query parameter and validate against token claim

`app/routers/vod_drm.py` — updated `get_decryption_key`:

```python
@router.get("/key/{key_id}")
def get_decryption_key(
    key_id: str,
    asset: str = Query(..., min_length=1, description="Asset ID"),
    tenant: str = Query(..., min_length=1, description="Tenant ID (creator user sub)"),
    token: str = Query(..., min_length=1, description="Playback entitlement token"),
):
    # 1. Validate entitlement token
    try:
        claims = validate_playback_entitlement(
            token=token,
            expected_audience=S.playback_entitlement_expected_audience or "playback",
        )
    except PlaybackEntitlementError as exc:
        ...raise HTTPException...

    # 2a. Verify asset_id in token matches the requested asset (existing check)
    token_asset_id = (claims.get("asset_id") or "").strip()
    if token_asset_id != asset.strip():
        raise HTTPException(
            status_code=403,
            detail={"code": "asset_mismatch",
                    "message": "token asset_id does not match requested asset"},
        )

    # 2b. NEW: Verify tenant_id in token matches the requested tenant (GAP-0373)
    token_tenant_id = (claims.get("tenant_id") or "").strip()
    if not token_tenant_id:
        raise HTTPException(
            status_code=403,
            detail={"code": "missing_tenant_claim",
                    "message": "token is missing tenant_id claim"},
        )
    if token_tenant_id != tenant.strip():
        raise HTTPException(
            status_code=403,
            detail={"code": "tenant_mismatch",
                    "message": "token tenant_id does not match requested tenant"},
        )

    # 3. Validate key_id matches expected derivation (tenant-scoped — GAP-0372)
    try:
        if not validate_key_id(key_id, asset, tenant_id=token_tenant_id):
            raise HTTPException(status_code=404, detail={"code": "key_not_found", ...})
    except VodDrmKeyError as exc:
        raise HTTPException(status_code=400, detail={...})

    # 4. Derive and return the content key (tenant-scoped — GAP-0372)
    try:
        content_key = derive_content_key(asset, tenant_id=token_tenant_id)
    except VodDrmKeyError as exc:
        raise HTTPException(status_code=500, detail={...})

    return Response(content=content_key, media_type="application/octet-stream", ...)
```

### Update `get_key_uri` to embed `tenant` in the manifest URI

`app/services/vod_drm_keys.py:get_key_uri` (also updated in GAP-0372):

```python
def get_key_uri(asset_id: str, tenant_id: str, key_slot: int = 0) -> str:
    key_id = derive_key_id(asset_id, tenant_id, key_slot)
    base_url = (S.vod_drm_key_server_base_url or "...").rstrip("/")
    return f"{base_url}/key/{key_id}?asset={asset_id}&tenant={tenant_id}"
```

HLS players embed this URI in the `#EXT-X-KEY` tag. The player will pass `tenant` to
the key server on every segment playlist fetch, making the tenant claim verifiable end-to-end.

### Backward compatibility and token migration

Existing tokens already contain `tenant_id` in their payload (confirmed in
`playback_entitlements.py:237`), so no token re-issuance is required. The only backward
compatibility risk is the new required `tenant` query parameter on the endpoint. Any
client that previously called the key URI without `?tenant=...` (e.g., custom players or
old HLS manifests) will receive a 422 `Unprocessable Entity` from FastAPI's query
parameter validation. Update the manifest assembly code (`get_key_uri`) in the same
deployment to ensure all new manifests include the `tenant` param.

### Dev/Prod parity (SECOPS-007)

The `tenant_id` claim is validated from the JWT payload, which is a pure crypto
operation with no AWS calls. The query parameter is standard FastAPI. Both environments
use identical token signing and validation logic. No dev mock is needed.

## 5. Testing, Verification & Rollout

### Regression test — fails before / passes after

**pytest offline** (`tests/test_vod_drm_tenant_validation.py`):

```python
"""GAP-0373: Regression test — tenant_id validation at key serve time.

BEFORE fix: key server ignores the tenant query param; any tenant can use any token.
AFTER fix: token tenant_id must match the ?tenant= query param; mismatch → 403.
"""
import os
os.environ.setdefault("VOD_DRM_KEY_ROOT", "test-root-key-for-gap-0373")
os.environ.setdefault("VOD_DRM_ENABLED", "1")
os.environ.setdefault("PLAYBACK_ENTITLEMENT_SECRET", "test-entitlement-secret")
os.environ.setdefault("UI_ACCESS_TOKEN_SECRET", "test-secret")
os.environ.setdefault("DEV_MODE", "1")
import pytest
from fastapi.testclient import TestClient

@pytest.fixture
def client():
    from app.main import create_app
    return TestClient(create_app())

@pytest.fixture
def alice_token():
    from app.services.playback_entitlements import issue_playback_entitlement
    return issue_playback_entitlement(
        tenant_id="tenant-alice",
        asset_id="vid-shared",
        session_id="sess-a",
        device_id="dev-a",
        profile="auto",
        audience="playback",
        ttl_seconds=120,
    )["token"]

def test_tenant_mismatch_returns_403(client, alice_token):
    """Token is for alice but request supplies tenant=bob → 403."""
    from app.services.vod_drm_keys import derive_key_id
    # After GAP-0372 fix, key_id is tenant-scoped; use alice's key_id
    key_id = derive_key_id("vid-shared", tenant_id="tenant-alice")
    # Request key for bob's tenant using alice's token
    resp = client.get(
        f"/v1/vod/drm/key/{key_id}?asset=vid-shared&tenant=tenant-bob&token={alice_token}"
    )
    assert resp.status_code == 403, (
        f"Expected 403 on tenant mismatch, got {resp.status_code}. "
        "GAP-0373 not fixed: tenant_id not validated at key serve time."
    )
    assert resp.json()["detail"]["code"] == "tenant_mismatch"

def test_correct_tenant_returns_200(client, alice_token):
    """Token for alice with tenant=alice → 200."""
    from app.services.vod_drm_keys import derive_key_id
    key_id = derive_key_id("vid-shared", tenant_id="tenant-alice")
    resp = client.get(
        f"/v1/vod/drm/key/{key_id}?asset=vid-shared&tenant=tenant-alice&token={alice_token}"
    )
    assert resp.status_code == 200
    assert len(resp.content) == 16

def test_missing_tenant_param_returns_422(client, alice_token):
    """No tenant param → FastAPI 422 (required param missing)."""
    from app.services.vod_drm_keys import derive_key_id
    key_id = derive_key_id("vid-shared", tenant_id="tenant-alice")
    resp = client.get(
        f"/v1/vod/drm/key/{key_id}?asset=vid-shared&token={alice_token}"
    )
    assert resp.status_code == 422
```

The `test_tenant_mismatch_returns_403` test **fails on the current codebase** because the
endpoint returns 200 regardless of any `tenant` parameter (it is not even declared as a
query param, so it is silently ignored).

### Manual QA steps

1. Issue a token for `(tenant=alice, asset=vid_001)`.
2. Request `GET /v1/vod/drm/key/<key_id>?asset=vid_001&tenant=bob&token=<alice_token>`.
3. Confirm response is `403 {"code": "tenant_mismatch"}`.
4. Request with `tenant=alice` → confirm `200 <16 bytes>`.
5. Request without `tenant` param → confirm `422`.

### Metrics / observability

Add counters:
- `vod_drm_key_tenant_mismatch_total` — incremented on 403 tenant_mismatch. Alert if
  non-zero burst (indicates active probing).
- `vod_drm_key_missing_tenant_claim_total` — incremented when the JWT has no
  `tenant_id` claim (should be 0 for all tokens issued after current code; non-zero
  indicates legacy tokens or token forgery attempts).

### Rollout

- **Effort**: S (< 1 engineer-day for the router change alone; M together with
  GAP-0372 for the combined migration)
- **Risk**: Medium. Adding a required `tenant` query parameter is a breaking change for
  existing HLS manifests embedded in cached playlists or CDN-cached player pages. Plan:
  (a) deploy with `tenant` as optional, logging a warning when absent; (b) after 24 h
  confirm all manifests include the param; (c) make it required.
- **Sequencing**: Must ship in the **same release as GAP-0372**. Neither fix is complete
  without the other. Tag the combined PR as `security/drm-tenant-isolation`.
- **Rollback**: Revert the `tenant` query parameter addition and the claim comparison
  block. No data migrations to reverse.
