# GAP-0131: Expired invite not checked in `accept_guest_invite()` — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. Build on the
> investigation doc (docs/tickets/gap-tickets/investigations/GAP-0131.md) if it exists.

## 1. Summary & Classification

**Bug statement**: The `accept_guest_invite()` service function in the broadcast co-streaming flow
validates that an invite is not already `accepted`, `expired`, or `revoked` (via status-field check),
but additionally performs a timestamp-based expiry guard against invites that are still technically
`pending` yet whose `expires_at` wall-clock time has already passed.

**Claim accuracy**: The original GAP ticket states "only `status == 'pending'` checked; expired
invites in pending state can still be accepted if cleanup sweep hasn't run." After reading the actual
production code at `app/services/broadcast_input_store.py:244–266`, this claim is **incorrect as
filed**. The expiry timestamp check IS already present in the current codebase:

```python
# broadcast_input_store.py:257-260
ts = now_ts()
if invite.expires_at and invite.expires_at < ts:
    _update_invite_status(session_id, invite_id, "expired")
    raise HTTPException(status_code=410, detail="Invite has expired.")
```

The function (a) first rejects invites whose `status` field is already `"expired"` or `"revoked"`
(lines 253–255), then (b) performs a real-time timestamp check that also auto-transitions the
record to `"expired"` status before raising 410. The gap described — where the cleanup sweep's
absence would allow acceptance — does not exist in the as-built code.

**Verdict**: Claim corrected. The fix recommended in the GAP ticket has already been applied; no
product code change is needed.

- **Severity**: HIGH (as originally filed)
- **Source ticket**: BCAST-016
- **Status**: Resolved in code (no action required)
- **Owning area**: Broadcast / co-streaming input management
- **Related tickets**: BCAST-016, SECOPS-007

## 2. Current-State Investigation (root cause)

### Code path

The accept flow begins at:

```
POST /ui/sessions/{session_id}/guest-invites/{invite_id}/accept
  → broadcast.py:3939  accept_guest_invite_route()
    → broadcast_input_store.py:244  accept_guest_invite()
      → broadcast_input_store.py:251  get_guest_invite()   # DDB fetch
      → broadcast_input_store.py:252-255  status guard
      → broadcast_input_store.py:256-260  timestamp guard (the fix)
      → broadcast_input_store.py:261-266  _update_invite_fields() writes accept
```

**`broadcast_input_store.py:244–266` (full function)**:

```python
def accept_guest_invite(
    session_id: str,
    invite_id: str,
    *,
    guest_user_id: str,
    guest_display_name: str,
) -> BroadcastGuestInvite:
    invite = get_guest_invite(session_id, invite_id)
    if invite.status == "accepted":
        raise HTTPException(status_code=409, detail="Invite already accepted.")
    if invite.status in ("expired", "revoked"):
        raise HTTPException(status_code=410, detail="Invite is no longer valid.")
    ts = now_ts()
    if invite.expires_at and invite.expires_at < ts:
        # Auto-expire
        _update_invite_status(session_id, invite_id, "expired")
        raise HTTPException(status_code=410, detail="Invite has expired.")
    return _update_invite_fields(session_id, invite_id, {
        "status": "accepted",
        "guest_user_id": guest_user_id,
        "guest_display_name": guest_display_name,
        "accepted_at": ts,
    })
```

### What exists vs. what was claimed missing

| Guard | Status in code |
|---|---|
| Status-field rejection (`accepted`, `expired`, `revoked`) | Present — lines 252–255 |
| Real-time timestamp check (`expires_at < now_ts()`) | Present — lines 257–260 |
| Auto-transition to `"expired"` on stale record | Present — line 259 |
| 410 HTTP response for expired invite | Present — line 260 |

The companion `expire_pending_invites()` function at `broadcast_input_store.py:273–281` is a bulk
sweep helper callable for cleanup tasks, but the inline guard means the sweep is **not** on the
critical path for correctness. Even if the sweep has never run, a stale `pending` invite with an
elapsed `expires_at` will be rejected by the inline check on every accept attempt.

### Supporting context: `expire_pending_invites()`

`broadcast_input_store.py:273–281` provides a bulk sweep helper:

```python
def expire_pending_invites(session_id: str) -> int:
    invites = list_guest_invites(session_id, status_filter="pending")
    ts = now_ts()
    count = 0
    for inv in invites:
        if inv.expires_at and inv.expires_at < ts:
            _update_invite_status(session_id, inv.invite_id, "expired")
            count += 1
    return count
```

This function exists to proactively mark stale invites before any accept attempt, which reduces
the window in which a stale invite record sits in `pending` state in the database. However, this
sweep is a maintenance optimisation, not a security gate. The inline check in `accept_guest_invite()`
is the authoritative barrier. Whether or not the sweep has ever been called, the inline check
correctly rejects late accept attempts.

### `create_invite` side: when `expires_at` is populated

Looking at the create path (not shown in the ticket), `expires_at` is an optional field set
by the broadcaster when issuing the invite. If left unset (None or 0), the invite is indefinite —
the falsy guard `if invite.expires_at and ...` correctly skips the timestamp check in that case,
allowing perpetual invites to remain valid until explicitly revoked. Creators must opt in to
time-bounded invites.

### When was this fixed?

The gap ticket references a second-pass as-built review of BCAST-016. It appears the inline
timestamp check was included during the original BCAST-016 implementation. The gap audit either
reviewed an intermediate draft or misread the branch of logic that handles `status in ("expired",
"revoked")` as the only guard, overlooking the subsequent timestamp branch at lines 257–260.

## 3. Impact / Exploit / Blast Radius

### If the guard were absent (hypothetical)

A malicious guest-invite recipient who retained an invite link beyond its scheduled expiry window
could:

1. Wait for the `expires_at` timestamp to pass (e.g. a 24-hour invite issued yesterday).
2. POST to `/ui/sessions/{session_id}/guest-invites/{invite_id}/accept` before the background
   sweep marks it `expired`.
3. Receive a valid `BroadcastGuestInvite` with `status=accepted`, gaining co-stream credentials.

This would be an authorization window-bypass: invites are issued with deliberate expiry for access
revocation reasons (e.g. "invite expires in 2 hours" means the creator expects no late joiners).
Accepting a stale invite could violate creator intent and allow unexpected parties to appear in a
live broadcast.

### Actual impact (code as written)

Because the inline check is present, there is no active vulnerability. The blast radius is zero.

### Residual considerations

- **Race condition**: There is a sub-millisecond TOCTOU between `now_ts()` at line 256 and the
  `_update_invite_fields()` write at line 261. In practice, the write occurs within the same
  request, so no concurrent acceptor can exploit this.
- **`expires_at` absence**: When `invite.expires_at` is falsy (None / 0), the timestamp check is
  skipped. This is intentional for indefinite invites. Creators who want time-bounded invites must
  supply `expires_at` when creating the invite.

## 4. Fix Design (code-level)

No product code change is required. The recommended fix from the gap ticket has already been
implemented.

### Recommended hardening (defence in depth)

Although the code is correct, two optional improvements would strengthen the system:

**A. Conditional-expression write (optimistic lock)**

Replace the unconditional `_update_invite_fields()` call with a DynamoDB
`ConditionExpression="attribute_exists(pk) AND #s = :pending AND (attribute_not_exists(expires_at) OR expires_at > :now)"`.
This prevents a race condition where a concurrent request reads `pending` but the record expires
between the read and the write.

**B. Explicit test for `expires_at` == 0**

The current guard `if invite.expires_at and invite.expires_at < ts` treats `expires_at=0` as
falsy (no expiry). This is correct but implicit. A comment or enum sentinel (`NEVER_EXPIRES = 0`)
would clarify intent.

### Dev/Prod parity (SECOPS-007)

The fix path uses `now_ts()` (integer Unix seconds) from `app/core/time.py`. Both dev (DynamoDB
Local) and prod (DynamoDB) evaluate the same `invite.expires_at` field. There is no mock/dev
bypass in `accept_guest_invite()`. Parity is maintained.

def _make_invite(expires_at=None, status="pending"):

class TestAcceptGuestInviteExpiry:

    def test_expired_timestamp_raises_410(self, monkeypatch):

            "sess_test",

            guest_user_id="user_alice",

### Metrics / observability

The auto-transition to `"expired"` at line 259 is silent. Consider adding a
`logger.info("guest_invite_expired_on_accept", ...)` call after `_update_invite_status()` so that
late-accept attempts appear in application logs for creator-support investigations.

Similarly, `expire_pending_invites()` logs nothing on success or failure. Adding a log line such as
`logger.info("guest_invite_bulk_sweep session=%s expired=%d", session_id, count)` would make sweep
activity visible to operators without incurring extra DynamoDB cost.
