## 1. Summary & Classification

**Gap**: The original gap ticket flagged `app/routers/kyc_cases.py:830` as the site where `SCREENING_STORE.screen_case()` should be called on every KYC case submission, and noted that the call was unconfirmed. Code inspection confirms the hook is **absent**: the `submit_kyc_case` endpoint (lines 895–971) performs no call to `SCREENING_STORE.screen_case()` anywhere in its body, and `kyc_cases.py` does not import `app.services.kyc_sanctions_screening` at all.

- **Severity**: HIGH
- **Source ticket**: KYC-006
- **Area**: Backend (KYC submission pipeline)
- **Status**: Confirmed — the claim is accurate. The screening hook is absent. Line 830 (cited in the ticket) is within the `attach_file_to_kyc_case` endpoint, not the `submit_kyc_case` endpoint; neither calls `SCREENING_STORE.screen_case()`.
- **Claim note**: The ticket says "line 830" is where the call should be stitched, but line 830 is actually inside `attach_file_to_kyc_case`. The correct hook site is after `STORE.submit_case()` in `submit_kyc_case` (lines 941–971). The claim is substantively correct (hook absent) but the line citation is off by ~65 lines.
- **Impact**: Every KYC case submission bypasses sanctions/PEP screening entirely unless an admin manually triggers a re-screen. AML regulations require screening at the point of submission, not as a manual afterthought.
- **Related tickets**: KYC-006 (parent feature), GAP-0259 (profile-change re-screening also absent), KYC-008 (risk score uses screening results), SECOPS-007 (dev/prod parity).

## 3. Impact / Exploit / Blast Radius

### 3.1 AML/sanctions bypass at point of submission

Without automatic screening on submission, every user who submits a KYC case bypasses OFAC, PEP, and adverse media checks unless a reviewer manually clicks "Run Screening" from the admin panel. In a production deployment, this means:

- Sanctioned individuals can submit and potentially get approved if reviewers are busy or unaware of the manual screening requirement.
- PEP-identified individuals are not flagged for enhanced due diligence at submission time.
- The `result` field on the case's screening summary remains `None` at the point of review, so the reviewer sees no screening signal when making their approve/reject decision.

### 3.2 Risk score inaccuracy

`app/services/kyc_sanctions_screening.py:_write_case_screening_summary()` (line 357) updates the case's `screening_summary` DDB attribute with the latest result. This summary is consumed by the KYC-008 risk engine. Without a submission-time screen, the risk score used to gate tier upgrades, transaction limits, and compliance reports is computed without sanctions data.

### 3.3 Cascading compliance failures

- Automated compliance reports (KYC analytics, `KycComplianceReportsPage.tsx`) will show zero screening events for submitted cases.
- The `kyc_screening_results` DynamoDB table will remain empty for all cases not manually re-screened, invalidating the `ByStatus` and `ByUserSub` GSIs for any reporting queries.
- In a FATF evaluation or internal audit, the absence of automatic screening would be a Category A finding.

## 4. Fix Design (code-level)

### 4.1 Add the screening call to `submit_kyc_case`

In `app/routers/kyc_cases.py`, add an import at the top of the file (after the existing imports, ~line 65):

```python
from app.services.kyc_sanctions_screening import STORE as SCREENING_STORE
```

Then, in `submit_kyc_case` after line 959 (`updated = _ensure_review_ticket(updated)`), add:

```python
    # KYC-006 / GAP-0258: run sanctions screening on every submission
    try:
        SCREENING_STORE.screen_case(
            case_id=case_id,
            user_sub=user.sub,
            trigger="submission",
        )
    except Exception:
        # Screening failure must NOT block the submission — fail open, log the error.
        import logging
        logging.getLogger(__name__).exception(
            "kyc.screening.submission_hook_failed case_id=%s", case_id
        )
```

The `try/except` is mandatory per the fix specification: screening failure should never rollback a submission. The GAP ticket requirement states "wrapped in try/except so screening failure does not block submission."

### 4.2 Naming and constant

The trigger string `"submission"` matches `TRIGGER_SUBMISSION` defined at `app/services/kyc_sanctions_screening.py` (the constant). Import it explicitly to avoid magic strings:

```python
from app.services.kyc_sanctions_screening import (
    STORE as SCREENING_STORE,
    TRIGGER_SUBMISSION,
)
```

Then use `trigger=TRIGGER_SUBMISSION` in the call.

### 4.3 Idempotency

`_store_result` in `app/services/kyc_sanctions_screening.py:360` writes a new row with `screen_key = f"{screen_type}:{ts}"` where `ts` is `now_ts() + offset`. This means re-submissions of the same case (after `needs_more_info`) will create additional screening rows rather than overwriting existing ones. This is the correct behaviour: each submission event should produce its own screening record for audit purposes. Reviewers see the most recent result.

### 4.4 Dev/Prod parity (SECOPS-007)

The screening store uses DynamoDB Local in dev (SECOPS-007 compliant). The watchlist is in-process and requires no outbound calls. No feature flag or environment-specific code is needed. The `pytest` suite runs offline with moto mocking the DynamoDB table — the test below uses a fake table to keep it fast.

### 4.5 Alternatives considered

- **Run screening asynchronously** (fire-and-forget background task): Considered but rejected for the submission path. The reviewer sees the case immediately in the queue; if screening is async, the reviewer may act before screening completes. Synchronous inline execution ensures results are available at the moment the case appears in the admin queue. The total screening time is in-process (no outbound calls) and completes in milliseconds.
- **Run screening in `STORE.submit_case()` (service layer)**: Rejected. The service layer should not import the screening store — it would create a circular dependency (`kyc_cases.py` already imports `kyc_sanctions_screening` from the same service tree). The router is the correct integration point.
