# GAP-0008: Commission Replay — No Idempotency Guard on put_item — Remediation Write-up

> ~5 pages. Fix-oriented. Grounded in the investigation doc
> (docs/tickets/gap-tickets/investigations/GAP-0008.md) and real code at
> app/services/referrals.py:270–289.

---

## 1. Summary & Classification

**Bug statement.** `record_affiliate_commission()` in `app/services/referrals.py`
writes commission entries to DynamoDB using a sort key of
`COMMISSION#{ts}#{transaction_id}`, where `ts = now_ts()` is the current Unix
wall-clock second. If the same `transaction_id` is submitted at two different
wall-clock seconds — for example, due to a network retry, a webhook redelivery,
or a double-call from a billing event handler — DynamoDB creates two separate
items with different sort keys. Each item is a fully independent commission
record crediting the referrer. There is no `ConditionExpression` on the
`put_item` call to prevent this.

**One-line impact.** A single billing event (purchase, subscription, etc.) can
generate two or more commission ledger entries that are paid out to the
referrer, resulting in fraudulent double (or N-times) platform revenue drain.

**Related tickets.** SEC-013 (financial replay prevention), SEC-004 (billing
idempotency), GAP-0309 (payout balance race condition), GAP-0123 (billing
atomicity gap in write_private_billing).

## 2. Current-State Investigation (root cause)

### Service function (`app/services/referrals.py:270–289`)

The relevant section:

```python
    ts = now_ts()
    now = _now_iso()

    entry: Dict[str, Any] = {
        "pk": f"AFFILIATE#{referrer_id}",
        "sk": f"COMMISSION#{ts}#{transaction_id}",  # ts is wall-clock
        "Entity": "AffiliateCommission",
        "referrer_user_id": referrer_id,
        "referred_user_id": referred_user_id,
        "source_transaction_id": transaction_id,
        "source_type": source_type,
        "gross_amount_cents": gross_amount_cents,
        "net_amount_cents": net_amount,
        "commission_rate_bps": rate_bps,
        "commission_cents": commission_cents,
        "currency": "usd",
        "status": "pending",
        "created_at": now,
    }
    tbl.put_item(Item=entry)   # <-- no ConditionExpression
    return entry
```

The SK `COMMISSION#{ts}#{transaction_id}` embeds two variable components:
`ts` (wall-clock second, always different between retries) and
`transaction_id` (caller-supplied, stable across retries). Because DynamoDB
uses `(pk, sk)` as the composite primary key, two calls with the same
`transaction_id` but different `ts` values produce two physically distinct
items. No `ConditionalCheckFailedException` is raised — both writes succeed.

### The replay window

The caller at `app/routers/referrals.py:140` is on `internal_router`. In dev
mode, `internal_router` requires no session auth. In production, the router
is protected at the network level (not accessible from the public internet)
but accessible from any backend service, Lambda, or webhook handler that can
reach `localhost:8000`. A webhook retry arriving even one second apart opens
the window.

### Equivalent vulnerability in `affiliate_links.py`

`app/services/affiliate_links.py:299` contains a structurally identical
problem: `record_conversion()` uses a random `conv_id` as part of the SK —
`CONV#{conv_id}` — with no `order_id` dedup guard. Two calls with the same
`order_id` create two conversion records and double-increment
`commission_earned_cents` on the link record via an `update_item` accumulator.

### Why the gap exists

The SK was designed as a time-bucketed log key for human readability in the
DynamoDB console. Including `ts` made it sortable by time but inadvertently
removed the idempotency guarantee that comes from a deterministic SK.
No separate dedup sentinel or `ConditionExpression` guard was added when
the billing path was integrated.

### Dev vs prod

DynamoDB Local and production DynamoDB behave identically for `put_item`.
The bug is reproducible in dev by firing the internal endpoint twice within
two different wall-clock seconds with the same `transaction_id`.

## 3. Impact / Exploit / Blast Radius

### Exploit scenario A: network retry

1. A billing event handler calls `POST /internal/referrals/commission` with
   `transaction_id="txn_stripe_pi_1234"`.
2. The first call succeeds; the response times out or the TCP connection is
   dropped before the caller receives the 200.
3. The caller retries at `ts+2` seconds.
4. Both calls succeed. The referrer now has two `COMMISSION#` items totaling
   2× commission_cents.
5. The nightly payout rollup sums all `COMMISSION#` items → double payout.

### Exploit scenario B: webhook redelivery

Stripe, PayPal, and CCBill all retry webhooks on 5xx responses (or on
network errors). If the backend's webhook handler calls
`record_affiliate_commission()` and the response is slow, the webhook
dispatcher may fire a second delivery before the first has persisted.
Both land in separate seconds → two commissions.

### Exploit scenario C: adversarial internal caller

The `/internal/referrals/commission` endpoint is on `internal_router`,
which is unauthenticated in dev mode. Any developer tool, test script, or
compromised internal service can call it twice deliberately. In production
the network boundary provides the only guard.

### Financial worst case

Commission rate is typically 5–15% (500–1500 bps). On a $100 purchase:
`$100 × 10% = $10` commission. With N duplicates, the platform pays out
`$10 × N`. For a high-volume creator with 1,000 referred purchases per day,
a systematic retry bug delivering each purchase twice costs the platform
$10,000/day in fraudulent commission payouts before the next audit.

The bug also corrupts `list_commissions()` reporting — dashboards show
double the actual referral activity, making detection harder.

## 4. Fix Design (code-level)

Two options are documented. Option A (recommended) is simpler and safer.

### Option A (recommended): deterministic SK + ConditionExpression

Drop `ts` from the sort key. Use `transaction_id` alone as the SK
discriminator. Add a `ConditionExpression` to reject duplicate writes.

**Change in `app/services/referrals.py:270–289`:**

```python
    entry: Dict[str, Any] = {
        "pk": f"AFFILIATE#{referrer_id}",
        "sk": f"COMMISSION#{transaction_id}",   # deterministic — ts removed
        "Entity": "AffiliateCommission",
        "referrer_user_id": referrer_id,
        "referred_user_id": referred_user_id,
        "source_transaction_id": transaction_id,
        "source_type": source_type,
        "gross_amount_cents": gross_amount_cents,
        "net_amount_cents": net_amount,
        "commission_rate_bps": rate_bps,
        "commission_cents": commission_cents,
        "currency": "usd",
        "status": "pending",
        "created_at": _now_iso(),
    }
    try:
        tbl.put_item(
            Item=entry,
            ConditionExpression="attribute_not_exists(pk) AND attribute_not_exists(sk)",
        )
    except tbl.meta.client.exceptions.ConditionalCheckFailedException:
        logger.info(
            "commission_duplicate_ignored referrer=%s transaction_id=%s",
            referrer_id, transaction_id,
        )
        return None   # caller must handle None = already recorded
    return entry
```

The `ConditionExpression="attribute_not_exists(pk) AND attribute_not_exists(sk)"`
check is atomic in DynamoDB — only one of two concurrent writes with the same
`(pk, sk)` can succeed. The other receives `ConditionalCheckFailedException`,
which is caught and swallowed as a successful deduplication.

**Update callers** of `record_affiliate_commission()` to handle `None` return
(treat as success — commission already recorded).

### Option B: dedup sentinel (preserves ts in SK for audit trail)

If preserving the time-ordered SK for audit is required, write a separate
sentinel record first:

```python
    sentinel = {
        "pk": f"AFFILIATE#{referrer_id}",
        "sk": f"COMMISSION_DEDUP#{transaction_id}",
        "created_at": _now_iso(),
    }
    try:
        tbl.put_item(
            Item=sentinel,
            ConditionExpression="attribute_not_exists(pk)",
        )
    except tbl.meta.client.exceptions.ConditionalCheckFailedException:
        logger.info("commission_duplicate_ignored transaction_id=%s", transaction_id)
        return None
    # Sentinel written — now safe to write the timestamped commission entry
    ts = now_ts()
    entry = {
        "pk": f"AFFILIATE#{referrer_id}",
        "sk": f"COMMISSION#{ts}#{transaction_id}",
        ...
    }
    tbl.put_item(Item=entry)
```

Option B requires an extra write per commission but preserves the existing SK
schema for any existing data or queries that depend on the time-ordered key
format. Prefer Option A for new deployments where no existing production data
relies on the timestamp-in-SK format.

### Same fix for `affiliate_links.record_conversion()`

`app/services/affiliate_links.py:299` — change the SK from
`CONV#{random_conv_id}` to `CONV#{order_id}` (or `CONV#{transaction_id}`)
and add `ConditionExpression="attribute_not_exists(pk)"` to the `put_item`.
Simultaneously, guard the `update_item` accumulator for
`commission_earned_cents` with an idempotency check (read-first-or-increment-
with-dedup).

### Dev/Prod parity (SECOPS-007)

`put_item` with `ConditionExpression` is a standard DynamoDB API feature
available in both DynamoDB Local and production. No AWS-specific code path is
introduced. The `ConditionalCheckFailedException` is raised identically in
both environments. No schema migration is needed for Option A (the SK format
changes, but existing records are simply not matched by new queries that use
the new format — they remain in DDB as historical data under the old SK).

## 5. Testing, Verification & Rollout

### Regression test (fails before fix, passes after)

**`tests/test_referrals.py`** (pytest offline, moto DynamoDB):

```python
import pytest
from app.services.referrals import record_affiliate_commission


@pytest.fixture
def referral_setup(ddb_tables, seed_attribution):
    """seed_attribution creates an affiliate link and referral record for alice→bob."""
    return {"referrer_id": "alice", "referred_user_id": "bob"}


def test_commission_not_replayed(referral_setup, ddb_tables):
    """FAILS before fix (two DDB items written), PASSES after (second is None)."""
    kwargs = dict(
        referred_user_id=referral_setup["referred_user_id"],
        transaction_id="txn_stripe_pi_9999",
        source_type="purchase",
        gross_amount_cents=1000,
    )
    result1 = record_affiliate_commission(**kwargs)
    result2 = record_affiliate_commission(**kwargs)

    assert result1 is not None, "First write must succeed"
    assert result1["commission_cents"] > 0

    # Before fix: result2 is a new entry (second commission written).
    # After fix:  result2 is None (duplicate suppressed).
    assert result2 is None, "Duplicate transaction must be suppressed"

    # Assert: exactly one commission entry exists in DDB
    from app.core.tables import T
    resp = T.referrals.query(
        KeyConditionExpression="pk = :pk AND begins_with(sk, :prefix)",
        ExpressionAttributeValues={
            ":pk": "AFFILIATE#alice",
            ":prefix": "COMMISSION#",
        },
    )
    commission_items = resp.get("Items", [])
    assert len(commission_items) == 1, (
        f"Expected 1 commission item, got {len(commission_items)}"
    )


def test_distinct_transactions_both_written(referral_setup, ddb_tables):
    """Different transaction_ids must each produce a commission record."""
    r1 = record_affiliate_commission(
        referred_user_id=referral_setup["referred_user_id"],
        transaction_id="txn_a",
        source_type="purchase",
        gross_amount_cents=500,
    )
    r2 = record_affiliate_commission(
        referred_user_id=referral_setup["referred_user_id"],
        transaction_id="txn_b",
        source_type="purchase",
        gross_amount_cents=500,
    )
    assert r1 is not None
    assert r2 is not None

    from app.core.tables import T
    resp = T.referrals.query(
        KeyConditionExpression="pk = :pk AND begins_with(sk, :prefix)",
        ExpressionAttributeValues={
            ":pk": "AFFILIATE#alice",
            ":prefix": "COMMISSION#",
        },
    )
    assert len(resp.get("Items", [])) == 2
```

### Manual QA steps

1. `just up` — start dev stack.
2. In the DynamoDB local console (`localhost:8001`), observe the referrals table.
3. Fire `POST /internal/referrals/commission` twice with the same
   `transaction_id` from a terminal — first at T=0, second at T=2 seconds.
4. Before fix: two `COMMISSION#...` items with different SKs appear.
5. After fix: second call returns `null` body; only one item in DDB.

### Schema migration for existing data

Option A changes the SK format for new records. Existing records in production
with `COMMISSION#{ts}#{transaction_id}` SKs are untouched and remain valid
historical entries. No migration script is needed. Any rollup query that uses
`begins_with(sk, "COMMISSION#")` continues to match both old-format and
new-format records. Verify that payout rollup queries (`list_commissions`)
are SK-prefix-based (they are — `begins_with(sk, "COMMISSION#")`) so both
old and new entries are summed correctly.

If a production audit reveals duplicate commission entries created before this
fix, a one-time cleanup script can identify duplicates by grouping on
`source_transaction_id` and deleting all but one entry per `(referrer_id,
transaction_id)` pair. This script should be run under a maintenance window
with the `POST /internal/referrals/commission` endpoint disabled temporarily.

### Rollout precaution for high-volume referrers

For referrers with large commission histories (thousands of entries), the
SK change is transparent because queries use `begins_with`. However, if any
frontend or analytics pipeline constructs SK patterns like
`COMMISSION#{ts}#` (time-bucketed prefix), those queries will stop matching
new records after the fix. Audit all `KeyConditionExpression` patterns in
`list_commissions()` and related analytics queries before deploying.

### Metrics / observability

Log `commission_duplicate_ignored` at INFO level (done in the fix above).
Monitor `commission_duplicate_ignored_count` — a spike indicates a webhook
retry storm or a misconfigured billing event handler.

### Rollback

The `ConditionExpression` addition is a pure addition with no breaking
schema change. Rollback means removing the `ConditionExpression` and
restoring the `ts`-prefixed SK. No DDB schema changes are required in
either direction.

### Risks

- **Concurrent writes in the same second:** Option A is safe — DynamoDB's
  conditional write is atomic. The loser gets `ConditionalCheckFailedException`.
- **Callers that depend on non-None return:** Any caller that unconditionally
  uses `record_affiliate_commission()` return value must be audited to handle
  `None`. In practice the internal router (`routers/referrals.py:140`) only
  returns a 200 body, so `None` just means the response body is `null` —
  harmless.
- **`affiliate_links.py` scope:** This ticket's fix covers `referrals.py`.
  A follow-on ticket should apply the identical guard to
  `affiliate_links.record_conversion()`.

  const body = {

  const r2 = await request.post("/internal/referrals/commission", { data: body });
