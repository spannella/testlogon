# GAP-0330: Auto-revoke fires on ALL web_push_send failures, not only 410 Gone — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing; cites `file:line`.

## 1. Summary & Classification

**Severity**: HIGH
**Source ticket**: PLATFORM-016
**Owning area**: Push notification delivery / device management
**Status**: Open — duplicate root cause confirmed; partially overlaps GAP-0328

**Plain-English statement**: `send_push_for_alert()` in `app/services/push.py` revokes a user's push device subscription whenever `web_push_send()` returns `False`. The function `web_push_send()` returns `False` for every type of delivery failure: HTTP 410 Gone (subscription permanently revoked by the browser), HTTP 404 Not Found (endpoint no longer exists), network timeouts, push-service 500 errors, and push-service 429 rate-limit responses. Only 410 and 404 indicate that the subscription is permanently invalid. The other failure types are transient; the subscription is still valid and should be retried at the next notification. Because the revoke fires on all `False` returns, a transient push-service outage silently deletes all registered web-push devices for every user who receives an alert during the outage window.

**Verdict**: Claim confirmed. The condition at `app/services/push.py:300` reads `if not success and not S.dev_mode`, where `success` is a `bool`. `web_push_send()` returns `False` for all failure categories (lines 221–235), with no signal distinguishing permanent from transient failures.

**Relationship to GAP-0328**: GAP-0328 (source: PLATFORM-010) and GAP-0330 (source: PLATFORM-016) describe the same root-cause defect from two separate audit passes. Both are resolved by the same code change. This write-up provides the PLATFORM-016 perspective and additional detail on the failure classification taxonomy; the fix section cross-references and expands on the design in GAP-0328.

**Related tickets**: GAP-0328 (same bug, different audit source), PLATFORM-016, PLATFORM-010.

## 2. Current-State Investigation (root cause)

### `web_push_send()` return type — uniform `False` for all failures

`app/services/push.py:142–235` is the complete web-push delivery function. It returns a plain `bool`. The exit paths that return `False` are:

**Path A** — non-2xx HTTP status code (`push.py:220–222`):
```python
else:
    logger.warning("Web push failed: status=%s, endpoint=%s", status, endpoint[:80])
    return False
```
This is reached when pywebpush completes without raising an exception but returns a status code outside 200/201/202. This includes:
- 400 Bad Request (malformed payload or headers)
- 429 Too Many Requests (push service rate-limiting the platform)
- 500/503 Internal Server Error (push service degraded)
- 410 Gone (caught as a non-exception in some pywebpush versions)
- 404 Not Found (same)

**Path B** — `WebPushException` or other exception with "410" / "Gone" substring (`push.py:227–229`):
```python
if "410" in exc_str or "Gone" in exc_str:
    logger.info("Web push subscription expired (410): endpoint=%s", endpoint[:80])
    return False  # Caller should revoke device
```

**Path C** — `WebPushException` with "404" (`push.py:231–233`):
```python
if "404" in exc_str:
    logger.info("Web push subscription not found (404): endpoint=%s", endpoint[:80])
    return False
```

**Path D** — any other exception (`push.py:234–235`):
```python
logger.exception("Web push send error: endpoint=%s", endpoint[:80])
return False
```

Path D is the widest catch: it handles `requests.Timeout`, `requests.ConnectionError`, `ssl.SSLError`, `OSError`, and any other low-level exception from the network stack. None of these indicate that the subscription is permanently invalid; they all indicate that the current delivery attempt failed.

### The revocation decision in `send_push_for_alert()`

`app/services/push.py:293–312`:

```python
success = web_push_send(tok, title, body, ...)
if not success and not S.dev_mode:
    try:
        sub = json.loads(tok)
        if "endpoint" in sub:
            revoke_push_device(user_sub, device_id)
```

The only guard other than `not S.dev_mode` is that `tok` must parse as JSON with an `"endpoint"` key. For every legitimately registered web-push subscription, this condition is always `True` (the subscription JSON always contains `endpoint`, `keys.p256dh`, and `keys.auth`). There is no check for whether the failure was permanent.

### Failure taxonomy not implemented

The Web Push specification (RFC 8030 §8.3) states:
- **410 Gone**: "The subscription has expired or has been unsubscribed." The push service MAY return 410 to indicate that the subscription resource has been removed. The application server SHOULD NOT attempt to send to this endpoint again.
- **404 Not Found**: The push resource does not exist. Same implication.
- All other 4xx and 5xx codes: transient or client-error (malformed payload). The push service may accept future attempts.

The current code comments correctly identify 410 as the staleness signal (`# Caller should revoke device`), but the `bool` return type prevents the caller from acting on that identification.

### Scope of devices affected

`send_push_for_alert()` iterates over the first 25 push devices per user (`push.py:284`). In a push-service outage scenario where 1,000 users receive alerts per minute, up to 25,000 device revocations can occur per minute. Recovery requires every affected user to re-enable push notifications manually in their browser — a process many users will not know to do, resulting in a permanent degradation of push notification reach.

## 3. Impact / Exploit / Blast Radius

**Primary impact — silent mass device revocation**: During any transient push-service failure lasting more than a few seconds, all web-push subscriptions for users receiving alerts are permanently deleted. This is a one-way operation; revoked subscriptions cannot be restored server-side.

**Cascade impact on security alerting**: Push notifications are the primary out-of-band channel for security events (login from new device, MFA failure, access denied). Silently disabling push notifications for a user during a brief outage removes this security channel precisely when an attacker might initiate an account-takeover attempt (timing the attack to coincide with a push-service degradation).

**Quantified worst case**: Assume a platform with 50,000 active users, 30% with web-push subscriptions (15,000 users). A 5-minute push-service outage that affects all delivers results in:
- Up to 15,000 users losing all web-push devices (if each receives at least one alert during the window)
- Re-opt-in rate based on industry data: 20–40% of users will not re-enable push, resulting in permanent 60–80% reduction in push notification reach post-outage.

**Exploitability**: A malicious actor who can induce a brief push-service failure (e.g., by exploiting the push provider's rate limits via the platform's own send volume) can cause mass device revocation during a targeted window. This is a moderate-sophistication attack that yields persistent reduction in security notification reach.

## 4. Fix Design (code-level)

This section provides the complete, standalone fix. It is identical to the fix described in GAP-0328 but presented from the PLATFORM-016 audit perspective.

### 4.1 Replace `bool` return type with a three-state enum

Add to `app/services/push.py` after imports:

```python
from enum import Enum

class WebPushResult(str, Enum):
    """Typed result for web_push_send(), distinguishing permanent from transient failures."""
    OK        = "ok"         # Successfully delivered
    STALE     = "stale"      # 410 Gone or 404 Not Found — revoke subscription
    TRANSIENT = "transient"  # Network error, 429, 5xx — leave subscription intact
```

### 4.2 Updated `web_push_send()` with typed exit paths

**Dev mode** (`push.py:192`): return `WebPushResult.OK` (unchanged logic, updated type).

**Success path** (`push.py:217–219`): `return WebPushResult.OK`

**Non-2xx status path** (`push.py:220–222`): split by status code:
```python
elif status in (404, 410):
    logger.info("Web push permanent failure: status=%s, endpoint=%s",
                status, endpoint[:80])
    return WebPushResult.STALE
else:
    logger.warning("Web push transient failure: status=%s, endpoint=%s",
                   status, endpoint[:80])
    return WebPushResult.TRANSIENT
```

**Exception path B — 410** (`push.py:227–229`): `return WebPushResult.STALE`

**Exception path C — 404** (`push.py:231–233`): `return WebPushResult.STALE`

**Exception path D — other** (`push.py:234–235`): `return WebPushResult.TRANSIENT`

### 4.3 Updated `send_push_for_alert()` revocation guard

Replace `if not success and not S.dev_mode:` (`push.py:300`) with:

```python
if result == WebPushResult.STALE and not S.dev_mode:
    # Permanent failure confirmed (410/404): revoke subscription.
    try:
        sub = json.loads(tok)
        if "endpoint" in sub:
            revoke_push_device(user_sub, device_id)
            logger.info(
                "Auto-revoked stale push device: user=%s, device=%s",
                user_sub, device_id,
            )
    except (json.JSONDecodeError, TypeError):
        pass
elif result == WebPushResult.TRANSIENT:
    # Transient failure: subscription remains valid; log but do NOT revoke.
    logger.warning(
        "Transient push delivery failure (subscription retained): "
        "user=%s, device=%s",
        user_sub, device_id,
    )
```

### 4.4 Optional: retry queue for `TRANSIENT` failures

The fix above prevents incorrect revocation but does not retry failed deliveries. A follow-up improvement is to enqueue `TRANSIENT` failures for retry (e.g., via an SQS FIFO queue or a DynamoDB-backed retry table) with exponential back-off. This is out of scope for this gap but is the natural next step. The `WebPushResult.TRANSIENT` return value provides the hook needed for the retry logic.

### 4.5 Dev/Prod parity (SECOPS-007)

- `WebPushResult` is a pure Python enum with no AWS dependency.
- `web_push_send()` in dev mode returns `WebPushResult.OK` immediately (short-circuits at `S.dev_mode` check, `push.py:192`), exactly as it returned `True` before. No behaviour change in dev mode.
- `send_push_for_alert()` in dev mode: the guard `and not S.dev_mode` is retained verbatim in the updated code, so revocation never fires in dev mode regardless of `WebPushResult` value. This is the correct parity: dev mode uses placeholder VAPID keys that will always fail pywebpush delivery; suppressing revocation prevents dev-mode test runs from deleting seeded push devices.
- All paths in the updated function use the same DynamoDB table (`T.push_devices`) in both dev and prod.

## 5. Testing, Verification & Rollout

### Regression test (pytest offline)

Add to `tests/test_push.py` (supplementing the GAP-0328 test class with PLATFORM-016-specific scenarios):

```python
import pytest
import json
from unittest.mock import MagicMock, patch
from app.services.push import WebPushResult, web_push_send, send_push_for_alert


SUB_JSON = json.dumps({
    "endpoint": "https://push.googleapis.com/fcm/send/abc123",
    "keys": {"p256dh": "BKEY", "auth": "AUTH"},
})


class TestWebPushResultTypes:
    """GAP-0330 / PLATFORM-016: all transient errors must return TRANSIENT not STALE."""

    def _patch_env(self, mocker):
        return mocker.patch("app.services.push.S", dev_mode=False,
                            vapid_private_key="key", vapid_public_key="pub",
                            vapid_subject="mailto:a@b.com")

    def test_timeout_is_transient(self, mocker):
        """Requests timeout must map to TRANSIENT."""
        self._patch_env(mocker)
        import requests
        mocker.patch("app.services.push.webpush",
                     side_effect=requests.Timeout("timed out"))
        result = web_push_send(SUB_JSON, "T", "B")
        assert result == WebPushResult.TRANSIENT

    def test_connection_error_is_transient(self, mocker):
        """Network ConnectionError must map to TRANSIENT."""
        self._patch_env(mocker)
        import requests
        mocker.patch("app.services.push.webpush",
                     side_effect=requests.ConnectionError("refused"))
        result = web_push_send(SUB_JSON, "T", "B")
        assert result == WebPushResult.TRANSIENT

    def test_500_is_transient(self, mocker):
        """5xx HTTP response from push service must map to TRANSIENT."""
        self._patch_env(mocker)
        mock_resp = MagicMock()
        mock_resp.status_code = 503
        mocker.patch("app.services.push.webpush", return_value=mock_resp)
        result = web_push_send(SUB_JSON, "T", "B")
        assert result == WebPushResult.TRANSIENT

    def test_429_is_transient(self, mocker):
        """429 Too Many Requests must map to TRANSIENT (not revoke the subscription)."""
        self._patch_env(mocker)
        mock_resp = MagicMock()
        mock_resp.status_code = 429
        mocker.patch("app.services.push.webpush", return_value=mock_resp)
        result = web_push_send(SUB_JSON, "T", "B")
        assert result == WebPushResult.TRANSIENT

    def test_410_is_stale(self, mocker):
        """410 Gone must map to STALE."""
        self._patch_env(mocker)
        mocker.patch("app.services.push.webpush",
                     side_effect=Exception("Response status 410 Gone"))
        result = web_push_send(SUB_JSON, "T", "B")
        assert result == WebPushResult.STALE

    def test_410_status_code_is_stale(self, mocker):
        """410 returned as HTTP status (not exception) must map to STALE."""
        self._patch_env(mocker)
        mock_resp = MagicMock()
        mock_resp.status_code = 410
        mocker.patch("app.services.push.webpush", return_value=mock_resp)
        result = web_push_send(SUB_JSON, "T", "B")
        assert result == WebPushResult.STALE

    def test_transient_does_not_revoke(self, mocker):
        """FAILS before fix: transient failure calls revoke_push_device.
           PASSES after fix: revoke_push_device is NOT called."""
        mocker.patch("app.services.push.S",
                     dev_mode=False, push_enabled=True,
                     web_push_enabled=True, fcm_enabled=False,
                     vapid_private_key="k", vapid_public_key="p")
        mocker.patch("app.services.push.get_alert_prefs",
                     return_value={"push_event_types": ["new_message"]})
        mocker.patch("app.services.push.can_send_alert_channel", return_value=True)
        mocker.patch("app.services.push.T").push_devices.query.return_value = {
            "Items": [{"token": SUB_JSON, "device_id": "dev_xyz", "platform": "web"}]
        }
        revoke_mock = mocker.patch("app.services.push.revoke_push_device")
        mocker.patch("app.services.push.web_push_send",
                     return_value=WebPushResult.TRANSIENT)

        send_push_for_alert("user_abc", "new_message", "New msg", "Bob said hi", "a1")

        # BEFORE fix: revoke called once → AssertionError
        # AFTER fix:  revoke not called → passes
        revoke_mock.assert_not_called()

    def test_stale_does_revoke(self, mocker):
        """410 STALE result must still revoke the device after the fix."""
        mocker.patch("app.services.push.S",
                     dev_mode=False, push_enabled=True,
                     web_push_enabled=True, fcm_enabled=False,
                     vapid_private_key="k", vapid_public_key="p")
        mocker.patch("app.services.push.get_alert_prefs",
                     return_value={"push_event_types": ["new_message"]})
        mocker.patch("app.services.push.can_send_alert_channel", return_value=True)
        mocker.patch("app.services.push.T").push_devices.query.return_value = {
            "Items": [{"token": SUB_JSON, "device_id": "dev_xyz", "platform": "web"}]
        }
        revoke_mock = mocker.patch("app.services.push.revoke_push_device")
        mocker.patch("app.services.push.web_push_send",
                     return_value=WebPushResult.STALE)

        send_push_for_alert("user_abc", "new_message", "New msg", "Bob said hi", "a1")

        revoke_mock.assert_called_once_with("user_abc", "dev_xyz")
```

**Test count**: 8 tests.
**Fails before fix**: `test_transient_does_not_revoke`, `test_timeout_is_transient`, `test_connection_error_is_transient`, `test_500_is_transient`, `test_429_is_transient` — all return incorrect `bool` type or trigger incorrect revocation.

### Observability and alerting

Add to `app/metrics.py`:

```python
WEB_PUSH_RESULT = Counter(
    "web_push_result_total",
    "Web push delivery outcomes by result type",
    ["result"],  # ok / stale / transient
)
```

Increment in `send_push_for_alert()` after the `result` is obtained:
```python
from app.metrics import WEB_PUSH_RESULT
WEB_PUSH_RESULT.labels(result=result.value).inc()
```

Alert rules:
- `rate(web_push_result_total{result="transient"}[5m]) > 10` → PagerDuty P2 (push service degraded)
- `rate(web_push_result_total{result="stale"}[5m]) > 50` → PagerDuty P3 (unusual volume of stale subscriptions, possibly a browser update wave)

The `transient` counter trending upward without a corresponding `stale` spike is the clearest signal that a push service outage is in progress, and with the fix in place, it no longer implies mass device revocation.

### Rollout

- **Effort**: S (small — same file, ~20 lines changed, no schema changes)
- **Risk**: Minimal. Only behavior that changes is: transient failures no longer revoke devices. This is strictly safer for users. Permanent failures (410/404) continue to revoke exactly as before.
- **Coordination with GAP-0328**: Both tickets require the same change. A single PR should close both. The PR title should reference both GAP-0328 and GAP-0330.
- **Rollback**: Revert the `WebPushResult` enum and restore `if not success and not S.dev_mode`. No DynamoDB or infrastructure changes to reverse.
- **Deployment sequence**: The change is self-contained within `app/services/push.py`. Deploy as a normal backend release. No frontend changes required. No database migration required.
