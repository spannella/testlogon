# GAP-0119: `inventory_segments` Production Path Is a Stub — Remediation Write-up

> ~5 pages. Fix-oriented. Real code verified against the codebase; cite `file:line`.

## 1. Summary & Classification

**Gap**: `inventory_segments` in `app/services/broadcast_recording_worker.py` always returns an empty list, both in mock mode and in the nominal production path. The production branch (lines 55–58) contains only a log statement followed by `return []`. No S3 `ListObjectsV2` call is made, so the downstream concatenation, transcoding, and finalization steps receive an empty segment list and produce zero-duration recordings.

**Severity**: HIGH
**Source ticket**: BCAST-006
**Status**: Open
**Owning area**: `app/services/broadcast_recording_worker.py` → `inventory_segments`
**Related tickets**: GAP-0120 (`concatenate_segments` is also a stub), BCAST-006 (Recording pipeline feature), BCAST-008 (MP4 download depends on the same pipeline)

**Verdict**: Claim confirmed. `app/services/broadcast_recording_worker.py:45–58` — both the mock path (line 53, `return []`) and the production path (line 58, `return []`) are stubs. No S3 pagination is implemented.

**One-line impact**: All broadcast recordings complete with `segment_count=0`, `duration_seconds=0`, and an empty HLS manifest — the recording is a valid DynamoDB record with status `ready` but no actual video content.


## 2. Current-State Investigation (root cause)

### Current implementation

`app/services/broadcast_recording_worker.py:45–58`:

```python
def inventory_segments(recording: RecordingRecord) -> List[str]:
    """List .ts segment files from the archive prefix.

    In mock mode, returns an empty list (no real segments).
    In production, would list S3 objects under s3_archive_prefix.
    """
    if _should_mock():
        logger.info("Recording %s: mock inventory (no segments)", recording.recording_id)
        return []

    # Production: list S3 objects under the archive prefix
    # For now in dev, return empty since no real segments exist
    logger.info("Recording %s: inventorying segments at %s", recording.recording_id, recording.s3_archive_prefix)
    return []         # <-- stub: always empty
```

The comment "For now in dev, return empty since no real segments exist" reveals that this was left as an intentional placeholder. No S3 client is imported; no `list_objects_v2` paginator is called.

### What `_should_mock()` returns

```python
def _should_mock() -> bool:
    if S.broadcast_recording_mock_on_no_ffmpeg and not _ffmpeg_available():
        return True
    return False
```

`S.broadcast_recording_mock_on_no_ffmpeg` defaults to `True` (line 1454 of `app/core/settings.py`). In dev mode FFmpeg is typically absent, so `_should_mock()` returns `True` and the mock `return []` branch fires. In a production environment where FFmpeg is installed, `_should_mock()` returns `False` and the production stub branch fires — also returning `[]`.

### Downstream cascade

`process_recording` at line 212–216:

```python
segments = inventory_segments(recording)          # always []
concat_path = concatenate_segments(recording, segments)   # segments is empty → returns None
transcode_result = transcode_recording(recording, concat_path)   # concat_path=None → mock metadata
```

With `segments=[]`:

1. `concatenate_segments` short-circuits at `if _should_mock() or not segments: return None` (line 66).
2. `transcode_recording` short-circuits at `if _should_mock() or concat_path is None:` returning mock metadata: `{"renditions": [...], "duration_seconds": 0, "total_bytes": 0}` (lines 81–89).
3. `generate_mp4` short-circuits similarly, producing a placeholder key with `mp4_size_bytes=0`.
4. `finalize_recording` writes status `ready` with `duration_seconds=0` and `segment_count=0`.

The recording is marked `ready` but is entirely empty.

### S3 infrastructure already in place

The infrastructure needed for a real implementation exists:

- `S.broadcast_recording_vod_bucket` (line 1450 of `app/core/settings.py`): the S3 bucket name, defaulting to `"broadcast-vod"`.
- `recording.s3_archive_prefix` (dataclass field, line 29 of `broadcast_recording.py`): the object key prefix under which the HLS ingest pipeline deposits `.ts` segment files. Set during session stop/recording creation.
- `app/core/aws_clients.py:114` — `s3_client()` factory that honours dev-mode moto patching. In dev mode, `_s3_endpoint_url()` returns `None` (line 81), meaning boto3 uses the standard HTTP layer which moto intercepts transparently.
- `app/core/dev_s3.py` — moto in-process S3 mock, started at app startup. The `broadcast-vod` bucket is pre-created if listed in the startup bucket list.
- `S.broadcast_recording_max_segments` (line 1452): upper bound on the number of segments to inventory (default 10000), preventing memory exhaustion from large sessions.

The only missing piece is the S3 pagination loop that maps these existing settings to actual API calls.

### Why `list_objects_v2` pagination is essential

A single `list_objects_v2` call returns at most 1000 objects. A long broadcast at 4-second HLS segment intervals runs 900 segments per hour. A 3-hour session produces ~2700 segments — three times the single-page limit. Without pagination the inventory is silently truncated to the first 1000 segments, producing a recording that covers only the first ~67 minutes. The fix must use `get_paginator("list_objects_v2")` which transparently handles continuation tokens.


## 3. Impact / Exploit / Blast Radius

### Functional impact

- Every production recording (and dev recording when `BROADCAST_RECORDING_MOCK_ON_NO_FFMPEG=0`) completes as a zero-duration, zero-byte MP4 shell.
- Viewers who attempt to play back a recording via `GET /broadcast/sessions/{id}/recording` receive a presigned URL that points to a non-existent or empty manifest.
- The `allow_download` and `allow_viewer_download` flags (BCAST-008) are set to `True` by default but the downloadable MP4 has `mp4_size_bytes=0`.

### Financial impact

- Broadcasters have paid for (or are owed) recorded content. Delivering zero-byte recordings is a service-level failure that may trigger refunds, chargebacks, or SLA penalties.
- Tip totals, viewer counts, and chat logs are correctly recorded, but without the video the recorded session has no playback value.

### Blast radius

All broadcast sessions for which the recording pipeline runs. In dev mode the mock path fires regardless, so local testing always produces empty recordings. In production (FFmpeg present, `BROADCAST_RECORDING_MOCK_ON_NO_FFMPEG=0`), the production stub fires and the outcome is the same.


## 4. Fix Design (code-level)

### Implementation of `inventory_segments`

Replace the stub production path with a paginated `list_objects_v2` call. The function should:

1. Validate that `recording.s3_archive_prefix` is non-empty.
2. Use `s3.get_paginator("list_objects_v2")` to enumerate all objects under the prefix.
3. Filter for `.ts` segment files (HLS transport stream segments).
4. Sort the keys lexicographically (HLS segment filenames are typically zero-padded sequence numbers; lexicographic order matches chronological order).
5. Respect `S.broadcast_recording_max_segments` as an upper bound.
6. Return the list of S3 keys (not signed URLs — the downstream FFmpeg call will use the keys with the bucket name).

**File**: `app/services/broadcast_recording_worker.py`, function `inventory_segments` (line 45).

```python
def inventory_segments(recording: RecordingRecord) -> List[str]:
    """List .ts segment files from the archive prefix in S3.

    In mock mode (no FFmpeg), returns an empty list.
    In production, paginates ListObjectsV2 under s3_archive_prefix.
    """
    if _should_mock():
        logger.info("Recording %s: mock inventory (no segments)", recording.recording_id)
        return []

    prefix = (recording.s3_archive_prefix or "").strip()
    if not prefix:
        logger.warning("Recording %s: s3_archive_prefix is empty; no segments to inventory", recording.recording_id)
        return []

    from app.core.aws_clients import s3_client
    s3 = s3_client()
    bucket = S.broadcast_recording_vod_bucket
    max_seg = S.broadcast_recording_max_segments

    keys: List[str] = []
    paginator = s3.get_paginator("list_objects_v2")
    try:
        for page in paginator.paginate(Bucket=bucket, Prefix=prefix):
            for obj in page.get("Contents", []):
                key = obj["Key"]
                if key.endswith(".ts"):
                    keys.append(key)
                    if len(keys) >= max_seg:
                        logger.warning(
                            "Recording %s: segment cap %d reached; truncating inventory",
                            recording.recording_id, max_seg,
                        )
                        return sorted(keys)
    except Exception as exc:
        logger.error("Recording %s: S3 inventory error: %s", recording.recording_id, exc, exc_info=True)
        raise

    segments = sorted(keys)
    logger.info("Recording %s: inventoried %d segments from s3://%s/%s",
                recording.recording_id, len(segments), bucket, prefix)
    return segments
```

### Dev/Prod parity (SECOPS-007)

The S3 client is obtained via `app/core/aws_clients.s3_client()`. In dev mode:
- `_s3_endpoint_url()` returns `None` when `S.dev_mode=True` (line 81 of `aws_clients.py`), which means boto3 uses the normal AWS SDK HTTP layer.
- moto's `mock_aws()` context (started at app startup by `dev_s3.start_s3_mock`) patches botocore at the HTTP transport layer, so the `list_objects_v2` call is served from moto's in-memory store transparently.
- The `broadcast-vod` bucket is pre-created by `start_s3_mock` if listed in `main.py`'s startup bucket list.

In production:
- `s3_client()` creates a real boto3 S3 client pointed at AWS.
- The `Prefix` parameter corresponds to the path under which the HLS ingest pipeline deposits segments.

**No feature flag or environment branch is needed** — the same code path runs in both environments. The mock path fires only when `_should_mock()` is `True` (dev + no FFmpeg).

### Bucket initialisation for dev

Ensure `S.broadcast_recording_vod_bucket` is included in the bucket list passed to `start_s3_mock`. If it is not, add it to `app/main.py`'s startup call:

```python
# app/main.py — startup
from app.core.dev_s3 import start_s3_mock
start_s3_mock([
    ...,
    S.broadcast_recording_vod_bucket,   # ensure "broadcast-vod" bucket exists in moto
])
```

### Backward compatibility

- `RecordingRecord.s3_archive_prefix` already exists in the dataclass (line 29 of `broadcast_recording.py`). No schema changes.
- The function signature `inventory_segments(recording: RecordingRecord) -> List[str]` is unchanged; callers (`process_recording` at line 214) are unaffected.
- `_should_mock()` continues to gate mock behaviour. Setting `BROADCAST_RECORDING_MOCK_ON_NO_FFMPEG=1` (the current default) completely bypasses the new S3 code, so dev environments without FFmpeg are unaffected.
- Recordings created before this fix have `segment_count=0` in DynamoDB. They are not retroactively corrected. If re-processing is needed, a one-off script can set their `status` back to `pending` and re-invoke `process_recording`. This is out of scope for the initial fix but should be documented as a follow-on task.
- The `s3_archive_prefix` may be empty on recordings created before the ingest pipeline was configured to set it. The guard `if not prefix: return []` handles this case cleanly with a warning log.

### Observability

The log line added to `inventory_segments` (`"inventoried %d segments"`) is structured and queryable in CloudWatch. Add a metric `broadcast_recording_segments_inventoried_total{recording_id}` using `app/metrics.py` for production observability.

Add a warning alert when `segment_count=0` after inventory on a non-mock path: this indicates either an empty `s3_archive_prefix` (ingest pipeline bug) or an S3 permissions issue. A recording marked `ready` with zero segments is a data integrity issue that should page on-call.

A secondary metric `broadcast_recording_inventory_duration_seconds` (histogram) measures how long the paginated S3 list takes. For sessions with thousands of segments this can take multiple seconds; tracking it enables capacity planning for the recording worker.

### Rollout

- **Effort**: M (implementation + tests; S3 pagination is standard but the moto test setup requires care).
- **Risk**: Low for the function itself. The wider risk is GAP-0120 (`concatenate_segments` also needs to be implemented) — these two must ship together or the non-empty segment list will pass into a stub concatenator that still returns `None`.
- **Sequence**: GAP-0119 and GAP-0120 form an atomic pair. Deploy together. The `_should_mock()` gate ensures no change in dev behaviour unless both `BROADCAST_RECORDING_MOCK_ON_NO_FFMPEG=0` and FFmpeg are present.
- **Rollback**: Revert to the stub `return []`. No data is lost; recordings will revert to zero-duration placeholder state.
