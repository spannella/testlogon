# GAP-0259: Profile-Change Re-Screening Not Wired — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Gap**: After a KYC case is approved, if a user changes their `display_name`, `first_name`, `last_name`, `birthday` (date of birth), or the `country`/`nationality` field stored in the users table, no re-screening is triggered. The AML continuous monitoring requirement mandates re-screening whenever identity-relevant attributes change for previously approved subjects.

- **Severity**: HIGH
- **Source ticket**: KYC-006
- **Area**: Backend (profile update endpoints + sanctions screening pipeline)
- **Status**: Confirmed — the gap exists exactly as described.
- **Claim note**: The ticket references `display_name`, `date_of_birth`, and `nationality`. Code inspection shows: (a) `date_of_birth` and `nationality` are not fields in `ProfileBase` / `ProfilePatchReq` / `ProfilePutReq` (models.py:1370–1394); instead, DOB is stored as `birthday` in `ProfileBase` and nationality is stored in the `users` DynamoDB table separately (not via `profile.py`). The substantive claim is correct — identity-relevant field changes do not trigger re-screening — but the specific field names cited need refinement. The sensitive fields that feed into screening via `_load_subject_identity()` are: `display_name`, `first_name`, `last_name`, `birthday` (from profile) and `country`/`nationality` (from the users table).
- **Impact**: An approved KYC user can change their legal name, DOB, or nationality after approval and remain on sanctions/PEP lists with no automatic re-check. This violates FATF Recommendation 10 (ongoing due diligence) and most AML program requirements.
- **Related tickets**: KYC-006 (parent feature), GAP-0258 (submission hook), KYC-008 (risk score), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (root cause)

### 2.1 Profile update endpoints (app/routers/profile.py)

`app/routers/profile.py` exposes three profile update paths:

- `PATCH /profile` (line 172) — `ui_patch_profile`: partial update via `body.model_dump(exclude_unset=True)`, calls `apply_profile_update(ctx["user_sub"], updates, replace=False)`.
- `PUT /profile` (line 178) — `ui_put_profile`: full replace, calls `apply_profile_update(ctx["user_sub"], updates, replace=True)`.
- `PATCH /profile` with a photo sub-path (line 283) — also calls `apply_profile_update`.

None of these endpoints contain any call to `SCREENING_STORE.screen_case()`, `SCREENING_STORE.rescreen_user()`, or anything in `app.services.kyc_sanctions_screening`.

### 2.2 apply_profile_update (app/services/profile.py:294)

```python
def apply_profile_update(user_sub: str, updates: Dict[str, Any], *, replace: bool) -> Dict[str, Any]:
    current = get_profile(user_sub)
    base = empty_profile() if replace else current
    normalized = normalize_profile_payload(updates)
    updated = {**base, **normalized}
    audit_entries: List[Dict[str, Any]] = []
    ts = now_ts()
    for field in PROFILE_FIELDS:
        if current.get(field) != updated.get(field):
            audit_entries.append(...)
    save_profile(user_sub, updated, audit_entries)
    return updated
```

The function already computes `audit_entries` — a list of field-level changes. This is the exact mechanism needed to detect when a screening-relevant field has changed. The hook point is after line 311 (`save_profile(user_sub, updated, audit_entries)`), where the caller knows which fields changed.

### 2.3 Sensitive fields for re-screening

`app/services/kyc_sanctions_screening.py:267–295` — `_load_subject_identity()` pulls:

- `display_name` / `first_name` / `last_name` from `get_profile(user_sub)` — these are in `PROFILE_FIELDS` (lines 16–33 of `app/services/profile.py`)
- `birthday` from profile — stored in PROFILE_FIELDS as `"birthday"` (line 22 of `profile.py`)
- `country` / `nationality` from `T.users.get_item(...)` — this is NOT part of `PROFILE_FIELDS`; it lives in the `users` DynamoDB table directly

The GAP ticket uses `date_of_birth` and `nationality`, but the actual stored field names in the profile are `birthday` (not `date_of_birth`) and the nationality field lives in the users table, not the profile. The actual sensitive fields to watch are:

```python
_SCREENING_SENSITIVE_PROFILE_FIELDS = frozenset({
    "display_name", "first_name", "last_name", "birthday"
})
```

Nationality changes go through a different update path (users table) and require a separate hook.

### 2.4 rescreen_user() signature

`app/services/kyc_sanctions_screening.py:535`:

```python
def rescreen_user(self, *, case_id: str, user_sub: str, trigger: str, ...) -> list[dict]:
    return self.screen_case(
        case_id=case_id, user_sub=user_sub, trigger=trigger, ...
    )
```

This requires a `case_id`. For a profile-change re-screening, the re-screening should be applied to the user's most recent approved KYC case. The screening store can find it via `get_results_for_case` or by querying `T.kyc_cases` by `user_sub`. Alternatively, a synthetic case_id can be generated: `f"rescreen_{user_sub}_{now_ts()}"` — this creates a new set of screening records without requiring an active case (following the `run_screening` endpoint pattern at `kyc_sanctions_screening.py:100–101`).

### 2.5 Where to hook the re-screening

**Option A (router hook)**: In `app/routers/profile.py:ui_patch_profile` and `ui_put_profile`, after calling `apply_profile_update`, check whether any sensitive field changed and call `SCREENING_STORE.screen_case()`. This is the lowest-friction change.

**Option B (service hook)**: Add a post-save callback parameter to `apply_profile_update` or add a separate `on_profile_updated` hook function. This is cleaner architecturally.

Option A is recommended for this fix (matches the pattern used in GAP-0258 for the submission hook — a try/except wrapper in the router).

### 2.6 Condition: only re-screen approved cases

Re-screening should only fire when the user has an approved KYC case (otherwise there is nothing to re-validate). This requires a lookup: `STORE.get_latest_case_for_user(user_sub)`. If no approved case exists, the re-screen is a no-op.

`app/services/kyc_cases.py` already has `list_cases_for_user(user_sub)` which can be used to find approved cases. The re-screen should be fired only when `any(c.get("status") == "approved" for c in list_cases_for_user(user_sub))`.

### 2.7 Dev vs prod parity (SECOPS-007)

Same as GAP-0258: the screening store uses DynamoDB Local in dev and DynamoDB in prod. No outbound calls. No environment-specific code needed. The fix is SECOPS-007-compliant.

## 3. Impact / Exploit / Blast Radius

### 3.1 Regulatory exposure

FATF Recommendation 10 ("Customer Due Diligence") requires financial institutions to conduct ongoing due diligence and update customer information "on a risk-sensitive basis". A user who changes their name after KYC approval without triggering re-screening has effectively circumvented the identity check. Specific scenarios:

- An approved user legally changes their name to one matching an OFAC SDN entry — not re-screened, continues operating.
- A PEP (Politically Exposed Person) approved under one name changes to a different public name — no flag is raised.
- A user changes `birthday` to avoid age-based risk rules — not re-screened.

### 3.2 Data integrity

The `kyc_screening_results` table will show `screened_name` from the original submission. If the user's actual current name differs, the result is stale and will produce incorrect "clear" results in any subsequent manual re-screen unless the reviewer explicitly passes the new name.

### 3.3 Blast radius

Every user with an approved KYC case who subsequently updates identity-relevant profile fields. There is no ceiling on this — in a production environment with thousands of KYC-approved users updating their profiles, all of them bypass continuous monitoring.

## 4. Fix Design (code-level)

### 4.1 Define sensitive fields constant

In `app/services/profile.py`, add (after line 33):

```python
# Fields whose change must trigger KYC re-screening for approved cases.
SCREENING_SENSITIVE_PROFILE_FIELDS = frozenset({
    "display_name",
    "first_name",
    "last_name",
    "birthday",
})
```

Export this constant so the router can reference it without duplicating the set.

### 4.2 Add re-screening hook to profile router

In `app/routers/profile.py`, add the import:

```python
from app.services.profile import SCREENING_SENSITIVE_PROFILE_FIELDS
```

Add a helper function (after the existing imports):

```python
def _maybe_rescreen_after_profile_update(
    user_sub: str,
    previous: dict,
    updated: dict,
) -> None:
    """Fire re-screening if any identity-sensitive field changed and user has approved case."""
    changed_sensitive = any(
        previous.get(f) != updated.get(f)
        for f in SCREENING_SENSITIVE_PROFILE_FIELDS
    )
    if not changed_sensitive:
        return
    try:
        from app.services.kyc_cases import STORE as KYC_CASE_STORE
        from app.services.kyc_sanctions_screening import STORE as SCREENING_STORE, TRIGGER_PROFILE_CHANGE
        from app.core.time import now_ts

        cases = KYC_CASE_STORE.list_cases_for_user(user_sub)
        approved_cases = [c for c in cases if c.get("status") == "approved"]
        if not approved_cases:
            return
        # Re-screen against the most recently approved case
        case_id = approved_cases[0].get("kyc_case_id") or f"rescreen_{user_sub}_{now_ts()}"
        SCREENING_STORE.screen_case(
            case_id=case_id,
            user_sub=user_sub,
            trigger=TRIGGER_PROFILE_CHANGE,
        )
    except Exception:
        import logging
        logging.getLogger(__name__).exception(
            "kyc.rescreen.profile_change_hook_failed user_sub=%s", user_sub
        )
```

`TRIGGER_PROFILE_CHANGE` should be added to `app/services/kyc_sanctions_screening.py` alongside the existing trigger constants:

```python
TRIGGER_PROFILE_CHANGE = "profile_change"
```

Update `ui_patch_profile` (line 172–176) and `ui_put_profile` (line 178–183) to call the helper:

```python
@router.patch("/profile")
async def ui_patch_profile(req: Request, body: ProfilePatchReq, ctx=Depends(require_ui_session)):
    updates = body.model_dump(exclude_unset=True)
    from app.services.profile import get_profile
    previous = get_profile(ctx["user_sub"])
    profile = apply_profile_update(ctx["user_sub"], updates, replace=False)
    audit_event("profile_update", ctx["user_sub"], req, outcome="success", mode="patch")
    _maybe_rescreen_after_profile_update(ctx["user_sub"], previous, profile)
    return {"profile": profile}
```

Note: `get_profile` is already called inside `apply_profile_update`. To avoid a double DynamoDB read, the `previous` profile can alternatively be passed from a modified `apply_profile_update` that returns `(updated, previous)` as a tuple. Either approach is acceptable; the simpler double-read path is lower risk for this fix.

### 4.3 Nationality changes (users table)

The `nationality` / `country` field lives in the `users` table (read by `_load_subject_identity()` at `kyc_sanctions_screening.py:289`), not the profile table. Profile update endpoints do not update this field. If there is a separate nationality/country update endpoint, the same `_maybe_rescreen_after_profile_update` pattern should be applied there. This is a follow-on task outside the scope of this fix.

### 4.4 Dev/Prod parity (SECOPS-007)

Same as GAP-0258. DynamoDB Local in dev, DynamoDB in prod. All logic is in-process. The `try/except` wrapper means screening failures are logged but never surface to the user.

### 4.5 Alternatives considered

- **Event-driven (DynamoDB Streams or SNS)**: Rejected for this fix. The current architecture uses synchronous in-request hooks (audit events, metrics). An async event bus would require new infrastructure and violates SECOPS-007's "same code path" principle without additional dev/prod flag management.
- **Polling job**: Rejected. A cron job that compares current profile data against screened identity data is error-prone and introduces a monitoring gap window.

### 5.2 Playwright E2E (informational)

A full Playwright test is impractical here because it would require Alice to have an approved KYC case, which takes multiple submission steps. An API-level test is sufficient:

```typescript
test.describe("175: Profile change triggers re-screening for approved case", () => {
  test("175.1 Screening result exists after profile name change", async ({ request }) => {
    // Assumes alice has an approved KYC case from earlier tests
    await request.patch("/ui/profile", {
      headers: { "x-csrf-token": sessions.alice.csrf_token,
                 Cookie: `ui_session=${sessions.alice.session_id};ui_csrf=${sessions.alice.csrf_token}` },
      data: { display_name: "Alice Rescreen Test " + Date.now() },
    });
    // Give screening 100ms to complete
    await new Promise(r => setTimeout(r, 100));
    // Admin fetches screening results for alice's case
    const resp = await request.get(
      `/ui/kyc/sanctions/user-screening?user_sub=${sessions.alice.user_sub}`,
      { headers: { Authorization: "Bearer " + sessions.root.access_token } },
    );
    expect(resp.ok()).toBeTruthy();
    const data = await resp.json();
    const profileChangeResults = data.results.filter(
      (r: any) => r.trigger === "profile_change"
    );
    expect(profileChangeResults.length).toBeGreaterThan(0);
  });
});
```

### 5.4 Rollout

- **Effort**: S (1 day — helper function + two router changes + constant + tests)
- **Risk**: Low. The `try/except` wrapper eliminates regression risk. The main risk is an unexpected KYC case lookup adding ~5ms to profile update latency; acceptable.
- **Rollback**: Remove `_maybe_rescreen_after_profile_update` call from the two router endpoints and remove the helper function. No data migration needed.
- **Sequencing**: Can be developed in the same PR as GAP-0258 (both are simple router-level hook additions). Pair them as "KYC-006 screening pipeline completion". Must be deployed after `TRIGGER_PROFILE_CHANGE` constant is added to `kyc_sanctions_screening.py`.
