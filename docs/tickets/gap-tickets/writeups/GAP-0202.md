# GAP-0202: Full Billing Table Scan on Every Rollup — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code in
> `app/services/platform_financial_dashboard.py`,
> `app/services/billing_shared.py`, and `scripts/local-ddb-init.py`.

## 1. Summary & Classification

**Claim status: Confirmed.** `_scan_ledger_entries` at
`app/services/platform_financial_dashboard.py:136` performs an unbounded
`T.billing.scan()` with no filter expression; the `billing` table holds payment methods,
balance rows, billing config, and all ledger entries for every user, and the code
post-filters in Python. No `GSI_LEDGER_DATE` index exists in `scripts/local-ddb-init.py`
(billing table definition at line 64).

- **Severity**: HIGH
- **Source ticket**: FIN-013
- **Status**: Open
- **Owning area**: Platform Financial Dashboard / Billing
- **One-line impact**: Every call to any financial KPI endpoint (`/kpis`, `/trends`,
  `/provider-breakdown`, `/type-breakdown`, `/top-creators`, `/export`) triggers a full
  DynamoDB scan of the `billing` table, which will exhaust read-capacity and Lambda memory
  at production scale, causing availability failures for the finance dashboard and indirectly
  taxing the billing table that every other feature also reads from.

**Related tickets**: GAP-0203 (provider field unreliable, same FIN-013 source). No
dependency between the two fixes; they can be deployed independently.

## 2. Current-State Investigation (root cause)

### The scan code

`app/services/platform_financial_dashboard.py:136`:

```python
def _scan_ledger_entries(date_set: Optional[set[str]] = None) -> List[Dict[str, Any]]:
    """Scan the billing table, keeping only LEDGER# rows. Optionally filter
    to a set of ledger_date strings (computed in-memory to avoid a GSI)."""
    out: List[Dict[str, Any]] = []
    kwargs: Dict[str, Any] = {}
    while True:
        resp = T.billing.scan(**kwargs)          # <-- full table scan
        for item in resp.get("Items", []):
            sk = str(item.get("sk", ""))
            if not sk.startswith("LEDGER#"):
                continue                          # discard non-ledger rows in Python
            ld = item.get("ledger_date")
            if not ld:
                ld = _ledger_date_fallback(item)
            if date_set is not None and ld not in date_set:
                continue                          # date filter also in Python
            out.append(item)
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return out
```

The entire loop uses `T.billing.scan()` with no `FilterExpression` and no
`ProjectionExpression`. DynamoDB's `scan` reads every item in the table (all pages) and
returns them all to the application, which then discards every non-ledger row. At 1 million
users with an average of 10 billing rows each (payment methods, balance row, ledger
entries), a single rollup call reads 10 million items from DynamoDB.

### The call chain

Every public query function calls `_entries_for_range` → `_scan_ledger_entries`:

```
get_kpis        → _entries_for_range → _scan_ledger_entries
get_trends      → _entries_for_range → _scan_ledger_entries
get_provider_breakdown → _entries_for_range → _scan_ledger_entries
get_type_breakdown     → _entries_for_range → _scan_ledger_entries
get_top_creators       → _entries_for_range → _scan_ledger_entries
export_summary_csv     → get_trends + get_kpis → two full scans
compute_daily_rollup   → _scan_ledger_entries
```

The router `app/routers/platform_financial_dashboard.py` exposes these as HTTP endpoints
callable by any ROOT or ADMIN user. A single admin dashboard page load that fetches KPIs,
trends, and a breakdown fires three to five sequential full table scans.

### Missing GSI

The billing table definition in `scripts/local-ddb-init.py:64` is:

```python
TableDef(_resolve_table_name(S.billing_table_name, "billing"), "pk", "sk"),
```

No `gsi` parameter. There is no `GSI_LEDGER_DATE` (or any GSI) on the `billing` table. The
`ledger_date` attribute (`YYYY-MM-DD`, written by `new_ledger_entry` at
`app/services/billing_shared.py:249`) is denormalized onto every ledger row explicitly for
this query path, but the query path never uses it as a GSI key.

### Dev vs prod manifestation

In dev (DynamoDB Local, port 8001, at most a few hundred rows), the scan completes in
milliseconds and is invisible. In production (millions of billing rows, provisioned
capacity), each `scan()` consumes all available read-capacity units, causes throttling for
concurrent users trying to pay or update payment methods on the same table, and risks OOM
in the uvicorn process if the result set grows to hundreds of MB.

## 3. Impact / Exploit / Blast Radius

- **Availability**: Each financial dashboard page load can monopolize DDB read capacity for
  up to tens of seconds. At peak, simultaneous admin dashboard loads cascade into read
  throttling across the entire `billing` table, breaking payment flows for end users.
- **Cost**: DynamoDB charges per read-capacity unit. A full scan of a 10 GB billing table
  costs ~3,300 RCUs per 4 KB page. At 1 RCU per page, 2.5 million pages = 2.5 million RCU
  per dashboard load. With provisioned capacity at 500 RCU/s, a single scan holds the table
  for 83 minutes.
- **No financial data corruption**: The scan is read-only. No money figures are modified.
- **No security exposure**: The endpoint already requires ROOT/ADMIN session auth. The scan
  itself does not leak data beyond what the admin is authorized to see.
- **Blast radius**: All other features backed by the `billing` table (payment initiation,
  wallet deposit, subscription charge, ledger writes) face secondary throttling during a
  scan. This makes the gap an availability threat to core billing flows, not just to the
  dashboard.

## 4. Fix Design (code-level)

### Approach: Add GSI_LEDGER_DATE to the billing table

The `billing` table item for a ledger entry has structure:
- `pk = USER#<user_id>`
- `sk = LEDGER#<ts>#<entry_id>`
- `ledger_date = "YYYY-MM-DD"` (written by `new_ledger_entry` at
  `billing_shared.py:249`)

A GSI keyed on `ledger_date` (partition key) and `sk` (sort key) allows querying all
ledger entries for a specific date without touching payment method or balance rows.

#### `scripts/local-ddb-init.py` — add GSI to billing table

Replace the existing bare `TableDef` at line 64:

```python
# Before:
TableDef(_resolve_table_name(S.billing_table_name, "billing"), "pk", "sk"),

# After:
TableDef(
    _resolve_table_name(S.billing_table_name, "billing"),
    "pk",
    "sk",
    gsi=[{
        "index_name": "GSI_LEDGER_DATE",
        "partition_key": "ledger_date",
        "sort_key": "sk",
    }],
    attr_types={"ledger_date": "S"},
),
```

Note: `ledger_date` is a string attribute (`YYYY-MM-DD`). No `attr_types` override for `sk`
needed because `sk` is already defined as the table's range key (`S` type). The `attr_types`
dict in `TableDef` is only needed for GSI sort keys that differ from the table's type
declarations; `ledger_date` is a new attribute (string) and must be declared.

#### `app/services/platform_financial_dashboard.py` — replace scan with GSI query

```python
def _query_ledger_by_date(date_str: str) -> List[Dict[str, Any]]:
    """Query all ledger entries for a single date via GSI_LEDGER_DATE.

    Returns only LEDGER# sort-key rows for date_str. Non-ledger rows never
    carry ledger_date so they are naturally excluded.
    """
    from boto3.dynamodb.conditions import Key

    out: List[Dict[str, Any]] = []
    kwargs: Dict[str, Any] = {
        "IndexName": "GSI_LEDGER_DATE",
        "KeyConditionExpression": Key("ledger_date").eq(date_str)
            & Key("sk").begins_with("LEDGER#"),
    }
    while True:
        resp = T.billing.query(**kwargs)
        out.extend(resp.get("Items", []))
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return out


def _scan_ledger_entries(date_set: Optional[set[str]] = None) -> List[Dict[str, Any]]:
    """Return ledger entries, using the GSI when a date_set is provided.

    Falls back to a full scan only when date_set is None (all-time queries,
    which should be rare and explicitly rate-limited).
    """
    if date_set is not None:
        out: List[Dict[str, Any]] = []
        for d in date_set:
            out.extend(_query_ledger_by_date(d))
        return out

    # No date filter: fall back to scan (all-time export, rate-limit at call site).
    out = []
    kwargs: Dict[str, Any] = {}
    while True:
        resp = T.billing.scan(
            FilterExpression="begins_with(sk, :pfx)",
            ExpressionAttributeValues={":pfx": "LEDGER#"},
            **kwargs,
        )
        out.extend(resp.get("Items", []))
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return out
```

With this change, every date-bounded call (`get_kpis`, `get_trends`, all breakdowns) uses
`_query_ledger_by_date` per day, consuming only the read capacity actually needed for those
ledger entries. A 30-day dashboard window runs 30 GSI queries instead of one catastrophic
full table scan.

### AWS production migration

The GSI must be added to the production DynamoDB table via an `UpdateTable` call (not a
recreation). DynamoDB backfills the GSI asynchronously from existing items; the table
remains available during backfill. The GSI is queryable once its status transitions to
`ACTIVE` (typically minutes for small tables, hours for large ones). A deployment gate
should verify `GSI_LEDGER_DATE` status is `ACTIVE` before routing dashboard traffic.

For older ledger entries written before `ledger_date` was added (if any exist from before
FIN-013 implementation), the `_ledger_date_fallback` function (`line 160`) can populate the
field via a one-off DynamoDB backfill script that reads each `LEDGER#` item without a
`ledger_date` attribute and updates it using `ts` fallback.

### Dev/Prod parity (SECOPS-007)

Both the GSI definition in `local-ddb-init.py` and the query code in
`platform_financial_dashboard.py` are the same for dev and production. DynamoDB Local
supports GSIs fully. The fix introduces no `S.dev_mode` branches and no mock-specific
paths. The `T.billing` table handle resolves to DynamoDB Local in dev and to AWS DynamoDB
in prod via `app/core/tables.py`.

### Alternatives considered

- **FilterExpression on every scan**: Reduces bytes returned but not RCU consumed — DynamoDB
  charges per page read before filtering. Does not fix the capacity problem.
- **Separate `billing_ledger` table**: Cleanest long-term architecture, but requires
  migrating all `new_ledger_entry` write sites and all ledger-read sites. Too disruptive
  for this ticket; noted as a follow-on.
- **Pre-aggregated `financial_rollups` table**: Already exists
  (`_store_daily_rollup`/`_store_live_rollup`). The rollup-read path uses it; the
  rollup-compute path (which must read raw entries) is what needs the GSI. Not a
  replacement.

## 5. Testing, Verification & Rollout

### Regression test (pytest offline)

```python
# tests/test_platform_financial_dashboard_gsi.py
from unittest.mock import patch, call, MagicMock
from app.services.platform_financial_dashboard import _scan_ledger_entries

MOCK_ENTRIES = [
    {"pk": "USER#u1", "sk": "LEDGER#1700000000#abc", "ledger_date": "2026-01-15",
     "type": "deposit", "amount_cents": 1000, "state": "settled"},
    {"pk": "USER#u2", "sk": "LEDGER#1700000001#def", "ledger_date": "2026-01-15",
     "type": "tip_debit", "amount_cents": 500, "state": "settled"},
]

def test_scan_with_date_set_uses_gsi_not_scan():
    """_scan_ledger_entries with a date_set must query GSI, not scan."""
    with patch("app.services.platform_financial_dashboard.T") as mock_T:
        mock_T.billing.query.return_value = {"Items": MOCK_ENTRIES}
        mock_T.billing.scan = MagicMock()
        result = _scan_ledger_entries(date_set={"2026-01-15"})

    # FAILS BEFORE fix (scan is called instead of query)
    mock_T.billing.scan.assert_not_called()
    mock_T.billing.query.assert_called_once()
    call_kwargs = mock_T.billing.query.call_args.kwargs
    assert call_kwargs["IndexName"] == "GSI_LEDGER_DATE"
    assert len(result) == 2

def test_scan_without_date_set_falls_back_to_scan():
    """_scan_ledger_entries with no date_set falls back to filtered table scan."""
    with patch("app.services.platform_financial_dashboard.T") as mock_T:
        mock_T.billing.scan.return_value = {"Items": MOCK_ENTRIES}
        _scan_ledger_entries(date_set=None)

    mock_T.billing.scan.assert_called_once()

def test_multi_date_issues_one_query_per_date():
    """A date_set of N dates issues exactly N GSI queries."""
    with patch("app.services.platform_financial_dashboard.T") as mock_T:
        mock_T.billing.query.return_value = {"Items": []}
        _scan_ledger_entries(date_set={"2026-01-01", "2026-01-02", "2026-01-03"})

    # FAILS BEFORE fix; PASSES AFTER
    assert mock_T.billing.query.call_count == 3
```

### Rollout and risks

- **Effort**: M (GSI provisioning, code change, migration script for existing items, tests).
- **Risk (production)**: MEDIUM during GSI backfill — DynamoDB reserves additional
  write-capacity headroom while building the index. Schedule the `UpdateTable` call during
  low-traffic hours. The code change should be deployed only after the GSI is `ACTIVE`.
- **Risk (dev)**: LOW — `just restart` recreates the table from scratch with the GSI.
- **Rollback**: If the GSI fails to build, revert the code change to `_scan_ledger_entries`
  to restore the scan path. The GSI can remain on the table (inert, no cost when not queried).
- **Sequencing**: Deploy GSI schema change and backfill first; deploy code change second
  once GSI status is `ACTIVE`. Do not swap the two — querying a non-existent index raises a
  `ResourceNotFoundException`.
