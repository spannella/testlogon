# GAP-0023: Users Table Key Schema Mismatch in `kyc_risk_scoring.py` — Remediation Write-up

> ~5 pages. Fix-oriented. Built on investigation doc: `docs/tickets/gap-tickets/investigations/GAP-0023.md`.
> Note: the GAP ticket names `kyc_tiers.py` as the offender; the investigation confirms
> that service is correct. The **actual offender** is `kyc_risk_scoring.py`.

## 1. Summary & Classification

**Bug statement**: Three methods in `app/services/kyc_risk_scoring.py` call
`T.users.get_item(Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"})` — a composite
`pk`/`sk` key format that does not match the `users` table's actual key schema
(`user_sub` only, no sort key). DynamoDB silently returns an empty item for every such
call. As a result, all three scoring factors — country risk, profile completeness, and
account age — return hardcoded fallback-high-risk values for every user, systematically
inflating every risk score in the system.

## 2. Current-State Investigation (root cause)

### Table key schema (ground truth)

`scripts/local-ddb-init.py:49-54` defines the `users` table:

```python
TableDef(
    _resolve_table_name(S.users_table_name, "users"),
    "user_sub",          # partition key — simple string, no sort key
    gsi=[{"index_name": "ByKycTier", ...}],
    attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"},
),
```

The primary key is a single-attribute `user_sub` (string). There is no sort key, no
composite `pk`/`sk` structure. All services that write to this table (`registration.py`,
`sso_saml_jit.py`, `kyc_tiers.py`, `kyc_sanctions_screening.py`) use
`Key={"user_sub": user_sub}`.

### Services that use the correct key format

| File | Line | Key |
|------|------|-----|
| `app/services/kyc_tiers.py` | 32, 40, 65, 159, 172 | `{"user_sub": user_sub}` |
| `app/services/registration.py` | 43 | `{"user_sub": user_sub}` |
| `app/services/sso_saml_jit.py` | 19 | `{"user_sub": user_sub}` |
| `app/services/kyc_sanctions_screening.py` | 289 | `{"user_sub": user_sub}` |

The GAP ticket incorrectly identifies `kyc_tiers.py` as the offender; all of its calls
are correct.

### The actual offender: `kyc_risk_scoring.py`

Three methods in `KycRiskScorer` use the wrong key:

**`_compute_country_risk()` — line 335**:
```python
def _compute_country_risk(self, *, case_id: str, user_sub: str) -> dict:
    try:
        resp = T.users.get_item(Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"})
        profile = resp.get("Item", {})
        country = str(profile.get("country", "") or profile.get("nationality", "") or "").upper().strip()
    except Exception:
        country = ""
    if not country:
        return {"score": 30, "raw_value": "unknown", "description": "Country not specified"}
    ...
```
Because the key never matches a real item, `resp.get("Item", {})` always returns `{}`.
`country` is always `""`, so the method always returns `score: 30`.

**`_compute_profile_completeness()` — line 434**:
```python
    resp = T.users.get_item(Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"})
    profile = resp.get("Item", {})
    missing = 0
    for field in critical_fields:     # first_name, last_name, date_of_birth, email
        val = profile.get(field)
        if not val or ...:
            missing += 1
    score = min(100, missing * 20)    # always 80 (4 missing × 20) when profile is {}
```
With an empty item, all four critical fields are missing; `score` is always 80 (actually
`4 * 20 = 80`). The method always returns `score: 80` (would return `score: 40` for the
`unavailable` fallback if an exception were raised, but the empty dict path does not
raise). Wait — looking at line 445-446: `except Exception: return {"score": 40, ...}`.
The non-exception path with all-missing returns `score: 80`.

**`_compute_account_age()` — line 451**:
```python
    resp = T.users.get_item(Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"})
    profile = resp.get("Item", {})
    created_at = profile.get("created_at")
    if not created_at:
        return {"score": 60, "raw_value": "unknown", "description": "Account creation date unknown"}
```
`created_at` is always `None` from the empty item, so always returns `score: 60`.

### Why DynamoDB does not raise an error

`GetItem` with a key that does not match any item returns `{"ResponseMetadata": ...,
"Item": {}}` — it does not raise `ClientError`. The `except Exception` blocks in each
method are therefore never triggered; the code silently reads an empty dict and falls
into the "data not available" branch.

### Cumulative effect on risk scoring

With country_risk always 30, profile_completeness always 80, and account_age always 60,
the weighted contribution from these three factors is consistently high for every user,
regardless of their actual profile. The `KycRiskScorer.compute_score()` accumulates
these into a score that is systematically biased toward high-risk.

## 3. Impact / Exploit / Blast Radius

### KYC false-positive blocks

Users with verified, low-risk profiles (established accounts, GB/DE/US nationality,
fully populated profiles) receive elevated risk scores due to the broken reads. Depending
on the score thresholds for `auto_approve` and `auto_escalate` in the risk engine
configuration, this may:

- Block tier upgrades for legitimate users who should auto-approve.
- Trigger false-positive escalations to manual KYC review queues, increasing operational
  load.
- Cause systematic delays in user onboarding for any feature that is KYC-gated.

### Not a privilege escalation

High risk scores lead to stricter KYC requirements, not looser ones. An attacker cannot
exploit this bug to bypass KYC checks — the opposite occurs. The blast radius is
operational and compliance-related, not a security privilege escalation.

### Compliance and regulatory risk

KYC regulations (AML / FATF) require risk scoring to be based on actual user data.
Submitting inflated risk scores to regulators, or documenting a risk model that silently
ignores country and profile data, can expose the platform to regulatory findings during
audits. The risk model is demonstrably not functioning as described.

### Data integrity

Historical risk scores stored in the `kyc_risk_scores` table are permanently incorrect
for any user scored while this bug was active. A retroactive correction script would need
to re-score all existing cases once the fix is applied.

## 4. Fix Design (code-level)

### Determining the correct source table

Before applying the fix, the correct table for `_compute_country_risk`,
`_compute_profile_completeness`, and `_compute_account_age` must be confirmed:

- `T.users` items (written by `registration.py:43`) contain: `user_sub`, `email`,
  `first_name`, `last_name`, `created_at`, `kyc_tier`, `kyc_tier_updated_at`.
  They do NOT reliably contain `country` or `nationality` (those come from KYC document
  extraction).
- `T.profiles` (separate table, PK `user_sub`) may contain the extended fields
  `country`, `nationality`, `date_of_birth` depending on how profile updates work.

The investigation recommends verifying against the actual stored fields. **Option A**
(fix key in `T.users` reads) will work for `created_at` (account age) and possibly
`first_name`/`last_name`/`email` (profile completeness), but likely will not return
`country`/`nationality` (country risk). **Option B** (read from `T.profiles`) is likely
correct for `_compute_country_risk` and `_compute_profile_completeness`.

### Recommended fix (Option A + B combined)

```python
# app/services/kyc_risk_scoring.py

def _compute_country_risk(self, *, case_id: str, user_sub: str) -> dict:
    """Score based on user's country."""
    try:
        # T.profiles holds extended KYC profile data including country/nationality
        resp = T.profiles.get_item(Key={"user_sub": user_sub})
        profile = resp.get("Item", {})
        country = str(
            profile.get("country", "") or profile.get("nationality", "") or ""
        ).upper().strip()
    except Exception:
        country = ""
    ...  # rest unchanged

def _compute_profile_completeness(self, *, case_id: str, user_sub: str) -> dict:
    """Score based on how many critical profile fields are populated."""
    critical_fields = ["first_name", "last_name", "date_of_birth", "email"]
    try:
        # T.profiles contains extended profile fields; T.users contains auth fields
        resp = T.profiles.get_item(Key={"user_sub": user_sub})
        profile = resp.get("Item", {})
        ...  # rest unchanged

def _compute_account_age(self, *, case_id: str, user_sub: str) -> dict:
    """Score: newer accounts are higher risk."""
    try:
        # T.users contains created_at (written by registration.py)
        resp = T.users.get_item(Key={"user_sub": user_sub})
        profile = resp.get("Item", {})
        ...  # rest unchanged
```

If `T.profiles` is confirmed to also contain `created_at`, all three can use
`T.profiles`. The key correction is the same in either case: remove `{"pk": ...,
"sk": "PROFILE"}` and replace with `{"user_sub": user_sub}`.

### Minimal correct fix (guaranteed safe)

If source-table selection is deferred, the immediate safe fix is to correct all three
key expressions to use the canonical `users` table key format, which at minimum fixes
`_compute_account_age` and partially fixes `_compute_profile_completeness`:

```python
# Replace all three instances of:
resp = T.users.get_item(Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"})
# With:
resp = T.users.get_item(Key={"user_sub": user_sub})
```

This is a three-line change at lines 335, 434, and 451.

### Dev/Prod parity (SECOPS-007)

DynamoDB Local and AWS DynamoDB both behave identically for `GetItem` with an incorrect
key: they return an empty item without raising an error. The fix is a pure key-format
correction; no AWS-specific behaviour, environment variable, or feature flag is involved.
The fix behaves identically in dev and production.

### Backward compatibility / migration

Existing risk scores in the `kyc_risk_scores` table are incorrect. After deploying the
fix, a one-time re-scoring script should iterate open KYC cases and call
`KycRiskScorer().compute_score()` for each. This is a data-quality migration, not a
schema migration; no table structure changes are required.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline, moto)

```python
# tests/test_kyc_risk_scoring_users_key.py
import pytest
from app.core.tables import T
from app.core.time import now_ts
from app.services.kyc_risk_scoring import KycRiskScorer


def test_country_risk_reads_real_profile(ddb_tables):
    """_compute_country_risk must return score 0 for a known low-risk country."""
    user_sub = "test-user-country"
    # Write a record with the correct users table key format
    T.users.put_item(Item={
        "user_sub": user_sub,
        "country": "GB",
        "created_at": now_ts() - 200 * 86400,
    })
    scorer = KycRiskScorer()
    result = scorer._compute_country_risk(case_id="c1", user_sub=user_sub)

    # BEFORE fix: score == 30 (unknown, because key never matched)
    # AFTER fix:  score == 0  (GB is in _LOW_RISK_COUNTRIES)
    assert result["score"] == 0, f"Expected score 0 for GB, got {result}"
    assert result["raw_value"] == "GB"


def test_account_age_reads_created_at(ddb_tables):
    """_compute_account_age must use created_at from the users table."""
    user_sub = "test-user-age"
    old_ts = now_ts() - 200 * 86400   # 200 days old = low risk
    T.users.put_item(Item={"user_sub": user_sub, "created_at": old_ts})
    scorer = KycRiskScorer()
    result = scorer._compute_account_age(case_id="c2", user_sub=user_sub)

    # BEFORE fix: score == 60 ("unknown" because created_at not found)
    # AFTER fix:  score == 0  (>180 days old)
    assert result["score"] == 0, f"Expected score 0 for 200-day-old account, got {result}"


def test_profile_completeness_reads_name_fields(ddb_tables):
    """_compute_profile_completeness must count populated fields correctly."""
    user_sub = "test-user-profile"
    T.users.put_item(Item={
        "user_sub": user_sub,
        "first_name": "Alice",
        "last_name": "Smith",
        "date_of_birth": "1990-01-01",
        "email": "alice@example.com",
    })
    scorer = KycRiskScorer()
    result = scorer._compute_profile_completeness(case_id="c3", user_sub=user_sub)

    # BEFORE fix: score == 80 (4 fields "missing" from empty item)
    # AFTER fix:  score == 0  (all 4 fields present)
    assert result["score"] == 0, f"Expected score 0 for complete profile, got {result}"
    assert result["raw_value"] == "complete"
```

All three tests fail before the fix (scores 30, 60, 80 instead of 0) and pass after.

5. Verify that a new user with no profile data still scores 30/80/60 as expected (the

### Metrics / observability

Add a structured log line in each `_compute_*` method when the item is empty but no
exception was raised:

```python
if not profile:
    logger.warning("kyc_risk.profile_empty", extra={"user_sub": user_sub, "factor": "country_risk"})
```

This allows operations to monitor for users whose profiles are genuinely absent vs.
silently broken.

### Rollback

Revert the three `Key=` expression changes. No database migration required. Rollback
returns the system to the (broken) current state.

### Risk

Low. The change makes reads succeed instead of silently returning empty dicts. The only
regression risk is if some other part of the codebase depends on the broken scores
(unlikely; scores are used downstream for gating, not upstream for producing other data).

### Effort

**S** — estimated 30-45 minutes: correct three `Key=` expressions, confirm table
selection, write three pytest tests, run `just test`.

### Sequencing

Apply this fix before the re-scoring migration script. Also coordinate with GAP-0267
(`ByKycTier` GSI declaration) since both touch the `users` table schema. This fix does
not modify the table schema; it only corrects the read key format.

### Clarification on investigation verdict vs. ticket description

The GAP ticket (line 7) names `app/services/kyc_tiers.py` as the offender. The
investigation confirms this is incorrect: every `GetItem` / `UpdateItem` call in
`kyc_tiers.py` uses the correct `Key={"user_sub": user_sub}` format (verified at lines
32, 40, 65, 159, and 172). The actual offender is `kyc_risk_scoring.py` — a separate
service written by a different developer. The fix target is therefore three lines in
`kyc_risk_scoring.py`, not any line in `kyc_tiers.py`.

This distinction matters for code review: any PR that modifies `kyc_tiers.py` in
response to this ticket is incorrect and should be rejected. The correct PR modifies only
`kyc_risk_scoring.py:335`, `:434`, and `:451`.

### Confirming the correct source table before shipping

Before marking this fix done, the following must be verified in the actual data model:

1. Open `scripts/local-ddb-init.py` and find the `profiles` table definition — confirm
   its partition key is `user_sub` and that it stores `country`, `nationality`, and
   `date_of_birth` fields.
2. Open `app/services/registration.py` and identify all `put_item` calls on `T.users` —
   confirm which fields are written (likely `first_name`, `last_name`, `email`,
   `created_at`, `kyc_tier` but not `country`).
3. Cross-reference: `_compute_country_risk` needs `country`/`nationality` → likely
   `T.profiles`; `_compute_account_age` needs `created_at` → likely `T.users`;
   `_compute_profile_completeness` needs all four critical fields → split or choose
   whichever table contains all of them.

If the `profiles` table does not exist or does not contain these fields, Option A
(correcting the key to `T.users`) is the safe fallback, even if it means some scoring
factors still return partial data from the flat users record.
