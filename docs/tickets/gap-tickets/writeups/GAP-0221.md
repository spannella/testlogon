# GAP-0221: No Audit Events Emitted by SSH Key Manager Service — Remediation Write-up

> Source ticket: INFRA-002 · Severity: HIGH · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** The SSH key manager service (`app/services/ssh_key_manager.py`) performs six security-sensitive operations — key generation, key upload, key deletion, private-key decryption, host association, and host disassociation — but none of them writes an entry to the platform audit trail. Every operation emits only a local structured `logger.info(...)` call whose output goes to the process log and is never forwarded to the security-event store consumed by SECOPS-001 telemetry and alert routing.

**Verdict (from investigation):** Confirmed. The ticket claim is accurate. The file contains exactly zero calls to `audit_event`. All six public functions (`generate_key`, `upload_key`, `delete_key`, `get_decrypted_private_key`, `associate_key_with_host`, `disassociate_key_from_host`) terminate their happy path with a `logger.info(...)` line and return. The `audit_event` helper defined at `app/services/alerts.py:631` is never imported or called from this module.

**Severity and area.** HIGH / Infrastructure Security. SSH private keys are KMS-encrypted secrets that, once decrypted, allow passwordless root-level access to user-provisioned EC2 instances and containers. Any unauthorised access, exfiltration, or accidental deletion goes entirely undetected by the audit trail. This is a SECOPS-001 compliance gap and an INFRA-002 spec violation.

**Related tickets.** INFRA-002 (SSH key management spec), GAP-0220 (stored-key auth not wired into SSH terminal), GAP-0229 (VNC/SSH passwords not stored per SECOPS-022). No blocking dependencies; the fix is additive and isolated to `ssh_key_manager.py`.

## 2. Current-State Investigation (root cause)

### Module-level audit infrastructure is absent

The file's import block (`app/services/ssh_key_manager.py:1–26`) contains:

```python
from app.core.crypto import kms_encrypt, kms_decrypt
from app.core.tables import T
from app.core.settings import S
from app.core.time import now_ts
```

There is no import of `audit_event` from `app.services.alerts`. The module does define `logger = logging.getLogger(__name__)` at line 26 and uses it exclusively.

### `generate_key` (line 133–186)

After storing the DDB item at line 182, the function emits:

```python
logger.info("key_generated user_sub=%s key_id=%s key_type=%s bits=%d",
            user_sub, key_id, key_type, bits)
```

The structured log contains the right fields but goes only to the process stdout/stderr stream captured by `uvicorn`. It never reaches the `T.alerts` DynamoDB table that backs the SECOPS-001 audit trail.

### `upload_key` (line 189–237)

Identical pattern: after `T.ssh_keys.put_item(Item=item)` at line 230, `logger.info("key_uploaded ...")` is called. No `audit_event`. Notably this operation is higher-risk than `generate_key` because an uploaded key may have been generated externally and the ciphertext material is accepted from the caller before validation completes.

### `delete_key` (line 258–268)

After `T.ssh_keys.delete_item(...)` at line 265:

```python
logger.info("key_deleted user_sub=%s key_id=%s", user_sub, key_id)
```

Key deletion is an irreversible destructive action. If an attacker deletes a user's keys to disrupt SSH access (DoS) or to cover tracks after exfiltration, no audit record exists.

### `get_decrypted_private_key` (line 271–296)

This is the highest-risk function. It calls `kms_decrypt(encrypted_blob)` at line 283, returning the plaintext PEM private key, and then emits:

```python
logger.info("key_decrypted user_sub=%s key_id=%s", user_sub, key_id)
```

This function is described as "INTERNAL USE ONLY" in its docstring but is reachable through the SSH bridge (`GAP-0220`). Every call materialises a plaintext private key in process memory. There is no audit trail record of *when* or *how often* this decryption occurs, making it impossible to detect abnormal decryption patterns (e.g., a compromised service account repeatedly decrypting keys it should not access).

### `associate_key_with_host` (line 299–317) and `disassociate_key_from_host` (line 320–335)

Both functions update the `associated_hosts` list on the key record and emit `logger.info("key_associated ...")` and `logger.info("key_disassociated ...")` respectively. A malicious actor who re-associates a key with a different host_id (e.g., pivoting an existing key to a newly launched instance they do not own) would leave no audit trail.

### Comparison: `host_inventory.py` does it right

The sibling module `app/services/host_inventory.py` defines a local `_audit()` wrapper at line 625 that calls `audit_event` from `app.services.alerts` inside a `try/except` guard, and invokes it from `create_host` (line 240), `update_host` (line 320), and `delete_host` (line 330). The SSH key manager should follow exactly this pattern.

### `audit_event` signature

```python
# app/services/alerts.py:631
def audit_event(event: str, user_sub: str, request=None, **fields: Any) -> None:
```

The function writes to the platform audit store, attaches IP and user-agent when a `request` object is supplied, resolves display name / email from the profile store, and forwards to SECOPS-001 webhooks. The `ssh_key_manager` service has no access to the HTTP request object at call sites (it is a service layer, not a router), but the `request=None` default makes it safe to call without one — the audit record will lack IP/UA but will still be indexed for key-level forensics.

### Dev vs prod behaviour

The gap is identical in both environments. DynamoDB Local and the real AWS DynamoDB table both receive the same `T.ssh_keys.put_item` / `delete_item` / `update_item` calls; in neither environment is `audit_event` ever called. In dev mode, the local process log captures `logger.info` output on the console and nothing else. In production, those log lines flow to CloudWatch Logs but are not correlated with the security-event store or alert routing pipelines.

## 3. Impact / Exploit / Blast Radius

### Compliance failure

INFRA-002 explicitly lists the required audit events: `ssh_key.generate`, `ssh_key.upload`, `ssh_key.delete`, `ssh_key.decrypt`, `ssh_key.associate`, `ssh_key.disassociate`. Their absence means:

- No SOC-2 / audit-log evidence that SSH keys were created or deleted by authorised actors.
- No SIEM correlation between a key decryption event and a subsequent suspicious login to a provisioned instance.
- No alerting threshold on `ssh_key.decrypt` frequency (abnormal volume = possible key harvesting).

### Attack scenarios

**Key exfiltration via compromised service account.** If an attacker gains access to a service account that can call `get_decrypted_private_key`, they can exfiltrate every user's private key without leaving any trace in the audit trail. The only observable signal would be KMS CloudTrail entries for `Decrypt` operations — but those are not correlated to the application-level user or key identity.

**Stealth key deletion (DoS).** An attacker with write access to the `ssh_keys` DynamoDB table can delete any user's keys. `delete_key` at line 265 calls `T.ssh_keys.delete_item` and logs to stdout, but nothing is written to the audit trail. The user loses SSH access to all associated hosts with no audit record of the deletion.

**Host-association pivot.** `associate_key_with_host` at line 310 appends a `host_id` to the key's `associated_hosts` list. If an attacker can call this endpoint for a key they do not own (IDOR), the association change is invisible to security monitoring.

**Blast radius.** Every user who has generated or uploaded SSH keys is affected. As of any production deployment, this means any instance that can be accessed via the SSH bridge has had its entire key lifecycle recorded only in ephemeral process logs rather than in durable, queryable audit records.

## 4. Fix Design (code-level)

### Approach

Add a module-local `_audit()` helper (matching the pattern in `host_inventory.py`) and call it at the end of each of the six public functions, after the DDB write and before the return.

### Implementation

**Step 1 — add the `_audit` wrapper** (after the existing `logger = logging.getLogger(...)` at line 26):

```python
# after line 26
def _audit(event: str, user_sub: str, **fields: Any) -> None:
    """Forward to the platform audit trail; never raises so it cannot break callers."""
    try:
        from app.services.alerts import audit_event
        audit_event(event, user_sub, **fields)
    except Exception:  # pragma: no cover
        logger.debug("audit_event failed for %s", event, exc_info=True)
```

**Step 2 — `generate_key`** (after `logger.info` at line 184):

```python
_audit("ssh_key.generate", user_sub, key_id=key_id, key_type=key_type, key_bits=bits)
```

**Step 3 — `upload_key`** (after `logger.info` at line 232):

```python
_audit("ssh_key.upload", user_sub, key_id=key_id, key_type=key_type, key_bits=bits,
       passphrase_protected=passphrase is not None)
```

**Step 4 — `delete_key`** (after `logger.info` at line 267):

```python
_audit("ssh_key.delete", user_sub, key_id=key_id)
```

**Step 5 — `get_decrypted_private_key`** (after `logger.info` at line 295):

```python
_audit("ssh_key.decrypt", user_sub, key_id=key_id)
```

**Step 6 — `associate_key_with_host`** (after `logger.info` at line 316):

```python
_audit("ssh_key.associate", user_sub, key_id=key_id, host_id=host_id)
```

**Step 7 — `disassociate_key_from_host`** (after `logger.info` at line 334):

```python
_audit("ssh_key.disassociate", user_sub, key_id=key_id, host_id=host_id)
```

### Dev/Prod parity (SECOPS-007)

The `_audit()` wrapper delegates unconditionally to `audit_event` regardless of `S.dev_mode` or any feature flag. `audit_event` itself resolves profile information from DynamoDB, which is mocked via DynamoDB Local in dev — so audit records are written to the local DDB instance during development and to real DynamoDB in production. No code path divergence is introduced. The `try/except Exception` guard means that if `audit_event` fails in either environment (e.g., `T.alerts` table does not exist locally), the SSH key operation succeeds and only a `DEBUG` log line is emitted, matching the behaviour of every other service that uses the same pattern.

### Backward compatibility

The change is purely additive. No existing API surface, DDB schema, or configuration is altered. The `_audit` call is fire-and-forget from the caller's perspective. No migration or feature flag is required.

### Alternatives considered

**Emit from the router layer instead of the service layer.** The SSH key router (`app/routers/ssh_key_manager.py`) has access to the HTTP request object and could call `audit_event` with IP/UA information. This is rejected because: (a) `get_decrypted_private_key` is intended to be called from the SSH bridge (non-HTTP context), not from the router; (b) splitting audit calls across router and service creates gaps whenever the service is called from background tasks or other services. Service-layer auditing is the consistent pattern used by `host_inventory.py`, `admin_impersonation`, and the billing subsystem.

## 5. Testing, Verification & Rollout

### Regression test (fails before / passes after)

Add `tests/test_ssh_key_manager_audit.py`:

```python
"""Regression test for GAP-0221 — audit_event must be called for every
SSH key lifecycle operation."""

import pytest
from unittest.mock import patch, call
from tests.conftest import make_test_client  # or however the project bootstraps


USER = "test-user-sub-0221"


@pytest.fixture()
def mock_audit(monkeypatch):
    calls = []
    monkeypatch.setattr(
        "app.services.ssh_key_manager.audit_event",
        lambda event, user_sub, **fields: calls.append((event, user_sub, fields)),
        raising=False,
    )
    return calls


def test_generate_key_emits_audit(mock_audit, ddb_tables):
    from app.services import ssh_key_manager as skm
    skm.generate_key(USER, label="test-key")
    events = [e for e, *_ in mock_audit]
    assert "ssh_key.generate" in events, "generate_key must emit ssh_key.generate audit event"


def test_upload_key_emits_audit(mock_audit, ddb_tables, ed25519_pem):
    from app.services import ssh_key_manager as skm
    skm.upload_key(USER, label="uploaded", private_key_pem=ed25519_pem)
    events = [e for e, *_ in mock_audit]
    assert "ssh_key.upload" in events


def test_delete_key_emits_audit(mock_audit, ddb_tables):
    from app.services import ssh_key_manager as skm
    meta = skm.generate_key(USER, label="to-delete")
    mock_audit.clear()
    skm.delete_key(USER, meta["key_id"])
    events = [e for e, *_ in mock_audit]
    assert "ssh_key.delete" in events


def test_decrypt_key_emits_audit(mock_audit, ddb_tables):
    from app.services import ssh_key_manager as skm
    meta = skm.generate_key(USER, label="to-decrypt")
    mock_audit.clear()
    skm.get_decrypted_private_key(USER, meta["key_id"])
    events = [e for e, *_ in mock_audit]
    assert "ssh_key.decrypt" in events


def test_associate_emits_audit(mock_audit, ddb_tables):
    from app.services import ssh_key_manager as skm
    meta = skm.generate_key(USER, label="to-associate")
    mock_audit.clear()
    skm.associate_key_with_host(USER, meta["key_id"], "h_abc123")
    events = [e for e, *_ in mock_audit]
    assert "ssh_key.associate" in events


def test_disassociate_emits_audit(mock_audit, ddb_tables):
    from app.services import ssh_key_manager as skm
    meta = skm.generate_key(USER, label="to-disassociate")
    skm.associate_key_with_host(USER, meta["key_id"], "h_abc123")
    mock_audit.clear()
    skm.disassociate_key_from_host(USER, meta["key_id"], "h_abc123")
    events = [e for e, *_ in mock_audit]
    assert "ssh_key.disassociate" in events
```

**Before fix:** All six assertions fail because `audit_event` is never called, so `mock_audit` stays empty after each operation.

**After fix:** All six assertions pass because `_audit()` calls the monkeypatched `audit_event` at the end of each operation.

### Manual QA steps

1. Start the local dev stack (`just up`).
2. Generate a new SSH key via `POST /ui/ssh-keys` (or via the DevTools UI).
3. Query the audit trail endpoint (`GET /ui/alerts/audit`) or DDB scan of `T.alerts` filtered by `event = "ssh_key.generate"`.
4. Confirm an entry exists with `user_sub`, `key_id`, `key_type`, and `ts` fields.
5. Repeat for upload, delete, and associate operations.

### Observability

Once deployed, add a CloudWatch Metric Filter (or equivalent) on the `T.alerts` table for events with prefix `ssh_key.*`. Create an alarm on `ssh_key.decrypt` rate exceeding N calls per minute per `user_sub` as a key-exfiltration detector.

### Rollback

The change is purely additive. Rolling back means removing the `_audit()` wrapper and its seven call sites. No DDB schema changes, no migration, no feature flag needed.

### Effort and sequencing

Effort: **S** (estimated 1–2 hours of implementation + test authoring). No dependencies on other open tickets. Can be merged as a standalone PR. Recommend shipping before GAP-0220 (stored-key SSH terminal) is released, so that all decryption events are audited from the moment the feature is used in production.
