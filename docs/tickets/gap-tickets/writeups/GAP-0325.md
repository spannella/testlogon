# GAP-0325: Double Silent-Failure Envelope Around Email Fanout — Remediation Write-up

> **Claim status**: CONFIRMED — `app/services/alerts.py:792` has a bare
> `except Exception: pass` wrapping the entire email fanout section, adding a second layer
> of silent failure on top of the one inside `send_alert_email()` itself (GAP-0324).

---

## 1. Summary & Classification

**Source ticket**: PLATFORM-006 (alert email delivery hardening)
**Severity as filed**: HIGH
**Status**: Open
**Owning area**: Alert delivery / email subsystem

The `audit_event()` function in `app/services/alerts.py` is the central dispatcher for all security alert notifications. After persisting the alert and sending push/webhook/SIEM deliveries, it runs an "Optional email fanout" block (lines 744-793). The entire block is wrapped in `except Exception: pass` (line 792).

This creates a double-silent-failure pattern:
1. **Inner** (`send_alert_email` lines 470-479, GAP-0324): SES `ClientError` is swallowed inside the send function.
2. **Outer** (lines 744-792, this ticket): any other failure — `get_alert_prefs()` DynamoDB read error, `render_ticket_email_template()` exception, `render_alert_email_template()` exception — is also silently discarded.

The combination means that for security-critical events (login from new device, MFA changes, API-key creation), the email notification path has **no observable failure mode** at all. An operator configuring the system for the first time — or an attacker who has somehow disrupted the email path — receives zero signal.

**Verdict**: Confirmed. Line 792 exactly matches the claim. The outer `except Exception: pass` is distinct from and additive to the one inside `send_alert_email()`.

**Related tickets**: GAP-0324 (inner silent-except in `send_alert_email()` — must be fixed in the same PR).

## 2. Current-State Investigation (root cause)

### 2.1 Exact code path

`app/services/alerts.py:744-793`:

```python
# Optional email fanout
try:                                           # ← line 745: outer try begins
    prefs = get_alert_prefs(user_sub)
    emails = prefs.get("emails") or []
    enabled = set(prefs.get("email_event_types") or [])
    if emails and (alert_type in enabled) and can_send_alert_channel(user_sub, "email"):
        ticket_template = render_ticket_email_template(
            alert_type=alert_type, payload=payload, outcome=outcome

        if ticket_template is not None:
            subj, body = ticket_template
            send_alert_email(emails, subj, body)
        else:

            html_template = None

                try:
                    from app.services.alert_email_templates import render_alert_email_template
                    html_template = render_alert_email_template(alert_type, payload)
                except Exception:             # ← line 761: inner silent-except #3
                    pass
            if html_template is not None:
                subj, body = html_template
                send_alert_email(emails, subj, body)
            else:
                subj = f"[Alert] {alert_type}: {event} ({outcome})"
                # … build body … (lines 766-790)
                send_alert_email(emails, subj, "\n".join(lines))
except Exception:                             # ← line 792: OUTER SILENT CATCH
    pass
```

There are now **three** silent exception discards in the email notification stack:

| Location | Catches | Effect |
|---|---|---|
| `line 761` | `render_alert_email_template` import/call errors | Falls back to plaintext template — acceptable |
| `line 478` (GAP-0324) | SES `ClientError` | Email silently not sent |
| `line 792` (this ticket) | Everything else in the fanout (DDB reads, template errors) | Entire email section silently skipped |

### 2.2 What the outer except hides

Beyond the SES error already covered by GAP-0324, the outer `except Exception: pass` discards:

- **`get_alert_prefs()` DynamoDB read failures** (e.g., `ResourceNotFoundException` if the `alert_prefs` table does not exist, `ProvisionedThroughputExceededException` during a traffic spike): email preferences cannot be read, so no emails are sent, with no log or metric.
- **`can_send_alert_channel()` errors** (e.g., an uncaught exception in rate-limit check code): rate-limit enforcement is bypassed, or emails are silently suppressed without checking.
- **`render_ticket_email_template()` exceptions** (e.g., a `KeyError` in a template that references a missing payload field): the template rendering fails, and the fallback to `send_alert_email` never runs.
- **String-formatting errors** in the fallback body builder (lines 766-790), e.g., if `json.dumps(payload, ...)` raises `TypeError` on a non-serialisable Decimal value from DynamoDB.

### 2.3 Relationship to the inner silent-except

If GAP-0324 is fixed but GAP-0325 is not:
- SES errors become observable (logged and DDB-recorded).
- DDB errors in `get_alert_prefs()` remain silent.
- Template rendering errors remain silent.

If GAP-0325 is fixed but GAP-0324 is not:
- The outer except is removed; template/prefs errors become observable.
- SES errors remain silent inside `send_alert_email()`.

Both must be fixed in the same PR to achieve full observability. The recommended approach is to fix GAP-0324 first (making `send_alert_email` log + record on failure), then address this outer except.

### 2.4 The pattern is repeated for SMS

Lines 795-812 apply the identical `try: ... except Exception: pass` pattern to the SMS fanout. That is outside the scope of this ticket but should be fixed in the same pass for consistency.

## 3. Impact / Exploit / Blast Radius

**Security impact** (HIGH):

The email fanout block is responsible for delivering alerts for the following event types (selected from `ALERT_CATEGORIES` at `app/services/alerts.py:31-40`):

- `security` category: `device_new`, `totp_device_added`, `totp_device_removed`, `api_key_created`, `api_key_revoked`, `session_revoked` — all high-value targets for an attacker performing account takeover.
- `activity` category: `subscription_started`, `new_follower` — lower sensitivity but still user-visible.

If `get_alert_prefs()` raises a DynamoDB error due to table misconfiguration, capacity exhaustion, or a schema migration error, every security alert email across all users silently stops. The DynamoDB error itself is already likely to be logged elsewhere, but the connection to the email delivery failure is invisible.

**Worst-case scenario**: A deployment to production introduces a DynamoDB table name mismatch (e.g., `T.alert_prefs` pointing to a non-existent table). All alert emails fail on every call. The platform's security email pipeline is completely silenced. Operators will not know until a user reports they did not receive a device-login notification — likely only after a successful account compromise.

**Double-silence compounding**: With both GAP-0324 and GAP-0325 present, a single bad SES configuration produces complete silence:
- The outer try at line 745 succeeds (no exception yet).
- `send_alert_email` raises a `ClientError` that is caught by the inner bare except at line 478.
- The outer except at line 792 is never reached (no exception propagated).
- Zero observable signal.

If instead `get_alert_prefs()` raises:
- The outer bare except at line 792 catches it.
- Zero observable signal.

## 4. Fix Design (code-level)

### 4.1 Remove the outer `except Exception: pass`

The fix is to replace the outer bare-except with a version that logs the error. The email fanout is explicitly labelled "Optional" in the source comment — so the caller (`audit_event`) does not need to re-raise. What matters is that the failure is visible.

```python
# app/services/alerts.py — replace lines 744-793

    # Optional email fanout
    try:
        prefs = get_alert_prefs(user_sub)
        emails = prefs.get("emails") or []
        enabled = set(prefs.get("email_event_types") or [])
        if emails and (alert_type in enabled) and can_send_alert_channel(user_sub, "email"):
            ticket_template = render_ticket_email_template(
                alert_type=alert_type, payload=payload, outcome=outcome
            )
            if ticket_template is not None:
                subj, body = ticket_template
                send_alert_email(emails, subj, body)
            else:
                html_template = None
                if S.notification_email_templates_enabled:
                    try:
                        from app.services.alert_email_templates import render_alert_email_template
                        html_template = render_alert_email_template(alert_type, payload)
                    except Exception:
                        pass  # Falls back to plaintext — acceptable.
                if html_template is not None:
                    subj, body = html_template
                    send_alert_email(emails, subj, body)
                else:
                    subj = f"[Alert] {alert_type}: {event} ({outcome})"
                    lines = [
                        f"Type: {alert_type}",
                        f"Event: {event}",
                        f"Outcome: {outcome}",
                        f"Time: {payload.get('ts')}",
                    ]
                    # … existing body-builder lines 768-790 …
                    send_alert_email(emails, subj, "\n".join(lines))
    except Exception:
        logger.exception(
            "audit_event: email fanout failed for user=%s event=%s alert_type=%s",
            user_sub,
            event,
            alert_type,
        )
        record_auth_event("alert_email_fanout_failed")
```

The only change is replacing `pass` with `logger.exception(...)` and `record_auth_event("alert_email_fanout_failed")`. The caller (`audit_event`) does not re-raise; the exception is absorbed after logging.

### 4.4 Dev/Prod parity (SECOPS-007)

In dev mode (`S.dev_mode = True`), `send_alert_email()` writes to a log file and returns before the SES call; it does not raise. The outer except at line 792 has never been triggered by the dev email path. After the fix:

- Dev: if `get_alert_prefs()` fails (e.g., the `alert_prefs` DDB table is absent during a fresh dev run), the exception is now logged instead of swallowed. This actually improves dev diagnostics.
- Production: SES errors are caught and logged inside `send_alert_email()` (GAP-0324 fix); any other fanout error is caught and logged by the outer except (this fix).

Both paths use the same logger and `record_auth_event()` call. No mock-only code path is introduced.

### 4.5 Backward compatibility

The change is purely additive: `logger.exception()` and `record_auth_event()` are appended to the existing exception handling. The caller's behaviour is unchanged — `audit_event()` still completes and returns `{"alert_id": ..., "ts": ...}` regardless of whether the email fanout succeeded.

def test_double_silent_failure_eliminated(caplog, monkeypatch):
