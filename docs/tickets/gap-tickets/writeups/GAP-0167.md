# GAP-0167: `participant_count` can go negative and has no floor — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement.** The Watch Party service (ENGAGE-004) tracks how many users
are currently active in a party via a `participant_count` integer field on the
`watch_parties` DynamoDB item. Three code paths decrement this counter: a
user leaving voluntarily (`leave_party`), a user being kicked
(`kick_participant`), and the heartbeat expiry cleanup path. Each decrement
is an unconditional `SET participant_count = participant_count + :d` where
`:d` is `-1`. There is no lower-bound guard: if the counter is already `0`
(e.g., because a previous decrement was applied twice due to a race condition,
a retry, or the initial party record having `participant_count = 0` before
anyone increments it), the field becomes negative. A negative
`participant_count` is semantically invalid, can cause false "party is full"
errors on join, and makes capacity-check logic unreliable.

**Severity:** HIGH  
**Source ticket:** ENGAGE-004  
**Status:** Open  
**Owning area:** `app/services/watch_party.py` — `_update_participant_count`,
`leave_party`, `kick_participant`  
**Effort:** S

**Verdict from code investigation:** Claim confirmed. `_update_participant_count`
at `app/services/watch_party.py:428-433` performs an unconditional ADD with
no `ConditionExpression`. All three decrement call sites pass `delta=-1`
without any guard.

**Related tickets:** GAP-0166, ENGAGE-004.

## 2. Current-State Investigation (root cause)

### `_update_participant_count` — no floor guard

`app/services/watch_party.py:428-433`:

```python
def _update_participant_count(party_id: str, delta: int) -> None:
    T.watch_parties.update_item(
        Key={"party_id": party_id},
        UpdateExpression="SET participant_count = participant_count + :d, updated_at = :u",
        ExpressionAttributeValues={":d": delta, ":u": now_ts()},
    )
```

The expression `participant_count + :d` with `:d = -1` will produce `-1` if
`participant_count` is currently `0`. DynamoDB stores this as a negative
`Number` without complaint.

### Decrement call sites

**`leave_party`** — `app/services/watch_party.py:181-198`:

```python
def leave_party(party_id: str, user_sub: str) -> None:
    existing = _get_participant(party_id, user_sub)
    if not existing or existing.get("status") != "active":
        return
    T.watch_party_participants.update_item(...)  # status → "left"
    _update_participant_count(party_id, -1)      # ← no floor check
```

The guard (`if not existing or existing.get("status") != "active"`) prevents
double-counting in the normal flow. However, in a concurrent scenario where
two requests read the participant record simultaneously (both see `active`)
and both proceed to decrement, the count is decremented twice for one
departure.

**`kick_participant`** — `app/services/watch_party.py:328-354`:

```python
if participant.get("status") == "active":
    _update_participant_count(party_id, -1)      # ← no floor check
```

Same issue: the `active` check is a read-then-write without a DynamoDB
condition. Two concurrent kick requests for the same target user that both
read `active` status before either write completes will both call the
decrement.

**Heartbeat expiry** — `app/services/watch_party.py` (the heartbeat cleanup
path that transitions stale participants to `"left"`) also calls
`_update_participant_count(party_id, -1)` via the same helper. If a user
leaves voluntarily while a heartbeat expiry for the same user is in-flight,
both paths decrement.

### Interaction with `join_party` capacity check

`app/services/watch_party.py:141-144`:

```python
current_count = int(party.get("participant_count", 0))
max_p = int(party.get("max_participants", 50))
if current_count >= max_p and not existing:
    raise HTTPException(status_code=409, detail="party is full")
```

When `participant_count` goes negative it reads as e.g. `-2`, so
`current_count >= max_p` is `False` even for `max_p=50`. The capacity guard
continues to work correctly for negative values in this specific comparison.
However, the displayed count (returned to clients in `PartyOut`) is negative,
which is confusing, and if the counter is negative a re-join could drive it
back up to `0` without representing a real participant, desynchronising
capacity management.

### DynamoDB and atomicity

DynamoDB `update_item` with `SET x = x + :d` is **atomic** — it is a
compare-and-swap at the attribute level within a single item. The race
condition described above is therefore real only if two separate `update_item`
calls are issued concurrently for the same `party_id`. In that case, DynamoDB
serialises them at the item level but neither call has a condition to prevent
it from going below zero.

## 3. Impact / Exploit / Blast Radius

**Who is affected:** Any watch party where users leave or are kicked
concurrently, or where a double-fire of the heartbeat expiry logic occurs.

**Corrupt party state.** A negative `participant_count` persists in DynamoDB
for the lifetime of the party record. The displayed occupancy shown to the
host and participants will be wrong (e.g., "Participants: -1"). This erodes
trust in the feature.

**Capacity bypass via undercount.** A negative count can allow more users
to join than `max_participants` once the natural decrement pushes the count
below the real occupancy (e.g., count is `-1` but 1 real user is active; a
second join sees `count = -1 < max_p`, joins, now `count = 0` with 2 real
users). Each subsequent leave/join cycle further desynchronises the count
from reality.

**Latent double-kick DoS.** A malicious host (or a bug in the admin kick
API) that issues two concurrent kick requests for the same user can drive the
count below zero by 1. On a party with only 1 participant this results in
`participant_count = -1` permanently (since that participant is now kicked and
no one will leave to trigger further decrements). The party record is
corrupted until it is manually repaired or the party ends.

**Blast radius:** Confined to the `watch_parties` DynamoDB table. No
financial data or messages are affected. No security boundary is broken.

## 4. Fix Design (code-level)

### Preferred fix — `ConditionExpression` floor guard on every decrement

Replace the unconditional `update_item` in `_update_participant_count` with a
conditional write that refuses to go below zero:

```python
def _update_participant_count(party_id: str, delta: int) -> None:
    """Atomically update participant count, clamping to a floor of 0."""
    from botocore.exceptions import ClientError

    try:
        if delta < 0:
            # Only decrement if count > 0
            T.watch_parties.update_item(
                Key={"party_id": party_id},
                UpdateExpression=(
                    "SET participant_count = participant_count + :d, updated_at = :u"
                ),
                ConditionExpression="participant_count > :zero",
                ExpressionAttributeValues={
                    ":d": delta,
                    ":u": now_ts(),
                    ":zero": 0,
                },
            )
        else:
            # Increment — no floor needed
            T.watch_parties.update_item(
                Key={"party_id": party_id},
                UpdateExpression=(
                    "SET participant_count = participant_count + :d, updated_at = :u"
                ),
                ExpressionAttributeValues={":d": delta, ":u": now_ts()},
            )
    except ClientError as e:
        if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
            # Count is already 0; silently swallow the no-op.
            logger.debug(
                "watch_party: participant_count already at 0, skip decrement party=%s",
                party_id,
            )
        else:
            raise
```

`ConditionExpression="participant_count > :zero"` with `:zero = 0` causes
DynamoDB to reject the write if the current value is `0` or negative,
raising `ConditionalCheckFailedException`. This is caught and treated as a
no-op (the count is already at or below the floor, so the decrement is
genuinely spurious).

This is the approach recommended in the GAP ticket.

### Why not `MAX(participant_count + :d, 0)` via a conditional expression?

DynamoDB's `UpdateExpression` does not support a `MAX()` function. The
equivalent pattern would require a more complex `ConditionExpression`-plus-
fallback-update pattern or a DynamoDB transaction, which adds latency and
complexity. The conditional-write-with-swallowed-exception pattern is the
standard DynamoDB idiom for floor-bounded counters.

### Scrub existing corrupt records (migration)

Run a one-time script at deploy time:

```python
# scripts/fix_negative_participant_counts.py
import boto3
from boto3.dynamodb.conditions import Attr
from app.core.settings import S

ddb = boto3.resource("dynamodb", endpoint_url=S.ddb_endpoint_url)
table = ddb.Table(S.watch_parties_table)

resp = table.scan(FilterExpression=Attr("participant_count").lt(0))
for item in resp.get("Items", []):
    table.update_item(
        Key={"party_id": item["party_id"]},
        UpdateExpression="SET participant_count = :zero",
        ExpressionAttributeValues={":zero": 0},
    )
```

### Dev/Prod parity (SECOPS-007)

DynamoDB `ConditionExpression` is supported identically by DynamoDB Local
(port 8001) and production DynamoDB. No dev-mode shim is required. The
`botocore.exceptions.ClientError` handling path is the same in both
environments. The migration script references `S.ddb_endpoint_url` so it
picks up the local endpoint in dev and the real endpoint in prod.

### Backward compatibility / feature flags

No API surface change. The floor guard is internal to the service layer.
No DynamoDB schema migration is required. The fix is fully backward
compatible — existing items with valid (non-negative) counts continue to
work exactly as before.

**Fails before fix:** `test_decrement_at_zero_is_no_op` fails because the
count becomes `-1`.  
**Passes after fix:** The conditional write is rejected when count is `0`;
the helper swallows `ConditionalCheckFailedException`; count stays `0`.

### Integration test — concurrent leave race

```python
def test_concurrent_leave_does_not_go_negative(moto_watch_parties_table):
    """
    Two simultaneous leave calls for the same user on a party with count=1
    must leave count at 0, not -1.
    """
    import threading
    from app.services.watch_party import _update_participant_count

    party_id = "wp_test_race_001"
    moto_watch_parties_table.put_item(
        Item={"party_id": party_id, "participant_count": 1, "updated_at": 0}
    )

    results = []
    def decrement():
        try:
            _update_participant_count(party_id, -1)
            results.append("ok")
        except Exception as e:
            results.append(str(e))

    t1 = threading.Thread(target=decrement)
    t2 = threading.Thread(target=decrement)
    t1.start(); t2.start()
    t1.join(); t2.join()

    item = moto_watch_parties_table.get_item(Key={"party_id": party_id})["Item"]
    assert int(item["participant_count"]) >= 0, (
        f"participant_count is negative: {item['participant_count']}"
    )
```

### Observability

The `logger.debug` call in the `ConditionalCheckFailedException` handler
produces visible output at `DEBUG` log level:

```
watch_party: participant_count already at 0, skip decrement party=wp_abc
```

Monitor the rate of this log line in production. A high rate indicates
that the double-decrement race is being triggered frequently, which may
warrant a more aggressive fix (e.g., a DynamoDB transaction that atomically
reads and conditionally decrements within a single atomic operation).

### Rollback

Remove the `ConditionExpression` and `ClientError` handling from
`_update_participant_count`, reverting to the original two-line implementation.
No schema or data migration needed to roll back (the migration script that
clamps negative values to zero is idempotent and safe to leave in place).

### Risk

**Low.** The change is entirely within `_update_participant_count` — a
single private helper. The `ConditionalCheckFailedException` catch is a
standard pattern used throughout DynamoDB-backed services in this codebase.
The only behavioural difference is that spurious double-decrements are
silently swallowed rather than applied; this is the intended and correct
behaviour.

### Effort

**S** — approximately 45 minutes: code change (~20 lines), unit tests
(~30 min), migration script (~15 min).
