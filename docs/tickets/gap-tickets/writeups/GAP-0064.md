# GAP-0064: E2E Spec Absent for ADS-016 Ad Scheduling — Remediation Write-up

> ~5 pages. Fix-oriented. Claim verified directly against the code before writing; cites file:line.

## 1. Summary & Classification

**Claim status: CORRECTED.** The gap ticket states "no ad-scheduling.spec.ts; 12 tests in sections 408-410 are entirely unwritten." This is inaccurate. The file `frontend/e2e/ad-dayparting.spec.ts` exists (433 lines, 20 tests) and covers all three claimed missing areas:

- Section 408: Dayparting Configuration API (5 tests, including ownership isolation)
- Section 409: Flight Scheduling API (5 tests, including overlap/boundary rejection)
- Section 410: Eligibility & Budget Pacing API (4 tests)
- Section 411: Schedule UI (1 test — a smoke test for the campaign scheduling tab)

The gap audit searched for `ad-scheduling.spec.ts` and found nothing; the actual file is named `ad-dayparting.spec.ts`, matching the service module `app/services/ad_dayparting.py`. The claimed "12 tests" are actually 20 tests in the file.

However, as noted in GAP-0063, sections 408 and 409 in `ad-dayparting.spec.ts` collide with sections 408 and 409 in `ad-creative-affiliate.spec.ts`. This collision is a real problem even though both files exist.

- **Severity**: HIGH (as filed) — downgraded to LOW on investigation; the coverage gap is a naming/discoverability issue, not missing tests.
- **Source ticket**: ADS-016  
- **Owning area**: Ads / Ad Scheduling / E2E Test Suite  
- **One-line impact**: The ad-scheduling E2E spec exists and covers dayparting, flight scheduling, eligibility, and pacing; the gap is a filename mismatch versus the expected name.  
- **Related tickets**: GAP-0063 (same pattern — spec exists under a different name), GAP-0065 (unit tests for ADS-016 — also corrected), ADS-016 (parent feature).

### Root cause of the false gap

The gap audit expected `ad-scheduling.spec.ts` (matching the feature concept "ad scheduling") but the file was named after the service module `ad_dayparting.py`. The two names refer to the same feature — the service handles both flight scheduling (date ranges) and dayparting (intra-day scheduling) under the `ad_dayparting` module name.

### Section-number collision (genuine issue)

This matches the same collision documented in GAP-0063. Both `ad-dayparting.spec.ts` and `ad-creative-affiliate.spec.ts` claim sections 408 and 409:

| File | Section 408 content | Section 409 content |
|------|---------------------|---------------------|
| `ad-dayparting.spec.ts` | Dayparting config API | Flight scheduling API |
| `ad-creative-affiliate.spec.ts` | Ownership edge cases | Affiliate Discount UI |

The collision means that any bug-tracking ticket that references "section 408" is ambiguous. CI failure reports attributed to section 408 could refer to either file.

### What is genuinely missing

All claimed test coverage exists. The only genuine gaps in the ADS-016 E2E area are:

1. **No test for the named schedule template endpoint** — if the backend exposes `PUT /ui/ads/scheduling/campaigns/{id}/template` with a `template` key (e.g., `"weekdays_business"`), the existing spec tests only custom schedule objects passed as inline JSON. Named template expansion is exercised only by the offline unit tests in `test_ad_dayparting.py`.
2. **No UI test for the flight management sub-panel** — section 411 is a single smoke test that navigates to the scheduling page and verifies it loads. It does not interact with the "Add Flight" form, date pickers, or the flight status badges.
3. **No test for `DELETE /ui/ads/scheduling/campaigns/{id}/flights/{flight_id}`** — flight deletion is not tested either via API or UI. If a flight is set and the advertiser wants to remove it before it activates, that path is untested.

These are incremental coverage gaps, not the complete absence of a spec file as originally claimed.

## 3. Impact / Exploit / Blast Radius

### Functional risk from the naming gap

None — Playwright discovers all `*.spec.ts` files by glob; the test suite runs correctly regardless of filename. The naming gap only impacts human discoverability in documentation and gap audits.

### Risk from section-number collision

Same as GAP-0063: low today, escalating as CI tooling matures. A failure in `ad-dayparting.spec.ts` section 408 and a failure in `ad-creative-affiliate.spec.ts` section 408 produce identical CI failure labels, making triage ambiguous. The collision is symmetric — both sections are test sections that legitimately exist; neither is a placeholder or stub. Any bug-tracking workflow that auto-assigns failures by section number will route one of the two to the wrong team.

Beyond section 408 and 409, the collision also means that a future developer adding a new section to one spec file must manually check all other spec files to avoid re-using a number — there is no automated guard preventing future collisions from accumulating.

### Risk from missing template, flight-UI, and flight-delete tests

Medium for flight-delete. The named schedule templates (`SCHEDULE_TEMPLATES` in `app/services/ad_dayparting.py:35-49`) are thin wrappers over `validate_dayparting_config` — already covered by the offline unit tests in `tests/test_ad_dayparting.py`. The risk there is low.

The flight-delete gap is more significant: if an advertiser sets a flight with incorrect dates and then tries to delete it before it activates, a regression in the flight deletion endpoint would cause unexpected billing exposure (the campaign might serve under an unintended schedule). That path is currently untested by both E2E and unit tests.

### Risk from missing template and flight-UI tests

Low for UI regression: the flight creation form is a React controlled component. Without an E2E test that fills the date picker and submits, a CSS or event-handler regression in the flight creation UI would be invisible to automated testing. Given the low frequency of change in date-picker components this is acceptable short-term, but it should be resolved before the scheduling feature is promoted to general availability.

### Auth pattern note

`ad-dayparting.spec.ts` uses the same `e2e_admin_session_setup.py` session injection as other ADS-spec files. The `apiPut`, `apiGet`, and `apiPost` helpers in the spec (defined around lines 70-105) all accept an `identity` string, look up the stored session, and attach the CSRF token header. For the additional flight-delete test, the same `apiDelete` pattern can be used:

```typescript
async function apiDelete(page: Page, identity: string, path: string) {
  const sessions = getAdminSessions();
  const resp = await page.request.delete(`${BASE}${path}`, {
    headers: { "x-csrf-token": sessions[identity].csrf_token },
  });
  return resp;
}
```

This pattern is consistent with the existing helpers in the spec and requires no changes to the session setup script.
