# GAP-0187: `validate_promo_code` Returns Generic `message` Strings With No Machine-Readable `error_code` — Remediation Write-up

> Source ticket: FIN-002 · Severity: HIGH · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** Every failure path in `validate_promo_code`
(`app/services/promo_codes.py:251–332`) returns a `fail` dict that contains only a
human-readable `message` string. No `error_code` key is present in the dict, and
`PromoValidateOut` (the Pydantic model at `app/models.py:3318–3325`) does not declare
an `error_code` field either. The frontend — specifically `Checkout.tsx:116` — has no
choice but to surface the raw human string as the error: it calls
`result.message ?? "Invalid code"`. Future surfaces (subscription upgrade flow,
messaging tip/unlock checkout, a mobile app) cannot programmatically distinguish
"expired" from "already used" or "wrong creator" without screen-scraping the English
string.

**Verdict: Confirmed.** Reading `app/services/promo_codes.py:251–332` confirms all
eight distinct failure paths (`not found / deactivated`, `expired`, `usage_limit`,
`already_used`, `checkout_type_mismatch`, `product_mismatch / creator_scope`,
`free_trial_on_non_sub`, and `min_order`) set `fail["message"]` but never set
`fail["error_code"]`. The `PromoValidateOut` model at `app/models.py:3318` has no
`error_code` field, and the TypeScript interface `PromoValidateOut` at
`frontend/src/api/types.ts:3959` likewise omits it.

**Severity and area.** HIGH / Billing & Promo (FIN-002). The immediate consequence is
that the frontend can only display the exact English string supplied by the backend; it
cannot conditionally render a "Renew subscription for full discount" call-to-action when
the error is `already_used`, or offer a "Try a different payment amount" hint when the
error is `min_order`. Any i18n effort is also blocked: the translation key must be
derived from a stable code string, not from the English message itself.

**Related tickets.** GAP-0186 (extends `PromoValidateOut` with `error_code` and other
fields — the two fixes are siblings and should ship together). GAP-0188 (tip/unlock
checkout types — will add `checkout_type_mismatch` as a first-class error). No other
blocking dependencies.

## 2. Current-State Investigation (root cause)

### Fail-dict initialisation: `app/services/promo_codes.py:251–259`

```python
fail = {
    "valid": False,
    "code_id": None,
    "discount_type": None,
    "discount_cents": 0,
    "final_price_cents": item_price_cents,
    "free_trial_days": 0,
    "message": None,
}
```

`error_code` is absent from every `fail` return and from every branch that mutates it.

### The eight failure branches (lines 261–319)

| Line range | Condition | `message` set | `error_code` |
|-----------|-----------|---------------|--------------|
| 261–264 | code not found or `active=False` | `"Code not found"` | absent |
| 269–273 | `expires_at < now` | `"This code has expired"` | absent |
| 276–281 | `current_uses >= max_uses` | `"This code has been fully redeemed"` | absent |
| 284–291 | per-user redeems >= `max_uses_per_user` | `"You have already used this code"` | absent |
| 293–298 | `checkout_type not in applies_to` | `"This code does not apply to this checkout type"` | absent |
| 300–304 | `creator_user_id` mismatch | `"This code is not valid for this creator"` | absent |
| 306–311 | `free_trial` on non-subscription | `"Free trial codes are only valid for subscriptions"` | absent |
| 313–319 | `item_price_cents < min_purchase_cents` | `"Minimum purchase of $X.XX required"` | absent |

The `"Code not found"` branch conflates two distinct states: the code string does not
exist at all in DynamoDB, and the code exists but was soft-deactivated (`active=False`).
The `get_promo_code_by_string` lookup (`line 261`) returns the item regardless of
`active` state; the `active` flag is checked immediately after. Separating these into
`not_found` vs `deactivated` error codes is therefore straightforward.

### Router: `app/routers/promo_codes.py:154`

```python
return PromoValidateOut(**result)
```

Even if `validate_promo_code` were patched to return `error_code` in the `fail` dict,
Pydantic would silently drop the key because `PromoValidateOut` does not declare the
field. The model fix from GAP-0186 is a prerequisite.

### Frontend: `Checkout.tsx:116`

```typescript
setPromoError(result.message ?? "Invalid code");
```

The only discriminator available to the frontend is the English string in `message`.
Any conditional rendering (e.g., "Add $X more to use this code" for `min_order`) is
impossible without parsing the string.

### Dev vs prod parity

`validate_promo_code` is pure DynamoDB; there is no dev-mode / mock branch in the
function. The absence of `error_code` is identical in both environments.

## 3. Impact / Exploit / Blast Radius

**UX degradation.** Error messages are surfaced verbatim to the user. Changing the
English text of a server error (e.g. in a copy-editing pass) silently breaks any client
that has a string match against the old message.

**i18n blockage.** Internationalising promo error messages requires a stable key.
Without `error_code`, the translation layer must key off the English string, which is
fragile and easy to break with a server-side change.

**Frontend extensibility blocked.** Contextual recovery actions — "Add $X to qualify",
"This code is for subscriptions only — go to subscriptions" — require knowing which
specific error class was returned. None of these are implementable against free-text
messages without regex or string matching.

**Downstream API consumers.** Any third-party integration or mobile client that calls
`/ui/promo-codes/validate` (e.g. an affiliate checkout embed) has the same limitation.
A machine-readable `error_code` is the standard contract for programmatic error
handling.

**No security or financial exploit.** The gap does not expose confidential information;
the human-readable messages do not reveal internal state that a bad actor could exploit.
The impact is developer-experience and frontend capability.

## 4. Fix Design (code-level)

### Prerequisite: add `error_code` field to `PromoValidateOut` (see GAP-0186)

Both GAP-0186 and GAP-0187 extend the same model. The combined model after both fixes:

```python
class PromoValidateOut(BaseModel):
    valid: bool
    code_id: Optional[str] = None
    discount_type: Optional[str] = None
    discount_cents: int = 0
    discount_pct: Optional[int] = None
    original_price_cents: int = 0
    final_price_cents: int = 0
    free_trial_days: int = 0
    buy_x: Optional[int] = None
    get_y: Optional[int] = None
    free_item_description: Optional[str] = None
    error_code: Optional[str] = None            # ← this fix
    message: Optional[str] = None
```

### Step 1 — Extend the `fail` dict initialiser (`app/services/promo_codes.py:251`)

```python
fail = {
    "valid": False,
    "code_id": None,
    "discount_type": None,
    "discount_cents": 0,
    "discount_pct": None,
    "original_price_cents": item_price_cents,
    "final_price_cents": item_price_cents,
    "free_trial_days": 0,
    "buy_x": None,
    "get_y": None,
    "free_item_description": None,
    "error_code": None,   # ← will be set by each branch
    "message": None,
}
```

### Step 2 — Add `error_code` to every failure branch

```python
# not found (code does not exist)
if not promo:
    fail["message"] = "Code not found"
    fail["error_code"] = "not_found"
    return fail

# deactivated (code exists but active=False)
if not promo.get("active", True):
    fail["message"] = "This code is no longer active"
    fail["error_code"] = "deactivated"
    fail["code_id"] = promo["code_id"]
    return fail

# expired
if exp > 0 and exp < ts:
    fail["message"] = "This code has expired"
    fail["error_code"] = "expired"
    fail["code_id"] = promo["code_id"]
    return fail

# usage limit exhausted
if max_uses > 0 and current >= max_uses:
    fail["message"] = "This code has been fully redeemed"
    fail["error_code"] = "usage_limit"
    fail["code_id"] = promo["code_id"]
    return fail

# per-user limit
if len(user_redeems) >= max_per:
    fail["message"] = "You have already used this code"
    fail["error_code"] = "already_used"
    fail["code_id"] = promo["code_id"]
    return fail

# checkout type mismatch
if checkout_type not in applies:
    fail["message"] = "This code does not apply to this checkout type"
    fail["error_code"] = "checkout_type_mismatch"
    fail["code_id"] = promo["code_id"]
    return fail

# creator / product scope mismatch
if promo["creator_user_id"] != creator_user_id:
    fail["message"] = "This code is not valid for this creator"
    fail["error_code"] = "product_mismatch"
    fail["code_id"] = promo["code_id"]
    return fail

# free_trial on non-subscription
if dtype == "free_trial" and checkout_type != "subscription":
    fail["message"] = "Free trial codes are only valid for subscriptions"
    fail["error_code"] = "checkout_type_mismatch"
    fail["code_id"] = promo["code_id"]
    return fail

# minimum order not met
if min_cents > 0 and item_price_cents < min_cents:
    dollars = min_cents / 100
    fail["message"] = f"Minimum purchase of ${dollars:.2f} required"
    fail["error_code"] = "min_order"
    fail["code_id"] = promo["code_id"]
    return fail
```

Note: the current code checks `not promo or not promo.get("active", True)` in a single
condition at line 262. Splitting this into two conditions (one for `not promo`, one for
`active=False`) is required to assign the correct `error_code` and is safe because
`promo.get("active")` is only accessed when `promo` is truthy.

### Step 3 — Add `error_code` to the success return dict

```python
return {
    "valid": True,
    "code_id": promo["code_id"],
    "discount_type": dtype,
    "discount_cents": discount_cents,
    "discount_pct": discount_pct,
    "original_price_cents": item_price_cents,
    "final_price_cents": final_price,
    "free_trial_days": trial_days,
    "buy_x": buy_x,
    "get_y": get_y,
    "free_item_description": free_item_desc,
    "error_code": None,   # null on success
    "message": None,
}
```

### Step 4 — Frontend update (`Checkout.tsx` and `types.ts`)

Update `frontend/src/api/types.ts` (shared with GAP-0186):

```typescript
export interface PromoValidateOut {
  ...
  error_code: string | null;
  message: string | null;
}
```

Update `Checkout.tsx:116` to use `error_code` for UI branching when present, falling
back to `message` for unknown codes:

```typescript
const errMsg = result.error_code === "min_order"
  ? `Add more items to qualify (min: ${formatCents(result.original_price_cents)})`
  : result.error_code === "already_used"
  ? "You've already used this code"
  : result.message ?? "Invalid code";
setPromoError(errMsg);
```

### Dev/Prod parity (SECOPS-007)

`validate_promo_code` has no dev-mode branch. The error-code additions are inserted
into the pure-logic layer and apply identically to the local DynamoDB mock and AWS
DynamoDB in production. The `promo_codes_enabled` feature flag at
`app/core/settings.py:1797` still gates the entire feature; no new flag is needed.

### Backward compatibility

`error_code` is `Optional[str] = None` in the model. Existing callers that only read
`message` will receive `error_code: null` in JSON and can safely ignore it. The English
`message` strings are unchanged on all existing branches, so no old clients are broken.
The only behavioural change is the split of the single `not found / deactivated` branch
into two, which changes the English message for the `deactivated` case from `"Code not
found"` to `"This code is no longer active"` — a clearer message that is acceptable to
change.

## 5. Testing, Verification & Rollout

### Regression tests (pytest, fails-before / passes-after)

```python
@pytest.mark.parametrize("scenario,expected_code", [
    ("nonexistent_code", "not_found"),
    ("deactivated_code", "deactivated"),
    ("expired_code", "expired"),
    ("usage_limit_exhausted", "usage_limit"),
    ("already_used_by_user", "already_used"),
    ("wrong_checkout_type", "checkout_type_mismatch"),
    ("wrong_creator", "product_mismatch"),
    ("below_min_order", "min_order"),
])
def test_validate_promo_error_code(client, promo_fixtures, auth_headers,
                                   scenario, expected_code):
    req = promo_fixtures[scenario]
    resp = client.post("/ui/promo-codes/validate", json=req, headers=auth_headers)
    data = resp.json()
    assert data["valid"] is False
    # Fails before fix: "error_code" key absent (KeyError) or None where string expected
    assert data["error_code"] == expected_code
    # message must still be non-empty (human readable)
    assert data["message"]

def test_validate_promo_success_error_code_is_null(client, promo_fixtures, auth_headers):
    req = promo_fixtures["valid_shop_code"]
    resp = client.post("/ui/promo-codes/validate", json=req, headers=auth_headers)
    data = resp.json()
    assert data["valid"] is True
    assert data["error_code"] is None
```

**Fails before:** `data["error_code"]` raises `KeyError` because `PromoValidateOut`
strips unknown keys before serialisation and `validate_promo_code` never populates it.

**Passes after:** both the service dict and the model carry `error_code`; Pydantic
serialises it.

### Manual QA

1. Start dev stack (`just up`).
2. Create a promo code with `max_uses=1`. Apply it once as Alice: confirm the response
   has `valid: true` and `error_code: null`. Apply it a second time: confirm
   `error_code: "already_used"` in the browser devtools response JSON.
3. Create a code with a short `expires_at` (or seed one in the past directly via
   DynamoDB Local admin or `rootctl`): apply it, confirm `error_code: "expired"` and
   the UI error message reads "This code has expired".
4. Apply a code with `applies_to=["subscription"]` from the shop checkout (`checkout_type="shop"`):
   confirm `error_code: "checkout_type_mismatch"`.
5. Soft-deactivate a code: confirm `error_code: "deactivated"` is distinct from
   `"not_found"` (the single-branch fix for the `not promo or not active` check).
6. Apply a code from a different creator's scope: confirm `error_code: "product_mismatch"`.
7. Apply a code with `min_purchase_cents=10000` against a $20 cart: confirm
   `error_code: "min_order"`.
8. For each error case: confirm the `message` field is non-empty (the human-readable
   string must be present alongside `error_code`, as older clients rely on it).
9. For the success case: confirm `error_code: null` in the response body (the field
   should be explicitly serialised as `null`, not omitted).

### Observability

Add a Prometheus counter increment in the router or service keyed on `error_code` so
the ops team can track which promo failure reasons are most common:

```python
PROMO_VALIDATE_FAILURE.labels(error_code=result.get("error_code") or "unknown").inc()
```

This counter can be added to `app/metrics.py` alongside the existing billing metrics.

### Rollout and risks

- **Effort:** S (eight one-line additions in `promo_codes.py`; one model field; one
  TypeScript type line; optional frontend UX improvement).
- **Risk:** Very low. All changes are additive; English messages are preserved on
  all branches except the `deactivated` sub-case (deliberate improvement).
- **Sequencing:** Ship with GAP-0186 in the same PR (both touch `PromoValidateOut` and
  the `fail` dict). GAP-0188 (tip/unlock) can follow; the `checkout_type_mismatch` code
  will already exist when those checkout types are added.
- **Rollback:** Remove `error_code` from the model and service dicts; frontend falls
  back to raw `message`.
