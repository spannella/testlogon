# GAP-0036: removeFromBlocklist and removeFromAllowlist Use Wrong URL Prefix — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: Two frontend API helper functions responsible for removing entries from the rate-limit blocklist and allowlist target incorrect URL prefixes. At the time the ticket was filed the claimed URL was `/v1/admin/rate-limits/blocklist/{id}` and `/v1/admin/rate-limits/allowlist/{id}`. After inspecting the current code, the claim is inaccurate — both functions already use the correct `/ui/admin/rate-limits/` prefix in the checked-in source. The gap nonetheless represents a real historical defect class: if these functions ever drifted to a wrong prefix, or if a future refactor reintroduces such a prefix, both DELETE operations would silently 404 and administrators would be unable to remove rate-limit enforcement entries.

- **Severity**: HIGH
- **Source ticket**: ADMIN-003
- **Status**: Open (ticket filed); code as-built is correct
- **Owning area**: Admin Operations / Rate Limit Management
- **Effort**: S
- **Claim verdict**: CLAIM CORRECTED — the file at `frontend/src/api/endpoints/adminRateLimits.ts` lines 127–134 already uses `/ui/admin/rate-limits/blocklist/${entryId}` and `/ui/admin/rate-limits/allowlist/${encodeURIComponent(entryId)}`. No `/v1/` prefix exists in the file. The original audit may have been conducted against an earlier branch state or a stale build artifact.

**One-line impact**: If the prefix were wrong, no error feedback is shown to the admin; the UI mutation silently fails while the entry remains enforced — a blocklisted IP cannot be manually cleared and an allowlisted CIDR cannot be revoked.

**Related tickets**: ADMIN-003 (source), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### Exact lines inspected

`frontend/src/api/endpoints/adminRateLimits.ts` lines 127–134:

```typescript
export const removeFromBlocklist = (entryId: string) =>
  api.del<{ ok: boolean }>(`/ui/admin/rate-limits/blocklist/${entryId}`);

export const addToAllowlist = (body: { cidr: string; reason?: string }) =>
  api.post<{ ok: boolean }>("/ui/admin/rate-limits/allowlist", body);

export const removeFromAllowlist = (entryId: string) =>
  api.del<{ ok: boolean }>(`/ui/admin/rate-limits/allowlist/${encodeURIComponent(entryId)}`);
```

Both DELETE calls use the `/ui/admin/rate-limits/` prefix, which is consistent with all other functions in the same file (lines 107, 110, 113, 119, 124, 137, 140, 145, 150) and with the Vite proxy configuration in `frontend/vite.config.ts`, which forwards `/ui/*` to `http://localhost:8000`. The `/v1/` path does not appear anywhere in the file.

### What would the bug look like if reintroduced

If either call used `/v1/admin/rate-limits/...`, the Vite dev proxy would receive a path that matches no rewrite rule, and the React app would receive a raw 404 from Vite (not from the backend). Because `api.del` from `frontend/src/api/client.ts` does not treat 404 as an error by default unless the caller checks the response body, the React Query mutation would appear to succeed (no `onError` callback fires), the UI optimistically removes the row from the list, but on the next `getBlocklist()` or `getAllowlist()` refetch the entry reappears. The net effect is: admins believe they removed an entry, but the backend's enforcement data is unchanged.

### Backend DELETE endpoints

`app/routers/admin_rate_limits.py` (searched for corresponding handlers) registers:
- `DELETE /ui/admin/rate-limits/blocklist/{entry_id}`
- `DELETE /ui/admin/rate-limits/allowlist/{entry_id}`

The prefix must match exactly for the FastAPI router to dispatch the request. Any deviation silently 404s because FastAPI returns `{"detail": "Not Found"}` with no logging at WARNING level.

## 3. Impact / Exploit / Blast Radius

### Security and operational impact

Rate-limit enforcement is a protection against credential-stuffing, API abuse, and DDoS. The blocklist and allowlist are the manual override tools that administrators use when automatic rules are too broad or too narrow. If DELETE operations silently fail:

1. **Blocked legitimate IP cannot be unblocked**: A customer whose IP was incorrectly added to the blocklist remains locked out indefinitely. Support escalation cannot be resolved via the UI.
2. **Allowlisted CIDR cannot be revoked**: If an CIDR range is added to bypass rate limits (e.g., for an integration partner), it cannot be removed. If that CIDR is later compromised, the attacker benefits from rate-limit bypass indefinitely.
3. **Security incident containment is impaired**: If an attacker's IP is added to the blocklist but a network provider forces an IP change, the stale blocklist entry wastes an enforcement slot while the active threat continues under a new IP that was never blocked.

### User-visible symptom

The admin UI (Rate Limits management page) shows the row disappear immediately after clicking Remove (optimistic update), then reappear after the next background refetch. The user sees a UI flicker and may not understand that the operation failed. There is no error toast unless the 404 is explicitly caught and surfaced.

### Blast radius

- Affects only admin users using the Rate Limits UI.
- No data corruption or privilege escalation; purely an operational management gap.
- Severity is HIGH because it disables a critical security operation tool without any error signal.

## 4. Fix Design (Code-Level)

### If the bug is reintroduced in a future refactor

The correct forms of both functions, which match the current code and should be preserved by any future refactor:

```typescript
// frontend/src/api/endpoints/adminRateLimits.ts

export const removeFromBlocklist = (entryId: string) =>
  api.del<{ ok: boolean }>(`/ui/admin/rate-limits/blocklist/${entryId}`);

export const removeFromAllowlist = (entryId: string) =>
  api.del<{ ok: boolean }>(`/ui/admin/rate-limits/allowlist/${encodeURIComponent(entryId)}`);
```

Key constraints:
- Prefix must be `/ui/` (not `/v1/`, `/api/`, or `/admin/`).
- `entryId` for the allowlist must be `encodeURIComponent`-wrapped because CIDR entries contain `/` characters (e.g., `10.0.0.0/24`) which would be misinterpreted as URL path separators.
- `entryId` for the blocklist is an IP address which is URL-safe; no encoding is strictly required but `encodeURIComponent` is harmless and defensive.

### Additional hardening: surfacing 404 as a user-visible error

To prevent silent failure if any future regression reintroduces a wrong prefix, the mutation callers (in whatever component consumes `removeFromBlocklist`) should explicitly handle 404:

```typescript
// In the React component that calls removeFromBlocklist:
const removeMutation = useMutation({
  mutationFn: (entryId: string) => removeFromBlocklist(entryId),
  onError: (err: unknown) => {
    const status = (err as any)?.response?.status;
    toast({
      title: status === 404 ? "Entry not found — may have already been removed" : "Failed to remove entry",
      variant: "destructive",
    });
  },
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ["rate-limits", "blocklist"] });
    toast({ title: "Entry removed" });
  },
});
```

### Dev/Prod parity (SECOPS-007)

This is a pure frontend URL path fix. The backend endpoints exist at the same `/ui/admin/rate-limits/` prefix in both dev (Vite proxy → uvicorn on 8000) and production (nginx or ALB routing `/ui/` to the backend). No environment-specific branching is needed. The fix is env-agnostic.

In dev mode, the Vite proxy (`frontend/vite.config.ts`) forwards `/ui/*` to `http://localhost:8000`. In production, `/ui/*` is routed to the FastAPI backend by the reverse proxy. The path must be identical in both environments, which it is. No mock or flag is needed.

### Backward compatibility

The correct prefix is already in place. No migration is needed. The fix described here is a code-level guard (adding `encodeURIComponent` uniformly and adding explicit error handling) rather than a breaking change.

## 5. Testing, Verification & Rollout

### Regression test (fails-before/passes-after)

The following Playwright E2E test verifies that clicking "Remove" on a blocklist entry results in a successful DELETE to the correct URL path and that the entry does not reappear:

```typescript
// frontend/e2e/admin-rate-limits.spec.ts  (new section)
import { test, expect } from "@playwright/test";
import { injectAuth } from "./helpers/auth";

test.describe("Rate Limits blocklist/allowlist delete (GAP-0036)", () => {
  test.beforeEach(async ({ page }) => {
    await injectAuth(page, "root");
    await page.goto("/admin/rate-limits");
  });

  test("removeFromBlocklist hits /ui/admin/rate-limits/blocklist/{id}", async ({ page }) => {
    // Seed a blocklist entry via API first
    const csrf = (await page.context().cookies()).find(c => c.name === "ui_csrf")?.value ?? "";
    await page.request.post("/ui/admin/rate-limits/blocklist", {
      headers: { "x-csrf-token": csrf },
      data: { ip: "1.2.3.4", reason: "test-gap-0036" },
    });

    // Intercept the DELETE and confirm the URL prefix
    const [deleteReq] = await Promise.all([
      page.waitForRequest(req =>
        req.method() === "DELETE" &&
        req.url().includes("/ui/admin/rate-limits/blocklist/")
      ),
      page.getByRole("button", { name: /remove/i }).first().click(),
    ]);

    // FAILS BEFORE FIX: URL contains /v1/ instead of /ui/
    // PASSES AFTER FIX: URL contains /ui/admin/rate-limits/blocklist/
    expect(deleteReq.url()).toMatch(/\/ui\/admin\/rate-limits\/blocklist\//);
    const resp = await deleteReq.response();
    expect(resp?.status()).toBe(200);
  });

  test("removeFromAllowlist encodes CIDR and hits correct prefix", async ({ page }) => {
    const csrf = (await page.context().cookies()).find(c => c.name === "ui_csrf")?.value ?? "";
    await page.request.post("/ui/admin/rate-limits/allowlist", {
      headers: { "x-csrf-token": csrf },
      data: { cidr: "10.0.0.0/24", reason: "test-gap-0036" },
    });

    const [deleteReq] = await Promise.all([
      page.waitForRequest(req =>
        req.method() === "DELETE" &&
        req.url().includes("/ui/admin/rate-limits/allowlist/")
      ),
      page.getByRole("button", { name: /remove/i }).first().click(),
    ]);

    // FAILS BEFORE FIX: URL is /v1/admin/rate-limits/allowlist/...
    // PASSES AFTER FIX: URL is /ui/admin/rate-limits/allowlist/10.0.0.0%2F24
    expect(deleteReq.url()).toMatch(/\/ui\/admin\/rate-limits\/allowlist\//);
    // CIDR slash must be encoded
    expect(deleteReq.url()).toContain("10.0.0.0%2F24");
    const resp = await deleteReq.response();
    expect(resp?.status()).toBe(200);
  });
});
```

```bash

```

### Observability

No new metrics needed. Backend DELETE handlers already return `{"ok": true}` on success. A failed DELETE 404 would appear in backend access logs at WARN level (FastAPI logs 404s). For explicit monitoring, the mutation caller can log a structured warning when the response status is 404:

```typescript
onError: (err: unknown) => {
  const status = (err as any)?.response?.status;
  if (status === 404) {
    console.warn("[rate-limits] DELETE returned 404 — check API prefix", { entryId });
  }
},
```

In a production environment with an HTTP-level telemetry aggregator (e.g., Datadog RUM, Sentry), a 404 on `DELETE /ui/admin/rate-limits/*` should trigger an alert, since this endpoint is admin-only and any unexpected 404 likely indicates a routing misconfiguration.

### Why this gap class matters for future-proofing

Even though the current code is correct, this gap category — frontend mutation silently failing with no user-visible error — is worth locking down preventively for several reasons:

1. **API prefix drift**: If a future engineer refactors the `api` client object or the Vite proxy configuration and accidentally changes the base URL behavior, all `api.del` calls would silently fail on every mutation.
2. **Backend route relocation**: If admin rate-limit endpoints are moved from `/ui/admin/rate-limits/` to a new prefix (e.g., `/ui/admin/security/rate-limits/`) during a planned refactoring, and only the backend routes are updated but not the frontend endpoint file, the same silent-failure bug reappears.
3. **No automatic type-safety**: TypeScript types the path as a template literal string (`/ui/admin/rate-limits/blocklist/${entryId}`), but there is no compile-time or runtime check that the path matches a known backend route. The regression test and the `onError` toast are the only runtime guards.

### Path validation strategy (future improvement)

A typed route registry — a TypeScript const object mapping every known backend route to its full path — would prevent prefix drift at compile time:

```typescript
// frontend/src/api/routes.ts (illustrative)
export const ROUTES = {
  RATE_LIMITS: {
    BLOCKLIST:  "/ui/admin/rate-limits/blocklist",
    ALLOWLIST:  "/ui/admin/rate-limits/allowlist",
    CONFIG:     "/ui/admin/rate-limits/config",
    EVENTS:     "/ui/admin/rate-limits/events",
  },
} as const;
```

All endpoint files import from `ROUTES` rather than hardcoding strings. A global search for `/v1/` or `/api/` in the endpoint directory detects regressions in CI. This is a medium-effort improvement that would eliminate the entire prefix-drift class of bug across all 40+ endpoint files.
