# GAP-0018: Unvalidated `RelayState` Open Redirect (SAML ACS) — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real file:line. Built on the verified investigation at
> `docs/tickets/gap-tickets/investigations/GAP-0018.md`.

## 1. Summary & Classification

**Plain-English statement**: The SAML Assertion Consumer Service (ACS) endpoint in
`app/routers/sso_saml.py` reads the `RelayState` value from the POST form body and redirects
the browser to it unconditionally after a successful authentication. No validation checks
whether the URL is same-origin. Any value — including `https://attacker.example.com/steal` —
is accepted. This is a classic open-redirect (CWE-601) with full session-cookie disclosure
risk.

- **Severity**: CRIT
- **Source ticket**: ENTERPRISE-002
- **Status**: Open
- **Owning area**: Backend / SSO / Security
- **Verdict**: **Confirmed** — lines 212 and 568 of `app/routers/sso_saml.py` redirect to
  an unvalidated `relay_state` value in both the production path and the dev-bypass path.
- **One-line impact**: An attacker with control over the SAML response or the ACS POST can
  redirect authenticated users to an arbitrary external domain and harvest session cookies.
- **Related tickets**: SEC-011 (open-redirect host header — independently cites the same
  lines), ENTERPRISE-002 (source feature), GAP-0175 (relay-state carries attacker-controlled
  form field).

---

## 2. Current-State Investigation (Root Cause)

### The vulnerable ACS handler

`app/routers/sso_saml.py:75-78` reads `RelayState` from the unvalidated POST form:

```python
form = await request.form()
saml_response_b64 = form.get("SAMLResponse")
relay_state = form.get("RelayState", "/")     # line 78 — attacker-controlled
tenant_id = str(form.get("tenant_id", "default"))
```

After SAML response validation succeeds (XML signature check, audience restriction, etc.),
the server sets session cookies and issues the redirect at line 212:

```python
redirect = RedirectResponse(url=str(relay_state or "/"), status_code=303)
set_session_cookies(redirect, session)
```

`relay_state` is used as-is. `str(relay_state or "/")` cannot produce a safe URL from
attacker-controlled input: `str("https://evil.com")` == `"https://evil.com"`.

### The dev-bypass path is equally vulnerable

`app/routers/sso_saml.py:546-568` (`_dev_bypass_acs`) accepts `relay_state` as a parameter
(it is passed from the same form at line 92) and uses it identically at line 568:

```python
redirect = RedirectResponse(url=relay_state or "/", status_code=303)
```

The dev-bypass path skips SAML XML parsing entirely (it trusts the `X-User-Sub` header),
making exploitation trivially easy in any environment where `S.dev_mode = True`.

### Why no existing guard catches this

1. The SAML library validates only the `SAMLResponse` XML blob — it has no opinion about
   `RelayState`, which is an opaque application value in the SAML spec.
2. `FastAPI`'s `RedirectResponse` accepts any string as a URL.
3. `set_session_cookies` attaches `ui_session`, `ui_csrf`, and `ui_access_token` cookies
   to the redirect response — these ride along to the attacker's domain as `Set-Cookie`
   headers in the 303 response.
4. No middleware validates the `Location` header of outgoing responses.

### SEC-011 cross-reference

`docs/tickets/SEC-011-open-redirect-host-header.md` explicitly cites `sso_saml.py:78,212`
as the open-redirect location using the same attack vector. GAP-0018 and SEC-011 are
duplicate findings; fixing GAP-0018 resolves SEC-011's RelayState concern simultaneously.

## 3. Impact / Exploit / Blast Radius

### Concrete exploit walkthrough

**Preconditions**: The target organisation uses SAML SSO (any IdP). The attacker knows the
ACS URL (it is published in SP metadata, typically `/saml/acs`).

**Step 1 — Craft the malicious POST**

The attacker creates a web page that auto-submits a form:

```html
<form action="https://platform.example.com/saml/acs" method="POST">
  <input type="hidden" name="SAMLResponse" value="<valid_saml_response>">
  <input type="hidden" name="RelayState" value="https://attacker.example.com/steal">
</form>
<script>document.forms[0].submit();</script>
```

A "valid SAMLResponse" can be obtained if:
- The attacker controls a trusted IdP (e.g., they are an enterprise tenant admin).
- The attacker intercepted a legitimate authentication (XML signature replay if the clock
  tolerance is wide).
- In dev mode with `dev_bypass=1`, no SAMLResponse is validated at all.

**Step 2 — Server issues 303 to attacker domain**

The server validates the SAMLResponse, creates a session, attaches `Set-Cookie` headers to
the `RedirectResponse`, and returns:

```
HTTP/1.1 303 See Other
Location: https://attacker.example.com/steal
Set-Cookie: ui_session=...; HttpOnly; Secure
Set-Cookie: ui_csrf=...; Secure
Set-Cookie: ui_access_token=...; HttpOnly; Secure
```

**Step 3 — Browser follows redirect**

The browser follows the redirect to `https://attacker.example.com/steal`. The cookies are
`HttpOnly` so JavaScript on the attacker page cannot read them directly, but the attacker
can now issue cross-origin requests to the platform using the browser as a proxy (CSRF).
More practically, the `ui_csrf` cookie is NOT HttpOnly — it is readable by JavaScript on
the attacker's origin if the browser follows the redirect and the attacker can induce further
navigation back to the platform.

**Step 4 — Phishing amplification**

Even without direct cookie theft, the victim is now on the attacker's page with a valid
session established. The attacker page can display a phishing UI ("Enter your 2FA code to
continue") while the session cookie is being used from the attacker's server.

### Severity assessment

- **CVSS score**: ~8.2 (High) — network-accessible, low privileges required (any SAML-
  configured tenant), no user interaction beyond clicking a link.
- In dev mode with `dev_bypass=1`, the attack requires zero valid SAML credentials.
- All enterprise SSO tenants are affected.

## 4. Fix Design (Code-Level)

### 4.1 Add `_safe_relay_state()` validator

In `app/routers/sso_saml.py`, add a validator before the first use of `relay_state`. It
should live near the top of the file after the imports:

```python
from urllib.parse import urlparse

def _safe_relay_state(relay_state: str | None) -> str:
    """Return relay_state if it is a safe same-origin path; otherwise return '/'.

    Accepts:
      - Empty / None → "/"
      - Relative paths starting with "/" (but not "//") → unchanged
    Rejects:
      - Protocol-relative URLs ("//evil.com/...")
      - Absolute URLs whose host differs from S.public_base_url
      - Any value that raises during parsing
    """
    if not relay_state:
        return "/"
    rs = str(relay_state).strip()
    if rs.startswith("//"):
        # Protocol-relative URL — always a redirect to an external host.
        return "/"
    if not rs.startswith("/"):
        # Absolute URL: parse and compare netloc.
        try:
            parsed = urlparse(rs)
            allowed = urlparse(S.public_base_url)
            if parsed.netloc != allowed.netloc:
                return "/"
        except Exception:
            return "/"
    return rs
```

### 4.2 Replace both redirect sites

**Line 212 (main ACS path)**:

```python
# Before:
redirect = RedirectResponse(url=str(relay_state or "/"), status_code=303)

# After:
redirect = RedirectResponse(url=_safe_relay_state(relay_state), status_code=303)
```

**Line 568 (`_dev_bypass_acs`)**:

```python
# Before:
redirect = RedirectResponse(url=relay_state or "/", status_code=303)

# After:
redirect = RedirectResponse(url=_safe_relay_state(relay_state), status_code=303)
```

That is the complete change: one new function (~20 lines) and two one-line substitutions.

### 4.3 Edge cases handled by the validator

| Input | Output | Reason |
|---|---|---|
| `None` | `/` | Default |
| `""` | `/` | Default |
| `/dashboard` | `/dashboard` | Safe relative path |
| `/messages/conv_123` | `/messages/conv_123` | Safe relative path |
| `https://platform.example.com/dashboard` | `/dashboard`* | Same host, strip origin |
| `https://evil.com/steal` | `/` | Different host — rejected |
| `//evil.com/steal` | `/` | Protocol-relative — rejected |
| `javascript:alert(1)` | `/` | Non-`/`-starting non-http(s) — rejected |

*Optionally, the function can strip the origin for same-host absolute URLs and return the
path only, for cleanliness. The simplest safe behavior is to return `/` for any absolute
URL, requiring callers to use relative paths.

### 4.4 Dev/Prod parity (SECOPS-007)

`S.public_base_url` is defined in `app/core/settings.py:324`:

```python
public_base_url: str = os.environ.get("PUBLIC_BASE_URL", "http://localhost:8000").rstrip("/")
```

In dev, this resolves to `http://localhost:8000`; in prod, it is the configured public
hostname. The validator uses `S.public_base_url` in both environments with no branch, so
there is no dev/prod divergence. `.env.local.example` already has `PUBLIC_BASE_URL` set.

The fix is purely input validation — no new AWS calls, no new table schema, no environment
flags. SECOPS-007 has no additional requirements for this change.

### 4.5 Alternatives considered

- **HMAC-sign the RelayState at SP-initiated login time**: This is the most secure
  approach — the SP generates the RelayState, signs it with a secret, and the ACS validates
  the signature. Rejected for this ticket because it requires changes to the SP-initiated
  login flow (`/saml/login`), increases complexity, and the URL allowlist is sufficient for
  CWE-601 mitigation.
- **Store RelayState in the session before redirect**: Avoids passing it through the IdP
  entirely. Adds a DynamoDB write; rejected as over-engineering for an S-effort fix.
- **Reject all non-relative RelayState values**: Simpler but breaks legitimate
  absolute-URL RelayState values that some IdPs generate (e.g., ADFS issues the full SP
  URL). The validator's host-comparison approach handles this correctly.

    """External RelayState must be rejected and replaced with '/'."""
    resp = await async_client.post(
        "/saml/acs?dev_bypass=1",

### Rollout

- **Zero downtime**: The change is a pure input validation; no schema or session changes.
- **Backward compat**: Any SP-initiated flow that stores the full absolute URL as RelayState
  (e.g., `https://platform.example.com/dashboard`) will land on `/` after the fix. If this
  is a concern, extend `_safe_relay_state` to strip the origin from same-host absolute URLs
  rather than returning `/`.

### Relationship to GAP-0175

GAP-0175 documents that `relay_state` carries an attacker-controlled form field — a finding
that overlaps directly with this GAP. The distinction is:

- **GAP-0018** focuses on the *redirect destination* being unvalidated (CWE-601 — open
  redirect).
- **GAP-0175** may focus on the `relay_state` being passed as a POST form parameter that an
  attacker can inject via a CSRF or SAML-response-forgery mechanism (CWE-352/CWE-918).

Both are resolved by the same `_safe_relay_state()` validator. Once GAP-0018 is fixed,
GAP-0175 should be re-evaluated to confirm no additional remediation is needed.

### HMAC-signed RelayState as a defence-in-depth upgrade

While the allowlist validator is sufficient for CWE-601, a higher-assurance mitigation
is to HMAC-sign the RelayState when the SP initiates the login, and verify the signature
at ACS time. This prevents any attacker-injected RelayState from being trusted, even if it
passes the origin check:

```python
# In /saml/login (SP-initiated):
import hmac, hashlib, base64
relay_state_raw = request.query_params.get("relay_state", "/")
safe_rs = _safe_relay_state(relay_state_raw)
sig = hmac.new(S.ui_access_token_secret.encode(), safe_rs.encode(), hashlib.sha256).digest()
signed_rs = safe_rs + "." + base64.urlsafe_b64encode(sig).decode()
# Pass signed_rs as the RelayState to the IdP

# In /saml/acs (ACS handler):
# Split signed_rs, verify HMAC, extract original path
```

This approach eliminates reliance on `S.public_base_url` for origin comparison and is
immune to subdomain-takeover attacks where an attacker controls a subdomain of the platform
domain. It is recommended as a follow-up hardening step after the immediate fix.

### Affected endpoint inventory

Both redirect sites must be patched in the same commit to avoid a partial fix where one path
is validated and the other is not. The two locations:

| File | Line | Code | Path |
|---|---|---|---|
| `app/routers/sso_saml.py` | 212 | `RedirectResponse(url=str(relay_state or "/"), ...)` | Production ACS |
| `app/routers/sso_saml.py` | 568 | `RedirectResponse(url=relay_state or "/", ...)` | Dev-bypass ACS |

A code review checklist item should also verify that no other files in `app/routers/` or
`app/services/` construct a `RedirectResponse` from user-supplied data. A one-time scan:

```bash
grep -rn "RedirectResponse" app/ | grep -v "url=\"/"
```

Any hit where the `url=` argument is not a string literal beginning with `/` should be
reviewed for the same open-redirect pattern.
