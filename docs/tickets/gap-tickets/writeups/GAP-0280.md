# GAP-0280: Address-Change Detection Hook Is Not Wired Into `app/services/profile.py` — Remediation Write-up

> Source ticket: KYC-018 · Severity: HIGH · Effort: M · Status: Open

## 1. Summary & Classification

**Gap**: The KYC-018 residency verification system includes `AddressVerificationService.invalidate_verification` (`app/services/kyc_address_verification.py` line 563), which resets the latest verification attempt to `pending/needs_review` when a user's address changes. The KYC-018 spec (§4.7) requires `update_profile` to compare old vs new address fields and call this method when address fields change. The hook was never wired: `app/services/profile.py` does not import `AddressVerificationService` and does not check for address changes after a profile save.

**Claim verdict**: CONFIRMED. `invalidate_verification` is fully implemented at line 563 of `app/services/kyc_address_verification.py` with the correct signature and logic. `apply_profile_update` in `app/services/profile.py` (line 294) has a field-diff loop that detects changes to `mailing_address` (a `PROFILE_FIELDS` member, line 28) but never triggers any side-effect for address changes. No import of `kyc_address_verification` exists in `profile.py`.

The ticket specifies fields `address_line_1`, `city`, `state`, `postal_code`, `country`. The profile service stores these as sub-keys of `mailing_address` (normalized by `_normalize_mailing_address`, line 128): `line1`, `line2`, `city`, `state`, `postal_code`, `country`. The field name `address_line_1` in the ticket should be `mailing_address.line1` — a minor naming discrepancy, but the underlying claim is correct.

**Severity**: HIGH. A user who changes their address after residency verification will retain a stale `verified` status. They can pass tier-2 KYC readiness checks using an address that has not been re-verified, defeating the purpose of address verification as a tier gate.

**Owning area**: Profile — `app/services/profile.py`; KYC Address Verification — `app/services/kyc_address_verification.py`.

**Related tickets**: KYC-018, GAP-0277 (country-change trigger), GAP-0259 (profile-change re-screening).

## 2. Current-State Investigation (root cause)

### Profile update path today

`apply_profile_update` in `app/services/profile.py` (line 294):

```python
def apply_profile_update(user_sub: str, updates: Dict[str, Any], *, replace: bool) -> Dict[str, Any]:
    current = get_profile(user_sub)
    base = empty_profile() if replace else current
    normalized = normalize_profile_payload(updates)
    updated = {**base, **normalized}

    audit_entries: List[Dict[str, Any]] = []
    ts = now_ts()
    for field in PROFILE_FIELDS:
        if current.get(field) != updated.get(field):
            audit_entries.append({
                "ts": ts, "field": field,
                "from": current.get(field), "to": updated.get(field),
            })

    save_profile(user_sub, updated, audit_entries)
    return updated
```

`PROFILE_FIELDS` includes `"mailing_address"` (line 28 of `profile.py`). The diff loop correctly detects when `mailing_address` changes (because `current.get("mailing_address") != updated.get("mailing_address")`). This change is written to the audit log. However, there is no side-effect call to `AddressVerificationService` — only `save_profile` and then return.

### `invalidate_verification` implementation

```python
# app/services/kyc_address_verification.py lines 563–579
def invalidate_verification(self, *, case_id: str, reason: str = "address_changed") -> None:
    """Reset the latest verification to pending (called on address change)."""
    latest = self.get_latest(case_id)
    if latest is None:
        return
    ts = now_ts()
    self._table.update_item(
        Key={"pk": _case_pk(case_id), "sk": latest["sk"]},
        UpdateExpression="SET #s = :s, decision = :d, updated_at = :ts",
        ExpressionAttributeNames={"#s": "status"},
        ExpressionAttributeValues={
            ":s": STATUS_PENDING,          # "pending"
            ":d": DECISION_NEEDS_REVIEW,   # "needs_review"
            ":ts": ts,
        },
    )
    logger.info("kyc.address.invalidated case_id=%s reason=%s", case_id, reason)
```

The method is safe: if no verification exists (`get_latest` returns `None`), it exits silently. It requires a `case_id` — the KYC case the address verification is attached to.

### Finding the case_id from a user_sub

The `invalidate_verification` call needs the KYC case ID for the user's active case. The `KycCaseService.list_cases_by_owner` method (line 659 of `kyc_cases.py`) returns cases for a given user. Only cases in active verification statuses (e.g., `in_progress`, `pending_review`) need to have their address verification invalidated; approved cases that are already closed do not.

```python
# app/services/kyc_cases.py line 659
def list_cases_by_owner(self, *, user_sub: str, limit: int = 25) -> list[dict[str, Any]]:
    response = self._table.query(
        IndexName=S.kyc_cases_owner_index_name,
        KeyConditionExpression="gsi_owner_pk = :pk",
        ExpressionAttributeValues={":pk": _owner_pk(user_sub)},
        ScanIndexForward=False,
        Limit=max(1, min(int(limit or 25), 100)),
    )
    return [row for row in response.get("Items", []) if row.get("entity_type") == "kyc_case"]
```

The statuses that warrant address invalidation are: `in_progress`, `pending_review`, `approved` (an approved user who changes address should trigger re-verification of the address).

### Which address sub-fields trigger invalidation

`_normalize_mailing_address` (line 128) normalizes to these keys: `line1`, `line2`, `city`, `state`, `postal_code`, `country`. Any change to these keys should trigger invalidation. The `mailing_address` field in `PROFILE_FIELDS` is compared as a whole dict object — if any sub-key changes, `current.get("mailing_address") != updated.get("mailing_address")` evaluates to `True`. This single comparison is sufficient to detect any address field change.

## 3. Impact / Exploit / Blast Radius

### Stale verified status exploit

1. Alice applies for Tier 2. She provides address `123 Main St, Austin TX 78701, US`.
2. Admin approves her residency verification. `kyc_address_verification` record has `status="verified"`.
3. The tier readiness check consults the address verification: `status="verified"` → gate passes.
4. Alice PATCHes her profile: `mailing_address = {"line1": "456 Fraud Ave", "city": "London", "country": "GB"}`.
5. No `invalidate_verification` is called. Her address verification remains `status="verified"` pointing to the old Austin address.
6. Alice submits a new KYC upgrade to Tier 3. The readiness check reads the verification record: `status="verified"` — still passes. The admin reviewer may not notice the address mismatch if they rely on the automated check.

### Cross-tier impact

Address verification is a gate for Tier 2 and above. If the stale verification is not invalidated, every tier upgrade after the address change inherits the fraudulent verified status.

### Volume

The issue affects every user who updates their mailing address after a KYC case involves address verification. On a platform with an active KYC program, this could be a large fraction of verified users who move house.

## 4. Fix Design (code-level)

### 4.1 Add address invalidation to `apply_profile_update` in `app/services/profile.py`

```python
# app/services/profile.py — apply_profile_update (line 294)
def apply_profile_update(user_sub: str, updates: Dict[str, Any], *, replace: bool) -> Dict[str, Any]:
    current = get_profile(user_sub)
    base = empty_profile() if replace else current
    normalized = normalize_profile_payload(updates)
    updated = {**base, **normalized}

    audit_entries: List[Dict[str, Any]] = []
    ts = now_ts()
    address_changed = False
    for field in PROFILE_FIELDS:
        if current.get(field) != updated.get(field):
            audit_entries.append({
                "ts": ts, "field": field,
                "from": current.get(field), "to": updated.get(field),
            })
            if field == "mailing_address":
                address_changed = True

    save_profile(user_sub, updated, audit_entries)

    # ── KYC address invalidation (GAP-0280) ─────────────────────────────
    if address_changed:
        _invalidate_address_verification_for_user(user_sub, current, updated)
    # ─────────────────────────────────────────────────────────────────────

    return updated
```

### 4.2 `_invalidate_address_verification_for_user` helper

```python
# app/services/profile.py — new helper

_ADDRESS_INVALIDATION_STATUSES = frozenset({
    "in_progress", "pending_review", "approved",
})


def _invalidate_address_verification_for_user(
    user_sub: str,
    old_profile: Dict[str, Any],
    new_profile: Dict[str, Any],
) -> None:
    """Invalidate address verification for all active KYC cases when address changes.

    Called after a successful profile save. Never raises — failures are logged
    and suppressed to avoid rolling back a legitimate profile update.
    """
    import logging
    _log = logging.getLogger(__name__)
    try:
        from app.services.kyc_cases import CASE_SERVICE                     # lazy import
        from app.services.kyc_address_verification import ADDRESS_VERIFICATION_SERVICE  # lazy

        cases = CASE_SERVICE.list_cases_by_owner(user_sub=user_sub, limit=25)
        for case in cases:
            if str(case.get("status", "")) not in _ADDRESS_INVALIDATION_STATUSES:
                continue
            case_id = str(case.get("kyc_case_id") or "")
            if not case_id:
                continue
            ADDRESS_VERIFICATION_SERVICE.invalidate_verification(
                case_id=case_id,
                reason="address_changed",
            )
            _log.info(
                "kyc.address.invalidated_on_profile_update user_sub=%s case_id=%s",
                user_sub, case_id,
            )

    except Exception:
        import logging as _logging
        _logging.getLogger(__name__).exception(
            "kyc.address.profile_invalidation_error user_sub=%s", user_sub
        )
```

**Design decisions**:

- **Lazy imports**: `kyc_cases` and `kyc_address_verification` import from `app/core/tables`, which may not be available during tests that only import `profile.py`. Lazy imports prevent circular dependencies and allow test-level mocking at call time.
- **`except Exception` swallowed**: A failed invalidation is logged but must never prevent the profile from being saved. The profile write is already committed when this function is called.
- **`list_cases_by_owner` with `limit=25`**: A user is unlikely to have more than a handful of concurrent KYC cases. If the limit is exceeded, the worst case is that some cases are not invalidated — an acceptable trade-off for the edge case. A warning log can be added if `len(cases) == 25`.
- **`_ADDRESS_INVALIDATION_STATUSES`**: Includes `approved` to handle the post-approval address change scenario. `rejected` and `closed` cases do not need invalidation since they are terminal.

### 4.3 Dev/Prod parity (SECOPS-007)

- `ADDRESS_VERIFICATION_SERVICE.invalidate_verification` writes to `T.kyc_address_verifications`, which is DynamoDB Local in dev and real DynamoDB in prod. No branching needed.
- `CASE_SERVICE.list_cases_by_owner` queries the `kyc_cases` table via the owner GSI. Fully testable in dev via moto / DynamoDB Local.
- No `S.dev_mode` gate: the invalidation should run identically in both environments. If address verification records do not exist in dev (no prior KYC flow), `get_latest` returns `None` and the function exits silently.

### 4.4 Backward compatibility

Existing users with verified address records will have those records reset to `needs_review` the next time they update their `mailing_address`. This is the correct and intended behaviour per the spec. No data migration is required; the invalidation only applies at the time of the profile update.

### Metrics / observability

The `logger.info("kyc.address.invalidated_on_profile_update ...")` log line can be monitored for rate spikes (unusual number of address changes could indicate account takeover or bulk testing). The exception log `kyc.address.profile_invalidation_error` should be alerted on if it appears in production.

### Rollout / risk

- **Risk**: MEDIUM. Existing users with `approved` KYC status who change their address will have their address verification reset to `pending`. This may trigger re-verification prompts in the UI. This is the correct behaviour and should be communicated to support teams before rollout.
- **Migration**: No retroactive fix needed for users who already changed their address before this fix. After deployment, only new address changes will trigger invalidation. Admins may want to audit existing cases where `mailing_address` in the profile differs from the verified address on record — this would require a separate one-time script.
- **Feature flag**: The fix can be gated by a `KYC_ADDRESS_INVALIDATION_ON_PROFILE_UPDATE=true` env-var (defaults to `true`) if operations wants a staged rollout.
- **Effort**: M (the invalidation logic is trivial; the effort is in correctly identifying case statuses and testing edge cases).
- **Sequencing**: Can be deployed independently. Coordinate with GAP-0277 (country-change KYC trigger) — both touch `apply_profile_update` and should ideally land in the same PR to avoid double-patching the same function.
