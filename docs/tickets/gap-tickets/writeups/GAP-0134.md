# GAP-0134: Wildcard scope assignments never resolved in `get_bots_for_conversation()` — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. Build on the
> investigation doc (docs/tickets/gap-tickets/investigations/GAP-0134.md) if it exists.

## 1. Summary & Classification

**Bug statement**: `get_bots_for_conversation()` queries only the GSI for direct
`CONV#{conversation_id}` assignments. Bot assignments with wildcard scopes
(`SCOPE#ALL_DMS`, `SCOPE#ALL_GROUPS`, `SCOPE#ALL_BROADCASTS`) are stored with a different PK
structure that has no `GSI1PK` value, so the GSI query never returns them. Any bot assigned at
wildcard scope — e.g., "reply in all DMs" — is invisible to the trigger evaluation path and
never fires.

**Claim accuracy**: Confirmed. `app/services/chat_bot.py:251–263` contains only a single GSI1
query keyed on `CONV#{conversation_id}`. The `_build_assignment_gsi1pk()` function at lines
397–402 explicitly returns `None` for all wildcard target types, so wildcard assignments are
stored without a `GSI1PK` attribute and are structurally unreachable by the existing query.

- **Severity**: HIGH — wildcard-scoped bots are silently non-functional
- **Source ticket**: BOT-001
- **Status**: Open
- **Owning area**: Bot subsystem / assignment resolution
- **Related tickets**: BOT-001, GAP-0133 (trigger hook not called at all), SECOPS-007

## 2. Current-State Investigation (root cause)

### The DynamoDB assignment record structure

`app/services/chat_bot.py:187–224` `assign_bot()` constructs the assignment item:

```python
# chat_bot.py:197-200
sk = _build_assignment_sk(target_type, target_id)
gsi1pk = _build_assignment_gsi1pk(target_type, target_id)

# ...
item = {
    "pk": f"BOT#{bot_id}",
    "sk": sk,
    "bot_id": bot_id,
    "creator_id": creator_id,
    "target_type": target_type,
    ...
}
if target_id:
    item["target_id"] = target_id
if gsi1pk:                          # ← only set for direct assignments
    item["GSI1PK"] = gsi1pk
    item["GSI1SK"] = f"BOT#{bot_id}"
```

**`_build_assignment_sk()` (lines 383–394)**:

| `target_type` | `sk` value |
|---|---|
| `conversation` | `CONV#{target_id}` |
| `broadcast` | `BCAST#{target_id}` |
| `all_dms` | `SCOPE#ALL_DMS` |
| `all_groups` | `SCOPE#ALL_GROUPS` |
| `all_broadcasts` | `SCOPE#ALL_BROADCASTS` |

**`_build_assignment_gsi1pk()` (lines 397–402)**:

```python
def _build_assignment_gsi1pk(target_type: str, target_id: str | None) -> str | None:
    if target_type == "conversation" and target_id:
        return f"CONV#{target_id}"
    if target_type == "broadcast" and target_id:
        return f"BCAST#{target_id}"
    return None          # ← all wildcard types fall here
```

So wildcard assignments are stored as:
```
pk = BOT#{bot_id}
sk = SCOPE#ALL_DMS          (or ALL_GROUPS, ALL_BROADCASTS)
bot_id = <bot_id>
creator_id = <creator_id>
target_type = all_dms
# NO GSI1PK, NO GSI1SK
```

### `get_bots_for_conversation()` — the incomplete query

```python
# chat_bot.py:251-263
def get_bots_for_conversation(*, conversation_id: str) -> list[dict]:
    """Find all bots assigned to a conversation (direct assignment via GSI1)."""
    resp = T.bot_assignments.query(
        IndexName="GSI1",
        KeyConditionExpression=Key("GSI1PK").eq(f"CONV#{conversation_id}"),
    )
    bot_ids = [item["bot_id"] for item in resp.get("Items", [])]
    bots = []
    for bid in bot_ids:
        b = get_bot(bot_id=bid)
        if b and b["status"] == "active":
            bots.append(b)
    return bots
```

The docstring itself notes "(direct assignment via GSI1)" — the limitation is documented in the
code but not addressed.

### What the function must also do

For a given `conversation_id`, the function must additionally find bots whose
`target_type` matches the conversation's type:

- If the conversation is a DM (`type = "dm"`): also fetch all `SCOPE#ALL_DMS` assignments.
- If the conversation is a group chat (`type = "group"`): also fetch all `SCOPE#ALL_GROUPS` assignments.
- If the conversation is a broadcast (`type = "broadcast"`): also fetch `SCOPE#ALL_BROADCASTS` assignments.

But wildcard assignments are not indexed by conversation; they are indexed by creator/bot. The
secondary lookup must scan per creator. There are two viable strategies:

**Strategy A: Scan all creators for wildcard scopes** (expensive, not scalable)
Query `T.bot_assignments` with a filter on `target_type = "all_dms"` across the full table. Bad.

**Strategy B: Query per active bot that the conversation's creator owns, then check wildcard scopes**
Conversely, get the conversation's creator, list their bots, and for each bot check if any wildcard
assignment matches the conversation type.

**Strategy C: Add a secondary GSI for wildcard scope lookup** (preferred)
Add a `GSI2PK = CREATOR#{creator_id}` + `GSI2SK = SCOPE#{scope}` to every wildcard assignment
item at write time. Then `get_bots_for_conversation()` can look up wildcard assignments per creator
efficiently.

Strategy C is recommended because it avoids full-table scans and keeps query time O(bots per creator).

### Missing context: conversation type lookup

`get_bots_for_conversation()` currently receives only `conversation_id`. To determine the
conversation type (DM / group / broadcast), it needs one additional DDB fetch:

```python
convo = _get_conversation_or_404(conversation_id)
convo_type = convo.get("type", "dm")
```

This is an existing helper in `messaging.py`; it can be called here because `chat_bot.py`
would import it, or the conversation type can be passed as an argument.

## 3. Impact / Exploit / Blast Radius

### Functional impact

- Any bot configured with `target_type = "all_dms"` or `"all_groups"` is permanently invisible.
- A creator setting up a platform-wide auto-reply bot ("reply to all DMs from new users") gets
  zero response, with no error feedback.
- This affects all creators who use the wildcard assignment feature introduced in BOT-001.

### Security / financial impact

Bots are not a security surface. However, if bots are used for compliance automation (e.g., "all
DMs must be greeted with a disclosure message"), the silent failure could create a compliance gap.

### Scale of affected users

All bots assigned at wildcard scope. The `T.bot_assignments` table can be scanned to measure the
current count of `SCOPE#ALL_*` records. In a new deployment this may be zero (if no creator has
tried wildcard assignments yet), but the gap is latent and will manifest as soon as wildcard
assignment is used.

## 4. Fix Design (code-level)

### Step 1: Add GSI to wildcard assignment items at write time

Modify `_build_assignment_gsi1pk()` to return a creator-scoped value for wildcard types, and also
add a `GSI2PK/GSI2SK` pair for scope-based lookups:

```python
# chat_bot.py: replace _build_assignment_gsi1pk
def _build_assignment_gsi1pk(target_type: str, target_id: str | None) -> str | None:
    if target_type == "conversation" and target_id:
        return f"CONV#{target_id}"
    if target_type == "broadcast" and target_id:
        return f"BCAST#{target_id}"
    return None  # wildcard scopes use GSI2, not GSI1
```

In `assign_bot()`, add a GSI2 pair for wildcard assignments:

```python
# After the existing gsi1pk block, add:
scope_sk = _build_assignment_scope_sk(target_type)
if scope_sk:
    item["GSI2PK"] = f"CREATOR#{creator_id}"
    item["GSI2SK"] = scope_sk

def _build_assignment_scope_sk(target_type: str) -> str | None:
    if target_type == "all_dms":
        return "SCOPE#ALL_DMS"
    if target_type == "all_groups":
        return "SCOPE#ALL_GROUPS"
    if target_type == "all_broadcasts":
        return "SCOPE#ALL_BROADCASTS"
    return None
```

This requires adding `GSI2` to `T.bot_assignments` table definition in
`scripts/local-ddb-init.py`.

### Step 2: Extend `get_bots_for_conversation()`

```python
def get_bots_for_conversation(
    *,
    conversation_id: str,
    conversation_type: str = "dm",   # pass from caller
    creator_id: str | None = None,   # pass from caller (conversation owner)
) -> list[dict]:
    """Find all bots for a conversation: direct assignments + wildcard scope matches."""
    # 1. Direct assignments (existing)
    resp = T.bot_assignments.query(
        IndexName="GSI1",
        KeyConditionExpression=Key("GSI1PK").eq(f"CONV#{conversation_id}"),
    )
    bot_ids: set[str] = {item["bot_id"] for item in resp.get("Items", [])}

    # 2. Wildcard scope assignments
    if creator_id:
        scope_for_type = {
            "dm": "SCOPE#ALL_DMS",
            "group": "SCOPE#ALL_GROUPS",
            "broadcast": "SCOPE#ALL_BROADCASTS",
        }.get(conversation_type)

        if scope_for_type:
            wildcard_resp = T.bot_assignments.query(
                IndexName="GSI2",
                KeyConditionExpression=(
                    Key("GSI2PK").eq(f"CREATOR#{creator_id}") &
                    Key("GSI2SK").eq(scope_for_type)
                ),
            )
            for item in wildcard_resp.get("Items", []):
                bot_ids.add(item["bot_id"])

    # 3. Resolve bots, filter active
    bots = []
    for bid in bot_ids:
        b = get_bot(bot_id=bid)
        if b and b["status"] == "active":
            bots.append(b)
    return bots
```

### Caller change in `_run_bot_trigger_evaluation()` (GAP-0133 fix)

Pass the conversation type and creator from the message item:

```python

```

The `creator_id` for the conversation is available via the conversation record's `owner_id` or
`host_user_id` field, which can be fetched alongside the conversation type in one DDB read.

### DynamoDB table change

Add to `scripts/local-ddb-init.py` for the `bot_assignments` table:

```python
TableDef(
    name=S.bot_assignments_table,
    pk="pk",
    sk="sk",
    gsis=[
        GsiDef("GSI1", "GSI1PK", "GSI1SK"),
        GsiDef("GSI2", "GSI2PK", "GSI2SK"),   # NEW
    ],
)
```

### Migration for existing wildcard assignments

Existing wildcard assignment records lack `GSI2PK/GSI2SK`. A one-time migration script should
scan `T.bot_assignments` for items where `sk` starts with `SCOPE#`, then update each item to
add the `GSI2PK = CREATOR#{creator_id}` and `GSI2SK = {sk}` attributes.

### Dev/Prod parity (SECOPS-007)

The GSI addition is a DynamoDB schema change. In dev: `scripts/local-ddb-init.py` must be
updated and the DynamoDB Local instance re-initialised (or the GSI created via the AWS CLI
against the running local instance). In prod: a CloudFormation/CDK update to the `bot_assignments`
table. Both paths use the same `T.bot_assignments.query(IndexName="GSI2", ...)` call; no
mock/dev-only code path is needed.

### Effort / Sequencing

- **Effort**: M (GSI addition + code change + migration script + tests)
- **Risk**: Medium — DynamoDB GSI additions on existing tables require a backfill period during
  which the index is `CREATING`; queries against GSI2 during backfill may return partial results.
  Deploy the code change after the GSI has reached `ACTIVE` state.
- **Sequencing**: Must be deployed together with GAP-0133 (trigger hook wiring). The two fixes are
  interdependent: the hook (GAP-0133) calls `get_bots_for_conversation()` (GAP-0134), so fixing
  only one leaves bots partially functional.
- **Rollback**: Remove the `GSI2` branch from `get_bots_for_conversation()`; wildcard bots return
  to non-functional state. GSI can be left in the table (harmless, no write overhead after
  `ACTIVE`).
