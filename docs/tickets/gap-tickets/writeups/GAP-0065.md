## 2. Current-State Investigation (root cause)

### Verification of existing coverage

`tests/test_ad_dayparting.py:1-188` — confirmed present. The file is imported as:

```python
from app.services import ad_dayparting as dp
```

This imports `app/services/ad_dayparting.py` directly — the same module that implements all dayparting, flight scheduling, and pacing logic described in ADS-016.

### Coverage mapping against the claimed "9 tests"

The gap ticket proposed 9 tests covering "validation, eligibility, flight resolution, and pacing." The existing file exceeds this:

| Proposed area | Proposed count | Actual tests |
|---------------|----------------|--------------|
| Validation | ~2 | 4 (valid config, invalid timezone, empty schedule, bad hours) |
| Eligibility | ~3 | 4 (active hour, inactive hour, no config, timezone conversion) |

### Root cause of the false gap

Same naming pattern as GAP-0063 and GAP-0064: the gap audit expected `test_ad_scheduling.py` (matching the ADS-016 ticket title "Ad Scheduling") but the file is named `test_ad_dayparting.py` (matching the service module). The design doc used "scheduling" as the conceptual name; the implementation used "dayparting" as the module/file name; the gap audit used the design-doc name to search.

### Genuine gaps in the existing test suite

While the file exists and provides solid coverage, there are four areas that the existing 16 tests do not cover:

1. **Named schedule templates** — `SCHEDULE_TEMPLATES` dict in `ad_dayparting.py:35-49` is never directly tested. Tests validate arbitrary `schedule` dicts but not the named template expansion. This matters if a template entry is edited incorrectly.

2. **`_resolve_now` edge cases** — the function at line 55 handles `now=None` (falls back to wall clock) and `now=int` (converts Unix timestamp). The `now=None` path is not tested — a test would need to verify that `is_campaign_eligible_now` called without `now=` uses real wall-clock time.

3. **`_zone` invalid input** — `_zone("UTC")` is tested implicitly, but `_zone("")` (empty string) and `_zone(None)` are not. If `campaign_timezone` is stored as empty string in DynamoDB, the subsequent `.astimezone(tz)` call would raise `AttributeError`.

4. **`calculate_dayparted_budget` with `spend_today_cents` injection** — the pacing tests verify `hourly_budget_cents` and `remaining_budget_cents` at `hours_remaining == active_hours` (start of day), but do not test mid-day pacing where `spend_today_cents > 0` has already been consumed. The function signature accepts `spend_today_cents` as an optional parameter but no test exercises the non-zero case.

## 3. Impact / Exploit / Blast Radius

### Functional risk from the naming gap

None — `pytest` discovers test files by glob (`test_*.py`). The existing file runs correctly as part of `just test`.

### Risk from uncovered edge cases

**`_zone("")` (empty timezone string)**: If an advertiser creates a campaign with `campaign_timezone: ""` (blank string — possible if the UI sends an empty form field), `_zone("")` returns `None`, and `_resolve_now` receives `tz=None`, causing `datetime.fromtimestamp(...).astimezone(None)` which raises `TypeError` at serving time. This would make the campaign ineligible to serve rather than defaulting to UTC — a silent revenue loss.

**Mid-day pacing with `spend_today_cents`**: If the pacing calculation is called with historical spend already consumed, the `remaining_budget_cents` should decrease proportionally. Without a test, a future refactor could accidentally return full daily budget regardless of prior spend.

**Template coverage**: The `SCHEDULE_TEMPLATES` dict is referenced by the campaign scheduling UI dropdown. If a template key is renamed or its hour list is edited, the change would not be caught by offline tests.

### Add missing tests to `tests/test_ad_dayparting.py`

```python
# ── Template tests ──────────────────────────────────────────────────

def test_template_weekdays_business():
    """weekdays_business template should have Mon-Fri hours 9-17, Sat/Sun empty."""
    t = dp.SCHEDULE_TEMPLATES["weekdays_business"]
    assert t["monday"] == list(range(9, 18))
    assert t["saturday"] == []
    assert t["sunday"] == []


def test_template_always():
    """always template should cover all 24 hours every day."""
    t = dp.SCHEDULE_TEMPLATES["always"]
    for day in dp.VALID_DAYS:
        assert t[day] == list(range(24))


def test_template_evenings():
    """evenings template: hours 18-23 every day."""
    t = dp.SCHEDULE_TEMPLATES["evenings"]
    for day in dp.VALID_DAYS:
        assert t[day] == list(range(18, 24))


# ── _zone edge cases ────────────────────────────────────────────────

def test_zone_empty_string_returns_none():
    """Empty timezone string must return None (treated as invalid)."""
    result = dp._zone("")
    assert result is None


def test_zone_none_raises_or_returns_none():
    """None timezone string must not propagate to datetime operations."""
    result = dp._zone(None)
    assert result is None


# ── Mid-day pacing ──────────────────────────────────────────────────

def test_budget_pacing_mid_day_with_prior_spend():
    """Mid-day: remaining_budget_cents = daily - already_spent."""
    cfg = {"timezone": "UTC", "schedule": {"monday": list(range(8, 20))}}
    # 2026-06-01 14:00 → 12 active hours total; 6 have passed (8,9,10,11,12,13)
    pacing = dp.calculate_dayparted_budget(
        daily_budget_cents=120000,
        dayparting=cfg,
        now=_ts(2026, 6, 1, 14),
        spend_today_cents=60000,   # half the daily budget already spent
    )
    assert pacing["active_hours_today"] == 12
    assert pacing["hours_remaining"] == 6       # 14..19 inclusive
    assert pacing["remaining_budget_cents"] == 60000   # 120000 - 60000


def test_budget_pacing_overspend_clamps_to_zero():
    """If spend_today_cents exceeds daily budget, remaining must not go negative."""
    cfg = {"timezone": "UTC", "schedule": {"monday": list(range(8, 20))}}
    pacing = dp.calculate_dayparted_budget(
        daily_budget_cents=10000,
        dayparting=cfg,
        now=_ts(2026, 6, 1, 10),
        spend_today_cents=15000,   # over budget
    )
    assert pacing["remaining_budget_cents"] == 0
```

These tests address all four genuine gaps identified above. They are all offline (no DynamoDB required) and will run in `just test` without any stack dependency.

### Dev/Prod parity (SECOPS-007)

Offline unit tests call the service functions directly and do not touch DynamoDB. The `_zone`, `_resolve_now`, `validate_dayparting_config`, `is_campaign_eligible_now`, `get_active_flight`, `validate_flights`, and `calculate_dayparted_budget` functions are pure computation functions with no I/O side effects. There is no AWS-specific code path — identical behaviour in dev and prod.
