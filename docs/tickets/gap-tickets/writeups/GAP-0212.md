# GAP-0212: No Undo Window for Bulk Payout/Refund Batches — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: FIN-017. No prior investigation doc.
> Claim verified against actual code.

## 1. Summary & Classification

**Severity**: HIGH
**Source ticket**: FIN-017 (Bulk Payout/Refund Tools)
**Owning area**: `app/services/bulk_payout_tools.py`, `app/routers/bulk_payout_tools.py`, `app/models.py`
**Status**: Open — no fix applied

**Claim verification**: CONFIRMED. The as-built gap review stated that `_persist_batch` (`:202`) stores no `undo_expires_at` field, `BulkBatchOut` (models.py `:1599`) has no `undo_expires_at` field, and no undo endpoint exists in the router. All three deficiencies are present in the live code. The DDB item, the Pydantic model, and the router were each checked individually.

After a bulk batch executes (`POST /ui/admin/bulk-payouts/execute`) it transitions to status `"completed"` or `"completed_with_errors"`. There is no 5-minute reversal window: no timestamp is stored, no undo endpoint exists, and there is no per-item reversal path. An admin who approves the wrong batch — or the right batch with wrong items — has no self-service path to undo the damage within a safety window.

**Related tickets**: GAP-0213 (no CSV import endpoint, same source ticket FIN-017) is the companion HIGH gap from FIN-017. Together these two gaps represent the most operationally dangerous missing features in the bulk-ops tool.

## 2. Current-State Investigation (root cause)

### _persist_batch stores no undo window

`app/services/bulk_payout_tools.py`, lines 202–227 (`_persist_batch`):

```python
item = {
    "batch_id": batch_id,
    "created_at": created_at,
    "created_by": created_by,
    "kind": kind,
    "status": status,
    "item_count": summary["item_count"],
    "success_count": int(success_count),
    "failure_count": int(failure_count),
    "total_cents": summary["total_cents"],
    "items": items,
    "gsi_all": _GSI_ALL,
}
T.bulk_payout_batches.put_item(Item=item)
```

There is no `undo_expires_at` key in this dict. The DDB item contains no timestamp that the backend could compare to when evaluating whether an undo is still valid.

### BulkBatchOut has no undo_expires_at field

`app/models.py`, lines 1599–1609:

```python
class BulkBatchOut(BaseModel):

    created_at: int
```

No `undo_expires_at` field. The execute response carries no signal to the frontend that a reversal window is available.

### No undo endpoint in the router

`app/routers/bulk_payout_tools.py` defines five routes:

- `GET /eligible`
- `POST /preview`
- `POST /execute`
- `GET /batches`
- `GET /batches/{batch_id}`

There is no `POST /batches/{batch_id}/undo`. The reversal logic — calling `reject_payout` or `reverse_refund` for already-approved items — is absent from both router and service.

### execute_batch performs no undo guard either

`app/services/bulk_payout_tools.py`, lines 329–332: the only status guard prevents re-execution of an already-completed batch:

```python
if existing.get("status") in (STATUS_COMPLETED, STATUS_COMPLETED_WITH_ERRORS):
    raise ValueError("batch already executed")
```

There is no `undo_expires_at` read or undo guard in this path.

### The single-item reversal primitives exist

`app/services/creator_payouts.py` exports `reject_payout`. `app/services/refund_requests.py` exports `reject_request`. The building blocks for per-item reversal are present — they are simply not wired into any bulk-undo path.

### Dev vs. prod

The gap is identical in both environments. The DDB item is written by the same `_persist_batch` function regardless of `S.dev_mode`. No mock path bypasses this deficiency.

## 3. Impact / Exploit / Blast Radius

### Operational risk

A bulk execute call approves every eligible item in one shot. Without an undo window:

- An admin who accidentally includes 50 wrong payout IDs in a batch has no recovery path.
- A double-click or race condition (two admins submitting the same preview batch) could double-process items. The `"batch already executed"` guard prevents the second execute on the same `batch_id`, but two admins who independently built batches covering the same payout IDs are not guarded.
- In the case of refund batches, approving a refund credits the user's wallet immediately via `approve_request`. Without reversal, funds are committed.

### Financial blast radius

The system processes real wallet credits (refunds) and payout status transitions that feed into provider payouts when `S.bulk_payout_use_real_provider=True` in production. A mistaken bulk-approve of 100 refund requests at $50 average = $5,000 of unintended credits issued in a single HTTP request, with no self-service reversal path.

### No security exploit

There is no authentication bypass or data-leak vector here. The risk is purely financial: incorrect bulk disbursement with no recovery mechanism within a safety window.

## 4. Fix Design (code-level)

### Overview

1. Add `undo_expires_at: Optional[int]` to `BulkBatchOut` (models.py) and to the DDB item written by `_persist_batch`.
2. Set `undo_expires_at = now_ts() + UNDO_WINDOW_SECONDS` (300 seconds = 5 minutes) when `status` is `completed` or `completed_with_errors`.
3. Add `undo_batch(batch_id, admin_sub)` to the service that validates the window, iterates successful items, and calls the per-item reversal primitive.
4. Add `POST /batches/{batch_id}/undo` to the router.

### Step 1 — Model changes (`app/models.py`)

```python
class BulkBatchOut(BaseModel):

    created_at: int
    created_by: Optional[str] = None
    kind: str
    status: str
    item_count: int

    failure_count: int = 0
    total_cents: int
    items: List[BulkBatchItem] = Field(default_factory=list)
    undo_expires_at: Optional[int] = None   # NEW: Unix ts until which undo is valid
    undo_performed_at: Optional[int] = None # NEW: set when undo completes
```

### Step 2 — Service: store undo window in `_persist_batch`

```python
UNDO_WINDOW_SECONDS = 300  # 5-minute reversal window

def _persist_batch(..., status: str, ...) -> dict:
    now = now_ts()
    undo_expires_at = (now + UNDO_WINDOW_SECONDS
                       if status in (STATUS_COMPLETED, STATUS_COMPLETED_WITH_ERRORS)
                       else None)
    item = {
        "batch_id": batch_id,
        "created_at": created_at,
        "created_by": created_by,
        "kind": kind,
        "status": status,
        "item_count": summary["item_count"],
        "success_count": int(success_count),
        "failure_count": int(failure_count),
        "total_cents": summary["total_cents"],
        "items": items,
        "gsi_all": _GSI_ALL,
        "undo_expires_at": undo_expires_at,   # NEW
    }
    T.bulk_payout_batches.put_item(Item=item)
    return _batch_to_out(item)
```

Update `_batch_to_out` to read and return `undo_expires_at` and `undo_performed_at`.

### Step 3 — Service: `undo_batch`

```python
STATUS_UNDONE = "undone"

def undo_batch(batch_id: str, admin_sub: str) -> dict:
    """Reverse all successful items in a completed batch within the undo window."""
    existing = T.bulk_payout_batches.get_item(
        Key={"batch_id": batch_id}
    ).get("Item")
    if not existing:
        raise ValueError("batch not found")

    status = existing.get("status")
    if status not in (STATUS_COMPLETED, STATUS_COMPLETED_WITH_ERRORS):
        raise ValueError(f"batch is not in a completed state (status={status})")

    undo_expires_at = existing.get("undo_expires_at")
    if not undo_expires_at or now_ts() > int(undo_expires_at):
        raise ValueError("undo window has expired")

    if existing.get("undo_performed_at"):
        raise ValueError("batch has already been undone")

    kind = existing.get("kind")
    items = existing.get("items", [])
    reversal_results: list[dict] = []

    for item in items:
        if item.get("status") != "success":
            reversal_results.append(item)
            continue
        ref_id = item.get("ref_id", "")
        try:
            if kind == KIND_PAYOUT:
                reject_payout(ref_id, admin_sub, notes="Bulk batch undo")
            else:
                reject_request(ref_id, admin_sub, notes="Bulk batch undo")
            reversal_results.append({**item, "status": "undone"})
        except Exception as e:
            reversal_results.append({**item, "status": "undo_failed", "reason": str(e)})

    undo_ts = now_ts()
    T.bulk_payout_batches.update_item(
        Key={"batch_id": batch_id},
        UpdateExpression=(
            "SET #st = :st, undo_performed_at = :uat, "
            "undo_performed_by = :uby, items = :items"
        ),
        ExpressionAttributeNames={"#st": "status"},
        ExpressionAttributeValues={
            ":st": STATUS_UNDONE,
            ":uat": undo_ts,
            ":uby": admin_sub,
            ":items": reversal_results,
        },
    )
    updated = T.bulk_payout_batches.get_item(
        Key={"batch_id": batch_id}
    ).get("Item", {})
    return _batch_to_out(updated)
```

### Step 4 — Router: undo endpoint

In `app/routers/bulk_payout_tools.py`, add:

```python
from app.services.bulk_payout_tools import undo_batch  # new import

@bulk_payout_tools_router.post(
    "/batches/{batch_id}/undo",
    response_model=BulkBatchOut,
)
def bulk_undo_batch(
    batch_id: str,
    request: Request,
    _admin=Depends(require_admin_or_root),
):
    try:
        out = undo_batch(batch_id, _admin.sub)
    except ValueError as e:
        raise HTTPException(status_code=400, detail=str(e))
    audit_event(
        "bulk_payout.undo",
        _admin.sub,
        request,
        batch_id=batch_id,
    )
    return out
```

### Dev/Prod parity (SECOPS-007)

`undo_batch` calls `reject_payout` and `reject_request` — the same single-item service functions used by execute. When `S.bulk_payout_use_real_provider=False` (dev/test), these functions run the in-process mock path with no external provider call. When `True` (production), the same functions invoke the real provider. No special mock branching is added; the parity is inherited from the existing single-item services.

The `undo_expires_at` timestamp is a pure integer comparison using `now_ts()`, which is environment-agnostic.

### Backward compatibility

`undo_expires_at` and `undo_performed_at` are nullable in `BulkBatchOut`. Existing batch records in DDB that predate this fix will have neither field; `_batch_to_out` will return `None` for both. Existing API consumers will see these new optional fields as `null` — no breaking change.

### Alternatives considered

- **Soft-delete only (mark undone, no actual reversal)**: Provides a paper trail but leaves the funds/status change in place. Rejected — the goal is financial reversal, not just a status label.
- **30-minute window**: Longer window increases the risk that a single-item reversal fails because the creator has already withdrawn funds. 5 minutes is consistent with payment-industry norms for reversal windows.
- **Make undo window configurable via `billing_config`**: Could be added later without changing the core logic. Out of scope for this fix.

```python

import pytest
from unittest.mock import patch, MagicMock
from app.services.bulk_payout_tools import (
    UNDO_WINDOW_SECONDS,
    STATUS_COMPLETED,

def test_undo_batch_within_window(mock_ddb_batch_table, seed_completed_batch):

    from app.services.bulk_payout_tools import undo_batch
    result = undo_batch(seed_completed_batch["batch_id"], "admin_root")
```
