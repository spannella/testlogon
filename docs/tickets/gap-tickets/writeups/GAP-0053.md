# GAP-0053: record_transparency() Never Called from Billing Pipeline — Remediation Write-up

## 1. Summary & Classification

**Gap**: `record_transparency` is fully implemented in
`app/services/content_ad_controls.py` (lines 243–277) but is never invoked from the
ad billing pipeline. As a result, `get_advertiser_transparency` always returns an empty
list for every creator, regardless of how many ads have served on their content.

**Severity**: HIGH  
**Source ticket**: ADS-010  
**Owning area**: Ad Billing / Ad Analytics  
**Status**: Open — claim confirmed. `record_transparency` is defined at line 243 of
`content_ad_controls.py`. A global search for call sites across the entire `app/`
directory finds zero calls to it (`grep -rn "record_transparency" app/` returns only the
definition). The ticket's claim is accurate.

**One-line impact**: The advertiser-transparency feature (`GET /ui/ads/creator/transparency`)
is completely non-functional; every creator sees an empty advertiser list regardless of ad
activity.

**Related tickets**: GAP-0054 (dynamic revenue share also missing from billing pipeline),
GAP-0049 (platform revenue share not written to ledger), ADS-010.

---

## 2. Current-State Investigation (root cause)

### record_transparency is defined but never called

`app/services/content_ad_controls.py`, lines 243–277:

```python
def record_transparency(
    creator_sub: str,
    account_id: str,
    company_name: str,
    month: str,
    *,
    impressions: int = 0,
    clicks: int = 0,
    revenue_cents: int = 0,
) -> None:
    """Atomically increment the transparency record for creator/advertiser/month.

    Best-effort — called by the ad billing pipeline on each charge event.
    """
    try:
        T.billing.update_item(
            Key={"pk": f"USER#{creator_sub}", "sk": f"AD_TRANSPARENCY#{account_id}#{month}"},
            ...
        )
    except Exception:
        logger.warning("transparency_record_failed", ...)
```

The docstring says "called by the ad billing pipeline on each charge event" — but the
billing pipeline (`app/services/ad_billing.py`) contains no import of
`content_ad_controls` and no call to `record_transparency`. Running:

```
grep -rn "record_transparency" app/
```

Returns a single result: the function definition at line 243. No caller exists anywhere.

### The billing pipeline's _split_revenue is the correct call site

`app/services/ad_billing.py`, `_split_revenue` function, lines 150–169:

```python
def _split_revenue(*, charge_cents: int, creator_id: str, meta: dict, ts: int) -> None:
    """Split ad revenue between platform and creator."""
    platform_share = max(0, (charge_cents * PLATFORM_REVENUE_SHARE_PCT) // 100)
    creator_share = charge_cents - platform_share

    if creator_share > 0 and creator_id:
        try:
            _sk, credit_item = new_ledger_entry(...)
            T.billing.put_item(Item=credit_item)
        except Exception:
            logger.warning("ad_revenue_creator_credit_failed", ...)
```

After writing the creator credit, `_split_revenue` has everything needed to call
`record_transparency`: the `creator_id`, the `account_id` (available from `meta` or via
the charge record), and the `charge_cents` / `creator_share`. The `month` is derivable
from `ts`. The `company_name` requires a lookup of the ad account record.

### get_advertiser_transparency reads AD_TRANSPARENCY# records

`content_ad_controls.py`, lines 280–304. It queries DDB with
`Key("sk").begins_with("AD_TRANSPARENCY#")` on the creator's billing partition. Because
`record_transparency` never writes those records, the query always returns an empty list.

### Why this is severity HIGH

The transparency feature is a trust/compliance feature: it tells creators which
advertisers ran ads on their content. If it is never populated, the endpoint is a lie. Any
advertiser dispute, brand-safety audit, or regulatory inquiry that relies on this data will
find blank records.

---

## 3. Impact / Exploit / Blast Radius

**Creators**: The transparency dashboard (`GET /ui/ads/creator/transparency`) returns
`[]` for all creators at all times. Creators cannot audit which advertisers served on
their content. This undermines the brand-safety controls that the ADS-010 ticket was
specifically designed to provide.

**Compliance / contractual**: Many creator-platform contracts require disclosure of
advertiser identity. A technically provided but permanently empty transparency log does
not satisfy that obligation.

**Financial audit trail**: The `revenue_cents` field in each transparency record was meant
to provide a per-advertiser revenue breakdown reconcilable against creator payouts. Without
it, creators cannot cross-check their ad revenue earnings by advertiser, opening the
platform to revenue disputes.

**No security exploit in the traditional sense**, but the failure enables a scenario where
a creator has blocked an advertiser (`block_advertiser`), the block is properly checked
in `serve_ad`, but the transparency log is empty — so the creator cannot verify that the
block is working correctly by inspecting the transparency history.

## 4. Fix Design (code-level)

### Where to call record_transparency

The correct injection point is in `_split_revenue`, after the creator credit is written.
This function is called on every impression charge, click charge, and conversion charge
via `_process_charge`.

### What data is available

`_split_revenue` receives:
- `charge_cents` and `creator_id` — direct parameters.
- `meta` dict — from `charge_impression` calls, `meta` contains `creative_id`,
  `content_id`, and `model`. It does **not** contain `account_id` directly.
- `ts` — the integer Unix timestamp; the month key is `datetime.fromtimestamp(ts).strftime("%Y-%m")`.

The `account_id` is not directly available inside `_split_revenue`. Two approaches:

**Option A** — Pass `account_id` as an explicit parameter to `_split_revenue`. All three
callers (`charge_impression`, `charge_click`, `charge_conversion`) already have the
`account_id` parameter. The change is straightforward.

**Option B** — Store `account_id` in `meta` before passing it to `_split_revenue`. The
meta dicts for all three charge types are constructed in the caller functions; adding
`"account_id": account_id` to each is a one-line change.

Option A is cleaner (no mixing of billing metadata with transparency metadata).

### The company_name lookup

`record_transparency` requires `company_name`. This comes from the ad account record
(`ad_accounts` table, `company_name` field). A DynamoDB `get_item` on the ad account is
needed. To avoid blocking the hot path with a synchronous lookup on every charge, the
approach is:

1. Do the lookup inside the `try/except` block in `_split_revenue` (the transparency call
   is already documented as best-effort).
2. Pass `company_name=""` (empty string) as a fallback if the lookup fails — the record
   will still be created with correct numeric counters; `company_name` can be backfilled.

### Revised `_split_revenue`

```python
def _split_revenue(
    *, charge_cents: int, creator_id: str, account_id: str, meta: dict, ts: int
) -> None:
    """Split ad revenue between platform and creator."""
    from datetime import datetime, timezone

    platform_share = max(0, (charge_cents * PLATFORM_REVENUE_SHARE_PCT) // 100)
    creator_share = charge_cents - platform_share

    if creator_share > 0 and creator_id:
        try:
            _sk, credit_item = new_ledger_entry(
                key_name="pk",
                key_value=user_pk(creator_id),
                entry_type="ad_revenue_credit",
                amount_cents=creator_share,
                state="settled",
                reason="Ad revenue share",
                meta={**meta, "platform_share_pct": PLATFORM_REVENUE_SHARE_PCT},
            )
            T.billing.put_item(Item=credit_item)
        except Exception:
            logger.warning("ad_revenue_creator_credit_failed",
                           extra={"creator_id": creator_id})

    # Record advertiser transparency (ADS-010 / GAP-0053) — best-effort
    if creator_id and account_id:
        try:
            from app.services.content_ad_controls import record_transparency
            from app.services.ad_accounts import get_ad_account

            month = datetime.fromtimestamp(ts, tz=timezone.utc).strftime("%Y-%m")
            entry_type = meta.get("model", "")
            acct = get_ad_account(account_id)
            company_name = acct.get("company_name", "") if acct else ""

            record_transparency(
                creator_sub=creator_id,
                account_id=account_id,
                company_name=company_name,
                month=month,
                impressions=1 if entry_type == "cpm" else 0,
                clicks=1 if entry_type == "cpc" else 0,
                revenue_cents=creator_share,
            )
        except Exception:
            logger.warning("transparency_record_failed",
                           extra={"creator_id": creator_id, "account_id": account_id})
```

### Callers: add account_id parameter

In `_process_charge` (line 142), the call to `_split_revenue` must include `account_id`:

```python
# Before:
_split_revenue(charge_cents=charge_cents, creator_id=creator_id, meta=meta, ts=ts)

# After:
_split_revenue(charge_cents=charge_cents, creator_id=creator_id,
               account_id=account_id, meta=meta, ts=ts)
```

The `account_id` is already a parameter of `_process_charge` (line 101).

### Dev / Prod parity (SECOPS-007)

The fix adds only DynamoDB interactions via the existing `T.billing` and `T.ad_accounts`
table handles. In dev, these resolve to DynamoDB Local (port 8001). In prod, they resolve
to real DynamoDB. No new AWS service dependency is introduced. The `record_transparency`
call is already wrapped in a `try/except` — it fails gracefully in both environments.
SECOPS-007 is satisfied by construction.

### Idempotency

`record_transparency` uses `update_item` with `if_not_exists(count, :z) + :delta`. This
is idempotent in the sense that it accumulates counts correctly across multiple calls for
the same `(creator_sub, account_id, month)` tuple. It is not idempotent for duplicate
charge events (double-counting is possible if `_process_charge` is retried), but that is
the same risk as the existing creator credit ledger entry — acceptable for a best-effort
transparency log.

### Manual QA

1. Create ad account `acct1` with company name "Acme Corp".
2. Create a campaign and creative.
3. Call `POST /ui/ads/track?event=impression&account_id=acct1&campaign_id=...&creator_id=creator1`.
4. Call `GET /ui/ads/creator/transparency` as creator1.
5. Expect at least one entry with `company_name="Acme Corp"` and `total_impressions > 0`.
6. Trigger a click charge: call `POST /ui/ads/track?event=click&...` with the same creator.
7. Call `GET /ui/ads/creator/transparency` again; verify `total_clicks` increments.
8. Call the month-filtered variant `GET /ui/ads/creator/transparency?month=2026-06`; verify
   only the current month's record appears.
9. Test with a creator who has no ad activity: `GET /ui/ads/creator/transparency` should
   return `[]` (not 500).

### Edge cases to validate

- **company_name unavailable** (ad account not found or DDB failure): `record_transparency`
  must write the record with `company_name=""` rather than failing silently. The numeric
  counters must still be incremented.
- **Concurrent charges from the same advertiser**: `update_item` with
  `if_not_exists(count, :z) + :delta` is the standard DynamoDB atomic increment pattern.
  Concurrent calls for the same `(creator, account, month)` tuple must produce correct
  aggregated totals, not last-write-wins overwrite behavior.
- **New month rollover**: Charges in January and February must produce separate
  `AD_TRANSPARENCY#acct1#2026-01` and `AD_TRANSPARENCY#acct1#2026-02` items.
  The month-filter in `get_advertiser_transparency` must correctly isolate them.
- **Creator with blocked advertiser**: `record_transparency` should still write even if
  the advertiser is on the creator's block list (the block list prevents future serving,
  not historical recording). The transparency log is an audit trail.

### Observability

Existing `logger.warning("transparency_record_failed", ...)` in `record_transparency`
provides failure visibility. Add a `logger.debug("transparency_recorded creator=%s ...")` 
on the success path to confirm call frequency in staging.

### Rollout

- **Effort**: S (1 day of code + 1 day of tests)
- **Risk**: Low — purely additive write. The billing path already has error handling; the
  transparency call is inside a `try/except` so it cannot break billing even if it fails.
- **Sequencing**: Can be shipped independently of GAP-0051 and GAP-0054. Should be
  coordinated with the schema review confirming the `billing` table accepts
  `AD_TRANSPARENCY#` sort keys (it does — single-table design uses `begins_with` queries).
- **Rollback**: Remove the transparency call and revert the `account_id` parameter to
  `_split_revenue`. No DynamoDB table changes.
- **Historical data**: Transparency records will only exist from the deployment date
  forward. Retroactive backfill from the `ad_billing` ledger entries is possible but
  optional; the `meta` field on each charge contains `creative_id` but not `company_name`,
  so a backfill would need to join to the `ad_accounts` table.
