# GAP-0028: `POST /feed/record` Accepts Arbitrary `user_id` from Request Body (SEC-005 IDOR) — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: The `POST /feed/record` endpoint in the activity-feed subsystem requires a valid authenticated session, but then ignores the session's proven identity when writing the activity record. Instead of using the session's `user_sub` as the activity owner, the handler blindly passes `body.user_id` — a value supplied entirely by the caller in the request body — to the `record_activity` service function. This means any authenticated user can forge activity entries on behalf of any other user.

- **Severity**: Critical (CRIT)
- **Source ticket**: PLATFORM-012
- **Status**: Open
- **Owning area**: Activity Feed / Social / Platform
- **Effort**: S

**Verdict**: Confirmed. The investigation (`docs/tickets/gap-tickets/investigations/GAP-0028.md`) verified the exact vulnerable code path at `app/routers/activity_feed.py:148–170`. The session's `user_sub` is extracted by `require_ui_session` but never compared to or substituted for `body.user_id`.

**One-line impact**: Any authenticated user can inject fabricated social activity entries (tips, follows, likes, comments) into any other user's feed, poisoning social metrics and enabling impersonation-level noise attacks.

**Related tickets**: SEC-005 (IDOR — Broken Object-Level Authorization), PLATFORM-012 (source), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### The vulnerable endpoint

`app/routers/activity_feed.py:148–170` defines:

```python
@router.post("/feed/record")
def record_activity(
    body: RecordActivityIn,
    session=Depends(require_ui_session),
):
    """Record an activity item (for testing/internal use).

    In production, activities are created by service-layer hooks
    when social events occur (follow, like, comment, etc.).
    """
    item = activity_feed_service.record_activity(
        user_id=body.user_id,          # ← body.user_id is caller-controlled
        actor_id=body.actor_id,
        activity_type=body.activity_type,
        target_type=body.target_type,
        target_id=body.target_id,
        metadata=body.metadata,
    )
    return {
        "ok": True,
        "activity_id": item["activity_id"],
        "created_at": item["created_at"],
    }
```

`require_ui_session` is correctly applied: the caller must present a valid `ui_session` cookie (or Bearer token). The dependency returns a session dict containing `user_sub`, `role`, and `admin_profile`. However, the handler immediately discards this information. The `user_id` passed to `record_activity` comes from `body.user_id`, not from `session["user_sub"]`. There is no ownership check and no admin-role gate.

### What `record_activity` does

`activity_feed_service.record_activity(user_id=..., actor_id=..., activity_type=..., ...)` writes a DynamoDB item to the `activity_feed` table with the supplied `user_id` as the primary partition key. The `user_id` is the "whose feed is this entry in" field — it is the owner of the feed, not the actor. An attacker who passes `user_id="victim_sub"` writes an entry into the victim's feed.

### The docstring confirms the intent

The endpoint's own docstring states `"for testing/internal use"`. This is a clear marker that the endpoint was built as a development/test harness and was never intended to be called by end users without access controls. The absence of an admin-role gate means the "internal use only" intent was not enforced.

### Where the session identity goes unused

`require_ui_session` extracts and returns a session dict containing `session["user_sub"]`, `session["role"]`, and `session["admin_profile"]`. The handler binds this as `session` but never reads from it. The variable `session` is used only as a dependency marker to enforce authentication. An IDE or linter would flag this as an "unused variable," which is itself a signal that the ownership check was overlooked during code review.

In every other authenticated POST endpoint in this codebase, the pattern is:

```python
session = Depends(require_ui_session)
user_sub = session["user_sub"]   # extract and use
```

This endpoint extracts the session but discards `user_sub`, passing `body.user_id` instead.

### Root cause

The endpoint was implemented as a test/debug utility. The developer wrote `body.user_id` to allow test scripts to inject activity on behalf of arbitrary users without setting up multiple sessions. The guard (`session["user_sub"]` ownership check) was omitted because it was not needed for test use cases, but the endpoint was never restricted to admin or dev-mode callers before being deployed. Production-equivalent access controls were not applied because the endpoint was mentally categorized as "internal only" without that intent being enforced in code.

## 3. Impact / Exploit / Blast Radius

### Exploit walkthrough

1. Attacker authenticates as their own valid account (any user).
2. Attacker calls:
   ```
   POST /feed/record
   Content-Type: application/json
   Cookie: ui_session=<attacker_session>
   x-csrf-token: <attacker_csrf>

   {
     "user_id": "victim_user_sub",
     "actor_id": "attacker_user_sub",
     "activity_type": "tip",
     "target_type": "post",
     "target_id": "some_post_id",
     "metadata": {"amount_cents": 10000}
   }
   ```
3. The server writes an activity entry to the victim's feed indicating the victim received a $100 tip from the attacker. No actual money changes hands; the ledger is not modified. The feed entry is fictitious.
4. The victim's activity feed now shows fabricated social events. If the victim uses this feed to track earnings or social interactions, they receive misleading information.

### Variants

- **Noise/harassment**: Flood a target user's feed with hundreds of fake activity entries by replaying the request in a loop. This degrades the usefulness of the feed for the target user.
- **Social metric manipulation**: Inject fake `follow` entries to inflate perceived follower counts in feed aggregations or analytics dashboards.
- **Impersonation**: Craft `actor_id` = celebrity user, `user_id` = victim → the victim's feed shows that a well-known creator interacted with their content, creating misleading social proof.
- **Analytics poisoning**: Platform-side aggregations that count tip events, follow events, or engagement from the activity feed will be skewed by injected entries.

### Blast radius

This is an **IDOR (Insecure Direct Object Reference)** at the feed write level. It does not escalate to data exfiltration or account takeover, but it allows cross-user data corruption of the activity feed for any platform user. The attacker only needs a valid session (any tier).

**Rate of attack**: The endpoint has no rate limiting. A script can replay the POST request thousands of times per minute, each with a different fabricated `activity_type` and `metadata`. A single attacker session can flood any target user's feed with arbitrary noise in seconds, making the feed entirely unusable for the target.

**Notification side-effects**: If the `record_activity` call triggers notification webhooks, push notifications, or email alerts (depending on how the activity feed is integrated with the notification subsystem in `NOTIFY-001`), each injected activity entry could also generate a spurious notification to the target user. This would be experienced as notification spam even if the user is not actively viewing their activity feed.

## 4. Fix Design (Code-Level)

### Minimal fix (single-line, Option A — preferred)

Replace `user_id=body.user_id` with `user_id=session["user_sub"]` at `app/routers/activity_feed.py:158`:

```python
# BEFORE (app/routers/activity_feed.py:158):
    item = activity_feed_service.record_activity(
        user_id=body.user_id,

# AFTER:
    item = activity_feed_service.record_activity(
        user_id=session["user_sub"],   # always use authenticated identity
```

This is a one-line change. The `body.user_id` field in `RecordActivityIn` can be removed from the model or retained (it will simply be ignored). Removing it is cleaner and signals the intent.

### Admin injection path (Option B — if needed)

If an admin-accessible injection path is required for test or operational tooling, add a separate endpoint guarded by `require_admin_session`:

```python
# app/routers/activity_feed.py — existing user endpoint (patched):
@router.post("/feed/record")
def record_activity(
    body: RecordActivityIn,
    session=Depends(require_ui_session),
):
    item = activity_feed_service.record_activity(
        user_id=session["user_sub"],  # enforced: writes only to caller's feed
        actor_id=body.actor_id,
        activity_type=body.activity_type,
        target_type=body.target_type,
        target_id=body.target_id,
        metadata=body.metadata,
    )
    return {"ok": True, "activity_id": item["activity_id"], "created_at": item["created_at"]}


# New admin endpoint in admin_router:
@admin_router.post("/feed/record")
def admin_record_activity(
    body: RecordActivityIn,   # body.user_id now used intentionally under admin gate
    session=Depends(require_admin_session),
):
    """Admin-only: inject activity item on behalf of any user (for testing/support)."""
    item = activity_feed_service.record_activity(
        user_id=body.user_id,   # admin may specify arbitrary target user_id
        actor_id=body.actor_id,
        activity_type=body.activity_type,
        target_type=body.target_type,
        target_id=body.target_id,
        metadata=body.metadata,
    )
    return {"ok": True, "activity_id": item["activity_id"], "created_at": item["created_at"]}
```

Option A (patching the single call site) is recommended for the immediate fix. Option B is an enhancement if admin tooling requires the injection capability.

### Model change (optional cleanup)

Remove `user_id` from `RecordActivityIn` in `app/models.py` to prevent confusion:

```python
# app/models.py — RecordActivityIn (remove user_id field):
class RecordActivityIn(BaseModel):
    actor_id: str
    activity_type: str
    target_type: str
    target_id: str
    metadata: Optional[Dict[str, Any]] = None
    # user_id: str  ← remove; derived from session
```

If other non-user callers depend on `user_id` in this model, retain it as an optional field that is ignored at the user endpoint.

### Dev/Prod Parity (SECOPS-007)

The `activity_feed` table is a DynamoDB table present in both dev and production environments. The fix is a pure Python routing change with no AWS-specific code path. `require_ui_session` works identically in dev mode (via cookie-based session) and production (via Cognito JWT or cookie). No parity concern is introduced.

### Backward compatibility

Any existing test scripts or internal tooling that calls `POST /feed/record` with `user_id` pointing to a different user will now silently write to the caller's own feed instead. This is the correct behavior. If the admin injection path is needed, those callers should be migrated to the new `admin_router` endpoint.

## 5. Testing, Verification & Rollout

### Regression test — IDOR fix (pytest offline, fails-before / passes-after)

```python
# tests/test_activity_feed_idor.py
import pytest


def test_record_activity_uses_session_user_not_body_user(
    test_client, alice_session, bob_user_sub
):
    """
    FAILS BEFORE FIX: POST /feed/record with user_id=bob writes to Bob's feed;
                       response is 200 and item.user_id == bob_user_sub.
    PASSES AFTER FIX:  item is written with user_id == alice_user_sub regardless
                       of what was passed in body.user_id.
    """
    resp = test_client.post(
        "/ui/feed/record",
        json={
            "user_id": bob_user_sub,   # attacker tries to write to Bob's feed
            "actor_id": alice_session["user_sub"],
            "activity_type": "tip",
            "target_type": "post",
            "target_id": "post_123",
            "metadata": {"amount_cents": 100},
        },
        cookies=alice_session["cookies"],
        headers={"x-csrf-token": alice_session["csrf_token"]},
    )
    assert resp.status_code == 200
    data = resp.json()
    assert data["ok"] is True

    # Verify the item was written to Alice's feed, NOT Bob's
    from app.services import activity_feed as svc
    from app.core.tables import T

    item = T.activity_feed.get_item(
        Key={"user_id": alice_session["user_sub"], "activity_id": data["activity_id"]}
    ).get("Item")
    assert item is not None, "Item should be in Alice's feed"

    # Verify Bob's feed was NOT polluted
    bob_items = T.activity_feed.query(
        KeyConditionExpression="user_id = :u",
        ExpressionAttributeValues={":u": bob_user_sub},
    ).get("Items", [])
    bob_ids = {i["activity_id"] for i in bob_items}
    assert data["activity_id"] not in bob_ids, "Bob's feed must not be polluted"


def test_record_activity_rejects_cross_user_injection(
    test_client, alice_session, bob_user_sub
):
    """
    Alternative assertion style: verify no 2xx allows writing to another user's feed.
    The endpoint should return 200 but write to alice, not bob.
    """
    resp = test_client.post(
        "/ui/feed/record",
        json={
            "user_id": bob_user_sub,
            "actor_id": alice_session["user_sub"],
            "activity_type": "follow",
            "target_type": "user",
            "target_id": bob_user_sub,
        },
        cookies=alice_session["cookies"],
        headers={"x-csrf-token": alice_session["csrf_token"]},
    )
    assert resp.status_code == 200
    # Regardless of body.user_id, the written item must have user_id == Alice
    data = resp.json()
    from app.core.tables import T
    # Check the item was NOT written to bob
    bob_item = T.activity_feed.get_item(
        Key={"user_id": bob_user_sub, "activity_id": data["activity_id"]}
    ).get("Item")
    assert bob_item is None
```

### Manual QA steps

1. Start the dev stack: `just up`.
2. Authenticate as Alice via the `/login` page.
3. Obtain Alice's CSRF token from the `ui_csrf` cookie.
4. Call `POST /ui/feed/record` with `user_id=<bob_sub>` and Alice's session/CSRF cookies.
5. **Before fix**: Bob's feed (`GET /ui/feed?user_id=<bob_sub>`) shows the injected entry.
6. **After fix**: the entry appears in Alice's feed only; Bob's feed is unchanged.

### Metrics and observability

- Consider adding a structured log line at `INFO` level when `record_activity` is called directly via this endpoint: `"activity_feed.record_direct user=%s activity_type=%s"`. This provides an audit trail for any remaining direct calls, which should be rare in production (activity is normally created by service-layer hooks).
- A spike in `record_activity` direct endpoint calls in production metrics (distinct from service-layer calls) would indicate automated abuse of this endpoint.

### Rollback

Single-line code change. Rollback is a code revert and redeploy. No DynamoDB changes. No data to reverse — items already written to victim feeds by the exploit would need manual cleanup if the endpoint was actively abused before the fix.

### Risks

- **Test-script breakage**: Any existing test or automation that relied on passing an arbitrary `user_id` to this endpoint will now receive activity entries on the calling user's feed instead of the target user. This is intentional and correct; affected scripts should be updated.
- **Data already corrupted**: If the endpoint was exploited before the fix, fabricated activity entries will remain in victim feeds. These can be identified and removed via a DynamoDB scan for entries with an `activity_id` created by users other than the `user_id` owner, if audit logs are available.

### Linting / static analysis prevention

Add a custom linting rule or a pre-commit comment to flag any endpoint where `Depends(require_ui_session)` is present but `session["user_sub"]` is not used when the handler performs a write operation. This is a class of vulnerability that a simple AST-based check can detect: `POST`/`PUT`/`PATCH`/`DELETE` handlers that have `session=Depends(require_ui_session)` but contain no reference to `session["user_sub"]` or `session.get("user_sub")` should be flagged for review. This prevents the same class of IDOR from appearing in future endpoints.

### Effort and sequencing

**S** — one-line change at the call site, one optional model change, and a unit test. Total implementation time: under 1 hour. The linting rule is an optional follow-on that can be added as a separate PR.
