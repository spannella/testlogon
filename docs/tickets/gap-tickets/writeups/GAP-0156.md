# GAP-0156: /delegates route missing from App.tsx — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement.** `DelegatesPage` — the page that lets a creator manage their delegates (assign, remove, update permissions) — exists as a fully-implemented React component at `frontend/src/pages/delegates/DelegatesPage.tsx` but is not reachable via any route in the single-page application. There is no `<Route path="delegates" ...>` entry in `frontend/src/App.tsx`. Navigating to `/delegates` renders the application's catch-all 404 page.

**Severity:** HIGH — an entire product surface (delegate management) is invisible to end users even though the underlying backend API and frontend component are both complete.

**Source ticket:** DELEGATE-001  
**Status:** Open  
**Owning area:** Frontend routing / DELEGATE feature set  
**Effort:** S (< 1 hour)

**Verdict from code investigation:** Claim confirmed. The route is absent. A parallel lazy-import (`DelegationApiKeysPage`) was added for the API-key sub-page and did receive a route at line 346, but the parent `DelegatesPage` — which manages the delegate *relationships* themselves — was never wired.

**Related tickets:** DELEGATE-004 (GAP-0157), DELEGATE-005 (GAP-0158), GAP-0037 (admin dead-code pattern).

---

## 2. Current-State Investigation (root cause)

### Lazy-import present, route absent

`frontend/src/App.tsx:52-54` declares a lazy import for `DelegationApiKeysPage`:

```tsx
const DelegationApiKeysPage = lazy(
  () => import("@/pages/delegates/DelegationApiKeysPage"),
);
```

That component is routed at `frontend/src/App.tsx:346`:

```tsx
<Route path="delegation-api" element={<DelegationApiKeysPage />} />
```

However, `frontend/src/pages/delegates/DelegatesPage.tsx` — confirmed to exist on disk — has **no corresponding lazy-import declaration** and **no `<Route>` entry anywhere in `App.tsx`**. A `grep -n "DelegatesPage\|delegates" frontend/src/App.tsx` returns only the two `DelegationApiKeysPage` lines; the path string `"delegates"` does not appear at all in the route tree.

### Why the split exists

The two pages serve distinct purposes:

- `DelegatesPage.tsx` — manage the delegation *relationship* (invite delegate by email, set permissions bitmask, revoke, view pending/active delegates). This is the creator-facing CRUD page for DELEGATE-001.
- `DelegationApiKeysPage.tsx` — manage the *API keys* a delegate creates to call the delegation API programmatically. This is a follow-on feature (DELEGATE-005).

When DELEGATE-005 work added `DelegationApiKeysPage` and its route, the already-missing `DelegatesPage` route was not noticed. The gap survived because:

1. `DelegatesPage` is never imported in `App.tsx`, so TypeScript never complains about an unused import.
2. There are no E2E tests that navigate to `/delegates` because the route does not exist; the tests that do exist for the delegations feature use direct API calls.
3. The Sidebar navigation component that should link to `/delegates` may or may not have an entry (the nav can render without the route resolving correctly because React Router silently falls through to the 404 component).

### Dev vs prod behaviour

The failure is identical in both environments: React Router renders the 404/not-found component for `/delegates`. There is no environment-specific gating or feature flag involved.

---

## 3. Impact / Exploit / Blast Radius

**Who is affected.** Every creator who needs to manage their delegate list. Without this route:

- Creators cannot invite new delegates via the UI.
- Creators cannot modify delegate permissions via the UI.
- Creators cannot revoke a delegate via the UI.
- All of these actions are only available through direct API calls (which are not exposed to ordinary users).

**Financial / data integrity.** No financial data is at risk. The backend delegate CRUD API remains fully functional; the gap is purely navigational. However, because delegate management is unavailable in the UI, delegated access effectively becomes a hidden/unused feature, meaning any creator-facing revenue tied to delegated workflows (e.g., a delegate posting on a creator's behalf) is inaccessible through normal channels.

**Security.** This is not a security vulnerability — the missing route *reduces* surface area, not increases it. No unauthorised access is possible because the page simply cannot be reached.

**Compliance / SLA.** DELEGATE-001 is a shipped feature. Any creator support ticket asking "where do I manage my delegates?" cannot be answered with a UI walkthrough. If SLAs commit to the feature being accessible, this is a breach.

## 4. Fix Design (code-level)

### Step 1 — Add the lazy import to App.tsx

Add a new `const` after the existing `DelegationApiKeysPage` lazy import
(`frontend/src/App.tsx:52-54`):

```tsx
const DelegatesPage = lazy(
  () => import("@/pages/delegates/DelegatesPage"),
);
```

### Step 2 — Add the route to the authenticated route tree

Add a `<Route>` entry adjacent to the existing `delegation-api` route
(`frontend/src/App.tsx:346`):

```tsx
<Route path="delegates" element={<DelegatesPage />} />
<Route path="delegation-api" element={<DelegationApiKeysPage />} />
```

The path `"delegates"` is consistent with the existing naming convention
(tickets → `/tickets`, contacts → `/contacts`, etc.).

### Step 3 — Verify Sidebar navigation

Inspect `frontend/src/components/layout/Sidebar.tsx` (or wherever nav links
are defined) to confirm that a `<Link to="/delegates">` entry already exists.
If absent, add it alongside the delegation-api link under whatever navigation
group hosts delegation-related items. This is cosmetic but required for the
route fix to be discoverable without manually typing the URL.

The Sidebar is the primary navigation surface for authenticated users. Without
a sidebar entry, even after the route is added, creators will need to know the
exact URL path. A sidebar link should use a representative icon (e.g.,
`UsersRound` from lucide-react) and label it "Delegates" or "Manage Delegates".

### Step 4 — Confirm DelegatesPage imports

Before shipping, verify that `DelegatesPage.tsx` imports compile cleanly
and that any backend endpoints it calls (`GET /ui/delegates`, `POST /ui/delegates`,
`DELETE /ui/delegates/{delegate_id}`, etc.) are registered and working. These
are DELEGATE-001 backend endpoints and should already be tested, but the
absence of the route means they have never been exercised through the real
browser render path.

Compile check:

```bash
cd frontend && npx tsc --noEmit 2>&1 | grep delegates
```

If TypeScript reports no errors for the delegates directory, proceed with
deployment.

### Dev/Prod parity (SECOPS-007)

This change is purely a React Router configuration change. No backend code is
touched, no AWS services are involved, and no feature flags are required. The
fix is identical in dev and prod environments. There is no mock/real
bifurcation to maintain.

The lazy `import()` pattern used by all pages in `App.tsx` means the
`DelegatesPage` bundle chunk is only downloaded by the browser when the user
first navigates to `/delegates`. This is consistent with every other page in
the router and introduces no additional load on the server or CDN at startup.

### Alternatives considered

- **Route the page under `/delegation-api/delegates`** — rejected. The page
  manages the delegation *relationship*, not the API keys; nesting it under
  the API-key path is semantically wrong and would break any bookmarks.
- **Redirect `/delegates` → `/delegation-api`** — rejected for the same
  reason; the two pages serve different purposes and user mental models differ.
- **Feature-flag the route** — not needed. The page and backend are already
  complete and tested; the absence of the route is a pure oversight, not an
  intentional gate.
- **Merge `DelegatesPage` and `DelegationApiKeysPage` into one combined page**
  — rejected. Delegate *relationship* management (invite, revoke, view status)
  is conceptually distinct from API key management (create, rotate, revoke
  keys). Keeping them on separate routes allows for independent navigation,
  deep-linking, and future permission checks on each page independently.

## 5. Testing, Verification & Rollout

### Regression test (fails-before, passes-after)

Add a Playwright test to `frontend/e2e/delegates.spec.ts` (or the existing
delegation spec if one exists):

```typescript
import { test, expect } from "@playwright/test";
import { injectAuth } from "./helpers/auth";

test.describe("GAP-0156: /delegates route", () => {
  test("renders DelegatesPage (not a 404 fallback)", async ({ page }) => {
    // Inject creator session for Alice
    await injectAuth(page, "alice");

    // Before fix: React Router falls through to the catch-all <Route path="*">
    // which renders the app's NotFound component containing "Page not found".
    // After fix: <Route path="delegates"> matches and mounts DelegatesPage.
    await page.goto("/delegates");
    await page.waitForLoadState("domcontentloaded");

    // Negative assertion: the not-found state must NOT be visible.
    // (Works whether the 404 page says "Not Found", "Page not found", "404", etc.)
    await expect(page.getByText(/not found/i)).not.toBeVisible({ timeout: 5000 });

    // Positive assertion: DelegatesPage renders a relevant heading.
    // The exact text depends on DelegatesPage implementation; adjust as needed.
    await expect(
      page.getByRole("heading", { name: /delegates/i })
    ).toBeVisible({ timeout: 8000 });
  });

  test("lazy chunk for DelegatesPage is loaded (no chunk error)", async ({ page }) => {
    const chunkErrors: string[] = [];
    page.on("pageerror", (err) => {
      if (/loading chunk/i.test(err.message)) chunkErrors.push(err.message);
    });

    await injectAuth(page, "alice");
    await page.goto("/delegates");
    await page.waitForLoadState("networkidle");

    expect(chunkErrors).toHaveLength(0);
  });
});
```

**Why it fails before the fix:** React Router has no `"delegates"` path in the
tree; it falls through to the wildcard `<Route path="*">` which renders a
not-found state. The heading assertion times out or the "not found" text is
visible.

**Why it passes after the fix:** The new
`<Route path="delegates" element={<DelegatesPage />} />` entry matches the
path; React `lazy()` downloads the chunk; `DelegatesPage` mounts and renders
its heading.

No backend change → no new pytest test required. The existing delegation

7. Confirm that navigating to a non-existent path (e.g., `/foobar`) still

### Observability

No new backend metrics needed. Frontend navigation errors (unhandled chunk
load failures) can be tracked via the existing client-side error boundary if
one is configured. The fix adds no new endpoints or DynamoDB operations, so
there is no operational overhead.

If the application has a client-side analytics layer (e.g., a page-view event),
navigations to `/delegates` will now appear in the analytics stream —
previously they were swallowed by the 404 fallback.

### Rollback

The change is a two-line React Router addition plus an optional Sidebar link.
Rollback: remove the `<Route>` line and the `const DelegatesPage = lazy(...)` 
import, then redeploy the frontend. No database migrations, no feature flags,
no server restarts. The lazy-loaded JavaScript chunk is cached in the CDN but
serves no function without the route; it can be safely ignored.

### Risk

**Very low.** The route addition cannot break existing functionality because
the path `"delegates"` was previously unmapped. No user can be relying on
the 404 behaviour of that path. The `DelegatesPage` component was implemented
as part of DELEGATE-001 and compiles successfully; its API calls go to backend
endpoints that are independently tested. The only risk is if `DelegatesPage`
has an unresolved compile dependency, which the `npx tsc --noEmit` check in
Step 4 will catch before deployment.

### Effort

**S** — approximately 15–20 minutes of code change plus 30 minutes for E2E
test authoring. Total: under 1 hour. Can be batched with any other
DELEGATE-series ticket in the same PR for a single review cycle.
