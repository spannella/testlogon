# GAP-0377: Clip Job Exception Never Calls `fail_job` — Remediation Write-up

> Source ticket: VOD-015 · Severity: HIGH · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** When `process_clip_job` in `app/services/video_clipper.py` raises any exception — S3 download failure, FFmpeg crash, timeout, or any other error — the job record in DynamoDB is left permanently in `status = "running"`. The bare `except Exception: logger.exception(...); raise` block at line 305 logs the error but never calls `fail_job(job_id, ...)`. The worker that picked up the job will crash or move on, and no retry or terminal-failure transition is ever written. The job is frozen in `running` forever.

**Verdict:** Confirmed. Lines 305–307 of `app/services/video_clipper.py` are:

```python
    except Exception:
        logger.exception("Clip job %s failed", job_id)
        raise
```

There is no call to `fail_job` anywhere in this block. The `fail_job` function exists and is correct at `app/services/transcode_job_store.py:244`; it just is not called.

**Severity and area.** HIGH / Video Processing. A stuck-running job is never retried by the worker (workers typically skip `running` jobs already claimed by another worker), so the user's clip creation silently hangs at `status = "running"` with no user-visible error and no automatic recovery.

**Related tickets.** VOD-015 (source feature), GAP-0379 (identical pattern in `video_concatenator.py`). The two bugs are parallel and should be fixed together.

---

## 2. Current-State Investigation (root cause)

### The job processing loop

`process_clip_job` at `app/services/video_clipper.py:224` orchestrates the full clip pipeline:

1. Downloads source from S3 (line 254).
2. Calls `execute_clip` via FFmpeg (line 258).
3. Uploads clip to S3 (line 268).
4. Updates video metadata in DynamoDB (line 271).
5. Enqueues a standard transcode job (line 288).
6. Calls `complete_job(job_id, ...)` (line 298).

The `try` block begins at line 250. The `except` clause at line 305 reads:

```python
# app/services/video_clipper.py:305-309
    except Exception:
        logger.exception("Clip job %s failed", job_id)
        raise
    finally:
        shutil.rmtree(scratch_dir, ignore_errors=True)
```

No transition to `failed` or `queued` (retry) state is written before re-raising. The `complete_job` call on line 298 is only reached on the success path; on any exception the job record retains `status = "running"` from the moment the worker claimed it.

### What `fail_job` does

`app/services/transcode_job_store.py:244–294` implements the correct retry/fail logic:

```python
def fail_job(job_id: str, error_message: str, attempt: int) -> Dict[str, Any]:
    ts = now_ts()
    max_attempts = S.transcode_max_attempts
    new_attempt = attempt + 1
    if new_attempt < max_attempts:
        # back to queued with exponential-backoff retry
        T.transcode_jobs.update_item(...)   # status = "queued", next_retry_at = ...
    else:
        # terminal failure
        T.transcode_jobs.update_item(...)   # status = "failed"
    return get_job(job_id)
```

This function already handles both the "retry available" and "terminal failure" paths and writes the `error_message`, `attempt`, and `next_retry_at` fields. It is used by the transcode worker for regular transcode jobs but is never called in the clip-job path.

### How the job arrives with `attempt`

`create_job` at `app/services/transcode_job_store.py` sets `attempt = 0` on creation. The job dict passed to `process_clip_job` carries this field. The call to `fail_job` must pass `job.get("attempt", 0)` to allow correct incrementation.

### How the worker claims a job

Before `process_clip_job` is invoked, the worker loop calls a `claim_job` (or equivalent) function that atomically transitions the job from `status = "queued"` to `status = "running"` and writes its `worker_id`. This ensures no other worker picks up the same job concurrently. The job stays `running` until either `complete_job` or `fail_job` writes the final state. If neither is called — as is the case today on any exception — the job is stranded: it is in `running` state with a `worker_id` that has already exited, and no other worker will touch it.

The worker loop's main polling interval (typically 15–30 seconds in dev) does not include a "reclaim stale running jobs" pass. Production deployments may add a separate dead-letter reaper, but none is present in this codebase. The only recovery path is manual operator intervention.

### Runtime manifestation

After any exception:

- `T.transcode_jobs` record: `status = "running"`, `worker_id = <worker-id>`, no `error_message`, no `completed_at`.
- Worker queue: the job is never re-enqueued; workers poll for `status IN ("queued")` so it is invisible to all workers.
- User-visible state: the clip video record stays at `status = "pending_encoding"` indefinitely with no way to detect the failure or trigger a re-attempt through any UI or API surface.
- In production under AWS ECS/Lambda, a container restart or timeout leaves exactly the same artifact in DynamoDB.

## 3. Impact / Exploit / Blast Radius

**User impact.** Any clip creation attempt that encounters an error — including transient S3 errors, FFmpeg not installed, source file not yet available, scratch-disk full, or encoding timeout — will leave the clip permanently stuck. The user has no error message and no retry path through the UI.

**Operational impact.** In production, `running` jobs accumulate in the job table. A monitor that counts jobs by status will show an ever-growing `running` count. There is no automatic recovery; an operator must manually update the DynamoDB record to `failed` or delete it to unblock the user.

**Blast radius.** Limited to users who attempt clip creation when any infrastructure condition causes an exception. No data is corrupted; the source video and partially-created clip video record are left intact. The financial impact is indirect: users who encounter the bug may churn.

**Security.** No confidentiality or integrity concern. The scratch directory is cleaned up by the `finally` block (line 308–309), so no temporary files are left on disk even when an exception is raised mid-job.

**Accumulation over time.** In a busy production environment with thousands of clip-creation requests per day, even a 0.1% error rate produces dozens of zombie `running` jobs per day. Dashboard queries that show "active jobs" will inflate, obscuring the true worker queue depth. Capacity planning and autoscaling decisions based on the `running` job count will be systematically wrong.

## 4. Fix Design (code-level)

### Minimal fix: call `fail_job` in the `except` block

```python
# app/services/video_clipper.py — replace lines 305-307
    except Exception as e:
        logger.exception("Clip job %s failed", job_id)
        try:
            from app.services.transcode_job_store import fail_job
            fail_job(job_id, str(e), job.get("attempt", 0))
        except Exception:
            logger.exception("fail_job itself failed for clip job %s", job_id)
        raise
```

Key design choices:

- **`job.get("attempt", 0)`**: The job dict is available in the outer scope (line 237 assigns `job_id = job["job_id"]`; the full `job` dict is a parameter). Passing the current attempt count allows `fail_job` to compute retries correctly.
- **Inner try/except around `fail_job`**: If the DynamoDB call in `fail_job` itself fails (e.g., DDB Local is down), we log the secondary failure but still re-raise the original exception. This prevents a `fail_job` crash from masking the real error in the log.
- **`raise` is preserved**: The caller (worker loop) still sees the exception, allowing it to log and move on. The job state is now correctly updated before the exception propagates.

### Full corrected function signature (relevant lines)

```python
async def process_clip_job(job: Dict[str, Any]) -> None:
    ...
    job_id = job["job_id"]
    ...
    try:
        # ... existing success path ...
        complete_job(job_id, output_manifest_uri=clip_s3_key)
        logger.info("Clip job %s completed ...", job_id, ...)

    except Exception as e:                                        # ← was: except Exception:
        logger.exception("Clip job %s failed", job_id)
        try:                                                      # ← new
            from app.services.transcode_job_store import fail_job # ← new
            fail_job(job_id, str(e), job.get("attempt", 0))      # ← new
        except Exception:                                         # ← new
            logger.exception("fail_job itself failed for %s", job_id)  # ← new
        raise
    finally:
        shutil.rmtree(scratch_dir, ignore_errors=True)
```

### Dev/Prod parity (SECOPS-007)

`fail_job` calls `T.transcode_jobs.update_item(...)` which routes through `app/core/tables.py → T.transcode_jobs`. In dev this is DynamoDB Local (port 8001); in production it is the real DynamoDB table. The `fail_job` function itself already handles both environments because `T.transcode_jobs` is configured from `S.ddb_transcode_jobs_table`. No environment-specific branching is needed in this fix.

`process_clip_job` is called by the worker polling loop which runs in the same process as the FastAPI app in dev and as an ECS task/Lambda in production. The fix is identical in both environments.

### Backward compatibility and migration

No DynamoDB schema changes. The `error_message` and `next_retry_at` attributes written by `fail_job` are already present in the `transcode_jobs` table schema (used by the regular transcode path). No migration is required.

### Alternative considered: wrap at the worker loop level

One alternative is to catch exceptions in the worker loop and call `fail_job` there rather than inside `process_clip_job`. This is rejected because:

1. The worker loop is shared across job types; centralizing error handling there would require it to know each job type's `attempt` field, coupling concerns.
2. The identical fix is needed for `process_concat_job` (GAP-0379); it is cleaner to fix both at the service function level where `job` is already in scope.
3. Moving the `fail_job` call to the worker loop would mean the worker loop needs to import `fail_job` and manage the exception-to-state mapping — duplicating logic that `fail_job` already owns correctly.

### Alternative considered: worker-level stale-job reaper

A background task that periodically scans for `status = "running"` jobs older than a threshold and re-queues them would paper over the bug without fixing the root cause. This is rejected because:

1. It adds latency to recovery (the reaper period) rather than failing immediately.
2. It is ambiguous whether a `running` job is genuinely being processed by a live worker or is a zombie; the reaper would need cross-worker liveness checks.
3. The correct fix is a two-line change; adding a reaper instead is over-engineering the wrong solution.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline — fails before, passes after)

```python
# tests/test_video_clipper_fail_job.py
import pytest
from unittest.mock import patch, AsyncMock, MagicMock

@pytest.mark.asyncio
async def test_process_clip_job_calls_fail_job_on_exception(mock_ddb_tables):
    """Verify fail_job is called when process_clip_job encounters an error."""
    job = {
        "job_id": "job_clip_001",
        "video_id": "vid_001",
        "source_uri": "videos/owner/vid_001/source.mp4",
        "clip_start_seconds": "0",
        "clip_end_seconds": "10",
        "tenant_id": "user_001",
        "attempt": 0,
    }

    # Make S3 download fail
    with patch("boto3.client") as mock_boto:
        mock_s3 = MagicMock()
        mock_boto.return_value = mock_s3
        mock_s3.download_file.side_effect = Exception("S3 access denied")

        with patch("app.services.transcode_job_store.fail_job") as mock_fail:
            from app.services.video_clipper import process_clip_job
            with pytest.raises(Exception, match="S3 access denied"):
                await process_clip_job(job)

            mock_fail.assert_called_once()
            call_args = mock_fail.call_args
            assert call_args[0][0] == "job_clip_001"      # job_id
            assert "S3 access denied" in call_args[0][1]  # error_message
            assert call_args[0][2] == 0                    # attempt

@pytest.mark.asyncio
async def test_process_clip_job_does_not_call_fail_job_on_success(mock_ddb_tables):
    """Verify fail_job is NOT called on a successful run."""
    job = {
        "job_id": "job_clip_002",
        "video_id": "vid_002",
        "source_uri": "videos/owner/vid_002/source.mp4",
        "clip_start_seconds": "0",
        "clip_end_seconds": "5",
        "tenant_id": "user_001",
        "attempt": 0,
    }
    with patch("boto3.client"), \
         patch("app.services.video_clipper.execute_clip", new_callable=AsyncMock) as mock_exec, \
         patch("app.services.transcode_job_store.complete_job"), \
         patch("app.services.transcode_job_store.create_job"), \
         patch("app.services.transcode_job_store.fail_job") as mock_fail:
        from pathlib import Path
        from app.services.video_clipper import ClipResult
        mock_exec.return_value = ClipResult(
            output_path=Path("/tmp/clip.mp4"), duration_seconds=5.0, method="copy"
        )
        from app.services.video_clipper import process_clip_job
        await process_clip_job(job)
        mock_fail.assert_not_called()
```

**Before fix:** `mock_fail.assert_called_once()` raises `AssertionError` — `fail_job` is never called.
**After fix:** assertion passes; `fail_job` is called with the correct `job_id`, error string, and `attempt=0`.

### Manual QA steps

1. Start the dev stack (`just up`).
2. Create a clip job targeting a source video whose S3 key does not exist.
3. Trigger the clip worker (or call `process_clip_job` directly).
4. Query `T.transcode_jobs` via DynamoDB Local admin console or `aws ddb scan --table-name TranscodeJobs --endpoint-url http://localhost:8001`.
5. **Before fix:** confirm `status = "running"`, no `error_message`.
6. **After fix:** confirm `status = "queued"` (if attempts remain) or `status = "failed"`, with `error_message` populated.

### Metrics and observability

Add a log-based metric alert on `"fail_job itself failed"` to catch the rare case where the secondary `fail_job` DDB call also fails. The existing `logger.exception("Clip job %s failed")` line already emits a structured log; route that to a CloudWatch alarm in production.

Consider adding a DynamoDB stream-based canary: if a `TranscodeJobs` record has `status = "running"` and `updated_at < now - 1800` (30 minutes), fire a CloudWatch alarm. This acts as a catch-all for any future failure path that similarly misses a `fail_job` call, regardless of job type.

### Rollout

- **Effort:** S (small — two lines changed, no schema changes).
- **Risk:** Very low. The fix only adds a `fail_job` call in the exception path, which was previously a no-op (the job was left running anyway).
- **Sequencing:** Fix GAP-0377 and GAP-0379 in the same commit (identical pattern). No deployment dependencies.
- **Rollback:** Reverting the two lines restores the original (broken) behavior; no data migration needed.

### Acceptance criteria

The fix is complete when:
1. A clip job that fails during S3 download transitions to `status = "queued"` (if `attempt < max_attempts`) or `status = "failed"` (if at max attempts) with a non-empty `error_message` in DynamoDB.
2. `fail_job` is never called on the success path (verified by the `test_process_clip_job_does_not_call_fail_job_on_success` test).
3. The two new pytest tests in `tests/test_video_clipper_fail_job.py` pass green in CI.
4. Manual QA in dev confirms the job record transitions to `failed` rather than staying `running` after a simulated S3 error.
