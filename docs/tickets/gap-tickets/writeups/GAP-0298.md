# GAP-0298: `GET /ui/licenses/compliance/content/{content_id}` blocks admin access — Remediation Write-up

> ~5 pages. Fix-oriented. No investigation doc exists; the claim is verified directly against the codebase.

## 1. Summary & Classification

**Bug statement:** The `GET /ui/licenses/compliance/content/{content_id}` endpoint enforces a strict `creator_id == session["user_sub"]` ownership check and returns HTTP 403 for any caller who is not the content's creator — including admins and root users. LICENSE-006 specified "Content owner or admin" as the allowed audience. Admins cannot review the compliance status of content they do not own without using the separate admin scan endpoint, which gives aggregate data and does not provide per-content detail.

- **Severity:** HIGH
- **Source ticket:** LICENSE-006
- **Status:** Open — no role bypass is present in the current code
- **Owning area:** License Compliance / Auth
- **Claim verdict:** CONFIRMED. The enforcement is at `app/routers/license_compliance.py:76-77`. The session dict returned by `require_ui_session` contains a `role` field (set in `app/services/sessions.py:398`) that is never consulted by this endpoint.

**Related tickets:** LICENSE-006 (parent); GAP-0298 (this ticket); SECOPS-007 (dev/prod parity).


## 2. Current-State Investigation (root cause)

**File:** `app/routers/license_compliance.py:65-78`

```python
@license_compliance_router.get(
    "/content/{content_id}", response_model=ComplianceStatusOut
)
async def content_compliance_detail(
    content_id: str,
    session: dict = Depends(require_ui_session),
):
    record = svc.get_compliance_status(content_id=content_id)
    if not record:
        raise HTTPException(404, "No compliance record for this content")
    # Creator may only view their own content's status.
    if record.get("creator_id") and record["creator_id"] != session["user_sub"]:
        raise HTTPException(403, "Not authorized to view this content's compliance")  # ← blocks admins
    return ComplianceStatusOut(**record)
```

The `session` dict returned by `require_ui_session` (`app/services/sessions.py:395-402`) always includes a `role` field:

```python
out = {
    "user_sub": resolved_user_sub,
    "session_id": session_id,
    "role": role.value,   # e.g. "admin", "root", "user"
    "ip": str(it.get("ip") or ""),
}
```

The endpoint reads `session["user_sub"]` but never checks `session["role"]`. The comparison on line 76 is evaluated for every non-creator caller regardless of privilege level.

**Why the oversight occurred:** The comment on line 75 says "Creator may only view their own content's status" — it was written as a creator-scoped endpoint without ever adding the admin bypass path. The admin-level endpoints in the same router (`license_compliance_admin_router`, lines 139+) are correctly guarded with `require_admin_or_root`, but the creator-scoped endpoints have no escalation path.

**Affected endpoints on the same router:**

The same gap applies to two adjacent endpoints in the creator-scoped router that also lack admin bypass:
- `GET /ui/licenses/compliance/content/{content_id}/refs` (line 81-88) — lists license refs; no creator check present (returns data without auth check beyond session), but worth auditing.
- `GET /ui/licenses/compliance/content/{content_id}/flags` (line 91-100) — lists flags; also lacks creator check, returns flags for any authenticated caller. This is a separate issue.

The primary gap is on the `content_compliance_detail` endpoint.

**Dev vs prod behaviour:** Identical in both environments. The `require_ui_session` dependency correctly populates `role` in both dev and prod (the admin session setup scripts in `e2e_admin_session_setup.py` write role-bearing JWTs); the issue is the endpoint ignoring the role value.

**Auth import already present:** `app/auth/policy.py`'s `require_admin_or_root` and `app/auth/roles.py`'s `Role` are already imported at the top of `license_compliance.py` (lines 20 and 22 import from `app.models`; the policy module is imported for the admin router). Adding the role check requires only a one-line change to the 403 guard.


## 3. Impact / Exploit / Blast Radius

**Who is affected:**

- **Platform admins (role=ADMIN):** Cannot call `GET /ui/licenses/compliance/content/{content_id}` for content they do not own. If an admin wants to investigate a compliance complaint about a specific piece of content (e.g., following a DMCA flag), they must use the indirect `GET /ui/admin/licenses/compliance/issues` endpoint which does not return per-content compliance detail — it returns aggregate issues. The admin must then cross-reference externally.
- **Root users (role=ROOT):** Same restriction applies.

**Operational impact:** Content moderation and legal/compliance workflows are impaired. An admin responding to a license violation report cannot call the endpoint directly. They must use the aggregate issues list and manually correlate, adding latency to compliance responses.

**Security non-issue:** This is an **under-permissioning** bug, not an over-permissioning one. Regular users cannot see other users' compliance records; that check is correct. The only broken case is that admins and root users — who should have elevated access by design — are blocked.

**Blast radius:** MEDIUM — affects admin and root users only; no regular user data is exposed or corrupted. The impact is operational friction rather than a data breach or financial loss. It is classed HIGH because compliance workflows are a legal/regulatory obligation and blocking admins from accessing compliance data can cause missed deadlines.

**Exploit scenario (operational):**

1. User Alice reports a DMCA infringement against content item `vid_xyz`.
2. A platform admin opens the compliance detail endpoint:
   `GET /ui/licenses/compliance/content/vid_xyz`
3. Admin receives HTTP 403 — "Not authorized to view this content's compliance".
4. Admin cannot determine compliance status without contacting the content creator directly or using indirect aggregate queries.
5. DMCA response window (typically 24-48 hours) may be missed.


## 4. Fix Design (code-level)

### Option A (preferred): Role check in the existing creator endpoint

The simplest fix adds a role bypass to the existing 403 guard. When the session role is `admin` or `root`, skip the ownership check:

```python
# app/routers/license_compliance.py

from app.auth.roles import Role, normalize_role   # add to imports if not present

@license_compliance_router.get(
    "/content/{content_id}", response_model=ComplianceStatusOut
)
async def content_compliance_detail(
    content_id: str,
    session: dict = Depends(require_ui_session),
):
    record = svc.get_compliance_status(content_id=content_id)
    if not record:
        raise HTTPException(404, "No compliance record for this content")
    caller_role = normalize_role(session.get("role"))
    is_owner = record.get("creator_id") == session["user_sub"]
    is_privileged = caller_role in {Role.ADMIN, Role.ROOT}
    if record.get("creator_id") and not is_owner and not is_privileged:
        raise HTTPException(403, "Not authorized to view this content's compliance")
    return ComplianceStatusOut(**record)
```

`normalize_role` is already available in `app/auth/roles.py` and is used extensively throughout `app/services/sessions.py`. The `session["role"]` value is a string (e.g., `"admin"`) that `normalize_role` converts to the `Role` enum.

### Related endpoints to review

While the primary fix is on `content_compliance_detail`, two other endpoints in the same creator-scoped router deserve review for consistency:

**`GET /ui/licenses/compliance/content/{content_id}/refs` (line 81-88):** Returns license references for a content item. No creator ownership check exists — any authenticated session can call it. This is likely intentional (license refs are not sensitive), but should be confirmed.

**`GET /ui/licenses/compliance/content/{content_id}/flags` (line 91-100):** Returns compliance flags for a content item. No creator ownership check exists. A flag could contain sensitive reporter information. This should also receive an admin-bypass or at minimum a creator-ownership check.

Both are separate from GAP-0298's primary scope but should be remediated in the same commit.

### Option B: Separate admin endpoint for per-content detail

Add a mirrored endpoint under `license_compliance_admin_router`:

```python
@license_compliance_admin_router.get(
    "/content/{content_id}", response_model=ComplianceStatusOut
)
async def admin_content_compliance_detail(
    content_id: str,
    _admin: AuthenticatedUser = Depends(require_admin_or_root),
):
    record = svc.get_compliance_status(content_id=content_id)
    if not record:
        raise HTTPException(404, "No compliance record for this content")
    return ComplianceStatusOut(**record)
```

Option B is cleaner from an API-design perspective (separate concern, separate prefix) but doubles the endpoint count and requires admin API consumers to use a different path. Option A is preferred for simplicity and backward compatibility.

### Dev/prod parity (SECOPS-007)

The `session["role"]` value is populated by `require_ui_session` from the `ui_access_token` JWT cookie (or Cognito Bearer token), both of which are available identically in dev and prod. No mock-specific code path is introduced. The `normalize_role` function is deterministic and environment-agnostic. SECOPS-007 is satisfied.

### Backward compatibility

The change **relaxes** the 403 guard for a previously blocked population (admins/root). No existing callers are broken. Regular users continue to receive 403 for content they do not own.

### Authentication pathway detail

`require_ui_session` returns `role` as a string value (e.g., `"admin"`, `"root"`, `"user"`). The `normalize_role` function in `app/auth/roles.py` converts this string to a `Role` enum value. The `Role` enum defines `ADMIN` and `ROOT` as the two privileged values. This chain is already used in other endpoints throughout the codebase (e.g., `app/services/sessions.py:308`), so the fix integrates with the existing pattern rather than introducing a new pattern.

One subtlety: `require_ui_session` returns a dict with `"role": role.value` (a string). The `get_authenticated_user` dependency returns an `AuthenticatedUser` dataclass with a `.role: Role` enum attribute. The fix uses `normalize_role(session.get("role"))` rather than adding a second dependency (`get_authenticated_user`) to keep the endpoint signature minimal and consistent with the existing creator-scoped endpoints on the same router, all of which use only `require_ui_session`.
