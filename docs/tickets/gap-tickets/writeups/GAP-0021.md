# GAP-0021: `dissolve_group()` never calls `dissolve_treasury()` — Remediation Write-up

> ~5 pages. Fix-oriented. Built on investigation doc: `docs/tickets/gap-tickets/investigations/GAP-0021.md`.

## 1. Summary & Classification

**Bug statement**: When a group administrator dissolves a group, the dissolution handler
in `app/services/user_groups.py` marks the group record as `dissolved`, deletes all member
rows, and logs the event — but never invokes the treasury service that distributes
contributed and donated funds back to their rightful owners. All money held in the group
treasury is permanently orphaned in DynamoDB.

| Field | Value |
|-------|-------|
| Severity | **CRIT** |
| Status | Open |
| Source ticket | GROUP-004 |
| Owning area | Group treasury / billing service |
| Investigation verdict | **Confirmed** — `app/services/user_groups.py:474-501` |
| Effort | S (< 1 hour) |

**One-line impact**: Every group dissolution silently strands all contributed funds and
diverts donations away from escrow, causing direct financial loss to contributors and
compliance exposure for the platform.

**Related tickets**: GROUP-004 (group treasury design), GAP-0219 (two-phase treasury
dissolution atomicity), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (root cause)

### Code path today

The dissolution entry point is `dissolve_group()` in
`app/services/user_groups.py:474-501`. The function:

1. Calls `_require_role(group_id, admin_id, "admin")` to authorise the caller.
2. Loads the group META record with `get_group_or_404(group_id)`.
3. Guards against double-dissolution with a `status == "dissolved"` check.
4. Writes `status = "dissolved"` to the META row via `T.user_groups.update_item`.
5. Calls `list_all_members(group_id)` and iterates member records, issuing
   `T.user_groups.delete_item` for each member row and `_remove_user_group_index` for
   the reverse GSI.
6. Logs `group.dissolved` and returns `{"ok": True, "status": "dissolved"}`.

The complete function as it stands:

```python
# app/services/user_groups.py:474-501
def dissolve_group(*, group_id: str, admin_id: str) -> Dict[str, Any]:
    _require_role(group_id, admin_id, "admin")
    meta = get_group_or_404(group_id)
    if meta.get("status") == "dissolved":
        raise HTTPException(status_code=410, detail="This group has been dissolved")

    ts = now_ts()
    T.user_groups.update_item(
        Key={"pk": f"GROUP#{group_id}", "sk": "META"},
        UpdateExpression="SET #s = :s, updated_at = :t",
        ExpressionAttributeNames={"#s": "status"},
        ExpressionAttributeValues={":s": "dissolved", ":t": ts},
    )

    # Clean up all member records and user-group indexes
    all_members = list_all_members(group_id)
    for m in all_members:
        uid = m.get("user_id", "")
        T.user_groups.delete_item(Key={"pk": f"GROUP#{group_id}", "sk": f"MEMBER#{uid}"})
        _remove_user_group_index(group_id, uid)

    logger.info("group.dissolved", extra={"group_id": group_id, "admin": admin_id})
    return {"ok": True, "status": "dissolved"}
```

The import block at lines 1-16 of `user_groups.py` confirms there is no import of
`group_treasury` or any other billing service:

```python
from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts
from boto3.dynamodb.conditions import Key
from fastapi import HTTPException
```

`group_treasury` is therefore entirely absent from the dissolution flow.

### What exists but is never called

`app/services/group_treasury.py:487-600` implements `dissolve_treasury(group_id)`. The
function is fully working: it reads the current treasury balance, computes pro-rata
contributor refunds, credits each contributor's wallet via `apply_wallet_delta`, sweeps
leftover donated funds to `PLATFORM#ESCROW`, and zeroes the group treasury balance. It
handles the `balance <= 0` edge case cleanly by returning immediately with a no-op
result. It is simply never imported or called from `user_groups.py`.

### How the bug manifests

After dissolution, the DynamoDB `billing` table retains a live row under
`GROUP#{group_id}` with a non-zero `balance_cents`. Contributors' wallet balances are
never restored. The donation component never reaches the escrow ledger. There is no
background task or cleanup job that would catch this at a later time.

In development the bug is identical to production: both environments use the same
`T.billing` DynamoDB table and the same service-layer code path. There is no mock that
hides the missing call.

## 3. Impact / Exploit / Blast Radius

### Financial impact

Any group that has held a treasury balance at any point in its lifecycle and then been
dissolved has its treasury silently retained. Contributors cannot recover their funds
through any product surface: there is no endpoint that allows a credit from a dissolved
group's `billing` row to a user wallet (only internal `apply_wallet_delta` could do so,
and it is not exposed). The money is permanently locked in the table row.

The `billing` table row for the dissolved group persists indefinitely under
`pk=GROUP#{group_id}`, `sk=WALLET`. Because the group META record is marked `dissolved`,
no new contributions or withdrawals are accepted, but the balance field retains its last
value. Platform accounting systems that sum all `WALLET` rows to compute platform-wide
funds-in-custody will incorrectly count these orphaned balances as real, accessible
funds.

**Concrete example**: A group with 10 contributors averaging $50 each ($500 total
treasury) is dissolved by its admin. All $500 remains in `GROUP#{group_id}` in
`T.billing`. No user wallet is credited. The donations portion ($200, say) never reaches
`PLATFORM#ESCROW`. The platform cannot account for it. From the users' perspective the
money simply disappears.

### Compliance / audit exposure

Unreconciled balances in billing records create an accounting gap. Any financial audit
will find `billing` rows for dissolved groups with non-zero balances that have no
corresponding debit or credit leg. This is a GAAP and SOX-adjacent concern for any
jurisdiction where the platform operates with real money.

### Insider threat

An insider who retains DynamoDB read access can enumerate dissolved groups with positive
balances. They cannot move the funds through the API, but the orphaned balance is visible
and represents a discrepancy that could be exploited in social-engineering claims
("we are owed a refund").

### No outward privilege escalation

There is no path from this bug to gaining elevated access. The only damage is financial:
money loss for contributors and failure to route donations to escrow. The dissolved group
record itself is immutable after dissolution (the `status == "dissolved"` guard prevents
re-entry), so there is no risk of double-dissolution or double-refund once the fix is in
place and `dissolve_treasury()` has been called.

## 4. Fix Design (code-level)

### Minimal fix

Add a lazy import inside `dissolve_group()` to avoid any circular-dependency risk, then
call `dissolve_treasury(group_id)` before the `update_item` that marks the group
dissolved. Calling it first ensures the treasury records (contributor amounts, wallet
pointers) are still intact at the time of the pro-rata calculation.

```python
# app/services/user_groups.py — dissolve_group() after fix
def dissolve_group(*, group_id: str, admin_id: str) -> Dict[str, Any]:
    _require_role(group_id, admin_id, "admin")
    meta = get_group_or_404(group_id)
    if meta.get("status") == "dissolved":
        raise HTTPException(status_code=410, detail="This group has been dissolved")

    # Distribute treasury funds BEFORE marking dissolved so contributor records exist
    from app.services import group_treasury as _treasury_svc
    treasury_result = _treasury_svc.dissolve_treasury(group_id)

    ts = now_ts()
    T.user_groups.update_item(
        Key={"pk": f"GROUP#{group_id}", "sk": "META"},
        UpdateExpression="SET #s = :s, updated_at = :t",
        ExpressionAttributeNames={"#s": "status"},
        ExpressionAttributeValues={":s": "dissolved", ":t": ts},
    )

    # Clean up all member records and user-group indexes
    all_members = list_all_members(group_id)
    for m in all_members:
        uid = m.get("user_id", "")
        T.user_groups.delete_item(Key={"pk": f"GROUP#{group_id}", "sk": f"MEMBER#{uid}"})
        _remove_user_group_index(group_id, uid)

    logger.info("group.dissolved", extra={
        "group_id": group_id, "admin": admin_id,
        "treasury": treasury_result,
    })
    return {"ok": True, "status": "dissolved", "treasury": treasury_result}
```

### Why lazy import

`user_groups.py` is imported by several other services. A top-level import of
`group_treasury` would add a circular-dependency risk if `group_treasury` ever imports
`user_groups`. A local `from app.services import group_treasury` inside the function
body executes only once at dissolution time and is entirely safe.

### Top-level import alternative

If the codebase audit confirms there is no circular dependency, the cleaner form is a
module-level import added after line 14:

```python
from app.services import group_treasury as _treasury_svc
```

Either form is acceptable; the lazy import is the safer default.

### Dev/Prod parity (SECOPS-007)

`dissolve_treasury()` uses `T.billing` (DynamoDB, local or AWS) and
`apply_wallet_delta()` which is a pure service-layer function with no AWS-specific
branching. The mock KMS and moto S3 are not touched. There is no dev-only code path in
the treasury service. The fix behaves identically in both environments: in dev,
DynamoDB Local handles the wallet delta writes; in production, AWS DynamoDB does. No
feature flag is required; no migration is needed because the bug only affects
newly-dissolved groups going forward (already-dissolved groups cannot be un-dissolved by
this fix, but their orphaned balances could be corrected by a one-time reconciliation
script outside scope of this ticket).

### Alternatives considered

**Option: background reconciliation job** — scan `billing` for dissolved-group rows and
run treasury distribution retroactively. Rejected: it would not catch the root cause;
future dissolutions would still be broken; retroactive refund timing is ambiguous.

**Option: expose treasury state in dissolution API response** — already included in the
fix above (`"treasury": treasury_result` in the return dict) so callers can confirm
funds were distributed.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline, moto)

import pytest

def seed_wallet(user_sub, amount_cents):
    from app.core.tables import T
    from app.core.time import now_ts

        "pk": f"USER#{user_sub}", "sk": "WALLET",
        "balance_cents": amount_cents, "updated_at": now_ts(),

def get_wallet_balance(user_sub):
    from app.core.tables import T
    resp = T.billing.get_item(Key={"pk": f"USER#{user_sub}", "sk": "WALLET"})

def test_dissolve_group_calls_treasury_and_refunds_contributors(ddb_tables):
    from app.services.user_groups import create_group, dissolve_group
    from app.services.group_treasury import contribute, get_treasury_balance

    alice = "alice-sub-001"
    g = create_group(creator_sub=alice, name="Test Group")

    # Sanity: treasury has the funds before dissolution
    assert get_treasury_balance(group_id)["balance_cents"] == 1000

    result = dissolve_group(group_id=group_id, admin_id=alice)

    # After fix: treasury zeroed, contributor refunded
    assert result["status"] == "dissolved"
    assert get_treasury_balance(group_id)["balance_cents"] == 0  # FAILS before fix
    assert get_wallet_balance(alice) == 1000                      # FAILS before fix
    assert "treasury" in result                                   # FAILS before fix

def test_dissolve_group_zero_balance_is_noop(ddb_tables):

**Before fix**: `get_treasury_balance` returns 1000, `get_wallet_balance` returns 0.
**After fix**: both assertions pass.

### Manual QA steps

1. Run `just restart` to start a clean stack.
2. Create a group, seed the creator's wallet, contribute 500 cents.
3. `POST /ui/groups/{group_id}/dissolve` with admin credentials.
4. Verify response body includes `"treasury": {"refunded_count": 1, "escrow_cents": 0}`.
5. Call `GET /ui/billing/wallet` for the contributor — balance should be 500.
6. Query DynamoDB directly: `aws dynamodb get-item --table-name billing --key '{"pk":{"S":"GROUP#<id>"},"sk":{"S":"WALLET"}}'` — `balance_cents` should be 0.

### Metrics / observability

The existing `logger.info("group.dissolved")` line is extended to include the
`treasury_result` dict. Alerting on `treasury.refunded_count >= 0` (structured log
field) confirms the hook ran. An additional CloudWatch metric `group.dissolution.treasury_distribution_cents` can be emitted from `dissolve_treasury()` if future observability is desired.

### Rollback

The fix is additive: one import + one function call. Removing those two lines reverts the
behaviour to the pre-fix state. No schema changes; no data migrations; DynamoDB table
structure is unchanged.

### Risk

Low. `dissolve_treasury()` already handles every edge case including zero balance (early
return), missing contributor records, and partial failures. The only new risk is
`dissolve_treasury()` raising an unhandled exception before the META status write,
leaving the group in its pre-dissolved state. This is the correct failure mode: better to
abort with an error than to orphan funds. The caller can retry.

### Effort

**S** — estimated 30-45 minutes: add lazy import, add function call, update return dict,
write two pytest tests, run `just test`.

### Sequencing

This fix should be applied before the GAP-0219 atomicity ticket is resolved. GAP-0219
addresses what happens if `dissolve_treasury()` partially completes before the META write
fails; this ticket addresses the more fundamental issue that the call is never made at
all.

### Additional regression test: donations routed to escrow

Beyond contributor refunds, the fix must also ensure that the donation surplus is swept
to `PLATFORM#ESCROW`. The existing `dissolve_treasury()` implementation handles this
internally, but a second test scenario confirms it end-to-end:

```python
def test_dissolve_group_routes_donations_to_escrow(ddb_tables):
    from app.services.user_groups import create_group, dissolve_group
    from app.services.group_treasury import donate, get_treasury_balance
    from app.core.tables import T

    alice = "alice-sub-003"
    g = create_group(creator_sub=alice, name="Donation Group")
    group_id = g["group_id"]

    # Seed Alice's wallet and make a donation (not a contribution)
    seed_wallet(alice, 500)
    donate(group_id=group_id, user_sub=alice, amount_cents=500)
    assert get_treasury_balance(group_id)["total_donated_cents"] == 500

    dissolve_group(group_id=group_id, admin_id=alice)

    # After dissolution with fix: escrow row should reflect the donated amount
    escrow = T.billing.get_item(Key={"pk": "PLATFORM#ESCROW", "sk": "WALLET"})
    escrow_balance = int(escrow.get("Item", {}).get("balance_cents", 0))
    assert escrow_balance >= 500, "Donated funds must reach PLATFORM#ESCROW on dissolution"
```

This test fails before the fix (escrow remains zero) and passes after the fix routes
donations through `dissolve_treasury()`.

### Audit trail

The updated log line `logger.info("group.dissolved", extra={..., "treasury": treasury_result})`
records `refunded_count`, `escrow_cents`, and any error details as structured fields.
Operations can query these logs to confirm every dissolution event routed funds correctly.
A missing or zero-amount `treasury` key in the log for a group that had positive
contributions is an indicator that the fix was not applied or that the call raised an
exception.
