# GAP-0077: Monthly Usage Reset Not Automated — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase 2026-06-05; claim is **confirmed**
> — `usage_reset_at` is stored but no background task resets `current_month_usage_cents`.

## 1. Summary & Classification

- **Severity**: HIGH — without an automated reset, a key's `monthly_budget_cents` limit
  applies across the entire lifetime of the key instead of renewing monthly. Users who exhaust
  their budget in month 1 can never use the key again unless they manually edit the record.
- **Source ticket**: AGENT-001 · **Status**: Open
- **Owning area**: `app/services/llm_provider_keys.py`, `app/main.py`
- **Related tickets**: GAP-0076 (budget race), AGENT-001, SECOPS-007 (dev/prod parity)

**Verdict: CLAIM CONFIRMED.** The field `usage_reset_at` is initialized to `0` on key
creation (`app/services/llm_provider_keys.py:126`) and appears in the safe-output field
list (`line 422`). However, no background task, scheduled job, or startup hook exists in
`app/main.py` that scans for keys whose `usage_reset_at` has passed and zeros out
`current_month_usage_cents`. The field is stored but completely inert.

**One-line impact**: Monthly budget limits never renew; budget-exceeded keys stay locked
forever unless manually reset.

---

## 2. Current-State Investigation (root cause)

### What is stored

`app/services/llm_provider_keys.py`, function `add_key` (line 89):

```python
item: Dict[str, Any] = {
    ...
    "monthly_budget_cents": monthly_budget_cents,
    "current_month_usage_cents": 0,
    "usage_reset_at": 0,          # line 126 — timestamp of next reset; initialized to 0
    ...
    "status": "active",
}
```

The intent is clear: `usage_reset_at` stores a Unix timestamp after which the counter
should be zeroed and the key reactivated. When a budget is set to, say, 1000 cents,
`usage_reset_at` should be set to `now + 30 days` and a background job should fire
when that time is reached.

### What is missing

A search of `app/main.py` for all startup tasks registered via `add_event_handler`:

```
app.add_event_handler("startup", start_billing_dunning_task)       # billing
app.add_event_handler("startup", start_filemgr_purge_task)         # files
app.add_event_handler("startup", start_scheduled_messages_task)    # messages
app.add_event_handler("startup", start_deletion_scheduler_task)    # account deletion
app.add_event_handler("startup", start_kyc_sla_checker_task)       # KYC
...
```

There is **no** `start_llm_usage_reset_task` or equivalent. The `usage_reset_at` field is
never read by any scheduled job.

Furthermore, the `add_key` function initializes `usage_reset_at = 0`, meaning no reset date
is computed at key creation time. The `update_key` function (not shown here, exists in the
service) can update `monthly_budget_cents` but does not set `usage_reset_at` when doing so.

### Compounding effect with GAP-0076

If the concurrent budget bypass (GAP-0076) fires and leaves the key in `budget_exceeded`
status with an inflated counter, there is no monthly reset to recover from it. Both gaps
compound: the budget can be bypassed AND once exceeded it can never reset automatically.

### Dev vs prod manifestation

Both dev and prod are equally affected: DynamoDB Local and real DynamoDB hold the same
data structure. In prod the key is permanently locked until an admin manually writes
`current_month_usage_cents=0` and `status=active` directly to DynamoDB. In dev the same
lockout happens but tests can work around it with a fresh `just restart`.

## 3. Impact / Exploit / Blast Radius

### Direct impact on users

1. User creates a key with `monthly_budget_cents = 1000`.
2. On day 15 of month 1, usage hits 1000 cents. Key flips to `budget_exceeded`.
3. On day 1 of month 2, the budget should have renewed. It does not.
4. All agent sessions fail with "Key is not active" for all subsequent months.
5. User must contact support or manually call a reset endpoint (which does not exist).

### Financial impact

If the platform bills users for a "managed LLM budget" feature (per-month subscription),
the non-renewal constitutes a failure to deliver the contracted service.

### Operational impact

- Admin burden: ops team would need to manually scan and reset keys monthly via DynamoDB
  console or direct API — error-prone and unscalable.
- Trust damage: users who configured budgets for cost control cannot rely on them actually
  rolling over.

### Blast radius

All users who have `monthly_budget_cents > 0` and have reached their budget at any point.
Keys with `monthly_budget_cents = 0` (unlimited) are unaffected. Estimated affected
population: any active agent user with cost controls enabled.

## 4. Fix Design (code-level)

### Part A — Set `usage_reset_at` on key creation and budget update

`app/services/llm_provider_keys.py`, `add_key` function:

```python
import calendar

def _next_reset_at(from_ts: int) -> int:
    """Return the Unix timestamp of the first second of the next calendar month."""
    import datetime
    dt = datetime.datetime.utcfromtimestamp(from_ts)
    # First day of the next month
    if dt.month == 12:
        next_month = datetime.datetime(dt.year + 1, 1, 1)
    else:
        next_month = datetime.datetime(dt.year, dt.month + 1, 1)
    return int(next_month.timestamp())
```

In `add_key`, replace `"usage_reset_at": 0` with:

```python
"usage_reset_at": _next_reset_at(ts) if monthly_budget_cents > 0 else 0,
```

Also update the `update_key` function to recalculate `usage_reset_at` when
`monthly_budget_cents` is changed from 0 to a positive value.

### Part B — Background task to perform the reset

Add a new module `app/services/llm_usage_reset.py`:

```python
"""Monthly LLM usage reset task (GAP-0077 fix)."""
import asyncio
import logging
from app.core.tables import T
from app.core.time import now_ts

logger = logging.getLogger(__name__)
_INTERVAL_SECONDS = 3600  # run hourly; reset fires only when usage_reset_at <= now


async def _reset_loop() -> None:
    while True:
        try:
            _run_reset_pass()
        except Exception:
            logger.exception("llm_usage_reset error")
        await asyncio.sleep(_INTERVAL_SECONDS)


def _run_reset_pass() -> int:
    """Scan all keys with usage_reset_at <= now and reset their monthly counters.
    Returns the count of keys reset."""
    now = now_ts()
    reset_count = 0

    # Full-table scan with FilterExpression.
    # The table is partitioned per user (pk=USER#{user_id}), so a GSI on
    # usage_reset_at would be needed for efficient targeting. In the interim,
    # a scan with filter is safe for small-to-medium key counts; add a GSI
    # (see below) before production scale-out.
    paginator_kwargs: dict = {
        "FilterExpression": "usage_reset_at > :zero AND usage_reset_at <= :now",
        "ExpressionAttributeValues": {":zero": 0, ":now": now},
    }
    resp = T.llm_provider_keys.scan(**paginator_kwargs)

    while True:
        for item in resp.get("Items", []):
            pk, sk = item["pk"], item["sk"]
            if not sk.startswith("KEY#"):
                continue
            budget = int(item.get("monthly_budget_cents", 0) or 0)
            if budget <= 0:
                continue  # no budget set — skip

            from app.services.llm_provider_keys import _next_reset_at
            new_reset_at = _next_reset_at(now)

            try:
                T.llm_provider_keys.update_item(
                    Key={"pk": pk, "sk": sk},
                    UpdateExpression=(
                        "SET current_month_usage_cents = :zero, "
                        "#st = :active, "
                        "usage_reset_at = :next_reset "
                        "REMOVE budget_exceeded_at"
                    ),
                    ConditionExpression="usage_reset_at <= :now",
                    ExpressionAttributeNames={"#st": "status"},
                    ExpressionAttributeValues={
                        ":zero": 0,
                        ":active": "active",
                        ":now": now,
                        ":next_reset": new_reset_at,
                    },
                )
                reset_count += 1
                logger.info(
                    "llm_key_monthly_reset pk=%s sk=%s next_reset_at=%d",
                    pk, sk, new_reset_at,
                )
            except T.llm_provider_keys.meta.client.exceptions \
                    .ConditionalCheckFailedException:
                pass  # already reset by a concurrent worker

        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
        resp = T.llm_provider_keys.scan(
            ExclusiveStartKey=last_key, **paginator_kwargs
        )

    if reset_count:
        logger.info("llm_usage_reset_pass reset_count=%d", reset_count)
    return reset_count


def start_llm_usage_reset_task() -> None:
    """Register the monthly reset loop as a FastAPI startup background task."""
    import asyncio
    loop = asyncio.get_event_loop()
    loop.create_task(_reset_loop())
    logger.info("llm_usage_reset_task started")
```

### Part C — Wire the task in `app/main.py`

```python
from app.services.llm_usage_reset import start_llm_usage_reset_task
...
app.add_event_handler("startup", start_llm_usage_reset_task)
```

### Part D — DynamoDB schema addition (for prod scale)

Add a GSI to the `llm_provider_keys` table in `scripts/local-ddb-init.py` to avoid a full
scan when the number of keys grows large:

```python
TableDef(
    _resolve_table_name(S.llm_provider_keys_table_name, "llm_provider_keys"),
    "pk", "sk",
    gsi=[
        {"index_name": "ByProvider",   "partition_key": "pk", "sort_key": "provider"},
        {"index_name": "ByCreatedAt",  "partition_key": "pk", "sort_key": "created_at"},
        # NEW: enables efficient range query for "keys due for reset"
        # Partition key = a fixed shard ("RESET") + sort key = usage_reset_at (N).
        # Alternative: use a sparse GSI with pk="HAS_BUDGET" projected attribute.
        {"index_name": "ByResetAt",    "partition_key": "reset_shard", "sort_key": "usage_reset_at"},
    ],
    attr_types={"created_at": "N", "usage_reset_at": "N"},
)
```

For the interim scan-based approach (Part B), no schema change is needed. The GSI is a
production scale-out optimization only.

### Dev/Prod parity (SECOPS-007)

The background task uses `T.llm_provider_keys` which resolves to DynamoDB Local in dev
and real DynamoDB in prod via `S.ddb_endpoint_url`. No new AWS services are introduced.
The `asyncio` event loop pattern is already used by `start_scheduled_messages_task` and
`start_billing_dunning_task` — the new task follows the same pattern.

The `_next_reset_at` helper uses Python's stdlib `datetime` — no AWS dependency.

### Regression test (pytest, offline, fails-before / passes-after)

```python
"""Regression test for GAP-0077 — monthly usage reset not automated."""
import time
import pytest
from unittest.mock import patch

from app.services.llm_provider_keys import add_key, record_usage, get_key
from app.services.llm_usage_reset import _run_reset_pass


def test_usage_reset_at_set_on_key_creation(mock_ddb):
    """After fix: usage_reset_at is non-zero when monthly_budget_cents > 0."""
    key = add_key(
        user_id="u1", provider="openai", label="test",
        api_key="sk-x", monthly_budget_cents=1000,
    )
    # Before fix: usage_reset_at == 0 always
    # After fix:  usage_reset_at > 0, approximately now + 30 days
    assert key["usage_reset_at"] > 0


def test_reset_pass_zeroes_overdue_key(mock_ddb):
    """After fix: _run_reset_pass zeros current_month_usage_cents and reactivates key."""
    user_id, key_id_str = "u1", None
    key = add_key(
        user_id=user_id, provider="openai", label="test",
        api_key="sk-x", monthly_budget_cents=100,
    )
    key_id_str = key["key_id"]

    # Simulate full usage driving key to budget_exceeded
    record_usage(user_id=user_id, key_id=key_id_str, tokens=100, cost_cents=100)
    key_after = get_key(user_id=user_id, key_id=key_id_str)
    assert key_after["status"] == "budget_exceeded"

    # Backdoor usage_reset_at to be in the past
    from app.core.tables import T
    T.llm_provider_keys.update_item(
        Key={"pk": f"USER#{user_id}", "sk": f"KEY#{key_id_str}"},
        UpdateExpression="SET usage_reset_at = :past",
        ExpressionAttributeValues={":past": 1},  # epoch = definitely past
    )

    # Before fix: _run_reset_pass does not exist / returns 0 and does nothing
    # After fix:  returns 1 and key is active with zeroed usage
    count = _run_reset_pass()
    assert count == 1

    key_reset = get_key(user_id=user_id, key_id=key_id_str)
    assert key_reset["current_month_usage_cents"] == 0
    assert key_reset["status"] == "active"
    assert key_reset["usage_reset_at"] > 1  # next reset is in the future


def test_reset_pass_skips_key_without_budget(mock_ddb):
    """Keys with monthly_budget_cents=0 are not reset (no budget = no reset needed)."""
    key = add_key(
        user_id="u2", provider="openai", label="free",
        api_key="sk-y", monthly_budget_cents=0,
    )
    count = _run_reset_pass()
    assert count == 0
```

### Rollout

- **Effort**: S–M. Part A (set `usage_reset_at` on creation) is 2 lines. Part B (task
  module) is ~60 lines. Part C (main.py wire) is 2 lines. Part D (GSI) is optional for V1.
- **Risk**: LOW. The reset is guarded by a `ConditionExpression` so concurrent runs are
  idempotent. Existing keys with `usage_reset_at = 0` will not be reset (filter excludes
  zero). After deployment, new keys get a proper reset date; existing keys need a one-time
  backfill script to set `usage_reset_at = next_month_boundary`.
- **Backfill**: One-time script: scan all keys with `monthly_budget_cents > 0` and
  `usage_reset_at = 0`; write `usage_reset_at = _next_reset_at(now)`.
- **Sequencing**: Deploy after GAP-0076 fix (budget race) to avoid a reset landing on a
  partially-overcounted counter. No other hard dependencies.
- **Rollback**: Remove the `add_event_handler` line; the task stops running. No data
  corruption — existing resets already written remain valid.

### Status reactivation edge case

When the reset fires, it unconditionally sets `status = "active"`. This is correct for
keys in `budget_exceeded` state (the intended use case). However, if a key was manually
suspended by an admin (`status = "suspended"`) and also happens to have a `usage_reset_at`
in the past, the reset would incorrectly reactivate it.

The fix should add a `ConditionExpression` that only reactivates keys in `budget_exceeded`
status:

```python
T.llm_provider_keys.update_item(
    Key={"pk": pk, "sk": sk},
    UpdateExpression=(
        "SET current_month_usage_cents = :zero, "
        "#st = :active, "
        "usage_reset_at = :next_reset"
    ),
    ConditionExpression="usage_reset_at <= :now AND #st = :exceeded",
    ExpressionAttributeNames={"#st": "status"},
    ExpressionAttributeValues={
        ":zero": 0,
        ":active": "active",
        ":now": now,
        ":next_reset": new_reset_at,
        ":exceeded": "budget_exceeded",
    },
)
```

This ensures the reset only fires for budget-exceeded keys, leaving suspended, revoked, or
errored keys untouched.

### Interaction with GAP-0076

If GAP-0076 (the race condition) allows a key to reach `budget_exceeded` with a counter
higher than the actual budget (due to concurrent ADD operations), the monthly reset will
zero the counter and reactivate the key. This is the correct behavior — the reset's job
is to start a fresh month. The race condition in GAP-0076 is a within-month problem;
this fix addresses the cross-month renewal. Both should be fixed independently.
