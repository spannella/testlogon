# GAP-0141: API Key Ciphertext Must Never Appear in API Responses — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Gap statement**: When the planned `GET /ui/bots/{bot_id}/ai-config` endpoint is implemented as part of BOT-004, the raw KMS ciphertext stored in the `ai_api_key_encrypted` DynamoDB field must never be serialised into the JSON response. The response model (`AiConfigOut`) must expose only a masked representation — conventionally `"..." + key[-3:]` — mirroring the pattern already used by the AGENT-001 LLM-key service.

- **Severity**: HIGH
- **Source ticket**: BOT-004
- **Status**: Open — BOT-004 itself is unbuilt (`app/services/bot_ai.py` does not exist). The gap is therefore pre-emptive: the risk materialises the moment the feature is shipped without the masking safeguard.
- **Owning area**: `app/services/bot_ai.py` (to create), `app/routers/bot_ai.py` (to create), `app/models.py` (new `AiConfigOut` model)
- **Investigation verdict**: Claim is accurate in intent; however the cited file `app/services/bot_ai.py` does not exist at all. The analogous risk is fully confirmed in the reference implementation at `app/services/llm_provider_keys.py` and `app/models.py`. The GAP ticket correctly identifies the control that must be built.
- **Related tickets**: SEC-022 (credential exposure general policy), SECOPS-007 (dev/prod parity for KMS paths), GAP-0009 (SSRF via provider URL in the same BOT-004 feature), BOT-004 parent.

## 2. Current-State Investigation (root cause)

### 2.1 BOT-004 feature status

`app/services/bot_ai.py` does not exist. `app/routers/bot_ai.py` does not exist. There is no `AiConfigOut` Pydantic model in `app/models.py`. The BOT-004 write-up (`docs/tickets/writeups/BOT-004.md`) confirms the feature is entirely unbuilt.

The gap is therefore a design constraint that must be enforced when the feature is implemented, not a regression in already-running code.

### 2.2 Reference implementation: `app/services/llm_provider_keys.py`

The AGENT-001 feature solves an identical problem — storing a third-party LLM API key encrypted at rest and exposing only a harmless suffix to callers. The implementation is at `app/services/llm_provider_keys.py`:

```python
# llm_provider_keys.py:107-119
key_suffix = api_key[-4:] if len(api_key) >= 4 else "****"
item = {
    ...
    "encrypted_api_key": encrypted,   # KMS ciphertext, never returned to callers
    "key_suffix": key_suffix,         # safe suffix, always returned
    ...
}
```

The `_safe_out` helper at `llm_provider_keys.py:408-410` removes the ciphertext before any caller sees the dict:

```python
def _safe_out(item):
    out = {k: v for k, v in item.items()
           if k not in ("encrypted_api_key", "pk", "sk")}
    ...
    return out
```

Every public-facing function — `add_key`, `list_keys`, `get_key`, `rotate_key`, `list_all_keys_admin` — passes through `_safe_out` before returning. The Pydantic output model `LlmKeyOut` at `app/models.py:4217` declares a `key_suffix: str` field and has no `encrypted_api_key` field, providing a second defence-in-depth layer.

The dev/prod code path is the same: KMS is mocked at port 7999 in dev (`scripts/mock_kms_server.py`) via the `KMS_ENDPOINT_URL` env var; in prod it hits AWS KMS. The same `kms_encrypt` / `kms_decrypt` calls at `app/core/crypto.py:16,22` are used in both environments (SECOPS-007 satisfied in the reference implementation).

### 2.3 Where the gap would appear in BOT-004

The planned `GET /ui/bots/{bot_id}/ai-config` endpoint needs to return the AI configuration for a bot's creator. If the service layer naively fetches the DynamoDB item and serialises it, `ai_api_key_encrypted` — a base64 KMS ciphertext that can be decrypted to the raw third-party API key if the attacker also compromises the KMS key — leaks to the frontend.

Even if the frontend never renders it, the ciphertext appears in browser DevTools network responses, server-side logs (if the response body is logged), and any downstream cache. A stolen session cookie plus DevTools inspection is sufficient to harvest the ciphertext; a separately compromised KMS key then turns the ciphertext into a live API key.

### 2.4 GAP in the claim

The ticket cites `app/services/bot_ai.py` as the location. That file does not exist yet; the gap is therefore in the not-yet-written code. The risk is real and the prescription is correct. No correction to the claim is needed other than noting the pre-emptive nature.

## 3. Impact / Exploit / Blast Radius

**Who is affected**: Creators who configure an AI bot with their own OpenAI/Anthropic/custom provider API key.

**Concrete exploit scenario** (if BOT-004 is shipped without the fix):

1. Attacker obtains a creator's authenticated session cookie (phishing, XSS, network interception on a shared WiFi).
2. Attacker calls `GET /ui/bots/{bot_id}/ai-config` with the stolen session.
3. Response body includes `"ai_api_key_encrypted": "AQICAHj...base64..."`.
4. If the attacker also has access to the AWS KMS key (e.g., via a separate IAM credential leak), `aws kms decrypt --ciphertext-blob fileb://<b64-decoded>` returns the raw API key.
5. Even without KMS access, the ciphertext is a valuable stepping stone: it can be used to demonstrate to the key-owner that their key material was extracted from the platform, enabling social engineering or regulatory pressure.

**Financial impact**: Third-party API keys (OpenAI, Anthropic) carry direct billing liability. A leaked key used by an attacker to generate completions charges the creator's account. Costs can reach thousands of dollars per hour for high-throughput abuse.

**Data classification**: KMS ciphertext is classified as credential material under most data-security frameworks; its exposure is a reportable event under SOC 2 CC6.1 and ISO 27001 A.9.4.

**Blast radius**: Limited to the bot-creator population and to keys stored in the `bot_ai_configs` DynamoDB table. Does not affect the AGENT-001 LLM-key table (`llm_provider_keys`) which already strips ciphertext correctly.

## 4. Fix Design (code-level)

### 4.1 `app/services/bot_ai.py` — storage helper

Mirror `_safe_out` exactly:

```python
# app/services/bot_ai.py

_STRIP_FIELDS = frozenset({"ai_api_key_encrypted", "pk", "sk"})

def _safe_out(item: dict) -> dict:
    """Strip KMS ciphertext and DDB key fields before returning to callers."""
    out = {k: v for k, v in item.items() if k not in _STRIP_FIELDS}
    # Expose a safe masked representation
    suffix = str(item.get("ai_api_key_suffix") or "***")
    out["api_key_masked"] = "..." + suffix[-3:]
    return out
```

Store both `ai_api_key_encrypted` (KMS ciphertext) and `ai_api_key_suffix` (last 3 chars of the raw key) when the creator uploads the key:

```python
def configure_ai_bot(*, bot_id: str, user_id: str, provider_url: str,
                     api_key: str, system_prompt: str, ...) -> dict:
    from app.core.crypto import kms_encrypt
    encrypted = kms_encrypt(api_key)
    suffix = api_key[-3:] if len(api_key) >= 3 else "***"
    item = {
        "pk": f"BOT#{bot_id}",
        "sk": "AI_CONFIG",
        "ai_api_key_encrypted": encrypted,   # never returned to callers
        "ai_api_key_suffix": suffix,
        "provider_url": _validated_provider_url(provider_url),  # GAP-0009
        "system_prompt": system_prompt,
        ...
    }
    T.bot_ai_configs.put_item(Item=item)
    return _safe_out(item)
```

Decrypt only in the internal path used to make the LLM call:

```python
def _get_raw_api_key(bot_id: str) -> str:
    """Internal use only — for making LLM calls."""
    from app.core.crypto import kms_decrypt
    item = T.bot_ai_configs.get_item(Key={"pk": f"BOT#{bot_id}", "sk": "AI_CONFIG"}).get("Item")
    if not item:
        raise ValueError("bot ai config not found")
    return kms_decrypt(item["ai_api_key_encrypted"]).decode()
```

### 4.2 `app/models.py` — Pydantic output model

```python
class AiConfigOut(BaseModel):
    bot_id: str
    provider_url: str
    api_key_masked: str          # "...XYZ" — safe suffix, never the ciphertext
    system_prompt: str
    forbidden_topics: List[str] = Field(default_factory=list)
    max_history_turns: int = 10
    rate_limit_per_user_per_hour: int = 20
    monthly_budget_cents: int = 0
    created_at: int = 0
    updated_at: int = 0
    # NO ai_api_key_encrypted field — intentionally absent
```

The `response_model=AiConfigOut` declaration on the FastAPI endpoint acts as a compile-time guarantee: even if `_safe_out` were ever omitted from the service layer, FastAPI's response serialisation would silently drop any field not declared in the model.

### 4.3 Dev/prod parity (SECOPS-007)

The KMS mock (`scripts/mock_kms_server.py`, port 7999) is active in dev when `KMS_ENDPOINT_URL=http://localhost:7999` is set in `.env.local`. `kms_encrypt` / `kms_decrypt` in `app/core/crypto.py:16,22` automatically use the mock endpoint. No dev-only short-circuit is needed or acceptable; the ciphertext-stripping logic must be identical in both environments.

Feature flag: add `bot_ai_enabled: bool = bool(os.environ.get("BOT_AI_ENABLED", "0"))` to `app/core/settings.py`. Gate the router registration in `app/main.py` on this flag so the endpoints do not appear at all until the feature is production-ready.

### 4.4 Alternatives considered

- **Encrypting at the field level inside the Pydantic model** (e.g., `validator("ai_api_key_encrypted", always=True)` that raises): rejected because silent validator suppression is less obvious than simply not declaring the field.
- **Returning the full ciphertext but marking it `write_only=True`**: not a Pydantic/FastAPI standard; not reliable.
- **Not storing the suffix, returning `"***"` always**: valid but reduces debuggability for creators who have multiple keys. Returning `"...XYZ"` lets a creator confirm which key is configured without exposing anything exploitable.
