### 2.2 Case version extraction is fragile

`KycCaseDetailPage.tsx:298-303`:
```typescript
const caseVersion: number = (() => {
  if (!caseData) return 1;
  const updatedEvent = caseData.timeline.find((e) => e.event_type === "kyc_case_updated");
  const v = (updatedEvent?.details as Record<string, unknown>)?.version;
  return typeof v === "number" ? v : 1;
})();
```

The code attempts to extract the case version from a `kyc_case_updated` timeline event's
`details.version` field. This is fragile for two reasons:

1. **First use**: A freshly submitted case has no `kyc_case_updated` event — it only has
   `kyc_case_submitted`. The fallback `return 1` is correct for this scenario.
2. **Multiple updates**: If the case was updated multiple times, `find()` returns the
   **first** `kyc_case_updated` event (oldest) rather than the latest. The version used for
   optimistic locking would be stale.

The backend admin detail response should expose `version` at the top level of the `case`
object. If `caseData.version` were available, this extraction logic would be a one-liner.

automatically from the `ui_csrf` cookie. No manual CSRF threading is needed.

## 3. Impact / Exploit / Blast Radius

### 3.1 Current state (page fully present)

There is no functional impact from this gap ticket. The KYC case detail workflow is
operational: reviewers can view documents, approve/reject/request-info with reason codes,
and see the full timeline.

### 3.2 Regression risk from fragile version extraction

If the backend begins returning cases with multiple `kyc_case_updated` events before the
version extraction logic is fixed, optimistic locking will use a stale version. The backend
will return a `kyc_case_update_conflict` error (the conflict detection path at line 320
handles this), but the reviewer will need to refresh and re-enter their decision — a UX
degradation but not a data integrity issue.

### 3.3 Missing "Assign to me" / "Claim case" action

The Actions panel (line 484-522) shows Approve, Reject, and Request Info. There is no
"Assign" or "Claim" button to set `assigned_admin_sub`. This means cases remain unassigned
unless the backend auto-assigns on status transition, or a supervisor assigns via a separate
admin API. This is a workflow gap, not a security gap.

### 3.4 Non-image document rendering

The `DocumentViewer` renders documents as `<img>` tags (line 199). PDF KYC documents would
not render. The `files_ref` items can have any MIME type. A PDF viewer component (e.g.,
react-pdf or an iframe to a signed URL) is absent. If KYC accepts PDF proof-of-address
documents, reviewers see a broken image icon.

## 4. Fix Design (code-level)

### 4.1 Fix version extraction — use top-level `case.version` field

**Backend change** (prerequisite): Add `version: int` to the KYC case admin detail response
in `app/models.py` and populate it from the DDB item.

**Frontend change**: Replace the fragile extraction at `KycCaseDetailPage.tsx:298-303`:

```typescript
// Before (fragile): searches timeline for version
const caseVersion: number = (() => {
  if (!caseData) return 1;
  const updatedEvent = caseData.timeline.find(...);
  ...
})();

// After: use top-level field, fall back to 1 for compatibility
const caseVersion: number = (caseData?.version as number | undefined) ?? 1;
```

### 4.2 Add PDF support in DocumentViewer

Replace the `<img>` element with a conditional renderer:

```tsx
{activeFile?.mime_type === "application/pdf" ? (
  <iframe
    src={`/ui/files/download?path=${encodeURIComponent(file.path)}`}
    title={FILE_TYPE_LABELS[file.type] ?? file.type}
    className="w-full"
    style={{ minHeight: "400px" }}
    data-testid="doc-pdf-iframe"
  />
) : (
  <img
    src={`/ui/files/download?path=${encodeURIComponent(file.path)}`}
    alt={FILE_TYPE_LABELS[file.type] ?? file.type}
    className="max-w-full transition-transform"
    style={{ transform: `scale(${scale}) rotate(${rotation}deg)` }}
    data-testid="doc-image"
  />
)}
```

This requires `KycFileRef` to include a `mime_type` field (add to
`frontend/src/api/endpoints/kyc-admin.ts` and the backend model).

### 4.3 Add "Claim / Assign" action button

Add a fourth action button that POSTs to the backend assignment endpoint:

```tsx
<Button
  variant="outline"
  onClick={() => assignMut.mutate()}
  disabled={!!caseData.assigned_admin_sub || assignMut.isPending}
  data-testid="claim-case-btn"
>
  Claim Case
</Button>
```

Where `assignMut` calls `assignKycCase(caseId!, currentAdminSub)`.

### 4.4 Dev/Prod parity (SECOPS-007)

All three action endpoints (`approveKycCase`, `rejectKycCase`, `requestKycInfo`) use the
admin-auth-required `/ui/admin/kyc/cases/:id/...` routes. In dev mode the backend KYC
service writes to the local DynamoDB. In production it writes to AWS DynamoDB. The frontend
component is environment-agnostic. SECOPS-007 is satisfied: no client-side env-conditional
code for these mutations.

### 5.4 Accessibility and keyboard navigation

Action dialogs (Approve, Reject, Request Info) use the shadcn/ui `Dialog` component which
handles focus trapping, `aria-modal="true"`, and Escape key closing automatically. However,
the reason code checkboxes use `<Checkbox>` with `<Label>` pairs (lines 542-554). Confirm
that each `<Checkbox id="approve-rc-...">` is correctly associated with
`<Label htmlFor="approve-rc-...">` — this association is in place in the current code. A
manual accessibility audit with a screen reader is recommended as part of the rollout QA
pass, since KYC reviewers may be using assistive technology in regulated environments.

### 5.5 Optimistic locking — edge case analysis

The `expected_version` field sent in approve/reject bodies (lines 307-308, 333-334) is used
by the backend for optimistic concurrency control. The current extraction logic (lines
298-303) returns `1` for any case without a `kyc_case_updated` timeline event, including
cases that have been updated once (the first update changes version from 1 to 2, then the
`kyc_case_updated` event has `details.version = 2`, but `find()` would return the event with
version 2 — so for the second decision attempt the version would be correct). The actual
failure mode is when a case is updated **before** the reviewer's page loads: if the backend
version is already `3` but the frontend derives `1` (no events), the backend rejects the
action with `kyc_case_update_conflict` — which the error handler at line 320 correctly
catches and displays to the user. The UX degradation is one forced refresh; no data is lost.
Adding `version: int` to the case detail response API eliminates this class of spurious
conflicts entirely.
