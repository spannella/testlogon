# GAP-0159: Background recommendation refresh job not registered — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement.** The recommendation engine (DISC-001) stores pre-computed
"For You" video lists for each user under `RECO#{user_id} / FOR_YOU` in
`T.recommendations`. These lists are only valid for the period they were
computed; they must be periodically refreshed as new signals accumulate and
video popularity changes. `refresh_user_recommendations` in
`app/services/recommendations.py:503` recomputes this list for a single user,
but there is no background task that iterates over all users and calls this
function on a schedule. Nothing in `app/main.py` registers a startup handler
for periodic recommendation refresh. As a result, `RECO#*/FOR_YOU` records
are never written by background processing; every user is permanently served
from the cold-start/trending fallback that is used when no pre-computed record
exists.

**Severity:** HIGH — core algorithmic feature silently non-functional. The
platform's personalised recommendation feed (`GET /ui/videos/gallery/for-you`)
degrades to a generic trending fallback for 100 % of users.  
**Source ticket:** DISC-001  
**Status:** Open  
**Owning area:** `app/services/recommendations.py`, `app/main.py`  
**Effort:** S

**Verdict from code investigation:** Claim confirmed with one additional
nuance. The `/internal/recommendations/refresh` endpoint
(`app/routers/recommendations.py:338`) exists and can trigger a per-user
refresh when called with a `user_id` body. However, when called with no
`user_id` it returns `users_processed: 0` and does nothing (line 355), so
even the on-demand path cannot currently refresh all users. Neither issue
is the same as a registered background task; both need fixing.

**Related tickets:** GAP-0160 (engagement signals never recorded from frontend),
DISC-001.

## 2. Current-State Investigation (root cause)

### The algorithm is implemented but never triggered

`app/services/recommendations.py` contains a complete collaborative-filtering
implementation:

- `record_signal` (line 91) — stores per-user engagement signals.
- `compute_affinity_scores` (line 170) — converts signals into creator/video
  affinity weights.
- `compute_for_you` (line 201) — uses affinities to rank candidate videos.
- `refresh_user_recommendations` (line 503) — calls `compute_for_you` +
  `compute_creator_suggestions` for a single user and writes results to DDB.

`app/main.py` registers approximately 20 startup tasks (lines 496–806),
covering billing reconciliation, scheduled messages, broadcast scheduling,
KYC analytics, SSH recording cleanup, etc. A grep for
`refresh.*reco`, `reco.*startup`, or `start_reco` in `app/main.py` returns
zero results. The recommendations service has no entry in the startup handler
list.

### The `refresh_user_recommendations` function

```python
# app/services/recommendations.py:503
def refresh_user_recommendations(user_id: str) -> Dict[str, Any]:
    """Recompute all recommendations for a single user."""
    t0 = time.time()
    for_you = compute_for_you(user_id)
    creators = compute_creator_suggestions(user_id)
    duration = time.time() - t0
    return {
        "user_id": user_id,
        "for_you_count": len(for_you),
        "creator_count": len(creators),
        "duration_seconds": round(duration, 2),
    }
```

This function is only called from `app/routers/recommendations.py:351` (the
on-demand internal endpoint), and only when `body.user_id` is provided.

### The on-demand refresh endpoint is also broken for "all users"

```python
# app/routers/recommendations.py:338-355
@internal_router.post("/refresh", response_model=RefreshOut)
def refresh_endpoint(body: RefreshIn):
    t0 = _time.time()
    if body.user_id:
        result = refresh_user_recommendations(body.user_id)
        duration = _time.time() - t0
        return RefreshOut(ok=True, users_processed=1, duration_seconds=...)
    else:
        return RefreshOut(ok=True, users_processed=0, duration_seconds=0.0)
```

When `body.user_id` is absent (i.e., "refresh all"), the endpoint returns
`users_processed: 0` without doing anything. This is a stub that was never
completed.

### Config setting exists but is unused

`app/core/settings.py:1805`:

```python
reco_refresh_interval_hours: int = int(
    os.environ.get("RECO_REFRESH_INTERVAL_HOURS", "6")
)
```

The setting (`S.reco_refresh_interval_hours`) is defined and defaults to 6
hours, but it is referenced by zero application code outside of `settings.py`.

### What happens at runtime without the background task

`compute_for_you` (`app/services/recommendations.py:201`) checks whether a
pre-computed `FOR_YOU` record exists in `T.recommendations`. When none is
found, it falls back to a trending/popular-video list
(`_get_trending_fallback` or similar). This means:

- All users always see the same trending feed regardless of their viewing
  history.
- Engagement signals recorded via `record_signal` accumulate in DDB but are
  never acted on.
- The personalised discovery feature is entirely inert.

## 3. Impact / Exploit / Blast Radius

**Who is affected:** All users of the discovery/for-you feed
(`GET /ui/videos/gallery/for-you`). This is the primary content discovery
surface.

**Business impact:**

- Creator monetisation through personalised recommendations is zero. Creators
  whose content would rank highly for specific user affinities receive no
  additional views.
- User retention suffers: a static trending feed provides no personalisation
  incentive to return.
- The DISC-001 feature was shipped and billed to stakeholders as "implemented",
  but it silently delivers no value.

**Data integrity.** `SIGNAL#*/VIDEO#*` records accumulate in `T.recommendations`
(TTL-bounded; see `_signal_ttl`). No data is lost or corrupted, but the
signals are stale-forever until a refresh runs.

**Security/exploit:** No security risk. The gap is a liveness/availability
issue, not a security issue.

**Compound gap with GAP-0160.** GAP-0160 (engagement signals never sent from
the frontend) means that even if the background refresh task were running, it
would process near-empty signal sets. GAP-0159 and GAP-0160 must both be
fixed for personalised recommendations to work end-to-end.

## 4. Fix Design (code-level)

### Step 1 — Add `refresh_all_users` to `recommendations.py`

The function must iterate over all users who have signals recorded and refresh
their recommendations. The canonical way to find users with signals is to
query the `T.recommendations` table for all `SIGNAL#*` partition keys.

```python
# app/services/recommendations.py — add after refresh_user_recommendations

import asyncio

def _list_all_signal_users() -> List[str]:
    """Return the set of user_ids that have at least one engagement signal."""
    user_ids: Set[str] = set()
    kwargs: Dict[str, Any] = {
        "FilterExpression": Attr("pk").begins_with("SIGNAL#"),
        "ProjectionExpression": "pk",
    }
    while True:
        resp = T.recommendations.scan(**kwargs)
        for item in resp.get("Items", []):
            pk = item.get("pk", "")
            if pk.startswith("SIGNAL#"):
                user_ids.add(pk[len("SIGNAL#"):])
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return list(user_ids)


def refresh_all_users() -> Dict[str, Any]:
    """Recompute recommendations for every user that has engagement signals."""
    user_ids = _list_all_signal_users()
    t0 = time.time()
    processed = 0
    errors = 0
    for uid in user_ids:
        try:
            refresh_user_recommendations(uid)
            processed += 1
        except Exception:
            logger.exception("reco: refresh_all_users: error for user %s", uid)
            errors += 1
    duration = time.time() - t0
    logger.info(
        "reco: refresh_all_users complete: %d users, %d errors, %.1fs",
        processed, errors, duration,
    )
    return {"users_processed": processed, "errors": errors, "duration_seconds": round(duration, 2)}
```

### Step 2 — Register the background task in `app/main.py`

Add an import and a startup handler alongside the other periodic tasks
(e.g., after `start_kyc_analytics_precompute_task` at line 586):

```python
# app/main.py — new import (add with other service imports at top)
from app.services.recommendations import refresh_all_users as _refresh_all_reco

# Inside create_app(), alongside other startup handlers:
def _start_reco_refresh_task() -> None:
    if not S.recommendations_enabled:
        return
    interval_seconds = S.reco_refresh_interval_hours * 3600

    async def _loop() -> None:
        await asyncio.sleep(60)       # brief startup delay
        while True:
            try:
                await asyncio.get_event_loop().run_in_executor(
                    None, refresh_all_users
                )
            except Exception:
                logger.exception("reco: background refresh loop error")
            await asyncio.sleep(interval_seconds)

    asyncio.get_event_loop().create_task(_loop())

app.add_event_handler("startup", _start_reco_refresh_task)
```

The 60-second startup delay prevents the refresh from running during the
critical server boot window (DynamoDB table creation, seed data, etc.).

### Step 3 — Fix the on-demand "all users" path in the refresh endpoint

```python
# app/routers/recommendations.py:338
@internal_router.post("/refresh", response_model=RefreshOut)
def refresh_endpoint(body: RefreshIn):
    t0 = _time.time()
    if body.user_id:
        refresh_user_recommendations(body.user_id)
        return RefreshOut(ok=True, users_processed=1,
                          duration_seconds=round(_time.time() - t0, 2))
    else:
        # GAP-0159 fix: actually refresh all users when no user_id given
        from app.services.recommendations import refresh_all_users
        result = refresh_all_users()
        return RefreshOut(
            ok=True,
            users_processed=result["users_processed"],
            duration_seconds=result["duration_seconds"],
        )
```

### Dev/Prod parity (SECOPS-007)

- `T.recommendations` is a DynamoDB table present in both environments
  (defined in `scripts/local-ddb-init.py`).
- The `asyncio.get_event_loop().run_in_executor` pattern is the established
  pattern used by other background tasks in this codebase.
- `S.recommendations_enabled` guards the task in both environments; set
  `RECOMMENDATIONS_ENABLED=0` in `.env.local` to disable during development
  if needed.
- `S.reco_refresh_interval_hours` defaults to `6` in both environments.
  In dev, operators can set `RECO_REFRESH_INTERVAL_HOURS=0.01` (i.e., ~36s)
  to exercise the loop quickly.

### Performance considerations

`_list_all_signal_users` performs a DynamoDB `Scan` with a `FilterExpression`.
For a large table this can be slow and expensive. Optimisations (out of scope
for this fix):

- Maintain a separate `USER_INDEX#{user_id}` key in `T.recommendations` for
  every user who has ever had a signal, enabling a targeted `Query` instead
  of a `Scan`.
- Use a DynamoDB Streams consumer to enqueue users for refresh asynchronously.

For the initial fix, the Scan approach is correct and safe given that
`T.recommendations` is a purpose-built narrow table.

## 5. Testing, Verification & Rollout

### Regression test — pytest (offline)

```python
# tests/services/test_reco_background.py
from unittest.mock import patch, call
import pytest
from app.services.recommendations import refresh_all_users, refresh_user_recommendations


def test_refresh_all_users_calls_per_user_refresh(mock_reco_tables):
    """GAP-0159: refresh_all_users must iterate all signal users and refresh each."""
    # Simulate two signal users in the table
    with (
        patch(
            "app.services.recommendations._list_all_signal_users",
            return_value=["user_a", "user_b"],
        ),
        patch(
            "app.services.recommendations.refresh_user_recommendations",
        ) as mock_refresh,
    ):
        result = refresh_all_users()

    assert mock_refresh.call_count == 2
    mock_refresh.assert_any_call("user_a")
    mock_refresh.assert_any_call("user_b")
    assert result["users_processed"] == 2
    assert result["errors"] == 0


def test_refresh_all_users_tolerates_per_user_errors(mock_reco_tables):
    """Errors for individual users do not abort the whole refresh."""
    with (
        patch(
            "app.services.recommendations._list_all_signal_users",
            return_value=["user_ok", "user_bad"],
        ),
        patch(
            "app.services.recommendations.refresh_user_recommendations",
            side_effect=[None, RuntimeError("DDB timeout")],
        ),
    ):
        result = refresh_all_users()

    assert result["users_processed"] == 1
    assert result["errors"] == 1
```

**Fails before fix:** `refresh_all_users` does not exist; `ImportError`.

**Passes after fix:** `refresh_all_users` is defined and the mock is called
correctly.

### Rollback

Remove the startup handler registration from `app/main.py` and the
`refresh_all_users` + `_list_all_signal_users` functions from
`recommendations.py`. The `FOR_YOU` records already written to DDB remain but
go stale; the fallback logic handles missing records gracefully.

### Risk

**Low–Medium.** The DynamoDB Scan on a large table is the main risk. Mitigate
by setting `RECO_REFRESH_INTERVAL_HOURS` to a long interval initially (e.g.,
24 hours) and monitoring DDB read throughput. The task runs in an executor
thread (non-blocking to the event loop). Error handling is per-user so a
single DDB timeout does not abort the batch.

### Effort

**S** — approximately 60–90 minutes including `refresh_all_users`,
`_list_all_signal_users`, startup registration, and tests.

### Sequencing

This fix is most effective when deployed together with GAP-0160
(which ensures signals are actually recorded by the frontend). In isolation,
the background task will run but process empty signal sets for most users,
producing the same trending-fallback output. Deploy GAP-0160 first (or
simultaneously) so that the first background refresh has real signals to work
with.
