# GAP-0383: Watermarked-download endpoint does not enforce VOD-019 download-tier entitlement — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. No prior investigation doc exists for this GAP.

## 1. Summary & Classification

- **Plain-English statement**: `POST /ui/videos/{video_id}/download/watermarked` checks that the video has `allow_download=True` and that a download MP4 exists, but it does not call `check_entitlement_purchase_only` to verify whether the caller's purchase tier includes download rights (`ent.download_allowed`). The plain download endpoint at `app/routers/video_listing.py:800-804` has this check; the watermarked download endpoint at `app/routers/watermark.py:106-110` does not. A viewer who purchased a "permanent-view" tier (with `download_allowed=False`) can bypass the download paywall by calling the watermarked download route instead.
- **Severity**: HIGH — direct paywall bypass. A customer can obtain a downloadable MP4 of premium content without paying the download-tier price differential.
- **Source ticket**: VOD-020 (watermarked downloads). **Status**: Open. **Owning area**: VOD / Entitlement / Billing.
- **Claim verification**: CONFIRMED. `app/routers/watermark.py:106-110` reads:
  ```python
  if not video.allow_download:
      raise HTTPException(status_code=403, detail="downloads not enabled for this video")
  if not video.download_mp4_key or video.download_mp4_status != "ready":
      raise HTTPException(status_code=409, detail="download MP4 not yet generated")
  ```
  There is no call to `check_entitlement_purchase_only` anywhere in `watermark.py`. The setting `S.vod_purchase_tiers_enabled` is referenced in `video_listing.py:800` but never in `watermark.py`.
- **Related tickets**: VOD-019 (view-once/rental access tiers), VOD-020, SEC-013 (economic abuse), GAP-0375 (download rate limiting not enforced).

## 2. Current-State Investigation (root cause)

### The plain download endpoint (has the check)

`app/routers/video_listing.py:793-804`:

```python
requires_purchase = bool(
    getattr(video, "available_purchase_types", None)
    or getattr(video, "price_cents", None)
    or getattr(video, "download_price_cents", None)
    or getattr(video, "entitlement_sku", None)
)
if S.vod_purchase_tiers_enabled and requires_purchase:
    from app.services.vod_purchase import check_entitlement_purchase_only
    ent = check_entitlement_purchase_only(user_id=user_sub, video_id=video_id)
    if not ent.entitled or not ent.download_allowed:
        raise HTTPException(status_code=403, detail="Download access not included in your purchase")
```

This guard is correctly placed: before `allow_download` is checked, so a user with no entitlement at all also gets a 403.

### The watermarked download endpoint (missing the check)

`app/routers/watermark.py:92-124`:

```python
@router.post("/{video_id}/download/watermarked", response_model=WatermarkDownloadResponse)
def request_watermarked_download(video_id: str, ctx=Depends(require_ui_session)):
    user_id = ctx["user_sub"]
    video = get_video(video_id)

    if not video.allow_download:                                    # ← line 106
        raise HTTPException(403, "downloads not enabled for this video")

    if not video.download_mp4_key or video.download_mp4_status != "ready":   # ← line 109
        raise HTTPException(409, "download MP4 not yet generated")

    # (proceeds directly to watermark job creation or cache lookup)
    ...
```

The two guards at lines 106–110 are necessary but not sufficient. The plain download endpoint adds the `requires_purchase` check before both of these. The watermarked endpoint skips it entirely.

### Root cause

When `watermark.py` was implemented as part of VOD-020, the entitlement check was copied from the simpler flag checks in `video_listing.py` but the purchase-tier guard block (lines 793–804) was not ported. The VOD-019 entitlement model (`vod_purchase.py`) was a separate ticket and the coupling between the two routers was not captured in code review.

### `check_entitlement_purchase_only` behavior

`app/services/vod_purchase.py:316-367`:

```python
def check_entitlement_purchase_only(*, user_id: str, video_id: str) -> EntitlementStatus:
    ...
    download_allowed = bool(item.get("download_allowed", False))
    ...
    return EntitlementStatus(..., download_allowed=download_allowed)
```

The function returns an `EntitlementStatus` dataclass. `ent.entitled` is `True` if the user has any valid purchase; `ent.download_allowed` is `True` only if the specific purchase tier includes download rights (the "download" tier at `vod_purchase.py:415` sets `download_allowed=True`; "permanent" and "rental" tiers set it to `False`).

### How the bypass works in practice

1. Creator publishes video with `allow_download=True`, `access_mode="purchase"`, entitlement SKU set, and two tiers: "permanent view" ($5, `download_allowed=False`) and "download" ($15, `download_allowed=True`).
2. Viewer purchases the $5 "permanent view" tier. `vod_purchase.py` writes an entitlement record with `download_allowed=False`.
3. Viewer calls `GET /ui/videos/{id}/download` → 403 ("Download access not included in your purchase"). Paywall enforced correctly.
4. Viewer calls `POST /ui/videos/{id}/download/watermarked` → job created, watermarked MP4 URL returned. Paywall bypassed — viewer obtains a downloadable watermarked MP4 for $5 instead of $15.

The watermark only identifies the user; it does not enforce the entitlement. The output is a fully playable MP4.

## 3. Impact / Exploit / Blast Radius

### Financial impact

Every content creator who uses the two-tier download model (view-only vs. download) loses the price differential for the download tier whenever a viewer exploits this bypass. The magnitude depends on the creator's pricing, but on a platform with many premium content sellers the aggregate revenue loss can be significant.

### Content protection impact

Watermarked downloads are designed for paid-download scenarios — the watermark identifies the leaker if content is redistributed. However, the entitlement bypass means unauthorized users can initiate a download at all, defeating the "download is a premium feature" paywall. Even with the watermark, the content is freely accessible.

### Scope

- All videos with `allow_download=True` and purchase-based access control (`available_purchase_types` set, or `price_cents`/`entitlement_sku` set).
- Any authenticated user who has any entitlement (including the cheapest view-only tier) can exploit this.
- Users with no entitlement at all cannot exploit this because `video.allow_download` is typically `False` for free/public videos, and the endpoint would return 403 at line 106 before the watermark job is created.

### Cascading effects

- `count_active_jobs(user_id)` rate-limits concurrent watermark jobs per user (default 5 via `S.watermark_max_concurrent_jobs`). An attacker running the bypass will consume watermark job slots, potentially exhausting capacity for legitimate paying users.
- Each watermark job writes a record to the download history table, potentially inflating creator download metrics.

## 4. Fix Design (code-level)

### 4.1 Add the entitlement check to `request_watermarked_download`

The fix mirrors the guard at `video_listing.py:793-804` verbatim, inserted immediately after `get_video(video_id)` and before any other check:

```python
@router.post("/{video_id}/download/watermarked", response_model=WatermarkDownloadResponse)
def request_watermarked_download(video_id: str, ctx=Depends(require_ui_session)):
    user_id = ctx["user_sub"]
    video = get_video(video_id)

    # ─── VOD-019 download-tier entitlement check (GAP-0383) ───────────────────
    requires_purchase = bool(
        getattr(video, "available_purchase_types", None)
        or getattr(video, "price_cents", None)
        or getattr(video, "download_price_cents", None)
        or getattr(video, "entitlement_sku", None)
    )
    if S.vod_purchase_tiers_enabled and requires_purchase:
        from app.services.vod_purchase import check_entitlement_purchase_only
        ent = check_entitlement_purchase_only(user_id=user_id, video_id=video_id)
        if not ent.entitled or not ent.download_allowed:
            raise HTTPException(
                status_code=403,
                detail="Download access not included in your purchase",
            )
    # ─── end entitlement check ────────────────────────────────────────────────

    if not video.allow_download:
        raise HTTPException(status_code=403, detail="downloads not enabled for this video")

    if not video.download_mp4_key or video.download_mp4_status != "ready":
        raise HTTPException(status_code=409, detail="download MP4 not yet generated")

    # … rest of function unchanged …
```

The check is placed before the `allow_download` flag check because `allow_download` is a creator-level toggle while the entitlement is a per-user per-purchase control. Both must pass for a download to be permitted.

### 4.2 Placement before cache lookup

The GAP ticket specifies the check should be "before the cache lookup in `request_watermarked_download`". The cache lookup is at `app/routers/watermark.py:127` (`find_cached_watermark`). The entitlement check must precede it so that a cached watermarked MP4 URL is not served to an unauthorized user. The fix above places the check at lines 103–115 (before line 127), satisfying this requirement.

### 4.3 Shared helper to avoid drift

To prevent future drift between the two download endpoints, extract the entitlement guard into a shared helper in `app/services/vod_purchase.py`:

```python
def enforce_download_entitlement(video: Any, user_id: str) -> None:
    """Raise HTTP 403 if the user's entitlement does not include download rights.
    Must be called before any download URL is minted.
    
    No-op if vod_purchase_tiers_enabled is False or the video has no purchase gate.
    """
    from app.core.settings import S
    from fastapi import HTTPException

    requires_purchase = bool(
        getattr(video, "available_purchase_types", None)
        or getattr(video, "price_cents", None)
        or getattr(video, "download_price_cents", None)
        or getattr(video, "entitlement_sku", None)
    )
    if not (S.vod_purchase_tiers_enabled and requires_purchase):
        return

    ent = check_entitlement_purchase_only(user_id=user_id, video_id=video.video_id)
    if not ent.entitled or not ent.download_allowed:
        raise HTTPException(
            status_code=403,
            detail="Download access not included in your purchase",
        )
```

Then both `video_listing.py` and `watermark.py` call `enforce_download_entitlement(video, user_id)`, removing the duplicated inline block and making future audits trivial.

### 4.4 Dev/Prod parity (SECOPS-007)

`check_entitlement_purchase_only` reads from the `VodEntitlements` DynamoDB table via `T.vod_entitlements`, which resolves to DynamoDB Local in dev and real AWS DynamoDB in production. The same code path runs in both environments with no branching. `S.vod_purchase_tiers_enabled` defaults to `True` in both environments (`settings.py:1627`). No feature flag change is needed.

### 4.5 Alternatives considered

- **Check only `download_allowed` without `entitled`**: Rejected. A user with an expired rental who has `entitled=False` should also be blocked, even if their historical purchase had `download_allowed=True`.
- **Move the check into `create_watermark_job`**: Rejected. The check belongs in the router guard layer so it fires before any DynamoDB write (including the job creation record), not inside the service layer where it would need to bubble up an error through the watermark generator.

### Rollback

The fix adds a single guard block. Reverting it removes the guard. No DynamoDB schema changes, no data migrations.

### Risks

- **`get_video` returns a partial VideoMetadata model**: `getattr(video, "available_purchase_types", None)` uses `getattr` with a default to handle models that may not have all optional fields populated. This is the same defensive pattern used in `video_listing.py:794-799`.
- **Performance**: `check_entitlement_purchase_only` makes a single DynamoDB `get_item` call. At P99 DynamoDB latency (~5ms), this adds negligible overhead to the download initiation request.

### Effort / Sequencing

**Effort**: S (1–2 hours including tests). No schema changes. Apply independently of GAP-0381 and GAP-0382; this is a pure authorization fix.
