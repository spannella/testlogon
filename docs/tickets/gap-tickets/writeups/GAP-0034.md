# GAP-0034: `VideoMetadata.hls_manifest_url` Never Populated After Transcoding — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real code at file:line. Builds on investigation doc
> `docs/tickets/gap-tickets/investigations/GAP-0034.md`.

## 1. Summary & Classification

**GAP-0034** identifies a data-linkage gap in the VOD transcoding completion path.
After a transcode job finishes successfully, the worker writes the HLS manifest URI,
thumbnail keys, and rendition list into the `transcode_jobs` DynamoDB table but never
writes them back into the `video_metadata` table. As a result,
`VideoMetadataModel.hls_manifest_url` (and `thumbnail_url`, `renditions`) remain `null`
for every published video. The video appears as "published" in all listings but cannot
be played by any HLS client.

- **Severity**: CRIT (complete video playback outage after successful transcoding)
- **Source ticket**: VOD-005
- **Owning area**: Transcode worker completion path (`app/services/transcode_worker.py:199-205`,
  `app/services/video_metadata_store.py:365-399`)
- **Status**: Open
- **Effort**: S (~2 hours)

**Verdict**: Confirmed. `app/services/transcode_job_store.py` (`complete_job_with_outputs`
function) writes `output_hls_manifest_uri`, `output_thumbnail_keys`, and related fields to
the `transcode_jobs` table only. The immediately subsequent call to `transition_video_status`
(`app/services/video_metadata_store.py:365-399`) writes only `status`, `updated_at`, and
`published_at` — no URL fields. The two tables were never linked in the completion path.

**One-line impact**: Every successfully transcoded video is permanently unplayable because
`GET /ui/videos/{video_id}` always returns `hls_manifest_url: null`.

**Related tickets**: VOD-005 (original spec), GAP-0033 (FFmpeg receives `s3://` URI —
the upstream gap; both must be fixed for end-to-end playback to work), GAP-0302
(thumbnail/HLS URL not populated in dev — related symptom, different surface).

## 2. Current-State Investigation (Root Cause)

### 2.1 What `complete_job_with_outputs` writes

`app/services/transcode_job_store.py` — `complete_job_with_outputs` (lines 181-241)
writes the following fields to the **`transcode_jobs` table**:

```
output_hls_manifest_uri
output_s3_prefix
output_total_bytes
output_object_count
output_upload_duration_seconds
output_thumbnail_keys
output_playback_url
output_playback_expires_at
progress_pct
```

The final `T.transcode_jobs.update_item(...)` touches only the `transcode_jobs` table.
There is no write to `T.video_metadata`.

### 2.2 What `transition_video_status` writes

`app/services/video_metadata_store.py:365-399`:

```python
def transition_video_status(
    *,
    video_id: str,
    to_status: str,
    reason: str = "",
    actor: str = "",
) -> VideoMetadataModel:
    current = get_video(video_id)
    ...
    update_data: Dict[str, Any] = {
        "status": to_status,
        "updated_at": ts,
    }
    if to_status == "deleted":
        update_data["deleted_at"] = ts
    if to_status == "published" and current.published_at is None:
        update_data["published_at"] = ts
    # ← No hls_manifest_url, thumbnail_url, or renditions ever added here
    updated = current.model_copy(update=update_data)
    T.video_metadata.put_item(Item=video_to_item(updated))
    return updated
```

The signature accepts only `video_id`, `to_status`, `reason`, and `actor`. There is no
parameter for `hls_manifest_url`, `thumbnail_url`, or `renditions`. The function was
designed as a pure state-machine transition helper and was never extended to carry output
URL data.

### 2.3 The completion call site in the worker

`app/services/transcode_worker.py:199-205`:

```python
# Transition video to published if video_metadata store is available
try:
    from app.services.video_metadata_store import transition_video_status

    transition_video_status(video_id=job["video_id"], to_status="published")
    # ← Only status changes; hls_manifest_url stays None
except Exception:
    logger.warning("Could not transition video %s to published", job["video_id"])
```

At this point in the code the worker has already computed:

- `upload_result` (from `vod_s3_uploader.upload_transcode_outputs`) — contains
  `manifest_s3_uri`, `manifest_s3_key`, `thumbnail_s3_keys`, and upload statistics.
- `playback_url` (from `mint_vod_playback_url`) — contains `url` (the signed CDN/CDN-
  equivalent URL) and `expires_at`.
- `completed_renditions` — list of rendition name strings.

All of this data is available in the worker's local scope but is never passed to
`transition_video_status`. The `complete_job_with_outputs` call at line 190 already
wrote this data to `transcode_jobs`, but the linkage to `video_metadata` was omitted.

### 2.4 Fields that remain null in `VideoMetadataModel`

`app/services/video_metadata_store.py:48-50`:

```python
thumbnail_url: Optional[str] = None      # line 48
...
hls_manifest_url: Optional[str] = None  # line 50
```

`app/services/video_metadata_store.py:220-222` (in `item_to_video`):

```python
thumbnail_url=item.get("thumbnail_url"),       # always None after transcode
hls_manifest_url=item.get("hls_manifest_url"), # always None after transcode
```

Because `transition_video_status` never sets these attributes, every `get_video` call
returns `hls_manifest_url=None` regardless of whether the video was successfully
transcoded.

### 2.5 Root cause

VOD-005 implemented `complete_job_with_outputs` for job tracking and
`transition_video_status` for status state management, but did not extend the
`video_metadata` update to include the output URL fields. The two tables serve different
purposes (`transcode_jobs` for job lifecycle, `video_metadata` for content consumption),
and the bridge between them — populating playback URLs after transcoding — was never built.

## 3. Impact / Exploit / Blast Radius

**Who is affected**: Every user who has a video successfully transcoded (assuming GAP-0033
is also fixed) or any future user after GAP-0033 is resolved.

**User-facing failure mode**:
1. Transcode job completes with `status: completed`.
2. Video transitions to `status: published` in `video_metadata`.
3. `GET /ui/videos/{video_id}` returns `{"hls_manifest_url": null, "thumbnail_url": null}`.
4. The frontend HLS player receives `null` and either shows a blank screen or throws an
   error. No video plays.
5. Thumbnail images are also missing; video cards in listings show no preview.

**Secondary effects**:
- `renditions` field is also `null` — the player cannot adapt bitrate.
- The video is permanently stuck; there is no re-transcoding or repair path unless the
  worker is re-run with a modified code path.

**No security exploit**: This is a functional availability gap, not a confidentiality or
integrity issue. No user data is exposed beyond what is expected.

**Interaction with GAP-0033**: GAP-0033 causes every job to fail before completion.
GAP-0034 affects jobs that complete successfully. Both must be fixed for end-to-end
playback to work. Fixing GAP-0033 without fixing GAP-0034 would result in jobs completing
but videos being unplayable.

## 4. Fix Design (Code-Level)

### 4.1 Extend `transition_video_status` signature

In `app/services/video_metadata_store.py`, extend the function signature to accept
optional URL fields:

```python
def transition_video_status(
    *,
    video_id: str,
    to_status: str,
    reason: str = "",
    actor: str = "",
    hls_manifest_url: str | None = None,
    thumbnail_url: str | None = None,
    renditions: list[dict] | None = None,
) -> VideoMetadataModel:
    """Validate and apply a status transition. Optionally update output URLs.

    The hls_manifest_url, thumbnail_url, and renditions parameters are used
    only on the queued→published transition after a successful transcode.
    They are ignored for all other transitions.
    """
    current = get_video(video_id)
    validation = validate_transition(current.status, to_status)
    if not validation.legal:
        raise HTTPException(
            status_code=409,
            detail={
                "code": validation.error_code,
                "from_status": current.status,
                "to_status": to_status,
            },
        )

    ts = now_ts()
    update_data: Dict[str, Any] = {
        "status": to_status,
        "updated_at": ts,
    }
    if to_status == "deleted":
        update_data["deleted_at"] = ts
    if to_status == "published" and current.published_at is None:
        update_data["published_at"] = ts
    # Populate output URL fields when provided (transcode completion path).
    if hls_manifest_url is not None:
        update_data["hls_manifest_url"] = hls_manifest_url
    if thumbnail_url is not None:
        update_data["thumbnail_url"] = thumbnail_url
    if renditions is not None:
        update_data["renditions"] = renditions

    updated = current.model_copy(update=update_data)
    T.video_metadata.put_item(Item=video_to_item(updated))
    return updated
```

All existing callers pass only `video_id` and `to_status` and are unaffected because
the new parameters have `None` defaults and are conditionally applied.

### 4.2 Update the caller in `transcode_worker.py`

Replace lines 199-205 in `app/services/transcode_worker.py`:

```python
# Before (broken):
try:
    from app.services.video_metadata_store import transition_video_status
    transition_video_status(video_id=job["video_id"], to_status="published")
except Exception:
    logger.warning("Could not transition video %s to published", job["video_id"])

# After (fixed):
try:
    from app.services.video_metadata_store import transition_video_status
    # Use the signed CDN playback URL (not the raw s3:// manifest key)
    # as the canonical hls_manifest_url stored in video_metadata.
    manifest_url = playback_url.url if playback_url else None
    thumb_url = (
        upload_result.thumbnail_s3_keys[0]
        if upload_result and upload_result.thumbnail_s3_keys
        else None
    )
    rendition_list = [{"name": r} for r in completed_renditions]
    transition_video_status(
        video_id=job["video_id"],
        to_status="published",
        hls_manifest_url=manifest_url,
        thumbnail_url=thumb_url,
        renditions=rendition_list,
    )
except Exception:
    logger.warning(
        "Could not transition video %s to published", job["video_id"], exc_info=True
    )
```

Note: `playback_url.url` from `mint_vod_playback_url` is the signed CDN (or CDN-equivalent)
URL — the correct public-facing HLS manifest URL for the frontend player. Using
`upload_result.manifest_s3_uri` (the raw `s3://` URI) would store an internal URI that
the frontend cannot use directly.

### 4.3 Thumbnail URL handling

The thumbnail stored in `video_metadata` should be a URL the frontend can render in an
`<img>` tag, not a raw S3 key. In dev mode, `upload_result.thumbnail_s3_keys[0]` is an
S3 key (e.g., `tenants/t1/assets/v1/thumbnails/thumb_0.jpg`). The existing dev pattern
in `_message_out_from_item` converts S3 keys to `/mock/s3/<key>` paths for browser
consumption. `thumbnail_url` in `video_metadata` should follow the same pattern: store
the S3 key and serve via the mock S3 path in dev. Alternatively, if the CDN URL for
thumbnails can be derived from the base CDN URL, use that. For the initial fix, storing
the S3 key is acceptable; the frontend can render it via the `/mock/s3/` proxy in dev
or a CDN URL in prod.

### 4.4 Dev/Prod parity (SECOPS-007)

| Aspect | Dev | Prod |
|---|---|---|
| `playback_url.url` value | `http://localhost:8000/ui/videos/{id}/playback` (dev proxy) | CloudFront signed URL |
| `thumbnail_s3_keys[0]` value | S3 key string, served via `/mock/s3/` proxy | Raw S3 key; CDN URL derived at serve time |
| `T.video_metadata` target | DynamoDB Local port 8001 | AWS DynamoDB |
| Code path | identical | identical |

The `transition_video_status` change is purely in the data layer; no environment-specific
branching is introduced. The only environment-specific consideration is the format of
`playback_url.url`, which is already handled correctly by `mint_vod_playback_url`.

### 4.5 Alternatives considered

- **Write `hls_manifest_url` directly in `complete_job_with_outputs`**: `complete_job_with_outputs`
  is in `transcode_job_store.py` and should own only the `transcode_jobs` table. Writing
  to `video_metadata` from `transcode_job_store.py` would create an undesirable cross-domain
  dependency. Rejected.
- **Add a separate `update_video_output_urls` function**: More granular than extending
  `transition_video_status`. Acceptable, but would require a new DDB `update_item` call
  in addition to the one in `transition_video_status`, resulting in two writes instead of
  one. The extended-signature approach is preferred for atomicity.
- **Poll `transcode_jobs` from the frontend**: The frontend could query the job record for
  `output_hls_manifest_uri` and fall back to that when `hls_manifest_url` is null.
  Rejected — it creates a divergent data model, ties the frontend to implementation details
  of the job system, and is not how `GET /ui/videos/{id}` is designed to work.

### 5.1 Regression tests (pytest offline)

```python
# tests/test_video_metadata_transition.py
from app.services.video_metadata_store import transition_video_status, get_video

def test_transition_to_published_populates_hls_manifest_url(mock_video_queued):
    """Before fix: hls_manifest_url is None after transition to published.
    After fix: hls_manifest_url is populated from the passed parameter.
    """
    video_id = mock_video_queued.video_id
    result = transition_video_status(
        video_id=video_id,
        to_status="published",
        hls_manifest_url="https://cdn.example.com/v1/index.m3u8",
        thumbnail_url="tenants/t1/assets/v1/thumbs/0.jpg",
        renditions=[{"name": "360p"}, {"name": "720p"}],
    )
    assert result.status == "published"
    assert result.hls_manifest_url == "https://cdn.example.com/v1/index.m3u8"
    assert result.thumbnail_url == "tenants/t1/assets/v1/thumbs/0.jpg"
    assert len(result.renditions) == 2


def test_transition_without_urls_leaves_existing_value_unchanged(mock_video_queued):
    """When hls_manifest_url is not passed, it should not be overwritten to None
    if it was already set (idempotent safe re-transition guard)."""
    video_id = mock_video_queued.video_id
    # First set a URL
    transition_video_status(
        video_id=video_id,
        to_status="published",
        hls_manifest_url="https://cdn.example.com/v1/index.m3u8",

    # Re-read and verify it persists when not supplied
    video = get_video(video_id)
    assert video.hls_manifest_url == "https://cdn.example.com/v1/index.m3u8"

    """hls_manifest_url parameter is ignored for non-published transitions."""

        video_id=video_id,

    assert result.status == "deleted"
    # Verify original hls_manifest_url is unchanged
```

### 5.2 Manual QA steps

1. Start dev stack (`just up`). Apply the GAP-0033 fix simultaneously.
2. Upload a short test video, submit a transcode job.
3. Poll `GET /ui/transcode/jobs/{id}` until `status: completed`.
4. Call `GET /ui/videos/{video_id}` — verify `hls_manifest_url` is a non-null string.
5. In the frontend, navigate to the video and verify the HLS player loads the stream.
6. Verify a thumbnail image is displayed in the video listing card.

### 5.3 Observability

Add `exc_info=True` to the existing `logger.warning` at the `transition_video_status`
catch site (change shown in §4.2 above) so that any `transition_video_status` failure
emits a full stack trace to the uvicorn log rather than a silent warning. This helps
distinguish "function not found" errors from "DynamoDB write failed" errors during
rollout.

### 5.4 Rollout and rollback

- No DynamoDB schema migration. `hls_manifest_url` and `thumbnail_url` are optional
  string attributes in the existing `video_metadata` table; adding them to an existing
  item is a safe `put_item` with `model_copy`.
- Videos that completed transcoding before this fix was deployed will retain
  `hls_manifest_url: null`. A one-time backfill can be run by querying
  `transcode_jobs` for completed jobs and re-calling `transition_video_status` with
  the stored `output_playback_url`; this is a low-urgency operational task.
- Rollback: revert `video_metadata_store.py` signature and `transcode_worker.py` call
  site. No data loss; the `transcode_jobs` table retains all output data.

### 5.5 Risk and effort

- **Risk**: Very low. The change adds new optional keyword parameters to an existing
  function and conditionally sets attributes on the model. All existing callers
  (which pass only `video_id` and `to_status`) are unaffected.
- **Effort**: S — ~2 hours: extend `transition_video_status` signature (~10 lines),
  update worker caller (~8 lines), write three pytest cases (~50 lines).
- **Sequencing**: Must be deployed alongside or after GAP-0033 to produce working
  end-to-end video playback. GAP-0034 alone produces a completed (but url-less)
  `video_metadata` record; without GAP-0033 fix no job completes successfully to
  trigger the new code path.
