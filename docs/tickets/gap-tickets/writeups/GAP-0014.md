# GAP-0014: `_message_out_from_item` Never Populates Bot Fields — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: BOT-001. Investigation: docs/tickets/gap-tickets/investigations/GAP-0014.md.

---

## 1. Summary & Classification

**Plain-English statement**: The `MessageOut` Pydantic model declares five bot-specific fields (`sender_type`, `bot_id`, `bot_name`, `bot_avatar_url`, `quick_replies`). The `_message_out_from_item` function that converts a raw DynamoDB item into a `MessageOut` response never reads or populates these five fields — they are unconditionally absent from every API response. Bot messages are therefore indistinguishable from human messages at the API level: they carry no `sender_type: "bot"` indicator, no bot name, no avatar URL, and no quick-reply buttons.

## 2. Current-State Investigation (root cause)

### `MessageOut` model fields

`app/models.py` declares five optional bot fields in `MessageOut`. A grep for these field names in `messaging.py` restricted to the `_message_out_from_item` function and the `return MessageOut(...)` call returns zero hits. The fields are present in the model but never sourced.

### The `return MessageOut(...)` call

`app/routers/messaging.py:4162–4230` — the `return MessageOut(...)` call at line 4162 spans approximately 70 keyword arguments covering every other message field (text, image, file, calendar, GIF, sticker, encryption, reactions, tips, scheduling, locking, etc.) but does not include any of the five bot fields. The call ends at line 4230 with `is_unlocked=is_unlocked,` and no bot keyword arguments follow.

The merged DDB item (`merged_item`) is available at this point and contains whatever attributes were stored by the bot message writer. However, `merged_item.get("sender_type")`, `merged_item.get("bot_id")`, etc. are never called.

### The model definition (confirmed)

The five fields exist in `MessageOut` as `Optional` with `None` defaults. Serialization uses `exclude_none=True` (standard pattern across this codebase), so absent fields simply disappear from the JSON response rather than appearing as explicit `null` values. This makes the omission invisible in API responses — clients receive a normal-looking message object with no indication that bot fields were silently dropped.

### Why this matters even before GAP-0015 is fixed

Even if the DDB table were manually seeded with a bot message item containing these fields, the API would still return them as absent because `_message_out_from_item` never reads them. The fix in this ticket is an independent, always-necessary correction: the serializer must be updated regardless of how bot messages are written.

### Root cause

`_message_out_from_item` is a very long function (~360 lines in `messaging.py`). The `MessageOut` model was extended with bot fields during BOT-001 model design (or a later pass), but the corresponding additions to the serialization call were missed. No compile-time mechanism (e.g., `model_validate` from a typed dict) would catch this omission — the call uses positional/keyword construction, so missing optional fields are silently defaulted to `None`.

## 3. Impact / Exploit / Blast Radius

**Frontend rendering failures**: The frontend's `MessageBubble` component would need to check `msg.sender_type === "bot"` to render bot UI chrome (distinct avatar, bot name header, quick-reply button row). Since `sender_type` is always absent/`None`, this check never passes. Bot messages appear identical to user messages with no way to distinguish them.

**Affected features**:
- Bot name and avatar display — never rendered
- Quick-reply buttons — never rendered (the `quick_replies` array is always absent)
- Bot message filtering or search by `sender_type` — would always return zero results

**Scope**: All conversations that receive bot messages. In practice, given that GAP-0015 also means bot messages are never written to DynamoDB, there are currently no bot messages in any conversation to display. However, this fix is a pre-condition for the bot framework to work at all.

**Security**: No security exploit. Missing data only — no data is exposed that should be hidden, and no authorization boundary is crossed.

**Data integrity**: The underlying DDB items are unaffected. Once GAP-0015 is fixed (bot messages written to DDB), those items will contain the correct `bot_id`, `bot_name`, etc. attributes. This fix ensures the serializer surfaces them correctly.

## 4. Fix Design (code-level)

### The fix is a five-line addition

In `app/routers/messaging.py`, inside the `return MessageOut(...)` call at line 4162, add five keyword arguments immediately before the closing parenthesis (currently at line 4230):

```python
# app/routers/messaging.py:4162 — return MessageOut(...) — add before closing paren

    # Bot message fields (populated only when sender_type="bot")
    sender_type=merged_item.get("sender_type"),
    bot_id=merged_item.get("bot_id"),
    bot_name=merged_item.get("bot_name"),
    bot_avatar_url=merged_item.get("bot_avatar_url"),
    quick_replies=merged_item.get("quick_replies") or None,
```

The `or None` on `quick_replies` normalizes an empty list `[]` to `None` so that `exclude_none=True` omits it from non-bot messages, consistent with how other optional list fields are handled in the same function.

### No other changes required

- `MessageOut` already has the five fields declared as `Optional` with `None` defaults.
- `merged_item` is the fully-merged DDB item dict that contains all stored attributes.
- All five fields are `Optional`; for non-bot messages, `merged_item.get(...)` will return `None` and they will be omitted from the serialized response (`exclude_none=True`). Zero behavioral change for non-bot messages.

### Full `return MessageOut(...)` addition in context

```python
# app/routers/messaging.py:4226-4232 (existing lines before fix)
    view_once=bool(merged_item.get("view_once")),
    expired=expired,
    locked=has_lock,
    lock_price_cents=int(merged_item["lock_price_cents"]) if merged_item.get("lock_price_cents") else None,
    lock_description=merged_item.get("lock_description"),
    is_unlocked=is_unlocked,
    # ↓ ADD THESE FIVE LINES
    sender_type=merged_item.get("sender_type"),
    bot_id=merged_item.get("bot_id"),
    bot_name=merged_item.get("bot_name"),
    bot_avatar_url=merged_item.get("bot_avatar_url"),
    quick_replies=merged_item.get("quick_replies") or None,
)
```

### Dev/Prod parity (SECOPS-007)

- `merged_item.get(...)` reads from a plain Python dict (the deserialized DDB item). This is identical in dev (DynamoDB Local) and production (AWS DynamoDB). No parity risk whatsoever.
- No environment-specific code path, feature flag, or mock branch is involved.
- The fix is purely additive: five optional fields. It cannot break existing tests or behavior.

### Backward compatibility

- Adding five `None`-defaulted optional fields to the `MessageOut` constructor call is fully backward-compatible. Existing non-bot message items in DynamoDB do not have these attributes; `merged_item.get(...)` returns `None`; the fields are excluded from the response by `exclude_none=True`. Zero change in API response shape for non-bot messages.
- Existing API clients that do not read bot fields are unaffected.
- Existing tests that assert on message response shapes will continue to pass (the new fields are `None` and therefore absent from JSON output).

### Alternatives considered

- **`model_validate` from TypedDict**: Replacing the explicit `return MessageOut(...)` construction with `MessageOut.model_validate(merged_item)` would make omissions impossible (all fields would be auto-populated if present). Rejected as too large a refactor for a targeted gap fix — the 70-argument call is load-bearing and changing it risks introducing regressions in other field mappings.
- **A separate `_bot_fields_from_item` helper**: Extract bot field extraction into a small helper. This is a clean design but adds complexity for a five-line addition. Deferred to a later refactor pass.

## 5. Testing, Verification & Rollout

### Regression test — pytest (offline, fails before / passes after)

```python
# tests/test_message_out_bot_fields.py

import pytest
from app.core.tables import T
from app.core.time import now_ts


def test_message_out_from_item_populates_bot_fields(client, dynamodb_tables, alice_session):
    """GET /ui/messaging/conversations/{id}/messages must include bot fields.
    Before fix: sender_type, bot_id, bot_name, bot_avatar_url, quick_replies all absent.
    After fix:  all five fields present with correct values.
    """
    convo_id = "conv_bot_test_001"
    msg_id = "m_bot_msg_001"
    now = now_ts()

    # Seed a bot message directly in T.messages (simulates what GAP-0015 fix will write)
    T.messages.put_item(Item={
        "conversation_id": convo_id,
        "message_id": msg_id,
        "sender_id": "bot:bot_123",
        "sender_type": "bot",
        "bot_id": "bot_123",
        "bot_name": "HelperBot",
        "bot_avatar_url": "https://cdn.example.com/bot.png",
        "quick_replies": [{"label": "Yes", "value": "yes"}, {"label": "No", "value": "no"}],
        "text": "Which option?",
        "kind": "text",
        "created_at": now,
        "status": "active",
        "is_encrypted": False,
        "view_once": False,
    })

    # Seed conversation membership so Alice can read the message
    T.conversations.put_item(Item={
        "conversation_id": convo_id,
        "participant_id": alice_session["user_sub"],
        "status": "active",
        "created_at": now,
    })

    resp = client.get(
        f"/ui/messaging/conversations/{convo_id}/messages",
        cookies=alice_session["cookies"],
        headers={"x-csrf-token": alice_session["csrf_token"]},
    )
    assert resp.status_code == 200
    messages = resp.json()
    msg = next((m for m in messages if m["message_id"] == msg_id), None)
    assert msg is not None, "bot message not found in response"

    # FAIL before fix (all five fields absent/None)
    # PASS after fix
    assert msg.get("sender_type") == "bot"
    assert msg.get("bot_id") == "bot_123"
    assert msg.get("bot_name") == "HelperBot"
    assert msg.get("bot_avatar_url") == "https://cdn.example.com/bot.png"
    qr = msg.get("quick_replies")
    assert isinstance(qr, list) and len(qr) == 2
    assert qr[0]["label"] == "Yes"


def test_non_bot_message_has_no_bot_fields(client, dynamodb_tables, alice_session):
    """Non-bot messages must not include bot fields in the response."""
    convo_id = "conv_no_bot_001"
    msg_id = "m_user_msg_001"
    now = now_ts()

    T.messages.put_item(Item={
        "conversation_id": convo_id,
        "message_id": msg_id,
        "sender_id": alice_session["user_sub"],
        "text": "Hello",
        "kind": "text",
        "created_at": now,
        "status": "active",
        "is_encrypted": False,
        "view_once": False,
    })
    T.conversations.put_item(Item={
        "conversation_id": convo_id,
        "participant_id": alice_session["user_sub"],
        "status": "active",
        "created_at": now,
    })

    resp = client.get(
        f"/ui/messaging/conversations/{convo_id}/messages",
        cookies=alice_session["cookies"],
        headers={"x-csrf-token": alice_session["csrf_token"]},
    )
    messages = resp.json()
    msg = next((m for m in messages if m["message_id"] == msg_id), None)
    assert msg is not None

    # Non-bot messages must not leak bot fields
    assert "sender_type" not in msg or msg.get("sender_type") is None
    assert "bot_id" not in msg or msg.get("bot_id") is None
    assert "bot_name" not in msg or msg.get("bot_name") is None
    assert "quick_replies" not in msg or msg.get("quick_replies") is None
```

### Observability

No new metrics needed. The fix has no error paths — it is five `merged_item.get(...)` reads, all of which return `None` gracefully if the attribute is absent.

### Rollout

- Deploy as part of the BOT-001 feature rollout.
- Can be deployed before GAP-0015 is fixed — it will have no visible effect until bot messages are actually written to DynamoDB, but it does not break any existing functionality.
- Recommended sequencing: fix GAP-0015 first (writes bot messages to DDB), then this fix (ensures they are correctly serialized in responses). Both can be in the same PR.

### Risks

- **Zero risk** of regression for non-bot messages — all five new arguments are `None` for non-bot items and are excluded from JSON output by `exclude_none=True`.
- The only possible failure mode is if `merged_item.get("quick_replies")` returns a value that is not JSON-serializable. `quick_replies` is stored as a DynamoDB List of Maps; boto3 deserializes this to a `list[dict]`. Pydantic validates it against `Optional[List[Dict[str, str]]]`. If a malformed item is stored, Pydantic will raise a `ValidationError` at response-construction time, returning a 500. This is acceptable — malformed data in the messages table should surface as errors.

**Effort**: S — approximately 30 minutes: five lines of code plus test writing (~2–3 hours with test fixture setup).
