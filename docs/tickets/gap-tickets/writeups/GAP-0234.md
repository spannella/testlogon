# GAP-0234: No Per-Host `record_sessions` Flag (INFRA-001 Dependency) — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code; file:line citations are from
> the live codebase at `/home/ubuntu/testlogon`.

## 1. Summary & Classification

**Gap**: The INFRA-010 / INFRA-001 design requires each host record to carry a
`record_sessions: bool` field. When the flag is `true`, the WebSocket `connect`
handler should automatically call `start_recording()` without requiring the caller
to manually POST to the recording endpoint first. Neither the field nor the
`_should_record()` gate exists anywhere in the `app/services/host_inventory.py`
service or the `app/routers/browser_ssh_terminal.py` handler.

**Severity**: HIGH. Owning area: Infrastructure / SSH Terminal (INFRA-010).
**Status**: Open. **Source ticket**: INFRA-010 (same ticket as GAP-0233).
**Effort**: M.

**Claim accuracy**: Confirmed. `app/services/host_inventory.py` line 159–177
(`_item_to_host`) serializes fourteen fields; `record_sessions` is absent.
`create_host` (line 184) and `update_host` (line 262) have no `record_sessions`
parameter. The string `record_sessions` and `_should_record` do not appear in any
Python file under `app/`.

**Impact**: Recording enforcement is entirely manual and opt-in per session.
Administrators who set a policy that all connections to a given host must be
recorded have no mechanism to enforce it at the infrastructure layer.

**Related tickets**: INFRA-010 (parent), GAP-0233 (missing recording hook in
WebSocket output loop — the mechanism this flag would control), INFRA-001
(host inventory design), SECOPS-007 (dev/prod parity).


## 2. Current-State Investigation (root cause)

### Host inventory schema — `record_sessions` absent

`app/services/host_inventory.py` serializes host items via `_item_to_host` at
line 150–177. The complete field list is:

```
host_id, label, hostname, port, protocol, username, description,
tags, group, os_type, created_at, updated_at, last_connected_at,
connection_count, status, is_pinned, source
```

`record_sessions` is not in this list. The DynamoDB item for a host therefore never
has this attribute.

### `create_host` — no parameter, no storage

`create_host` (line 184) accepts `label`, `hostname`, `port`, `protocol`,
`username`, `description`, `tags`, `group`, `os_type`, and `source`. There is no
`record_sessions` parameter. The item written to DynamoDB at line 239 does not
include the field.

### `update_host` — no path to set the flag

`update_host` (line 262) accepts `**updates` kwargs and dynamically builds an
`UpdateExpression`. Because no validation or whitelist exists for `record_sessions`,
even if a caller passed `record_sessions=True` in kwargs it would be silently
dropped. (In practice the router validates the request body via Pydantic and would
reject an unknown field at that layer.)

### Browser SSH handler — never reads host record

`app/routers/browser_ssh_terminal.py` processes a `connect` message using only the
fields in `normalized` (the validated payload dict): `host`, `port`, `username`,
`authType`, and credential fields. There is no lookup of the `host_id` from the
host inventory, and no `_should_record()` gate. The connect handler (lines 828–965)
makes no call to any host inventory service function.

### The recording service is ready

`app/services/ssh_session_recording.py` line 123 (`start_recording`) is fully
implemented and tested. The missing piece is purely the trigger: reading the
`record_sessions` flag and calling `start_recording` automatically.

### Dev vs prod parity (SECOPS-007)

Host inventory writes to `T.host_inventory` (DynamoDB; tables.py line 538).
The recording service writes to `T.ssh_session_recordings`. Both are DynamoDB tables
available in dev (Local) and production (AWS). No mock/real branch exists in either
service. Adding `record_sessions` as a DynamoDB attribute is inherently parity-safe.


## 3. Impact / Exploit / Blast Radius

**Policy enforcement gap**: Organizations that need mandatory session recording for
specific hosts (e.g., production database servers, compliance-sensitive machines)
cannot enforce the policy at the platform layer. A user connecting via browser SSH
can skip recording entirely by not calling the recording API.

**Audit traceability gap**: Even if GAP-0233 is fixed (server-side auto-recording),
without the per-host flag there is no way to say "record all sessions to host X but
not host Y". The only available granularity is the global
`SSH_SESSION_RECORDING_ENABLED` setting, which applies to all hosts uniformly.

**No data exfiltration or privilege escalation**: This is a missing compliance
control, not an access-control vulnerability. The blast radius is limited to
compliance posture and audit trail completeness.

**Interaction with GAP-0233**: GAP-0233 adds server-side automatic recording for
all sessions. GAP-0234 adds per-host opt-in/out. Both can be delivered together or
sequentially (GAP-0234 depends on GAP-0233's recording hook, but the schema change
can be merged first independently).


## 4. Fix Design (code-level)

### 4.1 Add `record_sessions` to the host schema

In `app/services/host_inventory.py`, extend `_item_to_host` (line 150):

```python
# Add after "source": item.get("source", "manual"),
"record_sessions": bool(item.get("record_sessions", False)),
```

Extend `create_host` signature and item dict:

```python
def create_host(
    user_sub: str,
    *,
    label: str,
    hostname: str,
    port: Optional[int] = None,
    protocol: str = "ssh",
    username: str = "",
    description: str = "",
    tags: Optional[List[str]] = None,
    group: str = "",
    os_type: str = "unknown",
    source: str = "manual",
    record_sessions: bool = False,      # NEW
) -> Dict[str, Any]:
    ...
    item = {
        ...
        "record_sessions": bool(record_sessions),   # NEW
    }
```

Extend `update_host` to accept the field explicitly (add to its whitelist of
accepted kwargs, or handle via the existing generic `**updates` path with an
explicit allowlist check):

```python
# In update_host, add to the accepted-fields set:
_UPDATABLE_FIELDS = {
    "label", "hostname", "port", "protocol", "username", "description",
    "tags", "group", "os_type", "is_pinned", "record_sessions",   # record_sessions added
}
```

### 4.2 Pydantic models in `app/models.py`

The `HostCreateIn` and `HostUpdateIn` models must include the new field:

```python
class HostCreateIn(BaseModel):
    label:           str
    hostname:        str
    port:            Optional[int] = None
    protocol:        str = "ssh"
    username:        str = ""
    description:     str = ""
    tags:            List[str] = []
    group:           str = ""
    os_type:         str = "unknown"
    record_sessions: bool = False       # NEW

class HostUpdateIn(BaseModel):
    label:           Optional[str] = None
    hostname:        Optional[str] = None
    ...
    record_sessions: Optional[bool] = None   # NEW

class HostOut(BaseModel):
    host_id:          str
    ...
    record_sessions:  bool = False      # NEW
```

### 4.3 `_should_record()` helper

Add to `app/services/host_inventory.py` (or a thin compute policy module):

```python
def _should_record(user_sub: str, host_id: str | None) -> bool:
    """Return True if the host requires automatic session recording.

    Falls back to False if host_id is absent or host is not found.
    This function must never raise — it is called from the hot WebSocket path.
    """
    if not host_id:
        return False
    if not S.ssh_session_recording_enabled:
        return False
    try:
        raw = _get_raw(user_sub, host_id)
        return bool((raw or {}).get("record_sessions", False))
    except Exception:
        logger.exception("_should_record lookup failed host_id=%s", host_id)
        return False
```

### 4.4 Wire into the WebSocket connect handler

The `connect` payload can optionally include `host_id` (the registered host to
connect to, used for inventory lookup). After the existing destination-policy check
in `browser_ssh_terminal.py` (line 876), add:

```python
# Resolve per-host recording preference
connect_host_id = str((normalized.get("host_id") or "")).strip()
auto_record = False
if connect_host_id and S.ssh_session_recording_enabled:
    from app.services.host_inventory import _should_record
    auto_record = _should_record(session_user_sub, connect_host_id)
```

Then in the success branch (line 930+), replace the unconditional
`if S.ssh_session_recording_enabled:` check from GAP-0233 with:

```python
if auto_record or S.ssh_session_recording_always_record:
    # start_recording() as described in GAP-0233 fix
    ...
```

`S.ssh_session_recording_always_record` is an optional global override that records
all sessions regardless of the per-host flag; defaults `False`.

### 4.5 Dev/Prod parity (SECOPS-007)

- `_should_record` reads from DynamoDB only; no mock/real branch needed.
- `record_sessions` is a plain boolean DynamoDB attribute — present in both
  DynamoDB Local (dev) and AWS DynamoDB (production).
- The feature flag `SSH_SESSION_RECORDING_ENABLED` gates the entire system on both
  paths uniformly.

### 4.6 DynamoDB migration

No new table or GSI is required. The `record_sessions` attribute is simply added
to new and updated host items. Existing host records will lack the attribute and
`_item_to_host` defaults it to `False`, which matches current behavior (no automatic
recording for pre-existing hosts). Opt-in is explicit.

### Alternatives considered

- **Global `record_sessions` setting only (no per-host granularity)**: Simpler,
  but the ticket design explicitly requires per-host control. A global flag is
  retained as `ssh_session_recording_always_record` for environments that want
  universal recording.
- **Tag-based policy (`record_sessions` as a tag string)**: More flexible but
  inconsistent with the rest of the host schema; a typed boolean is cleaner.
- **Recording decided by `connect` payload from client**: The client cannot be
  trusted to enforce compliance-mandated recording. Server-side enforcement via the
  host record is required.

### API-level test (Playwright / E2E)

```typescript
// frontend/e2e/host-recording-flag.spec.ts  (new spec)
test("record_sessions flag is returned and settable via API", async ({ request }) => {
  const create = await request.post("/ui/compute/hosts", {
    data: { label: "prod", hostname: "10.0.0.1", record_sessions: true },
  });
  expect(create.status()).toBe(201);
  const host = await create.json();
  expect(host.record_sessions).toBe(true);

  const update = await request.patch(`/ui/compute/hosts/${host.host_id}`, {
    data: { record_sessions: false },
  });
  const updated = await update.json();
  expect(updated.record_sessions).toBe(false);
});
```

### Schema compatibility and migration

The DynamoDB `host_inventory` table uses `PK=user_sub`, `SK=HOST#{host_id}`. No
GSI change is needed for the `record_sessions` field — it is never queried in
isolation. Existing host records in DynamoDB lack the attribute. `_item_to_host`
defaults `record_sessions` to `False` via `bool(item.get("record_sessions", False))`,
which produces correct behavior: all existing hosts will not auto-record until the
field is explicitly set.

No migration script is required. Operators who want to enable recording on existing
hosts can call `PATCH /ui/compute/hosts/{id}` with `{"record_sessions": true}`.

### Observability

`_should_record` is a read-only helper with a full `try/except`; failures are logged
at `exception` level with `host_id` context. Add a structured log at the connect
point in the WebSocket handler:
```python
logger.info(
    "browser_ssh auto_record_decision auto_record=%s host_id=%s",
    auto_record, connect_host_id or "(none)"
)
```
This gives a log entry for every connection showing whether auto-recording was
activated, making it easy to audit in a log aggregation system.

### Rollout

- **Effort**: M (schema change in service + Pydantic model updates + host inventory
  tests + WebSocket handler changes + 2–3 new test files).
- **Risk**: Low. The new field defaults `False` — zero behavioral change for all
  existing hosts. The only new behavior is opt-in and explicit.
- **Sequencing**: The schema and model changes (sections 4.1–4.2) can be merged
  independently and in advance of GAP-0233. The `_should_record` integration
  (sections 4.3–4.4) depends on GAP-0233's recording hook being present in the
  WebSocket handler; that integration should be merged as a single PR after GAP-0233.
- **Rollback**: If issues arise, set `SSH_SESSION_RECORDING_ENABLED=false` to
  disable all recording globally. To roll back the schema change, remove
  `record_sessions` from `HostCreateIn`, `HostUpdateIn`, `HostOut`, and
  `_item_to_host`. Existing DDB items with the attribute are harmless (ignored after
  rollback).
- **Future extension**: A `record_sessions_min_duration_seconds` field per host
  would allow suppressing very short sessions (accidental connects) from being
  recorded. This is out of scope for this ticket.
