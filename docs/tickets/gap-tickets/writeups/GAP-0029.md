# GAP-0029: Old `POST /ui/privacy/delete-account` Endpoint Skips Production Password Verification — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: The platform has two account-deletion endpoints. The new endpoint (`POST /ui/privacy/account-deletion/request` in `app/routers/account_deletion.py`) correctly calls `verify_user_password(user_sub, body.password)` which invokes Cognito `AdminInitiateAuth` in production. The old endpoint (`POST /ui/privacy/delete-account` in `app/routers/privacy.py`) contains a password-verification block that is nothing but a comment placeholder: the `if not S.dev_mode:` branch is completely empty. In production (`S.dev_mode=False`), any non-empty string — including a single character such as `"x"` — is accepted as the user's password. An attacker with a stolen session cookie can schedule account deletion for the victim without knowing their password.

- **Severity**: Critical (CRIT)
- **Source ticket**: PLATFORM-018
- **Status**: Open
- **Owning area**: Privacy / Account Management / Auth
- **Effort**: S

**Verdict**: Confirmed. The investigation (`docs/tickets/gap-tickets/investigations/GAP-0029.md`) confirmed two coexisting delete-account endpoints with materially different security postures. The old route is registered and reachable at `POST /ui/privacy/delete-account` via `privacy_router` included at `app/main.py:630`.

**One-line impact**: A session-hijacked account can be scheduled for full data deletion without the attacker knowing the victim's real password, bypassing the only authentication layer protecting this irreversible action.

**Related tickets**: PLATFORM-018 (source), SEC-018 (session revocation), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### The new endpoint (correct)

`app/routers/account_deletion.py:58–75` defines `POST /ui/privacy/account-deletion/request`:

```python
@account_deletion_router.post("/request", status_code=201)
def create_deletion(
    body: AccountDeletionRequestIn,
    ctx: Dict[str, Any] = Depends(require_ui_session),
) -> AccountDeletionStatusOut:
    if not S.account_deletion_enabled:
        raise HTTPException(status_code=503, detail="Account deletion is temporarily unavailable")
    user_sub = ctx["user_sub"]

    if not verify_user_password(user_sub, body.password):
        logger.warning("privacy.password_verification_failed user=%s", user_sub)
        raise HTTPException(status_code=401, detail="Invalid password")
    ...
```

`verify_user_password` at `app/services/cognito_auth.py:21` behaves as follows:

- Empty password → returns `False` immediately.
- `S.dev_mode=True` or Cognito not configured → returns `True` (accepts any non-empty password; dev-mode convenience).
- Production (`S.dev_mode=False`, Cognito configured) → calls `AdminInitiateAuth` with `ADMIN_USER_PASSWORD_AUTH` flow; returns `True` only if Cognito confirms the password.

This is the correct implementation.

### The old endpoint (broken)

`app/routers/privacy.py:126–154` defines `POST /ui/privacy/delete-account` (note the different URL path):

```python
@router.post("/delete-account", status_code=201)
def request_deletion(
    body: DeleteAccountRequestIn,
    ctx: Dict[str, Any] = Depends(require_ui_session),
) -> DataRequestOut:
    if not S.privacy_deletion_enabled:
        raise HTTPException(status_code=403, detail="Account deletion is currently disabled")

    user_sub = ctx["user_sub"]

    if has_retention_hold(user_sub):
        raise HTTPException(status_code=403, detail="Account has a retention hold")

    if has_pending_deletion(user_sub):
        raise HTTPException(status_code=409, detail="Pending deletion request already exists")

    # Password verification (in dev mode, accept any non-empty password)
    if not body.password:
        raise HTTPException(status_code=401, detail="Password required")

    if not S.dev_mode:
        # In production, verify against Cognito
        # For now, this is a placeholder
        pass   # ← THE GAP: this block is completely empty

    item = create_deletion_request(user_sub, reason=body.reason)
    return DataRequestOut(**_item_to_out(item))
```

The logic flow in production (`S.dev_mode=False`):
1. `if not body.password:` — requires a non-empty password string. Rejects empty string `""`.
2. `if not S.dev_mode:` — enters the block because `S.dev_mode=False` in production.
3. `pass` — does nothing. Execution continues to `create_deletion_request(...)`.

Result: any non-empty password value — `"x"`, `"wrong"`, `"idonotknowthepassword"` — is silently accepted in production. There is no Cognito call.

### Router registration

`app/routers/privacy.py:43` sets `router = APIRouter(prefix="/ui/privacy", ...)`. This router is imported and included in `app/main.py:630`:

```python
app.include_router(privacy_router)
```

The old endpoint is live and reachable at `POST /ui/privacy/delete-account`.

### SEC-018 cross-reference

The old route also does not call `revoke_all_sessions` or any session-revocation step when the deletion is scheduled. The new route defers session revocation to the background deletion processor. The old route calls `create_deletion_request(user_sub, ...)` from a different service module (`app/services/privacy.py` vs `app/services/account_deletion.py`), meaning the lifecycle, grace-period handling, and retention-hold checks differ between the two code paths.

### Root cause

`app/routers/account_deletion.py` was added as part of PLATFORM-018 as a complete replacement for the legacy deletion flow in `privacy.py`. The old endpoint was marked with a `# For now, this is a placeholder` comment but was never removed. The new endpoint was deployed alongside the old one, leaving both active simultaneously with divergent security postures.

## 3. Impact / Exploit / Blast Radius

### Exploit walkthrough

An attacker who has obtained a valid session cookie for a victim (via XSS, session fixation, malicious browser extension, or similar) can execute account deletion without knowing the victim's password:

1. Obtain victim's session cookies: `ui_session`, `ui_csrf`, `ui_access_token`.
2. Call:
   ```
   POST /ui/privacy/delete-account
   Cookie: ui_session=<victim_session>; ui_csrf=<victim_csrf>
   x-csrf-token: <victim_csrf>
   Content-Type: application/json

   {"password": "x", "reason": "test"}
   ```
3. Server accepts the request with HTTP 201 because `body.password = "x"` is non-empty and the `if not S.dev_mode:` block is a `pass`.
4. `create_deletion_request` schedules the victim's account for deletion after the grace period.

**Worst case**: If `S.account_deletion_destructive=True` (the production setting for full data cascade), after the grace period expires the deletion processor permanently deletes the victim's messages, files, subscriptions, and payment history. There is typically no recovery path after the grace period.

**Cross-reference with SEC-018**: Even if the attacker's session is revoked after the fact, the deletion request is already in the queue. The current grace period check in `create_deletion_request` requires the victim to explicitly cancel before the deadline. The old route (`app/routers/privacy.py`) also does not call `revoke_all_sessions(user_sub)` on initiation, meaning the attacker's stolen session remains valid throughout the grace period. The new route defers revocation to the background deletion processor, which is a longer window but at least provides eventual revocation. In the old route, no revocation is planned at any stage.

**Notification gap**: The old `create_deletion_request` path (in `app/services/privacy.py`) may not send the same confirmation email that the new path (`app/services/account_deletion.py`) sends. If the victim does not receive a deletion-confirmation email, they have no signal that their account has been scheduled for deletion and cannot cancel before the grace period expires.

### Without session hijacking (authentication bypass vector)

If an attacker can predict or enumerate CSRF tokens (a separate SEC concern), they can perform deletion without any session cookie. The first line of defense (valid session) is still in place, but the second factor (real password) is completely absent.

### Blast radius

- **Any authenticated user** who has their session cookie exposed (a realistic threat in environments with other unrelated XSS vulnerabilities or where sessions are shared via browser profiles) is at risk.
- **Scope**: every account on the platform. The endpoint accepts any authenticated session.
- **Irreversibility**: account deletion with `account_deletion_destructive=True` cannot be undone after the grace period. Financial records, message history, file data, and identity information are all destroyed.

## 4. Fix Design (Code-Level)

### Option A — Remove the old endpoint (preferred)

Delete the `request_deletion` handler from `app/routers/privacy.py` (lines 126–154). This is the correct approach because the new endpoint in `account_deletion.py` already provides the correct implementation with full password verification, grace-period lifecycle, audit trail, and retention-hold checks.

```python
# app/routers/privacy.py — DELETE lines 126–154:
# @router.post("/delete-account", status_code=201)
# def request_deletion(...):
#     ...  (remove entire function)
```

Update any frontend code that calls `/ui/privacy/delete-account` to instead call `/ui/privacy/account-deletion/request`. Search `frontend/src/` for references:

```bash
grep -r "delete-account\|privacy/delete" frontend/src/
```

### Option B — Patch the old endpoint (fallback if frontend migration is not immediately feasible)

Replace the placeholder block in `app/routers/privacy.py:144–151`:

```python
# BEFORE (app/routers/privacy.py:144–151):
    if not body.password:
        raise HTTPException(status_code=401, detail="Password required")

    if not S.dev_mode:
        # In production, verify against Cognito
        # For now, this is a placeholder
        pass

# AFTER:
    from app.services.cognito_auth import verify_user_password
    if not verify_user_password(user_sub, body.password):
        raise HTTPException(status_code=401, detail="Invalid password")
```

This two-line change brings the old endpoint to parity with the new one. `verify_user_password` handles the dev/prod split internally: in dev mode it accepts any non-empty password; in production it calls Cognito.

Option A is strongly preferred because it eliminates the duplicated code path and the risk of future divergence between the two endpoints.

### Dev/Prod Parity (SECOPS-007)

`verify_user_password` (`app/services/cognito_auth.py:21`) already implements the correct dev/prod split:

```python
def verify_user_password(user_sub: str, password: str) -> bool:
    if not password:
        return False
    if S.dev_mode or not _cognito_configured():
        return True  # dev mode: accept any non-empty password
    # production: call Cognito AdminInitiateAuth
    ...
```

In dev mode (`S.dev_mode=True`), the fix accepts any non-empty password, consistent with the rest of the stack and with the correct new endpoint. In production (`S.dev_mode=False`, Cognito configured), Cognito verifies the real password. No additional parity work is required.

### Backward compatibility

Option A may break existing frontend code that still calls the old URL. An audit of the frontend is required before removing the endpoint. A temporary redirect (HTTP 301) from `/ui/privacy/delete-account` to `/ui/privacy/account-deletion/request` can bridge the gap during the migration period:

```python
# Temporary bridge (optional, in app/routers/privacy.py):
@router.post("/delete-account", status_code=301, include_in_schema=False)
def delete_account_redirect():
    from fastapi.responses import RedirectResponse
    return RedirectResponse(url="/ui/privacy/account-deletion/request", status_code=307)
```

Note: 307 (Temporary Redirect) preserves the POST method; 301 would convert it to GET.

## 5. Testing, Verification & Rollout

### Regression test — password bypass (pytest offline, fails-before / passes-after)

```python
# tests/test_privacy_delete_account_password.py
import pytest


def test_old_delete_account_rejects_wrong_password_in_prod(
    test_client, alice_session, monkeypatch
):
    """
    FAILS BEFORE FIX: POST /ui/privacy/delete-account with password='wrong_but_nonempty'
                       returns 201 (deletion scheduled) because verification is a no-op.
    PASSES AFTER FIX:  returns 401 (Invalid password).

    Simulates production by patching S.dev_mode=False and mocking Cognito to reject.
    """
    from app.core.settings import S
    from app.services import cognito_auth

    # Simulate production: dev_mode=False, Cognito configured and rejects the password
    monkeypatch.setattr(S, "dev_mode", False)
    monkeypatch.setattr(
        cognito_auth,
        "verify_user_password",
        lambda user_sub, pw: False,  # always reject
    )

    resp = test_client.post(
        "/ui/privacy/delete-account",
        json={"password": "wrong_but_nonempty", "reason": "test"},
        cookies=alice_session["cookies"],
        headers={"x-csrf-token": alice_session["csrf_token"]},
    )
    # Before fix: 201 (deletion scheduled — password not verified)
    # After fix:  401 (Invalid password)
    assert resp.status_code == 401
    assert "password" in resp.json().get("detail", "").lower()


def test_old_delete_account_accepts_empty_password(test_client, alice_session):
    """Empty password must always be rejected (pre-existing check)."""
    resp = test_client.post(
        "/ui/privacy/delete-account",
        json={"password": "", "reason": "test"},
        cookies=alice_session["cookies"],
        headers={"x-csrf-token": alice_session["csrf_token"]},
    )
    assert resp.status_code == 401


def test_new_delete_account_endpoint_still_works(
    test_client, alice_session, monkeypatch

    from app.services import cognito_auth
    monkeypatch.setattr(

    resp = test_client.post(
        "/ui/privacy/account-deletion/request",
```

### Manual QA steps

1. Start the dev stack: `just up`.
2. Log in as Alice.
3. Call `POST /ui/privacy/delete-account` with `password="x"` (any non-empty wrong password).
4. **Before fix**: response is `201 Created` — deletion is scheduled.
5. **After fix** (Option A): response is `404 Not Found` (endpoint removed).
6. **After fix** (Option B): response is `401 Unauthorized` with `"Invalid password"` detail.
7. Call `POST /ui/privacy/account-deletion/request` with `password="x"` — should still return `201` in dev mode (dev mode accepts any non-empty password).
8. Repeat step 3 with `S.dev_mode` simulated as `False` — should return `401`.

### Metrics and observability

- The new endpoint already logs `logger.warning("privacy.password_verification_failed user=%s", user_sub)` on failure. After applying Option A, monitor CloudWatch for the absence of calls to the old path (`/ui/privacy/delete-account`). A non-zero call rate after deployment would indicate a frontend client not yet migrated.
- Set a CloudWatch alarm for `account_deletion_request` rate spike — a sudden increase might indicate exploitation of the vulnerability before the fix was applied.

### Rollback

Option A rollback: restore the deleted endpoint handler and redeploy. Option B rollback: revert two lines. No DynamoDB changes required. Any deletion requests already queued via the exploited endpoint should be reviewed and cancelled if fraudulent.

### Risks

- **Frontend migration (Option A)**: Removing the endpoint breaks any frontend component or third-party integration that still calls `/ui/privacy/delete-account`. Audit all call sites before removing. The `grep` above (`grep -r "delete-account\|privacy/delete" frontend/src/`) should return zero results after migration.
- **Pending fraudulent deletions**: If the endpoint was exploited between its deployment and the fix, fraudulent deletion requests may already be queued. Audit the `data_requests` DynamoDB table for deletion records where `initiated_at` is close to the deploy date and cross-reference with account activity.

### Preventing recurrence

Add an automated test that asserts only one delete-account endpoint is registered at the given URL. This prevents a future regression where a new endpoint is added that re-introduces the same gap:

```python
# tests/test_no_duplicate_deletion_endpoints.py
def test_only_new_deletion_endpoint_is_registered(test_client):
    """Verify the old /ui/privacy/delete-account route is gone."""
    resp = test_client.options("/ui/privacy/delete-account")
    # After Option A: 404 (route removed)
    # If route must remain: 405 Method Not Allowed for POST (redirect only)
    assert resp.status_code in (404, 307)

    resp2 = test_client.options("/ui/privacy/account-deletion/request")
    # New route must still exist
    assert resp2.status_code != 404
```

Add a code review checklist item: any new account-deletion or account-modification endpoint must call `verify_user_password` before scheduling any irreversible operation. This mirrors the principle of "step-up authentication for destructive actions" that is common in identity management best practices.

### Effort and sequencing

**S** — removing the handler (or adding two lines) plus updating frontend call sites plus unit tests. The frontend audit (searching for calls to the old URL) is the bulk of the work. Estimated total: 2–4 hours including frontend migration validation and integration test authoring.
