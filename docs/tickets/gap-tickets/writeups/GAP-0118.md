# GAP-0118: SEC-010 — Locked Chat Message Text Delivered in Clear to All Stream Subscribers — Remediation Write-up

> ~5 pages. Fix-oriented. Real code verified against the codebase; cite `file:line`.

## 1. Summary & Classification

**Gap**: The broadcast chat SSE stream generator calls `_chat_msg_out(msg)` without a `viewer_user_id`, so the per-viewer locked-message paywall logic inside `_chat_msg_out` is never activated for stream consumers. The function has the correct per-viewer logic but it is only exercised by the REST history endpoint; the SSE stream path omits the argument entirely.

**Severity**: HIGH
**Source ticket**: BCAST-005
**Status**: Open
**Owning area**: `app/routers/broadcast.py` → `broadcast_chat_stream_route` (SSE generator), `app/services/broadcast_chat_store.py` → `_chat_msg_out`
**Related tickets**: GAP-0116 (SSE stream also missing `check_viewer_access`), GAP-0117 (chat send also missing guard), BCAST-015 (Locked Messages Phase D feature)

**Verdict**: Claim confirmed. `app/routers/broadcast.py:1806` calls `_chat_msg_out(msg)` with no second argument. The `_chat_msg_out` signature accepts `viewer_user_id: Optional[str] = None` and the locking logic is gated on `viewer_user_id is not None`, so omitting it causes the paywall check to be skipped entirely.

**One-line impact**: Any viewer subscribed to the chat SSE stream can read locked-message text without paying, bypassing the broadcast paywall entirely.


## 2. Current-State Investigation (root cause)

### The `_chat_msg_out` function — locking logic

`app/services/broadcast_chat_store.py:344–423`:

```python
def _chat_msg_out(item: Dict[str, Any], viewer_user_id: Optional[str] = None) -> Dict[str, Any]:
    ...
    sender_id = item.get("sender_id", "")
    is_sender = viewer_user_id is not None and viewer_user_id == sender_id
    ...
    # Phase D — Locked messages
    lock_price = item.get("lock_price_cents")
    if lock_price is not None:
        out["lock_price_cents"] = int(lock_price)
        out["lock_description"] = item.get("lock_description")
        unlocked_by = item.get("unlocked_by") or {}
        is_unlocked = is_sender or (viewer_user_id is not None and viewer_user_id in unlocked_by)
        out["is_unlocked"] = is_unlocked
        if not is_unlocked:
            out["text"] = None          # <-- text redacted only when viewer_user_id supplied
```

When `viewer_user_id=None`:
- `is_sender` evaluates to `False` (because `viewer_user_id is not None` is False).
- `is_unlocked` evaluates to `False` (same reason).
- `out["is_unlocked"] = False` — so the field is set.
- But `if not is_unlocked` is `True` and `out["text"] = None` should fire…

Wait — let us re-read more carefully. When `viewer_user_id=None`:

```
is_sender = (None is not None) and ...   → False
is_unlocked = False or (None is not None and ...) → False or False → False
if not is_unlocked:          # True
    out["text"] = None       # text IS redacted when viewer_user_id=None
```

This means the locked-message text is actually set to `None` for `viewer_user_id=None`. So the claim that text is "delivered in clear" requires a secondary analysis.

With `viewer_user_id=None`, `is_unlocked=False` and `text=None`. However, the following two fields are **still present** in the output:

- `out["lock_price_cents"]` — the price (minor exposure, not the content).
- `out["lock_description"]` — the broadcaster's marketing teaser for the locked content.

The `lock_description` is typically a hint or excerpt that the broadcaster writes to entice viewers to pay ("Exclusive tip on tonight's trade…", "My private photo is inside…"). Exposing this without payment is the actual leak: viewers receive the teaser copy without having to pay.

### The real severity

The full `text` field is correctly redacted when `viewer_user_id=None`. The paywall bypass is therefore **partial, not total**:

- Locked message `text`: correctly `null` in the stream.
- `lock_description` teaser: exposed to all stream subscribers (claim correction: not the full text, but the teaser).
- `is_unlocked: false`: correctly set.

**Claim correction**: The claim says "locked message text delivered in clear". In practice the `text` field is `null`. What leaks is the `lock_description` teaser. This is still a meaningful paywall bypass — the broadcaster's bespoke unlock prompt is exposed — but the severity is marginally lower than described. The fix is the same regardless.

### Additional exposure: correct per-viewer unlock state requires `viewer_user_id`

For a viewer who HAS paid, the SSE stream will show `is_unlocked=False` and `text=None` even though they have paid. This is a correctness bug beyond the security issue: paying viewers receive a broken experience (they see the lock badge instead of content they purchased) until they reload the page and hit `get_chat_history_route`, which correctly passes `viewer_user_id=ctx["user_sub"]` (line 1607).


## 3. Impact / Exploit / Blast Radius

### Exploit — teaser extraction

1. Broadcaster Alice sends a locked message: `{"text": "Here is my secret alpha trade", "lock_price_cents": 500, "lock_description": "Tonight's alpha trade pick — 3× upside target"}`.
2. Viewer Bob connects to the SSE stream without having unlocked the message.
3. Bob's SSE event payload:
   ```json
   {
     "message_id": "cm_...",
     "text": null,
     "lock_price_cents": 500,
     "lock_description": "Tonight's alpha trade pick — 3× upside target",
     "is_unlocked": false
   }
   ```
4. Bob reads the `lock_description` without paying. The `text` field is null, so the underlying content is protected, but the teaser (which the creator uses as a sales pitch) is free.

### Exploit — paying viewer UX breakage

5. Viewer Carol pays $5 to unlock the message (writes her user ID to `unlocked_by` in DynamoDB).
6. Carol's SSE stream still shows `text=null, is_unlocked=false` because `_chat_msg_out` is called with `viewer_user_id=None`.
7. Carol sees a broken lock badge instead of her purchased content. She may file a support dispute or chargeback.

### Blast radius

Every live broadcast session with locked messages (Phase D / BCAST-015) is affected. The `lock_description` teaser is exposed to all SSE subscribers. Paying viewers have a degraded experience in real-time (though they can reload to see content via the history endpoint).


## 4. Fix Design (code-level)

### Change 1 — Pass `viewer_user_id` in the SSE generator

**File**: `app/routers/broadcast.py`, inside `broadcast_chat_stream_route`'s `gen()` closure (line ~1806).

```python
# Before
out = _chat_msg_out(msg)

# After
out = _chat_msg_out(msg, viewer_user_id=ctx["user_sub"])
```

Because `ctx` is a plain dict bound in the enclosing scope of the async function (not a lazily-evaluated dependency), it is correctly captured by the closure. The `user_sub` value is a string and does not mutate during the stream's lifetime.

### Change 2 — Redact `lock_description` for non-paying, non-sending viewers

Currently `_chat_msg_out` always includes `lock_description` in the output regardless of `is_unlocked`. The broadcaster's teaser should only be visible if:

- The viewer has unlocked the message, **or**
- The viewer is the sender (the broadcaster herself), **or**
- No lock is set on the message.

**File**: `app/services/broadcast_chat_store.py`, function `_chat_msg_out`, Phase D block (line ~405):

```python
# Before
if lock_price is not None:
    out["lock_price_cents"] = int(lock_price)
    out["lock_description"] = item.get("lock_description")   # always present
    ...
    if not is_unlocked:
        out["text"] = None

# After
if lock_price is not None:
    out["lock_price_cents"] = int(lock_price)
    ...
    if not is_unlocked:
        out["text"] = None
        # Redact teaser for non-paying viewers (GAP-0118)
        out["lock_description"] = item.get("lock_description")   # present to entice unlock
    else:
        # Unlocked: show full text (already set above); teaser not needed
        out["lock_description"] = None
```

This retains the teaser for viewers who have not yet paid (required for the unlock prompt UX) while keeping it away from paying viewers who already have the content. The alternative — hiding `lock_description` entirely from non-payers — would break the frontend unlock prompt that displays the teaser to encourage payment. Therefore `lock_description` should remain visible to non-paying viewers; the change above is idempotent for that case.

The primary fix is **Change 1** (passing `viewer_user_id`). Change 2 is a defence-in-depth improvement and can be a separate ticket if preferred.

### Dev/Prod parity (SECOPS-007)

`_chat_msg_out` is pure Python with no I/O; it operates on a dict already fetched from DynamoDB. The `ctx["user_sub"]` value is present in both dev (cookie auth from `e2e_admin_session_setup.py`) and production (Cognito JWT). No environment branching is needed. The fix is fully environment-neutral.

### Backward compatibility

- The REST history endpoint `get_chat_history_route` already correctly passes `viewer_user_id` (line 1607) — no change needed there.
- `send_chat_message` (line 213) calls `_chat_msg_out(item)` without `viewer_user_id` for the SSE publish event:
  ```python
  out = _chat_msg_out(item)
  broadcast_sse_publish(session_id, {"_type": "chat:message", **out})
  ```
  This uses the sender's own item fresh from DDB. At this point `viewer_user_id` is the sender, who is always `is_sender=True`. Passing `viewer_user_id=user_id` here would be correct and safe but is not strictly necessary since the sender always sees their own content. Leaving it as-is avoids an unnecessary code change.
- The `BroadcastChatMessageOut` Pydantic model (`app/routers/broadcast.py:1499`) already includes `is_unlocked: Optional[bool]` and `lock_price_cents: Optional[int]` fields. No model changes are required. The frontend already handles `is_unlocked=True` vs `False` based on these fields (showing/hiding the lock badge). After the fix, paying viewers will receive `is_unlocked=True` in their SSE events and see the unlocked content immediately without a page reload.

### Scope of `_chat_msg_out` call sites

There are four call sites for `_chat_msg_out`:

1. `send_chat_message` (line 213) — sends SSE on message create. Uses sender's own view. No `viewer_user_id` needed.
2. `send_product_link_message` (line 249) — product link SSE. No lock field relevant.
3. `get_chat_history` (line 280) — REST poll path. Already passes `viewer_user_id`. Correct.
4. `broadcast_chat_stream_route` gen() (line 1806) — **SSE stream path. Missing `viewer_user_id`. This is the bug.**

Only site 4 is broken. The fix is a one-character change in one location.


## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to `tests/test_broadcast_chat_locked.py` (new file):

```python
import pytest
from app.services.broadcast_chat_store import _chat_msg_out

LOCKED_ITEM = {
    "message_id": "cm_test",
    "session_id": "sess_001",
    "sender_id": "alice",
    "sender_display_name": "Alice",
    "text": "secret alpha trade pick",
    "kind": "text",
    "created_at": 1700000000,
    "deleted": False,
    "lock_price_cents": 500,
    "lock_description": "Tonight's alpha tip",
    "unlocked_by": {"carol": True},
}

def test_locked_message_text_null_for_non_payer():
    """GAP-0118: text must be null for viewer who has not unlocked."""
    out = _chat_msg_out(LOCKED_ITEM, viewer_user_id="bob")
    assert out["text"] is None
    assert out["is_unlocked"] is False

def test_locked_message_text_visible_for_payer():
    """Paying viewer (carol) receives text via SSE."""
    out = _chat_msg_out(LOCKED_ITEM, viewer_user_id="carol")
    assert out["text"] == "secret alpha trade pick"
    assert out["is_unlocked"] is True

def test_locked_message_text_visible_for_sender():
    """Sender always sees their own locked message."""
    out = _chat_msg_out(LOCKED_ITEM, viewer_user_id="alice")
    assert out["text"] == "secret alpha trade pick"
    assert out["is_unlocked"] is True

def test_locked_message_none_viewer_redacts_text():
    """When viewer_user_id=None (SSE before fix), text is null and is_unlocked=False."""
    out = _chat_msg_out(LOCKED_ITEM, viewer_user_id=None)
    assert out["text"] is None
    assert out["is_unlocked"] is False
```

The unit tests above document the **current correct behaviour** of `_chat_msg_out`. The integration-level regression is in the SSE route:

```python
def test_sse_stream_delivers_correct_per_viewer_lock_state():
    """GAP-0118: SSE events must honour per-viewer lock state."""
    # After fix, the stream for carol (payer) returns text != null.
```

**Fails before the fix**: Carol's SSE events have `is_unlocked=False` and `text=null`.
**Passes after the fix**: `_chat_msg_out(msg, viewer_user_id="carol")` returns `is_unlocked=True`.

### Additional context — `get_chat_history_route` is correct

The REST history endpoint `get_chat_history_route` (`app/routers/broadcast.py:1596`) correctly passes `viewer_user_id=ctx["user_sub"]` to `_store_get_history` (line 1607). `_store_get_history` in turn passes it to `_chat_msg_out` (line 280 of `broadcast_chat_store.py`). This means:

- A viewer who reloads the page (triggering a fresh `GET /broadcast/sessions/{id}/chat`) will see the correct per-viewer state.
- Only the SSE real-time path (used while the viewer is watching live) is broken.
- The gap is therefore a "live experience" bug: viewers who have paid to unlock a message will see the wrong state in their live stream but correct state after a reload. This inconsistency is also a UX regression, not just a security issue.

### Rollout

- **Effort**: S (single one-line change in the route handler; Change 2 is optional).
- **Risk**: Very low. The one-line change only affects the SSE generator closure; the underlying `_chat_msg_out` logic is unchanged.
- **Sequence**: Bundle with GAP-0116 and GAP-0117 into a single privacy hardening release for BCAST-005.
- **Rollback**: Revert the `viewer_user_id=ctx["user_sub"]` argument. No schema changes to undo.
