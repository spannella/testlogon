# GAP-0166: Watch-party SSE reuses broadcast-session namespace — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement.** The Watch Party feature (ENGAGE-004) streams real-time
events — `participant_joined`, `participant_left`, `party_ended`, etc. — to
connected clients over Server-Sent Events (SSE). However, the SSE
subscribe/unsubscribe/publish functions it calls are
`broadcast_sse_subscribe`, `broadcast_sse_unsubscribe`, and
`broadcast_sse_publish`, which all operate on a single shared in-memory
dict `_BROADCAST_SUBSCRIBERS`. Watch-party `party_id` values and broadcast
`session_id` values are stored in the same namespace. A watch party whose
`party_id` happens to collide with a live broadcast `session_id` — or,
more practically, when both systems publish events using the same key — can
deliver watch-party events to broadcast viewers and vice versa, creating
cross-contamination of SSE streams.

**Severity:** HIGH  
**Source ticket:** ENGAGE-004  
**Status:** Open  
**Owning area:** `app/routers/watch_party.py`, `app/services/watch_party.py`,
`app/services/broadcast_sse.py`  
**Effort:** S

**Verdict from code investigation:** Claim confirmed exactly as stated.
`watch_party.py` imports and calls `broadcast_sse_subscribe`,
`broadcast_sse_publish`, and `broadcast_sse_unsubscribe` directly with the
raw `party_id` string. The dict `_BROADCAST_SUBSCRIBERS` is keyed by
whichever string the caller passes — there is no namespacing. Watch-party
and broadcast-session keys share the same flat dictionary.

**Related tickets:** ENGAGE-004, GAP-0167.

## 2. Current-State Investigation (root cause)

### Shared subscriber dictionary

`app/services/broadcast_sse.py:8`:

```python
_BROADCAST_SUBSCRIBERS: Dict[str, Set[asyncio.Queue]] = {}
```

This is a single flat dict. Every call to `broadcast_sse_subscribe(key)`,
`broadcast_sse_publish(key, event)`, and `broadcast_sse_unsubscribe(key, q)`
uses that same dict with whatever `key` is passed by the caller.

### How broadcast sessions use the dict

`app/services/broadcast_store.py` imports and calls all three functions with
a `session_id` (e.g., `bcast_abc123`). The SSE endpoint registered in
`app/routers/broadcast.py:722`:

```python
q = broadcast_sse_subscribe(session_id)
```

### How watch parties use the same dict

`app/services/watch_party.py:17`:

```python
from app.services.broadcast_sse import broadcast_sse_publish
```

`app/routers/watch_party.py:24-27`:

```python
from app.services.broadcast_sse import (
    broadcast_sse_publish,
    broadcast_sse_subscribe,
    broadcast_sse_unsubscribe,
)
```

The SSE endpoint at `app/routers/watch_party.py:262-281`:

```python
@router.get("/{party_id}/stream")
async def party_stream_route(party_id: str, session: dict = Depends(require_ui_session)):
    _ = get_party(party_id)  # 404 if not exists
    q = broadcast_sse_subscribe(party_id)          # ← uses raw party_id
    ...
    finally:
        broadcast_sse_unsubscribe(party_id, q)     # ← raw party_id
```

And every service event publisher in `app/services/watch_party.py` (lines
172, 195, 219, 281, 318, 351) calls:

```python
broadcast_sse_publish(party_id, {"_type": "participant_joined", ...})
```

with the raw `party_id` — no prefix, no namespace.

### Collision scenario at runtime

Both `party_id` and `session_id` are generated from `uuid4().hex` with
different prefixes (`wp_` vs `bcast_`), so an **exact** string collision is
very unlikely. However:

1. The namespace collision is not guarded at any level. Any future refactor
   that changes ID generation could create real overlaps without triggering
   any test failure.
2. A watch-party event such as `participant_joined` published to a key that
   happens to be subscribed by a broadcast-session SSE client will be
   delivered to that client silently. The client may ignore the unknown event
   type, but the risk is real and the coupling is architecturally unsound.
3. In tests and dev environments where `party_id` and `session_id` are often
   short or deterministic strings (`"p1"`, `"s1"`), collisions are easy to
   trigger accidentally and have already masked bugs in practice.

### Why the coupling exists

`watch_party.py` was implemented after `broadcast_sse.py` existed. Rather
than creating a dedicated in-memory pub/sub channel for watch parties, the
implementer reused the broadcast SSE infrastructure verbatim. This was noted
as a gap in the second-pass ENGAGE-004 review.

## 3. Impact / Exploit / Blast Radius

**Who is affected:** Any concurrent users of watch parties and live
broadcasts on the same server process.

**SSE cross-contamination:** A viewer subscribed to a broadcast SSE stream
(`broadcast_sse_subscribe("bcast_xyz")`) will receive events intended for a
watch party if the watch-party service calls
`broadcast_sse_publish("bcast_xyz", ...)`. The probability is negligible with
UUID-based IDs in production but is not zero, and the lack of a namespace
guard is a correctness defect regardless.

**Dev and test instability:** In unit tests that use short, deterministic keys
for both broadcast sessions and watch parties, the collision probability is
high. A test that subscribes to `"session1"` and a watch-party test that
publishes to `"session1"` will cross-fire, producing intermittent false
positives and hard-to-diagnose test failures.

**Availability side-effect:** When a watch party ends and its SSE keys are
cleaned up via `broadcast_sse_unsubscribe`, if a key overlap exists the
broadcast session's subscriber set can be inadvertently pruned. This would
cause broadcast viewers to stop receiving real-time events without an error
message — they would simply see a stalled stream until they refresh.

**Blast radius:** Confined to in-process memory state; no DynamoDB or
persistent data is affected. Restart of the process resets all subscriber
dicts to empty. In production, `uvicorn` runs with `--workers 1` in dev
mode (per CLAUDE.md), so the shared dict is consistent within a process.

## 4. Fix Design (code-level)

The smallest, safest fix is to add a watch-party-specific wrapper around
`broadcast_sse` that prefixes all keys with `"wp:"`. This requires no change
to the shared `_BROADCAST_SUBSCRIBERS` dict and no change to the broadcast
session code path.

### Option A — Key prefix wrapper (preferred, effort S)

Create `app/services/watch_party_sse.py`:

```python
"""Watch-party SSE wrappers — namespaced over broadcast_sse (GAP-0166)."""
from __future__ import annotations

import asyncio
from typing import Any, Dict

from app.services.broadcast_sse import (
    broadcast_sse_publish,
    broadcast_sse_subscribe,
    broadcast_sse_unsubscribe,
)

_WP_PREFIX = "wp:"


def wp_sse_subscribe(party_id: str) -> asyncio.Queue:
    return broadcast_sse_subscribe(f"{_WP_PREFIX}{party_id}")


def wp_sse_unsubscribe(party_id: str, q: asyncio.Queue) -> None:
    broadcast_sse_unsubscribe(f"{_WP_PREFIX}{party_id}", q)


def wp_sse_publish(party_id: str, event: Dict[str, Any]) -> None:
    broadcast_sse_publish(f"{_WP_PREFIX}{party_id}", event)
```

Then update `app/routers/watch_party.py` to import from the new module:

```python
# Before:
from app.services.broadcast_sse import (
    broadcast_sse_publish,
    broadcast_sse_subscribe,
    broadcast_sse_unsubscribe,
)
# After:
from app.services.watch_party_sse import (
    wp_sse_publish as broadcast_sse_publish,
    wp_sse_subscribe as broadcast_sse_subscribe,
    wp_sse_unsubscribe as broadcast_sse_unsubscribe,
)
```

And update `app/services/watch_party.py`:

```python
# Before:
from app.services.broadcast_sse import broadcast_sse_publish
# After:
from app.services.watch_party_sse import wp_sse_publish as broadcast_sse_publish
```

The local aliases (`broadcast_sse_publish`, `broadcast_sse_subscribe`,
`broadcast_sse_unsubscribe`) preserve all existing call sites in both files
unchanged.

### Option B — Separate `_WATCH_PARTY_SUBSCRIBERS` dict (alternative, effort S)

Create a standalone `watch_party_sse.py` with its own `Dict[str, Set[asyncio.Queue]]`.
This is architecturally cleaner (full isolation) but duplicates ~50 lines of
pub/sub logic. Option A is preferred because it avoids duplication while
still achieving complete namespace isolation.

### Dev/Prod parity (SECOPS-007)

`_BROADCAST_SUBSCRIBERS` is in-process memory; there is no AWS-backed
equivalent in production. The parity concern does not apply here — the fix
is purely in-memory and behaves identically in dev and prod.

### Backward compatibility / migration

No DynamoDB schema changes. No API contract changes. Clients subscribing
to `/ui/watch-parties/{party_id}/stream` are unaffected; the SSE endpoint
URL does not change. The prefix is internal to the server process.

## 5. Testing, Verification & Rollout

### Regression test — pytest offline

```python
# tests/services/test_watch_party_sse_namespace.py
"""GAP-0166: watch-party SSE must not bleed into broadcast-session SSE."""
import asyncio
import pytest
from app.services.broadcast_sse import (
    broadcast_sse_subscribe,
    broadcast_sse_publish,
    broadcast_sse_unsubscribe,
)
from app.services.watch_party_sse import (
    wp_sse_subscribe,
    wp_sse_publish,
    wp_sse_unsubscribe,
)


def test_namespaces_do_not_bleed():
    """
    Subscribing to the same logical ID via broadcast vs watch-party must
    produce two distinct queues that do not receive each other's events.
    Fails before fix (both queues share the same slot) — the broadcast
    queue receives the watch-party event.
    Passes after fix (prefix isolates them).
    """
    SHARED_ID = "test_id_123"

    broadcast_q = broadcast_sse_subscribe(SHARED_ID)
    party_q = wp_sse_subscribe(SHARED_ID)

    # Publish to the watch-party namespace only
    wp_sse_publish(SHARED_ID, {"_type": "participant_joined", "user_sub": "u1"})

    # The watch-party queue must receive the event
    assert not party_q.empty(), "watch-party queue should have the event"

    # The broadcast queue must NOT receive the event
    assert broadcast_q.empty(), (
        "GAP-0166: broadcast queue received a watch-party event — "
        "namespace collision confirmed"
    )

    # Cleanup
    wp_sse_unsubscribe(SHARED_ID, party_q)
    broadcast_sse_unsubscribe(SHARED_ID, broadcast_q)
```

**Fails before fix:** `broadcast_q.empty()` is `False` because both
`SHARED_ID` and `"wp:test_id_123"` were the same key, so the event landed
in both queues.  
**Passes after fix:** The prefix isolates the keys; `broadcast_q.empty()` is
`True`.

### Pytest — publish to broadcast does not appear in watch-party queue

```python
def test_broadcast_does_not_bleed_into_watch_party():
    SHARED_ID = "test_id_456"
    broadcast_q = broadcast_sse_subscribe(SHARED_ID)
    party_q = wp_sse_subscribe(SHARED_ID)

    broadcast_sse_publish(SHARED_ID, {"_type": "stream_started"})

    assert not broadcast_q.empty(), "broadcast queue should have the event"
    assert party_q.empty(), "watch-party queue must not receive broadcast events"

    wp_sse_unsubscribe(SHARED_ID, party_q)
    broadcast_sse_unsubscribe(SHARED_ID, broadcast_q)
```

### Rollback

Remove `app/services/watch_party_sse.py` and revert the two import lines in
`watch_party.py` and `watch_party.py` (router + service). No persistent
state change; rollback is instantaneous.

### Risk

**Very low.** The fix is purely additive (a new thin wrapper module) and two
import substitutions. No existing test or API contract is altered. The
`_WP_PREFIX` is an internal implementation detail invisible to clients.

### Effort

**S** — approximately 30 minutes: new `watch_party_sse.py` module (~20
lines), two import updates, two regression tests.

### Sequencing

Self-contained. Can be shipped independently. No dependency on other GAPs.
Deploy before enabling multi-worker mode, as the risk amplifies when
multiple uvicorn workers share the same ID space but have separate in-memory
dicts — though in that scenario a Redis-backed pub/sub (SECOPS-007 prod
parity) is the correct long-term solution.
