# GAP-0349: `add_catalog_item` Does Not Store `creator_user_id` on the Cart Item Record — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. No investigation doc exists.

## 1. Summary & Classification

**Bug statement.** The `add_catalog_item` function in `app/services/shoppingcart.py` (lines 366–392) fetches a catalog item from DynamoDB and copies only four fields — `sku`, `name`, `quantity`, `unit_price_cents` — into the cart item payload. It does not copy `creator_id` from the catalog item. As a result, the `creator_user_id` field is absent from every catalog-backed cart item record. When the cart is purchased, `_resolve_cart_creator` (lines 456–466) reads `creator_user_id` (or `seller_id`) from each cart item and returns `None` for any catalog-backed cart. This `None` propagates to the promo-code validation path, where `creator_user_id=None` causes the system to substitute the buyer's own `user_sub` as the creator. Any promo code scoped to a specific creator will fail validation ("not valid for this creator") for every catalog-backed cart item.

- **Severity**: HIGH — creator-scoped promo codes are completely non-functional for catalog items. This silently breaks a revenue-generating feature.
- **Source ticket**: SHOP-002 (promo/checkout integration); cross-ref SEC-024 (e-commerce price tampering)
- **Status**: Open
- **Owning area**: Shop / Cart / `app/services/shoppingcart.py`
- **Claim verdict**: CONFIRMED. Code inspection confirms that `add_catalog_item` (line 386) builds the payload with exactly four keys (`sku`, `name`, `quantity`, `unit_price_cents`) and no `creator_user_id`. The catalog item fetched at line 377 (`T.catalog.get_item(…)`) contains `creator_id` (visible at `app/routers/catalog.py:250`, where new items are written with `"creator_id": ctx["user_sub"]`). The `_resolve_cart_creator` function at line 461 reads `item.get("creator_user_id") or item.get("seller_id")` — both of which will be absent from catalog-backed cart items.
- **Related tickets**: SHOP-002, SEC-024, SECOPS-007

## 2. Current-State Investigation (root cause)

### The catalog item write path

When a creator publishes a catalog item (`POST /ui/catalog/categories/{category_id}/items`, `app/routers/catalog.py:~240`), the item is stored in `T.catalog` with:

```python
{
    "PK": f"CAT#{category_id}",
    "SK": f"ITEM#{item_id}",
    "item_id": item_id,
    "category_id": category_id,
    "creator_id": ctx["user_sub"],   # <-- set here (catalog.py:250)
    "name": body.name,
    "price_cents": body.price_cents,
    ...
}
```

The field name in the catalog record is `creator_id`.

### The cart item write path

`add_catalog_item` (shoppingcart.py:366–392):

```python
def add_catalog_item(
    user_sub: str,
    cart_id: str,
    *,
    category_id: str,
    item_id: str,
    quantity: int = 1,
) -> Dict[str, Any]:
    cart = get_cart(user_sub, cart_id)
    _require_open_cart(cart)

    resp = T.catalog.get_item(Key=_catalog_item_key(category_id, item_id))
    item = resp.get("Item")
    if not item or item.get("entity") != "item":
        raise HTTPException(status_code=404, detail="Catalog item not found")

    currency = item.get("currency", "USD")
    if cart.get("currency") and cart.get("currency") != currency:
        raise HTTPException(status_code=409, detail="Cart currency mismatch")

    payload = {
        "sku": f"catalog:{item_id}",
        "name": item.get("name", "Catalog item"),
        "quantity": quantity,
        "unit_price_cents": int(item.get("price_cents", 0)),
        # "creator_user_id" is NOT set here <-- root cause
    }
    return add_item(user_sub, cart_id, payload)
```

The payload is then passed to `add_item` (shoppingcart.py:~320), which writes it as a cart item to `T.shopping_cart`. The cart item record in DynamoDB therefore has no `creator_user_id` field.

### The promo resolution path

`_resolve_cart_creator` (lines 456–466):

```python
def _resolve_cart_creator(items: List[Dict[str, Any]]) -> Optional[str]:
    """Return the single creator_user_id if all items are from the same creator.
    Returns None if mixed or no creator info."""
    creators = set()
    for item in items:
        cid = item.get("creator_user_id") or item.get("seller_id")
        if cid:
            creators.add(cid)
    if len(creators) == 1:
        return creators.pop()
    return None
```

For a cart containing only catalog items (all missing `creator_user_id`), `creators` remains an empty set and the function returns `None`.

### Where `None` propagates

`purchase_cart` (line 469) calls `_resolve_cart_creator` at line 549 and assigns the result to `creator_id`. At line 566, `creator_id` is passed to promo-code validation as `creator_user_id=creator_id`. Inside promo validation, `None` is treated as "no creator", which means creator-scoped promo codes (those with a non-null `creator_user_id` column) will compare against `None` and reject with "not valid for this creator".

### Field name mismatch: `creator_id` vs `creator_user_id`

The catalog record stores `creator_id`; the cart item convention uses `creator_user_id`. The fix must translate between the two field names at the point of copy — not rename the catalog record field (which would require a migration and break other catalog reads).

## 3. Impact / Exploit / Blast Radius

### Broken creator-scoped promo codes (primary)

Any promo code issued by a creator that is scoped to that creator's catalog items will silently fail at checkout for every buyer. The buyer sees "promo code not valid" without any useful indication of why, even though the code is legitimate. Creator promotional campaigns (flash sales, loyalty codes, affiliate codes) are completely non-functional for catalog-backed purchases.

### Revenue loss

Creators offering discount codes to drive catalog sales will observe a 0% redemption rate for catalog items. This directly reduces platform revenue (no promo-driven purchases, potentially driving creators to competing platforms with working discount features).

### Silent failure

There is no error log, alert, or frontend indication that `creator_user_id` is missing from the cart item. The failure mode is invisible — the promo code validation runs, the check fails, and the message returned to the buyer is generic ("promo code not valid for this purchase"). Support tickets are the only signal.

### Security angle (SEC-024 cross-ref)

If promo codes are not validated against the correct creator, a buyer who obtains a creator-scoped code for creator A could potentially use it on catalog items from creator B (if creator B's items also lack `creator_user_id`). The null check in promo validation may treat `None == None` as a match depending on implementation — this needs verification in the promo validation service, but the field absence creates ambiguity.

## 4. Fix Design (code-level)

### 4a. One-line fix in `add_catalog_item`

The minimal fix is to add `"creator_user_id"` to the payload dict inside `add_catalog_item` (shoppingcart.py:386):

**Current code** (lines 386–391):

```python
    payload = {
        "sku": f"catalog:{item_id}",
        "name": item.get("name", "Catalog item"),
        "quantity": quantity,
        "unit_price_cents": int(item.get("price_cents", 0)),
    }
```

**Fixed code**:

```python
    payload = {
        "sku": f"catalog:{item_id}",
        "name": item.get("name", "Catalog item"),
        "quantity": quantity,
        "unit_price_cents": int(item.get("price_cents", 0)),
        "creator_user_id": item.get("creator_id"),   # propagate catalog creator to cart item
    }
```

The field `item.get("creator_id")` reads the `creator_id` attribute set at catalog item creation time (catalog.py:250). When stored in the cart item, it is placed under the `creator_user_id` key that `_resolve_cart_creator` and the promo validation path already expect.

If `creator_id` is absent from the catalog record (e.g., older items written before the field was standardized), `item.get("creator_id")` returns `None`, and `creator_user_id: None` in the payload is either omitted by `add_item` (which skips `None` values when building the DDB item) or written as `None`. In either case the behavior is identical to the current buggy behavior for that item — no regression.

### 4b. Verify `add_item` handles `None` gracefully

Inspect `add_item` (shoppingcart.py:~320) to confirm it does not reject `None`-valued fields or write a DynamoDB `NULL` that would break other reads. If `add_item` constructs the DDB payload by passing the dict directly to `T.shopping_cart.put_item`, DynamoDB rejects `None` values with `TypeError`. In that case, conditionally set the field:

```python
    payload = {
        "sku": f"catalog:{item_id}",
        "name": item.get("name", "Catalog item"),
        "quantity": quantity,
        "unit_price_cents": int(item.get("price_cents", 0)),
    }
    creator_id = item.get("creator_id")
    if creator_id:
        payload["creator_user_id"] = creator_id
```

This is the defensive form. It does not regress existing behavior for items without `creator_id` and populates `creator_user_id` correctly when the field is present.

### 4c. Dev/prod parity (SECOPS-007)

The fix touches `T.catalog.get_item` and `T.shopping_cart.put_item` — both map to DynamoDB Local in dev and AWS DynamoDB in prod. No mock or feature-flag divergence is needed. The catalog items in both environments contain `creator_id` (set at creation time); the fix merely propagates it.

### 4d. Existing cart items (migration consideration)

Cart items written before this fix do not have `creator_user_id`. These are open (non-purchased) carts. Options:

1. **Accept the gap**: Existing open carts for catalog items remain broken for promo code validation until the cart is closed and a new cart is created. This is acceptable because open carts are transient (typically minutes to hours in a shopping session) and this is a forward-fix.
2. **Backfill on purchase**: In `purchase_cart`, if `_resolve_cart_creator` returns `None`, fall back to re-reading `creator_id` from the catalog table for each catalog-backed item. This is a belt-and-suspenders approach for in-flight carts but adds a read per item at purchase time. Not recommended as the primary fix.

Option 1 is recommended. The window of exposure for existing open carts is narrow and the operational cost of option 2 is not justified.

### 4e. Alternatives considered

- **Store `creator_user_id` on the catalog record itself** (rename `creator_id` → `creator_user_id`): Rejected. This requires a DynamoDB migration of all existing catalog records, breaks existing code that reads `creator_id`, and provides no additional value over the one-line copy at `add_catalog_item`.
- **Fix `_resolve_cart_creator` to fall back to a catalog lookup**: Rejected. This would require `_resolve_cart_creator` to accept DynamoDB access, adding a hidden remote call inside a function that is currently pure. It also does not fix the root cause of the missing field.

## 5. Testing, Verification & Rollout

### Regression test (fails before / passes after fix)

Add to `tests/test_shoppingcart.py` (offline, moto-backed):

```python
def test_add_catalog_item_stores_creator_user_id(mock_catalog_item, mock_cart):
    """Cart item created from a catalog item must carry creator_user_id."""
    # Seed a catalog item with creator_id="seller@test.local"
    mock_catalog_item(
        category_id="cat-1", item_id="item-1",
        creator_id="seller@test.local", price_cents=1000, name="Widget"
    )
    # Add it to a cart
    cart_item = add_catalog_item(
        "buyer@test.local", "cart-1",
        category_id="cat-1", item_id="item-1", quantity=1,
    )
    assert cart_item.get("creator_user_id") == "seller@test.local"


def test_creator_scoped_promo_resolves_correctly_for_catalog_item(
    mock_catalog_item, mock_cart, mock_promo_code
):
    """A creator-scoped promo code must apply to catalog items from that creator."""
    mock_catalog_item(
        category_id="cat-1", item_id="item-1",
        creator_id="seller@test.local", price_cents=1000
    )
    mock_promo_code(
        code="SALE10", creator_user_id="seller@test.local", discount_pct=10
    )
    add_catalog_item(
        "buyer@test.local", "cart-1",
        category_id="cat-1", item_id="item-1", quantity=1,
    )
    result = purchase_cart(
        "buyer@test.local", "cart-1",
        promo_code="SALE10",
    )
    assert result["discount_applied"] is True
    assert result["discount_cents"] == 100  # 10% of 1000


def test_resolve_cart_creator_returns_none_without_creator_user_id():
    """Baseline: without fix, _resolve_cart_creator returns None for catalog items."""
    items = [{"sku": "catalog:item-1", "unit_price_cents": 1000}]
    assert _resolve_cart_creator(items) is None

def test_resolve_cart_creator_returns_creator_after_fix():
    """After fix, cart item has creator_user_id and resolver returns it."""
    items = [{"sku": "catalog:item-1", "unit_price_cents": 1000,
              "creator_user_id": "seller@test.local"}]
    assert _resolve_cart_creator(items) == "seller@test.local"
```

The first two tests fail on the current code and pass after the fix. The last two tests characterize the before/after state of `_resolve_cart_creator` for regression visibility.

### Rollout and risks

- **Effort**: S (very small) — one line of code added to `add_catalog_item`, plus tests.
- **Risk**: Minimal. The change only adds a field to the cart item payload; it does not change existing field semantics. Existing non-catalog cart items (those added via `add_item` directly) are unaffected.
- **Backward compatibility**: Cart items written before the fix continue to work (promo code validation falls through to the same `None` path as before). Only newly added catalog items benefit.
- **Sequencing**: Can be deployed at any time. No IaC or DDB schema changes required.
- **Rollback**: Remove the `creator_user_id` line. The promo failure behavior reverts to pre-fix state.
