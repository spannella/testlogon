# GAP-0317: No Dedicated VAPID Web-Push Subscribe/Unsubscribe Endpoint — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase; no prior investigation doc exists.

## 1. Summary & Classification

**Bug statement**: The backend `POST /ui/push/register` endpoint was designed for FCM-style
`{token, platform}` pairs. The frontend `PushDevices.tsx` correctly obtains a full Web Push
`PushSubscription` object from the browser and serialises it to JSON (containing `endpoint`,
`keys.p256dh`, and `keys.auth`), but then stuffs the entire JSON string into the `token` field
of `PushRegisterReq` and calls the same FCM endpoint. The backend stores this blob as a raw
string in DynamoDB. The delivery function `web_push_send()` at `app/services/push.py:142`
correctly calls `json.loads(subscription_json)` and reads `keys.p256dh` / `keys.auth`, so
delivery currently works — but it works by accident (the JSON blob is stored in the `token`
column, and delivery re-parses it). The gap ticket's claim that "web_push_send() correctly reads
keys.p256dh + keys.auth ... but the stored blob is a JSON string, not a parsed dict" is
**technically accurate** — the delivery path round-trips through `json.loads` and succeeds. The
real gap is the absence of a first-class `POST /ui/push/subscribe` endpoint with proper
structured storage and a matching `DELETE` unsubscribe path, which makes the design fragile,
untestable, and unextensible.

**Claim verdict**: PARTIALLY CONFIRMED. The delivery path does not silently fail as implied —
`web_push_send()` at line 164 explicitly calls `json.loads(subscription_json)` before reading
`p256dh`/`auth`. However, the architectural defect is real: the contract between the frontend,
the storage schema, and the delivery service is implicit rather than explicit, and the lack of a
DELETE endpoint means browser-side `pushManager.unsubscribe()` is never synchronised to the
backend.

**Severity**: HIGH  
**Source ticket**: NOTIFY-001  
**Owning area**: Push Notifications  
**Related tickets**: SECOPS-007 (dev/prod parity), PLATFORM-010 (push architecture origin).

## 2. Current-State Investigation (root cause)

### Model — `app/models.py:674`

```python
class PushRegisterReq(BaseModel):
    token: str
    platform: str
```

A single untyped `token: str` field. Web push subscriptions are structurally different from FCM
device tokens (a compact opaque string), but the model does not distinguish them.

### Router — `app/routers/push.py:32`

```python
@router.post("/push/register")
async def ui_register_push(req: Request, body: PushRegisterReq, ctx=Depends(require_ui_session)):
    if not S.push_enabled:
        raise HTTPException(400, "Push disabled")
    token = (body.token or "").strip()
    if len(token) < 20:
        raise HTTPException(400, "Bad token")
    platform = (body.platform or "").strip()[:32]
    it = upsert_push_device(ctx["user_sub"], token, platform)
    ...
```

The only validation is `len(token) < 20`. A full web-push subscription JSON (which is 300–600
characters) trivially passes this check.

### Storage — `app/services/push.py:117`

```python
def upsert_push_device(user_sub: str, token: str, platform: str) -> Dict[str, Any]:
    did = push_device_id(token)   # SHA-256 of the raw token string
    T.push_devices.put_item(Item=with_ttl({
        "user_sub": user_sub,
        "device_id": did,
        "token": token,           # raw JSON string for web; FCM opaque string for native
        "platform": platform,
        ...
    }, ttl_epoch=ttl))
```

The `device_id` is a SHA-256 hash of the full subscription JSON. For FCM this is stable. For
web-push, the `PushSubscription` object contains an `expirationTime` field that may change on
re-subscription; any change invalidates the stored `device_id`, resulting in duplicate records.

### Delivery — `app/services/push.py:292`

```python
if platform == "web" and S.web_push_enabled:
    success = web_push_send(
        tok, title, body, url=url, tag=alert_type, ...
    )
```

And inside `web_push_send` at line 164:

```python
subscription = json.loads(subscription_json)  # parses the blob
endpoint = subscription.get("endpoint", "")
keys = subscription.get("keys", {})
p256dh = keys.get("p256dh", "")
auth = keys.get("auth", "")
if not (endpoint and p256dh and auth):
    logger.warning("Web push: invalid subscription (missing fields)")
    return False
```

This confirms delivery works today — `json.loads` succeeds because the frontend stores the
serialised `PushSubscription.toJSON()` output, which always includes `endpoint`, `keys.p256dh`,
and `keys.auth`.

### Frontend — `frontend/src/pages/alerts/PushDevices.tsx:85`

```typescript
const subscriptionJson = await subscribeToPush(vapidPublicKey);
await registerPush({ token: subscriptionJson, platform: "web" });
```

`subscribeToPush` (in `frontend/src/lib/pushSetup.ts:51`) calls `registration.pushManager.subscribe()`
and returns `JSON.stringify(subscription.toJSON())`. This blob is passed as `token` with
`platform: "web"` to the generic `/ui/push/register` endpoint.

### Missing: DELETE endpoint for unsubscribe

`frontend/src/lib/pushSetup.ts:114` implements `unsubscribeFromPush()` which calls
`subscription.unsubscribe()` on the browser side, but there is no corresponding backend endpoint
that accepts the subscription's `endpoint` URL and removes the matching DynamoDB record.
`DELETE /ui/push/subscribe` does not exist. The existing `/ui/push/revoke` endpoint requires a
`device_id` (the SHA-256 hash of the token string), which the frontend would need to compute or
store separately — an undocumented requirement that is not implemented.

## 3. Impact / Exploit / Blast Radius

**Primary impact — stale subscriptions accumulate**: Without a DELETE endpoint tied to the
browser unsubscribe event, revoked subscriptions remain in DynamoDB until their 180-day TTL
expires. During that window, push delivery attempts to the stale endpoint return HTTP 410 (Gone)
from the push service. The auto-revoke in `send_push_for_alert` at line 300 partially mitigates
this (it parses the JSON and calls `revoke_push_device`), but only fires after a failed
delivery — every alert triggers one spurious outbound HTTPS call.

**Secondary impact — opaque contract**: The implicit contract that `token` for `platform=web`
contains a JSON subscription object is not enforced by the model, making it easy for a future
developer to pass a raw endpoint URL or a different format and silently break delivery.

**Security impact — subscription endpoint exposure**: A web-push `endpoint` URL is a
capability URL — possession of the URL is sufficient to send (non-VAPID-authenticated)
notifications in some push service implementations. Storing it verbatim in a `token` column
mixes it with FCM opaque tokens and may cause logging or debugging tools to inadvertently
expose it.

**Financial/availability impact**: Low — push is a non-critical notification path and delivery
already works. The risk is a slow accumulation of stale records degrading delivery performance
and increasing DynamoDB storage costs at scale.

## 4. Fix Design (code-level)

### 4.1 New Pydantic models — `app/models.py`

```python
class WebPushSubscribeReq(BaseModel):
    endpoint: str = Field(..., min_length=10, max_length=2048)
    keys_p256dh: str = Field(..., min_length=20, max_length=256)
    keys_auth: str = Field(..., min_length=10, max_length=64)
    expiration_time: Optional[int] = None   # milliseconds epoch, may be None

class WebPushUnsubscribeReq(BaseModel):
    endpoint: str = Field(..., min_length=10, max_length=2048)
```

### 4.2 New endpoints — `app/routers/push.py`

```python
@router.post("/push/subscribe")
async def ui_web_push_subscribe(
    req: Request,
    body: WebPushSubscribeReq,
    ctx=Depends(require_ui_session),
):
    """Register a browser Web Push subscription (VAPID / RFC 8030)."""
    if not S.push_enabled:
        raise HTTPException(400, "Push disabled")
    if not S.vapid_public_key:
        raise HTTPException(400, "Web push not configured")
    # Canonicalise into the same storage format used by web_push_send().
    subscription_dict = {
        "endpoint": body.endpoint,
        "keys": {"p256dh": body.keys_p256dh, "auth": body.keys_auth},
    }
    if body.expiration_time is not None:
        subscription_dict["expirationTime"] = body.expiration_time
    token = json.dumps(subscription_dict, separators=(",", ":"))
    it = upsert_push_device(ctx["user_sub"], token, "web")
    audit_event("push_web_subscribe", ctx["user_sub"], req, outcome="success")
    return it


@router.delete("/push/subscribe")
async def ui_web_push_unsubscribe(
    req: Request,
    body: WebPushUnsubscribeReq,
    ctx=Depends(require_ui_session),
):
    """Revoke a Web Push subscription by endpoint URL."""
    # Find the matching device_id by re-deriving it from the canonical JSON.
    # We query all devices for this user and match by endpoint.
    devices = list_push_devices_raw(ctx["user_sub"])
    for dev in devices:
        tok = dev.get("token", "")
        try:
            sub = json.loads(tok)
            if sub.get("endpoint") == body.endpoint:
                revoke_push_device(ctx["user_sub"], dev["device_id"])
                audit_event("push_web_unsubscribe", ctx["user_sub"], req, outcome="success")
                return {"ok": True}
        except (json.JSONDecodeError, TypeError):
            continue
    return {"ok": True}  # idempotent — not found is not an error
```

`list_push_devices_raw` is a new variant of `list_push_devices` that returns the full item
including the `token` field (the current public version strips it for safety).

### 4.3 Frontend update — `frontend/src/pages/alerts/PushDevices.tsx`

Replace the call to `registerPush({ token: subscriptionJson, platform: "web" })` with a new
API endpoint call:

```typescript
const sub = JSON.parse(subscriptionJson) as {
  endpoint: string;
  keys: { p256dh: string; auth: string };
  expirationTime?: number | null;
};
await api.post("/ui/push/subscribe", {
  endpoint: sub.endpoint,
  keys_p256dh: sub.keys.p256dh,
  keys_auth: sub.keys.auth,
  expiration_time: sub.expirationTime ?? undefined,
});
```

And on device revoke, call `DELETE /ui/push/subscribe` with the endpoint URL (retrieved from
DynamoDB via `GET /ui/push/devices` — add `endpoint` to `PushDeviceOut` for web devices).

### 4.4 Dev/Prod parity (SECOPS-007)

The `VAPID` key check (`if not S.vapid_public_key`) gates the new endpoint the same way as the
existing `GET /ui/push/vapid-key`. In dev mode `VAPID_PUBLIC_KEY` is unset by default, so the
endpoint returns 400, which is the correct behaviour (no push service is reachable from
localhost). No separate mock path is needed; the existing `/ui/push/register` can remain for
backward compatibility with native FCM clients.

### 4.5 Backward compatibility

Keep `POST /ui/push/register` for native (FCM) clients unchanged. The new
`POST /ui/push/subscribe` is web-push-only. After the frontend is updated, emit a deprecation
log warning if `POST /ui/push/register` is called with `platform=web`.

### Rollout

1. Deploy backend changes (new models + endpoints). The existing `/ui/push/register` continues
   to work, so native clients are unaffected.
2. Deploy frontend changes. Existing web-push registrations in DynamoDB (stored as JSON blobs in
   the `token` column) continue to work via `web_push_send()`'s `json.loads` path.
3. Over the following 180-day TTL window the old records expire naturally; no migration needed.

**Rollback**: Revert the frontend change. The backend endpoint is additive (no existing call
sites removed).
