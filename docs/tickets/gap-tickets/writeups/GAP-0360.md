# GAP-0360: Block/Unblock UI Absent from `PublicUserProfilePage` — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code. Source ticket: SOCIAL-004.

## 1. Summary & Classification

**Plain-English statement**: Users can block each other via the API (`POST /ui/social/block`)
and via the `BlockedUsersPage` (Settings → Blocked Users, which exposes *unblock only*).
There is no way to *initiate* a block from the `PublicUserProfilePage` (`/u/:identifier`),
which is the natural surface users expect for this action. The `BlockButton.tsx` shared
component referenced in the fix plan does not exist. The acceptance criterion "User can
block from profile page" (SOCIAL-004 AC-10) is therefore unmet.

**Claim verdict**: CONFIRMED. A complete read of
`frontend/src/pages/profile/PublicUserProfilePage.tsx` (363 lines) confirms:
- No import of `blockUser`, `unblockUser`, or `getBlockStatus` from
  `frontend/src/api/endpoints/blocking.ts`
- No `DropdownMenu` component in the file
- No `BlockButton.tsx` in `frontend/src/components/shared/` (directory listed, file absent)
- The action buttons section (lines 232–261) renders only `FollowButton`, `Message`, and
  `Add Contact`. No block option exists.

`BlockedUsersPage.tsx` (`frontend/src/pages/settings/BlockedUsersPage.tsx`) imports
`getBlockedUsers` and `unblockUser` but exposes no block initiation surface.

- **Severity**: HIGH (user safety feature non-functional from primary surface)
- **Source ticket**: SOCIAL-004
- **Status**: Open
- **Owning area**: Frontend — Profile / Social
- **Related tickets**: SOCIAL-004 (parent — also documents discovery filter gap and
  notification suppression gap), GAP-0356, GAP-0358
- **Dependencies**: Backend blocking API is fully implemented and tested
  (`POST /ui/social/block`, `POST /ui/social/unblock`, `GET /ui/social/block-status/{id}`,
  `GET /ui/social/blocked`). All blocking.ts API wrappers exist. Only frontend UI work
  is required.

## 2. Current-State Investigation (root cause)

### 2.1 Backend blocking API — fully implemented

`frontend/src/api/endpoints/blocking.ts` exports:
- `blockUser(body: { target_user_id: string; reason?: string })` → `POST /ui/social/block`
- `unblockUser(body: { target_user_id: string })` → `POST /ui/social/unblock`
- `getBlockedUsers(params?)` → `GET /ui/social/blocked`
- `getBlockStatus(targetUserId: string)` → `GET /ui/social/block-status/{targetUserId}`

The backend returns `BlockStatusResponse`:

```ts
// frontend/src/api/types.ts (inferred from BlockedUsersPage usage)
type BlockStatusResponse = {
  is_blocked_by_me: boolean;
  is_blocking_me: boolean;
};
```

All four API functions are production-ready.

### 2.2 The existing `BlockedUsersPage` — unblock-only

`frontend/src/pages/settings/BlockedUsersPage.tsx:10` imports `getBlockedUsers` and
`unblockUser` but shows only a list of already-blocked users with "Unblock" buttons. It
has no "Block a user" input or search box, and it is accessible only via
Settings → Blocked Users, not from any user profile.

### 2.3 The `PublicUserProfilePage` action button row

`PublicUserProfilePage.tsx:232–261`:

```tsx
<div className="flex flex-col gap-2 sm:flex-row sm:flex-wrap sm:items-center">
  {isAuthenticated && !isOwnProfile && (
    <FollowButton userId={pub.user_id} isFollowing={isFollowing} ... />
  )}
  <Button onClick={handleMessage} ...>Message</Button>
  <Button ... onClick={() => contactMut.mutate(pub.user_id)}>Add contact</Button>
  {!isAuthenticated && (
    <Button onClick={() => navigate("/login")}>Sign in to view more</Button>
  )}
</div>
```

The block action must be added to this section. The SOCIAL-004 ticket specifies a
`DropdownMenu` with a "Block" option next to the Follow button (a common social-product
pattern that avoids cluttering the primary action row with a destructive action).

### 2.4 Missing `BlockButton.tsx` component

`frontend/src/components/shared/` contains many reusable components (`PageHeader.tsx`,
`ErrorPage.tsx`, etc.) but no `BlockButton.tsx`. The component must be created.

### 2.5 Block status not fetched on profile load

`PublicUserProfilePage.tsx` makes no call to `getBlockStatus(pub.user_id)`. Without this,
the profile page cannot display the blocked state ("You've blocked this user") and cannot
conditionally disable the Follow / Message actions when a block is active.

## 3. Impact / Exploit / Blast Radius

**User safety**: Blocking is a user safety and harassment-prevention feature. The inability
to block from a profile page is a significant UX gap: users encountering harassment on a
profile must navigate away to Settings → Blocked Users, a non-obvious path. Mobile users in
particular will struggle to find this path.

**Functional gap**: Once blocked, the blocker cannot re-unblock from the profile page either.
All block management is confined to a settings page, which is inconsistent with industry
norms (Twitter/X, Instagram, TikTok all support block-from-profile).

**Secondary gaps** (from SOCIAL-004, not addressed in this ticket but noted):
- Discovery search does not filter blocked users (separate sub-gap)
- Notification system does not suppress alerts from blocked users (separate sub-gap)
- `/ui/social/status/{id}` returns `is_blocked_by_me` but it is never consumed on the
  profile page (sub-gap fixed by this ticket)

**Security**: This gap is not a security vulnerability. The underlying blocking API is
functional; this is solely a missing UI entry point.

## 4. Fix Design (code-level)

### 4.1 Create `frontend/src/components/shared/BlockButton.tsx`

```tsx
import { useState } from "react";
import { Ban, MoreVertical } from "lucide-react";
import { useMutation, useQuery, useQueryClient } from "@tanstack/react-query";
import { toast } from "sonner";
import {
  DropdownMenu,
  DropdownMenuContent,
  DropdownMenuItem,
  DropdownMenuTrigger,
} from "@/components/ui/dropdown-menu";
import { Button } from "@/components/ui/button";
import {
  AlertDialog,
  AlertDialogAction,
  AlertDialogCancel,
  AlertDialogContent,
  AlertDialogDescription,
  AlertDialogFooter,
  AlertDialogHeader,
  AlertDialogTitle,
} from "@/components/ui/alert-dialog";
import { blockUser, unblockUser, getBlockStatus } from "@/api/endpoints/blocking";

interface BlockButtonProps {
  targetUserId: string;
  targetDisplayName?: string;
}

export function BlockButton({ targetUserId, targetDisplayName = "this user" }: BlockButtonProps) {
  const queryClient = useQueryClient();
  const [confirmOpen, setConfirmOpen] = useState(false);

  const statusQ = useQuery({
    queryKey: ["block-status", targetUserId],
    queryFn: () => getBlockStatus(targetUserId),
    staleTime: 30_000,
  });

  const isBlocked = statusQ.data?.is_blocked_by_me ?? false;

  const blockMut = useMutation({
    mutationFn: () => blockUser({ target_user_id: targetUserId }),
    onSuccess: () => {
      toast.success(`${targetDisplayName} has been blocked`);
      queryClient.invalidateQueries({ queryKey: ["block-status", targetUserId] });
      queryClient.invalidateQueries({ queryKey: ["blocked-users"] });
    },
    onError: () => toast.error("Failed to block user"),
  });

  const unblockMut = useMutation({
    mutationFn: () => unblockUser({ target_user_id: targetUserId }),
    onSuccess: () => {
      toast.success(`${targetDisplayName} has been unblocked`);
      queryClient.invalidateQueries({ queryKey: ["block-status", targetUserId] });
      queryClient.invalidateQueries({ queryKey: ["blocked-users"] });
    },
    onError: () => toast.error("Failed to unblock user"),
  });

  if (statusQ.isLoading) return null;

  if (isBlocked) {
    return (
      <Button
        variant="outline"
        size="sm"
        className="w-full sm:w-auto text-destructive border-destructive"
        onClick={() => unblockMut.mutate()}
        disabled={unblockMut.isPending}
      >
        <Ban className="mr-2 h-4 w-4" />
        Unblock
      </Button>
    );
  }

  return (
    <>
      <DropdownMenu>
        <DropdownMenuTrigger asChild>
          <Button variant="outline" size="icon" aria-label="More actions">
            <MoreVertical className="h-4 w-4" />
          </Button>
        </DropdownMenuTrigger>
        <DropdownMenuContent align="end">
          <DropdownMenuItem
            className="text-destructive focus:text-destructive"
            onClick={() => setConfirmOpen(true)}
          >
            <Ban className="mr-2 h-4 w-4" />
            Block {targetDisplayName}
          </DropdownMenuItem>
        </DropdownMenuContent>
      </DropdownMenu>

      <AlertDialog open={confirmOpen} onOpenChange={setConfirmOpen}>
        <AlertDialogContent>
          <AlertDialogHeader>
            <AlertDialogTitle>Block {targetDisplayName}?</AlertDialogTitle>
            <AlertDialogDescription>
              Blocking this user will prevent them from messaging you or seeing your content.
              You can unblock at any time from their profile or Settings → Blocked Users.
            </AlertDialogDescription>
          </AlertDialogHeader>
          <AlertDialogFooter>
            <AlertDialogCancel>Cancel</AlertDialogCancel>
            <AlertDialogAction
              className="bg-destructive text-destructive-foreground hover:bg-destructive/90"
              onClick={() => { blockMut.mutate(); setConfirmOpen(false); }}
              disabled={blockMut.isPending}
            >
              Block
            </AlertDialogAction>
          </AlertDialogFooter>
        </AlertDialogContent>
      </AlertDialog>
    </>
  );
}
```

### 4.3 Block-state awareness on profile page

The `BlockButton` component fetches `getBlockStatus(targetUserId)` internally, so the
profile page automatically shows "Unblock" when the current viewer has already blocked the
target. Additionally, `statusQ.data?.is_blocking_me` (being blocked by the target) can be
used to show a banner in `PublicUserProfilePage`:

```tsx
const blockStatusQ = useQuery({
  queryKey: ["block-status", pub.user_id],
  queryFn: () => getBlockStatus(pub.user_id),
  enabled: isAuthenticated && !isOwnProfile,
});

// Render notice if blocked by target
{blockStatusQ.data?.is_blocking_me && (
  <p className="text-sm text-muted-foreground">
    This user has restricted who can view their profile.
  </p>
)}
```

This is optional for the initial fix but closes the SOCIAL-004 LOW sub-gap regarding
`is_blocked_by_me` / `is_blocking_me` not being surfaced on the profile page.

### 4.4 Dev/Prod parity (SECOPS-007)

All blocking API calls go through the same FastAPI backend in both dev and prod.
`/ui/social/block` and `/ui/social/unblock` use `require_ui_session` (cookie auth with
CSRF). The React Query cache key `["block-status", targetUserId]` is consistent. No mock
paths, no feature flags, no AWS-specific code involved. Dev and prod behavior are identical.

If a `blocking_enabled: bool = True` feature flag is desired (e.g., for A/B testing), add
it to `app/core/settings.py` and return 404 from block/unblock endpoints when disabled.
The frontend `BlockButton` should handle 404 gracefully by hiding the button.

### 4.5 Alternatives considered

- **Inline buttons instead of DropdownMenu**: Simpler but adds a permanent "Block" button
  to the primary action row, which dark-patterns research shows increases accidental clicks
  on destructive actions. The DropdownMenu-behind-ellipsis pattern is standard.
- **Report + Block combined dialog**: The platform may add a report feature later; the
  DropdownMenu can be extended with a "Report" option without changing the component
  contract.

### 5.4 Accessibility considerations

- The `DropdownMenuTrigger` uses `aria-label="More actions"` to communicate its purpose to
  screen readers.
- The `AlertDialog` uses `role="alertdialog"` with a descriptive title.
- The "Block" confirmation button has high-contrast destructive styling (`bg-destructive`).
- The `Ban` icon is decorative and does not need an `aria-label` (the adjacent text
  provides the accessible name).
