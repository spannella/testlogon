# GAP-0207: Billing Router Never Calls Fraud Evaluation — Remediation Write-up

> ~5 pages. Fix-oriented. Code verified against the live tree; all `file:line` citations confirmed.

## 1. Summary & Classification

**Gap**: The fraud-detection engine introduced by FIN-015 (`app/services/fraud_detection.py`) exposes `evaluate_transaction()` and `is_frozen()` for exactly this purpose, but `app/routers/billing.py` never imports or calls either function. Every payment initiation — wallet deposits, tips, content unlocks, one-time charges, balance payments — proceeds without velocity checks, risk-score gating, or freeze enforcement.

- **Severity**: HIGH — transactions from flagged, high-risk, or frozen accounts execute without restriction.
- **Source ticket**: FIN-015 (`docs/tickets/FIN-015-fraud-detection-dashboard.md`)
- **Status**: Open
- **Owning area**: Billing / Fraud & Risk
- **Verdict**: Claim CONFIRMED. `grep -n "evaluate_transaction\|is_frozen" app/routers/billing.py` returns no output. The fraud-detection service module is a complete, tested subsystem that is simply never called on the hot payment path.
- **Related tickets**: GAP-0208 (chargeback not recorded), GAP-0206 (provider gate absent), SEC-004, SECOPS-007

## 2. Current-State Investigation (root cause)

### 2.1 What the fraud service provides

`app/services/fraud_detection.py:262` defines `evaluate_transaction`:

```python
def evaluate_transaction(
    *, user_id: str, amount_cents: int, entry_type: str,
    tx_id: str = "", ip_address: Optional[str] = None, account_age_days: int = 0,
) -> Dict[str, Any]:
    """Run all fraud rules against a transaction; flag/block as needed.
    Returns {triggered_rules, risk_score, flagged, action}.
    When FRAUD_DETECTION_ENABLED is false, short-circuits to 'allow'.
    """
```

The function runs four rule checks in sequence: `velocity_check`, `large_amount_check`, `new_account_check`, `chargeback_check`. It returns an `action` string: `"allow"`, `"flag"`, or `"block"`. The `"block"` action is controlled by a second flag `S.fraud_block_enabled`; when `False`, `"block"` is downgraded to `"flag"` so that the system can be deployed in audit-only mode.

`app/services/fraud_detection.py:428` defines `is_frozen`:

```python
def is_frozen(user_id: str) -> bool:
```

Both are safe to call in dev: `S.fraud_detection_enabled` (default `False` unless `FRAUD_DETECTION_ENABLED=1`) causes `evaluate_transaction` to short-circuit to `"allow"` immediately, so all dev and CI tests that don't explicitly set the env var remain unaffected.

### 2.2 The billing charge paths — none call fraud evaluation

The four payment-initiation functions confirmed in the GAP-0206 investigation (`pay_balance` at line 946, `charge_once` at 1046, `create_checkout_session` at 1206, `wallet_deposit` at 2316) plus any tip/unlock calls routed through `app/services/billing_shared.py` have no interaction with `fraud_detection`. Importing the module in `billing.py` would be the first touch point.

A targeted search confirms the gap:

```
grep -rn "fraud_detection\|evaluate_transaction\|is_frozen" app/routers/billing.py app/routers/billing_ccbill.py
# → (no output)
```

The fraud service is only invoked from:
- `app/routers/fraud_detection.py` (the admin dashboard API — read-only queries and manual operations)
- Unit tests in `tests/`

No import of `app.services.fraud_detection` appears anywhere in the billing router module. The fraud service is entirely isolated to its own admin-facing router.

### 2.3 `is_frozen` is equally unwired

`app/services/fraud_detection.py:428` provides `is_frozen(user_id: str) -> bool`, which performs a single DynamoDB `get_item` on `pk=RISK#USER#{user_id}`, `sk=SCORE` and checks the `frozen` attribute. Admins can call `POST /v1/admin/fraud/users/{user_id}/freeze` to set this flag. However, because `is_frozen` is never called on the billing path, a manually frozen user can continue to initiate payments without restriction.

This means the freeze action is purely decorative from a payment perspective — it only affects what the admin dashboard displays and may affect future features that check frozen status, but it has no real-time financial effect.

### 2.4 Related gap: `account_age_days` not threaded through

The FIN-015 gap doc notes that `evaluate_transaction` accepts `account_age_days` but `compute_risk_score` (called inside `evaluate_transaction` at line 285) does not receive it from the caller, leaving the account-age risk component permanently at 0. `compute_risk_score` falls back to the stored SCORE row's `components.account_age` value if `account_age_days` is `None`, but since `evaluate_transaction` passes `account_age_days` through explicitly when provided by the billing caller, this fallback path is bypassed. This is a separate MED gap in FIN-015 but should be fixed at the same time as the billing integration to ensure the account-age risk component is correctly computed from the first deployment.

### 2.5 Dev vs. prod behaviour

In dev mode (`S.dev_mode=True`, `S.fraud_detection_enabled=False` by default), `evaluate_transaction` short-circuits to `{"action": "allow", ...}` immediately on line 272. No DynamoDB reads occur. The fix therefore has zero runtime overhead in the default dev configuration and does not break any existing E2E tests.

In prod, `FRAUD_DETECTION_ENABLED=1` enables the checks. `FRAUD_BLOCK_ENABLED=1` enables hard blocks; without it, violating transactions are flagged for manual review but allowed through. This two-stage flag scheme allows a safe canary rollout that collects fraud signal data without immediately blocking legitimate users.

## 3. Impact / Exploit / Blast Radius

**Velocity abuse**: A bad actor can flood `POST /ui/billing/wallet/deposit` with dozens of small deposits in rapid succession. `velocity_check` (line 101) would catch this at `>20 tx/hour` or `>$500/hour`, but is never called. The DynamoDB billing ledger accumulates entries unhindered.

**Large-amount exploit**: A compromised account can initiate a `charge_once` for any amount without triggering the `large_amount_check` (line 158, threshold $250). With no fraud gate, the check at `app/services/fraud_detection.py:158` never fires.

**Frozen account bypass**: An account manually frozen by an admin (`freeze_user` at line 435) is stored in DynamoDB with `frozen: True`. However, because `is_frozen` is never called on the billing path, a frozen user can still initiate payments. The freeze has effect only on the admin dashboard display.

**Chargeback loop**: A user who has already been flagged for multiple chargebacks (see GAP-0208) is not blocked from further transactions. The `chargeback_check` in `evaluate_transaction` would catch them, but it is never called.

**Blast radius**: Every user on the platform. Financial exposure scales with the platform's transaction volume.

## 4. Fix Design (code-level)

### 4.1 Import the fraud service

```python
# app/routers/billing.py  — add to imports
from app.services import fraud_detection as fd
```

### 4.2 Helper: evaluate and gate

```python
# app/routers/billing.py  — add near top of file after imports
def _fraud_gate(
    user_id: str,
    amount_cents: int,
    entry_type: str,
    tx_id: str = "",
    req: Request = None,
) -> None:
    """Run fraud evaluation; raise 403 on block, log on flag."""
    # Freeze check always runs (synchronous DDB read, fast)
    if fd.is_frozen(user_id):
        logger.warning("fraud_gate_frozen", extra={"user_id": user_id})
        raise HTTPException(
            status_code=403,
            detail="Account is frozen. Contact support.",
        )

    # Fraud evaluation: short-circuits to 'allow' when FRAUD_DETECTION_ENABLED=0
    ip = req.client.host if req and req.client else None
    result = fd.evaluate_transaction(
        user_id=user_id,
        amount_cents=amount_cents,
        entry_type=entry_type,
        tx_id=tx_id,
        ip_address=ip,
    )
    action = result.get("action", "allow")
    if action == "block":
        logger.warning(
            "fraud_gate_blocked",
            extra={
                "user_id": user_id,
                "amount_cents": amount_cents,
                "triggered_rules": result.get("triggered_rules"),
                "risk_score": result.get("risk_score"),
            },
        )
        raise HTTPException(
            status_code=403,
            detail="Transaction blocked by fraud prevention. Contact support.",
        )
    if action == "flag":
        logger.info(
            "fraud_gate_flagged",
            extra={
                "user_id": user_id,
                "amount_cents": amount_cents,
                "triggered_rules": result.get("triggered_rules"),
                "risk_score": result.get("risk_score"),
            },
        )
        # Continue — flagged transactions are allowed but queued for review
```

### 4.3 Wire into each charge function

```python
# pay_balance (line ~948)
    user_id, admin_tags = _billing_write_user_context(ctx, user_sub, actor)
    _fraud_gate(user_id, amount, "credit", req=req)        # ADD after resolving amount

# charge_once (line ~1048)
    user_id, admin_tags = _billing_write_user_context(ctx, user_sub, actor)
    _fraud_gate(user_id, int(body.amount_cents), "credit", req=req)  # ADD

# wallet_deposit (line ~2318)
    user_id, admin_tags = _billing_write_user_context(ctx, user_sub, actor)
    _fraud_gate(user_id, int(body.amount_cents), "credit", req=req)  # ADD
```

`create_checkout_session` is a redirect flow; fraud eval should run but a `"flag"` result should not block (since the final charge occurs asynchronously via webhook). For that endpoint, run evaluation in observe-only mode by not raising on `"block"` but logging with high severity.

### 4.4 Fix the `account_age_days` threading gap (FIN-015 MED)

At the same time, thread `account_age_days` through from the caller. Billing already has access to `get_profile` which includes `created_at`. A helper:

```python
def _account_age_days(user_id: str) -> int:
    prof = get_profile(user_id) or {}
    created = prof.get("created_at", 0)
    if not created:
        return 0
    return max(0, (now_ts() - int(created)) // 86400)
```

Pass `account_age_days=_account_age_days(user_id)` to `_fraud_gate` → `evaluate_transaction`.

### 4.5 Dev/Prod parity (SECOPS-007)

`S.fraud_detection_enabled` (from env `FRAUD_DETECTION_ENABLED`, default `False`) acts as the master switch. When `False`, `evaluate_transaction` returns `{"action": "allow"}` on the first line — no DDB reads, no latency impact. Dev and CI are unaffected by default.

`S.fraud_block_enabled` (from env `FRAUD_BLOCK_ENABLED`, default `False`) controls whether `"block"` actions raise 403 or downgrade to `"flag"`. This allows a production canary where blocking is disabled while observability data is collected.

Both flags are already defined in `app/core/settings.py`. No new env vars are needed.

### 5.3 Observability and metrics

- `_fraud_gate` logs `fraud_gate_frozen` at WARNING and `fraud_gate_blocked` at WARNING.
- `fraud_gate_flagged` logged at INFO to track observe-mode signals.
- `evaluate_transaction` already logs `fraud_evaluation` at INFO with triggered rules and action.
- Add a Prometheus counter `fraud_gate_blocks_total{provider, reason}` incremented on each 403 to enable alerting on fraud block rate.

### 5.4 Rollout sequencing

- **Phase 1** (observe): Deploy with `FRAUD_DETECTION_ENABLED=1`, `FRAUD_BLOCK_ENABLED=0`. All charges proceed as normal; fraud flags are written to the review queue. Monitor flag queue daily; measure false-positive rate (legitimate transactions that would have been blocked). Target: false-positive rate below 0.1% of transaction volume.
- **Phase 2** (enforce): After a 7-day soak with acceptable false-positive rate, set `FRAUD_BLOCK_ENABLED=1`. The action downgrade logic in `evaluate_transaction` (line 297) ensures a clean transition: only transactions with score ≥ 90 or three or more triggered rules are hard-blocked, giving a natural safety margin.
- **Phase 3** (tune): Adjust thresholds via `POST /v1/admin/fraud/config` (using `FraudConfigUpdate` model). Velocity limit (`velocity_max_tx_per_hour`, default 20) and large-amount threshold (`large_tx_threshold`, default $250) are the most likely candidates for tuning based on platform usage patterns.
- **Effort**: M (1–2 days including testing and canary monitoring).
- **Rollback**: Set `FRAUD_DETECTION_ENABLED=0` to restore prior behaviour instantly; no schema changes needed. The `RISK#USER#*` rows written to `fraud_cases` during the canary are benign and can be left or pruned.
- **Dependency**: This fix should ship alongside or after GAP-0208 (chargeback recording from Stripe webhook), since `chargeback_check` in `evaluate_transaction` reads the `chargeback_count` that GAP-0208 populates. Without GAP-0208, the chargeback rule fires only on manually recorded chargebacks.
