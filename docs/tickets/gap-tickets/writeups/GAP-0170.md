# GAP-0170: `tenant_pk()` helper defined but never called — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement.** ENTERPRISE-001 introduced multi-tenancy infrastructure
including a `tenant_pk()` helper (`app/core/tenant.py:31-42`) that is
intended to prefix every DynamoDB partition key with `TENANT#<tid>#` when
`multi_tenancy_enabled` is `True`. However, `tenant_pk()` is defined in
`app/core/tenant.py` but is **never imported or called by any service file**.
All 476 service-layer files continue to construct PKs using bare f-strings
such as `f"USER#{user_sub}"`, `f"CONV#{conv_id}"`, `f"SESSION#{session_id}"`,
and similar patterns — 363 such constructions were found across 75 service
files. When `MULTI_TENANCY_ENABLED=1`, the middleware sets a tenant context
variable, but because no service reads it via `tenant_pk()`, all DynamoDB
reads and writes use bare keys — data isolation across tenants is silently
non-functional.

**Severity:** HIGH — the primary security guarantee of the multi-tenancy
feature (tenant data isolation) is not enforced in any table at the service
layer.  
**Source ticket:** ENTERPRISE-001  
**Status:** Open  
**Owning area:** `app/core/tenant.py`, all service files in `app/services/`  
**Effort:** L

**Verdict from code investigation:** Claim confirmed and strengthened. The
GAP ticket states "zero service files import or call" `tenant_pk()`. A
codebase-wide grep for `tenant_pk(` in `app/` returns exactly one result:
the function definition at `app/core/tenant.py:31`. No caller exists
anywhere in the service or router layers. The `tenant_pk_for()` function
referenced in the GAP ticket description does not exist in `tenant.py` —
only `tenant_pk()` is defined there. The claim is otherwise accurate.

**Correction note:** The GAP ticket refers to both `tenant_pk()` and
`tenant_pk_for()`. Only `tenant_pk()` exists in `app/core/tenant.py`;
`tenant_pk_for()` is not defined and was not found in any file. The
substance of the gap is unchanged.

**Related tickets:** ENTERPRISE-001, SECOPS-007.

## 2. Current-State Investigation (root cause)

### `tenant_pk()` — defined, never called

`app/core/tenant.py:31-42`:

```python
def tenant_pk(entity_prefix: str, entity_id: str) -> str:
    """Build a partition key, optionally scoped to the current tenant.

    When ``multi_tenancy_enabled`` is ``True``:
        ``TENANT#<tid>#<prefix>#<id>``
    Otherwise:
        ``<prefix>#<id>``
    """
    if S.multi_tenancy_enabled:
        tid = get_current_tenant()
        return f"TENANT#{tid}#{entity_prefix}#{entity_id}"
    return f"{entity_prefix}#{entity_id}"
```

A codebase-wide search for callers:

```bash
grep -rn "tenant_pk(" app/ --include="*.py" | grep -v "__pycache__" | grep -v "def tenant_pk"
```

Returns **zero results**. The function exists in isolation.

### `tenant_pk_for()` — does not exist

The GAP ticket mentions `tenant_pk_for()` as a companion helper. It is not
present in `app/core/tenant.py`, which contains only `tenant_pk()`,
`set_current_tenant()`, `get_current_tenant()`, `TenantSettings`,
`set_tenant_settings()`, and `get_tenant_settings()`.

### Middleware sets context — services never read it

`app/middleware/tenant.py` imports `set_current_tenant` and calls it during
request processing to set the tenant context variable for each request.
This means `get_current_tenant()` inside `tenant_pk()` would return the
correct tenant ID if called — but no service calls `tenant_pk()`, so the
context is set and then immediately forgotten.

### Scale of bare PK construction

A grep across all service files:

```bash
grep -rn 'f"USER#\|f"CONV#\|f"SESSION#\|f"MSG#\|f"PM#\|f"BILLING\|f"TICKET#\|f"POST#\|f"SUBS#\|f"FEED#' \
    app/services/ | wc -l
```

Returns **363 lines** across **75 service files** (plus additional
constructions using other entity prefixes not counted here). Every one of
these constructions bypasses `tenant_pk()` and produces a non-tenant-scoped
key regardless of the `multi_tenancy_enabled` flag.

### Pattern examples (representative samples)

`app/services/shoppingcart.py:31`:
```python

    return f"USER#{user_sub}"
```

`app/services/broadcast_tip_store.py:68`:
```python
billing_pk = f"USER#{user_id}"
```

`app/services/scheduled_actions.py:35`:
```python
return f"USER#{user_sub}"
```

`app/services/shoppingcart.py`, `app/services/discovery.py`,
`app/services/ad_serving.py`, and 71 other service files all use the same
pattern.

### `multi_tenancy_enabled` setting

`app/core/settings.py:1974`:

```python
multi_tenancy_enabled: bool = os.environ.get("MULTI_TENANCY_ENABLED", "0") not in ("0", "false", "False")
```

Defaults to `False`. Any deployment where `MULTI_TENANCY_ENABLED=1` (i.e.,
any enterprise customer using the multi-tenancy feature) will trigger the
tenant middleware but receive no actual data isolation.

## 3. Impact / Exploit / Blast Radius

**Who is affected:** Any enterprise deployment with `MULTI_TENANCY_ENABLED=1`
and more than one tenant.

**Complete tenant data isolation failure.** Tenant A's DynamoDB items have
keys `USER#alice_sub`, `CONV#conv_123`, etc. Tenant B's items have the
same key format (different user/entity IDs but same schema). Any query on
`USER#alice_sub` by tenant A is also a valid query for tenant B's user if
their user IDs happen to match (e.g., both tenants use the same Cognito
user pool, or share an email address). More importantly, the isolation
model guarantees that `TENANT#A#USER#alice` can never be returned to a
tenant B query for `TENANT#B#USER#alice` — but since `tenant_pk()` is
never called, both tenants use `USER#alice` as the key, so the data is
the same record.

**Cross-tenant data leakage.** A user authenticated as a member of Tenant
A who queries `/ui/messages/conversations` will receive conversations from
the shared `CONV#` key space — which includes conversations belonging to
Tenant B users with the same conversation IDs. In practice, different tenants
generate different conversation IDs (UUID-based), so cross-tenant item
overlap is rare by accident. But the architecture provides no barrier: the
isolation guarantee is entirely absent.

**Privilege escalation.** If `MULTI_TENANCY_ENABLED=1` and two tenants
share a Cognito user pool, a user in Tenant A with sub `user_123` can read
and modify DynamoDB records for a user in Tenant B with the same sub, because
both resolve to `USER#user_123` without tenant scoping.

**Compliance exposure.** GDPR Article 25 (data protection by design) and
SOC 2 Type II require tenant isolation for SaaS platforms. An enterprise
customer's audit would fail on this control. This is a blocking issue for
enterprise sales, not just a feature gap.

**Blast radius:** All DynamoDB tables. All service-layer functions. The
fix scope is L (large) precisely because it touches 75 service files.

## 4. Fix Design (code-level)

This is a large, systematic migration. The fix must be rolled out in phases
to avoid breaking the single-tenant (default) deployment while incrementally
enabling tenant isolation.

### Phase 1 — Add `tenant_pk_for()` convenience wrapper and lint rule

Add a secondary helper to `app/core/tenant.py` for the common pattern where
the caller already has a fully assembled bare key:

```python
def tenant_pk_for(bare_key: str) -> str:
    """Scope an already-assembled bare key to the current tenant.

    Example:
        bare = f"USER#{user_sub}"     # "USER#abc"
        scoped = tenant_pk_for(bare)  # "TENANT#tid#USER#abc" if enabled
    """
    if S.multi_tenancy_enabled:
        tid = get_current_tenant()
        return f"TENANT#{tid}#{bare_key}"
    return bare_key
```

This allows incremental migration: existing `f"USER#{user_sub}"` expressions
can be wrapped as `tenant_pk_for(f"USER#{user_sub}")` without restructuring
the call site.

### Phase 2 — Migrate high-risk service files first

Priority order (by access sensitivity):

1. **`app/services/billing.py`** — payment methods, wallets, ledger
2. **`app/services/messaging.py`** — conversations, messages
3. **`app/services/account.py`** — user profiles
4. **`app/services/auth/sessions.py`** — session tokens
5. All remaining 71 service files in alphabetical order

For each helper function that constructs a bare PK:

```python
# Before:
def _user_pk(user_sub: str) -> str:
    return f"USER#{user_sub}"

# After:
from app.core.tenant import tenant_pk_for

def _user_pk(user_sub: str) -> str:
    return tenant_pk_for(f"USER#{user_sub}")
```

### Phase 3 — Lint/CI guard to prevent regressions

Add a `pre-commit` hook or CI `grep` check that blocks raw PK construction
in service files:

```bash
# scripts/check_bare_pks.sh
#!/usr/bin/env bash
# Fail if any service file constructs raw USER#, CONV#, MSG# keys
# without going through tenant_pk() or tenant_pk_for().
VIOLATIONS=$(grep -rn 'f"USER#\|f"CONV#\|f"MSG#\|f"PM#\|f"TICKET#\|f"POST#' \
    app/services/ --include="*.py" \
    | grep -v "# noqa: tenant-pk" \
    | grep -v "__pycache__")

if [ -n "$VIOLATIONS" ]; then
    echo "ERROR: Bare PK construction found. Use tenant_pk() or tenant_pk_for()."
    echo "$VIOLATIONS"
    exit 1
fi
```

Existing violations can be suppressed with a `# noqa: tenant-pk` comment
until they are migrated, providing a clear migration backlog.

### Phase 4 — DynamoDB table re-keying migration (prod)

When `MULTI_TENANCY_ENABLED` is first set to `1` in a production environment
that already has data:

1. Run a migration script that reads all items from each table and re-writes
   them with the tenant-scoped PK (`TENANT#default#USER#...`).
2. Keep `MULTI_TENANCY_ENABLED=0` during migration; cut over after all data
   is re-keyed.
3. Point-in-time recovery (DynamoDB PITR) must be enabled before the migration.

### Dev/Prod parity (SECOPS-007)

`tenant_pk()` and `tenant_pk_for()` check `S.multi_tenancy_enabled` which
reads `MULTI_TENANCY_ENABLED` env var. In dev mode (`MULTI_TENANCY_ENABLED`
not set, defaults to `0`), the functions return bare keys — identical
behaviour to today. In prod with `MULTI_TENANCY_ENABLED=1`, tenant-scoped
keys are returned. No mock path is required; the flag itself is the parity
gate. The DynamoDB Local instance (port 8001) supports arbitrarily long
key strings, so `TENANT#tid#USER#sub` keys work identically in dev.

### Backward compatibility / migration / feature flag

`MULTI_TENANCY_ENABLED` defaults to `0` (False). Until it is explicitly
set, all behaviour is identical to today — `tenant_pk_for(f"USER#{sub}")`
returns `f"USER#{sub}"`. The migration is fully backward compatible for
single-tenant deployments.

## 5. Testing, Verification & Rollout

### Regression test — pytest offline

```python
# tests/core/test_tenant_pk.py
"""GAP-0170: tenant_pk() and tenant_pk_for() must namespace keys when enabled."""
import pytest
from unittest.mock import patch
from app.core.tenant import tenant_pk, tenant_pk_for, set_current_tenant


def test_tenant_pk_disabled_returns_bare_key():
    """When multi_tenancy_enabled is False, tenant_pk returns bare key."""
    with patch("app.core.tenant.S") as mock_s:
        mock_s.multi_tenancy_enabled = False
        result = tenant_pk("USER", "alice_sub")
    assert result == "USER#alice_sub"


def test_tenant_pk_enabled_returns_scoped_key():
    """When multi_tenancy_enabled is True, tenant_pk returns scoped key."""
    with patch("app.core.tenant.S") as mock_s:
        mock_s.multi_tenancy_enabled = True
        set_current_tenant("tenant_acme")
        result = tenant_pk("USER", "alice_sub")
    assert result == "TENANT#tenant_acme#USER#alice_sub"


def test_tenant_pk_for_disabled_returns_bare_key():
    """tenant_pk_for passthrough when disabled."""
    with patch("app.core.tenant.S") as mock_s:
        mock_s.multi_tenancy_enabled = False
        result = tenant_pk_for("USER#alice_sub")
    assert result == "USER#alice_sub"


def test_tenant_pk_for_enabled_returns_scoped_key():
    """tenant_pk_for scopes when enabled."""
    with patch("app.core.tenant.S") as mock_s:
        mock_s.multi_tenancy_enabled = True
        set_current_tenant("tenant_beta")
        result = tenant_pk_for("CONV#conv_abc")
    assert result == "TENANT#tenant_beta#CONV#conv_abc"


def test_different_tenants_produce_different_keys():
    """
    Two tenants with the same entity ID must produce non-overlapping keys.
    Fails before fix: both tenants use bare USER#alice key.
    Passes after fix: distinct TENANT#X#USER#alice keys.
    """
    from app.core.tenant import set_current_tenant, tenant_pk_for
    with patch("app.core.tenant.S") as mock_s:
        mock_s.multi_tenancy_enabled = True

        set_current_tenant("tenant_a")
        key_a = tenant_pk_for("USER#alice")

        set_current_tenant("tenant_b")
        key_b = tenant_pk_for("USER#alice")

    assert key_a != key_b, (
        "GAP-0170: two tenants produce the same DynamoDB key — no isolation"
    )
    assert "tenant_a" in key_a
    assert "tenant_b" in key_b
```

**Fails before fix:** `test_different_tenants_produce_different_keys`
fails because `tenant_pk_for()` does not exist and service files use bare
f-strings that ignore tenant context entirely — `key_a == key_b == "USER#alice"`.  
**Passes after fix:** `tenant_pk_for()` exists and applies the tenant prefix;
`key_a = "TENANT#tenant_a#USER#alice"`, `key_b = "TENANT#tenant_b#USER#alice"`.

This warning will appear in logs whenever the misconfiguration is active,
alerting operators before any customer data is at risk.

### Rollback

Because `tenant_pk_for()` returns the bare key when `multi_tenancy_enabled`
is False, the rollback for any phase-2 migration is simply setting
`MULTI_TENANCY_ENABLED=0`. No data migration is needed for rollback of the
code change; the DynamoDB re-keying migration (Phase 4) is the only
irreversible step and should be preceded by a DynamoDB backup via PITR.

### Risk

**High for Phase 4 (prod data migration).** Writing new keys for all items
in all tables requires a large DynamoDB batch-write operation. Errors in
the migration script could duplicate or lose records. Mitigations:
(a) PITR backup before migration, (b) run in parallel with the old key
scheme (dual-write) for a shadow period, (c) verify row counts before
cutting over.

**Low for Phases 1–3.** Adding `tenant_pk_for()` and the lint rule are
purely additive and do not affect any existing behaviour when
`MULTI_TENANCY_ENABLED=0` (the default and the only currently deployed
configuration).

### Effort

**L** — as assessed in the GAP ticket. Breakdown:
- Phase 1 (`tenant_pk_for()` + lint script): **S** (~2 hours)
- Phase 2 (migrate 75 service files): **L** (~2–3 days, reviewable in
  batches of 10–15 files per PR)
- Phase 3 (CI enforcement): **S** (~1 hour)
- Phase 4 (prod data migration script + runbook): **M** (~1 day)

Total: approximately **4–5 engineering days**.

### Sequencing

1. Land Phase 1 first (non-breaking, adds `tenant_pk_for()` and lint
   script). All new service files written after this point use
   `tenant_pk_for()` by default.
2. Migrate service files in Phase 2 incrementally — start with the
   billing and messaging services as highest-risk areas. Each batch is
   a reviewable PR.
3. Enable Phase 3 (CI check) after the first 10 service files are
   migrated, using `# noqa: tenant-pk` to suppress the remaining
   backlog entries. The noqa count is a progress metric.
4. Phase 4 runs in a planned maintenance window when `MULTI_TENANCY_ENABLED`
   is first set to `1` in production, preceded by a PITR snapshot and
   followed by a 24-hour shadow-read verification.

Do not set `MULTI_TENANCY_ENABLED=1` in production until all 75 service
files have been migrated (Phase 2 complete), otherwise the data re-keying
migration will produce inconsistent results (some tables scoped, others
not).
