# GAP-0104: No Scheduled-Publish Background Loop — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code; `file:line` citations are live.

## 1. Summary & Classification

**Severity**: HIGH
**Source ticket**: AGENT-017
**Owning area**: Marketing Agent — content lifecycle
**Status**: Open (no fix deployed as of this write-up)

The Marketing Agent allows users to schedule content items for future publication: `schedule_content` at `app/services/agent_marketing.py:507` writes `status = "scheduled"`, `scheduled_publish_at = <unix timestamp>`, and a GSI3 entry (`GSI3PK = "USER#{user_id}#SCHEDULED"`, `GSI3SK = publish_at`). No background task is registered in `app/main.py` to periodically query this GSI and auto-promote due items to `status = "published"`. Scheduled items never auto-publish without manual operator intervention.

**Claim accuracy**: The ticket cites `app/services/agent_marketing.py:507`. Code inspection confirms `schedule_content` is at line 507 and that there is no `publish_due_scheduled_content` function anywhere in `app/services/agent_marketing.py` (verified by exhaustive grep). No marketing-related background task appears in `app/main.py` startup handlers. **Claim is confirmed and accurate.**

**Related tickets**: GAP-0050 (compute_hourly_rollup never called), GAP-0010 (agent loop not running as background task), GAP-0048 (no daily spent reset background task).

## 2. Current-State Investigation (root cause)

### 2.1 `schedule_content` at `app/services/agent_marketing.py:507`

```python
def schedule_content(*, user_id: str, content_id: str, publish_at: int) -> Optional[Dict[str, Any]]:
    item = _get_item(user_id=user_id, content_id=content_id)
    if not item:
        return None
    status = item.get("status")
    if status != "approved":
        raise PermissionError(f"Cannot schedule content with status: {status}")
    if publish_at <= now_ts():
        raise ValueError("publish_at must be in the future")
    return _set_status(
        user_id=user_id,
        content_id=content_id,
        status="scheduled",
        extra={
            "scheduled_publish_at": int(publish_at),
            "GSI3PK": f"USER#{user_id}#SCHEDULED",
            "GSI3SK": int(publish_at),
        },
    )
```

The function correctly writes the scheduling metadata and GSI keys. The GSI index structure exists (`scripts/local-ddb-init.py` at lines 139–163 for the marketing_content table shows `GSI3` with `GSI3PK`/`GSI3SK`). The issue is solely that no periodic process reads this GSI to promote due items.

## 3. Impact / Exploit / Blast Radius

### 3.1 Functional: scheduled content never auto-publishes

Every content item ever scheduled via `POST /ui/agents/marketing/content/{id}/schedule` remains permanently in `status = "scheduled"`. A user relying on scheduled social posts, blog articles, or newsletter sends will see no output even when the scheduled time passes. The silence is the worst aspect: the API returns 200, DDB is written correctly, but nothing ever happens.

### 3.2 Data accumulation

Over time, the GSI3 partition `USER#{user_id}#SCHEDULED` accumulates all scheduled items. With `marketing_agent_execute_commands = True`, a real promotion engine (posting to social platforms, triggering email sends) never fires. Budget and calendar views will show a growing backlog of "scheduled" items with past `scheduled_publish_at` timestamps.

### 3.3 Blast radius

All users who have configured the Marketing Agent and used the scheduling feature are affected. In a multi-tenant deployment this is every content creator who expected automated publishing. The impact is purely functional (no security or financial consequence), but it constitutes a contract breach: the platform promises auto-publish and fails to deliver.

## 4. Fix Design (code-level)

### 4.1 Add `publish_due_scheduled_content` to `app/services/agent_marketing.py`

Add after `publish_content` (after line 542):

```python
def publish_due_scheduled_content() -> int:
    """Scan all users' scheduled content and publish any items whose
    scheduled_publish_at is in the past.

    Uses a full-table scan over GSI2 (or a platform-level GSI that indexes
    all scheduled items regardless of user) because GSI3PK includes the
    user_id — a per-user scan would require knowing all user IDs.

    Returns the count of items promoted to 'published'.

    Design note: for large tables, this should be replaced with a GSI that
    uses a fixed partition key (e.g., GSI_PK = "SCHEDULED") so a single
    query finds all overdue items.  The current GSI3 design stores one
    partition per user which prevents a cross-user range query.
    """
    ensure_tables()
    now = now_ts()
    promoted = 0
    # Scan for all items with status=scheduled and scheduled_publish_at <= now
    # FilterExpression is applied after the full page read — acceptable for
    # the marketing_content table which is expected to be small.
    paginator_kwargs: Dict[str, Any] = {
        "FilterExpression": Attr("status").eq("scheduled") & Attr("scheduled_publish_at").lte(now),
        "ProjectionExpression": "pk, sk, #uid, content_id",
        "ExpressionAttributeNames": {"#uid": "owner_user_id"},
    }
    while True:
        resp = T.marketing_content.scan(**paginator_kwargs)
        for item in resp.get("Items", []):
            user_id = item.get("owner_user_id") or item.get("pk", "").replace("USER#", "")
            content_id = item.get("content_id", "")
            if not user_id or not content_id:
                continue
            try:
                result = publish_content(user_id=user_id, content_id=content_id)
                if result:
                    promoted += 1
                    logger.info(
                        "Auto-published scheduled content content_id=%s user=%s",
                        content_id, user_id,
                    )
            except PermissionError:
                # Status changed between scan and update — skip
                pass
            except Exception as exc:
                logger.error(
                    "Failed to auto-publish content_id=%s: %s", content_id, exc
                )
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        paginator_kwargs["ExclusiveStartKey"] = lek
    return promoted
```

### 4.2 Add a `start_marketing_publish_task` function

Add to `app/services/agent_marketing.py`:

```python
import asyncio

async def _marketing_publish_loop() -> None:
    """Background coroutine: promote due scheduled content every 30 seconds."""
    while True:
        try:
            if S.marketing_agent_execute_commands or S.dev_mode:
                count = publish_due_scheduled_content()
                if count:
                    logger.info("Scheduled-publish loop promoted %d items", count)
        except Exception as exc:
            logger.error("Scheduled-publish loop error: %s", exc)
        await asyncio.sleep(30)


def start_marketing_publish_task() -> None:
    """Register the scheduled-publish background loop at app startup."""
    try:
        loop = asyncio.get_event_loop()
    except RuntimeError:
        loop = asyncio.new_event_loop()
        asyncio.set_event_loop(loop)
    loop.create_task(_marketing_publish_loop())
    logger.info("Marketing scheduled-publish background task started")
```

| Aspect | Dev | Prod |
|--------|-----|------|
| Task registered | Yes — `start_marketing_publish_task` runs on startup | Yes — identical |
| Gate | Runs when `S.dev_mode = True` OR `S.marketing_agent_execute_commands = True` | Runs when `S.marketing_agent_execute_commands = True` |

Running the loop in dev mode (gated by `S.dev_mode`) enables E2E tests to verify auto-publish without setting the execute-commands flag.

### 4.6 Alternatives considered

- **AWS EventBridge Scheduler / Lambda**: decouples the publish loop from the FastAPI process; correct long-term architecture. Rejected for this fix because it requires infrastructure changes (Lambda, EventBridge rule, IAM role) and the pattern is inconsistent with the other background loops in main.py (broadcast scheduler, scheduled messages, etc.) which all run as asyncio tasks.
- **Unified Scheduler** (`app/services/unified_scheduler.py`, already registered): suitable long-term home for the marketing publish task. For the minimum fix, a standalone task is simpler and avoids touching the unified scheduler's job registry.
- **Per-user cron trigger from the API**: requires the client to call a "check due" endpoint; doesn't scale and is not automatic.

### 5.4 Rollout and risks

- **Effort**: S (small) — one new function, one startup registration, one import line in main.py.
- **Backward compatibility**: existing scheduled items with past `scheduled_publish_at` will be promoted on the first loop run after deploy. This is the desired behaviour.
- **Rollback**: remove the `add_event_handler` call. In-flight promotions are idempotent (publish_content is a status transition — running it twice on an already-published item raises `PermissionError` which is caught).
- **Risk**: The scan-based approach is `O(table_size)`. For tables with millions of items, this is expensive. Mitigation: add a platform-level `SCHEDULED` GSI (fixed partition key) before table size exceeds ~10k items.
- **Sequencing**: this fix is self-contained. Ship it before enabling `MARKETING_AGENT_EXECUTE_COMMANDS=1`.
