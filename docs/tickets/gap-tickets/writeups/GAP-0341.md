# GAP-0341: Cognito User Not Disabled/Deleted on Account Deletion — Remediation Write-up

## 1. Summary & Classification

**Gap**: When a user's GDPR/privacy deletion request is fully processed by
`process_deletion` in `app/services/gdpr_service.py`, every DynamoDB record
belonging to that user (sessions, MFA devices, billing, profile, addresses, etc.)
is purged, but the corresponding Cognito identity is never disabled or deleted.
This means a deleted user can still present a valid Cognito JWT and authenticate
against any endpoint that accepts `Authorization: Bearer <token>`.

- **Severity**: HIGH
- **Source ticket**: PRIVACY-001 (also cross-referenced by SEC-018 — token revocation does not propagate)
- **Owning area**: Identity / Privacy / Backend
- **Status**: Open — no Cognito call is present anywhere in `process_deletion`

**Claim accuracy**: Confirmed. Reading `app/services/gdpr_service.py:672–827` shows
no Cognito API call. The `app/services/cognito.py` module exports
`cognito_admin_confirm_sign_up` and wraps `cognito_client()` but has no
`admin_disable_user` or `admin_delete_user` helper.

**One-line impact**: Deleted users retain live Cognito credentials and can re-authenticate
indefinitely, defeating the entire point of account deletion under GDPR/CCPA.

**Related tickets**: SEC-018 (token revocation), PRIVACY-001

## 2. Current-State Investigation (Root Cause)

`process_deletion` is the sole execution path for GDPR account deletions. It is called
from the approved-request background handler after a grace period. The function spans
`app/services/gdpr_service.py:672–827` and executes ten numbered steps:

```
Step 1  – Anonymize / delete billing records
Step 2  – delete_user_data (sessions, MFA, API keys)
Step 3  – Delete profile row
Step 4  – Delete addresses
Step 5  – Delete contacts
Step 6  – Delete calendar events
Step 7  – Delete subscriptions
Step 8  – Delete account_state
Step 9  – Delete tickets
Step 10 – Delete video metadata
```

After all ten steps the request record is marked `"completed"` at line 803 and an alert
is written at line 817. There is no Step 11 for Cognito.

The `_cognito_available()` guard that correctly gates dev vs. prod Cognito paths lives
in `app/routers/register.py:54–57`:

```python
def _cognito_available() -> bool:
    if S.dev_mode:
        return False   # Use direct DDB registration path in dev mode
    return bool(S.cognito_app_client_id)
```

This function is not imported by `gdpr_service.py`. The same pattern is used for all
other Cognito-guarded paths (registration, password reset, etc.) but was never replicated
for deletion.

`app/services/cognito.py` provides a thin wrapper around `app/core/aws_clients.cognito_client()`
and already calls `admin_confirm_sign_up` at line 122. Adding `admin_disable_user` /
`admin_delete_user` wrappers to `app/services/cognito.py` follows the exact same pattern.

**Dev behaviour**: In dev mode (`S.dev_mode = True`) `_cognito_available()` returns
`False`, so the guard must short-circuit safely. DynamoDB sessions are deleted by
`delete_user_data` (Step 2), which revokes cookie-based auth in dev; only Cognito JWT
auth remains broken.

**Prod behaviour**: `COGNITO_USER_POOL_ID` is set and Cognito JWTs are verified via
JWKS. After DDB deletion the profile row is gone and `require_bearer_token` will 404 on
any resource lookup, but the token itself remains valid. Any endpoint that skips the
profile lookup (e.g. raw identity checks) remains open. More critically, the user can
obtain new tokens via the Cognito hosted UI or SDK directly, bypassing the application
completely.

## 3. Impact / Exploit / Blast Radius

**Authentication bypass after deletion**

1. Alice submits a deletion request.
2. Admin approves; `process_deletion` runs and wipes all DynamoDB rows.
3. Alice's Cognito password is unchanged. She calls `cognito_client.initiate_auth` (or
   uses the Cognito hosted UI) and obtains a fresh `id_token` with a 1-hour TTL.
4. Alice sends `Authorization: Bearer <id_token>` to any API endpoint that uses
   `require_bearer_token`. The JWKS signature check passes, the token sub is extracted,
   and the endpoint proceeds as if she is an authenticated user.
5. Endpoints that do not make secondary DDB lookups (e.g. low-level health or telemetry
   endpoints, messaging SSE subscription) accept the request.

**Compliance consequences**

Under GDPR Art. 17 "right to erasure", the controller must cease processing personal
data and revoke all means of access. Leaving a live Cognito identity constitutes
continued processing. Under CCPA §1798.105 the same obligation applies to California
residents. Regulatory fine exposure is material.

**Token lifetime window**

Cognito `id_token` and `access_token` default TTL is 1 hour. Without disabling the
account, an attacker who obtained tokens before deletion can use them for up to 1 hour.
After disabling (but before deleting) the user, any token refresh attempt is blocked by
Cognito. After deleting, existing short-lived tokens may still verify against the JWKS
cached public key until they expire.

**Blast radius**: All users who submit a deletion request and whose requests are approved
— the entire deleted-user cohort.

**Regulatory timeline**: Under GDPR Art. 12(3), controllers must respond to erasure
requests "without undue delay and in any event within one month". The current
implementation marks the request "completed" and notifies the user at
`gdpr_service.py:817–824`, giving the user a false assurance that their data has been
fully erased when in fact their Cognito identity remains. A supervisory authority
investigating a data subject complaint would identify the live Cognito record as a clear
breach of the erasure obligation. CCPA penalties can reach $7,500 per intentional
violation; if the live Cognito identity is later found to have been exploited, the
"intentional" bar may be met given that the gap was known.

**Interaction with SEC-018 (token revocation)**: SEC-018 notes that token revocation
does not propagate. The Cognito fix partially addresses this: disabling the user prevents
new token issuance and refresh token use. Existing access tokens with a 1-hour TTL remain
valid until expiry. A complete remediation would also call
`cognito_client().admin_user_global_sign_out(UserPoolId=..., Username=...)` before the
`admin_delete_user` call; this invalidates all currently-issued tokens for the user.
The full three-step sequence should be: `admin_disable_user` → `admin_user_global_sign_out`
→ `admin_delete_user`.

## 4. Fix Design (Code-Level)

### 4.1 Add admin helpers to `app/services/cognito.py`

```python
def cognito_admin_disable_user(username: str) -> None:
    """Disable a Cognito user, preventing token refresh and new logins."""
    client = cognito_client()
    try:
        client.admin_disable_user(
            UserPoolId=_cognito_user_pool_id(),
            Username=username,
        )
    except client.exceptions.UserNotFoundException:
        # Already deleted or never registered via Cognito — not an error
        pass


def cognito_admin_delete_user(username: str) -> None:
    """Permanently delete a Cognito user record."""
    client = cognito_client()
    try:
        client.admin_delete_user(
            UserPoolId=_cognito_user_pool_id(),
            Username=username,
        )
    except client.exceptions.UserNotFoundException:
        pass
```

Both functions follow the same pattern as `cognito_admin_confirm_sign_up`
(`app/services/cognito.py:122–132`): they call `_cognito_user_pool_id()`, catch
`UserNotFoundException`, and let other exceptions propagate.

### 4.2 Add Step 11 to `process_deletion` in `app/services/gdpr_service.py`

After line 813 (`_write_audit(request_id, user_sub, "completed", {"summary": summary})`),
add:

```python
    # Step 11: Disable and delete Cognito identity
    from app.routers.register import _cognito_available
    from app.services.cognito import (
        cognito_admin_disable_user,
        cognito_admin_delete_user,
    )
    if _cognito_available():
        # user_sub is the Cognito Username (email used at registration)
        # Retrieve email from profile snapshot stored in summary, or look up via user_sub
        try:
            email = _resolve_deletion_email(user_sub)   # see §4.3
            if email:
                cognito_admin_disable_user(email)
                cognito_admin_delete_user(email)
                summary["cognito_deleted"] = True
                _write_audit(request_id, user_sub, "cognito_deleted", {"email": email})
        except Exception as e:
            logger.warning("Cognito deletion error for %s: %s", user_sub, e)
            summary["cognito_error"] = str(e)
    else:
        summary["cognito_skipped"] = True
```

The call sequence must be: disable first (blocks token refresh immediately), then delete
(removes the record). Disabling is idempotent; deleting is final.

### 4.3 Resolving the Cognito username (email)

Cognito uses the email address as `Username`. By the time `process_deletion` reaches
Step 11, the profile row has already been deleted in Step 3. The email must be captured
before the profile is deleted. Two approaches:

**Option A (preferred — zero extra reads)**: Capture the email at the start of
`process_deletion`, before any deletion step:

```python
def process_deletion(user_sub: str, request_id: str) -> Dict[str, Any]:
    # Capture email before any deletion
    _deletion_email: Optional[str] = None
    try:
        profile = T.profile.get_item(Key={"user_sub": user_sub}).get("Item") or {}
        _deletion_email = profile.get("email")
    except Exception:
        pass
    ...
    # Step 11 uses _deletion_email
```

**Option B**: Read the `deletion_email` already stored on the request record when the
request was approved (admin approval step already has the profile).

Option A requires one additional DDB read at the start of the function; it is simple
and self-contained.

### 4.4 Dev / Prod Parity (SECOPS-007)

The `_cognito_available()` guard ensures the Cognito calls are only made when a real
Cognito pool is configured and `S.dev_mode` is `False`. In the local development stack
(where `S.dev_mode = True`), the block is skipped and `summary["cognito_skipped"] = True`
is recorded. The code path is identical in both environments; only the guard determines
whether AWS is called. No feature flag is needed beyond the existing settings.

### 4.5 Alternatives Considered

- **Only disable, never delete**: Simpler, but does not satisfy the GDPR erasure
  obligation which requires deleting the personal data record in Cognito.
- **Schedule an async job**: Introduces a race window where the deleted user can
  re-authenticate between DDB deletion and Cognito deletion. Synchronous is better.
- **Revoke active tokens via Cognito GlobalSignOut**: Would require knowing the current
  access token, which is not stored server-side. `admin_disable_user` + `admin_delete_user`
  is the correct Cognito-server-side approach; it also invalidates any refresh tokens.

## 5. Testing, Verification & Rollout

### 5.2 Manual QA Steps

1. Start the full local stack (`just up`).
2. Register a test user via `POST /ui/register/start` + confirm.
3. Submit a deletion request via `POST /ui/privacy/deletion-request`.
4. Approve via root CLI or admin endpoint.
5. Wait for background processing or trigger manually.
6. In dev mode, verify `summary["cognito_skipped"] = True` in the completed request.
7. In a prod-like environment (with `COGNITO_USER_POOL_ID` set and `DEV_MODE=0`),
   verify that after deletion `aws cognito-idp admin-get-user` returns `UserNotFoundException`.
8. Attempt to call `initiate_auth` with the old credentials — should fail with
   `NotAuthorizedException`.

### 5.3 Observability

- `_write_audit` call with action `"cognito_deleted"` provides an immutable audit entry.
- `summary["cognito_deleted"]` or `summary["cognito_error"]` is stored in the
  `deletion_summary` attribute of the request record and visible to admins.
- Add a structured log line:
  ```python
  logger.info("cognito_identity_deleted user_sub=%s", user_sub)
  ```

### 5.4 One-Time Remediation for Existing Deleted Users

Users whose accounts were deleted via `process_deletion` before this fix is deployed
still have live Cognito identities. A one-time remediation script should be run after
deployment:

1. Query all completed deletion requests from `T.data_requests` where `status =
   "completed"` and `cognito_deleted` is absent from `deletion_summary`.
2. For each request, resolve the email from the audit trail or a backup profile snapshot.
3. Call `cognito_admin_disable_user(email)` followed by `cognito_admin_delete_user(email)`.
4. Mark the request record with `cognito_remediated = True` and write an audit event.

This script should be run under a maintenance window with a root-level operator present.
If the email cannot be resolved for a given user (e.g., the profile was deleted before
the email was captured), log the `user_sub` for manual review by the security team.

### 5.5 Rollout

- **Effort**: S (Small) — approximately 40 lines of new code, no schema changes, no
  new tables.
- **Backward compat**: No migration needed. Existing completed deletion records lack the
  `cognito_deleted` flag; they should be audited manually for a one-time cleanup using
  the remediation script described in §5.4.
- **Rollback**: Remove the Step 11 block; no persistent state change on the application
  side. Cognito users already deleted cannot be recreated automatically.
- **Risk**: Low for new deletions. Mild risk of Cognito `UserNotFoundException` if the
  email changed between registration and deletion — mitigated by catching
  `UserNotFoundException` in both helper functions. If the Cognito user pool is
  unavailable (network partition, quota throttle), the exception is caught, logged, and
  stored in `summary["cognito_error"]` for retry. The deletion request itself is still
  marked `completed` so the customer receives their deletion confirmation; the Cognito
  cleanup is best-effort with a retry path.
- **Sequencing**: Implement before next privacy audit. No dependency on other GAP tickets.
  Coordinate with SEC-018 (token revocation) to ensure any outstanding Bearer tokens
  issued to the deleted user are also addressed; after Cognito deletion, refresh token
  calls will fail, but short-lived access tokens (1-hour TTL) remain valid until expiry.
