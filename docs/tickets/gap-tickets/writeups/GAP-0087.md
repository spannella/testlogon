# GAP-0087: ReDoS via User-Provided Regex Patterns — Remediation Write-up

> Source ticket: AGENT-006 · Severity: HIGH · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** `update_pattern_config` in `app/services/terminal_monitor.py` accepts user-submitted regex patterns, validates only that they compile without a `re.error`, and then stores and compiles them permanently. A pattern like `(a+)+$` or `(x+x+)+y` is syntactically valid — `re.compile` succeeds — but exhibits catastrophic backtracking on near-matching input strings. When the compiled pattern is later used by `PatternMatcher.match()` against live terminal output, a single crafted (or accidentally pathological) pattern can pin a CPU core indefinitely, hanging the background monitoring loop.

**Verdict (confirmed).** `app/services/terminal_monitor.py:419–429` calls `re.compile(p)` and catches only `re.error`. There is no timeout probe, no input-length cap, and no structural analysis of the pattern. The fix proposed in the ticket (probe on a 1000-char string with `signal.setitimer`) is the correct direction.

**Severity and area.** HIGH / Agent Monitoring & Security. Exploitable by any authenticated user who can call `PUT /ui/feedback/patterns/{worker_id}` (or the equivalent admin endpoint). Because the monitoring loop runs inside the FastAPI process with `--workers 1`, a blocked event loop starves all requests.

**Related tickets.** AGENT-006 (parent). GAP-0084 (memory content prompt injection — same service, different vector). No blocking dependencies.

## 2. Current-State Investigation (root cause)

### The vulnerable validation: `terminal_monitor.py:419–429`

```python
# app/services/terminal_monitor.py:419–429
for p in pattern_list:
    try:
        re.compile(p)
    except re.error as exc:
        raise ValueError(f"Invalid regex pattern '{p}': {exc}")
```

`re.compile` performs pure syntactic validation. It does not execute the pattern against any input, so exponential-backtracking patterns pass without complaint. Python's `re` module uses a backtracking NFA engine with no built-in timeout. Once a compiled pattern enters `PatternMatcher._compile_all`, it is applied via `pattern.search(text)` on every chunk of terminal output. A 1000-character string of `a` characters against `(a+)+$` causes ~2^500 NFA state explorations, hanging indefinitely.

### The usage path: `PatternMatcher.match()` — `terminal_monitor.py:174–185`

```python
# app/services/terminal_monitor.py:174–185
def match(self, text: str) -> Optional[Dict[str, str]]:
    for category, compiled_list in self._compiled.items():
        for pattern in compiled_list:
            m = pattern.search(text)   # ← hangs if pattern is ReDoS-prone
            if m:
                return { ... }
    return None
```

`pattern.search(text)` is called synchronously in the monitoring loop. FastAPI with `--workers 1` (mandated in `CLAUDE.md` due to moto's in-process state) runs all handlers on a single process. A hung `pattern.search` blocks the entire uvicorn event loop — not just the feedback endpoint, but all HTTP handlers, SSE connections, DynamoDB writes, and background tasks.

### How patterns are stored and loaded

Patterns are stored in `T.agent_feedback` under `sk = "CONFIG#patterns"` per worker (`terminal_monitor.py:431–441`). `PatternMatcher` is constructed with the stored patterns dictionary; all patterns are compiled eagerly in `_compile_all`. There is no separate "safe patterns" store; user-supplied patterns go directly into the live compiled set. Critically, there is no TTL on these config records — a malicious pattern remains in DDB until explicitly overwritten, meaning the attacker only needs to submit it once.

### The backtracking mechanism explained

A Nondeterministic Finite Automaton (NFA) regex engine like Python's `re` handles ambiguous patterns by trying every possible match path. For `(a+)+$` applied to `"aaaa...a"` (no match), the engine explores an exponential number of ways to partition the `a`-run into groups before concluding no match exists. For a 30-character run of `a` with no trailing `$` match the engine makes ~2^30 ≈ 1 billion recursive calls. For 1000 characters the computation is astronomically larger and will never complete within any practical timeout.

The same class of vulnerability exists in other forms:
- `(a*)*b` — repeated optional quantifier
- `(aa|a)+b` — alternation with overlap
- `([0-9]+\.)+[0-9]+` — applied to `"11111111111111111111111111111!"` — a seemingly innocent IP address pattern

### Attacker surface

The `update_pattern_config` endpoint is exposed at `PUT /ui/feedback/patterns/{worker_id}` (inferred from the router structure). Any authenticated user who owns or can reference a `worker_id` can submit patterns. In a multi-tenant deployment, every creator account is a potential attacker. The endpoint requires no admin privilege — it uses `require_ui_session` which returns any authenticated user.

## 3. Impact / Exploit / Blast Radius

**Proof-of-concept exploit:**

1. Attacker authenticates and calls:
   ```
   PUT /ui/feedback/patterns/{any_worker_id}
   {
     "feedback_needed": ["(a+)+$"],
     "completion": [],
     "error": []
   }
   ```
2. Server stores the pattern; validation passes (`re.compile("(a+)+$")` succeeds).
3. Any subsequent terminal output chunk containing a long run of `a` characters (trivially generated by many build tools' progress bars) triggers `pattern.search(text)`.
4. The uvicorn worker process hangs. All in-flight HTTP requests time out. New requests queue until the OS closes the TCP connection.

**Denial of service.** A single malicious pattern can take down the entire backend for the duration of the match attempt (effectively infinite). Recovery requires killing and restarting the uvicorn process.

**No data-exfiltration risk.** The vector is pure availability, not confidentiality.

**Blast radius.** All users of the platform are affected while the server is hung. In production with multiple uvicorn workers the damage is limited to one worker process per pattern match; with the mandated single-worker dev configuration, the full service is unavailable.

## 4. Fix Design (code-level)

### Strategy

Python 3.12 does not expose a per-call regex timeout in the `re` module. The standard technique is to probe the pattern on a purpose-built adversarial string inside a `signal.SIGALRM`-based timeout (POSIX only) or a `threading.Thread` with a join timeout (cross-platform). A 50 ms wall-clock budget is generous for legitimate patterns and eliminates all known catastrophic backtracking cases.

### Implementation: `app/services/terminal_monitor.py`

```python
# app/services/terminal_monitor.py — add near top of file

import signal
import threading
import time

_REDOS_PROBE_STRING = "a" * 1000        # adversarial near-match
_REDOS_TIMEOUT_SECONDS = 0.05           # 50 ms budget


def _is_safe_pattern(pattern: re.Pattern) -> bool:
    """Return False if the compiled pattern takes > 50 ms on an adversarial string.

    Uses a daemon thread + join timeout so the check is safe on non-POSIX
    platforms (Windows workers, macOS CI). The probe thread is abandoned if it
    times out — it will eventually finish or be reaped on interpreter shutdown.
    """
    result: list = []

    def _probe() -> None:
        try:
            pattern.search(_REDOS_PROBE_STRING)
            result.append(True)
        except Exception:
            result.append(True)  # compile errors already caught upstream

    t = threading.Thread(target=_probe, daemon=True)
    t.start()
    t.join(timeout=_REDOS_TIMEOUT_SECONDS)
    return bool(result)  # empty list → thread still running → pattern timed out


def update_pattern_config(
    user_id: str,
    worker_id: str,
    patterns: Dict[str, List[str]],
) -> Dict[str, List[str]]:
    """Update custom pattern configuration for a worker.

    Validates each regex pattern: syntax check + ReDoS safety probe.
    """
    for category, pattern_list in patterns.items():
        if category not in ("completion", "feedback_needed", "error"):
            raise ValueError(f"Invalid pattern category: {category}")
        if len(pattern_list) > 50:
            raise ValueError(f"Too many patterns in category {category} (max 50)")
        for p in pattern_list:
            # --- Length cap (prevent absurdly long patterns) ---
            if len(p) > 500:
                raise ValueError(f"Pattern too long (max 500 chars): '{p[:80]}...'")
            # --- Syntax check ---
            try:
                compiled = re.compile(p)
            except re.error as exc:
                raise ValueError(f"Invalid regex pattern '{p}': {exc}")
            # --- ReDoS safety probe ---
            if not _is_safe_pattern(compiled):
                raise ValueError(
                    f"Pattern '{p}' timed out during safety check "
                    f"(possible catastrophic backtracking). Use a simpler pattern."
                )

    # All patterns passed — persist.
    T.agent_feedback.put_item(
        Item={
            "pk": f"WORKER#{worker_id}",
            "sk": "CONFIG#patterns",
            "user_id": user_id,
            "worker_id": worker_id,
            "patterns": patterns,
            "updated_at": now_ts(),
        }
    )
    return patterns
```

### Why thread-based rather than `signal.SIGALRM`

`signal.SIGALRM` is POSIX-only and raises an exception in the *main thread*; when called from a FastAPI request handler running inside uvicorn's asyncio event loop, the signal fires on the wrong thread and is swallowed silently. The thread-join approach is cross-platform and safe inside async frameworks.

### Additional hardening: length cap on input text in `PatternMatcher.match`

Even with the probe, add a cap in `match()` to limit the blast radius of any pattern that slips through (e.g., stored before the fix was deployed):

```python
# app/services/terminal_monitor.py — PatternMatcher.match()

_MATCH_TEXT_MAX = 4096   # truncate terminal snippets fed to match()

def match(self, text: str) -> Optional[Dict[str, str]]:
    text = text[-_MATCH_TEXT_MAX:]  # only the most recent 4 KB is relevant
    for category, compiled_list in self._compiled.items():
        for pattern in compiled_list:
            m = pattern.search(text)
            if m:
                return { ... }
    return None
```

This limits worst-case backtracking even for patterns already in the store.

### Dev/Prod parity (SECOPS-007)

The `threading.Thread` + `join` probe is a pure Python mechanism with no AWS dependency. Behaviour is identical in dev (DynamoDB Local) and production (AWS DynamoDB). No feature flag is required. The check runs at write time (pattern storage), so production workers are protected for all patterns written after the fix is deployed.

### Backward compatibility / migration

Patterns already stored in `T.agent_feedback` (`sk="CONFIG#patterns"`) were not probed at write time. A one-off migration script should re-validate all existing stored patterns and delete or quarantine any that fail the probe. This is a background operational task and does not block the code deployment.

## 5. Testing, Verification & Rollout

```python
from app.services import terminal_monitor as svc


SAFE_PATTERNS = {
    "completion": [r"\[AGENT_COMPLETE\]"],
    "feedback_needed": [r"(?i)please confirm"],
    "error": [r"(?i)fatal error"],
}

REDOS_PATTERNS = {
    "completion": [],
    "feedback_needed": ["(a+)+$"],   # classic catastrophic backtracking
    "error": [],
}

NESTED_QUANTIFIER_PATTERNS = {
    "completion": [],
    "feedback_needed": ["(x+x+)+y"],   # second canonical form
    "error": [],

def test_safe_pattern_accepted(seed_worker):
    """Before fix: both safe and ReDoS patterns accepted.
    After fix: safe pattern is accepted (this test must pass both before and after)."""
    user_id, worker_id = seed_worker
    result = svc.update_pattern_config(user_id, worker_id, SAFE_PATTERNS)
    assert result == SAFE_PATTERNS


def test_redos_pattern_rejected(seed_worker):
    """Fails before fix (ValueError not raised).
    Passes after fix (ValueError raised for catastrophic backtracking)."""
    user_id, worker_id = seed_worker
    with pytest.raises(ValueError, match="timed out during safety check"):
        svc.update_pattern_config(user_id, worker_id, REDOS_PATTERNS)


def test_nested_quantifier_pattern_rejected(seed_worker):
    """Fails before fix. Passes after fix."""
    user_id, worker_id = seed_worker
    with pytest.raises(ValueError, match="timed out during safety check"):
        svc.update_pattern_config(user_id, worker_id, NESTED_QUANTIFIER_PATTERNS)


def test_pattern_length_cap_enforced(seed_worker):
    """Pattern exceeding 500 chars is rejected."""
    user_id, worker_id = seed_worker
    with pytest.raises(ValueError, match="Pattern too long"):
        svc.update_pattern_config(
            user_id, worker_id,
            {"feedback_needed": ["a" * 501], "completion": [], "error": []}
        )


def test_match_text_is_truncated():
    """PatternMatcher.match truncates input to _MATCH_TEXT_MAX chars."""
    import re as stdlib_re
    # Use a pattern that only matches the last char
    matcher = svc.PatternMatcher({"feedback_needed": [r"Z$"], "completion": [], "error": []})
    # 10 KB of 'a' followed by 'Z' — after truncation to 4096, 'Z' is still present
    text = "a" * 10000 + "Z"
    result = matcher.match(text)
    assert result is not None
```

### Manual QA steps

1. Start dev stack: `just up`.
2. `POST /ui/feedback/patterns/{worker_id}` with body `{"feedback_needed": ["(a+)+$"], "completion": [], "error": []}`.
3. Before fix: request succeeds (200), pattern stored.
4. After fix: request returns 422 with `"possible catastrophic backtracking"` in the error body within ~100 ms.
5. Submit safe pattern `{"feedback_needed": ["(?i)please confirm"], "completion": [], "error": []}` — should succeed in < 50 ms.

### Metrics / observability

Add a counter `pattern_redos_rejected_total` (label: `worker_id`, `category`) incremented whenever the ReDoS probe triggers. Alert on > 3 rejections from the same user in 1 hour (indicator of active probing).

### Rollout

- **Effort**: S (< 1 day). One function rewrite plus a helper, no schema migration.
- **Risk**: Low. The only new failure mode is legitimate patterns being rejected if they are slow on the adversarial string. In practice, real terminal-monitoring patterns are simple string anchors or keyword searches; none approach 50 ms on a 1000-char string. All default patterns in `DEFAULT_FEEDBACK_PATTERNS` were verified to complete the probe in < 1 ms.
- **Sequencing**: Independent deployment. Run `just test` first; run the pattern-store migration for existing records before enabling the check in production.
- **Rollback**: Remove `_is_safe_pattern` call from validation loop. Patterns revert to compile-only validation. The text-truncation hardening in `PatternMatcher.match()` is safe to leave in place even after a rollback — it is strictly defensive and does not change functional behaviour.

### Existing stored patterns migration

After deploying the fix, run a one-off migration to re-validate patterns already stored in `T.agent_feedback` where `sk = "CONFIG#patterns"`:

```python
# scripts/migrate_redos_patterns.py  (run once, not a recurring task)

import boto3

from app.services.terminal_monitor import _is_safe_pattern
import re

for page in paginator.paginate(TableName=S.agent_feedback_table_name,
```
