# GAP-0099: Backend Computes Source Hashes Directly from Filesystem — Remediation Write-up

> Claim accuracy note: The ticket states that `_compute_source_hash` at
> `app/services/agent_docs.py:198` "opens files via `open(path,'rb')` on the backend server."
> **This claim is INACCURATE.** Code inspection at lines 198–208 shows that `_compute_source_hash`
> does NOT perform any filesystem I/O whatsoever. It derives a deterministic, content-independent
> token purely from the path string using Python's built-in `hash()` function:
> `return f"h_{abs(hash(path)) & 0xFFFFFFFF:08x}"`. No `open()` call exists anywhere in the
> function. The docstring even explicitly states "The backend never touches the filesystem."
> The REAL gap is subtler and more serious: because the hash is path-derived (not
> content-derived), it is permanently identical for a given path regardless of what the file
> actually contains. The freshness detection system (`check_doc_freshness`) therefore can never
> detect that a file has changed — it always reports every doc as current. The ticket's
> recommended fix ("gate local hash computation on S.dev_mode; accept externally-provided
> source_hashes from agent") correctly identifies the intended production architecture and
> remains the right remedy, but the stated root-cause mechanism is wrong.

## 1. Summary & Classification

**Bug**: `_compute_source_hash` in `app/services/agent_docs.py` produces a hash token derived solely from the file's path string. Since the token is path-deterministic (not content-deterministic), it never changes between calls for the same path, regardless of what the file contains. The `check_doc_freshness` function compares the stored hash (recorded at doc-registration time) against the current hash (recomputed from the same path) — and the comparison is always equal. Stale-documentation detection is therefore permanently inoperative. In production, where the backend container and agent terminals are on separate machines, this matters even more: the backend has no access to the agent's working files, and the path-only hash silently presents every doc as "fresh" even when months of code changes have accumulated since registration.

- **Severity**: HIGH
- **Source ticket**: AGENT-014
- **Owning area**: Agent Documentation service / source freshness detection
- **Status**: Open
- **Verdict**: Partially confirmed — the symptom (hash never reflects content changes, freshness detection always returns fresh) is correct; the cited mechanism (`open()` call) does not exist in the code
- **One-line impact**: `check_doc_freshness` always returns `stale: false`; agents never regenerate docs, and operate indefinitely on stale documentation snapshots.
- **Related tickets**: GAP-0096 (architect path validation — related agent file-system concern), SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (root cause)

### The actual hash function

`app/services/agent_docs.py:198–212`:

```python
def _compute_source_hash(path: str) -> str:
    """Compute a stable hash token for a source file.

    Hashes are normally produced by the agent in its terminal session (real git
    blob hashes). The backend never touches the filesystem; in mock/dev mode it
    derives a deterministic content-independent token from the path so freshness
    detection is exercisable without git. When the same path is registered and
    later re-verified with no intervening update call, the token is identical →
    the doc is considered fresh.
    """
    return f"h_{abs(hash(path)) & 0xFFFFFFFF:08x}"


def compute_source_hashes(paths: List[str]) -> Dict[str, str]:
    return {p: _compute_source_hash(p) for p in (paths or []) if p}
```

There is no `open()` call. The function uses Python's built-in `hash()` on the path string. The docstring is self-aware: it acknowledges "derives a deterministic content-independent token" and "the backend never touches the filesystem." The function was deliberately written this way for mock/dev testability. The gap is that this mock implementation is the only implementation — there is no production code path that accepts real content hashes from the agent.

### How freshness detection consumes hashes

`app/services/agent_docs.py:420–454` (`check_doc_freshness`):

```python
# lines 424–449 (condensed):
def check_doc_freshness(*, user_id: str, doc_id: str) -> Dict[str, Any]:
    ...
    refs = _loads_list(item.get("source_refs"))
    ...
    stored = _loads_map(item.get("source_hashes"))  # line 448: stored at registration time
    current = compute_source_hashes(refs)            # line 449: recomputed now
    stale = stored != current
```

`compute_source_hashes` calls `_compute_source_hash(path)` for each path in `refs`. Since the hash function is deterministic and path-only, `stored` and `current` are always identical for the same set of paths. `stale` is always `False`. The function additionally returns a `changed_files` list (the diff between stored and current) — this list is always empty.

### Doc registration path

`app/services/agent_docs.py:295–308` (`register_doc`):

```python
source_hashes = compute_source_hashes(source_refs)  # line 301
...
"source_hashes": json.dumps(source_hashes),          # line 308
```

At registration, path-derived tokens such as `{"app/models.py": "h_3a2b1c0d"}` are stored. The freshness check recomputes the same tokens. No content ever flows through any layer.

The update path (`update_doc_source`, line ~350) follows the same pattern — it calls `compute_source_hashes` to update stored hashes, but the new values are identical to the old values for any unchanged path.

### The intended production architecture

The docstring's phrase "Hashes are normally produced by the agent in its terminal session (real git blob hashes)" describes the correct design. In production, the agent runs co-located with the source files (in a worker terminal session with a git checkout). It should compute `git hash-object <file>` for each source ref and supply the resulting SHA-1 blob hashes to the backend via the API payload. The backend stores them and compares them at freshness-check time — but never accesses the filesystem itself. This production path does not exist today: no API parameter accepts externally-supplied hashes.

### Dev vs prod divergence (SECOPS-007)

In dev, backend and agent terminal share the same host. It would be technically possible to call `open(path, "rb")` in dev mode — but the code deliberately does not, for good separation-of-concerns reasons. In production, the backend is a FastAPI container with no access to the developer's working tree. The current behaviour is identically broken in both environments (always fresh). The dev behaviour is "predictably wrong and harmless"; the prod behaviour is "wrong and silently misleading."

### Related: `validate_path` security

The `validate_path` helper at `agent_docs.py:174–185` correctly rejects absolute paths. Even if a `source_hash` computation were to read files in dev mode, the path validation guard (covered by GAP-0096) must be applied first. The fix in this ticket adds a new `source_hashes` API parameter; that parameter's keys should also be validated with `validate_path`.

## 3. Impact / Exploit / Blast Radius

**Functional impact — always-fresh documentation**:

Every call to `GET /ui/agent/docs/{doc_id}/freshness` returns `{"stale": false}`. The `changed_files` field is always `[]`. Agents that query freshness to decide whether to regenerate documentation will never regenerate it, even when months of code changes have accumulated since the doc was registered.

**Worst case**:

1. An agent registers a doc for `app/services/billing.py` at version V1.
2. `billing.py` undergoes a significant refactor in V2 — new endpoint signatures, new DynamoDB table schemas, changed fee calculation logic.
3. An agent checks freshness → `stale: false` → uses the V1 doc as authoritative context.
4. The agent generates new code based on V1 understanding of the billing service. The generated code calls removed functions, uses old table names, and assumes obsolete fee structures.
5. The incorrect code is committed and causes billing errors in production.

**Compliance impact**: Regulated environments may require that documentation used in compliance workflows accurately reflects current code. A system that never flags stale docs undermines audit trails.

**No direct security exploit**: The hash function does not perform arbitrary file reads or expose server credentials. However, a malicious user cannot exploit this gap to gain privileges. The risk is entirely integrity and correctness.

**Blast radius**: Affects all agents using the doc freshness system. The feature is entirely decorative until this gap is fixed — it provides false assurance of doc currency.

## 4. Fix Design (code-level)

### Two-phase approach

**Phase 1 (immediate, no env-gating needed)**: Accept externally-provided hashes from the agent via the API payload. The agent computes `git hash-object` values in its terminal session and passes them to the backend. The backend stores and compares them. No filesystem access on the backend side.

**Phase 2 (dev convenience, SECOPS-007 gated)**: In `S.dev_mode`, compute real file content hashes from the local filesystem so that freshness detection works correctly in the development environment without requiring an agent terminal session.

### Phase 1: agent-supplied hashes

**In `app/models.py`** — add `source_hashes` field to the doc-registration and doc-update request models:

```python
class RegisterDocIn(BaseModel):
    doc_id: Optional[str] = None
    title: str
    doc_type: str
    source_refs: List[str] = []
    source_hashes: Optional[Dict[str, str]] = None
    # ^ keys: relative paths (validated by validate_path); values: git blob SHA-1 or similar
    content_summary: Optional[str] = None
    tags: List[str] = []


class UpdateDocSourceIn(BaseModel):
    source_refs: List[str]
    source_hashes: Optional[Dict[str, str]] = None
```

**In `app/services/agent_docs.py`** — update `register_doc` to accept and prefer externally-supplied hashes:

```python
def register_doc(
    *,
    user_id: str,
    agent_id: str,
    worker_id: str = "",
    title: str,
    doc_type: str,
    source_refs: Optional[List[str]] = None,
    source_hashes: Optional[Dict[str, str]] = None,   # NEW
    content_summary: str = "",
    tags: Optional[List[str]] = None,
    doc_id: Optional[str] = None,
) -> Dict[str, Any]:
    ...
    # Validate any agent-supplied hash keys for path safety
    if source_hashes:
        bad_paths = [p for p in source_hashes if not validate_path(p)]

        hashes = {p: str(h) for p, h in source_hashes.items() if p}
    else:
        # Fall back to path-derived stubs (exercisable in tests; always-fresh in prod)
        hashes = compute_source_hashes(source_refs)
    ...

```

**Update `check_doc_freshness`** to accept caller-supplied current hashes:

```python
def check_doc_freshness(
    *,
    user_id: str,
    doc_id: str,
    current_hashes: Optional[Dict[str, str]] = None,  # agent-supplied at check time

    ...
    stored = _loads_map(item.get("source_hashes"))
    if current_hashes:

        changed = [p for p, h in current_hashes.items() if stored.get(p) != h]
    else:

        # Log a warning so engineers know the check is non-functional
        logger.warning("check_doc_freshness: no current_hashes supplied; skipping real comparison doc_id=%s", doc_id)
        stale = False
        changed = []
    ...
```

### Phase 2: dev-mode filesystem hash (SECOPS-007 gated)

```python
def _compute_source_hash(path: str) -> str:
    """Compute a stable hash for a source file path.

    In dev mode: reads the actual file content and returns a SHA-256 prefix,
    enabling real freshness detection without an agent terminal.
    In production: returns a path-derived stub; real hashes must be supplied
    by the agent via the API source_hashes parameter.
    """
    if S.dev_mode:
        try:
            import hashlib
            with open(path, "rb") as fh:
                return "d_" + hashlib.sha256(fh.read()).hexdigest()[:16]
        except OSError:
            pass  # File inaccessible; fall back to path-derived stub
    # Prod or fallback: path-derived stub (h_ prefix marks it as non-content hash)
    return f"h_{abs(hash(path)) & 0xFFFFFFFF:08x}"
```

The `h_` vs `d_` prefix scheme allows `check_doc_freshness` to detect when stored hashes are path-derived stubs and return `stale: null` (indeterminate) rather than a false `stale: false`:

```python
# In check_doc_freshness, before the comparison:
all_stubs = all(
    v.startswith("h_") for v in stored.values()
) if stored else True
if all_stubs and not current_hashes:
    return {**base_out, "stale": None, "reason": "source_hashes_not_computed",
            "changed_files": []}
```

### Backward compatibility

Existing registered docs have `h_`-prefixed stored hashes. On the first freshness check after the fix, the `all_stubs` guard returns `stale: null` rather than a false `stale: false`. This is the correct behaviour: the system acknowledges it cannot make a determination from path-only hashes. Agents can re-register their docs with real hashes using the updated `RegisterDocIn` model.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

```python

import os

class TestSourceHashFreshness:
```

### Observability

Add a log `WARNING` whenever `check_doc_freshness` returns `stale: null` (stub hashes detected). In production, monitor the fraction of freshness checks returning `null` — a high fraction indicates that docs registered before the fix have not yet been re-registered with real hashes.

### Rollout

- **Effort**: M (medium — API model change, service logic update, router parameter threading; no DDB schema migration; backward-compatible)
- **Risk**: Low for Phase 1 (purely additive). Phase 2 (dev-mode filesystem read) is negligible risk due to `S.dev_mode` gate.
- **Sequencing**: Phase 1 ships first (unblocked). Phase 2 follows as a dev-experience improvement. After Phase 1 ships, send a migration note to existing agent users asking them to re-register docs with real `source_hashes`.
- **Rollback**: Remove the `source_hashes` parameter from models and revert `check_doc_freshness`; freshness silently reverts to always-fresh behaviour; no DDB data is corrupted.
