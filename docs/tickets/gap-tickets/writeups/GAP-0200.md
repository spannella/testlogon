# GAP-0200: Content Ownership Not Validated on Assign — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code; claim confirmed.

## 1. Summary & Classification

**Plain-English statement**: When a collaboration participant assigns a content item to a collaboration via `POST /ui/collaborations/{collab_id}/content`, the backend verifies that the caller is a participant of the collaboration, but it never verifies that the caller actually _owns_ the content being assigned. Any participant can assign any content item — including content they do not own — and from that point on all revenue earned by that content is split according to the collaboration agreement. A malicious user could assign a rival creator's popular content to their own collaboration and siphon a portion of the revenue.

- **Severity**: HIGH (with financial and reputational impact)
- **Source ticket**: FIN-011
- **Status**: Open — ownership check entirely absent
- **Owning area**: Collaboration Revenue / Content Assignment
- **Verdict**: Confirmed. `app/services/collaboration_revenue.py:115`, the `assign_content` function, validates: (1) collaboration exists and is accepted, (2) assigner is a participant, (3) content_type is allowed, (4) max_content_items not exceeded, (5) content not already in another active collaboration. It does **not** validate that `assigned_by` is the owner of `content_id`.
- **Impact**: Financial fraud. A participant can redirect revenue from content they do not own into a collaboration where they receive a split percentage.
- **Related tickets**: FIN-011 (parent), GAP-0199 (sibling), SEC-004 (cross-reference for content ownership validation patterns)

## 2. Current-State Investigation (root cause)

### The missing check

`app/services/collaboration_revenue.py:115–187`, the `assign_content` function:

```python
def assign_content(
    collaboration_id: str,
    content_id: str,
    content_type: str,
    assigned_by: str,
    title: str = "",
) -> Dict[str, Any]:
    collab = get_collaboration(collaboration_id)
    if not collab:
        raise KeyError("not_found")
    _require_participant(collab, assigned_by)          # ✓ caller is a participant
    if collab.get("status") != "accepted":
        raise NotActiveError("not_active")

    allowed_types = collab.get("content_types") or []
    if allowed_types and content_type not in allowed_types:
        raise ValueError(...)

    existing = get_content_assignment(collaboration_id, content_id)
    if existing:
        return existing

    other = find_collaboration_for_content(content_id)
    if other and other.get("collaboration_id") != collaboration_id:
        raise AlreadyAssignedError("already_assigned")

    # ← NO OWNERSHIP CHECK HERE
    # The function proceeds directly to T.collaboration_agreements.put_item(Item=item)
```

The function never asks: "does `assigned_by` own `content_id`?"

### Router call site

`app/routers/collaborations.py:366–389`:

```python
@router.post("/{collab_id}/content", status_code=200)
def assign_content_to_collab(
    collab_id: str, body: CollabContentAssignIn, ctx: Dict = Depends(require_ui_session),
```

The router passes `assigned_by=ctx["user_sub"]` (the authenticated caller), but the service layer does nothing to validate whether `ctx["user_sub"]` is the owner of `body.content_id`.

### Precedent: ownership checks in the codebase

Two other services perform content ownership validation:

1. **`app/services/sponsorship_deals.py:295`** — `_verify_content_ownership(content_type, content_id, creator_sub)` — raises `SponsorshipError(403)` if `content_type == "post"` and the post's `user_id` does not match `creator_sub`. Only handles `post` type.

2. **`app/services/dmca_content_operations.py:16`** — `resolve_content_owner(content_type, content_id)` — returns the owner's `user_id` for `feed_post`, `feed_media`, and `video` content types. This is a pure lookup function (no enforcement).

Neither is called from `assign_content`. The `resolve_content_owner` function is the most general helper, but it only covers three content types and returns an empty string for unknown types.

### Exploit walkthrough

1. Alice (initiator) and Mallory (recipient) enter a 50/50 collaboration agreement. Agreement is accepted.
2. Mallory knows the `content_id` of Bob's popular video (e.g., learned from a public URL or API response).
3. Mallory calls `POST /ui/collaborations/{alice_mallory_collab_id}/content` with `content_id = bob_video_id`, `content_type = "video"`.
4. The assignment succeeds (Mallory is a participant, video is not already assigned elsewhere).
5. The next time Bob's video earns revenue (e.g., via `execute_content_split`), the billing pipeline calls `find_collaboration_for_content(bob_video_id)`, finds the Alice-Mallory collaboration, and splits 50% to Alice and 50% to Mallory.
6. Bob (the actual owner) receives 0% of the revenue.

This attack requires no admin access and only one API call from a legitimate session. The `AlreadyAssigned` exclusivity check means the attack works only if the content is not already in another collaboration — but that is almost always the case for new or unaffiliated content.

## 3. Impact / Exploit / Blast Radius

### Financial severity

- **Direct revenue theft**: Any content earning revenue (video, feed post, catalog item, subscription) can have its revenue siphoned. The attack is persistent — it continues until the assignment is explicitly deleted.
- **Retroactive accounting**: Splits already executed remain in the ledger even after the fraudulent assignment is removed. Reversing them requires manual ledger correction.
- **Scale**: A single malicious actor who joins any collaboration can target any unassigned content. The blast radius is not limited to the collaborators' own content.

### Reputational and compliance risk

- **Creator trust**: Content creators who discover their revenue is being shared without consent will lose trust in the platform and may pursue legal action.
- **Compliance**: Revenue attribution is a financial record; fraudulent splits may constitute wire fraud depending on jurisdiction.

### Detection difficulty

The fraudulent assignment looks identical to a legitimate one in DynamoDB. There is no audit log differentiating "assigned by owner" from "assigned by non-owner participant." The attack is silent.

## 4. Fix Design (code-level)

### 4a. Ownership resolution helper (`app/services/collaboration_revenue.py`)

Extend `resolve_content_owner` from `dmca_content_operations.py` into a local helper inside `collaboration_revenue.py` that covers all collaboration-relevant content types:

```python
def _resolve_content_owner(content_type: str, content_id: str) -> str:
    """Return the owner user_id for content. Returns '' if type unknown or lookup fails.

    Supported types: feed_post, feed_media, video, catalog_item, subscription_plan.
    """
    from app.services.dmca_content_operations import resolve_content_owner as _base
    owner = _base(content_type, content_id)
    if owner:
        return owner

    # Additional types not covered by the DMCA helper
    if content_type == "catalog_item":
        try:
            from app.core.tables import T as _T
            item = _T.catalog.get_item(
                Key={"PK": f"ITEM#{content_id}", "SK": f"ITEM#{content_id}"}
            ).get("Item")
            if item:
                return str(item.get("creator_id") or item.get("user_id") or "")
        except Exception:
            pass

    if content_type == "subscription_plan":
        try:
            from app.core.tables import T as _T
            item = _T.subscription_plans.get_item(
                Key={"plan_id": content_id}
            ).get("Item")
            if item:
                return str(item.get("creator_id") or item.get("user_id") or "")
        except Exception:
            pass

    return ""
```

### 4b. Ownership validation in `assign_content`

Add the check immediately after the participant check and before the `put_item`:

```python
def assign_content(
    collaboration_id: str,
    content_id: str,
    content_type: str,
    assigned_by: str,
    title: str = "",
    skip_ownership_check: bool = False,  # admin-only bypass; defaults False
) -> Dict[str, Any]:
    collab = get_collaboration(collaboration_id)
    if not collab:
        raise KeyError("not_found")
    _require_participant(collab, assigned_by)
    if collab.get("status") != "accepted":
        raise NotActiveError("not_active")

    allowed_types = collab.get("content_types") or []
    if allowed_types and content_type not in allowed_types:
        raise ValueError(f"content_type '{content_type}' not allowed for this collaboration")

    existing = get_content_assignment(collaboration_id, content_id)
    if existing:
        return existing

    # ─── NEW: content ownership check ────────────────────────────────────
    if not skip_ownership_check:
        owner = _resolve_content_owner(content_type, content_id)
        if owner and owner != assigned_by:
            raise PermissionError("content_not_owned")
        # If owner == "" (unknown content type or lookup failure), allow — graceful degradation
        # for content types not yet covered by _resolve_content_owner.
    # ─────────────────────────────────────────────────────────────────────

    other = find_collaboration_for_content(content_id)
    if other and other.get("collaboration_id") != collaboration_id:
        raise AlreadyAssignedError("already_assigned")
    ...
```

**Design decision on graceful degradation**: When `_resolve_content_owner` returns `""` (unknown type or transient lookup failure), the check is skipped rather than rejecting the assignment. This prevents a lookup outage from blocking legitimate use. A `logger.warning` should be emitted in this case for monitoring:

```python
    if not skip_ownership_check:
        owner = _resolve_content_owner(content_type, content_id)
        if owner == "":
            logger.warning(
                "assign_content: could not verify ownership for %s/%s by %s — skipping",
                content_type, content_id, assigned_by,
            )
        elif owner != assigned_by:
            raise PermissionError("content_not_owned")
```

### 4c. Router — surface the new error

`app/routers/collaborations.py:366` already catches `PermissionError` and returns 403:
```python
    except PermissionError:
        raise HTTPException(403, "Not a collaboration participant")
```

The message should be updated to distinguish participant vs ownership errors:

```python
    except PermissionError as exc:
        detail = "You do not own this content" if "content_not_owned" in str(exc) else "Not a collaboration participant"
        raise HTTPException(403, detail)
```

### 4d. Admin bypass for `skip_ownership_check`

Admins may legitimately need to assign content on behalf of a participant (e.g., when migrating legacy data). The router passes `skip_ownership_check=_is_admin(ctx)`:

```python
    cr.assign_content(
        collaboration_id=collab_id,
        content_id=body.content_id,
        content_type=body.content_type,
        assigned_by=ctx["user_sub"],
        title=body.title,
        skip_ownership_check=_is_admin(ctx),
    )
```

This preserves the admin escape hatch while closing the gap for regular users.

### 4e. Dev/Prod parity (SECOPS-007)

The `_resolve_content_owner` helper reads from DynamoDB tables (`T.catalog`, `T.subscription_plans`, the app single-table for posts). In dev these map to DynamoDB Local; in prod to live DynamoDB. The same code path runs in both environments. No feature flags are needed. The `skip_ownership_check=False` default ensures protection is on by default in all environments.

### 4f. Alternatives considered

- **Reject unknown content types entirely**: Would break existing content assignments for less common types while the ownership lookup coverage is incomplete. Rejected in favour of graceful degradation with monitoring.
- **Store owner at assignment time and re-check on split execution**: Adding the check at split time would prevent the revenue leak even if the assignment slipped through, but would add latency to the hot payment path. Better to block at assignment (one-time cost) than at every split.
- **Validate at the router level only**: Keeping the check in the service function `assign_content` is preferred because the service is the authoritative access-control layer; router-only checks are bypassed by direct service calls from tests or future callers.

### Observability

- Add a `content_assign_ownership_denied_total{content_type="..."}` Prometheus counter in the except block. Spike indicates active exploitation attempts.

### Rollout

**Effort**: S (1 day for backend; no frontend changes needed — the API contract is unchanged for valid cases, and the 403 response is already handled by the existing error toast in the collaboration content UI).

**Sequencing**: Ship immediately; this is a security fix. No dependency on GAP-0199. The fix is entirely server-side and requires no frontend change beyond potentially updating the error message display for the new 403 detail string "You do not own this content".

**Backward compatibility**: Existing content assignments in DynamoDB are unaffected (the check fires only at assignment time). Any previously fraudulent assignments that are already in the table should be audited post-deploy: enumerate all `CONTENT#` sub-items in the `collaboration_agreements` table and cross-reference `assigned_by` with `_resolve_content_owner(content_type, content_id)`. Any mismatch is a candidate for manual review and potential removal.

**Rollback**: Remove the ownership check block from `assign_content` (5 lines). The `skip_ownership_check` parameter defaults to `False`; removing the parameter itself is a clean revert with no downstream impact since no existing caller passes it.

**Risk**: Low-medium. The graceful degradation path (unknown content type → `owner == ""` → allow + warning log) ensures no false positives for content types not yet covered by `_resolve_content_owner`. The only breaking change is that a participant who was previously assigning content owned by their collaborator will now receive a 403. This is a narrow case: in a legitimate collaboration, each participant should only assign content they created. If a legitimate use-case emerges where a participant assigns content on behalf of an absent collaborator, an admin can invoke the bypass via `skip_ownership_check=True` through a privileged support endpoint.

### Post-deploy audit script (data integrity)

```python
# scripts/audit_content_assignments.py
"""Scan all content assignments and flag those where assigned_by != content owner."""
import sys
sys.path.insert(0, ".")
from app.core.tables import T
from app.services.collaboration_revenue import _resolve_content_owner
from boto3.dynamodb.conditions import Key

def audit():
    scan_kwargs = {
        "FilterExpression": "begins_with(sk, :p)",
        "ExpressionAttributeValues": {":p": "CONTENT#"},
    }
    paginator = T.collaboration_agreements.meta.client.get_paginator("scan")
    mismatches = []
    for page in paginator.paginate(TableName=T.collaboration_agreements.name):
        for item in page.get("Items", []):
            if not str(item.get("sk", "")).startswith("CONTENT#"):
                continue
            ct = item.get("content_type", "")
            cid = item.get("content_id", "")
            assigned_by = item.get("assigned_by", "")
            owner = _resolve_content_owner(ct, cid)
            if owner and owner != assigned_by:
                mismatches.append({
                    "collaboration_id": item["collaboration_id"],
                    "content_id": cid,
                    "content_type": ct,
                    "assigned_by": assigned_by,
                    "actual_owner": owner,
                })
    return mismatches

if __name__ == "__main__":
    results = audit()
    for m in results:
        print(m)
    print(f"\nTotal mismatches: {len(results)}")
```

Run this once after deploy. Any mismatch should trigger a manual review and, if confirmed fraudulent, a DELETE of the assignment record followed by recalculation of any splits already executed.
