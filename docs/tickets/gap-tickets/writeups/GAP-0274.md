# GAP-0274: `kyc.case.created` Event Not Dispatched from the Router — Remediation Write-up

> Claim status: **CLAIM OK** — confirmed by code inspection. The user-facing `create_kyc_case`
> router handler at `app/routers/kyc_cases.py:539–557` calls `_audit_state_transition` (an
> internal audit log) and `_emit_kyc_metric`, but never calls `_emit_kyc_event_safe`. The
> `kyc.case.created` event is dispatched only in the **partner API** flow
> (`app/services/kyc_partner_api.py:329–336`), not from the user-facing endpoint. The ticket
> states the router "logs an audit event `kyc_case_created` at line 548 but never calls
> `emit_kyc_event`" — this is accurate.

---

## 1. Summary & Classification

**Bug/Gap**: The user-facing KYC case creation endpoint (`POST /v1/kyc/cases`) does not emit
the `kyc.case.created` webhook/notification event. When a user creates a new KYC case through
the normal UI flow, no in-app confirmation alert is written, no email is sent, and no webhook
delivery fires for any subscriber watching `kyc.case.created`. The case is stored correctly in
DynamoDB and an internal audit trail entry is written (`_audit_state_transition` → `audit_event`
calls), but the user-facing notification channel is dark.

**Severity**: HIGH — KYC-011. While `kyc.case.created` is arguably the lowest-urgency of the
three missing events (the user just took the action; they know the case was created), it is
still a required signal for:

- Webhook subscribers that orchestrate onboarding flows (e.g., "start document pre-processing
  as soon as a case is opened").
- In-app confirmation that acts as a receipt and deep-links to the case status page.
- Partner integrations that need to correlate case IDs with their own tracking systems.

**Verdict**: Confirmed. The router (`create_kyc_case`, lines 539–557) contains no
`_emit_kyc_event_safe` call. The `STORE.create_case()` service method (`app/services/
kyc_cases.py:110–149`) also has no event dispatch. By contrast, `submit_case` (same file,
line 412) and the partner API (`kyc_partner_api.py:329–336`) do emit their respective events.

**Claim nuance**: The ticket says "the kyc_partner_api fires it only for partner-originated
flows." This is accurate: `kyc_partner_api.py:329–336` calls `_emit_callback(partner_id,
event="kyc.case.created", ...)` which ultimately calls `emit_kyc_event` routed to the
partner's webhook endpoint, not to the user's in-app notification channel. The user-facing
`POST /v1/kyc/cases` endpoint has no equivalent call at all.

**Related tickets**: GAP-0272 (`kyc.case.approved/rejected`), GAP-0273 (`kyc.case.needs_info`),
KYC-011, SECOPS-007.

## 2. Current-State Investigation (Root Cause)

### Router handler (user-facing case creation)

`app/routers/kyc_cases.py:539–557`:

```python
@router.post("", response_model=KycCaseEnvelope)
def create_kyc_case(
    body: KycCaseCreateRequest,
    request: Request,
    _ctx: dict[str, str] = Depends(require_ui_session),
    user: AuthenticatedUser = Depends(get_authenticated_user),
):
    created = STORE.create_case(user_sub=user.sub, intake_profile=body.intake_profile)
    _audit_state_transition(          # <-- internal audit only
        event_name="kyc_case_created",
        actor_sub=user.sub,
        request=request,
        case_id=str(created.get("kyc_case_id") or ""),
        from_status=None,
        to_status=str(created.get("status") or ""),
        action="create",
    )
    _emit_kyc_metric(request, metric_name="kyc_funnel_transition",   # <-- metrics only
                     tags={"to_status": str(created.get("status") or "")})
    return _wrap_case(created)
```

`_audit_state_transition` calls `audit_event` (internal Prometheus-style ledger, not a
user-visible channel). `_emit_kyc_metric` writes a KYC metric record. Neither sends a
notification to the user or fires a webhook.

### Service layer (create_case)

`app/services/kyc_cases.py:110–149` (`create_case`): performs a `put_item` and returns the
created item. No `_emit_kyc_event_safe` call. The module-level helper is defined at line 17
but called only once in this module (line 412, `submit_case`).

### Partner API (the only place it fires today)

`app/services/kyc_partner_api.py:329–336`:

```python
_emit_callback(
    partner_id,
    event="kyc.case.created",
    case_id=case_id,
    application_id=application_id,
    external_id=external_id,
    status="draft",
)
```

`_emit_callback` at line 615 calls `emit_kyc_event(event=event, user_sub=partner_id, ...)`.
The `user_sub` here is the **partner's** sub (a service account), not the applicant's
`user_sub`. This event is dispatched to the partner's registered webhook endpoint. It does
not generate an in-app notification for the end user.

### Event infrastructure is complete

`app/services/kyc_webhooks.py:38`: `"kyc.case.created": "Verification case created"` in
`_ALERT_TITLES`. The event type is in the `KYC_WEBHOOK_EVENT_TYPES` registry (confirmed by
the partner API being able to dispatch it). There is no `if event == "kyc.case.created":`
branch in `emit_kyc_event` (unlike `submitted/approved/rejected/needs_info`) because the
created event has no special side effects beyond the standard alert + webhook dispatch path.

## 3. Impact / Exploit / Blast Radius

**User experience**: After creating a KYC case, the user sees no confirmation notification in
their in-app alerts feed. The `action_url` that would deep-link to `/kyc/status?case_id=...`
is never written.

**Webhook subscribers**: Systems subscribed to `kyc.case.created` (e.g., a CRM that triggers
a "start onboarding" workflow) receive no signal for user-originated cases. Partner-originated
cases (via the partner API) do fire the event, creating an inconsistency: the same logical
event fires for partner-submitted cases but not for user self-submitted cases.

**Audit trail completeness**: While the internal `audit_event("kyc_case_created", ...)` call
creates an internal record, external compliance systems relying on the webhook for their own
audit log will have a gap for all user-originated cases.

**Downstream automations**: Any automation that starts a document pre-processing job or
sends a "we received your application" confirmation on `kyc.case.created` fails for all
user-originated cases.

**Blast radius**: 100% of user-facing case creation calls are affected. The partner API path
is unaffected (already emits the event).

## 4. Fix Design (Code-Level)

### Option A — Emit from the router (recommended for user-facing endpoint)

The user-facing endpoint already has `user.sub` and the fully-created `created` dict. The
event should be emitted from the router to keep the service layer generic and to have access
to the request context (correlation ID, IP, etc.):

**File**: `app/routers/kyc_cases.py`

```python
# Required import (add to top of file if not already present):
from app.services.kyc_cases import KycCaseConflictError, KycCaseValidationError, STORE, _emit_kyc_event_safe

# In create_kyc_case(), after _emit_kyc_metric(...) and before return:
@router.post("", response_model=KycCaseEnvelope)
def create_kyc_case(
    body: KycCaseCreateRequest,
    request: Request,
    _ctx: dict[str, str] = Depends(require_ui_session),
    user: AuthenticatedUser = Depends(get_authenticated_user),
):
    created = STORE.create_case(user_sub=user.sub, intake_profile=body.intake_profile)
    _audit_state_transition(
        event_name="kyc_case_created",
        ...
    )
    _emit_kyc_metric(request, metric_name="kyc_funnel_transition",
                     tags={"to_status": str(created.get("status") or "")})

    # ADD:
    _emit_kyc_event_safe(
        event="kyc.case.created",
        user_sub=user.sub,
        case_id=str(created.get("kyc_case_id") or ""),
        status=str(created.get("status") or ""),
        intake_profile=str(created.get("intake_profile") or "") or None,
    )

    return _wrap_case(created)
```

`_emit_kyc_event_safe` is already importable from `app.services.kyc_cases`; the router already
imports `STORE` from that module (line 53 of the router).

### Option B — Emit from the service layer (create_case)

Alternatively, add the emit call in `KycCaseStore.create_case()` in `app/services/kyc_cases.py`:

```python
        self._table.put_item(Item=item)
        # ADD after put_item:
        _emit_kyc_event_safe(
            event="kyc.case.created",
            user_sub=user_sub,
            case_id=case_id,
            status=normalized_status,
        )
        return item
```

This option fires the event for all callers of `create_case`, including any future service-to-
service calls. However, `create_case` is currently also called by the partner API flow indirectly
(via `STORE.create_case` inside the partner API service), which already emits `kyc.case.created`
via its own path. Calling `create_case` from the partner API and having it also emit would result
in a duplicate event for partner-originated cases.

**Recommendation**: Option A (router-level emit) is preferred because:
1. It avoids the double-emit risk for partner-originated flows.
2. It keeps the service layer `create_case` a simple CRUD operation.
3. It is consistent with the router already being the place that calls `_audit_state_transition`
   and `_emit_kyc_metric`.

### Dev/Prod Parity (SECOPS-007)

`_emit_kyc_event_safe` is dev/prod parity-correct (see GAP-0272 Section 4 analysis). No AWS
code path is touched. No feature flag required.

### Backward compatibility

Adding an event emission to `create_kyc_case` is purely additive. The HTTP response does not
change. The DDB case record does not change. No migration is needed.

## 5. Testing, Verification & Rollout

### Regression test (fails-before / passes-after)

Add to `tests/test_kyc_cases_router.py`:

```python
from unittest.mock import patch

class TestCreateKycCaseEmitsEvent:
    """GAP-0274: POST /v1/kyc/cases must emit kyc.case.created event."""

    def test_create_emits_kyc_case_created_event(self, client, alice_session):
        emitted = []

        import app.services.kyc_cases as svc
        with patch.object(svc, "_emit_kyc_event_safe",
                          side_effect=lambda **kw: emitted.append(kw)):
            resp = client.post(
                "/v1/kyc/cases",
                json={"intake_profile": "standard"},
                headers=alice_session["headers"],
                cookies=alice_session["cookies"],
            )

        assert resp.status_code == 201
        case = resp.json()["case"]

        assert len(emitted) == 1, (
            f"Expected 1 event from create_kyc_case, got {len(emitted)}. "
            f"GAP-0274: kyc.case.created was not dispatched before fix."
        )
        ev = emitted[0]
        assert ev["event"] == "kyc.case.created"
        assert ev["user_sub"] == alice_session["user_sub"]
        assert ev["case_id"] == case["kyc_case_id"]

    def test_create_event_not_emitted_for_partner_api(self, partner_client, partner_principal):
        """Partner API already emits the event via its own path; no double-emit."""
        # This test verifies that create_case() service method alone does not emit,
        # keeping the partner path unaffected.
        emitted = []
        import app.services.kyc_cases as svc
        with patch.object(svc, "_emit_kyc_event_safe",
                          side_effect=lambda **kw: emitted.append(kw)):
            # Call STORE.create_case directly (as partner API does)
            from app.services.kyc_cases import STORE
            STORE.create_case(user_sub="partner_user_sub", status="draft")

        assert len(emitted) == 0, (
            "Service-layer create_case() must not emit; only the router should emit "
            "to avoid double-emit with the partner API path."
        )
```

**Before fix (Option A)**: `test_create_emits_kyc_case_created_event` fails (`len(emitted)==0`).
**After fix (Option A)**: both tests pass.
