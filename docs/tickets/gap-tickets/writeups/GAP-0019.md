# GAP-0019: `consumer_tax_documents.py` Aggregates Creator EARNINGS (Credits) Instead of Consumer SPENDING (Debits) — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real file:line. Built on the verified investigation at
> `docs/tickets/gap-tickets/investigations/GAP-0019.md`.

## 1. Summary & Classification

**Plain-English statement**: `app/services/consumer_tax_documents.py` is named and routed as
a consumer-spending summary (FIN-004) but internally queries `type="credit"` ledger entries
and reuses the creator-earnings classification function. Every consumer who generates a "tax
document" receives a summary of money they *received* as a creator, not money they *spent*
as a buyer. Consumers with no creator credits see an empty document; creators see their
income rather than their spending. This is a data-direction inversion.

- **Severity**: CRIT
- **Source ticket**: FIN-004
- **Status**: Open
- **Owning area**: Backend / Billing / Tax
- **Verdict**: **Confirmed** — `app/services/consumer_tax_documents.py:107-134` filters
  `type="credit"` and imports `classify_entry` from `creator_earnings.py`. The FIN-004 spec
  unambiguously requires `type="debit"` and a new `classify_category` function.
- **One-line impact**: Users receive completely wrong tax data; pure-consumer users receive
  blank documents they cannot use for expense reporting.
- **Related tickets**: GAP-0020 (TIN/SSN absent from 1099 form), FIN-004 (source ticket),
  FIN-008 (creator 1099 — correctly uses credit entries and is indirectly affected by this
  fix).

`tax_form_1099.py` legitimately needs `_query_credit_entries` and `compute_earnings_summary`

- `consumer_tax_documents.py` → queries debits, uses new `classify_category`
- `tax_form_1099.py` → imports credit-based helpers directly or retains them under their
  original names

### How the bug manifests

**For Alice (pure consumer, zero creator credits)**:
- `compute_earnings_summary` queries her credit entries → 0 results.
- `grand_total_cents = 0`.
- `generate_tax_document` raises `ValueError("below_threshold:...")` because
  `0 < S.tax_documents_min_earnings_cents`.
- Alice is blocked from generating any document at all.

**For Bob (active creator who also buys subscriptions)**:
- `compute_earnings_summary` returns Bob's creator income (tips received, subscription
  revenue, etc.).
- Bob's "consumer tax document" shows his income as a creator, not his spending as a buyer.
- If Bob's income exceeds the threshold (e.g., $600), he sees a $600 "earnings" document
  when he wanted a spending summary.

## 3. Impact / Exploit / Blast Radius

### Data integrity

Every generated consumer tax document on the platform contains incorrect data. A user who
relies on the document for personal tax expense deduction (subscriptions paid, tips given)
has no usable record.

### IRS / Compliance risk

FIN-004 specifies consumer spending summaries, not income documents. Presenting income data
as a spending summary is factually wrong but does not constitute a tax filing (consumers
file this for their own records, not with the IRS). However, if users submit this document
to justify deductions, incorrect data could create tax liability.

### Financial threshold gate misconfigured

`S.tax_documents_min_earnings_cents` applies an income threshold (intended for creator 1099
eligibility, e.g., $60,000 cents = $600 IRS threshold). Consumer spending summaries have no
such threshold — a user who spent $1 should be able to generate their annual summary. After
the fix, the threshold should either be removed for consumer documents or set to a very low
value (e.g., $1).

### No external exploit

Data is user-scoped via `session["user_sub"]` throughout. A user can only see their own
(wrong) data. No cross-user data leak.

## 4. Fix Design (Code-Level)

### 4.1 Replace `_query_credit_entries` with `_query_debit_entries`

In `app/services/consumer_tax_documents.py`, rename and invert the filter:

```python
def _query_debit_entries(
    *, user_sub: str, date_from: int, date_to: int
) -> List[Dict[str, Any]]:
    """Query billing ledger *debit* entries (consumer spending) within [date_from, date_to]."""
    pk = user_pk(user_sub)
    key_cond = Key("pk").eq(pk) & Key("sk").between(
        f"LEDGER#{date_from}#", f"LEDGER#{date_to}#~"
    )
    query_kwargs: Dict[str, Any] = {
        "KeyConditionExpression": key_cond,
        "FilterExpression": Attr("type").eq("debit"),   # ← changed from "credit"
        "Limit": 500,
    }
    collected: List[Dict[str, Any]] = []
    for _ in range(40):
        resp = T.billing.query(**query_kwargs)
        collected.extend(resp.get("Items", []))
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
        query_kwargs["ExclusiveStartKey"] = last_key
    return collected
```

### 4.2 Replace `CATEGORIES` and add `classify_category`

```python
# Replace the old CATEGORIES constant (line 48):
CATEGORIES = ("subscriptions", "tips", "purchases", "unlocks", "deposits", "other")

# Remove: from app.services.creator_earnings import classify_entry

# Add new function:
def classify_category(entry: Dict[str, Any]) -> str:
    """Map a debit ledger entry's reason to a consumer spending category."""
    if entry.get("type") != "debit":
        return "other"
    reason = str(entry.get("reason", "")).lower()
    if reason.startswith(("subscription", "plan")):
        return "subscriptions"
    if reason.startswith("tip"):
        return "tips"
    if reason.startswith(("purchase", "cart", "order")):
        return "purchases"
    if reason.startswith("unlock"):
        return "unlocks"
    if reason.startswith(("deposit", "wallet")):
        return "deposits"
    return "other"
```

### 4.3 Rename `compute_earnings_summary` → `compute_spending_summary`

```python
def compute_spending_summary(          # renamed from compute_earnings_summary
    *, user_sub: str, date_from: int, date_to: int
) -> Dict[str, Any]:
    """Aggregate debited spending by category for a date range."""
    entries = _query_debit_entries(    # renamed query function
        user_sub=user_sub, date_from=date_from, date_to=date_to
    )
    totals: Dict[str, int] = {c: 0 for c in CATEGORIES}
    counts: Dict[str, int] = {c: 0 for c in CATEGORIES}
    grand_total = 0
    txn_count = 0
    currency = "usd"

    for entry in entries:
        amount = _to_int(entry.get("amount_cents", 0))
        category = classify_category(entry)     # new local function
        if category not in totals:
            category = "other"
        totals[category] += amount
        counts[category] += 1
        grand_total += amount
        txn_count += 1
        cur = entry.get("currency")
        if cur:
            currency = str(cur).lower()

    categories = [
        {"category": c, "total_cents": totals[c], "transaction_count": counts[c]}
        for c in CATEGORIES
    ]
    return {
        "date_from": date_from,
        "date_to": date_to,
        "categories": categories,
        "grand_total_cents": grand_total,
        "transaction_count": txn_count,
        "currency": currency,
    }
```

Update `get_annual_summary` and `generate_tax_document` to call `compute_spending_summary`.

### 4.5 Update `tax_form_1099.py` to not import from the renamed function

`app/services/tax_form_1099.py` currently imports:

```python
from app.services.consumer_tax_documents import (
    _query_credit_entries,
    compute_earnings_summary,
    ...
)
```

After the rename, `_query_credit_entries` and `compute_earnings_summary` no longer exist in
`consumer_tax_documents.py`. Two options:

**Option A (recommended)**: Keep the credit-based functions available in
`consumer_tax_documents.py` under their original names as thin aliases pointing to the
internal implementations, clearly marked for creator-1099 use only. This is backward-safe:

```python
# Kept for use by tax_form_1099.py — queries credit (earnings) entries for creators.
_query_credit_entries = _build_credit_query  # internal rename
compute_earnings_summary = _compute_credit_summary  # internal rename
```

**Option B**: Move credit-based aggregation into `creator_earnings.py` or a new shared
module `billing_ledger_queries.py` and update `tax_form_1099.py` imports. Cleaner
long-term, but a larger refactor than this ticket requires.

### 4.6 Remove the income threshold for consumer documents

In `generate_tax_document` (line 391):

```python
min_cents = int(S.tax_documents_min_earnings_cents)
if summary["grand_total_cents"] < min_cents:
    raise ValueError(...)
```

Consumer spending summaries should not have an income threshold. Either:
- Skip this check for consumer documents (`doc_type="consumer_spending"`).
- Add `S.tax_documents_min_spending_cents` (defaulting to `0`) to settings.

### 4.7 Dev/Prod parity (SECOPS-007)

The billing DynamoDB table is used identically in dev and prod. The fix is pure Python
query-filter and classification logic — no new AWS calls, no new environment variables, no
feature flags. The mock DDB in tests (moto) handles `FilterExpression` correctly. SECOPS-007
has no additional requirements.

### Rollout and migration

- **No DynamoDB schema change**: the billing table already has `type` on every entry.
- **Cache invalidation**: Existing `CACHE#{year}` records in `tax_documents` table were
  computed with credit entries. On first access after the fix, `get_annual_summary` will
  skip the stale cache for past years if `use_cache=True` still hits it. Add a
  `cache_version` field to the cache row; bump it after this fix so all prior caches are
  treated as stale:
  ```python
  # In _write_cache():
  item["cache_version"] = 2  # bump from 1 to 2 to invalidate prior credit-based caches

  # In get_annual_summary():
  if cached and cached.get("cache_version", 1) >= 2 and cached.get("categories"):
      return _cache_to_summary(cached, date_from, date_to)
  # Otherwise: recompute and overwrite
  ```

### Interaction with `tax_form_1099.py`

The creator 1099 service (`tax_form_1099.py`) currently imports `compute_earnings_summary`
and `_query_credit_entries` from `consumer_tax_documents.py`. After this fix, the rename
requires that `tax_form_1099.py` either:

(a) Continue importing the renamed-but-preserved aliases (`_query_credit_entries`,
    `compute_earnings_summary` kept in `consumer_tax_documents.py` as backward-compat stubs
    for the duration of a migration window), or

(b) Be updated in the same PR to import from a new shared `billing_ledger_queries.py`
    module.

Option (a) is lower risk for this ticket. The stubs are clearly marked:

```python
# consumer_tax_documents.py — kept for tax_form_1099.py backward compat
# TODO: move to billing_ledger_queries.py once tax_form_1099 is updated
_query_credit_entries = _build_ledger_query_factory(entry_type="credit")

    query_fn=_query_credit_entries,
    classify_fn=classify_entry,
    categories=_CREATOR_CATEGORIES,

```

Removing these stubs is a follow-up task to be done once `tax_form_1099.py` has been
updated to import directly.

### Threshold configuration for consumer documents

After the fix, `S.tax_documents_min_earnings_cents` (which gates 1099 generation) is the
wrong threshold for consumer spending summaries. A consumer who spent $10 across 5
subscriptions should be able to generate their summary, but the current code rejects anyone
below the $600 (60,000 cents) IRS threshold. The router for consumer tax documents should
use a separate, much lower setting:

```python
# In app/core/settings.py:
tax_documents_min_spending_cents: int = int(os.environ.get("TAX_DOCS_MIN_SPENDING_CENTS", "100"))
# Default: $1.00 — effectively no threshold for consumer documents
```

This avoids a regression where the fix makes consumer spending summaries technically correct
but still inaccessible to users who spent below the creator income threshold.
