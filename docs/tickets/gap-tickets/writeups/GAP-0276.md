# GAP-0276: Background Review-Checker and Re-Screening Loops Are Never Started — Remediation Write-up

> Source ticket: KYC-016 · Severity: HIGH · Effort: M · Status: Open

## 1. Summary & Classification

**Gap**: The KYC ongoing-monitoring system provides two critical background loops — a periodic review-checker (`run_review_checker`) that promotes overdue schedules through grace-period and auto-downgrade states, and a re-screening pass (`run_rescreening`) that checks approved users against sanctions lists. Both functions exist and are fully implemented in `app/services/kyc_monitoring.py`, but neither is ever launched as a startup background task. They can only be triggered manually by an admin via HTTP POST endpoints in `app/routers/kyc_monitoring.py`.

**Claim verdict**: CONFIRMED. The gap ticket states that "neither `kyc_monitoring_scheduler.py` nor any equivalent startup hook exists." The code does not have a separate `kyc_monitoring_scheduler.py` file, and `app/main.py` has no `add_event_handler("startup", ...)` call that invokes either `run_review_checker` or `run_rescreening`. The service logic is complete; the wiring is entirely absent.

**Severity**: HIGH. Without the background loops, users whose KYC review dates have passed are never transitioned to grace-period or downgraded status unless an admin manually calls the endpoint. The sanctions re-screening — a legal and compliance obligation — is equally inert. The system presents a fully functional monitoring facade to admins via the dashboard while the actual enforcement is completely passive.

**Owning area**: KYC/Compliance — `app/services/kyc_monitoring.py`, `app/main.py`.

**Related tickets**: KYC-016, GAP-0277 (trigger-event injection), GAP-0259 (profile-change re-screening not wired).

## 2. Current-State Investigation (root cause)

### What exists

`app/services/kyc_monitoring.py` contains fully-implemented service functions:

- `run_review_checker(dry_run=False)` (line 284): queries the `ByNextReviewDate` GSI on `kyc_review_schedule` for overdue `active`, `needs_review`, and `grace_period` schedules, then calls `_enter_grace_period` or `_auto_downgrade` as appropriate.
- `run_rescreening(dry_run=False)` (line 405): iterates all `active` schedules, applies `_deterministic_screening_hit` (a `zlib.crc32`-based deterministic mock in dev; a real sanctions check in prod), and records a `screening_hit` trigger event.
- Both are guarded by feature flags (`S.kyc_rescreening_enabled`, line 420) and handle `dry_run` safely.

`app/routers/kyc_monitoring.py` exposes admin-only HTTP endpoints that call these functions on-demand:
- `POST /v1/kyc/monitoring/admin/review-check` (line 54)
- `POST /v1/kyc/monitoring/admin/rescreening` (line 62)

### What is missing

The analogous task-startup wiring present throughout `app/main.py` for other subsystems does not exist for KYC monitoring:

```python
# app/main.py — existing pattern (lines 521–528)
app.add_event_handler("startup", start_billing_dunning_task)
app.add_event_handler("startup", start_filemgr_purge_task)
app.add_event_handler("startup", start_scheduled_messages_task)
app.add_event_handler("startup", start_kyc_sla_checker_task)   # KYC SLA loop IS present
```

`start_kyc_sla_checker_task` (imported from `app/services/kyc_case_assignment`, line 125, registered at line 528) shows the exact pattern that KYC-016 monitoring should follow. There is no parallel `start_kyc_review_checker_task` or `start_kyc_rescreening_task` anywhere in the codebase.

### Structural comparison: kyc_case_assignment vs kyc_monitoring

`app/services/kyc_case_assignment.py` (lines 730–749) follows the established pattern:

```python
async def kyc_sla_checker_loop(interval_seconds: int = 300) -> None:
    import asyncio
    while True:
        try:
            ASSIGNMENT_SERVICE.run_sla_escalation_sweep()
        except Exception:
            logger.exception("kyc.assignment.sla_checker_error")
        await asyncio.sleep(max(5, int(interval_seconds)))

def start_kyc_sla_checker_task() -> None:
    import asyncio
    if S.kyc_assignment_enabled and S.kyc_sla_checker_enabled:
        asyncio.ensure_future(kyc_sla_checker_loop())
        logger.info("KYC SLA checker started")
```

`app/services/kyc_monitoring.py` has no equivalent `_kyc_review_checker_loop`, `_kyc_rescreening_loop`, or `start_kyc_monitoring_task` functions. The service ends at line 485 with `get_monitoring_dashboard`.

### Dev vs prod behaviour today

In **dev mode** the admin HTTP endpoints work normally. An admin can call `POST .../admin/review-check` or `POST .../admin/rescreening` at will. In **production** those endpoints require `require_admin_or_root` auth — meaning only an admin who knows to call them, on a schedule they maintain externally, would trigger enforcement. There is no automatic enforcement in either environment.

## 3. Impact / Exploit / Blast Radius

### Compliance failure

KYC-016 compliance obligations (AML/BSA) require periodic re-screening of approved users. If the background loop is absent, users approved under a previous sanctions list may never be re-checked. This is a regulatory gap, not just a product bug.

### Tier-downgrade bypass

A user whose next_review_date has passed remains at `status="active"` in the `kyc_review_schedule` table indefinitely. The `ByNextReviewDate` GSI correctly indexes these records; however, without the loop calling `run_review_checker`, no grace-period warning is ever written to the user's alert feed and no `_auto_downgrade` is ever triggered. The user retains their KYC tier even when the review is months overdue.

### Concrete walkthrough

1. User Bob is approved for Tier 2 with `risk_tier="medium"`. `create_review_schedule` writes a record with `next_review_date = now + 365 days`.
2. 366 days later Bob's schedule has `status="active"` and `next_review_date < now`. The review is overdue.
3. Without the loop, no action fires. Bob remains on Tier 2 indefinitely.
4. An admin would need to manually call `POST /v1/kyc/monitoring/admin/review-check` to detect this — a step that exists nowhere in the operational runbook.

### Scale

The `ByNextReviewDate` GSI uses a GSI PK of `gsi_status_pk` (the schedule status string). As the user base grows, a single loop iteration queries only overdue `active`-status records, which is efficient. The absence of the loop scales the problem linearly with the number of approved users.

## 4. Fix Design (code-level)

### 4.1 Add loop functions and startup helper to `app/services/kyc_monitoring.py`

Append the following to the end of `app/services/kyc_monitoring.py` (after `get_monitoring_dashboard`, currently at line 485):

```python
# ── Background task startup ─────────────────────────────────────────────────

_KYC_REVIEW_CHECKER_INTERVAL_SECONDS = int(
    os.environ.get("KYC_REVIEW_CHECKER_INTERVAL_SECONDS", str(6 * 3600))
)
_KYC_RESCREENING_INTERVAL_SECONDS = int(
    os.environ.get("KYC_RESCREENING_INTERVAL_SECONDS", str(24 * 3600))
)


async def _kyc_review_checker_loop() -> None:
    """Every KYC_REVIEW_CHECKER_INTERVAL_SECONDS: run the review-checker."""
    import asyncio
    interval = max(60, _KYC_REVIEW_CHECKER_INTERVAL_SECONDS)
    while True:
        try:
            results = run_review_checker()
            logger.info(
                "kyc.monitoring.review_checker_loop completed "
                "entered_grace=%d auto_downgraded=%d",
                results["entered_grace_period"],
                results["auto_downgraded"],
            )
        except Exception:  # pragma: no cover - defensive
            logger.exception("kyc.monitoring.review_checker_loop_error")
        await asyncio.sleep(interval)


async def _kyc_rescreening_loop() -> None:
    """Every KYC_RESCREENING_INTERVAL_SECONDS: run the re-screening pass."""
    import asyncio
    interval = max(300, _KYC_RESCREENING_INTERVAL_SECONDS)
    while True:
        try:
            if S.kyc_rescreening_enabled:
                results = run_rescreening()
                logger.info(
                    "kyc.monitoring.rescreening_loop completed "
                    "screened=%d matches=%d triggers=%d",
                    results["total_screened"],
                    results["matches_found"],
                    results["triggers_created"],
                )
        except Exception:  # pragma: no cover - defensive
            logger.exception("kyc.monitoring.rescreening_loop_error")
        await asyncio.sleep(interval)


def start_kyc_monitoring_task() -> None:
    """Register the KYC review-checker and re-screening background loops."""
    import asyncio
    import os as _os

    if not S.kyc_review_schedule_table_name:
        logger.warning("kyc.monitoring: kyc_review_schedule_table not configured, skipping")
        return
    asyncio.ensure_future(_kyc_review_checker_loop())
    if S.kyc_rescreening_enabled:
        asyncio.ensure_future(_kyc_rescreening_loop())
    logger.info(
        "KYC monitoring loops started (review_checker interval=%ds, rescreening interval=%ds)",
        _KYC_REVIEW_CHECKER_INTERVAL_SECONDS,
        _KYC_RESCREENING_INTERVAL_SECONDS,
    )
```

### 4.4 Dev/Prod parity (SECOPS-007)

- **Dev mode**: `_deterministic_screening_hit` (lines 391–402 of `kyc_monitoring.py`) uses `zlib.crc32` to produce a stable, process-safe deterministic result — this is already correct. The background loop runs identically in dev and prod; the same `run_rescreening` function is invoked.
- **AWS path**: `T.kyc_review_schedule` is a table handle wired via `app/core/tables.py`; in prod it uses the real DynamoDB endpoint; in dev it uses DynamoDB Local on port 8001. No special branching is needed.
- **Feature flag**: Guarded by `S.kyc_rescreening_enabled` (default `true`). The review-checker loop does not need a separate flag because it is core enforcement — but a `KYC_REVIEW_CHECKER_ENABLED` env-var can be added to `Settings` if operations requires the ability to disable it independently.

### 4.5 Alternatives considered

- **Cron/external scheduler**: An external cron job calling the admin API is operationally viable but introduces credential management complexity (admin JWT must be injected into cron) and breaks the single-binary model. Rejected in favour of the in-process asyncio loop pattern already used by `start_kyc_sla_checker_task`.
- **Single combined loop**: Combining review-checker and re-screening into one loop couples their intervals. Keeping them separate allows the re-screening interval (daily) to differ from the review-checker interval (every 6 h) without coordination. Separate loops retained.

### Metrics / observability

Each loop iteration logs structured output:
```
kyc.monitoring.review_checker_loop completed entered_grace=N auto_downgraded=M
kyc.monitoring.rescreening_loop completed screened=N matches=M triggers=K
```
These log lines should be included in the monitoring dashboard and alarmed if `auto_downgraded > 0` in a single pass (possible compliance signal).

### Rollout / risk

- **Risk**: LOW. The loops only write to DDB and call `write_alert`; they perform no irreversible financial operations.
- **Rollback**: Set `KYC_RESCREENING_ENABLED=false` and `KYC_REVIEW_CHECKER_ENABLED=false` (once the flag is added) to disable both loops without redeployment.
- **Effort**: S (the service logic is complete; this is wiring only).
- **Sequencing**: Deploy after GAP-0277 (trigger-event injection) so that the first review-checker pass has meaningful data to process. Can be deployed independently.
