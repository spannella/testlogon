# GAP-0130: `_find_sort_key()` is O(n) Scan for Reactions/Unlocks — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at
> `app/services/broadcast_chat_store.py:330–341` and
> `app/services/broadcast_chat_rich.py:229–232`. No prior investigation doc exists.

## 1. Summary & Classification

**Bug**: `_find_sort_key(session_id, message_id)` resolves a `message_id` to its DynamoDB
composite `sort_key` by issuing a forward query across all items in the
`BroadcastChatMessages` partition for that session, using a `FilterExpression` on
`message_id`. This is an O(n) table scan within a partition: DynamoDB reads up to
`Limit=200` items (consuming RCUs for all of them) and discards all that don't match.

The function is called on every reaction, reply lookup, message delete, message unlock,
and (indirectly) on reply validation. At high session cardinality (>200 messages) the
function silently misses its target if the message falls outside the first 200 items
returned, returning `None` and causing a 400 error to the API caller. At >5,000
messages the latency and RCU consumption become unacceptable.

- **Severity**: HIGH — functional correctness (messages not found), performance
  (O(n) RCU cost), availability (cascading rate-limit exhaustion at scale)
- **Source ticket**: BCAST-015
- **Status**: Open
- **Owning area**: Broadcast / Chat
- **Claim verdict**: Confirmed. `app/services/broadcast_chat_store.py:330–341` matches
  the description exactly. The `Limit=200` caps the scan and `ScanIndexForward=False`
  (newest-first) partially mitigates the issue for recent messages, but older messages
  in long sessions will be missed.
- **One-line impact**: Reactions, unlocks, replies, and deletes silently fail for any
  broadcast chat message that is not among the 200 most recent items in the session.
- **Related tickets**: GAP-0129 (`_write_chat_billing` atomicity gap — same file),
  SECOPS-007.

## 2. Current-State Investigation (root cause)

### The function

`_find_sort_key` is defined at `app/services/broadcast_chat_store.py:330–341`:

```python
def _find_sort_key(session_id: str, message_id: str) -> Optional[str]:
    """Find sort_key by message_id via a filter on the partition."""
    resp = T.broadcast_chat_messages.query(
        KeyConditionExpression=Key("session_id").eq(session_id),
        FilterExpression=Attr("message_id").eq(message_id),
        Limit=200,
        ScanIndexForward=False,
    )
    items = resp.get("Items", [])
    if items:
        return items[0]["sort_key"]
    return None
```

### Why it is O(n) and incorrect

1. **DynamoDB `FilterExpression` is post-read**: DynamoDB evaluates `Limit` on the
   number of items **read** (before the filter), not the number of items **returned**.
   With `Limit=200`, DynamoDB reads the 200 most recent items in the partition and
   then discards those that don't match `message_id`. A single matching item may be
   among items 201–∞; it will never be found.

2. **`ScanIndexForward=False` is a partial mitigation only**: the query returns the
   most recent 200 items first, which means reactions/unlocks on very recent messages
   work correctly. However, any reaction or unlock on a message older than the 200
   most-recent items returns `None` → 400 "Message not found" — a silent functional
   break at > ~200 messages per session.

3. **No `LastEvaluatedKey` loop**: the function makes a single query call. Even if
   the limit were removed, a 1MB read cap applies. The function does not paginate,
   so messages in a large session that happen to fall beyond the first 1MB would
   also be missed.

4. **RCU cost**: each call reads up to 200 items (eventually-consistent), regardless
   of which one matched. In a busy session with concurrent reactions/unlocks, this
   multiplies the RCU consumption linearly with session message count.

### Callers

`_find_sort_key` is called from five code paths:

| Caller | File | Line | Operation |
|--------|------|------|-----------|
| `react_to_chat_message` | `broadcast_chat_rich.py` | 87 | Reaction add/remove |
| `unlock_chat_message` | `broadcast_chat_rich.py` | 165 | Unlock paywall |
| `_find_sort_key` (re-export) | `broadcast_chat_rich.py` | 229–232 | Delegates to store |
| `send_chat_message` (reply) | `broadcast_chat_store.py` | 181 | Validate reply target |
| `delete_chat_message` | `broadcast_chat_store.py` | 311 | Soft delete |

All five paths fail silently for messages not in the most-recent 200. The paid unlock
path (`unlock_chat_message`) is the highest-severity failure: viewers are blocked from
unlocking content they paid to access.

### Dev vs prod behaviour

In dev mode sessions are short (< 200 messages), so the bug is rarely observed.
In production, popular broadcasters may accumulate thousands of messages per session.
The threshold for the first failure is approximately 200 messages (at `Limit=200`).
Beyond that point, older messages become permanently inaccessible to reactions,
replies, unlocks, and deletes.

## 3. Impact / Exploit / Blast Radius

### Functional correctness

- A viewer attempts to react to a message posted 30 minutes ago in a busy session
  (250+ messages). The `_find_sort_key` query returns `None`. The API returns
  `HTTP 400 "Message not found"`.
- A viewer who purchased an unlock for a locked message from an hour ago receives
  `HTTP 400 "Message not found"` — unable to unlock despite having paid (in
  combination with GAP-0129, this is a double failure: billing may succeed but the
  content is never released).
- A broadcaster attempts to delete a spam message from earlier in the session — cannot
  do so if it is beyond position 200.

### Performance / cost

In a session with 5,000 messages, each `_find_sort_key` call:
- Issues a partition query consuming up to 200 × 0.5KB = 100KB of eventually-consistent
  read capacity.
- Returns `None` for ~99.96% of messages.
- If reactions arrive at 10/second, this generates ~200 × 10 = 2,000 RCUs/second from
  `_find_sort_key` alone — likely saturating provisioned throughput and triggering
  throttling.

### Cascading availability risk

Throttling of the `BroadcastChatMessages` table affects all chat writes and reads
(chat history, message delivery). A busy session receiving high-frequency reactions
or unlocks can starve the table, causing chat message delivery to stall. This is
an availability concern beyond the functional correctness issue.

### Blast radius

Every broadcast session with more than ~200 chat messages is affected. Actions on
any message outside the most-recent 200 are silently broken. The severity increases
with session duration and viewer engagement.

## 4. Fix Design (code-level)

### Option A (Recommended): Add a `MessageIdIndex` GSI

Add a GSI to `BroadcastChatMessages` with `message_id` as the partition key. This
enables O(1) lookup by `message_id`, eliminating the scan entirely.

**Schema change (`scripts/local-ddb-init.py`)**:

```python
# scripts/local-ddb-init.py — modify BroadcastChatMessages TableDef
TableDef(
    _resolve_table_name(S.broadcast_chat_messages_table_name, "BroadcastChatMessages"),
    "session_id",
    "sort_key",
    gsi=[
        {
            "index_name": "MessageIdIndex",
            "partition_key": "message_id",
        }
    ],
),
```

No `attr_types` override needed — `message_id` is a string.

**Updated `_find_sort_key`** in `app/services/broadcast_chat_store.py:330`:

```python
def _find_sort_key(session_id: str, message_id: str) -> Optional[str]:
    """Find sort_key by message_id using MessageIdIndex GSI (O(1))."""
    resp = T.broadcast_chat_messages.query(
        IndexName="MessageIdIndex",
        KeyConditionExpression=Key("message_id").eq(message_id),
    )
    items = resp.get("Items", [])
    if not items:
        return None
    # Confirm the message belongs to the requested session (partition ownership)
    for item in items:
        if item.get("session_id") == session_id:
            return item["sort_key"]
    return None
```

The session-ownership check is a correctness guard: two different sessions could
theoretically have a message with the same `message_id` prefix if IDs were not
globally unique. In practice `message_id = "cm_" + uuid4().hex` is globally unique,
but the check costs nothing and prevents cross-session data leakage.

**LOTTERY# and LENTRY# items**: these config items in `BroadcastChatMessages` have
`sort_key` starting with `LOTTERY#` or `LENTRY#` and no `message_id` attribute. The
GSI `MessageIdIndex` will simply not index these items (DynamoDB skips items without
the GSI key attribute), which is the desired behaviour.

### Option B (Alternative): Accept `sort_key` from callers

All callers that hold the `sort_key` from a previous chat delivery step pass it through
directly to reaction/unlock/delete. This avoids the lookup entirely.

**Pros**: no schema change, no migration, works with existing data.
**Cons**: requires API contract changes — callers (frontend and API clients) must
persist and supply `sort_key`; `sort_key` is an internal implementation detail of the
DynamoDB schema and should not be exposed to clients. Rejected as primary option.

### Option C: Remove the `Limit` cap and paginate

Replace the single `Limit=200` query with a paginating loop. This fixes the
correctness issue (finds the message regardless of position) but does not fix the
performance/RCU issue — it makes it worse by reading the entire partition on every
lookup. Rejected.

### Primary recommendation: Option A

Add the GSI. It is the only option that is both correct and O(1).

### Dev/prod parity (SECOPS-007)

DynamoDB Local (port 8001) and moto both support GSIs via the same
`GlobalSecondaryIndexes` create parameter used by other tables in `local-ddb-init.py`.
`scripts/local-ddb-init.py` creates the GSI when the table is first created; the dev
stack recreates tables on `just restart`, so the GSI is always present in dev.

For production (AWS DynamoDB), adding a GSI to an existing table is an online operation
(no downtime). AWS provisions the GSI asynchronously and backfills it from existing data.
The backfill for `BroadcastChatMessages` is bounded by the 7-day TTL on messages — the
table is not expected to contain more than a few weeks of data.

During the backfill window (typically minutes to an hour depending on table size),
`_find_sort_key` must temporarily fall back to the old scan for messages not yet indexed
by the GSI. A safe approach is to query the GSI first; if the result is empty, fall back
to the paginating scan (Option C) for a short transition period, then remove the fallback
once GSI backfill is confirmed complete.

### Backward compatibility / migration

No changes to the DynamoDB item structure. Items without a `message_id` attribute
(LOTTERY# and LENTRY# config items) are unaffected by the GSI. The `sort_key` format
and all existing API contracts are unchanged.

## 5. Testing, Verification & Rollout

### Regression test — O(1) correctness for deep messages (pytest, offline)

```python
# tests/services/test_broadcast_chat_find_sort_key.py

def test_find_sort_key_locates_old_message_beyond_200(
    moto_broadcast_chat_messages_table,
):
    """
    BEFORE fix (with Limit=200, no GSI): _find_sort_key returns None for message at
    position 201 (oldest item in a 201-message partition), causing 400 errors.
    AFTER fix (with GSI): returns the correct sort_key regardless of position.
    """
    from app.services.broadcast_chat_store import _find_sort_key

    session_id = "sess_deep_test"
    target_message_id = None
    target_sort_key = None

    # Write 201 messages; the first message written will be the oldest.
    for i in range(201):
        msg_id = f"cm_{i:04d}abc"
        sk = f"{i:016d}#{msg_id}"
        if i == 0:
            target_message_id = msg_id
            target_sort_key = sk
        moto_broadcast_chat_messages_table.put_item(Item={
            "session_id": session_id,
            "sort_key": sk,
            "message_id": msg_id,
            "text": f"msg {i}",
        })

    result = _find_sort_key(session_id, target_message_id)
    assert result == target_sort_key, (
        f"Expected sort_key {target_sort_key!r}, got {result!r}. "
        "Old code with Limit=200 returns None for messages beyond position 200."
    )
```

**Fails before fix**: `Limit=200`, `ScanIndexForward=False` → returns the 200 most
recent messages → message 0 (oldest) is outside the window → `_find_sort_key` returns
`None` → assertion `result == target_sort_key` fails.

**Passes after fix**: GSI lookup by `message_id` returns the item directly → correct
`sort_key` returned.

### Regression test — session isolation

```python
def test_find_sort_key_does_not_cross_sessions(moto_broadcast_chat_messages_table):
    """Messages from a different session with the same message_id prefix are not returned."""
    from app.services.broadcast_chat_store import _find_sort_key

    # Same message_id in two sessions
    for sess in ("sess_a", "sess_b"):
        moto_broadcast_chat_messages_table.put_item(Item={
            "session_id": sess,
            "sort_key": f"000000000000001#cm_shared",
            "message_id": "cm_shared",
            "text": "shared id",
        })

    result = _find_sort_key("sess_a", "cm_shared")
    assert result is not None
    # Result belongs to sess_a
    item = moto_broadcast_chat_messages_table.get_item(
        Key={"session_id": "sess_a", "sort_key": result}
    ).get("Item")
    assert item is not None
    assert item["session_id"] == "sess_a"
```

### Observability

- Add a warning log when `_find_sort_key` returns `None` after a GSI lookup (indicating
  a message was deleted or never existed). Differentiate from the old "scan miss"
  scenario.
- Metric: `broadcast.chat.find_sort_key_miss` — alert if > 0 in a window (legitimate
  misses should be zero in a healthy session).
- Monitor RCU consumption on `BroadcastChatMessages`: after the fix, per-reaction RCU
  should drop from O(n) to O(1).

### Rollout

1. **Dev**: add GSI to `scripts/local-ddb-init.py` and update `_find_sort_key` in
   the same PR. Run `just restart` to recreate tables with the new GSI.
2. **Staging**: deploy code + run `local-ddb-init.py` equivalent (or migration script)
   to add the GSI online.
3. **Production**: add the GSI via the AWS Console or IaC (`aws dynamodb
   update-table`). Wait for `IndexStatus: ACTIVE`. Deploy the updated code.
4. **Transition period**: optionally enable the scan fallback (configurable via
   `S.broadcast_chat_find_sk_fallback_enabled`) during GSI backfill; disable after
   `IndexStatus: ACTIVE` confirmed.

### Rollback

Revert to the old `_find_sort_key` with `Limit=200`. The GSI can remain on the table
(it does not affect reads or writes that don't use it). Rolling back code is sufficient.
