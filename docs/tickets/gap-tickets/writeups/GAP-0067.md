# GAP-0067: creative_weights Written by apply_recommendation But Not Consumed by Serving Engine — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase 2026-06-05; claim is **confirmed**.

## 1. Summary & Classification

- **Severity**: HIGH
- **Source ticket**: ADS-017 · **Status**: Open
- **Owning area**: Backend / Ad Serving Engine (`app/services/ad_serving.py`)
- **Verdict**: CONFIRMED. `apply_recommendation` for action `reallocate_budget` persists a
  `creative_weights` dict to the campaign's DynamoDB record, but `serve_ad` never reads this
  field. The serving engine selects creatives using only the per-creative `rotation_weight`
  column, making the entire `reallocate_budget` recommendation type a no-op.
- **Impact**: Advertisers who accept a budget-reallocation recommendation believe ad spend is
  being redistributed to the better-performing creative; in reality the weight split remains
  unchanged. Advertiser trust, revenue optimisation, and platform ROAS reporting are all
  affected.
- **Related tickets**: GAP-0066 (frontend components — false-positive), GAP-0049 (platform
  revenue share accounting), ADS-017 source ticket.

## 2. Current-State Investigation (root cause)

### Write path — `apply_recommendation` in `app/services/ad_optimization.py`

When an advertiser clicks "Apply" on a `reallocate_budget` recommendation, the frontend calls:

```
POST /ui/ads/optimization/campaigns/{campaign_id}/recommendations/{rec_id}/apply
```

`apply_recommendation` (line 614) handles the `reallocate_budget` case at lines 663–666:

```python
# app/services/ad_optimization.py:663-666
elif action == "reallocate_budget":
    weights = rec.get("details", {}).get("creative_weights") or {}
    _set_campaign_field(account_id, campaign, "creative_weights", weights)
    applied["creative_weights"] = weights
```

`_set_campaign_field` performs a DynamoDB `update_item` that writes the `creative_weights`
attribute to the campaign item. The attribute is a dict mapping `creative_id → int_weight`,
computed by `calculate_creative_weights` (line 123) and embedded in the recommendation's
`details` sub-object when recommendations are generated (line 526):

```python
# app/services/ad_optimization.py:514-526
"recommendation_id": _rec_id(campaign_id, "reallocate_budget", best["creative_id"], salt),
"action": "reallocate_budget",
# …
"details": {"creative_weights": weights},
```

The write succeeds; the campaign record now has a `creative_weights` field with values like
`{"cr_abc123": 75, "cr_def456": 25}`.

### Read path — `serve_ad` in `app/services/ad_serving.py`

`serve_ad` (line 45) builds a list of `candidates`, each carrying the raw campaign dict and its
approved creatives. After selecting the highest-scoring campaign (line 132–133), it calls:

```python
# app/services/ad_serving.py:135-136
# 5. Select creative (weighted random by rotation_weight)
creative = _weighted_random_creative(winner["creatives"])
```

`_weighted_random_creative` (lines 395–402) reads only the `rotation_weight` field from each
**creative** record, completely ignoring any `creative_weights` on the parent campaign:

```python
# app/services/ad_serving.py:395-402
def _weighted_random_creative(creatives: list[dict]) -> dict:
    if len(creatives) == 1:
        return creatives[0]
    weights = [int(c.get("rotation_weight", 50)) for c in creatives]
    total = sum(weights)
    if total == 0:
        return random.choice(creatives)
    return random.choices(creatives, weights=weights, k=1)[0]
```

The campaign dict is never passed to this helper. There is no code path anywhere in
`ad_serving.py` that reads `campaign.get("creative_weights")`. The field is written to DynamoDB
and then silently discarded.

### Why the bug is silent

- The API response from `apply_recommendation` returns `{"ok": True, "status": "applied",
  "creative_weights": {...}}` — this looks successful to the frontend.
- The UI invalidates the recommendations query and shows the recommendation as "applied".
- No error is raised, no log entry indicates a mismatch.
- The serving engine's comment on line 135 even says "weighted random by rotation_weight",
  directly naming the wrong field, confirming the disconnect was present at implementation time.

## 3. Impact / Exploit / Blast Radius

### Advertiser trust and ROAS

When a `reallocate_budget` recommendation fires, the optimisation engine has detected that one
creative has a meaningfully higher CTR than others. The recommended weight split directs the
majority of impressions to the winner. After applying the recommendation, an advertiser
reasonably expects to see improved CTR and ROAS in their campaign analytics. Because the weight
is not actually consumed, CTR remains flat, and the advertiser may conclude the optimisation
system is broken or that their better-performing creative is not being served.

### Financial impact

- Advertisers whose campaigns have under-performing creatives continue spending budget on those
  creatives at the original weight ratio. The platform collects its 30 % revenue share on all
  spend, but the advertiser receives worse return, which increases churn risk.
- There is no over-billing or under-billing — the impact is opportunity cost, not an accounting
  error.

### Data integrity

`creative_weights` is written to the campaign record in DynamoDB but is logically dead weight.
If a future developer reads the field and assumes it is honoured by the serving engine, they may
build additional features on a false assumption.

### Blast radius scope

All advertisers who have ever applied a `reallocate_budget` recommendation (via any campaign on
the platform) are affected. The serving engine has served the wrong creative split from the
moment those recommendations were applied. There is no exploitation path (this is not a security
gap), but financial and trust impact affects every such advertiser.

## 4. Fix Design (code-level)

### Approach

Pass the winning campaign dict into `_weighted_random_creative`, and inside that helper prefer
the `campaign.creative_weights` map over the per-creative `rotation_weight` fallback. The
`creative_weights` map is keyed by `creative_id`, so the override is per-creative.

The change is entirely local to `ad_serving.py` — no model changes, no DynamoDB schema changes,
no frontend changes.

### Precise code change

**`app/services/ad_serving.py` — call site (line 135–136)**

Replace:
```python
    # 5. Select creative (weighted random by rotation_weight)
    creative = _weighted_random_creative(winner["creatives"])
```

With:
```python
    # 5. Select creative — prefer campaign-level creative_weights (set by
    # reallocate_budget recommendations) then fall back to per-creative
    # rotation_weight.
    creative = _weighted_random_creative(
        winner["creatives"], campaign_weights=winner["campaign"].get("creative_weights") or {}
    )
```

**`app/services/ad_serving.py` — helper (lines 395–402)**

Replace:
```python
def _weighted_random_creative(creatives: list[dict]) -> dict:
    if len(creatives) == 1:
        return creatives[0]
    weights = [int(c.get("rotation_weight", 50)) for c in creatives]
    total = sum(weights)
    if total == 0:
        return random.choice(creatives)
    return random.choices(creatives, weights=weights, k=1)[0]
```

With:
```python
def _weighted_random_creative(
    creatives: list[dict],
    campaign_weights: dict | None = None,
) -> dict:
    """Select a creative using weighted random sampling.

    If the campaign has a ``creative_weights`` dict (written by a
    ``reallocate_budget`` optimisation recommendation), those values take
    precedence over the per-creative ``rotation_weight`` field.

    Args:
        creatives: list of approved creative dicts for the winning campaign.
        campaign_weights: optional ``{creative_id: int}`` map from the campaign
            record (``campaign.get("creative_weights")``). A missing or zero
            entry falls back to the creative's own ``rotation_weight``.
    """
    if len(creatives) == 1:
        return creatives[0]
    cw = campaign_weights or {}
    weights: list[int] = []
    for c in creatives:
        cid = c.get("creative_id", "")
        if cid in cw:
            weights.append(max(1, int(cw[cid])))  # campaign-level override
        else:
            weights.append(int(c.get("rotation_weight", 50)))
    total = sum(weights)
    if total == 0:
        return random.choice(creatives)
    return random.choices(creatives, weights=weights, k=1)[0]
```

### Why this design

- **Backwards compatible**: campaigns without `creative_weights` behave identically to today
  because `cw` defaults to `{}` and the per-creative `rotation_weight` fallback is unchanged.
- **Graceful degradation**: a creative missing from `creative_weights` (e.g., a new creative
  added after the recommendation was applied) still receives its own `rotation_weight` weight.
- **No DynamoDB schema change**: `creative_weights` is already being written; this fix merely
  reads it.
- **Thread-safe**: `random.choices` uses the module-level PRNG, which is thread-safe for
  `--workers 1` dev mode; in production with multiple workers each worker has an independent
  PRNG state, which is correct behaviour.

### Dev/Prod parity (SECOPS-007)

The fix operates on data already in DynamoDB. Both dev (DynamoDB Local on port 8001) and prod
(real AWS DynamoDB) store `creative_weights` identically via the existing write path. No
environment flag or mock/real split is needed. The change is identical in both environments.

### Migration

Campaigns that have had a `reallocate_budget` recommendation applied already have the
`creative_weights` field in DynamoDB. **No backfill is needed** — on the next `serve_ad`
invocation for those campaigns the new code will immediately honour the stored weights.

## 5. Testing, Verification & Rollout

### Regression test — fails before fix, passes after

```python
# tests/test_gap_0067_creative_weights.py
"""
GAP-0067 regression: creative_weights written by apply_recommendation must be
consumed by _weighted_random_creative in ad_serving.py.

Run with: .venv/bin/pytest tests/test_gap_0067_creative_weights.py -v
"""
import random
import pytest

# ── Unit test: _weighted_random_creative honours campaign_weights ────────────

def test_weighted_random_creative_uses_campaign_weights():
    """When campaign_weights is supplied, it must override rotation_weight."""
    from app.services.ad_serving import _weighted_random_creative

    creatives = [
        {"creative_id": "cr_a", "rotation_weight": 50},
        {"creative_id": "cr_b", "rotation_weight": 50},
    ]
    campaign_weights = {"cr_a": 95, "cr_b": 5}

    # Run 1000 samples; with 95:5 split cr_a should win ~95 % of the time.
    # Before fix: campaign_weights is ignored (signature lacks the parameter),
    # so both creatives get weight=50 → ~50 % each → test fails.
    counts = {"cr_a": 0, "cr_b": 0}
    random.seed(42)
    for _ in range(1000):
        result = _weighted_random_creative(creatives, campaign_weights=campaign_weights)
        counts[result["creative_id"]] += 1

    # With 95:5 weights we expect cr_a to win >85 % of samples (generous threshold).
    assert counts["cr_a"] > 850, (
        f"cr_a won {counts['cr_a']}/1000 — creative_weights are not being honoured. "
        "This is the GAP-0067 regression."
    )


def test_weighted_random_creative_fallback_without_campaign_weights():
    """When no campaign_weights is provided, behaviour must be unchanged."""
    from app.services.ad_serving import _weighted_random_creative

    creatives = [
        {"creative_id": "cr_a", "rotation_weight": 80},
        {"creative_id": "cr_b", "rotation_weight": 20},
    ]
    counts = {"cr_a": 0, "cr_b": 0}
    random.seed(99)
    for _ in range(1000):
        result = _weighted_random_creative(creatives)
        counts[result["creative_id"]] += 1

    # 80:20 → cr_a should win >65 % of samples.
    assert counts["cr_a"] > 650


def test_weighted_random_creative_partial_campaign_weights():
    """Creatives absent from campaign_weights fall back to rotation_weight."""
    from app.services.ad_serving import _weighted_random_creative

    creatives = [
        {"creative_id": "cr_a", "rotation_weight": 50},
        {"creative_id": "cr_b", "rotation_weight": 50},
        {"creative_id": "cr_c", "rotation_weight": 50},  # not in campaign_weights
    ]
    campaign_weights = {"cr_a": 80, "cr_b": 20}  # cr_c absent

    # Should not raise; cr_c is present in the output pool.
    results = {
        _weighted_random_creative(creatives, campaign_weights=campaign_weights)["creative_id"]
        for _ in range(200)
    }
    # All three creatives should be reachable.
    assert "cr_c" in results, "cr_c (absent from campaign_weights) never selected"
```

**Before the fix**: `_weighted_random_creative` does not accept `campaign_weights`, so calling
it with that keyword argument raises `TypeError` — the test for the new behaviour will error or
fail at the call-site assertion.

**After the fix**: all three tests pass.

### Observability

Add a structured log line in `serve_ad` when `campaign_weights` is used:

```python
if cw:
    logger.debug(
        "ad_serving_campaign_weights campaign_id=%s weights=%s",
        winner["campaign"]["campaign_id"], cw,

```

This is low-volume (one log per ad impression that uses campaign weights) and aids debugging.

### Rollback

Revert the two-line change in `ad_serving.py`. Campaigns that had `creative_weights` applied
will continue to have the field in DynamoDB but it will again be ignored, reverting to the
pre-fix behaviour. No data loss.

### Risks

- **Statistical tests are probabilistic**: the unit test uses `random.seed(42)` to make results
  deterministic. If the PRNG implementation changes between Python versions, the seed may
  produce different counts. Use a generous threshold (85 % not 95 %) to reduce flakiness.
- **Per-creative weight fallback**: the `max(1, ...)` floor on campaign_weights ensures that a
  weight of 0 in the map does not silently exclude a creative (use 0 explicitly to get the
  fallback, but a configured 0 in the recommendation would be a bug upstream). Consider
  documenting that 0 is treated as 1 in the serving engine.
