# GAP-0076: Budget Bypass via Race Condition — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase 2026-06-05; claim is **confirmed**
> — the two-step ADD + conditional SET in `record_usage` is present exactly as described.

## 1. Summary & Classification

- **Severity**: HIGH — financial controls can be bypassed; a user can exceed their monthly
  LLM spending budget by issuing concurrent agent sessions.
- **Source ticket**: AGENT-001 · **Status**: Open
- **Owning area**: `app/services/llm_provider_keys.py` — `record_usage` function
- **Related tickets**: GAP-0077 (monthly reset absent), AGENT-001 (LLM key management),
  SECOPS-007 (dev/prod parity)

**Verdict: CLAIM CONFIRMED.** The `record_usage` function at line 310 performs an atomic
`ADD` on `current_month_usage_cents`, then does a separate `get_item` + conditional `update_item`
to flip `status` to `budget_exceeded`. Between those two DynamoDB calls, a concurrent agent
session can observe `status = "active"` and proceed to spend beyond the configured monthly
budget.

**One-line impact**: Concurrent LLM calls can each pass the "key is active" check after the
budget is already exhausted, causing real overspend against a third-party API key.

## 2. Current-State Investigation (root cause)

### Exact code path

`app/services/llm_provider_keys.py`, function `record_usage` (line 310):

```python
def record_usage(user_id, key_id, *, tokens, cost_cents):
    ts = now_ts()
    # Step 1 — atomic ADD (correct, but only covers the counter)
    T.llm_provider_keys.update_item(
        Key={"pk": f"USER#{user_id}", "sk": f"KEY#{key_id}"},
        UpdateExpression=(
            "ADD total_requests :one, total_tokens_used :tok, "
            "current_month_usage_cents :cost "
            "SET last_used_at = :ts, updated_at = :ts"
        ),
        ExpressionAttributeValues={...},
    )
    # Step 2 — non-atomic read
    item_resp = T.llm_provider_keys.get_item(...)   # line 337
    item = item_resp.get("Item")
    if item:
        budget  = int(item.get("monthly_budget_cents", 0) or 0)
        current = int(item.get("current_month_usage_cents", 0) or 0)
        if budget > 0 and current >= budget and item.get("status") == "active":
            # Step 3 — conditional SET (no ConditionExpression guards against concurrent write)
            T.llm_provider_keys.update_item(
                ...,
                UpdateExpression="SET #st = :exceeded",
                ...
            )
```

### Why it is broken

**Step 1** uses DynamoDB `ADD`, which is atomic at the item level. This correctly increments
`current_month_usage_cents` and prevents counter corruption. However, the budget enforcement
decision requires knowing the *post-increment* value AND updating `status` atomically in the
same operation.

**Step 2** (the `get_item`) is a separate round-trip. Between Step 1 and Step 2, any number of
concurrent `record_usage` calls can:

1. Execute their own Step 1 (`ADD cost_cents`) and see the counter above budget.
2. Execute their own Step 2 (`get_item`) before *any* of them has completed Step 3
   (`SET status = budget_exceeded`).
3. All concurrent callers observe `status = "active"` and conclude the key has not yet
   been marked exceeded.

The result is that **N concurrent calls can each allow a new LLM request** after the budget is
crossed, because none of them has yet written `status = budget_exceeded`.

**Step 3** lacks a `ConditionExpression="attribute_not_exists(#st) OR #st = :active"` guard, so
even if multiple callers reach Step 3 simultaneously, each simply overwrites the same value —
this is harmless but highlights that there is no optimistic-lock protection on the status flip.

### Budget enforcement upstream (caller side)

The caller that checks budget before dispatching an LLM call is:

`app/services/agent_orchestrator.py` (or equivalent) — calls `get_key` to check
`budget_remaining_cents`. If `status != "active"`, the request is blocked. The window between
the final `record_usage` and the status flip is where bypass is possible.

### Dev vs prod manifestation

In dev mode the `T.*` table handles target **DynamoDB Local** (port 8001). The race is
reproducible locally with concurrent `pytest` workers or `asyncio.gather`. In prod it targets
real **DynamoDB**, where network latency between calls is larger — but production workloads with
agent pools issuing parallel LLM requests make the race *more* likely at scale, not less.

## 3. Impact / Exploit / Blast Radius

### Concrete exploit walkthrough

1. User sets `monthly_budget_cents = 500` (five dollars) on an Anthropic key.
2. User launches 10 concurrent agent workers, each dispatching an LLM request for ~50 cents.
3. Each worker's `record_usage` fires `ADD 50` at near the same instant.
4. All 10 `get_item` calls return `current_month_usage_cents` values that vary depending on
   which ADD has replicated, but all see `status = "active"` (none has written `budget_exceeded`
   yet).
5. All 10 workers' Step 3 updates fire. Each writes `budget_exceeded`. But the damage is done:
   ten 50-cent calls were allowed through, spending $5 instead of the $0.00 remaining after
   the first call hit the $5 budget.

In the worst case, if many agents share one key and requests are larger, the overspend can be
an integer multiple of the budget before any single call lands its `budget_exceeded` write.

### Financial consequence

- **Direct**: The user's third-party LLM provider bill for the key in question grows beyond
  `monthly_budget_cents`. The platform cannot claw back this spend.
- **Indirect**: If the platform absorbs LLM costs on behalf of users (prepaid model), the
  overspend is a direct loss. If users pay the key costs, the budget feature becomes a false
  guarantee, causing support escalations and trust damage.

### Data integrity consequence

The `current_month_usage_cents` counter itself remains accurate (thanks to the atomic `ADD`).
Only the `status` flip is racy. Reporting and billing ledger totals are not corrupted.

### Blast radius

Scoped to users with `monthly_budget_cents > 0` who run concurrent agent sessions.
Users who run a single sequential session are unaffected. No other data is at risk.
The vulnerability does **not** allow access to other users' keys.

## 4. Fix Design (code-level)

### Option A — Single atomic `UpdateItem` with `ConditionExpression` (recommended)

Replace the three-step ADD → GET → conditional SET with a **single `UpdateItem`** that:

1. `ADD` the usage counters.
2. Conditionally sets `status = "budget_exceeded"` in the same expression, using
   `ADD` result visibility via a `ConditionExpression` that fires only when the new
   total meets or exceeds the budget and the current status is `"active"`.

DynamoDB does not expose the post-ADD value inside the same expression, so the cleanest
approach is to use a **DynamoDB Transaction** (`transact_write`) or split into two
operations with an **optimistic lock**:

```python
def record_usage(user_id: str, key_id: str, *, tokens: int, cost_cents: int) -> None:
    ts = now_ts()
    key = {"pk": f"USER#{user_id}", "sk": f"KEY#{key_id}"}

    # Step 1: atomic increment — same as today
    T.llm_provider_keys.update_item(
        Key=key,
        UpdateExpression=(
            "ADD total_requests :one, total_tokens_used :tok, "
            "current_month_usage_cents :cost "
            "SET last_used_at = :ts, updated_at = :ts"
        ),
        ExpressionAttributeValues={
            ":one": 1, ":tok": tokens, ":cost": cost_cents, ":ts": ts,
        },
    )

    # Step 2: read the post-ADD state (unavoidable — DDB ADD doesn't return new value)
    item_resp = T.llm_provider_keys.get_item(Key=key)
    item = item_resp.get("Item")
    if not item:
        return

    budget  = int(item.get("monthly_budget_cents", 0) or 0)
    current = int(item.get("current_month_usage_cents", 0) or 0)
    status  = item.get("status", "active")

    if budget > 0 and current >= budget and status == "active":
        # Step 3: conditional SET — only fires when status is still "active"
        # ConditionExpression prevents overwrite races and double-logging
        try:
            T.llm_provider_keys.update_item(
                Key=key,
                UpdateExpression="SET #st = :exceeded",
                ConditionExpression="#st = :active",
                ExpressionAttributeNames={"#st": "status"},
                ExpressionAttributeValues={
                    ":exceeded": "budget_exceeded",
                    ":active": "active",
                },
            )
            logger.warning(
                "llm_key_budget_exceeded user_id=%s key_id=%s "
                "budget_cents=%d usage_cents=%d",
                user_id, key_id, budget, current,
            )
        except T.llm_provider_keys.meta.client.exceptions.ConditionalCheckFailedException:
            # Another concurrent call already set budget_exceeded — that's fine
            pass
```

The `ConditionExpression="#st = :active"` ensures that exactly one concurrent caller
"wins" the status flip; all others get `ConditionalCheckFailedException` and silently
skip, knowing the status was already updated. This converts the race into an idempotent
single-writer pattern.

### Option B — DynamoDB Transaction (heavier, not necessary)

A `transact_write` with `Update` + `ConditionCheck` achieves the same guarantee but
adds transactional overhead and costs 2× the write capacity. Prefer Option A.

### Dev/Prod parity (SECOPS-007)

The fix is **pure DynamoDB** — it works identically against DynamoDB Local (dev, port 8001)
and real AWS DynamoDB (prod). No new flags, mocks, or environment branches are required.
The `ConditionalCheckFailedException` class path is the same on both because it is raised
by the botocore layer.

`app/core/tables.py` → `T.llm_provider_keys` resolves to the correct endpoint based on
`S.ddb_endpoint_url`, so the fix is environment-agnostic by construction.

### Backward compatibility

No DynamoDB schema change required. No migration needed. The fix is a pure code change to
`record_usage`. Deployed atomically — inflight requests just before deployment use the old
two-step path; requests after use the new single-step path with the condition expression.
No data loss or corruption in either path.

### Rollout

- **Effort**: S (small) — 15–20 lines changed in a single function.
- **Risk**: LOW — the condition expression degrades gracefully; worst case under extremely
  high concurrency is that the warning log fires once instead of N times, with no data loss.
- **Sequencing**: No dependencies. Can be merged and deployed independently. No migration.
- **Rollback**: Removing the `ConditionExpression` and `except ConditionalCheckFailedException`
  block restores previous behavior; the race window reopens but no data is corrupted.

### Why DynamoDB Transactions are not needed here

DynamoDB `TransactWriteItems` would allow the ADD and the conditional SET to happen in a
single ACID transaction, but this introduces two costs: the transaction uses 2× write
capacity units, and DynamoDB transactions have a 25-item limit and add ~5–10ms of latency.
The `ConditionExpression` approach on the second `update_item` achieves the same safety
guarantee (exactly one winner for the status flip) at lower cost: the ADD fires atomically
in step 1 regardless, so the only race is on the status update, which the condition
expression resolves idempotently.

The pattern is consistent with the way the rest of the codebase handles optimistic
concurrency — for example, `app/services/messaging.py` uses `ConditionExpression` to
prevent duplicate message delivery rather than transactions. Following this established
pattern keeps the fix reviewable and consistent with team conventions.

### Broader budget-enforcement improvement

As a follow-on improvement, budget enforcement could also be moved upstream to
`get_decrypted_api_key` (line 159), which is called by the provisioner before injecting
the key into a worker session. Adding a check there means that budget-exceeded keys are
blocked at session start, not just during usage recording:

```python
def get_decrypted_api_key(user_id: str, key_id: str) -> str:
    ...
    if item.get("status") == "budget_exceeded":
        raise ValueError("Monthly budget for this key has been exceeded")

```

This is a defense-in-depth measure; the primary fix remains in `record_usage`.
