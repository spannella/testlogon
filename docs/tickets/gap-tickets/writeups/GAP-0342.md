# GAP-0342: Promo Codes Not Integrated into Subscription Checkout — Remediation Write-up

## 1. Summary & Classification

**Gap**: The subscription checkout endpoint (`POST /api/plans/{plan_id}/subscribe` in
`app/routers/subscription_server.py`) accepts a `discount_code` field that resolves to
a creator-owned **subscription discount** record stored in DynamoDB — a completely
separate system from the platform-wide `promo_codes` service. Promo codes created via
`POST /ui/promo-codes` with `applies_to: ["subscription"]` are never consulted during
subscription checkout, meaning customers cannot use platform promo codes to get
discounts on subscriptions.

- **Severity**: HIGH
- **Source ticket**: PROMO-001
- **Owning area**: Subscriptions / Billing / Backend
- **Status**: Open

**Claim accuracy**: Confirmed. The `subscribe` handler at
`app/routers/subscription_server.py:817–993` calls `_get_discount` at line 843, which
resolves to `ddb_get_item(pk_creator(creator_id), _discount_sk(code))` at line 186 —
a simple key lookup in the subscriptions table for a creator-specific discount row.
`app/services/promo_codes.validate_promo_code` and `redeem_promo_code` are never called
from `subscription_server.py`.

**One-line impact**: Customers entering platform promo codes at subscription checkout
silently receive no discount; the platform-wide promo code system is dead for the
subscription product.

**Related tickets**: PROMO-001, GAP-0343 (shop checkout), GAP-0185 (TOCTOU concern in
promo validation)

---

## 2. Current-State Investigation (Root Cause)

### 2.1 The two separate discount systems

**System A — creator subscription discounts** (currently wired):

Located inside `subscription_server.py`. A creator can create percentage-off discount
codes via `POST /api/creators/{creator_id}/discounts`. These are stored under the key
pattern `pk_creator(creator_id)` / `DISCOUNT#{code}` in the subscriptions table.

`_get_discount` (`subscription_server.py:186`):
```python
def _get_discount(creator_id: str, code: str) -> Optional[Dict[str, Any]]:
    return ddb_get_item(pk_creator(creator_id), _discount_sk(code))
```

`SubscribeIn` model (`subscription_server.py:331`):
```python
class SubscribeIn(BaseModel):
    subscriber_id: Optional[str] = None
    interval: Optional[Literal["month", "year"]] = None
    discount_code: Optional[str] = None
    trial_days: Optional[conint(ge=1, le=365)] = None
```

The `subscribe` handler uses only `body.discount_code` (line 842–851), applies the
percentage discount via `_apply_discount`, and records it in the subscription row. There
is no per-user redemption count, no expiry check beyond what `_is_discount_active`
provides, and no atomic TOCTOU guard on usage limits.

**System B — platform promo codes** (not wired):

`app/services/promo_codes.py` is a full promo code engine with:
- `validate_promo_code(code, user_id, checkout_type, item_price_cents, creator_user_id)`
  — runs expiry, max-uses, per-user limit, and `applies_to` checks
- `redeem_promo_code(code_id, user_id, ...)` — atomically increments `current_uses`
  with a DDB `ConditionExpression` TOCTOU guard (line 380)
- `applies_to` field supports `["subscription"]` as a valid value

The `validate_promo_code` function (`promo_codes.py:239`) accepts
`checkout_type="subscription"` and correctly rejects codes whose `applies_to` list
does not include `"subscription"`. This entire path is never reached from
`subscription_server.py`.

### 2.2 Frontend state

`frontend/src/pages/subscriptions/PlanBrowser.tsx:49` passes only `discount_code` to
the `subscribe` API call. There is no promo code input field; the UI has a generic
`discountCode` state variable that maps to the old system. No `promo_code` field is
sent.

### 2.3 Dev vs. prod

Both systems are pure DynamoDB operations and behave identically in dev and prod. The
promo_codes table is created in `scripts/local-ddb-init.py` and is available in both
environments.

## 3. Impact / Exploit / Blast Radius

**Business impact**: Promo codes issued by creators or the platform with
`applies_to: ["subscription"]` are inert. A creator who runs a promotional campaign and
hands out codes will see zero redemptions and zero discount applied, even though the
codes are valid in the system. Customers who received codes via email or advertising
receive no discount and no error — the code is silently ignored.

**Financial integrity**: The existing `discount_code` path (System A) has no TOCTOU
guard and no atomic increment. A race condition between two concurrent subscription
attempts with the same discount code could allow double-discount, though the impact
is bounded to a single subscription price rather than a monetary payout.

**Scope**: All users attempting to subscribe to a plan using a platform promo code.

**Comparison with shop checkout**: The shop checkout in `app/services/shoppingcart.py`
already integrates `validate_promo_code` and `redeem_promo_code` with a TOCTOU guard.
The subscription checkout explicitly has an older, simpler discount mechanism that
predates the platform-wide promo code system. This inconsistency means users discover
that promo codes work at the shop but not at the subscription checkout — a confusing
user experience that may reduce subscription revenue during promotional campaigns.

## 4. Fix Design (Code-Level)

### 4.1 Extend `SubscribeIn` model

Add `promo_code: Optional[str]` to `SubscribeIn`
(`app/routers/subscription_server.py:331`):

```python
class SubscribeIn(BaseModel):
    subscriber_id: Optional[str] = None
    interval: Optional[Literal["month", "year"]] = None
    discount_code: Optional[str] = None    # existing creator-specific discount (keep)
    promo_code: Optional[str] = None       # NEW: platform-wide promo code
    trial_days: Optional[conint(ge=1, le=365)] = None
```

### 4.2 Extend the `subscribe` handler

After the existing `discount_code` block (lines 842–886), add promo code handling.
The promo code must be validated before the subscription record is written, and
redeemed atomically after the write succeeds. The full block to insert after line 886
(after `if applied_discount: sub["discount"] = ...`):

```python
    # --- Platform promo code (PROMO-001) ---
    applied_promo: Optional[Dict[str, Any]] = None
    if body.promo_code:
        from app.services.promo_codes import validate_promo_code, redeem_promo_code
        promo_result = validate_promo_code(
            code=body.promo_code.strip().upper(),
            user_id=subscriber_id,
            checkout_type="subscription",
            item_price_cents=base_price,
            creator_user_id=plan["creator_id"],
        )
        if not promo_result["valid"]:
            raise HTTPException(
                status_code=422,
                detail={"code": "invalid_promo_code", "message": promo_result["message"]},
            )
        # Apply promo discount — takes precedence over / stacks with creator discount
        # depending on policy. For now: promo discount applied on top of any creator discount.
        if promo_result["discount_cents"] > 0:
            price_cents = max(0, price_cents - promo_result["discount_cents"])
        applied_promo = promo_result
```

After `save_subscription(sub)` (line 893) and before `record_billing_subscription`:

```python
    sub["price_cents"] = price_cents    # update stored price with promo applied
    if applied_promo:
        sub["promo_code_id"] = applied_promo["code_id"]
        sub["promo_discount_cents"] = applied_promo["discount_cents"]
```

After `save_subscription(sub)` write succeeds — redeem the promo code:

```python
    if applied_promo and applied_promo.get("code_id"):
        try:
            redeem_promo_code(
                code_id=applied_promo["code_id"],
                user_id=subscriber_id,
                original_price_cents=base_price,
                final_price_cents=price_cents,
                checkout_type="subscription",
                checkout_item_id=subscription_id,
            )
        except Exception as e:
            logger.warning("promo_code redeem failed sub=%s: %s", subscription_id, e)
            # Subscription already created; do not roll back.
            # Log the failure for manual reconciliation.
```

The `redeem_promo_code` function already implements the TOCTOU guard via
`ConditionExpression=Attr("current_uses").lt(max_uses)` (`promo_codes.py:380`).

### 4.3 Ordering guarantee (TOCTOU)

`validate_promo_code` is a read-then-check. A concurrent subscriber could pass
validation simultaneously. `redeem_promo_code` performs the atomic increment and will
raise `ConditionalCheckFailedException` for the late winner if `max_uses` is exceeded.
The subscribe handler should catch this after the subscription is written and record it
in the subscription's metadata so the subscriber can be notified to try a different code.

### 4.4 Frontend update (`frontend/src/pages/subscriptions/PlanBrowser.tsx`)

The component currently passes `{ discount_code: discountCode }`. Add a second input
for `promo_code` and pass it separately:

```typescript
subscribe(planId, {
  ...(discountCode ? { discount_code: discountCode } : {}),
  ...(promoCode    ? { promo_code: promoCode }      : {}),
})
```

A single text input with a label "Promo code" is sufficient. The backend now accepts
both fields independently.

### 4.5 Dev / Prod Parity (SECOPS-007)

Both `validate_promo_code` and `redeem_promo_code` are pure DynamoDB operations that
use the mocked local DynamoDB in dev and real DynamoDB in prod. No AWS service
boundary is crossed. The `_cognito_available`-style guard is not needed here. No feature
flag is required beyond the existing `S.promo_codes_enabled` check: the router should
add an early return if `not S.promo_codes_enabled` before calling the promo service.

## 5. Testing, Verification & Rollout

### 5.1 Pytest Regression Test (fails-before / passes-after)

Create `tests/test_subscription_promo_code.py`:

```python
"""Regression: subscription checkout must honour platform promo codes."""
import pytest
from unittest.mock import patch


def _make_promo_result(discount_cents: int) -> dict:
    return {
        "valid": True,
        "code_id": "promo_abc",
        "discount_type": "percentage",
        "discount_cents": discount_cents,
        "final_price_cents": 1000 - discount_cents,
        "free_trial_days": 0,
        "message": None,
    }


def test_subscribe_applies_promo_code_discount(client, alice_headers, seed_plan):
    """A valid promo code reduces the subscription price."""
    plan_id = seed_plan["plan_id"]          # $10.00 / month plan
    with patch(
        "app.services.promo_codes.validate_promo_code",
        return_value=_make_promo_result(300),   # $3 off
    ) as mock_validate, patch(
        "app.services.promo_codes.redeem_promo_code",
        return_value=({"code_id": "promo_abc"}, None),
    ) as mock_redeem:
        resp = client.post(
            f"/api/plans/{plan_id}/subscribe",
            json={"promo_code": "SAVE30"},
            headers=alice_headers,
        )
    assert resp.status_code == 200
    sub = resp.json()
    assert sub["price_cents"] == 700    # 1000 - 300
    mock_validate.assert_called_once_with(
        code="SAVE30",
        user_id=alice_headers["X-User-Id"],
        checkout_type="subscription",
        item_price_cents=1000,
        creator_user_id=seed_plan["creator_id"],
    )
    mock_redeem.assert_called_once()


def test_subscribe_rejects_invalid_promo_code(client, alice_headers, seed_plan):
    """An invalid promo code returns 422 with a meaningful message."""
    plan_id = seed_plan["plan_id"]
    with patch(
        "app.services.promo_codes.validate_promo_code",
        return_value={"valid": False, "code_id": None, "message": "Code not found",
                      "discount_cents": 0, "final_price_cents": 1000,
                      "free_trial_days": 0, "discount_type": None},
    ):
        resp = client.post(
            f"/api/plans/{plan_id}/subscribe",
            json={"promo_code": "BADCODE"},
            headers=alice_headers,
        )
    assert resp.status_code == 422
    assert "promo_code" in resp.json()["detail"]["code"]
```

**Fails before fix**: The `SubscribeIn` model ignores `promo_code`; the handler never
calls `validate_promo_code`; the price is unchanged and the mock is never invoked.

**Passes after fix**: The handler validates and applies the discount.

### 5.3 Metrics / Observability

- Add `logger.info("promo_code_applied sub=%s code_id=%s discount_cents=%s",
  subscription_id, applied_promo["code_id"], applied_promo["discount_cents"])`
- `redeem_promo_code` already writes a `REDEEM#` row in DynamoDB for audit. These rows
  serve as both an immutable redemption ledger and the per-user usage counter data source
  used by `_query_promo_user_redeems`.
- Add a structured log warning when `redeem_promo_code` fails after a successful
  subscription write:
  ```python
  logger.warning(
      "promo_redeem_failed_post_subscribe sub=%s code_id=%s err=%s",
      subscription_id, applied_promo["code_id"], e,
  )
  ```
  Set a CloudWatch alarm on this log pattern so ops can manually increment `current_uses`
  if the failure was transient.
- Consider emitting a metric counter `subscription.promo_code_applied` segmented by
  `discount_type` to measure promotional campaign effectiveness.

### 5.4 Interaction with the Existing `discount_code` System

The existing `discount_code` field (System A) should be retained for backward
compatibility. Creators may have already shared System A discount codes with their
subscribers. The two systems can coexist in the same request; the handler should:

1. Evaluate System A (`discount_code`) first and compute `base_price` after creator
   discount.
2. Evaluate System B (`promo_code`) against the post-System-A price, or against the
   original `base_price`, depending on stacking policy. The recommended default is
   sequential stacking (System A first, then promo code), which gives creators
   control over the floor price.
3. Store both `discount` (System A) and `promo_code_id` (System B) on the subscription
   record for billing reconciliation.

If both fields are provided and both are valid, the handler applies them in order.
If the combined discount would reduce the price below zero, clamp to 0.

### 5.5 Rollout

- **Effort**: M (Medium) — approximately 60–80 lines of new handler code, one model
  field addition, one frontend input addition. No new tables or migrations.
- **Backward compat**: Existing subscriptions with `discount_code` are unaffected.
  The new `promo_code` field is optional. No existing subscription records are modified.
  The `SubscribeIn.discount_code` field remains and continues to function exactly as
  before.
- **Rollback**: Remove the `body.promo_code` block and revert the `SubscribeIn` model
  change; existing subscriptions are unaffected.
- **Risk**: Low. The `redeem_promo_code` TOCTOU guard is already proven in the shop
  checkout path (`app/services/shoppingcart.py:377–391`). The only new concurrency
  concern is that `validate_promo_code` and `redeem_promo_code` are not in the same
  DynamoDB transaction, so the validate→subscribe→redeem sequence has a narrow window
  where max_uses could be exceeded by one. The `ConditionExpression` on `redeem_promo_code`
  is the atomic guard; a failed redeem after a successful subscribe should be logged for
  reconciliation rather than causing the subscription to roll back.
- **Sequencing**: Can be implemented independently. Coordinate with PROMO-001 frontend
  work; no dependency on GAP-0343. This ticket should be implemented before any
  promotional campaigns that use platform promo codes for subscription plans are launched.
