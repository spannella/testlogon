# GAP-0153: check_milestone Has No Call Sites — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at app/services/milestones.py and all qualifying event-write paths.

## 1. Summary & Classification

**Plain-English statement:** The `check_milestone` function in `app/services/milestones.py:49` is a complete, production-quality implementation that detects creator metric threshold crossings (subscriber counts, total tips, views, total earnings) and writes idempotent milestone records to DynamoDB. However, the function is never called from any application code path. Milestones can only appear in the system if manually seeded via DynamoDB directly; the automatic detection that should fire after tip payments, subscription signups, and analytics rollups does not exist.

- **Severity:** HIGH — a complete creator engagement feature is entirely non-functional in production.
- **Source ticket:** CREATOR-003
- **Status:** Open
- **Owning area:** Creator Features / Milestone Detection / Analytics

**Claim verdict:** Confirmed. Exhaustive grep of all `.py` files confirms zero invocations of `check_milestone` outside its own definition at `app/services/milestones.py:49`. The function is also not imported by any other module.

**Related tickets:** GAP-0152 (dashboard_sse_publish call sites — milestone events should trigger SSE after detection), CREATOR-003, SECOPS-007.

## 2. Current-State Investigation (Root Cause)

### The milestone detection logic is complete

`app/services/milestones.py:49–98` implements:
- Threshold tables for four metrics: `subscribers` (9 levels), `tips_total_cents` (7 levels), `views` (5 levels), `earnings_total_cents` (6 levels).
- Finding the highest achieved threshold for the current value.
- Writing a DynamoDB item with `ConditionExpression="attribute_not_exists(pk) AND attribute_not_exists(sk)"` — idempotent; duplicate milestone records are safely rejected.
- Logging and returning the milestone dict on new achievement, `None` on duplicate or no-threshold-crossed.

Supporting functions (`acknowledge_milestone`, `list_milestones`, `get_milestone_settings`, `update_milestone_settings`) are all implemented and wired to router endpoints (presumably in `app/routers/creator_dashboard.py` or similar).

The service is fully ready to be called; the gap is purely the absence of call sites.

### Three qualifying event types that should trigger check_milestone

#### 1. Tip received — `earnings_total_cents` and `tips_total_cents` metrics

When a creator receives a tip, `write_tip_ledger` in `app/services/tip_ledger.py:88` writes the credit entry. At this point the creator's cumulative earnings and tip totals increase. The caller has `entry.recipient_user_id` and `entry.amount_cents` available. However, `write_tip_ledger` does not maintain a running total; it only appends ledger rows. To check a threshold crossing, the current total must be queried from the analytics or aggregated from the ledger.

The realistic approach at tip time is:
- Query the creator's current total earnings from the `AnalyticsRollups` table (or a dedicated aggregate attribute on the user record).
- Call `check_milestone(user_id, "tips_total_cents", current_total)`.
- Call `check_milestone(user_id, "earnings_total_cents", current_total)`.

If no aggregate is maintained in real time, the milestone check at tip time is approximate (based on the pre-tip value). An alternative is to run the check at analytics rollup completion, which is more accurate but less timely.

#### 2. Subscription signup — `subscribers` metric

When a user subscribes to a creator's plan, the subscription service (`app/routers/subscription_server.py`) processes the signup. At `save_subscription` (`subscription_server.py:517`), the new subscriber record is written. The creator's subscriber count is maintained on the subscription tier record (`admin_subscription_tiers.py:150`). After incrementing the subscriber count, `check_milestone(creator_id, "subscribers", new_count)` should be called.

#### 3. Analytics rollup completion — all metrics

`app/routers/creator_analytics.py:320` references `S.analytics_rollup_lookback_days` for a rollup operation. The analytics rollup service computes aggregate views, subscribers, and earnings and writes them to `AnalyticsRollups`. After each rollup write, all four metrics can be checked accurately against the freshly computed totals. This is the most natural and authoritative call site.

### Why the gap was not caught earlier

The milestone service and its supporting router endpoints were implemented in CREATOR-003. The service layer was completed before the call-site integration was done, and the integration step was never performed. All four supporting functions work correctly when called directly (e.g. from `pytest` or via direct DynamoDB seed + list endpoint), which is why the service itself appears healthy on casual inspection.

## 3. Impact / Exploit / Blast Radius

### Creator engagement feature is entirely non-functional

Milestones are designed to drive creator retention:
- Celebration animations and in-app notifications fire on milestone achievement.
- Email notifications (gated by `milestone_prefs.email_enabled`) should be sent.
- Push notifications (gated by `milestone_prefs.push_enabled`) should be sent.
- The creator dashboard milestone panel (`GET /ui/dashboard/milestones`) shows an empty list for all creators because no milestone records are ever written automatically.

Since `check_milestone` is never called, none of these flows ever trigger. A creator who accumulates 1,000 subscribers or $1,000 in tips receives no in-app acknowledgement.

### No financial loss or security risk

Milestone records are decorative/engagement metadata. They do not gate payments, unlock features, or affect account permissions. The absence of milestones does not cause data corruption or financial inaccuracy.

### Blast radius

- All creators are affected equally — no milestone is ever auto-detected.
- The `list_milestones` endpoint works but always returns `[]` unless manually seeded.
- The `acknowledge_milestone` endpoint is functional but unreachable through normal product flows.
- Compounded by GAP-0152: even when milestones start being detected, the SSE push will still not fire until GAP-0152 is also fixed.

## 4. Fix Design (Code-Level)

### Recommended integration point: analytics rollup completion

The cleanest and most accurate integration point is the analytics rollup completion. After the rollup writes fresh aggregate values to `AnalyticsRollups`, all four metrics are known precisely. This avoids the awkward approximation problem at tip time.

The rollup worker or service (in `app/routers/creator_analytics.py` or its backing service) should, after updating a creator's rollup record, call:

```python
from app.services.milestones import check_milestone

# Inside rollup completion, after writing the updated aggregate for `creator_id`:
for metric, value in [
    ("subscribers",          int(rollup.get("total_subscribers", 0))),
    ("views",                int(rollup.get("total_views", 0))),
    ("earnings_total_cents", int(rollup.get("total_earnings_cents", 0))),
    ("tips_total_cents",     int(rollup.get("total_tips_cents", 0))),
]:
    try:
        milestone = check_milestone(creator_id, metric, value)
        if milestone:
            # Notify dashboard stream (GAP-0152 fix)
            from app.services.dashboard_sse import dashboard_sse_publish
            dashboard_sse_publish(creator_id, {
                "type": "milestone:reached",
                "milestone_id": milestone["milestone_id"],
                "metric": metric,
                "threshold": milestone["threshold"],
                "formatted": milestone["formatted"],
                "achieved_at": milestone["achieved_at"],
            })
    except Exception:
        logger.warning("check_milestone failed for %s metric=%s", creator_id, metric, exc_info=True)
```

### Secondary integration point: subscription signup

In `app/routers/subscription_server.py`, after `save_subscription` increments the subscriber count on the tier, retrieve the new count and call:

```python
from app.services.milestones import check_milestone

try:
    # `new_subscriber_count` is the updated count after the subscribe action
    check_milestone(creator_id, "subscribers", new_subscriber_count)
except Exception:
    logger.warning("check_milestone failed on subscription", exc_info=True)
```

This provides faster (real-time) milestone detection for the subscriber metric without waiting for the next rollup window.

### Tertiary integration point: tip ledger write

For the `tips_total_cents` and `earnings_total_cents` metrics, calling `check_milestone` at tip time requires a running total. If the platform maintains a `creator_stats` DynamoDB record with `total_tips_cents` (updated atomically at tip time), add:

```python
from app.services.milestones import check_milestone

try:
    new_total = increment_creator_tip_total(entry.recipient_user_id, entry.amount_cents)
    check_milestone(entry.recipient_user_id, "tips_total_cents", new_total)
    check_milestone(entry.recipient_user_id, "earnings_total_cents", new_total)
except Exception:
    logger.warning("check_milestone failed on tip", exc_info=True)
```

If no such running total exists, defer to the rollup path.

### Dev/Prod parity (SECOPS-007)

`check_milestone` writes to the `APP_TABLE` DynamoDB table (the single-table store), which is `app_single_table` in dev (DynamoDB Local port 8001) and the real DynamoDB table in production. The `ddb.Table(APP_TABLE)` client transparently targets whichever endpoint is configured in the environment (`DDB_ENDPOINT_URL` in dev, no override in prod). No mocking or dev-mode branching is required; the same code path runs in both environments.

The ConditionExpression deduplication means milestone records are idempotent — running the analytics rollup multiple times for the same creator at the same value will not create duplicate milestone records.

### Backward compatibility

- No schema migration required — milestone records are new items in the existing single-table store.
- The `list_milestones` endpoint will begin returning results automatically as milestones are detected; no API contract change.
- `acknowledge_milestone` and settings endpoints are unaffected.

### Rollout

- **Effort:** S (Small) — wiring the call sites is straightforward; the integration is approximately 30–50 lines across 1–3 files.
- **Risk:** Low. The `ConditionExpression` deduplication ensures idempotency; even if `check_milestone` is called multiple times (e.g. from both rollup and subscription signup), no duplicate records are written.
- **Sequencing:** Fix alongside GAP-0152 (`dashboard_sse_publish` call sites). When `check_milestone` returns a non-None result, the `dashboard_sse_publish` call in the same code block will push `milestone:reached` to the creator's dashboard stream.
- **Rollback:** Remove the `check_milestone` call sites. Existing milestone records in DynamoDB are benign (they only surface through the listing endpoint).
