# GAP-0296: `/ui/licenses/revenue/process-split` endpoint allows any user to trigger arbitrary splits — Remediation Write-up

> ~5 pages. Fix-oriented. No investigation doc exists; the claim is verified directly against the codebase.

## 1. Summary & Classification

**Bug statement:** The `POST /ui/licenses/revenue/process-split` endpoint is protected only by `require_ui_session`. Any authenticated user can POST to it with any `content_id`, `licensee_id`, and `source_amount_cents`, causing the platform to write real billing ledger entries and transfer wallet balances without any actual underlying transaction having taken place.

- **Severity:** HIGH
- **Source ticket:** LICENSE-003
- **Status:** Open — no remediation applied
- **Owning area:** License Revenue / Billing
- **Claim verdict:** CONFIRMED. The endpoint exists at `app/routers/license_revenue.py:140-158`, is protected only by `require_ui_session`, and calls `svc.process_revenue_split(...)` which performs real DynamoDB writes to the billing ledger and applies wallet deltas.

**Related tickets:** LICENSE-003 (parent); GAP-0292 (billing ledger integrity); SECOPS-007 (dev/prod parity).

**Scope note:** The same missing auth guard applies to two adjacent endpoints on the same router (`register-license` at line 107 and `revoke-license` at line 127), but GAP-0296 is formally scoped to `process-split`. All three endpoints should be remediated together.


## 2. Current-State Investigation (root cause)

The `process-split` endpoint was added as a developer convenience — a way to drive the split engine without going through a full tip or unlock flow. It was never guarded with an admin or dev-mode gate before shipping.

**File:** `app/routers/license_revenue.py`

```python
# Line 140-158
@router.post("/process-split")
async def process_split(
    body: dict,
    ctx: dict = Depends(require_ui_session),   # <-- only auth check
):
    """Trigger revenue split processing for a content item.

    This endpoint allows testing the split engine without going through
    the full tip/unlock flow.
    """
    splits = svc.process_revenue_split(
        content_id=body["content_id"],
        licensee_id=body.get("licensee_id", ctx["user_sub"]),
        source_type=body.get("source_type", "tip"),
        source_amount_cents=int(body["source_amount_cents"]),
        source_txn_id=body.get("source_txn_id", "test_txn"),
        currency=body.get("currency", "usd"),
    )
    return {"ok": True, "splits": splits}
```

`require_ui_session` (defined in `app/services/sessions.py:284`) validates only that a valid, non-revoked session exists and that CSRF passes for cookie-auth callers. It does not inspect the `role` field it returns — the endpoint reads only `ctx["user_sub"]` for the default `licensee_id`. The `role` value is present in the returned dict (`app/services/sessions.py:398`) but is never checked in `process_split`.

The called service, `process_revenue_split` in `app/services/license_revenue.py:82`, performs full production writes:

- `_process_fixed_fee` — writes a `LEDGER` DynamoDB entry and calls `apply_wallet_delta`.
- Revenue/profit shares — write additional `LEDGER` entries and apply wallet deltas to the licensor's wallet.
- All writes go through the same `billing_shared` helpers used by real transactions.

No `S.dev_mode` guard exists on the router or service level. The endpoint is registered on the main `router` (prefix `/ui/licenses/revenue`) which is imported unconditionally in `app/main.py`.

The router registration in `app/main.py` includes the `router` object (user-facing license-revenue endpoints) alongside `admin_router` (admin prefix). Both are included without conditional guards. There is no pattern in the existing codebase for removing individual endpoints from a router by environment — the preferred pattern observed elsewhere (e.g., mock billing endpoints) is to gate the service call body behind `S.dev_mode` or `require_admin_or_root`.

The other two endpoints on the same router that share this pattern — `register-license` (line 107) and `revoke-license` (line 127) — have the same auth gap. `register-license` accepts `licensor_id` as a body parameter (line 117), meaning a regular user can register a license claiming to be any licensor, which would then entitle that licensor to future revenue splits. `revoke-license` (line 132-137) accepts any `content_id`/`issued_license_id` pair without verifying ownership, allowing any user to revoke another creator's license. Both are in scope for the same fix but outside the formal title of GAP-0296.

**Dev vs prod behaviour today:** Identical. The endpoint is reachable in both environments and produces real wallet and ledger state.

**Service layer audit:** `process_revenue_split` in `app/services/license_revenue.py:82` contains no internal privilege check. It calls `list_licenses_for_content` (a read), then `_process_fixed_fee` and a revenue/profit loop, each calling `apply_wallet_delta` and `new_ledger_entry` from `app/services/billing_shared.py`. Both helpers write directly to the billing DynamoDB table. The service was designed as an internal function (called by billing hooks) and correctly assumes its callers have already validated authorization. The gap is entirely at the router layer.


## 3. Impact / Exploit / Blast Radius

**Who is affected:** All users on any environment where the platform is running.

**Concrete exploit walkthrough:**

1. Attacker Alice authenticates normally and obtains session cookies with CSRF token.
2. Alice discovers (or guesses) a `content_id` that has active licenses.
3. Alice posts:
   ```
   POST /ui/licenses/revenue/process-split
   {
     "content_id": "vid_abc123",
     "licensee_id": "alice_user_id",
     "source_amount_cents": 1000000,
     "source_txn_id": "fake_txn_9999"
   }
   ```
4. The service fetches all active licenses for `vid_abc123`, calculates splits (up to the 80% safety cap), and credits each licensor's wallet with synthetic earnings.
5. Licensors now have inflated wallet balances they can withdraw. Platform revenue records are corrupted.

**Worst case:**
- Arbitrary inflation of any licensor's wallet balance without a real payment source.
- `source_txn_id` is stored as-is; there is no FK or idempotency check against the actual billing ledger, so the attacker can replay with a new `source_txn_id` on every call.
- The safety cap of 80% (`SAFETY_CAP_PCT = 80`, `app/services/license_revenue.py:23`) limits each call's maximum transfer to 80% of the stated `source_amount_cents`, but there is no rate limit or per-user cap on calls.
- A fully automated attack could drain the platform's treasury through repeated synthetic splits at the maximum ceiling.

**Data integrity:** Every ledger entry written by this path has `source_type` and `source_txn_id` set to caller-controlled values, making forensic reconstruction of legitimate vs synthetic activity difficult.

**Compliance:** Fabricated ledger entries could trigger incorrect tax obligations (1099s, etc.) for licensors who receive synthetic revenue.

**Blast radius:** HIGH — affects any content with active licenses; monetary impact scales with platform size.


## 4. Fix Design (code-level)

### Option A (preferred): Admin/root gate + dev_mode flag

Gate the endpoint so that in production it is only callable by admins and root users; in dev mode it remains callable by any authenticated user for testing convenience.

```python
# app/routers/license_revenue.py

from app.auth.deps import AuthenticatedUser, get_authenticated_user
from app.auth.roles import Role
from app.core.settings import S

@router.post("/process-split")
async def process_split(
    body: dict,
    ctx: dict = Depends(require_ui_session),
    user: AuthenticatedUser = Depends(get_authenticated_user),
):
    """Trigger revenue split processing for a content item.

    In production: restricted to admin/root users only.
    In dev mode: available to any authenticated user for testing.
    """
    if not S.dev_mode and user.role not in {Role.ADMIN, Role.ROOT}:
        raise HTTPException(403, "Admin or root required")
    splits = svc.process_revenue_split(
        content_id=body["content_id"],
        licensee_id=body.get("licensee_id", ctx["user_sub"]),
        source_type=body.get("source_type", "tip"),
        source_amount_cents=int(body["source_amount_cents"]),
        source_txn_id=body.get("source_txn_id", "test_txn"),
        currency=body.get("currency", "usd"),
    )
    return {"ok": True, "splits": splits}
```

The same pattern applies to `register-license` (line 107) and `revoke-license` (line 127) which are similarly unguarded test-convenience endpoints.

### Option B (more restrictive): Remove from production router entirely

Before choosing an option, note that `register-license` and `revoke-license` should receive the same treatment. `register-license` additionally needs a licensor-ownership check: if a non-admin caller provides a `licensor_id` different from their own `user_sub`, that should be rejected even in dev mode unless they are admin/root. The fix should enforce `licensor_id == ctx["user_sub"]` or admin override.



Move `process-split`, `register-license`, and `revoke-license` to a dedicated `dev_router` that is only registered when `S.dev_mode` is `True`:

```python
# app/routers/license_revenue.py
dev_router = APIRouter(prefix="/ui/licenses/revenue", tags=["license-revenue-dev"])

@dev_router.post("/process-split")
async def process_split(body: dict, ctx: dict = Depends(require_ui_session)):
    ...  # existing body
```

```python
# app/main.py — conditional registration
if S.dev_mode:
    app.include_router(license_revenue.dev_router)
```

Option B provides stronger isolation but breaks any legitimate admin use of the endpoint in production. Option A is preferred because it preserves admin utility while blocking regular users.

### Dev/prod parity (SECOPS-007)

The fix uses `S.dev_mode` as a runtime flag (read from `DEV_MODE` environment variable, `app/core/settings.py:273`). In local dev (`DEV_MODE=1`, the default), any authenticated session can call the endpoint. In production (`DEV_MODE=0`), only `Role.ADMIN` or `Role.ROOT` can. Both environments follow the same code path — no separate mock branch is introduced. This satisfies the SECOPS-007 requirement that dev and prod parity is maintained through flag selection rather than code forking.

### Backward compatibility

No model or table changes required. The endpoint signature is unchanged. Callers that are already admin/root (E2E test admin session, `e2e_charlie@test.local`) continue to work unchanged in both dev and production. Callers that are regular users (`e2e_alice@test.local`, `e2e_bob@test.local`) will receive HTTP 403 in production mode and continue to work in dev mode.

### Migration

No migration needed. The ledger entries written by previous unauthorized calls remain in DynamoDB. A one-time audit query against the `LEDGER` table for records with `source_txn_id = "test_txn"` (or containing "test") should be run to identify and reverse any synthetic entries already present.

No dedicated E2E spec is needed for this endpoint; it is an internal testing tool. Document in API spec that the endpoint is admin-only in production.

### Audit query for existing synthetic entries

After deploying the fix, run the following DynamoDB scan to identify billing ledger entries that may have been written by unauthorized callers:

```python
# scripts/audit_synthetic_splits.py
import boto3
from boto3.dynamodb.conditions import Attr

ddb = boto3.resource("dynamodb", endpoint_url="http://localhost:8001")
table = ddb.Table("billing")
resp = table.scan(
    FilterExpression=Attr("source_txn_id").begins_with("test_txn")
    | Attr("source_txn_id").eq("test_txn"),
    ProjectionExpression="pk, sk, source_txn_id, amount_cents, created_at, user_sub",
)
for item in resp.get("Items", []):
    print(item)
```

Any entries found with `source_txn_id = "test_txn"` (the default value hard-coded in the endpoint body) are likely synthetic and should be reversed with compensating ledger entries. Real callers going through tip or unlock flows generate UUIDs for `source_txn_id`, not the literal string `"test_txn"`.

### Rollout

- **Effort:** S (small — single guard added in one function; companion fixes for `register-license` and `revoke-license` are equally small)
- **Risk:** LOW — only blocks unauthorized callers; all admin/root callers and dev-mode callers are unaffected
- **Sequencing:** (1) Deploy backend role check; (2) Run audit script for synthetic entries; (3) Reverse any found with compensating ledger entries
- **Rollback:** Revert the role check; no DB migration needed
