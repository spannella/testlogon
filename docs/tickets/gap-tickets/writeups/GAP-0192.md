# GAP-0192: `/receipts/zip` bulk export endpoint not implemented — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code in
> `app/routers/consumer_tax_documents.py`, `app/services/consumer_tax_documents.py`,
> `app/services/receipts.py`, and `app/routers/invoices.py`.

## 1. Summary & Classification

**Bug / Gap**: The FIN-004 spec requires a `GET /ui/tax-documents/receipts/zip` endpoint
that accepts `date_from` and `date_to` query parameters, fetches individual invoice/receipt
PDFs for every transaction in that range, bundles them into a ZIP archive, and streams the
archive to the browser as a download. No such endpoint exists anywhere in the codebase.

**Claim verdict**: Confirmed. A full-text search of
`app/routers/consumer_tax_documents.py`, `app/routers/invoices.py`,
`app/services/consumer_tax_documents.py`, and `app/services/receipts.py` returns no
matches for `zip`, `bulk_export`, `export_receipts`, or `ZipFile`.

**Severity**: HIGH — FIN-004 source ticket.
**Status**: Open.
**Owning area**: Tax Documents / Billing.
**Impact**: Users cannot bulk-export their purchase receipts for a tax filing period.
Finance/tax teams that need to submit receipts for reimbursement or audit are forced to
download individual PDFs one at a time, which is impractical for users with hundreds of
transactions. This is a core deliverable of FIN-004.

**Related tickets**: GAP-0191 (cart reminders), SECOPS-007 (dev/prod parity).

---

## 2. Current-State Investigation (root cause)

### What is built for FIN-004

`app/routers/consumer_tax_documents.py` (`consumer_tax_documents_router`, prefix
`/ui/tax-documents`, registered in `app/main.py`) has six endpoints:

| Endpoint | Purpose |
|---|---|
| `GET /summary` | Earnings summary for date range |
| `GET /summary/pdf` | Summary PDF download |
| `GET /comparison` | Year-over-year comparison |
| `GET /history` | List of generated tax documents |
| `POST /generate` | Generate a new annual tax document |
| `GET /document/{year}/pdf` | Download one year's PDF |

`app/routers/invoices.py` (`invoices_router`, prefix `/ui/invoices`) has four endpoints
for individual invoice operations: list, get, download PDF, email. Neither router contains
a bulk ZIP export endpoint.

`app/services/receipts.py` provides `get_or_create_receipt(user_sub, txn_id)` which
renders a single PDF for one transaction. `_render_pdf` at `app/services/receipts.py:53`
is a generic PDF builder. There is **no function** that iterates across a date range and
bundles receipts.

`app/services/consumer_tax_documents.py` imports `_render_pdf` from receipts for its
own PDF generation but likewise has no ZIP-related logic.

### Why it is missing

The FIN-004 ticket specifies the endpoint as part of a "bulk export" phase. The
gap audit in the FIN-004 spec confirms the endpoint is required but it was not
included in `docs/tickets/writeups/` (no FIN-004.md exists in the writeups directory).
The developer who implemented FIN-004 built the individual-PDF download path
(`GET /document/{year}/pdf`) but left the bulk ZIP path unimplemented — likely
because it requires a dependency on Python stdlib `zipfile` and per-receipt S3 fetches
that add latency and complexity beyond the single-document path.

### `app/services/receipts.py` — relevant context

`app/services/receipts.py:199–213` provides `get_or_create_receipt(user_sub, txn_id)`
which generates a single receipt PDF and uploads it to S3 (via
`upload_billing_receipt`). The `_render_pdf` function at line 53 builds a
minimal valid PDF from a list of text lines. Both functions are already tested by
existing billing tests and are the correct foundation for the ZIP export — there is no
need to introduce a new PDF library.

### Runtime behaviour today

`GET /ui/tax-documents/receipts/zip?date_from=...&date_to=...` returns HTTP 404 because
FastAPI finds no matching route. No 501 / 503 is returned; the router simply does not
register the path.

## 3. Impact / Exploit / Blast Radius

**User impact**: Bulk export is a common workflow requirement during tax season. Users
with 50–500 transactions cannot efficiently assemble a receipt package for an accountant
or expense report. This is a regression from an expected FIN-004 feature.

**Financial impact**: Nil beyond user frustration and potential support tickets.

**Security / exploit**: No exploit is implied. The missing endpoint is purely additive.

**Availability concern**: The implementation must stream the ZIP and avoid materialising
the entire archive in memory. A naive in-memory approach for a user with 500 receipts
(each ~5 KB) would allocate ~2.5 MB per request, which is acceptable; for larger PDFs
(say 50 KB each) this reaches 25 MB. The fix should page through transactions and use
`zipfile.ZipFile` with `io.BytesIO` or direct streaming. Very large exports (>500
transactions) should be capped or paginated, with a `max_count` guard.

## 4. Fix Design (code-level)

### 4.1 Service function (`app/services/consumer_tax_documents.py`)

Add the following function. It reuses `app/services/receipts.get_or_create_receipt`
for per-receipt PDF generation and builds the archive with Python stdlib `zipfile`:

```python
import io
import zipfile

MAX_ZIP_RECEIPTS = 500   # guard against runaway memory


def export_receipts_zip(
    *,
    user_sub: str,
    date_from: int,
    date_to: int,
) -> bytes:
    """Collect all purchase transactions in [date_from, date_to] for user_sub,
    generate a receipt PDF for each one, and return them bundled as a ZIP archive.

    Raises ValueError if no transactions are found or the range exceeds
    MAX_ZIP_RECEIPTS items (caller should return 422).
    """
    from app.services.purchase_history import list_transactions_range
    from app.services.receipts import get_or_create_receipt

    txns = list_transactions_range(user_sub, date_from=date_from, date_to=date_to)
    if not txns:
        raise ValueError("no_transactions:No transactions found in the specified range")
    if len(txns) > MAX_ZIP_RECEIPTS:
        raise ValueError(
            f"too_many_transactions:Date range contains {len(txns)} transactions "
            f"(max {MAX_ZIP_RECEIPTS}). Please narrow the range."
        )

    buf = io.BytesIO()
    with zipfile.ZipFile(buf, mode="w", compression=zipfile.ZIP_DEFLATED) as zf:
        for txn in txns:
            txn_id = txn["txn_id"]
            try:
                receipt = get_or_create_receipt(user_sub, txn_id)
                pdf_url = receipt.get("receipt_url")
                if not pdf_url:
                    continue
                # Fetch PDF bytes from S3 / mock S3
                pdf_bytes = _fetch_pdf_bytes(pdf_url)
                zf.writestr(f"receipt_{txn_id}.pdf", pdf_bytes)
            except Exception:
                logger.warning("export_receipts_zip: skipped txn %s", txn_id)
    buf.seek(0)
    return buf.read()


def _fetch_pdf_bytes(url: str) -> bytes:
    """Fetch a receipt PDF from S3 (real or mock) by URL."""
    if S.dev_mode and "/mock/s3/" in url:
        # Dev: re-derive the S3 key from the mock URL and fetch via boto3
        # URL shape: /mock/s3/{bucket}/{key}
        parts = url.split("/mock/s3/", 1)[1].split("/", 1)
        bucket, key = parts[0], parts[1]
        resp = _s3.get_object(Bucket=bucket, Key=key)
        return resp["Body"].read()
    # Prod: presigned URL path — re-fetch using the path directly
    import urllib.request
    with urllib.request.urlopen(url, timeout=10) as r:
        return r.read()
```

Note: `list_transactions_range` is assumed to exist in
`app/services/purchase_history.py`; if only `get_transaction_item` is available, the
function should query `T.billing` for `LEDGER#` sk-prefixed rows in the date range
using the same date-range pattern used by `consumer_tax_documents._compute_credits`.

### 4.2 Router endpoint (`app/routers/consumer_tax_documents.py`)

Add to `consumer_tax_documents_router` after the `download_document_pdf` endpoint
(after line 171):

```python
from datetime import datetime, timezone as _tz


@consumer_tax_documents_router.get("/receipts/zip")
def export_receipts_zip_endpoint(
    date_from: int = Query(..., description="Start of range (Unix timestamp, seconds)"),
    date_to: int = Query(..., description="End of range (Unix timestamp, seconds)"),
    session: Dict[str, str] = Depends(require_ui_session),
) -> Response:
    """Download all receipts for a date range as a ZIP archive.

    Max 500 receipts per request.
    """
    _ensure_enabled()
    if date_from >= date_to:
        raise HTTPException(
            status_code=422, detail="date_from must be before date_to"
        )
    try:
        zip_bytes = svc.export_receipts_zip(
            user_sub=session["user_sub"],
            date_from=date_from,
            date_to=date_to,
        )
    except ValueError as exc:
        code, _, message = str(exc).partition(":")
        raise HTTPException(status_code=422, detail={"code": code, "message": message or code})

    from_dt = datetime.fromtimestamp(date_from, tz=_tz.utc).strftime("%Y%m%d")
    to_dt = datetime.fromtimestamp(date_to, tz=_tz.utc).strftime("%Y%m%d")
    filename = f"receipts-{from_dt}-to-{to_dt}.zip"

    return Response(
        content=zip_bytes,
        media_type="application/zip",
        headers={
            "Content-Disposition": f'attachment; filename="{filename}"',
            "Cache-Control": "no-store",
        },
    )
```

### 4.3 Dev/prod parity (SECOPS-007)

Receipt PDFs are stored in S3. In dev the S3 backend is moto (in-process, intercepted
at the botocore layer by `app/core/dev_s3.py`). The `_s3` client in
`app/services/consumer_tax_documents.py` (`_s3 = s3_client()` at line 42) is already
wired via `app/core/aws_clients.py` which reads `S.kms_endpoint_url` /
`S.aws_endpoint_url` and routes to the correct endpoint. No additional dev-path
branching is required: `get_or_create_receipt` already uses the same S3 client and
functions correctly in dev.

The `_fetch_pdf_bytes` helper above adds one dev-mode branch (`if S.dev_mode and "/mock/s3/" in url`)
so that the mock URL path (which is an internal HTTP path, not a real S3 URI) is
translated back to a boto3 `get_object` call. In prod, URLs are presigned S3 URLs
that can be fetched directly.

**Feature flag**: The endpoint is gated behind `_ensure_enabled()` which checks
`S.tax_documents_enabled` (default `True` from `.env.local.example`). No additional
flag is needed; disabling `TAX_DOCUMENTS_ENABLED` suppresses the endpoint in both
environments.

### 4.4 Alternatives considered

- **Stream the ZIP instead of buffering**: FastAPI's `StreamingResponse` could yield
  ZIP chunks incrementally. Rejected for now because individual receipts must be
  fetched from S3 one by one; there is no performance advantage over buffering a
  ~2–25 MB archive. Streaming can be added later if needed.
- **Background job / async approach**: Generating a zip in a background task and
  providing a download link is more scalable but adds a job queue dependency. Ruled
  out for an M-effort ticket.
- **Separate `receipts` router**: The existing `consumer_tax_documents_router` is the
  natural home for this endpoint given its prefix `/ui/tax-documents`.

### Pagination / large dataset design note

For users with more than 500 transactions the endpoint returns 422. A future
enhancement could accept `date_from` / `date_to` ranges capped to 90-day windows
(reducing the maximum per call) and expose a paginated batch endpoint. This is
intentionally deferred for the initial M-effort implementation.

### Observability

Log at `INFO` level: `export_receipts_zip: user=%s range=[%d,%d] count=%d skipped=%d`.
Any S3 fetch failure increments a `receipts.zip.fetch_error` counter.

### Rollout

- **Effort**: M (2–3 days: service function + endpoint + tests + frontend button).
- **Migration**: None; the endpoint is purely additive.
- **Rollback**: Remove or 501-stub the endpoint; no data is modified.
- **Risk**: MEDIUM — the in-memory ZIP approach could consume significant memory for
  a user with many large receipts. Enforce `MAX_ZIP_RECEIPTS = 500` guard and add
  an upper-bound on `date_to - date_from` (e.g., one calendar year) to limit scope.
- **Sequencing**: No hard dependencies. Can be shipped independently of other FIN-004
  gaps.
