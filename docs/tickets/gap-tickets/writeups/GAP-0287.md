# GAP-0287: Document file bytes are read from the multipart upload but never stored in S3 — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/routers/kyc_partner_api.py`
> (lines 196–212) and `app/services/kyc_partner_api.py` (lines 464–510).

## 1. Summary & Classification

**Plain-English statement**: When a partner calls `POST /api/v1/kyc/applications/{id}/documents`,
the router reads the uploaded file bytes from the multipart form (`contents = await file.read()`),
records file metadata (document type, MIME type, filename, size) in DynamoDB, and then
**discards the bytes**. The binary content is never written to S3. There is no way to
retrieve the document afterwards. A downstream KYC reviewer cannot view or verify the
uploaded identity document because it does not exist anywhere in durable storage.

- **Severity**: HIGH — data loss; submitted KYC evidence is silently discarded
- **Source ticket**: KYC-021
- **Owning area**: KYC Platform / Partner Integrations
- **Status**: Open
- **Claim accuracy**: Confirmed exactly. Lines 196–204 of `app/routers/kyc_partner_api.py`
  read the bytes then pass only metadata (no `contents`) to `svc.upload_document()`.
  `app/services/kyc_partner_api.py` `upload_document()` (lines 464–510) accepts no `bytes`
  parameter and calls no S3 API.

**Impact in one line**: Every document uploaded through the partner API is silently lost
— KYC cases submitted by external partners can never be reviewed, creating a compliance
and data-integrity gap.

**Related tickets**: GAP-0286 (no rate limiting on the same upload endpoint),
KYC-021 write-up; contrast with `app/services/kyc_document_verification.py` (lines 185–202)
which correctly stores documents to S3 for the non-partner KYC flow.

## 2. Current-State Investigation (root cause)

### Router — bytes read but not forwarded

`app/routers/kyc_partner_api.py`, lines 196–212:

```python
# line 196
contents = await file.read()          # ← bytes read here …
result = svc.upload_document(
    principal,
    application_id,
    document_type=document_type,
    file_type=str(file.content_type or "application/octet-stream"),
    filename=str(file.filename or ""),
    size_bytes=len(contents),          # ← only the length is forwarded
)
# `contents` is never used again — it is dropped when the function returns
```

The `size_bytes=len(contents)` parameter passes only the file size. The actual bytes are
not forwarded to the service layer.

### Service layer — no S3 call, no bytes parameter

`app/services/kyc_partner_api.py`, `upload_document()` signature (line 464):

```python
def upload_document(
    principal: Dict[str, Any],
    application_id: str,
    *,
    document_type: str,
    file_type: str,
    filename: str = "",
    size_bytes: int = 0,          # ← no `contents: bytes` parameter
) -> Dict[str, Any]:
```

The function appends a document metadata dict to the DynamoDB `documents` list on the
submission record (lines 494–499) but has no `s3_key` field and no boto3 S3 call.

### How the existing internal KYC flow stores documents

`app/services/kyc_document_verification.py` (lines 185–202) shows the correct pattern for
non-partner uploads:

```python
s3_key = f"{S.kyc_documents_s3_prefix}{document_id}/{safe_name}"
# …
s3_client().put_object(
    Bucket=S.kyc_documents_bucket,
    Key=s3_key,
    Body=file_bytes,
    ContentType=content_type,
)
```

The relevant S3 settings already exist in `app/core/settings.py`:
- `S.kyc_documents_bucket` (default `"local-uploads"`)
- `S.kyc_documents_s3_prefix` (default `"kyc-documents/"`)

The moto S3 mock is active in dev mode (started in-process by `app/core/dev_s3.py`), so
no extra infrastructure is needed for local development or offline tests.

### Comparison with the internal document verification flow

`app/services/kyc_document_verification.py` (lines 185–202) shows the expected pattern:
the bytes are received from the caller, a `document_id` is generated, an S3 key is
constructed as `f"{S.kyc_documents_s3_prefix}{document_id}/{safe_name}"`, `put_object`
is called, and the key is stored on the DynamoDB record. The residency document service
(`app/services/kyc_residency.py`, line 342) and liveness service both follow the same
three-step pattern. The partner API is the only upload path that skips the S3 write.

The settings infrastructure is already present and functional: `S.kyc_documents_bucket`
(default `"local-uploads"`) and `S.kyc_documents_s3_prefix` (default `"kyc-documents/"`)
are defined at `app/core/settings.py` lines 1214–1215. The `s3_client()` helper is at
`app/core/aws_clients.py` line 114 and resolves to the moto mock in dev mode. No new
configuration or table changes are required — only the two-change fix below.

### DynamoDB record — no `s3_key` field

The document dict stored at lines 486–493:

```python
doc = {
    "document_id": document_id,
    "document_type": normalized_type,
    "file_type": str(file_type or "application/octet-stream"),
    "filename": str(filename or ""),
    "size_bytes": int(size_bytes or 0),
    "uploaded_at": ts,
    # ← no s3_key, no s3_bucket
}
```

Without `s3_key` the document cannot be retrieved even if the bytes had been stored.

## 3. Impact / Exploit / Blast Radius

### Data loss

A partner integrating the KYC partner API follows the documented flow:

1. `POST /api/v1/kyc/applications` → creates draft case
2. `POST /api/v1/kyc/applications/{id}/documents` with `id_front` (JPEG, ~800 KB) →
   receives `{"document_id": "doc_…", "document_type": "id_front"}` with HTTP 201
3. Partner assumes document is stored. Calls `POST /applications/{id}/submit`.
4. KYC reviewer opens the case — the document viewer shows "No documents attached to this
   case" because `files_ref` in the admin detail response is populated from the underlying
   KYC case's S3 references, not from the partner submission's orphaned metadata.

The partner has no feedback that the upload failed (HTTP 201 is returned). Data loss is
silent and systematic.

### Compliance

In jurisdictions requiring document retention for AML / KYC compliance (FATF, EU AMLD5,
US BSA), permanent loss of identity documents submitted during onboarding creates a
regulatory exposure. The platform may be unable to demonstrate due diligence if audited.

### Blast radius

Every document uploaded through the partner API route since the feature was deployed is
affected. There is no partial failure — 100% of partner-API document uploads result in
discarded bytes. Internal KYC uploads (non-partner flow) are not affected.

## 4. Fix Design (code-level)

### Step 1 — Add `contents: bytes` parameter to `svc.upload_document()` and store in S3

Modified `app/services/kyc_partner_api.py`, `upload_document()`:

```python
def upload_document(
    principal: Dict[str, Any],
    application_id: str,
    *,
    document_type: str,
    file_type: str,
    filename: str = "",
    size_bytes: int = 0,
    contents: bytes = b"",          # ← NEW
) -> Dict[str, Any]:
    partner_id = _partner_id(principal)
    normalized_type = str(document_type or "").strip().lower()
    if normalized_type not in _ALLOWED_DOCUMENT_TYPES:
        raise HTTPException(
            status_code=400,
            detail={
                "code": "kyc_api_invalid_document_type",
                "message": "Document type must be one of: " + ", ".join(sorted(_ALLOWED_DOCUMENT_TYPES)),
            },
        )
    item = _require_submission(partner_id, application_id)
    ts = now_ts()
    document_id = f"doc_{uuid.uuid4().hex[:16]}"

    # ── Store bytes to S3 ────────────────────────────────────────
    s3_key = (
        f"kyc-api-docs/{partner_id}/{application_id}/"
        f"{document_id}/{document_type}"
    )
    if contents:
        from app.core.aws_clients import s3_client
        from app.core.settings import S
        try:
            s3_client().put_object(
                Bucket=S.kyc_documents_bucket,
                Key=s3_key,
                Body=contents,
                ContentType=str(file_type or "application/octet-stream"),
            )
        except Exception:
            import logging
            logging.getLogger(__name__).warning(
                "kyc_partner_api: S3 put_object failed for %s", s3_key
            )
            raise HTTPException(
                status_code=502,
                detail={"code": "kyc_api_storage_error", "message": "Document storage failed"},
            )

    doc = {
        "document_id": document_id,
        "document_type": normalized_type,
        "file_type": str(file_type or "application/octet-stream"),
        "filename": str(filename or ""),
        "size_bytes": int(size_bytes or 0),
        "s3_key": s3_key,                    # ← NEW
        "s3_bucket": S.kyc_documents_bucket,  # ← NEW
        "uploaded_at": ts,
    }
    # … remainder unchanged
```

### Step 2 — Forward `contents` from the router

`app/routers/kyc_partner_api.py`, lines 196–204, becomes:

```python
contents = await file.read()
result = svc.upload_document(
    principal,
    application_id,
    document_type=document_type,
    file_type=str(file.content_type or "application/octet-stream"),
    filename=str(file.filename or ""),
    size_bytes=len(contents),
    contents=contents,             # ← NEW
)
```

### Step 3 — Add a download endpoint

Without a download endpoint the stored bytes are inaccessible via the API. Add to the
router:

```python
@kyc_partner_api_router.get("/applications/{application_id}/documents/{document_id}")
async def download_document(
    application_id: str,
    document_id: str,
    principal: Dict[str, Any] = Depends(require_api_key_principal),
):
    svc.require_scope(principal, "kyc:read")
    return svc.get_document_download_url(principal, application_id, document_id)
```

The service implementation uses `s3_client().generate_presigned_url(...)` with a 300-second
expiry, following the pattern already established in the file-manager service.

### Dev/Prod parity (SECOPS-007)

The moto S3 mock is started in-process by `app/core/dev_s3.py` whenever `S.dev_mode`
is true. The same `s3_client()` call resolves to the moto endpoint in dev and real AWS
S3 in production. No separate mock path is needed. Offline pytest tests use the moto
`mock_aws` context manager (same as `tests/conftest.py`).

The S3 bucket (`S.kyc_documents_bucket`, default `"local-uploads"`) is created by
`scripts/local-ddb-init.py` for local dev; the production bucket is provisioned via
infrastructure-as-code.

### File size limit

Add a guard before the S3 write:

```python
_MAX_DOCUMENT_BYTES = int(os.environ.get("KYC_API_MAX_DOCUMENT_BYTES", str(25 * 1024 * 1024)))

if len(contents) > _MAX_DOCUMENT_BYTES:
    raise HTTPException(
        status_code=413,
        detail={"code": "kyc_api_document_too_large", "message": "Document exceeds 25 MB limit"},
    )
```

### Backward compatibility / migration

Existing DynamoDB document records for previously-uploaded (now-lost) documents have no
`s3_key`. A migration script should mark such records with `status: "s3_missing"` so
that the admin UI can surface them as requiring re-upload rather than silently showing
empty document viewers. No DynamoDB table schema changes are required (no new GSIs).

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline — fails before fix, passes after)

```python
# tests/test_kyc_partner_api_document_storage.py
import io
import pytest
from moto import mock_aws
import boto3

@mock_aws
def test_upload_document_stores_bytes_in_s3(test_client, kyc_partner_principal, sample_application_id):
    """Document bytes must be persisted to S3 after upload."""
    # Set up moto S3 bucket
    s3 = boto3.client("s3", region_name="us-east-1")
    s3.create_bucket(Bucket="local-uploads")

    file_content = b"fake_jpeg_bytes_for_testing_12345"
    r = test_client.post(
        f"/api/v1/kyc/applications/{sample_application_id}/documents",
        files={"file": ("id_front.jpg", io.BytesIO(file_content), "image/jpeg")},
        data={"document_type": "id_front"},
        headers={
            "Authorization": "ApiKey testkey",
            "Idempotency-Key": "doc-upload-001",
        },
    )
    assert r.status_code == 201
    body = r.json()
    doc_id = body["document_id"]

    # Verify the object exists in S3
    objects = s3.list_objects_v2(Bucket="local-uploads", Prefix="kyc-api-docs/")
    keys = [obj["Key"] for obj in objects.get("Contents", [])]
    assert any(doc_id in k for k in keys), (
        f"Expected S3 key containing {doc_id}, found: {keys}"
    )
    # Verify content matches
    matching_key = next(k for k in keys if doc_id in k)
    retrieved = s3.get_object(Bucket="local-uploads", Key=matching_key)
    assert retrieved["Body"].read() == file_content

@mock_aws
def test_upload_document_returns_s3_key_in_metadata(test_client, kyc_partner_principal, sample_application_id):
    """The document record in DynamoDB must include s3_key after upload."""
    s3 = boto3.client("s3", region_name="us-east-1")
    s3.create_bucket(Bucket="local-uploads")

    r = test_client.post(
        f"/api/v1/kyc/applications/{sample_application_id}/documents",
        files={"file": ("selfie.jpg", io.BytesIO(b"img"), "image/jpeg")},
        data={"document_type": "selfie"},
        headers={"Authorization": "ApiKey testkey", "Idempotency-Key": "doc-upload-002"},
    )
    assert r.status_code == 201
    # Retrieve the application and check that documents list has s3_key
    app_r = test_client.get(
        f"/api/v1/kyc/applications/{sample_application_id}",
        headers={"Authorization": "ApiKey testkey"},
    )
    assert app_r.status_code == 200
    docs = app_r.json()["documents"]
    assert any(d.get("s3_key") for d in docs), "s3_key should be present on uploaded document"
```

**Before fix**: `test_upload_document_stores_bytes_in_s3` fails with `AssertionError:
Expected S3 key containing doc_…, found: []`.
**After fix**: Both tests pass.

### Idempotency and the S3 interaction

The document upload endpoint already has idempotency key support. When a partner retries
an upload (same `Idempotency-Key` + same body fingerprint), `check_idempotency` returns
the cached 201 response and the handler returns early — the `await file.read()` line is
reached but `svc.upload_document()` is not called, so no duplicate S3 write occurs.
This is correct behaviour. However, the fingerprint currently uses only `document_type`
and `filename` (line 186–188 of the router), not the file bytes. If a partner retries
with the same filename but different content (e.g., a re-scan of the document), the
idempotency cache incorrectly returns the original response without storing the new bytes.
The fingerprint should include a hash of `contents` to distinguish byte-level changes:

```python
fingerprint = svc._body_fingerprint({
    "application_id": application_id,
    "document_type": document_type,
    "filename": file.filename,
    "content_sha256": hashlib.sha256(contents).hexdigest(),  # ← add this
})
```

This change should be made alongside the S3 storage fix.

3. Add the download endpoint.
