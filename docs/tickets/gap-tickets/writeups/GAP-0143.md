# GAP-0143: No Callee-Side Local Timer to Auto-Dismiss Ringing Overlay — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Gap statement**: When the callee's `ConversationView` enters the `incoming_ringing` phase (triggered by a `call.invite` SSE event), no client-side timer is set to auto-dismiss the overlay if the `call.missed` SSE event is lost, delayed, or arrives after a network hiccup. The ringing overlay remains visible indefinitely under adverse network conditions, with no self-healing.

- **Severity**: HIGH
- **Source ticket**: CALL-007
- **Status**: Open — confirmed in production code.
- **Owning area**: `frontend/src/pages/messages/ConversationView.tsx`
- **Investigation verdict**: Claim is fully confirmed. There is a caller-side 30-second timer at `ConversationView.tsx:821-829` that fires `REMOTE_DECLINE` when the caller gets no answer. There is no corresponding callee-side timer that fires `REMOTE_DECLINE` on the `incoming_ringing` phase. The frontend SSE handler for `call.missed` at line 880-884 works correctly when the event arrives, but if it does not arrive, the overlay persists.
- **Related tickets**: GAP-0142 (missing SSE fanout — the primary fix; this GAP is the belt to that suspender), CALL-007 parent.

## 2. Current-State Investigation (root cause)

### 2.1 Caller-side timer exists; callee-side timer does not

`ConversationView.tsx:821-829`:

```typescript
callTimeoutRef.current = window.setTimeout(async () => {
    dispatchCall({ type: "REMOTE_DECLINE", reason: "timeout" });
    if (res.call_id) {
        try {
            const { timeoutCall } = await import("@/api/endpoints/messaging");
            await timeoutCall(res.call_id, { reason: "no_answer" });
        } catch { /* best-effort */ }
    }
}, 30_000);
```

This fires on the **caller** side (inside `callMutation.onSuccess`, which runs only for the user who initiated the call). When the timer fires, the caller's overlay transitions to `timeout` and the HTTP timeout endpoint is called.

The callee's overlay waits for an SSE `call.missed` event. The SSE handler is at `ConversationView.tsx:880-884`:

```typescript
} else if (eventType === "call.missed") {
    if (isCurrentUserCallee) {
        dispatchCall({ type: "REMOTE_DECLINE", reason: "timeout" });
    }
}
```

This handler correctly transitions the callee's overlay to `timeout` — but only when the event arrives. Under GAP-0142 (missing fanout), no SSE event is ever sent. Even after GAP-0142 is fixed, an SSE delivery failure (network partition, browser backgrounding, connection drop) would still leave the callee ringing indefinitely.

### 2.2 Existing `useEffect` hooks for other phases

`ConversationView.tsx:746-756` handles `reconnecting` → `RECONNECT_ATTEMPT` with a 1-second timer:

```typescript
React.useEffect(() => {
    if (callMachine.phase !== "reconnecting") return;
    const timer = window.setTimeout(
        () => dispatchCall({ type: "RECONNECT_ATTEMPT" }), 1000
    );
    return () => window.clearTimeout(timer);
}, [callMachine.phase]);
```

The same pattern — a `useEffect` gated on a specific phase, setting a timer that fires a state-machine event, and cleaning up on phase change — is exactly what GAP-0143 requires for the `incoming_ringing` phase.

### 2.3 Server-side ringing timeout value

`app/core/settings.py:1149`:
```python
messaging_webrtc_call_ringing_timeout_seconds: int = int(
    os.environ.get("MESSAGING_WEBRTC_CALL_RINGING_TIMEOUT_SECONDS", "30")
)
```

Default is 30 seconds. The client timer on the caller side also uses 30 seconds (hardcoded `30_000` ms at line 829). The callee-side guard timer should fire at `ringing_timeout_ms + 2000` — i.e., 32 seconds — giving the SSE event from GAP-0142's fix 2 extra seconds to arrive before the local guard fires.

### 2.4 State machine transition for `REMOTE_DECLINE` on `incoming_ringing`

`callStateMachine.ts:105-109`:

```typescript
case "REMOTE_DECLINE": {
    if (!["incoming_ringing", "outgoing_inviting", "outgoing_ringing",
          "outgoing_connecting", "reconnecting"].includes(state.phase)) return state;
    if (event.reason === "busy")    return withPhase(state, "busy", ...);
    if (event.reason === "timeout") return withPhase(state, "timeout", ...);
    return withPhase(state, "declined", ...);
}
```

`incoming_ringing` is already an allowed source state for `REMOTE_DECLINE`. Firing `{ type: "REMOTE_DECLINE", reason: "timeout" }` from a client-side timer is therefore a no-op state-machine transition to `timeout` — clean, no new cases needed.

### 2.5 `clearCallTimeout` is caller-only

`ConversationView.tsx:739-744`:

```typescript
const clearCallTimeout = React.useCallback(() => {
    if (callTimeoutRef.current) {
        window.clearTimeout(callTimeoutRef.current);
        callTimeoutRef.current = null;
    }
}, []);
```

`callTimeoutRef` is only set in `startOutgoingCall`'s `onSuccess` handler. The callee-side timer must use a **separate** ref to avoid interference. Naming it `calleeRingTimeoutRef` avoids collisions.

## 3. Impact / Exploit / Blast Radius

**Primary UX harm**: The callee's ringing overlay (with audio/video call rings) persists indefinitely if the `call.missed` SSE event is lost. On mobile browsers, when the app is backgrounded and then foregrounded, the SSE connection may be re-established from scratch; events delivered during the background period are silently lost. The callee opens the app to find a ringing call that ended minutes ago.

**Device resource waste**: The ringing audio/video stream and the call overlay hold media permissions and UI state until the user manually dismisses (currently there is no explicit dismiss button on a ringing overlay — the only action is to accept or decline). A user who cannot dismiss the overlay is effectively locked out of the conversation view.

**Dependency on GAP-0142**: If GAP-0142 is fixed but GAP-0143 is not, the system is one SSE drop away from the same indefinite-ring bug. Defence in depth requires both fixes. If GAP-0142 is not fixed, this GAP becomes the primary (and only) protection.

**Blast radius**: All callees in all DM conversations with WebRTC calling enabled. The scenario is rare under nominal conditions (SSE is reliable in a single-server dev setup) but credible in production with load balancers, mobile clients, and transient network partitions.

## 4. Fix Design (code-level)

### 4.1 New ref for callee-side timer

Add a second ref immediately after `callTimeoutRef` at `ConversationView.tsx:94`:

```typescript
const callTimeoutRef      = React.useRef<number | null>(null);  // existing, line 94
const calleeRingTimerRef  = React.useRef<number | null>(null);  // new
```

### 4.2 New `useEffect` for `incoming_ringing` phase

Insert immediately after the existing `reconnecting` timer effect at approximately line 756:

```typescript
// GAP-0143: callee-side guard — auto-dismiss ringing if call.missed SSE is lost
const CALLEE_RING_GUARD_MS = 32_000; // ringing_timeout (30s) + 2s grace

React.useEffect(() => {
    if (callMachine.phase !== "incoming_ringing") {
        if (calleeRingTimerRef.current) {
            window.clearTimeout(calleeRingTimerRef.current);
            calleeRingTimerRef.current = null;
        }
        return;
    }
    calleeRingTimerRef.current = window.setTimeout(() => {
        // SSE event was never received — dismiss locally
        dispatchCall({ type: "REMOTE_DECLINE", reason: "timeout" });
        calleeRingTimerRef.current = null;
    }, CALLEE_RING_GUARD_MS);

    return () => {
        if (calleeRingTimerRef.current) {
            window.clearTimeout(calleeRingTimerRef.current);
            calleeRingTimerRef.current = null;
        }
    };
}, [callMachine.phase]);
```

### 4.3 Cleanup on component unmount

The existing cleanup effect at `ConversationView.tsx:758-761` calls `clearCallTimeout()`. Extend it to also clear the callee timer:

```typescript
React.useEffect(() => () => {
    clearCallTimeout();
    if (calleeRingTimerRef.current) {
        window.clearTimeout(calleeRingTimerRef.current);
        calleeRingTimerRef.current = null;
    }
    teardownCallResources(callResourcesRef.current);
}, [clearCallTimeout]);
```

### 4.4 Timer value — configurability

`CALLEE_RING_GUARD_MS = 32_000` is hardcoded in the frontend. To align with the backend setting without a runtime API call, this constant should match `messaging_webrtc_call_ringing_timeout_seconds * 1000 + 2000`. Document the coupling in a comment. Alternatively, include `ringing_timeout_ms` in the conversation object returned by `GET /messaging/conversations/{id}` so the frontend can read it dynamically — but that is scope for a follow-up; for the immediate fix the hardcoded 32-second value is correct and safe.

### 4.5 Dev/prod parity (SECOPS-007)

This is a pure frontend change. No backend path differences. The fix runs identically in both environments. No feature flag needed — the guard only fires when an SSE event is absent, which is harmless in the nominal path.

### 4.6 Interaction with GAP-0142

When GAP-0142 is also fixed, the callee timer is started on `incoming_ringing`, and in the nominal case the `call.missed` SSE event arrives within 1-2 seconds (well before the 32-second guard), dispatching `REMOTE_DECLINE`. The `useEffect` cleanup fires, clears `calleeRingTimerRef`, and the guard timer never reaches its callback. The guard only fires if the SSE event is lost or delayed by more than 32 seconds.

### 4.7 Alternatives considered

- **Show a "Dismiss" button after N seconds**: Requires additional UI state, less immediate than auto-dismiss, and still leaves the overlay open for N seconds. Rejected in favour of silent auto-dismiss (matching the `timeout` phase behaviour).
- **Poll the call state via REST every 5 seconds**: Higher server load, adds latency, and duplicates SSE semantics. Rejected.
- **Use the `online` event to trigger a refetch that detects the missed call**: Indirect, adds a full RTT, and only works when the network comes back. Rejected as primary mechanism (valid as a secondary fallback).

## 5. Testing, Verification & Rollout

### 5.1 Regression test — Jest / React Testing Library

```typescript
// src/pages/messages/__tests__/ConversationView.calleeTimer.test.tsx
import { render, act } from "@testing-library/react";
import { ConversationView } from "../ConversationView";
import { callStateReducer, createInitialCallMachineState } from "../callStateMachine";

jest.useFakeTimers();

test("callee ringing auto-dismisses after 32 seconds if no SSE event", () => {
    const { dispatchMock } = renderConversationViewWithMockedDispatch();

    // Simulate incoming call invite
    act(() => {
        dispatchMock({ type: "INCOMING_INVITE", mode: "audio", peerName: "Bob" });
    });

    // Phase is incoming_ringing — timer should be set
    act(() => { jest.advanceTimersByTime(31_999); });
    // Must NOT have fired yet
    expect(dispatchMock).not.toHaveBeenCalledWith(
        expect.objectContaining({ type: "REMOTE_DECLINE" })
    );

    // Advance past the guard
    act(() => { jest.advanceTimersByTime(2); });
    expect(dispatchMock).toHaveBeenCalledWith(
        { type: "REMOTE_DECLINE", reason: "timeout" }
    );

    // FAILS-BEFORE: no timer set → dispatchMock never called → assertion fails
    // PASSES-AFTER: timer set in useEffect → fires at 32s → assertion passes
});

test("callee timer is cancelled when SSE call.missed arrives", () => {
    const { dispatchMock, fireCallEvent } = renderConversationViewWithMockedDispatch();

    act(() => {
        dispatchMock({ type: "INCOMING_INVITE", mode: "audio", peerName: "Bob" });
    });

    // SSE event arrives at 5s
    act(() => { jest.advanceTimersByTime(5_000); });
    act(() => { fireCallEvent("call.missed"); });

    // No duplicate REMOTE_DECLINE from the guard timer
    act(() => { jest.advanceTimersByTime(30_000); });
    const declineCalls = dispatchMock.mock.calls.filter(
        ([ev]) => ev.type === "REMOTE_DECLINE"
    );
    expect(declineCalls).toHaveLength(1);  // exactly one, from SSE, not timer
});
```

### 5.4 Observability

The timer fires a local dispatch only; no backend call is made. Log the event client-side with a `console.warn` or a telemetry event: `"callee_ring_guard_fired callId=%s"` — this is a signal that the SSE event was lost and GAP-0142 may not be fully fixed.

### 5.5 Rollout

- **Effort**: S (30 minutes — one new ref, one new `useEffect`, one cleanup addition)
- **Risk**: Minimal. The new effect only activates on `incoming_ringing` and fires a `REMOTE_DECLINE` that the state machine already handles. The worst case is a false-positive dismissal if the timer fires before the callee clicks Accept — but at 32 seconds, a call that has been ringing for 32 seconds without an answer should be dismissed.
- **Rollback**: Remove the new `useEffect` and the ref. Behaviour regresses to the prior polling-based pattern.
- **Sequencing**: Can ship independently of GAP-0142 but should be shipped together with it. Ship GAP-0142 first (backend), then GAP-0143 (frontend) in the same release if possible.
