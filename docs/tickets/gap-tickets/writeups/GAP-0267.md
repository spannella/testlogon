# GAP-0267: `ByKycTier` GSI not declared in DDB init — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: KYC-009. Owning area: DynamoDB schema / KYC tier service.

## 1. Summary & Classification

**Bug**: The gap audit stated that the `ByKycTier` Global Secondary Index was not declared in
`scripts/local-ddb-init.py`, causing `list_users_by_tier()` to fail with a `ValidationException`
at runtime.

**Claim accuracy**: **Claim is INCORRECT as of current codebase.** Code inspection shows that
the `ByKycTier` GSI is already declared in `scripts/local-ddb-init.py` at **line 52**, with
the required `attr_types` for both numeric keys:

```python
TableDef(
    _resolve_table_name(S.users_table_name, "users"),
    "user_sub",
    gsi=[{"index_name": "ByKycTier", "partition_key": "kyc_tier", "sort_key": "kyc_tier_updated_at"}],
    attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"},
),
```

The GSI was added in a prior fix (not documented as a separate commit). This write-up records
the analysis, explains why the gap was valid when filed, documents the resolution, and identifies
a **residual issue** in the same vicinity: the users table query pattern in `kyc_tiers.py` uses
`Key={"user_sub": user_sub}` while other KYC services access the same users table with
`Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"}`. This key-format divergence is a live bug
that invalidates all tier reads/writes.

- **Severity**: HIGH (original gap) / CRITICAL (residual key-schema mismatch; see GAP-0023)
- **Source ticket**: KYC-009
- **Status**: GSI declaration — resolved. Key schema mismatch — open (tracked as GAP-0023).
- **Related tickets**: GAP-0023 (users table key schema mismatch), GAP-0268 (tier gating),
  GAP-0269 (auto-upgrade triggers)

## 2. Current-State Investigation (root cause)

### Original gap: ByKycTier GSI

The `list_users_by_tier` function in `app/services/kyc_tiers.py` (line 238–255) queries:

```python
resp = T.users.query(
    IndexName="ByKycTier",
    KeyConditionExpression="kyc_tier = :tier",
    ExpressionAttributeValues={":tier": tier},
    ScanIndexForward=False,
    Limit=min(limit, 100),
)
```

`kyc_tier` is an integer (e.g. `2`). Without `attr_types={"kyc_tier": "N"}` in the `TableDef`,
DynamoDB Local stores the attribute as type `String`, and a subsequent integer-keyed GSI query
raises `ValidationException: Type mismatch for key kyc_tier expected: N actual: S`. The same
issue applies to the sort key `kyc_tier_updated_at`.

**Current state**: `scripts/local-ddb-init.py` line 49–54 declares the `TableDef` with both
the GSI entry and `attr_types`. The `TableDef.attr_types` field is applied in the DDB-init
table-creation loop, which emits `AttributeDefinitions` for both `kyc_tier` and
`kyc_tier_updated_at` with type `N`. The gap is resolved.

### Residual issue: users table key schema mismatch

`kyc_tiers.py` accesses `T.users` using a single-key pattern:

```python
# get_user_kyc_tier (line 32)
item = T.users.get_item(Key={"user_sub": user_sub}).get("Item")

# upgrade_tier (line 160)
item = T.users.get_item(Key={"user_sub": user_sub}).get("Item", {})

# upgrade_tier UpdateItem (line 172)
T.users.update_item(Key={"user_sub": user_sub}, ...)
```

However, `kyc_risk_scoring._compute_country_risk` (line 335) accesses the same users table
with a composite-key pattern:

```python
resp = T.users.get_item(Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"})
```

The DDB-init definition at line 50–54 declares the users table with `partition_key="user_sub"`
only (no sort key). This means:

- `kyc_tiers.py` reads and writes correctly (single-key schema).
- `kyc_risk_scoring._compute_country_risk` reads with `{"pk": ..., "sk": ...}` — these keys
  do not exist in the single-key users table; every `get_item` returns an empty `Item`, so
  `country` defaults to `""` and the country factor always scores 30 ("Country not specified").

The users table as defined in DDB-init has only `partition_key="user_sub"` (no sort key
parameter). Profile data is stored in a separate `profiles` table (line 84:
`_resolve_table_name(S.profile_table_name, "profiles")`, `partition_key="user_sub"`). The
`kyc_risk_scoring` code is reading the wrong table or using the wrong key format. This is
tracked as GAP-0023.

### Why the GSI gap was originally valid

When the `ByKycTier` GSI was first written into `kyc_tiers.py` as a query target, the
`TableDef` for users had no `gsi=` or `attr_types=` parameters. Any call to
`list_users_by_tier` would have raised a `ResourceNotFoundException` (GSI does not exist) or
`ValidationException` (type mismatch). The fix was applied but not captured in a gap-closing
commit comment. The gap audit correctly flagged it; the subsequent fix closed the specific
GSI issue. The residual country-risk mismatch (also noted in GAP-0023) was identified
during this write-up investigation and was not part of the original gap report.

### DDB-init TableDef constructor pattern

`scripts/local-ddb-init.py` lines 28–35 show the `TableDef` dataclass:

```python
@dataclass(frozen=True)
class TableDef:
    name: str
    partition_key: str
    sort_key: Optional[str] = None
    gsi: List[Dict[str, str]] = field(default_factory=list)
    attr_types: Dict[str, str] = field(default_factory=dict)
```

`attr_types` defaults to an empty dict. Any numeric attribute used as a key (table or GSI)
must be explicitly listed here. The pattern is documented in `CLAUDE.md` under "Common
gotchas — DynamoDB numeric GSI sort keys." The `ByKycTier` GSI correctly follows this
pattern with `attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"}` at line 53.

## 3. Impact / Exploit / Blast Radius

### ByKycTier GSI (resolved)

If the GSI had remained absent, `GET /v1/kyc/tiers/admin/by-tier/{tier}` (the admin endpoint
that calls `list_users_by_tier`) would have raised an unhandled 500. The failure mode depends
on which error occurred first:

- **GSI not declared at table-creation time**: the `CreateTable` call omits the GSI.
  Subsequent `query(IndexName="ByKycTier", ...)` raises `ResourceNotFoundException` with
  message "The table does not have the specified index: ByKycTier".
- **GSI declared but `attr_types` missing**: DynamoDB Local creates the table but stores
  integer values of `kyc_tier` as type `String` (the default). A query with
  `KeyConditionExpression="kyc_tier = :tier"` where `:tier` is an integer raises
  `ValidationException: Type mismatch for key kyc_tier expected: N actual: S`.

Either way, no data loss or security exposure — operational impact only (admin tier-management
dashboard broken; the root user cannot enumerate users by tier).

### Residual country-risk factor mis-read (active)

`_compute_country_risk` in `kyc_risk_scoring.py` always reads an empty profile (wrong
table/key), so `country = ""` for all users. The factor consistently returns score 30
("Country not specified"). This means:

- High-risk-country users (score should be 100) receive only 30, under-representing their
  actual risk.
- Low-risk-country users (score should be 0) also receive 30, slightly over-representing risk.
- Combined with the absent submission hook (GAP-0266), scoring is both missing and inaccurate
  when it does run.

### Blast radius

- All `list_users_by_tier` calls before the GSI was added: broken.
- All `compute_score` calls (currently only from ID scanner and liveness call): country risk
  factor is always 30, skewing every risk score by up to ±4.5 points (0.15 weight × ±30 pts).

## 4. Fix Design (code-level)

### Fix 1 — Verify GSI + attr_types (already applied)

No code change required. Document the resolution in the DDB-init comment block:

```python
# KYC-009 / GAP-0267: ByKycTier GSI with numeric sort key for list_users_by_tier.
TableDef(
    _resolve_table_name(S.users_table_name, "users"),
    "user_sub",
    gsi=[{"index_name": "ByKycTier", "partition_key": "kyc_tier",
          "sort_key": "kyc_tier_updated_at"}],
    attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"},
),
```

### Fix 2 — Correct `_compute_country_risk` table lookup (residual GAP-0023)

In `app/services/kyc_risk_scoring.py`, `_compute_country_risk` (line 333–347) should read
from the `profiles` table (not `T.users`) and use the single-key pattern, or read from
`T.users` using `Key={"user_sub": user_sub}` for the dedicated tier/country columns:

```python
def _compute_country_risk(self, *, case_id: str, user_sub: str) -> dict:
    try:
        # Country is stored as a top-level attribute on T.users (not in the
        # composite-key "profiles" table which uses pk/sk layout).
        resp = T.users.get_item(Key={"user_sub": user_sub})
        profile = resp.get("Item", {})
        country = str(profile.get("country", "") or profile.get("nationality", "") or "").upper().strip()
    except Exception:
        country = ""
    # ... existing scoring logic unchanged
```

This aligns with `kyc_tiers.py`'s access pattern and correctly reads the `country` and
`nationality` attributes written by the registration flow.

### Dev/Prod parity (SECOPS-007)

The DDB-init script runs against DynamoDB Local in dev and against Amazon DynamoDB in prod
via the same `boto3` API. The `TableDef` is the single source of truth for both environments;
no environment-specific logic is needed. The `_compute_country_risk` fix is purely a Python
change with no AWS-environment-specific branching required.

### Backward compatibility

The GSI already exists in the running DDB Local instance (created on last `just up`). No
migration is needed for dev. In production, the GSI must be added to the live DynamoDB table
via an AWS console `CreateGlobalSecondaryIndex` backfill operation before deploying the code
that queries it. The backfill is non-breaking (read-only until complete).

### Alternatives considered — country-risk factor

**Alternative A: Read from `profiles` table using `Key={"user_sub": sub}`**. The `profiles`
table (`S.profile_table_name`) stores the structured profile including `country`. However,
inspecting `profile.py:220–227` shows the `profiles` table stores data under a nested
`item["profile"]` sub-dict, and country is not typically stored there (it lives on the
users record). Reading the right table (`T.users` with single-key) is simpler.

**Alternative B: Use `profile` service for all user data in risk scoring**. A complete
refactor of `kyc_risk_scoring.py` to call `get_profile(user_sub)` for all profile-based
factors would give a consistent access pattern. This is the right long-term direction but
is out of scope for a targeted GAP fix. The immediate fix (correcting the `get_item` key)
is sufficient to unblock accurate scoring.

### Additional residual finding — `_compute_profile_completeness` also uses wrong key

`kyc_risk_scoring._compute_profile_completeness` (lines 430–446) similarly uses
`T.users.get_item(Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"})` to check
`first_name`, `last_name`, `date_of_birth`, `email`. This key pattern returns an empty
item for the same reason as `_compute_country_risk`. All four "critical fields" are missing,
scoring 80 ("4 critical profile fields missing") for every user. This must be corrected in
the same fix as the country-risk factor: switch to `Key={"user_sub": user_sub}` and read
the relevant fields from the users record or the profiles service.

### Coordination with GAP-0266 and GAP-0270

The country-risk and profile-completeness fixes are blocking-quality corrections for the
risk-scoring engine. If GAP-0266 (submission hook) is deployed without these fixes, the
first automated risk score computed at submission time will have two systematically wrong
factors:

- `country_risk.score` = 30 for all users (wrong key pattern; no country data read).
- `profile_completeness.score` = 80 for all users (same wrong key; all 4 fields "missing").

These two factors have a combined weight of 0.20 (15% + 5%), contributing up to 22 points
of false positive risk. A genuinely low-risk user (true score ~15) would score 37 with these
bugs active, landing in the "medium" tier rather than "low", and never auto-approving.
Recommend bundling all three fixes (GAP-0266, GAP-0267 residual, GAP-0270) in a single PR.

  returns results rather than raising exceptions. Run `GET /v1/kyc/tiers/admin/by-tier/0`
  as a smoke test.
- Country-risk and profile-completeness fix: apply as part of the GAP-0266 submission hook PR.
  Both changes are isolated to `kyc_risk_scoring.py`. Effort: **S**.
- Production GSI backfill: coordinate with infra to run `CreateGlobalSecondaryIndex` on
  the live users table before deploying any code that calls `list_users_by_tier`. Estimated
