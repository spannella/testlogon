# GAP-0381: `static/ads/` directory and placeholder creative files do not exist — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. No prior investigation doc exists for this GAP.

## 1. Summary & Classification

- **Plain-English statement**: The ad placement service emits three dev-mode creative URLs — `/static/ads/placeholder_preroll.mp4`, `/static/ads/placeholder_midroll.mp4`, and `/static/ads/placeholder_overlay.png` — but the backing directory `app/static/ads/` has never been created and no placeholder files have ever been added to version control. Every request to those URLs returns HTTP 404 from FastAPI's static file handler.
- **Severity**: HIGH — the entire ad-supported video flow cannot be exercised in development. The video player has no ad creative to play for any of the three slot types (pre-roll, mid-roll, overlay), which silently breaks integration testing of VOD-018 and any E2E or manual QA that depends on seeing an ad before or during playback.
- **Source ticket**: VOD-018 (ad-supported video tier). **Status**: Open. **Owning area**: VOD / Media Pipeline.
- **Claim verification**: CONFIRMED. `app/static/` exists and contains only `index.html`, `broadcast-devtools.html`, and `uploads/`. There is no `ads/` subdirectory. The three URLs are hard-coded constants at `app/services/ad_placement.py:30,37,44`.
- **Related tickets**: GAP-0382 (impression deduplication), VOD-018.

---

## 2. Current-State Investigation (root cause)

### Static file mount

FastAPI's static file handler is mounted at application startup in `app/main.py:387-389`:

```python
static_dir = Path(__file__).resolve().parent / "static"
app.mount("/static", StaticFiles(directory=static_dir), name="static")
```

The resolved path is `/home/ubuntu/testlogon/app/static/`. `StaticFiles` will serve any file under that directory, but it will return a 404 for any path that does not correspond to an existing file.

### The missing files

`app/services/ad_placement.py:24-47` defines the module-level constant `DEV_AD_CREATIVES`:

```python
DEV_AD_CREATIVES = [
    {
        "creative_id": "dev_ad_preroll_15s",
        "type": "video",
        "duration_seconds": 15,
        "url": "/static/ads/placeholder_preroll.mp4",
        "title": "Placeholder Pre-Roll Ad",
    },
    {
        "creative_id": "dev_ad_midroll_30s",
        "type": "video",
        "duration_seconds": 30,
        "url": "/static/ads/placeholder_midroll.mp4",
        "title": "Placeholder Mid-Roll Ad",
    },
    {
        "creative_id": "dev_ad_overlay",
        "type": "image",
        "duration_seconds": 10,
        "url": "/static/ads/placeholder_overlay.png",
        "title": "Placeholder Overlay Ad",
    },
]
```

These creatives are returned by the ad slot resolution path in `get_ad_config` (called by the router at `app/routers/video_listing.py:1460`) when `S.dev_mode` is `True`. The video player frontend receives the creative object, including the `url` field, and attempts to load the media. Because `app/static/ads/` does not exist, every load request returns a 404.

### Why the directory is absent

The `app/static/` directory is a git-tracked directory checked in with only the HTML index files. The `ads/` subdirectory was specified in the VOD-018 design but was never created as part of the implementation. Git does not track empty directories, and no `setup_ubuntu.sh` step creates them. The gap went unnoticed because `record_ad_impression` can still be called via the API and the unit tests in `tests/test_ad_placement.py` do not perform HTTP-level requests for the creative assets — they call the service layer directly.

### How `get_ad_config` uses these URLs

The full resolution chain is:

1. The player calls `GET /ui/videos/{video_id}/ad-config` which is routed to `video_listing.py:1446-1467`.
2. That calls `_get_ad_config(video_id, user_sub)` which in turn calls `get_ad_config` from `app/services/ad_placement.py`.
3. `get_ad_config` resolves the ad creative for each slot. When `S.dev_mode` is `True` and no campaign override exists for the video, it falls back to `DEV_AD_CREATIVES` indexed by slot type (pre_roll → index 0, mid_roll → index 1, overlay → index 2).
4. The creative object, including the `url` field (`/static/ads/placeholder_preroll.mp4` etc.), is returned as part of the slot definition in the API response.
5. The frontend video player receives the slot URL and attempts to fetch it. The FastAPI `StaticFiles` handler resolves the path to `app/static/ads/placeholder_preroll.mp4`, which does not exist, and returns 404.

The round-trip failure is entirely silent from the perspective of the backend: no exception is raised, no log entry is written. The frontend player may suppress the 404 in its ad loader and simply skip the ad slot, or it may display an error overlay depending on the player implementation. Either way, the developer cannot observe the full ad flow.

### Runtime manifestation

- **Dev/local**: Player loads ad slot metadata correctly from `GET /{video_id}/ad-config`. The returned slot includes the creative URL. The player (or any HTTP client) then requests `/static/ads/placeholder_preroll.mp4` → 404. The pre-roll plays nothing; the player may fall through to the main content immediately, masking the ad flow entirely.
- **Production**: In production, `DEV_AD_CREATIVES` is never used — the service resolves creatives from the DynamoDB `Campaigns`/`Creatives` tables and returns real S3 URLs. The missing static files have zero production impact.

## 3. Impact / Exploit / Blast Radius

This is an **infrastructure gap** with no security or financial exposure in production. The blast radius is confined to the development and testing lifecycle:

1. **Manual QA**: Any developer who builds or tests the ad-supported video tier in dev mode will see no pre-roll, mid-roll, or overlay ad creative. The ad impression flow (which does write to DynamoDB and credit revenue) still executes in response to API calls, but the visual confirmation that an ad actually played is absent. This can cause a QA reviewer to incorrectly conclude that ads are not working.

2. **E2E / Playwright tests**: A Playwright test that navigates to an ad-supported video page and asserts that a `<video>` source is loaded will see the player attempt to fetch the placeholder URL, fail silently, and potentially render an error state. Tests checking for a non-empty `src` attribute on the ad creative element could produce false negatives.

3. **Frontend developer experience**: The video player component's ad slot integration cannot be visually verified without a workaround (manually creating files). This extends every developer's onboarding time and makes it impossible to catch player-side ad rendering regressions.

4. **Automated startup health check** (if any): If a health check or smoke test requests `/static/ads/placeholder_preroll.mp4`, it will return 404, which may trip monitoring thresholds.

There is no revenue impact, no data leak, and no security exposure.

## 4. Fix Design (code-level)

### 4.1 Create the directory and placeholder files

The fix has two parts:

**Part A — Create `app/static/ads/` and add placeholder media files.**

The simplest valid placeholder MP4 is the FFmpeg "lavfi" null output: a 1-second, 1×1-pixel black video with a silent audio track, encoded to H.264/AAC in a valid MP4 container. The resulting file is approximately 5–10 KB — small enough to commit to version control.

Generate once (not part of the running application; a developer-side one-off command):

```bash
# In the repo root
mkdir -p app/static/ads

# Minimal valid MP4: 1s, 1×1 black, silent
ffmpeg -y -f lavfi -i color=black:s=1x1:r=1 -f lavfi -i anullsrc \
  -c:v libx264 -c:a aac -t 1 -shortest \
  app/static/ads/placeholder_preroll.mp4

ffmpeg -y -f lavfi -i color=black:s=1x1:r=1 -f lavfi -i anullsrc \
  -c:v libx264 -c:a aac -t 1 -shortest \
  app/static/ads/placeholder_midroll.mp4

# Minimal valid PNG: 1×1 white pixel
python3 -c "
import struct, zlib
def mk_png():
    def chunk(name, data):
        c = struct.pack('>I', len(data)) + name + data
        return c + struct.pack('>I', zlib.crc32(c[4:]) & 0xFFFFFFFF)
    ihdr = struct.pack('>IIBBBBB', 1, 1, 8, 2, 0, 0, 0)
    idat = zlib.compress(b'\x00\xff\xff\xff')
    return b'\x89PNG\r\n\x1a\n' + chunk(b'IHDR', ihdr) + chunk(b'IDAT', idat) + chunk(b'IEND', b'')
open('app/static/ads/placeholder_overlay.png', 'wb').write(mk_png())
"
```

Both MP4 files and the PNG should be committed to the repository so that `git clone` plus `just up` produces a working dev stack with no manual steps.

**Part B — Add a `.gitkeep`-equivalent guard.**

Since the files themselves are committed, no `.gitkeep` is needed. However, add a comment in `scripts/setup_ubuntu.sh` (or the `justfile`) that documents the static assets so future contributors know they are intentional:

```bash
# In scripts/setup_ubuntu.sh (documentation comment only, no code change needed
# if files are committed):
# app/static/ads/ — dev-mode ad creative placeholders (committed to repo)
```

### 4.2 Optional: runtime assertion at startup

Add a startup check in `app/services/ad_placement.py` that warns (not raises) if any `DEV_AD_CREATIVES` URL resolves to a missing file:

```python
# In app/services/ad_placement.py, after DEV_AD_CREATIVES definition
import pathlib as _pathlib

def _warn_missing_dev_creatives() -> None:
    from app.core.settings import S
    if not S.dev_mode:
        return
    static_root = _pathlib.Path(__file__).resolve().parents[1] / "static"
    for creative in DEV_AD_CREATIVES:
        rel = creative["url"].lstrip("/")
        path = static_root / rel
        if not path.exists():
            logger.warning("dev_creative_missing: %s not found at %s", creative["url"], path)

_warn_missing_dev_creatives()
```

This makes the gap visible in the uvicorn startup log rather than silently returning 404 at request time.

### 4.3 Dev/Prod parity (SECOPS-007)

The placeholder files are gated entirely to the `S.dev_mode` code path. Production never serves from `DEV_AD_CREATIVES` — real creatives come from DynamoDB. The `app/static/` mount exists in both environments (FastAPI raises `RuntimeError` at startup if `static_dir` is missing), but in production the `ads/` subdirectory may legitimately be absent. The warning in §4.2 is guarded by `if not S.dev_mode: return`, satisfying SECOPS-007's requirement that the same code path runs in both environments without AWS-specific branching in business logic.

No feature flag is required because the placeholder directory is additive and inert in production. No migration is needed.

### Additional context: why not serve a redirect to an external CDN instead?

An alternative approach would be to change `DEV_AD_CREATIVES` to point at a publicly hosted test video (e.g., a Wikimedia Commons MP4). This was considered and rejected for two reasons:

1. **Network isolation in CI**: the dev stack runs in environments (CI, air-gapped laptops, Docker networks) where outbound HTTP to arbitrary CDN domains is blocked. A local file always works.
2. **SECOPS-007 parity**: SECOPS-007 mandates that the dev and prod paths use the same code with only the backing store differing. Pointing dev at an external CDN while prod uses S3 creates a divergent code path. Serving from `app/static/` mirrors the production pattern (where real creatives are served from S3 via presigned URLs and served through CloudFront), and the resolution logic in `get_ad_config` already handles both cases without branching.

### Note on `.gitkeep` vs. committed binary files

Some repositories use `.gitkeep` sentinel files to track otherwise-empty directories. This approach is appropriate when the directory is intended to be empty (populated at runtime by the application). In this case the files themselves must be committed, because the static file server serves them directly without any runtime generation step. Committing small binary files (5–10 KB each, totalling under 25 KB) to a code repository is standard practice for fixtures and test assets of this size.
