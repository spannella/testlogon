# GAP-0171: `AuthenticatedUser` lacks `tenant_id` field — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real file:line. No prior investigation doc; claim verified
> against live code as part of this write-up.

## 1. Summary & Classification

**Plain-English statement**: The `AuthenticatedUser` dataclass, returned by every auth
dependency and used as the identity object throughout the backend, carries no `tenant_id`
field. As a result there is no mechanism to validate that a session cookie minted for
**Tenant A** is rejected when the same cookie is replayed on **Tenant B**'s hostname. A
session is globally valid across all tenants on the same backend instance, contradicting the
isolation guarantee the multi-tenancy design (ENTERPRISE-001, section 3.5.3) requires.

- **Severity**: HIGH
- **Source ticket**: ENTERPRISE-001
- **Status**: Open
- **Owning area**: Backend / Auth / Multi-tenancy
- **Verdict**: **Confirmed** — `app/auth/deps.py` lines 125–130 define `AuthenticatedUser`
  with only `sub`, `role`, and `admin_profile`. No `tenant_id` field exists. No call site
  in `require_ui_session` (`app/services/sessions.py` lines 284–402) compares the session's
  stored tenant against `request.state.tenant_id`.
- **Related tickets**: ENTERPRISE-001 (design), GAP-0172 (suspended-tenant bypass), SECOPS-007
  (dev/prod parity requirements).

## 2. Current-State Investigation (root cause)

### The dataclass

`app/auth/deps.py` lines 125–130:

```python
@dataclass(frozen=True)
class AuthenticatedUser:
    sub: str
    role: Role = Role.USER
    admin_profile: AdminProfile = AdminProfile()
```

No `tenant_id` field. All three auth code paths — cookie JWT (line 230), Cognito Bearer
(line 248), and dev fallback (line 260) — instantiate `AuthenticatedUser` with only `sub`,
`role`, and `admin_profile`. None of them read `request.state.tenant_id`, which is set by
`TenantMiddleware` (`app/middleware/tenant.py` lines 99 and 145).

### Session creation

`app/services/sessions.py` `create_real_session` (line 404) writes session records to
DynamoDB with fields `user_sub`, `session_id`, `csrf_token`, `created_at`, etc. The session
item does **not** store the `tenant_id` that was active when the session was created.
Consequently, on a subsequent request there is nothing in the DDB record to compare against.

### The validation gap

`require_ui_session` (lines 284–402) loads the session from DynamoDB, validates CSRF, checks
TTL and revocation, then returns a dict containing `user_sub`, `session_id`, `role`, and
`ip`. No step reads `request.state.tenant_id` or compares it to anything in the session
record. The `out` dict returned at line 395 never includes `tenant_id`.

### How it manifests at runtime

With `MULTI_TENANCY_ENABLED=1`, the backend runs `TenantMiddleware` which sets
`request.state.tenant_id` per request (line 145). Cookies — the HS256 `ui_access_token`
plus the `ui_session` value — are set by `set_session_cookies` with no domain restriction
beyond the shared `.example.com` wildcard. If Alice authenticates on `tenantA.example.com`
and then sends the same cookies to `tenantB.example.com`:

1. `TenantMiddleware` resolves `tenant_id = "tenantB"` from the Host header.
2. `get_authenticated_user` decodes the `ui_access_token` cookie — it contains `sub=alice`
   minted for tenantA, but the JWT contains no `tenant_id` claim.
3. `require_ui_session` looks up `(alice, session_id)` in DynamoDB and finds the session,
   because the sessions table is not partitioned by tenant.
4. The request succeeds. Alice is now authenticated on tenantB with her tenantA session.

In dev mode (`MULTI_TENANCY_ENABLED=0`) the middleware always sets
`tenant_id = S.default_tenant_id` (line 97), so the cross-tenant attack surface does not
exist, but the missing field still means tenant-aware endpoint code can never use it.

## 3. Impact / Exploit / Blast Radius

### Exploit walkthrough

1. Attacker creates a legitimate account on `tenantA.example.com` (or obtains a
   compromised session).
2. The `ui_session` + `ui_access_token` + `ui_csrf` cookies are captured (from a logged-in
   browser, via XSS, or from a compromised device).
3. Attacker sends those cookies in a request to `tenantB.example.com/ui/me`.
4. The response returns the attacker's profile — authenticated on the wrong tenant.
5. All subsequent authenticated actions (messaging, file access, admin endpoints if the
   account happens to be ADMIN on tenantB's tables) succeed.

### Worst case

- **Data exfiltration**: Any data that `require_ui_session` gates on the wrong tenant
  becomes readable by a cross-tenant session replay.
- **Privilege escalation**: If the same `user_sub` exists in both tenants' user records with
  different roles (e.g., USER in tenantA, ADMIN in tenantB's DDB table), the role extracted
  from the JWT cookie reflects the minted value, which may differ from the tenant's stored
  role.
- **Compliance / audit trail**: Audit events logged by `audit_event` do not include
  `tenant_id` from the session, so cross-tenant activity becomes invisible in per-tenant
  audit queries.

### Scope

Active only when `MULTI_TENANCY_ENABLED=1`. The default dev setting is `0`, so this is a
production-only risk with no dev equivalent today. Affects all endpoints that use
`require_ui_session`, `get_authenticated_user`, or `require_bearer_token`.

The affected surface is large: every authenticated API endpoint in the backend uses one
of these dependencies. That includes messaging, file manager, calendar, billing, admin
endpoints, and the newsfeed — in a multi-tenant deployment, all of these would be
accessible cross-tenant with a replayed session cookie. The fix is equally broad: once
the check is added to `require_ui_session`, all downstream endpoints are protected without
further changes.

## 4. Fix Design (code-level)

### Step 1 — Add `tenant_id` to `AuthenticatedUser`

`app/auth/deps.py` lines 125–130: add the field with a safe default of `"default"`.

```python
@dataclass(frozen=True)
class AuthenticatedUser:
    sub: str
    role: Role = Role.USER
    admin_profile: AdminProfile = AdminProfile()
    tenant_id: str = "default"
```

### Step 2 — Store `tenant_id` in the session record at creation time

`app/services/sessions.py` `create_real_session` (line 404): accept an optional
`tenant_id` parameter and write it to the DDB item:

```python
def create_real_session(
    req: Request,
    user_sub: str,
    *,
    tenant_id: str = "default",
    mfa_verified_at: Optional[int] = None,
    risk_score: int = 0,
    refresh_ttl_seconds: Optional[int] = None,
) -> SessionInfo:
    ...
    item: Dict[str, Any] = {
        ...
        "tenant_id": tenant_id,
        ...
    }
```

All callers that already have the request object can derive `tenant_id` from
`getattr(request.state, "tenant_id", "default")`. The call sites are:
- `app/routers/ui_session.py` `ui_session_start` — has `req: Request`
- `app/routers/sso_saml.py` `saml_acs` and `_dev_bypass_acs` — both have `request: Request`

### Step 3 — Populate `tenant_id` in `get_authenticated_user`

In `app/auth/deps.py` `get_authenticated_user`, read the tenant from `request.state` and
attach it to the returned object. All three branches (cookie, Cognito Bearer, dev fallback)
need this addition:

```python
_tenant_id = getattr(getattr(request, "state", None), "tenant_id", None) or "default"
return AuthenticatedUser(sub=..., role=..., admin_profile=..., tenant_id=_tenant_id)
```

### Step 4 — Enforce tenant isolation in `require_ui_session`

`app/services/sessions.py` lines 331–333: after loading the session item, compare the
stored `tenant_id` against the request's tenant:

```python
it = T.sessions.get_item(Key={"user_sub": resolved_user_sub, "session_id": session_id}).get("Item")
if not it:
    raise HTTPException(401, "Unknown session")

session_tenant = str(it.get("tenant_id") or "default")
request_tenant = str(getattr(getattr(request, "state", None), "tenant_id", None) or "default")
if S.multi_tenancy_enabled and session_tenant != request_tenant:
    raise HTTPException(401, "Session tenant mismatch")
```

The check is gated on `S.multi_tenancy_enabled` so single-tenant deployments are
unaffected.

### Step 5 — Propagate `tenant_id` in the return dict

In `require_ui_session`, add `tenant_id` to the returned dict so callers can read it:

```python
out = {
    "user_sub": resolved_user_sub,
    "session_id": session_id,
    "role": role.value,
    "ip": str(it.get("ip") or ""),
    "tenant_id": str(it.get("tenant_id") or "default"),
}
```

Many downstream routers currently ignore unknown keys in the context dict, so adding
`tenant_id` here is additive and non-breaking. Endpoints that need to enforce
tenant-specific logic (e.g., listing resources scoped to the caller's tenant) can now
read `ctx["tenant_id"]` rather than separately reading `request.state.tenant_id`.

### Step 6 — Embed `tenant_id` in the `ui_access_token` JWT (optional, defence-in-depth)

The `ui_access_token` cookie JWT is minted in `app/services/sessions.py` `mint_access_token`.
Adding `tenant_id` as a JWT claim makes the cookie self-describing: even if the DDB session
record is unavailable (e.g., during a partial outage), the middleware can verify that the
cookie's `tenant_id` claim matches `request.state.tenant_id` before the DI framework runs.
The check in `get_authenticated_user` (cookie branch, `app/auth/deps.py` lines 218–231)
would become:

```python
payload = jwt.decode(
    access_cookie,
    access_secret,
    algorithms=["HS256"],
    options={"verify_exp": False},
)
user_sub = payload.get("sub")
if user_sub:
    _tenant_id = getattr(getattr(request, "state", None), "tenant_id", None) or "default"
    cookie_tenant = payload.get("tenant_id", "default")
    if S.multi_tenancy_enabled and cookie_tenant != _tenant_id:
        # Cookie was minted for a different tenant — reject without hitting DDB
        pass  # fall through to next auth method → 401
    ...
```

This is an optional hardening layer, not required for the core fix, but provides
inline rejection without a DDB round-trip for the common cross-tenant replay case.

### Dev/prod parity (SECOPS-007)

The enforcement is gated behind `S.multi_tenancy_enabled` which defaults to `0` in dev
(`MULTI_TENANCY_ENABLED` env var). The field is added unconditionally so tests can exercise
it with `MULTI_TENANCY_ENABLED=1`. No separate mock path is required. The same DDB write
and read code runs in dev and prod; the feature flag merely controls whether the mismatch
is rejected or silently ignored.

### Backward compatibility

Old session records in DDB lack a `tenant_id` field. The comparison treats a missing field
as `"default"` (same as existing `request_tenant` for single-tenant deployments), so
existing sessions continue to work. New sessions written after the deploy will carry the
correct field. This grace period means the feature can be deployed before the migration
script runs without causing user-visible disruptions.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

`tests/test_tenant_session_isolation.py`:

```python
import pytest
from unittest.mock import patch, MagicMock
from fastapi.testclient import TestClient
from app.main import app

@pytest.fixture
def tenant_a_cookies(client):
    # Login on tenantA -> get session cookies
    ...

def test_cross_tenant_replay_rejected(client, tenant_a_cookies):
    """Session minted on tenantA must be rejected on tenantB when multi_tenancy_enabled."""
    with patch("app.core.settings.S.multi_tenancy_enabled", True):
        # Request with tenantA cookies but X-Tenant-Id: tenantB
        resp = client.get(
            "/ui/me",
            cookies=tenant_a_cookies,
            headers={"X-Tenant-Id": "tenantB"},
        )
    # BEFORE fix: 200 OK (cross-tenant replay succeeds)
    # AFTER fix:  401 Unauthorized
    assert resp.status_code == 401
    assert "tenant" in resp.json()["detail"].lower()

def test_same_tenant_session_accepted(client, tenant_a_cookies):
    """Session minted on tenantA must still work on tenantA."""
    with patch("app.core.settings.S.multi_tenancy_enabled", True):
        resp = client.get(
            "/ui/me",
            cookies=tenant_a_cookies,
            headers={"X-Tenant-Id": "tenantA"},
        )
    assert resp.status_code == 200

def test_single_tenant_mode_unaffected(client, tenant_a_cookies):
    """With multi_tenancy_enabled=False, tenant field is ignored."""
    with patch("app.core.settings.S.multi_tenancy_enabled", False):
        resp = client.get(
            "/ui/me",
            cookies=tenant_a_cookies,
            headers={"X-Tenant-Id": "tenantB"},
        )
    assert resp.status_code == 200
```

### Manual QA steps

1. Start the stack with `MULTI_TENANCY_ENABLED=1`.
2. Seed two tenant records (`tenantA` and `tenantB`) in DynamoDB via `scripts/local-ddb-seed.py`
   or directly with `aws dynamodb put-item --table-name tenants ...`.
3. Log in as Alice on `localhost:3000` (tenantA via `X-Tenant-Id: tenantA` dev header).
4. Capture session cookies from browser DevTools (Network tab → any authenticated request →
   Request Headers → `Cookie`).
5. Replay those cookies against tenantB: `curl -b "<cookies>" -H "X-Tenant-Id: tenantB" http://localhost:8000/ui/me` — expect HTTP 401.
6. Confirm the same cookies still work with `X-Tenant-Id: tenantA` — expect HTTP 200.
7. Log in as a ROOT user on tenantA; confirm the root session also correctly fails on
   tenantB (root is not above tenant isolation).
8. Run `just e2e` to confirm no existing tests regress. The existing E2E sessions all use
   the default tenant; the `tenant_id = "default"` grace period means they are unaffected.

### Metrics / observability

Add a `session_tenant_mismatch_total{tenant_requested, tenant_stored}` counter in
`app/metrics.py` and increment it at the rejection point in `require_ui_session`. This
makes anomalous cross-tenant probing visible in the Prometheus/Grafana dashboards and
allows alerting if a sustained stream of mismatch attempts is detected, which could
indicate an attacker systematically testing stolen cookies across tenants. Also add a
corresponding audit event `session_tenant_mismatch` via `audit_event(...)` so the
incident is recorded per-user in the audit log.

### Rollout sequencing

1. **Phase 1 (safe)**: Deploy with `MULTI_TENANCY_ENABLED=0` (current default). The
   `tenant_id` field is added to `AuthenticatedUser`, session writes, and the return dict,
   but no enforcement check runs. Zero user impact. Monitor for 24 hours.
2. **Phase 2 (backfill)**: Run migration script to write `tenant_id = "default"` onto all
   existing session records in DDB that lack the field (use a scan + conditional update).
   This ensures the enforcement check will treat all existing sessions correctly once enabled.
3. **Phase 3 (canary)**: Enable `MULTI_TENANCY_ENABLED=1` on one staging tenant. Verify
   that cross-tenant replays are rejected and same-tenant requests succeed. Run the full
   E2E test suite.
4. **Phase 4 (production)**: Enable per production tenant in rolling fashion, starting
   with tenants that have the fewest historical session records to minimise backfill risk.
5. **Full rollout** after one week of canary soak with no regressions.

**Effort**: M (3–5 days: data model change across 4 code sites, migration script, tests,
rollout scripting).

**Risk**: Low. Feature-flagged throughout. Graceful degradation via `"default"` fallback
for old session records. The worst case of a false-positive rejection causes a 401, which
the frontend handles with a redirect to the login page — a recoverable UX event, not data
loss.
