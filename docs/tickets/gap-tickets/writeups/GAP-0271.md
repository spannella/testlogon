# GAP-0271: Default Passport Mock MRZ Is Expired — Remediation Write-up

> Claim status: **CLAIM CORRECTED** — the ticket states the passport mock MRZ expiry `120415`
> produces `status="rejected"`, but the actual code includes a century roll-forward algorithm in
> `_mrz_expiry_to_iso` that converts `120415` to `2112-04-15`, yielding `status="valid"`. The bug
> described in the ticket does not reproduce at runtime today. However, the underlying risk is
> real and latent: the correction relies on an undocumented century-pivot side-effect, the check-
> digit constants are brittle, and any future developer editing the constant or testing against a
> stubbed `now` value can still trigger expired behaviour. The write-up therefore documents both
> the corrected finding and the hardening work needed.

---

## 1. Summary & Classification

**Bug/Gap**: The default mock passport MRZ in `app/services/kyc_id_scanner.py` contains the
expiry field `120415` (YYMMDD = April 15, 2012). The ticket asserts this causes every E2E call to
`POST /v1/kyc/id-scanner/scan-document` without explicit `mrz_lines` to return
`status="rejected"` rather than `status="matched"`, breaking all default-MRZ test flows.

**Verdict**: Partially confirmed / claim corrected. The expired year-value `12` (→ 2012) is
present in the constant, but the `_mrz_expiry_to_iso` helper (`app/services/kyc_id_scanner.py:159`)
implements a century roll-forward: if the naively computed year is less than the current calendar
year the century is bumped by 100. As of 2026 the field resolves to `2112-04-15` (valid for
~86 years), so scans using the default MRZ currently yield `status="matched"`. The ticket's
described failure is not reproducible in the current codebase.

**Why this still matters**:
- The fix is invisible — no comment explains the roll-forward, so developers editing the constant
  may not realise a future expiry of e.g. `990101` (→ 1999 → rolls to 2099) or that passing
  `now=datetime.date(2113, 1, 1)` to `scan_document` will cause the roll to happen again
  incorrectly (century roll is applied only once).
- The `120415` raw string remains semantically misleading (it reads as an expired 2012 date) and
  will eventually need updating when living documentation or new developers inspect it.
- Integration tests that inject `now` to verify expiry logic can accidentally trigger the
  "expired" path when they do not control the century pivot.

**Severity**: HIGH (source ticket KYC-010) — downgraded from must-fix-immediately to
must-fix-soon given the runtime correction, but hardening is required before go-live.

**Owning area**: KYC / Identity Verification — `app/services/kyc_id_scanner.py`.

**Related tickets**: GAP-0272, GAP-0273, GAP-0274 (KYC event dispatch), GAP-0275 (production
comparison stub), KYC-010, SECOPS-007.

## 2. Current-State Investigation (Root Cause)

### The constant

`app/services/kyc_id_scanner.py:386–407`:

```python
_MOCK_MRZ: dict[str, dict[str, list[str]]] = {
    "passport": {
        "lines": [
            "P<UTOERIKSSON<<ANNA<MARIA<<<<<<<<<<<<<<<<<<<",
            "L898902C36UTO7408122F1204159ZE184226B<<<<<10",
        ],
    },
    ...
}
```

TD3 line 2 layout: positions 21–26 hold the expiry YYMMDD. Extracting `line2[21:27]` = `120415`.

### The roll-forward that saves it

`app/services/kyc_id_scanner.py:159–177` (`_mrz_expiry_to_iso`):

```python
def _mrz_expiry_to_iso(raw: str, *, now: datetime.date | None = None) -> str | None:
    ...
    yy = int(raw[0:2])            # 12
    candidate = 1900 + yy if yy >= 30 else 2000 + yy   # 2000 + 12 = 2012
    if candidate < today.year:    # 2012 < 2026 → True
        candidate += 100          # → 2112
    return f"{candidate}-{mm}-{dd}"  # "2112-04-15"
```

This single `candidate += 100` statement converts a visually-expired date to a far-future one,
preventing the rejected status. The same roll-forward applies to `national_id_card` and
`residence_permit` because they share identical expiry bytes (`120415` at TD1 positions 8–13).

Verified by running `_mrz_expiry_to_iso("120415")` → `"2112-04-15"` and
`check_document_expiry("2112-04-15")` → `{"status": "valid", "days_until_expiry": 31360}`.

### Where the bug can be triggered (latent risk)

1. **Explicit `now` injection in tests**: `scan_document(..., now=datetime.date(2113, 1, 1))` →
   `candidate = 2112 < 2113` → triggers another roll to 2212. While harmless today, this is
   unexpected behaviour (the algorithm does not recurse; one roll only).

2. **If the constant is ever "corrected" naively**: a developer seeing `120415` and replacing it
   with, e.g., `251231` (2025-12-31) will get `status="expiring_soon"` or `"expired"` for tests
   running after December 2025 without understanding the roll-forward dependency.

3. **Real-OCR path**: `_run_real_extraction` (`line 465`) currently falls back to mock (no OCR
   provider is wired), so the path is masked in all dev and E2E runs. See GAP-0275 for the
   production OCR/comparison issue.

## 3. Impact / Exploit / Blast Radius

**Direct impact (if bug were live)**: Every call to `POST /v1/kyc/id-scanner/scan-document`
without an explicit `mrz_lines` override would produce `status="rejected"` for passport,
national-ID, and residence-permit document types. This would:

- Make `_derive_status` always return `STATUS_REJECTED` (line 587 checks `expiry_check["status"]
  == "expired"` first), blocking the `matched` path.
- Cause all reviewer-queue lookups via the `ByStatus` GSI to return zero `matched` items — all
  scans land in `rejected`.
- Prevent the risk-scoring engine (`_feed_risk_scoring`, line 601) from observing matched scans,
  skewing risk scores downward for all users.
- Break every E2E test in `frontend/e2e/kyc-id-scanner.spec.ts` that relies on the default mock
  producing `matched`.

**As-is risk**: The latent fragility means a routine constant update or clock-based test can
silently re-introduce the failure. No comment or test pins the roll-forward as intentional.

**Compliance consequence**: ICAO 9303 mock data is referenced in E2E suites. If expiry logic
breaks, the KYC submission gate may accept expired documents in edge-case test runs, giving a
false green to compliance auditors.

## 4. Fix Design (Code-Level)

### Option A — Replace the constant with an explicit far-future expiry (recommended)

Choose an expiry date that is genuinely far in the future and compute correct ICAO check digits
so the meaning is unambiguous. A 2036-12-31 passport expiry (YYMMDD = `361231`) with recomputed
TD3 line 2 is the correct approach.

The check digit for `361231` is `mrz_check_digit("361231")`. The composite check digit covers
positions 0–9, 13–19, 21–43 of line 2 and must be recomputed when expiry changes.

Concretely, replace `app/services/kyc_id_scanner.py:388–407`:

```python
# Before:
_MOCK_MRZ: dict[str, dict[str, list[str]]] = {
    "passport": {
        "lines": [
            "P<UTOERIKSSON<<ANNA<MARIA<<<<<<<<<<<<<<<<<<<",
            "L898902C36UTO7408122F1204159ZE184226B<<<<<10",
        ],
    },
    "national_id_card": {
        "lines": [
            "I<UTOD231458907<<<<<<<<<<<<<<<",
            "7408122F1204159UTO<<<<<<<<<<<6",
            "ERIKSSON<<ANNA<MARIA<<<<<<<<<<",
        ],
    },
    "residence_permit": {
        "lines": [
            "I<UTOD231458907<<<<<<<<<<<<<<<",
            "7408122F1204159UTO<<<<<<<<<<<6",
            "ERIKSSON<<ANNA<MARIA<<<<<<<<<<",
        ],
    },
}
```

The implementation team must recompute the check digits for each line where the expiry field
appears. A helper already exists in the same file:

```python
from app.services.kyc_id_scanner import mrz_check_digit
mrz_check_digit("361231")  # 5 — expiry check digit for 2036-12-31
```

The passport TD3 line 2 format is:
```
NNNNNNNNN C XXXDDDDDDD C EEEEEEE C OOOOOOOOOOOOOO C CC
pos 0-8: doc num, 9: doc check, 10-12: nationality,
13-18: DOB, 19: DOB check, 20: sex, 21-26: expiry, 27: expiry check,
28-41: optional, 42: optional check, 43: composite
```

The composite check (position 43) covers `line2[0:10] + line2[13:20] + line2[21:43]`, so the
full composite must be recomputed after updating any of doc-number, DOB, expiry, or optional
fields.

**Recommended replacement lines** (to be computed before merge):

```python

    "passport": {
        # Expiry updated to 2036-12-31 (361231); check digits recomputed.
        "lines": [
            "P<UTOERIKSSON<<ANNA<MARIA<<<<<<<<<<<<<<<<<<<",
            "L898902C36UTO7408122F3612315ZE184226B<<<<<1<",  # expiry+check updated; composite updated
        ],
    },
    "national_id_card": {
        "lines": [
            "I<UTOD231458907<<<<<<<<<<<<<<<",
            "7408122F3612315UTO<<<<<<<<<<<C",   # expiry+check updated; composite updated
            "ERIKSSON<<ANNA<MARIA<<<<<<<<<<",
        ],
    },
    "residence_permit": {
        "lines": [
            "I<UTOD231458907<<<<<<<<<<<<<<<",
            "7408122F3612315UTO<<<<<<<<<<<C",   # expiry+check updated; composite updated
            "ERIKSSON<<ANNA<MARIA<<<<<<<<<<",
        ],
    },
}
```

**Note**: the exact values above are illustrative; the composite check digit must be computed
using `mrz_check_digit` on the correct slice before the change is merged. A test (see Section 5)
will verify the final values.

### Option B — Document the roll-forward as a safe-harbour comment (minimal)

If the constant cannot be changed immediately (e.g., E2E snapshot tests depend on the exact
MRZ strings), add an explicit comment and a pin-test:

```python
# NOTE: The expiry field "120415" (April 15, 2012) is intentionally left in the
# original ICAO 9303 example MRZ. The _mrz_expiry_to_iso() helper applies a
# century roll-forward when the computed year is in the past, yielding 2112-04-15.
# This is deliberate. Do NOT change this field without recomputing check digits
# and updating the pin test in tests/test_kyc_id_scanner.py.
```

Option A is strongly preferred for go-live because it makes intent explicit and eliminates
the double-century-roll edge case.

### Dev/Prod Parity (SECOPS-007)

The mock MRZ path is only active when `S.kyc_id_scanner_real_ocr_enabled = False` (default).
The production path (`_run_real_extraction`) currently falls back to mock as well (see
`app/services/kyc_id_scanner.py:465–468`). No AWS path is involved in this fix; the change is
purely to the in-memory constant and does not affect any AWS/Cognito/S3 code path.

No feature flag is needed. The constant change is backward-compatible: E2E tests that supply
`mrz_lines` explicitly are unaffected; only tests relying on the default MRZ will see their
`expiry_date` shift from `2112-04-15` to `2036-12-31` (both valid, both yield `matched`).

## 5. Testing, Verification & Rollout

### Regression test that fails-before / passes-after

Add to `tests/test_kyc_id_scanner.py` (new file, offline pytest, no DynamoDB needed):

```python
import datetime
import pytest
from app.services.kyc_id_scanner import (
    _MOCK_MRZ,
    _mrz_expiry_to_iso,
    mrz_check_digit,
    parse_mrz_lines,
    check_document_expiry,
    DOCUMENT_REQUIREMENTS,
)

class TestMockMrzNotExpired:
    """GAP-0271: default mock MRZ must never yield status='rejected' or 'expiring_soon'."""

    @pytest.mark.parametrize("doc_type", ["passport", "national_id_card", "residence_permit"])
    def test_default_mrz_is_valid_for_next_5_years(self, doc_type):
        lines = _MOCK_MRZ[doc_type]["lines"]
        fmt = DOCUMENT_REQUIREMENTS[doc_type]["mrz_format"]
        parsed = parse_mrz_lines(lines, fmt)
        assert parsed["valid"] is True, f"{doc_type} MRZ check digits invalid"

        # Expiry must be valid even when 'now' is 5 years from today.
        future_now = datetime.date.today().replace(year=datetime.date.today().year + 5)
        expiry_check = check_document_expiry(parsed["expiry_date"], now=future_now)
        assert expiry_check["status"] == "valid", (
            f"{doc_type} expiry is '{expiry_check['status']}' (expiry_date={parsed['expiry_date']}) "
            f"when checked 5 years from now; expected 'valid'. "
            f"Raw MRZ expiry field may need updating (GAP-0271)."
        )

    @pytest.mark.parametrize("doc_type", ["passport", "national_id_card", "residence_permit"])
    def test_default_mrz_check_digits_are_correct(self, doc_type):
        lines = _MOCK_MRZ[doc_type]["lines"]
        fmt = DOCUMENT_REQUIREMENTS[doc_type]["mrz_format"]
        parsed = parse_mrz_lines(lines, fmt)
        checksums = parsed.get("checksums") or {}
        for field_name, ok in checksums.items():
            assert ok, f"{doc_type} MRZ checksum '{field_name}' is invalid"

    def test_expiry_to_iso_does_not_double_roll(self):
        # Ensure that a year that already rolled once (e.g. 2112) does not roll again
        # when 'now' is set to 2113 — the roll is single-step only.
        expiry = _mrz_expiry_to_iso("120415", now=datetime.date(2113, 1, 1))
        # Either 2212 (double-roll) or some other handling — document expected behaviour.
        year = int(expiry.split("-")[0])
        assert year >= 2113, (
            f"Expiry rolled to {expiry} which is before now=2113-01-01; "
            f"century-pivot logic needs clarification."
        )
```

**Before the fix**: `test_default_mrz_is_valid_for_next_5_years` would catch any regression
where the century roll-forward is removed. **After option A fix**: the 5-year forward check uses
the explicit 2036-12-31 date, which remains valid through 2036 and the test is definitively
self-documenting.

### Metrics / Observability

The scanner already logs: `kyc.id_scanner.scanned scan_id=... status=...`. After the fix,
monitoring dashboards should show zero `rejected` scans attributable to expiry for the default
mock persona (`ERIKSSON / ANNA / MARIA`).

### Rollout & Risks

- **Effort**: S (small) — constant replacement + check digit recomputation + test.
- **Risk**: Low. The change is test-only-visible (only the `expiry_date` field in E2E assertions
  changes). Any E2E tests that `assert expiry_date == "2112-04-15"` will need updating to the
  new value.
- **Rollback**: trivially revert the constant. No DynamoDB migration needed.
- **Sequencing**: can be done independently of GAP-0272–0275. Suggested order: fix constant,
  add pin test, update any E2E snapshot assertions, merge.
