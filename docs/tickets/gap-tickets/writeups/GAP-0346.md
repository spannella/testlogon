# GAP-0346: No `user reactivate` or `user undelete` Commands — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. No investigation doc exists.

## 1. Summary & Classification

**Bug statement.** The `rootctl` break-glass CLI (app/cli/rootctl.py) ships `user deactivate` and `user delete` commands but no corresponding reversal commands. There is no `user reactivate` to lift a `deactivated` account back to `active`, and no `user undelete` to restore a soft-deleted account whose `status` is `"deleted"`. The only way to restore either state today is to connect directly to DynamoDB and hand-edit the `account_state` record — a dangerous, unaudited, unapproved procedure.

- **Severity**: HIGH
- **Source ticket**: ROOTCTL-001 (break-glass hardening)
- **Status**: Open
- **Owning area**: Platform / Root Operations / `app/cli/rootctl.py`
- **Claim verdict**: CONFIRMED. Code search found no `reactivate` or `undelete` sub-parsers anywhere in `app/cli/rootctl.py` (the file is 2453 lines; a grep for either term returns zero hits). The `_require_mutable_account_state` helper at line 842 explicitly blocks `deactivate` and `set-password` operations on accounts whose status is already `"deactivated"` or `"deleted"`, which makes the missing reversal commands doubly painful — once an account is in either terminal state, no standard CLI path can touch it at all.
- **Related tickets**: ROOTCTL-001, SECOPS-007 (dev/prod parity), SEC-018 (account-state revocation propagation)

## 2. Current-State Investigation (root cause)

### The forward commands exist; the reversal commands do not

`app/cli/rootctl.py` implements the `user` command group between lines 2146 and 2261. The following sub-parsers are registered:

| Command | Handler | Lines |
|---|---|---|
| `user create` | `_user_create_command` | 2147–2167 |
| `user list` | `_user_list_command` | 2169–2186 |
| `user verify` | `_user_verify_command` | 2188–2201 |
| `user set-password` | `_user_set_password_command` | 2203–2216 |
| `user deactivate` | `_user_deactivate_command` | 2218–2229 |
| `user deactivate-bulk` | `_user_deactivate_bulk_command` | 2231–2247 |
| `user delete` | `_user_delete_command` | 2249–2261 |

There is no `user reactivate` and no `user undelete` entry.

### How `deactivate` works — and what reversal requires

`_user_deactivate_command` (line 1024) does three things:

1. Writes `T.account_state.put_item(…, status="deactivated", …)` (line 1053).
2. Writes audit fields (`deactivated_at`, `deactivated_by`, `deactivation_reason`, `deactivation_ticket`) to the `T.users` record (line 1062).
3. Calls `revoke_all_sessions` and `revoke_all_api_keys` (lines 1076–1077).

A `reactivate` command must at minimum:

- Set `account_state.status` back to `"active"` (or `"pending_verification"` if the operator wants email re-verification).
- Write corresponding audit metadata to `T.users` (`reactivated_at`, `reactivated_by`, `reactivation_reason`, `reactivation_ticket`).
- Emit an `audit_event` for `user_reactivated_cli` so the security timeline captures the event.
- **Not** re-issue sessions or API keys — those were intentionally revoked; the user must log in again.

### How `delete` works and what restoration requires

`_user_delete_command` (line 1173) supports soft-delete (default) and hard-delete (`--hard-delete` flag). Soft-delete (line 1208) writes `status="deleted"` to `account_state` and marks `deleted_at` / `deleted_by` / `deletion_reason` on the user record. Hard-delete (line 1205) physically removes both records from DynamoDB.

An `undelete` command applies only to soft-deletes. It must:

- Check that the current `account_state.status` is `"deleted"` (hard-deletes leave no record to restore).
- Restore `account_state.status` to `"active"` (or `"pending_verification"`).
- Write audit metadata (`undeleted_at`, `undeleted_by`, `undeletion_reason`, `undeletion_ticket`) to `T.users`.
- Emit `user_undeleted_cli` audit event.
- **Not** re-issue sessions or API keys.

### The `_require_mutable_account_state` guard creates a hard wall

Line 842–849:

```python
def _require_mutable_account_state(target_user_sub: str) -> str:
    state = T.account_state.get_item(Key={"user_sub": target_user_sub}).get("Item") or {}
    status = _normalize_status(str(state.get("status") or "active"))
    if status in {"deactivated", "deleted"}:
        raise CliPolicyError(
            "target user state does not permit this operation",
            details={"code": "account_state_forbidden", "status": status, ...},
        )
    return status
```

Every mutating user command except `delete` calls this guard. This means: once an account enters `deactivated` or `deleted` state, not even `set-password` or `verify` can run on it. The only sanctioned recovery path is a new `reactivate`/`undelete` command. Without those commands, operators are pushed toward raw DynamoDB edits, which produce no audit trail.

## 3. Impact / Exploit / Blast Radius

### Operational impact (primary)

When a user account is deactivated for investigation (e.g., suspected abuse) and is later cleared, there is no supported mechanism to reinstate the account. The operator must either:

a) Use a DDB console or `aws dynamodb put-item` to overwrite `account_state`, which leaves no audit trail in `T.alerts` or `T.role_audit`.
b) Use `user create` with the same email to try to re-create the record — but `_user_create_command` calls `T.users.put_item` with `ConditionExpression="attribute_not_exists(user_sub)"` (line 717), which throws because the user record still exists (soft-delete does not erase `T.users`).

This means (b) always fails for soft-deleted accounts, and (a) is an unaudited workaround that violates ROOTCTL-001 and SECOPS-007.

### Support / compliance impact

Platform support workflows sometimes deactivate accounts pending identity verification. If the investigation resolves favorably, the inability to restore the account via an audited mechanism forces a manual DynamoDB mutation. Under any compliance framework that requires audit trails for account state changes (SOC 2, ISO 27001, GDPR Article 5), this gap is a direct finding.

### Accidental amplification of `deactivate`

Because there is no `reactivate`, operators are reluctant to deactivate accounts preemptively during incidents — knowing there is no clean way back. This can lead to under-use of a legitimate security tool, allowing bad actors to continue using accounts that should be suspended.

### Financial consequence

Subscription billing and pay-per-view revenue depend on account state. A falsely deactivated creator who cannot be reactivated without a DDB hack loses income for the duration; the platform may face contractual liability.

## 4. Fix Design (code-level)

### 4a. `_user_reactivate_command` function

Add the following handler to `app/cli/rootctl.py` after `_user_deactivate_bulk_command` (around line 1172):

```python
def _user_reactivate_command(args: argparse.Namespace) -> Dict[str, Any]:
    shared = _shared_opts(args)
    root_sub = str(getattr(args, "root_sub", "") or "").strip()
    actor_sub = str(getattr(args, "actor_sub", "") or "").strip()
    reason = str(getattr(args, "reason", "") or "").strip()
    ticket = str(getattr(args, "ticket", "") or "").strip()
    target_user_sub = str(getattr(args, "target_user_sub", "") or "").strip()

    _require_existing_non_root_user(target_user_sub, root_sub=root_sub)

    # Must currently be deactivated (not deleted — use undelete for that)
    state = T.account_state.get_item(Key={"user_sub": target_user_sub}).get("Item") or {}
    current_status = _normalize_status(str(state.get("status") or "active"))
    if current_status != "deactivated":
        raise CliPolicyError(
            "reactivate requires account status to be 'deactivated'",
            details={"code": "invalid_state_transition",
                     "current_status": current_status,
                     "target_user_sub": target_user_sub},
        )

    if bool(shared.dry_run):
        return {
            "ok": True, "group": str(args.group), "command": str(args.command),
            "dry_run": True, "actor_sub": actor_sub, "target_user_sub": target_user_sub,
            "previous_status": current_status, "new_status": "active",
            "reason": reason, "ticket": ticket,
            "request_id": shared.request_id, "correlation_id": shared.correlation_id,
            "message": "dry-run: user would be reactivated",
        }

    ts = now_ts()
    T.account_state.put_item(Item={
        "user_sub": target_user_sub, "status": "active",
        "updated_at": ts, "reason": reason, "requested_by": actor_sub,
    })
    T.users.update_item(
        Key={"user_sub": target_user_sub},
        UpdateExpression=(
            "SET reactivated_at=:ts, reactivated_by=:actor, "
            "reactivation_reason=:reason, reactivation_ticket=:ticket"
        ),
        ExpressionAttributeValues={
            ":ts": ts, ":actor": actor_sub,
            ":reason": reason, ":ticket": ticket,
        },
    )

    audit_event(
        "user_reactivated_cli", target_user_sub, None,
        outcome="success", actor_sub=actor_sub,
        target_user_sub=target_user_sub,
        previous_status=current_status, new_status="active",
        reason=reason, ticket_id=ticket,
        request_id=shared.request_id,
        correlation_id=shared.correlation_id, cli=True,
    )

    return {
        "ok": True, "group": str(args.group), "command": str(args.command),
        "dry_run": False, "actor_sub": actor_sub, "target_user_sub": target_user_sub,
        "previous_status": current_status, "new_status": "active",
        "reason": reason, "ticket": ticket,
        "request_id": shared.request_id, "correlation_id": shared.correlation_id,
        "audit_event": "user_reactivated_cli",
    }
```

### 4b. `_user_undelete_command` function

```python

    ticket = str(getattr(args, "ticket", "") or "").strip()
    target_user_sub = str(getattr(args, "target_user_sub", "") or "").strip()

    user_item = _require_existing_non_root_user(target_user_sub, root_sub=root_sub)
    # user record must still exist (hard-deletes remove it)
    state = T.account_state.get_item(Key={"user_sub": target_user_sub}).get("Item") or {}
    current_status = _normalize_status(str(state.get("status") or "active"))

        raise CliPolicyError(
            "undelete requires account status to be 'deleted'",

                     "target_user_sub": target_user_sub},

    if bool(shared.dry_run):

            "ok": True, "group": str(args.group), "command": str(args.command),

            "previous_status": current_status, "new_status": "active",
            "reason": reason, "ticket": ticket,
```

### 4c. Sub-parser registration in `_add_group_commands`

Inside the `if group_name == "user":` block (after line 2261, after the `delete` sub-parser), add:

```python
        reactivate = commands.add_parser(
            "reactivate",
            help="Restore a deactivated user account to active status",
        )
        _add_shared_options(reactivate)
        _add_mutation_guard_options(reactivate)
        reactivate.add_argument(
            "--target-user-sub", required=True, help="Target user subject"
        )
        reactivate.set_defaults(
            handler=_user_reactivate_command,
            group=group_name,
            mutating=True,
            requires_root=True,
            requires_ticket=True,
            requires_confirm=False,
        )

        undelete = commands.add_parser(
            "undelete",
            help="Restore a soft-deleted user account to active status",
        )
        _add_shared_options(undelete)
        _add_mutation_guard_options(undelete)
        undelete.add_argument(
            "--target-user-sub", required=True, help="Target user subject"
        )
        undelete.set_defaults(
            handler=_user_undelete_command,
            group=group_name,
            mutating=True,
            requires_root=True,
            requires_ticket=True,
            requires_confirm=True,  # destructive reversal requires --confirm
        )
```

`requires_ticket=True` is consistent with `deactivate` and `delete`. `requires_confirm=True` on `undelete` matches the pattern used by `delete` — since restoring a deleted account is an unusual, high-stakes action that the operator should explicitly confirm.

### 4d. Dev/prod parity (SECOPS-007)

Both new commands only write to `T.account_state` and `T.users`. These tables are served by DynamoDB Local in dev (port 8001, via `scripts/run_local_mock_backend.sh` and `.env.local`) and by AWS DynamoDB in production. The code path does not diverge between environments — there are no feature flags needed. The `audit_event` helper writes to `T.alerts`, which is also DynamoDB-backed in both environments. No mock path is required.

### 4e. Alternatives considered

- **Re-use `user create` with the existing sub**: Rejected. `T.users.put_item` with `attribute_not_exists` condition (line 717) fails for soft-deleted records because the user record is never deleted. Even removing the condition would overwrite audit trail fields.
- **A generic `user set-status` command**: Considered but rejected. A single command that allows arbitrary status transitions creates a footgun (e.g., setting a user from `active` directly to `deleted` without the `--hard-delete` guard). Separate named commands with state-machine guards are clearer and safer.

## 5. Testing, Verification & Rollout

### Regression test (fails before / passes after fix)

Add to `tests/test_rootctl.py`:

```python
def test_user_reactivate_requires_deactivated_status(mock_ddb):
    """user reactivate should fail when account is not deactivated."""
    # Create a user in active state
    _seed_user(mock_ddb, sub="alice@test.local", status="active")
    result = invoke_rootctl(
        "user reactivate --target-user-sub alice@test.local "
        "--actor-sub root@test.local --reason test --ticket T-001"
    )
    assert result.exit_code == ExitCode.AUTHZ_ERROR
    assert "invalid_state_transition" in result.stderr

def test_user_reactivate_restores_active_status(mock_ddb):
    """Reactivating a deactivated user should set status to active and emit audit."""
    _seed_user(mock_ddb, sub="alice@test.local", status="deactivated")
    result = invoke_rootctl(
        "user reactivate --target-user-sub alice@test.local "
        "--actor-sub root@test.local --reason cleared --ticket T-001"
    )
    assert result.exit_code == 0
    state = mock_ddb.get_account_state("alice@test.local")
    assert state["status"] == "active"
    audit = mock_ddb.last_alert()
    assert audit["event"] == "user_reactivated_cli"

def test_user_undelete_requires_deleted_status(mock_ddb):
    _seed_user(mock_ddb, sub="alice@test.local", status="active")
    result = invoke_rootctl(
        "user undelete --target-user-sub alice@test.local "
        "--actor-sub root@test.local --reason test --ticket T-001 "
        "--confirm alice@test.local"
    )
    assert result.exit_code == ExitCode.AUTHZ_ERROR

def test_user_undelete_restores_soft_deleted_user(mock_ddb):

        "--actor-sub root@test.local --reason reinstated --ticket T-002 "

    assert result.exit_code == 0
    state = mock_ddb.get_account_state("alice@test.local")
    assert state["status"] == "active"
```

### Manual QA steps

1. Run `just up` to start the full dev stack.
2. Create a test user: `python app/cli/rootctl.py user create --email qa@test.local --actor-sub root@testdev.local --reason test`.
3. Deactivate it: `python app/cli/rootctl.py user deactivate --target-user-sub qa@test.local --actor-sub root@testdev.local --reason qa --ticket T-000 --confirm qa@test.local`.
4. Verify login fails (account deactivated).
5. Reactivate: `python app/cli/rootctl.py user reactivate --target-user-sub qa@test.local --actor-sub root@testdev.local --reason qa --ticket T-001`.
6. Verify `T.account_state` record shows `status: active` via DDB console (port 8001).
7. Verify login succeeds.
8. Repeat steps 2–3 with soft-delete (`user delete`), then run `user undelete` with `--confirm`.

### Observability

Both new handlers write to `T.alerts` via `audit_event`. The security timeline query (`rootctl audit security`) will surface `user_reactivated_cli` and `user_undeleted_cli` events. No additional metrics are required.

### Rollout and risks

- **Effort**: S (small) — approximately 120 lines of new Python, mirroring existing command structure.
- **Risk**: Low. Both commands only write to existing tables (`T.account_state`, `T.users`, `T.alerts`). They cannot alter role or create sessions.
- **Sequencing**: Can be shipped independently. No schema changes needed.
- **Rollback**: Remove the sub-parser registrations. The handler functions are dead code if not registered.
