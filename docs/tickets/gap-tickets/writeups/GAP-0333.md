# GAP-0333: Analytics events table not created — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `scripts/local-ddb-init.py`, `app/core/tables.py`, and `app/core/settings.py`.

## 1. Summary & Classification

**Gap**: The `analytics_events` DynamoDB table — intended to store raw event records (page views, revenue events, subscriber events, engagement events) before they are rolled up into `AnalyticsRollups` — is never created in `scripts/local-ddb-init.py`, never declared in `app/core/tables.py`, and has no corresponding setting in `app/core/settings.py`. The `AnalyticsRollups` table (the aggregated output) is created and wired correctly, but the raw event input table is absent. If any code attempts to write to `analytics_events` it will receive an immediate `ResourceNotFoundException` from DynamoDB Local (dev) and from DynamoDB (prod).

**Claim status**: Confirmed. A comprehensive search across `scripts/local-ddb-init.py`, `app/core/tables.py`, and `app/core/settings.py` finds zero occurrences of `analytics_events`. The GAP ticket correctly identifies that the table is absent. The claim that `analytics_events.py` recording functions are "missing" is addressed in GAP-0334; this ticket covers only the DynamoDB infrastructure layer.

**Severity**: HIGH — without the table the entire analytics event pipeline is broken from the infrastructure up. Any attempt to record an event crashes the recording service, and the rollup engine (GAP-0335) can never aggregate from data that was never stored.

**Source ticket**: PLATFORM-019. **Status**: Open. **Effort**: S. **Owning area**: Analytics / Infrastructure.

**Related tickets**: GAP-0334 (`analytics_events.py` service not implemented), GAP-0335 (rollup engine not implemented). This ticket is the prerequisite for both; they must be sequenced GAP-0333 → GAP-0334 → GAP-0335.

### What this means at runtime

The `creator_analytics.py` service reads from `T.analytics_rollups` (the aggregated output). The dashboard endpoints work today only because `upsert_daily_rollup` can be called directly from the manual `POST /refresh` endpoint. But the automated pipeline that is supposed to populate `AnalyticsRollups` from raw `analytics_events` records can never work because:
1. The `analytics_events` table does not exist.
2. The `analytics_events.py` service (GAP-0334) is not implemented.
3. The rollup engine (GAP-0335) is not implemented.

In dev, the first call to any event-recording function that tries to access `analytics_events` will raise `ResourceNotFoundException: Requested resource not found`. In prod (real DynamoDB), the same error occurs. The missing table is not a localstack-specific issue; it is a universal gap.

### Dev vs prod parity

The gap is symmetric: the table does not exist in either environment. The fix (adding a `TableDef` entry in `local-ddb-init.py` for dev + an equivalent AWS CloudFormation / Terraform definition for prod) follows the existing pattern for every other table in the project.


## 3. Impact / Exploit / Blast Radius

**Functional impact**: The creator analytics dashboard (ANALYTICS-001) currently serves data only when `upsert_daily_rollup` is called manually (via `POST /refresh`) or via any service that directly calls the write function with pre-computed data. In the intended architecture, raw events flow into `analytics_events` first, the rollup engine aggregates them, and then the dashboard reads rollup rows. Without the raw events table, the pipeline is broken from the first step.

**Blast radius**:
- Every creator analytics metric that depends on automated event ingestion (page views, revenue events, subscriber events) will return zero or stale data.
- The `rollup_engine` (when implemented per GAP-0335) will query `analytics_events` and receive `ResourceNotFoundException`, causing the background task to crash on startup or on each rollup run.
- If `analytics_events.py` (GAP-0334) is deployed without this fix, every call to `record_page_view`, `record_revenue_event`, etc. crashes with a 500 error.

**Security / compliance**: No direct security impact. However, analytics data (revenue events, subscriber events) feeds into financial reporting and creator payouts. Missing revenue events means creator earnings may be understated or not reported, which is a billing-integrity concern.


## 4. Fix Design (code-level)

### 4a. Add table schema to `scripts/local-ddb-init.py`

The `analytics_events` table stores individual raw events with a TTL for automatic expiry. The GSI allows querying all events for a given creator in a date range (required by the rollup engine):

```python
# scripts/local-ddb-init.py — add inside _table_defs(), after the AnalyticsRollups entry

# Analytics Events raw log (ANALYTICS-001 / PLATFORM-019)
TableDef(
    os.environ.get("DDB_ANALYTICS_EVENTS", "analytics_events"),
    "pk",   # CREATOR#{creator_id}
    "sk",   # {event_type}#{ts_ms}#{event_id}
    gsi=[
        {
            "index_name": "GSI1",
            "partition_key": "GSI1PK",   # CREATOR#{creator_id}
            "sort_key":     "GSI1SK",    # DATE#{YYYY-MM-DD}
        },
    ],
    ttl_field="ttl_epoch",
),
```

The `ttl_field` parameter is already supported by the `TableDef` class (used by other tables, e.g. `account_deletion_requests`). The TTL ensures raw events are automatically purged after the configured retention window (default: 90 days), preventing unbounded table growth.

### 4e. Dev/Prod parity (SECOPS-007)

The fix follows the exact pattern used by every other DynamoDB table in the project:
- Dev: table created by `scripts/local-ddb-init.py` against DynamoDB Local (port 8001).
- Prod: table created by the infrastructure-as-code layer (CloudFormation / Terraform) using the same schema.
- Both environments use the `T.analytics_events` handle from `app/core/tables.py`, which routes to the correct endpoint via `DDB_ENDPOINT_URL`.

No mock or environment-specific branching is needed. DynamoDB Local behaves identically to real DynamoDB for all operations used here (PutItem, Query, GSI, TTL attribute).

### 4f. Key schema design notes

- **PK**: `CREATOR#{creator_id}` — all events for one creator are co-located on the same partition. This enables efficient creator-scoped queries without a table scan.
- **SK**: `{event_type}#{timestamp_ms}#{uuid4_hex8}` — allows sorting by time within a creator, with the event type and a random suffix for uniqueness.
- **GSI1PK / GSI1SK**: `GSI1PK = CREATOR#{creator_id}`, `GSI1SK = DATE#{YYYY-MM-DD}` — the rollup engine queries `GSI1PK = CREATOR#X AND GSI1SK BETWEEN DATE#2026-01-01 AND DATE#2026-01-31` to collect all events for a creator in a date range.
- **ttl_epoch**: Unix timestamp (seconds) set to `now_ts() + S.analytics_events_ttl_days * 86400` at write time. DynamoDB TTL deletes expired items automatically.

### Key schema rationale and trade-offs

The proposed schema deserves brief justification because DynamoDB table design decisions are difficult to change after data is stored.

**Why `pk = CREATOR#{creator_id}` and not a flat event table?**

A flat table (PK = `event_id`) would require a full table scan to aggregate per-creator data, which is O(all events ever). Co-locating all of a creator's events on one PK means a creator-scoped query is O(events for that creator), which is far more efficient. The downside is that popular creators become "hot partitions" if many events arrive per second. Mitigation: DynamoDB auto-scaling handles bursts; for extremely high-volume creators (top 0.1%) a time-based sub-partitioning scheme (`pk = CREATOR#{creator_id}#SHARD#{date}`) can be introduced later without breaking the current design.

**Why a GSI instead of the base table SK for date-range queries?**

The base table SK is `{event_type}#{timestamp_ms}#{uuid}` — optimised for writing (no collisions, ordered by time within type). A date-range query on the base SK would require a `begins_with("page_view#")` expression per event type, making cross-type aggregation awkward. The `GSI1` with `GSI1SK = DATE#{YYYY-MM-DD}` lets the rollup engine issue one query per (creator, date) and get all event types in a single pass. The trade-off is eventual consistency on the GSI (new events may not appear immediately); the rollup engine's `lookback_days=3` window compensates for this.

**TTL design**

Setting `ttl_epoch = now_ts() + S.analytics_events_ttl_days * 86400` (default 90 days) means raw events are automatically purged by DynamoDB after 90 days. The rollup aggregation should complete well within this window; rolled-up data in `AnalyticsRollups` is retained indefinitely (no TTL on that table). This is the correct trade-off: raw events are high-volume ephemeral data; rolled-up aggregates are low-volume durable data used for reporting.

**`attr_types` for GSI1SK**

The `GSI1SK` is a string (`DATE#{YYYY-MM-DD}`). The `TableDef` for this table must NOT include `attr_types={"GSI1SK": "N"}` — a common error in this codebase (noted in the CLAUDE.md "Common gotchas" section). String sort keys in GSIs are inferred as type `S` by default; specifying `"N"` would cause every write to fail with a DynamoDB key type mismatch.

### Infrastructure-as-code note

The `scripts/local-ddb-init.py` change covers the local dev environment. For production, the `analytics_events` table must also be added to the CloudFormation/CDK stack with:
- `BillingMode: PAY_PER_REQUEST` (event tables have unpredictable throughput spikes).
- TTL enabled via `TimeToLiveSpecification: {AttributeName: ttl_epoch, Enabled: true}`.
- The GSI projection set to `ALL` (the rollup engine reads multiple fields per event).
- Point-in-time recovery (PITR) enabled, consistent with other tables in the stack.
