# GAP-0030: No Break-Glass Secret or KMS Gate on CLI Mutations — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: The `rootctl` CLI is the platform's break-glass tool for root-level administration: resetting passwords, wiping MFA devices, revoking all sessions, and granting or revoking admin roles. These are the most destructive operations available on the platform. The only authentication gate before executing any of these mutations is a string-equality check: `actor_sub == root_sub`. Both `actor_sub` and `root_sub` are strings — one comes from a `--actor-sub` CLI flag supplied by whoever is running the command, the other from the `ROOT_USER_SUB` environment variable which is commonly a human-readable email address. There is no secret, password, OTP, cryptographic proof, or second factor of any kind. Anyone with DynamoDB read/write credentials who knows (or guesses) the root user's subject identifier can execute any mutation the CLI exposes.

- **Severity**: Critical (CRIT)
- **Source ticket**: ROOTCTL-001
- **Status**: Open
- **Owning area**: Root Admin / Operations Security / ROOTCTL
- **Effort**: M

**Verdict**: Partially confirmed — stronger than the ticket implied, but the core gap remains real. The investigation (`docs/tickets/gap-tickets/investigations/GAP-0030.md`) confirmed that `_validate_preflight` at `app/cli/rootctl.py:1980` enforces `reason`, `ticket`, `confirm`, and `actor_sub != ""` checks but contains no `ROOTCTL_BREAK_GLASS_SECRET` check or any other cryptographic/OTP gate. The `requires_root` check (`actor_sub == root_sub` at line 2010) is a string equality on a caller-supplied argument.

**One-line impact**: Any operator with DynamoDB credentials and knowledge of `ROOT_USER_SUB` can reset the root password, wipe all MFA, and mass-revoke every user session without needing any additional secret.

**Related tickets**: ROOTCTL-001 (source), SEC-022 (credential exposure), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### The preflight validation function

`app/cli/rootctl.py:1980–2034` defines `_validate_preflight(args)`:

```python
def _validate_preflight(args: argparse.Namespace) -> str:
    try:
        root_sub = validate_root_user_sub_config()
    except RuntimeError as exc:
        raise ValueError(str(exc)) from exc

    if not bool(getattr(args, "mutating", False)):
        return root_sub   # read-only commands bypass all further checks

    reason = str(getattr(args, "reason", "") or "").strip()
    if not reason:
        raise ValueError("reason is required for mutating commands")

    if bool(getattr(args, "requires_ticket", False)):
        ticket = str(getattr(args, "ticket", "") or "").strip()
        if not ticket:
            raise ValueError("ticket is required for high-risk commands")

    if bool(getattr(args, "requires_confirm", False)):
        confirm = str(getattr(args, "confirm", "") or "").strip()
        expected = str(getattr(args, "confirm_expected", "") or "").strip()
        if not confirm or not expected or confirm != expected:
            raise ValueError(f"confirm must match expected value: {expected}")

    actor_sub = str(getattr(args, "actor_sub", "") or "").strip()
    if not actor_sub:
        raise ValueError("actor_sub is required for mutating commands")

    if bool(getattr(args, "requires_root", False)) and actor_sub != root_sub:
        raise CliPolicyError(
            "root actor required for mutating command",
            details={"code": "role_required", ...},
        )
    ...
```

The `requires_root` check at line 2010 is `actor_sub != root_sub`. The `actor_sub` value comes from `argparse` parsing `--actor-sub` (line 2045 in `_add_mutation_guard_options`). It is a caller-supplied string with no cryptographic binding. Passing `--actor-sub root.admin@testdev.local` is sufficient to bypass the root gate.

### What `ROOT_USER_SUB` typically looks like

`validate_root_user_sub_config` reads `S.root_user_sub` from the `ROOT_USER_SUB` environment variable. In the dev stack this is `root.admin@testdev.local`. In production it is typically an email address or a cognito sub UUID. The email-address form is guessable from audit log entries, error messages, or the `e2e_admin_session_setup.py` script (which prints the root sub during setup).

### What is present

The existing guards are meaningful audit controls, not security controls:
- `reason` ensures intent is recorded.
- `ticket` ensures a change-management record exists.
- `confirm` matching `target_user_sub` prevents fat-finger mistakes.
- `actor_sub != ""` ensures someone claims responsibility.

None of these prevent a malicious actor from satisfying all conditions while supplying a forged `--actor-sub`.

### What is absent

A search across all of `app/cli/rootctl.py` and the broader `app/` codebase finds:
- Zero references to `ROOTCTL_BREAK_GLASS_SECRET`.
- Zero references to `getpass` being used for secret verification (it is imported at line 4 but only used for the CLI prompt display, not for secret verification).
- Zero KMS decrypt calls in the mutation path.
- Zero TOTP/OTP checks.

### Root cause

The CLI was designed with the implicit assumption that AWS IAM controls access to DynamoDB, making "who can run the tool at all" an infrastructure-layer concern. The `actor_sub` string equality was intended as an audit-trail mechanism ("record who acted") rather than as an authentication mechanism ("prove who you are"). The design never specified a second credential for the CLI itself; ROOTCTL-001 did not include a `ROOTCTL_BREAK_GLASS_SECRET` requirement in its original implementation plan.

## 3. Impact / Exploit / Blast Radius

### Threat model

The break-glass CLI is not exposed over HTTP; it requires direct access to the host running the tool. The realistic threat actors are:

1. **Compromised CI/CD pipeline**: A CI runner with DynamoDB write permissions (common for deployment automation) could be exploited to run `rootctl` mutations.
2. **Misconfigured IAM role**: An over-permissioned EC2 instance or Lambda with DynamoDB access.
3. **Insider threat**: A developer or DevOps engineer with AWS credentials who should not have root-level CLI power.
4. **Compromised developer workstation**: An attacker who gains shell access to a developer machine where AWS credentials are cached (`~/.aws/credentials`).

### Concrete exploit

```bash
# Attacker has DynamoDB credentials but should not have root CLI access:
export AWS_ACCESS_KEY_ID=<stolen_key>
export AWS_SECRET_ACCESS_KEY=<stolen_secret>
export ROOT_USER_SUB=root.admin@company.com   # guessed from audit log

python -m app.cli.rootctl root reset-password \
  --actor-sub "root.admin@company.com" \
  --reason "maintenance" \
  --confirm "root.admin@company.com" \
  --new-password "AttackerControlledPassword1!"

# Result: root account password changed to attacker-controlled value.
# Attacker can now log in as root via the web application.
```

Variant 2 — mass session revocation (denial of service):

```bash
python -m app.cli.rootctl user revoke-all-sessions \
  --actor-sub "root.admin@company.com" \
  --reason "security incident" \
  --target-user-sub "*"
```

### Worst-case chain

1. Attacker resets root password via CLI.
2. Attacker logs in as root via the web application.
3. Attacker uses the root session to grant themselves admin privileges.
4. Attacker accesses all user data, billing records, and private messages via admin APIs.

### Blast radius quantification

- **Full platform compromise**: The root account has access to every admin endpoint, every user's data, and every financial record.
- **Irreversibility**: Session revocation is immediate. Password reset is immediate. Recovery requires a platform-level re-bootstrap if the root account is locked out.
- **No indicator of compromise without audit logging**: The mutation writes an audit log entry — but if the attacker also has DynamoDB write permissions, they can delete the audit log entry after the fact.

## 4. Fix Design (Code-Level)

### New function: `_require_break_glass_auth()`

Add to `app/cli/rootctl.py` after the existing imports (after `import getpass` at line 4 and `import os` at line 6):

```python
import hmac

_BREAK_GLASS_ENV = "ROOTCTL_BREAK_GLASS_SECRET"
_BREAK_GLASS_TOKEN_ENV = "ROOTCTL_BREAK_GLASS_TOKEN"


def _require_break_glass_auth() -> None:
    """Verify ROOTCTL_BREAK_GLASS_SECRET before any mutating CLI command.

    The secret is read from ROOTCTL_BREAK_GLASS_SECRET (env).
    The token provided by the operator is read from ROOTCTL_BREAK_GLASS_TOKEN
    (env) or prompted interactively via getpass.
    Uses hmac.compare_digest to prevent timing attacks.
    """
    expected = os.environ.get(_BREAK_GLASS_ENV, "").strip()
    if not expected:
        raise CliPolicyError(
            f"{_BREAK_GLASS_ENV} is not configured; CLI mutations are disabled. "
            "Set the environment variable to enable break-glass operations.",
            details={"code": "break_glass_unconfigured"},
        )

    # Prefer env-var token (for non-interactive CI/CD with secrets manager injection)
    provided = os.environ.get(_BREAK_GLASS_TOKEN_ENV, "").strip()
    if not provided:
        try:
            provided = getpass.getpass(
                "Break-glass secret (or set ROOTCTL_BREAK_GLASS_TOKEN): "
            ).strip()
        except (EOFError, KeyboardInterrupt):
            provided = ""

    if not provided:
        raise CliPolicyError(
            "break-glass authentication failed: no token provided",
            details={"code": "break_glass_no_token"},
        )

    if not hmac.compare_digest(
        provided.encode("utf-8"), expected.encode("utf-8")
    ):
        raise CliPolicyError(
            "break-glass authentication failed: invalid token",
            details={"code": "break_glass_auth_failed"},
        )
```

### Integration into `_validate_preflight`

In `_validate_preflight` at `app/cli/rootctl.py:1986`, insert the `_require_break_glass_auth()` call as the first check for mutating commands — before `reason`, `ticket`, `confirm`, and `actor_sub` checks:

```python
def _validate_preflight(args: argparse.Namespace) -> str:
    try:
        root_sub = validate_root_user_sub_config()
    except RuntimeError as exc:
        raise ValueError(str(exc)) from exc

    if not bool(getattr(args, "mutating", False)):
        return root_sub

    _require_break_glass_auth()   # ← ADD THIS LINE (first check for all mutations)

    reason = str(getattr(args, "reason", "") or "").strip()
    ...  # existing checks unchanged
```

By placing `_require_break_glass_auth()` before all other checks, mutations are blocked immediately if the secret is wrong, without leaking information about which specific checks would follow.

### Secret generation and management

**Dev environment** (`scripts/setup_ubuntu.sh`): Generate and store the break-glass secret alongside other secrets:

```bash
# In setup_ubuntu.sh, alongside existing secret generation:
ROOTCTL_BREAK_GLASS_SECRET=$(python3 -c "import secrets; print(secrets.token_hex(32))")
echo "ROOTCTL_BREAK_GLASS_SECRET=${ROOTCTL_BREAK_GLASS_SECRET}" >> .env.local
```

**Production**: Store `ROOTCTL_BREAK_GLASS_SECRET` in AWS Secrets Manager or Parameter Store (SecureString). The operator retrieves and exports it immediately before a break-glass operation:

```bash
export ROOTCTL_BREAK_GLASS_SECRET=$(aws secretsmanager get-secret-value \
  --secret-id rootctl/break-glass-secret --query SecretString --output text)
# Then run the CLI command; secret is in memory for the duration of the session only.
```

**KMS-enhanced path (optional higher assurance)**: Store the secret as a KMS-encrypted blob. Require the operator to have KMS decrypt permission as a second IAM gate:

```bash
export ROOTCTL_BREAK_GLASS_SECRET=$(aws kms decrypt \
  --ciphertext-blob fileb:///etc/rootctl/break-glass.enc \
  --output text --query Plaintext | base64 --decode)
```

This adds a second AWS IAM control (KMS `kms:Decrypt` permission) on top of the DynamoDB permissions, providing defense-in-depth against IAM misconfiguration.

### Dev/Prod Parity (SECOPS-007)

In dev mode, `ROOTCTL_BREAK_GLASS_SECRET` is set to a known dev value in `.env.local` (e.g., `dev-break-glass`). The same code path runs in both environments — no dev-mode bypass is added to `_require_break_glass_auth`. This is intentional: the break-glass gate must be exercised in dev to ensure it is configured correctly before production use. The dev secret is low-assurance by design (it is checked into `.env.local.example` as a well-known value) but ensures the code path is tested.

Read-only commands (`mutating=False`) bypass `_require_break_glass_auth` entirely, so `just status` and other non-mutating invocations are unaffected. This preserves existing dev workflows.

### Backward compatibility

All existing rootctl invocations that do not set `ROOTCTL_BREAK_GLASS_SECRET` will fail immediately with a clear error message. This is the intended behavior — the absence of the secret must be a hard failure, not a silent bypass. After deployment, all automated scripts and runbooks that invoke mutating rootctl commands must be updated to source or inject `ROOTCTL_BREAK_GLASS_SECRET`.

   Should proceed past the break-glass gate to the remaining preflight checks.

### Metrics and observability

- Add a structured log line when `_require_break_glass_auth` succeeds: `logger.warning("rootctl.break_glass_auth_success actor=%s command=%s", actor_sub, command)`. Use `WARNING` level because every successful break-glass authentication is a significant security event that should be visible in monitoring.
- Add a log line on failure: `logger.critical("rootctl.break_glass_auth_failure token_length=%d", len(provided))`.
- In production, configure a CloudWatch alarm for any `rootctl.break_glass_auth_failure` event — this may indicate a brute-force attempt or misconfigured automation.

### Rollout sequence

1. Generate `ROOTCTL_BREAK_GLASS_SECRET` in `setup_ubuntu.sh` and commit the `setup_ubuntu.sh` change.
2. Add `ROOTCTL_BREAK_GLASS_SECRET` to `.env.local.example` with a placeholder value.
3. Update production secrets manager with the production break-glass secret.
4. Update all CI/CD automation and runbooks that invoke mutating rootctl commands.
5. Deploy the code change.
6. Verify no existing automation breaks (all automated mutating commands should have been updated in step 4).

### Rollback

Revert the code change. The `ROOTCTL_BREAK_GLASS_SECRET` env var is additive — its absence before the fix is the gap being remediated. Removing the check restores the pre-fix behavior.

### Risks

- **Automation breakage**: Any CI/CD pipeline or cron job that runs mutating rootctl commands without sourcing `ROOTCTL_BREAK_GLASS_SECRET` will fail after the fix is deployed. A comprehensive audit of all rootctl invocations in automation scripts is required before deployment.
- **Operator lockout**: If `ROOTCTL_BREAK_GLASS_SECRET` is lost or corrupted in the secrets manager, all mutating CLI operations are blocked. A recovery procedure (re-seeding the secret from a backup) must be documented before production deployment.
- **Secret rotation**: The break-glass secret should be rotated periodically. A rotation procedure that updates both the secrets manager entry and notifies all operators must be established.

### Effort and sequencing

**M** — the `_require_break_glass_auth` function (~30 lines), one call-site insertion in `_validate_preflight`, secret generation in `setup_ubuntu.sh`, production secrets-manager wiring, runbook updates, and tests. Estimated effort: 1–2 days.
