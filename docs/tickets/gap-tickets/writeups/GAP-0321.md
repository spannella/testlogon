# GAP-0321: `locale` Field Absent from User Profile Model — Remediation Write-up

> **Claim status**: INCORRECT — the `locale` field is fully implemented and validated.
> This write-up documents the actual state, why the gap ticket was raised in error, and
> what residual (genuine) gaps remain after careful review.

---

## 1. Summary & Classification

**Source ticket**: PLATFORM-003 (i18n / locale support)
**Severity as filed**: HIGH
**Status**: Closed — already implemented
**Owning area**: Profile service / i18n subsystem

The gap ticket claims that `locale` is absent from the user profile model and that no validation against `I18N_SUPPORTED_LOCALES` has been added. Both claims are wrong. The field was introduced during the PLATFORM-003 implementation and is present in the Pydantic model, the service layer, and the DynamoDB read/write paths.

**Verdict**: The original claim is inaccurate. `locale: Optional[str] = None` appears in `ProfileBase` at `app/models.py:1386`, is listed in `PROFILE_FIELDS` at `app/services/profile.py:32`, and is validated against `S.i18n_supported_locales` in the service at `app/services/profile.py:188-195`. No product code change is required.

The sole residual gap worth noting is that the `locale` field is classified `"private"` in `PROFILE_FIELD_VISIBILITY` (`app/services/profile.py:56`), so it is never exposed in the public profile response (`PublicProfileResponse`, `app/models.py:2683`). That is arguably the correct design (the user's language preference is personal), but it means the SEO metadata service (`app/services/seo_metadata.py`) cannot use the stored locale to set `og:locale` per-user. That is a minor omission, not a security or data-integrity issue, and is not what the filed ticket described.

**Related tickets**: GAP-0322 (backend meta endpoint), GAP-0323 (crawler-detection middleware); all three share source ticket PLATFORM-003 / PLATFORM-005.

`ProfilePatchReq` (line 1389) and `ProfilePutReq` (line 1393) both inherit from `ProfileBase` via `pass`, so the field is accepted by both the `PATCH /ui/profile` and `PUT /ui/profile` endpoints without any change.

### 2.2 Service layer — field is stored and validated

`app/services/profile.py:16-33` defines the canonical field list:

```python
PROFILE_FIELDS = (
    "display_name", "first_name", "middle_name", "last_name",
    "title", "description", "birthday", "gender", "location",
    "displayed_email", "displayed_telephone_number",
    "mailing_address", "languages",
    "profile_photo_url", "cover_photo_url",
    "locale",            # line 32 — PRESENT

```

The `_normalize_profile_data()` function is the single entry-point for all profile writes. It handles `locale` at lines 188-195:

```python
if "locale" in data:
    locale_val = _clean_str(data.get("locale"), max_len=10)
    # Validate against supported locales
    from app.core.settings import S as _settings
    supported = [loc.strip() for loc in _settings.i18n_supported_locales.split(",")
                 if loc.strip()]
    if locale_val and locale_val not in supported:
        raise HTTPException(400, "unsupported locale")
    out["locale"] = locale_val
```

The `max_len=10` cap prevents trivially long locale strings. The `HTTPException(400)` guard rejects any value not listed in the `I18N_SUPPORTED_LOCALES` configuration, raising a structured error before any DynamoDB write. The default empty-profile factory at line 199 also seeds `"locale": None`, ensuring the attribute is present in every new user's DDB record from creation, avoiding missing-key edge cases in downstream readers.

### 2.3 Settings configuration

`app/core/settings.py:1841`:

```python
i18n_supported_locales: str = os.environ.get("I18N_SUPPORTED_LOCALES", "en,es,fr")
```

The `I18N_SUPPORTED_LOCALES` environment variable directly controls which locale codes are accepted at runtime. The default of `"en,es,fr"` is sufficient for initial rollout. Operators can extend the list without a code deployment by updating the environment variable and restarting the backend.

### 2.4 i18n module integration

`app/i18n/__init__.py:52-59` exposes two convenience helpers that read the same setting:

```python
def get_supported_locales() -> list[str]:
    return [loc.strip() for loc in S.i18n_supported_locales.split(",") if loc.strip()]

def is_supported_locale(locale: str) -> bool:
    return locale in get_supported_locales()
```

The `get_user_locale_from_request()` function at line 62 implements a full three-tier resolution strategy:
1. Check `request.state.auth_context["locale"]` (populated from the session's stored profile locale).
2. Parse the `Accept-Language` HTTP header and take the first BCP-47 primary subtag.
3. Fall back to `S.i18n_default_locale` (default: `"en"`).

This means every authenticated request already carries the user's stored locale preference through the request context. The pipeline from storage to request context to response translation is complete.

### 2.5 PROFILE_FIELD_VISIBILITY controls exposure

`app/services/profile.py:40-57` assigns a visibility level to each field. `locale` is classified `"private"`:

```python
PROFILE_FIELD_VISIBILITY = {
    "display_name": "public",
    ...
    "locale": "private",    # line 56
}
```

This means `locale` is visible to the owning user but not to other users or anonymous callers. The `PublicProfileResponse` model (`app/models.py:2683`) does not include a `locale` field at all. This is the architecturally correct design — a user's language preference is a private setting analogous to their birthday or phone number.

### 2.6 Why the ticket was raised

The gap ticket was generated by a second-pass audit that ran before the PLATFORM-003 implementation PR was merged into the main branch. At the time the audit ran, the `locale` field may genuinely have been absent from the model. The ticket was not closed or marked "resolved" when the implementation landed, leading to its appearance in the gap backlog.

### 2.7 Genuine residual gap (og:locale not per-user)

Because `locale` is classified `"private"`, the SEO metadata service (`app/services/seo_metadata.py`) cannot read it for a given user and therefore hardcodes `DEFAULT_LOCALE = "en_US"` for all profile-type OG metadata (line 38). A French creator whose stored locale is `"fr"` will have their profile shared with `og:locale = "en_US"` rather than `og:locale = "fr_FR"`. This is a minor SEO quality gap — it does not affect security, data integrity, or financial flows — and is not what the filed ticket described.

## 3. Impact / Exploit / Blast Radius

Because the locale field is implemented and validated, there is **no security or data-integrity impact** from this ticket. Attempting to send an unsupported locale string via `PATCH /ui/profile` will return `HTTP 400 "unsupported locale"` before any DDB write occurs.

**Normal users**: no impact. The locale round-trips correctly. A user who sets their locale to `"es"` will have Spanish UI strings served on subsequent requests via `get_user_locale_from_request()`.

**Malicious input**: any attempt to inject an unexpected locale string (e.g., `../../../../etc/passwd`, an XSS payload, a non-BCP-47 string) is rejected by the service-layer validation (line 193: `raise HTTPException(400, "unsupported locale")`) and additionally capped to 10 characters by `_clean_str(..., max_len=10)`.

**Misconfigured production environment**: if `I18N_SUPPORTED_LOCALES` is missing or set to an empty string, `get_supported_locales()` returns an empty list. In that state, any non-None locale value in the PATCH body will be rejected with 400 (because the empty list doesn't contain any valid locale). This is a misconfiguration risk that could cause `PATCH /ui/profile` with a locale to fail unexpectedly. However, the default hard-coded in `app/core/settings.py:1841` (`"en,es,fr"`) means the variable only becomes relevant when operators wish to extend the supported set.

**SEO quality impact**: The sole practical consequence of the `"private"` visibility classification is that the SEO metadata service at `app/services/seo_metadata.py:38` hardcodes `DEFAULT_LOCALE = "en_US"` for all profile-type OG metadata. A multilingual creator whose bio is in Spanish (`locale = "es"`) has their profile shared on social platforms with `og:locale = "en_US"` rather than `og:locale = "es_ES"`. This affects share-preview metadata quality but not security, finances, or availability.

**Blast radius**: effectively zero for this ticket's stated claim. The ticket should be closed as resolved.

## 4. Fix Design (code-level)

Because the core claim is incorrect — the field and validation already exist — no changes to the profile model or service are required.

### 4.1 Recommended cosmetic improvement: pass user locale to SEO metadata

To resolve the residual `og:locale` gap, `_profile_metadata()` in `app/services/seo_metadata.py:177` could read the user's stored locale and convert it to BCP-47 format:

```python
# In _profile_metadata(), after reading `profile`:
raw_locale = _clean(profile.get("locale")) or "en"
og_locale = raw_locale.replace("-", "_")          # e.g. "fr" → "fr", "pt-BR" → "pt_BR"
# Then in _assemble() call, pass og_locale to override DEFAULT_LOCALE.
```

This is a one-line addition and does not affect any security boundary. The stored locale string is already validated against `I18N_SUPPORTED_LOCALES` at write time, so it is safe to use directly in the OG tag without further sanitization beyond `html.escape()` (already applied by `render_meta_tags()`).

### 4.2 Dev/Prod parity (SECOPS-007)

The profile write path is identical in dev mode and production. In dev mode, the `_normalize_profile_data()` validation still runs. The `I18N_SUPPORTED_LOCALES` setting is controlled by `.env.local` in dev and by the equivalent environment variable in production. No mock path bypasses the validation. No changes are needed.

### 4.3 Alternatives considered

- Exposing `locale` in `PublicProfileResponse` to allow frontend-side `og:locale` injection via `react-helmet-async`: rejected because locale is a personal preference, not a public attribute, and client-side Helmet tags do not reach social bots (the core SEO problem addressed by GAP-0323).
- Adding a Pydantic validator to `ProfileBase` for locale: unnecessary since service-layer validation at write time is the correct boundary in this architecture (the model accepts `Optional[str]` and the router always calls the service layer).

## 5. Testing, Verification & Rollout

### 5.1 Regression test — fails before (hypothetical) and passes after

The following pytest test verifies the full locale write-validate-read cycle using the offline in-memory test client:

```python
# tests/test_profile_locale.py
import pytest

def test_locale_accepted_when_supported(client_alice):
    """PUT /ui/profile with a supported locale must persist it."""
    resp = client_alice.patch("/ui/profile", json={"locale": "es"})
    assert resp.status_code == 200
    get = client_alice.get("/ui/profile")
    assert get.json()["locale"] == "es"


def test_locale_rejected_when_unsupported(client_alice, monkeypatch):
    """PATCH with an unsupported locale must return 400."""
    import app.core.settings as _s
    monkeypatch.setattr(_s.S, "i18n_supported_locales", "en,es,fr")
    resp = client_alice.patch("/ui/profile", json={"locale": "klingon"})
    assert resp.status_code == 400
    assert "unsupported locale" in resp.json().get("detail", "")


def test_locale_cleared_with_null(client_alice):
    """Setting locale to None must clear it."""
    client_alice.patch("/ui/profile", json={"locale": "fr"})
    resp = client_alice.patch("/ui/profile", json={"locale": None})
    assert resp.status_code == 200
    get = client_alice.get("/ui/profile")
    assert get.json()["locale"] is None


def test_locale_not_exposed_in_public_profile(client_alice, client_anon):
    """locale must not appear in the public profile response."""
    client_alice.patch("/ui/profile", json={"locale": "fr"})
    resp = client_anon.get("/ui/profile/alice")
    assert "locale" not in resp.json()
```

These tests exercise the `_normalize_profile_data()` path, the `HTTPException(400)` guard, and the visibility rule. They run fully offline using moto DynamoDB — no real AWS credentials required.
