# GAP-0334: `analytics_events.py` service not implemented — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/services/creator_analytics.py`, `app/routers/creator_analytics.py`, and `app/core/tables.py`.

## 1. Summary & Classification

**Gap**: The `analytics_events.py` service file — which should expose `record_page_view`, `record_revenue_event`, `record_subscriber_event`, and `record_engagement_event` for writing raw event data to the `analytics_events` DynamoDB table — does not exist anywhere in `app/services/`. The creator analytics dashboard endpoints in `app/routers/creator_analytics.py` serve aggregated rollup data from `T.analytics_rollups`, but the automated pipeline that feeds raw events into `analytics_events` first has no implementation. Without this service, no raw analytics data is ever stored and the rollup engine (GAP-0335) has nothing to aggregate.

**Claim status**: Confirmed. A search across all `app/services/*.py` files finds no `analytics_events.py` file, no `record_page_view`, no `record_revenue_event`, no `record_subscriber_event`, and no `record_engagement_event` function definitions anywhere. The gap is real and complete.

**Severity**: HIGH — all four event recording functions are missing. The analytics pipeline's input layer is entirely absent, meaning every analytics metric on the creator dashboard is either zero (if no rollup row exists) or stale (if a manual rollup was ever triggered for a creator). This affects revenue reporting, audience analytics, and subscriber metrics.

**Source ticket**: PLATFORM-019. **Status**: Open. **Effort**: M. **Owning area**: Analytics / Creator Tools.

**Related tickets**: GAP-0333 (analytics_events table not created — prerequisite), GAP-0335 (rollup engine not implemented — dependent), GAP-0337 (zero event instrumentation in any router). GAP-0334 is the core recording layer; GAP-0337 tracks the upstream call sites in routers that need to call these functions.


## 2. Current-State Investigation (root cause)

### Architecture intent vs implementation reality

The ANALYTICS-001 / PLATFORM-019 design specifies a three-layer pipeline:

```
Router events (views, revenue, subscriptions, engagement)
    ↓  record_*() functions
analytics_events DynamoDB table (raw, TTL-tagged)
    ↓  rollup engine (GAP-0335)
analytics_rollups DynamoDB table (aggregated daily rows)
    ↓  creator_analytics.py
Dashboard endpoints
```

Layers 3 and 4 are implemented (`app/services/creator_analytics.py` reads from `T.analytics_rollups`; the router exposes the dashboard endpoints). Layer 2 (`analytics_events` table) is absent per GAP-0333. Layer 1 (`analytics_events.py` recording service) is the subject of this ticket and is entirely absent.

### What `creator_analytics.py` does today

`app/services/creator_analytics.py` exposes `upsert_daily_rollup(user_id, date_str, data)` at line 523, which writes directly to `T.analytics_rollups`. The manual refresh endpoint (`POST /ui/analytics/refresh`, `app/routers/creator_analytics.py:303`) calls `upsert_daily_rollup` with zeros or with data sourced from other tables. This is a bypass of the event-first pipeline and produces inaccurate data because it skips event aggregation entirely.

The settings file (`app/core/settings.py:1751`) defines `analytics_rollup_enabled`, `analytics_rollup_interval_seconds`, and `analytics_rollup_lookback_days`, confirming that a background rollup loop was intended. The rollup engine (GAP-0335) is supposed to read `analytics_events` and call `upsert_daily_rollup`. Neither piece exists.

### Missing functions — specification

Based on the gap ticket and the existing `creator_analytics.py` rollup schema (fields like `total_views`, `unique_viewers`, `watch_time_seconds`, `revenue_cents`, `new_subscribers`, `post_reactions`, `post_comments`), the four recording functions need the following signatures and semantics:

| Function | Trigger | Key fields written to `analytics_events` |
|---|---|---|
| `record_page_view(creator_id, content_id, viewer_id, watch_time_seconds)` | Content view / VOD play | `event_type="page_view"`, `content_id`, `viewer_id`, `watch_time_seconds` |
| `record_revenue_event(creator_id, revenue_type, amount_cents, subscriber_id, content_id)` | Purchase, tip, unlock, subscription renewal, ad revenue | `event_type="revenue"`, `revenue_type` (sub/tip/unlock/vod/ad/call), `amount_cents` |
| `record_subscriber_event(creator_id, subscriber_id, event_kind)` | New subscription, cancellation, renewal, churn | `event_type="subscriber"`, `event_kind` (new/renewed/cancelled/churned) |
| `record_engagement_event(creator_id, content_id, actor_id, action)` | Reaction, comment, share | `event_type="engagement"`, `action` (reaction/comment/share) |

### Dev vs prod parity

The gap is symmetric: neither environment has the recording service. The fix is pure Python (no AWS-specific code beyond DynamoDB writes via `T.analytics_events`), and will work identically in dev (DynamoDB Local) and prod (real DynamoDB) by design.


## 3. Impact / Exploit / Blast Radius

**Functional impact**: Creator analytics metrics are permanently zero or fabricated. Creators making monetisation decisions — which content to post, what subscription price to set, which audience segments to target — are operating without data. This is a significant product-completeness gap for a platform with creator analytics as a first-class feature.

**Financial / billing integrity**: `record_revenue_event` is the source-of-truth input for creator revenue analytics. Without it, the `revenue_cents` breakdown on the analytics dashboard is always zero even when the creator is earning. If earnings reports are ever used for tax or payout calculations (e.g. 1099 generation), missing event data is a financial reporting risk.

**Blast radius**:
- All creators on the platform (as soon as they check their analytics dashboard).
- The rollup engine (GAP-0335) once implemented will produce zero-row outputs since no events exist to aggregate.
- Any downstream feature that depends on analytics event history (recommendations, creator tiers, featured-creator logic) will be starved of data.

**No security exploit** — this gap is a functional completeness issue, not a vulnerability.


## 4. Fix Design (code-level)

### 4a. Create `app/services/analytics_events.py`

The service is a pure write layer. Reads happen only in the rollup engine (GAP-0335). All four functions write to `T.analytics_events` with consistent key structure and TTL:

```python
"""Analytics event recording service (ANALYTICS-001 / PLATFORM-019).

Writes raw event records to the analytics_events DynamoDB table.
Records are TTL-tagged for automatic expiry after S.analytics_events_ttl_days.
The rollup engine (analytics_rollup_engine.py) aggregates these into daily rows
in the analytics_rollups table for the creator dashboard.

Event key schema:
  PK: CREATOR#{creator_id}
  SK: {event_type}#{timestamp_ms}#{short_uuid}
  GSI1PK: CREATOR#{creator_id}
  GSI1SK: DATE#{YYYY-MM-DD}    ← used by rollup engine to query by date
"""
from __future__ import annotations

import logging
import uuid
from datetime import datetime, timezone
from typing import Optional

from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts

logger = logging.getLogger(__name__)

_ANON = "anonymous"


def _event_sk(event_type: str, ts_ms: int) -> str:
    uid = uuid.uuid4().hex[:8]
    return f"{event_type}#{ts_ms:016d}#{uid}"


def _date_from_ts(ts: int) -> str:
    return datetime.fromtimestamp(ts, tz=timezone.utc).strftime("%Y-%m-%d")


def _ttl(ts: int) -> int:
    return ts + S.analytics_events_ttl_days * 86400


def record_page_view(
    creator_id: str,
    content_id: str,
    viewer_id: Optional[str] = None,
    watch_time_seconds: int = 0,
) -> None:
    """Record a content page view or VOD play event."""
    try:
        ts = now_ts()
        ts_ms = ts * 1000
        date_str = _date_from_ts(ts)
        T.analytics_events.put_item(Item={
            "pk": f"CREATOR#{creator_id}",
            "sk": _event_sk("page_view", ts_ms),
            "GSI1PK": f"CREATOR#{creator_id}",
            "GSI1SK": f"DATE#{date_str}",
            "event_type": "page_view",
            "creator_id": creator_id,
            "content_id": content_id,
            "viewer_id": viewer_id or _ANON,
            "watch_time_seconds": watch_time_seconds,
            "created_at": ts,
            "ttl_epoch": _ttl(ts),
        })
    except Exception:
        logger.exception("analytics.record_page_view failed creator=%s content=%s", creator_id, content_id)


def record_revenue_event(
    creator_id: str,
    revenue_type: str,
    amount_cents: int,
    subscriber_id: Optional[str] = None,
    content_id: Optional[str] = None,
) -> None:
    """Record a revenue event (subscription, tip, unlock, VOD, ad, call).

    revenue_type must be one of: 'subscription', 'tip', 'unlock', 'vod', 'ad', 'call'.
    """
    _VALID_TYPES = {"subscription", "tip", "unlock", "vod", "ad", "call"}
    if revenue_type not in _VALID_TYPES:
        logger.warning("analytics.record_revenue_event unknown type=%s", revenue_type)
        revenue_type = "other"
    try:
        ts = now_ts()
        ts_ms = ts * 1000
        date_str = _date_from_ts(ts)
        item = {
            "pk": f"CREATOR#{creator_id}",
            "sk": _event_sk("revenue", ts_ms),
            "GSI1PK": f"CREATOR#{creator_id}",
            "GSI1SK": f"DATE#{date_str}",
            "event_type": "revenue",
            "revenue_type": revenue_type,
            "creator_id": creator_id,
            "amount_cents": amount_cents,
            "created_at": ts,
            "ttl_epoch": _ttl(ts),
        }
        if subscriber_id:
            item["subscriber_id"] = subscriber_id
        if content_id:
            item["content_id"] = content_id
        T.analytics_events.put_item(Item=item)
    except Exception:
        logger.exception(
            "analytics.record_revenue_event failed creator=%s type=%s cents=%d",
            creator_id, revenue_type, amount_cents,
        )


def record_subscriber_event(
    creator_id: str,
    subscriber_id: str,
    event_kind: str,
) -> None:
    """Record a subscription lifecycle event.

    event_kind must be one of: 'new', 'renewed', 'cancelled', 'churned'.
    """
    _VALID_KINDS = {"new", "renewed", "cancelled", "churned"}
    if event_kind not in _VALID_KINDS:
        logger.warning("analytics.record_subscriber_event unknown kind=%s", event_kind)
        event_kind = "other"
    try:
        ts = now_ts()
        ts_ms = ts * 1000
        date_str = _date_from_ts(ts)
        T.analytics_events.put_item(Item={
            "pk": f"CREATOR#{creator_id}",
            "sk": _event_sk("subscriber", ts_ms),
            "GSI1PK": f"CREATOR#{creator_id}",
            "GSI1SK": f"DATE#{date_str}",
            "event_type": "subscriber",
            "event_kind": event_kind,
            "creator_id": creator_id,
            "subscriber_id": subscriber_id,
            "created_at": ts,
            "ttl_epoch": _ttl(ts),
        })
    except Exception:
        logger.exception(
            "analytics.record_subscriber_event failed creator=%s kind=%s sub=%s",
            creator_id, event_kind, subscriber_id,
        )


def record_engagement_event(
    creator_id: str,
    content_id: str,
    actor_id: str,
    action: str,
) -> None:
    """Record a content engagement event (reaction, comment, share).

    action must be one of: 'reaction', 'comment', 'share'.
    """
    _VALID_ACTIONS = {"reaction", "comment", "share"}
    if action not in _VALID_ACTIONS:
        logger.warning("analytics.record_engagement_event unknown action=%s", action)
        action = "other"
    try:
        ts = now_ts()
        ts_ms = ts * 1000
        date_str = _date_from_ts(ts)
        T.analytics_events.put_item(Item={
            "pk": f"CREATOR#{creator_id}",
            "sk": _event_sk("engagement", ts_ms),
            "GSI1PK": f"CREATOR#{creator_id}",
            "GSI1SK": f"DATE#{date_str}",
            "event_type": "engagement",
            "action": action,
            "creator_id": creator_id,
            "content_id": content_id,
            "actor_id": actor_id,
            "created_at": ts,
            "ttl_epoch": _ttl(ts),
        })
    except Exception:
        logger.exception(
            "analytics.record_engagement_event failed creator=%s content=%s action=%s",
            creator_id, content_id, action,
        )
```

### 4b. Error handling design

All four functions use a `try/except Exception` wrapper that logs and swallows errors. This is the correct pattern for analytics instrumentation: a failed event recording must never cause a request to the primary business endpoint (post creation, message send, subscription signup) to fail. Analytics recording is fire-and-forget from the caller's perspective.

### 4c. Call sites (GAP-0337 scope — not in this ticket)

The recording functions must be called from the appropriate routers. This is tracked separately under GAP-0337 ("zero event instrumentation in any router"). The table below documents the intended instrumentation to be implemented in GAP-0337:

| Recording call | Call site router | Trigger |
|---|---|---|
| `record_page_view(post.author_id, post_id, viewer_id)` | `app/routers/newsfeed.py` → `GET /posts/{id}` | Post view |
| `record_page_view(video.creator_id, video_id, viewer_id, watch_time)` | VOD router | VOD play |
| `record_revenue_event(creator_id, "tip", amount_cents, subscriber_id=tipper_id)` | `app/routers/newsfeed.py` → `POST /posts/{id}/tip` | Post tip |
| `record_revenue_event(creator_id, "subscription", amount_cents, subscriber_id)` | `app/routers/subscription_server.py` → subscribe | New/renewed subscription |
| `record_subscriber_event(creator_id, subscriber_id, "new")` | `app/routers/subscription_server.py` → subscribe | New subscription |
| `record_subscriber_event(creator_id, subscriber_id, "cancelled")` | `app/routers/subscription_server.py` → cancel | Cancellation |
| `record_engagement_event(post.author_id, post_id, reactor_id, "reaction")` | `app/routers/newsfeed.py` → `POST /posts/{id}/reactions` | Reaction |

### 4d. Dev/Prod parity (SECOPS-007)

The service uses only `T.analytics_events` (DynamoDB via `app/core/tables.py`). No new AWS dependency is introduced. In dev the table resolves to DynamoDB Local; in prod to real DynamoDB. No `if S.dev_mode` branching is needed. The `try/except` wrappers ensure that if the table is not yet created in a dev environment (e.g. before running `local-ddb-init.py`), recording silently no-ops instead of crashing.

### Idempotency and duplicate event protection

Each recording function generates a unique SK via `_event_sk(event_type, ts_ms)` which appends an 8-character UUID suffix. This means two calls with identical arguments will produce two separate DynamoDB rows — which is correct behaviour (two page views by the same viewer count as two events). However, if a router calls a recording function and the request is retried (e.g. due to a network error), the event may be recorded twice. The rollup engine then over-counts.

For high-impact events (revenue, subscriber lifecycle) an optional idempotency key can be added:

```python
def record_revenue_event(
    creator_id: str,
    revenue_type: str,
    amount_cents: int,
    subscriber_id: Optional[str] = None,
    content_id: Optional[str] = None,
    idempotency_key: Optional[str] = None,   # e.g. billing transaction ID
) -> None:
    ...
    sk = idempotency_key or _event_sk("revenue", ts_ms)
    # Use put_item with ConditionExpression=attribute_not_exists(sk)
    # to prevent double-writes on retry
```

For the MVP, idempotency keys are optional. The rollup lookback window of 3 days means a duplicate event from a retry would affect at most 3 days of metrics by a small fraction — acceptable for analytics. Revenue-critical deduplication should be handled in the billing service (billing ledger rows are already idempotent), not in analytics recording.

### Graceful degradation if table not yet created

The `try/except Exception` wrapper in each recording function is intentional. If the `analytics_events` table does not yet exist (e.g. in a fresh dev environment before running `just up`, or during a rolling deploy where GAP-0333 has not yet been applied), recording functions fail silently with a log warning rather than raising a 500 to the caller. This is consistent with the analytics-as-optional-instrumentation design: the analytics layer must never impede the primary business transaction. In production, a CloudWatch alarm on `analytics.record_*_failed` error log lines signals when the table is missing or misconfigured so the issue can be remediated without user impact.
