# GAP-0189: Multi-Stage Reminder Schedule Not Implemented — Remediation Write-up

> Source ticket: FIN-003 · Severity: HIGH · Effort: L · Status: Open

## 1. Summary & Classification

**Bug statement.** The FIN-003 specification for cart abandonment calls for a
configurable multi-stage reminder schedule: each cart should progress through a
numbered sequence of reminder stages (e.g. Stage 1 at 24 h, Stage 2 at 72 h with a
different subject and body, Stage 3 at 168 h with a discount offer). The current
implementation (`app/services/shoppingcart.py:781–846`) sends a single, hardcoded
reminder per eligible cart per cooldown window. There is no concept of stages, no per-
stage configuration, and the background loop (`app/routers/shoppingcart.py:266–290`)
simply calls `send_cart_reminder(cart)` once for every cart returned by
`scan_abandoned_carts`. A cart is considered ineligible for further reminders only when
`reminder_count >= max_reminders` (a single environment variable, default 2) — there is
no stage ID written on the cart, no per-stage delay, and no per-stage message template.

**Verdict: Confirmed.** `app/services/shoppingcart.py:781–846` contains `send_cart_reminder`,
which has a hardcoded subject `"You left items in your cart"`, a hardcoded body string,
and unconditionally increments `reminder_count` without recording which stage the cart
is in. `scan_abandoned_carts` (lines 735–778) uses a single `cooldown` value derived
from `S.cart_abandonment_reminder_cooldown_hours` and a single `max_reminders` gate —
no per-stage delay or subject is read from any configuration source. The
`cart_reminder_config` DDB table mentioned in the fix recommendation does not exist in
`scripts/local-ddb-init.py` and `app/core/settings.py` has no
`cart_reminders_enabled` flag.

**Severity and area.** HIGH / E-Commerce & Cart (FIN-003). Without multi-stage
reminders, the platform sends at most two identical emails to every abandoner, which is
both less effective at recovering sales and potentially more annoying than a well-timed
three-stage sequence. The inability to configure per-stage delays or copy blocks the
marketing team from running targeted campaigns (e.g. "Stage 3 includes a 10% discount
code").

**Related tickets.** GAP-0190 (recovery links — closely coupled; both fix the same
`send_cart_reminder` function and should ship together). FIN-003 also has three other
lower-severity gaps (user opt-out, admin config UI, analytics) that can follow
independently.

## 2. Current-State Investigation (root cause)

### Background loop: `app/routers/shoppingcart.py:266–290`

```python
async def _cart_abandonment_loop() -> None:
    await asyncio.sleep(10)
    while True:
        if S.cart_abandonment_enabled:
            try:
                carts = scan_abandoned_carts(
                    threshold_hours=S.cart_abandonment_threshold_hours,
                )
                for cart in carts:
                    try:
                        send_cart_reminder(cart)    # ← single send, no stage
                    except Exception:
                        logger.warning("cart_reminder_failed", ...)
                try:
                    expire_abandoned_carts()
                except Exception:
                    logger.exception("Cart auto-expire failed")
            except Exception:
                logger.exception("Cart abandonment check failed")
        await asyncio.sleep(S.cart_abandonment_scan_interval_sec)
```

The loop calls `send_cart_reminder(cart)` for each cart that `scan_abandoned_carts`
returns. It has no knowledge of stage progression.

### `scan_abandoned_carts`: `app/services/shoppingcart.py:735–778`

```python
cooldown = S.cart_abandonment_reminder_cooldown_hours * 3600
max_reminders = S.cart_abandonment_max_reminders

for item in items:
    last_reminder = int(item.get("last_reminder_at", 0) or 0)
    count = int(item.get("reminder_count", 0) or 0)
    if count >= max_reminders:
        continue
    if last_reminder and (last_reminder + cooldown) > now:
        continue
    eligible.append(item)
```

The eligibility logic uses:
- `max_reminders` (env var, default `2`) — a single global cap with no per-stage
  meaning.
- `cooldown` (env var, default `48 h`) — a single global cooldown applied uniformly
  after every reminder, regardless of which reminder number was last sent.
- `reminder_count` stored on the cart — an integer that grows without recording which
  stage template was used.

There is no `current_stage` or `next_stage_at` field on the cart; the number of
reminders sent is not linked to a stage configuration.

### `send_cart_reminder`: `app/services/shoppingcart.py:781–846`


Subject, body, and update expression are all hardcoded. There is no parameter for stage

## 3. Impact / Exploit / Blast Radius

**Revenue loss.** Cart abandonment recovery is a direct revenue function. A
single identical reminder sent twice is significantly less effective than a
three-stage sequence with escalating urgency and a final-stage discount offer. Industry
benchmarks cite 5–15% recovery rate improvement for staged vs single-blast sequences.

**Marketing inflexibility.** The marketing team cannot A/B test reminder copy, adjust
stage timing, or run seasonal campaigns (e.g. "last chance" messages before a sale ends)
without a backend code deployment.

**User experience.** Sending two identical "You left items in your cart" emails looks
like a bug to the user, not a deliberate campaign, which damages brand trust.

**No security exploit.** The gap is a missing feature, not a security vulnerability.
The blast radius is limited to cart abandonment reminder quality and the platform's
ability to run configurable email campaigns.

---

## 4. Fix Design (code-level)

### Overview

Introduce a `cart_reminder_config` DynamoDB table that stores per-stage configuration
as individual items. Create `app/services/cart_reminders.py` with a
`process_abandoned_carts()` function that reads the stage list and advances each cart
through it. Refactor the background loop to call `process_abandoned_carts()` instead
of the bare `send_cart_reminder` loop.

### Step 1 — DynamoDB table: `scripts/local-ddb-init.py`

```python
TableDef(
    name=_resolve_table_name(S.cart_reminder_config_table_name, "cart_reminder_config"),
    partition_key="pk",
    sort_key="sk",
),
```

Row layout:
- `pk="CONFIG#GLOBAL"`, `sk="META"` — global flag (`enabled: bool`, `default_stages:
  list`).
- `pk="STAGE#{n}"`, `sk="META"` — per-stage config: `stage_number: int`,
  `delay_hours: int`, `subject: str`, `body_template: str`, `include_recovery_link:
  bool`, `include_promo_code: str | null`.
- `pk="OPTOUT#USER#{sub}"`, `sk="META"` — user opt-out (see FIN-003 gap #3).

### Step 2 — Settings: `app/core/settings.py`

```python
cart_reminders_enabled: bool = os.environ.get("CART_REMINDERS_ENABLED", "1") not in (
    "0", "false", "False")
cart_reminder_config_table_name: str = os.environ.get(
    "CART_REMINDER_CONFIG_TABLE", "cart_reminder_config")
```

The existing `cart_abandonment_enabled` flag continues to gate the background task
startup; `cart_reminders_enabled` gates the new multi-stage service (so the old path
can be preserved during the migration).

### Step 3 — `app/services/cart_reminders.py` (new file)

```python
"""
Multi-stage cart abandonment reminder service (FIN-003).

Reads stage configuration from the cart_reminder_config DDB table.
Advances each eligible cart through its reminder stages, using per-stage
delay_hours, subject, and body_template.
"""
from __future__ import annotations
import secrets
from typing import Any, Dict, List, Optional

from boto3.dynamodb.conditions import Key
from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts
from app.services.alerts import write_alert, send_alert_email
from app.services.profile import get_profile


def _get_stages() -> List[Dict[str, Any]]:
    """Load stage configs from DDB, sorted by stage_number ascending."""
    resp = T.cart_reminder_config.query(
        KeyConditionExpression=Key("pk").eq("STAGE#CONFIG") & Key("sk").begins_with("STAGE#")
    )
    stages = resp.get("Items", [])
    if not stages:
        # Fall back to built-in defaults if table is empty
        stages = _default_stages()
    return sorted(stages, key=lambda s: int(s.get("stage_number", 0)))


def _default_stages() -> List[Dict[str, Any]]:
    return [
        {
            "stage_number": 1,
            "delay_hours": 24,
            "subject": "You left items in your cart",
            "body_template": (
                "You have {items_count} item(s) waiting. "
                "Complete your purchase: {recovery_url}"
            ),
            "include_recovery_link": True,
        },
        {
            "stage_number": 2,
            "delay_hours": 72,
            "subject": "Still thinking it over?",
            "body_template": (
                "Your cart is waiting — don't miss out. "
                "{items_count} item(s) ready: {recovery_url}"
            ),
            "include_recovery_link": True,
        },
        {
            "stage_number": 3,
            "delay_hours": 168,
            "subject": "Last chance — your cart expires soon",
            "body_template": (
                "This is your final reminder. "
                "{items_count} item(s) in your cart: {recovery_url}"
            ),
            "include_recovery_link": True,
        },
    ]


def _is_opted_out(user_sub: str) -> bool:
    item = T.cart_reminder_config.get_item(
        Key={"pk": f"OPTOUT#USER#{user_sub}", "sk": "META"}
    ).get("Item")
    return bool(item and item.get("opted_out"))


def process_abandoned_carts(*, now: Optional[int] = None) -> Dict[str, int]:
    """Advance all eligible carts through their reminder stage pipeline.

    Returns counts: {scanned, reminded, skipped}.
    """
    if not S.cart_reminders_enabled:
        return {"scanned": 0, "reminded": 0, "skipped": 0}

    from app.services.shoppingcart import scan_abandoned_carts

    now = now or now_ts()
    stages = _get_stages()
    if not stages:
        return {"scanned": 0, "reminded": 0, "skipped": 0}

    max_stage = len(stages)
    # Use longest delay as the scan threshold
    max_delay = max(int(s.get("delay_hours", 24)) for s in stages)
    # Scan broadly: threshold = stage 1 delay
    min_delay = int(stages[0].get("delay_hours", 24))
    carts = scan_abandoned_carts(threshold_hours=min_delay, now=now)

    reminded = skipped = 0

    for cart in carts:
        current_stage_idx = int(cart.get("current_reminder_stage", 0))
        last_reminder_at = int(cart.get("last_reminder_at", 0) or 0)

        if current_stage_idx >= max_stage:
            skipped += 1
            continue

        stage = stages[current_stage_idx]
        stage_delay_sec = int(stage.get("delay_hours", 24)) * 3600
        abandoned_at = int(cart.get("abandoned_at", 0) or 0) or int(
            cart.get("last_activity_at", 0) or 0)

        # Stage 0: send after stage_delay from abandonment time
        # Subsequent stages: send after stage_delay from last_reminder_at
        reference_ts = abandoned_at if current_stage_idx == 0 else last_reminder_at
        if now < reference_ts + stage_delay_sec:
            skipped += 1
            continue

        user_sub = cart["PK"].replace("USER#", "")
        if _is_opted_out(user_sub):
            skipped += 1
            continue

        _send_stage_reminder(cart, stage, now=now)
        reminded += 1

    return {"scanned": len(carts), "reminded": reminded, "skipped": skipped}


def _send_stage_reminder(
    cart: Dict[str, Any], stage: Dict[str, Any], *, now: int
) -> None:
    """Send one stage reminder and advance the cart's stage counter."""
    from app.services.shoppingcart import _count_cart_items  # or inline

    user_sub = cart["PK"].replace("USER#", "")
    cart_id = cart.get("cart_id", "")
    stage_number = int(stage.get("stage_number", 1))

    # Count items (race-guard: skip empty carts)
    items_count = _count_cart_items(user_sub, cart_id)
    if items_count == 0:
        return

    # Generate recovery URL (see GAP-0190)
    from app.services.cart_reminders import generate_recovery_link
    recovery_url = generate_recovery_link(user_sub, cart_id)

    subject = stage.get("subject", "You left items in your cart")
    body_tpl = stage.get(
        "body_template",
        "You have {items_count} item(s) waiting: {recovery_url}",
    )
    body_text = body_tpl.format(items_count=items_count, recovery_url=recovery_url)

    write_alert(
        user_sub,
        event="cart.abandoned",
        outcome=f"reminder_stage_{stage_number}",
        title=subject,
        details={
            "cart_id": cart_id,
            "alert_type": "cart.abandoned",
            "link": f"/cart/recover?token={recovery_url.split('token=')[-1]}",
            "items_count": str(items_count),
            "stage": str(stage_number),
        },
    )

    profile = get_profile(user_sub) or {}
    email = profile.get("email") or profile.get("displayed_email")
    if email:
        send_alert_email([email], subject=subject, body_text=body_text)

    T.shopping_cart.update_item(
        Key={"PK": cart["PK"], "SK": cart["SK"]},
        UpdateExpression=(
            "SET last_reminder_at = :ts, "
            "current_reminder_stage = :stage, "
            "abandoned_at = if_not_exists(abandoned_at, :ts) "
            "ADD reminder_count :one"
        ),
        ExpressionAttributeValues={
            ":ts": now,
            ":stage": stage_number,  # advance to next stage index on next scan
            ":one": 1,
        },
    )
```

Note: `current_reminder_stage` is written as the stage number just sent. On the next
scan, `cart.get("current_reminder_stage", 0)` returns this value, and
`stages[current_stage_idx]` advances to the next stage dict.

### Step 4 — Refactor the background loop (`app/routers/shoppingcart.py`)

Replace the current inner loop in `_cart_abandonment_loop`:

```python
# Before:
carts = scan_abandoned_carts(...)
for cart in carts:
    send_cart_reminder(cart)

# After:
from app.services.cart_reminders import process_abandoned_carts
result = process_abandoned_carts()
logger.info("cart_abandonment_sweep", extra=result)
```

The old `send_cart_reminder` function in `shoppingcart.py` is retained as a fallback
(and used by the `/carts/sweep` admin endpoint until it is updated to also call
`process_abandoned_carts`).

### Dev/Prod parity (SECOPS-007)

The new `cart_reminder_config` table is provisioned by `scripts/local-ddb-init.py` for
local dev and by the Terraform/CDK IaC for production. `send_alert_email` and
`write_alert` are already environment-aware (dev mock vs SES in production). No new
dev-only code path is introduced; the fallback to `_default_stages()` when the table is
empty means the service works on a fresh local environment without seeding. The
`cart_reminders_enabled` flag (`CART_REMINDERS_ENABLED=1` by default) can be set to
`0` in `.env.local` to disable during development without affecting production.

### Backward compatibility

Existing carts in DynamoDB have no `current_reminder_stage` field; `cart.get
("current_reminder_stage", 0)` defaults to `0` (Stage 1), which is the correct
starting position. Carts that have already received reminders under the old system have
`reminder_count > 0`; the new service does not use `reminder_count` for stage gating
(it uses `current_reminder_stage`), so these carts will restart the stage sequence
from Stage 1 on the first run after deployment. To avoid double-reminding, a migration
option is to set `current_reminder_stage = reminder_count` for all existing carts with
`reminder_count > 0` in a one-off script at deployment time.

### Regression tests (pytest, fails-before / passes-after)

```python
def test_single_stage_sent_then_second_stage_after_delay(
    mock_cart_table, mock_email, mock_stages
):
    """
    mock_stages: [stage1 (delay=24h), stage2 (delay=72h), stage3 (delay=168h)]
    Cart abandoned at t=0. process_abandoned_carts called at t=25h: stage 1 sent.
    Called again at t=49h: nothing sent (stage 2 delay from last_reminder is 72h,
    only 24h has elapsed). Called at t=97h: stage 2 sent.
    """
    t0 = 1_700_000_000
    cart = make_cart(abandoned_at=t0, current_reminder_stage=0, reminder_count=0)

    # t=25h: stage 1 should fire
    result = process_abandoned_carts(now=t0 + 25 * 3600)
    assert result["reminded"] == 1
    assert mock_email.call_count == 1
    subject_1 = mock_email.call_args_list[0].kwargs["subject"]
    # Fails before: only one hardcoded subject; no stage progression
    assert subject_1 == "You left items in your cart"   # stage 1 subject

    # t=49h: stage 2 delay (72h from last reminder) not yet elapsed
    mock_email.reset_mock()
    result = process_abandoned_carts(now=t0 + 49 * 3600)
    assert result["reminded"] == 0    # cooldown not met

    # t=97h: 72h since stage 1 reminder → stage 2 should fire
    mock_email.reset_mock()
    result = process_abandoned_carts(now=t0 + 97 * 3600)
    assert result["reminded"] == 1
    subject_2 = mock_email.call_args_list[0].kwargs["subject"]
    # Fails before: function doesn't know about stages; sends same subject again
    assert subject_2 == "Still thinking it over?"    # stage 2 subject

def test_cart_at_max_stage_is_skipped(mock_cart_table, mock_stages):
    t0 = 1_700_000_000
    cart = make_cart(abandoned_at=t0, current_reminder_stage=3, reminder_count=3)
    result = process_abandoned_carts(now=t0 + 200 * 3600)
    assert result["reminded"] == 0
    assert result["skipped"] == 1
```

**Fails before:** `process_abandoned_carts` does not exist; the old `send_cart_reminder`
always sends the same hardcoded subject.

**Passes after:** the new service reads stage config, advances `current_reminder_stage`,
and sends the per-stage subject/body.

### Rollout and risks

- **Effort:** L. New service file, new DDB table, stage config seeding, loop refactor,
  migration script for existing carts.
- **Risk:** Medium. The `_default_stages()` fallback means the system degrades
  gracefully to single-stage behaviour if the DDB table is not seeded. The main risk
  is double-reminding existing carts without the migration script. Run the migration in
  a maintenance window before switching the loop to `process_abandoned_carts`.
- **Sequencing:** Ship GAP-0190 (recovery link generation) in the same PR — the new
  `generate_recovery_link` function is called from `_send_stage_reminder`.
- **Rollback:** Set `CART_REMINDERS_ENABLED=0`; the background loop returns to the old
  `send_cart_reminder` path. No DDB table data needs cleanup.
