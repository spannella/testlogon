# GAP-0269: Auto-upgrade triggers not wired — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: KYC-009. Owning area: KYC tier progression / registration.

## 1. Summary & Classification

**Bug**: `auto_evaluate_tier()` exists in `app/services/kyc_tiers.py` (line 217) and is
correctly implemented — it walks tiers from `current+1` to `KYC_TIER_MAX`, checks requirements,
and calls `upgrade_tier()` on the first eligible tier. However, it is **never called
automatically** from any of the three event-driven trigger points specified in KYC-009:

1. **Email verification completion** — `app/routers/register.py`, `register_confirm` (after
   `mark_user_verified`)
2. **Phone MFA setup** — `app/routers/mfa_devices.py` (after phone device confirmed)
3. **KYC case approval** — `app/services/kyc_cases.py`, `apply_admin_decision` (after
   decision written and case reaches `approved`)

The function is only reachable today via the explicit API endpoint
`POST /v1/kyc/tiers/me/evaluate`, which requires the user to manually request their own
re-evaluation.

**Claim accuracy**: **Confirmed correct.** All three trigger sites were inspected; none import
or call `auto_evaluate_tier`. The GAP-0269 source also cites `app/services/kyc_cases.py:534`
— the function there is `apply_admin_decision` starting at line 586 (line numbers shifted as
the file has grown); the core claim is correct regardless.

- **Severity**: HIGH
- **Source ticket**: KYC-009
- **Status**: Open
- **Owning area**: KYC tier progression / registration / MFA devices
- **One-line impact**: Users who satisfy Tier 1 or Tier 2 requirements are permanently stuck
  at Tier 0 unless they discover and manually call the evaluate endpoint; the progressive
  verification ladder is effectively broken.
- **Related tickets**: GAP-0268 (feature gating depends on correct tier), GAP-0267 (ByKycTier
  GSI), KYC-009

## 2. Current-State Investigation (root cause)

### Trigger 1 — Email verification (`register_confirm`)

`app/routers/register.py`, lines 187–238. After successful verification:

```python
mark_user_verified(username)                    # line 217 — sets verified=True in DDB
audit_event("register_confirm", ...)            # line 218
# <--- no auto_evaluate_tier call here
session = create_real_session(req, username, mfa_verified_at=now_ts())
```

`mark_user_verified` presumably sets `email_verified=True` on the user record. Tier 1
requires `{"email_verified", "phone_verified"}`. After email verification a user may already
satisfy the `email_verified` requirement but `auto_evaluate_tier` is never called to check
this and promote them.

### Trigger 2 — Phone MFA setup (`mfa_devices.py`)

`app/routers/mfa_devices.py` — a grep for `auto_evaluate_tier` or `phone_verified` returns
no results. The endpoint that marks a phone device as verified (completing the SMS MFA setup
flow) does not call `auto_evaluate_tier`. `check_tier_requirements` in
`app/services/kyc_tiers.py` (line 77–80) checks `profile.get("phone_verified")`, so the flag
must be set separately — but no call to `auto_evaluate_tier` follows it.

### Trigger 3 — KYC case approval (`apply_admin_decision`)

`app/services/kyc_cases.py`, `apply_admin_decision` (line 586–659). After the case is
written as `approved`:

```python
_emit_kyc_event_safe(
    event="kyc.case.approved",   # (emitted via kyc_webhooks, not shown here)
    ...
)
return self.get_case(case_id)
```

The router `_admin_decide_case` (in `kyc_cases.py`) calls `apply_admin_decision`, then
handles KYC-016 monitoring schedule creation (lines 1247–1259), then returns. No
`auto_evaluate_tier` call is present. Tier 2 requires `{"tier_1", "kyc_case_approved"}`. A
newly-approved case means the user is ready for Tier 2 — but will remain at Tier 1 until
manual re-evaluation.

### Why manual evaluation is insufficient

The only public trigger today is `POST /v1/kyc/tiers/me/evaluate`. Most users do not know
this endpoint exists, and the UI does not surface it automatically after each verification
step. User tier progression is blocked unless:
- Support manually overrides via `POST /v1/kyc/tiers/admin/{user_sub}/override`, or
- The user discovers and calls the evaluate endpoint.

## 3. Impact / Exploit / Blast Radius

**User experience**: Users who complete email + phone verification and a KYC case remain at
Tier 0 (or Tier 1) even though they are eligible for Tier 2. If GAP-0268's tier gating is
enabled, they will receive 403 errors on billing and subscription endpoints despite having
completed all required verification steps. This is a direct friction / conversion funnel issue.

**Compliance**: The KYC-009 intent is that tier upgrades happen automatically upon satisfying
requirements. Manual-only upgrades mean reviewer workload is required even for clear-cut cases,
violating the automated-triage intent of the tier system.

**No security exploit**: The missing triggers don't open a privilege escalation path. They
only prevent legitimate upgrades. The risk is operational / compliance, not adversarial.

**Blast radius**: Every user who has completed Tier 1 requirements but not explicitly called
`/me/evaluate`. In a production deployment, this is the entire user base post-launch.

## 4. Fix Design (code-level)

All three fixes follow the same pattern: a best-effort `try/except` call to
`auto_evaluate_tier(user_sub)` at the appropriate point, matching the established convention
for post-event hooks in this codebase.

### Fix 1 — Email verification trigger

In `app/routers/register.py`, `register_confirm` (line 217), immediately after
`mark_user_verified(username)`:

```python
mark_user_verified(username)
audit_event("register_confirm", username, req, outcome="success")

# KYC-009 / GAP-0269: auto-evaluate KYC tier after email verification.
try:
    from app.services.kyc_tiers import auto_evaluate_tier
    auto_evaluate_tier(username, request=req)
except Exception:
    logger.warning("kyc.tier.auto_evaluate_failed user_sub=%s", username, exc_info=True)
```

`mark_user_verified` sets `email_verified=True`; `auto_evaluate_tier` then checks whether
`email_verified + phone_verified` are both satisfied. If only email is done, it returns
`current_tier` unchanged (Tier 1 requires both). No upgrade fires prematurely.

### Fix 2 — Phone MFA setup trigger

In `app/routers/mfa_devices.py`, after the SMS device is confirmed and `phone_verified` is
set to `True` on the user record, add:

```python
# KYC-009 / GAP-0269: auto-evaluate KYC tier after phone verification.
try:
    from app.services.kyc_tiers import auto_evaluate_tier
    auto_evaluate_tier(user_sub, request=request)
except Exception:
    logger.warning("kyc.tier.auto_evaluate_failed user_sub=%s", user_sub, exc_info=True)
```

The exact insertion point depends on where `mfa_devices.py` writes `phone_verified=True`
(the confirm/verify endpoint). This must be called after the DDB write completes so
`check_tier_requirements` reads the updated state.

### Fix 3 — KYC case approval trigger

In `app/routers/kyc_cases.py`, `_admin_decide_case` (line 1247+), immediately after the
KYC-016 monitoring schedule block:

```python
# KYC-009 / GAP-0269: auto-evaluate KYC tier after case approval.
if decision == "approve" and str(updated.get("status") or "") == "approved":
    try:
        from app.services.kyc_tiers import auto_evaluate_tier
        auto_evaluate_tier(
            str(updated.get("user_sub") or ""),
            request=request,
        )
    except Exception:
        logger.warning(
            "kyc.tier.auto_evaluate_failed user_sub=%s case_id=%s",
            updated.get("user_sub"), case_id, exc_info=True,
        )
```

This fires only on `approve` decisions, not `reject`. The check `decision == "approve"`
is already present in the monitoring block above, so the pattern is consistent.

### Dev/Prod parity (SECOPS-007)

`auto_evaluate_tier` internally calls `get_user_kyc_tier`, which short-circuits to
`KYC_TIER_MAX` when `S.kyc_tier_gating_enabled=False` (line 31 in `kyc_tiers.py`):

```python
def get_user_kyc_tier(user_sub: str) -> int:
    if not S.kyc_tier_gating_enabled:
        return KYC_TIER_MAX  # When gating disabled, treat everyone as max tier
```

When the feature flag is off (dev default), `auto_evaluate_tier` reads `current = KYC_TIER_MAX`
and the loop `range(KYC_TIER_MAX + 1, KYC_TIER_MAX + 1)` is empty — the function returns
immediately without any DDB writes. The wiring is therefore safe to deploy in dev with the
flag disabled. This satisfies SECOPS-007: same code path, flag-selected behavior.

### Race condition note

The KYC-009 gaps document calls out a potential race: two concurrent `auto_evaluate_tier`
calls for the same user could both read `current_tier=0` and both call `upgrade_tier`. The
result is a duplicate history entry but the correct tier value (the second `update_item`
is idempotent for the tier itself). This is acceptable as a known, documented limitation
(see GAP-0269 race condition bullet). A conditional `ConditionExpression` on the
`upgrade_tier` UpdateItem can be added as a follow-up (Effort: S).

### Manual QA steps

1. Register a new account via `POST /ui/register/start` + `POST /ui/register/confirm`.
2. Immediately after confirm, call `GET /v1/kyc/tiers/me` (using the session from the
   confirm response). If the user had `phone_verified=True` pre-seeded, expect `current_tier: 1`.
   Otherwise expect `current_tier: 0` (email alone is insufficient for Tier 1).
3. Complete phone verification (add SMS MFA device). Immediately call `GET /v1/kyc/tiers/me`
   again — expect `current_tier: 1` (email + phone now both satisfied).
4. Create and submit a KYC case. Admin approves it via `POST /ui/kyc/admin/cases/{id}/approve`.
5. Call `GET /v1/kyc/tiers/me` once more — expect `current_tier: 2`.

### Checking tier history

After each trigger fires, the tier history can be verified:

```bash
# GET /v1/kyc/tiers/me returns history array
curl -s http://localhost:8000/v1/kyc/tiers/me \
  -H "Cookie: ui_session=...; ui_csrf=..." | python3 -m json.tool
# Expected: {"current_tier": 2, "history": [
#   {"from_tier": 0, "to_tier": 1, "reason": "auto_evaluation", ...},
#   {"from_tier": 1, "to_tier": 2, "reason": "auto_evaluation", ...}
# ]}
```

If `auto_evaluate_tier` fires but the user is not yet eligible, no history entry is written
(the function returns `get_tier_details` without calling `upgrade_tier`). This is correct
behaviour — a Tier 0 user who verifies only email has no history entry until phone is also
verified.

### Observability

The existing `kyc.tier.changed` log line (emitted in `upgrade_tier`) will appear in logs at
each trigger point. The `warning` log lines added in the `except` blocks
(`kyc.tier.auto_evaluate_failed`) provide an alert surface for cases where the hook fails
(e.g., DynamoDB temporarily unreachable). These log lines should be monitored: a high rate
of `auto_evaluate_failed` warnings indicates a systemic issue with the tier-evaluation
pipeline (e.g., table misconfiguration introduced by GAP-0267-class bugs).

An additional metric counter `kyc.tier.auto_upgraded` (incremented inside `upgrade_tier`
when `reason="auto_evaluation"`) would provide a dashboard signal for tier-upgrade velocity
per day. This helps detect if the triggers fired but conditions were never met (counter stays
zero while user base grows), suggesting an issue with `check_tier_requirements` logic.

### Integration with GAP-0268 (tier gating)

GAP-0269 is a hard dependency for GAP-0268 to be safe to enable in production. The failure
mode if gating is enabled without triggers wired: a user completes email verification, which
satisfies `email_verified` but the tier is never evaluated. The user's tier remains 0. They
attempt to send a message, receive a 403. They have no self-service path to fix this except
the undisclosed `POST /v1/kyc/tiers/me/evaluate` endpoint. Support ticket volume spikes.

With GAP-0269 fixes in place, the flow is: user completes email verification →
`register_confirm` fires `auto_evaluate_tier` → tier remains 0 (phone not yet verified) →
user adds phone → `mfa_devices` confirm fires `auto_evaluate_tier` → tier becomes 1 →
user can now send messages. The gating and auto-upgrade work together as intended.

### Alternatives considered

**Alternative A: Trigger via the `kyc.case.approved` webhook event** (using `kyc_webhooks`).
An async consumer could call `auto_evaluate_tier` in response to the event. This is cleaner
architecturally and decouples the tier evaluation from the synchronous request path. The
downside is that `kyc_webhooks` is not running as a reliable separate consumer in dev, and
async delivery adds latency / failure modes (webhook delivery is best-effort). The
synchronous in-process hook is safer and simpler for the current architecture.

**Alternative B: Periodic batch evaluation** (a cron job that evaluates all users nightly).
This works but means tier upgrades are delayed up to 24 hours after verification. For a user
who just completed their documents and expects immediate access, this creates a confusing
experience. Event-driven triggers are the correct approach.

**Alternative C: Client-initiated only** (the user clicks "Check my tier" in the UI). This
is the current state. It is insufficient: most users are not aware of the tier system and
will not know to click a re-evaluation button.

### Dependency sequencing

GAP-0269 (auto-upgrade triggers) should be deployed **before** GAP-0268 (feature gating).
If gating is enabled before the triggers are wired, users who complete Tier 1 requirements
are blocked by the gate but receive no automatic promotion. They must call the explicit
evaluate endpoint, which is not surfaced in the UI. Deploying in the wrong order creates
a support burden. Recommended deploy order: GAP-0269 → verify tier history in staging →
GAP-0268 with flag enabled.

### Rollout

All three fixes are additive `try/except` calls. They can be deployed together or
independently. With `KYC_TIER_GATING_ENABLED=false`, the calls are harmless no-ops. Enable
the flag in staging after deployment, run the E2E suite with tier-seeded sessions (see
GAP-0268 guidance), then enable in production. Effort: **S** (< half-day for all three
trigger points including tests). The race-condition hardening (conditional UpdateItem) is
a follow-up with Effort: S.
