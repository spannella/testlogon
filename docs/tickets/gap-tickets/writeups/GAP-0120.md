# GAP-0120: `concatenate_segments` Production Path Is a Stub — Remediation Write-up

> ~5 pages. Fix-oriented. Real code verified against the codebase; cite `file:line`.

## 1. Summary & Classification

**Gap**: `concatenate_segments` in `app/services/broadcast_recording_worker.py` logs the segment count and then always returns `None`, even when a real segment list is provided and FFmpeg is available. The production comment says "FFmpeg concat demuxer" but no subprocess is launched and no output file is produced.

**Severity**: HIGH
**Source ticket**: BCAST-006
**Status**: Open
**Owning area**: `app/services/broadcast_recording_worker.py` → `concatenate_segments`
**Related tickets**: GAP-0119 (`inventory_segments` also a stub — must be fixed together), BCAST-006 (Recording pipeline), BCAST-008 (MP4 download depends on concat output)

**Verdict**: Claim confirmed. `app/services/broadcast_recording_worker.py:61–72` — the production branch (lines 69–72) ends with `return None` after a single `logger.info` call. No FFmpeg subprocess is spawned, no temporary file is written, and nothing is uploaded to S3.

**One-line impact**: Even when `inventory_segments` returns a non-empty list (after GAP-0119 is fixed), all recordings remain zero-duration because `concatenate_segments` never produces a real merged file.


## 2. Current-State Investigation (root cause)

### Current implementation

`app/services/broadcast_recording_worker.py:61–72`:

```python
def concatenate_segments(recording: RecordingRecord, segments: List[str]) -> Optional[str]:
    """Concatenate .ts segments into a single transport stream.

    Returns the path to the concatenated file, or None in mock mode.
    """
    if _should_mock() or not segments:
        logger.info("Recording %s: mock concatenation (skip)", recording.recording_id)
        return None

    # Production: FFmpeg concat demuxer
    logger.info("Recording %s: concatenating %d segments", recording.recording_id, len(segments))
    return None    # <-- stub: never produces output
```

The structure is clear: mock/empty guard fires `return None`; the production block logs and also `return None`.

### Cascade from GAP-0119

With GAP-0119 fixed, `inventory_segments` returns a real `List[str]` of S3 keys. Those keys are passed to `concatenate_segments`. The `not segments` guard will no longer fire — but the production stub `return None` still fires. The downstream `transcode_recording` and `generate_mp4` calls receive `concat_path=None` and fall into their mock branches:

```python
# transcode_recording (line 81):
if _should_mock() or concat_path is None:   # concat_path is None → True
    return {"renditions": [...], "duration_seconds": 0, "total_bytes": 0}

# generate_mp4 (line 102):
if _should_mock() or concat_path is None:   # same
    return {"mp4_s3_key": ..., "mp4_size_bytes": 0, ...}
```

So without fixing `concatenate_segments`, fixing GAP-0119 alone has no effect on output quality.

### Existing FFmpeg infrastructure

`generate_mp4` (lines 96–135) already contains a working FFmpeg subprocess invocation:

```python
args = [
    S.ffmpeg_binary_path, "-hide_banner", "-loglevel", "warning", "-y",
    "-i", concat_path,
    "-c", "copy",
    "-movflags", "+faststart",
    mp4_path,
]
result = subprocess.run(args, capture_output=True, text=True, timeout=600)
if result.returncode != 0:
    raise RuntimeError(f"FFmpeg MP4 remux failed: {result.stderr[:500]}")
```

This demonstrates that the subprocess invocation pattern is established. `concatenate_segments` needs to follow the same pattern using the FFmpeg concat demuxer.

### S3 download / upload requirement

The `.ts` segments live in S3 (or moto in dev). FFmpeg cannot read directly from S3 keys without a pre-signed URL or local copy. The implementation must:

1. Download each segment from S3 to a local temp directory.
2. Write an FFmpeg `concat` demuxer input file listing the local segment paths.
3. Run FFmpeg to concatenate the segments into a single `.ts` file.
4. Upload the concatenated `.ts` to S3.
5. Clean up the temp directory.
6. Return the local path of the concatenated file (for the subsequent `transcode_recording` and `generate_mp4` calls that expect a local path).

`generate_mp4` already leaves the local MP4 in place without uploading it (comment at line 131: "Upload to S3 would happen here in production"). The same deferred-upload pattern should be adopted initially: upload after transcode to avoid re-downloading.


## 3. Impact / Exploit / Blast Radius

### Functional impact

The impact compounds GAP-0119:

- Even after GAP-0119 is fixed, the pipeline stalls at step 2. `concat_path=None` cascades through transcode and MP4 generation, producing zero-byte outputs.
- `finalize_recording` marks the recording `ready` with `duration_seconds=0`, `total_bytes=0`, `segment_count=0`.
- The presigned playback URL returned by `mint_recording_playback_url` points to `{session_id}/recording/master.m3u8` — a key that does not exist in S3 (never written). Any player that follows the URL will receive a 403 or 404.

### Financial and legal impact

- Broadcasters who rely on recordings for on-demand revenue or archive compliance receive empty files.
- If a GDPR data-export request includes broadcast recordings, the exported file will be empty (zero-byte MP4). This may create regulatory exposure if recordings are expected to be preserved.
- BCAST-008 (viewer download) exposes `allow_viewer_download=true` by default. Viewers who pay for a download receive a zero-byte file.

### Blast radius

All sessions where `S.broadcast_recording_enabled=True` (the default). The mock path fires in dev (FFmpeg absent), so the bug is invisible locally. The production stub fires when FFmpeg is installed. Both paths return `None`; the practical blast radius is every production recording since BCAST-006 shipped.


## 4. Fix Design (code-level)

### Implementation of `concatenate_segments`

**File**: `app/services/broadcast_recording_worker.py`, function `concatenate_segments` (line 61).

The fix requires three helpers:

1. `_download_segments(s3, bucket, keys, tmp_dir)` — downloads each key to `tmp_dir`.
2. `_write_concat_file(segment_paths, concat_file_path)` — writes FFmpeg concat demuxer input.
3. `_upload_to_s3(s3, bucket, local_path, s3_key)` — uploads the concatenated file.

Complete replacement for `concatenate_segments`:

```python
def concatenate_segments(recording: RecordingRecord, segments: List[str]) -> Optional[str]:
    """Concatenate .ts segments via FFmpeg concat demuxer.

    Downloads segments from S3, writes a concat list, runs FFmpeg, uploads result.
    Returns the local path of the concatenated .ts file, or None in mock/empty mode.
    """
    if _should_mock() or not segments:
        logger.info("Recording %s: mock concatenation (skip)", recording.recording_id)
        return None

    import os
    import subprocess
    import tempfile

    from app.core.aws_clients import s3_client
    from app.core.settings import S as _S

    s3 = s3_client()
    bucket = _S.broadcast_recording_vod_bucket

    tmp_dir = tempfile.mkdtemp(prefix=f"bcast_concat_{recording.recording_id}_")
    try:
        logger.info("Recording %s: downloading %d segments to %s",
                    recording.recording_id, len(segments), tmp_dir)

        # Step 1: Download all segments
        local_paths: List[str] = []
        for i, key in enumerate(segments):
            local_name = os.path.join(tmp_dir, f"seg{i:06d}.ts")
            s3.download_file(bucket, key, local_name)
            local_paths.append(local_name)

        # Step 2: Write FFmpeg concat demuxer input file
        concat_list_path = os.path.join(tmp_dir, "concat.txt")
        with open(concat_list_path, "w") as fh:
            for lp in local_paths:
                # FFmpeg requires forward slashes and single-quotes for safety
                safe = lp.replace("'", r"'\''")
                fh.write(f"file '{safe}'\n")

        # Step 3: Run FFmpeg concat demuxer
        output_path = os.path.join(tmp_dir, "concatenated.ts")
        args = [
            _S.ffmpeg_binary_path,
            "-hide_banner", "-loglevel", "warning", "-y",
            "-f", "concat", "-safe", "0",
            "-i", concat_list_path,
            "-c", "copy",
            output_path,
        ]
        logger.info("Recording %s: running FFmpeg concat: %s",
                    recording.recording_id, " ".join(args))
        result = subprocess.run(args, capture_output=True, text=True, timeout=3600)
        if result.returncode != 0:
            raise RuntimeError(
                f"FFmpeg concat failed (rc={result.returncode}): {result.stderr[:500]}"
            )

        concat_size = os.path.getsize(output_path)
        logger.info("Recording %s: concatenation complete, size=%d bytes", recording.recording_id, concat_size)

        # Step 4: Upload concatenated .ts to S3 for downstream use
        s3_concat_key = f"{recording.session_id}/recording/concatenated.ts"
        s3.upload_file(output_path, bucket, s3_concat_key)

        # Persist the S3 key so subsequent pipeline restarts can skip re-concat
        from app.services.broadcast_recording import update_recording_status
        update_recording_status(
            recording.recording_id,
            recording.status,   # keep current status (processing)
            s3_concatenated_key=s3_concat_key,
        )

        return output_path

    except Exception:
        import shutil
        shutil.rmtree(tmp_dir, ignore_errors=True)
        raise
    # Note: tmp_dir is NOT cleaned up on success — downstream steps (transcode, MP4)
    # read output_path. Cleanup is delegated to process_recording's finally block.
```

### `_upload_to_s3` helper

For re-use by `generate_mp4` (which currently has a "Upload to S3 would happen here" comment):

```python
def _upload_to_s3(s3_client_obj, bucket: str, local_path: str, s3_key: str) -> None:
    """Upload a local file to S3."""
    import os
    file_size = os.path.getsize(local_path)
    logger.info("Uploading %s → s3://%s/%s (%d bytes)", local_path, bucket, s3_key, file_size)
    s3_client_obj.upload_file(local_path, bucket, s3_key)
```

This same helper can replace the "Upload to S3 would happen here" comment in `generate_mp4`, closing both stubs.

### Dev/Prod parity (SECOPS-007)

The S3 client is obtained from `app/core/aws_clients.s3_client()`. In dev mode, moto's `mock_aws()` patches botocore, so `s3.download_file()` and `s3.upload_file()` are served from moto's in-memory store. The `_should_mock()` guard continues to gate mock behaviour: when FFmpeg is absent, the function returns `None` and no S3 calls are made. When FFmpeg is present (even in a dev environment with `BROADCAST_RECORDING_MOCK_ON_NO_FFMPEG=0`), the real S3 (or moto) calls are made. The same code path runs in both environments.

### Disk safety

`S.ffmpeg_min_free_disk_gb` (default 5 GB, line 1429 of settings) should be checked before downloading segments. Add a preflight guard:

```python
import shutil as _shutil
free_gb = _shutil.disk_usage(tempfile.gettempdir()).free / (1024**3)
if free_gb < _S.ffmpeg_min_free_disk_gb:
    raise RuntimeError(
        f"Insufficient disk space for recording: {free_gb:.1f} GB free, "
        f"{_S.ffmpeg_min_free_disk_gb} GB required"
    )
```

### Backward compatibility

- No DynamoDB schema changes. `s3_concatenated_key` is already a field on `RecordingRecord` (line 49 of `broadcast_recording.py`) and in `_record_to_item`/`_record_from_item`.
- The `update_recording_status` call using `s3_concatenated_key` is a new kwarg path. Verify `update_recording_status` passes through extra kwargs to DynamoDB `UpdateExpression` — confirm at `app/services/broadcast_recording.py`.
- `process_recording` passes `recording` (not a fresh fetch) to `concatenate_segments`; the local `recording` variable is not mutated by the DDB write inside `concatenate_segments`, which is correct.

### Rollout

- **Effort**: M (implementation + S3 download/upload logic + comprehensive tests + disk safety check).
- **Risk**: Medium. First production execution will trigger real FFmpeg processes and S3 I/O that have never run before. Recommend a canary deployment to a small subset of production sessions before full rollout.
- **Sequence**: Must ship with GAP-0119. Deploying GAP-0119 alone (non-empty segment list) without this fix changes nothing visible, because `concatenate_segments` will still return `None`. Deploying both together activates the full pipeline for the first time.
- **Pre-deployment checklist**:
  - Confirm `FFMPEG_BINARY_PATH` resolves to a working `ffmpeg` binary in the production AMI/container image.
  - Confirm `BROADCAST_RECORDING_VOD_BUCKET` matches the actual S3 bucket name and the recording worker IAM role has `s3:GetObject`, `s3:PutObject`, and `s3:ListBucket` permissions on that bucket.
  - Confirm `FFMPEG_MIN_FREE_DISK_GB` is set to at least 2× the expected maximum session recording size (e.g., a 3-hour stream at 4 Mbps produces ~5.4 GB of `.ts` data; with temp copies the required disk headroom is ~11 GB).
  - Run `just test` with `BROADCAST_RECORDING_MOCK_ON_NO_FFMPEG=0` in a CI environment that has FFmpeg installed.
- **Rollback**: Set `BROADCAST_RECORDING_MOCK_ON_NO_FFMPEG=1` (env var, no deploy needed) to revert to mock behaviour instantly. Code rollback removes the production path; recordings return to placeholder state.

### Long-term: async worker architecture

The current `process_recording` function is invoked synchronously (inline) when `broadcast_recording_worker_inline=True` (the default in dev, controlled by line 1453 of `settings.py`). In production the recording worker should run asynchronously (SQS-triggered Lambda or a dedicated ECS task) to avoid blocking the FastAPI event loop. The fix designed above is compatible with both inline and async invocation patterns since it is a pure Python function with no async/await dependency. The worker architecture change is out of scope for this gap but should be tracked as a follow-on scalability ticket.
