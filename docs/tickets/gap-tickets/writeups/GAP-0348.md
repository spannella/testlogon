# GAP-0348: `adjust_stock` Uses a Full-Table Scan to Find Item by `item_id` — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. No investigation doc exists.

## 1. Summary & Classification

**Bug statement.** The `adjust_stock` endpoint (`PATCH /ui/catalog/items/{item_id}/stock`, `app/routers/catalog.py:656`) calls `_find_item_by_id` (line 662), which performs a full paginated scan of the entire `shopping_catalog` DynamoDB table filtered to `item_id = :iid`. Because DynamoDB `FilterExpression` is applied after data is read (up to 1 MB per page), this scan reads every item in the catalog before returning one result. At scale (thousands of catalog items), this is catastrophically inefficient and cost-prohibitive.

- **Severity**: HIGH — O(n) scan where n is the total catalog size; each call can exhaust DynamoDB read capacity, cause latency spikes, and incur unbounded cost.
- **Source ticket**: SHOP-001 (inventory management); cross-ref SEC-024 (e-commerce abuse)
- **Status**: Open
- **Owning area**: Shop / Catalog / `app/routers/catalog.py`, `scripts/local-ddb-init.py`
- **Claim verdict**: CONFIRMED. `_find_item_by_id` at lines 639–653 explicitly uses `T.catalog.scan()` with a `FilterExpression`. The `shopping_catalog` table definition in `scripts/local-ddb-init.py` (lines 96–100) has only one GSI (`GSI1` with `GSI1PK`/`GSI1SK`), which is not indexed on `item_id`. The ticket's suggested fix is correct.
- **Related tickets**: SHOP-001, SEC-024, SECOPS-007

## 2. Current-State Investigation (root cause)

### Table schema

The `shopping_catalog` table (local-ddb-init.py:96–100) uses a composite key:

- **PK**: `PK` (category-scoped, e.g., `CAT#{category_id}`)
- **SK**: `SK` (item-scoped, e.g., `ITEM#{item_id}`)
- **GSI1**: `GSI1PK` / `GSI1SK` (purpose unknown from schema alone; not indexed on bare `item_id`)

The `item_id` field lives inside the item as a regular attribute, not as a key or GSI partition key. To look up an item by `item_id` alone (without knowing `category_id`), DynamoDB must read every item in the table.

### The scan function

`_find_item_by_id` (lines 639–653):

```python
def _find_item_by_id(item_id: str) -> Optional[Dict[str, Any]]:
    """Scan catalog table for an item by item_id (paginated scan)."""
    kwargs: Dict[str, Any] = {
        "FilterExpression": "item_id = :iid AND entity = :ent",
        "ExpressionAttributeValues": {":iid": item_id, ":ent": "item"},
    }
    while True:
        resp = T.catalog.scan(**kwargs)
        items = resp.get("Items", [])
        if items:
            return items[0]
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            return None
        kwargs["ExclusiveStartKey"] = lek
```

There is no `Limit` parameter — it scans the entire table in 1 MB chunks until the item is found or the table is exhausted. For a table with 100,000 items where the target item is near the end, this could require 100+ round-trips, each consuming the full 1 MB read allocation.

### The `adjust_stock` route

```python
@router.patch("/items/{item_id}/stock", response_model=CatalogStockOut)
async def adjust_stock(
    item_id: str,
    body: CatalogStockAdjustIn,
    ctx=Depends(require_ui_session),
):
    item = _find_item_by_id(item_id)     # <-- full table scan here
    if not item:
        raise HTTPException(status_code=404, detail="Item not found.")
    category_id = item["category_id"]
    _require_category_owner(category_id, ctx["user_sub"])
    ...
```

Once `category_id` is retrieved from the scanned item (line 665), it is immediately used to build the DynamoDB key for the subsequent `update_item` call (line 669): `key = {"PK": item["PK"], "SK": item["SK"]}`. This means the `category_id` was always available to the caller — it simply is not exposed in the route URL.

### Why this matters in production

DynamoDB scales linearly with consumed capacity units, not item count. A full table scan of a 100,000-item catalog at DynamoDB's default 4 KB read granularity consumes approximately 25,000 RCUs per scan pass (100,000 × 4 KB / 4 KB per eventually-consistent RCU / 4 = 25,000). At production pricing, a single `adjust_stock` call on a large catalog costs ~$0.025 per call — compared to a point query at $0.00000025. A flash sale with 10,000 concurrent stock decrements would cost roughly $250 in RCUs from scans alone versus $0.0025 from point queries.

## 3. Impact / Exploit / Blast Radius

### Performance degradation

Every stock adjustment for any item triggers a full table scan. On a catalog with many creators and items, this scan competes with catalog listing queries (which use GSI1), degrading all catalog reads globally, not just stock adjustments.

### Cost amplification (economic abuse, cross-ref SEC-024)

An adversary who can trigger stock adjustments (e.g., by purchasing and immediately returning items, or by exploiting the `/adjust_stock` endpoint with a valid session) can cause unbounded DynamoDB read cost proportional to table size. With a 1,000,000-item catalog, a single call can consume 250,000 RCUs.

### Latency

For large catalogs, each `adjust_stock` call waits for the scan to complete before returning. At 1 MB per scan page and DynamoDB's 1–3 ms per page, a 50 MB catalog scan takes 50–150 ms minimum just for the lookup — before the actual `update_item` write occurs.

### Inventory race condition

Because the scan is non-atomic with the update, two concurrent `adjust_stock` calls for the same item could both scan, both get a stale view of the item key, and then both execute `update_item` with no ordering guarantee. The `update_item` itself uses `ConditionExpression="attribute_exists(PK)"` (line 676), which prevents writing to a non-existent item but does not prevent concurrent updates.

## 4. Fix Design (code-level)

There are two viable fixes. The ticket recommends both but they are independent. Either alone solves the scan problem.

### Option A (Preferred): Change route to accept `category_id` in path

**Change the route** from `PATCH /ui/catalog/items/{item_id}/stock` to `PATCH /ui/catalog/categories/{category_id}/items/{item_id}/stock`.

With `category_id` in the URL, the lookup becomes a single DynamoDB `get_item` using the exact composite key:

```python
@router.patch(
    "/categories/{category_id}/items/{item_id}/stock",
    response_model=CatalogStockOut,
)
async def adjust_stock(
    category_id: str,
    item_id: str,
    body: CatalogStockAdjustIn,
    ctx=Depends(require_ui_session),
):
    resp = T.catalog.get_item(Key=_catalog_item_key(category_id, item_id))
    item = resp.get("Item")
    if not item or item.get("entity") != "item":
        raise HTTPException(status_code=404, detail="Item not found.")
    _require_category_owner(category_id, ctx["user_sub"])
    ...
```

`_catalog_item_key` already exists in the module (used by `add_catalog_item` in `shoppingcart.py:377`). It constructs `{"PK": f"CAT#{category_id}", "SK": f"ITEM#{item_id}"}`. The `get_item` call is O(1) regardless of catalog size.

**Frontend impact**: Any client calling `PATCH /ui/catalog/items/{item_id}/stock` must be updated to include `category_id` in the path. The `CatalogStockAdjustIn` model may need to carry `category_id` if clients do not have it in context, but since this endpoint is creator-facing (requires `_require_category_owner`), the creator already knows their `category_id`.

**Backward compatibility**: Add a deprecated alias route that extracts `category_id` via the old scan for a transition period:

```python
@router.patch("/items/{item_id}/stock", deprecated=True, response_model=CatalogStockOut)
async def adjust_stock_legacy(...):
    # delegates to the new handler after scanning for category_id
    # logs a deprecation warning
    ...
```

### Option B: Add a `ByItemId` GSI on the catalog table

Add a GSI with `item_id` as the partition key to `shopping_catalog`:

In `scripts/local-ddb-init.py`, update the `TableDef` for `shopping_catalog` (line 96):

```python
TableDef(
    _resolve_table_name(S.catalog_table_name, "shopping_catalog"),
    "PK",
    "SK",
    gsi=[
        {"index_name": "GSI1", "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "ByItemId", "partition_key": "item_id"},
    ],
),
```

Then replace `_find_item_by_id` with a GSI query:

```python
def _find_item_by_id(item_id: str) -> Optional[Dict[str, Any]]:
    """Query the ByItemId GSI to find an item by its item_id (O(1))."""
    from boto3.dynamodb.conditions import Key as DKey, Attr
    resp = T.catalog.query(
        IndexName="ByItemId",
        KeyConditionExpression=DKey("item_id").eq(item_id),
        FilterExpression=Attr("entity").eq("item"),
        Limit=1,
    )
    items = resp.get("Items", [])
    return items[0] if items else None
```

**Trade-off**: GSI writes increase storage cost and write cost marginally (every catalog item write now populates an additional GSI key). However, the query cost savings on `adjust_stock` far outweigh this.

**Recommended approach**: Option A is preferred because it eliminates the scan entirely without adding infrastructure, and makes the API contract more explicit (callers must supply `category_id`, which they already have). Option B is a fallback for cases where the route signature cannot be changed without a larger API versioning effort.

### Dev/prod parity (SECOPS-007)

Both fixes use `T.catalog`, which is DynamoDB Local in dev and AWS DynamoDB in production. No mock divergence is needed. For Option B, the GSI must be added to the real table in production via IaC (Terraform/CDK `GlobalSecondaryIndex` on `shopping_catalog`). For Option A, the route change is code-only.

## 5. Testing, Verification & Rollout

### Regression test (fails before / passes after fix)

Add to `tests/test_catalog.py` (offline, moto-backed):

```python
def test_adjust_stock_does_not_scan_table(mock_catalog_with_items, monkeypatch):
    """adjust_stock must not call T.catalog.scan()."""
    scan_calls = []
    original_scan = T.catalog.scan

    def spy_scan(*args, **kwargs):
        scan_calls.append((args, kwargs))
        return original_scan(*args, **kwargs)

    monkeypatch.setattr(T.catalog, "scan", spy_scan)

    # Option A: test new route with category_id in path
    response = client.patch(
        f"/ui/catalog/categories/{CATEGORY_ID}/items/{ITEM_ID}/stock",
        json={"delta": -1},
        headers=auth_headers("creator"),
    )
    assert response.status_code == 200
    assert len(scan_calls) == 0  # fails before fix (scan called), passes after


def test_adjust_stock_uses_get_item_for_lookup(mock_catalog_with_items, monkeypatch):
    """After fix, lookup must use get_item (O(1)) not scan."""
    get_calls = []
    original_get = T.catalog.get_item

    def spy_get(Key, **kwargs):
        get_calls.append(Key)
        return original_get(Key=Key, **kwargs)

    monkeypatch.setattr(T.catalog, "get_item", spy_get)

    client.patch(
        f"/ui/catalog/categories/{CATEGORY_ID}/items/{ITEM_ID}/stock",
        json={"absolute": 10},
        headers=auth_headers("creator"),
    )
    assert any(ITEM_ID in str(k) for k in get_calls)
```

### Rollout and risks

- **Effort**: S (small for Option A — route rename + `get_item` substitution, ~20 lines changed; M for Option B if GSI provisioning requires IaC coordination).
- **Option A risks**: Frontend and any third-party API clients calling the old path will receive 404 until updated. The deprecated alias route mitigates this.
- **Option B risks**: Adding a GSI to an existing production DynamoDB table is an online operation (no downtime) but takes minutes to hours to backfill. During backfill, new writes populate the GSI immediately; reads may miss recently written items until backfill completes.
- **Sequencing (Option A)**: Deploy backend with both new route and deprecated legacy alias → update frontend → monitor legacy alias traffic drops to zero → remove alias in a follow-up.
- **Sequencing (Option B)**: Add GSI in IaC (DDB online update) → deploy backend with GSI query → remove old scan function.
