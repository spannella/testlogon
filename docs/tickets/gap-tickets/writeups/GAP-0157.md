# GAP-0157: Banned viewer can still send chat messages — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement.** When a platform administrator bans a user account (writing
a `BAN_STATUS` record to `T.account_state` via `is_user_currently_banned` in
`app/services/moderation_policy_engine.py`), that user is correctly blocked
from creating new sessions and from calling most UI endpoints. However, they
can still post messages to live broadcast chat sessions. The `send_chat_message`
function in `app/services/broadcast_chat_store.py` calls `_enforce_chat_mute`
(which checks the per-session mute state stored in `T.broadcast_chat_mutes`)
but never calls the global account ban check provided by
`is_viewer_banned` in `app/services/delegate_broadcast.py` or
`is_user_currently_banned` in `app/services/moderation_policy_engine.py`.

**Note on the ticket's table name:** The ticket (GAP-0157) refers to the fix
calling `T.broadcast_moderation BAN# item`. Investigation shows that the
`is_viewer_banned` function lives in `app/services/delegate_broadcast.py:557`
and it does query `T.broadcast_moderation` keyed by `SESSION#{session_id}` /
`BAN#{user_id}`. This is a *per-session* broadcast ban, separate from the
platform-wide account ban tracked in `T.account_state`. Both gaps exist and
are described below; the ticket description is accurate in naming the
`BAN#` item path.

**Severity:** HIGH — moderation enforcement bypass. A banned user can evade
the intended consequence of their ban in a live broadcast context.  
**Source ticket:** DELEGATE-004  
**Status:** Open  
**Owning area:** Broadcast chat moderation, `app/services/broadcast_chat_store.py`  
**Effort:** S

**Verdict from code investigation:** Claim confirmed with an important
clarification. There are two distinct ban mechanisms:

1. **Platform-wide account ban** (`T.account_state`, `is_user_currently_banned`
   in `moderation_policy_engine.py`) — checked at session creation and in
   `require_ui_session` (`app/auth/deps.py:135`), but **not** inside
   `send_chat_message`.
2. **Per-session broadcast ban** (`T.broadcast_moderation`, `BAN#` key,
   `is_viewer_banned` in `delegate_broadcast.py:557`) — written by `ban_viewer`
   in the same file, but **never consulted** by `send_chat_message` in
   `broadcast_chat_store.py`.

The fix must close both gaps. The ticket specifically names the per-session
`BAN#` path; the platform-wide ban is an additional (and more severe) gap.

**Related tickets:** GAP-0156 (missing delegates route), GAP-0158 (API key
ban bypass), DELEGATE-004.

`_store_send_chat` resolves to `send_chat_message` in

There is no call to `is_viewer_banned` (per-session ban, `T.broadcast_moderation`)
and no call to `is_user_currently_banned` (platform-wide ban, `T.account_state`).

### Where the per-session ban is written

`app/services/delegate_broadcast.py:209` — `ban_viewer`:

```python
def ban_viewer(session_id: str, user_id: str, reason: str = "") -> dict:
    item = {
        "pk": f"SESSION#{session_id}",
        "sk": f"BAN#{user_id}",
        ...
    }
    T.broadcast_moderation.put_item(Item=item)
```

`app/services/delegate_broadcast.py:557` — `is_viewer_banned`:

```python
def is_viewer_banned(session_id: str, user_id: str) -> bool:
    resp = T.broadcast_moderation.get_item(
        Key={"pk": f"SESSION#{session_id}", "sk": f"BAN#{user_id}"}
    )
    return resp.get("Item") is not None
```

`is_viewer_banned` is never imported into `broadcast_chat_store.py` and is
never called from the send path.

### Where the platform-wide ban is checked

`app/auth/deps.py:135`:

```python
if is_user_currently_banned(user_sub):
    raise HTTPException(status_code=403, detail="Account is suspended")
```

This guard runs on every request that uses `require_ui_session`. A banned
user's **existing session cookie** remains valid for its TTL; if the user has
an active browser session at the moment of the ban, they can continue to send
chat messages until the session expires (or until they navigate to a page that
triggers a full re-auth). The `send_chat_message_route` uses `_ctx` which
calls `require_ui_session`, so the session-level check does run — but that
only helps if the ban takes effect before the current session's JWT expires.
For an in-progress broadcast the TTL window can be substantial.

### `send_product_link_message` has the same gap

`app/services/broadcast_chat_store.py:219` — `send_product_link_message`
also calls only `_enforce_chat_mute`, not the ban check.

## 3. Impact / Exploit / Blast Radius

**Scenario A — Per-session broadcast ban bypass:**

1. Creator bans viewer Bob from their broadcast via
   `POST /sessions/{sid}/ban-viewer`.
2. Bob's `BAN#` item is written to `T.broadcast_moderation`.
3. Bob continues to send messages via `POST /sessions/{sid}/chat`.
4. `send_chat_message` checks mute (clean) and rate limit (clean) — no
   per-session ban check — message is accepted and broadcast to all viewers.

This completely nullifies the broadcast moderation tool that creators use to
manage abusive viewers during live events.

**Scenario B — Platform-wide ban + live session:**

1. Admin bans Alice's account via the moderation policy engine.
2. Alice is mid-session watching a live broadcast with an unexpired
   `ui_access_token` cookie (JWT TTL can be up to the session expiry, which
   may be hours).
3. `require_ui_session` will raise 403 for most endpoints, but if the token is
   still valid the broadcast chat POST succeeds because the JWT check passes.
4. Alice can post chat messages for the remaining lifetime of her session token.

**Blast radius:** Every live broadcast session on the platform. In a high-
traffic scenario with many concurrent broadcasts, a suspended/banned account
could spam many sessions simultaneously before the session cookie expires.

**Financial / compliance impact:** Chat messages from banned users may contain
illegal or CSAM-adjacent content. Platforms that host live broadcasts have
regulatory obligations (e.g., DSA, OFCOM) to enforce moderation decisions
promptly. A delay of even 30 minutes between a ban decision and enforcement
in chat represents a compliance risk.

## 4. Fix Design (code-level)

### Primary fix — add `_enforce_chat_ban` in `broadcast_chat_store.py`

Add a new helper function and call it before `_enforce_chat_mute` in both
`send_chat_message` and `send_product_link_message`.

```python
# At top of app/services/broadcast_chat_store.py, add import:
from app.services.delegate_broadcast import is_viewer_banned

def _enforce_chat_ban(session_id: str, user_id: str) -> None:
    """Raise 403 if the viewer is banned from this broadcast session."""
    if is_viewer_banned(session_id, user_id):
        from fastapi import HTTPException
        raise HTTPException(
            status_code=403,
            detail={
                "code": "BROADCAST_CHAT_BANNED",
                "message": "You have been banned from this broadcast.",
            },
        )
```

In `send_chat_message` (line 158) and `send_product_link_message` (line 226),
change the enforcement block from:

```python
_enforce_chat_mute(session_id, user_id)
```

to:

```python
_enforce_chat_ban(session_id, user_id)
_enforce_chat_mute(session_id, user_id)
```

The ban check runs first: a banned user gets a deterministic 403 regardless
of mute state or rate limits.

### Secondary fix — platform-wide ban check in `send_chat_message`

For defence in depth against the scenario where a platform-wide banned user
has an unexpired session token, add a direct `is_user_currently_banned` call:

```python
from app.services.moderation_policy_engine import is_user_currently_banned

def _enforce_chat_ban(session_id: str, user_id: str) -> None:
    from fastapi import HTTPException
    # Check platform-wide account ban first (fastest, shared table)
    if is_user_currently_banned(user_id):
        raise HTTPException(
            status_code=403,
            detail={"code": "ACCOUNT_SUSPENDED", "message": "Account is suspended."},
        )
    # Then check per-session broadcast ban
    if is_viewer_banned(session_id, user_id):
        raise HTTPException(
            status_code=403,
            detail={"code": "BROADCAST_CHAT_BANNED", "message": "You have been banned from this broadcast."},
        )
```

### Dev/Prod parity (SECOPS-007)

Both `T.broadcast_moderation` and `T.account_state` are DynamoDB tables
present in both dev (DynamoDB Local) and prod (AWS DynamoDB). The lookup code
path is identical in both environments. No mock/flag bifurcation is needed.
The only dev-specific consideration is that `T.broadcast_moderation` must
exist in `scripts/local-ddb-init.py`; confirm it has a `TableDef` entry
(it does — `broadcast_moderation_table_name` is referenced in
`app/core/settings.py:2113`).

### Circular-import risk

`broadcast_chat_store.py` imports from `broadcast_sse.py`.
`delegate_broadcast.py` imports from `app.core.tables` and `app.core.time`
only. Adding `from app.services.delegate_broadcast import is_viewer_banned`
in `broadcast_chat_store.py` introduces a new cross-service import but does
not create a circular dependency. Confirm with a dry-run import check before
merging.

### Backward compatibility

The change adds new 403 responses to an existing endpoint. Clients that
currently rely on ban not being enforced (i.e., no legitimate clients) will
start receiving 403. The `BROADCAST_CHAT_BANNED` error code is new; frontend
WebSocket / SSE chat clients should handle the 403 gracefully by suppressing
the send attempt and optionally displaying an informational message to the
user.

returns `True`; `HTTPException(403)` is raised.

### Metrics / observability

Add a Prometheus counter `broadcast_chat_ban_enforced_total{reason="session_ban|account_ban"}` in `_enforce_chat_ban`. This makes it possible to monitor ban-enforcement rates and detect attempts to send through the banned path.

### Rollback

The change is additive (new helper + two call sites). Rollback: remove the
`_enforce_chat_ban` calls and the helper function. No schema changes.

### Risk

**Low.** The change adds DynamoDB reads (one `get_item` per chat message send).
At high broadcast chat volume (e.g., 10,000 messages/minute) this adds 10,000
`get_item` calls/minute to `T.broadcast_moderation`. DynamoDB Local and AWS
handle this well; the table is keyed exactly for this access pattern. Use a
short in-process TTL cache (`functools.lru_cache` with `maxsize` and a 5-second
TTL) if latency becomes a concern.

**S** — approximately 30 minutes of implementation plus test authoring.
