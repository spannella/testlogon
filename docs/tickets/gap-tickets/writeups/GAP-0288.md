# GAP-0288: `KycPiiSection` component is never used in any page — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at
> `frontend/src/components/shared/KycPiiSection.tsx` and
> `frontend/src/pages/admin/KycCaseDetailPage.tsx`.

## 1. Summary & Classification

**Plain-English statement**: The `KycPiiSection` component — which composes `PiiFieldDisplay`
and `PiiAuditLog` to display masked PII with per-field reveal and root-only key management —
exists at `frontend/src/components/shared/KycPiiSection.tsx` but is imported nowhere in the
application. The admin case detail page (`KycCaseDetailPage.tsx`) does not import or render
`KycPiiSection`, meaning the entire PII review and reveal workflow described in KYC-023
§3.12 is invisible to reviewers despite the backend endpoints being fully implemented.

- **Severity**: HIGH — feature is completely inaccessible from the UI
- **Source ticket**: KYC-023
- **Owning area**: Admin Frontend / KYC
- **Status**: Open
- **Claim accuracy**: Confirmed. Grep across all of `frontend/src/` finds zero imports of
  `KycPiiSection`, `PiiFieldDisplay`, or `PiiAuditLog` outside their own definition files.
  `KycCaseDetailPage.tsx` (685 lines) has no reference to any of these components.

**Note on claim wording**: The source GAP ticket states the fix requires props
`caseId`, `isAssigned`, and `isRoot`. The actual `KycPiiSection` component interface
(line 39–47 of `KycPiiSection.tsx`) uses `caseId`, `userSub`, `canReveal`, and `isRoot`
— not `isAssigned`. The fix below uses the actual props. The difference is that
`canReveal` captures both "assigned admin" and "root" scenarios, computed from
`KycCaseDetail.decision_state.assigned_admin_sub` and the viewer's role.

**Impact in one line**: Admins and root reviewers cannot view, reveal, or audit any
encrypted PII field on any KYC case, despite the backend API being production-ready.

**Related tickets**: KYC-023 (PII encryption + reveal endpoints), GAP-0287 (document
storage), `frontend/src/components/shared/PiiFieldDisplay.tsx`,
`frontend/src/components/shared/PiiAuditLog.tsx`.

## 2. Current-State Investigation (root cause)

### Component exists but is orphaned

`frontend/src/components/shared/KycPiiSection.tsx` is a complete, self-contained component
(177 lines). It:

- Queries `GET /ui/kyc-cases/{caseId}/pii` via `getMaskedPii(caseId)` to display masked
  field values.
- Renders one `PiiFieldDisplay` per field, each with its own "Reveal" button that calls
  the backend reveal endpoint.
- For `isRoot=true`, shows key management buttons (Rotate / Destroy) and the `PiiAuditLog`.

Its props interface (lines 39–47):

```typescript
export interface KycPiiSectionProps {
  caseId: string;
  userSub: string;       // case owner's sub — used for key rotate/destroy calls
  canReveal: boolean;    // true for assigned admin or root
  isRoot: boolean;       // true for root-only key management + audit log
}
```

### KycCaseDetailPage.tsx has no PII rendering

`frontend/src/pages/admin/KycCaseDetailPage.tsx` (685 lines) imports only:

```typescript
import { KycFacialComparisonReview } from "@/pages/admin/KycFacialComparisonReview";
```

There is no import of `KycPiiSection`, `PiiFieldDisplay`, or `PiiAuditLog`. The page
renders a two-column layout (lines 431–526): the left column shows `DocumentViewer` +
`KycFacialComparisonReview`; the right column shows Case Information, Actions, and
Timeline. There is no PII section in either column.

### What data is available on the page

`KycCaseDetail` (from `frontend/src/api/endpoints/kyc-admin.ts`, line 36) includes:

```typescript
user_sub: string;          // ← needed for KycPiiSection.userSub
decision_state: {
  assigned_admin_sub: string | null;  // ← needed to compute canReveal
  // …
};
```

The page already has `caseData.user_sub` and `caseData.decision_state.assigned_admin_sub`
available. The viewer's own identity (to compute `isRoot`) is available from
`useAuthStore` which is imported across the admin pages.

### `PiiFieldDisplay` and `PiiAuditLog` are also orphaned

`frontend/src/components/shared/PiiFieldDisplay.tsx` and
`frontend/src/components/shared/PiiAuditLog.tsx` are both fully implemented and are
imported only by `KycPiiSection.tsx` itself. Since `KycPiiSection` has no consumer,
none of the three components are ever mounted. `PiiFieldDisplay` renders a masked value
(e.g., `na**`) with a "Reveal" button that calls `revealPiiField(caseId, fieldName)`,
which POSTs to `GET /ui/kyc-cases/{id}/pii/{field}/reveal`. `PiiAuditLog` queries
`GET /ui/kyc-cases/{id}/pii/audit` and renders a timeline of access events. Both
backend endpoints are implemented (in `app/routers/kyc_cases.py`) and protected by
admin/root role requirements.

### Why the gap exists

The component and its two sub-components were likely shipped as part of the KYC-023
backend-focused sprint. The frontend integration step — adding `KycPiiSection` to
`KycCaseDetailPage` — was skipped or deferred and never completed. There is no feature
flag or conditional that hides it; it simply has no import anywhere.

### `KycCaseDetail` type has everything needed

The `KycCaseDetail` interface returned by `fetchKycCaseDetail()` (defined in
`frontend/src/api/endpoints/kyc-admin.ts`, lines 36–51) includes:
- `kyc_case_id: string` → maps to `KycPiiSection.caseId`
- `user_sub: string` → maps to `KycPiiSection.userSub`
- `decision_state.assigned_admin_sub: string | null` → used to compute `canReveal`

The viewer's own role is available from `useAuthStore` which is already used throughout
the admin pages. No new API calls or data fetching are required to supply the four props.

## 3. Impact / Exploit / Blast Radius

### Functional impact

Every admin and root reviewer that navigates to `/admin/kyc/{caseId}` sees the full
document viewer, facial comparison, timeline, and action buttons — but **no PII fields**.
The KYC-023 requirement that reviewers can verify applicant data (name, date of birth,
address) against submitted documents is unmet.

### Compliance gap

KYC regulations (FinCEN, FCA, EBA) require that an investigator can access all submitted
identity data during case review. If `KycPiiSection` is not rendered, reviewers cannot
confirm PII accuracy without leaving the platform to look up the underlying data
externally — creating an audit trail gap.

### Root key management inaccessible

The key rotation (`/ui/kyc-cases/user-keys/{sub}/rotate`) and destruction
(`/ui/kyc-cases/user-keys/{sub}/destroy`) operations — required for GDPR right-to-erasure
and for periodic key rotation — are only exposed via `KycPiiSection`. They are currently
unreachable from the UI. The only path to invoke them is a direct API call, which
requires root-level knowledge of the API structure.

### No blast radius on production data

This is a missing-feature gap, not a data corruption or unauthorized-access bug. Existing
data in DynamoDB and S3 is unaffected. No user data has been exposed; it is simply
inaccessible through the intended UI.

## 4. Fix Design (code-level)

### Change 1 — Import `KycPiiSection` and read viewer role in `KycCaseDetailPage.tsx`

Add to the import block (after line 47):

```typescript
import { KycPiiSection } from "@/components/shared/KycPiiSection";
import { useAuthStore } from "@/stores/authStore";
```

Inside the component body, after the existing state declarations (around line 292), add:

```typescript
const viewerSub = useAuthStore((s) => s.user?.sub ?? "");
const viewerRole = useAuthStore((s) => s.user?.role ?? "user");
const isRoot = viewerRole === "root";
```

### Change 2 — Compute `canReveal`

`canReveal` should be true for the assigned admin (matching `decision_state.assigned_admin_sub`)
or for any root user. Add after `const isRoot = …`:

```typescript
const canReveal =
  isRoot ||
  (!!caseData?.decision_state?.assigned_admin_sub &&
    caseData.decision_state.assigned_admin_sub === viewerSub);
```

### Change 3 — Render `KycPiiSection` in the right column

Insert after the Timeline card (currently the last element in the right column, line 525):

```tsx
{/* PII — masked fields, reveal, key management (KYC-023) */}
<KycPiiSection
  caseId={caseData.kyc_case_id}
  userSub={caseData.user_sub}
  canReveal={canReveal}
  isRoot={isRoot}
/>
```

This makes `KycPiiSection` the last card in the right-hand panel, below Timeline. If the
right column becomes too tall in practice, it can be moved to a dedicated "PII" tab in a
future UX pass, but the structural fix is to render it at all.

### Dev/Prod parity (SECOPS-007)

`KycPiiSection` uses the standard Axios `api` client from `frontend/src/api/client.ts`,
which proxies `/ui` requests through Vite to the backend in dev and hits the real FastAPI
server in production. The mocked AWS KMS and S3 are active in dev mode. No separate mock
path or feature flag is required. The component will work identically in both environments
once the session carries the correct `role` claim (which it does, via the HS256
`ui_access_token` JWT cookie).

The `getMaskedPii`, `rotateUserKey`, and `destroyUserKeys` functions in
`frontend/src/api/endpoints/kyc-cases.ts` are already implemented and use the same `api`
client.

### Backward compatibility

No backend changes are required. No DynamoDB schema changes. The fix is purely a frontend
import and render addition. Existing sessions, API keys, and data are unaffected. Rolling
back the change simply removes the rendered section without data loss.

### Observability

The backend already logs `kyc.pii.reveal` audit events (to the KYC PII audit table).
No additional instrumentation is needed at the component level. A dashboard query on
`kyc.pii.reveal` events will show adoption after the fix ships.

Once `KycPiiSection` is rendered, the `PiiAuditLog` component will automatically surface
the audit trail for each root user. If `kyc.pii.reveal` events are being generated in
production today (via direct API calls from reviewers who know the endpoint), those events
will become visible in the audit log immediately upon deployment — providing retrospective
visibility into any out-of-band reveals that occurred during the gap period.

### Accessibility of key management before the fix

The only current path to call `rotateUserKey` or `destroyUserKeys` is a direct API call
using a root-scoped session cookie or Bearer token. The backend endpoints are:
`POST /ui/kyc-cases/user-keys/{user_sub}/rotate` and
`POST /ui/kyc-cases/user-keys/{user_sub}/destroy`. Both require root role. In production,
these would only be invoked by engineers with direct API access — a significant operational
risk for GDPR erasure requests, which must be processed promptly. Adding `KycPiiSection`
to the admin UI makes these operations available to authorized root users through the
normal admin workflow, reducing the dependency on engineers for compliance actions.
