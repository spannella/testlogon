# GAP-0010: Agent Loop Not Running as Background Task — Remediation Write-up

> ~5 pages. Fix-oriented. Grounded in the investigation doc
> (docs/tickets/gap-tickets/investigations/GAP-0010.md) and real code at
> app/services/agent_orchestrator.py:705–736.

---

## 1. Summary & Classification

**Bug statement.** `start_agent_loop()` in
`app/services/agent_orchestrator.py:705` sets an in-memory flag
(`_running_loops[worker_id] = True`) and returns
`{"ok": True, "message": "Agent loop started. Will begin picking up eligible
tickets."}` — but it never spawns an `asyncio` coroutine or any other
background task. There is no `run_agent_loop` function anywhere in the codebase.
The result: calling `POST /ui/agent/workers/{id}/loop/start` makes the agent
appear to be running while it is completely inert. No tickets are ever claimed,
worked, or completed autonomously.

| Field | Value |
|-------|-------|
| Severity | **CRITICAL** |
| Source ticket | AGENT-003 |
| Status | Open |
| Owning area | Agent / Worker Orchestration |
| Investigation verdict | **Confirmed** |

**One-line impact.** Agents that are marked "running" never autonomously pick
up or process tickets; the entire autonomous agent feature does not function.

**Related tickets.** AGENT-003 (core loop design), AGENT-004 (worker fleet UI
— depends on loop being real), AGENT-005 (memory/context injection — depends
on loop dispatching tickets), AGENT-006 (terminal monitoring and feedback —
currently acts as the only active agent-loop code), GAP-0086 (feedback request
does not pause agent — requires a running loop to pause).

## 2. Current-State Investigation (root cause)

### The stub function (`app/services/agent_orchestrator.py:705–736`)

```python
def start_agent_loop(user_id: str, worker_id: str) -> Dict[str, Any]:
    """Mark the agent loop as started.

    The actual background task loop (run_agent_loop) is managed by
    AGENT-006. This function initializes state and marks the loop running.
    """
    worker = _get_worker_item(user_id, worker_id)
    if not worker:
        raise ValueError("Worker not found")

    if worker_id in _running_loops:
        raise ValueError("Agent loop is already running for this worker.")

    current_state = worker.get("agent_state", "")
    ts = now_ts()
    if not current_state or current_state in ("", "error"):
        T.agent_workers.update_item(
            Key={"pk": f"USER#{user_id}", "sk": f"WORKER#{worker_id}"},
            UpdateExpression="SET agent_state = :idle, heartbeat_at = :hb, ...",
            ExpressionAttributeValues={":idle": "idle", ":hb": ts, ...},
        )

    _running_loops[worker_id] = True
    logger.info("agent.loop.started worker_id=%s user_id=%s", worker_id, user_id)

    return {
        "ok": True,
        "worker_id": worker_id,
        "agent_state": ...,
        "message": "Agent loop started. Will begin picking up eligible tickets.",
    }
    # No asyncio.create_task(), no coroutine reference, nothing.
```

The docstring explicitly defers the real loop to "AGENT-006", but AGENT-006
(`terminal_monitor.py`, `agent_feedback.py`) was scoped to terminal monitoring
and feedback injection — not autonomous ticket dispatch.

### Supporting functions exist but are never called from the loop

A global search confirms the following fully-implemented helpers exist in
`app/services/agent_orchestrator.py`:

| Function | Line range | Purpose |
|----------|-----------|---------|
| `find_next_ticket()` | 238 | Query DDB for eligible tickets for a worker |
| `claim_ticket()` | 255 | Atomic conditional DDB claim (prevents race) |
| `complete_ticket()` | 403 | Mark ticket complete + transition agent state |
| `transition_agent_state()` | ~68 | State machine transitions |
| `inject_ticket_context()` | 598 | Build context prompt for ticket |

All the machinery for an autonomous loop is in place. The coroutine that
orchestrates them in sequence is simply absent.

### Background loop pattern used everywhere else

All other timed background tasks in the codebase use `asyncio.create_task()`:
- `app/services/broadcast_scheduler.py:109`
- `app/services/bot_scheduler.py:317`
- `app/services/billing_dunning.py:302`

The agent orchestrator was written before these patterns were established and
was never upgraded.

### In-process dict limitation

`_running_loops: Dict[str, bool] = {}` is a module-level dict. In a single
uvicorn worker (`--workers 1`, as required in dev by the moto constraint), this
is fine. In a multi-process or multi-instance production deployment, each
process has its own `_running_loops`. A worker started on instance A is
invisible to instance B. `is_loop_running()` returns `False` for workers
started elsewhere, and `start_agent_loop()` would attempt to double-start the
loop on a second instance. This is a known architectural limitation that must
be addressed before multi-instance production deployment.

## 3. Impact / Exploit / Blast Radius

This is a **functional gap** rather than a security vulnerability.

**Primary impact.** The autonomous agent feature (AGENT-003) does not work at
all. Tickets assigned to an agent worker are never processed. The
`agent_state` transitions (`idle → claiming → working → completing → idle`)
never fire. Workers accumulate in `_running_loops` as "running" with stale
heartbeats, which triggers the `find_stale_workers()` alert path and sends
false heartbeat-missed alerts.

**Downstream cascades:**
- AGENT-005 (context injection) — `inject_ticket_context()` is never called,
  so the terminal never receives ticket context.
- AGENT-006 (feedback monitoring) — `detect_completion_signals()` is never
  invoked from a loop, so completion detection is purely reactive (only when
  the frontend polls).
- GAP-0086 (feedback request pause) — pausing requires the loop to be running;
  if the loop doesn't exist, pause state is set in DDB but no running coroutine
  observes it.

**Multi-instance deployment risk.** Deploying without fixing the in-process
dict on a load-balanced multi-instance setup would allow the same worker to
be "started" on multiple instances simultaneously, leading to concurrent ticket
claims (partially mitigated by `claim_ticket()`'s conditional write, but
creating unnecessary noise and resource contention).

## 4. Fix Design (code-level)

### Step 1 — Implement `run_agent_loop` coroutine

Add to `app/services/agent_orchestrator.py`, directly above
`start_agent_loop()` at line ~704:

```python
import asyncio  # add to existing imports at top of file

async def run_agent_loop(user_id: str, worker_id: str) -> None:
    """Autonomous agent loop: poll for eligible tickets and work them.

    Runs as an asyncio background task until the worker_id is removed
    from _running_loops (by stop_agent_loop) or an unrecoverable error
    transitions the agent to 'error' state.

    NOTE (SECOPS-007 / AGENT-003): _running_loops is an in-process dict.
    This implementation is correct for single-process (uvicorn --workers 1)
    deployments. For multi-process/multi-instance deployments a distributed
    lock (e.g., DynamoDB conditional write or SQS visibility timeout) must
    replace this dict before production scaling.
    """
    poll_interval = getattr(S, "agent_loop_poll_interval_seconds", 30)
    logger.info("agent.loop.running worker_id=%s user_id=%s", worker_id, user_id)
    try:
        while worker_id in _running_loops:
            # 1. Re-fetch current worker state — honour pause/stop signals
            worker = _get_worker_item(user_id, worker_id)
            if not worker:
                logger.warning("agent.loop.worker_missing worker_id=%s", worker_id)
                break
            state = worker.get("agent_state", "idle")
            if state in ("paused", "error"):
                await asyncio.sleep(poll_interval)
                continue

            # 2. Update heartbeat
            try:
                T.agent_workers.update_item(
                    Key={"pk": f"USER#{user_id}", "sk": f"WORKER#{worker_id}"},
                    UpdateExpression="SET heartbeat_at = :hb",
                    ExpressionAttributeValues={":hb": now_ts()},
                )
            except Exception:
                logger.warning("agent.loop.heartbeat_failed worker_id=%s", worker_id)

            # 3. Find next eligible ticket
            ticket = find_next_ticket(user_id, worker_id)
            if not ticket:
                await asyncio.sleep(poll_interval)
                continue

            # 4. Claim ticket (atomic — handles race with other workers)
            try:
                transition_agent_state(user_id, worker_id, "claiming")
                claim_ticket(user_id, worker_id, ticket["ticket_id"])
            except ValueError as exc:
                # Claim lost to another worker — back to idle
                logger.info(
                    "agent.loop.claim_lost worker_id=%s ticket_id=%s reason=%s",
                    worker_id, ticket["ticket_id"], exc,
                )
                transition_agent_state(user_id, worker_id, "idle")
                await asyncio.sleep(1)   # brief pause before next poll
                continue

            # 5. Inject context and transition to working
            try:
                context = inject_ticket_context(user_id, worker_id, ticket["ticket_id"])
                transition_agent_state(user_id, worker_id, "working")
                logger.info(
                    "agent.loop.ticket_claimed worker_id=%s ticket_id=%s",
                    worker_id, ticket["ticket_id"],
                )
                # Dispatch to execution layer — AGENT-004/006
                await _dispatch_ticket(user_id, worker_id, ticket, context)
            except Exception:
                logger.exception(
                    "agent.loop.dispatch_error worker_id=%s ticket_id=%s",
                    worker_id, ticket["ticket_id"],
                )
                transition_agent_state(user_id, worker_id, "error")
                # Release the ticket so another worker can pick it up
                try:
                    release_ticket(user_id, worker_id, ticket["ticket_id"])
                except Exception:
                    pass

            await asyncio.sleep(poll_interval)
    finally:
        _running_loops.pop(worker_id, None)
        logger.info("agent.loop.exited worker_id=%s", worker_id)
```

### Step 2 — Wire `create_task` in `start_agent_loop()`

At `app/services/agent_orchestrator.py:728`, after setting
`_running_loops[worker_id] = True`, add one line:

```python
    _running_loops[worker_id] = True
    asyncio.create_task(run_agent_loop(user_id, worker_id))  # ADD THIS
    logger.info("agent.loop.started worker_id=%s user_id=%s", worker_id, user_id)
```

`asyncio.create_task()` schedules the coroutine on the current running event
loop. FastAPI/uvicorn always runs in an async event loop, so this call is safe
from any async or sync context that uvicorn will call. (Sync endpoint handlers
share the same event loop via the default thread-pool executor.)

### Step 3 — Add `_dispatch_ticket` stub

Add a minimal async dispatch function (to be expanded by AGENT-004/006):

```python
async def _dispatch_ticket(
    user_id: str, worker_id: str,
    ticket: Dict[str, Any], context: str
) -> None:
    """Dispatch a claimed ticket to the agent execution layer.

    Currently a stub — actual execution is handled by the terminal
    session injection (AGENT-006). Future: send context to active
    terminal via SSE/WS, then monitor for completion signals.
    """
    # Inject the context into the agent's terminal session
    from app.services import terminal_monitor
    try:
        terminal_monitor.inject_context_to_terminal(
            user_id=user_id,
            worker_id=worker_id,
            context=context,
        )
    except Exception:
        logger.warning("agent.dispatch.inject_failed worker_id=%s", worker_id)
    # Loop exits; completion detection is driven by terminal_monitor feedback
```

### Step 4 — Add `agent_loop_poll_interval_seconds` to settings

In `app/core/settings.py`, add near the other agent settings:

```python
agent_loop_poll_interval_seconds: int = int(
    os.environ.get("AGENT_LOOP_POLL_INTERVAL_SECONDS", "30")
)
```

### Dev/Prod parity (SECOPS-007)

`asyncio.create_task()` is a standard Python async primitive with no AWS
dependency. No external services are introduced. The fix works identically
in dev (DynamoDB Local) and production (AWS DynamoDB).

**Critical parity note:** The `_running_loops` in-process dict is not
distributed. For the current dev deployment (uvicorn `--workers 1`, single
EC2 instance), this is correct. Before scaling to multiple uvicorn workers or
multiple EC2 instances, the dict must be replaced with a DynamoDB conditional
write as a distributed mutex:

```python
# Distributed start guard (future — not part of this fix):
T.agent_workers.update_item(
    Key={"pk": f"USER#{user_id}", "sk": f"WORKER#{worker_id}"},
    UpdateExpression="SET loop_lock = :ts",
    ConditionExpression="attribute_not_exists(loop_lock)",
    ExpressionAttributeValues={":ts": now_ts()},
)
```

This is a known follow-on (marked in the code comment per SECOPS-007).

### Rollback

Remove the `asyncio.create_task(...)` line and the `run_agent_loop` coroutine.
`_running_loops` flag is still set but no coroutine runs — returns to current
stub behaviour. No DDB changes required.

### Risks

- **Event loop blocking:** `run_agent_loop` must never block the event loop.
  All blocking I/O is via `T.*` (boto3) which is synchronous. To avoid
  blocking, wrap DDB calls with `asyncio.to_thread()` or use aioboto3. For
  the initial fix, at `poll_interval=30` seconds the blocking risk is low
  for a single DDB call. A follow-on ticket should migrate to `asyncio.to_thread`.
- **`asyncio.create_task()` from sync context:** FastAPI sync endpoint handlers
  run in a thread pool. Calling `asyncio.create_task()` from a thread requires
  `asyncio.get_event_loop().call_soon_threadsafe(lambda: asyncio.create_task(...))`.
  If `start_agent_loop` is called from a sync endpoint, replace with:
  ```python
  loop = asyncio.get_event_loop()
  loop.call_soon_threadsafe(
      lambda: asyncio.ensure_future(run_agent_loop(user_id, worker_id))
  )
  ```
- **Multi-instance:** As documented in SECOPS-007 note in the code, the
  in-process dict must be replaced with a DDB distributed lock before
  horizontal scaling. Deploy this fix only to single-worker instances first.
- **Unhandled coroutine exception:** `asyncio.create_task()` silently swallows
  exceptions that are not awaited. The `try/finally` in `run_agent_loop`
  ensures cleanup, but adding an exception handler callback is prudent:
  ```python
  task = asyncio.create_task(run_agent_loop(user_id, worker_id))
  task.add_done_callback(
      lambda t: t.exception() and logger.error(
          "agent.loop.uncaught_exception worker_id=%s", worker_id, exc_info=t.exception()
      )
  )
  ```

### Effort

**L** — Writing a correct and safe `run_agent_loop` coroutine requires careful
handling of: state machine transitions, claim races, error recovery, heartbeat
updates, graceful shutdown, and the distributed-deployment concern. Scaffolding
is ~80 lines but thorough testing and the multi-instance concern make this a
larger effort than GAP-0006/0007/0008/0009. Estimated: 1–2 days development,

### Sequencing
