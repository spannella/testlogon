# GAP-0180: Circuit Breaker Not Integrated into Dispatcher Loop — Remediation Write-up

> Source ticket: ENTERPRISE-005 · Severity: HIGH · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** `app/services/webhook_circuit_breaker.py` is a fully implemented three-state
circuit breaker (closed/open/half-open) with `should_attempt_delivery` and
`record_delivery_result` functions. `app/services/webhook_dispatcher.py` — the background task
that actually delivers webhooks — never imports or calls either function. Every webhook delivery
is attempted regardless of the endpoint's circuit state. An endpoint that has been marked
`"open"` by the circuit breaker (because it has failed `N` consecutive times) continues to
receive delivery attempts, generating noise in the delivery log and burning retry budget
until DLQ promotion, exactly as if the circuit breaker did not exist.

**Verdict:** Confirmed. `app/services/webhook_dispatcher.py` imports from `webhook_service`
only (line 11–20). There is no import of `webhook_circuit_breaker` anywhere in the file, and
no call to `should_attempt_delivery` or `record_delivery_result` in either
`run_webhook_dispatcher_loop` (lines 28–85) or `run_webhook_dispatcher_once` (lines 103–138).
The circuit breaker module exists and is fully functional in isolation but is completely
disconnected from the delivery pipeline.

**Severity and area.** HIGH / Webhooks & Integrations (ENTERPRISE-005). Without circuit
breaker integration, a misbehaving or permanently-down endpoint:
- Consumes retry budget and exhausts DLQ capacity.
- Generates spurious delivery failure events and error logs.
- Creates a thundering-herd risk if many endpoints go down simultaneously (e.g., during a
  dependency outage).
- Defeats the purpose of the circuit breaker feature entirely.

**Related tickets.** ENTERPRISE-005 (webhook feature). No blocking dependency on other gaps;
this is a two-line integration change.

## 2. Current-State Investigation (root cause)

### The dispatcher loop: `webhook_dispatcher.py:44–71`

```python
for delivery in due:
    try:
        endpoint_id = delivery.get("endpoint_id", "")
        user_sub = delivery.get("user_sub", "")
        endpoint = _get_endpoint_raw(user_sub, endpoint_id)
        if not endpoint or not endpoint.get("enabled", True):
            mark_delivery_dead_letter(delivery, reason="endpoint_disabled")
            continue

        secret = _decrypt_secret(endpoint["secret"])
        result = await deliver_webhook(        # ← delivery attempted unconditionally
            url=endpoint["url"],
            payload=delivery.get("payload", "{}"),
            secret=secret,
            delivery_id=delivery.get("delivery_id", ""),
            event_type=delivery.get("event_type", ""),
        )

        if result["success"]:
            mark_delivery_success(delivery, result)
            reset_endpoint_failure_count(endpoint_id, user_sub)
            _processed += 1
        else:
            handle_delivery_failure(delivery, endpoint, result)  # ← no circuit update
            _failed += 1
    except Exception:
        _failed += 1
        logger.exception(...)
```

The loop checks `endpoint.get("enabled")` and handles delivery success/failure, but:
1. It never calls `should_attempt_delivery(endpoint, now)` before attempting delivery.
2. It never calls `record_delivery_result(endpoint, success)` after the outcome is known.

### The circuit breaker module: `webhook_circuit_breaker.py`

`should_attempt_delivery` at `webhook_circuit_breaker.py:25–50` implements the correct guard:

```python
def should_attempt_delivery(endpoint: Dict[str, Any], now: int) -> bool:
    if not S.webhooks_circuit_breaker_enabled:
        return True
    state = get_circuit_state(endpoint)   # reads endpoint["circuit_state"]
    if state == "closed":
        return True
    if state == "half_open":
        return True
    if state == "open":
        test_at = endpoint.get("circuit_test_at", 0)
        if test_at and now >= int(test_at):
            transition_circuit(..., "half_open")
            return True
        return False   # ← skip delivery if circuit is open and cooldown hasn't expired
    return True
```

`record_delivery_result` at `webhook_circuit_breaker.py:53–120` handles state transitions:
- Success on `closed`: resets consecutive failures.
- Success on `half_open` or `open`: closes the circuit.
- Failure on `half_open`: doubles the cooldown and re-opens.
- Failure on `closed` when `consecutive >= threshold`: opens the circuit.

Both functions are deterministic and fully unit-tested in isolation (based on their logic), but
they are never called by the dispatcher.

### The `run_webhook_dispatcher_once` function (lines 103–138)

The same pattern appears in `run_webhook_dispatcher_once`, the "run now" path invoked from the
admin job-runner UI. This path also performs unconditional delivery with no circuit check.

### Settings confirm intent

`app/core/settings.py:1730–1733` declares:

```python
webhooks_circuit_breaker_enabled: bool = ... (default True)
webhooks_default_circuit_failure_threshold: int = ... (default 10)
webhooks_circuit_initial_cooldown_seconds: int = ... (default 300)
webhooks_circuit_max_cooldown_seconds: int = ... (default 86400)
```

These settings are read inside `webhook_circuit_breaker.py` but have no effect in production
because the circuit breaker functions are never called.

## 3. Impact / Exploit / Blast Radius

**Thundering herd on outages.** When a downstream webhook consumer goes down for minutes or
hours, the dispatcher continues attempting delivery on every poll cycle (every 10 seconds).
With the default batch size of 50 and the default poll interval of 10 seconds, a single dead
endpoint can generate 18 000 failed HTTP requests per hour. If multiple consumers are down
simultaneously (e.g., during a shared cloud provider incident), this saturates the dispatcher's
HTTP connection pool and delays delivery for healthy endpoints.

**Retry budget exhaustion.** `handle_delivery_failure` increments a retry counter and
eventually promotes to DLQ after `max_attempts` failures. With the circuit breaker disabled,
the `max_attempts` budget is consumed at full speed. A 3-attempt budget for an endpoint
that is down for 30 minutes is exhausted in under 60 seconds (3 retries × 10s poll = 30s),
after which the delivery is permanently dead-lettered even though the endpoint will recover.

**Noise and alert fatigue.** Every failed delivery logs an error and writes a failure record
to DynamoDB. A 24-hour outage on one endpoint generates ~8 640 error log lines and DynamoDB
writes, creating noise that masks real errors from healthy endpoints.

**No security exploit or data loss.** The bug causes excess attempts and premature DLQ
promotion, not data leakage or injection. No user data is at risk.

**Blast radius.** All `pending` and `failed` webhook deliveries in every poll cycle, for every
endpoint regardless of circuit state. The `WEBHOOKS_CIRCUIT_BREAKER_ENABLED` flag has no effect
until the integration fix is deployed.

## 4. Fix Design (code-level)

### Two-line integration in the delivery loop

The fix is minimal: add the circuit check before delivery and the result recording after.

```python
# app/services/webhook_dispatcher.py

# Add to imports (top of file):
from app.services.webhook_circuit_breaker import (
    should_attempt_delivery,
    record_delivery_result,
)

# Inside run_webhook_dispatcher_loop, replace the delivery block (lines 44–71):

for delivery in due:
    try:
        endpoint_id = delivery.get("endpoint_id", "")
        user_sub = delivery.get("user_sub", "")
        endpoint = _get_endpoint_raw(user_sub, endpoint_id)
        if not endpoint or not endpoint.get("enabled", True):
            mark_delivery_dead_letter(delivery, reason="endpoint_disabled")
            continue

        # ── CIRCUIT BREAKER GUARD (new) ────────────────────────────
        if not should_attempt_delivery(endpoint, now):
            logger.debug(
                "Circuit open for endpoint %s — skipping delivery %s",
                endpoint_id,
                delivery.get("delivery_id", ""),
            )
            continue
        # ──────────────────────────────────────────────────────────

        secret = _decrypt_secret(endpoint["secret"])
        result = await deliver_webhook(
            url=endpoint["url"],
            payload=delivery.get("payload", "{}"),
            secret=secret,
            delivery_id=delivery.get("delivery_id", ""),
            event_type=delivery.get("event_type", ""),
        )

        if result["success"]:
            mark_delivery_success(delivery, result)
            reset_endpoint_failure_count(endpoint_id, user_sub)
            record_delivery_result(endpoint, success=True)    # ← new
            _processed += 1
        else:
            handle_delivery_failure(delivery, endpoint, result)
            record_delivery_result(endpoint, success=False)   # ← new
            _failed += 1
    except Exception:
        _failed += 1
        logger.exception("Webhook delivery error for %s", delivery.get("delivery_id", ""))
```

Apply the identical change to `run_webhook_dispatcher_once` (lines 112–137) for consistency:

```python
# run_webhook_dispatcher_once — same additions
if not should_attempt_delivery(endpoint, now_ts()):
    continue
...
record_delivery_result(endpoint, success=result["success"])
```

### Why `now` is already available

In `run_webhook_dispatcher_loop`, `now = now_ts()` is computed at the top of each iteration
(line 39). Pass this value to `should_attempt_delivery(endpoint, now)` so the circuit
cooldown comparison uses a consistent timestamp for the entire batch rather than calling
`now_ts()` redundantly per delivery.

In `run_webhook_dispatcher_once`, compute `now = now_ts()` at the start (it already exists
at line 106) and pass it through.

### Dev/prod parity (SECOPS-007)

`webhook_circuit_breaker.py` calls `T.webhook_endpoints.update_item` for state transitions.
`T.webhook_endpoints` is a DynamoDB table handle that resolves to DynamoDB Local in dev and
AWS DynamoDB in production. No `S.dev_mode` fork is needed; the fix is identical in both
environments. The `WEBHOOKS_CIRCUIT_BREAKER_ENABLED=0` feature flag (which defaults to `True`
but can be set to `0`) allows disabling the circuit breaker without a code deploy in any
environment.

### `record_delivery_result` and the stale `endpoint` dict

`endpoint` is fetched from DynamoDB at the top of the loop by `_get_endpoint_raw`. The circuit
state fields (`circuit_state`, `circuit_consecutive_failures`, etc.) are read from this snapshot.
`record_delivery_result` writes updated state back to DynamoDB but does not mutate the Python
dict. For a single loop iteration this is correct because each delivery uses a freshly-fetched
endpoint snapshot. If two workers process the same endpoint concurrently (possible during a
rolling deploy), the `_increment_consecutive_failures` call in `record_delivery_result` uses
an absolute SET (not an atomic increment), which could cause a count to be overwritten.

To make the failure counter increment atomic:

```python
# webhook_circuit_breaker.py — replace _increment_consecutive_failures:
def _increment_consecutive_failures(endpoint_id: str, user_sub: str) -> None:
    """Atomically increment the consecutive failure counter."""
    T.webhook_endpoints.update_item(
        Key={"pk": f"USER#{user_sub}", "sk": f"ENDPOINT#{endpoint_id}"},
        UpdateExpression="ADD circuit_consecutive_failures :one",
        ExpressionAttributeValues={":one": 1},
    )
```

The `ADD` operation on a numeric attribute is atomic in DynamoDB. The `record_delivery_result`
function passes `consecutive` (computed from the stale dict) to the old implementation; with
the atomic version it no longer needs to compute a local count.

**Alternatives considered:**

- **DynamoDB Streams trigger**: have circuit transitions happen via a stream-based Lambda
  instead of inline in the dispatcher. Rejected: adds infrastructure complexity for a
  change that is a two-line import addition.
- **Skip `record_delivery_result` and only gate on `should_attempt_delivery`**: the circuit
  would never open because nothing records failures. Rejected: both halves are required.

### Regression test (pytest offline — fails before fix, passes after)

```python
# tests/test_webhook_dispatcher.py

import asyncio
import pytest
from unittest.mock import patch, MagicMock, AsyncMock


def _make_delivery(endpoint_id="ep1", user_sub="user_a"):
    return {
        "delivery_id": "del_001",
        "endpoint_id": endpoint_id,
        "user_sub": user_sub,
        "payload": "{}",
        "event_type": "test.event",
    }


def _make_endpoint(circuit_state="closed", endpoint_id="ep1", user_sub="user_a"):
    return {
        "endpoint_id": endpoint_id,
        "user_sub": user_sub,
        "url": "https://example.com/hook",
        "secret": "enc_secret",
        "enabled": True,
        "circuit_state": circuit_state,
        "circuit_test_at": 0,
        "circuit_consecutive_failures": 0,
    }


def test_dispatcher_skips_open_circuit(monkeypatch):
    """Deliveries for open-circuit endpoints must be skipped, not attempted."""
    delivery = _make_delivery()
    endpoint = _make_endpoint(circuit_state="open")
    # Set circuit_test_at far in the future so cooldown has not expired
    endpoint["circuit_test_at"] = 9_999_999_999

    attempted = []

    async def _fake_deliver(**kwargs):
        attempted.append(kwargs["delivery_id"])
        return {"success": True, "status_code": 200}

    with patch(
        "app.services.webhook_dispatcher._get_endpoint_raw",
        return_value=endpoint,
    ), patch(
        "app.services.webhook_dispatcher.deliver_webhook",
        side_effect=_fake_deliver,
    ), patch(
        "app.services.webhook_dispatcher.query_due_deliveries",
        return_value=[delivery],
    ), patch(
        "app.services.webhook_dispatcher._decrypt_secret",
        return_value="secret",
    ):
        from app.services.webhook_dispatcher import run_webhook_dispatcher_once
        asyncio.get_event_loop().run_until_complete(run_webhook_dispatcher_once())

    # No delivery should have been attempted
    assert attempted == [], (
        "Expected 0 deliveries (circuit open), got: " + str(attempted)
    )


def test_dispatcher_records_failure_result(monkeypatch):
    """After a failed delivery, record_delivery_result must be called with success=False."""
    delivery = _make_delivery()
    endpoint = _make_endpoint(circuit_state="closed")

    results_recorded = []

    with patch(
        "app.services.webhook_dispatcher._get_endpoint_raw",
        return_value=endpoint,
    ), patch(
        "app.services.webhook_dispatcher.deliver_webhook",
        return_value={"success": False, "status_code": 500, "error": "server error"},
    ), patch(
        "app.services.webhook_dispatcher.query_due_deliveries",
        return_value=[delivery],
    ), patch(
        "app.services.webhook_dispatcher._decrypt_secret",
        return_value="secret",

        from app.services.webhook_dispatcher import run_webhook_dispatcher_once

        "Expected record_delivery_result(success=False), got: " + str(results_recorded)

def test_dispatcher_records_success_result(monkeypatch):
```

**Before fix:** `test_dispatcher_skips_open_circuit` fails because `attempted` is `["del_001"]`
(delivery was attempted despite open circuit). `test_dispatcher_records_failure_result` fails
because `record_delivery_result` is never imported or called (mock is never invoked).

**After fix:** All three tests pass.

### Manual QA steps

1. Create a webhook endpoint via `POST /ui/webhooks/endpoints` pointing to a non-existent URL
   (e.g., `https://localhost:9999/nonexistent`).
2. Trigger a webhook delivery via any event (e.g., send a message).
3. Observe 10 consecutive failures — confirm the endpoint's `circuit_state` transitions to
   `"open"` in DynamoDB.
4. Trigger another delivery for the same endpoint.
5. Check the dispatcher logs — confirm "Circuit open for endpoint — skipping delivery" appears
   and no HTTP request is made to the endpoint URL.
6. Wait for `circuit_test_at` to expire (default 300 seconds) — confirm the next delivery
   triggers a `half_open` transition and actually attempts one HTTP call.

### Observability

- Add a `webhook.circuit_skipped` counter metric (Prometheus/CloudWatch) incremented each
  time `should_attempt_delivery` returns `False`. An alert on this metric provides visibility
  into how many endpoints are currently circuit-open.
- Log at `INFO` level when `should_attempt_delivery` returns `False` (already in the proposed
  fix above). Use structured logging: `endpoint_id`, `circuit_state`, `circuit_test_at`.
- DynamoDB: alert if any endpoint has `circuit_state = "open"` for more than
  `webhooks_circuit_max_cooldown_seconds` (24 hours) — this indicates the endpoint is
  permanently down and should be disabled.

### Rollout

1. Deploy `webhook_dispatcher.py` change — two import additions and four new lines.
2. No DynamoDB schema changes. No migration. No downtime.
3. Verify by inspecting dispatcher logs after deploy: circuits that are currently `"open"`
   (if any exist from accumulated failures) should show "skipping delivery" log lines.
4. Monitor `webhook.circuit_skipped` metric; confirm it behaves as expected.
