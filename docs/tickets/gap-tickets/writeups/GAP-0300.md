# GAP-0300: Token refresh callback absent from `MediaPlayer` — Remediation Write-up

> ~5 pages. Fix-oriented. No investigation doc exists; the claim is verified directly against the codebase.

## 1. Summary & Classification

**Bug statement:** `MediaPlayer` includes no mechanism to refresh an expiring playback token. Playback tokens are time-limited JWTs (or signed URL query parameters). When a token expires mid-stream, the CDN or key server begins rejecting segment and key requests. HLS.js eventually surfaces a fatal network error, killing playback. There is no proactive refresh: no `onTokenExpiring` callback prop, no `exp`-claim timer, and no path to update `hls.config.xhrSetup` with a new token on an already-running instance.

- **Severity:** HIGH
- **Source ticket:** MEDIA-001
- **Status:** Open — no token refresh mechanism exists
- **Owning area:** Frontend / MediaPlayer / Session management
- **Claim verdict:** CONFIRMED. A full-text search of `frontend/src/components/shared/MediaPlayer.tsx` yields zero occurrences of `xhrSetup`, `exp`, `jwt`, `token`, `refresh`, or `Authorization`. The `VideoPlayerPage` (`frontend/src/pages/videos/VideoPlayerPage.tsx`) builds the playback URL as `${hls_manifest_url}?token=${playback_token}` (line 377) and makes no provision for refreshing it. The `token_expires_at` field is defined in two response types (`VodRentalStartResponse` and `VodAdSupportedStartResponse`, `frontend/src/api/types.ts:9300,10178`) but is never consumed by the player page.

**Related tickets:** MEDIA-001 (parent); GAP-0299 (DRM configuration, same file); SECOPS-007 (dev/prod parity).


## 2. Current-State Investigation (root cause)

### 2.1 How the playback token reaches the player

`VideoPlayerPage` fetches video detail via `getVideoDetail(videoId)` using React Query (`useQuery`). The response includes `hls_manifest_url` and `playback_token` (defined in `VideoDetail` at `frontend/src/api/endpoints/videos.ts:85`). The page constructs the playback URL:

```typescript
// frontend/src/pages/videos/VideoPlayerPage.tsx:374-378
const playbackUrl =
  video?.hls_manifest_url && video?.playback_token
    ? `${video.hls_manifest_url}?token=${video.playback_token}`
    : null;
```

This URL is passed to `<MediaPlayer src={playbackUrl} .../>` (line 482) and does not change for the lifetime of the page unless the page itself re-fetches (the `handleRetry` callback on line 387 calls `refetch()` which re-queries `getVideoDetail`). There is no scheduled re-fetch before token expiry.

### 2.2 How `token_expires_at` is ignored

The `VodRentalStartResponse` type declares `token_expires_at: number` (`frontend/src/api/types.ts:9300`) and `VodAdSupportedStartResponse` also declares it (`types.ts:10178`). Neither field is used in `VideoPlayerPage`. The `video` object in the page comes from `VideoDetail` which does not include `token_expires_at` in the `playback_token`-bearing response — the token expiry is embedded inside the JWT but never decoded. There is no `jwtDecode` import anywhere in the player pages.

### 2.3 What happens at token expiry

When the playback token JWT expires:

1. HLS.js fetches the next TS segment. The CDN validates the token in the query string and returns HTTP 403.
2. HLS.js retries up to `fragLoadingMaxRetry: 6` times (line 318 in `MediaPlayer.tsx`), all failing with 403.
3. After exhausting retries, HLS.js fires `Hls.Events.ERROR` with `data.fatal = true` and `data.type = Hls.ErrorTypes.NETWORK_ERROR`.
4. `MediaPlayer`'s error handler (line 357-394) shows "Stream unavailable. It may have ended or the URL has expired." and sets state to `"error"`.
5. The user sees the error overlay. Recovery requires a full page reload, which re-fetches a fresh token.

This means for any video session longer than the token TTL (typically 1–4 hours for VOD), the user is interrupted mid-playback with an unrecoverable error unless they manually reload.

### 2.4 `MediaPlayer` component internals — no `xhrSetup`

```typescript
// frontend/src/components/shared/MediaPlayer.tsx:310-325
const hlsConfig: Partial<...> = {
  startLevel: -1,
  enableWorker: true,
  lowLatencyMode: mode === "live",
  maxBufferLength: mode === "live" ? 6 : 30,
  maxMaxBufferLength: mode === "live" ? 12 : 60,
  fragLoadingMaxRetry: 6,
  manifestLoadingMaxRetry: 4,
  levelLoadingMaxRetry: 4,
};
```

There is no `xhrSetup` hook in `hlsConfig`. HLS.js's `xhrSetup` callback is the canonical mechanism for intercepting every XHR request (manifest fetches, segment fetches, key fetches) to inject updated auth headers or URL parameters. Without it, there is no way to swap in a new token on an existing HLS.js instance.

### 2.5 Retry path does not refresh token

`MediaPlayer`'s `retry` handler (line 545-600) creates a new `Hls()` instance and reloads from the same `src` prop. If `src` still contains an expired token, the new HLS.js instance immediately fails again. A token refresh requires the _parent_ to provide a new `src` or a new token.

**Dev vs prod:** Both environments are affected. In dev the token TTL may be very long (or absent from mock responses), masking the issue locally.


## 3. Impact / Exploit / Blast Radius

**Who is affected:** Any user watching a video whose session outlasts the playback token TTL. For short videos this is rarely triggered; for long-form content (movies, lectures, live recordings), the token is very likely to expire during normal viewing.

**Specific scenarios:**

- **VOD long-form content:** A user starts a 2-hour film with a 1-hour token. At the 60-minute mark, playback crashes with an error overlay. The user must reload the page (losing watch position unless server-side progress is tracked).
- **Live streams:** Live tokens may have shorter TTLs (30–60 minutes) to limit CDN cache poisoning exposure. A viewer watching a 3-hour live event would be disconnected multiple times.
- **DRM key requests (GAP-0299):** DRM license tokens typically have a shorter TTL than manifest tokens. Without `xhrSetup`, a renewed DRM token cannot be injected into in-flight key requests.
- **Subscription or rental access:** For rented content (VOD-rental), the CDN token may embed rental validity. A user who has a valid rental but expired session token appears to have no access — leading to support tickets and potential refund demands.

**Blast radius:** HIGH for long-session viewers; MEDIUM for short VOD content. Affects 100% of viewers whose session exceeds the token TTL.


## 4. Fix Design (code-level)

### 4.1 New `onTokenExpiring` prop on `MediaPlayerProps`

```typescript
// frontend/src/components/shared/MediaPlayer.tsx — Props section

export interface MediaPlayerProps {
  // ... existing props ...

  /**
   * Called ~30 seconds before the playback token is expected to expire.
   * Should return a Promise resolving to the new token string (or full signed URL).
   * If the promise rejects, the player will surface an error to onError.
   */
  onTokenExpiring?: () => Promise<string>;

  /**
   * Unix timestamp (seconds) when the current playback token expires.
   * Required for proactive refresh; derived from JWT `exp` claim or server response.
   */
  tokenExpiresAt?: number;
}
```

### 4.2 `xhrSetup` for in-flight token injection

```typescript
// Inside the HLS setup useEffect, after `const hls = new Hls(hlsConfig)`:

// tokenRef holds the mutable current token value so xhrSetup always uses
// the latest token without requiring HLS.js to be re-initialised.
const tokenRef = useRef<string | null>(null);

// Extract initial token from the src URL (query param `token=...`)
const extractToken = (url: string): string | null => {
  try {
    return new URL(url).searchParams.get("token");
  } catch {
    return null;
  }
};
tokenRef.current = extractToken(src);

// xhrSetup: inject current token into every XHR before it fires
(hlsConfig as Record<string, unknown>).xhrSetup = (
  xhr: XMLHttpRequest,
  url: string,
) => {
  if (!tokenRef.current) return;
  // Re-write the query param on every request
  try {
    const u = new URL(url, window.location.origin);
    u.searchParams.set("token", tokenRef.current);
    // HLS.js reads `xhr.open` args; override URL via the 'open' method before send
    // (HLS.js 1.x supports xhrSetup mutation of the URL via the `url` argument)
  } catch {
    // Non-parseable URL: leave untouched
  }
};
```

> Note: HLS.js 1.x `xhrSetup` receives `(xhr, url)` before `xhr.open()` is called. The `url` argument is the resolved segment URL. To mutate it, wrap via `Hls`'s `loadPolicy` or use `hls.config.xhrSetup` which is a post-`open` hook. For token injection the recommended pattern is `xhr.setRequestHeader("Authorization", "Bearer " + tokenRef.current)` if the CDN accepts header auth, or use HLS.js 1.x's `loader` override for query-param mutation.

### 4.3 Token refresh timer

```typescript
// After hls is instantiated, add a refresh scheduler:

const refreshTimerRef = useRef<ReturnType<typeof setTimeout>>();

useEffect(() => {
  if (!tokenExpiresAt || !onTokenExpiring) return;
  const now = Math.floor(Date.now() / 1000);
  const refreshIn = tokenExpiresAt - now - 30; // 30 s before expiry
  if (refreshIn <= 0) {
    // Token already nearly expired — refresh immediately
    onTokenExpiring()
      .then((newToken) => { tokenRef.current = newToken; })
      .catch(() => {
        onError?.({ code: "TOKEN_REFRESH_FAILED", message: "Playback session could not be renewed." });
      });
    return;
  }

  refreshTimerRef.current = setTimeout(async () => {
    try {
      const newToken = await onTokenExpiring();
      tokenRef.current = newToken;
    } catch {
      onError?.({ code: "TOKEN_REFRESH_FAILED", message: "Playback session could not be renewed." });
    }
  }, refreshIn * 1000);

  return () => {
    if (refreshTimerRef.current) clearTimeout(refreshTimerRef.current);
  };
}, [tokenExpiresAt, onTokenExpiring, onError]);
```

### 4.4 Parent integration (`VideoPlayerPage`)

```typescript
// frontend/src/pages/videos/VideoPlayerPage.tsx

const handleTokenExpiring = useCallback(async (): Promise<string> => {
  // Re-fetch the video detail to get a fresh playback_token
  const fresh = await queryClient.fetchQuery({
    queryKey: ["video", videoId],
    queryFn: () => getVideoDetail(videoId!),
  });
  return fresh.playback_token ?? "";
}, [videoId, queryClient]);

// Derive tokenExpiresAt from the JWT `exp` claim
const tokenExpiresAt = useMemo(() => {
  if (!video?.playback_token) return undefined;
  try {
    const payload = JSON.parse(atob(video.playback_token.split(".")[1]!));
    return typeof payload.exp === "number" ? payload.exp : undefined;
  } catch {
    return undefined;
  }
}, [video?.playback_token]);

// In JSX:
<MediaPlayer
  src={playbackUrl}
  mode="vod"
  autoplay
  poster={video.thumbnail_url ?? undefined}
  title={video.title}
  onError={handleMediaError}
  onTokenExpiring={handleTokenExpiring}
  tokenExpiresAt={tokenExpiresAt}
  subtitleTracks={...}
/>
```

### 4.5 Dev/prod parity (SECOPS-007)

The token refresh path is exercised whenever `tokenExpiresAt` is provided and `onTokenExpiring` is non-null. In dev mode, playback tokens may have a very long TTL or no `exp` claim; the `useMemo` returns `undefined` and the timer is never scheduled — dev behaviour is unchanged. In production, tokens have real expiry and the refresh fires proactively. The same component code runs in both environments; no dev-specific branches are introduced.

### 4.6 Backward compatibility

`onTokenExpiring` and `tokenExpiresAt` are optional props. All existing callers that pass neither continue to work exactly as before. The `xhrSetup` change is additive — it only activates when `tokenRef.current` is non-null (i.e., when the `src` URL contains a `token=` query parameter).

### Regression test (Vitest)

```typescript
// frontend/src/components/shared/__tests__/MediaPlayer.tokenRefresh.test.tsx

import { render, act } from "@testing-library/react";
import { MediaPlayer } from "../MediaPlayer";

jest.useFakeTimers();

describe("MediaPlayer token refresh", () => {
  it("calls onTokenExpiring 30 seconds before tokenExpiresAt", async () => {
    const now = Math.floor(Date.now() / 1000);
    const expiresAt = now + 120; // 2 minutes from now
    const onTokenExpiring = jest.fn().mockResolvedValue("new-token-xyz");

    render(
      <MediaPlayer
        src="https://cdn.example.com/stream.m3u8?token=old-token"
        tokenExpiresAt={expiresAt}
        onTokenExpiring={onTokenExpiring}
      />
    );

    // Before 90s elapses (120 - 30), callback should NOT be called
    act(() => { jest.advanceTimersByTime(89_000); });
    expect(onTokenExpiring).not.toHaveBeenCalled();

    // At 90s, callback fires (120s - 30s buffer = 90s)
    await act(async () => { jest.advanceTimersByTime(1_500); });
    expect(onTokenExpiring).toHaveBeenCalledTimes(1);
  });

  it("calls onTokenExpiring immediately when token is already near expiry", async () => {
    const now = Math.floor(Date.now() / 1000);
    const expiresAt = now + 10; // only 10 s remaining (< 30 s buffer)
    const onTokenExpiring = jest.fn().mockResolvedValue("new-token-abc");

    render(
      <MediaPlayer
        src="https://cdn.example.com/stream.m3u8?token=near-expired"
        tokenExpiresAt={expiresAt}
        onTokenExpiring={onTokenExpiring}
      />
    );

    await act(async () => { jest.advanceTimersByTime(100); });
    expect(onTokenExpiring).toHaveBeenCalledTimes(1);
  });

  it("does not schedule a timer when neither prop is provided", () => {
    const setTimeoutSpy = jest.spyOn(global, "setTimeout");
    render(<MediaPlayer src="https://cdn.example.com/stream.m3u8" />);
    // No refresh-related setTimeout beyond the controls-hide timer
    const refreshCalls = setTimeoutSpy.mock.calls.filter(
      ([, delay]) => typeof delay === "number" && delay > 3_000
    );
    expect(refreshCalls).toHaveLength(0);
  });
});
```

**Fails-before:** `test_calls_onTokenExpiring_30_seconds_before` — the callback is never called because no timer is scheduled.
**Passes-after:** Callback fires at the correct time.

### Rollout

- **Effort:** S (small — new props + one `useEffect` + one `useRef`; parent integration in `VideoPlayerPage` is also small)
- **Risk:** LOW for existing callers (both new props are optional). MEDIUM for new callers until the `xhrSetup` token injection is validated against the CDN configuration (header vs query-param auth).
- **Sequencing:** (1) Implement `onTokenExpiring` + `tokenExpiresAt` props and timer in `MediaPlayer`; (2) Add `xhrSetup` token injection; (3) Update `VideoPlayerPage` to pass both props; (4) Test with a short-TTL token in staging
- **Rollback:** Remove the two new props from `VideoPlayerPage`; `MediaPlayer` defaults gracefully to no-op when props are absent
- **Dependencies:** Requires backend to include `playback_token` with an `exp` JWT claim, or a separate `token_expires_at` field in `VideoDetail`. Currently `VideoDetail` has `playback_token?: string | null` (`api/endpoints/videos.ts:85`) but no expiry field. The backend must be extended to return `playback_token_expires_at: int` alongside `playback_token` in the video detail response.
