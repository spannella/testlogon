# GAP-0191: No user opt-out preference for cart reminders — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code in `app/routers/shoppingcart.py`,
> `app/services/shoppingcart.py`, and `app/core/settings.py`.

## 1. Summary & Classification

**Bug / Gap**: The cart abandonment reminder pipeline (`send_cart_reminder`) sends in-app
alerts and emails to every eligible user regardless of whether the user has opted out of
marketing communications. There is no `OPTOUT` storage record, no `is_user_opted_out()`
function, and no `GET /ui/shoppingcart/reminders/preferences` or
`PUT /ui/shoppingcart/reminders/preferences` endpoint.

**Claim verdict**: Confirmed. A search of `app/routers/shoppingcart.py` and
`app/services/shoppingcart.py` finds no references to `OPTOUT`, `opt_out`, `preferences`,
or any reminder-suppression logic keyed on user preference.

**Severity**: HIGH — FIN-003 source ticket.
**Status**: Open.
**Owning area**: E-commerce / Cart & Notifications.
**Impact**: Users who wish not to receive cart-reminder emails or in-app nudges cannot
opt out. In regulated markets (CAN-SPAM, GDPR, CASL) failure to honour a
do-not-contact preference is a compliance violation and can result in fines. Operationally,
every call to `send_cart_reminder` blindly triggers `send_alert_email`
(`app/services/shoppingcart.py:828`) and `write_alert`
(`app/services/shoppingcart.py:811`) for opted-out users.

**Related tickets**: GAP-0189 (multi-stage reminder schedule not implemented),
GAP-0190 (recovery links missing), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (root cause)

### Code path today

Background loop (`app/routers/shoppingcart.py:266–290`):

```python
async def _cart_abandonment_loop() -> None:
    ...
    carts = scan_abandoned_carts(threshold_hours=S.cart_abandonment_threshold_hours)
    for cart in carts:
        try:
            send_cart_reminder(cart)
        except Exception:
            logger.warning("cart_reminder_failed", ...)
```

Admin-triggered sweep (`app/routers/shoppingcart.py:213–246`) follows the identical path.
Both paths converge in `send_cart_reminder` at
`app/services/shoppingcart.py:781–846`:

```python
def send_cart_reminder(cart: Dict[str, Any], *, now: Optional[int] = None) -> None:
    user_sub = cart["PK"].replace("USER#", "")
    ...
    write_alert(user_sub, event="cart.abandoned", ...)      # line 811
    ...
    if email:
        send_alert_email([email], subject="You left items in your cart", ...)  # line 828
    T.shopping_cart.update_item(...)  # line 838 — marks reminder sent
```

There is **no opt-out check** between the eligibility filter
(`scan_abandoned_carts`, `app/services/shoppingcart.py:735–778`) and the reminder
dispatch. `scan_abandoned_carts` filters only on `status == "OPEN"`,
`last_activity_at < cutoff`, `reminder_count < max_reminders`, and cooldown window.
It never queries an opt-out preference.

### What is present vs missing

| Component | Present | Missing |
|-----------|---------|---------|
| Cart abandonment scan | Yes (`scan_abandoned_carts`, line 735) | — |
| Background reminder loop | Yes (line 266) | — |
| Opt-out DDB row (`OPTOUT/USER#<sub>`) | No | Needed in `cart_reminder_config` table (or `shopping_cart` table) |
| `is_user_opted_out(user_sub)` | No | Needed in `app/services/shoppingcart.py` |
| `GET /ui/shoppingcart/reminders/preferences` | No | Needed in `app/routers/shoppingcart.py` |
| `PUT /ui/shoppingcart/reminders/preferences` | No | Needed in `app/routers/shoppingcart.py` |
| Opt-out guard in `send_cart_reminder` | No | Needed at start of function body |

### Settings involved

`app/core/settings.py:780–785` defines `cart_abandonment_enabled`,
`cart_abandonment_max_reminders`, `cart_abandonment_reminder_cooldown_hours`, etc.
None of these control per-user preference; they are platform-wide knobs.

The scan interval (`CART_ABANDONMENT_SCAN_INTERVAL_SEC`, default 300 seconds) means
that in a production deployment with many users, a user who opted out at T+0 could
still receive a reminder as late as T+300 seconds if the scan had already fired and
`send_cart_reminder` is in mid-flight. The fix prevents the reminder from being sent
even if the cart was already selected by the scan, because the opt-out check is inside
`send_cart_reminder` itself (after the race guard but before any side effects).

### Dev vs prod behaviour

The background loop is registered unconditionally when `S.cart_abandonment_enabled == True`
(default `"1"` in `.env.local.example`). There is no difference between dev and prod in
whether the opt-out check is missing; both paths are broken identically.

### Interaction with `email_alerts_enabled` preference

The platform has a broader `send_alert_email` function in `app/services/alerts.py`.
If a separate global email-alerts opt-out preference is added elsewhere, the cart
reminder opt-out is orthogonal: a user may want account-security emails but not
marketing cart-reminder emails. The cart-specific `REMINDER_PREFS` row allows
granular control without coupling to whatever global email preference system exists
or may be introduced.

## 3. Impact / Exploit / Blast Radius

**Compliance blast radius**: Every opted-out user with an abandoned cart in any environment
where `CART_ABANDONMENT_ENABLED=1` receives unsolicited email on each sweep
(background loop fires every `CART_ABANDONMENT_SCAN_INTERVAL_SEC` seconds, default 300,
up to `CART_ABANDONMENT_MAX_REMINDERS` times, default 2, with
`CART_ABANDONMENT_REMINDER_COOLDOWN_HOURS` between bursts, default 48 hours).

In production this means a user who has clicked "unsubscribe" or invoked any other
opt-out mechanism will still receive up to 2 reminder emails per abandoned cart.
Under GDPR Article 21 / CAN-SPAM §5, a single non-honoured opt-out after written
request is actionable. Aggregate fines for bulk violations can reach €20 M or 4 % of
global annual turnover.

**User experience blast radius**: Users who have no opted-out but set a low reminder
frequency expectation also have no self-service control — there is no UI to disable
reminders at all, so aggressive power-users cannot reduce noise.

**No authentication bypass or financial exploit** is implied by this gap.

## 4. Fix Design (code-level)

### 4.1 DynamoDB table selection

Use the existing `shopping_cart` table to store opt-out rows rather than a new table.
This avoids a new `TableDef` in `scripts/local-ddb-init.py` and keeps cart data
co-located. The row shape:

```
PK = "USER#<user_sub>"
SK = "REMINDER_PREFS"
opted_out: bool  (stored as 1/0 number for GSI compatibility)
updated_at: int  (Unix timestamp)
```

No GSI is required; lookups are always by exact `(PK, SK)`.

If the project decides a separate `cart_reminder_config` table is warranted (for
forward-compat with multi-cart-type preferences), a `TableDef` entry should be added
to `scripts/local-ddb-init.py` with `pk` as hash key and no sort key.

### 4.2 Service layer (`app/services/shoppingcart.py`)

Add after the existing imports (around line 30):

```python
def is_user_opted_out(user_sub: str) -> bool:
    """Return True if the user has opted out of cart abandonment reminders."""
    resp = T.shopping_cart.get_item(
        Key={"PK": f"USER#{user_sub}", "SK": "REMINDER_PREFS"}
    )
    item = resp.get("Item")
    if not item:
        return False
    return bool(int(item.get("opted_out", 0)))


def set_reminder_preference(user_sub: str, opted_out: bool) -> Dict[str, Any]:
    """Write or update the user's reminder opt-out preference."""
    ts = int(datetime.now(timezone.utc).timestamp())
    T.shopping_cart.put_item(Item={
        "PK": f"USER#{user_sub}",
        "SK": "REMINDER_PREFS",
        "opted_out": 1 if opted_out else 0,
        "updated_at": ts,
    })
    return {"opted_out": opted_out, "updated_at": ts}


def get_reminder_preference(user_sub: str) -> Dict[str, Any]:
    """Return current reminder preference; defaults to opted_in (False)."""
    resp = T.shopping_cart.get_item(
        Key={"PK": f"USER#{user_sub}", "SK": "REMINDER_PREFS"}
    )
    item = resp.get("Item")
    if not item:
        return {"opted_out": False, "updated_at": None}
    return {
        "opted_out": bool(int(item.get("opted_out", 0))),
        "updated_at": int(item.get("updated_at", 0)) or None,
    }
```

Modify `send_cart_reminder` (`app/services/shoppingcart.py:781`) to add an early-exit
guard immediately after the race guard (after line 798):

```python
    # GAP-0191: respect user opt-out preference
    if is_user_opted_out(user_sub):
        return
```

### 4.3 Router layer (`app/routers/shoppingcart.py`)

Add two endpoints and update imports. Add to the imports from `app.services.shoppingcart`:
`get_reminder_preference`, `set_reminder_preference`.

Add these endpoints (after the `ui_cart_abandonment_status` endpoint, around line 261):

```python
class ReminderPreferenceIn(BaseModel):
    opted_out: bool


@router.get("/reminders/preferences")
async def ui_get_reminder_preference(ctx=Depends(require_ui_session)):
    """Get the authenticated user's cart reminder opt-out preference."""
    return get_reminder_preference(ctx["user_sub"])


@router.put("/reminders/preferences")
async def ui_set_reminder_preference(
    body: ReminderPreferenceIn,
    req: Request = None,
    ctx=Depends(require_ui_session),
):
    """Set cart reminder opt-out preference for the authenticated user."""
    result = set_reminder_preference(ctx["user_sub"], body.opted_out)
    audit_event(
        "cart_reminder_preference_updated",
        ctx["user_sub"],
        req,
        outcome="success",
        opted_out=body.opted_out,
    )
    return result
```

`ReminderPreferenceIn` is a small inline model; if the project prefers it in
`app/models.py` it can be moved there alongside `ShoppingCartItemIn`.

### 4.4 Dev/prod parity (SECOPS-007)

The `shopping_cart` table is backed by DynamoDB Local in dev (port 8001) and real
DynamoDB in prod. The `T.shopping_cart` handle from `app/core/tables.py` resolves
the correct endpoint from `S.ddb_endpoint_url` automatically. No special dev/prod
branching is required for this feature: the same service code runs in both
environments without mock. The `cart_abandonment_enabled` flag wraps the background
loop; disabling it in dev does not affect unit tests because they inject `now`
deterministically and call `send_cart_reminder` directly.

### 4.5 Model additions (`app/models.py`)

```python
class ReminderPreferenceOut(BaseModel):
    opted_out: bool
    updated_at: Optional[int] = None
```

Update router imports accordingly.

### 4.6 Alternatives considered

- **Separate `cart_reminder_config` table**: Cleaner isolation but adds a new table
  definition; ruled out to minimise DDB schema churn for this M-effort ticket.
- **Global `opted_out` in user profile table**: Conflates cart-reminder preference
  with broader notification preferences; ruled out.

### Playwright E2E (new tests to add in `frontend/e2e/shoppingcart.spec.ts`)

Two new cases:
1. `GET /ui/shoppingcart/reminders/preferences` returns `{ opted_out: false }` for a
   fresh session (no row).
2. `PUT /ui/shoppingcart/reminders/preferences` with `{ opted_out: true }` → 200, then
   the subsequent `GET` reflects the new value.

### Manual QA steps

1. Start dev stack (`just up`).
2. Add an item to a cart as Alice and abandon it (don't purchase).
3. Call `PUT /ui/shoppingcart/reminders/preferences` with `{ "opted_out": true }` for
   Alice using the dev CSRF token.
4. Trigger an admin sweep: `POST /ui/shoppingcart/admin/cart-abandonment/scan`.
5. Confirm Alice receives **zero** in-app alerts (check `/ui/alerts`).
6. Revert opt-out (`opted_out: false`) and re-run sweep; confirm Alice now receives
   the alert.

### Observability / metrics

Add a counter metric in `send_cart_reminder` for the skip case:
`metrics.increment("cart.reminder.skipped_opt_out")`. This allows monitoring
compliance over time and demonstrating to auditors that opt-outs are being honoured.

Suggested log line in the skip path:
```python
logger.info(
    "cart_reminder_skipped_opt_out",
    extra={"user_sub": user_sub, "cart_id": cart_id},
)
```

The `GET /ui/shoppingcart/reminders/preferences` and `PUT` endpoints should also
emit `audit_event("cart_reminder_preference_updated", ...)` entries that appear in
the alerts/audit stream, giving compliance teams a self-service record of when each
user changed their preference and from which IP address.

### Frontend

A small UI component in the shop or account-settings area should expose the toggle:
"Receive cart abandonment reminders: [Yes] / [No]". The component calls
`GET /ui/shoppingcart/reminders/preferences` on mount and `PUT` on change, following
the same React Query pattern as other preference pages (React Hook Form + `useMutation`).
This is not required for the backend fix to be useful (API clients can call the
endpoint directly) but should be included in the same sprint to ensure the feature
is user-accessible.

### Rollout

- **Effort**: M (2–3 days backend + test; 1 day frontend toggle in settings page).
- **Migration**: No data migration; absence of `REMINDER_PREFS` row = opted in
  (default), so existing users are unaffected.
- **Rollback**: Remove the `is_user_opted_out` call in `send_cart_reminder`; endpoints
  can remain without risk.
- **Risk**: LOW — the guard is additive and only fires when the new DDB row exists.
- **Sequencing**: Should be shipped before or alongside GAP-0189 (multi-stage reminder
  schedule), as that ticket increases reminder frequency and amplifies the compliance
  risk of this gap.
