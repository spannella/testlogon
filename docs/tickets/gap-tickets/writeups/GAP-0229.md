# GAP-0229: VNC Password / SSH Password Not Stored (SEC-022 Surface) — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/services/connection_profiles.py` and `app/core/crypto.py`.

## 1. Summary & Classification

**Plain-English statement**: The Connection Profiles service (`app/services/connection_profiles.py`, INFRA-006) supports `auth_method: "password"` as a valid value for both SSH and VNC profiles. However, there is no `vnc_password` or `ssh_password` field anywhere in the data model, the `create_profile` function, the `update_profile` function, the DynamoDB item structure, or the `_item_to_profile` serializer. A user can declare password-based authentication as their connection method but cannot store the actual password. Additionally, any future implementation that did store a password would expose it in the `_item_to_profile` return value, violating the SEC-022 principle (credentials must be encrypted at rest with KMS and never returned as plaintext via API).

- **Severity**: HIGH
- **Source ticket**: INFRA-006
- **Status**: Open
- **Owning area**: Remote Compute / Connection Profiles / Security
- **Verdict**: Claim **confirmed**. The `_VALID_AUTH_METHODS` set at `app/services/connection_profiles.py:50` includes `"password"`, but `create_profile` (lines 171-285), `update_profile` (lines 313-444), and `_item_to_profile` (lines 135-157) have no `vnc_password`, `ssh_password`, `password`, or `has_password` field at any point. The `app/core/crypto.py:kms_encrypt` function exists and is used elsewhere in the codebase; it is not imported or used in `connection_profiles.py`.
- **One-line impact**: Password authentication profiles are declared but non-functional; any real passwords stored in a naive future fix would be exposed as plaintext in API responses.
- **Related tickets**: SEC-022 (credential-at-rest encryption standard), INFRA-006, GAP-0035 (CSRF on template mutation endpoints as a point of reference for the pattern of fixing incomplete auth flows).

## 2. Current-State Investigation (root cause)

### Current data model

`_item_to_profile` at `app/services/connection_profiles.py:135-157` returns:

```python
{
    "profile_id": ...,
    "label": ...,
    "protocol": ...,  # "ssh" or "vnc"
    "hostname": ...,
    "auth_method": ...,  # one of: "key", "key_ref", "password"
    "ssh_key_id": ...,
    # No vnc_password, ssh_password, password, or has_password field
    ...
}
```

The `create_profile` signature (lines 171-188) has no `password` or `vnc_password` parameter. The stored DDB item (lines 256-279) similarly has no password field.

### Auth method validation

`_VALID_AUTH_METHODS = {"key", "key_ref", "password"}` at line 50. The `create_profile` function validates `auth_method` against this set at line 201-203 and stores it. There is no conditional branch that, when `auth_method == "password"`, validates that a password was supplied or stores it.

### KMS infrastructure

`app/core/crypto.py` provides:

```python
def kms_encrypt(plaintext: str) -> str:
    if not S.kms_key_id:
        raise RuntimeError("KMS_KEY_ID not set")
    r = kms.encrypt(KeyId=S.kms_key_id, Plaintext=plaintext.encode("utf-8"))
    return base64.b64encode(r["CiphertextBlob"]).decode("ascii")

def kms_decrypt(ct_b64: str) -> bytes:
    ct = base64.b64decode(ct_b64)
    r = kms.decrypt(CiphertextBlob=ct)
    return r["Plaintext"]
```

The KMS client (`app/core/aws.py:kms`) is wired to the mock KMS server at `http://localhost:7999` in dev mode (via `S.kms_endpoint_url` → `KMS_ENDPOINT_URL` env var, which is set by `scripts/mock_kms_server.py`). The same code path works against AWS KMS in production. This infrastructure is already exercised by other features (e.g., `filemgr_sftp_credentials`).

### SEC-022 pattern

SEC-022 mandates: credentials must be KMS-encrypted before storage; plaintext must never be returned in API responses; a `has_password: bool` flag is used to indicate whether a credential is stored without revealing it. This pattern is already implemented in at least two places in the codebase:
- `app/core/settings.py:filemgr_mount_secret_kms_key_id` — SFTP credential encryption.
- The general crypto module itself demonstrates the encrypt/decrypt pattern.

### Why it is broken

The feature was scaffolded: `"password"` was added to `_VALID_AUTH_METHODS` and the `auth_method` field was stored. But the actual password storage and encryption implementation was never added. This is an incomplete feature rather than a regression.

## 3. Impact / Exploit / Blast Radius

**Functional impact**:
- A user who creates a profile with `auth_method: "password"` has no mechanism to store or later retrieve the password. Quick connect (`quick_connect` function) returns `auth_method: "password"` in the descriptor but no password field — the terminal client would need to prompt the user for a password at connection time, defeating the purpose of a "quick connect" profile.

**Security impact (forward-looking)**:
- If a developer adds a naive password field to `_item_to_profile` without KMS encryption, passwords will be stored in plaintext in DynamoDB and returned in API JSON responses. Both are SEC-022 violations.
- DynamoDB backups (Point-in-Time Recovery) and DynamoDB Streams export — if enabled — would contain plaintext passwords.
- API responses containing plaintext passwords would appear in application logs, browser developer tools, and any monitoring/APM tool that captures HTTP response bodies.

**Blast radius**: Currently limited to users who selected `auth_method: "password"` (their profiles are non-functional but no data is leaked because no password is stored). The risk materializes when the missing implementation is added without the KMS guard.

## 4. Fix Design (code-level)

### Principle

Follow the SEC-022 pattern exactly:
1. Accept optional `vnc_password` / `ssh_password` on create and update.
2. KMS-encrypt before writing to DynamoDB as `password_enc`.
3. Never return the plaintext or ciphertext in `_item_to_profile`.
4. Return `has_password: bool` only.
5. Quick connect resolves the password (KMS-decrypt) for the terminal layer, but does NOT include it in the HTTP response body.

### Change 1: `app/services/connection_profiles.py`

**At the top, add the import:**

```python
from app.core.crypto import kms_encrypt, kms_decrypt
```

**Extend `_item_to_profile` to include `has_password`:**

```python
def _item_to_profile(item: Dict[str, Any]) -> Dict[str, Any]:
    return {
        ...existing fields...,
        "has_password": bool(item.get("password_enc", "")),
        # password_enc is NEVER included in the returned dict
    }
```

**Extend `create_profile` signature and body:**

```python
def create_profile(
    user_sub: str,
    *,
    ...,
    auth_method: str = "key_ref",
    vnc_password: str = "",
    ssh_password: str = "",
    ...
) -> Dict[str, Any]:
    ...
    # Determine which password applies
    raw_password = ""
    if auth_method == "password":
        if protocol == "vnc" and vnc_password:
            raw_password = vnc_password
        elif protocol == "ssh" and ssh_password:
            raw_password = ssh_password
        elif vnc_password:
            raw_password = vnc_password
        elif ssh_password:
            raw_password = ssh_password

    password_enc = ""
    if raw_password:
        if len(raw_password) > 256:
            raise ProfileValidationError("password too long (max 256 characters)")
        password_enc = kms_encrypt(raw_password)

    item = {
        ...existing fields...,
        "password_enc": password_enc,
    }
    T.connection_profiles.put_item(Item=item)
    ...
```

**Extend `update_profile` to support password rotation:**

```python
def update_profile(
    user_sub: str,
    profile_id: str,
    *,
    ...,
    password: Optional[str] = None,
    clear_password: bool = False,
    ...
) -> Dict[str, Any]:
    ...
    if clear_password:
        sets.append("password_enc = :pe")
        values[":pe"] = ""
    elif password is not None:
        if len(password) > 256:
            raise ProfileValidationError("password too long")
        sets.append("password_enc = :pe")
        values[":pe"] = kms_encrypt(password)
    ...
```

**Extend `quick_connect` to decrypt and pass through (NOT in the HTTP response):**

```python
def quick_connect(user_sub: str, profile_id: str) -> Dict[str, Any]:
    ...
    # Resolve password for the terminal layer (internal use only)
    password_resolved = ""
    password_enc = item.get("password_enc", "")
    if password_enc and profile["auth_method"] == "password":
        try:
            password_resolved = kms_decrypt(password_enc).decode("utf-8")
        except Exception:
            logger.exception(
                "connection_profiles.password_decrypt_failed profile_id=%s",
                profile_id,
            )
            raise ProfileValidationError("Failed to decrypt stored password")

    return {
        ...existing fields...,
        # password_resolved is returned for the internal terminal layer only.
        # The router must strip this before sending to the client,
        # or pass it directly to the WebSocket session handler.
        "password_resolved": password_resolved,
        "has_password": bool(password_enc),
    }
```

The router (`app/routers/connection_profiles.py`) must not include `password_resolved` in the HTTP response model. It should be extracted and passed to the SSH/VNC session initiator in-process only.

### Change 2: Pydantic models (`app/models.py`)

Add `has_password: bool = False` to `ConnectionProfileOut`. Do NOT add `password_enc` or `password_resolved`. Add optional `vnc_password: Optional[str] = None` and `ssh_password: Optional[str] = None` to `ConnectionProfileCreateIn`.

### Dev/Prod parity (SECOPS-007)

- **Dev mode**: `S.kms_key_id` is set to a mock key ID by `scripts/mock_kms_server.py` and written to `.env.local`. The `kms_client()` in `app/core/aws_clients.py` uses `S.kms_endpoint_url` (defaults to `http://localhost:7999`). `kms_encrypt` and `kms_decrypt` therefore work identically in dev using the mock KMS server.
- **Prod mode**: `S.kms_key_id` points to an AWS KMS CMK. Same code path; no environment branching needed.
- **Guard against missing `KMS_KEY_ID`**: `kms_encrypt` already raises `RuntimeError("KMS_KEY_ID not set")` if `S.kms_key_id` is empty. This surfaces clearly as a 500 rather than silently storing plaintext. An additional validation guard in `create_profile` could check `if auth_method == "password" and raw_password and not S.kms_key_id: raise ProfileValidationError("Password auth requires KMS to be configured")` — this gives a 400 rather than 500 and is more user-friendly.
- **Backward compatibility**: Existing profiles with `auth_method: "password"` have no `password_enc` field. `_item_to_profile` will return `has_password: False` for them, which is accurate (no password was ever stored).

## 5. Testing, Verification & Rollout

### Regression test (fails-before / passes-after)

```python
# tests/test_connection_profiles.py (add these tests)

import pytest
from app.services import connection_profiles as svc


def test_create_profile_password_kms_encrypted(monkeypatch, ddb):
    """GAP-0229: password must be KMS-encrypted before storage."""
    encrypted_values = []

    def fake_kms_encrypt(plaintext: str) -> str:
        encrypted_values.append(plaintext)
        return f"ENC({plaintext})"  # deterministic fake

    monkeypatch.setattr("app.services.connection_profiles.kms_encrypt", fake_kms_encrypt)

    profile = svc.create_profile(
        "alice",
        label="My VNC",
        protocol="vnc",
        hostname="192.168.1.1",
        port=5900,
        auth_method="password",
        vnc_password="s3cr3t",
    )

    # Before fix: encrypted_values == [] and profile has no has_password field
    # After fix:
    assert "s3cr3t" in encrypted_values, "kms_encrypt must be called with the plaintext"
    assert profile.get("has_password") is True, "has_password must be True"
    # The plaintext must NOT appear in the returned profile dict
    assert "s3cr3t" not in str(profile), "plaintext password must not appear in profile output"
    assert "password_enc" not in profile, "encrypted blob must not appear in profile output"


def test_item_to_profile_never_exposes_password_enc(ddb):
    """GAP-0229: _item_to_profile must expose has_password but never password_enc."""
    item = {
        "user_sub": "alice", "profile_id": "cp_test",
        "sk": "PROFILE#cp_test", "label": "Test",
        "protocol": "ssh", "hostname": "example.com",
        "auth_method": "password", "password_enc": "SOME_CIPHERTEXT",
        "port": 22, "username": "alice",
        "created_at": 1000000, "updated_at": 1000000, "last_used_at": 0,
    }
    out = svc._item_to_profile(item)
    assert "password_enc" not in out, "password_enc must be scrubbed from output"
    assert "SOME_CIPHERTEXT" not in str(out), "ciphertext must not appear in output"
    assert out.get("has_password") is True


def test_create_profile_password_auth_method_no_password_is_allowed(ddb):
    """Creating a password-auth profile without providing a password should succeed (deferred entry)."""
    profile = svc.create_profile(
        "alice",
        label="My SSH no-pw",
        protocol="ssh",
        hostname="10.0.0.1",
        port=22,
        auth_method="password",
    )
    assert profile.get("has_password") is False
```

### Manual QA steps

1. `just restart`.
2. Navigate to Remote > Connection Profiles.
3. Create a new profile: protocol=VNC, hostname=192.168.1.1, auth_method=password, password=mypassword.
4. Verify the profile is saved and the UI shows "Password: stored" (or a lock icon), NOT the plaintext.
5. Open browser DevTools → Network, inspect the `POST /ui/connections` response body. Confirm that `password_enc` is absent and `has_password: true` is present.
6. Call `GET /ui/connections/{profile_id}` and verify the same: no plaintext, no ciphertext, only `has_password: true`.
7. DDB console: confirm the `password_enc` field contains a base64-encoded ciphertext, NOT the plaintext.

### Metrics / observability

- Add a counter `connection_profile_password_decrypt_error_total` for KMS decrypt failures in `quick_connect`.
- Log `connection_profiles.password_encrypted profile_id=%s` at DEBUG level on successful encrypt (do not log the plaintext or ciphertext).

### Rollout

- **Effort**: M (1-2 days: data model, service changes, router model update, tests)
- **Risk**: Medium (touches KMS calls which require the mock KMS server to be running in dev). The existing `kms_encrypt` function is proven; the risk is in the DynamoDB write path and the `_item_to_profile` scrubbing logic.
- **Sequencing**: Deploy alongside any other INFRA-006 fixes. No database migration needed for existing profiles (backward-compatible: missing `password_enc` → `has_password: False`).
- **Rollback**: Remove the `password_enc` write path and restore `_item_to_profile` to the version without `has_password`. Existing profiles are unaffected (no password was ever stored). Profiles created during the rollout window will silently lose their password on rollback — communicate this in the deploy runbook.
