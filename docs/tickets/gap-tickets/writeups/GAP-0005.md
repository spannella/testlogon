# GAP-0005: `elevate_feed_items()` Not Called from Newsfeed Router — Remediation Write-up

> Source ticket: ADS-012 · Severity: CRIT · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** `app/services/content_boost.py:elevate_feed_items()` (line 409) is a fully implemented feed re-ranking function that elevates actively-boosted posts above organic results by adding `BOOST_RANK_WEIGHT = 1000` to their effective score. The function is never called from `app/routers/newsfeed.py` or anywhere else in the codebase. Creators are charged when they create a boost — the charge fires, the boost record is stored — but the feed rank is unchanged. Every boost sold since the feature was deployed has had zero effect on content visibility.

**Verdict (from investigation):** Confirmed. A full codebase grep shows exactly one definition of `elevate_feed_items` (`content_boost.py:409`) and zero call sites. The `GET /feed` handler in `newsfeed.py:5133–5138` assembles `feed_items`, calls `_inject_sponsored_posts()` (ADS-005, which works), but never calls `elevate_feed_items()`.

**Severity and area.** Critical / Advertising & Monetisation / Creator Trust. This is both a billing integrity issue (creators charged for a non-functional service) and a product correctness issue (the boost feature is entirely inert). Every boost transaction is potentially subject to a refund demand.

**Related tickets.** ADS-012 (content boost feature), GAP-0058 (no content-ownership validation at boost creation), GAP-0059 (no duplicate active-boost guard). Both GAP-0058 and GAP-0059 should be addressed in the same release to ensure the boost system is correct end-to-end.

## 2. Current-State Investigation (root cause)

### The implemented but orphaned function: `content_boost.py:409–433`

```python
# app/services/content_boost.py:409–433
BOOST_RANK_WEIGHT = 1000  # line 46

def elevate_feed_items(
    items: list[dict[str, Any]],
    *,
    content_type: str = "post",
    id_key: str = "content_id",
    score_key: str = "score",
    now: int | None = None,
) -> list[dict[str, Any]]:
    """Re-rank a list of feed items, elevating actively-boosted content.

    Each item is expected to carry an id (``id_key``) and an organic ranking
    score (``score_key``, default 0). Boosted items get ``BOOST_RANK_WEIGHT``
    added and an ``is_boosted`` flag set. Returns a new list sorted by the
    effective score (highest first). Non-destructive: input items are copied.
    """
    out: list[dict[str, Any]] = []
    for it in items:
        copy = dict(it)
        base = int(copy.get(score_key, 0) or 0)
        bonus = boost_rank_bonus(content_type, str(copy.get(id_key, "")), now=now)
        copy["is_boosted"] = bonus > 0
        copy["effective_score"] = base + bonus
        out.append(copy)
    out.sort(key=lambda x: x["effective_score"], reverse=True)
    return out
```

The function is complete, documented, and correct. It calls `boost_rank_bonus()` at line 428, which in turn calls `active_boost_for_content()` at line 394 — a DynamoDB lookup that checks `T.content_boosts` for an active boost on the given content. The function returns a new, re-sorted list and adds `is_boosted` and `effective_score` to each item.

### The missing call site: `newsfeed.py:5133–5138`

```python
# app/routers/newsfeed.py:5133–5138
```

The handler correctly calls `_inject_sponsored_posts()` for ADS-005 paid placements, but the ADS-012 elevation step is absent. `feed_items` is returned to the client with no boost-based reranking applied.

### The `id_key` mismatch (critical sub-issue)

`elevate_feed_items` defaults to `id_key="content_id"`. However, newsfeed post dicts carry the ID as `"post_id"`, not `"content_id"`. If the function is called with the default `id_key`, `copy.get("content_id", "")` returns `""` for every post, `boost_rank_bonus()` looks up a boost for the empty string, finds none, and returns `0`. The function silently produces no elevation effect even after the fix is applied, unless `id_key="post_id"` is passed explicitly.

This sub-issue is confirmed by the investigation and must be addressed as part of the same fix.

## 3. Impact / Exploit / Blast Radius

### Creator billing impact

Every creator who has purchased a content boost has been charged for a service with zero effect. The charge flow (`POST /ui/content-boost`, `charge_impression` via `ad_billing.py`) fires correctly, but the corresponding feed elevation never happens. Affected creators can be identified by scanning `T.content_boosts` for any item with `status = "active"` or `status = "expired"` (all of them represent charges with no delivery).

If the platform has processed N boost purchases at an average price of $P each, the total potential refund liability is N × P — potentially significant depending on how long the feature has been deployed.

### Product impact

The boost feature as visible to creators in the UI is entirely non-functional. A creator who boosts a post with low organic visibility and then checks their analytics will see no change in impression count or feed position. Trust in the paid boost product is zero once creators notice.

### Feed response divergence

The `is_boosted` flag and `effective_score` field that `elevate_feed_items` sets on each post are absent from all `GET /feed` responses today. Any frontend code that conditionally renders a "Boosted" badge based on `is_boosted: true` will never display it. After the fix, `is_boosted: true` will appear on elevated posts, which the frontend must handle (the badge should already be implemented per ADS-012 scope, but verify).

## 4. Fix Design (code-level)

### The fix: one import + one function call in `newsfeed.py`

In `app/routers/newsfeed.py`, after the `_inject_sponsored_posts` call and before constructing the `out` dict, add:

```python
# app/routers/newsfeed.py — fix for GAP-0005
# Add import at the top of the file (or inline):
from app.services.content_boost import elevate_feed_items

# ...existing code...

        # ADS-005: Inject sponsored posts into the feed
        feed_items = ordered[:limit]
        if not author_filter:  # Only inject in the main feed, not author-filtered views
            feed_items = _inject_sponsored_posts(feed_items, user_id)
            # ADS-012: Elevate boosted posts in the feed
            feed_items = elevate_feed_items(
                feed_items,
                content_type="post",
                id_key="post_id",   # CRITICAL: newsfeed dicts use "post_id", not "content_id"
            )

        out = {"items": feed_items, "next_cursor": encode_cursor(next_eks)}
```

**Ordering rationale.** `elevate_feed_items` is placed after `_inject_sponsored_posts` so that sponsored posts (which have their own placement logic) are in the list before boost-based reranking is applied. Both operations affect the same `feed_items` list. Boost elevation respects organic scores; sponsored post injection uses a separate slot-insertion mechanism that does not compete with boost scores.

**`id_key="post_id"` is mandatory.** Without this argument, the default `id_key="content_id"` causes `copy.get("content_id", "")` to return `""` for all newsfeed posts, making `boost_rank_bonus()` look up a boost for an empty string ID and return `0` for all items. The function would appear to run successfully but would produce no reranking effect — an undetectable silent failure.

**Scope guard.** The `if not author_filter:` guard is already on `_inject_sponsored_posts`. The `elevate_feed_items` call is placed inside this guard for the same reason: boost elevation should only apply to the main feed, not author-filtered profile views (where reranking by boost could produce confusing ordering on a creator's own post list).

### Dev/Prod parity (SECOPS-007)

`elevate_feed_items` calls `active_boost_for_content()` which queries `T.content_boosts` (DynamoDB). In dev this is DynamoDB Local on port 8001; in production it is AWS DynamoDB. The code path is identical. No `DEV_MODE` branch exists in `content_boost.py`. No parity gap is introduced.

The `BOOST_RANK_WEIGHT = 1000` constant in `content_boost.py:46` applies in both environments. If the boost weight needs to be tunable per environment, it can be moved to a settings value; for now the constant is sufficient.

### Backward compatibility

`elevate_feed_items` is non-destructive (copies each item dict) and returns a new list. The existing `post_id`, `text`, `author`, and all other fields are preserved. Two new fields are added to each post in the response: `is_boosted: bool` and `effective_score: int`. Frontend clients that do not read these fields are unaffected. Clients that implement the "Boosted" badge (per ADS-012) will begin showing it.

No DynamoDB schema changes needed. No backward-incompatible API changes (additive only).

### Feed performance

Each call to `elevate_feed_items` performs one DynamoDB `get_item` per post via `active_boost_for_content()`. For a feed page of 20 posts this is 20 DynamoDB reads. At current traffic this is acceptable. A future optimisation is to batch these reads into a `batch_get_item` call — a separate performance ticket.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline — `tests/test_feed_boost_elevation.py`)

```python
import pytest
from unittest.mock import patch
from app.services.content_boost import elevate_feed_items, BOOST_RANK_WEIGHT


# --- Passes before AND after fix (unit test of the function itself) ---

def test_elevate_feed_items_raises_boosted_post():
    """Boosted post (p1) overtakes higher-organic post (p2) after elevation."""
    items = [
        {"post_id": "p1", "score": 5, "text": "low organic"},
        {"post_id": "p2", "score": 10, "text": "high organic"},
    ]

    def mock_bonus(content_type, content_id, now=None):
        return BOOST_RANK_WEIGHT if content_id == "p1" else 0

    with patch("app.services.content_boost.boost_rank_bonus", side_effect=mock_bonus):
        result = elevate_feed_items(items, id_key="post_id")

    assert result[0]["post_id"] == "p1"
    assert result[0]["is_boosted"] is True
    assert result[0]["effective_score"] == 5 + BOOST_RANK_WEIGHT
    assert result[1]["post_id"] == "p2"
    assert result[1]["is_boosted"] is False


def test_elevate_feed_items_id_key_mismatch_produces_no_elevation():
    """CRITICAL: default id_key='content_id' on newsfeed posts silently does nothing."""
    items = [{"post_id": "p1", "score": 5}]

    def mock_bonus(content_type, content_id, now=None):
        # Real boost exists for "p1"
        return BOOST_RANK_WEIGHT if content_id == "p1" else 0

    with patch("app.services.content_boost.boost_rank_bonus", side_effect=mock_bonus):
        # Wrong: default id_key="content_id"; no field named "content_id" in newsfeed posts
        result_wrong = elevate_feed_items(items)  # uses id_key="content_id"
        # Correct: explicitly pass id_key="post_id"
        result_correct = elevate_feed_items(items, id_key="post_id")

    assert result_wrong[0]["is_boosted"] is False     # silent failure with wrong id_key
    assert result_correct[0]["is_boosted"] is True    # correct with explicit id_key


# --- Fails BEFORE fix (integration-level: function not called from router) ---
# --- Passes AFTER fix ---

@pytest.mark.asyncio
async def test_get_feed_elevates_boosted_post(async_client, alice_session, seeded_boost):
    """After fix: GET /feed returns boosted post before higher-organic post."""
    # seeded_boost fixture creates an active boost for post_id="test_post_low"
    resp = await async_client.get(
        "/ui/newsfeed/feed",
        cookies=alice_session["cookies"],
    )
    assert resp.status_code == 200
    items = resp.json()["items"]
    post_ids = [i["post_id"] for i in items]
    boosted_idx = post_ids.index("test_post_low")
    organic_high_idx = post_ids.index("test_post_high")
    # Before fix: test_post_high appears before test_post_low (higher organic score)
    # After fix: test_post_low appears before test_post_high (boost elevation)
    assert boosted_idx < organic_high_idx, (
        "Boosted post should appear before higher-organic post"
    )
    # Verify is_boosted flag in response
    boosted_item = items[boosted_idx]
    assert boosted_item.get("is_boosted") is True
```

**Fails-before / passes-after contract:**
- `test_elevate_feed_items_raises_boosted_post` passes in both states (it tests the service function directly, which already works correctly).
- `test_elevate_feed_items_id_key_mismatch_produces_no_elevation` passes in both states (it documents the id_key pitfall for future contributors).
- `test_get_feed_elevates_boosted_post` fails before the fix (the router does not call `elevate_feed_items`; boost order is not applied) and passes after (the router calls it with `id_key="post_id"`).

### Observability

Add a metric `newsfeed_feed_elevated_posts_per_request` (histogram) tracking how many posts per feed page have `is_boosted: true`. A baseline of 0 before the fix rising to >0 after confirms correct wiring. Add a `boost_elevation_applied` structured log field to the existing feed query log at `newsfeed.py:5143`.

### Rollout & risks

- **Risk:** `active_boost_for_content()` adds N DynamoDB reads per feed page (one per post). With 20 posts per page at high QPS, this increases DynamoDB read unit consumption. Monitor read capacity and add a `batch_get_item` optimisation if needed.
- **Risk:** Frontend may not yet render `is_boosted: true` with a "Boosted" badge. Verify the ADS-012 frontend implementation in the same release; if absent, the backend-only fix is safe to ship — the field is additive and ignored by clients that don't read it.
- **Risk:** If `T.content_boosts` is empty (no boosts purchased), `active_boost_for_content()` returns `None` for all posts and the function returns the list in unchanged order with `is_boosted: false` for all items — identical to the pre-fix behaviour. No regression for feeds without active boosts.
- **Rollback:** Remove the `elevate_feed_items(...)` call from `newsfeed.py`. No data changes to roll back.
- **Effort:** S — one import and one function call in `newsfeed.py`, with `id_key="post_id"` being the only non-obvious detail.
- **Sequence:** Fix GAP-0058 (content-ownership validation at boost creation) and GAP-0059 (duplicate active-boost guard) in the same release to ensure the boost system is correct end-to-end before elevation takes effect in production.
