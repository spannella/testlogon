# WOV-001 — Work-order entity — model, table, flag, create + read service

**Type**: Feature | **Priority**: P1 | **Estimate**: 2d
**Source**: `docs/open-property/WORKORDERS_VENDORS_TICKETS.md` §WOV-001 + `docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §C

---

## 1. Summary & Goal

WOV-001 is the foundational ticket for the property-maintenance Work Order vertical. It delivers exactly four things: (1) the `maintenance_orders` DynamoDB table with two GSIs and correct `attr_types`, (2) the `MAINTENANCE_ORDERS_ENABLED` master feature flag with `_flag_on()` / `_require_enabled()`, (3) the Pydantic models `MaintenanceOrderIn` / `MaintenanceOrderOut` (plus `MaintenanceOrderTransitionIn` / `MaintenanceOrderAssignIn` stubs needed by WOV-002), and (4) the service functions `create_work_order`, `get_work_order`, and `_item_to_out` in the new module `app/services/maintenance_orders.py`.

No router is shipped in this ticket. WOV-002 adds the router alongside the lifecycle mutations. With `MAINTENANCE_ORDERS_ENABLED=false` (the default), the platform is byte-for-byte unchanged: no HTTP surface is exposed, no DynamoDB I/O occurs, and every service entry point returns HTTP 404.

WOV-001 is a property-scoped variant of the planned FXA-012 maintenance-work-order service (`docs/ofbiz/specs/FXA-012.md`): identical lifecycle/idempotency/audit machinery, but the table is keyed on `PROPERTY#{property_id}` rather than an asset FK, and three additive fields are present — `priority`, `unit_id`, and `vendor_id` — that open-property's gap analysis (`docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §C) identifies as missing from the existing `tickets.py` foundation.

## 2. Context & Current State

### 2.1 What exists today that WOV-001 reuses

**Ticket lifecycle dict** (`app/services/tickets.py:30–40`): `_STATUS_TRANSITIONS: dict[str, tuple[str, ...]]` maps each status to its legal successors. WOV-001 defines its own `VALID_TRANSITIONS: dict[str, set[str]]` as a module-level constant that mirrors this shape — a work-order is not a support ticket, so the two dicts remain independent. The _pattern_ (a pure-Python module-level constant + 409 guard) is reused; there is no import dependency.

**Board column pattern** (`app/services/tickets.py:61–70`): `_DEFAULT_BOARD_COLUMNS` is a tuple of `{column_id, title, status_key, order}` dicts consumed by `default_board_columns()`. WOV-005 (frontend Kanban) re-skins the work-order statuses using this exact display-only relabeling idiom — the same service-layer constant shape is used, keyed to `wo_status` strings. No import from `tickets.py` is needed; WOV-001 defines its own `_DEFAULT_WO_COLUMNS` tuple in `maintenance_orders.py`.

**Feature flag pattern** (`app/services/inventory.py:50–56`): The canonical `_flag_on()` / `_require_enabled()` template, with `_require_enabled()` raising `HTTPException(status_code=404, ...)`. The settings entry that drives it is at `app/core/settings.py:839`:
```python
inventory_reservations_enabled: bool = os.environ.get("INVENTORY_RESERVATIONS_ENABLED", "false").lower() == "true"
```
WOV-001 copies this pattern verbatim. Neither `maintenance_orders_enabled` nor `maintenance_orders_table_name` appears anywhere in the current `app/core/settings.py` or `app/core/tables.py`.

**Deterministic ID derivation** (`app/services/commerce_order_service.py:67`):
```python
order_id = hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]
```
WOV-001 uses the same derivation: `work_order_id = sha256(corr.encode()).hexdigest()[:32]`, where `corr = correlation_id or f"wo:{actor_sub}:{uuid4().hex}"`.

**Audit helper pattern** (`app/services/inventory.py:92–98`): A lazy-import `_audit()` wrapper that calls `app.services.alerts.audit_event` inside a bare `try/except`, guaranteeing that an audit failure never blocks a service mutation. Copied verbatim into `maintenance_orders.py`.

**Decimal coercion helper** (`app/services/inventory.py:67–73`): `_to_int(value, default=0)` coerces DynamoDB `Decimal` objects to `int`. Copied verbatim; used in `_item_to_out` for all numeric fields (`created_at`, `updated_at`, `scheduled_for`, `cost_cents`, `completed_at`).

**Cursor pagination** (`app/core/cursor.py:94, 103`): `encode_cursor` / `decode_cursor` for signed, version-tagged pagination over `LastEvaluatedKey`. Used by `list_work_orders` (WOV-002).

**Table handle wiring** (`app/core/tables.py:65–66`, `321–572`): `_safe_table(name)` wraps a `boto3` Table in a `_FloatSafeTable` proxy that coerces floats to Decimal on every write. All new table handles use this wrapper.

**`now_ts()`** (`app/core/time.py:2`): Returns `int(time.time())`.

### 2.2 What does NOT exist today

Running `grep -rn "maintenance_orders\|MAINTENANCE_ORDERS"` against `app/core/settings.py`, `app/core/tables.py`, and `scripts/local-ddb-init.py` returns nothing. The `maintenance_orders` table, `T.maintenance_orders` handle, `S.maintenance_orders_enabled` setting, and `app/services/maintenance_orders.py` module are all net-new introductions.

### 2.3 Relationship to PROP and FXA

PROP-001 (`docs/open-property/specs/PROP-001.md`) introduces the `properties` table with PK `property_id` / SK `"META"` and the `create_property` / `get_property` service. WOV-001 depends on PROP-001 being merged first, because `create_work_order` calls the PROP property service to validate that the `property_id` FK target exists before writing a work-order row. If PROP-001 is unbuilt, the property-existence check can be gated behind a `try/except ImportError` — WOV-001 still functions (with a weaker guard), but the dependency is explicit and documented.

FXA-012 (`docs/ofbiz/specs/FXA-012.md`) specifies a `maintenance_orders` table keyed on `ASSET#{asset_id}` / `WO#{work_order_id}`. WOV-001 re-keys this partition to `PROPERTY#{property_id}` for property-scoped co-location, adds `priority` + `unit_id` + `vendor_id`, and drops the asset FK. The two domains do not share a table; they share only the service idioms.

## 3. Data Model

### 3.1 DynamoDB table: `maintenance_orders`

Single-table DynamoDB. One row per work order; co-located by property for cheap per-property queue scans.

**Primary key**

| Key | Type | Value pattern |
|---|---|---|
| `pk` | S (PK) | `"PROPERTY#{property_id}"` |
| `sk` | S (SK) | `"WO#{work_order_id}"` |

**Item attributes**

| Attribute | DDB Type | Nullable | Notes |
|---|---|---|---|
| `pk` | S | No | `"PROPERTY#{property_id}"` |
| `sk` | S | No | `"WO#{work_order_id}"` |
| `work_order_id` | S | No | `sha256(corr.encode()).hexdigest()[:32]`; 32-char hex |
| `property_id` | S | No | Denormalized FK — target of PROP-001's `properties` table |
| `unit_id` | S | Yes | Optional FK to `UNIT#{unit_id}` row (PROP-002). Absent = property-level WO, not unit-specific |
| `vendor_id` | S | Yes | Optional FK to WOV-004 vendor (`supplier_id`). Set by WOV-002 `assign_work_order` |
| `assignee_sub` | S | Yes | Optional staff `user_sub`. `GSI_WO_ASSIGNEE` partition key (sparse GSI — absent rows are not indexed) |
| `title` | S | No | Short description; 1–200 chars |
| `description` | S | Yes | Full details; max 2000 chars |
| `priority` | S | No | `"urgent"` / `"high"` / `"normal"` / `"low"`. Default `"normal"` |
| `wo_status` | S | No | `"open"` / `"assigned"` / `"in_progress"` / `"completed"` / `"cancelled"`. `GSI_WO_STATUS` partition key |
| `scheduled_for` | N | Yes | Optional Unix timestamp for planned maintenance. Absent until set |
| `cost_cents` | N | Yes | Optional; recording-only (no GL write). Set by WOV-002 on `completed` transition. Absent until set |
| `created_at` | N | No | `now_ts()` — integer Unix seconds. GSI sort key for both GSIs |
| `updated_at` | N | No | `now_ts()` — set on every mutation |
| `completed_at` | N | Yes | `now_ts()` when `wo_status` advances to `"completed"`. Absent until completed |
| `correlation_id` | S | No | Stored idempotency key; value used to derive `work_order_id` |
| `actor_sub` | S | No | `user_sub` of the creating staff member |

**GSIs**

Both GSIs project `ALL` attributes.

| Index name | Partition key | Sort key | Use case |
|---|---|---|---|
| `GSI_WO_STATUS` | `wo_status` (S) | `created_at` (N) | System-wide status queue — drives Kanban columns in WOV-005; queries `wo_status = "open"` etc. newest-first |
| `GSI_WO_ASSIGNEE` | `assignee_sub` (S) | `created_at` (N) | Work orders by staff assignee — sparse; only rows with `assignee_sub` present are indexed |

**`attr_types` requirement**: both GSIs use `created_at` as the numeric sort key. Per the CLAUDE.md DynamoDB numeric GSI gotcha (and `scripts/local-ddb-init.py:34` comment), the `TableDef` must declare `attr_types={"created_at": "N"}`. Omitting it causes DynamoDB Local to store `created_at` as a String attribute, which produces `ValidationException` at runtime when querying either GSI with an integer `KeyConditionExpression`.

**`TableDef` entry** (to be appended in `scripts/local-ddb-init.py` inside `_table_defs()`, following the `reservations` and `returns` entries at `settings.py:841–847`):

```python
TableDef(
    _resolve_table_name(S.maintenance_orders_table_name, "maintenance_orders"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "GSI_WO_STATUS",   "partition_key": "wo_status",    "sort_key": "created_at"},
        {"index_name": "GSI_WO_ASSIGNEE", "partition_key": "assignee_sub", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

```python
WO_PRIORITIES: frozenset[str] = frozenset({"urgent", "high", "normal", "low"})
WO_STATUSES:   frozenset[str] = frozenset({"open", "assigned", "in_progress", "completed", "cancelled"})

# VALID_TRANSITIONS is defined here for WOV-002 to use; not used by WOV-001 service functions.
VALID_TRANSITIONS: dict[str, set[str]] = {
    "open":        {"assigned", "in_progress", "cancelled"},
    "assigned":    {"in_progress", "open", "cancelled"},
    "in_progress": {"completed", "cancelled"},
    "completed":   set(),
    "cancelled":   set(),
}

def _flag_on() -> bool: ...
def _require_enabled() -> None: ...    # raises HTTPException(404) when flag off
def _wo_pk(property_id: str) -> str: ...    # returns "PROPERTY#{property_id}"
def _wo_sk(work_order_id: str) -> str: ...  # returns "WO#{work_order_id}"
def _audit(event: str, user_sub: str, **fields: Any) -> None: ...    # best-effort
def _to_int(value: Any, default: int = 0) -> int: ...
def _item_to_out(item: dict) -> MaintenanceOrderOut: ...
def create_work_order(property_id: str, body: MaintenanceOrderIn, actor_sub: str) -> MaintenanceOrderOut: ...
def get_work_order(property_id: str, work_order_id: str) -> MaintenanceOrderOut | None: ...
```

**`_flag_on` / `_require_enabled`**: exact copy of `app/services/inventory.py:50–56`, substituting `"maintenance_orders_enabled"` and the 404 detail string `"Maintenance work orders are not enabled"`.

**`_wo_pk` / `_wo_sk`**: trivial key constructors; extracted to helpers so tests and WOV-002 reference them rather than embedding literal format strings.

**`_audit`**: verbatim copy of `app/services/inventory.py:92–98`.

**`_to_int`**: verbatim copy of `app/services/inventory.py:67–73`.

**`_item_to_out`**: reads a DynamoDB item dict and returns `MaintenanceOrderOut`. Calls `_to_int` on every numeric field (`created_at`, `updated_at`, `scheduled_for`, `cost_cents`, `completed_at`). Uses `.get(field)` with appropriate defaults.

**`create_work_order(property_id, body, actor_sub) -> MaintenanceOrderOut`**:

1. `_require_enabled()` — raises 404 if flag off; no DDB I/O.
2. Validate `body.priority in WO_PRIORITIES`; raise `HTTPException(422, detail="invalid_priority")` otherwise.
3. Validate that `property_id` exists: lazy-import `app.services.property_mgmt.get_property`; if it returns `None`, raise `HTTPException(404, detail="property_not_found")`. If `property_mgmt` is not yet importable (WOV-001 may land before PROP-001 in some builds), catch `ImportError` and skip the check — the missing guard is logged at `WARNING` level but does not block WOV-001.
4. Derive `corr = body.correlation_id or f"wo:{actor_sub}:{uuid4().hex}"`.
5. Derive `work_order_id = hashlib.sha256(corr.encode()).hexdigest()[:32]` (pattern: `commerce_order_service.py:67`).
6. Build the DDB item with `wo_status="open"`, `created_at=now_ts()`, `updated_at=now_ts()`, all optional fields only if not `None` (absent from the DDB item when not provided — sparse attribute policy).
7. `T.maintenance_orders.put_item(Item=item, ConditionExpression="attribute_not_exists(sk)")`.
8. On `ClientError` with code `"ConditionalCheckFailedException"`: the work order already exists. Fetch it with `get_work_order(property_id, work_order_id)` and return it. Emit `_audit("maintenance_order.create.idempotent", actor_sub, work_order_id=work_order_id)`.
9. On success: emit `_audit("maintenance_order.created", actor_sub, work_order_id=work_order_id, property_id=property_id)`.
10. Return `_item_to_out(item)`.

**`get_work_order(property_id, work_order_id) -> MaintenanceOrderOut | None`**:

1. `_require_enabled()`.
2. `resp = T.maintenance_orders.get_item(Key={"pk": _wo_pk(property_id), "sk": _wo_sk(work_order_id)})`.
3. Return `_item_to_out(resp["Item"])` if `"Item"` in resp, else `None`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotency

`create_work_order` is idempotent on `correlation_id`. Given the same `correlation_id`, `sha256(corr)[:32]` always produces the same `work_order_id`, and the `attribute_not_exists(sk)` conditional `put_item` ensures exactly one DDB row is written. A second call with the same `correlation_id` hits the `ConditionalCheckFailedException` branch, fetches the existing row, and returns it unchanged — the caller receives the same `MaintenanceOrderOut` both times. The `maintenance_order.create.idempotent` audit event distinguishes the replay from an original write.

When the caller does not supply a `correlation_id`, the service generates `f"wo:{actor_sub}:{uuid4().hex}"` — a random, non-colliding key — making every call produce a new work order. This mirrors the FXA-012 §5.1 contract exactly.

### 5.2 Flag-off behavior

When `MAINTENANCE_ORDERS_ENABLED=false` (the default), `_require_enabled()` at the top of every service function immediately raises `HTTPException(status_code=404)`. No DDB read or write occurs. The table does not need to exist. The setting is evaluated at call time (not module import time) via `getattr(S, "maintenance_orders_enabled", False)`, which also means toggling the env var and restarting the process is sufficient to enable or disable the feature without code changes.

### 5.3 Priority validation

`body.priority` is validated against `WO_PRIORITIES = frozenset({"urgent", "high", "normal", "low"})` in `create_work_order`, not in the Pydantic model. This follows the service-layer validation pattern used in PUR-003 and FXA-012 (a free-form `str` field in the Pydantic model, a `frozenset` guard in the service). Rationale: future additions to the priority enum do not require a model rebuild; the frozenset check raises a 422 with `detail="invalid_priority"` and a descriptive `allowed` list.

### 5.4 Property FK validation

`create_work_order` validates the `property_id` FK by calling `get_property(property_id)` from `app.services.property_mgmt`. If the property does not exist or is archived, `get_property` returns `None` and `create_work_order` raises `HTTPException(404, detail="property_not_found")`. No cascade validation of `unit_id` is performed in this ticket — that guard is in WOV-002's `assign_work_order`, where `unit_id` can also be set or updated.

The lazy import (`from app.services.property_mgmt import get_property` inside the function body) avoids a circular import at module load time. If `app.services.property_mgmt` is not yet present (PROP-001 unbuilt), the `ImportError` is caught, a warning is logged, and `create_work_order` proceeds without the property guard. This means WOV-001 is deployable before PROP-001 is merged.

### 5.5 Sparse attributes

`unit_id`, `vendor_id`, `assignee_sub`, `scheduled_for`, `cost_cents`, and `completed_at` are absent from the DDB item when not provided. They are NOT written as `None` or empty string. `_item_to_out` uses `.get(field)` with `None` default for all optional fields; the Pydantic `MaintenanceOrderOut` model accepts `Optional[int]` / `Optional[str]` for each. This matches the sparse attribute policy throughout the codebase (e.g., `app/services/billing_shared.py` ledger items).

### 5.6 Decimal coercion

DynamoDB returns numeric attributes as `Decimal`. `_to_int` coerces every numeric field in `_item_to_out`. Without this, `MaintenanceOrderOut.created_at` would be a `Decimal`, which serializes fine via Pydantic `json()` but breaks equality assertions in tests. The `_FloatSafeTable` proxy in `app/core/tables.py:29–66` coerces `float → Decimal` on writes; reads still return `Decimal` and must be coerced in the service layer.

### 5.7 `_DEFAULT_WO_COLUMNS` constant

`maintenance_orders.py` defines a module-level display-only Kanban column map mirroring `tickets.py:61–70` `_DEFAULT_BOARD_COLUMNS`:

```python
_DEFAULT_WO_COLUMNS: tuple[dict, ...] = (
    {"column_id": "wo_open",        "title": "Open",        "status_key": "open",        "order": 0},
    {"column_id": "wo_assigned",    "title": "Assigned",    "status_key": "assigned",    "order": 1},
    {"column_id": "wo_in_progress", "title": "In Progress", "status_key": "in_progress", "order": 2},
    {"column_id": "wo_completed",   "title": "Completed",   "status_key": "completed",   "order": 3},
    {"column_id": "wo_cancelled",   "title": "Cancelled",   "status_key": "cancelled",   "order": 4},
)

def default_wo_columns() -> list[dict]:
    return [dict(c) for c in _DEFAULT_WO_COLUMNS]
```

This constant is consumed by WOV-005's Kanban renderer. Defining it in WOV-001 avoids adding a separate commit when WOV-005 is implemented.

### 5.8 `cost_cents` is reporting-only in WOV-001

`cost_cents` is stored as a numeric attribute on the work-order item. It is NOT written to any billing ledger in this ticket, and it does NOT call `billing_shared.new_ledger_entry`. It is a plain reporting field recorded by WOV-002's `transition_work_order` on the `completed` transition. Optional escrowed paid maintenance (where real money moves) is the scope of WOV-003, which delegates to the TBT bounty escrow primitives. This separation means WOV-001 and WOV-002 can ship with zero billing impact.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 Dev/prod parity

There are zero `if S.dev_mode` branches in `maintenance_orders.py`. The `T.maintenance_orders` handle is wired via `_safe_table(S.maintenance_orders_table_name)` in `app/core/tables.py` — in dev, boto3 calls are intercepted by moto (the in-process mock at `app/core/dev_s3.py` and the DynamoDB Local endpoint at port 8001); in prod, they reach real DynamoDB. The service code is identical in both environments. This satisfies the SECOPS-007 requirement: no AWS divergence in business logic.

### 7.2 Idempotency contract

`create_work_order` is idempotent on `correlation_id`. The `attribute_not_exists(sk)` guard is a DynamoDB conditional write — it is atomic under concurrent requests for the same `correlation_id`; exactly one writer wins, the others observe `ConditionalCheckFailedException` and return the existing item. This is the same pattern as FXA-012 §5.1 and `app/services/inventory.py` reservation creation.

### 7.3 Security

No WOV-001 service function is callable by unauthenticated clients: `_require_enabled()` runs first (throws 404 when flag off), and the router (in WOV-002) enforces `require_admin_or_root_csrf` on mutations and `require_ui_session` on reads. There is no sensitive data in work-order rows (no PII beyond `actor_sub` / `assignee_sub`), so no KMS encryption is needed.

`actor_sub` is supplied by the router from the authenticated session, never from the request body — preventing impersonation of the creating user.

### 7.4 Money safety (WOV-001 scope)

WOV-001 contains no money movement. `cost_cents` is a plain integer attribute on the work-order row and is never passed to `billing_shared.new_ledger_entry`, `apply_balance_delta`, or any billing primitive. There is no risk of an incorrect ledger entry in this ticket. The billing primitives are first touched in WOV-003.

No existing file has a line modified other than the four append points. All existing tests and endpoints are unaffected. The platform is byte-for-byte unchanged when `MAINTENANCE_ORDERS_ENABLED=false`.

### 8.2 DynamoDB table creation

`scripts/local-ddb-init.py` creates the `maintenance_orders` table at dev stack start (via `just up` or `just restart`). In production, the table must be created via an `aws dynamodb create-table` call (or Terraform / CDK) before `MAINTENANCE_ORDERS_ENABLED=true` is set. Setting the flag before the table exists will produce a `ResourceNotFoundException` on the first DDB call.

Recommended migration sequence for production:
1. Deploy code with `MAINTENANCE_ORDERS_ENABLED=false` (default). No DDB I/O; table absence is harmless.
2. Create the `maintenance_orders` table + both GSIs with `attr_types={"created_at": "N"}`.
3. Set `MAINTENANCE_ORDERS_ENABLED=true` and deploy.

No backfill is needed; the table starts empty.

### 8.3 No schema migration for existing tables

WOV-001 does not modify `billing`, `tickets`, `alerts`, or any other existing DynamoDB table. Zero backward-compatibility concerns.

## 10. Open Questions / Assumptions

1. **PROP-001 merge order**: This spec assumes PROP-001 is merged before WOV-001 so that `app.services.property_mgmt.get_property` is importable. The `ImportError` fallback (§5.4) makes WOV-001 deployable before PROP-001 as a safety net, but the intended build order is `PROP-001 → WOV-001 → WOV-004 → WOV-002 → WOV-003 → WOV-005`.

2. **`unit_id` FK validation**: WOV-001 does not validate that `unit_id` resolves to a real unit row in the PROP-002 `properties` table (child `UNIT#{id}` row). This validation is deferred to WOV-002's `assign_work_order`. A work order can be created with an arbitrary `unit_id` string in WOV-001. This is intentional — create is staff-only and a weak guard is acceptable at creation time; the stronger guard on assignment ensures the WO is not dispatched to a non-existent unit.

3. **`vendor_id` at creation**: WOV-001 stores `vendor_id` on the item if the caller supplies it, but does not validate it against the WOV-004 vendor directory. The active-vendor guard is the responsibility of WOV-002's `assign_work_order`. If a caller sets `vendor_id` on create (outside the normal workflow), WOV-002's assign path will validate it when the WO is formally assigned.

4. **Table size and scan prevention**: No-filter `list_work_orders` → 400 (implemented in WOV-002). WOV-001 does not expose a list endpoint. The `GSI_WO_STATUS` and `GSI_WO_ASSIGNEE` GSIs ensure all production query paths are bounded (by status partition or by assignee partition). Full table scans are never needed in the normal operating model.

5. **`scheduled_for` past timestamps**: No minimum is enforced on `scheduled_for` at creation or scheduling time. Staff may record a work order that was completed in the past with a historical `scheduled_for`. Enforcing future-only scheduling is a product decision deferred to WOV-002.
