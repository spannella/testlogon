# WOV-004 — Trade-categorized vendor directory (on the PUR-003 supplier model)

**Type**: Feature | **Priority**: P1 | **Estimate**: 1.5d
**Source**: `docs/open-property/WORKORDERS_VENDORS_TICKETS.md` §WOV-004 + `docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §C

---

## 1. Summary & Goal

WOV-004 introduces a trade-categorized vendor directory for property maintenance, built as a thin wrapper over the PUR-003 supplier party service (`docs/ofbiz/specs/PUR-003.md`). A "maintenance vendor" is a PUR-003 supplier with two additional attributes: a `trade_category` enum value and a `source="maintenance_vendor"` marker. No new DynamoDB table is created when PUR-003 is available; the existing `suppliers` table (introduced by PUR-002) is reused directly.

The deliverables are:

1. **`app/services/maintenance_vendors.py`** — a six-function wrapper module that validates `trade_category`, delegates all persistence to `app/services/suppliers.py` (PUR-003), and exposes a clean vendor-focused API surface to its callers.
2. **`VendorOut` / `VendorCreateIn` / `VendorPatchIn` Pydantic models** added to `app/models.py` (a thin extension of the PUR-003 `SupplierOut` shape with `trade_category` added).
3. **HTTP endpoints** mounted in `app/routers/maintenance_orders.py` under `/ui/maintenance/vendors`, with staff-only mutations and `require_ui_session` reads, gated by the `MAINTENANCE_ORDERS_ENABLED` master flag (and `PURCHASING_SCM_ENABLED` when PUR-003 is present).
4. The `get_vendor(vendor_id)` function specifically, which WOV-002's `assign_work_order` lazy-imports as the active-vendor guard for work-order assignment.

With both flags off (the default) the platform is byte-for-byte unchanged. No existing table, router, or service is modified.

## 2. Context & Current State

### 2.1 The gap

The open-property gap analysis (`docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §C, row "Vendor directory (by trade)") marks this capability as **PLANNED** via PUR-003. The current codebase has no `trade_category` concept, no vendor directory, and no `maintenance_vendors.py` module. A `grep -rn "maintenance_vendors\|trade_category\|VENDOR_CATEGORIES"` across the repository returns zero hits.

### 2.2 PUR-003 supplier service — the base layer

`docs/ofbiz/specs/PUR-003.md` specifies `app/services/suppliers.py` with the following public API:

- `create_supplier(user_sub, name, *, email=None, phone=None, address=None, default_currency="USD", payment_terms_days=30) -> dict` — deterministic `supplier_id = sha256(f"supplier:{user_sub}:{name}")[:32]` (PUR-003 §5.1); idempotent per `(user_sub, name)`.
- `get_supplier(supplier_id) -> dict | None` — direct key lookup; returns `None` if absent.
- `update_supplier(supplier_id, user_sub, *, name=None, ...) -> dict` — partial update; raises `HTTPException(404)` for unknown id.
- `set_supplier_status(supplier_id, status, user_sub) -> dict` — status ∈ `{"active","inactive"}`; raises 422 on invalid value, 404 on missing id.
- `list_suppliers(status="active", *, cursor=None, limit=50) -> dict` — queries `GSI_STATUS` (PK=`status` S, SK=`created_at` N) with cursor pagination via `encode_cursor`/`decode_cursor` (`app/core/cursor.py:94,103`).

The PUR-003 supplier table (introduced by PUR-002) is:

| Key | Type | Value |
|---|---|---|
| `supplier_id` (PK) | S | `sha256(f"supplier:{user_sub}:{name}")[:32]` |
| `sk` (SK) | S | Always `"META"` |
| `status` | S | `"active"` / `"inactive"` |
| `created_at` | N | `now_ts()` — `GSI_STATUS` sort key |

`attr_types={"created_at": "N"}` declared by PUR-002's `TableDef` entry in `scripts/local-ddb-init.py` (after the `returns` block at line 2492).

## 3. Data Model

### 3.1 Primary path — PUR-003 `suppliers` table (when PUR-002/PUR-003 are available)

WOV-004 adds no new DynamoDB table in this path. All vendor rows live in the `suppliers` table introduced by PUR-002, co-located with any other suppliers in the platform. The `trade_category` and `source` attributes are extra pass-through fields on the existing PUR-003 `SupplierOut` shape:

| Attribute | DDB Type | Notes |
|---|---|---|
| `supplier_id` (PK) | S | `sha256(f"supplier:{user_sub}:{name}")[:32]`; used as `vendor_id` FK on work orders |
| `sk` (SK) | S | Always `"META"` |
| `name` | S | Vendor display name; 1–200 chars |
| `status` | S | `"active"` / `"inactive"` |
| `trade_category` | S | One of the seven-value enum (§3.3); required on create |
| `source` | S | Always `"maintenance_vendor"` — distinguishes vendor records from non-maintenance suppliers in cross-domain queries |
| `email` | S | Optional |
| `phone` | S | Optional; stored in E.164 after `normalize_phone()` |
| `address` | M | Optional map `{line1, line2, city, state, postal_code, country}` |
| `default_currency` | S | ISO 4217; default `"USD"` |
| `payment_terms_days` | N | Net-days integer; default `30` |
| `created_by` | S | `user_sub` of creating admin |
| `user_sub` | S | **Optional (decision D2)** — links the vendor to a real platform account whose wallet receives on-platform escrow payout (WOV-003). Absent/`None` for external vendors with no platform account; in that case WOV-003 escrow release falls back to the maintenance clearing account. Distinct from `created_by` (the admin who registered the vendor). |
| `created_at` | N | `now_ts()` integer — `GSI_STATUS` sort key |
| `updated_at` | N | `now_ts()` on every write |

`GSI_STATUS` (PK=`status` S, SK=`created_at` N) is provided by PUR-002. `attr_types={"created_at": "N"}` declared there covers the sort key.

`list_vendors(trade_category="plumbing")` applies a `FilterExpression=Attr("trade_category").eq(trade_category)` post-query filter on the `GSI_STATUS` results. Because `FilterExpression` is evaluated after the page is fetched (CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha), callers must follow `cursor` to exhaustion when requesting a trade-filtered list on a large dataset.

### 3.2 Standalone-table fallback — `maintenance_vendors` table

When PUR-002/PUR-003 are unbuilt, WOV-004 adds a `maintenance_vendors` `TableDef` to `scripts/local-ddb-init.py` after the `maintenance_orders` entry:

```python
# maintenance_vendors: standalone vendor directory for WOV-004
# (used only when PUR-002/PUR-003 are not yet built; superseded by the
# PUR-003 suppliers table once PUR-002 merges)
TableDef(
    _resolve_table_name(S.maintenance_vendors_table_name, "maintenance_vendors"),
    "vendor_id",
    "sk",
    gsi=[
        {
            "index_name": "GSI_VENDOR_STATUS",
            "partition_key": "status",
            "sort_key": "created_at",
        },
    ],
    attr_types={"created_at": "N"},
),
```

Key design decisions:
- `vendor_id` is the hash key (not `supplier_id`) to make the standalone table self-documenting. In practice `vendor_id == supplier_id` because both use the same `sha256(f"supplier:{user_sub}:{name}")[:32]` formula — FK compatibility is preserved.
- SK is always `"META"` (one row per vendor, identical to PUR-003's single-row-per-supplier shape).
- `attr_types={"created_at": "N"}` is mandatory; without it DynamoDB Local stores `created_at` as String, causing `ValidationException` when the GSI is queried with an integer sort key expression (CLAUDE.md "DynamoDB numeric GSI keys" gotcha).

#### 4.3.1 Flag helper

#### 4.3.2 Public function signatures

```python
VENDOR_TRADE_CATEGORIES: frozenset[str] = frozenset({
    "plumbing", "electrical", "hvac",
    "handyman", "cleaning", "landscaping", "general",
})

def _validate_trade_category(tc: str) -> None:
    """Raises HTTPException(422) when tc not in VENDOR_TRADE_CATEGORIES."""
    if tc not in VENDOR_TRADE_CATEGORIES:
        raise HTTPException(
            status_code=422,
            detail={
                "code": "invalid_trade_category",
                "allowed": sorted(VENDOR_TRADE_CATEGORIES),
            },
        )

def create_vendor(
    actor_sub: str,
    body: VendorCreateIn,
) -> VendorOut:
    """
    Validate trade_category → delegate to create_supplier (PUR-003) or inline
    standalone CRUD. Idempotent per (actor_sub, name) via sha256 deterministic id.
    Stamps trade_category + source="maintenance_vendor" on the item.
    When body.user_sub is provided (decision D2), stamps user_sub onto the item to
    link the vendor to a platform account (enables on-platform escrow payout via
    WOV-003); when absent the vendor is external and escrow falls back to the
    maintenance clearing account.
    Emits audit event "maintenance_vendor.created".
    """

def get_vendor(vendor_id: str) -> VendorOut | None:
    """
    Direct key lookup. Returns VendorOut if found, None if absent.
    Used by WOV-002 assign_work_order active-vendor guard (imported lazily).
    Does NOT require maintenance_orders_enabled — WOV-002 handles its own flag.
    """

def update_vendor(
    vendor_id: str,
    actor_sub: str,
    body: VendorPatchIn,
) -> VendorOut:
    """
    Partial update of mutable fields. Validates trade_category when non-None.
    Raises 404 for unknown vendor_id. Emits "maintenance_vendor.updated".
    Decision D2: body.user_sub set (non-empty) links/relinks the vendor to a
    platform account; body.user_sub == "" clears the link (REMOVE user_sub on the
    item) so the vendor reverts to external/clearing-account payout. A None field
    (omitted from the PATCH body) leaves the existing link unchanged.
    """

def set_vendor_status(
    vendor_id: str,
    status: str,
    actor_sub: str,
) -> VendorOut:
    """
    Soft deactivation / reactivation. status ∈ {"active","inactive"}.
    Raises 422 for invalid status, 404 for unknown vendor_id.
    Emits "maintenance_vendor.status_changed".
    Inactive vendors remain valid historical FKs on work orders;
    they are excluded from list_vendors(status="active") but resolvable by get_vendor.
    """

def list_vendors(
    status: str = "active",
    *,
    trade_category: Optional[str] = None,
    cursor: Optional[str] = None,
    limit: int = 50,
) -> VendorListOut:
    """
    Paginated listing. Queries GSI_STATUS (PUR-003 path: GSI_STATUS on suppliers;
    standalone path: GSI_VENDOR_STATUS on maintenance_vendors).
    Optional trade_category FilterExpression applied post-query.
    limit capped at 200.
    Returns VendorListOut with vendors, cursor, count.
    """
```

#### 4.3.3 `create_vendor` — detailed steps (delegating path)

1. `_require_enabled()`.
2. `_validate_trade_category(body.trade_category)`.
3. Delegate to `suppliers.create_supplier(actor_sub, body.name, email=body.email, phone=body.phone, address=body.address, default_currency=body.default_currency, payment_terms_days=body.payment_terms_days)` — this call handles the deterministic `supplier_id` derivation (`sha256(f"supplier:{actor_sub}:{name}")[:32]`), the `attribute_not_exists(sk)` idempotency guard, and phone normalization (PUR-003 §5.1, §5.2).
4. Upsert `trade_category`, `source="maintenance_vendor"`, and (when `body.user_sub` is non-empty) `user_sub` onto the returned item via `T.suppliers.update_item(Key={"supplier_id": sid, "sk": "META"}, UpdateExpression="SET trade_category = :tc, #src = :s, updated_at = :ts[, user_sub = :us]", ...)`. The `user_sub` SET clause is included only when `body.user_sub` is provided (decision D2). This two-step (create then patch) is necessary because `create_supplier` does not accept arbitrary extra fields — the wrapper adds the vendor-specific attributes afterward. The second write is idempotent (same values on replay).
5. Re-fetch via `get_vendor(supplier_id)` and return as `VendorOut`.
6. Emit `_audit("maintenance_vendor.created", actor_sub, vendor_id=supplier_id, trade_category=body.trade_category)`.

**Idempotency note**: The `suppliers.create_supplier` call is idempotent (same `(actor_sub, name)` → same `supplier_id`, no duplicate row). The subsequent `update_item` is also idempotent (same values). The combined operation is therefore idempotent end-to-end.

#### 4.3.4 `get_vendor` — used by WOV-002 lazy import

```python
def get_vendor(vendor_id: str) -> VendorOut | None:
    # Does NOT call _require_enabled() — this function is called from
    # WOV-002's assign_work_order, which has already checked its own flag.
    item = _backend_get(vendor_id)   # dispatches to suppliers.get_supplier or standalone T.maintenance_vendors
```

`_item_to_vendor_out` calls `_to_int` for all numeric fields and `.get(field)` with appropriate defaults. This is the function WOV-002 calls as part of the active-vendor guard, relying on the returned `VendorOut`'s `status` attribute to distinguish active vs inactive vendors.

## 5. Detailed Behavior & Edge Cases

### 5.1 Trade-category validation

`_validate_trade_category(tc)` is called in both `create_vendor` and `update_vendor` (when `body.trade_category is not None`). The error shape is:

```json
{
  "code": "invalid_trade_category",
  "allowed": ["cleaning","electrical","general","handyman","hvac","landscaping","plumbing"]
}
```

(sorted alphabetically). Adding a new trade category requires only updating `VENDOR_TRADE_CATEGORIES` — no schema migration and no DDB index change is needed because `trade_category` is stored as a plain string attribute with no GSI key dependency.

### 5.2 Idempotency — `(actor_sub, name)` scope

`create_vendor` inherits PUR-003's per-`(actor_sub, name)` idempotency scope: `sha256(f"supplier:{actor_sub}:{name}")[:32]` produces the same `vendor_id` for the same calling admin and vendor name. Two different admins creating a vendor named "ABC Plumbing" produce different `vendor_id`s (this follows PUR-003 §5.7 by design). If global-unique vendor names across all admins are required, that is a UI-layer concern (duplicate-name warning) not a hard DDB constraint.

The two-step create (`create_supplier` + `update_item` to add `trade_category`) is atomic enough for idempotency: the second step is a targeted `update_item` with fixed values, so replaying it produces the same state.

### 5.3 Soft deactivation and FK preservation

`set_vendor_status(vendor_id, "inactive", actor_sub)` changes `status` on the DDB item (via `update_item` — same pattern as PUR-003 §5.3). After deactivation:

- `list_vendors(status="active")` omits the vendor (GSI partition key changed from `"active"` to `"inactive"`).
- `get_vendor(vendor_id)` still resolves the vendor (direct `get_item` on PK/SK, not the GSI).
- `assign_work_order` (WOV-002) raises HTTP 422 `vendor_inactive` when the guard calls `get_vendor` and finds `status=="inactive"`.
- Existing work orders that already have `vendor_id` set to this vendor are **not** invalidated — the FK is historical. The deactivation only prevents new assignments.

Re-activation (`set_vendor_status(vendor_id, "active", ...)`) is always valid; there is no one-way-only lifecycle on the vendor status (same as PUR-003 §5.5).

### 5.4 `list_vendors` — `FilterExpression` pagination hazard

Per the CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha: DynamoDB fetches up to `Limit` items before applying the `trade_category` filter. On a large `suppliers` table with many non-maintenance-vendor rows, a `limit=50` page may return fewer than 50 vendors after filtering. Callers (the WOV-005 frontend) must follow `cursor` to exhaustion to get a complete trade-filtered list.

The `source="maintenance_vendor"` FilterExpression is also applied in all `list_vendors` calls to exclude non-maintenance PUR-003 suppliers from the vendor directory view. This means both `source` and `trade_category` filters are applied post-query when both are present.

### 5.5 `update_vendor` — trade_category update

When `body.trade_category` is non-None, `_validate_trade_category` fires before any DDB write. The update path uses `update_item` (partial update — only provided fields are written), preserving `created_at`, `created_by`, and any fields not in the PATCH body.

### 5.6 `get_vendor` — flag bypass for WOV-002

`get_vendor` does not call `_require_enabled()`. This is intentional: WOV-002's `assign_work_order` uses `get_vendor` as an FK-resolution call and has already validated `MAINTENANCE_ORDERS_ENABLED` before calling the assign service function. Adding a second flag check inside `get_vendor` would cause a spurious 404 when called from a context that has already validated the flag independently.

### 5.7 Unknown `vendor_id` behavior

`get_vendor("nonexistent")` returns `None` (not `HTTPException`). This matches `get_supplier`'s contract (PUR-003 §4.1.3). The HTTP-level 404 is raised in the router handler (not the service layer), following the pattern at `app/routers/tickets.py` and `app/routers/maintenance_orders.py` (WOV-002's `GET /work-orders/{id}`).

### 5.8 `source` attribute and cross-domain isolation

All vendor rows created by `create_vendor` carry `source="maintenance_vendor"`. The `list_vendors` function always filters by `source="maintenance_vendor"` so that non-maintenance PUR-003 suppliers (e.g. wholesale product suppliers from the PUR-006 purchase-order flow) never appear in the vendor directory. This prevents contamination of the vendor directory with unrelated supplier records on the shared `suppliers` table.

### 5.9 `trade_category` as a FilterExpression — sparse attribute handling

In the standalone table path, every vendor row has `trade_category` present (it is required on create). In the PUR-003 delegating path, non-vendor supplier rows on the `suppliers` table do NOT have `trade_category`, so a `FilterExpression` for a specific trade category naturally excludes them. The `source` filter is the primary isolation; `trade_category` is a secondary narrowing filter.

### 5.10 `user_sub` — optional platform-account link (decision D2)

`user_sub` is an **optional, sparse** attribute (decision D2; `docs/CROSS_TICKET_AUDIT.md §D2`). It links a maintenance vendor to a real platform account whose wallet receives escrow payout on the WOV-003 on-platform path. Behavior:

- **Absent / `None`** (the common case — most maintenance vendors are external parties with no platform account): the attribute is simply not written. `VendorOut.user_sub` serializes as `null`. WOV-003 `_release_escrow` then takes the **clearing-account fallback** (credits `CLEARING#maintenance` + writes a pending-disbursement marker for off-platform admin payout) — it never raises a 409 dead-end.
- **Set on create** (`VendorCreateIn.user_sub`): stamped in the §4.3.3 step-4 patch. On-platform escrow payout is enabled immediately.
- **Set/changed on update** (`VendorPatchIn.user_sub` non-empty): the link is established or re-pointed at a different account.
- **Cleared on update** (`VendorPatchIn.user_sub == ""`): `update_vendor` issues `REMOVE user_sub` so the vendor reverts to external/clearing-account payout. (Distinguished from `None`/omitted, which leaves the existing value untouched.)
- **Validation**: `user_sub` is stored as-is; it is not verified against the users table at write time (a vendor may be linked to an account that is later deactivated). WOV-003 is responsible for crediting whatever wallet `user_sub` names; an invalid/stale sub credits a non-existent wallet's BALANCE row exactly as any other wallet write would (no special-casing). No GSI key dependency — `user_sub` is a plain attribute.
- **Distinct from `created_by`**: `created_by` is the admin who registered the vendor; `user_sub` is the vendor's own platform identity. They are unrelated and must never be conflated as the payout target.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 Dev/prod parity

`app/services/maintenance_vendors.py` and `app/routers/maintenance_orders.py` (vendor endpoints) contain **zero** `if S.dev_mode` branches. All DDB I/O is identical in dev (DynamoDB Local at port 8001, moto in tests), and prod (real DynamoDB via `T.*` handles). The backend-selection logic (`_PUR_AVAILABLE`) is a one-time import-time detection, not an env-based branch — it is the same in all environments. This satisfies SECOPS-007.

### 7.2 Idempotency

| Operation | Idempotency mechanism |
|---|---|
| `create_vendor` | `create_supplier` uses a read-then-conditional-write (PUR-003 §5.1); the subsequent `update_item` for `trade_category`/`source` is idempotent (same values). Same `(actor_sub, name)` → same `vendor_id`, one row. |
| `get_vendor` | Pure read; inherently idempotent. |
| `update_vendor` | Full-item or targeted `update_item`; re-calling with same args produces same state. |
| `set_vendor_status` | `update_item` SET; same status → same DDB state. `active → active` and `inactive → inactive` are no-ops. |
| `list_vendors` | Pure read; inherently idempotent. |

### 7.3 Security

- **Staff-only mutations**: All `POST`, `PATCH` vendor endpoints use `require_admin_or_root_csrf` (`app/auth/policy.py:100`). Non-admin callers receive HTTP 403. CSRF header (`x-csrf-token`) is enforced for cookie-auth sessions.
- **Read access**: `GET` endpoints use `require_ui_session`, making vendor listings available to any authenticated session (e.g. tenants browsing vendor profiles is a product decision; the default router allows any session user).
- **`vendor_id` is not a capability token**: It is a truncated sha256 of public inputs (`actor_sub` + `name`). Access control is enforced at the router auth layer.
- **`actor_sub` is never from the request body**: It is extracted from the authenticated session by the router, preventing impersonation.
- **No PII on work-order rows**: The `vendor_id` FK stored on the work-order row is an opaque identifier. PII (email, phone, address) lives only on the vendor row and is returned only to authenticated callers with `require_ui_session`.
- **Audit trail**: Every mutation emits `_audit(...)` via `app.services.alerts.audit_event` (`:644`). The best-effort wrapper ensures audit failures never block service mutations.

### 7.4 Money safety

**WOV-004 involves no money movement whatsoever.**

- No call to `billing_shared.new_ledger_entry` (`billing_shared.py:224`).
- No call to `billing_shared.settle_or_reverse_ledger` (`billing_shared.py:262`).
- No call to `billing_shared.apply_balance_delta` (`billing_shared.py:83`).
- No call to `billing_shared.compute_due` (`billing_shared.py:158`).
- No payment provider (Stripe, PayPal, CCBill) is called.
- No wallet delta is applied.

The vendor is a directory record only. Actual money movement tied to vendors (vendor payout on WO completion) is WOV-003's domain, which delegates to the TBT bounty escrow primitives (`docs/ticket-bounty/specs/TBT-003.md`, `TBT-006.md`, `TBT-007.md`) and reads the `vendor_sub` from WOV-004's `get_vendor` result. WOV-004 itself has zero financial impact.

### 8.2 Build-order flexibility

WOV-004 is designed to ship either before or after PUR-002/PUR-003:

- **WOV-004 before PUR-002/003**: standalone `maintenance_vendors` table is created, all CRUD is inlined. `PURCHASING_SCM_ENABLED` flag is absent from settings — `getattr(S, "purchasing_scm_enabled", False)` safely returns `False`, selecting the standalone path.

### 8.3 DynamoDB table creation (standalone path)

`scripts/local-ddb-init.py` creates `maintenance_vendors` at dev stack start. In production with the standalone path, create the table before enabling `MAINTENANCE_ORDERS_ENABLED`. Setting the flag without the table causes `ResourceNotFoundException` on the first DDB call. Recommended sequence: (1) deploy with flag off, (2) create table + GSI with `attr_types={"created_at": "N"}`, (3) enable flag.

### 8.4 No schema migration for existing tables

WOV-004 does not modify `billing`, `tickets`, `alerts`, `maintenance_orders`, or any other existing DynamoDB table. Zero backward-compatibility concerns.

## 10. Open Questions / Assumptions

1. **PUR-002/003 merge order**: The preferred build order is `PUR-002 → PUR-003 → WOV-001 → WOV-004`. The standalone fallback (§2.5) exists for cases where WOV-004 is built before PUR. Once PUR is merged and the delegating path is active, the standalone `maintenance_vendors` table is no longer written to; it can be dropped after a transition period if no rows were written to it.

2. **Global vendor-name uniqueness**: Currently per `(actor_sub, name)`. Two different admins can create "ABC Plumbing" with different `vendor_id`s. If platform-wide uniqueness is required, the hash must change to `sha256(f"supplier:global:{name}")[:32]` (a PUR-013 design concern, not WOV-004). Assumption: per-actor-sub uniqueness is sufficient.

3. **Vendor profile fields beyond PUR-003**: The current `VendorCreateIn` exposes the PUR-003 supplier fields (`email`, `phone`, `address`, `payment_terms_days`, `default_currency`) plus the optional `user_sub` platform-account link (decision D2). Other maintenance-specific fields such as `license_number`, `insurance_expiry`, `service_area_zip_codes`, or `rating` are out of scope for WOV-004 and are deferred to a future WOV-006 ticket. These would be additive attributes on the same row.

   **RESOLVED (decision D2, 2026-06-13)**: The earlier open question of whether `VendorOut` should carry the vendor's own platform identity is now decided. `user_sub` is an optional field (§3.4, §5.10); it is no longer deferred. This unblocks the WOV-003 escrow-payout dependency (`docs/CROSS_TICKET_AUDIT.md §D2`).

4. **`payment_terms_days` relevance for maintenance vendors**: Inherited from PUR-003, this field is optional but present. For maintenance vendors it may represent the vendor's invoice net terms. Assumption: the field is accepted and stored but not functionally used in the WOV cluster.

5. **`trade_category` as a GSI key vs. FilterExpression**: Making `trade_category` a GSI partition key would allow an O(1) lookup of all active plumbers, eliminating the FilterExpression pagination hazard (§5.4). However, a seven-value enum as a GSI key creates hot partitions (all plumbers in one partition) and adds `attr_types` complexity. The FilterExpression approach is sufficient for the expected scale (tens to low hundreds of vendors per installation). If a larger deployment needs trade-category indexing, a future `GSI_TRADE_CATEGORY` with PK=`trade_category`+`source`, SK=`created_at` can be added without breaking the current contract.

6. **`source="maintenance_vendor"` written on the `suppliers` table**: When using the delegating path, the `source` attribute is added to a PUR-003 supplier row via a post-create `update_item`. If `update_vendor` is called on a row that already has `source="maintenance_vendor"`, no change occurs. If `update_supplier` (PUR-003 direct) is called on the same row, `source` is preserved because `update_supplier` uses a merge/put pattern that preserves fields not in the patch body (PUR-003 §5.2).

### Cross-ticket reconciliation (decision D2, 2026-06-13)

Per `docs/CROSS_TICKET_AUDIT.md §D2` (hybrid vendor payout), `VendorOut` / the vendor model gains an **optional `user_sub: str | None`** field (default `None`) that links a maintenance vendor (a PUR-003 supplier-directory record) to a real platform account. CRUD support is added: `VendorCreateIn.user_sub` stamps the link on create; `VendorPatchIn.user_sub` sets it (non-empty) or clears it (`""` → `REMOVE user_sub`), while an omitted/`None` field leaves it unchanged (§3.4, §4.3.3, §5.10, test plan §9.1). A set `user_sub` enables WOV-003's on-platform escrow payout to that vendor's wallet; an absent `user_sub` (external vendor) routes WOV-003 escrow to the `CLEARING#maintenance` clearing account instead of the old 409 dead-end. This resolves the escalated open product decision previously recorded in WOV-003 §10.2 item 2 / verification row 34. WOV-004 itself still moves no money (§7.4 unchanged) — it only stores the link the WOV-003 payout path reads.
