# LSE-001 — Lease entity — DDB model, table, flag, and state-machine service

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 3 d
**Flag:** `LEASES_ENABLED` (default OFF)

---

## 1. Summary & Goal

Introduce the **Lease entity**: a time-bounded tenancy agreement that binds a tenant
(`tenant_id`) to a specific unit (`unit_id`) within a property (`property_id`), carrying
the property-specific economic terms — monthly rent, security deposit, due-day, late-fee
structure, grace period — and a lifecycle state machine modeled on the real-estate domain
(`draft → upcoming | active → ended`).

This ticket delivers the foundational persistence and service layer only: the DynamoDB
table definition, the two `app/core/` registrations (Settings + Tables), the service
module with `create_lease`, `get_lease`, and `transition_status`, and the Pydantic model
stubs required for the router (LSE-002). No router, no frontend, no background loop —
those land in LSE-002 and LSE-003.

The lease entity is the **QUO-004 CRM-contract scaffold** (`docs/suitecrm/specs/QUO-004.md`)
specialized for real estate. QUO-004's generic `value_cents` body and AOS party fields are
replaced with property-specific economic attributes; QUO-004's stage vocabulary
(`draft/active/expired/terminated/renewed`) is replaced with the property-domain status
vocabulary (`draft/upcoming/active/ended`). Every primitive QUO-004 reused — the counter
pattern, conditional-write state machine, cursor pagination, `audit_event`, startup hook
wiring — is reused verbatim here.

With `LEASES_ENABLED=0` (the default): every service function short-circuits to `None`,
the `leases` table is never touched, and no existing behavior changes by a single byte.

## 3. Data Model

### 3.1 DynamoDB table: `leases`

Environment variable: `LEASES_TABLE_NAME` (default `"leases"`).
Single-table design; mirrors QUO-004 §3.1 key shape.

```
PK  = USER#{user_sub}       string   (landlord / property owner)
SK  = LEASE#{lease_id}      string   (lease_id = "lse_" + uuid4().hex[:16])

COUNTER row (in same table):
    PK = "COUNTER"
    SK = "LEASE_SEQ"
    next_seq: N   (atomic ADD, same as invoices.py:82)
```

### 3.2 Item attributes

| Attribute | DDB Type | Constraints | Notes |
|---|---|---|---|
| `pk` | S | — | `USER#{user_sub}` |
| `sk` | S | — | `LEASE#{lease_id}` |
| `lease_id` | S | — | Bare id without prefix |
| `lease_number` | S | — | `LSE-{year}-{seq:05d}` from atomic counter |
| `user_sub` | S | — | Denormalized owner for GSI queries |
| `tenant_id` | S | opaque string | FK → TEN; no validation in this ticket (QUO-004 opaque-string precedent) |
| `property_id` | S | opaque string | FK → PROP property |
| `unit_id` | S | opaque string | FK → PROP unit (the occupied unit) |
| `status` | S | enum | `draft` \| `upcoming` \| `active` \| `ended` |
| `start_date` | N | required, `gt=0` | Unix timestamp; beginning of lease term |
| `end_date` | N | optional, `gt=start_date` | Unix timestamp; absent = open-ended / month-to-month |
| `monthly_rent_cents` | N | `ge=0` | Integer cents; informational only — RNT posts charges, not LSE |
| `security_deposit_cents` | N | `ge=0`, default 0 | Integer cents |
| `rent_due_day` | N | `ge=1, le=28` | Day-of-month rent is due; capped at 28 to avoid short-month ambiguity |
| `late_fee_type` | S | enum | `none` \| `flat` \| `percent` |
| `late_fee_cents` | N | `ge=0`, default 0 | Flat late fee in cents; used only when `late_fee_type="flat"` |
| `late_fee_percent_bps` | N | `ge=0, le=10000`, default 0 | Late fee as basis points (500 = 5%); used only when `late_fee_type="percent"` |
| `late_fee_grace_days` | N | `ge=0`, default 0 | Grace days after `rent_due_day` before late fee applies |
| `currency` | S | ISO 4217 lowercase | Default `"usd"` |
| `notes` | S | — | Free text; `""` when absent |
| `renewal_notice_days` | N | `ge=1, le=365`, default 30 | Days before `end_date` to trigger expiration notice (LSE-003) |
| `renewal_notified_at` | N | optional | Unix ts when notice was sent; absent = not yet sent (idempotency marker) |
| `created_at` | N | — | Unix ts set at creation |
| `updated_at` | N | — | Unix ts updated on every write |
| `GSI1PK` | S | literal | `"LEASES#ALL"` on every item; drives admin/cross-user scan |
| `GSI1SK` | N | — | `created_at` value at creation time |
| `GSI2PK` | S | — | `USER#{user_sub}#STATUS#{status}` — updated on every status transition |
| `GSI2SK` | N | sparse | `end_date` when present; items with no `end_date` omit this attribute and are absent from GSI2 |

### 3.3 GSIs

**GSI1 — admin / cross-user list + RNT consumption:**

```
GSI1PK = "LEASES#ALL"        (literal string written on every item)
GSI1SK = created_at          (N — MUST be declared in attr_types)
Index name: leases-all-index
```

Used by `admin_list_leases()` (LSE-002) and by the RNT rent-run / expiration sweep that
iterates all active leases system-wide. Projects all attributes.

**GSI2 — per-owner status + end-date filter:**

```
GSI2PK = USER#{user_sub}#STATUS#{status}
GSI2SK = end_date            (N — MUST be declared in attr_types; sparse)
Index name: leases-by-status-index
```

Used by `list_leases(status=...)` (LSE-002), the upcoming-expiration query (LSE-003), and
the renewal notification loop. Items with no `end_date` do not project `GSI2SK` and are
absent from this index — intentional, as open-ended leases cannot expire.

## 4. API / Service Design

### 4.1 Service module: `app/services/leases.py`

Every public function begins with the flag guard:

```python
if not S.leases_enabled:
    return None
```

This means all callers (router handlers, tests) receive `None` when the flag is off and
must treat it as a no-op. The router layer converts `None` to a 404 response (LSE-002).

#### `_next_lease_number() -> str`

Clone of `invoices.py:82–92`. Targets `T.leases`:

```python
result = T.leases.update_item(
    Key={"pk": "COUNTER", "sk": "LEASE_SEQ"},
    UpdateExpression="ADD next_seq :inc",
    ExpressionAttributeValues={":inc": 1},
    ReturnValues="UPDATED_NEW",
)
seq = int(result["Attributes"]["next_seq"])
year = datetime.now(timezone.utc).year
return f"LSE-{year}-{seq:05d}"
```

Returns `LSE-2026-00001`, `LSE-2026-00002`, etc. The counter row is in the same `leases`
table under `PK="COUNTER"`, `SK="LEASE_SEQ"`, avoiding a separate counter table.

#### `create_lease(user_sub, *, tenant_id, property_id, unit_id, start_date, end_date=None, monthly_rent_cents, security_deposit_cents=0, rent_due_day, late_fee_type="none", late_fee_cents=0, late_fee_percent_bps=0, late_fee_grace_days=0, currency="usd", notes="", renewal_notice_days=30) -> dict | None`

1. Flag guard: return `None` if `not S.leases_enabled`.
2. **Validate inputs:**
   - `start_date` must be a positive integer.
   - If `end_date` is provided, `end_date > start_date` must hold; else raise `HTTPException(400, detail={"code": "invalid_date_range"})`.
   - `late_fee_type` must be one of `{"none", "flat", "percent"}`.
3. Determine initial status:
   - `status = "upcoming"` if `start_date > now_ts()` else `"active"`.
   - Rationale: a lease whose term hasn't started yet is `upcoming`; one currently in its
     term is `active`. There is no `draft` default in the property domain (unlike QUO-004).
     A caller who wants an unconfirmed lease must explicitly create it as `draft` — which
     is a legal starting point for `transition_status` (`draft → upcoming | active`).
     The `draft` status exists in `_LEASE_TRANSITIONS` for pre-signing workflows.
4. Mint identifiers: `lease_id = "lse_" + uuid4().hex[:16]`, `lease_number = _next_lease_number()`.
5. Build item dict with all attributes, plus GSI keys:
   - Always: `GSI1PK="LEASES#ALL"`, `GSI1SK=created_at` (int).
   - Always: `GSI2PK=f"USER#{user_sub}#STATUS#{status}"`.
   - Only when `end_date` is set: `GSI2SK=end_date` (int). Open-ended leases omit `GSI2SK`.
6. Call `T.leases.put_item(Item=item)`.
7. Call `audit_event("lease.created", user_sub, lease_id=lease_id, lease_number=lease_number, status=status)`.
8. Return the item dict.

#### `get_lease(user_sub, lease_id) -> dict | None`

```python
resp = T.leases.get_item(Key={"pk": f"USER#{user_sub}", "sk": f"LEASE#{lease_id}"})
item = resp.get("Item")
if not item or item.get("user_sub") != user_sub:
    return None
return item
```

Returns `None` (→ 404 in router) for both absent and foreign-owner items, leaking no
information about another landlord's leases.

#### `transition_status(user_sub, lease_id, new_status) -> dict`

Mirrors `tickets.py:913` (`update_status`) and QUO-004 §5 (`transition_stage`).

**Allowed transitions** (`_LEASE_TRANSITIONS`):

```python
_LEASE_TRANSITIONS: dict[str, set[str]] = {
    "draft":    {"upcoming", "active"},
    "upcoming": {"active", "ended"},
    "active":   {"ended"},
    # "ended" has no outbound edges — terminal
}
```

`draft → upcoming`: lease is signed but move-in date is future.
`draft → active`: lease signed and already in term (backdated or same-day start).
`upcoming → active`: move-in day arrived.
`upcoming → ended`: cancelled before tenant moved in (e.g. applicant withdrew).
`active → ended`: lease expired naturally or terminated early.
`ended` is terminal — any attempt to transition out of `ended` raises
`HTTPException(400, detail={"code": "invalid_status_transition", "from": "ended", "to": new_status})`.

**Implementation:**

1. Flag guard: return `None` if `not S.leases_enabled`.
2. Fetch current item via `get_lease(user_sub, lease_id)`; 404 if absent.
3. `current_status = item["status"]`.
4. Validate: if `new_status not in _LEASE_TRANSITIONS.get(current_status, set())`,
   raise `HTTPException(400, detail={"code": "invalid_status_transition", "from": current_status, "to": new_status})`.
5. Build `UpdateExpression` that rewrites `status`, `GSI2PK`, `updated_at`, and
   conditionally `GSI2SK` (write only when `end_date` is present on the existing item).
6. Execute conditional `update_item` with
   `ConditionExpression="#s = :old_status"` mapping `#s` → `"status"` and `:old_status` → current value.
   This prevents a race where two concurrent callers both read the same state and both
   attempt the same transition — the second writer gets `ConditionalCheckFailedException`
   → `HTTPException(409, detail={"code": "concurrent_update"})`.
7. **Unit occupancy side-effect** (best-effort, `try/except`):
   - Transition `→ active`: call `prop_unit_service.set_occupancy_status(unit_id, "occupied")` if available.
   - Transition `→ ended`: call `prop_unit_service.set_occupancy_status(unit_id, "vacant")`.
   - Wrapped in `try/except Exception`: a PROP service failure must never roll back the
     lease transition (mirrors EC2/K8s host-inventory best-effort pattern, CLAUDE.md).
     When PROP is not yet deployed the import fails silently and the call is a no-op.
8. Call `audit_event("lease.status_changed", user_sub, lease_id=lease_id, from_status=current_status, to_status=new_status)`.
9. Return the updated item via a subsequent `get_lease` call (or from `update_item` `ReturnValues="ALL_NEW"`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Status auto-assignment on create

`create_lease` determines `status` from `start_date` vs `now_ts()`:

- `start_date > now_ts()` → `"upcoming"` (the lease has been signed but the term has not
  yet begun — common for leases signed weeks ahead of move-in).
- `start_date <= now_ts()` → `"active"` (the term is already running — used for
  back-dating existing tenancies into the system, or for same-day starts).

The caller cannot supply `status` at creation time; it is always derived. If the caller
wants a `"draft"` lease (pre-signing, e.g. during negotiation), they must create with a
future `start_date` and then the LSE-002 endpoint allows `transition_status("upcoming" →
... wait, that requires going through draft)`. Clarification: `draft` is an explicit
starting point, not the default. To create a draft lease, the caller sets an early
`start_date` (even past) and the service will set `upcoming`/`active` — or the caller
uses a dedicated `draft` mode via an optional `force_draft: bool = False` parameter on
`LeaseCreateIn` that, when `True`, overrides the auto-assigned status to `"draft"`.
This is cleaner than requiring a `status` field and avoids the `draft → upcoming → active`
extra round-trip for the common fast-path case.

### 5.2 Open-ended leases

When `end_date` is absent (month-to-month):
- `GSI2SK` is not written to the item (sparse index).
- The item is absent from GSI2 and therefore from all expiration queries.
- `list_leases(status=...)` via GSI2 still returns it if the `GSI2PK` matches (the sort
  key is not required for equality queries on the partition key alone with no sort-key
  condition).
- The renewal notification loop never emits a notice for open-ended leases.

### 5.3 `GSI2PK` consistency

`GSI2PK` is always `USER#{user_sub}#STATUS#{current_status}`. After `transition_status`,
the `UpdateExpression` rewrites `GSI2PK` in the same atomic `update_item` call. There is
no window where the item's `status` field and its `GSI2PK` are inconsistent, because DDB
attribute updates within a single `update_item` are atomic.

### 5.4 Race condition — concurrent transitions

Two concurrent processes that both read the same `status=active` and both attempt
`→ ended` will race at the conditional `update_item`. The first writer succeeds; the
second gets `ConditionalCheckFailedException` (the attribute `status` no longer equals the
old value). The service layer catches this and raises HTTP 409 `concurrent_update`.
Callers must treat 409 as a stale-read signal and re-fetch before retrying.

### 5.5 Terminal status

`ended` has no outbound edges in `_LEASE_TRANSITIONS`. Any `transition_status` call with
`user_sub, lease_id, new_status` where the current item has `status="ended"` raises
HTTP 400 `invalid_status_transition` regardless of `new_status`. This is enforced by the
`_LEASE_TRANSITIONS.get("ended", set())` lookup returning an empty set.

### 5.6 FK validation

`tenant_id`, `property_id`, and `unit_id` are stored as opaque strings. No FK validation
is performed in this ticket — matching the QUO-004 precedent where `contact_id` and
`account_id` are opaque (`QUO-004.md §2`). FK integrity is the responsibility of the
PROP/TEN service layers when those entities land.

### 5.7 Unit occupancy side-effect

When `transition_status` transitions to `active`, it attempts to call the PROP unit
service to set `occupancy_status="occupied"`. When transitioning to `ended`, it attempts
`occupancy_status="vacant"`. Both calls are:
- Wrapped in `try/except Exception: logger.warning(...)` — never raise.
- Conditional on a lazy import succeeding: `from app.services.prop_unit import set_occupancy_status`.
  If the module does not exist (PROP not yet deployed), the `ImportError` is caught and
  the call is a no-op.
- Executed **after** the DDB `update_item` has already succeeded — the lease write is
  never rolled back by a PROP failure.

### 5.8 Monetary fields

`monthly_rent_cents` and `security_deposit_cents` are **informational only** on the lease
entity. They describe the agreed rent but generate no ledger entries here. The RNT
rent-run cluster (downstream consumer) reads these fields from active leases to compute
the monthly charge and posts it via `billing_shared.new_ledger_entry`
(`app/services/billing_shared.py:224`). LSE-001 contains no call to `new_ledger_entry`,
`settle_or_reverse_ledger`, or `apply_balance_delta` — money movement is out of scope
for the entity layer.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no `dev_mode` branch

`app/services/leases.py` contains no `if S.dev_mode:` branch. The single code path uses
`T.leases` (boto3 → DDB Local at `http://localhost:8001` in dev, real DynamoDB endpoint
in prod). `send_alert_email` (LSE-003) owns the dev/prod email divergence internally at
`app/services/alerts.py:459–468` — the lease service calls it identically in both
environments.

### 7.2 Idempotency

- `create_lease` uses `put_item` (not a conditional put). If the same `lease_id` is
  somehow reused (astronomically unlikely: 64-bit hex prefix of UUID4), the item is
  overwritten. The lease number counter is monotonically increasing via `ADD` — it never
  resets, so `LSE-{year}-{seq}` pairs are unique.
- `transition_status` is idempotent in the sense that transitioning to the current status
  is rejected (the `new_status not in _LEASE_TRANSITIONS[current]` check catches
  `current → current` since `current` is never in its own outbound set). Concurrent
  writers are serialized by the DDB conditional write.
- The `renewal_notified_at` marker (LSE-003) is the idempotency key for the notification
  loop — once written, the sweep never re-notifies.

### 7.3 Ownership isolation

All reads and writes use `PK=USER#{user_sub}`. A request for `lease_id` that belongs to
another landlord simply returns no item from DDB (different partition) → `None` → 404.
This leaks zero information about other users' leases.

### 7.4 Money safety

- LSE-001 writes no ledger entries and calls no payment provider. It stores monetary
  amounts as informational integers (`monthly_rent_cents`, `security_deposit_cents`) in
  the DDB item only.
- Future callers (RNT) that post rent charges must use `billing_shared.new_ledger_entry`
  (`billing_shared.py:224`) and must never read the lease's `monthly_rent_cents` and write
  a raw DDB item — they must go through the established ledger primitives.
- Any future deposit refund or fee reversal must reuse `settle_or_reverse_ledger`
  (`billing_shared.py:262`) — a void is a state transition on the ledger row, not a
  deletion. This constraint is in the cross-cutting constraints of `LEASES_TICKETS.md`
  §6 and is enforced by code review.

### 7.5 Input validation

`rent_due_day` is capped at 28 (not 31) to avoid ambiguity in February. Late-fee
basis-points are capped at 10,000 (100%) to prevent data-entry errors from expressing
implausible late fees. These are Pydantic validators on `LeaseCreateIn` / `LeasePatchIn`
and raise HTTP 422 automatically before any service code runs.

never queries it. After creation, set `LEASES_ENABLED=1` to enable the feature. There is
no data backfill required for new deployments (no pre-existing lease data).

## 10. Open Questions & Assumptions

1. **`draft` status at creation.** The spec derives `status` from `start_date` vs current
   time, producing `upcoming` or `active`. If the product requires a pre-signing draft
   workflow, `LeaseCreateIn` should accept an optional `force_draft: bool = False` field.
   This is a minor API question; the state-machine already supports `draft → upcoming | active`.

2. **`unit_id` uniqueness constraint.** Should the service enforce that a unit cannot have
   two `active` leases simultaneously? Currently there is no such check because PROP is
   not yet deployed. When PROP lands, an optional pre-write check
   (`query GSI2 for USER#...#STATUS#active` filtered by `unit_id`) should be added — but
   this would require a table scan or a third GSI. **Assumption for now:** the product
   enforces uniqueness at the UI layer (LSE-004); no DDB-level constraint is added.

3. **Currency validation.** `currency` is stored as a free-text ISO 4217 lowercase string
   with no enum validation. If multi-currency support with exchange rates is required in
   the future, a `Literal["usd", "cad", "gbp", "eur", ...]` enum should be added at the
   Pydantic model layer.

4. **`renewal_notice_days` default.** Defaulting to 30 days matches QUO-004. Some
   jurisdictions require 60 or 90 days notice — landlord must override per-lease.

5. **`late_fee_percent_bps` vs `late_fee_cents` mutual exclusivity.** The spec stores both
   fields always; validation that only one is non-zero when `late_fee_type` is set is left
   to the Pydantic model validator in LSE-002 (a `@model_validator(mode="after")` that
   checks the combination).
