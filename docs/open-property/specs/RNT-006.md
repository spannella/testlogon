**Ticket type:** Feature
**Priority:** P2

**Flag:** `RENT_LEDGER_ENABLED` (default OFF, shared across all RNT tickets)
**Depends on:** RNT-001 (rent-run timer, `post_rent_charge`, idempotency marker), RNT-002 (`record_payment`, `derive_charge_status`, `list_rent_ledger_for_lease`), RNT-003 (`list_rent_history`, `void_rent_row`), RNT-004 (`period_summary`, `list_periods`), RNT-005 (`charge_lease_now`, `run_rent_charges_for_owner`)

## 1. Summary & Goal

RNT-006 delivers the **React user interface and the complete test suite** for the rent-ledger
feature cluster. It is the final ticket in the RNT chain and assumes that all five earlier
tickets (RNT-001 through RNT-005) have been merged, meaning the backend service module
`app/services/rent_ledger.py` and the router `app/routers/rent_ledger.py` are fully
functional.

The deliverable has three distinct layers:

1. **TypeScript API layer** — types (`frontend/src/api/types.ts`) and endpoint wrappers
   (`frontend/src/api/endpoints/rent.ts`) that mirror the RNT-002/003/004/005 Pydantic
   models exactly.

2. **Frontend page** (`frontend/src/pages/rent/RentLedgerPage.tsx`) — a single-page
   layout with a **period navigator** (prev/next month via `list_periods`), a **portfolio
   summary bar** (charged/collected/outstanding/overdue from `period_summary`), a
   **per-lease rent table** with charge status badges, and three in-page dialogs: record
   payment, void row, and charge-now.

3. **Test suite** — a hermetic offline pytest module (`tests/test_rent_ledger.py`) that
   covers the entire RNT service layer end-to-end, plus a Playwright E2E spec
   (`frontend/e2e/rent-ledger.spec.ts`) that covers both the API surface and the UI.

The page is **entirely additive and flag-gated**: it degrades gracefully to a
"rent ledger not enabled" notice when the backend returns 404 (i.e., when
`RENT_LEDGER_ENABLED=0`). No existing page, route, or component is modified.

The page deliberately **does not include a card/payment-method selector** in the
record-payment dialog. Rent payments are *recorded* (cash, check, bank transfer —
informational), never charged. This is the open-property constraint
(`OPEN_PROPERTY_GAP_ANALYSIS.md` Headline; `RENT_LEDGER_TICKETS.md` §constraints 2 and 5).

## 4. API / Service Design

### 4.1 TypeScript types (`frontend/src/api/types.ts`)

Add the following interfaces at the end of the file (additive, no existing types modified):

```ts
// ─── Rent Ledger (RNT-001..RNT-005) ────────────────────────────────────────

export type RentChargeStatus = "open" | "partial" | "paid" | "overdue" | "voided";
export type RentPaymentMethod = "cash" | "check" | "bank_transfer" | "card_external" | "other";

  amount_cents: number;
  reason: string;

  rent_kind: "charge" | "payment";
  period: string;
  lease_id: string;
  method?: RentPaymentMethod;
  reference?: string;
  paid_on?: number;
  notes?: string;
  status?: RentChargeStatus;  // charge rows only; derived by derive_charge_status

export interface RentLedgerHistoryResp {
  rows: RentLedgerRow[];
  count: number;
  next_cursor: string | null;
}

export interface RentAging {
  current_cents: number;
  days_30_cents: number;
  days_60_cents: number;
  days_90_plus_cents: number;

export interface RentPeriodSummary {

  scope: string;              // lease_id | "all"

  collected_cents: number;

  overdue_cents: number;
  aging: RentAging | null;
  charge_count: number;
  paid_count: number;
  lease_count: number;
}

export interface RentPaymentInput {
  amount_cents: number;        // ge=1
  method: RentPaymentMethod;
  paid_on?: number;            // Unix ts; defaults to now server-side
  reference?: string;

  row: RentLedgerRow;
```

### 4.2 Endpoint wrappers (`frontend/src/api/endpoints/rent.ts`)

New file. All functions use the `api` singleton from `api/client.ts` with method shortcuts
(`api.get`, `api.post`) that already attach CSRF and auth headers.

```ts
import { api } from "@/api/client";
import type {
  RentLedgerHistoryResp,
  RentLedgerRow,
  RentPeriodSummary,
  RentPaymentInput,
  RecordPaymentResp,
  VoidRentRowResp,
  ChargeNowResp,
  RentRunResp,
} from "@/api/types";

// Per-lease paginated history (charges + payments)
export const listRentLedger = (
  leaseId: string,
  params?: { kind?: "charge" | "payment"; limit?: string; cursor?: string }
) =>
  api.get<RentLedgerHistoryResp>(
    `/ui/rent/leases/${leaseId}/ledger`,
    params as Record<string, string> | undefined
  );

// Charge rows only, each annotated with status
export const listLeaseCharges = (leaseId: string) =>
  api.get<{ rows: RentLedgerRow[] }>(`/ui/rent/leases/${leaseId}/charges`);

// Record a received payment (no card selector; method is informational)
export const recordPayment = (leaseId: string, body: RentPaymentInput) =>
  api.post<RecordPaymentResp>(`/ui/rent/leases/${leaseId}/payments`, body);

// Void a single ledger row (reversal, not deletion)
export const voidRentRow = (leaseId: string, ledgerSk: string, reason = "") =>
  api.post<VoidRentRowResp>(
    `/ui/rent/leases/${leaseId}/ledger/${encodeURIComponent(ledgerSk)}/void`,
    { reason }
  );

// Period summary (whole portfolio or scoped to one lease)
export const getRentSummary = (params?: { period?: string; lease_id?: string }) =>
  api.get<RentPeriodSummary>("/ui/rent/summary", params as Record<string, string> | undefined);

// Trailing N "YYYY-MM" strings for period navigation
export const listRentPeriods = (params?: { lease_id?: string; count?: string }) =>
  api.get<{ periods: string[] }>("/ui/rent/periods", params as Record<string, string> | undefined);

// On-demand charge for a single active lease
export const chargeLeaseNow = (leaseId: string, period?: string) =>
  api.post<ChargeNowResp>(`/ui/rent/leases/${leaseId}/charge`, { period });

// Owner-scoped rent run (caller's leases only)
export const runRentForOwner = (period?: string) =>
  api.post<RentRunResp>("/ui/rent/run", { period });
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Page layout — `frontend/src/pages/rent/RentLedgerPage.tsx`

The page is organized top-to-bottom:

1. **Period navigator** — a row with `<` / `>` buttons and the current period label
   (`"January 2026"` etc.) anchored to `selectedPeriod` state (defaults to `periods[0]` =
   current month). `listRentPeriods` is called once on mount; navigation updates
   `selectedPeriod` which drives the summary refetch.

2. **Summary bar** — four `Card` tiles showing `charged_cents`, `collected_cents`,
   `outstanding_cents`, `overdue_cents` from `getRentSummary({ period: selectedPeriod })`.
   Each tile uses a `Skeleton` while loading. The `aging` object, when non-null (OFB-015
   enabled), expands to a five-column sub-row showing current / 30 / 60 / 90+ day buckets.

3. **Per-lease table** — populated by `listRentLedger` with `useInfiniteQuery` keyed
   `["rent", "ledger", leaseId, selectedPeriod]`. Columns: Lease #, Tenant/Unit
   (degrades to plain `lease_id` if PROP/TEN labels are not yet available), Period,
   Charge (cents formatted as currency), Paid (sum of non-reversed `rent_payment` rows
   for the period), Status badge (see §5.2), Due day, Actions.

4. **Actions column** per charge row:
   - **Record payment** button → opens `RecordPaymentDialog` (§5.3).
   - **Void** button (trash icon) → opens `VoidConfirmDialog` (§5.4). Disabled when row
     is already `voided`.
   - **Charge now** button (per-lease, shown once in a "header" row) → calls
     `chargeLeaseNow`, toasts the `already_charged` outcome rather than erroring (§5.5).

5. **Run rent** button in the page header → calls `runRentForOwner({ period: selectedPeriod })`,
   toasts `"Charged ${charged} lease(s) for ${selectedPeriod}. ${skipped} already charged."`.

6. **Pagination** — `useInfiniteQuery` with `getNextPageParam: (last) => last.next_cursor ?? undefined`
   and a "Load more" button that calls `fetchNextPage` when `hasNextPage` is true.

### 5.2 Status badge mapping

`derive_charge_status` returns one of five values. These map to `StatusBadge` variants
(using the same `variant` type as `frontend/src/pages/billing/Ledger.tsx:33–46`):

| Status | Variant | Color | Label |
|---|---|---|---|
| `paid` | `success` | green | Paid |
| `partial` | `warning` | amber | Partial |
| `open` | `neutral` | grey | Open |
| `overdue` | `danger` | red | Overdue |
| `voided` | `neutral` | grey | Voided |

Payment rows (`rent_kind="payment"`) do not have a status field and render with no badge.
Reversed payment rows show `state="reversed"` in the row type column.

### 5.3 Record-payment dialog — `RecordPaymentDialog.tsx`

A modal `Dialog` containing a React Hook Form + Zod form with these fields:

```ts
const schema = z.object({
  amount_cents: z.number().int().min(1, "Amount must be at least 1 cent"),
  method: z.enum(["cash", "check", "bank_transfer", "card_external", "other"]),
  paid_on: z.number().optional(),        // date picker → unix ts
  reference: z.string().max(255).optional(),
  period: z.string().regex(/^\d{4}-\d{2}$/).optional(),  // defaults to selectedPeriod
  notes: z.string().max(1000).optional(),
});
```

There is **no card/payment-method selector** — the `method` field is an informational
enum. The dialog does not touch `frontend/src/api/endpoints/billing.ts`.

On submit: call `recordPayment(leaseId, body)` via `useMutation`. `onSuccess`:
- Invalidate `["rent", "ledger", leaseId]` and `["rent", "summary"]`.
- Close the dialog.
- Toast `"Payment of ${formatCents(amount_cents)} recorded for ${period}."`.

On 4xx error: surface the `detail` string in a form-level error message (no toast — errors
should stay visible while the form is open).

### 5.4 Void confirm dialog — `VoidConfirmDialog.tsx`

A small confirmation `AlertDialog` (shadcn/ui) with:
- Row summary: type, amount, period.
- Optional `reason` text input (max 255 chars).
- "Void entry" confirm button.

`useMutation` calling `voidRentRow(leaseId, row.sk, reason)`.

`onSuccess`:
- Invalidate `["rent", "ledger", leaseId]` and `["rent", "summary"]`.
- Close dialog.
- Toast `"Entry reversed. The row remains visible as voided."`.

`onError` for 409 `already_voided`: toast `"This entry is already voided."` without
re-throwing (the row was already in the correct terminal state).

The voided row **remains visible** in the table with `status="voided"` badge and
`state="reversed"`. It is never hidden or removed from the list — this is the
MONEY-SAFETY constraint from `RENT_LEDGER_TICKETS.md` §constraints 3.

### 5.5 Charge-now and run-rent — toast-on-skip behavior

Both `chargeLeaseNow` and `runRentForOwner` can return an `already_charged` skip
outcome (not an HTTP error — the backend returns 200 with `{ skipped: true, reason:
"already_charged" }`). The UI must:

- On `skipped: true` → toast `"Rent for ${period} was already charged for this lease."` (info level).
- On success with a new row → toast `"Rent charge of ${formatCents(row.amount_cents)} posted for ${period}."`.
- In both cases invalidate `["rent", "ledger", leaseId]` and `["rent", "summary"]`.

This matches the pattern used by the `run_rent_charges_for_owner` response shape which
returns `{ charged, skipped }` rather than an error.

### 5.6 Flag-off degradation

When `RENT_LEDGER_ENABLED=0`, every API call returns HTTP 404. `useQuery` and
`useMutation` surface errors through their `isError` state. The page should detect a 404
with `detail === "rent ledger not enabled"` (via `ApiError.status === 404`) and render an
`EmptyState` component with the message "Rent ledger is not enabled on this server" rather
than a generic error banner. This check is done in the query `onError` or via the
`error?.status` field on the query result.

### 5.7 Period navigator — boundary conditions

- `listRentPeriods` returns trailing N months ending at the current month. The `>` (next)
  button is disabled when `selectedPeriod` equals `periods[0]` (the current month — no
  future periods).
- The `<` (prev) button is disabled when `selectedPeriod` equals `periods[count-1]`
  (the oldest available period). To navigate further back the user can increase `count`
  (not a UI goal in this ticket — open question §10).
- Changing the period fires a new `getRentSummary` query and updates the `useInfiniteQuery`
  key for the ledger table, triggering a full refetch (the list is filtered to the new
  period server-side).

### 5.8 CSRF and auth

The `api` wrapper at `frontend/src/api/client.ts:179` attaches `X-CSRF-Token` from the
`ui_csrf` cookie on every non-GET. No manual header is set by any component in this page.
`Authorization: Bearer` is attached from `useAuthStore` at `client.ts:169`. Session
refresh on 401 is handled by `client.ts:205–215` transparently (the 401 branch is at
line 205; the refresh guard/retry is at lines 215–228).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no dev_mode branch in any RNT service

`RENT_LEDGER_TICKETS.md` §constraints 5 is absolute: no RNT service or router contains

### 7.2 MONEY-SAFETY summary for reviewers

Every monetary operation surfaces one or more of these three primitives and no others:

| Primitive | Location | Used for |
|---|---|---|
| `new_ledger_entry(...)` | `billing_shared.py:224` | Creating `rent_charge` / `rent_payment` rows |
| `settle_or_reverse_ledger(...)` | `billing_shared.py:262` | Void = reversal, never `delete_item` on a LEDGER row |
| `apply_balance_delta(...)` | `billing_shared.py:83` | Bumping / inverting `owed_settled_cents` / `payments_settled_cents` |

No Stripe/PayPal/CCBill SDK is imported by any RNT module.
No `delete_item` is ever called on a `LEDGER#` key.
No bespoke balance math exists in `rent_ledger.py` — all arithmetic is delegated.

### 7.3 Idempotency

- **Rent charge** — `post_rent_charge` writes a conditional-put marker under
  `pk="RENT_PERIOD#{user_sub}"`, `sk="LEASE#{lease_id}#PERIOD#{period}"` with
  `ConditionExpression="attribute_not_exists(pk)"` (RNT-001). A second call → 200 with
  `{ skipped: true }`, never a double charge.
- **Payment recording** — `record_payment` is idempotent-by-intent only (the landlord may
  record the same payment twice by mistake). The void path is provided to correct this.
  No automatic deduplication is applied; the landlord is responsible for accuracy.
- **Void** — `void_rent_row` pre-checks `state != "reversed"` before calling
  `settle_or_reverse_ledger`. A second void of the same row → 409 `already_voided`; the
  UI toasts a user-friendly message (§5.4) and does not re-throw.
- **`runRentForOwner`** — iterates `charge_lease_now` per active lease; each delegates to
  `post_rent_charge` and its marker. No double charges regardless of how many times the
  button is clicked.

### 7.4 Security — ownership isolation

All service functions call `get_lease(user_sub, lease_id)` as their first step, which
queries `T.leases` under `pk=USER#{user_sub}` — a lease belonging to another landlord is
simply not in that partition → 404, leaking nothing (constraint 8 of
`RENT_LEDGER_TICKETS.md`). The `void_rent_row` function additionally cross-checks that the
fetched ledger row's `extra.lease_id` matches the path parameter before voiding.

The `POST /ui/admin/rent/run` endpoint uses `Depends(require_root_session)` (delivered by
RNT-005); any non-root session receives 403. The E2E test for this endpoint (§9.2 section 5)
verifies this boundary explicitly.

## 8. Backward Compatibility & Migration

This ticket is purely additive:

- **No existing routes are modified.** The `/rent` route is new.
- **No existing DynamoDB tables are modified.** `T.billing` gains new row types
  (`rent_charge`, `rent_payment`) only when the flag is on and a charge/payment is
  recorded. The `BALANCE` row gains `owed_settled_cents` / `payments_settled_cents`
  increments, but those fields already exist and default to zero via `if_not_exists`.
- **No existing TypeScript types or API endpoint files are modified.** Types are added
  to the end of `types.ts`; `rent.ts` is a new file.
- **No existing Pydantic models are modified.** New models are additive in `models.py`.
- **No existing tests are impacted.** The new pytest module is standalone; no shared
  fixture is modified.
- **Flag-off behavior is unchanged.** With `RENT_LEDGER_ENABLED=0` (the default), no
  endpoint returns anything other than 404, no background loop starts, and no
  existing query pattern changes.

No DynamoDB table migration is needed. The new `RENT_PERIOD#` marker partition uses the
existing `T.billing` table with a new `pk` prefix; existing rows are unaffected.

## 10. Open Questions / Assumptions

1. **Lease list source for the per-lease table**: `RentLedgerPage` groups the ledger rows
   by `lease_id`. It does not have access to a flat list of leases independently of the
   ledger rows. **Assumption**: the per-lease table is built by grouping `listRentLedger`
   rows by `lease_id`, extracting the lease number and tenant/unit labels from the `extra`
   fields denormalized onto each row (RNT-001 constraint 8). If PROP/TEN labels are not yet
   available in those fields, the page degrades to showing `lease_id` directly.

2. **Sidebar link placement**: assumed to go near the billing section in `Sidebar.tsx`.
   Exact position relative to other open-property pages (once PROP/TEN/LSE frontend pages
   are built) is left to the UI polish pass.

3. **Flag-off E2E test strategy**: E2E section 6 requires the flag to be off. If the test
   environment always runs with `RENT_LEDGER_ENABLED=1`, these tests can use Playwright's
   `page.route` to intercept `/ui/rent/*` and return a mock 404 to test the UI degradation
   path. The backend authz path (§9.2 section 6) can be an integration test in the pytest
   suite instead (test 1 in §9.1 already covers this with `S.rent_ledger_enabled=False`).

4. **Period navigation depth**: `listRentPeriods` with default `count=12` returns 12 months.
   For landlords with older leases, the oldest visible period may not be far enough back.
   A future enhancement could add a date-picker fallback or increase the default count. This
   ticket uses count=12 (matching the trailing-12-month convention used by OFB-015 aging
   buckets).

5. **`run_rent_charges_for_owner` return shape**: the spec documents `{ charged, skipped }`.
   If the backend delivers a simpler `{ count: int }`, the toast message should be adjusted
   accordingly at implementation time.
