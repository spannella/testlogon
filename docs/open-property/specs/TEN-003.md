# TEN-003 — Tenant historical lease records (LSE integration) + router

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 2 days
**Flag:** `PROPERTY_TENANTS_ENABLED` (shared with TEN-001/002, default OFF)
**Depends on:** TEN-001 (entity, table, flag, `_require_enabled`), TEN-002 (PROFILE + INCOMEDOC service layer), LSE-001 (lease entity, `T.leases`, `S.leases_enabled`), LSE-002/003 (`list_leases_for_tenant`)

---

## 1. Summary & Goal

TEN-003 delivers two things:

1. **Lease-history read-projection** — a new service function
   `list_tenant_leases(owner_sub, tenant_id, *, cursor, limit)` in
   `app/services/property_tenant.py` that reads the tenant's historical leases from the
   **LSE lease cluster** without duplicating data in the `property_tenants` table, and
   degrades gracefully to an empty list when the LSE flag or cluster is absent.

2. **HTTP router** — `app/routers/property_tenant.py` (prefix `/ui/property/tenants`,
   tags `["property-tenants"]`) wiring the complete TEN surface (all of TEN-001 through
   TEN-003's service layer) into HTTP endpoints with flag-gating, auth, CSRF, Pydantic
   models, and route-order safety.

The gap analysis (`docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §B, line 54) marks
*"Tenant historical lease records"* as **MISSING** with the explicit qualifier *"depends on
Lease"*. This ticket closes that gap the moment the LSE cluster ships, while remaining safe
to deploy before LSE does (the graceful-degradation path returns an empty list rather than
an error).

### 2.3 Lease-history via LSE — no data re-storage

The LSE cluster stores each lease with a `tenant_id` attribute on the lease item. LSE-001
defines `T.leases` (`app/core/tables.py`, key `USER#{user_sub}` / `LEASE#{lease_id}`) with
a base-table partition query that supports `FilterExpression=Attr("tenant_id").eq(tenant_id)`.
LSE-003 (`docs/open-property/specs/LSE-003.md` §4.1) defines:

```python
def list_leases_for_tenant(
    user_sub: str,
    tenant_id: str,
    *,
    limit: int = 50,
    cursor: str | None = None,
) -> dict:
```

This function is the canonical read path: it queries the owner's lease partition, filters
by `tenant_id`, sorts by `start_date` descending, and returns a paged dict with
`{"leases": [...], "count": int, "next_cursor": str | None}`. Each lease item includes
`lease_id`, `unit_id`, `status`, `start_date`, `end_date`, `monthly_rent_cents`, and
`security_deposit_cents` — everything `TenantLeaseSummaryOut` needs.

TEN-003 does **not** store lease data on `property_tenants`. It delegates entirely to
`list_leases_for_tenant`, isolating the tenant cluster from the LSE schema.

### 2.7 Route-order caution — FastAPI first-match-wins

CLAUDE.md documents the "declare literal-segment routes before `/{id}` dynamic routes"
constraint: the audit-export router forced `/schedules` before `/{export_id}` to prevent
FastAPI capturing the literal `"schedules"` as a path parameter. The same constraint applies
here: literal sub-paths (`/profile`, `/income-docs`, `/active-unit`, `/leases`) must be
declared before `/{tenant_id}` in `app/routers/property_tenant.py`. LSE-003 §2.1 cites the
same constraint for `GET /ui/leases/expiring` before `GET /ui/leases/{lease_id}`.

### 2.8 Ownership isolation

All endpoints enforce `owner_id == ctx["user_sub"]`. Service functions scope reads to
`PK=TENANT#{tenant_id}` (single-row access) or `GSI_OWNER` (partitioned by `owner_id`).
A tenant whose `owner_id` differs from the caller's `user_sub` returns HTTP **404** (not
403), to avoid leaking the existence of another landlord's tenant — same security posture
as LSE-001 §7.3. See §10 question 3 for the rationale. (TEN-001 §7.4 says 403; TEN-003
deliberately overrides this to 404 for security — note the correction in §10 Q3 below.)

## 4. API / Service Design

### 4.1 New service function — `list_tenant_leases` in `app/services/property_tenant.py`

This is the only service-layer addition in TEN-003. All other service functions were
introduced by TEN-001 and TEN-002.

```python
def list_tenant_leases(
    owner_sub: str,
    tenant_id: str,
    *,
    cursor: Optional[str] = None,
    limit: int = 50,
) -> dict:
    """
    Returns lease summaries for a tenant, newest-first, from the LSE cluster.
    Degrades gracefully to {"leases": [], "count": 0, "next_cursor": None}
    when LSE is unavailable (flag off, module absent, or any runtime error).
    Never raises.
    """
```

**Algorithm:**

1. `_require_enabled()` — raises 503 if `property_tenants_enabled` is off.
2. Verify the tenant exists and belongs to the caller:
   `item = get_tenant(tenant_id)` — returns `None` if absent.
   If `item is None or item.get("owner_id") != owner_sub`: raise `HTTPException(404, "Tenant not found")`.
3. Attempt the LSE delegation inside a broad `try/except`:
   ```python
   try:
       from app.services.leases import list_leases_for_tenant
       if not S.leases_enabled:
           return {"leases": [], "count": 0, "next_cursor": None}
       return list_leases_for_tenant(owner_sub, tenant_id, cursor=cursor, limit=limit)
   except Exception:
       return {"leases": [], "count": 0, "next_cursor": None}
   ```
4. The `try/except` catches: `ImportError` (LSE not yet merged), `AttributeError` (T.leases
   absent), `S.leases_enabled` off (already handled by step 3's early return), and any
   DynamoDB runtime error. In every case the tenant cluster remains functional.
5. The lazy `from app.services.leases import list_leases_for_tenant` import is used (not a
   module-level import) to avoid `ImportError` at startup if LSE has not yet shipped.
   This mirrors the established lazy-import pattern for best-effort cross-cluster calls:
   `app/services/ec2_launcher.py` `_record_timeline` helper and the
   `app/services/ssh_bastion.py` SSH key manager import.

### 4.2 Router — `app/routers/property_tenant.py`

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behavior

With `PROPERTY_TENANTS_ENABLED=0` (the default), every handler in
`app/routers/property_tenant.py` returns `HTTP 503 {"detail": "Property tenants are not
enabled"}` before any service call is made. No DynamoDB reads or writes occur. The
`property_tenants` table may or may not exist; with the flag off it is never accessed.
The LSE table is also never touched.

### 5.2 Lease-history graceful degradation

`list_tenant_leases` degrades in these scenarios:

| Condition | Behavior |
|---|---|
| `S.leases_enabled = False` | Returns `{"leases": [], "count": 0, "next_cursor": None}` |
| `app.services.leases` not importable (`ImportError`) | Returns empty list — caught by `try/except` |
| `list_leases_for_tenant` raises any exception (DDB error, network) | Returns empty list — caught by `try/except` |
| LSE running, `tenant_id` has no leases | `list_leases_for_tenant` returns empty list normally |
| Both LSE and TENANTS flags are on | Full lease history returned, cursor-paginated |

The router endpoint (row 11) serializes the result via `TenantLeaseListOut` regardless of
source. An empty list is a valid 200 response, never a 404 or 503.

### 5.3 Multipart income-doc upload (`POST …/income-docs`)

The endpoint signature:

```python
@router.post("/{tenant_id}/income-docs", status_code=201)
def upload_income_doc(
    tenant_id: str,
    file: UploadFile = File(...),
    doc_kind: str = Form(...),
    ctx: dict = Depends(require_ui_session),
):
```

`doc_kind` is a `Form(...)` field (not JSON body) because multipart requests cannot mix
JSON and file upload in the same body without FastAPI's `Form` + `File` pattern (established
at `app/routers/filemanager.py:1809`). Validation: `doc_kind` must be one of
`{"pay_stub", "tax_return", "bank_statement", "offer_letter", "other"}` — raise
`HTTPException(422, "Invalid doc_kind")` on an unrecognized value before calling the service.

The handler calls `tenant_svc.add_income_doc(owner_sub, tenant_id, file=file, doc_kind=doc_kind)`.
The service calls `upload_file(owner_sub, f"Tenant Documents/{tenant_id}/{file.filename}", file)`,
stores the returned record-link in a `INCOMEDOC#{doc_id}` row, and returns the metadata dict.

### 5.4 Ownership isolation at the router layer

Every endpoint that reads or mutates a specific tenant performs:

```python
item = tenant_svc.get_tenant(tenant_id)
if item is None:
    raise HTTPException(404, "Tenant not found")
_own_or_404(item, ctx["user_sub"])  # raises 404 (not 403) for wrong owner — §10 Q3
```

This is the router-layer ownership check. TEN-001 §7.4 originally said 403 for wrong-owner; TEN-003 uses 404 instead (security posture: do not reveal the existence of another landlord's tenant). The helper is named `_own_or_404`, not `_own_or_403`. The service functions themselves do not enforce this check (they accept `tenant_id` as an opaque argument), so the router must do it before any mutation.

For `list_tenants`, ownership is enforced structurally: the service queries `GSI_OWNER`
with `owner_id = ctx["user_sub"]`, so a landlord can only ever see their own tenants.

For `list_tenant_leases`, the service delegates to `list_leases_for_tenant(owner_sub, ...)`,
which partitions the `T.leases` query on `USER#{owner_sub}` — another landlord's leases are
in a different DynamoDB partition and are never returned.

### 5.5 PATCH `/{tenant_id}` — unknown field rejection

If `UpdateTenantIn` fields are all `None` (empty patch), the router raises
`HTTPException(400, "Nothing to update")` before calling `update_tenant`, matching the
TEN-001 §5.6 `ValueError("Nothing to update")` convention.

### 5.6 `PUT …/active-unit` — PROP unit validation

`set_active_unit(tenant_id, unit_id)` in TEN-002 validates the unit against the PROP unit
service. If PROP is not yet deployed, the call degrades (same lazy-import + `try/except`
pattern as `list_tenant_leases`). The router does not perform its own unit validation; it
relies entirely on the TEN-002 service. A missing or invalid `unit_id` raises
`HTTPException(404, "Unit not found")` from the service, which propagates naturally.

### 5.7 `GET …/leases` cursor parameter validation

`cursor` from the query string is passed directly to `list_tenant_leases`, which passes it
to `decode_cursor(cursor)` (`app/core/cursor.py:103`). An invalid/tampered cursor silently
decodes to `None` (the cursor library's behavior, per `cursor.py:112-123`), which
effectively starts a fresh page. This is the same tolerance applied to all other cursor-
paginated endpoints in the codebase.

### 5.8 `DELETE …/income-docs/{doc_id}` — 204 on missing doc

If `doc_id` does not exist for the tenant, `remove_income_doc` in TEN-002 is a no-op
(delete-idempotent). The router returns `204 No Content` regardless of whether the row
existed, matching the HTTP semantics for DELETE on a resource that may already be absent.

### 5.9 Decimal coercion in lease summaries

Lease items from `T.leases` contain DynamoDB `Decimal` types for numeric attributes.
`_item_to_lease_summary(item)` must coerce these to `int` before constructing
`TenantLeaseSummaryOut`. The pattern is `int(item.get("monthly_rent_cents", 0))`,
matching `_serialize` in LSE-002 §4.1 and the `_clean_lek` helper at
`app/services/invoices.py:65-79` (Decimal→int coercion logic is at lines 72-79;
the function is named `_clean_lek`, not `_coerce_decimals` — same correction made in
LSE-002 §12 entry 22).

To exercise the full lease-history endpoint, both `PROPERTY_TENANTS_ENABLED=1` and
`LEASES_ENABLED=1` must be set. Setting only `PROPERTY_TENANTS_ENABLED=1` returns an
empty lease list (not an error) — the endpoint is functional and the frontend can render
a "No lease history" empty state cleanly.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no `S.dev_mode` branch

`app/routers/property_tenant.py` and the `list_tenant_leases` addition to
`app/services/property_tenant.py` contain no `if S.dev_mode:` branch. All DynamoDB access
flows through `T.property_tenants` and (lazily) `T.leases` via the `_FloatSafeTable` proxy
(`app/core/tables.py:29-62`), which is identical in dev (DynamoDB Local, port 8001) and
prod (real DynamoDB endpoint). The `/mock/s3/...` dev URL for income-doc downloads is
injected entirely within `app/services/filemanager.py:upload_file` — the tenant service and
router are agnostic to the storage environment. This is the same posture as TEN-001 §7.1,
TEN-002 §7.1, and every other open-property service.

### 7.2 Money-safety — no financial path in TEN-003

TEN-003 has no financial surface. The `GET …/leases` endpoint reads lease items from the
LSE cluster, which carry `monthly_rent_cents` and `security_deposit_cents` as
**informational integers only** (LSE-001 §5.8). These values are projected into
`TenantLeaseSummaryOut` as read-only display fields. TEN-003 makes no calls to:
- `billing_shared.new_ledger_entry` (`billing_shared.py:224`)
- `billing_shared.settle_or_reverse_ledger` (`billing_shared.py:262`)
- `billing_shared.compute_due` (`billing_shared.py:158`)
- `billing_shared.apply_balance_delta` (`billing_shared.py:121`)
- Any Stripe, PayPal, or CCBill endpoint

Rent charges and deposit accounting belong exclusively to the RNT rent-ledger cluster
(RNT-001..006). Any future modification that adds financial writes to this router MUST route
every monetary row through `new_ledger_entry` and all voids through `settle_or_reverse_ledger`
(reversal by state transition, never deletion), as required by the TEN cross-cutting
constraints in `docs/open-property/TENANTS_TICKETS.md` §3.

### 7.3 Idempotency

The `POST /ui/property/tenants` endpoint calls `create_tenant`, which uses a conditional
`put_item` with `attribute_not_exists(PK)` (TEN-001 §4.1 §5.1). Replaying the same
`correlation_id` returns the existing tenant with `201` or `200` (the service returns the
existing item on `ConditionalCheckFailedException`; the router sets `status_code=201`
uniformly since the item either was just created or already existed with identical content).
Callers that need idempotent creates should supply `correlation_id`.

`PUT …/profile` is read-merge-write (TEN-002 §4.3): passing the same profile data twice
produces the same DynamoDB item. `PUT …/active-unit` with the same `unit_id` is a no-op
at the DDB conditional-write level (TEN-002's `set_active_unit` checks current value).

### 7.4 Authorization hardening

- All endpoints use `Depends(require_ui_session)` from `app/services/sessions`
  (`app/routers/contacts.py:12` import pattern).
- Non-GET endpoints require the `x-csrf-token` header (standard cookie-auth CSRF rule, CLAUDE.md).
- Ownership is double-checked at the router layer (`_own_or_404`) before any mutation,
  even if the service function would also isolate by partition. Returns 404 (not 403) for
  wrong-owner — §10 Q3.
- `tenant_id` in path parameters is an opaque hex string. No SQL injection or path
  traversal is possible; DynamoDB key lookups are parameterized.
- The `doc_kind` `Form` field is validated against an explicit allowlist
  (`{"pay_stub", "tax_return", "bank_statement", "offer_letter", "other"}`) before the
  service call, preventing junk values from reaching the `INCOMEDOC#` row.

### 7.5 Input size limits

`UploadFile` for income docs is not explicitly size-limited by this router (the existing
filemanager handles storage). A future ticket should add a `Content-Length` guard if large
document uploads become a concern. The emergency-contact list cap (5 entries) is enforced
by TEN-002's `update_profile` service before the DynamoDB write.

## 10. Open Questions / Assumptions

1. **LSE `tenant_id` FK direction.** This spec assumes the LSE lease item carries a `tenant_id`
   attribute matching the TEN `tenant_id` value (an opaque string FK from LSE into TEN). This
   is stated in LSE-001 §3.2 and LSE-003 §4.1. If LSE uses a different FK field name, the
   `list_leases_for_tenant` `FilterExpression` must be updated. **Assumption:** `tenant_id` is
   the correct attribute name on the LSE lease item.

2. **Owner sub as the `user_sub` for LSE partition key.** `list_leases_for_tenant(owner_sub,
   tenant_id)` queries `PK=USER#{owner_sub}` in the `leases` table. This assumes the landlord
   who owns the tenant also owns the leases (same `user_sub`). If a property management company
   uses a shared service account for leases but per-PM accounts for tenant management, this
   partition alignment breaks. **Assumption:** for the initial rollout, one landlord = one
   `user_sub` across both TEN and LSE.

3. **`GET …/{tenant_id}` ownership: 404 vs 403.** The spec returns **404** for both "not
   found" and "wrong owner" to avoid leaking the existence of another landlord's tenants —
   same security posture as LSE-001 §7.3 `get_lease` returning `None` for foreign-owner
   items. The ownership helper is named `_own_or_404` (corrected from the earlier
   `_own_or_403` draft; TEN-001 §7.4 says 403 but this spec uses 404 for the security
   reason above — callers from TEN-004 always own their own tenants and will never see the
   difference). **Resolution:** 404 for both cases. `_own_or_404` raises
   `HTTPException(404, "Tenant not found")`. `list_tenant_leases` step 2 also raises 404
   (not 403) for wrong owner, making all endpoints consistent.

4. **Lease-history pagination on the tenant profile page.** `TEN-004`'s lease-history section
   is described as a "read-only table" — it may or may not implement cursor pagination in the
   UI. The API supports pagination (`cursor`/`limit` params) regardless; the frontend can
   ignore `next_cursor` and limit to the first 50 for a simple read-only panel. If tenants
   accumulate many leases (e.g., long-term tenants with month-to-month renewals tracked as
   separate leases), pagination becomes important. **Assumption:** TEN-004 implements a "Load
   more" link for the lease-history section.

5. **`doc_kind` validation in service vs router.** Currently `doc_kind` validation is
   specified at the router layer (§5.3). Moving it into TEN-002's `add_income_doc` service
   function would be more defensive but requires modifying TEN-002's already-defined
   interface. **Assumption:** router-layer validation is sufficient for this ticket; a future
   improvement can push it to the service.
