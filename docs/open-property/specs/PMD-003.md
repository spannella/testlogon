**Ticket type:** Feature
**Priority:** P1
**Estimate:** 3 d
**Flag:** `PROPERTY_DASHBOARD_ENABLED` (default OFF; shared master flag for the PMD cluster)
**Depends on:** PMD-001 (rent-policy entity + `get_policy`), PROP-003 (`list_properties`/`compute_property_occupancy`), LSE-002 (`list_leases(status="active")`), LSE-003 (`list_upcoming_expirations`)

## 1. Summary & Goal

PMD-003 delivers a **read-only KPI aggregation service** for a landlord's property portfolio, mirroring the in-memory bucketing and ledger-scan strategy of `app/services/platform_financial_dashboard.py` (module docstring §"Aggregation strategy") but scoped to the **rent-roll view** rather than platform GMV/revenue. The gap analysis (`docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §A rows 4–5) marks **Portfolio KPIs** and **Monthly rent snapshot** as MISSING precisely because `platform_financial_dashboard` is merchant revenue, not a landlord's rent ledger — the two share zero entry types.

Three aggregation surfaces are introduced:

1. **`compute_kpis(owner_sub)`** — four headline KPIs: `occupancy_rate`, `active_lease_count`, `outstanding_rent_cents`, `open_work_order_count`.
2. **`monthly_rent_snapshot(owner_sub, year, month)`** — rent-ledger bucketing for a calendar month into `collected_cents`, `outstanding_cents`, `overdue_cents`, `charged_cents`.
3. **`priority_items(owner_sub, limit)`** — upcoming lease expirations and open work orders/tickets requiring attention.

A fourth surface, a **`portfolio_summary` dashlet provider**, is registered in `app/services/crm_dashlet_data.py` (introduced by RPT-007, `docs/suitecrm/specs/RPT-007.md` §4.1) so the KPI dict is reachable from the RPT-006/007 configurable dashboard.

PMD-003 is **purely read-only**: it writes nothing to any DynamoDB table and calls no payment provider. All monetary figures come from the existing billing ledger (`T.billing`) via `billing_shared.compute_due` and the rent-charge entry scan pattern (`app/services/billing_shared.py:158,224`). No new DynamoDB table is introduced.

## 3. Data Model

### 3.1 No new DynamoDB tables

PMD-003 introduces **zero new DynamoDB tables and zero new DynamoDB writes**. All data is read from existing tables:

| Source table | Handle | Access pattern |
|---|---|---|
| `T.billing` | `app/core/tables.py` (from billing cluster) | Per-owner ledger scan: `pk = USER#{owner_sub}`, `begins_with(sk, "LEDGER#")` + `ledger_date` prefix filter |

| `T.rent_policy` | `app/core/tables.py` (PMD-001) | Via `rent_policy.get_policy(owner_sub)` — point read |

Because PMD-003 is read-only, **no `attr_types` declarations** are introduced in `scripts/local-ddb-init.py`. The `attr_types` for numeric GSI keys on `T.leases` (`GSI1SK`, `GSI2SK`) are already declared by LSE-001 (`docs/open-property/specs/LSE-001.md` §3.4).

### 3.2 Ledger entry types consumed

PMD-003 reads the following `type` values from `T.billing` ledger rows, introduced by the RNT cluster (`docs/open-property/RENT_LEDGER_TICKETS.md` §"Cross-cutting constraints"):

| `type` value | `state` values observed | Meaning | PMD-003 bucket |
|---|---|---|---|
| `rent_charge` | `"settled"` | Monthly rent charge posted by rent-run | charged + outstanding (if unpaid) |
| `rent_payment` | `"settled"` | Landlord-recorded payment against a charge | collected |
| `rent_charge` | `"reversed"` | Voided charge (via `settle_or_reverse_ledger`) | excluded from all buckets |
| `rent_payment` | `"reversed"` | Voided payment | excluded from all buckets |

A row whose `state == "reversed"` is always excluded regardless of type — the reversal was written by `settle_or_reverse_ledger` at `billing_shared.py:262`. PMD-003 applies this filter before bucketing.

#### `_iter_owner_rent_ledger(owner_sub: str, ledger_date_prefix: Optional[str] = None) -> Iterator[Dict[str, Any]]`

Private generator. Queries `T.billing` with `KeyConditionExpression: pk.eq("USER#{owner_sub}") & sk.begins_with("LEDGER#")`, paginating via `LastEvaluatedKey` (mirrors `platform_financial_dashboard._scan_ledger_entries` at `:161–191` and `csv_export._iter_billing_entries` at `:52–87`). When `ledger_date_prefix` is provided (e.g. `"2025-03"`), applies a `FilterExpression: begins_with(ledger_date, :prefix)` client-side filter after fetching each page — DynamoDB `FilterExpression` does not reduce page size (CLAUDE.md gotcha), so the loop always drains `LastEvaluatedKey`. Caps at `S.portfolio_kpi_max_ledger_scan_pages` pages to prevent unbounded scans. Yields only rows with `type` in `{_RNT_CHARGE_TYPE, _RNT_PAYMENT_TYPE}` and `state != "reversed"`.

```python
def _iter_owner_rent_ledger(
    owner_sub: str,
    *,
    ledger_date_prefix: Optional[str] = None,
    max_pages: Optional[int] = None,
) -> Iterator[Dict[str, Any]]:
    from boto3.dynamodb.conditions import Key, Attr
    from app.core.tables import T

    pk_val = f"USER#{owner_sub}"
    max_p = max_pages or _to_int(getattr(S, "portfolio_kpi_max_ledger_scan_pages", 50)) or 50
    kwargs: Dict[str, Any] = {
        "KeyConditionExpression": Key("pk").eq(pk_val) & Key("sk").begins_with("LEDGER#"),
    }
    if ledger_date_prefix:
        kwargs["FilterExpression"] = Attr("ledger_date").begins_with(ledger_date_prefix)
    page = 0
    while True:
        resp = T.billing.query(**kwargs)
        for item in resp.get("Items", []):
            t = str(item.get("type", ""))
            s = str(item.get("state", ""))
            if t in (_RNT_CHARGE_TYPE, _RNT_PAYMENT_TYPE) and s != "reversed":
                yield item
        lek = resp.get("LastEvaluatedKey")
        page += 1
        if not lek or page >= max_p:
            break
        kwargs["ExclusiveStartKey"] = lek
```

#### `compute_kpis(owner_sub: str) -> Dict[str, Any]`

Returns the four headline KPIs. Each sub-computation is wrapped in a `try/except` that catches all exceptions and returns a safe zero-value — a missing cluster (PROP not yet deployed, RNT not yet deployed, WOV not yet deployed) degrades to `0`/`0.0` rather than 500-ing.

```python
def compute_kpis(owner_sub: str) -> Dict[str, Any]:
    _require_enabled()

    # 1. Occupancy
    occupancy_rate = 0.0
    unit_count = 0
    occupied_units = 0
    try:
        from app.services import property_mgmt as _pm
        if _pm._flag_on():
            rollup = _pm.portfolio_occupancy_rollup(owner_sub)
            if rollup:
                unit_count = _to_int(rollup.get("unit_count"))
                occupied_units = _to_int(rollup.get("occupied"))
                occupancy_rate = float(rollup.get("occupancy_rate", 0.0))
    except Exception:
        pass

    # 2. Active lease count
    active_lease_count = 0
    try:
        from app.services import leases as _lse
        if getattr(S, "leases_enabled", False):
            cursor = None
            while True:
                page = _lse.list_leases(owner_sub, status="active", limit=200, cursor=cursor)
                if not page:
                    break
                active_lease_count += len(page.get("leases", []))
                cursor = page.get("next_cursor")
                if not cursor:
                    break
    except Exception:
        pass

    # 3. Outstanding rent (BALANCE row fast path; falls back to ledger scan)
    outstanding_rent_cents = 0
    try:
        from app.core.tables import T
        from app.services.billing_shared import user_pk, compute_due
        balance_item = T.billing.get_item(
            Key={"pk": user_pk(owner_sub), "sk": "BALANCE"}
        ).get("Item")
        if balance_item:
            due = compute_due(balance_item)
            outstanding_rent_cents = max(0, _to_int(due.get("due_settled_cents")))
        else:
            # Fallback: sum unsettled rent_charge rows
            for item in _iter_owner_rent_ledger(owner_sub):
                if str(item.get("type")) == _RNT_CHARGE_TYPE:
                    outstanding_rent_cents += _to_int(item.get("amount_cents"))
    except Exception:
        pass

    # 4. Open work-order count (WOV primary; ticket fallback)
    open_work_order_count = 0
    try:
        from app.services import work_orders as _wov
        if getattr(S, "work_orders_enabled", False):
            open_work_order_count = _wov.count_open_work_orders(owner_sub)
    except Exception:
        # WOV fallback: property-linked tickets in open-family statuses
        try:
            from app.services.tickets import TicketStore
            from app.core.tables import T
            store = TicketStore()
            result = store.list_tickets(owner_sub, limit=500)
            tickets = result.get("tickets", []) if result else []
            for t in tickets:
                if str(t.get("status", "")) in _OPEN_STATUSES:
                    open_work_order_count += 1
        except Exception:
            open_work_order_count = 0

    return {
        "occupancy_rate": occupancy_rate,
        "unit_count": unit_count,
        "occupied_units": occupied_units,
        "active_lease_count": active_lease_count,
        "outstanding_rent_cents": outstanding_rent_cents,
        "open_work_order_count": open_work_order_count,
        "computed_at": now_ts(),
    }
```

#### `monthly_rent_snapshot(owner_sub: str, *, year: int, month: int) -> Dict[str, Any]`

Scans the owner's billing ledger filtered to `ledger_date` prefix `YYYY-MM`, buckets into four totals, and derives `overdue_cents` using the PMD-001 rent policy.

```python
def monthly_rent_snapshot(owner_sub: str, *, year: int, month: int) -> Dict[str, Any]:
    _require_enabled()

    if not (1 <= month <= 12):
        raise HTTPException(status_code=422, detail="month must be 1–12")
    if year < 2000:
        raise HTTPException(status_code=422, detail="year must be >= 2000")

    prefix = f"{year:04d}-{month:02d}"

    # Fetch overdue threshold from PMD-001 policy
    rent_due_day = 1
    grace_period_days = 0
    try:
        from app.services import rent_policy as _rp
        if _rp._flag_on():
            policy = _rp.get_policy(owner_sub)
            rent_due_day = int(policy.get("rent_due_day", 1))
            grace_period_days = int(policy.get("grace_period_days", 0))
    except Exception:
        pass

    # Overdue threshold: a rent_charge posted in this month is overdue if
    # now > last day of `prefix` month + grace_period_days
    # (a simple heuristic: once we are past the due window in the SAME calendar
    # month, all unsettled charges for that month are overdue)
    from datetime import datetime, timezone, timedelta
    import calendar as _calendar
    last_day = _calendar.monthrange(year, month)[1]
    due_ts = datetime(year, month, min(rent_due_day, last_day),
                      tzinfo=timezone.utc).timestamp() + grace_period_days * 86400
    now = now_ts()

    charged_cents = 0
    collected_cents = 0
    outstanding_cents = 0
    overdue_cents = 0

    for item in _iter_owner_rent_ledger(owner_sub, ledger_date_prefix=prefix):
        amount = _to_int(item.get("amount_cents"))
        item_type = str(item.get("type", ""))
        item_ts = _to_int(item.get("ts"))

        if item_type == _RNT_CHARGE_TYPE:
            charged_cents += amount
            # Check if this charge has been settled by a matching payment
            # The payment state on the charge row itself is not stored; instead
            # we rely on `state` of the charge row:
            #   state="settled"  → charge recognized (owed)
            #   A separate rent_payment row records the collection
            # Outstanding = charges with no matching payment collected this month
            # We approximate: if sum(rent_payment) < sum(rent_charge) for the
            # month, the difference is outstanding. Overdue = outstanding &&
            # past the grace window.
            outstanding_cents += amount  # will net off payments below

        elif item_type == _RNT_PAYMENT_TYPE:
            collected_cents += amount
            outstanding_cents -= amount  # net off against charges

    # Clamp outstanding to >= 0 (payments can exceed charges in edge cases)
    outstanding_cents = max(0, outstanding_cents)

    # Overdue = unpaid portion past the grace window
    # Only mark overdue if we are past the due+grace date for this month
    if now > due_ts and outstanding_cents > 0:
        overdue_cents = outstanding_cents

    return {
        "year": year,
        "month": month,
        "charged_cents": charged_cents,
        "collected_cents": collected_cents,
        "outstanding_cents": outstanding_cents,
        "overdue_cents": overdue_cents,
        "rent_due_day": rent_due_day,
        "grace_period_days": grace_period_days,
        "computed_at": now_ts(),
    }
```

#### `priority_items(owner_sub: str, *, limit: int = 20) -> Dict[str, Any]`

Returns the union of upcoming lease expirations and open work orders/tickets, sorted by urgency (soonest expiration / most-recently-updated ticket first), capped at `limit`.

```python
def priority_items(owner_sub: str, *, limit: int = 20) -> Dict[str, Any]:
    _require_enabled()
    limit = max(1, min(int(limit), 100))

    upcoming_expirations = []
    try:
        from app.services import leases as _lse
        if getattr(S, "leases_enabled", False):
            result = _lse.list_upcoming_expirations(owner_sub, within_days=60)
            # list_upcoming_expirations returns list[dict] (LSE-003 §4.1:212), not a dict
            if result:
                for lse in result:
                    upcoming_expirations.append({
                        "kind": "lease_expiring",
                        "lease_id":   lse.get("lease_id"),
                        "lease_number": lse.get("lease_number"),
                        "unit_id":    lse.get("unit_id"),
                        "property_id": lse.get("property_id"),
                        "tenant_id":  lse.get("tenant_id"),
                        "end_date":   _to_int(lse.get("end_date")),
                        "monthly_rent_cents": _to_int(lse.get("monthly_rent_cents")),
                    })
        # Sort by end_date ascending (soonest first)
        upcoming_expirations.sort(key=lambda x: x["end_date"])
    except Exception:
        upcoming_expirations = []

    open_work_orders = []
    try:
        from app.services import work_orders as _wov
        if getattr(S, "work_orders_enabled", False):
            wos = _wov.list_open_work_orders(owner_sub, limit=limit)
            for wo in (wos or []):
                open_work_orders.append({
                    "kind": "open_work_order",
                    "work_order_id": wo.get("work_order_id"),
                    "title":   wo.get("title"),
                    "status":  wo.get("status"),
                    "priority": wo.get("priority"),
                    "property_id": wo.get("property_id"),
                    "updated_at": _to_int(wo.get("updated_at")),
                })
    except Exception:
        # WOV fallback: open-family tickets
        try:
            from app.services.tickets import TicketStore
            store = TicketStore()
            result = store.list_tickets(owner_sub, limit=limit)
            for t in (result.get("tickets", []) if result else []):
                if str(t.get("status", "")) in _OPEN_STATUSES:
                    open_work_orders.append({
                        "kind": "open_ticket",
                        "ticket_id": t.get("ticket_id"),
                        "subject":   t.get("subject"),
                        "status":    t.get("status"),
                        "updated_at": _to_int(t.get("updated_at")),
                    })
        except Exception:
            open_work_orders = []

    # Interleave: alternate expiration/WO entries up to limit
    combined = (upcoming_expirations + open_work_orders)[:limit]

    return {
        "upcoming_expirations": upcoming_expirations[:limit],
        "open_work_orders":     open_work_orders[:limit],
        "items":                combined,
        "count":                len(combined),
    }
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Graceful degradation when upstream clusters are absent

Each of the four KPI sub-computations is wrapped independently in `try/except Exception`. When a cluster is not yet deployed:

| Missing cluster | KPI impact | Fallback value |
|---|---|---|
| PROP (`property_mgmt.py`) | `occupancy_rate`, `unit_count`, `occupied_units` | All `0` / `0.0` |
| LSE (`leases.py`) | `active_lease_count`, `upcoming_expirations` | `0` / `[]` |
| RNT (`T.billing` rent rows) | `outstanding_rent_cents` | `0` (BALANCE row absent → ledger scan returns no rent-type rows → `0`) |
| WOV (`work_orders.py`) | `open_work_order_count` | Ticket fallback (see §5.2); if that also fails, `0` |

An owner who has no properties at all returns: `{"occupancy_rate": 0.0, "unit_count": 0, "occupied_units": 0, "active_lease_count": 0, "outstanding_rent_cents": 0, "open_work_order_count": 0}`. This is a valid response — not an error.

### 5.2 Work-order fallback (ticket system)

Until the WOV cluster (`WORKORDERS_VENDORS_TICKETS.md`) is deployed, PMD-003 falls back to `TicketStore.list_tickets(owner_sub)` from `app/services/tickets.py:614`, filtering for `status in {"open", "in_progress", "waiting_on_user"}` (matching `_DEFAULT_BOARD_COLUMNS` at `tickets.py:61-66`). The fallback returns `open_work_order_count` as the count of those open-family tickets. The `kind` field in `priority_items` is `"open_ticket"` (not `"open_work_order"`) in the fallback path so the frontend can distinguish the two.

### 5.3 `monthly_rent_snapshot` reconciliation invariant

The four buckets satisfy: `collected_cents + outstanding_cents == charged_cents` (within rounding). `overdue_cents <= outstanding_cents` always. If payments exceed charges in a given month (pre-payment), `outstanding_cents` is clamped to `0` and `collected_cents` may exceed `charged_cents` — this is recorded faithfully and is not an error.

### 5.4 `outstanding_rent_cents` — BALANCE row vs. ledger scan

The fast path reads the `BALANCE` row (`sk="BALANCE"`) from `T.billing` for the owner's partition and calls `billing_shared.compute_due` at `:158`. The `due_settled_cents` value (`owed_settled - payments_settled`) represents total rent owed across all time. The fallback (no BALANCE row) sums all `rent_charge` ledger rows minus `rent_payment` rows — this is correct but O(n) in the number of ledger entries. The BALANCE row is populated and maintained by the RNT `apply_balance_delta` calls (`billing_shared.py:83`); before RNT lands, the BALANCE row is absent and the fallback is used.

### 5.5 Overdue threshold computation

A `rent_charge` row for month `YYYY-MM` is overdue when all of the following hold:
1. The charge row has no matching `rent_payment` covering it (i.e., `outstanding_cents > 0`).
2. `now_ts() > last_day_of_month_ts + grace_period_days * 86400` where `last_day_of_month_ts` is the Unix timestamp of the last day of the query month at midnight UTC plus `grace_period_days`.
3. The `rent_due_day` from PMD-001's `get_policy(owner_sub)` falls before the last day of the month (it is always <= 28 per PMD-001 §5.2, so this holds for all months).

For the **current month**, overdue computation returns `0` until the grace window has elapsed — a rent charge posted on the 1st of March is not overdue on the 5th of March if `grace_period_days=5`.

### 5.6 `priority_items` — open-ended leases excluded

`list_upcoming_expirations` (LSE-003, `docs/open-property/specs/LSE-003.md` §2.1) queries GSI2 (`GSI2SK = end_date`, sparse) — open-ended leases have no `GSI2SK` and are therefore absent from the GSI. They never appear in the expiration priority list. This is the correct behavior.

### 5.7 `priority_items` — `limit` semantics

`limit` caps each sub-list independently: up to `limit` items from `upcoming_expirations` and up to `limit` items from `open_work_orders`. The combined `items` list contains up to `limit` items total (first N from either list). Frontend callers that want separate pagination should call the lists independently and implement their own merge.

### 5.8 Dashlet double-flag guard

The `portfolio_summary` dashlet is reachable via `GET /ui/crm/dashboard/dashlets/{dashlet_id}/data` only when BOTH `CRM_REPORTS_ENABLED=true` AND `PROPERTY_DASHBOARD_ENABLED=true`. The outer RPT-007 router checks `S.crm_reports_enabled` (→ 404). The `_provider_portfolio_summary` function checks `S.property_dashboard_enabled` and raises `ValueError("unknown_dashlet_type")` when off, which RPT-007's handler converts to **HTTP 422** (`docs/suitecrm/specs/RPT-007.md` §5.8 and router code: `if code in ("unknown_dashlet_type", "report_id_required"): raise HTTPException(status_code=422, detail=code)`). The dashlet configuration can be saved with `dashlet_type="portfolio_summary"` by RPT-006 regardless of the property flag (the config row is just data); the 422 is only thrown at data-read time.

### 5.9 `FilterExpression` does not reduce page size

All ledger scans loop via `LastEvaluatedKey` regardless of the number of items returned per page. The `_iter_owner_rent_ledger` generator continues until DynamoDB returns no `LastEvaluatedKey` OR `max_pages` is hit. This matches the explicit CLAUDE.md gotcha and the `platform_financial_dashboard._scan_ledger_entries` implementation at `:161–191`.

### 5.10 `asyncio.to_thread` wrapping

Every handler wraps the service call in `asyncio.to_thread`. The service functions are synchronous (boto3 is a blocking SDK). This prevents the event loop from stalling during large ledger scans. `asyncio.to_thread` is the correct pattern for blocking work in FastAPI/uvicorn async handlers, matching the pattern in `app/routers/google_drive_integration.py`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no `if S.dev_mode` branch

`app/services/portfolio_dashboard.py` contains zero `if S.dev_mode:` branches. The single code path uses `T.billing`, `T.properties`, `T.leases`, `T.tickets`, and `T.rent_policy` — all boto3 resource handles that are intercepted by moto in dev and hit real DynamoDB in prod. This matches `platform_financial_dashboard.py` and `billing_config.py`, both of which are cited as SECOPS-007 compliant in `POLICY_DOCS_DASHBOARD_TICKETS.md` §"Dev/prod parity". The service is purely read-only, so there is no mock payment path and no dev divergence risk.

### 7.2 Money-safety

PMD-003 is **read-only**. It calls `compute_due` (`billing_shared.py:158`) for reading balance, but never calls `new_ledger_entry`, `settle_or_reverse_ledger`, `apply_balance_delta`, or any Stripe/PayPal/CCBill SDK function. No money moves. The `outstanding_rent_cents` value is derived from existing ledger rows and the BALANCE row — PMD-003 does not create, modify, or delete any row in `T.billing`.

The money-safety guarantee from `POLICY_DOCS_DASHBOARD_TICKETS.md` §"Cross-cutting constraints" applies: PMD-003 reads the ledger but never writes it. Any future modification to ledger state (void, payment recording) belongs exclusively to the RNT cluster and must route through `new_ledger_entry` + `settle_or_reverse_ledger`.

### 7.3 Idempotency

All three endpoints are idempotent GET reads. Repeated calls return the same (or more current) data. There are no writes, conditional or otherwise.

### 7.4 Cross-user isolation

All ledger reads use `pk = "USER#{owner_sub}"` where `owner_sub` is the `session["user_sub"]` extracted by `require_ui_session`. There is no cross-owner ledger scan. Property and lease queries are scoped to the authenticated owner via GSI keys (`GSI_OWNER` on `T.properties`, `GSI2PK` on `T.leases`). An admin user sees only their own portfolio — there is no admin-cross-owner view in PMD-003 (that surface belongs to PMD-005 integration tests and a future admin aggregate endpoint).

### 7.5 DoS / runaway scan protection

`_iter_owner_rent_ledger` caps at `S.portfolio_kpi_max_ledger_scan_pages` (default 50) DynamoDB pages. A landlord with a very large billing table (e.g. years of daily transactions) will have scans silently truncated at the cap — the KPI result is approximate but the endpoint does not time out or exhaust memory. The cap is configurable via env var.

## 10. Open Questions / Assumptions

1. **`outstanding_rent_cents` semantics: BALANCE row vs. ledger scan.** The BALANCE row (maintained by RNT `apply_balance_delta`) gives a running total across all time. The ledger scan gives a sum for a specific time window. PMD-003 uses the BALANCE row's `due_settled_cents` for the headline KPI (all-time outstanding) and the period-filtered ledger scan for `monthly_rent_snapshot`. This means the two figures may not agree when there are carry-over unpaid charges from prior months. *Assumption: the headline KPI is "all-time outstanding rent balance" and the snapshot is "within-month analysis" — a deliberate distinction.*

2. **Multi-property, multi-currency.** PMD-003 sums `outstanding_rent_cents` across all of the owner's leases regardless of currency (it reads from the single `BALANCE` row). If an owner has leases in USD and GBP, the sum is meaningless. *Assumption: the platform is single-currency per owner (PMD-001 provides one policy with one currency per owner). Multi-currency ledger is a future consideration.*

3. **WOV fallback accuracy.** The ticket fallback counts any open-family tickets owned by the landlord, not just property-linked ones. This may overcount if the landlord has software tickets, support tickets, etc. *Assumption: acceptable approximation until WOV lands; the `kind="open_ticket"` label disambiguates the fallback path in the frontend.*

4. **Admin cross-owner KPI aggregate.** PMD-003 provides only per-owner (session user's own) views. A platform admin viewing all landlords' portfolios is not in scope. *Assumption: deferred to a future admin aggregate endpoint in PMD-005 or a subsequent ticket.*

5. **Caching.** Compute-heavy KPI reads (scanning large ledger tables) are not cached. *Assumption: for now acceptable; a short-TTL in-memory cache (same pattern as `billing_config._cache`) can be added if latency becomes an issue.*

6. **`PORTFOLIO_KPI_MAX_LEDGER_SCAN_PAGES` default of 50.** At 1 MB per DDB page, this caps at ~50 MB of ledger data per request. A landlord with 5+ years of daily rent charges may have > 50 pages. *Assumption: 50 pages covers multi-year portfolios; the cap is a DoS guard, not a correctness cap for typical usage.*
