# LSE-003 — Lease history per tenant + upcoming-expiration query + renewal-notice loop

**Ticket type:** Feature
**Priority:** P2
**Estimate:** 2 d
**Flag:** `LEASES_ENABLED` (shared, default OFF) + sub-flag `LEASES_RENEWAL_NOTIFICATIONS_ENABLED` (default OFF)
**Depends on:** LSE-001 (entity, table, state machine), LSE-002 (list/filter/edit service + router)

---

## 1. Summary & Goal

LSE-003 adds three capabilities on top of the Lease entity and router established by LSE-001
and LSE-002:

1. **Per-tenant lease history** — a paginated read of all leases (any status) for a single
   `tenant_id`, allowing a tenant-profile page to display current and historical tenancies
   newest-first.

2. **Upcoming-expiration query** — a single-partition GSI2 range query that returns only
   `active` leases whose `end_date` falls within a configurable look-ahead window (default 60
   days), powering the portfolio dashboard's "leases expiring soon" priority list
   (gap analysis §A portfolio dashboard narrative) and feeding the downstream **RNT** rent-ledger cluster so it can stop
   posting charges for leases that are about to end.

3. **Background renewal-notice loop** — a startup-registered `asyncio.ensure_future` task
   (exact clone of `app/services/compute_billing.py:653–676`) that sweeps active leases
   across all owners every hour, sends one expiration-warning email per qualifying lease via
   `app/services/alerts.py:459 send_alert_email`, and writes an idempotency marker
   (`renewal_notified_at`) so the email is sent exactly once regardless of how many sweep
   cycles run.

All three pieces are additive, flag-gated (both endpoints 404 and the loop never starts with
`LEASES_ENABLED=0`), reuse existing primitives without forking, and contain no
`if S.dev_mode:` branches (SECOPS-007 parity). Money movement — rent charges, deposit
refunds, fee reversals — is out of scope for this ticket; those flows belong to the RNT
rent-ledger cluster and must use `billing_shared.new_ledger_entry` / `settle_or_reverse_ledger`
exclusively.

## 3. Data Model

### 3.1 No new tables or GSIs

LSE-003 introduces **no new DynamoDB tables and no new GSIs**. It relies exclusively on the
`leases` table and its two GSIs defined and registered in LSE-001.

The two read patterns this ticket adds map directly onto existing structures:

- **Tenant history** — base-table partition `PK=USER#{user_sub}` + `FilterExpression=Attr("tenant_id").eq(tenant_id)`. A dedicated `GSI3PK=USER#{user_sub}#TENANT#{tenant_id}` / `GSI3SK=start_date` (N) index would allow a direct key-condition query and avoid the filter-loop, but at expected per-landlord volumes (tens to low hundreds of leases per owner) the filtered scan is sufficient and avoids a third GSI. The optimization is documented as a deferred option in §10.

- **Upcoming expirations** — GSI2, key-condition:
  `GSI2PK = USER#{user_sub}#STATUS#active` + `GSI2SK BETWEEN now_ts() AND now_ts() + within_days*86400`.
  This is a proper range key-condition (no `FilterExpression`); open-ended leases naturally
  never appear because they have no `end_date` and therefore no `GSI2SK` projection (sparse
  GSI, QUO-004 §3.2 / LEASES_TICKETS.md constraint 5).

- **Cross-user renewal sweep** — GSI1, key-condition:
  `GSI1PK = "LEASES#ALL"` with `FilterExpression=Attr("status").eq("active") & Attr("end_date").between(now_ts(), now_ts()+90*86400)`.
  The `FilterExpression` does **not** reduce page size here; the sweep must loop on
  `LastEvaluatedKey`.

### 3.2 Idempotency marker attribute

The `renewal_notified_at` (N, optional) attribute is already part of the lease item schema
defined in LSE-001. It is absent from newly created leases. The renewal loop writes it
exactly once with a conditional `update_item` pattern (see §5.3). No schema migration is
required.

### 3.3 Numeric GSI key types (mandatory)

The `leases` `TableDef` in `scripts/local-ddb-init.py` already carries:

```python
attr_types={"GSI1SK": "N", "GSI2SK": "N"}
```

LSE-003 does not modify `scripts/local-ddb-init.py`. If LSE-001 was deployed without
these `attr_types`, any `GSI2SK.between(low, high)` call will raise
`ValidationException: Comparators of type N cannot be used with string attribute`. This is
the single most critical prerequisite LSE-003 has on LSE-001.

### 4.1 New service functions — `app/services/leases.py`

All three functions begin with the standard guard (LEASES_TICKETS.md cross-cutting constraint 1):

```python
if not S.leases_enabled:
    return None   # caller (router) raises 404
```

---

#### `list_leases_for_tenant(user_sub: str, tenant_id: str, *, limit: int = 50, cursor: str | None = None) -> dict`

Returns all leases (any status) where the authenticated landlord owns the lease and the
lease's `tenant_id` matches. Newest-first by `start_date` (application-level sort, since
there is no dedicated index ordering by `start_date` for this access pattern).

**Algorithm:**

1. `if not S.leases_enabled: return None`
2. Decode `ExclusiveStartKey` from `cursor` via `decode_cursor` (`app/core/cursor.py:103`).
3. Issue a base-table query:
   ```python
   T.leases.query(
       KeyConditionExpression=Key("pk").eq(f"USER#{user_sub}") & Key("sk").begins_with("LEASE#"),
       FilterExpression=Attr("tenant_id").eq(tenant_id),
       ScanIndexForward=False,
       Limit=min(limit, 200),
       **({ExclusiveStartKey: lek} if lek else {}),
   )
   ```
4. Because `FilterExpression` does not reduce page size, loop on `LastEvaluatedKey` until the
   result set contains `limit` items or the table partition is exhausted. Accumulate into a
   list, stopping when `len(accumulated) >= limit` or no `LastEvaluatedKey` is returned.
5. Sort the accumulated page by `start_date` descending before returning (application-level
   sort covers the case where the base-table natural scan order differs from the desired
   recency order).
6. Encode `LastEvaluatedKey` from the final DynamoDB page (or `None` if exhausted) via
   `encode_cursor` (`app/core/cursor.py:94`).
7. Return `{"leases": [<serialized items>], "count": len(items), "next_cursor": str | None}`.

**Ownership isolation:** The query is partitioned by `USER#{user_sub}`, so leases owned by
another landlord are not accessible. A `tenant_id` that exists only in another owner's
partition returns an empty list — 200 with zero results, not a 404.

---

#### `list_upcoming_expirations(user_sub: str, *, within_days: int = 60, limit: int = 50) -> list[dict]`

Returns active leases for one owner whose `end_date` falls within the next `within_days`
days. Powers the per-landlord dashboard dashlet.

**Algorithm:**

1. `if not S.leases_enabled: return []`
2. Compute `now = now_ts()`, `window_end = now + within_days * 86400`.
3. Issue a GSI2 range query:
   ```python
   T.leases.query(
       IndexName="leases-by-status-index",
       KeyConditionExpression=(
           Key("GSI2PK").eq(f"USER#{user_sub}#STATUS#active")
           & Key("GSI2SK").between(now, window_end)
       ),
       ScanIndexForward=True,        # earliest expiring first
       Limit=min(limit, 200),
   )
   ```
4. This is a proper key-condition (no `FilterExpression`) so a single page is sufficient for
   the typical per-landlord portfolio. Return the items as a plain list (no cursor — the
   dashboard always wants the complete window, not a paginated view).

**Open-ended leases are excluded automatically:** leases with no `end_date` carry no
`GSI2SK` and are absent from the `leases-by-status-index`, so they never appear in this
result (QUO-004 §3.2 sparse-GSI property).

**`within_days` bounds:** Validated at the router layer: `ge=1, le=365` (a 1-day minimum
prevents trivially empty results; a 365-day cap prevents accidental full-table scans on very
busy portfolios).

---

#### `check_expiring_leases() -> int`

Cross-user sweep for the background loop. Scans GSI1 for all active leases with an `end_date`
in the next 90 days, then for each lease whose `end_date - now_ts() <= renewal_notice_days *
86400` and which has not yet been notified (`renewal_notified_at` absent), sends one email,
writes the idempotency marker, and emits an audit event.

**Algorithm:**

1. `if not S.leases_renewal_notifications_enabled: return 0`
2. `if not S.leases_enabled: return 0`
3. `now = now_ts()`, `sweep_end = now + 90 * 86400` (fixed 90-day sweep horizon keeps
   the scan bounded without requiring a per-owner loop; leases due beyond 90 days are picked
   up on a future sweep cycle).
4. Loop over GSI1 with `LastEvaluatedKey`:
   ```python
   lek = None
   count = 0
   while True:
       resp = T.leases.query(
           IndexName="leases-all-index",
           KeyConditionExpression=Key("GSI1PK").eq("LEASES#ALL"),
           FilterExpression=(
               Attr("status").eq("active")
               & Attr("end_date").between(now, sweep_end)
           ),
           **({ExclusiveStartKey: lek} if lek else {}),
       )
       for item in resp.get("Items", []):
           if item.get("renewal_notified_at"):
               continue   # already sent — idempotency gate
           days_remaining = (int(item["end_date"]) - now) // 86400
           notice_window = int(item.get("renewal_notice_days", 30))
           if days_remaining > notice_window:
               continue   # not yet in the notification window
           _send_renewal_notice(item, days_remaining)
           count += 1
       lek = resp.get("LastEvaluatedKey")
       if not lek:
           break
   return count
   ```
5. `_send_renewal_notice(item, days_remaining)` — internal helper (not public):
   a. Calls `get_profile_identity(item["user_sub"])` (`app/services/profile.py:305`) to
      resolve the landlord's `email`. If `email` is `None` or empty, logs a warning and
      skips (never raises).
   b. Calls `send_alert_email([email], subject, body_text)` (`app/services/alerts.py:459`).
      `send_alert_email` owns the dev(log)/prod(SES) divergence; `check_expiring_leases`
      contains no `if S.dev_mode:` branch.
   c. Writes the idempotency marker with a conditional `update_item`:
      ```python
      T.leases.update_item(
          Key={"pk": item["pk"], "sk": item["sk"]},
          UpdateExpression="SET renewal_notified_at = :ts",
          ConditionExpression="attribute_not_exists(renewal_notified_at)",
          ExpressionAttributeValues={":ts": now_ts()},
      )
      ```
      `ConditionalCheckFailedException` is silently swallowed — a concurrent sweep already
      sent the notice.
   d. Calls `audit_event("lease.renewal_notified", item["user_sub"], lease_id=item["lease_id"], lease_number=item["lease_number"], days_remaining=days_remaining)` (`app/services/alerts.py:644`).

**Short-circuit when sub-flag is off:** step 1 returns 0 immediately. The function never
queries DynamoDB in that state.

#### `run_leases_renewal_check_loop(*, poll_interval: int | None = None) -> None` (async)

Exact clone of `app/services/compute_billing.py:653–666`:

```python
async def run_leases_renewal_check_loop(*, poll_interval: int | None = None) -> None:
    interval = poll_interval if poll_interval is not None else S.leases_renewal_check_interval_seconds
    while True:
        try:
            check_expiring_leases()
        except Exception:
            logger.exception("leases_renewal_check_loop error")
        await asyncio.sleep(interval)
```

```python
def start_leases_renewal_check_task() -> None:

        asyncio.ensure_future(run_leases_renewal_check_loop())
        logger.info(
            "Leases renewal check loop started (interval=%ds)",
            S.leases_renewal_check_interval_seconds,
        )
```

This mirrors `start_compute_billing_timer_task` at `app/services/compute_billing.py:669–676`

## 5. Detailed Behavior & Edge Cases

### 5.1 Per-tenant history edge cases

- **Tenant has no leases with this owner.** The base-table query returns an empty `Items`
  list. Return `{"leases": [], "count": 0, "next_cursor": null}` — never 404.

- **Tenant has one `active` and two `ended` leases.** All three are returned (no status
  filter). The sort by `start_date` descending means the most recently started lease appears
  first.

- **Large owner partition** (100+ leases). The `FilterExpression` post-filter may return zero
  matching items in a DynamoDB page even though more pages exist. The internal loop must
  continue iterating until the result set fills the requested `limit` or the partition is
  exhausted — stopping after the first empty page would silently omit matching items (CLAUDE.md
  gotcha: *"DynamoDB fetches up to 1MB before applying FilterExpression"*).

- **cursor tampering.** `decode_cursor` returns `None` for invalid/tampered cursors; the query
  proceeds without an `ExclusiveStartKey` (restarts from the beginning). This is consistent
  with the behavior of all other list endpoints in the codebase.

- **`tenant_id` belongs to a different owner.** The query is constrained to
  `PK=USER#{user_sub}`, so leases owned by other landlords are never returned. A
  `tenant_id` with no cross-owner leases returns an empty list — correct behavior, no
  information leak.

### 5.2 Upcoming-expiration edge cases

- **Open-ended lease (`end_date` absent).** No `GSI2SK` is written at create time.
  The item is not projected into `leases-by-status-index` for the `active` partition key.
  It will never appear in a `GSI2SK.between(...)` range query — correct, open-ended leases
  never expire.

- **`within_days=1`.** Query window is `[now, now+86400)`. A lease expiring today at midnight
  is included; a lease expiring tomorrow afternoon is included (within 1 day); a lease that
  already expired (`end_date < now`) is not included (GSI2SK lower bound is `now`).

- **`within_days=365`.** The upper bound is `now + 31536000`. For very large portfolios this
  may return up to `limit=200` leases per call; the cap prevents unbounded result sets.

- **Lease transitions to `ended` before expiry.** The `transition_status` function in LSE-001
  rewrites `GSI2PK` to `USER#{user_sub}#STATUS#ended`. The item immediately disappears from
  the `active` GSI2 partition and stops appearing in expiration queries — correct behavior.

- **Concurrent `within_days` range and `transition_status`.** A race between the expiration
  query and a landlord manually ending a lease may yield a result that is stale by a
  millisecond. This is acceptable — the caller (dashboard) re-queries on page load. No
  transactional guarantee is needed here.

### 5.3 Renewal-notice loop edge cases

- **Email already sent (`renewal_notified_at` present).** The loop checks
  `item.get("renewal_notified_at")` first and skips the item. The conditional
  `update_item(ConditionExpression="attribute_not_exists(renewal_notified_at)")` provides a
  second safety net against a race between two concurrent sweep workers (future horizontal
  scaling), swallowing `ConditionalCheckFailedException` silently.

- **Lease ends before the sweep runs.** If `status` transitions to `ended` between when the
  item is fetched from GSI1 and when `_send_renewal_notice` runs, the notification still
  goes out (the item was `active` during the scan). This is acceptable — the landlord is
  informed the lease was expiring; the transition to `ended` is a separate event.

- **`get_profile_identity` returns `email=None`.** The landlord has not set a display email.
  `_send_renewal_notice` logs a warning, skips `send_alert_email`, but still writes
  `renewal_notified_at` and emits the audit event. Skipping the email prevents repeated
  fruitless email attempts on every subsequent sweep cycle.

- **`send_alert_email` raises an exception (SES throttle, network partition in prod).** The
  exception propagates up to `_send_renewal_notice`, which does NOT catch it. The outer loop
  in `run_leases_renewal_check_loop` catches all exceptions from `check_expiring_leases` via
  `except Exception: logger.exception(...)` (identical to the compute-billing timer at
  `compute_billing.py:664–666`), logs it, sleeps, and retries on the next cycle. The
  idempotency marker is **not** written if `send_alert_email` raised — the next cycle will
  retry the send. This is the correct behavior: write `renewal_notified_at` only after
  successful delivery.

- **Loop interval.** `S.leases_renewal_check_interval_seconds` (default 3600). An operator
  can set it to 300 for testing without redeploying code.

- **Both flags off.** `check_expiring_leases()` returns 0 immediately at step 1. No DynamoDB
  queries are issued.

- **`LEASES_ENABLED=1` but `LEASES_RENEWAL_NOTIFICATIONS_ENABLED=0`.** The loop never starts
  (`start_leases_renewal_check_task` checks both flags). The two endpoints `GET /ui/leases/expiring`
  and `GET /ui/tenants/{tenant_id}/leases` remain available (they gate only on
  `LEASES_ENABLED`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 — no `if S.dev_mode:` branches

`app/services/leases.py` (all three new functions) contains zero `if S.dev_mode:` branches.
Email dispatch goes through `send_alert_email` at `app/services/alerts.py:459`, which owns
the dev/prod divergence internally: in dev it appends to `S.dev_email_log`; in prod it calls
SES. The DynamoDB calls go through `T.leases` which resolves to DynamoDB Local in dev and real
DynamoDB in prod — the boto3 call is identical. This matches the contract pattern in QUO-004
§7 and every other background loop in the codebase (CLAUDE.md).

### Idempotency of the renewal notice

`renewal_notified_at` is written with `ConditionExpression="attribute_not_exists(renewal_notified_at)"`.
Once written, the attribute is never cleared or reset (no lifecycle event on the lease clears
it). If a landlord extends the `end_date` after the notice was sent, a second notice is **not**
sent for the original expiration — this is a deliberate design choice. If a second notice is
needed after an extension, the landlord must manually reset `renewal_notified_at` (an admin
PATCH endpoint is outside the scope of this ticket; documented in §10). Idempotency is preserved
across server restarts, horizontal scaling, and repeated loop invocations.

### Ownership isolation / security

- `list_leases_for_tenant` is scoped to `PK=USER#{user_sub}` — the authenticated user's
  partition. A landlord cannot request tenant history for another landlord's tenant even if
  the `tenant_id` string is guessed.
- `list_upcoming_expirations` is similarly scoped to `GSI2PK=USER#{user_sub}#STATUS#active`.
- The renewal sweep accesses all partitions via GSI1 (`LEASES#ALL`). This is a server-side
  background task; it is never exposed as a user-facing endpoint. The only callable surface
  is the `/ui/admin/leases` endpoint (guarded by `require_admin_or_root`, LSE-002) and the
  internal startup handler.
- Bearer-auth API clients receive the same 404 as cookie-auth clients when
  `LEASES_ENABLED=0`.

### Money safety (no-op in this ticket)

LSE-003 does not write or modify any billing ledger rows. `monthly_rent_cents` and
`security_deposit_cents` stored on the lease item are read-only informational cents. Any rent
charge, deposit hold, or late fee must be posted by the RNT rent-ledger cluster via
`billing_shared.new_ledger_entry` (`app/services/billing_shared.py:224`). Any void or reversal
must use `settle_or_reverse_ledger` (`app/services/billing_shared.py:262`) — never a custom
DynamoDB delete or direct counter mutation. These functions are listed in §2.2 explicitly to
document the non-use and prevent future accidental forking.

DynamoDB String. `list_upcoming_expirations` will fail with `ValidationException`. The remediation
is to delete and recreate the `leases` table in dev (via `just restart`) or issue an
`UpdateTable` in prod to add the `leases-by-status-index` GSI with numeric attribute type.
This is a pre-existing constraint documented in LSE-001; no new migration work is required for
LSE-003 itself.

## 10. Open Questions / Assumptions

1. **Route prefix resolution for `GET /ui/tenants/{tenant_id}/leases`.** The leases router
   has `prefix="/ui/leases"`. Two options: (a) declare the endpoint with path
   `"/../../tenants/{tenant_id}/leases"` — fragile; (b) register the endpoint on a separate
   `APIRouter(prefix="/ui/tenants")` imported into `app/main.py` alongside the leases
   router. Option (b) is cleaner and avoids path-prefix confusion. The implementation must
   pick one and document it in the router file. **Assumption:** the spec requires the tenant
   history endpoint to surface at `/ui/tenants/{tenant_id}/leases` — the routing mechanics
   are an implementation detail.

2. **Second renewal notice after `end_date` extension.** Currently, if a landlord extends
   `end_date` from 25 days out to 120 days out after the notice fires, the idempotency
   marker prevents a second notice. Stakeholder preference: should a PATCH of `end_date`
   reset `renewal_notified_at`? The current spec says no — once notified, always notified.
   This can be changed in a follow-up ticket.

3. **Deferred GSI3 for hot tenant profiles.** At high per-landlord lease volumes (1000+
   leases per owner), the `FilterExpression` loop in `list_leases_for_tenant` may scan the
   full owner partition multiple times per page request. A `GSI3PK=USER#{user_sub}#TENANT#{tenant_id}` /
   `GSI3SK=start_date` (N) index would make this a direct key-condition query. The decision
   to add GSI3 should be made when actual per-owner volumes are measured in production.

4. **Loop concurrency.** The spec assumes a single background loop instance per process
   (single uvicorn worker in dev, CLAUDE.md). Horizontal scaling with multiple workers
   would result in multiple concurrent sweeps; the `attribute_not_exists(renewal_notified_at)`
   conditional write prevents duplicate emails, but the `get_profile_identity` and
   `send_alert_email` calls would still race. A DDB-backed advisory lock or SQS fan-out
   would be needed at scale. This is documented as a future concern.

5. **`leases_renewal_check_interval_seconds` lower bound.** No floor is validated in
   settings. An operator setting `LEASES_RENEWAL_CHECK_INTERVAL_SECONDS=0` would create a
   tight loop. A minimum of 60 should be enforced either in the settings validator or the
   loop startup function.
