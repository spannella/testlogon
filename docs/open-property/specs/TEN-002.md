# TEN-002 — Tenant profile — employment, income verification (+ doc attachments), emergency contacts, active-unit link

**Type**: Feature | **Priority**: P0 | **Estimate**: 3 d
**Source**: `docs/open-property/TENANTS_TICKETS.md` §TEN-002 + `docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §B
**Depends on**: TEN-001 (tenant entity, table, flag), PROP-002 (unit entity + `get_unit`)

---

## 1. Summary & Goal

TEN-002 adds the **net-new tenant profile layer** that no existing codebase entity carries.
Today the codebase has only the thin contacts address-book (`app/routers/contacts.py`) and
the planned PTY PERSON party (`docs/ofbiz/specs/PTY-004`); neither stores employment data,
income, income-verification document links, emergency contacts, or an active-unit FK.

This ticket delivers exactly these four surfaces, all within the existing `property_tenants`
table that TEN-001 creates, and all gated behind the same
`S.property_tenants_enabled` flag TEN-001 establishes:

1. **PROFILE row** — a single `SK=PROFILE` row per tenant carrying structured `employment`,
   `income`, and `emergency_contacts` sub-objects; partial updates always merge rather than
   clobber siblings.
2. **INCOMEDOC rows** — one `SK=INCOMEDOC#{doc_id}` row per income-verification attachment;
   bytes live in the existing file manager (S3), the tenant table stores only the record-link.
3. **Income-verification state** — `verification_status ∈ {unverified, pending, verified,
   rejected}` with `verified_at` / `verified_by` stamps; transitions emit audit events.
4. **Active-unit link** — `active_unit_id` on the META row validated against the PROP unit
   service (`property_mgmt.get_unit`); transitions tenant `status` to `active`/`past`.

With `PROPERTY_TENANTS_ENABLED=false` (default) the entire surface returns HTTP 404 and
touches no table. With the flag on and TEN-001 merged, the four service functions are purely
additive; no existing row, index, or behavior is modified.

## 2. Context & Current State

### 2.1 No employment / income / emergency-contact model exists today

`docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §B (lines 51–53) records all three as
**MISSING**. A `grep -rn "employer_name\|annual_income\|emergency_contact\|income_verification" app/`
returns zero results — there are no existing service files, Pydantic models, DynamoDB attributes,
or router endpoints for these fields anywhere in the running codebase.

The closest structural analogues are:

- **CUS-001 customer entity** (`docs/openbankproject/specs/CUS-001`) — a person record
  (customer_number, legal name, date of birth, contact info, kyc_status) with a typed
  key-value attribute sub-store. CUS-001 does **not** carry employment/income sub-records
  directly; those belong to KYC case data. TEN-002 borrows the single-table child-row
  posture (same `customer_id` partition, typed `SK` rows for each sub-entity), but its
  employment + income sub-objects are net-new to the property domain.
- **KYC `create-packets` read-merge-write** (CLAUDE.md "KYC template-signature endpoints"):
  `create-packets` does a read-merge-write of the `signature` map to avoid clobbering sibling
  sub-objects. `update_profile` copies this exact posture for the `PROFILE` row (see §4.3).
- **EVT-011 record-link pattern** (`docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` line 72):
  documents linked to a tenant via a path/metadata pointer, never bytes. TEN-002's
  `INCOMEDOC#` row is this pattern applied to income verification attachments.

### 2.4 File manager for document bytes

`app/services/filemanager.py:2110` defines `upload_file(user, path, file, *, encryption_meta)`.
It uploads bytes to S3 (via the in-process moto-S3 or real S3 depending on environment — the
fork is internal to `filemanager.py`, not visible to callers), writes a DynamoDB node record,
and returns `{"path": p, "size": size}` (lines 2110–2204). **The return dict contains only
`path` and `size` — not `name`, `content_type`, or a dev `url`.** TEN-002's `add_income_doc`
must therefore source `file_name` from `file.filename` and `content_type` from
`file.content_type` directly (not from the returned node dict); see the corrected code block
in §4.5. Bytes never touch the tenant table — the tenant service stores only the path
record-link, keeping it env-agnostic (SECOPS-007).

### 2.7 PROP unit validation (`get_unit`)

`set_active_unit` must validate that the supplied `unit_id` actually exists and belongs to a
property owned by the same `owner_id`. PROP-002's `app/services/property_mgmt.get_unit` is
the canonical lookup. `get_unit` signature is `get_unit(property_id, unit_id)` — it requires
`property_id` as the first argument (PROP-002.md:252); there is **no** `get_unit_by_id(unit_id)`
shortcut, and `GSI_UNIT_OCCUPANCY` (PK=`property_id`/SK=`occupancy_status`, PROP-002.md:139)
cannot map a bare `unit_id` back to its property. DESIGN RESOLUTION: rather than perform an
expensive cross-partition scan for the `UNIT#{unit_id}` SK, `set_active_unit` **requires the
caller to supply `property_id` alongside `unit_id`** (both are carried in the PUT body, §4.10)
and calls `get_unit(property_id, unit_id)` directly — no scan, no new index, contract-compatible
with PROP-002. The lazy cross-module import (`try/except ImportError`) preserves deploy-before-PROP-002
compatibility. NOTE: PROP-002 §2.9 discusses the SAME-module forward-reference case
(`compute_property_occupancy` in `property_mgmt.py`) and correctly says `try/except ImportError`
does NOT work for same-module names; it uses a bare call + `except Exception` instead.
TEN-002's case is a CROSS-module import (`from app.services.property_mgmt import get_unit`),
so `try/except ImportError` IS the correct and effective pattern here. If PROP-002 is
unavailable at import time, `set_active_unit` raises HTTP 503 `"Unit validation unavailable"`.

### 2.8 Phone / email normalization

`app/core/normalize.normalize_email` (`normalize.py:60–64`) and `normalize_phone`
(`normalize.py:66–81`) are used for emergency-contact `email` and `phone` fields when
provided. They raise HTTP 400 on malformed input — this is the same normalization applied
to the tenant META row by TEN-001.

## 4. API / Service Design

### 4.1 Service module — `app/services/property_tenant.py` (extends TEN-001)

All functions call `_require_enabled()` as first statement. All emit `_audit(...)` on
success. Work against `T.property_tenants` (wired by TEN-001 in `app/core/tables.py`).

#### 4.2 `get_profile(tenant_id) -> dict`

```python
def get_profile(tenant_id: str) -> dict:
    _require_enabled()
    item = T.property_tenants.get_item(
        Key={"PK": f"TENANT#{tenant_id}", "SK": "PROFILE"}
    ).get("Item") or {}
    return _normalize_profile(item)
```

Returns a merged dict with keys `employment`, `income`, `emergency_contacts`, `updated_at`.
`_normalize_profile` coerces Decimal → int/float for numeric fields and ensures missing
sub-objects default to `{}` or `[]`.

Returns `{}` (empty dict, not 404) when no PROFILE row exists — the profile is
lazily created on first `update_profile` call.

#### 4.3 `update_profile(tenant_id, *, employment=None, income=None, emergency_contacts=None) -> dict`

Read-merge-write pattern (mirror: KYC `create-packets` in CLAUDE.md):

```python
def update_profile(tenant_id, *, employment=None, income=None,
                   emergency_contacts=None) -> dict:
    _require_enabled()
    existing = get_profile(tenant_id)
    merged_employment = {**existing.get("employment", {}), **(employment or {})}
    merged_income     = {**existing.get("income", {}), **(income or {})}
    merged_ec         = existing.get("emergency_contacts", []) \
                        if emergency_contacts is None \
                        else _validate_emergency_contacts(emergency_contacts)
    item = {
        "PK": f"TENANT#{tenant_id}",
        "SK": "PROFILE",
        "employment": merged_employment,
        "income": merged_income,
        "emergency_contacts": merged_ec,
        "updated_at": now_ts(),
    }
    T.property_tenants.put_item(Item=item)
    # _owner_for: private helper → get_tenant(tenant_id).get("owner_id", "unknown")
    # (not defined in TEN-001 spec by name; implement inline or as a one-liner)
    _audit("tenant_profile_updated", _owner_for(tenant_id),
           tenant_id=tenant_id)
    return _normalize_profile(item)
```

Passing `employment=None` leaves the existing employment map untouched; passing
`employment={}` explicitly clears it. The same rule applies to `income`. Emergency contacts
passed as a list **replace** the current list entirely (not append); callers wishing to
add a single contact must first fetch the current list, append, and send the full list.

#### 4.4 `_validate_emergency_contacts(contacts: list) -> list`

- Raises HTTP 400 `"emergency_contacts may not exceed 5 entries"` when `len(contacts) > 5`.
- Raises HTTP 422 `"emergency contact requires a name"` when any entry lacks `name`.
- Assigns `ec_id = uuid4().hex` to any entry that lacks one (new entries).
- Normalizes `phone` via `normalize_phone` when present; normalizes `email` via
  `normalize_email` when present. Propagates their HTTP 400 on bad format.

#### 4.5 `add_income_doc(tenant_id, owner_sub, file, *, doc_kind="other") -> dict`

```python
def add_income_doc(tenant_id: str, owner_sub: str, file: UploadFile,
                   *, doc_kind: str = "other") -> dict:
    _require_enabled()
    from app.services import filemanager
    doc_id = uuid4().hex
    # doc_id sub-folder avoids require_not_exists collisions for same-named files
    # (§5.4). upload_file returns only {"path": p, "size": size}; name/content_type
    # are sourced directly from the UploadFile object.
    file_path = f"Tenant Documents/{tenant_id}/{doc_id}/{file.filename}"
    node = filemanager.upload_file(owner_sub, file_path, file)
    item = {
        "PK": f"TENANT#{tenant_id}",
        "SK": f"INCOMEDOC#{doc_id}",
        "doc_id": doc_id,
        "tenant_id": tenant_id,
        "file_node_path": node["path"],
        "file_name": file.filename or "",
        "content_type": file.content_type or "application/octet-stream",
        "size_bytes": int(node.get("size", 0)),
        "doc_kind": doc_kind,
        "uploaded_at": now_ts(),
        "uploaded_by": owner_sub,
    }
    T.property_tenants.put_item(Item=item)
    _audit("tenant_income_doc_added", owner_sub,
           tenant_id=tenant_id, doc_id=doc_id, doc_kind=doc_kind)
    return item
```

Filemanager handles S3 upload, quota enforcement, and DynamoDB node creation
internally (`filemanager.py:2110–2204`). TEN-002 never calls S3 directly.
Note: `upload_file` does NOT inject dev `/mock/s3/...` URL — the returned dict is
`{"path": p, "size": size}` only. Dev URL injection (if needed for the response) must
come from a separate presign or mock call; TEN-002 simply stores the path.

#### 4.7 `remove_income_doc(tenant_id, owner_sub, doc_id) -> bool`

```python
def remove_income_doc(tenant_id: str, owner_sub: str, doc_id: str) -> bool:
    _require_enabled()
    item = T.property_tenants.get_item(
        Key={"PK": f"TENANT#{tenant_id}", "SK": f"INCOMEDOC#{doc_id}"}
```

#### 4.8 `set_income_verification(tenant_id, status, verifier_sub) -> dict`

Valid `status` values: `unverified`, `pending`, `verified`, `rejected`. Any other value
raises HTTP 400. Stamps `verified_at = now_ts()` and `verified_by = verifier_sub` only when
`status == "verified"`; clears both fields when `status ∈ {unverified, pending, rejected}`.

```python
def set_income_verification(tenant_id: str, status: str, verifier_sub: str) -> dict:
    _require_enabled()
    VALID = {"unverified", "pending", "verified", "rejected"}
    if status not in VALID:
        raise HTTPException(400, f"Invalid verification_status: {status!r}")
    profile = get_profile(tenant_id)
    income = {**profile.get("income", {}), "verification_status": status}
    if status == "verified":
        income["verified_at"] = now_ts()
        income["verified_by"] = verifier_sub
    else:
        income.pop("verified_at", None)
        income.pop("verified_by", None)
    result = update_profile(tenant_id, income=income)
    _audit("tenant_income_verified", verifier_sub,
           tenant_id=tenant_id, status=status)
    return result
```

#### 4.9 `set_active_unit(tenant_id, owner_sub, property_id, unit_id) -> dict`

```python
def set_active_unit(tenant_id: str, owner_sub: str,
                    property_id: str | None, unit_id: str | None) -> dict:
    _require_enabled()
    if unit_id is not None:
        if not property_id:
            raise HTTPException(422, "property_id is required when unit_id is set")
        try:
            from app.services.property_mgmt import get_unit
        except ImportError:
            raise HTTPException(503, "Unit validation unavailable")
        # get_unit(property_id, unit_id) — both keys supplied by the caller;
        # the properties table PK is property_id, so no scan/extra index is used.
        unit = get_unit(property_id, unit_id)
        if not unit:
            raise HTTPException(404, f"Unit {unit_id!r} not found")
        # Ownership: the unit's parent property must belong to owner_sub.
        if unit.get("owner_sub") not in (None, owner_sub):
            raise HTTPException(404, f"Unit {unit_id!r} not found")
        new_status = "active"
    else:
        new_status = "past"
    T.property_tenants.update_item(
        Key={"PK": f"TENANT#{tenant_id}", "SK": "META"},
        UpdateExpression="SET active_unit_id = :u, #s = :s, updated_at = :t",
        ExpressionAttributeNames={"#s": "status"},
        ExpressionAttributeValues={
            ":u": unit_id,
            ":s": new_status,
            ":t": now_ts(),
        },
    )
    _audit("tenant_active_unit_set", owner_sub,
           tenant_id=tenant_id, unit_id=unit_id, new_status=new_status)
    return get_tenant(tenant_id)  # returns updated META row
```

DESIGN RESOLUTION (was an open RISK): `get_unit` is defined as `get_unit(property_id, unit_id)`
(PROP-002.md:252) and the `properties` table PK is `property_id`; there is **no**
`get_unit_by_id(unit_id)` shortcut and no unit→property reverse index (`GSI_UNIT_OCCUPANCY` is
keyed PK=`property_id`/SK=`occupancy_status`, PROP-002.md:139, so it cannot map a bare `unit_id`
back to its property). The TEN-001 tenant META row also carries no `property_id`
(TEN-001 §3.1 — only `active_unit_id`). Rather than force an expensive table scan, `set_active_unit`
**requires the caller to supply `property_id` alongside `unit_id`** (the PUT body provides both —
see §4.10 / §5.x). This respects PROP-002's `get_unit` contract exactly and adds no new index.
The lazy import of `property_mgmt` is wrapped in `try/except ImportError` so TEN-002 can
deploy before PROP-002 with degraded `set_active_unit` behaviour. When `unit_id=None`,
`active_unit_id` is set to DynamoDB NULL (boto3 serializes Python `None` as NULL) and
`property_id` is ignored. A subsequent call with a non-null `unit_id` overwrites it cleanly.

## 5. Detailed Behavior & Edge Cases

### 5.1 PROFILE row — lazy creation

No PROFILE row is created when TEN-001 creates the tenant. `get_profile` returns `{}` (not
404) when the row is absent. The first `update_profile` call creates it via `put_item` with
no `ConditionExpression` — idempotent because the row is fully overwritten each time.

### 5.2 Partial profile updates — merge semantics

`update_profile(tenant_id, income={"annual_income_cents": 75000})` must not erase
`employment` or `emergency_contacts`. The read-merge-write in §4.3 guarantees this: `income`
from the request is shallow-merged with the existing `income` map; `employment` and
`emergency_contacts` are carried forward unchanged when their arguments are `None`.

A call passing `employment={}` (empty dict) explicitly clears the employment sub-object.
This is intentional: the service distinguishes `None` ("don't touch") from `{}` ("clear").

### 5.3 Emergency-contact cap enforcement

`_validate_emergency_contacts` raises HTTP 400 (`"emergency_contacts may not exceed 5 entries"`)
when the caller submits a list of 6 or more entries. The cap is enforced on the **submitted**
list, not on a per-add basis, because the PUT endpoint replaces the list wholesale. A
landlord wishing to add a 6th contact must first remove one.

### 5.4 Income-document uniqueness

No uniqueness constraint on filename — a landlord may upload two documents with the same
filename for the same tenant (they are different documents). Each upload produces a new
`doc_id` and a new `INCOMEDOC#` row. `filemanager.upload_file` does enforce that a given
file path does not already exist (`require_not_exists` at `filemanager.py:2122`); TEN-002
sidesteps this by appending `doc_id` to the folder path:
`f"Tenant Documents/{tenant_id}/{doc_id}/{file.filename}"`.

### 5.5 `set_active_unit` with unit owned by a different owner

`set_active_unit` confirms the unit's parent property belongs to `owner_sub`. This is done
by reading the unit record via `get_unit(property_id, unit_id)` (caller-supplied `property_id`,
§4.9) and verifying the unit's `owner_sub == owner_sub`. If the unit belongs to a different
owner, the lookup is treated as a miss → HTTP 404 `"Unit {unit_id!r} not found"` (an existence
leak is avoided by returning 404 rather than 403). This prevents a tenant landlord from linking
a unit from another landlord's property.

### 5.6 `set_active_unit(unit_id=None)` — clearing

When `unit_id=None`, `active_unit_id` is set to DynamoDB NULL and `status` is set to
`"past"`. If the tenant has an active LSE lease at time of clearing, the status transition
is logged as `past` regardless — the lease lifecycle is LSE's responsibility. TEN-002 does
not query the LSE table to override this decision.

### 5.7 `set_income_verification` — who may call it

The service function accepts any `verifier_sub`. The router (TEN-003) will require at least
`require_ui_session` and must check `ctx["role"] >= ADMIN` (admin or root) before calling
this function — income verification is an admin/owner action, not a tenant self-service
action. TEN-002 itself does not encode the role check (service layer is role-agnostic per
the contacts.py precedent); the router enforces it.

### 5.8 `remove_income_doc` — file cleanup best-effort

The DynamoDB `INCOMEDOC#` row is deleted first. The filemanager `delete_node` call is
wrapped in `try/except Exception: pass`. A failure to delete the S3 object does not roll
back the row deletion — this mirrors the host-inventory + EC2 cleanup pattern documented in
CLAUDE.md (GAP-0223/0224: cleanup failures must NOT roll back the primary operation).

### 5.9 Concurrent profile writes — last-write-wins

`update_profile` does not use a version counter (no optimistic locking). Profile updates
are rare, low-contention, human-initiated operations. A `ConditionExpression` version guard
would complicate the partial-update read-merge-write. Last-write-wins is acceptable here.
If future load warrants it, a `version` attribute and `ConditionExpression="#v = :expected"`
can be added without breaking existing rows (they simply have no version).

### 5.10 `employment_type` and `doc_kind` validation

`employment_type` and `doc_kind` are validated in the service layer against their enumerated
values. Invalid values raise HTTP 400. This is not delegated to Pydantic `Literal` because
the service layer uses plain dicts (PTY-004 §4.3). Validation is a two-line guard:

```python
VALID_EMPLOYMENT_TYPES = {"full_time","part_time","self_employed","contract",
                           "unemployed","retired","student"}
if employment.get("employment_type") not in VALID_EMPLOYMENT_TYPES | {None}:
    raise HTTPException(400, "Invalid employment_type")
```

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no dev_mode branch

No `if S.dev_mode:` branch exists anywhere in TEN-002 service code. Income-document bytes
flow through `filemanager.upload_file` (`filemanager.py:2110`), which internally uses the
moto-S3 in-process mock in dev and real S3 in prod. The tenant service sees only the
returned `path` dict — the same shape in both environments. This is the same parity
guarantee used by the EVT-011 record-link pattern and the SSH session-recording service
(CLAUDE.md INFRA-010).

### 7.2 Idempotency

- **`update_profile`** — unconditional `put_item` on a fixed PK/SK (`TENANT#{id}`/`PROFILE`).
  Replaying the same `update_profile` call with the same payload produces the same row;
  `updated_at` will advance but no data is corrupted.
- **`add_income_doc`** — a new `doc_id = uuid4().hex` is minted on every call; two uploads
  of the same file are two distinct records. Callers must not retry on network timeout without
  first checking `list_income_docs` (standard at-least-once caveat for non-idempotent
  uploads). The router may optionally accept a client-supplied `idempotency_key` in a future
  ticket.
- **`set_active_unit`** — conditional free: calling it twice with the same `unit_id` is safe
  (the `update_item` expression is idempotent; `status` and `active_unit_id` are overwritten
  with the same values).
- **`set_income_verification`** — replaying with the same `status` is safe; `verified_at`
  advances by a few seconds at most.

### 7.3 Money-safety

TEN-002 has **no money-out path**. Employment/income/emergency data is informational
metadata for the landlord. No `new_ledger_entry`, no `apply_balance_delta_for_key`, no
`settle_or_reverse_ledger`, no Stripe/PayPal/CCBill call exists in this ticket. The rent
ledger is RNT-001's domain; TEN-002 does not touch it.

### 7.4 Authorization — ownership enforcement

Every service function receives an explicit `owner_sub` (the `user_sub` from the
`require_ui_session` dependency). Before any write, `_require_owned(tenant_id, owner_sub)`
is called:

```python
def _require_owned(tenant_id: str, owner_sub: str) -> dict:
    tenant = get_tenant(tenant_id)
    if not tenant:
        raise HTTPException(404, "Tenant not found")
    if tenant["owner_id"] != owner_sub:
        raise HTTPException(403, "Not your tenant")
    return tenant
```

This prevents cross-tenant reads/writes: a landlord cannot read or modify another landlord's
tenant profile, income docs, or emergency contacts.

### 7.5 PII handling — emergency contacts

Emergency-contact `phone` and `email` are stored in DynamoDB unencrypted. This is consistent
with the existing contacts table (`app/routers/contacts.py`) and the platform's general
approach to user-managed contact data. If encryption at rest is required by a compliance
obligation, `app/core/crypto.kms_encrypt` / `kms_decrypt` can be layered in; TEN-002 does
not implement it and leaves the decision to a future security ticket.

## 8. Backward Compatibility & Migration

### 8.1 No schema migration needed

The `property_tenants` table was created by TEN-001. TEN-002 adds two new SK prefixes
(`PROFILE`, `INCOMEDOC#`) as new rows; it does not alter existing rows or GSIs. A
`just restart` re-runs `scripts/local-ddb-init.py` which drops and recreates the table
(no migration path in dev). In production the table definition is unchanged — new SK rows
are additive and DynamoDB's schemaless nature means no `UpdateTable` call is required.

### 8.2 META row `active_unit_id` — additive attribute

Existing META rows (created by TEN-001) simply lack `active_unit_id`. Code that reads
META rows must use `.get("active_unit_id")` (which returns `None` by default) rather than
direct key access. TEN-001's `_item_to_tenant_out` helper will be updated by TEN-003 to
include `active_unit_id: Optional[str] = None` in `TenantOut`, defaulting to `None`.

### 8.3 Flag off — zero impact

With `PROPERTY_TENANTS_ENABLED=false` (the default) all service functions return 404 at the
`_require_enabled()` guard. No DynamoDB table is created, no existing behavior changes.
Existing contacts, billing, files, messaging, and every other subsystem are completely
unaffected.

### 8.4 Deploy order

TEN-001 must be deployed before TEN-002. The lazy-import pattern for `property_mgmt.get_unit`
in `set_active_unit` means TEN-002 can be deployed before PROP-002 (unit validation simply
returns HTTP 503 until PROP-002 is present). TEN-003 (router) must be deployed after
TEN-002 (service).

## 10. Open Questions / Assumptions

1. **Employment `start_date` format**: Spec assumes ISO-8601 date string (`YYYY-MM-DD`)
   stored as DynamoDB `S`. If the frontend needs sortable date queries, switch to Unix
   integer. Decision deferred to TEN-004 frontend work.

2. **Income currency**: The `income_currency` field defaults to `"usd"`. Multi-currency
   tenants (e.g. Canadian properties) would need `normalize_currency()` validation. Current
   assumption: landlord-set, free-string, no validation beyond length check. Revisit if
   RNT-001 rent-policy settings introduce a per-property currency.

3. **Emergency-contact `ec_id` stability**: The spec assigns `ec_id = uuid4().hex` on first
   add and expects callers to send it back on subsequent full-list PUTs. If the frontend
   loses `ec_id` between renders, a new id is minted. This is cosmetically harmless but may
   cause audit log noise. A future enhancement could make `ec_id` deterministic on
   `(tenant_id, name, relationship)`.

4. **Income-doc folder collision**: The spec uses
   `f"Tenant Documents/{tenant_id}/{doc_id}/{file.filename}"` to avoid `require_not_exists`
   collisions. This implies a `doc_id`-namespaced sub-folder per document. Filemanager's
   `ensure_folder_exists` creates the folder lazily. If the filemanager quota system counts
   folders, this could create a large number of 1-item folders for active tenants. Assumed
   acceptable for the current implementation.

5. **`set_active_unit` and LSE lease consistency**: The spec transitions tenant `status →
   past` when `unit_id=None` regardless of active leases. The correct behavior when an
   active lease still exists is an open question (block the transition? soft-warn?). Deferred
   to LSE integration in TEN-003/LSE cluster.

6. **PROP-002 availability at deploy time**: `set_active_unit` lazy-imports
   `property_mgmt.get_unit`. If PROP-002 has not yet been deployed, `set_active_unit` with
   a non-null `unit_id` will return HTTP 503. This is accepted as a deploy-order constraint
   rather than a code smell.
