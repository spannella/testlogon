# TEN-004 — Frontend — Tenant Directory + Tenant Profile Page

**Type:** Feature | **Priority:** P1 | **Estimate:** 3 days
**Source:** `docs/open-property/TENANTS_TICKETS.md` §TEN-004 + `docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §B
**Depends on:** TEN-001, TEN-002, TEN-003; **PROP** cluster (unit picker for active-unit), **LSE** cluster (lease-history links)

---

## 1. Summary & Goal

TEN-004 delivers the landlord/property-manager-facing React UI for the entire tenant cluster. It builds on the backend established by TEN-001 (entity + table + flag), TEN-002 (profile, income docs, emergency contacts, active-unit), and TEN-003 (HTTP router with all endpoints) to provide:

1. **TypeScript types** for all TEN-003 Pydantic response shapes, added to `frontend/src/api/types.ts` under a clearly delimited `// ─── Property Management — Tenants (TEN-004)` section.
2. **API endpoint wrappers** in a new file `frontend/src/api/endpoints/propertyTenants.ts` using the existing shared fetch-based `api` client (`frontend/src/api/client.ts`, exported as `{ api }`) and React Query hooks.
3. **Tenant directory page** (`frontend/src/pages/property/tenants/TenantsPage.tsx`, route `/property/tenants`) — a searchable, filterable, cursor-paginated table of tenants with a New-Tenant creation dialog.
4. **Tenant profile page** (`frontend/src/pages/property/tenants/TenantProfilePage.tsx`, route `/property/tenants/:tenantId`) — a five-section tabbed detail view covering identity, employment, income/docs, emergency contacts, and lease history.
5. **E2E spec** `frontend/e2e/property-tenants.spec.ts` covering directory CRUD, profile editing, income-doc upload/delete, emergency-contact management, and lease-history rendering.

The entire frontend is additive. With `PROPERTY_TENANTS_ENABLED=0` (the default), the API returns HTTP 503 on every call; the pages detect this and render a clean "this feature is not enabled" banner instead of crashing.

## 2. Context & Current State

### 2.1 No property-tenant UI exists today

There is no `frontend/src/pages/property/` directory. `grep -rn "property/tenants" frontend/src/` returns nothing. The `frontend/src/App.tsx` has no `/property/*` routes (confirmed: lines 1–550 show no such lazy import or `Route` path for `property`). The existing `frontend/src/api/endpoints/tenants.ts` is for the multi-tenancy ENTERPRISE-001 feature (admin-tenant subdomain management at `/v1/admin/tenants`, `frontend/src/api/types.ts:4970–4984`) — a wholly different entity. TEN-004 creates a new, clearly namespaced file `propertyTenants.ts` to avoid any collision.

### 2.2 Contacts page as the closest directory analogue

`frontend/src/pages/contacts/ContactsPage.tsx` is the most relevant existing directory-style page. It uses `useQuery` + `useMutation` + `useQueryClient` from `@tanstack/react-query` (`:3`), the shared fetch-based `api` client from `api/client.ts` (exported as `{ api }`, not Axios — see §4.1), shadcn/ui `Dialog`/`DropdownMenu`/`Button`/`Separator` primitives, and a flat list rendering pattern with avatar, name, and action controls. TEN-004's `TenantsPage` follows the same structural pattern but adds a tabular layout (shadcn `Table`) and cursor-based "Load more" pagination, which the contacts page does not currently need.

### 2.3 Tabs pattern

`frontend/src/pages/billing/BillingPage.tsx:3` imports `{ Tabs, TabsContent, TabsList, TabsTrigger }` from `@/components/ui/tabs` and uses them at lines 40–49 to organize usage/overview/wallet/methods/ledger/subscriptions sections. `TenantProfilePage` copies this exact six-tab structure (adapted to: Identity, Employment, Income, Emergency Contacts, Lease History) using the same shadcn `Tabs` primitives.

### 2.4 Infinite / cursor-based "Load more" pagination

`frontend/src/pages/earnings/EarningsPage.tsx:2,423` uses `useInfiniteQuery` with `getNextPageParam: (last) => last.next_cursor ?? undefined` and renders a "Load more" button gated by `hasNextPage` (`:544–545`). `TenantsPage` adopts this exact pattern for the tenant directory listing, passing each page's `next_cursor` as the `pageParam` for the next backend call.

### 2.5 File upload UX precedent

`frontend/src/pages/messages/FilePickerDialog.tsx` is a reusable file-browser dialog (`FilePickerDialogProps` at `:16`). For income-document upload, TEN-004 does **not** reuse this component (it browses existing nodes; income docs are new uploads). Instead, TEN-004 implements a direct file-upload `<input type="file">` inside the Income section, mirroring the newsfeed image-upload pattern (`frontend/src/pages/feed/CreatePost.tsx:1489` uses a hidden file input + `uploadPostImage` mutation). The uploaded file is sent as `multipart/form-data` to `POST /ui/property/tenants/{id}/income-docs` via the endpoint wrapper.

### 2.6 Zod + React Hook Form

The existing codebase uses React Hook Form + Zod validation for mutation-heavy forms, as seen throughout the registration and calendar pages. `TenantsPage`'s New-Tenant dialog and `TenantProfilePage`'s edit sections use `zodResolver` from `@hookform/resolvers/zod`, `useForm` from `react-hook-form`, and `z.object(...)` schemas defined co-located in each component file. The established patterns are `frontend/src/pages/Register.tsx:4,107` and `frontend/src/pages/calendar/EventDialog.tsx:3,66`. (Note: `RootRoleManagementPage.tsx` does NOT use zodResolver — it was incorrectly cited; confirmed absent via `grep -n "zodResolver" frontend/src/pages/admin/RootRoleManagementPage.tsx`.)

### 2.7 Feature-flag error handling

`frontend/src/api/client.ts:106` defines `ApiError` with a `status` field. The `TEN-003` endpoints return `HTTP 503` when the flag is off. Both pages catch `ApiError` where `error.status === 503` in their React Query `onError` / `isError` branches and render a `<Card>` with a "Property tenant management is not enabled on this server" message instead of an empty or broken state. This mirrors the bot-auto-reply pattern where the backend's 503 is surfaced as a clean disabled-feature state.

### 2.8 Router + auth conventions

All TEN-003 endpoints (`/ui/property/tenants/...`) use `Depends(require_ui_session)` (TEN-003 §4.2, following `app/routers/contacts.py:12`; `require_ui_session` is defined in `app/services/sessions.py:330`, not `app/auth/deps.py`). Write operations require the `X-CSRF-Token` header (exact case sent by the client), which the shared fetch-based `api` client in `frontend/src/api/client.ts:179–181` attaches automatically from the `ui_csrf` cookie via `getCookie("ui_csrf")`. No Bearer-auth path is used here; the UI always uses the cookie session.

## 4. API / Service Design

### 4.1 New file: `frontend/src/api/endpoints/propertyTenants.ts`

Uses the shared `api` client from `frontend/src/api/client.ts` (exported as `{ api }`, a custom `fetch`-based wrapper — not Axios; attaches `X-CSRF-Token` header automatically and handles 401 → logout). All functions are thin wrappers returning typed promises; React Query hooks live in the page components, not here. This is the same pattern as `frontend/src/api/endpoints/contacts.ts`, `tickets.ts`, etc.

```typescript
import { api } from "@/api/client";
import type {
  PropertyTenantOut, PropertyTenantListOut,
  CreatePropertyTenantIn, UpdatePropertyTenantIn,
  TenantProfileOut, TenantProfileIn,
  IncomeDocOut, IncomeDocListOut,
  TenantLeaseListOut,
} from "@/api/types";

const BASE = "/ui/property/tenants";

// ── Directory ──────────────────────────────────────────────────────────────
// NOTE: api.get(path, params) takes params as a flat Record<string,string>,
// not {params: ...} — this is a fetch-based client, not Axios (client.ts:290).
export const listPropertyTenants = (opts?: {
  status?: string; q?: string; cursor?: string; limit?: number;
}): Promise<PropertyTenantListOut> => {
  const params: Record<string, string> = {};
  if (opts?.status) params.status = opts.status;
  if (opts?.q) params.q = opts.q;
  if (opts?.cursor) params.cursor = opts.cursor;
  if (opts?.limit != null) params.limit = String(opts.limit);
  return api.get<PropertyTenantListOut>(BASE, params);
};

export const createPropertyTenant = (
  body: CreatePropertyTenantIn,
): Promise<PropertyTenantOut> =>
  api.post<PropertyTenantOut>(BASE, body);

export const getPropertyTenant = (
  tenantId: string,
): Promise<PropertyTenantOut> =>
  api.get<PropertyTenantOut>(`${BASE}/${tenantId}`);

export const updatePropertyTenant = (
  tenantId: string,
  body: UpdatePropertyTenantIn,
): Promise<PropertyTenantOut> =>
  api.patch<PropertyTenantOut>(`${BASE}/${tenantId}`, body);

// ── Profile ─────────────────────────────────────────────────────────────────
export const getTenantProfile = (
  tenantId: string,
): Promise<TenantProfileOut> =>
  api.get<TenantProfileOut>(`${BASE}/${tenantId}/profile`);

export const updateTenantProfile = (
  tenantId: string,
  body: TenantProfileIn,
): Promise<TenantProfileOut> =>
  api.put<TenantProfileOut>(`${BASE}/${tenantId}/profile`, body);

export const setIncomeVerification = (
  tenantId: string,
  status: string,
): Promise<TenantProfileOut> =>
  api.put<TenantProfileOut>(`${BASE}/${tenantId}/income-verification`, { status });

export const setActiveUnit = (
  tenantId: string,
  propertyId: string | null,  // required when unitId is non-null (TEN-002 §4.9)
  unitId: string | null,
): Promise<PropertyTenantOut> =>
  api.put<PropertyTenantOut>(`${BASE}/${tenantId}/active-unit`,
    { property_id: propertyId, unit_id: unitId });

// ── Income docs ──────────────────────────────────────────────────────────────
export const listIncomeDocs = (
  tenantId: string,
  opts?: { cursor?: string; limit?: number },
): Promise<IncomeDocListOut> => {
  const params: Record<string, string> = {};
  if (opts?.cursor) params.cursor = opts.cursor;
  if (opts?.limit != null) params.limit = String(opts.limit);
  return api.get<IncomeDocListOut>(`${BASE}/${tenantId}/income-docs`, params);
};

export const uploadIncomeDoc = (
  tenantId: string,
  file: File,
  docKind: string,
): Promise<IncomeDocOut> => {
  const fd = new FormData();
  fd.append("file", file);
  fd.append("doc_kind", docKind);
  // api.upload does NOT set Content-Type — browser adds multipart boundary automatically
  // (client.ts:319: "Does NOT set Content-Type — the browser adds the boundary automatically")
  return api.upload<IncomeDocOut>(`${BASE}/${tenantId}/income-docs`, fd);
};

export const deleteIncomeDoc = (
  tenantId: string,
  docId: string,
): Promise<void> =>
  api.del<void>(`${BASE}/${tenantId}/income-docs/${docId}`);
  // NOTE: the method is api.del (not api.delete) — client.ts:312

// ── Lease history ────────────────────────────────────────────────────────────
export const listTenantLeases = (
```

### 4.2 React Query key conventions

All React Query keys are arrays with a leading domain segment:

| Data | Query key |
|---|---|
| Tenant list (paginated) | `["propertyTenants", "list", { status, q }]` |
| Single tenant | `["propertyTenants", "detail", tenantId]` |
| Tenant profile | `["propertyTenants", "profile", tenantId]` |
| Income docs | `["propertyTenants", "incomeDocs", tenantId]` |
| Lease history | `["propertyTenants", "leases", tenantId]` |

On successful mutation (`createPropertyTenant`, `updatePropertyTenant`, `updateTenantProfile`, etc.) the relevant query key is invalidated via `queryClient.invalidateQueries(...)`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Tenant Directory Page (`TenantsPage.tsx`)

**Route:** `/property/tenants` (lazy-loaded, protected by `ProtectedRoute`).

**Layout:** Full-width container (`max-w-6xl mx-auto p-4 sm:p-6`) with:
- `PageHeader` ("Tenants", description "Manage your property tenants").
- A toolbar row: text search input (debounced 300ms, updates `q` param), status filter (shadcn `Select` with options "All", "Prospect", "Active", "Past"), and a "New Tenant" button.
- A shadcn `Table` with columns: Name, Email, Phone, Status (colored `Badge`), Active Unit, Created, Actions.
- A "Load more" button (enabled when `hasNextPage`), following the `EarningsPage.tsx:544–545` pattern.

**Cursor pagination:** `useInfiniteQuery` with:
```typescript
{
  queryKey: ["propertyTenants", "list", { status: filterStatus, q: debouncedQ }],
  queryFn: ({ pageParam }) =>
    listPropertyTenants({ status: filterStatus, q: debouncedQ, cursor: pageParam }),
  getNextPageParam: (last) => last.next_cursor ?? undefined,
  initialPageParam: undefined,
}
```
All pages are flattened: `data?.pages.flatMap(p => p.tenants) ?? []`. The status filter and search term both reset the infinite query (change the `queryKey`) — React Query automatically re-fetches from page 1.

**New-Tenant dialog:** A shadcn `Dialog` containing a React Hook Form validated by:
```typescript
const schema = z.object({
  display_name: z.string().min(1, "Name is required"),
  email: z.string().email("Invalid email").optional().or(z.literal("")),
  phone: z.string().optional().or(z.literal("")),
});
```
On submit, `useMutation` calls `createPropertyTenant`. On success: close dialog, invalidate `["propertyTenants", "list"]`, show `toast.success("Tenant created")`. On error: show `toast.error(error.message)`.

**503 state:** When `useInfiniteQuery` fails with `ApiError.status === 503`, render a single `Card` body: "Property tenant management is not available (PROPERTY_TENANTS_ENABLED is off on this server)." No retry button — the setting requires a server restart.

**Empty state:** When no tenants match and the query succeeded, render a centered illustration placeholder with "No tenants yet. Create your first tenant to get started."

**Loading state:** Skeleton rows (shadcn `Skeleton`) for the table body during initial fetch.

**Clicking a row** navigates to `/property/tenants/:tenantId` via `useNavigate`.

### 5.2 Tenant Profile Page (`TenantProfilePage.tsx`)

**Route:** `/property/tenants/:tenantId` (lazy-loaded, protected).

**Header:** Tenant `display_name`, status `Badge` (color-coded: prospect=gray, active=green, past=slate), `active_unit_id` (chip linking to the unit detail if PROP cluster is deployed, else plain text), and an "Edit" button that opens the identity edit inline or in a small `Dialog`.

**Five tabs** using `Tabs`/`TabsContent`/`TabsList`/`TabsTrigger` from `@/components/ui/tabs` (exactly as `BillingPage.tsx:3,40–49`):

#### Tab 1 — Identity
Displays `display_name`, `email`, `phone`, `party_id` (displayed as a code chip), `status`, `active_unit_id`. An "Edit" button opens a `Dialog` with a React Hook Form for `display_name`/`email`/`phone`/`status`, calling `updatePropertyTenant` on submit.

Active-unit field: a text input that calls `setActiveUnit`. When PROP cluster is live, this becomes a searchable `Combobox` populated from the PROP unit list; when PROP is absent (response is empty or 503), fall back to a plain text input. Clearing the field and confirming calls `setActiveUnit(tenantId, null)`.

#### Tab 2 — Employment
Displays the `employment` sub-object from `getTenantProfile`: employer name, job title, employment type (formatted), start date, employer phone. An "Edit" button opens a form with:
```typescript
const employmentSchema = z.object({
  employer_name: z.string().min(1, "Employer name is required"),
  job_title: z.string().optional(),
  employment_type: z.enum([
    "full_time","part_time","self_employed","contract","unemployed","retired","student"
  ]).optional(),
  start_date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/, "Use YYYY-MM-DD").optional().or(z.literal("")),
  employer_phone: z.string().optional().or(z.literal("")),
});
```
On submit, calls `updateTenantProfile(tenantId, { employment: formValues })`. Profile is read-merge-write on the backend (TEN-002 §4.3); income and emergency contacts are untouched.

#### Tab 3 — Income
Displays `income.annual_income_cents` (formatted as currency), `income.pay_frequency`, `income.income_currency`, and a verification status badge:
- `unverified` → gray badge "Unverified"
- `pending` → yellow badge "Pending"
- `verified` → green badge "Verified" + `verified_at` date + `verified_by` sub
- `rejected` → red badge "Rejected"

"Mark Verified" / "Mark Pending" / "Mark Rejected" action buttons (visible to owner only; enforcement is at the router — TEN-003 §5.7 notes the router checks role). Each calls `setIncomeVerification`. After success, invalidate `["propertyTenants", "profile", tenantId]`.

**Income Documents sub-section:** Below the income fields, a `Card` lists `IncomeDocOut` rows fetched via `listIncomeDocs`. Each row shows `file_name`, `doc_kind` badge, `size_bytes` formatted, `uploaded_at` date, and a delete button. Delete calls `deleteIncomeDoc` with a confirm popover (shadcn `Popover` with "Are you sure?" confirmation, matching the pattern in billing dispute UX).

Upload widget: An `<input type="file" accept="*/*" hidden ref={fileInputRef} />` triggered by a "Upload document" `Button`. A `Select` lets the user choose `doc_kind` before clicking upload. On file selection, `uploadIncomeDoc` is called in a `useMutation`. On success, invalidate `["propertyTenants", "incomeDocs", tenantId]`. Shows upload progress via `isPending` state on the button.

#### Tab 4 — Emergency Contacts
A list of up to 5 `EmergencyContactOut` entries. Each row displays `name`, `relationship`, `phone`, `email`, and a delete ("×") button.

An "Add contact" button appends an inline row with a mini-form:
```typescript
const ecSchema = z.object({
  name: z.string().min(1, "Name is required"),
  relationship: z.string().optional().or(z.literal("")),
  phone: z.string().optional().or(z.literal("")),
  email: z.string().email().optional().or(z.literal("")),
});
```
When confirmed, the current full list (existing contacts + new entry) is sent as `emergency_contacts` to `updateTenantProfile`. This full-list-replacement posture is correct: the backend's `update_profile` replaces the emergency_contacts list wholesale (TEN-002 §5.2). The frontend maintains the in-progress list in local state, only committing to the server on "Save contacts" — a "Save contacts" button is shown whenever local list differs from the server list (dirty-state detection via JSON.stringify comparison).

Delete: removes the entry from local state and triggers the same "Save contacts" commit.

Cap enforcement: "Add contact" button is disabled when `contacts.length >= 5`, with a tooltip "Maximum 5 emergency contacts".

#### Tab 5 — Lease History
Read-only table of `TenantLeaseSummaryOut` entries from `listTenantLeases`. Columns: Unit ID (link to `/property/units/:unitId` when PROP cluster is live, else plain text), Status badge (upcoming=blue, active=green, ended=gray), Start Date, End Date, Monthly Rent (formatted), Deposit.

Pagination: "Load more" button gated on `hasNextPage` from `useInfiniteQuery`.

**Empty state:** "No lease history" card when the list is empty.

**LSE unavailable state:** When `listTenantLeases` returns an empty list (the backend returns `[]` gracefully when LSE is off — TEN-003 §5.3), render the empty state without an error. Do not show 503 for this tab even if LSE is absent.

### 5.3 503 handling across all tabs

When any query in `TenantProfilePage` returns `ApiError.status === 503`, render a full-width `Alert` variant `"destructive"` at the top of the page: "Tenant management is currently disabled (PROPERTY_TENANTS_ENABLED is off). Contact your administrator." The page does not crash; tabs remain visible but all data queries show empty/loading states.

### 5.4 404 handling

When `getPropertyTenant` returns 404 (tenant does not exist, or belongs to a different owner), render an `ErrorPage` ("Tenant not found") with a "Back to tenants" link. The `ErrorPage` component is already used throughout the app at `frontend/src/components/shared/ErrorPage.tsx`.

### 5.5 Navigation and breadcrumbs

`TenantProfilePage` renders a breadcrumb trail: `Tenants / <display_name>`. **Correction**: `PageHeader` (`frontend/src/components/shared/PageHeader.tsx:3–24`) does NOT have a `breadcrumb` prop — it only accepts `title`, `description`, `actions`, `className`. There is no breadcrumb primitive in `ProjectDetailPage.tsx` either (`grep -rn "breadcrumb" frontend/src/pages/projects/ProjectDetailPage.tsx` returns nothing). The breadcrumb must be implemented inline above the `<PageHeader>` component, e.g. as a simple `<nav>` element with a `Link` to `/property/tenants` and the tenant's `display_name` as the current segment. Clicking "Tenants" navigates to `/property/tenants`. The browser Back button also works because both pages are separate routes.

### 5.6 Strict-mode-safe selectors (E2E concern)

`display_name` appears in both the table row and the profile page header. E2E tests must use scoped locators (e.g. `page.locator("tr").filter({ hasText: tenantName })`) to avoid strict-mode violations, following the CLAUDE.md pattern for sidebar-vs-bubble disambiguation.

## 6. Feature Flag & Config

### 6.1 Backend flag (inherited, not new)

`PROPERTY_TENANTS_ENABLED` (default `0` → `False`) is established by TEN-001 in `app/core/settings.py`. TEN-004 does not add any new backend setting.

### 6.2 Frontend feature flag

TEN-004 adds a Vite environment variable gate in `frontend/src/lib/featureFlags.ts`:

```typescript
export const propertyTenantsEnabled = toBool(
  env.VITE_PROPERTY_TENANTS_ENABLED, false
);
export const isPropertyTenantsEnabled = () => propertyTenantsEnabled;
```

This is **advisory only** — it can hide the sidebar nav entry and the lazy-import routes when the frontend knows the feature is off, preventing a visible-but-broken link. The authoritative gate is the backend 503. Frontend pages still handle 503 gracefully even when the flag is accidentally enabled client-side without the backend flag.

`frontend/.env.local.example` gains:
```
VITE_PROPERTY_TENANTS_ENABLED=false
```

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 No dev_mode branch

`propertyTenants.ts` contains no `if (import.meta.env.DEV)` branch. The `api` client (`api/client.ts`) handles cookies and CSRF the same way in dev and prod. Dev mock URLs (`/mock/s3/...`) for income docs are returned by the backend filemanager and surface as `IncomeDocOut.file_node_path` — the frontend renders them as-is in anchor `href` attributes, which work in dev (Vite proxies `/mock/s3/...` to the backend) and in prod (real S3 pre-signed URLs are returned by the backend). This is the same path taken by the messaging file-share feature (CLAUDE.md "File share messaging").

### 7.2 Money-safety

TEN-004 has no money-out path. No payment method is collected, no ledger entry is written, no Stripe/PayPal/CCBill interaction occurs. The rent ledger belongs to the RNT cluster. Income doc upload flows through `filemanager.upload_file` (quota-enforced, billed to the owner's storage quota, not to a payment provider). `annual_income_cents` is informational metadata — it is never passed to any billing primitive.

### 7.3 CSRF

All non-GET API calls (`createPropertyTenant`, `updatePropertyTenant`, `updateTenantProfile`, `setIncomeVerification`, `setActiveUnit`, `uploadIncomeDoc`, `deleteIncomeDoc`) go through the shared `api` client, which attaches `X-CSRF-Token: getCookie("ui_csrf")` (header name at `client.ts:181`) on every request when the `ui_csrf` cookie is present (CLAUDE.md §CSRF). No special handling is needed in TEN-004.

### 7.4 Owner-scoped access

The backend enforces `owner_id == ctx["user_sub"]` (TEN-001 §7.4, TEN-002 §7.4). The frontend does not implement additional client-side ownership checks — the backend 403 surfaces as `ApiError(403)`, which the mutation's `onError` handler converts to `toast.error("Not authorized")`. This is consistent with the rest of the codebase.

### 7.5 Income-doc upload at-most-once caution

The income-doc upload is not idempotent (TEN-002 §7.2): retrying on network timeout creates a duplicate `INCOMEDOC#` row. `TenantProfilePage` disables the upload button while `isPending` is `true` to prevent double-submissions. If the upload times out, the UI shows a `toast.error("Upload failed – please check your documents list before retrying")` to guide the user.

## 10. Open Questions / Assumptions

1. **Unit picker for `active_unit_id`**: The spec defaults to a plain text input when PROP-002 is absent. If PROP is always deployed alongside TEN-004, upgrade to a `Combobox` + `listUnits` API call for a richer UX. Decision deferred to implementation; the plain-text fallback is sufficient for the acceptance criteria.

2. **Lease detail navigation**: Lease rows in the history tab have a "unit_id" link. Whether this navigates to a PROP unit detail page (if `/property/units/:unitId` exists) or is plain text depends on whether PROP-004 (unit detail page) is available at deploy time. TEN-004 conditionally renders the link: if `import.meta.env.VITE_PROPERTY_UNITS_ENABLED === "true"`, render `<Link to={...}>`, else render plain text.

3. **income-doc download**: `IncomeDocOut.file_node_path` is a DDB path, not a presigned S3 URL. A future ticket should add a `GET /ui/property/tenants/{id}/income-docs/{doc_id}/download` endpoint (presigned URL for prod, `/mock/s3/...` redirect for dev). For now, TEN-004 renders the `file_node_path` as a non-clickable label. Tracked as follow-up.

4. **Sidebar nav placement**: The "Tenants" entry in the sidebar nav should nest under a "Property" section header alongside the PROP/LSE/RNT cluster pages. If the sidebar does not yet have a "Property" group, the entry can be placed alongside "Contacts" as a temporary location, with a refactor once PROP-004 adds the group header.

5. **Employment `start_date` display format**: The `start_date` is stored as ISO-8601 string (`YYYY-MM-DD`, TEN-002 §2.1). The UI can render it as-is or use `Intl.DateTimeFormat` for locale-specific display. The spec assumes locale-formatted display; the exact locale is left to the implementer.

6. **Role check for income verification in UI**: `setIncomeVerification` is restricted to admin/root at the router (TEN-003 §5.7). The TenantProfilePage should check `ctx.role >= ADMIN` (from `useAuthStore`) before showing "Mark Verified" buttons, to avoid a confusing 403 toast for USER-role landlords. This requires a clarification on whether landlords are expected to be `ADMIN` role or `USER` role — current assumption is that property landlords are `USER` role with ownership scoping, and income-verification is an admin/root-only action for compliance purposes.

7. **`propertyTenantsEnabled` Vite flag vs. backend 503**: Some deployments may enable the backend flag without updating the frontend env var (or vice versa). The pages handle this gracefully in both directions (503 → banner; flag off but API available → routes still work via the 503 banner). The Vite flag only gates the sidebar nav link.
