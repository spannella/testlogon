# PMD-002 — Document linking — property/unit/lease/tenant record-link on file-manager nodes (EVT-011 extension)

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 2 d
**Flag (primary):** `CRM_DOCUMENT_LIBRARY_ENABLED` (default OFF) — gates the file-manager
PATCH/search endpoints (EVT-011 flag, unchanged).
**Flag (secondary):** `PROPERTY_DASHBOARD_ENABLED` (default OFF, introduced by PMD-001) — gates
the property-scoped convenience-read endpoints added by this ticket. Both flags must be ON for
the `…/documents` endpoints to respond; either flag OFF returns HTTP 404.

---

## 1. Summary & Goal

The file-manager today has no concept of "this PDF is the lease for unit 4B." PMD-002 bridges
the real-estate spine (PROP/Unit/Lease/Tenant) to the existing file-manager document-library
by extending the EVT-011 record-link allowlist with four property-domain types and adding
thin property-scoped convenience-read endpoints that surface the linked files for a given
record.

The design is purely additive — no new DynamoDB table, no new GSI, no changes to existing
endpoints or data. All behavior is identical to today when either flag is off.

**Goals:**

1. Allow a file node to be linked to a `property`, `unit`, `lease`, or `tenant` record via the
   existing `PATCH /v1/fs/crm-metadata` endpoint and the `linked_record_type` field.
2. Allow callers to retrieve all documents linked to a specific property, unit, lease, or tenant
   via new convenience-read endpoints on the property-domain routers.
3. Ensure that when EVT-012 (`CRM_DOCUMENT_REVISIONS_ENABLED`) is also on, a lease document's
   record link is carried forward to the replacement live node on overwrite (EVT-012 §11
   carry-forward — no new code here; exercised in PMD-005 if EVT-012 is present).

**What this ticket does NOT do:**

- Validate that `linked_record_id` references an existing property/unit/lease/tenant record
  (opaque-string contract, same as the existing EVT-011 `contact`/`ticket`/`account` types).
- Implement a UI for document linking (deferred to PMD-004 or a standalone FE ticket).
- Introduce any new DynamoDB table, GSI, or schema migration.
- Fork or reimplement EVT-011 service logic.

## 2. Context & Current State

### 2.1 File-manager node shape — no record-link today

`upload_file` (`app/services/filemanager.py:2110-2188`) writes a node item whose attributes are
enumerated in EVT-011 §2 ("there is no `crm_category`, `crm_description`, `linked_record_type`,
or `linked_record_id` field today"). The node key layout is:

- `PK = USER#<owner_sub>` — assembled by `pk_user` (`app/services/filemanager.py:438-439`)
- `SK = NODE#<normalised_path>` — assembled by `sk_node` (`app/services/filemanager.py:442-443`)
- `node_key(user, path)` returns both (`app/services/filemanager.py:446-447`)

The `file_manager` table is declared at `scripts/local-ddb-init.py:327-335` with two GSIs
(`GSI1`, `GSI2`), both string sort keys — no `attr_types` entry is required for this ticket
because PMD-002 adds no new GSI or numeric key.

### 2.2 EVT-011 primitives that PMD-002 reuses verbatim

EVT-011 (`docs/suitecrm/specs/EVT-011.md`) delivers the two service functions PMD-002 depends
on — they are not reimplemented here, only extended:

- **`update_crm_metadata(owner, path, *, crm_category, crm_description, linked_record_type, linked_record_id)`**
  (`app/services/filemanager.py`, added by EVT-011) — writes the four CRM attributes to the
  existing `NODE#<path>` item via a targeted `update_item`. Validates `linked_record_type`
  against the module-level `_LINKED_RECORD_TYPES` frozenset before any DDB call (EVT-011 §4.1).

- **`search_by_linked_record(owner, linked_record_type, linked_record_id, *, limit, cursor)`**
  (`app/services/filemanager.py`, added by EVT-011) — paginated `scan` with

  (`EVT-011 §4.1`). Loop cap of 30 scan rounds mirrors `admin_search_metadata`
  (`app/services/filemanager.py:128-130`). Scoped to the caller's `PK` — no cross-user scan.

- **`_LINKED_RECORD_TYPES`** — the module-level frozenset at `app/services/filemanager.py`
  (added by EVT-011): `frozenset({"contact", "ticket", "account", "party"})`. PMD-002 widens

  - `PATCH /v1/fs/crm-metadata` — guarded by `_require_crm_document_library_enabled()` (→ 404

## 3. Data Model

### 3.1 No new DynamoDB table, no new GSI

All record-link data is stored as additive attributes on the existing `NODE#<path>` item in the
`file_manager` table (PK=`USER#<owner>`, SK=`NODE#<path>`). The attributes written by EVT-011's
`update_crm_metadata` are unchanged; PMD-002 only widens the valid values of the
`linked_record_type` string.

No new GSI is introduced. The `search_by_linked_record` scan is already user-scoped
(`FilterExpression = Attr("PK").eq(pk_user(owner)) & …`) so it is safe to run as a paginated
scan without a cross-user index.

**`scripts/local-ddb-init.py` is unchanged by this ticket.** The `file_manager` `TableDef` at
line 327 requires no new GSI entry and no new `attr_types` declaration. (EVT-012 adds `GSI3` +
`attr_types={"GSI3SK": "N"}` when it ships; that is EVT-012's concern, not PMD-002's.)

### 3.2 New attribute values for `linked_record_type`

PMD-002's entire data-model change is one line: widening `_LINKED_RECORD_TYPES` in
`app/services/filemanager.py` from the EVT-011 set to the union:

```python
_LINKED_RECORD_TYPES: frozenset[str] = frozenset({
    # EVT-011 originals — unchanged
    "contact", "ticket", "account", "party",
    # PMD-002 additions — property domain
    "property", "unit", "lease", "tenant",
})
```

All four new values follow the same opaque-string contract as the existing types: the
`linked_record_id` is accepted as-is without validating that the referenced record exists in
the `properties`, `leases`, or `property_tenants` tables (see §10, Open Question 1).

### 3.3 Attribute table for the four new record-link values

No new DDB attribute is introduced; the following table documents the valid `linked_record_type`
values and their semantics after PMD-002:

| `linked_record_type` | `linked_record_id` format | Referencing entity | Table (when entity is live) |
|---|---|---|---|
| `contact` | opaque string ≤ 200 chars | CRM contact (EVT-011 original) | `contacts` |
| `ticket` | opaque string ≤ 200 chars | Support ticket (EVT-011 original) | `tickets` |
| `account` | opaque string ≤ 200 chars | CRM account (EVT-011 original) | future PTY |
| `party` | opaque string ≤ 200 chars | PTY party (EVT-011 original) | future PTY |
| `property` | `property_id` string | Rental property (PROP-001) | `properties` |
| `unit` | `unit_id` string | Dwelling unit (PROP-002) | `properties` (sub-row) |
| `lease` | `lease_id` e.g. `LSE-2026-00042` | Lease agreement (LSE-001) | `leases` |
| `tenant` | `tenant_id` string | Property tenant (TEN-001) | `property_tenants` |

## 4. API / Service Design

### 4.1 Service change — `app/services/filemanager.py`

**One-line change** to the `_LINKED_RECORD_TYPES` constant (see §3.2). All other service
logic (`update_crm_metadata`, `search_by_linked_record`, validation, `SET`/`REMOVE` expression
construction, scan loop) is **unchanged and reused verbatim** as shipped by EVT-011.

No new service function is introduced. The convenience-read endpoints delegate directly to
`search_by_linked_record` via a thin adapter in each router.

### 4.2 Router changes — property-domain routers

Four convenience-read endpoints are added, one per record type. Each endpoint is a one-function
pass-through to `search_by_linked_record` with a fixed `linked_record_type` value. All four
use the same double-flag guard.

#### Guard helper (shared, inline in each router that uses it)

```python
def _require_property_documents_enabled() -> None:
    from app.core.settings import S
    if not (
        bool(getattr(S, "property_dashboard_enabled", False))
        and bool(getattr(S, "crm_document_library_enabled", False))
    ):
        raise HTTPException(status_code=404, detail="not found")
```

This guard mirrors `_require_crm_document_library_enabled()` (EVT-011 §4.4) and the
`_require_enabled()` pattern in `app/services/inventory.py:54-56`. It is defined inline in
each router that uses it (not a shared import) to avoid cross-router coupling.

#### `GET /ui/properties/{property_id}/documents`

Added to `app/routers/property_mgmt.py` (PROP-004 router).

```python
@router.get("/{property_id}/documents")
async def list_property_documents(
    property_id: str,
    limit: int = Query(50, ge=1, le=200),
    cursor: Optional[str] = Query(default=None),
    session: dict = Depends(require_ui_session),
) -> CrmSearchOut:
    _require_property_documents_enabled()
    user_sub = session["user_sub"]
    cursor_payload = decode_cursor(cursor)
    items, next_key = search_by_linked_record(
        user_sub,
        linked_record_type="property",
        linked_record_id=property_id,
        limit=limit,
        cursor=cursor_payload,
    )
    return CrmSearchOut(
        items=[_to_crm_metadata_out(it) for it in items],
        cursor=encode_cursor(next_key) if next_key else None,
        count=len(items),
    )
```

`_to_crm_metadata_out` is a small helper that extracts the five `CrmMetadataOut` fields
(`path`, `crm_category`, `crm_description`, `linked_record_type`, `linked_record_id`,
`crm_metadata_updated_at`) from a raw DDB item dict, identical in every convenience-read
endpoint.

## 5. Detailed Behavior & Edge Cases

### 5.1 Linking a file to a property record (nominal path)

1. Caller uploads a lease PDF: `POST /v1/fs/upload?path=/leases/unit4b-lease.pdf` (existing
   upload endpoint, unchanged).
2. Caller links the file to lease `LSE-2026-00042`:
   `PATCH /v1/fs/crm-metadata?path=/leases/unit4b-lease.pdf`
   with body `{"linked_record_type": "lease", "linked_record_id": "LSE-2026-00042", "crm_category": "Lease Agreement"}`.
3. `update_crm_metadata` validates `"lease" in _LINKED_RECORD_TYPES` (now true after PMD-002's
   widening), then issues `update_item` with `SET linked_record_type=:t, linked_record_id=:i,
   crm_category=:c, crm_metadata_updated_at=:ts`. The node item is updated in place.
4. Caller retrieves all documents for that lease:
   `GET /ui/leases/LSE-2026-00042/documents`.
5. Handler calls `search_by_linked_record(user_sub, "lease", "LSE-2026-00042", limit=50)`.
6. `search_by_linked_record` runs a `scan` on the `file_manager` table with
   `FilterExpression = PK=USER#<user_sub> & SK begins_with NODE# & linked_record_type="lease" & linked_record_id="LSE-2026-00042"`.
   Returns the lease PDF node. Response: `{"items": [{path, crm_category, ...}], "cursor": null, "count": 1}`.

### 5.2 Unknown `linked_record_type` still rejected

Passing `linked_record_type="invoice"` (or any value not in the widened `_LINKED_RECORD_TYPES`)
to `PATCH /v1/fs/crm-metadata` still raises HTTP 400 with `{"code": "invalid_linked_record_type"}`
from EVT-011's validation step. PMD-002 does not change the rejection behavior for unknown types;
it only adds four more accepted values to the closed set.

### 5.3 Cross-user isolation

`search_by_linked_record` scopes its `FilterExpression` to `Attr("PK").eq(pk_user(owner))`
where `owner = session["user_sub"]` from the authenticated session. A landlord (Alice) querying
`GET /ui/properties/P-001/documents` will never see Bob's files even if Bob independently linked
a file to the same property ID. The scan partition is always the authenticated user's own
`USER#<sub>` partition.

### 5.4 File linked to a deleted or non-existent record

The convenience-read endpoints do not validate that the referenced property/unit/lease/tenant
exists. If a record was deleted after the file was linked, `GET /ui/leases/{id}/documents`
still returns the linked file node (assuming the file itself is not soft-deleted). This is
consistent with the EVT-011 opaque-string contract and avoids a cross-service dependency at
read time. A future cleanup job (out of scope) could scan for dangling links.

### 5.5 FilterExpression and scan loop correctness

DynamoDB `FilterExpression` does not reduce page size (CLAUDE.md "DDB FilterExpression doesn't
reduce page size" gotcha). `search_by_linked_record` already implements the correct
`LastEvaluatedKey` loop with the 30-scan-round cap (`app/services/filemanager.py:128-130`
pattern). The convenience-read endpoints inherit this behavior via direct delegation — no
additional loop is written.

### 5.6 Pagination cursor encoding

`search_by_linked_record` returns a raw DDB `LastEvaluatedKey` dict as its second return value.
The convenience-read endpoints encode it with `encode_cursor(next_key)` from
`app/core/cursor.py:94` (HMAC-signed, version-prefixed token). Incoming `cursor` query
parameters are decoded with `decode_cursor(cursor)` from `app/core/cursor.py:103`. Both
functions are already imported by the property-domain routers via the LSE-002 pattern
(`docs/open-property/specs/LSE-002.md` §2 primitives table).

### 5.7 SFTP-mounted paths

The `PATCH /v1/fs/crm-metadata` endpoint calls `_enforce_sftp_mount_flags_for_path(path, operation="write")`
(`app/routers/filemanager.py:426-435`). This is EVT-011's code and is unchanged. The
convenience-read endpoints do not call this guard because `search_by_linked_record` scans only
`NODE#` items — SFTP-mounted items are stored in a separate backend and never appear as `NODE#`
items in the `file_manager` table.

### 5.8 EVT-012 carry-forward (informational)

When `CRM_DOCUMENT_REVISIONS_ENABLED` is also on and a lease PDF is overwritten, EVT-012's
`_archive_revision` archives the prior node (preserving `linked_record_type=lease` and
`linked_record_id`) and the new live node inherits the CRM fields because EVT-012 explicitly
copies them from `existing_node` into the replacement item (EVT-012 §11 "carry EVT-011 fields
forward"). PMD-002 requires no code to support this — it is a consequence of the carry-forward
logic in EVT-012. The integration is exercised in PMD-005 §cross-module when EVT-012 is
present.

### 5.9 Both flags off — no DDB access

When either `CRM_DOCUMENT_LIBRARY_ENABLED` or `PROPERTY_DASHBOARD_ENABLED` is off:
- `PATCH /v1/fs/crm-metadata` → 404 (EVT-011 guard, unchanged).
- `GET /v1/fs/crm-search` → 404 (EVT-011 guard, unchanged).
- `GET /ui/*/documents` → 404 (`_require_property_documents_enabled()` guard fires before
  any `search_by_linked_record` call).
No DDB read or write occurs in either case.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 parity

PMD-002 contains no `if S.dev_mode` branch. The entire implementation consists of:

- One constant widening in `app/services/filemanager.py` (`_LINKED_RECORD_TYPES`).
- Four router handler functions in the property-domain routers, each delegating to
  `search_by_linked_record` — a pure DynamoDB `scan` call.

`search_by_linked_record` uses `_table()` (`app/services/filemanager.py:104-107`) which calls
`ddb.Table(S.filemgr_table_name)`. In dev this resolves to DynamoDB Local (port 8001); in prod
to real DynamoDB. The code path is identical. Mirrors the EVT-011 parity guarantee (EVT-011 §7
"no `if S.dev_mode` branches").

### 7.2 Idempotency

`update_crm_metadata` (EVT-011) uses `update_item` — calling it twice with the same payload
produces the same final item state (second call advances `crm_metadata_updated_at` only,
no side effects). The convenience-read endpoints are read-only and naturally idempotent.

### 7.3 Security — ownership enforcement

Every read path is scoped to `session["user_sub"]`. The `search_by_linked_record` `FilterExpression`
anchors on `Attr("PK").eq(pk_user(owner))` where `owner` is the authenticated user's sub.
No cross-user file can appear in the result regardless of `linked_record_id` value. The
write path (`update_crm_metadata`) additionally validates node ownership via `get_node(owner, path)`
(`app/services/filemanager.py:450-457`) before issuing the `update_item` (EVT-011 §7 "ownership
enforcement").

### 7.4 Money safety (not directly applicable)

PMD-002 is a pure document-metadata feature with no monetary operations. The rent ledger
(`billing_shared.new_ledger_entry`, `compute_due`, `settle_or_reverse_ledger`) is not touched
by this ticket. Documents may be linked to lease records whose corresponding ledger rows are
managed by the RNT cluster, but PMD-002 has no code path that reads or writes billing data.
The money-safety constraint from the POLICY_DOCS_DASHBOARD_TICKETS.md header is satisfied
by absence.

### 7.5 Input sanitisation

All four new `linked_record_type` values are constants validated by the closed frozenset
check in `update_crm_metadata` (EVT-011). `linked_record_id` max length 200 chars is enforced
by Pydantic `Field(max_length=200)` (EVT-011 §4.2) before the service is called. Path-injection
is impossible because DDB attribute names are hardcoded strings.

## 8. Backward Compatibility & Migration

### 8.1 Zero migration required

The `_LINKED_RECORD_TYPES` widening is a purely additive change to an in-process constant.
Existing nodes in the `file_manager` table that have no `linked_record_type` attribute are
unaffected. Nodes with `linked_record_type` ∈ `{"contact", "ticket", "account", "party"}`
(written by EVT-011 before PMD-002) continue to work identically.

### 8.2 No DynamoDB schema change

`scripts/local-ddb-init.py` is unchanged. No `UpdateTable` call, no backfill script, no GSI
addition. `just restart` continues to work without modification.

### 8.3 Flag toggling safety

Turning `PROPERTY_DASHBOARD_ENABLED` on after previously off: all existing file nodes are
unaffected; nodes already linked to `property`/`unit`/`lease`/`tenant` (written while the EVT-011
flag was on but PROPERTY_DASHBOARD_ENABLED was off) immediately become discoverable via the
convenience-read endpoints. No data migration required.

Turning `CRM_DOCUMENT_LIBRARY_ENABLED` off after it was on: the convenience-read endpoints
return 404, but the `linked_record_type` and `linked_record_id` attributes remain in the DDB
items — they are not removed. Re-enabling the flag restores full functionality without any
data loss.

### 8.4 EVT-011 vs PMD-002 deployment ordering

PMD-002 is a strict forward-extension of EVT-011. EVT-011 must be deployed first. If PMD-002
is deployed before EVT-011, `update_crm_metadata` and `search_by_linked_record` do not exist
in `app/services/filemanager.py` and the router imports will fail at startup. The dependency
order in the PR pipeline must be enforced (EVT-011 merged → PMD-002 merged).

## 10. Open Questions / Assumptions

1. **No existence validation for `linked_record_id`.** The spec deliberately treats
   `linked_record_id` as an opaque string for all four new record types. If PROP/LSE/TEN
   routers are deployed but PMD-002 has not yet validated referential integrity, a dangling
   link (e.g. `lease_id` pointing to a deleted lease) causes no error at read time — the file
   node still appears in the search result. A referential-integrity pass (validating the ID
   against the target table) is deferred to a follow-on ticket or PMD-005 integration test.

2. **Property documents vs. unit documents — should `property` link also surface unit files?**
   In the current design, `GET /ui/properties/{id}/documents` returns only nodes explicitly
   linked with `linked_record_type="property"`, not files linked to child `unit` records of
   that property. A "roll-up" query (property documents + all unit documents for units belonging
   to that property) would require either multiple `search_by_linked_record` calls fan-out or a
   new GSI. Deferred — the simple per-type query is the correct first step.

3. **Unit `linked_record_id` globally unique assumption.** The spec assumes `unit_id` values
   are globally unique (not composite keys). If PROP-002 scopes `unit_id` per-property (e.g.
   `unit_id="U-001"` within property `P-001` is different from `unit_id="U-001"` in `P-002`),
   the search results for `linked_record_type="unit", linked_record_id="U-001"` would be
   ambiguous. PMD-002 assumes PROP-002 generates globally unique unit IDs (e.g. UUID-based or
   composite like `UNIT#{property_id}#{seq}`). If this assumption is wrong, the
   `linked_record_id` for units should be the composite `{property_id}#{unit_id}` string.

4. **`CrmSearchOut` import path.** EVT-011 defines `CrmSearchOut` / `CrmMetadataOut` inline in
   `app/routers/filemanager.py` (EVT-011 §4.2). If these models remain inline (not promoted to
   `app/models.py`), the property-domain routers must import from `app.routers.filemanager`,
   which creates a router-to-router import. The cleaner option is for EVT-011 to promote the
   models to `app/models.py`; PMD-002 can adopt whichever location EVT-011 chooses.

5. **Auth symmetry: `_current_user` vs `require_ui_session`.** EVT-011's endpoints use
   `_current_user` (which supports both session cookies and API key principals,
   `app/routers/filemanager.py:249-254`). The property-domain convenience-read endpoints use
   `require_ui_session` (session-only). This asymmetry means API-key callers can write record
   links via EVT-011 but cannot read them via the PMD-002 convenience endpoints. Assumption:
   this is acceptable for the initial implementation; a follow-up can align the auth dependency.
