# WOV-003 — Optional escrowed paid maintenance (bounty/escrow on a work order)

**Type**: Feature | **Priority**: P2 | **Estimate**: 2d
**Source**: `docs/open-property/WORKORDERS_VENDORS_TICKETS.md` §WOV-003 +
`docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §C
**Depends on**: WOV-001, WOV-002, WOV-004 (vendor directory), TBT-001, TBT-003, TBT-006, TBT-007

---

## 1. Summary & Goal

WOV-003 allows a work order to carry an escrowed dollar amount — funded by the
posting staff member from their platform wallet at work-order creation time and
released to the assigned vendor on completion (or refunded on cancellation). It
extends WOV-001/002 with an **optional**, sub-flag-gated money layer by
**delegating entirely to the Ticket Bounty escrow primitives** (TBT-003
`post_bounty`-equivalent, TBT-006 release, TBT-007 refund) rather than
introducing new billing math. When the sub-flag `MAINTENANCE_ORDERS_ESCROW_ENABLED`
is off (the default), work orders are pure maintenance records — the existing
WOV-001/002 create and transition paths are unchanged in every measurable way.

Key design decisions:
- **Escrow row lives on `T.billing`** — co-located with per-user ledger entries,
  no new DynamoDB table, no new GSI (TBT-001 §3.2 rationale applies verbatim).
- **All ledger writes go through `billing_shared.new_ledger_entry`** — the platform
  financial dashboard (`app/services/platform_financial_dashboard.py`) and
  `compute_due` (`billing_shared.py:158`) remain read-only consumers; no fork of
  those functions.
- **`settle_or_reverse_ledger` (not delete) for void** — cancelled escrow produces
  a reversal ledger entry; no row is ever deleted.
- **No online payment provider** — funds come exclusively from the poster's
  platform wallet balance (`apply_wallet_delta`, `billing_shared.py:185`).

## 2. Context & Current State

### 2.1 WOV-001/002 — the maintenance-order foundation

`app/services/maintenance_orders.py` (delivered by WOV-001/002) provides:
- `create_work_order(property_id, body: MaintenanceOrderIn, actor_sub)` — idempotent,
  deterministic-id (`sha256(corr)[:32]`), stores `wo_status="open"`, optional
  `cost_cents` field (reporting-only, no ledger write per WOV-001 §5.8).
- `transition_work_order(property_id, work_order_id, body: MaintenanceOrderTransitionIn, actor_sub)`
  — enforces `VALID_TRANSITIONS`, `ConditionExpression="wo_status = :current"` guard,
  sets `completed_at` + `cost_cents` on `completed`.
- `VALID_TRANSITIONS` (WOV-002): terminal states `"completed"` and `"cancelled"` have
  empty successor sets; once a WO is in either terminal state no further transitions
  are possible.
- Table: `maintenance_orders`, PK `PROPERTY#{property_id}`, SK `WO#{work_order_id}`,
  GSIs `GSI_WO_STATUS` and `GSI_WO_ASSIGNEE` (both `created_at` numeric sort key,
  `attr_types={"created_at": "N"}` — WOV-001 §3.1).
- Feature flag: `S.maintenance_orders_enabled` / `MAINTENANCE_ORDERS_ENABLED`
  (default `false`); `_require_enabled()` pattern from `app/services/inventory.py:50–56`.

WOV-001 §5.8 explicitly states that `cost_cents` is a plain reporting field and that
"optional escrowed paid maintenance where real money moves is the scope of WOV-003."

### 2.2 Ticket Bounty escrow primitives

The escrow infrastructure used by WOV-003 is defined in the TBT cluster:

**TBT-001** (`docs/ticket-bounty/specs/TBT-001.md` §3.1): The escrow sentinel row
lives on `T.billing` with PK `BOUNTY#{bounty_id}` / SK `"ESCROW"`. Attributes:
`bounty_id`, `ticket_id`, `poster_sub`, `amount_cents`, `currency`, `status`
(`"held"` → `"released"` / `"refunded"`), `created_at`, `ledger_sk`. This decision
is authoritative for WOV-003: the maintenance escrow row follows the exact same
shape, substituting `work_order_id` for `ticket_id` and using a
`MAINT_ESCROW#{work_order_id}` PK prefix to namespace it from bounty rows.

**TBT-003** (`docs/ticket-bounty/specs/TBT-003.md` §4): `post_bounty` in
`app/services/ticket_bounties.py` — three-item `transact_write_items` on
`T.billing`: (a) wallet debit `ConditionExpression="wallet_balance_cents >= :amount"`
on `USER#{poster_sub}/WALLET`, (b) escrow Put with `attribute_not_exists(pk)`,
(c) ledger entry Put. Uses `_transact_client()` (mirrors
`group_treasury.py:716–740`), `_to_ddb_item` (`group_treasury.py:47–53`).
WOV-003 does not import `post_bounty` directly; it replicates the
three-item transaction pattern for the maintenance domain (different PK prefix,
`vendor_sub` instead of `assignee_sub`).

**TBT-006** (`docs/ticket-bounty/specs/TBT-006.md` §2): Release is a credit-only
`new_ledger_entry(entry_type="credit", state="settled", reason="bounty_payout")`
to the assignee's `USER#{vendor_sub}` partition, followed by
`apply_wallet_delta(T.billing, user_pk(vendor_sub), +net_cents)` and
`settle_or_reverse_ledger(T.billing, "pk", user_pk(poster_sub), escrow.ledger_sk, "settled_released")`.
WOV-003 mirrors this for maintenance payouts using `reason="maintenance_payout"`.

**TBT-007** (`docs/ticket-bounty/specs/TBT-007.md` §2): Refund pattern mirrors
`refund_payment` (`app/routers/billing.py:1286–1344`): write
`new_ledger_entry(entry_type="adjustment", state="settled", reason="refund")` to
poster + credit wallet via `apply_wallet_delta` + call
`settle_or_reverse_ledger(..., "reversed")` on the original debit ledger sk.
Conditional on `ConditionExpression="escrow_status = :held"` to prevent
double-refund.

## 3. Data Model

### 3.1 Escrow sentinel row on `T.billing`

WOV-003 follows TBT-001 §3.2 exactly: the escrow sentinel lives on the existing
`T.billing` table (`app/core/tables.py:333`, table name from
`S.billing_table_name` at `app/core/settings.py:348`, default `"billing"`).
**No new DynamoDB table. No new GSI. No `attr_types` change.**

The billing table `TableDef` (`scripts/local-ddb-init.py:67–77`) already declares
`pk`/`sk` as generic strings and the single `GSI_LEDGER_DATE` index keyed on the
string attribute `ledger_date`. The escrow row does **not** set `ledger_date`, so
it is sparse to that GSI and never appears in platform-financial-dashboard date
scans — exactly matching TBT-001 §3.3.

**Row key:**

| Key | Type | Value |
|---|---|---|
| `pk` | S | `"MAINT_ESCROW#{work_order_id}"` |
| `sk` | S | `"ESCROW"` |

The `MAINT_ESCROW#` prefix namespaces maintenance escrow rows from the
`BOUNTY#{bounty_id}` rows created by TBT-003, preventing accidental PK collision
even if `_bounty_id(work_order_id)` and `work_order_id` were to clash.

**Item attributes written at hold time:**

| Attribute | DDB Type | Notes |
|---|---|---|
| `pk` | S | `MAINT_ESCROW#{work_order_id}` |
| `sk` | S | `"ESCROW"` |
| `work_order_id` | S | Denormalized FK to `maintenance_orders` |
| `property_id` | S | Denormalized from the work order (audit context) |
| `poster_sub` | S | Staff member whose wallet is debited |
| `vendor_sub` | S | Initially absent; set when vendor is assigned (see §5.4) |
| `amount_cents` | N | Validated in `[min_cents, max_cents]` |
| `currency` | S | `"usd"` (v1 only) |
| `escrow_status` | S | `"held"` on creation; `"released"` / `"refunded"` on terminal |
| `created_at` | N | `now_ts()` |
| `released_at` | N | Set by release path |
| `refunded_at` | N | Set by refund path |
| `ledger_sk` | S | SK of the paired poster-debit ledger entry |
| `payout_ledger_sk` | S | SK of the payout-credit ledger entry (set on release) |
| `refund_ledger_sk` | S | SK of the poster-credit ledger entry (set on refund) |
| `payout_target` | S | Decision D2: `"wallet"` (vendor `user_sub` linked) or `"clearing"` (external vendor → `CLEARING#maintenance`); set on release |
| `payout_sub` | S | Decision D2: the credited sub on release — the vendor's `user_sub` (wallet path) or the reserved `CLEARING#maintenance` system sub (clearing path) |
| `disbursement_status` | S | Decision D2, clearing path only: `"pending"` when escrow lands in the clearing account awaiting off-platform admin disbursement; `"disbursed"` once an admin reconciles it (out of scope for v1 — the marker is written, the disbursement endpoint is a follow-up) |

### 3.2 Ledger entries on `T.billing`

Three ledger entry types are written over the escrow lifecycle, all via
`billing_shared.new_ledger_entry(...)` (`billing_shared.py:224`):

| Phase | `entry_type` | PK | `state` | `reason` |
|---|---|---|---|---|
| Hold (fund) | `"debit"` | `USER#{poster_sub}` | `"pending"` | `"maintenance_escrow"` |
| Release — linked vendor (D2) | `"credit"` | `USER#{vendor_sub}` | `"settled"` | `"maintenance_payout"` |
| Release — external vendor (D2) | `"credit"` | `USER#CLEARING#maintenance` | `"settled"` | `"maintenance_payout_clearing"` |
| Refund (cancel) | `"adjustment"` | `USER#{poster_sub}` | `"settled"` | `"maintenance_escrow_refund"` |

**Decision D2 (hybrid payout)**: the release-credit PK depends on whether the assigned vendor has a linked platform account (`VendorOut.user_sub`, WOV-004 §3.4). If `user_sub` is set, the credit lands on `USER#{vendor_sub}` (the on-platform wallet path). If the vendor is external (no `user_sub`), the credit lands on the reserved maintenance clearing account `USER#CLEARING#maintenance` and a pending-disbursement marker is written for an admin to disburse off-platform and reconcile. Both branches use the **same** `new_ledger_entry` mechanism and the same atomic transaction shape — there is no second ledger system and no double-pay.

On release, the hold ledger entry is flipped to `"settled_released"` via
`settle_or_reverse_ledger(T.billing, "pk", user_pk(poster_sub), escrow.ledger_sk, "settled_released")`.
On refund, it is flipped to `"reversed"`. Neither path deletes any row.

### 3.3 Work-order row additions

Two additive attributes are written to the `maintenance_orders` row
(PK `PROPERTY#{property_id}`, SK `WO#{work_order_id}`) by this ticket:

| Attribute | DDB Type | Notes |
|---|---|---|
| `escrow_amount_cents` | N | Absent when no escrow; set at fund time; never updated |
| `escrow_status` | S | `"held"` / `"released"` / `"refunded"`; absent when no escrow |

These attributes are absent from rows created before WOV-003 is enabled (sparse
attribute policy — `_item_to_out` uses `.get()` with `None` default). No
backfill is needed.

### 3.4 No new GSI / no `attr_types` change

The `maintenance_orders` table already has `attr_types={"created_at": "N"}` for its
two existing GSIs (WOV-001 §3.1). WOV-003 adds no new index; the two new
attributes `escrow_amount_cents` and `escrow_status` are top-level item attributes
not used as any GSI key. No change to `scripts/local-ddb-init.py` is required for
table-schema purposes (only the settings block and model additions touch other files).

### 4.4 Service functions in `app/services/maintenance_orders.py`

#### `fund_work_order_escrow(work_order_id, property_id, poster_sub, amount_cents) -> None`

Called from `create_work_order` when `body.amount_cents` is not `None` and the
sub-flag is on. Not a public endpoint; internal to the service module.

Step-by-step:
1. `_require_enabled()` + `_require_escrow_enabled()`.
2. Validate `amount_cents` ∈ `[S.maintenance_escrow_min_cents, S.maintenance_escrow_max_cents]`
   → `HTTPException(422, detail="escrow_amount_out_of_range")`.
3. Check that no held escrow already exists for this `work_order_id` (idempotency
   guard): `T.billing.get_item(Key={"pk": f"MAINT_ESCROW#{work_order_id}", "sk": "ESCROW"})`;
   if `"Item"` present and `item["escrow_status"] == "held"` → return (idempotent no-op).
4. Build `ts = now_ts()`; `entry_id = ulidish()`;
   `lsk, ledger_item = new_ledger_entry(key_name="pk", key_value=user_pk(poster_sub), entry_type="debit", amount_cents=amount_cents, state="pending", reason="maintenance_escrow", meta={"work_order_id": work_order_id, "property_id": property_id})`.
5. Build three `transact_write_items` items (pattern: `group_treasury.py:631–751`):
   - **(a) Wallet debit** `Update` on `USER#{poster_sub}` / `WALLET`:
     `UpdateExpression="SET wallet_balance_cents = wallet_balance_cents + :neg, updated_at = :t"`,
     `ConditionExpression="wallet_balance_cents >= :amount"` (insufficient balance →
     `TransactionCanceledException`, reason index 0 → `HTTPException(402, "insufficient_wallet_balance")`).
   - **(b) Escrow Put** on `MAINT_ESCROW#{work_order_id}` / `ESCROW`:
     `ConditionExpression="attribute_not_exists(pk)"` (idempotency guard → if
     `ConditionalCheckFailed` on item b → idempotent success, return).
   - **(c) Ledger Put** on `USER#{poster_sub}` / `lsk`:
     `ConditionExpression="attribute_not_exists(sk)"` (belt-and-suspenders).
6. Serialize all items with `_to_ddb_item(...)` and call `_transact_client().transact_write_items(...)`.
7. On success: `update_item` on `T.maintenance_orders` to stamp `escrow_amount_cents` and
   `escrow_status="held"` on the WO row (separate non-transactional update; crash recovery
   via idempotent re-call per TBT-003 §5 step 8 rationale).
8. `_audit("maintenance_escrow.funded", poster_sub, work_order_id=work_order_id, amount_cents=amount_cents)`.

#### `_release_escrow(work_order_id, property_id, vendor_id, poster_sub) -> None`

Called from `transition_work_order` on `target="completed"` when `escrow_status="held"`.
Not a public endpoint. **Decision D2 (hybrid payout)**: the function resolves the
assigned vendor's optional platform-account link and pays either the linked wallet or
the maintenance clearing account — it never dead-ends with a 409 for an unlinked vendor.

The reserved clearing-account sub is a module-level constant:

```python
MAINT_CLEARING_SUB = "CLEARING#maintenance"   # reserved system sub; never a real user
```

Step-by-step:
1. Load escrow row: `T.billing.get_item(Key={"pk": f"MAINT_ESCROW#{work_order_id}", "sk": "ESCROW"})`.
   If absent or `escrow_status != "held"` → raise `HTTPException(409, "escrow_not_held")`.
2. **Resolve payout target (decision D2)** via `_resolve_payout_target(vendor_id)` (§5.4):
   - vendor has a linked `user_sub` → `payout_sub = user_sub`, `payout_target = "wallet"`.
   - vendor is external (no `user_sub`) OR `vendor_id` is absent OR WOV-004 not built →
     `payout_sub = MAINT_CLEARING_SUB`, `payout_target = "clearing"`.

   This step does NOT raise for a missing/unlinked vendor — that is the whole point of
   the D2 fallback. (A genuinely unknown `vendor_id` that WOV-004 *can* resolve but that
   carries no `user_sub` also routes to clearing; see §5.4.)
3. Compute fee: `fee_cents = escrow.amount_cents * S.maintenance_escrow_fee_bps // 10000`.
   `net_cents = escrow.amount_cents - fee_cents`.
4. Build payout ledger entry against the resolved target:
   `payout_lsk, payout_item = new_ledger_entry(key_name="pk", key_value=user_pk(payout_sub), entry_type="credit", amount_cents=net_cents, state="settled", reason=("maintenance_payout" if payout_target == "wallet" else "maintenance_payout_clearing"), meta={"work_order_id": work_order_id, "property_id": property_id, "payout_target": payout_target})`.
5–8. **Single atomic `transact_write_items`** (mandatory — see MONEY-SAFETY below; mirrors TBT-006 `approve_bounty`). Serialize each item with `_to_ddb_item(...)` and submit via `_transact_client().transact_write_items(TransactItems=[...])`:
   - (a) **Payout ledger `Put`**: `payout_item` from step 4.
   - (b) **Payout wallet credit `Update`**: `+net_cents` on `user_pk(payout_sub)` wallet row (the same balance mutation `apply_wallet_delta` performs, expressed as a transaction item so it commits atomically with the rest). On the clearing path this credits the `CLEARING#maintenance` wallet row — identical mechanism, no special-casing.
   - (c) **Escrow row `Update`** with `ConditionExpression="escrow_status = :held"`: `SET escrow_status = "released", released_at = now_ts(), payout_ledger_sk = payout_lsk, payout_sub = :ps, payout_target = :pt[, vendor_sub = :vs][, disbursement_status = "pending"]`. The `disbursement_status = "pending"` clause is included **only** on the clearing path so an admin can later disburse + reconcile. `vendor_sub` is set when a linked sub was resolved.
   A `TransactionCanceledException` whose cancellation reason is the (c) condition failure → escrow already released → treat as idempotent success (no second payout, because (a)/(b) roll back with it). The original poster-debit ledger settle (`settle_or_reverse_ledger(T.billing, "pk", user_pk(poster_sub), escrow.ledger_sk, "settled_released")`) is a separate, idempotent state-flip and may run after the transaction commits.
9. Update WO row: `escrow_status="released"` on `T.maintenance_orders`.
10. `_audit("maintenance_escrow.released", payout_sub, work_order_id=work_order_id, net_cents=net_cents, payout_target=payout_target)`.

Because both branches differ only in the **resolved `payout_sub`/`payout_target`** and an
extra `disbursement_status="pending"` marker on the clearing branch, they share one ledger
write, one wallet-credit mechanism, and one atomic transaction — exactly-once payout is
guaranteed by the same `ConditionExpression="escrow_status = :held"` guard regardless of
which target was chosen (no double-pay across the two branches).

**MONEY-SAFETY — release MUST be atomic (resolved)**: Steps 5–8 of `_release_escrow`
**must** be committed as a single `transact_write_items` call, exactly mirroring the
TBT-006 `approve_bounty` release that this ticket delegates to
(`docs/ticket-bounty/specs/TBT-006.md` §4.1 — atomic multi-item transaction including
the escrow-status flip). The transaction holds three items: (a) payout ledger `Put`,
(b) vendor wallet `Update` (the credit), and (c) escrow row `Update` setting
`escrow_status="released"` guarded by `ConditionExpression="escrow_status = :held"`.
Because the conditional escrow-row update is committed in the **same** transaction as
the wallet credit and ledger write, DynamoDB guarantees exactly-once payout: a retry
after a crash either finds the transaction already committed (escrow row no longer
`"held"` → condition fails → no second credit) or finds it never committed (safe to
re-run). A non-atomic put-then-update sequence is **not acceptable** here, because the
wallet credit would land before the conditional guard is evaluated, enabling a
double-credit on crash-retry. `_refund_escrow` follows the identical atomic pattern
(refund ledger `Put` + poster wallet `Update` + escrow-row conditional `Update`).

If `S.maintenance_escrow_payout_hold_seconds > 0` (default 0): instead of
crediting the vendor wallet immediately, write a `state="pending"` credit entry
and schedule settlement via the audit trail; in v1 with the default of 0 this
branch is never taken.

#### `_refund_escrow(work_order_id, poster_sub) -> None`

Called from `transition_work_order` on `target="cancelled"` when `escrow_status="held"`.

Step-by-step:
1. Load escrow row. If absent or `escrow_status != "held"` → no-op (WO cancelled with no
   escrow, or double-cancel; either case is safe to ignore).
2. Write refund ledger entry:
   `refund_lsk, refund_item = new_ledger_entry(key_name="pk", key_value=user_pk(poster_sub), entry_type="adjustment", amount_cents=escrow.amount_cents, state="settled", reason="maintenance_escrow_refund", meta={"work_order_id": work_order_id})`.
   `T.billing.put_item(Item=refund_item)`.
3. Credit poster wallet: `apply_wallet_delta(T.billing, user_pk(poster_sub), +escrow.amount_cents)`.
4. Reverse original debit ledger:
   `settle_or_reverse_ledger(T.billing, "pk", user_pk(poster_sub), escrow.ledger_sk, "reversed")`.
5. Update escrow row: conditional `update_item` with
   `ConditionExpression="escrow_status = :held"` to prevent double-refund;
   set `escrow_status="refunded"`, `refunded_at=now_ts()`, `refund_ledger_sk=refund_lsk`.
   `ConditionalCheckFailedException` → already refunded (idempotent success).
6. Update WO row: `escrow_status="refunded"` on `T.maintenance_orders`.
7. `_audit("maintenance_escrow.refunded", poster_sub, work_order_id=work_order_id, amount_cents=escrow.amount_cents)`.

#### Modifications to `create_work_order`

```python
def create_work_order(property_id, body: MaintenanceOrderIn, actor_sub) -> MaintenanceOrderOut:
    _require_enabled()
    # ... existing validation and DDB put (WOV-001) ...
    if body.amount_cents is not None:
        if not _escrow_enabled():
            raise HTTPException(422, detail="escrow_not_enabled")
        fund_work_order_escrow(
            work_order_id=work_order_id,
            property_id=property_id,
            poster_sub=actor_sub,
            amount_cents=body.amount_cents,
        )
    # ... return _item_to_out(item) ...
```

When `_escrow_enabled()` is `False` and the caller sends `amount_cents`, the
function raises 422. When `_escrow_enabled()` is `True`, escrow funding runs after
the WO row is written and before the function returns.

#### Modifications to `transition_work_order`

```python
def transition_work_order(property_id, work_order_id, body: MaintenanceOrderTransitionIn, actor_sub):
    _require_enabled()
    # ... existing fetch, VALID_TRANSITIONS check (WOV-002) ...
    if _escrow_enabled():
        # Re-read the current item to check escrow_status BEFORE committing status change.
        # Escrow release/refund must run first (and succeed) so that any error from
        # _release_escrow / _refund_escrow leaves the WO status unchanged.
        item = get_work_order(property_id, work_order_id)  # pre-transition read
        if body.target_status == "completed" and item.escrow_status == "held":
            # Decision D2: _release_escrow resolves the vendor link internally and
            # pays the linked wallet OR the maintenance clearing account. It does NOT
            # raise 409 for an unlinked/missing vendor (the clearing fallback covers it).
            _release_escrow(work_order_id, property_id, item.vendor_id, actor_sub)
        elif body.target_status == "cancelled" and item.escrow_status == "held":
            _refund_escrow(work_order_id, actor_sub)
    # Only AFTER the escrow block succeeds (or is skipped): commit the WO status update.
    # ... conditional update_item (WOV-002) ...
    # ... return ...
```

**CORRECTED from draft**: the escrow block must run **before** the WOV-002
`update_item` that advances `wo_status`, not after. If `_release_escrow` (or
`_refund_escrow`) raises, the `update_item` is never reached — the WO status is
unchanged (see §5.5). Note that under decision D2 the common "no linked vendor"
case no longer raises: `_release_escrow` falls back to the clearing account and the
transition proceeds. Implementers must reorder the
WOV-002 `update_item` to the end of `transition_work_order`, after the escrow block.

The escrow block is entirely guarded by `_escrow_enabled()`; when the sub-flag is
off this block is never entered, and `transition_work_order` behaves byte-for-byte
as WOV-002.

### 4.5 Router additions

No new endpoints are added by WOV-003. The existing router endpoints from WOV-002
(`POST /ui/properties/{property_id}/work-orders`,
`PATCH /ui/maintenance/work-orders/{work_order_id}`) absorb the escrow logic
transparently — callers pass `amount_cents` on create and the lifecycle transitions
trigger escrow release/refund automatically. The router does not need to know about
escrow internals. `MaintenanceOrderOut` gains the two new optional fields which are
serialized in the response JSON when present.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behavior (default)

With `MAINTENANCE_ORDERS_ESCROW_ENABLED=false`:
- `create_work_order` with `amount_cents` → 422 `"escrow_not_enabled"` before any
  DDB write.
- `create_work_order` without `amount_cents` → unchanged WOV-001/002 behavior.
- `transition_work_order` → unchanged WOV-002 behavior; the `_escrow_enabled()` guard
  is `False`, so the escrow block is skipped entirely.
- No `MAINT_ESCROW#` rows are ever written. No ledger entries for maintenance escrow.
  Platform billing system is byte-for-byte unchanged.

### 5.2 Idempotency on fund

`fund_work_order_escrow` is idempotent: if the escrow row already exists with
`escrow_status="held"` (from a prior successful call), the function detects it at
step 3 and returns without a second debit. The `attribute_not_exists(pk)` guard in
the transaction (step 6b) provides an additional atomic layer — only one escrow
row can exist per `work_order_id`.

If a network timeout occurs between the `transact_write_items` (step 6) and the
WO row update (step 7), the escrow row exists but the WO's `escrow_status` field
is absent. On retry, step 3 detects the existing escrow row and skips the
transaction, then proceeds to step 7 to converge the WO row — identical to the
TBT-003 §5 step 8 crash-recovery design.

### 5.3 Idempotency on release and refund

Both `_release_escrow` and `_refund_escrow` use a
`ConditionExpression="escrow_status = :held"` conditional `update_item` on the
escrow row (step 8 / step 5 respectively). A second call after successful
release/refund hits `ConditionalCheckFailedException`, which the code treats as an
idempotent success (already in terminal state). This prevents double-credit and
double-refund at the DDB atomic-update level.

### 5.4 Payout-target resolution (decision D2 — hybrid)

`_release_escrow` needs a `payout_sub` to credit. The work-order row stores `vendor_id`
(the WOV-004 `supplier_id`); the WOV-004 vendor record carries an **optional**
`user_sub` (WOV-004 §3.4, decision D2) linking the vendor to a platform account. Under
decision D2 (`docs/CROSS_TICKET_AUDIT.md §D2`) WOV-003 resolves the payout target with a
**never-409 fallback**:

```python
MAINT_CLEARING_SUB = "CLEARING#maintenance"   # reserved system sub; never a real user

def _resolve_payout_target(vendor_id: str | None) -> tuple[str, str]:
    """
    Returns (payout_sub, payout_target).
    payout_target == "wallet"   → pay the vendor's linked platform wallet.
    payout_target == "clearing" → pay the maintenance clearing account
                                   (external vendor; admin disburses off-platform).
    Never raises for a missing/unlinked vendor — that is the D2 fallback.
    """
    if vendor_id:
        try:
            from app.services.maintenance_vendors import get_vendor  # lazy; avoids circular dep
            vendor = get_vendor(vendor_id)
            sub = getattr(vendor, "user_sub", None) if vendor else None
            if sub:
                return sub, "wallet"
        except ImportError:
            pass  # WOV-004 not yet built → clearing fallback
    return MAINT_CLEARING_SUB, "clearing"
```

Behavior under the four cases:

- **Linked vendor** (`get_vendor(...).user_sub` set) → `("sub_vendor", "wallet")`; the
  escrow net amount is credited directly to the vendor's platform wallet (the original
  on-platform path).
- **External vendor** (vendor resolves but has no `user_sub`) → `(MAINT_CLEARING_SUB, "clearing")`.
- **No `vendor_id` on the WO** (escrow funded but never assigned) → clearing.
- **WOV-004 not yet built** (`ImportError`) → clearing.

The clearing branch credits `USER#CLEARING#maintenance` and stamps
`disbursement_status="pending"` on the escrow row so an admin can later disburse the
funds off-platform (e.g. ACH to the external vendor) and mark the marker `"disbursed"`
during reconciliation. The disbursement/reconciliation endpoint is a follow-up (see §5.7);
v1 writes the marker and routes the money safely into the clearing account.

The old hard 409 `"vendor_has_no_user_sub"` dead-end is **removed** — it is now the
clearing-account fallback. Completing a WO with escrow and no linked vendor therefore
succeeds (funds park in the clearing account) instead of blocking the transition.

The escrow row's `vendor_sub` field (when a linked sub is known) may still be stamped
at assign time: WOV-002's `assign_work_order` can call a thin
`_update_escrow_vendor_sub(work_order_id, vendor_sub)` helper as an additive,
best-effort update. This is purely informational; `_release_escrow` re-resolves the
target authoritatively at release time so a vendor linked after assignment is honored.

### 5.5 Completing with no assigned (or unlinked) vendor — decision D2

Under decision D2 this is no longer a dead-end. If `transition_work_order(target="completed")`
is called when `escrow_status="held"` AND the WO has no `vendor_id`, or has a `vendor_id`
whose WOV-004 record carries no `user_sub`:

- `_resolve_payout_target` returns `(MAINT_CLEARING_SUB, "clearing")`. `_release_escrow`
  credits the maintenance clearing account, stamps `disbursement_status="pending"` on the
  escrow row, and the transition **proceeds** — the WO advances to `"completed"`. The funds
  are safely parked in the clearing account for an admin to disburse off-platform and
  reconcile.

This replaces the previous behavior (409 `"no_vendor_assigned"` / `"vendor_has_no_user_sub"`
that blocked the transition). Operators are no longer forced to link a platform account
before completing a WO with escrow.

Recommended operator workflow when on-platform payout is desired: link the vendor to a
platform account (`PATCH /ui/maintenance/vendors/{id}` with `user_sub`, WOV-004) before
completing, so the payout lands in the vendor's wallet instead of the clearing account.
The escrow can still be voided/refunded to the poster via the admin escrow-void path
(§5.7) if completion is not appropriate.

### 5.6 Completing with released/refunded escrow

If `escrow_status` is already `"released"` or `"refunded"` (e.g., admin voided the
escrow earlier), `transition_work_order(target="completed")` skips the
`_release_escrow` call (because `item.escrow_status != "held"`). The WO transitions
to `"completed"` normally with no money movement. This is intentional — escrow and
lifecycle are decoupled after escrow is settled.

### 5.7 Admin escrow-void endpoint (optional, deferred to WOV-005 scope)

An admin-only endpoint `POST /ui/maintenance/work-orders/{id}/escrow/void` (staff
or ROOT only) calling `_refund_escrow` directly allows staff to release an
otherwise-stuck held escrow (e.g., vendor permanently unavailable). This endpoint
is listed here as a behavioral note; its implementation may be deferred to WOV-005
or a follow-up ticket since the refund path is already implemented.

**Decision D2 — clearing-account disbursement (follow-up)**: when escrow released to
the `CLEARING#maintenance` account (external vendor, §5.4), the funds sit there with
`disbursement_status="pending"` on the escrow row. A companion admin/ROOT endpoint
(e.g. `POST /ui/maintenance/work-orders/{id}/escrow/disburse`) records the off-platform
disbursement (ACH/check reference) and flips the marker to `"disbursed"` for
reconciliation. v1 of WOV-003 writes the pending marker but defers the disbursement
endpoint itself; the money is already safely accounted for in the clearing account's
wallet + ledger, so no funds are at risk while the endpoint is pending.

### 5.8 Fee-bps = 0 default

With `S.maintenance_escrow_fee_bps = 0` (the default):
`fee_cents = amount * 0 // 10000 = 0`, so `net_cents = amount_cents` and no fee
ledger entry is written. The vendor receives the full escrowed amount. This mirrors
TBT-001 §4.1 Open Decision D1.

### 5.9 No online payment provider

`fund_work_order_escrow` deducts funds exclusively from `USER#{poster_sub}/WALLET`
(platform wallet balance). It never calls Stripe, PayPal, or CCBill. The wallet
must be pre-funded. Insufficient balance → 402.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 Dev/prod parity

There are **zero `if S.dev_mode` branches** in `maintenance_orders.py` for the
escrow path. `T.billing` is the same handle in both environments; in dev, boto3
calls are intercepted by DynamoDB Local (port 8001) via the existing moto/endpoint
setup; in prod they reach real AWS DynamoDB. The `_transact_client()` helper derives
endpoint and credentials from `T.billing.meta.client` at call time
(`group_treasury.py:716–740` precedent), ensuring no hard-coded endpoint divergence.
No mock branches, no `S.dev_mode` guards — SECOPS-007 parity is unconditional.

### 7.2 Money-safety invariants

1. **Poster debited exactly once.** The `attribute_not_exists(pk)` guard on the
   escrow `Put` item in `transact_write_items` makes double-debit physically
   impossible: only one `MAINT_ESCROW#{id}/ESCROW` row can ever exist.

2. **Atomicity of hold.** The wallet debit and escrow creation are in one
   `transact_write_items` call. Partial failure leaves either both committed or
   neither — no phantom hold, no phantom debit.

3. **Void via reversal, never delete.** `_refund_escrow` calls
   `settle_or_reverse_ledger(..., "reversed")` on the original debit ledger entry
   (`billing_shared.py:262–274`). The ledger entry is never deleted. The
   `"reversed"` state signals a settled reversal in `compute_due` and the
   platform financial dashboard — the audit trail is complete.

4. **Release is credit-only.** `_release_escrow` writes a new `"credit"` ledger
   entry to the **resolved payout partition** (decision D2: the linked vendor's
   `USER#{vendor_sub}` on the wallet path, or `USER#CLEARING#maintenance` on the
   clearing path) and credits that wallet. The poster's debit entry is settled
   (not reversed) — it remains in the audit trail as a legitimate spend. No second
   debit on the poster. `write_tip_ledger` (which writes both debit + credit in one
   call) is explicitly **not used** (TBT-006 §1 and TBT-007 §2 rationale: using it
   would double-debit the poster).

   **Decision D2 money-safety — single ledger, no double-pay across branches.** The
   wallet and clearing branches are mutually exclusive per release and share the
   identical atomic `transact_write_items` (payout ledger `Put` + wallet credit
   `Update` + escrow-row conditional `Update` guarded by `escrow_status = :held`).
   Exactly-once payout therefore holds regardless of which target was resolved: a
   crash-retry finds the escrow row already non-`"held"` and the condition fails, so
   neither a second wallet credit nor a second clearing credit can occur. The
   clearing path adds only a `disbursement_status="pending"` marker (no extra money
   movement) — off-platform disbursement is a separate, later admin action against
   funds already in the clearing account, not a second escrow payout.

5. **`compute_due` and `apply_balance_delta` used unmodified.** The wallet
   **debit** in `fund_work_order_escrow` is performed as an `Update` action inside
   `transact_write_items` (step 5a), NOT via `apply_wallet_delta` — this is
   intentional so the debit, escrow Put, and ledger Put are committed atomically.
   The wallet **credit** on release (`_release_escrow` step 6) and **credit** on
   refund (`_refund_escrow` step 3) DO use `apply_wallet_delta(T.billing, pk,
   +amount)` (`billing_shared.py:185`). WOV-003 does NOT call `apply_balance_delta`
   (`billing_shared.py:83`) — the `owed_settled_cents` / `payments_settled_cents`
   counters on BALANCE rows are rent-ledger concepts managed by the RNT cluster,
   not by maintenance escrow. `compute_due` (`billing_shared.py:158`) reads those
   counters and is left entirely unmodified. No fork of any billing primitive.

6. **Double-release / double-refund prevented.** Both `_release_escrow` and
   `_refund_escrow` use `ConditionExpression="escrow_status = :held"` on the
   atomic escrow-row update. After the first terminal operation, `escrow_status`
   is no longer `"held"`, so any concurrent or replayed call hits
   `ConditionalCheckFailedException` and is treated as a no-op.

### 7.3 Security

- **Actor is the poster.** `actor_sub` (from the authenticated session) is used as
  `poster_sub` in `fund_work_order_escrow`; it is never taken from the request
  body. No impersonation path.
- **Staff-only mutations.** `create_work_order` and `transition_work_order` are
  gated by `require_admin_or_root_csrf` in the WOV-002 router; escrow funding and
  release/refund are downstream of those same auth checks.
- **Vendor wallet isolation.** The payout target is resolved server-side
  (decision D2): either the `user_sub` on the assigned vendor's WOV-004 record, or
  the fixed reserved `CLEARING#maintenance` system sub. A caller cannot specify an
  arbitrary payout recipient — neither the vendor link nor the clearing sub comes
  from the request body. The clearing sub is a constant, never a user-supplied value.

## 8. Backward Compatibility & Migration

### 8.1 Fully additive

WOV-003 modifies exactly these files:
- `app/core/settings.py` — five new fields appended inside the WOV block.
- `app/models.py` — two new optional fields appended to `MaintenanceOrderIn`
  and `MaintenanceOrderOut`.
- `app/services/maintenance_orders.py` — new internal functions
  (`fund_work_order_escrow`, `_release_escrow`, `_refund_escrow`,
  `_resolve_payout_target` (decision D2), `_escrow_enabled`,
  `_require_escrow_enabled`) plus the `MAINT_CLEARING_SUB` constant and
  two conditional code blocks inside `create_work_order` and
  `transition_work_order`. No existing function signature changes.
- `.env.local.example` — new comment block.

No router file is changed (WOV-003 is transparent to the HTTP layer). No
`scripts/local-ddb-init.py` change is needed. No existing test is broken.

### 8.2 Existing work orders

Work orders created before WOV-003 is enabled have no `escrow_amount_cents` or
`escrow_status` attribute. `_item_to_out` uses `.get()` for both fields, returning
`None`. `MaintenanceOrderOut.escrow_amount_cents` and `.escrow_status` serialize
as `null` in JSON. No backfill is needed. Completing or cancelling such a WO with
`_escrow_enabled()` on simply skips the escrow block (the `if item.escrow_status == "held"`
guard is `False`).

### 8.3 Enabling escrow on a running system

Recommended production sequence:
1. Deploy code with `MAINTENANCE_ORDERS_ESCROW_ENABLED=false` (default). No
   `T.billing` writes for escrow; no behavioral change.
2. Ensure the `billing` table exists (it already does — no new table needed).
3. Set `MAINTENANCE_ORDERS_ESCROW_ENABLED=true` and deploy. From this point,
   `create_work_order` with `amount_cents` funds escrow.

No schema migration. No backfill. Rollback = flip the sub-flag back to `false`;
in-flight `"held"` escrows remain in `T.billing` and are refundable via the
`_refund_escrow` path (e.g., through an admin escrow-void endpoint) after rollback.

## 10. Open Questions / Assumptions

1. **TBT cluster build status.** WOV-003 replicates the TBT escrow transaction pattern
   (`group_treasury.py` primitives) rather than importing `post_bounty` directly, because
   the TBT service module (`app/services/ticket_bounties.py`) may not yet be merged when
   WOV-003 ships. If TBT-003 is available, `fund_work_order_escrow` may delegate to a
   shared escrow utility rather than duplicating `_transact_client`/`_to_ddb_item`. The
   decision is: prefer the thin delegation pattern if TBT is merged; fall back to the
   inline copy if not.

2. **`vendor_sub` resolution — RESOLVED (decision D2, 2026-06-13).** Previously
   ESCALATED: WOV-004 `VendorOut` had no `user_sub`, so `_resolve_vendor_sub` always
   returned `None` and every release raised 409 `"vendor_has_no_user_sub"`. Decision
   D2 (`docs/CROSS_TICKET_AUDIT.md §D2`) resolves this with a **hybrid payout**:
   (a) WOV-004 now defines an optional `user_sub` on the vendor model (WOV-004 §3.4,
   §5.10); (b) `_release_escrow` resolves the target via `_resolve_payout_target`
   (§5.4) — linked vendor → pay the wallet; external/unlinked vendor → credit the
   `CLEARING#maintenance` clearing account + write a pending-disbursement marker for
   off-platform admin payout. The 409 dead-end is removed. Both branches use the same
   single ledger mechanism and are idempotent/money-safe (§7.2 invariant 4). WOV-003
   escrow release now works end-to-end whether or not the vendor has a platform
   account.

3. **Partial completions.** If a work order covers multiple vendors (e.g., split work),
   WOV-003 does not support split payouts. The entire escrowed amount goes to the single
   assigned vendor. Multi-vendor split payout is a v2 concern.

4. **`maintenance_escrow_payout_hold_seconds > 0` (deferred).** The setting is parsed and
   stored; the hold logic (deferring wallet credit) is not implemented in v1. With the
   default of 0 this branch is never taken. The hold path (writing a `pending` credit
   ledger entry and scheduling a settlement) would mirror the `ticket_bounty_payout_hold_seconds`
   path in TBT-006 and is deferred to a follow-up.

5. **Assumption — `T.billing` table key schema.** Verified: `scripts/local-ddb-init.py:67–77`
   declares `pk`/`sk` as generic strings. A `MAINT_ESCROW#` prefix is accepted with no
   schema change.

6. **Assumption — `_to_ddb_item` filters `None` values.** Verified: `group_treasury.py:53`
   uses `{k: _serializer.serialize(v) for k, v in item.items() if v is not None}`.
   Attributes with `None` values (e.g., `vendor_sub` before assignment) must be omitted
   from the escrow row dict at transaction build time, not set to `None`.

### Cross-ticket reconciliation (decision D2, 2026-06-13)

Per `docs/CROSS_TICKET_AUDIT.md §D2` (hybrid vendor payout), `_release_escrow` now resolves its payout target via `_resolve_payout_target` (§5.4) instead of the old `_resolve_vendor_sub` 409 dead-end: if the assigned vendor's WOV-004 record carries a `user_sub` (the new optional platform-account link), the escrow net amount is credited to that wallet via the existing on-platform path (`new_ledger_entry` credit + atomic wallet `Update` + `settle_or_reverse_ledger`); otherwise (external vendor, no `vendor_id`, or WOV-004 unbuilt) it is credited to the reserved `CLEARING#maintenance` clearing account with a `disbursement_status="pending"` marker for an admin to disburse off-platform and reconcile. The former hard 409 `vendor_has_no_user_sub` is removed (now the clearing fallback), so completing an escrowed WO never blocks on a missing vendor link. Both branches share a single ledger mechanism and the same atomic `transact_write_items` guarded by `ConditionExpression="escrow_status = :held"`, keeping payout exactly-once and money-safe with no double-pay (§3.1, §3.2, §4.4, §5.4, §5.5, §7.2, §7.3, §9.1, §10 item 2, §11.1, verification row 34). This resolves the previously escalated open product decision (WOV-003 §10 item 2 / row 34) and pairs with the optional `VendorOut.user_sub` field added in WOV-004.
