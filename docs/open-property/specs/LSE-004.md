## 1. Summary & Goal

LSE-004 delivers the **React frontend surface** for the Lease entity: a filterable,
paginated lease table with inline editing, a status-transition control, and a reusable
tenant lease-history panel. The gap analysis (§B row 56) names this surface explicitly:
*"Lease table + status filter + inline edit … mirror QUO-004 list pattern"*. The ticket
delivers:

1. **`frontend/src/api/types.ts`** additions — `Lease`, `LeaseCreateInput`,
   `LeasePatchInput`, `LeaseListResponse` TypeScript interfaces mirroring the LSE-002
   Pydantic models (`LeaseOut`, `LeaseCreateIn`, `LeasePatchIn`, `LeaseListOut`).
2. **`frontend/src/api/endpoints/leases.ts`** — eight typed wrappers over the LSE-002/003
   endpoints using the shared `api` client from `frontend/src/api/client.ts`.
3. **`frontend/src/pages/leases/LeasesPage.tsx`** — lease table (shadcn `DataTable`) with a
   status-filter segmented control, cursor-based load-more pagination, expiry flagging, and
   inline-edit cells for mutable fields.
4. **`frontend/src/pages/leases/LeaseCreateDialog.tsx`** — React Hook Form + Zod creation
   dialog.
5. **`frontend/src/pages/leases/TenantLeasesPanel.tsx`** — reusable tenant lease-history
   panel consumed by the TEN tenant-profile page.
6. **Route `/leases`** added to `frontend/src/App.tsx` as a lazy-loaded protected route,
   degrading gracefully (empty/"not enabled" state) when the backend returns 404.
7. **E2E spec** `frontend/e2e/leases.spec.ts` covering all six sections (CRUD API, status
   filter + pagination, inline edit + transition, tenant history, admin-list authz,
   flag-off guard).

Money movement is entirely out of scope for this ticket. The `monthly_rent_cents` and
`security_deposit_cents` values displayed here are informational integers stored by LSE-001;
the downstream RNT rent-run cluster is the sole caller of
`billing_shared.new_ledger_entry` (`app/services/billing_shared.py:224`). LSE-004 never
posts, reads, or displays billing ledger rows.

## 4. API / Service Design

### 4.1 Endpoint wrappers — `frontend/src/api/endpoints/leases.ts`

New file. Mirrors the structure of `tenants.ts` (optional params → `Record<string,string>`)
and `billing.ts` (one-liner arrows). All functions import `api` from `@/api/client` and
types from `@/api/types`.

```typescript
import { api } from "@/api/client";
import type {
  Lease,
  LeaseCreateInput,
  LeasePatchInput,
  LeaseListResponse,
  LeaseStatusTransitionInput,
} from "@/api/types";

const BASE = "/ui/leases";

/** Create a new lease (POST /ui/leases). */
export const createLease = (body: LeaseCreateInput): Promise<Lease> =>
  api.post<Lease>(BASE, body);

/** List leases with optional status filter and cursor pagination. */
export function listLeases(params?: {
  status?: string;
  limit?: number;
  cursor?: string;
}): Promise<LeaseListResponse> {
  const qs: Record<string, string> = {};
  if (params?.status) qs.status = params.status;
  if (params?.limit)  qs.limit  = String(params.limit);
  if (params?.cursor) qs.cursor = params.cursor;
  return api.get<LeaseListResponse>(BASE, qs);
}

/** Get a single lease by id. */
export const getLease = (id: string): Promise<Lease> =>
  api.get<Lease>(`${BASE}/${id}`);

/** Inline-edit mutable fields (PATCH /ui/leases/{id}). */
export const updateLease = (id: string, patch: LeasePatchInput): Promise<Lease> =>
  api.patch<Lease>(`${BASE}/${id}`, patch);

/** Transition lease status (POST /ui/leases/{id}/status). */
export const transitionLeaseStatus = (
  id: string,
  body: LeaseStatusTransitionInput,
): Promise<Lease> =>
  api.post<Lease>(`${BASE}/${id}/status`, body);

/** List leases expiring within N days (GET /ui/leases/expiring).
 *  Returns LeaseListResponse shape (leases[], count, next_cursor — always null
 *  for this endpoint per LSE-003 §4.3). */
export function listExpiringLeases(withinDays?: number): Promise<LeaseListResponse> {
  const qs: Record<string, string> = {};
  if (withinDays !== undefined) qs.within_days = String(withinDays);
  return api.get<LeaseListResponse>(`${BASE}/expiring`, qs);
}

/** All leases for a tenant — history panel (GET /ui/tenants/{id}/leases). */
export function listTenantLeases(
  tenantId: string,
  params?: { cursor?: string; limit?: number },
): Promise<LeaseListResponse> {
  const qs: Record<string, string> = {};
  if (params?.cursor) qs.cursor = params.cursor;
  if (params?.limit)  qs.limit  = String(params.limit);
  return api.get<LeaseListResponse>(`/ui/tenants/${tenantId}/leases`, qs);
}

/** Admin cross-owner lease list (GET /ui/admin/leases, ADMIN/ROOT only). */
export function adminListLeases(params?: {
  cursor?: string;
  limit?: number;
}): Promise<LeaseListResponse> {
  const qs: Record<string, string> = {};
  if (params?.cursor) qs.cursor = params.cursor;
  if (params?.limit)  qs.limit  = String(params.limit);
  return api.get<LeaseListResponse>("/ui/admin/leases", qs);
}
```

**Note on CSRF**: `api.post` and `api.patch` in `frontend/src/api/client.ts` automatically
attach the `x-csrf-token` header by reading the `ui_csrf` cookie. No caller-side CSRF
handling is needed (pattern already verified in `billing.ts`, `tickets.ts`, etc.).

### 4.2 Pages and components (`frontend/src/pages/leases/`)

#### `LeasesPage.tsx`

The primary page. Mounts at route `/leases`.


## 5. Detailed Behavior & Edge Cases

### 5.1 Inline editing — mutable fields

Each mutable column in the lease table renders in one of two modes: **display** (static
text / formatted value) and **edit** (focused `<Input>` or `<Select>`). The toggle is
managed by a `editingCell: { leaseId: string; field: string } | null` state local to
`LeasesPage`.

**Editable fields and their input types:**

| Field | Input | Constraint hint shown |
|---|---|---|
| `monthly_rent_cents` | `number` input (shows dollars: `value / 100`) | "Must be ≥ 0" |
| `security_deposit_cents` | `number` input (shows dollars) | "Must be ≥ 0" |
| `rent_due_day` | `number` input | "Day 1–28" |
| `end_date` | date picker / `<Input type="date">` | "Leave blank for open-ended" |
| `notes` | `<Textarea>` | — |
| `late_fee_type` | `<Select>` (none / flat / percent) | — |
| `late_fee_cents` | `number` input | Shown only when `late_fee_type="flat"` |
| `late_fee_percent_bps` | `number` input | Shown only when `late_fee_type="percent"` |
| `late_fee_grace_days` | `number` input | — |
| `renewal_notice_days` | `number` input | "Days before end-date to send notice" |

**Commit flow:**

1. User presses Enter or blurs the focused cell → call `updateLease(lease.lease_id, patch)`
   via `useMutation`.
2. `onSuccess`: `queryClient.invalidateQueries({ queryKey: ["leases"] })` + close edit
   mode for that cell.
3. `onError`: toast the error message; keep the cell in edit mode so the user can
   correct the value. A 400 `invalid_late_fee_config` error is surfaced as
   `"Late fee configuration invalid: flat fee requires a non-zero amount"`.
4. Pressing Escape cancels without committing (resets local edit state to the prior value).

**Immutable fields** (`lease_number`, `tenant_id`, `property_id`, `unit_id`, `start_date`,
`status`, `lease_id`, `created_at`, `updated_at`) are rendered as plain text with no
click-to-edit handler. The `status` column uses a dedicated transition control (§5.2).

### 5.2 Status transition control

The `status` column renders:

1. A colored `<Badge>` showing the current status.
2. A `<Select>` dropdown populated with only the **legal next states** derived from the
   frontend-side `_LEASE_TRANSITIONS` map (mirrors `app/services/leases.py:_LEASE_TRANSITIONS`
   defined in LSE-001 ticket):

```typescript
const LEASE_TRANSITIONS: Record<string, string[]> = {
  draft:    ["upcoming", "active"],
  upcoming: ["active", "ended"],
  active:   ["ended"],
  ended:    [],  // terminal — dropdown hidden
};
```

When `LEASE_TRANSITIONS[currentStatus].length === 0` (i.e. status is `"ended"`), the
select is replaced by the badge alone (no control rendered).

**Transition mutation:**
```typescript
const transitionMut = useMutation({
  mutationFn: ({ id, status }: { id: string; status: string }) =>
    transitionLeaseStatus(id, { status }),
  onSuccess: () => {
    toast.success("Lease status updated");
    queryClient.invalidateQueries({ queryKey: ["leases"] });
  },
  onError: (err: AxiosError) => {
    const code = (err.response?.data as any)?.detail;
    if (err.response?.status === 400) {
      toast.error(`Invalid transition: ${code ?? "check lease status"}`);
    } else if (err.response?.status === 409) {
      toast.error("Another update happened concurrently — please refresh");
      queryClient.invalidateQueries({ queryKey: ["leases"] });
    } else {
      toast.error(`Status change failed: ${err.message}`);
    }
  },
});
```

The 400 `invalid_status_transition` and 409 `concurrent_update` errors (from LSE-001
`transition_status`) are surfaced as descriptive toasts rather than generic errors.

### 5.3 Expiry flagging

A row whose `status === "active"` and `end_date !== null` and
`end_date - Date.now() / 1000 <= 60 * 86400` (within 60 days) is highlighted with an
amber `<Badge variant="outline">Expiring soon</Badge>` in the term column and a warning
icon (`AlertTriangle` from lucide-react) in the row. This is a purely frontend
calculation with no additional API call; the `listExpiringLeases` endpoint (LSE-003) is
consumed by the portfolio dashboard dashlet, not by the lease table row flags.

Open-ended leases (`end_date === null`) never show the expiry flag.

### 5.4 Tenant lease-history panel — ordering and pagination

`listTenantLeases(tenantId)` calls `GET /ui/tenants/{id}/leases`, which is backed by
`list_leases_for_tenant` (LSE-003). The backend applies
`FilterExpression=Attr("tenant_id").eq(tenant_id)` and loops on `LastEvaluatedKey` to
guarantee completeness (CLAUDE.md FilterExpression gotcha; LSE-003 §5). The response is
`LeaseListResponse` with `next_cursor`.

`TenantLeasesPanel` renders all statuses (active, upcoming, ended) newest-first. Status
badges use distinct colors: `active` → green, `upcoming` → blue, `ended` → gray.
The panel is read-only — no edit controls, no create button.

### 5.5 Admin list view

When the authenticated user has `role === "admin"` or `role === "root"` (readable from the
`ui_access_token` cookie JWT, as used in `TicketsPage.tsx:43–44` via
`getRoleFromAccessToken`), `LeasesPage` renders an additional "Admin view" toggle button
in the page header. When toggled on, the query switches from `listLeases` to
`adminListLeases`, which calls `GET /ui/admin/leases` and returns leases across all
owners. The `user_sub` column is shown in admin view to identify the owning landlord.

A USER-role session never sees the toggle. If a USER session somehow calls
`GET /ui/admin/leases` directly (e.g. via devtools), the backend returns 403 and the
frontend shows a toast `"Admin access required"`.

### 5.6 Flag-off graceful degradation

When `LEASES_ENABLED=0` (the default), every backend endpoint returns HTTP 404 with
`detail: "leases not enabled"`. The frontend handles this by:

1. `listLeases` → React Query `isError` with status 404 → `LeasesPage` renders an empty
   placeholder: `"Lease management is not enabled on this instance."` with no table or
   create button.
2. `TenantLeasesPanel` with a 404 error → renders `"Lease history unavailable"` in place
   of the table.

The 404 is not re-thrown as an unhandled error; both components catch it in the `isError`
branch of their `useQuery` result. This follows the pattern used by other flag-gated
pages (e.g. `TicketsPage` which checks the feature availability before rendering the
kanban board).

### 5.7 Currency display

All cent amounts are displayed as `(amount_cents / 100).toLocaleString("en-US", { style: "currency", currency: lease.currency.toUpperCase() })`. The `currency` field on the
lease item is ISO 4217 lowercase (LSE-001 data model); `.toUpperCase()` converts to the
format `Intl.NumberFormat` expects. When `lease.currency` is absent or empty, fall back
to `"USD"`.

Default-OFF negation polarity: absent env var → `"0"` → not in `("0","false","False")` →

feature by default.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no `dev_mode` branch

LSE-004 is a pure frontend ticket; there are no backend service changes in this ticket.
The backend service and router (LSE-001/002/003) already contain no `if S.dev_mode` branch.
The frontend `api` client (`api/client.ts`) sends requests to `/ui/...` regardless of
environment; Vite proxies to `http://localhost:8000` in dev and the prod build hits the
real backend — one code path either way.

`send_alert_email` (the renewal notification, LSE-003's concern) handles dev/prod
divergence internally at `app/services/alerts.py:459`. LSE-004 does not call
`send_alert_email` at all.

### 7.2 Money-safety invariants

LSE-004 **never writes to the `billing` table** and **never calls any billing primitive**.
Specifically:

- `billing_shared.new_ledger_entry` (`app/services/billing_shared.py:224`) is never called
  from any frontend endpoint wrapper or page component.
- `billing_shared.settle_or_reverse_ledger` (`app/services/billing_shared.py:262`) is
  never called; any future void/refund of a rent charge must go through this primitive
  in the RNT cluster, not through a UI direct-write.
- `billing_shared.compute_due` (`app/services/billing_shared.py:158`) is never called;
  outstanding-rent totals for the dashboard are the RNT cluster's responsibility.
- No Stripe, PayPal, or CCBill integration is present. Rent is manually recorded; the
  lease table displays the `monthly_rent_cents` informational field only.
- `monthly_rent_cents` and `security_deposit_cents` are displayed as formatted currency
  amounts but are not used as inputs to any payment flow.

Inline-editing `monthly_rent_cents` via `PATCH /ui/leases/{id}` only updates the
informational field on the lease DynamoDB item in `T.leases`. It does not retroactively
adjust any posted ledger entries, recalculate any balances, or initiate any charge. This
is by design: the economic field on the lease is the "future rate" reference; the RNT
rent-run reads it when it next posts a monthly charge.

### 7.3 Ownership isolation

Every user-scoped endpoint read/write is partitioned under `USER#{user_sub}` in DynamoDB
(LSE-001 key design). A logged-in landlord Alice can never see or modify Bob's leases:
`GET /ui/leases` queries `Key("pk").eq(f"USER#{alice_sub}")`. The frontend contributes to
isolation by never constructing cross-user URL paths; all `listLeases`, `getLease`, and
`updateLease` calls omit the `user_sub` from the URL (it is injected by `require_ui_session`
on the backend from the session cookie).

### 7.4 CSRF

The `api` client in `frontend/src/api/client.ts` reads the `ui_csrf` cookie and attaches
`x-csrf-token: <value>` on every non-GET request. `createLease` (POST),
`updateLease` (PATCH), and `transitionLeaseStatus` (POST) all require this header, which
is enforced by `require_ui_session` on the backend. The E2E tests that exercise these
endpoints must include the CSRF header (see §9.2).

### 7.5 Idempotency

`updateLease` (PATCH) is last-writer-wins in the backend service (LSE-002 §5 — no
optimistic concurrency token for economic-field edits). The frontend does not add client-side
deduplication. `transitionLeaseStatus` uses a backend conditional `update_item` guard;
the 409 `concurrent_update` response is surfaced as a descriptive toast and triggers a
`queryClient.invalidateQueries` to refresh the stale row.

## 8. Backward Compatibility & Migration

### 8.1 Additive-only changes to shared files

Three shared files receive additive changes:

- **`frontend/src/api/types.ts`**: five new interfaces appended. No existing interface
  is modified or removed.
- **`frontend/src/App.tsx`**: one new `lazy` import and one new `<Route>` added. No

  path.
- **`frontend/src/api/endpoints/`**: new file `leases.ts` added. No existing file is
  modified.

### 8.2 Route path safety

`/leases` does not conflict with any existing route in `App.tsx` (confirmed by scanning
`App.tsx:1–567`; no route at that path exists). The Vite dev-server proxy (`vite.config.ts`)
proxies `/api`, `/ui`, `/mock`, `/internal`, `/telemetry` to the backend but not `/leases`
(a plain React Router path), so no proxy conflict arises.

### 8.3 Backend table creation precedes frontend deployment

The `leases` table must exist before the frontend is deployed to any environment where
`LEASES_ENABLED=1`. In dev, `just restart` re-runs `scripts/local-ddb-init.py` which
creates the table from the `TableDef` added in LSE-001. In production:

1. Create the `leases` table with both GSIs via `aws dynamodb create-table` (or Terraform)
   before deploying code.
2. Deploy code with `LEASES_ENABLED=0` (default); confirm no startup errors.
3. Set `LEASES_ENABLED=1` to expose endpoints.

The frontend degrades gracefully (§5.6) even if the table exists but the flag is off —
or if the flag is on but the table is not yet created (backend will error on first DDB
call; all endpoints return 500, which the frontend surfaces as a toast and empty state).

### 8.4 TEN / PROP pickers — graceful absence

The `LeaseCreateDialog` uses plain `<Input>` fields for `tenant_id`, `property_id`, and
`unit_id` when the TEN/PROP picker components are not yet available. When TEN and PROP
frontend tickets land, those inputs are swapped for `<TenantPicker>` and `<UnitPicker>`
components with no other change to the dialog logic. The Zod schema and mutation function
are unchanged.

## 10. Open Questions / Assumptions

1. **TEN / PROP picker availability** — `LeaseCreateDialog` uses plain `<Input>` fields for
   `tenant_id`, `property_id`, and `unit_id` until the TEN/PROP frontend components land.
   Assumption: plain id inputs are acceptable for the initial LSE-004 release; the upgrade
   to proper pickers is a follow-up in the TEN/PROP frontend tickets.

2. **Sidebar navigation link** — This spec assumes `/leases` is reachable only via direct
   URL or from the Dashboard KPI dashlet (portfolio dashboard, RPT-006/007). A sidebar
   navigation entry for "Leases" is a UX decision for the property-management vertical
   rollout; it can be added to `AppShell` without any change to this spec.

3. **`currency` display for non-USD leases** — `toLocaleString` with `currency: lease.currency.toUpperCase()` works correctly for all valid ISO 4217 codes. If the backend
   stores an invalid/empty string, `Intl.NumberFormat` throws; the fallback to `"USD"`
   (§5.7) prevents an uncaught render error.

4. **Load-more vs. `useInfiniteQuery`** — The spec uses the manual cursor + load-more
   pattern matching `TicketsPage.tsx:49,317–318` rather than `useInfiniteQuery`. If the
   number of leases per landlord grows large (hundreds), switching to `useInfiniteQuery`
   with virtual scrolling is a performance follow-up. At P2 priority and expected
   per-landlord scale (tens of leases), load-more is sufficient.

5. **Expiry threshold hardcoded to 60 days** — The `listExpiringLeases` endpoint accepts a
   `within_days` parameter; the lease table row flag uses a hardcoded 60-day frontend
   calculation. If a per-user configurable threshold is needed, it should come from a
   lease settings endpoint (future ticket); for now 60 days matches the LSE-003
   `list_upcoming_expirations` default.

6. **`admin_list_leases` user_sub display** — The admin view shows `user_sub` as a raw
   string. A future enhancement resolves it to a display name via `GET /ui/profile/{sub}`.
   Deferred to keep LSE-004 self-contained.

7. **Keyboard navigation in editable cells** — Tab-to-next-cell navigation is not specified.
   The implementation may use click-to-edit only. Tab navigation across cells is a UX
   follow-up.
