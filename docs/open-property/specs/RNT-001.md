# RNT-001 — Rent-run background timer — monthly `rent_charge` per active lease (idempotent per lease+period)

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 3 d
**Flag:** `RENT_LEDGER_ENABLED` + `RENT_RUN_ENABLED` (both default OFF)
**Depends on:** LSE-001 / LSE-002 (active-lease entity and query surface)

---

## 1. Summary & Goal

RNT-001 delivers the automated monthly rent-recognition engine for the open-property
vertical. Once per calendar month a background timer iterates **every active lease
system-wide** and posts exactly one `rent_charge` ledger entry per `(lease_id, period)`
pair. The `period` is a `"YYYY-MM"` string. The entry is written through the existing
`new_ledger_entry` primitive (`app/services/billing_shared.py:224`) into the existing
`T.billing` DynamoDB table — no new table, no new money math, no online payment provider.

This is the rent-domain analogue of `_tick_all_running_resources`
(`app/services/compute_billing.py:616`), but monthly instead of per-minute and
recognizing a rent obligation rather than deducting from a compute wallet.
The gap analysis (`docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §B row 57) names
it explicitly: *"clone `compute_billing.py` rent-run → `new_ledger_entry`"*.

The design is fully additive. With both feature flags off (the default), no existing
surface changes by a single byte: `T.billing` is untouched, no background loop starts,
every new service function short-circuits to `None`, and every new endpoint returns 404.

## 2. Context & Current State

### 2.1 Billing ledger primitives (all reused verbatim, never forked)

The financial core of the entire platform lives in `app/services/billing_shared.py`.
Every function here is already exercised by Stripe, PayPal, and CCBill billing paths.
RNT-001 reuses them unchanged:

- **`new_ledger_entry(...)`** (`billing_shared.py:224–259`) — accepts `key_name`,
  `key_value`, `entry_type`, `amount_cents`, `state`, `reason`, optional `extra`/`meta`
  dicts, and returns `(sk, item)`. The `sk` is `LEDGER#{ts}#{entry_id}` (`:220–221`).
  The item carries a denormalized `ledger_date` (`:253`) for the `GSI_LEDGER_DATE` index.
  `extra` fields are written directly onto the persisted item (`:255–256`).

- **`apply_balance_delta(table, pk, delta, *, currency)`** (`billing_shared.py:83–105`) —
  atomic `ADD` on `BALANCE` row using `if_not_exists` guards. Ensures the
  `owed_settled_cents` / `payments_settled_cents` running counters stay correct so
  `compute_due` can net rent owed against rent collected.

- **`compute_due(balance_item)`** (`billing_shared.py:158–170`) — reads the four counter
  fields (`owed_settled_cents`, `owed_pending_cents`, `payments_settled_cents`,
  `payments_pending_cents`) and returns `due_settled_cents` and
  `due_if_all_settles_cents`. RNT-001 bumps `owed_settled_cents` per charge;
  `compute_due` is read unmodified, serving the period-summary endpoint (RNT-004).

- **`settle_or_reverse_ledger(table, key_name, key_value, ledger_sk_value, new_state)`**
  (`billing_shared.py:262–274`) — a single `update_item` that flips the `state` field.
  RNT-001 does not call this directly; it is the only permitted void path for later
  tickets (RNT-003). The billing refund path at `app/routers/billing.py:1323–1324`
  shows this exact usage pattern.

- **`user_pk(user_id)`** (`billing_shared.py:23`) — returns `USER#{user_id}`.
  **`ledger_sk(ts, entry_id)`** (`billing_shared.py:220`) — returns `LEDGER#{ts}#{entry_id}`.
  **`ddb_put(table, item)`** (`billing_shared.py:32–36`) — `table.put_item(Item=item)`.
  **`ddb_query_pk(table, pk)`** (`billing_shared.py:43–48`) — full-partition query.

### 2.3 Lease entity (the iteration source)

The `leases` table is introduced by LSE-001 (`docs/open-property/specs/LSE-001.md`).
Its key shape:

```
PK  = USER#{user_sub}       (landlord)
SK  = LEASE#{lease_id}
GSI1: GSI1PK="LEASES#ALL"  / GSI1SK=created_at (N)   index: leases-all-index
GSI2: GSI2PK=USER#{user_sub}#STATUS#{status} / GSI2SK=end_date (N, sparse)
```

RNT-001's system-wide sweep queries **GSI1** filtering `status=active`. The
`monthly_rent_cents`, `rent_due_day`, `currency`, `lease_id`, `property_id`,
`unit_id`, `tenant_id`, and `lease_number` attributes are all set by LSE-001 and
carried on each lease item.

`app/core/settings.py:821` carries a representative use of the negation-polarity
form `os.environ.get("CART_REMINDERS_ENABLED", "1") not in ("0", "false", "False")`.
The canonical **default-OFF** variant (`"0"` as the env-var fallback) can be seen at
line 17: `s3_use_path_style: bool = os.environ.get("S3_USE_PATH_STYLE", "0") not in ("0", "false", "False")`.
The rent flags follow this default-OFF form exclusively.

`app/core/settings.py:2385` shows `compute_billing_enabled` (default `"1"` → ON) and
`:2386` `compute_billing_poll_interval` (default `"300"` s) as the structural model for
the two new settings. Note: `compute_billing_enabled` defaults to **ON** because compute
billing is a core platform feature; the rent flags deliberately default to **OFF**
(`"0"`) because the property-management vertical is fully additive.

### 2.4 Idempotency pattern precedents

The CLAUDE.md "Common gotchas" documents two canonical conditional-put idempotency
patterns in this codebase:
1. **Cart-recovery consume row** — `ConditionExpression="attribute_not_exists(pk)"`
   with a dedicated marker item; on `ConditionalCheckFailedException` treat as already-done.
2. **Audit-export claim CAS** — compare-and-swap on `status==pending` before processing.

RNT-001 uses pattern (1): a marker row written under `pk=RENT_PERIOD#{user_sub}`,
`sk=LEASE#{lease_id}#PERIOD#{period}` with `attribute_not_exists(pk)`. A
`ConditionalCheckFailedException` means this lease was already charged for this period;
skip silently with no second `new_ledger_entry` call.

no `rent_period_markers` table or table handle, and no `RentChargeOut` Pydantic model.
This ticket introduces all of them at the service layer; the router surface for manual

## 3. Data Model

### 3.1 Reused table: `T.billing`

Rent rows live in the existing `billing` table
(`S.billing_table_name`, default `"billing"`, `app/core/settings.py:348`).
Schema for existing rows: `pk="USER#{user_sub}"`, `sk` varies by row kind
(`LEDGER#...`, `BALANCE`, `PM#...`). RNT-001 adds two new `sk` prefixes to the same
table — no schema migration:

**Rent ledger row** (written by `new_ledger_entry`):
```
pk           = USER#{user_sub}
sk           = LEDGER#{ts}#{entry_id}
entry_id     = ulidish() value
ts           = now_ts()
type         = "rent_charge"
state        = "settled"
amount_cents = int(lease["monthly_rent_cents"])
reason       = "Rent {period} — {lease_number}"
ledger_date  = "YYYY-MM-DD"   (from ledger_date_for_ts, for GSI_LEDGER_DATE)
--- extra fields (denormalized) ---
lease_id     = str
property_id  = str
unit_id      = str
tenant_id    = str
period       = "YYYY-MM"
rent_kind    = "charge"
currency     = str  (e.g. "usd")
```

The `extra` dict is passed directly to `new_ledger_entry` and written onto the item
via the `item.update(extra)` call at `billing_shared.py:255–256`. Denormalizing these
FKs means per-lease and per-period queries never need a join.

**Balance row** (managed by `apply_balance_delta`, existing `BALANCE` sk):
```
pk                     = USER#{user_sub}
sk                     = "BALANCE"
owed_settled_cents     = N  (incremented by monthly_rent_cents on each charge)
owed_pending_cents     = N
payments_settled_cents = N
payments_pending_cents = N
currency               = str
updated_at             = N
```

### 3.2 New table: `rent_period_markers`

The idempotency markers require a dedicated table so that:
- The conditional `put_item` can use `attribute_not_exists(pk)` cleanly without
  colliding with the billing table's existing `BALANCE` row or `LEDGER#` rows.
- The marker can be deleted on void (RNT-003) without touching any ledger row.

```
PK  = RENT_PERIOD#{user_sub}        string
SK  = LEASE#{lease_id}#PERIOD#{period}   string
```

Item attributes:
```
pk          = RENT_PERIOD#{user_sub}
sk          = LEASE#{lease_id}#PERIOD#{period}
ledger_sk   = the LEDGER#... sk of the charge row (for traceability)
charged_at  = now_ts() (N)
amount_cents = N
```

No GSIs required for RNT-001; the primary key uniquely identifies a
`(landlord, lease, period)` charge attempt. The marker is the only artifact that
is ever deleted (via `ddb_del` on charge-void in RNT-003); the ledger row itself
is never deleted.

**`scripts/local-ddb-init.py` entry:**

```python
TableDef(
    _resolve_table_name(S.rent_period_markers_table_name, "rent_period_markers"),
    "pk",
    "sk",
),
```

No numeric GSI sort keys → no `attr_types` override needed (the existing CLAUDE.md
gotcha only applies to numeric GSI sort keys; this table's sort key is a string).

**`post_rent_charge(user_sub: str, lease: dict, *, period: str | None = None) -> dict | None`**

The single-lease charge primitive. Called by the background timer and by the
manual-trigger endpoint in RNT-005.

```python
def post_rent_charge(
    user_sub: str,
    lease: dict,
    *,
    period: str | None = None,
) -> dict | None:
```

Steps:
1. Flag guard: `if not S.rent_ledger_enabled: return None`.
2. `period = period or _current_period()`.
3. Build marker keys: `mpk = _marker_pk(user_sub)`,
   `msk = _marker_sk(lease["lease_id"], period)`.
4. Attempt to claim the idempotency marker:
   ```python
   from botocore.exceptions import ClientError
   try:
       T.rent_period_markers.put_item(
           Item={
               "pk": mpk, "sk": msk,
               "ledger_sk": "",          # placeholder; back-filled after step 6
               "charged_at": now_ts(),
               "amount_cents": int(lease["monthly_rent_cents"]),
           },
           ConditionExpression="attribute_not_exists(pk)",
       )
   except ClientError as exc:
       if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
           return {"skipped": True, "reason": "already_charged", "period": period}
       raise
   ```
5. Build the ledger `reason` string:
   `reason = f"Rent {period} — {lease.get('lease_number', lease['lease_id'])}"`.
6. Write the charge row via `new_ledger_entry`:
   ```python
   from app.services.billing_shared import (
       new_ledger_entry, apply_balance_delta, user_pk, ddb_put,
   )
   sk, item = new_ledger_entry(
       key_name="pk",
       key_value=user_pk(user_sub),
       entry_type="rent_charge",
       amount_cents=int(lease["monthly_rent_cents"]),
       state="settled",
       reason=reason,
       extra={
           "lease_id": lease["lease_id"],
           "property_id": lease.get("property_id", ""),
           "unit_id": lease.get("unit_id", ""),
           "tenant_id": lease.get("tenant_id", ""),
           "period": period,
           "rent_kind": "charge",
           "currency": lease.get("currency", "usd"),
       },
   )
   ddb_put(T.billing, item)
   ```
7. Back-fill the `ledger_sk` onto the marker:
   ```python
   T.rent_period_markers.update_item(
       Key={"pk": mpk, "sk": msk},
       UpdateExpression="SET ledger_sk = :s",
       ExpressionAttributeValues={":s": sk},
   )
   ```
8. Bump the `owed_settled_cents` balance counter:
   ```python
   apply_balance_delta(
       T.billing,
       user_pk(user_sub),
       {"owed_settled_cents": int(lease["monthly_rent_cents"])},
       currency=lease.get("currency", "usd"),
   )
   ```
9. Emit audit event:
   ```python
   from app.services.alerts import audit_event
   audit_event(
       "rent.charge_posted",
       user_sub,
       lease_id=lease["lease_id"],
       period=period,
       amount_cents=int(lease["monthly_rent_cents"]),
       ledger_sk=sk,
   )
   ```
10. Return `item` (the created ledger entry dict including all `extra` fields).

**Error contract:** if the `ddb_put(T.billing, item)` call fails after the marker was
already written, the marker is orphaned (it prevents a duplicate charge) and the failure
propagates. The orphaned marker is not a double-charge; it is a missed charge. The
operator can void the marker manually (using the same `ddb_del` used by RNT-003) and
re-run. This is the same CAS-before-write pattern used by the audit-export worker.

**`_scan_active_leases() -> list[dict]`**

Iterates active leases system-wide using GSI1 (`leases-all-index`). Clones the
`_scan_all_running_instances` `LastEvaluatedKey` loop (`compute_billing.py:507–522`).

```python
from boto3.dynamodb.conditions import Key, Attr

def _scan_active_leases() -> list[dict]:
    items: list[dict] = []
    kwargs: dict = {
        "IndexName": "leases-all-index",
        "KeyConditionExpression": Key("GSI1PK").eq("LEASES#ALL"),
        "FilterExpression": Attr("status").eq("active"),
    }
    while True:
        resp = T.leases.query(**kwargs)
        items.extend(resp.get("Items", []))
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return items
```

The `FilterExpression` does not reduce page size — pages are up to 1 MB of raw items
before filter application. The loop must run until `LastEvaluatedKey` is absent or
active leases beyond the first page would be silently skipped (CLAUDE.md gotcha;
`compute_billing.py:507–522` is the canonical reference).

---

**`run_rent_charges(*, period: str | None = None) -> int`**

The system-wide charge sweep. Clones `_tick_all_running_resources`
(`compute_billing.py:616–650`).

```python
def run_rent_charges(*, period: str | None = None) -> int:
    if not S.rent_ledger_enabled:
        return 0
    period = period or _current_period()
    leases = _scan_active_leases()
    charged = 0
    skipped = 0
    for lease in leases:
        user_sub = lease.get("user_sub", "")
        if not user_sub:
            continue
        try:
            result = post_rent_charge(user_sub, lease, period=period)
            if result and not result.get("skipped"):
                charged += 1
            else:
                skipped += 1
        except Exception:
            logger.exception(
                "rent_run_charge_failed user_sub=%s lease_id=%s period=%s",
                user_sub, lease.get("lease_id"), period,
            )
    logger.info(
        "rent_run period=%s charged=%d skipped=%d",
        period, charged, skipped,
    )
    return charged
```

Per-lease exceptions are caught and logged but do not abort the batch — the same pattern
as `_tick_resource` / `_auto_terminate_resource` in `compute_billing.py:595–613`.

```python
async def run_rent_run_loop(*, poll_interval: int | None = None) -> None:
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotency guarantee

The conditional `put_item` with `attribute_not_exists(pk)` on `T.rent_period_markers`
is the hard gate. The sequence is:

1. Write marker (CAS).
2. On `ConditionalCheckFailedException` → return skip sentinel, no further DDB writes.
3. On success → write ledger row → back-fill marker with `ledger_sk` → bump balance.

If the process crashes between step 1 and step 3, the marker exists but the ledger row
is absent. The marker prevents re-entry (the charge is considered "in-flight"). An
operator can recover by deleting the marker row from `T.rent_period_markers` and
re-running. This is the same trade-off accepted by the audit-export claim CAS
(CLAUDE.md).

A re-run of the full `run_rent_charges` sweep within the same calendar month produces
zero new rows — every active lease already has a marker for the current period. The
`charged=0 skipped=N` log line is the expected outcome after the first successful run.

### 5.2 `FilterExpression` does not reduce page size

`_scan_active_leases` uses a GSI query with `FilterExpression=Attr("status").eq("active")`.
DynamoDB fetches up to 1 MB of items from GSI1 before applying the filter; items past the
first 1 MB page are only reached by following `LastEvaluatedKey`. An installation with
hundreds of leases across multiple landlords must loop. The implementation loops
unconditionally until `LastEvaluatedKey` is absent. This is the same pattern as
`_scan_all_running_instances` (`compute_billing.py:507–522`) and is required per the
CLAUDE.md gotcha.

### 5.3 `monthly_rent_cents = 0` leases

If a lease carries `monthly_rent_cents = 0` (e.g., a rent-free arrangement), `post_rent_charge`
will write a zero-amount `rent_charge` row with `state="settled"`. This is intentional:
the ledger records the contractual amount (zero). When `apply_balance_delta` is called with
`{"owed_settled_cents": 0}`, line 92 (`if value == 0: continue`) skips the ADD expression
for that counter, so the `owed_settled_cents` balance is unchanged — the monetary outcome is
a no-op. The `BALANCE` row's `updated_at` timestamp is still refreshed (the UPDATE
is still issued), which is harmless. The idempotency marker still fires so the lease is
not re-processed. The operator can filter zero-amount rows in the UI (RNT-006).

### 5.4 Multi-landlord isolation

Every rent ledger row is keyed under `USER#{user_sub}` (the landlord). The
`_scan_active_leases` function reads `user_sub` from each lease item (LSE-001 denormalizes
it onto every item as `GSI1PK = "LEASES#ALL"` + `user_sub` attribute). Each
`post_rent_charge` call uses the lease's own `user_sub`, so the resulting `BALANCE` row
and `LEDGER#...` rows land in the correct landlord's partition. A lease item with a
missing or empty `user_sub` is skipped with a warning log rather than writing into
`USER#` (which would be a data corruption).

### 5.5 Mid-month deploys and period semantics

The period is derived from `_current_period()` (UTC wall clock at run time). A deploy
that happens on the 15th of a month and triggers the timer will compute
`period = "YYYY-MM"` for that month. The idempotency marker ensures that if the timer
subsequently wakes again before month-end, the lease is not double-charged. The charge
is recognized at the start of the month in which it is first posted — consistent with
most commercial accounting practices and matching the gap analysis note: *"charge once
at the start of the period … a mid-month deploy still bills the month exactly once
thanks to the idempotency marker"* (RENT_LEDGER_TICKETS.md constraint 7).

### 5.6 Clock drift / timezone

`_current_period()` always uses `datetime.now(timezone.utc)`. The `now_ts()` used by
`new_ledger_entry` (`billing_shared.py:239`) is also UTC Unix time. There is no
local-time dependency.

### 5.7 `rent_due_day` is informational only in RNT-001

The `rent_due_day` field on the lease is used by `derive_charge_status` (RNT-002) to
compute whether a charge is `open` vs `overdue`. RNT-001 does not consult `rent_due_day`
when deciding whether to post. The default policy is: post the charge on the first timer
run of the calendar month. This simplifies the timer and keeps idempotency straightforward.
An operator who wants day-of-month semantics can adjust the timer start time or use the
manual `charge_lease_now` endpoint (RNT-005).

### 5.8 Exception isolation

A failure in `post_rent_charge` for one lease does not abort the sweep. Each lease is
wrapped in `try/except Exception` in `run_rent_charges`. The exception is logged at
`ERROR` level with `lease_id` and `user_sub` for operator visibility. This mirrors the
`_tick_resource` / `_auto_terminate_resource` exception isolation in
`compute_billing.py:607–613`.

### 5.9 Audit trail

`audit_event("rent.charge_posted", ...)` writes a structured record to `T.alerts`
carrying `lease_id`, `period`, `amount_cents`, and `ledger_sk`. This satisfies the
audit requirement without duplicating ledger data. The `audit_event` function
(`app/services/alerts.py:644`) is already used by all state-changing service functions
across the platform.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 — No `dev_mode` branch

`app/services/rent_ledger.py` contains zero `if S.dev_mode:` branches. All DDB
operations target `T.billing` and `T.rent_period_markers`, which resolve to:
- **Dev:** DynamoDB Local at `localhost:8001` (via `DDB_ENDPOINT_URL` in `.env.local`)
  with moto-intercepted boto3 client (same as every other service in the platform).
- **Prod:** Real AWS DynamoDB (same boto3 client, different endpoint).

There is no online payment provider call to mock — rent charges are pure ledger
entries. This is the cleanest possible SECOPS-007 outcome: no payment divergence at
all because rent is recorded, not processed.

### Money-safety: `new_ledger_entry` is the only write path

No bespoke `amount_cents` arithmetic exists in `rent_ledger.py`. Every monetary row
goes through `new_ledger_entry` (`billing_shared.py:224`). The balance counters are
updated only through `apply_balance_delta` (`billing_shared.py:83`). The
`_deduct_from_wallet` path in `compute_billing.py:141` is deliberately **not** reused —
that path touches the compute wallet; rent charges recognize an obligation in the
landlord's ledger, which is a different semantic.

### Money-safety: void = reversal, never delete

RNT-001 itself never voids a charge (that is RNT-003). The design however establishes
the constraint: `settle_or_reverse_ledger` (`billing_shared.py:262`) is the only
permitted mutation on a `LEDGER#` row's state. No `delete_item` is ever called on any
`LEDGER#` row, consistent with `app/routers/billing.py:1323–1324`.

### Idempotency contract

The `attribute_not_exists(pk)` conditional on `T.rent_period_markers` is the
single source of truth for "has this lease been charged for this period?" The
`run_rent_charges` sweep can be called any number of times within a calendar month
and will post **exactly one** `type="rent_charge"` row per `(user_sub, lease_id, period)`
triple. This guarantee holds whether the run is triggered by the background timer,
a manual `POST /ui/rent/run` (RNT-005), or a direct service-layer call in tests.

### Ownership isolation

`post_rent_charge` always uses the `user_sub` sourced from the lease item itself (not
from a caller-supplied parameter in the background path). The resulting billing row is
keyed under that landlord's `USER#{user_sub}` partition. A `lease_id` in another
landlord's partition cannot be reached by this sweep because `_scan_active_leases`
reads `user_sub` from the lease item's own attribute.

## 8. Backward Compatibility & Migration

### No schema changes to existing tables

`T.billing` already has `pk="USER#{user_sub}"`, `sk="LEDGER#{ts}#{entry_id}"` rows.
The two new `type` values (`rent_charge`, `rent_payment`) are additions to the
`type` enum in the application layer only — DynamoDB is schema-less. No `UpdateTable`
or backfill is required.

The existing `GSI_LEDGER_DATE` on `T.billing` (defined in `scripts/local-ddb-init.py:67–77`)
covers new rent rows automatically: every `new_ledger_entry` call writes `ledger_date`
(`billing_shared.py:253`), so rent charges appear in the platform financial dashboard's
day-bucket queries without any change to that GSI or its query code.

### New table: `rent_period_markers`

This table does not exist yet. It must be created before the feature is enabled:
- **Dev:** `just restart` re-runs `scripts/local-ddb-init.py`, which picks up the new
  `TableDef`. No manual intervention needed.
- **Prod:** The `TableDef` entry triggers `CreateTable` in the init script during the
  next deployment. The timer must be started (flags set to `1`) only after the table
  exists.

### Settings additions are backward-compatible

New `Settings` fields carry defaults (`"0"` → `False`). An existing deployment with no
new env vars set behaves identically to before: both flags evaluate to `False`, the
timer never starts, and `T.rent_period_markers` is never opened.

### Existing `T.billing` consumers are unaffected

The `GET /billing/ledger` endpoint (`app/routers/billing.py:2448–2454`) filters on
`sk.startswith("LEDGER#")` and returns all matching rows to the landlord. Rent charge
rows appear in the ledger list when present — additive, not breaking. If the flag is
off, no rows exist, so the output is unchanged.

## 10. Open Questions / Assumptions

1. **Charge-on-due-day policy (deferred).** The default policy is "charge once per
   calendar month on the first timer run." An alternative is "charge only after
   `rent_due_day` has passed in the current period." This is deferred to a follow-on
   ticket; the idempotency marker scheme accommodates either policy because it is
   keyed on `period`, not on the specific day.

2. **Timezone for `rent_due_day`.** The spec assumes UTC throughout. If landlords are
   in a non-UTC timezone, the calendar month boundary (and therefore the period string)
   could differ by up to 24 hours from the landlord's local expectation. For the MVP
   this is acceptable; a future setting `landlord_timezone` could adjust
   `_current_period()`.

3. **`monthly_rent_cents` currency assumption.** The `currency` field is read from the
   lease item (LSE-001 carries ISO 4217 lowercase, default `"usd"`). The billing ledger
   supports any currency string. No currency conversion is performed.

4. **Concurrent timer wakes.** The hourly timer wakes once per `poll_interval`. If a
   deployment restart causes two instances to briefly run simultaneously (e.g. rolling
   deploy), both can call `run_rent_charges` concurrently. The `attribute_not_exists(pk)`
   conditional ensures exactly one of them wins the marker write; the other gets the
   skip path. No duplicate charges result.

5. **`T.leases` availability.** RNT-001 has a hard dependency on LSE-001 and LSE-002
   having been deployed (the `leases` table and `T.leases` handle must exist). The
   `start_rent_run_task` function is registered unconditionally in `main.py`; if the
   flag is on but the `leases` table is absent, `_scan_active_leases` will raise a
   `ResourceNotFoundException`. Guard: both `LEASES_ENABLED` and `RENT_RUN_ENABLED`
   must be `1` simultaneously for the timer to be useful.

6. **Platform financial dashboard.** Rent charge rows carry `ledger_date` and are
   written to `T.billing`, so they already appear in `GSI_LEDGER_DATE` queries. The
   `type="rent_charge"` value will appear in any platform GMV rollup that does not
   filter by type. It is assumed that the platform financial dashboard
   (`app/services/platform_financial_dashboard.py`) will add a `type` filter when
   presenting only payment-processing revenue. This is a dashboard concern, not a
   ledger concern.
