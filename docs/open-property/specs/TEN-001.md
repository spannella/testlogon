# TEN-001 — Tenant entity, table, flag & directory CRUD service

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Source:** `docs/open-property/TENANTS_TICKETS.md` §TEN-001 + `docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §B

---

## 1. Summary & Goal

TEN-001 is the foundational ticket for the open-property Tenant cluster. It delivers exactly three things:

1. **Feature flag** — `S.property_tenants_enabled` (`PROPERTY_TENANTS_ENABLED`, default `False`) and `S.property_tenants_table_name` (`DDB_PROPERTY_TENANTS_TABLE`, default `"property_tenants"`), added to `app/core/settings.py` following the boolean-env pattern at `:839` (`inventory_reservations_enabled`).

2. **DynamoDB table** — `property_tenants` with a `TENANT#{tenant_id}/META` key pattern, a `GSI_OWNER` newest-first index per landlord, and a `GSI_PARTY` reverse-lookup index from PTY `party_id`. Both GSIs declared in `scripts/local-ddb-init.py` with the mandatory `attr_types={"created_at": "N"}` annotation.

3. **CRUD service** — `app/services/property_tenant.py` exposing `create_tenant`, `get_tenant`, `list_tenants`, and `update_tenant`, working exclusively with plain `dict` objects (no `app/models.py` dependency at the service layer), with idempotent write, PTY PERSON party creation, cursor-paginated listing, and audit events on every mutation.

With `PROPERTY_TENANTS_ENABLED=false` (the default) no new HTTP surface is exposed, no table is read or written, and no existing behavior is altered. TEN-002, TEN-003, and TEN-004 all depend on this ticket and cannot proceed without it.

### 2.3 Audit event primitive


All mutations in `property_tenant.py` call this function. ### 2.4 PTY PERSON party spine

`docs/ofbiz/specs/PTY-004.md` §4.1 establishes `create_party("PERSON", user_sub=…, correlation_id=…) -> dict` as the factory for a PTY PERSON party row on the `T.party` table (PK `PARTY#{party_id}`, SK `META`). Per `docs/open-property/TENANTS_TICKETS.md:35-45`, a Tenant is a **property-domain projection over a PTY PERSON party**: TEN-001 stores the returned `party_id` on the tenant META row and back-populates it in `GSI_PARTY`, so future code can resolve a tenant from a PTY party in O(1). Neither PTY-004's service module nor its table are modified by this ticket.

When `party_id` is provided by the caller (linking to a pre-existing PERSON), `create_party` is skipped. When it is `None`, `create_party` is called with `user_sub=owner_id` and a derived `correlation_id = f"tenant:{tenant_id}"`.

### 2.5 Deterministic-ID idempotency pattern

`app/services/commerce_order_service.py:66-67` derives IDs deterministically:

```python
corr = str(correlation_id or ...)
order_id = hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]
```

TEN-001 derives `tenant_id = hashlib.sha256(correlation_id.encode()).hexdigest()[:32]` when a `correlation_id` is supplied, and `uuid4().hex` otherwise (PTY-004 §2.3 precedent). The subsequent `put_item` uses `ConditionExpression="attribute_not_exists(PK)"`, catching `ConditionalCheckFailedException` to return the existing item (idempotent replay emits no second audit event).

### 2.6 Cursor pagination

`app/core/cursor.py:94` (`encode_cursor`) and `:103` (`decode_cursor`) wrap DynamoDB `LastEvaluatedKey` in a signed HMAC v2 token. The `_json_default` coercion at `cursor.py:12-18` handles `Decimal`-typed numeric GSI key values in the `LastEvaluatedKey`, making it safe for the `created_at` (N) sort key without extra conversion. `app/services/license_agreements.py:268,298` uses this pattern; `list_tenants` follows it exactly.

### 2.7 Contact listing posture

`app/routers/contacts.py:52-57` sorts contacts favorites-first then alphabetically via `_sort_contacts`. `list_tenants` uses a different posture — newest-first from the `GSI_OWNER` sort key — which is native to DynamoDB (`ScanIndexForward=False`) rather than in-memory. The optional `status` filter and case-insensitive `q` substring match are applied in-memory to each DynamoDB page. Note: `list_contacts` itself (`:63-81`) does NOT do in-memory filtering — it fetches all items and sorts them. The in-memory filtering posture for `list_tenants` is a new addition to this service, not directly borrowed from contacts.

### 2.8 Profile identity seeding

`app/services/profile.py:305` defines `get_profile_identity(user_sub) -> dict` returning `display_name`, `email`, `phone`, `profile_photo_url`. When a tenant maps to a platform user (i.e., the tenant's email matches an existing user sub), `create_tenant` calls this function to pre-populate `display_name` — same pattern as `app/routers/contacts.py:93-98`. This is best-effort; failure is silently swallowed.

## 3. Data Model

### 3.1 Table: `property_tenants`

Single DynamoDB table. All TEN sub-tickets (TEN-002 profile, TEN-003 lease history, TEN-004 frontend) reuse this same table by adding new SK prefixes to existing `TENANT#{tenant_id}` partitions. The tenant-meta row is the only row introduced by this ticket.

**Primary key**

| Attribute | DDB Type | Value |
|---|---|---|
| `PK` | S (hash) | `TENANT#{tenant_id}` |
| `SK` | S (range) | `META` |

**Tenant-meta row attributes**

| Attribute | DDB Type | Nullable | Notes |
|---|---|---|---|
| `PK` | S | No | `TENANT#{tenant_id}` |
| `SK` | S | No | Always `"META"` |
| `tenant_id` | S | No | `uuid4().hex` or `sha256(correlation_id)[:32]` |
| `owner_id` | S | No | The landlord/PM `user_sub`; `GSI_OWNER` partition key |
| `party_id` | S | No | PTY `PERSON` party id; `GSI_PARTY` partition key |
| `display_name` | S | No | Human-readable name; non-empty string |
| `email` | S | Yes | Normalized via `app/core/normalize.normalize_email` (`normalize.py:60`); stored lowercased |
| `phone` | S | Yes | Normalized via `app/core/normalize.normalize_phone` (`normalize.py:66`) |
| `status` | S | No | `prospect` \| `active` \| `past`; default `"prospect"` |
| `active_unit_id` | S | Yes | Wired by TEN-002 `set_active_unit`; `None`/absent at TEN-001 creation |
| `created_at` | N | No | `now_ts()` integer Unix seconds (`app/core/time.py:2`) |
| `updated_at` | N | No | `now_ts()` at create; bumped by every `update_tenant` call |
| `correlation_id` | S | Yes | Stored for audit; not queried |

**GSIs**

| Index name | Partition key | Sort key | Purpose |
|---|---|---|---|
| `GSI_OWNER` | `owner_id` (S) | `created_at` (N) | Newest-first directory listing per landlord (`list_tenants`) |
| `GSI_PARTY` | `party_id` (S) | `SK` (S) | O(1) reverse lookup: from a PTY `party_id` to the tenant META row |

Both GSIs project all attributes (`ALL`).

**`attr_types`**: `{"created_at": "N"}` — mandatory per the CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha. Without this declaration, DynamoDB stores `created_at` as String, causing `ValidationException` when `GSI_OWNER` is queried with an integer `ExclusiveStartKey`. This is the identical requirement documented for the `party` table in `docs/ofbiz/specs/PTY-004.md` §2.2. Note: PTY-002/PTY-004 are spec-only and not yet in the live `scripts/local-ddb-init.py`; the pattern is exemplified in that file at entries using `attr_types={"created_at": "N"}` (e.g., the instance-monitoring and compute tables at lines ~84–94).

**TableDef** (append inside `_table_defs()` in `scripts/local-ddb-init.py`, after the last existing entry):

```python
TableDef(
    _resolve_table_name(S.property_tenants_table_name, "property_tenants"),
    "PK",
    "SK",
    gsi=[
        {"index_name": "GSI_OWNER", "partition_key": "owner_id", "sort_key": "created_at"},
        {"index_name": "GSI_PARTY", "partition_key": "party_id", "sort_key": "SK"},
    ],
    attr_types={"created_at": "N"},
),
```

## 4. API / Service Design

### 4.1 Service module: `app/services/property_tenant.py`

The service works exclusively with plain `dict` objects to avoid circular imports between `app/services/property_tenant.py` and `app/models.py` (PTY-004 §2.7 pattern). Pydantic conversions happen at the router layer (TEN-003 deliverable).

**Module-level helpers**

```python
# Flag helpers — mirror app/services/inventory.py:50-57 (404 gate, matching PROP-001)
def _flag_on() -> bool:
    return bool(getattr(S, "property_tenants_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Property tenants are not enabled")

# Audit wrapper — mirror app/services/inventory.py:92-98
def _audit(event: str, user_sub: str, **fields: Any) -> None:
    try:
        from app.services.alerts import audit_event
        audit_event(event, user_sub or "system", None, **fields)
    except Exception:
        pass
```

**Public function signatures**

```python
def create_tenant(
    owner_id: str,
    *,
    display_name: str,
    email: Optional[str] = None,
    phone: Optional[str] = None,
    party_id: Optional[str] = None,
    correlation_id: Optional[str] = None,
) -> dict:
    ...

def get_tenant(tenant_id: str) -> Optional[dict]:
    ...

def list_tenants(
    owner_id: str,
    *,
    status: Optional[str] = None,
    q: Optional[str] = None,
    cursor: Optional[str] = None,
    limit: int = 50,
) -> dict:
    ...

def update_tenant(tenant_id: str, **patch) -> dict:
    ...
```

#### `create_tenant` — detailed contract

1. `_require_enabled()` — raises 404 if flag is off.
2. Derive `tenant_id`:
   - If `correlation_id` is supplied: `tenant_id = hashlib.sha256(correlation_id.encode("utf-8")).hexdigest()[:32]` (deterministic; same as `app/services/commerce_order_service.py:67`).
   - Else: `tenant_id = uuid4().hex`.
3. Normalize `email` via `normalize_email(email)` if provided (`app/core/normalize.py:60`); normalize `phone` via `normalize_phone(phone)` if provided (`:66`). Both functions raise `HTTPException(400, …)` on invalid input — let it propagate.
4. If `party_id` is `None`: call `party.create_party("PERSON", user_sub=owner_id, correlation_id=f"tenant:{tenant_id}")` (PTY-004 §4.1) and use the returned `party["party_id"]`. If `party_id` is supplied, use it as-is (caller's responsibility to validate ownership).
5. Attempt to seed `display_name` from profile if the caller passes `None` and `email` matches a known user — best-effort `get_profile_identity` call, silently swallowed on any exception (`app/routers/contacts.py:93-98` pattern).
6. Build `item` dict with all META fields; set `created_at = updated_at = now_ts()`, `status = "prospect"`, `active_unit_id = None`.
7. `T.property_tenants.put_item(Item=item, ConditionExpression="attribute_not_exists(PK)")` — idempotent first-write guarantee (PTY-004 §2.3 / `app/services/cart_reminders.py:207`).
8. On `ConditionalCheckFailedException`: fetch the existing item and return it **without** emitting an audit event (replay semantics — one META row, one audit event, ever).
9. On success: `_audit("tenant_created", owner_id, tenant_id=tenant_id, party_id=party_id)`.
10. Return the `item` dict.

#### `get_tenant` — detailed contract

`T.property_tenants.get_item(Key={"PK": f"TENANT#{tenant_id}", "SK": "META"})` → return `.get("Item")` or `None`. No flag guard; callers that bypass the guard accept responsibility.

#### `list_tenants` — detailed contract

1. `_require_enabled()`.
2. `lek = decode_cursor(cursor)` — signed cursor → DynamoDB `ExclusiveStartKey` (`app/core/cursor.py:103`).
3. Query `GSI_OWNER`: `KeyConditionExpression=Key("owner_id").eq(owner_id)`, `ScanIndexForward=False`, `Limit=limit` (up to 50), `ExclusiveStartKey=lek` if set.
4. Collect `resp["Items"]`; capture `resp.get("LastEvaluatedKey")` as `next_lek`.
5. In-memory filter: if `status` is set, drop items where `item["status"] != status`; if `q` is set (stripped), drop items where `q.lower()` is not a substring of `(item.get("display_name","") + " " + item.get("email","")).lower()`. This is a loose-search posture consistent with the contacts pattern; `list_contacts` itself does not filter but does in-memory sort (`contacts.py:52-57`, `80`).
6. `next_cursor = encode_cursor(next_lek)` → HMAC-signed v2 token (`app/core/cursor.py:94`).
7. Return `{"tenants": items, "next_cursor": next_cursor, "count": len(items)}`.

Note: `FilterExpression` is intentionally not used here. In-memory filtering on the page keeps the query simple; the per-owner dataset is expected to be landlord-sized (O(100–1000) per `owner_id`). DynamoDB `FilterExpression` does not reduce page size against the `Limit` parameter (CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha), so a GSI query + in-memory filter is correct.

#### `update_tenant` — detailed contract

1. `_require_enabled()`.
2. Validate `patch` keys are a subset of `{"display_name", "email", "phone", "status"}`. Raise `ValueError` on unknown keys.
3. Validate `status` if present is one of `{"prospect", "active", "past"}`.
4. Normalize `email` / `phone` if patched.
5. Build `UpdateExpression` / `ExpressionAttributeValues` programmatically; always include `updated_at = now_ts()`.
6. `T.property_tenants.update_item(Key={"PK":…, "SK":"META"}, …, ConditionExpression="attribute_exists(PK)", ReturnValues="ALL_NEW")` — `app/routers/contacts.py:144-154` pattern.
7. On `ConditionalCheckFailedException`: raise `HTTPException(404, "Tenant not found")`.
8. `_audit("tenant_updated", caller_sub, tenant_id=tenant_id, **patch_summary)`.
9. Return `resp["Attributes"]`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent replay

`create_tenant` with the same `correlation_id` produces the same `tenant_id` via `sha256`. The conditional `put_item` catches `ConditionalCheckFailedException` and returns the existing META row. Exactly one audit event is emitted (on first creation only). This guarantees idempotent replay from retry-prone callers (e.g., an import script that re-runs after a partial failure).

### 5.2 Party creation ordering

`party.create_party(...)` is called **before** the `put_item` for the tenant META row. If `put_item` fails (e.g., network error after party creation), a dangling PERSON party may exist without a corresponding tenant. This is acceptable: the caller retries with the same `correlation_id`, the tenant `put_item` succeeds on the second attempt (same `tenant_id`), and the `party_id` passed in on retry is the same hash-derived value — so `party.create_party` is itself idempotent (PTY-004 §5.1: conditional put on `attribute_not_exists(PK)`), returning the existing party silently.

### 5.3 Email/phone normalization failure

`normalize_email` and `normalize_phone` raise `HTTPException(400, …)` on invalid input. These propagate directly from the service layer to the router and then to the HTTP response. Callers that receive 400 must fix the input before retrying.

### 5.4 `list_tenants` with status filter and q

Both filters apply **after** DynamoDB returns items from `GSI_OWNER`. The `Limit` is applied at the DynamoDB layer before filtering, so a page with `Limit=50` that has 30 items matching the filter returns 30 items and a `next_cursor` pointing at item 51 in DynamoDB order. Callers that need exactly N results must page until exhausted. (The `contacts.py:67-78` reference was a page-loop pattern, not a filtering example; the filtering posture here is a new design for `list_tenants`.)

### 5.5 `q` search scope

The `q` substring search covers `display_name` and `email` concatenated. It does not search `phone` (to avoid leaking partial phone fragments in URL query strings). Case-insensitive. Empty `q` (after `.strip()`) is treated as no-filter.

### 5.6 `update_tenant` with no recognized keys

`patch` kwargs containing no recognized field (`display_name`, `email`, `phone`, `status`) raise `ValueError("Nothing to update")`, converted to `HTTP 400` at the router layer.

### 5.7 `active_unit_id` is read-only in TEN-001

`update_tenant` does not accept `active_unit_id` as a patchable field; that is TEN-002's `set_active_unit` responsibility. Attempting to pass it as a `**patch` kwarg raises `ValueError("Unknown patch field: active_unit_id")`.

### 5.8 Status transitions

No transition guard is enforced in TEN-001 (any `status` value from `{"prospect", "active", "past"}` may be set at any time via `update_tenant`). The `status` field is purely informational at this stage; TEN-002 `set_active_unit` will set `status="active"` and `status="past"` automatically, but it does so via a direct `update_tenant` call without a transition matrix. A formal transition matrix (if later needed) belongs in TEN-002.

### 5.9 `GSI_PARTY` usage

`GSI_PARTY` (partition `party_id`, sort `SK`) allows TEN-002 and TEN-003 to resolve a tenant from a PTY `party_id` without a table scan. A query `Key("party_id").eq(party_id)` returns at most one META row per `party_id` because a party is linked to exactly one tenant (enforced by convention, not a DynamoDB constraint — future deduplication logic should check for zero or one result).

|---|---|---|---|
| `property_tenants_enabled` | `PROPERTY_TENANTS_ENABLED` | `False` | bool |

- Every service function that calls `_require_enabled()` raises `HTTP 404`.
- No DynamoDB reads or writes to `property_tenants` occur.

- Zero impact on billing, messaging, contacts, files, or any other subsystem.

`.env.local` should contain:

```
PROPERTY_TENANTS_ENABLED=0
DDB_PROPERTY_TENANTS_TABLE=property_tenants
```

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no `S.dev_mode` branch

`property_tenant.py` contains no `if S.dev_mode` branch. DynamoDB access goes through `T.property_tenants` identically in dev (DynamoDB Local at port 8001) and prod (real DynamoDB). The `T` handle is the `_FloatSafeTable` proxy (`app/core/tables.py:29-62`) in both environments. This is identical to the pattern in `app/services/host_inventory.py` and `app/services/kyc_cases.py` — no env divergence anywhere in the service.

### 7.2 No money path in TEN-001

TEN-001 creates no ledger entries, charges no providers, and holds no escrow. There is no interaction with `billing_shared.new_ledger_entry`, `compute_due`, `settle_or_reverse_ledger`, `apply_balance_delta`, or any Stripe/PayPal/CCBill endpoint. The rent ledger integration belongs entirely to the RNT cluster (RNT-001..006). This ticket is financially inert.

### 7.3 Idempotency surface

`create_tenant` with a fixed `correlation_id` is fully idempotent: same `tenant_id`, same PERSON party (PTY-004's own idempotency), same single audit event. `update_tenant` is last-write-wins (no version vector here); callers that need optimistic concurrency should add a `version` attribute in a future sub-ticket, following the KYC `apply_admin_decision` pattern.

### 7.4 Authorization scope

All mutations are scoped to `owner_id == ctx["user_sub"]` (the authenticated session's `user_sub`). `get_tenant` and `update_tenant` must verify that the item's `owner_id` matches the caller's `user_sub` before returning or mutating — cross-owner reads/writes must return `HTTP 403`. This check is enforced at the router layer (TEN-003 deliverable) rather than the service layer, following the PTY-004 §4.2 pattern.

### 7.5 Input normalization

`normalize_email` (`app/core/normalize.py:60`) and `normalize_phone` (`:66`) are the only normalization primitives used. They are deterministic and raise `HTTP 400` on malformed input — no silent truncation or coercion.

## 8. Backward Compatibility & Migration

### 8.1 Purely additive

TEN-001 adds:
- Two new settings fields to `app/core/settings.py` (append-only).
- One new `property_tenants` table entry in `scripts/local-ddb-init.py` (append-only; existing table creation is unaffected).
- One new `property_tenants: Any` field on the `Tables` dataclass in `app/core/tables.py` (append-only; frozen dataclass fields are positionally safe because the `Tables` instance is constructed with keyword arguments in the module-level `T` block).
- One new service file `app/services/property_tenant.py` (new file, no imports from existing modules that would create circular deps).

No existing file has a line modified by TEN-001 except the three append-only additions above.

### 8.2 `just restart` creates the table automatically

`scripts/local-ddb-init.py` runs `just restart` as part of `local-stack-up.sh`. The new `TableDef` entry causes the `property_tenants` table to be created on next restart. No manual migration or backfill is required.

### 8.3 Zero rollback risk

Because the flag defaults to `False`, a deployment of TEN-001 to production with the env var unset is a no-op from the application's perspective. Rolling back to a pre-TEN-001 binary does not corrupt data (the dormant table simply goes unread). There is no schema migration to reverse.

## 10. Open Questions / Assumptions

1. **PTY-004 availability at merge time.** TEN-001 imports `app.services.party.create_party`. If PTY-004 has not shipped yet, the import must be guarded with a `try/except ImportError` fallback that assigns `party_id = uuid4().hex` directly without calling the party service. This degraded mode should be removed once PTY-004 is merged. The spec assumes PTY-004 is either already merged or will be merged in the same batch.

2. **`T.party` handle.** `create_party` internally uses `T.party`. If PTY-002's table handle is absent (i.e., `T` has no `party` attribute), the `create_party` call will raise `AttributeError` at runtime. The degraded-mode guard above covers this case as well.

3. **Multi-tenancy / PM companies.** This spec treats `owner_id` as a single landlord's `user_sub`. Property management companies with multiple agents sharing a tenant directory will require an additional `org_id` scope; that is out of scope for TEN-001.

4. **Tenant ↔ platform user linkage.** `create_tenant` may or may not map to an existing platform user. The current design stores an optional `email` for contact purposes but does not create a platform account for the tenant. A future ticket could add a `user_sub` field to the tenant META row to support tenant-portal features (login, portal access, etc.).

5. **`display_name` required at creation.** The current contract requires a non-empty `display_name`. If the caller cannot supply one (e.g., an import that only has email), they should pass `email` as the temporary `display_name`. A future improvement could default `display_name` from `email` when absent.

6. **Soft-delete.** TEN-001 has no `delete_tenant` function. Tenant records are permanent (status `"past"` signals inactive). A future `archive_tenant` operation would set `status="past"` and add a DynamoDB TTL, following the `archive_property` pattern in PROP-001 §4.3 (`app/services/property_mgmt.py`). This is deferred to a follow-up ticket.
