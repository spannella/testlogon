**Ticket type:** Feature
**Priority:** P2
**Estimate:** 2 d
**Flag:** `RENT_LEDGER_ENABLED` (default OFF, shared across all RNT tickets)
**Depends on:** RNT-001 (`rent_charge` rows, idempotency marker, `post_rent_charge`), RNT-002 (`record_payment`, `derive_charge_status`, `list_rent_ledger_for_lease`), RNT-003 (`void_rent_row`, reversal counter deltas), LSE-001/002 (lease entity and query surface), OFB-015 (`compute_ar_aging`, soft / graceful-fallback dependency)

## 1. Summary & Goal

RNT-004 delivers the portfolio-facing **period summary**: a single endpoint that aggregates
`rent_charge` and `rent_payment` ledger rows for a given calendar month (`"YYYY-MM"`) and
returns the four running totals a landlord needs to manage collections:

- **charged** — total rent posted (sum of non-reversed `rent_charge` rows for the period)
- **collected** — total cash recorded (sum of non-reversed `rent_payment` rows for the period)
- **outstanding** — `charged − collected` for the period, cross-checked against `compute_due`
  (`billing_shared.py:158`) at the all-time level for reconciliation
- **overdue** — charges whose `derive_charge_status` is `"overdue"`, optionally enriched with
  AR-aging buckets from OFB-015's `compute_ar_aging` when that feature is enabled

A companion `list_periods` helper returns the trailing N calendar months as `"YYYY-MM"`
strings, enabling the frontend to render a prev/next period navigator without scanning DDB.

The summary can be scoped to **a single lease** or to the landlord's **entire portfolio**.
Both scopes use the same service function with an optional `lease_id` filter.

This ticket satisfies gap-matrix §B row 58 (*"period totals (charged/collected/outstanding/overdue) …
reuse `compute_due` + planned OFB-015 aging"*) from
`docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md`.

With `RENT_LEDGER_ENABLED=0` (the default): every new endpoint returns 404, every new
service function short-circuits to `None`, and no existing surface changes by a single byte.

| `apply_balance_delta(table, pk, delta, *, currency="usd") -> None` | `billing_shared.py:83` | Used by RNT-001/002/003 to maintain running counters; RNT-004 reads the BALANCE row those writes produce |
| `compute_due(balance_item) -> dict` | `billing_shared.py:158–170` | Returns `{"due_settled_cents": int, "due_if_all_settles_cents": int}` from the BALANCE row; used as an all-time cross-check in the period summary |
| `settle_or_reverse_ledger(table, key_name, key_value, ledger_sk_value, new_state)` | `billing_shared.py:262–274` | Written by RNT-003 void; RNT-004 excludes `state="reversed"` rows from aggregation |

`compute_due` at `billing_shared.py:158–170` computes:
- `due_settled_cents = owed_settled_cents − payments_settled_cents`
- `due_if_all_settles_cents = (owed_settled + owed_pending) − (payments_settled + payments_pending)`

Both counter families are written to the `BALANCE` row (`pk=USER#{user_sub}`, `sk="BALANCE"`)
by `apply_balance_delta` (`billing_shared.py:83`). RNT-001 bumps `owed_settled_cents` per
`rent_charge`; RNT-002 bumps `payments_settled_cents` per `rent_payment`; RNT-003 void
reverses the matching counter (net effect: the BALANCE row reflects the running landlord
position across all time).

`app/services/platform_financial_dashboard.py` is a **platform-GMV** aggregator for the

### 2.3 How existing ledger rows are scanned per landlord

`app/routers/billing.py:2451` shows the canonical per-user ledger query:
```python
items = ddb_query_pk(T.billing, user_pk(user_id))
led = [it for it in items if it["sk"].startswith("LEDGER#")]
led.sort(key=lambda x: x.get("ts", 0), reverse=True)
return {"items": led[:max(1, min(limit, 200))]}
```
`ddb_query_pk` (`billing_shared.py:43`) fetches all items under a partition key without
filtering — filtering must be done client-side (CLAUDE.md: "FilterExpression does not reduce
page size"). RNT-004 follows this exact pattern: fetch the entire landlord partition, then
filter in-memory to `LEDGER#` rows with matching `extra.lease_id` and `extra.period`.

For the **all-leases portfolio scope**, the partition is the same `USER#{user_sub}` partition
(all of the landlord's leases live under the same partition key because the billing table
stores rows keyed by the landlord's `user_sub`, not by lease). There is **no cross-partition
scan** — the `period_summary` for a landlord always reads exactly one partition, which is
bounded by the number of leases owned by that landlord.

## 3. Data Model

### 3.1 No new DynamoDB tables

RNT-004 introduces **no new tables** and **no new GSIs**. All data is read from:

- **`T.billing`** — the existing billing table (`S.billing_table_name`, default `"billing"`,
  `app/core/settings.py:348`; handle at `app/core/tables.py:333`). The period summary
  reads the landlord's partition (`pk=USER#{user_sub}`) to find `rent_charge` and
  `rent_payment` rows written by RNT-001 and RNT-002.
  - Charge rows: `sk.startswith("LEDGER#")`, `type="rent_charge"`, `state` in `{"settled","reversed"}`,
    `extra.period = "YYYY-MM"`, `extra.lease_id`, `extra.rent_kind = "charge"`.
  - Payment rows: `sk.startswith("LEDGER#")`, `type="rent_payment"`, `state` in `{"settled","reversed"}`,
    `extra.period = "YYYY-MM"`, `extra.lease_id`, `extra.rent_kind = "payment"`.
  - BALANCE row: `sk="BALANCE"` — carries `owed_settled_cents` and `payments_settled_cents`
    for the `compute_due` cross-check.
- **`T.leases`** — the leases table introduced by LSE-001 (`S.leases_table_name`, default
  `"leases"`; handle registered in `app/core/tables.py` by LSE-001). Used to resolve the
  `lease_count` (number of active leases in scope) and to supply per-lease context
  (`monthly_rent_cents`, `rent_due_day`, `late_fee_grace_days`, `currency`) for the
  `derive_charge_status` fallback path.

### 3.2 Ledger row fields read by the aggregation

The following `extra` fields are denormalized onto every `rent_charge` / `rent_payment` row
at write time (RNT-001/002, per `RENT_LEDGER_TICKETS.md` constraint 8):

| Field | Source | Used in RNT-004 |
|---|---|---|
| `period` | `"YYYY-MM"` written by RNT-001/002 via `extra=` arg (merged top-level by `new_ledger_entry:255`) | Primary filter — `r.get("period") == period` |
| `lease_id` | bare lease ID, merged top-level | Scope filter — `r.get("lease_id") == lease_id` |
| `rent_kind` | `"charge"` or `"payment"`, merged top-level | Separate charge vs. payment — `r.get("rent_kind")` |
| `property_id` | from lease, merged top-level | Available for future property-scoped rollups (not used in RNT-004) |
| `tenant_id` | from lease, merged top-level | Available for tenant-scoped queries (not used in RNT-004) |
| `amount_cents` | integer cents | Accumulated into running totals |
| `state` | `"settled"` or `"reversed"` | `"reversed"` rows are excluded from all sums |

> **Layout note (MONEY-SAFETY):** `new_ledger_entry` (`billing_shared.py:255`) does
> `item.update(extra)` — all `extra=` key/value pairs are merged **flat onto the top-level
> item dict**, not stored under a nested `"extra"` sub-object. Access rent fields directly:
> `r.get("period")`, `r.get("lease_id")`, `r.get("rent_kind")`. Any code using
> `r.get("extra", {}).get("period")` would silently return `None` and produce zero totals.

## 4. API / Service Design

### 4.1 Service additions — `app/services/rent_ledger.py`

All functions added by this ticket short-circuit on `if not S.rent_ledger_enabled: return None`.

#### `list_periods(user_sub: str, *, lease_id: str | None = None, count: int = 12) -> list[str]`

**Purpose:** Period navigation helper. Returns the trailing `count` `"YYYY-MM"` strings
ending at (and including) the current month, in ascending order. Pure date math; no DDB
access; `user_sub` and `lease_id` are accepted for signature consistency but ignored
(all periods exist for any landlord).

```python
def list_periods(
    user_sub: str,
    *,
    lease_id: str | None = None,
    count: int = 12,
) -> list[str]:
    if not S.rent_ledger_enabled:
        return []
    count = max(1, min(count, 60))  # clamp: 1–60 months
    now_utc = datetime.now(timezone.utc)
    periods: list[str] = []
    for i in range(count - 1, -1, -1):
        # subtract i months from current month (year-aware)
        y = now_utc.year
        m = now_utc.month - i
        while m <= 0:
            m += 12
            y -= 1
        periods.append(f"{y:04d}-{m:02d}")
    return periods
```

Returns e.g. `["2025-07", "2025-08", ..., "2026-06"]` for `count=12` as of June 2026.

#### `period_summary(user_sub: str, *, period: str | None = None, lease_id: str | None = None) -> dict | None`

**Purpose:** The main aggregation function. Reads the landlord's billing partition, filters
to the requested period (default: current month), and returns the four running totals plus
optional OFB-015 aging buckets.

**Signature:**
```python
def period_summary(
    user_sub: str,
    *,
    period: str | None = None,
    lease_id: str | None = None,
) -> dict | None:
```

**Steps:**

1. **Flag guard.** `if not S.rent_ledger_enabled: return None`.

2. **Period normalization.** `period = period or _current_period()`. Validate format with
   `re.fullmatch(r"\d{4}-(?:0[1-9]|1[0-2])", period)` → raise `ValueError("invalid_period")` if malformed; the router maps this to HTTP 422.

3. **Single-lease ownership check (optional scope).** When `lease_id` is supplied, call
   `get_lease(user_sub, lease_id)` (LSE-001) → if the lease is not found in the landlord's
   partition, raise `HTTPException(404, "lease_not_found")`. Ownership is implicitly
   enforced by the DDB key (`pk=USER#{user_sub}`, `sk=LEASE#{lease_id}`).

4. **Fetch all ledger rows for the landlord partition.**
   ```python
   all_items = ddb_query_pk(T.billing, user_pk(user_sub))
   ```
   Filter client-side (CLAUDE.md: `FilterExpression` does not reduce page size — constraint 6):
   ```python
   ledger_rows = [
       it for it in all_items
       if it.get("sk", "").startswith("LEDGER#")
       and it.get("rent_kind") in ("charge", "payment")
       and it.get("period") == period
   ]
   ```
   When `lease_id` is supplied, further narrow:
   ```python
   ledger_rows = [r for r in ledger_rows if r.get("lease_id") == lease_id]
   ```

5. **Separate charges and payments; exclude reversed rows.**
   ```python
   charges  = [r for r in ledger_rows if r.get("rent_kind") == "charge"  and r.get("state") != "reversed"]
   payments = [r for r in ledger_rows if r.get("rent_kind") == "payment" and r.get("state") != "reversed"]
   ```

6. **Compute the four primary totals.**
   ```python
   charged_cents    = sum(int(r["amount_cents"]) for r in charges)
   collected_cents  = sum(int(r["amount_cents"]) for r in payments)
   outstanding_cents = charged_cents - collected_cents
   charge_count     = len(charges)
   payment_count    = len(payments)
   ```

7. **Compute `due_settled_cents_all_time` from BALANCE row** (cross-check for reconciliation).
   Fetch `ddb_get(T.billing, user_pk(user_sub), "BALANCE")`. If absent (no rent rows yet),
   treat all balance fields as 0. Pass to `compute_due(balance_item)`:
   ```python
   bal = ddb_get(T.billing, user_pk(user_sub), "BALANCE") or {}
   due_totals = compute_due(bal)
   ```
   Surface `due_totals["due_settled_cents"]` as `due_settled_cents_all_time` in the response
   (all-time net outstanding for reconciliation, not per-period).

8. **Compute `overdue_cents` and `aging` buckets.**

   **Path A — OFB-015 available and enabled:**
   ```python
   if getattr(S, "ar_ap_subledgers_enabled", False):
       try:
           from app.services.ar_subledger import compute_ar_aging
           aging_raw = compute_ar_aging(user_sub=user_sub, as_of_ts=now_ts())
           overdue_cents = aging_raw.get("total_open_cents", 0)
           aging = {
               "current_cents":      aging_raw.get("current_cents", 0),
               "days_30_cents":      aging_raw.get("days_30_cents", 0),
               "days_60_cents":      aging_raw.get("days_60_cents", 0),
               "days_90_plus_cents": aging_raw.get("days_90_plus_cents", 0),
               "total_open_cents":   aging_raw.get("total_open_cents", 0),
               "open_item_count":    aging_raw.get("open_item_count", 0),
               "source":             "ar_subledger",
           }
       except Exception:
           logger.warning("period_summary: ar_subledger unavailable, falling back", exc_info=True)
           overdue_cents, aging = _fallback_overdue(user_sub, charges, period)
   else:
       overdue_cents, aging = _fallback_overdue(user_sub, charges, period)
   ```

   **Path B — Fallback (OFB-015 off or import failure):**
   `_fallback_overdue(user_sub, charges, period) -> tuple[int, None]` iterates the `charges`
   list and, for each charge, calls `derive_charge_status` (RNT-002):
   ```python
   def _fallback_overdue(user_sub, charges, period) -> tuple[int, None]:
       try:
           # list_rent_ledger_for_lease and derive_charge_status are defined
           # in this same module (rent_ledger.py); call them directly rather
           # than importing from self to avoid the circular-import smell.
           # gather payments for the matching lease+period for each charge
           overdue_total = 0
           for charge_row in charges:
               lid = charge_row.get("lease_id")
               lease = _get_lease_soft(user_sub, lid)
               if not lease:
                   continue
               payments_for_lease = list_rent_ledger_for_lease(user_sub, lid)
               status = derive_charge_status(charge_row, payments=payments_for_lease, lease=lease)
               if status == "overdue":
                   overdue_total += int(charge_row["amount_cents"])
           return overdue_total, None
       except Exception:
           logger.warning("period_summary: fallback overdue failed", exc_info=True)
           return 0, None
   ```
   The double try/except guarantees the summary never errors even if RNT-002 functions are
   unavailable.

9. **Compute `lease_count`.**
   When `lease_id` is supplied: 1 (or 0 if the lease is `ended`/`draft`).
   When all-portfolio: query LSE's GSI2 (`USER#{user_sub}#STATUS#active`) for the count of
   active leases. On failure (LSE not yet enabled): fall back to the number of distinct
   `lease_id` values seen in the current period's charge rows — best-effort, wrapped in
   `try/except`.

10. **Assemble and return the result dict.**
    ```python
    return {
        "period":                    period,
        "scope":                     lease_id or "all",
        "charged_cents":             charged_cents,
        "collected_cents":           collected_cents,
        "outstanding_cents":         outstanding_cents,
        "overdue_cents":             overdue_cents,
        "due_settled_cents_all_time": due_totals["due_settled_cents"],
        "charge_count":              charge_count,
        "payment_count":             payment_count,
        "lease_count":               lease_count,
        "aging":                     aging,  # None when OFB-015 absent/off
    }
    ```

### 4.2 Helper: `_get_lease_soft(user_sub, lease_id) -> dict | None`

Internal helper that calls `get_lease(user_sub, lease_id)` (LSE-001) inside a bare

## 5. Detailed Behavior & Edge Cases

### 5.1 Period with no rows (future month or period before rent-run started)

When the landlord has no `rent_charge` or `rent_payment` rows for the requested `period`,
all running totals are 0: `charged_cents=0`, `collected_cents=0`, `outstanding_cents=0`,
`overdue_cents=0`, `charge_count=0`, `payment_count=0`. The response is valid and non-erroneous.
`lease_count` reflects the current number of active leases even for future periods.

### 5.2 Period with partial payments (outstanding > 0)

A partial payment (one `rent_payment` row with `amount_cents < charge.amount_cents`) yields
`outstanding_cents > 0`. A voided payment (state=`"reversed"`) is excluded from
`collected_cents`, correctly increasing `outstanding_cents` — consistent with RNT-003's
balance reversal.

### 5.3 Void of a `rent_charge` mid-period

When RNT-003 voids a `rent_charge`, it calls `settle_or_reverse_ledger` (flipping `state` to
`"reversed"`) and `apply_balance_delta({"owed_settled_cents": -amount})`. The period summary
picks this up naturally: the reversed row is excluded from `charges` (step 5), so
`charged_cents` drops immediately without any special-casing in RNT-004.

### 5.4 Multiple leases in portfolio scope

All `rent_charge` and `rent_payment` rows for all of the landlord's leases live under the
same partition (`pk=USER#{user_sub}`), so the single `ddb_query_pk` call in step 4 fetches
all of them in one request (bounded by the number of ledger rows, not by the number of
leases). The client-side `period` filter applied in step 4 scopes to the requested month.

### 5.5 `ddb_query_pk` returns all rows, not just LEDGER rows

The partition also contains `BALANCE`, `PM#`, `BILLING`, and other rows. The client-side
filter `sk.startswith("LEDGER#")` and `extra.rent_kind in ("charge","payment")` narrows the
set to only rent rows. Non-rent ledger rows (e.g. `type="tip_debit"`) are excluded by the
`rent_kind` check.

### 5.6 `due_settled_cents_all_time` vs. `outstanding_cents`

`outstanding_cents` is **period-scoped**: it counts only the current period's charges and
payments. `due_settled_cents_all_time` (from `compute_due`) is **all-time**: it reflects the
net of every `rent_charge` / `rent_payment` ever posted against the landlord's BALANCE row.
These values will diverge when there are prior unpaid periods. Both are surfaced in the
response so the frontend can show the per-period figure prominently and the all-time figure
as a reconciliation check.

### 5.7 OFB-015 graceful fallback

When `S.ar_ap_subledgers_enabled=False` or when the import of `compute_ar_aging` raises any
exception (module not yet deployed, table not yet created, etc.), the fallback path is
taken. The fallback computes `overdue_cents` by iterating `charges` and calling
`derive_charge_status`. If that also fails, `overdue_cents=0` and `aging=None` are returned.
Neither path raises an HTTP error — the summary is always returned, potentially with
`overdue_cents=0` if both computation paths fail. Warnings are logged.

### 5.8 `list_periods` count boundary

`count` is clamped to `[1, 60]`. A request for `count=0` returns 1 period; `count=61`
returns 60. The function never raises on out-of-range values.

### 5.9 Invalid `period` format

`period` must match `^\d{4}-(0[1-9]|1[0-2])$`. The FastAPI `Query(pattern=...)` validator
rejects malformed strings with HTTP 422 before the handler is called. The service-layer
`re.fullmatch` in step 2 provides a defense-in-depth guard for direct service calls.

### 5.10 Single-lease scope with a lease belonging to another landlord

`get_lease(user_sub, lease_id)` (LSE-001) resolves via `pk=USER#{user_sub}`,
`sk=LEASE#{lease_id}`. If the lease is owned by a different landlord, the DDB item is simply
absent from the calling landlord's partition → 404 `"lease_not_found"`. No lease data from
other landlords is ever accessed (constraint 8).

### 5.11 Very large billing partitions

A landlord managing hundreds of leases over many years will accumulate thousands of ledger
rows under their partition. `ddb_query_pk` fetches up to 1MB per call. For partitions that
exceed 1MB, a single `query()` call silently misses items beyond the first page (CLAUDE.md
gotcha). However, `ddb_query_pk` (`billing_shared.py:43`) does **not** loop on
`LastEvaluatedKey`.

For the initial implementation (P2 priority), the 1MB limit is acceptable because:
- Each ledger row is small (~500 bytes); 1MB accommodates ~2000 rows.
- A landlord would need 2000+ rent rows to hit this limit (166+ years of monthly rent on a
  single-lease portfolio, or ~170 active leases with 12 months of history each).

An open question (§10) flags whether a paginated scan should replace `ddb_query_pk` if
portfolio sizes warrant it.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no dev_mode branch

`period_summary` and `list_periods` contain **no `if S.dev_mode:` branch**. Both call
`ddb_query_pk(T.billing, ...)` directly; in dev the call resolves to DynamoDB Local (via
moto in tests or `DDB_ENDPOINT_URL=http://localhost:8001` in the dev stack), in prod to real
DynamoDB. One code path for both environments (constraint 5 of `RENT_LEDGER_TICKETS.md`).
There is no online payment provider integration in RNT-004 and therefore no payment divergence
to mock.

### 7.2 Idempotency

`period_summary` and `list_periods` are **read-only** operations: they make no writes to any
DDB table. Calling either endpoint any number of times produces the same result for fixed
inputs (deterministic). No idempotency marker is needed.

### 7.3 MONEY-SAFETY

RNT-004 is a read-only aggregation layer. It:
- Makes **no calls** to `new_ledger_entry`, `apply_balance_delta`, or
  `settle_or_reverse_ledger`.
- Performs **no deletes** on any table.
- Reads `amount_cents` as `int(r["amount_cents"])` to safely coerce DynamoDB `Decimal`
  values (standard practice following `compute_due`'s own `int()` casts at
  `billing_shared.py:159–162`).
- Never constructs a balance total from raw arithmetic independent of the ledger — the
  `outstanding_cents` field is a simple period-scoped sum, not a new money primitive.
- The `due_settled_cents_all_time` cross-check calls `compute_due` verbatim with the BALANCE
  row — unmodified (constraint 4).

### 7.4 Ownership isolation

The `period_summary` function reads only `pk=USER#{user_sub}` — the calling landlord's
partition. It is structurally impossible to access another landlord's ledger rows. When
`lease_id` is supplied, the `get_lease(user_sub, lease_id)` pre-check enforces ownership
via the DDB access pattern (`pk=USER#{user_sub}`, `sk=LEASE#{lease_id}`) — a lease belonging
to another landlord simply does not exist in the caller's partition (constraint 8).

### 7.5 Auth and CSRF

Both endpoints use `Depends(require_ui_session)`. They are `GET` methods; CLAUDE.md states
that CSRF is enforced only for non-GET cookie-auth requests. No `x-csrf-token` header is
required for these endpoints.

## 10. Open Questions / Assumptions

**Q1 (Partition size — `ddb_query_pk` loop).** The current implementation uses
`ddb_query_pk` (`billing_shared.py:43`), which does **not** loop on `LastEvaluatedKey`.
For portfolios with many hundreds of leases and years of history, this silently truncates
results beyond the first 1MB DynamoDB page. Should `period_summary` use a paginated scan
loop (cloning `_scan_all_running_instances` at `compute_billing.py:507–522`) instead?

*Assumption for RNT-004 (P2):* the single-query approach is acceptable for typical portfolios
at this stage. A follow-up ticket can add the `LastEvaluatedKey` loop if needed.

**Q2 (All-time vs. period-scoped `due_settled_cents`).** `compute_due` operates on
all-time counters. When the landlord has multiple periods with unpaid charges, the all-time
`due_settled_cents` will exceed the current period's `outstanding_cents`. Is the distinction
clear enough in the API response? If not, should the BALANCE row be supplemented with
per-period balance rows?

*Assumption:* surfacing both values (`outstanding_cents` = period-scoped; `due_settled_cents_all_time`
= all-time cross-check) is sufficient. The FE should label them clearly.

**Q3 (OFB-015 `user_sub` scoping for AR aging).** `compute_ar_aging` can accept `user_sub`
to scope to a single landlord's invoices. However, OFB-015's AR aging is designed for
platform invoices, not rent ledger rows. When `user_sub` is supplied, it returns the
landlord's *invoice* aging, which may not map cleanly to rent-overdue semantics. Should
RNT-004 always use the fallback path and only use OFB-015 when a dedicated per-tenant AR
entry type is defined?

*Assumption:* use `compute_ar_aging(user_sub=user_sub, ...)` and surface the buckets
as-is with `source="ar_subledger"`. The downstream rent team can override this in a later
ticket if the semantics diverge.

**Q4 (Currency support).** All sums are in `int` cents. The response does not currently
include a `currency` field. If a landlord has leases in multiple currencies, aggregation
across them would produce a meaningless number. Should `period_summary` reject or warn on
mixed-currency portfolios?

*Assumption:* for P2, the response returns cents without currency annotation and the
service assumes a single currency per landlord (the `currency` field from the first charge
row's `extra.currency`). A follow-up ticket can add per-currency breakdowns.

**Q5 (Admin / root scope).** RNT-004 scopes to the calling landlord only. Is a ROOT-scoped
system-wide period summary (across all landlords) needed?

*Assumption:* out of scope for this ticket. A `GET /ui/admin/rent/summary` endpoint can be
added as a separate ticket when needed, reusing `period_summary` with `user_sub=None` and a
cross-user GSI scan.
