# WOV-002 — Work-order lifecycle — assignment, scheduling, cost, status queue

## 1. Summary & Goal

WOV-002 adds the full mutating lifecycle to the maintenance work-order service introduced by WOV-001. The deliverables are:

1. **`assign_work_order`** — attach a vendor (`vendor_id`) and/or staff member (`assignee_sub`) to an open or already-assigned work order; advance status to `assigned` when coming from `open`; update `GSI_WO_ASSIGNEE`.
2. **`schedule_work_order`** — record (or update) the planned execution timestamp `scheduled_for`; re-callable for rescheduling.
3. **`transition_work_order`** — enforce the five-state machine (`open → assigned → in_progress → completed / cancelled`) with optimistic-lock protection against concurrent transitions; stamp `completed_at` and `cost_cents` on completion.
4. **`list_work_orders`** — three-mode paginated query (by property, by status queue, by assignee) that drives the Kanban board columns in WOV-005.
5. **`app/routers/maintenance_orders.py`** — HTTP router wiring the service functions to property-scoped and system-wide endpoints, registered in `app/main.py`.

All code is additive. With `MAINTENANCE_ORDERS_ENABLED=false` (the default) the platform is byte-for-byte unchanged.

### 2.4 Optimistic-lock transition pattern — FXA-012 §5.4

The `ConditionExpression="wo_status = :current"` guard on `update_item` is established by the FXA-012 spec (`docs/ofbiz/specs/FXA-012.md` §5.4). A concurrent second caller whose `update_item` fires after the first caller's write wins gets `ConditionalCheckFailedException`; WOV-002 maps that to HTTP 409 `concurrent_transition` (distinct from `illegal_transition` so callers can disambiguate).

### 2.5 Vendor active-supplier guard — PUR-003 §5.3 + §5.6

`docs/ofbiz/specs/PUR-003.md` §5.3 specifies that `set_supplier_status("inactive")` soft-deactivates a supplier; the row persists but is excluded from active-status GSI queries. §5.6 ("Interaction with downstream tickets") notes that the active-supplier enforcement on creation is a *per-consumer* concern (PUR-003 §5.6 specifically cites PUR-006's `create_purchase_order` as the pattern; WOV-002 follows the same principle for `assign_work_order`). WOV-002's `assign_work_order` therefore rejects assignment to an inactive vendor with HTTP 422 `vendor_inactive`, mirroring PUR-006's pattern. The guard lazy-imports `app.services.maintenance_vendors.get_vendor` (WOV-004); when WOV-004 is unbuilt the import is wrapped in `try/except ImportError` and the vendor check is skipped (staff sub assignment still works).

| Attribute | DDB Type | Notes |
|---|---|---|
| `pk` | S | `"PROPERTY#{property_id}"` — partition key |

**GSIs (declared by WOV-001 in `scripts/local-ddb-init.py`):**

| Index | PK | SK | `attr_types` | Use |
|---|---|---|---|---|
| `GSI_WO_STATUS` | `wo_status` (S) | `created_at` (N) | `{"created_at": "N"}` | System-wide status queue; drives Kanban columns |

## 5. Detailed Behavior & Edge Cases

### 5.1 `assign_work_order`

```
1. _require_enabled()
2. Fetch item: pk=_wo_pk(property_id), sk=_wo_sk(work_order_id)
   → 404 "work_order_not_found" if absent
3. Validate at least one of body.vendor_id / body.assignee_sub is non-None
   → 422 "assign_requires_target" if both absent
4. Vendor guard (when body.vendor_id is not None):
   try:
       from app.services.maintenance_vendors import get_vendor
       vendor = get_vendor(body.vendor_id)
       if vendor is None:
           raise HTTPException(404, "vendor_not_found")
       if vendor.status == "inactive":
           raise HTTPException(422, "vendor_inactive")
   except ImportError:
       pass   # WOV-004 not yet built; skip guard, allow assignment
5. Build update expression:
   SET vendor_id = :v, assignee_sub = :a, unit_id = :u, updated_at = :ts
   (set only the fields present in body; absent fields are left unchanged)
6. If item["wo_status"] == "open":
   add "wo_status = :assigned" to the SET expression
   target_status = "assigned"
   (open → assigned is a free upgrade on first assignment; no VALID_TRANSITIONS
    check needed because the assign endpoint is the *canonical* path for this step)
7. T.maintenance_orders.update_item(
       Key=...,
       UpdateExpression="SET ...",
       ExpressionAttributeValues=...,
   )
   (no ConditionExpression here — concurrent assign calls are last-write-wins
    because two staff simultaneously assigning different vendors to the same
    open WO is not a destructive race: the later write wins and the audit trail
    shows both attempts)
8. Re-fetch updated item; return _item_to_out(item)
9. _audit("maintenance_order.assigned", actor_sub,
           work_order_id=..., property_id=...,
           vendor_id=..., assignee_sub=..., unit_id=...)
```

**Why no ConditionExpression on assign:** Unlike `transition_work_order`, assignment is not a terminal state change; reassignment is always valid. The ConditionExpression would add latency and spurious 409s without adding safety.

**`wo_status` advance on assign:** Only `open → assigned` is an implicit advance. If the work order is already `in_progress` or `completed`, calling `/assign` updates vendor/assignee attributes without changing `wo_status`. If it is `cancelled`, the endpoint raises 409 `illegal_assignment_terminal`.

### 5.2 `schedule_work_order`

```
1. _require_enabled()
2. Fetch item → 404 if absent
3. Reject if wo_status ∈ {"completed", "cancelled"}
   → 409 "cannot_schedule_terminal"
4. T.maintenance_orders.update_item(
       Key=...,
       UpdateExpression="SET scheduled_for = :sf, updated_at = :ts",
       ExpressionAttributeValues={":sf": body.scheduled_for, ":ts": now_ts()},
   )
5. Re-fetch; return _item_to_out
6. _audit("maintenance_order.scheduled", actor_sub,
           work_order_id=..., property_id=..., scheduled_for=...)
```

Rescheduling (calling `/schedule` again on the same WO) is a valid idempotent update — there is no guard against overwriting a prior `scheduled_for`. Staff can freely move the schedule date. Past timestamps are accepted (recording a completed schedule after the fact).

### 5.3 `transition_work_order`

```
1. _require_enabled()
2. Fetch item → 404 "work_order_not_found" if absent
3. current = item["wo_status"]
   target = body.target_status
   if target not in VALID_TRANSITIONS.get(current, set()):
       raise HTTPException(409, "illegal_transition",
                           headers={"X-Current-Status": current, "X-Target-Status": target})
4. ts = now_ts()
   update_parts = ["wo_status = :s", "updated_at = :ts"]
   expr_vals = {":s": target, ":ts": ts, ":current": current}
   if target == "completed":
       update_parts.append("completed_at = :ts")
   if body.cost_cents is not None:
       # Reject cost_cents on non-completed transitions at the router level (HTTP 422
       # "cost_cents_only_on_completion"); the service itself stores it unconditionally
       # to keep layer boundaries clean — router owns this validation.
       update_parts.append("cost_cents = :cc")
       expr_vals[":cc"] = body.cost_cents
   if body.assignee_sub is not None:
       update_parts.append("assignee_sub = :as")
       expr_vals[":as"] = body.assignee_sub
   if body.vendor_id is not None:
       update_parts.append("vendor_id = :vi")
       expr_vals[":vi"] = body.vendor_id
5. try:
       T.maintenance_orders.update_item(
           Key={"pk": _wo_pk(property_id), "sk": _wo_sk(work_order_id)},
           UpdateExpression="SET " + ", ".join(update_parts),
           ExpressionAttributeValues=expr_vals,
           ConditionExpression="wo_status = :current",
       )
   except ClientError as exc:
       if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
           raise HTTPException(409, "concurrent_transition")
       raise
6. Re-fetch updated item; return _item_to_out
7. _audit(f"maintenance_order.{target}", actor_sub, ...)
```

**VALID_TRANSITIONS for WOV-002 (five-state machine):**
```
"open":        {"assigned", "in_progress", "cancelled"}
"assigned":    {"in_progress", "open", "cancelled"}
"in_progress": {"completed", "cancelled"}
"completed":   set()
"cancelled":   set()
```

The `assigned` state is additive vs FXA-012's four-state machine: it allows walking back from `assigned → open` (vendor removed, WO returned to queue) which is the open-property WO workflow.

**Illegal transitions table:**
| `current` | `target` | HTTP |
|---|---|---|
| `open` | `completed` | 409 `illegal_transition` |
| `assigned` | `completed` | 409 `illegal_transition` |
| `completed` | any | 409 `illegal_transition` |
| `cancelled` | any | 409 `illegal_transition` |

### 5.4 `list_work_orders` — three query modes

Mode selection priority: `property_id` > `wo_status` > `assignee_sub`. No-filter call → HTTP 400 `supply_filter`.

**Mode A — by property (base table, bounded partition):**
- `KeyConditionExpression = Key("pk").eq(_wo_pk(property_id))`
- `ScanIndexForward=False` → newest-first by `sk` (random UUID, not timestamp) — not chronological; caller should sort by `created_at` client-side for strict ordering, or rely on the GSI for time-ordered queries.
- Optional `wo_status` → `FilterExpression`. Per the CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha, filtering a sparse attribute means a single DDB page may return fewer than `limit` items; callers must follow `cursor` to exhaustion to get a complete list.

**Mode B — by status (GSI_WO_STATUS):**
- `IndexName="GSI_WO_STATUS"`, `KeyConditionExpression = Key("wo_status").eq(wo_status)`
- `ScanIndexForward=False` → newest `created_at` first.
- Drives each Kanban column: the frontend calls Mode B once per status column.
- Optional `assignee_sub` → `FilterExpression`.

**Mode C — by assignee (GSI_WO_ASSIGNEE):**
- `IndexName="GSI_WO_ASSIGNEE"`, `KeyConditionExpression = Key("assignee_sub").eq(assignee_sub)`
- Sparse index: WOs with no `assignee_sub` are absent (they were never indexed).
- Optional `wo_status` → `FilterExpression`.

```python
def list_work_orders(property_id=None, wo_status=None, assignee_sub=None,
                     cursor=None, limit=50) -> WoListOut:
    _require_enabled()
    if limit > 200:
        limit = 200
    kwargs = {"ScanIndexForward": False, "Limit": limit}
    if cursor:
        start_key = decode_cursor(cursor)
        if start_key:
            kwargs["ExclusiveStartKey"] = start_key
    if property_id:
        kwargs["KeyConditionExpression"] = Key("pk").eq(_wo_pk(property_id))
        if wo_status:
            kwargs["FilterExpression"] = Attr("wo_status").eq(wo_status)
        resp = T.maintenance_orders.query(**kwargs)
    elif wo_status:
        kwargs["IndexName"] = "GSI_WO_STATUS"
        kwargs["KeyConditionExpression"] = Key("wo_status").eq(wo_status)
        if assignee_sub:
            kwargs["FilterExpression"] = Attr("assignee_sub").eq(assignee_sub)
        resp = T.maintenance_orders.query(**kwargs)
    elif assignee_sub:
        kwargs["IndexName"] = "GSI_WO_ASSIGNEE"
        kwargs["KeyConditionExpression"] = Key("assignee_sub").eq(assignee_sub)
        if wo_status:
            kwargs["FilterExpression"] = Attr("wo_status").eq(wo_status)
        resp = T.maintenance_orders.query(**kwargs)
    else:
        raise HTTPException(400, "supply_filter")
    items = [_item_to_out(i) for i in resp.get("Items", [])]
    return WoListOut(
        items=items,
        count=len(items),
        cursor=encode_cursor(resp.get("LastEvaluatedKey")),
    )
```

### 5.5 Decimal coercion in `_item_to_out`

DynamoDB Local and moto return numeric attributes as `Decimal`. `_item_to_out` (delivered in WOV-001) coerces via `int(item["created_at"])` and `int(v) if (v := item.get("field")) is not None else None` for nullable numeric fields (`scheduled_for`, `completed_at`, `cost_cents`). This pattern is established by FXA-012 §5.6 and prevents `ValidationError` from Pydantic on `int` fields receiving `Decimal`.

### 5.6 `cost_cents` router-layer validation

The router raises HTTP 422 `cost_cents_only_on_completion` when `body.cost_cents is not None` and `body.target_status != "completed"`. The service layer stores `cost_cents` unconditionally to keep the boundary clean (same design rationale as FXA-012 §5.4 cost policy note).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 Dev/prod parity (SECOPS-007)

`app/services/maintenance_orders.py` and `app/routers/maintenance_orders.py` contain **zero** `if S.dev_mode` branches. All DDB I/O uses identical code paths against DynamoDB Local (port 8001, dev), moto (in-process, tests), and real DynamoDB (prod). `encode_cursor`/`decode_cursor` handle `Decimal` in all three environments via `_json_default` at `cursor.py:12` (logic body at lines 17–18). The vendor guard lazy-imports `maintenance_vendors.get_vendor` which is also a pure DDB call with no environment branch.

### 7.2 Idempotency

| Operation | Idempotency mechanism |
|---|---|
| `assign_work_order` | Last-write-wins `update_item`; calling twice with same args produces the same row state. Not guarded by condition — concurrent assigns are last-writer-wins (acceptable for a non-terminal state update). |
| `schedule_work_order` | Last-write-wins `update_item`; rescheduling is explicitly valid. |
| `transition_work_order` | `ConditionExpression="wo_status = :current"` prevents double-apply. A replay of `open → in_progress` after the state is already `in_progress` returns 409 `concurrent_transition` (or 409 `illegal_transition` if the machine has moved further). Callers should re-fetch on 409 to see the current state. |
| `list_work_orders` | Pure read; inherently idempotent. |

### 7.3 Security

- **Staff-only mutations.** All PATCH endpoints use `require_admin_or_root_csrf` (`policy.py:100`): non-admin callers receive HTTP 403 before any service function runs. GET endpoints use `require_ui_session`, making work-order reads available to any authenticated session user (tenants viewing their own property's work orders, for example).
- **CSRF enforcement.** Cookie-auth PATCH requests require `x-csrf-token` header matching the session's `csrf_token` and the `ui_csrf` cookie, enforced by `enforce_cookie_csrf` at `policy.py:71`. Bearer-auth requests skip CSRF.
- **Property isolation.** `_wo_pk(property_id)` bounds all reads and writes to a single property partition. A staff member can read any property's work orders (no owner check at the service level); ownership / tenancy scoping is a PROP-cluster concern.
- **Vendor ownership.** The `get_vendor` call in `assign_work_order` uses the WOV-004 service which enforces that the `vendor_id` exists in the platform vendor directory. Cross-user vendor injection is not possible because the FK resolves through a controlled service layer.
- **No PII.** Work-order rows contain `assignee_sub` (opaque Cognito sub, not email), title/description (arbitrary text — callers should avoid embedding PII), and timestamps. No email, phone, or address data is stored on the work-order row itself.
- **Audit trail.** Every mutation emits a best-effort `_audit(...)` call that writes to `T.alerts` via `alerts.audit_event` at `alerts.py:644`. These events are queryable by admins via the existing audit log infrastructure.

### 7.4 Money safety

**WOV-002 involves no money movement whatsoever.**

- `cost_cents` is a plain DDB integer attribute stored for reporting on the work-order row. It does not call `billing_shared.new_ledger_entry` (`billing_shared.py:224`), `apply_balance_delta` (`billing_shared.py:83`), `settle_or_reverse_ledger` (`billing_shared.py:262`), `compute_due` (`billing_shared.py:158`), or any billing router function.
- No payment provider (Stripe, PayPal, CCBill) is called.
- No wallet delta is applied.
- Escrowed paid maintenance (actual money held and released via `billing_shared` ledger primitives) is WOV-003's domain and depends on this ticket being complete first.

## 10. Open Questions / Assumptions

1. **`assigned → open` walk-back semantics.** The state machine allows `assigned → open` (vendor or assignee removed, WO returned to queue). When this transition fires, should `vendor_id` and `assignee_sub` be cleared? Assumption: yes — `transition_work_order` to `open` should also null out `vendor_id` and `assignee_sub` on the item. Pending confirmation.

2. **Unassigned WO queue ("who's available").** `GSI_WO_ASSIGNEE` is sparse — WOs with no `assignee_sub` do not appear in Mode C queries. If a "show me all unassigned open work orders" view is needed, it must use Mode B (`wo_status="open"`) with a client-side filter for `assignee_sub == None`. A sentinel `"UNASSIGNED"` value would enable a GSI query but would require a schema change and a migration of all existing rows. Assumption: Mode B with client-side unassigned filter is sufficient for WOV-005.

3. **`property_id` in PATCH body vs. path.** The `PATCH /ui/maintenance/work-orders/{work_order_id}` family carries `property_id` in the request body (same decision as FXA-013 for `asset_id`). An alternative is a GSI keyed on `work_order_id` alone, which would allow the handler to resolve the property partition without client-supplied data. Assumption: body field is simpler and avoids a new GSI; callers (WOV-005 frontend) always have `property_id` available.

4. **`cost_cents` on a non-completed transition.** The router raises 422 when `cost_cents` is non-null on a non-completed transition. Some workflows record an estimated cost before completion. Assumption: only actual completion cost is valid; estimates belong in a separate `estimated_cost_cents` field (future ticket).

5. **`list_work_orders` Mode A ordering.** Mode A queries the base table with `ScanIndexForward=False` on the sort key (`WO#{work_order_id}` — lexicographic UUID ordering, not timestamp ordering). For true chronological order the caller should sort the returned `items` by `created_at`. Assumption: WOV-005 sorts client-side; the API contract does not guarantee created-at ordering for Mode A.

6. **Concurrent assign vs. concurrent transition.** `assign_work_order` uses no `ConditionExpression` (last-write-wins). Two concurrent assigns overwriting each other are tolerated. If assign triggers a status advance (`open → assigned`) and is called concurrently from two sessions, one write will win. This is acceptable because both writes are advancing to the same `assigned` state. No correctness invariant is violated.
