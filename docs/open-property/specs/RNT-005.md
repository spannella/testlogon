# RNT-005 — Manual rent-run trigger + per-lease charge-now

**Ticket type:** Feature
**Priority:** P2
**Estimate:** 1 d
**Flag:** `RENT_LEDGER_ENABLED` (default OFF, shared across all RNT tickets)
**Depends on:** RNT-001 (`post_rent_charge`, idempotency marker, `run_rent_charges`,
`_current_period`), RNT-002 (`list_rent_ledger_for_lease`, `RentChargeOut`,
`RentChargeSkipOut`), RNT-003 (`list_rent_history`), LSE-001 (`get_lease`, `T.leases`,
lease item schema), LSE-002 (`list_leases(status="active")`, GSI2 per-owner query)

---

## 1. Summary & Goal

RNT-005 delivers the **on-demand counterparts** to the RNT-001 background rent-run timer,
giving landlords the ability to post rent charges without waiting for the automatic loop and
giving administrators the ability to trigger a system-wide backfill for any past period.

Three surfaces are added:

1. **`charge_lease_now`** — a single-lease on-demand charge. A landlord can click "Charge
   rent" on a specific active lease and get back either the newly created ledger row or the
   `already_charged` skip sentinel if the period was already billed (whether by the timer
   or a previous manual trigger).

2. **`run_rent_charges_for_owner`** — a landlord-scoped sweep that charges all of the
   caller's active leases for a given (or current) period. This is the per-owner variant of
   the system-wide `run_rent_charges` sweep from RNT-001 and uses the single-partition
   GSI2 query from LSE-002 rather than the cross-user GSI1 scan.

3. **`POST /ui/admin/rent/run`** — a root-only endpoint that invokes the full system-wide
   `run_rent_charges` from RNT-001. This is the manual trigger for the cross-user sweep,
   analogous to `POST /ui/remote/billing/tick`
   (`app/routers/compute_billing.py:156–187`) which sits alongside the automated
   compute-billing timer (`app/services/compute_billing.py:495` commentary).

All three paths delegate to the **same idempotent `post_rent_charge`** introduced in
RNT-001 (`app/services/rent_ledger.py`). The idempotency marker
(`T.rent_period_markers`, `pk=RENT_PERIOD#{user_sub}`, `sk=LEASE#{lease_id}#PERIOD#{period}`,
`attribute_not_exists(pk)` conditional-put) is shared by the timer and all manual paths:
a manual charge for a period the timer already billed is a silent no-op — never a duplicate
entry.

Open-property explicitly excludes online payment processing
(`docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` Headline and §B row 57). These
endpoints post `rent_charge` ledger rows through `new_ledger_entry`
(`app/services/billing_shared.py:224`) and never touch Stripe, PayPal, or CCBill.

With `RENT_LEDGER_ENABLED=0` (the default): all three endpoints return 404, both new service
functions short-circuit to `None`, and no existing surface changes by a single byte.

## 2. Context & Current State

### 2.1 The existing primitive that all three paths delegate to

`post_rent_charge(user_sub, lease, *, period=None) -> dict | None` is defined in
`app/services/rent_ledger.py` (RNT-001). Its contract:

- Returns the created `LEDGER#` item (a `rent_charge` row written via
  `new_ledger_entry`, `billing_shared.py:224`) on first call for a `(user_sub, lease_id,
  period)` triple.
- Returns `{"skipped": True, "reason": "already_charged", "period": period}` when the
  `T.rent_period_markers` conditional-put raises `ConditionalCheckFailedException`
  (meaning that triple was already charged — by the timer or a prior manual call).
- Returns `None` when `S.rent_ledger_enabled` is `False`.

Every new function in this ticket is a thin routing wrapper around `post_rent_charge`.
No new money math, no new ledger format, no new balance counter logic.

### 2.2 System-wide sweep already implemented in RNT-001

`run_rent_charges(*, period=None) -> int` (`app/services/rent_ledger.py`, RNT-001) performs
the cross-user active-lease sweep using GSI1 (`leases-all-index`) with the
`LastEvaluatedKey` loop cloned from `compute_billing.py:507–522`. The `POST /ui/admin/rent/run`
endpoint in this ticket is a one-line call to that function.

### 2.3 Per-owner lease query (the non-cross-user path)

LSE-002 exposes `list_leases(user_sub, *, status=None, ...)` which queries GSI2:
`Key("GSI2PK").eq(f"USER#{user_sub}#STATUS#active")`. This confines the sweep to a single
landlord's partition and never reads other landlords' data. RNT-005's
`run_rent_charges_for_owner` uses this surface rather than the cross-user GSI1 scan,
satisfying the ownership-isolation constraint (RNT cross-cutting constraint 8,
`docs/open-property/RENT_LEDGER_TICKETS.md`).

IMPORTANT: `list_leases` returns a `dict` — `{"leases": [...], "count": int,
"next_cursor": str|None}` (LSE-002 §4.1 step 7). The GSI2 status path makes a **single
`query()` call** with `Limit=limit` (default 50) and does NOT loop internally
(LSE-002 §4.1 step 4: "Returns directly from the single `query()` call"). For owners
with more than 50 active leases, `run_rent_charges_for_owner` will silently miss leases
beyond the first page. Implementors must extract `result["leases"]` (not iterate the
dict directly), and address the pagination gap (see Open Question §10 Q1).

### 2.4 The manual billing-tick analogue

`POST /ui/remote/billing/tick` in `app/routers/compute_billing.py:156–187` is the
canonical pattern for a manual trigger endpoint that sits alongside an automated timer.
It calls `record_billing_tick` (the same primitive the timer uses), wraps it with a
single `Depends(require_ui_session)`, and surfaces the result. RNT-005 mirrors this
structure exactly.

### 2.5 Root-only admin endpoint pattern

`app/auth/deps.py:308` defines `require_root_session(request) -> AuthenticatedUser`,
which raises HTTP 403 unless `user.role == Role.ROOT`. The audit-export admin endpoint
(`POST /ui/admin/audit-exports`) and the KYC partner admin endpoints use this dependency
for operations that touch all users' data. `POST /ui/admin/rent/run` follows the same
pattern because it performs a cross-user sweep over all landlords' leases.

### 2.6 What does not yet exist for this ticket

At the time RNT-005 is implemented, `app/services/rent_ledger.py` already contains
(from RNT-001 through RNT-004):

`T.rent_period_markers` with schema `pk=RENT_PERIOD#{user_sub}` / `sk=LEASE#{lease_id}#PERIOD#{period}`

adds no new marker logic — it delegates entirely to `post_rent_charge`, which owns the

## 4. API / Service Design

### 4.1 Service additions to `app/services/rent_ledger.py`

All service functions begin with the standard flag guard used throughout this cluster:
```python
if not S.rent_ledger_enabled:
    return None
```

---

**`charge_lease_now(user_sub: str, lease_id: str, *, period: str | None = None) -> dict | None`**

The per-lease on-demand charge primitive.

```python
def charge_lease_now(
    user_sub: str,
    lease_id: str,
    *,
    period: str | None = None,
) -> dict | None:
```

Steps:
1. Flag guard: `if not S.rent_ledger_enabled: return None`.
2. Fetch and validate ownership: `lease = get_lease(user_sub, lease_id)` (LSE-001).
   If `get_lease` returns `None` (not found or foreign partition) → raise
   `HTTPException(status_code=404, detail={"code": "lease_not_found"})`.
3. Check active status: `if lease["status"] != "active":` → raise
   `HTTPException(status_code=409, detail={"code": "lease_not_active",
   "message": "Lease must be active to charge rent"})`.
   `upcoming` and `ended` leases are rejected — only `active` leases may be charged.
4. Delegate entirely: `return post_rent_charge(user_sub, lease, period=period)`.
   The returned value is either the new ledger item dict or the skip sentinel
   `{"skipped": True, "reason": "already_charged", "period": period}`. No other logic.

No balance math, no ledger writes — all of that lives in `post_rent_charge` (RNT-001).

---

**`run_rent_charges_for_owner(user_sub: str, *, period: str | None = None) -> dict | None`**

The per-owner (single-partition) variant of `run_rent_charges`.

```python
def run_rent_charges_for_owner(
    user_sub: str,
    *,
    period: str | None = None,
) -> dict | None:
```

Steps:
1. Flag guard: `if not S.rent_ledger_enabled: return None`.
2. `period = period or _current_period()`.
3. Fetch owner's active leases via LSE-002's `list_leases`:
   ```python
   from app.services.leases import list_leases
   result = list_leases(user_sub, status="active")
   leases = result["leases"]   # list_leases returns {"leases": [...], "count": int, "next_cursor": str|None}
   ```
   `list_leases` queries GSI2 (`USER#{user_sub}#STATUS#active`) — a single-partition
   query that never reads another landlord's data (constraint 8). NOTE: the GSI2 status
   path returns a single `query()` call with `Limit=50` (LSE-002 §4.1 step 4); it does
   NOT loop to exhaustion. For owners with more than 50 active leases the caller must
   page via `next_cursor` (see Open Question §10 Q1).
4. Iterate leases, calling `post_rent_charge(user_sub, lease, period=period)` for each.
   Per-lease exceptions are caught and logged (same `except Exception: logger.exception`
   pattern used in `run_rent_charges` — RNT-001 §4.1; see also `compute_billing.py:460–464`
   in the RNT-001 clone target `_tick_all_running_resources` at `:616–650`):
   ```python
   charged = skipped = errors = 0
   for lease in leases:
       try:
           r = post_rent_charge(user_sub, lease, period=period)
           if r and not r.get("skipped"):
               charged += 1
           else:
               skipped += 1
       except Exception:
           logger.exception(
               "rent_run_owner_charge_failed user_sub=%s lease_id=%s period=%s",
               user_sub, lease.get("lease_id"), period,
           )
           errors += 1
   ```
5. Emit a single audit event summarizing the run:
   ```python
   audit_event(
       "rent.owner_run",
       user_sub,
       period=period,
       charged=charged,
       skipped=skipped,
       lease_count=len(leases),
   )
   ```
6. Return `{"period": period, "charged": charged, "skipped": skipped,
   "lease_count": len(leases)}`.

The system-wide `run_rent_charges` from RNT-001 is **not** called here. This function
is deliberately single-partition so that `POST /ui/rent/run` cannot be abused to charge
other landlords' leases.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotency — the shared marker guarantees no duplicates

Both the background timer path (`run_rent_run_loop` → `run_rent_charges` → `post_rent_charge`)
and all three manual paths in RNT-005 converge on `post_rent_charge`. The
`attribute_not_exists(pk)` conditional on `T.rent_period_markers` is a DynamoDB-level
atomic check (CLAUDE.md "Common gotchas — Cart recovery consume row"). Regardless of
which path writes the marker first, subsequent calls for the same `(user_sub, lease_id,
period)` triple return the skip sentinel and write nothing to `T.billing`.

Concrete scenarios:
- Timer ran at 00:01 UTC on June 1, charged all active leases for `2026-06`. A landlord
  then clicks "Charge rent" via `POST /ui/rent/leases/{id}/charge` at 09:15 UTC on June 1.
  `charge_lease_now` calls `post_rent_charge`, which fails the CAS and returns
  `{"skipped": True, "reason": "already_charged", "period": "2026-06"}`. HTTP 200, frontend
  shows a "already charged" toast rather than an error.
- A landlord calls `POST /ui/rent/run` twice in quick succession (e.g. double-click).
  The first call charges N leases; the second call returns `{charged: 0, skipped: N}`.

### 5.2 `upcoming` and `ended` leases — 409 not 400

`charge_lease_now` raises HTTP 409 (`lease_not_active`) rather than HTTP 400 for
status mismatches. The 409 communicates "the resource exists but its current state
prevents this operation" — semantically correct for a lifecycle violation. This is the
same HTTP status used throughout the platform for resource-state conflicts
(e.g. `app/services/tickets.py:913` `update_status` which raises `TicketStateError`
on invalid state-machine transitions, surfaced as 409 in the router; the
`ConditionalCheckFailedException`→409 pattern is at `tickets.py:788`).

The check is strict: only `status == "active"` passes. A `draft` lease (not yet
`upcoming`) is rejected; an `ended` lease is rejected; a `upcoming` lease (term hasn't
started yet) is rejected. This prevents accidentally billing a tenant before their tenancy
begins or after it concludes.

### 5.3 `run_rent_charges_for_owner` — no cross-user access

`list_leases(user_sub, status="active")` (LSE-002 GSI2 query) reads only items where
`GSI2PK = USER#{user_sub}#STATUS#active`. DynamoDB never returns items from other
landlords' partitions via this query. Even if the caller is an administrator, the
landlord-scoped run only charges the caller's own leases. The admin endpoint
(`POST /ui/admin/rent/run`) is the explicit opt-in for the cross-user sweep.

### 5.4 Period parameter validation

When `body.period` is provided, the handler validates the format before calling the
service:
```python
import re
_PERIOD_RE = re.compile(r"^\d{4}-\d{2}$")
if body.period and not _PERIOD_RE.match(body.period):
    raise HTTPException(400, detail={"code": "invalid_period_format",
                                     "message": "period must be YYYY-MM"})
```
Future periods (e.g. `"2027-01"`) are not blocked — a landlord can pre-post a charge
for an upcoming period if the lease is active. The idempotency marker prevents double
posting in any case.

Past periods are explicitly allowed for the backfill use-case: if the timer was not
running in a prior month, an admin can call `POST /ui/admin/rent/run` with a past
`period` to recognize the missed charges.

### 5.5 `monthly_rent_cents = 0` leases

`post_rent_charge` will write a zero-amount row (RNT-001 §5.3). `charge_lease_now`
does not add an additional guard for zero-cent leases — writing a zero-amount
recognition row is intentional (the contractual amount is zero). The idempotency
marker fires, preventing re-entry.

### 5.6 No partial success status code distinction

`run_rent_charges_for_owner` and the admin run always return HTTP 200 with the result
counts. A partial failure (some leases raise exceptions) is reflected in the count
fields (`charged`, `skipped`) and logged at ERROR level. The HTTP layer always returns
200 for the batch endpoints because partial success is the expected outcome for a sweep
that may encounter individually malformed lease items. Callers should inspect
`charged` + `skipped` + `lease_count` to detect anomalies.

### 5.7 `FilterExpression` / pagination — `list_leases` GSI2 path does NOT loop

CORRECTION: `list_leases(user_sub, status="active")` (LSE-002 §4.1) uses the GSI2
status path which makes a **single `query()` call** with `Limit=limit` (default 50).
It does **not** loop on `LastEvaluatedKey` — the loop is only on the all-leases base-table
path (no `status` arg). This is by design (GSI key-condition queries don't need the
FilterExpression-loop caveat) but it means the GSI2 path is capped at `limit` results
per call.

Consequence for `run_rent_charges_for_owner`: for an owner with > 50 active leases,
the first call returns only 50 leases and `next_cursor` is non-null. RNT-005 does not
re-implement the pagination loop — see Open Question §10 Q1 for how to resolve this.

The CLAUDE.md `FilterExpression` gotcha applies to the base-table all-leases path
(where non-LEASE# rows can fill pages before the filter) and to `_scan_active_leases`
(GSI1 + FilterExpression) at `compute_billing.py:507–522`, not to the GSI2 key-condition
query used here.

### 5.8 Concurrent calls

If two concurrent requests call `POST /ui/rent/leases/{id}/charge` for the same lease
and period, DynamoDB's atomic `put_item` with `attribute_not_exists(pk)` ensures exactly
one wins the marker write; the other receives the skip sentinel. There is no race
condition or double charge. This is identical to the concurrent-timer-wake analysis in
RNT-001 §5.4 (open question 4).

### 5.9 Large owner portfolios

A landlord with hundreds of active leases will have `run_rent_charges_for_owner` iterate
all of them in a single synchronous service call. For very large portfolios this could
be slow (blocking the event loop's thread-pool for the duration of the DDB writes).
In the MVP this is acceptable — most landlords have O(10)–O(100) leases. A future
improvement could make the sweep async-batched, but that is out of scope here.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no `dev_mode` branch

`charge_lease_now` and `run_rent_charges_for_owner` contain no `if S.dev_mode:` branch.
They delegate to `post_rent_charge` and `list_leases`, both of which are equally branchless
(RNT-001 §7, LSE-002 §7). All DDB operations resolve to DynamoDB Local in dev (via
`DDB_ENDPOINT_URL=http://localhost:8001` in `.env.local`) and real AWS DynamoDB in prod —
one boto3 code path, no divergence. There is no payment provider to mock because rent
charges are pure ledger entries.

### 7.2 Money-safety: `post_rent_charge` is the only write gate

`charge_lease_now` and `run_rent_charges_for_owner` contain zero direct DynamoDB writes.
Every ledger row, every idempotency marker, and every balance counter update is performed
inside `post_rent_charge` via `new_ledger_entry` (`billing_shared.py:224`),
`apply_balance_delta` (`billing_shared.py:83`), and the `T.rent_period_markers.put_item`
CAS. RNT-005 adds no new money paths.

The `_deduct_from_wallet` path in `compute_billing.py:141` is **not** used. Rent charges
recognize a ledger obligation for the landlord (`owed_settled_cents` counter); they are not
wallet deductions.

### 7.3 Money-safety: void is `settle_or_reverse_ledger`, never delete

RNT-005 adds no void path. Voids happen in RNT-003 via `settle_or_reverse_ledger`
(`billing_shared.py:262`). This constraint (`RENT_LEDGER_TICKETS.md` §constraint 3) is
enforced by the design of the overall cluster: `charge_lease_now` and
`run_rent_charges_for_owner` create rows; they have no delete or update path on
`LEDGER#` rows.

### 7.4 Ownership isolation — the critical invariant for the admin endpoint

`POST /ui/rent/run` (landlord sweep) is locked to `ctx["user_sub"]` — the
authenticated landlord can only charge their own leases. The service function
`run_rent_charges_for_owner` takes `user_sub` explicitly and passes it to
`list_leases(user_sub, ...)` (GSI2, single-partition).

`POST /ui/admin/rent/run` (system-wide sweep) requires `Role.ROOT` via
`require_root_session`. A non-root session (USER, ADMIN) gets HTTP 403 before
`run_rent_charges` is ever called. This prevents any landlord from accidentally
triggering charges against other landlords' leases.

A URL-manipulation attack where a landlord crafts `POST /ui/rent/leases/{foreign_lease_id}/charge`
is defeated by `get_lease(user_sub, lease_id)` (LSE-001), which queries
`T.leases.get_item(Key={"pk": f"USER#{user_sub}", "sk": f"LEASE#{lease_id}"})`. If the
lease belongs to another landlord, it is not in this partition and the query returns
`None` → HTTP 404 (leaking nothing).

### 7.5 Audit trail

Every call to `post_rent_charge` (via any path) emits `audit_event("rent.charge_posted", ...)`
(`app/services/alerts.py:644`). `run_rent_charges_for_owner` additionally emits
`audit_event("rent.owner_run", user_sub, period=..., charged=..., skipped=...,
lease_count=...)` after the sweep completes. The admin path (which calls `run_rent_charges`
from RNT-001) emits both the per-lease `rent.charge_posted` events and a
`rent.system_run` summary event added to `run_rent_charges` in RNT-001. All events are
written to `T.alerts` via the existing `audit_event` helper.

### 7.6 No online payment provider

`POST /ui/rent/leases/{lease_id}/charge` is not a payment endpoint. It writes a ledger
row recording that rent is owed. The "payment method" family of checks in
`app/services/payment_provider_health.py` (GAP-0206/0207) is never invoked. There is no
Stripe `PaymentIntent`, no PayPal charge, no CCBill transaction. The billing gates
(`_require_provider_enabled`, `_fraud_gate`) are never called here.

## 10. Open Questions / Assumptions

1. **`list_leases` single-page cap (CONFIRMED RISK).** LSE-002 §4.1 confirms that
   `list_leases(user_sub, status="active")` (GSI2 status path) makes a **single**
   `query()` call with `Limit=50` and does NOT loop internally. `run_rent_charges_for_owner`
   will silently miss leases beyond the first 50 for large landlords. Resolution options:
   (a) call `list_leases` in a cursor loop until `next_cursor` is null, accumulating all
   pages; (b) increase `limit` to a large value (e.g. 1000); (c) accept the 50-lease
   cap as an MVP constraint. Option (a) is recommended — the loop mirrors
   `_scan_active_leases` at `compute_billing.py:507–522`.

2. **Async vs sync.** `run_rent_charges_for_owner` and `charge_lease_now` are synchronous
   functions running in FastAPI's thread-pool executor (standard uvicorn pattern for sync
   route handlers). For a landlord with O(100) active leases the DDB write loop may take
   a few seconds. An async version with `asyncio.gather` over per-lease tasks would
   parallelize writes but adds complexity. Deferred to a follow-on performance ticket.

3. **Response on all-skipped `run_rent_charges_for_owner`.** When every lease in the
   portfolio was already charged, the endpoint returns HTTP 200 with `charged=0,
   skipped=N`. The frontend (RNT-006) should interpret this as a success case ("all up
   to date") rather than an error. The HTTP status code design assumes the caller can
   distinguish all-skipped from a real failure via the count fields.

4. **Future period posting policy.** Posting to a future `period` (e.g. pre-billing July
   rent in May) is not blocked. The idempotency marker is keyed on `period`, not on
   "current-or-past-only". Whether to gate future periods behind a policy flag is deferred.

5. **`run_rent_charges` summary audit event.** RNT-001's `run_rent_charges` does not
   currently emit a summary `audit_event` (it only has the per-lease `rent.charge_posted`
   events). RNT-005's admin endpoint (`POST /ui/admin/rent/run`) calls `run_rent_charges`
   directly and does not wrap it with an additional audit event. Adding a
   `rent.system_run` summary event to `run_rent_charges` in RNT-001 is a follow-on
   improvement that would make the admin sweep auditable at the batch level.

6. **`run_rent_charges` return type mismatch.** RNT-001 §4.1 specifies
   `run_rent_charges(*, period=None) -> int` returning only `charged` count. The admin
   endpoint here declares `response_model=RentRunResultOut` which requires `charged`,
   `skipped`, and `lease_count`. This is irreconcilable with the current RNT-001 signature.
   Resolution: extend `run_rent_charges` to return
   `{"charged": int, "skipped": int, "lease_count": int}` — backward-compatible since
   the timer loop (`run_rent_run_loop`) ignores the return value. Until then the admin
   endpoint must drop `skipped`/`lease_count` from its response or use a narrower
   `{"period": str, "charged": int}` model.

7. **`charge_lease_now` for `draft` leases.** The current design rejects `draft` leases
   with a 409. An alternative is to reject only `ended` leases and allow `upcoming` and
   `draft` — e.g. to pre-post a deposit or advance rent. The stricter `status=="active"`
   only requirement follows the RENT_LEDGER_TICKETS.md source ticket text which says
   "requires `lease['status'] == 'active'` (else 409 `lease_not_active`)". If pre-posting
   for non-active leases is a real use-case it should be a separate endpoint.
