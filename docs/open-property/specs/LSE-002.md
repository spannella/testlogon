# LSE-002 — Lease list, status filter, and inline editing

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 2 d
**Flag:** `LEASES_ENABLED` (default OFF, shared with LSE-001)
**Depends on:** LSE-001 (lease entity, `T.leases`, `_LEASE_TRANSITIONS`, `S.leases_enabled`)

---

## 1. Summary & Goal

LSE-002 adds the list, filter, and inline-edit surface for the Lease entity introduced by
LSE-001. The gap analysis (§B row 56) names this surface explicitly: *"Lease table + status
filter + inline edit … mirror QUO-004 list pattern"*. The ticket delivers:

1. **`list_leases`** — paginated, optionally status-filtered owner list via GSI2 (status path)
   or the base-table partition (all-leases path), returning HMAC-signed cursors.
2. **`update_lease`** — partial update of the mutable economic fields (rent, deposit, due-day,
   late-fee structure, end-date, notes); immutable identity fields (tenant, property, unit,
   start-date, status) are rejected at the API layer.
3. **`admin_list_leases`** — cross-owner admin view via GSI1, guarded by
   `require_admin_or_root`.
4. **Six HTTP endpoints** in `app/routers/leases.py` completing the CRUD + transition
   surface started by LSE-001 (`POST`, `GET` list, `GET` single, `PATCH`, `POST .../status`,
   `GET /admin`).
5. **Four Pydantic models** in `app/models.py` (`LeaseCreateIn`, `LeasePatchIn`, `LeaseOut`,
   `LeaseListOut`) following the QUO-004 §4.4 shape.

Money movement is out of scope. The `monthly_rent_cents` and `security_deposit_cents` fields
are informational integers; ledger rows are posted exclusively by the downstream RNT
rent-run cluster via `billing_shared.new_ledger_entry` (`app/services/billing_shared.py:224`).
LSE-002 never touches the billing table.

### QUO-004 precedent

QUO-004 (`docs/suitecrm/specs/QUO-004.md`) is the authoritative scaffold. LSE-002
mirrors its `list_contracts` / `update_contract` / `admin_list_contracts` function
signatures and router endpoint shape verbatim, substituting the lease-domain field names.
The list's `status` query param maps to the lease `_LEASE_TRANSITIONS` vocabulary (`draft`,
`upcoming`, `active`, `ended`) rather than the contract `stage` vocabulary.

### FilterExpression does not reduce page size (CLAUDE.md gotcha)

Any query that uses a `FilterExpression` post-filter (e.g. the all-leases base-table path
that `begins_with(SK, "LEASE#")`) must loop on `LastEvaluatedKey` to guarantee complete
pages. `list_leases` applies `FilterExpression` only on the base-table path; the GSI2 path
is a proper key-condition and does not need the loop caveat.

## 4. API / Service Design

### 4.1 Service additions — `app/services/leases.py`

All three new functions follow the LSE-001 preamble convention: short-circuit on
`if not S.leases_enabled: return None`.

#### `list_leases(user_sub, *, status=None, limit=50, cursor=None) -> dict`

Mirror of `list_contracts` in QUO-004 §4.1.

```python
def list_leases(
    user_sub: str,
    *,
    status: str | None = None,
    limit: int = 50,
    cursor: str | None = None,
) -> dict:
```

**Algorithm:**

1. Short-circuit: `if not S.leases_enabled: return None`.
2. Clamp: `limit = min(limit, 200)`.
3. Decode cursor: `esk = decode_cursor(cursor)` (`app/core/cursor.py:103`).
4. **Status path** (when `status` is not `None`):
   - `KeyConditionExpression = Key("GSI2PK").eq(f"USER#{user_sub}#STATUS#{status}")`
   - `IndexName = "leases-by-status-index"`, `ScanIndexForward=False`, `Limit=limit`
   - `ExclusiveStartKey=esk` when non-None.
   - Returns directly from the single `query()` call; no `FilterExpression` loop needed
     (the GSI key condition is exact).
5. **All-leases path** (when `status` is `None`):
   - `KeyConditionExpression = Key("pk").eq(f"USER#{user_sub}")`
   - `FilterExpression = Attr("sk").begins_with("LEASE#")`
   - `ScanIndexForward=False`, `Limit=limit`, `ExclusiveStartKey=esk` when non-None.
   - **Must loop on `LastEvaluatedKey`** until `limit` items collected or exhausted, per
     CLAUDE.md FilterExpression gotcha (filter applied after page fetch; page may contain
     non-LEASE# rows like the COUNTER row if it ever shares the same partition).
6. Encode cursor: `next_cursor = encode_cursor(response.get("LastEvaluatedKey"))` 
   (`app/core/cursor.py:94`).
7. Return `{"leases": [_serialize(item) for item in items], "count": len(items), "next_cursor": next_cursor}`.

`_serialize` strips internal GSI key attributes (`GSI1PK`, `GSI1SK`, `GSI2PK`, `GSI2SK`)
and coerces DynamoDB `Decimal` values to `int` for JSON serialization (mirroring the
`_clean_lek` helper pattern visible in `app/services/invoices.py:65–79`; the Decimal→int
coercion logic is at lines 72–79 of that function — the helper is named `_clean_lek`,
not `_coerce_decimals`).

#### `update_lease(user_sub, lease_id, *, <mutable-fields>) -> dict | None`

Mirror of `update_contract` in QUO-004 §4.1.

```python
def update_lease(
    user_sub: str,
    lease_id: str,
    *,
    end_date: int | None = None,
    monthly_rent_cents: int | None = None,
    security_deposit_cents: int | None = None,
    rent_due_day: int | None = None,
    late_fee_type: str | None = None,
    late_fee_cents: int | None = None,
    late_fee_percent_bps: int | None = None,
    late_fee_grace_days: int | None = None,
    currency: str | None = None,
    notes: str | None = None,
    renewal_notice_days: int | None = None,
) -> dict | None:
```

**Algorithm:**

1. Short-circuit: `if not S.leases_enabled: return None`.
2. Fetch: `existing = get_lease(user_sub, lease_id)` → `None` bubbles to router as 404.
3. Build `UpdateExpression` covering only the non-`None` kwargs plus
   `updated_at = now_ts()`. Use `ExpressionAttributeNames` for reserved words (e.g.
   `#notes` for `notes`).
4. If `end_date` is provided and differs from `existing["end_date"]`: rewrite `GSI2SK`
   in the same `UpdateExpression` (`SET GSI2SK = :end_date`). If `end_date` is provided
   as `None` (open-ended patch): remove `GSI2SK` via `REMOVE GSI2SK` clause.
5. Execute `T.leases.update_item(Key={"pk": f"USER#{user_sub}", "sk": f"LEASE#{lease_id}"}, ...)`.
6. `audit_event("lease.updated", user_sub, lease_id=lease_id, fields_changed=[...])`.
7. Return updated item via `get_lease(user_sub, lease_id)`.

`start_date`, `tenant_id`, `property_id`, `unit_id`, and `status` are **not parameters**
of `update_lease`. The router rejects patches containing those keys before calling the
service (§4.3 below).

Mirror of `admin_list_contracts` in QUO-004 §4.1.

```python
def admin_list_leases(
```

3. Decode cursor.
4. Query `GSI1`: `Key("GSI1PK").eq("LEASES#ALL")`, `ScanIndexForward=False`, `Limit=limit`,

5. Encode cursor; return `{"leases": [...], "count": int, "next_cursor": str | None}`.

## 5. Detailed Behavior & Edge Cases

### Status filter — GSI2 design implications

`list_leases(status="active")` queries `GSI2PK = "USER#{user_sub}#STATUS#active"`.
`GSI2SK = end_date` is a **sparse** attribute: open-ended leases (no `end_date`) omit the
attribute entirely and therefore do not appear in this index. This is correct behavior:
`list_leases(status="active")` still returns open-ended active leases because the status
path uses only `GSI2PK` as the key condition; `GSI2SK` is the sort key and its absence
only removes the item from range-key queries (e.g. `between`). DynamoDB returns all items
for a given hash key regardless of whether the sort key is present.

Concretely: an active lease with `end_date=None` has `GSI2PK="USER#{sub}#STATUS#active"`
but no `GSI2SK`. It projects into the index (hash-only match) and is returned by
`list_leases(status="active")`. It is correctly excluded from the upcoming-expiration query
(LSE-003) which adds a `GSI2SK.between(...)` range condition.

### `update_lease` — `end_date` transitions

Three distinct cases for the `end_date` patch argument:

1. **Not provided** (`end_date` absent from PATCH body / `LeasePatchIn.end_date` is
   defaulted `None` and the caller did not set it): `end_date` is not in the
   `UpdateExpression`; `GSI2SK` is untouched. The service distinguishes "caller explicitly
   passed `None`" from "caller omitted the field" by inspecting which keys are set in
   `LeasePatchIn.model_dump(exclude_unset=True)`.

2. **Set to a new integer** (e.g. extending a month-to-month lease): `GSI2SK` is added or
   updated to the new value via `SET GSI2SK = :end_date`.

3. **Set to `None` (explicit open-ended conversion)**: `GSI2SK` is removed via
   `REMOVE GSI2SK` so the item becomes sparse in the index and will never appear in
   date-range expiration queries.

`model_dump(exclude_unset=True)` is the mechanism that distinguishes cases 1 and 3.

### Concurrent PATCH safety

`update_lease` does not use a conditional `update_item` guard (unlike `transition_status`,
which does). Last-writer-wins is acceptable for economic-field edits (rent amount, notes)
because these are not state-machine transitions and the risk of data loss from concurrent
PATCH is low in a single-landlord context. If optimistic concurrency is added later (e.g.
an `If-Match: ETag` header), the implementation uses `ConditionExpression="updated_at = :prev_ts"` — never a delete/re-create.

### `admin_list_leases` — no `user_sub` filter

`admin_list_leases` returns all leases across all owners (GSI1 full scan). The admin
view intentionally shows every lease to support cross-portfolio root/admin oversight.
This endpoint is guarded by `require_admin_or_root` (`app/auth/policy.py:67`), which
enforces `role in {Role.ADMIN, Role.ROOT}`. A session with `role=USER` receives HTTP 403.

### Empty PATCH body

A PATCH with a body that has no recognized mutable fields (i.e. all fields are `None`
in `model_dump(exclude_unset=True)`) is a valid no-op that returns the unchanged lease.
The service skips the `update_item` call and returns `get_lease(user_sub, lease_id)` to
avoid a spurious DDB write. `updated_at` is not advanced for a no-op patch.

### Pagination cursor integrity

`encode_cursor` at `app/core/cursor.py:94` wraps `LastEvaluatedKey` in a versioned
envelope (`{"v": "v2", "k": last_evaluated_key}`) and signs it with an HMAC keyed on
`CURSOR_SIGNING_SECRET`. `decode_cursor` at `:103` verifies the signature before
returning the key. A tampered or expired cursor is silently discarded (returns `None`),
causing the list endpoint to return the first page — no error is surfaced to the caller.
DynamoDB `Decimal` values in a `LastEvaluatedKey` (e.g. `GSI1SK = created_at`) are
handled by `_json_default` at `cursor.py:12`, which coerces integral `Decimal` to `int`.

### `late_fee_type` cross-validation

`late_fee_type="flat"` requires `late_fee_cents > 0`; `late_fee_type="percent"` requires
`late_fee_percent_bps > 0`. These cross-field invariants are validated in `create_lease`
(LSE-001). `update_lease` re-validates after merging the patch with the existing item:
the merged `late_fee_type` is checked against the merged `late_fee_cents` /
`late_fee_percent_bps`. A PATCH that sets `late_fee_type="flat"` but leaves
`late_fee_cents=0` returns HTTP 400 `invalid_late_fee_config`.

### Immutable fields in PATCH — double defense

`LeasePatchIn(extra="forbid")` rejects unknown keys at the Pydantic layer (HTTP 422).
The router additionally raises HTTP 400 `immutable_field` if it detects keys that should
never reach `update_lease` (defensive check for clients that bypass Pydantic). The two
layers ensure no codepath silently ignores an attempt to mutate `tenant_id`, `start_date`,
or `status` via PATCH.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 — no `dev_mode` branch

There is no `if S.dev_mode` branch anywhere in `app/services/leases.py` or
`app/routers/leases.py`. DynamoDB calls use `T.leases`, which in dev resolves to
DynamoDB Local via moto (`ddb_endpoint_url = http://localhost:8001`; same boto3 path as
prod). `send_alert_email` (called by LSE-003, not LSE-002) handles the dev/prod divergence
internally at `app/services/alerts.py:459` (dev writes to a log file; prod calls SES).
LSE-002 code sees only one function signature in both environments.

### Money-safety invariants

LSE-002 **never writes to the `billing` table**. The `monthly_rent_cents` and
`security_deposit_cents` fields stored on the lease item are **informational integer
cents** used by downstream RNT code to compute charges; they carry no immediate ledger
effect. The `billing_shared` primitives are the exclusive write path for money:

- Rent charges: RNT rent-run calls `billing_shared.new_ledger_entry` (`billing_shared.py:224`) per active lease.
- Voids/reversals: any future void of a rent charge must call `billing_shared.settle_or_reverse_ledger` (`billing_shared.py:262`) — never a DELETE of the ledger row.
- Balance queries: `billing_shared.compute_due` (`billing_shared.py:158`) is the sole source of truth for outstanding amounts; LSE-002 never reimplements the due-calculation logic.
- No online payment provider is involved. Rent is manually recorded via the RNT cluster; LSE-002 exposes no payment initiation endpoint.

### Ownership isolation

All reads and writes are keyed under `USER#{user_sub}`. A `get_lease(user_sub, lease_id)`
call for a lease owned by a different landlord returns `None` (the `get_item` key simply
does not exist in that partition), which the router maps to HTTP 404. No information is
leaked about the existence of leases belonging to other users. `admin_list_leases` bypasses
this isolation intentionally and is gated by `require_admin_or_root`.

### CSRF

Cookie-auth non-GET requests (`POST`, `PATCH`) require the `x-csrf-token` header matching
both the session's stored `csrf_token` and the `ui_csrf` cookie. `require_ui_session`
enforces this automatically. Bearer-token clients skip CSRF (CLAUDE.md auth section).

### Idempotency

`update_lease` is last-writer-wins with no idempotency token. `list_leases` and
`admin_list_leases` are read-only and naturally idempotent. `transition_status` (LSE-001,
called via `POST .../status`) uses a conditional `update_item` with
`ConditionExpression="#s = :old_status"` (mapping `#s` → `"status"` via
`ExpressionAttributeNames`, since `status` is a DynamoDB reserved word) to prevent
double-transitions; the loser receives HTTP 409 `concurrent_update`.

## 10. Open Questions / Assumptions

1. **`status="upcoming"` in GSI2 filter** — The `upcoming` status is written to `GSI2PK` by
   `create_lease` and `transition_status` (LSE-001). An `upcoming` lease may have a future
   `end_date` and therefore a `GSI2SK` value, or it may be open-ended (no `GSI2SK`). The
   `list_leases(status="upcoming")` query returns all items with the matching hash key
   regardless. This is the intended behavior.

2. **Scoped-admin visibility** — The current design gives any `ADMIN`-role user access to
   all leases via `GET /ui/admin/leases`. If the platform adds scoped admin profiles
   (e.g. an admin who manages only a subset of landlords), a future ticket must add a
   `FilterExpression=Attr("user_sub").eq(scoped_sub)` post-filter. This is out of scope
   for LSE-002; the `require_admin_or_root` guard is sufficient.

3. **`currency` enum validation** — `LeasePatchIn.currency` accepts any string. A stricter
   validator checking ISO 4217 codes (e.g. via a `Literal` type or `pydantic.AnyStr` with
   a regex) is a follow-up. The existing billing primitives do not enforce ISO 4217 either.

4. **`renewal_notice_days` mutation and already-sent notifications** — If a landlord patches
   `renewal_notice_days` to a shorter window on a lease that has already had its
   `renewal_notified_at` set, no second notification is sent (the `renewal_notified_at`
   idempotency marker in LSE-001/LSE-003 prevents it). Clearing `renewal_notified_at` to
   re-arm the notification is an admin-only DDB console operation; no API is provided for
   this in LSE-002.

5. **Audit event granularity for PATCH** — `audit_event("lease.updated", ...)` currently
   logs only `fields_changed: [list-of-field-names]`. A richer diff (old→new value pairs)
   is a follow-up enhancement; adding it does not require a schema change because
   `audit_event` accepts arbitrary `**fields`.

6. **Ordering of the all-leases base-table path** — `ScanIndexForward=False` on a base-table
   query sorts by SK (i.e. `LEASE#{lease_id}` lexicographic descending). Since `lease_id`
   is `"lse_" + uuid4().hex[:16]`, this is creation-time-ish but not strictly
   chronological. If strict newest-first ordering is required, a GSI3 (`GSI3PK = USER#{sub}`,
   `GSI3SK = created_at (N)`) can be added without a table rebuild. Deferred pending
   product requirement.
