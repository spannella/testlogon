# PMD-004 — Frontend — portfolio dashboard page

**Ticket type:** Feature
**Priority:** P2
**Estimate:** 2 d
**Flag:** `PROPERTY_DASHBOARD_ENABLED` (default OFF; introduced by PMD-001, shared master flag for the entire PMD cluster)
**Hard dependencies:** PMD-001 (rent-policy endpoints), PMD-003 (KPI/snapshot/priority endpoints + dashlet provider)
**Soft dependency:** RPT-006/007 (dashlet grid; the `/portfolio` page works standalone without it)

---

## 1. Summary & Goal

PMD-004 delivers the **React frontend** for the property portfolio dashboard. It consumes
the three PMD-003 read endpoints (`/ui/portfolio/kpis`, `/ui/portfolio/rent-snapshot`,
`/ui/portfolio/priority-items`) and the two PMD-001 policy endpoints
(`GET /ui/rent-policy`, `PUT /ui/rent-policy`), composing them into a single-page
landlord dashboard at the new route `/portfolio`.

The page surfaces:
- **Four headline KPI cards** — occupancy rate, active lease count, outstanding rent,
  open work orders — refreshed from `GET /ui/portfolio/kpis`.
- **Monthly rent snapshot card** — collected / outstanding / overdue / charged totals
  for a user-navigable year/month, rendered with recharts (same library already used by
  `frontend/src/pages/earnings/EarningsPage.tsx`).
- **Priority-items panel** — upcoming lease expirations and open work orders from
  `GET /ui/portfolio/priority-items`, with deep links to the lease and ticket pages.
- **Rent-policy dialog** — admin/root-only; edits `rent_due_day`, `late_fee_cents`,
  `grace_period_days`, `currency` via React Hook Form + Zod and `PUT /ui/rent-policy`.
- **`PortfolioSummaryDashlet` tile component** — renders the `portfolio_summary` dashlet
  payload inside the RPT-006/007 configurable dashboard grid.

When `PROPERTY_DASHBOARD_ENABLED` is off, the backend returns 404 on every `/ui/portfolio/*`
and `/ui/rent-policy` call. The frontend handles this gracefully: the `/portfolio` page
renders an empty/disabled state, the sidebar nav entry is suppressed, and no console
crash occurs.

## 3. Data Model

PMD-004 is a **pure frontend ticket**. It does not create any new DynamoDB tables, GSIs,
or backend service code. All DynamoDB contracts belong to PMD-001 and PMD-003; this
section records the response shapes that the frontend TypeScript types must mirror.

### 3.1 `PortfolioKpis` (mirrors `PortfolioKpisOut` from PMD-003)

```ts
// frontend/src/api/types.ts — additive
export interface PortfolioKpis {
  occupancy_rate: number;       // 0.0–1.0; 0.0 when no units
  unit_count: number;
  occupied_units: number;
  active_lease_count: number;
  outstanding_rent_cents: number;
  open_work_order_count: number;
  computed_at: number;          // Unix seconds; present on backend PortfolioKpisOut
}
```

### 3.2 `RentSnapshot` (mirrors `RentSnapshotOut` from PMD-003)

```ts
export interface RentSnapshot {
  year: number;
  month: number;
  charged_cents: number;
  collected_cents: number;
  outstanding_cents: number;
  overdue_cents: number;
  rent_due_day: number;         // from RentSnapshotOut (PMD-003 §4.3)
  grace_period_days: number;    // from RentSnapshotOut
  computed_at: number;          // Unix seconds
}
```

The invariant `collected_cents + outstanding_cents == charged_cents` and
`overdue_cents <= outstanding_cents` is enforced by the backend (PMD-003 §5); the
frontend renders the values as-is without re-computing.

### 3.3 `PriorityItems` (mirrors `PriorityItemsOut` from PMD-003)

The backend `PriorityItemOut` is a **flat polymorphic shape** with a `kind` discriminator
(`"lease_expiring" | "open_work_order" | "open_ticket"`). Lease fields use `end_date`
(Unix seconds) rather than `expiry_ts`, carry no precomputed `days_remaining` or
`unit_label`/`tenant_name`, and the work-order shape has no `property_label`/`created_at`.
The TypeScript types must mirror the actual backend response — PMD-003 §4.3:

```ts
// Single polymorphic item shape (backend PriorityItemOut)
export interface PriorityItemOut {
  kind: string;                 // "lease_expiring" | "open_work_order" | "open_ticket"
  // Lease-expiring fields (optional)
  lease_id?: string;
  lease_number?: string;
  unit_id?: string;
  property_id?: string;
  tenant_id?: string;
  end_date?: number;            // Unix seconds; NOTE: field is end_date, not expiry_ts
  monthly_rent_cents?: number;
  // Work-order / ticket fields (optional)
  work_order_id?: string;
  ticket_id?: string;
  subject?: string;
  title?: string;
  status?: string;
  priority?: string;
  updated_at?: number;
}

export interface PriorityItems {
  upcoming_expirations: PriorityItemOut[];
  open_work_orders: PriorityItemOut[];
  items: PriorityItemOut[];     // combined list from backend
  count: number;
}
```

The frontend computes `days_remaining` locally as
`Math.floor(((item.end_date ?? 0) - Date.now() / 1000) / 86400)` for the "Expiring soon"
badge threshold. The deep link for lease expirations uses `item.lease_id`; for work
orders it uses `item.ticket_id ?? item.work_order_id`.

## 4. API / Service Design

### 4.1 `frontend/src/api/endpoints/portfolio.ts` — new file

```ts
import { api } from "@/api/client";
import type {
  PortfolioKpis,
  RentSnapshot,
  PriorityItems,
  RentPolicy,
  RentPolicyUpdateIn,
} from "@/api/types";

// ─── Portfolio KPI / snapshot / priority (PMD-003) ───────────────

export const getPortfolioKpis = () =>
  api.get<PortfolioKpis>("/ui/portfolio/kpis");

export const getRentSnapshot = (year: number, month: number) =>
  api.get<RentSnapshot>("/ui/portfolio/rent-snapshot", {
    year: String(year),
    month: String(month),

export const getPriorityItems = (limit = 20) =>
  api.get<PriorityItems>("/ui/portfolio/priority-items", {
    limit: String(limit),

// ─── Rent policy (PMD-001) ────────────────────────────────────────

export const getRentPolicy = () =>
  api.get<RentPolicy>("/ui/rent-policy");

export const putRentPolicy = (body: RentPolicyUpdateIn) =>
  api.put<RentPolicy>("/ui/rent-policy", body);
```

`api.get` and `api.put` are the typed convenience wrappers already defined in

## 5. Detailed Behavior & Edge Cases

### 5.1 KPI cards

- On load, all four cards show a `Loader2` spinner (identical to `QuickStatCard` in
  `EarningsPage.tsx:125`) until `kpisQ.isLoading` is false.
- Zero state: an owner with no properties → `occupancy_rate = 0`, all numeric KPIs `0`.
  Cards render `0%`, `0`, `$0.00`, `0` without any error or empty-state overlay.
- Error state: if `kpisQ.isError` (backend 404 when flag is off, or network failure), each
  card renders a muted `—` placeholder. A single `<Alert>` banner beneath the cards reads
  "Portfolio dashboard is unavailable." No toast — the page handles it inline.

### 5.2 Period navigation on the rent snapshot card

- Default period: the current calendar month (`new Date()` → `year`/`month`).
- "Prev" arrow decrements month (wrapping December → previous year's December).
- "Next" arrow increments month, **disabled** when the displayed period equals the current
  month (prevent fetching future data).
- Each navigation updates the React state `[year, month]` which changes the React Query
  key `["portfolio", "rent-snapshot", year, month]`, triggering a fresh fetch. The card
  shows a spinner overlay while the new period loads (do not clear the previous data —
  use `placeholderData: keepPreviousData` from React Query so the previous numbers stay
  visible during transition).
- The bar chart renders four bars side-by-side: `charged` (gray), `collected` (green),
  `outstanding` (amber), `overdue` (red). Uses `recharts` `BarChart`/`Bar` with
  `ResponsiveContainer` at height 200. Tooltip formatter: `$${(v/100).toFixed(2)}`.
- Zero state: if all four values are `0`, display a muted "No rent activity this period"
  message inside the chart area (same pattern as `RevenueChart`'s empty-check in
  `EarningsPage.tsx:170-176`).

### 5.3 Priority items panel

- Upcoming expirations are sorted ascending by `end_date` (soonest first). Rows
  where `Math.floor(((item.end_date ?? 0) - Date.now() / 1000) / 86400) < 30`
  display a red `<Badge>` with "Expiring soon".
- Open work orders are sorted by `updated_at` descending (most recently updated first);
  backend provides `updated_at`, not `created_at` on the polymorphic item shape.
- The deep link for lease expirations navigates to `/leases/${lease_id}` — a route
  provided by the LSE frontend (LEASES_TICKETS §LSE-FE). If that route does not yet
  exist (LSE FE not merged), the link still renders but navigates to a 404; this is
  acceptable because PMD-004 has no hard dependency on the LSE FE ticket.
- The deep link for work orders navigates to `/tickets/${ticket_id ?? work_order_id}`
  (the existing `TicketsPage` route at `App.tsx:382`; the lazy import is at line 77).
- When `items.upcoming_expirations` is empty and `items.open_work_orders` is empty, the
  panel shows "No priority items — great job!" with a check-circle icon.

### 5.4 Rent-policy dialog (admin/root only)

- Visibility: the "Edit Policy" button is rendered only when
  `getRoleFromAccessToken(accessToken)` returns `"admin"` or `"root"`. A regular user
  (`"user"` role) never sees the button; the page layout otherwise remains identical.
- The dialog is seeded with the currently fetched `RentPolicy` values. When the policy
  `is_default` is true, a yellow informational banner reads "No custom policy saved —
  showing platform defaults."
- **Zod schema** for the form:
  ```ts
  const policySchema = z.object({
    rent_due_day: z.number().int().min(1).max(28),
    late_fee_cents: z.number().int().min(0),
    grace_period_days: z.number().int().min(0),
    currency: z.string().regex(/^[a-z]{3}$/, "Must be a 3-letter ISO currency code"),
  });
  ```
- `useForm` is initialised with `defaultValues` derived from the `RentPolicy` query data.
  When the query has not yet resolved, the dialog defaults to `{ rent_due_day: 1,
  late_fee_cents: 0, grace_period_days: 0, currency: "usd" }`.
- On successful `PUT`, `queryClient.invalidateQueries(["portfolio", "rent-policy"])` and
  `queryClient.invalidateQueries(["portfolio", "kpis"])` are called, then the dialog is
  closed. A success toast reads "Rent policy updated."
- On 422 from the backend (validation error), the form displays field-level error messages
  using the shadcn `FormMessage` component. The toast is suppressed for 422s (the
  `silent403` pattern from `client.ts:153`).
- The `PUT` is sent via `api.put` which sets the CSRF header automatically
  (`client.ts:179-182`). No manual CSRF header wiring required.

### 5.5 `PortfolioSummaryDashlet` tile

- Receives `data: PortfolioKpis` and `isLoading: boolean` as props.
- Renders four metric rows: occupancy %, active leases, outstanding rent $, open WOs.
- When `isLoading`, shows a `Loader2` spinner occupying the tile area.
- An "Open Dashboard" link navigates to `/portfolio`.
- The component is gated by the parent `DashboardPage` (RPT-007): if
  `dashlet_type === "portfolio_summary"` but `S.property_dashboard_enabled` is off,
  the `_provider_portfolio_summary` provider raises `ValueError("unknown_dashlet_type")`,
  which the RPT-007 router (§4.2) converts to **HTTP 422** with body
  `{"detail": "unknown_dashlet_type"}` — NOT a `provider_error` 400. The tile should
  handle status 422 with `detail === "unknown_dashlet_type"` and render "This dashlet is
  temporarily unavailable" (the error tile behavior described in RPT-007 §4.2 and §5.9).

### 5.6 Flag-off degradation

When `PROPERTY_DASHBOARD_ENABLED=false`:
- All five API calls return HTTP 404.
- The `PortfolioDashboardPage` detects `kpisQ.error?.status === 404` and renders the
  "Portfolio dashboard is unavailable" state — no console error, no React error boundary
  needed.
- The sidebar nav entry for `/portfolio` is hidden. The nav visibility check reads
  `kpisQ.isError && kpisQ.error?.status === 404` after the first query attempt, storing
  the result in React state. The nav hides on the first successful 404 detection.
- The `PortfolioSummaryDashlet` handles the standard RPT-007 `provider_error` shape and
  renders the standard unavailable message.

### 5.7 Sidebar navigation entry

A nav item "Portfolio" with a `Building2` icon (from `lucide-react`, already a dependency)
is added to the AppShell sidebar. It is visible to all authenticated users but suppressed
at runtime when the backend 404s on the first KPI fetch. This matches the pattern used for
feature-flagged pages elsewhere (the nav never hard-codes flag state from env vars; it
reacts to the API response).

### 6.1 Master flag

`PROPERTY_DASHBOARD_ENABLED` — introduced by PMD-001 in `app/core/settings.py` (after

property_dashboard_enabled: bool = (

Default: `false`. PMD-004 reads this flag only through API 404 responses — the frontend

PMD-004 does **not** use a `VITE_*` compile-time environment variable for the
`PROPERTY_DASHBOARD_ENABLED` flag. Feature detection is purely runtime: the React Query
error state of `getPortfolioKpis` signals whether the vertical is active. This avoids the
need to rebuild the frontend when the flag changes.

### 6.3 No new env vars or feature flags in the frontend

`frontend/.env.local` and `frontend/.env.local.example` are not modified. All flag
behavior is expressed through backend 404 responses and React Query error handling.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — identical code path dev and prod

PMD-004 is a pure frontend change. All business logic lives in PMD-001 and PMD-003
backend services, which follow SECOPS-007 (no `if S.dev_mode` branches). The
frontend `api` helper is the same in dev and prod; Vite proxies `/ui/*` and `/api/*`
to `http://localhost:8000` in dev (CLAUDE.md §"Dev stack") and the production Nginx/CDN
does the same mapping in prod. No `if import.meta.env.DEV` branches in PMD-004.

### 7.2 CSRF on PUT

`PUT /ui/rent-policy` is a cookie-auth non-GET request; the backend's `require_admin_or_root_csrf`
dependency validates the `x-csrf-token` header against both the session's stored
`csrf_token` and the `ui_csrf` cookie value (CLAUDE.md §"CSRF"). The `api` client
attaches the CSRF token automatically at `client.ts:179-182`. No manual wiring; no risk
of omission.

### 7.3 Money-safety — read-only dashboard

PMD-004 does not write any monetary data. The rent-policy dialog mutates `rent_due_day`,
`late_fee_cents`, and `grace_period_days` — policy configuration only, not ledger entries.
All ledger writes (rent charges, payments, voids) live in the PMD-001/003 backend services
and downstream RNT cluster, which use `new_ledger_entry` and `settle_or_reverse_ledger`
exclusively. PMD-004 has no code path that touches the billing ledger.

### 7.4 Idempotency of the rent-policy PUT

Submitting the dialog twice with identical values produces two AUDIT rows on the backend
(PMD-001 §AC) but is otherwise idempotent: the second PUT overwrites the CURRENT row with
the same values. The frontend does not attempt de-duplication; it simply fires the
mutation on each submit. This is correct behavior per PMD-001's audit-is-append-only
contract.

### 7.5 No online payment provider

The portfolio dashboard page does not initiate any payment flow. Outstanding rent figures
are **read-only** aggregations from the billing ledger. The "Record payment" workflow
(manually marking a rent charge as paid) is in the RNT cluster and is explicitly out of
scope for PMD-004.

### 7.6 Cross-user data isolation

All backend endpoints are scoped to `session["user_sub"]` (`require_ui_session`). A
landlord sees only their own properties, leases, and ledger rows. The frontend does not
pass any `user_sub` parameter — the backend derives it from the session cookie.

**Impersonation note**: `require_ui_session` in `app/services/sessions.py` does NOT
replace `session["user_sub"]` with the impersonated user's sub — the returned dict
keeps `user_sub = actor_sub` and separately provides `effective_sub` (line 454-461).
PMD-003 backend handlers must use `session.get("effective_sub", session["user_sub"])`
to correctly serve an impersonating admin's view of the target user's portfolio. This
is a PMD-003 implementation concern; PMD-004 (frontend) is unaffected either way since
it sends no `user_sub` parameter.

- Before PMD-001/003: all five API calls return 404 → the page shows the "unavailable"
  state silently.
- After PMD-001/003 with flag off: same 404 degradation.
- After PMD-001/003 with flag on: full dashboard is active.

The route `/portfolio` is always registered in the SPA; deep links work even when the
flag is off (they show the unavailable state).
