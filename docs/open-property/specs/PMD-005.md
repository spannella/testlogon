**Ticket type:** Test
**Priority:** P1
**Estimate:** 2 d
**Flag:** `PROPERTY_DASHBOARD_ENABLED` (default OFF; shared master flag for PMD cluster,
introduced by PMD-001)
**Hard dependencies:** PMD-001, PMD-002, PMD-003, PMD-004
**Soft dependencies (integration seams, skip-marked when absent):** LSE cluster

## 1. Summary & Goal

PMD-005 delivers the **complete automated test harness** for the PMD cluster (PMD-001
through PMD-004) and exercises the four cross-module integration seams that the cluster
depends on: the LSE policy-inheritance hook, the EVT-011/012 document-linking carry-forward,
the RPT-007 dashlet dispatch, and the end-to-end KPI roll-up across all four upstream
clusters (PROP/LSE/RNT/WOV).

The primary deliverables are:

1. **Four hermetic pytest suites** — one per PMD-001..003 service and one for the RPT-007
   dashlet provider — each offline with no real AWS and no network.
2. **One cross-module integration pytest suite** (`tests/test_pmd_integration.py`) that
   exercises the seams between PMD and its upstream clusters, with every absent cluster
   wrapped in a `pytest.mark.skipif` guard so a missing module is a clean skip rather than
   a test failure.
3. **One Playwright E2E spec** (`frontend/e2e/portfolio-dashboard.spec.ts`) covering
   rent-policy CRUD, document-linking isolation, KPI/snapshot/priority API shape, the
   dashboard UI, the RPT dashlet tile, and a flag-off smoke.

No production code is introduced in this ticket. The tests are strictly additive. With
`PROPERTY_DASHBOARD_ENABLED=false`, every PMD endpoint returns HTTP 404 and every test
suite must assert that path explicitly.

### 2.2 Upstream billing ledger primitives (must be reused, never forked)

Every monetary assertion in the tests flows through these primitives verbatim:

- `new_ledger_entry` at `app/services/billing_shared.py:224` — the sole write path for rent
  charges; emits `pk="USER#{user_sub}"`, `sk="LEDGER#{ts}#{entry_id}"`, `ledger_date`

- `compute_due(balance_item)` at `app/services/billing_shared.py:158` — reads the four
  `BAL_FIELDS` counters and returns `due_settled_cents` / `due_if_all_settles_cents`. The

  `compute_due` to derive `outstanding_rent_cents`.
- `settle_or_reverse_ledger` at `app/services/billing_shared.py:262` — the mandatory void
  path: updates `state` to `"reversed"` via `update_item`; never deletes the ledger row.
  The test suite asserts that voiding a seeded charge is reflected as a decrease in
  `outstanding_rent_cents` on the next `compute_kpis` call.
- `apply_balance_delta` at `app/services/billing_shared.py:83` — the atomic counter
  update; tested indirectly through balance row seeding.
- `ledger_date_for_ts` at `app/services/billing_shared.py:10` — UTC `YYYY-MM-DD`
  derivation; tests patch `now_ts` to fix a deterministic date so `ledger_date` filtering

### 2.4 Test harness pattern

All Python tests in this repo are hermetic and offline. The authoritative harness pattern is:

- **Frozen `T`**: `T` is a frozen `@dataclass` (`app/core/tables.py:68`). To swap a table
  handle for a moto-backed table, mutate via `object.__setattr__(T, "rent_policy",
  ddb.Table("rent_policy"))`, and restore in `addCleanup` / `teardown`. Examples:
  `tests/test_gap_0199_0200_collaboration_revenue.py:113-125`,
  `tests/test_gap_0151_fan_club_feature_flag.py:26`.
- **Frozen `S`**: Settings is also frozen. Toggle flags with
  `object.__setattr__(S, "property_dashboard_enabled", True)` and restore after.
  `tests/test_gap_0151_fan_club_feature_flag.py:26,35`.
- **Async route coroutines**: call route handlers directly on a fresh event loop:
  `loop = asyncio.new_event_loop(); loop.run_until_complete(handler(...))`.
  Pattern from `tests/test_gap_0233_0234_ssh_session_recording.py:290-296`.
  (`tests/test_gap_0235_0236_ssh_bastion_multihop.py` uses synchronous handlers only
  and contains no asyncio — it is not the correct reference.)
- **No `TestClient`**: the FastAPI `TestClient` is not used in hermetic suites (it spins up
  a full ASGI app that re-reads `T`/`S` outside test control).
- **`patch.object` for lazy-imported collaborators**: PMD-003 uses lazy local imports for
  PROP/LSE/RNT/WOV to avoid circular deps. Tests use `patch.object(portfolio_dashboard,
  "_list_properties", ...)` (or the module-level name) to inject canned responses.

## 3. Data Model

PMD-005 introduces **no new DynamoDB tables or GSIs**. All data seeded by the tests lives
in the tables already defined by PMD-001..003 and their upstream clusters:

| Table (T.*) | Settings key | Use in tests |
|---|---|---|
| `T.rent_policy` | `S.rent_policy_table_name` ("rent_policy") | PMD-001 tests: policy CURRENT + AUDIT rows |
| `T.billing` | `S.billing_table_name` ("billing") | PMD-003 / integration: LEDGER + BALANCE rows |
| `T.file_manager` | `S.filemgr_table_name` ("file_manager") | PMD-002 tests: NODE items with CRM attrs |
| `T.properties` | `S.properties_table_name` ("properties") | integration: property items |
| `T.leases` | `S.leases_table_name` ("leases") | integration: lease items |
| `T.tickets` | `S.tickets_table_name` ("tickets") | integration: WOV fallback open tickets |

**Moto initialization pattern** (per test file): each suite starts moto with
`@moto.mock_aws`, creates the required tables with the same `TableDef` parameters used in
`scripts/local-ddb-init.py`, binds them to the frozen `T` via `object.__setattr__`, and
restores on teardown. No table is re-created across test files — each file is isolated.

**Key shapes seeded in tests** (all follow existing schemas; no new keys):

- Rent-policy rows: `{pk: "POLICY#{owner_sub}", sk: "CURRENT", rent_due_day: N, ...}`;
  audit rows: `{pk: "POLICY#{owner_sub}", sk: "AUDIT#{ts}#{event_id}", ...}`.
- Billing ledger rows: `{pk: "USER#{owner_sub}", sk: "LEDGER#{ts}#{entry_id}",
  type: "rent_charge", amount_cents: N, state: "open"|"settled"|"reversed",
  ledger_date: "YYYY-MM-DD"}` — written via `new_ledger_entry` to guarantee
  `ledger_date` is populated (the scan in `monthly_rent_snapshot` relies on it).
- Balance row: `{pk: "USER#{owner_sub}", sk: "BALANCE", owed_settled_cents: N,
  payments_settled_cents: N, ...}` — seeded via `apply_balance_delta`
  (`app/services/billing_shared.py:83`) for `compute_due` assertions.
- File-manager node: `{PK: "USER#{caller}", SK: "NODE#/leases/lease42.pdf",
  linked_record_type: "lease", linked_record_id: "<lease_id>", crm_category: "Lease", ...}`.

**Numeric GSI sort key note**: `T.rent_policy` has no GSI (only per-owner partition reads).
`T.billing`'s `GSI_LEDGER_DATE` uses `partition_key="ledger_date"` (S) and
`sort_key="sk"` (S) — both are strings; no numeric attribute is involved on this GSI
(verified at `scripts/local-ddb-init.py:71-76`). No `attr_types` change is required for
PMD-005. If any additional table seeded in the integration test introduces a numeric GSI
sort key, the `TableDef` in the test setup must include `attr_types={"created_at": "N"}`
(CLAUDE.md DynamoDB numeric-GSI gotcha).

## 5. Detailed Behavior & Edge Cases

### 5.1 PMD-001 rent-policy tests

**Effective defaults path**: seed an empty `rent_policy` table; call `get_policy(owner_sub)`
directly (no HTTP, direct service call); assert the returned dict has `rent_due_day=1`,
`late_fee_cents=0`, `grace_period_days=0`, `currency="usd"` (from `S.default_currency`),
and `is_default=True`. No DDB write occurs.

**Saved policy path**: call `set_policy(owner_sub, rent_due_day=15, late_fee_cents=5000,
grace_period_days=3, currency="gbp", actor_sub="admin1")`; then `get_policy(owner_sub)`;
assert `is_default=False`, all four fields match, `updated_at` is non-zero.

**Validation edge cases** (each expects `HTTPException(422)` from the service, or 422 from
the route handler called directly):
- `rent_due_day=0` → 422 (below minimum 1).
- `rent_due_day=29` → 422 (above maximum 28).
- `late_fee_cents=-1` → 422 (negative).
- `grace_period_days=-1` → 422 (negative).
- `currency="USDD"` (4-letter) → 422 (not a 3-letter code).
- `currency="1US"` (non-alpha) → 422.

**Audit append-only**: call `set_policy` twice with different values. Assert two `AUDIT#`
rows exist in the table and `updated_at` on the second is strictly greater than the first.
A third identical call (same values) must still write a new AUDIT row — PMD-001 is
append-only regardless of whether values changed (distinct from `billing_config`'s no-op
behavior, which applies to the full CURRENT-item diff; the policy service always audits).

**Cache invalidation**: patch `billing_config.invalidate_cache` logic equivalent to confirm
that after `set_policy`, the next `get_policy` call performs a fresh DDB read rather than
returning a stale in-memory cached value. Implemented by: (a) monkey-patching
`rent_policy._config_cache` to a stale value, (b) calling `set_policy`, (c) asserting
`_config_cache` is `None` (or that the returned value reflects the new write, not the stale
patch).

**Flag-off 404**: call each route handler directly with
`object.__setattr__(S, "property_dashboard_enabled", False)`. Assert `HTTPException(404)`
is raised before any DDB call (`T.rent_policy` mock must NOT be touched).

### 5.2 PMD-002 document-linking tests

**Allowlist test**: inspect `filemanager._LINKED_RECORD_TYPES` (the module-level frozenset);
assert each of `"property"`, `"unit"`, `"lease"`, `"tenant"` is a member. Assert that the
pre-existing types `"contact"`, `"ticket"`, `"account"`, `"party"` are still present
(additive, not replacing).

**PATCH writes link**: seed a `file_manager` node item for caller `"alice"` at path
`/leases/42.pdf`. Call `update_crm_metadata(user_sub="alice", path="/leases/42.pdf",
linked_record_type="lease", linked_record_id="lease_42", ...)`. Fetch the node with
`get_item`; assert `linked_record_type="lease"` and `linked_record_id="lease_42"` are
present on the item. Assert existing node attributes (`PK`, `SK`, `type`, `name`) are
unchanged (additive update).

**Unknown type → 400**: call `update_crm_metadata` with `linked_record_type="invoice"`;
assert `HTTPException(400, detail={"code":"invalid_linked_record_type"})` is raised.

**Cross-user isolation**: seed two nodes — one for `"alice"` linked to `property_id="p1"`,
one for `"bob"` linked to the same `property_id`. Call `search_by_linked_record(user_sub=
"alice", linked_record_type="property", linked_record_id="p1")`. Assert only the alice node
is returned, not bob's. This exercises the `PK=USER#{caller}` scope in the scan.

**`GET /info` projection unchanged**: fetch `file_info` on the patched node; assert the
response dict contains none of `linked_record_type`, `linked_record_id`, `crm_category`,
`crm_description` (EVT-011 additive-only contract).

**Double-flag 404**: test each flag combination — `PROPERTY_DASHBOARD_ENABLED=True,
CRM_DOCUMENT_LIBRARY_ENABLED=False` → 404 on `…/documents`; `True,True` → 200.

### 5.3 PMD-003 portfolio dashboard tests

**KPI roll-up**: Seed moto data for the four clusters (using lazy patches for PROP/LSE
since those tables may not exist in the test environment):
- Patch `portfolio_dashboard._list_properties` to return two properties with occupancy
  `{total:4, occupied:3}` and `{total:2, occupied:2}` → `occupancy_rate ≈ 0.833`,
  `unit_count=6`, `occupied_units=5`.
- Patch `portfolio_dashboard._list_active_leases` to return 3 leases →
  `active_lease_count=3`.
- Seed two open rent ledger rows (state=`"open"`) totaling 250000 cents plus one settled
  row into `T.billing`; assert `outstanding_rent_cents=250000`.
- Patch `portfolio_dashboard._count_open_work_orders` to return 2 →
  `open_work_order_count=2`.

**Graceful degradation**: call `compute_kpis` with all patched helpers raising
`ImportError`; assert the response is `{occupancy_rate: 0.0, unit_count: 0, occupied_units:
0, active_lease_count: 0, outstanding_rent_cents: 0, open_work_order_count: 0}` with no
exception.

**Snapshot bucket reconciliation**: seed five ledger rows for a fixed month `(2026, 3)` by
patching `now_ts` to return a timestamp in that month at `new_ledger_entry` call time:
- Two `state="settled"`, `amount_cents=120000` each → `collected_cents=240000`.
- Two `state="open"`, `amount_cents=100000` each → `outstanding_cents=200000`.
- One `state="reversed"` → excluded from all buckets.
- Total `charged_cents=440000` (settled + open before reversal correction).
- Assert invariant: `collected_cents + outstanding_cents == charged_cents` (440000 == 440000).

**Overdue bucketing uses policy**: seed a policy with `rent_due_day=1, grace_period_days=0`
and patch the current date to the 15th of the period month. Assert that open rows whose
`ledger_date` falls before the due-day threshold are classified as `overdue`, and
`overdue_cents <= outstanding_cents`.

**Priority items excludes open-ended leases**: patch `_list_upcoming_expirations` to return
a mix of active fixed-term leases and one open-ended lease (`end_date=None`). Assert the
open-ended lease is absent from `priority_items`.

**`priority_items` limit**: pass `limit=2` with three seeded items; assert exactly two are
returned.

two unpaid rent ledger rows (state=`"open"`), one open ticket linked to the property; call
`compute_kpis(owner_sub)` with a real moto `T.billing` table; assert all four KPI fields
are non-zero and match the seeded values.

### 5.6 E2E edge cases

**State accumulation**: every E2E test run leaves policy rows, file nodes, ledger rows, and
priority items in DynamoDB local. The spec must run `just restart` before the first full
suite run (CLAUDE.md "Test data accumulates" gotcha). Sections 70–75 are idempotent where
possible (use unique `TS`-suffixed IDs).

**Flag-off smoke** (Section 75): all five endpoints (`GET /ui/rent-policy`,
`PUT /ui/rent-policy`, `GET /ui/portfolio/kpis`, `GET /ui/portfolio/rent-snapshot`,
`GET /ui/portfolio/priority-items`, and the four `…/documents` convenience reads) must
return HTTP 404 when the backend is started with `PROPERTY_DASHBOARD_ENABLED=0`. The E2E
run in flag-off mode is a separate Playwright project or a conditional block using the
backend's runtime environment.

**Admin-gating on rent-policy PUT**: Alice (role USER) calling `PUT /ui/rent-policy`
must receive HTTP 403 (not 404). Charlie (role ADMIN) must receive 200.

**CSRF on PUT**: a PUT without `x-csrf-token` header from a session-auth caller returns
403. Bearer-auth callers (global `request` fixture) bypass CSRF.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

**SECOPS-007 parity**: PMD-005 tests exercise the same code path in dev (moto-intercepted
boto3) as would run in prod (real DynamoDB). The test assertions rely on moto's DDB
semantics, which are spec-compatible with real DynamoDB for `put_item`, `update_item`,
`query` with `begins_with`, and `scan` with `FilterExpression`. No `if S.dev_mode` branch
exists in any PMD service (this is asserted by a static grep check in the test suite
module docstring, consistent with the SECOPS-007 requirement across all PMD services).

**Idempotency of test setup**: each test's `setUp` creates a fresh moto table with
`@moto.mock_aws`. `tearDown` drops the table handle from `T` and resets `S` flags. Tests
can be run in any order; no test depends on state left by another.

**Money-safety assertions**: the test suite includes an explicit negative test: calling
`settle_or_reverse_ledger` to void a rent charge must NOT delete the ledger row. After
calling `settle_or_reverse_ledger(T.billing, "pk", "USER#alice", sk, "reversed")`, a
`get_item` on the same key must return the row with `state="reversed"` (not `None`). This
directly verifies the "void = state update, never delete" invariant from `billing_shared.py:262`.

**No online payment provider**: rent charges are posted via `new_ledger_entry` with
`state="open"` and recorded as paid via `settle_or_reverse_ledger` with `state="settled"`.
The tests confirm this: no Stripe/PayPal/CCBill call, mock, or import appears anywhere in
the PMD test files. An import-time assertion (`assert "stripe" not in sys.modules` after
importing the PMD services) is included in the test module setup as a money-safety guard.

**Cross-user isolation**: every service function that reads ledger rows uses
`pk = "USER#{owner_sub}"` to scope to the requesting user's partition. The test suite
seeds data for both `"alice"` and `"bob"` and asserts that `compute_kpis("alice")` never
includes bob's ledger rows — the partition key is the only isolation boundary, not a
`FilterExpression` (which DynamoDB evaluates post-fetch; misuse would allow cross-user
leakage for multi-user scans).

## 10. Open Questions / Assumptions

1. **WOV cluster availability**: PMD-005 assumes the work-order KPI falls back to the ticket
   system (`app/services/tickets.py`) when WOV is absent. If WOV lands before PMD-005, the
   integration test in §9.5 must be extended to seed a WOV work-order item rather than a
   ticket item. The skip guard `_wov_available()` follows the same pattern as
   `_lse_available()`.

2. **Flag-off E2E mode** (Section 75): it is assumed either (a) a second Playwright project
   in `playwright.config.ts` starts the backend with `PROPERTY_DASHBOARD_ENABLED=0`, or
   (b) Section 75 mocks the five endpoints at the Vite proxy level to return 404, avoiding
   a second backend process. The latter approach is preferred for CI speed; the spec will
   use `page.route("/ui/portfolio/**", route => route.fulfill({status:404}))` and
   `page.route("/ui/rent-policy*", ...)` to simulate the flag-off state.

3. **`T.crm_dashboards` table existence**: the dashlet provider tests assume
   `T.crm_dashboards` is defined (introduced by RPT-001). If RPT-001 is not yet merged,
   `tests/test_pmd_003_dashlet_provider.py` is skip-guarded with `_crm_dashboards_available()`.

4. **`list_upcoming_expirations` return shape**: PMD-005 assumes LSE-003 returns
   `{"expirations": [...], "count": N}` per the LSE-003 spec. If the shape differs at
   merge time, the priority-items test patching must be updated.

5. **Audit append-on-identical-PUT**: The PMD-001 spec says the audit log is always
   append-only (unlike `billing_config` which skips audit for no-op updates). The
   integration test asserts two AUDIT rows after two identical PUTs. If the PMD-001
   implementation adopts a no-op strategy, this test needs to be adjusted to use
   differing values per PUT.

6. **`rent_due_day=28` boundary**: the spec accepts 1–28 (not 31) because February always
   has at least 28 days, avoiding invalid due-dates. The boundary test for `rent_due_day=28`
   must succeed (200), while `rent_due_day=29` must fail (422).
