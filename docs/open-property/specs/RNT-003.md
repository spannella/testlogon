## 1. Summary & Goal

RNT-003 delivers two complementary capabilities that close the audit and correction loop for
the rent ledger:

1. **`list_rent_history`** — a paginated, filterable view of all `rent_charge` and
   `rent_payment` rows for a specific lease, sorted newest-first, each annotated with the
   derived charge status from RNT-002. This satisfies gap-matrix §B row 61 (*"payment history
   + void … ledger query + `settle_or_reverse_ledger`"*) for the history side.

2. **`void_rent_row`** — the MONEY-SAFETY-compliant void primitive. A voided row is
   **reversed, never deleted**: `settle_or_reverse_ledger` (`app/services/billing_shared.py:262`)
   flips the row's `state` to `"reversed"`, the original item stays intact in `T.billing` for
   audit, the corresponding balance counter is inverted with `apply_balance_delta`
   (`billing_shared.py:83`) so `compute_due` stays correct, and — only when the voided row is a
   `rent_charge` — the idempotency marker from RNT-001 is released so a corrected charge can be
   re-posted for that period.

Two HTTP endpoints surface these services:
- `GET  /ui/rent/leases/{lease_id}/ledger` — paginated per-lease history (charges + payments,
  optional `kind` filter).
- `POST /ui/rent/leases/{lease_id}/ledger/{ledger_sk}/void` — void a single row.

With `RENT_LEDGER_ENABLED=0` (the default) every new endpoint returns 404 and every new
service function returns `None`. No existing surface changes by a single byte.

**`settle_or_reverse_ledger` in detail** (`billing_shared.py:262–274`):

```python
def settle_or_reverse_ledger(
    table: Any,
    key_name: str,
    key_value: str,
    ledger_sk_value: str,
    new_state: str,
) -> None:
    table.update_item(
        Key={key_name: key_value, "sk": ledger_sk_value},
        UpdateExpression="SET #s = :s",
        ExpressionAttributeNames={"#s": "state"},
        ExpressionAttributeValues={":s": new_state},
    )
```

It is unconditional — it does not guard against already-reversed rows. The 409
`already_voided` guard in `void_rent_row` is therefore a pre-check (read-then-check-then-call),
not a CAS inside the primitive. The billing refund path at `billing.py:1323–1324` also calls
this primitive without a condition expression; that is the precedent.

**`apply_balance_delta` in detail** (`billing_shared.py:83–105`):

The actual implementation calls `ensure_balance_row` first (which creates the `BALANCE` row
if absent), then uses `if_not_exists(key, :z) + :delta` in the `SET` expression as an
additional guard. Passing a **negative** delta (e.g., `{"owed_settled_cents": -amount_cents}`)
is the balance reversal path — the same arithmetic already used by the billing refund at
`billing.py:1318–1321` (the `else` branch at line 1321 for settled-state payments):
```python
# billing.py:1318–1321 (conditional on payment status)
if pay.get("status") in ("processing", "requires_action"):
    apply_balance_delta(T.billing, pk, {"payments_pending_cents": -amount}, ...)
else:
    apply_balance_delta(T.billing, pk, {"payments_settled_cents": -amount}, ...)
```
RNT-003 applies the same negative-delta pattern for void.

### 2.2 The existing ledger list model this ticket mirrors

`GET /billing/ledger` (`app/routers/billing.py:2448–2454`):

```python
def list_ledger(ctx, ..., limit: int = 50, ...) -> Dict[str, Any]:
    items = ddb_query_pk(T.billing, user_pk(user_id))
    led = [it for it in items if it["sk"].startswith("LEDGER#")]
    led.sort(key=lambda x: x.get("ts", 0), reverse=True)
    return {"items": led[: max(1, min(limit, 200))]}
```

This is a full-partition scan capped at 200 rows. It is suitable for the platform billing
page but **not** for the per-lease rent history, which can span years. RNT-003's
`list_rent_history` adds:
- A `lease_id` filter (post-query, same as `billing.py:2452`'s `startswith` filter).
- An optional `kind` filter (`"charge"` or `"payment"`).
- HMAC-signed cursor pagination via `encode_cursor`/`decode_cursor`
  (`app/core/cursor.py:94`,`:103`), replacing the hard cap with genuine paging.

### 2.3 Cursor pagination — the HMAC-signed v2 scheme

`app/core/cursor.py:94–101` — `encode_cursor(last_evaluated_key)` wraps the DynamoDB
`LastEvaluatedKey` in a JSON envelope `{"v": "v2", "k": {...}}`, base64-URL encodes it, and
appends an HMAC-SHA256 signature using the `CURSOR_SIGNING_SECRET` env var (default
`"dev-cursor-secret"`). `decode_cursor` (`cursor.py:103–131`) verifies the signature
(current + optional previous secret) and extracts the key. A tampered or expired cursor
decodes to `None` — treated as "no cursor" (start from the beginning). The `_json_default`
hook at `cursor.py:12–19` coerces `Decimal` values so numeric GSI key components serialise
cleanly.

Because `list_rent_ledger_for_lease` (RNT-002) performs an in-process `ddb_query_pk` +
Python-sort pattern (not a DDB-native paginated query), cursors in this implementation carry
an **offset index** — the `sk` of the last item returned — rather than a raw
`LastEvaluatedKey`. The offset is signed with the same HMAC envelope so it is tamper-evident.

### 2.4 Void precedent — billing refund path

The full refund path at `billing.py:1286–1344` (function defined at `@dual_route("POST", "/billing/refund")` line 1286; post-Stripe-API body begins at line 1306) is the architectural model:
1. Validates the payment record.
2. Calls the Stripe refund API.
3. Writes a new `type="refund"` ledger row via `new_ledger_entry`.
4. Adjusts balance counters with `apply_balance_delta` (negative delta).
5. Calls `settle_or_reverse_ledger(T.billing, "pk", pk, pay["ledger_sk"], "reversed")`
   (`billing.py:1323–1324`) to flip the original row to `"reversed"`.
6. Emits `audit_event("billing_refund", ...)` (`billing.py:1332–1343`).

RNT-003 follows **the same sequence** for rent void, with two differences:
- Step 2 (provider call) is absent — rent is not processed online.
- Step 3 (new reversal ledger row) is omitted — the void of a rent row is fully captured
  by flipping the original row's `state`. The net effect on `compute_due` is identical
  because the balance counter is inverted in step 4.

### 2.5 Idempotency marker (RNT-001) and its release on charge-void

RNT-001 writes an idempotency marker for each charged `(user_sub, lease_id, period)`:

```
PK = "RENT_PERIOD#{user_sub}"
SK = "LEASE#{lease_id}#PERIOD#{period}"
```

Stored in **`T.rent_period_markers`** (a dedicated table introduced by RNT-001 —
`app/core/tables.py`, `app/core/settings.py:rent_period_markers_table_name`) via a
conditional `put_item("attribute_not_exists(pk)")`. Keeping the marker in its own table
prevents `attribute_not_exists(pk)` collisions with the `BALANCE` and `LEDGER#` rows that
share `USER#{user_sub}` PKs in `T.billing`. `void_rent_row` deletes the marker from
`T.rent_period_markers` when the voided row is a `rent_charge`, allowing `post_rent_charge`
(RNT-001) to re-post a corrected charge for that period without hitting the
`ConditionalCheckFailedException` skip path. No `LEDGER#` row is ever deleted.

#### `list_rent_history`

```python
def list_rent_history(
    user_sub: str,
    lease_id: str,
    *,
    kind: str | None = None,          # "charge" | "payment" | None (both)
    limit: int = 50,
    cursor: str | None = None,
) -> dict | None:
```

**Returns:**

```python
{
    "rows":        list[dict],   # RentLedgerRowOut dicts, newest-first
    "count":       int,
    "next_cursor": str | None,   # encode_cursor(...) token or None when exhausted
}
```

**Behaviour:**

1. Short-circuit on `not S.rent_ledger_enabled → return None`.
2. Delegate ownership check to `get_lease(user_sub, lease_id)` (LSE-001) — raises HTTP 404
   if the lease does not belong to `user_sub`.
3. Fetch all rows in the landlord partition via `ddb_query_pk(T.billing, user_pk(user_sub))`
   (mirrors `billing.py:2451`).
4. Filter to rent rows: `sk.startswith("LEDGER#") and extra.get("lease_id") == lease_id
   and extra.get("rent_kind") in {"charge", "payment"}`.
5. If `kind` is provided, further filter: `extra.get("rent_kind") == kind`.
6. Sort by `ts` descending (newest-first), matching `billing.py:2453`.
7. Decode `cursor` via `decode_cursor(cursor)` (`cursor.py:103`). A valid cursor carries
   `{"offset": int}` (the last-returned row's position in the sorted list). An invalid or
   absent cursor starts at offset 0.
8. Slice `rows[offset : offset + capped_limit]` where
   `capped_limit = max(1, min(limit, 200))`.
9. Annotate each `rent_charge` row with `derive_charge_status(row, payments=all_payment_rows_for_lease, lease=lease_item)` (RNT-002). Payment rows are returned as-is (no status annotation needed — they are the payment side).
10. Compute `next_offset = offset + capped_limit`. If `next_offset < len(all_rows)`:
    `next_cursor = encode_cursor({"offset": next_offset})` (`cursor.py:94`), else `None`.
11. Return `{"rows": annotated_slice, "count": len(all_rows), "next_cursor": next_cursor}`.

**Notes on the cursor approach:** Because the underlying data is a full-partition scan sorted
in-process, the offset cursor is safe for append-only ledgers (new rows sort to the front;
existing rows never move). It is not safe for concurrent deletions of ledger rows — but
`LEDGER#` rows are never deleted (constraint 3), so the cursor index remains stable across
pages.

#### `void_rent_row`

```python
def void_rent_row(
    user_sub: str,
    lease_id: str,
    ledger_sk: str,
    *,
    reason: str = "",
) -> dict | None:
```

**Returns:**

```python
{"ok": True, "ledger_sk": str, "state": "reversed"}
```

or raises `HTTPException(status_code=404)` / `HTTPException(status_code=409)`.

**Behaviour (ordered; every step must complete before the next):**

1. Short-circuit on `not S.rent_ledger_enabled → return None`.
2. **Ownership check:** `get_lease(user_sub, lease_id)` (LSE-001) → 404 if not owned.
3. **Row fetch:** `row = ddb_get(T.billing, user_pk(user_sub), ledger_sk)`
   (`billing_shared.py:27`). If absent → 404 `"rent row not found"`.
4. **Cross-lease fence:** if `row.get("lease_id") != lease_id` → 404 (prevents voiding a
   row from a different lease in the same landlord partition — constraint 8 from
   `RENT_LEDGER_TICKETS.md`).
5. **Row type guard:** if `row.get("rent_kind") not in {"charge", "payment"}` → 404
   `"not a rent row"` (prevents accidental void of non-RNT billing rows that happen to be
   in the partition).
6. **Idempotency guard:** if `row.get("state") == "reversed"` → raise
   `HTTPException(409, detail={"code": "already_voided", "ledger_sk": ledger_sk})`.
   This prevents a second balance decrement on a row that has already been reversed.
7. **State flip:** `settle_or_reverse_ledger(T.billing, "pk", user_pk(user_sub), ledger_sk, "reversed")`
   (`billing_shared.py:262`). **This is the only mutation on the ledger row itself.**
8. **Balance inversion** (constraint 4 / MONEY-SAFETY):
   - If `rent_kind == "charge"`:
     `apply_balance_delta(T.billing, user_pk(user_sub), {"owed_settled_cents": -amount_cents}, currency=row.get("currency","usd"))`
   - If `rent_kind == "payment"`:
     `apply_balance_delta(T.billing, user_pk(user_sub), {"payments_settled_cents": -amount_cents}, currency=row.get("currency","usd"))`
   The negative delta is the same pattern used by `billing.py:1318–1321` (the refund path).
9. **Marker release** (only for `rent_charge` voids, constraint 7): delete the idempotency
   marker `pk="RENT_PERIOD#{user_sub}"`, `sk="LEASE#{lease_id}#PERIOD#{period}"` from
   **`T.rent_period_markers`** (the dedicated marker table from RNT-001, NOT `T.billing`)
   via `ddb_del(T.rent_period_markers, f"RENT_PERIOD#{user_sub}", f"LEASE#{lease_id}#PERIOD#{row['period']}")`.
   This is the **only** `delete_item` call in the entire RNT cluster; it targets the
   marker row, not the ledger row.
10. **Audit:** `audit_event("rent.row_voided", user_sub, lease_id=lease_id, ledger_sk=ledger_sk, rent_kind=row["rent_kind"], amount_cents=int(row["amount_cents"]), period=row.get("period"), reason=reason)` (`app/services/alerts.py:644`).
11. Return `{"ok": True, "ledger_sk": ledger_sk, "state": "reversed"}`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Per-lease history scoping

`list_rent_history` issues a single `ddb_query_pk(T.billing, user_pk(user_sub))` (a DDB
Query on the full `USER#{user_sub}` partition), then filters in-process. The billing table
partition for a typical landlord contains: a `BALANCE` row, zero or more `PM#` payment-method
rows, a `BILLING` config row, and a bounded set of `LEDGER#` rows covering all product types.
The `lease_id` filter restricts the returned rows to a single lease. This approach mirrors
`billing.py:2451–2452` exactly and is appropriate for typical portfolios. Cross-partition
scans (multi-landlord admin views) are out of scope for RNT-003 — they belong to RNT-004
and RNT-005.

### 5.2 Cross-lease cross-tenancy fence

Because `T.billing` is partitioned by landlord (`USER#{user_sub}`), a landlord can only
query their own partition. However, within one landlord's partition there may be ledger rows
for multiple leases. `void_rent_row` step 4 checks `row.get("lease_id") != lease_id` to
prevent voiding a row that belongs to a different lease (e.g., if the client supplies a
correct `ledger_sk` but wrong `lease_id`). This also prevents a landlord from voiding
another landlord's row because `ddb_get(T.billing, user_pk(user_sub), ledger_sk)` can only
reach their own partition.

### 5.3 Already-reversed rows in `list_rent_history`

Voided rows are returned by `list_rent_history` with `state="reversed"` and — for charge
rows — `status="voided"` (from `derive_charge_status` in RNT-002: *"`"reversed"` → status
`"voided"`"*). They are never hidden from the history view. This is the audit guarantee:
landlords can always see what was voided and when. The frontend may visually dim them but
must not filter them out.

### 5.4 `derive_charge_status` annotation in list

`list_rent_history` annotates each `rent_charge` row by calling `derive_charge_status(row,
payments=<all_payment_rows_for_lease>, lease=<lease_item>)` (RNT-002). The payment rows used
as the second argument are the **complete** set of non-reversed `rent_payment` rows for the
lease, not just the paged slice. This ensures status derivation is never distorted by the
current pagination window. Implementation: collect all rows before slicing, derive statuses,
then slice for the response.

### 5.5 Void atomicity and partial-failure

`void_rent_row` steps 7 (state flip), 8 (balance inversion), and 9 (marker delete) are
**three separate DynamoDB operations**, not a transaction. DynamoDB transactions
(`transact_write_items`) are not used here — the existing billing primitives
(`settle_or_reverse_ledger`, `apply_balance_delta`, `ddb_del`) do not use them, and
introducing transactions would require touching `billing_shared.py` (a fork, prohibited by
constraint 2 from `RENT_LEDGER_TICKETS.md`).

Failure modes:
- If step 7 succeeds but step 8 fails (a rare DDB connectivity interruption): the row is
  `"reversed"` but the balance counter is not decremented. A retry of the void will hit the
  409 `already_voided` guard (step 6), preventing a double balance decrement.
  The balance inconsistency is self-correcting: `compute_due` will over-report outstanding
  by `amount_cents`. This is the same partial-failure posture as the billing refund path at
  `billing.py:1323–1324`.
- If step 8 succeeds but step 9 fails (marker not deleted): the charge can never be
  re-posted for that period until the marker is manually removed (admin tooling is out of
  scope for RNT-003; a follow-up admin endpoint or DDB console operation suffices).

**Operational recommendation** (not an implementation requirement): a background reconciler
(out of scope) can periodically check that `state="reversed"` `rent_charge` rows have
corresponding deleted markers, and fix any discrepancy.

### 5.6 Re-void prevention (idempotent 409)

`void_rent_row` step 6 checks `row.get("state") == "reversed"` before calling
`settle_or_reverse_ledger`. If the row is already reversed, a 409 is raised immediately.
This prevents the balance counter from being decremented twice for the same original
transaction — the most dangerous money-safety failure mode for a void operation.

### 5.7 Pagination cursor stability

Because `LEDGER#` rows are never deleted (constraint 3) and `void_rent_row` only mutates
the `state` field of an existing row, the total count of lease ledger rows is monotonically
non-decreasing. Offset cursors computed in one `list_rent_history` call remain valid across
subsequent calls: new rows added since the cursor was issued appear only at lower offsets
(earlier positions in the newest-first sort), so existing pages are not invalidated. The
one exception is a void that changes a row's `status` annotation — the row remains in the
same position but with updated `status: "voided"`. This is expected behavior (no pagination
gap introduced).

### 5.8 `kind` filter and count accuracy

The `count` field in `RentHistoryOut` reflects the **total** number of matching rows
(after `lease_id` + optional `kind` filter), not just the current page. This lets the
frontend render accurate "X of Y" pagination labels without a separate count query.

### 5.9 Void of a payment row does not touch the idempotency marker

A `rent_payment` void (step 8, `payments_settled_cents` decremented) does **not** touch
the `RENT_PERIOD#` marker row (step 9 is guarded by `rent_kind == "charge"`). A payment
is not idempotency-guarded; multiple payments for the same period are legal (partial
payments, overpayments). Voiding a payment decrements the collected balance, which changes
`derive_charge_status` from `"paid"` or `"partial"` back toward `"partial"` or `"open"` for
the affected period.

### 5.10 Currency handling in balance inversion

`apply_balance_delta` accepts an optional `currency` kwarg (default `"usd"`). The void
path reads `row.get("currency", "usd")` from the original row — the same currency the
original charge or payment was posted in. This prevents a mismatched balance row if a
landlord uses a non-USD currency for a particular lease.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no `dev_mode` branch

`app/services/rent_ledger.py` and `app/routers/rent_ledger.py` contain **zero**
`if S.dev_mode:` branches. Both `T.billing` and `T.leases` are DynamoDB tables — DDB Local
in dev (connected via `DDB_ENDPOINT_URL=http://localhost:8001`), real DynamoDB in prod. The
boto3 call path is identical in both environments; the only difference is the endpoint URL,
which is resolved by the existing `app/core/aws.py` / `app/core/tables.py` plumbing.
`settle_or_reverse_ledger` has no AWS-service dependencies beyond DynamoDB — it is already
SECOPS-007 compliant.

### 7.2 MONEY-SAFETY: void = reversal, never delete

The `LEDGER#` row written by `new_ledger_entry` (`billing_shared.py:224`) is never passed
to `ddb_del`. Only `settle_or_reverse_ledger` (`billing_shared.py:262`) mutates it, and only
to flip `state`. The row remains in `T.billing` indefinitely, providing a permanent audit
trail. This mirrors the billing refund path (`billing.py:1323–1324`) and the
audit-export claim CAS (CLAUDE.md).

### 7.3 MONEY-SAFETY: balance counter double-decrement prevention

The 409 `already_voided` guard (step 6 in `void_rent_row`) is checked **before**
`settle_or_reverse_ledger` is called. Because `settle_or_reverse_ledger` is unconditional
(no CAS), the application-level pre-check is the only protection against calling it twice.
The 409 response surfaces the `already_voided` code to the client so the UI can toast a
clear message rather than treating it as a generic error.

### 7.4 MONEY-SAFETY: no online payment provider

RNT-003 calls zero payment-provider SDK functions (no Stripe, PayPal, CCBill). A void
purely adjusts the `state` field of a ledger row and the `BALANCE` row. No refund is issued
to a tenant, no money moves on any payment rail. This is consistent with
`OPEN_PROPERTY_GAP_ANALYSIS.md` Headline: *"open-property deliberately excludes online
payment processing"* and `RENT_LEDGER_TICKETS.md` constraint 2.

### 7.5 Idempotency: `list_rent_history`

Pure read; idempotent by definition. Repeated calls with the same cursor return the same
rows (given no concurrent new rows are posted for that lease in the interval).

### 7.6 Idempotency: `void_rent_row`

The first void succeeds; all subsequent calls for the same `ledger_sk` return 409
`already_voided`. The balance counter is never decremented more than once per `ledger_sk`.

### 7.7 Ownership isolation

All DDB operations are keyed under `user_pk(user_sub)` (`"USER#{user_sub}"`). A landlord
cannot observe or modify another landlord's ledger rows because DDB partition isolation
prevents cross-partition reads entirely. The `get_lease(user_sub, lease_id)` ownership
check (step 2 in both service functions) is an additional defense-in-depth guard: even if
the client sends a plausible `ledger_sk` that belongs to a different lease, step 4's
`row.get("lease_id") != lease_id` fence blocks the void.

### 7.8 CSRF enforcement

`POST /ui/rent/leases/{lease_id}/ledger/{ledger_sk}/void` uses `require_ui_session`, which
enforces the `x-csrf-token` header matching the session's `csrf_token` and `ui_csrf` cookie
for all non-GET requests (CLAUDE.md "CSRF" section; `app/auth/deps.py`). Bearer-auth
requests bypass CSRF — applicable if API-key clients automate corrections.

## 10. Open Questions / Assumptions

**Q1. `ddb_query_pk` and large billing partitions.**
The assumption is that a typical landlord's billing partition (all `USER#{user_sub}` rows in
`T.billing`) fits within a DDB Query's 1MB response limit. If a landlord has thousands of
ledger rows (many properties over many years), `ddb_query_pk` will return only the first 1MB
page. This ticket inherits the same limitation as `billing.py:2451` — a known constraint,
not a regression. A future optimization (adding a per-lease GSI to `T.billing` or a separate
`rent_ledger` table) is deferred to a follow-up ticket. For RNT-003 the in-process filter
approach is explicitly modeled on the existing billing ledger endpoint and is adequate for
P1 delivery.

**Q2. Concurrent void + payment race.**
If a landlord voids a charge and records a new payment for the same period concurrently, the
`derive_charge_status` output on subsequent `list_rent_history` calls will reflect the new
state (charge voided → `"voided"`; new payment present but no charge to apply against → the
payment stands in the ledger unallocated). The status derivation handles this gracefully:
`derive_charge_status` skips reversed charges. No corrupted state arises; the business
semantics are user-visible and self-documenting via the audit trail.

**Q3. `ledger_sk` path encoding in the void URL.**
The `ledger_sk` is `LEDGER#{ts}#{entry_id}` — it contains `#` characters which are not
URL-safe. The router uses `{ledger_sk:path}` to capture the full value including `#`. The
frontend must URL-encode `#` as `%23` when constructing the URL. The `:path` converter in
FastAPI un-encodes `%23` back to `#` before calling the handler.

NOTE: There is no existing precedent in `app/routers/billing.py` for a `{ledger_sk:path}`
endpoint — the billing router has no route with a `ledger_sk` path parameter (the closest
is `app/routers/billing.py:2448` `GET /billing/ledger`, which accepts `ledger_sk` as a query
parameter, not a path segment). The `:path` pattern is established by FastAPI itself and is
safe to introduce here without a billing-router analogue.

**Q4. Assumption: `get_lease` is available from LSE-001.**
RNT-003 assumes `get_lease(user_sub, lease_id) -> dict` exists in `app/services/leases.py`
(LSE-001). It must raise `HTTPException(404)` when the lease does not belong to `user_sub`.
If LSE-001 is not deployed, RNT-003 cannot enable the flag.

**Q5. Assumption: `RentLedgerRowOut` model_rebuild.**
If `RentLedgerRowOut` contains a forward reference to another model, it may require a
`model_rebuild()` call after `app/models.py` is fully loaded. The pattern for this is
established in `ConversationOut.model_rebuild()` (CLAUDE.md). For RNT-003 the model is
self-contained and no `model_rebuild` is expected to be necessary.
