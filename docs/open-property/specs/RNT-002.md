## 1. Summary & Goal

RNT-002 adds the two complementary services that turn the raw `rent_charge` ledger rows
posted by RNT-001 into an actionable collection workflow:

1. **`record_payment`** — a thin `new_ledger_entry` wrapper that lets a landlord record a
   received payment (cash, check, bank transfer, etc.) against a lease, posting a
   `rent_payment` ledger row and bumping the `payments_settled_cents` balance counter.
   There is **no online payment provider involved**: open-property explicitly excludes
   payment processing (`OPEN_PROPERTY_GAP_ANALYSIS.md` Headline, §B row 59 — *"thin wrapper
   over `new_ledger_entry`"*). No Stripe/PayPal/CCBill surface is ever touched.

2. **`derive_charge_status`** — a pure, deterministic function that computes the
   `open | partial | paid | overdue | voided` status of a `rent_charge` row from the
   charge's `extra.period`, the sum of allocated payment rows, the lease's `rent_due_day`
   and `late_fee_grace_days`, and an optional `as_of_ts` clock. The derivation satisfies
   gap-matrix §B row 60: *"derive from ledger `state` + due_day"*.

A third helper, **`list_rent_ledger_for_lease`**, is introduced here because both
the status derivation and later tickets (RNT-003 history, RNT-004 summary) depend on
scoping the landlord's billing partition to a single lease.

Two HTTP endpoints surface these services:
- `POST /ui/rent/leases/{lease_id}/payments` — record a payment and return the updated
  charge status for that period.
- `GET  /ui/rent/leases/{lease_id}/charges` — list all `rent_charge` rows for a lease,
  each annotated with its derived status.

With `RENT_LEDGER_ENABLED=0` (the default), every new endpoint returns 404 and every new
service function returns `None`. No existing surface changes.

## 3. Data Model

### 3.1 `rent_payment` ledger row (new row kind in existing `T.billing`)

Written by `record_payment` via `new_ledger_entry`. The `extra=` dict is merged onto the
DDB item at `billing_shared.py:255`. No schema changes to `T.billing` are required.

```
pk           = "USER#{user_sub}"                  (landlord partition)
sk           = "LEDGER#{ts}#{entry_id}"           (ledger_sk format, billing_shared.py:220)
type         = "rent_payment"                     (new entry_type, additive)
state        = "settled"                          (immediately settled — no pending/async)
amount_cents = <int, ge=1>                        (recorded amount; no wallet deduction)
reason       = "Rent payment — lease {lease_number}"
ledger_date  = "YYYY-MM-DD"                       (set by new_ledger_entry:253, for GSI_LEDGER_DATE)
entry_id     = <ulidish>                          (new_ledger_entry:240 — `entry_id = ulidish()`)
ts           = <int, now_ts()>                    (billing_shared.py:239 — `ts = now_ts()`)

# From extra= dict:
lease_id     = <str>
property_id  = <str>
unit_id      = <str>
tenant_id    = <str>
period       = "YYYY-MM"                          (the rent period this payment covers)
rent_kind    = "payment"                          (distinguishes from rent_charge rows)
method       = "cash" | "check" | "bank_transfer" | "card_external" | "other"
reference    = <str>                              (check number, transfer ref, etc.; "" if absent)
paid_on      = <int>                              (Unix ts of when payment was received; defaults to now_ts())
currency     = <str>                              (from lease)

# From meta= dict (nested, not flat on item):
meta.notes   = <str>                              (free-text landlord notes; "" if absent)
```

The `GSI_LEDGER_DATE` index (declared in `scripts/local-ddb-init.py:67–77`) indexes on
`ledger_date` (S) / `sk` (S). The `new_ledger_entry` function always writes `ledger_date`,
so `rent_payment` rows appear in this index automatically without further changes.

### 3.2 No new table, no new GSI, no new `attr_types`

All `rent_payment` rows live in `T.billing` using the existing `pk` / `sk` composite key.
The `billing` table `TableDef` in `scripts/local-ddb-init.py` already declares
`attr_types={"ledger_date": "S"}` for the `GSI_LEDGER_DATE` sort key. Rent rows carry
only string and integer attributes; no new numeric GSI sort keys are introduced.

### 3.3 Per-lease ledger scan — no dedicated index needed

`list_rent_ledger_for_lease` uses a full partition scan (`ddb_query_pk`) plus
client-side filter on `extra.lease_id`. This is correct and safe: a single landlord's
billing partition is bounded (one row per month per lease, plus payment rows); the
`T.billing` table does not support a cross-attribute GSI filter on `lease_id` without a
new GSI. Adding a dedicated `lease_id` GSI is explicitly deferred to a follow-up if
portfolio scale warrants it (noted in §10 Open Questions).

#### `list_rent_ledger_for_lease(user_sub: str, lease_id: str) -> list[dict]`

Returns all `rent_charge` and `rent_payment` rows for a single lease, newest-first.

```python
def list_rent_ledger_for_lease(user_sub: str, lease_id: str) -> list[dict]:
    if not S.rent_ledger_enabled:
        return []
    rows = ddb_query_pk(T.billing, user_pk(user_sub))   # billing_shared.py:43
    rent_rows = [
        r for r in rows
        if r.get("sk", "").startswith("LEDGER#")
        and r.get("lease_id") == lease_id
        and r.get("rent_kind") in {"charge", "payment"}
    ]
    rent_rows.sort(key=lambda r: int(r.get("ts", 0)), reverse=True)
    return rent_rows
```

Dependency: `ddb_query_pk` (`billing_shared.py:43`), `user_pk` (`billing_shared.py:23`).
Called by `record_payment` (to compute updated charge status), `derive_charge_status`,
RNT-003 `list_rent_history`, and RNT-004 `period_summary`.

#### `record_payment(user_sub, *, lease_id, amount_cents, method, paid_on=None, reference="", period=None, notes="") -> dict | None`

The manual-collection entry point. **Never calls a payment provider.**

**Parameters:**

| Name | Type | Constraint | Notes |
|---|---|---|---|
| `user_sub` | str | — | Landlord's user sub |
| `lease_id` | str | — | Must be owned by `user_sub` |
| `amount_cents` | int | `ge=1` | Recorded amount; no wallet deduction |
| `method` | str | enum | `cash` \| `check` \| `bank_transfer` \| `card_external` \| `other` |
| `paid_on` | int \| None | optional | Unix ts of receipt; defaults to `now_ts()` |
| `reference` | str | optional | Check number, transfer ref, etc. |
| `period` | str \| None | `"YYYY-MM"` | Period this payment covers; defaults to `_current_period()` (RNT-001) |
| `notes` | str | optional | Free text; stored in `meta.notes` |

**Steps:**

1. Short-circuit: `if not S.rent_ledger_enabled: return None`.
2. `lease = get_lease(user_sub, lease_id)` (LSE-001 `app/services/leases.py`). Raises
   `HTTPException(404)` if absent or owned by a different landlord (ownership isolation,
   `RENT_LEDGER_TICKETS.md` constraint 8).
3. Validate `amount_cents >= 1` (raises `HTTPException(422)` otherwise).
4. Resolve `period = period or _current_period()`.
5. Resolve `paid_on = paid_on or now_ts()`.
6. Construct via `new_ledger_entry` (`billing_shared.py:224`):
   ```python
   sk, item = new_ledger_entry(
       key_name="pk",
       key_value=user_pk(user_sub),
       entry_type="rent_payment",
       amount_cents=amount_cents,
       state="settled",
       reason=f"Rent payment — lease {lease['lease_number']}",
       extra={
           "lease_id": lease_id,
           "property_id": lease.get("property_id", ""),
           "unit_id": lease.get("unit_id", ""),
           "tenant_id": lease.get("tenant_id", ""),
           "period": period,
           "rent_kind": "payment",
           "method": method,
           "reference": reference,
           "paid_on": paid_on,
           "currency": lease.get("currency", "usd"),
       },
       meta={"notes": notes} if notes else None,
   )
   ddb_put(T.billing, item)
   ```
7. Bump the balance counter (constraint 4):
   ```python
   apply_balance_delta(
       T.billing,
       user_pk(user_sub),
       {"payments_settled_cents": amount_cents},
       currency=lease.get("currency", "usd"),
   )
   ```
8. Emit audit event:
   ```python
   audit_event(
       "rent.payment_recorded", user_sub,
       lease_id=lease_id, period=period,
       amount_cents=amount_cents, method=method,
       reference=reference, ledger_sk=sk,
   )
   ```
9. Return the created ledger item dict.

**Returns:** The `item` dict as written to DDB, with `sk` populated.

#### `derive_charge_status(charge_row: dict, *, payments: list[dict], lease: dict, as_of_ts: int | None = None) -> str`

Pure, deterministic. No DDB calls. Accepts pre-fetched data so callers control the
snapshot (avoids TOCTOU between listing and status computation).

**Algorithm:**

```
as_of = as_of_ts or now_ts()

1. If charge_row["state"] == "reversed":
       return "voided"

2. period = charge_row.get("period")   # extra fields are merged flat via item.update(extra) at
                                       # billing_shared.py:255–256; there is no nested "extra" key
   charge_amount = int(charge_row["amount_cents"])

3. Compute paid_total = sum of amount_cents for all payment rows p where:
       p.get("rent_kind") == "payment"
       AND p.get("period") == period
       AND p.get("lease_id") == charge_row.get("lease_id")
       AND p.get("state") != "reversed"

4. if paid_total >= charge_amount:
       return "paid"

5. if 0 < paid_total < charge_amount:
       return "partial"

6. # paid_total == 0 — determine open vs overdue
   rent_due_day = int(lease.get("rent_due_day", 1))    # 1–28
   grace_days   = int(lease.get("late_fee_grace_days", 0))

   # Parse the period month
   year, month = int(period[:4]), int(period[5:7])

   # Construct the due timestamp: midnight UTC on rent_due_day of the period month
   # rent_due_day is capped at 28 by LSE-001 so no short-month arithmetic needed
   due_dt = datetime(year, month, rent_due_day, tzinfo=timezone.utc)
   due_ts = int(due_dt.timestamp()) + grace_days * 86400

7. if as_of > due_ts:
       return "overdue"
   else:
       return "open"
```

**Invariants:**
- Pure function; no I/O. Safe to call repeatedly with the same arguments.
- `payments` list may contain rows from multiple periods; the period-scope filter in
  step 3 ensures only the matching period's payments reduce the charge balance.
- `rent_due_day` is guaranteed `1–28` by LSE-001 (`docs/open-property/specs/LSE-001.md §3.2`),
  eliminating all month-length edge cases.
- `grace_days=0` means overdue immediately after midnight of `rent_due_day`.


```
Path:        /ui/rent/leases/{lease_id}/payments
Auth:        require_ui_session (cookie + CSRF required for non-GET)
Request:     RentPaymentIn (§4.3)

Status:      201 Created

  422  amount_cents < 1 or method not in enum
```

Handler body (abbreviated):

```python
@router.post("/leases/{lease_id}/payments", status_code=201)
async def post_rent_payment(
    lease_id: str,
    body: RentPaymentIn,
    ctx=Depends(require_ui_session),
) -> RentPaymentOut:
    if not S.rent_ledger_enabled:
        raise HTTPException(404, "rent_ledger_not_enabled")
    user_sub = ctx["user_sub"]
    item = record_payment(
        user_sub,
        lease_id=lease_id,
        amount_cents=body.amount_cents,
        method=body.method,
        paid_on=body.paid_on,
        reference=body.reference or "",
        period=body.period,
        notes=body.notes or "",
    )
    # Compute updated charge status for the period
    rows = list_rent_ledger_for_lease(user_sub, lease_id)
    lease = get_lease(user_sub, lease_id)
    period = body.period or _current_period()
    charge_row = next(
        (r for r in rows if r.get("rent_kind") == "charge" and r.get("period") == period),
        None,
    )
    status = (
        derive_charge_status(charge_row, payments=rows, lease=lease)
        if charge_row else None
    )
    return RentPaymentOut(
        ledger_sk=item["sk"],
        period=period,
        amount_cents=item["amount_cents"],
        method=item.get("method", ""),
        reference=item.get("reference", ""),
        paid_on=item.get("paid_on"),
        charge_status=status,
    )
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Payment recorded before any charge exists

`record_payment` does **not** require a matching `rent_charge` row for the period. A
landlord may record a received payment before the rent-run timer has fired (or in a manual
workflow). The `POST /payments` response carries `charge_status: null` in this case (no
charge row to derive status from). The payment row is still written and the balance counter
is still bumped — it will be applied when `derive_charge_status` is eventually called with
a charge row present.

### 5.2 Multiple payments for one period

`derive_charge_status` sums **all** settled (non-reversed) `rent_payment` rows for the
`(lease_id, period)` tuple. If a landlord records three partial payments for March, the
status transitions `open → partial → partial → paid` as each is added. The allocation
is always the full-period sum; there is no per-payment "allocation" concept in this ticket.

### 5.3 Over-payment

`paid_total > charge_amount` resolves to `"paid"` (not a separate `overpaid` status). The
excess is not automatically credited to the next period. RNT-004 `period_summary` will
surface `collected > charged` numerically; a separate reconciliation workflow is out of
scope for RNT-002.

### 5.4 Overdue boundary with `grace_days=0`

When `late_fee_grace_days=0`, the overdue threshold is midnight UTC on `rent_due_day`
of the period month. A payment recorded at any time before that threshold (even one second
before midnight) resolves to `open`; a derivation called one second after midnight with
no payment resolves to `overdue`.

### 5.5 `as_of_ts` override for deterministic tests

`GET /ui/rent/leases/{lease_id}/charges` accepts an optional `as_of_ts` query parameter.
When provided, it is passed through to `derive_charge_status` in place of `now_ts()`. This
enables hermetic E2E and unit tests to assert `open` vs `overdue` without clock dependency.
The parameter is never validated for "reasonableness" — any integer is accepted.

### 5.6 Lease not found or not owned

`record_payment` calls `get_lease(user_sub, lease_id)` as its first non-flag-check step.
The LSE-001 service raises `HTTPException(404)` if the lease is absent from the
`USER#{user_sub}` partition, leaking no information about whether the lease exists at all
under another landlord (constraint 8).

### 5.7 Reversed (voided) charge rows

`derive_charge_status` returns `"voided"` immediately when `charge_row["state"] == "reversed"`.
This happens when RNT-003 `void_rent_row` has been called on a charge. A voided charge row
is never further evaluated for `open`/`overdue`/`paid` — the entire payment-sum logic is
short-circuited. A subsequent payment for that period still accumulates against the
(future) replacement charge.

### 5.8 Currency consistency

`apply_balance_delta` is called with `currency=lease.get("currency", "usd")`. The
`ensure_balance_row` helper (`billing_shared.py:69`) creates the BALANCE row with the
given currency if it does not yet exist. Subsequent calls with a different currency would
create a mismatch in the existing BALANCE row, but this cannot occur in normal operation:
the `currency` field on a lease is treated as stable for the life of the lease.
**CORRECTION**: LSE-002 §3 (Mutable vs immutable field classification, line 134) lists
`currency` as **Mutable** via `LeasePatchIn`. Changing a lease's currency mid-tenancy is
permitted by the data model. The risk of a mixed-currency BALANCE row is therefore real if
`currency` is patched. This is acknowledged as an open multi-currency concern in §10 Q5.
The practical mitigation is that `record_payment` always reads the current `lease.currency`
at call time; the BALANCE row accumulates the most recent currency. Implementors should
treat `currency` as effectively immutable in the rent-workflow context even though the
schema permits mutation.

### 5.9 `period` format and validation

The `period` field uses the `"YYYY-MM"` format, enforced by the Pydantic `pattern`
validator on `RentPaymentIn`. If a caller passes a period string for a month that has
already passed (e.g., backfilling a missed payment for two months ago), it is accepted
without restriction. There is no policy against backdating.

### 5.10 `method` is informational only

The `method` field (`cash | check | bank_transfer | card_external | other`) carries
metadata about how the landlord received the funds. It has no bearing on any automated
action: no payment is initiated, no webhook is fired, no provider is contacted. A
`method="card_external"` entry means the tenant paid by card via a third-party tool and
the landlord is recording the fact.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-Safety

### 7.1 SECOPS-007 — No `dev_mode` branch

Neither `record_payment` nor `derive_charge_status` contains an `if S.dev_mode:` branch.
Both functions run identically in dev (DDB Local via moto, port 8001) and prod (real
DynamoDB). This is possible because rent is **manually recorded** — there is no online
payment provider mock needed. The `T.billing` boto3 client resolves to the mock endpoint
in dev via the `DDB_ENDPOINT_URL` env var and to real DynamoDB in prod — one code path,
satisfying SECOPS-007.

### 7.2 MONEY-SAFETY — `new_ledger_entry` is the only write path

`record_payment` writes exclusively through `new_ledger_entry` (`billing_shared.py:224`).
No bespoke `put_item` constructs a ledger row manually. No `delete_item` is ever called on
a ledger row. The only deletable artifact in the whole RNT cluster is the idempotency
marker row (`RENT_PERIOD#{user_sub}` / `LEASE#{lease_id}#PERIOD#{period}`), which is
owned by RNT-001/003.

### 7.3 MONEY-SAFETY — Balance via `apply_balance_delta` only

The `payments_settled_cents` counter is bumped exclusively via `apply_balance_delta`
(`billing_shared.py:83`), which uses an `if_not_exists`-guarded atomic `ADD`. There is no
inline `update_item` math in `record_payment`. The BALANCE row is automatically
initialized by `ensure_balance_row` (`billing_shared.py:69`) if it does not yet exist.

### 7.4 MONEY-SAFETY — No online payment provider

No Stripe/PayPal/CCBill client, SDK, or configuration is imported or referenced in
`app/services/rent_ledger.py` or `app/routers/rent_ledger.py`. The `method` field is a
plain string enum; it does not drive any payment dispatch. This is the core open-property
design invariant.

### 7.5 Idempotency

`record_payment` is **not idempotent** by design: each call creates a new ledger row,
modeling a distinct payment event. A landlord who calls it twice records two payments
(e.g., two partial payments summing to the full rent). There is no deduplication key for
payment rows; if the caller wants to cancel a duplicate entry, that is done via RNT-003
`void_rent_row`.

The caller-side idempotency guard (retrying on network failure) should be implemented at
the API client level using a client-generated idempotency key — this is surfaced as an
Open Question in §10.

### 7.6 Ownership isolation

The `get_lease(user_sub, lease_id)` call at the top of `record_payment` and inside both
handlers gates every write on a per-landlord partition check. A `lease_id` that belongs
to another landlord is absent from `USER#{caller_sub}` and raises 404 (no information
leakage). Cross-landlord reads of billing rows are similarly impossible because the
partition key `USER#{user_sub}` is always the caller's sub.

### 7.7 CSRF enforcement

`POST /ui/rent/leases/{lease_id}/payments` is a non-GET endpoint authenticated via cookie
session. Per CLAUDE.md, cookie-auth non-GET requests require `x-csrf-token` matching
both the session's `csrf_token` and the `ui_csrf` cookie. The `require_ui_session`
dependency at `app/services/sessions.py:330` enforces this automatically.

## 8. Backward Compatibility & Migration

### 8.1 No changes to existing routes or models

This ticket adds two new endpoints under the `/ui/rent` prefix (introduced by RNT-001)
and four new Pydantic models to `app/models.py`. No existing endpoint, model, or service
function is modified.

### 8.2 No schema migration for `T.billing`

`rent_payment` rows are new row kinds written into the existing `billing` table using the
standard `pk` / `sk` key shape. The `type` field value `"rent_payment"` is new but
additive; all existing query paths that filter on `type` (e.g., the platform financial
dashboard `GSI_LEDGER_DATE` query) will simply skip rows with unknown types or bucket them
as unrecognized — no breakage.

### 8.3 BALANCE row counter additions

`apply_balance_delta` uses `if_not_exists(payments_settled_cents, 0) + delta`. If the
BALANCE row exists from prior billing activity (e.g., a Stripe payment), the increment
lands correctly. If it does not exist, `ensure_balance_row` creates it first. No existing
balance computation is affected.

### 8.4 Flag toggle safety

With `RENT_LEDGER_ENABLED=0` (the default), zero `rent_payment` rows are ever written.
Enabling the flag for the first time on a live system is safe: there are no pre-existing
rows to reconcile, and enabling does not trigger any backfill or migration.

## 10. Open Questions / Assumptions

| # | Question | Assumption / Deferral |
|---|---|---|
| Q1 | Should `record_payment` support a caller-supplied idempotency key (e.g., `X-Idempotency-Key` header) to prevent duplicate POST on network retry? | Deferred. No idempotency key for payment rows. Duplicate entries are voided via RNT-003. Revisit if frontend retry storms are observed. |
| Q2 | Should `paid_on` be validated to reject future dates (e.g., a `paid_on` of tomorrow)? | Not validated. Backdating and forward-dating are both landlord prerogatives (e.g., recording a payment on the date the check cleared). |
| Q3 | Should `period` be validated to reject future periods? | Not validated. A landlord may pre-record a prepaid 6-month payment against a future period. |
| Q4 | A dedicated `lease_id` GSI on `T.billing` would make `list_rent_ledger_for_lease` an O(1) DDB query rather than an O(partition-size) scan + client-filter. Add it? | Deferred. A typical landlord's billing partition is small (one charge + a few payments per month per lease). If portfolio scale warrants it, add a `lease_id` GSI to `T.billing` in a follow-up. The service function signature is unchanged. |
| Q5 | Multi-currency: a landlord managing properties in different currencies would have one BALANCE row per currency? | The existing `apply_balance_delta` / `ensure_balance_row` design uses a single `BALANCE` row per partition (`pk`). Mixed-currency rent tracking is not addressed in this ticket; assumed single-currency per landlord at launch. |
| Q6 | Does `derive_charge_status` need to handle the case where `rent_due_day` falls on a month with fewer than 28 days (e.g., February 28 but `rent_due_day=28`)? | No. LSE-001 constrains `rent_due_day` to `1–28` (`docs/open-property/specs/LSE-001.md §3.2`), and February always has at least 28 days. |
