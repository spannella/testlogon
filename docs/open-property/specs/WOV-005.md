# WOV-005 — Frontend — work-order Kanban board + vendor directory + E2E

**Type**: Feature | **Priority**: P2 | **Estimate**: 2.5d
**Source**: `docs/open-property/WORKORDERS_VENDORS_TICKETS.md` §WOV-005 +
`docs/open-property/OPEN_PROPERTY_GAP_ANALYSIS.md` §C
**Depends on**: WOV-001, WOV-002, WOV-003 (optional), WOV-004, PROP-001, PROP-002, PROP-005

---

## 1. Summary & Goal

WOV-005 delivers the React/TypeScript frontend for the maintenance work-order vertical and
its companion vendor directory, wiring the WOV-002 and WOV-004 API surfaces into a
cohesive property-management UI. The flag-gated deliverables are:

1. **TypeScript types** mirroring `app/models.py` work-order and vendor models
   (`frontend/src/api/types.ts` — additive `// --- Maintenance Work Orders (WOV) ---` block).
2. **API endpoint wrappers** in `frontend/src/api/endpoints/maintenance.ts`.
3. **Work-order Kanban board** (`frontend/src/pages/maintenance/WorkOrdersPage.tsx`) —
   five-column status board (`open / assigned / in_progress / completed / cancelled`),
   column definitions fetched from `GET /ui/maintenance/work-orders/board-columns`, per-column
   card list from `GET /ui/maintenance/work-orders?wo_status={status}`, drag-and-drop
   transitions, priority badges, and a create dialog.
4. **Work-order detail drawer** (`WorkOrderDetailDrawer.tsx`) — full lifecycle timeline,
   assign/schedule/transition actions.
5. **Vendor directory** (`frontend/src/pages/maintenance/VendorsPage.tsx`) — trade-category
   filter, create/edit/deactivate, and vendor picker used by the WO assign action.
6. **Routes** in `frontend/src/App.tsx` and a **sidebar nav group** in
   `frontend/src/components/layout/Sidebar.tsx`.
7. **Integration pytest** `tests/test_wov_005_integration.py` — full create→assign→schedule→
   transition→complete round-trip via route coroutines on a fresh event loop, moto-bound
   tables.
8. **E2E spec** `frontend/e2e/maintenance.spec.ts` — Playwright, `charlie_admin` cookie auth,
   full lifecycle + vendor flows + flag-off 404 check.

With `MAINTENANCE_ORDERS_ENABLED=false` (the default): nav entries are hidden, routes are
registered (nav absence is sufficient gating for standard users), and every API call returns
404 from the backend's `_require_enabled()`. The UI renders a "Maintenance orders are not
enabled" callout on flag-off rather than a broken page, matching the Inventory vertical
pattern.

### 2.3 Ticket Kanban as the proven pattern

`frontend/src/pages/tickets/TicketKanbanBoard.tsx:1-37` implements the existing ticket Kanban
using `@dnd-kit/core` (already a project dependency at `frontend/package.json:17-20`). The
maintenance Kanban board re-skins this pattern with WO-specific statuses and card fields.
Key conventions:
- `VALID_TRANSITIONS` local constant mirrors the backend transitions (for client-side drag
  validation before the API call, same as `TicketKanbanBoard.tsx:24-30`).

- On `DragEndEvent`: call `PATCH .../{id}` transition API; on 409 `illegal_transition` toast

### 2.7 WOV-003 escrow sub-flag conditional field

When `MAINTENANCE_ORDERS_ESCROW_ENABLED=true` (WOV-003 sub-flag), the create-WO dialog
exposes an optional `amount_cents` field. The frontend detects sub-flag availability by
attempting a `GET /ui/maintenance/work-orders/board-columns` probe or by checking for the
`escrow_state` field in any returned work order item. For MVP, the approach is simpler:
the create dialog always renders the `amount_cents` field but marks it as "(requires escrow
enabled)" in the label; when the sub-flag is off and the backend ignores/rejects the field,
the UI degrades gracefully (field is optional in the Zod schema with `default: undefined`).

## 5. Detailed Behavior & Edge Cases

### 5.1 `WorkOrdersPage.tsx` — Kanban board

**Column bootstrap**: on mount, `useQuery({ queryKey: ["maintenance", "board-columns"], queryFn: getWoBoardColumns })` fetches the five column definitions from the `GET .../board-columns` endpoint (backed by WOV-001's `default_wo_columns()` function). While loading, render five skeleton columns. On success, render five `<DroppableColumn>` components in ascending `order`.

**Per-column card list**: each column fires its own `useQuery`:
```typescript
useQuery({
  queryKey: ["maintenance", "work-orders", { wo_status: column.status_key }],
  queryFn: () => listWorkOrders({ wo_status: column.status_key, limit: 50 }),
  staleTime: 30_000,
})
```
Cards are sorted by `created_at` descending (newest at top). Pagination: if `cursor` is
returned, a "Load more" button at the column bottom triggers a second fetch appending to
the local list. Full `useInfiniteQuery` is not required for the initial implementation.

**Card content** (one `<DraggableWorkOrderCard>` per `MaintenanceOrder`):
- Title (truncated to 2 lines).
- Priority badge: `urgent` → destructive red, `high` → warning orange, `normal` → secondary,
  `low` → outline; using shadcn/ui `<Badge>` variants.
- Property name (queried from the property service via a separate query keyed on
  `["properties", work_order.property_id]` or displayed as the raw ID when the
  properties feature is disabled).
- Unit label (if `unit_id` present) or "—".
- Vendor name (fetched from `["maintenance", "vendors", work_order.vendor_id]` or "Unassigned").
- `scheduled_for` formatted as `new Date(ts * 1000).toLocaleDateString()` or "—".
- `cost_cents` formatted via `formatCents` (pattern: `frontend/src/pages/Dashboard.tsx:30-35`)
  when present, otherwise "—".
- When `escrow_state` is present (WOV-003): small escrow status chip (`held`/`released`/`refunded`).
- Clicking the card opens the `WorkOrderDetailDrawer` (see §5.3).

**Drag-and-drop transitions**: uses `@dnd-kit/core` `DndContext` with `closestCenter`
collision detection (same pattern as `TicketKanbanBoard.tsx:14-16`). `useDraggable` on
each card, `useDroppable` on each column. `onDragEnd`:
1. Identify `sourceStatus` (from drag data) and `targetStatus` (from drop target column's
   `status_key`).
2. Client-side validation: `WO_VALID_TRANSITIONS[sourceStatus]` (a local constant mirroring
   `VALID_TRANSITIONS` from `app/services/maintenance_orders.py`, WOV-002 §4.1). If the
   target is not in the set, show `toast.error("Cannot move to that status")` and abort —
   no API call is made.
3. Optimistic update: move the card item to the target column's query cache via
   `queryClient.setQueryData(["maintenance", "work-orders", { wo_status: targetStatus }], ...)`.
4. Call `transitionWorkOrder(work_order_id, { property_id, target_status: targetStatus })`.
5. On success: `queryClient.invalidateQueries({ queryKey: ["maintenance", "work-orders"] })`.
6. On error (409 `illegal_transition`, 409 `concurrent_transition`, or network failure):
   revert the optimistic update and show `toast.error(err.response?.data?.detail ?? "Transition failed")`.

**"New Work Order" button**: top-right of the page, admin-only (hidden for `role === "user"`).
Opens the create dialog (§5.2). On success toasts "Work order created" and invalidates
`["maintenance", "work-orders"]`.

**Status filter tab strip**: above the Kanban, a horizontal tab bar (shadcn/ui `<Tabs>`)
with tabs "All", "Open", "Assigned", "In Progress", "Completed", "Cancelled". "All" renders
all five columns; a specific tab collapses to a single-column list view for that status.
This matches the open-property WO board pattern while reusing the WOV-002 status-queue
query (`Mode B: GSI_WO_STATUS`).

**Flag-off behavior**: when `getWoBoardColumns` returns 404, the page renders a centered
card: "Maintenance work orders are not enabled on this platform." with no Kanban columns.

### 5.2 Create work-order dialog

A shadcn/ui `<Dialog>` opened by the "New Work Order" button. React Hook Form + Zod:

```typescript
const createWoSchema = z.object({
  title:         z.string().min(1, "Title is required").max(200),
  description:   z.string().max(2000).optional(),
  priority:      z.enum(["urgent", "high", "normal", "low"]).default("normal"),
  property_id:   z.string().min(1, "Property is required"),
  unit_id:       z.string().optional(),
  scheduled_for: z.number().int().positive().optional(),
  amount_cents:  z.number().int().min(0).optional(),   // WOV-003 optional
});
```

Fields rendered:
- `title` — `<Input>` required.
- `description` — `<Textarea>` optional.
- `priority` — `<Select>` with four options, default "Normal".
- `property_id` — `<Select>` populated from `listProperties({ status: "active" })` (PROP-005
  endpoint); shows property name. Required.
- `unit_id` — `<Select>` populated from `listUnits(property_id)` (PROP-005 endpoint) when a
  `property_id` is selected; optional. Dynamically fetched on property selection.
- `scheduled_for` — `<Input type="date">` optional; converted to Unix timestamp on submit
  via `new Date(value).getTime() / 1000 | 0`.
- `amount_cents` — `<Input type="number" step="0.01">` optional, labeled "Escrow amount
  ($, if escrow enabled)"; not shown when `MAINTENANCE_ORDERS_ESCROW_ENABLED` is known to
  be off. For MVP, always shown but optional.

On submit: `useMutation({ mutationFn: (data) => createWorkOrder(data.property_id, data) })`.
Submit button is disabled while `isPending`. On success: close dialog, `toast.success`,
invalidate `["maintenance", "work-orders"]`. On 422 validation error, display inline field
errors from the response `detail`.

**Idempotency**: the frontend generates a `correlation_id` (`crypto.randomUUID()`) in the
`onSubmit` handler and includes it in the request body. This prevents double-submit races
(the backend's `attribute_not_exists(sk)` conditional put returns the existing item on a
duplicate call — per WOV-001 §5.1).

### 5.3 `WorkOrderDetailDrawer.tsx` / detail page

A slide-over drawer (shadcn/ui `<Sheet>` side panel) or a dedicated
`/maintenance/work-orders/:workOrderId` route page (the detail route in §4.2 covers the
latter; the `<Sheet>` provides the former for in-board use). The drawer fetches
`getWorkOrder(propertyId, workOrderId)` on open.

Content sections:
1. **Header**: title (editable inline via PATCH if admin), priority badge, status chip.
2. **Details row**: Property name | Unit label | Created at | Updated at.
3. **Assignment section** (admin only): vendor picker (dropdown populated from
   `listVendors({ status: "active" })`) + staff sub input field + "Assign" button calling
   `assignWorkOrder`. Shows active vendor name and `assignee_sub` when set.
4. **Schedule section** (admin only): date picker for `scheduled_for`; "Set Schedule" button
   calling `scheduleWorkOrder`.
5. **Lifecycle actions** (admin only): context-aware transition buttons derived from
   `WO_VALID_TRANSITIONS[current_status]`:
   - `open` → buttons "Assign", "Start Work" (`in_progress`), "Cancel".
   - `assigned` → buttons "Start Work" (`in_progress`), "Requeue" (`open`), "Cancel".
   - `in_progress` → "Complete" (shows optional `cost_cents` input), "Cancel".
   - `completed` / `cancelled` → no transition buttons (read-only).
6. **Cost section** (shown on completed WOs): `cost_cents` formatted as currency.
7. **Escrow section** (shown when `escrow_state` is present): escrow state chip, amount.
8. **Description**: full text in a readable prose block.

On successful transition, invalidate `["maintenance", "work-orders"]` and
`["maintenance", "work-orders", workOrderId]`.

**Cost input on completion**: the "Complete" button opens a small inline form with a
`cost_cents` number input (optional). On submit, calls `transitionWorkOrder(workOrderId, { property_id, target_status: "completed", cost_cents: parsedValue })`.

### 5.4 `VendorsPage.tsx` — vendor directory

### 5.6 Edge cases

| Scenario | Behavior |
|---|---|
| Drag WO to illegal status column (e.g., `open → completed`) | Client-side `WO_VALID_TRANSITIONS` check blocks API call; `toast.error("Cannot move from open to completed")` |
| Drag WO while a previous transition is in-flight | `isLoading` on the transition mutation disables the drag interaction (`pointer-events: none` on card) |
| `transitionWorkOrder` returns 409 `concurrent_transition` | Revert optimistic update; `toast.error("Work order was updated concurrently — please refresh")` |
| Assign to inactive vendor from drawer | Backend returns 422 `vendor_inactive`; `toast.error("Vendor is inactive — activate it first")` |
| `listWorkOrders` returns `cursor` (paginated column) | "Load more" button appends next page to column items; `cursor` is stored in component state, not in the query key |
| Create WO dialog submitted twice (double-click) | Submit button `disabled={isPending}`; backend idempotency via `correlation_id` (WOV-001 §5.1) catches any race |
| `scheduled_for` date picker — past date | Allowed (backend permits historical scheduling per WOV-002 §5.2); no client-side future-only guard |
| Flag off — `getWoBoardColumns` 404 | Render "not enabled" callout; all query hooks are disabled (`enabled: false` when `columns?.length === 0`) |
| WOV-003 not built — `amount_cents` field present but ignored | Backend WOV-003 escrow guard silently ignores the field when sub-flag off (WOV-003 §5.2); no frontend error |

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no dev-mode branches

WOV-005 is a pure frontend ticket. All backend interactions go through the WOV-001/002/004
services and router, which contain zero `if S.dev_mode` branches (WOV-002 §7.1). The
frontend itself has no concept of dev mode — it calls the same endpoints in both environments.

The hermetic pytest (`tests/test_wov_005_integration.py`) toggles `S.maintenance_orders_enabled`
via `object.__setattr__` but never sets `S.dev_mode`. All service calls go through the same
DynamoDB code path with moto intercepting boto3 — same code in dev and prod (SECOPS-007).

### 7.2 Idempotency — double-submit protection

The create dialog generates a `correlation_id = crypto.randomUUID()` once per open (on
mount or on `onOpenChange(true)`). The same UUID is sent on retry or accidental double-submit.
The backend's `attribute_not_exists(sk)` conditional put (WOV-001 §5.1) returns the existing
work order without a duplicate write. The submit button is disabled while `isPending` as a
UI guard.

Transition mutations are also safe to retry: `transitionWorkOrder` on an already-transitioned
WO returns 409 `concurrent_transition` (from the `ConditionExpression` guard, WOV-002 §5.3),
which the UI handles by re-fetching the current state.

### 7.3 Security — admin-only mutations

All mutation-triggering UI controls are conditionally rendered based on
`getRoleFromAccessToken(token) === "admin" || ... === "root"` (same guard as
`TicketsPage.tsx:43-44`). The backend enforces `require_admin_or_root_csrf` independently
on every PATCH and POST endpoint — the frontend guard is a UX convenience, not a security
boundary.

CSRF is enforced by the `api` client automatically injecting the `x-csrf-token` header from
the `ui_csrf` cookie (`client.ts:179`). Bearer-auth requests skip CSRF (CLAUDE.md auth
conventions).

### 7.4 Money-safety

**WOV-005 contains no money movement.** The frontend displays `cost_cents` as a formatted
currency string (reporting-only metadata, per WOV-001 §5.8 and WOV-002 §7.4). It never
calls `billing_shared.new_ledger_entry` (`billing_shared.py:224`),
`settle_or_reverse_ledger` (`:262`), `apply_balance_delta` (`:83`), or `compute_due` (`:158`).

When the WOV-003 escrow sub-flag is on, the `amount_cents` field is submitted to
`createWorkOrder` and the backend's `maintenance_orders.py` delegates escrowed funding to
the TBT-003 escrow service (which owns all `T.billing` writes). The frontend never calls
any billing endpoint directly; the escrow is a server-side side effect of the WO create
call. No online payment provider is involved — rent and maintenance escrow are manually
recorded platform-wallet operations, never Stripe/PayPal/CCBill.

## 10. Open Questions / Assumptions

1. **`work_order_id` available on drag without `property_id`**: The `PATCH .../assign` and
   `PATCH .../{work_order_id}` endpoints require `property_id` in the request body. Kanban
   cards hold the full `MaintenanceOrder` object (including `property_id`), so this is always
   available to the drag handler. Confirmed — the card query keys include the full item.

2. **Cross-property Kanban view (`GSI_WO_STATUS` Mode B)**: The default `/maintenance/work-orders`
   Kanban shows all work orders system-wide per status (Mode B query). For property-specific
   views, `PropertyDetailPage` (PROP-005) will later embed a scoped Kanban using Mode A
   (`GET /ui/properties/{id}/work-orders`). WOV-005 ships the global Kanban only; the property-
   scoped tab is a PROP-005 follow-up.

3. **`property_id` display on cards**: Cards need the property name, not just the ID. For MVP,
   the card fetches the property name from the React Query cache (`["properties", property_id]`)
   or displays the raw `property_id` if PROP-005 is not merged. A per-card `useQuery` for each
   property creates N+1 fetches — the alternative is a batch-property-lookup endpoint (future
   work). For MVP, the N+1 is acceptable given small Kanban sizes.

4. **WOV-003 sub-flag detection**: The frontend cannot reliably detect the escrow sub-flag state
   without a dedicated feature-caps endpoint. For MVP, the `amount_cents` field is always shown
   in the create dialog with a label note. When the sub-flag is off and the backend ignores
   the field, no error occurs (backend WOV-003 guard). If a dedicated `/ui/maintenance/config`
   endpoint is added later (returning flag states), the dialog can conditionally render the field.

5. **`@dnd-kit` accessibility**: The existing `TicketKanbanBoard.tsx` uses `@dnd-kit` with
   `PointerSensor` and `KeyboardSensor`. WOV-005 mirrors this configuration including
   `KeyboardSensor` for keyboard accessibility of drag-and-drop. Confirmation with the design
   system owner is recommended.

6. **Vendor pagination in `VendorPicker`**: `listVendors` paginates with `cursor`. The picker
   `<Combobox>` fetches the first page (default `limit=50`). For portfolios with > 50 active
   vendors, a "Load more" option or an unbounded search (passing `name_prefix` query param if
   the backend exposes it) is needed. Assumption: 50 active vendors is sufficient for MVP
   (gap analysis notes single-landlord portfolios are small).

7. **`WO_VALID_TRANSITIONS` local constant drift**: The local frontend constant must stay in
   sync with the backend `VALID_TRANSITIONS` dict in `app/services/maintenance_orders.py`.
   If the state machine changes in a future ticket, both must be updated. Recommendation:
   add a comment in both files cross-referencing each other.
