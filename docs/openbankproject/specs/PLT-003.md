## 1. Summary & Goal

Open Bank Project (OBP) ships a `/glossary` endpoint that serves a machine-readable dictionary of API terms and their markdown definitions. Client tooling (API Explorer, SDK generators, onboarding portals) calls the glossary to annotate field names and code values with human-readable explanations. The gap analysis (`docs/openbankproject/OBP_GAP_ANALYSIS.md:85`) classifies this as **MISSING (net-new)**.

This ticket closes that gap by adding a small, DDB-backed, admin-editable glossary to testlogon's `/v1` API surface. The feature is entirely additive: when `GLOSSARY_ENABLED=0` (the default) the router is not registered and every `/v1/glossary*` path returns 404. No existing table, middleware, or service is altered. No money moves.

Concrete deliverables:

- New DynamoDB table `glossary` (PK `term_id` S, with a `GSI_BY_TERM` GSI for alphabetical list queries).
- New service `app/services/glossary.py` implementing `list_glossary`, `get_glossary_term`, `upsert_glossary_term`, `delete_glossary_term`.
- New router `app/routers/glossary.py` with five endpoints: two public reads and three admin mutating operations.
- `app/core/settings.py` additions: `glossary_enabled`, `glossary_table_name`, `glossary_definition_max_chars`.
- `app/core/tables.py` + `scripts/local-ddb-init.py` additions: `T.glossary` handle and `TableDef`.
- Hermetic offline pytest `tests/test_plt_003_glossary.py`.

## 3. Data Model

### New DynamoDB table: `glossary`

Single-table design. One item type: a glossary term entry.

**Primary key:**
- `term_id` (S) — partition key; server-generated opaque identifier, format `"gloss_{uuid4().hex[:12]}"`.

No sort key — the table is a flat key-value store (one item per term).

**Item attributes:**

| Attribute | Type | Notes |
|---|---|---|
| `term_id` | S | PK; immutable after creation. |
| `term` | S | Short name of the term (e.g., `"transaction_id"`). Not unique-constrained at DDB level; uniqueness is enforced in the service. Max 200 chars. |
| `definition` | S | Markdown-formatted explanation. Max `S.glossary_definition_max_chars` (default 4096) chars. Validated by Pydantic before write. |
| `tags` | L(S) | Optional list of tag strings (e.g., `["transactions", "identifiers"]`). Empty list when absent. |
| `created_at` | N | `now_ts()` at first write. |
| `updated_at` | N | `now_ts()` at every write (create and patch). Plain item attribute — not used as a GSI key. <!-- CORRECTED: original said "Used as the GSI sort key"; the GSI sort key is GSI1SK (lowercased term), not updated_at --> |
| `updated_by` | S | `user_sub` of the admin who last wrote the item. |
| `GSI1PK` | S | Constant sentinel `"GLOSSARY#ALL"` — allows `query()` on the GSI to enumerate all terms without a `scan()`. |
| `GSI1SK` | S | `term.lower()` — ASCII-folded term name, enabling alphabetical `ScanIndexForward` traversal and `begins_with` prefix search. |

**GSI: `GSI_BY_TERM`**

| Key | Attribute | Type |
|---|---|---|
| Partition key | `GSI1PK` | S |
| Sort key | `GSI1SK` | S |

The sort key is a string (lowercased term), so **no `attr_types` override is needed for this GSI**. The `updated_at` field is numeric but is not used as a GSI key; it is a plain item attribute. `attr_types` must only list key attributes (primary-key or GSI/LSI keys) — including a non-key attribute causes DynamoDB to raise `ValidationException: Number of attributes in KeySchema does not exactly match number of AttributeDefinitions` (see `_attribute_definitions` in `scripts/local-ddb-init.py:2496–2506` which translates all `attr_types` entries into `AttributeDefinitions`). No `attr_types` entry is required or appropriate for the glossary table.

All functions are synchronous (DynamoDB operations are synchronous in boto3). No `async` keyword.

        terms) this is acceptable; a future full-text GSI can replace it.
    cursor : opaque HMAC-signed cursor from a previous response.
    limit : items per page, default 100, max 500.
    """
    ...


def get_glossary_term(term_id: str) -> Optional[Dict[str, Any]]:
    """Fetch a single term by its ``term_id``.  Returns None if absent."""
    ...


def upsert_glossary_term(
    *,
    term: str,
    definition: str,
    tags: Optional[List[str]] = None,
    term_id: Optional[str] = None,
    updated_by: str,
) -> Dict[str, Any]:
    """Create (term_id=None) or replace (term_id supplied) a glossary entry.

    On create: generates a new ``term_id``, sets ``created_at``.
    On replace (PATCH semantics via the router): replaces only the supplied fields;
    ``created_at`` and ``term_id`` are never overwritten.
    Returns the persisted item.
    """
    ...


def delete_glossary_term(term_id: str) -> bool:
    """Delete a term.  Returns True if the item existed and was deleted; False if absent."""
    ...

**`list_glossary` implementation detail:**
Query `T.glossary` on `GSI_BY_TERM` with `Key("GSI1PK").eq("GLOSSARY#ALL")`, `ScanIndexForward=True` (alphabetical), `Limit=min(limit, 500)`. If `search` is provided apply `FilterExpression=Attr("GSI1SK").contains(search.lower())` — the GSI sort key `GSI1SK` already holds the lowercased term, so case-insensitive substring matching is exact and cheap on the already-fetched attribute. <!-- CORRECTED: was Attr("term").contains(...); filtering on the lowercased GSI1SK is correct for case-insensitive search --> Cursor paging via `decode_cursor(cursor)` → `ExclusiveStartKey` and `encode_cursor(resp.get("LastEvaluatedKey"))` → `next_cursor`. Return `{"terms": [...], "next_cursor": str|None, "count": int}`.

**`upsert_glossary_term` implementation detail:**
For create: `term_id = f"{_TERM_ID_PREFIX}{uuid.uuid4().hex[:12]}"`. The item carries both `created_at = now_ts()` and `updated_at = now_ts()`. The GSI attributes `GSI1PK = "GLOSSARY#ALL"` and `GSI1SK = term.strip().lower()` are written on every upsert (so a term rename correctly repositions the item in the GSI). Write via `T.glossary.put_item(Item={...})`.

For update (term_id supplied): fetch the existing item first (`get_glossary_term`); if absent raise `HTTPException(404)`. Merge the supplied fields over the existing item preserving `term_id` and `created_at`, then `put_item` the merged result (full replace on the DDB row — simpler than a partial `update_item` expression and the item is small).

**`delete_glossary_term` implementation detail:**
`T.glossary.delete_item(Key={"term_id": term_id}, ReturnValues="ALL_OLD")`. Return `True` if `"Attributes"` key is present in the response (item existed), `False` otherwise.

@router.get("/v1/glossary", response_model=GlossaryListOut)
def list_terms(
    search: Optional[str] = Query(default=None, max_length=200),
    cursor: Optional[str] = Query(default=None),
    limit: int = Query(default=100, ge=1, le=500),
):
    return _svc.list_glossary(search=search, cursor=cursor, limit=limit)


@router.get("/v1/glossary/{term_id}", response_model=GlossaryTermOut)
def get_term(term_id: str):
    item = _svc.get_glossary_term(term_id)
    if item is None:
        raise HTTPException(status_code=404, detail="term not found")
    return item


@router.post("/v1/admin/glossary", response_model=GlossaryTermOut, status_code=201)
def create_term(body: GlossaryCreateIn, req: Request, admin_user: str = Depends(_require_admin_user)):
    item = _svc.upsert_glossary_term(
        term=body.term, definition=body.definition,
        tags=body.tags or [], updated_by=admin_user,
    )
    audit_event("glossary_upsert", admin_user, req, term_id=item["term_id"], action="create")
    return item


@router.patch("/v1/admin/glossary/{term_id}", response_model=GlossaryTermOut)
def patch_term(term_id: str, body: GlossaryPatchIn, req: Request, admin_user: str = Depends(_require_admin_user)):
    existing = _svc.get_glossary_term(term_id)
    if existing is None:
        raise HTTPException(status_code=404, detail="term not found")
    merged = {**existing}
    if body.term is not None:
        merged["term"] = body.term
    if body.definition is not None:
        merged["definition"] = body.definition
    if body.tags is not None:
        merged["tags"] = body.tags
    item = _svc.upsert_glossary_term(
        term=merged["term"], definition=merged["definition"],
        tags=merged["tags"], term_id=term_id, updated_by=admin_user,
    )
    audit_event("glossary_upsert", admin_user, req, term_id=term_id, action="patch")
    return item


@router.delete("/v1/admin/glossary/{term_id}", status_code=204)
def delete_term(term_id: str, req: Request, admin_user: str = Depends(_require_admin_user)):
    deleted = _svc.delete_glossary_term(term_id)
    if not deleted:
        raise HTTPException(status_code=404, detail="term not found")
    audit_event("glossary_delete", admin_user, req, term_id=term_id)

## 5. Detailed Behavior & Edge Cases

### List endpoint: alphabetical order and filtering

`GET /v1/glossary` queries `GSI_BY_TERM` with `ScanIndexForward=True`. Because `GSI1SK` is `term.lower()`, results are alphabetically ordered by lowercased term. The `?search=foo` filter uses `FilterExpression=Attr("GSI1SK").contains(search.lower())` — this is a post-fetch filter, so the DDB page scan may fetch up to `limit` items before filtering. On a small glossary corpus (hundreds to low thousands of terms) this is acceptable. If the corpus grows, a dedicated full-text index (e.g., OpenSearch) can replace the filter without changing the API contract.

`?search=` (empty string) is treated as absent — the service checks `if search` before applying the filter.

### Term uniqueness

The DDB schema does not enforce unique term names. The service does not enforce uniqueness either. Admin tooling is responsible for avoiding duplicates. Two terms with the same `term` but different `term_id` are both served. This matches OBP's own glossary model and avoids a conditional-write scan.

### Definition length enforcement

`S.glossary_definition_max_chars` (default 4096) is validated in the service function, not only by Pydantic. This means an operator who raises the cap at runtime (without a redeploy) will immediately accept longer definitions. The Pydantic `max_length=4096` in the model is a static guard; the service raises `HTTPException(422, detail="definition exceeds maximum length")` when the live setting is lower than the Pydantic cap but the operator has reduced it. This pattern is consistent with the codebase's settings-driven caps (e.g., `api_key_ttl_days`, `sandbox_import_max_items`).

### PATCH semantics

`PATCH /v1/admin/glossary/{term_id}` performs a field-level merge: only explicitly supplied non-`None` fields from `GlossaryPatchIn` overwrite the stored values. `term_id` and `created_at` are always preserved. `updated_at` is always refreshed to `now_ts()`. `updated_by` is always set to the calling admin sub.

### DELETE idempotency

`DELETE /v1/admin/glossary/{term_id}` returns 404 when the term does not exist. This is intentional: callers retrying a failed delete will get 404 on the second attempt (item is already gone). A fully idempotent 204 on re-delete would be acceptable too but 404 is the more informative choice and aligns with the rest of the codebase.

### Cursor tamper protection

`encode_cursor` produces an HMAC-signed cursor (`app/core/cursor.py:94`). A tampered or expired cursor raises `HTTPException(400)` from `decode_cursor`. This is the standard behavior for all paginated endpoints in the codebase and requires no special handling in the glossary router.

### Flag-off behavior

When `S.glossary_enabled` is `False` the router is never registered. FastAPI returns its default 404 for any path under `/v1/glossary*`. No empty response or feature-disabled JSON is returned — the route simply does not exist, matching the behavior of every other flag-gated router in the codebase.

### Admin auth when allowlist is empty

`_require_admin_user` (`admin_usage.py:41`) returns 403 with `"admin privileges not configured"` when `S.filemgr_admin_users` is empty. This means glossary admin endpoints are effectively locked even for the root user when the allowlist is not configured. Operators must add their user sub to `FILEMGR_ADMIN_USERS` to use the admin mutation endpoints. This matches the existing admin-usage router behavior.

### Tags field

`tags` is stored as a DynamoDB `List` of strings. An absent `tags` key on a pre-existing item is treated as `[]` when read. On create the service writes an explicit `[]` when `tags` is `None` to ensure the field is always present in the response model.

### `updated_at` on create

On creation, both `created_at` and `updated_at` are set to the same `now_ts()` value. This is the same pattern used by `audit_export_schedule.py:71` which sets `now = now_ts()` for both timestamps at creation time.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 dev/prod parity

There is no `if S.dev_mode:` branch in `app/services/glossary.py` or `app/routers/glossary.py`. All DynamoDB reads and writes go through the frozen `T.glossary` handle — DynamoDB Local in dev, real DynamoDB in prod. This is the same code path in both environments.

The only environment-specific behavior is controlled by settings (`GLOSSARY_TABLE_NAME`) and is resolved transparently through `T.glossary` — no mock paths, no special-cased dev logic.

### Idempotency of admin writes

`POST /v1/admin/glossary` always creates a new item (new `term_id`) even if a term with the same text already exists. Retrying a failed `POST` will create a second term with a different `term_id`. This is acceptable for a rare admin operation. If strict idempotency is required, the caller should use `PATCH` on the known `term_id` after a successful create.

`PATCH /v1/admin/glossary/{term_id}` is idempotent: re-sending the same payload writes the same field values (with a refreshed `updated_at`). No conditional writes are required.

`DELETE /v1/admin/glossary/{term_id}` is non-idempotent by design (returns 404 on re-delete). The `delete_item` DDB call itself is always safe — DynamoDB silently no-ops a delete of a non-existent key; the 404 is the service-layer decision.

### Security

**Public read endpoints** carry no auth. They are listed in `API_KEY_ROUTE_EXEMPTIONS` so the API-key metering middleware does not reject them with 401/403. They return no user-specific data, no PII, and no financial information. The only risk is enumeration of internal terminology by anonymous callers, which is acceptable for a public API dictionary.

**Admin mutation endpoints** are gated by `_require_admin_user`, which validates the caller's `user_sub` against `S.filemgr_admin_users`. An unauthenticated caller receives 401 from `require_ui_session` before `_require_admin_user` runs. A non-admin authenticated caller receives 403.

**No CSRF risk on public reads.** The `GET` endpoints carry no session cookie requirement and perform no state mutations. The admin `POST`/`PATCH`/`DELETE` endpoints use `require_ui_session` via `_current_user` → `_require_admin_user`; non-GET requests from cookie-authenticated sessions enforce CSRF via the existing middleware (`app/auth/deps.py`).

**Definition content.** Definitions are markdown strings stored verbatim and returned verbatim. Sanitization (HTML escaping, XSS prevention) is the responsibility of the client rendering layer. The backend performs no sanitization beyond the length cap.

### Money-safety

Not applicable. This ticket writes no ledger rows, initiates no payments, calls no billing service, and touches no wallet or subscription state. There is no interaction with `billing_shared.py`, `tip_ledger.py`, or any payment provider SDK.

## 8. Backward Compatibility & Migration

### Additive only

No existing table is modified. No existing endpoint changes signature. No existing model gains a new required field. No existing middleware or startup hook changes.

### Table creation

`scripts/local-ddb-init.py` gains one `TableDef` entry for the `glossary` table. Running `just restart` in the local dev stack recreates all tables from scratch; no migration is required in dev.

In production, the `glossary` table must be created before `GLOSSARY_ENABLED=1` is deployed. The recommended sequence:

1. Deploy the code with `GLOSSARY_ENABLED=0` — the router is not registered; the settings and table handle are loaded but dormant.
2. Run the DynamoDB `CreateTable` call for the `glossary` table (use the `TableDef` parameters from `local-ddb-init.py`).
3. Set `GLOSSARY_ENABLED=1` and redeploy. The router registers and begins serving.

No DDB table backfill is required because the glossary starts empty. Seed data can be loaded via `POST /v1/admin/glossary` after the feature is enabled.

### Versioning

The `/v1/glossary` path matches the existing `/v1/*` API surface used for file manager, newsfeed, and API-usage routes. If the glossary schema changes in a future ticket, a `/v2/glossary` path can be introduced without removing `/v1/glossary`.

### `API_KEY_ROUTE_EXEMPTIONS` entry

Adding two entries to the `API_KEY_ROUTE_EXEMPTIONS` dict in `api_key_route_scope_registry.py` is backward compatible. Existing entries are never removed. The dict is an in-memory constant loaded at startup; no DDB migration is required.

## 10. Open Questions / Assumptions

1. **Term uniqueness.** The spec deliberately omits a unique constraint on `term`. OBP's own glossary allows two entries with the same term slug in different contexts (e.g., `"amount"` in the transaction domain and `"amount"` in the balance domain, differentiated by tags). If the platform requires uniqueness, a second GSI on `term` with a conditional write check can enforce it — left as a follow-up.

2. **Admin allowlist reuse.** `_require_admin_user` (`admin_usage.py:35`) reads from `S.filemgr_admin_users`. This conflates "file-manager billing admin" with "glossary editor". A future `GLOSSARY_ADMIN_USERS` setting can decouple them; for now the shared allowlist is simpler and consistent with the existing `admin_usage.py` pattern.

3. **Alphabetical sort vs. weighted relevance for search.** The `?search=` filter returns terms in alphabetical order matching the underlying GSI traversal. This is adequate for small corpora. If a relevance-ranked search is needed, a future ticket can add a secondary `search_index_table` using the existing search-token primitives (`app/services/search.py`).

4. **Tag-based filtering.** The current design does not support `?tag=transactions` filtering. Tags are an informational field only. A `GSI_BY_TAG` can be added in a follow-up ticket if tag-filtered queries are needed by OBP client tools.

5. **Maximum number of terms.** No global cap on total terms is enforced. For the expected use case (API documentation dictionary with a few hundred to a few thousand terms), the glossary table will remain well under DynamoDB free-tier limits. A `GLOSSARY_MAX_TERMS` setting could be added if needed.

6. **PATCH route ordering.** `PATCH /v1/admin/glossary/{term_id}` and the eventual future `GET /v1/admin/glossary/{term_id}/history` (audit trail) share a path prefix. FastAPI matches routes in declaration order. The `PATCH` route is declared before any hypothetical sub-resource route, so no collision exists today. Future sub-resource routes must be declared first (same pattern as audit_export_schedule.py where `/schedules` is declared before `/{export_id}`).

7. **Internationalization.** `term` and `definition` are stored as-is. No language codes are stored. If multilingual glossaries are required (e.g., `term_en`, `term_de`), that is a follow-up schema change.
