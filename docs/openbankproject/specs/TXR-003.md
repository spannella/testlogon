# TXR-003 — Step-up SCA challenge — mint OTP on threshold, hold request PENDING

**Ticket prefix**: TXR | **Priority**: P1 | **Estimate**: 3 days
**Source**: `docs/openbankproject/OBP_TXN_REQUESTS_SCA_TICKETS.md` §TXR-003
**Feature flag**: `TXN_REQUESTS_ENABLED` (default `false`, shared with TXR-001/002)

---

## 1. Summary & Goal

When a transaction request exceeds an amount threshold **or** is of a sensitive type (`PAYOUT`, `REFUND`, `COUNTERPARTY`), the system must hold it `PENDING` behind a step-up Strong Customer Authentication challenge before any money moves. This ticket wires the existing MFA/challenge stack directly into the `create_request` path introduced in TXR-001 and extended in TXR-002.

Concretely: after TXR-001 records an `INITIATED` item and TXR-002 validates per-type amount limits, `create_request` now calls `_sca_required(user_sub, type, amount_cents)`. When the decision is `true`, it immediately transitions the item `INITIATED → PENDING`, mints a challenge via `sessions.create_stepup_challenge(req, user_sub, required_factors, purpose="txn_request_sca")` (which correctly seeds both `required_factors` and the `passed` map — `create_action_challenge` does neither), stamps `sca_challenge_id` onto the request item, and returns a `TxnRequestOut` with `status="PENDING"`, `sca_challenge_id`, and `required_factors`. The caller then drives the **existing, unchanged** `/ui/mfa/{totp,sms,email}/verify` endpoints with that `challenge_id`; TXR-004 checks `sessions.challenge_done(chal)` before executing.

No new OTP codes, send paths, or cryptographic primitives are introduced. The MFA stack in `app/services/mfa.py` and `app/routers/ui_mfa.py` is reused verbatim. Dev-mode mock OTP codes and prod Twilio/SES delivery are inherited without any `if S.dev_mode` branches in the request engine (SECOPS-007).

## 3. Data Model

### No new DynamoDB table

TXR-003 reuses two existing tables:

**`txn_requests` table** (introduced in TXR-001, `TableDef` in `scripts/local-ddb-init.py`):
- PK `user_sub` (S), SK `request_id` (S, prefix `txr_`)
- GSI `GSI_STATUS`: PK `status` (S) / SK `created_at` (N) — `attr_types={"created_at": "N"}` already required by TXR-001
- TXR-003 adds two attributes to the item written at create time (or updated during the INITIATED→PENDING transition):
  - `sca_challenge_id` (S | absent) — the `challenge_id` returned by `create_stepup_challenge`; absent when SCA was not required
  - `sca_required_factors` (List[S] | absent) — snapshot of `required_factors` at challenge mint time; stored so callers can surface this without re-reading `T.sessions`

**`sessions` table** (`T.sessions`, PK `user_sub`, SK `session_id`):
- Challenge items written by `create_stepup_challenge` carry:
  - `pending_auth: True` (required by `load_challenge_or_401` at `sessions.py:519`)
  - `purpose: "txn_request_sca"` (prevents `maybe_finalize` from completing a login at `sessions.py:657`)
  - `required_factors: List[str]` — from `compute_required_factors(user_sub)` (or the fallback list `["email"]`)
  - `passed: {factor: False for factor in required_factors}` — updated by `mark_factor_passed`
  - `expires_at: int` — `now_ts() + ttl_seconds` (default `S.session_challenge_ttl_seconds = 300`)
  - `request_id: str` — stamped as payload so the challenge is traceable to the TXR item without a separate lookup
  - `amount_cents: int`, `txn_type: str` — stamped as payload for audit context
  - TTL attribute via `with_ttl(item, ttl_epoch=expires_at)` (`app/services/ttl.py:5`)

No new GSIs or attribute-type declarations are required for TXR-003. All writes go to existing tables with existing key schemas.

## 4. API / Service Design

### 4.1 New settings (`app/core/settings.py`)

```python
txn_request_sca_threshold_cents: int = int(
    os.environ.get("TXN_REQUEST_SCA_THRESHOLD_CENTS", "5000")
)
# Comma-separated sensitive types that always require SCA regardless of amount.
# Default: PAYOUT,REFUND,COUNTERPARTY (money leaving platform / reversing a charge).
_sca_sensitive_raw: str = os.environ.get(
    "TXN_REQUEST_SCA_SENSITIVE_TYPES", "PAYOUT,REFUND,COUNTERPARTY"
)
txn_request_sca_sensitive_types: frozenset = frozenset(
    t.strip().upper() for t in _sca_sensitive_raw.split(",") if t.strip()
)
```

These join the existing `txn_requests_enabled` / per-type limit settings from TXR-002.

### 4.2 Service layer — `app/services/txn_requests.py`

**`_sca_required(user_sub: str, txn_type: str, amount_cents: int) -> tuple[bool, list[str]]`**

```
Inputs:
  user_sub        str  — caller identity
  txn_type        str  — one of TxnRequestType enum values
  amount_cents    int  — validated positive integer

Returns:
  (required: bool, factors: list[str])
  required = True  iff:
    amount_cents >= S.txn_request_sca_threshold_cents
    OR txn_type.upper() in S.txn_request_sca_sensitive_types
  factors = compute_required_factors(user_sub) when required
  If required but factors is empty (no enrolled devices):
    factors = ["email"]   (fallback: email OTP to account email)
  If required=False: factors = []
```

Does not call `create_stepup_challenge` itself. Pure decision function — no I/O except the three DDB reads inside `compute_required_factors`.

**`_mint_sca_challenge(req: Request, user_sub: str, request_id: str, txn_type: str, amount_cents: int, required_factors: list[str]) -> str`**

```
Calls:
  sessions.create_stepup_challenge(
      req,
      user_sub,
      required_factors,
      purpose="txn_request_sca",
  )
Then stamps extra payload onto the challenge item:
  T.sessions.update_item(
      Key={"user_sub": user_sub, "session_id": challenge_id},
      UpdateExpression="SET request_id=:r, amount_cents=:a, txn_type=:t",
      ExpressionAttributeValues={":r": request_id, ":a": amount_cents, ":t": txn_type},
  )
Returns: challenge_id (str)
```

Alternative: use `create_action_challenge(req, user_sub, purpose="txn_request_sca", send_to=[], payload={...}, ttl_seconds=S.session_challenge_ttl_seconds)` which merges the payload dict onto the item in a single `put_item`. Either approach is acceptable; `create_stepup_challenge` + a follow-up `update_item` is preferred because it correctly seeds the `passed` map (which `create_action_challenge` does not — it does not set `required_factors` or `passed`). **Choose `create_stepup_challenge`** and add the payload fields via the follow-up update.

**`create_request(user_sub: str, body: TxnRequestCreateIn, req: Request) -> TxnRequestOut`** — extended from TXR-001

After TXR-002's `enforce_amount_limit(body.type, body.amount_cents)` passes, the function now:

1. Writes the `INITIATED` item as before (TXR-001).
2. Calls `_sca_required(user_sub, body.type, body.amount_cents)`.
3. **If `required=False`**: returns `TxnRequestOut(status="INITIATED", sca_challenge_id=None, required_factors=[])`. No transition — TXR-004 will execute directly from `INITIATED`.
4. **If `required=True`**:
   a. Calls `_mint_sca_challenge(req, user_sub, request_id, body.type, body.amount_cents, factors)` → `challenge_id`.
   b. Calls `_transition(user_sub, request_id, expected_status="INITIATED", new_status="PENDING", sca_challenge_id=challenge_id, sca_required_factors=factors)` — a conditional `update_item` asserting `status = "INITIATED"`. On `ConditionalCheckFailedException`: log and surface as `409 invalid_transition` (should never happen on a freshly written item but defended nonetheless).
   c. Calls `audit_event("txn_request.sca_required", user_sub, req, request_id=request_id, challenge_id=challenge_id, amount_cents=body.amount_cents, txn_type=body.type)`.
   d. Returns `TxnRequestOut(status="PENDING", sca_challenge_id=challenge_id, required_factors=factors)`.

## 5. Detailed Behavior & Edge Cases

### 5.1 SCA decision matrix

| `txn_type` | `amount_cents` | `amount >= threshold` | `type in sensitive_set` | SCA? |
|---|---|---|---|---|
| `WALLET_TRANSFER` | 1 000 ($10) | No | No | No — `INITIATED`, execute immediately |
| `WALLET_TRANSFER` | 10 000 ($100) | Yes | No | Yes — `PENDING` |
| `FREE_FORM` | 1 000 | No | No | No |
| `PAYOUT` | 100 ($1) | No | **Yes** | Yes — always |
| `REFUND` | 100 | No | **Yes** | Yes — always |
| `COUNTERPARTY` | 100 | No | **Yes** | Yes — always |

### 5.2 No enrolled factors — fallback

`compute_required_factors(user_sub)` returns `[]` when the user has no enabled TOTP/SMS/EMAIL device. TXR-003 falls back to `required_factors = ["email"]`. The `POST /ui/mfa/email/begin` route (`ui_mfa.py:150`) then sends an OTP to the account email address. If the account has no verified email, `email/begin` will raise `400 No email devices`; the SCA challenge is already written (revoke it) and the request should transition `PENDING → FAILED` with `failure_reason="sca_no_factor"`. This fallback-failure path must be handled in TXR-004's execute precondition check (or surface as a `POST /ui/txn-requests/{id}/cancel` endpoint in a follow-up).

Optionally, the security review may decide to raise `409 sca_enrollment_required` at create time instead of falling back to email; the design above defaults to the email-fallback path and documents the alternative.

### 5.3 Challenge TTL and expiry

The challenge expires after `S.session_challenge_ttl_seconds` (default 300 s, env `SESSION_CHALLENGE_TTL_SECONDS`). After expiry `load_challenge_or_401` raises `401 Challenge expired` (checked at `sessions.py:521-527`). The request item stays `PENDING` indefinitely — a sweep job (not part of this ticket) should time out stale `PENDING` requests; TXR-004 will surface `401` from the verify step and the request can be re-initiated. A separate `TXN_REQUEST_PENDING_TIMEOUT_SECONDS` setting (TXR-002 scope) governs request-level expiry.

### 5.4 Concurrent duplicate creates

Two concurrent `POST /ui/txn-requests` with the same `idempotency_key` (TXR-001 dedup logic) collapse to one INITIATED item before TXR-003 runs. Two requests without an idempotency key produce two independent INITIATED items, each getting their own challenge — correct.

The `_transition(INITIATED → PENDING)` conditional `update_item` asserts `status = "INITIATED"`. A losing concurrent transition gets `ConditionalCheckFailedException` and returns `409`. Because the challenge item is written **before** the transition, a lost-transition race leaves an orphaned challenge item in `T.sessions`; this is safe — it expires via DDB TTL and `maybe_finalize` won't consume it (the `purpose` guard at `sessions.py:657`). The winning path's challenge is correctly bound to the PENDING item.

### 5.5 SCA challenge is single-use

`revoke_challenge` is called by TXR-004 on successful execute. A second execute attempt on a `COMPLETED` request short-circuits via status-lock before ever loading the (already-revoked/absent) challenge. The challenge cannot be re-used to authorize a different transaction request because it carries `request_id` in its payload (verified by TXR-004 by reading `chal["request_id"]` and asserting it matches the path `{request_id}`).

### 5.6 `maybe_finalize` does NOT consume SCA challenges

`sessions.maybe_finalize` at line 657 returns `None` when `chal.get("purpose")` is truthy. `"txn_request_sca"` is non-empty, so a TXR SCA challenge can never accidentally create a browser session — the guard is already in place with no code change required.

### 5.7 Rate limiting on OTP verify attempts

Inherited unchanged from `rate_limit.py:175` — `rate_limit_mfa_verify(user_sub, ip, factor)` enforces `S.mfa_verify_max_per_window` (default 10) attempts per `S.mfa_verify_window_seconds` (default 600 s) per user+factor, and per-IP. No additional rate limiting is added by TXR-003.

### 5.8 Webhook events

`txn_request.sca_required` (and `txn_request.sca_passed`) are registered in `WEBHOOK_EVENT_TYPES_V2` (`app/services/webhook_service.py:60`) by TXR-001 §6 alongside the rest of the `txn_request.*` set (`txn_request.created` / `.sca_required` / `.sca_passed` / `.executed` / `.failed`). As of the current codebase no `txn_request.*` events appear in `WEBHOOK_EVENT_TYPES_V2` yet — TXR-001 adds them. There is **no `emit_txn_event` helper** in the codebase, and TXR-001 does not introduce one: per TXR-001 §6, webhook dispatch uses the EXISTING `webhook_service.dispatch_webhook_event(event_type, user_sub, data)` (`webhook_service.py:556`) directly. TXR-003 therefore calls `audit_event` synchronously for `txn_request.sca_required` / `txn_request.sca_passed`, then emits the corresponding webhook best-effort via `webhook_service.dispatch_webhook_event(...)` (try/except, non-blocking) — NOT via an invented `emit_txn_event` helper.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

**Dev/prod parity.** `create_stepup_challenge` writes to DDB Local in dev (same code path as prod). `mfa.send_email_code` at `mfa.py:57` already branches on `S.dev_mode` to write to `S.dev_email_log` and `stderr` instead of SES — this is the existing provider abstraction, not a business-logic branch in `txn_requests.py`. Twilio (SMS) uses the same pattern. **No `if S.dev_mode` branch lives in `txn_requests.py` or `_sca_required`.**

**Challenge integrity.** The `challenge_id` is an unguessable 128-bit hex string prefixed with `"chal_"` (from `create_stepup_challenge` at `sessions.py:602`: `"chal_" + uuid.uuid4().hex`). Note: if `create_action_challenge` were used instead it would produce a `"txn_request_sca_"` prefix, but `create_stepup_challenge` is the correct choice here (see §4.2). It is stored in `T.sessions` keyed on `user_sub`; a different user cannot load it (`load_challenge_or_401` key = `{user_sub, challenge_id}` — foreign challenge → item-not-found → 401).

**Binding challenge to request.** `chal["request_id"]` is stamped onto the challenge item. TXR-004 asserts `chal["request_id"] == path_request_id` before accepting the challenge as satisfied. This prevents a user from reusing a challenge from one transaction request to authorize a different one.

**Money-safety.** TXR-003 holds the request `PENDING` — no money moves. The `PENDING` status is the lock: `apply_wallet_delta`, `request_payout`, and `refund_payment` are only reached inside TXR-004's execute path, which is gated on `challenge_done(chal)`. A PENDING request with an unsatisfied challenge cannot reach any money-movement primitive.

**OTP secrets never leave the server.** The client receives only `challenge_id` and `required_factors`. The OTP code is delivered out-of-band (Twilio/SES in prod; dev log in dev). The server verifies the code via `mfa.py` internal helpers.

**Idempotency.** `create_request` is idempotent via the `idempotency_key` dedup from TXR-001. The SCA challenge is minted at most once per request: `_transition(INITIATED → PENDING)` is conditional — if it fails the item is already PENDING with an existing challenge, and the function returns the existing `TxnRequestOut` without minting a second challenge.

**CSRF.** `POST /ui/txn-requests` uses `Depends(require_ui_session)` which enforces the `x-csrf-token` header for non-GET requests (`auth/deps.py`). No new auth dependency is needed.

## 8. Backward Compatibility & Migration

**Additive only.** The `sca_challenge_id` and `sca_required_factors` attributes are optional on the `txn_requests` table. Pre-existing items (none exist today, since the table is new in TXR-001) and any test items created before TXR-003 deploys simply lack these fields — `TxnRequestOut` uses `Optional[str] = None` and `list[str] = []`.

**No DDB schema change.** TXR-003 adds attributes to existing items; it does not add new GSIs or change the table's key schema. No `UpdateTable`, backfill, or migration script is needed.

**Existing billing and MFA endpoints are untouched.** The `/ui/mfa/*` verify endpoints work identically for SCA challenges and login challenges — the `purpose` field on the challenge item is checked only by `maybe_finalize` (not by any verify route). Driving verify with a `txn_request_sca` challenge_id has exactly the same effect as driving it with a login challenge: `mark_factor_passed` writes one attribute, `challenge_done` reads it.

**Flag-off behavior.** With `TXN_REQUESTS_ENABLED=false`, the `txn_requests` router is not registered in `app/main.py` and all new endpoints return 404. The `_sca_required` function, `_mint_sca_challenge`, and the extended `create_request` code path are never reached.

## 10. Open Questions / Assumptions

1. **No-factor rejection vs. email fallback.** The spec defaults to `required_factors = ["email"]` when the user has no enrolled device. The security review may decide that a zero-factor state should instead return `409 sca_enrollment_required` at create time to force enrollment before any high-value transfer. The implementation should make this a single conditional branch gated by a new `TXN_REQUEST_SCA_REQUIRE_ENROLLED_FACTOR` bool setting (default `false` = use email fallback).

2. **Challenge TTL vs. request PENDING timeout.** The challenge TTL (`SESSION_CHALLENGE_TTL_SECONDS`, 300 s by default) is much shorter than a realistic user session. Should there be a separate `TXN_REQUEST_SCA_CHALLENGE_TTL_SECONDS` (default e.g. 600 s) to give more time for out-of-band OTP delivery? The current design reuses `S.session_challenge_ttl_seconds` for simplicity; a dedicated setting is straightforward to add.

3. **PENDING request with expired challenge — re-initiation flow.** When the SCA challenge expires the request stays `PENDING`. The user cannot re-mint a challenge for an existing PENDING request without a `POST /ui/txn-requests/{id}/refresh-sca` endpoint (not in scope for this ticket). For now, the user cancels and creates a new request. A `refresh-sca` endpoint is deferred to a follow-up.

4. **Webhook for `txn_request.sca_required`.** `WEBHOOK_EVENT_TYPES_V2` must include this event key. The assumption is that TXR-001 adds all `txn_request.*` keys in a single batch; TXR-003 only fires the event, it does not define the taxonomy.

5. **Sensitive-type set is env-configurable.** The default `PAYOUT,REFUND,COUNTERPARTY` may be too broad for some deployments (e.g., internal `REFUND` operations by admins should perhaps bypass SCA). An admin-bypass path is out of scope; the env var gives operators control at deploy time.
