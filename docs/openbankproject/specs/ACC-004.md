# ACC-004 — Account-holder co-access — multi-owner + view-based co-access on the account

**Ticket type**: Backend (ownership grants + view binding)
**Priority**: P2
**Estimate**: 3 days
**Depends on**: ACC-001 (account entity, default-account bootstrap, ownership resolution), ACC-002 (transaction list projection), ACC-003 (transaction metadata). **Soft dependency** on VEW-001/VEW-002/VEW-003 (account views — view binding is a no-op when the VEW flag is off).
**Flag**: `banking_account_views_enabled` (env `BANKING_ACCOUNT_VIEWS_ENABLED`, default OFF) — gates the view-based co-access read path. Multi-owner CRUD is gated only by the parent `banking_accounts_enabled` flag.

---

## 1. Summary & Goal

ACC-004 makes a bank account shareable in two orthogonal ways that mirror OBP's "account holders + Views" design:

1. **Multi-owner (co-holders).** A primary account owner can grant a second user full read/write access to the account by adding them as a co-owner. Co-owners are treated identically to the primary owner by every ACC endpoint. The grant is materialized as a reverse-index row in the `banking_accounts` table so the new owner's `list_accounts` call (ACC-001) surfaces the shared account automatically.

2. **View-based co-access (field-level scoped read).** The account owner binds the account to the VEW Account-View primitive (VEW-001/002/003) — granting a *specific named view* (e.g. `auditor`, `accountant`, `public`) to another user. That grantee can then call the ACC-001/002/003 GET endpoints, but receives only the fields the view's `grants` map permits. ACC-004 does NOT reimplement the view or grant machinery; it consumes the VEW service by calling `resolve_active_grant` and `project_resource` from `app/services/account_views.py`.

The net effect: ACC reads become *access-aware*. Every GET handler in ACC-001/002/003 gains a two-step authorization: (a) owner/co-owner check (full access, no projection), then (b) VEW grant check (if `banking_account_views_enabled`, scoped access, projected response). A caller with neither a co-owner entry nor a VEW grant receives 404 — no information leak.

No money-moving code is touched. No billing primitives are forked. The wallet/ledger (`app/services/billing_shared.py:173,176,224`) remains the single source of truth for money; co-owners or view-holders reading balances and transactions still read through to `T.billing` via the same ACC-002 projection.

## 3. Data Model

### Existing table: `banking_accounts` (introduced by ACC-001)

ACC-004 writes two new row types and reads the existing account row. No new table is needed.

**Table**: `banking_accounts` — `pk` (S, partition key), `sk` (S, sort key). `GSI_ACCOUNT_BY_ID`: partition key `account_id` (S), sort key `created_at` (N). Settings key `S.banking_accounts_table_name` (env `BANKING_ACCOUNTS_TABLE_NAME`, default `"banking_accounts"`). Handle at `T.banking_accounts` (`app/core/tables.py`). Declared in `scripts/local-ddb-init.py` with `attr_types={"created_at": "N"}` — required because `created_at` is a numeric GSI sort key; omitting `attr_types` causes a `ValidationException` at runtime (CLAUDE.md "DynamoDB numeric GSI sort keys").

**Row type 1 — Co-owner reverse-index row** (written by `add_account_owner`, deleted by `remove_account_owner`):

```
pk  = "USER#{co_owner_sub}"
sk  = "ACCOUNT_REF#{account_id}"
account_id   : str    # the shared account id
owner_sub    : str    # primary owner's sub — needed to resolve the full account row
              #        (full row lives at pk=USER#{owner_sub}, sk=ACCOUNT#{account_id})
added_by_sub : str    # the sub who granted co-ownership (audit)
added_at     : int    # Unix timestamp (now_ts())
```

This is the row shape ACC-001 already documents as belonging to the schema — ACC-004 is the ticket that populates it. On `list_accounts` (ACC-001), a query on `pk=USER#{viewer_sub}` returns both `ACCOUNT#` owned rows and `ACCOUNT_REF#` shared rows; the service resolves each `ACCOUNT_REF#` row via `GSI_ACCOUNT_BY_ID` to get the full account.

**Row type 2 — Holder audit log row** (in-table record, mirrors the `AUDIT#` pattern used by delegates):

```
pk  = "USER#{owner_sub}"
sk  = "HOLDER_AUDIT#{account_id}#{ts}#{event_id}"
account_id   : str
event        : str    # "holder.added" | "holder.removed"
actor_sub    : str
target_sub   : str
ts           : int
event_id     : str    # uuid4().hex[:10]
```

These rows are append-only and are never queried by the core read path — they exist for per-account audit history (accessible via `list_holder_audit_events` for owner/admin). No GSI is needed; a `begins_with("HOLDER_AUDIT#{account_id}#")` query on the owner partition suffices.

**Account row mutation** (`add_account_owner` / `remove_account_owner`): the `owners` list attribute on the account row `pk=USER#{owner_sub}`, `sk=ACCOUNT#{account_id}` is updated atomically via a `list_append` / `delete` `UpdateExpression`. The conditional guard `attribute_exists(owners)` ensures the row exists; a version-bump or conditional check is not required because co-owner mutations are owner-only and the `owners` list is a set-like DDB List attribute (duplicates are rejected in service logic before the write).

### No new table, no new GSI required

All row types above fit in the existing `banking_accounts` table. The `GSI_ACCOUNT_BY_ID` index (already declared by ACC-001 with `attr_types={"created_at": "N"}`) is sufficient for resolving accounts by id from co-owner reverse-index rows.

## 4. API / Service Design

### Service: `app/services/banking_accounts.py` (additions)

All functions added to the existing `banking_accounts.py` module introduced by ACC-001.

```python
def add_account_owner(
    account_id: str,
    caller_sub: str,
    new_owner_sub: str,
) -> dict:
    """
    Grant co-ownership of account_id to new_owner_sub.
    Caller must already be in account.owners (owner-only gate).
    Raises HTTPException(404) if account not found.
    Raises HTTPException(403) if caller is not an owner.
    Raises HTTPException(400) if new_owner_sub already in owners (idempotent guard).
    Raises HTTPException(400) if new_owner_sub == caller_sub (self-grant guard).
    Writes ACCOUNT_REF# reverse-index row under new_owner_sub partition.
    Appends new_owner_sub to owners list on the account row.
    Emits audit_event("account.holder.added", caller_sub, ...).
    Writes in-table HOLDER_AUDIT# row.
    Returns updated account dict.
    """

def remove_account_owner(
    account_id: str,
    caller_sub: str,
    target_sub: str,
) -> dict:
    """
    Removes target_sub from co-ownership.
    Caller must be an owner.
    Raises HTTPException(409) if target_sub is the last owner (cannot remove last owner).
    Raises HTTPException(400) if target_sub is not a current owner.
    Deletes ACCOUNT_REF# reverse-index row under target_sub partition.
    Removes target_sub from owners list on the account row.
    Emits audit_event("account.holder.removed", caller_sub, ...).
    Writes in-table HOLDER_AUDIT# row.
    Returns updated account dict.
    """

def list_account_holders(
    account_id: str,
    requester_sub: str,
) -> list[dict]:
    """
    Returns [{user_sub, added_at, is_primary_owner}, ...] for every owner.
    Caller must be an owner (404 otherwise — no info leak).
    Resolves via GSI_ACCOUNT_BY_ID, then reads account.owners list.
    Primary owner = first element of owners list (insertion order is preserved).
    """

def resolve_account_access(
    caller_sub: str,
    account_id: str,
) -> dict:
    """
    Returns {"role": "owner" | "viewer" | None, "view_id": str | None, "grants": dict | None}
    Step 1: resolve account via GSI_ACCOUNT_BY_ID (404 if not found).
    Step 2: if caller_sub in account.owners → return {"role": "owner"}.
    Step 3: if S.banking_account_views_enabled:
               try: from app.services.account_views import resolve_active_grant
               except ImportError: pass
               else: # view_id must be supplied — pass it from the caller context or query param.
                     # resolve_active_grant(grantee_sub, resource_type, resource_id, view_id: str)
                     # is a DDB point-read (sk=VIEWGRANT#{grantee_sub}#{view_id}); it does NOT
                     # accept None and there is no "first active grant" scan in VEW-002.
                     # Implementation must obtain view_id from the request (e.g. ?view_id= query
                     # param) or list the caller's active grants via list_views_shared_with_me
                     # and pick one before calling resolve_active_grant.
                     # For the first implementation, require an explicit view_id param; if absent,
                     # fall through to 404.
                     if view_id:
                         grant = resolve_active_grant(caller_sub, "account", account_id, view_id)
                         if grant: return {"role": "viewer", "view_id": grant["view_id"], "grants": grant["grants"]}
    Step 4: return {"role": None} → callers raise HTTPException(404).
    Never 403 on a non-owner — always 404 to prevent account-id enumeration.
    """
```

The `resolve_account_access` function is the integration seam between ACC and VEW. Every ACC-001/002/003 GET handler that currently checks `caller_sub in account.owners` is updated to call `resolve_account_access` instead, and if `role == "viewer"` it passes the response dict through `project_resource` before serializing.

### Router: `app/routers/banking_accounts.py` (additions)

Three new endpoints, added to the existing router registered at prefix `/ui/banking`. All use `Depends(require_ui_session)` and enforce CSRF on non-GET (CLAUDE.md auth pattern).

```
GET    /ui/banking/accounts/{account_id}/holders
         → list_account_holders(account_id, caller_sub)
         Response: 200 {holders: [{user_sub, added_at, is_primary_owner}]}

POST   /ui/banking/accounts/{account_id}/holders

The `/holders` literal segment is not ambiguous with any existing dynamic path.

### ACC-001/002/003 GET handler updates (integration points)

Every read handler in the banking router that currently asserts ownership via a direct `owners` list check is updated to use `resolve_account_access`:

## 5. Detailed Behavior & Edge Cases

### Multi-owner co-access

**Adding a co-owner — atomicity.** The sequence is: (1) write the `ACCOUNT_REF#` reverse-index row, (2) `list_append` to the `owners` attribute on the account row. If step 2 fails after step 1 succeeds (e.g. DDB transient error), the `ACCOUNT_REF#` row exists but the `owners` list is stale. On the next `add_account_owner` call, the service detects `new_owner_sub in account.owners` (idempotent guard via `get_account` resolution) and skips the `owners` append; the `ACCOUNT_REF#` row is then a no-op re-write. To avoid this inconsistency entirely, the implementation MAY use a DDB `TransactWriteItems` (two put-item operations in one transaction). If not using TransactWrite, the idempotent guard on both rows ensures eventual consistency.

**Removing the last owner.** `remove_account_owner` resolves the account, checks `len(account["owners"]) == 1 and target_sub == account["owners"][0]`, and raises `HTTPException(409, "Cannot remove the last account owner")`. This mirrors `delete_account`'s 409 guard on the default account (ACC-001) and `org_service`'s last-owner protection pattern.

**Self-removal.** An owner may remove themselves if they are not the last owner. `remove_account_owner(caller_sub=X, target_sub=X)` is valid if `len(owners) > 1`. This allows voluntary exit from a shared account. After self-removal the caller's `ACCOUNT_REF#` row is deleted and the account no longer appears in their `list_accounts`.

**Default wallet-backed account and co-ownership.** A co-owner added to the default `WALLET` account (`wallet_backed=True`) sees the PRIMARY OWNER'S balance when they call `GET /ui/banking/accounts/{id}/balance`. The balance read-through is `billing_shared.get_wallet_balance(T.billing, user_pk(primary_owner_sub))` — the primary owner's `USER#{sub}` partition, not the co-owner's. This is correct: the wallet is the primary owner's money. The co-owner can read it but cannot withdraw (no money-out endpoint exists in ACC scope). A comment in the handler documents this.

**Co-owner and `list_accounts`.** ACC-001's `list_accounts` already queries `pk=USER#{sub}` + `sk begins_with "ACCOUNT_REF#"` and resolves each via `GSI_ACCOUNT_BY_ID`. With ACC-004 writing `ACCOUNT_REF#` rows, shared accounts automatically appear. The co-owner sees `account.owners` including themselves, confirming their status.

### View-based co-access

**VEW not deployed / flag off.** When `S.banking_account_views_enabled` is `False`, `resolve_account_access` never attempts to import `account_views`. The `try/except ImportError` guard around the `project_resource` call in each GET handler means a non-owner with no co-ownership entry always gets 404. There is no partial-access mode: if VEW is not enabled, only full owners/co-owners get access.

**view_id resolution.** `resolve_active_grant` in VEW-002 requires `view_id: str` — it is a DDB point-read keyed on `sk=VIEWGRANT#{grantee_sub}#{view_id}` and does NOT support `view_id=None` or any "first active grant" scan (VEW-002 spec §3.3: "Pure DDB point-read — no GSI scan"). ACC-004's `resolve_account_access` must therefore receive the `view_id` from the caller (e.g. an optional `?view_id=` query parameter on the ACC read endpoints). When `view_id` is absent, the VEW branch is skipped and the non-owner caller receives 404. If a grantee holds multiple active views on one account (e.g. both `accountant` and `auditor`), they must pass a specific `view_id`; the ACC read endpoints do not pick on their behalf. [CORRECTED from original spec which incorrectly described view_id=None as valid and claimed VEW would return the broadest grant — VEW-002 defines no such behavior.]

**Projection completeness.** `project_resource(resource, grants, "account")` strips any field whose grant key is not `True` in the grants map. Fields not in `FIELD_TO_GRANT["account"]` are always stripped — deny-by-default. The owner's own read path is never projected (fast path: `role == "owner"` → skip `project_resource` entirely).

**`iban` field hiding.** An `auditor` view that omits `can_see_account_iban` (if such a grant key is defined in VEW's `VIEW_FIELD_GRANTS`) will cause `iban` to be absent from the response. Acceptance criterion: verify `iban` is absent in the projected response for an auditor-view grantee.

**Public view path.** VEW-002 defines an unauthenticated signed-token endpoint `GET /ui/views/public/{token}` that calls `resolve_public_view(token)` and then passes the resource through `project_resource`. For a resource of type `"account"`, that means calling `get_account(account_id)` (ACC-001) and projecting it. This path is owned entirely by the VEW router and requires no changes to the ACC router — the public view endpoint resolves `resource_type="account"` and `resource_id=account_id` and calls the ACC service for the raw data, which VEW then projects before responding.

**No money-out through a view.** View-based grantees have read-only access. The co-access mechanism exposes no write or money-moving endpoints (there are no `POST /holders` analogues in the viewer path). Write access is strictly owner/co-owner only. This invariant is enforced by the access check in each handler: write-path handlers (`PATCH /accounts/{id}`, `PUT .../narrative`, etc.) only accept `role == "owner"` and raise 404 on any other.

### Concurrent mutations

If two owners simultaneously call `add_account_owner` with different `new_owner_sub` values, both operations are `list_append` on the `owners` attribute. DDB's conditional update on the base account row is not strictly required here because `list_append` is atomic at the item level; however the service checks for duplicates via `get_account` before writing. A small race window exists where both callers pass the duplicate check and both append — the result is a duplicated `sub` in the `owners` list. Guard: `add_account_owner` deduplicates by checking `new_owner_sub in account["owners"]` at read time and using the `attribute_not_exists` or `contains` condition expression. The simpler approach — acceptable for P2 — is to use DDB's `ADD` expression on a StringSet attribute instead of a List, which naturally deduplicates.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 dev/prod parity

All persistence in ACC-004 goes through `T.banking_accounts` (a `_FloatSafeTable` handle, `app/core/tables.py:29`) — DynamoDB Local on port 8001 in dev, real DynamoDB in prod. There are no `if S.dev_mode:` branches in any service function. The `ACCOUNT_REF#` row write, the `owners` list append, and the `HOLDER_AUDIT#` row write all use the same code path in both environments.

VEW integration (`resolve_active_grant`, `project_resource`) uses `try/except ImportError` — a module-presence guard, not an environment check. Both dev and prod will have the VEW module present once VEW is deployed. The guard exists only to let ACC-004 ship before VEW.

### Idempotency

- **`add_account_owner` is idempotent on the `ACCOUNT_REF#` row**: a second call with the same `new_owner_sub` hits the duplicate check (`new_owner_sub in account["owners"]`) and returns 400 *before* writing. The caller can distinguish "already an owner" from a first-time grant by the 400 response. If truly idempotent behavior (200 for repeat calls) is needed, the service can switch to a `PUT`-style upsert; the ticket spec keeps 400 as the guard to match `delegates.py:364` `_require_not_already_delegate`.
- **`remove_account_owner` is safe to retry**: if the `ACCOUNT_REF#` delete succeeds but the `owners` list remove fails, the next retry re-reads the account, finds `target_sub` still in `owners`, and re-executes the list remove. The `ACCOUNT_REF#` re-delete is a no-op (DDB `delete_item` on a missing key returns 200).

### Security

**404 not 403 for non-owners.** All GET handlers return 404 (not 403) when the caller has no access to the account. This prevents account-id enumeration: an adversary cannot probe whether an account_id exists by observing 403 vs 404. This matches the ACC-001 ownership enforcement pattern and the KYC pattern (`kyc_cases.py` returns 404 for unknown cases regardless of ownership).

**Owners list is never returned to non-owners.** `list_account_holders` is owner-only. A view-based grantee whose view does not include `can_see_owners` will see the `owners` field stripped by `project_resource` before the response is serialized.

**Co-owner cannot add further co-owners beyond their own level.** Any current owner (primary or co-owner) can call `add_account_owner`. This is intentional — OBP's account-holder model treats all owners equally. If the platform requires a stricter "only the primary owner can add co-owners" rule, the `add_account_owner` function checks `account["owners"][0] == caller_sub` (first element = primary owner by insertion order). For this spec, any owner may add; the acceptance criterion documents this assumption explicitly.

### Money-safety

ACC-004 has **no money-moving code**. It does not call `new_ledger_entry`, `apply_wallet_delta`, `settle_or_reverse_ledger`, or any billing primitive. The `add_account_owner` and `remove_account_owner` operations are purely metadata mutations on the `banking_accounts` table. Balance reads by co-owners continue to call through to `billing_shared.get_wallet_balance` on the primary owner's partition (§5 above). There is no double-charge risk, no ledger write, and no payment path.

## 8. Backward Compatibility & Migration

### Additive-only changes to ACC-001/002/003 GET handlers

The change from a direct `caller_sub in account["owners"]` check to `resolve_account_access(...)` is backward-compatible:
- When `banking_account_views_enabled=False` (the default), `resolve_account_access` returns `{"role": "owner"}` if the caller is an owner, and `{"role": None}` otherwise — exactly the same authorization outcome as before.
- When `banking_account_views_enabled=True`, an owner still gets `{"role": "owner"}` and the full unprojected response. A non-owner with a VEW grant gets `{"role": "viewer"}` and a projected response. A non-owner with no grant gets 404.

No existing API response shape changes for owner callers. The `AccountOut` model gains no new required fields; the `owners` list was already present from ACC-001.

### DynamoDB schema

The `ACCOUNT_REF#` row shape was defined in ACC-001's schema section as a known future row type. No table migration is required — it is a new sort-key prefix in the existing `banking_accounts` table. `HOLDER_AUDIT#` rows are similarly new sort-key prefixes. DynamoDB's schemaless design means these rows can be written immediately without any table update.

No new GSI is added by ACC-004. The existing `GSI_ACCOUNT_BY_ID` (with `attr_types={"created_at": "N"}`, declared by ACC-001) is sufficient.

### Rollout sequence

ACC-004 should be deployed after ACC-001, ACC-002, and ACC-003. The `banking_account_views_enabled` flag may be enabled independently of `banking_accounts_enabled` (though it requires the latter at runtime). VEW-001/002/003 may be deployed before or after ACC-004; the `ImportError` guard ensures clean behavior either way.

## 10. Open Questions / Assumptions

1. **Who can add co-owners — any owner or only the primary owner?** This spec assumes any current owner may add further co-owners (OBP model: all owners equal). If the product requires "primary owner only", the guard changes to `account["owners"][0] == caller_sub`. Document the assumption explicitly in the service's docstring.

2. **DDB List vs StringSet for `owners`.** The current ACC-001 spec defines `owners: list[str]`. For deduplication safety under concurrent `add_account_owner` calls, a DDB StringSet (`SS`) attribute with an `ADD` expression is simpler. This is a schema detail that should be decided before ACC-001 is implemented (ACC-004 inherits it). This spec is agnostic — either works given the service-level duplicate guard.

3. **`view_id` is required by `resolve_active_grant`.** VEW-002's `resolve_active_grant` is a DDB point-read — it requires a non-None `view_id:str` (sk=`VIEWGRANT#{grantee_sub}#{view_id}`). The ACC read endpoints must accept an optional `?view_id=` query parameter and pass it through. When absent, the VEW branch is skipped and non-owners receive 404. Grantees holding multiple active views (e.g. both `accountant` and `auditor`) must specify which view they want; ACC does not auto-select. [CORRECTED: original question assumed VEW would auto-return a first/broadest match — no such API exists in VEW-002.]

4. **Co-owner access to metadata (ACC-003).** This spec treats co-owners as full owners for metadata reads and writes. If the product needs metadata write access to be restricted to the primary owner only, the metadata PUT/POST/DELETE handlers need a separate primary-owner check. Not currently specified.

5. **Audit log retention.** `HOLDER_AUDIT#` rows are append-only with no TTL. For long-lived accounts with frequent co-owner churn, these rows accumulate. Consider a TTL attribute (e.g. `expires_at = now_ts() + 90 * 86400`) or an admin-sweep cron for cleanup. Not addressed in this ticket.

6. **`list_views_shared_with_me` vs. `list_account_holders` from VEW.** A grantee can already discover which accounts they have view access to via `GET /ui/views/shared-with-me` (VEW-002). ACC-004 does not add a complementary "accounts I have view access to" endpoint in the ACC router — users are expected to use the VEW shared-with-me endpoint and then call `GET /ui/banking/accounts/{id}` with their view grant active.
