# PLT-002 — Top-N metrics leaderboard — admin ranking of top consumers / top endpoints

**Ticket type**: Backend (new admin endpoint + service helper)
**Priority**: P2
**Estimate**: 2 days
**Flag**: `METRICS_LEADERBOARD_ENABLED` (default **off**)
**Status**: Unimplemented

---

## 1. Summary & Goal

PLT-002 adds a single, admin-only `GET /v1/admin/api-usage/leaderboard` endpoint that returns the platform-wide top-N API consumers (by API key) and top-N API endpoints (by route), ranked by a caller-chosen metric for a given billing period. The OBP gap analysis (`docs/openbankproject/OBP_GAP_ANALYSIS.md` §D) classifies this as **PARTIAL**: *"aggregates exist; no ranked leaderboard endpoint."*

No new aggregation math is introduced. The underlying per-period aggregate rows (`API_USAGE#KEY#` / `API_USAGE#ROUTE#`) are already written atomically by `_apply_key_aggregate` / `_apply_route_aggregate` (`app/services/api_usage_metering.py:273,289`) on every recorded API call. This ticket adds:

1. A new `aggregate_leaderboard` helper function in `app/services/api_usage_metering.py` that performs a platform-wide scan of the existing aggregate rows and merges totals across users before ranking.
2. A new route handler added directly to `app/routers/admin_usage.py` (no new router file — the file already owns all admin-usage endpoints and the `_require_admin_user` dependency).
3. New `S.metrics_leaderboard_enabled` and `S.metrics_leaderboard_max_top_n` settings in `app/core/settings.py`.

With `METRICS_LEADERBOARD_ENABLED=0` (the default), the route is never registered, no scan ever runs, and the platform is byte-for-byte unchanged from today.

## 2. Context & Current State

### Existing aggregate infrastructure (all in `app/services/api_usage_metering.py`)

**Per-call event recording** — `record_api_usage_event_and_aggregates` (`api_usage_metering.py:343`) writes the raw event row and calls `_apply_api_usage_aggregates` (`api_usage_metering.py:335`), which in turn calls `_apply_period_aggregate`, `_apply_key_aggregate`, `_apply_route_aggregate`, `_apply_product_aggregate`, and `_apply_daily_aggregate` in the same request. Each aggregate is an `update_item` with ADD increments so writes are idempotent on retry. The table is `api_usage_events` (setting `S.api_usage_table_name`, `settings.py:1108`), accessed by the module-private `_api_usage_table()` helper (`api_usage_metering.py:1619`) which returns `ddb.Table(name)` or `None` when unconfigured.

**Key-aggregate rows** — written at `api_usage_metering.py:273`; DDB key `PK=USER#{user_sub}`, `SK=API_USAGE#KEY#{api_key_id}#PERIOD#{period_id}`; carries `entity_type="api_key_usage_period_totals"`, `user_sub`, `api_key_id`, `period_id`, `calls_total`, `billable_calls_total`, `request_units_total`, `cost_subtotal_micros`.

**Route-aggregate rows** — written at `api_usage_metering.py:289`; DDB key `PK=USER#{user_sub}`, `SK=API_USAGE#ROUTE#{route_id}#PERIOD#{period_id}`; carries `entity_type="api_route_usage_period_totals"`, `user_sub`, `route_id`, `period_id`, plus the same four metric counters and `unit_price_micros`.

**Per-user query helpers** — `query_api_key_period_totals(table, *, user_sub, period_id)` (`api_usage_metering.py:429`) returns `list[ApiUsageKeyPeriodTotals]` for a single user; `query_api_route_period_totals(table, *, user_sub, period_id)` (`api_usage_metering.py:463`) returns `list[ApiUsageRoutePeriodTotals]`. Both issue a `table.query(KeyConditionExpression=Key("PK").eq(...) & Key("SK").begins_with(...))` and filter in-memory by `period_id`.

**Sort/rank helper** — `_apply_breakdown_query(rows, *, search, sort_by, order, limit, cursor)` (`api_usage_metering.py:502`). Accepts a pre-fetched list of dicts, sorts by the requested metric using the key-function map `{"calls_total": ..., "cost_subtotal_micros": ..., "request_units_total": ...}` at line 516, applies a cursor-based page, and returns `{"items": [...], "next_cursor": ..., "count": ..., "total": ...}`. All ranking in PLT-002 is delegated to this function — no new sort logic.

**Full-table scan helper** — `_scan_api_usage_events(table, *, user_sub=None, period_id=None)` (`api_usage_metering.py:864`). When called without `user_sub`, it issues a single `table.scan(Limit=5000)` (no `LastEvaluatedKey` loop) and filters by `entity_type == "api_usage_event"`. PLT-002 introduces an analogous scan filtered by `entity_type` in `{api_key_usage_period_totals, api_route_usage_period_totals}`. Unlike the existing helper, the new `aggregate_leaderboard` helper **must** loop via `LastEvaluatedKey` because aggregate rows span all user partitions and can exceed one DynamoDB scan page. This is new logic — not a copy of the existing single-page helper.

> **CORRECTED**: The original draft described the new scan as using "the same loop discipline as `_scan_api_usage_events` at `api_usage_metering.py:877`." The actual function at line 877 performs a **single-page** `table.scan(Limit=5000)` with no `LastEvaluatedKey` loop. The multi-page loop shown in §5 is new code that the new helper introduces, not a pre-existing idiom.

**Admin router and auth dependency** — `app/routers/admin_usage.py`. The router has prefix `"/v1/admin"` (line 28) and already imports and re-exports `_api_usage_table` from `api_usage_metering`. The `_require_admin_user` dependency (line 35) reads `S.filemgr_admin_users` (a comma-separated allowlist at `app/core/settings.py:1056`) and raises HTTP 403 if the authenticated user is not in it. All new endpoints in PLT-002 use this same dependency — no new role system.

**Audit pattern** — `audit_event("api_key_rollout_state_view", admin_user, req, ...)` at `admin_usage.py:454` shows the exact call shape. PLT-002 emits `audit_event("api_usage_leaderboard_view", admin_user, req, ...)` using the same `from app.services.alerts import audit_event` import already present at line 25.

**`period_id_for_datetime`** — imported at `api_usage_metering.py:19` from `app.services.usage_metering`; signature `period_id_for_datetime(value: Optional[datetime] = None) -> str` (`usage_metering.py:184`) returns `"YYYY-MM"` for the given datetime (or now). Used as the default period when the caller omits `period_id`.

### What is missing

There is no cross-user (platform-wide) scan of aggregate rows today. `query_api_key_period_totals` and `query_api_route_period_totals` both require a `user_sub` argument and only query one user's partition. A platform-wide leaderboard requires merging the `api_key_id` / `route_id` totals from every user's partition for the specified period. That cross-user aggregation is the sole net-new logic in this ticket.

There is also no `GET /v1/admin/api-usage/leaderboard` endpoint anywhere in the codebase, and no `metrics_leaderboard_enabled` / `METRICS_LEADERBOARD_ENABLED` setting.

## 4. API / Service Design

### Service helper: `aggregate_leaderboard`

> **Import note**: `api_usage_metering.py` currently imports only `Key` from `boto3.dynamodb.conditions` (`api_usage_metering.py:9`). The new helper uses `Attr` for `FilterExpression`. The `from boto3.dynamodb.conditions import Key` import at line 9 must be extended to `from boto3.dynamodb.conditions import Attr, Key`.

Add to `app/services/api_usage_metering.py`:

```python
def aggregate_leaderboard(
    table: Any,
    *,
    period_id: str,
    dimension: str,           # "consumers" | "endpoints"
    metric: str,              # "calls_total" | "cost_subtotal_micros" | "request_units_total"
    top_n: int,               # already clamped by caller to [1, S.metrics_leaderboard_max_top_n]
    user_sub: str | None = None,  # None = platform-wide; str = single-user scope
) -> dict[str, Any]:
```

**Behavior:**

1. If `user_sub` is provided, call the existing per-user query helper directly:
   - `dimension == "consumers"` → `query_api_key_period_totals(table, user_sub=user_sub, period_id=period_id)`
   - `dimension == "endpoints"` → `query_api_route_period_totals(table, user_sub=user_sub, period_id=period_id)`
   Then delegate immediately to `_apply_breakdown_query(rows, search=None, sort_by=metric, order="desc", limit=top_n, cursor=None)` and return.

2. If `user_sub` is `None` (platform-wide scan):
   - Determine the target `entity_type`: `"api_key_usage_period_totals"` for `consumers`, `"api_route_usage_period_totals"` for `endpoints`.
   - Determine the group key field: `"api_key_id"` for `consumers`, `"route_id"` for `endpoints`.
   - Issue `table.scan(FilterExpression=Attr("entity_type").eq(target_entity_type), Limit=10000)` and loop via `LastEvaluatedKey` until exhausted (same loop discipline as `_scan_api_usage_events` at `api_usage_metering.py:877`).
   - Filter each item: skip rows where `str(item.get("period_id"))` does not equal `period_id`.
   - Accumulate into a `dict[str, dict]` keyed by the group key field, summing `calls_total`, `billable_calls_total`, `request_units_total`, `cost_subtotal_micros` across all users. For `endpoints` also track `unit_price_micros` as the value from the last-seen row (the price is route-level, not user-level).
   - Build a flat list of merged dicts (one entry per unique `api_key_id` / `route_id`), set `user_sub=""` on each merged row since it is a cross-user sum, and pass to `_apply_breakdown_query(rows, search=None, sort_by=metric, order="desc", limit=top_n, cursor=None)`.
   - Return the result with an added `total_rows_scanned` field.

**No money math, no writes, no side effects.** The function is read-only.

### Router: new endpoint in `app/routers/admin_usage.py`

```python
@router.get("/api-usage/leaderboard")
async def get_api_usage_leaderboard(
    req: Request,
    period_id: Optional[str] = Query(None, description="YYYY-MM; defaults to current month"),
    dimension: Literal["consumers", "endpoints"] = Query("consumers"),
    metric: Literal["calls_total", "cost_subtotal_micros", "request_units_total"] = Query("cost_subtotal_micros"),
    top_n: int = Query(10, ge=1),
    user_sub_filter: Optional[str] = Query(None, description="Scope to a single user; omit for platform-wide"),
    admin_user: str = Depends(_require_admin_user),
) -> LeaderboardResponse:
```

**Handler logic:**

1. Guard: `if not S.metrics_leaderboard_enabled: raise HTTPException(404)`. This ensures the route returns 404 even if it were accidentally registered when the flag is off (belt-and-braces alongside the `if S.metrics_leaderboard_enabled:` block in `main.py`).
2. Resolve `period_id`: if `None`, call `period_id_for_datetime()` (imported at the top of the service via `from app.services.usage_metering import period_id_for_datetime`).
3. Clamp `top_n = max(1, min(top_n, S.metrics_leaderboard_max_top_n))`.
4. Resolve `table = _api_usage_table()`. If `None`, return an empty `LeaderboardResponse` with `items=[]` and `total_rows_scanned=0` rather than raising — the table may simply be unconfigured in a stripped dev environment.
5. Call `aggregate_leaderboard(table, period_id=period_id, dimension=dimension, metric=metric, top_n=top_n, user_sub=user_sub_filter)`.
6. Emit `audit_event("api_usage_leaderboard_view", admin_user, req, period_id=period_id, dimension=dimension, metric=metric, top_n=top_n, scope="user" if user_sub_filter else "platform")`.
7. Build and return `LeaderboardResponse` from the result.

**Full route path** (prefix `/v1/admin` from line 28 of `admin_usage.py`):
`GET /v1/admin/api-usage/leaderboard`

**Auth**: `Depends(_require_admin_user)` — same guard used on all other admin-usage endpoints. Non-admin callers receive HTTP 403.

**Registration in `app/main.py`**: The `admin_usage_router` is already registered unconditionally at `main.py:675`. However, the leaderboard endpoint's internal `if not S.metrics_leaderboard_enabled: raise HTTPException(404)` guard makes it invisible when the flag is off. This matches the existing pattern where individual handlers (not just routers) gate on flags. An alternative — wrapping the entire router registration in `if S.metrics_leaderboard_enabled:` — is not preferred here because `admin_usage.py` contains many other admin endpoints that must always be active.

**No API key route exemption needed**: This is an authenticated admin endpoint, not a public no-auth read. It must not be added to `API_KEY_ROUTE_EXEMPTIONS` in `app/services/api_key_route_scope_registry.py`.

## 5. Detailed Behavior & Edge Cases

### Period resolution

`period_id` must be a `YYYY-MM` string (e.g. `"2026-06"`). If the caller passes a malformed string it will produce zero results (no rows match), not a validation error — this is intentional and consistent with how the existing `query_api_key_period_totals` and `query_api_route_period_totals` helpers behave (they filter in-memory with a string equality check). If the format must be enforced, add a regex `Pattern("^\d{4}-\d{2}$")` to the Pydantic field.

### Cross-user scan pagination

`table.scan` in DynamoDB returns at most 1 MB per call. For large deployments the scan must loop via `LastEvaluatedKey`:

```python
kwargs = {"FilterExpression": Attr("entity_type").eq(target_entity_type)}
rows_scanned = 0
while True:
    resp = table.scan(**kwargs)
    for item in resp.get("Items", []):
        rows_scanned += 1
        if str(item.get("period_id")) != period_id:
            continue
        # accumulate...
    lek = resp.get("LastEvaluatedKey")
    if not lek:
        break
    kwargs["ExclusiveStartKey"] = lek
```

A `Limit=10000` per page keeps individual call latency bounded. The scan is not paginated from the caller's perspective — all matching rows are merged in-memory before the top-N selection. For a platform with millions of users this scan will be slow; see Open Questions for the caching strategy.

### Merging cross-user rows

When two different users have called the same route (or used the same API key across orgs, which should not happen but is theoretically possible with shared keys), the merge accumulates all four counter fields. The `user_sub` field on the merged `LeaderboardItem` is set to `""` to signal it is a cross-user sum; callers should not attempt to look up a user by it.

For `dimension="consumers"`, `api_key_id` values are globally unique (created by `secrets.token_hex(16)` in `api_keys.py:143`, stored as the 32-char hex `key_id`), so two users cannot share a key. The merge step is effectively a no-op for consumers — each merged row will have exactly one contributing user. The field is kept as `""` for API shape consistency.

### `top_n` clamping

`top_n` is clamped to `[1, S.metrics_leaderboard_max_top_n]` (default max 100) before being passed to `_apply_breakdown_query`. `_apply_breakdown_query` itself also clamps at 500 (`api_usage_metering.py:523`), so the effective ceiling is `min(top_n_clamped, 500)`. The admin-level clamp provides a lower, configurable default ceiling.

### Empty table / no data for period

If the table has no rows matching `entity_type + period_id`, `aggregate_leaderboard` returns `{"items": [], "next_cursor": None, "count": 0, "total": 0, "total_rows_scanned": N}` and the endpoint returns an empty `LeaderboardResponse`. This is not an error.

### `_api_usage_table()` returns `None`

When `S.api_usage_table_name` is empty (unconfigured environments), `_api_usage_table()` returns `None`. The handler detects this and returns an empty leaderboard rather than raising an `AttributeError`. This matches the defensive pattern already in `emit_api_usage_event` (`api_usage_metering.py:1626`).

### Audit on every successful view

Every successful call (even returning an empty list) emits `audit_event("api_usage_leaderboard_view", ...)`. This is intentional — the OBP model and the existing `admin_usage.py:454` audit pattern both emit on every view of sensitive admin data.

### Metric field availability

All three metric fields (`calls_total`, `billable_calls_total`, `request_units_total`, `cost_subtotal_micros`) are present on every aggregate row written by `_apply_generic_counter_row` (`api_usage_metering.py:239`). Rows written before PLT-002 is deployed carry the same fields (no migration needed). Integer coercion via `int(item.get("calls_total") or 0)` handles any missing or Decimal-typed values.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 parity

There is no `if S.dev_mode:` branch anywhere in the leaderboard code path. The scan reads the same `T.*` handle (`_api_usage_table()` returns `ddb.Table(name)`) in both DynamoDB Local (dev) and real DynamoDB (prod). The flag gate (`METRICS_LEADERBOARD_ENABLED`) is the only mode switch. This satisfies the SECOPS-007 requirement that no new code introduces a dev-only shortcut.

### Idempotency

The endpoint is a read-only `GET`. It produces no writes, no side effects, and is fully idempotent. The audit event write (via `audit_event`) is a best-effort fire-and-forget that does not affect the response; duplicate audit events from retried requests are benign.

### Security

- **Auth gate**: `Depends(_require_admin_user)` is FastAPI dependency injection that runs before the handler body. A non-admin caller never reaches the scan. HTTP 403 is returned before any DDB call is made.
- **No sensitive data exposure**: The response carries `api_key_id` strings (opaque identifiers, not the raw key secret) and `route_id` strings (path patterns). It does not expose user PII, raw API key secrets, or billing account details beyond the numeric counters already visible in the admin API-usage breakdown endpoints.
- **Scan scope**: The `FilterExpression` on `entity_type` reduces DynamoDB's consumed read capacity by avoiding scanning event rows (which carry the same PK prefix range but a different `entity_type`). Capacity consumption is bounded by the aggregate row count, not the raw event count.

### Money-safety

This ticket is read-only. No money moves, no ledger writes, no wallet deltas. The `MONEY-SAFETY` constraints (TXR/PAY/ACC settlement primitives, double-charge prevention, fraud gate, SCA gate) are not applicable to a read-only admin analytics endpoint.

## 8. Backward Compatibility & Migration

### No migration required

- No new DynamoDB table, no new GSI, no `scripts/local-ddb-init.py` change.
- All existing aggregate rows are immediately readable by the new helper. Rows written before this ticket is deployed carry all required fields.
- `admin_usage_router` is already registered in `app/main.py:675` and all its existing endpoints are unaffected.
- The two new `Settings` fields have safe defaults (`False` and `100`). Deployments that do not set `METRICS_LEADERBOARD_ENABLED` will have a 404 route and no scan, indistinguishable from the current state.
- `LeaderboardItem` and `LeaderboardResponse` are new Pydantic models added to `app/models.py` — purely additive with no collision risk.

### Progressive rollout

Because the flag defaults off, operators can deploy the code change first and enable the endpoint later (e.g. after verifying scan latency in staging). No coordination with dependent services is required — the endpoint is entirely self-contained.

## 10. Open Questions / Assumptions

1. **Scan latency at scale**: A full-table scan of `api_usage_events` filtered to `entity_type=api_key_usage_period_totals` will read every aggregate row for every user, every period. For a multi-tenant platform with millions of keys this can be slow (seconds to tens of seconds) and expensive (RCUs proportional to total table size). A production hardening step — pre-computing a `LEADERBOARD#{period_id}` summary row as a materialized view, updated on each `_apply_key_aggregate` write — is not included in this ticket (P2 scope) but is the natural follow-on. **Assumption**: the initial implementation uses the scan approach, documented as a known latency trade-off, with the materialized-view optimization deferred.

2. **`FILEMGR_ADMIN_USERS` as the admin gate**: The `_require_admin_user` dependency (`admin_usage.py:35`) gates on `S.filemgr_admin_users`, which is a file-manager admin allowlist repurposed as the general admin gate throughout `admin_usage.py`. This naming is a pre-existing rough edge in the codebase. PLT-002 reuses it unchanged rather than introducing a new allowlist. **Assumption**: the existing allowlist is acceptable for this ticket; a renamed `ADMIN_USERS` setting is a separate cleanup ticket.

3. **Merged `user_sub` field**: When `user_sub_filter=None`, the merged `LeaderboardItem.user_sub` is `""`. A richer implementation could return a `list[str]` of contributing `user_sub` values per item (useful for drilling into a specific consumer's breakdown). This is deferred to a follow-on ticket. **Assumption**: empty `user_sub` for platform-wide rows is acceptable for P2.

4. **`api_key_id` display names**: The leaderboard items carry opaque `api_key_id` strings. The OBP leaderboard typically shows consumer app names. Enriching the items with the key's `label` field (from `api_keys.get_api_key_item`) is not included in this ticket to keep the scan hot-path free of N+1 DDB reads. **Assumption**: the caller can resolve labels in a second pass if needed.

5. **Frontend leaderboard page**: PLT-002 is backend-only. A `LeaderboardPage` in `frontend/src/pages/admin/` is a natural companion but is out of scope here. **Assumption**: the endpoint can be used directly by admins via Swagger UI (`/docs`) or the planned Admin Dashboard until a dedicated UI page is built.
