# ACC-002 — Per-account transaction list — project the existing ledger (running new_balance, date-range + cursor)

**Type**: Backend (read-side projection + endpoint)
**Priority**: P1
**Estimate**: 3 days
**Depends on**: ACC-001 (account entity, default-account bootstrap, ownership resolution)

---

## 1. Summary & Goal

ACC-002 adds a **read-side projection** of the existing single-entry billing ledger into a
per-account, date-range-filterable, cursor-paginated transaction list with a running
`new_balance` and a typed `amount{currency, value}` — the core OBP "get transactions for
account" shape.

**No new money rows are written.** The existing `LEDGER#{ts}#{entry_id}` rows in
`T.billing` (written by `billing_shared.new_ledger_entry`, `billing_shared.py:224`) are
the single source of truth; this ticket adds only a read path that reshapes them into a
typed `Transaction` object and layers on a running balance anchored to the live wallet.

Goals:

1. Expose `GET /ui/banking/accounts/{account_id}/transactions` with date-range, limit,
   cursor, and order parameters — returning the typed `Transaction` list with
   `new_balance`.
2. Expose `GET /ui/banking/accounts/{account_id}/transactions/{transaction_id}` — single
   transaction fetch, needed by ACC-003 metadata.
3. Prove the projection is non-duplicating: the same `entry_id`s appear in both
   `GET /billing/ledger` (the existing billing endpoint, `billing.py:2448`) and this new
   endpoint, guaranteeing no copy of the ledger is created.
4. Lay the groundwork for ACC-003 metadata enrichment: every `Transaction` carries a
   stable `transaction_id` (the ledger `entry_id`) that metadata sub-rows key off of.

## 2. Context & Current State

### Existing billing ledger

The single-entry ledger is written by `billing_shared.new_ledger_entry`
(`billing_shared.py:224-259`). Each row lives in `T.billing` under:

- **Partition key**: `pk = USER#{owner_sub}` (via `billing_shared.user_pk`,
  `billing_shared.py:23`)
- **Sort key**: `sk = LEDGER#{ts}#{entry_id}` (via `billing_shared.ledger_sk`,
  `billing_shared.py:220`)

The sort key embeds the Unix timestamp first, so natural DynamoDB sort order **is**
chronological — a key-condition range on `sk` between `LEDGER#{from_ts}` and
`LEDGER#{to_ts}~` performs the date filter at the DynamoDB layer without a
`FilterExpression`.

Each ledger item carries: `entry_id`, `ts`, `type`, `amount_cents`, `state`
(`pending`/`settled`/`reversed`), `reason`, `ledger_date`, and optionally `provider`,
`meta`, plus any `extra` pass-through fields (e.g., `provider: "stripe"` per GAP-0203).

### Existing ledger read endpoint

`GET /billing/ledger` (`billing.py:2448-2454`) reads all `LEDGER#` rows for a user via
`ddb_query_pk`, filters in Python (`it["sk"].startswith("LEDGER#")`), sorts by `ts`
descending, and returns up to `min(limit, 200)` items. It has **no date-range query, no
cursor, and no running balance** — confirming the gap analysis statement
(`OBP_GAP_ANALYSIS.md §B`: *"no per-account view / date-range pagination / running
balance"*).

### Wallet balance

`billing_shared.get_wallet_balance(T.billing, user_pk(owner_sub))`
(`billing_shared.py:176-182`) reads the `WALLET` singleton row and returns
`wallet_balance_cents` plus `currency`. This is the authoritative current balance from
which the running `new_balance` is anchored.

### Cursor signing

`app/core/cursor.py:94` (`encode_cursor`) and `:103` (`decode_cursor`) implement the
HMAC-signed v2 cursor envelope. `encode_cursor` accepts a `LastEvaluatedKey` dict and
produces a `v2.<payload_b64>.<sig>` token signed with `CURSOR_SIGNING_SECRET`. A tampered
or expired cursor produces `None` from `decode_cursor` (never raises), which the caller
treats as page-1. The `_json_default` helper at `cursor.py:12` coerces DynamoDB `Decimal`
values from numeric GSI keys into plain JSON numbers so they round-trip cleanly.

### ACC-001 dependency

ACC-001 introduces `ensure_default_account(owner_sub)` (idempotent lazy bootstrap),
`get_account(account_id, *, requester_sub)` (resolves via `GSI_ACCOUNT_BY_ID`, asserts
ownership — 404 on foreign requests), and the `wallet_backed` flag that tells ACC-002 to
read from `T.billing`. ACC-002 calls both functions; it does not duplicate ownership
logic.

## 3. Data Model

### No new DynamoDB table

ACC-002 reads exclusively from the **existing** `T.billing` table (
`S.billing_table_name`, defaulting to `"billing"`, `settings.py:348`). The date-range
query uses the existing `pk` + `sk` key schema:

```
pk  = USER#{owner_sub}   (HASH, S)
sk  = LEDGER#{ts}#{entry_id}   (RANGE, S)
```

The `sk` sort key is a **string** with a zero-padded integer timestamp prefix, so
lexicographic range comparisons work correctly for timestamps up to year ~2286
(`ts` is a 10-digit Unix int). No new `attr_types` declaration is needed for this
table — `sk` is already declared as `S` in `scripts/local-ddb-init.py`.

The existing `GSI_LEDGER_DATE` GSI (`local-ddb-init.py:67-77`) is not used by ACC-002;
it serves the platform financial dashboard. ACC-002 queries the base table directly by
`pk` + `sk` range.

### In-memory `Transaction` projection shape

The `Transaction` Pydantic model (new, added to `app/models.py`) is a read-only
projection — it is never persisted to DynamoDB:

```python
class TransactionAmountOut(BaseModel):
    currency: str           # e.g. "usd"
    value: str              # decimal string, e.g. "12.50" (cents / 100)

class TransactionOut(BaseModel):
    transaction_id: str     # = ledger entry_id
    account_id: str         # the resolved account_id (from ACC-001)
    type: str               # ledger "type" field (deposit/tip/payout/refund/…)
    amount: TransactionAmountOut
    status: str             # ledger "state" field (pending/settled/reversed)
    posted_at: int          # ledger "ts" (Unix int)
    description: str        # ledger "reason"
    provider: Optional[str] # pass-through from ledger item (GAP-0203)
    new_balance: TransactionAmountOut  # running balance AFTER this txn (settled rows only)

class TransactionListOut(BaseModel):
    transactions: list[TransactionOut]
    cursor: Optional[str]   # encode_cursor result; None = last page
```

`new_balance` is populated for ALL returned rows, but only **settled** rows advance the
running balance. For `pending` and `reversed` rows, `new_balance` carries the same value
as the preceding settled row (no movement — documented in Section 5).

## 4. API / Service Design

### Service functions — `app/services/banking_accounts.py`

Two new public functions are added to the service module introduced by ACC-001:

```python
def list_account_transactions(
    account_id: str,
    *,
    requester_sub: str,
    from_ts: Optional[int] = None,
    to_ts: Optional[int] = None,
    limit: int = 50,
    cursor: Optional[str] = None,
    order: str = "desc",          # "desc" | "asc"
) -> dict:                        # {"transactions": list[TransactionOut], "cursor": str|None}
```

```python
def get_account_transaction(
    account_id: str,
    transaction_id: str,
    *,
    requester_sub: str,
) -> TransactionOut:              # raises HTTPException(404) if not found
```

Both call `get_account(account_id, requester_sub=requester_sub)` from ACC-001 first. For
a `wallet_backed=True` account, `owner_sub` is read from the account row to form the
`T.billing` partition key.

#### `list_account_transactions` — internal logic

1. **Authorize**: `acc = get_account(account_id, requester_sub=requester_sub)` — raises
   404 if not owner/co-owner (ownership enforced by ACC-001's
   `GSI_ACCOUNT_BY_ID` lookup + owner assertion).
2. **Validate wallet-backed**: for `acc.wallet_backed == False` (non-wallet account),
   return an empty list with no cursor (no ledger rows exist for this account in this
   tier; future tiers may add their own rows).
3. **Decode cursor**: `lek = decode_cursor(cursor)` — `None` for first page, `None` on
   tampered cursor (treated as page-1, never 500).
4. **Build key condition**: `pk = USER#{acc.owner_sub}`, `sk BETWEEN LEDGER#{from_ts}
   AND LEDGER#{to_ts}~`. When `from_ts` is `None`, lower bound = `"LEDGER#"` (start of
   LEDGER prefix). When `to_ts` is `None`, upper bound = `"LEDGER#~"` (tilde `~` sorts
   after all digits in ASCII). Using `sk` range in the key condition (not a
   `FilterExpression`) ensures DynamoDB pages correctly — a `FilterExpression` does NOT
   reduce the 1 MB read page (CLAUDE.md gotcha; billing.py uses Python-side filter
   instead, which is why it misses this).
5. **Query loop**: issue DynamoDB `query` with `ScanIndexForward=(order=="asc")`,
   `Limit=limit+1` (one extra to detect has-more), `ExclusiveStartKey=lek`. Because the
   key condition IS the date filter, a single DynamoDB call fills the page for dense
   ledgers. For sparse secondary predicates (if added in future), loop on
   `LastEvaluatedKey`.
6. **Anchor balance**: call `get_wallet_balance(T.billing, user_pk(acc.owner_sub))` once
   to get `wallet_balance_cents` (the "now" balance, authoritative).
7. **Compute running `new_balance`**: walk the fetched rows **newest-first** regardless
   of the requested order. The newest settled transaction's `new_balance` = current wallet
   balance. For each older row: `new_balance[i] = new_balance[i+1] - signed_amount[i+1]`
   where `signed_amount` is positive for credits (deposit/refund) and negative for debits
   (tip/payout/charge). Then re-order to the requested `order` before serializing.
8. **Cursor**: if `len(rows) > limit`, pop the extra row and `encode_cursor` its key;
   otherwise cursor = `None`.
9. **Project**: map each ledger item to `TransactionOut`.

#### `get_account_transaction` — internal logic

1. Authorize via `get_account`.
2. For wallet-backed account: compute `sk_prefix = LEDGER#` and query for `entry_id`
   matching `transaction_id`. Because `ledger_sk` embeds the ts before the entry_id
   (`LEDGER#{ts}#{entry_id}`), a direct `get_item` is not possible without the ts.
   Use a `FilterExpression` query on the base table with `pk = USER#{owner_sub}`,
   `sk begins_with "LEDGER#"`, and a filter `entry_id = :txn_id`. Since this is a
   point-lookup (single row), the small extra scan cost is acceptable. If not found →
   `HTTPException(404)`.
3. For the single-row case, `new_balance` is set to the current wallet balance (best
   effort; single-row context does not walk history). ACC-003 uses this function only to
   confirm the transaction exists — it does not use `new_balance` from this call.

### Router — `app/routers/banking_accounts.py`

`limit` is clamped: `max(1, min(limit, 200))` — mirrors the existing billing endpoint cap

## 5. Detailed Behavior & Edge Cases

### Running balance algorithm

The running `new_balance` is anchored to the **live wallet** (`get_wallet_balance`,
`billing_shared.py:176`), not to a stored or computed historical balance. This is correct
because the wallet balance IS the authoritative sum of all settled ledger rows
(maintained by `apply_wallet_delta`, `billing_shared.py:185`).

Walk order: regardless of the `order` query parameter, the running balance must be
computed newest-to-oldest before re-sorting. For the `desc` (newest-first) response:

```
transactions[0].new_balance = wallet_balance_cents  (newest row = current state)
transactions[1].new_balance = transactions[0].new_balance - transactions[0].signed_amount
...
transactions[N].new_balance = transactions[N-1].new_balance - transactions[N-1].signed_amount
```

`signed_amount` sign convention: **CORRECTED** — the ledger does not use the type names
`deposit`, `tip`, `payout`, or `charge`. The actual `entry_type` values written by
`new_ledger_entry` across the codebase are: `credit`, `debit`, `adjustment`,
`refund_credit`, `refund_debit`, `vod_purchase_credit`, `vod_purchase_debit`,
`sponsorship_payout`, `ad_revenue_credit`, `click_charge`, `conversion_charge`,
`impression_charge`, `license_revenue_credit`, `license_revenue_debit`, `purchase`, etc.

The sign mapping for `new_balance` computation must be:
- Types ending in `_credit`, equal to `"credit"`, or `"adjustment"` with a positive delta
  applied by `apply_wallet_delta` → **positive** (increases balance).
- Types ending in `_debit`, equal to `"debit"`, or domain-specific charge types
  (`click_charge`, `conversion_charge`, `impression_charge`, `purchase`) → **negative**
  (decreases balance).
- `"adjustment"` alone: defaults to **credit / positive** (the canonical `refund_payment`
  pattern writes refunds/adjustments as positive credits; `billing.py:1306-1324`). Where a
  bespoke reversal/refund type exists it carries its own explicit row below, removing any
  guesswork for the reader.

**Explicit sign-derivation table (audit A4 — enumerated so no reader has to guess):**

| `entry_type` | Direction | Sign | Notes |
|---|---|---|---|
| `credit`, `*_credit` (e.g. `refund_credit`, `ad_revenue_credit`, `license_revenue_credit`, `vod_purchase_credit`) | credit | **+** | increases balance |
| `debit`, `*_debit` (e.g. `refund_debit`, `license_revenue_debit`, `vod_purchase_debit`) | debit | **−** | decreases balance |
| `*_charge` / `purchase` (`click_charge`, `conversion_charge`, `impression_charge`, `purchase`) | debit | **−** | decreases balance |
| `sponsorship_payout` | debit | **−** | payout decreases balance |
| `adjustment` | credit (default) | **+** | canonical refund/adjustment is a positive credit (`refund_payment`); see default rule above |
| `shipping_refund` | credit | **+** | SHP-019 shipping refund; positive unsigned amount, paired reversal-typed credit |
| `invoice_void_reversal` | credit | **+** | SuiteCRM INV-009 / QUO-005 invoice void reversal (`state="reversed"`); positive unsigned amount, credit note |

Any unlisted type falls through to the documented safe default (credit / positive).

The `amount_cents` field is always stored as an absolute value
(`billing_shared.py:249`: `int(amount_cents)`); sign is derived from `type` as above.

> **RISK (Open Question 3 update)**: the sign-convention mapping is more complex than a
> short allow-list of 6 names. The implementation of `list_account_transactions` MUST
> enumerate all current and future type strings (or adopt a naming convention, e.g.,
> `_credit` suffix → positive, `_debit` / `_charge` suffix → negative). Any unlisted
> type falls through to the documented safe default (positive/credit). A `signed_amount_cents`
> field persisted at write time (future TXR-001+ work) would eliminate this ambiguity.

**Pending and reversed rows**: these do not move the wallet balance, so they carry the
same `new_balance` as the nearest preceding settled row. They are still included in the
list (they represent in-flight or cancelled transactions).

**Empty history**: if no ledger rows exist (new user), return `transactions: []`,
`cursor: None`. The wallet balance is not included in this response (there is nothing to
anchor it to).

**Page boundary balance**: when using cursor pagination, the balance anchor
(`get_wallet_balance`) is always fetched fresh on each page request. This means the
`new_balance` of the oldest row on page 2 will be computed from the current wallet
balance minus all rows from page 1 that were ALSO older than the page-2 rows. To handle
this correctly, the service fetches `limit+1` rows and includes `new_balance` only for
the `limit` rows it returns; the page-2 anchor is recalculated server-side from the
current wallet at page-2 request time.

**Cross-page consistency caveat (documented)**: if the wallet receives a new transaction
between page-1 and page-2 requests, the `new_balance` values may be slightly inconsistent
across pages. This is an expected property of a stateless pagination design over a live
wallet; it matches OBP's own pagination behavior. For strict consistency, callers should
use the single-page (no-cursor) endpoint.

### Date-range key condition details

DynamoDB sort key comparisons are lexicographic on string-typed `sk`. The `LEDGER#` prefix
is followed by a decimal integer timestamp, then `#`, then the entry_id. For the range to
work correctly with lexicographic comparison, timestamps must be zero-padded or
monotonically increasing in the string representation. Existing `ledger_sk`
(`billing_shared.py:220`) writes `LEDGER#{ts}#{entry_id}` without zero-padding, but Unix
timestamps are currently 10 digits (through year 2286), so string comparison equals
numeric comparison for this window. Document this assumption; if the sort key format
changes, the key condition must be updated.

Key condition expression:
```
pk = :pk AND sk BETWEEN :sk_lo AND :sk_hi
```
where `:sk_lo = "LEDGER#{from_ts}"` and `:sk_hi = "LEDGER#{to_ts}~"` (the `~` character
has ASCII value 126, higher than any digit or `#`). When `to_ts` is omitted,
`:sk_hi = "LEDGER#~"` which is lexicographically higher than any `LEDGER#...` value.

### Non-wallet-backed accounts

For accounts with `wallet_backed=False` (type=`SAVINGS` or `EXTERNAL`, introduced by
ACC-001 but not backed by a ledger in this tier), `list_account_transactions` returns
`{transactions: [], cursor: null}` immediately. This is the correct default — these
accounts have no money rows in this tier. Future tickets may add their own ledger
semantics.

### Ownership enforcement

All ownership checks are delegated to ACC-001's `get_account(account_id,
requester_sub=requester_sub)`. A request from a non-owner returns 404 (not 403) to avoid
confirming the account exists. This is enforced by ACC-001's `GSI_ACCOUNT_BY_ID` lookup
pattern — no cross-user partition scan is performed.

### Tampered / foreign cursors

`decode_cursor(cursor)` returns `None` for any cursor that fails HMAC verification
(`cursor.py:103-131`). The service treats `None` as page-1 (no `ExclusiveStartKey`). This
is consistent with all other cursor-paginated endpoints in the codebase (e.g.,
`profile.py:554`, `social.py:340`). A 400 is NOT raised — silent fallback to page-1 is
safer for API clients that lose cursor state.

### `from` / `to` coercion

The router accepts `from` / `to` as either Unix integers or ISO-8601 strings. The
coercion helper is inline in the router (not a shared utility, to keep the service
pure-Python). An invalid date format raises `HTTPException(400, detail="Invalid date
format for 'from'/'to'; use Unix timestamp or ISO-8601")`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 dev/prod parity

ACC-002 contains **zero** `if S.dev_mode` branches. The only data source is `T.billing`
(DynamoDB Local in dev, real DynamoDB in prod) accessed through the same
`_safe_table`-wrapped handle (`tables.py:65`). The `get_wallet_balance` and ledger query
paths are identical in both environments. No mock data is returned, no conditional logic
forks on environment.

### Money-safety guarantees

ACC-002 is **entirely read-only** — it calls no `put_item`, `update_item`, `delete_item`,
or `batch_writer` on any table. It cannot double-charge, create phantom ledger entries,
or mutate the wallet. The running-balance computation is a pure arithmetic projection over
immutable ledger rows; it has no side effects.

Specifically:
- `new_ledger_entry` (`billing_shared.py:224`) is **never called** by ACC-002.
- `apply_wallet_delta` (`billing_shared.py:185`) is **never called** by ACC-002.
- `settle_or_reverse_ledger` (`billing_shared.py:262`) is **never called** by ACC-002.

The only writes allowed by billing primitives (TXR/PAY/ACC invariant) must flow through
`settle_or_reverse_ledger` + `new_ledger_entry` from the existing billing/TXR service
layer. ACC-002 is a read-side projection and does not participate in any write path.

### Idempotency

Read endpoints are inherently idempotent. Repeated requests with the same parameters
return the same result (modulo concurrent wallet changes — documented in Section 5).
The cursor is stateless and HMAC-signed; it does not create any server-side state.

### Security

- **CSRF**: all `/ui/` endpoints with cookie auth are protected by the existing CSRF
  middleware (`app/services/sessions.py:330` `require_ui_session`). ACC-002 GET endpoints do not
  require a CSRF token (GET is exempted by the CSRF check in `require_ui_session`).
  _(Note: CLAUDE.md §Router conventions lists `app/auth/deps.py` as the auth dependency
  module, but `require_ui_session` is actually defined at `app/services/sessions.py:330`;
  `app/auth/deps.py` defines `require_root_session`, `get_authenticated_user`, and
  `require_kyc_tier`. All routers import `require_ui_session` from `sessions.py`.)_
- **Ownership isolation**: the `T.billing` query always uses `pk = USER#{owner_sub}`
  where `owner_sub` is resolved from the account row by ACC-001's
  `get_account(..., requester_sub=requester_sub)`. A requester cannot access another
  user's ledger by crafting an `account_id` — they would fail ACC-001's ownership check
  (404) before any `T.billing` query executes.
- **No PII in cursor**: the cursor encodes only the DynamoDB `LastEvaluatedKey` (which
  contains `pk` and `sk` values). The `pk` (`USER#{sub}`) is implicitly present; callers
  should treat cursors as opaque tokens. The HMAC signature prevents cursor forging.

## 10. Open Questions / Assumptions

1. **Timestamp zero-padding**: `ledger_sk` (`billing_shared.py:220`) does not zero-pad
   the timestamp. The current 10-digit Unix epoch (year 2001–2286) produces correct
   lexicographic ordering. If the sort key format ever changes (e.g., milliseconds or
   zero-padded), the key-condition range expression must be updated. This assumption is
   documented in Section 5 and should be noted in `docs/dynamodb.md`.

2. **Multi-page balance consistency**: the running `new_balance` is re-anchored to the
   live wallet on every page request. Between two page requests, if a new transaction
   lands, the balance values across pages will be inconsistent (see Section 5). This is
   accepted behavior matching OBP's own pagination design. If strict consistency is
   required, a future ticket could introduce a snapshot balance at cursor-creation time
   (stored in the cursor payload or a short-lived DDB row). That is out of scope for this
   ticket.

3. **`signed_amount` sign convention**: the ledger `amount_cents` is always stored as a
   positive integer; the sign derives from `type`. The full mapping of `type →
   credit/debit` must be documented and tested (TC-002/003). If new types are added to
   the ledger in future, the sign mapping must be updated. A safe fallback: unknown type
   → credit (positive). Document the assumption.

4. **`get_account_transaction` scan cost**: the single-row fetch uses a query +
   `FilterExpression` on `entry_id`, which scans all `LEDGER#` rows for the user until
   the entry is found. For users with very large ledger histories (thousands of rows), this
   is O(N). A future optimization is to embed the `ts` in the `transaction_id` response
   so callers can reconstruct the `sk` prefix and use a more selective `begins_with`. This
   is deferred since ACC-003 (the primary consumer of `get_account_transaction`) performs
   point lookups infrequently.

5. **Non-wallet-backed accounts**: `SAVINGS` and `EXTERNAL` accounts are created by
   ACC-001 but have no ledger backing in this tier. The empty-list response is a safe and
   explicit default. Future tickets may add a separate ledger for non-wallet accounts or
   link them to external data sources.

6. **`from` / `to` ISO string coercion**: the router accepts ISO-8601 but the service
   accepts only Unix ints. The coercion is in the router layer. Timezone handling: ISO
   strings without a timezone suffix are treated as UTC (Python `datetime.fromisoformat`
   behavior in 3.11+). This assumption should be documented in the API spec comment.
