# CSN-003 — Dynamic Entities — runtime JSON-schema registration to generated CRUD (admin-gated)

**Type:** Feature | **Priority:** P3 | **Estimate:** 3.5d
**Flag:** `DYNAMIC_ENTITIES_ENABLED` (new, default **off**)
**Source ticket:** `docs/openbankproject/OBP_CONSENTS_DYNAMIC_TICKETS.md` §CSN-003
**Gap row:** `docs/openbankproject/OBP_GAP_ANALYSIS.md:87` — "Dynamic Entities / Dynamic Endpoints — MISSING"

---

## 1. Summary & Goal

CSN-003 delivers the **Dynamic Entity** capability from the Open Bank Project (OBP) specification: a
ROOT-privileged administrator registers a named, JSON-Schema-described custom entity at runtime and
the platform **generates working CRUD endpoints for it immediately — no code deploy required**. The
generated CRUD is backed by a generic single-table DynamoDB row store, owner-scoped, schema-validated
on every write, and fully audited.

This is the lowest-fit OBP feature in the codebase (no analogue exists today) and carries the
highest extensibility risk, so the entire surface is **additive, flag-gated default-off, and
admin-controlled**. When `DYNAMIC_ENTITIES_ENABLED` is `false` (the default), no router is
registered, no table is read, and the platform is byte-for-byte unchanged. The sibling ticket
CSN-004 (Dynamic Endpoints) builds a gateway layer on top of the entity CRUD delivered here; CSN-003
is independently shippable.

## 2. Context & Current State

### 2.1 Nothing analogous exists today

The OBP gap analysis (`OBP_GAP_ANALYSIS.md:87`) marks Dynamic Entities as **MISSING** — there is no
runtime schema-registration or generated CRUD surface anywhere in the codebase. The closest
structural analog is the achievements system (`app/routers/achievements.py:68`), which uses
`Depends(require_root_session)` (`app/auth/deps.py:308`) to gate admin writes — the same
`require_root_session` gating pattern CSN-003 adopts. Note: achievements does **not** call
`audit_event`; the audit pattern is sourced from `app/routers/api_keys.py` (see §2.3).

### 2.2 Auth primitives that will be reused

`require_root_session` (`app/auth/deps.py:308`) raises HTTP 403 for any caller whose `role != ROOT`.
It is already used for admin-write gating throughout: achievements (`app/routers/achievements.py:68,
89, 98, 115, 280`), open-data admin writes (planned CSN-005), and the KYC case-assignment admin path.
`require_ui_session` (`app/auth/deps.py`, imported by every feature router) provides the
owner-scoped session context (`ctx["user_sub"]`) used for CRUD row ownership.

### 2.3 Audit machinery

`audit_event(event, user_sub, request, **fields)` (`app/services/alerts.py:644`) is the single
audit sink. It is called from every mutation in `app/routers/api_keys.py:21, 28, 35` and
throughout the KYC, billing, and admin routers. CSN-003 follows the same pattern for
`dynamic_entity.registered` and `dynamic_entity.deleted` events.

### 2.4 DynamoDB table definition and the numeric-GSI gotcha

All tables are declared as `TableDef` frozen dataclasses in `scripts/local-ddb-init.py:29-35`. The
`attr_types` field must list any numeric GSI/sort key (`scripts/local-ddb-init.py:52-53` — the
`users` table example uses `attr_types={"kyc_tier":"N","kyc_tier_updated_at":"N"}`). Omitting
`attr_types` for a numeric key causes `ValidationException` at query time. Table handles are wired
in `app/core/tables.py` (the `_FloatSafeTable` proxy at line 29 coerces `float → Decimal` on writes
automatically). Settings are added to `app/core/settings.py` following the pattern of
`api_keys_table_name: str = os.environ.get("API_KEYS_TABLE_NAME", "api_keys")` (line 44).

### 2.5 Conditional router registration

`app/main.py` uses two patterns for flag-gated routers:
- A conditional `if _S.<flag>:` import + `app.include_router(...)` inside `create_app()`
  (line 699: `if _S.ticket_boards_enabled: ... app.include_router(ticket_boards_router)`).
- A flag-off path that raises HTTP 404 inside a handler (line 526:
  `if not browser_ssh_terminal_enabled(): raise HTTPException(404, ...)`).

CSN-003 uses the first pattern: neither the definition router nor the generated-CRUD router is
imported or registered when `S.dynamic_entities_enabled` is `False`. This is the
"router is not registered" guarantee from the cross-cutting constraints (`OBP_CONSENTS_DYNAMIC_TICKETS.md:49`).

### 2.6 Rate-limit / bucket-limit primitive

`_bucket_limit(user_sub, sid, max_n, win)` (`app/services/rate_limit.py:60`) is the single
DDB-backed counter used by the KYC partner API throttle (`rate_limit.py:385`) and MFA send-rate
limits. The entity row-write rate limit added in CSN-003 reuses this primitive keyed on
`entity:{entity_name}:{user_sub}`.

### 2.7 Cursor pagination

`app/core/cursor.py` provides HMAC-signed opaque cursor encode/decode. Its `_json_default` helper
(line 12) already handles `Decimal` from numeric GSI `LastEvaluatedKey`. All list endpoints in
CSN-003 use this for pagination.

### 2.8 Dependency-free pure-Python validation posture

`app/services/receipts.py` and `app/services/audit_export_pipeline.py` implement complex logic
(PDF rendering, SHA-256 manifest) with zero new system/pip dependencies. `jsonschema` is **not** in
`requirements.txt`. Schema validation in CSN-003 is therefore implemented as a bounded pure-Python
validator (required-field presence, scalar type coercion checks, depth/count caps) — no external
library. This matches the SECOPS-007 parity posture.

## 3. Data Model

### 3.1 Two new DynamoDB tables

#### Table 1: `dynamic_entity_defs`

Stores the registered schema definitions. One row per entity name.

```
PK: entity_name  (S)       # e.g. "widget", "loan_product"
SK: sk="DEF"     (S)       # single logical row per entity
```

Fields:

| Attribute | Type | Notes |
|---|---|---|
| `entity_name` | S | Lowercase, validated regex (see §5.1) |
| `json_schema` | M (DDB Map) | Stored JSON-Schema object |
| `created_by` | S | ROOT `user_sub` who registered it |
| `created_at` | N | `now_ts()` integer Unix seconds |
| `updated_at` | N | `now_ts()` on each upsert |
| `version` | N | Monotonic, incremented on each update; starts at 1 |

**GSI:** `ByCreatedAt` — partition `created_by` (S), sort `created_at` (**N**).

```python
TableDef(
    _resolve_table_name(S.dynamic_entity_defs_table_name, "dynamic_entity_defs"),
    partition_key="entity_name",
    sort_key="sk",
    gsi=[{
        "index_name": S.dynamic_entity_defs_creator_index,
        "partition_key": "created_by",
        "sort_key": "created_at",
    }],
    attr_types={"created_at": "N"},   # ← REQUIRED: numeric GSI sort key
)
```

Settings (`app/core/settings.py`):
- `dynamic_entity_defs_table_name: str = os.environ.get("DYNAMIC_ENTITY_DEFS_TABLE_NAME", "dynamic_entity_defs")`
- `dynamic_entity_defs_creator_index: str = os.environ.get("DYNAMIC_ENTITY_DEFS_CREATOR_INDEX", "created_by-created_at-index")`

Handle: `T.dynamic_entity_defs` added to `app/core/tables.py`.

#### Table 2: `dynamic_entity_rows`

Generic per-entity row store. All registered entities share one physical DynamoDB table,
partitioned by `entity_name`.

```
PK: entity_name  (S)       # partition = entity type
SK: row_id       (S)       # "dyn_" + uuid4().hex
```

Fields:

| Attribute | Type | Notes |
|---|---|---|
| `entity_name` | S | Denormalized from PK for GSI |
| `row_id` | S | `dyn_{uuid4().hex}` |
| `owner_sub` | S | `ctx["user_sub"]` of the creator |
| `data` | M | Validated map of entity fields |
| `created_at` | N | `now_ts()` |
| `updated_at` | N | `now_ts()` on write |
| `ttl_epoch` | N | Optional reap epoch written by `S.ddb_ttl_attr` (default `"ttl_epoch"`); set when entity is deleted |

**GSI:** `ByOwner` — partition `owner_sub` (S), sort `created_at` (**N**).

```python
TableDef(
    _resolve_table_name(S.dynamic_entity_rows_table_name, "dynamic_entity_rows"),
    partition_key="entity_name",
    sort_key="row_id",
    gsi=[{
        "index_name": S.dynamic_entity_rows_owner_index,
        "partition_key": "owner_sub",
        "sort_key": "created_at",
    }],
    attr_types={"created_at": "N"},   # ← REQUIRED: numeric GSI sort key
)
```

Settings:
- `dynamic_entity_rows_table_name: str = os.environ.get("DYNAMIC_ENTITY_ROWS_TABLE_NAME", "dynamic_entity_rows")`
- `dynamic_entity_rows_owner_index: str = os.environ.get("DYNAMIC_ENTITY_ROWS_OWNER_INDEX", "owner_sub-created_at-index")`
- `dynamic_entity_max_properties: int = int(os.environ.get("DYNAMIC_ENTITY_MAX_PROPERTIES", "50"))`
- `dynamic_entity_max_depth: int = int(os.environ.get("DYNAMIC_ENTITY_MAX_DEPTH", "3"))`
- `dynamic_entity_max_required: int = int(os.environ.get("DYNAMIC_ENTITY_MAX_REQUIRED", "20"))`
- `dynamic_entity_row_write_rate_per_hour: int = int(os.environ.get("DYNAMIC_ENTITY_ROW_WRITE_RATE_PER_HOUR", "200"))`
- `dynamic_entities_enabled: bool = os.environ.get("DYNAMIC_ENTITIES_ENABLED", "false").lower() == "true"`

Handle: `T.dynamic_entity_rows` added to `app/core/tables.py`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Entity name validation

Accepted regex: `^[a-z][a-z0-9_]{2,39}$` — lowercase start, 3–40 chars total, letters/digits/underscore only. Applied in `register_entity` before any DDB write; failure → `400 invalid_entity_name`.

**Reserved name denylist** — reject any name that collides with a real router prefix:
`{"users", "billing", "messaging", "calendar", "feed", "tickets", "catalog", "sessions",
"admin", "internal", "dynamic", "open-data", "consents", "subscriptions", "filemanager",
"notifications", "webhooks", "kyc", "api", "auth", "health", "metrics", "openapi"}`.
Failure → `400 reserved_entity_name`.

### 5.2 JSON-Schema validation (bounded pure-Python)

`validate_against_schema` implements a bounded validator — no `jsonschema` pip dependency. The stored
`json_schema` must be a JSON-Schema object with:
- `type: "object"` at the top level
- `properties`: a dict of property descriptors; each descriptor must have `type` ∈
  `{string, integer, number, boolean, array, object}` and optionally `items` (for `array`)
- `required`: a list of property names present in `properties`

**Hard caps enforced at registration time** to prevent abuse:
- `len(properties) <= S.dynamic_entity_max_properties` (default 50)
- Nesting depth (counting `object`/`array` property types recursively) `<= S.dynamic_entity_max_depth` (default 3)
- `len(required) <= S.dynamic_entity_max_required` (default 20)

Violation → `400 schema_too_complex` with the offending cap name.

At **row write time**, `validate_against_schema` checks:
1. All `required` properties are present in `data`; missing → `400 schema_validation_failed` with
   `{"code": "schema_validation_failed", "field": "<name>", "reason": "required"}`
2. Each property's value matches the declared `type` (Python type mapping: `string → str`,
   `integer → int`, `number → (int|float)`, `boolean → bool`, `array → list`,
   `object → dict`); mismatch → `400 schema_validation_failed` with
   `{"code": "schema_validation_failed", "field": "<name>", "reason": "type_mismatch", "expected": "<type>"}`
3. Extra properties not declared in `properties` are **allowed** (open-world schema by default).

### 5.3 Owner scoping

- `create_row` stamps `owner_sub = ctx["user_sub"]` — the caller owns every row they create.
- `get_row`: loads by `Key={entity_name, row_id}`; returns `None` (→ HTTP 404) if not found **or**
  `item["owner_sub"] != owner_sub`. This prevents enumeration of other users' rows.
- `update_row` / `delete_row`: conditional `ConditionExpression=Attr("owner_sub").eq(owner_sub)`;
  `ConditionalCheckFailedException` → HTTP 404 (not 403, to prevent existence disclosure).
- `list_rows` with `owner_sub` param: queries `ByOwner` GSI (`owner_sub = :u`); without it: queries
  the base table by `entity_name` PK (admin-only access pattern — callers from the CRUD router
  always pass `owner_sub`; a future admin list path may omit it).

### 5.4 Row write rate limiting

To prevent bulk-insert abuse, `create_row` and `update_row` call
`_bucket_limit(f"entity:{entity_name}:{owner_sub}", "rl#dyn_write", S.dynamic_entity_row_write_rate_per_hour, 3600)`
(`app/services/rate_limit.py:60`). Bucket exhaustion → HTTP 429 with
`{"code": "dynamic_entity_rate_limited", "limit": <cap>, "window_seconds": 3600, "Retry-After": <remaining>}`.

### 5.5 Entity deletion and orphaned row handling

`delete_entity` removes the DEF row and then pages through all rows in the `entity_name` partition
(looping `LastEvaluatedKey`), setting the TTL attribute (`S.ddb_ttl_attr`, defaulting to `ttl_epoch`)
to `now_ts() + 86400 * 7` on each via `update_item` with
`UpdateExpression="SET #ttl = :ttl"` (same pattern as `app/services/shoppingcart.py:73` and
`app/services/sessions.py:534`). Note: `app/services/ttl.py:with_ttl` is a dict mutator for
`put_item` calls only — it cannot be used to update an attribute on an existing row.
DynamoDB TTL asynchronously reaps the rows within 48 hours.
Immediate hard delete of all rows is avoided because partitions may be large and a synchronous bulk
delete would block the request thread; TTL reaping is the established pattern for row cleanup
(sessions, messages, etc.).

After deletion, any CRUD request to `/ui/dynamic/{entity_name}/...` returns `404 entity_not_found`
because `get_entity_def` returns `None` for the deleted name.

### 5.6 Concurrent schema update (versioning)

`register_entity` on an already-existing entity name performs a conditional `update_item` with
`ConditionExpression=Attr("version").eq(body.expected_version)` when `expected_version` is supplied.
Without `expected_version`, the upsert is unconditional (last writer wins). `version` is incremented
with `SET version = version + :one`. This is the same optimistic-concurrency pattern used in
`tickets._conditional_update_meta`.

### 5.7 Unknown entity on CRUD

Every CRUD handler calls `get_entity_def(entity_name)` first. `None` return → raise
`HTTPException(404, {"code": "entity_not_found", "entity_name": entity_name})`. This provides a
clean contract for CSN-004's `dynamic_entity_proxy` connector.

|---|---|---|

| `DYNAMIC_ENTITY_ROWS_TABLE_NAME` | `dynamic_entity_rows` | DDB table name |

**WARNING — do not set `DYNAMIC_ENTITY_ROW_WRITE_RATE_PER_HOUR=0` expecting it to disable the
throttle.** In `_bucket_limit` (`app/services/rate_limit.py:60`), `count >= max_n` with `max_n=0`

bypass pattern in the codebase (`rate_limit_kyc_partner_api` at line 385 uses `or 100` / `or 200`
etc. to prevent zero from reaching `_bucket_limit` at all). To disable the write throttle,
set the cap to a very large value (e.g., `999999`) or add an explicit `if cap <= 0: return`
guard in the `create_row`/`update_row` callers.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — zero `dev_mode` branch

There is no `if S.dev_mode:` anywhere in `dynamic_entities.py` or `dynamic_entities` router. Every
DDB read/write goes through the frozen `T.dynamic_entity_defs` / `T.dynamic_entity_rows` handles
(`_FloatSafeTable` proxies). In dev these resolve to DynamoDB Local (port 8001); in prod to real
DynamoDB. The validation, rate-limiting, and ownership checks are identical in both environments.

### 7.2 Idempotency on registration

`register_entity` is idempotent: a second `POST /ui/dynamic-entities` with the same `entity_name`
upserts the schema (incrementing `version`). Schema registration is intentionally non-destructive —
existing rows are **not** re-validated against the updated schema (schema evolution is append-only
by convention: adding a new optional property is safe; removing a required property is the
operator's responsibility). The `updated_at` timestamp is refreshed on each upsert.

### 7.3 Admin gate enforcement

All definition CRUD requires `Depends(require_root_session)` which raises HTTP 403 for any
`role != Role.ROOT` caller (`app/auth/deps.py:308-313`). A non-root session that calls
`POST /ui/dynamic-entities` receives `403` before the service layer is reached. Generated CRUD
(`/ui/dynamic/{entity_name}`) requires only `require_ui_session` (standard user sessions) because
the *use* of a registered entity is a user-facing feature; registration is the privileged act.

### 7.4 Input sanitization / injection prevention

`data` fields are stored as a DDB Map (`M` type). Values are only read back and serialized as JSON
— they are never interpolated into queries, DDB expressions, or shell commands. DynamoDB's
attribute-path expression syntax (`#key = :val`) is used with explicit
`ExpressionAttributeNames` and `ExpressionAttributeValues` on all `update_item` calls, as in the
rest of the codebase. No SQL, no expression injection risk.

Property names in the stored schema are validated at registration time to match
`^[a-zA-Z][a-zA-Z0-9_]{0,63}$` — this prevents a schema property name from containing characters
that could break a DynamoDB expression attribute name.

### 7.5 No money-safety concerns

CSN-003 is purely a metadata/CRUD feature. No ledger rows, no wallet reads/writes, no payment-method
access, no `new_ledger_entry`, no `apply_wallet_delta`, no `settle_or_reverse_ledger` call exists in
this ticket. Money-safety is not in scope (and would be a hard error if any such call appeared here).

### 7.6 Audit completeness

Every admin mutation emits `audit_event` (`app/services/alerts.py:644`) before returning:
- `dynamic_entity.registered` — fired by `register_entity`, fields: `entity_name`, `version`,
  `property_count`
- `dynamic_entity.deleted` — fired by `delete_entity`, fields: `entity_name`

These follow the pattern in `app/routers/api_keys.py:21, 28` where `audit_event` is called
immediately after the successful service call and before the response is returned.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact when flag is off

The two new tables are created by `scripts/local-ddb-init.py` unconditionally (table creation is
idempotent via `CreateTable` with `ResourceInUseException` handling). The tables existing in DynamoDB
does not activate any behavior — only the registered routers activate I/O.

In production: DynamoDB table creation is a one-time operation requiring `CreateTable` + table
`ACTIVE` wait before the flag is turned on. The migration plan is:
1. Deploy the code (tables created at stack init or via a one-time migration script).
2. Verify tables are `ACTIVE`.
3. Set `DYNAMIC_ENTITIES_ENABLED=true` and restart the service.

No existing table is altered. No data migration is required.

### 8.2 Schema evolution (existing entities)

When an operator updates a registered entity's schema (e.g., adds a new optional property), existing
rows whose `data` no longer passes a stricter schema are not retroactively invalidated. Reads always
return raw stored `data`. Writes always validate against the **current** schema. This is intentional
append-forward compatibility — the same model used by the billing ledger's `extra` pass-through map.

### 8.3 Naming collision with future routes

The denylist in §5.1 prevents registration of any entity name whose CRUD path `/ui/dynamic/{name}`
would shadow an existing registered path. FastAPI resolves routes in registration order, so the
static admin router (`/ui/dynamic-entities`) is registered **before** the CRUD router
(`/ui/dynamic/{entity_name}`) to prevent the literal string `"dynamic-entities"` from being
captured as an `entity_name` path parameter.

## 10. Open Questions / Assumptions

1. **Schema evolution enforcement.** Currently the spec allows operators to tighten a schema (e.g.,
   add a new `required` field) without re-validating existing rows. Should an explicit "validate
   existing rows" dry-run endpoint be added? Left as a follow-up — the additive posture is safer.

2. **Admin visibility of all rows.** The current spec has ROOT only accessing definition
   management; a future admin "list all rows across all owners for an entity" path is not included.
   The `list_rows` without `owner_sub` scan path is stubbed in the service but not exposed in the
   router. Confirming this scope boundary is desirable before implementation.

3. **Field-level ACL on dynamic entities.** The OBP "Views" concept (`OBP_VIEWS_ENTITLEMENTS_TICKETS.md`)
   could eventually gate which `data` fields are visible per caller. Out of scope here; dynamic
   entities are owner-all-or-nothing for now.

4. **`jsonschema` library availability.** The current posture is pure-Python bounded validation to
   avoid adding a new pip dependency. If `jsonschema` is added to `requirements.txt` for another
   feature, `validate_against_schema` should be refactored to use it for full Draft-7 compliance.
   The bounded-validator surface (§5.2) is narrow enough that the refactor would be isolated to one
   function.

5. **Max row count per entity.** No hard cap exists today on total rows per entity (only a per-user
   per-hour write rate). A per-entity partition-level cap (`DYNAMIC_ENTITY_MAX_ROWS_PER_ENTITY`,
   default unlimited) could be added if abuse is observed — left as a post-launch tunable.

6. **Row bulk-delete on entity deletion.** The current spec uses TTL reaping (7-day window). If
   immediate deletion is required for compliance/privacy reasons, a background job or streaming
   `delete_item` loop would be needed. This is not wired here.
