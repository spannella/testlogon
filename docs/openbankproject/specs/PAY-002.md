# PAY-002 — Standing orders — recurring outbound payment entity + scheduler executor

**Ticket type**: Backend (entity + recurring job)
**Priority**: P1
**Estimate**: 3.5 days
**Depends on**: PAY-001 (counterparty entity), TXR-001 (TransactionRequest create), TXR-004 (execute), PAY-004 (FX convert — soft dependency for non-USD counterparties)
**Status**: Unimplemented

## 1. Summary & Goal

PAY-002 adds the **standing order** — a user-defined instruction to pay a stored
counterparty (PAY-001) a fixed amount on a repeating cadence (weekly, biweekly, or
monthly). On each due occurrence the engine emits exactly one `type=COUNTERPARTY`
Transaction Request (TXR-001/TXR-004) and advances the schedule. No money-out logic
lives in PAY-002 itself; the single payment rail is TXR.

The goal is to deliver:

1. A `standing_orders` DynamoDB table with a `ByDue` GSI that the unified scheduler
   can query without a scan.
2. A `app/services/standing_orders.py` service providing full CRUD, pause/resume/cancel,
   and the `execute_due_standing_order` function that emits the TXR request.
3. A `app/routers/standing_orders.py` router (prefix `/ui/standing-orders`, cookie
   session auth, CSRF) registered in `app/main.py` behind the
   `PAYMENTS_COUNTERPARTIES_ENABLED` flag.
4. A thin executor step wired into the **existing** `run_unified_scheduler_loop`
   (`app/services/unified_scheduler.py:35`) — no new asyncio loop or startup task.
5. Hermetic pytest coverage + an E2E spec (PAY-005).

Everything is additive and default-OFF. Existing billing, scheduling, and MFA surfaces
are untouched.

## 3. Data Model

### New table: `standing_orders`

Single-table design. Each row is a standing order for one user.

**TableDef** (add to `scripts/local-ddb-init.py`):

**Due-index discipline**: `GSI_DUE_PK="SO_DUE"` and `next_run_at` are present on

them. This mirrors `scheduled_actions.cancel_action` (`scheduled_actions.py:251`).

Note `GSI_DUE_PK="SO_DUE"` is distinct from `scheduled_actions`'s `"DUE"` to avoid
cross-table GSI naming conflicts if both tables ever share a secondary-index name in the
same account.

**`execute_due_standing_order` — detailed steps:**

1. **Load and guard.** `get_standing_order(user_sub, standing_order_id)`. If
   `status != "active"` or `next_run_at` is absent → log + return (idempotent skip;
   should not happen under normal scheduler flow).

2. **Build idempotency key.** `idempotency_key = f"{standing_order_id}#{next_run_at}"`.
   This is deterministic per occurrence — a scheduler retry with the same
   `next_run_at` reuses the same key (money-safety §2 from the ticket file).

3. **FX conversion (conditional).** Load the counterparty via
   `counterparties.get_counterparty(user_sub, counterparty_id)`. If
   `counterparty.currency != "usd"`, call
   `fx_rates.convert(amount_cents, counterparty.currency, "usd")` (PAY-004). Stamp
   `fx_rate`, `source_currency`, `source_amount_cents` into the TXR `target` map.
   If `fx_rates.convert` raises `LookupError("fx_rate_missing")`, mark the
   occurrence `skipped` (`audit_event("standing_order.skipped", ...)`) and do NOT
   advance `next_run_at` — the order stays due and will retry next scheduler cycle.
   This is the safe failure mode (no debit, no schedule advance).

4. **Emit the COUNTERPARTY Transaction Request.**

   ```python
   from app.services import txn_requests
   txr_body = TxnRequestCreateIn(
       type="COUNTERPARTY",
       amount_cents=usd_amount_cents,   # after FX conversion
       currency="usd",
       target={
           "counterparty_ref": counterparty_id,
           "standing_order_id": standing_order_id,
           "fx_rate": fx_rate_used,         # None when currency is already usd
           "source_currency": source_ccy,   # None when same
       },
       reason=so.get("reason") or "standing_order",
       idempotency_key=idempotency_key,
   )
   txr = txn_requests.create_request(user_sub, txr_body, req=req)
   txn_requests.execute_request(user_sub, txr["request_id"], req=req)
   ```

   TXR owns the wallet debit, fraud gate, ledger writes, and any SCA hold. PAY-002
   never calls `apply_wallet_delta`, `new_ledger_entry`, or `settle_or_reverse_ledger`.

5. **Conditionally advance `next_run_at`.** Compute
   `new_next = _next_occurrence(cadence, prev_next_run_at)`. Determine
   `completed = end_at is not None and new_next > end_at`.

   ```python
   if completed:
       T.standing_orders.update_item(
           Key={"user_sub": user_sub, "standing_order_id": standing_order_id},
           UpdateExpression=(
               "SET #st=:completed, runs_count=runs_count+:one, "
               "last_run_at=:now, updated_at=:now "
               "REMOVE GSI_DUE_PK, next_run_at"
           ),
           ConditionExpression="next_run_at = :expected",
           ExpressionAttributeNames={"#st": "status"},
           ExpressionAttributeValues={
               ":completed": "completed", ":one": 1,
               ":now": now_ts(), ":expected": prev_next_run_at,
           },
       )
   else:
       T.standing_orders.update_item(
           Key={"user_sub": user_sub, "standing_order_id": standing_order_id},
           UpdateExpression=(
               "SET next_run_at=:new_next, GSI_DUE_PK=:due, "
               "runs_count=runs_count+:one, last_run_at=:now, updated_at=:now"
           ),
           ConditionExpression="next_run_at = :expected",
           ExpressionAttributeValues={
               ":new_next": new_next, ":due": "SO_DUE", ":one": 1,
               ":now": now_ts(), ":expected": prev_next_run_at,
           },
       )
   ```

   The `ConditionExpression="next_run_at = :expected"` is money-safety §3: two
   concurrent ticks for the same occurrence — only one advances; the losing
   `ConditionalCheckFailedException` is caught and treated as a no-op (the idempotency
   key on the TXR side already collapsed any double-create). This mirrors the slot-claim
   conditional in `scheduled_actions.claim_action` (`scheduled_actions.py:384`).

6. **Audit.** `audit_event("standing_order.executed", user_sub, standing_order_id=..., request_id=..., amount_cents=..., idempotency_key=...)`.

## 5. Detailed Behavior & Edge Cases

### `_next_occurrence` cadence arithmetic

- **weekly**: `from_ts + 7 * 86400`. Pure integer offset. DST-safe (UTC only).
- **biweekly**: `from_ts + 14 * 86400`. Same.
- **monthly**: Use stdlib `datetime` in UTC. Advance the `month` field by 1 (wrapping
  December → January + year+1). Handle day-overflow (e.g., January 31 → February 28/29)
  by clamping to `monthrange` last day using `calendar.monthrange`. Convert back with
  `datetime.timestamp()`.

### `start_at` handling

`create_standing_order` computes `first_next = _next_occurrence(cadence, start_at)`.
If `start_at` is in the past the first occurrence is still the next calendar slot after
`start_at`, which may be in the past too — if `first_next <= now`, it becomes
immediately due and will fire on the next scheduler poll. This is intentional: a user
who sets `start_at=yesterday` gets their first run on the next scheduler tick, not a
`400` error.

### Pause / resume state transitions

- `pause` is only valid from `status="active"`. A conditional `update_item` asserts
  `#status = :active`; `ConditionalCheckFailedException` → `409 invalid_transition`.
- `resume` is only valid from `status="paused"`. It computes a fresh `next_run_at =
  _next_occurrence(cadence, now_ts())` (not the original `next_run_at` — time passed
  while paused) and re-adds the GSI keys.
- `cancel` is valid from any non-terminal status (active, paused). A conditional
  `update_item` asserts `status IN (active, paused)` via
  `Attr("status").is_in(["active","paused"])`. Once `cancelled` or `completed` the
  order is terminal; subsequent cancels return `409`.

### `end_at` completion

At step 5 of execution, if `new_next > end_at`, the order transitions to `completed`
and the GSI keys are removed. A standing order whose `end_at` falls between two
executions is always completed on the first tick that would cross it — it never
over-fires.

### SCA hold (PENDING TXR)

When `execute_request` returns a request with `status="PENDING"` (TXR-003 SCA
threshold crossed), PAY-002 does **not** advance `next_run_at` — the occurrence is
considered in-flight. The standing order sits with its current `next_run_at` until the
SCA challenge is answered and TXR completes or fails. Once TXR completes, PAY-002
needs to be notified to advance; this is handled by a TXR completion callback
(TXR-004 design detail) or, pragmatically for the first iteration, by the scheduler
re-querying the still-due order on the next poll and seeing that the TXR for this
`idempotency_key` already exists (TXR `create_request` returns the existing item);
PAY-002 detects `status="PENDING"` on the returned TXR and skips the advance again,
auditing `"standing_order.skipped"` with `reason="sca_pending"`.

### TXR `FAILED` outcome handling

When `execute_request` returns `status="FAILED"` (e.g., `insufficient_funds`, fraud
`block`, or — in the early iteration before the real COUNTERPARTY rail is wired —
`counterparty_unsupported` per TXR-004), `execute_due_standing_order` must **advance
`next_run_at`** to the next slot (same conditional update as a successful execution) and
audit `"standing_order.failed"` with `reason=txr["failure_reason"]`. Leaving
`next_run_at` unchanged on `FAILED` would cause the order to re-fire on every
scheduler poll until the end of time, accumulating `FAILED` TXRs — a correctness and
storage hazard. The idempotency key uniquely scopes to `(order, occurrence)`, so
advancing to the next slot gives the next occurrence a fresh key and no re-debit risk.

### Idempotent retry safety

The idempotency key `f"{standing_order_id}#{next_run_at}"` is scoped to one
`(order, occurrence)` pair. If the scheduler crashes after `create_request` but
before the conditional `update_item` advance, the next scheduler run:

1. Finds the order still in the `ByDue` GSI (same `next_run_at`).
2. Calls `execute_due_standing_order` again.
3. `create_request` receives the same `idempotency_key` → returns the existing TXR
   without writing a second row.
4. `execute_request` on an already-`COMPLETED` request is a no-op (TXR-004's
   conditional guard sees `status != PENDING` and returns the terminal item).
5. The conditional advance proceeds, moving the order to the next slot.

At most one debit per occurrence — guaranteed by the TXR idempotency key and the
`next_run_at` conditional.

### Counterparty deleted while orders active

`counterparties.delete_counterparty` (PAY-001) checks for active standing orders
before deleting (by querying `T.standing_orders` by `user_sub` and filtering
`counterparty_id` match). If any active order references the counterparty, the delete
returns `409 counterparty_in_use`. PAY-002 itself is resilient: if somehow the
counterparty is missing at execution time, `get_counterparty` raises `404`, the order
is audited as `"standing_order.skipped"` with `reason="counterparty_not_found"`, and
`next_run_at` is not advanced.

### Currency mismatch / FX unavailable

If `counterparty.currency != "usd"` and `fx_rates.convert` raises
`LookupError("fx_rate_missing")`, the execution is audited as
`"standing_order.skipped"` with `reason="fx_rate_missing"`. The order stays active
and due — it will retry on the next scheduler cycle (when hopefully an admin has set
the rate via PAY-004). This is the correct money-safe behavior: do not debit in a
wrong currency.

### Concurrent scheduler workers

DynamoDB Local and real DynamoDB are consistent. Two scheduler pods that both see
the same due order:

- Both call `execute_due_standing_order`.
- Both call `txn_requests.create_request` with the same idempotency key → second
  call returns the existing TXR, no second row.
- Both try the conditional `update_item` asserting `next_run_at = :expected` → one
  advances, the other gets `ConditionalCheckFailedException` → logged and no-op.

Exactly one execution, exactly one money movement per occurrence.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 dev/prod parity

There is **no `if S.dev_mode` branch** in any PAY-002 business logic. The single code
path runs against DynamoDB Local (port 8001) in dev and real DynamoDB in prod. TXR's
wallet-delta calls go through `billing_shared.apply_wallet_delta`, which is already
parity-safe. FX conversion is through `fx_rates.convert`, which reads from DDB
(no mock-vs-real divergence in the data path). The existing `moto` in-process S3 and
the mock KMS are untouched.

### Idempotency: per-occurrence, end-to-end

1. **TXR idempotency key** (`{standing_order_id}#{next_run_at}`): TXR-001 persists the
   key on the item (`TXR-001.md:266`); the deduplication is owned by **TXR-004 §4.6**
   (`TXR-004.md:389-393`): `create_request` queries `T.txn_requests` within the caller's
   `user_sub` PK partition via `FilterExpression="idempotency_key = :k"` and returns the
   existing non-`FAILED` item, collapsing duplicate creates. A retry returns the existing item.
2. **Conditional next_run advance**: `update_item` with
   `ConditionExpression="next_run_at = :expected"` ensures at most one slot advance
   per occurrence regardless of concurrency or retries.

### Money-safety binding constraints

1. **PAY-002 never calls `apply_wallet_delta`, `new_ledger_entry`, or
   `settle_or_reverse_ledger` directly.** All money movement flows through TXR-004's
   `execute_request`. Verified by code review / grep.
2. **No double-charge.** TXR idempotency key collapses duplicate TXR creates; TXR-004's
   `IN_FLIGHT`/`COMPLETED` status-as-lock conditional write prevents double-execution.
   The deduplication mechanism IS specified — in **TXR-004 §4.6** (`TXR-004.md:389-393`):
   `create_request` queries `T.txn_requests` within the caller's `user_sub` partition via
   `FilterExpression="idempotency_key = :k"` and returns the existing non-`FAILED` item.
   PAY-002's retry-safety (`create_request` returning the existing item for a duplicate key)
   is therefore satisfied by the TXR cluster, and is exercised in
   `test_retry_same_occurrence_no_second_txr`. The true money-safety guard is the
   `IN_FLIGHT` conditional write at execute time (`TXR-004.md:428,532`), not the create-time
   dedup (which is best-effort, `TXR-004.md:393`).
3. **Conditional `next_run_at` advance.** Losing concurrent writes are no-ops.
4. **Fraud gate.** TXR-004 calls `billing._fraud_gate` (`billing.py:118`) before any
   wallet delta. PAY-002 inherits this without duplicating it.
5. **FX is annotation-only.** `fx_rates.convert` returns a `usd`-denominated
   `amount_cents`; it writes no ledger row and does not change the wallet directly.
   The ledger stays single-currency.

### Security

- **Ownership enforcement**: `get_standing_order` uses `Key={user_sub, standing_order_id}`.
  A user cannot read or mutate another user's standing orders. The `user_sub` in the
  key comes exclusively from `require_ui_session` (cookie auth, `ui_access_token` JWT).
- **CSRF**: all non-GET endpoints require `x-csrf-token` header (CLAUDE.md conventions).
- **Amount limit at create**: standing orders with `amount_cents > S.txn_request_limit_counterparty_cents`
  are rejected at create time with `400 amount_over_limit`, preventing silent
  schedule-time failures.
- **SCA escalation**: high-value executions (above `S.txn_request_sca_threshold_cents`)
  produce a `PENDING` TXR and an SCA challenge via TXR-003; PAY-002 does not bypass
  this gate.
- **Audit trail**: every state transition and execution emits `audit_event` to
  `T.alerts` for compliance traceability.

## 10. Open Questions / Assumptions

1. **SCA pending → when to advance `next_run_at`?** The spec above leaves the order
   at its current `next_run_at` when TXR enters `PENDING`. On the next scheduler poll
   the order is still due; `create_request` returns the existing TXR; PAY-002 checks
   its status. If `PENDING` → skip (audit `"standing_order.skipped" reason="sca_pending"`).
   If `COMPLETED` → advance. If `FAILED` → treat as failed execution, advance anyway
   (to avoid the order getting permanently stuck). **Open**: should a user be able to
   manually retry a failed occurrence, or should it simply proceed to the next slot?
   Default assumption: advance on failure (do not accumulate missed runs).

2. **`biweekly` vs `fortnightly` vs `semi-monthly`**: This spec uses `biweekly = 14
   days` (every two weeks). OBP uses `"STANDING_ORDER_INTERVAL_FORTNIGHT"`. If the
   enum value needs to match the OBP wire name exactly, rename in `app/models.py`.

3. **Missed executions while paused**: When a standing order is resumed after a long
   pause, it fires from the next slot after now — it does not back-fill missed
   occurrences. This matches the `audit_export_schedule` pattern
   (`audit_export_schedule.py:138`). If back-fill is required, it is a future feature.

4. **`start_at` in the past**: First `next_run_at = _next_occurrence(cadence, start_at)`
   may be in the past. The scheduler will fire it immediately. No `400` is raised.
   Alternative: reject `start_at` that would produce an already-past `next_run_at`.
   Assumption: allow; fire immediately on next poll.

5. **TXR-004 callback on COMPLETED**: For the SCA-pending case to auto-advance, TXR-004
   could emit an event or call a `standing_orders.on_txr_completed(idempotency_key)`
   hook. This is a TXR-004 design decision outside PAY-002's scope. For the first
   iteration PAY-002 relies on the poll-based check described in §5.

6. **Counterparty currency mismatch and FX not yet built**: PAY-004 is a soft
   dependency. If PAY-004 has not yet landed, all counterparties should be created with
   `currency="usd"` to avoid FX skips. The `create_standing_order` service should
   reject non-`"usd"` `currency` values if `S.fx_rates_enabled` (PAY-004 flag) is
   false, to provide a clear `400` rather than a silent runtime skip.
