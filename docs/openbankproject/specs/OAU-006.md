## 1. Summary & Goal

OAU-006 delivers the hermetic, offline regression test suite that covers every code path introduced by OAU-001 through OAU-005. The goal is fivefold:

1. Prove that every acceptance criterion stated in OAU-001 through OAU-005 is mechanically verified by a test that runs without any external process (no real DynamoDB, no real AWS KMS, no network, no Cognito).
2. Establish the same fixture pattern — moto in-memory DDB bound to frozen `T.oauth_consumers` via `object.__setattr__`, frozen `S` flags toggled the same way, async handlers invoked on a fresh `asyncio.new_event_loop()` — used consistently across all five test modules so future contributors can extend coverage without inventing new patterns.
3. Provide complete negative-path coverage for every reject branch: replayed auth codes, PKCE mismatches, redirect-URI violations, wrong `client_secret`, out-of-allowlist scopes, disabled consumers, and old secrets after rotation.
4. Assert the SECOPS-007 invariants: no `if S.dev_mode:` branch is exercised by any test; the same code path runs under moto as would run against real DynamoDB in production.
5. (Optional, within this ticket's scope) Provide a Playwright E2E section that drives the full browser flow against the live local stack with the OAU flags enabled, serving as a smoke test for the frontend-facing authorize redirect.

The five test modules map one-to-one to the OAU tickets they cover: `test_oau_001_consumer_registry.py`, `test_oau_002_authcode_pkce.py`, `test_oau_003_oidc.py`, `test_oau_004_scope_enforcement.py`, and `test_oau_005_lifecycle.py`. All five live under the `tests/` directory alongside `test_gap_0286_0287_kyc_partner_api.py` and `test_gap_0241_0242_google_drive_oauth.py`, which serve as the canonical recipes for this project's hermetic async test pattern.

            {"AttributeName": "sk",        "KeyType": "RANGE"},

### Handle injection

```python
class _BaseOauTest(unittest.TestCase):
    _mock_ctx = None   # moto mock_aws context
    _ddb       = None  # boto3 DynamoDB resource
    _tbl       = None  # the in-memory table

    def setUp(self):
        self.stack = ExitStack()
        self._mock_ctx = mock_aws()
        self._mock_ctx.__enter__()
        self._ddb = boto3.resource("dynamodb", region_name="us-east-1")
        self._tbl = _make_oauth_consumers_table(self._ddb)
        # CORRECTED: also create and bind T.sessions — required by require_fresh_mfa (sessions.py:699)
        # which reads mfa_verified_at from T.sessions via ctx["session_id"].  Without this binding
        # the MFA-gate tests either crash or silently pass because compute_required_factors
        # (sessions.py:571) catches DDB errors and returns [] → require_fresh_mfa returns early.
        self._sessions_tbl = self._ddb.create_table(
            TableName="sessions_test",
            KeySchema=[
                {"AttributeName": "user_sub", "KeyType": "HASH"},
                {"AttributeName": "session_id", "KeyType": "RANGE"},
            ],
            AttributeDefinitions=[
                {"AttributeName": "user_sub", "AttributeType": "S"},
                {"AttributeName": "session_id", "AttributeType": "S"},
            ],
            BillingMode="PAY_PER_REQUEST",
        )

        # Bind frozen T handles
        original_tbl = getattr(T, "oauth_consumers", None)
        object.__setattr__(T, "oauth_consumers", self._tbl)
        self.stack.callback(object.__setattr__, T, "oauth_consumers", original_tbl)

        original_sessions = getattr(T, "sessions", None)
        object.__setattr__(T, "sessions", self._sessions_tbl)
        self.stack.callback(object.__setattr__, T, "sessions", original_sessions)

        # Toggle flags
        _set_settings(
            self.stack,
            oauth_provider_enabled=True,
            api_key_pepper="test-pepper-for-oau-tests",
            ws_token_secret="test-ws-token-secret",
            ui_access_token_secret="test-access-token-secret",
        )

    def tearDown(self):
        self.stack.close()
        self._mock_ctx.__exit__(None, None, None)
```

All five test classes inherit or replicate this pattern; OIDC-specific tests additionally patch `kms_encrypt`/`kms_decrypt` and toggle `oauth_provider_oidc_enabled=True`.

> **NOTE on MFA gate tests:** `require_fresh_mfa` (`app/services/sessions.py:699`) first calls `compute_required_factors(user_sub)` (`sessions.py:571`), which queries `T.totp`, `T.sms`, and `T.email` for enrolled factors. If the user has no enrolled factors the function returns `[]` and `require_fresh_mfa` exits immediately — the stale-`mfa_verified_at` branch is never reached. To make the MFA-staleness test meaningful, the simplest approach is to patch `require_fresh_mfa` at the router namespace (`app.routers.oauth_consumers.require_fresh_mfa`) rather than injecting session rows and TOTP records into multiple moto tables. Alternatively, seed a `T.totp` row with `enabled=True` (requires also binding `T.totp` in setUp) so `compute_required_factors` returns `["totp"]`, then seed the sessions table with a session carrying a stale `mfa_verified_at`. The patch approach is preferred for test isolation.

## 5. Detailed Behavior & Edge Cases

### 5.1 Registry tests (`test_oau_001_consumer_registry.py`)

**Happy path: create → list → get → update → delete**

- `create_consumer` returns `client_id`, `client_secret_prefix` (`oc_{client_id[:8]}`), and the one-time plaintext `client_secret` (`oc_{client_id}.{secret}`).
- A second `get_consumer(client_id)` returns the META row with `client_secret_hash` present but never returns `client_secret` plaintext.
- `list_consumers("alice")` returns the consumer with `client_secret_hash` omitted from the response shape (stripped before serialisation, as `list_api_keys` does).
- `update_consumer("alice", client_id, name="New Name")` changes only `name`; a separate `get_consumer` confirms the change and that `created_at` is unchanged.
- `delete_consumer("alice", client_id)` removes the META row; `get_consumer` returns `None`.

**Hash correctness:**

```python
from app.services.api_keys import api_key_hash
# create_consumer return dict: {client_id, client_secret, client_secret_prefix, name, created_at}
# client_secret format: f"oc_{client_id}.{raw_secret}"
raw_secret = result["client_secret"].split(".", 1)[1]  # strip "oc_{id}." prefix
meta = get_consumer(result["client_id"])  # read full META item from DDB
assert meta["client_secret_hash"] == api_key_hash(raw_secret)
# CORRECTED: original had result["stored_hash"] — that key does not exist in the create_consumer
# return value. The hash lives in the DDB META item, accessible via get_consumer().
```

**Redirect-URI rejection (400):**

- `redirect_uris=["ftp://example.com/cb"]` → `{"code": "invalid_redirect_uri"}`. <!-- CORRECTED: OAU-001 §4 `_validate_redirect_uris` raises code "invalid_redirect_uri", not "redirect_uri_invalid" -->
- `redirect_uris=[""]` → same.
- `redirect_uris=["https://"]` (empty netloc) → same.

**Scope rejection (400):**

- `allowed_scopes=["nonexistent:scope"]` → `{"code": "invalid_scope"}` because `"nonexistent:scope"` is not in the `API_KEY_ROUTE_SCOPE_REGISTRY` vocabulary. <!-- CORRECTED: OAU-001 §4 `_validate_allowed_scopes` raises code "invalid_scope", not "scope_invalid" -->

**Owner isolation (404):**

- `update_consumer("bob", client_id_owned_by_alice, ...)` raises `HTTPException(404)` via the `ConditionExpression="owner_sub = :u"` failure.
- `delete_consumer("bob", client_id_owned_by_alice)` same.

**MFA requirement:**

- `require_fresh_mfa` reads `mfa_verified_at` from `T.sessions` (not from `ctx`), so the test must: (a) bind `T.sessions` to a moto table in `setUp`, (b) seed a session row with a stale `mfa_verified_at`, and (c) include `session_id` in `ctx`. Alternatively, patch `require_fresh_mfa` at the router namespace (`app.routers.oauth_consumers.require_fresh_mfa`) to raise directly. The simpler approach is patching. <!-- CORRECTED: original spec said "Inject ctx['mfa_verified_at'] = ...", but require_fresh_mfa (sessions.py:699) ignores ctx['mfa_verified_at']; it reads from T.sessions via ctx['session_id']. Additionally, compute_required_factors (sessions.py:571) returns [] if T.totp/sms/email have no enrolled factors, causing require_fresh_mfa to return early without checking staleness — making the test a no-op unless a factor is seeded or require_fresh_mfa is patched. -->

### 5.2 Auth-code/PKCE tests (`test_oau_002_authcode_pkce.py`)

**PKCE S256 verification:**

- `code_verifier` whose `BASE64URL(SHA256(verifier))` does not equal the stored `code_challenge` must return `{"error": "invalid_grant", "error_description": "code_verifier mismatch"}` (400).
- A `code_verifier` that is the correct inverse passes.

**Single-use auth code (replay attack prevention):**

- Exchange the code once → access token returned (200).
- Exchange the same code a second time → 400, because the conditional `update_item` with `ConditionExpression="attribute_not_exists(consumed_at)"` fails (the `consumed_at` attribute now exists on the row). This is the same mechanism as `provider_oauth.py:203-215` and the cart-recovery one-time-use pattern (`CART_RECOVERY_LINK_TTL_DAYS` section in CLAUDE.md).

**Redirect-URI mismatch:** `redirect_uri` in the token request differs from the one stored on the code row → `{"error": "invalid_grant"}`.

**Wrong `client_secret` (confidential client):** `verify_client_secret` returns false → `{"error": "invalid_client"}`.

**Disabled consumer at token endpoint:** `set_consumer_enabled` called before `/token` exchange → `{"error": "unauthorized_client", "code": "oauth_consumer_disabled"}` (401).

**Out-of-allowlist scope at `/authorize`:** `scope="admin:root"` (not in consumer's `allowed_scopes`) → 403. `scope` that is a subset of `allowed_scopes` passes.

**Refresh-token rotation:** Issue refresh token (`offline_access` in scope), call `/token` with `grant_type=refresh_token` → new access token; old refresh token hash no longer matches in DDB (the grant row is updated).

**DirectLogin gate:** When `OAUTH_PROVIDER_DIRECTLOGIN_ENABLED=False`, `grant_type=password` → `{"error": "unsupported_grant_type"}`. When `True`, patch `_verify_local_password` to return `"alice"` and assert access token is issued.

**OAuth-bearer acceptance by `get_authenticated_user`:** Call `get_authenticated_user` with a mock `Request` carrying `Authorization: Bearer <issued_token>` and assert the returned `AuthenticatedUser.sub == "alice"` and `request.state.oauth_scope == "messager:read"`.

### 5.3 OIDC tests (`test_oau_003_oidc.py`)

**Discovery document completeness:**

All of the following keys must be present and non-empty in `GET /.well-known/openid-configuration`: `issuer`, `authorization_endpoint`, `token_endpoint`, `jwks_uri`, `userinfo_endpoint`, `response_types_supported`, `grant_types_supported`, `scopes_supported`, `id_token_signing_alg_values_supported`, `code_challenge_methods_supported`. `scopes_supported` must include `"openid"`, `"profile"`, `"email"`, and at least one scope from `API_KEY_ROUTE_SCOPE_REGISTRY`.

**JWKS stability:** Call `GET /oauth/jwks` twice → same `kid`; the key is stored in DDB so a second call reuses the stored keypair rather than generating a new one.

**`id_token` absent when `openid` not in scope:** Issue a token with `scope="messager:read"` and assert `"id_token"` key is absent from the token response.

**`id_token` present when `openid` in scope:** Issue a token with `scope="openid messager:read"` and assert `id_token` is returned, verifiable against the JWKS public key, with correct `iss`, `aud`, `sub`, `nonce`. The `nonce` claim must equal the `nonce` parameter passed to `/authorize`.

**Profile/email claim gating:** Token with `scope="openid profile email"` → `id_token` carries `email` and `name` claims (patch `T.users.get_item` to return a user with those fields). Token with `scope="openid"` only → neither `email` nor `name` appears in the `id_token`.

**`/userinfo` scope filtering:** Call `GET /userinfo` with a token carrying `scope="openid profile"` → response includes `name` but not `email`. With `scope="openid email"` → `email` but not `name`. Without any token → 401.

**OIDC-flag-off:** Set `oauth_provider_oidc_enabled=False`; the OIDC router is not registered, so calls to the discovery/JWKS/userinfo paths return 404, and `POST /oauth/token` (OAU-002 path) returns no `id_token`.

**Private key never exposed:** The OIDC signing-key DDB row (per OAU-003 §3.2: PK=`"OIDC_SIGNING_KEY"`, SK=`"META"`) stores the encrypted PEM under field `private_key_ct_b64` (KMS-encrypted, base64), never plaintext. Assert `"private_key_pem"` and `"private_key"` are not keys in the stored DDB item. <!-- CORRECTED: OAU-003 §3.2 defines the row at PK="OIDC_SIGNING_KEY"/SK="META" with field "private_key_ct_b64", not at sk="KEY#oidc" with field "private_key_kms" as previously stated in section 2.3 of this spec -->

### 5.4 Scope enforcement tests (`test_oau_004_scope_enforcement.py`)

**Allowed path:** `GET:/messaging/conversations` with `scope="messager:read"` → no exception.

**Blocked path:** `POST:/messaging/conversations/{conversation_id}/messages` with `scope="messager:read"` (missing `messager:write`) → `HTTPException(403)` with `code="oauth_insufficient_scope"`, `required_scopes=["messager:write"]`, `granted_scopes=["messager:read"]`.

**Exempt route allowed:** Any route in `API_KEY_ROUTE_EXEMPTIONS` (`api_key_route_scope_registry.py:70`) passes regardless of scope.

**Unregistered route allowed:** A route ID not present in either `API_KEY_ROUTE_SCOPE_REGISTRY` or `API_KEY_ROUTE_EXEMPTIONS` passes (consistent with `is_route_registered_or_exempt` semantics, `api_key_route_scope_registry.py:316-318`).

**Non-OAuth callers unaffected:** A request with no `oauth_scope` on `request.state` (cookie session, api-key principal) → `enforce_oauth_scope_for_route` returns immediately without reading the registry.

**Flag-off:** `oauth_provider_scope_enforcement_enabled=False` → `enforce_oauth_scope_for_route` is a no-op even for OAuth callers; the would-be 403 route returns without raising.

**Denial audit:** Patch `app.services.alerts.audit_event` and assert it is called with `event_type="oauth_scope_denied"` when a scope denial occurs. (Pattern mirrors `app/auth/policy.py:156-165`.)

### 5.5 Lifecycle tests (`test_oau_005_lifecycle.py`)

**Disable instant effect:** Disable consumer → attempt `/authorize` (401 `oauth_consumer_disabled`) → attempt `/token` (401) → attempt bearer auth via `get_authenticated_user` mock (401). Re-enable → all three succeed.

**Owner isolation on disable/enable/rotate:** Calling `set_consumer_enabled("bob", client_id_owned_by_alice, ...)` raises 404 (conditional update failure). Same for `rotate_client_secret`.

**Secret rotation idempotency:** Rotate twice → each rotation returns a fresh plaintext; the second rotation invalidates the first. After each rotation, only the most recent plaintext passes `verify_client_secret`.

**`secret_rotated_at` updated:** After rotation, `get_consumer(client_id)["secret_rotated_at"]` is greater than the pre-rotation value.

**MFA required for lifecycle mutations:** Same approach as OAU-001 tests — patch `require_fresh_mfa` at the router namespace (`app.routers.oauth_consumers.require_fresh_mfa`) to raise `HTTPException(401, "Fresh MFA required")` when testing the stale-MFA path. <!-- CORRECTED: "stale mfa_verified_at injection" was incorrect; require_fresh_mfa reads T.sessions at runtime and exits early if no MFA factors are enrolled, so ctx-dict injection is a no-op -->

**Audit events emitted:** Patch `app.services.alerts.audit_event` and assert each mutation (`oauth_consumer_enable`, `oauth_consumer_disable`, `oauth_consumer_secret_rotate`) emits one call with the correct `event_type` and `client_id`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 parity assertions

The tests are the primary enforcement mechanism for SECOPS-007 in the OAU feature set. Every test runs the production code path — the same `app/services/oauth_consumers.py`, `app/routers/oauth_authorize.py`, `app/services/oauth_scope_enforcement.py`, etc. — against moto in-memory DynamoDB instead of real DynamoDB. Because the `T.oauth_consumers` handle is substituted via `object.__setattr__` rather than through a mock, the production service code makes real boto3 DynamoDB API calls (to moto, not to a mock object). This means that any `if S.dev_mode:` branch that diverts to a shortcut would be detectable if it exists — the tests would then be testing a different code path from production. The invariant: **no OAU code file contains a `if S.dev_mode:` branch**; tests assert this implicitly by running with `S.dev_mode=False`.

### KMS parity

OAU-003's RS256 private-key storage uses `kms_encrypt` / `kms_decrypt` from `app/core/crypto.py:16-25`. The mock KMS server (port 7999, `scripts/mock_kms_server.py`) handles this transparently in the local dev stack. Tests patch these two functions at the source to avoid any KMS dependency, but the patch is a passthrough base64 encode/decode that preserves the round-trip semantics — it does not change the DDB item shape that the real path would produce.

### Single-use code idempotency

The `ConditionExpression="attribute_not_exists(consumed_at)"` pattern (from `provider_oauth.py:203-215`) is the project's standard one-time-use mechanism. The OAU-002 replay test specifically verifies that moto enforces the condition, giving confidence that the same guarantee holds in real DynamoDB (where the same conditional semantics apply). Idempotency is achieved: a consumer that retries a token exchange on network error gets 400 on the retry, not a second token.

### Money-safety

OAU-006 tests no money-movement code. No billing ledger, wallet, or payment-method rows are involved in any OAU ticket. The scope enforcement tests verify that a token with `shopping:checkout:write` scope would be required to POST to the purchase endpoint, but they do not exercise the purchase path itself (that is covered by billing and shop E2E tests). There is no TXR/PAY/ACC consideration in this ticket.

## 10. Open Questions / Assumptions

1. **`require_fresh_mfa` import path in router tests.** The router tests patch `require_fresh_mfa` at `app.services.sessions.require_fresh_mfa`. If the router imports it as `from app.services.sessions import require_fresh_mfa` and calls it by the bound name, patching the module attribute does not intercept the call. The patch target must be `app.routers.oauth_consumers.require_fresh_mfa` (the name in the router's namespace). This is consistent with the pattern in `tests/test_gap_0241_0242_google_drive_oauth.py` where collaborators are patched at the router-module namespace, not at the service module.

2. **`asyncio.new_event_loop()` on Python 3.12.** The `_run(coro)` helper uses `asyncio.new_event_loop()` and `loop.run_until_complete(coro)` rather than `asyncio.run()`. On Python 3.12 `asyncio.run()` is preferred and creates its own event loop; either works, but the project-wide convention (`test_gap_0286_0287_kyc_partner_api.py:51-56`) uses the explicit `new_event_loop` pattern for clarity in parallel-test environments. OAU-006 follows the same pattern.

3. **Confidential vs. public client in happy-path tests.** `test_oau_002_authcode_pkce.py` primarily tests confidential clients (with `client_secret`). The public-client path (`is_confidential=False`, no `client_secret` required, mandatory PKCE) is covered by one dedicated test (`test_public_client_no_secret_required`). If public-client PKCE becomes a primary use case, additional negative-path tests for missing `code_challenge` on public clients should be added.

4. **DirectLogin `password` grant test user.** `test_directlogin_works_when_flag_on` patches `_verify_local_password` at `app.auth.deps._verify_local_password` (the source-module symbol) to return `"alice"` deterministically. Tests do not attempt to create a real password-hash record in moto DDB because the PBKDF2 derivation is not the thing under test here — only the grant-type branch gating is.

5. **Consent screen.** The OAU-002 ticket spec notes that `GET /oauth/authorize` auto-consents for first-party apps, deferring a consent UI to a follow-up. The tests reflect this: there is no UI consent-page assertion. If an explicit consent step is added later, the authorize-handler tests will need to be updated.

6. **E2E dependency on the full stack.** The optional Playwright E2E section requires all OAU-001 through OAU-005 to be fully implemented and deployed to the local stack, plus `OAUTH_PROVIDER_ENABLED=1` in `.env.local`. Running `just e2e` with the flag absent gracefully skips the section.
