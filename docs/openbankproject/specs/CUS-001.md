# CUS-001 — Customer entity — DDB model, table, flag + CRUD + typed attributes

**Ticket type**: Backend — data model + endpoints
**Priority**: P1 (foundation — CUS-002 through CUS-005 all depend on this)
**Estimate**: 3 days
**Flag**: `CUSTOMER_ENTITY_ENABLED` (default `false`)

---

## 1. Summary & Goal

Introduce a first-class **Customer** entity into testlogon, decoupled from any single KYC
case, together with a typed key-value attribute store. Today, identity lives exclusively
inside a KYC case (`app/services/kyc_cases.py:116` `KycCaseStore`). This ticket lifts the
durable customer fields — `customer_number`, legal name, date of birth, contact info,
`branch_id`, `kyc_status` — into a reusable, independently addressable entity that
subsequent tickets (user-link CUS-002, cards CUS-003, financial products CUS-004,
frontend CUS-005) reference by `customer_id`.

The deliverables for this ticket are:

- A new DynamoDB table `customers` with two GSIs.
- `app/services/customers.py` — a `CustomerStore` dataclass with CRUD + optimistic
  concurrency + attribute sub-store, mirroring `KycCaseStore`'s structure.
- `app/routers/customers.py` — five endpoint groups gated by the feature flag.
- Pydantic models in `app/models.py` and table/settings wiring in `app/core/settings.py`,
  `app/core/tables.py`, and `scripts/local-ddb-init.py`.
- Full hermetic pytest coverage in `tests/test_cus_001_customer_entity.py`.

No money movement is introduced in this ticket; there are no interactions with the billing
ledger, wallet, SCA stack, or fraud gate. Those primitives are relevant to CUS-003 (card
charge interactions) and the TXN-REQUEST tickets.

## 2. Context & Current State

**Customer identity today lives only inside a KYC case.** `KycCaseStore.create_case`
(`app/services/kyc_cases.py:120`) writes `user_sub`, `status`, and identity metadata but
there is no standalone entity a card, a message thread, or a financial product can
reference independently of a specific case. The `OWNER#{user_sub}` GSI
(`app/services/kyc_cases.py:67-68`) lets a user's cases be enumerated, but the case is
stateful (it has a lifecycle: `draft → submitted → approved`) and is tied to a submission;
it is not a reusable customer record.

**Optimistic concurrency pattern to copy.** `KycCaseStore.update_case_status`
(`app/services/kyc_cases.py:209-233`) is the canonical pattern: read `version`, compare,
conditional `update_item` with `ConditionExpression="version = :expected_version"`, catch
`ConditionalCheckFailedException`, raise domain-specific `KycCaseConflictError`. This
ticket copies that exact pattern for customer updates.

**Audit infrastructure is ready.** `audit_event` (`app/services/alerts.py:644`) writes an
item to `T.alerts` with `event`, `user_sub`, `ts`, optional `ip`/`user_agent` from
`request`, and arbitrary keyword fields — no setup needed beyond importing it. The `try`
block around the DDB write at line 688 means audit failures never block business logic.
(Line 668 is a separate `try` around `get_profile_identity`; the best-effort DDB write
is at line 688.)

**Admin gate to use.** A shared `require_admin_or_root` FastAPI dependency exists at
`app/auth/policy.py:67` — `async def require_admin_or_root(user: AuthenticatedUser = Depends(get_authenticated_user)) -> AuthenticatedUser`.
It raises `HTTPException(403, {"code": "role_required", ...})` for non-admin callers.
This is the pattern already used by `app/routers/license_agreements.py` and
`app/routers/kyc_translations.py` (`from app.auth.policy import require_admin_or_root`).
The customer router imports and uses this shared dependency — **not** the private
`_require_admin_or_root` from `app/routers/kyc_cases.py:2212`, which calls
`_raise_kyc_error("kyc_admin_role_required")` (a KYC-specific error envelope) and is
private to the KYC router. Using the shared dep also means `require_ui_session` may be
omitted because `require_admin_or_root` already chains `get_authenticated_user`.

**Table handle plumbing.** `app/core/tables.py` exposes `T` as a frozen dataclass of
`_FloatSafeTable` wrappers. The `_FloatSafeTable` proxy at lines 29-66 auto-coerces
`float` → `Decimal` on every `put_item` and `update_item`, so service code never needs
explicit `Decimal()` calls. Adding `T.customers` follows the same `_safe_table(...)` call
pattern used for every existing table (`T = Tables(...)` starts at line 321). The
corresponding settings field is added to the `Settings` dataclass in
`app/core/settings.py` (frozen dataclass pattern, lines 6-7).

**DDB numeric GSI sort key gotcha (CLAUDE.md).** `scripts/local-ddb-init.py` line 35
declares the `TableDef` `attr_types` field (`attr_types: Dict[str, str] = field(default_factory=dict)`);
line 34 is the comment explaining it.
`attr_types={"created_at":"N"}` must be declared whenever a GSI sort key is numeric.
The `sticker_collections` table at lines 79-85 is the closest example — GSI on
`created_at` (N). Omitting this causes DynamoDB Local to store the value as String and
throw `ValidationException` when the query supplies an integer value. Both new GSIs in
this ticket (one does not sort on a number, one does) are handled correctly.

**Auth dependency.** `require_ui_session` is defined in `app/services/sessions.py:330`
(not `app/auth/deps.py`). It is imported in routers as
`from app.services.sessions import require_ui_session`. Its return dict contains
`user_sub`, `session_id`, `role` (as `.value` string), `ip`, and `tenant_id` —
`admin_profile` is NOT in the returned dict; it is accessed via
`AuthenticatedUser = Depends(get_authenticated_user)` (from `app/auth/deps.py:199`),
which is the second dependency used alongside `require_ui_session` in all existing
admin-gated routers. Since `require_admin_or_root` (see above) already chains
`get_authenticated_user`, the customer router does not need a separate
`require_ui_session` dependency for its admin-only endpoints.

**`app/services/kyc_cases.py` does NOT have any customer record today.** Searching for
`customer_number` or `customer_id` in the live codebase returns zero results — the entity
is entirely net-new.

## 3. Data Model

### DynamoDB table: `customers`

Single-table design, one table, PK/SK composite key. All SK variants share the same table
handle `T.customers`.

| Key | Type | Purpose |
|-----|------|---------|
| PK `pk` | S | `CUST#{customer_id}` — partition per customer |
| SK `sk` | S | `META` for the main record; `ATTR#{attribute_id}` for typed attributes |

**META row** — written by `create_customer`, updated by `update_customer`:

| Attribute | Type | Notes |
|-----------|------|-------|
| `pk` | S | `CUST#{customer_id}` |
| `sk` | S | `"META"` |
| `entity_type` | S | `"customer"` (for scan disambiguation) |
| `customer_id` | S | `cust_{uuid4().hex[:12]}` — server-minted |
| `customer_number` | S | string derived from `now_ts()` at creation time; implementation chooses plain `str(now_ts())` (e.g. `"1751745600"`, 10 digits in 2026) — zero-padding is optional and should match §4.2/§5.1 exactly |
| `legal_name` | S | required at create |
| `date_of_birth` | S | nullable ISO-8601 date string, e.g. `"1985-04-23"` |
| `mobile_phone` | S | nullable; stored normalized (E.164 stripped of spaces) |
| `email` | S | nullable; stored lowercased |
| `branch_id` | S | nullable |
| `kyc_status` | S | default `"none"`; set by CUS-002 link when a KYC case is backfilled |
| `created_at` | N | `now_ts()` Unix seconds |
| `updated_at` | N | `now_ts()` on every update |
| `version` | N | starts at `1`; incremented atomically on every `update_customer` |
| `gsi_number_pk` | S | constant `"CUSTNUM"` — partition key for `GSI_NUMBER` |
| `gsi_branch_pk` | S | `BRANCH#{branch_id}` when `branch_id` is non-null, else omitted (sparse) |

**ATTR row** — written by `set_attribute`:

| Attribute | Type | Notes |
|-----------|------|-------|
| `pk` | S | `CUST#{customer_id}` |
| `sk` | S | `ATTR#{attribute_id}` |
| `attribute_id` | S | `attr_{uuid4().hex[:8]}` |
| `name` | S | attribute name |
| `type` | S | one of `STRING`, `INTEGER`, `DOUBLE`, `DATE_WITH_DAY` |
| `value` | S | always stored as string; caller preserves type semantics |
| `created_at` | N | `now_ts()` |

### GSIs

**GSI_NUMBER** — lookup by `customer_number`:

| | Key | Type |
|-|-----|------|
| Partition | `gsi_number_pk` | S (`"CUSTNUM"`) |
| Sort | `customer_number` | S |

`customer_number` is a string, so no `attr_types` override is needed. The constant
`gsi_number_pk="CUSTNUM"` keeps all customer numbers in one GSI partition. This mirrors
how `kyc_cases.py:155` uses `gsi_status_pk = STATUS#{status}` to enumerate all cases of
a given status.

**GSI_BRANCH** — list customers by branch, ordered by creation time:

| | Key | Type |
|-|-----|------|
| Partition | `gsi_branch_pk` | S (`BRANCH#{branch_id}`) |
| Sort | `created_at` | **N** |

**`attr_types={"created_at":"N"}` is mandatory** (CLAUDE.md numeric-GSI gotcha; see
`scripts/local-ddb-init.py:34` `attr_types` field). Customers with no `branch_id` omit
`gsi_branch_pk` entirely, making the GSI sparse — same technique as KYC's sparse
`gsi_status_pk` on non-status rows.

### 4.2 Service: `app/services/customers.py`

```python
@dataclass
class CustomerStore:
    _table: Any = field(default=T.customers)  # matches KycCaseStore and all other stores

    def create_customer(
        self,
        *,
        legal_name: str,
        date_of_birth: str | None = None,
        mobile_phone: str | None = None,
        email: str | None = None,
        branch_id: str | None = None,
        actor_sub: str,
        request=None,
    ) -> dict[str, Any]: ...

    def get_customer(self, customer_id: str) -> dict[str, Any] | None: ...

    def get_by_number(self, customer_number: str) -> dict[str, Any] | None: ...

    def list_by_branch(
        self,
        branch_id: str,
        *,
        cursor: str | None = None,
        limit: int = 50,
    ) -> tuple[list[dict[str, Any]], str | None]: ...

    def update_customer(
        self,
        *,
        customer_id: str,
        expected_version: int,
        actor_sub: str,
        request=None,
        **fields,          # legal_name, date_of_birth, mobile_phone, email, branch_id, kyc_status
    ) -> dict[str, Any]: ...

    def set_attribute(
        self,
        customer_id: str,
        *,
        name: str,
        type: str,
        value: str,
        actor_sub: str,
        request=None,
    ) -> dict[str, Any]: ...

    def list_attributes(self, customer_id: str) -> list[dict[str, Any]]: ...

    def delete_attribute(
        self, customer_id: str, attribute_id: str, *, actor_sub: str, request=None
    ) -> bool: ...
```

**`create_customer` internals:**
- Mint `customer_id = f"cust_{uuid4().hex[:12]}"`.
- Mint `customer_number = str(now_ts())` (unique enough for correctness; collision
  probability is negligible at human scale; if needed a short suffix can be appended).
- Write META row with `version=1`.
- If `branch_id` is set, also write `gsi_branch_pk = f"BRANCH#{branch_id}"`.
- Call `audit_event("customer.created", actor_sub, request, customer_id=customer_id)`.
- Return the item dict.

**`update_customer` internals:**
- Read the existing item; raise `CustomerNotFoundError` (404) if absent.
- Compare `existing["version"]` to `expected_version`; if mismatched raise
  `CustomerConflictError` (409) before even attempting the DDB write — fail fast.
- Build `UpdateExpression` including all provided non-None fields plus `updated_at`,
  `version = version + 1`, and refreshed GSI fields if `branch_id` changed.
- Issue `update_item` with `ConditionExpression="version = :expected_version"`.
- Catch `ConditionalCheckFailedException` → raise `CustomerConflictError`.
- Call `audit_event("customer.updated", ...)`.
- Return re-fetched item via `get_customer`.

**`set_attribute` internals:**
- Validate `type` ∈ `{"STRING", "INTEGER", "DOUBLE", "DATE_WITH_DAY"}` (ValueError →
  HTTP 422 in the router).
- Check the customer META exists; raise `CustomerNotFoundError` if absent.
- Write `ATTR#{attribute_id}` row (`put_item`; no conditional needed — last-write-wins
  for attributes is acceptable; use a natural `attribute_id` keyed by `name` if
  upsert semantics are desired, or always mint a new UUID for append semantics — see
  Open Questions).
- Call `audit_event("customer.attribute_set", ...)`.

## 5. Detailed Behavior & Edge Cases

### 5.1 `customer_number` uniqueness

`customer_number` is seeded from `now_ts()` at creation time. In tests and low-traffic
environments this produces values like `"1751745600"`. In a high-concurrency environment,
two simultaneous creates in the same second would produce the same value. The
`GSI_NUMBER` GSI (PK=`CUSTNUM`, SK=`customer_number`) does not enforce uniqueness by
itself.

**Mitigation**: `create_customer` does a conditional `put_item` with
`attribute_not_exists(pk)` on the META row (which uses `customer_id` in `pk`, not
`customer_number`). If two customers somehow get the same `customer_number`, both are
created successfully but the second number lookup via `GSI_NUMBER` will return two items.
The `get_by_number` method returns the first item and logs a warning. For CUS-001 this is
acceptable; a monotonic atomic counter or a UUID-based number can be added in a follow-up
without breaking the interface.

### 5.2 Optimistic concurrency on PATCH

The `expected_version` field is required in `CustomerPatchIn`. The flow is:

1. Client `GET /ui/customers/{id}` → receives `{ ..., "version": 3 }`.
2. Client `PATCH /ui/customers/{id}` with `{ "legal_name": "...", "expected_version": 3 }`.
3. Service reads item: `existing["version"] == 3` → proceed.
4. `update_item` with `ConditionExpression="version = :expected_version"` (`:expected_version = 3`).
5. If a concurrent write bumped it to 4 between read and write, DynamoDB raises
   `ConditionalCheckFailedException` → service raises `CustomerConflictError` → router
   returns HTTP 409.

The client retries by re-fetching with GET (getting the new version) and re-applying its
changes.

### 5.3 Attribute upsert semantics

`PUT /ui/customers/{customer_id}/attributes` sets a single attribute. The design
choice (Open Question §10) is **upsert-by-name**: the SK is `ATTR#{name}` rather than
`ATTR#{uuid}`. This means:

- Setting the same attribute name twice updates the existing row in place.
- `list_attributes` returns at most one entry per `name`.
- `delete_attribute` deletes by `name` (the `attribute_id` in the response equals the
  `name` for simplicity, or a deterministic ID derived from it).

If append-style history is required, the SK becomes `ATTR#{uuid}` (a new row per set
call). The router and service signatures are identical either way; only the SK construction
changes. The ticket uses upsert-by-name for simplicity.

### 5.4 Sparse GSI_BRANCH

When `branch_id` is `None`, the `gsi_branch_pk` attribute is omitted from the item
entirely. DynamoDB simply does not index the item in `GSI_BRANCH`. This is intentional
and allows `branch_id` to be optional without polluting the index with null-keyed items.

When `branch_id` is later set via PATCH, the update expression adds `gsi_branch_pk`.
When it is cleared (set to `None`), the update expression uses `REMOVE gsi_branch_pk`
to drop the attribute and remove the item from the index.

### 5.5 `kyc_status` field

`kyc_status` is writable by admin via `PATCH` (through `CustomerPatchIn.kyc_status`).
CUS-002 will additionally write it automatically when a user is linked (back-filling from
the user's latest KYC case). For CUS-001 the field is treated as a plain string; no enum
validation is applied (the KYC case owns the allowed status set; the customer entity
stores the derived summary).

### 5.6 Flag off — no table access

When `S.customer_entity_enabled` is `False`, every route returns HTTP 404 before
touching DynamoDB. The `T.customers` handle is still initialized at process start (same
as every other table handle), but it is never called. This means DynamoDB Local does not
need the `customers` table to be created when the flag is off; the table will simply not
exist and no error will occur.

### 5.7 PII handling

`legal_name`, `date_of_birth`, `mobile_phone`, and `email` are contact-data PII. They
are stored in plaintext in DynamoDB (same treatment as KYC case `user_sub`, the user
`email` in the `users` table, and billing contact fields). They are **never logged** —
the `audit_event` calls only log `customer_id`, not the PII fields. No KMS encryption
is applied in CUS-001; this is a follow-up concern if compliance requirements mandate
field-level encryption (which would reuse `app/core/crypto.kms_encrypt`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### Dev/prod parity

There are **no `if S.dev_mode` branches** in the customer entity business logic. The
service calls `T.customers.put_item` and `T.customers.update_item` directly — in dev
these hit DynamoDB Local at `DDB_ENDPOINT_URL=http://localhost:8001`; in prod they hit
real DynamoDB in the configured region. The `audit_event` helper (`app/services/alerts.py:644`)
writes to `T.alerts` in both environments; in dev this is the local DynamoDB instance,
in prod it is the regional table. This is exactly the same parity model used by
`kyc_cases.py`, `billing.py`, and every other service in the codebase.

### Idempotency

- **Create is not idempotent**: each `POST /ui/customers` mints a new `customer_id` and
  `customer_number`. There is no natural idempotency key (unlike Stripe's
  `Idempotency-Key` header). Staff should be careful about duplicate submits; a
  follow-up can add a client-supplied idempotency key.
- **PATCH is idempotent**: repeating the same PATCH with the correct `expected_version`
  produces the same result. Repeating it with a stale version fails with 409, which is
  safe.
- **Attribute set is idempotent** (upsert-by-name semantics): `PUT .../attributes` with
  the same `name` and `value` is a no-op in effect (overwrite with same value).

### Security

- All admin/root-only endpoints verify role via `_require_admin_or_root` before any
  DDB access. A `USER`-role caller receives HTTP 403 and an audit event is written.
- `customer_id` and `customer_number` are server-minted; callers cannot supply them.
- `kyc_status` is writable only by admin; a `USER` cannot elevate their own KYC status.
- PII fields are never emitted in audit logs (only `customer_id` is logged).
- No API key route registration is needed for CUS-001: all endpoints are admin/session
  only; there is no public or API-key-accessible surface.

### Money-safety note

CUS-001 introduces no money movement, no ledger entries, no billing calls, no Stripe
interaction, and no wallet mutations. The money-safety invariants (single money-mover,
`settle_or_reverse_ledger`, fraud gate, SCA gate) are not applicable here and will be
enforced in the relevant downstream tickets (CUS-003 card charge paths, TXN-001 onward).

## 8. Backward Compatibility & Migration

### Additive-only

CUS-001 adds:
- A new DynamoDB table (`customers`) — no existing table is modified.
- Two new settings fields — default values mean no change in behavior for existing
  deployments.
- New router registered in `app/main.py` — appended after existing routers, no
  path collisions (no existing route starts with `/ui/customers`).
- New Pydantic models in `app/models.py` — append-only.

No existing endpoint, service, table, or migration is altered.

### `just restart` behavior

`scripts/local-ddb-init.py` creates the `customers` table on startup when the flag is
on **or** always (table creation is idempotent; DynamoDB Local returns a "table already
exists" error which `local-ddb-init.py` suppresses). The table creation is unconditional
so that the table is ready as soon as the flag is flipped on, without requiring a
restart.

### Production migration

No in-place migration is required. The `customers` table must be created via
`aws dynamodb create-table` (or Terraform/CDK) with the schema defined in §3 before the
flag is enabled. The two GSIs are specified at table creation time (DynamoDB does not
require a `UpdateTable` GSI backfill for an empty table). After the table exists, setting
`CUSTOMER_ENTITY_ENABLED=true` in the environment and redeploying activates the feature.

There is no data to backfill — the customer entity starts empty; existing KYC cases are
linked by CUS-002.

## 10. Open Questions / Assumptions

1. **Attribute identity: upsert-by-name vs. append-by-UUID.** The spec chooses
   upsert-by-name (SK=`ATTR#{name}`) for simplicity. If the OBP API requires tracking
   attribute history (multiple values for the same name over time), the SK must be
   `ATTR#{uuid4().hex[:8]}` and a separate `list_attributes` with filtering by name
   would be added. Decision to make before implementation.

2. **`customer_number` collision avoidance.** `now_ts()` in seconds suffices for manual
   staff-driven creation but is unsafe under load (> 1 create/sec). A monotonic DDB
   counter using `ADD` on an `atomic_counters` row would give true serial numbers.
   Deferred; the `GSI_NUMBER` lookup handles the duplicate-warning case gracefully.

3. **PII encryption at rest.** `legal_name`, `dob`, `mobile_phone`, `email` are stored
   in plaintext. If the deployment requires field-level encryption, it can be layered
   using `app/core/crypto.kms_encrypt` (same approach as `ssh_key_manager.py` for PEM
   keys) without changing the API surface. Deferred to a hardening follow-up.

4. **Pagination of global customer list.** `list_customers` without a `branch_id`
   requires a DynamoDB scan. This is acceptable while the table is small; a GSI on a
   constant partition key (analogous to `gsi_number_pk="CUSTNUM"`) with `created_at` as
   sort key would allow efficient global listing. Deferred; the branch-filtered path
   covers the common admin use-case.

5. **`kyc_status` enum.** The field is stored as a free string. A closed set mirroring
   `_ALLOWED_STATUSES` in `kyc_cases.py:33-48` could be validated at write time. For
   CUS-001 validation is omitted since the KYC case owns the authority; the customer
   field is a cached copy. CUS-002 will set it to the linked KYC case's status value,
   which is always one of the known statuses.
