# ACC-001 — Bank + Account entities — DDB model, table, flag + default-account bootstrap

**Ticket type**: Backend (data model + CRUD endpoints)
**Priority**: P1 (foundation — all other ACC tickets depend on this)
**Estimate**: 3 days
**Status**: Unimplemented (testlogon has no bank-account model today)

---

## 1. Summary & Goal

ACC-001 introduces the two core banking entities — `Bank` and `Account` — as new DynamoDB rows, additively layered over the existing wallet/ledger. It does not touch any existing money-moving code.

The central design decision is explicit and load-bearing: **each user's default Account is a thin projection of their existing per-user wallet row and billing ledger, not a second store of money.** The account entity holds ownership metadata; the money continues to live in `T.billing` under the same `USER#{sub}` partition key that billing already owns (`app/services/billing_shared.py:23` `user_pk`). Balance reads on the default account call through to `billing_shared.get_wallet_balance` (`billing_shared.py:176`); no balance is duplicated.

The goal is to establish the bank + account schema that ACC-002 (transaction list), ACC-003 (metadata enrichment), and ACC-004 (co-access) will build on, while leaving the existing billing surface completely unchanged and behind a default-OFF feature flag.

## 2. Context & Current State

### Current money model (what we are layering over, never forking)

testlogon moves money through a single-entry billing ledger and a per-user wallet row, both stored under `pk=USER#{sub}` in `T.billing` (`app/core/settings.py:348` `billing_table_name`, defaulting to `"billing"`; `app/core/tables.py:81` `T.billing`).

The wallet row is keyed `pk=USER#{sub}`, `sk="WALLET"` (`billing_shared.py:173` `WALLET_SK`). `get_wallet_balance(table, pk)` (`billing_shared.py:176`) returns `{wallet_balance_cents, currency, updated_at}`. `apply_wallet_delta(table, pk, delta_cents)` (`billing_shared.py:185`) atomically updates it with a conditional-on-balance withdrawal guard.

Ledger rows are keyed `sk=LEDGER#{ts}#{entry_id}` (`billing_shared.py:220` `ledger_sk`). `new_ledger_entry(...)` (`billing_shared.py:224`) mints a new ledger row with `entry_id`, `ts`, `type`, `amount_cents`, `state`, `reason`, `ledger_date`. `settle_or_reverse_ledger(...)` (`billing_shared.py:262`) flips `state` to `settled` or `reversed` without touching any other field.

The existing balance endpoint is `GET /billing/balance` (`app/routers/billing.py:840`); the ledger list is `GET /billing/ledger` (`app/routers/billing.py:2448`), which filters `sk.startswith("LEDGER#")` and sorts by `ts` descending. **These endpoints are untouched by ACC-001 through ACC-005.**

### What is missing

The gap analysis (`docs/openbankproject/OBP_GAP_ANALYSIS.md` §A) states: *"Bank Account entity (account_id/IBAN/routing/multi-owner/attributes/product) — MISSING; money is a per-user `WALLET` row (`billing_shared.py:173`), not an account."* There is no `bank_id`, no `account_id`, no typed `account_type`, no `iban`, no `owners` list, no `product_code`, and no `account_attributes` shape anywhere in the codebase.

## 3. Data Model

### New table: `banking_accounts` (single-table, covers Banks + Accounts)

Banks and Accounts share one table to keep the table count low and to leverage single-table design. The table name is controlled by settings key `banking_accounts_table_name` (env `BANKING_ACCOUNTS_TABLE_NAME`, default `"banking_accounts"`).

**Table schema**

| Attribute | Type | Role |
|---|---|---|
| `pk` | S (partition key) | Owner partition — `USER#{owner_sub}` for account rows; `BANK` for bank catalog rows |
| `sk` | S (sort key) | Entity discriminator — see row types below |
| `account_id` | S | Denormalized on every account row; enables `GSI_ACCOUNT_BY_ID` |
| `created_at` | N | Unix timestamp int |
| `updated_at` | N | Unix timestamp int |

**GSI: `GSI_ACCOUNT_BY_ID`**

- Partition key: `account_id` (S)
- Sort key: `created_at` (N) — allows range-query without scanning all copies of an account id (there will be at most one in practice, but the `N` type is needed to avoid a `ValidationException` because DDB infers the type from the first item written)
- Enables `get_account(account_id)` to resolve an account without knowing the owner `sub` — required by ACC-004 co-access reads

Because `created_at` is numeric, the `TableDef` in `scripts/local-ddb-init.py` **must** declare:
```python
attr_types={"created_at": "N"}
```
Omitting this causes DDB to store `created_at` as String on the first write, which then breaks GSI range queries with integer values.

**Row types**

*Bank catalog row*
```
pk  = "BANK"
sk  = "BANK#{bank_id}"
bank_id      : str        # slug, e.g. "testlogon"
name         : str        # display name, e.g. "Testlogon"
short_name   : str
logo_url     : str (optional)
website      : str (optional)
created_at   : int
```

*Account row (owned)*
```
pk  = "USER#{owner_sub}"     # same partition format as billing
sk  = "ACCOUNT#{account_id}"
account_id     : str         # uuid4().hex
bank_id        : str         # FK to bank catalog row
label          : str         # user-editable, e.g. "Wallet"
account_type   : str         # "WALLET" | "SAVINGS" | "EXTERNAL"
product_code   : str         # free string, e.g. "default"
currency       : str         # e.g. "usd" (matches single-currency ledger)
owners         : list[str]   # [owner_sub, ...] — multi-owner; ACC-004 manages additions
is_default     : bool        # True for the auto-provisioned wallet-backed account
wallet_backed  : bool        # True → balance/txn projections read T.billing
iban           : str | None  # opaque string, no validation
routing_number : str | None  # opaque string
account_number_masked : str | None
attributes     : list[{name: str, type: str, value: str}]  # OBP typed key-values
created_at     : int
updated_at     : int
account_id     : str         # denormalized for GSI_ACCOUNT_BY_ID
```

*Account reverse-index row (written by ACC-004, defined here for schema completeness)*
```
pk  = "USER#{co_owner_sub}"
sk  = "ACCOUNT_REF#{account_id}"
account_id     : str
owner_sub      : str         # the primary owner's sub, to resolve the full account row
created_at     : int
```

**TableDef entry** (in `scripts/local-ddb-init.py`):
```python
TableDef(
    _resolve_table_name(S.banking_accounts_table_name, "banking_accounts"),
    "pk",
    "sk",
    gsi=[
        {
            "index_name": "GSI_ACCOUNT_BY_ID",
            "partition_key": "account_id",
            "sort_key": "created_at",
        }
    ],
    attr_types={"created_at": "N"},
),
```

## 4. API / Service Design

### Service: `app/services/banking_accounts.py`

All service functions are synchronous; they use `T.banking_accounts` and `T.billing` via the existing `_FloatSafeTable` proxy (`app/core/tables.py:29`).

```python
from app.core.tables import T
from app.core.settings import S
from app.core.time import now_ts
from app.services.billing_shared import get_wallet_balance, user_pk
from app.services.alerts import audit_event
from app.core.cursor import encode_cursor, decode_cursor
from uuid import uuid4
from fastapi import HTTPException


# ---- Bank catalog ----

def list_banks() -> list[dict]:
    """Query pk="BANK", sk begins_with "BANK#". Returns all bank rows as dicts."""

def get_bank(bank_id: str) -> dict:
    """Get single bank by bank_id. Raises 404 if not found."""


# ---- Default-account bootstrap ----

def ensure_default_account(owner_sub: str) -> dict:
    """
    Idempotent lazy bootstrap of the wallet-backed default account.

    1. Query T.banking_accounts pk=USER#{owner_sub}, sk begins_with "ACCOUNT#"
       filtering is_default=True. If found, return the existing row (stable account_id).
    2. If not found, put_item with a new account_id=uuid4().hex, account_type="WALLET",
       is_default=True, wallet_backed=True, bank_id=S.banking_default_bank_id,
       label="Wallet", currency="usd", owners=[owner_sub], product_code="default",
       attributes=[], created_at=now_ts(), updated_at=now_ts().
    3. Uses condition_expression="attribute_not_exists(sk)" on the item's sort key to guard
       against concurrent first calls (on ConditionalCheckFailedException, re-read and
       return the row created by the racing caller).
       NOTE: attribute_not_exists(pk) would be WRONG here — the pk "USER#{owner_sub}"
       already exists for any user with even one account row, so that condition would fail
       on every subsequent put, preventing second-account creation. The sk-level check
       is correct: sk="ACCOUNT#{new_uuid}" is always unique per put.
    4. Emits audit_event("banking.account.created", owner_sub, account_id=account_id,
       account_type="WALLET", is_default=True).
    5. Returns the account dict.
    """


# ---- Account CRUD ----

def create_account(
    owner_sub: str,
    *,
    label: str,
    account_type: str,      # "SAVINGS" | "EXTERNAL" — not "WALLET" (that is default only)
    bank_id: str,
    product_code: str = "default",
    currency: str = "usd",
    attributes: list[dict] | None = None,
    iban: str | None = None,
    routing_number: str | None = None,
    account_number_masked: str | None = None,
) -> dict:
    """
    Creates a non-default account row. Validates account_type not "WALLET"
    (only ensure_default_account may create WALLET type; caller gets 422 if attempted).
    Validates bank_id exists (get_bank or 422).
    Emits audit_event("banking.account.created", ...).
    """

def list_accounts(viewer_sub: str) -> list[dict]:
    """
    Returns all accounts the viewer owns or co-owns.
    1. Query T.banking_accounts pk=USER#{viewer_sub}, sk begins_with "ACCOUNT#"
       (owned accounts).
    2. Query T.banking_accounts pk=USER#{viewer_sub}, sk begins_with "ACCOUNT_REF#"
       (co-owned reverse-index rows). For each, resolve the full account row via
       GSI_ACCOUNT_BY_ID (account_id from the REF row).
    3. Dedup by account_id; call ensure_default_account(viewer_sub) first so the list
       always returns at least one account for any authenticated user.
    """

def get_account(account_id: str, *, requester_sub: str) -> dict:
    """
    Resolves via GSI_ACCOUNT_BY_ID (query index, partition key = account_id).
    Asserts requester_sub in item["owners"] — if not, raises 404 (no information leak).
    Returns the account dict.
    """

def update_account(
    account_id: str,
    owner_sub: str,
    *,
    label: str | None = None,
    attributes: list[dict] | None = None,
    iban: str | None = None,
    routing_number: str | None = None,
    account_number_masked: str | None = None,
) -> dict:
    """
    Owner-only update. Verifies owner_sub in item["owners"] (else 403).
    Conditional update_item (attribute_exists check on pk+sk so a non-existent
    account returns 404 rather than silently creating a row).
    Sets updated_at=now_ts(). Emits audit_event("banking.account.updated", ...).
    Returns updated account dict.
    """

def delete_account(account_id: str, owner_sub: str) -> None:
    """
    Owner-only delete. Verifies owner_sub in item["owners"] (else 403).
    Refuses with 409 if item["is_default"] is True
    (message: "Cannot delete the default wallet account").
    Emits audit_event("banking.account.deleted", ...).
    Deletes the item from T.banking_accounts.
    """


# ---- Balance read-through ----

def get_account_balance(account_id: str, *, requester_sub: str) -> dict:
    """
    Resolves + authorizes the account (calls get_account).
    If wallet_backed=True: calls billing_shared.get_wallet_balance(T.billing,
      user_pk(owner_sub)) and returns
      {currency, current: wallet_balance_cents / 100,
       available: wallet_balance_cents / 100}
      (inline cents→dollars; no `dollars_from_cents` helper exists in the codebase)
      (no holds model in this tier → available == current).
    If wallet_backed=False: returns {currency, current: 0, available: 0}
      (non-wallet accounts carry no money in this tier).
    """
```

## 5. Detailed Behavior & Edge Cases

### Default-account bootstrap idempotency

`ensure_default_account` is called at the start of `GET /ui/banking/accounts` and by any downstream service that needs to resolve a user's default account. It must be idempotent across concurrent callers:

1. Query `pk=USER#{sub}`, `sk begins_with "ACCOUNT#"`, filter `is_default=True`. If found, return the first match — the `account_id` is stable for the life of the account.
2. If not found, `put_item` with `ConditionExpression="attribute_not_exists(sk)"`. On `ConditionalCheckFailedException`, another process raced us and created the row; re-read and return it.
3. A second call to `GET /ui/banking/accounts` for the same user returns the exact same `account_id` — verified by the idempotency acceptance criterion.

### GSI_ACCOUNT_BY_ID ownership check

`get_account(account_id, requester_sub)` queries `GSI_ACCOUNT_BY_ID` with `KeyConditionExpression="account_id = :id"`. The GSI projects all attributes (no projection — DDB default). The query returns the full account row. The function then asserts `requester_sub in item["owners"]`; if not, it raises `HTTPException(status_code=404)` — a 404 rather than 403 to avoid confirming the account exists to an unauthorized requester.

This pattern follows the same "no leak" principle as `host_inventory.get_decrypted_private_key` and the KYC case fetch by unauthorized users.

### Delete-default guard

`delete_account` reads the account row via `get_account(account_id, owner_sub)`. If `item["is_default"]` is truthy, it raises `HTTPException(status_code=409, detail="Cannot delete the default wallet account")`. There is no bypass. A future admin-level path might soft-delete with a different owner assertion, but that is explicitly out of scope for ACC-001.

### `account_type="WALLET"` creation guard

`create_account` rejects `account_type="WALLET"` with `HTTPException(status_code=422, detail="account_type WALLET is reserved for the default account")`. Only `ensure_default_account` may produce WALLET-type rows. This prevents a user from creating a second wallet-backed account and confusing the balance read-through.

### Bank ID validation on account create

`create_account` calls `get_bank(bank_id)`. If the bank does not exist in the catalog, it raises `HTTPException(status_code=422, detail=f"Unknown bank_id: {bank_id}")`. In practice the house bank is seeded at startup, so this guard fails loudly only on misconfiguration or API misuse.

### Balance read-through proof

`GET /ui/banking/accounts/{id}/balance` for the default account calls `billing_shared.get_wallet_balance(T.billing, user_pk(owner_sub))` (`billing_shared.py:176`). This reads the live WALLET row in `T.billing` — no caching, no copy. Depositing to the wallet via the existing `POST /billing/wallet/deposit` endpoint increments `wallet_balance_cents` on the same row; the next balance call to the banking endpoint reflects the change immediately. This is the fundamental "additive projection" invariant.

### Non-wallet accounts carry no money

`SAVINGS` and `EXTERNAL` account types are pure metadata containers in this tier. `get_account_balance` for a non-wallet-backed account returns `{currency: "usd", current: 0, available: 0}`. This is explicitly documented in the response — callers should not interpret a `0` balance as an error.

### `attributes` round-trip

The `attributes` field is stored as a DynamoDB List of Maps `[{name, type, value}]`. The `_FloatSafeTable` proxy (`app/core/tables.py:29`) handles `float → Decimal` coercion transparently. Values are stored as strings; no type validation beyond the enum check on `type` (STRING/INTEGER/DOUBLE/BOOLEAN/DATE) in the Pydantic model.

### `iban`/`routing_number`/`account_number_masked` are opaque strings

No IBAN checksum validation, no routing number format check. They are free-form cosmetic fields for OBP shape parity. Strip leading/trailing whitespace on input; persist as-is.

### Audit trail

Every mutating operation (`create_account`, `update_account`, `delete_account`, `ensure_default_account` first creation) calls `audit_event(event_name, owner_sub, account_id=account_id, ...)` which writes to `T.alerts` (`billing_shared.py` and KYC services use the same helper). Audit is best-effort: a failure in the alert write must not roll back the account mutation. Wrap the `audit_event` call in `try/except`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 dev/prod parity

There is no `if S.dev_mode:` branch in any banking service or router. DynamoDB Local (port 8001) and real DynamoDB use identical code paths. The `T.banking_accounts` handle is wired via `_safe_table(S.banking_accounts_table_name)` (`app/core/tables.py:65`), which wraps `ddb.Table(name)` — the same factory used by every other table, already handling dev (DDB Local endpoint) vs prod (real DynamoDB) transparently via the `DDB_ENDPOINT_URL` env var (`app/core/settings.py:11`).

### Money-safety invariants

ACC-001 has no money-out paths. The only money-touching operation is the **read-through** in `get_account_balance`, which calls `get_wallet_balance` (`billing_shared.py:176`). This is a `get_item` read — it does not mutate the wallet row. There is no `apply_wallet_delta`, no `new_ledger_entry`, no `settle_or_reverse_ledger` call anywhere in ACC-001. The account entity is a metadata wrapper; all money math remains in the existing billing layer.

Non-default accounts (`SAVINGS`/`EXTERNAL`) carry a stored `currency` field but no balance. Creating or deleting these rows has no effect on any wallet or ledger row. The `delete_account` guard on `is_default=True` ensures the metadata wrapper for the wallet-backed account can never be orphaned while the underlying wallet row survives.

### Idempotency

- `ensure_default_account`: conditional `put_item` + re-read on race (`ConditionalCheckFailedException`) — fully idempotent, safe to call on every `GET /ui/banking/accounts` request.
- `create_account`: produces a new `account_id = uuid4().hex` on each call — not idempotent by design. Callers that want idempotency should check `list_accounts` first.
- `update_account`: conditional update with `attribute_exists(sk)` — safe against non-existent accounts; repeated calls with the same payload produce the same result (modulo `updated_at`).

### Authentication and ownership security

- All endpoints require `require_ui_session` (cookie + CSRF). No public routes are added by ACC-001. The `/ui/banking/banks` endpoint is authenticated — public bank listings are not in scope for this ticket.
- Ownership is enforced at the DDB access layer: account rows are partitioned by `USER#{owner_sub}`, so a query on a different user's partition physically cannot return another user's rows. The `GSI_ACCOUNT_BY_ID` lookup adds an explicit `requester_sub in item["owners"]` check before returning any data, producing a 404 rather than a 403 on unauthorized access.
- `iban`, `routing_number`, `account_number_masked` are stored in plain text (they are cosmetic, opaque strings). No KMS encryption is required for these fields in this tier — they are not real credentials and hold no bank-access value. If a future tier adds real credentials, KMS encryption (via `app/core/crypto.kms_encrypt`) should be applied at that time.

## 8. Backward Compatibility & Migration

### Zero impact on existing endpoints

Every existing billing, wallet, and ledger endpoint is untouched:
- `GET /billing/balance` (`billing.py:840`) reads `T.billing` `pk/BALANCE` — unchanged.
- `GET /billing/ledger` (`billing.py:2448`) reads `T.billing` `pk/LEDGER#*` — unchanged.
- `apply_wallet_delta`, `new_ledger_entry`, `settle_or_reverse_ledger` in `billing_shared.py` — unchanged.

No existing DynamoDB table schema is modified. `T.billing` gains no new GSIs or attributes from this ticket.

### Table creation is additive

`scripts/local-ddb-init.py` gains one new `TableDef` entry for `banking_accounts`. Because the table did not exist before, there is no migration to existing data. For production, `CREATE TABLE` via the deployment script is the only required operation.

In development, `just restart` wipes and recreates all tables (including the new one) and re-seeds sessions. Engineers who add the new `TableDef` entry and run `just restart` will have a clean, correct local state.

### Flag-off is the default

`BANKING_ACCOUNTS_ENABLED=0` is the default. Existing deployments that do not set this env var will see no change in behavior — the router is not registered, the table is not accessed, and all `/ui/banking/*` requests return 404 from FastAPI's route resolver.

### Future migration path for non-default accounts

Non-default `SAVINGS`/`EXTERNAL` accounts created through ACC-001 are pure metadata. If a future ticket adds a real money-movement path for these account types, the account row already has `currency`, `bank_id`, `product_code`, and `owners` — no schema migration is needed, only new service logic.

## 10. Open Questions / Assumptions

1. **Single-table for banks + accounts**: The spec folds both entity types into `banking_accounts`. An alternative is a separate `banking_banks` table, which keeps bank catalog queries cleaner. The single-table approach is chosen here to minimize new table count, consistent with the KYC single-table pattern (`kyc_cases` holds cases, documents, and review rows). If the bank catalog grows significantly (multi-bank SaaS), split to its own table.

2. **House bank self-seed on first use**: `ensure_default_account` optionally seeds the house bank if `get_bank` returns 404. This sidesteps a seed script ordering dependency. If the seed script approach is preferred, remove the self-seed and rely on `scripts/local-ddb-seed.py` always running before account creation.

3. **`GSI_ACCOUNT_BY_ID` sort key `created_at`**: The GSI needs a sort key to force DDB to declare `created_at` as `N`. If all accounts have unique `account_id` (they do — `uuid4().hex`), the sort key is never used in range queries. An alternative is to use a `dummy` constant string as the sort key, but numeric `created_at` has practical value (e.g., for ACC-004 time-ordered co-owner joins).

4. **Non-wallet accounts have zero balance**: `SAVINGS` and `EXTERNAL` account types return a hard-coded `0` balance. This is the correct scope for ACC-001 — future tickets can add a real balance pathway. Callers should not treat `0` as an error; the `wallet_backed: false` flag signals the reason.

5. **Currency is always `usd`**: The ledger is single-currency. The `currency` field is stored on the account row to allow future multi-currency extension without a schema migration. For now, all accounts default to `"usd"`.

6. **`owners` list vs separate co-owner table**: Owners are a `list[str]` on the account row. This is fine for small co-owner sets (typical: 1–3 people). For accounts with many co-owners, a separate owners table would be more DynamoDB-efficient. ACC-004 adds the reverse-index `ACCOUNT_REF#` rows; the `owners` list on the account row is the authoritative source.
