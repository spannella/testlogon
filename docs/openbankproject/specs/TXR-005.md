## 1. Summary & Goal

TXR-005 closes the TXR series by providing two deliverables that make the engine production-ready without touching any backend business logic:

1. **Hermetic regression test suite** (`tests/test_txr_txn_requests.py`) — a single offline pytest file that covers the full state machine, per-type amount limits, SCA gating, per-type execution dispatch (WALLET_TRANSFER, PAYOUT, REFUND, COUNTERPARTY, FREE_FORM), idempotency, and fraud/freeze blocking. All tests run with no live AWS stack (moto + object.__setattr__ frozen table/settings injection, matching the established repo pattern).

2. **Typed frontend client + React Query hook** — `frontend/src/api/endpoints/txnRequests.ts` (four thin axios wrappers), `frontend/src/hooks/useTxnRequest.ts` (three React Query hooks), and the corresponding TypeScript types in `frontend/src/api/types.ts`. When a create response arrives with `status="PENDING"` and a `sca_challenge_id`, the hook surfaces `{ challengeId, requiredFactors }` so any page can drive the **existing** `/ui/mfa/*` verify endpoints without owning new OTP logic.

3. **E2E spec** (`frontend/e2e/txn-requests.spec.ts`) with three critical paths: sub-threshold → INITIATED → execute → COMPLETED; high-value → PENDING → dev-mode OTP → execute → COMPLETED; double-execute idempotency.

4. **Documentation** — `docs/file-reference.md` update and a CLAUDE.md "Common gotchas" entry covering the flag, one-refund-mechanism, status-as-lock, and fraud-on-execute rules.

No new backend endpoints, DynamoDB tables, or settings are introduced by this ticket. Everything implemented here is pure test scaffolding and frontend wiring over the engine delivered by TXR-001 through TXR-004.

### 4.4 Frontend hook (`frontend/src/hooks/useTxnRequest.ts`)

Three React Query hooks:

**`useCreateTxnRequest()`** — mutation hook.

```typescript
// Returns: UseMutationResult<TxnRequest, Error, TxnRequestCreateIn>
// On success: if result.status === "PENDING" and result.sca_challenge_id,
//   the hook exposes { challengeId: string, requiredFactors: string[] }
//   on the mutation result data so the consuming page can drive MFA verify.
```

**`useTxnRequest(requestId: string | null | undefined)`** — query hook.

```typescript
// Enabled: !!requestId
// queryKey: ["txn-request", requestId]
// queryFn: getTxnRequest(requestId!)
// refetchInterval: (data) =>
//   data?.status === "INITIATED" || data?.status === "PENDING" ? 2000 : false
// Polls every 2 seconds while the request is in a non-terminal status.
// Stops polling once status reaches COMPLETED or FAILED.
```

The polling cadence uses React Query's `refetchInterval` option (a value or callback returning `number | false`). Terminal statuses short-circuit the interval to `false`, ensuring no wasted polling after settlement. [NOTE: `useCallBillingHeartbeat.ts` uses a self-rescheduling `setTimeout`, not React Query — it is not the right reference for `refetchInterval` pattern. The correct reference pattern is `useQuery({ refetchInterval: (data) => ... })` as used in other query hooks in the project.]

**`useExecuteTxnRequest()`** — mutation hook.

```typescript
// Returns: UseMutationResult<TxnRequest, Error, string> (mutate takes requestId)
// On success: invalidates ["txn-request", requestId] query.
// On 403 with body.detail containing "sca_incomplete": surfaces that error
//   to the caller without swallowing (the page drives the MFA flow first).
```

**SCA flow composition pattern** (how a page wires these together):

```
1. createMut.mutate(body)
2. if createMut.data.status === "PENDING":
     surface SCA UI using createMut.data.sca_challenge_id + required_factors
     drive existing POST /ui/mfa/{factor}/verify with the challenge_id
     wait until all factors pass (poll useTxnRequest or wait for MFA verify success)
3. executeMut.mutate(createMut.data.request_id)
4. useTxnRequest(request_id) shows live status until COMPLETED/FAILED
```

The hook does **not** own the MFA UI. It exposes only `challengeId` and `requiredFactors` so any existing MFA verify component can be passed those values. This reuses the SCA dialog already wired for `/ui/mfa/*` routes rather than introducing new UI.

## 5. Detailed Behavior & Edge Cases

### 5.1 State machine coverage (test-level specification)

The pytest suite must assert these exact transition outcomes:

| From | Event | To | HTTP | Notes |
|---|---|---|---|---|
| (none) | create sub-threshold + non-sensitive | INITIATED | 201 | No challenge |
| (none) | create at/above threshold | PENDING | 201 | `sca_challenge_id` set |
| (none) | create sensitive type (PAYOUT) | PENDING | 201 | Regardless of amount |
| INITIATED | execute (no SCA) | COMPLETED | 200 | Fraud gate passes |
| PENDING | execute, `challenge_done=False` | — | 403 `sca_incomplete` | No transition |
| PENDING | execute, `challenge_done=True` | COMPLETED | 200 | Challenge revoked |
| INITIATED | illegal direct → COMPLETED | — | 409 `invalid_transition` | No money move |
| COMPLETED | execute again | COMPLETED | 200 | Idempotent: same object |
| FAILED | execute | — | 409 `invalid_transition` | Terminal |
| PENDING | concurrent execute × 2 | COMPLETED | 200 / 409 | Exactly one wins |

The concurrent-execute test provisions two greenlets/coroutines calling `execute_request` simultaneously. Per TXR-004 §4.2, the true lock is the `PENDING → IN_FLIGHT` conditional `_transition` (Step 2a); only one caller wins that write. The other receives `ConditionalCheckFailedException` → 409. Both return the same terminal `TxnRequestOut` (status=`COMPLETED`) and money moves exactly once. [CORRECTED: the original description said the lock was `PENDING → COMPLETED` — but TXR-004 introduced `IN_FLIGHT` as the intermediate gating status precisely to prevent dispatch race before the terminal write.]

### 5.2 Per-type execution edge cases

**WALLET_TRANSFER insufficient funds**: sender's WALLET row has balance 500 cents; request is for 501 cents. `apply_wallet_delta` (`billing_shared.py:185`) raises `ConditionalCheckFailedException` → `execute_request` catches it, calls `_transition(... → FAILED, failure_reason="insufficient_funds")`, returns 200 with `status="FAILED"`. The recipient wallet is untouched (the debit leg failed before the credit leg ran — atomicity guaranteed by the `transact_write_items` batch pattern from `group_treasury._batch_transact`).

**REFUND one-refund-mechanism**: `stripe.Refund.create` is patched to a `MagicMock` that records call count. The test calls `execute_request` twice on the same REFUND request. The second call finds `status="COMPLETED"` and short-circuits before reaching `_do_refund`. Assert `stripe.Refund.create.call_count == 1`. A second, separate REFUND request for the same `payment_intent_id` must also result in at most one new `Refund.create` call; the legacy guard in `_do_refund` checks whether the payment record already carries `status="refunded"` and raises before calling Stripe a second time.

**PAYOUT `request_payout` delegation**: `creator_payouts.request_payout` is called via a patched module-level reference. The test asserts it receives `(user_id, amount_cents, method_id=target["payout_method_id"])` and that the returned `payout_id` is persisted into `ledger_refs` on the `COMPLETED` item. A `ValueError` from `request_payout` (e.g. "Amount must be at least X cents") → `_transition(... → FAILED, failure_reason=str(e))`.

**COUNTERPARTY fallback**: Until the Tier-2 Counterparties entity exists, `execute_request` for `COUNTERPARTY` type: (1) debits the sender wallet, (2) writes `new_ledger_entry(entry_type="debit", reason="counterparty_payment", state="pending")`, (3) **immediately reverses the debit** via a second `apply_wallet_delta(+amount)` call (so the platform is balance-neutral), then (4) transitions to `FAILED counterparty_unsupported`. The test asserts `status="FAILED"`, `failure_reason="counterparty_unsupported"`, and **sender wallet balance is unchanged** (debit reversed). [CORRECTED: the reversal step was omitted in an earlier draft — see TXR-004 §4.4 and §5.9 for the authoritative dispatch. MONEY-SAFETY: not verifying the reversal would allow tests to pass while masking a net debit.]

**FREE_FORM no target.to_user_sub**: If `target.to_user_sub` is absent, TXR-004 §4.3 specifies execution **debits** the sender wallet and writes a single `new_ledger_entry(entry_type="debit", reason="free_form_payment", state="settled")` — this is a fee/service-charge pattern, not a self-credit. `status="COMPLETED"`, `ledger_refs` contains the debit ledger SK. The test must verify the sender wallet is debited, not credited. [CORRECTED from earlier draft which incorrectly said `entry_type="credit"` with no wallet change — see TXR-004 §4.3 for the authoritative dispatch.]

### 5.3 Idempotency

A second `POST /ui/txn-requests` with the same `idempotency_key` returns the existing `INITIATED` item (201 with the original body) without writing a new item. The test: write item with `idempotency_key="k1"`, call `create_request` again with same key, assert `get_item` returns exactly one item for that user and the returned `request_id` matches the original.

A second `POST /ui/txn-requests/{id}/execute` on a `COMPLETED` request returns `200` with the terminal `TxnRequestOut` unchanged. The conditional `update_item` guard (`attribute_value(status, "=", "PENDING")` or `"INITIATED"`) fails, the except branch reads and returns the current item without re-executing. Money moved exactly once.

### 5.4 Fraud/freeze blocking

The test patches `_fraud_gate` at its definition site — `monkeypatch.setattr("app.routers.billing._fraud_gate", ...)` — to raise `HTTPException(403, ...)` simulating a frozen account. Per TXR-004 §4.2, `_fraud_gate` is **lazy-imported** inside `execute_request` (not at module level in `txn_requests.py`) to avoid a circular import, so patching the name in the txn_requests module namespace would not intercept the call; the billing module is the correct patch target. [CORRECTED: earlier draft incorrectly claimed `billing_router._fraud_gate` was a module-level name in `app/routers/txn_requests.py`.] `execute_request` surfaces the 403 and the item remains `INITIATED` / `PENDING` (no terminal write). A subsequent execute with fraud gate restored succeeds normally.

### 5.5 Frontend polling termination

`useTxnRequest` uses `refetchInterval: (data) => (data?.status === "INITIATED" || data?.status === "PENDING") ? 2000 : false`. The test (Jest/vitest unit test) mocks `useQuery` and asserts the computed interval is `false` for `COMPLETED`/`FAILED` and `2000` for non-terminal statuses.

### 5.6 Flag off behavior

With `S.txn_requests_enabled = False`, every TXR endpoint returns 404 (the router is not registered in `app/main.py`). The test sets `S.txn_requests_enabled = False` via `object.__setattr__` and asserts the route handler is not reachable (or that importing the router does not register it). The E2E spec skips all tests when the flag env var is absent (using `test.skip` or a `beforeAll` guard that checks `VITE_TXN_REQUESTS_ENABLED`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 parity

No `if S.dev_mode` branches exist in `app/services/txn_requests.py` or `app/routers/txn_requests.py`. The dev/prod distinction lives entirely inside existing provider abstractions:

- OTP delivery: `app/services/mfa.py` dev path writes codes to `S.dev_email_log` and `_dev_sms_codes` dict; prod path calls Twilio/SES. TXR-003 uses `create_stepup_challenge` which is the same call in both envs.
- Stripe: `stripe-mock` on port 12111 in dev (wired via `S.stripe_api_base`); real Stripe in prod. `_do_refund` calls `stripe.Refund.create` through the same code path.
- DynamoDB: DynamoDB Local on port 8001 in dev (wired via `S.ddb_endpoint_url`); real DynamoDB in prod. Same boto3 calls.

The pytest suite uses moto (`@mock_aws`) for DynamoDB and `MagicMock` for Stripe — the same approach as `tests/test_billing.py` and `tests/test_gap_0286_0287_kyc_partner_api.py`. No test exercises real AWS or real Stripe.

### 7.2 Money-safety invariants verified by tests

These invariants are binding from the TXR cross-cutting constraints and must each have at least one explicit test assertion:

1. **No double-charge**: double-execute test verifies `stripe.Refund.create.call_count == 1` for REFUND; `apply_wallet_delta.call_count == 1` (via mock) or equivalent balance-check for WALLET_TRANSFER.
2. **No partial move**: WALLET_TRANSFER insufficient-funds test verifies recipient wallet unchanged after sender debit fails (the `transact_write_items` batch is all-or-nothing; if the debit condition fails the batch is not committed).
3. **Status is the lock**: concurrent-execute test verifies exactly one `PENDING → IN_FLIGHT` claim wins (TXR-004 §4.2 locking step); the loser gets 409 and the item carries the terminal `COMPLETED` status from the winner. Money moves exactly once because dispatch only runs after winning the `IN_FLIGHT` claim.
4. **Fraud gate on execute**: frozen-account test verifies the item stays `INITIATED`/`PENDING` after a 403 from `_fraud_gate`; no ledger row is written.
5. **One refund mechanism**: REFUND type calls `billing._do_refund` (the shared callable factored from `billing.refund_payment`); the test asserts `stripe.Refund.create` is called exactly once and that the ledger entry matches the legacy refund path's shape (`entry_type="adjustment"`, `reason="refund"`, `state="settled"`, `extra.provider="stripe"`).
6. **SCA gates value**: PENDING-execute-before-challenge-done test verifies `403 sca_incomplete` and no money movement.

### 7.3 Idempotency

- **Create idempotency**: `idempotency_key` deduplication is a DDB conditional put (`attribute_not_exists(idempotency_key)`) or a pre-write lookup; a duplicate create returns the existing item without writing a new one.
- **Execute idempotency**: the `PENDING/INITIATED → COMPLETED` transition uses a conditional `update_item` asserting `attribute_value(status)` in `{PENDING, INITIATED}`; a second execute on a `COMPLETED` item raises `ConditionalCheckFailedException`, which the service layer maps to a clean read-and-return of the terminal item (not an error to the caller).

### 7.4 Security

- Ownership: `GET /ui/txn-requests/{id}` and `POST /ui/txn-requests/{id}/execute` use `Key={"user_sub": caller_sub, "request_id": id}` access pattern; a foreign `request_id` returns no item → 404. Users cannot read or execute each other's requests.
- CSRF: all POST endpoints are session-auth with CSRF enforced (non-GET cookie-auth requests require `x-csrf-token` header per CLAUDE.md). Bearer-auth callers skip CSRF.
- Challenge scope: `purpose="txn_request_sca"` prevents `maybe_finalize` (`sessions.py:653`) from treating a completed TXR challenge as a completed login. (`maybe_finalize` returns `None` early when `chal.get("purpose")` is set; verified at `app/services/sessions.py:657`.) The challenge is revoked on successful execute via `revoke_challenge` so it cannot be reused.
- Amount limits: enforced at create time by `enforce_amount_limit(type, amount_cents)` (`app/core/settings.py` ceiling); a forged execute with a `request_id` for an oversized amount is impossible because the item was never written.

## 10. Open Questions / Assumptions

1. **Dev-mode OTP retrieval in E2E**: The email OTP is written to `S.dev_email_log` (a file path). 2. **COUNTERPARTY type in E2E**: Since `COUNTERPARTY` always results in `FAILED counterparty_unsupported` until Tier-2 Counterparties lands, the E2E spec does not cover COUNTERPARTY happy-path execution. The pytest unit test covers the `FAILED` path. **Assumption**: acceptable; COUNTERPARTY E2E happy-path is blocked on the Tier-2 ticket.

3. **Hook polling vs SSE**: The `useTxnRequest` poll cadence of 2000ms is a pragmatic choice. A more efficient approach would use the existing SSE stream (`/ui/events`) with a new `txn_request.status_changed` event type dispatched by the engine. **Assumption**: polling is acceptable for the initial implementation; SSE delivery is a follow-up optimization.

4. **`useTxnRequest` concurrent stale update**: if the execute mutation and the polling query race, the query may return a stale `PENDING` state for up to 2000ms after execute succeeds. **Assumption**: acceptable UX; the mutation's `onSuccess` callback manually invalidates `["txn-request", requestId]` via `queryClient.invalidateQueries`, eliminating the stale window in practice.

5. **`_do_refund` factoring (TXR-004 pre-req)**: TXR-005's refund test relies on `billing._do_refund` being the single callable. If TXR-004 was not implemented as a true factoring (and the logic remains inline in `refund_payment`), the test must patch `billing_router.refund_payment` instead of `billing_router._do_refund`. **Assumption**: TXR-004 delivers the factoring; the test patches `billing._do_refund`.
