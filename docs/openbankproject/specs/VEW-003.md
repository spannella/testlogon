# VEW-003 — Field-level projection enforcement when reading through a View

**Ticket prefix**: VEW | **Priority**: P1 (enforcement layer) | **Estimate**: 2 days
**Source**: `docs/openbankproject/OBP_VIEWS_ENTITLEMENTS_TICKETS.md` §VEW-003
**Flag**: `account_views_enabled` (env `ACCOUNT_VIEWS_ENABLED`, default OFF)

---

## 1. Summary & Goal

VEW-003 is the enforcement layer that makes Views meaningful. When a financial resource is read **through a View** — either by an authenticated grantee holding an active grant (VEW-002's `resolve_active_grant`) or by an unauthenticated caller following a public signed link (VEW-002's `resolve_public_view`) — the response contains **only the fields the View's `grants` map permits**.

Without this layer a View grant is pure metadata: the grant exists but the read path returns the full resource regardless. VEW-003 closes that gap with two additions:

1. A pure, deterministic, side-effect-free `project_resource(resource, grants, resource_type)` function that strips every field not explicitly unlocked by the caller's grants, and masks (rather than drops) fields whose parent grant is on but whose `metadata_visibility` flag requests blur treatment.
2. A single new REST endpoint — `GET /ui/views/{resource_type}/{resource_id}/{view_id}/data` — that assembles the full resource via existing read primitives, projects it through the caller's grant-map, appends a `_view` provenance block, and emits an `account_view.read` audit event.

The public-link read path wired in VEW-002 (`GET /ui/views/public/{token}`) calls the same projector, so both authenticated and unauthenticated reads share one code path. The existing owner read paths (`billing.py`, `creator_payouts.py`) are unchanged — no `if S.account_views_enabled` branch touches them.

## 2. Context & Current State

### 2.1 What VEW-003 builds on

**VEW-001** (`app/services/account_views.py`) defines:
- `VIEW_FIELD_GRANTS: set[str]` — the master catalog of per-field boolean keys (`can_see_balance`, `can_see_transaction_amount`, `can_see_counterparty`, `can_add_comment`, …).
- `VIEW_PRESETS` — the four OBP canonical presets (`owner` / `accountant` / `auditor` / `public`), each a named grant-map over `VIEW_FIELD_GRANTS`.
- `get_view(resource_type, resource_id, view_id) -> dict | None` — retrieves a View row including its `grants` map and `metadata_visibility` field.
- `ensure_owner_view(owner_sub, resource_type, resource_id) -> dict` — idempotent auto-provision of the immutable `owner` system view whose grant-map is the full `VIEW_FIELD_GRANTS`.

**VEW-002** (`app/services/account_views.py`, additions) defines:
- `resolve_active_grant(grantee_sub, resource_type, resource_id, view_id) -> dict | None` — checks the `account_views` table for an `active` VIEWGRANT row and returns it together with the View's `grants` map, or `None` if no active grant exists.
- `resolve_public_view(token) -> {resource_type, resource_id, view_id, grants}` — verifies the HMAC-signed public-link token (using the `_sign_recovery_token` / `_verify_recovery_token` HMAC-SHA256 pattern from `app/services/cart_reminders.py:150-166`, **not** `verify_ws_token` which is hardcoded to `S.ws_token_secret`; the secret resolver uses `account_view_public_secret` → `ui_access_token_secret` fallback) and returns the resolved grants.

Neither of these functions performs field projection — that is VEW-003's sole responsibility.

### 2.2 The delegation analogue in the existing codebase

The closest existing primitive is `app/services/delegates.py:243-270` — `check_delegate_permission` / `require_delegate_permission`. Those functions gate a **whole action** (boolean allow/deny). VEW-003 does the per-field analogue: instead of a binary gate it **shapes the response body** by removing every field not permitted by the caller's grants. The pattern is: resolve grants → assemble full resource → project.

### 2.3 Resource assembly — existing read primitives (not forked)

VEW-003 calls the existing resource assembly functions read-only and projects their output. It does not re-implement any resource logic.

- **Wallet resource** (`resource_type="wallet"`): the full wallet dict is built from `app/services/billing_shared.py:176` `get_wallet_balance(table, pk)` (returns `wallet_balance_cents`, `currency`, `updated_at`) and the BALANCE row fields from the billing table. The `resource_id` is the owner's `user_sub`; the `pk` passed to `get_wallet_balance` is `user_pk(user_sub)` (`billing_shared.py:23`).
- **Payout destination** (`resource_type="payout_destination"`): assembled via `app/services/creator_payouts.py:66` `_payout_to_dict(item)`, which returns `payout_id`, `user_id`, `amount_cents`, `method`, `method_id`, `status`, `created_at`, `updated_at`, `notes`, `reject_reason`, `approved_by`, `completed_at`. The `resource_id` is the `payout_id` (or `method_id` for payout-method rows).
- **Ledger account** (`resource_type="ledger_account"`): a list of ledger rows from the billing table (`pk=USER#{user_sub}`, `sk` begins with `LEDGER#`). Assembled by a thin helper in `account_views.py` that queries the billing table and returns `{balance_summary: {...}, transaction_list: [{...}]}`.

### 2.4 No existing field-projection layer

There is currently no code in the codebase that strips or masks fields from a resource dict based on a caller-supplied grant-map. `project_resource` is entirely net-new. Because it is a pure function with no I/O, it can be placed anywhere in `app/services/account_views.py` and called from both the authenticated endpoint and the public-link handler without circular import risk.

### 2.5 Audit infrastructure

`app/services/alerts.py:644` — `audit_event(event, user_sub, request=None, **fields)` is the single canonical audit write path (`T.alerts`, fields flatten to top-level DDB item). VEW-003 calls it with `event="account_view.read"` after every successful projected read. The same function is imported by `app/routers/admin_roles.py:19` and `app/auth/policy.py:10` for read reference.

### 2.6 Auth dependencies

- User-facing endpoint: `Depends(require_ui_session)` from `app/services/sessions.py` (cookie + optional Bearer). All non-GET endpoints require `x-csrf-token` header; the read endpoint is a GET, so no CSRF.
- Owner implicit grant: the resource owner (`caller.sub == resource_id` for wallet/ledger, or verified via `_assert_owns_resource`) is implicitly granted the `owner` view and receives the full projection without a VIEWGRANT row.
- Public endpoint: registered on a separate unauthenticated router (no `require_ui_session`). Must be listed in `API_KEY_ROUTE_EXEMPTIONS` (following the `calendar_public_event_router` pattern in `app/main.py:61`).

## 3. Data Model

VEW-003 introduces **no new DynamoDB tables or attributes**. All persistence changes are in VEW-001 (the `account_views` table) and VEW-002 (VIEWGRANT rows on that same table). This section documents the projection-relevant shape of the data that VEW-003 reads.

### 3.1 The `account_views` table (established by VEW-001)

Partition key: `pk` (S), sort key: `sk` (S).

**View definition row** (`sk=VIEW#{view_id}`):
| Attribute | Type | Relevant to VEW-003 |
|---|---|---|
| `grants` | Map `{field_key: bool}` | The projection mask: only truthy entries allow the field through |
| `metadata_visibility` | S (optional) | `"counterparty_blur"` → mask present but blur rather than drop |
| `preset` | S (optional) | Informational; not used by the projector itself |
| `resource_type` | S | Selects the `FIELD_TO_GRANT` registry entry |
| `is_system_alias` | Bool | True on the auto-provisioned `owner` view (full grants) |

**VIEWGRANT row** (`sk=VIEWGRANT#{grantee_sub}#{view_id}`):
| Attribute | Type | Relevant to VEW-003 |
|---|---|---|
| `status` | S | Must be `"active"` for `resolve_active_grant` to return the grant |
| `view_id` | S | Used to look up the View definition row for its `grants` map |

**GSIs** (defined by VEW-001, not modified here):
- `by-owner` GSI: `GSI1PK=OWNER#{owner_sub}`, `GSI1SK=created_at` (N) — `attr_types={"GSI1SK":"N"}`. Not queried by VEW-003 directly.
- `by-grantee` GSI (VEW-002): `GSI2PK=GRANTEE#{grantee_sub}`, `GSI2SK=accepted_at` (N) — `attr_types={"GSI2SK":"N"}`. Not queried by VEW-003 directly; used by `resolve_active_grant`. (**Note**: this is GSI2, not GSI1 — `GSI1PK`/`GSI1SK` are already claimed by `by-owner`; using the same attribute names for both GSIs would cause a DynamoDB `ValidationException`.)

### 3.2 The `FIELD_TO_GRANT` registry (new, in-memory constant)

This is not a DynamoDB construct — it is a Python constant defined in `app/services/account_views.py`. It maps each `resource_type` to a `dict[response_field_path, grant_key]` where `grant_key` is a member of `VIEW_FIELD_GRANTS`.

```
FIELD_TO_GRANT: dict[str, dict[str, str]] = {
    "wallet": {
        "wallet_balance_cents":     "can_see_balance",
        "available_balance_cents":  "can_see_available_balance",
        "currency":                 "can_see_account_label",
        "label":                    "can_see_account_label",
        "updated_at":               "can_see_account_label",
    },
    "ledger_account": {
        "balance_summary":          "can_see_balance",
        "transaction_list":         "can_see_transaction_list",
    },
    "payout_destination": {
        "method":                   "can_see_payout_destination_masked",
        "method_id":                "can_see_payout_destination_masked",
        "status":                   "can_see_payout_destination_masked",
        "amount_cents":             "can_see_transaction_amount",
        "created_at":               "can_see_account_label",
        "updated_at":               "can_see_account_label",
        "notes":                    "can_see_transaction_description",
        "reject_reason":            "can_see_transaction_description",
        "approved_by":              "can_see_counterparty",
        "completed_at":             "can_see_account_label",
    },
}

# Per-field registry for rows within a transaction_list
TRANSACTION_ROW_FIELD_TO_GRANT: dict[str, str] = {
    "amount_cents":             "can_see_transaction_amount",
    "description":              "can_see_transaction_description",
    "counterparty":             "can_see_counterparty",
    "counterparty_name":        "can_see_counterparty_name",
    "reason":                   "can_see_transaction_description",
    "state":                    "can_see_transaction_amount",
    "ts":                       "can_see_transaction_amount",
    "entry_id":                 "can_see_transaction_amount",
}
```

Fields not present in the registry for a resource type are **always stripped** under a view (deny-by-default). Fields that are technically identifiers (`payout_id`, `user_id`, `resource_type`, `resource_id`) are included in the response unconditionally because they identify the envelope, not the financial data.

## 4. API / Service Design

### 4.1 Pure projector function

```python
def project_resource(
    resource: dict,
    grants: dict[str, bool],
    resource_type: str,
    *,
    metadata_visibility: str = "",
) -> dict:
```

**Location**: `app/services/account_views.py`

**Behavior**:
1. Look up `FIELD_TO_GRANT.get(resource_type)`. If the resource type is unknown return `{}` immediately (deny-all, fail-closed).
2. Iterate over `field_map.items()`. For each `(field, grant_key)`: include the field in the output iff `grants.get(grant_key) is True`. Otherwise omit it entirely.
3. Always include envelope-identity fields: `resource_type`, `resource_id`, `payout_id`, `user_id` — whichever are present on the raw dict.
4. If `"transaction_list"` is present in the output (i.e. `can_see_transaction_list` is truthy), recurse over each row in the list applying `TRANSACTION_ROW_FIELD_TO_GRANT`:
   - For each row, keep a transaction-row field iff `grants.get(TRANSACTION_ROW_FIELD_TO_GRANT[field])` is True; strip unmapped fields.
5. Apply `metadata_visibility` blur: if `metadata_visibility == "counterparty_blur"` and `grants.get("can_see_counterparty")` is True, replace the `counterparty` value with `"••••"` and `counterparty_name` with `"••••"` rather than including the real values. This honors OBP's blurring behavior: the field is present (so the caller knows there is a counterparty) but its identity is masked.
6. Return the projected dict. The function is pure — it never raises, never performs I/O, never modifies the input dict.

### 4.2 Resource assembler helpers (new, thin, read-only)

These helpers live in `app/services/account_views.py` and call existing primitives without forking them.

```python
def _assemble_wallet_resource(owner_sub: str) -> dict:
    """Call get_wallet_balance + BALANCE row fields; return full wallet dict."""

def _assemble_ledger_resource(owner_sub: str, *, limit: int = 50) -> dict:
    """Query T.billing for LEDGER# rows; return {balance_summary, transaction_list}."""

def _assemble_payout_destination_resource(owner_sub: str, resource_id: str) -> dict:
    """Get payout-method row from T.creator_payouts; return _payout_to_dict output."""
```

Each raises `HTTPException(404)` if the resource does not exist. Each is called by the read endpoint and never called outside VEW-003.

### 4.3 Read endpoint

**Endpoint**: `GET /ui/views/{resource_type}/{resource_id}/{view_id}/data`

**Router**: `app/routers/account_views.py` (existing router from VEW-001/002; this endpoint appended)

**Auth**: `Depends(require_ui_session)` — cookie or Bearer token. GET request, so no CSRF.

**Route ordering note**: the literal `/data` suffix is the last path segment, following the existing pattern where the `/{view_id}` segment was already declared in VEW-001. This avoids any capture collision.

**Request**: path parameters only — `resource_type: str`, `resource_id: str`, `view_id: str`. No query parameters for the initial implementation.

**Response model** (`ViewedResourceOut`, new in `app/models.py`):
```python
class ViewProvenanceOut(BaseModel):
    view_id: str
    view_name: str        # from the View row's `name` attribute (VEW-001 stores field as `name`, not `view_name`)
    preset: str | None
    granted_fields: list[str]   # list of grant_keys that resolved to True

class ViewedResourceOut(BaseModel):
    resource_type: str
    resource_id: str
    data: dict            # projected field subset
    view: ViewProvenanceOut = Field(alias="_view")  # use Field(alias="_view") — bare `_view: ...` is a Pydantic private attr and will NOT appear in model_dump() / the JSON response
    model_config = ConfigDict(populate_by_name=True)
```

**Important**: `ViewProvenanceOut` must be defined before `ViewedResourceOut` in `app/models.py`. The `view` field uses `Field(alias="_view")` so that the JSON key is `_view` (matching OBP convention) while the Python attribute name is `view` — consistent with Pydantic v2 behavior where a bare `_view: T` declaration is silently treated as a private class variable and excluded from serialization.

**Handler logic** (in `app/routers/account_views.py`):
1. Determine whether the caller is the resource owner via `_assert_owns_resource(caller.sub, resource_type, resource_id)` — a read-only ownership check that does not raise on non-owners, returning a bool instead.
2. If the caller **is** the owner: use `ensure_owner_view(caller.sub, resource_type, resource_id)` to get the full-grant view object. The `view_id` path parameter is ignored in this branch (the owner always reads the `owner` view).
3. If the caller is **not** the owner: call `resolve_active_grant(caller.sub, resource_type, resource_id, view_id)`. If `None` is returned, raise `HTTPException(403, "No active view grant")`.
4. Call the appropriate `_assemble_*_resource` helper for `resource_type`. Unknown `resource_type` → `HTTPException(400, "Unknown resource_type")`.
5. Call `project_resource(full_resource, grant_obj.grants, resource_type, metadata_visibility=view.get("metadata_visibility", ""))`.
6. Build the `_view` provenance block: `view_id`, `view_name` (from `view_row["name"]` — the View row field is `name` per VEW-001 §3.1, not `view_name`), `preset`, and `granted_fields = [k for k, v in grant_obj.grants.items() if v]`.
7. Call `audit_event("account_view.read", caller.sub, resource_type=resource_type, resource_id=resource_id, view_id=view_id)`.
8. Return `ViewedResourceOut(resource_type=..., resource_id=..., data=projected, _view=provenance)`.

### 4.4 Public-path wiring (in VEW-002's unauthenticated handler)

The `GET /ui/views/public/{token}` handler (established by VEW-002, unauthenticated router) gains the following addition after resolving the token:

```python
resolved = resolve_public_view(token)          # VEW-002; raises on expired/tampered
# _assemble_resource is a thin dispatcher in account_views.py that routes to
# _assemble_wallet_resource / _assemble_ledger_resource / _assemble_payout_destination_resource
full = _assemble_resource(resolved["resource_type"], resolved["resource_id"])
projected = project_resource(
    full,
    resolved["grants"],
    resolved["resource_type"],
    metadata_visibility=resolved.get("metadata_visibility", ""),
)
provenance = {
    "view_id": resolved["view_id"],
    "view_name": resolved["view_name"],
    "preset": resolved.get("preset"),
    "granted_fields": [k for k, v in resolved["grants"].items() if v],
}
return {"resource_type": ..., "resource_id": ..., "data": projected, "_view": provenance}
```

The same `project_resource` function is called in both paths. No separate projector for the public path.

## 5. Detailed Behavior & Edge Cases

### 5.1 Deny-by-default for unmapped fields

Any response field that does not appear in `FIELD_TO_GRANT[resource_type]` is stripped unconditionally. If a future resource assembly helper adds a new field (e.g. a new ledger row attribute) that is not yet listed in the registry, that field will be absent from all view-projected responses until the registry is updated. This is the safe direction: over-stripping is never a data-leak; under-stripping would be.

### 5.2 Unknown `resource_type`

`project_resource` returns `{}` for an unknown `resource_type`. The endpoint handler rejects unknown `resource_type` values with `400` before calling the projector, so the `{}` return from the projector is a defense-in-depth backstop (e.g. if called directly from the public-link path where the resource type came from a token).

### 5.3 Owner implicit grant (full fidelity, bypasses projection)

The resource owner reading their own wallet via `GET /ui/views/wallet/{user_sub}/owner/data` goes through the `ensure_owner_view` branch. The `owner` view's grant-map contains every key in `VIEW_FIELD_GRANTS` set to `True`, so `project_resource` passes all mapped fields through. The owner's full read path is unchanged: `billing.py` and `creator_payouts.py` endpoints remain untouched and unaffected by the feature flag.

### 5.4 Grantee with `accountant` preset

The `accountant` preset (VEW-001 `VIEW_PRESETS`) grants: `can_see_balance`, `can_see_available_balance`, `can_see_transaction_amount`, `can_see_counterparty`, `can_see_counterparty_name`, and `can_see_account_label`. It does **not** grant `can_see_transaction_description`, `can_see_transaction_list`, or any `can_add_*` / `can_delete_*` key. An accountant reading a wallet resource sees `wallet_balance_cents`, `available_balance_cents`, `currency`, `label` — not `transaction_list`, not `notes` or `description` on any ledger row.

### 5.5 Grantee with `auditor` preset

The `auditor` preset grants all `can_see_*` keys and zero `can_add_*` / `can_delete_*` keys. An auditor reading a ledger account sees the full `transaction_list` with all row-level read fields (`amount_cents`, `description`, `counterparty`, `counterparty_name`, …) but cannot use the `can_add_comment` write affordance (since write affordances are not included in the projected data response — they are future enrichment endpoints covered by later VEW work).

### 5.6 `metadata_visibility == "counterparty_blur"`

When a View row has `metadata_visibility = "counterparty_blur"`:
- If `can_see_counterparty` is `True` in the grants: the `counterparty` field is present in the projection but its value is replaced with `"••••"`.
- If `can_see_counterparty` is `False`: the field is stripped normally (no blur, just absent).
- Same applies to `counterparty_name` when `can_see_counterparty_name` is `True`.
- This is applied both at the top-level resource and within each `transaction_list` row.

### 5.7 `public` preset projection

The `public` preset grants only `can_see_account_label` (and nothing else by default, though owners may configure). The projected response for a `wallet` resource under the `public` preset contains only `label` and `currency` (both mapped to `can_see_account_label`). `wallet_balance_cents` requires `can_see_balance` which the public preset does not grant. The integration test in §9 explicitly asserts that `wallet_balance_cents` is absent from a public-link response.

### 5.8 Revoked grant

If a grantee's grant has been revoked (status transitions from `active` to `revoked` / row deleted — VEW-002 `revoke_view_grant`), `resolve_active_grant` returns `None` on the next call. The endpoint raises `HTTPException(403)`. No stale-grant caching: every request re-reads the grant row from DynamoDB.

### 5.9 Expired public-link token

`resolve_public_view(token)` checks the HMAC expiry (`verify_ws_token`-style; `app/core/crypto.py:57`). An expired token raises `HTTPException(400)` before `project_resource` is ever called.

### 5.10 Large `transaction_list`

`_assemble_ledger_resource` queries `T.billing` for LEDGER rows and defaults to `limit=50`. The VEW-003 endpoint may accept an optional `?limit=` query parameter (max 200, default 50) to control the window. If DynamoDB returns a `LastEvaluatedKey`, the response includes a `next_cursor` field (using `app/core/cursor.py:94` `encode_cursor`) so callers can page through the full ledger. The projection is applied per row — cursor encoding and per-page projection are independent.

### 5.11 `transaction_list` top-level vs. row-level grant split

`can_see_transaction_list` gates whether the `transaction_list` key appears in the response at all. If it is `False`, the key is dropped before any row-level processing. If it is `True`, each row is individually projected through `TRANSACTION_ROW_FIELD_TO_GRANT`. A grants map where `can_see_transaction_list=True` but `can_see_transaction_amount=False` returns rows that have `description`, `counterparty`, etc. but not `amount_cents` — consistent with OBP's per-field design.

### 5.12 `_view` provenance block not projected

The `_view` envelope block (`view_id`, `view_name`, `preset`, `granted_fields`) is appended to the response after projection. It is metadata about the view, not a financial field, so it is never subject to the grant filter.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no `dev_mode` branch

All DynamoDB reads in VEW-003 go through `T.account_views` and `T.billing` / `T.creator_payouts` via the `_FloatSafeTable` proxy (`app/core/tables.py:29`). DynamoDB Local on port 8001 in dev, real DynamoDB in prod — same code path, no `if S.dev_mode` branch anywhere in VEW-003.

The HMAC public-link token verification (`resolve_public_view`) uses the same HMAC-SHA256 / `b64url(payload).b64url(sig)` scheme as `app/services/cart_reminders.py:150-166` `_sign_recovery_token`/`_verify_recovery_token` with `hmac.compare_digest` constant-time compare (same logic as `app/core/crypto.py:44-52`, but using a custom secret resolver rather than calling `verify_ws_token` directly — `verify_ws_token` hardcodes `S.ws_token_secret` and cannot use `account_view_public_secret`). The `account_view_public_secret` → `ui_access_token_secret` fallback means dev (no extra env var) and prod (explicit secret set in env) both verify correctly with zero code divergence.

### 7.2 Projection is side-effect-free

`project_resource` is a pure function with no I/O. It cannot change a DynamoDB row, debit a balance, or trigger a side-effect. The read endpoint assembles resources read-only and projects them — no mutation ever occurs.

### 7.3 No money-safety concerns in this ticket

VEW-003 is a read-only projection layer. It does not call `new_ledger_entry`, `apply_wallet_delta`, `settle_or_reverse_ledger`, or any Stripe / PayPal / CCBill SDK path. Money-safety constraints (TXR/PAY/ACC), `_fraud_gate`, and SCA gating are not applicable to a read-only operation. The audit trail (`account_view.read`) is the only write in the entire request path.

### 7.4 Idempotency

The read endpoint is idempotent by definition. Repeated identical requests to `GET .../data` return the same projected dict given the same grants and resource state. No counter increments, no state mutations.

### 7.5 Deny-by-default is the security invariant

The security contract of `project_resource` is: **a field is only present if its grant key maps to `True` in the caller's grants**. An implementation bug that accidentally includes an extra field leaks data; an implementation bug that accidentally omits a field reduces functionality. The design therefore favors stripping (over-strip rather than under-strip). Unknown resource type → `{}` enforces this at the outermost level.

### 7.6 No grant escalation through the projector

`project_resource` never reads the `account_views` table itself. It takes the `grants` dict as a parameter already resolved by `resolve_active_grant` or `resolve_public_view`. If those upstream functions are correct (VEW-002), the projector cannot escalate beyond the supplied grants.

### 7.7 Audit trail on every read

Every authenticated call to `GET .../data` emits `audit_event("account_view.read", caller.sub, resource_type=..., resource_id=..., view_id=...)` via `app/services/alerts.py:644`. Public-link reads emit `audit_event("account_view.public_read", "anonymous", resource_type=..., resource_id=..., view_id=...)` (user_sub is the literal string `"anonymous"` since there is no authenticated caller). This mirrors OBP's requirement that view access is logged.

## 8. Backward Compatibility & Migration

### 8.1 No schema migration required

VEW-003 introduces no new DynamoDB attributes and no new tables. The `FIELD_TO_GRANT` registry and `project_resource` function are in-memory constants and pure code respectively. The `ViewedResourceOut` and `ViewProvenanceOut` Pydantic models are net-new additions to `app/models.py` and do not modify any existing model.

### 8.2 Existing read endpoints are unchanged

`billing.py` wallet/balance endpoints, `creator_payouts.py` payout endpoints, and all other financial-resource read paths are byte-for-byte unmodified by VEW-003. No existing test, no existing client, and no existing endpoint is affected by the presence of the VEW-003 code in the repository while the flag is off.

### 8.4 Additive Pydantic models

`ViewedResourceOut` and `ViewProvenanceOut` are added to `app/models.py` as new, non-replacing model definitions. No existing model is modified. `app/models.py` currently has no model with these names.

### 8.5 `FIELD_TO_GRANT` is extensible

When the banking data model (Tier-2 tickets per `OBP_GAP_ANALYSIS.md`) introduces new `resource_type` values, the team adds a new entry to `FIELD_TO_GRANT`. The projector's unknown-type `{}` return means any new resource type is safe by default until its registry entry is added.

## 10. Open Questions / Assumptions

1. **`ledger_account` resource assembly pagination in VEW-003**: The initial implementation returns up to 50 ledger rows (or a configurable `?limit=` up to 200). Whether the full historical ledger should be exposed via views is a product decision. Assumption: 50 rows is sufficient for the initial implementation; cursor-based pagination (`encode_cursor` / `decode_cursor` from `app/core/cursor.py:94,103`) is wired but returning only the first page is acceptable for the test suite.

2. **Write affordances (VEW-001 `can_add_comment`, `can_add_tag`, etc.)**: The `FIELD_TO_GRANT` registry covers only read (data) fields. Write affordances are grant keys that gate future enrichment endpoints (add comment, add tag, add narrative) — those endpoints are out of scope for VEW-003. The projector does not need to include write-affordance flags in the response body; they are enforced at those future write endpoints. Assumption: VEW-003 data response carries only data fields, not write-permission flags.

3. **Which `resource_types` are in scope for the initial release**: The spec covers `wallet`, `ledger_account`, and `payout_destination`. `ledger_account` assumes the billing table format (`billing_shared.py` LEDGER rows). If the Tier-2 bank-account model (ACC-001..ACC-005) introduces a distinct account entity, the `FIELD_TO_GRANT` registry will need an `"account"` entry — that is out of scope for VEW-003.

4. **Counterparty blur on payout_destination**: OBP's `counterparty_blur` was originally designed for bank-transfer counterparty names. On a payout-method row the closest analogue is `approved_by` (the admin who approved a payout). Whether `counterparty_blur` should mask `approved_by` on `payout_destination` is a product decision. Assumption: `counterparty_blur` is applied to the `counterparty` and `counterparty_name` sub-fields of ledger transaction rows only; it does not affect `payout_destination` fields in the initial implementation.

5. **Rate-limiting the `/data` endpoint**: VEW-003 assembles financial data on each call. High-frequency polling could be expensive. The `rate_limit.py` `_bucket_limit` primitive (`app/services/rate_limit.py`) is available. Assumption: rate limiting on the `/data` endpoint is out of scope for VEW-003 and can be layered on in a follow-up ticket.
