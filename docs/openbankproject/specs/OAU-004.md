# OAU-004 — Per-consumer scope enforcement on API calls

**Ticket type**: Backend (middleware + service + auth-layer wiring)
**Priority**: P1
**Estimate**: 2.5 days
**Status**: Unimplemented
**Flags**: `OAUTH_PROVIDER_ENABLED` (master, from OAU-001, default off) + `OAUTH_PROVIDER_SCOPE_ENFORCEMENT_ENABLED` (new, this ticket, default off)

---

## 1. Summary & Goal

OAU-002 issues OAuth2 access tokens that carry a `scope` claim, but nothing in the current
codebase enforces those scopes at the API boundary. Any OAuth-bearer caller that authenticates
successfully can call any endpoint regardless of which scopes were granted in their token.

OAU-004 closes that gap by wiring the per-consumer `granted_scope` set from each OAuth access
token into the **same route-to-scope policy registry** that already governs API-key callers
(`API_KEY_ROUTE_SCOPE_REGISTRY`, `app/services/api_key_route_scope_registry.py:17-67`). A
single registry governs both auth modes. The enforcement is an additive middleware-layer hook
with no changes to any existing router, endpoint, or API-key path — non-OAuth callers
(cookie sessions, Cognito JWTs, API keys) are completely unaffected.

The three concrete goals of this ticket are:

1. Implement `app/services/oauth_scope_enforcement.py` — a stateless helper that reads
   `request.state.oauth_scope` (written by OAU-002's auth branch), looks up the registry,
   and raises a 403 when any required scope is missing from the token's granted set.
2. Wire that helper into the existing API-key policy middleware path
   (`app/services/api_key_policy_enforcement.py:31-261`) as a sibling check — same request
   lifecycle point, same gate shape, same audit trail.
3. Register the new setting `S.oauth_provider_scope_enforcement_enabled` and gate the check
   so that toggling the flag off returns enforcement to identity-only (tokens authenticate
   but scope is not enforced).

Nothing in this ticket changes DynamoDB tables, token issuance, or any existing auth dep.

## 2. Context & Current State

### The API-key scope enforcement path (the pattern to mirror)

API-key scope enforcement is already fully built and in production. Understanding it precisely
is the prerequisite for understanding what OAU-004 adds.

**Registry**: `API_KEY_ROUTE_SCOPE_REGISTRY` maps `"METHOD:/path/template"` strings to
`RouteScopePolicy` dicts (`app/services/api_key_route_scope_registry.py:17-67`). Each policy
carries `product`, `required_scopes: List[str]`, and `entitlement_required: bool`.
`API_KEY_ROUTE_EXEMPTIONS` (`api_key_route_scope_registry.py:70-256`) lists routes that are
deliberately excluded from scope enforcement. Helper functions:
`get_route_scope_policy(route_id)` → `RouteScopePolicy | None` (line 275),
`resolve_required_scopes_for_route(route_id)` → `List[str]` (line 279),
`is_route_registered_or_exempt(route_id)` → `bool` (line 316).

**Route-id construction**: `route_id_from_request(request)` in
`app/services/api_metering_contract.py:90-96` reads `request.scope["route"]` (an `APIRoute`)
and calls `resolve_route_id(request.method, route)` → `normalize_route_id` (lines 33-37),
which produces `"GET:/messaging/conversations"` form. This is the canonical key used both by
the registry and by the API-key enforcement path.

**Enforcement function**: `maybe_enforce_api_key_route_policy(request)` in
`app/services/api_key_policy_enforcement.py:31-261`. It is wired as a **per-router
`Depends`** on each of the seven product routers (`messaging`, `filemanager`, `newsfeed`,
`tickets`, `catalog`, `shoppingcart`, `purchase_history`) — not as a central Starlette
middleware. It runs on every request that carries `ApiKey`/`X-API-Key` headers. It resolves
the principal from DDB (`require_api_key_principal`), calls `get_route_scope_policy(route_id)`,
feeds the result to `requires_scope_for_request_from_registry`
(`app/services/api_key_authorization.py`), and raises 403 on mismatch or delegates to the
audit trail + metrics. On a 403 it emits `audit_event("api_key_scope_denied", user_sub,
request, ...)` (condition at line 220, `audit_event(` call at line 222).

**How `api_key_principal` reaches `get_authenticated_user`**: The API-key policy function
stores the resolved principal on `request.state.api_key_principal` (via
`require_api_key_principal`). `get_authenticated_user` (`app/auth/deps.py:209-224`) reads it
from `request.state` as the first check, before cookie/Cognito paths.

### What OAU-002 adds to `request.state` (the input for OAU-004)

OAU-002's auth branch in `get_authenticated_user` (`app/auth/deps.py:199`) decodes the
OAuth access token, verifies it as HS256 (`S.ui_access_token_secret`), confirms
`token_type=="access"` and `client_id` present, resolves the resource owner's role from
`T.users`, and then stores the token's `scope` claim on `request.state.oauth_scope` and the
`client_id` on `request.state.oauth_client_id` (`OAU-002 spec, lines 355-356`).

OAU-004 also requires `request.state.oauth_user_sub` for the audit event — see the **IMPORTANT
GAP** note in section 4.3. OAU-002's implementor must add that third write.

Format: `request.state.oauth_scope` is a space-delimited string, e.g.
`"messager:read filemanager:read"`, exactly matching the OAuth2 RFC 6749 `scope` wire format.
OAU-004 splits on whitespace to produce a `frozenset[str]`.

### What does NOT exist yet (the gap)

There is no code that reads `request.state.oauth_scope` and cross-references it against the
`API_KEY_ROUTE_SCOPE_REGISTRY`. The spec `docs/openbankproject/OBP_OAUTH_CONSUMERS_TICKETS.md`
(lines 326-369) describes the desired enforcement service and its wiring precisely. This ticket
implements exactly that description.

### Existing scope strings (no new taxonomy)

The scope strings in `API_KEY_ROUTE_SCOPE_REGISTRY` are the authoritative list:
`messager:read`, `messager:write`, `messager:manage`, `filemanager:read`, `filemanager:write`,
`filemanager:share`, `newsfeed:read`, `newsfeed:write`, `newsfeed:moderate`, `tickets:read`,
`tickets:write`, `tickets:admin`, `shopping:catalog:read`, `shopping:cart:write`,
`shopping:checkout:write`, `shopping:orders:read`
(`api_key_route_scope_registry.py:19-67`). OAU-004 introduces no new scope strings.

### Admin-scope denial audit (the pattern for `oauth_scope_denied`)

`app/auth/policy.py:156-165` shows the exact `audit_event` shape for a policy denial:

```python
audit_event(
    "admin_scope_denied",
    user.sub,
    request,
    outcome="error",
    status_code=403,
    required_scope=normalized_scope.value,
    actual_role=role.value,
    actual_admin_profile=profile.to_dict(),
)
```

OAU-004 mirrors this pattern with event name `"oauth_scope_denied"` and appropriate kwargs.

## 3. Data Model

OAU-004 introduces **no new DynamoDB tables and no new DynamoDB rows**. All enforcement
is stateless: it reads `request.state.oauth_scope` (set in memory by OAU-002's auth branch)
and cross-references the in-memory `API_KEY_ROUTE_SCOPE_REGISTRY` dict. No DDB reads occur
during scope enforcement.

The only persistence is the `audit_event(...)` call on denial, which writes to `T.alerts`
exactly as all other audit events do (`app/services/alerts.py`). The alerts table schema
is unchanged.

**Settings additions** (no table changes, just `app/core/settings.py`):

| Setting field | Env var | Type | Default |
|---|---|---|---|
| `oauth_provider_scope_enforcement_enabled` | `OAUTH_PROVIDER_SCOPE_ENFORCEMENT_ENABLED` | `bool` | `false` |

This setting is additive alongside the OAU-001 settings
(`oauth_provider_enabled`, `oauth_consumers_table_name`, etc.) and the OAU-002 settings
(`oauth_access_token_ttl_seconds`, `oauth_refresh_token_ttl_seconds` — note `_seconds`
suffix as defined in `docs/openbankproject/specs/OAU-002.md:504-505`). It gates
enforcement only; with it
off, OAuth tokens still authenticate (OAU-002) but scope is not checked.

The secondary flag `OAUTH_PROVIDER_ENABLED` (master, OAU-001) must also be true for scope
enforcement to be meaningful: if the OAuth routers are not registered, no OAuth tokens are
issued, so the enforcement branch is never reached regardless. The code gates on
`S.oauth_provider_scope_enforcement_enabled` alone — it does not re-check
`S.oauth_provider_enabled` inside the enforcement helper, because the presence of
`request.state.oauth_scope` is already proof that the OAU-002 auth branch ran.

## 4. API / Service Design

### 4.1 New service: `app/services/oauth_scope_enforcement.py`

This module is the single new file introduced by OAU-004. It is stateless (no DDB, no S3).

```python
# app/services/oauth_scope_enforcement.py

from __future__ import annotations
from typing import FrozenSet, List, Optional
from fastapi import HTTPException, Request
from app.core.settings import S
from app.services.api_metering_contract import route_id_from_request
from app.services.api_key_route_scope_registry import (
    resolve_required_scopes_for_route,
    is_route_registered_or_exempt,
)
from app.services.alerts import audit_event


def _parse_oauth_scope(raw: str) -> FrozenSet[str]:
    """Split a space-delimited OAuth scope string into a frozenset."""
    return frozenset(s.strip().lower() for s in (raw or "").split() if s.strip())


def enforce_oauth_scope_for_route(request: Request) -> None:
    """
    Enforce the OAuth token's granted_scope set against the route's required
    scopes from API_KEY_ROUTE_SCOPE_REGISTRY.

    MUST be called only when S.oauth_provider_scope_enforcement_enabled is True.
    Returns immediately (no-op) when the request carries no oauth_scope
    (cookie/Cognito/API-key callers are completely unaffected).
    Raises HTTP 403 when required scopes are not all covered by granted scopes.
    """
    state = getattr(request, "state", None)
    raw_scope: Optional[str] = getattr(state, "oauth_scope", None)
    if not raw_scope:
        # Not an OAuth-bearer request; nothing to enforce.
        return

    route_id: Optional[str] = route_id_from_request(request)
    if not route_id:
        # Probe/excluded path; allow.
        return

    if not is_route_registered_or_exempt(route_id):
        # Route is outside all known scope-enforcement prefixes; allow.
        return

    required: List[str] = resolve_required_scopes_for_route(route_id)
    if not required:
        # Route is in the exemptions dict; allow (mirrors api_key behavior).
        return

    granted: FrozenSet[str] = _parse_oauth_scope(raw_scope)
    missing: List[str] = [s for s in required if s not in granted]

    if not missing:
        return  # All required scopes are present.

    user_sub: str = str(getattr(state, "oauth_user_sub", None) or "")
    client_id: str = str(getattr(state, "oauth_client_id", None) or "")

    audit_event(
        "oauth_scope_denied",
        user_sub,
        request,
        outcome="error",
        status_code=403,
        route_id=route_id,
        required_scopes=required,
        granted_scopes=sorted(granted),
        missing_scopes=missing,
        client_id=client_id,
    )

    raise HTTPException(
        status_code=403,
        detail={
            "code": "oauth_insufficient_scope",
            "message": "OAuth token does not have the required scopes for this route",
            "required_scopes": required,
            "granted_scopes": sorted(granted),
            "missing_scopes": missing,
            "route_id": route_id,
        },
    )
```

**Key design decisions in this function:**

- The `if not raw_scope: return` guard makes it a complete no-op for every non-OAuth request.
  Cookie sessions, Cognito JWTs, and API keys never set `request.state.oauth_scope`, so they
  are never touched.
- `is_route_registered_or_exempt(route_id)` (line 316 of `api_key_route_scope_registry.py`)
  gates the entire check. An unregistered route (one not in either the registry dict or the
  exemptions dict) is allowed — same behavior as the API-key path.
- `resolve_required_scopes_for_route(route_id)` returning `[]` means the route is in the
  exemptions dict; the function returns without raising. This is the correct behavior: exempt
  routes are deliberately not scope-gated.
- `_parse_oauth_scope` lowercases and strips whitespace for defense-in-depth normalization.
  The scope strings in the registry are already lowercase (e.g. `"messager:read"`).
- `oauth_user_sub` and `oauth_client_id` are additional fields OAU-002 must also store on
  `request.state` alongside `oauth_scope`, for use in the audit event. OAU-002's auth branch
  already resolves both; this ticket specifies they be stored.

### 4.2 Wiring into `app/services/api_key_policy_enforcement.py`

`maybe_enforce_api_key_route_policy(request)` (lines 31-261) is wired as a per-router
`Depends` on each of the seven product routers (verified in `app/routers/messaging.py:243`,
`app/routers/filemanager.py:165`, `app/routers/newsfeed.py:78`, `app/routers/tickets.py:25`,
`app/routers/catalog.py:42`, `app/routers/shoppingcart.py:50`,
`app/routers/purchase_history.py:33`). OAU-004 adds the OAuth scope enforcement **inside
`maybe_enforce_api_key_route_policy`** as a trailing call, after all API-key logic completes.
This requires no changes to any router file — the enforcement is centralized in the one
function that already runs for all seven affected routers. The pattern is:

```python
# At the end of maybe_enforce_api_key_route_policy, after all api-key checks:
# New: OAuth scope enforcement (no-op for all non-OAuth requests)
if S.oauth_provider_scope_enforcement_enabled:
    from app.services.oauth_scope_enforcement import enforce_oauth_scope_for_route
    enforce_oauth_scope_for_route(request)
```

The import is a local/deferred import (`from app.services.oauth_scope_enforcement import ...`)
so it is not pulled in when `OAUTH_PROVIDER_SCOPE_ENFORCEMENT_ENABLED=false`. The call is
synchronous (no DDB, no I/O). It runs after all api-key processing completes (including the
`prefer_session` early-return path at line 61) — the two checks are independent and do not
share state. Placing the call at the end of the function (after the `try/except` block) rather
than inside the `try` block ensures that an unexpected error in OAuth enforcement does not
silently swallow an API-key error.

**Important ordering note**: the `prefer_session` early-return at line 61 exits
`maybe_enforce_api_key_route_policy` before reaching the trailing OAuth call. If a request
carries both an API-key header and a Bearer token (dual-credential) with `mode="prefer_session"`,
the API-key check is bypassed AND the OAuth scope check is also bypassed. To ensure OAuth
enforcement runs in that scenario, the deferred call should be placed at the END of the
function body (below the outer `try/except`) rather than inside the `try` block.

### 4.3 OAU-002 `request.state` contract (clarification for implementors)

OAU-002's auth branch in `get_authenticated_user` (`app/auth/deps.py:199`) must store
**three fields** on `request.state` for OAU-004's use:

| Field | Type | Value |
|---|---|---|
| `request.state.oauth_scope` | `str` | Space-delimited scope claim from the JWT, e.g. `"messager:read filemanager:read"` |
| `request.state.oauth_user_sub` | `str` | Resource owner's `sub` (for audit events) |
| `request.state.oauth_client_id` | `str` | `client_id` from the JWT (for audit events) |

**IMPORTANT GAP**: The OAU-002 spec (`docs/openbankproject/specs/OAU-002.md:355-356`)
currently stores only `oauth_scope` and `oauth_client_id` — `oauth_user_sub` is **absent**
from the OAU-002 code snippet. OAU-002's implementor must add:
```python
request.state.oauth_user_sub = owner_sub
```
alongside the two existing state writes. Without this, OAU-004's audit event receives an
empty string for `user_sub`. (OAU-004's `getattr(state, "oauth_user_sub", None)` gracefully
degrades to `""` rather than crashing, so the audit write will succeed but be uncorrelated
with the user.)

These three fields are written only for OAuth-bearer callers and are absent for all other
auth modes. OAU-004 reads them with `getattr(state, field, None)` and treats `None` as
absent (no-op). This interface is the entire coupling between OAU-002 and OAU-004.

### 4.4 No new HTTP endpoints

OAU-004 exposes no new HTTP endpoints. The enforcement is purely middleware-layer logic. The
only observable API change is that some existing endpoints now return 403 with the new
`"oauth_insufficient_scope"` error body when called with an OAuth token missing a required
scope. The 403 shape is new but additive.

### 4.5 Response model for scope-denial 403

The denial response body is a plain JSON dict (not a Pydantic model, matching the existing
`api_key_scope_denied` shape from `api_key_authorization.py:52-63`):

```json
{
    "code": "oauth_insufficient_scope",
    "message": "OAuth token does not have the required scopes for this route",
    "required_scopes": ["messager:write"],
    "granted_scopes": ["messager:read"],
    "missing_scopes": ["messager:write"],
    "route_id": "POST:/messaging/conversations/{conversation_id}/messages"
}
```

This is intentionally transparent to the consumer app: it tells them exactly what scopes they
need to request from the resource owner during the OAU-002 authorization flow. The shape
mirrors `api_key_scope_denied` (`api_key_authorization.py:52-63`) so tooling that already
handles the API-key denial can handle the OAuth denial with minimal adaptation.

## 5. Detailed Behavior & Edge Cases

### 5.1 Normal enforce path

1. Consumer app sends `Authorization: Bearer <oauth_access_token>` on
   `POST /messaging/conversations/{conversation_id}/messages`.
2. `get_authenticated_user` (`deps.py:199`) decodes the HS256 token, confirms
   `token_type=="access"` and `client_id` present, resolves the resource owner's role,
   stores `request.state.oauth_scope = "messager:read"`,
   `request.state.oauth_user_sub = "<owner_sub>"`,
   `request.state.oauth_client_id = "<client_id>"`, returns `AuthenticatedUser`.
3. Middleware calls `enforce_oauth_scope_for_route(request)`.
4. `_parse_oauth_scope("messager:read")` → `frozenset({"messager:read"})`.
5. `route_id_from_request(request)` → `"POST:/messaging/conversations/{conversation_id}/messages"`.
6. `is_route_registered_or_exempt(route_id)` → `True` (it is in the registry).
7. `resolve_required_scopes_for_route(route_id)` → `["messager:write"]`
   (`api_key_route_scope_registry.py:61`).
8. `missing = ["messager:write"]` (not in granted set).
9. `audit_event("oauth_scope_denied", ...)` fires.
10. 403 raised with `"oauth_insufficient_scope"` body.

### 5.2 Token with sufficient scope

Same request but token `scope = "messager:read messager:write"`:
- `granted = frozenset({"messager:read", "messager:write"})`.
- `missing = []`.
- Function returns normally. The router handler executes.

### 5.3 Exempt route

`GET /feed/for-you` is in `API_KEY_ROUTE_EXEMPTIONS` (`api_key_route_scope_registry.py:71`).
`is_route_registered_or_exempt(route_id)` → `True`; `resolve_required_scopes_for_route` →
`[]`; function returns. Any OAuth token can call it.

### 5.4 Unregistered route

A route not in either the registry or the exemptions dict (e.g. a brand-new endpoint not yet
catalogued): `is_route_registered_or_exempt` → `False`; function returns. Unregistered
routes are allowed, consistent with the API-key policy (no "fail closed" on unknown routes).

### 5.5 Non-OAuth caller (cookie session)

`request.state.oauth_scope` is `None`/absent. First guard `if not raw_scope: return` fires
immediately. Zero cost, zero change in behavior.

### 5.6 Feature flag off

`S.oauth_provider_scope_enforcement_enabled = False` (the default). The calling site does not
call `enforce_oauth_scope_for_route` at all. OAuth tokens still authenticate via OAU-002's
auth branch and can call any endpoint (identity without scope enforcement). This is the
safe rollout mode: enable identity first, add enforcement later.

### 5.7 Disabled consumer (OAU-005)

OAU-005's `set_consumer_enabled(owner_sub, client_id, enabled=False)` flips `enabled=False`
on the consumer META row. OAU-002's auth branch re-checks `get_consumer(client_id).enabled`
before accepting the token — the token is rejected at auth with 401 `oauth_consumer_disabled`
before OAU-004's scope check is ever reached. OAU-004 has no dependency on the `enabled`
flag; OAU-005 handles that path.

### 5.8 Token expiry

An expired OAuth token is rejected at OAU-002's auth branch with 401 (`jwt.ExpiredSignatureError`)
before the scope check runs. OAU-004 never sees an expired token.

### 5.9 Scope comparison is exact and case-insensitive

`_parse_oauth_scope` lowercases all scope strings. The registry keys are already lowercase.
`"Messager:Read"` in a token (malformed but defensive) would be normalized to
`"messager:read"` and match correctly.

### 5.10 Multiple required scopes (AND semantics)

If a route ever requires `["foo:read", "foo:write"]` (both), `missing` is the list of
all absent required scopes. The 403 detail includes all missing scopes at once rather than
failing on the first. This matches the API-key path behavior (`api_key_authorization.py:51`).

### 5.11 `openid`, `profile`, `email` OIDC scopes

These OIDC scopes (from OAU-003) are never registered in `API_KEY_ROUTE_SCOPE_REGISTRY`.
`resolve_required_scopes_for_route` returns `[]` for OIDC-only routes (e.g. `/userinfo`),
and the check is a no-op. OIDC scopes and API-domain scopes live in orthogonal namespaces.

### 5.12 Audit-only / observe mode (no direct support, use flag)

There is no separate "audit only" mode for OAU-004's scope check. The flag controls
enforcement entirely. If a team wants to observe denials without actually blocking, they can
set `OAUTH_PROVIDER_SCOPE_ENFORCEMENT_ENABLED=1` in a staging/shadow environment and watch
the `oauth_scope_denied` audit stream before enabling in production.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 (dev/prod parity)

OAU-004 contains **no `if S.dev_mode:` branch**. The enforcement function reads
`request.state.oauth_scope` (set by OAU-002's auth branch), cross-references the in-memory
registry dict, and calls `audit_event` (which writes to `T.alerts` — DynamoDB Local in dev,
real DynamoDB in prod). The code path is identical in both environments.

There is no mock path, no dev shortcut, and no conditional based on `S.dev_mode`. If
`OAUTH_PROVIDER_SCOPE_ENFORCEMENT_ENABLED=1` and `OAUTH_PROVIDER_ENABLED=1` are both set in
`.env.local`, the enforcement runs exactly as it would in production.

### Idempotency

`enforce_oauth_scope_for_route` is a pure read — it reads in-memory state and either raises
or returns. It writes exactly one audit event on denial and raises immediately, so a retry of
the same denied request produces the same result (another audit event + 403). There is no
counter increment, no DDB conditional, and no state mutation. The function is trivially
idempotent.

### Security

**Scope downgrade via token manipulation is not possible.** The OAuth access token is an
HS256 JWT signed with `S.ui_access_token_secret`. Tampering with the `scope` claim
invalidates the signature, and OAU-002's auth branch rejects it with 401 before
`enforce_oauth_scope_for_route` is ever called.

**Scope inflation via allowlisted routes is not a concern.** Unregistered routes are allowed
through, but so are they for API-key callers. The exemptions list is curated and checked in
by a developer action (adding an entry to `API_KEY_ROUTE_EXEMPTIONS`), not computed at runtime.

**Scope string injection is not possible.** `_parse_oauth_scope` only splits on whitespace
and lowercases. The granted-scope frozenset is compared against the registry's `required_scopes`
list by exact string equality. There is no wildcard expansion, no glob matching, and no
scope-hierarchy logic — each scope string is atomic. This matches the API-key behavior.

**Fail-open vs fail-closed.** When `S.oauth_provider_scope_enforcement_enabled = False`
(default), enforcement is off. This is intentional: the flag must be explicitly enabled, and
scope enforcement is never silently skipped in production once enabled. The function either
returns normally (allowed) or raises 403 (denied). It never swallows exceptions silently.

**No money movement.** OAU-004 is a pure access-control gate. It carries no billing logic,
no ledger writes, and no wallet mutations. The MONEY-SAFETY checklist (settle_or_reverse_ledger,
new_ledger_entry, fraud-gate, SCA) is not applicable to this ticket.

### Interaction with API-key dual-credential mode

`maybe_enforce_api_key_route_policy` handles requests that carry both an API-key header and a
Bearer token via `S.api_key_dual_credential_mode` (`api_key_policy_enforcement.py:45-84`).
When `mode="prefer_session"` and a Bearer token is present, the API-key check returns early.
In that case, the OAuth scope enforcement runs (since `request.state.oauth_scope` may have
been set by OAU-002's auth branch). The ordering is correct: API-key check first, OAuth
scope check second.

## 8. Backward Compatibility & Migration

### Zero-change for existing callers

Cookie-session, Cognito-bearer, and API-key callers are completely unaffected:

- They never set `request.state.oauth_scope`.
- The enforcement function's first guard (`if not raw_scope: return`) exits immediately.
- No new dependency, no new middleware, no change to routing.

### Default-OFF flag

`OAUTH_PROVIDER_SCOPE_ENFORCEMENT_ENABLED` defaults to `"0"` (false). Deploying this ticket
without setting the flag changes nothing — the calling site's `if S.oauth_provider_scope_enforcement_enabled`
guard never calls `enforce_oauth_scope_for_route`. The deployed code is inert.

### Migration path

1. Deploy OAU-001 (consumer registry + table). No traffic impact.
2. Deploy OAU-002 (auth flow). OAuth tokens are issued but scope is not enforced.
3. Deploy OAU-003 (OIDC, optional). No scope-enforcement impact.
4. Deploy OAU-004 (this ticket). Scope enforcement is **off by default**.
5. Deploy OAU-005 (enable/disable lifecycle). No scope-enforcement impact.
6. When ready to enforce: set `OAUTH_PROVIDER_SCOPE_ENFORCEMENT_ENABLED=1` and restart.
   From this point, OAuth tokens missing required scopes receive 403 instead of 200.

There is no backfill, no DDB migration, and no consumer notification step. The transition is
a single flag flip. Because the flag defaults off, operators can test enforcement in staging
before enabling it in production.

### Rolling back

Flip `OAUTH_PROVIDER_SCOPE_ENFORCEMENT_ENABLED` back to `"0"` and restart. Enforcement stops
immediately. No DDB cleanup required.

## 10. Open Questions / Assumptions

**Q1: Scope expansion / aliasing.** The API-key path expands capabilities via
`expand_api_key_capabilities` (`app/services/api_key_capabilities.py`). Does OAU-004 need
to apply the same expansion to OAuth scope strings?

**Assumption**: No. API-key capabilities are a distinct concept (structured capability names
that expand to multiple scopes). OAuth scopes are atomic strings registered directly in
`API_KEY_ROUTE_SCOPE_REGISTRY`. The `scope` claim in an OAuth token already contains the
final expanded scope strings (e.g. `"messager:read messager:write"`), not capability names.
There is nothing to expand. If a future requirement maps capability names to OAuth scopes,
that mapping belongs in the consumer-registration flow (OAU-001), not in OAU-004's
enforcement path.

**Q2: Should `enforce_oauth_scope_for_route` be a FastAPI `Depends` or a direct function call?**

**CORRECTED Assumption**: The actual API-key enforcement is NOT a central Starlette
middleware — it is a per-router `Depends` on each of the seven product routers (verified in
`app/routers/messaging.py:243`, `app/routers/filemanager.py:165`, etc.). Therefore the two
viable implementation approaches are: (a) add `Depends(lambda req: enforce_oauth_scope_for_route(req))` alongside `maybe_enforce_api_key_route_policy` in each router's `dependencies=` list — clean and parallel; or (b) add the deferred call INSIDE `maybe_enforce_api_key_route_policy` itself after authentication, so it runs at the same call site for all seven routers without touching router files. Approach (b) is preferred because it keeps all scope-enforcement wiring in `api_key_policy_enforcement.py` and avoids touching seven routers. The original concern about "having to add it to every router" applies equally to both — either way the seven routers are affected. The difference is where the logic lives.

**Q3: Should the enforcement also check that `client_id` in the token matches an `enabled`
consumer (re-reading DDB on every request)?**

**Assumption**: No. Checking `enabled` on every request would add a DDB read per OAuth call,
introducing latency and a new DDB dependency for an otherwise stateless function. OAU-005
handles consumer disable by causing OAU-002's auth branch to reject tokens from disabled
consumers at the decode site (the auth branch re-checks `get_consumer(client_id).enabled`).
OAU-004 can assume that if `request.state.oauth_scope` is set, the token already passed the
OAU-002 enabled-check.

**Q4: What happens if `API_KEY_ROUTE_SCOPE_REGISTRY` is modified at runtime?**

**Assumption**: The registry is a module-level dict defined at import time
(`api_key_route_scope_registry.py:17-67`). It does not change at runtime. Changes to it
require a code deployment. This is consistent with all current uses of the registry.

**Q5: Should there be a per-consumer scope-override mechanism (e.g. some consumers exempt
from scope enforcement)?**

**Assumption**: No, not in OAU-004. The registry is the single source of truth for
all callers. Per-consumer overrides would introduce a second source of scope policy and are
out of scope for this ticket.
