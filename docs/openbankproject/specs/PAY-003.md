# PAY-003 — Direct-debit mandates — pull authorization, cap enforcement + execution hook

**Ticket type**: Backend (entity + recurring pull executor)
**Priority**: P1
**Estimate**: 3 days
**Status**: Unimplemented
**Dependencies**: PAY-001 (counterparty entity), TXR-001 / TXR-004 (COUNTERPARTY transaction request + execution), PAY-004 (FX conversion — soft, only if non-USD counterparties used)

---

## 1. Summary & Goal

PAY-003 introduces the **direct-debit mandate**: a user-owned authorization for a stored counterparty to *pull* money from the user's wallet up to an explicit per-cadence cap. This is the inverse direction of a standing order — the payee initiates the pull on a schedule, but the payer (our user) has pre-authorized it and retains a hard server-side cap and an unconditional `revoke` kill-switch.

The goal is strictly additive: define the DynamoDB entity, the `app/services/direct_debit_mandates.py` service layer (CRUD + cap enforcement + pull execution), and the `app/routers/direct_debit_mandates.py` REST surface. Scheduler integration wires a `"direct_debit_tick"` executor into the existing `unified_scheduler` loop (no new asyncio loop or startup task). Every outbound pull is realized as a `type=COUNTERPARTY` Transaction Request; the mandate service **never calls `apply_wallet_delta`, `new_ledger_entry`, or `settle_or_reverse_ledger` directly** — TXR owns the single money-out path.

Everything is gated behind the shared flag `PAYMENTS_COUNTERPARTIES_ENABLED` (default `false`, introduced by PAY-001). With the flag off all new routes return 404 and the scheduler step is skipped.

## 3. Data Model

### New DynamoDB table: `direct_debit_mandates`

**Primary key**: `user_sub` (S) hash + `mandate_id` (S) sort.

Ownership is encoded in the composite key: `Key={"user_sub": user_sub, "mandate_id": mandate_id}` is a direct ownership check — a foreign `mandate_id` returns nothing.

**GSI `ByDue`**:

| Attribute | Type | Notes |
|---|---|---|
| `GSI_DUE_PK` | S | Literal `"DUE"` when active; removed (REMOVE) on revoke/complete/pause |
| `next_run_at` | N | Next scheduled pull as Unix seconds |

**`attr_types={"next_run_at": "N"}` is mandatory.** The CLAUDE.md numeric-GSI gotcha applies: without this declaration DynamoDB Local stores `next_run_at` as String, causing `ValidationException` when queried with an integer `ExclusiveStartKey`. Pattern is established at `scripts/local-ddb-init.py:1327` for `scheduled_actions` (`attr_types={"GSI_DUE_SK": "N"}`).

Here `next_run_at` is both the DDB item attribute and the GSI sort key (unlike `scheduled_actions` which uses a separate `GSI_DUE_SK` alias). This simplifies the item — one field serves both purposes.

## 5. Detailed Behavior & Edge Cases

### `create_mandate`

1. Verify the session owner has an active counterparty with `counterparty_id` via `counterparties.get_counterparty(user_sub, counterparty_id)` (PAY-001). Foreign or missing → `400 counterparty_not_found`.
2. Validate `start_at >= now_ts()`. Reject past start times.
3. Validate `end_at > start_at` when provided.
4. Compute `next_run_at = _next_occurrence(cadence, start_at)`.
5. Build the item with `status="active"`, `GSI_DUE_PK="DUE"`, `pulled_this_window_cents=0`, `window_started_at=_window_start_for(cadence, start_at)`, `runs_count=0`.
6. `put_item` to `T.direct_debit_mandates`.
7. `audit_event("mandate.created", user_sub, mandate_id=mandate_id, counterparty_id=counterparty_id, max_amount_cents=max_amount_cents, cadence=cadence)`.
8. Return `MandateOut`.

### `execute_mandate_pull` (the core logic — money-safety critical)

This function is the only one that may cause money to leave the user's wallet via TXR. All paths are explicit — no silent partial pulls.

**Step 1 — Load and validate mandate state.**
Read `Key={"user_sub": user_sub, "mandate_id": mandate_id}`. Status must be `"active"`; any other status → `MandateNotActive` exception (logged, no TXR request created).

**Step 2 — Window rollover.**
If `now_ts() >= _window_start_for(cadence, now) + cadence_window_seconds` (i.e., the current cadence window has advanced past `window_started_at`), reset: `pulled_this_window_cents = 0`, `window_started_at = _window_start_for(cadence, now)`. This reset must be persisted **atomically with the cap check** in Step 3 (use a single conditional `update_item`).

**Step 3 — Cap enforcement (money-safety constraint #4).**
Two checks, either alone is sufficient to block the pull:
- **Per-pull cap**: `pull_amount_cents > max_amount_cents` → skip.
- **Cumulative window cap**: `pulled_this_window_cents + pull_amount_cents > max_amount_cents` → skip.

On skip: write `status` annotation `exceeded` on the occurrence (as a log / audit record), fire `audit_event("mandate.skipped", user_sub, mandate_id=mandate_id, reason="cap_exceeded", pull_amount_cents=pull_amount_cents, pulled_this_window_cents=pulled_this_window_cents)`. Do **not** create a TXR request. Do **not** advance `next_run_at` (the mandate remains due; the scheduler will not retry within the same tick, but the next tick will attempt again — the cadence advance should happen regardless of cap skip to prevent spinning). **Design decision**: advance `next_run_at` even on a skipped pull (mark the occurrence as processed, avoid starvation), but write `reason="cap_exceeded"` to the audit record. If the intent is that a skipped occurrence should retry (e.g., for smaller amounts), this is an open question — see §10.

**Step 4 — FX conversion (if non-USD).**
If `mandate.currency != "usd"`, call `fx_rates.convert(pull_amount_cents, mandate.currency, "usd")` (PAY-004). If the FX rate is missing (`LookupError("fx_rate_missing")`), mark the occurrence `skipped` with `reason="fx_rate_missing"` and advance `next_run_at` (same skip path). The `fx_rate` and `source_currency` are stamped onto the TXR `meta` dict; the ledger row stays single-currency `usd` (money-safety constraint #5 from the file header).

**Step 5 — Idempotency key.**
Compute `idempotency_key = f"{mandate_id}#{next_run_at}"` — deterministic per-occurrence key (money-safety constraint #2). A scheduler retry for the same `next_run_at` value produces the same key → TXR-001's `create_request` collapses the duplicate and returns the existing `TxnRequestOut` without a second debit.

**Step 6 — Emit TXR COUNTERPARTY request.**
```python
from app.services import txn_requests  # TXR-001/004
req = TxnRequestCreateIn(
    type="COUNTERPARTY",
    amount_cents=usd_amount_cents,  # after FX conversion
    currency="usd",
    target={"counterparty_ref": counterparty_id},
    reason="direct_debit",
    idempotency_key=idempotency_key,
    meta={
        "mandate_id": mandate_id,
        "original_currency": mandate.currency,
        "original_amount_cents": pull_amount_cents,
        "fx_rate": fx_rate,           # None if usd
        "window_started_at": window_started_at,
    },
)
request = txn_requests.create_request(user_sub, req)
# Server-initiated run: immediately execute (TXR-004).
# CORRECTION: execute_request is a SYNC function (def, not async); it must be
# dispatched via asyncio.to_thread. It also requires a FastAPI Request object
# as its third argument (used by _fraud_gate). The mandate scheduler operates
# outside an HTTP request context, so `req` must be None or a sentinel object
# that _fraud_gate tolerates — verify with TXR-004 implementation.
#
# If SCA is required (amount >= S.txn_request_sca_threshold_cents),
# create_request (via TXR-003 post-create hook) returns status="PENDING".
# Calling execute_request on a PENDING request where SCA is NOT yet complete
# raises HTTPException(403, {"code": "sca_incomplete"}) — it does NOT return
# a PENDING status. PAY-003's execute_mandate_pull must catch HTTPException(403)
# with code="sca_incomplete", record the sca_challenge_id from the request item
# in the audit record, and NOT advance next_run_at.
result = await asyncio.to_thread(txn_requests.execute_request, user_sub, request.request_id, None)
```

PAY-003 **never** calls `apply_wallet_delta`, `new_ledger_entry`, or `settle_or_reverse_ledger`. All of those are called inside TXR's execution path.

**Step 7 — Conditional `next_run_at` advance (money-safety constraint #3).**
Use a conditional `update_item` asserting `next_run_at = :old_next_run_at`:
```python
T.direct_debit_mandates.update_item(
    Key={"user_sub": user_sub, "mandate_id": mandate_id},
    UpdateExpression=(
        "SET next_run_at = :new_nra, last_run_at = :now, "
        "runs_count = runs_count + :one, "
        "pulled_this_window_cents = pulled_this_window_cents + :amt, "
        "updated_at = :now"
    ),
    ConditionExpression="next_run_at = :old_nra",
    ExpressionAttributeValues={
        ":new_nra": new_next_run_at,
        ":old_nra": old_next_run_at,
        ":now": now_ts(),
        ":one": 1,
        ":amt": pull_amount_cents,
    },
)
```
`ConditionalCheckFailedException` → the same occurrence was already advanced by a concurrent tick; this is a no-op (the TXR idempotency key has already collapsed the second TXR create into a no-op too).

If `end_at` is set and `new_next_run_at > end_at`: set `status="completed"` and `REMOVE GSI_DUE_PK, next_run_at` from the item in the same `update_item`.

**Step 8 — Audit.**
`audit_event("mandate.debited", user_sub, mandate_id=mandate_id, request_id=request.request_id, amount_cents=usd_amount_cents, runs_count=new_runs_count)`.

### `revoke_mandate`

Sets `status="revoked"` and removes `GSI_DUE_PK` + `next_run_at` from the item via `REMOVE GSI_DUE_PK, next_run_at`. This removes the mandate from the `ByDue` GSI so the scheduler never selects it again. Revoke is **irreversible** — no `resume` path from `revoked`. `audit_event("mandate.revoked", user_sub, mandate_id=mandate_id)`.

The counterparty's `delete_counterparty` (PAY-001) must check for active mandates referencing it before allowing deletion; until that integration is built, `delete_counterparty` should refuse deletion if any `active` mandate references the counterparty (a Query on PK=`user_sub` filtering `counterparty_id = :cpid AND status = :active`).

### SCA behavior on server-initiated pulls

**CORRECTION — SCA behavior (verified against TXR-004 spec):**

The SCA `PENDING` state is set by TXR-003's post-create hook inside `create_request`, not by `execute_request`. The correct flow is:

1. `create_request(user_sub, req)` — if `amount_cents >= S.txn_request_sca_threshold_cents`, TXR-003 transitions the request to `PENDING` and mints an SCA challenge. The returned `TxnRequestOut` has `status="PENDING"` and a non-null `sca_challenge_id`.
2. Calling `execute_request` on a `PENDING` request where SCA is **not yet complete** raises `HTTPException(403, {"code": "sca_incomplete"})` — it does **not** return a PENDING status object. (Source: TXR-004 §4.2 Step 2.)
3. `execute_mandate_pull` must catch `HTTPException(403)` (checking `detail.get("code") == "sca_incomplete"`), extract `sca_challenge_id` from `request.sca_challenge_id`, write `audit_event("mandate.sca_pending", ...)`, and **not advance `next_run_at`** — leaving the mandate due so the scheduler retries.
4. On the next tick the idempotency key `{mandate_id}#{next_run_at}` collapses `create_request` to the existing PENDING item (no second challenge minted). `execute_request` raises 403 again until the user completes SCA out-of-band.
5. Once the user completes SCA (TXR-002/TXR-003 flow), the challenge is marked done. On the next scheduler tick, `execute_request` passes the SCA gate, executes the money movement, and returns `COMPLETED`. The `next_run_at` conditional advance then proceeds normally.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 — one code path

There is no `if S.dev_mode:` branch in `direct_debit_mandates.py`. DynamoDB Local (port 8001, `DDB_ENDPOINT_URL=http://localhost:8001`) and real DynamoDB both use the same boto3 resource. moto intercepts S3 calls in-process; DDB Local is a real DDB-compatible process. The TXR `execute_request` path uses the existing `billing_shared.apply_wallet_delta` whose only mock/real difference is the DDB endpoint — no business-logic branch. KMS decrypt for any stored credential (counterparty routing at-rest encryption, if added later) goes through `app/core/crypto.kms_decrypt` which already handles dev mock KMS vs prod transparently.

### Idempotency

- **Per-occurrence**: `idempotency_key = f"{mandate_id}#{next_run_at}"` — TXR-001's `create_request` collapses duplicate creates for the same key. Two concurrent scheduler ticks for the same occurrence produce at most one TXR request and at most one wallet debit.
- **`next_run_at` advance**: conditional `update_item` with `ConditionExpression="next_run_at = :old_nra"` — exactly one concurrent winner advances; the loser gets `ConditionalCheckFailedException` and is a no-op.
- **Revoke**: `update_item` with `ConditionExpression="#status = :active"` — prevents double-revoke from concurrent requests.

### Money-safety

All five binding constraints from the file header apply:

1. PAY-003 never calls `apply_wallet_delta` / `new_ledger_entry` / `settle_or_reverse_ledger` directly; TXR is the single money-out path.
2. Idempotency key collapses duplicate `create_request` calls — at most one debit per occurrence.
3. Conditional `update_item` on `next_run_at` — at most one advance per occurrence under concurrency.
4. **Cap enforcement server-side**: per-pull check `pull_amount_cents > max_amount_cents` AND cumulative window check `pulled_this_window_cents + pull_amount_cents > max_amount_cents` — over-cap yields no TXR request and no debit. The cap check and `pulled_this_window_cents` increment happen in the same atomic conditional `update_item` (using `ConditionExpression="pulled_this_window_cents + :amt <= :max_amt"`), preventing a race where two concurrent pulls both read the counter as zero and both succeed under a single-unit cap.
5. FX conversion produces a `usd`-denominated `amount_cents` stamped on TXR `meta`; no non-USD ledger rows are written.

### Security

- **Ownership**: every read/write uses `Key={"user_sub": user_sub, "mandate_id": mandate_id}` — a foreign `mandate_id` from another user returns nothing from `get_item` without a secondary ownership check.
- **Revoke is immediate**: removing `GSI_DUE_PK` + `next_run_at` from the item prevents future scheduler selections in O(1) time — no lag.
- **SCA inherited via TXR**: high-value pulls (above `S.txn_request_sca_threshold_cents`) automatically go `PENDING` in TXR-002/TXR-003; the mandate does not need its own SCA implementation.
- **Audit trail**: every state transition emits `audit_event(...)` to `T.alerts` — creation, each successful pull, each skipped pull, revocation.

## 10. Open Questions / Assumptions

1. **Skipped-occurrence advance policy**: The spec above advances `next_run_at` on a cap-skipped occurrence (to prevent the scheduler spinning on the same `next_run_at`). An alternative is to leave `next_run_at` unchanged so the pull is retried on the next scheduler tick with the same occurrence timestamp. The latter risks infinite spin if the cap is structurally too low; the former means a skipped pull is silently skipped for the whole cadence period. **Decision needed before implementation.** Current spec: advance on skip.

2. **Partially consumed window cap**: the spec uses `max_amount_cents` as both the per-pull limit and the per-window cumulative cap (i.e., only one full-size pull per window). If the intended behavior is "N smaller pulls up to a cumulative `max_amount_cents` per window", the cap model is already correct, but `pull_amount_cents` would need to vary per pull. For the scheduler-driven path `pull_amount_cents` always equals `max_amount_cents` (single full pull), which trivially makes the window cap equivalent to the per-pull cap. If partial pulls from a third-party initiator are needed, a separate API path is required — this is deferred.

3. **Mandate-initiated vs. payer-initiated pull**: the current design is payer-initiated (the payer sets up the mandate, the scheduler on the payer's platform executes it). A true pull-payment model would have the payee initiate a pull API call. This second flow (payee-API-initiated pull, not scheduler-driven) is out of scope for PAY-003 and would require a separate consumer-auth path (OAU series). Assumption: scheduler-driven payer-side execution only for now.

4. **Non-USD mandate currency**: PAY-004 (FX) is listed as a soft dependency. Until PAY-004 is implemented, attempting to create a mandate with `currency != "usd"` should return `400 fx_not_supported` (a guard in `create_mandate`). The FX path in `execute_mandate_pull` is wired but guarded behind `PAY-004`'s `fx_rates.convert` being present.

5. **Counterparty deletion guard**: PAY-001's `delete_counterparty` is specified to refuse deletion if referenced by an active mandate. This is noted in PAY-001 as a check added in PAY-003. PAY-003 should add the cross-table lookup (`Query direct_debit_mandates PK=user_sub, filter counterparty_id=X AND status=active`) to the counterparty service when the mandate table is available.
