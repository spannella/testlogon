# CUS-002 — User-customer link + bidirectional customer messages thread

**Ticket type**: Backend — link model + threaded messaging service  
**Priority**: P1  
**Estimate**: 3 days  
**Flag**: `CUSTOMER_ENTITY_ENABLED` (default `false`, shared with CUS-001)

---

## 1. Summary & Goal

This ticket adds two tightly related capabilities on top of the Customer entity introduced by
CUS-001:

1. **User-to-customer link** — a bidirectional pointer between a platform `user_sub` and a
   `customer_id`, so a logged-in user can resolve their own customer record in a single
   `get_item` call, and admin staff can enumerate all users linked to a given customer.

2. **Bidirectional customer message thread** — a durable, chronologically ordered thread of
   messages between staff (ADMIN/ROOT role) and the linked customer (the user whose `user_sub`
   is on the link). A staff member posts as `STAFF`; the linked user posts as `CUSTOMER`. Each
   staff post fires an in-app alert and email notification to the linked user via the existing
   `write_alert` / `send_alert_email` stack. Customer replies are visible to any ADMIN/ROOT
   querying the thread.

The KYC case's "request more info" message path
(`app/routers/kyc_cases.py:710-731, _ensure_request_info_ticket_message`) is a strictly
**one-way** admin-to-user notification; it carries a ticket message, not a first-class thread.
This ticket is the first place a user can reply to a staff message through a persistent, typed
channel.

No money moves in this ticket. The billing ledger, wallet, fraud gate, and SCA stack are not
touched here; they become relevant in CUS-003 (card charge interactions) and any
TXN-REQUEST/SCA tickets.

## 2. Context & Current State

### 2.1 User identity is case-scoped today

The only stable per-user identity anchor is the Cognito `user_sub`. KYC identity fields
(`legal_name`, `date_of_birth`, etc.) live exclusively inside a KYC case created by
`KycCaseStore.create_case` (`app/services/kyc_cases.py:120-172`). The `OWNER#{user_sub}` GSI
projection (key function `_owner_pk` at `app/services/kyc_cases.py:67`) allows listing a
user's cases, but a case is stateful (lifecycle `draft → submitted → approved`) and is not a
reusable customer object that cards, message threads, or financial products can reference.
CUS-001 introduces `app/services/customers.py` with `CustomerStore` to fill this gap; CUS-002
wires a user `user_sub` to that new customer entity.

### 2.2 One-way KYC "request info" message exists already

`request_more_info` in `app/services/kyc_cases.py` (invoked from
`app/routers/kyc_cases.py:1588`, which calls helper `_ensure_request_info_ticket_message` at
`app/routers/kyc_cases.py:720`) adds a single message to the case's linked support ticket
via `_ensure_request_info_ticket_message`. It is admin-initiated, idempotent (deduplicated by
`[kyc_request_info:{hash}]` marker), and the customer has no dedicated reply path in the KYC
layer. The KYC webhook event `kyc.case.needs_info` (registered in
`app/services/webhook_service.py:150`) notifies externally but there is no in-system
thread the customer can reply into.

### 2.3 Alert + notification infrastructure (HAVE)

`write_alert` (`app/services/alerts.py:356`) writes an alert row to `T.alerts` (PK
`user_sub`, SK `alert_id`) and fires an SSE event. It does **not** automatically send email —
email must be called separately via `send_alert_email`. `send_alert_email`
(`app/services/alerts.py:459`) is dev-mode-aware (logs to file in dev; sends via SES in prod,
SECOPS-007 parity). Both are already used by `KycCaseStore`'s emit helpers — e.g.,
`_emit_kyc_event_safe` (`app/services/kyc_cases.py:20-29`) — and the messaging router's tip
and lock notifications. CUS-002 reuses both without any modification.

### 2.4 Pagination cursor (HAVE)

`encode_cursor` / `decode_cursor` (`app/core/cursor.py:94` / `app/core/cursor.py:103`) produce
HMAC-signed, versioned opaque cursors from a DynamoDB `LastEvaluatedKey`. The cursor handles
`Decimal` values in numeric GSI keys via `_json_default` (`app/core/cursor.py:12`). Message
list pagination uses these helpers directly.

### 2.5 Optimistic concurrency pattern to copy (HAVE)

`KycCaseStore.update_case_status` (`app/services/kyc_cases.py:177-234`) is the canonical
optimistic-concurrency pattern: read `version`, compare to `expected_version`, issue a
conditional `update_item` with `ConditionExpression="version = :expected_version"`, catch
`ConditionalCheckFailedException`, raise a domain-specific `*ConflictError`. CUS-002 does
not need this pattern for message rows (which are append-only), but the link operation applies
a conditional `put_item` (`attribute_not_exists(pk)`) to enforce single-link semantics.

### 2.6 Auth dependency (HAVE)

`require_ui_session` (`app/services/sessions.py:330`) returns
`{"user_sub", "session_id", "role", "ip", "tenant_id"}` for cookie-session callers; note
`role` is a **string value** (e.g. `"admin"`) not a `Role` enum object, and `admin_profile`
is **not** in the returned dict (use `Depends(get_authenticated_user)` from
`app/auth/deps.py:199` for the `AuthenticatedUser` typed object with `admin_profile`).

For admin/root role enforcement the customer router uses `require_admin_or_root` from
`app/auth/policy.py:67` — a shared FastAPI dependency that raises `HTTPException(403,
{"code":"role_required",...})`. Do **not** import or call the private
`_require_admin_or_root` from `app/routers/kyc_cases.py:2212`, which is internal to the
KYC router and raises a KYC-specific error envelope via `_raise_kyc_error`; it also
expects an `AuthenticatedUser` object, not the `ctx` dict. CUS-002 uses the shared dep.

### 2.7 KYC GSI for kyc_status back-fill

The `OWNER#{user_sub}` GSI on `T.kyc_cases` (`_owner_pk` helper at
`app/services/kyc_cases.py:67`) + `gsi_owner_sk = UPDATED#{ts:013d}#KYC#{case_id}` sort key
(descending order) lets `link_user` read the user's most recent KYC case by querying
`gsi_owner_pk = OWNER#{user_sub}`, `ScanIndexForward=False`, `Limit=1` — a single cheap query,
no scan. `kyc_status` from that case is stamped onto the customer META row.

## 3. Data Model

All rows land on the **existing `customers` table** introduced by CUS-001 (single-table
design). No new DynamoDB table is needed for this ticket.

### 3.1 Row types added in CUS-002

#### Link row (forward pointer — customer owns the link)

```
PK  = CUST#{customer_id}
SK  = LINK#USER#{user_sub}
```

Fields: `customer_id`, `user_sub`, `linked_at` (int, `now_ts()`), `linked_by` (actor
`user_sub`), `entity_type = "customer_link"`.

At most one `LINK#USER#{user_sub}` SK per `customer_id`. A `put_item` with
`ConditionExpression="attribute_not_exists(pk) OR attribute_not_exists(sk)"` — or simply
`attribute_not_exists(sk)` since PK must already exist (META row is present) — makes a
double-link a no-op idempotent rather than an error (the second call sees the existing row
and suppresses the write without raising).

#### Reverse pointer (user → customer lookup)

```
PK  = CUSTLINK#{user_sub}
SK  = META
```

Fields: `user_sub`, `customer_id`, `linked_at`, `entity_type = "customer_reverse_link"`.

Written atomically in the same DynamoDB `TransactWriteItems` call as the forward link row
(two `Put` operations in a single transaction — guaranteed all-or-nothing). This ensures
`resolve_customer_for_user` never reads a dangling pointer.

#### Message row

```
PK  = CUST#{customer_id}
SK  = MSG#{ts:013d}#{message_id}
```

Fields: `customer_id`, `message_id` (format `cmsg_{uuid4().hex[:12]}`), `author_sub`,
`author_role` (`"STAFF"` | `"CUSTOMER"`), `body` (str, max 10 000 chars), `created_at` (int).

The SK format `MSG#{ts:013d}#{message_id}` gives natural chronological ordering when DynamoDB
queries with `ScanIndexForward=True` (oldest-first) or `ScanIndexForward=False`
(newest-first). `now_ts()` (`app/core/time.py`) returns **seconds** (a 10-digit integer in
2026), so `{ts:013d}` zero-pads it to 13 digits (e.g. `"0001751745600"`) — this is
second-granularity ordering, not millisecond. The zero-padding ensures correct lexicographic
sort. The random `{message_id}` suffix prevents collisions on simultaneous writes within the
same second. There are no update or delete operations on message rows — they are append-only.

### 3.2 GSI additions (none required)

No new GSI is needed. All access patterns for this ticket are:

| Pattern | DynamoDB operation |
|---|---|
| Resolve customer for logged-in user | `get_item(PK=CUSTLINK#{sub}, SK=META)` |
| List all user-links for a customer | `query(PK=CUST#{id}, begins_with(SK, "LINK#USER#"))` |
| Post message | `put_item(PK=CUST#{id}, SK=MSG#{ts}#{id})` |
| List messages (oldest-first + cursor) | `query(PK=CUST#{id}, begins_with(SK, "MSG#"), ScanIndexForward=True)` |

The `begins_with` KeyConditionExpression is valid on the SK of a composite-key table (the
`customers` table has PK `pk` and SK `sk`).

### 3.3 `attr_types` note

No new numeric GSI sort keys are introduced in CUS-002. The only new numeric field on message
rows is `created_at`, which is stored as a regular attribute, not a GSI sort key — so no
`attr_types` declaration is needed in `scripts/local-ddb-init.py` for this ticket. The
`customers` table `TableDef` with its existing GSIs (declared in CUS-001) is unchanged.

## 4. API / Service Design

### 4.1 Service: `app/services/customers.py` (extend CUS-001's `CustomerStore`)

The following methods are added to the `CustomerStore` dataclass:

```python
@dataclass
class CustomerStore:
    _table: Any = field(default=T.customers)

    # --- CUS-002 additions ---

    def link_user(
        self,
        customer_id: str,
        user_sub: str,
        actor_sub: str,
    ) -> dict[str, Any]:
        """
        Write LINK#USER#{user_sub} on the customer PK + CUSTLINK#{user_sub}/META
        reverse pointer atomically via TransactWriteItems.
        Idempotent: if the link already exists, returns the existing rows without error.
        Back-fills customer.kyc_status from the user's latest KYC case.
        """

    def get_link(self, customer_id: str, user_sub: str) -> dict[str, Any] | None:
        """Return the LINK# row or None if not linked."""

    def list_links(self, customer_id: str) -> list[dict[str, Any]]:
        """Return all LINK#USER# rows for a customer (sorted by linked_at)."""

    def resolve_customer_for_user(self, user_sub: str) -> dict[str, Any] | None:
        """get_item on CUSTLINK#{user_sub}/META → {customer_id} or None."""
```

@dataclass
class CustomerMessageStore:
    _table: Any = field(default=T.customers)

    def post_message(
        self,
        customer_id: str,
        *,
        author_sub: str,
        author_role: Literal["STAFF", "CUSTOMER"],

        ScanIndexForward=not newest_first.

#### Endpoint signatures (pseudo-code)

```python
@router.post("/{customer_id}/link", response_model=CustomerLinkOut)
def link_customer_user(
    customer_id: str,
    body: CustomerLinkIn,
    request: Request,
    user: AuthenticatedUser = Depends(require_admin_or_root),  # from app.auth.policy
):
    _require_flag()
    store = CustomerStore()
    customer = store.get_customer(customer_id)
    if not customer:
        raise HTTPException(404)
    result = store.link_user(customer_id, body.user_sub, actor_sub=user.sub)
    audit_event("customer.linked", user.sub, request, customer_id=customer_id,
                linked_user_sub=body.user_sub)
    return result


@router.get("/me", response_model=CustomerOut)
def get_my_customer(
    ctx: dict = Depends(require_ui_session),  # from app.services.sessions
):
    _require_flag()
    store = CustomerStore()
    customer_ref = store.resolve_customer_for_user(ctx["user_sub"])
    if not customer_ref:
        raise HTTPException(404, detail={"code": "customer_not_linked"})
    customer = store.get_customer(customer_ref["customer_id"])
    if not customer:
        raise HTTPException(404)
    return customer


@router.post("/{customer_id}/messages", response_model=CustomerMessageOut)
def post_customer_message(
    customer_id: str,
    body: CustomerMessageCreateIn,
    request: Request,
    ctx: dict = Depends(require_ui_session),  # from app.services.sessions
):
    _require_flag()
    _assert_message_access(ctx, customer_id)   # raises 403 if no access
    # ctx["role"] is a string value (e.g. "admin"); Role is str-enum so equality works.
    role_str = "STAFF" if normalize_role(ctx["role"]) in (Role.ADMIN, Role.ROOT) else "CUSTOMER"
    msg_store = CustomerMessageStore()
    msg = msg_store.post_message(
        customer_id,
        author_sub=ctx["user_sub"],
        author_role=role_str,
        body=body.body,
    )
    audit_event("customer.message_sent", ctx["user_sub"], request,
                customer_id=customer_id, message_id=msg["message_id"],
                author_role=role_str)
    return msg


@router.get("/{customer_id}/messages", response_model=CustomerMessageListOut)
def list_customer_messages(
    customer_id: str,
    cursor: str | None = Query(None),
    limit: int = Query(50, ge=1, le=200),
    ctx: dict = Depends(require_ui_session),  # from app.services.sessions
):
    _require_flag()
    _assert_message_access(ctx, customer_id)
    msg_store = CustomerMessageStore()
    return msg_store.list_messages(customer_id, cursor=cursor, limit=limit)
```

#### `_assert_message_access` helper

```python
def _assert_message_access(ctx: dict, customer_id: str) -> None:
    """
    Permit ADMIN/ROOT unconditionally.
    Permit the user whose CUSTLINK#{sub}/META points to this customer_id.
    All others → 403.
    ctx["role"] is a string value from require_ui_session; normalize_role converts it to a
    Role enum so the comparison works regardless of case.
    """
    if normalize_role(ctx["role"]) in (Role.ADMIN, Role.ROOT):
        return
    ref = CustomerStore().resolve_customer_for_user(ctx["user_sub"])
    if not ref or ref.get("customer_id") != customer_id:
        raise HTTPException(403, detail={"code": "customer_access_forbidden"})
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Link idempotency

`link_user` issues a DynamoDB `TransactWriteItems` with two `Put` operations:
- Forward: `CUST#{customer_id}` / `LINK#USER#{user_sub}`, with
  `ConditionExpression="attribute_not_exists(sk)"`.
- Reverse: `CUSTLINK#{user_sub}` / `META`, with
  `ConditionExpression="attribute_not_exists(pk)"`.

If either `ConditionExpression` fails (the link already exists), the transaction raises
`TransactionCanceledException`. `link_user` catches this, re-reads the existing forward link
row, and returns it — making the operation fully idempotent from the caller's perspective
(HTTP 200, not 409).

### 5.2 `kyc_status` back-fill on link

After writing the link rows, `link_user` calls:

```python
from app.services.kyc_cases import KycCaseStore
cases = KycCaseStore().list_cases_by_owner(user_sub=user_sub, limit=1)
if cases:
    latest_status = cases[0]["status"]
    store.update_customer(customer_id,
        expected_version=customer["version"],
        kyc_status=latest_status,
        actor_sub=actor_sub,
    )
```

`list_cases_by_owner` (at `app/services/kyc_cases.py:1002`; note: there is no
`list_cases_for_user` — use `list_cases_by_owner` with keyword arg `user_sub=`)
queries `GSI_OWNER` (`gsi_owner_pk = OWNER#{user_sub}`) with
`ScanIndexForward=False, Limit=1` — a single cheap GSI query. If the user has no KYC case,
`kyc_status` is left unchanged at its default `"none"`. The `update_customer` call uses
optimistic concurrency (`expected_version`); if a concurrent update causes a conflict, the
back-fill is retried once. Failure to back-fill is non-blocking (best-effort: wrapped in
`try/except`).

### 5.3 Notification on staff message

When `post_message` is called with `author_role="STAFF"`:

1. `CustomerMessageStore.get_linked_user(customer_id)` queries
   `PK=CUST#{customer_id}`, `begins_with(SK, "LINK#USER#")`, returns the first
   `user_sub` found.
2. If a linked user exists, `write_alert` is called:
   ```python
   write_alert(
       user_sub=linked_user_sub,
       event="customer.message",
       outcome="info",
       title="New message from support",
       details={
           "customer_id": customer_id,
           "message_id": msg["message_id"],
           "preview": body[:120],
       },
   )
   ```
   This writes to `T.alerts` (SSE push + in-app notification). `write_alert` does **not**
   automatically send email; `send_alert_email` is a separate function at
   `app/services/alerts.py:459`. If email notification is desired, `post_message` must call
   `send_alert_email` explicitly after `write_alert`. The email send is dev-mode-aware (dev
   logs to file, prod sends via SES — SECOPS-007 parity).
3. The entire notification block is wrapped in `try/except Exception` — a notification
   failure must never prevent the message row from being committed.

### 5.4 Notification on customer message (optional staff alert)

When `post_message` is called with `author_role="CUSTOMER"`, the system writes an alert
to each ADMIN/ROOT user who has previously participated in the thread (i.e., has at least
one `STAFF` message in the thread). This is resolved by querying
`begins_with(SK, "MSG#")` and collecting all `author_sub` values where `author_role == "STAFF"`.
The alert payload uses `event="customer.reply"`, `outcome="info"`,
`title="Customer replied to message thread"`. The query is bounded to the last 50 messages;
if no prior staff messages exist, no staff alert is sent. The entire block is best-effort.

### 5.5 A user linked to multiple customers

The reverse-pointer model (`CUSTLINK#{user_sub}/META`) stores exactly one `customer_id`.
If admin attempts to link a user who is already linked to a different customer, the
`attribute_not_exists(pk)` condition on the reverse-pointer row fires, the `TransactWriteItems`
is cancelled, and `link_user` detects this case by reading the existing reverse-pointer and
comparing `customer_id`. If the existing pointer points to the **same** `customer_id`, the call
is idempotent (return existing). If it points to a **different** `customer_id`, raise
`CustomerLinkConflictError` → HTTP 409, body
`{"code": "customer_already_linked", "existing_customer_id": "..."}`.

### 5.6 Message pagination

`list_messages` issues a `query` with `begins_with(sk, "MSG#")` as the SK
`KeyConditionExpression`, following the same pattern used throughout the codebase
(e.g. `app/services/license_agreements.py:263,268` — `begins_with("LICENSE#")` combined
with `ExclusiveStartKey`). The claim that "DynamoDB does not support `begins_with` combined
with `ExclusiveStartKey`" is **incorrect** — DynamoDB supports this combination fully, and
every paginated `begins_with` query in the codebase uses it. An alternative `BETWEEN "MSG#"
AND "MSG$"` (ASCII 35 < 36) is also valid but is unnecessary and deviates from the codebase
pattern; prefer `begins_with`.

Pagination cursor encodes the DynamoDB `LastEvaluatedKey` via `encode_cursor`;
`decode_cursor` recovers the `ExclusiveStartKey` for the next page. Empty `cursor` → no
`ExclusiveStartKey` → first page. `limit` is passed as `Limit` in the query;
`FilterExpression` is not used (all rows in the SK range are messages).

### 5.7 Body size enforcement

`CustomerMessageCreateIn.body` has `max_length=10_000`. The FastAPI/Pydantic validation
layer rejects longer bodies with a 422 before they reach the service.

### 5.8 Customer or link not found

- `POST /{customer_id}/link`: `get_customer(customer_id)` returns `None` → 404.
- `GET /me`: `resolve_customer_for_user` returns `None` → 404 with
  `{"code": "customer_not_linked"}`.
- `POST/GET /{customer_id}/messages`: `get_customer(customer_id)` returns `None` → 404.
  Note: `_assert_message_access` performs the ownership check before the message query; it
  calls `resolve_customer_for_user` which is a cheap `get_item`.

### 5.9 Route ordering in `app/routers/customers.py`

Declaration order in the FastAPI router must be:

```python
router.get("/me", ...)              # static — must come before /{customer_id}
router.post("/{customer_id}/link", ...)
router.get("/{customer_id}/links", ...)
router.post("/{customer_id}/messages", ...)
router.get("/{customer_id}/messages", ...)
router.get("/{customer_id}", ...)   # catch-all last
```

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 — single code path

All DynamoDB operations target `T.customers` (DynamoDB Local in dev, real DynamoDB in prod).
No `if S.dev_mode` branch exists in the customer link or message service logic. Notification:
`write_alert` (`app/services/alerts.py:356`) and `send_alert_email` (`app/services/alerts.py:459`)
already implement the dev/prod split internally — dev writes to a log file, prod sends via
SES. CUS-002 calls these functions as-is; there is no diverging branch in the new code.

### Idempotency

- **Link**: idempotent by `attribute_not_exists` conditional write + conflict-detection
  re-read (see §5.1). A retry of the same link request always returns the same result.
- **Messages**: append-only with a random `message_id` per write — retrying creates a
  duplicate message. Callers (UI, E2E tests) must not retry on network timeout without
  deduplication. The router does not implement server-side message deduplication; this is
  acceptable for the current scope (staff portal use case, low volume).

### Security

- **Auth gates**: every write endpoint is behind `require_ui_session` with an explicit
  admin-or-root or ownership check. Bearer-token callers (API key holders) pass
  `require_ui_session`'s Bearer path and are subject to the same role check.
- **CSRF**: `require_ui_session` enforces CSRF for cookie-session non-GET requests
  (`x-csrf-token` header must match `ui_csrf` cookie). Bearer-auth requests skip CSRF as per
  existing contract (`app/auth/deps.py`).
- **Ownership isolation**: the `CUSTLINK#{user_sub}` reverse-pointer PK is computed from the
  session's `user_sub` — an attacker who controls their own session cannot impersonate another
  user's reverse pointer because the PK includes the session-owner's `sub`.
- **Body sanitization**: message bodies are stored verbatim (no HTML injection possible since
  there is no server-side HTML rendering). The frontend is responsible for escaping on display.
  The `max_length=10_000` limit prevents denial-of-service via oversized payloads.
- **PII**: message `body` may contain PII. It is stored on DynamoDB (at-rest encrypted via
  DynamoDB encryption). It is never logged; `audit_event` writes only `customer_id` and
  `message_id` (not the body) to `T.alerts`.

### Money-safety

No money movement in this ticket. There is no interaction with the billing ledger, wallet,
`settle_or_reverse_ledger`, `new_ledger_entry`, or `_fraud_gate`. This section is included
for completeness: the absence of money movement is intentional and enforced at the
implementation boundary.

## 8. Backward Compatibility & Migration

### Backward compatibility

CUS-002 is entirely additive:

- **No existing DynamoDB tables are modified.** New rows are written only to `T.customers`
  (introduced in CUS-001). All new row types use SK prefixes (`LINK#USER#`, `MSG#`,
  `CUSTLINK#`) that are disjoint from the existing `META` and `ATTR#` rows.
- **No existing endpoints are changed.** The KYC "request more info" path
  (`app/routers/kyc_cases.py:710-731`) is read-only from this ticket's perspective.
- **No existing services are changed.** `KycCaseStore`, `alerts.write_alert`, and
  `alerts.send_alert_email` are called as-is.

### Migration

No DynamoDB migration is required. The `customers` table is created by `scripts/local-ddb-init.py`
(CUS-001) and the new row types are written on first use. In production, the `customers` table
must be provisioned (via `UpdateTable` or a fresh `CreateTable`) before the flag is enabled —
exactly as documented in CUS-001.

Existing KYC cases are **not** retroactively linked to customer records. If an operator wants
existing users linked to customers, they call `POST /ui/customers/{id}/link` for each user.
There is no automatic migration sweep.

## 10. Open Questions / Assumptions

1. **One user per customer vs. many**: The current design enforces a 1:1 `user_sub → customer_id`
   mapping via the reverse pointer. OBP does not mandate this; a future ticket could lift the
   constraint to allow joint accounts. For CUS-002 the 1:1 model is assumed; a multi-user
   variant would need a different reverse index (e.g. a GSI on the `customers` table keyed on
   `user_sub`).

2. **Message soft-delete**: No delete or retract endpoint is specified. If needed in future,
   a `deleted: bool` flag can be added to the MSG row and filtered in `list_messages` — the
   SK key structure does not change.

3. **Notification targeting for staff**: CUS-002 notifies the single linked user on staff
   messages. If a customer is later linked to multiple users (see question 1), the notification
   should fan out to all linked users — deferred.

4. **`list_cases_by_owner` on `KycCaseStore`**: The existing method at
   `app/services/kyc_cases.py:1002` is `list_cases_by_owner(*, user_sub: str, limit: int = 25)`
   — keyword-only args. There is **no** `list_cases_for_user`. CUS-002 calls
   `KycCaseStore().list_cases_by_owner(user_sub=user_sub, limit=1)` directly; no new method
   needs to be added to `KycCaseStore`.

5. **Body content moderation**: Message bodies are stored verbatim. No content moderation is
   applied in this ticket. A future integration with the platform's `moderation_policy_engine`
   could be added as a best-effort pre-filter.

6. **Rate limiting on message posts**: Not implemented in this ticket. If volume becomes a
   concern, the existing `_bucket_limit` helper in `app/services/rate_limit.py` can be dropped
   in front of `post_message` with a `customer_message:{customer_id}` key.
