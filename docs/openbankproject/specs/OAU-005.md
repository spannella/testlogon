# OAU-005 — Consumer enable/disable + client-secret rotation

**Ticket type**: Backend (service + router extension)
**Priority**: P2
**Estimate**: 1.5 days
**Status**: Unimplemented
**Flags**: `OAUTH_PROVIDER_ENABLED` (master flag from OAU-001, default off)

---

## 1. Summary & Goal

OAU-005 adds the **operational lifecycle** layer to the consumer-app registry introduced in OAU-001: an owner (or an admin) can **disable** a compromised consumer app or **rotate** its client secret — and both operations take effect immediately with no grant enumeration required.

Disabling a consumer causes every subsequent use of that consumer's identity to be rejected at the existing auth chokepoint (`get_authenticated_user`, `app/auth/deps.py:199`) without touching any issued grant row. Re-enabling restores the consumer instantly. Secret rotation mints a fresh `secrets.token_urlsafe(32)` secret, writes only the new `client_secret_hash`, and returns the new plaintext exactly once — the old secret stops verifying at the moment `update_item` completes because there is a single hash slot.

Both operations are modeled directly on the API-key revoke and capability-update flows (`app/services/api_keys.py:187-196,329-341`), use the same auth guards (`require_ui_session` + `require_fresh_mfa` + `audit_event`) as `app/routers/api_keys.py:17-29`, and are added to the `app/services/oauth_consumers.py` service and `app/routers/oauth_consumers.py` router that OAU-001 establishes. No new files, no new tables, and no new primitives are introduced.

The goal of this ticket is:

1. Extend `app/services/oauth_consumers.py` with `set_consumer_enabled` and `rotate_client_secret`.
2. Add three POST endpoints to `app/routers/oauth_consumers.py`: `enable`, `disable`, and `rotate-secret`.
3. Wire disabled-consumer enforcement into the OAU-002 auth-bearer branch (`deps.py`) and the OAU-002 `/oauth/authorize` + `/oauth/token` handlers so that disabling a consumer instantly kills both new authorizations and bearer-token acceptance without enumerating or revoking individual grant rows.
4. Cover the full lifecycle in `tests/test_oau_005_lifecycle.py` (hermetic, offline, moto-bound).

None of these exist yet in the codebase — they are specified in `docs/openbankproject/specs/OAU-001.md` and must be implemented before OAU-005.

### 2.2 The API-key lifecycle pattern (direct analogue)

The API-key registry (`app/services/api_keys.py`) is the blueprint for both operations:

**Revoke (maps to disable):** `revoke_api_key` at `api_keys.py:187-196`:

```python
def revoke_api_key(user_sub: str, key_id: str) -> None:
    try:
        T.api_keys.update_item(
            Key={"key_id": key_id},
            UpdateExpression="SET revoked = :t, revoked_at = :now",
            ConditionExpression="user_sub = :u",
            ExpressionAttributeValues={":t": True, ":now": now_ts(), ":u": user_sub},
        )
    except Exception:
        raise HTTPException(404, "API key not found")
```

The `ConditionExpression="user_sub = :u"` enforces owner isolation — the same conditional must be written as `owner_sub = :u` for consumer rows.

**Capability update (maps to the `enabled`/`secret_hash` field update):** `set_api_key_capabilities` at `api_keys.py:329-341`:

```python
def set_api_key_capabilities(user_sub: str, key_id: str, capabilities: ...) -> Dict[str, Any]:
    ...
    try:
        T.api_keys.update_item(
            Key={"key_id": key_id},
            UpdateExpression="SET capabilities = :caps, updated_at = :now",
            ConditionExpression="user_sub = :u",
            ExpressionAttributeValues={":caps": normalized, ":u": user_sub, ":now": now_ts()},
        )
    except Exception:
        raise HTTPException(404, "API key not found")
```

**Secret generation** (maps to rotation): `new_api_key_secret()` returns `secrets.token_urlsafe(32)` (`api_keys.py:18`). `api_key_hash(secret)` returns `sha256_str(secret + "|" + S.api_key_pepper)` (`api_keys.py:31-34`), where `sha256_str` is `hashlib.sha256(s.encode("utf-8")).hexdigest()` (`app/core/crypto.py:13-14`). The plaintext is returned once as `f"ak_{key_id}.{secret}"` (`api_keys.py:178-185`); for consumers the prefix is `oc_` (established in OAU-001).

### 2.3 Router auth pattern (direct analogue)

`app/routers/api_keys.py:17-29` shows the three-part guard — `require_ui_session` (session dep), `require_fresh_mfa(ctx)` (step-up), `audit_event(...)` (write-through audit) — that every mutation endpoint uses:

### 2.4 Current auth layer (where disabled-consumer enforcement is wired)

`get_authenticated_user` at `app/auth/deps.py:199` resolves callers in order: API-key principal (`deps.py:209-224`), cookie/HS256 JWT (`deps.py:226-252`), Cognito JWT Bearer (`deps.py:254-273`), dev-mode fallbacks (`deps.py:275-305`).

All three sites are within OAU-002's scope. OAU-005 defines the `set_consumer_enabled` service function and the router endpoints; OAU-002 defines the enforcement sites. The two tickets coordinate here: OAU-005 must be spec'd and reviewed together with the OAU-002 enforcement wiring.

## 3. Data Model

### 3.1 No new table

OAU-005 adds no new DynamoDB table. All writes go to the `oauth_consumers` table defined in OAU-001 (PK `client_id`, SK `sk`). The consumer META row (`sk="META"`) already carries `enabled: bool`, `client_secret_hash: str`, and `secret_rotated_at: int` as established by OAU-001.

### 3.2 Fields touched by OAU-005 operations

| Operation | Fields updated | Expression |
|---|---|---|
| `set_consumer_enabled(enabled=False)` | `enabled`, `updated_at` | `SET enabled=:e, updated_at=:now` |
| `set_consumer_enabled(enabled=True)` | `enabled`, `updated_at` | `SET enabled=:e, updated_at=:now` |
| `rotate_client_secret(...)` | `client_secret_hash`, `secret_rotated_at`, `updated_at` | `SET client_secret_hash=:h, secret_rotated_at=:now, updated_at=:now` |

All updates use `ConditionExpression="owner_sub = :u"` (owner isolation). A conditional-check failure (wrong `owner_sub` or item does not exist) raises `HTTPException(404, "Consumer not found")` — identical to the `revoke_api_key` shape (`api_keys.py:187-196`).

### 3.3 `attr_types` — no new numeric keys

The `oauth_consumers` table already declares `attr_types={"created_at": "N"}` for the `ByOwner` GSI sort key (`created_at`). The new fields (`updated_at`, `secret_rotated_at`, `enabled`) are stored as DDB attribute values on the META item, not as GSI keys — they require no additional `attr_types` declaration.

### 3.4 Existing grant rows are not touched

`GRANT#` rows (refresh-grant rows written by OAU-002 under `sk="GRANT#{grant_id}"`) are not enumerated, modified, or deleted by any OAU-005 operation. Enforcement is at the `get_consumer().enabled` chokepoint: a disabled consumer's grants are implicitly rejected when the bearer-token or token-endpoint path reads the META row and finds `enabled=False`. This is intentional (same design rationale as disabling an API key: no need to enumerate individual issued keys).

## 4. API / Service Design

### 4.1 Service layer — `app/services/oauth_consumers.py` (extends OAU-001)

```python
def set_consumer_enabled(
    owner_sub: str,
    client_id: str,
    enabled: bool,
) -> Dict[str, Any]:
    """
    Enable or disable a consumer.  Owner-scoped conditional update.
    Returns the updated META item (without client_secret_hash).
    Raises HTTPException(404) if client_id not found or owner mismatch.
    """
    try:
        T.oauth_consumers.update_item(
            Key={"client_id": client_id, "sk": "META"},
            UpdateExpression="SET enabled = :e, updated_at = :now",
            ConditionExpression="owner_sub = :u",
            ExpressionAttributeValues={
                ":e": enabled,
                ":now": now_ts(),
                ":u": owner_sub,
            },
        )
    except Exception:
        raise HTTPException(404, "Consumer not found")
    return _get_consumer_safe(client_id)   # hides client_secret_hash


def rotate_client_secret(
    owner_sub: str,
    client_id: str,
) -> Dict[str, Any]:
    """
    Mints a new client_secret, writes only the new hash, returns the
    plaintext exactly once.  Raises HTTPException(404) on owner mismatch.
    """
    secret = new_consumer_secret()          # secrets.token_urlsafe(32)
    secret_hash = api_key_hash(secret)      # sha256_str(secret + "|" + S.api_key_pepper)
    ts = now_ts()
    try:
        T.oauth_consumers.update_item(
            Key={"client_id": client_id, "sk": "META"},
            UpdateExpression=(
                "SET client_secret_hash = :h, secret_rotated_at = :now,"
                "    updated_at = :now"
            ),
            ConditionExpression="owner_sub = :u",
            ExpressionAttributeValues={
                ":h": secret_hash,
                ":now": ts,
                ":u": owner_sub,
            },
        )
    except Exception:
        raise HTTPException(404, "Consumer not found")
    return {
        "client_id": client_id,
        "client_secret": f"oc_{client_id}.{secret}",   # plaintext, returned once
        "secret_rotated_at": ts,
    }
```

`new_consumer_secret()` is an alias for `secrets.token_urlsafe(32)`, matching `new_api_key_secret()` at `api_keys.py:18`. `api_key_hash` is imported from `app/services/api_keys` (not re-implemented) — the same pepper, the same `sha256_str`, the same `hmac.compare_digest` compare used by `verify_client_secret` in OAU-001.

`_get_consumer_safe(client_id)` is the `get_consumer` helper from OAU-001 that strips `client_secret_hash` before returning — the same safety invariant as `list_api_keys` hiding `secret_hash` (`api_keys.py:349-374`).

### 4.2 Router layer — `app/routers/oauth_consumers.py` (extends OAU-001)

The three new endpoints are appended to the existing router (established by OAU-001 with prefix `/ui/oauth/consumers`). Because the new paths are two segments deep (`/{client_id}/enable`, `/{client_id}/disable`, `/{client_id}/rotate-secret`) while the existing `GET /{client_id}` / `PATCH /{client_id}` / `DELETE /{client_id}` patterns are single-segment paths, FastAPI's path matching never confuses the two groups regardless of declaration order — no path-prefix-ordering concern applies here (contrast with the KYC `/schedules` vs `/{export_id}` conflict where the collision is at the same depth).

```python
@router.post("/{client_id}/enable")
async def ui_enable_consumer(
    req: Request,
    client_id: str,
    ctx: Dict = Depends(require_ui_session),
) -> Dict:
    require_fresh_mfa(ctx)
    updated = set_consumer_enabled(ctx["user_sub"], client_id, enabled=True)
    audit_event(
        "oauth_consumer_enable",
        ctx["user_sub"],
        req,
        outcome="success",
        client_id=client_id,
    )
    return updated


@router.post("/{client_id}/disable")
async def ui_disable_consumer(
    req: Request,
    client_id: str,
    ctx: Dict = Depends(require_ui_session),
) -> Dict:
    require_fresh_mfa(ctx)
    updated = set_consumer_enabled(ctx["user_sub"], client_id, enabled=False)
    audit_event(
        "oauth_consumer_disable",
        ctx["user_sub"],
        req,
        outcome="success",
        client_id=client_id,
    )
    return updated


@router.post("/{client_id}/rotate-secret")
async def ui_rotate_consumer_secret(
    req: Request,
    client_id: str,
    ctx: Dict = Depends(require_ui_session),
) -> Dict:
    require_fresh_mfa(ctx)
    result = rotate_client_secret(ctx["user_sub"], client_id)
    audit_event(
        "oauth_consumer_secret_rotate",
        ctx["user_sub"],
        req,
        outcome="success",
        client_id=client_id,
    )
    return result
```

All three endpoints:
- Are authenticated via `Depends(require_ui_session)` (cookie + CSRF enforcement from `app/services/sessions.py:330`).
- Require `require_fresh_mfa(ctx)` (step-up gate, `sessions.py:699`).
- Write an `audit_event` on every successful mutation (`app/services/alerts.py:644`).
- Use HTTP `POST` (state-changing operations — not `PATCH`, because they are named actions, not field updates).
- Return `{"ok": True}` plus relevant fields, not the full consumer item (the secret on rotation; the updated item for enable/disable without the hash).

### 4.3 Pydantic request/response models (`app/models.py`)

No new request body is needed for `enable` or `disable` (the path parameter carries the `client_id`). The `rotate-secret` endpoint likewise has no body — the `client_id` comes from the path.

Response models (additive, in `app/models.py`):

```python
class OAuthConsumerEnabledOut(BaseModel):

class OAuthConsumerRotateSecretOut(BaseModel):
```

### 4.4 Disabled-consumer enforcement wiring (OAU-002 sites)

These three enforcement sites live in OAU-002 code but are contractually specified here:

**Site 1 — `GET /oauth/authorize` (OAU-002 router)**
After validating `client_id` is present in `oauth_consumers`, add:
```python
consumer = get_consumer(client_id)
if not consumer or not consumer.get("enabled"):
    raise HTTPException(401, {"code": "oauth_consumer_disabled"})
```

**Site 2 — `POST /oauth/token` (OAU-002 router)**
At the top of every grant-type handler, before any code/grant-row lookup:
```python
consumer = get_consumer(client_id)
if not consumer or not consumer.get("enabled"):
    raise HTTPException(401, {"code": "oauth_consumer_disabled"})
```

**Site 3 — OAuth-bearer branch of `get_authenticated_user` (`app/auth/deps.py`)**
After decoding the JWT payload and extracting `client_id` from the `client_id` claim:
```python
consumer = get_consumer(decoded_client_id)
if not consumer or not consumer.get("enabled"):
    raise HTTPException(401, {"code": "oauth_consumer_disabled"})
```

All three sites call `get_consumer(client_id)` which does a DDB `get_item` on PK `client_id` + SK `"META"`. Because the META row is a single DDB point-read, the overhead is one read per OAuth request — equivalent to the API-key lookup already performed on every api-key-authenticated request (`api_keys.py:417-444`, `check_api_key_allowed`).

### 4.5 Admin override path

Admin users (`role >= ADMIN`) can disable/enable/rotate any consumer, not just those they own. The service function signature takes `owner_sub`; when the caller is an admin the router passes the **consumer's actual `owner_sub`** (fetched first with a `get_consumer` that does not enforce ownership) rather than the admin's own sub. A separate admin-specific endpoint can be added as a follow-up; for the initial implementation the owner-scoped endpoint suffices and admin override is noted as an open question.

## 5. Detailed Behavior & Edge Cases

### 5.1 Enable/disable semantics

- **Disable** flips `enabled=False` and updates `updated_at`. The operation is idempotent: disabling an already-disabled consumer succeeds silently (the conditional only checks `owner_sub`, not the current value of `enabled`).
- **Enable** flips `enabled=True` and updates `updated_at`. Idempotent in the same way.
- A disabled consumer's **existing auth codes** (OAU-002 `CODE#` rows in the same table) are invalidated implicitly: `POST /oauth/token` checks `enabled` before inspecting the code row, so even a valid unexpired code is rejected for a disabled consumer.
- A disabled consumer's **existing refresh grants** (`GRANT#` rows) are invalidated implicitly for the same reason: the token-endpoint refresh path checks `enabled` first.
- A disabled consumer's **existing issued access tokens** (HS256 JWTs, not stored in DDB) are invalidated implicitly: the OAuth-bearer branch in `deps.py` re-reads `get_consumer(client_id)` on every request.

The net effect: disabling a consumer **immediately** revokes all active sessions for that consumer's token holders without any batch job or grant enumeration.

### 5.2 Secret rotation semantics

- `rotate_client_secret` is **not** idempotent — each call mints a fresh secret and returns it. Repeated calls each return a different secret; each supersedes the previous.
- There is exactly **one** `client_secret_hash` slot in the META row. Writing a new hash atomically invalidates the old secret. There is no "grace period" during which both old and new secrets are valid — if a grace window is needed it is a follow-up feature.
- The plaintext `oc_{client_id}.{secret}` is returned in the HTTP response body and **never stored**. If the caller does not capture it, they must rotate again.
- `verify_client_secret` (OAU-001) computes `api_key_hash(submitted_secret)` and calls `hmac.compare_digest` against the stored `client_secret_hash` — after rotation, only the new hash is stored, so only the new secret passes.
- If `is_confidential=False` (public PKCE-only client, from OAU-001), the client has no usable secret and `rotate-secret` should return `400 {"code": "oauth_public_client_no_secret", "message": "Public clients do not use a client_secret"}`. The `is_confidential` field is read from the META row before calling `rotate_client_secret`; the check lives in the router handler (not the service), keeping the service pure.

### 5.3 Owner isolation

Both `set_consumer_enabled` and `rotate_client_secret` use `ConditionExpression="owner_sub = :u"`. If `client_id` does not exist at all, or exists but has a different `owner_sub`, the DDB conditional fails and the service raises `HTTPException(404, "Consumer not found")`. This prevents leaking the existence of a consumer owned by another user — the 404 shape is identical to `revoke_api_key` (`api_keys.py:195`).

### 5.4 Concurrent rotation safety

DDB conditional expressions are atomic. Two simultaneous `rotate-secret` calls for the same `client_id` both succeed (the condition is `owner_sub = :u`, not a version or `attribute_not_exists`). Both write their respective new hashes; whichever write lands last wins. The caller that loses the race receives a stale plaintext. This is acceptable because each rotation returns a fresh secret and consumers are expected to use the returned value immediately. If strict "at-most-one-rotation-wins" semantics are required, an optimistic-lock `version` counter can be added as a follow-up.

### 5.5 CSRF requirements

All three endpoints live under the `/ui/` prefix and use `Depends(require_ui_session)`. Cookie-authenticated callers must include `x-csrf-token: <token>` matching `session.csrf_token` and the `ui_csrf` cookie, exactly as all other mutation endpoints in the platform. Bearer-auth callers (unlikely for these endpoints — they are owner-UI operations) skip CSRF per the standard platform rule (`app/auth/deps.py` CSRF gate, CLAUDE.md "Auth dependency").

### 5.6 Rate limiting

No new rate-limit bucket is introduced. The existing session-level rate limiting (applied at the middleware layer) covers these endpoints. If per-consumer abuse is a concern (e.g., an attacker repeatedly rotating their own secret), the existing `_bucket_limit` helper (`app/services/rate_limit.py`) can be applied in a follow-up.

### 5.7 MFA freshness window

`require_fresh_mfa(ctx)` enforces that the session's `mfa_verified_at` is within `S.ui_stepup_max_age_seconds` (default value from settings). There is no separate, stricter window for these endpoints in the initial implementation. For production deployments a tighter window (e.g., 300s) may be configured per the settings key.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 parity

There is no `if S.dev_mode:` branch anywhere in OAU-005 service or router code. All DDB reads and writes go through `T.oauth_consumers` (DynamoDB Local on port 8001 in dev, real DynamoDB in prod). JWT signing uses `S.ui_access_token_secret` both envs. Secret hashing uses `S.api_key_pepper` both envs. The enforcement check at `get_consumer(client_id)["enabled"]` is a plain DDB `get_item` that behaves identically in both environments.

### 7.2 No money-safety concerns

OAU-005 does not initiate, modify, or reverse any financial transaction. The billing ledger (`app/services/billing_shared.py`), wallet rows, `new_ledger_entry`, `settle_or_reverse_ledger`, and fraud-gate paths are not involved. This is a pure auth-lifecycle operation.

### 7.3 Idempotency

- **`set_consumer_enabled`**: idempotent (re-enabling an enabled consumer or re-disabling a disabled consumer succeeds with the same outcome and does not increment any counter).
- **`rotate_client_secret`**: not idempotent by design — each call produces a new secret. The router does not add any deduplication; callers must treat the returned `client_secret` as a one-time value.

### 7.4 Secret hygiene

- The new `client_secret` plaintext is present only in the HTTP response body and in the `rotate_client_secret` return value in memory. It is not logged anywhere — `audit_event` at `app/services/alerts.py:644` receives only `client_id` and `outcome`, never the secret value.
- `client_secret_hash` is never returned in any API response. `_get_consumer_safe` (OAU-001 helper) strips it before returning, mirroring how `list_api_keys` hides `secret_hash` (`api_keys.py:349-374`).
- The `oc_{client_id}.{secret}` format (prefix `oc_`) is analogous to `ak_{key_id}.{secret}` (`api_keys.py:182`). Secret scanning tools can pattern-match on the `oc_` prefix to detect accidental leaks.

### 7.5 Audit trail

Three new audit event strings are introduced:

| Event string | Trigger |
|---|---|
| `"oauth_consumer_enable"` | `POST /ui/oauth/consumers/{client_id}/enable` success |
| `"oauth_consumer_disable"` | `POST /ui/oauth/consumers/{client_id}/disable` success |
| `"oauth_consumer_secret_rotate"` | `POST /ui/oauth/consumers/{client_id}/rotate-secret` success |

All three are passed to `audit_event(event, user_sub, req, outcome="success", client_id=...)` (`app/services/alerts.py:644`), writing a row to `T.alerts` with the caller's `user_sub`, the `client_id`, and the timestamp. No audit is written on failure — the caller receives a 404 (not found / not owned) or 401 (MFA required).

## 8. Backward Compatibility & Migration

### 8.1 No schema migration required

The `oauth_consumers` table is new (introduced in OAU-001). There are no existing rows to migrate. The `enabled`, `client_secret_hash`, and `secret_rotated_at` fields are present on the META item from the moment it is created by `create_consumer` (OAU-001). No `UpdateTable` backfill is required.

### 8.2 No breaking changes

OAU-005 adds three POST endpoints under `/ui/oauth/consumers/{client_id}/`. No existing endpoints are modified. No existing request/response shapes change. No existing middleware, auth dependencies, or DDB table schemas are altered. All changes are strictly additive.

### 8.3 Rollout order

OAU-005 must be deployed after OAU-001 (table + service foundation) and after OAU-002 (the enforcement sites that check `enabled`). Deploying OAU-005 endpoints without OAU-002 enforcement sites means the `/disable` endpoint writes `enabled=False` to DDB but the auth layer never checks it — a silent no-op from a security perspective. The correct deploy sequence is: OAU-001 → OAU-002 → OAU-004 → OAU-005 (or OAU-002 and OAU-005 in the same deployment, which is the preferred approach).

## 10. Open Questions / Assumptions

**Q1: Admin override path.**
The current design scopes all three endpoints to the consumer's owner (`ConditionExpression="owner_sub = :u"`). Should an `ADMIN` or `ROOT` user be able to disable any consumer across all owners? The assumption here is yes for ROOT (emergency kill-switch for a compromised app), but the mechanism (a separate admin endpoint, or a role-check bypass in the existing service function) is deferred to a follow-up. For the initial implementation, only the owner can perform these operations.

**Q2: Grace period on secret rotation.**
OBP's consumer management supports a brief overlap window during which both the old and new secrets are valid. This simplifies coordinated secret rotation for distributed consumer deployments. The current spec takes the simpler approach (immediate single-slot replacement, matching the API-key pattern). If overlap is needed, a `previous_client_secret_hash` field with a configurable expiry TTL could be added additively.

**Q3: Webhook event for disable/enable.**
Should `oauth_consumer_disable` / `oauth_consumer_enable` emit a webhook event (via `app/services/webhook_service.py`) in addition to the internal audit event? The assumption is no for the initial implementation — webhook events are for resource owners who want external notification, and the consumer lifecycle is a platform-owner concern. This is a follow-up if external notification is required.

**Q4: Re-authorization requirement after enable.**
When a consumer is re-enabled, should existing access tokens that were issued before the disable be considered valid or stale? The current design considers them valid (the JWT signature check and the `enabled=True` check both pass). If revocation of pre-disable tokens is required, a `disabled_at` timestamp would need to be stored and compared against the token's `iat` claim — this is not in scope here.

**Assumption A1**: The `enabled` field is a plain DDB boolean. DDB stores it as a boolean attribute type. The `update_item` expression `SET enabled = :e` with `:e = True/False` writes it correctly via boto3.

**Assumption A2**: `require_fresh_mfa(ctx)` raises `HTTPException(401)` synchronously before any DDB write occurs. The three new endpoints call it before calling any service function, so a stale-MFA 401 never leaves a partial write.
