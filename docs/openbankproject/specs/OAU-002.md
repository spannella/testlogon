# OAU-002 — OAuth2 authorization-code + PKCE flow (`GET /oauth/authorize`, `POST /oauth/token`)

**Ticket type**: Backend (auth flow + token issuance + auth-layer integration)
**Priority**: P1
**Estimate**: 4 days
**Status**: Unimplemented
**Flags**: `OAUTH_PROVIDER_ENABLED` (master, from OAU-001, default off) + `OAUTH_PROVIDER_DIRECTLOGIN_ENABLED` (new, default off)

---

## 1. Summary & Goal

OAU-002 is the core OAuth2 authorization-code + PKCE grant for testlogon acting as an **authorization server**. A registered consumer app (from OAU-001) redirects a resource owner's browser to `GET /oauth/authorize`, the logged-in user consents, a short-lived signed authorization code is redirected back, and the consumer exchanges it at `POST /oauth/token` for an HS256 access token (+ optional refresh token). The issued token is immediately accepted by the existing auth layer (`get_authenticated_user`, `app/auth/deps.py:199`) as a new recognized branch — no changes to any existing endpoint or middleware are needed.

The central design decision is that this flow is **entirely additive and default-off**. With `OAUTH_PROVIDER_ENABLED=false` (the default), the two new routers are not registered (`app/main.py` conditional, same pattern as all other flag-gated routers), and the new auth branch inside `get_authenticated_user` is a dead path. The platform is byte-for-byte unchanged.

The optional **DirectLogin** grant (`grant_type=password`, OBP's non-redirect username/password flow) is gated behind its own `OAUTH_PROVIDER_DIRECTLOGIN_ENABLED` flag, also default off, and reuses `_verify_local_password` (`app/auth/deps.py:167`) — no new password verification logic.

## 2. Context & Current State

### Current auth layer (what OAU-002 extends)

testlogon authenticates inbound callers via three paths in `get_authenticated_user` (`app/auth/deps.py:199–305`):

1. **Cookie/HS256 JWT** (`ui_access_token` cookie): minted by `mint_access_token` (`app/services/sessions.py:206`) as `jwt.encode(payload, S.ui_access_token_secret, algorithm="HS256")` (`sessions.py:228`). The cookie path decodes with `verify_exp=False` (`deps.py:236`) so the refresh endpoint can still identify an expired-cookie user.
2. **Cognito JWT Bearer** (`deps.py:255–273`): RS256, verified against the Cognito JWKS. This branch runs only when `_cognito_enabled()` (`deps.py:25`) is true (`COGNITO_USER_POOL_ID` + `COGNITO_APP_CLIENT_ID` both set).
3. **Dev-mode fallbacks** (`deps.py:275–305`): `x-user-sub` header or bare Bearer token, only when `S.dev_mode` is true and Cognito is not configured. These remain unchanged.

The `api_key_principal` path (`deps.py:210–224`) is a fourth branch, injected by the API-key middleware onto `request.state` before auth resolution. OAU-002 adds a **fifth branch** — the OAuth-bearer branch — slotted in **after the `api_key_principal` block (`deps.py:224`) and before the cookie path (`deps.py:226`)** (it must also precede Cognito at `deps.py:255` so that an OAU-002 HS256 access token is not sent to `_decode_cognito_token`, which only accepts RS256).

### Current OAuth posture (testlogon is only a client today)

testlogon acts as an OAuth **client** to Google Drive: `build_google_oauth_start` and `complete_google_oauth_callback` in `app/services/provider_oauth.py` (lines 99–224). This module is the **contrast**, not the foundation — OAU-002 builds the **reverse direction** (testlogon as server). The only primitives borrowed from `provider_oauth.py` are:

- The single-use state-consumption pattern via `ConditionExpression="attribute_not_exists(consumed_at)"` (`provider_oauth.py:203–215`), used identically for auth-code single-use enforcement.
- The redirect-URI validation shape: `_validate_google_redirect_uri` (`provider_oauth.py:84–96`) checks `parsed.scheme in {"http", "https"}` and `parsed.netloc` non-empty against an allowlist. OAU-002 applies the same logic against the consumer's stored `redirect_uris`.

### Secret + token primitives (reuse, never fork)

- **HMAC signed artifact envelope**: `mint_ws_token` / `verify_ws_token` (`app/core/crypto.py:35–61`). Both use `base64url(payload_json) + "." + base64url(hmac_sha256_sig)` with `S.ws_token_secret`. OAU-002 reuses this scheme to wrap the opaque `code_id` in a tamper-evident envelope — a corrupted code is rejected before any DDB read. The `user_sub` field in the payload is repurposed to carry `code_id`; the `exp` field enforces the short TTL.
- **HS256 JWT minting**: `jwt.encode(payload, S.ui_access_token_secret, algorithm="HS256")` (`sessions.py:228`). Access tokens are minted with the same secret and algorithm. The OAU-002 payload adds `token_type="access"`, `client_id`, and `scope` to distinguish OAuth tokens from session tokens at the decode site.
- **Secret hashing** (for refresh tokens): `api_key_hash(secret)` = `sha256_str(secret + "|" + S.api_key_pepper)` (`app/services/api_keys.py:31–34`, `app/core/crypto.py:13–14`). Refresh-token plaintext is stored client-side only; the hash lives in DDB, never the plaintext.
- **TTL rows**: `with_ttl(item, ttl_epoch=...)` (`app/services/ttl.py:5`) writes `S.ddb_ttl_attr` (default `"ttl_epoch"`) onto the item. Auth-code rows (60s TTL) and refresh-grant rows (configurable TTL) both use this.
- **Local password verification**: `_verify_local_password(username, password)` (`deps.py:167–196`) — PBKDF2-SHA256 with the stored `hash_b64`/`salt_b64`/`iterations` from `T.users`. Used by the DirectLogin branch.
- **`now_ts()`**: integer Unix seconds (`app/core/time.py`). All `issued_at`, `exp`, `created_at` fields use this.

### Scope registry (shared with API keys)

`API_KEY_ROUTE_SCOPE_REGISTRY` (`app/services/api_key_route_scope_registry.py:17–67`) and `resolve_required_scopes_for_route` / `get_route_scope_policy` (`api_key_route_scope_registry.py:275–283`) govern both API-key and OAuth callers. An OAuth token's `scope` claim uses the same string identifiers (`messager:read`, `filemanager:write`, etc.). No second scope taxonomy is introduced.

## 3. Data Model

### Existing table reused: `oauth_consumers` (from OAU-001)

OAU-001 declares `oauth_consumers` as a single-table covering three row types via the `sk` discriminator: consumer `META` rows, auth-code rows, and issued-grant (refresh-token) rows. OAU-002 writes the second and third row types.

**`oauth_consumers` table** (declared in `scripts/local-ddb-init.py` by OAU-001):

```
PK: client_id (S)
SK: sk (S)

GSI "ByOwner":
  partition: owner_sub (S)
  sort:      created_at (N)
  attr_types: {"created_at": "N"}   ← required; omitting causes ValidationException
```

Settings keys (added by OAU-001): `S.oauth_consumers_table_name` (env `OAUTH_CONSUMERS_TABLE_NAME`, default `"oauth_consumers"`); `T.oauth_consumers` wired in `app/core/tables.py`.

### New row type 1: Auth-code row

```
PK:  client_id
SK:  CODE#{code_id}

Fields:
  code_id            S    — opaque random ID (secrets.token_hex(16))
  owner_user_sub     S    — resource owner who consented
  client_id          S    — denormalized for cross-key queries
  redirect_uri       S    — the exact redirect_uri from the /authorize request
  granted_scopes     S    — space-delimited granted scope string
  code_challenge     S    — BASE64URL(SHA256(code_verifier)) from the request
  code_challenge_method  S — always "S256"
  issued_at          N    — now_ts()
  consumed_at        S    — absent until consumed; set by single-use conditional
  ttl_epoch          N    — now_ts() + S.oauth_code_ttl_seconds (default 60)
```

The `ttl_epoch` attribute name is `S.ddb_ttl_attr` (default `"ttl_epoch"`), written via `with_ttl(item, ttl_epoch=...)` (`app/services/ttl.py:5`). DynamoDB TTL removes stale unconsumed codes automatically.

The `consumed_at` field is **absent on creation**. The `attribute_not_exists(consumed_at)` `ConditionExpression` on token exchange (`provider_oauth.py:203–215` pattern) atomically marks it consumed; a second exchange attempt fails the condition and returns 400 `code_already_used`.

### New row type 2: Issued-grant row (refresh token)

```
PK:  client_id
SK:  GRANT#{grant_id}

Fields:
  grant_id           S    — secrets.token_hex(16)
  owner_user_sub     S    — resource owner
  client_id          S    — denormalized
  granted_scopes     S    — space-delimited; copied from the code row at issuance
  refresh_token_hash S    — api_key_hash(refresh_plaintext)
  issued_at          N    — now_ts()
  rotated_at         S    — absent until rotated; set on each refresh-token use
  revoked            BOOL — default False; set true on consumer disable
  ttl_epoch          N    — now_ts() + S.oauth_refresh_token_ttl_seconds (default 30d)
```

### No new DynamoDB tables

OAU-002 introduces no new tables. All artifacts live under the `oauth_consumers` table established by OAU-001. The `T.users` handle (existing `app/core/tables.py`) is read in the OAuth-bearer branch of `get_authenticated_user` to resolve the resource owner's role — no modification required.

### 4.2 Router A: `app/routers/oauth_authorize.py` (new)

Prefix: `/oauth` (no `/ui` prefix — these are OAuth standard paths, not session-UI paths).
Registered in `app/main.py` inside `if S.oauth_provider_enabled:` (same pattern as all flag-gated routers).

```
GET /oauth/authorize
  Auth dep:   Depends(require_ui_session)
  Query params (all str):
    response_type       required, must be "code"
    client_id           required
    redirect_uri        required
    scope               required, space-delimited
    state               required (anti-CSRF, passed through)
    code_challenge      required
    code_challenge_method  required, must be "S256"
    nonce               optional (passed to OAU-003 id_token; stored on code row)

  Returns: 302 redirect to {redirect_uri}?code=<signed>&state=<state>
  Errors (302 to redirect_uri?error=…&state=…):
    invalid_client        — client_id not found or disabled
    unauthorized_client   — redirect_uri not in consumer's allowlist
    invalid_scope         — requested scope not ⊆ consumer.allowed_scopes
    invalid_request       — missing/malformed params, code_challenge_method != "S256"
  Errors redirected to redirect_uri are standard OAuth2 error redirects.
  Fatal errors (bad redirect_uri itself, or no valid redirect registered)
    return 400 JSON (cannot redirect to an invalid URI).
```

**Request validation sequence** inside the handler:

1. Load consumer via `get_consumer(client_id)` (OAU-001 service). Missing or `enabled=False` → 400 JSON (no redirect, client is untrusted).
2. Validate `redirect_uri`: exact-match against `consumer.redirect_uris`, `http`/`https` + non-empty netloc (`provider_oauth.py:84–96` shape). Mismatch → 400 JSON.
3. Validate `code_challenge_method == "S256"`. Mismatch → redirect with `error=invalid_request`.
4. Validate `scope`: `_validate_requested_scopes(scope, consumer_item)`. Failure → redirect with `error=invalid_scope`.
5. For public clients (`consumer.is_confidential=False`): require `code_challenge` non-empty. Missing → redirect `error=invalid_request`.
6. Call `issue_auth_code(...)` → signed code string.
7. Return `RedirectResponse(f"{redirect_uri}?code={code}&state={state}", 302)`.

### 4.3 Router B: `app/routers/oauth_token.py` (new)

Prefix: `/oauth`
**No session dependency** — this endpoint is called by the consumer app server-side, not the user's browser. Authentication is via `client_id`+`client_secret` (confidential) or PKCE alone (public). CSRF does not apply.

POST /oauth/token
  Content-Type: application/x-www-form-urlencoded  (standard OAuth2)
  Auth dep:   none (client-credential authenticated in-handler)

  Body fields vary by grant_type:

    password          required
    client_id         required
    client_secret     required

    {
      "access_token":  "<HS256 JWT>",
      "token_type":    "bearer",
      "expires_in":    <int seconds>,
      "scope":         "<space-delimited granted scopes>",
      "refresh_token": "<opaque string>"  // only when offline_access in scope
    }

  Returns 400 JSON (OAuth2 error response):
    {
      "error":             "<oauth2_error_code>",
      "error_description": "<human string>"
    }
  OAuth error codes:

### 4.4 OAuth-bearer branch in `get_authenticated_user` (`app/auth/deps.py`)

A new `if S.oauth_provider_enabled:` block is inserted **after the `api_key_principal` block (`deps.py:224`), before the cookie path (`deps.py:226`)**, and before the Cognito path (`deps.py:255`). (The line-199 number refers to the enclosing `get_authenticated_user` function definition; the actual insertion point is between lines 224 and 226 in the current file.)

```python
if S.oauth_provider_enabled:
    auth_header = request.headers.get("authorization", "")
    if auth_header.lower().startswith("bearer "):
        candidate = auth_header.split(" ", 1)[1].strip()
        try:
            payload = jwt.decode(
                candidate,
                S.ui_access_token_secret,
                algorithms=["HS256"],
                options={"verify_exp": True},
            )
        except jwt.ExpiredSignatureError:
            raise HTTPException(401, "oauth_token_expired")
        except jwt.PyJWTError:
            payload = None
        if payload and payload.get("token_type") == "access" and payload.get("client_id"):
            # This is an OAU-002 access token.
            owner_sub = str(payload.get("sub") or "").strip()
            client_id = str(payload.get("client_id") or "").strip()
            if not owner_sub or not client_id:
                raise HTTPException(401, "invalid_oauth_token")
            # Re-check consumer enabled (OAU-005: disable kills existing tokens instantly).
            consumer = get_consumer(client_id)  # from app.services.oauth_consumers
            if not consumer or not consumer.get("enabled"):
                raise HTTPException(401, "oauth_consumer_disabled")
            # Resolve owner's role from T.users (same as api-key principal branch, deps.py:215).
            try:
                user_item = T.users.get_item(Key={"user_sub": owner_sub}).get("Item") or {}
                role = normalize_role(user_item.get("role"))
            except Exception:
                role = Role.USER
            role = enforce_root_role_invariant(user_sub=owner_sub, role=role)
            _enforce_not_banned(user_sub=owner_sub, role=role)
            # Stash granted scope for OAU-004 enforcement.
            request.state.oauth_scope = str(payload.get("scope") or "")
            request.state.oauth_client_id = client_id
            return AuthenticatedUser(
                sub=owner_sub, role=role,
                tenant_id=_request_tenant_id(request),
            )
```

**Important**: the bearer-token presence check uses `payload.get("token_type") == "access"` as a discriminator. A token without `token_type` (a Cognito JWT, or a legacy `ui_access_token` used incorrectly as a Bearer) will have `payload=None` or a missing field and will fall through to the Cognito branch unchanged. This means the new branch cannot interfere with existing Cognito bearer callers.

## 5. Detailed Behavior & Edge Cases

### 5.1 Authorization-code grant — step-by-step

1. **Browser arrives at `GET /oauth/authorize`** with `response_type=code`, `client_id`, `redirect_uri`, `scope`, `state`, `code_challenge` (BASE64URL-SHA256 of `code_verifier`), `code_challenge_method=S256`. The user is authenticated via `require_ui_session` (cookie path). If the user is not logged in, the session dep returns 401 — the `/oauth/authorize` endpoint does not redirect to a login page (the consumer app is responsible for sending authenticated users).

2. **Validation sequence** (errors redirect with `error=…` to `redirect_uri` except fatal URI errors which return 400 JSON):
   - Consumer exists and `enabled=True`.
   - `redirect_uri` exact-match in consumer's `redirect_uris`.
   - `code_challenge_method == "S256"` (plain is intentionally unsupported per RFC 7636 §4.2 security note).
   - `requested_scopes ⊆ consumer.allowed_scopes`.
   - `code_challenge` non-empty for public (`is_confidential=False`) clients.

3. **Code issuance**: `code_id = secrets.token_hex(16)`. The `CODE#{code_id}` row is written to DDB with `ttl_epoch = now_ts() + S.oauth_code_ttl_seconds` (default 60). The opaque code returned to the consumer is `mint_ws_token`-style HMAC: `BASE64URL(json({"code_id": code_id, "exp": now+60})) + "." + BASE64URL(HMAC-SHA256(payload))` using `S.ws_token_secret` (`crypto.py:35–42`). The signed envelope prevents any enumeration or forgery of `code_id` values — even a valid DDB row is unreachable without the correct signature.

4. **302 redirect**: `{redirect_uri}?code={signed_code}&state={state}`.

### 5.2 Token exchange — step-by-step

1. Consumer POSTs `grant_type=authorization_code` with `code`, `redirect_uri`, `client_id`, `code_verifier`, `client_secret` (if confidential) to `POST /oauth/token`.

2. **Load consumer**: `get_consumer(client_id)` → 400 `invalid_client` if missing or disabled.

3. **Verify client_secret** (confidential clients only): `verify_client_secret(client_id, client_secret)` (OAU-001 service). The secret comparison must use `hmac.compare_digest` on the `api_key_hash` digests (constant-time). Note: `api_keys.py:434` uses plain `!=` comparison — `verify_client_secret` must be implemented with `hmac.compare_digest` to avoid the timing side-channel present in the api_key verification path. Wrong secret → 400 `invalid_client`.

4. **Verify code signature**: `verify_ws_token(code)` (`crypto.py:44–61`). Bad signature or expired envelope → 400 `invalid_grant`. Extract `code_id` from the verified payload.

5. **Single-use consume**: `update_item` on `CODE#{code_id}` with `ConditionExpression="attribute_exists(client_id) AND attribute_exists(sk) AND attribute_not_exists(consumed_at)"`, `UpdateExpression="SET consumed_at = :now"` (`provider_oauth.py:204–215` pattern). `ConditionalCheckFailedException` → 400 `invalid_grant` with description `"authorization code already used"`. (The `attribute_exists(client_id)` guard ensures the row exists before the single-use check, matching the full three-clause form at `provider_oauth.py:204`.)

6. **Cross-check**: `redirect_uri` must match code row's stored `redirect_uri`. `client_id` must match code row's `client_id`. Mismatch → 400 `invalid_grant`.

7. **PKCE verify**: `_pkce_verify(code_verifier, code_row.code_challenge)` — compute `BASE64URL(SHA256(code_verifier.encode("ascii")))` using `crypto.py:27` `b64url(hashlib.sha256(code_verifier.encode("ascii")).digest())` and compare with `hmac.compare_digest` (constant-time). Mismatch → 400 `invalid_grant`.

8. **Mint access token**: `_mint_oauth_access_token(owner_user_sub, client_id, granted_scopes, ttl_seconds=S.oauth_access_token_ttl_seconds)`. Payload: `{"sub": owner_user_sub, "client_id": client_id, "scope": granted_scopes, "token_type": "access", "iss": S.public_base_url, "exp": now+ttl, "iat": now}`.

9. **Issue refresh token** (when `"offline_access"` is in `granted_scopes` or `S.oauth_always_issue_refresh_token=True`): `refresh_plaintext = secrets.token_urlsafe(32)`, write `GRANT#{grant_id}` row with `refresh_token_hash = api_key_hash(refresh_plaintext)` and `ttl_epoch = now_ts() + S.oauth_refresh_token_ttl_seconds`. Return `refresh_token = f"oar_{grant_id}.{refresh_plaintext}"` (mirrors the `ak_` prefix convention from `api_keys.py:166`).

10. Return `OAuthTokenResponse`.

### 5.3 Refresh-token rotation

1. POST `grant_type=refresh_token` with `refresh_token`, `client_id`, `client_secret` (if confidential).
2. Parse `refresh_token` format `oar_{grant_id}.{plaintext}`.
3. `get_item(PK=client_id, SK=GRANT#{grant_id})` → 400 `invalid_grant` if missing, `revoked=True`, or TTL expired (`ttl_epoch <= now_ts()`).
4. `api_key_hash(plaintext) == stored refresh_token_hash` → 400 `invalid_grant` on mismatch.
5. Re-check consumer `enabled=True` → 400 `invalid_client` if not.
6. **Rotate**: generate new `refresh_plaintext2`, update row with new `refresh_token_hash = api_key_hash(refresh_plaintext2)` + `rotated_at = now_ts()`. The old plaintext stops working immediately (single stored hash).
7. Return new `access_token` + new `refresh_token`.

### 5.4 DirectLogin (flag-gated)

When `S.oauth_provider_directlogin_enabled` is False, `grant_type=password` returns 400 `unsupported_grant_type` without inspecting any other field. When the flag is on:

1. Require `client_secret` (always confidential for DirectLogin).
2. Verify `client_secret` via `verify_client_secret`.
3. Call `_verify_local_password(username, password)` (`deps.py:167–196`) — returns `user_sub` or `None`. `None` → 400 `invalid_grant` with description `"invalid credentials"`.
4. Validate `scope ⊆ consumer.allowed_scopes`.
5. Mint access token + optional refresh grant. No auth code row is written (no redirect involved).

### 5.5 Consumer-disabled revocation

At every path through the auth layer and the token endpoint, `get_consumer(client_id)` is called and `enabled` is checked. There is no need to enumerate or revoke individual `GRANT#` rows: disabling a consumer (OAU-005) causes every subsequent access-token verification and refresh attempt to fail with 401 `oauth_consumer_disabled`. Existing access tokens (short-lived, ~15 min) will expire on their own; the disabled check ensures no new access is possible immediately after disable.

### 5.6 Edge cases and error paths

| Condition | Response |
|---|---|
| `response_type != "code"` | redirect `error=unsupported_response_type` |
| `code_challenge_method != "S256"` | redirect `error=invalid_request` |
| redirect_uri contains fragment (`#`) | 400 JSON `invalid_request` (RFC 6749 §3.1.2) |
| Requested scope is empty string | redirect `error=invalid_scope` |
| Code TTL elapsed before exchange (`exp` in signed envelope) | 400 `invalid_grant` — the `verify_ws_token` expiry check (`crypto.py:57`) fires before DDB read |
| Code exchanged after DDB TTL removes the row | 400 `invalid_grant` (get_item returns empty; treat as missing) |
| Refresh token row TTL-expired (row still present but `ttl_epoch <= now`) | 400 `invalid_grant` |
| Public client sends `client_secret` | accepted silently (per RFC 6749 §2.1, public clients may have a secret but it is not used for authentication) |
| `scope` param on `authorization_code` token exchange | ignored; granted scope comes from the code row |
| `nonce` on `/authorize` | stored on `CODE#` row; returned in `id_token` by OAU-003 when `openid` scope is present; no effect in OAU-002 alone |

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 dev/prod parity

There is **no `if S.dev_mode:` branch** in any OAU-002 code path. Both the authorization-code flow and the token endpoint read and write `T.oauth_consumers` (DynamoDB Local in dev, real DynamoDB in prod). JWT signing uses `S.ui_access_token_secret` in both environments. PKCE verification uses `hashlib.sha256` and `hmac.compare_digest` in both. The `_verify_local_password` path (DirectLogin) reads `T.users` in both. The only difference between dev and prod is the DynamoDB endpoint URL (`DDB_ENDPOINT_URL`), which is the existing infrastructure-level distinction that all other DDB-backed features share.

### Idempotency

- **Auth-code rows** are single-use by design. A replayed code returns a deterministic 400 `invalid_grant` regardless of how many times it is replayed — the `attribute_not_exists(consumed_at)` conditional is the atomic guard.
- **Token endpoint** is not idempotent (each valid exchange produces a new access token), which is standard for OAuth2 token endpoints.
- **Refresh-token rotation** is also not idempotent — each call consumes the old refresh token and issues a new one.

### Security properties

- **Code binding**: the signed code envelope (`mint_ws_token` scheme, `crypto.py:35–42`) binds the code to `S.ws_token_secret`. A code cannot be forged without the server secret; it cannot be tampered with (HMAC covers the payload). The DDB row provides the single-use guarantee.
- **PKCE S256**: `code_challenge_method=plain` is not accepted. `plain` is insecure (the verifier is the challenge, so an intercepted code carries the verifier implicitly). Only `S256` is implemented.
- **No token in query string**: the access token is returned in the JSON response body, never in a URL query parameter or fragment. The authorization code is in the redirect URL (as required by OAuth2) but it is short-lived (60s) and single-use.
- **State parameter**: the `state` value from `/authorize` is echoed back in the redirect without modification. The consumer is responsible for validating state (CSRF protection for the consumer). testlogon does not validate state — it is opaque.
- **Constant-time comparisons**: `hmac.compare_digest` must be used for `client_secret` verification in `verify_client_secret` (OAU-001 service), for refresh-token hash comparison, and for PKCE verification. **Important**: the existing `api_keys.py:434` uses a plain `!=` comparison on sha256 hex digests — `verify_client_secret` must NOT copy this pattern; it must use `hmac.compare_digest(api_key_hash(provided_secret), stored_hash)` explicitly to close the timing side-channel.
- **No money involvement**: OAU-002 does not move money, modify balances, write ledger entries, or call any billing function. The spec is therefore free of money-safety concerns at this layer. Money-gated operations (billing charge paths) remain protected by their own `_fraud_gate` (`app/routers/billing.py`) and SCA (`app/services/mfa.py`) guards — an OAuth token that reaches a billing endpoint is subject to those guards exactly as a cookie session would be (since `get_authenticated_user` returns an equivalent `AuthenticatedUser`).

## 8. Backward Compatibility & Migration

### Zero migration required

OAU-002 is purely additive. With `OAUTH_PROVIDER_ENABLED=false`:
- `GET /oauth/authorize` does not exist (404) — no existing client calls it.
- `POST /oauth/token` does not exist (404).
- `get_authenticated_user` (`deps.py:199`) gains a new early-exit branch, but the branch is guarded by `if S.oauth_provider_enabled:` and by `payload.get("token_type") == "access" and payload.get("client_id")`. Existing Cognito JWTs do not carry `token_type="access"` with a `client_id` claim, so they fall through to the Cognito branch unchanged. Existing `ui_access_token` cookie JWTs are never sent as `Authorization: Bearer` headers by the browser SPA.

### DynamoDB table

The `oauth_consumers` table (`scripts/local-ddb-init.py`) is created by OAU-001 at `just up` / `just restart` time. The two new row types (`CODE#`, `GRANT#`) use the same PK/SK as the `META` row — no `UpdateTable` is required. No backfill is required (there are no pre-existing code or grant rows).

### Enabling in production

The production rollout sequence is:
1. Deploy backend with new code (routers registered but `OAUTH_PROVIDER_ENABLED=false`).
2. Verify `oauth_consumers` DynamoDB table exists (created by OAU-001 deployment).
3. Set `OAUTH_PROVIDER_ENABLED=true` in the environment and redeploy (or use an in-place env update + `just restart` equivalent).

No database migration, no backfill, no downtime window required.

## 10. Open Questions / Assumptions

1. **Consent screen**: the `GET /oauth/authorize` endpoint currently auto-consents for any authenticated user. A proper consent screen (showing the consumer's name, requested scopes, and Accept/Deny buttons) is deferred to a follow-up ticket. The auto-consent is safe for first-party consumer apps and for the initial OBP integration; it should be addressed before publishing the authorize endpoint to untrusted third parties.

2. **`ws_token_secret` for code signing**: the code envelope reuses `S.ws_token_secret`. If this secret rotates, in-flight authorization codes (max 60s) would be invalidated. This is acceptable behavior (the user would need to restart the flow). An alternative is to use a dedicated `OAUTH_CODE_SIGNING_SECRET` setting — decision deferred; the current approach minimizes new secret management.

3. **PKCE for confidential clients**: RFC 7636 originally positioned PKCE as a public-client mechanism, but RFC 9700 recommends it for all clients. OAU-002 requires PKCE for public clients and accepts (but does not require) PKCE for confidential clients. Requiring it universally is recommended before production rollout.

4. **Scope string format**: scopes are space-delimited strings (OAuth2 standard). The `API_KEY_ROUTE_SCOPE_REGISTRY` uses colon-namespaced strings (`messager:read`, `filemanager:write`). The `openid`, `profile`, `email`, and `offline_access` OIDC/OAuth2 standard scopes are handled as pass-through by OAU-002 and are meaningful only to OAU-003. The union of all `required_scopes` values in `API_KEY_ROUTE_SCOPE_REGISTRY` should be published as `scopes_supported` in the OAU-003 discovery doc.

5. **Rate limiting on `/authorize` and `/token`**: OAU-002 does not add a per-consumer rate limit on these endpoints. The `_bucket_limit` helper (`rate_limit.py:60`) is available; whether to apply it and at what threshold is left to OAU-004 scope enforcement work.

6. **Token revocation endpoint (`POST /oauth/revoke`)**: RFC 7009 defines a standard revocation endpoint. OAU-002 does not implement it. Refresh grants can be revoked by consumer-disable (OAU-005); per-token revocation via a `POST /oauth/revoke` endpoint is deferred.
