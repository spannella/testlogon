# VEW-002 — Grant / revoke a View to a grantee + unauthenticated public view

**Ticket type:** Feature  
**Priority:** P1  
**Estimate:** 3 days  
**Feature flag:** `account_views_enabled` (env `ACCOUNT_VIEWS_ENABLED`, default OFF)  
**Depends on:** VEW-001 (View entity, `account_views` table, `VIEW_FIELD_GRANTS`, `create_view` / `get_view` service)

---

## 1. Summary & Goal

VEW-002 makes a View *grantable*: the resource owner extends a named view (defined in
VEW-001) to a specific grantee user, creating a `VIEWGRANT` row in the `account_views`
table that travels through a `pending → active → revoked` lifecycle identical to the
`delegates.py` delegate-invite pattern. When the grantee holds an active grant, the
`resolve_active_grant` primitive returns the effective `grants` map; VEW-003 consumes this to
shape the resource response.

The ticket also delivers the **unauthenticated public view path**: an owner may mint a
signed, time-limited, revocable token (using the same HMAC scheme as cart-recovery links,
`app/services/cart_reminders.py:150-165`) for any view whose `preset == "public"` or
`is_public=True`, and the resulting URL at `/ui/views/public/{token}` is reachable without
any session or Bearer token. This implements OBP's public-view primitive — a read-only
field-level snapshot of a financial resource shared as a plain link.

The concrete goals are:

- Grant, accept/decline, and revoke view access with full audit trail.
- Reverse lookup ("views shared with me") via a `by-grantee` GSI — exact mirror of
  `delegates.py:216` `list_managed_creators`.
- Mint and verify public-view signed links; support owner-initiated revocation of a live link
  via a consumed-marker row.
- Expose `resolve_active_grant(grantee_sub, resource_type, resource_id, view_id)` as the
  single authorization primitive consumed by VEW-003.
- All paths flag-gated default-OFF; public endpoint registered in `app/main.py` next to the
  other unauthenticated public routers.

## 2. Context & Current State

### 2.1 Existing delegation pattern — `app/services/delegates.py`

The coarse-grained delegate system (`app/services/delegates.py`) is the direct structural
predecessor of VEW-002. Its complete grant/revoke/accept lifecycle is already implemented and
tested, and VEW-002 mirrors every aspect of it:

| delegates.py concept | VEW-002 equivalent |
|---|---|
| `CREATOR#{creator_id}` partition key | `RESOURCE#{resource_type}#{resource_id}` |
| `DELEGATE#{delegate_id}` sort key | `VIEWGRANT#{grantee_sub}#{view_id}` |
| `status: pending/active` | same — `pending/active/revoked` |
| `GSI1PK=DELEGATE#{delegate_id}`, `GSI1SK=accepted_at` | `GSI1PK=GRANTEE#{grantee_sub}`, `GSI1SK=accepted_at` |
| `respond_to_invite` (`delegates.py:112`) | `respond_to_view_grant` |
| `revoke_delegate` (`:196`) | `revoke_view_grant` |
| `list_managed_creators` (`:216`) — GSI1 reverse lookup | `list_views_shared_with_me` |
| `_require_not_self` (`:359`), `_require_not_already_delegate` (`:364`) | same guards |
| `get_creator_settings` require_acceptance (`:273`) | per-resource `require_acceptance` |
| `_write_audit` (`:386`) | same in-table `AUDIT#` rows |

The key **net-new dimension** is: a VIEWGRANT row holds a `view_id` reference rather than a
flat permission list, and a single grantee may hold multiple distinct views over one resource
(`sk=VIEWGRANT#{grantee_sub}#{view_id}`).

### 2.2 Signed-token pattern — `app/services/cart_reminders.py`

The public-link token format is identical to the cart-recovery link (CLAUDE.md cart-recovery
note): a JSON payload signed with HMAC-SHA256, base64url-encoded as
`b64url(payload).b64url(sig)` (`cart_reminders.py:150-165`). The signing secret resolver

## 3. Data Model

All VEW-002 data shares the **`account_views` table** defined by VEW-001. No new table is
introduced. The table is defined in `scripts/local-ddb-init.py` by VEW-005 with:

```
TableDef(
    S.account_views_table_name or "account_views",
    partition_key="pk",
    sort_key="sk",
    gsi=[
        {
            "index_name": "by-owner",
            "partition_key": "GSI1PK",
            "sort_key": "GSI1SK",           # numeric created_at
        },
        {
            "index_name": "by-grantee",     # NEW in VEW-002
            "partition_key": "GSI2PK",
            "sort_key": "GSI2SK",           # numeric accepted_at
        },
    ],
    attr_types={"GSI1SK": "N", "GSI2SK": "N"},
)
```

The `attr_types={"GSI1SK": "N", "GSI2SK": "N"}` declaration is mandatory to prevent
`ValidationException` when querying with integer values (CLAUDE.md "DynamoDB numeric GSI
sort keys" gotcha).

### 3.1 VIEWGRANT row

```
pk  = "RESOURCE#{resource_type}#{resource_id}"
sk  = "VIEWGRANT#{grantee_sub}#{view_id}"
```

Attributes:

| Attribute | Type | Notes |
|---|---|---|
| `grant_id` | S | `uuid4().hex` |
| `view_id` | S | FK to `VIEW#{view_id}` row (VEW-001) |
| `grantee_sub` | S | user receiving the grant |
| `owner_sub` | S | resource owner who granted |
| `resource_type` | S | `"wallet"` / `"ledger_account"` / `"payout_destination"` |
| `resource_id` | S | |
| `status` | S | `"pending"` / `"active"` / `"revoked"` |
| `invited_at` | N | `now_ts()` at grant creation |
| `accepted_at` | N | `now_ts()` on acceptance; `0` while pending |
| `updated_at` | N | last mutation timestamp |
| `GSI2PK` | S | `"GRANTEE#{grantee_sub}"` — reverse-lookup GSI key |
| `GSI2SK` | N | `accepted_at` value (0 while pending; set on accept) |

The `sk` encodes both `grantee_sub` and `view_id`, allowing one grantee to hold multiple
distinct views over the same resource without collision. The owner can inspect all grants for
a resource via a `begins_with("VIEWGRANT#")` query on the main index.

### 3.2 Public-link revocation row

```
pk  = "PUBLIC_REVOKED#{jti}"
sk  = "META"
```

Attributes: `jti`, `view_id`, `resource_type`, `resource_id`, `revoked_at` (N),
`revoked_by_sub`. Written by `revoke_public_link`; checked by `resolve_public_view` before
returning data. Uses the same conditional-`put_item`-with-`attribute_not_exists(pk)` pattern
as `_mark_token_consumed` in `cart_reminders.py:198-211`.

### 3.3 In-table audit rows (shared with VEW-001)

```
pk  = "RESOURCE#{resource_type}#{resource_id}"
sk  = "AUDIT#{ts:013d}#{event_id}"
```

Written by `_write_audit(resource_type, resource_id, actor_sub, action, ...)` for every
grant/revoke/accept mutation. Read newest-first by
`get_grant_audit_log(resource_type, resource_id)`. Mirrors `delegates.py:386-409`.
Note: `delegates.py` uses no zero-padding (`sk = f"AUDIT#{ts}#{event_id}"`); VEW-002 (following
VEW-001) intentionally introduces the `{ts:013d}` zero-padding for correct lexicographic sort
on the range key — this is a deliberate deviation from the delegate pattern.

### 3.4 GSI summary

| GSI name | PK field | SK field | SK attr_type | Purpose |
|---|---|---|---|---|
| `by-owner` (VEW-001) | `GSI1PK = OWNER#{owner_sub}` | `GSI1SK = created_at` | N | List views an owner defined |
| `by-grantee` (VEW-002) | `GSI2PK = GRANTEE#{grantee_sub}` | `GSI2SK = accepted_at` | N | "Views shared with me" |

Both `GSI1SK` and `GSI2SK` are numeric; both must appear in `attr_types` in
`local-ddb-init.py`.

## 4. API / Service Design

### 4.1 Service additions — `app/services/account_views.py`

All functions live in the same module started by VEW-001. No new file needed.

#### grant_view

```python
def grant_view(
    owner_sub: str,
    resource_type: str,
    resource_id: str,
    view_id: str,
    grantee_sub: str,
) -> dict:
```

Steps:
1. `_require_not_self(owner_sub, grantee_sub)` — 400 if identical (mirrors `delegates.py:359`).
2. `get_view(resource_type, resource_id, view_id)` — 404 if view absent.
3. `_assert_owns_resource(owner_sub, resource_type, resource_id)` — 403 if not owner.
4. `_require_not_already_granted(resource_type, resource_id, view_id, grantee_sub)` — `T.account_views.get_item(Key={"pk":..., "sk":...})`; 409 if row exists with `status != "revoked"`.
5. Read `_get_resource_settings(owner_sub, resource_type, resource_id)` for `require_acceptance` flag.
6. Build VIEWGRANT item (§3.1); `status = "pending"` if `require_acceptance`, else `"active"` + `accepted_at = now_ts()` + `GSI2SK = now_ts()`.
7. `T.account_views.put_item(Item=item)`.
8. `_write_audit(resource_type, resource_id, owner_sub, "view_granted", grantee_sub, {"view_id": view_id})`.
9. `audit_event("account_view.granted", owner_sub, resource_type=resource_type, resource_id=resource_id, view_id=view_id, grantee_sub=grantee_sub)`.
10. Return the VIEWGRANT item.

#### create_public_view_link

```python
def create_public_view_link(
    owner_sub: str,
    resource_type: str,
    resource_id: str,
    view_id: str,
    *,
    ttl_days: int | None = None,
) -> dict:  # {url, token, expires_at}
```

Steps:
1. `_assert_owns_resource(owner_sub, resource_type, resource_id)` — 403.
2. `get_view(resource_type, resource_id, view_id)` — 404 if absent.
3. Guard: `view["preset"] == "public" or view.get("is_public")` — 400 "view not public" otherwise. Never auto-public.
4. Resolve TTL: `ttl_days or S.account_view_public_link_ttl_days` (default 7, from `settings.py`, same pattern as `cart_recovery_link_ttl_days`, `settings.py:830`).
5. Build payload: `{"resource_type": resource_type, "resource_id": resource_id, "view_id": view_id, "owner_sub": owner_sub, "jti": uuid4().hex, "exp": now_ts() + ttl_days * 86400, "iat": now_ts()}`.
6. Sign with `_public_link_secret()` (resolves `S.account_view_public_secret or S.ui_access_token_secret`) using the same HMAC-SHA256 / `b64url(raw).b64url(sig)` scheme from `cart_reminders.py:150-165` and `app/core/crypto.py:35-42`.
7. URL: `f"{S.public_base_url}/ui/views/public/{token}"` — same `S.public_base_url` used by `generate_recovery_link` (`cart_reminders.py:223`).
8. `audit_event("account_view.public_link_created", owner_sub, view_id=view_id, expires_at=expires_at)`.
9. Return `{"url": url, "token": token, "expires_at": expires_at}`.

#### resolve_public_view

```python
def resolve_public_view(token: str) -> dict:
    # {resource_type, resource_id, view_id, grants, owner_sub, exp}
```

Steps:
1. Split `token` on `.`; `raw = b64url_decode(parts[0])`; recompute HMAC; `hmac.compare_digest` — 403 on mismatch.
2. Decode payload; check `exp >= now_ts()` — 400 "token expired".
3. Check revocation: `T.account_views.get_item(Key={"pk": f"PUBLIC_REVOKED#{payload['jti']}", "sk": "META"})` — 403 if row exists.
4. `get_view(resource_type, resource_id, view_id)` — 404 if view was deleted since link was minted.
5. Re-verify `view["preset"] == "public" or view.get("is_public")` — 403 if view was un-published after link creation.
6. Return payload + `grants: view["grants"]`. Consumed by VEW-003 projector.

#### revoke_public_link

```python
def revoke_public_link(
    owner_sub: str,
    token: str,
) -> None:
```

1. Verify token signature and expiry (same as `resolve_public_view` steps 1-2; a revoke of an already-expired token is still accepted — the row prevents replay if someone cached it before expiry).
2. Assert `payload["owner_sub"] == owner_sub` — 403.
3. Conditional `put_item` with `ConditionExpression="attribute_not_exists(pk)"` on the `PUBLIC_REVOKED#{jti}` row. If `ConditionalCheckFailedException`: already revoked, return idempotently (no error).
4. `audit_event("account_view.public_link_revoked", owner_sub, view_id=payload["view_id"])`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Grant lifecycle

**Owner grants a view:**
- `require_acceptance=True` (the default, mirroring `delegates.py:79`): creates a `pending` row; `GSI2SK=0` so the grantee appears in their "views shared with me" GSI query but `status != "active"`, and `resolve_active_grant` returns `None` until acceptance.
- `require_acceptance=False`: creates an `active` row immediately; `GSI2SK=accepted_at=now_ts()`.

**Grantee responds:**
- Accept: `update_item` sets `status="active"`, `accepted_at=now_ts()`, `GSI2SK=now_ts()`. `resolve_active_grant` now returns the row.
- Decline: `delete_item`. The owner sees no trace (row deleted); audit trail records the decline.
- Responding to a non-pending row (already-active or revoked): `400` "grant is not pending".
- Only the grantee (`session.user_sub == grantee_sub`) may respond; the owner calling respond gets `403`.

**Owner revokes:**
- Immediate effect: row deleted. `resolve_active_grant` returns `None` on next call.
- Revoking a non-existent grant: `404` "grant not found".
- Revoking a pending grant is allowed — owner withdraws uninvited invitation.

**Self-grant guard:** `_require_not_self` at `delegates.py:359` is mirrored. An owner attempting `grant_view(owner_sub=X, grantee_sub=X, ...)` receives `400`.

**Duplicate-grant guard:** If a `VIEWGRANT#{grantee_sub}#{view_id}` row already exists with `status != "revoked"` (pending or active), return `409`. If `status == "revoked"` the slot is recycled: `put_item` overwrites the revoked row with a new `pending` grant (idempotent re-invite after revocation).

**Multi-view per grantee:** A grantee may hold the `accountant` view and the `auditor` view simultaneously over the same resource — they are separate `VIEWGRANT#{grantee_sub}#<view_id_A>` and `VIEWGRANT#{grantee_sub}#<view_id_B>` rows. `resolve_active_grant` is called with a specific `view_id` so there is no ambiguity.

**View deleted while grant is active:** If the owner deletes a view (VEW-001 `delete_view`), the cascade-delete of VIEWGRANT rows means `resolve_active_grant` returns `None` for any existing grants on that view. VEW-003's read endpoint receives `None` and returns `403`.

### 5.2 Public-link lifecycle

**Minting:** Only views with `preset=="public"` or `is_public=True` are linkable. An owner attempting to mint a link for an `auditor`-preset view receives `400`. The `is_public` flag is an owner opt-in attribute set at view creation or update (VEW-001 `ViewUpdateIn`); it is never set automatically.

**Token format:** `b64url(json_payload).b64url(hmac_sha256_sig)`. The payload encodes `resource_type`, `resource_id`, `view_id`, `owner_sub`, `jti` (unique per mint), `exp`, `iat`. Changing any byte of the base64 payload invalidates the HMAC — tamper-evident.

**Token binding:** The token binds to a specific `(resource_type, resource_id, view_id)` triple. A token for wallet X cannot be used to read wallet Y even if the attacker has both — the view resolution step calls `get_view(resource_type, resource_id, view_id)` which must return a row matching the token's own fields.

**Expiry:** Checked against `now_ts()` in `resolve_public_view`. An expired token returns `400` — distinct from a tampered token (`403`) so callers can distinguish "needs re-mint" from "attack".

**Revocation:** Owner calls `DELETE /ui/views/public/{token}`. A `PUBLIC_REVOKED#{jti}` sentinel row is written. Subsequent calls to `resolve_public_view` with the same token read this row and return `403`. The sentinel lives in the `account_views` table (same single-table pattern). No TTL is set on the sentinel — even if the token has naturally expired, the sentinel is retained indefinitely as a tamper-evidence record.

**No re-mint on revoke:** Revoking does not prevent the owner from minting a new link. Each new mint produces a new `jti`; the old sentinel only blacklists the old `jti`.

**Concurrent revokes:** `ConditionExpression="attribute_not_exists(pk)"` ensures exactly one writer wins. A second revoke attempt (e.g., client retry) receives `ConditionalCheckFailedException` which the service catches and returns `204` idempotently — same as the cart-recovery consumed-marker pattern (`cart_reminders.py:198-211`).

**View un-published after link minted:** If the owner updates the view to remove `is_public` (or changes the preset away from `public`) after a link was minted, `resolve_public_view` re-checks `view["preset"] == "public" or view.get("is_public")` at step 5 and returns `403`. This is the safe direction: existing links stop working when the owner narrows the view's public status.

### 5.3 Sparse GSI pagination

`list_views_shared_with_me` queries the `by-grantee` GSI. Applying a `FilterExpression` for `status=="active"` does NOT reduce the DynamoDB page size before filtering (CLAUDE.md "DDB FilterExpression doesn't reduce page size"). The loop must drain `LastEvaluatedKey`:

```python
results = []
lek = decode_cursor(cursor)
while True:
    kwargs = {
        "IndexName": "by-grantee",
        "KeyConditionExpression": Key("GSI2PK").eq(f"GRANTEE#{grantee_sub}"),
        "FilterExpression": Attr("status").eq("active"),
        "Limit": limit,
    }
    if lek:
        kwargs["ExclusiveStartKey"] = lek
    resp = T.account_views.query(**kwargs)
    results.extend(resp.get("Items", []))
    lek = resp.get("LastEvaluatedKey")
    if not lek or len(results) >= limit:
        break
next_cursor = encode_cursor(lek) if lek else None
```

### 5.4 `require_acceptance` per resource

Stored in a `SETTINGS` row on the `account_views` table:
`pk=RESOURCE#{resource_type}#{resource_id}`, `sk=SETTINGS`. Default: `{"require_acceptance": True}`.
`_get_resource_settings` returns defaults if the row is absent (mirrors `get_creator_settings` in `delegates.py:273-292`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 dev/prod parity

All persistence goes through `T.account_views` (`_FloatSafeTable`), which routes to
DynamoDB Local (port 8001) in dev and real DynamoDB in prod. There is **no `if S.dev_mode`
branch** in any VEW-002 service function. The signed-token logic (`_public_link_secret()`,
HMAC-SHA256) is identical in both environments — the only difference is which secret value
populates `ACCOUNT_VIEW_PUBLIC_SECRET` (empty in dev → falls back to
`UI_ACCESS_TOKEN_SECRET`; provisioned explicitly in prod). Audit writes go to `T.alerts` via
`audit_event` — DynamoDB Local in dev, real DynamoDB in prod, same code path.

### 7.2 Idempotency

| Operation | Idempotency behavior |
|---|---|
| `grant_view` | 409 if grant row exists and `status != "revoked"`; overwrites if revoked |
| `respond_to_view_grant(accept)` | 400 if not pending (already responded) |
| `revoke_view_grant` | 404 if row absent (already revoked/deleted) |
| `revoke_public_link` | `ConditionalCheckFailedException` caught → 204 (idempotent) |
| `create_public_view_link` | Each call mints a new `jti` — not idempotent by design; owner may have multiple live links |

### 7.3 Security

**No money movement in VEW-002.** This ticket grants/revokes field-level read access and
mints view links. There is no payment, wallet mutation, ledger entry, or payout in VEW-002.
The MONEY-SAFETY checklist (TXR/PAY/ACC primitives, SCA gates, fraud gate, settle_or_reverse)
does not apply to this ticket. VEW-003 (the enforcement layer, a separate ticket) reads
financial resource data through the projection filter but does not mutate balances.

**Token security:**
- The `jti` is `uuid4().hex` (128 bits of randomness) — not guessable.
- HMAC-SHA256 over the full JSON payload: any single-bit mutation invalidates the signature.
- `hmac.compare_digest` used throughout — constant-time; no timing-based forgery.
- Token binds to `(resource_type, resource_id, view_id, owner_sub)` — a stolen token for
  resource A cannot be used for resource B.
- The `is_public` / `preset=="public"` guard on `create_public_view_link` ensures a
  carelessly shared `auditor` or `accountant` view link cannot be created — the owner must
  explicitly mark a view public.

**CSRF:** All non-GET authenticated endpoints enforce `x-csrf-token` via the standard
`require_ui_session` CSRF check. The unauthenticated public endpoint (`GET /ui/views/public/{token}`)
is a safe method (read-only GET) and therefore CSRF-exempt by definition. Bearer-auth callers
skip CSRF per platform convention.

**Ownership re-validation:** `create_public_view_link` calls `_assert_owns_resource` before
minting. Even if the owner's account is later downgraded, an in-flight public link continues
to work until expiry or explicit revocation — this is by design (the link was legitimately
minted; revocation is the owner-controlled kill switch).

**Grantee authorization boundary:** `resolve_active_grant` is a point-read keyed on
`(resource_type, resource_id, grantee_sub, view_id)`. Cross-resource access (grantee for
resource A trying to read resource B) is structurally impossible — the `pk` encodes the
resource identity.

## 8. Backward Compatibility & Migration

### 8.1 Additive only

VEW-002 adds new rows (`VIEWGRANT#`, `PUBLIC_REVOKED#`, `AUDIT#`) and new endpoints to the
`account_views` table and router. No existing table schema, existing endpoint, existing service
function, or existing Pydantic model is modified. `delegates.py`, `billing_shared.py`,
`creator_payouts.py`, and all other existing services are read-only references — nothing is
forked or modified.

### 8.2 Flag-off restores prior behavior

With `ACCOUNT_VIEWS_ENABLED=false` (the default), `app/main.py` does not import the
`account_views` module. All `/ui/views/*` paths return 404. If the flag is later toggled ON
and then OFF again, existing `VIEWGRANT` rows in DynamoDB are retained but unreachable — no
data loss, no corruption.

### 8.3 New GSI on existing table

VEW-002 adds `by-grantee` (GSI2) to the `account_views` table. In dev, `just restart` drops
and recreates the table with the new GSI (from `local-ddb-init.py`). In production, `by-grantee`
is added via a `UpdateTable` + asynchronous backfill before the VEW-002 router is deployed.
The backfill populates `GSI2PK`/`GSI2SK` on any pre-existing VIEWGRANT rows. During the
backfill window `list_views_shared_with_me` may return incomplete results — acceptable given
the feature is default-OFF and the backfill is fast on a near-empty table.

### 8.4 No breaking change to VEW-001 service

`delete_view` (VEW-001) cascade-deletes VIEWGRANT rows. The cascade is implemented as a
`begins_with("VIEWGRANT#")` query on the resource partition followed by batch-delete. This
means VEW-001 already anticipates VIEWGRANT rows — no interface change when VEW-002 lands.

## 10. Open Questions / Assumptions

1. **Multiple simultaneous public links.** The spec allows an owner to mint multiple live
   public links for the same view (each has a unique `jti`). The owner can revoke each
   individually. Is a "revoke all public links for view" bulk operation needed? Assumption:
   not for V1; a future VEW-006 can scan `PUBLIC_REVOKED#*` prefixes or maintain a link
   registry.

2. **Grant limit per resource.** VEW-001 defines `account_views_max_per_resource` (default
   25) for the number of *view definitions*. Should there be a separate limit on the number of
   *grantees* per view? Assumption: no hard limit on grantees in V1 (the list endpoint is
   paginated); subject to the cross-cutting constraint in VEW-005.

3. **Notification on invite.** `grant_view` creates a pending row but does not send a
   notification to the grantee. Should it call `alerts.write_alert` / `send_alert_email`?
   Assumption: yes, best-effort (`try/except`) `write_alert` to the grantee's `T.alerts`
   table on invite creation — mirrors the invite pattern in other features but is not
   auditable.

4. **Token format version.** The current HMAC scheme does not include a version byte. If the
   signing algorithm changes in a future version, all outstanding tokens will become invalid.
   Assumption: acceptable for V1; include a `ver=1` field in the payload for future
   discrimination.

5. **`require_acceptance` per-view vs per-resource.** The current spec stores
   `require_acceptance` at the resource level (one SETTINGS row per resource). Should it be
   per-view? Assumption: per-resource is simpler and sufficient for V1 — an owner who wants
   some views auto-active can set `require_acceptance=False` for the whole resource.

6. **Public endpoint returning `PublicViewDataOut`.** The spec delegates the actual resource
   assembly and projection to VEW-003. However, VEW-002 must ship and be testable before
   VEW-003 lands. Resolution: `GET /ui/views/public/{token}` in VEW-002 returns only the
   raw `grants` map from `resolve_public_view`; the full projected data is wired in VEW-003.
   The route handler is a stub that calls `resolve_public_view` and returns `{"view_id":
   ..., "grants": ..., "expires_at": ...}` until VEW-003 lands.
