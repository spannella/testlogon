# PLT-005 — account / transaction.created / balance.threshold webhook events — taxonomy + ledger/account firing

**Type:** Feature | **Priority:** P2 | **Estimate:** 3d
**Flag:** `ACCOUNT_LEDGER_WEBHOOKS_ENABLED` (new, default **off**)
**Branch prefix:** `feature/plt-005-account-ledger-webhooks`

---

## 1. Summary & Goal

OBP's event-webhook specification fires `account.*`, `transaction.created`, and `balance.threshold` events from the ledger write path so downstream consumers can react to money movements in real time. Today, testlogon's HMAC webhook bus (`app/services/webhook_service.py`) already carries a `wallet.deposit` / `wallet.withdrawal` taxonomy but has no account/transaction/threshold event types — the OBP Gap Analysis (§D) marks this gap as **PARTIAL**: *"event taxonomy is billing/messaging, not account/ledger events."*

This ticket closes that gap by:

1. Adding `transaction.created`, `balance.threshold`, and `account.balance_low` to `WEBHOOK_EVENT_TYPES_V2` so endpoints can subscribe to them through the existing subscription API.
2. Introducing a thin `emit_ledger_webhook` helper in `app/services/billing_shared.py` that any `new_ledger_entry` call site can invoke after persisting a ledger row, without touching the unrelated call sites that have not yet been migrated.
3. Wiring the threshold edge-trigger (downward crossing only, one event per crossing) into `apply_wallet_delta` (`billing_shared.py:185`) via a narrow post-update check, stored in a `balance_threshold_cents` / `last_threshold_crossed` pair on the `WALLET` row.
4. Providing a small `PUT /ui/billing/wallet/threshold` endpoint so users can configure (or clear) their own threshold.

All three new event types go through the existing signed, retried `dispatch_webhook_event` pipeline (`webhook_service.py:556`). With `ACCOUNT_LEDGER_WEBHOOKS_ENABLED=0` (or `WEBHOOKS_ENABLED=0`) no new event is ever dispatched; the underlying ledger and balance writes are byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Webhook infrastructure (fully reused, nothing forked)

**`WEBHOOK_EVENT_TYPES_V2` (`app/services/webhook_service.py:60`)**
The canonical registry dict of 100+ event types. It already contains `wallet.deposit` (line 35) and `wallet.withdrawal` (line 75). `account.login`, `account.mfa_change`, and `account.profile_update` are in the v1 `WEBHOOK_EVENT_TYPES` dict (lines 46–48); the v2 expansion adds `account.created`, `account.deleted`, `account.password_changed`, `account.email_verified`, `account.api_key_created`, `account.api_key_revoked` (lines 130–135). **`dispatch_webhook_event(event_type, user_sub, data)` (`webhook_service.py:556`)**
Queries `T.webhook_endpoints` for subscribed endpoints (`EVENT#{event_type}` PK), creates `pending` delivery items in `T.webhook_deliveries`, and returns a list of delivery IDs. Retry schedule is `RETRY_DELAYS_SECONDS = [0, 60, 300, 1800, 7200]` (`webhook_service.py:214`).

**Best-effort emit discipline**
Every existing webhook caller wraps `dispatch_webhook_event` in `try/except`. The KYC pattern (`_emit_kyc_event_safe`, `app/services/kyc_cases.py:20`) and the ad-platform pattern (`emit_ad_event`, `app/services/ad_webhooks.py:45`) both swallow all exceptions so a dispatch failure can never break a state transition. PLT-005 follows the same pattern.

## 3. Data Model

### 3.1 No new DynamoDB tables

All deliveries continue to land in the existing `webhook_endpoints` and `webhook_deliveries` tables. The existing `ByStatus` GSI (`status` / `next_retry_at`, both numeric, declared `attr_types={"next_retry_at": "N", "created_at": "N"}` at `scripts/local-ddb-init.py:1299`) handles delivery polling without any schema change.

### 3.2 New fields on the `WALLET` row (`T.billing`, PK `USER#{user_sub}`, SK `WALLET`)

Two optional fields are added to the existing wallet row (`billing_shared.py:173 WALLET_SK = "WALLET"`). They are never required for existing callers; `apply_wallet_delta` only reads and writes them when PLT-005 is enabled.

| Field | Type | DynamoDB attr type | Purpose |
|---|---|---|---|
| `balance_threshold_cents` | int | N | User-configured low-balance threshold. Absent or 0 means no threshold. |
| `last_threshold_crossed` | bool (stored as DDB BOOL) | BOOL | True when the balance is currently below threshold (prevents re-fire). Reset to False when balance recovers above threshold. |

These fields do not require a new GSI. No `attr_types` change to `scripts/local-ddb-init.py` is needed because neither field is a GSI key.

### 3.3 New `WEBHOOK_EVENT_TYPES_V2` entries (`webhook_service.py:60`)

```python
# PLT-005 — account/ledger events
"transaction.created": "A new ledger transaction was recorded",
"balance.threshold": "An account balance crossed a configured threshold",
"account.balance_low": "Account balance fell below the low-balance threshold",
```

These three keys are inserted into `WEBHOOK_EVENT_TYPES_V2` at the existing `"account.*"` block (after `"account.api_key_revoked"` at line 135). No new canonical sub-dict like `KYC_WEBHOOK_EVENT_TYPES` is required; the three types are not domain-partitioned.

### 3.4 Ledger event payload schema

`transaction.created` payload (carried in the `data` field of the standard webhook envelope):

```json
{
  "transaction_id": "1735000000_a1b2c3d4",
  "type": "credit",
  "amount_cents": 2500,
  "currency": "usd",
  "reason": "wallet_deposit",
  "state": "settled",
  "ledger_date": "2026-06-12",
  "provider": "stripe"
}
```

`balance.threshold` / `account.balance_low` payload:

```json
{
  "balance_cents": 450,
  "threshold_cents": 1000,
  "currency": "usd",
  "direction": "below"
}
```

All fields are scalar strings or integers; no nested objects. This keeps the payload flat, consistent with the existing KYC and ad-platform event shapes.

## 4. API / Service Design

### 4.1 New helper: `emit_ledger_webhook` (`app/services/billing_shared.py`)

```python
def emit_ledger_webhook(user_sub: str, item: Dict[str, Any]) -> None:
    """Fire a best-effort transaction.created webhook after a ledger persist.

    Must be called with the item dict returned by new_ledger_entry, after
    the table.put_item call has succeeded.  Never raises — a dispatch failure
    must never roll back or fail the underlying ledger write.
    """
```

**Behaviour:**
- Returns immediately (no-op) if `not S.account_ledger_webhooks_enabled` or `not S.webhooks_enabled`.
- Extracts `entry_id`, `type`, `amount_cents`, `currency` (defaulting to `"usd"` if absent), `reason`, `state`, `ledger_date`, and optional `provider` from `item`.
- Calls `dispatch_webhook_event("transaction.created", user_sub, payload)` inside `try/except Exception` — swallows all exceptions, logs at WARNING level with `exc_info=True`.

**Import discipline:** `dispatch_webhook_event` is imported inside the function body via a lazy local import (`from app.services.webhook_service import dispatch_webhook_event`) to avoid a circular import between `billing_shared` (a pure-data module imported by virtually every service) and `webhook_service` (which imports `app.core.settings`).

**Migration order:** The first call sites to be wired are the five consumer-facing Stripe paths in `app/routers/billing.py`:
- Line 1126 (pay_balance settled path)
- Line 1234 (charge_once settled path)
- Line 1306 (refund path — emits `transaction.created` with `type=adjustment`, `reason=refund`; the actual `entry_type` at this call site is `"adjustment"`, not `"credit"`)
- Line 2522 (wallet_deposit settled path)
- Line 2592 (wallet_withdrawal path)

Each becomes a two-liner after the existing `put_item` call: `_sk, _item = new_ledger_entry(...); T.billing.put_item(Item=_item); emit_ledger_webhook(user_id, _item)`. Un-migrated call sites in `paypal.py`, `billing_ccbill.py`, and service files are deferred to follow-up tickets; the emit gate ensures zero behaviour change for them.

### 4.2 Threshold check wired into `apply_wallet_delta` (`billing_shared.py:185`)

`apply_wallet_delta` already returns the post-update `wallet_balance_cents` via `ReturnValues="ALL_NEW"`. The threshold check is added as a post-call block:

```python
def apply_wallet_delta(table, pk, delta_cents, *, currency="usd") -> int:
    # ... existing update_item logic unchanged ...
    new_balance = int(result["Attributes"].get("wallet_balance_cents", 0))
    _check_balance_threshold(table, pk, new_balance,
                             result["Attributes"], currency)
    return new_balance
```

**`_check_balance_threshold(table, pk, new_balance, attrs, currency)` (private helper, same file):**

```python
def _check_balance_threshold(
    table: Any,
    pk: str,
    new_balance: int,
    attrs: Dict[str, Any],
    currency: str,
) -> None:
    """Edge-trigger threshold check. Must never raise."""
```

- Returns immediately if `not S.account_ledger_webhooks_enabled` or `not S.webhooks_enabled`.
- Reads `threshold = int(attrs.get("balance_threshold_cents") or 0)`. If `threshold <= 0`, returns — no threshold configured.
- Reads `last_crossed = bool(attrs.get("last_threshold_crossed", False))`.
- **Downward crossing:** `new_balance < threshold` and `not last_crossed`. Sets `last_threshold_crossed = True` via `table.update_item(Key={"pk": pk, "sk": WALLET_SK}, UpdateExpression="SET last_threshold_crossed = :t", ...)`. Then dispatches both `"balance.threshold"` and `"account.balance_low"` with the threshold payload. The two events are identical in content but target different subscription keys, matching OBP's convention of having a generic `balance.threshold` plus a domain-named `account.balance_low` alias.
- **Recovery:** `new_balance >= threshold` and `last_crossed`. Sets `last_threshold_crossed = False` — no event fired on recovery (OBP does not define an `account.balance_recovered` event).
- **No re-fire while below:** `new_balance < threshold` and `last_crossed` — returns without action.
- All `update_item` and `dispatch_webhook_event` calls are inside `try/except Exception`.

The `last_threshold_crossed` attribute reset (deposit path) happens atomically only when both conditions are met. No TTL on the attribute; it persists until the next balance movement clears it.

### 4.3 New endpoint: `PUT /ui/billing/wallet/threshold` (`app/routers/billing.py`)

Allows an authenticated user to configure or clear their balance threshold.

**Auth:** `Depends(require_ui_session)` — same as all other `/ui/billing/*` endpoints. CSRF enforced automatically.

**Request model (`app/models.py`):**

```python
class SetWalletThresholdReq(BaseModel):
    threshold_cents: int = Field(ge=0, description="0 = disable threshold")
```

**Response:** `{"ok": True, "threshold_cents": <int>, "currency": "usd"}`

**Implementation:**
```python
@dual_route("PUT", "/billing/wallet/threshold")   # registers /ui/billing/wallet/threshold + /api/billing/wallet/threshold
def set_wallet_threshold(
    body: SetWalletThresholdReq,
    req: Request = None,
    ctx = Depends(require_ui_session),
) -> Dict[str, Any]:
```
Note: `billing.py` uses `dual_route` for all user-facing endpoints to register both `/ui/…` and `/api/…` prefixes simultaneously. Using a bare `@router.put(...)` would only register one prefix.

Writes `balance_threshold_cents = body.threshold_cents` to the `WALLET` row via `update_item`. If `threshold_cents == 0`, also sets `last_threshold_crossed = False` (clearing any stale edge state). Emits `audit_event("wallet_threshold_set", user_id, req, threshold_cents=body.threshold_cents)`. Returns the new threshold value.

**Read:** The existing `GET /billing/wallet` endpoint (registered via `@dual_route("GET", "/billing/wallet")`, decorated function at `billing.py:2484`) calls `get_wallet_balance(T.billing, user_pk(user_id))` (`billing_shared.py:176`) and returns `Dict[str, Any]`. There is no `WalletBalanceOut` Pydantic model in `app/models.py`; the wallet endpoint is untyped. PLT-005 extends `get_wallet_balance` to include `balance_threshold_cents` and `last_threshold_crossed` in its returned dict. If a typed response model is desired, a new `WalletBalanceOut` model must be added to `app/models.py` with optional fields `threshold_cents: Optional[int]` and `threshold_active: Optional[bool]` (and the existing three fields `wallet_balance_cents`, `currency`, `updated_at`).

### 4.4 No new router registration required

The `PUT /ui/billing/wallet/threshold` endpoint is added directly to the existing `billing.py` router which is already registered in `app/main.py`. No `API_KEY_ROUTE_EXEMPTIONS` entry is needed because this is a cookie-auth mutating endpoint, not a public read.

## 5. Detailed Behavior & Edge Cases

### 5.1 `transaction.created` idempotency

`new_ledger_entry` generates a unique `entry_id = ulidish()` (`billing_shared.py:240`) on every call. Because `emit_ledger_webhook` is called immediately after a successful `put_item`, and `put_item` in DynamoDB is idempotent only when the SK is stable, the emit is inherently tied to a single successful write. Retry/replay scenarios: if a caller retries a `new_ledger_entry` due to a transient error and the first write actually succeeded (no conditional), a second `put_item` with a new `entry_id` and new SK would succeed, generating a second ledger row and a second event. This is the same double-write risk that exists today in the ledger itself; PLT-005 does not worsen it. Call sites that use `idempotency_key` (e.g., `wallet_deposit` at `billing.py:2504`) already guard against this at the provider level.

### 5.2 `balance.threshold` edge semantics

The edge trigger is **downward crossing only** (balance crosses from `>= threshold` to `< threshold`). A deposit that brings the balance back above threshold resets `last_threshold_crossed = False` silently. The next withdrawal that crosses the threshold again will fire a new event. This prevents alert storms when the balance oscillates near the threshold value.

If `apply_wallet_delta` is called with a withdrawal that undershoots the threshold but the `ConditionalCheckFailedException` is raised (insufficient balance), the `update_item` fails before `ReturnValues` are produced — `_check_balance_threshold` is never reached.

### 5.3 Threshold set/clear during an active below-threshold state

If a user raises their threshold while their balance is already below it, `last_threshold_crossed` may be `False` (never crossed under the new higher threshold), causing an immediate event fire on the next write. This is acceptable: the semantic is "your balance is below your new threshold" which is true and useful. Conversely, lowering the threshold below the current balance sets `last_threshold_crossed = False` atomically (via `set_wallet_threshold`), re-arming future crossings correctly.

### 5.4 `dispatch_webhook_event` returns empty when no endpoints are subscribed

`dispatch_webhook_event` queries `EVENT#transaction.created` in `T.webhook_endpoints` and returns `[]` when no subscribed endpoints exist. This is the common case during initial rollout. The `emit_ledger_webhook` helper discards the return value; `[]` and a non-empty list are both acceptable.

### 5.5 Concurrent `apply_wallet_delta` calls

DynamoDB's `update_item` is atomic. Two concurrent deposits both succeed and return their respective post-update balances. `_check_balance_threshold` may fire twice if the first brings the balance below the threshold, but because the `last_threshold_crossed = True` write is a separate `update_item`, there is a narrow race window where both could read `last_threshold_crossed = False` and both emit. This is acceptable: webhook delivery is best-effort and at-most-a-few-times; the consumer's receive-side should be idempotent on `event_id` anyway. A conditional `update_item` (`attribute_not_exists(last_threshold_crossed) OR last_threshold_crossed = :false`) could prevent the race but would add a `ConditionalCheckFailedException` code path in the emit helper — given the at-most-once delivery guarantee is already advisory, the simpler unconditional write is preferred.

### 5.6 `tip_ledger.py` and other non-`new_ledger_entry` call sites

`tip_ledger.py` (`app/services/tip_ledger.py:142–174`) writes paired debit/credit rows directly via `T.billing.put_item` without calling `new_ledger_entry`. These entries do not go through `emit_ledger_webhook` in the initial migration and do not emit `transaction.created`. This is explicitly deferred — `tip_ledger` is a specialized path and bringing it in-scope would require its own analysis. The OBP ticket acceptance criteria are met by the wallet deposit/withdrawal/charge/refund paths alone.

### 5.7 Webhook flag interaction

With `WEBHOOKS_ENABLED=0`, `dispatch_webhook_event` returns `[]` at line 565. With `ACCOUNT_LEDGER_WEBHOOKS_ENABLED=0`, `emit_ledger_webhook` and `_check_balance_threshold` short-circuit before calling `dispatch_webhook_event`. Either flag alone is sufficient to suppress all account/ledger events.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### Dev/prod parity

`emit_ledger_webhook` and `_check_balance_threshold` both call `dispatch_webhook_event` which writes to `T.webhook_deliveries` — the same DynamoDB Local table in dev and real DynamoDB in prod. There is no `if S.dev_mode:` branch. The webhook delivery worker (`webhook_service.py` dispatcher loop registered in `app/main.py`) is the same in both environments. SECOPS-007 is satisfied.

### Money-safety

**No ledger write is gated on webhook success.** `emit_ledger_webhook` is always called *after* `T.billing.put_item(Item=led_item)` has returned without error. A webhook dispatch failure (network, DDB timeout, any exception) is caught by the `try/except` and logged; it cannot prevent the ledger row from persisting. This mirrors `billing.py:1286 refund_payment` where `settle_or_reverse_ledger` is called before any notification side-effect.

**No money moves in this ticket.** PLT-005 adds event emission only. It does not introduce new payment-initiation endpoints, does not call `apply_wallet_delta` in a new context, and does not interact with `_fraud_gate` or `settle_or_reverse_ledger` beyond what already exists. The `SET /ui/billing/wallet/threshold` endpoint is purely metadata and does not touch `amount_cents` or wallet balance.

**`apply_wallet_delta` atomicity is preserved.** The threshold check is added *after* the `update_item` returns `ALL_NEW`. The threshold check itself does not modify `wallet_balance_cents`. The `last_threshold_crossed` attribute update is a separate `update_item` on the same key. A crash between the balance update and the threshold state write means `last_threshold_crossed` stays `False`, which causes a duplicate event fire on the next crossing — acceptable under at-most-a-few-times semantics.

### Idempotency

Each `dispatch_webhook_event` call generates a fresh `event_id = _gen_event_id()` (`webhook_service.py:577`). Downstream consumers are expected to deduplicate on `event.id`. The existing webhook delivery table TTL (`webhooks_delivery_ttl_days`, default 30 days) ensures delivery records are eventually cleaned up.

### Security

`balance_threshold_cents` is set only by the authenticated user via `PUT /ui/billing/wallet/threshold` (cookie + CSRF). There is no admin-override path in this ticket. The threshold value itself is not sensitive (it is a comparison trigger, not a balance amount owned by someone else). The webhook payload contains `balance_cents` and `threshold_cents` both of which the subscriber already knows (they set the threshold and their own balance is accessible via `GET /ui/billing/wallet/balance`). No PII beyond what the subscriber already holds is disclosed in the event payload.

## 8. Backward Compatibility & Migration

### 8.1 Existing event subscriptions unaffected

Adding three new entries to `WEBHOOK_EVENT_TYPES_V2` does not change the validation or delivery of any existing event type. The dict is read-only after startup. Existing subscribers to `wallet.deposit` / `wallet.withdrawal` continue to receive those events unchanged; the `transaction.created` event supplements rather than replaces them. Operators who want both old and new semantics can subscribe to all four.

### 8.2 `WALLET` row schema is backward compatible

Existing `WALLET` rows that lack `balance_threshold_cents` or `last_threshold_crossed` are treated as having `threshold = 0` and `last_crossed = False` by `_check_balance_threshold`. No backfill or migration is required.

### 8.3 `get_wallet_balance` return value extension

`get_wallet_balance` is called by `billing.py:2484` (`GET /billing/wallet`, accessible at `/ui/billing/wallet`). Adding `threshold_cents` and `threshold_active` to the returned `Dict[str, Any]` is backward compatible: clients receive additional optional keys, existing clients ignore unknown fields. Note: the wallet endpoint currently has no Pydantic response model (`WalletBalanceOut` does not yet exist in `app/models.py`); if PLT-005 introduces one, it is a new addition rather than an extension.

### 8.4 Incremental call-site migration

Because `emit_ledger_webhook` is purely opt-in (call sites invoke it explicitly), the migration of remaining call sites (`paypal.py`, `billing_ccbill.py`, `tip_ledger.py`, `ad_placement.py`, etc.) can happen in follow-up PRs without any flag or schema change. Each migration is a one-line addition after the existing `put_item` call.

## 10. Open Questions / Assumptions

1. **`apply_wallet_delta` in services that don't go through `billing.py`**: `group_treasury.py` and `compute_billing.py` also call `apply_wallet_delta`. If those paths should emit threshold events, they will benefit from the `_check_balance_threshold` addition automatically (it is wired into `apply_wallet_delta` itself). The assumption is that this is desired — if not, the check should be moved to call sites instead.

2. **Threshold recovery event**: OBP has no `account.balance_recovered` event type. This spec does not add one. If product later wants a recovery notification, it can be added to `_check_balance_threshold` without any schema change.

3. **Multi-currency wallets**: `billing_shared.py` hardcodes `currency="usd"` in most paths. The threshold is compared as integer cents in a single currency. If multi-currency wallets are introduced later, `balance_threshold_cents` would need a `threshold_currency` companion field. For now, `currency` in the event payload is taken from the `WALLET` row's `currency` field (defaulting to `"usd"`).

4. **`tip_ledger.py` migration scope**: this spec explicitly defers `tip_ledger.py` to a follow-up. The assumption is that the OBP acceptance criteria for PLT-005 are satisfied by the Stripe billing paths alone. If all ledger paths must emit, the scope of this ticket doubles.

5. **Threshold value validation**: `SetWalletThresholdReq` uses `ge=0` (non-negative). A threshold of 0 disables the feature. Should there be an upper cap (e.g., `le=10_000_000`)? Assuming no upper cap for now; the threshold is purely informational.

6. **Admin-set threshold**: the spec only exposes user-self-service threshold configuration. An admin override (e.g., a compliance minimum-balance alert) could be added later as a separate admin endpoint with a distinct `admin_threshold_cents` field.

### Money-Safety Assessment

**PASSED.** The design correctly places `emit_ledger_webhook` after `T.billing.put_item` returns without error, meaning webhook dispatch failure can never roll back a ledger write. `apply_wallet_delta` atomicity is fully preserved — the threshold check fires only after `ReturnValues="ALL_NEW"` returns. No new money-moving code paths are introduced. The `PUT /ui/billing/wallet/threshold` endpoint is pure metadata (no `amount_cents` writes, no `apply_wallet_delta` call). `settle_or_reverse_ledger` is not touched. No double-charge risk.

### Security Assessment

**PASSED.** The threshold endpoint requires `require_ui_session` (cookie + CSRF). No admin override path. The webhook payload for `balance.threshold` / `account.balance_low` discloses only `balance_cents` and `threshold_cents` — data the authenticated subscriber already possesses. No PII leakage. No token type errors (HS256/RS256 irrelevant here — webhook HMAC signing is separate from auth token signing and not changed by this ticket). No public endpoints added.

- **RESOLVED (RISK LOW, accepted):** `paypal.py` `new_ledger_entry` is a standalone reimplementation that bypasses `billing_shared.new_ledger_entry`.
