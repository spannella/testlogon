# ACC-003 — Transaction metadata enrichment — tags / comments / narrative / geotag / image

**Type**: Backend (metadata sub-rows + S3 image upload + endpoints)
**Priority**: P2
**Estimate**: 3 days
**Depends on**: ACC-002 (transaction resolution), ACC-001 (account entity, ownership)
**Status**: Unimplemented

---

## 1. Summary & Goal

ACC-003 layers OBP-style **transaction metadata** — user-authored tags, comments, a
narrative, a geotag, and a single image — on top of the immutable billing ledger
transactions established by ACC-001/002. The underlying `LEDGER#{ts}#{entry_id}` rows in
`T.billing` are **never mutated**; they are the money record and must remain byte-identical
before and after any metadata operation. Metadata lives entirely in NEW sub-rows, keyed to
the `banking_accounts` table by `account_id` and `transaction_id`.

Goals:

1. Expose eight endpoints (GET all metadata, PUT narrative, PUT geotag, POST image,
   POST/DELETE tags, POST/DELETE comments) under
   `/ui/banking/accounts/{account_id}/transactions/{transaction_id}/...`.
2. Store metadata sub-rows in the existing `banking_accounts` table (single-table design,
   no new DynamoDB table) using a `ACCOUNT#` partition and structured `META#` sort keys.
3. Upload transaction images to S3 via the existing `app.core.aws_clients.s3_client()`
   factory (`aws_clients.py:114`) — the same path messaging and file-share use — achieving
   full dev/prod parity with no `if S.dev_mode` branch in business logic.
4. Gate the entire feature on a sub-flag `banking_account_metadata_enabled`; keep existing
   billing, wallet, ledger, and ACC-001/002 surfaces completely unaffected when the flag is
   off.

## 3. Data Model

### No new DynamoDB table

ACC-003 reuses the `banking_accounts` table introduced by ACC-001. No new `TableDef` entry
is needed — the existing `pk/sk` schema already accommodates the `ACCOUNT#{account_id}`
partition used below.

### Metadata sub-row layout

All metadata rows live in the `banking_accounts` table under:

```
pk  = ACCOUNT#{account_id}    (S — note: different partition from the account ownership row)
sk  = META#{transaction_id}#{subtype}...
```

Using `ACCOUNT#{account_id}` as the partition (rather than `USER#{sub}`) deliberately
decouples metadata from the owner's user sub. This means:
- A `begins_with("META#{transaction_id}#")` key-condition query on the
  `ACCOUNT#{account_id}` partition fetches ALL metadata kinds for one transaction in a
  **single DynamoDB call**.
- Co-owners (ACC-004) — who know `account_id` but may differ in `user_sub` — can query
  metadata without knowing the owner's sub.

**Singleton rows** (PUT-replaces; one row per transaction, last write wins):

| Sort key | Fields stored |
|---|---|
| `META#{transaction_id}#NARRATIVE` | `text` (str, max 2000 chars), `author_sub`, `updated_at` (N) |
| `META#{transaction_id}#GEOTAG` | `lat` (N, float, −90..90), `lon` (N, float, −180..180), `label` (str, optional, max 200 chars), `author_sub`, `updated_at` (N) |
| `META#{transaction_id}#IMAGE` | `s3_key` (str), `bucket` (str), `url` (str — dev: `/mock/s3/...`, prod: presigned), `image_id` (str, uuid), `author_sub`, `created_at` (N) |

**Multi rows** (one row per item; append + delete):

| Sort key | Fields stored |
|---|---|
| `META#{transaction_id}#TAG#{tag_id}` | `value` (str, max 100 chars, normalized lowercase), `author_sub`, `created_at` (N) |
| `META#{transaction_id}#COMMENT#{comment_id}` | `text` (str, max 1000 chars), `author_sub`, `created_at` (N) |

`tag_id` and `comment_id` are `uuid4().hex` minted at write time by the service.

**GSI considerations.** No new GSI is required for ACC-003. The `begins_with` key
condition on `pk=ACCOUNT#{account_id}` + `sk begins_with META#{transaction_id}#` is a
base-table query — no index needed. The `updated_at` and `created_at` fields on metadata
rows are numeric Unix timestamps but are NOT used as GSI sort keys, so no additional
`attr_types` declaration is needed beyond what ACC-001 already declares
(`attr_types={"created_at": "N"}` for `GSI_ACCOUNT_BY_ID`).

**Metadata response shape.** The aggregate read (`get_transaction_metadata`) returns:


whether a `META#{transaction_id}#` prefix exists (a `Count`-only query, 1 read unit), NOT

by the dedicated `GET .../metadata` endpoint or the single-transaction `GET .../

### S3 bucket and key schema

S3 objects for transaction images are written to the bucket controlled by `S.banking_s3_bucket`
(env `BANKING_S3_BUCKET`, introduced in Section 6). When `BANKING_S3_BUCKET` is empty the
service must fall back to a hard-coded default name (e.g. `"banking-images"`) — there is
no existing `S.s3_bucket` or `S.billing_s3_bucket` setting in `app/core/settings.py` to
fall back to. Key schema:
<!-- CORRECTED: S.s3_bucket and S.billing_s3_bucket do not exist in settings.py;
the only bucket setting relevant here is S.banking_s3_bucket introduced by this ticket -->

```
banking-metadata/{account_id}/{transaction_id}/{image_id}
```

This namespacing keeps transaction images isolated from messaging/file-share keys
(`banking-metadata/` prefix), enabling per-prefix bucket policies or S3 lifecycle rules
without ambiguity.

## 5. Detailed Behavior & Edge Cases

### Ledger immutability guarantee

The `LEDGER#` rows in `T.billing` are **never touched** by any ACC-003 code path. The
service does NOT call `T.billing.update_item` or `T.billing.put_item` anywhere. The test
plan (Section 9) explicitly asserts byte-identity of the billing item before and after
every metadata write. This is the load-bearing invariant.

### Singleton PUT-replace semantics

`put_transaction_narrative` and `put_transaction_geotag` use DynamoDB `put_item` with no
`ConditionExpression` — they are unconditional overwrites. There is no "append to narrative"
path; the last writer wins. `author_sub` and `updated_at` are refreshed on every PUT.
Calling `put_transaction_narrative` a second time with different text replaces the row
entirely; there is no history or undo.

For `set_transaction_image`, the same singleton `IMAGE` sort key is overwritten on every
call. The OLD S3 object is NOT deleted (S3 lifecycle or retention policy cleans up orphans;
deletion is out of scope for this ticket). The metadata row always points to the most
recently uploaded image; older images remain in S3 but are unreachable via the API.

### Multi-row tag/comment limits

To prevent runaway storage, a hard cap is enforced:

- **Tags**: max 20 tags per transaction. `add_transaction_tag` counts existing `TAG#` rows
  via a `Select=COUNT` query before inserting; if `count >= 20` → `HTTPException(422,
  detail={"code": "tag_limit_reached"})`.
- **Comments**: max 100 comments per transaction. Same `COUNT` check; returns
  `HTTPException(422, detail={"code": "comment_limit_reached"})`.

Tag deduplication: `value` is normalized to lowercase and stripped before storage.
`add_transaction_tag` 409s if a row with the same normalized value already exists for that
transaction (case-insensitive exact match). This check queries `TAG#` rows and compares
`value` fields in Python (no GSI needed; max 20 rows).

### Transaction existence gate

Every metadata endpoint calls `get_account_transaction(account_id, transaction_id, *,
requester_sub=...)` (from ACC-002) before any DDB write. If the `transaction_id` is unknown
in the account's ledger (i.e., the ledger has no row matching `entry_id == transaction_id`
for the resolved account owner), `get_account_transaction` raises `HTTPException(404)`.
This propagates unchanged; the metadata endpoint never creates a dangling metadata row for a
non-existent transaction.

### Authorization model for metadata

ACC-003 inherits authorization entirely from ACC-001's ownership model:

- **Account owners** (anyone in `account.owners`) may read AND write all metadata.
- **Co-owners added via ACC-004** inherit the same full read/write permission.
- **View-based viewers (ACC-004 / VEW)** may read metadata subject to ACC-004's
  `project_resource` projection logic (out of scope for this ticket). The VEW spec
  (`OBP_VIEWS_ENTITLEMENTS_TICKETS.md`, VEW-003) defines `metadata_visibility` as a
  `"counterparty_blur"` flag — NOT a `"hidden"` value. The exact projection predicate
  for metadata rows will be determined by the VEW-003 implementation; ACC-003 passes
  `TransactionMetadataOut` through unchanged.
  <!-- CORRECTED: The VEW spec uses "counterparty_blur", not "hidden", as the
  metadata_visibility flag value. Neither ACC-004 nor VEW-003 specs define "hidden". --> Without an explicit co-access grant, a non-owner gets a 404 — consistent
  with ACC-001's "no-leak" ownership pattern.
- **Comment deletion**: both the comment's `author_sub` AND any account owner may delete a
  comment. A co-owner (non-original-commenter) deleting another user's comment emits an
  audit event with both `actor_sub` and `comment_author_sub` in the fields.

### Image MIME type validation

Allowed MIME types: `image/jpeg`, `image/png`, `image/gif`, `image/webp`. Any other
`content_type` → `HTTPException(422, detail={"code": "unsupported_image_type"})`. Maximum
file size is controlled by `S.banking_image_max_bytes` (env
`BANKING_IMAGE_MAX_BYTES`, default `5242880` = 5 MB). If `len(image_bytes) >
S.banking_image_max_bytes` → `HTTPException(413, detail={"code": "image_too_large"})`.
Both checks happen **before** the S3 `put_object` call.

### `has_metadata` flag in transaction list

The `list_account_transactions` function in ACC-002 sets `has_metadata` by issuing one
additional per-transaction DynamoDB query with `Select="COUNT"` and
`Limit=1` on `pk=ACCOUNT#{account_id}`, `sk begins_with META#{transaction_id}#`. A
`Count > 0` means metadata exists. This adds one read per transaction in the page but
avoids loading metadata content for every list item. Implementations MAY batch these as
`BatchGetItem` calls or defer them (returning `has_metadata=False` always) until performance
measurement justifies the extra reads. The `metadata` field on `TransactionOut` remains
`None` in list responses; it is only populated by `GET .../metadata` or
`GET .../transactions/{transaction_id}`.

### Concurrent write safety

Narrative and geotag PUT operations are unconditional overwrites — last-write-wins under
concurrent requests. Tag and comment additions are idempotent in that each `uuid4().hex`
`tag_id`/`comment_id` is unique, so two concurrent `POST .../tags` calls for the same value
may both succeed and create two rows (before the dedup check runs). The dedup check is
therefore a soft guard (it runs in the same request before the insert), not a distributed
lock. For the max-20-tags constraint, two concurrent inserts at count=19 could both pass
the `COUNT` check and create a 21st row. This is an accepted race condition; enforcement
at count=20 is best-effort.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007: single code path, no dev_mode branches in business logic

The `s3_client()` factory (`aws_clients.py:114`) handles dev vs prod transparently:
in dev, moto intercepts boto3 S3 calls in-process (no separate S3 process; `_s3_endpoint_url()`
returns `None` when `S.dev_mode` is True at `aws_clients.py:81-83`) and the metadata
service calls `put_object` + `generate_presigned_url` against moto's in-memory state.
In prod, `s3_client()` returns a real boto3 S3 client pointed at AWS.

The one difference in behavior (URL shape for the `image.url` field) is handled by a
localized helper inside `_build_image_url(s3_key, bucket)`:

```python
def _build_image_url(s3_key: str, bucket: str) -> str:
    if S.dev_mode:
        return f"/mock/s3/{bucket}/{s3_key}"
    return s3_client().generate_presigned_url(
        "get_object",
        Params={"Bucket": bucket, "Key": s3_key},
        ExpiresIn=3600,
    )
```

This mirrors the identical pattern in `messaging.py:3836-3846` for voice/image messages.
The service function itself has NO other `if S.dev_mode` branching — DDB writes, MIME
validation, rate-limit checks, and audit events run identically in both environments.

### Money-safety

ACC-003 is **read/annotate only** — it writes metadata sub-rows and S3 objects. It never
calls `apply_wallet_delta`, `new_ledger_entry`, `settle_or_reverse_ledger`, or any other
money-moving primitive. The ledger immutability invariant (Section 5) is enforced both by
code review (no `T.billing` write calls in `banking_accounts.py`) and by the explicit
test assertion (Section 9).

No payment method, fraud gate, or SCA challenge is needed because no money movement occurs.

### Idempotency

- PUT narrative / geotag: fully idempotent — the same request sent twice produces identical
  DDB state (same `sk`, last writer wins; `updated_at` differs but the row content is the
  same).
- POST image: not strictly idempotent (each call mints a new `image_id` and uploads a new
  S3 object), but the DDB IMAGE row is overwritten by the latest upload, so the API
  response is consistent after any number of calls.
- POST tag: idempotent for the same normalized value (dedup → 409). Two calls with
  different values mint different `tag_id`s as intended.
- POST comment: not idempotent (each call mints a new `comment_id`). Callers must not retry
  on network timeout without checking for an existing comment first (client responsibility).

### Security

- **No cross-user data leak.** Metadata is scoped to `pk=ACCOUNT#{account_id}`. The only
  way to reach this partition is through `get_account_transaction`, which enforces ownership
  via `get_account` (ACC-001) using `GSI_ACCOUNT_BY_ID` + owner-list check. A requester
  who does not appear in `account.owners` receives a 404, not a 403, so account existence
  is not leaked to non-owners.
- **S3 key predictability.** The key `banking-metadata/{account_id}/{transaction_id}/
  {image_id}` embeds a UUID `image_id`. S3 presigned URLs expire after 3600 seconds;
  the DDB row stores the raw `s3_key`, and the URL is regenerated on every `GET .../metadata`
  call.
- **CSRF.** All mutating endpoints use cookie auth and are subject to the existing CSRF
  middleware (the `x-csrf-token` header check in `require_ui_session`). This is the same
  protection that billing mutation endpoints use.
- **Narrative/comment text.** No HTML sanitization is applied server-side; the frontend is
  responsible for rendering these as plain text (not raw HTML). Content is stored and
  returned as a raw string.

## 8. Backward Compatibility & Migration

### Flag-off means zero footprint

With `BANKING_ACCOUNT_METADATA_ENABLED=0` (the default), the metadata endpoint handlers
return 404 and no metadata rows are ever written. `T.billing` is never touched. The
`banking_accounts` table (created by ACC-001's table init) gains no new rows. Existing
wallet/ledger endpoints (`GET /billing/balance`, `GET /billing/ledger`) are entirely
unaffected.

### Schema is additive on `TransactionOut`

The two new fields on `TransactionOut` (`has_metadata: bool = False`,
`metadata: Optional[TransactionMetadataOut] = None`) have default values, so existing
callers that ignore unknown fields (or use partial deserialization) see no change.
Callers that pin a strict schema will receive the new fields with their default values
when `BANKING_ACCOUNT_METADATA_ENABLED=0` (i.e., `has_metadata=False`, `metadata=null`).

### No data migration

There are no existing metadata rows to migrate — the `banking_accounts` table and
its `ACCOUNT#{account_id}` + `META#...` sort key space are net-new. No backfill is needed.

### Enabling metadata for the first time in an existing deployment

Enabling `BANKING_ACCOUNT_METADATA_ENABLED=1` on a deployment that already has ACC-001/002
active is non-destructive: the metadata endpoints become reachable, the `banking_accounts`
table already exists (created by ACC-001), and no schema change is required. Existing
account and transaction rows are unaffected. The first metadata write creates the first
`ACCOUNT#{account_id}` partition row in the table.

## 10. Open Questions / Assumptions

1. **Image size limit.** The 5 MB default (`BANKING_IMAGE_MAX_BYTES=5242880`) is a
   conservative choice matching the messaging image path. If creators want to attach
   receipts or invoices (higher resolution), this can be raised per-deployment without code
   change.

2. **Narrative version history.** The current design is last-write-wins with no history.
   If audit requirements demand a narrative change log, a `META#{transaction_id}#NARRATIVE_V#{n}`
   multi-row scheme would be needed. Out of scope for this ticket; deferred to a future
   ACC-003-ext ticket.

3. **`has_metadata` read cost.** Issuing one `COUNT`-only DDB query per transaction in the
   list response adds read-unit cost proportional to page size. If the additional cost is
   significant in production (monitored via DDB consumed-capacity metrics), `has_metadata`
   can be denormalized onto the account row (`last_enriched_transaction_ids`) or simply
   omitted (returned as `False`) until a dedicated metadata-browse endpoint is implemented.

4. **Image deletion.** Today `set_transaction_image` overwrites the DDB row without
   deleting the previous S3 object. An explicit `DELETE .../image` endpoint (not in this
   ticket) would be needed to support full image removal. Orphan objects are handled by
   S3 lifecycle rules configured outside the application.

5. **ACC-004 view-based metadata visibility.** The current spec says viewers may read
   metadata only if their View grants `metadata_visibility != "hidden"`. The projection
   logic lives in ACC-004/VEW-003 and is not implemented here; ACC-003 only enforces the
   owner/co-owner gate. The `TransactionMetadataOut` shape is passed through to VEW-003's
   projection helper once ACC-004 ships.

6. **Assumption: `transaction_id` == ledger `entry_id`.** ACC-002 surfaces the billing
   ledger `entry_id` (from `billing_shared.ulidish()`) as `transaction_id`. This spec
   assumes that mapping is stable. If ACC-002's projection changes the identifier
   scheme, ACC-003 must be updated to match.
