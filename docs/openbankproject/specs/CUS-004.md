# CUS-004 — Financial Products + Product Collections (catalog-pattern reuse)

**Ticket type**: Backend (product model + collections)
**Priority**: P2
**Estimate**: 3 days
**Flag**: `FINANCIAL_PRODUCTS_ENABLED` (default OFF)
**Dependencies**: CUS-001 (shared attribute-type enum, audit conventions, flag pattern)

---

## 1. Summary & Goal

CUS-004 introduces a **financial-product** entity and **product-collection** grouping to
testlogon, mapping to the OBP open-data `/products` and `/product_collections` surfaces
(e.g. savings-account products, card products, loan products). A financial product is the
bank-product analogue of a catalog SKU; a collection is an ordered grouping analogous to a
catalog category.

The goal is an additive, default-OFF backend feature that:

1. Stores financial products with typed attributes in a dedicated `financial_products`
   DynamoDB table, reusing the single-table patterns from `app/routers/catalog.py`.
2. Exposes admin-only CRUD endpoints for products and collections under
   `/ui/financial-products`.
3. Provides a category-filtered list backed by a GSI (no scan), cursor-paginated via
   `app/core/cursor.py`.
4. Audits every mutation to `T.alerts` using the same `audit_event` helper that every
   other CUS ticket and KYC use.
5. Is entirely additive and leaves `T.catalog`, `app/routers/catalog.py`,
   `app/routers/billing.py`, and every other existing endpoint untouched.

## 2. Context & Current State

### 2.1 Existing catalog (the pattern to reuse)

`app/routers/catalog.py` owns the shopping-catalog feature on `T.catalog`
(`S.catalog_table_name`, default `"shopping_catalog"`, `app/core/settings.py:832`).
Its single-table layout uses `PK`/`SK` with the helpers:

- `cat_pk(category_id)` → `"CAT#{category_id}"` (`catalog.py:55`)
- `item_pk(item_id)` / `item_sk(item_id)` → `"ITEM#{item_id}"` (`catalog.py:59–64`)
- `_query_page(pk, sk_begins, limit, start_key)` — keyed query returning `(items, lek)`
  (`catalog.py:182–196`)
- `encode_next_token` / `decode_next_token` — base64 cursor helpers used in every list
  endpoint (`catalog.py:158–175`)
- `create_item` at `catalog.py:353` — conditional `put_item` with
  `attribute_not_exists(PK) AND attribute_not_exists(SK)`
- `reorder_catalog_items` at `catalog.py:422` — sets integer `position` per item via
  `update_item`
- `search_items` at `catalog.py:466` — full-scan search with token matching

CUS-004 reuses these patterns on a *separate* `financial_products` table so as never to
pollute the shopping catalog.

Note that `catalog.py` uses ISO-string `created_at` (`now_iso()`, `catalog.py:47`), while
the KYC/billing stack uses integer Unix `created_at` (`now_ts()`). CUS-004 adopts integer
`created_at` (Unix seconds from `app/core/time.now_ts`) to stay consistent with the KYC
pattern and to satisfy the numeric-GSI-sort-key constraint (see §3).

## 3. Data Model

### 3.1 DynamoDB table: `financial_products`

Single-table design on a new dedicated table, mirroring `T.catalog`'s `PK`/`SK` scheme.
Table name configured by `S.financial_products_table_name` (env
`FINANCIAL_PRODUCTS_TABLE_NAME`, default `"financial_products"`).

**Primary key**: `PK` (S), `SK` (S)

**Row types**:

| Row type | PK | SK | Description |
|---|---|---|---|
| Product META | `PRODUCT#{product_code}` | `META` | Core product fields + version |
| Product attribute | `PRODUCT#{product_code}` | `ATTR#{attribute_id}` | Typed KV attribute |
| Collection META | `COLLECTION#{collection_code}` | `META` | Ordered `product_codes` list |

**Key helper functions** (in `app/services/financial_products.py`):

```python
def _prod_pk(product_code: str) -> str:
    return f"PRODUCT#{product_code}"

def _coll_pk(collection_code: str) -> str:
    return f"COLLECTION#{collection_code}"
```

**GSI `GSI_CATEGORY`**:

| Attribute | Value | Type |
|---|---|---|
| Partition key | `gsi_cat_pk` | S — value `CATEGORY#{category}` |
| Sort key | `created_at` | **N** (integer Unix seconds) |

Only product META rows that have a `category` field carry `gsi_cat_pk`; attribute and
collection rows are sparse (no `gsi_cat_pk`), so they never pollute this GSI.

**CRITICAL**: `attr_types={"created_at": "N"}` **must** be declared in the `TableDef` in
`scripts/local-ddb-init.py`. Omitting it causes DynamoDB to store `created_at` as String
→ `ValidationException` at runtime when the GSI is queried with an integer range condition
(CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha).

**`TableDef` entry** (to add to `scripts/local-ddb-init.py`):

```python
TableDef(
    _resolve_table_name(S.financial_products_table_name, "financial_products"),
    "PK",
    "SK",
    gsi=[
        {
            "index_name": "GSI_CATEGORY",
            "partition_key": "gsi_cat_pk",
            "sort_key": "created_at",
        }
    ],
    attr_types={"created_at": "N"},
),
```

```
{
  "PK": "PRODUCT#{product_code}",
  "SK": "META",
  "entity": "product",
  "product_code": str,            # natural key, OBP product_code
  "name": str,
  "parent_product_code": str|None,
  "category": str|None,
  "family": str|None,
  "super_family": str|None,
  "more_info_url": str|None,
  "description": str|None,
  "created_at": int,              # Unix seconds (now_ts())
  "updated_at": int,
  "version": int,                 # starts at 1; incremented by update_product
  "gsi_cat_pk": str|None,        # "CATEGORY#{category}" — present only when category != None
}
```

### 3.3 Product attribute item shape

```
{
  "PK": "PRODUCT#{product_code}",
  "SK": "ATTR#{attribute_id}",
  "entity": "product_attribute",
  "product_code": str,
  "attribute_id": str,            # uuid4().hex[:12]
  "name": str,
  "type": "STRING"|"INTEGER"|"DOUBLE"|"DATE_WITH_DAY",
  "value": str,                   # always stored as string; caller parses by type
  "created_at": int,
}
```

### 3.4 Collection META item shape

```
{
  "PK": "COLLECTION#{collection_code}",
  "SK": "META",
  "entity": "collection",
  "collection_code": str,
  "name": str,
  "product_codes": list[str],     # ordered, deduped list
  "updated_at": int,
}
```

Collections have no `version` field (their mutation is idempotent read-merge-write;
concurrent collection edits do not require optimistic locking since the list is an ordered
set, not a financial state).

## 5. Detailed Behavior & Edge Cases

### 5.1 Product lifecycle

**Create**: `POST /ui/financial-products` uses a conditional `put_item` with
`attribute_not_exists(PK) AND attribute_not_exists(SK)` (identical to `catalog.py:383`).
`product_code` is the natural key — the caller chooses it (OBP convention). Server-mints
nothing. Initial `version=1`, `created_at=updated_at=now_ts()`.

**Update — optimistic concurrency**: `PATCH /{product_code}` requires `expected_version`
in the request body. The handler calls `store.update_product(product_code,
expected_version=body.expected_version, ...)`, which issues:
```python
ConditionExpression="version = :expected_version"
```
A `ConditionalCheckFailedException` from DynamoDB is caught and re-raised as
`ProductConflictError` → HTTP 409. The update sets `version = version + 1` and
`updated_at = now_ts()`. This mirrors `kyc_cases.py:209–233` exactly.

**GSI maintenance on category change**: when `category` changes during an update, the
handler must update `gsi_cat_pk` atomically in the same `update_item` call — either to
`"CATEGORY#{new_category}"` or removed (if set to `None`, use a `REMOVE gsi_cat_pk`
clause). A two-step read-then-write would create a race.

**Delete**: deletes the META row and all `ATTR#` sibling rows (batch_writer). Collections
that reference the deleted `product_code` are **not** automatically cleaned — the caller is
responsible. An open question (§10) is whether a 409 guard is needed if the product is in
any collection.

### 5.2 Attribute lifecycle

Attributes are plain KV rows with no version of their own. `set_attribute` always creates
a new `attribute_id`; there is no "update in place by name" (same as KYC attributes in
CUS-001). To replace an attribute by name, the caller deletes the old one and sets a new
one. `list_attributes` returns all `ATTR#` rows for the product in no guaranteed order (DDB
returns them in SK order, which is lexicographic on the `attribute_id` hex).

### 5.3 Collection lifecycle — read-merge-write

`upsert_collection` fully replaces `product_codes` with the caller-supplied list
(deduped order-preserving via `list(dict.fromkeys(product_codes))`). This mirrors the KYC
template-packets write-merge pattern (CLAUDE.md). A `get_item` is issued first to read the
current `name` if the body omits it (not applicable here since `name` is required). A plain
`put_item` (no conditional) is used — upsert semantics.

`add_to_collection` / `remove_from_collection` do a read-modify-write:
```
current = get_collection(collection_code)
new_list = current["product_codes"] + [product_code]   # add: append if absent
new_list = [c for c in current["product_codes"] if c != product_code]  # remove
```
These are not atomic (no optimistic lock on collections). For this phase, last-write-wins
is acceptable since collection ordering is an admin configuration concern, not a financial
state. A follow-up can add optimistic concurrency on collections if contention is observed.

### 5.4 Route-ordering test (mandated by acceptance criteria)

`GET /ui/financial-products/collections` MUST resolve to the `list_collections` handler,
not the `get_product` handler. This is verified in the pytest test (§9.1, test case
`test_route_ordering_collections_not_product_code`).

### 5.5 Pagination

`list_products` uses `encode_cursor` / `decode_cursor` from `app/core/cursor.py:94–131`
(HMAC-signed, version-tagged cursor). The `LastEvaluatedKey` from DynamoDB is wrapped:
```python
cursor = encode_cursor(last_evaluated_key)   # None when no more pages
```
Clients pass `?cursor=<value>` which is decoded via `decode_cursor` → passed as
`ExclusiveStartKey`. An invalid or tampered cursor decodes to `None` (the cursor.py
implementation swallows decode errors) — this is treated as "start from beginning", not a
400 error, matching existing behavior in billing/KYC list endpoints.

### 5.6 Public / read-only endpoints

In the OBP open-data model, financial products are public (no auth). This ticket
implements all endpoints as admin-only for the initial version (the bank admin configures
products; consumers see them via a future public read endpoint). A public no-auth
`GET /ui/financial-products/{product_code}` can be added in CUS-005 or a follow-up, gated
by an additional `FINANCIAL_PRODUCTS_PUBLIC_READ_ENABLED` flag and registered in
`API_KEY_ROUTE_EXEMPTIONS` (`app/services/api_key_route_scope_registry.py:70`).

### 5.7 Audit events

Every mutation emits to `T.alerts` via `audit_event` (`app/services/alerts.py:644`):

| Event | Trigger |
|---|---|
| `product.created` | `create_product` success |
| `product.updated` | `update_product` success |
| `product.deleted` | `delete_product` success |
| `product.attribute_set` | `set_attribute` success |
| `product.attribute_deleted` | `delete_attribute` success |
| `product.collection_updated` | `upsert_collection`, `add_to_collection`, `remove_from_collection` success |

These are also added to `WEBHOOK_EVENT_TYPES_V2` in `app/services/webhook_service.py` so
consumers can subscribe via the existing webhook registry.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 dev/prod parity

CUS-004 has **no money-movement**. All state lives in DynamoDB. There is no `if S.dev_mode`
branch in `app/services/financial_products.py` or `app/routers/financial_products.py`.
The same code runs against DynamoDB Local (port 8001, `DDB_ENDPOINT_URL=http://localhost:8001`)
in dev and real DynamoDB in prod. The existing `_safe_table` / `ddb()` abstraction
in `app/core/aws.py` handles endpoint routing transparently.

Audit events written to `T.alerts` use `app/services/alerts.py:write_alert` which already
handles dev (local DDB + in-process SSE) vs prod (DDB + SES) via the existing
`send_alert_email` abstraction — CUS-004 adds no new branching.

### 7.2 Idempotency

- **Create** (`POST /ui/financial-products`): conditional `put_item` with
  `attribute_not_exists(PK) AND attribute_not_exists(SK)`. A duplicate call returns 409;
  it does not silently overwrite.
- **Upsert collection** (`PUT /collections/{code}`): idempotent by design. Repeated calls
  with the same body produce the same state (read-merge-write with dedup). The collection
  row is a plain `put_item` (no condition); calling with the same `product_codes` is a
  no-op in effect.
- **Update product**: requires `expected_version`. The same `PATCH` body replayed after a
  successful write will fail with 409 (version mismatch) — correct behavior for optimistic
  concurrency.
- **set_attribute**: always mints a fresh `attribute_id`. Calling twice with the same
  `name`/`value` creates two distinct attribute rows. This matches CUS-001 / KYC attribute
  behavior (attributes are identified by id, not name).

### 7.3 Security

- All write endpoints require admin/root role. A USER-role caller on any
  `POST`/`PATCH`/`PUT`/`DELETE` receives 403 via `require_admin_or_root` from
  `app/auth/policy.py:67`.
- `product_code` is a path parameter that becomes a DynamoDB partition key. It must be
  validated to reject characters that could confuse key construction. Validation rule:
  `product_code` must match `^[a-zA-Z0-9_\-]{1,64}$`. This is enforced in the Pydantic
  model via `Field(pattern=r"^[a-zA-Z0-9_\-]{1,64}$")`.
- `more_info_url` is a URL field; validate with Pydantic `AnyHttpUrl` or a `http[s]://`
  prefix check to prevent stored XSS via open-redirect.
- Attribute `value` is stored as a plain string with no interpretation. It is never
  executed. Max 2048 chars (enforced by Pydantic `Field(max_length=2048)`).

### 7.4 Money-safety

CUS-004 introduces no money movement, no ledger writes, no wallet mutations, and no
payment-provider calls. There is nothing analogous to `new_ledger_entry`,
`apply_wallet_delta`, `settle_or_reverse_ledger`, or `_fraud_gate` here. Financial products
are a configuration entity (product catalogue metadata), not a transactional entity. Any
future ticket that uses a financial product as a billing template (e.g. "create an account
of this product type") will go through the existing billing primitives in
`app/services/billing_shared.py` at that time.

DynamoDB when items carrying `gsi_cat_pk` are written (no manual backfill needed).

## 10. Open Questions / Assumptions

1. **Public read endpoint**: The OBP open-data spec makes financial products publicly
   readable (no auth). This ticket implements admin-only. Should `GET /{product_code}` also
   be available without auth for consumers? If yes, add to `API_KEY_ROUTE_EXEMPTIONS`
   (see `app/services/api_key_route_scope_registry.py:70`) in CUS-005.
   **Assumption**: admin-only for now; public read deferred to CUS-005 or follow-up.

2. **Product deletion guard**: if a product is referenced in a collection, should deletion
   be blocked (409) or silently leave a dangling reference in the collection? Current spec
   says best-effort cleanup (no guard). If banking integrity requires referential
   consistency, add a `list_collections_for_product` scan and block deletion.
   **Assumption**: no deletion guard in this ticket.

3. **`more_info_url` validation**: OBP allows arbitrary URL strings. Pydantic `AnyHttpUrl`
   is strict (requires scheme). A more permissive `Optional[str]` with a custom regex may
   be needed for OBP compatibility.
   **Assumption**: use `Optional[str]` with a `^https?://` prefix check.

4. **Collection concurrency**: the current spec has no optimistic lock on collections.
   If two admin sessions concurrently add different products, one write silently wins.
   Acceptable for a config entity, but a `version` field could be added if needed.
   **Assumption**: no collection versioning in this ticket.

5. **Webhook event scope**: the `product.created` / `product.updated` events are added to
   `WEBHOOK_EVENT_TYPES_V2` but are not added to any per-consumer subscription scope.
   Should they be gated by an `financial_products:webhooks` API-key scope?
   **Assumption**: no new scope in this ticket; the events use the existing unrestricted
   webhook subscription model.
