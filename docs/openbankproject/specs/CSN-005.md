**Type:** Feature | **Priority:** P3 | **Estimate:** 2.5d

**Source ticket:** `docs/openbankproject/OBP_CONSENTS_DYNAMIC_TICKETS.md` §CSN-005

---

## 1. Summary & Goal

CSN-005 delivers the **Open-data Branches and ATMs** surface from the Open Bank Project (OBP)
specification. The OBP open-data API allows any caller — without authentication — to discover
physical bank locations: branch addresses, opening hours, accessibility flags, and ATM
co-ordinates. Testlogon has no physical branches; this ticket exists purely to establish OBP
Tier-3 parity behind a default-off feature flag.

The deliverable is two things:

1. **Admin CRUD** (ROOT-only): create, update, and delete `Branch` and `ATM` records stored in a
   single DynamoDB table.
2. **Public read** (no auth): four unauthenticated GET endpoints that return active records.

Everything is **additive and flag-gated default-off**. When `OPEN_DATA_ENABLED` is `false`, no
router is registered, no DynamoDB table is read, and the platform is byte-for-byte unchanged. When
the flag is on, a new `open_data` table is consumed but no existing table is touched.

`audit_event(event, user_sub, request, **fields)` (`app/services/alerts.py:644`) is the single

`open_data.branch_upsert`, `open_data.atm_upsert`, and `open_data.delete`.

### 2.6 Pagination with cursor

Cursor-based pagination is provided by `encode_cursor` / `decode_cursor` in `app/core/cursor.py`
(`cursor.py:94, 103`). List endpoints use these to emit a signed, tamper-evident `next_cursor`

KYC list endpoints.

All timestamps are integer Unix seconds from `app/core/time.py:2`. `T.*` table handles are
`_FloatSafeTable` wrappers (`app/core/tables.py:29`) that coerce Python floats to `Decimal` on
write, so geo co-ordinates (`lat`/`lng`) stored as Python floats are safe to write directly.

## 3. Data Model

### 3.1 New DynamoDB table: `open_data`

A **single table** stores both `Branch` and `ATM` records with `kind` as the partition key
and `resource_id` as the sort key, keeping the two entity types fully isolated by partition
while sharing one table and one `T.*` handle.

**`TableDef` to add in `scripts/local-ddb-init.py`:**

```python
TableDef(
    _resolve_table_name(S.open_data_table_name, "open_data"),
    "kind",          # partition key (S): "BRANCH" | "ATM"
    "resource_id",   # sort key      (S): "brn_{uuid4().hex}" | "atm_{uuid4().hex}"
    gsi=[
        {
            "index_name": S.open_data_active_index,   # "ByActive"
            "partition_key": "kind_active",           # "BRANCH#1" | "ATM#1" | "ATM#0" etc.
            "sort_key": "name",
        }
    ],
    # name is a String — no attr_types needed for this GSI.
)
```

**GSI design — `ByActive`:**

The public list endpoints must return only active records efficiently. A compound `kind_active`
partition key (e.g. `"BRANCH#1"` for active branches, `"BRANCH#0"` for inactive) and `name`
sort key provides an exact-match query returning only active records without a scan or
`FilterExpression` post-filter. The partition value is written on every upsert:

```python
item["kind_active"] = f"{kind}#{1 if is_active else 0}"
```

Admin list endpoints (which must see inactive records) query the base table directly with
`KeyConditionExpression: Key("kind").eq("BRANCH")`.

**No numeric GSI sort key in this table:** `name` is a String (`S`), so no `attr_types` override
is needed. If a future revision adds a `created_at` numeric GSI sort key it must declare
`attr_types={"created_at": "N"}` per the repo's documented gotcha
(`scripts/local-ddb-init.py:34` — the `TableDef.attr_types` field comment; the `users` table
at `:53` is an existing example of this pattern applied).

## 4. API / Service Design

### 4.1 Pydantic models (`app/models.py`)

```python
class OpeningHours(BaseModel):
    day: Literal["Mon","Tue","Wed","Thu","Fri","Sat","Sun"]
    opens: str   # "HH:MM" 24-hour
    closes: str  # "HH:MM" 24-hour

class AddressIn(BaseModel):
    line1: str
    line2: str | None = None
    city: str
    region: str | None = None
    country: str   # validated: exactly 2 uppercase alpha chars
    postcode: str

class LocationIn(BaseModel):
    lat: float   # -90 .. +90
    lng: float   # -180 .. +180

class BranchIn(BaseModel):
    name: str
    address: AddressIn
    location: LocationIn
    opening_hours: List[OpeningHours] = []
    accessibility: List[str] = []
    phone: str | None = None
    is_active: bool = True

class BranchOut(BaseModel):
    branch_id: str
    name: str
    address: AddressIn
    location: LocationIn
    opening_hours: List[OpeningHours]
    accessibility: List[str]
    phone: str | None
    is_active: bool
    created_at: int
    updated_at: int

class AtmIn(BaseModel):
    name: str
    address: AddressIn
    location: LocationIn
    is_active: bool = True
    has_deposit: bool = False
    is_accessible: bool = False

class AtmOut(BaseModel):
    atm_id: str
    name: str
    address: AddressIn
    location: LocationIn
    is_active: bool
    has_deposit: bool
    is_accessible: bool
    created_at: int
    updated_at: int

class OpenDataListOut(BaseModel):
    items: List[BranchOut | AtmOut]
    next_cursor: str | None
```

Validation rules enforced by Pydantic validators:
- `country` must match `^[A-Z]{2}$`.
- `lat` must be in `[-90, 90]`; `lng` in `[-180, 180]`.
- `opens`/`closes` must match `^\d{2}:\d{2}$` and `opens < closes`.

### 4.2 Service (`app/services/open_data.py`)

```python
def upsert_branch(admin_sub: str, body: BranchIn, req) -> BranchOut:
    ...
def upsert_atm(admin_sub: str, body: AtmIn, req) -> AtmOut:
    ...
def get_branch(branch_id: str) -> BranchOut | None:
    ...
def get_atm(atm_id: str) -> AtmOut | None:
    ...
def list_branches(*, active_only: bool = True,
                  cursor: str | None = None,
                  limit: int = 50) -> tuple[list[BranchOut], str | None]:
    ...
def list_atms(*, active_only: bool = True,
              cursor: str | None = None,
              limit: int = 50) -> tuple[list[AtmOut], str | None]:
    ...
def delete_resource(kind: Literal["BRANCH", "ATM"], resource_id: str,
                    admin_sub: str, req) -> None:
    ...
```

**`upsert_branch` / `upsert_atm` implementation notes:**
- On create: `resource_id = f"brn_{uuid4().hex}"` (or `atm_*`); `created_at = updated_at = now_ts()`.
- On update (if `resource_id` provided in the path): conditional `put_item` or `update_item` with
  `updated_at = now_ts()`; `created_at` preserved.
- Both write `kind_active = f"{kind}#{1 if body.is_active else 0}"`.
- Both call `audit_event("open_data.branch_upsert" | "open_data.atm_upsert", admin_sub, req,
  resource_id=..., name=...)` after a successful write.
- Both use `T.open_data.put_item(Item=item)` — no conditional expression is required for upsert
  semantics since `resource_id` is admin-chosen on PUT or system-generated on POST.

**`list_branches` / `list_atms` implementation notes:**
- `active_only=True` (public path): query `ByActive` GSI with
  `KeyConditionExpression=Key("kind_active").eq(f"{kind}#1")`, `Limit=limit`,
  `ExclusiveStartKey=decode_cursor(cursor)`.
- `active_only=False` (admin path): query base table with
  `KeyConditionExpression=Key("kind").eq(kind)`.
- `DynamoDB FilterExpression` is **not** used; the GSI partition value is the filter.
- Return `(items, encode_cursor(resp.get("LastEvaluatedKey")))`.

**`delete_resource`:**
- `T.open_data.delete_item(Key={"kind": kind, "resource_id": resource_id})`.
- Audit `open_data.delete` with `kind`, `resource_id`.
- A non-existent `resource_id` is a no-op (DynamoDB `delete_item` is idempotent); the handler
  returns `204` regardless.

## 5. Detailed Behavior & Edge Cases

### 5.1 Create vs. update semantics

`POST /ui/open-data/branches` always generates a fresh `resource_id` (`brn_{uuid4().hex}`).
`PUT /ui/open-data/branches/{branch_id}` is a full replacement upsert: if a record with that
`resource_id` exists it is overwritten; if it does not exist a new record is created with the
caller-supplied id. This matches OBP's upsert-on-PUT semantics and avoids a separate
`ConditionExpression` "must exist" gate on PUT (which would return 404 for a legitimate new id).
`created_at` is preserved on update by fetching the existing item before the `put_item` (or by
using `update_item SET ... IF attribute_exists(created_at)`).

### 5.2 Active/inactive visibility

- Public `GET /open-data/branches` queries the `ByActive` GSI with `kind_active="BRANCH#1"`.
  Inactive branches are in a different GSI partition (`"BRANCH#0"`) and are never returned.
- Public `GET /open-data/branches/{branch_id}` fetches the item by PK+SK and then checks
  `is_active` in Python — if `false`, returns `404 open_data_not_found`. This prevents a
  caller from probing whether an inactive branch exists.
- Admin `GET /ui/open-data/branches` uses `active_only=False` by default (returns all); the
  query parameter `?active_only=true` can restrict to the active set.

### 5.3 DELETE idempotency

DynamoDB `delete_item` does not error on a missing key. The admin `DELETE` handler always
calls `delete_item` directly (without a pre-existence check) and returns `204` regardless of
whether the item existed, satisfying the idempotency requirement. Note: `app/services/host_inventory.delete_host`
(`host_inventory.py:360`) performs a `get_item` pre-check and returns early without calling
`delete_item` when the host is absent; CSN-005 `delete_resource` skips that pre-check and
relies on DynamoDB's own idempotent `delete_item` semantics instead.

### 5.4 Coordinate precision and float safety

`lat`/`lng` are stored as DynamoDB `N` (Number) attributes. The `_FloatSafeTable` wrapper
(`app/core/tables.py:29`) converts Python `float` to `Decimal(str(v))` on every `put_item`
and `update_item` (via `_to_decimal` at `tables.py:11`), so no float-precision issue arises at the storage layer. The Pydantic model
returns them as `float` in JSON responses, which is the standard representation.

### 5.5 Pagination DoS guard

Public list endpoints accept an optional `?limit=N` query parameter, capped at `min(N, 200)`.
The default is 50. A large `limit` does not bypass the DynamoDB `Limit` parameter — the cap is
enforced before passing to the query, preventing a single unauthenticated request from
exhausting read capacity.

### 5.6 Audit on admin GETs

Admin `GET` endpoints do **not** emit an audit event (reads are not mutating). Only
`upsert_branch`, `upsert_atm`, and `delete_resource` audit. This is consistent with the pattern
throughout the codebase (api_keys, KYC, billing).

### 5.7 Opening hours validation

`opens` and `closes` strings are validated as `HH:MM` format and must satisfy `opens < closes`
(lexicographic comparison is valid for zero-padded 24-hour times). A branch with
`[{day: "Mon", opens: "09:00", closes: "17:00"}]` is valid;
`[{day: "Mon", opens: "17:00", closes: "09:00"}]` raises a Pydantic `ValidationError` → HTTP 422.
An empty `opening_hours` list is allowed (branch with unspecified hours).

### 5.8 Geo bounding

Out-of-range `lat`/`lng` values (e.g. `lat=200`) raise a Pydantic `ValidationError` → HTTP 422
with a clear field-level error message. The validator uses `ge=-90, le=90` and `ge=-180, le=180`
Pydantic field constraints.

### 5.9 No public write surface

The public router carries **zero** non-GET routes. There is no publicly accessible POST, PUT,
or DELETE. The admin write surface is `/ui/open-data/…` behind `require_root_session`, which
requires a valid ROOT-role session cookie. Unauthenticated POSTs to the public prefix return
`404` (the route does not exist, not `403`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 (dev/prod parity)

There is **no `if S.dev_mode:` branch** anywhere in the CSN-005 service or router. All DynamoDB
reads and writes go through the frozen `T.open_data` handle, which resolves to DynamoDB Local in
dev (`DDB_ENDPOINT_URL=http://localhost:8001`) and to real DynamoDB in prod. The `_FloatSafeTable`
wrapper handles Decimal coercion transparently in both environments. This is exactly the same
posture documented for every CSN ticket in `OBP_CONSENTS_DYNAMIC_TICKETS.md:91-95`.

### 7.2 Idempotency

- `PUT /ui/open-data/branches/{id}` is a full-replace upsert — repeating it with the same body
  produces the same stored item (updated `updated_at` differs; the logical result is the same).
- `DELETE` is idempotent: a second call on a deleted resource returns `204` with no error.
- `POST /ui/open-data/branches` mints a new `resource_id` on every call — it is not idempotent
  by design (matches standard REST semantics for POST-as-create).

### 7.3 Security

- **No public write surface.** All mutation endpoints require `Depends(require_root_session)`.
  A non-ROOT authenticated user gets `403`; an unauthenticated caller on the admin path gets
  `401` (session missing) → this is the normal `require_root_session` path
  (`app/auth/deps.py:308`).
- **Path traversal.** The `{branch_id}` and `{atm_id}` path parameters are opaque DynamoDB
  sort key values (validated by `^(brn|atm)_[0-9a-f]{32}$` regex in the handler before the
  `get_item` call). An id that does not match the regex returns `400 invalid_resource_id`, not
  a DynamoDB read.
- **Input validation.** Country codes, coordinates, and opening-hours strings are validated by
  Pydantic before reaching the service layer. Invalid input returns HTTP 422 with field-level
  errors, never propagated to DynamoDB.
- **`kind` is always system-set.** The `kind` attribute (`"BRANCH"` or `"ATM"`) is set by the
  service based on which endpoint was called — it is never taken from the request body, so a
  caller cannot write an ATM record to the `BRANCH` partition.
- **No money movement.** CSN-005 has no billing, wallet, ledger, or payment path. There are
  no `new_ledger_entry`, `apply_wallet_delta`, `settle_or_reverse_ledger`, or `_fraud_gate`
  calls. This is purely a metadata store; money-safety constraints do not apply.

### 7.4 Audit trail

Every admin mutation emits an `audit_event` to `T.alerts` via `app/services/alerts.py:644`:

- `audit_event("open_data.branch_upsert", admin_sub, req, resource_id=..., name=...)`
- `audit_event("open_data.atm_upsert", admin_sub, req, resource_id=..., name=...)`
- `audit_event("open_data.delete", admin_sub, req, kind=..., resource_id=...)`

No public GET emits an audit event.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact when flag is off

When `OPEN_DATA_ENABLED=0` (the default):

- The `open_data` table is never read or written because the routers are not registered.
- `app/main.py` does not import from `app/routers/open_data` (the import is inside the
  `if S.open_data_enabled:` block).
- No startup task, middleware, or module-level code touches the `open_data` table.
- Existing test runs are unaffected: the table is not created by `local-ddb-init.py` unless the
  `TableDef` entry is included in the `_table_defs()` return list, which only runs at
  `just up` / `just restart`. Adding the `TableDef` unconditionally (regardless of the flag)
  is the correct approach — the table existing but unused is harmless; an absent table at
  flag-on time would cause a startup `ResourceNotFoundException`. This matches the pattern for
  every other optional table in the codebase.

### 8.2 Schema migration

There is no existing `open_data` table to migrate. The `TableDef` entry in
`scripts/local-ddb-init.py` creates the table on `just restart`. In production, the table is
created via an `aws dynamodb create-table` call (or Terraform/CDK) before the flag is turned on.
No backfill is needed because the table starts empty.

### 8.3 `API_KEY_ROUTE_EXEMPTIONS` is additive

Adding four entries to the `API_KEY_ROUTE_EXEMPTIONS` dict is a pure addition — existing entries
are untouched. No existing route has its enforcement changed.

## 10. Open Questions / Assumptions

1. **Pagination on public endpoints: should `next_cursor` be signed?** The current cursor
   implementation (`cursor.py:94`) signs cursors with an HMAC (`CURSOR_SIGNING_SECRET`). This
   is appropriate for authenticated endpoints (prevents cursor forgery). For fully public
   endpoints, an unsigned cursor would also be acceptable. This spec retains the signed cursor
   for consistency; if performance profiling shows signing overhead is a concern on high-traffic
   public endpoints, unsigned cursors can be adopted as a follow-up.

2. **Country code validation source:** This spec validates `country` as `^[A-Z]{2}$` (ISO 3166-1
   alpha-2 format). It does not maintain a whitelist of all 249 country codes. If OBP parity
   requires exact ISO whitelist validation, a static set can be added to the Pydantic model's
   validator without changing the DDB schema.

3. **`PUT` upsert vs. "must exist" semantics:** The spec treats `PUT` as a true upsert (create
   if absent, replace if present). OBP's own spec treats PUT as "must exist" (404 if unknown).
   This can be flipped to a conditional `update_item` with `attribute_exists(kind)` raising 404
   if desired; the DDB schema is unchanged either way. The assumption here is upsert semantics
   for simplicity.

4. **`DELETE` hard vs. soft delete:** This spec performs a hard `delete_item`. A soft delete
   (`is_active=false`) is an alternative that preserves the audit trail in the table itself.
   Soft delete can be implemented later without a schema change (the `is_active` flag already
   exists); the hard-delete path is chosen here as the simpler default.

5. **`opening_hours` max length:** No cap on the `opening_hours` list is enforced beyond
   Pydantic's model validation. A maximum of 7 entries (one per day of the week) could be
   enforced by a `max_length=7` field constraint if desired.

6. **Public endpoint rate limiting:** No per-IP rate limit is applied to the four public GET
   endpoints in this ticket. A DDoS-protection layer (e.g. CloudFront rate limiting or a
   lightweight per-IP bucket) is a separate infrastructure concern and is not scoped here.
