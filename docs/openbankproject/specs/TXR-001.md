# TXR-001 — TransactionRequest entity — DDB model, table, flag + create endpoint (records INITIATED)

**Ticket prefix**: TXR | **Priority**: P1 (foundation) | **Estimate**: 2.5 days
**Source**: `docs/openbankproject/OBP_TXN_REQUESTS_SCA_TICKETS.md` §TXR-001

---

## 1. Summary & Goal

Introduce the `TransactionRequest` entity — a unified, typed money-movement request object — as a new DynamoDB table, Pydantic models, service layer, and a single `POST /ui/txn-requests` endpoint that records a request with `status="INITIATED"` and returns immediately. **No money moves on create.** This ticket is the foundation that TXR-002 (state machine + limits), TXR-003 (SCA/step-up challenge), TXR-004 (execution), and TXR-005 (tests + FE) all build on.

The Open Bank Project model defines a Transaction Request as the durable "intent" object that walks a status machine (`INITIATED → PENDING → COMPLETED | FAILED`) and separates the act of recording a payment intention from the act of executing it. testlogon already moves money through per-flow endpoints (`billing.py`, `tip_ledger.py`, `creator_payouts.py`) with no unified request wrapper. This ticket adds that wrapper — a thin orchestration layer — without touching any existing billing primitive.

The entire feature is behind a new `TXN_REQUESTS_ENABLED` flag, default `false`. Every new endpoint, startup task, and table consumer is conditioned on this flag; existing billing, tip, and payout endpoints are untouched.

## 3. Data Model

### 3.1 DynamoDB table: `txn_requests`

**Table name setting**: `S.txn_requests_table_name` (env `TXN_REQUESTS_TABLE`, default `"txn_requests"`).

**Primary key**:
- PK `user_sub` (S) — the requesting user's Cognito sub / internal user ID.
- SK `request_id` (S) — format `txr_{uuid4().hex}` (16-byte random, 36-char string with prefix). Mirrors the `tip_` prefix in `tip_ledger.py` (line 60: `f"tip_{uuid.uuid4().hex}"`). Note: `api_keys.py` uses `secrets.token_hex(16)` with **no string prefix** on the `key_id` value (the `"key_"` appears only in field names and in the composite secret `f"ak_{key_id}.{secret}"`); the `txr_` prefix is therefore modelled on `tip_ledger.py` alone.

**GSI `GSI_STATUS`**:
- Partition key: `status` (S) — one of `INITIATED`, `PENDING`, `COMPLETED`, `FAILED`.
- Sort key: `created_at` (N — integer Unix seconds).
- **`attr_types={"created_at": "N"}`** is mandatory in the `TableDef`. Without it, DDB stores `created_at` as a String type, causing `ValidationException` when the sweep in TXR-003 queries by integer range. This matches the pattern at `scripts/local-ddb-init.py:83-85`.
- Purpose: TXR-003 sweeps `status=PENDING` requests to expire stale challenges; TXR-002 exposes `?status=` filter queries.

**Item attributes** (all written on create; later tickets add `sca_challenge_id`, `ledger_refs`, `failure_reason`):

| Attribute | DDB type | Notes |
|---|---|---|
| `user_sub` | S | PK — owner |
| `request_id` | S | SK — `txr_{uuid4().hex}` |
| `type` | S | `WALLET_TRANSFER \| COUNTERPARTY \| PAYOUT \| REFUND \| FREE_FORM` |
| `amount_cents` | N | Integer, must be > 0 |
| `currency` | S | ISO 4217, default `"usd"` |
| `target` | M (map) | Per-type shape (see §4.2) |
| `status` | S | `INITIATED` on create |
| `reason` | S / NULL | Caller-supplied narrative |
| `idempotency_key` | S / NULL | Caller-supplied; used for duplicate-create collapse in TXR-004 |
| `created_at` | N | `now_ts()` — also the `GSI_STATUS` sort key |
| `updated_at` | N | `now_ts()` — updated on every transition |
| `sca_challenge_id` | S / NULL | Populated by TXR-003 when SCA is required |
| `ledger_refs` | L / NULL | List of ledger/payout IDs written by TXR-004 |
| `failure_reason` | S / NULL | Machine-readable code set by TXR-004 on FAILED |

**Single-table note**: `txn_requests` is its own table (not combined with `billing`). The billing table's `LEDGER#` rows use `pk=USER#{sub}` and are owned by `billing_shared.py`. The `txn_requests` table uses `user_sub` as PK directly, matching the `sessions`, `totp_devices`, and `alerts` table pattern.

### 4.2 Per-type `target` validation

Validated by `_validate_target(type, target)` in `app/services/txn_requests.py`. Raises `HTTPException(400, code="invalid_target")` on failure:

| Type | Required key(s) | Notes |
|---|---|---|
| `WALLET_TRANSFER` | `to_user_sub: str` | Recipient must differ from sender (validated) |
| `FREE_FORM` | `to_user_sub: str` (optional) | Tip-style; may have no recipient |
| `PAYOUT` | `payout_method_id: str` | Existence checked in TXR-004 at execute time, not here |
| `REFUND` | `payment_intent_id: str` | Format check `pi_` prefix; existence validated at execute time |
| `COUNTERPARTY` | `counterparty_ref: str` | Opaque until Tier-2 Counterparties entity lands |

### 4.3 Service: `app/services/txn_requests.py`

```python
def create_request(
    user_sub: str,
    body: TxnRequestCreateIn,
    req: Request,           # passed through for future fraud gate + IP logging
) -> TxnRequestOut:
```

Steps:
1. Guard: if `not S.txn_requests_enabled` → `raise HTTPException(404)`. (The router also guards, but defensive double-check inside the service keeps the service independently testable.)
2. Validate `body.amount_cents > 0` (Pydantic `gt=0` already enforces; belt-and-suspenders check for direct service calls from tests).
3. Call `_validate_target(body.type, body.target)`.
4. Generate `request_id = "txr_" + uuid.uuid4().hex`.
5. Compute `ts = now_ts()`.
6. Build item dict (all fields listed in §3.1; `status="INITIATED"`, `sca_challenge_id=None`, `ledger_refs=[]`, `failure_reason=None`).
7. Write via `T.txn_requests.put_item(Item=item)`. No `ConditionExpression` on create — `request_id` is a UUID so collisions are negligible; idempotency-key deduplication (TXR-004) is a separate lookup by `idempotency_key` via a future GSI or scan filter.
8. Call `audit_event("txn_request.created", user_sub, req, request_id=request_id, type=body.type, amount_cents=body.amount_cents, currency=body.currency)`.
9. Return `TxnRequestOut` populated from the written item.

**No money movement, no ledger writes, no wallet reads.** INITIATED is a durable intent record only.

Helper `_item_to_out(item: dict) -> TxnRequestOut` converts a raw DynamoDB item to `TxnRequestOut`, coercing DynamoDB `Decimal` to `int` for numeric fields (matches the pattern in `billing_shared.py:179`).

### 4.4 Router: `app/routers/txn_requests.py`

```python

@router.post("", status_code=201, response_model=TxnRequestOut)
async def create_txn_request(
    body: TxnRequestCreateIn,
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag off

When `S.txn_requests_enabled` is `false`:
- Router is not registered → FastAPI returns `404` for `/ui/txn-requests` as if the route does not exist. No import of `txn_requests.py` occurs at startup.
- `T.txn_requests` is still constructed (the table handle is always present in `T`), but no endpoint touches it.
- All existing billing/tip/payout endpoints continue to function identically.

### 5.2 `amount_cents` validation

- `amount_cents <= 0` → Pydantic validation error → FastAPI returns `422 Unprocessable Entity`. This is the standard FastAPI path for `Field(gt=0)` failures; no custom error code needed.

### 5.3 Per-type `target` shape errors

`_validate_target` raises `HTTPException(400, detail={"code": "invalid_target", "type": ..., "missing_key": ...})` for:
- `WALLET_TRANSFER` / `FREE_FORM` with missing `to_user_sub` key.
- `WALLET_TRANSFER` where `target["to_user_sub"] == user_sub` (self-transfer; returns `400` with `code="self_transfer_not_allowed"`).
- `PAYOUT` with missing `payout_method_id`.
- `REFUND` with missing `payment_intent_id` or a value not starting with `"pi_"`.
- `COUNTERPARTY` with missing `counterparty_ref`.
- Any type with extra unexpected keys: tolerated (persisted as-is for forward compat; no error).

### 5.4 Idempotency key

If `body.idempotency_key` is provided, it is stored on the item as-is. Full idempotency-key deduplication (collapse duplicate creates to the same request) is implemented in TXR-004 using a GSI or conditional-put. In TXR-001, the key is simply persisted. A second create with the same `idempotency_key` from the same user currently produces a second `INITIATED` item (because TXR-001 has no deduplication logic). The TXR-004 spec addresses this fully; the TXR-001 acceptance criteria do not require dedup.

### 5.5 `audit_event` is fire-and-forget

`app/services/alerts.py:644` writes to `T.alerts` synchronously but is wrapped in a `try/except` in all call sites. Follow that pattern: wrap the `audit_event` call in `txn_requests.py` in a `try/except Exception` so a transient DDB alert-table failure never blocks the create response.

### 5.6 `target` stored as DynamoDB Map

The `target` dict is stored as a DDB `M` (Map) attribute. The `_FloatSafeTable` proxy in `app/core/tables.py:29` recursively coerces `float` to `Decimal` on `put_item`, so float values in `target` are safe. String-keyed maps do not need `attr_types`.

### 5.7 `INITIATED` is not a terminal state

`INITIATED` requests are eligible for the `POST /ui/txn-requests/{id}/execute` endpoint (TXR-004) — they proceed directly to `COMPLETED` when no SCA is required. If SCA is required (TXR-003), the request is transitioned `INITIATED → PENDING` before `INITIATED` is ever returned to the caller; the create response shows `status="PENDING"`. However TXR-001 does not implement that transition — it always returns `INITIATED`. The SCA decision is added in TXR-003 as a post-create step within `create_request`.

### 5.8 `currency` is stored as-is but validated to 3 chars

The platform ledger is effectively single-currency `"usd"`. Future FX support (OBP gap analysis §B) is out of scope. Accept any 3-char ISO code on create to allow forward compatibility; TXR-004 will enforce currency parity between the request and the target wallet at execute time.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 Dev/prod parity

There are no `if S.dev_mode` branches in `txn_requests.py`. The only provider-abstraction differences are:
- DynamoDB: dev uses DynamoDB Local (port 8001); prod uses real AWS DynamoDB. Same `T.txn_requests` handle in both environments — the `ddb` client in `app/core/aws.py` routes to the endpoint specified by `DDB_ENDPOINT_URL` (set in `.env.local` for dev).
- `audit_event` writes to `T.alerts` in both dev and prod; no mock branch.
- `uuid.uuid4()` produces real UUIDs in both environments; no predictable mock IDs.

### 7.2 Money-safety on create

TXR-001 is money-safe by construction: **no money moves on create**. The `create_request` function does not call `apply_wallet_delta`, `new_ledger_entry`, `write_tip_ledger`, `request_payout`, or any Stripe/PayPal/CCBill primitive. The billing table is not read or written. The only DDB write is to `T.txn_requests`.

### 7.3 Status as the lock

The `status="INITIATED"` write in TXR-001 is unconditional (no `ConditionExpression`). Status becomes the concurrent-modification lock in TXR-002 via `_transition(user_sub, request_id, expected_status, new_status, **patch)`, which uses a conditional `update_item(ConditionExpression=Attr("status").eq(expected_status))`. The `ConditionalCheckFailedException` path in `tickets._conditional_update_meta` at `app/services/tickets.py:723` (~~not 788~~) is the canonical pattern to follow.

### 7.4 Security

- `user_sub` is always taken from the session context (`ctx["user_sub"]`), never from the request body. A caller cannot create a `TransactionRequest` on behalf of another user via this endpoint.
- `request_id` is a UUID4 — 122 bits of entropy — making enumeration infeasible.
- The `target` dict is stored as-is. When `target.to_user_sub` references another user, that user's existence is **not** validated on create (validation at execute time in TXR-004 avoids a TOCTOU race against account deletion and keeps create fast). Document this explicitly in the CLAUDE.md "Common gotchas" update (TXR-005).
- CSRF: the POST endpoint uses `require_ui_session`, which validates `x-csrf-token` header for non-GET requests (CLAUDE.md "CSRF" section). No additional CSRF logic needed.

### 7.5 No double-charge risk at create

Since no money moves, there is no risk of a double-charge from TXR-001. The double-charge risk sits entirely in TXR-004's execution path and is addressed there by the status-as-lock conditional transition.

## 8. Backward Compatibility & Migration

### 8.1 Existing endpoints unchanged

`POST /billing/pay-balance`, `POST /billing/charge-once`, `POST /billing/wallet-deposit`, `POST /billing/refund`, `POST /creator-payouts`, and all tip endpoints in `app/routers/messaging.py` are untouched. They continue to work independently of `TXN_REQUESTS_ENABLED`.

### 8.2 DynamoDB table creation

`scripts/local-ddb-init.py` runs at `just up` and `just restart` via `scripts/local-stack-up.sh`. Adding the `TableDef` entry in §3.2 means the `txn_requests` table is created on the next `just restart`. No existing table is altered. In production, a deployment of the settings + init script creates the new table; no `UpdateTable` migration is required because it is a brand-new table.

### 8.3 `T` dataclass addition

Adding `txn_requests: Any` to the `Tables` frozen dataclass is backward-compatible at runtime. Tests that construct `T` via `object.__setattr__` patch only the fields they use; the new field is invisible to existing tests. Tests that use `T` as a whole (e.g., those that call `create_app()`) will fail if `S.txn_requests_table_name` resolves to a name that does not exist in the moto mock — guard against this in test setup by either (a) creating the table in the moto fixture or (b) pointing `S.txn_requests_table_name` to an existing moto table in test scope.

### 8.4 `app/models.py` additions

Appending `TxnRequestType`, `TxnRequestCreateIn`, `TxnRequestOut` to the end of `app/models.py` is purely additive. No existing model is modified.

## 10. Open Questions / Assumptions

1. **`FREE_FORM` with no `to_user_sub`**: The ticket spec says `to_user_sub` is optional for `FREE_FORM`. This spec treats a `FREE_FORM` request with `target={}` as valid (narrative-only). At execute time (TXR-004), a `FREE_FORM` without `to_user_sub` will debit the sender wallet and write a ledger entry with no corresponding credit (a "fee" or "charge" pattern). If product intent is that `FREE_FORM` always requires a recipient, change `_validate_target` to require `to_user_sub` for `FREE_FORM` as well. **Assumption**: optional until TXR-004 clarifies the execute path.

2. **Self-transfer for `FREE_FORM`**: A `FREE_FORM` with `to_user_sub == user_sub` could be used for a "deposit into own wallet" narrative. Allowing it avoids blocking a valid use case. `WALLET_TRANSFER` with `to_user_sub == user_sub` is still rejected (`code="self_transfer_not_allowed"`) as it would be a no-op debit+credit.

3. **`idempotency_key` uniqueness scope**: The spec assumes `idempotency_key` is scoped to `(user_sub, idempotency_key)`. A malicious user cannot block another user's idempotency key. The deduplication GSI (or scan filter) in TXR-004 queries within the caller's `user_sub` partition. No cross-user collision risk.

4. **`target` JSON depth limit**: No depth limit is specified. In practice, `target` is a flat one-level dict for all defined types. If the `COUNTERPARTY` type eventually carries nested structured data (IBAN, routing number, BIC), the `target` map will grow. No limit is enforced today; DDB's 400KB item limit is the practical ceiling.

5. **Concurrency on create**: Two concurrent POSTs with different `idempotency_key` values (or no key) from the same user will each produce an independent `INITIATED` item. This is correct — there is no single-in-flight constraint at the create level. The single-payout-slot constraint (`claim_payout_sentinel` in `creator_payouts.py:225`) is enforced at execute time (TXR-004) for `PAYOUT` type.

6. **Table name in prod**: If the production deployment already has a `txn_requests` table from another system, the `TXN_REQUESTS_TABLE` env var can point to a different name (e.g., `"svc_txn_requests"`). The `_resolve_table_name` helper in `local-ddb-init.py:38` handles this.
