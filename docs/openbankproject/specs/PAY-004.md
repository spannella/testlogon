# PAY-004 — FX rate store + convert helper for cross-currency requests

**Ticket type**: Backend (data model + service + REST endpoints)
**Priority**: P1 (independently shippable; consumed by PAY-002/PAY-003 for non-USD counterparties)
**Estimate**: 2 days
**Status**: Unimplemented
**Sibling specs**: PAY-001 (`docs/openbankproject/specs/PAY-001.md`), PAY-002 (`PAY-002.md`)

---

## 1. Summary & Goal

PAY-004 introduces a **persistent FX rate store** and a **pure `convert` helper** that
cross-currency standing orders (PAY-002), direct-debit mandates (PAY-003), and
COUNTERPARTY Transaction Requests (TXR-001) call to express a non-USD amount in the
ledger's single `usd` currency. The goals are narrow and additive:

1. Define the `fx_rates` DynamoDB table: one row per `(pair, as_of)`, newest row wins,
   full history retained for audit.
2. Implement `app/services/fx_rates.py` with three operations: `set_rate` (admin-set,
   append-only), `get_rate` (read newest), and `convert` (pure integer math — no wallet
   or ledger writes).
3. Expose three HTTP endpoints in `app/routers/fx_rates.py` under the
   `PAYMENTS_COUNTERPARTIES_ENABLED` flag.
4. Emit `fx_rate.set` audit events via the existing `audit_event` helper.

**What this ticket does NOT do:** move money, write ledger rows, modify wallet balances,
change settlement currency, add a rate-refresh background task to the scheduler loop (that
is optional and deferred), or touch any existing billing/tip/payout code. The ledger stays
single-currency `usd`; FX conversion produces only an annotating
`{fx_rate, source_currency}` pair that callers stamp onto a Transaction Request `meta`.

## 2. Context & Current State

### Ledger is single-currency USD

`app/services/billing_shared.py:176` `get_wallet_balance(table, pk)` returns
`{"wallet_balance_cents": int, "currency": row.get("currency", "usd"), ...}`. The
`currency` field always defaults to `"usd"` in practice; no multi-currency wallet row
exists anywhere in the codebase. `apply_wallet_delta` (`billing_shared.py:185`) accepts a `currency` keyword parameter
(defaulting to `"usd"`) but does not validate it against the existing wallet row's
stored currency — a cross-currency delta is accepted silently. For deposits it writes
the `currency` attribute; for withdrawals it omits the field entirely. The function
therefore cannot enforce single-currency discipline; all callers pass the default `"usd"`.
The
`new_ledger_entry` function (`billing_shared.py:224`) stores `amount_cents: int(amount_cents)` with no
currency field on the item; every ledger row is implicitly USD. The gap analysis
(`docs/openbankproject/OBP_GAP_ANALYSIS.md` §B) classifies "FX rates (get/convert pair)"
as **MISSING**: "ledger is single-currency `usd`".

### Amount-cents integer discipline

All money values across the codebase are stored and computed as integer `amount_cents`.
`billing_shared.py:248` casts `int(amount_cents)`. `tip_ledger.py` `TipLedgerEntry.amount_cents`
is asserted `> 0`. `creator_payouts.py` payout amounts are expressed as cents integers.
FX conversion must honour this discipline: the `rate` stored in DynamoDB uses a
`rate_micros` integer (rate × 1,000,000) so the conversion arithmetic is purely integer —
`target_cents = round(amount_cents * rate_micros) // 1_000_000` — avoiding float
accumulation or `Decimal` drift.

The `Tables` proxy in `app/core/tables.py:29` (`_FloatSafeTable`) already coerces
Python `float` values to `Decimal` on `put_item`/`update_item` writes. However, storing
an integer `rate_micros` is preferred: it avoids the `Decimal`→float round-trip on
read, keeps arithmetic deterministic, and matches the `amount_cents` integer convention
used throughout `billing_shared.py` and `tip_ledger.py`.

### Newest-row-by-numeric-sort-key pattern

`app/services/kyc_risk_scoring.py:173` `get_latest_score` queries a table keyed by
`(user_sub, timestamp)` (the sort key is named `timestamp`, not `score_id`) with
`ScanIndexForward=False, Limit=1` to get the single
most-recent item per user. The `fx_rates` table mirrors this: PK `pair` (S), SK `as_of`
(N) — `query(KeyConditionExpression=Key("pair").eq(pair), ScanIndexForward=False, Limit=1)`
returns the newest rate for that pair in one call, with full historical rows retained for
audit.

## 3. Data Model

### New DynamoDB table: `fx_rates`

**Table name**: resolved via `S.fx_rates_table_name` (new setting, default `"fx_rates"`).

**Primary key**:
- Hash key: `pair` (S) — canonical form `"{SRC}_{TGT}"`, always uppercase, e.g.
  `"EUR_USD"`, `"GBP_USD"`, `"USD_USD"`.
- Sort key: `as_of` (N) — Unix timestamp integer from `now_ts()` at the moment the rate
  was set. Append-only: `set_rate` always writes a new row; prior rows are never mutated.

**Numeric sort key declaration**: because `as_of` is numeric, the `TableDef` in
`scripts/local-ddb-init.py` **must** include `attr_types={"as_of": "N"}` — failing to
declare this causes DynamoDB to store the attribute as String, which breaks the
`ScanIndexForward=False` newest-first query (per CLAUDE.md numeric-GSI gotcha; same
pattern as `users` table with `attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"}`
at `scripts/local-ddb-init.py:53`).

**No GSI is needed** for the primary usage pattern: every query is by a known `pair`,
returning the newest `as_of` row (`ScanIndexForward=False, Limit=1`). A full listing of
all pairs requires a `scan` — acceptable given the expected low cardinality (at most a
few dozen active pairs). A `ByUpdatedAt` GSI for listing could be added in a follow-up
if needed; it is not part of this ticket.

**Item schema**:

| Attribute | Type | Notes |
|---|---|---|
| `pair` | S | `"{SRC}_{TGT}"` uppercase, e.g. `EUR_USD` |
| `as_of` | N | Unix timestamp (`now_ts()`); sort key |
| `source_currency` | S | Uppercase ISO 4217, e.g. `EUR` |
| `target_currency` | S | Uppercase ISO 4217, e.g. `USD` |
| `rate_micros` | N | `round(rate * 1_000_000)` — integer, always positive |
| `source` | S | `"admin"` or `"fetched"` |
| `set_by` | S | `user_sub` of the admin who set it, or `"system"` for fetched |
| `created_at` | N | Same as `as_of`; redundant but useful for filtering/display |

**No TTL attribute**: rate history is retained indefinitely for audit purposes. Row count
stays bounded by the number of distinct pairs × rate-update frequency.

## 4. API / Service Design

### Service: `app/services/fx_rates.py`

All public functions are synchronous (DynamoDB Local / real DynamoDB calls are
synchronous via boto3). No `asyncio` needed.

#### `set_rate`

```python
def set_rate(
    source_currency: str,
    target_currency: str,
    rate: float,
    *,
    source: Literal["admin", "fetched"] = "admin",
    set_by: str,
) -> FxRateOut:
```

- Normalises both currency codes to uppercase (`.upper().strip()`).
- Rejects `rate <= 0` with `ValueError("rate_must_be_positive")`.
- Rejects `source_currency == target_currency` with `ValueError("identity_pair_not_stored")` —
  `USD_USD` is always handled synthetically in `get_rate`; storing it is an error.
- Computes `pair = f"{source_currency}_{target_currency}"`.
- Computes `rate_micros = round(rate * 1_000_000)` (integer, avoids float drift).
- Calls `T.fx_rates.put_item(Item={...})` — always a new row; existing rows are never
  overwritten (append-only).
- Calls `audit_event("fx_rate.set", set_by, source_currency=source_currency,
  target_currency=target_currency, rate_micros=rate_micros, source=source)`.
- Returns `FxRateOut` constructed from the persisted item.

#### `get_rate`

```python
def get_rate(
    source_currency: str,
    target_currency: str,
) -> FxRateOut | None:
```

- Normalises currency codes.
- If `source_currency == target_currency`: returns a synthetic `FxRateOut` with
  `rate_micros=1_000_000`, `source="identity"`, `as_of=0`, `set_by="system"` — no DDB
  call. This handles `USD_USD` cleanly and makes `convert` always work for same-currency
  requests.
- Otherwise: queries `T.fx_rates` with
  `KeyConditionExpression=Key("pair").eq(pair), ScanIndexForward=False, Limit=1`
  (mirrors `kyc_risk_scoring.py:175` `get_latest_score`).
- If no row exists → returns `None` (caller decides whether to raise).
- If `S.fx_rate_max_age_seconds > 0` and `now_ts() - item["as_of"] > S.fx_rate_max_age_seconds` →
  returns `None` (stale rate treated as missing, so callers see the same `LookupError`
  path as a missing pair and can decide to skip or fail the occurrence).
- Returns `FxRateOut` from the item.

#### `convert`

```python
def convert(
    amount_cents: int,
    source_currency: str,
    target_currency: str,
) -> FxConvertOut:
```

- Calls `get_rate(source_currency, target_currency)`.
- If `None` → raises `LookupError("fx_rate_missing")`. Callers (PAY-002/003 execution
  path) catch this and mark the occurrence as `skipped` (no request created, no debit).
- Computes `target_amount_cents = round(amount_cents * rate_micros) // 1_000_000`
  using pure integer arithmetic.
- **Writes no ledger row, no wallet delta, no DDB row of any kind** — this is a pure
  read + arithmetic function (money-safety #5 from the PAY cross-cutting constraints:
  "FX is read-only against the ledger").
- Returns `FxConvertOut{source_currency, target_currency, source_amount_cents=amount_cents,
  target_amount_cents, rate_micros, as_of}`.

#### `list_rates` (for the GET /ui/fx/rates endpoint)

```python
def list_rates() -> list[FxRateOut]:
```

- Scans `T.fx_rates` and, for each unique `pair`, returns only the item with the largest
  `as_of` (i.e. the newest rate per pair). In practice, a `scan` is acceptable given the
  low expected row count (a few dozen pairs × a few updates each).
- Alternative implementation: collect all items, group by `pair`, take `max(as_of)` per
  group in Python — avoids a multi-query approach.
- Returns the list sorted by `pair` alphabetically for deterministic UI ordering.

### Pydantic models in `app/models.py`


`FxRateOut.rate` is `rate_micros / 1_000_000` (a Python float) computed at
serialisation time. It is never stored as a float in DynamoDB; `rate_micros` is the
authoritative stored value. This matches the codebase convention of exposing
human-readable floats in API responses while storing integers internally.

## 5. Detailed Behavior & Edge Cases

### Identity pair (USD→USD)

`convert(1000, "USD", "USD")` must return `FxConvertOut{source_amount_cents=1000,
target_amount_cents=1000, rate=1.0, rate_micros=1_000_000, as_of=0}`. `get_rate`
short-circuits before any DDB call for same-currency pairs, returning a synthetic
identity `FxRateOut`. `set_rate` rejects `source_currency == target_currency` with
`ValueError("identity_pair_not_stored")` — storing an explicit `USD_USD` rate is
unnecessary and could confuse the identity short-circuit. PAY-002/003 callers must
always call `convert` (not special-case USD themselves); the identity path makes this
safe.

### Missing pair

If no rate has been set for `EUR_USD` and a caller asks `convert(5000, "EUR", "USD")`,
`get_rate` returns `None` and `convert` raises `LookupError("fx_rate_missing")`. The
PAY-002 standing-order executor (`execute_due_standing_order`) catches this and:
- Marks the occurrence as `skipped` on the standing order item.
- Fires `audit_event("standing_order.skipped", user_sub, reason="fx_rate_missing")`.
- Does NOT create a Transaction Request (no TXR call → no debit).
- Does NOT advance `next_run_at` (the occurrence is retried at the next scheduler tick
  after an admin sets the rate).

PAY-003 mandate execution (`execute_mandate_pull`) catches this and marks the occurrence
`skipped` with `reason="fx_rate_missing"` and **does advance** `next_run_at` (unlike the
PAY-002 standing-order path). This difference is intentional per PAY-003 design: mandates
treat a skipped occurrence as fully processed to avoid scheduler spin — the cadence
advances, and the FX-missing condition should be resolved by an admin before the next due
date. See `PAY-003.md:334`.

### Stale rates

When `S.fx_rate_max_age_seconds > 0` and the newest stored rate is older than that
threshold, `get_rate` returns `None` (stale treated as missing). This triggers the
same `skipped` path as a missing pair, preventing a cross-currency payment from
settling against an arbitrarily old rate. Default is `0` (no staleness check) so the
behavior is opt-in per deployment.

### Rate precision and rounding

`rate_micros = round(rate * 1_000_000)` — Python's `round()` uses banker's rounding
(round-half-to-even), which is acceptable for financial rate storage. The conversion
`target_cents = round(amount_cents * rate_micros) // 1_000_000` uses integer division
after a `round()` to avoid off-by-one from integer truncation. For example:
`convert(10000, "EUR", "USD")` with `rate_micros=1_085_000` (rate=1.085) →
`round(10000 * 1_085_000) // 1_000_000 = 10_850_000_000 // 1_000_000 = 10850`.
No float accumulation occurs.

### Concurrent `set_rate` calls

Two admins setting the same pair concurrently both succeed: each writes a new `as_of`
row. The newer `as_of` wins on the next `get_rate` call. DynamoDB's conditional-write
mechanism is not needed here because `put_item` on a composite PK with a new `as_of`
never collides (the probability of two writes with the same `now_ts()` value is
negligible and the worst case is one rate being overwritten, which is acceptable for
admin-set rates). If strict conflict detection is required, a conditional
`attribute_not_exists(pair) AND attribute_not_exists(as_of)` expression can be added,
but it is not required by this ticket.

### Currency code validation

Currency codes are normalised to uppercase and validated to be exactly 3 characters
by the Pydantic model (`min_length=3, max_length=3`). The service does not validate
against a fixed ISO 4217 list — that would require bundling a currency table and is
unnecessary for the first version. Unknown codes simply produce a missing-rate 404 on
`convert`, which is the correct handling.

### `convert` is a pure function with no side effects

`convert` calls only `get_rate` (one DDB `query`) and returns a value object. It writes
no DDB rows, emits no audit events, touches no wallet, and does not call
`new_ledger_entry` or `apply_wallet_delta`. This is intentional and enforced by the
design (money-safety #5). The `FxConvertOut` returned by `convert` carries `as_of` so
the caller can stamp it onto the Transaction Request `meta` field, creating an
immutable audit trail of the rate used at the time of conversion.

### `GET /ui/fx/convert` as a preview endpoint

The HTTP endpoint exists for frontend use: standing-order and mandate creation forms
can call it to show users the equivalent USD amount before confirming. It never
triggers a payment. It is intentionally accessible to any authenticated user (not
admin-only) because users need to preview conversion for their own orders.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007: single code path, no `if S.dev_mode` branches

`fx_rates.py` contains no `if S.dev_mode` branches in business logic. In dev, `T.fx_rates`
is backed by DynamoDB Local (port 8001). In prod, it is backed by real DynamoDB. The
`_safe_table` wrapper in `app/core/tables.py:65` handles boto3 `Decimal` coercion
identically in both environments. The `audit_event` helper writes to `T.alerts`
(DynamoDB Local in dev, real DynamoDB in prod) — same call, no branch.

If a future `refresh_fetched_rates()` function is added, it must also follow SECOPS-007:
the "dev" path returns a deterministic mock rate table through the same provider
abstraction as `provider_oauth.py` (which already decides mock-vs-real underneath),
not via `if S.dev_mode` in `fx_rates.py`.

### Money-safety

PAY-004 is entirely read-side. Money-safety constraints from the PAY cross-cutting spec:

- **#5 (FX is read-only against the ledger)**: `convert` writes no ledger row, no wallet
  delta, no DDB item. Every call to `convert` is a pure computation. The `FxConvertOut`
  result is passed by the caller (PAY-002/003 executor) to `txn_requests.create_request`
  as metadata only; the TXR service owns the actual ledger write.
- **#1 (one money-out path)**: PAY-004 never calls `apply_wallet_delta`,
  `new_ledger_entry`, or `settle_or_reverse_ledger`. It has no import of
  `billing_shared` at all (only `app/core/tables.T` and `app/core/time.now_ts`).

### Idempotency of `set_rate`

`set_rate` is append-only: each call writes a new `(pair, as_of)` row. It is NOT
idempotent in the sense that calling it twice produces two rows. This is intentional
for audit purposes (full rate history). Admin UIs must not auto-retry `set_rate` on
network error without user confirmation; the router returns `201` only on the first
successful write.

### Authorization and CSRF

- Read endpoints (`GET /ui/fx/rates`, `GET /ui/fx/convert`) require `require_ui_session` —
  any authenticated user. No CSRF is required for `GET` methods (per CLAUDE.md: "CSRF
  enforced for non-GET per CLAUDE.md").
- Write endpoint (`POST /ui/admin/fx/rates`) requires `require_admin_or_root_csrf` —
  enforces both role (`ADMIN`/`ROOT`) and CSRF token (`x-csrf-token` header matching the
  session's stored `csrf_token` and `ui_csrf` cookie). Bearer-auth admin clients skip
  CSRF (per `app/auth/policy.py:71` `enforce_cookie_csrf` which exits early when there is
  no session cookie).

### Rate stored as integer, not float

Storing `rate_micros` (integer) instead of the raw `float` rate avoids the boto3
`TypeError: Float types are not supported` error (which `_FloatSafeTable` handles, but
adds a Decimal round-trip) and avoids `Decimal` precision edge cases in DynamoDB
comparisons. The human-readable `rate: float` in `FxRateOut` is reconstructed at
serialisation (`rate_micros / 1_000_000`) and never persisted.

### Purely additive

PAY-004 adds a new table (`fx_rates`), a new service file (`app/services/fx_rates.py`),
a new router file (`app/routers/fx_rates.py`), two new settings fields, one new `Tables`

  and one new `_safe_table(...)` wiring line.
- `app/main.py` — one new `include_router` call inside the existing
  `if S.payments_counterparties_enabled:` block.
- `app/models.py` — three new Pydantic model classes appended.
- `scripts/local-ddb-init.py` — one new `TableDef` appended to `_table_defs()`.
- `app/services/api_key_route_scope_registry.py` — three new `API_KEY_ROUTE_EXEMPTIONS`

No existing tables, routes, service functions, or models are modified. No data migration
is required: the `fx_rates` table starts empty and accumulates rows only after admins
call `POST /ui/admin/fx/rates`.

### Dev stack table creation

`just restart` (which calls `scripts/local-ddb-init.py`) creates the new `fx_rates`
table on a clean restart. Existing long-lived dev environments need a one-time table
creation (either `just restart` or manually calling the `TableDef` creation logic).

### Production deployment

1. Deploy the code (new table handle wired into `T`, but `T.fx_rates` is not referenced
   until `S.payments_counterparties_enabled=true`).
2. Run `scripts/local-ddb-init.py` equivalent against real DynamoDB to create the table
   (a `CreateTable` call with the `pair`/`as_of` schema and `attr_types={"as_of": "N"}`).
3. Set `PAYMENTS_COUNTERPARTIES_ENABLED=true` and restart.
4. Populate initial rates via `POST /ui/admin/fx/rates` before enabling any cross-currency
   standing orders or mandates.

There is no backfill: the table is empty until rates are set. Existing USD-only
standing orders and mandates (when PAY-002/003 land) are unaffected — `convert`
is only called when `counterparty.currency != "usd"`.

## 10. Open Questions / Assumptions

1. **Fetched-rate refresh loop**: The ticket spec says `refresh_fetched_rates()` is
   optional ("behind the same provider abstraction"). This spec defers the background
   task entirely. If a rate provider is configured, a future sub-ticket adds a startup
   task that polls the provider and calls `set_rate(..., source="fetched", set_by="system")`
   on a configurable interval. The table schema already accommodates `source="fetched"`.

2. **Rate inversion**: If `EUR_USD` is stored but a caller asks for `USD_EUR`, should
   `get_rate` auto-invert? This spec says **no** — callers must store both directions
   explicitly if needed. Standing orders store the counterparty's `currency` (the
   non-USD side) and always call `convert(amount_cents, counterparty_currency, "usd")`,
   so only the `X_USD` direction is needed in practice.

3. **Multi-currency ledger**: The convert helper is deliberately scoped to produce a
   USD-denominated `target_amount_cents`. When a multi-currency ledger lands (OFB series),
   `convert` will need to return an arbitrary `target_currency` and the TXR execution
   path will need updating. For now `target_currency` is always `"USD"` in practice.

4. **`rate_micros` precision**: Storing rates as `rate_micros = round(rate * 1_000_000)`
   gives 6 decimal places of precision, sufficient for all major currency pairs. Exotic
   pairs with very small rates (e.g. `JPY_USD ≈ 0.0067`) require 6 significant figures,
   which `rate_micros` handles correctly (`6700` for `0.0067`).

5. **`GET /ui/fx/rates` pagination**: Currently returns all pairs via a scan. If the
   number of unique pairs exceeds a few hundred, pagination should be added. Assumption:
   the initial deployment will have at most ~50 currency pairs; pagination is deferred.

6. **`as_of` collision on the sort key**: Two `set_rate` calls in the same second produce
   the same `as_of` and would collide on the composite PK. Assumption: admin rate-set
   frequency is low (at most one per second per pair). If high-frequency automated
   updates are needed, `as_of` should be derived from `now_ts() * 1000 + nonce` (millisecond
   precision). Deferred for now.

PAY-004 has no dependency on `app/services/mfa.py` or the SCA challenge flow. FX
rate lookup and conversion are read-only operations that do not require step-up
authentication. SCA is relevant only at the TXR execution step, which lives in the

PAY-004 uses only the existing coarse `require_admin_or_root_csrf` / `require_ui_session`

a `"payments:fx:write"` scope to the admin write endpoint without changing the service

the PAY series matures and an API-key scope for `payments` is defined, these can be
promoted to `API_KEY_ROUTE_SCOPE_REGISTRY` with `required_scopes=["payments:read"]`
and `["payments:fx:admin"]` respectively, without changing the service or router logic.

PAY-004 fires `audit_event("fx_rate.set", ...)` to `T.alerts` only. No
`WEBHOOK_EVENT_TYPES_V2` entry is needed in this ticket. Account-/transaction-level
webhook events are deferred to the OBP Tier 2 account-webhook ticket.
