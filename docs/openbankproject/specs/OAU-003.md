# OAU-003 — OIDC layer — discovery, JWKS, id_token, /userinfo

**Ticket type**: Backend (service + router)
**Priority**: P2
**Estimate**: 3 days
**Status**: Unimplemented
**Flags**: `OAUTH_PROVIDER_ENABLED` (master, from OAU-001) + `OAUTH_PROVIDER_OIDC_ENABLED` (new, default OFF)

---

## 1. Summary & Goal

OAU-003 layers the OpenID Connect identity surface on top of the OAuth2 authorization-code flow introduced by OAU-002. The goal is to let consumer apps use testlogon as a standard **identity provider** — "sign in with testlogon" — rather than just an API authorizer. This adds four surfaces that together constitute a minimal but conformant OIDC provider:

1. **`GET /.well-known/openid-configuration`** — the OIDC discovery document that any standard library can use to autoconfigure the client.
2. **`GET /oauth/jwks`** — the public JSON Web Key Set, so relying parties can verify `id_token` signatures without shared secrets.
3. **`id_token` co-issuance** — when `openid` is in the requested scope, `POST /oauth/token` (OAU-002) additionally returns an RS256-signed `id_token` carrying standard identity claims.
4. **`GET /userinfo`** — the bearer-authenticated endpoint returning scope-filtered identity claims.

The core design constraint is that the OAU-002 **access token** remains HS256 (shared `UI_ACCESS_TOKEN_SECRET`, internal only), while the **`id_token`** is RS256 (asymmetric, public key published via JWKS). This is the only way a standard OIDC relying party — which does not and must not know the shared access-token secret — can verify identity tokens independently.

All four surfaces are wholly additive. With `OAUTH_PROVIDER_OIDC_ENABLED=false` (the default), none of the OIDC router is registered, `POST /oauth/token` returns no `id_token`, and the platform is byte-for-byte unchanged relative to OAU-002.

## 2. Context & Current State

### 2.1 What testlogon has today

**HS256 token signing.** All existing JWTs are issued with `jwt.encode(payload, S.ui_access_token_secret, algorithm="HS256")` (`app/services/sessions.py:228`). `S.ui_access_token_secret` is the `UI_ACCESS_TOKEN_SECRET` env var (`app/core/settings.py:108`). This secret cannot be published, so a standard OIDC relying party cannot verify a token signed with it. OAU-003 does not change this for access tokens; it introduces a separate signing key exclusively for `id_token`s.

**RS256 verification already understood.** `app/auth/deps.py:72` already uses `jwt.algorithms.RSAAlgorithm.from_jwk(json.dumps(key))` to deserialise an RSA public JWK (Cognito's) and `jwt.decode(token, public_key, algorithms=["RS256"], ...)` to verify it (`app/auth/deps.py:74-81`). OAU-003 runs the same pattern in reverse: generate an RSA keypair, publish the public half as JWK, sign `id_token`s with the private half.

**KMS encryption of secrets at rest.** `app/core/crypto.py:16-25` provides `kms_encrypt(plaintext: str) -> str` (base64-encoded ciphertext) and `kms_decrypt(ct_b64: str) -> bytes`. Both use `app/core/aws.kms` — the mock KMS server (port 7999) in dev, real AWS KMS in prod, transparent to callers. `app/services/provider_credentials.py:14,402` and `app/services/provider_oauth.py:312-314` use this same abstraction to store OAuth refresh tokens. OAU-003 uses `kms_encrypt`/`kms_decrypt` to protect the RSA private key at rest in DynamoDB — no new KMS abstraction needed.

**OAuth2 access token and `oauth_consumers` table already established by OAU-002.** The `oauth_consumers` DynamoDB table (PK `client_id`, SK `sk`) defined in OAU-001 holds META rows, auth-code rows (`sk="CODE#{code_id}"`), and grant rows (`sk="GRANT#{grant_id}"`). OAU-003 adds a **signing-key row** (`sk="KEY#oidc"`) to the same table without any schema change — single-table design.

**`S.public_base_url`.** `app/core/settings.py:349` defines `public_base_url: str = os.environ.get("PUBLIC_BASE_URL", "http://localhost:8000").rstrip("/")`. This value is used by `app/services/cart_reminders.py:223` to build absolute URLs. OAU-003 uses it identically to construct all OIDC endpoint URLs in the discovery document.

**`API_KEY_ROUTE_EXEMPTIONS`.** `app/services/api_key_route_scope_registry.py:70-80` is the dict of routes that bypass scope enforcement. The three new OIDC public endpoints (`/.well-known/openid-configuration`, `/oauth/jwks`) and the bearer-authenticated `/userinfo` must be added here to prevent the API-key scope middleware from blocking them.

**`T.users`.** `app/core/tables.py:327` wires `T.users = _safe_table(S.users_table_name)`. The `/userinfo` endpoint and `id_token` profile/email claim population read `email`, `name`, and similar fields from this table via `T.users.get_item(Key={"user_sub": sub})`, the same call pattern used by `get_authenticated_user` at `app/auth/deps.py:218`.

**`cryptography` package.** RSA key generation and serialisation require `cryptography` (the `cryptography.hazmat.primitives.asymmetric.rsa` module). The package is already installed (`cryptography==41.0.7`, confirmed on this host) because PyJWT pulls it in for RSA algorithms. No new dependency is added.

**OAuth bearer branch in `get_authenticated_user`.** OAU-002 adds an OAuth-bearer branch to `get_authenticated_user` (`app/auth/deps.py:199-305`) that, when it recognises a token with `token_type=="access"` and `client_id` present, resolves the resource owner and stashes the granted scope on `request.state.oauth_scope`. `GET /userinfo` relies on this branch — it uses `Depends(get_authenticated_user)` and extracts the scope from `request.state.oauth_scope`.

### 2.2 What is currently missing

- No OIDC discovery document at any path.
- No JWKS endpoint; no RSA keypair generated or stored anywhere.
- No `id_token` in any token response.
- No `/userinfo` endpoint.
- No `OAUTH_PROVIDER_OIDC_ENABLED` setting.
- The `oauth_consumers` table has no signing-key row shape; the `oauth_consumers_table_name` setting and `T.oauth_consumers` handle are added by OAU-001.

## 3. Data Model

### 3.1 No new DynamoDB table

OAU-003 adds one new row shape to the existing `oauth_consumers` table defined in OAU-001. No `TableDef` change is needed beyond what OAU-001 already declares.

### 3.2 Signing-key row (`sk="KEY#oidc"`)

Stored under `PK=client_id="__SYSTEM__"` (a synthetic system-level key, not a real consumer client_id) to avoid collisions with registered consumers while staying in the same table. Alternatively — and preferred for clarity — the row lives under a dedicated sentinel partition `PK="OIDC_SIGNING_KEY"`, `SK="META"`.

**Preferred layout:**

| Attribute | Type | Value |
|---|---|---|
| `client_id` | S | `"OIDC_SIGNING_KEY"` |
| `sk` | S | `"META"` |
| `kid` | S | random `secrets.token_hex(8)` at generation time |
| `alg` | S | `"RS256"` |
| `private_key_ct_b64` | S | `kms_encrypt(pem_private_key_utf8)` |
| `public_key_pem` | S | PEM-encoded RSA public key (not sensitive; safe to store plaintext) |
| `public_key_jwk_n` | S | Base64url-encoded RSA modulus (`n` component of JWK) |
| `public_key_jwk_e` | S | Base64url-encoded RSA public exponent (`e` component) |
| `created_at` | N | `now_ts()` |
| `rotated_at` | N | `now_ts()` at rotation time (if applicable) |

The row is written once on first call to `get_or_create_oidc_signing_key()` (lazy initialisation). Repeated calls return the cached row. A future rotation endpoint (out of scope here) writes a new row and increments `kid`.

**Why store `public_key_jwk_n/e` redundantly?** Avoids serialising the PEM on every JWKS request and avoids decrypting the private key for public-key operations.

### 3.3 No numeric GSI sort key introduced

The signing-key row carries `created_at` as a plain attribute but there is no GSI on it — the row is always fetched by PK/SK direct lookup, never range-queried. No `attr_types` addition is needed for this ticket.

### 3.4 Settings additions

The following fields are added to the `Settings` dataclass in `app/core/settings.py` (mirroring the pattern of existing feature flags):


`T.oauth_consumers` is wired in `app/core/tables.py` by OAU-001 as `oauth_consumers=_safe_table(S.oauth_consumers_table_name)`.

## 4. API / Service Design

### 4.1 Service: `app/services/oauth_oidc_keys.py`

This new module owns the RSA signing-key lifecycle. It is the only place that touches the KMS-encrypted private key.

```python
# Imports: app.core.crypto (kms_encrypt, kms_decrypt), app.core.tables (T),
#          app.core.time (now_ts), secrets, json
# cryptography.hazmat.primitives.asymmetric.rsa, serialization, padding

def get_or_create_oidc_signing_key() -> dict:
    """
    Returns the signing-key metadata dict (with decrypted private key PEM NOT included —
    callers that need to sign use sign_id_token directly).
    On first call: generates RSA-2048 keypair, KMS-encrypts the private key,
    stores the row, returns metadata.
    On subsequent calls: returns the existing row (in-process cache after first DB read).
    """

def _generate_and_store_signing_key() -> dict:
    """
    Internal. Generates RSA-2048 via cryptography.hazmat, serialises both halves,
    KMS-encrypts the private key PEM, writes the DDB row with put_item
    ConditionExpression="attribute_not_exists(client_id)" to avoid races
    (client_id is the actual PK attribute name per OAU-001 table definition),
    returns the row dict.
    """

def get_public_jwks() -> dict:
    """
    Returns {"keys": [<JWK>]} for /oauth/jwks.
    JWK shape: {"kty": "RSA", "use": "sig", "alg": "RS256", "kid": <kid>,
                "n": <b64url modulus>, "e": <b64url exponent>}
    """

def sign_id_token(payload: dict) -> str:
    """
    Decrypts the private key via kms_decrypt, signs payload with RS256
    using jwt.encode(payload, private_key_obj, algorithm="RS256",
                     headers={"kid": kid}).
    Returns the compact JWT string.
    Private key object is deserialized via
    cryptography.hazmat.primitives.serialization.load_pem_private_key.
    The decrypted PEM bytes are NEVER stored on any attribute or logged.
    """
```

**In-process caching.** A module-level `_KEY_CACHE: Optional[dict] = None` holds the last-fetched signing-key metadata (public fields only, never the decrypted PEM). The cache is warmed on first request and invalidated only on rotation. This avoids a DDB read on every `/oauth/jwks` request.

### 4.2 Service extension: `app/services/oauth_token.py` (OAU-002, extended here)

OAU-003 adds one function to the token-issuance service:

```python
def build_id_token(
    owner_user_sub: str,
    client_id: str,
    granted_scopes: list[str],
    nonce: Optional[str],
    *,
    user_item: Optional[dict] = None,   # pre-fetched T.users row; avoids double read
) -> str:
    """
    Called by POST /oauth/token when 'openid' in granted_scopes and
    S.oauth_provider_oidc_enabled is True.
    Builds the OIDC claims payload and delegates to sign_id_token.
    Claims always included: iss, sub, aud, exp, iat, auth_time.
    Optional nonce: echoed verbatim if present (replay protection is
    the relying party's responsibility per OIDC spec).
    'profile' scope: adds name/given_name/family_name from user_item.
    'email' scope: adds email/email_verified from user_item.
    user_item is fetched from T.users if not supplied.
    """
```

### 4.3 Router: `app/routers/oauth_oidc.py`

New router, conditionally registered in `app/main.py` only when both `S.oauth_provider_enabled` and `S.oauth_provider_oidc_enabled`. All three public-facing endpoints are no-auth.

```python
router = APIRouter(tags=["oidc"])

@router.get("/.well-known/openid-configuration")
async def openid_configuration() -> JSONResponse:
    """
    No auth. Returns the OIDC discovery document.
    All endpoint URLs are derived from _issuer_base().
    """

@router.get("/oauth/jwks")
async def jwks() -> JSONResponse:
    """
    No auth. Returns the JWKS from oauth_oidc_keys.get_public_jwks().
    Cache-Control: max-age=3600, must-revalidate
    """

@router.get("/userinfo")
async def userinfo(
    request: Request,
    ctx: AuthenticatedUser = Depends(get_authenticated_user),
) -> JSONResponse:
    """
    Bearer-authenticated (via OAU-002's OAuth bearer branch in get_authenticated_user).
    Returns scope-filtered claims.
    Raises 401 if request.state.oauth_scope is not set (non-OAuth caller used this endpoint).
    Raises 403 with code='insufficient_scope' if 'openid' is not in granted scopes.
    """
```

### 4.4 Discovery document shape (`GET /.well-known/openid-configuration`)

```json
{
  "issuer": "<S.oidc_issuer_url or S.public_base_url>",
  "authorization_endpoint": "<base>/oauth/authorize",
  "token_endpoint": "<base>/oauth/token",
  "userinfo_endpoint": "<base>/userinfo",
  "jwks_uri": "<base>/oauth/jwks",
  "registration_endpoint": "<base>/ui/oauth/consumers",
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token"],
  "subject_types_supported": ["public"],
  "id_token_signing_alg_values_supported": ["RS256"],
  "scopes_supported": ["openid", "profile", "email", "<registry scope union>"],
  "token_endpoint_auth_methods_supported": ["client_secret_post", "none"],
  "claims_supported": ["sub", "iss", "aud", "exp", "iat", "email", "name", "given_name", "family_name", "email_verified"],
  "code_challenge_methods_supported": ["S256"],
  "service_documentation": "<base>/docs"
}
```

`scopes_supported` is built by iterating `API_KEY_ROUTE_SCOPE_REGISTRY` (via `api_key_route_scope_registry.py:17-67`) to collect the union of all `required_scopes` values, then prepending `["openid", "profile", "email"]`. This keeps the scope vocabulary in one place.

`grant_types_supported` includes `"password"` only when `S.oauth_provider_directlogin_enabled` is also true (DirectLogin from OAU-002).

### 4.5 `id_token` payload shape

```json
{
  "iss": "<issuer>",
  "sub": "<owner_user_sub>",
  "aud": "<client_id>",
  "exp": <now + S.oidc_id_token_ttl_seconds>,
  "iat": <now>,
  "auth_time": <session.created_at if available, else iat>,
  "nonce": "<echoed from /authorize request if present>",
  "email": "<from T.users, only if 'email' in granted_scopes>",
  "email_verified": <bool, only if 'email' in granted_scopes>,
  "name": "<from T.users profile_name or display_name, only if 'profile' in granted_scopes>",
  "given_name": "<first_name if available, only if 'profile' in granted_scopes>",
  "family_name": "<last_name if available, only if 'profile' in granted_scopes>"
}
```

JWT header: `{"alg": "RS256", "kid": "<kid from signing-key row>", "typ": "JWT"}`.

The `id_token` is appended to the existing `POST /oauth/token` response body (OAU-002) under the key `"id_token"`. When `S.oauth_provider_oidc_enabled` is false, the key is absent. The OAU-002 access-token shape is never modified.

### 4.6 `/userinfo` response

```json
{
  "sub": "<owner_user_sub>",
  "email": "<T.users email, only if 'email' in granted_scopes>",
  "email_verified": <bool, only if 'email' in granted_scopes>,
  "name": "<only if 'profile' in granted_scopes>",
  "given_name": "<only if 'profile' in granted_scopes>",
  "family_name": "<only if 'profile' in granted_scopes>"
}
```

`sub` is always returned. Any claim not covered by the token's granted scopes is omitted entirely (not set to null).

## 5. Detailed Behavior & Edge Cases

### 5.1 Signing-key lazy initialisation and race safety

`get_or_create_oidc_signing_key()` checks the in-process cache first. On a cache miss it calls `T.oauth_consumers.get_item(Key={"client_id": "OIDC_SIGNING_KEY", "sk": "META"})`. If the item exists, it populates the cache and returns. If it does not exist, it calls `_generate_and_store_signing_key()`, which uses `put_item` with `ConditionExpression="attribute_not_exists(client_id)"`. A concurrent process that wins the conditional write will cause the loser to receive a `ConditionalCheckFailedException`; the loser catches this and re-reads the row. The result: exactly one RSA keypair is ever stored, regardless of startup concurrency. This is the same conditional-write pattern used for cart-recovery consumed tokens (`cart_reminders.py:200-207` — `attribute_not_exists(pk)` conditional on `T.cart_reminder_config`; note `provider_oauth.py:168-216` uses the complementary `attribute_not_exists(consumed_at)` single-use consume pattern, not a race-safe create).

### 5.2 `id_token` only issued with `openid` scope

`build_id_token` is called only when all three are true: (a) `S.oauth_provider_oidc_enabled`, (b) `"openid"` is in the code row's `granted_scopes`, (c) the `authorized_scope` carried on the OAU-002 grant/code also contains `"openid"`. If `openid` was not in the originally requested scope at `/oauth/authorize`, it cannot appear in the code row, and cannot be claimed retroactively at `/oauth/token`.

### 5.3 Nonce handling

The `/oauth/authorize` request passes `nonce` as an optional query parameter. OAU-002 stores the `nonce` on the auth-code row. `build_id_token` reads it from the code row and echoes it in the `id_token`. The nonce is a replay-prevention mechanism owned by the relying party; the server's only obligation is accurate echo (no uniqueness enforcement server-side).

### 5.4 `auth_time` claim

If the access token was issued via the authorization-code flow, the resource owner's session `created_at` (from OAU-002's auth-code row `owner_session_created_at`, stored at consent time) is used for `auth_time`. If unavailable, `iat` is used. This ensures the relying party can enforce maximum authentication age constraints (`max_age` parameter — out of scope for OAU-003 enforcement, but the claim is present).

### 5.5 `/userinfo` with non-OAuth caller

If a cookie-auth or API-key caller hits `/userinfo`, `request.state.oauth_scope` is absent (OAU-002 sets it only for OAuth-bearer tokens). The endpoint checks: `if not hasattr(request.state, "oauth_scope"): raise HTTPException(401, {"code": "bearer_token_required"})`. This prevents privilege escalation where a cookie session (which carries full user permissions) could extract identity claims through this endpoint without a proper OAuth flow.

### 5.6 Consumer `enabled` check at `/userinfo`

`/userinfo` resolves the `client_id` from the bearer token's payload, then calls `get_consumer(client_id)` (OAU-001 service). If `enabled is False`, it returns 401 `oauth_consumer_disabled`. This is consistent with OAU-005's enforcement that disabling a consumer instantly kills all of its flows.

### 5.7 Private key never leaves the service boundary

`sign_id_token` decrypts the PEM in memory, constructs a `cryptography` private key object, passes it to `jwt.encode`, and lets it go out of scope. The decrypted PEM bytes are never assigned to a long-lived variable, never stored in the in-process cache (only the public fields are cached), never logged, never serialised to a response body. The `private_key_ct_b64` column in DDB is the only persisted copy, and it is KMS-encrypted at rest.

### 5.8 JWKS key rotation (future scope, design impact today)

Key rotation is out of scope for OAU-003 (no rotation endpoint is built here), but the design accommodates it: `kid` is a stable identifier in the JWK and in the `id_token` header. A rotation would generate a new keypair, write a new DDB row (new `kid`), and update the cache. Relying parties that cache JWKS and see an unknown `kid` should re-fetch; the published OIDC discovery document's `jwks_uri` remains stable. Because OIDC clients are expected to implement this re-fetch behaviour, no grace period with two simultaneous active keys is required for OAU-003.

### 5.9 `profile` and `email` claims: missing fields are omitted

If a user has no `name` stored in `T.users`, the `name` claim is simply not included in the `id_token` or `/userinfo` response, rather than being set to null. This avoids exposing a `null` claim that some relying parties might interpret incorrectly. The OIDC spec allows claims to be absent if not available.

### 5.10 Discovery document caching

The discovery document is a static JSON response and is cheap to compute. No DDB read is required (all values come from `S.*`). The router returns it with `Cache-Control: max-age=86400` to enable aggressive CDN/client caching in production.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 parity

No `if S.dev_mode:` branch anywhere in `oauth_oidc.py`, `oauth_oidc_keys.py`, or the `id_token` issuance path. Both dev (DynamoDB Local, mock KMS at port 7999) and prod (real DynamoDB, real KMS) execute identical code paths. `kms_encrypt`/`kms_decrypt` (`app/core/crypto.py:16-25`) already handle the dev/prod distinction transparently by pointing at `S.kms_endpoint_url` when set.

### 7.2 Idempotency of signing-key creation

The `put_item ConditionExpression="attribute_not_exists(client_id)"` conditional (section 5.1) ensures the RSA keypair is generated exactly once per deployment. Re-deploying the application server never overwrites an existing key. The in-process cache ensures the DDB row is read at most once per process lifetime under normal operation.

### 7.3 Private key security

- The RSA private key PEM is KMS-encrypted before any DDB write. The plaintext PEM is never logged (no `logger.debug(pem)` or similar).
- `private_key_ct_b64` is a server-internal attribute. It is never returned by any API endpoint.
- The `/oauth/jwks` response contains only the public key (`n`, `e` components); the `private_key_ct_b64` attribute is not included.
- `sign_id_token` decrypts inline per call; the decrypted key object is GC'd after the JWT is encoded.

### 7.4 No money-safety concerns

OAU-003 is an identity layer with no financial operations. It does not call `new_ledger_entry`, `apply_wallet_delta`, `settle_or_reverse_ledger`, or any billing primitive. No money-out path is introduced.

### 7.5 Token audience binding

`id_token` carries `"aud": client_id`. A relying party that decodes the token must verify `aud == their client_id`. This prevents a token issued for consumer A from being accepted by consumer B. The `build_id_token` function enforces this by taking `client_id` as an explicit parameter — no caller can omit it.

### 7.6 No `sub` forgery

The `sub` claim in `id_token` is always `owner_user_sub` — the resource owner resolved through the OAU-002 authorization-code flow, which itself resolved from a valid `require_ui_session` dependency (the user was authenticated to testlogon at consent time). The `id_token` cannot claim a `sub` that did not go through the authorization flow.

## 8. Backward Compatibility & Migration

### 8.1 Existing auth surface unchanged

The cookie-based, Cognito-JWT, and API-key auth paths in `get_authenticated_user` (`app/auth/deps.py:199-305`) are not modified by OAU-003. The OAuth-bearer branch introduced by OAU-002 is also not modified. All `Depends(require_ui_session)` endpoints continue to work identically.

### 8.2 `POST /oauth/token` response is additive

The `id_token` key is appended to the existing response body. OAU-002 consumers that do not request `openid` scope receive a response identical to the pre-OAU-003 state. OAU-002 consumers that do request `openid` scope but run against a deployment with `OAUTH_PROVIDER_OIDC_ENABLED=false` receive no `id_token` and must not break — the key is absent, not null.

### 8.3 No DynamoDB table migration

The `OIDC_SIGNING_KEY / META` row is written on first use. The `oauth_consumers` table (created by OAU-001's `local-ddb-init.py` `TableDef`) uses `client_id` as its partition key attribute — the sentinel value `"OIDC_SIGNING_KEY"` is stored under that attribute (not a separate `pk` attribute). All DDB calls must use `Key={"client_id": "OIDC_SIGNING_KEY", "sk": "META"}` and `ConditionExpression="attribute_not_exists(client_id)"`. No `UpdateTable` or index change is required; the existing table definition accommodates the new row shape.

In production environments that already have OAU-001 deployed and the `oauth_consumers` table live, deploying OAU-003 simply adds the signing-key row on first OIDC endpoint access. No backfill or migration script is needed.

### 8.4 `API_KEY_ROUTE_EXEMPTIONS` is additive

Adding entries to this dict is always backward-compatible — it can only reduce false 403s, never introduce new ones.

## 10. Open Questions / Assumptions

1. **Single active signing key.** This spec assumes one active RS256 keypair at a time. Key rotation (writing a new keypair and retiring the old one) is out of scope. If rotation is needed before OAU-003 ships, a `POST /ui/oauth/oidc/rotate-signing-key` endpoint should be added in a follow-up, with a two-key grace window to avoid invalidating recently-issued tokens.

2. **`auth_time` precision.** The spec echoes the resource owner's session `created_at` as `auth_time`. The OAU-002 spec's `CODE#` row schema (`docs/openbankproject/specs/OAU-002.md`, row fields at lines 86-95) does **not** include an `owner_session_created_at` field. OAU-003 implementers must either: (a) accept that `auth_time` always equals `iat` (fallback path, safe default), or (b) add `owner_session_created_at` to the OAU-002 `issue_auth_code` call and code row before OAU-003 ships. The fallback to `iat` is conformant per OIDC Core §2.

3. **Consent screen.** The OAU-002 ticket defers a consent UI (auto-consenting for first-party apps). For OIDC deployments where `openid` scope exposes identity data to third-party consumer apps, a real consent screen (showing what identity data will be shared) should be built before enabling `OAUTH_PROVIDER_OIDC_ENABLED=true` in any environment where external developers have registered consumers.

4. **`T.oauth_consumers` PK attribute name — RESOLVED.** The OAU-001 spec defines the table's partition key attribute as `client_id` (not `pk`). All DDB operations on the signing-key row in this spec have been corrected to use `Key={"client_id": "OIDC_SIGNING_KEY", "sk": "META"}` and `ConditionExpression="attribute_not_exists(client_id)"`. The `pk` attribute name does not exist in the `oauth_consumers` table; using it would cause a DynamoDB `ValidationException` at runtime. The sentinel value `"OIDC_SIGNING_KEY"` is sufficiently distinguishable from real `client_id` values (which are `secrets.token_hex(16)` — 32-character hex strings).

5. **`email_verified` source.** The spec assumes `T.users` stores an `email_verified: bool` field. If this field does not exist, `email_verified` defaults to `false` for all users until a verification flow is implemented.

6. **RSA key size.** RSA-2048 is specified. RSA-4096 provides a larger security margin but increases signing/verification time and JWK payload size. For a SaaS context RSA-2048 is standard and widely accepted by OIDC libraries.
