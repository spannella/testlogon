# ACC-005 — Tests — pytest unit coverage for banks/accounts/transactions/metadata/co-access

**Ticket type**: Testing
**Priority**: P1 (ships with the feature)
**Estimate**: 2.5 days
**Depends on**: ACC-001, ACC-002, ACC-003, ACC-004 (tests the code they add)
**Flag**: Inherits the flags under test — `banking_accounts_enabled`, `banking_account_metadata_enabled`, `banking_account_views_enabled` (all default OFF, toggled in tests via `object.__setattr__`).

---

## 1. Summary & Goal

ACC-005 delivers the **offline, hermetic pytest test suite** for all four ACC implementation tickets (ACC-001 through ACC-004). These tests are the acceptance signal that the banking data model is correctly wired, the read-through invariants hold, and the additive-over-billing guarantee is verifiable without a running dev stack.

The primary engineering goals are:

1. **Immutability proof.** Every test that writes transaction metadata (ACC-003) must assert that the underlying `LEDGER#` billing row is byte-identical before and after — this is the load-bearing guarantee that ACC never forks billing.
2. **Read-through proof.** Tests for ACC-001/002 must show that mutating the live wallet balance (via `billing_shared.apply_wallet_delta`) is immediately reflected in `GET .../balance` and the `new_balance` on the newest settled transaction — proving the projection reads `T.billing` directly, not a copied value.
3. **Coverage of every flag-off branch.** With each feature flag at its default (off), the router registration must be absent and the service functions must be unreachable from the HTTP surface.
4. **Hermetic isolation.** No dev stack, no real AWS, no network. All DynamoDB I/O goes through moto in-memory tables; all S3 I/O goes through a lightweight in-memory fake (or moto S3 inside the same `mock_aws` context). Frozen `T.*` and `S` handles are mutated via `object.__setattr__` and restored on teardown.

The four test modules are:

| Module | Tests | Ticket |
|---|---|---|
| `tests/test_acc_001_accounts.py` | ~16 tests | ACC-001: Bank catalog + Account CRUD + default-account bootstrap |
| `tests/test_acc_002_transactions.py` | ~14 tests | ACC-002: Ledger projection, running `new_balance`, date-range, cursor |
| `tests/test_acc_003_metadata.py` | ~18 tests | ACC-003: Metadata sub-rows, S3 image, immutability, flag-off |
| `tests/test_acc_004_coaccess.py` | ~14 tests | ACC-004: Multi-owner grants, VEW-stubbed projection, flag-off |

All modules run under `.venv/bin/pytest tests/test_acc_*.py` with no additional environment setup.

## 2. Context & Current State

### What ACC-001..004 add (what these tests verify)

**ACC-001** introduces a new DynamoDB table `banking_accounts` (handle `T.banking_accounts` added to `app/core/tables.py`; settings key `S.banking_accounts_table_name`), a Bank catalog (rows `pk=BANK`, `sk=BANK#{bank_id}`), and Account rows (`pk=USER#{owner_sub}`, `sk=ACCOUNT#{account_id}`). The `GSI_ACCOUNT_BY_ID` GSI (partition `account_id` S, sort `created_at` N, `attr_types={"created_at": "N"}` in `scripts/local-ddb-init.py`) enables cross-owner resolution. `ensure_default_account(user_sub)` is idempotent — first call mints a `WALLET`/`is_default=True`/`wallet_backed=True` account row; subsequent calls return the same `account_id`. The service lives in `app/services/banking_accounts.py`; the router in `app/routers/banking_accounts.py` (prefix `/ui/banking`, registered in `app/main.py` only inside `if S.banking_accounts_enabled:`).

**ACC-002** adds `list_account_transactions` and `get_account_transaction` in `app/services/banking_accounts.py`. These read `LEDGER#{ts}#{entry_id}` rows from `T.billing` under `pk=USER#{owner_sub}` (same partition as `billing_shared.user_pk`, `billing_shared.py:23`). The sort-key embedding `LEDGER#{ts}#` allows date-range filtering as a DDB key condition (no `FilterExpression`). Running `new_balance` is computed by anchoring on the current `billing_shared.get_wallet_balance` result (`billing_shared.py:176`) and walking settled rows backward. Cursor pagination uses `app/core/cursor.py:94` `encode_cursor` / `cursor.py:103` `decode_cursor` — the HMAC-signed `v2` envelope; a tampered or expired cursor decodes to `None` and the service falls back to page-1.

**ACC-003** adds metadata sub-rows in the `banking_accounts` table under `pk=ACCOUNT#{account_id}`, with sort keys `META#{transaction_id}#NARRATIVE`, `#GEOTAG`, `#IMAGE`, `#TAG#{tag_id}`, `#COMMENT#{comment_id}`. S3 image upload uses `app.core.aws_clients.s3_client()` (`aws_clients.py:114`) — the same factory messaging and file-share use; no `S.dev_mode` branch. Audit events fire via `app/services/alerts.audit_event` (`alerts.py:644`). The `billing_shared.new_ledger_entry` row (`billing_shared.py:224`) is **never mutated** by metadata writes — the billing item must be byte-identical after any metadata operation.

**ACC-004** adds `add_account_owner`, `remove_account_owner`, `list_account_holders`, and `resolve_account_access` in `app/services/banking_accounts.py`. Multi-owner grants write a reverse-index row (`pk=USER#{co_owner_sub}`, `sk=ACCOUNT_REF#{account_id}`) to `banking_accounts`. View-based co-access is gated by `S.banking_account_views_enabled` and calls `app/services/account_views.py:resolve_active_grant` + `project_resource` — which ACC-004 imports with a `try/except ImportError` guard so it ships independently of VEW. Tests stub these collaborators so no VEW tables are needed.

## 3. Data Model

ACC-005 writes no new DynamoDB tables or rows of its own. The tables under test are:

### Tables used in tests (all created in-memory via moto)

**`banking_accounts`** — the single table introduced by ACC-001 for banks, accounts, metadata sub-rows, and co-owner reverse-index rows. Test harnesses create it with:

```python
TableDef equivalent:
  pk (S, HASH) + sk (S, RANGE)
  GSI "GSI_ACCOUNT_BY_ID": partition_key="account_id" (S), sort_key="created_at" (N)
  attr_types={"created_at": "N"}   # REQUIRED — omitting causes ValidationException
```

The `attr_types={"created_at": "N"}` declaration is tested implicitly: any test that writes an account row (with `created_at` as an integer) and then queries `GSI_ACCOUNT_BY_ID` by `account_id` will fail with a `ValidationException` if the GSI sort key is incorrectly typed as `S`. This is the live enforcement of the CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha.

**`billing`** — the existing ledger + wallet table introduced by the platform. Test harnesses create it with the same schema as the real table: `pk` (S, HASH), `sk` (S, RANGE), plus the `GSI_LEDGER_DATE` index (`ledger_date` S / `sk` S) used by the platform financial dashboard (irrelevant for ACC tests but declared for schema correctness). Test fixtures write:
- Wallet row: `pk=USER#{sub}`, `sk="WALLET"`, `wallet_balance_cents=<int>`, `currency="usd"`.
- Ledger rows: `pk=USER#{sub}`, `sk=LEDGER#{ts}#{entry_id}` via `billing_shared.new_ledger_entry`.

**`alerts`** — needed as the target of `audit_event`. Tests that verify audit emission bind a real moto table and spy on writes, or simply patch `audit_event` to a `MagicMock` (the KYC test pattern).

### What is NOT created

ACC-005 does NOT create a `banking_banks` table; banks share the `banking_accounts` table (single-table design — `pk=BANK`, `sk=BANK#{bank_id}`). No new `TableDef` rows need to be declared in `scripts/local-ddb-init.py` beyond what ACC-001 specifies.

### S3 bucket (ACC-003 only)

ACC-003 image upload tests use a `_FakeS3` in-process dict (keys → bytes) patched onto the `s3_client` call site in `banking_accounts.py`. Alternatively, the same `mock_aws()` context can create a real moto S3 bucket — either approach satisfies the "no real AWS" constraint. The fake approach is preferred (lower surface area, no bucket-name coordination):

```python
class _FakeS3:
    def __init__(self): self._store = {}
    def put_object(self, Bucket, Key, Body, ContentType=None): self._store[(Bucket, Key)] = Body
    def generate_presigned_url(self, _, Params, ExpiresIn=300): return f"/mock/s3/{Params['Bucket']}/{Params['Key']}"
```

## 4. API / Service Design

ACC-005 tests service functions and route handlers directly — it does NOT use FastAPI's `TestClient` (which requires a running app with all startup hooks and database connections, violating the hermetic constraint). Synchronous service functions are called directly; async route handlers are called with `asyncio.get_event_loop().run_until_complete(handler(...))` or on a fresh loop via `asyncio.new_event_loop()`.

### Test harness base class

Each test module uses `unittest.TestCase` with an `ExitStack` + `mock_aws()`:

```python
@unittest.skipIf(mock_aws is None, "moto is not installed")
class TestAccNNN(unittest.TestCase):
    def setUp(self):
        self.stack = ExitStack()
        self.addCleanup(self.stack.close)
        self.stack.enter_context(mock_aws())
        ddb = boto3.resource("dynamodb", region_name="us-east-1")
        self.banking_table = _make_banking_accounts_table(ddb)
        self.billing_table  = _make_billing_table(ddb)
        self.alerts_table   = _make_alerts_table(ddb)
        # Bind frozen T handles
        from app.services import banking_accounts as svc
        self.svc = svc
        fake_T = SimpleNamespace(
            banking_accounts=self.banking_table,
            billing=self.billing_table,
            alerts=self.alerts_table,
        )
        self.stack.enter_context(patch.object(svc, "T", fake_T))
        # Enable the feature flag
        from app.core.settings import S
        self._S = S
        self._orig_flags = {
            "banking_accounts_enabled": S.banking_accounts_enabled,
            "banking_account_metadata_enabled": S.banking_account_metadata_enabled,
            "banking_account_views_enabled": S.banking_account_views_enabled,
        }
        object.__setattr__(S, "banking_accounts_enabled", True)
        self.addCleanup(self._restore_settings)
    def _restore_settings(self):
        for k, v in self._orig_flags.items():
            object.__setattr__(self._S, k, v)
```

`_make_banking_accounts_table(ddb)` creates the table with the `GSI_ACCOUNT_BY_ID` GSI and `attr_types={"created_at": "N"}` so integer sort keys write correctly. This matches the `TableDef` pattern in `scripts/local-ddb-init.py:29`.

### Helper factories used across modules

```python
def _seed_wallet(billing_table, user_sub: str, balance_cents: int = 10_000) -> None:
    """Write a WALLET row directly (mirrors apply_wallet_delta without the guard)."""
    billing_table.put_item(Item={
        "pk": f"USER#{user_sub}", "sk": "WALLET",
        "wallet_balance_cents": balance_cents, "currency": "usd",
        "updated_at": int(time.time()),
    })

def _seed_ledger_entry(billing_table, user_sub: str, *, amount_cents: int,
                        state: str = "settled", type_: str = "deposit",
                        ts_offset: int = 0) -> dict:
    """Seed one ledger row; return the item. ts_offset lets callers create rows
    at distinct timestamps without patching now_ts globally."""
    from app.services.billing_shared import new_ledger_entry, user_pk
    ts_patch = int(time.time()) + ts_offset
    with patch("app.services.billing_shared.now_ts", return_value=ts_patch):
        sk, item = new_ledger_entry(
            key_name="pk", key_value=user_pk(user_sub),
            entry_type=type_, amount_cents=amount_cents,
            state=state, reason="test",
        )
    billing_table.put_item(Item=item)
    return item
```

## 5. Detailed Behavior & Edge Cases

### ACC-001 test cases (`tests/test_acc_001_accounts.py`)

**Default-account bootstrap is idempotent**
Call `ensure_default_account(sub)` twice. Assert both calls return the same `account_id`. Assert the `banking_accounts` table contains exactly one account row for that user (scan `pk=USER#{sub}` prefix, count rows where `sk.startswith("ACCOUNT#")`). This proves no duplicate rows are created on repeated calls.

**Balance read-through**
Seed a wallet row with 5 000 cents. Call `GET /ui/banking/accounts/{id}/balance` (or call the service directly: `get_wallet_balance(T.billing, user_pk(sub))` reshaped). Assert `value == "50.00"` and `currency == "usd"`. Then call `apply_wallet_delta(billing_table, user_pk(sub), 1_000)` to add 10 dollars. Re-read the balance. Assert it is now `"60.00"`. This proves the account projection is a live read, not a cached copy.

**Typed attributes round-trip**
Create an account with `attributes=[{"name": "nickname", "type": "STRING", "value": "my-acc"}]`. Fetch with `get_account`. Assert the `attributes` list round-trips exactly (field names, types, values).

**`iban` and `routing_number` persist as opaque strings**
Create an account with `iban="GB29NWBK60161331926819"` (not validated). Assert `get_account` returns the same string unchanged.

**Non-owner `get_account` returns 404**
Create an account for `user_A`. Call `get_account(account_id, requester_sub="user_B")` (no co-owner row for B). Assert 404 (or equivalent `AccountNotFound` exception). This verifies ownership enforcement via `GSI_ACCOUNT_BY_ID` lookup + owner assertion — no cross-user leak.

**Delete-default returns 409**
Create the default account via `ensure_default_account`. Call `delete_account(account_id, owner_sub)`. Assert a 409-equivalent exception with a message containing "default" or "wallet".

**Flag-off: routes absent / service raises**
With `object.__setattr__(S, "banking_accounts_enabled", False)`, call `ensure_default_account` through the router or assert the module's guarded entry point raises 404. The simplest form: import the router module and check it has no routes if constructed with the flag off, or call the handler and expect a 404 `HTTPException`.

**Bank catalog: list and get**
Seed one bank row (`pk=BANK`, `sk=BANK#testlogon`). Call `list_banks()`. Assert the returned list contains one entry with the correct `bank_id`. Call `get_bank("nonexistent")`. Assert 404.

### ACC-002 test cases (`tests/test_acc_002_transactions.py`)

**Projection equals the billing ledger**
Seed five `LEDGER#` rows for `user_A`. Call `list_account_transactions(account_id, requester_sub="user_A")`. Assert the returned `transaction_id` set equals the set of `entry_id` values from the seeded rows. This proves no duplication and no omission.

**Newest settled `new_balance` equals live wallet**
Seed wallet at 20 000 cents. Seed three settled ledger rows. Call `list_account_transactions` (order=`desc`, limit=10). Assert `transactions[0]["new_balance"]["value"]` equals `"200.00"` (the live wallet balance converted to dollars). This is the load-bearing read-through assertion.

**Running balance chains backward correctly**
Using the three settled rows above (amounts 100, 200, 300 cents in order oldest→newest), the newest row's `new_balance` is the wallet balance (20 000 cents = $200.00). The middle row's `new_balance` should be wallet − newest_signed_amount; the oldest should chain one step further. Assert each transition: `txns[i]["new_balance"]["value"] == txns[i-1]["new_balance"]["value"] - cents_to_dollars(txns[i-1]["amount"]["value"])`. Note: only `state=settled` rows move the balance; a `pending` row between two settled rows must show the carried balance without subtraction.

**Date-range bounds via `sk` key condition**
Seed rows at `ts = [1000, 2000, 3000, 4000]`. Call with `from_ts=2000, to_ts=3000`. Assert exactly two rows are returned (ts 2000 and 3000). Assert no row outside the range appears.

**Cursor round-trips, full pagination yields every row once**
Seed 12 rows. Call with `limit=5`. Save the cursor. Call again with `limit=5, cursor=<saved>`. Call a third time with `limit=5, cursor=<second_cursor>`. Collect all returned `transaction_id` values. Assert the union equals all 12 seeded `entry_id` values with no duplicates.

**Tampered cursor falls back to page-1, not 500**
Build a valid cursor string, flip one character in the signature segment. Call `list_account_transactions(cursor=<tampered>)`. Assert the result is the same as a page-1 call (first N rows) and no exception is raised. This tests `decode_cursor` returning `None` and the service treating `None` as `ExclusiveStartKey=None`.

**Non-owner request returns 404**
Seed an account for `user_A`. Call `list_account_transactions(account_id, requester_sub="user_B")`. Assert 404.

### ACC-003 test cases (`tests/test_acc_003_metadata.py`)

**Ledger row is byte-identical before and after metadata write (immutability proof)**
Seed one `LEDGER#` row and capture its full item dict via `billing_table.get_item`. Call `put_transaction_narrative(account_id, transaction_id, text="hello", author_sub="user_A")`. Re-fetch the billing item. Assert the two dicts are equal (use `==` on the full item). Repeat for `add_transaction_tag`, `add_transaction_comment`, `put_geotag`, `set_transaction_image`. This is the central invariant of the entire ACC design.

**Tags are multi (N rows); narrative is singleton (PUT-replaces)**
Add two tags with different values. Assert the `banking_accounts` table has two rows matching `sk.startswith(f"META#{txn_id}#TAG#")`. Add a narrative. Add a second narrative (different text). Assert only one row exists for `META#{txn_id}#NARRATIVE` and it contains the second text (last write wins).

**Comment add + delete**
Add two comments. Delete one by `comment_id`. Fetch metadata via `get_transaction_metadata`. Assert only one comment is returned.

**`get_transaction_metadata` issues one `begins_with` query**
Patch `banking_accounts_table.query` to count calls. Seed narrative + two tags + one comment + geotag. Call `get_transaction_metadata`. Assert exactly **one** `query` call was made (verifying the single `begins_with("META#{txn_id}#")` design). Assert all five items appear in the response.

**Image upload stores via S3 and returns a URL**
Patch `s3_client` to `_FakeS3()`. Call `set_transaction_image(account_id, transaction_id, image_bytes=b"FAKEIMAGE", content_type="image/png", author_sub="user_A")`. Assert `_FakeS3._store` contains the key `banking-metadata/{account_id}/{transaction_id}/{image_id}`. Fetch metadata. Assert the `image.url` field is non-empty (dev: `/mock/s3/...` shape or whatever the fake returns).

**Metadata on unknown `transaction_id` returns 404**
Call `put_transaction_narrative(account_id, "nonexistent_txn_id", ...)`. Assert a 404-equivalent exception is raised. This tests that `get_account_transaction` is called first and fails fast.

**Non-owner metadata write returns 403/404**
Seed an account for `user_A`. Call `put_transaction_narrative(account_id, txn_id, author_sub="user_B")` with `requester_sub="user_B"` and no co-owner row. Assert 403 or 404 (implementation choice; both are acceptable; the critical property is that the write is rejected).

**Flag-off: metadata routes absent**
With `object.__setattr__(S, "banking_account_metadata_enabled", False)`, call `put_transaction_narrative` through the guarded path and assert it raises 404. The `banking_accounts_enabled` flag must also be True for this test to isolate the sub-flag.

### ACC-004 test cases (`tests/test_acc_004_coaccess.py`)

**`add_account_owner` surfaces account in new owner's `list_accounts`**
Create an account owned by `user_A`. Call `add_account_owner(account_id, owner_sub="user_A", new_owner_sub="user_B")`. Call `list_accounts("user_B")`. Assert the shared account appears in the list. Assert its `owners` list contains both `user_A` and `user_B`.

Verify the reverse-index row was written: query `banking_table` for `pk=USER#user_B`, `sk=ACCOUNT_REF#{account_id}`. Assert the row exists with `owner_sub="user_A"`.

**`remove_account_owner` reverses the grant**
After `add_account_owner`, call `remove_account_owner(account_id, owner_sub="user_A", target_sub="user_B")`. Call `list_accounts("user_B")`. Assert the account no longer appears. Assert the `ACCOUNT_REF#` row is gone.

**Remove-last-owner raises 409**
Call `remove_account_owner(account_id, owner_sub="user_A", target_sub="user_A")` (the only owner trying to remove themselves). Assert 409. The `owners` list must not change.

**Non-owner with VEW grant receives projected response**
Stub `resolve_active_grant(grantee_sub, "account", account_id, view_id)` to return a mock grant object indicating `iban` is hidden (`can_see_iban=False`). Stub `project_resource(resource, grants, "account")` to return the resource dict with `iban` omitted. Call `get_account(account_id, requester_sub="user_B")` where `user_B` has no co-owner row but `resolve_account_access` resolves via the stub. Assert the returned dict does NOT contain `iban`. Assert `user_A` (the owner) calling the same function DOES receive `iban` (unprojected path).

The stub pattern:
```python
self.stack.enter_context(
    patch("app.services.banking_accounts.resolve_active_grant",
          return_value=mock_grant)
)
self.stack.enter_context(
    patch("app.services.banking_accounts.project_resource",
          side_effect=lambda res, grants, rt: {k: v for k, v in res.items() if k != "iban"})
)
```

**No grant + no ownership → 404, no information leak**
Call `get_account(account_id, requester_sub="user_C")` where `user_C` has no co-owner row and `resolve_active_grant` returns `None`. Assert 404. This is the critical no-leak assertion.

**`banking_account_views_enabled=False` skips view path; multi-owner still works**

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 — one code path, no `dev_mode` branches

ACC-005 verifies this by design: every test calls the real service function against a moto-backed `T.billing` table. There are no `if S.dev_mode:` conditionals in the services under test (the ACC-001..004 specs are explicit about this). If a dev-mode branch were introduced in `banking_accounts.py`, the moto-based tests would exercise it and the prod path would be uncovered — `coverage.py` on CI would surface the gap.

The S3 image upload test (ACC-003) uses a `_FakeS3` that behaves identically to the real boto3 S3 client interface (same method names and parameter shapes). This mirrors the `_process_export_inline` / `_process_export_s3` test pattern for audit exports and ensures the service's S3 call site is identical in both paths.

### Idempotency

`ensure_default_account` is tested for idempotency: two calls → one row, same `account_id`. This is the principal idempotency invariant for ACC.

`put_transaction_narrative` is idempotent by PUT-replace semantics — tested by calling it twice and asserting exactly one `META#...#NARRATIVE` row exists. Same for `put_geotag` and `set_transaction_image`.

The reverse-index write in `add_account_owner` is also effectively idempotent: calling it twice for the same pair must not create two `ACCOUNT_REF#` rows (the service uses a conditional `put_item` or checks existence first — the test asserts only one row after two calls).

### Money-safety

The **ledger-immutability test** (ACC-003 `test_ledger_row_byte_identical_after_metadata_write`) is the primary money-safety check. It must be run for every metadata mutation type (narrative, tag, comment, geotag, image). Failure of any of these tests means ACC-003 is forking billing — a critical regression.

The **balance read-through test** (ACC-001/002) is the dual check: the account balance is always the live wallet value, never a stale copy. These two tests together are the "additive over billing" guarantee in executable form.

No money-moving code is introduced by ACC-001..004 or tested by ACC-005. Any test that finds itself calling `apply_wallet_delta` with a non-zero delta in a context other than fixture setup is incorrect — `apply_wallet_delta` in tests is only used to prove the read-through (i.e., deposit into the wallet, then re-read the account balance).

### Security

Non-owner access tests (`get_account` 404 for foreign requester, metadata write rejection, VEW grant gate) are the security assertions. These are covered under every ACC sub-module's test set.

The cursor tamper test (ACC-002) verifies that a forged `cursor` query parameter cannot be used to page from an arbitrary DynamoDB key — `decode_cursor` returns `None` on signature failure and the service falls back to page-1, consistent with `cursor.py:103-124`.

## 8. Backward Compatibility & Migration

ACC-005 adds only new test files and has no runtime surface. It does not modify any production code, existing tests, migrations, or DynamoDB schemas.

The test files create tables in the moto in-memory context with `CreateTable` calls scoped to `mock_aws()` — they do not interact with DynamoDB Local or any persistent data store. The `ExitStack` + `addCleanup` pattern ensures all moto resources are torn down after each test class, preventing cross-test pollution.

Existing tests (`tests/test_gap_*.py`, `tests/test_billing*.py`, etc.) are unaffected. ACC-005 test modules are entirely new files under `tests/`.

The `billing_shared.py`, `cursor.py`, and `aws_clients.py` primitives are not modified by these tests. They are imported and exercised read-only (or via fixture writes that mirror their normal call sites). If a future refactor changes a primitive's interface, ACC-005 tests will fail loudly — which is the intended early-warning behavior.

## 10. Open Questions / Assumptions

**Q1: Are route handlers async or sync?**
The ACC-001..004 specs do not specify. The test harness assumes they may be async (following the pattern in `tests/test_gap_0265_0266_kyc_risk_scoring.py`) and calls them via `asyncio.new_event_loop().run_until_complete(handler(...))` when needed. If the handlers are synchronous (like most billing endpoints), the call is a direct invocation. The `setUp` code should detect the handler type and dispatch accordingly, or the implementation can be forced to sync for simplicity.

**Q2: VEW module name and import path**
ACC-004 imports `resolve_active_grant` and `project_resource` from `app/services/account_views.py` (the planned VEW implementation). The exact module path must match what VEW-001..003 will deliver. ACC-005 stubs these at `app.services.banking_accounts.resolve_active_grant` (the import site in the service module, after `from app.services.account_views import resolve_active_grant`). If the VEW module name changes, the patch path changes accordingly.

**Q3: `_FakeS3` vs moto S3**
The spec recommends `_FakeS3` for simplicity. If ACC-003's image upload implementation uses boto3 S3 methods beyond `put_object` and `generate_presigned_url` (e.g., `create_multipart_upload`, `copy_object`), moto S3 is the safer choice. The implementation detail should be confirmed before writing the image tests.

**Q4: `audit_event` assertion style — spy vs moto T.alerts**
Both approaches are valid. The spec shows patching `audit_event` to a `MagicMock` for simplicity (KYC pattern from `test_gap_0272_0273_kyc_decision_events.py`). If the audit assertion is "did any audit row land in DDB" (not just "was the function called"), the moto `T.alerts` approach (seeded table, query after operation) is more rigorous. The choice should be consistent within a module.

**Q5: `Settings` attribute names**
ACC-005 assumes the settings keys added by ACC-001 are exactly `banking_accounts_enabled`, `banking_account_metadata_enabled`, `banking_account_views_enabled`, and `banking_accounts_table_name`. If ACC-001 uses different names, the `object.__setattr__` calls in `setUp` will raise `AttributeError` — which is the intended early failure. The ACC-001 spec (`docs/openbankproject/specs/ACC-001.md` §3 "Settings additions") must be the authoritative source.

**Assumptions**

- `app/services/banking_accounts.py` is a single service module (not split into `banking_banks.py` and `banking_accounts.py`). If split, the `patch.object` calls must target both modules.
- `TestClient` is intentionally NOT used; this is consistent with the KYC and EC2 test pattern and the CLAUDE.md note that the test harness does not require the dev stack.
- The `create_app()` factory in `app/main.py` exists and conditionally registers the banking router — but ACC-005 does NOT call `create_app()`. Route-presence tests are done by inspecting `S.banking_accounts_enabled` and the router's route list directly.
- The `billing_shared` module's `now_ts` import is `from app.core.time import now_ts` (per `billing_shared.py:7`). Patching `app.services.billing_shared.now_ts` is correct.
