## 1. Summary & Goal

VEW-004 closes the gap identified in `docs/openbankproject/OBP_GAP_ANALYSIS.md` §C:

> *"Entitlement REQUESTS (user requests role → admin approves) — MISSING; no self-service request/approval queue"*

The feature adds a self-contained, single-table workflow where a regular user **requests** a named role or admin scope; the request lands in an **admin approval queue** with a `pending → under_review → approved | rejected` state machine plus requester-initiated `cancelled`; on approval, the grant is applied through the **planned STU ACL** (`assign_role_to_user` — STU-002 §4.1). The approve step is soft-coupled to STU via an `ImportError`-guarded adapter: the queue ships and is fully functional before STU lands; if the ACL module is absent at approval time the request is still marked `approved` with `grant_pending_acl=true`, which a later reconciliation sweep can replay without re-running the approval workflow.

The lifecycle machine and queue mechanics mirror `app/services/kyc_case_assignment.py` (claim/CAS/audit pattern) and the privilege-grant posture of `app/routers/admin_roles.py` (ROOT-only grant, ADMIN claim/reject). This is the queue backbone that Open Bank Project calls the "entitlement request" surface.

Goals:

1. New `entitlement_requests` DynamoDB table with two GSIs (by-status queue, by-requester feed).
2. `app/services/entitlement_requests.py` — full lifecycle service.
3. `app/routers/entitlement_requests.py` — user routes + admin queue routes, conditionally registered.
4. Pydantic models in `app/models.py`.
5. Webhook events in `app/services/webhook_service.py:WEBHOOK_EVENT_TYPES_V2`.
6. Rate limiting on `create_request` reusing `rate_limit._bucket_limit`.
7. Hermetic test suite `tests/test_vew_004_entitlement_requests.py`.

## 3. Data Model

### 3.1 New DynamoDB table: `entitlement_requests`

Single-table design. Add `TableDef` to `scripts/local-ddb-init.py` and handle `T.entitlement_requests` to `app/core/tables.py`.

**Partition key**: `pk` (S)
**Sort key**: `sk` (S)

#### Request row — lifecycle record

```
pk  = ENTREQ#{request_id}
sk  = META
```

Attributes:

| Attribute | Type | Notes |
|-----------|------|-------|
| `request_id` | S | `uuid4().hex` — 32-char hex |
| `requester_sub` | S | User who submitted the request |
| `entitlement_kind` | S | `"acl_role"` or `"admin_scope"` (allowlist) |
| `target_ref` | S | `role_id` (STU ACL) or `AdminScope` value |
| `justification` | S | Free text, max 2000 chars |
| `status` | S | `pending` / `under_review` / `approved` / `rejected` / `cancelled` |
| `claimed_by_sub` | S | Admin who claimed the request (set on claim) |
| `claimed_at` | N | Unix timestamp of claim |
| `decided_by_sub` | S | Admin/root who approved or rejected |
| `decided_at` | N | Unix timestamp of decision |
| `decision_reason` | S | Free text, max 1000 chars |
| `grant_pending_acl` | BOOL | `True` when STU ACL absent at approval — requires reconciliation |
| `created_at` | N | `now_ts()` at creation |
| `updated_at` | N | `now_ts()` on every state transition |
| `GSI1PK` | S | `STATUS#{status}` — by-status queue GSI key |
| `GSI1SK` | N | `created_at` — queue ordered newest-first |
| `GSI2PK` | S | `REQUESTER#{requester_sub}` — by-requester feed GSI key |
| `GSI2SK` | N | `created_at` — requester feed ordered newest-first |

#### Audit row — per-request event log

```
pk  = ENTREQ#{request_id}
sk  = AUDIT#{ts:013d}#{event_id}
```

Attributes: `event_type` (S), `actor_sub` (S), `from_status` (S), `to_status` (S), `reason` (S), `created_at` (N). No GSI needed; queried by partition key only, `ScanIndexForward=False`.

#### GSI definitions

**`by-status`** (admin queue):
- `IndexName`: `by-status`
- `KeySchema`: `GSI1PK` (HASH, S), `GSI1SK` (RANGE, N)
- `attr_types`: `{"GSI1SK": "N"}` — **required** to avoid `ValidationException` when querying with integer comparators (CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha; see live example `local-ddb-init.py:52-53`).
- Projection: `ALL`

**`by-requester`** (user feed):
- `IndexName`: `by-requester`
- `KeySchema`: `GSI2PK` (HASH, S), `GSI2SK` (RANGE, N)
- `attr_types`: `{"GSI2SK": "N"}` — same requirement.
- Projection: `ALL`

## 4. API / Service Design

### 4.1 Service: `app/services/entitlement_requests.py`

Module-level constants:

```python
VALID_ENTITLEMENT_KINDS: frozenset[str] = frozenset({"acl_role", "admin_scope"})
VALID_ADMIN_SCOPES: frozenset[str] = frozenset({s.value for s in AdminScope})
OPEN_STATUSES: frozenset[str] = frozenset({"pending", "under_review"})
```

#### Function signatures

```python
def create_request(
    requester_sub: str,
    entitlement_kind: str,
    target_ref: str,
    justification: str,
) -> dict
```
- Validates `entitlement_kind` in `VALID_ENTITLEMENT_KINDS` → `HTTPException(400, code="invalid_kind")`.
- For `"admin_scope"`: validates `target_ref` in `VALID_ADMIN_SCOPES` → `400 code="invalid_scope"`.
- For `"acl_role"`: attempts `from app.services.crm_acl import get_acl_role; get_acl_role(target_ref)` — adapter-gated (`except ImportError: pass`; if module present but role absent → `404 code="role_not_found"`).
- Calls `_check_duplicate_open_request(requester_sub, entitlement_kind, target_ref)`: queries `by-requester` GSI for `GSI2PK=REQUESTER#{requester_sub}`, filters in-process for `entitlement_kind + target_ref + status in OPEN_STATUSES` → `409 code="duplicate_open_request"` if found (DDB FilterExpression doesn't reduce page size — CLAUDE.md; must loop `LastEvaluatedKey`).
- Enforces `entitlement_request_max_open_per_user` count limit → `429 code="open_request_limit_reached"`.
- Calls `rate_limit_entitlement_request(requester_sub)` → `429` if over window.
- Writes META row + both GSI keys.
- Writes in-table AUDIT row (`event_type="created"`).
- Calls `audit_event("entitlement_request.created", requester_sub, request_id=..., kind=..., target_ref=...)`.
- Returns the new request dict.

```python
def list_queue(
    status: str = "pending",
    *,
    cursor: str | None = None,
    limit: int = 50,
) -> dict  # {"requests": list[dict], "next_cursor": str | None}
```
- Validates `status` in `{"pending", "under_review", "approved", "rejected", "cancelled"}` → `400`.
- Queries `by-status` GSI: `GSI1PK=STATUS#{status}`, `ScanIndexForward=False` (newest-first), `Limit=limit`.
- Passes `ExclusiveStartKey=decode_cursor(cursor)` if cursor provided.
- Loops `LastEvaluatedKey` only if the caller passed `limit` that overshoots the page boundary (single call for the normal path; looping only if `limit > 1MB_page_ceiling`).
- Returns `{"requests": [...], "next_cursor": encode_cursor(...)}`.

```python
def list_my_requests(requester_sub: str) -> list[dict]
```
- Queries `by-requester` GSI: `GSI2PK=REQUESTER#{requester_sub}`, `ScanIndexForward=False`.
- Loops `LastEvaluatedKey` (CLAUDE.md: FilterExpression / sparse-attr gotcha).
- Returns all requests (no cursor). Note: `entitlement_request_max_open_per_user` bounds only *open* (pending + under_review) requests. A user with many terminal requests (approved/rejected/cancelled) can accumulate more total rows than this limit; the function returns all of them without pagination. If list growth is a concern in future, a cursor can be added.

```python
def get_request(request_id: str) -> dict  # raises HTTPException(404) if absent
```
- `T.entitlement_requests.get_item(Key={"pk": f"ENTREQ#{request_id}", "sk": "META"})`.
- Returns item or raises `404 code="request_not_found"`.

```python
def claim_request(request_id: str, admin_sub: str) -> dict
```
- Reads current item via `get_request`.
- **Compare-and-swap** `update_item` with `ConditionExpression="#st = :pending AND attribute_not_exists(claimed_by_sub)"`:
  - `UpdateExpression`: SET `status=under_review`, `claimed_by_sub`, `claimed_at`, `updated_at`, `GSI1PK=STATUS#under_review`.
  - On `ConditionalCheckFailedException` (botocore `ClientError` with code `ConditionalCheckFailedException`): re-read item; if `claimed_by_sub != admin_sub` → `409 code="already_claimed"`; if `status not in OPEN_STATUSES` → `409 code="request_not_open"`.
- Writes AUDIT row (`event_type="claimed"`, `from_status="pending"`, `to_status="under_review"`).
- Calls `audit_event("entitlement_request.claimed", admin_sub, request_id=..., requester_sub=...)`.
- Returns updated item.

```python
def approve_request(request_id: str, admin_sub: str, *, reason: str = "") -> dict
```
- Reads item, validates `status in OPEN_STATUSES` → `400 code="request_not_open"`.
- Transitions to `approved`: `update_item` SET `status`, `decided_by_sub`, `decided_at`, `decision_reason`, `updated_at`, `GSI1PK=STATUS#approved`.
- **Applies the STU ACL grant** — adapter-gated:
  ```python
  grant_applied = False
  grant_pending_acl = False
  try:
      from app.services.crm_acl import assign_role_to_user
      assign_role_to_user(admin_sub, item["target_ref"], item["requester_sub"])
      grant_applied = True
  except ImportError:
      grant_pending_acl = True
  except Exception as exc:
      logger.warning("entitlement_requests: STU ACL grant failed request_id=%s: %s", request_id, exc)
      grant_pending_acl = True
  ```
  If `grant_pending_acl`, `update_item` additionally sets `grant_pending_acl=True`.
- Writes AUDIT row + `audit_event("entitlement_request.approved", admin_sub, requester_sub=..., target_ref=..., grant_applied=grant_applied, grant_pending_acl=grant_pending_acl)`.
- Returns updated item. **Never raises** out of the approval (the request is `approved` regardless of the ACL step).

```python
def reject_request(request_id: str, admin_sub: str, reason: str) -> dict
```
- Validates `status in OPEN_STATUSES` → `400 code="request_not_open"`.
- Transitions to `rejected`; writes AUDIT row + `audit_event("entitlement_request.rejected", ...)`.

```python
def cancel_request(request_id: str, requester_sub: str) -> dict
```
- Reads item; validates `item["requester_sub"] == requester_sub` → `403 code="not_requester"`.
- Validates `status in OPEN_STATUSES` → `400 code="request_not_open"`.
- Transitions to `cancelled`; writes AUDIT row + `audit_event("entitlement_request.cancelled", requester_sub, ...)`.

```python
def get_request_history(request_id: str) -> list[dict]
```
- `query(KeyConditionExpression=Key("pk").eq(f"ENTREQ#{request_id}") & Key("sk").begins_with("AUDIT#"), ScanIndexForward=False)`.
- Returns list of audit row dicts, newest-first.

## 5. Detailed Behavior & Edge Cases

### 5.1 Duplicate-open-request guard

`create_request` must reject a second request for the same `(requester_sub, entitlement_kind, target_ref)` where the existing request is still open (`status in {"pending", "under_review"}`). Because DynamoDB `FilterExpression` does not reduce page size (CLAUDE.md gotcha), the duplicate check loops `LastEvaluatedKey` on the `by-requester` GSI and applies the composite filter in-process. This is bounded by `entitlement_request_max_open_per_user` (default 10), so the maximum scan is 10 items per check — safe.

### 5.2 CAS claim conflict

When two admins race to claim the same `pending` request:

- Admin A's `update_item` with `ConditionExpression="status = :pending AND attribute_not_exists(claimed_by_sub)"` succeeds, setting `status=under_review`.
- Admin B's identical CAS fires `ConditionalCheckFailedException`.
- The service catches it, re-reads the item, and returns `409 code="already_claimed"` with `claimed_by_sub` in the response so the admin UI can display who claimed it.

An admin may claim a request they themselves already claimed (idempotent; CAS re-check: `claimed_by_sub == admin_sub` → update `claimed_at` timestamp only).

### 5.3 STU ACL adapter gating on approve

Three scenarios at `approve_request` time:

1. **STU present, role exists**: `assign_role_to_user(admin_sub, target_ref, requester_sub)` succeeds; `grant_applied=True`, `grant_pending_acl=False`.
2. **STU module absent** (`ImportError`): request transitions to `approved`, `grant_pending_acl=True`. Logged at WARNING. A later reconciliation sweep (out-of-scope for VEW-004) can query `by-status` GSI for `STATUS#approved` rows where `grant_pending_acl=True` and replay the grant once STU lands.
3. **STU present, role absent or service error**: same as case 2 — `grant_pending_acl=True`. The approval is NOT rolled back. The admin sees `grant_pending_acl: true` in the response and may re-trigger via a future `POST /ui/admin/entitlement-requests/{id}/retry-grant` endpoint (out of scope for this ticket).

### 5.4 `admin_scope` target validation

When `entitlement_kind = "admin_scope"`, `target_ref` must be a value in `AdminScope` (`roles.py:14-19`): one of `auth_support`, `billing_support`, `content_moderation`, `content_moderation_senior`. On approve, the ACL step for `admin_scope` calls `assign_admin_scope(admin_sub, requester_sub, target_ref)` rather than `assign_role_to_user` — this is another adapter-gated import from the STU service. In the interim (STU absent), the request is marked `approved + grant_pending_acl=True`.

### 5.5 State machine invariants

| Transition | Guard |
|---|---|
| `pending → under_review` | CAS: `status = pending AND attribute_not_exists(claimed_by_sub)` |
| `under_review → approved` | `status in {pending, under_review}`, ROOT only |
| `under_review → rejected` | `status in {pending, under_review}`, ADMIN or ROOT |
| `pending/under_review → cancelled` | `status in {pending, under_review}`, requester only |
| `approved/rejected/cancelled → any` | Forbidden (`400 code="request_not_open"`) — terminal states |

An approved request can never be re-opened (no undo; if the grant was wrong, a ROOT-initiated revocation via `admin_roles.py` is the correct path).

### 5.6 Open-request count limit

`create_request` counts open requests (status in `OPEN_STATUSES`) for the requester by looping the `by-requester` GSI and filtering in-process. If `count >= S.entitlement_request_max_open_per_user` → `429 code="open_request_limit_reached"`. This is a soft limit (config-tunable, not a DDB conditional put), checked before the write.

### 5.7 Pagination edge case

The `list_queue` endpoint returns up to `limit` items (default 50, max 200) per page. Because `FilterExpression does not reduce page size` (CLAUDE.md), each GSI query page may return fewer than `limit` results even if more exist. The service issues a single query call with `Limit=limit`; if the caller needs the next page they pass the `next_cursor`. The admin UI is expected to implement cursor-based navigation, not client-side "load all".

### 5.8 `justification` minimum length

`EntitlementRequestCreateIn.justification` has `min_length=10` to reject trivially empty submissions (`"."`, `"ok"`, etc.). The router returns `422 Unprocessable Entity` from Pydantic validation before reaching the service layer.

### 5.9 Self-request guard

`create_request` does not explicitly forbid a user from requesting their own current role (a USER requesting `USER` scope, or an ADMIN requesting a scope they already hold). The STU ACL `assign_role_to_user` is idempotent for already-held roles, so this is harmless. The duplicate-open-request guard prevents spam.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007: no dev_mode branch

All persistence goes through `T.entitlement_requests` (a `_FloatSafeTable`, `tables.py:29-60`) backed by DynamoDB Local (port 8001) in dev and real DynamoDB in prod. There is no `if S.dev_mode:` branch in `entitlement_requests.py`. The STU ACL adapter gate (`try: from app.services.crm_acl import ...`) behaves identically in dev and prod — both resolve the same module import at runtime.

### 7.2 Idempotency

- **`create_request`** is NOT idempotent by design (each call creates a new `request_id`). The duplicate-open guard prevents identical pending requests.
- **`claim_request`** is idempotent for the claiming admin: re-claiming a request you already claimed updates `claimed_at` only (CAS re-check: `claimed_by_sub == admin_sub`).
- **`approve_request`** / **`reject_request`** / **`cancel_request`** are idempotent in the sense that they reject terminal-state items with `400 code="request_not_open"`. If the same admin calls approve twice, the second call returns `400`.
- **STU `assign_role_to_user`** is expected to be idempotent on the STU side (assigning an already-held role is a no-op). VEW-004 does not enforce this at the service boundary.

### 7.3 Security

- **Privilege escalation guard**: `approve_request` requires `Depends(require_root)` (`policy.py:63`). An ADMIN attempting to approve receives `403 role_required {required_roles: ["root"]}`. Claim and reject use `require_admin_or_root_csrf`, which also validates the CSRF token for cookie-auth sessions (`policy.py:100-106`).
- **Requester isolation**: `cancel_request` validates `item["requester_sub"] == requester_sub` before proceeding; an admin cannot cancel on a requester's behalf through this endpoint (they may reject instead).
- **`justification` stored as-is**: no HTML rendering — displayed in an admin UI text cell, not injected into HTML. No XSS risk. Truncation at 2000 chars at the Pydantic layer.
- **Rate limiting on `create_request`**: `_bucket_limit` uses `T.sessions` (existing table, no new infra), key `rl#entreq#create`, window = 1 hour, max = 20 requests. Prevents bulk-spamming the queue.
- **No money movement**: VEW-004 is a role-granting workflow. No wallet balance, ledger entries, billing charges, or payment methods are touched. `settle_or_reverse_ledger`, `new_ledger_entry`, `_fraud_gate` are not involved.

### 7.4 Money-safety (not applicable, noted for completeness)

VEW-004 has no money paths. The STU ACL grant is a privilege assignment, not a financial transaction. No billing-layer primitives are called. This note satisfies the MONEY-SAFETY requirement by explicit exclusion.

### 7.5 Audit completeness

Every state transition writes both:
1. A global `audit_event(...)` to `T.alerts` (queryable by admins cross-resource via the alerts table GSI).
2. A per-request in-table `AUDIT#` row (queryable by request ID via `get_request_history`).

Both paths are synchronous and happen before the endpoint returns. A failure in the audit write does not abort the state transition (the `_write_audit_row` helper catches exceptions and logs at WARNING — same best-effort pattern as `kyc_case_assignment._write_audit_event`).

6. **Webhook dispatch**: VEW-004 adds event types to `WEBHOOK_EVENT_TYPES_V2` but does not add webhook dispatch calls in the service (the `audit_event` path is sufficient for V1). A follow-up may wire `emit_webhook_event(...)` calls on the four transitions once the event taxonomy stabilizes.
