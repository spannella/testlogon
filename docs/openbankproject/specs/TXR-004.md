# TXR-004 — Execution — money movement via existing primitives, fraud-gated, idempotent to COMPLETED

**Ticket series**: OBP Tier-1 Transaction Requests + Step-Up SCA
**Depends on**: TXR-001 (entity + create), TXR-002 (state machine + limits), TXR-003 (step-up SCA)
**Unblocks**: TXR-005 (tests + FE hook)
**Estimate**: 3.5 days
**Feature flag**: `TXN_REQUESTS_ENABLED` (default `false`)

---

## 1. Summary & Goal

TXR-004 is the execution engine for the Transaction Request state machine: it takes a request that is `INITIATED` (no SCA required) or `PENDING` (SCA satisfied via TXR-003) and drives the underlying money movement by dispatching to the existing billing primitives, then flips the request to `COMPLETED` (or `FAILED` on any error). Money moves exactly once per `request_id`, no matter how many times the endpoint is called.

This ticket adds one new endpoint — `POST /ui/txn-requests/{request_id}/execute` — and extends `app/services/txn_requests.py` with type-dispatch logic. It does not introduce any new billing table, wallet column, or ledger schema. Every cent moved goes through exactly the same primitives that the live charge, tip, payout, and refund endpoints already use.

**What this ticket does:**

1. Validates preconditions (SCA completeness, fraud gate) before touching any money primitive.
2. Dispatches by `type` to:
   - `WALLET_TRANSFER` / `FREE_FORM`: atomic `transact_write_items` debit+credit via `apply_wallet_delta` + paired `tip_ledger.write_tip_ledger`.
   - `PAYOUT`: `creator_payouts.request_payout`.
   - `REFUND`: a new shared `_do_refund(...)` callable factored from `billing.refund_payment` — `stripe.Refund.create` + `new_ledger_entry` + `settle_or_reverse_ledger`.
   - `COUNTERPARTY`: wallet debit + narrative ledger entry; marks `FAILED counterparty_unsupported` if no settlement rail is wired.
3. Implements idempotency: a second `execute` on the same `request_id` finds a terminal status and returns without moving money again.
4. Finalizes: `_transition(... → COMPLETED)` with `ledger_refs` on success; `_transition(... → FAILED, failure_reason=...)` on any error. Both writes are conditional on status (the status-as-lock invariant from TXR-002).

**What this ticket does NOT do:** Add new ledger schema, new wallet columns, new DDB tables, new OTP logic (TXR-003 owns that), new Stripe/PayPal/CCBill provider primitives, or any frontend UI (TXR-005).

- `_fraud_gate(user_id, amount_cents, entry_type, tx_id, req, *, enforce_block)` at line 118 — always runs a freeze check (single DDB read via `fraud_detection.is_frozen`); then calls `fraud_detection.evaluate_transaction`; raises `HTTPException(403)` for frozen accounts or `block` action. **Status as the lock** (`app/services/txn_requests.py`, introduced in TXR-002):

- `_transition(user_sub, request_id, expected_status, new_status, **patch)` — conditional `update_item` asserting `#status = :expected`; raises `HTTPException(409, "invalid_transition")` on `ConditionalCheckFailedException`. This is the single concurrency primitive that prevents double-execution: the first `execute` call wins the `PENDING → COMPLETED` write; a concurrent second call hits `ConditionalCheckFailedException` and returns the already-`COMPLETED` item, never reaching the money-movement dispatch.

## 4. API / Service Design

### 4.1 Execute endpoint

```
POST /ui/txn-requests/{request_id}/execute
```

- **Auth**: `Depends(require_ui_session)` (cookie-based; CSRF enforced for all non-GET requests per CLAUDE.md).
- **Response**: `200 TxnRequestOut` on success (both idempotent re-hit and fresh execution). Returns `201` on create; `200` on re-hit is consistent with the pattern in `creator_payouts.request_payout` returning the existing payout when already terminal.
- **Flag gate**: `if not S.txn_requests_enabled: raise HTTPException(404)`.

```python
@router.post("/{request_id}/execute", response_model=TxnRequestOut)
async def execute_txn_request(
    request_id: str,
    req: Request,
    ctx=Depends(require_ui_session),
) -> TxnRequestOut:
    if not S.txn_requests_enabled:
        raise HTTPException(status_code=404)
    user_sub = ctx["user_sub"]
    return await asyncio.to_thread(execute_request, user_sub, request_id, req)
```

The service call runs in a thread (`asyncio.to_thread`) because it may issue multiple synchronous DDB calls (and a Stripe API call for REFUND). This mirrors the pattern in `google_drive_integration.py` where the sync service is run in `asyncio.to_thread`.

### 4.2 Service: `execute_request`

```python
def execute_request(
    user_sub: str,
    request_id: str,
    req: Request,
) -> TxnRequestOut:
```

**Full execution flow:**

**Step 1 — Load and guard:**
```python
item = get_request(user_sub, request_id)   # raises 404 if not owned
```
Check `item["status"]`:
- If `COMPLETED` or `FAILED` (already terminal): return `_item_to_out(item)` immediately. Money moved exactly once; idempotent re-hit.
- If not in `{"INITIATED", "PENDING"}`: raise `HTTPException(409, {"code": "invalid_transition", "current_status": item["status"]})`.

**Step 2 — SCA gate (PENDING requests only):**
```python
if item["status"] == "PENDING":
    sca_challenge_id = item.get("sca_challenge_id")
    if not sca_challenge_id:
        # Corrupted state — should never happen; PENDING without a challenge is a bug.
        _fail(user_sub, request_id, "sca_incomplete")
        raise HTTPException(403, {"code": "sca_incomplete"})
    chal = sessions.load_challenge_or_401(user_sub, sca_challenge_id)
    if not sessions.challenge_done(chal):
        raise HTTPException(403, {"code": "sca_incomplete", "required_factors": chal.get("required_factors")})
    # Challenge is done — revoke it (one-shot) before money moves.
    sessions.revoke_challenge(user_sub, sca_challenge_id)
```

`load_challenge_or_401` (sessions.py:517) raises `401` if the challenge is expired or revoked. An expired challenge means the user must re-create the request (or re-trigger TXR-003 if a re-challenge path is added). TXR-004 does not re-mint challenges — it only validates and revokes.

**Step 3 — Fraud gate:**
```python
entry_type = "debit" if item["type"] in ("WALLET_TRANSFER", "FREE_FORM", "PAYOUT", "COUNTERPARTY") else "adjustment"
_fraud_gate(
    user_id=user_sub,
    amount_cents=int(item["amount_cents"]),
    entry_type=entry_type,
    tx_id=request_id,
    req=req,
    enforce_block=True,
)
```

`_fraud_gate` is imported via a **lazy local import** from `app.routers.billing` (to avoid a circular import — `txn_requests.py` is a service, and `app.routers.billing` imports from `app.services.*`; the lazy-import pattern is already used in `app/services/billing_dunning.py:189` for the same reason). If it raises `HTTPException(403)`, the request is transitioned to `FAILED`:
```python
try:
    _fraud_gate(...)
except HTTPException as exc:
    if exc.status_code == 403:
        _fail(user_sub, request_id, "fraud_blocked" if "fraud" in str(exc.detail).lower() else "account_frozen")
    raise
```

**Step 4 — Dispatch by type:**

```python
try:
    ledger_refs = _dispatch(user_sub, item, req)
except HTTPException:
    raise    # already sets status via _fail within each dispatcher
except Exception as exc:
    _fail(user_sub, request_id, "internal_error", detail=str(exc))
    raise HTTPException(500, "internal_error")
```

`_dispatch` returns a list of opaque reference strings (ledger SKs, payout IDs) to store in `ledger_refs`.

**Step 5 — Finalize:**
```python
updated = _transition(user_sub, request_id, item["status"], "COMPLETED", ledger_refs=ledger_refs)
audit_event("txn_request.executed", user_sub, req, request_id=request_id, type=item["type"], amount_cents=item["amount_cents"], ledger_refs=ledger_refs)
# dispatch webhook (best-effort)
try:
    # NOTE: the function is dispatch_webhook_event (not dispatch_event) — webhook_service.py:556
    webhook_service.dispatch_webhook_event("txn_request.executed", user_sub, data={"request_id": request_id, ...})
except Exception:
    pass
return _item_to_out(updated)
```

`_transition` uses the status already read in Step 1 as `expected_status`. If a concurrent second execute already landed `COMPLETED`, `_transition` raises `409` — this is caught at the top of `execute_request` when the item is re-read: the idempotent guard at Step 1 will return early on the re-read. The small window between Step 1 (read) and Step 5 (conditional write) is safe: the conditional write is the real lock; the early return at Step 1 is only an optimization for the common case.

### 4.3 Internal helper: `_fail`

```python
def _fail(user_sub: str, request_id: str, failure_reason: str, *, detail: str = "") -> None:
    """Transition the request to FAILED from any non-terminal status.

    Uses _transition with expected_status matching the current state.
    If the request is already terminal (409), swallows silently — the terminal
    state is already correct.
    """
    try:
        item = get_request(user_sub, request_id)
        current = item.get("status", "INITIATED")
        if current in ("COMPLETED", "FAILED"):
            return
        _transition(user_sub, request_id, current, "FAILED", failure_reason=failure_reason)
        audit_event("txn_request.failed", user_sub, None, request_id=request_id, failure_reason=failure_reason, detail=detail)
    except Exception:
        pass   # best-effort; never let cleanup block the caller's error path
```

### 4.4 Type dispatchers

All dispatchers live in `app/services/txn_requests.py`. Each returns `List[str]` (ledger refs). Each raises `HTTPException` on error and calls `_fail` before raising.

#### `_dispatch_wallet_transfer(user_sub, item)` — WALLET_TRANSFER and FREE_FORM

```python
def _dispatch_wallet_transfer(user_sub: str, item: Dict[str, Any]) -> List[str]:
```

For `WALLET_TRANSFER` (and `FREE_FORM` when `to_user_sub` is present):

1. Build the `TipLedgerEntry`:
   ```python
   entry = TipLedgerEntry(
       tipper_user_id=user_sub,
       recipient_user_id=item["target"]["to_user_sub"],
       amount_cents=int(item["amount_cents"]),
       currency=item.get("currency", "usd").upper(),
       content_type="broadcast",
       content_id=item["request_id"],
       extra_meta={"txn_request_id": item["request_id"], "reason": item.get("reason", "")},
   )
   ```
2. Build the wallet-debit `transact_write_items` batch using the `_transact_client()` / `_batch_transact` pattern from `group_treasury.py:716,743`. The batch contains:
   - `Update` on `USER#{user_sub}` WALLET row: `SET wallet_balance_cents = wallet_balance_cents + :delta` with `ConditionExpression="wallet_balance_cents >= :needed"`.
   - `Update` on `USER#{recipient}` WALLET row: `SET wallet_balance_cents = if_not_exists(wallet_balance_cents, :z) + :amount`.
   Both writes go to `T.billing`. The `transact_write_items` call is all-or-nothing.
3. On `TransactionCanceledException` (insufficient funds): call `_fail(user_sub, request_id, "insufficient_funds")`; raise `HTTPException(402, "insufficient_funds")`.
4. Call `write_tip_ledger(entry)` for the paired ledger rows. `write_tip_ledger` wraps both the debit write and the credit write in individual `try/except` blocks (see `tip_ledger.py:141,161`) — the outer ledger writes are already best-effort. Wrap the `write_tip_ledger` call itself in `try/except Exception` here to keep ledger audit non-blocking (money has moved; a ledger write failure must not roll back the wallet move). NOTE: `write_tip_ledger` returns `{"debit_entry_id": ..., "credit_entry_id": ...}`, NOT the `tip_payment_id`. The `tip_payment_id` is available as `entry.tip_payment_id` (auto-assigned in `TipLedgerEntry.__init__`).
5. Return `[entry.tip_payment_id]` as `ledger_refs`. (Access via `entry.tip_payment_id`, not from `write_tip_ledger`'s return value.)

For `FREE_FORM` without `to_user_sub` (narrative-only, no recipient):
- Only debit the sender wallet via `apply_wallet_delta(T.billing, user_pk(user_sub), -amount)`.
- Write a single debit ledger row via `new_ledger_entry(entry_type="debit", reason="free_form_payment", state="settled")` + `T.billing.put_item(led_item)`.
- No credit issued.
- Return `[led_sk]`.

#### `_dispatch_payout(user_sub, item)` — PAYOUT

```python
def _dispatch_payout(user_sub: str, item: Dict[str, Any]) -> List[str]:
```

1. Extract `method_id = item["target"].get("payout_method_id")`.
2. Call:
   ```python
   result = request_payout(
       user_id=user_sub,
       amount_cents=int(item["amount_cents"]),
       method="bank_transfer",
       notes=item.get("reason", ""),
       method_id=method_id,
   )
   ```
   `request_payout` (creator_payouts.py:282) validates minimum amount, available balance, and the per-user payout slot (`claim_payout_sentinel`, line 225).
3. On `ValueError("DUPLICATE_PAYOUT")`: call `_fail(user_sub, request_id, "payout_duplicate")`; raise `HTTPException(409, "payout_duplicate")`.
4. On `ValueError` with minimum-amount message: call `_fail(user_sub, request_id, "payout_minimum_not_met")`; raise `HTTPException(400, "payout_minimum_not_met")`.
5. Return `[result["payout_id"]]`.

#### `_dispatch_refund(user_sub, item, req)` — REFUND

```python
def _dispatch_refund(user_sub: str, item: Dict[str, Any], req: Request) -> List[str]:
```

1. Extract `payment_intent_id = item["target"]["payment_intent_id"]`.
2. Call `_do_refund(user_id=user_sub, payment_intent_id=payment_intent_id, amount_cents=int(item["amount_cents"]), reason=item.get("reason", ""), req=req)`.
3. `_do_refund` is the new callable factored from `refund_payment` (billing.py:1287). It:
   - Calls `stripe.Refund.create(payment_intent=payment_intent_id, amount=amount_cents, reason=reason)`.
   - Writes `new_ledger_entry(entry_type="adjustment", state="settled", reason="refund", extra={"provider": "stripe", "stripe_payment_intent_id": ..., "stripe_refund_id": ...})` + `T.billing.put_item(led_item)`.
   - Calls `apply_balance_delta(T.billing, pk, {"payments_pending_cents": -amount_cents})` or `payments_settled_cents` depending on original payment status.
   - Calls `settle_or_reverse_ledger(T.billing, "pk", pk, pay["ledger_sk"], "reversed")` if the original ledger SK is stored on the payment record.
   - Calls `update_payment_status(user_id, payment_intent_id, "refunded", charge_id=refund.get("charge"))`.
   - Calls `mark_reverted(user_id, purchase_txn_id, reason)` if `purchase_txn_id` is set on the payment record.
   - Returns `(led_sk, refund_id)`.
4. If Stripe raises an error for an already-refunded intent (e.g., `stripe.error.InvalidRequestError` with code `charge_already_refunded`): call `_fail(user_sub, request_id, "refund_already_issued")`; raise `HTTPException(409, "refund_already_issued")`. NOTE (defense-in-depth): this catch handles an out-of-band manual Stripe refund of the same charge. It is NOT the primary double-refund guard — that is the `PENDING → IN_FLIGHT` single-winner conditional claim (§4.2 Step 2), which structurally prevents a TXR REFUND request from reaching `stripe.Refund.create` twice. The catch is best-effort: the error-code match string must not be relied on for money-safety (stripe-mock may not emit `charge_already_refunded`), but the IN_FLIGHT guard holds regardless.
5. Return `[led_sk]`.

The legacy `POST /billing/refund` endpoint continues to call `refund_payment`, which now calls `_do_refund` internally. The call chain is:
```
legacy endpoint → refund_payment() → _do_refund()
engine:        → _dispatch_refund() → _do_refund()
```
`stripe.Refund.create` is called exactly once per invocation of `_do_refund`. Because the execution is idempotent at the status-lock level (Step 1 returns early for a `COMPLETED` request), `_do_refund` is never called twice for the same `request_id`.

#### `_dispatch_counterparty(user_sub, item)` — COUNTERPARTY

```python
def _dispatch_counterparty(user_sub: str, item: Dict[str, Any]) -> List[str]:
```

Until the Tier-2 Counterparties entity exists, this dispatcher:

1. Debits the sender wallet via `apply_wallet_delta(T.billing, user_pk(user_sub), -amount)`.
2. On success, writes a single debit ledger entry: `new_ledger_entry(entry_type="debit", reason="counterparty_payment", state="pending", extra={"counterparty_ref": item["target"].get("counterparty_ref"), "txn_request_id": request_id})` + `T.billing.put_item(led_item)`.
3. Marks the request `FAILED counterparty_unsupported` and raises `HTTPException(501, "counterparty_unsupported")` so the caller knows money was debited but the outbound settlement rail is not yet wired. The wallet debit **is** reversed immediately by calling `apply_wallet_delta(T.billing, user_pk(user_sub), +amount)` before the FAILED transition.

This is an explicit, non-silent failure: money never leaves the platform, the sender is not debited net, and the failure reason tells the caller exactly why. A follow-up ticket wires the real outbound settlement rail.

### 4.6 Idempotency key deduplication (duplicate create collapse)

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotency — double execute returns the same result

Two concurrent `POST /execute` calls on the same `PENDING` request:

1. Both enter `execute_request` and call `get_request` — both see `status="PENDING"`.
2. Both pass SCA gate (challenge is read but not yet revoked at this point).
3. Both call `_fraud_gate` — both pass.
4. Both call `_dispatch_wallet_transfer` (or whichever dispatcher). Both attempt `transact_write_items`.
5. The `transact_write_items` call is NOT idempotent at the DDB level — it is possible for both to succeed if they are truly concurrent. To prevent double-debit, the debit leg of the `transact_write_items` must include a conditional check: `ConditionExpression="attribute_not_exists(txr_lock_{request_id})"` plus a corresponding `SET txr_lock_{request_id} = :ts` on the sender wallet row. Alternatively — and more simply — the status-lock check in Step 1 plus the `_transition` conditional write provide a second guard: one caller wins `_transition(... PENDING → COMPLETED)`; the other hits `ConditionalCheckFailedException` in `_transition` and re-reads the item at the start, seeing `COMPLETED`, and returns early. The `transact_write_items` has already completed for the winning caller; the losing caller's dispatch is rolled back (never reaches `_transition`'s conditional write because `_transition` raises `409` before dispatch is attempted — but `_transition` is called *after* dispatch in the current flow). **Correction**: the status conditional write must wrap the dispatch, not follow it. The correct safe ordering is:

   **Status-first ordering (safe):**
   a. Claim `PENDING → IN_FLIGHT` via conditional `_transition(expected="PENDING", new="IN_FLIGHT")`. This is an intermediate status that gates concurrent callers out before any money moves.
   b. Dispatch (money moves).
   c. `_transition(expected="IN_FLIGHT", new="COMPLETED")` on success; `_transition(expected="IN_FLIGHT", new="FAILED")` on error.

   The `IN_FLIGHT` status is an implementation detail hidden from the `TxnRequestOut` model (clients may observe it briefly). This is the same pattern the `creator_payouts.claim_payout_sentinel` uses: claim the slot first, then do the work, then advance or release. For `INITIATED → COMPLETED` (no-SCA fast path), `IN_FLIGHT` is used the same way.

   Add `IN_FLIGHT` to the state machine and the `_LEGAL_TRANSITIONS` set in `txn_requests.py`. Include it in the status enum but document it as transient. The `GET /ui/txn-requests/{id}` endpoint surfaces it as-is; clients polling status must tolerate it.

### 5.2 `WALLET_TRANSFER` insufficient funds — no partial move

The `transact_write_items` batch containing the sender debit with `ConditionExpression="wallet_balance_cents >= :needed"` is atomic. If the condition fails, neither the debit nor the credit is applied. The dispatcher catches `TransactionCanceledException`, calls `_fail(... "insufficient_funds")`, and raises `HTTPException(402)`. The request ends `FAILED`.

### 5.3 `PAYOUT` with an already-active payout

`request_payout` (creator_payouts.py:282) calls `_has_active_payout(user_id)` as a fast pre-check, then `claim_payout_sentinel(user_id, payout_id)` as the atomic claim. If `claim_payout_sentinel` raises `ValueError("DUPLICATE_PAYOUT")`, `_dispatch_payout` calls `_fail(... "payout_duplicate")` → request is `FAILED`. No wallet debit has occurred because `request_payout` validates before any balance movement.

### 5.4 `REFUND` of an already-refunded intent

Stripe returns `InvalidRequestError` for a double refund. `_do_refund` catches Stripe exceptions and maps `charge_already_refunded` to `refund_already_issued` → `_dispatch_refund` calls `_fail(... "refund_already_issued")` → request is `FAILED`. The `_do_refund` factoring ensures there is exactly one place in the codebase where `stripe.Refund.create` is called, eliminating the risk of two code paths accidentally issuing two Stripe refunds for the same `payment_intent_id`.

### 5.5 Fraud gate — frozen account

`_fraud_gate` (billing.py:118) reads `fraud_detection.is_frozen(user_id)` via a DDB read, then calls `evaluate_transaction`. On frozen: `HTTPException(403)`. TXR-004 catches the `403`, calls `_fail(... "account_frozen")`, and re-raises. The request ends `FAILED`. No money moves.

### 5.6 `FREE_FORM` without `to_user_sub`

A narrative-only `FREE_FORM` request (no recipient) debits the sender wallet and writes a single ledger entry. This is the "fee" / "service charge" pattern. The caller is debited but no user is credited; the platform may separately process the credited funds (e.g., to a platform escrow wallet `PLATFORM#FEES`). If this behavior is not desired, `FREE_FORM` without `to_user_sub` should be rejected in `_validate_target` (TXR-001). **Assumption for TXR-004**: accept it; document in `CLAUDE.md` "Common gotchas".

### 5.7 Status observed as `COMPLETED` by idempotent caller

The second caller who hits `_transition`'s `ConditionalCheckFailedException` re-reads the item and returns `_item_to_out(current_item)` (status=`COMPLETED`, `ledger_refs` populated). The HTTP status code is `200`, not `409`. The `409` only propagates if the current status is genuinely an illegal target (e.g., `FAILED`). This behavior is by design: a retry on a network timeout should receive the same `200 COMPLETED` as the first successful call.

### 5.8 `IN_FLIGHT` cleanup on crash

If the backend crashes between Step a (`IN_FLIGHT` claim) and Step c (terminal write), the request is stuck in `IN_FLIGHT`. TXR-003 already introduces a sweep task (`start_txn_requests_sweep_task`) for expiring stale `PENDING` challenges. That same sweep should transition any `IN_FLIGHT` request older than a configurable TTL (default `300` seconds) to `FAILED internal_error`. This cleanup task is part of the TXR-003 sweep or a shared background loop in `txn_requests.py`; the design is noted here as a TXR-005/follow-up responsibility but does not block TXR-004.

### 5.9 `COUNTERPARTY` — wallet reversal

As described in §4.4, the COUNTERPARTY dispatcher does not perform a net debit — it reverses the debit before failing. This keeps the platform balance-neutral until a real outbound rail is wired. The ledger entry for the failed attempt is written with `state="cancelled"` for auditability.

### 5.10 Challenge expiry vs `PENDING` request

If the SCA challenge TTL (default `300s`, `S.session_challenge_ttl_seconds` at settings.py:97) elapses before the user completes verification, `load_challenge_or_401` raises `401 "Challenge expired"`. TXR-004 maps this to `_fail(... "sca_incomplete")` — the request transitions to `FAILED`. The user must submit a new request. This is intentional: a timed-out SCA challenge should not be automatically re-mintable from the execute endpoint (that would bypass the SCA security model).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 Dev/prod parity

There are no `if S.dev_mode` branches in `txn_requests.py`. Provider differences are handled entirely by the existing abstractions:

- **DDB**: `T.billing` / `T.txn_requests` route to DDB Local (dev) or real DynamoDB (prod) via `ddb_endpoint_url` in settings — no code divergence.
- **Stripe**: `_do_refund` calls `stripe.Refund.create`. In dev, the Stripe mock (port 12111) handles this call. The mock binary is already running in the dev stack. No `dev_mode` branch is added (SECOPS-007).
- **Fraud detection**: `_fraud_gate` calls `fraud_detection.evaluate_transaction` and `is_frozen` — both are DDB-backed and work identically in dev and prod.
- **MFA/SCA**: `sessions.load_challenge_or_401` and `sessions.challenge_done` read from `T.sessions` (DDB) — same path both environments. Dev-mode OTP mock codes are injected by `mfa.py`'s existing mock branch; TXR-004 never calls `mfa.py` directly, only `sessions.py`.
- **`transact_write_items`**: `_transact_client()` (group_treasury.py:716) constructs a low-level boto3 client inheriting endpoint/credentials from the resource client — dev points to DDB Local, prod to real DDB, with no `S.dev_mode` check.

### 7.2 Idempotency guarantees

Three layers of idempotency:

1. **Early return on terminal status** (Step 1): the cheapest guard. A second `execute` on a `COMPLETED` request returns the existing `TxnRequestOut` immediately, before any fraud check or dispatch.
2. **`IN_FLIGHT` status claim** (`_transition(expected="PENDING/INITIATED", new="IN_FLIGHT")`): prevents concurrent second execution from entering the dispatch phase. Only one caller can win the `→ IN_FLIGHT` conditional write.
3. **Optional idempotency key dedup** on create (§4.6): collapses duplicate `POST /ui/txn-requests` calls to a single `INITIATED` item, ensuring only one request is ever created for a given key from a given user.

### 7.3 Money-safety properties

| Property | Mechanism | Reference |
|---|---|---|
| No double-charge | `IN_FLIGHT` conditional write before dispatch; `COMPLETED` early-return on re-hit | §5.1 |
| Atomic debit+credit for WALLET_TRANSFER | `transact_write_items` batch — all-or-nothing | group_treasury.py:743 |
| Insufficient funds = hard fail | `wallet_balance_cents >= :needed` condition in debit leg; `TransactionCanceledException` → FAILED | billing_shared.py:209 |
| ONE refund mechanism | `_do_refund` is the single `stripe.Refund.create` call site | §4.5 |
| No orphaned IN_FLIGHT | Sweep task (TXR-003/follow-up) transitions stale IN_FLIGHT → FAILED | §5.8 |
| Fraud gate runs before money moves | `_fraud_gate` called before `_dispatch`; 403 → FAILED | §4.2 Step 3 |
| SCA gate runs before money moves | `challenge_done` checked before `IN_FLIGHT` claim for PENDING requests | §4.2 Step 2 |
| COUNTERPARTY debit is always reversed | No net debit until outbound rail exists | §4.4 |

### 7.4 Security

- `user_sub` is always taken from `ctx["user_sub"]` (session dependency), never from the request body or path — a caller cannot execute another user's request.
- `get_request(user_sub, request_id)` uses `Key={"user_sub": user_sub, "request_id": request_id}` — ownership is enforced at the DDB access pattern level. A foreign `request_id` owned by a different `user_sub` simply returns no item → `404`.
- `revoke_challenge` is called before any money moves (Step 2 of execute flow) — an attacker intercepting the `challenge_id` after a successful SCA cannot replay it to trigger a second execution.
- `tx_id=request_id` passed to `_fraud_gate` allows fraud rules to correlate by transaction request ID in their audit log.

### 7.5 Audit trail

Every terminal transition emits:
- `audit_event("txn_request.executed", ...)` or `audit_event("txn_request.failed", ...)` to `T.alerts`.
- Webhook `txn_request.executed` / `txn_request.failed` to `WEBHOOK_EVENT_TYPES_V2` subscribers (best-effort, fire-and-forget).
- The billing/ledger writes produce their own DDB records in `T.billing`, queryable by the existing platform financial dashboard.

## 8. Backward Compatibility & Migration

### 8.1 `_do_refund` refactoring

The existing `POST /billing/refund` (`refund_payment` at billing.py:1287) is refactored so its body is extracted into `_do_refund`. The public behavior of `POST /billing/refund` is **identical**. The refactoring is purely internal — the HTTP endpoint, request/response models, auth, and audit are unchanged. Any existing test that exercises `refund_payment` continues to pass because `_do_refund` contains the same logic.

### 8.2 New `IN_FLIGHT` status in state machine

`IN_FLIGHT` is a new transient status. Existing code that checks `item["status"] in ("COMPLETED", "FAILED")` for terminal detection is unaffected. The TXR-002 `_LEGAL_TRANSITIONS` set is extended:

```
INITIATED → IN_FLIGHT
PENDING   → IN_FLIGHT
IN_FLIGHT → COMPLETED
IN_FLIGHT → FAILED
```

`INITIATED → COMPLETED` (direct, no-SCA) is now `INITIATED → IN_FLIGHT → COMPLETED`. For the external API, clients never poll fast enough to observe `IN_FLIGHT` in practice (it is a millisecond window), but they must not break if they do.

### 8.3 No existing table migrations

No existing DDB table schema changes. `txn_requests` receives new `failure_reason` and `ledger_refs` values on existing rows (both attributes are already declared in TXR-001's item shape as nullable/absent on create). DynamoDB's schemaless nature means rows written by TXR-001/002/003 without `ledger_refs` are simply absent on those attributes; TXR-004 writes them on the `COMPLETED` transition.

### 8.4 Flag off = no behavior change to existing endpoints

`S.txn_requests_enabled = false` (default) means the router is not registered. The refactored `_do_refund` is called unconditionally from `refund_payment` regardless of the flag — there is no gate on the refactoring. This is correct: `_do_refund` is simply a code organization change; it does not add new behavior to the existing endpoint.

## 10. Open Questions / Assumptions

1. **`IN_FLIGHT` visibility in TxnRequestOut**: Should `IN_FLIGHT` be exposed to frontend clients? It is a valid observable state during a concurrent race. **Assumption**: expose it; document it as transient in TXR-005's CLAUDE.md update. Clients polling with a `useQuery` hook (TXR-005) will see it briefly and then see `COMPLETED` on the next poll.

2. **`FREE_FORM` debit without recipient — platform accounting**: A `FREE_FORM` with no `to_user_sub` debits the sender but credits no one visible. Should the credit go to a `PLATFORM#FEES` wallet? **Assumption**: for now, no credit is issued. The ledger entry (`entry_type="debit", reason="free_form_payment"`) provides auditability. A follow-up wires the platform-fee wallet credit.

3. **`PAYOUT` via TXR vs direct `POST /creator-payouts`**: The TXR PAYOUT path delegates to `request_payout`, which creates a payout record in `T.creator_payouts`. This means a PAYOUT request appears in both the `txn_requests` table (as `COMPLETED`) and the `creator_payouts` table (as its own entity). There is a brief inconsistency window between the payout record appearing and the TXR status becoming `COMPLETED`. **Assumption**: acceptable; the TXR is the initiating record, the payout record is the settlement record.

4. **Challenge revocation timing**: `revoke_challenge` is called before the `IN_FLIGHT` claim. If the `IN_FLIGHT` claim fails (concurrent race), the challenge has already been revoked. The losing concurrent caller will find their challenge revoked and receive `401`. **Assumption**: this is the correct behavior — one of the two concurrent callers succeeds, the other must re-authenticate. This prevents two executions from both seeing `challenge_done=True`.

5. **`COUNTERPARTY` wallet debit reversal atomicity**: The current design reverses the debit with a second `apply_wallet_delta(+amount)` call before the `FAILED` transition. These two calls are not atomic (two separate `update_item`s). If the process crashes between the debit and the reversal, the sender is debited with no corresponding FAILED record. **Assumption**: acceptable for the stub implementation. A production COUNTERPARTY implementation should use `transact_write_items` for the debit+reversal or avoid debiting at all (defer the debit to when the outbound rail is wired). Document in TXR-005's CLAUDE.md note.
