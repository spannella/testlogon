# CUS-003 — Cards as a managed resource — list/create/status lifecycle + attributes

**Ticket type**: Backend — resource layer over existing `PM#` rows  
**Priority**: P2  
**Estimate**: 2.5 days  
**Flag**: `CUSTOMER_ENTITY_ENABLED` (shared with CUS-001/002; default `false`)  
**Depends on**: CUS-001 (the `CUSTOMER_ENTITY_ENABLED` flag, audit/error-envelope conventions). The card-attribute `type` literal is defined inline by this ticket (`CardAttributeSetIn.type`), not inherited from CUS-001.  
**Independent of**: CUS-002 (user-link + messages thread)

## 1. Summary & Goal

Expose **Cards** as a first-class managed resource with a four-state status lifecycle
(`ACTIVE`, `INACTIVE`, `FROZEN`, `CANCELLED`) and a typed key-value attribute store —
layered entirely over the **existing** `PM#{pm_id}` rows on the `billing` table
(`app/routers/billing.py:765`). No new card table is introduced. No PAN is ever stored
or transmitted.

The net-new behaviour is:

1. A `card_status` field (additive, defaults `ACTIVE` for pre-existing rows without it)
   and an optimistic-concurrency `card_version` field stamped onto each `PM#` row on
   the `billing` table.
2. A service `app/services/cards_resource.py` that wraps `list_payment_methods_ddb`,
   drives status transitions with a validated transition table, and guards each
   conditional update with `card_version` — mirroring `KycCaseStore.update_case_status`
   exactly.
3. A per-card attribute sub-store using sibling rows
   `pk=USER#{user_id}, sk=CARDATTR#{pm_id}#{attr_name}` on the **same** `billing` table
   (single-table design; no schema additions to `scripts/local-ddb-init.py` beyond those
   already declared for the billing table).
4. A card sub-router mounted under `/ui/cards`, all endpoints gated by
   `S.customer_entity_enabled`, owner-scoped via the existing `user_pk(user_id)` partition.

The card-as-resource delta is purely additive: the existing `add_card` / `list_payment_methods`
/ `set_default_pm` / `refund_payment` paths in `app/routers/billing.py` are **not modified**.
A `FROZEN` or `CANCELLED` card becomes ineligible for auto-selection as the default payment
method (enforced in `set_card_status`); the charge-path rejection hook is a follow-up (noted
in §10).

## 2. Context & Current State

### 2.1 Existing payment-method store (the base layer)

`app/routers/billing.py:765` defines `pm_sk(payment_method_id: str) -> str` returning
`f"PM#{payment_method_id}"`. `list_payment_methods_ddb` at line 769 queries the `billing`
table on `pk = USER#{user_id}` and returns all rows whose `sk` starts with `"PM#"`. Each
row carries exactly: `payment_method_id`, `provider`, `provider_method_id`, `method_type`,
`label`, `brand`, `last4`, `exp_month`, `exp_year`, `priority`, `created_at` (line 928-942).
The row contains **no PAN, no CVV, no full expiry date beyond month/year** — the no-PAN
invariant is already enforced.

`current_default_pm` at line 779 reads `BILLING` row's `default_payment_method_id`.
`set_default_pm` at line 784 upserts it. `list_payment_methods` at line 977 reads all `PM#`
rows and projects them into `StripePaymentMethodOut` (defined in `app/models.py`), setting
`is_default` by comparing against `current_default_pm`.

`add_card` at line 884 is the only card-creation path: it calls `stripe.PaymentMethod.create`
+ `stripe.PaymentMethod.attach`, then writes the `PM#` row, sets a default if none exists,
and fires `audit_event("billing_add_card", ...)`. This is the single Stripe-attach mechanism;
CUS-003 does not add another one.

**There are no `card_status`, `card_version`, or `CARDATTR#` fields anywhere in the
codebase today** (confirmed by grepping `billing.py`, `billing_shared.py`, and `models.py`).

### 2.2 Billing table DDB shape (single-table)

`scripts/local-ddb-init.py:67-77` declares the `billing` table with PK `pk` (S), SK `sk` (S),
and one GSI `GSI_LEDGER_DATE` on `ledger_date` (S) / `sk` (S). The `billing` table already
uses multiple SK prefixes for a single-table design: `PM#`, `PAY#`, `BILLING`, `BALANCE`,
`WALLET`, `LEDGER#`. CUS-003 adds two more SK prefixes: the additive `card_status` /
`card_version` fields written into existing `PM#` rows, and new `CARDATTR#` rows — no GSI
additions needed.

### 2.3 Optimistic concurrency pattern to copy

`KycCaseStore.update_case_status` (`app/services/kyc_cases.py:177-234`; the core
`update_item` + `ConditionalCheckFailedException` try/except is at lines 209-233) is the
canonical model: read current `version` from DDB; compare against the `expected_version`
from the caller; issue `update_item` with `ConditionExpression="version = :expected_version"`;
catch `ConditionalCheckFailedException`; raise `KycCaseConflictError`. The cards service
copies this verbatim, using `card_version` as the optimistic lock field.

## 3. Data Model

### 3.1 No new DynamoDB table

All card-resource data lives on the **existing** `billing` table
(`S.billing_table_name`, default `"billing"`), using the `user_pk(user_sub)` partition
(`"USER#{user_sub}"`). The billing table's `TableDef` in `scripts/local-ddb-init.py:67-77`
is **not modified** for CUS-003.

### 3.2 Additive fields on `PM#` rows

When a card-resource operation touches a `PM#` row, three additive fields are written
(or read with a default for rows that predate this ticket):

| Field | Type | Default | Notes |
|-------|------|---------|-------|
| `card_status` | String | `"ACTIVE"` | One of `ACTIVE`, `INACTIVE`, `FROZEN`, `CANCELLED` |
| `card_status_at` | Number (Unix ts) | `created_at` | Timestamp of last status change |
| `card_version` | Number | `1` | Optimistic-concurrency lock; incremented on every status change |

These fields are **never read by existing billing code** — `list_payment_methods_ddb`
returns the raw item dict, and `StripePaymentMethodOut` uses only the fields it was
designed for. The additive fields are transparent to all existing billing paths.

### 3.3 Card attribute rows

Typed per-card attributes are stored as sibling rows on the `billing` table:

```
PK  = USER#{user_sub}          (same partition as the PM# row)
SK  = CARDATTR#{pm_id}#{name}  (one row per attribute name per card)
```

Item shape:

| Field | Type | Notes |
|-------|------|-------|
| `pk` | S | `USER#{user_sub}` |
| `sk` | S | `CARDATTR#{pm_id}#{name}` |
| `attribute_id` | S | `uuid4().hex[:12]` — opaque id returned in the response |
| `card_id` | S | `pm_id` |
| `name` | S | Attribute name (e.g. `"spend_limit"`, `"region"`) |
| `type` | S | One of `STRING`, `INTEGER`, `DOUBLE`, `DATE_WITH_DAY` |
| `value` | S | Stored as string regardless of type |
| `created_at` | N | `now_ts()` — integer Unix seconds |
| `updated_at` | N | `now_ts()` on upsert |

Because the SK embeds both `pm_id` and `name`, `set_card_attribute` is a natural upsert
(`put_item` with the composite SK). Listing all attributes for a card is a `query` on
`pk = USER#{user_sub}` with `begins_with(sk, "CARDATTR#{pm_id}#")`.

Deleting an attribute is `delete_item(pk, "CARDATTR#{pm_id}#{name}")`.

The `CARDATTR#` prefix is distinct from `PM#`, `PAY#`, `BILLING`, `BALANCE`, `WALLET`,
and `LEDGER#` — no collision.

No new GSI is required for the attribute store; the PK-query with `begins_with` is
sufficient for listing a single card's attributes, and cross-card attribute queries are
not part of this ticket's scope.

### 3.4 Status transition table

```
ACTIVE   → INACTIVE  (owner freeze-by-disabling)
ACTIVE   → FROZEN    (operator/compliance hold)
ACTIVE   → CANCELLED (terminal)
INACTIVE → ACTIVE    (re-enable)
INACTIVE → FROZEN
INACTIVE → CANCELLED (terminal)
FROZEN   → ACTIVE    (unfreeze)
FROZEN   → INACTIVE
FROZEN   → CANCELLED (terminal)
CANCELLED → *        ILLEGAL (terminal; 422)
```

Any transition not in the above set returns `422 Unprocessable Entity` with
`{"code": "card_illegal_transition", "from": "<current>", "to": "<requested>"}`.

## 4. API / Service Design

### 4.1 Service: `app/services/cards_resource.py`

```python
from __future__ import annotations
from dataclasses import dataclass, field
from typing import Any, Dict, List, Optional

from botocore.exceptions import ClientError
from app.core.tables import T
from app.core.time import now_ts
from app.services.billing_shared import (
    user_pk, ddb_get, ddb_put, ddb_update, ddb_del, ddb_query_pk,
)
from app.routers.billing import (
    list_payment_methods_ddb, current_default_pm, set_default_pm,
)  # these helpers are defined in billing.py (not billing_shared), at lines 769, 779, 784
from app.services.alerts import audit_event

_VALID_TRANSITIONS: frozenset[tuple[str, str]] = frozenset({
    ("ACTIVE",   "INACTIVE"),
    ("ACTIVE",   "FROZEN"),
    ("ACTIVE",   "CANCELLED"),
    ("INACTIVE", "ACTIVE"),
    ("INACTIVE", "FROZEN"),
    ("INACTIVE", "CANCELLED"),
    ("FROZEN",   "ACTIVE"),
    ("FROZEN",   "INACTIVE"),
    ("FROZEN",   "CANCELLED"),
})
_NON_CHARGEABLE = frozenset({"FROZEN", "INACTIVE", "CANCELLED"})

class CardConflictError(Exception): ...
class CardIllegalTransitionError(Exception): ...
class CardNotFoundError(Exception): ...

@dataclass
class CardResourceStore:
    _table: Any = field(default_factory=lambda: T.billing)

    # ---- list / project ----

    def list_cards(self, user_id: str) -> list[dict]:
        default = current_default_pm(user_id)
        pms = list_payment_methods_ddb(user_id)
        return [self._pm_to_card(it, default) for it in pms if it.get("method_type") == "card"]

    @staticmethod
    def _pm_to_card(item: dict, default_pm_id: str | None) -> dict:
        return {
            "card_id":      item["payment_method_id"],
            "brand":        item.get("brand"),
            "last4":        item.get("last4"),
            "exp_month":    item.get("exp_month"),
            "exp_year":     item.get("exp_year"),
            "label":        item.get("label"),
            "is_default":   item.get("payment_method_id") == default_pm_id,
            "card_status":  item.get("card_status", "ACTIVE"),
            "card_version": int(item.get("card_version", 1)),
            "created_at":   item.get("created_at"),
        }

    def get_card(self, user_id: str, card_id: str) -> dict | None:
        item = ddb_get(self._table, user_pk(user_id), f"PM#{card_id}")
        if not item:
            return None
        default = current_default_pm(user_id)
        return self._pm_to_card(item, default)

    # ---- create (thin delegate over add_card) ----

    def stamp_new_card(self, user_id: str, pm_id: str, *, actor_sub: str, request=None) -> None:
        """Called by the router AFTER billing.add_card writes the PM# row.
        Adds card_status / card_version onto the newly created row.
        Does NOT call Stripe — that was already done by add_card."""
        ddb_update(
            self._table, user_pk(user_id), f"PM#{pm_id}",
            "SET card_status = :s, card_status_at = :t, card_version = :v",
            {":s": "ACTIVE", ":t": now_ts(), ":v": 1},
        )
        audit_event("card.created", actor_sub, request,
                    outcome="success", card_id=pm_id, user_id=user_id)

    # ---- status lifecycle ----

    def set_card_status(
        self,
        user_id: str,
        card_id: str,
        new_status: str,
        *,
        expected_version: int,
        actor_sub: str,
        request=None,
    ) -> dict:
        item = ddb_get(self._table, user_pk(user_id), f"PM#{card_id}")
        if not item:
            raise CardNotFoundError(card_id)

        current_status = item.get("card_status", "ACTIVE")
        current_version = int(item.get("card_version", 1))

        if current_version != int(expected_version):
            raise CardConflictError("card_update_conflict")

        transition = (current_status, new_status)
        if transition not in _VALID_TRANSITIONS:
            raise CardIllegalTransitionError(f"{current_status}->{new_status}")

        next_version = current_version + 1
        ts = now_ts()
        try:
            self._table.update_item(
                Key={"pk": user_pk(user_id), "sk": f"PM#{card_id}"},
                UpdateExpression=(
                    "SET card_status = :s, card_status_at = :t, card_version = :v"
                ),
                ConditionExpression="card_version = :ev",
                ExpressionAttributeValues={
                    ":s": new_status, ":t": ts, ":v": next_version, ":ev": current_version,
                },
            )
        except ClientError as exc:
            if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
                raise CardConflictError("card_update_conflict") from exc
            raise

        # If card is no longer chargeable and it was the default, clear default.
        if new_status in _NON_CHARGEABLE:
            if current_default_pm(user_id) == card_id:
                set_default_pm(user_id, None)

        audit_event("card.status_changed", actor_sub, request,
                    outcome="success", card_id=card_id, user_id=user_id,
                    old_status=current_status, new_status=new_status)
        return self.get_card(user_id, card_id)

    # ---- attributes ----

    def set_card_attribute(
        self,
        user_id: str,
        card_id: str,
        name: str,
        attr_type: str,
        value: str,
        *,
        actor_sub: str,
        request=None,
    ) -> dict:
        import uuid
        ts = now_ts()
        sk = f"CARDATTR#{card_id}#{name}"
        # read existing to preserve attribute_id if it already exists
        existing = ddb_get(self._table, user_pk(user_id), sk)
        attr_id = existing["attribute_id"] if existing else uuid.uuid4().hex[:12]
        ddb_put(self._table, {
            "pk": user_pk(user_id),
            "sk": sk,
            "attribute_id": attr_id,
            "card_id": card_id,
            "name": name,
            "type": attr_type,
            "value": str(value),
            "created_at": existing["created_at"] if existing else ts,
            "updated_at": ts,
        })
        audit_event("card.attribute_set", actor_sub, request,
                    outcome="success", card_id=card_id, attr_name=name)
        return {"attribute_id": attr_id, "name": name, "type": attr_type,
                "value": str(value), "created_at": existing["created_at"] if existing else ts}

    def list_card_attributes(self, user_id: str, card_id: str) -> list[dict]:
        pk = user_pk(user_id)
        resp = self._table.query(
            KeyConditionExpression="pk = :pk AND begins_with(sk, :pfx)",
            ExpressionAttributeValues={":pk": pk, ":pfx": f"CARDATTR#{card_id}#"},
        )
        return [
            {
                "attribute_id": it["attribute_id"],
                "name": it["name"],
                "type": it["type"],
                "value": it["value"],
                "created_at": it.get("created_at"),
            }
            for it in resp.get("Items", [])
        ]

    def delete_card_attribute(
        self, user_id: str, card_id: str, name: str, *, actor_sub: str, request=None
    ) -> None:
        ddb_del(self._table, user_pk(user_id), f"CARDATTR#{card_id}#{name}")
        audit_event("card.attribute_deleted", actor_sub, request,
                    outcome="success", card_id=card_id, attr_name=name)
```

### 4.3 Router: `app/routers/cards_resource.py`

Prefix `/ui/cards`. Registered in `app/main.py` alongside existing routers. Every handler
checks `S.customer_entity_enabled` and returns `HTTPException(404)` when it is `False`.
All endpoints use `Depends(require_ui_session)` (cookie + CSRF); no admin gate.

```
GET  /ui/cards
     → list_cards(user_id)
     → CardListOut

POST /ui/cards
     → calls billing.add_card semantics first (delegates to the existing endpoint;
       see §5.1), then stamps card_status via store.stamp_new_card()
     → CardOut

PATCH /ui/cards/{card_id}/status
     body: CardStatusUpdateIn
     → store.set_card_status(...)
     → CardOut
     409 on CardConflictError
     422 on CardIllegalTransitionError
     404 if card not owned by caller

PUT /ui/cards/{card_id}/attributes
    body: CardAttributeSetIn
    → store.set_card_attribute(...)
    → CardAttributeOut

GET /ui/cards/{card_id}/attributes
    → store.list_card_attributes(...)
    → list[CardAttributeOut]

DELETE /ui/cards/{card_id}/attributes/{name}
    → store.delete_card_attribute(...)
    → {"ok": True}
```

**Route ordering.** The static `/{card_id}/attributes` segment is declared before any
catch-all in the router. FastAPI matches routes in declaration order; the attributes
sub-routes must come before any `/{card_id}` param-only route to prevent the literal
`"attributes"` from being captured as a `card_id` value (same pattern as the KYC
`/schedules` route declared before `/{export_id}` — CLAUDE.md, §Scheduled audit export
reports).

**Ownership enforcement.** Every handler reads `ctx["user_sub"]` from the session and
queries only `user_pk(user_sub)` on the `billing` table. A card not found under that
partition → `404` (not `403`, to avoid enumeration). The store never receives a
`user_id` it did not derive from a valid session.

## 5. Detailed Behavior & Edge Cases

### 5.1 Card creation: thin-delegate contract

`POST /ui/cards` must not reimplement Stripe attachment. The correct sequence is:

1. The handler calls the **same internal add-card flow** that `billing.add_card` executes:
   create and attach a Stripe `PaymentMethod`, write the `PM#` row to DDB. To avoid
   duplicating that logic, the router **imports and delegates** to the `add_card` handler
   function (or its service-layer equivalent if one is extracted as part of CUS-001
   cleanup). If `add_card` is still implemented purely at the router layer when CUS-003
   ships, the card-resource `POST /ui/cards` handler calls
   `add_card(body, req, ctx, _kyc=None)` directly (passing `_kyc=None` is safe because
   `require_kyc_tier(2)` is currently inert when `kyc_tier_enforcement_enabled` is off,
   which is the default — see `app/auth/deps.py:355`) and captures the returned
   `payment_method_id`.
2. After the `PM#` row exists, `store.stamp_new_card(user_id, pm_id, ...)` is called to
   write `card_status="ACTIVE"`, `card_status_at`, and `card_version=1` onto the row.
3. The response is `CardOut` projected from the updated row.

If `add_card` raises (Stripe error, DDB error), the `stamp_new_card` call does not run
and the error propagates as-is. There is no partial-write state to clean up: the `PM#`
row is either absent or fully written by `add_card` before `stamp_new_card` touches it.

### 5.2 Status lifecycle enforcement

- `set_card_status` validates the transition before the `update_item`. An invalid
  transition (e.g. caller tries `CANCELLED → ACTIVE`) raises `CardIllegalTransitionError`
  which the router maps to `422` with body
  `{"code": "card_illegal_transition", "from": "CANCELLED", "to": "ACTIVE"}`.
- Stale `expected_version` raises `CardConflictError` → `409` with body
  `{"code": "card_update_conflict"}`.
- After a successful transition to `FROZEN`, `INACTIVE`, or `CANCELLED`, the service
  checks whether the affected card was the user's default PM (`current_default_pm` at
  `billing.py:779`). If yes, it calls `set_default_pm(user_id, None)` to clear the
  default. This prevents the charge path from auto-selecting a non-chargeable card.
  **It does not assign a new default** — that is a user action.
- `CANCELLED` is terminal. A second `PATCH` on a `CANCELLED` card always returns `422`.

### 5.3 Pre-existing `PM#` rows (no `card_status` field)

`list_cards` and `get_card` both call `item.get("card_status", "ACTIVE")`, so rows added
by `billing.add_card` before this ticket deployed are presented as `ACTIVE` with
`card_version=1`. The first `PATCH .../status` call on such a row will fail the optimistic
check if the caller submits `expected_version != 1` — but the default is 1, so any client
that reads the card first and echoes `card_version` back will work correctly. An explicit
migration is not needed.

### 5.4 `card_version` initialisation on `stamp_new_card`

`stamp_new_card` writes `card_version = 1` unconditionally. If for any reason (race,
retry) it is called twice on the same `PM#` row, the second call is idempotent: it sets
`card_version = 1` and `card_status = "ACTIVE"` again. Because `card_version = 1` is
the invariant for a freshly-created card, this is safe — the write is idempotent at the
cost of resetting `card_status_at`, which is acceptable for the creation edge case.

### 5.5 Attribute uniqueness and overwrite

The attribute SK is `CARDATTR#{pm_id}#{name}`. Setting an attribute with an existing
`name` is an upsert (`put_item` without `attribute_not_exists`). The `attribute_id` is
preserved from the existing row so responses remain stable across upserts. The `created_at`
is also preserved; only `updated_at` and `value` change.

There is no maximum attribute count enforced in this ticket; a follow-up can add a
`count(begins_with)` guard if needed.

### 5.6 Ownership check on `set_card_status`

The store queries `ddb_get(T.billing, user_pk(user_id), f"PM#{card_id}")`. If the row
is absent — whether because the card does not exist or because it belongs to a different
user — the result is `None`, and the handler returns `404`. The owner partition
`USER#{user_sub}` is derived from the authenticated session, not from any caller-supplied
field.

### 5.7 `CARDATTR#` rows survive card deletion

If a `PM#` row is deleted via the existing `billing.py` delete endpoint, the `CARDATTR#`
sibling rows remain (orphaned). This is acceptable for the CUS-003 scope; a cleanup
utility is noted as an open question in §10.

### 5.8 `method_type` filtering in `list_cards`

`list_payment_methods_ddb` returns all `PM#` rows including `us_bank_account` rows (added
by `create_us_bank_setup_intent` at `billing.py:871`). `list_cards` filters to
`item.get("method_type") == "card"` so bank accounts are excluded. Non-card PM types do
not participate in the status lifecycle.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 dev/prod parity

There are **no `if S.dev_mode` branches** in `cards_resource.py`. The service reads and
writes DynamoDB via `T.billing`, which resolves to DynamoDB Local in dev (port 8001, from
`DDB_ENDPOINT_URL`) and real DynamoDB in prod. The `_FloatSafeTable` proxy at
`app/core/tables.py:29-66` handles both environments identically. Stripe operations
(already in `add_card`) use the stripe-mock at port 12111 in dev and real Stripe in prod —
CUS-003 does not add any new Stripe calls.

### 7.2 Idempotency

- `stamp_new_card`: idempotent (see §5.4).
- `set_card_status`: the `card_version` guard makes it idempotent for a fixed
  `(status, version)` pair — a retry with the same payload that succeeded yields `409`
  (version was bumped), not a double-write.
- `set_card_attribute`: idempotent by SK; repeated calls with the same `(name, value)`
  update `updated_at` but are otherwise no-ops from the caller's perspective.

### 7.3 No-PAN invariant

The cards service never reads, writes, transmits, or logs a PAN, CVV, or full card number.
`list_cards` and `get_card` project only `brand`, `last4`, `exp_month`, `exp_year`, plus
the additive `card_status` / `card_version` fields. The underlying `PM#` row in DynamoDB
also contains no PAN (enforced by `billing.add_card`, which stores only what Stripe
returns in `pm.get("card", {})`). No change to this invariant is introduced.

### 7.4 Money-safety

CUS-003 introduces no money movement. The ledger primitives
`new_ledger_entry` (line 224) and `settle_or_reverse_ledger` (line 262) from
`app/services/billing_shared.py`, plus `apply_wallet_delta` (line 185 of the same file),
are not called in this ticket.

However, the status lifecycle has one money-adjacent side effect: clearing the default
payment method when a card becomes non-chargeable (`§5.2`). This uses the existing
`set_default_pm(user_id, None)` at `billing.py:784` — a single `update_item` on the
`BILLING` row. It does not cancel outstanding charges, reject pending PaymentIntents, or
modify the Stripe customer object. Those follow-up hooks are noted in §10 and are the
responsibility of the charge-path integration (TXN-REQUEST tickets).

### 7.5 CSRF

Cookie-auth non-GET requests require `x-csrf-token` header matching the session's stored
`csrf_token` and the `ui_csrf` cookie. This is already enforced by `require_ui_session`
(the same dep used by `billing.py`) and requires no additional implementation in
`cards_resource.py`.

### 7.6 Rate limiting

No new per-endpoint rate limits are introduced in this ticket. The `rate_limit.py`
`_bucket_limit` primitive is available for a follow-up if card status changes need
per-user throttling.

All changes are additive:

`CUSTOMER_ENTITY_ENABLED=false` (the default) on the running app is sufficient to make
all `/ui/cards*` routes return 404 without dropping the table or schema-migrating rows.

## 10. Open Questions / Assumptions

1. **Charge-path rejection hook.** CUS-003 clears the default PM when a card is frozen,
   but it does not reject charges attempted directly against a `FROZEN` or `CANCELLED`
   card `pm_id`. The integration point is in `billing.py`'s `pay_balance` / `charge_once`
   handlers: before the Stripe charge, check `ddb_get(T.billing, user_pk(user_id), pm_sk(pm_id)).get("card_status", "ACTIVE")` and raise `422` if it is in `_NON_CHARGEABLE`.
   This is a follow-up — noted but out of scope for CUS-003.

2. **Admin read/patch of other users' cards.** The current spec is owner-only.
   Admin-impersonation paths (read a specific user's cards as admin) are deferred to
   CUS-005 which will extend the router with a dual-auth pattern mirroring
   `billing.py`'s `_billing_write_user_context` / `_billing_read_user_sub` admin helpers.

3. **`CARDATTR#` orphan cleanup on PM deletion.** When a `PM#` row is deleted via the
   existing billing endpoint (`DELETE /ui/billing/payment-methods/{id}`), the `CARDATTR#`
   sibling rows remain. A cleanup utility (query `begins_with(sk, "CARDATTR#{pm_id}#")` +
   batch-delete) should run in the delete handler. Out of scope for this ticket.

4. **Attribute count cap.** No maximum number of attributes per card is enforced. If
   required (e.g. for billing-table size management), a pre-write count query with a
   configurable `S.card_attribute_max_count` setting can be added.

5. **`stamp_new_card` vs. inline in `add_card`.** The current spec calls `stamp_new_card`
   from the card-resource router *after* the `add_card` call. An alternative is to inline
   the stamp into `add_card` itself (guarded by `if S.customer_entity_enabled`). The
   inline approach has one code path but violates the "no if S.dev_mode/feature_flag
   branches in existing flows" principle. The delegate approach is preferred.

6. **`CardOut.card_version` client contract.** Clients must echo the `card_version` they
   received back in the `PATCH` body. If a card was created before CUS-003 deployed (no
   `card_version` field in DDB), the client will receive `card_version=1` from `list_cards`
   and must send `expected_version=1` in the `PATCH`. This is the intended UX and matches
   how KYC cases present `version=1` on first creation.
