# PLT-001 — Per-consumer rate-limit middleware — configurable minute/hour/day/week/month windows on all metered routes

**Type:** Feature | **Priority:** P1 | **Estimate:** 3d  
**Flag:** `API_CONSUMER_RATE_LIMIT_ENABLED` (default **off**)  
**Branch prefix:** `feature/plt-001-api-consumer-rate-limit`

---

## 1. Summary & Goal

OBP's rate-limiter specification requires that every API consumer (identified by their API key) is subject to configurable windowed call budgets across five time horizons: minute, hour, day, week, and month. Today, testlogon's DDB-backed bucket limiter (`app/services/rate_limit.py:60 _bucket_limit`) is wired to specific flows only — MFA sends, share-link password attempts, file-mount onboarding, and (the closest analogue) the KYC Partner API (`rate_limit.py:385 rate_limit_kyc_partner_api`). There is no uniform per-consumer throttle applied across all metered API routes.

This ticket generalises the KYC-partner pattern into a single pre-request middleware that intercepts every request carrying an API key, checks all configured windows in sequence, and returns HTTP 429 with a `Retry-After` header on any breach. Cookie/session (UI) traffic that carries no API key is never affected. The feature is entirely additive and flag-gated: with `API_CONSUMER_RATE_LIMIT_ENABLED=0` the middleware is a no-op and the platform is byte-for-byte unchanged.

## 2. Context & Current State

### Existing primitives (all reused, nothing forked)

**`_bucket_limit` (app/services/rate_limit.py:60)**  
Fixed-window DDB counter keyed on `(user_sub, session_id)`. Reads the current bucket item from `T.sessions`, resets the window when `(now - bucket_start) >= win`, atomically increments, writes back with a TTL of `now + win + 3600`. Returns `True` (allowed) or `False` (denied). Used today by MFA, share-link, file-mount, and KYC-partner flows. The `user_sub` parameter is a logical identity key, not literally a user sub — `rate_limit_kyc_partner_api` (line 411) already passes `f"apikey:{api_key_id}"` as the first argument, demonstrating the convention.

**`rate_limit_kyc_partner_api` (app/services/rate_limit.py:385)**  
The closest existing analogue. Implements per-key hourly caps across four KYC categories by calling `_bucket_limit(key=f"apikey:{api_key_id}", sid=f"rl#kyc_api#{category}", cap, win=3600)`. Raises `HTTPException(429, detail={code, message, category, limit, window_seconds})` with `Retry-After` header on denial. The new `rate_limit_api_consumer` function is structurally identical but operates across five window widths simultaneously.

**`_extract_api_key_id` (app/services/api_usage_metering.py:119)**  
Resolves the API key ID from `X-Api-Key`, `X-Api_Key`, or `Authorization: APIKey <token>` headers. Returns `""` when no key is present — the middleware uses this to identify requests that should be throttled (non-empty) vs. skipped (empty, i.e., cookie/session auth).

**`route_id_from_request` (app/services/api_metering_contract.py:90)**  
Returns a stable `METHOD:/path/with/{param_placeholders}` route identifier. Already called in `_api_usage_metering_middleware` (app/main.py:333) which runs after the new middleware.

**`_api_usage_metering_middleware` (app/main.py:333)**  
Calls `enforce_api_package_entitlement_pre_request` + `enforce_account_quota_pre_request` before delegating to the handler, then records the result via `record_api_usage_from_response`. A 429 from the new consumer rate-limit middleware is returned before `call_next` is reached and is itself recorded as a denied call via `classify_api_call(..., is_rate_limited=status==429)` at line 163 of `api_usage_metering.py`.

**`get_api_key_item` (app/services/api_keys.py:344)**  
Fetches the full API key DDB item from `T.api_keys`. The item already carries `monthly_calls_cap`, `monthly_spend_cap_micros`, and `route_caps`. The new `rate_limit_overrides` field (per-window caps) will be stored on this same item via an extension to `set_api_key_self_limits` (api_keys.py:285).

**`set_api_key_self_limits` (app/services/api_keys.py:285)**  
Currently persists `monthly_calls_cap`, `monthly_spend_cap_micros`, and `route_caps` with guardrail enforcement against `api_usage_account_monthly_calls_limit`. A new optional `rate_limit_overrides` dict is added to this function's update expression.

**`T.sessions` (app/core/tables.py:322)**  
The sessions DynamoDB table (PK `user_sub`, SK `session_id`) reused by all `_bucket_limit` callers. No schema change is needed — the new middleware writes bucket rows with `user_sub=f"apikey:{api_key_id}"` and `session_id=f"rl#api#{window}"`, the same pattern as `rate_limit_kyc_partner_api`.

**`build_limit_denial_headers` (app/services/api_metering_policy.py:118)**  
Constructs `x-api-limit-*` response headers; `Retry-After` is only included when a `reset_at` epoch is present in the detail dict. Note: the new 429 response from the consumer rate-limit middleware constructs its headers directly (`Retry-After: {window_seconds}`, `x-api-limit-code: api_consumer_rate_limited`) rather than calling this function, because `build_limit_denial_headers` requires a `reset_at` field that the per-window bucket detail does not supply.

**`API_KEY_ROUTE_EXEMPTIONS` (app/services/api_key_route_scope_registry.py:70)**  
A dict of `route_id → {reason}` for routes that must never be throttled (health probe, metrics, OpenAPI schema, public calendar endpoints, etc.). The middleware checks this set before calling the rate limiter — any route present in `API_KEY_ROUTE_EXEMPTIONS` is passed through without consuming budget.

**Middleware registration order (app/main.py:540-543)**  
```
app.middleware("http")(_crawler_meta_middleware())           # crawler/meta (registered 1st = innermost)
app.middleware("http")(rate_limit_middleware_factory())      # layer 1 IP
app.middleware("http")(_api_usage_metering_middleware())     # metering + quota
app.middleware("http")(_playback_entitlement_middleware())   # (registered last = outermost, runs first)
```
FastAPI/Starlette middleware uses LIFO stack order: the **last-registered** middleware is the **outermost** layer and runs **first** for incoming requests. The new `_api_consumer_rate_limit_middleware` must be registered **before** `_api_usage_metering_middleware()` in the source file (i.e., between `rate_limit_middleware_factory()` and `_api_usage_metering_middleware()`), so that metering (registered later = outermost relative to consumer_rl) wraps the consumer limiter and sees its 429 responses — recording them as denied metered calls.

## 3. Data Model

### No new DynamoDB tables

All per-consumer bucket state is written into the **existing `sessions` table** (PK `user_sub`, SK `session_id`) — the same table used by every `_bucket_limit` call site. The composite key encoding ensures no collision with real session rows or other rate-limit rows:

| Attribute | Value |
|---|---|
| `user_sub` | `apikey:{api_key_id}` |
| `session_id` | `rl#api#{window_name}` where `window_name` ∈ {`minute`, `hour`, `day`, `week`, `month`} |
| `bucket_start` | Unix timestamp (int) when the current window opened |
| `bucket_count` | Number of requests in the current window (int) |
| `ttl_epoch` | `bucket_start + window_seconds + 3600` (DynamoDB TTL cleanup) |

This is identical to how `rate_limit_kyc_partner_api` writes `(f"apikey:{api_key_id}", f"rl#kyc_api#{category}", ...)`. Up to five rows per API key are live at any time; rows auto-expire when the TTL passes.

### Extension to the `api_keys` table

`set_api_key_self_limits` gains an optional `rate_limit_overrides` parameter. This is stored as a DynamoDB map attribute on the existing `api_keys` table item (`key_id` PK):

```
rate_limit_overrides: {
    "minute":  <int | null>,
    "hour":    <int | null>,
    "day":     <int | null>,
    "week":    <int | null>,
    "month":   <int | null>
}
```

A `null` / absent entry means "use the account default for this window." An explicit `0` means "disable this window for this key." No new GSI is required — this attribute is read via `get_api_key_item` which already fetches the full item.

### `scripts/local-ddb-init.py`

No new `TableDef` entry is needed. The `sessions` table already exists. The `api_keys` table schema (PK `key_id`, GSI `user_sub-index`) already exists. The `rate_limit_overrides` map attribute requires no schema declaration (DynamoDB single-table, schemaless attributes).

## 4. API / Service Design

### 4.1 New service function: `rate_limit_api_consumer`

**File:** `app/services/rate_limit.py` (after `rate_limit_kyc_partner_api` at line 385)

```python
def rate_limit_api_consumer(api_key_id: str, route_id: str) -> None:
    """
    Per-consumer windowed rate limiter for all metered API routes (PLT-001).

    Checks five fixed windows in order from narrowest to widest. Raises
    HTTPException(429) at the first window that is exhausted. Uses the same
    DDB-backed _bucket_limit primitive as rate_limit_kyc_partner_api.

    Args:
        api_key_id: resolved key ID (non-empty; caller guards empty case)
        route_id:   METHOD:/path/with/{placeholders} from route_id_from_request
    """
```

**Window definitions** (all checked in sequence; first breach raises):

| Window name | `win` (seconds) | Default cap env var |
|---|---|---|
| `minute` | 60 | `API_CONSUMER_RATE_LIMIT_MINUTE` |
| `hour` | 3600 | `API_CONSUMER_RATE_LIMIT_HOUR` |
| `day` | 86400 | `API_CONSUMER_RATE_LIMIT_DAY` |
| `week` | 604800 | `API_CONSUMER_RATE_LIMIT_WEEK` |
| `month` | 2592000 | `API_CONSUMER_RATE_LIMIT_MONTH` |

**Per-key override resolution:**
1. Call `get_api_key_item(api_key_id)` — if the key is revoked or not found, skip throttling (fail-open; auth middleware will reject the request independently).
2. For each window, use `item.get("rate_limit_overrides", {}).get(window_name)` if non-None; otherwise use the account-wide `S.api_consumer_rate_limit_{window_name}` default.
3. A resolved cap of `0` skips `_bucket_limit` for that window entirely.

**429 response shape** (identical to `rate_limit_kyc_partner_api`):
```json
{
  "detail": {
    "code": "api_consumer_rate_limited",
    "message": "API rate limit exceeded for this key",
    "window": "minute",
    "limit": 60,
    "window_seconds": 60
  }
}
```
Headers: `Retry-After: {window_seconds}` and `x-api-limit-code: api_consumer_rate_limited`.

### 4.2 New middleware factory: `_api_consumer_rate_limit_middleware`

**File:** `app/main.py` (new function, registered between `rate_limit_middleware_factory()` and `_api_usage_metering_middleware()`)

```python
def _api_consumer_rate_limit_middleware():
    async def _middleware(request: Request, call_next):
        if not getattr(S, "api_consumer_rate_limit_enabled", False):
            return await call_next(request)
        api_key_id = _extract_api_key_id(request)
        if not api_key_id:
            return await call_next(request)
        route_id = route_id_from_request(request)
        if not route_id:
            return await call_next(request)
        if get_route_exemption(route_id) is not None:
            return await call_next(request)
        try:
            rate_limit_api_consumer(api_key_id, route_id)
        except HTTPException as exc:
            detail = exc.detail if isinstance(exc.detail, dict) else {"code": "api_consumer_rate_limited"}
            win_secs = detail.get("window_seconds", 60)
            headers = {"Retry-After": str(win_secs), "x-api-limit-code": str(detail.get("code", ""))}
            return JSONResponse(status_code=429, content={"detail": detail}, headers=headers)
        return await call_next(request)
    return _middleware
```

`get_route_exemption` is already available via `app/services/api_key_route_scope_registry.py:294`.

## 5. Detailed Behavior & Edge Cases

**Window independence.** Each window is enforced by an independent `_bucket_limit` call. Exhausting the minute window does not consume day/week/month budget beyond the single call that triggered the denial.

**Narrowest-first ordering.** Windows are checked minute → hour → day → week → month. The first breach raises immediately; later windows are not checked for that request. The `Retry-After` header reflects the breached window's duration.

**Zero-cap = disabled.** A configured cap of `0` (either default or override) skips `_bucket_limit` for that window. This means an operator can enable the feature flag but disable individual windows selectively.

**Per-key `get_api_key_item` cost.** One DDB `GetItem` per request (the API key item). This is the same read that `enforce_account_quota_pre_request` and `enforce_api_package_entitlement_pre_request` already perform independently. A future optimization may deduplicate via `request.state`; for now the read is accepted as the straightforward extension of the KYC-partner model, which does the same.

**Cookie/session UI requests.** `_extract_api_key_id` returns `""` for requests authenticated only via `ui_session` cookie (no `X-Api-Key` or `Authorization: APIKey` header). The middleware short-circuits immediately. Admin UI traffic is never throttled.

**Exempted routes.** Routes in `API_KEY_ROUTE_EXEMPTIONS` (app/services/api_key_route_scope_registry.py:70) — health probe, metrics, OpenAPI schema, public newsfeed feed-for-you, and other session-auth-only routes — are skipped without consuming budget. This mirrors the entitlement middleware's skip logic.

**Revoked / unknown API keys.** `get_api_key_item` returns `{}` only when the DDB item does not exist (key not found). A **revoked** key still has a DDB item and returns a non-empty dict with `revoked: True`. The implementation of `rate_limit_api_consumer` must therefore check both `if not item` (missing) **and** `if item.get("revoked", False)` (revoked) and skip throttling in either case — auth middleware will independently reject the request with 401/403.

**Retry-After accuracy.** `_bucket_limit` uses `bucket_start + win` as the reset time. The `Retry-After` header is set to `win` (the window in seconds) which is a safe upper bound. A more precise value would require reading `bucket_start` from the DDB item, which would require a second read; the conservative upper bound matches the existing KYC-partner implementation.

**Concurrent requests at window boundary.** `_bucket_limit` uses `put_item` (last-writer-wins), not a DDB atomic increment. Under high concurrency at window edges, a small number of requests may slip through above the cap. This is acceptable for a soft-rate-limit; the existing platform uses the same primitive for all its limiters without a consistency guarantee.

**429 is itself metered.** The consumer rate-limit middleware is registered **before** `_api_usage_metering_middleware` in the source file. Due to Starlette's LIFO stack, metering (registered later = outermost) wraps consumer_rl (registered earlier = inner). A 429 from consumer_rl is returned via `call_next` in the metering middleware, which then calls `record_api_usage_from_response(request, 429)`. `classify_api_call(429, is_rate_limited=True)` at `api_usage_metering.py:161` records the denial in the usage aggregate. This means denied calls appear in the consumer's usage statistics — matching OBP's behaviour.

**Override guardrail ceiling.** When `set_api_key_self_limits` is called with `rate_limit_overrides`, any per-window value that exceeds the configured account ceiling (`S.api_consumer_rate_limit_{window}`) is rejected with HTTP 400. A zero ceiling (window disabled) imposes no restriction. This mirrors the existing `monthly_calls_cap` guardrail at `api_keys.py:271` (the per-key top-level check; per-route checks start at line 279).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

**SECOPS-007.** The middleware reads from and writes to `T.sessions` (DynamoDB Local port 8001 in dev, real DynamoDB in prod). `_bucket_limit` has no `dev_mode` branch today and the new code adds none. Same code path, same DDB table, both environments. The only env-sensitive behaviour is the flag default (`0`/off).

**No `dev_mode` guard in the service function.** `rate_limit_api_consumer` in `rate_limit.py` contains no `if S.dev_mode` branch. Operators explicitly set `API_CONSUMER_RATE_LIMIT_ENABLED=1` and non-zero caps to observe throttling in dev.

**Idempotency.** `_bucket_limit` is last-writer-wins `put_item`. A repeated call within the same window increments the count but does not double-count a denial — once `count >= max_n` the function returns `False` without writing. A 429 response causes the usage-metering middleware to record one denied event (idempotent via the `idempotency_key` from `request_id + attempt`).

**Money-safety.** PLT-001 is a read-path gate — it never initiates a money movement. No ledger entries are written. No wallet deltas occur. The 429 response is returned before the route handler is invoked, so no payment is started. This ticket has no intersection with `new_ledger_entry`, `apply_wallet_delta`, or `settle_or_reverse_ledger`.

**Security.** The `api_key_id` resolved by `_extract_api_key_id` is the parsed `key_id` field from the structured API key token, not a raw user-supplied string — it is extracted via `parse_api_key` (api_keys.py:21) which validates the `ak_{key_id}.{secret}` format. The DDB key written is `f"apikey:{api_key_id}"` where `api_key_id` is a short opaque identifier, not a secret. No secret material touches the `sessions` table.

## 8. Backward Compatibility & Migration

**Additive-only.** With `API_CONSUMER_RATE_LIMIT_ENABLED=0` (the shipped default), the middleware is a registered no-op. Existing consumers see no change in behaviour, response headers, or error codes.

**`set_api_key_self_limits` extension.** The new `rate_limit_overrides` parameter is `Optional` with a default of `None`. Callers that do not pass it receive the existing behaviour. Existing DDB items without a `rate_limit_overrides` attribute are read as `{}` (no overrides), which correctly falls back to account defaults.

**`list_api_keys` response.** The `rate_limit_overrides` field is added to the list-item shape defaulting to `{}`. Clients that do not know about PLT-001 ignore the unknown field; clients that do may display per-key override info. No breaking change.

**No DynamoDB table migration.** The `sessions` table and `api_keys` table already exist and use schemaless attributes. No `UpdateTable` or backfill is required. The new `rate_limit_overrides` map attribute on `api_keys` items is written only on first call to the updated `set_api_key_self_limits`; items without it behave as if overrides are absent.

**Middleware ordering change.** One new `app.middleware("http")(...)` call is inserted in `create_app` (app/main.py:540-543). FastAPI/Starlette middleware is **last-registered-first-run** (LIFO stack): the last `app.middleware("http")(...)` call in the source is the outermost layer and executes first on every incoming request. The new consumer limiter must be registered **before** `_api_usage_metering_middleware` in the source file — i.e., between `rate_limit_middleware_factory()` and `_api_usage_metering_middleware()` — so that metering (registered after = outermost relative to consumer_rl) wraps the consumer limiter and records its 429 responses:

```python
app.middleware("http")(_crawler_meta_middleware())              # registered 1st = innermost
app.middleware("http")(rate_limit_middleware_factory())         # layer 1 IP
app.middleware("http")(_api_consumer_rate_limit_middleware())   # PLT-001 NEW (between rate_limit and metering)
app.middleware("http")(_api_usage_metering_middleware())        # metering + quota (outer to consumer_rl)
app.middleware("http")(_playback_entitlement_middleware())      # registered last = outermost, runs first
```

Request pipeline execution order: `playback_entitlement` → `api_usage_metering` → `consumer_rl` → `rate_limit` → `crawler` → handler.

## 9. Test Plan

### 9.1 Hermetic unit test: `tests/test_plt_001_api_consumer_rate_limit.py`

**Setup pattern** (matching existing offline tests such as `tests/test_gap_0286_0287_kyc_partner_api.py`):
- Start a moto in-memory DynamoDB; create the `sessions` table (PK `user_sub`, SK `session_id`) manually via `boto3`.
- Bind the in-memory table resource to `T.sessions` via `object.__setattr__(T, "sessions", moto_table)`.
- Set `S.api_consumer_rate_limit_enabled = True` via `object.__setattr__(S, "api_consumer_rate_limit_enabled", True)`.
- Patch `now_ts` at `app.services.rate_limit.now_ts` to a controllable integer.
- Call `rate_limit_api_consumer(api_key_id, route_id)` directly — no HTTP server, no TestClient.
- Restore `T.sessions` and `S` fields in a `finally` block.

**Test cases:**

1. **Flag off — no-op.** Set `api_consumer_rate_limit_enabled=False`. Call `rate_limit_api_consumer` 1000 times. Assert no DDB writes and no exception.

2. **Single window allow→deny.** Configure `api_consumer_rate_limit_hour=5`. Call 5 times with the same `api_key_id`. Assert all succeed. Call a 6th time. Assert `HTTPException(429)` with `detail.code == "api_consumer_rate_limited"` and `detail.window == "hour"`.

3. **Window reset.** After denial in the hourly window, advance `now_ts` by 3601 seconds. Assert the next call succeeds (bucket reset).

4. **Narrowest-window-first breach.** Configure `api_consumer_rate_limit_minute=2, api_consumer_rate_limit_hour=1000`. Send 2 allowed calls, then a 3rd. Assert `detail.window == "minute"` (not `hour`).

5. **Zero-cap skips window.** Configure `api_consumer_rate_limit_minute=0, api_consumer_rate_limit_hour=3`. Send 3 calls. All succeed (minute window is skipped). 4th call triggers hour denial.

6. **Per-key override supersedes account default.** Configure account default `api_consumer_rate_limit_hour=10`. Patch `get_api_key_item` to return `{"rate_limit_overrides": {"hour": 2}}`. Send 2 calls. Assert 3rd is denied. With `rate_limit_overrides={"hour": null}`, fallback to default cap of 10.

7. **Override guardrail.** With `api_consumer_rate_limit_hour=100`, attempt `set_api_key_self_limits(..., rate_limit_overrides={"hour": 200})`. Assert HTTP 400.

8. **Separate API keys have separate budgets.** Configure `api_consumer_rate_limit_minute=1`. Allow `key_A`, deny `key_A` on second call. Assert `key_B` is still allowed.

9. **Exempted route skips limiter.** Configure minute cap=1. Call `rate_limit_api_consumer` for a route that appears in `API_KEY_ROUTE_EXEMPTIONS`. ## 10. Open Questions / Assumptions

1. **`_bucket_limit` last-writer-wins race.** The existing primitive uses `put_item` rather than `update_item` with an atomic ADD, so concurrent requests at the window boundary can slightly exceed the configured cap. This is acceptable for a soft limiter (same behaviour as KYC-partner). If the product requires hard limits, a follow-up can replace the put with a conditional `ADD` expression on `bucket_count`.

2. **`get_api_key_item` call on every request.** Each metered request incurs one extra DDB read to resolve per-key overrides. For deployments with no per-key overrides, this is wasteful. An optimisation is to cache the override map in `request.state` keyed on `api_key_id`, but that is out of scope for PLT-001. Alternatively, callers that have no `rate_limit_overrides` on the item can skip the read by checking a sentinel field. Deferred.

3. **Week-window semantics.** A 604800-second (7-day) fixed window is not calendar-aligned. An operator expecting a "calls per calendar week" semantics will observe rolling windows instead. This matches OBP's bucket approach and is noted as an assumption.

4. **`Retry-After` precision.** The header is set to `window_seconds` (upper bound) rather than `bucket_start + win - now`. This is consistent with `rate_limit_kyc_partner_api`. A later ticket can improve precision by exposing `bucket_start` from `_bucket_limit`.

5. **Admin override ceiling of 0.** A ceiling of `0` means "no ceiling" (window disabled). An operator cannot use a ceiling of `0` to express "per-key overrides are not allowed for this window." This is consistent with existing `_enforce_self_limit_guardrails` behaviour at `api_keys.py:279`.
