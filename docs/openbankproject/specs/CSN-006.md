## 1. Summary & Goal

CSN-006 delivers the complete hermetic, offline regression test suite for the five feature tickets CSN-001 through CSN-005. It owns four pytest modules and (optionally) two Playwright specs that, together, assert every acceptance criterion from the upstream tickets — covering the AIS consent lifecycle, the SCA gate, the PIS consent + money-safety invariant, the consent-scoped rate limit, dynamic entity CRUD, dynamic endpoint dispatch, and the open-data public read surface.

The primary goal is that these tests pass without any real AWS, network, or browser session: they use moto in-memory DynamoDB tables bound to the frozen `T.*` handles, a frozen `S` with feature flags toggled via `object.__setattr__`, and async route handlers driven on a fresh `asyncio.new_event_loop()`. MFA collaborators run against the moto `T.sessions` table or are patched at source. No `TestClient` is used (known broken for this codebase's async handler + middleware stack — see `tests/test_gap_0286_0287_kyc_partner_api.py:52-56`).

A secondary, optional goal is end-to-end Playwright coverage that drives the consent lifecycle and the public open-data `GET` against the live local stack with all four CSN feature flags turned on.

## 3. Data Model

CSN-006 introduces **no new DynamoDB tables**. The four test modules create moto in-memory versions of the tables introduced by their upstream tickets and bind them to the frozen `T.*` handles. The relevant table shapes are:

### 3.1 Tables under test (moto-backed in CSN-006)

| Table | Upstream | PK (S) | SK (S) | GSIs requiring `attr_types` |
|---|---|---|---|---|
| `consents` | CSN-001 | `owner_sub` | `consent_id` (`csn_*`) | `ByConsumer` (pk=`consumer_ref`, sk=`created_at` **N**); `ByStatusExpiry` (pk=`status`, sk=`valid_until` **N**) |
| `dynamic_entity_defs` | CSN-003 | `entity_name` | `sk="DEF"` | `ByCreatedAt` (pk=`created_by`, sk=`created_at` **N**) — requires `attr_types={"created_at": "N"}` |
| `dynamic_entity_rows` | CSN-003 | `entity_name` | `row_id` (`dyn_*`) | `ByOwner` (pk=`owner_sub`, sk=`created_at` **N**) |
| `dynamic_endpoints` | CSN-004 | `endpoint_id` (`dye_*`) | `sk="DEF"` | `ByMethodPath` (pk=`method_path`, sk=`sk` **S** — no numeric attr needed); `ByCreatedAt` (pk=`created_by`, sk=`created_at` **N** — requires `attr_types={"created_at": "N"}`) |
| `open_data` | CSN-005 | `kind` (`BRANCH`/`ATM`) | `resource_id` (`brn_*`/`atm_*`) | `ByActive` (pk=`kind_active` **S** compound key e.g. `"BRANCH#1"`, sk=`name` **S** — no numeric attr needed) |

Numeric GSI sort keys marked **N** must be declared with `attr_types` in the `TableDef` call in `scripts/local-ddb-init.py` — the repo's documented #1 gotcha (`scripts/local-ddb-init.py:52-53`). Moto enforces this identically to real DynamoDB: writing an integer to a key declared as `S` (the default) results in a `ValidationException` at query time.

The `T.sessions` table (PK `user_sub`, SK `session_id`) is also used for the SCA challenge tests and for `_bucket_limit` rate-limit counters. That table already exists. Tests bind a fresh moto version of it alongside the CSN tables.

### 4.2 Helper / fixture signatures

Each module defines a self-contained `unittest.TestCase` subclass (mirroring `tests/test_gap_0286_0287_kyc_partner_api.py`). Shared helpers extracted as module-level functions:

```python
def _patch_frozen(tc, obj, attr, value):
    """Swap obj.attr to value, register addCleanup to restore original."""
    original = getattr(obj, attr)
    object.__setattr__(obj, attr, value)
    tc.addCleanup(lambda: object.__setattr__(obj, attr, original))

def _run(coro):
    """Drive an async coroutine on a fresh event loop."""
    loop = asyncio.new_event_loop()
    try:
        return loop.run_until_complete(coro)
    finally:
        loop.close()

def _fake_session_ctx(user_sub: str, role=Role.USER) -> dict:
    """Minimal session dict as returned by require_ui_session."""
    return {"user_sub": user_sub, "role": role, "admin_profile": None}

def _fake_root_ctx(admin_sub: str) -> dict:
    """Minimal session dict as returned by require_root_session."""
    return {"user_sub": admin_sub, "role": Role.ROOT, "admin_profile": None}
```

`_run` matches the pattern in `tests/test_gap_0286_0287_kyc_partner_api.py:50-56` and `tests/test_gap_0220_0221_ssh_stored_key.py:316-321`. (Note: `tests/test_gap_0241_0242_google_drive_oauth.py` uses `asyncio.run()` directly rather than a named `_run` helper — both patterns are equivalent; the named helper is preferred here for clarity.) Each async route handler is called directly — `await handler(request, ...)` — not via `TestClient`. Request objects are constructed as `Request({"type": "http", "method": "POST", "headers": []})` or via `unittest.mock.MagicMock(spec=Request)` for handlers that only read the IP/user-agent.

## 5. Detailed Behavior & Edge Cases

### 5.1 `tests/test_csn_001_002_psd2_consents.py`

**Class `ConsentModelTests`** — moto tables: `consents`, `sessions`.

#### CSN-001 lifecycle

1. **create → INITIATED**: Call `psd2_consents.create_consent(owner_sub, body, req)` with valid `account_refs` and `view_refs=["owner"]`. Assert the returned `ConsentOut.status == "INITIATED"` and that a `consents` DDB item exists with `status="INITIATED"`, `consent_id` matching `csn_*`, `valid_from` set.

2. **`account_refs` empty → 400**: Call `create_consent` with `account_refs=[]`. Assert `HTTPException(status_code=400)` is raised. The upstream implementation (CSN-001) raises with a plain string `detail="account_refs must not be empty"` (not a dict `code` field); assert `"account_refs" in str(exc.detail)`.

3. **`view_refs` outside static set → 400**: Call with `view_refs=["nonexistent_view"]`. Assert `HTTPException(status_code=400)`. The upstream implementation (CSN-001) raises with `detail="invalid view_ref: nonexistent_view"` (a plain string); assert `"invalid view_ref" in str(exc.detail)`.

4. **`valid_until` capping**: Call with `valid_until` beyond `S.psd2_consent_max_ttl_days * 86400 + now_ts()`. Assert the persisted `valid_until` is clamped to `now_ts() + S.psd2_consent_max_ttl_days * 86400` and no exception is raised. CSN-001 spec (§4.5, line 207 and §5.4 line 385) explicitly chose silent clamping over a `400`; this open question is resolved — the test must assert the clamp path only.

5. **`ByConsumer` list is consumer-scoped**: Create two consents for `consumer_A` and one for `consumer_B`. Call `list_consents_for_consumer("consumer_A")`. Assert only the two `consumer_A` rows are returned, never the `consumer_B` row.

6. **`?status=` filter**: Create one `INITIATED` and one `REVOKED` consent for the same owner. Call `list_consents_for_owner(owner_sub, status="INITIATED")`. Assert only the INITIATED consent is returned.

7. **revoke INITIATED → REVOKED**: Call `revoke_consent(owner_sub, consent_id)`. Assert `status="REVOKED"`, `revoked_at` set, `audit_event("consent.revoked", ...)` was called (patch `alerts.audit_event` at source and assert `call_args`).

8. **revoke ACCEPTED → REVOKED**: Manually set a consent to `ACCEPTED` in moto, then call `revoke_consent`. Assert the transition succeeds.

9. **second revoke → 409**: Call `revoke_consent` twice on the same consent. Assert the second call raises `HTTPException(status_code=409)` or returns a no-op response — the exact behavior is determined by the upstream implementation, but the double-revoke must never corrupt state or raise an unhandled exception.

10. **revoke terminal consent is a no-op/409**: Set a consent to `EXPIRED` in moto, then call `revoke_consent`. Assert `HTTPException(status_code=409)`.

11. **`is_consent_valid`**: Assert `True` for `ACCEPTED` + `valid_until > now_ts()`; `False` for `INITIATED`; `False` for `REVOKED`; `False` for `ACCEPTED` with `valid_until < now_ts()`.

12. **`expire_due_consents()`**: Seed two rows in moto: one `ACCEPTED` with `valid_until = now_ts() - 1` (past) and one `ACCEPTED` with `valid_until = now_ts() + 9999` (future). Call `expire_due_consents()`. Assert the past row is now `EXPIRED` and `audit_event("consent.expired", ...)` was called once. Assert the future row is still `ACCEPTED` and `revoked_at` is absent.

#### CSN-002 — SCA gate

13. **`/sca` mints a challenge**: Call `request_consent_sca(owner_sub, consent_id, req)` against a moto `sessions` table. Assert the returned `challenge_id` starts with `consent_sca_`, a `T.sessions` item exists with `purpose="consent_sca"`, `pending_auth=True`, `consent_id` in the payload, and `audit_event("consent.sca_required", ...)` was called.

14. **`/accept` before `challenge_done` → 403**: Call `accept_consent` when the challenge item has no `passed` factors set. Assert `HTTPException(status_code=403, detail.code="sca_incomplete")`.

15. **mark all required factors → ACCEPTED**: Patch `sessions.challenge_done` to return `True` (or manually set the moto sessions item to represent a completed challenge). Call `accept_consent`. Assert the consent transitions to `ACCEPTED`, the challenge row in moto is revoked (`revoked=True` or deleted), and `audit_event("consent.accepted", ...)` was called.

16. **replay `/accept` after ACCEPTED → idempotent or 409**: Call `accept_consent` on an already-`ACCEPTED` consent. Assert either a 200 no-op or `HTTPException(409)` — not a 500 and not a double-write.

17. **expired/revoked challenge rejected by `load_challenge_or_401`**: Set the sessions item to `revoked=True`. Assert `HTTPException(401)` is raised without any separate code path in `accept_consent`.

#### CSN-002 — PIS consent

18. **PIS consent stores `payment_ref`**: Call `create_consent` with `consent_type="PIS"`, `payment_ref="txr_abc123"`. Assert the DDB item has `payment_ref="txr_abc123"`, `consent_type="PIS"`, and `status="INITIATED"`.

19. **PIS always requires SCA**: The `_consent_requires_sca` helper must return `True` for any PIS consent regardless of amount. Assert this directly on the helper function.

20. **`consent_authorizes_payment` True only for ACCEPTED+unexpired+matching**: Test all permutations — `INITIATED`/`REVOKED`/`EXPIRED` each return `False`; `ACCEPTED` with `valid_until < now_ts()` returns `False`; `ACCEPTED` with wrong `payment_ref` returns `False`; `ACCEPTED` with matching `payment_ref` and future `valid_until` returns `True`.

21. **PIS consent never writes a ledger or wallet row**: Verify that `app.services.billing_shared.new_ledger_entry` and `app.services.billing_shared.apply_wallet_delta` are **never called** during the entire PIS consent lifecycle. Patch both functions at source with `unittest.mock.patch`, run create/sca/accept/revoke, and assert `call_count == 0` on both mocks.

#### CSN-002 — consent-scoped rate limit

22. **`rate_limit_consent(id, "read")` 429s at cap**: Set `S.psd2_consent_rl_read_per_hour = 3`. Call `rate_limit_consent(consent_id, "read")` four times. Assert the first three calls succeed (no exception) and the fourth raises `HTTPException(status_code=429)` with `detail.code="consent_rate_limited"`, `detail.limit=3`, `detail.window_seconds=3600`, and a `Retry-After` header equal to `"3600"`.

23. **distinct `consent_id`s have distinct budgets**: Set cap to 1. Call `rate_limit_consent(id_A, "read")` once (succeeds) and `rate_limit_consent(id_B, "read")` once (also succeeds). Call `rate_limit_consent(id_A, "read")` again — this one 429s; `id_B` still has budget.

24. **`0` cap disables the throttle**: Set `S.psd2_consent_rl_read_per_hour = 0`. Call `rate_limit_consent` 100 times. Assert no exception is raised.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007

Tests must not exercise a `dev_mode` code path that differs from the production path. No CSN service module may contain `if S.dev_mode:` branches in business logic. The tests assert this implicitly: by running under moto (which behaves identically to real DynamoDB) with `S.dev_mode = False`, any dev-mode shortcut would cause a test divergence that would be caught.

### 7.2 Idempotency assertions

- Test 16 (replay `/accept`) confirms that a second `accept_consent` call after the consent is already `ACCEPTED` does not create a new session challenge or emit a second audit event.
- Test 9 (double revoke) confirms that the conditional `update_item` with `ConditionExpression="status IN (:i,:a)"` prevents a second revoke from succeeding (either 409 or silent no-op — the test asserts the `status` field is not corrupted and no exception other than the expected one is raised).
- Tests 22-24 confirm the rate-limit bucket is idempotent across multiple calls within the window: calls within the cap succeed consistently; the cap is only triggered on the (cap+1)-th call.

### 7.3 Money-safety

Test 21 is the critical money-safety invariant for the entire CSN cluster: it patches `app.services.billing_shared.new_ledger_entry` and `app.services.billing_shared.apply_wallet_delta` at source and drives the full PIS consent lifecycle (create → SCA request → SCA accept → revoke). It asserts `call_count == 0` on both mocks. The PIS consent is an *authorization record* only; money moves exclusively through the TXR execution engine (`OBP_TXN_REQUESTS_SCA_TICKETS.md`, `txn_requests`, the `settle_or_reverse_ledger` path at `app/services/billing_shared.py:262`). A CSN test that somehow triggers a ledger write is a critical defect.

`rate_limit_consent` uses `T.sessions` via `_bucket_limit` (at `app/services/rate_limit.py:60`), which stores only counter rows — never monetary amounts. No billing table is touched in any rate-limit test.

### 7.4 Security

- Root-only gating: tests 26, 54, 47 verify that non-root session contexts (`Role.USER`) trigger `HTTPException(403)` on all admin write endpoints. The `require_root_session` dependency (`app/auth/deps.py:308`) is invoked directly by passing the right mock context dict rather than bypassed.
- Owner scoping: test 35 confirms that `update_row` and `delete_row` use a DynamoDB `ConditionExpression` on `owner_sub` so a user can never modify another user's rows.
- SCA completeness: tests 14-17 confirm that the consent cannot transition to `ACCEPTED` without a fully-passed MFA challenge, that a revoked challenge is rejected by `load_challenge_or_401` (`sessions.py:517`), and that a completed challenge is consumed (revoked) immediately so it cannot be replayed.

## 10. Open Questions / Assumptions

1. **`valid_until` clamping vs. rejection (test 4)**: ~~RESOLVED~~ — CSN-001 spec §4.5 (line 207) and §5.4 (line 385) explicitly chose silent clamping. The test asserts clamping (not `HTTPException(400)`). No update needed.

2. **`rate_limit_consent` bucket store**: The `_bucket_limit` implementation uses `T.sessions` as its counter table (`app/services/rate_limit.py:60`). The `rate_limit_consent` helper introduced by CSN-002 is expected to follow the same pattern (keys `consent:{consent_id}`, bucket in `T.sessions`). If the upstream implementation uses a separate rate-limit table, the moto setup in tests 22-24 must include that table. This spec assumes `T.sessions`.

3. **`maybe_finalize` short-circuit**: The existing `sessions.maybe_finalize` (`sessions.py:653`) returns `None` for challenges with a `purpose` field, preventing them from being upgraded to a real login session. Tests 13-17 rely on this behavior being unchanged by CSN-002. If CSN-002 introduces a new `finalize` path for consent challenges, tests must be updated.

4. **`dynamic_entity_proxy` list op auth**: The CSN-003 CRUD is session-scoped (`Depends(require_ui_session)`). When a `dynamic_entity_proxy` endpoint invokes `list_rows("widget")` from a gateway handler, the `owner_sub` used to scope the list must come from the gateway's session context. The test assumes `owner_sub = ctx["user_sub"]` is passed through. If the proxy supports unscoped admin lists, a separate test must cover that path.

5. **Flag-off 404 mechanism**: CSN-006 tests assert that routes return 404 when the corresponding flag is off. The mechanism is that the router is never included in `app/main.py` when the flag is off (mirror the conditional-router-registration pattern). Tests assert this by checking `app.routes` or `create_app().routes` does not contain the relevant path when the flag is off. The exact assertion form depends on how `create_app` exposes the route list.

6. **Playwright section A — TOTP availability**: The E2E spec for consent SCA assumes Alice has a registered TOTP device. If the E2E suite runs on a fresh stack, the test must register a TOTP device in `beforeAll` using the existing `POST /ui/mfa/totp/add` flow (same pattern as `frontend/e2e/bug-fixes-2.spec.ts` section 16).
