## 1. Summary & Goal

VEW-005 is the consolidation ticket that makes the entire VEW feature family shippable behind its two default-OFF flags. The four feature tickets (VEW-001 through VEW-004) deliver service logic, endpoints, and Pydantic models, but none of them individually wires the DynamoDB table definitions, the `Settings` entries, or the conditional `app/main.py` registration blocks. VEW-005 supplies all of that infrastructure, then adds the spanning integration test suite (`tests/test_vew_005_integration.py`) that exercises the cross-ticket end-to-end flows under one moto-backed harness, and updates the documentation files so the feature is discoverable.

Concrete deliverables:

1. **`scripts/local-ddb-init.py`** — two new `TableDef` entries (`account_views`, `entitlement_requests`) with all GSIs and all `attr_types` entries for numeric sort keys.
2. **`app/core/tables.py`** — `T.account_views` and `T.entitlement_requests` handles added to the frozen `Tables` dataclass and its singleton initializer.
3. **`app/core/settings.py`** — six new settings fields with their env-var bindings and safe defaults.
4. **`.env.local.example`** — matching commented-out env vars so devs can opt in.
5. **`app/main.py`** — two conditional-import/register blocks, one for each flag, following the existing optional-router pattern used throughout the file.
6. **`tests/test_vew_005_integration.py`** — spanning hermetic offline test covering the full authenticated View flow, the public signed-link flow, the entitlement-request lifecycle, the flag-matrix (both flags OFF), and audit event coverage.
7. **`docs/dynamodb.md`**, **`docs/file-reference.md`**, **`CLAUDE.md`** — schema entries, file-map additions, and a "Common gotchas" note.

Nothing in this ticket re-implements logic that belongs to VEW-001..004. It only wires what those tickets define.

## 2. Context & Current State

### 2.1 Table init pattern (cite)

`scripts/local-ddb-init.py` uses the `TableDef` dataclass (`:29-35`) with fields `name`, `partition_key`, `sort_key`, `gsi` (list of dicts), and `attr_types` (dict mapping attribute names to `"N"` or `"S"`). The live `_table_defs()` function (`:42`) returns the master list consumed by the recreation loop. Examples with numeric GSI sort keys:

- `sticker_collections` (`:80-85`): `attr_types={"created_at": "N"}` for the `created_at` GSI sort key.
- `kyc_risk_scores` (`:170-179`): `attr_types={"timestamp": "N"}` for two GSIs sharing the same numeric sort key.
- `users` (`:50-54`): `attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"}` demonstrating multiple numeric attributes in one `TableDef`.

The VEW tables follow this same pattern. Omitting `attr_types` for a numeric GSI sort key causes DynamoDB to infer type `S` (string), which produces a `ValidationException` when an integer value is written — a documented project gotcha (CLAUDE.md "DynamoDB numeric GSI sort keys").

### 2.2 Tables singleton pattern (cite)

`app/core/tables.py` defines a frozen `Tables` dataclass (`:68-319`) with one `Any`-typed field per table. The singleton `T` at `:321` is constructed once at import time via `_safe_table(S.<setting_name>)`. Two new fields — `account_views` and `entitlement_requests` — are appended to the `Tables` dataclass and to the `T` constructor call. Tests freeze them with `object.__setattr__(T, "account_views", moto_table)` (the established pattern throughout the test suite, e.g. `tests/test_gap_0223_0224_ec2_host_inventory.py`).

### 2.3 Settings pattern (cite)

`app/core/settings.py:839` is the canonical default-OFF idiom for feature flags:

```python
inventory_reservations_enabled: bool = os.environ.get(
    "INVENTORY_RESERVATIONS_ENABLED", "false"
).lower() == "true"
```

The secret fallback pattern mirrors `cart_recovery_link_secret` (`:826-829`):

```python
cart_recovery_link_secret: str = (
    os.environ.get("CART_RECOVERY_LINK_SECRET")
    or os.environ.get("UI_ACCESS_TOKEN_SECRET", "")
)
```

VEW-005 adds six settings using these exact idioms.

### 2.4 Conditional router registration in main.py (cite)

`app/main.py` already imports dozens of routers unconditionally (`:17-329`). The pattern for optional feature routers that must stay dormant until a flag is on is: defer the import inside the `create_app` function body guarded by `if _S.<flag>:`. This is the approach used by other optional routers: `ticket_boards_enabled` (`:699-701`) defers the import inside the guard block, and `honeypot_endpoints_enabled` (`:797-800`) follows the same pattern. Two such blocks are added for VEW, one per flag. **Note**: `browser_ssh_terminal_router` at `:101-104` is NOT a valid analogue — it is imported unconditionally at module level and always registered; its flag is checked only inside the route handler body, not at registration time.

### 2.5 Authenticated and unauthenticated router split

`app/main.py` already registers unauthenticated public routers separately from the authenticated router tree. The `file_share_links_public_router` (`:59`), `calendar_public_router` (`:60`), and `calendar_public_event_router` (`:61`) are registered alongside the signed-in routers with no session dependency. VEW-002 defines a `public_account_views_router` (prefix `/ui/views/public`) that must be registered in the same unauthenticated section so the `GET /ui/views/public/{token}` endpoint requires no session cookie.

### 2.6 Audit infrastructure (cite)

`app/services/alerts.py:644` — `audit_event(event, user_sub, request=None, **fields)` is the canonical audit write path used by all VEW mutations. VEW-005's integration tests patch `audit_event` at the service module's namespace (not at `alerts.audit_event` directly) to spy on call arguments, identical to the pattern in `tests/test_gap_0265_0266_kyc_risk_scoring.py`.

### 2.7 Prior VEW specs (context for what this wires)

- VEW-001 (`docs/openbankproject/specs/VEW-001.md`): defines `account_views` table layout, `T.account_views` handle, `account_views_enabled` flag, and the `app/services/account_views.py` / `app/routers/account_views.py` surface.

## 3. Data Model

### 3.1 `account_views` table

This table is defined by VEW-001/002 and wired here. VEW-005 only adds the `TableDef` entry. Shown here as the authoritative schema for the init script.

**Primary key**: `pk` (S) / `sk` (S).

**Row types** (discriminated by `sk` prefix):

| Row type | `pk` | `sk` | Purpose |
|---|---|---|---|
| View definition | `RESOURCE#{resource_type}#{resource_id}` | `VIEW#{view_id}` | Named field-grant template |
| VIEWGRANT | `RESOURCE#{resource_type}#{resource_id}` | `VIEWGRANT#{grantee_sub}#{view_id}` | Active/pending grant to a grantee |
| In-table audit | `RESOURCE#{resource_type}#{resource_id}` | `AUDIT#{ts:010d}#{event_id}` | Resource-scoped mutation history |
| Public-link revoke marker | `PUBREVOKE#{jti}` | `META` | One-time-use public link consumption record |

**GSI1 — `by-owner`** (`GSI1PK=OWNER#{owner_sub}`, `GSI1SK=created_at` numeric): enables `list_views_by_owner(owner_sub)` — all views an owner defined across resources, sorted by creation time. Mirrors `delegates.GSI1` (`delegates.py:97-98`).

**GSI2 — `by-grantee`** (`GSI2PK=GRANTEE#{grantee_sub}`, `GSI2SK=accepted_at` numeric): enables `list_views_shared_with_me(grantee_sub)` — all views actively granted to a grantee, sorted by accepted time (active grants only). Mirrors `delegates.GSI1` used by `list_managed_creators` (`delegates.py:216-223`).

**`attr_types`**:

```python
attr_types={"GSI1SK": "N", "GSI2SK": "N"}
```

Both GSI sort keys are integer Unix timestamps (from `now_ts()`). Without the `"N"` declaration, DynamoDB Local infers `"S"` and raises `ValidationException` when an integer is written as the sort key value.

**`TableDef` entry in `scripts/local-ddb-init.py`**:

```python
TableDef(
    S.account_views_table_name,   # new settings key, default "account_views"
    "pk",
    "sk",
    gsi=[
        {"index_name": "by-owner",   "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "by-grantee", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
    ],
    attr_types={"GSI1SK": "N", "GSI2SK": "N"},
),
```

### 3.2 `entitlement_requests` table

**Primary key**: `pk` (S) / `sk` (S).

**Row types**:

| Row type | `pk` | `sk` | Purpose |
|---|---|---|---|
| Request (main) | `ENTREQ#{request_id}` | `META` | Lifecycle state for one entitlement request |
| In-table audit | `ENTREQ#{request_id}` | `AUDIT#{ts:013d}#{event_id}` | Per-request mutation history (newest-first) |

**GSI1 — `by-status`** (`GSI1PK=STATUS#{status}`, `GSI1SK=created_at` numeric): admin queue — list all requests in a given status sorted by creation time. Mirrors `kyc_case_assignment`'s `gsi_status_pk` index (`kyc_case_assignment.py:146`).

**GSI2 — `by-requester`** (`GSI2PK=REQUESTER#{requester_sub}`, `GSI2SK=created_at` numeric): "my requests" view for the authenticated requester.

**`attr_types`**:

```python
attr_types={"GSI1SK": "N", "GSI2SK": "N"}
```

`created_at` is the GSI sort key for both GSIs. It is set at row creation via `now_ts()` and never updated (same value on both GSIs so a single `created_at` attribute serves both sort positions).

**`TableDef` entry**:

```python
TableDef(
    S.entitlement_requests_table_name,   # default "entitlement_requests"
    "pk",
    "sk",
    gsi=[
        {"index_name": "by-status",    "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "by-requester", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
    ],
    attr_types={"GSI1SK": "N", "GSI2SK": "N"},
),
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Table recreation correctness

`just restart` calls `scripts/local-ddb-init.py` which drops and recreates all tables. The two VEW `TableDef`s must appear in `_table_defs()` unconditionally — they are infrastructure definitions, not code paths. Even when both flags are OFF, the tables must be recreatable so that `just restart` does not fail when the codebase contains the definitions. The handles `T.account_views` and `T.entitlement_requests` are constructed at import time (with DynamoDB Local on port 8001); if the tables do not exist at startup the handles will fail on the first DDB call, not at construction time — safe.

### 5.2 Flag-OFF behavior: router not imported

When `S.account_views_enabled` is `False`, the `import app.routers.account_views` line is never executed. FastAPI never registers the routes. Any request to `/ui/views/*` or `/ui/views/public/*` reaches the default 404 handler — the same outcome as any undefined path. No 403 is produced; the feature is fully dark. Same for `entitlement_requests_enabled` and `/ui/entitlement-requests/*`. This is stricter than a runtime flag check inside a handler (which would 403 or 503) and matches the STU-002 §6.2 pattern referenced in the ticket's cross-cutting constraints.

### 5.3 Flag-OFF behavior: projection helper called from always-on paths

`project_resource` (VEW-003) is a pure function with no I/O. If any always-on code path calls it speculatively when the flag is OFF, the function must short-circuit to returning the resource unchanged (or `{}` for unknown type — VEW-003's fail-closed rule). The integration test's flag-matrix case asserts that calling `project_resource` with a mock resource when `account_views_enabled=False` returns the resource unchanged and never touches DDB.

### 5.4 `account_view_public_secret` fallback

`account_view_public_secret` is resolved at settings construction time using the `or` chain. If `ACCOUNT_VIEW_PUBLIC_SECRET` is set to a non-empty string in the environment, that value is used. If it is absent or empty, the value falls back to `UI_ACCESS_TOKEN_SECRET`. This matches `cart_recovery_link_secret` (`settings.py:826-829`). In dev, `UI_ACCESS_TOKEN_SECRET` is always populated by `scripts/setup_ubuntu.sh`; in production, operators should set a distinct `ACCOUNT_VIEW_PUBLIC_SECRET`. The `verify_ws_token`-style verification in VEW-002's `resolve_public_view` uses this same resolved secret, so the secret is consistent across mint and verify.

### 5.5 GSI sort-key type correctness

Both VEW tables use integer Unix timestamps (`now_ts()`) as GSI sort keys (`GSI1SK`, `GSI2SK`). The `attr_types={"GSI1SK": "N", "GSI2SK": "N"}` entries in `_table_defs()` cause `local-ddb-init.py`'s `create_table` call to declare these attributes as `N` in `AttributeDefinitions`. Without this, DynamoDB Local defaults to `S` and raises `ValidationException: One or more parameter values were invalid: Type mismatch for Index Key` when a numeric value is written or queried. The integration tests create the tables via moto and must also declare the attribute types — they do this by creating the tables with the same `TableDef` definitions (see test setup in Section 9).

### 5.6 `entitlement_request_max_open_per_user` enforcement

`create_request` in `app/services/entitlement_requests.py` queries the `by-requester` GSI for open (non-terminal) requests from the same requester and raises `HTTPException(429)` if the count meets or exceeds `S.entitlement_request_max_open_per_user`. "Open" means `status in ("pending", "under_review")`. This guard runs before the duplicate-request check so the error is consistent regardless of deduplication.

### 5.7 Claim conflict handling

`claim_request` mirrors `kyc_case_assignment.claim` (`:478-498`), which uses an **application-level** check: read the row; if `claimed_by_sub` is already set to a different admin, raise `HTTPException(409, "Request already claimed by another admin")`; otherwise proceed with the `update_item`. This is NOT a DynamoDB-layer `ConditionExpression` CAS — there is no `ConditionalCheckFailedException`. A claimed-by-self idempotent re-claim is allowed (same admin re-claiming their own row is a no-op or succeeds). The race window between read and write is narrow but non-zero. VEW-004 implementers may choose to harden this with a DynamoDB `ConditionExpression` (`attribute_not_exists(claimed_by_sub) OR claimed_by_sub = :admin_sub`) for strict atomicity.

### 5.8 Public-link route ordering

Within `app/routers/account_views.py`, the literal route `GET /ui/views/public/{token}` (on the `public_router`) does not conflict with the dynamic routes on the `authenticated_router` because they are separate `APIRouter` instances registered independently. Within the authenticated router, the route `GET /ui/views/shared-with-me` must be declared before `GET /ui/views/{resource_type}/{resource_id}` to prevent FastAPI matching the literal segment `shared-with-me` as a `resource_type` path parameter. The VEW-001 spec (`VEW-001.md`) calls this out for `/grant-catalog`; the same ordering rule applies to `/shared-with-me` (from VEW-002).

### 5.9 Backward compatibility of `T` singleton construction

Adding new fields to the `Tables` dataclass and `T = Tables(...)` call is a purely additive change. The dataclass is `frozen=True` but not `total=True`; adding new fields only requires adding corresponding constructor arguments. Python's frozen dataclasses raise `FrozenInstanceError` on attribute assignment after construction, so only `object.__setattr__` can mutate them — which is exactly what tests do. No existing code references `T.account_views` or `T.entitlement_requests` before VEW-001/004 land, so there is no forward-reference risk.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 parity

All DDB access goes through `T.account_views` and `T.entitlement_requests` — `_FloatSafeTable`-wrapped boto3 table handles (`tables.py:29-66`). In dev, these point to DynamoDB Local on port 8001; in prod, they point to the real DynamoDB service. There is no `if S.dev_mode` branch anywhere in the VEW service or router code. The `account_view_public_secret` fallback works identically in both environments (dev uses `UI_ACCESS_TOKEN_SECRET`; prod uses the separately configured `ACCOUNT_VIEW_PUBLIC_SECRET`). No mock-only code paths, no `S.dev_mode` guards.

### 7.2 Idempotency of table init

`local-ddb-init.py` uses `try/except` around each `create_table` call, catching `ResourceInUseException` (the table already exists). Adding the two VEW `TableDef` entries is therefore idempotent across repeated `just restart` runs: the first run creates the tables; subsequent runs skip creation silently. The integration test's `setUp` uses moto and creates fresh in-memory tables each run.

### 7.3 Public-link token security

Public-link tokens use the **cart-recovery HMAC scheme** from `app/services/cart_reminders.py:150-165`, **not** `mint_ws_token`/`verify_ws_token`. `mint_ws_token`/`verify_ws_token` (`app/core/crypto.py:35-61`) use `S.ws_token_secret` (the WebSocket token secret, bound to `WS_TOKEN_SECRET`) — the wrong key for this purpose. VEW-002 instead defines custom signing helpers that use `S.account_view_public_secret` directly (mirroring `_sign_recovery_token`/`_verify_recovery_token` in `cart_reminders.py`). The token format is identical: `b64url(json_payload).b64url(hmac_sha256_sig)`. The payload encodes `resource_type`, `resource_id`, `view_id`, `exp` (expiry as Unix timestamp), and `jti` (random nonce for revocation). The HMAC signature uses `hmac.compare_digest` (`crypto.py:52`) for constant-time comparison — no timing-oracle vulnerability. Expired tokens are rejected before the resource is assembled. Tampered tokens produce a wrong HMAC and are rejected without revealing which field was modified. The `jti` is checked against the `PUBREVOKE#` marker row (a conditional `put_item` on `attribute_not_exists(pk)`) to implement one-time-revoke semantics mirroring `_mark_token_consumed` in `cart_reminders.py:198-211`.

### 7.4 Money safety

VEW-003's `GET /ui/views/{resource_type}/{resource_id}/{view_id}/data` is a **read-only** endpoint. It calls existing read primitives (`billing_shared.py` wallet/balance, `creator_payouts.py` payout destination) and applies a projection filter. It never calls `new_ledger_entry`, `apply_wallet_delta`, `settle_or_reverse_ledger`, or any money-moving function. The public-link path is also read-only. VEW-004's `approve_request` calls `crm_acl.assign_role_to_user` (a role grant, not a money movement). No VEW endpoint initiates a financial transaction.

### 7.5 Entitlement approval ROOT-only gate

`approve_request` is gated by `Depends(require_root)` (`policy.py:63`). An ADMIN calling this endpoint receives 403. This mirrors the posture of `admin_roles.grant_role` (`admin_roles.py:202`). Claim, reject, and list-queue are `require_admin_or_root` (`policy.py:67`). All admin endpoints also enforce CSRF via `require_admin_or_root_csrf` (`policy.py:100`) when the request arrives via a browser session cookie.

### 7.6 Claim compare-and-swap (concurrency safety)

Two admins racing to claim the same entitlement request can only result in one success. **Correction**: the modelled CAS in VEW-004's `claim_request` mirrors the application-level check in `kyc_case_assignment.claim()` (`:478-498`), which performs a read-then-conditional-update at the application layer (read the row → if `claimed_by_sub` is set and differs from the requesting admin → raise 409). This is NOT a DynamoDB-layer `ConditionExpression` CAS; there is no `ConditionalCheckFailedException`. The race window is narrow (both admins read an unclaimed row before either writes) but not zero. Implementations that need strict atomicity should upgrade to a DynamoDB `ConditionExpression` (`attribute_not_exists(claimed_by_sub) OR claimed_by_sub = :admin_sub`) to close the race; the VEW-004 spec should specify which approach is used. No deadlock risk (no multi-row operation; each claim touches one row).

## 10. Open Questions / Assumptions

1. **`account_views_table_name` as a settings key vs. hardcoded default.** The spec assumes `S.account_views_table_name` follows the pattern of every other table name setting (e.g. `S.cart_reminder_config_table_name`, `settings.py:822`). If VEW-001 hard-codes the table name as `"account_views"` instead of going through `S`, VEW-005 should align with that choice. Hardcoding is acceptable given the default value matches.

2. **`entitlement_requests` GSI `by-requester` scope.** The spec states only `active` grants appear in `list_views_shared_with_me` but the `by-requester` GSI on `entitlement_requests` returns all requests regardless of status (callers can filter client-side or the service can apply a `FilterExpression`). Since `FilterExpression` does not reduce page size (CLAUDE.md gotcha), the service should loop `LastEvaluatedKey` and collect all pages before filtering, not rely on a single `query()` call with a `FilterExpression` to return a complete result on a busy table.

3. **`crm_acl` module naming.** VEW-004 references `app.services.crm_acl` as the STU-002 ACL adapter. If STU-002 lands with a different module name (e.g. `app.services.acl`), the `ImportError`-guarded adapter import in `approve_request` must be updated to match. This is a soft dependency and VEW-005 does not make the import; it only confirms the pattern compiles.

4. **`resource_id` for `wallet` type.** The spec assumes `resource_id == owner_sub` for `resource_type="wallet"` (the wallet is per-user). This matches `billing_shared.py:23` (`user_pk(user_id) -> "USER#{user_id}"`) where `user_id` is the `user_sub`. VEW-001's `_assert_owns_resource` enforces this; VEW-005's integration tests use `resource_id="alice"` (the test `user_sub`) accordingly.

5. **`project_resource` flag guard.** The flag-matrix test asserts that calling `project_resource` with `S.account_views_enabled=False` is safe. VEW-003 defines the function as pure with no DDB I/O, so there is nothing to guard — the function works regardless of the flag. The assertion in Test 4 is therefore a smoke test that the function exists and doesn't crash, not a behavioral gate.

6. **Public router path prefix.** VEW-002 defines the public router with prefix `/ui/views/public`. This means the public-link endpoint is `GET /ui/views/public/{token}` — inside the `/ui/` namespace. The Vite proxy at `frontend/vite.config.ts` proxies all `/ui/` paths to the backend, so this endpoint is reachable from the browser without additional proxy configuration.
