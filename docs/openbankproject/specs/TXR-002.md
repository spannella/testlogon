# TXR-002 — Status state-machine + get-status endpoint + per-type amount-limit config

**Ticket series**: OBP Tier-1 Transaction Requests + Step-Up SCA  
**Depends on**: TXR-001 (entity + create endpoint)  
**Unblocks**: TXR-003 (step-up SCA), TXR-004 (execute + money movement)  
**Estimate**: 2 days  
**Feature flag**: `TXN_REQUESTS_ENABLED` (default `false`)

---

## 1. Summary & Goal

TXR-002 introduces the formal lifecycle state machine for `TransactionRequest` objects created by TXR-001, exposes read endpoints so callers can observe the current status, and adds per-type ceiling configuration that enforces amount limits at create time. Together these three capabilities underpin the safety guarantees in TXR-003 and TXR-004: the status machine is the concurrency lock, the read endpoints are the polling surface, and the per-type limits are the first-line defense before any money moves.

**What this ticket does:**

1. Codifies the legal status transitions (`INITIATED → PENDING`, `INITIATED → COMPLETED`, `PENDING → COMPLETED`, `{INITIATED,PENDING} → FAILED`) as a tested `_transition(...)` helper in `app/services/txn_requests.py` that uses a conditional DynamoDB `update_item` asserting the current status — so a concurrent caller on the same request gets `ConditionalCheckFailedException` → `409 invalid_transition`, never a double-move.
2. Adds `GET /ui/txn-requests/{request_id}` (single fetch) and `GET /ui/txn-requests` (paginated list, optional `?status=` filter) endpoints backed by the `GSI_STATUS` index created in TXR-001.
3. Adds `enforce_amount_limit(type, amount_cents)` to `app/services/txn_requests.py`, reading per-type ceilings from `S` (env-configurable, no DDB), called from TXR-001's `create_request` before writing `INITIATED` — so an over-limit request never touches DynamoDB.

**What this ticket does NOT do:** No money moves; no OTP challenges are minted (TXR-003); no execution path (TXR-004). This is purely lifecycle machinery and read/config surface.

## 4. API / Service Design

### 4.1 Service layer — `app/services/txn_requests.py`

All functions added in or extended by TXR-002 (TXR-001 introduced `create_request`):

```python
def _transition(
    user_sub: str,
    request_id: str,
    expected_status: str,
    new_status: str,
    **patch: Any,
) -> Dict[str, Any]:
    """Conditional DynamoDB update asserting current status == expected_status.

    On success, returns the updated item dict.
    On ConditionalCheckFailedException, raises HTTPException(409, "invalid_transition").
    """
```

`patch` carries any additional fields to write alongside `status` and `updated_at` (e.g., `failure_reason`, `sca_challenge_id`, `ledger_refs`). The `UpdateExpression` sets `#status = :new, updated_at = :ts` plus one SET clause per key in `patch`. The `ConditionExpression` is `#status = :expected`. Both use `ExpressionAttributeNames={"#status": "status"}` to avoid the DynamoDB reserved-word conflict.

```python
def get_request(user_sub: str, request_id: str) -> Dict[str, Any]:
    """Fetch a single request. Raises HTTPException(404) if not found or not owned by user_sub."""
```

```python
def list_requests(
    user_sub: str,
    status_filter: Optional[str],
    cursor: Optional[str],
    limit: int = 20,
) -> Dict[str, Any]:
    """
    Returns {"items": [...], "next_cursor": str|None}.

    When status_filter is provided, queries GSI_STATUS with
    KeyConditionExpression="status = :s" and FilterExpression="user_sub = :u".
    When not provided, queries the base table PK (user_sub) directly.
    Pagination via encode_cursor / decode_cursor (app/core/cursor.py:94,103).
    """
```

```python
def enforce_amount_limit(type_: str, amount_cents: int) -> None:
    """Raise HTTPException(400, "amount_over_limit") if amount_cents exceeds
    the per-type ceiling from S. Called by create_request() before writing INITIATED.
    """
```

The ceiling lookup table inside `enforce_amount_limit`:

```python
_LIMIT_ATTR: Dict[str, str] = {
    "WALLET_TRANSFER": "txn_request_limit_wallet_transfer_cents",
    "COUNTERPARTY":    "txn_request_limit_counterparty_cents",
    "PAYOUT":          "txn_request_limit_payout_cents",
    "REFUND":          "txn_request_limit_refund_cents",
    "FREE_FORM":       "txn_request_limit_free_form_cents",
}
ceiling = getattr(S, _LIMIT_ATTR[type_], 0)
if ceiling > 0 and amount_cents > ceiling:
    raise HTTPException(400, "amount_over_limit")
```

A ceiling of `0` means "unlimited" (matching the pattern in `creator_payouts.py:307` where `get_min_payout_cents()` defaults to `0` for "no minimum").

`create_request` (TXR-001) is updated to call `enforce_amount_limit(body.type, body.amount_cents)` as its first check, before any DDB write.

#### `GET /ui/txn-requests` — list

Query params: `status: Optional[str]`, `cursor: Optional[str]`, `limit: int = 20` (max 100).

Response `200`:

```json
{
  "items": [ /* TxnRequestOut */ ],
  "next_cursor": "..."
}
```

Ownership is implicit: the DDB query uses `user_sub` from the session, so a caller can never list another user's requests.

When `status` is supplied, the service queries `GSI_STATUS`:

```python
T.txn_requests.query(
    IndexName="GSI_STATUS",
    KeyConditionExpression=Key("status").eq(status),
    FilterExpression=Attr("user_sub").eq(user_sub),
    ExclusiveStartKey=decode_cursor(cursor),
    Limit=limit,
    ScanIndexForward=False,   # newest-first by created_at
)
```

Note: `FilterExpression` does not reduce the page size — the query fetches up to `Limit` items before filtering. The list endpoint must loop via `LastEvaluatedKey` until `limit` items are accumulated or `LastEvaluatedKey` is absent (per CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha).

When `status` is absent, the base-table query is used instead (PK-only, no GSI):

```python
T.txn_requests.query(
    KeyConditionExpression=Key("user_sub").eq(user_sub),
    ExclusiveStartKey=decode_cursor(cursor),
    Limit=limit,
    ScanIndexForward=False,
)
```

#### `GET /ui/txn-requests/{request_id}` — single fetch

```python
item = T.txn_requests.get_item(Key={"user_sub": user_sub, "request_id": request_id}).get("Item")
if not item:
    raise HTTPException(404, "not_found")
return TxnRequestOut(**item)
```

Ownership is enforced by the `Key={"user_sub": user_sub, ...}` access pattern — a foreign `request_id` that belongs to a different `user_sub` will simply not be found.

## 5. Detailed Behavior & Edge Cases

### 5.1 State machine

```
           ┌──────────────────────────────┐
           │        INITIATED             │  (TXR-001 writes this)
           └──┬─────────────┬────────────┘
              │ SCA needed  │ no SCA + execute (TXR-004)
              ▼             ▼
           PENDING      COMPLETED  ◄── terminal
              │
              │ SCA passed + execute (TXR-004)
              ▼
           COMPLETED  ◄── terminal
           
  {INITIATED, PENDING}  ──→  FAILED  ◄── terminal
```

Legal transitions and their triggers:

| From | To | Triggered by |
|---|---|---|
| `INITIATED` | `PENDING` | TXR-003: SCA required → mint challenge |
| `INITIATED` | `COMPLETED` | TXR-004: no-SCA execute succeeds |
| `INITIATED` | `FAILED` | TXR-004: fraud gate blocks / primitive error |
| `PENDING` | `COMPLETED` | TXR-004: SCA done + execute succeeds |
| `PENDING` | `FAILED` | TXR-004: fraud gate / primitive error / challenge expired |
| `COMPLETED` | (any) | ILLEGAL → `409 invalid_transition` |
| `FAILED` | (any) | ILLEGAL → `409 invalid_transition` |

`COMPLETED` and `FAILED` are terminal. Any attempt to write a new status from a terminal state raises `ConditionalCheckFailedException` (the condition `#status = :expected` fails) and is mapped to `409 invalid_transition`.

### 5.2 `_transition` implementation detail

The update expression always sets `updated_at` alongside `status`:

```python
update_expr = "SET #status = :new, updated_at = :ts"
attr_values = {":new": new_status, ":ts": now_ts(), ":expected": expected_status}
attr_names  = {"#status": "status"}

for k, v in patch.items():
    placeholder = f":p_{k}"
    update_expr += f", {k} = {placeholder}"
    attr_values[placeholder] = v

try:
    resp = T.txn_requests.update_item(
        Key={"user_sub": user_sub, "request_id": request_id},
        UpdateExpression=update_expr,
        ConditionExpression="#status = :expected",
        ExpressionAttributeNames=attr_names,
        ExpressionAttributeValues=attr_values,
        ReturnValues="ALL_NEW",
    )
    return resp["Attributes"]
except T.txn_requests.meta.client.exceptions.ConditionalCheckFailedException:
    # Another concurrent caller won the race — return the current state to the caller.
    current = get_request(user_sub, request_id)
    raise HTTPException(409, detail={"code": "invalid_transition", "current_status": current["status"]})
```

The `409` response body carries `current_status` so the caller can decide whether the transition they wanted already happened (e.g., a duplicate execute that already landed `COMPLETED`) or was genuinely illegal.

### 5.3 Amount limit enforcement

`enforce_amount_limit` runs as the first guard inside `create_request`, before any DDB write. If the request is over the ceiling, `HTTP 400 amount_over_limit` is returned with no item created and no audit event. A ceiling of `0` (the default for all types when the env vars are absent) means "no limit enforced".

The SCA threshold `S.txn_request_sca_threshold_cents` (consumed by TXR-003) is a separate setting and is not an amount limit — it controls when to require step-up authentication, not whether the request can exist.

> **Note on "0 = unlimited" precedent**: The analogous pattern for the amount ceiling (`ceiling == 0 → skip enforcement`) is most directly mirrored by the `_LIMIT_ATTR` lookup table itself — a missing or zero env var means no ceiling. The earlier claim that `get_min_payout_cents()` defaults to `0` is incorrect: its effective default is `S.payout_minimum_cents` which defaults to `1000` (env `PAYOUT_MINIMUM_CENTS`). The "0 = no constraint" convention here is a new one for TXR, not a reuse of the payout pattern.

### 5.4 List endpoint and FilterExpression pagination loop

Because `FilterExpression` does not count against DynamoDB's `Limit`, the service must loop:

```python
items, last_key = [], decode_cursor(cursor)
while len(items) < limit:
    kwargs = {"Limit": limit * 3, "ScanIndexForward": False}
    if last_key:
        kwargs["ExclusiveStartKey"] = last_key
    resp = T.txn_requests.query(IndexName="GSI_STATUS", ...)
    items.extend(resp.get("Items", []))
    last_key = resp.get("LastEvaluatedKey")
    if not last_key:
        break
```

The caller receives at most `limit` items and a `next_cursor` pointing to the DDB `LastEvaluatedKey` at the point of cutoff.

### 5.5 Concurrent transition — exactly-one semantics

Two concurrent callers attempting `INITIATED → COMPLETED` on the same request:

- Both read `status == INITIATED`.
- The first to call `update_item` with `ConditionExpression="#status = :expected"` (`:expected = "INITIATED"`) wins and transitions to `COMPLETED`.
- The second call hits `ConditionalCheckFailedException`. The `_transition` helper re-reads the item (now `COMPLETED`) and returns `409` with `current_status="COMPLETED"`.
- Money moves only inside the first caller's execution (TXR-004). The second caller never reaches the execution path.

### 5.6 Foreign request_id returns 404, not 403

A caller that guesses another user's `request_id` and queries `GET /ui/txn-requests/{request_id}` triggers a `DDB get_item` with `Key={"user_sub": caller_sub, "request_id": foreign_id}`. Because the item's real PK is a different `user_sub`, the item is not returned (`Item` absent → `get_item` returns `{}`). The handler raises `404 not_found`. This is the correct OBP-style behavior: it does not leak the existence of the request to the requester.

### 5.7 Status filter validation

If `?status=` is supplied with an unrecognized value (e.g., `status=BOGUS`), the endpoint returns `400 invalid_status` before issuing any DDB query. Valid values: `INITIATED`, `PENDING`, `COMPLETED`, `FAILED`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 Dev/prod parity

TXR-002 introduces no provider call, no AWS SDK call beyond DynamoDB, and no mock/real divergence. The same `_transition`, `get_request`, `list_requests`, and `enforce_amount_limit` functions run against DynamoDB Local in dev and real DynamoDB in prod — same code path both ways. No `if S.dev_mode` branch exists in the service (SECOPS-007). The `T.txn_requests` table handle resolves through `app/core/tables.py` which already selects DynamoDB Local vs real DynamoDB from `S.ddb_endpoint_url`.

### 7.2 Status as the concurrency lock

The conditional `update_item` in `_transition` (asserting `#status = :expected`) is the single concurrency primitive. No application-level mutex, no advisory lock. Two concurrent callers on the same `(user_sub, request_id)` pair can each read the same status, but at most one conditional write can succeed. The loser gets `409`. This is the same pattern used in `tickets._conditional_update_meta` (line 723) and `creator_payouts.claim_payout_sentinel` (line 225).

### 7.3 Amount limits as money safety

`enforce_amount_limit` fires before `INITIATED` is written. An over-limit request never enters DynamoDB, so there is no orphaned item to clean up. The limit is a ceiling, not a balance check — balance sufficiency is the responsibility of `apply_wallet_delta`'s `ConditionExpression` in TXR-004 (line 209 of `billing_shared.py`).

### 7.4 No money moves in TXR-002

TXR-002 is purely read/write of the `txn_requests` table row and `Settings` reads. No call to `apply_wallet_delta`, `new_ledger_entry`, `settle_or_reverse_ledger`, `stripe.*`, or `creator_payouts.*` is made in this ticket. Money-safety constraints (binding per the cross-cutting section of the ticket file) are enforced in TXR-004.

### 7.5 Audit on every transition

Every call to `_transition(...)` that succeeds emits an `audit_event(...)` to `T.alerts` via `from app.services.alerts import audit_event` (same import as `app/routers/billing.py:49`). The event name follows the taxonomy declared in the ticket: `txn_request.created` (TXR-001), `txn_request.sca_required` (TXR-003), `txn_request.sca_passed` (TXR-003), `txn_request.executed` (TXR-004), `txn_request.failed` (TXR-004). TXR-002 itself does not introduce new transition audit events (no new write paths), but the `_transition` helper it introduces carries the audit call as a hook for TXR-003/004 to call after a successful `update_item`.

### 7.6 No webhook events in TXR-002

Webhook dispatch (`webhook_service.py:WEBHOOK_EVENT_TYPES_V2`) for `txn_request.*` events is wired by TXR-004 when transitions reach terminal states. TXR-002 does not add to `WEBHOOK_EVENT_TYPES_V2`.

The `txn_requests` table is new (TXR-001). It does not exist before the TXR ticket series is deployed. There are no existing rows to migrate. A `just restart` wipes and recreates all DynamoDB Local tables from `scripts/local-ddb-init.py`.

### 8.2 Existing billing/ledger tables untouched

TXR-002 reads from and writes only to `T.txn_requests`. It does not touch `T.billing`, `T.sessions`, `T.alerts`, or any other table. Existing billing endpoints (`/ui/billing/*`, `/ui/payouts/*`, `/ui/refund/*`) are completely unaffected.

### 8.3 Flag-off is a hard 404

When `S.txn_requests_enabled = false` (the default), the `txn_requests_router` is not registered in `create_app()`. All `/ui/txn-requests/*` paths return `404 Not Found`. There is no partial state: either all TXR endpoints are present or none are.

### 8.4 Additive settings fields

The new `Settings` fields all have safe defaults (`0` for integers, `false` for booleans). An existing deployment without the new env vars does not need any `.env.local` changes to start — the fields default to "no limit" and "flag off".

## 9. Test Plan

### 9.1 Pytest unit tests — `tests/test_txr_002_state_machine.py`

**Pattern**: offline/hermetic, matching the repo convention. Moto in-memory `txn_requests` table bound to the frozen `T.txn_requests` handle via `object.__setattr__(T, "txn_requests", moto_table)`. `S` flags toggled via `object.__setattr__`. `now_ts` patched. Route handlers invoked directly (no `TestClient` — the TestClient/lifespan pattern is broken in this repo per the "hermetic offline tests" constraint in the spec brief). `audit_event` patched to a list-collecting spy.

**State machine — legal transitions:**

| Scenario | Expected outcome |
|---|---|
| `INITIATED → PENDING` (simulate TXR-003 path) | Returns updated item with `status="PENDING"` |
| `INITIATED → COMPLETED` (no-SCA fast path) | Returns updated item with `status="COMPLETED"` |
| `PENDING → COMPLETED` (SCA passed) | Returns updated item with `status="COMPLETED"` |
| `INITIATED → FAILED` | Returns updated item with `status="FAILED"` and `failure_reason` |
| `PENDING → FAILED` | Returns updated item with `status="FAILED"` |

**State machine — illegal transitions:**

| Scenario | Expected outcome |
|---|---|
| `COMPLETED → PENDING` | `_transition` raises `HTTPException(409)` with `code="invalid_transition"` |
| `COMPLETED → FAILED` | Same |
| `FAILED → INITIATED` | Same |
| `FAILED → COMPLETED` | Same |
| Call `_transition(expected="PENDING")` when actual status is `INITIATED` | `ConditionalCheckFailedException` → `409`, item unchanged |

**Concurrency (simulated):**

Write a `INITIATED` item to moto. Call `_transition(..., expected_status="INITIATED", new_status="COMPLETED")` twice in sequence (moto is synchronous, not truly concurrent, but the second call must observe the already-`COMPLETED` row and raise `409`). Assert the item is `COMPLETED` exactly once and the second call raises `409` carrying `current_status="COMPLETED"`.

**Amount limits:**

| Scenario | Expected outcome |
|---|---|
| `WALLET_TRANSFER`, amount=500, limit=1000 | No exception, item written |
| `WALLET_TRANSFER`, amount=1500, limit=1000 | `HTTPException(400, "amount_over_limit")`, no item written |
| Any type, limit=0 | No exception regardless of amount |
| `REFUND`, amount=200, limit=100 | `HTTPException(400, "amount_over_limit")` |

Limits are set via `object.__setattr__(S, "txn_request_limit_wallet_transfer_cents", 1000)` before the call and restored after.

**Get/list endpoints:**

- `get_request` with owned `request_id` → returns `TxnRequestOut`.
- `get_request` with unknown or foreign `request_id` → `HTTPException(404)`.
- `list_requests` with no filter → returns all items for `user_sub`, newest-first, with correct `next_cursor`.
- `list_requests` with `status="INITIATED"` → only `INITIATED` items returned.
- `list_requests` with `status="BOGUS"` → `HTTPException(400, "invalid_status")`.
- Cursor round-trip: seed 5 items, request with `limit=2`, follow `next_cursor` twice, assert all 5 appear in order without duplicates.

**Flag off:**

Set `S.txn_requests_enabled = False`. Assert the router is not registered and requests to `/ui/txn-requests` return `404`.

**Audit spy:**

For each legal `_transition` call, assert `audit_event` was called with the correct event name and `request_id`.

### 9.2 E2E tests (TXR-005)

TXR-002's read and limit behaviors are covered by the E2E spec in TXR-005 (`frontend/e2e/txn-requests.spec.ts`) rather than a separate spec file. The TXR-002-specific E2E scenarios:

- Create a request above the configured limit → `400 amount_over_limit`.
- Create a request below the limit → `201 INITIATED`.
- `GET /ui/txn-requests/{id}` returns the correct status after each state change.
- `GET /ui/txn-requests?status=INITIATED` returns the correct subset.
- `GET /ui/txn-requests/{id}` for a foreign id (created as a different E2E user) → `404`.

These scenarios are seeded via `page.request.post(...)` with `x-csrf-token` header per CLAUDE.md's E2E session auth pattern.

## 10. Open Questions / Assumptions

1. **Admin visibility into another user's requests.** The current design gates all access by `user_sub` from the session. A ROOT/ADMIN user who wants to inspect or force-fail a pending request has no endpoint. For now, assume admin intervention goes through direct DDB writes or a future admin-facing endpoint (out of scope for TXR-002). *Decision: deferred to a follow-up admin endpoint.*

2. **SCA threshold source.** `TXN_REQUEST_SCA_THRESHOLD_CENTS` is defined in Settings here and consumed by TXR-003. If TXR-002 ships before TXR-003, the field is unused but harmless. *Assumption: ship both settings fields together in TXR-002.*

3. **`GSI_STATUS` scan scope.** The GSI PK is `status` (not `user_sub#status`). A status-filter query reads across all users and then applies a `FilterExpression` for `user_sub`. On a large table this is expensive. For Tier-1 scale the current design is acceptable. A composite key `status#user_sub` would be more efficient but is harder to query. *Assumption: use the simple GSI design now; composite key is a follow-up optimization.*

4. **`limit` parameter maximum.** The spec says `max 100`. The `billing.py` list endpoints vary (some use 500). *Assumption: cap at 100 for TXR to stay consistent with the KYC partner API (GAP-0286) which also uses 100.*

5. **`updated_at` written by `_transition` only.** Any direct `put_item` (e.g., TXR-001's `create_request`) sets `created_at` and `updated_at` to the same value. Subsequent transitions only update `updated_at` via `_transition`. *Assumption: this is correct and consistent with how `tickets.py` separates `created_at` from `updated_at`.*
