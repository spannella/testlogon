# PLT-004 — Sandbox JSON import — admin endpoint bulk-seeding accounts/transactions/customers (dev/flag-gated)

**Type:** Feature | **Priority:** P2 | **Estimate:** 3d  
**Flag:** `SANDBOX_IMPORT_ENABLED` (default **off**) — AND `S.dev_mode` (both required)  
**Branch prefix:** `feature/plt-004-sandbox-import`

---

## 1. Summary & Goal

OBP ships a `/sandbox/data-import` HTTP endpoint that accepts a single JSON document and bulk-seeds a test environment with banks, accounts, transactions, customers, and users. The OBP gap analysis (`docs/openbankproject/OBP_GAP_ANALYSIS.md` §D) classifies testlogon's equivalent as **PARTIAL**: *"seed scripts exist; no admin import endpoint."*

This ticket adds a single `POST /v1/admin/sandbox/data-import` endpoint, gated behind both `SANDBOX_IMPORT_ENABLED=1` and `DEV_MODE=1` (the two-flag gate is the feature itself, not a SECOPS-007 shortcut). The endpoint is admin-only, accepts a JSON payload with three optional arrays (`customers`, `accounts`, `transactions`), and writes into the existing `T.users` / `T.profile` / `T.billing` DynamoDB tables through the same primitives that every other path uses — `T.users.put_item`, `T.profile.put_item`, `billing_shared.ensure_balance_row` / `apply_wallet_delta`, and `billing_shared.new_ledger_entry`. No bespoke table, no bespoke writer, no forked primitive.

The endpoint is additive and backward-incompatible in only one direction: it is invisible unless both flags are on. With both flags off the router is never registered, no `T.*` reads are issued, and the platform is byte-for-byte unchanged.

## 2. Context & Current State

### Existing primitives (all reused, nothing forked)

**`scripts/local-ddb-seed.py` — the write idiom this ticket generalises.**  
`local-ddb-seed.py:14` defines `_table(ddb, name)` (a thin `ddb.Table(name)` wrapper) and then issues bare `put_item` calls against each table handle.  `local-ddb-seed.py:43-61` shows the canonical user/profile shape:

- `T.users` row: `{user_sub, email, full_name?, password_hash?, role, created_at}` — as confirmed by `app/cli/rootctl.py:691-718` where `T.users.put_item(Item=item, ConditionExpression="attribute_not_exists(user_sub)")` is the production-safe write. NOTE: `local-ddb-seed.py:43-51` only writes `{user_sub, email, created_at, updated_at}` (no `full_name`, `password_hash`, or `role`); the fuller shape above comes from rootctl only. PLT-004's `_write_customer` should write `{user_sub, email, full_name?, created_at, updated_at, source}` without `password_hash` or `role` (sandbox users need neither).
- `T.profile` row: `{user_sub, profile: {display_name, bio, ...}, audit: [], updated_at}` — the exact shape written by `app/services/profile.py:324-333` (`save_profile`; the function starts at line 324, the `T.profile.put_item` call is at lines 328-333).

**`billing_shared.ensure_balance_row` (billing_shared.py:69)**  
Issues a `ddb_put` of `{pk, sk="BALANCE", currency, owed_pending_cents:0, ..., updated_at}` guarded by `ddb_get` check. Called before any `apply_balance_delta`. For the wallet surface the wallet row uses `sk=WALLET_SK` (`billing_shared.py:173 WALLET_SK = "WALLET"`) and is upserted by `apply_wallet_delta` via `if_not_exists` expressions (`billing_shared.py:195-213`).

**`billing_shared.apply_wallet_delta` (billing_shared.py:185)**  
Atomically increments `wallet_balance_cents` on `billing` table key `{pk, sk="WALLET"}`. For positive deltas uses `if_not_exists(..., :z) + :d` so the row is auto-created; for negative deltas a `ConditionExpression` prevents overdraft. Returns the new balance as `int`. This is the correct primitive for seeding initial wallet balances — it prevents double-seeds via idempotent row creation and the `ensure_balance_row_for_key` helper at `billing_shared.py:108` covers non-`pk`-keyed tables.

**`billing_shared.new_ledger_entry` (billing_shared.py:224)**  
Constructs a complete ledger item dict with a ULID-based `sk = LEDGER#{ts}#{entry_id}`, a `ledger_date = ledger_date_for_ts(ts)` (billing_shared.py:10), and an `entry_id`. The `table` is **not** passed to this function — it returns `(sk, item)` and the caller issues `table.put_item(Item=item)`. The caller must use `T.billing` (PK `pk`, SK `sk`) and supply `key_name="pk"`, `key_value=f"USER#{user_sub}"`. This is the only sanctioned path for writing ledger rows so that `ledger_date` is always populated and the `GSI_LEDGER_DATE` index remains consistent (`scripts/local-ddb-init.py:67-77`).

**`billing` table and GSI (scripts/local-ddb-init.py:67-77)**  
PK `pk` (String), SK `sk` (String). GSI `GSI_LEDGER_DATE` with partition key `ledger_date` (String) / sort key `sk` (String). The `attr_types={"ledger_date": "S"}` declaration confirms the type is String (date formatted as `YYYY-MM-DD`). Wallet rows (`sk=WALLET`) and ledger rows (`sk=LEDGER#...`) coexist in this table alongside payment method rows (`sk=PM#...`) and the billing-config row (`sk=BILLING`).

**`users` table (scripts/local-ddb-init.py:50-54)**  
PK `user_sub` (String), no sort key. GSI `ByKycTier` with partition key `kyc_tier` (N) / sort key `kyc_tier_updated_at` (N); `attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"}`. The `users` table therefore does NOT use a composite primary key — the `user_sub` alone is the hash key.

**`profiles` table (scripts/local-ddb-init.py:97)**  
PK `user_sub` (String), no sort key. No GSI. Profile content is stored as a nested `profile` map attribute.

**`_require_admin_user` (app/routers/admin_usage.py:35)**  
Reads `S.filemgr_admin_users` (`app/core/settings.py:1056`, comma-separated list), raises HTTP 403 if the authenticated user is not in the allowlist, and raises HTTP 403 with `"admin privileges not configured"` if the allowlist is empty. All sandbox import endpoints use this same dependency — no new role system.

**`audit_event` (app/services/alerts.py:644)**  
Signature: `audit_event(event: str, user_sub: str, request=None, **fields: Any) -> None`. Fires on every successful mutation in admin routers. PLT-004 emits `audit_event("sandbox_data_import", admin_sub, req, counts={...}, errors_total=N)` after each successful import.

**`app/core/normalize.py`**  
`normalize_email(s: str) -> str` (line 60) and `normalize_phone(s: str) -> str` (line 66) are used to clean customer fields before write — same pattern as registration.

**`app/core/time.py`**  
`now_ts() -> int` returns integer Unix seconds. All `created_at` / `updated_at` fields on seeded rows use `now_ts()`.

### What is missing

There is no HTTP endpoint that accepts a JSON document and drives writes into `T.users`, `T.profile`, and `T.billing` through the above primitives. The only current path is the offline `scripts/local-ddb-seed.py` which hardcodes a single `dev-user` record and must be run as a CLI script. An admin can log in and POST a JSON payload; the script cannot.

## 3. Data Model

PLT-004 writes to **three existing tables only** — no new table is introduced. All writes go through the existing DDB handles on `T.*`.

### 3.1 `users` table (existing — `T.users`)

| Key | Type | Notes |
|---|---|---|
| `user_sub` (PK) | String | Caller-supplied or auto-generated `customer_{hex12}` |
| `email` | String | `normalize_email(input.email)` |
| `full_name` | String | Optional |
| `created_at` | Number | `now_ts()` |
| `updated_at` | Number | `now_ts()` |
| `source` | String | `"sandbox_import"` — marks seeded rows |

Write: `T.users.put_item(Item=item, ConditionExpression="attribute_not_exists(user_sub)")` — same guarded put as `rootctl.py:718`. A `ConditionalCheckFailedException` on this put is treated as a row-level error (recorded in per-row errors) with `"code": "duplicate_user_sub"` and does NOT abort the batch.

### 3.2 `profiles` table (existing — `T.profile`)

| Key | Type | Notes |
|---|---|---|
| `user_sub` (PK) | String | Matches the users row |
| `profile` | Map | `{display_name, bio, ...}` |
| `audit` | List | `[]` for seeded rows |
| `updated_at` | Number | `now_ts()` |

Write: `T.profile.put_item(Item={user_sub, profile, audit:[], updated_at})` — same shape as `save_profile` at `app/services/profile.py:328`. No condition expression: a repeated import of the same customer always overwrites the profile (idempotent update semantics; the users row write is the idempotency gate).

### 3.3 `billing` table (existing — `T.billing`)

**Wallet row** (`sk = "WALLET"`, PK = `f"USER#{user_sub}"`):

Written via `apply_wallet_delta(T.billing, pk, delta_cents, currency=currency)` (`billing_shared.py:185`). For seeded accounts with `initial_balance_cents > 0`, a single positive delta seeds the wallet. For zero-balance accounts, call `apply_wallet_delta(T.billing, pk, 0, currency=currency)` — since `delta_cents=0 >= 0` the deposit branch fires and auto-creates the WALLET row with `wallet_balance_cents=0` via `if_not_exists`. Do NOT use `ensure_balance_row_for_key` (`billing_shared.py:108`) for zero-balance wallet seeding: that helper creates a `sk="BALANCE"` row (owed/payments tracking), which is a different row from `sk="WALLET"` and is not what `GET /billing/wallet` reads.

**Ledger row** (`sk = LEDGER#{ts}#{entry_id}`, PK = `f"USER#{user_sub}"`):

Each element of `transactions[]` is written via `new_ledger_entry(key_name="pk", key_value=pk, entry_type=..., amount_cents=..., state=..., reason=..., extra={"source": "sandbox_import"})` (`billing_shared.py:224`). The returned `(sk, item)` pair is persisted with `T.billing.put_item(Item=item)`. `ledger_date` is always set by `new_ledger_entry`'s `ledger_date_for_ts(ts)` call — every seeded transaction therefore appears in `GSI_LEDGER_DATE` queries.

**No new GSI, no new table, no schema change.** The `attr_types` for `GSI_LEDGER_DATE` (`{"ledger_date": "S"}`) already exists at `scripts/local-ddb-init.py:76`.

## 4. API / Service Design

### 4.1 New service — `app/services/sandbox_import.py`

```python
def import_sandbox_payload(
    payload: SandboxImportIn,
    *,
    actor_sub: str,
) -> SandboxImportResult:
    ...
```

The function is synchronous (all DDB calls are synchronous boto3). It processes the three sections in order — customers, accounts, transactions — and returns a `SandboxImportResult` with per-section created counts and a flat list of per-row errors. It never raises on a row-level failure; it catches each `Exception`, appends a `SandboxRowError` to the errors list, and continues.

**Inner helpers (module-private):**

```python
def _write_customer(row: SandboxCustomerIn) -> str:
    """Write users + profile rows. Returns the resolved user_sub."""

def _write_account(row: SandboxAccountIn) -> None:
    """Ensure wallet/balance row; apply initial balance delta."""

def _write_transaction(row: SandboxTransactionIn) -> str:
    """Write one ledger row via new_ledger_entry. Returns the ledger sk."""
```

**Cap enforcement:**  
Before iterating each section, the service checks `len(section) > S.sandbox_import_max_items` (default 500). Excess rows are silently truncated to the cap; a `SandboxRowError(index=-1, code="section_truncated", message=f"capped at {S.sandbox_import_max_items}")` is appended to the errors list so the caller knows truncation occurred.

### 4.2 Pydantic models — to be added to `app/models.py`

```python
class SandboxCustomerIn(BaseModel):
    user_sub: Optional[str] = None        # auto-generated if absent
    email: str
    full_name: Optional[str] = None
    display_name: Optional[str] = None
    bio: Optional[str] = None

class SandboxAccountIn(BaseModel):
    user_sub: str
    initial_balance_cents: int = 0        # ge=0
    currency: str = "usd"

class SandboxTransactionIn(BaseModel):
    user_sub: str
    entry_type: str                        # "credit" | "debit" | "adjustment"
    amount_cents: int                      # ge=0
    state: str = "settled"                 # "pending" | "settled"
    reason: str
    currency: str = "usd"

class SandboxImportIn(BaseModel):
    customers: List[SandboxCustomerIn] = []
    accounts:  List[SandboxAccountIn]  = []
    transactions: List[SandboxTransactionIn] = []

class SandboxRowError(BaseModel):
    section: str        # "customers" | "accounts" | "transactions"
    index: int          # 0-based row index; -1 = section-level
    code: str
    message: str

class SandboxImportResult(BaseModel):
    customers_created: int
    accounts_created: int
    transactions_created: int
    errors: List[SandboxRowError]
    ok: bool            # True even on partial success (len(errors) > 0)
```

### 4.3 New router — `app/routers/sandbox.py`

```python
router = APIRouter(prefix="/v1/admin/sandbox", tags=["sandbox"])

@router.post("/data-import", response_model=SandboxImportResult)
async def data_import(
    body: SandboxImportIn,
    req: Request,
    admin_sub: str = Depends(_require_admin_user),
) -> SandboxImportResult:
    if not (S.sandbox_import_enabled and S.dev_mode):
        raise HTTPException(status_code=404, detail="not found")
    result = import_sandbox_payload(body, actor_sub=admin_sub)
    audit_event(
        "sandbox_data_import",
        admin_sub,
        req,
        customers_created=result.customers_created,
        accounts_created=result.accounts_created,
        transactions_created=result.transactions_created,
        errors_total=len(result.errors),
    )
    return result
```

The `_require_admin_user` dependency is imported directly from `app/routers/admin_usage.py` (or promoted to `app/auth/deps.py`; see Section 10). The `if not (S.sandbox_import_enabled and S.dev_mode)` guard is applied at the handler level rather than at router registration level because `S.dev_mode` is `True` by default in dev. The router itself is registered in `app/main.py` only when `S.sandbox_import_enabled` is `True` (additional defence-in-depth).

**Path note:** `/v1/admin/sandbox/data-import` — the literal segment `data-import` cannot be misrouted because the router has no `/{param}` catch-all. No ordering concern.

### 4.4 Router registration — `app/main.py`

Added adjacent to the existing admin-usage router registration at `app/main.py:675`:

```python
if S.sandbox_import_enabled:
    from app.routers.sandbox import router as sandbox_router
    app.include_router(sandbox_router)
```

The conditional import ensures the router is not even parsed unless the flag is on.

## 5. Detailed Behavior & Edge Cases

### 5.1 Processing order

1. **customers** — each row: generate or accept `user_sub`; `normalize_email`; `T.users.put_item` with `attribute_not_exists(user_sub)` guard; if guard fails, record `SandboxRowError(section="customers", index=i, code="duplicate_user_sub", ...)` and continue; on success, `T.profile.put_item`.
2. **accounts** — each row: resolve `f"USER#{user_sub}"` as `pk`; call `apply_wallet_delta(T.billing, pk, initial_balance_cents, currency=currency)` for ALL rows (including zero-balance). When `initial_balance_cents=0`, `apply_wallet_delta` still fires the deposit branch (`delta_cents >= 0`) and auto-creates the WALLET row with `wallet_balance_cents=0`. Do NOT use `ensure_balance_row_for_key` here — it creates `sk="BALANCE"` (owed/payments tracking), not `sk="WALLET"`. A `ConditionalCheckFailedException` from `apply_wallet_delta` (negative delta precondition) records a row-level error; `initial_balance_cents ge=0` is enforced by Pydantic so this cannot occur in practice.
3. **transactions** — each row: validate `entry_type in {"credit", "debit", "adjustment"}`; call `new_ledger_entry(key_name="pk", key_value=f"USER#{user_sub}", entry_type=..., amount_cents=..., state=..., reason=..., extra={"source": "sandbox_import"})` (`billing_shared.py:224`); call `T.billing.put_item(Item=item)`. No wallet delta is applied for imported transactions — ledger rows are stand-alone accounting records.

### 5.2 Idempotency

- **customers** section: the `attribute_not_exists(user_sub)` condition on the `T.users` put means a re-import of the same customer produces a `duplicate_user_sub` error for that row (no silent overwrite of the user record). The `T.profile` put is unconditional, so the profile is always refreshed on re-import if the users row write succeeds.
- **accounts** section: `apply_wallet_delta` with a positive delta is additive — re-importing an account row will double-credit the wallet. Callers must be aware of this. The section cap and per-run dry-run response (with the `errors` list) are the safety net. There is no upsert-to-exact-value semantic because `billing_shared.apply_wallet_delta` does not support it and forking the write primitive is out of scope.
- **transactions** section: each call to `new_ledger_entry` generates a new ULID-based `entry_id` (`billing_shared.py:240 entry_id = ulidish()`), so transactions are not idempotent by design — re-importing a transactions array writes duplicate ledger entries. This is consistent with the OBP sandbox model and with the plain `put_item` calls in `local-ddb-seed.py`.

### 5.3 Validation and error handling

- **Flag gate:** returns HTTP 404 (not 403) when the flag gate fails — this conceals the endpoint from unauthenticated scanners. The 403 from `_require_admin_user` fires before the flag check is reached.
- **`entry_type` validation:** `SandboxTransactionIn.entry_type` is constrained to `Literal["credit", "debit", "adjustment"]` via a Pydantic validator, matching the entry types used in `app/routers/billing.py:1129,1309,2421`. Invalid values produce a Pydantic 422 before the handler is entered.
- **`amount_cents ge=0`:** negative amounts are rejected at the Pydantic layer with 422.
- **Section cap:** checked before iteration; excess rows are truncated (not rejected with 400) to keep the partial-success contract intact.
- **DynamoDB exceptions:** any `ClientError` or `Exception` at the row level is caught, converted to a `SandboxRowError`, and the loop continues. The function never raises to the HTTP layer from a row error.
- **Partial success response:** `ok=True` even when `len(errors) > 0`. The caller inspects `errors` to understand failures. HTTP status is always 200 on partial success. HTTP 500 is returned only for unexpected exceptions outside the per-row try/except (e.g. DynamoDB table unreachable).

### 5.4 `user_sub` generation

When `SandboxCustomerIn.user_sub` is absent or `None`, the service generates `user_sub = f"customer_{secrets.token_hex(6)}"` (12 hex chars). For comparison, KYC case IDs at `kyc_cases.py:136` use `f"kyc_{uuid.uuid4().hex[:12]}"` — both yield 12 hex chars but KYC uses UUID hex while PLT-004 uses `secrets.token_hex`. Either approach is fine; `secrets.token_hex` is slightly more cryptographically direct. The generated value is returned on the response; callers use it for subsequent `accounts[]` and `transactions[]` rows in the same payload. Callers that supply their own `user_sub` values (e.g. `"sandbox_alice"`) get exactly what they pass.

### 5.5 `source` field

All seeded rows carry `source="sandbox_import"` in the DDB item. For `T.users` rows this is an extra attribute on the item. For ledger rows it is passed via `extra={"source": "sandbox_import"}` to `new_ledger_entry` (`billing_shared.py:255-257 if extra: item.update(extra)`). This allows downstream queries to identify and purge sandbox data without scanning all rows.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 parity

The PLT cross-cutting constraints (`OBP_PLATFORM_TICKETS.md:53-57`) explicitly carve out PLT-004: *"SECOPS-007 dev/prod parity. No `if S.dev_mode:` branch in any new code path **except** PLT-004, whose sandbox-import endpoint is explicitly dev/flag-gated per the OBP sandbox model (the gate is the feature, not an environment shortcut) and the writes go through the same `T.*` handles in dev and (if ever enabled) prod."*

Concretely: `_write_customer`, `_write_account`, and `_write_transaction` contain no `if S.dev_mode:` branches. They call the same `T.users`, `T.profile`, `T.billing` handles and the same `billing_shared` primitives that the rest of the platform uses in both environments. The flag gate controls access, not the code path.

### 7.2 Money-safety

**No double-charge path.** The accounts writer uses `apply_wallet_delta` (billing_shared.py:185) for positive deltas. This is a simple credit — no payment provider call, no Stripe charge, no fraud gate. This is correct because sandbox seeding is administrative data setup, not a real payment. The `_fraud_gate` (`app/routers/billing.py:118`) and `settle_or_reverse_ledger` (`billing_shared.py:262`) are NOT involved: there is no pending charge to settle or reverse.

**No wallet overdraft from transaction imports.** Transaction rows are written as bare ledger entries via `new_ledger_entry` + `T.billing.put_item`. They do NOT call `apply_wallet_delta`, so they cannot underdraft the wallet. This mirrors `billing_shared.new_ledger_entry`'s design — it records the accounting entry without moving the balance. Balance and ledger are kept independent in the sandbox import, consistent with the existing `billing.py:1309` adjustment path.

**`ledger_date` always present.** By routing every transaction through `new_ledger_entry` (`billing_shared.py:224,253`), the `ledger_date` field is always populated. This is essential: seeded transactions will appear correctly in the `GSI_LEDGER_DATE` queries used by `app/services/platform_financial_dashboard.py` (CLAUDE.md FIN-013 / GAP-0202 note).

**No SCA gate.** Sandbox import is an admin-authenticated bulk-write of test data, not a payment initiation. There is no money leaving the platform — the admin is seeding balances into fictional test accounts. SCA gating is appropriate for `Transaction Requests` (OBP Tier-1, planned separately), not for admin data seeding.

### 7.3 Security

**Auth:** `_require_admin_user` enforces the `S.filemgr_admin_users` allowlist (admin_usage.py:35). A non-admin caller receives HTTP 403 before the flag gate is evaluated.

**404 on flag-off:** HTTP 404 (not 403) is returned when `not (S.sandbox_import_enabled and S.dev_mode)`. This prevents endpoint enumeration: an unauthenticated caller scanning paths cannot distinguish the sandbox endpoint from a genuinely absent path.

**No API key exemption.** `POST /v1/admin/sandbox/data-import` is NOT added to `API_KEY_ROUTE_EXEMPTIONS` (`app/services/api_key_route_scope_registry.py:70`). It is an authenticated, admin-only, cookie-session endpoint. If a caller uses Bearer / API-key auth, the standard `_require_admin_user` check still applies.

**`source` tagging.** All seeded rows carry `source="sandbox_import"`. Operators can identify and purge test data without affecting real records.

## 8. Backward Compatibility & Migration

### 8.1 No schema change

All three tables (`users`, `profiles`, `billing`) already exist with their current key schemas and GSI definitions. No `UpdateTable` is needed. No DynamoDB migration is required.

### 8.2 Additive `source` attribute

The `source="sandbox_import"` attribute on seeded rows is additive — existing rows have no `source` attribute; seeded rows do. No existing query filters on `source`, so no existing path is affected.

### 8.3 `scripts/local-ddb-init.py` — no change

No new `TableDef` entry is needed. The existing `billing` table `TableDef` (`local-ddb-init.py:67-77`) already declares the `GSI_LEDGER_DATE` index. The `users` and `profiles` tables already exist at `local-ddb-init.py:50-54,97`.

### 8.4 Router registration guard

The `if S.sandbox_import_enabled: app.include_router(sandbox_router)` guard in `app/main.py` means the new router module is never imported unless the flag is on. There is no risk of import-time side effects changing existing behaviour.

### 8.5 Flag default — off

`SANDBOX_IMPORT_ENABLED` defaults to `"0"`. Any existing deployment that does not set this env var is unaffected. CI and production deploys that do not set the flag experience no change to any endpoint, no change to any DDB table, and no change to any middleware.

## 10. Open Questions / Assumptions

1. **`_require_admin_user` import source.** Currently defined locally in `app/routers/admin_usage.py:35`. PLT-004 can import it from there directly (`from app.routers.admin_usage import _require_admin_user`) or it can be promoted to `app/auth/deps.py`. The latter is cleaner but is a scope change; the former is simpler and consistent with how PLT-002 uses the same dependency.

2. **Wallet double-credit on re-import.** The `apply_wallet_delta` is purely additive: re-importing an `accounts[]` row increments the wallet rather than setting it to the specified balance. A `upsert-to-exact-value` semantic would require a new `set_wallet_balance_exact` helper, which is out of scope. Callers should be aware of this and clear sandbox data with a `just restart` before re-importing.

3. **No purge / rollback endpoint.** The OBP sandbox API does not include a data-delete endpoint; neither does this ticket. Sandbox data is cleared by `just restart` (wipe + re-seed). A future `DELETE /v1/admin/sandbox/data` that removes rows tagged `source="sandbox_import"` is deferred.

4. **`profiles` table vs. `T.profile` field name.** The DynamoDB table name is `"profiles"` (`scripts/local-ddb-init.py:97`, `S.profile_table_name` default `"profiles"`), but the `T` struct field is `T.profile` (`app/core/tables.py:92`). This mismatch is an existing platform convention; PLT-004 uses `T.profile` everywhere.

5. **Schema for `users` row.** The `users` table has no sort key; the PK is `user_sub` alone. Accordingly `_write_customer` issues `T.users.put_item(Item={user_sub, email, ...})` with no `sk`. This is confirmed by `local-ddb-init.py:50-54` and `rootctl.py:718`.

6. **Transactions section does not adjust wallet balance.** This is an explicit design decision: ledger rows record accounting history; wallet balance is a separate WALLET row. Operators wishing to seed a user with a specific balance use the `accounts[]` section; the `transactions[]` section is for ledger history only. This matches the existing `billing_shared` architecture.

7. **`users` table `email` uniqueness.** The `users` table has no GSI on `email`; there is no uniqueness constraint on email at the DynamoDB level. A re-import with a different `user_sub` but the same `email` will succeed silently. This is consistent with `local-ddb-seed.py` and is acceptable for a sandbox tool.
