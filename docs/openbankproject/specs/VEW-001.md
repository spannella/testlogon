# VEW-001 — Account View entity — DDB model, field-grant catalog, view CRUD

**Ticket prefix**: VEW | **Priority**: P1 (foundation) | **Estimate**: 3 days
**Source**: `docs/openbankproject/OBP_VIEWS_ENTITLEMENTS_TICKETS.md` §VEW-001
**Flag**: `account_views_enabled` (env `ACCOUNT_VIEWS_ENABLED`, default OFF)

---

## 1. Summary & Goal

VEW-001 introduces the **View entity**: a named, owner-defined template of field-level visibility over a financial resource. A View declares a boolean grant-map over a catalogue of standardized OBP-style `can_see_*` / `can_add_*` field keys, four canonical presets (`owner` / `accountant` / `auditor` / `public`), and auto-provision of the immutable `owner` system alias. It is a pure definition layer — no access is granted to any party until VEW-002 attaches grantees.

The Open Bank Project's signature primitive is the View: a named, field-level data-sharing delegation. testlogon has a module-coarse analogue in `app/services/delegates.py` (`VALID_PERMISSIONS` set, `PERMISSION_PRESETS` dict) but no per-field granularity over financial resources. VEW-001 generalizes that grant/revoke pattern to per-field precision over the wallet/ledger/payout-destination resources exposed by `app/services/billing_shared.py` and `app/services/creator_payouts.py`.

Goals for this ticket:

1. Define and register the `account_views` DynamoDB single-table with two GSIs.
2. Add `T.account_views` and two settings keys to the existing infrastructure.
3. Implement `app/services/account_views.py` with the full View CRUD surface.
4. Implement `app/routers/account_views.py` with six REST endpoints, conditionally registered in `app/main.py`.
5. Add Pydantic models (`ViewGrantsMatrix`, `ViewCreateIn`, `ViewUpdateIn`, `ViewOut`, `ViewGrantCatalogOut`) to `app/models.py`.

VEW-002 (grant/revoke + public link), VEW-003 (projection enforcement), VEW-004 (entitlement-request queue), and VEW-005 (tables + wiring + integration tests) all build on this ticket.

## 2. Context & Current State

### 2.1 Existing delegation pattern (the template to extend, not fork)

`app/services/delegates.py` is the canonical grant-management primitive in this codebase. Key lines:

- **`VALID_PERMISSIONS`** (`delegates.py:20-28`): a flat `set[str]` of whole-feature actions (`chat_read`, `feed_post`, …). VEW-001 introduces the analogous `VIEW_FIELD_GRANTS: set[str]` for per-field boolean grants over financial resources.
- **`PERMISSION_PRESETS`** (`delegates.py:30-54`): a `dict[str, {label, permissions: list[str]}]` of named preset combinations — note the inner key is `permissions` (a list), not `grants`. VEW-001 mirrors the structure as `VIEW_PRESETS: dict[str, {label, grants: dict[str,bool]}]`; the inner key differs by design because VEW-001 uses a boolean map rather than a flat permission list.
- **`add_delegate`** (`delegates.py:63-110`): validates permissions (`_validate_permissions`, `:353`), enforces the self-grant guard (`_require_not_self`, `:359`), enforces a per-owner limit (`_enforce_delegate_limit`, `:370`), writes `pk=CREATOR#{creator_id}`, `sk=DELEGATE#{delegate_id}`, and writes an in-table audit row via `_write_audit` (`:386-409`). Note: `add_delegate` also calls `_require_not_already_delegate` (`:364`) to prevent duplicate rows — VEW-001 does not need this guard because each `create_view` always generates a new `uuid4().hex` view_id. VEW-001 mirrors this for View rows with `pk=RESOURCE#{resource_type}#{resource_id}`, `sk=VIEW#{view_id}`.
- **`_detect_preset`** (`delegates.py:378-383`): labels a permission set that exactly matches a known preset. VEW-001 replicates this for the grant-map.
- **`list_delegates`** (`delegates.py:207-213`): `Key("pk").eq(...) & Key("sk").begins_with("DELEGATE#")`. VEW-001 uses the same `begins_with("VIEW#")` pattern.
- **`list_managed_creators`** (`delegates.py:216-224`): reverse GSI1 lookup (`GSI1PK=DELEGATE#{delegate_id}`). VEW-001 has a `by-owner` GSI1 (`GSI1PK=OWNER#{owner_sub}`) for listing views across resources.
- **In-table audit rows**: `pk=CREATOR#{creator_id}`, `sk=AUDIT#{ts}#{event_id}` (`delegates.py:395`). VEW-001 writes `pk=RESOURCE#{resource_type}#{resource_id}`, `sk=AUDIT#{ts}#{event_id}` for resource-scoped history.

## 3. Data Model

### 3.1 DynamoDB table: `account_views` (single-table)

This table is single-table by design. View definition rows (`sk=VIEW#{view_id}`) and in-table audit rows (`sk=AUDIT#{ts}#{event_id}`) share the same resource partition. VEW-002 will add VIEWGRANT rows (`sk=VIEWGRANT#{grantee_sub}#{view_id}`) to the same partition, so all View-related data for a resource lives in one place.

**Table coordinates**

| Setting key | Env var | Default |
|---|---|---|
| `S.account_views_table_name` | `ACCOUNT_VIEWS_TABLE` | `"account_views"` |
| `S.account_views_max_per_resource` | `ACCOUNT_VIEWS_MAX_PER_RESOURCE` | `25` |

**Primary key**

| Attribute | Type | Value pattern |
|---|---|---|
| `pk` (hash) | S | `RESOURCE#{resource_type}#{resource_id}` |
| `sk` (range) | S | `VIEW#{view_id}` for view rows; `AUDIT#{ts:013d}#{event_id}` for audit rows |

**View definition row — full attribute set**

| Attribute | Type | Notes |
|---|---|---|
| `pk` | S | `RESOURCE#{resource_type}#{resource_id}` |
| `sk` | S | `VIEW#{view_id}` |
| `view_id` | S | `uuid4().hex` |
| `resource_type` | S | `"wallet"` / `"ledger_account"` / `"payout_destination"` — allowlist |
| `resource_id` | S | Opaque owner-scoped identifier |
| `owner_sub` | S | The user who owns the underlying resource |
| `name` | S | Human-readable label |

## 5. Detailed Behavior & Edge Cases

### 5.1 Grant validation

`_validate_grants` iterates `grants.keys()` and computes `invalid = set(grants) - VIEW_FIELD_GRANTS`. Any unknown key raises `HTTPException(400, f"Unknown grant keys: {sorted(invalid)}")`. A grant map that is empty (all `False`) is valid — it is a read-only observer view with no fields. Values that are not boolean are rejected by Pydantic before reaching the service.

### 5.2 Resource-type allowlist

`_assert_owns_resource` checks `resource_type` against the hardcoded allowlist `{"wallet", "ledger_account", "payout_destination"}`. An unknown value raises `HTTPException(400, "Unknown resource_type")` before any DDB I/O. New resource types may be added to the allowlist in future tickets; no schema migration is required since the type is stored as a string.

### 5.3 Ownership guard

For `resource_type="wallet"` and `resource_type="ledger_account"`, ownership is structural: the caller's `user_sub` must equal `resource_id`. For `resource_type="payout_destination"`, a DDB `get_item(Key={"payout_id": resource_id})` on `T.creator_payouts` is performed (hash-key-only lookup — `creator_payouts` has no sort key); if the item is absent or `item["user_id"] != owner_sub`, the guard raises `403`. The guard runs on every create, update, and delete call — not just create — so a compromised user cannot modify another user's views.

### 5.4 Per-resource view limit

`_enforce_view_limit` calls `list_views(resource_type, resource_id)` and counts the result (including any system-alias rows). If `count >= S.account_views_max_per_resource` (default 25), it raises `HTTPException(400, "View limit reached for this resource")`. The limit is enforced before `put_item`. Because `list_views` is a prefix query, this is an O(limit) scan, acceptable for the small per-resource view counts expected in practice.

### 5.5 `ensure_owner_view` idempotency

`ensure_owner_view` performs a conditional `put_item` with `ConditionExpression="attribute_not_exists(pk)"` on the specific `sk=VIEW#{OWNER_VIEW_CONSTANT_ID}` key. The constant ID is `"owner"` (a deterministic, non-uuid key so the same conditional put is always idempotent across the resource's lifetime). If the condition fails (the row already exists), the `ConditionalCheckFailedException` is caught and the function does a `get_item` to return the existing row — no double-create, no error to the caller.

The `owner` view's `is_system_alias=True` flag is written at creation. `update_view` and `delete_view` call `_require_not_system_alias` early, raising `409 Conflict` with `{"code": "system_view_immutable"}` before any mutation.

### 5.6 `ensure_owner_view` call site

`create_view` does NOT auto-call `ensure_owner_view`. The router's `POST /ui/views/{resource_type}/{resource_id}` handler calls `ensure_owner_view` first (idempotent), then calls `create_view` for the user-specified view. This guarantees every resource that has at least one user-created view also has its system `owner` view — without requiring a separate explicit call.

### 5.7 Preset detection on create and update

After any grant-map write, `_detect_preset(grants_dict)` iterates `VIEW_PRESETS` and returns the matching key if `set(grants_dict.keys() with value True)` exactly equals the preset's truthy-key set. On create, `preset` in the body is advisory — it is ignored if the supplied `grants` do not match. On update, `preset` is recomputed from the new grants map and stored.

### 5.8 Delete cascade (stub for VEW-002)

`delete_view` in VEW-001 deletes only the `VIEW#{view_id}` row. A TODO comment marks the cascade-delete of `VIEWGRANT#{grantee}#{view_id}` rows, which will be implemented in VEW-002 when those rows exist. The audit event `account_view.deleted` is emitted regardless.

### 5.9 `list_views_by_owner` pagination

The `by-owner` GSI may have many rows for a prolific owner. `list_views_by_owner` uses `ScanIndexForward=False` (newest-first) with `Limit=limit` and `ExclusiveStartKey=decode_cursor(cursor)`. The `LastEvaluatedKey` from each page is encoded with `encode_cursor(...)` (from `app/core/cursor.py:94`) and returned as `next_cursor`. Because the GSI may include audit rows from other partitions (unlikely with this key structure, but safe), callers must filter for `sk.startswith("VIEW#")`.

### 5.10 `GET /ui/views/{resource_type}/{resource_id}` owner enforcement

The `list_views` endpoint asserts that the caller's `user_sub` owns the resource before returning results. Specifically, `_assert_owns_resource(caller.user_sub, resource_type, resource_id)` is called; a non-owner gets `403`. A grantee who wants to see views they can access uses VEW-002's `/shared-with-me` endpoint instead.

### 5.11 `GET /ui/views/{resource_type}/{resource_id}/{view_id}` access

In VEW-001, this endpoint is owner-only. VEW-002 will extend it: active grantees will be able to retrieve the view definition (to understand what fields they are granted). The ownership check here is `_require_owner(caller.user_sub, view_item)` — a simple dict comparison that VEW-002 will wrap in an `or resolve_active_grant(...)` check.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

**SECOPS-007 dev/prod parity**: all persistence uses `T.account_views` (`_FloatSafeTable`) backed by DynamoDB Local (port 8001) in dev and real DynamoDB in prod. There are zero `if S.dev_mode:` branches in `app/services/account_views.py` or `app/routers/account_views.py`. The `ensure_owner_view` conditional `put_item` behaves identically on both DynamoDB Local and real DynamoDB (moto also correctly implements `attribute_not_exists` conditionals).

**Idempotency**: `ensure_owner_view` is fully idempotent via conditional put + get fallback. `create_view` is not idempotent by design (it always creates a new `view_id`), but the router does not expose a bulk-create path, and the limit guard bounds the total count. `update_view` is idempotent for the same field values — it will write the same DDB item if called twice with identical input.

**No money movement in VEW-001**: this ticket introduces only a metadata/delegation layer. No calls to `apply_wallet_delta`, `new_ledger_entry`, `settle_or_reverse_ledger`, or any billing primitive. The resource-ownership guard reads from `T.creator_payouts` for `payout_destination` type but writes nothing. Money-safety constraints (fraud gate, SCA, ledger idempotency) are relevant to VEW-003's read path and TXR-004's execution path, not this ticket.

**Field-level security**: `VIEW_FIELD_GRANTS` is a closed allowlist. Any grant key outside this set is rejected with `400` before reaching DDB. This prevents a caller from inventing novel grant keys that a future projection (VEW-003) might misinterpret. The allowlist is a module-level constant, not user-configurable.

**Ownership before every write**: `_assert_owns_resource` and `_require_owner` run on every mutating operation. There is no path through the service that writes a View row without verifying that the calling user owns the underlying financial resource.

**Audit completeness**: every call to `create_view`, `update_view`, `delete_view`, and `ensure_owner_view` emits both a canonical `audit_event("account_view.*", owner_sub, ...)` write to `T.alerts` and a local `_write_audit(...)` row in the `account_views` table. The in-table audit row is queryable by resource partition for resource-scoped history (VEW-002 adds a get-history endpoint). Both writes are best-effort — a failure in `_write_audit` is logged but never raises, so a failing audit never blocks the primary operation.

## 8. Backward Compatibility & Migration

VEW-001 is purely additive. No existing table, router, service, or model is modified. The new `account_views` table is created alongside existing tables by `scripts/local-ddb-init.py`; `just restart` recreates all tables including the new one.

**Zero-downtime**: because the router is conditionally registered, deploying the code with `ACCOUNT_VIEWS_ENABLED=false` (the default) leaves all existing behavior byte-for-byte unchanged. The feature can be enabled by flipping the env var and restarting the backend.

**No DDB schema migration**: the table is new; no existing rows need transformation. Future additions (VIEWGRANT rows in VEW-002) are additive to the same partition and do not require a table update.

**`T.account_views` handle**: adding a new field to the `Tables` dataclass is backward-compatible; Python dataclasses with explicit field defaults do not affect existing field access. The `_safe_table(S.account_views_table_name)` call at singleton initialization will raise if the env var resolves to an empty string and the DDB endpoint is unreachable, but the existing startup behavior already handles missing tables gracefully via `local-ddb-init.py`.

## 10. Open Questions / Assumptions

1. **`ledger_account` vs `wallet` distinction**: the current billing model has one wallet per user and a set of ledger rows. This spec treats `wallet` and `ledger_account` as separate resource types for OBP parity (OBP distinguishes account balance from transaction list), but both map to `resource_id=owner_sub`. If a future multi-account model is added (Tier-2 OBP ticket ACC-001), the `resource_id` for `ledger_account` would become an explicit account identifier. Assumption for VEW-001: `resource_id=owner_sub` for both.

2. **`payout_destination` masked vs full**: the `can_see_payout_destination_masked` grant exposes only the masked destination (last 4 digits, routing prefix). A future grant key `can_see_payout_destination_full` could expose the full routing number, but this is deferred pending a security review. Assumption: masked only for VEW-001.

3. **Cross-resource view limit**: `S.account_views_max_per_resource` limits views per resource partition. There is no current cross-resource limit per user. If a user owns many payout destinations, they could create `max_per_resource` views per destination. A global per-user limit could be added in a future ticket; deferred.

4. **`metadata_visibility` values**: only `"counterparty_blur"` is defined in this ticket. Additional visibility modes (e.g., `"amount_blur"`) would require adding grant keys and projection logic in VEW-003. Assumption: only `counterparty_blur` in VEW-001/003.

5. **Admin-readable views**: should ROOT/ADMIN be able to read any user's views for support purposes? Currently the router requires the caller to be the resource owner. An admin read-path could be added as a separate admin endpoint in VEW-005 or a later ticket. Assumption: owner-only for VEW-001.
