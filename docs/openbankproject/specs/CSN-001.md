# CSN-001 — PSD2 AIS consent — model, table, flag, grant/status/list-by-consumer/revoke

**Ticket type**: Feature
**Priority**: P2
**Estimate**: 3 days
**Status**: Unimplemented

---

## 1. Summary & Goal

CSN-001 introduces the foundational PSD2 Account Information Service (AIS) consent record into testlogon. An AIS consent is a durable, owner-scoped grant through which a resource owner authorizes a named third-party consumer application to read specific account views for a bounded time window.

This ticket delivers:
- The `consents` DynamoDB table with two GSIs: `ByConsumer` (for the "list-by-consumer" OBP surface) and `ByStatusExpiry` (for the expiry sweep);
- Pydantic models `ConsentCreateIn` and `ConsentOut` in `app/models.py`;
- The service module `app/services/psd2_consents.py` covering create, get, list (by owner and by consumer), revoke, validity check, and background expiry sweep;
- The router `app/routers/psd2_consents.py` exposing five endpoints, registered in `app/main.py` conditionally on `S.psd2_consents_enabled`;
- A startup loop `start_consent_expiry_task` that flips ACCEPTED consents past `valid_until` to EXPIRED and audits them.

The feature is strictly additive and **default OFF** (`PSD2_CONSENTS_ENABLED=false`). When the flag is off the router is not registered, the table is not read, and no startup task runs — the platform is byte-for-byte unchanged.

CSN-002 (SCA gate + PIS consent + consent-scoped rate limit) builds directly on top of this ticket. No money movement is introduced here; PIS consent is CSN-002's scope.

## 3. Data Model

### 3.1 DynamoDB table: `consents`

Add one `TableDef` to `scripts/local-ddb-init.py` (alongside the existing entries at lines 42+):

```python
TableDef(
    _resolve_table_name(S.consents_table_name, "consents"),
    "owner_sub",           # PK — String
    "consent_id",          # SK — String  (csn_{uuid4().hex})
    gsi=[
        {
            "index_name": S.consents_consumer_index,   # "ByConsumer"
            "partition_key": "consumer_ref",            # String
            "sort_key": "created_at",                  # Number
        },
        {
            "index_name": S.consents_status_index,     # "ByStatusExpiry"
            "partition_key": "status",                  # String
            "sort_key": "valid_until",                 # Number
        },
    ],
    attr_types={"created_at": "N", "valid_until": "N"},
)
```

**The `attr_types` declaration is non-negotiable**: both GSI sort keys are integer Unix timestamps. Omitting it stores them as String, causing `ValidationException` on any numeric GSI query — the repo's most common runtime mistake (CLAUDE.md "DynamoDB numeric GSI sort keys").

### 4.2 Service (`app/services/psd2_consents.py`)

```python
def create_consent(owner_sub: str, body: ConsentCreateIn, req: Request) -> ConsentOut
def get_consent(owner_sub: str, consent_id: str) -> Optional[ConsentOut]
def list_consents_for_owner(
    owner_sub: str, *, status: Optional[str] = None,
    limit: int = 20, cursor: Optional[str] = None
) -> ConsentListOut
def list_consents_for_consumer(
    consumer_ref: str, *, status: Optional[str] = None,
    limit: int = 20, cursor: Optional[str] = None
) -> ConsentListOut
def revoke_consent(owner_sub: str, consent_id: str) -> ConsentOut
def is_consent_valid(owner_sub: str, consent_id: str) -> tuple[bool, Optional[dict]]
def expire_due_consents() -> int          # returns count of transitioned rows
async def start_consent_expiry_task()     # startup loop
```

**`create_consent` logic**:

1. Validate `body.account_refs` is non-empty → `HTTP 400 detail="account_refs must not be empty"`.
2. Validate every element of `body.view_refs` is in `VALID_VIEW_REFS` → `HTTP 400 detail="invalid view_ref: {val}"`.
3. Compute `valid_until`: if `body.valid_until` is provided, cap at `now_ts() + S.psd2_consent_max_ttl_days * 86400` (clamp, not 400, per security policy — silently truncates overly long grants); if not provided, use `now_ts() + S.psd2_consent_default_ttl_days * 86400`.
4. Generate `consent_id = "csn_" + uuid.uuid4().hex`.
5. Write item via `T.consents.put_item(Item=with_ttl({...}, ttl_epoch=valid_until + 86400 * 7))` with `status="INITIATED"`.
6. Call `audit_event("consent.created", owner_sub, req, consent_id=consent_id, consumer_ref=body.consumer_ref)`.
7. Return `ConsentOut`.

**`revoke_consent` logic (conditional update — status is the lock)**:

```python
T.consents.update_item(
    Key={"owner_sub": owner_sub, "consent_id": consent_id},
    UpdateExpression="SET #st = :r, revoked_at = :now, updated_at = :now",
    ExpressionAttributeNames={"#st": "status"},
    ExpressionAttributeValues={
        ":r": "REVOKED", ":now": now_ts(),
        ":i": "INITIATED", ":a": "ACCEPTED",
    },
    ConditionExpression="#st IN (:i, :a)",
)
```

On `ConditionalCheckFailedException`: load the item; if not found → `HTTP 404`; if found and `status in ("REVOKED","EXPIRED")` → `HTTP 409 detail="consent_already_terminal"`. This pattern mirrors `tickets._conditional_update_meta` (`app/services/tickets.py:723-788`). Always audit `consent.revoked` on success.

**`is_consent_valid`** — used by CSN-002's enforcement:

```python
def is_consent_valid(owner_sub: str, consent_id: str) -> tuple[bool, Optional[dict]]:
    # PK+SK lookup: Key={"owner_sub": owner_sub, "consent_id": consent_id}
    # Returns (True, item) only when status=="ACCEPTED" and valid_until > now_ts().
    # owner_sub is REQUIRED: neither existing GSI (ByConsumer keyed on consumer_ref,
    # ByStatusExpiry keyed on status) supports lookup by consent_id alone without a
    # full table scan. CSN-002 callers must supply owner_sub from the session context.
    ...
    return (item["status"] == "ACCEPTED" and int(item["valid_until"]) > now_ts(), item)
```

> **Correction (DESIGN BUG FIXED)**: The original spec defined `is_consent_valid(consent_id: str)` (one parameter) and claimed it "performs a GSI lookup" to resolve the item without knowing `owner_sub`. This is **impossible** with the table as defined: `ByConsumer` is partitioned by `consumer_ref`; `ByStatusExpiry` is partitioned by `status`. Neither GSI has `consent_id` as a key attribute. The only way to retrieve an item by `consent_id` alone is a full-table scan (O(N) — unacceptable) or a new GSI on `consent_id` (not defined in §3.1). CSN-002's service functions already supply both `owner_sub` and `consent_id` (see CSN-002.md lines 78-79, 182-212), confirming the PK+SK access pattern is the right approach. The function signature is corrected to `(owner_sub: str, consent_id: str)` and the misleading GSI-lookup comment is removed.

**`expire_due_consents`**:

```python
def expire_due_consents() -> int:
    now = now_ts()
    resp = T.consents.query(
        IndexName=S.consents_status_index,
        KeyConditionExpression=Key("status").eq("ACCEPTED") & Key("valid_until").lt(now),
        Limit=100,
    )
    count = 0
    for item in resp.get("Items", []):
        try:
            T.consents.update_item(
                Key={"owner_sub": item["owner_sub"], "consent_id": item["consent_id"]},
                UpdateExpression="SET #st = :e, updated_at = :now",
                ExpressionAttributeNames={"#st": "status"},
                ExpressionAttributeValues={":e": "EXPIRED", ":now": now, ":a": "ACCEPTED"},
                ConditionExpression="#st = :a",
            )
            audit_event("consent.expired", item["owner_sub"], None,
                        consent_id=item["consent_id"])
            count += 1
        except ClientError as exc:
            if exc.response["Error"]["Code"] != "ConditionalCheckFailedException":
                raise
    # Loop over LastEvaluatedKey if present (DDB FilterExpression gotcha does not
    # apply here — we query by status=ACCEPTED, no filter on a sparse attr).
    return count
```

The native DynamoDB TTL is **not** used for the status transition (it would delete the row without leaving an auditable `EXPIRED` tombstone). The TTL set on creation (`valid_until + 7 days`) eventually reaps the row after expiry, but the status flip happens in the sweep.

**`start_consent_expiry_task`** (async startup loop, mirrors `start_k8s_ttl_checker_task`):

```python
async def start_consent_expiry_task():
    if not S.psd2_consents_enabled:
        return
    import asyncio
    while True:
        try:
            expire_due_consents()
        except Exception:
            pass
        await asyncio.sleep(S.psd2_consent_expiry_poll_interval)
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Status machine

```
INITIATED  ──(owner accepts via CSN-002 SCA)──▶  ACCEPTED
    │                                                │
    │  (owner revokes)                              │  (owner revokes)
    ▼                                                ▼
 REVOKED ◀──────────────────────────────────── REVOKED

ACCEPTED ──(valid_until < now_ts(), sweep)──▶ EXPIRED
```

Terminal statuses: `REVOKED` and `EXPIRED`. A conditional update to REVOKED only succeeds from `INITIATED` or `ACCEPTED` (`ConditionExpression="#st IN (:i, :a)"`). A second revoke of a terminal consent returns `HTTP 409 consent_already_terminal`. There is no transition from `EXPIRED` back to any live status; a new consent must be created.

In CSN-001 (without CSN-002 wired), creation lands directly in `INITIATED`. `is_consent_valid` returns `False` for `INITIATED` — a consumer cannot use a consent until the SCA gate (CSN-002) transitions it to `ACCEPTED`. This means all AIS data reads gated on `is_consent_valid` will return `403` until CSN-002 is deployed and the owner completes SCA.

### 5.2 `valid_until` clamping

If `body.valid_until` exceeds `now_ts() + S.psd2_consent_max_ttl_days * 86400`, it is silently clamped to the maximum. This is preferable to a `400` because a legitimate consumer app requesting "the longest allowed grant" should not fail; it should receive the platform maximum. The actual `valid_until` stored is returned in `ConsentOut` so the consumer can observe the clamped value.

### 5.3 `account_refs` semantics

`account_refs` are opaque strings in CSN-001. When the ACC cluster (bank/account entities) is deployed, these will be validated against `T.accounts`. Until then they are persisted as-is. An empty list is always rejected with `HTTP 400`.

### 5.4 `view_refs` semantics

`view_refs` are validated against the static set `VALID_VIEW_REFS = {"owner","accountant","auditor","public"}`. When the VIEWS cluster is deployed this set will be replaced by a dynamic lookup against the views registry. Any `view_ref` outside the static set → `HTTP 400 detail="invalid view_ref: {val}"`. An empty list is allowed; it defaults to `["owner"]` before write.

### 5.5 `consumer_ref` validation

`consumer_ref` must be a non-empty string of at most 256 characters. No further structural validation is applied in CSN-001. When OAU is deployed, a validation step will check that `consumer_ref` exists in `oauth_consumers` and is enabled. Until then, an unknown `consumer_ref` is accepted (the consent is created; data access enforcement happens at the AIS read layer, not at grant time).

### 5.6 `list_consents_for_consumer` isolation

The `ByConsumer` GSI partition key is `consumer_ref`. Querying with `Key("consumer_ref").eq(consumer_ref)` returns only rows whose `consumer_ref` matches exactly. A consumer querying for their own consents can never see another consumer's rows because the GSI partition isolates them. The `?status=` filter is applied via a `FilterExpression` on the GSI query result (not a separate scan). DDB's `FilterExpression` does not reduce page size (CLAUDE.md gotcha), so the implementation loops `LastEvaluatedKey` until the page is full or the index is exhausted.

### 5.7 Expiry sweep idempotency

The sweep uses a conditional update `ConditionExpression="#st = :a"` (status must still be `ACCEPTED`). If two sweep workers race (or the same consent is processed twice), the second write throws `ConditionalCheckFailedException`, which is silently caught. The audit event fires exactly once (on the successful write). This is intentional: an `EXPIRED` consent is stable.

### 5.8 Error catalog

| Condition | HTTP status | `detail` code |
|-----------|-------------|---------------|
| `account_refs` empty | 400 | `"account_refs must not be empty"` |
| Invalid `view_ref` value | 400 | `"invalid view_ref: {val}"` |
| `consent_id` not found or belongs to another owner | 404 | `"consent not found"` |
| Revoke of terminal consent | 409 | `"consent_already_terminal"` |
| Flag off → router not registered | 404 | FastAPI default (route not found) |
| Non-root caller on `/by-consumer/` | 403 | `"Root access required"` (from `require_root_session`) |

**Flag behavior when off**: The `if _S.psd2_consents_enabled:` guard in `create_app()` means:
- The `psd2_consents` router is never registered → all `/ui/consents*` paths return `404`.
- `start_consent_expiry_task` is never added to the event loop.
- `T.consents` is still initialized as a table handle object in `tables.py` (because `tables.py` is unconditionally imported) but no code path calls it when the flag is off.

To avoid even the table-handle initialization when the flag is off, the `T.consents` attribute can be made a `@property` on a lazy class, but this adds complexity for minimal benefit. The simpler approach — always initialize, never call — is consistent with how every other flag-gated feature in the codebase handles its table handle.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 parity

There is no `if S.dev_mode:` branch anywhere in `psd2_consents.py` or its router. All DynamoDB I/O goes through the frozen `T.consents` handle, which points to DynamoDB Local (port 8001) in dev and real DynamoDB in prod. The audit path (`alerts.audit_event`) writes to `T.alerts` in both environments identically. This is the same pattern used by all OBP tickets and enforced by CLAUDE.md ("No `if S.dev_mode:` business-logic branch in any CSN path").

### 7.2 Money-safety

CSN-001 is an AIS (read-only) consent ticket. **No money movement occurs.** There are no calls to `new_ledger_entry`, `apply_wallet_delta`, `settle_or_reverse_ledger`, or any Stripe/PayPal/CCBill SDK. This is by design: PIS (payment-initiation) consent and the TXR link is CSN-002's scope, and even there the consent itself never writes to the ledger — money moves exclusively through the TXR execution engine.

The absence of any billing-table write in this ticket is itself a safety property: a bug in the consent grant path cannot accidentally debit or credit a wallet.

### 7.3 Idempotency

`create_consent` generates a fresh `csn_*` ID on every call. It is intentionally non-idempotent: two calls with the same body create two separate consents. This matches PSD2 semantics (a consumer may hold multiple simultaneous grants to the same account). Callers that need idempotency at the application level should check `list_consents_for_consumer` before calling `create_consent`.

`revoke_consent` is idempotent at the semantic level: a second revoke of an already-revoked consent returns `409` (not an error that changes state). `expire_due_consents` is idempotent via the conditional update.

### 7.4 Owner-scoping

All service functions that operate on a single consent take `owner_sub` as the first argument and use it as the DDB partition key (`Key={"owner_sub": owner_sub, "consent_id": consent_id}`). A caller cannot read or modify another user's consent because the DDB key access pattern enforces ownership at the database layer, not only in application logic. This is the same pattern used by `api_keys.py`, `sessions.py`, and every other owner-scoped service.

### 7.5 `consent.id` prefix

Using `csn_` as the ID prefix (`csn_{uuid4().hex}`) makes log tracing and audit queries unambiguous. All IDs in the platform follow this convention (e.g. `m_` for messages, `INSTANCE#` for EC2 items, `txr_*` for TXR).

## 8. Backward Compatibility & Migration

### 8.1 Additive only

No existing table, model, endpoint, or service is modified. The `consents` table is new. The five new endpoints are new paths. The only changes to existing files are:
- `app/models.py`: add `ConsentCreateIn`, `ConsentOut`, `ConsentListOut` (additive).
- `app/core/settings.py`: add seven new settings fields with defaults (additive; frozen dataclass).
- `app/core/tables.py`: add `T.consents` handle (additive).
- `scripts/local-ddb-init.py`: add one `TableDef` entry (additive; creates a new table on next `just restart`).
- `app/main.py`: add the conditional `include_router` + `add_event_handler` block (additive; guarded by `if _S.psd2_consents_enabled`).

### 8.2 Table creation in dev

`just restart` calls `scripts/local-ddb-init.py`, which will create the `consents` table with both GSIs the first time after this spec is implemented. No manual migration is required in dev.

### 8.3 Table creation in prod

In production the `consents` table does not exist yet, so a one-time `CreateTable` call is needed before `PSD2_CONSENTS_ENABLED=true` is set. The recommended deploy sequence is:

1. Deploy the code with `PSD2_CONSENTS_ENABLED=false` (default).
2. Run the table-creation script (or a one-off Lambda/CLI) targeting real DynamoDB.
3. Verify the GSIs are `ACTIVE`.
4. Set `PSD2_CONSENTS_ENABLED=true` and deploy again (or set the env var in the running environment).

There is no backfill: the table starts empty and rows accumulate from the first POST.

## 10. Open Questions / Assumptions

1. **`valid_until` beyond max — clamp or reject?** This spec chooses silent clamping. If legal/compliance requirements demand the consumer receive an explicit error when their requested TTL is too long, change to `HTTP 400 detail="valid_until exceeds maximum allowed grant duration"`. This is surfaced as an open question for the security review.

2. **`consumer_ref` existence check**: CSN-001 accepts any non-empty string as `consumer_ref` (no OAU registry lookup yet). When OAU is deployed, `create_consent` should validate that `consumer_ref` exists in `oauth_consumers` and is `enabled=true`. Until then, a stale/invalid consumer ref creates a consent that will never be exercisable (harmless).

3. **Bulk-revoke on account deletion**: If a user deletes their account, should all their active consents be automatically revoked? The answer is almost certainly yes, but the account-deletion flow is out of scope for CSN-001. This is a follow-up dependency.

4. **`/by-consumer` auth model**: Currently gated by `require_root_session`. Once OAU is deployed, a consumer should be able to authenticate with its own `client_id`/`client_secret` and call this endpoint to list its own grants. This transition requires no change to the route signature — only the `Depends(...)` needs updating.

5. **Pagination correctness on `ByConsumer` GSI with `FilterExpression`**: The `?status=` filter applies a `FilterExpression` over the GSI result. If a consumer has many consents and most are in a different status, a DDB page may return 0 matching items before `LastEvaluatedKey` is exhausted. The implementation must loop until either `limit` items are collected or there is no more `LastEvaluatedKey`. Failing to do this would silently truncate results — the same gotcha documented in CLAUDE.md for sparse-attribute filter queries.
