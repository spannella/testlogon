## 1. Summary & Goal

PAY-005 closes the PAY cluster by adding the full regression-test suite and the typed
React frontend for the four backend surfaces introduced by PAY-001 through PAY-004:
counterparties/beneficiaries, standing orders, direct-debit mandates, and the FX rate
store. No new backend service logic is introduced here; every line of application code
being tested and surfaced already exists after PAY-001..004 land.

Goals:

1. **Four hermetic pytest modules** — one per backend surface — that run offline (no live
   stack, no real AWS, no real network) and prove the money-safety invariants that cannot
   be read off of types alone: single-emission idempotency, conditional `next_run_at`
   advance, mandate cap enforcement (no over-cap debit), integer FX math.
2. **Typed frontend API client** — `types.ts` additions + four endpoint files
   (`counterparties.ts`, `standingOrders.ts`, `mandates.ts`, `fx.ts`) using the existing
   `api/client.ts` axios wrapper.
3. **`PaymentsPage`** — a four-tab React page under `frontend/src/pages/payments/` (route
   `/payments`) that surfaces all four surfaces with React Query + React Hook Form + Zod;
   gated in `App.tsx` behind the frontend feature flag
   `VITE_PAYMENTS_COUNTERPARTIES_ENABLED` (default `false`).
4. **One E2E Playwright spec** `frontend/e2e/payments-counterparties.spec.ts` that covers
   the happy path of each surface end-to-end with the flag on.
5. **Documentation**: `docs/file-reference.md` updated; a `CLAUDE.md` Common Gotchas entry
   added for the PAY cluster.

## 5. Detailed Behavior & Edge Cases

### 5.1 Counterparty masking invariant

`CounterpartyCreateIn` accepts the full `iban` (e.g. `"GB82WEST12345698765432"`). The
service stores only `iban_last4 = iban[-4:]` in DynamoDB — the full string is discarded
at write time (mirrors `creator_payouts.py:681`). The `CounterpartyOut` model exposes
`iban_last4` only. Tests assert that the raw DDB item has no `iban` key and that
`CounterpartyOut.routing.iban_last4 == "5432"`.

A routing validation error (`scheme="IBAN"` supplied but no `iban` in the body) must
return `400` before any DDB write. The test for this calls the service function directly
and asserts a `ValueError` / `HTTPException(400)`.

### 5.2 Idempotency proof (standing orders + mandates)

The idempotency key `"{entity_id}#{occurrence_ts}"` is passed to `txn_requests.create_request`.
In tests, `create_request` is replaced by a `MagicMock` that records all calls. The test
drives `execute_due_standing_order` twice with the same `next_run_at` frozen value. The
first call succeeds; the second call is defeated by the conditional `update_item` (the
`next_run_at` has already advanced on the first successful call, so the
`ConditionExpression="next_run_at = :old_ts"` fails). The assert is therefore:

- `create_request.call_count == 1` (TXR was only invoked for the first occurrence).
- DDB item `runs_count == 1` (the second tick wrote nothing).

This mirrors the `claim_action` conditional-claim pattern (`scheduled_actions.py:377`)
and is the mechanical proof of money-safety constraint #2/#3 from the cross-cutting
constraints.

### 5.3 Mandate cap: over-cap emits nothing

For `test_over_cap_pull_emits_no_request_and_writes_nothing_to_billing`:

1. Patch `billing_shared.apply_wallet_delta`, `billing_shared.new_ledger_entry`,
   `billing_shared.settle_or_reverse_ledger` as `unittest.mock.MagicMock`.
2. Patch `txn_requests.create_request` as `MagicMock`.
3. Create a mandate with `max_amount_cents=1000`, `pulled_this_window_cents=0`.
4. Call `execute_mandate_pull(user_sub, mandate_id, pull_amount_cents=1500)`.
5. Assert: `create_request.call_count == 0`, `apply_wallet_delta.call_count == 0`,
   `new_ledger_entry.call_count == 0`, `settle_or_reverse_ledger.call_count == 0`.
6. Assert: mandate DDB item has an occurrence marker `skipped` or `exceeded`.

This is the mechanical proof of money-safety constraint #4.

### 5.4 FX integer math precision

The `convert` helper uses `rate_micros` (an integer stored in DynamoDB) to avoid
floating-point accumulation. PAY-004 §4 defines the canonical formula as:

```python
target_amount_cents = round(amount_cents * rate_micros) // 1_000_000
```

Because `amount_cents` and `rate_micros` are both integers, `round(int * int)` is a
no-op (the product is already an integer); the effective operation is pure integer
floor-division by 1,000,000.

The test uses a rate with significant decimal digits (e.g. `1.234567`) and an amount
where naive `float` multiplication would drift. The stored `rate_micros = 1_234_567`.
For `amount_cents = 100_000`:

```
100_000 × 1_234_567 = 123_456_700_000   (exact integer multiply, no float involved)
123_456_700_000 // 1_000_000 = 123_456  (integer floor-divide)
```

The test asserts `target_amount_cents == 123_456` (not `123_457` as naive
`round(100_000 × 1.234567)` gives due to IEEE-754 rounding of the `float` literal).
Confirm the formula is `// 1_000_000` (floor), not `round(... / 1_000_000)` (which
would give 123_457). Open question 4 in §10 documents both choices; whichever is
implemented must be consistent and have the test expected value adjusted accordingly.
This confirms that ledger-integer discipline (`billing_shared.py` always uses
`int(amount_cents)`) is maintained end-to-end.

### 5.5 Frontend: SCA pending state

When a standing-order tick or mandate pull results in a TXR with `status="PENDING"` (the
SCA threshold was crossed and TXR is holding the request for step-up verification), the
`PaymentsPage` must surface the SCA dialog rather than showing an error. The correct
behavior is to display the TXR-005 SCA challenge dialog (defined in
`OBP_TXN_REQUESTS_SCA_TICKETS.md`, TXR-005) — reuse that component, do not build a new
one. If TXR-005 has not landed, show a `"Payment pending — SCA verification required"`
inline message with a link to the Security page.

### 5.6 E2E: flag-off guard

The E2E spec must skip all sections when `PAYMENTS_COUNTERPARTIES_ENABLED` is not `"1"`
in the test environment. Use a `test.skip` conditional in `beforeAll`:

```typescript

  if (process.env.PAYMENTS_COUNTERPARTIES_ENABLED !== "1") {
    test.skip(true, "PAY flag off");
  }
});
```

Backend routes already return 404 when the flag is off (`app/main.py` conditional router
registration), so an accidental run against a flag-off stack produces clean 404s rather

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-Safety

### SECOPS-007: single code path

PAY-005 adds no new service logic and therefore introduces no new
dev-vs-prod branch risk. The test modules run against moto in-memory DynamoDB (same boto3
API as real DynamoDB); the collaborators `txn_requests.create_request` and
`txn_requests.execute_request` are patched in tests — they exercise the same code path
in dev (DynamoDB Local + mock KMS) and prod (real DynamoDB + KMS) because the PAY
services themselves have no `if S.dev_mode` branches.

### Money-safety summary (binding on this ticket's tests)

1. **No direct billing writes** — All four pytest test modules assert that
   `billing_shared.apply_wallet_delta`, `billing_shared.new_ledger_entry`, and
   `billing_shared.settle_or_reverse_ledger` are never called by PAY service functions.
   TXR's execute path (patched in tests) owns all three.
2. **Single emission** — The idempotency proof in `test_pay_standing_orders.py` and
   `test_pay_mandates.py` asserts `create_request.call_count == 1` for repeated ticks
   at the same `next_run_at` (see §5.2).
3. **Cap enforcement** — `test_over_cap_pull_emits_no_request_and_writes_nothing_to_billing`
   (§5.3) proves no money-out path is touched on an over-cap pull.
4. **No new money-out path in the frontend** — The `PaymentsPage` calls the same
   `/ui/standing-orders` / `/ui/mandates` endpoints as the backend CRUD surface.
   Actual payment execution is server-side (scheduler) or triggered by the user via
   COUNTERPARTY Transaction Request execution (which goes through TXR's SCA/fraud gate).

### CSRF

All `api.post`, `api.patch`, and `api.del` calls in the frontend endpoint files
automatically include `X-CSRF-Token: <ui_csrf>` via `getCookie("ui_csrf")` in
`frontend/src/api/client.ts:179`. No manual CSRF wiring is needed in the endpoint files.

### Sensitive routing data

The `CounterpartyCreateIn` body sent from the browser may contain a full IBAN or account
number. These are transmitted over TLS (never logged), masked to last-4 in the service
layer before any DDB write, and never returned in API responses. The `CounterpartyOut`
type in `types.ts` only exposes `*_last4` fields, so the frontend TypeScript type system
enforces this at compile time.

## 10. Open Questions / Assumptions

1. **TXR-001/TXR-004 availability**: PAY-005 tests stub `txn_requests.create_request` and
   `txn_requests.execute_request`. If TXR-001/004 land with a different function
   signature than assumed (`create_request(user_sub: str, body: TxnRequestCreateIn) -> dict`,
   `execute_request(user_sub: str, request_id: str, ...)` → `dict`), the mocks in
   `test_pay_standing_orders.py` and `test_pay_mandates.py` need to be updated to match.
   **Assumption**: TXR-001 ships before PAY-005 merges.

2. **SCA dialog reuse (TXR-005)**: The spec assumes the TXR-005 SCA dialog component
   exists as a reusable React component when PAY-005 ships. If TXR-005 is delayed, the
   `PaymentsPage` falls back to a plain "pending" status badge. This is a frontend-only
   decision; no backend change is needed.

3. **Internal scheduler trigger endpoint**: The E2E spec in §4.5 (Section 2.3) notes
   "POST /internal/scheduler/tick or wait for live scheduler". If a dev-only internal
   endpoint exists for this (the `"internal"` prefix is used by other dev tools,
   e.g. `GET /internal/newsfeed-recsys/refresh`), the E2E test should use it. If not,
   the test should directly `update_item` the `next_run_at` to `now - 1` via a seeded
   DDB write helper, then wait for the scheduler poll interval. **Assumption**: a
   `POST /internal/pay/scheduler/tick` endpoint will be added alongside PAY-002 for
   testability (this is the same pattern as `POST /internal/newsfeed-recsys/refresh`).

4. **FX `convert` integer division**: The spec uses `//` (floor division). If the ticket
   authors choose `round(amount_cents * rate_micros / 1_000_000)` instead (banker's
   rounding), the precision test in §5.4 must adjust its expected value accordingly.
   Either choice is acceptable as long as it is consistent and documented.

5. **`bespoke` field in counterparty**: PAY-001 defines `bespoke` as an opaque `dict`.
   DynamoDB stores it as a `Map`. The frontend `types.ts` uses
   `Record<string, unknown>`. No validation is applied to its contents. If future
   tickets impose a schema on `bespoke`, the `CounterpartyCreateIn` Pydantic model must
   be updated — PAY-005 treats it as pass-through.
