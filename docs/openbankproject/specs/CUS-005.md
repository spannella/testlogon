## 2. Context & Current State

### 2.1 DDB init — no tables declared yet

`scripts/local-ddb-init.py` currently builds all table definitions inside `_table_defs()`
(`scripts/local-ddb-init.py:42`). The `TableDef` dataclass (`scripts/local-ddb-init.py:29`)
accepts `attr_types: Dict[str, str]` for declaring the DynamoDB attribute type of every
attribute referenced in a GSI key schema. Any GSI sort key that holds a numeric value
(e.g., `created_at`) **must** declare `attr_types={"created_at": "N"}`; the absence of
this declaration causes DynamoDB to treat the attribute as `S` (string) → a
`ValidationException` is raised when the GSI is queried with an integer comparator. This
exact gotcha is documented in CLAUDE.md under "DynamoDB numeric GSI sort keys" and is
illustrated by the existing `users` table (`scripts/local-ddb-init.py:49-54`,
`attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"}`).

Neither `T.customers` nor `T.financial_products` exists in `app/core/tables.py` (line 321
onwards), and neither `S.customers_table_name` nor `S.financial_products_table_name` exists
in `app/core/settings.py`. The two routers (`app/routers/customers.py`,
`app/routers/financial_products.py`) are not imported in `app/main.py`.

## 3. Data Model

### 3.1 `customers` table

`TableDef` entry to add to `scripts/local-ddb-init.py` inside `_table_defs()`:

```python
TableDef(
    _resolve_table_name(S.customers_table_name, "customers"),
    "pk", "sk",
    gsi=[
        {"index_name": "GSI_NUMBER",
         "partition_key": "gsi_number_pk",   # value: "CUSTNUM" (constant partition)
         "sort_key":      "customer_number"}, # type S — lookup by human number
        {"index_name": "GSI_BRANCH",
         "partition_key": "gsi_branch_pk",   # value: "BRANCH#{branch_id}"
         "sort_key":      "created_at"},     # type N — list by branch, newest-first
    ],
    attr_types={"created_at": "N"},   # REQUIRED — numeric GSI sort key
)
```
<!-- CORRECTED: TableDef takes positional pk/sk args, not keyword pk=/sk=.
     The `gsi` field (not `gsis`) is a plain list of dicts with keys
     `index_name`, `partition_key`, `sort_key` — there is no GSIDef class.
     See scripts/local-ddb-init.py:29-35 and any existing entry e.g. line 52. -->

Row families (single-table, PK `pk`, SK `sk`):

| pk | sk | Purpose |
|----|----|----|
| `CUST#{customer_id}` | `META` | Customer master record |
| `CUST#{customer_id}` | `ATTR#{attribute_id}` | Typed attribute KV entry |
| `CUST#{customer_id}` | `LINK#USER#{user_sub}` | Forward link: which user is linked |
| `CUST#{customer_id}` | `MSG#{ts:013d}#{message_id}` | Chronological message entry |
| `CUSTLINK#{user_sub}` | `META` | Reverse pointer → `customer_id` |

The reverse-pointer partition uses a distinct PK prefix (`CUSTLINK#`) so that a single
`get_item` resolves a user's customer without a GSI scan.

**`frontend/src/pages/customers/MyCustomerPage.tsx`** — customer self-view:

A single-page view that calls `getMyCustomer()` (which hits `GET /ui/customers/me`). On

**`frontend/src/pages/cards/CardsPage.tsx`**:

Fetches `listCards()` via `useQuery(["cards"])`. Renders each card as a `Card` component

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behaviour

When `S.customer_entity_enabled` is `false`:
- `GET /ui/customers*`, `GET /ui/cards*` → `HTTP 404` from the flag guard at the top of
  each handler (matching the existing pattern in `app/routers/group_treasury.py:28-29`,
  `app/routers/legal_export.py:41-42`, and similar flag-gated routers — all raise
  `HTTPException(status_code=404, ...)`).
  <!-- CORRECTED: the original reference to `app/routers/kyc_cases.py` was wrong.
       kyc_cases.py raises 503 (not 404) for disabled features — it calls
       `_raise_kyc_error("kyc_feature_disabled")` which maps to HTTP 503 via
       `app/contracts/kyc_cases_contract.py:421`. The 404 flag-off pattern is
       present in group_treasury.py, legal_export.py, affiliate_links.py, etc. -->
- The existing `/ui/billing/payment-methods` (which underlies `list_payment_methods_ddb`)
  is **unaffected** — the cards resource layer adds endpoints, it never removes or wraps
  the existing billing endpoints.
- The `customers` and `financial_products` tables are created by `just restart`
  regardless of the flag, because `scripts/local-ddb-init.py` runs unconditionally.
  An empty table with no traffic is harmless.

When `S.financial_products_enabled` is `false`:
- `GET /ui/financial-products*` → `HTTP 404`. The `catalog` router is untouched.

### 5.2 Route ordering (FastAPI declaration order)

In `app/routers/customers.py`, the static sub-path `/me` must be declared **before** the
dynamic `/{customer_id}` route. Similarly, `/collections` in `app/routers/financial_products.py`
must precede `/{product_code}`. Violating this causes FastAPI to capture the literal string
`"me"` or `"collections"` as a path parameter value — the same gotcha noted for the KYC
`/schedules` route (`CLAUDE.md` → "Common gotchas"). The E2E spec explicitly asserts that
`GET /ui/customers/me` returns a 200/404 (not a 422 from a failed `customer_id` lookup),
and `GET /ui/financial-products/collections` returns a collection list (not a product lookup).

### 5.3 Optimistic-concurrency 409 handling in the UI

`patchCustomer`, `updateCardStatus`, and `patchProduct` all require `expected_version`.
The UI pattern:
1. On successful fetch, store `version` in component state.
2. On submit, send `expected_version: storedVersion`.
3. On 409 response, call `queryClient.invalidateQueries([...])`, toast "Record changed
   by another session — please review and resubmit", and reload the form with the fresh
   version. Do not silently clobber.

### 5.4 Customer message thread ownership gate

`POST /ui/customers/{id}/messages` has dual auth (from CUS-002): admin/root posts as
STAFF; the customer linked to this `customer_id` posts as CUSTOMER. The frontend:
- On `CustomersPage` (admin context), the compose bar always sends staff messages.
- On `MyCustomerPage` (user context), `getMyCustomer()` resolves the `customer_id` from
  the reverse pointer; the compose bar sends customer messages. If a non-linked user
  navigates to `/customers/me`, the 404 from `GET /ui/customers/me` shows the empty state
  rather than the thread.
- A user who navigates directly to `/customers/{other_id}/messages` receives a 403 from
  the ownership check; the frontend catches this with React Query's `onError` and shows
  a "Not authorised" toast + redirects to the dashboard.

### 5.5 DDB table recreation after `just restart`

`just restart` calls `scripts/local-ddb-init.py` which iterates `_table_defs()` and
calls `create_table` for each entry. Tables that already exist are skipped via a
`try/except ResourceInUseException` guard already present in the script. The critical
concern is that after a schema change (a new GSI is added) the dev must `just restart` to
drop and re-create the table; a table created under an older schema will not have the new
GSI. The `attr_types` declarations are validated at `create_table` time — a missing
`"N"` declaration will raise `ValidationException` before any endpoint is called.

### 5.6 Staff-to-customer notification (CUS-002 integration check)

The E2E test confirms that after a staff message is posted, the linked user's alert
row exists in `T.alerts` (verified by calling `GET /ui/alerts` as Alice). This exercises
the `write_alert` path (`app/services/alerts.py:356`) without needing to check SES in dev
(SECOPS-007: `send_alert_email` is a no-op in dev because the moto SES mock receives and
discards the email; the in-app `T.alerts` write is the observable side-effect).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 parity

All new code follows a single code path for both dev (DynamoDB Local + moto + mock KMS)
and prod (real DynamoDB/SES). Specific assertions:

- `write_alert` (`app/services/alerts.py:356`) already dispatches SES via
  `send_alert_email` (`app/services/alerts.py:459`), which is a real SES call in prod and
  a moto-intercepted no-op in dev. No `if S.dev_mode` branch is introduced.
- The `customers` and `financial_products` table handles are wired via `_safe_table`
  (`app/core/tables.py:65-66`) exactly like every other table, regardless of environment.
- Frontend nav entries are gated on runtime API responses, not on a hardcoded
  `import.meta.env.DEV` conditional.

### 7.2 No money movement in CUS-005

CUS-005 is a wiring + UI ticket. It introduces no charge paths, no ledger entries, and no
wallet mutations. The billing table is accessed read-only through the existing
`list_payment_methods_ddb` wrapper (`app/routers/billing.py:769`) — CUS-003 already
handles the additive write path. This ticket does not need `new_ledger_entry`,
`settle_or_reverse_ledger`, `apply_wallet_delta`, or any fraud gate.

### 7.3 CSRF on all mutating requests

The Axios client in `frontend/src/api/client.ts` already attaches `x-csrf-token` from the
`ui_csrf` cookie on every non-GET request. No additional CSRF configuration is needed for
the new endpoints — they all use `Depends(require_ui_session)` which enforces the CSRF
header check for cookie-authed sessions.

### 7.4 PAN invariant

`CardsPage` and its endpoint wrappers only ever transmit `card_id` (= `payment_method_id`),
`brand`, `last4`, `exp_month`, `exp_year`, and `card_status`. The full PAN and CVV are
never stored in `PM#` rows (enforced since billing.py:928) and never flow through any
customer-facing code path introduced by CUS-001..005.

### 7.5 Idempotency

- Linking a user who is already linked (`link_user` called twice with the same
  `user_sub`) is idempotent: the `LINK#USER#{user_sub}` row and the reverse-pointer row
  are both `put_item` (unconditional upsert), so a double-link leaves state identical to
  a single link. No error is raised; the response returns 200 with the unchanged customer.
- Collection upsert (`PUT /ui/financial-products/collections/{code}`) is a
  read-merge-write deduped list — calling it twice with the same payload produces the
  same collection order (mirrors the `template_packets` pattern documented in CLAUDE.md).

## 8. Backward Compatibility & Migration

### 8.1 No existing data is mutated

The two new tables (`customers`, `financial_products`) are empty on first creation. The
`billing` table's existing `PM#` rows gain new optional fields (`card_status`,
`card_version`) only when a `set_card_status` or `create_card` call is made; `list_cards`
defaults `card_status` to `"ACTIVE"` for rows lacking the field, so pre-existing payment
methods surface as active cards without requiring a migration sweep.

### 8.2 No routing conflicts with existing endpoints

- `/ui/customers*` is a new prefix not used by any existing router.
- `/ui/cards*` is a new prefix not used by any existing router (the existing payment-
  methods surface is at `/ui/billing/payment-methods`, not `/ui/cards`).
- `/ui/financial-products*` is a new prefix. The existing catalog is at `/ui/catalog`
  with `T.catalog` (table name defaults `shopping_catalog`) — no name or route overlap.

### 8.3 `just restart` recreates tables

In development, `just restart` wipes DynamoDB Local and re-runs `scripts/local-ddb-init.py`,
so the new `TableDef` entries are applied cleanly. In production, a `CreateTable` call
adds the new tables before the new code is deployed; the existing tables and data are
untouched. No backfill is needed because all new fields are additive.

## 10. Open Questions / Assumptions

1. **`GET /ui/config` for flag surfacing.** The spec assumes the frontend detects flag
   state from API response codes (503/404 on disabled endpoints). If a `GET /ui/config`
   endpoint returning active feature flags already exists or is added by another ticket,
   that is the preferred mechanism and the nav-gating logic should use it instead.
2. **Billing `add_card` delegate path.** CUS-003 specifies that `POST /ui/cards` is a
   "thin delegate" to the existing add-card flow. The exact Stripe interaction (attaching a
   `SetupIntent`-derived `payment_method`) lives in `app/routers/billing.py` and is not
   re-implemented. The frontend `CardsPage` accordingly does not render an "Add new card"
   form — it relies on the existing `BillingPage → PaymentMethods` flow to add cards, then
   surfaces them via `listCards`. If a standalone add-card form in `CardsPage` is desired,
   a follow-up ticket is needed.
3. **`detectCardNetwork` utility.** ~~RESOLVED~~ — `detectCardNetwork` is already
   extracted to `frontend/src/lib/cardNetwork.ts` and imported by `PaymentMethods.tsx`
   (`import { detectCardNetwork, formatCardNumber } from "@/lib/cardNetwork"`).
   `CardsPage` can import it directly from `@/lib/cardNetwork` with no refactoring required.
   <!-- CORRECTED: the conditional "if currently inlined" was a stale assumption.
        Verified: frontend/src/lib/cardNetwork.ts exists and PaymentMethods.tsx:25
        already imports from it. -->
4. **Staff alert for customer→staff reply.** CUS-002 specifies a `write_alert` for the
   staff leg (staff→customer) but leaves the customer→staff notification as "optional".
   The E2E spec asserts on the staff→customer alert only. Whether to notify the staff
   inbox on a customer reply is a product decision deferred to a follow-up.
5. **`customer_number` uniqueness.** CUS-001 mints `customer_number` from `now_ts()` as a
   monotonic seed. Under concurrent creation this can collide. The spec assumes this is
   acceptable for the current scale; a sequence-guaranteed approach (e.g., DynamoDB atomic
   counter on a `SEQUENCE` row) is a follow-up if uniqueness enforcement becomes necessary.
6. **Pagination in the UI.** `CustomersPage` uses `useInfiniteQuery` for the customer
   list. The `ProductsPage` also uses infinite scroll. Both rely on the backend cursor
   returned by `list_customers` and `list_products` (encoded via `app/core/cursor.py:94`).
   The frontend must decode/pass the opaque cursor back as a query param on each subsequent
   page load.
