# PAY-001 — Counterparty / beneficiary entity — DDB model, table, flag + CRUD

**Ticket type**: Backend (data model + CRUD endpoints)
**Priority**: P1 (foundation — PAY-002 standing orders and PAY-003 mandates both depend on this)
**Estimate**: 2.5 days
**Status**: Unimplemented

---

## 1. Summary & Goal

PAY-001 introduces the **counterparty** (also called a beneficiary) as a first-class, user-owned entity: a stored third-party payee carrying bank routing information that outbound-payment flows can reference by an opaque `counterparty_id`. This entity is the destination pointer that COUNTERPARTY Transaction Requests (TXR-001), standing orders (PAY-002), and direct-debit mandates (PAY-003) all resolve against.

The goal for this ticket is narrow and additive: define the DynamoDB schema, the `app/services/counterparties.py` service layer, and the `app/routers/counterparties.py` REST surface, all gated behind a new default-OFF flag `PAYMENTS_COUNTERPARTIES_ENABLED`. No existing billing, wallet, ledger, or payout-method code is modified. All routing numbers are stored **last-4-only** at rest (SEC-004 masking discipline, matching `creator_payouts.add_payout_method`, `app/services/creator_payouts.py:681`). No money moves in this ticket.

## 3. Data Model

### New DynamoDB table: `counterparties`

**Primary key**: `user_sub` (S) hash + `counterparty_id` (S) sort.

The composite primary key encodes ownership: `Key={"user_sub": user_sub, "counterparty_id": cp_id}` fetches exactly the owning user's record. A foreign `counterparty_id` presented by a different `user_sub` returns nothing from `get_item`, becoming the 404 guard without a secondary ownership check.

**GSI `ByUserCreatedAt`**:
- Partition key: `user_sub` (S)
- Sort key: `created_at` (N)
- **`attr_types={"created_at": "N"}` is mandatory** — the CLAUDE.md numeric-GSI gotcha. Omitting this causes DynamoDB Local to store `created_at` as String, producing `ValidationException` when queried with an integer `ExclusiveStartKey`. Pattern is established at `scripts/local-ddb-init.py:986`.

**TableDef entry** (to be added to `_table_defs()` in `scripts/local-ddb-init.py`):

```python
TableDef(
    _resolve_table_name(S.counterparties_table_name, "counterparties"),
    "user_sub",
    "counterparty_id",
    gsi=[
        {"index_name": "ByUserCreatedAt", "partition_key": "user_sub", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

**Item attributes**:

| Attribute | Type | Notes |
|---|---|---|
| `user_sub` | S | Hash key — owner's Cognito sub |
| `counterparty_id` | S | Sort key — `cp_{uuid4().hex}` |
| `name` | S | Human label, e.g. "Acme Ltd" |
| `is_beneficiary` | BOOL | `true` = outbound beneficiary; `false` = payor/reference |
| `routing_scheme` | S | `"IBAN"`, `"ACCOUNT_SORT_CODE"`, `"ACCOUNT_NUMBER"`, or `"BANK"` |
| `iban_last4` | S | Last 4 chars of IBAN (scheme=IBAN); never the full IBAN |
| `account_number_last4` | S | Last 4 digits (scheme=ACCOUNT_NUMBER or ACCOUNT_SORT_CODE) |
| `sort_code` | S | Full sort code (6-digit, not sensitive) — stored clear |
| `bank_code` | S | BIC/SWIFT or domestic bank code |
| `bank_name` | S | Human-readable bank name |
| `account_holder` | S | Name on the account |
| `currency` | S | ISO-4217 lowercase, default `"usd"` |
| `description` | S | Optional user note |
| `bespoke` | M | Opaque map for caller-supplied metadata (OBP "bespoke" field) |
| `created_at` | N | `now_ts()` — used as GSI sort key |
| `updated_at` | N | `now_ts()` on every write |

**Sensitive-number masking rule** (mirrors `creator_payouts.py:681`):
- `routing_scheme="IBAN"`: caller provides full IBAN; service extracts `iban[-4:]` → `iban_last4`; full IBAN is not persisted.
- `routing_scheme="ACCOUNT_NUMBER"` or `"ACCOUNT_SORT_CODE"`: caller provides full `account_number`; service extracts `account_number[-4:]` → `account_number_last4`; full number is not persisted.
- `sort_code`, `bank_code`, `bank_name`, `account_holder`, `currency` are stored as-is (not sensitive).

## 4. API / Service Design

### Service: `app/services/counterparties.py`

All functions are synchronous; they are called from async FastAPI handlers via `await asyncio.to_thread(...)` or directly (DynamoDB boto3 calls release the GIL and are fast in practice).

```python
def _cp_id() -> str:
    """Generate a counterparty ID. Mirrors creator_payouts._method_id()."""
    return f"cp_{uuid.uuid4().hex}"

def _mask_routing(routing: CounterpartyRouting) -> dict:
    """
    Apply SEC-004 masking. Returns the DDB-ready routing dict.
    Full IBAN / account_number never written; last-4 only.
    Raises ValueError("routing_invalid:...") on scheme/field mismatch.
    """

def create_counterparty(
    user_sub: str,
    *,
    name: str,
    is_beneficiary: bool = True,
    routing: CounterpartyRouting,
    description: str | None = None,
    bespoke: dict | None = None,
) -> dict:
    """
    Persist a new counterparty. Returns the CounterpartyOut dict (masked).
    Raises ValueError on invalid routing.
    """

def get_counterparty(user_sub: str, counterparty_id: str) -> dict:
    """
    Fetch by Key={user_sub, counterparty_id}.
    Raises KeyError("counterparty_not_found") if missing (callers → 404).
    """

def list_counterparties(
    user_sub: str,
    *,
    limit: int = 20,
    cursor: str | None = None,
) -> dict:  # {"items": [...], "next_cursor": str | None}
    """
    Query ByUserCreatedAt GSI, ScanIndexForward=False (newest first).
    Cursor pagination via app.core.cursor.encode_cursor / decode_cursor.
    """

def update_counterparty(
    user_sub: str,
    counterparty_id: str,
    *,
    name: str | None = None,
    description: str | None = None,
    is_beneficiary: bool | None = None,
    bespoke: dict | None = None,
) -> dict:
    """
    Partial update of mutable fields only. Routing is immutable after creation
    (callers must delete + re-create to change routing).
    Raises KeyError("counterparty_not_found") if the Key does not exist for this user.
    Uses update_item with ConditionExpression=attribute_exists(counterparty_id).
    """

def delete_counterparty(user_sub: str, counterparty_id: str) -> None:
    """
    Hard delete. Raises KeyError("counterparty_not_found") if not found.
    PAY-002/003 will add a guard here: refuse delete if active standing order
    or mandate references this id. PAY-001 performs a simple delete.
    """
```

## 5. Detailed Behavior & Edge Cases

### Routing scheme validation

Each scheme requires a specific subset of fields. Validation occurs in `_mask_routing` before any DDB write:

| Scheme | Required on input | Error if absent |
|---|---|---|
| `IBAN` | `iban` (non-empty, min 15 chars) | `routing_invalid:iban_required` |
| `ACCOUNT_SORT_CODE` | `account_number` + `sort_code` | `routing_invalid:account_number_and_sort_code_required` |
| `ACCOUNT_NUMBER` | `account_number` + `bank_code` | `routing_invalid:account_number_and_bank_code_required` |
| `BANK` | `bank_code` | `routing_invalid:bank_code_required` |

A `ValueError` from the service layer is caught by the router and re-raised as `HTTPException(status_code=400, detail=str(e))`.

### Ownership enforcement

`get_counterparty(user_sub, counterparty_id)` calls `T.counterparties.get_item(Key={"user_sub": user_sub, "counterparty_id": counterparty_id})`. If `Item` is absent, raises `KeyError("counterparty_not_found")`. Because the primary key includes `user_sub`, DynamoDB returns nothing for a valid `counterparty_id` that belongs to a different user — no secondary ownership check is needed. The router maps `KeyError` → `HTTPException(404)`.

### PATCH immutability of routing

`CounterpartyUpdateIn` intentionally omits all routing fields. Routing — once set — is immutable for the lifetime of the counterparty record. To change routing the caller must DELETE the counterparty and POST a new one. This matches the payout-method pattern (no `update_payout_method` exists in `creator_payouts.py`) and ensures that any standing orders or mandates pointing at a `counterparty_id` remain consistent with the routing they were validated against.

### DELETE safety (PAY-001 scope)

In PAY-001 the delete is unconditional: `T.counterparties.delete_item(Key={"user_sub": user_sub, "counterparty_id": counterparty_id})`. PAY-002 and PAY-003 will add a check for active `standing_orders` / `direct_debit_mandates` rows referencing this `counterparty_id` and refuse the delete with `409 Conflict`. The stub comment must be present in PAY-001's `delete_counterparty` to make this extension point explicit.

### Pagination

`list_counterparties` queries `ByUserCreatedAt` with `ScanIndexForward=False` (newest first). It passes `Limit=limit` to DynamoDB and encodes `LastEvaluatedKey` → `encode_cursor(...)` for the response's `next_cursor`. An incoming `cursor` query param is decoded via `decode_cursor(cursor)` → `ExclusiveStartKey`. An invalid or tampered cursor (HMAC fails) decodes to `None` and the query starts from the beginning, silently ignoring the cursor rather than 400ing — matching existing pagination behavior throughout the codebase.

### `bespoke` map

`bespoke` is stored as a DynamoDB Map. Callers may put any JSON-serializable key-value pairs. The service layer stores it verbatim without schema enforcement (OBP's "bespoke" counterparty metadata). On `update_counterparty`, if `bespoke` is provided it **replaces** the prior bespoke map entirely (no merge). If `bespoke` is omitted from the PATCH body it is unchanged. An explicit `bespoke: null` clears it.

### Audit events

Every mutating operation fires `audit_event(...)` (`alerts.py:644`) **after** the DDB write succeeds, using the `request` object for IP/user-agent capture:

| Operation | Event string |
|---|---|
| POST (create) | `"counterparty.created"` |
| PATCH (update) | `"counterparty.updated"` |
| DELETE | `"counterparty.deleted"` |

Additional fields passed: `counterparty_id`, `name`, `routing_scheme`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### Dev/prod parity

PAY-001 is pure DDB CRUD — no external provider calls, no S3, no KMS, no email. The same code path runs in dev (DynamoDB Local on port 8001, credentials `test/test`) and prod (real DynamoDB). There is no `if S.dev_mode` branch in the service or router. SECOPS-007 is trivially satisfied.

### Idempotency

`create_counterparty` is **not** idempotent by design: each POST mints a new `cp_{uuid4().hex}` and writes a new item. Duplicate POSTs with the same routing create two separate records. This matches OBP semantics (the caller decides whether to deduplicate). The service does not check for existing records with the same routing details before writing.

`update_counterparty` is idempotent: sending the same PATCH twice produces the same final state (same field values, only `updated_at` advances).

`delete_counterparty` is idempotent: a second delete on the same id returns `KeyError("counterparty_not_found")` → 404, which is the correct HTTP response for a resource that no longer exists.

### Security

**No full account numbers or IBANs at rest.** The masking is enforced in `_mask_routing` before any `put_item` call. There is no code path in PAY-001 that writes or reads a full account number or IBAN from DynamoDB.

**Ownership by primary key.** Because `user_sub` is the DynamoDB hash key, every get/update/delete operation is bounded to the calling user's partition. No cross-user enumeration is possible via normal key access.

**CSRF.** `require_ui_session` enforces CSRF for POST/PATCH/DELETE automatically (cookie auth path checks `x-csrf-token` header per `app/auth/deps.py`). Bearer-auth API clients bypass CSRF per existing convention, but counterparty routes are UI-facing only (`/ui/` prefix).

**Rate limiting.** PAY-001 does not add per-endpoint rate limiting. The existing DDB-backed `_bucket_limit` from `app/services/rate_limit.py` can be applied in a follow-up if abuse is observed. The current volume is expected to be low (a user rarely creates more than a handful of counterparties).

### Money safety

PAY-001 moves **no money**. It creates, reads, updates, and deletes metadata records. The only way money moves in the PAY cluster is via a COUNTERPARTY Transaction Request in TXR. PAY-001 does not call `apply_wallet_delta`, `new_ledger_entry`, `settle_or_reverse_ledger`, or any payment-provider SDK. This constraint is structural and cannot be accidentally violated because the service module does not import `billing_shared` or `billing.py`.

## 8. Backward Compatibility & Migration

### Additive only

No existing table is modified. No existing endpoint is changed. No existing model gains new required fields. The `counterparties` table is brand new.

### Zero-downtime rollout

1. Deploy the code with `PAYMENTS_COUNTERPARTIES_ENABLED=0` (default). The `counterparties` table handle is wired but the router is not registered. Existing traffic is unaffected.
2. Run `scripts/local-ddb-init.py` (or `just restart` in dev) to create the `counterparties` table. In prod this is a `CreateTable` API call; it completes asynchronously but the table is available within seconds.
3. Flip `PAYMENTS_COUNTERPARTIES_ENABLED=1` and redeploy (or hot-reload). The router is now registered.

### Re-keying when ACC entity lands

Counterparties today are owned by `user_sub`. When the ACC-001 account entity lands, standing orders and mandates may want to reference an `account_id` as the funding source rather than a raw `user_sub`. The counterparty table schema can be extended with an optional `account_id` attribute without a breaking change — existing rows without it continue to work using `user_sub` as the funding key.

## 10. Open Questions / Assumptions

1. **Full IBAN/account number for payment execution.** The spec stores only last-4 at rest (SEC-004). When TXR-001 executes a COUNTERPARTY Transaction Request it needs the full routing to dispatch to the actual payment rail. Assumption: the executing rail (external bank API or mock) is provided the routing details at the time the Transaction Request is created — the caller provides the full routing in the TXR body, not by re-reading the counterparty record. If the platform later needs to store and re-use the full routing server-side (e.g., for an internal payment rail), those values must be KMS-encrypted at rest (`app/core/crypto.kms_encrypt`), following the SSH key pattern in `app/services/ssh_key_manager.py`. This is out of scope for PAY-001.

2. **Currency validation.** PAY-001 stores `currency` as a free-form lowercase string (e.g., `"usd"`, `"eur"`). No ISO-4217 validation is applied. A future hardening pass can add a `Literal` or `constr(regex=...)` constraint. The gap analysis confirms the ledger is single-currency `usd` today (`OBP_GAP_ANALYSIS.md` §B: "ledger is single-currency `usd`"; the `usd` default appears in `billing_shared.py:180` — `row.get("currency", "usd")`); FX conversion is PAY-004's concern.

3. **Account entity re-keying.** When ACC-001 account entities land, counterparties can optionally carry an `account_id` as the funding source. The `delete_counterparty` guard (PAY-002/003 extension point) would also check `accounts` rows. Assumption: PAY-001 ships with `user_sub`-only ownership; the ACC re-keying is a non-breaking additive attribute.

4. **Per-user counterparty limit.** No limit is enforced in PAY-001. If abuse is a concern, a configurable cap (e.g., `MAX_COUNTERPARTIES_PER_USER=100`) can be added to `Settings` and enforced in `create_counterparty` with a `count_items` query before the `put_item`.

5. **`is_beneficiary` semantics.** The flag distinguishes a payee (outbound, `is_beneficiary=True`) from a payor or reference entity (`is_beneficiary=False`). In PAY-001 the flag is stored and returned but not enforced — PAY-002/003 may reject standing orders targeting a counterparty with `is_beneficiary=False`. Assumption: PAY-001 stores but does not enforce this flag.
