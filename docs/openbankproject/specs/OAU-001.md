# OAU-001 — Consumer-app registry — model, table, CRUD, secret hashing

**Ticket type**: Backend (data model + service + router)
**Priority**: P1 (foundation — OAU-002 through OAU-006 all depend on this)
**Estimate**: 2.5 days
**Status**: Unimplemented (testlogon has no OAuth consumer-app / redirect-URI / secret-rotation model today)

---

## 1. Summary & Goal

OAU-001 introduces the **consumer-app registry**: a first-party developer registers a third-party application and receives a `client_id` plus a one-time `client_secret`. The registry is the foundation for the entire OAuth2/OIDC authorization-server surface (OAU-002 through OAU-005). Nothing in the existing auth surface changes; the feature is wholly additive and guarded by a default-OFF flag.

The central design decision is explicit: **the consumer registry is modeled directly on the existing API-key registry** (`app/services/api_keys.py`). It reuses the same secret-generation function (`secrets.token_urlsafe(32)`, `api_keys.py:18`), the same pepper-HMAC hash (`api_key_hash`, `api_keys.py:31-34`, `app/core/crypto.py:13-14`), the same owner-scoped DDB access pattern (`ConditionExpression="owner_sub = :u"`), the same owner-GSI shape as the `api_keys` table (`scripts/local-ddb-init.py:57-60`), and the same auth guards (`require_ui_session` + `require_fresh_mfa` + `audit_event`, `app/routers/api_keys.py:17-29`). No primitives are forked.

The goal of this ticket is to:

1. Define and register the `oauth_consumers` DynamoDB table with its single-table layout and `ByOwner` GSI.
2. Add `T.oauth_consumers` to `app/core/tables.py` and the corresponding settings keys to `app/core/settings.py`.
3. Implement `app/services/oauth_consumers.py` with the full CRUD + secret-verification surface.
4. Implement `app/routers/oauth_consumers.py` with five REST endpoints under `/ui/oauth/consumers`, conditionally registered in `app/main.py` behind `S.oauth_provider_enabled`.
5. Validate redirect URIs and allowed scopes using only existing primitives (no new validation logic invented here).

OAU-001 has no dependencies. Every subsequent OAU ticket depends on it.

## 2. Context & Current State

### What testlogon has today

**API-key registry (the pattern to replicate, not fork).** `app/services/api_keys.py` provides the complete analogue:

- `new_api_key_secret()` → `secrets.token_urlsafe(32)` (`api_keys.py:18`).
- `api_key_hash(secret)` → `sha256_str(secret + "|" + S.api_key_pepper)` (`api_keys.py:31-34`); `sha256_str` is `hashlib.sha256(s.encode()).hexdigest()` (`app/core/crypto.py:13-14`).
- `create_api_key` mints a `key_id = secrets.token_hex(16)` (`api_keys.py:143`), sets `prefix = f"ak_{key_id[:8]}"` (`api_keys.py:166`), calls `with_ttl(item, ttl_epoch=ttl)` (`api_keys.py:174-175`), does `T.api_keys.put_item(Item=item)`, and returns a response containing `key_secret = f"ak_{key_id}.{secret}"` exactly once (`api_keys.py:178-185`). The hash — never the plaintext — is persisted.
- `revoke_api_key` uses `update_item` with `ConditionExpression="user_sub = :u"` (`api_keys.py:187-196`).
- `set_api_key_capabilities` uses the same conditional pattern (`api_keys.py:329-341`).
- `list_api_keys` queries the owner GSI `IndexName=S.api_keys_user_index` (`api_keys.py:349-374`).
- The `api_keys` `TableDef` declares `gsi=[{"index_name": S.api_keys_user_index, "partition_key": "user_sub"}]` with no `attr_types` override because the GSI partition key is a string (`scripts/local-ddb-init.py:57-60`).

**Router pattern.** `app/routers/api_keys.py` shows the exact auth+audit shape:

```python
# app/routers/api_keys.py:11,17-22
# (router = APIRouter is at line 11; first handler block is lines 17-22)
router = APIRouter(prefix="/ui", tags=["api-keys"])
```

`require_fresh_mfa(ctx)` is defined at `app/services/sessions.py:699`: checks the session's `mfa_verified_at` against `S.ui_stepup_max_age_seconds`, raising `HTTPException(401, "Fresh MFA required")` when stale. `audit_event` at `app/services/alerts.py:644` writes a DDB row to `T.alerts`.

**Scope registry (reuse for allowed-scope validation).** `API_KEY_ROUTE_SCOPE_REGISTRY` (`app/services/api_key_route_scope_registry.py:17-67`) maps route identifiers to `RouteScopePolicy` dicts containing `required_scopes`. `get_route_scope_policy(route_id)` (`api_key_route_scope_registry.py:275-276`) looks up a policy by route identifier. The union of all `required_scopes` values across the registry is the valid scope vocabulary. `is_route_registered_or_exempt(route_id)` (`api_key_route_scope_registry.py:316-318`) determines whether a route participates in scope enforcement. Consumer `allowed_scopes` must be validated against this vocabulary.

**Redirect-URI validation shape.** `_validate_google_redirect_uri` in `app/services/provider_oauth.py:84-96` parses a URI with `urlparse`, rejects non-http(s) schemes and empty `netloc` (lines 88-90), and then checks exact membership in a server-side allowlist (lines 92-95). OAU-001 borrows only the structural part (`http`/`https` scheme + non-empty `netloc`, lines 88-90) applied per-URI in the consumer's stored `redirect_uris` list. The allowlist check is omitted because the consumer's own stored `redirect_uris` list IS the allowlist for that consumer. OAU-001 additionally rejects URIs containing fragments (`#`), which `_validate_google_redirect_uri` does not enforce.

**Token/HMAC signing (for downstream OAU tickets).** `mint_ws_token` / `verify_ws_token` at `app/core/crypto.py:35-61` produce HMAC-signed, TTL-bearing envelopes used for auth codes in OAU-002. `kms_encrypt` / `kms_decrypt` at `app/core/crypto.py:16-25` provide the KMS abstraction used by `app/services/provider_oauth.py:312-314` for refresh-token encryption — reused by OAU-002/003. These are cited here for completeness; OAU-001 itself only uses `sha256_str` and `secrets`.

**TTL utility.** `with_ttl(item, ttl_epoch)` (`app/services/ttl.py:5`) sets `item[S.ddb_ttl_attr]`; used by `create_api_key` at `api_keys.py:174-175`. OAU-001 does not issue TTL rows (no codes yet), but auth-code and refresh-grant rows added in OAU-002 will use it on the same table.

**Settings and table wiring.** `Settings` is a `frozen=True` dataclass in `app/core/settings.py`. All table-name env vars follow the pattern `SOME_TABLE_NAME → S.some_table_name` (e.g., `S.api_keys_table_name` at `settings.py:44`). `T` is the singleton `Tables` dataclass instance from `app/core/tables.py:68-321`; each field is a `_FloatSafeTable` wrapping the real boto3 Table (`tables.py:65-66`).

**Gap analysis status.** `docs/openbankproject/OBP_GAP_ANALYSIS.md:72` marks consumer-app registration as **PARTIAL**: "API-key registry exists; no OAuth consumer-app / secret / redirect / rotation." OAU-001 closes this gap.

## 3. Data Model

### New table: `oauth_consumers` (single-table)

The table is single-table by design: the META row (this ticket), auth-code rows (`sk="CODE#{code_id}"`), and issued-grant rows (`sk="GRANT#{grant_id}"`) added in OAU-002 all live under the same `client_id` partition, avoiding cross-table lookups during token exchange.

**Table coordinates**

| Setting key | Env var | Default |
|---|---|---|
| `S.oauth_consumers_table_name` | `OAUTH_CONSUMERS_TABLE_NAME` | `"oauth_consumers"` |
| `S.oauth_consumers_owner_index` | `OAUTH_CONSUMERS_OWNER_INDEX` | `"ByOwner"` |

Add both to `app/core/settings.py` adjacent to `api_keys_table_name` (`settings.py:44`).

**Primary key**

| Attribute | DDB type | Role |
|---|---|---|
| `client_id` | S (partition key) | Unique consumer identifier |
| `sk` | S (sort key) | Row discriminator — `"META"` for this ticket; `"CODE#..."` / `"GRANT#..."` in OAU-002 |

**`ByOwner` GSI**

| Attribute | DDB type | Purpose |
|---|---|---|
| `owner_sub` | S (partition key) | List all consumers for a given user |
| `created_at` | N (sort key) | Newest-first ordering |

`attr_types={"created_at": "N"}` is **required** in the `TableDef` declaration to prevent DynamoDB from storing the numeric `created_at` as a String, which causes `ValidationException` when the GSI is queried with an integer comparator. This is the same gotcha documented in CLAUDE.md and applied at `scripts/local-ddb-init.py:52-53,84`.

```python
        "partition_key": "owner_sub",
        "sort_key": "created_at",
    }],
```

### Consumer META item schema

The META row is the sole row type OAU-001 writes. All fields are stored under `sk="META"`.

| Field | Type | Notes |
|---|---|---|
| `client_id` | str | `secrets.token_hex(16)`, 32 hex chars; same generation as `api_keys.py:143` |
| `sk` | str | Fixed `"META"` |
| `client_secret_hash` | str | `api_key_hash(secret)` — `sha256_str(secret + "\|" + S.api_key_pepper)` |
| `client_secret_prefix` | str | `f"oc_{client_id[:8]}"` — display-only hint, mirroring `prefix = f"ak_{key_id[:8]}"` at `api_keys.py:166` |
| `owner_sub` | str | The registering user's `user_sub`; GSI partition key |
| `name` | str | Human-readable app name, max 128 chars |
| `description` | str | Optional free-text, max 512 chars |
| `redirect_uris` | List[str] | Non-empty; each validated: `http`/`https` scheme + non-empty `netloc` (`provider_oauth.py:84-96` shape) |

| `secret_rotated_at` | int | `0` at create; updated by OAU-005 `rotate_client_secret` |

**No plaintext secret is ever stored.** The `client_secret` (plaintext) is returned exactly once in the `create_consumer` response and then discarded, mirroring `create_api_key`'s `key_secret` return at `api_keys.py:178-185`.

## 4. API / Service Design

### Service: `app/services/oauth_consumers.py`

All functions operate on `T.oauth_consumers`. The table handle is accessed via the module-level singleton `T` imported from `app/core/tables`. Functions do not import `T` lazily; the same pattern as `api_keys.py:12` applies.

**`_valid_scope_vocabulary() -> set[str]`**

Returns the union of all `required_scopes` lists across `API_KEY_ROUTE_SCOPE_REGISTRY`. Called at scope-validation time; not cached at module level (the registry is a module-level constant so the call is O(n) dict iteration, not I/O).

```python
def _valid_scope_vocabulary() -> set[str]:
    from app.services.api_key_route_scope_registry import API_KEY_ROUTE_SCOPE_REGISTRY
    vocab: set[str] = set()
    for policy in API_KEY_ROUTE_SCOPE_REGISTRY.values():
        vocab.update(policy["required_scopes"])
    return vocab
```

**`_validate_redirect_uris(uris: list[str]) -> list[str]`**

Validates each URI using the `provider_oauth.py:84-96` structural pattern (not the allowlist check — the consumer's own stored list IS the allowlist). Raises `HTTPException(400, {"code": "invalid_redirect_uri", ...})` if any URI has a non-http(s) scheme or empty `netloc`. Returns the deduplicated list with whitespace stripped.

**`_validate_allowed_scopes(scopes: list[str]) -> list[str]`**

Calls `_valid_scope_vocabulary()`, raises `HTTPException(400, {"code": "invalid_scope", "invalid": [...]})` for any scope not in the vocabulary. Returns the deduplicated list. Also validates the special OIDC scopes `openid`, `profile`, and `email` (always permitted regardless of the route registry — these are identity scopes introduced by OAU-003).

**`create_consumer(owner_sub: str, *, name: str, description: str = "", redirect_uris: list[str], allowed_scopes: list[str], is_confidential: bool = True) -> dict`**

```python
def create_consumer(owner_sub, *, name, description="", redirect_uris, allowed_scopes, is_confidential=True):
    ts = now_ts()
    client_id = secrets.token_hex(16)
    secret = secrets.token_urlsafe(32)        # same as new_api_key_secret(), api_keys.py:18
    secret_hash = api_key_hash(secret)        # api_keys.py:31-34
    uris = _validate_redirect_uris(redirect_uris)
    scopes = _validate_allowed_scopes(allowed_scopes)
    item = {
        "client_id": client_id, "sk": "META",
        "client_secret_hash": secret_hash,
        "client_secret_prefix": f"oc_{client_id[:8]}",
        "owner_sub": owner_sub,
        "name": (name or "")[:128],
        "description": (description or "")[:512],
        "redirect_uris": uris, "allowed_scopes": scopes,
        "is_confidential": is_confidential, "enabled": True,
        "created_at": ts, "updated_at": ts, "secret_rotated_at": 0,
    }
    T.oauth_consumers.put_item(Item=item)
    return {
        "client_id": client_id,
        "client_secret": f"oc_{client_id}.{secret}",   # returned exactly once
        "client_secret_prefix": item["client_secret_prefix"],
        "name": item["name"], "created_at": ts,
    }
```

**`get_consumer(client_id: str) -> dict`**

`T.oauth_consumers.get_item(Key={"client_id": client_id, "sk": "META"}).get("Item") or {}`. Returns the full item or `{}` for a missing key; callers treat `{}` as "not found". The hash is included because OAU-002's token endpoint needs it for `verify_client_secret`. The router layer strips it before returning to API callers.

**`list_consumers(owner_sub: str) -> list[dict]`**

Queries `ByOwner` GSI:

```python
resp = T.oauth_consumers.query(
    IndexName=S.oauth_consumers_owner_index,
    KeyConditionExpression=Key("owner_sub").eq(owner_sub),
    ScanIndexForward=False,
    Limit=100,
)
```

Maps results to safe dicts omitting `client_secret_hash`. Mirrors `list_api_keys` at `api_keys.py:349-374`.

**`update_consumer(owner_sub: str, client_id: str, *, name=None, description=None, redirect_uris=None, allowed_scopes=None) -> dict`**

Builds a dynamic `UpdateExpression` for the supplied non-None fields plus `updated_at = :now`, with `ConditionExpression="owner_sub = :u AND sk = :meta"`. Raises `HTTPException(404)` on `ConditionalCheckFailedException`, exactly as `set_api_key_capabilities` at `api_keys.py:329-341`. Validates any supplied `redirect_uris` / `allowed_scopes` before writing.

**`delete_consumer(owner_sub: str, client_id: str) -> None`**

`T.oauth_consumers.delete_item(Key={"client_id": client_id, "sk": "META"}, ConditionExpression="owner_sub = :u", ...)`. `ConditionalCheckFailedException` → `HTTPException(404)`.

**`verify_client_secret(client_id: str, secret: str) -> bool`**

```python
def verify_client_secret(client_id, secret):
    item = get_consumer(client_id)
    if not item or not item.get("enabled"):
        return False
    stored_hash = item.get("client_secret_hash", "")
    candidate_hash = api_key_hash(secret)
    return hmac.compare_digest(stored_hash, candidate_hash)
```

Uses `hmac.compare_digest` to prevent timing attacks. Note: the existing API-key verification at `api_keys.py:434` uses a plain `!=` comparison (`if api_key_hash(api_key_secret) != it.get("secret_hash")`), NOT `hmac.compare_digest`; OAU-001's `verify_client_secret` is a deliberate security improvement over that baseline. The `api_key_hash` function (`api_keys.py:31-34`) provides the canonical hash computation used on both sides.

## 5. Detailed Behavior & Edge Cases

**Secret returned exactly once.** The `create_consumer` response includes `client_secret = f"oc_{client_id}.{secret}"`. No subsequent `GET` or `PATCH` exposes the secret. The prefix `oc_` distinguishes consumer secrets from API keys (`ak_`). Callers must store the secret immediately; loss requires rotation (OAU-005).

**Public clients (`is_confidential=False`).** The `client_secret_hash` field is stored as an empty string, and `verify_client_secret` short-circuits to `False` for public clients. OAU-002's `/oauth/token` endpoint omits the `client_secret` requirement for public clients and instead enforces PKCE. Creating a public consumer with an explicit `allowed_scopes` set still requires those scopes to be in the vocabulary.

**Redirect-URI validation.** Each URI in `redirect_uris` is parsed with `urllib.parse.urlparse`. Scheme must be `http` or `https`; `netloc` must be non-empty. `localhost` is accepted (dev/test consumer apps). URI fragments (`#...`) are rejected (RFC 6749 §3.1.2). Duplicate URIs within the list are silently deduplicated. Empty `redirect_uris` list is a `400 invalid_redirect_uri`.

**Scope vocabulary.** `_valid_scope_vocabulary()` iterates `API_KEY_ROUTE_SCOPE_REGISTRY.values()` and collects all `required_scopes` strings. The three OIDC pseudo-scopes (`openid`, `profile`, `email`) are hardcoded as always-valid. A consumer requesting `messager:read` and `filemanager:write` is valid today; adding a new route to the registry in the future does not retroactively invalidate any stored consumer's `allowed_scopes` (the validation is only at create/update time).

**Owner isolation.** Every service function that reads or writes a META row passes `owner_sub` and uses a `ConditionExpression="owner_sub = :u"` guard. A `GET /{client_id}` by a non-owner returns 404 (not 403) to prevent client_id enumeration. The `list_consumers` GSI query is inherently owner-scoped since `owner_sub` is the partition key.

**Concurrent create.** `put_item` without a condition is idempotent only for the same `client_id`; since `client_id = secrets.token_hex(16)` is 128-bit random, collision probability is negligible. No additional uniqueness constraint is required.

**Name uniqueness.** Name is NOT required to be unique (the same developer may have test and prod consumers with the same name). Uniqueness is a display concern only.

**`ByOwner` GSI query and DynamoDB FilterExpression.** `list_consumers` uses a `Limit=100` without a `FilterExpression`. Because ALL items under an `owner_sub` partition key should be visible (there is no soft-delete in OAU-001), no post-filter loop is needed. Soft-deleted or disabled consumers are excluded from the list by the router layer if needed in a future iteration.

**MFA freshness.** `require_fresh_mfa(ctx)` (`sessions.py:699`) checks `mfa_verified_at` against `S.ui_stepup_max_age_seconds` (default 300 seconds). If the user has no MFA devices configured, `compute_required_factors(user_sub)` returns `[]` and the check is a no-op — consistent with the behavior in `api_keys.py`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

**SECOPS-007 — no `if S.dev_mode` branch.** All DDB reads/writes in `app/services/oauth_consumers.py` go through `T.oauth_consumers`, which resolves to DynamoDB Local on port 8001 in dev and to real DynamoDB in prod. The `api_key_hash` function uses `S.api_key_pepper` in both environments; the same pepper must be set in `.env.local` (it already is, per the existing API-key registry). No mock branch, no alternate code path.

**Secret hashing is environment-invariant.** `api_key_hash` (`api_keys.py:31-34`) calls `sha256_str(secret + "|" + S.api_key_pepper)` (`crypto.py:13-14`). The pepper comes from `API_KEY_PEPPER` env var, which is non-empty in both dev (`.env.local`) and prod (secrets manager injection). The hash is identical for the same secret + pepper regardless of deployment target.

**`hmac.compare_digest` in `verify_client_secret`.** Prevents timing-based secret oracle attacks. The comparison is always constant-time regardless of whether the stored hash matches, because both sides are fixed-length SHA-256 hex strings (64 bytes). This is a security improvement over the existing `api_keys.py:434` check, which uses a plain `!=` operator rather than a constant-time comparison.

**No secret in logs or audit events.** `audit_event` calls pass `client_id` as metadata, never `secret` or `client_secret_hash`. The create response containing `client_secret` is returned in the HTTP body over TLS and is not logged by the FastAPI request middleware.

**Money-safety: N/A for this ticket.** OAU-001 contains no money-moving code. The consumer registry stores metadata only. All billing/wallet operations remain in the existing billing primitives (`billing_shared.py`) and are not referenced by this ticket. Future tickets (OAU-002 onwards) that issue tokens which could be used to call billing endpoints go through the same fraud gate and SCA checks already on those billing routes — OAU-001 is transparent to them.

**Idempotency.** `put_item` for a new `client_id` is safe to retry (the same random `client_id` cannot collide in practice). `update_item` with the conditional is idempotent for repeated identical field values. `delete_item` is idempotent: a second delete raises `ConditionalCheckFailedException` (item gone), which the router translates to 404.

## 8. Backward Compatibility & Migration

**Zero impact on existing surfaces when flag is off.** The `oauth_consumers` table is created by `scripts/local-ddb-init.py` unconditionally (like all tables), but no existing code reads from it. The `oauth_provider_enabled` flag defaults to `False`, so the router is never registered, and `T.oauth_consumers` is never touched by any existing code path.

**Table creation.** `scripts/local-ddb-init.py` runs at stack startup (`just up` / `just restart`) and is idempotent (`CreateTable` is wrapped in a `try/except ResourceInUseException`). Adding the new `TableDef` requires no migration of existing tables.

**`app/core/tables.py` and `app/core/settings.py` changes are additive.** The `Tables` dataclass gains one field (`oauth_consumers`); the `Settings` dataclass gains four fields. Both dataclasses are `frozen=True`, so field addition is backward-compatible: existing code constructing these objects via keyword arguments is unaffected (Python `frozen=True` dataclass field addition is additive at the language level).

**`app/models.py` additions.** The new Pydantic models (`CreateConsumerReq`, `UpdateConsumerReq`, `ConsumerOut`, `CreateConsumerOut`) are append-only additions. No existing model is modified.

**Existing auth surface unchanged.** `get_authenticated_user` (`app/auth/deps.py:199-305`) is not modified by OAU-001. The OAuth-bearer branch that recognizes OAU-002 tokens is added in OAU-002 as a new branch before the Cognito branch (`deps.py:254`) — OAU-001 does not touch `deps.py`.

**In-production deployment order.** Because the flag defaults to off, deploying OAU-001 code before the `OAUTH_PROVIDER_ENABLED=1` env var is set is entirely safe. The DynamoDB table can be created ahead of time (or it will be created on the first deploy that runs `local-ddb-init.py`). In production, the recommended order is: deploy code → create table → set `OAUTH_PROVIDER_ENABLED=1`.

## 10. Open Questions / Assumptions

1. **Scope vocabulary is the route registry union.** The spec assumes `allowed_scopes` are validated against the union of `required_scopes` across `API_KEY_ROUTE_SCOPE_REGISTRY` plus the OIDC identity scopes. If a product team wants to define OAuth-only scopes not tied to a specific route (e.g., `billing:read` as a coarse scope), those would need to be added to the registry or a separate OAuth-scope vocabulary list. For now, parity with the API-key scope model is assumed.

2. **`is_confidential=False` (public clients).** The spec stores an empty `client_secret_hash` for public clients. An alternative is to refuse `create_consumer` with `is_confidential=False` until OAU-002 is deployed (which implements PKCE enforcement). Decision: store the flag now (OAU-001) and simply never call `verify_client_secret` for public clients in OAU-002's token endpoint. The field is present in the schema regardless.

3. **Maximum consumers per user.** No cap is enforced in this spec. The `list_consumers` GSI query uses `Limit=100`. If a user creates more than 100 consumers, the 101st is invisible in the list (pagination not implemented). This is acceptable for a developer-registry use case. If a cap is desired, a `count` counter on a `STATS#owner` row can be added in a follow-up.

4. **Admin management of foreign consumers.** The five CRUD endpoints only allow owner access. A root-admin endpoint to list/disable any consumer across all users is deferred to OAU-005 (the enable/disable lifecycle ticket). OAU-001 focuses on the self-service owner path.

5. **`API_KEY_PEPPER` reuse.** The spec reuses `API_KEY_PEPPER` for consumer-secret hashing because `api_key_hash` requires it. If a separate pepper for OAuth consumer secrets is desired (key separation), a new `OAUTH_CLIENT_SECRET_PEPPER` env var can be added and `oauth_consumers.py` can provide its own `consumer_secret_hash` function. For now, reuse is simpler and consistent with the stated goal of never forking.
