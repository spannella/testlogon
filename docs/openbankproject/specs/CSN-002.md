# CSN-002 — Consent SCA gate + PIS consent linked to a TXR + consent-scoped rate limit

**Type:** Feature | **Priority:** P2 | **Estimate:** 3d
**Flag:** `PSD2_CONSENTS_ENABLED` (`S.psd2_consents_enabled`, shared with CSN-001, default `false`)
**Depends on:** CSN-001 (consent model, table, lifecycle status machine)
**Soft links:** TXR cluster (`OBP_TXN_REQUESTS_SCA_TICKETS.md`, `txn_requests` table, `txr_*` SK);
MFA/SCA stack (`app/services/sessions.py`, `app/routers/ui_mfa.py`);
`rate_limit._bucket_limit` (`app/services/rate_limit.py:60`)

---

## 1. Summary & Goal

CSN-001 establishes the `consents` table and the `INITIATED → ACCEPTED / REVOKED / EXPIRED` status
machine for Account-Information-Service (AIS) consents. CSN-002 makes that lifecycle production-safe
with three additions:

1. **SCA gate before ACCEPTED.** Under PSD2 a consent must not become usable until the resource
   owner completes a step-up strong customer authentication challenge. CSN-002 wires the existing
   MFA challenge/answer stack (no new OTP code, no new crypto) exactly as TXR-003 does for
   payment initiation (`OBP_TXN_REQUESTS_SCA_TICKETS.md:159-208`). Only after all required
   factors pass does `POST /ui/consents/{id}/accept` flip `status` to `ACCEPTED`.

2. **Payment-Initiation-Service (PIS) consent type linked to a TXR.** `consent_type` is extended
   to accept `"PIS"`. A PIS consent carries a `payment_ref` pointing to a TXR `request_id` and
   always requires SCA. Once `ACCEPTED` it becomes the *authorization record* the TXR execution
   engine checks before moving money. The consent itself never writes a ledger or wallet row; the
   TXR execution engine remains the single money-mover.

3. **Consent-scoped rate limit.** Any endpoint that reads account data under a consent is throttled
   per `consent_id`, closing the "Rate-limit on consent — MISSING" gap row
   (`OBP_GAP_ANALYSIS.md:81`). The helper `rate_limit_consent(consent_id, category)` is modelled
   exactly on `rate_limit_kyc_partner_api` (`app/services/rate_limit.py:385`); no new bucket
   mechanism is introduced.

## 3. Data Model

### `consents` table (additive, no schema break)

Owned by CSN-001. CSN-002 adds two optional fields to the item schema only; no new table,
no new GSI, no change to `scripts/local-ddb-init.py`.

**New item fields (both nullable, absent on AIS consents):**

| Field | Type | Set by |
|---|---|---|
| `payment_ref` | S — a TXR `request_id` (`txr_*`) | `create_consent` when `consent_type="PIS"` |
| `sca_challenge_id` | S — a sessions challenge id (`consent_sca_*`) | `request_consent_sca` |

The `sca_challenge_id` field is already declared in the `ConsentOut` model by CSN-001 as
`sca_challenge_id: str | None`. It is written here, not in CSN-001.

### `T.sessions` (rate-limit + challenge rows — existing table, no change)

`_bucket_limit` stores its window-counter rows in `T.sessions` (PK `user_sub`, SK `sid`). The
consent rate-limit rows follow the same pattern as all other buckets already stored there:
`{"user_sub": f"consent:{consent_id}", "session_id": f"rl#consent#{category}", "bucket_start": ...,
"bucket_count": ..., ttl: ...}`. No schema change; the existing `_FloatSafeTable` proxy
(`app/core/tables.py:41-59`) handles float-to-Decimal coercion on write.

The SCA challenge rows are standard action-challenge items written by `create_action_challenge`
(`sessions.py:626`) with SK `consent_sca_{uuid4().hex}` (the `challenge_id = f"{purpose}_" +
uuid.uuid4().hex` pattern from `sessions.py:634`). No new table or GSI.

### Summary of DDB impact

| Table | Change |
|---|---|
| `consents` | Two optional new item fields (`payment_ref`, `sca_challenge_id`) |
| `sessions` | Rate-limit bucket rows (`consent:{id}` / `rl#consent#{cat}`) + SCA challenge rows — same row shapes as all existing bucket + challenge rows |

No new `TableDef` in `scripts/local-ddb-init.py`. No new numeric GSI sort keys. No `attr_types`
addition needed.

## 4. API / Service Design

### 4.1 Pydantic model additions (`app/models.py`)

```python
# Extend ConsentCreateIn (defined by CSN-001):
class ConsentCreateIn(BaseModel):
    consumer_ref: str
    consent_type: Literal["AIS", "PIS"] = "AIS"   # "PIS" is new in CSN-002
    account_refs: List[str] = []
    view_refs: List[str] = ["owner"]
    payment_ref: Optional[str] = None              # required when consent_type="PIS"
    valid_until: Optional[int] = None
    recurring: bool = True
    reason: Optional[str] = None

# New response shape for SCA mint:
class ConsentScaOut(BaseModel):
    challenge_id: str
    required_factors: List[str]
    consent_id: str
    status: str                  # always "INITIATED"

# ConsentOut already has sca_challenge_id: Optional[str] (CSN-001)
```

Validation rule: `consent_type="PIS"` requires `payment_ref` non-empty; `consent_type="AIS"` rejects
a non-null `payment_ref`. Validated in `create_consent` before the DDB write.

### 4.2 Service layer additions (`app/services/psd2_consents.py`)

**`_consent_requires_sca(consent: dict) -> bool`**

```python
def _consent_requires_sca(consent: dict) -> bool:
    if consent.get("consent_type") == "PIS":
        return True
    amount = int(consent.get("amount_hint_cents", 0) or 0)
    return amount >= int(getattr(S, "psd2_consent_sca_threshold_cents", 0) or 0)
```

A PIS consent always requires SCA. AIS consents above a configurable amount hint also require it
(default threshold `0` means the operator can opt in to AIS SCA without code change). This mirrors
`_sca_required` in `OBP_TXN_REQUESTS_SCA_TICKETS.md:168`.

**`request_consent_sca(owner_sub: str, consent_id: str, req: Request) -> dict`**

1. Load consent via `get_consent(owner_sub, consent_id)` (foreign id or wrong owner → 404).
2. Verify `status == "INITIATED"` — already ACCEPTED → `409 already_accepted`; terminal → `409`.
3. `required_factors = sessions.compute_required_factors(owner_sub)` (`sessions.py:571`).
   If empty and `_consent_requires_sca` is `True`, fall back to email OTP (same decision as
   TXR-003: `409 sca_enrollment_required` if no verified email).
4. `challenge_id = sessions.create_action_challenge(req, owner_sub, purpose="consent_sca",
   send_to=[...], payload={"consent_id": consent_id,
   "required_factors": required_factors,
   "passed": {f: False for f in required_factors}}, ttl_seconds=300)` (`sessions.py:626`).
   **`required_factors` and `passed` MUST be in the payload dict.** `create_action_challenge`
   does `item.update(payload)` (line 649), so they become item fields; `challenge_done` reads
   `chal.get("required_factors", [])` (line 567). Without these fields the challenge item has
   no `required_factors`, `challenge_done` returns `True` vacuously, and SCA is fully bypassed
   for every consent — this is a money-safety / SCA-security invariant, not optional.
5. Stamp `sca_challenge_id` onto the consent item:
   `T.consents.update_item(Key={...}, UpdateExpression="SET sca_challenge_id = :c, updated_at = :t",
   ExpressionAttributeValues={":c": challenge_id, ":t": now_ts()})`.
6. `audit_event("consent.sca_required", owner_sub, req, consent_id=consent_id, challenge_id=challenge_id)`.
7. Return `ConsentScaOut(challenge_id=challenge_id, required_factors=required_factors,
   consent_id=consent_id, status="INITIATED")`.

**`accept_consent(owner_sub: str, consent_id: str, req: Request) -> ConsentOut`**

1. Load consent — wrong owner/missing → 404; already `ACCEPTED` → `409 already_accepted`
   (idempotent replay path — see §5).
2. Read `sca_challenge_id` from the item. If `_consent_requires_sca(consent)` is `True` and
   `sca_challenge_id` is null → `403 sca_not_initiated`.
3. `chal = sessions.load_challenge_or_401(owner_sub, sca_challenge_id)` (`sessions.py:517`) —
   auto-raises 401 for expired/revoked.
4. `if not sessions.challenge_done(chal): raise HTTPException(403, "sca_incomplete")`.
5. Conditional `update_item` on `T.consents`:
   `SET status='ACCEPTED', updated_at=:t CONDITION status = 'INITIATED'` — concurrent/replay
   transitions raise `ConditionalCheckFailedException`, mapped to `409 already_accepted`.
6. `sessions.revoke_challenge(owner_sub, sca_challenge_id)` (`sessions.py:530`) — one-time-use.
7. `audit_event("consent.accepted", owner_sub, req, consent_id=consent_id)`.
8. Return `get_consent(owner_sub, consent_id)`.

**`consent_authorizes_payment(payment_ref: str) -> bool`**

```python
def consent_authorizes_payment(payment_ref: str) -> bool:
    """Return True iff an ACCEPTED, unexpired PIS consent exists for this payment_ref.
    Intended to be called by the TXR execution engine before moving money.
    Never writes a ledger, wallet, or billing row.
    """
    resp = T.consents.query(
        IndexName=S.consents_by_payment_ref_index,
        KeyConditionExpression=Key("payment_ref").eq(payment_ref),
    )
    now = now_ts()
    for item in resp.get("Items", []):
        if (item.get("status") == "ACCEPTED"
                and item.get("consent_type") == "PIS"
                and int(item.get("valid_until", 0) or 0) > now):
            return True
    return False
```

This requires a third GSI on `consents`: `ByPaymentRef` (partition `payment_ref` (S), no sort key —
payments are 1:1 with consents). Add to the `TableDef` in CSN-001's `scripts/local-ddb-init.py`
entry for `consents` as a new GSI (no numeric sort key → no `attr_types` addition). Settings:
`S.consents_by_payment_ref_index` (default `"ByPaymentRef"`). When TXR is not built the function is
present but uncalled.

### 4.3 Rate-limit helper (`app/services/rate_limit.py`)

Add `rate_limit_consent(consent_id: str, category: str) -> None` immediately after
`rate_limit_kyc_partner_api` (`rate_limit.py:385`):

```python
def rate_limit_consent(consent_id: str, category: str) -> None:
    """Per-consent hourly rate limit for AIS data reads under a consent (CSN-002).

    Keyed on consent:{consent_id} — each granted consent gets its own budget.
    Category caps (env-configurable):
      read     — S.psd2_consent_rl_read_per_hour    (default 1000)
      refresh  — S.psd2_consent_rl_refresh_per_hour (default 100)
    Same 429 shape as rate_limit_kyc_partner_api (code, limit, window_seconds, Retry-After).
    """
    caps = {
        "read":    int(getattr(S, "psd2_consent_rl_read_per_hour",    1000) or 1000),
        "refresh": int(getattr(S, "psd2_consent_rl_refresh_per_hour", 100)  or 100),
    }
    cap = caps.get(category)
    if cap is None:
        return
    win = 3600
    sid = f"rl#consent#{category}"
    key = f"consent:{consent_id or 'unknown'}"
    if not _bucket_limit(key, sid, cap, win):
        raise HTTPException(
            status_code=429,
            detail={
                "code": "consent_rate_limited",
                "message": "Too many requests under this consent; try again later",
                "category": category,
                "limit": cap,
                "window_seconds": win,
            },
            headers={"Retry-After": str(win)},
        )
```

A cap value of `0` (env override) leaves `_bucket_limit`'s `max_n=0` path: the first request
returns `False` and the call 429s immediately. This is intentional — operators can fully disable a
category by setting the cap to 0.

### 4.4 Router additions (`app/routers/psd2_consents.py`)

Two new endpoints added to the existing router (defined by CSN-001, prefix `/ui/consents`,
`Depends(require_ui_session)`, CSRF enforced on non-GET per CLAUDE.md):

```python
@router.post("/{consent_id}/sca", response_model=ConsentScaOut)
async def begin_consent_sca(
    consent_id: str,
    req: Request,
    ctx: dict = Depends(require_ui_session),

        request_consent_sca, ctx["user_sub"], consent_id, req

@router.post("/{consent_id}/accept", response_model=ConsentOut)

        accept_consent, ctx["user_sub"], consent_id, req

```

Both are behind `S.psd2_consents_enabled` (the router is not registered when the flag is off — same
conditional-registration pattern used in `app/main.py` for `browser_ssh_terminal_enabled`).

No public endpoints in CSN-002. No `API_KEY_ROUTE_EXEMPTIONS` additions. No new startup tasks.

## 5. Detailed Behavior & Edge Cases

### SCA flow — happy path

```
Client                         Backend
  │ POST /ui/consents          │  → status=INITIATED, sca_challenge_id=null
  │ POST /ui/consents/{id}/sca │  → create_action_challenge(purpose="consent_sca")
  │                            │     stamp sca_challenge_id on consent item
  │                            │  ← {challenge_id, required_factors}
  │ POST /ui/mfa/totp/verify   │  → mark_factor_passed(challenge_id, "totp")
  │    (existing route)        │  ← {passed: {totp: true}, remaining_factors: []}
  │ POST /ui/consents/{id}/accept  → load_challenge_or_401 → challenge_done → true
  │                            │     conditional update INITIATED→ACCEPTED
  │                            │     revoke_challenge
  │                            │  ← ConsentOut{status="ACCEPTED"}
```

### SCA — error paths

| Situation | HTTP code | `detail.code` |
|---|---|---|
| `/sca` on ACCEPTED consent | 409 | `already_accepted` |
| `/sca` on REVOKED/EXPIRED consent | 409 | `invalid_status` |
| `/accept` before `/sca` (no `sca_challenge_id`) | 403 | `sca_not_initiated` |
| `/accept` before all factors pass | 403 | `sca_incomplete` |
| `/accept` after challenge TTL (300s) expires | 401 | (raised by `load_challenge_or_401`) |
| `/accept` replay on ACCEPTED consent | 409 | `already_accepted` (conditional check fails) |
| OTP rate-limit exceeded during `/ui/mfa/*/verify` | 429 | (existing `rate_limit_mfa_verify`) |
| Stolen/replayed challenge (second `/accept`) | 409 | `already_accepted` (challenge already revoked) |

`revoke_challenge` is best-effort (catches all exceptions at `sessions.py:530`), so the
`load_challenge_or_401` guard (`it.get("revoked")`) catches replays on the next call.

### PIS consent creation validation

```
consent_type="PIS", payment_ref=null      → 400 payment_ref_required
consent_type="PIS", payment_ref="txr_abc" → OK (opaque ref stored as-is until TXR lands)
consent_type="AIS", payment_ref="txr_abc" → 400 payment_ref_not_allowed
```

The `payment_ref` field is stored on the item but never validated against the `txn_requests` table
in CSN-002 — the TXR cluster does not need to be built first. CSN-002 ships `consent_authorizes_payment`
as a callable service, not a cross-table foreign-key check.

### `consent_authorizes_payment` — money-safety invariants

- Returns `True` only when `status == "ACCEPTED"` AND `consent_type == "PIS"` AND
  `valid_until > now_ts()`. A revoked, expired, or INITIATED consent always returns `False`.
- The function is read-only; it never writes any table (not `billing`, `billing_shared`, `tip_ledger`,
  `creator_payouts`). The TXR execution engine (TXR-004) is the only caller that may follow a `True`
  return with a ledger write.
- A PIS consent does NOT auto-revoke after use. The TXR engine is responsible for deciding whether
  a PIS consent is `recurring: false` and should be revoked post-execution (out of scope for CSN-002;
  a TXR-004 design responsibility — `OBP_TXN_REQUESTS_SCA_TICKETS.md` does not currently contain
  any line referencing PIS consent lifecycle; the prior `:240` citation was incorrect — that line
  covers wallet-delta logic unrelated to consent revocation).

### Rate-limit edge cases

- A `consent_id` for a non-existent consent still consumes quota — the helper does not verify
  consent existence (mirrors `rate_limit_kyc_partner_api`'s `api_key_id` handling). Callers
  are expected to check consent validity before calling the throttle.
- Two concurrent requests from the same consent on the same worker: `_bucket_limit` does a
  get + put (not atomic). Under extreme concurrency a brief over-count is possible (same trade-off
  as all other `_bucket_limit` callers). This is acceptable — the bucket is a soft throttle.
- Cap `0` disables the category: `_bucket_limit(key, sid, 0, win)` → `count(0) >= max_n(0)` →
  returns `False` on the very first call → always 429. Use `cap=None`/missing env to disable
  enforcement entirely.

### `required_factors` = empty list

If the resource owner has no enrolled MFA factors, `compute_required_factors` returns `[]`.
`challenge_done` with `required=[]` returns `True` immediately (vacuous truth, `sessions.py:568`
`all(... for f in [])` = `True`). This means the challenge is "pre-passed" — `/accept` succeeds
without any OTP flow. For PIS consents this is a policy risk: operators SHOULD enforce at least one
factor via `S.psd2_consent_pis_require_sca_factor` (new boolean, default `True`). When set,
`request_consent_sca` raises `409 sca_enrollment_required` for PIS if `required_factors` is empty,
matching the TXR-003 policy (`OBP_TXN_REQUESTS_SCA_TICKETS.md:175`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### Dev/prod parity

- **No `if S.dev_mode:` branch anywhere in CSN-002.** The SCA challenge uses
  `sessions.create_action_challenge` which writes to `T.sessions` (DynamoDB Local in dev, real
  DynamoDB in prod) with the same item shape. OTP delivery inside the existing MFA verify routes
  (`ui_mfa.py:51-205`) already has its own dev-mock path (`mfa.py`) — CSN-002 inherits that
  without forking it.
- **KMS:** CSN-002 stores no secrets. `kms_encrypt`/`kms_decrypt` (`app/core/crypto.py:16-25`)
  are not called. The `payment_ref` field is an opaque string; it is not a secret.
- **Rate-limit bucket:** `_bucket_limit` (`rate_limit.py:60`) uses `T.sessions` — DynamoDB Local
  in dev, real DynamoDB in prod, same code path (SECOPS-007 parity — same as
  `rate_limit_kyc_partner_api:397`).

### Idempotency

- **`POST /ui/consents/{id}/sca` is idempotent:** calling it twice on the same INITIATED consent
  overwrites `sca_challenge_id` with a fresh challenge, invalidating the previous one (old
  challenge is NOT explicitly revoked; it will expire per its 300-second TTL). This is acceptable
  — the client re-initiates SCA when the first challenge is lost/expired.
- **`POST /ui/consents/{id}/accept` is idempotent:** the conditional `update_item` (`status =
  'INITIATED'`) is a no-op if already ACCEPTED; the 409 is mapped to a readable code so the client
  can distinguish "succeeded on an earlier attempt" from a real conflict.
- **`consent_authorizes_payment` is a pure read:** idempotent by construction.

### Security invariants

- **Ownership is always enforced by DDB access pattern.** `get_consent(owner_sub, consent_id)` uses
  `Key={"owner_sub": owner_sub, "consent_id": consent_id}` (PK+SK lookup — the `consents`
  table SK attribute is `consent_id`, not `session_id`) — a foreign `consent_id` returns
  `None → 404`. No cross-user data exposure is possible.
- **Challenge replay is prevented** by `revoke_challenge` at accept-time + `load_challenge_or_401`'s
  `it.get("revoked")` check on subsequent calls.
- **SCA is non-bypassable for PIS:** `_consent_requires_sca` returns `True` unconditionally for
  `consent_type="PIS"`, and `accept_consent` rejects `403 sca_not_initiated` if `sca_challenge_id`
  is null. An operator cannot disable PIS SCA via env vars.

### Money-safety

CSN-002 is not a money-movement path. The only money-related surface is `consent_authorizes_payment`:

- It is **read-only** (one DDB `query`, no writes).
- It gates on `status == "ACCEPTED"` + `valid_until > now_ts()` — an expired or non-accepted
  consent can never authorize a payment.
- It **never** calls `new_ledger_entry`, `apply_wallet_delta`, `settle_or_reverse_ledger`,
  `_fraud_gate`, or any Stripe/PayPal/CCBill SDK method.
- The fraud gate in `app/routers/billing.py` (`_fraud_gate(...)`) and the charge paths in
  `billing.py` remain the exclusive entry points for money movement; CSN-002 adds no parallel path.

## 8. Backward Compatibility & Migration

### Zero-impact when flag is off (the default)

The router is not registered in `app/main.py` when `S.psd2_consents_enabled` is `False`. Existing
tests, E2E specs, billing paths, and MFA flows are unaffected. The `rate_limit_consent` function
is added to `rate_limit.py` but is not called by any existing route.

### Additive DDB changes

Two new optional fields on `consents` items (`payment_ref`, `sca_challenge_id`). Old items without
these fields are valid — `item.get("payment_ref")` returns `None`. No migration or backfill is
needed; no existing attribute is renamed or removed.

The `ByPaymentRef` GSI on `consents` is new (CSN-001's table initially has two GSIs; this is a
third). Adding a GSI to an existing DynamoDB table:
- **Dev:** re-run `scripts/local-ddb-init.py` (or `just restart`) to recreate the table with the
  new GSI. Pre-existing data is lost (acceptable in dev).
- **Prod:** issue an `UpdateTable` API call to add the GSI asynchronously. The table remains
  available during the backfill. No application code reads `ByPaymentRef` until CSN-002 is
  deployed (the function is behind the `psd2_consents_enabled` flag).

### Consent items from CSN-001 before CSN-002 is deployed

CSN-001 creates INITIATED consents with no `sca_challenge_id`. When CSN-002 is enabled on a live
instance, those pre-existing items can be accepted only after a `/sca` call sets the challenge ID.
`accept_consent` detects the null `sca_challenge_id` and returns `403 sca_not_initiated` rather
than treating the absent field as "SCA already done". This is the safe default.

### Model extension

`ConsentCreateIn.consent_type` gains `"PIS"` as a valid literal. Existing `"AIS"` clients send no
`consent_type` field (it defaults to `"AIS"`) and are unaffected.

## 10. Open Questions / Assumptions

1. **`required_factors` empty + PIS consent.** The spec defaults to `409 sca_enrollment_required`
   (gated by `S.psd2_consent_pis_require_sca_factor`, default `True`). If the product team decides
   AIS consents with zero enrolled factors should silently self-accept (vacuous SCA), the threshold
   setting suffices. Final decision deferred to security review.

2. **PIS consent single-use vs. recurring.** A PIS consent with `recurring=True` can authorize
   multiple TXR executions until `valid_until`. Whether TXR-004 should revoke a non-recurring PIS
   consent after its first execution is a TXR-004 design decision (out of scope here). CSN-002
   leaves `recurring` on the item for TXR to inspect.

3. **`ByPaymentRef` GSI on the `consents` table.** `consent_authorizes_payment` needs this index.
   Alternatively, the TXR execution engine could store a denormalized `authorized_by_consent_id`
   field and re-verify by loading the consent directly (no GSI). The GSI approach is cleaner for
   the `payment_ref → consent` lookup direction required by TXR-004. Assumption: GSI is added.

4. **SCA TTL.** Default 300 seconds (matching TXR-003). If a user's TOTP app is unavailable, they
   must restart the `/sca` flow. Consider `S.psd2_consent_sca_ttl_seconds` (default 300) to make
   it configurable without code change — not added here to keep the Settings delta minimal.

5. **Audit trail for expired challenges.** `revoke_challenge` is best-effort. If the backend
   restarts between `/accept` and the revoke write, the challenge row will expire naturally per its
   DynamoDB TTL. A paranoid implementation would write the revoke as part of a DynamoDB transact-
   write with the consent status flip; not required here given the 409 idempotency guard.
