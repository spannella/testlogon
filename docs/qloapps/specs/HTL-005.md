# HTL-005 — Room Type entity — child rows on the `hotels` partition

**Type**: Feature | **Priority**: P1 | **Estimate**: 1.5d
**Source**: `docs/qloapps/ROOMTYPES_ROOMS_HOUSEKEEPING_TICKETS.md` §HTL-005 + "Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A

---

## 1. Summary & Goal

HTL-005 adds the **Room Type** entity to the Hotel-PMS vertical. A Room Type is the bookable nightly "product" of a hotel — the category a guest reserves (e.g. `"Deluxe King"`), carrying occupancy, bed-type, size, photos, and a base nightly rate. It is stored as a `ROOMTYPE#{room_type_id}` **child row co-located on the same DynamoDB partition** as the parent hotel's `META` header row (the FAC header+child idiom, `docs/ofbiz/specs/FAC-001.md` §3 "Table: `facilities`"). The deliverables are:

1. **Data model** — `ROOMTYPE#{room_type_id}` child rows on the existing `hotels` table (PK=`hotel_id`, SK=`ROOMTYPE#{id}`), one new GSI (`GSI_HOTEL_ROOMTYPES`) added to the existing HTL-001 `TableDef`, and Pydantic models `RoomTypeIn` / `RoomTypeOut` / `RoomTypeUpdateIn` in `app/models.py`.
2. **Service functions** in `app/services/hotel_pms.py` (the cluster service file landed by HTL-001) — `create_room_type`, `get_room_type`, `list_room_types`, `update_room_type`, `archive_room_type`.
3. **Flag gating** — every entrypoint calls `_require_enabled()` first, so with `HOTEL_PMS_ENABLED=false` (the default) the ticket is a byte-for-byte no-op.

HTL-005 ships **service layer only**. The HTTP router and the frontend are later tickets in the cluster. With the master flag off, no new behaviour is exposed; with the flag on, the `hotels` table already exists (HTL-001 precondition) and Room Type rows co-locate on it — **no second table is created**.

Room Type is **net-new**. The generic catalog item (`app/routers/catalog.py:350-392` `create_item`) is a PARTIAL analogue — it carries `name` / `price_cents` / `image_urls` / a free-form `attributes` map (gap analysis §A row 2, `QLOAPPS_GAP_ANALYSIS.md:70`) — but it has **no occupancy, no bed-type, and no per-hotel parent semantics**, so the Room Type field set is modeled fresh rather than forced onto the catalog shape. The structural model is the PROP-002 Unit child-row pattern (`docs/open-property/specs/PROP-002.md` §3.1): a Room Type ≈ a PROP Unit nested under a parent header, but keyed by `hotel_id` and carrying hospitality (nightly-rate / occupancy / bed-type) rather than long-let (market-rent / bedrooms / occupancy-status) attributes. The two domains never overlap.

## 2. Context & Current State

### 2.1 Gap — no Room Type entity exists today

`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A row 2 (`:70`) records the Room Type entity as **PARTIAL**: "generic catalog item has `name`/`price_cents`/`image_urls`/free-form `attributes` (`catalog.py:353-392`); no occupancy/bed-type/per-hotel semantics; variant depth PLANNED only (PRD-006/007)." A `grep -rn "room_type_id\|ROOMTYPE#\|base_occupancy" app/` returns no hotel-PMS results. The closest structural artefact is the FAC `LOC#{location_id}` child-row idiom and the PROP-002 `UNIT#{unit_id}` child row — both co-locate child rows with a `META` header on one partition. **The table shape is reused; the field set is not.**

### 2.2 The `hotels` table and flag are HTL-001's deliverable

HTL-005 depends entirely on HTL-001. Before HTL-005 can merge, HTL-001 must have:

- Created the `hotels` DynamoDB table (PK=`hotel_id`, SK=`META` + child rows) via a `TableDef` in `scripts/local-ddb-init.py` (the `TableDef` dataclass is at `scripts/local-ddb-init.py:28-36`; the `_table_defs()` list begins at `:43`).
- Added `S.hotel_pms_enabled` (env `HOTEL_PMS_ENABLED`, default `false`) and `S.hotels_table_name` to `app/core/settings.py`.
- Wired the `T.hotels` table handle in `app/core/tables.py`.
- Defined `_flag_on()`, `_require_enabled()`, and the `_audit()` lazy-import wrapper in the new file `app/services/hotel_pms.py`, plus the parent hotel CRUD (`create_hotel` / `get_hotel`) with the owner (`owner_sub`) ownership field on the `META` row.

HTL-005 **extends `hotel_pms.py` in place**, adds Room Type Pydantic models to `app/models.py`, and **amends** the `hotels` `TableDef` in `scripts/local-ddb-init.py` to add `GSI_HOTEL_ROOMTYPES`. No new service file, settings key, or table is introduced.

### 2.3 Flag-gate pattern (carried from HTL-001 / `inventory.py`)

The canonical flag-gate template is `app/services/inventory.py:50-56`:

Every Room Type service function must call `_require_enabled()` as its **first statement** — identical to how every `app/routers/inventory.py` handler delegates to `inv._require_enabled()` at the top (`app/routers/inventory.py:31-33`, then called at `:37`, `:46`, `:63`, `:79`). The 404 (not 403) on flag-off is deliberate: the entity simply does not exist when the vertical is disabled. Cross-cutting constraint: "Mirror the `INVENTORY_RESERVATIONS_ENABLED` contract exactly … raising **404** when off."

### 2.4 Audit wrapper (reused from `inventory.py:92-98`)

`app/services/inventory.py:92-98` provides the lazy-import `_audit()` wrapper that calls `app.services.alerts.audit_event` and swallows all exceptions:

```python
def _audit(event: str, user_sub: str, **fields: Any) -> None:
    try:
        from app.services.alerts import audit_event
        audit_event(event, user_sub or "system", None, **fields)
    except Exception:
        pass
```

HTL-001 already copies this into `hotel_pms.py`. Room Type functions reuse the same `_audit()` already present in the file — no new audit primitive is created.

### 2.5 Header+child co-location idiom (FAC-001 §3 / PROP-002 §3.1)

`docs/ofbiz/specs/FAC-001.md` §3 ("Table: `facilities`", `:77-84`) defines the canonical idiom: a partition holds a `META` header row plus per-facility `LOC#{location_id}` child rows, "co-located on the same partition for cheap per-facility scans." `FAC-001.md:310` shows `create_location` deriving `location_id = uuid4().hex` (non-deterministic — a facility may hold many locations with the same label). PROP-002 §3.1 applies this exact idiom to rental Units (`UNIT#{unit_id}` on the `properties` partition). HTL-005 applies it to Room Types: `ROOMTYPE#{room_type_id}` on the `hotels` partition, with the same `uuid4().hex` non-deterministic id contract.

### 2.6 `now_ts()` for timestamps

`created_at` and `updated_at` use `now_ts()` (`app/core/time.py:2`), which returns `int(time.time())` — integer Unix seconds. No ISO strings (the catalog router uses `now_iso()` at `app/routers/catalog.py:48`; the Hotel-PMS vertical does **not** follow that — it uses the integer convention shared by `inventory.py` and PROP-002).

### 2.7 Decimal coercion for numeric DynamoDB attributes

DynamoDB returns numeric attributes as `decimal.Decimal` via the boto3 resource API. `base_occupancy_adults`, `base_occupancy_children`, `max_occupancy`, `size_sqft`, `base_nightly_rate_cents`, `created_at`, `updated_at` are stored as `N` and must be coerced to `int` before returning from the service (so `RoomTypeOut` validates and round-trips cleanly). This is the same coercion requirement noted in PROP-002 §2.7 and the CLAUDE.md `MessageEncryptionEnvelope Decimal coercion` pattern. All Room Type numerics are integers — there is no `float` field (contrast PROP-002's `bathrooms`).

### 2.8 `list_room_types` GSI ordering + cursor pagination

DynamoDB query results on the base partition are ordered by SK (`ROOMTYPE#{uuid4().hex}` — non-meaningful for display). The `GSI_HOTEL_ROOMTYPES` index (PK=`hotel_id`, SK=`created_at`) provides a newest-first ordered fast path. `list_room_types` queries the GSI with `ScanIndexForward=False` and paginates via `encode_cursor` / `decode_cursor` (`app/core/cursor.py:94,103`). It returns the `{items, count, cursor}` shape (`{"room_types": [...], "count": int, "cursor": str | None}`) per CLAUDE.md `host_inventory.list_hosts`.

### 2.9 `GSI_HOTEL_ROOMTYPES` merging with HTL-001's `TableDef`

HTL-001 defines the `hotels` `TableDef` (PK=`hotel_id`, SK=`sk`) with its own GSI(s) (e.g. an owner index). HTL-005 adds `GSI_HOTEL_ROOMTYPES` (PK=`hotel_id`, SK=`created_at`, numeric) to the **same** `TableDef`. If HTL-001 merges first, HTL-005 amends the `TableDef` entry; if implemented together, a single `TableDef` with all GSIs is written at once. `just restart` recreates the table — no incremental `UpdateTable` migration in dev. The numeric SK MUST be declared via `attr_types={"created_at": "N"}` (CLAUDE.md numeric-GSI gotcha; cross-cutting constraint "`attr_types` for numeric GSI keys"; pattern at `scripts/local-ddb-init.py:34` `attr_types={...}`) — omitting it stores `created_at` as String → `ValidationException` at query time.

### 2.10 The catalog item is a deliberate non-reuse

`app/routers/catalog.py:350-392` `create_item` writes an `item` dict with `name`, `price_cents`, `image_urls`, and a free-form `attributes` map on `T.catalog` (PK=`CAT#{category_id}`, SK=`ITEM#{item_id}`). It is the closest existing "bookable product" but is **rejected as the storage model** because: (1) it is keyed under a generic catalog category, not a hotel; (2) it has no occupancy / bed-type / size first-class fields (they would be buried in the untyped `attributes` map, losing Pydantic validation and the `max_occupancy >= base sum` invariant); (3) its money field (`price_cents`) is a one-off sale price, not a per-night rate. HTL-005 therefore models the field set fresh on the `hotels` partition. This is documented in the gap analysis as PARTIAL precisely because of these missing semantics (`QLOAPPS_GAP_ANALYSIS.md:70`).

## 3. Data Model

### 3.1 Child row on the `hotels` table

Room Types are child rows on the **same** partition as the parent hotel `META` header. No second table is created. The PK/SK design follows the FAC `LOC#{location_id}` / PROP-002 `UNIT#{unit_id}` idiom applied to bookable nightly products.

**Primary key**

| Key | Type | Value |
|---|---|---|
| `hotel_id` | S (PK) | Same partition as the parent `META` row (from HTL-001) |
| `sk` | S (SK) | `"ROOMTYPE#{room_type_id}"` — `room_type_id = uuid4().hex` (non-deterministic; a hotel may hold several types with the same name) |

**Room Type row attributes**

| Attribute | DDB Type | Constraints / Notes |
|---|---|---|
| `hotel_id` | S | PK; FK to parent hotel `META` row |
| `sk` | S | `"ROOMTYPE#{room_type_id}"` |
| `room_type_id` | S | Convenience copy of the id; `uuid4().hex` (32-char hex string) |
| `name` | S | Room-type name (e.g. `"Deluxe King"`); non-empty string |
| `description` | S | Free-text description (may be empty) |
| `base_occupancy_adults` | N | Included adult capacity; non-negative integer |
| `base_occupancy_children` | N | Included child capacity; non-negative integer |
| `max_occupancy` | N | Hard max guests (adults + children); integer; `>= base_occupancy_adults + base_occupancy_children` |
| `bed_type` | S | Literal: `single` \| `twin` \| `double` \| `queen` \| `king` \| `suite` |
| `size_sqft` | N | Room size in square feet; non-negative integer |
| `base_nightly_rate_cents` | N | Base nightly rate in **cents** (integer; money-as-cents convention — never store fractional dollars) |
| `photo_urls` | L | List of photo URL strings (may be empty) |
| `status` | S | Literal: `active` \| `archived`; default `"active"` on create |
| `created_at` | N | `now_ts()` — integer Unix seconds (`app/core/time.py:2`) |
| `updated_at` | N | `now_ts()` — stamped on every `update_room_type` / `archive_room_type` call |

**Rationale for non-deterministic `room_type_id`**: a hotel may legitimately hold multiple room types with the same `name` over time (e.g. two `"Deluxe King"` types differing only in floor or view, or a renamed/re-created type). `uuid4().hex` avoids collisions and mirrors the FAC `create_location` and PROP-002 Unit id contracts. The trade-off: create is **not** idempotent on (hotel_id, name) — callers must dedupe before retrying (see §7.2).

### 3.2 GSI — `GSI_HOTEL_ROOMTYPES`

Added to the **same** `hotels` `TableDef` introduced by HTL-001. Purpose: list a hotel's room types newest-first, paginated, without a full partition scan that co-reads the `META` header.

| Index name | PK | SK | `attr_types` |
|---|---|---|---|
| `GSI_HOTEL_ROOMTYPES` | `hotel_id` (S) | `created_at` (N) | `{"created_at": "N"}` (numeric SK) |

**`TableDef` after HTL-005** (illustrative — reconcile with HTL-001's own GSIs):

```python
TableDef(
    _resolve_table_name(S.hotels_table_name, "hotels"),
    "hotel_id",
    "sk",
    gsi=[
        # ... HTL-001's own GSIs (e.g. owner index) ...
        {"index_name": "GSI_HOTEL_ROOMTYPES", "partition_key": "hotel_id", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

> Note: Room Type rows are **also** queryable by the base `hotels` PK
> (`Key={"hotel_id": hid}` + `begins_with(sk, "ROOMTYPE#")`) for a per-hotel scan
> that co-reads the `META` header; `GSI_HOTEL_ROOMTYPES` is the ordered/paginated fast path.

The `META` header row (SK=`"META"`) carries `created_at` too, so it **will appear** in `GSI_HOTEL_ROOMTYPES`. `list_room_types` must therefore exclude it — see §5.2.

`just restart` recreates the `hotels` table with the new GSI. In production, `GSI_HOTEL_ROOMTYPES` is added via `UpdateTable` + async backfill before HTL-005 code is deployed (during backfill the index may be incomplete — acceptable since the whole vertical defaults to flag-off; see §8.4).

### 3.3 Pydantic models (`app/models.py`)

Add adjacent to the `HotelIn` / `HotelOut` / `HotelUpdateIn` models introduced by HTL-001.

**`RoomTypeIn`** — creation payload:

```python
class RoomTypeIn(BaseModel):
    name: str
    description: str = ""
    base_occupancy_adults: int = Field(ge=0)
    base_occupancy_children: int = Field(default=0, ge=0)
    max_occupancy: int = Field(ge=1)
    bed_type: Literal["single", "twin", "double", "queen", "king", "suite"]
    size_sqft: int = Field(default=0, ge=0)
    base_nightly_rate_cents: int = Field(ge=0)
    photo_urls: list[str] = Field(default_factory=list)

    @model_validator(mode="after")
    def _check_occupancy(self) -> "RoomTypeIn":
        if self.max_occupancy < self.base_occupancy_adults + self.base_occupancy_children:
            raise ValueError("max_occupancy must be >= base_occupancy_adults + base_occupancy_children")
        return self
```

**`RoomTypeOut`** — full read response (all persisted fields):

```python
class RoomTypeOut(BaseModel):
    hotel_id: str
    room_type_id: str
    name: str
    description: str
    base_occupancy_adults: int
    base_occupancy_children: int
    max_occupancy: int
    bed_type: Literal["single", "twin", "double", "queen", "king", "suite"]
    size_sqft: int
    base_nightly_rate_cents: int
    photo_urls: list[str]
    status: Literal["active", "archived"]
    created_at: int
    updated_at: int
```

**`RoomTypeUpdateIn`** — partial update; all fields optional:

```python
class RoomTypeUpdateIn(BaseModel):
    name: Optional[str] = None
    description: Optional[str] = None
    base_occupancy_adults: Optional[int] = Field(default=None, ge=0)
    base_occupancy_children: Optional[int] = Field(default=None, ge=0)
    max_occupancy: Optional[int] = Field(default=None, ge=1)
    bed_type: Optional[Literal["single", "twin", "double", "queen", "king", "suite"]] = None
    size_sqft: Optional[int] = Field(default=None, ge=0)
    base_nightly_rate_cents: Optional[int] = Field(default=None, ge=0)
    photo_urls: Optional[list[str]] = None
```

`status` is **not** in `RoomTypeUpdateIn` — status transitions go through the dedicated `archive_room_type` function (`active` → `archived`), mirroring how PROP-001 archives Properties via a dedicated function rather than a free-form status field. The cross-field occupancy invariant on `RoomTypeUpdateIn` (a partial patch may move only one of the three occupancy fields) is re-validated at the service layer against the **merged** post-update values, since the model alone cannot validate fields the caller omitted (see §5.4).

## 4. API / Service Design

### 4.1 Service additions: `app/services/hotel_pms.py`

All five functions are added to the existing `hotel_pms.py` file created by HTL-001. No second service file is created. Each calls `_require_enabled()` first.

A shared helper for the SK is added once:

```python
def _roomtype_sk(room_type_id: str) -> str:
    return f"ROOMTYPE#{room_type_id}"
```

(mirrors `inventory._location_sk` at `app/services/inventory.py:58-59`).

#### 4.1.1 `create_room_type`

```python
def create_room_type(
    hotel_id: str,
    *,
    name: str,
    description: str = "",
    base_occupancy_adults: int,
    base_occupancy_children: int = 0,
    max_occupancy: int,
    bed_type: str,
    size_sqft: int = 0,
    base_nightly_rate_cents: int,
    photo_urls: list[str] | None = None,
    user_sub: str,
) -> dict:
```

**Behavior**:
1. `_require_enabled()`.
2. Reads the parent hotel `META` row: `T.hotels.get_item(Key={"hotel_id": hotel_id, "sk": "META"})`. Raises `HTTPException(404, "Hotel not found")` if absent (strongly-consistent `get_item`, not a GSI query).
3. Asserts caller ownership: if `meta["owner_sub"] != user_sub` raise `HTTPException(403, "Not the hotel owner")` (see §5.5 for the ROOT note).
4. Re-validates the occupancy invariant defensively: if `max_occupancy < base_occupancy_adults + base_occupancy_children` raise `HTTPException(422, ...)` (the Pydantic model already enforces this at the router edge; the service guard protects direct callers and tests).
5. Generates `room_type_id = uuid4().hex`.
6. Builds the row dict: all attributes, `sk=_roomtype_sk(room_type_id)`, `status="active"`, `created_at=now_ts()`, `updated_at=now_ts()`, `photo_urls = photo_urls or []`.
7. `T.hotels.put_item(Item=row)` — unconditional put (UUID id, no collision possible).
8. `_audit("hotel.room_type.created", user_sub, hotel_id=hotel_id, room_type_id=room_type_id, name=name)`.
9. Returns the row dict with numeric fields coerced to `int`.

> Unlike the parent hotel `META` (which carries an owner/created-by), child Room Type rows do **not** maintain a denormalized counter on `META` (contrast PROP-002's `unit_count`). HTL-005 keeps the header counter-free; if a `room_type_count` is wanted later it is an additive follow-up using the `ADD` atomic-counter pattern (`app/routers/messaging.py:4996`, `app/routers/newsfeed.py:3714`). This avoids the create/delete consistency surface in MVP.

#### 4.1.2 `get_room_type`

```python
def get_room_type(hotel_id: str, room_type_id: str) -> dict | None:
```

1. `_require_enabled()`.
2. `T.hotels.get_item(Key={"hotel_id": hotel_id, "sk": _roomtype_sk(room_type_id)})`.
3. Returns the coerced item dict or `None` if absent. (Never raises 404 — the caller/router maps `None` to 404; this mirrors `inventory.get_inventory` returning `None`.)

#### 4.1.3 `list_room_types`

```python
def list_room_types(
    hotel_id: str,
    *,
    status: str = "active",
    cursor: str | None = None,
    limit: int = 50,
) -> dict:
```

1. `_require_enabled()`.
2. Queries `GSI_HOTEL_ROOMTYPES`:
   ```python
   kwargs = {
       "IndexName": "GSI_HOTEL_ROOMTYPES",
       "KeyConditionExpression": Key("hotel_id").eq(hotel_id),
       "ScanIndexForward": False,         # newest-first by created_at
       "Limit": limit,
   }
   start = decode_cursor(cursor)
   if start:
       kwargs["ExclusiveStartKey"] = start
   resp = T.hotels.query(**kwargs)
   ```
3. Filters out the `META` row (`sk == "META"`) and any row whose `sk` does not begin with `"ROOMTYPE#"`, then applies the optional `status` filter (`status in {"active","archived"}`; the literal `"all"` skips the filter). Filtering is done in Python after the page fetch — see §5.2 for why a server-side `FilterExpression` on a GSI does not reduce the page budget.
4. Coerces Decimal numerics on each surviving item.
5. Returns `{"room_types": [...], "count": len(items), "cursor": encode_cursor(resp.get("LastEvaluatedKey"))}` (cursor is `None` when the page is the last). The `{items, count, cursor}` shape matches CLAUDE.md `host_inventory.list_hosts`.

#### 4.1.4 `update_room_type`

```python
def update_room_type(hotel_id: str, room_type_id: str, *, user_sub: str, **kwargs) -> dict:
```

Accepted `kwargs`: `name`, `description`, `base_occupancy_adults`, `base_occupancy_children`, `max_occupancy`, `bed_type`, `size_sqft`, `base_nightly_rate_cents`, `photo_urls`.

1. `_require_enabled()`.
2. Reads the existing row via `get_room_type(...)`. Raises `HTTPException(404, "Room type not found")` if absent.
3. Reads the parent `META` row; raises `HTTPException(404, "Hotel not found")` if the parent is gone (orphan scenario). Verifies caller ownership (`META["owner_sub"] == user_sub`, else 403).
4. **Merged occupancy invariant**: computes the post-update values of `base_occupancy_adults`, `base_occupancy_children`, `max_occupancy` from `kwargs` falling back to the existing row, then re-checks `max_occupancy >= base_adults + base_children`; raises `HTTPException(422, ...)` on violation (this catches a partial patch that lowers `max_occupancy` below the unchanged base sum, which `RoomTypeUpdateIn` alone cannot detect).
5. Builds an `UpdateExpression` from the present `kwargs` keys plus mandatory `updated_at = :ts`; only supplied keys are written (true partial update). Uses `ExpressionAttributeNames` to escape `name` (a DynamoDB reserved word) → `#name`.
6. `T.hotels.update_item(Key={"hotel_id": hotel_id, "sk": _roomtype_sk(room_type_id)}, ..., ReturnValues="ALL_NEW")`.
7. `_audit("hotel.room_type.updated", user_sub, hotel_id=hotel_id, room_type_id=room_type_id, fields=list(kwargs.keys()))`.
8. Returns the coerced `Attributes` from the update response.

#### 4.1.5 `archive_room_type`

```python
def archive_room_type(hotel_id: str, room_type_id: str, *, user_sub: str) -> dict:
```

1. `_require_enabled()`.
2. Reads the existing row via `get_room_type(...)`; raises `HTTPException(404)` if absent.
3. Reads `META`, verifies existence + ownership (same as update step 3).
4. `T.hotels.update_item(... UpdateExpression="SET #s = :archived, updated_at = :ts", ExpressionAttributeNames={"#s": "status"}, ExpressionAttributeValues={":archived": "archived", ":ts": now_ts()}, ReturnValues="ALL_NEW")`.
5. `_audit("hotel.room_type.archived", user_sub, hotel_id=hotel_id, room_type_id=room_type_id)`.
6. Returns the coerced updated row.

Archiving is a **soft** state change (status flip), not a hard delete — a Room Type that has historical bookings (later cluster tickets) must remain referenceable. There is therefore no `delete_room_type` and no no-raise-delete contract in HTL-005 (contrast PROP-002's `delete_unit`; the cross-cutting "no-raise delete contract" applies to the Rooms ticket HTL-006, not Room Types). Re-activation, if needed, is an additive follow-up.

### 4.2 Router endpoints (later-ticket preview)

HTL-005 ships only the service layer. The cluster router exposes these functions over HTTP with the standard auth split:

| Method | Path | Auth dep | Service call |
|---|---|---|---|
| `GET` | `/ui/hotels/{hotel_id}/room-types` | `require_ui_session` | `list_room_types(hotel_id, status=?, cursor=?, limit=?)` |

## 5. Detailed Behavior & Edge Cases

### 5.1 Parent hotel not found on `create_room_type`

If `hotel_id` has no `META` row, `create_room_type` raises `HTTPException(404, "Hotel not found")` before writing anything — no orphaned Room Type row is ever created. The check is a strongly-consistent `get_item`, not a GSI query.

### 5.2 `list_room_types` returns only `ROOMTYPE#` rows, never `META`

Because the `META` row carries `created_at`, it is indexed by `GSI_HOTEL_ROOMTYPES` and will surface in the query result. `list_room_types` therefore drops any item where `sk == "META"` or `not sk.startswith("ROOMTYPE#")` in Python. Per CLAUDE.md "DDB FilterExpression doesn't reduce page size" — DynamoDB fetches up to 1MB *before* applying a `FilterExpression`, so a server-side filter would not save read capacity and could yield a short page that still needs the cursor. Python-side filtering on the returned page is correct and the page is bounded by `Limit`. (At most one `META` row is filtered per hotel; the `status` filter may drop more — acceptable for MVP scale where a hotel holds tens of room types.)

### 5.3 `name` is a DynamoDB reserved word

`name` must be escaped via `ExpressionAttributeNames` (`#name`) in every `UpdateExpression` that touches it (`update_room_type`). `put_item` (create) is unaffected — reserved words only matter in expressions, not item maps.

### 5.4 Merged occupancy invariant on partial update

`RoomTypeIn` validates `max_occupancy >= base_adults + base_children` at create. On a partial `update_room_type`, a caller may patch only `max_occupancy` (lowering it below the unchanged base sum) or only `base_occupancy_adults` (raising it above the unchanged `max_occupancy`). `RoomTypeUpdateIn` cannot catch this (it sees only the supplied fields). The service therefore merges the patch over the existing row and re-validates the invariant (step 4.1.4 §4). Violation → `HTTPException(422)`; no write occurs.

### 5.5 Ownership enforcement — ADMIN vs ROOT

`create_room_type`, `update_room_type`, and `archive_room_type` check `META["owner_sub"] == user_sub`. This is correct for the single-platform deployment assumption (no cross-operator isolation in MVP). A ROOT user who owns the hotel passes the check; a ROOT user who does **not** own it is currently blocked. If a platform-admin override is required, condition the check: `if user.role != Role.ROOT and meta["owner_sub"] != user_sub: raise 403`. Documented as an open question (§10 item 1).

### 5.6 `status` lifecycle

A Room Type is `active` on create. `archive_room_type` flips it to `archived`. There is no `delete`. `list_room_types` defaults to `status="active"` so archived types are hidden from the default booking surface but remain readable via `get_room_type` and `list_room_types(status="archived")` / `status="all"`. No transition guard beyond active→archived is enforced (re-activation is a follow-up).

### 5.7 `base_nightly_rate_cents` is informational at this layer

HTL-005 stores `base_nightly_rate_cents` as the per-night base rate. It is **not** wired into any billing ledger, pricing-calendar, or payment primitive in this ticket. Per-date rate overrides and the booking/availability ledger are later cluster tickets. The money-as-cents integer convention is honoured (no fractional dollars; no float). No Stripe/PayPal/CCBill SDK is invoked; `T.billing` is never touched. See §7.4.

### 5.8 Decimal coercion on every read path

`get_room_type`, `list_room_types`, and the `ReturnValues="ALL_NEW"` responses from `update`/`archive` all pass items through a small `_coerce(row)` helper that maps the seven `N` fields (`base_occupancy_adults`, `base_occupancy_children`, `max_occupancy`, `size_sqft`, `base_nightly_rate_cents`, `created_at`, `updated_at`) from `Decimal` to `int`. `photo_urls` (a list) and the `S` fields pass through unchanged. Without this, `RoomTypeOut` validation accepts `Decimal` but downstream JSON/arithmetic consumers may misbehave; coercion at the service boundary is the codebase convention.

### 5.9 Empty / minimal room type

A Room Type with `description=""`, `photo_urls=[]`, `size_sqft=0`, `base_occupancy_children=0` is valid. The only hard floors are `base_occupancy_adults >= 0`, `max_occupancy >= 1`, `base_nightly_rate_cents >= 0`, and the merged occupancy invariant. A `base_occupancy_adults=0` type (e.g. a child-only or storage SKU) is permitted by the model but unusual — not blocked.

### 5.10 `list_room_types` for a hotel with no room types

Returns `{"room_types": [], "count": 0, "cursor": null}`. A GSI query that returns only the filtered-out `META` row (or nothing) is not an error.

### 5.11 Cursor stability across status filters

The cursor encodes the `LastEvaluatedKey` of the GSI query (`hotel_id` + `created_at` + base keys). Because `status` filtering happens **after** the page fetch, two pages requested with different `status` values are not interchangeable — a caller must keep `status` constant across a pagination run. This matches the inventory/host-inventory pagination contract and is documented for the router/frontend implementers.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_pms.py` must contain **no** `if S.dev_mode` branches across all five Room Type functions. The identical `T.hotels.*` code path runs in dev (boto3 intercepted by moto in-process) and prod (real DynamoDB). This matches the cross-cutting constraint: "Zero `if S.dev_mode` branches in business logic; the same `T.*` handles in both environments." The precedent is `app/services/inventory.py` — `grep dev_mode` returns only a docstring, never a code branch. Acceptance criterion: "No `if S.dev_mode` branch in the room-type service code."

### 7.2 Idempotency

`create_room_type` is **not** idempotent on (hotel_id, name) by design — the non-deterministic `uuid4().hex` id means each call creates a new row (mirrors FAC `create_location` and PROP-002 `create_unit`). Callers must dedupe at the application layer before retrying. `get_room_type` / `list_room_types` are read-only and trivially idempotent. `update_room_type` is idempotent in result (re-applying the same patch yields the same final state, differing only in `updated_at`). `archive_room_type` is idempotent in effect (re-archiving an already-archived type re-writes `status="archived"` + a new `updated_at`, no error).

### 7.3 Security — ownership & authorization

- **Ownership**: `create` / `update` / `archive` read the parent `META` row and compare `owner_sub` to `user_sub`. A non-owning ADMIN cannot mutate another operator's Room Types.
- **Auth boundary**: mutations require `require_admin_or_root_csrf` at the router (`app/auth/policy.py:100`), enforcing `role ∈ {ADMIN, ROOT}` + CSRF for cookie-auth; Bearer-auth skips CSRF (CLAUDE.md). Reads use `require_ui_session` (`app/services/sessions.py:330`) with no service-layer ownership check (single-platform read model, consistent with `inventory.py`).
- **CSRF**: cookie-auth non-GET requests require an `x-csrf-token` header matching the `ui_csrf` cookie, enforced inside `require_admin_or_root_csrf`.
- **Flag-off is 404, not 401/403**: an unauthenticated probe against a disabled vertical learns only "not found" — no entity-existence leak.

### 7.4 Money-safety — no ledger interaction

HTL-005 stores `base_nightly_rate_cents` as an informational integer only. It does **not** call `billing_shared.new_ledger_entry`, `settle_or_reverse_ledger`, `apply_balance_delta`, or `compute_due`; it does not access `T.billing`; it invokes no payment-provider SDK. The booking/availability ledger and per-date pricing are later cluster tickets and, when built, MUST route every charge through `new_ledger_entry` (never a raw `put_item`), void via `settle_or_reverse_ledger` (never `delete_item`), and read outstanding amounts via `compute_due` — these rules are stated here as forward constraints. All rate values stay in integer cents; there is no float money field anywhere in the model.

| Event | When |
|---|---|
| `hotel.room_type.created` | `create_room_type` success |
| `hotel.room_type.updated` | `update_room_type` success |

1. Add `GSI_HOTEL_ROOMTYPES` via `UpdateTable` (async backfill from existing rows). During backfill, `list_room_types` may be incomplete — acceptable since `HOTEL_PMS_ENABLED` defaults to `false`.

3. Enable `HOTEL_PMS_ENABLED=true` once the table + GSI are verified.

## 10. Open Questions / Assumptions

1. **ROOT bypass for ownership.** `create` / `update` / `archive` check `owner_sub == user_sub`; a non-owning ROOT is blocked. **Assumption**: ROOT users own hotels on a single-platform deployment, so no bypass is needed for MVP. If a platform-admin override is required, add `if user.role == Role.ROOT: pass` before the ownership check.
2. **No `room_type_count` on `META`.** HTL-005 keeps the hotel header counter-free (unlike PROP-002's `unit_count`) to avoid the atomic-counter consistency surface in MVP. **Assumption**: callers derive a count via `list_room_types` `count`; a denormalized counter is an additive follow-up (`ADD` pattern, `messaging.py:4996`).
3. **Soft-archive, no hard delete.** Room Types are archived, never deleted, to preserve referential integrity for future bookings. **Assumption**: a hard `delete_room_type` is unnecessary; re-activation (archived → active) is a follow-up if product wants it.
4. **`create` idempotency.** Non-deterministic `uuid4().hex` means no idempotency on (hotel_id, name). **Assumption**: callers dedupe; a future `GET .../room-types?name=X` search can be added without schema change.
5. **`status` filtering is post-fetch.** The `status` filter is applied in Python after the GSI page, so the page-size budget is consumed before filtering and cursors are not interchangeable across `status` values. **Assumption**: acceptable at MVP scale (tens of room types per hotel); a status-keyed GSI is a follow-up if the count grows.
6. **`base_nightly_rate_cents` is base-only.** Per-date overrides, seasonal pricing, and tax/fee composition are later cluster tickets. **Assumption**: HTL-005 stores a single base rate; the pricing-calendar ticket layers overrides on top without changing this field.
7. **`bed_type` enum scope.** The six literals (`single`/`twin`/`double`/`queen`/`king`/`suite`) cover common hospitality beds. **Assumption**: extending the enum is an additive model change; no per-hotel custom bed types in MVP.
