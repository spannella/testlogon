# HTL-006 — Individual Room entity — `hotel_rooms` table (per-hotel physical rooms)

**Type**: Feature | **Priority**: P1 | **Estimate**: 1.5d
**Source**: `docs/qloapps/ROOMTYPES_ROOMS_HOUSEKEEPING_TICKETS.md` §HTL-006 + "Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A row 3

---

## 1. Summary & Goal

HTL-006 adds the individual **Room** (physical instance) entity to the Hotel-PMS vertical. A
Room is the physical realization of a bookable Room Type (HTL-005): room number `"214"`, on
a floor, with an operational `status` (available / out_of_service) and a
`housekeeping_status` (the cleaning-workflow enum filled in by HTL-007). Structurally a Room
is **≈ an open-property PROP-002 Unit** (`docs/open-property/specs/PROP-002.md` §1, §3.1) —
the same child-row CRUD idiom — but it is **keyed by hotel** (its own table, PK=`hotel_id`)
rather than nested under the room-type, so a hotel's entire room grid is one cheap partition
query. The deliverables are:

1. **Data model** — a new `hotel_rooms` DynamoDB table (PK=`hotel_id`, SK=`ROOM#{room_id}`)
   with two GSIs (`GSI_ROOMTYPE`, `GSI_HK_STATUS`), a `TableDef` in
   `scripts/local-ddb-init.py`, a settings key `hotel_rooms_table_name`, a `T.hotel_rooms`
   handle, and Pydantic models `RoomIn` / `RoomOut` / `RoomUpdateIn` in `app/models.py`.
2. **Service functions** in `app/services/hotel_pms.py` (the cluster service landed in
   HTL-001) — `create_room`, `get_room`, `list_rooms`, `update_room`, `delete_room`.
3. **FK validation** — `create_room` validates that the parent hotel exists, the caller owns
   it, AND the supplied `room_type_id` resolves to a Room Type (HTL-005) on that hotel — a
   404 otherwise.

HTL-006 ships **no router** (that is HTL-008's deliverable) and **no frontend** (HTL-009).
The whole Hotel-PMS vertical is gated by the master flag `HOTEL_PMS_ENABLED` (default
`false`, landed in HTL-001). With the flag off, every room service entrypoint raises HTTP
404 and the platform is byte-for-byte unchanged. The `housekeeping_status` column is
**persisted** on the room row here (default `clean`) but is **mutated** by HTL-007's
dedicated transition function `set_room_housekeeping_status`, not by this ticket's generic
`update_room`.

The structural analogue is the PROP-002 Unit child-row pattern; the **contrast** is that the
generic catalog item (`app/services/catalog.py`) carries no per-hotel/physical-room
semantics (gap analysis §A row 3 records the Room entity as MISSING).

### 2.5 `delete_room` no-raise contract (mirrors host_inventory.delete_host)

`app/services/host_inventory.py:360–367` defines `delete_host`, which returns `False` (never

```python
def delete_host(user_sub: str, host_id: str) -> bool:
    """Hard-delete a host entry. Returns True if it existed."""
    raw = _get_raw(user_sub, host_id)
    if not raw:
        return False
    T.host_inventory.delete_item(Key={"user_sub": user_sub, "sk": _sk(host_id)})
```

CLAUDE.md documents this explicitly (K8s/EC2 host-inventory notes): "`delete_host` returns
`False` (never raises `HostNotFound`) for an unknown host, so a broad `except` suffices."

on a successful deletion — it never raises a 404/`HostNotFound`-style exception. This makes
the HTL-008 router idempotent on repeated DELETEs (it can map `False → 404` itself).

### 2.6 Decimal coercion for numeric DynamoDB attributes

DynamoDB returns numeric attributes as `decimal.Decimal` via the boto3 resource API.
`floor`, `created_at`, and `updated_at` are stored as `N` and must be coerced to `int` before
returning, exactly as PROP-002 §2.7 coerces `bedrooms`/`created_at` and as the CLAUDE.md
`MessageEncryptionEnvelope Decimal coercion` note documents. `inventory.py` provides the
canonical helper shape `_to_int(value, default=0)` at `app/services/inventory.py:67–73`;
HTL-001 carries an equivalent into `hotel_pms.py`. (Rooms have no float field — unlike PROP-002's
`bathrooms` — so all numerics coerce to `int`.)

### 2.7 `now_ts()` for timestamps

`created_at` and `updated_at` use `now_ts()` (`app/core/time.py:2–3`):

```python
def now_ts() -> int:
    return int(time.time())
```

Integer Unix seconds, consistent with every other entity in the platform.

### 2.8 `TableDef` + `attr_types` for numeric GSI sort keys

The `TableDef` dataclass is defined at `scripts/local-ddb-init.py:28–36`; its `attr_types`
field overrides the default `"S"` attribute type for keys that must be numeric. CLAUDE.md's
DynamoDB gotcha: "If a GSI sort key is a number (e.g. `created_at`), the `TableDef` … must
include `attr_types={"created_at": "N"}`. Missing this causes DynamoDB to store it as String
→ `ValidationException` when queried with integer values." `GSI_ROOMTYPE` has a numeric
`created_at` sort key, so `attr_types={"created_at": "N"}` is **required** on the
`hotel_rooms` `TableDef`. `GSI_HK_STATUS` has `housekeeping_status` (S) as its sort key — no
`attr_types` change for that index.

### 2.9 Cursor pagination (reused from cursor.py:94,103)

`list_rooms` paginates via the signed cursor helpers `encode_cursor`
(`app/core/cursor.py:94`) and `decode_cursor` (`app/core/cursor.py:103`). The cursor wraps
the DynamoDB `LastEvaluatedKey` in a signed, versioned envelope so a malicious client cannot
forge a `LastEvaluatedKey`. This is the same pagination machinery used across the platform.

### 2.10 `list_rooms` must loop `LastEvaluatedKey` when filtering

When `list_rooms` applies a `status` filter, CLAUDE.md's "DDB FilterExpression doesn't reduce
page size" gotcha applies: DynamoDB fetches up to 1MB **before** applying a `FilterExpression`,
so a single `query()` can return fewer than `limit` matching items even when more exist on a
later page. The per-page accumulation loop (`host_inventory.list_hosts`,
`app/services/host_inventory.py:371` comment "loops LastEvaluatedKey — FilterExpression does
NOT reduce page size", with the looping `_scan_all_hosts` at `:374+`) is the precedent. `list_rooms` accumulates filtered items across pages
until it reaches `limit` or exhausts the partition. (When no `status` filter is applied, a
single page up to `limit` is sufficient and `LastEvaluatedKey` becomes the next cursor.)

### 2.11 Why a separate table (not a child row on `hotels`)

Room Types (HTL-005) are child rows co-located on the `hotels` partition (`ROOMTYPE#{id}`),
because a hotel has few room types and they co-read cheaply with the `META` header. Rooms get
their **own** `hotel_rooms` table (PK=`hotel_id`) because: (a) a hotel may have hundreds of
physical rooms — keeping them off the `hotels` partition avoids bloating that partition and
keeps the per-hotel room grid a single cheap partition query; (b) Rooms need a cross-hotel
secondary index by `room_type_id` (`GSI_ROOMTYPE`) and a housekeeping-status bucket index
(`GSI_HK_STATUS`) that would otherwise be entangled with the hotel/room-type indexes. This is
the PROP-002 Unit child-row idiom (`docs/open-property/specs/PROP-002.md` §3.1 — a Unit ≈ a
Room) **promoted to its own table** keyed by hotel rather than nested under the parent.

### 2.12 Non-deterministic `room_id`

`room_id = uuid4().hex` (32-char hex). A hotel may renumber rooms or hold two rows with the
same `room_number` transiently during a renovation, so the id is non-deterministic — the same
contract as the PROP-002 Unit id (`docs/open-property/specs/PROP-002.md` §3.1 rationale) and
the HTL-005 Room Type id. The trade-off: `create_room` is **not** idempotent on
(hotel_id, room_number) — callers must dedupe before retrying a create (§7.2).

## 3. Data Model

### 3.1 New table: `hotel_rooms`

Unlike Room Types, Rooms get their own table. The PK/SK design follows the PROP-002 Unit
child-row idiom promoted to a standalone table keyed by hotel.

**Primary key**

| Key | Type | Value |
|---|---|---|
| `hotel_id` | S (PK) | All of a hotel's rooms on one partition |
| `sk` | S (SK) | `"ROOM#{room_id}"` — `room_id = uuid4().hex` (non-deterministic; a hotel may renumber rooms) |

**Room row attributes**

| Attribute | DDB Type | Constraints / Notes |
|---|---|---|
| `hotel_id` | S | PK; FK to the parent Hotel (HTL-001 `META` row) |
| `sk` | S | `"ROOM#{room_id}"` |
| `room_id` | S | Convenience copy of the id; `uuid4().hex` (32-char hex) |
| `room_type_id` | S | FK to the HTL-005 Room Type on this hotel; validated at create |
| `room_number` | S | Physical room number / label (e.g. `"214"`); non-empty string |
| `floor` | N | Floor number; integer (may be negative for basement levels) |
| `status` | S | Literal: `available` \| `out_of_service`; default `"available"` on create |
| `housekeeping_status` | S | Literal: `clean` \| `dirty` \| `inspected` \| `out_of_service`; default `"clean"` on create. The HTL-007 cleaning-workflow field, **persisted here** but **mutated by HTL-007** (`set_room_housekeeping_status`), not by `update_room` |
| `created_at` | N | `now_ts()` — integer Unix seconds (`app/core/time.py:2–3`) |
| `updated_at` | N | `now_ts()` — stamped on every `update_room` call |

> **Note on `status` vs `housekeeping_status`**: `status` is the operational availability of
> the room for booking (`available` / `out_of_service`). `housekeeping_status` is the cleaning
> lifecycle (`clean` / `dirty` / `inspected` / `out_of_service`). They share an
> `out_of_service` literal but are independent columns. The duplicated literal is intentional:
> a room can be operationally `out_of_service` (taken off the booking grid) while its cleaning
> state is separately tracked, and HTL-007's board buckets on `housekeeping_status`.

### 3.2 GSIs

Both GSIs are declared on the **same** `hotel_rooms` `TableDef` in `scripts/local-ddb-init.py`.

| Index name | PK | SK | `attr_types` | Purpose |
|---|---|---|---|---|
| `GSI_ROOMTYPE` | `room_type_id` (S) | `created_at` (N) | `{"created_at": "N"}` required | List every physical room of a given Room Type (across the hotel) newest-first — drives `list_rooms(room_type_id=)` |
| `GSI_HK_STATUS` | `hotel_id` (S) | `housekeeping_status` (S) | none needed (both `S`) | Query a hotel's rooms bucketed by housekeeping status — the HTL-007 board fast path, no partition scan |

The single `attr_types={"created_at": "N"}` on the `TableDef` covers `GSI_ROOMTYPE`'s
numeric `created_at` sort key (per §2.8). `GSI_HK_STATUS`'s `housekeeping_status` sort key is
`S`, so it needs no `attr_types` entry.

### 3.3 Complete `TableDef` (`scripts/local-ddb-init.py`)

Added to the `_table_defs()` list (`scripts/local-ddb-init.py:43+`), following the
`TableDef(...)` call shape at `scripts/local-ddb-init.py:44–48`:

## 4. API / Service Design

### 4.1 Service additions: `app/services/hotel_pms.py`

All five functions are added to the existing `hotel_pms.py` file (created by HTL-001). No new
service file. Each begins with `_require_enabled()`.

#### 4.1.1 `create_room`

```python
def create_room(
    hotel_id: str,
    *,
    room_type_id: str,
    room_number: str,
    floor: int,
    status: str = "available",
    user_sub: str,
) -> dict:
```

**Behavior**:
1. `_require_enabled()`.
2. Reads the parent hotel `META` row via `T.hotels.get_item(Key={"hotel_id": hotel_id, "sk": "META"})`.
   Raises `HTTPException(404, "Hotel not found")` if absent.
3. Asserts caller ownership: if `item["owner_sub"] != user_sub` raise
   `HTTPException(403, "Not the hotel owner")` (HTL-001's ownership helper; ROOT bypass is
   §10 Open-Q 1).
4. **FK validation**: calls `get_room_type(hotel_id, room_type_id)` (HTL-005). If it returns
   `None`, raise `HTTPException(404, "Room type not found")` — this rejects both an unknown
   `room_type_id` and a `room_type_id` belonging to a *different* hotel (the read is scoped to
   `Key={hotel_id, ROOMTYPE#...}`, so a foreign id misses).
5. Generates `room_id = uuid4().hex`.
6. Builds the room item: `hotel_id`, `sk=f"ROOM#{room_id}"`, `room_id`, `room_type_id`,
   `room_number`, `floor`, `status`, `housekeeping_status="clean"` (default),
   `created_at=now_ts()`, `updated_at=now_ts()`.
7. `T.hotel_rooms.put_item(Item=item)` — unconditional put (UUID-keyed, no collision).
8. `_audit("hotel.room.created", user_sub, hotel_id=hotel_id, room_id=room_id, room_type_id=room_type_id, room_number=room_number)`.
9. Returns the item dict with Decimal numerics coerced to `int`.

#### 4.1.2 `get_room`

```python
def get_room(hotel_id: str, room_id: str) -> dict | None:
```

1. `_require_enabled()`.
2. `T.hotel_rooms.get_item(Key={"hotel_id": hotel_id, "sk": f"ROOM#{room_id}"})`.
3. Returns the coerced item dict or `None` if absent.

#### 4.1.3 `list_rooms`

```python
def list_rooms(
    hotel_id: str,
    *,
    room_type_id: str | None = None,
    status: str | None = None,
    cursor: str | None = None,
    limit: int = 50,
) -> dict:
```

1. `_require_enabled()`.
2. **By hotel** (default, `room_type_id is None`): query the `hotel_rooms` PK —
   `KeyConditionExpression=Key("hotel_id").eq(hotel_id) & Key("sk").begins_with("ROOM#")`.
   The `begins_with("ROOM#")` guard excludes any future non-room child rows (e.g. HTL-007's
   `HKTASK#` rows that co-locate on the same partition).
3. **By room type** (`room_type_id` given): query `GSI_ROOMTYPE` —
   `IndexName="GSI_ROOMTYPE", KeyConditionExpression=Key("room_type_id").eq(room_type_id)`,
   `ScanIndexForward=False` for newest-first (the `created_at` sort key). This returns every
   physical room of that type across the hotel.
4. Optional `status` filter applied as a `FilterExpression`. When set, accumulate across
   pages via `LastEvaluatedKey` until `limit` matches are collected or the partition is
   exhausted (§2.10 — FilterExpression doesn't reduce page size).
5. `cursor` is decoded via `decode_cursor` (`app/core/cursor.py:103`) into the
   `ExclusiveStartKey`; the next-page cursor is `encode_cursor(last_evaluated_key)`
   (`app/core/cursor.py:94`), or `None` when the partition is exhausted.
6. Coerce numerics on each item.
7. Returns `{"rooms": [...], "count": int, "cursor": str | None}` — the `{items, count,
   cursor}` shape (CLAUDE.md `host_inventory.list_hosts` returns `{"hosts": [...], "count",
   "cursor"}`; HTL-005 `list_room_types` returns `{"room_types", "count", "cursor"}`).

#### 4.1.4 `update_room`

```python
def update_room(
    hotel_id: str,
    room_id: str,
    *,
    user_sub: str,
    **kwargs,
) -> dict:
```

Accepted `kwargs`: `room_type_id`, `room_number`, `floor`, `status`. **`housekeeping_status`
is rejected here** — it routes through HTL-007's `set_room_housekeeping_status` (a
defense-in-depth guard drops it from `kwargs` if present, §5.5).

1. `_require_enabled()`.
2. Reads the existing room via `get_room(hotel_id, room_id)`. Raises `HTTPException(404,
   "Room not found")` if absent.
3. Verifies parent-hotel existence + caller ownership (reads `META`, same as `create_room`
   steps 2–3).
4. If `room_type_id` is among the updated keys, re-validates the FK via
   `get_room_type(hotel_id, room_type_id)` → 404 if it does not resolve on this hotel.
5. Builds an `UpdateExpression` from the present `kwargs` plus mandatory `updated_at = :ts`
   (`now_ts()`). Only keys present in `kwargs` are written (partial update).
6. `T.hotel_rooms.update_item(Key={"hotel_id": hotel_id, "sk": f"ROOM#{room_id}"}, ...,
   ReturnValues="ALL_NEW")`.
7. `_audit("hotel.room.updated", user_sub, hotel_id=hotel_id, room_id=room_id, fields=list(kwargs.keys()))`.
8. Returns the updated item with numerics coerced.

#### 4.1.5 `delete_room`

```python
def delete_room(hotel_id: str, room_id: str, *, user_sub: str) -> bool:
```

1. `_require_enabled()`.
2. Reads the existing room via `get_room(hotel_id, room_id)`. If absent, returns `False`
   immediately — **never raises** (mirrors `host_inventory.delete_host`,
   `app/services/host_inventory.py:360–367`).
3. Verifies parent-hotel existence + caller ownership (reads `META`). If the parent hotel is
   gone, proceeds to delete the orphaned room row anyway (best-effort cleanup) with no
   ownership check — parent-absent means no `owner_sub` to verify.
4. `T.hotel_rooms.delete_item(Key={"hotel_id": hotel_id, "sk": f"ROOM#{room_id}"})`.
5. `_audit("hotel.room.deleted", user_sub, hotel_id=hotel_id, room_id=room_id)`.
6. Returns `True`.

There is no per-hotel `room_count` counter on the `META` row in HTL-006 (rooms live in a
separate table; a count is derivable via a `Select="COUNT"` query on the partition if a future
ticket needs it — contrast PROP-002's `unit_count`, which is denormalized because units
co-locate on the parent partition).

### 4.2 Router endpoints (HTL-008 preview)

HTL-006 ships only the service layer. HTL-008 exposes these over HTTP. The room subset:

| Method | Path | Auth dep | Service call |
|---|---|---|---|
| `GET` | `/ui/hotels/{hotel_id}/rooms` | `require_ui_session` | `list_rooms(hotel_id, room_type_id=, status=, cursor=, limit=)` |
| `POST` | `/ui/hotels/{hotel_id}/rooms` | `require_admin_or_root_csrf` | `create_room(hotel_id, **body, user_sub=user.sub)` |
| `GET` | `/ui/hotels/{hotel_id}/rooms/{room_id}` | `require_ui_session` | `get_room(hotel_id, room_id)` → 404 if `None` |
| `PUT` | `/ui/hotels/{hotel_id}/rooms/{room_id}` | `require_admin_or_root_csrf` | `update_room(hotel_id, room_id, user_sub=user.sub, **body.model_dump(exclude_none=True))` |
| `DELETE` | `/ui/hotels/{hotel_id}/rooms/{room_id}` | `require_admin_or_root_csrf` | `delete_room(hotel_id, room_id, user_sub=user.sub)` → map `False → 404` |

Auth split is identical to `app/routers/inventory.py`: reads → `require_ui_session`
(`app/services/sessions.py:330`); mutations → `require_admin_or_root_csrf`
(`app/auth/policy.py:100–107`, which calls `enforce_cookie_csrf(request)` then
`require_roles(user, {Role.ADMIN, Role.ROOT})`). The literal `/rooms` segment is declared
before the dynamic `/{room_type_id}` sibling and `/{room_id}/...` dynamic routes are declared
after their literal siblings (HTL-008's route-ordering concern).

### 4.3 Response shapes

- **`list_rooms`**: `{"rooms": [...RoomOut...], "count": int, "cursor": str | None}`.
- **`create_room` / `get_room` / `update_room`**: a single `RoomOut` (HTTP 200/201).
- **`delete_room`**: service returns `bool`; the HTL-008 router maps `True → {"ok": true,
  "room_id": "..."}` (200) and `False → HTTPException(404)`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Parent hotel not found on `create_room`

If `hotel_id` has no `META` row in the `hotels` table, `create_room` raises
`HTTPException(404, "Hotel not found")` before writing anything to `hotel_rooms`. The check is
a strongly-consistent `get_item` (not a GSI query). No orphan room row is ever created for a
non-existent hotel.

### 5.2 Unknown / foreign `room_type_id` on `create_room`

`create_room` calls `get_room_type(hotel_id, room_type_id)` (HTL-005). Because that read is
scoped to `Key={"hotel_id": hotel_id, "sk": f"ROOMTYPE#{room_type_id}"}`, a `room_type_id`
that exists on a *different* hotel returns `None` on *this* hotel's partition and is rejected
with `HTTPException(404, "Room type not found")`. This prevents creating a Room whose type
belongs to another property — the FK is enforced **within the hotel partition**.

### 5.3 `list_rooms` returns only `ROOM#` rows

The by-hotel path uses `begins_with(sk, "ROOM#")`, so HTL-007's co-located `HKTASK#` task
rows (and any future child-row kind on the `hotel_rooms` partition) are excluded from room
listings. The by-room-type path queries `GSI_ROOMTYPE`, which is sparse — only rows that carry
a `room_type_id` attribute project into it (HKTASK rows carry `room_id`, not `room_type_id`,
so they never appear in `GSI_ROOMTYPE`).

### 5.4 `housekeeping_status` defaults to `clean` and is not settable via create/update

`RoomIn` has no `housekeeping_status` field; `create_room` always writes `"clean"`.
`RoomUpdateIn` omits it; `update_room` rejects/drops it. The only mutator is HTL-007's
`set_room_housekeeping_status`, which `update_item`s the `housekeeping_status` + `updated_at`
on the `ROOM#` row and keeps `GSI_HK_STATUS` current. This separation keeps the cleaning
workflow audited under its own event (`hotel.room.housekeeping_status`) rather than buried in
a generic room update.

### 5.5 `update_room` defense-in-depth against `housekeeping_status`

Even though `RoomUpdateIn` cannot carry `housekeeping_status` from the router, `update_room`
accepts `**kwargs` and could be called directly by another service. As a guard, `update_room`
discards `housekeeping_status` (and `hotel_id`, `sk`, `room_id`, `created_at`) from `kwargs`
before building the `UpdateExpression`, so no caller can mutate the housekeeping enum or
immutable keys through the generic path.

### 5.6 `room_number` is a non-empty string, not unique

`room_number` is validated non-empty (Pydantic `min_length=1` or an explicit
`HTTPException(422)` in the service). It is **not** enforced unique within a hotel — two rows
may share `"214"` transiently during a renovation/renumber, which is why `room_id` is a UUID
(§2.12). A future "find room by number" path can add a `GSI` on `(hotel_id, room_number)` or a
`begins_with` scan without a schema break.

### 5.7 `floor` may be any integer

`floor` is stored as `N` and coerced to `int` on read. Negative values are permitted
(basement/parking levels: `-1`, `-2`). No range validation beyond integer typing.

### 5.8 `status` (`out_of_service`) does not cascade to bookings

HTL-006 stores `status` as an operational flag only. Marking a room `out_of_service` does not
free or cancel any existing reservation (the Reservation entity is a Tier-2 HTL cluster, out
of scope). The booking-availability engine (also Tier-2) will read `status` to exclude
out-of-service rooms from assignment. HTL-006 imposes no transition rules: any `status` → any
`status` is allowed.

### 5.9 `list_rooms` for a hotel with no rooms

Returns `{"rooms": [], "count": 0, "cursor": None}`. A `begins_with(sk, "ROOM#")` query on a
hotel that has not provisioned rooms legitimately returns zero items — not an error.

### 5.10 `delete_room` with HKTASK children (future)

When HTL-007 lands, a room may have associated `HKTASK#` task rows on the same partition.
HTL-006's `delete_room` deletes only the `ROOM#` row and leaves any HKTASK rows behind.
Cascade-cleanup of a deleted room's tasks is an HTL-007/HTL-008 concern (or a reconciliation
sweep) — documented as a follow-up (§10 Open-Q 4). HTL-006 hard-deletes the room row only.

### 5.11 Rooms are hard-deleted (not archived)

Unlike Hotels and Room Types (which are archived via a `status` flip), Room rows are
hard-deleted by `delete_room`. A physical room that no longer exists has no entity-level
historical significance — historical booking records attach to the Reservation entity
(Tier-2), not the room row. Deletion is captured via the `hotel.room.deleted` audit event.

### 5.12 `GSI_HK_STATUS` query semantics (HTL-007 consumer)

`GSI_HK_STATUS` (PK=`hotel_id`, SK=`housekeeping_status`) lets HTL-007 query a single
cleaning bucket cheaply:

```python
T.hotel_rooms.query(
    IndexName="GSI_HK_STATUS",
    KeyConditionExpression=Key("hotel_id").eq(hid) & Key("housekeeping_status").eq("dirty"),
)
```

Only rows carrying both `hotel_id` and `housekeeping_status` project in — every `ROOM#` row
does (both are always set). HKTASK rows carry no `housekeeping_status`, so they never appear.
HTL-006 keeps this index current automatically because `housekeeping_status` is always
written on create (`clean`) and updated by HTL-007's setter.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_pms.py` must contain **no** `if S.dev_mode` branches across the five room
functions. The same DynamoDB code path (`T.hotel_rooms.*`, `T.hotels.*`) runs in dev (boto3
intercepted by moto in-process, per the `app/core/dev_s3.py` pattern) and prod (real
DynamoDB). This matches the cross-cutting constraint in
`docs/qloapps/ROOMTYPES_ROOMS_HOUSEKEEPING_TICKETS.md` ("Zero `if S.dev_mode` branches in
business logic; the same `T.*` handles in both environments") and the
`app/services/inventory.py:27–29` precedent (its module docstring: "SECOPS-007 parity:
identical code in dev … and prod … no `dev_mode` branch"). A
`grep -n "dev_mode" app/services/inventory.py` confirms the only hit is that docstring.

### 7.2 Idempotency

- `create_room` is **not** idempotent on (hotel_id, room_number) by design — the
  non-deterministic `uuid4().hex` room_id means each call creates a new row. Callers dedupe at
  the application layer (e.g. check `list_rooms` for an existing `room_number` before creating).
- `get_room`, `list_rooms` are read-only and trivially idempotent.
- `update_room` is idempotent in result (re-applying the same `kwargs` yields the same final
  state, differing only in `updated_at`).
- `delete_room` is idempotent in effect — first call returns `True`, second returns `False`,
  neither raises (§2.5). This lets the HTL-008 DELETE handler be safely retried.

### 7.3 Security — ownership & authorization

- **Ownership check**: `create_room`, `update_room`, and `delete_room` read the parent hotel
  `META` row and compare `owner_sub` to `user_sub`. A non-owning ADMIN cannot create, update,
  or delete rooms under another hotel. (ROOT bypass is an open question — §10 Open-Q 1.)
- **FK scoping doubles as a tenancy boundary**: because `create_room`/`update_room` validate
  `room_type_id` via a partition-scoped `get_room_type(hotel_id, ...)`, a caller cannot attach
  a room to a room-type from a hotel they do not own (the foreign id simply misses → 404).
- **Auth boundary** (HTL-008): mutations require `require_admin_or_root_csrf`
  (`app/auth/policy.py:100–107`) — `role ∈ {ADMIN, ROOT}` plus CSRF for cookie-auth (Bearer
  auth skips CSRF per CLAUDE.md). Reads require `require_ui_session`
  (`app/services/sessions.py:330`); no service-layer ownership check on reads, consistent with
  HTL-005 and the single-platform-deployment assumption.
- **CSRF**: cookie-auth POST/PUT/DELETE require `x-csrf-token` matching the `ui_csrf` cookie,
  enforced by `enforce_cookie_csrf(request)` inside `require_admin_or_root_csrf`
  (`app/auth/policy.py:105`).

### 7.4 Money-safety — no billing interaction

HTL-006 stores **no monetary field** on the room row (the base nightly rate lives on the Room
Type, HTL-005). `create_room`/`update_room`/`delete_room` never call
`billing_shared.new_ledger_entry`, `settle_or_reverse_ledger`, `apply_balance_delta`, or
`compute_due`; the `billing` table is never accessed; no Stripe/PayPal/CCBill SDK is invoked.
Room operations are pure inventory metadata. (Booking-time charges land in the Tier-3 folio /
deposit clusters and will go through the ledger primitives — never raw `put_item`/`delete_item`
on the billing table.) This ticket is money-neutral.

### 7.5 Audit trail

Every room mutation emits a best-effort `_audit()` call (swallows exceptions per
`app/services/inventory.py:92–98`):

| Event | When |
|---|---|
| `hotel.room.created` | `create_room` success |
| `hotel.room.updated` | `update_room` success |
| `hotel.room.deleted` | `delete_room` success (room existed) |

`set_room_housekeeping_status` (HTL-007) emits `hotel.room.housekeeping_status` separately, so
cleaning transitions are auditable distinctly from operational room edits.

## 8. Backward Compatibility & Migration

### 8.1 Additive-only changes

HTL-006 adds:
- Three Pydantic models to `app/models.py`: `RoomIn`, `RoomOut`, `RoomUpdateIn` (additive; no
  existing model modified).
- Five functions to `app/services/hotel_pms.py` (additive; no existing function modified).
- One new `TableDef` (`hotel_rooms`) to `scripts/local-ddb-init.py` (a new entry; does not
  amend any existing `TableDef`).
- One settings key (`hotel_rooms_table_name`) to `app/core/settings.py`.
- One dataclass field + one `_safe_table(...)` wire in `app/core/tables.py`.

No existing endpoint, service function, DynamoDB table, or Pydantic model is altered.

### 8.2 New table — no `TableDef` reconciliation needed

Unlike PROP-002 (which **amends** the existing `properties` `TableDef` to add a GSI), HTL-006
introduces a **brand-new** `hotel_rooms` table. There is no merge-order entanglement with
HTL-005 (which amends the `hotels` `TableDef`) — the two changes touch different table
entries in `scripts/local-ddb-init.py`.

### 8.3 Dev table recreation

`just restart` runs `scripts/local-ddb-init.py`, which `CreateTable`s every `TableDef`
including the new `hotel_rooms`. Dev data is wiped on each restart — consistent with the dev
workflow. If `HOTEL_ROOMS_TABLE_NAME` is unset, the default `"hotel_rooms"` name is used.

### 8.4 Production deployment

1. Create the `hotel_rooms` table via `CreateTable` with both GSIs (`GSI_ROOMTYPE`,
   `GSI_HK_STATUS`) and the numeric `created_at` attribute type. As a fresh table there is no
   backfill — it starts empty.
2. Deploy HTL-006 code (new models + service functions; zero change to existing behavior).
3. Enable `HOTEL_PMS_ENABLED=true` once the table is verified (the whole vertical, HTL-001
   onward, flips on together).

### 8.5 Rollback

With `HOTEL_PMS_ENABLED=false`, the room service functions are dormant (every entrypoint
404s). Rolling back HTL-006 reverts the five file changes (`models.py`, `hotel_pms.py`,
`local-ddb-init.py`, `settings.py`, `tables.py`). In production the empty `hotel_rooms` table
can be left in place (inert with the flag off) or deleted via `DeleteTable`.

## 10. Open Questions / Assumptions

1. **ROOT bypass for ownership.** `create_room`/`update_room`/`delete_room` check
   `META["owner_sub"] == user_sub`. A ROOT user who does not own the hotel is currently
   blocked. If a platform-admin override is required, add `if user.role == Role.ROOT: pass`
   before the ownership check. **Assumption**: ROOT owns hotels on a single-platform
   deployment; no bypass for MVP (matches PROP-002 §10 item 1 and HTL-005).
2. **`room_number` uniqueness.** Not enforced — two rows may share a number transiently
   (renovation/renumber), which is why `room_id` is a UUID. **Assumption**: callers handle
   dedupe; a future `(hotel_id, room_number)` GSI or `find_room_by_number` path can be added
   without a schema break.
3. **`create_room` idempotency.** Non-deterministic `uuid4().hex` → no idempotency on
   (hotel_id, room_number). **Assumption**: callers dedupe before retrying a create; the API
   creates a new row per call.
4. **Cascade-delete of HKTASK children.** When HTL-007 lands, `delete_room` will leave a
   deleted room's `HKTASK#` rows orphaned on the partition. **Assumption**: cascade cleanup is
   an HTL-007/HTL-008 concern (or a reconciliation sweep); HTL-006 hard-deletes only the
   `ROOM#` row (§5.10).
5. **No `room_count` on the hotel `META` row.** Unlike PROP-002's `unit_count` (denormalized
   because units co-locate on the parent partition), rooms live in a separate table, so HTL-006
   keeps no denormalized count. **Assumption**: a count is derivable via a `Select="COUNT"`
   partition query if a future ticket (e.g. an HTL-009 dashboard) needs it; not added here.
6. **`status` → booking cascade.** Marking a room `out_of_service` does not touch reservations
   (Tier-2). **Assumption**: the availability/assignment engine reads `status` to exclude
   out-of-service rooms; HTL-006 imposes no transition rules.
7. **`floor` representation.** Stored as an integer `N`; non-numeric labels like `"G"`
   (ground) or `"M"` (mezzanine) are not supported. **Assumption**: callers map such labels to
   integers (`0`, `0.5→` not allowed since `floor` is `int`); a string `floor_label` field is a
   non-breaking follow-up if needed.

### Cross-ticket reconciliation (audit 2026-06-13)

Per `docs/CROSS_TICKET_AUDIT.md §B4` (row 9) — **room-status naming.** HTL-019 (from its parent
ticket doc) references an unowned `set_room_status(occupied/dirty/vacant)`. The room state is
actually split across two owners: **HTL-006 owns occupancy** via
`update_room(status ∈ {available, out_of_service})`, and **HTL-007 owns the cleaning state**
via `set_room_housekeeping_status(housekeeping_status ∈ {clean, dirty, inspected, out_of_service})`.
Reconciliation: HTL-019 (and any caller) must call **`update_room` for occupancy changes** and
**`set_room_housekeeping_status` for cleaning state** — the unowned `set_room_status` name and
its `occupied`/`vacant` values are dropped. HTL-006 exposes `update_room` (occupancy); it does
**not** own a `set_room_status` alias and does not own the cleaning enum (that is HTL-007).
