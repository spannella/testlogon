# HTL-026 — Public stay-search + quote endpoint: `GET /booking-engine/search` (rate-limited, no auth)

**Type**: Feature | **Priority**: P1 | **Estimate**: 1.5d
**Source**: `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md` §HTL-026 (`:140-214`) + "Cross-cutting constraints" (`:24-70`) + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C (Booking-engine storefront, `:135-141,174-178`)

---

## 1. Summary & Goal

HTL-026 lands the **public stay-search + quote endpoint** — the core funnel step of the booking-engine storefront: *given a hotel, a check-in/check-out date range, and an occupancy (adults / children / rooms), return the available room types with per-night availability and a summed multi-night total price.* It delivers exactly **one new service function** — `quote_stay(...)` in the storefront service `app/services/hotel_storefront.py` (the module created by HTL-025) — plus **two output-only Pydantic models** (`StayQuoteResultOut`, `StayQuoteOut`) and the wiring of **one public, unauthenticated, rate-limited route** `GET /booking-engine/search` on the `booking_engine_router` declared by HTL-027.

`quote_stay` is a thin, **public HTTP-facing wrapper** around the **HTL-017** `search_stays(...)` engine. The hard part — the per-date availability **intersection across the whole span** plus the **summed multi-night/occupancy price** — lives entirely in HTL-017 (`docs/qloapps/specs/HTL-017.md` §1, §4.3). HTL-026 does **not** re-implement any per-date or per-night math (acceptance criterion, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:203-204`). It adds exactly three things on top of the engine:

1. **A public, no-auth surface.** Mirroring the calendar public-router pattern (`app/routers/calendar.py:88` `public_router`, and its `list_booking_openings` handler `:1960-1974` — an unauthenticated read of availability over a window), the endpoint takes **no auth dependency**. Publication of the hotel (HTL-001 `status=="published"`) is the access gate, not a session (cross-cutting constraint, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:33-40`).
2. **Per-client rate limiting.** Because the endpoint is unauthenticated and fans out to the availability/price engine, the handler rate-limits per request client host **before** delegating, reusing the DDB bucket `app/services/rate_limit.py` `_bucket_limit(user_sub, sid, max_n, win)` (`:60`) — keyed on the request IP (there is no `user_sub`). Bucket exhaustion → **429** with `Retry-After` (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:184-193`).
3. **Input validation + storefront projection.** Validate the hotel is published (404 otherwise, reusing HTL-025 `public_get_hotel`), validate `checkout > checkin` (400) and a sane max length-of-stay, validate occupancy bounds, then project the engine output into the storefront quote shape.

Like every HTL ticket, HTL-026 is **additive + flag-gated, default OFF**: `quote_stay` calls `_require_enabled()` (the verbatim `app/services/inventory.py:50-56` 404 contract, reading `S.hotel_pms_enabled`) as its **first** statement, so with `HOTEL_PMS_ENABLED=false` the endpoint is a silent HTTP 404 no-op and the platform is byte-for-byte unchanged (cross-cutting, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:26-32`).

**In scope**: `quote_stay` service function; `StayQuoteResultOut` + `StayQuoteOut` models; the `GET /booking-engine/search` handler (rate-limit + validation + delegate + project); new `HOTEL_BOOKING_SEARCH_RL_*` settings; hermetic offline tests.

**Out of scope** (other tickets): the `booking_engine_router` declaration + `main.py` registration (HTL-027, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:273-306` — HTL-026 declares the route on that router but the router object + registration is HTL-027's deliverable); the `search_stays` engine itself (HTL-017, forward dep); the cart / guest / checkout funnel (HTL-027); the frontend booking site (HTL-028).

## 2. Context & Current State

### 2.1 Gap — no public booking-engine storefront exists today

`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:135-141,174-178` names the **booking-engine storefront** — "public room-search-by-dates+occupancy → results → cart → guest details → checkout, reusing the public booking-link route + ECM availability/cart patterns" — as a Tier-2 MISSING capability. The gap analysis (`:57-61`) records the two concepts that "defeat every existing primitive": a **per-date remaining-rooms inventory** (the existing OFB-003/004/ECM-005 inventory is a single scalar stock counter with no date dimension) and a **multi-night price computation across a check-in→check-out span** (the cart total is a naive line-item sum). Those two halves are solved upstream by HTL-012 (availability) + HTL-015 (price) and composed by HTL-017 (`search_stays`); HTL-026 is the **public HTTP wrapper** that surfaces that engine to an unauthenticated guest as the funnel's "search" step. `grep -rn "quote_stay\|booking-engine" app/` returns nothing today — neither the function nor the route exists.

### 2.2 The engine half already exists as a forward-dep primitive (HTL-017)

The availability-intersection + summed-price computation is **HTL-017's** deliverable (`docs/qloapps/specs/HTL-017.md` §1, §4.3): `search_stays(*, hotel_id, city=None, checkin, checkout, adults, children, rooms) -> StaySearchResult`. It is a **pure read-only composition** over HTL-012 `check_availability` (per-date intersection across `[checkin, checkout)`, checkout exclusive) and HTL-015 `compute_stay_price` (deterministic multi-night/occupancy price), and performs **zero DynamoDB writes** (`docs/qloapps/specs/HTL-017.md` §5.10). It already validates the span (`_validate_span`, HTL-017 §4.2 — 422 on a malformed or zero/negative-night span), skips sold-out room types (the intersection), catches an HTL-015 LOS 422 to exclude one room type without aborting the search (§5.5), and returns results **cheapest-first with a deterministic `room_type_id` tiebreak** (§5.9). HTL-026 calls `search_stays` **by id** and never re-implements any of this.

`StaySearchResult` (HTL-017 §3.3) carries `{checkin, checkout, nights, adults, children, rooms, results: List[StayRoomTypeResult], result_count}`. Each `StayRoomTypeResult` (HTL-017 §3.2) carries `{hotel_id, room_type_id, name, available, min_remaining, rooms, per_night: List[NightLineOut], total_cents, currency, applied_rule_ids}`. HTL-026 projects this verbatim into the storefront quote shape (§3, §4.4).

> **Engine signature note.** HTL-017 takes `hotel_id | city` (a disjunction; `docs/qloapps/specs/HTL-017.md` §3.1, §5.6). HTL-026's public endpoint is **always hotel-scoped** (the storefront search runs from a hotel page; query param `hotel` is required, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:180-181`), so `quote_stay` always passes `hotel_id=` (never `city=`). The `city` branch of `search_stays` is unused by HTL-026.

### 2.3 The publication-gate half already exists (HTL-025)

HTL-025 (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:74-138`) created `app/services/hotel_storefront.py` with the flag/audit scaffolding (copied verbatim from `inventory.py`, reading `S.hotel_pms_enabled`) and the public reads `public_get_hotel(hotel_id)` (404 unless `status=="published"` / `published==True`) and `public_list_room_types(hotel_id)`. `quote_stay` lives in the **same** service file (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:158-160`) and **reuses `public_get_hotel`** as its publication gate: a non-existent or unpublished hotel → 404 (acceptance, `:202`). HTL-026 does not duplicate the publication check — it calls `public_get_hotel(hotel_id)` and lets its 404 propagate.

### 2.5 The rate-limit bucket (from `app/services/rate_limit.py`)

The DDB-backed sliding-bucket limiter is `_bucket_limit` (`app/services/rate_limit.py:60`):

```python
# app/services/rate_limit.py:60-79
def _bucket_limit(user_sub: str, sid: str, max_n: int, win: int) -> bool:
    if not _sessions_table_enabled():
        return True                                   # fail-open: no sessions table → allow
    now = now_ts()
    it = T.sessions.get_item(Key={"user_sub": user_sub, "session_id": sid}).get("Item") or {}
    start = int(it.get("bucket_start", 0))
    count = int(it.get("bucket_count", 0))
    if start == 0 or (now - start) >= win:            # window expired → reset
        start = now
        count = 0
    if count >= max_n:                                # bucket full → deny
        return False
    try:
        T.sessions.put_item(Item=with_ttl(
            {"user_sub": user_sub, "session_id": sid, "bucket_start": start, "bucket_count": count + 1},
            ttl_epoch=now + win + 3600))
    except Exception:
        pass                                          # write hiccup → still allow this call
    return True
```

Key properties HTL-026 relies on:
- **Fail-open** (`:61-62`): when the sessions table is unavailable, it returns `True` (allow). A backing-store hiccup never blocks search (acceptance, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:206`).
- **Returns `bool`** (True = within budget, False = exhausted) — the caller raises the 429; the bucket itself never raises for the limit case.
- **Keyed on `(user_sub, session_id)`** of the `sessions` table. HTL-026 has no `user_sub`, so the **"subject"** is the request client host (`request.client.host`) — exactly the "keyed on IP/anon" approach the ticket specifies (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:184-188`). This mirrors `rate_limit_kyc_partner_api` (CLAUDE.md KYC-021) which keys on a per-key subject (`apikey:{id}`) rather than the partner `user_sub`.

The existing `rate_limit_or_429` (`app/services/rate_limit.py:17-58`) is the MFA-send limiter and is **not** reused (it raises a fixed "verification sends" 429 with no `Retry-After`); HTL-026 uses the lower-level `_bucket_limit` boolean and raises its own `HTTPException(429, ..., headers={"Retry-After": ...})`.

## 3. Data Model

HTL-026 introduces **no DynamoDB table, no GSI, and no new persisted attribute**. `quote_stay` is a pure read-only composition: it writes nothing of its own (the only write is `_bucket_limit`'s rate-limit counter put into the **existing** `sessions` table, `app/services/rate_limit.py:73-76`). It owns no persisted state. This section documents only the two output-only Pydantic models that flow through the function/handler.

### 3.1 `StayQuoteResultOut` — one available room type's availability + total (`app/models.py`)

```python
class StayQuoteResultOut(BaseModel):
    room_type: PublicRoomTypeOut           # storefront-safe room-type projection (HTL-025 §model)
    available_rooms: int                   # the binding night's remaining count (== min_remaining)
    per_night: List[PerNightAvailOut]      # [{date, rooms_available, rate_cents}] across the span
    total_price_cents: int                 # == search_stays result's total_cents for this room type
    currency: str                          # ISO 4217 lowercase, from the engine result
```

- `room_type` reuses **HTL-025's** `PublicRoomTypeOut` (the storefront-safe room-type fields: `room_type_id`, `name`, `description`, `occupancy_adults`, `occupancy_children`, `max_occupancy`, `bed_type`, `size_sqft`, `amenities`, `photos`, `base_rate_cents`, `currency` — `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:106-113,118-121`). HTL-026 does **not** redefine room-type fields; it composes the HTL-017 `StayRoomTypeResult` + the HTL-025 room-type projection. (If HTL-025's `public_list_room_types` is not consulted at quote-time, the projection is built from the fields HTL-017's `StayRoomTypeResult` already carries — `room_type_id`, `name` — plus the engine's price/availability; see §10.5 for the projection-source assumption.)
- `available_rooms` = the engine's `min_remaining` (the binding night's remaining count, HTL-017 §3.2) — always `>= rooms` for a surviving result.
- `per_night` is the per-night **availability** breakdown shape `{date, rooms_available, rate_cents}` named in the ticket (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:169`). It is sourced from the engine output (HTL-017's `per_night` carries the price line; the availability per-night comes from `check_availability`'s `per_night`). `PerNightAvailOut` is an output-only model; see §10.4 on reconciling the price-line vs availability-line shapes — HTL-026 surfaces what the engine returns and does not recompute.
- `total_price_cents` is **copied verbatim** from the engine's `StayRoomTypeResult.total_cents` (HTL-017 §3.2). HTL-026 performs no price arithmetic (acceptance, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:203-204`). Money stays in integer cents — no float money field.

### 3.2 `StayQuoteOut` — the full quote envelope (`app/models.py`)

```python
class StayQuoteOut(BaseModel):
    hotel_id: str
    checkin: str                           # echoed "YYYY-MM-DD"
    checkout: str                          # echoed "YYYY-MM-DD"
    nights: int                            # count of dates in [checkin, checkout) (from the engine)
    adults: int
    children: int
    rooms: int
    results: List[StayQuoteResultOut]      # cheapest-first (engine ordering preserved)
    currency: str                          # the quote's display currency (engine result currency)
```

This is exactly the shape the ticket prescribes (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:166-172`). `results` preserves the engine's **cheapest-first, deterministic-tiebreak** ordering (HTL-017 §5.9) — HTL-026 does not re-sort. Room types with **zero availability across the span** never appear in `results` (the engine already excludes them, HTL-017 §5.1-5.2; this layer just surfaces the engine's output — `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:170-172`).

### 3.3 No request-body model

The endpoint is `GET` with **query parameters** (`hotel`, `checkin`, `checkout`, `adults`, `children`, `rooms`), not a JSON body (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:178,195-197`). FastAPI `Query(...)` declarations on the handler signature carry the validation (`adults: int = Query(1, ge=1)`, etc.); there is no `StayQuoteIn` model.

### 3.4 No persisted numeric coercion at this layer

`quote_stay` performs no DynamoDB read of its own, so it does not itself coerce `Decimal`→`int`. The forward-deps it calls (`public_get_hotel`, `search_stays`) coerce their numerics at their own service boundaries (HTL-017 §3.5, HTL-025). The integer fields of `StayQuoteResultOut`/`StayQuoteOut` coerce again on field assignment as a belt-and-braces guard.

## 4. API / Service Design

### 4.1 Service function: `quote_stay` (`app/services/hotel_storefront.py`)

`quote_stay` is added to the **existing** HTL-025 service module `app/services/hotel_storefront.py` (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:158`). The module already imports the flag/audit scaffolding (HTL-025); HTL-026 adds an import of the engine and the date stdlib:

```python
# app/services/hotel_storefront.py — HTL-026 additions (engine imported at module level so
# tests can patch search_stays at the hotel_storefront namespace — KYC GAP-0262 idiom)
from datetime import date

from app.services.hotel_reservations import search_stays   # HTL-017 (engine, forward dep)
# public_get_hotel + _require_enabled + _flag_on + _audit already defined in this module (HTL-025)

_MAX_LOS_NIGHTS = 30   # sane max length-of-stay; configurable (see §6)


def quote_stay(
    *,
    hotel_id: str,
    checkin: str,        # "YYYY-MM-DD" (inclusive — first night)
    checkout: str,       # "YYYY-MM-DD" (exclusive — departure day, not a night)
    adults: int = 1,
    children: int = 0,
    rooms: int = 1,
) -> dict:
    """Public stay-search + quote. Thin wrapper around HTL-017 search_stays — no per-date /
    per-night math here. Validates publication + span + occupancy, delegates, projects."""
    _require_enabled()                                       # 404 when HOTEL_PMS_ENABLED=false

    # 1. Publication gate (reuse HTL-025) — 404 on missing/unpublished hotel.
    public_get_hotel(hotel_id)                               # raises HTTPException(404) if not published

    # 2. Span validation — 400 on a non-positive or absurd span (mirror calendar :1984-1985).
    nights = _validate_quote_span(checkin, checkout)         # 400 / 422 (see §4.2)

    # 3. Occupancy bounds (defensive; also enforced at the Query() edge).
    if adults < 1 or children < 0 or rooms < 1:
        raise HTTPException(status_code=400, detail="invalid occupancy")

    # 4. Delegate to the engine (HTL-017) — the availability intersection + summed price.
    engine = search_stays(
        hotel_id=hotel_id, checkin=checkin, checkout=checkout,
        adults=adults, children=children, rooms=rooms,
    )

    # 5. Project the engine output into the storefront quote shape.
    results = [_project_result(r) for r in engine.results]   # zero-availability types already excluded by engine
    currency = results[0].currency if results else _default_currency()
    return StayQuoteOut(
        hotel_id=hotel_id, checkin=checkin, checkout=checkout, nights=engine.nights,
        adults=adults, children=children, rooms=rooms, results=results, currency=currency,
    ).model_dump()
```

The function returns a plain `dict` (`.model_dump()`) so the router can re-wrap as `StayQuoteOut` for the `response_model` (the inventory/storefront convention). `quote_stay` performs **zero DDB writes** and no audit event (it is a read; consistent with HTL-017 §7.5 and HTL-025's read paths).

### 4.2 Span-validation helper

`quote_stay` does **not** re-implement HTL-017's `_validate_span` (which the engine already runs internally); it adds a public-facing pre-check that returns the ticket-mandated **400** (not 422) for `checkout <= checkin`, matching `reserve_booking_slot`'s contract (`app/routers/calendar.py:1984-1985`, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:162-164,202`) and enforces the sane max length-of-stay:

```python
def _validate_quote_span(checkin: str, checkout: str) -> int:
    try:
        ci = date.fromisoformat(checkin)
        co = date.fromisoformat(checkout)
    except (ValueError, TypeError):
        raise HTTPException(status_code=400, detail="checkin/checkout must be YYYY-MM-DD")
    nights = (co - ci).days
    if nights < 1:
        raise HTTPException(status_code=400, detail="checkout must be after checkin")
    if nights > _max_los_nights():
        raise HTTPException(status_code=400, detail=f"stay exceeds maximum {_max_los_nights()} nights")
    return nights
```

> **400 vs 422.** HTL-017's internal `_validate_span` raises **422** (a server-side defensive guard, HTL-017 §4.2). The ticket explicitly contracts the **public** endpoint to return **400** for `checkout <= checkin` (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:162-164,202`), matching the calendar public reserve idiom. So `quote_stay` runs its own `_validate_quote_span` (400) **before** delegating, and the engine's internal 422 is unreachable for a span HTL-026 has already accepted. Both layers agree on the checkout-exclusive `[checkin, checkout)` night count.

### 4.3 Result projection helper

```python
def _project_result(r) -> StayQuoteResultOut:   # r is an HTL-017 StayRoomTypeResult
    return StayQuoteResultOut(
        room_type=_room_type_projection(r),     # PublicRoomTypeOut-shape (§10.5)
        available_rooms=int(r.min_remaining),
        per_night=[_per_night(n) for n in r.per_night],
        total_price_cents=int(r.total_cents),
        currency=r.currency,
    )
```

The projection copies the engine's already-computed `total_cents`, `min_remaining`, `per_night`, and `currency` verbatim — **no recomputation** (acceptance, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:203-204`).

### 4.4 Router handler: `GET /booking-engine/search`

Declared on the `booking_engine_router` (HTL-027's router object, `prefix="/booking-engine"`, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:278`). The handler takes **no auth dependency** (the public-funnel contract), takes the FastAPI `Request` to read the client host, rate-limits, then delegates:

```python
from fastapi import APIRouter, Query, Request, HTTPException
from app.core.settings import S
from app.core.time import now_ts
from app.models import StayQuoteOut
from app.services import hotel_storefront
from app.services.rate_limit import _bucket_limit

# booking_engine_router declared in HTL-027; literal /search is declared BEFORE the dynamic
# /hotels/{hotel_id} route (FastAPI matches in declaration order — CLAUDE.md gotcha).

@booking_engine_router.get("/search", response_model=StayQuoteOut)
async def booking_engine_search(
    request: Request,
    hotel: str = Query(..., description="hotel_id of a published hotel"),
    checkin: str = Query(..., description="ISO date YYYY-MM-DD (inclusive)"),
    checkout: str = Query(..., description="ISO date YYYY-MM-DD (exclusive)"),
    adults: int = Query(1, ge=1, le=16),
    children: int = Query(0, ge=0, le=16),
    rooms: int = Query(1, ge=1, le=_MAX_ROOMS_PER_SEARCH),
):
    hotel_storefront._require_enabled()                      # 404 when HOTEL_PMS_ENABLED=false
    _rate_limit_search_or_429(request)                       # 429 + Retry-After on exhaustion
    quote = hotel_storefront.quote_stay(
        hotel_id=hotel, checkin=checkin, checkout=checkout,
        adults=adults, children=children, rooms=rooms,
    )
    return StayQuoteOut(**quote)
```

| Method | Path | Auth | Service | Query params |
|---|---|---|---|---|
| `GET` | `/booking-engine/search` | **none (public)** | `quote_stay` | `hotel` (req), `checkin` (req), `checkout` (req), `adults=1 ge=1`, `children=0 ge=0`, `rooms=1 ge=1 le=…` |

The handler calls `_require_enabled()` **first** (404 when off, router still mounted — byte-for-byte unchanged platform, cross-cutting `:26-32,297`). Per the declaration-order gotcha (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:62-66,292-295`, CLAUDE.md KYC `/templates`-before-`/{case_id}`), the literal `/search` route MUST be declared **before** any dynamic `/hotels/{hotel_id}` route on the `booking_engine_router` — otherwise FastAPI would capture `search` as a path param. (HTL-026 owns the `/search` declaration; HTL-027 owns the surrounding router + the dynamic routes, and must declare them in the right order — see §11.)

### 4.5 Rate-limit gate helper

```python
def _rate_limit_search_or_429(request: Request) -> None:
    ip = (request.client.host if request.client else "") or "unknown"
    sid = f"rl#booking_search#{ip}"
    win = S.hotel_booking_search_rl_window           # default 3600
    max_n = S.hotel_booking_search_rl_max            # default 60
    # _bucket_limit's "user_sub" is the IP subject (no session here); returns True = within budget.
    if not _bucket_limit(f"ip#{ip}", sid, max_n, win):
        raise HTTPException(
            status_code=429,
            detail="Too many searches; slow down and try again shortly.",
            headers={"Retry-After": str(win)},
        )
```

- **Subject = client IP** — keyed on `request.client.host` because the endpoint is unauthenticated (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:184-188`). Both the `user_sub` arg (`f"ip#{ip}"`) and the `session_id` (`f"rl#booking_search#{ip}"`) embed the IP so the DDB `Key` is fully IP-scoped (the `sessions` table PK is `user_sub`, `app/services/rate_limit.py:64`).
- **429 + `Retry-After`** — on bucket exhaustion, raise `HTTPException(429, ..., headers={"Retry-After": str(win)})` (acceptance, `:205`). `Retry-After` is the window length in seconds (a conservative upper bound; a precise "seconds until reset" is a non-breaking refinement, §10.3).
- **Fail-open** — `_bucket_limit` returns `True` when `_sessions_table_enabled()` is false (`app/services/rate_limit.py:61-62`), so a missing/unavailable sessions table never blocks search (acceptance, `:206`).
- **Order**: the rate-limit gate runs **after** `_require_enabled()` (so a disabled vertical 404s without consuming bucket budget) and **before** `quote_stay`'s fan-out to the engine (so an abusive client is throttled before the expensive availability/price composition runs, `:184-186`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Happy path — available room types with per-night availability + summed total

`GET /booking-engine/search?hotel=h1&checkin=2026-07-01&checkout=2026-07-04&adults=2&children=0&rooms=1` for a published hotel with availability over the span returns HTTP 200 + `StayQuoteOut` with `nights=3`, `results` cheapest-first, each result carrying `per_night` (3 entries) and a `total_price_cents` equal to the engine's summed multi-night price (acceptance, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:200-201`).

### 5.2 `checkout <= checkin` → 400

`_validate_quote_span` raises `HTTPException(400, "checkout must be after checkin")` for a zero- or negative-night span, and `HTTPException(400, "checkin/checkout must be YYYY-MM-DD")` for a malformed ISO date — **before** the publication or engine call. This matches `reserve_booking_slot`'s 400 (`app/routers/calendar.py:1984-1985`) and the acceptance criterion (`:202`). Note the publication gate (step 1) runs **before** span validation (step 2) in `quote_stay`, so a malformed span against an unpublished hotel returns **404** (the publication check fires first) — this is the deliberate "the vertical/entity simply does not exist" posture and prevents probing span-validation behavior for hidden hotels.

### 5.3 Unpublished / non-existent hotel → 404

`public_get_hotel(hotel_id)` (HTL-025) raises `HTTPException(404)` for a hotel that does not exist or whose `status != "published"`. `quote_stay` lets this propagate unchanged (acceptance, `:202`). Publication is the public-access gate, exactly as a booking-link `link_id` is the gate in `_load_booking_link` (`app/routers/calendar.py:289-309`).

### 5.4 Rate-limit exhaustion → 429 with `Retry-After`

When a single client IP exceeds `HOTEL_BOOKING_SEARCH_RL_MAX` (default 60) requests within `HOTEL_BOOKING_SEARCH_RL_WINDOW` (default 3600s), `_bucket_limit` returns `False` and the handler raises `HTTPException(429, ..., headers={"Retry-After": "3600"})` (acceptance, `:205`). The very next window (after `win` seconds, when `_bucket_limit` resets `start`/`count`, `app/services/rate_limit.py:67-69`) allows requests again.

### 5.5 Rate-limit fail-open when the sessions table is absent

If `_sessions_table_enabled()` is false (no `ddb_sessions_table` configured), `_bucket_limit` returns `True` and the search proceeds un-throttled (`app/services/rate_limit.py:61-62`; acceptance, `:206`). A backing-store hiccup degrades to "allow," never to "block all search" — the storefront's read availability is prioritized over strict throttling.

### 5.6 No availability for any room type → empty `results`, HTTP 200

The engine excludes every sold-out room type (HTL-017 §5.1); if **all** room types are sold out over the span, `search_stays(...).results == []` and `quote_stay` returns `StayQuoteOut` with `results=[]` and HTTP 200 (not an error). A fully-booked hotel is a valid, empty quote. `currency` defaults to `_default_currency()` (the platform default, e.g. `"usd"`) when there are no results to source it from.

### 5.7 Partial-span sold-out room type excluded (the core primitive)

A room type available on every night **except one** is excluded by the engine — `check_availability` returns `available=False` (the AND-reduction across the span, HTL-017 §5.2). HTL-026 surfaces only surviving room types; it adds no special-casing (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:170-172`). This per-date intersection is precisely the distinction the OFBiz scalar inventory counter cannot express (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:57-61`).

### 5.8 LOS-rule rejection excludes one room type without erroring the whole search

If a room type's length-of-stay (min/max-nights) rule rejects the span, the engine catches HTL-015's 422 and skips that room type without aborting the search (HTL-017 §5.5). HTL-026 inherits this transitively — the search returns the other room types. HTL-026's own `_MAX_LOS_NIGHTS` guard (§4.2) is a coarse public-endpoint sanity cap (e.g. 30 nights), distinct from any per-room-type rate-plan LOS rule.

### 5.9 Occupancy bounds

`adults` (`ge=1`), `children` (`ge=0`), `rooms` (`ge=1`) are validated at the `Query()` edge (422 from FastAPI for an out-of-range value) and re-checked defensively in `quote_stay` (400). Upper caps (`adults le=16`, `children le=16`, `rooms le=_MAX_ROOMS_PER_SEARCH`) prevent an absurd fan-out. Whether a requested occupancy exceeds a specific room type's `max_occupancy` is a **pricing/eligibility** concern owned by HTL-015 (priced as a supplement or rejected with a 422 the engine catches-and-skips) — HTL-026 does **not** independently re-validate occupancy vs `max_occupancy` (HTL-017 §5.8), keeping that logic single-sourced upstream.

### 5.10 `quote_stay` performs zero DDB writes (except the rate-limit counter)

`quote_stay` itself writes nothing. The only DynamoDB write in the request path is `_bucket_limit`'s rate-limit counter `put_item` into the **existing** `sessions` table (`app/services/rate_limit.py:73-76`), which is best-effort (swallows write exceptions, `:77-78`). No reservation, no hold, no inventory decrement — a search is a non-locking advisory read (HTL-017 §5.10). Inventory is only held at checkout (HTL-027 → HTL-018).

### 5.11 Engine ordering preserved

`quote_stay` does **not** re-sort `results` — it preserves the engine's cheapest-first + deterministic-`room_type_id`-tiebreak ordering (HTL-017 §5.9). The projection is a 1:1 map, so `len(quote.results) == engine.result_count` and order is identical.

### 5.12 Missing required query param → 422

A request omitting `hotel`, `checkin`, or `checkout` is rejected by FastAPI at the `Query(...)` edge with a 422 (FastAPI's standard required-param error) before the handler body runs — so no rate-limit budget is consumed for a malformed request. (The handler body's `_require_enabled()` only runs once FastAPI has bound valid params.)

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`quote_stay`, `_validate_quote_span`, `_project_result`, the handler, and `_rate_limit_search_or_429` must contain **no** `if S.dev_mode` branch. `quote_stay` issues no DynamoDB call of its own; the forward-deps it composes (`public_get_hotel`, `search_stays`) and the rate-limit bucket (`_bucket_limit`) already own any mock/real divergence internally — each uses the same `T.*` handles in dev (moto intercepts boto3) and prod (real DynamoDB), per the cross-cutting constraint (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:58-61`). HTL-026 calls them **identically** in both environments. Acceptance: `grep -n "dev_mode" app/services/hotel_storefront.py app/routers/booking_engine.py` returns nothing for HTL-026's additions (or only docstrings).

### 7.2 Idempotency

`quote_stay` is a **pure read** — naturally idempotent. Re-running it with identical inputs yields identical output, modulo concurrent availability/price changes in the underlying tables (which is correct — a quote reflects current state). It writes nothing of its own, so there is no idempotency-key or conditional-put concern. The only side effect in the request path is the rate-limit counter increment (`_bucket_limit`), which is **intentionally non-idempotent** — each request consumes one unit of budget (that is the point of a rate limiter). Two concurrent searches from the same IP may race the counter `get`→`put` (a benign lost-update at most undercounts by a request near the boundary — acceptable for a throttle, §10.1).

### 7.3 Security

- **Auth**: none — the endpoint is public by design (the storefront contract, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:33-40,178`). The access gate is hotel **publication** (HTL-025 `public_get_hotel` 404s an unpublished/non-existent hotel), not a session — exactly the calendar public-router posture (`app/routers/calendar.py:1946-1974`, gate = `link_id`).
- **Abuse protection**: the per-IP rate limit (§4.5) caps the fan-out an anonymous caller can drive into the availability/price engine. Without it, an unauthenticated endpoint that fans out to per-date availability reads would be a DoS amplifier (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:184-186`).
- **Flag-off is 404, not 401/403**: a probe against a disabled vertical learns only "not found" — no entity-existence leak (cross-cutting `:26-32`).
- **No information leak via the unpublished-hotel path**: an unpublished hotel returns the **same** 404 as a non-existent hotel (`public_get_hotel` does not distinguish them in the public response), so a guest cannot enumerate unpublished hotels by id.
- **Input safety**: `hotel`, `checkin`, `checkout` are validated/parsed; dates via `date.fromisoformat` (no injection surface — no SQL, no shell, no filesystem path). `hotel` flows only into the forward-deps' exact-match DDB key conditions (no scan-filter injection). Occupancy ints are range-bounded at the `Query()` edge.
- **IP spoofing caveat**: `request.client.host` is the immediate peer; behind a proxy/load-balancer it may be the LB IP unless `X-Forwarded-For` handling is configured at the ASGI/proxy layer. This is an operational deployment concern (the same caveat as any IP-keyed limiter), tracked as an assumption (§10.2). The fail-open + flag-gate posture means a degraded IP signal weakens throttling but never blocks legitimate search.

### 7.4 Money-safety — read-only, no ledger interaction

`quote_stay` is **read-only** and issues **no** Stripe/PayPal/CCBill call and writes **no** ledger entry (cross-cutting "checkout reuses the cart→order→payment money path" — but that is HTL-027's checkout, not search, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:46-53`). It surfaces `total_price_cents` for **display only** — the figure comes verbatim from the engine's `total_cents` (HTL-017 §7.4, sourced from HTL-015 `compute_stay_price`); search neither re-computes nor persists any monetary value. All money stays in integer cents — no float money field. The authoritative re-quote-at-add-time + the binding charge happen later in HTL-027's `add_room_to_cart` / `checkout_booking_cart` (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:245-268`), never in search. HTL-026 imports no billing primitive and has zero financial invariants to enforce.

### 7.5 Audit trail

`quote_stay` emits **no** audit event (it is a read; consistent with HTL-017 §7.5 and HTL-025's read paths, which emit at most a low-cardinality best-effort `hotel.storefront.viewed`). The `_audit()` wrapper already exists in `hotel_storefront.py` (HTL-025) for the HTL-027 mutation paths; HTL-026 does not call it. (An optional best-effort `hotel.storefront.searched` audit is a non-breaking additive follow-up, §10.6 — omitted from v1 to avoid high-cardinality, unauthenticated audit spam.)

### 8.1 Additive-only changes

HTL-026 adds:
- One service function `quote_stay` (+ helpers `_validate_quote_span`, `_project_result`, `_room_type_projection`, `_per_night`) to the **existing** `app/services/hotel_storefront.py` (HTL-025's module) — additive.
- One route handler `GET /booking-engine/search` (+ `_rate_limit_search_or_429`) on HTL-027's `booking_engine_router` — additive.
- Two output-only Pydantic models to `app/models.py`: `StayQuoteResultOut`, `StayQuoteOut` (additive; no existing model modified). `PublicRoomTypeOut` is reused from HTL-025; `PerNightAvailOut` is a small new output model (§3.1).
- Four `HOTEL_BOOKING_SEARCH_*` settings to `app/core/settings.py` with safe defaults (additive).

No existing endpoint, service function, DynamoDB table, GSI, or Pydantic model is modified. With `HOTEL_PMS_ENABLED=false` (the default), the endpoint 404s — the running platform is byte-for-byte unchanged and produces zero new DynamoDB traffic.

### 8.2 No DynamoDB migration

HTL-026 creates no table, no GSI, no `attr_types` change. `quote_stay` reads only through the forward-dep functions (which use HTL-001/005/010/011 tables); the rate-limit bucket reuses the existing `sessions` table (`app/services/rate_limit.py:64`). `just restart` in dev requires nothing new for HTL-026 itself.

### 8.3 Production deployment sequence

1. Deploy the upstream clusters (HTL-001/005/010/011/012/015/017/025) and HTL-027 (router declaration + registration) with `HOTEL_PMS_ENABLED=false` — all entrypoints 404.
2. Deploy HTL-026 (the `/search` handler + `quote_stay` + models + settings) with the flag still `false` — the route is mounted but 404s.
3. Enable `HOTEL_PMS_ENABLED=true` once the upstream tables/indexes are verified healthy — `GET /booking-engine/search` becomes live.

Zero-downtime; full rollback at any step by toggling the flag.

### 8.4 Rollback

Fast operational rollback: `HOTEL_PMS_ENABLED=false` — the endpoint 404s with no redeploy. Code rollback reverts the additive function/handler/model/settings changes. Because HTL-026 owns no persisted state (the rate-limit counters in the `sessions` table are TTL'd and self-expire, `app/services/rate_limit.py:75`), there is no data to migrate or drop on rollback.

### 8.5 Forward-dep ordering

HTL-026 is a **consumer** of HTL-017 (`search_stays`) and HTL-025 (`public_get_hotel`, the service module, the flag scaffolding), and is **mounted on** HTL-027's `booking_engine_router`. It can be **merged** before HTL-017/HTL-025/HTL-027 land (its hermetic tests patch the collaborators and call the handler coroutine directly, §9.1), but it cannot **run live** until they do. The parent doc's dependency order (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:429`) places HTL-025 → HTL-026 → HTL-027 in sequence.

## 10. Open Questions / Assumptions

1. **Rate-limit counter race.** Two concurrent searches from the same IP race the `_bucket_limit` `get`→`put` (`app/services/rate_limit.py:64-76`), a benign lost-update that can let a request or two slip past the cap near the boundary. **Assumption**: acceptable for a coarse abuse throttle on a public read; a strict atomic counter (a conditional `ADD` like `rate_limit_or_429`'s, `:42-58`) is a non-breaking refinement if precise enforcement is ever required. The existing `_bucket_limit` is the prescribed reuse (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:184-188`).

2. **IP source behind a proxy.** `request.client.host` is the immediate peer; behind an LB it may be the LB IP unless `X-Forwarded-For` is honored at the ASGI/proxy layer (§7.3). **Assumption**: the deployment configures forwarded-IP handling, or accepts coarser (LB-level) throttling. A per-IP-prefix key (like `rate_limit._ip_prefix`, `:84-91`) is a non-breaking alternative if per-exact-IP proves too granular behind NAT.

3. **`Retry-After` precision.** The header returns the full window length (`win`), a conservative upper bound, not the exact "seconds until the bucket resets." **Assumption**: a conservative `Retry-After` is acceptable; computing `win - (now - bucket_start)` is a non-breaking refinement (requires reading the bucket's `bucket_start`, which `_bucket_limit` does not currently return).

4. **`per_night` shape — price line vs availability line.** The ticket's quote shape names `per_night: [{date, rooms_available, rate_cents}]` (an availability+rate line, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:169`), while HTL-017's `StayRoomTypeResult.per_night` is the HTL-015 **price** line (`NightLineOut`, HTL-017 §3.2). **Assumption**: HTL-026 surfaces the engine's per-night data and maps it to `PerNightAvailOut{date, rooms_available, rate_cents}`, sourcing `rooms_available` from the availability half and `rate_cents` from the price half of the engine result. If HTL-017's `StayRoomTypeResult` does not co-carry both, HTL-026 either (a) reads the price `per_night` only and surfaces `rate_cents` (omitting `rooms_available` per night, carrying only the binding `available_rooms`), or (b) HTL-017 is extended (non-breaking) to co-carry availability per-night. The exact mapping reconciles at HTL-017 merge; HTL-026 never recomputes either value.

5. **Room-type projection source.** `StayQuoteResultOut.room_type` is `PublicRoomTypeOut`-shaped (full storefront fields: photos, amenities, bed_type, etc.). HTL-017's `StayRoomTypeResult` carries only `room_type_id` + `name`. **Assumption**: HTL-026 builds the full `PublicRoomTypeOut` by joining the engine result with HTL-025's `public_list_room_types(hotel_id)` (one lookup per quote, indexed by `room_type_id`), OR HTL-027/HTL-028 hydrate the richer fields client-side from a separate `/room-types` call. v1 returns at least `room_type_id` + `name` + the price/availability; the full hydration is a non-breaking enrichment tracked at HTL-025/HTL-017 merge.

6. **No `hotel.storefront.searched` audit in v1.** An unauthenticated, high-traffic search endpoint emitting an audit per call would flood the audit log. **Assumption**: v1 emits no audit (§7.5); a sampled or aggregate search-metric is a non-breaking follow-up if product wants search analytics.

7. **`city` search is out of scope.** The public endpoint is hotel-scoped (`hotel` required). **Assumption**: a multi-hotel/city public search is a separate future ticket (the engine already supports `city=`, HTL-017 §5.6); HTL-026 deliberately exposes only the hotel-scoped path.
