# HTL-035 — Hotel KPI reports — occupancy / ADR / RevPAR / revenue / arrivals-departures

**Type**: Feature | **Priority**: P1 | **Estimate**: 2d
**Source**: `docs/qloapps/CANCELLATION_REPORTS_TICKETS.md` §HTL-035 + "Cross-cutting constraints" (`:32-83`) + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §"Reports & KPIs" row (`:110`)

---

## 1. Summary & Goal

HTL-035 lands the **hotel KPI report service** — the four canonical hospitality metrics
(occupancy %, ADR, RevPAR, room revenue) plus the two front-desk counts (arrivals,
departures) computed over a `[from, to)` date range for a single hotel. It ships exactly
three deliverables:

1. **`app/services/hotel_reports.py`** (new file) — a pure-aggregation `compute_hotel_kpis`
   service that reads the existing `hotel_reservations` (HTL-018) + `hotel_availability`
   (HTL-010) GSIs and computes the metric table below. **No new DynamoDB table, no new GSI,
   no new write** — it is a read-only aggregation over inventory already landed by HTL-010
   and HTL-018.
2. **One read endpoint** `GET /ui/hotels/{hotel_id}/reports/kpis?from=&to=` declared under
   the hotels router, `require_ui_session` (read), flag-gated 404, 422 on an inverted or
   oversized range.
3. **A thin forward-compatible dashlet hook** — registering a `hotel_kpis` dashlet
   `dashlet_type` in the RPT-006 dashlet registry (`docs/suitecrm/specs/RPT-006.md` §4.1
   `VALID_DASHLET_TYPES`) whose data provider calls `compute_hotel_kpis` over a configurable
   `period_days` window, **mirroring** (not re-building) the PMD-003 property-KPI dashlet
   (`docs/open-property/specs/PMD-003.md` §"`portfolio_summary` dashlet provider"). The
   dashlet hook is additive to the RPT registry and only active when both `HOTEL_PMS_ENABLED`
   and the RPT dashboard flag are on.

The distinctive net-new computation is **room-night-basis aggregation across reservations
whose nights intersect a range**: `rooms_sold` is a room-*night* count (a 3-night stay = 3
sold room-nights), not a reservation count, and `room_revenue_cents` is the room-night
revenue of those stays. This is the hotel ADR/RevPAR math the platform's existing money
dashboards have no concept of: `app/services/platform_financial_dashboard.py` tracks
platform-wide GMV / net revenue / take-rate from the billing ledger
(`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:110` — "RPT-001..009 builder + PMD-003 property KPIs;
no hotel-specific ADR/RevPAR/arrivals dashlets"), and PMD-003 computes a landlord's rent-roll
occupancy — neither computes ADR/RevPAR/occupancy over a hotel's dated room-night inventory.

Without HTL-035 the gap-analysis "Reports & KPIs (occupancy, ADR, RevPAR, revenue,
arrivals/departures)" row (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:110`, **PARTIAL/PLANNED**)
is unmet. With HTL-035 merged but `HOTEL_PMS_ENABLED=false` (the default), the platform is
byte-for-byte unchanged: `compute_hotel_kpis` 404s before any DynamoDB access (the
`_require_enabled()` contract, `app/services/inventory.py:54-56`), the endpoint 404s, and the
dashlet provider only activates when both flags are on.

### 2.5 HTL-018 reservation GSIs — the room-night/revenue/arrivals source

HTL-018 (`docs/qloapps/specs/HTL-018.md` §3.1) lands the `hotel_reservations` table with three
GSIs and these header attributes HTL-035 reads:

| Attribute | DDB Type | HTL-035 use |
|---|---|---|
| `hotel_id` | S | GSI partition for the per-hotel reservation query |
| `checkin` | S `YYYY-MM-DD` | arrivals count + room-night span lower bound |
| `checkout` | S `YYYY-MM-DD` (exclusive) | departures count + room-night span upper bound (exclusive — departure day not a billable night, HTL-018 §3.1 / HTL-010 §5.5) |
| `nights` | N | denormalized night count of `[checkin, checkout)` (`_validate_span` result, HTL-018 §3.1) |
| `rooms` | N | rooms of this type held (≥1) — room-night multiplier |
| `total_cents` | N | frozen `compute_stay_price(...).total_cents` quote for the **whole stay** (HTL-018 §5.6) |
| `currency` | S | ISO-4217 lowercase echo of the price result |
| `status` | S | `confirmed`/`checked_in`/`checked_out`/`cancelled`/`no_show` (HTL-018 §3.1) |

The two GSIs HTL-035 uses:

| Index | PK | SK | HTL-035 use |
|---|---|---|---|
| `GSI_HOTEL_ARRIVALS` | `hotel_id` (S) | `checkin` (S `YYYY-MM-DD`) | All reservations whose **check-in** falls in a date window, date-ordered (lexical==chronological). The primary scan path: query `checkin BETWEEN(from, to_extended)` to capture every stay whose nights could intersect `[from, to)`. |
| `GSI_HOTEL_STATUS` | `hotel_id` (S) | `status` (S) | Optional secondary path: bucket a hotel's reservations by lifecycle status. Used only if the implementor prefers to query `status IN {confirmed, checked_in, checked_out}` per-status; the arrivals-window path (with an in-memory status filter) is the primary one — see §5.3. |

Both GSIs project `ALL` (HTL-018 §3.1), so a query returns full header rows — no second
`get_item` per reservation. The `GSI_GUEST` index (PK=`guest_party_id`) is **not** used by
HTL-035 (it is per-guest history).

> **Window-extension note.** `GSI_HOTEL_ARRIVALS` is keyed on `checkin`. A reservation with
> `checkin` *before* `from` can still have nights inside `[from, to)` (a stay spanning the
> window's left edge). HTL-035 therefore queries `checkin` over an **extended lower bound**
> `from - MAX_STAY_NIGHTS` (a config cap, §6.2) so no overlapping stay is missed, then computes
> each stay's per-night intersection in memory (§5.1). This is the standard date-range-overlap
> idiom for a single-date-keyed index. The alternative — a full per-hotel partition read with no
> SK bound — is also correct but reads more; the extended-window query is the documented default.

### 2.6 HTL-010 availability GSI — the rooms-available denominator

HTL-010 (`docs/qloapps/specs/HTL-010.md` §3.1) lands `hotel_availability` with one item per
`(hotel_id, room_type_id, date)` and `GSI_HOTEL_DATE` (PK=`hotel_id` S, SK=`date` S). HTL-035
reads:

| Attribute | DDB Type | HTL-035 use |
|---|---|---|
| `hotel_id` | S | `GSI_HOTEL_DATE` partition |
| `date` | S `YYYY-MM-DD` | `GSI_HOTEL_DATE` sort key — `between(from, to_inclusive)` is date-ordered for free |
| `total_rooms` | N | physical rooms of this type sellable on this date — the **per-date capacity** summed across all room types and all in-range nights to form `rooms_available` |

`rooms_available` is `sum over each night d in [from, to) of (sum over room types of total_rooms[d])`
— i.e. the per-date capacity from `GSI_HOTEL_DATE`, summed over every in-range night. A
never-seeded date contributes `0` (it has no `total_rooms` row → it is sold-out / no capacity,
the HTL-010 §5.4 zeroed-virtual semantic). HTL-035 reads `total_rooms` directly off the GSI rows;
it does **not** call HTL-010's `get_availability` per night (that is a per-`(hotel,room_type)`
span reader; the hotel-wide `GSI_HOTEL_DATE` query is the cheaper denominator source, exactly the
"hotel-wide availability calendar across ALL room types for a date range without scanning each
room type's partition separately" purpose stated in HTL-010 §3.1).

### 2.8 Cancelled / no-show exclusion (HTL-033/034 status)

Cancellation / no-show lifecycle status is owned by HTL-033 (refund engine) and HTL-034
(policy CRUD + reservation transitions), which set `status="cancelled"` / `status="no_show"` on

never counts it (it lives in the billing ledger, which HTL-035 does not read). See §5.4.

## 3. Data Model

HTL-035 introduces **no new DynamoDB table, no new GSI, and no new DynamoDB attribute**. The
cross-cutting constraint is explicit: "KPI reports are pure aggregation over existing reservation
+ availability GSIs (HTL-035) — no new table"
(`docs/qloapps/CANCELLATION_REPORTS_TICKETS.md:59-60`). This section documents which GSIs are
read and the single new Pydantic response model.

### 3.1 Tables/GSIs read (reused from HTL-018 + HTL-010)

| Table | Index read | PK / SK | Read pattern in HTL-035 |
|---|---|---|---|
| `hotel_reservations` (HTL-018 §3.1) | `GSI_HOTEL_ARRIVALS` | `hotel_id` (S) / `checkin` (S `YYYY-MM-DD`) | `KeyConditionExpression=Key("hotel_id").eq(hotel_id) & Key("checkin").between(from_ext, to_minus_one)` — every reservation whose check-in is in the extended window (§2.5), date-ordered. `LastEvaluatedKey`-looped. |
| `hotel_reservations` (HTL-018 §3.1) | `GSI_HOTEL_STATUS` | `hotel_id` (S) / `status` (S) | Optional alternate path (§5.3); not the default. |
| `hotel_availability` (HTL-010 §3.1) | `GSI_HOTEL_DATE` | `hotel_id` (S) / `date` (S `YYYY-MM-DD`) | `KeyConditionExpression=Key("hotel_id").eq(hotel_id) & Key("date").between(from, to_minus_one)` — every per-`(room_type, date)` capacity row in-range. `LastEvaluatedKey`-looped. |

**`attr_types`**: HTL-035 reads no numeric GSI sort key (`GSI_HOTEL_ARRIVALS` SK=`checkin` S,
`GSI_HOTEL_STATUS` SK=`status` S, `GSI_HOTEL_DATE` SK=`date` S are all String). It therefore
adds **no** `attr_types` entry (CLAUDE.md numeric-GSI rule N/A — the numeric `nights`/`rooms`/
`total_cents` fields are plain item attributes, never index keys). The cross-cutting constraint
confirms: "This cluster adds no new tables, so no new `attr_types`"
(`docs/qloapps/CANCELLATION_REPORTS_TICKETS.md:64-65`).

### 3.2 Pydantic model (`app/models.py`)

One new read-only response model — additive; no existing model modified.

```python
class HotelKpisOut(BaseModel):
    hotel_id: str
    from_ts: int                       # epoch seconds, inclusive lower bound of the range
    to_ts: int                         # epoch seconds, exclusive upper bound
    rooms_available: int               # denominator for occupancy & RevPAR (room-nights)
    rooms_sold: int                    # occupied room-nights in [from, to)
    occupancy_pct: float               # rooms_sold / max(rooms_available, 1) * 100, 1-decimal
    room_revenue_cents: int            # room-night revenue settled/owed in [from, to)
    adr_cents: int                     # room_revenue_cents // max(rooms_sold, 1)
    revpar_cents: int                  # room_revenue_cents // max(rooms_available, 1)
    arrivals: int                      # reservations with check_in in [from, to)
    departures: int                    # reservations with check_out in [from, to)
    currency: str                      # hotel default currency (lowercase ISO 4217)
```

All integer fields are cents/counts (the cross-cutting "money-as-cents" constraint,
`docs/qloapps/CANCELLATION_REPORTS_TICKETS.md:51-54`: `room_revenue_cents`/`adr_cents`/
`revpar_cents` are integer cents). `occupancy_pct` is the only float — rounded to 1 decimal in
the service (§4.3 step 8). The model accepts the service's already-coerced `int` dict and
re-coerces DynamoDB `Decimal` automatically for the integer fields, though the service hands it
clean `int`s (§4.4).

### 3.3 No dates as strings in the response

`from_ts` / `to_ts` are **epoch seconds** in the response (matching the endpoint query
contract, §4.5, where `from`/`to` are date strings the router converts). The KPI math internally
works in `YYYY-MM-DD` date strings (the inventory key convention), but the response echoes the
epoch bounds so the FE/dashlet has an unambiguous range (a date string would lose the half-open
`[from, to)` semantics). The router converts `?from=YYYY-MM-DD&to=YYYY-MM-DD` → epoch (midnight
UTC) before calling the service (§4.5).

### 4.1 Service module: `app/services/hotel_reports.py` (new file)

Modeled on `app/services/inventory.py` (flag/audit/`_to_int` idioms) and PMD-003's read-only

```python
def _audit(event: str, user_sub: str, **fields: Any) -> None:  # copy of inventory.py:92-98

def _to_int(value: Any, default: int = 0) -> int:        # copy of inventory.py:67-73
    try:
        return default if value is None else int(value)
    except (TypeError, ValueError):
        return default

def _date_str(epoch: int) -> str:
    from datetime import datetime, timezone
    return datetime.fromtimestamp(epoch, tz=timezone.utc).strftime("%Y-%m-%d")

def _date_range(start: str, end_exclusive: str) -> list[str]:
    """Half-open [start, end_exclusive) list of YYYY-MM-DD strings (the in-range NIGHTS)."""
    from datetime import date, timedelta
    d0, d1 = date.fromisoformat(start), date.fromisoformat(end_exclusive)
    out, cur = [], d0
    while cur < d1:                       # end exclusive — departure night not counted
        out.append(cur.isoformat()); cur += timedelta(days=1)
    return out
```

### 4.2 `compute_hotel_kpis`

```python
def compute_hotel_kpis(hotel_id: str, *, from_ts: int, to_ts: int) -> dict:
    """Pure aggregation over the HTL-018 reservation GSI + the HTL-010 availability GSI.
    _require_enabled() (404 when HOTEL_PMS_ENABLED off). 422 on to_ts <= from_ts or range
    > HOTEL_KPI_MAX_RANGE_DAYS. No scan, no new table, no DDB write."""
```

**Flow** (per `docs/qloapps/CANCELLATION_REPORTS_TICKETS.md` §HTL-035 service block `:349-362`):

1. **`_require_enabled()`** — 404 when `hotel_pms_enabled` off, before any DDB access.

2. **Validate the range** — `if to_ts <= from_ts: raise HTTPException(422, "to must be after
   from")`. Compute `range_days = (to_ts - from_ts) // 86400`; `if range_days >
   S.hotel_kpi_max_range_days: raise HTTPException(422, "range too large")` (default cap 366 days,
   §6.2). Derive the date strings: `from_date = _date_str(from_ts)`,
   `to_date_excl = _date_str(to_ts)`. `nights = _date_range(from_date, to_date_excl)` — the list
   of in-range billable nights (departure night excluded, the HTL-010 §5.5 / HTL-018 §3.1
   `[checkin, checkout)` convention).

3. **`rooms_available` (denominator)** — query `GSI_HOTEL_DATE` on `hotel_availability`:
   `KeyConditionExpression=Key("hotel_id").eq(hotel_id) & Key("date").between(from_date,
   _last_night(nights))`, looping on `LastEvaluatedKey` (the CLAUDE.md "DDB FilterExpression
   doesn't reduce page size" gotcha — must loop or a busy hotel silently truncates,
   `docs/qloapps/CANCELLATION_REPORTS_TICKETS.md` §HTL-035 `:353-356`). For each returned row
   whose `date` is in `set(nights)`, accumulate `rooms_available += _to_int(row["total_rooms"])`.
   A night with no row contributes `0` (zeroed-virtual, HTL-010 §5.4). `_last_night(nights)` is
   `nights[-1]` (the last in-range night) so the `between` upper bound is inclusive of the final
   billable night and the departure day is never read.

4. **Fetch in-range reservations** — query `GSI_HOTEL_ARRIVALS` on `hotel_reservations`:
   `KeyConditionExpression=Key("hotel_id").eq(hotel_id) & Key("checkin").between(from_ext,
   to_date_excl)` where `from_ext = _date_str(from_ts - S.hotel_kpi_max_stay_nights * 86400)`
   (the extended lower bound, §2.5 — captures stays that began before `from` but whose nights
   reach into the range), looping on `LastEvaluatedKey`. This yields every reservation whose
   check-in could overlap the range. (Reservations checking in on/after `to_date_excl` are
   excluded by the `between` upper bound — their first night is at/after the range end.)

5. **Per-reservation aggregation** — initialize `rooms_sold = 0`, `room_revenue_cents = 0`,
   `arrivals = 0`, `departures = 0`. For each reservation `r`:
   - **arrivals / departures** count regardless of status-sale-exclusion? No — count
     arrivals/departures over the **non-cancelled** front-desk view: a cancelled reservation is
     not an arrival. Decide via §5.4: arrivals/departures count reservations **excluding
     `cancelled`** (a no-show *is* a departure-day event and *is* an arrival expectation — but a
     no-show guest never arrived; per the ticket, `arrivals`/`departures` count reservations by
     `check_in_ts`/`check_out_ts` in range — see §5.4 for the authoritative status policy).
     Increment `arrivals += 1` if `from_date <= r["checkin"] < to_date_excl`; increment
     `departures += 1` if `from_date <= r["checkout"] < to_date_excl` (checkout is the
     `YYYY-MM-DD` departure date; both compared as date strings, lexical==chronological).
   - **room-night sale** — skip `if r["status"] in {"cancelled", "no_show"}` (§5.4). For a
     sold reservation, compute its **in-range night intersection**:
     `r_nights = _date_range(r["checkin"], r["checkout"])`;
     `in_range = [d for d in r_nights if from_date <= d < to_date_excl]`;
     `n_in = len(in_range)`; `rooms = _to_int(r["rooms"], 1)`;
     `rooms_sold += n_in * rooms`.
   - **room revenue** — the reservation's `total_cents` is the **whole-stay** quote (HTL-018
     §5.6). Pro-rate it to the in-range nights so a stay straddling the window contributes only
     its in-range share: `total_nights = _to_int(r["nights"]) or len(r_nights) or 1`;
     `room_revenue_cents += (_to_int(r["total_cents"]) * n_in) // total_nights`. Integer
     floor-division keeps it in integer cents (§5.5 details the rounding rule + rationale).

6. **`occupancy_pct`** — `occupancy_pct = round(rooms_sold / max(rooms_available, 1) * 100, 1)`
   — 1-decimal percent; `max(rooms_available, 1)` never divides by zero (the ticket's
   "never divides by zero", `docs/qloapps/CANCELLATION_REPORTS_TICKETS.md:340`).

7. **`adr_cents`** — `adr_cents = room_revenue_cents // max(rooms_sold, 1)` (integer floor;
   Average Daily Rate = room revenue ÷ rooms sold, `:342`).

8. **`revpar_cents`** — `revpar_cents = room_revenue_cents // max(rooms_available, 1)` (integer
   floor; Revenue Per Available Room = room revenue ÷ rooms available, `:343`; equivalently
   `adr × occupancy` — see §5.6 for the identity and the integer-rounding caveat).

9. **`currency`** — the hotel's default currency, lowercased. Source order: the most common
   non-empty `currency` across the in-range sold reservations (a hotel quotes one currency); else
   the HTL-001 hotel header default; else `"usd"`. HTL-035 does **no** FX conversion (the ticket:
   "`currency` is the hotel's default currency, carried for the FE; HTL-036 may convert via the
   INV-002 FX accessor when multi-currency is on", `:366-367`).

10. **Return** the dict:
    ```python
    return {
        "hotel_id": hotel_id, "from_ts": from_ts, "to_ts": to_ts,
        "rooms_available": rooms_available, "rooms_sold": rooms_sold,
        "occupancy_pct": occupancy_pct, "room_revenue_cents": room_revenue_cents,
        "adr_cents": adr_cents, "revpar_cents": revpar_cents,
        "arrivals": arrivals, "departures": departures, "currency": currency,
    }
    ```

All numeric values are plain `int` (`_to_int`-coerced) except `occupancy_pct` (`float`). No
audit event is emitted (read-only, §2.3). No DynamoDB write occurs.

### 4.3 LastEvaluatedKey looping helper

Both GSI reads loop until exhausted. A small private helper avoids duplication:

```python
def _query_all(index_name: str, key_cond, *, table) -> list[dict]:
    items, lek = [], None
    while True:
        kwargs = {"IndexName": index_name, "KeyConditionExpression": key_cond}
        if lek:
            kwargs["ExclusiveStartKey"] = lek
        resp = table.query(**kwargs)
        items.extend(resp.get("Items", []))
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            return items
```

This is the `_scan_ledger_entries` / `_query_ledger_by_date` `LastEvaluatedKey`-loop pattern
PMD-003 reuses (`docs/open-property/specs/PMD-003.md` §2.1 refs to
`platform_financial_dashboard.py:136,161,181-191`). No `FilterExpression` is used on either query
(both are pure key-range queries), so the loop is the only correctness concern — no page is
silently dropped on a busy hotel.

### 4.4 `_kpis_out` coercion

A tiny coercion helper (mirrors `inventory._record_out`, `app/services/inventory.py:101-115`)
guarantees every count/cents field is plain `int` and `occupancy_pct` is `float` before the dict
crosses into `HotelKpisOut`. The service builds the dict already-coerced in §4.2 step 10, so
`_kpis_out` is a thin defensive pass (idempotent).

### 4.5 Router endpoint

Declared under the hotels router (the HTL-001 hotels router, `app/routers/hotels.py`):

| Method | Path | Auth dep | Service call |
|---|---|---|---|
| `GET` | `/ui/hotels/{hotel_id}/reports/kpis?from=&to=` | `require_ui_session` (`app/services/sessions.py:330`) | `compute_hotel_kpis(hotel_id, from_ts=, to_ts=)` |

**Handler behavior**:
1. `from` / `to` are required `YYYY-MM-DD` query params. Parse each with
   `date.fromisoformat(...)` inside a `try/except` → `HTTPException(422, "invalid date")` on a
   malformed string. Convert to epoch midnight UTC:
   `from_ts = int(datetime(d.year, d.month, d.day, tzinfo=timezone.utc).timestamp())`.
2. `to_ts` is the **exclusive** upper bound — the caller passes the day *after* the last day they
   want included, OR (UX choice for the FE) the router adds one day to make `to` inclusive. The
   spec's default: `to` is **exclusive** (matches the half-open `[from, to)` convention end-to-end
   and the `checkout`-exclusive room-night model). HTL-036's FE sends `to = last_day + 1`.
3. `compute_hotel_kpis(hotel_id, from_ts=from_ts, to_ts=to_ts)` — propagates the service's 404
   (flag off) and 422 (`to <= from` / oversized range).
4. **404 on unknown hotel** — the ticket requires "404 on unknown hotel" (`:373`). HTL-035's
   service does not 404 an unknown hotel by itself (an empty reservation/availability query simply
   yields all-zero KPIs). The router enforces the unknown-hotel 404 via the HTL-001 hotel-existence
   check: `if not hotels.get_hotel(hotel_id): raise HTTPException(404, "hotel not found")` **before**
   calling `compute_hotel_kpis` (the same pattern other hotel sub-routers use). See §5.7.
5. Return `HotelKpisOut(**result)`.

**Declaration order**: the literal `/reports/kpis` sub-route MUST be declared **before** any
dynamic `/{...}` sibling under `/ui/hotels/{hotel_id}` so the literal `reports` segment is not
captured as a path param (the FastAPI declaration-order gotcha, CLAUDE.md — same class as the KYC
`/templates`-before-`/{case_id}` and audit-export `/schedules`-before-`/{export_id}` orderings;
the ticket calls it out explicitly, `:375-376`). Because `hotel_id` is a path param and
`reports/kpis` is a deeper literal segment, the ordering matters only relative to any
`/ui/hotels/{hotel_id}/{something}` dynamic sibling; declaring the KPI route before such a sibling
is the safe rule.

## 5. Detailed Behavior & Edge Cases

### 5.1 Room-night intersection (the core computation)

`rooms_sold` is a room-*night* count, not a reservation count (the ticket: "a 3-night stay = 3
sold room-nights, not a reservation count", `:389`). For each sold reservation, HTL-035 computes
`in_range = [d for d in [checkin, checkout) if from_date <= d < to_date_excl]` and adds
`len(in_range) * rooms`. Worked example: a reservation `checkin=2026-06-01`,
`checkout=2026-06-04` (nights `06-01, 06-02, 06-03`), `rooms=2`, queried over
`[2026-06-02, 2026-06-04)` → in-range nights `06-02, 06-03` → `rooms_sold += 2 * 2 = 4`. A stay
entirely outside the range contributes `0` and is harmless even though the extended-window query
returned it. A stay fully inside contributes all its nights × rooms.

### 5.2 Window extension and the extended lower bound

Because `GSI_HOTEL_ARRIVALS` is keyed on `checkin`, the query lower bound is extended by
`HOTEL_KPI_MAX_STAY_NIGHTS` days (`from_ext`, §4.2 step 4) so a stay that began before `from` but
reaches into the range is not missed. Any returned stay whose in-range intersection is empty
contributes nothing (§5.1) — the extension over-fetches slightly but never miscounts. A hotel
that allows stays longer than the cap would under-count those rare ultra-long stays; the cap
default (370 nights, §6.2) exceeds any realistic stay and the oversize is an accepted documented
limit (§10-Q2).

### 5.3 Status-bucket alternate query path (optional)

The §4.2 step 4 default queries `GSI_HOTEL_ARRIVALS` and filters status in memory. An alternate
is to query `GSI_HOTEL_STATUS` once per non-excluded status (`confirmed`, `checked_in`,
`checked_out`) — but that index is keyed on `status` with no date sort, so it returns *all* of the
hotel's reservations in that status (unbounded) and still needs the in-memory date intersection.
The arrivals-window path is therefore the documented default (date-bounded by the GSI SK). The
implementor MAY use `GSI_HOTEL_STATUS` if a hotel's lifetime reservation count in a status is
small; the result is identical. Either way the cancelled/no-show exclusion (§5.4) is applied.

### 5.4 Cancelled / no-show exclusion — authoritative status policy

- **`rooms_sold` / `room_revenue_cents`**: EXCLUDE `status in {"cancelled", "no_show"}`. A
  cancelled stay consumed no room-nights; a no-show guest occupied no room and (per the ticket,
  `:364-365`) the no-show *fee* is a penalty, not room revenue. Both are skipped entirely from the
  sale and revenue accumulation.
- **`arrivals` / `departures`**: count reservations whose `check_in_ts` / `check_out_ts` falls in
  `[from, to)` **excluding `cancelled`** (a cancelled booking is not a front-desk arrival). A
  `no_show` is **excluded from arrivals** (the guest never arrived) and **excluded from
  departures** (no occupancy to depart). This keeps `arrivals`/`departures` as the real front-desk
  movement count. (Rationale: the ticket's headline definition counts "reservations with check_in
  in range"; the front-desk-realistic reading excludes cancelled+no_show, which is the policy this
  spec adopts and tests assert — see §9.1 case 9.) The no-show fee never enters any HTL-035
  metric.

### 5.5 Revenue pro-rating and integer rounding

`total_cents` is the whole-stay quote (HTL-018 §5.6 — a frozen snapshot, the stay is priced once
at booking). When a stay straddles the window, only its in-range nights' share counts:
`room_revenue_cents += (total_cents * n_in) // total_nights` (integer floor-division), where
`total_nights = nights` (the denormalized HTL-018 field, falling back to `len([checkin, checkout))`
then `1`). Worked: `total_cents=30000`, `total_nights=3`, `n_in=2` →
`(30000 * 2) // 3 = 20000`. Multiply-before-divide (`total_cents * n_in` first) minimizes
truncation error vs dividing first. A fully-in-range stay (`n_in == total_nights`) yields exactly
`total_cents` (no rounding loss). All values stay integer cents — the cross-cutting money-as-cents
constraint (`docs/qloapps/CANCELLATION_REPORTS_TICKETS.md:51-54`); there is **no float money** path.

### 5.6 The RevPAR = ADR × occupancy identity (and why HTL-035 computes RevPAR directly)

Mathematically `RevPAR = ADR × occupancy = (revenue / sold) × (sold / available) =
revenue / available`. HTL-035 computes `revpar_cents = room_revenue_cents //
max(rooms_available, 1)` **directly from revenue ÷ available** rather than multiplying
`adr_cents × occupancy_pct`, because the latter compounds two integer/float roundings and would
disagree with the direct formula by up to a few cents. The direct formula is the canonical
definition (`:343`) and is exact-to-integer-floor. The identity holds to within rounding and is
asserted (within tolerance) in the test plan (§9.1 case 6).

### 5.7 Empty range / unknown hotel / zero capacity

- **Empty result** (no reservations and no availability rows in range): `rooms_available=0`,
  `rooms_sold=0`, `occupancy_pct = round(0 / max(0,1) * 100, 1) = 0.0`,
  `room_revenue_cents=0`, `adr_cents = 0 // max(0,1) = 0`, `revpar_cents = 0 // max(0,1) = 0`,
  `arrivals=0`, `departures=0`, `currency="usd"` (fallback). No division by zero anywhere — every
  denominator is `max(x, 1)` (the ticket's "never divides by zero", `:340`).
- **Unknown hotel**: the **router** 404s (§4.5 step 4) via the HTL-001 hotel-existence check; the
  service itself would return all-zero KPIs for a non-existent hotel (harmless), but the endpoint
  surface returns 404 per the acceptance criterion (`:394`).
- **Zero capacity, non-zero sold** (over-committed / capacity not seeded but reservations exist):
  `rooms_available=0` → `occupancy_pct = rooms_sold / max(0,1) * 100` could exceed 100 (a
  meaningful over-sold signal). HTL-035 returns it **unclamped** (matching HTL-010 §5.3's
  unclamped negative-available philosophy); the FE may cap the display at 100% if desired.

### 5.8 Flag-off and RPT-not-merged behavior

- **`HOTEL_PMS_ENABLED=false`** (default): `compute_hotel_kpis` raises
  `HTTPException(404, "Hotel PMS is not enabled")` via `_require_enabled()` before any DDB access;
  the endpoint 404s; the dashlet provider's `try/except` swallows the 404 and returns the
  zero-KPI dict (so a stale dashlet never 500s). Platform byte-for-byte unchanged.
- **RPT-006/007 not yet merged**: the `VALID_DASHLET_TYPES` extension and the
  `_provider_hotel_kpis` branch are deferred — they reference symbols that do not exist yet. The
  hook is documented as a forward-compatible stub (§2.7); the service + `/reports/kpis` endpoint
  ship and are the FE's primary path (HTL-036). The dashlet registration is wired when RPT-006/007
  land, with no change to the service.

### 5.9 Date-string comparison correctness

All in-range membership tests compare `YYYY-MM-DD` strings (`from_date <= d < to_date_excl`).
ISO `YYYY-MM-DD` sorts lexically in chronological order (HTL-010 §5.6 "lexical==chronological"),
so string comparison is exact date comparison — no parsing per comparison, no timezone ambiguity
(the date strings are the inventory key convention; the epoch `from_ts`/`to_ts` are converted to
midnight-UTC date strings once at the top of `compute_hotel_kpis`).

### 5.10 Decimal coercion

`total_rooms`, `nights`, `rooms`, `total_cents` are stored `N` and returned by boto3 as
`Decimal`. `_to_int(...)` coerces each to plain `int` at the point of accumulation, so every
arithmetic operation is integer arithmetic and the returned dict has no `Decimal` (the
`inventory._to_int` pattern, `app/services/inventory.py:67-73`). `occupancy_pct` is a Python
`float` computed in the service from already-int operands.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_reports.py` contains **no** `if S.dev_mode` branch. The same DynamoDB GSI
queries run in dev (boto3 intercepted by moto in-process at startup via `app/core/dev_s3.py`) and
prod (real DynamoDB) via the identical `T.hotel_reservations` / `T.hotel_availability` handles.
This mirrors the cross-cutting parity constraint
(`docs/qloapps/CANCELLATION_REPORTS_TICKETS.md:75-78`) and the `app/services/inventory.py`
precedent (`app/services/inventory.py` has no `dev_mode` *branch* in its business logic — the
only occurrence of the string is the SECOPS-007 parity note in its module docstring at
`app/services/inventory.py:28`). HTL-035 does no KMS,
no S3, no provider call — there is nothing that *could* diverge dev↔prod.

### 7.2 Idempotency

`compute_hotel_kpis` is a **pure read/aggregate** function — it writes nothing to DynamoDB and
emits no audit event. Re-running it with the same `(hotel_id, from_ts, to_ts)` against unchanged
data produces an identical result (`occupancy_pct` float is deterministic). It is trivially
idempotent and safe to call repeatedly (e.g., a dashlet refresh loop). There is no write path, so
no conditional put, no version CAS, and no replay concern.

### 7.3 Security — auth split + ownership

The endpoint uses `require_ui_session` (`app/services/sessions.py:330`) — a **read**, matching the
cross-cutting auth split (`docs/qloapps/CANCELLATION_REPORTS_TICKETS.md:72-74`, identical to
`app/routers/inventory.py`: reads on `require_ui_session` (`app/routers/inventory.py:37`),
mutations on `require_admin_or_root_csrf` (`app/routers/inventory.py:48`,
`app/auth/policy.py:100`)). HTL-035 has no mutation, so no
`require_admin_or_root_csrf` surface. The service layer does **no** cross-hotel isolation check —
the router scopes by `hotel_id` and (single-platform-operator assumption) the authenticated
session is trusted; a multi-tenant deployment adds a router-layer ownership check (caller's hotel
scope vs `hotel_id`), additive and without changing the service (§10-Q5). KPI figures are
aggregate counts/revenue for one hotel — no PII (no guest names, no `guest_party_id`) is returned,
so the read surface is low-sensitivity.

### 7.4 Money-safety — no money fork, no double-count

HTL-035 issues **no** Stripe/PayPal/CCBill call, reads **no** billing ledger, and writes **no**
ledger entry — it never imports `billing_shared`. `room_revenue_cents` is derived purely from the
reservation header's frozen `total_cents` quote (HTL-018 §5.6), pro-rated to in-range nights in
**integer cents** (§5.5) — there is no float-money path and no provider attribution to fork (the
cross-cutting "ONE refund mechanism — never fork" and "money-as-cents" constraints,
`docs/qloapps/CANCELLATION_REPORTS_TICKETS.md:43-54`, are vacuously satisfied: HTL-035 moves no
money). The no-show fee (a real ledger penalty owned by HTL-034) is explicitly **excluded** from
room revenue (§5.4) so KPI revenue is never inflated by penalties. Because the function is
read-only, there is no double-charge surface: re-running it re-reads the same reservations and
re-derives the same numbers (no accumulation across calls).

### 7.5 Audit trail

A KPI read emits **no** audit event (read-only, §2.3; the PMD-003 precedent
`docs/open-property/specs/PMD-003.md` §2.1 — read-only KPI endpoints emit none). The `_audit()`
wrapper is copied in for parity only (so a future "export"/"snapshot" mutation has it ready). The
underlying reservation/availability writes (HTL-018 `hotel.reservation.created`, HTL-010
`hotel.availability.set_total`) are independently audited by their own services.

## 10. Open Questions / Assumptions

1. **Room-revenue source — header `total_cents` vs folio.** HTL-035 derives `room_revenue_cents`
   from the reservation header's frozen `total_cents` (HTL-018 §5.6) pro-rated to in-range nights.
   The ticket notes room revenue "excludes add-ons/tax — folio-level, HTL-029" (`:341`). HTL-018's
   `total_cents` is the room-night stay price (no add-ons, computed by HTL-015 `compute_stay_price`),
   so it is already room-only. **Assumption**: `total_cents` is room revenue; if a future folio
   (HTL-029) splits room vs add-on revenue, HTL-035 switches to the folio's room-only subtotal —
   additive, no model change to the response (`room_revenue_cents` stays the contract).

2. **Stays longer than `HOTEL_KPI_MAX_STAY_NIGHTS`.** The extended-window query (§2.5, §5.2) misses
   a stay whose check-in precedes `from` by more than the cap. **Assumption**: 370 nights exceeds
   any realistic hotel stay; ultra-long stays are out of scope and the under-count is an accepted
   documented limit. Raising the env var or doing a full per-partition read (no SK bound) are the
   escape hatches.

3. **`to` inclusive vs exclusive at the endpoint.** The spec adopts **exclusive** `to`
   (half-open `[from, to)`, matching the `checkout`-exclusive room-night model end-to-end). The FE
   (HTL-036) sends `to = last_day + 1`. **Assumption**: exclusive is the contract; if product wants
   an inclusive `to`, the router adds one day before calling the service (a one-line router change,
   no service change). Tests pin the exclusive semantics (case 10).

4. **arrivals/departures status policy.** §5.4 excludes `cancelled` and `no_show` from
   arrivals/departures (front-desk-realistic). The ticket's headline definition is "reservations
   with check_in in range" without naming the status filter. **Assumption**: the front-desk reading
   (exclude cancelled+no_show) is correct and is what tests assert; if product wants the raw
   booking count (include no_show as a "scheduled arrival that didn't show"), it is a one-line
   filter change. Documented and tested either way (case 9).

5. **Cross-tenant isolation.** The service does no cross-hotel authorization. **Assumption**:
   single-platform-operator deployment; the authenticated session is trusted and the router scopes
   by `hotel_id`. A multi-tenant SaaS scenario adds a router-layer ownership check, additive and
   without changing the service.

6. **Currency / FX.** HTL-035 returns the hotel's single default currency and does **no** FX
   conversion (the ticket: HTL-036 may convert via the INV-002 FX accessor when multi-currency is
   on, `:366-367`). **Assumption**: a hotel quotes one currency; mixed-currency reservations under
   one hotel are out of scope (the "most common currency" heuristic, §4.2 step 9, degrades
   gracefully). Multi-currency aggregation is HTL-036's concern.

7. **GSI_HOTEL_DATE includes non-bookable / OOS room types.** `rooms_available` sums `total_rooms`
   across **all** room types that have availability rows for an in-range date. **Assumption**: a
   room type with `total_rooms=0` (or no row) contributes zero — out-of-service capacity is modeled
   by setting `total_rooms=0` (HTL-010 §5.2 preserve-on-set), so the denominator already reflects
   sellable capacity. No separate "active room type" filter is applied.
