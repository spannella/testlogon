# HTL-018 — Reservation entity — model, table, `create_reservation`

**Type**: Feature | **Priority**: P0 | **Estimate**: 2.5d
**Source**: `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md` §HTL-018 + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C row 1

---

## 1. Summary & Goal

HTL-018 lands the **Reservation** entity — the foundational net-new record of the QloApps
hotel-PMS booking vertical that the gap analysis flags as the heart of the missing
reservation lifecycle (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:89-93`). It ships exactly three
deliverables: (1) the `hotel_reservations` DynamoDB table — PK=`reservation_id`, SK=`META`
for the reservation header, with three GSIs (arrivals-by-hotel, guest-history, hotel-by-status)
and the correct `attr_types` for the one numeric GSI sort key; (2) the `create_reservation`
and `get_reservation` service functions in `app/services/hotel_reservations.py` (the file
created by HTL-017); and (3) the Pydantic I/O models `ReservationCreateIn` / `ReservationOut`
in `app/models.py`.

The reservation header is the OFBiz `ORDER`-SK header analogue
(`docs/ofbiz/specs/ORD-001.md` §3.2) — it carries a `version` field for the optimistic-concurrency
state machine that HTL-019 builds on, and child `HIST#{ts:020d}#{event_id}` rows co-locate on
the same partition (also HTL-019). What HTL-018 adds over a plain ORD order is the **multi-night
date span** (the LSE date-range idea, `docs/open-property/specs/LSE-001.md` §3.2, adapted to
`YYYY-MM-DD` date strings to match the HTL availability/price date convention) and the
**atomic inventory hold + price compute at create time**: `create_reservation` re-checks
availability (HTL-012), holds the room-nights across the whole span (HTL-011 `hold_rooms`),
and computes the stay total (HTL-015 `compute_stay_price`) — all before the header row is
written, so a sold-out span never produces an orphan reservation.

Without HTL-018 in place, HTL-019 (lifecycle state machine + check-in/out/no-show + modify)
has no entity to transition. With HTL-018 merged but `HOTEL_PMS_ENABLED=false` (the default),
the platform is byte-for-byte unchanged: every service entrypoint 404s before touching
DynamoDB, and no new HTTP surface is exposed (the router is HTL-019/Tier-3's deliverable).

## 2. Context & Current State

### 2.1 Gap — no room-night reservation entity exists today

The gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:92`) records the reservation entity as
**PARTIAL**: "closest is open-property **LSE** lease (date-bounded tenant↔unit) + calendar
event interval; none model multi-night room-night reservation w/ occupancy + assigned rooms."
The §C lifecycle row (`:93`) records the lifecycle (search→cart→book→confirmed→checked-in→
checked-out→cancel/no-show; modify) as **PARTIAL** too: the OFBiz ORD state machine + history
(ORD-001/005/006) and the LSE `draft→active→ended` flow are reusable *patterns*, but "check-in/out/
no-show + date/room modify are absent." HTL-018 lands the entity; HTL-019 lands the lifecycle.

The codebase today has no `hotel_reservations` table, no `S.hotel_reservations_table_name`
setting, no `T.hotel_reservations` handle, and no reservation Pydantic models. The closest
structural artefacts are forward-design only:
- **ORD `orders`** — an `order_id`/`sk` header (`sk="ORDER"`) + `HIST#` child rows + a CAS
  state machine (`docs/ofbiz/specs/ORD-001.md` §3.2). HTL-018 reuses the **shape**
  (header + co-located history, a `version` CAS counter) but not the field set: an ORD order is
  a cart total with no date span (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:93`).
- **LSE `leases`** — a date-bounded tenant↔unit tenancy with a non-deterministic `lease_id`
  (`docs/open-property/specs/LSE-001.md` §3.2). HTL-018 reuses the **date-range + non-deterministic
  id** idea but not the model: a lease is a tenancy with informational rent, not a room-night
  reservation that consumes dated inventory.

Both are design specs; neither table is implemented in the running codebase.

### 2.4 ID derivation — non-deterministic, contrasted with ORD

`reservation_id = "res_" + uuid4().hex[:16]` is **non-deterministic** — a guest may legitimately
book the same hotel/room-type/span twice (two separate room-nights consumed), so creation is NOT
idempotent on its arguments. This mirrors the LSE `lease_id` non-determinism
(`docs/open-property/specs/LSE-001.md` §3.2) and contrasts sharply with the ORD deterministic
`sha256(corr)[:32]` order id (`docs/ofbiz/specs/ORD-001.md` §2.4): an ORD id is keyed on a cart
correlation that dedupes a retried checkout, but a fresh booking has no such correlation. The
non-determinism is intentional and is why `create_reservation` is not idempotent (see §7.2 — the
hold is the inventory-consumption act, and `hold_rooms` is itself non-idempotent per
`docs/qloapps/specs/HTL-011.md` §10).

### 2.5 Span validation + the `now_ts()` primitive — already present

HTL-017 added `_validate_span(checkin, checkout) -> int` to `hotel_reservations.py`
(`docs/qloapps/specs/HTL-017.md` §4.2) — it parses two `YYYY-MM-DD` strings with
`date.fromisoformat`, enforces `nights >= 1` (i.e. `checkout > checkin`), and returns the night
count of `[checkin, checkout)` (checkout exclusive). HTL-018 reuses it verbatim. Timestamps use
`now_ts()` (`app/core/time.py:2`) — integer Unix seconds.

### 2.6 Forward-dep services (HTL-011 / HTL-012 / HTL-015)

HTL-018 calls three services by id and never re-implements them (the cross-cutting "reuse
primitives, never fork" constraint, `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:62-68`):

- **`hold_rooms(hotel_id, room_type_id, checkin, checkout, quantity, *, user_sub, ttl_seconds=None) -> dict`**
  (HTL-011, `docs/qloapps/specs/HTL-011.md` §4 line 208). All-or-nothing across the span: a
  hold that succeeds on nights 1–2 but hits a sold-out night 3 rolls back nights 1–2 and raises
  `HTTPException(409)`, writing **no** `HOLD#` meta row (`docs/qloapps/specs/HTL-011.md` §5
  "Span rollback"). On full success it mints `hold_id = uuid4().hex` and returns the meta dict
  carrying `hold_id` (`:236`). `release_hold(hold_id, *, reason, user_sub, terminal_status)`
  (`:245`) is the idempotent compensating release HTL-019 cancel/no-show calls.
- **`check_availability(hotel_id, room_type_id, checkin, checkout, rooms_needed=1) -> dict`**
  (HTL-012, `docs/qloapps/specs/HTL-012.md` §4 line 176). Returns
  `{"available": bool, "rooms_needed", "per_night": [...], "min_remaining": int}` where
  `available` is the AND-reduction across every night of `[checkin, checkout)`
  (`docs/qloapps/specs/HTL-012.md` §3.3).
- **`compute_stay_price(hotel_id, room_type_id, checkin, checkout, adults, children, rooms, advance_days=None) -> StayPriceResult`**
  (HTL-015, `docs/qloapps/specs/HTL-015.md` §4 line 142). Returns a `StayPriceResult` Pydantic
  model with `total_cents` (final, `(subtotal - los + advance) * rooms`, floored ≥ 0,
  `docs/qloapps/specs/HTL-015.md` §3 line 126) and `currency` (echo of the plan currency,
  `:127`). A room type with no rate plan still prices off `base_nightly_rate_cents` (the HTL-005
  field, `docs/qloapps/specs/HTL-005.md` §3.1, per `docs/qloapps/specs/HTL-017.md` §2 note). An
  LOS min/max-nights rejection raises `HTTPException(422, "stay too short/long")`
  (`docs/qloapps/specs/HTL-015.md` §5).

## 3. Data Model

### 3.1 Table: `hotel_reservations`

Single DynamoDB table. The PK/SK design follows the ORD `orders` header+child idiom
(`docs/ofbiz/specs/ORD-001.md` §3.2) and the LSE-001 §3.4 / ORD-001 §3.4 `TableDef` shape: a
`META` row holds the reservation header, and child `HIST#{ts:020d}#{event_id}` status-history
rows (added by HTL-019) co-locate on the same `reservation_id` partition, enabling a cheap
single-partition query for a reservation and its full history.

**Primary key**

| Key | Type | Value |
|---|---|---|
| `reservation_id` | S (PK) | `"res_" + uuid4().hex[:16]` (non-deterministic — see §2.4) |
| `sk` | S (SK) | `"META"` (reservation header row); HTL-019 adds `HIST#{ts:020d}#{event_id}` children |

**Header row attributes**

| Attribute | DDB Type | Constraints / Notes |
|---|---|---|
| `reservation_id` | S | PK; minted per call |
| `sk` | S | Always `"META"` for the reservation header |
| `hotel_id` | S | Owning hotel (opaque FK → HTL-001 hotel) |
| `guest_party_id` | S | Opaque FK → Contacts / OBP `CUS` / open-property `TEN` (the person; not re-modeled, §2.7) |
| `room_type_id` | S | Opaque FK → HTL-005 room type |
| `assigned_room_ids` | L | List of physical room ids (HTL-006 rooms); empty `[]` until check-in assigns them (HTL-019) |
| `checkin` | S | `"YYYY-MM-DD"` (inclusive — first night) |
| `checkout` | S | `"YYYY-MM-DD"` (exclusive — departure day, NOT a billable night) |
| `nights` | N | Count of dates in `[checkin, checkout)` (denormalized for display/reports); `_validate_span` result |
| `adults` | N | `ge=1` |
| `children` | N | `ge=0`, default 0 |
| `rooms` | N | `ge=1`, default 1 — number of rooms of this type held |
| `total_cents` | N | From `compute_stay_price(...).total_cents` (HTL-015) at create time |
| `deposit_cents` | N | Required-deposit amount in cents; default 0 (deposit *policy* + actual hold is HTL-033/Tier-3 — informational here) |
| `currency` | S | ISO 4217 lowercase; from the HTL-015 price result `currency`; default `"usd"` |
| `status` | S | Lifecycle status (HTL-019): `confirmed` \| `checked_in` \| `checked_out` \| `cancelled` \| `no_show`. Initial = `confirmed` |
| `hold_id` | S | The HTL-011 `hold_id` returned by `hold_rooms` (so HTL-019 cancel/no-show can `release_hold`) |
| `version` | N | Optimistic-concurrency counter; `1` at create, `+1` on each HTL-019 transition (ORD/KYC `version = :expected_version` CAS) |
| `created_at` | N | `now_ts()` (`app/core/time.py:2`) |
| `updated_at` | N | `now_ts()`; updated on every HTL-019 transition |

**GSIs**

| Index name | PK | SK | Purpose |
|---|---|---|---|
| `GSI_HOTEL_ARRIVALS` | `hotel_id` (S) | `checkin` (S, `YYYY-MM-DD`) | The arrivals board — a hotel's reservations by check-in date (front-desk console). String SK → **no** `attr_types` entry |
| `GSI_GUEST` | `guest_party_id` (S) | `created_at` (N) | A guest's booking history newest-first. Numeric SK → `attr_types={"created_at": "N"}` |
| `GSI_HOTEL_STATUS` | `hotel_id` (S) | `status` (S) | A hotel's reservations bucketed by lifecycle status (in-house / confirmed / departed). String SK → **no** `attr_types` entry |

All three GSIs project all attributes (`ALL`).

**`attr_types`**: `{"created_at": "N"}` — mandatory for the single numeric GSI sort key
(`GSI_GUEST` SK), per the CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha and the cross-cutting
constraint (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:57-61`): omitting it stores
`created_at` as String → `ValidationException` when `GSI_GUEST` is queried with an integer
`created_at` value. `GSI_HOTEL_ARRIVALS` (`checkin`) and `GSI_HOTEL_STATUS` (`status`) are
String SKs and need no `attr_types` entry.

**TableDef** (appended in `scripts/local-ddb-init.py` inside `_table_defs()`, after the last
existing entry, following the `TableDef` dataclass at `scripts/local-ddb-init.py:29-36` and the
LSE-001 §3.4 / ORD-001 §3.4 shape):

```python
TableDef(
    _resolve_table_name(S.hotel_reservations_table_name, "hotel_reservations"),
    "reservation_id",
    "sk",
    gsi=[
        {"index_name": "GSI_HOTEL_ARRIVALS", "partition_key": "hotel_id",       "sort_key": "checkin"},
        {"index_name": "GSI_GUEST",          "partition_key": "guest_party_id", "sort_key": "created_at"},
        {"index_name": "GSI_HOTEL_STATUS",   "partition_key": "hotel_id",       "sort_key": "status"},
    ],
    attr_types={"created_at": "N"},
),
```

## 4. API / Service Design

### 4.1 Service module: `app/services/hotel_reservations.py` (extended in place)

HTL-018 extends the file HTL-017 created. The flag/audit scaffolding (`_flag_on`,
`_require_enabled`, `_audit`), the `_validate_span` helper, and the module-level imports of the
forward-dep services are already present from HTL-017 (`docs/qloapps/specs/HTL-017.md` §4.1–4.2).
HTL-018 adds `create_reservation`, `get_reservation`, and a tiny `_reservation_out` row-coercion
helper. **No `if S.dev_mode` branch anywhere** — SECOPS-007 (§7.1).

### 4.2 `create_reservation`

```python
def create_reservation(
    *,
    hotel_id: str,
    guest_party_id: str,
    room_type_id: str,
    checkin: str,
    checkout: str,
    adults: int,
    children: int = 0,
    rooms: int = 1,
    deposit_cents: int = 0,
    user_sub: str,
) -> dict:
    """Create a confirmed reservation: re-check availability, compute price, hold
    inventory across the whole span, then write the META header (version=1)."""
```

**Flow** (per `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md` §HTL-018):

1. **`_require_enabled()`** — 404 when `hotel_pms_enabled` is off, before any DDB / service call.

2. **Validate the span** — `nights = _validate_span(checkin, checkout)` (HTL-017 helper, §2.5).
   Enforces `nights >= 1` (`checkout > checkin`) and well-formed `YYYY-MM-DD` strings; a
   malformed or zero/negative span raises `HTTPException(422)`. (Pydantic already enforces
   `adults >= 1`, `children >= 0`, `rooms >= 1`, `deposit_cents >= 0` at the model edge; the
   service trusts those bounds for direct callers but does no further bounds work.)

3. **Re-check availability at book time** —
   `check_availability(hotel_id, room_type_id, checkin, checkout, rooms_needed=rooms)`
   (HTL-012). A search result (HTL-017) can go stale between search and book, so the **binding**
   check lives here. If `not result["available"]` →
   `raise HTTPException(409, detail={"code": "no_availability"})`. This runs **before** any hold
   or write — no inventory is consumed and no header is written for a sold-out span.

4. **Compute price** —
   `price = compute_stay_price(hotel_id, room_type_id, checkin, checkout, adults, children, rooms)`
   (HTL-015). Read `total_cents = price.total_cents` and
   `currency = (price.currency or "usd").lower()`. An LOS min/max-nights violation raises
   `HTTPException(422, "stay too short/long")` from inside HTL-015 (propagated, not caught) —
   again before any hold or write. The price compute has no side effects, so propagating its 422
   leaves no orphan state.

5. **Atomically hold inventory across the span** —
   `hold = hold_rooms(hotel_id, room_type_id, checkin, checkout, quantity=rooms, user_sub=user_sub)`
   (HTL-011) → `hold_id = hold["hold_id"]`. `hold_rooms` is itself all-or-nothing across the span
   with compensating per-night rollback (`docs/qloapps/specs/HTL-011.md` §5): if a night sold out
   between the §3 check and here (a TOCTOU race), it rolls back the nights it touched and raises
   `HTTPException(409)`, which propagates — **no header row is written**, no inventory is left
   held. The hold MUST succeed before the header `put_item` so the room-nights are committed to
   this booking.

6. **Mint the header** — `reservation_id = "res_" + uuid4().hex[:16]`; `ts = now_ts()`; build the
   item dict:
   ```python
   item = {
       "reservation_id": reservation_id,
       "sk": "META",
       "hotel_id": hotel_id,
       "guest_party_id": guest_party_id,
       "room_type_id": room_type_id,
       "assigned_room_ids": [],
       "checkin": checkin,
       "checkout": checkout,
       "nights": nights,
       "adults": adults,
       "children": children,
       "rooms": rooms,
       "total_cents": total_cents,
       "deposit_cents": deposit_cents,
       "currency": currency,
       "status": "confirmed",
       "hold_id": hold_id,
       "version": 1,
       "created_at": ts,
       "updated_at": ts,
   }
   ```
   The three GSI partitions/sort keys are already present as plain attributes (`hotel_id`,
   `checkin`, `guest_party_id`, `created_at`, `status`) — no extra GSI key columns are needed.

7. **Write the header** — `T.hotel_reservations.put_item(Item=item)`. A bare `put_item` (no
   conditional) is correct: `reservation_id` is a fresh uuid (no collision possible), and the
   reservation is intentionally NOT idempotent on its arguments (§2.4, §7.2). If the `put_item`
   raises **after** the hold succeeded, best-effort compensate so the held rooms are not orphaned:
   ```python
   try:
       T.hotel_reservations.put_item(Item=item)
   except Exception:
       try:
           release_hold(hold_id, reason="reservation_write_failed",
                        user_sub=user_sub, terminal_status="released")
       except Exception:
           pass
       raise
   ```

8. **Append the initial history row** — best-effort append of the `None → confirmed`
   `HIST#{ts:020d}#{event_id}` event via the HTL-019 history helper (forward dep — a no-op stub
   until HTL-019 lands). Wrapped in `try/except`; a history-write failure never fails the create.

9. **Audit** —
   `_audit("hotel.reservation.created", user_sub, reservation_id=reservation_id,

## 5. Detailed Behavior & Edge Cases

### 5.1 Hold-before-write ordering (the core invariant)

`create_reservation` calls `hold_rooms` (HTL-011) **before** the header `put_item`. This is the
acceptance-critical ordering: the room-nights must be committed to this booking before the
reservation exists, so a confirmed reservation always has its inventory held (and a stored
`hold_id` HTL-019 can release). A 409 from `hold_rooms` (sold-out span / unseeded night) leaves
**no** reservation header written — the `put_item` is never reached.

### 5.2 Sold-out at book time — two distinct 409 sources

There are two places a booking can 409 on a sold-out span:
- **§4.2 step 3** — `check_availability` returns `available=false` (the fast, read-only
  pre-check). Raises `409 {"code": "no_availability"}` before any hold or write.
- **§4.2 step 5** — `hold_rooms` raises `409` because a night sold out in the window between the
  step-3 check and the step-5 hold (TOCTOU). `hold_rooms`'s own span rollback guarantees no
  partial hold survives (`docs/qloapps/specs/HTL-011.md` §5), so no compensation is needed and no
  header is written. The hold is the authoritative, atomic, single-writer check; the
  `check_availability` pre-check is an optimization that produces the friendlier
  `no_availability` error in the common case.

### 5.3 Non-idempotent creation

Calling `create_reservation` twice with identical arguments produces **two** reservations with
two distinct `reservation_id`s and **two** holds (two sets of room-nights consumed). This is
intentional (§2.4): a guest booking the same span twice is a legitimate act, and `hold_rooms`
itself is non-idempotent (`docs/qloapps/specs/HTL-011.md` §10). Callers needing dedupe must do it
client-side. There is no conditional put, no idempotency key, and no read-back-on-collision
(contrast PROP-001 / ORD's deterministic-id idempotent creation).

### 5.4 `assigned_room_ids` empty at create

`assigned_room_ids=[]` at create — a confirmed reservation holds *room-nights of a room type*,
not specific physical rooms. Physical room assignment happens at check-in (HTL-019). DynamoDB
stores `[]` as an empty `L`; it round-trips correctly. HTL-018 never writes a non-empty
`assigned_room_ids`.

### 5.5 `version=1` and the CAS contract

`version=1` at create. HTL-019 transitions (`confirmed → checked_in → checked_out`, plus
`cancelled` / `no_show`) use a version-gated conditional `update_item`
(`ConditionExpression="version = :expected_version"`, the KYC pattern at
`app/services/kyc_cases.py:228`, the ORD optimistic-concurrency pattern at
`docs/ofbiz/specs/ORD-005.md` §4.1.6), bumping `version` by 1 per successful transition. HTL-018
only sets the initial `1`; it does no transitions.

### 5.6 `total_cents` and `currency` provenance

`total_cents` is exactly `compute_stay_price(...).total_cents` (HTL-015) at create time — a
frozen snapshot. If rate plans change after booking, the reservation total does NOT re-price
(standard hotel behavior — the guest is quoted at booking). `currency` is the price result's
`currency` lowercased (ISO 4217), defaulting to `"usd"`. HTL-018 issues **no** payment — it only
records the computed total (and the informational `deposit_cents`); the actual charge/deposit
hold is HTL-033/Tier-3 (§7.4).

### 5.7 `deposit_cents` is informational

`deposit_cents` (default 0) is stored as-is from the caller — the deposit *policy* and the actual
deposit hold/charge are HTL-033/Tier-3, which must route through `refund_payment` /
`new_ledger_entry` (the cross-cutting "No money fork" constraint,
`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:80-82`). HTL-018 never multiplies, validates
against, or charges this field.

### 5.8 Write-failure compensation

If `put_item` fails after the hold succeeded (§4.2 step 7), HTL-018 best-effort calls
`release_hold(hold_id, ...)` to avoid orphaning the held room-nights, then re-raises. Both the
release and the re-raise are wrapped so a compensation failure never masks the original write
error. In the (rare) case the release also fails, the orphaned hold self-expires via HTL-011's
TTL sweep (`expires_at` + `start_hotel_hold_expiry_task`, `docs/qloapps/specs/HTL-011.md` §4) —
the hold is never permanently leaked.

### 5.9 Flag-off behavior

When `HOTEL_PMS_ENABLED=false` (default), both `create_reservation` and `get_reservation` raise
`HTTPException(404, "Hotel PMS is not enabled")` via `_require_enabled()` before touching
DynamoDB or any forward-dep service. The `hotel_reservations` table may or may not exist — the
flag check runs first.

### 5.10 Guest FK is opaque

`guest_party_id` is stored verbatim with **no** existence check against Contacts / CUS / TEN
(§2.7). A reservation may be created with a `guest_party_id` that does not (yet) resolve to a
person record. Booking history is served purely by the `GSI_GUEST` index. FK integrity is the
caller's responsibility (the QUO-004 / LSE-001 §5.6 opaque-string precedent).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_reservations.py` must contain **no** `if S.dev_mode` branch in the HTL-018
additions. The same DynamoDB code path runs in dev (boto3 intercepted by moto in-process) and
prod (real DynamoDB), per the cross-cutting parity constraint
(`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:76-79`) and the `app/services/inventory.py`
precedent (no `dev_mode` branch anywhere in that file). The forward-dep HTL-011/012/015 services
own any mock/real divergence internally — HTL-018 calls them identically in both envs. (Note:
HTL-011's hold uses the real KMS abstraction transparently; HTL-018 does no KMS work.)

### 7.2 Idempotency

`create_reservation` is **deliberately non-idempotent** (§2.4, §5.3): each call mints a fresh
`reservation_id` and a fresh hold. This is the correct semantics for a fresh booking and mirrors
the non-idempotent `hold_rooms` it composes (`docs/qloapps/specs/HTL-011.md` §10). `get_reservation`
is a pure read. There is no `delete_reservation` — cancellation is a status transition (HTL-019),
not a hard delete, preserving the audit trail and the released-hold record.

### 7.3 Security — auth split + ownership

The HTTP surface (Tier-3 router) follows the cross-cutting auth split
(`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:69-71`, identical to
`app/routers/inventory.py:48,65,81`): reads (`get_reservation`) →
`require_ui_session` (`app/services/sessions.py:330`); mutations (`create_reservation`) →
`require_admin_or_root_csrf` (`app/auth/policy.py:100`), which enforces `role ∈ {ADMIN, ROOT}`
plus cookie CSRF. HTL-018 ships only the service functions; the router is the Tier-3/HTL-019
deliverable. At the service layer there is no cross-hotel/cross-guest isolation check — the
admin/root caller is trusted (single-platform-operator assumption; multi-tenant isolation, if
needed, is a router-layer ownership check — see §10). The `user_sub` passed to
`create_reservation` is the acting admin's sub, threaded into the hold + audit for attribution,
not the guest.

### 7.4 Money-safety — no double-charge, no money fork

HTL-018 issues **no** Stripe/PayPal/CCBill call and writes **no** ledger entry — the cross-cutting
"No money fork" constraint (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:80-82`). It only
*records* the computed `total_cents` (a frozen quote snapshot) and the informational
`deposit_cents`; the actual charge/deposit hold and any refund is HTL-033/Tier-3, which must
route through `refund_payment` (`app/routers/billing.py:1287`) / `new_ledger_entry`. Because
HTL-018 never charges, there is no double-charge surface: a retried create produces a second
reservation + second hold (inventory, not money), and the §5.8 write-failure path releases the
hold (inventory), never reverses a payment. The price snapshot is integer cents end-to-end
(HTL-015 `total_cents` is `int`), so there is no float-rounding money bug.

### 7.5 Audit trail

`create_reservation` emits a best-effort `hotel.reservation.created` audit event via the
`_audit()` wrapper (§2.3), carrying `reservation_id`, `hotel_id`, `total_cents`, `hold_id`. Audit
failure is swallowed and never propagates. `hold_rooms` / `release_hold` emit their own
`hotel.hold.created` / `hotel.hold.released` events (`docs/qloapps/specs/HTL-011.md` §4), so the
inventory side of the booking is independently audited.

hotel_reservations.py additions, models) and (in prod) dropping the `hotel_reservations` table.
A partial rollback is also safe: keep the code deployed but ensure `HOTEL_PMS_ENABLED=false` —
all reservation entrypoints 404 and no data is read or written. Because HTL-018 issues no money
call, a rollback has no financial side effects; any holds created before rollback self-expire via
HTL-011's TTL sweep.

## 10. Open Questions / Assumptions

1. **Forward-dep module/import layout.** The exact import paths for `hold_rooms` / `release_hold`
   (HTL-011 → `app/services/hotel_availability`), `check_availability` (HTL-012 → same file), and
   `compute_stay_price` (HTL-015 → `app/services/hotel_rate_plans`) must reconcile when those
   tickets merge. **Assumption**: import them at module level on the `hotel_reservations`
   namespace (per HTL-017 §4.1 import note) and call by id; this spec names the functions, not the
   paths. The implementor finalizes the wiring at merge.

2. **`advance_days` passthrough to `compute_stay_price`.** HTL-015 accepts an optional
   `advance_days` (lead-time delta). HTL-018's `create_reservation` does not surface it.
   **Assumption**: omit `advance_days` (let HTL-015 default it) — last-minute/advance pricing
   driven from the reservation is an additive future extension. If the product needs it,
   `advance_days = (date.fromisoformat(checkin) - date.today()).days` is the natural derivation,
   added later without a model change to the persisted row.

3. **TOCTOU between `check_availability` and `hold_rooms`.** §5.2 documents that the §3 pre-check
   can pass and the §5 hold still 409 if a night sells out in between. **Assumption**: this is
   acceptable — `hold_rooms` is the authoritative atomic check and rolls itself back, so the
   pre-check is purely a UX optimization (friendlier `no_availability` in the common case). No
   locking/transaction across the two calls is attempted.

4. **History helper availability.** §4.2 step 8 appends the initial `None → confirmed` `HIST#`
   row via an HTL-019 helper. **Assumption**: until HTL-019 lands, this is a best-effort
   `try/except` no-op (the helper may not exist yet) — the create succeeds regardless. HTL-019
   owns the helper's real implementation and may backfill the initial event.

5. **Multi-room-type reservations.** A reservation holds `rooms` of a **single** `room_type_id`.
   **Assumption**: a guest booking two different room types makes two reservations (the QloApps
   one-room-type-per-reservation model). A multi-room-type "booking group" is an explicit future
   ticket, not HTL-018 scope.

6. **Cross-tenant isolation.** The service layer does no cross-hotel/cross-guest authorization.
   **Assumption**: single-platform-operator deployment; admin/root callers are trusted. A
   multi-tenant SaaS scenario needs a router-layer ownership check (caller's hotel scope vs
   `hotel_id`), added without changing the entity.
