# HTL-011 — Block/hold + overbooking + min/max availability controls

**Type**: Feature | **Priority**: P1 | **Estimate**: 2d
**Source**: `docs/qloapps/AVAILABILITY_INVENTORY_TICKETS.md` §HTL-011 + "Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §B

---

## 1. Summary & Goal

HTL-011 layers the **inventory-control verbs** on top of the per-date availability rows landed by HTL-010. It ships exactly four service capabilities plus their Pydantic I/O models, all on the **existing** `hotel_availability` table (no new table):

1. **`hold_rooms(hotel_id, room_type_id, checkin, checkout, quantity, *, user_sub, ttl_seconds=None)`** — an atomic, all-or-nothing block/hold across **every night** of a stay span. It reuses the OFBiz `inventory.reserve` conditional-decrement idiom (`app/services/inventory.py:362–372`) but applies it per-date (incrementing `held` on each `DATE#` row) and rolls back already-incremented nights on the first sold-out night.
2. **`release_hold(hold_id, *, reason, user_sub, terminal_status)`** — an idempotent terminal flip of the hold meta row (status-CAS guarded, `app/services/inventory.py:434–453`) that decrements `held` back on exactly the dates the hold touched.
3. **`expire_due_holds(*, now=None, limit=200)`** — a TTL sweep over a `GSI_HOLD_EXPIRY` index (a clone of `inventory.expire_due_reservations`, `app/services/inventory.py:538–562`) that auto-releases overdue holds. Driven by a 60 s background loop registered in `app/main.py`, gated on `hotel_pms_enabled`.
4. **`set_overbooking_allowance(...)`** and **`set_min_max_availability(...)`** — per-date setters for the `overbooking_allowance`, `min_availability`, and `max_availability` controls (the gap analysis "Overbooking controls + min/max availability per date" MISSING row, `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §B).

The hold lifecycle is the date-keyed analogue of the OFBiz soft-reservation pattern (`docs/ofbiz/specs/OFB-004.md`): a TTL-bearing reservation row whose terminal transition is a one-winner status-CAS. The distinctive net-new behavior versus OFBiz is **span atomicity**: a hold either succeeds on *all* nights or persists on *none* — because hotel availability across a stay is the intersection of every night's remaining count, not a single scalar (`docs/qloapps/AVAILABILITY_INVENTORY_TICKETS.md` lines 22–24).

Money-safety is **not applicable** (HTL-011 touches no billing/ledger/payment primitive), but **inventory-correctness** is the hard invariant: `held` must never be left partially incremented after a failed hold, never double-decremented on replayed releases, and never permit a hold that breaches the `min_availability` floor.

With `HOTEL_PMS_ENABLED=false` (the default), every entrypoint raises HTTP 404 before touching DynamoDB and the platform is byte-for-byte unchanged.

### 2.2 The OFBiz idioms reused verbatim

The conditional-decrement reserve idiom — `app/services/inventory.py:362–372`:

```python
resp = T.inventory.update_item(
    Key={"sku": sku, "location_sk": _location_sk(location_id)},
    UpdateExpression="SET reserved = reserved + :q, available = available - :q, updated_at = :now",
    ConditionExpression="available >= :q",
    ExpressionAttributeValues={":q": int(quantity), ":now": now_ts()},
    ReturnValues="ALL_NEW",
)
```

HTL-011 mirrors this single-writer update but (a) keys it on a `DATE#` row, (b) increments `held` (not `reserved`), and (c) makes the condition min-floor-aware: `total_rooms + overbooking_allowance - booked - held >= :q + min_availability`. There is no persisted `available` column on the date row to decrement — `available` is derived (`_available()`, the analogue of `inventory._record_out`'s `on_hand - reserved`, `app/services/inventory.py:101–115`), so the condition is written out in terms of the stored primitives.

The TTL soft-reservation row — `app/services/inventory.py:383–401`: a `META` row with `status="active"`, `created_at`, `expires_at = created_at + ttl`, and `gsi_expiry_pk = "SCHED#ACTIVE"` driving the expiry GSI.

The status-CAS terminal flip — `app/services/inventory.py:434–453` (`_close_reservation`): `ConditionExpression="#status = :active"` with `REMOVE gsi_expiry_pk`, returning `None` on `ConditionalCheckFailedException` (idempotent no-op replay).

The TTL sweep — `app/services/inventory.py:538–562` (`expire_due_reservations`): queries `GSI_EXPIRY` (`gsi_expiry_pk == "SCHED#ACTIVE" AND expires_at <= cutoff`) and calls the release path per overdue item.

### 2.3 The compensating-rollback precedent

OFBiz `inventory.reserve` decrements a **single** scalar row, so it needs no rollback — the conditional update is itself the atomic guard. A hotel hold touches **N date rows**, and DynamoDB has no cheap multi-item transaction here that also expresses a per-row conditional `>= :q + floor`. HTL-011 therefore makes the span atomic by **manual unwind**: increment night-by-night, and on the first `ConditionalCheckFailedException`, decrement back every night already incremented. This is the same shape as the legacy multi-row decrement rollback in `shoppingcart.py` noted in `docs/ofbiz/specs/OFB-004.md` §2.2.

### 2.4 The expiry-task registration precedent

`app/main.py` imports and registers ~30 background startup loops (e.g. line 224 `start_audit_export_worker_task`, line 225 `start_audit_export_scheduler_task`). The reservation-expiry analogue `start_reservation_expiry_task` is documented in `docs/ofbiz/specs/OFB-004.md` §4.2. HTL-011 adds `start_hotel_hold_expiry_task` to `app/main.py` in the same block, gated on `hotel_pms_enabled` (so flag-off = no loop spawned).

### 2.5 Auth split (reused from inventory router)

Per the cross-cutting constraint (`docs/qloapps/AVAILABILITY_INVENTORY_TICKETS.md` lines 61–64): reads → `require_ui_session` (`app/services/sessions.py:330`); mutations → `require_admin_or_root_csrf` (`app/auth/policy.py:100`). All HTL-011 verbs (`hold_rooms`, `release_hold`, `set_overbooking_allowance`, `set_min_max_availability`) are **mutations** → `require_admin_or_root_csrf`. The HTTP surface for these is wired in HTL-012's router (`app/routers/hotel_availability.py`); HTL-011 itself ships only the service functions and models. The inventory router's `_require_enabled` delegation idiom is at `app/routers/inventory.py:31–33`.

## 3. Data Model

HTL-011 adds **no new table**. It (a) writes the `held` / `overbooking_allowance` / `min_availability` / `max_availability` columns on the HTL-010 `DATE#` rows, and (b) co-locates a **hold meta row** on the same `hotel_availability` table under a distinct PK namespace, plus (c) one new GSI on the same `TableDef`.

### 3.1 Hold meta row (on the `hotel_availability` table)

The hold meta lives on its **own** partition (`HOLD#{hold_id}`) — mirroring `inventory._reservation_pk` (`app/services/inventory.py:63–64`) — so a hold's lifecycle row never collides with the `DATE#` availability rows on a room-type partition.

| Attribute | DDB Type | Notes |
|---|---|---|
| `availability_pk` | S (PK) | `"HOLD#{hold_id}"` where `hold_id = uuid4().hex` |
| `sk` | S (SK) | `"META"` |
| `hold_id` | S | Convenience copy of the uuid |
| `hotel_id` | S | The hotel of the held room type |
| `room_type_id` | S | The held room type |
| `checkin` | S | `YYYY-MM-DD` (inclusive first night) |
| `checkout` | S | `YYYY-MM-DD` (exclusive — guest does not occupy the departure night) |
| `dates` | L | List of `YYYY-MM-DD` nights this hold incremented (the authoritative undo list for `release_hold`, robust to later `total_rooms`/`checkout` shifts) |
| `quantity` | N | Rooms held per night |
| `status` | S | `active` \| `released` \| `expired` (terminal flip guarded by `status = active`) |
| `user_sub` | S | Holder |
| `created_at` | N | `now_ts()` (`app/core/time.py:2`) |
| `expires_at` | N | `created_at + ttl`; `GSI_HOLD_EXPIRY` sort key |
| `gsi_expiry_pk` | S | `"HOLD#ACTIVE"` while active; **REMOVE**d on terminal transition (sparse index — mirrors `app/services/inventory.py:399,443`) |
| `closed_at` | N | Stamped on terminal flip (mirrors `_close_reservation`) |
| `release_reason` | S | `"released"` / `"ttl_expired"` (audit convenience) |

### 3.2 Columns HTL-011 writes on the HTL-010 `DATE#` rows

These columns already exist on the HTL-010 schema (all default 0); HTL-011 is the owner that mutates them:

| Attribute | DDB Type | HTL-011 writer |
|---|---|---|
| `held` | N | `hold_rooms` (`+q` per night), `release_hold` / `expire_due_holds` (`-q` per night) |
| `overbooking_allowance` | N | `set_overbooking_allowance` (`SET = :a`) |
| `min_availability` | N | `set_min_max_availability` (`SET = :min`) |
| `max_availability` | N | `set_min_max_availability` (`SET = :max`) |
| `updated_at` | N | stamped `now_ts()` on every mutation |

`booked` is **not** written by HTL-011 — it is owned by the reservation cluster (HTL-018, forward ref). HTL-011 only reads it (transitively, inside `_available`).

### 3.3 New GSI on the `hotel_availability` `TableDef`

Add to the **same** `TableDef` HTL-010 declared in `scripts/local-ddb-init.py`:

- **`GSI_HOLD_EXPIRY`** — PK `gsi_expiry_pk` (S), SK `expires_at` (N). Drives the TTL sweep — exactly the `GSI_EXPIRY` pattern on the OFBiz reservations table (`docs/ofbiz/specs/OFB-004.md` §3.1, `app/services/inventory.py:547–552`). Sparse: only `active` holds carry `gsi_expiry_pk`, so the index holds only sweepable rows; `DATE#` rows and terminal holds are absent.

**`attr_types` update (mandatory).** The merged `TableDef` must declare `attr_types={"updated_at": "N", "expires_at": "N"}` — `expires_at` is a numeric GSI sort key, and omitting it stores the value as String → `ValidationException` at query time (CLAUDE.md "DynamoDB numeric GSI sort keys"; cross-cutting constraint lines 50–54).

The merged `TableDef` (HTL-010 + HTL-011, reconciled into one entry):

```python
TableDef(
    _resolve_table_name(S.hotel_availability_table_name, "hotel_availability"),
    "availability_pk",
    "sk",
    gsi=[
        {"index_name": "GSI_HOTEL_DATE",   "partition_key": "hotel_id",      "sort_key": "date"},
        {"index_name": "GSI_HOLD_EXPIRY",  "partition_key": "gsi_expiry_pk", "sort_key": "expires_at"},
    ],
    attr_types={"updated_at": "N", "expires_at": "N"},
),
```

> Like the PROP-001/PROP-002 reconciliation note, HTL-010 and HTL-011 both touch the same `TableDef`; their `local-ddb-init.py` changes must be merged into a single entry carrying both GSIs and both numeric `attr_types`.

## 4. API / Service Design

All functions are added to `app/services/hotel_availability.py`. Every entrypoint calls `_require_enabled()` first (404 when the flag is off). No `if S.dev_mode` branch anywhere (SECOPS-007).

### 4.1 Module-level helpers (added by HTL-011)

```python
_ACTIVE_HOLD_PARTITION = "HOLD#ACTIVE"

def _hold_pk(hold_id: str) -> str:
    return f"HOLD#{hold_id}"

def _hold_ttl(ttl_seconds: int | None) -> int:
    if ttl_seconds:
        return int(ttl_seconds)
    return int(getattr(S, "hotel_hold_ttl_seconds", 900))
```

`_availability_pk`, `_date_sk`, `_date_range`, `_available`, `_to_int`, `_audit`, `_flag_on`, `_require_enabled` are all reused from HTL-010 (do not re-define).

### 4.2 `hold_rooms`

```python
def hold_rooms(hotel_id, room_type_id, checkin, checkout, quantity, *, user_sub, ttl_seconds=None) -> dict:
```

1. `_require_enabled()`.
2. Validate `quantity >= 1` (→ 422) and `checkin < checkout` (→ 422). Compute `nights = _date_range(checkin, checkout_minus_one_day)` — the inclusive list of occupied nights `[checkin, checkout)`. Empty span (checkin == checkout) → 422.
3. `pk = _availability_pk(hotel_id, room_type_id)`. `incremented: list[str] = []`.
4. For each `night` in `nights`:
   ```python
   try:
       T.hotel_availability.update_item(
           Key={"availability_pk": pk, "sk": _date_sk(night)},
           UpdateExpression="SET held = held + :q, updated_at = :now",
           ConditionExpression=(
               "attribute_exists(availability_pk) AND "
               "total_rooms + overbooking_allowance - booked - held >= :q + min_availability"
           ),
           ExpressionAttributeValues={":q": int(quantity), ":now": now_ts()},
           ReturnValues="ALL_NEW",
       )
       incremented.append(night)
   except ClientError as exc:
       if exc.response["Error"].get("Code") == "ConditionalCheckFailedException":
           _rollback_holds(pk, incremented, quantity)   # compensating unwind
           raise HTTPException(status_code=409,
               detail=f"Room type sold out on {night}") from exc
       raise
   ```
   The condition also fails when the date row is absent (`attribute_exists(availability_pk)` false → a never-seeded date reads as sold-out, consistent with HTL-010's zeroed-virtual-row contract), so a hold over an unseeded night 409s and rolls back.
5. On full success, mint `hold_id = uuid4().hex`, write the `HOLD#{hold_id}` meta row (§3.1) with `status="active"`, `dates=nights`, `expires_at = created_at + _hold_ttl(ttl_seconds)`, `gsi_expiry_pk="HOLD#ACTIVE"`.
6. `_audit("hotel.hold.created", user_sub, hold_id=..., hotel_id=..., room_type_id=..., checkin=..., checkout=..., quantity=...)`.
7. Return `_hold_out(meta_item)`.

`_rollback_holds(pk, incremented, quantity)` issues an **unconditional** `SET held = held - :q` per already-incremented night (best-effort, but failures should be logged via `_audit("hotel.hold.rollback_error", ...)` — a stuck `held` is an inventory-correctness bug and must be visible).

### 4.3 `release_hold`

```python
def release_hold(hold_id, *, reason="released", user_sub="system", terminal_status="released") -> dict:
```

1. `_require_enabled()`.
2. Status-CAS terminal flip of the meta row (clone of `_close_reservation`, `app/services/inventory.py:434–453`):
   ```python
   UpdateExpression="SET #status = :new, closed_at = :now, release_reason = :r REMOVE gsi_expiry_pk"
   ConditionExpression="#status = :active"
   ```
   On `ConditionalCheckFailedException` → already terminal: re-read and return `_hold_out(existing)` (idempotent no-op). If the meta row is missing entirely → 404.
3. From the `ALL_OLD` attributes, read `dates`, `quantity`, `room_type_id`, `hotel_id`; `pk = _availability_pk(hotel_id, room_type_id)`. For each `date` in `dates`, unconditional `SET held = held - :q, updated_at = :now` (restoring availability).
4. `_audit("hotel.hold.released", user_sub, hold_id=..., reason=..., terminal_status=...)`.
5. Return `_hold_out(...)`.

### 4.4 `expire_due_holds`

```python
def expire_due_holds(*, now=None, limit=200) -> int:
```

A near-verbatim clone of `inventory.expire_due_reservations` (`app/services/inventory.py:538–562`): query `GSI_HOLD_EXPIRY` (`gsi_expiry_pk == "HOLD#ACTIVE" AND expires_at <= cutoff`, `Limit=limit`) and call `release_hold(hold_id, reason="ttl_expired", user_sub="system", terminal_status="expired")` per overdue hold (each in its own `try/except` so one bad hold doesn't abort the sweep). Returns the count expired. The status-CAS inside `release_hold` makes concurrent sweeps safe (one winner).

Background driver `start_hotel_hold_expiry_task()` (added to `app/services/hotel_availability.py`, registered in `app/main.py` next to the other `start_*_task` calls): a ~60 s loop gated on `getattr(S, "hotel_pms_enabled", False)` — when off, the loop is never spawned (parity with `start_reservation_expiry_task`, `docs/ofbiz/specs/OFB-004.md` §4.2).

### 4.5 `set_overbooking_allowance`

```python
def set_overbooking_allowance(hotel_id, room_type_id, start_date, end_date, allowance, *, user_sub) -> list[dict]:
```

`_require_enabled()`; for each `date` in `_date_range(start_date, end_date)` (inclusive — a control-range, not a stay span, so end is inclusive): `SET overbooking_allowance = :a, updated_at = :now`. If the date row does not exist yet, write a zeroed row first (read-merge, like `set_total_rooms`) so the control applies even to unseeded dates. One `_audit("hotel.overbooking.set", ...)` per range. Returns the updated rows (each via `_availability_out`, including derived `available`).

### 4.6 `set_min_max_availability`

```python
def set_min_max_availability(hotel_id, room_type_id, start_date, end_date, *, min_availability=None, max_availability=None, user_sub) -> list[dict]:
```

`_require_enabled()`; per date in `_date_range(start_date, end_date)`: build an `UpdateExpression` setting only the provided fields (`min_availability` and/or `max_availability`) plus `updated_at`. At least one of the two must be provided (else 422). Validate `min_availability <= max_availability` when both are set (else 422). One `_audit("hotel.minmax.set", ...)` per range. Returns the updated rows.

## 5. Detailed Behavior & Edge Cases

### 5.1 Span atomicity — partial-failure rollback (the core invariant)

A 3-night hold that succeeds on nights 1–2 but hits a sold-out night 3 must leave `held` **unchanged on all three nights**. The night-by-night loop tracks `incremented`; on the night-3 `ConditionalCheckFailedException`, `_rollback_holds` decrements nights 1 and 2 back, then the call raises 409. No `HOLD#` meta row is written (the meta is written only after the loop fully succeeds), so there is no orphan hold to reconcile. Acceptance: `held` on every night equals its pre-call value, and no `HOLD#` partition exists.

### 5.2 Overbooking math

The sell condition is `total_rooms + overbooking_allowance - booked - held >= quantity + min_availability`. With `total_rooms=2`, `booked=0`, `held=2`, `min_availability=0`, a 1-room hold fails (`2 - 2 = 0 < 1`). Set `overbooking_allowance=1` and the same hold succeeds (`2 + 1 - 2 = 1 >= 1`). Overbooking lets the operator deliberately sell beyond physical capacity — the gap analysis "Overbooking controls" MISSING row that the OFBiz hard `available >= qty` stop can never express.

### 5.3 Min-availability floor

`min_availability` is a **hold-back**: rooms reserved from the sellable pool (e.g. for walk-ins). With `total_rooms=5`, `booked=0`, `held=0`, `overbooking_allowance=0`, `min_availability=2`: a 3-room hold succeeds (`5 - 0 >= 3 + 2`), a 4-room hold fails (`5 < 4 + 2`). The floor is enforced **inside the conditional update**, so it is race-safe (no read-then-write window).

### 5.4 `max_availability` is a soft cap (advisory)

`max_availability` caps the *sellable* count for a date but is **not** enforced inside `hold_rooms`'s condition (a hold is constrained by physical+overbooking minus floor, which is the binding sell-stop). `max_availability` is surfaced on the calendar projection (HTL-012/013) for the operator to cap displayed/bookable rooms below physical capacity (e.g. holding inventory off-market). Enforcing it as a second hold condition is deferred — see §10.

### 5.5 Checkout-night exclusion

A 2026-07-04→2026-07-06 hold occupies nights **2026-07-04 and 2026-07-05** only (`[checkin, checkout)`); 2026-07-06 (departure) is not held. A hold whose checkout date is sold-out still succeeds. This matches HTL-010's `get_availability` span semantics (lines 176–180).

### 5.6 Idempotent double-release

`release_hold` on an already-`released`/`expired` hold is a no-op: the `status = active` CAS fails, the function re-reads and returns the existing hold without re-decrementing `held`. This is the inventory-correctness guarantee against double-restore (the analogue of `_close_reservation` returning `None`, `app/services/inventory.py:451–452`). A missing hold → 404.

### 5.7 TTL expiry restores `held`

`expire_due_holds(now=expires_at+1)` flips the overdue hold to `expired` and decrements `held` back on each stored `date`. Concurrent sweeps are safe — the status-CAS yields one winner, the loser's `release_hold` is the no-op of §5.6. A hold already manually released before its TTL is skipped (its `gsi_expiry_pk` was REMOVEd, so it is absent from the sweep query).

### 5.8 `dates` list is the authoritative undo set

`release_hold` decrements exactly the dates in the meta row's `dates` list — **not** a recomputed `[checkin, checkout)`. If an admin shifts `total_rooms` or a future change alters the span derivation, the release still targets the precise rows the hold incremented, preventing under- or over-restore.

### 5.9 Decimal coercion

`held`, `overbooking_allowance`, `min_availability`, `max_availability`, `quantity`, `created_at`, `expires_at` are DDB `N`, returned by boto3 as `Decimal`. Service functions coerce via `_to_int(...)` (reused from HTL-010) before returning; `HoldOut`/`AvailabilityDayOut` `int` fields coerce automatically.

### 5.10 Setting overbooking/min-max on unseeded dates

If a control-setter targets a date with no `DATE#` row yet, the setter writes a zeroed row carrying the control (read-merge, like `set_total_rooms`). The control then takes effect once `total_rooms` is seeded. This avoids a "set control before seeding inventory" ordering trap.

### 5.11 Flag-off behavior

When `HOTEL_PMS_ENABLED=false`, every HTL-011 function raises `HTTPException(404, "Hotel PMS is not enabled")` before any DDB access (delegating to the shared HTL-010 `_require_enabled()`). The `start_hotel_hold_expiry_task` loop is never spawned. The HTL-012 router handlers (which call `hold_rooms` etc.) 404 too.

### 5.12 Zero-night / inverted span

`checkin == checkout` (zero nights) → 422 (a hold must span at least one night). `checkin > checkout` → 422. These are validated before any DDB write.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_availability.py` (HTL-011 additions) contains **no** `if S.dev_mode` branch. The same `T.hotel_availability` handle and identical conditional `update_item` / GSI-query code run in dev (moto intercepts boto3 in-process) and prod (real DynamoDB). This mirrors `app/services/inventory.py:27–29` and the cross-cutting constraint (lines 65–67).

### 7.2 Idempotency

- **`hold_rooms`** is **not** idempotent on its arguments (each call mints a fresh `hold_id`); calling it twice creates two holds. This is intentional — a hold is a fresh act of inventory consumption. Callers that need idempotency must dedupe on `hold_id`.
- **`release_hold`** / **`expire_due_holds`** are fully idempotent via the `status = active` CAS — replays after the terminal flip are no-ops and never double-restore `held` (§5.6, §5.7).
- **`set_overbooking_allowance`** / **`set_min_max_availability`** are unconditional `SET` writes — re-running with the same payload produces the same final state.

### 7.3 Inventory-correctness (the hard invariant in lieu of money-safety)

HTL-011 touches **no** billing/ledger/payment primitive — `billing_shared` (`new_ledger_entry`, `apply_balance_delta`) is not imported. **Money-safety is therefore not applicable.** The equivalent hard invariant here is **inventory-correctness**, enforced by:
1. **No partial holds** — the night-by-night conditional increment + compensating rollback (§5.1) guarantees `held` is all-or-nothing across the span.
2. **No double-restore** — the status-CAS on `release_hold`/`expire_due_holds` guarantees `held` is decremented at most once per hold.
3. **No floor breach** — the `min_availability` floor is inside the conditional `update_item`, so it is race-safe (no read-modify-write window an oversell could slip through), exactly the one-winner guarantee `inventory.reserve` provides (`app/services/inventory.py:18–22` design note).

### 7.4 Security — auth & ownership

The HTL-012 router gates all HTL-011 mutations behind `require_admin_or_root_csrf` (`app/auth/policy.py:100`) — role `∈ {ADMIN, ROOT}` plus cookie-CSRF. The service layer does not itself enforce that the caller owns `hotel_id` (single-operator deployment assumption, consistent with PROP-001 §7.3). Multi-tenant hotel isolation (a `hotel_id`-scoped ownership check in the router) is deferred — see §10.

### 7.5 Audit trail

Every HTL-011 mutation emits a best-effort `_audit(...)` (the reused HTL-010 wrapper, itself copied from `app/services/inventory.py:92–98`): `hotel.hold.created`, `hotel.hold.released` (with `terminal_status` distinguishing manual release vs `expired`), `hotel.overbooking.set`, `hotel.minmax.set`, and `hotel.hold.rollback_error` on a rollback-decrement failure. Audit failure is swallowed and never propagates.

**Test cases**

1. **Flag-off 404** — set `hotel_pms_enabled=False`; assert `hold_rooms`, `release_hold`, `expire_due_holds`, `set_overbooking_allowance`, `set_min_max_availability` each raise `HTTPException(404)` before any DDB access.
2. **Conditional-decrement across span** — seed `total_rooms=5` over a 3-night span (via HTL-010 `set_total_rooms`); `hold_rooms(qty=2)`; assert `held=2` on all 3 date rows and a `HOLD#` meta row with `status="active"`, `dates=[3 nights]`, `expires_at=created_at+ttl`.
3. **Span rollback (the core invariant)** — seed nights 1–2 with `total_rooms=5`, night 3 with `total_rooms=1`; `hold_rooms(qty=2)` → assert `HTTPException(409)`; assert `held=0` on **all 3** nights (rollback) and **no** `HOLD#` partition exists.
4. **Unseeded-night rollback** — seed nights 1–2 only, leave night 3 unseeded; `hold_rooms` spanning all 3 → 409 (unseeded reads sold-out via `attribute_exists` condition); `held` unchanged on nights 1–2.
5. **Overbooking** — `total_rooms=2`, `held=2`; `hold_rooms(qty=1)` → 409; `set_overbooking_allowance(allowance=1)`; same hold now succeeds; `held` advances.
6. **Min-availability floor** — `total_rooms=5`, `min_availability=2`; `hold_rooms(qty=4)` → 409 (`5 < 4+2`); `hold_rooms(qty=3)` → succeeds (`5 >= 3+2`).
7. **release_hold restores held** — after a successful hold, `release_hold(hold_id)`; assert `held=0` on each stored date and meta `status="released"`, `gsi_expiry_pk` removed.
8. **Idempotent double-release** — `release_hold` twice; second call is a no-op (no further `held` decrement), returns `status="released"`.
9. **release_hold missing → 404** — `release_hold("does-not-exist")` raises `HTTPException(404)`.
10. **TTL expiry** — create a hold with a short ttl; `expire_due_holds(now=expires_at+1)` returns 1; assert meta `status="expired"` and `held` restored on each date; the hold is absent from a subsequent `GSI_HOLD_EXPIRY` query.
11. **Concurrent-sweep safety** — call `expire_due_holds(now=expires_at+1)` twice; second call returns 0 (status-CAS one-winner), `held` not double-restored.
12. **Checkout-night exclusion** — `hold_rooms(checkin=D, checkout=D+2)` increments exactly 2 nights (`D`, `D+1`); `D+2` row `held` unchanged.
13. **set_min_max_availability** — set `min=2`/`max=4` over a range; assert both persisted on each date row and `min<=max` validation (passing `min=5,max=4` raises 422).
14. **Decimal coercion** — after a hold, raw DDB `held`/`expires_at` are `Decimal`; service returns plain `int` in `HoldOut`.

## 10. Open Questions / Assumptions

1. **`max_availability` enforcement.** §5.4 treats `max_availability` as an advisory cap surfaced on the calendar, **not** enforced inside `hold_rooms`'s condition. An alternative makes it a second sell-stop: `... - held >= :q + min_availability` **AND** `held + booked + :q <= max_availability`. **Assumption**: advisory-only for HTL-011; enforcement is a non-breaking additive follow-up (the column and setter already exist).
2. **Hold idempotency key.** `hold_rooms` mints a fresh `hold_id` per call (not idempotent). A future caller (e.g. a booking flow that retries) may want an idempotency token to dedupe. **Assumption**: caller-side dedupe on `hold_id`; no server-side idempotency key in HTL-011.
3. **Hold vs booked interaction.** `held` and `booked` are independent counters; `_available` subtracts both. When the reservation cluster (HTL-018) converts a hold into a confirmed booking, it must atomically `held -= q` and `booked += q` (a "commit hold" verb, analogous to `inventory.commit_reservation`, `app/services/inventory.py:456–489`). **Assumption**: that commit verb is HTL-018's deliverable, not HTL-011's — HTL-011 ships only hold/release/expire.
4. **Multi-tenant `hotel_id` isolation.** The service does not check the caller owns `hotel_id`. **Assumption**: single-operator deployment (consistent with PROP-001 §10); a router-layer ownership check is a deferred additive change for multi-landlord SaaS.
5. **Rollback-failure handling.** `_rollback_holds` is best-effort; a network blip mid-rollback could leave `held` stuck. HTL-011 logs `hotel.hold.rollback_error` for visibility. **Assumption**: the TTL sweep is not a safety net here (no `HOLD#` row was written for a failed hold), so a stuck `held` requires the audit alert + manual `set_total_rooms` re-seed or a reconciliation tool (deferred). The probability is low (the rollback is unconditional `update_item`s on rows that exist), but it is the one non-atomic seam.
6. **Hold-expiry sweep interval.** Hardcoded ~60 s (parity with the OFBiz reservation loop). **Assumption**: not env-tunable for HTL-011; promote to a setting if operationally needed.
