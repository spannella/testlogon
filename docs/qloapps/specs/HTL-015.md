# HTL-015 — Multi-night price computation engine (`compute_stay_price` across a span)

**Type**: Feature | **Priority**: P1 | **Estimate**: 2d
**Source**: `docs/qloapps/RATE_PLANS_TICKETS.md` §HTL-015 + §"Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §B

---

## 1. Summary & Goal

HTL-015 lands the **deterministic multi-night / occupancy price computation engine** — the single net-new hotel pricing primitive the gap analysis flags as MISSING. It adds one pure function, `compute_stay_price(...)`, to `app/services/hotel_rate_plans.py` (the service file created in HTL-014), plus the result models it returns (`StayPriceResult`, `NightLineOut`). The function takes a room type, a check-in→check-out span, an occupancy (`adults`, `children`), a room count, and an optional lead time (`advance_days`), loads the room type's rate plan + rule rows (via HTL-014's `get_rate_plan` / `list_rules`), and produces an **itemized per-night breakdown plus a summed total**, applying rules in a fixed deterministic order.

The gap analysis records the exact gap this ticket fills: "**Booking-time availability check (dates+occupancy → available types + summed multi-night price)** — MISSING; nothing computes availability across a date range or sums per-night prices; the core net-new hotel primitive" (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:87`). HTL-015 owns the **price half** of that primitive (the summed multi-night price); the availability half is the sibling inventory cluster (HTL-009..HTL-013), and the consumer that joins the two is the **stay-search engine HTL-017** (a forward reference, out of scope here — see §11).

The goal is a **pure, deterministic, money-as-cents** computation: identical inputs + identical rule rows always yield byte-for-byte-identical output. No DDB writes, no randomness, no `now_ts()` inside the math except the `advance_days` default derivation (which the caller may pin for reproducible tests). With the master flag `HOTEL_PMS_ENABLED` off (the default), the function is a 404 no-op — the platform is byte-for-byte unchanged.

The single deliverable is `compute_stay_price` + its result models. The HTTP `/quote` endpoint that wraps it, the frontend price-preview, and the E2E tests are HTL-016's deliverables (referenced, not owned here).

## 2. Context & Current State

### 2.1 The gap — no per-night-of-stay or occupancy pricing exists

testlogon has two pricing layers today, and **neither** has a per-night-of-stay or guest-occupancy dimension (`docs/qloapps/RATE_PLANS_TICKETS.md:24-46`):

1. **Cart-quantity discount rules (OFB-019, spec only — not yet implemented).** The OFB-019 spec (`docs/ofbiz/specs/OFB-019.md`) defines `tiered` / `bulk` / `conditional` discount strategies keyed on **cart quantity** and **cart total**. `compute_discount(rule, cart_items, cart_total_cents, user_sub)` (`docs/ofbiz/specs/OFB-019.md:216-233`) discounts a *shopping-cart line-item sum*; there is no "night", "check-in", "occupancy", or "length-of-stay" concept anywhere in its config (`docs/ofbiz/specs/OFB-019.md:128-158`). **Note:** `app/services/pricing_rules.py` does **not** exist in the running codebase — OFB-019 is a design spec, not implemented (`find . -name pricing_rules.py` → none; only `app/services/api_pricing_catalog.py` exists). The contrast is therefore against the *design*, and against the one place cart totals are actually summed today (§2.2).

2. **Per-product date-windowed price components (PRD-012, spec).** `resolve_effective_price(item_id, as_of, price_type)` (`docs/ofbiz/specs/PRD-012.md:319-362`) queries a `ByItemPrice` GSI and returns **ONE effective price as-of a single instant** (`as_of`) — a SKU's current price, with a scalar fallback (`docs/ofbiz/specs/PRD-012.md:355-362`). It never iterates dates and never sums across a span.

A hotel needs nightly rates that vary by **season** (date-range override/delta), **occupancy** (extra-adult / extra-child surcharge above the room type's base occupancy), **length-of-stay** (min/max nights + stay discount), **advance / last-minute** (lead-time delta), and **weekend-vs-weekday** (day-of-week delta) — then **SUMMED across every night** of a check-in→check-out span (`docs/qloapps/RATE_PLANS_TICKETS.md:41-46`). That summation plus the occupancy dimension is the primitive that defeats both existing layers.

### 2.2 The naive cart-total sum we contrast against

The one place totals are summed in the live codebase today is `app/services/shoppingcart.py:301-303`:

```python
# app/services/shoppingcart.py:301-303
def cart_total_cents(user_sub: str, cart_id: str) -> int:
    items = list_items(user_sub, cart_id)
    return sum(item.get("line_total_cents", 0) for item in items)
```

This is a **flat sum of pre-computed per-line totals** (`line_total_cents = qty * unit`, `app/services/shoppingcart.py:87`). There is no per-date loop, no occupancy term, no whole-stay modifier, and no rule ordering. `compute_stay_price` is structurally different: it **constructs** each per-night line from a base rate by layering season/weekend/occupancy rules, **then** sums those lines, **then** applies whole-stay LOS + advance modifiers. The cart sum is the "after-the-fact addition" anti-pattern; HTL-015 is the "build each night then sum" pattern. Neither `cart_total_cents` nor the OFB-019 `compute_discount` is called by HTL-015.

### 2.3 Rule-ordering idea borrowed (not the code)

We reuse the **deterministic rule-evaluation-ordering idea** from the OFB-019 stacking algorithm — "Rules are evaluated in priority order (ascending integer)… ties broken by lowest `priority` integer" (`docs/ofbiz/specs/OFB-019.md:484-489`) — and the **negative-total guard idea** — "`apply_stacking` always caps `total_discount_cents <= cart_total_cents`. A cart can be discounted to 0 but never below" (`docs/ofbiz/specs/OFB-019.md:635-637`). We carry over the *ideas* (ascending-priority precedence, lowest-`priority` tiebreak, floor-at-zero), applied to **nights** rather than a cart, and the **money-as-cents** integer convention. The OFB-019 functions themselves are not called (they don't exist as code and operate on a cart, not a stay).

### 2.4 HTL-014 surface this engine consumes

HTL-015 depends entirely on HTL-014 (`docs/qloapps/RATE_PLANS_TICKETS.md:98-252`), which lands:

- The `hotel_rate_plans` DDB table (PK=`hotel_id#room_type_id`, SK=`META` header + SK=`RULE#{kind}#{rule_id}` child rows on one partition), `T.hotel_rate_plans` handle, `S.hotel_rate_plans_table_name`.
- The `HOTEL_PMS_ENABLED` master flag (`S.hotel_pms_enabled`) and the `_flag_on()` / `_require_enabled()` 404 contract copied from `app/services/inventory.py:50-56` (`_flag_on` at `:50`, `_require_enabled` at `:54`).
- `get_rate_plan(hotel_id, room_type_id) -> dict | None` — reads the SK=`META` header (holds `base_nightly_rate_cents`, `base_occupancy`, `currency`, `active`).
- `list_rules(hotel_id, room_type_id) -> list[dict]` — queries `begins_with(sk, "RULE#")`, sorted by (`priority`, `kind`, `rule_id`).
- The five rule kinds and their `rule_config` shapes (`docs/qloapps/RATE_PLANS_TICKETS.md:144-150`): `season`, `occupancy`, `los`, `advance`, `weekend`.

## 3. Data Model

HTL-015 **reads** the HTL-014 table; it writes nothing. It introduces only **result models** (no new DDB rows, no new table, no GSI).

### 3.1 Inputs (read from `hotel_rate_plans` table — HTL-014)

`compute_stay_price` reads exactly one partition (`hotel_id#room_type_id`):

**META header** (consumed fields):

| Attribute | DDB Type | Use |
|---|---|---|
| `base_nightly_rate_cents` | N | Starting per-night rate before any rule (`docs/qloapps/RATE_PLANS_TICKETS.md:131`) |
| `base_occupancy` | N | Adults included before extra-adult surcharge; default 2 (`:132`) |
| `currency` | S | ISO 4217, echoed into the result (`:133`) |

**RULE rows** (consumed by kind — `docs/qloapps/RATE_PLANS_TICKETS.md:144-150`):

| `kind` | `rule_config` fields read | Applied at |
|---|---|---|
| `season` | `start_date`, `end_date`, `mode` (`absolute`\|`delta`), `value_cents` | per-night step 1 |
| `weekend` | `dow` (list of ISO 1..7), `mode` (`absolute`\|`delta`), `value_cents` | per-night step 2 |
| `occupancy` | `extra_adult_cents`, `extra_child_cents` | per-night step 3 |
| `los` | `min_nights`, `max_nights` (int\|null), `discount_type` (`percentage`\|`fixed_cents`), `discount_value` | whole-stay step 5 |
| `advance` | `days_before_checkin`, `comparator` (`gte`\|`lte`), `mode` (`percentage`\|`fixed_cents`), `value` | whole-stay step 6 |

Each rule row also carries `priority` (N, default 500; lower = first) used for the season `absolute` tiebreak.

### 3.2 Result models (`app/models.py`)

Money fields are `int` cents. `season_delta_cents` / `weekend_delta_cents` / `advance_modifier_cents` are **signed** (negative = discount).

**`NightLineOut`** — one itemized night:

```python
class NightLineOut(BaseModel):
    date: str                    # "YYYY-MM-DD" — the night's calendar date (inclusive)
    base_cents: int              # base_nightly_rate_cents at the start of this night
    season_delta_cents: int      # signed; net effect of season rules on this night (absolute → final-base)
    weekend_delta_cents: int     # signed; net effect of weekend rules on this night
    occupancy_cents: int         # >= 0; extra-adult + extra-child surcharge for this night
    night_total_cents: int       # >= 0; floored final per-night charge (one room)
```

**`StayPriceResult`** — the full breakdown (returned as a Pydantic model so HTL-016's `/quote` endpoint serializes it directly):

```python
class StayPriceResult(BaseModel):
    nights: int                          # count of dates in [checkin, checkout)
    per_night: list[NightLineOut]        # len == nights; itemized
    stay_subtotal_cents: int             # sum(night_total_cents); ONE room, pre whole-stay mods
    los_discount_cents: int              # >= 0; LOS discount applied to the subtotal
    advance_modifier_cents: int          # signed; advance modifier (negative = discount)
    rooms: int                           # echo of input
    total_cents: int                     # final: (subtotal - los + advance) * rooms, floored >= 0
    currency: str                        # echo of plan currency
    applied_rule_ids: list[str]          # observability: every rule_id that affected the result
```

**Invariant** (acceptance, `docs/qloapps/RATE_PLANS_TICKETS.md:356-358`): `len(per_night) == nights` and `stay_subtotal_cents == sum(line.night_total_cents for line in per_night)`.

`StayPriceResult.model_rebuild()` is called after `NightLineOut` is defined if forward refs are used (standard `app/models.py` idiom).

## 4. API / Service Design

### 4.1 Function signature (`app/services/hotel_rate_plans.py`)

```python
def compute_stay_price(
    hotel_id: str,
    room_type_id: str,
    checkin: str,          # "YYYY-MM-DD" (inclusive — first night)
    checkout: str,         # "YYYY-MM-DD" (exclusive — departure day, NOT a billable night)
    adults: int,
    children: int,
    rooms: int = 1,
    advance_days: int | None = None,   # lead time; default = days between now_ts() and checkin
) -> StayPriceResult:
    """
    Deterministic per-night breakdown + summed total for one room type over a
    check-in→check-out span. Pure arithmetic; no DDB writes, no randomness.
    """
```

(Signature per `docs/qloapps/RATE_PLANS_TICKETS.md:274-288`.)

### 4.2 Algorithm

`_require_enabled()` is the **first line** (404 when `HOTEL_PMS_ENABLED` off, `app/services/inventory.py:54` idiom). Then:

**Step 0 — load once.**
- `plan = get_rate_plan(hotel_id, room_type_id)`; if `None` → `HTTPException(404, "rate plan not found")`.
- `rules = list_rules(hotel_id, room_type_id)`; bucket by `kind` into `season_rules`, `weekend_rules`, the single `occupancy_rule`, `los_rule`, `advance_rule`. (If multiple `occupancy`/`los`/`advance` rules exist, take the lowest-`priority` one deterministically — see §5.7.)
- `base = int(plan["base_nightly_rate_cents"])`, `base_occ = int(plan.get("base_occupancy", 2))`, `currency = plan.get("currency", "USD")`.

**Step 1 — enumerate nights.** Parse `checkin`/`checkout` as dates; the night list is every date `d` in `[checkin, checkout)` (checkout is the departure day, NOT a billable night — standard hotel convention; a 1-night stay is `checkin → checkin+1`, `docs/qloapps/RATE_PLANS_TICKETS.md:291-293`). `nights = len(night_dates)`.

**Per-night computation** (deterministic, fixed order — `docs/qloapps/RATE_PLANS_TICKETS.md:295-311`), for EACH night `d`, starting from `base`:

1. **season override.** If a `season` rule's `[start_date, end_date]` contains `d`: `absolute` mode **replaces** the night rate with `value_cents`; `delta` mode **adds** `value_cents` (may be negative). If multiple season rules match, the lowest-`priority` `absolute` wins (tiebreak by `rule_id`); all matching `delta` rules **sum**. `season_delta_cents` records the net effect vs `base` (for `absolute`, `final_after_season - base`).
2. **weekend delta.** If `d`'s ISO weekday (Mon=1..Sun=7) ∈ a `weekend` rule's `dow`: `absolute` **overrides** the post-season night rate; `delta` **adds** `value_cents`. `weekend_delta_cents` records the net effect.
3. **occupancy surcharge.** Add `occupancy_cents = max(0, adults - base_occ) * extra_adult_cents + children * extra_child_cents` (from the single `occupancy` rule, else 0).
4. **floor.** `night_total_cents = max(0, post-season + weekend-effect + occupancy)` — a delta can never drive a night negative.

Collect `NightLineOut(date=d, base_cents=base, season_delta_cents=…, weekend_delta_cents=…, occupancy_cents=…, night_total_cents=…)`. `stay_subtotal_cents = sum(night_total_cents)`.

**Whole-stay modifiers** (applied AFTER per-night summation, deterministic order — `docs/qloapps/RATE_PLANS_TICKETS.md:313-326`):

5. **LOS validation + discount.** If a `los` rule exists: reject when `nights < min_nights` → `HTTPException(422, "stay too short")`; reject when `max_nights is not None and nights > max_nights` → `HTTPException(422, "stay too long")`. Otherwise apply: `percentage` → `los_discount_cents = (stay_subtotal_cents * discount_value) // 100`; `fixed_cents` → `los_discount_cents = min(discount_value, stay_subtotal_cents)`. Subtract from subtotal.
6. **advance modifier.** If an `advance` rule's comparator on `advance_days` vs `days_before_checkin` holds (`gte` → `advance_days >= days_before_checkin`; `lte` → `advance_days <= days_before_checkin`), apply its modifier: `percentage` → `(post_los_subtotal * value) // 100`; `fixed_cents` → `value`. `advance_modifier_cents` is **signed** (advance-purchase = `gte` discount → negative; last-minute = `lte` surcharge → positive). Conventionally: a discount modifier stores a negative `advance_modifier_cents`; a surcharge stores positive.
7. **× rooms.** `total_cents = (stay_subtotal_cents - los_discount_cents + advance_modifier_cents) * rooms`.
8. **floor.** `total_cents = max(0, total_cents)` — never negative (`docs/ofbiz/specs/OFB-019.md:635-637` guard idea).

`applied_rule_ids` accumulates the `rule_id` of every rule that actually affected the result (season window hit, weekend dow hit, occupancy applied with surcharge > 0, los applied, advance comparator satisfied).

**Step 9 — return** `StayPriceResult(...)`.

### 4.3 `advance_days` default derivation

When `advance_days is None`, derive `advance_days = max(0, (checkin_date - date.fromtimestamp(now_ts())).days)` using `now_ts()` (`app/core/time.py:2`). This is the **only** non-deterministic input; the caller may pass an explicit `advance_days` to pin it for reproducible tests (`docs/qloapps/RATE_PLANS_TICKETS.md:342-345`). Negative lead times (checkin in the past) clamp to 0.

### 4.4 No new dependencies, no new env knobs

The function imports only what HTL-014 already provides plus `date`/`datetime` from the stdlib and `now_ts`. **No env-tunable weights** — every rate value lives in a DDB rule row, not in settings (contrast OFB-019's `NEWSFEED_RECSYS_WEIGHT_*`-style knobs, `docs/qloapps/RATE_PLANS_TICKETS.md:345`). The only config that gates the function is the HTL-014 master flag.

## 5. Detailed Behavior & Edge Cases

### 5.1 Checkout-day exclusion (night counting)

The night count is `len([checkin, checkout))` — checkout is the **departure day**, never a billable night. `2026-06-01 → 2026-06-04` = 3 nights (Jun 1, 2, 3). A 1-night stay is `2026-06-01 → 2026-06-02`. This is the universal hotel convention (`docs/qloapps/RATE_PLANS_TICKETS.md:291-293`) and the basis of acceptance criterion `len(per_night) == night count of [checkin, checkout)`.

### 5.2 Zero-night / inverted span

If `checkout <= checkin` (≤ 0 nights), the function raises `HTTPException(422, "checkout must be after checkin")` before any rule loop. A same-day in/out is not a valid stay. (Documented as a guard rather than returning an empty breakdown, to avoid a confusing `total_cents == 0`.)

### 5.3 Season `absolute` vs `delta` and multi-match

Multiple overlapping season rules can match one night. Deterministic resolution: the lowest-`priority` `absolute` rule wins the **base override** (tiebreak by `rule_id` ascending), then all matching `delta` rules are **summed** on top. If only `delta` rules match, they sum onto `base`. `season_delta_cents` on the line records the net `(post_season_rate - base)` so the breakdown reconciles (`base + season_delta = post-season rate`). This carries the OFB-019 ascending-priority + lowest-priority-tiebreak idea (`docs/ofbiz/specs/OFB-019.md:484-489`) onto nights.

### 5.4 Weekend after season

Weekend is computed on the **post-season** night rate (step 2 follows step 1). `absolute` weekend mode overrides the post-season value entirely; `delta` adds. ISO weekday is Mon=1..Sun=7 (Python `date.isoweekday()`). A typical Fri+Sat config is `dow=[5, 6]`. Weekday nights (`dow` miss) get `weekend_delta_cents = 0` and are unaffected (acceptance: "weekday nights do not", `docs/qloapps/RATE_PLANS_TICKETS.md:361-362`).

### 5.5 Occupancy surcharge math

`occupancy_cents = max(0, adults - base_occupancy) * extra_adult_cents + children * extra_child_cents`. When `adults <= base_occupancy` AND `children == 0`, the surcharge is exactly 0 and the occupancy rule contributes nothing (acceptance, `docs/qloapps/RATE_PLANS_TICKETS.md:363-364`). Every child is charged `extra_child_cents` (children are never "included" in `base_occupancy`, which counts adults only, per `docs/qloapps/RATE_PLANS_TICKETS.md:132`). The surcharge is per-night, added to every night identically.

### 5.6 LOS rejection precedence

LOS validation runs **before** the LOS discount and before the advance modifier. `nights < min_nights` → 422 "stay too short"; `max_nights is not None and nights > max_nights` → 422 "stay too long". A `null` `max_nights` means no upper bound. The rejection is raised even if the season/weekend/occupancy per-night loop has already run — the per-night work is wasted but the result is a clean 422 (the loop has no side effects, so this is safe and keeps the code linear). Acceptance: `nights < min_nights → 422 "too short"`, `nights > max_nights → 422 "too long"`, in-range gets the discount (`docs/qloapps/RATE_PLANS_TICKETS.md:365-366`).

### 5.7 Duplicate whole-stay rules

The model permits at most one each of `occupancy` / `los` / `advance` semantically, but the table does not enforce uniqueness. If multiple of the same whole-stay kind exist, `compute_stay_price` deterministically selects the **lowest-`priority`** one (tiebreak by `rule_id`) and ignores the rest. This is documented in §10 as an assumption; the HTL-014 service is expected to discourage duplicates but the engine must be robust to them.

### 5.8 Advance modifier sign convention

`advance_modifier_cents` is **signed**: a `gte` advance-purchase rule (`comparator="gte"`) is conventionally a discount and stores a **negative** value; an `lte` last-minute rule is conventionally a surcharge and stores a **positive** value. The magnitude is `(post_los_subtotal * value) // 100` (`percentage`) or `value` (`fixed_cents`). The sign is determined by the rule semantics, not hardcoded by comparator — a `gte` rule with a surcharge intent is permitted (the `value`/`mode` carry the intent). Step 7 adds the signed value: `subtotal - los + advance_modifier_cents`. Acceptance: "the modifier is signed in `advance_modifier_cents`" (`docs/qloapps/RATE_PLANS_TICKETS.md:367-368`).

### 5.9 Rooms multiplier and final floor

`total_cents = max(0, (stay_subtotal_cents - los_discount_cents + advance_modifier_cents) * rooms)`. The whole-stay modifiers are computed for **one** room, then the per-room total is multiplied by `rooms` (LOS/advance discounts scale linearly with room count — they are per-room, not per-booking). A discount larger than the subtotal yields `total_cents == 0`, never negative (`docs/qloapps/RATE_PLANS_TICKETS.md:369-371`, OFB-019 §7.4 guard idea `docs/ofbiz/specs/OFB-019.md:635-637`). `rooms` must be `>= 1` (a `rooms < 1` raises 422).

### 5.10 Rounding rules (explicit, deterministic)

All money is integer cents; no floats are ever stored. The only division operations are percentage discounts/modifiers, both using **floor division** (`//`) — `floor(subtotal * value / 100)` — which matches the spec's `floor(...)` wording (`docs/qloapps/RATE_PLANS_TICKETS.md:317-318`) and is deterministic across platforms. There is exactly one rounding point per percentage rule (LOS percentage, advance percentage); they are applied sequentially (LOS first on the subtotal, then advance on the post-LOS subtotal), so each rounds independently. No banker's rounding, no float intermediates. This guarantees byte-identical results regardless of host/locale.

### 5.11 No matching rate plan

If `get_rate_plan` returns `None` (no rate plan exists for the room type), the function raises `HTTPException(404, "rate plan not found")` — a quote for a room type with no rate plan is undefined. (HTL-016's `/quote` endpoint surfaces this as a 404 to the caller.)

### 5.12 Empty rule set

A rate plan with a `META` header but **zero** `RULE#` rows is valid: every night is just `base_nightly_rate_cents`, `stay_subtotal_cents = nights * base`, `total_cents = stay_subtotal * rooms`, all deltas 0, `applied_rule_ids == []`. This is the degenerate flat-rate case and must work.

### 5.13 Decimal coercion from DDB

`base_nightly_rate_cents`, `base_occupancy`, and every numeric `rule_config` value are returned by boto3 as `Decimal`. The engine coerces each to `int(...)` at read time before arithmetic so all math is pure integer (no `Decimal`/`int` mixing). Result model fields typed `int` coerce any residual `Decimal` automatically.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`compute_stay_price` contains **no** `if S.dev_mode` branch. It is **pure deterministic arithmetic** over rows read from `T.hotel_rate_plans` — the same `get_rate_plan` / `list_rules` code path runs in dev (boto3 intercepted by moto in-process) and prod (real DynamoDB). There is no randomness and no time-of-day non-determinism beyond the caller-supplied `checkin` / `checkout` / `advance_days` (`docs/qloapps/RATE_PLANS_TICKETS.md:85-89`). This mirrors `app/services/inventory.py`, which has no `dev_mode` branches anywhere.

### 7.2 Idempotency & determinism

The function is a **pure read** — no DDB writes, so it is trivially idempotent (calling it N times has no side effects). Stronger: it is **deterministic** — identical inputs (same dates / occupancy / `advance_days`) + identical rule rows always yield byte-for-byte-identical `StayPriceResult` (`docs/qloapps/RATE_PLANS_TICKETS.md:342-345,372`). The only non-deterministic input is the `advance_days` default derivation via `now_ts()`; a caller pins it by passing `advance_days` explicitly. Determinism is enforced by: fixed rule-application order (steps 1→8), ascending-`priority` + `rule_id` tiebreaks for any multi-match, integer-only arithmetic, and floor division (§5.10).

### 7.3 Security

`compute_stay_price` is a service-layer pure function; it performs no auth itself (the HTL-016 `/quote` router does — reads via `require_ui_session`, `docs/qloapps/RATE_PLANS_TICKETS.md:81-84`). It reads only the `(hotel_id, room_type_id)` partition it is given; it cannot leak cross-tenant data because it never queries a GSI or scans. No PII is read or returned. The flag check (`_require_enabled()`) runs first, so a flag-off caller cannot probe table existence.

### 7.4 Money-safety

Every amount is **integer cents** end-to-end (OFB-019 / PRD-012 convention, `docs/qloapps/RATE_PLANS_TICKETS.md:79-80`). No floats are ever introduced — percentage discounts use floor division (`//`) on integer cents (§5.10). Three money-safety invariants hold by construction:

1. **Per-night floor.** Every `night_total_cents = max(0, ...)` — a delta can never drive a night negative (step 4).
2. **Subtotal identity.** `stay_subtotal_cents == sum(night_total_cents)` exactly (no rounding between nights — nights are already integers).
3. **Final floor.** `total_cents = max(0, ...)` — a stay discount larger than the subtotal yields 0, never negative (step 8, OFB-019 §7.4 guard `docs/ofbiz/specs/OFB-019.md:635-637`).

The function touches **no** billing table, ledger entry, or payment primitive — it computes a quote, not a charge. `billing_shared` is not imported. The quote becomes a charge only downstream (HTL-017 stay-search → reservation → billing), out of scope here.

### 7.5 Observability

`applied_rule_ids` lists every `rule_id` that affected the result — a debugging/audit aid that lets a caller (or HTL-016's quote endpoint) explain a price without re-deriving it. No audit event is emitted (the function is a pure read; audit is for mutations only).

Adding a new rule `kind` later is a non-breaking change to HTL-014's table + this engine's per-night/whole-stay loop.

## 10. Open Questions / Assumptions

1. **Whole-stay rule duplication.** The model permits at most one `occupancy` / `los` / `advance` rule semantically, but the table doesn't enforce uniqueness. **Assumption**: if duplicates exist, the engine deterministically picks the lowest-`priority` one (tiebreak by `rule_id`) and ignores the rest (§5.7). HTL-014's CRUD is expected to discourage duplicates; the engine is robust either way.

2. **Advance modifier sign.** **Assumption**: the sign of `advance_modifier_cents` follows the rule's intent (`gte` advance-purchase → discount → negative; `lte` last-minute → surcharge → positive), but the engine derives the sign from the rule's `value`/`mode`, not hardcoded by comparator, so a `gte` surcharge is representable (§5.8). If the product wants comparator to dictate sign rigidly, the validator (HTL-014) should enforce it.

3. **LOS/advance scale with rooms.** **Assumption**: whole-stay discounts are **per-room** and scale linearly (subtotal − los + advance is computed for one room, then × rooms, §5.9). If a discount should be a flat per-booking amount (not per-room), the formula would change to `(subtotal × rooms) − los_booking + advance_booking`. The spec's "Multiply the post-modifier per-room total by `rooms`" (`docs/qloapps/RATE_PLANS_TICKETS.md:322`) supports per-room; documented here for confirmation.

4. **Rounding direction.** **Assumption**: floor division (`//`) for all percentages, matching the spec's `floor(...)` (`docs/qloapps/RATE_PLANS_TICKETS.md:317-318`). If finance requires round-half-up or per-night rounding instead of per-stay, this is a localized change to §5.10's two division points.

5. **Season `season_delta_cents` representation for `absolute`.** **Assumption**: for an `absolute` season night, `season_delta_cents = (override_value - base)` so that `base + season_delta == post-season rate` and the breakdown reconciles. An alternative is to leave `season_delta_cents == 0` and let `base_cents` carry the override; the chosen representation keeps `base_cents` constant across nights for clarity.

6. **Zero-night guard vs empty result.** **Assumption**: `checkout <= checkin` raises 422 (§5.2) rather than returning a zero-night `StayPriceResult`. A caller (HTL-017) is expected to validate the span before quoting, but the engine guards defensively.

7. **Currency uniformity.** **Assumption**: all rule values are in the plan's `currency`; the engine does no FX conversion. Mixed-currency rules are not supported (and HTL-014's model has no per-rule currency).
