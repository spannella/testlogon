## 1. Summary & Goal

HTL-021 is the final ticket in the Tier-2 booking/reservations cluster. It delivers the React/TypeScript frontend for the stay-search + reservation vertical and the full test suite (hermetic pytest + Playwright E2E) that validates the entire HTL-017..HTL-020 stack end-to-end.

The gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C) records the presentational rows as **MISSING / PARTIAL**:
- "Booking-engine storefront (public date+occupancy search → results+price → cart → checkout)" — **PARTIAL** (`QLOAPPS_GAP_ANALYSIS.md:95`): there is no date+occupancy room-type search funnel UI.
- "Reservation lifecycle (search→cart→book→confirmed→checked-in→checked-out→cancel/no-show; modify)" — **PARTIAL** (`:93`): the check-in/out/no-show + room-assignment + modify actions have no UI.
- "Front desk (arrivals/departures/in-house, walk-in, assign room, check-in/out, room-move)" — **MISSING** (`:94`): the reservations list + detail action bar is the first slice of this surface.

HTL-021 closes the presentational gap for the search → book → lifecycle slice. It does **not** ship the full front-desk console (arrivals board, walk-in, room-move), guest folios, deposits, or the public unauthenticated booking storefront — those are later cluster deliverables (gap analysis §C/§D, Tier-3).

**Deliverables:**

1. **TypeScript types** mirroring the `app/models.py` HTL-017/018/019 models (`frontend/src/api/types.ts`).
2. **API endpoint wrappers** calling the HTL-020 router via `frontend/src/api/client.ts` (`frontend/src/api/endpoints/hotelReservations.ts`).
3. **Three page components** under `frontend/src/pages/hotels/`:
   - `StaySearchPage.tsx` — a search form (hotel or city, check-in/check-out date pickers, adults/children/rooms steppers) → an available-room-type results list with per-night breakdown + total; "Book" → confirm dialog → `createReservation`.
   - `ReservationsPage.tsx` — a hotel's reservations list, filterable by status / arrival-date window, each row linking to detail.
   - `ReservationDetailPage.tsx` — header (hotel, guest, room type, span, occupancy, total, status badge), a lifecycle action bar with state-gated buttons (Check-in opens a room-assignment picker; Check-out; Cancel; No-show; Modify), a status-history timeline, and a Modify dialog (re-date / re-occupancy → re-priced quote preview before submit).
4. **Route registrations** in `frontend/src/App.tsx`.
5. **Sidebar nav item** in `frontend/src/components/layout/Sidebar.tsx`.
6. **Hermetic pytest** `tests/test_htl_reservations.py` covering HTL-017..HTL-020 (search, create+hold, each transition, version-conflict, cancel-releases-inventory, modify re-price, flag-off 404).
7. **E2E spec** `frontend/e2e/hotel-reservations.spec.ts` (cookie-auth admin: stay search → book → check-in → check-out lifecycle with room assignment → cancel another reservation; results list, status badge, history timeline, button enable/disable assertions).

With `HOTEL_PMS_ENABLED=false` (the default) all three pages are reachable via the browser (routes are registered unconditionally) but every API call returns 404 — the backend is a flag-gated no-op per HTL-018/019/020's `_require_enabled()` (copied from `app/services/inventory.py:54-56`). The sidebar nav item is always visible; the flag-off error state renders a user-facing "Hotel booking is not enabled" callout instead of broken data. This matches the Inventory vertical and the open-property PROP-005 precedent (`docs/open-property/specs/PROP-005.md` §1).

### 4.1 API endpoint wrappers (`frontend/src/api/endpoints/hotelReservations.ts`)

New file. Uses `api.get/post/put/del` from `frontend/src/api/client.ts:290-313`. No axios, no custom fetch. Paths mirror the HTL-020 router table (`STAY_SEARCH_RESERVATIONS_TICKETS.md:507-519`).

```typescript
import { api } from "@/api/client";
import type {
  StaySearchIn, StaySearchResult,
  Reservation, ReservationCreateIn, ReservationModifyIn,
  ReservationTransitionIn, ReservationListOut, ReservationHistoryOut,
} from "@/api/types";

// Stay search (POST-with-body, session-read auth — the search funnel, HTL-020 row 1)
export const searchStays = (body: StaySearchIn) =>
  api.post<StaySearchResult>("/ui/hotel-search", body);

// Reservations CRUD
export const createReservation = (hotelId: string, body: ReservationCreateIn) =>
  api.post<Reservation>(`/ui/hotels/${hotelId}/reservations`, body);

export const listReservations = (
  hotelId: string,
  params?: { status?: string; checkin_from?: string; checkin_to?: string; cursor?: string; limit?: number },
) =>
  api.get<ReservationListOut>(`/ui/hotels/${hotelId}/reservations`, params
    ? Object.fromEntries(
        Object.entries(params).filter(([, v]) => v !== undefined).map(([k, v]) => [k, String(v)]),
      )
    : undefined,
  );

export const getReservation = (hotelId: string, reservationId: string) =>
  api.get<Reservation>(`/ui/hotels/${hotelId}/reservations/${reservationId}`);

export const getReservationHistory = (hotelId: string, reservationId: string) =>
  api.get<ReservationHistoryOut>(`/ui/hotels/${hotelId}/reservations/${reservationId}/history`);

export const modifyReservation = (hotelId: string, reservationId: string, body: ReservationModifyIn) =>
  api.put<Reservation>(`/ui/hotels/${hotelId}/reservations/${reservationId}`, body);

// Lifecycle (literal sub-routes — declared before /{reservation_id} server-side, HTL-020 :521-527)
export const confirmReservation = (hotelId: string, reservationId: string) =>
  api.post<Reservation>(`/ui/hotels/${hotelId}/reservations/${reservationId}/confirm`);

export const checkInReservation = (hotelId: string, reservationId: string, body: ReservationTransitionIn) =>
  api.post<Reservation>(`/ui/hotels/${hotelId}/reservations/${reservationId}/check-in`, body);

export const checkOutReservation = (hotelId: string, reservationId: string, body?: ReservationTransitionIn) =>
  api.post<Reservation>(`/ui/hotels/${hotelId}/reservations/${reservationId}/check-out`, body ?? {});

export const cancelReservation = (hotelId: string, reservationId: string, body?: ReservationTransitionIn) =>
  api.post<Reservation>(`/ui/hotels/${hotelId}/reservations/${reservationId}/cancel`, body ?? {});

export const noShowReservation = (hotelId: string, reservationId: string, body?: ReservationTransitionIn) =>
  api.post<Reservation>(`/ui/hotels/${hotelId}/reservations/${reservationId}/no-show`, body ?? {});
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `StaySearchPage.tsx` — search form + results

**Search form** (top of page, always rendered): a React Hook Form + Zod form:
```typescript
const searchSchema = z.object({
  hotelOrCity: z.enum(["hotel", "city"]),
  hotel_id: z.string().optional(),
  city: z.string().optional(),
  checkin: z.string().min(1, "Check-in required"),    // <input type="date">
  checkout: z.string().min(1, "Check-out required"),
  adults: z.coerce.number().int().min(1),
  children: z.coerce.number().int().min(0).default(0),
  rooms: z.coerce.number().int().min(1).default(1),
}).refine(d => d.checkout > d.checkin, { message: "Check-out must be after check-in", path: ["checkout"] })
  .refine(d => (d.hotelOrCity === "hotel" ? !!d.hotel_id : !!d.city),
          { message: "Hotel or city is required", path: ["hotel_id"] });
```
A radio/toggle switches between "By hotel" (a `hotel_id` input/select) and "By city" (a free-text `city` input). Date pickers are native `<input type="date">` (the project does not bundle a heavy date-range widget; `YYYY-MM-DD` strings match the backend convention `STAY_SEARCH_RESERVATIONS_TICKETS.md:114-116`). Adults/children/rooms are numeric steppers (`Input type="number"` with +/- buttons or plain numeric input). The frontend mirrors the backend's `checkout > checkin` ≥1-night rule (`:125-127`) and `adults>=1` so the user gets inline validation before the 422 round-trip; the backend remains authoritative.

**Submit → search.** Submitting calls `useMutation({ mutationFn: searchStays })` (a mutation rather than a `useQuery`, since the search is user-triggered with a body; the result is held in component state / the mutation's `data`). Alternatively `useQuery({ queryKey: ["hotelReservations","search",body], enabled: hasSearched })`. On a 422 (`checkout must be after checkin`, or both `hotel_id`+`city` absent — `STAY_SEARCH_RESERVATIONS_TICKETS.md:134`), render the error detail inline. On a 404 (flag off), render the "Hotel booking is not enabled" callout.

**Results list.** `StaySearchResult.results` is already sorted cheapest-first server-side (`:148-150`); the frontend renders it in order without re-sorting. Each `StayRoomTypeResult` is a shadcn/ui `<Card>`:
- **Header**: `name` (`CardTitle`) + `min_remaining` rooms-left badge (e.g. `<Badge variant="outline">3 left</Badge>`).
- **Body**: a per-night breakdown table from `per_night` (each row: date → `formatCents(amount_cents)`); the summed `total_cents` rendered prominently via `formatCents(total_cents, currency.toUpperCase())`; nights count.
- **Footer**: a "Book" `<Button>` that opens a confirm dialog.

**Empty results.** `result_count === 0` → an empty-state card: "No available room types for these dates. Try different dates or occupancy."

**"Book" confirm dialog.** Opens a `<Dialog>` summarizing the room type, span, occupancy, and `total_cents`. The dialog requires a `guest_party_id` (an opaque person FK — Contacts/CUS/TEN per the cross-cutting constraint, `STAY_SEARCH_RESERVATIONS_TICKETS.md:72-75`); for MVP this is a free-text/contact-picker input, NOT re-modeled here. On confirm, `useMutation({ mutationFn: () => createReservation(hotel_id, { hotel_id, guest_party_id, room_type_id, checkin, checkout, adults, children, rooms }) })`. On 409 `no_availability` (a search result went stale between search and book — the binding re-check is server-side, `:278-281`), show `toast.error("Those rooms were just booked — please search again")` and re-run the search. On success, `toast.success("Reservation confirmed")` and navigate to `/hotels/${hotel_id}/reservations/${reservation_id}`.

### 5.2 `ReservationsPage.tsx` — a hotel's reservations list

Uses `useParams<{ hotelId: string }>()`. Calls `listReservations(hotelId, { status, checkin_from, checkin_to })` via `useQuery`. Filters:
- **Status filter** (shadcn/ui `<Select>`): `confirmed` / `checked_in` / `checked_out` / `cancelled` / `no_show` / `all`. Drives the `status` param (server-side `GSI_HOTEL_STATUS`, `STAY_SEARCH_RESERVATIONS_TICKETS.md:232-233`).
- **Arrival-date window** (two `<input type="date">`): `checkin_from` / `checkin_to` (server-side `GSI_HOTEL_ARRIVALS`, `:227-229`).

Renders a `<table>` (or stacked `<Card>` rows): reservation_id (short), guest_party_id, room_type_id, span (`checkin → checkout`, `nights`), occupancy (`adults`+`children`, `rooms`), `formatCents(total_cents, currency)`, a status `<Badge>` (colors per §5.5), and a "View" link to `/hotels/${hotelId}/reservations/${reservation_id}`.

**Pagination.** `listReservations` is cursor-based (`ReservationListOut.cursor`). MVP fetches one page (`limit=50`); if `cursor` is non-null, a "Load more" button issues a follow-up query with the next cursor (the PROP-005 §5.7 "Load more over infinite-scroll" precedent). **Empty state**: "No reservations match these filters."

### 5.3 `ReservationDetailPage.tsx` — header + lifecycle action bar + history timeline

Uses `useParams<{ hotelId: string; reservationId: string }>()`.

**Header.** `getReservation(hotelId, reservationId)` via `useQuery`. Renders hotel_id, guest_party_id, room_type_id, span (`checkin → checkout`, `nights` nights), occupancy (`adults` adults / `children` children / `rooms` rooms), `assigned_room_ids` (when non-empty), `formatCents(total_cents, currency.toUpperCase())`, and a status `<Badge>` (§5.5). A 404 (missing OR wrong hotel OR flag off, `:512`) renders a centered error card: "Reservation not found or hotel booking is not enabled." with a "Back to reservations" link.

**Lifecycle action bar** — buttons gated by the HTL-019 state machine (`_RESERVATION_TRANSITIONS`, `STAY_SEARCH_RESERVATIONS_TICKETS.md:354-360`). The frontend mirrors the allowlist exactly so only legal next actions are enabled; the backend remains authoritative (409 on an illegal edge):

| `status` | Enabled actions |
|---|---|
| `confirmed` | Check-in, Cancel, No-show, Modify |
| `checked_in` | Check-out |
| `checked_out` | (none — terminal) |
| `cancelled` | (none — terminal) |
| `no_show` | (none — terminal) |

A terminal reservation shows **no** action buttons (just the status badge + history). All mutation buttons are additionally hidden for non-admin sessions (`getRoleFromAccessToken`, §2.11) — the HTL-020 mutation endpoints are `require_admin_or_root_csrf` and would 403 a USER session.

- **Check-in** opens a **room-assignment picker** dialog. `assigned_room_ids` is **required** and its length must equal `reservation.rooms` (the HTL-019 `→ checked_in` rule, `:389-392`; a mismatch 422s server-side). For MVP the picker is `reservation.rooms` text/select inputs for room ids (the physical-rooms lister is HTL-006, forward-dep — the picker may accept free-text ids in MVP). On submit: `checkInReservation(hotelId, reservationId, { assigned_room_ids })`. A 422 (`assigned_room_ids required` / wrong length) surfaces inline.
- **Check-out** → `checkOutReservation(hotelId, reservationId)` (no body required). Best-effort backend releases physical rooms to housekeeping; the hold is NOT released on checkout (`:394-397`).
- **Cancel** → confirm dialog → `cancelReservation(...)`. Backend releases held inventory (`release_hold`, `:398-405`) and writes **no** ledger entry / issues **no** refund (HTL-033 owns money, cross-cutting "no money fork" `:80-83`). The dialog copy MUST NOT promise a refund: "Cancel this reservation? Held rooms are released back to inventory. (Refunds/penalties are handled separately.)"
- **No-show** → confirm dialog → `noShowReservation(...)`. Same inventory-release / no-money semantics as cancel.
- **Modify** → opens the Modify dialog (§5.4).

**Concurrent-update (version conflict).** Every transition is a version-gated CAS server-side (`version = :expected_version`, `:406-411`). A loser receives 409 `concurrent_update`. The frontend shows `toast.error("This reservation was just updated — refreshing")` and invalidates `["hotelReservations", hotelId, reservationId]` to re-fetch the current state (and re-derive the enabled buttons). The frontend does not surface `version` as an editable field.

**Status-history timeline.** `getReservationHistory(hotelId, reservationId)` via `useQuery`; the backend returns events newest-first (`:417`). Render a vertical timeline: each `ReservationHistoryEntry` shows `from_status → to_status`, `actor`, `reason` (when present), and a formatted `ts`. The initial `None → confirmed` event has `from_status: null` (render as "Created → confirmed").

### 5.4 Modify dialog — re-date / re-occupancy → re-priced quote preview

The Modify dialog is enabled only for `status === "confirmed"` (the HTL-019 rule: a non-`confirmed` reservation 409s, `:437-439`). It is a partial form (all fields default to the current reservation values): `checkin`, `checkout`, `room_type_id`, `adults`, `children`, `rooms`.

**Quote preview before submit.** Because `modify_reservation` re-checks availability + re-prices the new span (`:441-445`), the dialog SHOULD show the new price before committing. MVP approach: call `searchStays({ hotel_id, room_type_id?, checkin, checkout, adults, children, rooms })` (read-only, no hold) to preview the new `total_cents` and per-night breakdown for the proposed span, rendered as a "New total: …" line next to the current total. (This preview is best-effort UX; the authoritative re-price happens in `modify_reservation`.) On submit, `modifyReservation(hotelId, reservationId, partial)`. A 409 (`only confirmed reservations may be modified`, or new-hold `no_availability`) surfaces as a toast; the backend never leaves the reservation un-held (new-hold-before-old-release, `:443-444`).

### 5.5 Status badge colors

`"confirmed"` → blue/primary (`<Badge>`); `"checked_in"` → green (`<Badge className="bg-green-100 text-green-800">`); `"checked_out"` → gray (`<Badge variant="secondary">`); `"cancelled"` → red (`<Badge variant="destructive">`); `"no_show"` → amber/orange (`<Badge className="bg-amber-100 text-amber-800">`). A single local `statusBadge(status)` helper returns the variant/className; used identically in `ReservationsPage` rows and the `ReservationDetailPage` header.

### 5.6 Money display

All money is integer cents (`total_cents`, `deposit_cents`, `per_night[].amount_cents`). Displayed via the local `formatCents` helper (§2.10), upper-casing the lowercase ISO `currency`. The frontend never sums or recomputes prices — the backend (`compute_stay_price`, HTL-015) is the sole price authority (the cross-cutting "no money fork" stance, `STAY_SEARCH_RESERVATIONS_TICKETS.md:80-83`).

### 5.7 Date semantics in the UI

`checkin` is the first night (inclusive); `checkout` is the departure day (exclusive — NOT a billable night, `:114-116`). The detail/search UI labels the span as "`checkin` → `checkout` (`nights` nights)" so the user understands the checkout day is not charged. The per-night breakdown has exactly `nights` rows (= `len([checkin, checkout))`), matching the stored `nights` (`:213`).

### 5.8 Loading & error states

While `getReservation`/`listReservations`/`getReservationHistory`/`searchStays` are pending, render `<Skeleton>` placeholders (header skeleton, row skeletons, timeline skeleton). On any 404, render the "Hotel booking is not enabled" / "not found" callout (never a half-rendered broken page). On 403 (non-admin attempting a mutation that slipped past the hidden-control guard), `toast.error("Admin access required")`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no dev-mode branches

HTL-021 is a frontend + test ticket. Its only backend interaction is through the HTL-020 router + HTL-017/018/019 services, all of which enforce SECOPS-007 (zero `if S.dev_mode` branches in business logic; the same `T.*` handles in both envs — `STAY_SEARCH_RESERVATIONS_TICKETS.md:76-79`). The frontend has no concept of dev mode — it calls the same `/ui/*` endpoints in both environments.

### 7.2 SECOPS-007 — hermetic pytest does not use `dev_mode`

`tests/test_htl_reservations.py` toggles `S.hotel_pms_enabled` via `object.__setattr__` but never sets `S.dev_mode`. Service calls go through the same DynamoDB code path, with moto intercepting boto3 (the forward-dep collaborators are patched, not real). Identical to the SECOPS-007 parity approach in every existing hermetic test (`tests/test_gap_0262_0264_kyc_template_endpoints.py`, PROP-005 §7.2).

### 7.3 Security — admin-only mutations + CSRF

All create/modify/lifecycle operations are gated by `require_admin_or_root_csrf` at the HTL-020 router layer (`app/auth/policy.py:100`). Reads use `require_ui_session` (`app/services/sessions.py:330`). The frontend's mutation wrappers are callable by any authenticated session, but the backend 403s non-admin callers. The UI hides "Book"/"Check-in"/"Check-out"/"Cancel"/"No-show"/"Modify" controls from `role=USER` sessions via `getRoleFromAccessToken(useAuthStore.getState().accessToken)` (`@/lib/adminCapabilities`, the `frontend/src/pages/tickets/TicketsPage.tsx:15,43` pattern), preventing confusing 403s. CSRF is handled transparently by `frontend/src/api/client.ts:179-181` (injects the `ui_csrf` cookie as `X-CSRF-Token`) for the cookie-auth browser path; bearer-auth callers skip CSRF (CLAUDE.md auth section).

### 7.4 Money-safety — HTL-021 issues no charge, writes no ledger

HTL-021 (and the entire HTL-017..HTL-020 stack it drives) issues **no** Stripe/PayPal/CCBill call and writes **no** ledger entry (the cross-cutting "no money fork" invariant, `STAY_SEARCH_RESERVATIONS_TICKETS.md:80-83`). Cancel/no-show release held inventory only — refunds + cancellation penalties + no-show fees are HTL-033 (Tier-3, forward ref) and must route through `refund_payment` (`app/routers/billing.py:1287`) / `settle_or_reverse_ledger`, never a parallel mechanism. The frontend NEVER imports from `api/endpoints/billing.ts`, NEVER renders a refund amount, and the cancel/no-show dialog copy explicitly states refunds are handled separately (§5.3). `total_cents`/`deposit_cents` are display-only values computed by HTL-015.

### 7.5 Idempotency

- **Reservation ids are non-deterministic** (`"res_" + uuid4().hex[:16]`, `STAY_SEARCH_RESERVATIONS_TICKETS.md:205`) — a guest may book the same span twice. The "Book" button is therefore disabled while the mutation is `isPending` (`useMutation.isPending`) to prevent an accidental double-booking from a double-click; there is no backend idempotency key on create (by design — distinct bookings are legitimate).
- **Lifecycle transitions are idempotency-safe via the version CAS** (`:406-411`): a re-fired transition on an already-advanced reservation either 409s (illegal edge from the new state) or 409s `concurrent_update`; the frontend re-fetches and re-derives the enabled buttons (§5.3). The `confirm` endpoint is an explicit no-op/idempotent return of the header (`:515`).

### 7.6 Audit trail

Backend services emit best-effort `_audit(...)` events (`hotel.reservation.created`, `hotel.reservation.status_changed`, `app/services/inventory.py:92-98` wrapper pattern, `STAY_SEARCH_RESERVATIONS_TICKETS.md:297,419`). HTL-021 adds no frontend-side audit emission — the backend is the authoritative audit source. The reservation status-history timeline (`HIST#` rows, `:412-418`) is a domain history surface, distinct from the security audit log.

## 10. Open Questions / Assumptions

1. **`guest_party_id` source in the Book dialog.** The cross-cutting constraint says guests reuse the person model (Contacts / OBP `CUS` / open-property `TEN`) and `guest_party_id` is an opaque string with no FK validation (`STAY_SEARCH_RESERVATIONS_TICKETS.md:72-75`). **Assumption**: the MVP "Book" dialog accepts a `guest_party_id` via a free-text input or a lightweight Contacts picker (`app/routers/contacts.py`). A full guest-search/create flow is a later front-desk ticket. The backend does not validate the FK, so an arbitrary opaque id is accepted.

2. **`StaySearchResult.per_night` / `NightLine` exact shape.** HTL-017 says `per_night` reuses the HTL-015 `NightLineOut` shape (`:157-158`), defined in `docs/qloapps/RATE_PLANS_TICKETS.md` (HTL-015) which is a forward dep. **Assumption**: each night line has `{date, amount_cents, applied_rule_ids?}`. If HTL-015's `NightLineOut` differs (e.g., a `rate_plan_id` field), the `NightLine` TS interface must be reconciled when HTL-015 lands.

3. **`list_reservations` / history response envelopes.** HTL-020 says `list_reservations` returns `{reservations, count, cursor}` (`:533`). **Assumption**: `getReservationHistory` returns `{events: [...]}` (the `_LinkedRecord`-style envelope) rather than a bare array; if HTL-019/020 returns a bare array (like `GET .../messages`, MEMORY.md), `ReservationHistoryOut` and the timeline mapping must be adjusted to `ReservationHistoryEntry[]`.

4. **Room-assignment picker source.** The check-in picker needs the hotel's physical rooms (HTL-006 `list_rooms`, forward dep). **Assumption**: MVP accepts free-text room ids (`rooms` inputs); a real room-status-aware picker wires HTL-006 when that cluster's reader is available. The backend only requires `len(assigned_room_ids) == rooms` (`:389-392`), not that the ids are real rooms (room-status marking is best-effort, `:391`).

5. **Modify quote preview via `searchStays`.** §5.4 previews the new price by calling read-only `searchStays`. **Assumption**: a `searchStays` over the proposed span/room-type returns a comparable `total_cents` to what `modify_reservation` will re-price (both compose `compute_stay_price`). If the two diverge (e.g., modify applies a different rate context), the preview is advisory only and the authoritative total is the `modifyReservation` response — which the UI re-renders on success.

6. **Admin-only UI gating.** `useAuthStore` has no `role` field; role is decoded via `getRoleFromAccessToken(accessToken)` (`@/lib/adminCapabilities`, `frontend/src/pages/tickets/TicketsPage.tsx:15,43`). **Confirmed**: mutation/lifecycle controls are hidden for `role=USER`; reads are visible to any authenticated session (HTL-020 reads are `require_ui_session`).

7. **`i18nKey` for the sidebar entry.** Nav items carry an `i18nKey` (`frontend/src/components/layout/Sidebar.tsx:85,156`). **Assumption**: `"nav.hotelBooking"` is added to the translation file if one exists; otherwise the `label` string ("Hotel Booking") is the fallback (the PROP-005 §10.7 precedent).

8. **`ReservationsPage` discoverability.** The sidebar nav points to `/hotel-search` (the entry funnel). **Assumption**: a hotel's `ReservationsPage` is reached from the search → book flow (the detail page links back) and/or a future front-desk console; HTL-021 does not add a hotel-picker landing page (a later front-desk ticket). The route exists and is directly linkable.
