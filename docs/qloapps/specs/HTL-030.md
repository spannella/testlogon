# HTL-030 — Add-on / ancillary-service line items — catalog SKU → folio line

**Type**: Feature | **Priority**: P1 | **Estimate**: 1d
**Source**: `docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md` §HTL-030 (`:260-321`) + "Cross-cutting constraints" (`:50-99`) + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §"Service / ancillary add-ons" (`:102`)

---

## 1. Summary & Goal

HTL-030 lets the front desk **attach a catalog add-on SKU** — breakfast, airport
pickup, an extra bed — to a guest folio as a priced line item. It is the
**lowest-net-new** ticket in the folio cluster: a single new service function
`add_addon_to_folio(reservation_id, *, sku, quantity=1, user_sub)` in the
**existing** `app/services/hotel_folios.py` (landed by HTL-029) plus one tiny
Pydantic input model `FolioAddonIn`. There is **no new table, no new GSI, no new
setting, and no new feature flag** — the add-on is just an HTL-029 `LINE#` row with
`line_type="addon"` and a `sku` set, and the whole vertical stays gated behind the
HTL-001 master flag `S.hotel_pms_enabled`.

The function does exactly one new thing on top of HTL-029: it **resolves the price
from the catalog server-side** instead of trusting a client-supplied amount. It
looks the SKU up with `catalog._find_item_by_id(sku)` (the O(1) `ByItemId` GSI
lookup, `app/routers/catalog.py:702-718`), reads `unit_price_cents =
ddb_to_int(item["price_cents"])` (`catalog.py:71-75,115`) and `description =
item["name"]`, then delegates to HTL-029's `add_line_item(...)` so the
`amount_cents` math, the atomic `charges_total_cents` bump, the open-folio guard,
and the audit trail all flow through the **single** HTL-029 write path. No total or
ledger logic is duplicated.

The gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:102`) records the
service/ancillary add-on as **PARTIAL**: "catalog + cart provide products; no
'attach add-on to a booking' link." HTL-030 lands exactly that missing link. With
HTL-030 merged but `HOTEL_PMS_ENABLED=false` (the default), the platform is
byte-for-byte unchanged: `add_addon_to_folio` 404s at the `_require_enabled()`
gate before reading either the catalog or the folio, and **no folio line is ever
written**.

The deliverables are:

1. **Service function** `add_addon_to_folio` appended to `app/services/hotel_folios.py`.
2. A thin local resolver `_resolve_addon(sku) -> (price_cents, name)` keeping the
   catalog coupling (and the test patch point) in one place.
3. The Pydantic input model `FolioAddonIn` in `app/models.py`.

## 2. Context & Current State

### 2.1 Gap — products exist, but no "attach to a booking" link

The gap analysis §"Service / ancillary add-ons (breakfast, pickup, extra bed) on a
booking" (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:102`) records the row **PARTIAL**:
"catalog + cart provide products; no 'attach add-on to a booking' link." The
adjacent guest-folio row (`:101`) is the HTL-029 gap that HTL-030 layers on top of.

The platform already has everything HTL-030 needs *except* the link itself:

- **The catalog item store** — a `catalog` DynamoDB table with item rows carrying
  `item_id`, `name`, `price_cents` (integer cents), and `currency`
  (`app/routers/catalog.py:361-376`, the create path). Items are looked up O(1) by
  `item_id` via the `ByItemId` GSI in `_find_item_by_id`
  (`app/routers/catalog.py:702-718`). Add-on SKUs (breakfast, pickup, extra bed)
  are created via the **existing** `POST /ui/catalog/categories/{category_id}/items`
  endpoint (`catalog.py:352-391`) — HTL-030 introduces **no** new catalog ticket and
  no catalog code change.
- **The folio entity** — HTL-029's `hotel_folios` table (PK=`reservation_id`,
  SK=`META` header + `LINE#{line_id}` child rows,
  `docs/qloapps/specs/HTL-029.md` §3.1) and the `add_line_item` service that
  appends a `LINE#` row and atomically bumps `charges_total_cents`
  (`docs/qloapps/specs/HTL-029.md` §4.3).

What is missing is purely the *resolve-SKU-price-then-add-line* glue. HTL-030 is
that glue and nothing more.

### 2.2 The catalog item lookup to reuse (`_find_item_by_id`)

`app/routers/catalog.py:702-718` is the O(1) lookup HTL-030 calls:

```python
# catalog.py:702-718
def _find_item_by_id(item_id: str) -> Optional[Dict[str, Any]]:
    """Find a catalog item by item_id via the ByItemId GSI (O(1) query)."""
    resp = T.catalog.query(
        IndexName="ByItemId",
        KeyConditionExpression=Key("item_id").eq(item_id),
        FilterExpression="entity = :ent",
        ExpressionAttributeValues={":ent": "item"},
    )
    items = resp.get("Items", [])
    if items:
        return items[0]
    return None
```

The returned dict (when found) carries the fields HTL-030 reads: `name` (S),
`price_cents` (N → `Decimal`), `currency` (S), and `item_id` (S). The `entity =
"item"` filter is what excludes review rows that also carry an `item_id`
(`catalog.py:712-713`). A missing SKU returns `None` — HTL-030 turns that into a 404.

### 2.3 The catalog price-as-cents idiom (`ddb_to_int` + `price_cents`)

DynamoDB returns the catalog `price_cents` `N` attribute as a `Decimal`. The catalog
router coerces it with its local `ddb_to_int` (`app/routers/catalog.py:71-75`):

```python
# catalog.py:71-75
def ddb_to_int(value: Any) -> int:
    try:
        return int(value)
    except (TypeError, ValueError):
        return 0
```

and reads the item price as `price_cents=ddb_to_int(item["price_cents"])` in
`_catalog_item_out` (`catalog.py:115`). Catalog prices are **already integer
cents** at write time — `"price_cents": int(body.price_cents)`
(`catalog.py:370`) — so HTL-030 reads cents directly, no float ever involved
(money-safety, §7.4). HTL-030 reuses HTL-029's own `_to_int`
(`docs/qloapps/specs/HTL-029.md` §4.1, copied from `inventory.py:67`) for the
coercion rather than importing the catalog's `ddb_to_int`, keeping the catalog
coupling confined to the single `_find_item_by_id` call (§2.6).

### 2.4 The HTL-029 `add_line_item` write path to delegate to

HTL-029 (`docs/qloapps/specs/HTL-029.md` §4.3) defines the single charge-write path
HTL-030 routes through:

```
add_line_item(reservation_id, *, line_type, description, quantity=1,
              unit_price_cents, sku="", user_sub) -> dict
```

It: (1) `_require_enabled()`; (2) validates `line_type`, `quantity >= 1`,
`unit_price_cents >= 0`; (3) reads the `META` row → **404** if absent, **409** if
`status != "open"`; (4) mints `line_id = uuid4().hex`, computes `amount_cents =
quantity * unit_price_cents`; (5) puts the `LINE#{line_id}` row; (6) atomically
bumps the header `charges_total_cents` via `update_item` `ADD`; (7) audits
`hotel.folio.line_added`; (8) returns the created line dict. **HTL-030 owns none of
this math** — it computes only the SKU→price resolution and hands the rest to
`add_line_item`.

### 2.5 The flag / audit / coerce idioms (already in `hotel_folios.py`)

HTL-029 already copied the `inventory.py` idioms into `hotel_folios.py`
(`docs/qloapps/specs/HTL-029.md` §4.1):

- `_flag_on()` → `bool(getattr(S, "hotel_pms_enabled", False))` and
  `_require_enabled()` raising `HTTPException(404, "Hotel PMS is not enabled")`
  (the `inventory.py:50-56` 404 contract).
- `_audit(event, user_sub, **fields)` — the lazy-import best-effort audit wrapper
  (`inventory.py:92-98`).
- `_to_int(value, default=0)` Decimal coercion (`inventory.py:67`).

HTL-030 reuses all three verbatim — it adds **no** new helper of these kinds, only
the catalog resolver `_resolve_addon` (§4.2) and the public function.

### 2.6 No module-level catalog import (cycle avoidance)

`app/routers/catalog.py` imports nothing from `app/services/hotel_folios.py`, and a
module-level `from app.routers.catalog import _find_item_by_id` in
`hotel_folios.py` would create a layering smell (a service importing a router at
import time). Per the cluster note (`docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md:298-301`)
HTL-030 uses a **lazy import inside `_resolve_addon`**:

```python
from app.routers.catalog import _find_item_by_id
```

This keeps the only catalog coupling in one tiny function, makes the test patch
point obvious (`monkeypatch.setattr("app.services.hotel_folios._find_item_by_id_lazy", ...)`
or patching `app.routers.catalog._find_item_by_id`), and defers the import until
the flag is on and the function is actually invoked.

### 2.7 The `now_ts()` primitive

Timestamps come from `now_ts()` (`app/core/time.py:2`) — integer Unix seconds.
HTL-030 itself writes no timestamps directly; the `created_at` on the `LINE#` row is
set by `add_line_item` (`docs/qloapps/specs/HTL-029.md` §4.3 step 4). Listed here
for cluster completeness — HTL-030 never re-implements time.

### 2.8 What does NOT change

`grep -n "add_addon_to_folio\|FolioAddonIn" app/services/hotel_folios.py
app/models.py` returns nothing before HTL-030. No table, GSI, setting, flag, or
catalog code is touched. The `catalog` table, the `hotel_folios` table, the
`hotel_pms_enabled` flag, and the HTL-029 service functions are all **reused as-is**.

## 3. Data Model

HTL-030 introduces **no new table, no new GSI, no new settings key, and no schema
change**. It writes one existing row shape — the HTL-029 `LINE#{line_id}` folio line
— with `line_type="addon"` and the `sku` attribute populated.

### 3.1 The `addon` folio-line row (reused from HTL-029 §3.1)

Written to the `hotel_folios` table (PK=`reservation_id`, SK=`LINE#{line_id}`,
`line_id = uuid4().hex`) by HTL-029's `add_line_item`. HTL-030 supplies the field
values; the row shape is unchanged:

| Attribute | DDB Type | HTL-030 value |
|---|---|---|
| `reservation_id` | S | The folio PK (same partition as `META`). |
| `sk` | S | `"LINE#{line_id}"` (`line_id` minted by `add_line_item`). |
| `line_id` | S | Convenience copy of the id. |
| `line_type` | S | **Always `"addon"`** for HTL-030. |
| `description` | S | `f"{item['name']} x{quantity}"`, e.g. `"Breakfast x2"`. |
| `quantity` | N | The caller's `quantity` (`ge=1`). |
| `unit_price_cents` | N | **Server-resolved** `ddb_to_int(item["price_cents"])` from the catalog — never client-supplied. |
| `amount_cents` | N | `quantity * unit_price_cents` (computed by `add_line_item`). |
| `sku` | S | **The catalog `item_id`** — populated for `addon` lines (HTL-029 §3.1 sets `""` for non-addon). |
| `created_at` | N | `now_ts()` (set by `add_line_item`). |

The folio `META` header's `charges_total_cents` is bumped atomically by
`add_line_item` (HTL-029 §4.3 step 6) — HTL-030 adds no separate counter logic.

### 3.2 The catalog item row read (reused from `catalog.py`)

HTL-030 **reads** (never writes) the existing catalog item row. The fields consumed:

| Attribute | DDB Type | Use in HTL-030 |
|---|---|---|
| `item_id` | S | The `sku` argument; stored back onto the folio line's `sku`. |
| `name` | S | The line `description` (`f"{name} x{quantity}"`). |
| `price_cents` | N | `unit_price_cents` after `_to_int` coercion. |
| `entity` | S | The `_find_item_by_id` filter (`entity = "item"`) — excludes review rows. |

### 3.3 Pydantic model (`app/models.py`)

One additive input model (placed next to `FolioLineIn` from HTL-029,
`docs/qloapps/specs/HTL-029.md` §3.4 — after the existing `CatalogItemCreateIn` at
`app/models.py:538` is unaffected):

```python
class FolioAddonIn(BaseModel):
    sku: str
    quantity: int = Field(default=1, ge=1)
```

`FolioAddonIn` carries **no price** — the price is resolved server-side from the
catalog (anti-tamper, §7.3). The created add-on line is serialized with the
**existing** HTL-029 `FolioLineOut` model (`docs/qloapps/specs/HTL-029.md` §3.4) —
no new output model is needed.

> **Why no new output model.** An add-on line is just a `FolioLineOut` with
> `line_type="addon"` and `sku` set. Reusing it keeps the response shape identical
> across line types (room-night, addon, tax, fee), so the HTL-032 folio-detail
> projection renders all lines uniformly.

## 4. API / Service Design

The single service addition lives in `app/services/hotel_folios.py` (the HTL-029
file). **No `if S.dev_mode` branch anywhere** — SECOPS-007 (§7.1). The HTL-032
router binds `FolioAddonIn` and calls `add_addon_to_folio`; HTL-030 ships the
service only (the router endpoint is HTL-032's deliverable, §11.2).

### 4.1 No new module-level helpers beyond `_resolve_addon`

HTL-030 reuses the HTL-029 `_flag_on()`, `_require_enabled()`, `_audit()`,
`_to_int()`, and `_line_sk()` helpers unchanged (§2.5). It adds exactly one local
resolver.

### 4.2 `_resolve_addon(sku) -> tuple[int, str]`

The single point of catalog coupling — resolves a SKU to `(price_cents, name)` via
the lazy-imported catalog lookup. 404 if the SKU does not exist.

```python
def _resolve_addon(sku: str) -> tuple[int, str]:
    from app.routers.catalog import _find_item_by_id   # lazy — cycle/layer-safe (§2.6)
    item = _find_item_by_id(sku)
    if not item:
        raise HTTPException(status_code=404, detail="Add-on SKU not found")
    price_cents = _to_int(item.get("price_cents"))
    name = str(item.get("name") or sku)
    return price_cents, name
```

- The lazy import is inside the function (§2.6) so importing `hotel_folios.py` never
  pulls in the catalog router.
- `_to_int` (HTL-029 §4.1) coerces the `Decimal` `price_cents` to `int`.
- A blank or absent `name` falls back to the `sku` string so the description is
  never empty.
- `_resolve_addon` is the obvious test patch point (patch
  `app.routers.catalog._find_item_by_id` to return a fixed item dict, §9.1).

### 4.3 `add_addon_to_folio(reservation_id, *, sku, quantity=1, user_sub) -> dict`

The public function. A thin layer over `add_line_item` that resolves the price and
forces `line_type="addon"`.

1. **`_require_enabled()`** — raises `HTTPException(404, "Hotel PMS is not
   enabled")` when the flag is off, **before any catalog or folio read** (§5.5). This
   is the first statement.
2. **Validate `quantity >= 1`** → `HTTPException(422, "quantity must be >= 1")`
   (also enforced by the `FolioAddonIn` `Field(ge=1)`; defended again at the service
   boundary for non-router callers).
3. **Resolve the SKU** — `price_cents, name = _resolve_addon(sku)` (404 on unknown
   SKU, §5.1). The price is now **server-resolved**.
4. **Delegate to HTL-029's `add_line_item`** with the resolved values:

   ```python
   line = add_line_item(
       reservation_id,
       line_type="addon",
       description=f"{name} x{quantity}",
       quantity=quantity,
       unit_price_cents=price_cents,
       sku=sku,
       user_sub=user_sub,
   )
   ```

   `add_line_item` performs the open-folio guard (404 missing / 409 closed,
   §5.2-5.3), computes `amount_cents = quantity * price_cents`, writes the `LINE#`
   row, and atomically bumps `charges_total_cents` (HTL-029 §4.3). **HTL-030
   duplicates none of this.**
5. **Audit** — `_audit("hotel.folio.addon_added", user_sub, reservation_id=...,
   sku=sku, quantity=quantity, amount_cents=line["amount_cents"])`. This is in
   *addition* to the `hotel.folio.line_added` event `add_line_item` already emits —
   the add-on event carries the `sku` for catalog-attribution audit. Best-effort
   (the `_audit` wrapper swallows exceptions).
6. **Return** the created line dict (the `FolioLineOut` shape returned by
   `add_line_item`, numbers already `_to_int`-coerced).

Full sketch:

```python
def add_addon_to_folio(
    reservation_id: str,
    *,
    sku: str,
    quantity: int = 1,
    user_sub: str,
) -> dict:
    _require_enabled()
    if quantity < 1:
        raise HTTPException(status_code=422, detail="quantity must be >= 1")
    price_cents, name = _resolve_addon(sku)
    line = add_line_item(
        reservation_id,
        line_type="addon",
        description=f"{name} x{quantity}",
        quantity=quantity,
        unit_price_cents=price_cents,
        sku=sku,
        user_sub=user_sub,
    )
    _audit(
        "hotel.folio.addon_added",
        user_sub,
        reservation_id=reservation_id,
        sku=sku,
        quantity=quantity,
        amount_cents=line["amount_cents"],
    )
    return line
```

### 4.4 Ordering of guards

The guard order is deliberate and matters for both correctness and side-effect
safety:

1. `_require_enabled()` — flag-off 404 before *any* table access (§5.5, SECOPS-007
   parity).
2. `quantity` validation — 422 before any catalog read (cheap input check first).
3. `_resolve_addon` — SKU 404 (catalog read) **before** the folio is touched, so an
   unknown SKU never writes a `LINE#` row or bumps `charges_total_cents` (§5.1).
4. `add_line_item` — folio existence/open guards (404/409) and the actual write.

Because the SKU is resolved **before** `add_line_item` runs, a bad SKU and a
closed/missing folio are cleanly distinguishable by status code, and no partial
write ever occurs (§5.4).

## 5. Detailed Behavior & Edge Cases

### 5.1 Unknown SKU → 404, no write

`_resolve_addon(sku)` calls `_find_item_by_id(sku)`; an absent item returns `None`
→ `HTTPException(404, "Add-on SKU not found")`. This fires **before** `add_line_item`
is called, so **no `LINE#` row is written** and `charges_total_cents` is unchanged.
The catalog `ByItemId` GSI filter (`entity = "item"`) means a SKU that collides with
a review row's `item_id` still resolves to the item row, not the review.

### 5.2 Add-on on an unknown folio → 404

When the `reservation_id` has no `META` folio row, the inner `add_line_item` raises
`HTTPException(404, "Folio not found")` (HTL-029 §5.2) **after** the SKU resolves
successfully. The order means a valid-SKU + unknown-folio request 404s on the
folio, and an unknown-SKU + valid-folio request 404s on the SKU — both 404, but the
`detail` distinguishes them (`"Add-on SKU not found"` vs `"Folio not found"`). No
orphan `LINE#` row is written in either case.

### 5.3 Add-on on a closed folio → 409

When the folio's `META` `status == "closed"`, `add_line_item` raises
`HTTPException(409, "Folio is closed")` (HTL-029 §5.3). A closed folio is immutable —
no add-on may be charged after checkout-close. No `LINE#` row is written and
`charges_total_cents` is unchanged. (A correction after close is a void/credit, the
cancellation-cluster concern — HTL-029 §10 Q6.)

### 5.4 No partial write across the SKU-resolve / line-add boundary

The SKU is resolved (a pure catalog read) **before** any `hotel_folios` write. If
SKU resolution 404s, nothing is written. If `add_line_item` 404s/409s on the folio,
nothing is written (its own guards run before its `put_item`, HTL-029 §4.3 step 3).
There is no window in which a `LINE#` row exists without a successful charge bump
that HTL-030 itself introduces — `add_line_item` owns that atomicity (HTL-029 §5.4
discusses the line-put / header-`ADD` hedge; HTL-030 inherits it unchanged).

### 5.5 Flag-off → 404 (no catalog or folio access)

When `HOTEL_PMS_ENABLED=false` (the default), `_require_enabled()` raises
`HTTPException(404, "Hotel PMS is not enabled")` as the **first** statement —
before `_find_item_by_id` (no catalog query) and before any `hotel_folios` access.
The catalog table is never read, the folio table is never read or written, and no
audit row is emitted. The platform is byte-for-byte unchanged with the flag off
(cluster constraint, `docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md:52-60`).

### 5.6 `quantity < 1` → 422

`add_addon_to_folio` rejects `quantity < 1` with `HTTPException(422)` before reading
the catalog. The `FolioAddonIn` `Field(default=1, ge=1)` rejects it at the router
layer too (a 422 from FastAPI validation), so a malformed router request never
reaches the service. The double-check defends direct service callers (HTL-031/HTL-032
internal use). `quantity = 0` and negative values are both rejected.

### 5.7 Add-ons are not deduped — each call is a distinct charge

Two `add_addon_to_folio` calls for the same `sku` on the same folio create **two**
distinct `LINE#` rows (each with its own non-deterministic `line_id = uuid4().hex`,
HTL-029 §2.5) and bump `charges_total_cents` twice. This is correct: a guest may
legitimately order breakfast on two separate days, or two extra beds. `add_line_item`
is intentionally **not** idempotent (HTL-029 §7.2), and `add_addon_to_folio`
inherits that — an add-on is a real, repeatable charge, not a set-membership toggle.

### 5.8 `amount_cents` is server-computed from a server-resolved price

The client supplies only `sku` and `quantity` (`FolioAddonIn`). The `unit_price_cents`
comes from the catalog (`_resolve_addon`), and `amount_cents = quantity *
unit_price_cents` is computed inside `add_line_item`. A client **cannot** influence
the price — it cannot pass `price_cents`, `unit_price_cents`, or `amount_cents`.
This is the `unlock_post` server-side-price posture (CLAUDE.md / MEMORY:
"`unlock_post` validates PM from billing table … server-side price"). §7.3.

### 5.9 Zero-priced add-on is permitted

A catalog item with `price_cents == 0` (a complimentary breakfast, a $0 promo
extra) resolves to `unit_price_cents = 0`; `add_line_item`'s `unit_price_cents >= 0`
guard (HTL-029 §4.3 step 2) accepts it. The line is written with `amount_cents = 0`
and `charges_total_cents` is bumped by 0 (a no-op `ADD`). A $0 add-on line is a
valid, visible folio entry (it documents the comp).

### 5.10 Decimal coercion on the catalog price

The catalog `price_cents` `N` attribute returns as a `Decimal`; `_resolve_addon`
coerces it with HTL-029's `_to_int` so a plain `int` reaches `add_line_item`. The
folio line's numeric fields are `_to_int`-coerced again by `add_line_item` on the
way out (HTL-029 §5.8), so `FolioLineOut` receives plain `int`s, never `Decimal`.

### 5.11 Currency mismatch is out of scope (assumed same currency)

The catalog item carries a `currency` (`catalog.py:371`) and the folio carries a
`currency` (HTL-029 §3.1). HTL-030 does **not** reconcile or convert currencies — it
assumes the add-on catalog SKUs are priced in the folio's currency (single-currency
hotel, the default). Multi-currency reconciliation is the Tier-3 tax/currency
cluster's concern (HTL-029 §11.4) — §10 Q2.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`add_addon_to_folio` and `_resolve_addon` contain **no** `if S.dev_mode` branch.
The same DynamoDB code path runs in dev (boto3 intercepted by moto in-process) and
prod (real DynamoDB): the catalog `ByItemId` GSI query and the HTL-029
`hotel_folios` write are identical in both environments. This mirrors the cluster
cross-cutting constraint (`docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md:90-94`) and the
no-`dev_mode`-branch posture of `inventory.py` and HTL-029.

### 7.2 Idempotency

`add_addon_to_folio` is intentionally **not** idempotent — each call appends a fresh
non-deterministic `LINE#{uuid}` row and bumps `charges_total_cents` (§5.7). This is
correct for a repeatable charge. A retried/duplicate HTTP request will create a
duplicate add-on line; deduplication, if ever required, is a router-level
idempotency-key concern (HTL-032), not a service-layer guard — an add-on is a real
charge, not a set-membership toggle. (`open_folio` and `close_folio` remain
idempotent per HTL-029 §7.2; HTL-030 changes neither.)

### 7.3 Security — server-resolved price (anti-tamper) + auth split

- **The client never supplies a price.** `FolioAddonIn` carries only `sku` and
  `quantity`; `unit_price_cents` is read from the catalog server-side in
  `_resolve_addon` (§5.8). A malicious client cannot charge a folio at a tampered
  price — the same posture as `unlock_post` validating the PM/price server-side
  (CLAUDE.md / MEMORY). This is the **core** security property of HTL-030.
- **Auth split** (HTL-032 router, cluster constraint
  `docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md:82-85`): the add-on mutation endpoint is
  gated by `require_admin_or_root_csrf` (`app/auth/policy.py:100`) — only hotel
  staff (admin/root) attach add-ons, identical to `app/routers/inventory.py:48,65,81`.
  HTL-030 ships the service only; the router enforces auth (§11.2).
- **Ownership / tenancy** — the folio's `hotel_id` scoping (one hotel's staff cannot
  charge another hotel's folio) is a router concern (HTL-029 §10 Q3). The service
  resolves whatever `reservation_id` it is handed.

### 7.4 Money-safety

- **Integer cents throughout** — the catalog `price_cents` is integer cents at write
  time (`catalog.py:370`), read as `int` via `_to_int`; `unit_price_cents` and the
  derived `amount_cents = quantity * unit_price_cents` are integer arithmetic
  (computed by `add_line_item`, HTL-029 §7.4). **No float ever touches money.**
- **One charge-write path** — the `charges_total_cents` bump goes through HTL-029's
  atomic `update_item` `ADD` (HTL-029 §4.3 step 6). HTL-030 writes **no** money row,
  imports **no** `billing_shared`, and constructs **no** bespoke total math — it
  reuses the single HTL-029 path (cluster "ONE refund/ledger mechanism — never fork
  billing", `docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md:73-78`).
- **No client-supplied amount** — see §7.3; the only money input is the catalog's
  own `price_cents`.

### 7.5 Audit trail

`add_addon_to_folio` emits `hotel.folio.addon_added` (carrying `sku`, `quantity`,
`amount_cents`) via the best-effort `_audit()` wrapper (HTL-029 §4.1), **in addition
to** the `hotel.folio.line_added` event `add_line_item` already emits. The add-on
event preserves catalog attribution (which SKU was charged) for compliance. Audit
failure is swallowed and never propagates (the lazy-import + bare-`except`
contract).

## 10. Open Questions / Assumptions

1. **Catalog scope of add-on SKUs.** HTL-030 resolves any catalog `item_id` via the
   global `_find_item_by_id` lookup — it does **not** restrict SKUs to a designated
   "add-ons" category. **Assumption**: the front desk attaches only intended add-on
   SKUs (breakfast, pickup, extra bed), created in a hotel add-on catalog category
   via the existing catalog admin. A per-hotel add-on-category allowlist (so a clerk
   cannot attach an arbitrary unrelated product) is a HTL-032 router / catalog-tagging
   refinement, out of HTL-030 scope.

2. **Currency reconciliation.** HTL-030 reads the catalog `price_cents` directly and
   assumes the add-on SKU is priced in the folio's currency (§5.11). **Assumption**:
   single-currency hotel (the default). Cross-currency add-ons (a USD-priced SKU on a
   EUR folio) need conversion — the Tier-3 tax/currency cluster (HTL-029 §11.4), not
   HTL-030.

3. **Stock decrement.** The catalog item may carry `stock_count`
   (`catalog.py:377-379`). HTL-030 does **not** decrement stock when attaching an
   add-on (a folio add-on is a service charge, not a cart checkout). **Assumption**:
   add-on SKUs are services/unlimited (`stock_count` absent → "unlimited",
   `catalog.py:96-97`); coupling folio add-ons to inventory stock is a later ticket
   if physical add-ons (e.g. a sellable amenity) ever need it.

4. **Quantity-aware description.** The line description is `f"{name} x{quantity}"`
   (e.g. `"Breakfast x2"`). **Assumption**: this matches the folio-UX norm and is
   sufficient; a richer per-line note (date the add-on applies to) is a HTL-032 UI
   concern and can be added to the description by the caller if needed.

5. **No `remove_addon`.** HTL-030 ships no add-on-removal function — lines are
   append-only (HTL-029 §10 Q6). **Assumption**: a mistaken add-on is corrected by an
   offsetting negative-amount line or a void/credit (the cancellation cluster via
   `settle_or_reverse_ledger`), never by deleting a `LINE#` row.
