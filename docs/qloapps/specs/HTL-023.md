# HTL-023 — Front-desk action service — walk-in / assign-room / change-room / room-move

**Type**: Feature | **Priority**: P1 | **Estimate**: 2.5d
**Source**: `docs/qloapps/FRONT_DESK_TICKETS.md` §HTL-023 + §"Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C row "Front desk (arrivals/departures/in-house, walk-in, assign room, check-in/out, room-move)"

---

## 1. Summary & Goal

HTL-023 adds the **front-desk action service** — the four mutating operations a front-desk
agent performs at the counter: **walk-in booking** (create a reservation and immediately
check it in), **assign-room** (set the physical room(s) for a reservation), **change-room**
(swap the assignment set), and **room-move** (relocate a single checked-in guest from one
room to another). It is the action half of the front-desk console; HTL-022
(`docs/qloapps/FRONT_DESK_TICKETS.md` §HTL-022) is the read half (arrivals / departures /
in-house / occupancy queries).

Every action **wraps existing reservation and room services** — it adds **no new record and
no new DynamoDB table**, only orchestration + optimistic-concurrency version-gating + audit
over the existing entities:

- `walk_in_booking` delegates to the HTL-018 `reservations.create_reservation(...)` (the same
  create path the public booking storefront uses — never re-implemented, so the availability
  decrement and total computation are inherited) and then the HTL-019
  `reservations.check_in(...)` transition.
- `assign_room` / `change_room` / `room_move` write `assigned_room_ids` onto the HTL-018
  `hotel_reservations` META row via a **version-gated** `update_item`
  (`ConditionExpression="version = :v"` → 409 on stale version) and flip each affected room's
  housekeeping posture through the HTL-007 `room_inventory.set_room_housekeeping_status(...)`
  setter — this service **never writes a `hotel_rooms` row directly** (one owner per table).

HTL-023 ships **no router** (that is HTL-024's deliverable) and **no frontend** (HTL-024).
The whole hotel vertical is gated by the master flag `HOTEL_PMS_ENABLED` (default `false`,
landed in HTL-010). With the flag off, every action entrypoint raises HTTP 404 via
`_require_enabled()` and the platform is byte-for-byte unchanged. The gap analysis
(`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:94`) records the front-desk row — "walk-in, assign
room, check-in/out, room-move" — as **MISSING**; HTL-023 lands the action surface for it.

Without HTL-023, the front-desk console can only *view* the operational state (HTL-022); it
cannot *act* on it. With HTL-023 merged but `HOTEL_PMS_ENABLED=false` (the default), the
platform is unchanged.

### 2.6 Optimistic-concurrency CAS idiom (reused from `inventory.py:434-453`)

`app/services/inventory.py:434-453` (`_close_reservation`) documents the canonical
single-writer compare-and-swap idiom: a conditional `update_item` whose
`ConditionExpression` guards the prior state, with the `ConditionalCheckFailedException`
caught to resolve the race to exactly one winner:

```python
# inventory.py:440-453 (status-CAS one-winner idiom)
try:
    resp = T.reservations.update_item(
        Key=...,
        UpdateExpression="SET #status = :new, closed_at = :now ...",
        ConditionExpression="#status = :active",
        ...
    )
    return resp.get("Attributes")
except ClientError as exc:
    if exc.response["Error"].get("Code") == "ConditionalCheckFailedException":
        return None  # already terminal — idempotent no-op
    raise
```

HTL-023's three assignment writes clone this contract but guard on the reservation's
**`version`** field (the HTL-018/019 optimistic-concurrency token, mirroring the ORD/LSE
state-machine `version` bump the reservation entity clones, `docs/qloapps/FRONT_DESK_TICKETS.md:196-197`):
`ConditionExpression="version = :v"` → on `ConditionalCheckFailedException` raise
`HTTPException(409, "Reservation was modified concurrently")`. This is the same one-winner
guard, applied to `version` rather than `status`.

### 2.7 `now_ts()` for all timestamps

`app/core/time.py:2` defines `now_ts() -> int` (integer Unix seconds). HTL-023 uses it for
`updated_at` on the reservation META row and any action-side timestamp. No `datetime`/ISO
strings — the platform-wide convention is integer Unix seconds (the CLAUDE.md `_to_utc`
Decimal/ISO gotcha is the cautionary tale).

### 2.8 The HTL-018 reservation `version` field and `assigned_room_ids`

The HTL-018 `hotel_reservations` META item (forward dep) carries
(`docs/qloapps/FRONT_DESK_TICKETS.md:98-101,186-188,196-197`): `reservation_id`, `hotel_id`,
`room_type_id`, `guest_name`, `guest_sub`, `checkin` (`YYYY-MM-DD`, `S`), `checkout`,
`status` (`confirmed`/`checked_in`/`checked_out`/`no_show`/`cancelled`),
`occupancy_adults`/`occupancy_children`, `assigned_room_ids` (`L` of room-id strings;
possibly empty), `total_cents` (`N`), and `version` (`N`, optimistic-concurrency token,
bumped on every state-machine transition). HTL-023 reads `version` from the caller's payload,
guards the write on it, and bumps it (`ADD version :one`) on every successful assignment
write so the caller's next call must carry the new version.

### 2.9 The HTL-019 `check_in` transition

HTL-019 (forward dep, `docs/qloapps/FRONT_DESK_TICKETS.md:205-210,261`) supplies the
check-in transition: it flips the reservation `status` from `confirmed` to `checked_in`
(version-gated), records `assigned_room_ids`, and bumps `version`. `walk_in_booking` calls it
immediately after create. HTL-023 does **not** re-implement check-in — it delegates.

> **Forward-dep contract reconciliation (the HTL-019 spec has since landed).** The parent
> ticket (`docs/qloapps/FRONT_DESK_TICKETS.md:205-210`) sketched the transition as
> `reservations.check_in(reservation_id, *, version, assigned_room_ids, user_sub)`, and this
> spec was authored against that sketch. The now-landed `docs/qloapps/specs/HTL-019.md:379-403`
> instead exposes a **single** generic transition entrypoint —
> `transition_reservation(reservation_id, target_status, *, actor, reason="",
> assigned_room_ids=None)` — with **no `check_in` alias**. Differences `walk_in_booking` must
> adapt to: (a) `target_status="checked_in"` is a **positional** arg, not a dedicated
> function; (b) the actor kwarg is **`actor`**, not `user_sub`; (c) there is **no `version`
> parameter** — HTL-019 reads the current `version` from the META row itself and runs its own
> `version = :expected_version` CAS, so `walk_in_booking` does **not** thread a version into
> the transition; (d) on `→ checked_in`, `assigned_room_ids` is **required and non-empty** and
> `len(assigned_room_ids)` must equal the reservation's `rooms`
> (`HTL-019.md:399-402`) — an unassigned walk-in check-in is therefore **not** possible
> through HTL-019 (this narrows §5.2: defer-assignment means leaving the reservation
> `confirmed`, not checking it in empty); and (e) HTL-019's own check-in already flips each
> physical room `occupied` via the HTL-006 `set_room_status` setter (`HTL-019.md:403-409`),
> **not** the HTL-007 `set_room_housekeeping_status` housekeeping setter, so the walk-in
> room flip in §4.1.1 step 4 is **redundant with HTL-019's side-effect** and may be dropped to
> avoid a double flip. The thin-orchestration intent is unchanged; the call shape in §4.1.1
> step 3 must be rewritten to `reservations.transition_reservation(res["reservation_id"],
> "checked_in", actor=user_sub, assigned_room_ids=assigned_room_ids or [...])`. Tracked as
> Open-Q §10.6.

### 2.10 The HTL-007 housekeeping setter

HTL-007 (`docs/qloapps/specs/HTL-007.md` §4.1.1) owns
`set_room_housekeeping_status(hotel_id, room_id, *, housekeeping_status, user_sub) -> dict` —
a single `update_item` on the `ROOM#{room_id}` row that rewrites `housekeeping_status`
(re-bucketing the room under `GSI_HK_STATUS` automatically) and audits
`hotel.room.housekeeping_status`. The HTL-007 enum is `{clean, dirty, inspected,
out_of_service}` (`docs/qloapps/specs/HTL-007.md:199-209`); the room sellability lifecycle
`status ∈ {available, out_of_service}` is a **separate** column. HTL-023 calls this setter
for every room flip (occupy → `dirty`-on-departure / free → `clean`); the **exact target
enum lives with HTL-007** (`docs/qloapps/FRONT_DESK_TICKETS.md:216-220`) — HTL-023 calls the
setter, never writes the room row directly.

### 2.11 Decimal coercion on read

DynamoDB returns numeric attributes (`version`, `total_cents`, `created_at`, `updated_at`,
`occupancy_adults`, `occupancy_children`) as `decimal.Decimal` via the boto3 resource API.
`_row_from_reservation` (HTL-022) already coerces these to `int`; HTL-023's action functions
return through `_row_from_reservation`, inheriting the coercion (the CLAUDE.md
`MessageEncryptionEnvelope Decimal coercion` pattern; same requirement noted in
`docs/qloapps/specs/HTL-007.md` §2.8).

## 3. Data Model

### 3.1 No new table, no new row

HTL-023 introduces **no DynamoDB table and no new row** (`docs/qloapps/FRONT_DESK_TICKETS.md:43-45,186-188,239-240`).
Every action mutates **existing** rows:

| Row | Table | Mutated attributes |
|---|---|---|
| Reservation META | `hotel_reservations` (HTL-018 forward dep) | `assigned_room_ids` (`L`), `status` (`S`, only via the HTL-019 `check_in` path for walk-in), `version` (`N`, bumped), `updated_at` (`N`) |
| Physical room `ROOM#{room_id}` | `hotel_rooms` (HTL-006) | `housekeeping_status` (`S`) — **written only through the HTL-007 `set_room_housekeeping_status` setter**, never directly |

No GSI is added. The HTL-018 GSIs (`GSI_HOTEL_CHECKIN` / `GSI_HOTEL_CHECKOUT` /
`GSI_HOTEL_STATUS`) and the HTL-006/007 `GSI_HK_STATUS` already exist; HTL-023 only triggers
their automatic re-projection by rewriting their key attributes (`status` for the reservation
status transition, `housekeeping_status` for the room flip).

### 3.2 Pydantic models (`app/models.py`)

Add adjacent to the HTL-022 `FrontDeskRow` / `FrontDeskListOut` / `OccupancySnapshotOut`
models (`docs/qloapps/FRONT_DESK_TICKETS.md:97-103,190-198`).

**`WalkInBookingIn`** — the walk-in create+check-in payload. Mirrors the HTL-018
`create_reservation` input shape so the inner create call can be a passthrough:

## 4. API / Service Design

### 4.1 Service additions: `app/services/hotel_front_desk.py`

All four functions are added to the existing `hotel_front_desk.py` file (created by HTL-022).
No second service file is created. Every function calls `_require_enabled()` first. No `if
S.dev_mode` branch anywhere (SECOPS-007, §7.1). The HTL-018 `create_reservation`, HTL-019
`check_in`, and HTL-007 `set_room_housekeeping_status` are imported into the module namespace
(via the cluster's `reservations` / `room_inventory` collaborator modules) so tests can patch
them at the `hotel_front_desk` namespace.

**Module-level imports (forward-dep collaborators)** — referenced as
`reservations.create_reservation`, `reservations.check_in`,
`room_inventory.set_room_housekeeping_status`. The action code calls them; it never inlines
their logic.

#### 4.1.1 `walk_in_booking`

```python
def walk_in_booking(
    hotel_id: str,
    *,
    room_type_id: str,
    checkin: str,
    checkout: str,
    occupancy_adults: int,
    occupancy_children: int,
    guest_name: str,
    guest_sub: str | None = None,
    assigned_room_ids: list[str] | None = None,
    total_cents: int | None = None,
    user_sub: str,
    **rate,
) -> dict:
```

**Behavior**:
1. `_require_enabled()`.
2. Create the reservation by delegating to the HTL-018 create path (the same create the
   booking storefront uses — reuses its availability decrement + total computation, never
   re-implemented, `docs/qloapps/FRONT_DESK_TICKETS.md:200-210`):
   ```python
   res = reservations.create_reservation(
       hotel_id=hotel_id, room_type_id=room_type_id,
       checkin=checkin, checkout=checkout,
       occupancy_adults=occupancy_adults, occupancy_children=occupancy_children,
       guest_name=guest_name, guest_sub=guest_sub,
       total_cents=total_cents, user_sub=user_sub, **rate,
   )
   ```
   If create raises (e.g., no availability → HTL-018's 409 oversell guard), the exception
   propagates unchanged (§5.3). The created reservation starts `status="confirmed"`,
   `version=1` (the HTL-018 META is written with `version=1` at create,
   `docs/qloapps/specs/HTL-018.md:214,420` — **not** `0`).

   > **Forward-dep contract reconciliation (the HTL-018 spec has since landed).** The
   > `create_reservation` call shape above mirrors the parent-ticket sketch
   > (`docs/qloapps/FRONT_DESK_TICKETS.md:200-204`), but the now-landed
   > `docs/qloapps/specs/HTL-018.md:348-360` has a **different, keyword-only** signature:
   > `create_reservation(*, hotel_id, guest_party_id, room_type_id, checkin, checkout, adults,
   > children=0, rooms=1, deposit_cents=0, user_sub)`. Field-name deltas `walk_in_booking` must
   > map onto: the guest is an opaque **`guest_party_id`** FK (Contacts/CUS/TEN), **not**
   > `guest_name` + `guest_sub`; occupancy is **`adults` / `children`**, not
   > `occupancy_adults` / `occupancy_children`; physical-room count is **`rooms`** (default 1);
   > and **there is no `total_cents` or `assigned_room_ids` create input** — `total_cents` is
   > computed by HTL-015 `compute_stay_price` inside create (`HTL-018.md:209,384`) and
   > `assigned_room_ids` starts `[]` (`HTL-018.md:202,408,506-508`), assigned only at check-in.
   > The `WalkInBookingIn` model (§3.2) and this delegation must be re-keyed to the HTL-018
   > input set; the `total_cents` "passthrough" framing (§5.11, §7.4) does **not** hold against
   > the landed HTL-018 (pricing is owned by HTL-015, invoked by HTL-018 — still never forked
   > here, so the money-safety conclusion stands, only the mechanism changes). Tracked as
   > Open-Q §10.6.
3. Immediately check it in via the HTL-019 transition and any supplied `assigned_room_ids`.
   Against the **landed** HTL-019 contract (`docs/qloapps/specs/HTL-019.md:379-403`, see the
   reconciliation note in §2.9) this is the generic `transition_reservation` entrypoint with a
   positional `target_status`, the `actor` kwarg, **no** caller-threaded `version` (HTL-019
   reads + CAS-bumps it internally), and a **required non-empty** `assigned_room_ids`:
   ```python
   checked = reservations.transition_reservation(
       res["reservation_id"],
       "checked_in",
       actor=user_sub,
       assigned_room_ids=assigned_room_ids,   # required & non-empty by HTL-019
   )
   ```
   (The parent-ticket sketch was `reservations.check_in(reservation_id, *, version,
   assigned_room_ids, user_sub)`; that function name/signature does **not** exist in the landed
   HTL-019 — §2.9.)
4. If `assigned_room_ids` were supplied, flip each assigned room via the HTL-007 setter (the
   same room-occupy flip `assign_room` performs, §4.1.2 step 5) — wrapped in `try/except` so a
   room-flip failure does not roll back the already-checked-in reservation (§5.6).
5. One `_audit("hotel.frontdesk.walk_in", user_sub, hotel_id=hotel_id,
   reservation_id=res["reservation_id"], room_type_id=room_type_id,
   assigned_room_ids=assigned_room_ids or [])`.
6. Return `{"reservation": _row_from_reservation(checked), "affected_rooms": [...]}` (the
   `FrontDeskActionOut` shape). The reservation ends `status="checked_in"`.

Wraps existing services — **no duplicated reservation/availability logic**.

#### 4.1.2 `assign_room`

```python
def assign_room(
    hotel_id: str,
    reservation_id: str,
    *,
    assigned_room_ids: list[str],
    version: int,
    user_sub: str,
) -> dict:
```

**Behavior**:
1. `_require_enabled()`.
2. Read the reservation via the HTL-018 `get_reservation(reservation_id)` (or
   `T.hotel_reservations.get_item(Key={"reservation_id": reservation_id, "sk": "META"})`).
   Raise `HTTPException(404, "Reservation not found")` if absent.
3. Version-gated write of the new assignment (the CAS one-winner idiom, §2.6):
   ```python
   try:
       T.hotel_reservations.update_item(
           Key={"reservation_id": reservation_id, "sk": "META"},
           UpdateExpression="SET assigned_room_ids = :rids, updated_at = :ts ADD version :one",
           ConditionExpression="version = :v",
           ExpressionAttributeValues={
               ":rids": assigned_room_ids, ":ts": now_ts(),
               ":one": 1, ":v": int(version),
           },
       )
   except ClientError as exc:
       if exc.response["Error"].get("Code") == "ConditionalCheckFailedException":
           raise HTTPException(status_code=409, detail="Reservation was modified concurrently")
       raise
   ```
4. For each **newly assigned** room (the set added vs. the prior `assigned_room_ids`), flip
   the `hotel_rooms` row's posture via the HTL-007 setter — the room becomes occupied (the
   exact target enum lives with HTL-007; the occupy posture is `dirty`-on-departure /
   in-use, `docs/qloapps/FRONT_DESK_TICKETS.md:216-220`):
   ```python
   for rid in assigned_room_ids:
       room_inventory.set_room_housekeeping_status(
           hotel_id, rid, housekeeping_status="dirty", user_sub=user_sub,
       )
   ```
   Each flip is wrapped `try/except` so a single bad room id does not abort the assignment
   already written (§5.6) — but a `set_room_housekeeping_status` 404 (unknown room) on the
   *first* assign surfaces as the action's error before the write where validation is needed
   (§5.4). (HTL-024's router validates the room exists; the service flips defensively.)
5. `_audit("hotel.frontdesk.assign_room", user_sub, hotel_id=hotel_id,
   reservation_id=reservation_id, assigned_room_ids=assigned_room_ids)`.
6. Re-read and return `{"reservation": _row_from_reservation(...), "affected_rooms": [...]}`.

#### 4.1.3 `change_room`

```python
def change_room(
    hotel_id: str,
    reservation_id: str,
    *,
    assigned_room_ids: list[str],
    version: int,
    user_sub: str,
) -> dict:
```

**Behavior** — the same shape as `assign_room` but for a reservation that **already** has
assignments (`docs/qloapps/FRONT_DESK_TICKETS.md:221-226`):
1. `_require_enabled()`.
2. Read the reservation; 404 if absent. Capture `prior = set(item.get("assigned_room_ids", []))`.
3. Compute the symmetric difference against `new = set(assigned_room_ids)`:
   - `freed = prior - new` (rooms dropped) → flip each back to `clean` (free) via the HTL-007
     setter.
   - `added = new - prior` (rooms added) → flip each to the occupy posture (`dirty`) via the
     HTL-007 setter.
   - `prior & new` (unchanged) → no room flip.
4. Version-gated write of the new `assigned_room_ids` (same CAS as §4.1.2 step 3 → 409 on
   stale version).
5. Apply the room flips (`freed` → `clean`, `added` → occupy), each `try/except` (§5.6).
6. `_audit("hotel.frontdesk.change_room", user_sub, hotel_id=hotel_id,
   reservation_id=reservation_id, freed=list(freed), added=list(added))`.
7. Re-read and return the `FrontDeskActionOut` shape (`affected_rooms` = the freed + added
   rooms).

#### 4.1.4 `room_move`

```python
def room_move(
    hotel_id: str,
    reservation_id: str,
    *,
    from_room_id: str,
    to_room_id: str,
    version: int,
    user_sub: str,
) -> dict:
```

**Behavior** — relocate a single **checked-in** guest
(`docs/qloapps/FRONT_DESK_TICKETS.md:227-231`):
1. `_require_enabled()`.
2. Read the reservation; raise `HTTPException(404, "Reservation not found")` if absent.
3. Validate the reservation is `checked_in`; otherwise raise `HTTPException(409, "Reservation
   is not checked in")` (a guest can only be *moved* while in-house).
4. Validate `from_room_id` is in `assigned_room_ids`; otherwise raise `HTTPException(404,
   "from_room_id is not assigned to this reservation")`.
5. Compute the new assignment: `new = [to_room_id if r == from_room_id else r for r in
   assigned_room_ids]` (swap exactly one id, preserving the rest).
6. Version-gated write of `new` (same CAS → 409 on stale version).
7. Free `from_room_id` (flip → `clean`) and occupy `to_room_id` (flip → `dirty`) via the
   HTL-007 setter, each `try/except` (§5.6).
8. `_audit("hotel.frontdesk.room_move", user_sub, hotel_id=hotel_id,
   reservation_id=reservation_id, from_room_id=from_room_id, to_room_id=to_room_id)`.
9. Re-read and return the `FrontDeskActionOut` shape (`affected_rooms` = the freed +
   occupied rooms).

### 4.2 Shared invariants across the four actions

- Every mutation calls `_require_enabled()` first (§2.4).
- Every assignment write is **version-gated** (optimistic-concurrency `version = :v` CAS →
  409 on conflict, §2.6).
- Every action emits exactly one front-desk `_audit(...)` event (the HTL-007 setter emits its
  own `hotel.room.housekeeping_status` audit per room flip — that is HTL-007's audit, not
  duplicated here).
- All room-side flips route through the HTL-007 setter — this service **never writes a
  `hotel_rooms` row directly** (one owner per table,
  `docs/qloapps/FRONT_DESK_TICKETS.md:235-237`).

### 4.3 Router endpoints (HTL-024 preview)

HTL-023 ships only the service layer. HTL-024 exposes these over HTTP on the
`/ui/hotels/{hotel_id}/front-desk` prefix (`docs/qloapps/FRONT_DESK_TICKETS.md:293-302`):

| `POST` | `/ui/hotels/{hotel_id}/front-desk/reservations/{reservation_id}/assign-room` | `require_admin_or_root_csrf` | `assign_room(hotel_id, reservation_id, assigned_room_ids=..., version=..., user_sub=user.sub)` |

## 5. Detailed Behavior & Edge Cases

### 5.1 Walk-in ends `checked_in` in one call

`walk_in_booking` creates a reservation (HTL-018, `status="confirmed"`) and immediately
transitions it to `checked_in` (HTL-019) — one front-desk action, no intermediate
`confirmed` state visible to the caller. The acceptance criterion
(`docs/qloapps/FRONT_DESK_TICKETS.md:243-246`) "status ends `checked_in`; it reuses (does
not re-implement) the reservation create + availability decrement" is satisfied: the create
is a passthrough to HTL-018, the check-in a passthrough to HTL-019.

### 5.2 Walk-in with explicit vs. deferred assignment

If `assigned_room_ids` are supplied, they flow into the HTL-019 `check_in` call **and** each
room is flipped via the HTL-007 setter (§4.1.1 step 4). If omitted, the reservation is
checked in **unassigned** (`assigned_room_ids=[]`) — the agent assigns later via `assign_room`
(`docs/qloapps/FRONT_DESK_TICKETS.md:206-210`). An unassigned check-in is a valid state.

### 5.3 Walk-in with no availability

If the inner HTL-018 `create_reservation` finds no availability, it raises its own error
(the HTL-018 oversell/availability 409 guard, the same single-writer conditional the booking
storefront hits). `walk_in_booking` does **not** catch it — the exception propagates to the
router, which surfaces it to the agent. No reservation is created, no check-in attempted, no
room flipped (the create failed before any of those). This is the "walk-in with no
availability" edge case (per the ticket assignment).

### 5.4 `room_move` to an out-of-service / occupied room

The room-side validity of the target is owned by HTL-006/007 — `room_move` calls the HTL-007
setter for `to_room_id`. Two cases:
- **`to_room_id` does not exist** → the HTL-007 `set_room_housekeeping_status` 404s ("Room not
  found", `docs/qloapps/specs/HTL-007.md` §5.1). `room_move` lets that 404 surface (a move to
  a non-existent room is invalid). Because the reservation `assigned_room_ids` write
  (version-gated) happens *before* the room flip (§4.1.4 step 6 before step 7), a target-room
  validation belongs in HTL-024's router (it checks the target room exists/is sellable before
  calling the service) — see §10.1.
- **`to_room_id` is `out_of_service`** (the room sellability `status`, HTL-006): HTL-023 does
  **not** itself block a move into an out-of-service room — the room sellability gate is an
  operational-policy decision. The recommended guard (HTL-024 router or a future policy
  setting) rejects a move to a `status=out_of_service` room with 409. Documented in §10.2.
- **`to_room_id` already occupied by another reservation**: there is no cross-reservation
  occupancy lock on a `hotel_rooms` row in this cluster (occupancy is derived from in-house
  reservations' `assigned_room_ids`, HTL-022 `occupancy_snapshot`). HTL-023 does not detect a
  double-booked room; the recommended guard (HTL-024 / future policy) checks the
  `occupancy_snapshot`-derived occupied set before the move. Documented in §10.3.

### 5.5 `room_move` rejects an unassigned `from_room_id` or non-checked-in reservation

`room_move` validates (§4.1.4 steps 3-4):
- reservation `status != "checked_in"` → `HTTPException(409, "Reservation is not checked in")`
  (a guest can only be moved while in-house, `docs/qloapps/FRONT_DESK_TICKETS.md:228-231`).
- `from_room_id not in assigned_room_ids` → `HTTPException(404, "from_room_id is not assigned
  to this reservation")`.
Both checks run **before** any write — a rejected move mutates nothing.

### 5.6 Room-flip failure never rolls back the reservation write

Every HTL-007 setter call in the four actions is wrapped `try/except` (mirroring the
EC2/K8s host-inventory `try/except` cleanup-failure-must-not-roll-back idiom, CLAUDE.md
"EC2 host-inventory lifecycle" / "K8s pod host-inventory lifecycle"). The reservation
`assigned_room_ids` write is the source of truth; a `hotel_rooms` housekeeping flip is a
best-effort side-effect. If a flip fails (e.g., room id typo), the reservation assignment is
still committed and the action returns successfully — the room board may transiently show a
stale housekeeping status, reconciled on the next explicit `set_room_housekeeping_status`.
**Exception** (§5.4): a genuinely invalid `to_room_id` for `room_move` is a caller error that
HTL-024's router validates before the service runs.

### 5.7 Version-conflict 409 (optimistic concurrency)

`assign_room` / `change_room` / `room_move` all guard the reservation write on `version =
:v`. If two front-desk agents load the same reservation (same `version`) and both submit, the
first write wins (bumps `version`); the second's `ConditionExpression` fails →
`HTTPException(409, "Reservation was modified concurrently")` and the second agent must reload
(`docs/qloapps/FRONT_DESK_TICKETS.md:233-234,248-249`). This is the inventory status-CAS
one-winner guard (`app/services/inventory.py:434-453`) applied to `version`. The losing call
mutates **nothing** (the conditional fails before the SET applies; no room flip is reached
because the `except` raises before §4.1.2 step 4).

### 5.8 `change_room` symmetric-diff correctness

`change_room` computes `freed = prior - new` and `added = new - prior` (set difference on the
two `assigned_room_ids` lists). Rooms in both sets are untouched (no redundant flip). Example:
prior `["101","102"]`, new `["102","103"]` → `freed={"101"}` (→ `clean`), `added={"103"}` (→
occupy), `"102"` unchanged. The acceptance criterion
(`docs/qloapps/FRONT_DESK_TICKETS.md:250-251`) "frees dropped rooms and occupies added rooms
(symmetric diff)" is satisfied.

### 5.9 Idempotency of a repeated assignment

Re-calling `assign_room` with the **same** `assigned_room_ids` but the **current** `version`
re-writes the identical set and bumps `version` (a no-op in `assigned_room_ids`, an advance in
`version`). Re-calling with a **stale** `version` (the version before the first call) → 409.
So a flaky client that retries with the original version is safely rejected (it must reload to
get the new version), and a retry with the fresh version is harmless. Room flips on a repeat
re-flip the same rooms to the same posture (the HTL-007 setter is idempotent in result,
`docs/qloapps/specs/HTL-007.md` §7.2).

### 5.10 No room row written outside the HTL-007 setter

HTL-023 never calls `T.hotel_rooms.update_item` / `put_item` directly. Every
`housekeeping_status` change goes through `room_inventory.set_room_housekeeping_status` (one
owner per table, `docs/qloapps/FRONT_DESK_TICKETS.md:235-237,256-257`). This keeps the
HTL-007 audit trail (`hotel.room.housekeeping_status`) and `GSI_HK_STATUS` re-bucketing
correct, and means the room-side enum can evolve in HTL-007 without touching this service.

### 5.11 `walk_in_booking` `**rate` passthrough

HTL-018 `create_reservation` may take rate-plan inputs (rate plan id, nightly rate, taxes)
in addition to `total_cents` (`docs/qloapps/FRONT_DESK_TICKETS.md:192-194`). `walk_in_booking`
threads any extra keyword args through `**rate` to the create call unchanged — it does not
inspect or compute rates (that is HTL-018's job, never forked, §7.4).

### 5.12 Reservation not found

`assign_room` / `change_room` / `room_move` all read the reservation first and 404 if the
`reservation_id` does not resolve to a META row. No write is attempted for a missing
reservation.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_front_desk.py` must contain **no** `if S.dev_mode` branch across any of
the four HTL-023 actions. The same code path (the HTL-018 `create_reservation`, HTL-019
`check_in`, HTL-007 `set_room_housekeeping_status`, and the version-gated
`T.hotel_reservations.update_item`) runs in dev (boto3 intercepted by moto in-process) and
prod (real DynamoDB). This mirrors the cross-cutting constraint
(`docs/qloapps/FRONT_DESK_TICKETS.md:59-61`: "Zero `if S.dev_mode` branches in business
logic; the same `T.*` handles in both environments") and the `app/services/inventory.py`
precedent (the only `dev_mode` reference there is a module docstring comment,
`app/services/inventory.py:27`).

### 7.2 Idempotency

- `walk_in_booking` — **not** idempotent by construction: each call creates a new reservation
  (HTL-018 `create_reservation` mints a new reservation row; whether *it* is idempotent on
  any natural key is HTL-018's contract, not HTL-023's). A double-submitted walk-in creates
  two reservations unless HTL-018's create is keyed idempotently. Callers (the HTL-024 dialog)
  must not blindly retry.
- `assign_room` / `change_room` / `room_move` — idempotent **in effect via the version gate**
  (§5.9): a retry with the now-stale original version is rejected (409); a retry with the
  fresh version re-writes the same set harmlessly. The version-CAS makes the write
  one-winner (the inventory terminal-status idiom, §2.6).
- The HTL-007 room flips are idempotent in result (re-applying the same housekeeping status
  produces the same room row, `docs/qloapps/specs/HTL-007.md` §7.2).

### 7.3 Security — ownership, auth boundary, CSRF

- **Auth boundary** (HTL-024 router): all four actions are mutations → `require_admin_or_root_csrf`
  (`app/auth/policy.py:100`) — `role ∈ {ADMIN, ROOT}` + cookie-CSRF
  (`docs/qloapps/FRONT_DESK_TICKETS.md:51-54,299-302`).
- **CSRF**: cookie-auth `POST` requires an `x-csrf-token` header matching the `ui_csrf`
  cookie, enforced by `require_admin_or_root_csrf`. Bearer-auth requests skip CSRF (CLAUDE.md
  auth contract).
- **Ownership**: parent-hotel ownership (the HTL-001 single-platform `owner_sub == user_sub`
  contract) is enforced by the underlying HTL-018/019 services and the HTL-007 setter (each
  reads the hotel `META` and checks ownership, `docs/qloapps/specs/HTL-007.md` §5.11). HTL-023
  passes `user_sub=user.sub` through to those collaborators; it does not re-implement the
  ownership check (single owner per concern). ROOT bypass follows the cluster convention.
- **No PII leakage**: `guest_sub` / `assigned_room_ids` are internal identifiers; the
  `FrontDeskActionOut` surfaces them to the admin console only (mutations are admin-gated).

### 7.4 Money-safety — billing is never forked

The only money field in HTL-023 is `total_cents`, which is a **passthrough** to the HTL-018
`create_reservation` (§5.11). HTL-023 does **not** import or call
`billing_shared.new_ledger_entry`, `settle_or_reverse_ledger`, `apply_balance_delta`, or
`compute_due`; it invokes no Stripe/PayPal/CCBill provider SDK; it never accesses the
`billing` table. All reservation pricing, availability decrement, and any folio/ledger entry
are owned by HTL-018 (and the Tier-3 folio/deposit cluster) — HTL-023 composes them, never
re-implements them (`docs/qloapps/FRONT_DESK_TICKETS.md:200-210`). There are therefore no
financial invariants to enforce in this ticket beyond "do not fork the money path."

### 7.5 Audit trail

Every action emits a best-effort `_audit()` event (swallows exceptions, never propagates):

| Event | When |
|---|---|
| `hotel.frontdesk.walk_in` | `walk_in_booking` success |
| `hotel.frontdesk.assign_room` | `assign_room` success |
| `hotel.frontdesk.change_room` | `change_room` success |
| `hotel.frontdesk.room_move` | `room_move` success |

Each room flip additionally emits HTL-007's own `hotel.room.housekeeping_status` audit (from
inside the setter) — not duplicated here.

## 10. Open Questions / Assumptions

1. **Target-room existence/sellability validation locus.** `room_move` and `assign_room`
   write the reservation `assigned_room_ids` *before* flipping the room (§4.1.4 step 6 before
   step 7), and the room flips are best-effort (§5.6). A genuinely invalid `to_room_id`
   (non-existent room) therefore commits an assignment to a phantom room. **Assumption**: the
   HTL-024 router validates the target room exists (via HTL-006 `get_room`) and is sellable
   before calling the service; alternatively, the service could pre-validate the target via
   `get_room` before the version-gated write. Recommended: pre-validate in the service for
   `room_move`/`assign_room` to keep the invariant at the owning layer. Flagged for HTL-024.

2. **Move into an `out_of_service` room.** HTL-023 does not itself block a move/assignment to
   a room whose sellability `status=out_of_service` (HTL-006). The ticket lists "move to
   out_of_service room" as an edge case. **Assumption**: the guard (reject with 409) lives in
   HTL-024's router or a future operational-policy setting, since out-of-service is a
   sellability-policy decision, not a data-integrity one. Documented in §5.4.

3. **Double-booked target room.** There is no cross-reservation occupancy lock on a
   `hotel_rooms` row in this cluster (occupancy is *derived* from in-house reservations'
   `assigned_room_ids`, HTL-022 `occupancy_snapshot`). A move/assign to a room already in
   another in-house reservation's `assigned_room_ids` is not detected by HTL-023.
   **Assumption**: detection (compute the occupied set from `occupancy_snapshot` and reject
   409) is an HTL-024 / future-policy concern. A hard DDB-level occupancy lock would require a
   new conditional-put pattern on the room row — out of HTL-023 scope. Documented in §5.4.

4. **Occupy housekeeping target enum.** §4.1.2 uses `housekeeping_status="dirty"` for the
   occupy posture and `"clean"` for the free posture, but the cross-cutting note
   (`docs/qloapps/FRONT_DESK_TICKETS.md:216-220`) says "the exact target enum lives with
   HTL-007." **Assumption**: occupy→`dirty` (a room in use becomes dirty-on-departure) and
   free→`clean`; if HTL-007 later introduces an explicit `occupied` value, swap the literals
   here — the action only *calls* the setter, so the change is one-line. Confirm with HTL-007.

5. **Walk-in idempotency.** Whether a double-submitted walk-in creates two reservations
   depends entirely on whether HTL-018 `create_reservation` is keyed idempotently (e.g., on a
   correlation id). **Assumption**: HTL-023 does not add a walk-in dedup key; the HTL-024
   dialog disables the submit button after first click and relies on HTL-018's create
   contract. Documented in §7.2.

6. **Forward-dep contract alignment with the landed HTL-018 / HTL-019 specs (CONFIRMED
   drift).** The HTL-018 and HTL-019 specs have since landed and their entrypoints differ from
   the parent-ticket sketch this spec was authored against. Concretely:
   - HTL-019 exposes **`transition_reservation(reservation_id, target_status, *, actor,
     reason="", assigned_room_ids=None)`** (`docs/qloapps/specs/HTL-019.md:379-403`) — there is
     **no `check_in(...)` function**; `actor` (not `user_sub`); **no `version` parameter**
     (HTL-019 reads + CAS-bumps internally); `→ checked_in` **requires non-empty**
     `assigned_room_ids` with `len == rooms`; and HTL-019 already flips rooms `occupied` via the
     HTL-006 `set_room_status` setter. See §2.9.
   - HTL-018 `create_reservation` is **`(*, hotel_id, guest_party_id, room_type_id, checkin,
     checkout, adults, children=0, rooms=1, deposit_cents=0, user_sub)`**
     (`docs/qloapps/specs/HTL-018.md:348-360`) — `guest_party_id` FK (not `guest_name` +
     `guest_sub`), `adults`/`children` (not `occupancy_*`), `rooms`, **no `total_cents` /
     `assigned_room_ids` input** (price is HTL-015-computed; `version` starts at **1**). See
     §4.1.1 step 2.
   **Resolution**: §3.2 `WalkInBookingIn`, §4.1.1 steps 2-4, §5.2, §5.11, and §7.4 must be
   re-keyed to these landed signatures when HTL-023 is implemented. The thin-orchestration
   intent and the money-not-forked conclusion are unchanged; only the exact kwargs and the
   redundant walk-in room flip (now owned by HTL-019) change. This supersedes the original
   "assume the sketch matches" assumption.
