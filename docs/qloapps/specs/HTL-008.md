# HTL-008 — Router: room-types / rooms / housekeeping sub-routes + registration

**Type**: Feature | **Priority**: P1 | **Estimate**: 1d
**Source**: `docs/qloapps/ROOMTYPES_ROOMS_HOUSEKEEPING_TICKETS.md` §HTL-008 + "Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A

---

## 1. Summary & Goal

HTL-008 exposes the HTL-005/006/007 Hotel-PMS service layer over HTTP. It extends the
`hotels_router` (prefix `/ui/hotels`, landed by the HTL-001 hotels cluster in
`app/routers/hotels.py`) with the **room-types**, **rooms**, and **housekeeping**
sub-routes — delivering exactly **15 endpoints** under the `/ui/hotels/{hotel_id}/...`
path tree. The router is a thin, policy-correct HTTP façade over an already-complete
service layer (`app/services/hotel_pms.py`); every handler delegates directly to a service
function defined by HTL-005 (Room Types), HTL-006 (Rooms), or HTL-007 (Housekeeping).

The design contributes three non-trivial concerns beyond simple delegation, every one of
them copied verbatim from the canonical router idiom in `app/routers/inventory.py`:

1. **Auth split** — read endpoints (`GET`) use `require_ui_session`
   (`app/services/sessions.py:330`); mutation endpoints (`POST`/`PUT`/`DELETE`) use
   `require_admin_or_root_csrf` (`app/auth/policy.py:100`) — role `∈ {ADMIN, ROOT}` plus
   cookie CSRF. This is the identical split applied at `app/routers/inventory.py:37` (read)
   and `:46`, `:63`, `:79` (mutations).
2. **Route-declaration order** — the literal `/room-types`, `/rooms`, `/housekeeping`
   sub-trees and their literal trailing segments (`/housekeeping`, `/assign`, `/complete`)
   must be declared so that FastAPI does not capture a literal segment as a dynamic path
   parameter. The `/{room_type_id}` and `/{task_id}` captures are declared **after** their
   sibling literals (the same literal-before-dynamic gotcha CLAUDE.md documents for KYC
   `/templates`-before-`/{case_id}` and audit-export `/schedules`-before-`/{export_id}`).
3. **Feature-flag short-circuit** — every handler calls `_require_enabled()` as its first
   statement; when `HOTEL_PMS_ENABLED=false` (the default) the entire surface returns HTTP
   404 and the platform is byte-for-byte unchanged.

With the flag off the router is still mounted (just as `inventory_router` is always mounted
— `app/main.py:877`) but every handler is a silent 404 no-op. No existing endpoint, table,
GSI, Pydantic model, or behavioral contract is modified. HTL-008 introduces **no new
DynamoDB tables, no new GSIs, and no new Pydantic models** — all of those land in
HTL-005/006/007.

This closes the "no HTTP surface" gap for the genuinely net-new hospitality spine
identified in `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A rows 2 (Room Type), 3 (Room), and
5 (Housekeeping): the service functions exist after HTL-005/006/007, but until HTL-008 they
are unreachable over HTTP and the HTL-009 frontend has nothing to call.

### 2.3 Canonical router idiom — `app/routers/inventory.py`

`app/routers/inventory.py` is the exact template to follow (verified against the live
file):

- **Router declaration** (`:29`): `inventory_router = APIRouter(prefix="/ui/inventory",
  tags=["inventory"])` — a single `APIRouter` with a `/ui/` prefix and a single tag.
- **Local `_require_enabled()` wrapper** (`:31-33`): a module-level function that delegates
  to `inv._require_enabled()`. Every handler calls it as its first statement (`:37`, `:50`,
  `:63`, `:79`, `:91`).
- **Auth split**: GET endpoints use `session=Depends(require_ui_session)`
  (`app/routers/inventory.py:37`); mutation endpoints use `user: AuthenticatedUser =
  Depends(require_admin_or_root_csrf)` (`:46`, `:63`, `:79`). The admin-only low-stock read
  at `:79` shows reads can also be admin-gated, but HTL-008 keeps all GETs on
  `require_ui_session` per the ticket table.
- **Service import** (`:25`): `from app.services import inventory as inv`. HTL-008 imports
  `from app.services import hotel_pms as hotel_pms` (or `as hpms`).
- **`main.py` import and registration** (`:311`, `:877`): `from app.routers.inventory import
  inventory_router` then `app.include_router(inventory_router)` inside `create_app()`.

`hotels_router`'s new handlers mirror this pattern at every level.

### 2.4 Auth dependencies

- **`require_ui_session`** (`app/services/sessions.py:330`) — async FastAPI dependency;
  validates the cookie-based UI session (or Bearer JWT) and returns a `dict` with
  `user_sub`, `role`, `admin_profile`, etc. (the return-shape `{"user_sub": ..., "role":
  ...}` is built at `app/services/sessions.py:~345`). Used for all read (GET) endpoints. A
  read handler reads the caller as `session["user_sub"]`.
- **`require_admin_or_root_csrf`** (`app/auth/policy.py:100-106`) — async FastAPI
  dependency; calls `enforce_cookie_csrf(request)` then `require_roles(user, {Role.ADMIN,
  Role.ROOT})`. Raises **HTTP 403** on CSRF failure (`app/auth/policy.py:95,97`), on missing
  role, or on role mismatch (`require_roles` at `app/auth/policy.py:49`). Used for all
  mutation (POST/PUT/DELETE) endpoints. A mutation handler reads the caller as `user.sub`.
- **`AuthenticatedUser`** dataclass (`app/auth/deps.py:126`) — the type returned by
  `require_admin_or_root_csrf`; carries `.sub` (the `user_sub`), `.role`, `.admin_profile`.

The split is identical to `app/routers/inventory.py` and to the HTL cross-cutting
constraint: "reads → `require_ui_session` (`app/services/sessions.py:330`); mutations →
`require_admin_or_root_csrf` (`app/auth/policy.py:100`) — identical split to
`app/routers/inventory.py:37,46,63,79`."

### 2.6 Feature-flag flow

`hotel_pms._require_enabled()` (carried into `hotel_pms.py` by HTL-001, copied verbatim

# app/services/inventory.py:50-56 (HTL-001 copies this into hotel_pms.py, reading

def _flag_on() -> bool:
    return bool(getattr(S, "inventory_reservations_enabled", False))

### 3.2 Query parameters

- `GET /ui/hotels/{hotel_id}/room-types` accepts:
  - `status: str = "active"` — `"active"` | `"archived"` (passed straight to
    `list_room_types`; an unrecognized value is filtered to an empty page by the service,
    not a 422 — see §5.6).
  - `cursor: Optional[str] = None` — opaque HMAC-signed pagination token from `encode_cursor`
    (`app/core/cursor.py:94`); silently restarts from the beginning if tampered (per
    `decode_cursor`, `app/core/cursor.py:103`).
  - `limit: int = 50` — page size (service-capped).
- `GET /ui/hotels/{hotel_id}/rooms` accepts `room_type_id: Optional[str] = None`
  (switches the service from the by-hotel PK query to the `GSI_ROOMTYPE` query),
  `status: Optional[str] = None`, `cursor`, `limit`.
- `GET /ui/hotels/{hotel_id}/housekeeping/tasks` accepts `status: Optional[str] = None`
  (routes to `GSI_HK_TASK_STATUS`), `assignee_sub: Optional[str] = None` (routes to
  `GSI_HK_ASSIGNEE`), `cursor`, `limit`.

No query parameters for any single-item GET, the housekeeping-status PUT, or the
assign/complete PUTs.

### 4.2 Declaration-order rule (FastAPI literal-before-dynamic)

**The declaration order within the router is load-bearing.** FastAPI matches routes against
incoming paths in the order they were added to the router. CLAUDE.md documents this exact
class of bug ("the `/schedules` routes are declared BEFORE `/{export_id}` … FastAPI matches
in declaration order, so a dynamic `/{export_id}` first would capture the literal
`schedules`"; and the KYC `/templates`-before-`/{case_id}` case). HTL-008 has three
literal-vs-dynamic conflicts under `/ui/hotels/{hotel_id}/`:

1. `/rooms/{room_id}/housekeeping` (PUT) vs `/rooms/{room_id}` (GET/PUT/DELETE) — the
   trailing literal `housekeeping` is one segment past `{room_id}`, so these do not
   collide at the FastAPI level (different segment counts), but declaring the literal-suffix
   route first is the safe, documented convention.
2. `/housekeeping/tasks` (the housekeeping sub-tree) vs `/rooms/{room_id}` — these differ
   in their first sub-segment (`housekeeping` vs `rooms`), so no capture occurs; still,
   declare the `/housekeeping/...` block as its own contiguous group.
3. `/housekeeping/tasks/{task_id}/assign` and `.../complete` (PUT) vs any bare
   `/housekeeping/tasks/{task_id}` — **HTL-008 declares no bare
   `/housekeeping/tasks/{task_id}` route**, so there is no GET-by-id to be captured; but the
   `/{task_id}/assign` and `/{task_id}/complete` literal-suffix routes must still be grouped
   together and declared with the literal suffix explicit so neither captures the other.

**Mandated declaration order** (within `hotels.py`, after HTL-001's hotel/amenity routes):

```
# --- room-types ---
GET    /{hotel_id}/room-types                       # list   (literal sub-tree root)
POST   /{hotel_id}/room-types                       # create
GET    /{hotel_id}/room-types/{room_type_id}        # get
PUT    /{hotel_id}/room-types/{room_type_id}        # update
DELETE /{hotel_id}/room-types/{room_type_id}        # archive
# --- rooms ---
GET    /{hotel_id}/rooms                            # list
POST   /{hotel_id}/rooms                            # create
PUT    /{hotel_id}/rooms/{room_id}/housekeeping     # status (literal suffix FIRST)
GET    /{hotel_id}/rooms/{room_id}                  # get    (bare dynamic AFTER suffix)
PUT    /{hotel_id}/rooms/{room_id}                  # update
DELETE /{hotel_id}/rooms/{room_id}                  # delete
# --- housekeeping ---
GET    /{hotel_id}/housekeeping/tasks               # list
POST   /{hotel_id}/housekeeping/tasks               # create
PUT    /{hotel_id}/housekeeping/tasks/{task_id}/assign     # assign   (literal suffix)
PUT    /{hotel_id}/housekeeping/tasks/{task_id}/complete   # complete (literal suffix)
```

Declaring `/rooms/{room_id}/housekeeping` **before** the bare `/rooms/{room_id}` group is
the single most important detail — it guarantees that even under a future FastAPI matching
change (or if a bare `/rooms/{room_id}/{anything}` is ever added) the housekeeping
sub-route is never shadowed.

### 4.3 Endpoint specifications

All 15 handlers call `_require_enabled()` as their first statement. The full path is the
router prefix `/ui/hotels` + the handler path below.

#### Room Types

```python
@hotels_router.get("/{hotel_id}/room-types")
async def list_room_types(
    hotel_id: str,
    status: str = "active",
    cursor: Optional[str] = None,
    limit: int = 50,
    session=Depends(require_ui_session),
) -> dict:
    _require_enabled()
    return hotel_pms.list_room_types(hotel_id, status=status, cursor=cursor, limit=limit)


@hotels_router.post("/{hotel_id}/room-types", response_model=RoomTypeOut, status_code=201)
async def create_room_type(
    hotel_id: str,
    body: RoomTypeIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> RoomTypeOut:
    _require_enabled()
    item = hotel_pms.create_room_type(
        hotel_id,
        name=body.name,
        description=body.description,
        base_occupancy_adults=body.base_occupancy_adults,
        base_occupancy_children=body.base_occupancy_children,
        max_occupancy=body.max_occupancy,
        bed_type=body.bed_type,
        size_sqft=body.size_sqft,
        base_nightly_rate_cents=body.base_nightly_rate_cents,
        photo_urls=body.photo_urls,
        user_sub=user.sub,
    )
    return RoomTypeOut(**item)


@hotels_router.get("/{hotel_id}/room-types/{room_type_id}", response_model=RoomTypeOut)
async def get_room_type(hotel_id: str, room_type_id: str, session=Depends(require_ui_session)) -> RoomTypeOut:
    _require_enabled()
    item = hotel_pms.get_room_type(hotel_id, room_type_id)
    if item is None:
        raise HTTPException(status_code=404, detail="Room type not found")
    return RoomTypeOut(**item)


@hotels_router.put("/{hotel_id}/room-types/{room_type_id}", response_model=RoomTypeOut)
async def update_room_type(
    hotel_id: str, room_type_id: str, body: RoomTypeUpdateIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> RoomTypeOut:
    _require_enabled()
    kwargs = {k: v for k, v in body.model_dump().items() if v is not None}
    item = hotel_pms.update_room_type(hotel_id, room_type_id, user_sub=user.sub, **kwargs)
    return RoomTypeOut(**item)


@hotels_router.delete("/{hotel_id}/room-types/{room_type_id}", response_model=RoomTypeOut)
async def archive_room_type(
    hotel_id: str, room_type_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> RoomTypeOut:
    _require_enabled()
    item = hotel_pms.archive_room_type(hotel_id, room_type_id, user_sub=user.sub)
    return RoomTypeOut(**item)
```

- `create_room_type` passes `user_sub=user.sub` so the service can validate parent-hotel
  existence + caller ownership (404 if missing/foreign — HTL-005 §4.1). On `POST`, status
  `201`.
- `get_room_type` 404s on `None` (unknown id), mirroring `get_inventory_item`
  (`app/routers/inventory.py:38-41`).
- `DELETE` is a **soft-archive** (sets `status="archived"`); the row remains in DynamoDB
  (HTL-005). `update_room_type`/`archive_room_type` raise `HTTPException(404)` for an
  unknown id — propagated naturally.

## 5. Detailed Behavior & Edge Cases

### 5.1 Route-ordering correctness (the load-bearing detail)

Per §4.2, `/rooms/{room_id}/housekeeping` is declared before the bare `/rooms/{room_id}`
group, and the `/housekeeping/...` sub-tree is its own contiguous block declared after the
`/rooms/...` block. The acceptance criterion is explicit: "`/housekeeping/tasks` is NOT
captured by `/rooms/{room_id}`, and `/{task_id}/complete` is NOT captured by a bare
`/{task_id}`." Because the two `/housekeeping/tasks/{task_id}/...` routes both carry an
explicit literal suffix (`/assign`, `/complete`) and there is no bare
`/housekeeping/tasks/{task_id}` route, neither shadows the other regardless of declaration
order between them — but they are still grouped together for clarity and future-proofing.

A unit test asserts ordering directly against `hotels_router.routes` (§9 case 12): the
index of the `/rooms/{room_id}/housekeeping` route is less than the index of the bare
`/rooms/{room_id}` route.

### 5.2 Flag-off behavior

When `HOTEL_PMS_ENABLED=false` (the default), every handler calls `_require_enabled()`
which delegates to `hotel_pms._require_enabled()`, raising `HTTPException(404, "Hotel PMS is
not enabled")` before any DynamoDB read or write. The router (or its handlers) is still
mounted on `hotels_router`; the flag check is at the handler level, not the mount level
(same pattern as `inventory_router`). With the flag off the platform is byte-for-byte
unchanged and produces zero DynamoDB traffic.

### 5.3 CSRF enforcement on mutation endpoints

`require_admin_or_root_csrf` (`app/auth/policy.py:100-106`) calls `enforce_cookie_csrf(request)`
before the role check. For cookie-authenticated (browser) requests: validates that both the
`x-csrf-token` header and the `ui_csrf` cookie are present and match (raising 403 at
`app/auth/policy.py:95` for missing token, `:97` for mismatch). For Bearer-token API
clients (no `ui_session` cookie): CSRF is not applicable and `enforce_cookie_csrf` returns
early — so mutation endpoints are reachable via Bearer-auth admins without a CSRF header,
consistent with every other admin endpoint in the platform.

### 5.4 Role rejection on mutations

A caller with a valid UI session but role `USER` (not `ADMIN`/`ROOT`) calling any
mutation endpoint is rejected with **403** by `require_roles(user, {Role.ADMIN, Role.ROOT})`
(`app/auth/policy.py:49`, invoked from `require_admin_or_root_csrf:106`). Reads
(`require_ui_session`) accept any authenticated user.

### 5.5 404 propagation from the service layer

The router does **not** re-implement existence/ownership checks. `get_room_type` /
`get_room` 404 on a `None` service return (the only router-level 404s). All other 404s
(unknown hotel, foreign hotel, unknown `room_type_id` on create, unknown room/task on
mutate) are raised by the service functions (HTL-005/006/007) and propagate naturally —
the handlers contain no `try/except` around them (mirroring `app/routers/inventory.py`,
which lets service `HTTPException`s propagate).

### 5.6 `status` query filtering, not validation

`list_room_types`/`list_rooms`/`list_hk_tasks` pass `status` straight to the service. An
unrecognized status value yields an empty page (the GSI/filter simply matches nothing), not
a 422 — the HTL services treat `status` as a filter, not a validated enum (contrast
`app/routers/inventory.py:84`, which 422s on an invalid low-stock status because that
endpoint validates the filter explicitly). HTL-008 keeps the simpler filter-through
behavior per the HTL-005/006/007 list-function contracts.

### 5.7 Decimal coercion in response models

`RoomTypeOut`/`RoomOut`/`HkTaskOut` integer-semantics fields (`created_at`, `updated_at`,
`base_occupancy_*`, `max_occupancy`, `size_sqft`, `base_nightly_rate_cents`, `floor`,
`due_at`, `completed_at`) must be plain `int`, not `Decimal`. The HTL-005/006/007 service
`*_out()` helpers coerce Decimal → int before returning dicts; the Pydantic models coerce
again on assignment. No extra coercion is needed in the router (same as PROP-004 §5.8).

### 5.8 `housekeeping_status` mutation only via the dedicated route

`update_room` (PUT `/rooms/{room_id}`) does **not** accept `housekeeping_status` —
`RoomUpdateIn` omits it (HTL-006), so a client cannot bypass the HTL-007 transition
function (which keeps `GSI_HK_STATUS` current + emits the
`hotel.room.housekeeping_status` audit). The only path to change `housekeeping_status` is
`PUT /rooms/{room_id}/housekeeping`.

### 5.9 List response shape passthrough

The three list handlers return the service dict verbatim (`{"room_types"|"rooms"|"tasks":
[...], "count": int, "cursor": str|None}`). FastAPI serializes the dict; the embedded
service dicts are already coerced to plain JSON-safe types by the service `*_out()` helpers,
so no per-item Pydantic re-validation is required (matching `list_low_stock` at
`app/routers/inventory.py:79-85`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

The HTL-008 handlers in `app/routers/hotels.py` contain **no** `if S.dev_mode` branches.
The router imports no dev-mode helpers and calls no mock paths; the same handler code runs
in dev (moto-intercepted boto3 via `app/core/dev_s3.py`) and prod (real DynamoDB). This
mirrors the contract in the HTL cross-cutting constraints ("Zero `if S.dev_mode` branches
in business logic; the same `T.*` handles in both environments") and the precedent set by
`app/routers/inventory.py` (zero `dev_mode` branches). The moto interception is transparent
to the router — no special casing is needed.

### 7.2 Idempotency

- `POST /room-types`, `POST /rooms`, `POST /housekeeping/tasks` — generate `uuid4().hex`
  ids server-side (HTL-005/006/007); not deduped on name (a hotel may legitimately hold two
  room types of the same name), so repeated POSTs create distinct rows. This is the
  documented Room Type / Room id contract (non-deterministic ids, HTL-005/006).
- `PUT /room-types/{id}`, `PUT /rooms/{id}` — idempotent in final state; `updated_at`
  advances on each call (acceptable).
- `PUT /rooms/{room_id}/housekeeping` — idempotent (setting the same status twice yields the
  same row; `updated_at` advances).
- `PUT /housekeeping/tasks/{id}/assign` — idempotent re-assign (HTL-007).
- `PUT /housekeeping/tasks/{id}/complete` — idempotent via the service's `status <> done`
  conditional guard (second call is a no-op, HTL-007).
- `DELETE /rooms/{id}` (archive-or-delete) — idempotent: deleting an already-deleted room
  returns `{"ok": False}` with no error.
- `DELETE /room-types/{id}` (archive) — idempotent: archiving an already-archived type
  returns `status="archived"` again.

### 7.3 Security

- **Mutation auth**: all POST/PUT/DELETE require `require_admin_or_root_csrf` — role `ADMIN`
  or `ROOT` plus CSRF for cookie-auth clients (§5.3, §5.4).
- **Read auth**: all GET require `require_ui_session` — any authenticated user. No
  ownership filter is applied at the router for reads (single-platform deployment
  assumption; see §10.1).
- **Ownership on writes**: service-layer checks (`create_room_type` /`create_room` validate
  parent hotel existence + caller ownership via `user_sub=user.sub`; HTL-005/006). The
  router passes `user.sub` to every mutation; the ownership check lives in the service, not
  the router.
- **Path traversal**: `hotel_id`, `room_type_id`, `room_id`, `task_id` are FastAPI path
  parameters, URL-encoded; they key DynamoDB items (`Key={...}`) — no filesystem paths or
  shell commands, no traversal risk.

### 7.4 Money-safety

HTL-008 touches **no billing table, billing service, or payment provider.** The only
monetary field anywhere in the surface is `base_nightly_rate_cents` on `RoomTypeIn`/`Out` —
an integer cents value stored on the Room Type row (money-as-cents convention); it is a
catalog price, not a charge. There is no charge, ledger write, balance delta, or provider
call in this ticket. The router imports only `hotel_pms`, the HTL Pydantic models, and the
auth dependencies — no `billing_shared`, no Stripe/PayPal/CCBill client. Reservations,
folios, and payment recording are separate out-of-scope HTL clusters
(`docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md`); when built they will route every monetary row
through `billing_shared.new_ledger_entry` (never fork billing). HTL-008 has zero financial
invariants to enforce.

### 7.5 Audit trail

The router does not call `_audit()` directly — audit events
(`hotel.room_type.created/updated/archived`, `hotel.room.created`,
`hotel.room.housekeeping_status`, `hotel.hk_task.created/completed`, etc.) are emitted by
the service functions via the `_audit()` lazy-import wrapper (copied into `hotel_pms.py` by
HTL-001 from `app/services/inventory.py:92-98`). Audit failure is swallowed and never
propagates to the HTTP caller.

## 8. Backward Compatibility & Migration

### 8.1 Additive-only changes

HTL-008 adds **15 handlers + 4 model imports** to the existing `app/routers/hotels.py`. No
existing endpoint, service function, DynamoDB table, GSI, Pydantic model, or configuration
key is modified. With `HOTEL_PMS_ENABLED=false` (the default), the new handlers all return
404 and produce zero DynamoDB traffic.

### 8.2 No DynamoDB migration

HTL-008 reads/writes the `hotels` and `hotel_rooms` tables declared by HTL-001/005/006/007
in `scripts/local-ddb-init.py`. No new `TableDef`, no new GSI, no `attr_types` change.
`just restart` in dev recreates both tables from the existing `TableDef`s automatically.

### 8.3 Production deployment sequence

1. Deploy HTL-001 with `HOTEL_PMS_ENABLED=false` — creates the `hotels` table; all hotel
   handlers 404.
2. Deploy HTL-005/006/007 with the flag still `false` — service functions + the
   `hotel_rooms` table available, still unreachable.
3. Deploy HTL-008 with the flag still `false` — the 15 handlers mounted on `hotels_router`,
   all 404.
4. Enable `HOTEL_PMS_ENABLED=true` after verifying both tables (and all GSIs) are healthy —
   all 15 endpoints become live.

This allows safe, incremental rollout with zero downtime and full rollback at any step by
toggling the flag.

### 8.4 Rollback

Operational rollback is setting `HOTEL_PMS_ENABLED=false` — the handlers remain mounted but
all return 404, disabling the feature with no redeploy. Code rollback removes the 15
handlers + 4 imports from `app/routers/hotels.py` (and, for the sibling-router variant,
reverts the two `main.py` lines).

### 8.5 Sibling-router fallback variant

If `app/routers/hotels.py` is owned by a different cluster ticket, HTL-008 instead creates
`app/routers/hotel_rooms.py` with `hotel_rooms_router = APIRouter(prefix="/ui/hotels",
tags=["hotels"])` + a local `_require_enabled()` delegating to
`hotel_pms._require_enabled()`, holding all 15 handlers, and adds two additive lines to
`app/main.py`: `from app.routers.hotel_rooms import hotel_rooms_router` (next to
`app/main.py:311`) and `app.include_router(hotel_rooms_router)` (next to
`app/main.py:877`). FastAPI merges two routers sharing the `/ui/hotels` prefix into one
path tree; the `/room-types`, `/rooms`, `/housekeeping` sub-trees live entirely on the
sibling router and do not collide with HTL-001's hotel/amenity routes (different
sub-segments). The declaration-order rule (§4.2) applies **within** the sibling router.

    `AuthenticatedUser`; assert `HTTPException(403)` from `require_admin_or_root_csrf`.
18. **Registration**: `from app.main import create_app; app = create_app()`; assert a route
    with path `/ui/hotels/{hotel_id}/room-types` exists in `app.routes` (and, for the
    sibling-router variant, that `hotel_rooms_router` is included).

### 9.3 E2E — `frontend/e2e/hotel-pms.spec.ts` (HTL-009 deliverable)

HTL-008's acceptance criteria are transitively verified by the HTL-009 E2E suite: room-type
CRUD via the card grid, room-grid CRUD, the housekeeping board (status transitions + task
assign/complete), CSRF header (`x-csrf-token`) on all POST/PUT/DELETE via
`injectAuth(page, "charlie_admin")`, and flag-off → all endpoints 404.

## 10. Open Questions / Assumptions

### 10.1 Multi-tenant isolation on GET endpoints

Read endpoints do not enforce that `session["user_sub"]` matches the hotel's `owner_sub`;
any authenticated user with a valid session can read any hotel's room types / rooms /
tasks by id. **Assumption**: single-platform deployment where admins/root operate the same
hotel-group entity (matching PROP-004 §10.1 and the inventory router's read model). If
per-hotel isolation is later required, an ownership check (`fetch hotel META → compare
owner_sub → 403`) is a non-breaking additive change to the read handlers.

### 10.2 `status` query value validation

List endpoints filter-through `status` rather than 422-validating it (§5.6). **Assumption**:
an unrecognized status yielding an empty page is acceptable (the HTL list services treat it
as a filter). If strict validation is desired, the handler can 422 on a value outside the
literal set (one-line change, mirroring `app/routers/inventory.py:84`).

### 10.3 `POST` idempotency on duplicate names

Creating two room types (or rooms) with identical names produces two distinct rows
(non-deterministic `uuid4().hex` ids, HTL-005/006). **Assumption**: this is the intended
contract (a hotel may legitimately hold two "Deluxe King" inventories or renumbered rooms).
No dedup is added.

### 10.4 `DELETE /rooms/{id}` — `{"ok": False}` vs 404

`delete_room` returns `{"ok": False}` (HTTP 200) for an unknown room, not 404 — the
no-raise idempotent contract (HTL-006, `host_inventory.delete_host` lineage).
**Assumption**: idempotent DELETE is preferred. A 404-on-miss variant is a one-line change
(`if not ok: raise HTTPException(404)`).

### 10.5 In-place extension vs sibling router

This spec is written for extending `hotels_router` in `app/routers/hotels.py` in-place (the
ticket's primary plan). **Assumption**: HTL-001 owns and exposes that router as the
extension point. If ownership constraints force the sibling-router variant, §8.5 applies and
two `main.py` lines are added. The endpoint surface, auth, flag, and ordering rules are
identical either way.

### 10.6 HTL-007 spec not yet authored

HTL-007's standalone spec is not yet written (the cluster spec set currently ends at
HTL-006). HTL-008 grounds the five housekeeping service signatures
(`set_room_housekeeping_status`, `create_hk_task`, `assign_hk_task`, `list_hk_tasks`,
`complete_hk_task`) and the five models on the **HTL-007 ticket** body
(`docs/qloapps/ROOMTYPES_ROOMS_HOUSEKEEPING_TICKETS.md` §HTL-007), which fixes them
precisely. If HTL-007's final spec renames any signature, the corresponding handler
delegation updates 1:1 (no router-shape change).
