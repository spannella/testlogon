## 1. Summary & Goal

HTL-028 is the final ticket in the public booking-engine storefront cluster (HTL-025..HTL-028). It delivers the **guest-facing, unauthenticated** React/TypeScript booking site — `BookingEnginePage` — and the full test suite (hermetic pytest + Playwright E2E) that validates the entire public funnel end-to-end against the HTL-027 router.

The gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C row 4) records the booking-engine storefront as **PARTIAL** — testlogon has "no hospitality storefront today" (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:10`). QloApps ships a public guest funnel — **search by dates+occupancy → room-type results with per-night availability + summed multi-night price → cart → guest details → checkout/payment → reservation** (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:7-9`). HTL-025/026/027 land the backend (browse service, stay-search/quote endpoint, cart→checkout→reservation + the public `booking_engine_router`). HTL-028 closes the presentational gap: the public funnel page itself, its public/unauth route, and the test coverage.

**Deliverables:**

1. **TypeScript types** mirroring the `app/models.py` HTL public models (HTL-025/026/027): `PublicHotel`, `PublicRoomType`, `StayQuote`, `StayQuoteResult`, `BookingCart`, `BookingCheckoutResult` and the search/guest input shapes (`frontend/src/api/types.ts`).
2. **API endpoint wrappers** in `frontend/src/api/endpoints/bookingEngine.ts`, calling the **public** `/booking-engine/*` routes (no `/ui` prefix, no session/CSRF required) via the shared axios-style client `frontend/src/api/client.ts`.
3. **One page component** under `frontend/src/pages/booking/`: `BookingEnginePage.tsx` — a single public funnel page (search form → results cards → guest-details form → checkout → confirmation).
4. **One public/unauth route** in `frontend/src/App.tsx` — `/book/:hotelId` (and `/book`), lazy-loaded **outside** the authenticated `<AppShell>` tree, exactly like `PublicEventPage` at `/event/:calendarId/:eventId` (`frontend/src/App.tsx:306`).
5. **Hermetic pytest** `tests/test_htl_booking_storefront.py` covering the entire HTL-025..HTL-027 backend stack (public browse, search/quote, cart→checkout→reservation, rate-limit, flag-off 404, route ordering).
6. **E2E spec** `frontend/e2e/hotel-booking-engine.spec.ts` — drives the public funnel with **no auth** against a seeded published hotel, requires `HOTEL_PMS_ENABLED=1`.

With `HOTEL_PMS_ENABLED=false` (the default, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:26-32`) the route is still reachable (routes are registered unconditionally) but every `/booking-engine/*` API call returns 404 — the backend is a flag-gated no-op per HTL-025's `_require_enabled()`. The page handles the 404 gracefully with a "Booking is not available" callout. This matches the inventory-vertical / PROP-005 pattern (`docs/open-property/specs/PROP-005.md:31`).

### 2.7 API client (`frontend/src/api/client.ts`)

`frontend/src/api/client.ts` exports `api` plus convenience methods `api.get` (`:290`), `api.post` (`:293`), `api.put` (`:300`), `api.del` (`:312`). The client auto-injects the `Authorization: Bearer` header from the auth store **only when a token exists** (`:168-171`: `if (accessToken && !headers.has("Authorization"))`) and the `X-CSRF-Token` header **only when the `ui_csrf` cookie exists** (`:179-181`). For an anonymous guest both are absent, so the public `/booking-engine/*` calls go out with no auth/CSRF — exactly what the unauth router expects. The endpoint wrappers reuse this client verbatim; **no custom fetch, no second axios instance** (same constraint as `getPublicEvent` reusing `api.get`).

### 2.8 401 handling does NOT break the public page

`frontend/src/api/client.ts` handles 401 → token refresh → logout (CLAUDE.md "Auth"). The public booking endpoints never return 401 (they take no auth dependency — `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:33-40`); they return **404** (flag off / unpublished hotel), **400** (`checkout <= checkin`), **409** (sell-out between add and checkout), or **429** (rate-limit). None of these trigger the logout path. The page uses `retry: false` so a 404 surfaces as the "not available" callout immediately (cf. `PublicEventPage`, §2.6).

## 4. API / Service Design

### 4.1 API endpoint wrappers (`frontend/src/api/endpoints/bookingEngine.ts`)

New file. Uses `api.get`/`api.post` from `frontend/src/api/client.ts` (`:290,:293`) pointed at the **public** `/booking-engine/*` routes (HTL-027 §router table, §2.3). No `/ui` prefix, no CSRF/session — these are unauth. The client only attaches `Authorization`/`X-CSRF-Token` when a token/cookie is present (§2.7), so for an anonymous guest the requests are clean.

```typescript
import { api } from "@/api/client";
import type {
  PublicHotel, PublicRoomTypeList,
  StayQuote, StaySearchInput,
  BookingCart, AddRoomInput, GuestDetailsInput,
  CheckoutInput, BookingCheckoutResult,
} from "@/api/types";

// --- Browse (HTL-025) ---
export const getPublicHotel = (hotelId: string) =>
  api.get<PublicHotel>(`/booking-engine/hotels/${hotelId}`);

export const listPublicRoomTypes = (hotelId: string) =>
  api.get<PublicRoomTypeList>(`/booking-engine/hotels/${hotelId}/room-types`);

// --- Search / quote (HTL-026) ---
export const searchStays = (input: StaySearchInput) =>
  api.get<StayQuote>("/booking-engine/search", {
    hotel: input.hotel,
    checkin: input.checkin,
    checkout: input.checkout,
    adults: String(input.adults),
    children: String(input.children),
    rooms: String(input.rooms),
  });

// --- Cart → checkout (HTL-027) ---
export const createBookingCart = (hotelId: string) =>
  api.post<BookingCart>("/booking-engine/cart", { hotel_id: hotelId });

export const getBookingCart = (cartId: string) =>
  api.get<BookingCart>(`/booking-engine/cart/${cartId}`);

export const addRoomToCart = (cartId: string, body: AddRoomInput) =>
  api.post<BookingCart>(`/booking-engine/cart/${cartId}/rooms`, body);

export const setGuestDetails = (cartId: string, body: GuestDetailsInput) =>
  api.post<BookingCart>(`/booking-engine/cart/${cartId}/guest`, body);

export const checkoutBookingCart = (cartId: string, body: CheckoutInput) =>
  api.post<BookingCheckoutResult>(`/booking-engine/cart/${cartId}/checkout`, body);
```

> Route-ordering note (consumed, not introduced): the literal `/booking-engine/search` and `/booking-engine/cart` are declared **before** the dynamic `/booking-engine/hotels/{hotel_id}` on the backend router (HTL-027, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:292-295`). The frontend wrapper paths above are exact and never collide; the ordering guard is asserted by the hermetic pytest (§9.1).

## 5. Detailed Behavior & Edge Cases

`BookingEnginePage.tsx` is a single funnel page driven by a small `step` state machine: `search` → `results` → `guest` → `review` → `confirmation`. It uses `useParams<{ hotelId?: string }>()` for the hotel id and `useAuthStore((s) => s.isAuthenticated)` only to optionally pre-fill the guest form for a logged-in visitor (the page works fully anonymously). All steps render inside a centered guest-storefront layout (no sidebar).

### 5.1 Step 1 — Search form (`search`)

On mount, if `hotelId` is present, `getPublicHotel(hotelId)` (`useQuery`, `retry: false`) loads the storefront header (name, star rating, address, photos, amenities) and `listPublicRoomTypes(hotelId)` loads the pre-search "shop window" room cards (base nightly rate displayed via `formatCents(base_rate_cents)`). The search form contains:
- **Date-range picker** — check-in / check-out (two `<Input type="date">` or a shadcn/ui calendar popover). Default check-in = today, check-out = tomorrow.
- **Occupancy steppers** — adults (default 1, min 1), children (default 0, min 0), rooms (default 1, min 1) — `<Button>` +/− steppers or numeric `<Input>`.

On submit it sets `searchInput` state and runs `searchStays(searchInput)`. **Client-side guard**: if `checkout <= checkin`, show an inline form error and do not call the API (the backend also returns **400** — `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:163-164` — and the page surfaces that detail too if it slips through).

### 5.2 Step 2 — Results cards (`results`)

`searchStays` returns the `StayQuote` envelope. The page renders **one shadcn/ui `<Card>` per `StayQuoteResult`** in `quote.results`:
- **Header**: room-type name + a `<Badge variant="outline">` for max occupancy (e.g. "Sleeps 4").
- **Body**: photo (first of `room_type.photos`), description, bed type, size, amenities chips (`<Badge>` per amenity); a per-night availability hint (e.g. "{available_rooms} rooms left" derived from `min(per_night[].rooms_available)` / `result.available_rooms`); and the **formatted multi-night total** `formatCents(result.total_price_cents, result.currency)` with a sub-label "{quote.nights} nights" (and an optional "{formatCents(total/nights)}/night avg").
- **Footer**: a **Select** `<Button>`.

**Unavailable room types do not appear** — the backend excludes zero-availability room types from `results` (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:170-172`); the FE renders `results` verbatim, so no client-side filtering is needed. **Empty results** (`results.length === 0`): render an empty state — "No rooms available for these dates. Try different dates." with a "Modify search" button returning to step 1.

**Select** flow: on first selection the page calls `createBookingCart(hotelId)` (if no `cartId` yet), then `addRoomToCart(cartId, { hotel_id, room_type_id, checkin, checkout, adults, children, rooms })`. **The client sends no price** — the server re-quotes at add-time to lock the authoritative price + confirm availability (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:247-249`). On success the page stamps the returned `BookingCart` into state and advances to step 3. A **409** at add-time (sold out between search and select) shows a toast "That room just sold out — please search again" and returns to step 1.

### 5.3 Step 3 — Guest-details form (`guest`)

React Hook Form + Zod (`zodResolver`), matching `frontend/src/pages/Login.tsx`:
```typescript
const guestSchema = z.object({
  name: z.string().min(1, "Name is required"),
  email: z.string().email("Valid email is required"),
  phone: z.string().min(1, "Phone is required"),
  address: z.object({
    line1: z.string().optional(),
    line2: z.string().optional(),
    city: z.string().optional(),
    region: z.string().optional(),
    postal_code: z.string().optional(),
    country: z.string().optional(),
  }).optional(),
});
```
On submit, `setGuestDetails(cartId, data)` (the backend creates/reuses a **Contact** by email — `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:252-255`). On success advance to step 4. The submit button is disabled while `useMutation.isPending` (§7.5). For a logged-in visitor the form pre-fills name/email from the auth store (best-effort, still editable).

### 5.4 Step 4 — Review + checkout (`review`)

Render the cart summary from `getBookingCart(cartId)` (or the in-state cart): hotel name, each line (room-type name, dates, nights, occupancy), and the formatted grand total `formatCents(cart.total_price_cents, cart.currency)`. A **Confirm & Pay** `<Button>` calls `checkoutBookingCart(cartId, { payment_method_token })`. In dev/E2E the money path settles via stripe-mock (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:58-61`); the page passes whatever payment token the funnel collects (for MVP a mock/test token is acceptable — the real card-collection widget is reused from the shop checkout, §10 Q4). Checkout edge cases:
- **409** — a line sold out between add and checkout (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:258-259`): toast "A room in your cart just sold out", return to step 2 with a fresh search.
- **Declined payment** — the backend creates **no reservation and holds no inventory** (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:315-316`); the FE shows a payment-error callout and keeps the cart intact for a retry.
- **429** — rate-limited: toast "Too many attempts, please wait a moment" honoring `Retry-After`.

### 5.5 Step 5 — Confirmation (`confirmation`)

On checkout success render a confirmation screen: a success badge, the `reservation_ids` (e.g. "Reservation #..."), the `order_id`, the formatted total, and the hotel/dates summary from `confirmation`. A "Book another stay" button resets the funnel (clears `cartId`/`searchInput`/`step`). A logged-in visitor optionally sees a "View in My Reservations" link (deep-links into the authenticated app — best-effort, not required for the public flow).

### 5.6 Flag-off / 404 behavior

When `HOTEL_PMS_ENABLED=false`, **every** `/booking-engine/*` call returns 404 (`_require_enabled()`, HTL-025/026/027). On the initial `getPublicHotel` 404 the page renders a centered callout — "Booking is not available right now." — and renders nothing else (no broken partial). Because the wrappers use `retry: false` (§2.6) the 404 surfaces immediately. The same callout covers an **unpublished / non-existent hotel** (also 404 — `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:99-102`), since the storefront cannot distinguish "flag off" from "hotel not published" (both are 404 by design — publication is the access gate, not a session).

### 5.7 Currency display (cents → formatted)

All money fields (`base_rate_cents`, `rate_cents`, `total_price_cents`) are integer cents displayed via the local `formatCents(cents, currency)` helper (§2.10). Currency comes from the per-result / per-cart `currency` field (defaults `"USD"`). No raw cents are ever shown to the guest.

### 5.8 Opaque cart-id is the only ownership token

The booking cart has no session; `cartId` is held in page state (and may be reflected in the URL as a query param `?cart=` for resilience across reloads, MVP-optional). There is no per-user filtering — anyone with the opaque id can read/mutate the cart (the documented public-funnel posture, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:298-301`). The FE never persists the cart id beyond the active funnel (no localStorage for MVP) to limit accidental sharing.

### 5.9 Loading + error states

`getPublicHotel`/`listPublicRoomTypes`/`searchStays`/`getBookingCart` each render `<Skeleton>` placeholders while loading. Network errors (non-404) render an inline retry callout. Mutation errors render a `toast.error(err.detail)` (the client surfaces `detail` from the API error body — `frontend/src/api/client.ts` error handling).

### 5.10 React Router does not have the FastAPI ordering problem

`/book/:hotelId` and `/book` are distinct React Router v6 patterns matched by specificity, not declaration order — no conflict. The FastAPI literal-before-dynamic rule applies only **server-side** on the `booking_engine_router` (HTL-027 §router, asserted by the pytest §9.1), not in `App.tsx`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no dev-mode branches

HTL-028's only backend touchpoints are the HTL-025/026/027 services/router, all of which already enforce SECOPS-007 (zero `if S.dev_mode` branches in business logic; the same `T.*` handles and the same stripe-mock-vs-real money path in both envs — `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:58-61`). The frontend has no concept of dev mode — it calls the same `/booking-engine/*` endpoints in both environments. The hermetic pytest (§9.1) never sets `S.dev_mode`; it toggles only `S.hotel_pms_enabled` and relies on moto intercepting boto3, identical dev/prod.

### 7.2 Security — public-by-design, but rate-limited

Every `/booking-engine/*` endpoint is unauthenticated (the public-funnel contract). Cart ownership is enforced solely by the opaque, hard-to-guess `booking_cart_id` (same posture as a public booking-link `link_id`, `app/routers/calendar.py:289-298`). The cart-mutation + checkout endpoints are per-client rate-limited via the DDB `_bucket_limit` (`app/services/rate_limit.py:60`, fail-open, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:184-193`) → **429** + `Retry-After` on exhaustion. The FE surfaces 429 gracefully but never tries to bypass it. No admin role gate exists on this funnel (contrast PROP-005's admin-only mutations) — the publication of the hotel (HTL-001 `published`) is the only access gate.

### 7.3 Security — no internal fields leak to the guest

The browse/quote projections (`PublicHotel`, `PublicRoomType`) are storefront-safe — they exclude `owner_sub`, raw status, and audit metadata (HTL-025 acceptance, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:128`). The TypeScript types in §3.1 mirror only those safe fields; the FE never references an internal field (there is none to reference).

### 7.4 Money-safety — client never sends a price; checkout reuses the existing money path

The funnel **never trusts a client-supplied price** (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:248-249,317-318`): `AddRoomInput` has no `*_cents` field (§3.1); the server re-quotes at add-time and **re-validates availability for every line at checkout** (409 on sell-out, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:258-259`). Checkout settles through the **existing** `shoppingcart.purchase_cart` (`app/services/shoppingcart.py:474`) → `commerce_order_service` money path — NOT a forked payment path (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:312-313`). The reservation (`create_reservation`, HTL-018) and the per-date inventory hold run **only after the order settles** — a declined payment creates no reservation and holds no inventory (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:315-316`). The FE displays only server-quoted totals (`formatCents`) and passes through a payment token; it performs no client-side price math.

### 7.5 Idempotency

The funnel mutations are guarded against double-submit at the UI layer: each Select / Continue / Confirm `<Button>` is disabled while its `useMutation.isPending` is true. The backend is the authoritative safety net — re-checkout of an already-settled cart is rejected by the order pipeline (the cart is consumed by `purchase_cart`). A double **Select** of the same room-type/dates is deduped by the backend re-quote/add semantics (HTL-027). The FE does not implement its own idempotency keys.

### 7.6 Audit trail

Backend writes emit best-effort audit via `_audit()` (modeled on `app/services/inventory.py:92-96`): `hotel.storefront.viewed` (browse, HTL-025) and `hotel.booking.created` (successful checkout, HTL-027, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:266`). HTL-028 adds no frontend-side audit emission — the backend is the authoritative audit source.
