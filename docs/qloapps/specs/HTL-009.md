**Type**: Feature | **Priority**: P2 | **Estimate**: 2.5d

## 1. Summary & Goal

HTL-009 is the final ticket in the QloApps Hotel-PMS room-types / rooms / housekeeping
cluster. It delivers the React/TypeScript frontend for the room-type manager, the
per-hotel room grid, and the housekeeping board, plus the full test suite (hermetic
pytest + Playwright E2E) that validates the entire HTL-005..HTL-009 stack end-to-end.

The gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A — "Hotels + Room Types +
Rooms + Housekeeping") lists the presentational deliverable as **"FE: room grid +
housekeeping board on the ticket-board pattern"**. The cluster doc spells this out as
three views: a **room-type manager** (card list of a hotel's bookable nightly products),
a **room grid per hotel** (physical room instances with status + housekeeping-status
badges), and a **housekeeping board on the ticket-board pattern** (three columns
`open`/`in_progress`/`done`, mirroring the ticket board columns at
`app/services/tickets.py:17,30`). HTL-009 closes those gaps for the Room Type, Room, and
Housekeeping layer. It does not cover per-date availability inventory, nightly rate plans,
reservations, front desk, the booking-engine storefront, folios, or KPI reports — those
are separate HTL clusters in the gap analysis (Tier 1/2/3).

**Deliverables:**

1. **TypeScript types** mirroring the `app/models.py` HTL models (HTL-005/006/007) in
   `frontend/src/api/types.ts`.
2. **API endpoint wrappers** calling the HTL-008 router via `frontend/src/api/client.ts`
   in a new file `frontend/src/api/endpoints/hotelRooms.ts`.
3. **Three page components** under `frontend/src/pages/hotels/` (co-located with the
   HTL-001 hotel pages):
   - `RoomTypesPage.tsx` — room-type manager (card list + New/Edit/Archive dialogs).
   - `RoomsPage.tsx` — per-hotel room grid (status + housekeeping-status badges + inline
     housekeeping setter + Add/Edit/Delete dialogs).
   - `HousekeepingBoard.tsx` — three-column board on the ticket-board pattern (Assign +
     Mark-done actions).
4. **Route registrations** in `frontend/src/App.tsx` (lazy-loaded under the protected
   `AppShell` tree).
5. **Sidebar nav items** in `frontend/src/components/layout/Sidebar.tsx`.
6. **Hermetic pytest** `tests/test_htl_rooms_housekeeping.py` covering HTL-005..HTL-008
   (flag off → 404, room-type create + parent-ownership 404, room CRUD + room-type FK
   validation + `delete_room` no-raise, `housekeeping_status` transition + GSI
   re-bucketing, HK-task create/assign/list-by-status/list-by-assignee/complete
   idempotency, pagination, router route-ordering).
7. **E2E spec** `frontend/e2e/hotel-rooms.spec.ts` (cookie-auth admin: create hotel →
   add room types + rooms → set a room dirty → create/assign/complete a housekeeping task
   → assert the room-type cards, room grid, and three-column board render).

With `HOTEL_PMS_ENABLED=false` (the default master flag landed in the HTL-001 cluster),
all three pages are reachable in the browser (routes are registered unconditionally) but
every API call returns 404 — the backend is a flag-gated no-op per HTL-001's
`_require_enabled()` (mirroring `app/services/inventory.py:54-56` and
`app/routers/inventory.py:32-34`). The sidebar nav items are always visible; the
flag-off state renders a user-facing "Hotel management is not enabled" callout. This
matches the pattern used by the Inventory vertical.

## 3. Data Model

HTL-009 is primarily a frontend ticket. It introduces **no new DynamoDB tables, no new
GSIs, and no new DynamoDB attributes**. All schema is delivered upstream: Room Types are
`ROOMTYPE#{id}` child rows on the `hotels` partition with `GSI_HOTEL_ROOMTYPES` (HTL-005);
Rooms are `ROOM#{id}` rows on the new `hotel_rooms` table with `GSI_ROOMTYPE` /
`GSI_HK_STATUS` (HTL-006); Housekeeping tasks are `HKTASK#{id}` child rows on
`hotel_rooms` with `GSI_HK_TASK_STATUS` / `GSI_HK_ASSIGNEE` (HTL-007). This section
documents the TypeScript types that mirror the backend Pydantic models.

## 4. API / Service Design

### 4.1 API endpoint wrappers (`frontend/src/api/endpoints/hotelRooms.ts`)

New file. Uses `api.get`/`api.post`/`api.put`/`api.del` from `frontend/src/api/client.ts`
(`:290-313`). No axios, no custom fetch. The paths mirror the HTL-008 endpoint table
(`docs/qloapps/ROOMTYPES_ROOMS_HOUSEKEEPING_TICKETS.md` §HTL-008) — all rooted at
`/ui/hotels/{hotel_id}/...`.

```typescript
import { api } from "@/api/client";
import type {
  RoomType, RoomTypeIn, RoomTypeUpdateIn, RoomTypeListOut,
  Room, RoomIn, RoomUpdateIn, RoomListOut,
  HousekeepingStatus, HousekeepingStatusIn,
  HkTask, HkTaskIn, HkTaskAssignIn, HkTaskListOut,
} from "@/api/types";

function clean(params?: Record<string, unknown>): Record<string, string> | undefined {
  if (!params) return undefined;
  return Object.fromEntries(
    Object.entries(params)
      .filter(([, v]) => v !== undefined && v !== "")
      .map(([k, v]) => [k, String(v)]),
  );
}

// --- Room Types (HTL-005 / HTL-008) ---
export const listRoomTypes = (hotelId: string, params?: { status?: string; cursor?: string; limit?: number }) =>
  api.get<RoomTypeListOut>(`/ui/hotels/${hotelId}/room-types`, clean(params));

export const createRoomType = (hotelId: string, body: RoomTypeIn) =>
  api.post<RoomType>(`/ui/hotels/${hotelId}/room-types`, body);

export const getRoomType = (hotelId: string, roomTypeId: string) =>
  api.get<RoomType>(`/ui/hotels/${hotelId}/room-types/${roomTypeId}`);

export const updateRoomType = (hotelId: string, roomTypeId: string, body: RoomTypeUpdateIn) =>
  api.put<RoomType>(`/ui/hotels/${hotelId}/room-types/${roomTypeId}`, body);

export const archiveRoomType = (hotelId: string, roomTypeId: string) =>
  api.del<RoomType>(`/ui/hotels/${hotelId}/room-types/${roomTypeId}`);

// --- Rooms (HTL-006 / HTL-008) ---
export const listRooms = (hotelId: string, params?: { room_type_id?: string; status?: string; cursor?: string; limit?: number }) =>
  api.get<RoomListOut>(`/ui/hotels/${hotelId}/rooms`, clean(params));

export const createRoom = (hotelId: string, body: RoomIn) =>
  api.post<Room>(`/ui/hotels/${hotelId}/rooms`, body);

export const getRoom = (hotelId: string, roomId: string) =>
  api.get<Room>(`/ui/hotels/${hotelId}/rooms/${roomId}`);

export const updateRoom = (hotelId: string, roomId: string, body: RoomUpdateIn) =>
  api.put<Room>(`/ui/hotels/${hotelId}/rooms/${roomId}`, body);

export const deleteRoom = (hotelId: string, roomId: string) =>
  api.del<{ ok: boolean }>(`/ui/hotels/${hotelId}/rooms/${roomId}`);

export const setRoomHousekeepingStatus = (hotelId: string, roomId: string, housekeeping_status: HousekeepingStatus) =>
  api.put<Room>(`/ui/hotels/${hotelId}/rooms/${roomId}/housekeeping`, { housekeeping_status } as HousekeepingStatusIn);

// --- Housekeeping tasks (HTL-007 / HTL-008) ---
export const listHkTasks = (hotelId: string, params?: { status?: string; assignee_sub?: string; cursor?: string; limit?: number }) =>
  api.get<HkTaskListOut>(`/ui/hotels/${hotelId}/housekeeping/tasks`, clean(params));

export const createHkTask = (hotelId: string, body: HkTaskIn) =>
  api.post<HkTask>(`/ui/hotels/${hotelId}/housekeeping/tasks`, body);

export const assignHkTask = (hotelId: string, taskId: string, assignee_sub: string) =>
  api.put<HkTask>(`/ui/hotels/${hotelId}/housekeeping/tasks/${taskId}/assign`, { assignee_sub } as HkTaskAssignIn);

export const completeHkTask = (hotelId: string, taskId: string) =>
  api.put<HkTask>(`/ui/hotels/${hotelId}/housekeeping/tasks/${taskId}/complete`, {});
```

### 4.2 React Query key conventions

| Query key | Description |
|---|---|
| `["hotelRoomTypes", hotelId, params]` | `listRoomTypes` — room-type manager card list |
| `["hotelRoomType", hotelId, roomTypeId]` | `getRoomType` — edit-dialog prefill |
| `["hotelRooms", hotelId, params]` | `listRooms` — per-hotel room grid |
| `["hotelRoom", hotelId, roomId]` | `getRoom` — room detail |
| `["hotelHkTasks", hotelId, { status: "open" }]` | `listHkTasks` — board "Open" column |
| `["hotelHkTasks", hotelId, { status: "in_progress" }]` | board "In Progress" column |
| `["hotelHkTasks", hotelId, { status: "done" }]` | board "Done" column |

Invalidation rules:
- After a room-type mutation (create/update/archive) → invalidate
  `["hotelRoomTypes", hotelId]` (prefix).
- After a room mutation (create/update/delete) → invalidate `["hotelRooms", hotelId]`.
- After `setRoomHousekeepingStatus` → invalidate `["hotelRooms", hotelId]` (the
  housekeeping-status badge in the grid re-renders; the room re-buckets under
  `GSI_HK_STATUS` server-side).
- After an HK-task mutation (create/assign/complete) → invalidate `["hotelHkTasks",
  hotelId]` (prefix) so all three columns refetch — a `complete` moves a card from
  `in_progress`/`open` to `done`, an `assign` changes the card's assignee chip.

## 5. Detailed Behavior & Edge Cases

### 5.1 `RoomTypesPage.tsx` — room-type manager

Reads `hotelId` via `useParams`. Calls `listRoomTypes(hotelId, { status: "active" })` via
`useQuery({ queryKey: ["hotelRoomTypes", hotelId, { status: "active" }], ... })`.

**Card grid**: responsive CSS grid (`grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 gap-4`).
Each card is a shadcn/ui `<Card>`:
- **Header**: room-type `name` (`CardTitle`) + a bed-type `<Badge variant="outline">`
  (e.g., "King").
- **Body**: occupancy summary `base_occupancy_adults + base_occupancy_children / max`
  (e.g., "2 + 1 / 4"); `size_sqft` (e.g., "350 sqft"); base nightly rate via
  `formatCents(roomType.base_nightly_rate_cents)` (e.g., "$189.00"); a photo thumbnail
  rendered from `photo_urls[0]` (placeholder when empty).
- **Footer**: "Edit" and "Archive" buttons (admin-only — §5.6).

**"New Room Type" dialog**: a `<Button>` opens a `<Dialog>` with React Hook Form + Zod:
```typescript
const roomTypeSchema = z.object({
  name: z.string().min(1, "Name is required"),
  description: z.string().optional().default(""),
```

The Zod `.refine` mirrors the backend validation
(`max_occupancy >= base_occupancy_adults + base_occupancy_children`, HTL-005) so the user
gets a client-side error before the 422. On submit, `useMutation({ mutationFn: (d) =>
createRoomType(hotelId, d), onSuccess: () => { queryClient.invalidateQueries({ queryKey:
["hotelRoomTypes", hotelId] }); toast.success("Room type created"); close(); } })`. On
API error, `toast.error(err.detail)`.

**Edit dialog**: same schema, prefilled from the selected room type, calls
`updateRoomType`. **Archive**: calls `archiveRoomType` (sets `status="archived"`
server-side); confirmation dialog ("Archive '{name}'? It is hidden from the active list;
existing rooms keep their `room_type_id`."). Archive is one-way in MVP — `RoomTypeUpdateIn`
has no `status` field, so there is no "Restore" UI (mirrors PROP-005 §5.5 / §10).

**Status filter**: a `<Select>` with "Active" / "Archived" / "All" drives the `status`
query param. Default `"active"`.

**Empty state**: when the list is empty → "No room types yet. Create the first bookable
room type for this hotel."

### 5.2 `RoomsPage.tsx` — room grid per hotel

Reads `hotelId` via `useParams`. Calls `listRooms(hotelId)` via `useQuery({ queryKey:
["hotelRooms", hotelId, filters], ... })`. Also calls `listRoomTypes(hotelId)` (to map
`room_type_id → name` for display and to populate the room-type `<Select>` in the
add/edit dialog).

**Grid**: responsive card grid or a shadcn/ui table; each room shows `room_number`,
`floor`, the resolved room-type name, a `status` badge (`available` → green /
`out_of_service` → red `<Badge variant="destructive">`), and a `housekeeping_status` badge
(see §5.5). **Filters**: a room-type `<Select>` (drives `room_type_id`) and a status
`<Select>` (drives `status`).

**Inline housekeeping setter**: each room card has a small `<Select>` (or a dropdown) of
the four `HousekeepingStatus` values; changing it fires
`useMutation({ mutationFn: (s) => setRoomHousekeepingStatus(hotelId, room.room_id, s),
onSuccess: () => queryClient.invalidateQueries({ queryKey: ["hotelRooms", hotelId] }) })`.
This is the per-room transition path (HTL-007 `set_room_housekeeping_status`), distinct
from the generic room update.

**Add/Edit room dialogs**: React Hook Form + Zod:
```typescript
const roomSchema = z.object({
  room_type_id: z.string().min(1, "Room type is required"),
  room_number: z.string().min(1, "Room number is required"),
  floor: z.coerce.number().int(),
  status: z.enum(["available", "out_of_service"]).default("available"),
});
```
Submit → `createRoom` / `updateRoom`, invalidating `["hotelRooms", hotelId]`.

**Delete**: confirmation dialog → `deleteRoom`. The backend returns `{ ok: true }` even
for an unknown room (the no-raise delete contract — `delete_room` returns `False` for an
unknown room, mirroring `host_inventory.delete_host`, `app/services/host_inventory.py:360`)
— the UI treats any 200 as success and invalidates the grid.

**Empty state**: "No rooms yet. Add the first physical room to this hotel."

### 5.3 `HousekeepingBoard.tsx` — board on the ticket-board pattern

Reads `hotelId` via `useParams`. Renders three columns — `open`, `in_progress`, `done` —
mirroring the ticket-board columns (`app/services/tickets.py:17,30` backend;
`frontend/src/pages/tickets/TicketKanbanBoard.tsx:30-35` `KANBAN_COLUMNS` FE idiom). Each
column drives a separate `listHkTasks(hotelId, { status })` query
(`["hotelHkTasks", hotelId, { status }]`). Per the CLAUDE.md "FilterExpression doesn't
reduce page size" / GSI gotcha, the backend buckets via `GSI_HK_TASK_STATUS` (HTL-007), so
each column is a cheap status-keyed query.

Each task is a `<Card>` showing: the room number (resolved from `room_id` via a
`listRooms` lookup, falling back to the raw `room_id`), the assignee chip
(`assignee_sub` or "Unassigned"), the due time (`due_at` formatted; "—" when `0`), and
`notes`.

**Column rendering**: a column header `<Badge>`/label with a per-column accent color (cf.
`TicketKanbanBoard.tsx:30-35` `color` field) and a task count.

**Actions** (admin-only — §5.6):
- **Assign**: an "Assign" button on each `open`/`in_progress` card opens a small `<Dialog>`
  with an `assignee_sub` input (or a staff `<Select>` if a staff directory is available)
  → `assignHkTask(hotelId, task.task_id, assignee_sub)`. Re-assign is idempotent (HTL-007).
- **Mark done**: a "Mark done" button on each non-`done` card →
  `completeHkTask(hotelId, task.task_id)`. The backend uses a conditional `status <> done`
  guard, so a double-click is a safe no-op (idempotent, HTL-007); the UI disables the
  button while `isPending`.
- **New Task**: a top-level "New Task" button opens a `<Dialog>` (room `<Select>`,
  optional assignee, optional due date/time, notes) → `createHkTask`.

MVP uses Assign/Mark-done buttons (not drag-and-drop) to keep the board simple and to keep
the status transitions explicit (`open → assign → in_progress → complete → done`). A later
iteration MAY adopt the `@dnd-kit` drag machinery already used by
`TicketKanbanBoard.tsx:2-14` — but HTL-007's task lifecycle is `open`/`in_progress`/`done`
driven by `assign` and `complete`, not free-form column drags, so button actions are the
faithful MVP. Any task mutation invalidates `["hotelHkTasks", hotelId]` (prefix) so all
three columns refetch.

### 5.4 Base nightly rate / due-date display

`base_nightly_rate_cents` is integer cents (e.g., `18900` = $189.00), displayed via a
local `formatCents` copy (§2.10). `due_at` / `completed_at` are Unix-second integers
(`now_ts()`-scale, `app/core/time.py:2`); `0` is the "none" sentinel and renders as "—".
Non-zero timestamps render with `new Date(due_at * 1000).toLocaleString()`.

### 5.5 Housekeeping-status badge colors

| `housekeeping_status` | Badge style |
|---|---|
| `clean` | green — `<Badge className="bg-green-100 text-green-800">Clean</Badge>` |
| `dirty` | yellow — `<Badge className="bg-yellow-100 text-yellow-800">Dirty</Badge>` |
| `inspected` | blue — `<Badge className="bg-blue-100 text-blue-800">Inspected</Badge>` |
| `out_of_service` | red — `<Badge variant="destructive">Out of service</Badge>` |

Room `status` badges: `available` → green/secondary; `out_of_service` → destructive.
Bed-type and the room-type-name chips use `<Badge variant="outline">`.

### 5.6 Admin-only mutation controls

Per §2.11, derive `isAdmin` from the JWT: `const role =
getRoleFromAccessToken(useAuthStore(s => s.accessToken)); const isAdmin = role === "admin"
|| role === "root";`. Hide "New Room Type" / "Edit" / "Archive" (RoomTypesPage),
"Add Room" / "Edit" / "Delete" / inline housekeeping setter (RoomsPage), and
"New Task" / "Assign" / "Mark done" (HousekeepingBoard) for non-admin sessions. Reads
(`list*`, `get*`) work for any UI session (`require_ui_session` on the GET endpoints,
HTL-008) so USER-role staff can still view the boards; only mutations are gated. This
prevents confusing 403s.

### 5.7 Flag-off (404) behavior

The frontend never reads the `HOTEL_PMS_ENABLED` value directly — it infers "flag off"
from a 404 on any HTL API call. Each page's primary `useQuery` (`listRoomTypes`,
`listRooms`, `listHkTasks`) renders a centered callout on a 404: "Hotel management is not
enabled on this platform." (or "Hotel not found or hotel management is not enabled." when
the hotel itself is missing). This is the only content rendered when the flag is off — no
half-rendered grid. Loading states use `<Skeleton>` placeholders.

### 5.8 Pagination

`listRoomTypes`, `listRooms`, and `listHkTasks` are cursor-paginated (HTL-005/006/007 all
return `{ ..., count, cursor }`). For MVP each view does a single-page fetch with
`limit=50`. When a `cursor` is returned, a "Load more" button at the bottom of the grid /
column triggers a follow-up fetch with the next cursor (acceptable over infinite scroll
for MVP). A single hotel rarely exceeds 50 room types; rooms and tasks may, so "Load more"
is wired for `RoomsPage` and `HousekeepingBoard`.

### 5.9 Room-type resolution in the room grid / board

The room grid and board display the human-readable room-type `name` and `room_number`,
but the `Room` / `HkTask` rows carry only `room_type_id` / `room_id`. Both pages fetch
`listRoomTypes(hotelId)` and `listRooms(hotelId)` once and build `Map`s
(`room_type_id → name`, `room_id → room_number`) for O(1) lookup, falling back to the raw
id when a referenced entity is missing (e.g., an archived room type). No extra per-row
API call.

### 5.10 React Router specificity (no FastAPI-style capture problem)

React Router v6 matches by specificity, not declaration order, so the three sibling routes
`hotels/:hotelId/room-types`, `hotels/:hotelId/rooms`, `hotels/:hotelId/housekeeping` never
conflict — `room-types` / `rooms` / `housekeeping` are static segments under a single
`:hotelId` param. The literal-before-dynamic ordering rule applies only at the **backend**
HTL-008 router layer (`/room-types`/`/rooms`/`/housekeeping` literals declared before
`/{room_type_id}`/`/{room_id}`/`/{task_id}`, and `/assign`/`/complete` before a bare
`/{task_id}` — same gotcha as the KYC `/templates`-before-`/{case_id}` and audit-export
`/schedules`-before-`/{export_id}` ordering in CLAUDE.md), tested in §9.1.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no dev-mode branches in backend

HTL-009 is primarily a frontend ticket. Its backend interaction is solely through the
HTL-008 router and HTL-005/006/007 service functions, all of which enforce SECOPS-007 (zero
`if S.dev_mode` branches; the same `T.*` handles in dev and prod, moto intercepting boto3
in dev — per the cross-cutting constraints in
`docs/qloapps/ROOMTYPES_ROOMS_HOUSEKEEPING_TICKETS.md`, mirroring
`app/services/inventory.py:27-29`). The frontend has no concept of dev mode — it calls the
same API in both environments.

### 7.2 SECOPS-007 — hermetic pytest does not use `dev_mode`

`tests/test_htl_rooms_housekeeping.py` toggles `S.hotel_pms_enabled` via
`object.__setattr__` but never sets `S.dev_mode`. All service calls go through the same
DynamoDB code path with moto intercepting boto3 — identical to every existing hermetic
test.

### 7.3 Security — admin-only mutations + CSRF

All create/update/archive/delete/assign/complete operations are gated by
`require_admin_or_root_csrf` at the HTL-008 router layer (`app/auth/policy.py:100`). The FE
mutation wrappers are callable by any authenticated session, but the backend returns 403
for non-admin callers and for cookie-auth requests missing the `X-CSRF-Token` header. The
UI hides mutation controls from USER-role sessions (§5.6) and the axios client injects the
CSRF header automatically from the `ui_csrf` cookie (`frontend/src/api/client.ts:179,181`).
Reads use `require_ui_session` (`app/services/sessions.py:330`).

### 7.4 Money-safety — HTL-009 does not touch billing

HTL-009 renders `base_nightly_rate_cents` as a display value only (via `formatCents`) — it
is the catalog rate, NOT a charge. No HTL-009 mutation touches `billing_shared.py`,
`new_ledger_entry`, `apply_balance_delta`, or any payment provider. Reservation pricing,
folios, and charges are out of scope (separate HTL clusters). This separation is
intentional: `hotelRooms.ts` never imports from `api/endpoints/billing.ts`, and the
HTL-005/006/007 service functions never call `billing_shared`.

### 7.5 Idempotency

- `createRoomType` / `createRoom` use `uuid4().hex` ids server-side (HTL-005/006), so a
  double-submit creates two rows — the UI disables the submit button while
  `useMutation.isPending` to prevent accidental double-creates (a hotel may legitimately
  hold two room types with the same name, per the HTL-005 id contract, so backend
  dedup-by-name is intentionally absent).
- `assignHkTask` is idempotent (re-assigning the same staffer is a no-op, HTL-007).
- `completeHkTask` is idempotent via the conditional `status <> done` guard (HTL-007) — a
  replay returns the already-done task without error; the FE disables the button while
  pending and treats any 200 as success.

### 7.6 Audit trail

Backend mutations emit best-effort audit events via the `_audit()` lazy-import wrapper
(modeled on `app/services/inventory.py:92-98`): `hotel.room_type.created`,
`hotel.room.created`, `hotel.room.housekeeping_status`, `hotel.hk_task.created`,
`hotel.hk_task.completed`, etc. (HTL-005/006/007). HTL-009 adds no frontend-side audit
emission — the backend is the authoritative audit source.

**Prerequisites**: `HOTEL_PMS_ENABLED=true` in the backend `.env.local`; standard E2E
stack (`just up` + seeded sessions).

**Auth**: `injectAuth(page, "charlie_admin")` (admin session, `role=admin`) for cookie
auth; `newIdentityPage(browser, "charlie_admin")` builds the page context. Mutations send
the `x-csrf-token: sess.csrf_token` header (lowercase, matching the backend
`ui_csrf_header_name` default and the tickets-spec pattern at
`frontend/e2e/tickets.spec.ts:101,117`). `page.request` carries the cookie session for
direct API calls (the `apiPost`/`apiGet`/`apiDelete` helpers from
`frontend/e2e/tickets.spec.ts:96-117`).

**Section 1 — Hotel + Room Type API (admin)**

Uses `page.request` for direct API calls (cookie + CSRF):
- (T1) `POST /ui/hotels` (HTL-001) → 200, capture `hotel_id`.
- (T2) `POST /ui/hotels/{hotel_id}/room-types` with a valid payload → 200, capture
  `room_type_id`, `status="active"`.
- (T3) `GET /ui/hotels/{hotel_id}/room-types` → list contains the created room type.
- (T4) `POST .../room-types` with `max_occupancy < adults + children` → 422.
- (T5) `PUT .../room-types/{room_type_id}` updating `base_nightly_rate_cents` → 200,
  new value in response.

**Section 2 — Room API**
- (T6) `POST /ui/hotels/{hotel_id}/rooms` referencing `room_type_id` → 200, capture
  `room_id`, `housekeeping_status="clean"`.
- (T7) `POST .../rooms` with an unknown `room_type_id` → 404.
- (T8) `GET .../rooms` → list contains the new room (and only `ROOM#` rows).
- (T9) `PUT .../rooms/{room_id}/housekeeping` with `housekeeping_status="dirty"` → 200.
- (T10) `GET .../rooms?status=available` filter returns the room.
- (T11) `DELETE .../rooms/{room_id}` → 200; a second delete also returns 200 (no-raise).

**Section 3 — Housekeeping task API**
- (T12) `POST .../housekeeping/tasks` with `{ room_id }` → 200, `status="open"`.
- (T13) `PUT .../housekeeping/tasks/{task_id}/assign` with `{ assignee_sub }` → 200,
  assignee set.
- (T14) `GET .../housekeeping/tasks?status=open` → contains the task.
- (T15) `PUT .../housekeeping/tasks/{task_id}/complete` → 200, `status="done"`; a second
  complete → 200 (idempotent).

**Section 4 — RoomTypesPage UI**
- (T16) Navigate to `/hotels/{hotel_id}/room-types` (admin auth); assert a "Room Types"
  heading is visible.
- (T17) A room-type card is visible with the name, a bed-type badge, occupancy summary,
  and the base nightly rate as formatted currency (e.g., "$189.00").
- (T18) "New Room Type" button opens the dialog; fill the form; submit; assert a success
  toast and the new card appears.

**Section 5 — RoomsPage UI**
- (T19) Navigate to `/hotels/{hotel_id}/rooms`; assert a "Rooms" heading and the room grid.
- (T20) The room card shows `room_number`, the resolved room-type name, a status badge,
  and a housekeeping-status badge reflecting `dirty` (yellow).
- (T21) The inline housekeeping setter changes the status to `clean`; assert the badge
  updates.
- (T22) "Add Room" dialog: fill `room_number`/`floor`/room-type/status; submit; assert the
  new room card.

**Section 6 — HousekeepingBoard UI**
- (T23) Navigate to `/hotels/{hotel_id}/housekeeping`; assert all three column headers
  ("Open", "In Progress", "Done") render.
- (T24) A task card appears in the "Open" (or "In Progress") column with the room number
  and assignee chip.
- (T25) "Mark done" on the card moves it to the "Done" column (board refetch); the
  destination column shows the card.

## 10. Open Questions / Assumptions

1. **Response wrapper shapes.** This spec assumes the HTL-008 router wraps the service
   lists as `{ room_types/rooms/tasks: [...], count, cursor }` (the `{items, count, cursor}`
   shape per HTL-005/006/007 and CLAUDE.md `host_inventory.list_hosts`). If any endpoint
   returns a plain array (cf. the CLAUDE.md "messages return a plain array" gotcha), the
   `RoomTypeListOut`/`RoomListOut`/`HkTaskListOut` typings and the `useQuery` `select`
   logic must be adjusted. **Re-verify against the actual HTL-008 router on merge.**

2. **Standalone routes vs. hotel-detail tabs.** This spec ships three standalone routes
   (`/hotels/:hotelId/room-types`, `/rooms`, `/housekeeping`). If the HTL-001 cluster ships
   a hotel-detail page (`/hotels/:hotelId`) with a tab strip, the three views may instead
   be tabs on that page (HTL-009 §HTL-009 explicitly allows "or as tabs on the HTL-001
   hotel-detail route"). **Assumption**: standalone routes for MVP, to avoid coupling to
   the HTL-001 FE shape; convertible to tabs without API changes.

3. **Staff directory for HK-task assignment.** `assign_hk_task` takes a raw `assignee_sub`.
   MVP renders a free-text `assignee_sub` input. A staff `<Select>` requires a staff-roster
   endpoint not in this cluster's scope. **Assumption**: free-text input for MVP.

4. **Field set / validation parity.** The TypeScript `*In` shapes and the Zod schemas
   mirror the HTL-005/006/007 Pydantic models as documented in the cluster doc, but the
   real `app/models.py` HTL models do not yet exist. **Re-verify field names, literals
   (`bed_type`, statuses), and required/optional flags against `app/models.py` on merge.**

5. **`HousekeepingBoard` drag-and-drop.** MVP uses Assign/Mark-done buttons, not `@dnd-kit`
   drags, because the HTL-007 lifecycle is `assign`/`complete`-driven, not free-form column
   moves. A later iteration MAY adopt the `TicketKanbanBoard.tsx` `@dnd-kit` machinery.
   **Assumption**: button actions for MVP.

6. **`i18nKey` translations.** The sidebar `NavItem` has an optional `i18nKey`
   (`Sidebar.tsx:87`). If a translation file exists, add `nav.hotels` (etc.); otherwise the
   `label` is the fallback. **Assumption**: add keys if a translation file exists.

7. **Bed-type / status display labels.** Stored literals (`king`, `out_of_service`, …) need
   human-readable labels. **Assumption**: a local mapping in each component file (e.g.,
   `{ king: "King", out_of_service: "Out of service" }`), no i18n key for MVP.
