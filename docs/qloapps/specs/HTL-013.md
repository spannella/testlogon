## 1. Summary & Goal

HTL-013 is the final ticket in the QloApps per-date availability inventory cluster (HTL-010 → HTL-011 → HTL-012 → HTL-013). It delivers the React/TypeScript **availability calendar grid** UI and the full test suite (hermetic pytest + Playwright E2E) that validates the entire HTL-010..HTL-013 stack end-to-end.

The gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §B) records the presentational rows this ticket closes as **MISSING**:
- "Availability calendar (bookable dates + remaining room counts)" (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:84`) — "calendar (`calendar.py`) is appointment-slot/rrule-recurrence, not room-night inventory".
- "Overbooking controls + min/max availability per date" (`:86`) — "inventory hard-stops at `available >= qty`; no per-date caps".
- "Blocking/holding rooms for dates" (the `held` lifecycle surfaced by the block/hold dialog) and "Per-room-type per-date available-rooms inventory" (`:83`) — the grid's per-cell remaining count is the only UI surface for that net-new primitive.

The deliverable is a **room-type rows × date columns** grid: each cell shows the remaining sellable count for a `(room_type, date)`, color-coded sold-out / low / open with held/overbooked badges. Admin-only dialogs (gated on the JWT role, §7.3) drive `setTotalRooms`, `holdRooms`, and `setOverbooking`. The page is the human-facing window onto the HTL-012 router; OFBiz inventory (the structural analogue we contrast, not reuse) has **no calendar surface** — its UI is a single per-SKU stock number (`docs/ofbiz/specs/OFB-003.md`; the gap analysis says it bluntly at `:83`: "inventory (OFB-003) is `(sku, location)` scalar `on_hand`/`reserved` — no date dimension").

**Deliverables:**
1. **TypeScript types** mirroring `app/models.py` HTL models — `AvailabilityDay`, `AvailabilityCalendar`, `AvailabilityCheck`, `Hold` + the in/set shapes — appended additively to `frontend/src/api/types.ts`.
2. **API endpoint wrappers** in a new file `frontend/src/api/endpoints/hotelAvailability.ts` calling the HTL-012 router through `frontend/src/api/client.ts`.
3. **One page component** `AvailabilityCalendarPage.tsx` under `frontend/src/pages/hotels/` — the grid + the three admin dialogs.
4. **Route registration** in `frontend/src/App.tsx` (`/hotels/:hotelId/availability`, lazy-loaded).
5. **Sidebar nav item** in `frontend/src/components/layout/Sidebar.tsx`.
6. **Hermetic pytest** `tests/test_htl_availability.py` covering HTL-010..HTL-012 (flag off, date-range seeding, conditional decrement, span-intersection check, overbooking, hold TTL, route ordering).
7. **E2E spec** `frontend/e2e/hotel-availability.spec.ts` (admin sets total rooms → grid renders counts → holds dates → cell drops → availability check).

Follows the established frontend feature recipe (CLAUDE.md "Adding a new feature — checklist" steps 5–9). With `HOTEL_PMS_ENABLED=false` (the default) the route is reachable via the browser and the sidebar nav item is visible, but every API call returns 404 — the backend is a flag-gated no-op per HTL-010's `_require_enabled()` (`app/services/inventory.py:54-56` idiom; AVAILABILITY_INVENTORY_TICKETS.md:36-42). The page shows a "Hotel availability is not enabled" callout instead of data. This matches the Inventory and PROP verticals exactly.

## 3. Data Model

HTL-013 is primarily a frontend + tests ticket. It introduces **no new DynamoDB tables, no new GSIs, and no new DynamoDB attributes** — all schema is delivered by HTL-010 (`hotel_availability` table, `GSI_HOTEL_DATE`) and HTL-011 (`HOLD#{hold_id}` rows, `GSI_HOLD_EXPIRY`). This section documents the TypeScript types that mirror the backend Pydantic models in `app/models.py` (HTL-010 `AvailabilityDayOut`/`AvailabilitySetIn`/`AvailabilityDayIn` at AVAILABILITY_INVENTORY_TICKETS.md:152-155; HTL-011 `HoldRoomsIn`/`HoldOut`/`OverbookingSetIn`/`MinMaxSetIn` at `:248-252`; HTL-012 `availability_calendar`/`check_availability` return shapes at `:328-343`).

### 3.1 TypeScript types (`frontend/src/api/types.ts`)

All interfaces are **additive** — appended at the end of `types.ts` in a new `// --- Hotel Availability (HTL-010..HTL-013) ---` section. No existing type is modified.

```typescript
// --- Hotel Availability (HTL-010..HTL-013) ---

// One (room_type, date) row — mirrors AvailabilityDayOut (HTL-010).
// `available` is the derived sellable count:
//   total_rooms + overbooking_allowance - booked - held  (clamped at min floor)
export interface AvailabilityDay {
  hotel_id: string;
  room_type_id: string;
  date: string;                  // YYYY-MM-DD
  total_rooms: number;
  booked: number;
  held: number;
  overbooking_allowance: number;
  min_availability: number;
  max_availability?: number | null;
  available: number;             // derived; what the grid cell shows
  updated_at: number;
}

// Hotel-wide calendar across ALL room types for a date range — mirrors
// availability_calendar() (HTL-012).
export interface AvailabilityCalendar {
  hotel_id: string;
  start_date: string;            // YYYY-MM-DD inclusive
  end_date: string;              // YYYY-MM-DD inclusive
  room_types: Record<string, AvailabilityDay[]>;  // room_type_id -> day rows
}

// Booking-time span-intersection check — mirrors check_availability() (HTL-012).
export interface AvailabilityCheckNight {
  date: string;
  remaining: number;
  sufficient: boolean;
}
export interface AvailabilityCheck {
  available: boolean;            // true iff EVERY night satisfies rooms_needed
  rooms_needed: number;
  per_night: AvailabilityCheckNight[];
  min_remaining: number;         // the binding (smallest) night
}

// A block/hold — mirrors HoldOut (HTL-011).
export type HoldStatus = "active" | "released" | "expired";
export interface Hold {
  hold_id: string;
  hotel_id: string;
  room_type_id: string;
  checkin: string;               // YYYY-MM-DD (inclusive)
  checkout: string;              // YYYY-MM-DD (exclusive — departure night not held)
  dates: string[];               // the nights this hold incremented `held`
  quantity: number;
  status: HoldStatus;
  user_sub: string;
  created_at: number;
  expires_at: number;
}

// --- Mutation input shapes ---

export interface AvailabilitySetTotalIn {
  start_date: string;            // YYYY-MM-DD inclusive
  end_date: string;              // YYYY-MM-DD inclusive
  total_rooms: number;
}
export interface HoldRoomsIn {
  checkin: string;
  checkout: string;              // exclusive
  quantity: number;
  ttl_seconds?: number;
}
export interface OverbookingSetIn {
  start_date: string;
  end_date: string;
  allowance: number;
}
export interface MinMaxSetIn {
  start_date: string;
  end_date: string;
  min_availability?: number;
  max_availability?: number;
}
```

> **Decimal coercion note.** DynamoDB serializes numeric attributes as `Decimal`; the HTL-010/011 service layer coerces them to `int` before returning (the same `int(...)` discipline as `inventory.py`, e.g. `app/services/inventory.py:366`). The TypeScript `number` types above assume the backend has already coerced — no client-side `Number()` wrapping is required, but `available`/`held` are read defensively as `Number(cell.available)` in the grid render to be safe against any uncoerced path.

## 4. API / Service Design

### 4.1 API endpoint wrappers (`frontend/src/api/endpoints/hotelAvailability.ts`)

New file. Uses `api.get/post/put/del` from `frontend/src/api/client.ts:290-313`. No axios, no custom fetch. Eight wrappers, one per HTL-012 endpoint (AVAILABILITY_INVENTORY_TICKETS.md:359-368).

```typescript
import { api } from "@/api/client";
import type {
  AvailabilityDay, AvailabilityCalendar, AvailabilityCheck, Hold,
  AvailabilitySetTotalIn, HoldRoomsIn, OverbookingSetIn, MinMaxSetIn,
} from "@/api/types";

// ─── Hotel availability (HTL-010..HTL-012) ───────────────────────────
// All endpoints are flag-gated server-side (HOTEL_PMS_ENABLED, default OFF)
// and 404 when off. Reads use require_ui_session; mutations are
// admin/root + CSRF (require_admin_or_root_csrf).

// Reads (require_ui_session)
export const getCalendar = (hotelId: string, startDate: string, endDate: string) =>
  api.get<AvailabilityCalendar>(
    `/ui/hotels/${encodeURIComponent(hotelId)}/availability/calendar`,
    { start_date: startDate, end_date: endDate },
  );

export const checkAvailability = (
  hotelId: string,
  params: { room_type_id: string; checkin: string; checkout: string; rooms_needed: number },
) =>
  api.get<AvailabilityCheck>(
    `/ui/hotels/${encodeURIComponent(hotelId)}/availability/check`,
    {
      room_type_id: params.room_type_id,
      checkin: params.checkin,
      checkout: params.checkout,
      rooms_needed: String(params.rooms_needed),
    },
  );

export const getAvailability = (
  hotelId: string, roomTypeId: string, checkin: string, checkout: string,
) =>
  api.get<AvailabilityDay[]>(
    `/ui/hotels/${encodeURIComponent(hotelId)}/availability/${encodeURIComponent(roomTypeId)}`,
    { checkin, checkout },
  );

// Mutations (require_admin_or_root_csrf)
export const setTotalRooms = (hotelId: string, roomTypeId: string, body: AvailabilitySetTotalIn) =>
  api.put<AvailabilityDay[]>(
    `/ui/hotels/${encodeURIComponent(hotelId)}/availability/${encodeURIComponent(roomTypeId)}/total-rooms`,
    body,
  );

export const holdRooms = (hotelId: string, roomTypeId: string, body: HoldRoomsIn) =>
  api.post<Hold>(
    `/ui/hotels/${encodeURIComponent(hotelId)}/availability/${encodeURIComponent(roomTypeId)}/hold`,
    body,
  );

export const releaseHold = (hotelId: string, holdId: string) =>
  api.post<Hold>(
    `/ui/hotels/${encodeURIComponent(hotelId)}/availability/holds/${encodeURIComponent(holdId)}/release`,
  );

export const setOverbooking = (hotelId: string, roomTypeId: string, body: OverbookingSetIn) =>
  api.put<AvailabilityDay[]>(
    `/ui/hotels/${encodeURIComponent(hotelId)}/availability/${encodeURIComponent(roomTypeId)}/overbooking`,
    body,
  );

export const setMinMax = (hotelId: string, roomTypeId: string, body: MinMaxSetIn) =>
  api.put<AvailabilityDay[]>(
    `/ui/hotels/${encodeURIComponent(hotelId)}/availability/${encodeURIComponent(roomTypeId)}/min-max`,
    body,
  );
```

> **URL ordering note.** Because these are *client* calls to fixed literal paths (`/availability/calendar`, `/availability/check`, `/availability/holds/{id}/release`), the FastAPI literal-before-dynamic capture problem (AVAILABILITY_INVENTORY_TICKETS.md:370-377) is the **backend's** concern (HTL-012 declares literal routes first). The client just calls the exact path; there is no React Router conflict because the only FE route is `/hotels/:hotelId/availability`.

### 4.2 React Query key conventions

| Query key | Description |
|---|---|
| `["hotelAvailability", hotelId, "calendar", startDate, endDate]` | `getCalendar` — the grid |
| `["hotelAvailability", hotelId, "check", roomTypeId, checkin, checkout, roomsNeeded]` | `checkAvailability` — the check panel (enabled only when all inputs set) |

After any mutation (`setTotalRooms`, `holdRooms`, `releaseHold`, `setOverbooking`, `setMinMax`) the page invalidates the calendar prefix key `["hotelAvailability", hotelId, "calendar"]` so the grid refetches the new remaining counts. There is no fine-grained cache surgery — a single calendar invalidation re-pulls the whole visible range (a landlord-portfolio-sized range is small; the GSI aggregation is cheap, AVAILABILITY_INVENTORY_TICKETS.md:333).

## 5. Detailed Behavior & Edge Cases

### 5.1 `AvailabilityCalendarPage.tsx` — layout

`useParams<{ hotelId: string }>()` extracts `hotelId`. Page top: an `<h1>` "Availability" + a **date-range picker** (two `<input type="date">`, defaulting to today → today+13 days, a 14-day window) that drives `getCalendar`. The query is `useQuery({ queryKey: ["hotelAvailability", hotelId, "calendar", startDate, endDate], queryFn: () => getCalendar(hotelId, startDate, endDate), enabled: !!startDate && !!endDate && startDate <= endDate })`.

**The grid** (shadcn `<Table>`): the header row is the date columns (`dateRange(startDate, endDate)`); each body row is a room type from `calendar.room_types`. The leftmost sticky column is the room-type id/label. Each cell `(room_type, date)` shows `Number(day.available)` — the remaining sellable count. Color-coding:
- `available <= 0` → **sold-out** (`<Badge variant="destructive">` / red cell).
- `0 < available <= lowThreshold` (default 3, a local const) → **low** (yellow).
- `available > lowThreshold` → **open** (green/neutral).
A cell additionally shows a small **`held`** badge when `day.held > 0` and an **"OB"** (overbooked) badge when `day.overbooking_allowance > 0`. Missing `(room_type, date)` rows surface as `available = 0` zeroed virtual rows from the backend (AVAILABILITY_INVENTORY_TICKETS.md:178-180) — they render as sold-out, not blank.

### 5.2 Admin-only controls

The three action `<Button>`s ("Set total rooms", "Block / hold dates", "Overbooking") and the `<Dialog>`s they open are rendered **only** when the viewer is admin/root, derived from the JWT via `getRoleFromAccessToken(useAuthStore(s => s.accessToken))` (`@/lib/adminCapabilities`, the `frontend/src/pages/tickets/TicketsPage.tsx:43` pattern). `useAuthStore` has no `role` field (§7.3). A USER-role viewer sees the read-only grid only — preventing confusing 403s from the `require_admin_or_root_csrf` mutation endpoints.

Each dialog is React Hook Form + Zod:

```typescript
const setTotalSchema = z.object({
  room_type_id: z.string().min(1, "Room type is required"),
  start_date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/, "YYYY-MM-DD"),
  end_date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/, "YYYY-MM-DD"),
  total_rooms: z.coerce.number().int().min(0),
}).refine(v => v.start_date <= v.end_date, { message: "end_date must be >= start_date", path: ["end_date"] });

const holdSchema = z.object({
  room_type_id: z.string().min(1),
  checkin: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  checkout: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  quantity: z.coerce.number().int().min(1),
}).refine(v => v.checkin < v.checkout, { message: "checkout must be after checkin", path: ["checkout"] });

const overbookingSchema = z.object({
  room_type_id: z.string().min(1),
  start_date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  end_date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  allowance: z.coerce.number().int().min(0),
}).refine(v => v.start_date <= v.end_date, { message: "end_date must be >= start_date", path: ["end_date"] });
```

On submit each dialog fires a `useMutation` (`setTotalRooms` / `holdRooms` / `setOverbooking`); `onSuccess` closes the dialog, `toast.success(...)`, and `queryClient.invalidateQueries({ queryKey: ["hotelAvailability", hotelId, "calendar"] })`. On API error → `toast.error(err.message)`. The submit button is disabled while `mutation.isPending` (idempotency belt-and-braces, §7.5). The room-type `<Select>` is populated from the current `calendar.room_types` keys plus a free-text fallback (since the room-type entity is out of scope, AVAILABILITY_INVENTORY_TICKETS.md:28).

### 5.3 Block / hold semantics

`holdRooms` increments `held` across **every night** of `[checkin, checkout)` (checkout exclusive — the departure night is not held, AVAILABILITY_INVENTORY_TICKETS.md:233,256). On success the grid cells for those nights show a higher `held` badge and a lower `available`. If the hold exceeds capacity on **any** night the backend returns **409** with a compensating rollback (no partial hold persists, `:259-267`); the dialog surfaces `toast.error` and the grid is unchanged. The page does **not** implement release UI in MVP beyond a per-hold "Release" affordance behind a future holds-list panel (forward ref); `releaseHold` is wrapped and tested but the holds-list table is a follow-up. (Holds also self-release via the `expire_due_holds` TTL sweep, `:272-278`.)

### 5.4 Availability check panel

A small "Check availability" panel (always visible to all roles) takes `room_type_id`, `checkin`, `checkout`, `rooms_needed` and calls `checkAvailability`. The result renders: a top-level `available` boolean badge (green "Available" / red "Not available"), `min_remaining` (the binding night), and a per-night strip (`per_night[]`) where each `sufficient: false` night is highlighted. This makes the **span-intersection** primitive visible: a stay is bookable iff every night satisfies `rooms_needed` — the distinction OFBiz's scalar counter cannot express (AVAILABILITY_INVENTORY_TICKETS.md:336-343). The checkout-night exclusion is honored by the backend; the panel does not draw a column for the departure date.

### 5.5 Loading / empty / flag-off states

- **Loading**: while `getCalendar` is `isLoading`, render `<Skeleton>` rows in the grid body.
- **Empty range**: when `calendar.room_types` is `{}`, render a centered empty state: "No room types have availability seeded for this range. Use 'Set total rooms' to seed."
- **Flag off (404)**: any 404 from `getCalendar` (flag off OR unknown hotel) → a centered `<Alert>`: "Hotel availability is not enabled on this platform." This is the only content rendered — no half-broken grid. The frontend never reads `HOTEL_PMS_ENABLED`; it infers "off" from the 404, identical to the Inventory/PROP verticals.

### 5.6 Date-range guards

If `start_date > end_date` the query is disabled (`enabled: startDate <= endDate`) and an inline hint is shown. A very wide range is capped client-side at e.g. 60 columns to keep the table renderable (a hint suggests narrowing); the backend GSI query is unbounded but the UI caps for layout.

### 5.7 Color thresholds and badges

`lowThreshold = 3` is a local const (not env-driven). Badge colors: sold-out → `<Badge variant="destructive">`; low → `className="bg-yellow-100 text-yellow-800"`; open → `<Badge variant="secondary">` (neutral) with the count. `held` badge → small outline badge "H{n}"; overbooking badge → "OB{allowance}". No color mapping is enforced server-side; the grid derives everything from the `AvailabilityDay` numerics.

### 5.8 Mutation refetch race

After `setTotalRooms`/`holdRooms` the calendar invalidation triggers a refetch; the grid shows the new counts once it lands. The E2E spec waits on the GET refetch response (or asserts on the changed cell text with `expect(...).toHaveText` polling) rather than a fixed timeout, per CLAUDE.md Playwright race guidance.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no dev-mode branches

HTL-013 is a frontend + tests ticket. Its only backend interaction is through the HTL-012 router + HTL-010/011 services, all of which already enforce SECOPS-007 (zero `if S.dev_mode` branches; the same `T.*` handles in dev and prod, moto intercepting boto3 in dev — AVAILABILITY_INVENTORY_TICKETS.md:65-67, mirroring `app/services/inventory.py:27-29`). The frontend has no concept of dev mode — it calls the same endpoints in both environments.

### 7.2 SECOPS-007 — hermetic pytest does not use `dev_mode`

`tests/test_htl_availability.py` toggles `S.hotel_pms_enabled` via `object.__setattr__` but never sets `S.dev_mode`. All service calls go through the same DynamoDB code path with moto intercepting boto3 — identical to every existing hermetic test.

### 7.3 Security — admin-only mutations

All four mutating endpoints (`total-rooms`, `hold`, `holds/{id}/release`, `overbooking`, `min-max`) are gated by `require_admin_or_root_csrf` at the HTL-012 router layer (`app/auth/policy.py:100`; AVAILABILITY_INVENTORY_TICKETS.md:379-380). Reads use `require_ui_session` (`app/services/sessions.py:330`). The FE hides the admin dialogs from USER-role sessions by decoding the role from the JWT: `const role = getRoleFromAccessToken(useAuthStore(s => s.accessToken)); const isAdmin = role === "admin" || role === "root";` — `getRoleFromAccessToken` from `@/lib/adminCapabilities` (the `frontend/src/pages/tickets/TicketsPage.tsx:43` pattern). `useAuthStore` exposes only `accessToken`/`userId`/`isAuthenticated` — **no `role` field** — so the role must be decoded from the access-token JWT, not read off the store. CSRF is auto-injected by the client (`X-CSRF-Token`, `frontend/src/api/client.ts:181`); the E2E spec sends `x-csrf-token` explicitly on `page.request` mutations.

### 7.4 Money-safety — HTL-013 does not touch billing

The availability vertical is room-count inventory, not money. HTL-013 displays and mutates `total_rooms`/`held`/`overbooking_allowance`/`available` — integer room counts, never cents. No mutation touches `billing_shared.py` (`new_ledger_entry`, `settle_or_reverse_ledger`, `apply_balance_delta`, `compute_due`). The summed multi-night **price** half is explicitly out of scope — it lives in the rate-plan cluster; HTL-012 answers only "are there rooms?", not "what does it cost" (AVAILABILITY_INVENTORY_TICKETS.md:345-349). HTL-013 never imports `api/endpoints/billing.ts`.

### 7.5 Idempotency

- `setTotalRooms` is naturally idempotent: re-setting the same range to the same `total_rooms` re-writes the same per-date rows, preserving `booked`/`held`/`overbooking_allowance` (read-merge per date, AVAILABILITY_INVENTORY_TICKETS.md:169-173). A double-submit produces the same end state.
- `holdRooms` is **not** idempotent (each call mints a new `hold_id` and increments `held`); the UI disables the submit button while `mutation.isPending` to prevent a double-hold from a double-click. `releaseHold` **is** idempotent — a double-release is a status-CAS no-op (`:268-271`).
- `setOverbooking`/`setMinMax` are idempotent per-date sets.

### 7.6 Audit trail

Backend mutations emit best-effort audit events via the HTL `_audit()` wrapper (the `app/services/inventory.py:92-98` idiom): `hotel.availability.set_total`, `hotel.hold.created`, `hotel.hold.released`, `hotel.overbooking.set`, `hotel.minmax.set` (AVAILABILITY_INVENTORY_TICKETS.md:173,267,271,279-285). HTL-013 adds no frontend-side audit emission — the backend is the authoritative source. In the hermetic test, `_audit`/`alerts.audit_event` are patched to no-ops.

## 10. Open Questions / Assumptions

1. **Calendar response shape — `room_types` map vs. array.** HTL-012 specifies `availability_calendar` returns `{"hotel_id", "start_date", "end_date", "room_types": {room_type_id: [AvailabilityDayOut...]}}` (AVAILABILITY_INVENTORY_TICKETS.md:330-333). **Assumption**: `room_types` is a `Record<string, AvailabilityDay[]>` keyed by room-type id (the `AvailabilityCalendar` type in §3.1). If the router instead returns a flat array of rows, the grid groups client-side by `room_type_id` — a one-line `reduce`; the type would change to `AvailabilityDay[]`.

2. **`check_availability` returns a plain object, not `{ result: ... }`.** §4.1 assumes `GET /availability/check` returns the `AvailabilityCheck` object directly (`{available, rooms_needed, per_night, min_remaining}`, AVAILABILITY_INVENTORY_TICKETS.md:341-343), not wrapped. Confirm against the HTL-012 router handler.

3. **`get_availability` returns a plain array.** §4.1 assumes `GET /availability/{room_type_id}` returns `AvailabilityDay[]` directly (AVAILABILITY_INVENTORY_TICKETS.md:175-180 describes "the per-date rows"). If it is wrapped as `{days: [...]}`, the wrapper type changes. (This mirrors the messaging-list array-vs-object gotcha in CLAUDE.md.)

4. **Admin-only UI controls via JWT role.** §7.3: `useAuthStore` has **no** `role` field; role is decoded from the access-token JWT via `getRoleFromAccessToken` (`@/lib/adminCapabilities`, the `TicketsPage.tsx:43` pattern). **Confirmed** against `frontend/src/lib/adminCapabilities.ts:22` (`export function getRoleFromAccessToken`). The dialogs are hidden for `role !== "admin" && role !== "root"`.

5. **`:hotelId` source for the nav link.** The Hotel-entity (with a picker) is out of scope (AVAILABILITY_INVENTORY_TICKETS.md:28-30). **Assumption**: the sidebar nav item uses a placeholder hotel id (`/hotels/default/availability`); the page reads `useParams().hotelId` so any value works. A real hotel-picker is a forward dependency (the Hotel-entity Tier-1 cluster). If a picker exists when HTL-013 ships, the nav points at it instead.

6. **Room-type `<Select>` source.** No room-type entity exists yet (AVAILABILITY_INVENTORY_TICKETS.md:28). **Assumption**: the dialog `<Select>` is populated from the room-type ids already present in `calendar.room_types`, with a free-text input fallback so an admin can seed a brand-new room type. When the Room-Type cluster lands, the select reads from it.

7. **`i18nKey` for the nav item.** `NavItem.i18nKey` is optional (`frontend/src/components/layout/Sidebar.tsx:87`). **Assumption**: a translation key (`nav.availability`) is added to the locale file if one exists; otherwise the `label` string ("Availability") is the fallback (the existing items all carry both).

8. **Hold release UI scope.** MVP ships `releaseHold` wrapped + tested but no holds-list table panel (§5.3). **Assumption**: holds self-release via the TTL sweep (`expire_due_holds`), so an explicit release UI is a follow-up, not blocking.
