# HTL-007 — Housekeeping status + tasks (per-room enum + task entity with assignment)

**Type**: Feature | **Priority**: P1 | **Estimate**: 1.5d
**Source**: `docs/qloapps/ROOMTYPES_ROOMS_HOUSEKEEPING_TICKETS.md` §HTL-007 + §"Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A row 5

---

## 1. Summary & Goal

HTL-007 adds the **housekeeping workflow** to the Hotel-PMS vertical — the genuinely net-new
cleaning-operations layer flagged in the gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A
row 5: "Housekeeping / room-status (clean/dirty/inspected/out-of-service + task assignment) —
**MISSING**"). The gap analysis records exactly one weak overlap — the open-property PROP-002 Unit
`occupancy_status` (vacant/occupied/turnover) — but that is "a rental flag, not a cleaning workflow;
no task-assignment entity". Housekeeping is therefore modeled fresh.

The ticket lands two cooperating parts on top of the HTL-006 `hotel_rooms` table:

1. **Per-room housekeeping status enum** — `housekeeping_status ∈ {clean, dirty, inspected,
   out_of_service}` persisted on the existing `ROOM#{room_id}` row (the column is *added by
   HTL-006*; HTL-007 owns the dedicated transition function `set_room_housekeeping_status` that
   mutates it and keeps the HTL-006 `GSI_HK_STATUS` board index current).
2. **Housekeeping task entity** — a `HKTASK#{task_id}` child row co-located on the `hotel_rooms`
   partition (the FAC header+child idiom, `docs/ofbiz/specs/FAC-001.md` §3, applied to a cleaning
   task rather than a warehouse bin). A task carries an assignee `user_sub`, a `status ∈ {open,
   in_progress, done}` lifecycle, an optional `due_at`, and free-text `notes`.

The deliverables are: the `HKTASK#` child-row schema + two new GSIs added to the **same**
`hotel_rooms` `TableDef`; Pydantic models (`HousekeepingStatusIn`, `HkTaskIn`, `HkTaskOut`,
`HkTaskAssignIn`, `HkTaskUpdateIn`); and the service functions in `app/services/hotel_pms.py` —
`set_room_housekeeping_status`, `create_hk_task`, `assign_hk_task`, `list_hk_tasks`,
`complete_hk_task`.

HTL-007 ships **no router** (that is HTL-008's deliverable) and **no frontend** (HTL-009). With
`HOTEL_PMS_ENABLED=false` (the default), every housekeeping entrypoint raises HTTP 404 and the
platform is byte-for-byte unchanged. No new DynamoDB table is created — task rows co-locate on the
HTL-006 `hotel_rooms` table.

> **Frontend analogue, not backend reuse.** The ticket-board service
> (`app/services/tickets.py:61` `_DEFAULT_BOARD_COLUMNS`, and the `open`/`in_progress`/`done`
> members of `_STATUS_TRANSITIONS` at `:30`) is the **UI analogue** for the HTL-009 housekeeping
> board (three columns of cards). It is *not* the backend store: housekeeping tasks persist to the
> `hotel_rooms` table here, never to the `tickets`/`ticket_spaces` tables. The contrast is
> deliberate — the tickets domain models software work items with a 10-state transition graph and a
> label-fan-out index; housekeeping tasks are a flat 3-state cleaning lifecycle keyed by hotel/room.

## 2. Context & Current State

### 2.1 No housekeeping domain exists today

The gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A row 5) records housekeeping as
**MISSING**. A `grep -rn "housekeeping\|HKTASK\|inspected" app/` returns no hotel-PMS results
today. The only weak structural shadow is the open-property PROP-002 Unit `occupancy_status`
(`vacant`/`occupied`/`turnover`/`unavailable`, `docs/open-property/specs/PROP-002.md` §3.1) — and
the gap analysis is explicit that this is "a rental flag, not a cleaning workflow". The two enums
are distinct and never share a field: `occupancy_status` answers *is a tenant living here?*,
`housekeeping_status` answers *is the room ready to sell tonight?*.

### 2.2 HTL-006 is the hard prerequisite

HTL-007 depends entirely on HTL-006 (`docs/qloapps/ROOMTYPES_ROOMS_HOUSEKEEPING_TICKETS.md`
§HTL-006). Before HTL-007 can be merged, HTL-006 must have:

- Created the `hotel_rooms` DynamoDB table (PK=`hotel_id`, SK=`ROOM#{room_id}` + child rows) via
  the `TableDef` in `scripts/local-ddb-init.py`, following the dataclass at
  `scripts/local-ddb-init.py:28-35` and the entry idiom at `:44+`.
- Added the `housekeeping_status` attribute (default `"clean"`) to the `ROOM#` row and the
  `GSI_HK_STATUS` index (PK=`hotel_id`, SK=`housekeeping_status`, both `S`) on the `hotel_rooms`
  `TableDef`.
- Added `S.hotel_rooms_table_name` to `app/core/settings.py` and wired `T.hotel_rooms` in
  `app/core/tables.py`.
- Created `app/services/hotel_pms.py` (landed in the HTL-001 cluster, extended by HTL-005/006) with
  `_flag_on()`, `_require_enabled()`, `_audit()`, `now_ts` imports, `create_room`, `get_room`,
  `list_rooms`, `update_room`, `delete_room`, and the parent-hotel ownership check.

HTL-007 extends `hotel_pms.py` in-place, adds the housekeeping Pydantic models to `app/models.py`,
and amends the `hotel_rooms` `TableDef` in `scripts/local-ddb-init.py` to add the two new task GSIs.

### 2.3 Flag-gate pattern (reused via HTL-001 → `hotel_pms.py`)

The cross-cutting constraints require mirroring the `INVENTORY_RESERVATIONS_ENABLED` contract
exactly. The canonical template is `app/services/inventory.py:50-56`:

```python
# inventory.py:50-56
def _flag_on() -> bool:
    return bool(getattr(S, "inventory_reservations_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Inventory reservations are not enabled")
```

HTL-001 carries this into `hotel_pms.py` as `_flag_on()` (gated on `hotel_pms_enabled` /
`HOTEL_PMS_ENABLED`) and `_require_enabled()` (→ 404 `"Hotel PMS is not enabled"`). Every HTL-007
service function calls `_require_enabled()` as its **first statement** — identical to how every
handler in `app/routers/inventory.py` delegates to `inv._require_enabled()` (via the
module-level `_require_enabled` wrapper at `app/routers/inventory.py:32-33`) as its first
statement (e.g. the first handler call at `app/routers/inventory.py:38`).

### 2.4 Audit wrapper (reused from `inventory.py:92-98`)

`app/services/inventory.py:92-98` provides the lazy-import `_audit()` wrapper:

```python
def _audit(event: str, user_sub: str, **fields: Any) -> None:
    try:
        from app.services.alerts import audit_event
        audit_event(event, user_sub or "system", None, **fields)
    except Exception:
        pass
```

HTL-001 copies this into `hotel_pms.py`. HTL-007's mutations reuse the existing `_audit()` already in
the file, emitting `hotel.room.housekeeping_status`, `hotel.hk_task.created`, `hotel.hk_task.assigned`,
and `hotel.hk_task.completed`.

### 2.5 Idempotent terminal-transition guard (reused from the inventory reservation idiom)

`app/services/inventory.py` documents (module docstring `:23-24`) the canonical
idempotency-under-replay pattern: "Commit / release / expire flip the reservation row's terminal
`status` with a `status = active` guard so they are idempotent under replay/concurrency." HTL-007's
`complete_hk_task` clones this contract: a conditional `update_item` flipping `status` to `done`
guarded by `status <> :done` — so a second call to `complete_hk_task` is a no-op (the
`ConditionalCheckFailedException` is swallowed) and `completed_at` is stamped exactly once.

### 2.6 `now_ts()` for all timestamps

`app/core/time.py:2` defines `now_ts() -> int` (integer Unix seconds). HTL-007 uses it for
`created_at`, `updated_at`, `completed_at`, and the *default* of an unset `due_at` (`0`). No
`datetime`/ISO strings — the platform-wide convention is integer Unix seconds (the CLAUDE.md
`_to_utc` Decimal/ISO gotcha is the cautionary tale).

### 2.7 Numeric GSI sort key → `attr_types`

Per the CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha and the cross-cutting constraint, any GSI
whose sort key is numeric (`created_at`) MUST be declared in the `TableDef` `attr_types` map —
omitting it stores the value as String → `ValidationException` at query time. HTL-007's
`GSI_HK_ASSIGNEE` has a numeric `created_at` sort key and must extend `attr_types={"created_at":
"N"}` (already present on the HTL-006 `hotel_rooms` `TableDef`). `GSI_HK_TASK_STATUS` keys are both
`S` (no `attr_types` change).

### 2.8 Decimal coercion on read

DynamoDB returns numeric attributes as `decimal.Decimal` via the boto3 resource API. `due_at`,
`created_at`, `updated_at`, `completed_at` are stored as `N` and must be coerced to `int` before
returning (the CLAUDE.md `MessageEncryptionEnvelope Decimal coercion` pattern; same requirement noted
in PROP-002 §2.7). `HkTaskOut` integer fields typed `int` will coerce a `Decimal` automatically, but
the service should coerce explicitly for dict round-trips and comparisons.

### 2.9 `set_room_housekeeping_status` keeps `GSI_HK_STATUS` current

HTL-006 declares `GSI_HK_STATUS` (PK=`hotel_id`, SK=`housekeeping_status`) so a hotel's rooms can be
bucketed by cleaning status without a scan. Because `housekeeping_status` is the GSI's *sort key*, a
plain `update_item` that rewrites the attribute on the `ROOM#` row automatically re-projects the row
into the new bucket — DynamoDB maintains the GSI. HTL-007 therefore needs no extra index write;
`set_room_housekeeping_status` is a single `update_item`.

### 2.10 Why `set_room_housekeeping_status` is dedicated (not part of `update_room`)

HTL-006 §HTL-006 explicitly routes the `housekeeping_status` mutation through HTL-007's
`set_room_housekeeping_status`, *not* the generic `update_room`. The rationale: the housekeeping
transition is an operational event with its own audit trail (`hotel.room.housekeeping_status`) and
its own validation (the four-value cleaning enum, distinct from the room's `available` /
`out_of_service` lifecycle `status`). Keeping it separate also gives HTL-008 a dedicated
`PUT .../rooms/{room_id}/housekeeping` route and a clean place to hang future side-effects (e.g.
auto-creating a HK task when a room is flagged `dirty`).

### 2.11 `list_hk_tasks` triple-mode query

A housekeeping board (HTL-009) needs three access patterns: (a) all of a hotel's tasks in a status
bucket (the board columns), (b) one staffer's assigned worklist, (c) all of a hotel's tasks. HTL-007
serves these from one function with three query branches: status → `GSI_HK_TASK_STATUS`, assignee →
`GSI_HK_ASSIGNEE`, hotel-all → the `hotel_rooms` PK + `begins_with(sk, "HKTASK#")`. This mirrors the
HTL-006 `list_rooms` dual-mode (by-hotel PK query vs. `GSI_ROOMTYPE`).

### 2.12 `FilterExpression` does not reduce page size — loop on `LastEvaluatedKey`

Per the CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha: on a busy `hotel_rooms`
partition that interleaves `ROOM#` and `HKTASK#` rows, the hotel-all branch of `list_hk_tasks` (which
filters `begins_with(sk, "HKTASK#")`) must loop `LastEvaluatedKey` until the requested page is filled
or the partition is exhausted — a single `query()` would silently miss `HKTASK#` rows beyond the
first 1 MB. The GSI branches do not need the filter (the GSIs index only `HKTASK#` rows — `ROOM#`
rows have no `status`/`assignee_sub` attributes, so they are sparse from these indexes; see §5.9).

## 3. Data Model

### 3.1 Part 1 — `housekeeping_status` on the `ROOM#` row (added by HTL-006, mutated here)

The per-room cleaning status is **not a new row** — it is the `housekeeping_status` attribute on the
existing `ROOM#{room_id}` row, added by HTL-006 (`docs/qloapps/ROOMTYPES_ROOMS_HOUSEKEEPING_TICKETS.md`
§HTL-006 table, default `"clean"`).

| Attribute | DDB Type | Constraints / Notes |
|---|---|---|
| `housekeeping_status` | S | Literal: `clean` \| `dirty` \| `inspected` \| `out_of_service`; default `"clean"` at room create (HTL-006); mutated **only** through `set_room_housekeeping_status` |

The four values model the standard hotel cleaning cycle:
- `clean` — cleaned, ready to assign/sell.
- `dirty` — checked-out or used; needs cleaning.
- `inspected` — cleaned **and** supervisor-verified (the QA gate before "ready to sell").
- `out_of_service` — pulled from the cleaning rotation entirely (deep maintenance, broken fixture).

Note the room row *also* carries a separate `status ∈ {available, out_of_service}` (HTL-006) — the
sellability lifecycle. `housekeeping_status=out_of_service` and `status=out_of_service` are distinct
columns; HTL-007 does not couple them (see §5.10 / Open-Q §10.4).

### 3.2 Part 2 — `HKTASK#{task_id}` child row on `hotel_rooms`

Housekeeping tasks are child rows co-located on the **same** `hotel_rooms` partition as the `ROOM#`
rows (the FAC `LOC#{location_id}` header+child idiom, `docs/ofbiz/specs/FAC-001.md` §3, applied to a
cleaning task). No second table is created.

**Primary key**

| Key | Type | Value |
|---|---|---|
| `hotel_id` | S (PK) | Same partition as the hotel's `ROOM#` rows |
| `sk` | S (SK) | `"HKTASK#{task_id}"` — `task_id = uuid4().hex` (non-deterministic; a room may accumulate many tasks over time, mirroring the HTL-006 `room_id` id contract) |

**Task row attributes**

| Attribute | DDB Type | Constraints / Notes |
|---|---|---|
| `hotel_id` | S | PK; same partition as the `ROOM#` rows |
| `sk` | S | `"HKTASK#{task_id}"` |
| `task_id` | S | Convenience copy of the id; `uuid4().hex` (32-char hex) |
| `room_id` | S | FK to the physical `ROOM#{room_id}` row this task targets (validated at create) |
| `assignee_sub` | S | Staff `user_sub` the task is assigned to; `""` until assigned (empty string, never `None` — DynamoDB cannot store `None` as a GSI key) |
| `status` | S | Literal: `open` \| `in_progress` \| `done`; default `"open"` at create |
| `due_at` | N | Due timestamp (`now_ts()`-scale Unix seconds); `0` if no due date |
| `notes` | S | Free-text instructions (e.g., `"VIP turndown, extra towels"`); `""` if none |
| `created_at` | N | `now_ts()` |
| `updated_at` | N | `now_ts()` — stamped on every mutation |
| `completed_at` | N | `now_ts()` at transition to `done`; `0` otherwise |

**Rationale for non-deterministic `task_id`**: a room is cleaned many times; each cleaning is a
distinct task. `uuid4().hex` avoids collisions and is intentionally **not** idempotent on
(room_id, anything) — see §7.2. This mirrors the HTL-006 `room_id` / PROP-002 `unit_id` UUID id
contract.

**Rationale for co-location on `hotel_rooms`** (vs. a separate `housekeeping_tasks` table): a hotel's
entire housekeeping board (rooms + their tasks) is then a single cheap partition query
(`Key={"hotel_id": hid}` + `begins_with(sk, "HKTASK#")` for tasks, `begins_with(sk, "ROOM#")` for
rooms). A separate table would force a cross-table join to render the board and would duplicate the
ownership/flag plumbing. The single-table header+child idiom (FAC-001 §3, reused throughout this
cluster) is the established choice; the `attr_types` numeric-GSI rule is already satisfied by the
HTL-006 `TableDef`. **Decision: child rows on `hotel_rooms`, no new table.**

### 3.3 GSIs — added to the **same** `hotel_rooms` `TableDef`

HTL-006 defines `hotel_rooms` with `GSI_ROOMTYPE` (PK=`room_type_id`, SK=`created_at`) and
`GSI_HK_STATUS` (PK=`hotel_id`, SK=`housekeeping_status`). HTL-007 adds two more for tasks:

| Index name | PK | SK | `attr_types` | Purpose |
|---|---|---|---|---|
| `GSI_HK_TASK_STATUS` | `hotel_id` (S) | `status` (S) | none new (both `S`) | List a hotel's tasks bucketed by `open`/`in_progress`/`done` — the HTL-009 board columns |
| `GSI_HK_ASSIGNEE` | `assignee_sub` (S) | `created_at` (N) | `{"created_at": "N"}` (already present) | List a staff member's assigned tasks, newest-first |

Both project all attributes (`ALL`). The `created_at` numeric `attr_types` declaration already exists
on the HTL-006 `TableDef`, so `GSI_HK_ASSIGNEE` is covered without an additional `attr_types` entry.

**Complete `hotel_rooms` `TableDef` after HTL-007** (all four GSIs):

```python
TableDef(
    _resolve_table_name(S.hotel_rooms_table_name, "hotel_rooms"),
    "hotel_id",
    "sk",
    gsi=[
        {"index_name": "GSI_ROOMTYPE",       "partition_key": "room_type_id", "sort_key": "created_at"},
        {"index_name": "GSI_HK_STATUS",      "partition_key": "hotel_id",     "sort_key": "housekeeping_status"},
        {"index_name": "GSI_HK_TASK_STATUS", "partition_key": "hotel_id",     "sort_key": "status"},
        {"index_name": "GSI_HK_ASSIGNEE",    "partition_key": "assignee_sub", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

`just restart` recreates the `hotel_rooms` table with all four GSIs. In production, the two new GSIs
are added via `UpdateTable` + async backfill before HTL-007 code is deployed (acceptable to be
incomplete during backfill — the whole vertical defaults flag-off; see §8.4).

> **Sparse-index note.** `GSI_HK_TASK_STATUS` keys on `status` and `GSI_HK_ASSIGNEE` keys on
> `assignee_sub` — attributes that exist **only** on `HKTASK#` rows. `ROOM#` rows have no `status`
> attribute named `status`? — they *do* (the `available`/`out_of_service` sellability lifecycle).
> This is the one collision to guard: a `ROOM#` row carries a `status` and would project into
> `GSI_HK_TASK_STATUS`. See §5.9 for the `begins_with(sk, "HKTASK#")` filter that excludes `ROOM#`
> rows from task listings. `GSI_HK_ASSIGNEE` has no such collision (`ROOM#` rows have no
> `assignee_sub`, so they are naturally sparse from it).

## 4. API / Service Design

### 4.1 Service additions: `app/services/hotel_pms.py`

All five functions are added to the existing `hotel_pms.py` file (created by HTL-001, extended by
HTL-005/006). No second service file is created. Every function calls `_require_enabled()` first. No
`if S.dev_mode` branch anywhere (SECOPS-007, §7.1).

#### 4.1.1 `set_room_housekeeping_status`

```python
def set_room_housekeeping_status(
    hotel_id: str,
    room_id: str,
    *,
    housekeeping_status: str,
    user_sub: str,
) -> dict:
```

**Behavior**:
1. `_require_enabled()`.
2. Validate the enum: `housekeeping_status` must be one of `{clean, dirty, inspected,
   out_of_service}`; otherwise raise `HTTPException(422, "Invalid housekeeping status")`. (The router
   gets this for free from `HousekeepingStatusIn`; the service revalidates as a defense in depth.)
3. Read the room via `get_room(hotel_id, room_id)` (HTL-006). Raise `HTTPException(404, "Room not
   found")` if absent.
4. Verify parent-hotel ownership (read the hotel `META` row; `owner_sub == user_sub`, the HTL-001
   ownership contract; ROOT bypass per §5.11 / Open-Q §10.1). Raise `HTTPException(403)` otherwise.
5. `T.hotel_rooms.update_item(Key={"hotel_id": hotel_id, "sk": f"ROOM#{room_id}"},
   UpdateExpression="SET housekeeping_status = :hk, updated_at = :ts", ...)`. This rewrite re-buckets
   the room under `GSI_HK_STATUS` automatically (§2.9).
6. `_audit("hotel.room.housekeeping_status", user_sub, hotel_id=hotel_id, room_id=room_id,
   housekeeping_status=housekeeping_status)`.
7. Re-read and return the updated room dict (numeric Decimals coerced).

#### 4.1.2 `create_hk_task`

```python
def create_hk_task(
    hotel_id: str,
    *,
    room_id: str,
    assignee_sub: str = "",
    due_at: int = 0,
    notes: str = "",
    user_sub: str,
) -> dict:
```

**Behavior**:
1. `_require_enabled()`.
2. Read the target room via `get_room(hotel_id, room_id)`. Raise `HTTPException(404, "Room not
   found")` if absent — a task may not reference a non-existent room.
3. Verify parent-hotel ownership (same as §4.1.1 step 4).
4. `task_id = uuid4().hex`.
5. Build the item: `sk=f"HKTASK#{task_id}"`, `status="open"`, `assignee_sub=assignee_sub or ""`,
   `due_at=int(due_at)`, `notes=notes or ""`, `created_at=now_ts()`, `updated_at=now_ts()`,
   `completed_at=0`.
6. `T.hotel_rooms.put_item(Item=item)` — unconditional put (UUID id, no collision possible).
7. `_audit("hotel.hk_task.created", user_sub, hotel_id=hotel_id, room_id=room_id, task_id=task_id,
   assignee_sub=assignee_sub)`.
8. Return the task dict (Decimals coerced).

#### 4.1.3 `assign_hk_task`

```python
def assign_hk_task(
    hotel_id: str,
    task_id: str,
    *,
    assignee_sub: str,
    user_sub: str,
) -> dict:
```

**Behavior**:
1. `_require_enabled()`.
2. Read the task via `T.hotel_rooms.get_item(Key={"hotel_id": hotel_id, "sk":
   f"HKTASK#{task_id}"})`. Raise `HTTPException(404, "Task not found")` if absent.
3. Verify parent-hotel ownership (same as §4.1.1).
4. `T.hotel_rooms.update_item(... SET assignee_sub = :a, updated_at = :ts ...)`. Rewriting
   `assignee_sub` re-keys the row under `GSI_HK_ASSIGNEE` automatically (it is that GSI's PK).
   **Idempotent re-assign**: assigning the same `assignee_sub` twice is a harmless no-op (only
   `updated_at` advances). Re-assigning to a *new* staffer moves the row out of the old assignee's
   partition into the new one — DynamoDB GSI maintenance handles the move atomically.
5. `_audit("hotel.hk_task.assigned", user_sub, hotel_id=hotel_id, task_id=task_id,
   assignee_sub=assignee_sub)`.
6. Re-read and return the updated task dict.

> Note: `assign_hk_task` does **not** change `status` (a freshly-assigned task stays `open` until the
> staffer starts it via an `HkTaskUpdateIn` `status="in_progress"` through HTL-008's update route, or
> is completed via `complete_hk_task`). Assignment and lifecycle are orthogonal.

#### 4.1.4 `list_hk_tasks`

```python
def list_hk_tasks(
    hotel_id: str | None = None,
    *,
    status: str | None = None,
    assignee_sub: str | None = None,
    cursor: str | None = None,
    limit: int = 50,
) -> dict:
```

**Behavior** (three mutually-prioritized branches):
1. `_require_enabled()`.
2. **By assignee** (`assignee_sub` given): query `GSI_HK_ASSIGNEE`
   (`KeyConditionExpression=Key("assignee_sub").eq(assignee_sub)`), `ScanIndexForward=False`
   (newest-first by `created_at`). Optional in-bucket `status` filter applied as a
   `FilterExpression`.
3. **By hotel + status** (`hotel_id` and `status` given, no `assignee_sub`): query
   `GSI_HK_TASK_STATUS` (`Key("hotel_id").eq(hotel_id) & Key("status").eq(status)`), with a
   `FilterExpression=Attr("sk").begins_with("HKTASK#")` to exclude any `ROOM#` row that shares the
   `status` attribute (§5.9).
4. **By hotel (all tasks)** (`hotel_id` given, no `status`, no `assignee_sub`): query the
   `hotel_rooms` PK (`Key("hotel_id").eq(hotel_id) & Key("sk").begins_with("HKTASK#")`).
5. Decode the incoming `cursor` via `decode_cursor` (`app/core/cursor.py:103`); loop
   `LastEvaluatedKey` until `limit` items are collected or the source is exhausted (§2.12); encode the
   forward cursor via `encode_cursor` (`app/core/cursor.py:94`) if more remain.
6. Coerce Decimal numeric fields on each item.
7. Return `{"tasks": [...], "count": int, "cursor": str | None}` (the `{items, count, cursor}` shape
   per CLAUDE.md `host_inventory.list_hosts`).

If none of `assignee_sub`/`hotel_id` is provided, raise `HTTPException(422, "hotel_id or
assignee_sub required")` — there is no global "all tasks across all hotels" scan path (a deliberate
guardrail; see Open-Q §10.5).

#### 4.1.5 `complete_hk_task`

```python
def complete_hk_task(hotel_id: str, task_id: str, *, user_sub: str) -> dict:
```

**Behavior**:
1. `_require_enabled()`.
2. Read the task; raise `HTTPException(404, "Task not found")` if absent.
3. Verify parent-hotel ownership.
4. Conditional `update_item` flipping the terminal status (the inventory reservation idempotency
   idiom, §2.5):
   ```python
   try:
       T.hotel_rooms.update_item(
           Key={"hotel_id": hotel_id, "sk": f"HKTASK#{task_id}"},
           UpdateExpression="SET #s = :done, completed_at = :ts, updated_at = :ts",
           ConditionExpression="#s <> :done",
           ExpressionAttributeNames={"#s": "status"},
           ExpressionAttributeValues={":done": "done", ":ts": now_ts()},
       )
   except ClientError as e:
       if e.response["Error"]["Code"] != "ConditionalCheckFailedException":
           raise
       # already done — idempotent no-op
   ```
   (`status` is a DynamoDB reserved word → use `#s` ExpressionAttributeName.)
5. `_audit("hotel.hk_task.completed", user_sub, hotel_id=hotel_id, task_id=task_id)` (emitted on the
   first completion path; a replayed no-op may still emit a best-effort audit — acceptable, audit is
   advisory).
6. Re-read and return the task dict (`status="done"`, `completed_at` set).

## 5. Detailed Behavior & Edge Cases

### 5.1 Room not found on status transition

`set_room_housekeeping_status` reads the `ROOM#` row via `get_room` (a strongly-consistent
`get_item`, not a GSI query) before writing. If absent → `HTTPException(404, "Room not found")` and
nothing is written. The room's `housekeeping_status` cannot be set for a non-existent `room_id`.

### 5.2 Invalid enum value

A `housekeeping_status` outside `{clean, dirty, inspected, out_of_service}` is rejected: at the router
boundary by `HousekeepingStatusIn` (Pydantic 422), and again at the service boundary as defense in
depth (`set_room_housekeeping_status` step 2 → 422). No invalid value can reach DynamoDB. The
acceptance criterion "invalid enum → 422" is satisfied at both layers.

### 5.3 `GSI_HK_STATUS` re-bucketing is automatic

Because `housekeeping_status` is the **sort key** of `GSI_HK_STATUS` (HTL-006), a plain `update_item`
rewriting that attribute re-projects the `ROOM#` row into the new status bucket — DynamoDB maintains
the GSI; HTL-007 issues no separate index write. After `set_room_housekeeping_status(..., "dirty")`,
a `query(IndexName="GSI_HK_STATUS", Key("hotel_id").eq(hid) & Key("housekeeping_status").eq("dirty"))`
returns the room; a query for `"clean"` no longer does.

### 5.4 No transition rules on `housekeeping_status` (any → any)

HTL-007 does **not** enforce a cleaning state machine (e.g., `dirty → inspected` only after
`clean`). Any value → any value is allowed (a supervisor may jump a room straight to `out_of_service`
from `clean`). Transition enforcement is a future operational-policy concern (Open-Q §10.2),
consistent with how PROP-002 leaves `occupancy_status` transitions free (PROP-002 §5.6).

### 5.5 Task references an unknown room

`create_hk_task` validates `room_id` via `get_room` and 404s if the room does not exist (§4.1.2 step
2). A housekeeping task is always anchored to a real physical room. (The room is not required to be in
any particular `housekeeping_status` — a task can be created against a `clean` room, e.g. a scheduled
turndown.)

### 5.6 Tasks never appear in `list_rooms`, rooms never appear in `list_hk_tasks`

`list_rooms` (HTL-006) uses `begins_with(sk, "ROOM#")`; `list_hk_tasks` uses `begins_with(sk,
"HKTASK#")`. The two SK prefixes partition the shared `hotel_rooms` partition cleanly. A `HKTASK#`
row is never returned by `list_rooms`, and a `ROOM#` row is never returned by `list_hk_tasks` (the
`begins_with(sk, "HKTASK#")` filter on the hotel-all and status branches excludes it, §5.9).

### 5.7 `assign_hk_task` idempotent re-assign; reassign moves GSI partition

Assigning the same `assignee_sub` again is a no-op beyond `updated_at`. Re-assigning to a different
staffer rewrites the `assignee_sub` attribute — which is the `GSI_HK_ASSIGNEE` PK — so the row leaves
the old staffer's index partition and joins the new one. `list_hk_tasks(assignee_sub=old)` no longer
returns it; `list_hk_tasks(assignee_sub=new)` does. Assignment does not alter `status`.

### 5.8 `complete_hk_task` idempotency

The conditional `update_item` with `#s <> :done` guard makes completion idempotent: the first call
flips `status=done` and stamps `completed_at`; a second call raises
`ConditionalCheckFailedException`, which is swallowed → no second `completed_at` rewrite, no error.
This is the inventory-reservation terminal-status idiom (§2.5). `complete_hk_task` can therefore be
safely retried by a flaky client or a board double-click.

### 5.9 Excluding `ROOM#` rows from `GSI_HK_TASK_STATUS`

`ROOM#` rows carry a `status` attribute (the `available`/`out_of_service` sellability lifecycle,
HTL-006) — the same attribute name as the task `status` — so they project into `GSI_HK_TASK_STATUS`.
A `query(IndexName="GSI_HK_TASK_STATUS", Key("hotel_id").eq(hid) & Key("status").eq("out_of_service"))`
would surface both an `out_of_service` *room* row and any `out_of_service`... but tasks only use
`open`/`in_progress`/`done`, none of which equal a room `status` value (`available`/`out_of_service`).
So in practice the value spaces are **disjoint** — a task-status query for `"open"` cannot match a
room row. Nonetheless, HTL-007 applies `FilterExpression=Attr("sk").begins_with("HKTASK#")` on the
status branch as a belt-and-suspenders guard (cheap; the filter runs post-fetch but the value-space
disjointness means it rarely discards anything). `GSI_HK_ASSIGNEE` needs no such filter — `ROOM#`
rows have no `assignee_sub` attribute and are naturally sparse.

### 5.10 `housekeeping_status=out_of_service` vs. room `status=out_of_service`

These are two independent columns. A room can be `status=available` (sellable) yet
`housekeeping_status=dirty` (awaiting cleaning), or `status=out_of_service` (pulled from sale) yet
`housekeeping_status=clean`. HTL-007 deliberately does **not** auto-sync them (e.g., setting
`housekeeping_status=out_of_service` does not flip `status`). Coupling the two is an operational
policy decision deferred to a later cluster (Open-Q §10.4).

### 5.11 Ownership enforcement — ADMIN vs ROOT

Every mutation reads the hotel `META` row and checks `owner_sub == user_sub` (the HTL-001 single
-platform ownership contract). A non-owning ADMIN cannot mutate another hotel's housekeeping. ROOT
bypass (administrative override) follows the cluster's chosen convention — `if user.role == Role.ROOT:
pass` before the ownership check — applied uniformly across HTL-005/006/007 (Open-Q §10.1). Reads
(`list_hk_tasks` via `require_ui_session`) do not enforce ownership at the service layer, consistent
with HTL-006 `list_rooms` and PROP-002 §7.3.

### 5.12 `due_at` and `notes` defaults; empty assignee

An unassigned task stores `assignee_sub=""` (never `None` — a `None` GSI key value is unstorable, and
an empty-string PK simply means the row does not usefully appear in any one staffer's
`GSI_HK_ASSIGNEE` partition until assigned). `due_at=0` means "no due date"; `notes=""` means none.
All three are valid stored states for a freshly created, not-yet-assigned task.

### 5.13 Task rows are hard-deleted only via room cascade (none in HTL-007)

HTL-007 exposes **no** `delete_hk_task` — a completed task is retained (it is the cleaning audit
record). The HTL-006 `delete_room` deletes only the `ROOM#` row, not its `HKTASK#` children
(orphaned task rows remain queryable by `hotel_id`+`begins_with(sk,"HKTASK#")`). Cascading task
deletion on room delete is an Open-Q (§10.6) — out of HTL-007 scope.

### 5.14 `list_hk_tasks` for a hotel/assignee with no tasks

Returns `{"tasks": [], "count": 0, "cursor": null}`. A query that matches zero rows is not an error.

### 5.15 Pagination ordering

`GSI_HK_ASSIGNEE` (numeric `created_at` SK) supports meaningful newest-first ordering via
`ScanIndexForward=False`. `GSI_HK_TASK_STATUS` (string `status` SK) and the hotel-all PK query order
by the SK string (`HKTASK#{uuid}` — non-deterministic for display); a board UI groups by column and
does not rely on intra-column ordering, so no Python re-sort is mandated (contrast PROP-002 `list_units`
which sorts by `label`). If a deterministic ordering is later required, sort by `created_at` in Python
after fetch (the CLAUDE.md `list_messages sort by created_at` pattern).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_pms.py` must contain **no** `if S.dev_mode` branch across any of the five
housekeeping functions. The same DynamoDB code path (`T.hotel_rooms.*`) runs in dev (boto3
intercepted by moto in-process) and prod (real DynamoDB). This mirrors the cross-cutting constraint
("Zero `if S.dev_mode` branches in business logic; the same `T.*` handles in both environments",
`docs/qloapps/ROOMTYPES_ROOMS_HOUSEKEEPING_TICKETS.md` §"Cross-cutting constraints") and the
`app/services/inventory.py` precedent (the only `dev_mode` reference there is a module docstring
comment).

### 7.2 Idempotency

- `set_room_housekeeping_status` — idempotent in result: re-applying the same status produces the same
  final row (only `updated_at` advances).
- `create_hk_task` — **not** idempotent on (room_id, ...) by design: the non-deterministic
  `uuid4().hex` `task_id` means each call creates a new task row (each cleaning is a distinct task).
  Callers must not blindly retry creates; deduplication, if needed, is the caller's responsibility.
- `assign_hk_task` — idempotent in result (re-assigning the same staffer is a no-op beyond
  `updated_at`).
- `complete_hk_task` — idempotent in effect via the `#s <> :done` conditional guard (second call is a
  swallowed no-op; `completed_at` written exactly once). This is the inventory-reservation
  terminal-status idiom (§2.5).
- `list_hk_tasks` — read-only, trivially idempotent.

### 7.3 Security — ownership, auth boundary, CSRF

- **Ownership**: every mutation reads the hotel `META` row and compares `owner_sub` to `user_sub`
  (HTL-001 contract); non-owning ADMINs are blocked (403). ROOT bypass per the cluster convention
  (§5.11 / §10.1).
- **Auth boundary** (HTL-008 router): mutations require `require_admin_or_root_csrf`
  (`app/auth/policy.py:100`) — `role ∈ {ADMIN, ROOT}` + cookie-CSRF; reads require `require_ui_session`
  (`app/services/sessions.py:330`).
- **CSRF**: cookie-auth `PUT`/`POST` require an `x-csrf-token` header matching the `ui_csrf` cookie,
  enforced by `require_admin_or_root_csrf`. Bearer-auth requests skip CSRF (CLAUDE.md auth contract).
- **No PII leakage**: `assignee_sub` is an internal `user_sub`; the HTL-009 board may resolve it to a
  display name via the existing contacts/roles surface — HTL-007 stores only the opaque sub.

### 7.4 Money-safety — no billing primitive touched

Housekeeping touches **no** money. HTL-007 does not import or call `billing_shared.new_ledger_entry`,
`settle_or_reverse_ledger`, `apply_balance_delta`, or `compute_due`; no Stripe/PayPal/CCBill provider
SDK is invoked; the `billing` table is never accessed. There is no cents-valued field on a room or a
task. (Hotel revenue/folio money lands in the Tier-3 HTL folio/deposit cluster — entirely separate.)
There are therefore no financial invariants to enforce in this ticket.

### 7.5 Audit trail

Every mutation emits a best-effort `_audit()` event (swallows exceptions, never propagates):

| Event | When |
|---|---|
| `hotel.room.housekeeping_status` | `set_room_housekeeping_status` success |
| `hotel.hk_task.created` | `create_hk_task` success |
| `hotel.hk_task.assigned` | `assign_hk_task` success |
| `hotel.hk_task.completed` | `complete_hk_task` (first completion; replayed no-op may re-emit) |

## 8. Backward Compatibility & Migration

### 8.1 Additive-only changes

HTL-007 adds:
- Five Pydantic models to `app/models.py` (`HousekeepingStatusIn`, `HkTaskIn`, `HkTaskOut`,
  `HkTaskAssignIn`, `HkTaskUpdateIn`) — additive; no existing model altered.
- Five functions to `app/services/hotel_pms.py` — additive; no existing function altered.
- Two GSIs (`GSI_HK_TASK_STATUS`, `GSI_HK_ASSIGNEE`) to the `hotel_rooms` `TableDef` in
  `scripts/local-ddb-init.py` — amends the HTL-006 entry; backward-compatible because `just restart`
  recreates the table.

No existing endpoint, service function, DynamoDB table schema, or Pydantic model is modified. The
`housekeeping_status` column itself is added by **HTL-006**, not HTL-007 (HTL-007 only mutates it).

### 8.2 `TableDef` reconciliation with HTL-006

The `hotel_rooms` `TableDef` introduced by HTL-006 (two GSIs: `GSI_ROOMTYPE`, `GSI_HK_STATUS`) must
be amended by HTL-007 to add `GSI_HK_TASK_STATUS` + `GSI_HK_ASSIGNEE` (four total). In a sequential
merge, HTL-006 lands first and HTL-007 amends the same entry; if merged together, a single four-GSI
`TableDef` is written at once (preferred). The shared `attr_types={"created_at": "N"}` covers
`GSI_HK_ASSIGNEE`'s numeric sort key.

### 8.3 Dev table recreation

`just restart` calls `scripts/local-ddb-init.py`, which `CreateTable`s every `TableDef`. The
`hotel_rooms` table is dropped and recreated with all four GSIs; existing dev test data is wiped each
restart (the standard dev workflow).

### 8.4 Production deployment

1. Add `GSI_HK_TASK_STATUS` + `GSI_HK_ASSIGNEE` to the live `hotel_rooms` table via `UpdateTable`
   (DynamoDB allows only one GSI add per `UpdateTable` call — issue two sequential `UpdateTable`s).
   Backfill is asynchronous; during backfill the new task GSIs may be incomplete — acceptable, since
   `HOTEL_PMS_ENABLED` defaults `false`.
2. Deploy HTL-007 code (new service functions; zero existing-behavior change).
3. Enable `HOTEL_PMS_ENABLED=true` once the table + both GSIs are `ACTIVE`.

### 8.5 Rollback

With `HOTEL_PMS_ENABLED=false`, all housekeeping functions are dormant (404). Rolling back HTL-007
reverts three file changes (`models.py`, `hotel_pms.py`, `local-ddb-init.py`). The two task GSIs may
be left on the table (inert with the flag off) or removed via `UpdateTable`
`GlobalSecondaryIndexUpdates: [{Delete: {IndexName: ...}}]`.

## 10. Open Questions / Assumptions

1. **ROOT bypass for ownership.** Every mutation checks `META["owner_sub"] == user_sub`. Whether ROOT
   bypasses this (`if user.role == Role.ROOT: pass`) is a cluster-wide convention set in HTL-001 and
   applied uniformly across HTL-005/006/007. **Assumption**: single-platform deployment; ROOT owns
   the hotels, no per-ticket bypass invented here.
2. **`housekeeping_status` transition enforcement.** HTL-007 allows any → any. A strict cleaning state
   machine (`dirty → clean → inspected`) is deferred. **Assumption**: free transitions for MVP, mirror
   PROP-002 §5.6.
3. **Auto-create a task when a room goes `dirty`.** A natural future behavior is for
   `set_room_housekeeping_status(..., "dirty")` to auto-spawn an `open` HK task. HTL-007 keeps the two
   actions decoupled. **Assumption**: explicit task creation for MVP; auto-spawn is a follow-up.
4. **Coupling `housekeeping_status=out_of_service` to room `status`.** The two `out_of_service`
   columns are independent (§5.10). **Assumption**: no auto-sync in HTL-007; coupling is an
   operational-policy follow-up.
5. **Global cross-hotel task listing.** `list_hk_tasks` requires either `hotel_id` or `assignee_sub`
   (422 otherwise) — there is no platform-wide task scan. **Assumption**: a staffer's cross-hotel
   worklist is served by `assignee_sub` alone (which spans hotels via `GSI_HK_ASSIGNEE`); no
   all-hotels scan path is needed for MVP.
6. **Task cascade on room delete.** HTL-006 `delete_room` deletes only the `ROOM#` row, orphaning its
   `HKTASK#` children. **Assumption**: orphaned tasks are acceptable (they remain the cleaning audit
   record); a cascade or a `delete_hk_task` is a follow-up if churn is high.
7. **`HkTaskUpdateIn` (status/notes/due_at) generic update route.** The §HTL-008 table includes
   `assign` and `complete` but the in-progress transition (`status="in_progress"`) and notes/due-date
   edits would flow through a generic `PUT .../tasks/{task_id}` consuming `HkTaskUpdateIn`. **Assumption**:
   HTL-008 adds this generic update route (the model is defined here in §3.4 for it); if omitted,
   `in_progress` is set only via the future board. This spec defines the model and leaves the route to
   HTL-008.
