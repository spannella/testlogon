## 1. Summary & Goal

HTL-004 is the final ticket in the QloApps hotel-PMS "hospitality spine" cluster (HTL-001..HTL-004). It delivers the React/TypeScript frontend for the Hotel + amenity vertical and the full test suite (hermetic pytest + Playwright E2E) that validates the entire HTL-001..HTL-004 stack end-to-end.

The gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A) records the hospitality spine as the **lowest-reuse vertical analyzed** — "testlogon has *no hospitality domain at all*." §A row 1 marks the Hotel entity (star rating, amenities, check-in/out times, policies, photos, contact) as **MISSING (PLANNED-adjacent)** and §A row 4 marks the "Hotel features / amenities catalog (wifi/pool/parking attached to hotels+room types)" as **MISSING**. The §A "FE" note ("hotel cards + detail + amenity chips") has no implemented analogue. HTL-004 closes the presentational gap for the Hotel and amenity layer.

HTL-004 does **not** cover Room Types, individual Rooms, housekeeping, the per-date availability calendar, nightly rate plans, the stay-search engine, reservations, the front desk, the booking storefront, folios, deposits, or KPI reports — those are the rest of Tier 1 plus Tiers 2 & 3 in the gap analysis and are out of scope here.

**Deliverables:**

1. **TypeScript types** mirroring `app/models.py` HTL models (`frontend/src/api/types.ts`).
2. **API endpoint wrappers** calling the HTL-003 router via `frontend/src/api/client.ts` (`frontend/src/api/endpoints/hotels.ts`).
3. **Two page components** under `frontend/src/pages/hotels/`:
   - `HotelsPage.tsx` — responsive hotel card grid + "New Hotel" dialog + status filter.
   - `HotelDetailPage.tsx` — hotel header (name + star rating + address + archive), check-in/out + policy summary, photo gallery, amenity-chips section (attach/detach dialog), edit-hotel dialog.
4. **Route registrations** in `frontend/src/App.tsx`.
5. **Sidebar nav item** in `frontend/src/components/layout/Sidebar.tsx`.
6. **Hermetic pytest** `tests/test_htl_hotels_amenities.py` covering HTL-001..HTL-003 (flag off, hotel + amenity CRUD, idempotency, attach/detach, `list_amenities_for` hydration, `list_hotels` pagination, route ordering).
7. **E2E spec** `frontend/e2e/hotels.spec.ts` (cookie-auth admin, end-to-end create hotel → create + attach amenity → card grid → detail page → amenity chips → photo gallery).

With `HOTEL_PMS_ENABLED=false` (the default — see `docs/qloapps/HOTELS_AMENITIES_TICKETS.md` "Cross-cutting constraints"), both pages are reachable in the browser (routes are registered unconditionally) but every API call returns 404 — the backend is a flag-gated no-op per HTL-001's `_require_enabled()` (the `app/services/inventory.py:50-56` template). The sidebar nav item is always visible; the error state renders a user-facing "Hotel management is not enabled" callout. This matches the Inventory vertical and PROP-005.

## 4. API / Service Design

### 4.1 API endpoint wrappers (`frontend/src/api/endpoints/hotels.ts`)

New file. Uses `api.get`/`api.post`/`api.put`/`api.del` from `frontend/src/api/client.ts` (`:290-313`). No axios, no custom fetch. Param maps are stringified and `undefined`-filtered (mirrors the PROP-005 `properties.ts` pattern).

```typescript
import { api } from "@/api/client";
import type {
  Hotel, HotelIn, HotelUpdateIn, HotelListOut,
  Amenity, AmenityIn, AmenityAttachIn, AmenityAssociation,
} from "@/api/types";

const qp = (params?: Record<string, unknown>) =>
  params
    ? Object.fromEntries(
        Object.entries(params)
          .filter(([, v]) => v !== undefined && v !== null)
          .map(([k, v]) => [k, String(v)]),
      )
    : undefined;

// Hotels
export const listHotels = (params?: { status?: string; cursor?: string; limit?: number }) =>
  api.get<HotelListOut>("/ui/hotels", qp(params));

export const createHotel = (body: HotelIn) =>
  api.post<Hotel>("/ui/hotels", body);

export const getHotel = (hotelId: string) =>
  api.get<Hotel>(`/ui/hotels/${hotelId}`);

export const updateHotel = (hotelId: string, body: HotelUpdateIn) =>
  api.put<Hotel>(`/ui/hotels/${hotelId}`, body);

export const archiveHotel = (hotelId: string) =>
  api.del<Hotel>(`/ui/hotels/${hotelId}`);

// Amenities (dictionary + many-to-many attach)
export const listAmenities = (params?: { category?: string }) =>
  api.get<Amenity[]>("/ui/hotels/amenities", qp(params));

export const createAmenity = (body: AmenityIn) =>
  api.post<Amenity>("/ui/hotels/amenities", body);

export const attachAmenity = (body: AmenityAttachIn) =>
  api.post<{ ok: boolean }>("/ui/hotels/amenities/attach", body);

export const detachAmenity = (body: AmenityAttachIn) =>
  api.post<{ ok: boolean }>("/ui/hotels/amenities/detach", body);

export const listAmenitiesForHotel = (hotelId: string) =>
  api.get<AmenityAssociation[]>(`/ui/hotels/${hotelId}/amenities`);
```

> Both `attach` and `detach` POST the same `AmenityAttachIn` body (`target_type`, `target_id`, `amenity_id`); the frontend always passes `target_type: "hotel"` and `target_id: hotelId` — the `room_type` target is forward-compat backend surface (HTL-002) with no FE caller yet.

### 4.2 React Query key conventions

| Query key | Description |
|---|---|
| `["hotels", params]` | `listHotels` — card grid |
| `["hotels", hotelId]` | `getHotel` — detail header |
| `["hotels", hotelId, "amenities"]` | `listAmenitiesForHotel` — chips section |
| `["hotels", "amenities", category]` | `listAmenities` — attach-dialog picker |

After any hotel mutation (create/update/archive), invalidate `["hotels"]` (all prefix keys). After amenity attach/detach, invalidate `["hotels", hotelId, "amenities"]`. After `createAmenity`, invalidate `["hotels", "amenities"]`.

### 4.3 Routes (`frontend/src/App.tsx`)

Two new lazy imports appended adjacent to the projects imports (`:37-38`):

## 5. Detailed Behavior & Edge Cases

### 5.1 `HotelsPage.tsx` — layout and behavior

**Hotel card grid**: calls `listHotels({ status: "active" })` via `useQuery({ queryKey: ["hotels", { status: "active" }], ... })`. On success, renders a responsive CSS grid (`grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 gap-4`). Each card is a shadcn/ui `<Card>`:
- **Header**: hotel name (`CardTitle`) + a star-rating display (see §5.4) + a status `<Badge variant="outline">`.
- **Body**: a thumbnail image from `photo_urls[0]` (with a neutral placeholder when `photo_urls` is empty); formatted address (`line1, city, region postal_code`); a short description (truncated).
- **Footer**: a "View" button (`<Button asChild><Link to={`/hotels/${hotel.hotel_id}`}>`) navigating to the detail page.

**"New Hotel" dialog**: a `<Button>` labeled "New Hotel" (admin-only — see §7.3) at the top-right opens a `<Dialog>` with a React Hook Form + Zod schema:
```typescript
const timeRe = /^([01]\d|2[0-3]):[0-5]\d$/;
const hotelSchema = z.object({
  name: z.string().min(1, "Name is required"),
  description: z.string().optional(),
  star_rating: z.coerce.number().int().min(1).max(5),
  address: z.object({
    line1: z.string().min(1, "Address is required"),
    line2: z.string().optional(),
    city: z.string().min(1, "City is required"),
    region: z.string().min(1, "Region is required"),
    postal_code: z.string().min(1, "Postal code is required"),
    country: z.string().min(1, "Country is required"),
  }),
  check_in_time: z.string().regex(timeRe, "HH:MM").default("15:00"),
  check_out_time: z.string().regex(timeRe, "HH:MM").default("11:00"),
  smoking: z.boolean().default(false),
  children: z.boolean().default(true),
  cancellation_text: z.string().optional(),
  pet_policy: z.string().optional(),
  photo_urls: z.string().optional(),   // newline/comma-separated, parsed on submit
});
```
The `star_rating` field renders as a 1–5 `<Select>`; check-in/out as `<Input type="time">` (or text inputs validated by `timeRe`); policy toggles (`smoking`, `children`) as switches/checkboxes. On submit it composes the nested `policies`/`contact` objects and parses `photo_urls` (`.split(/[\n,]/).map(s => s.trim()).filter(Boolean)`), then calls `useMutation({ mutationFn: createHotel, onSuccess: () => { queryClient.invalidateQueries({ queryKey: ["hotels"] }); toast.success("Hotel created"); close(); } })`. On API error it shows `toast.error(err.detail)`. The submit button is disabled while `mutation.isPending`.

**Status filter**: a shadcn/ui `<Select>` with "Active" / "Archived" / "All" options drives the `status` param of `listHotels`; the query key changes and React Query refetches. Default `"active"`.

**Empty state**: when `listHotels` returns `{items: [], count: 0}`, renders a centered "No hotels yet. Create your first hotel." card.

**Loading / flag-off**: while loading, render `<Skeleton>` card placeholders. On a 404 (flag off), render an inline callout — "Hotel management is not enabled on this platform." — as the only page content (no broken partial render).

### 5.2 `HotelDetailPage.tsx` — layout and behavior

Uses `useParams<{ hotelId: string }>()` to extract `hotelId`.

**Hotel header**: calls `getHotel(hotelId)` via `useQuery`. Renders the hotel name as `<h1>`, the star-rating display, the formatted full address, and the status badge. An "Edit" button (admin-only) opens an edit-hotel dialog (same Zod schema as create, pre-populated from the current hotel, calls `updateHotel`). An "Archive" button (admin-only, shown only when `hotel.status === "active"`) opens a confirmation `<Dialog>` ("Archive '{name}'? This hides it from the active list.") that calls `archiveHotel` and navigates back to `/hotels` on success.

**Check-in/out + policy summary**: a small `<Card>` row showing `check_in_time` / `check_out_time` and policy facts (cancellation text, pet policy, smoking allowed yes/no, children welcome yes/no) derived from `hotel.policies`. Contact details (`phone`/`email`/`website`) render here when present.

**Photo gallery**: renders `hotel.photo_urls` as a grid (or simple carousel) of `<img>` thumbnails. When `photo_urls` is empty, renders an "No photos yet" placeholder. (MVP uses URL strings only — no upload widget; photo upload is a future ticket, §10 Open Question #2.)

**Amenity chips section**: calls `listAmenitiesForHotel(hotelId)` via `useQuery({ queryKey: ["hotels", hotelId, "amenities"], ... })`. Renders each association as a `<Badge>` chip (icon + name), **grouped by `category`** (a heading per non-empty category: Connectivity, Wellness, Parking, Dining, Family, Accessibility, General). Each chip has a small "×" (admin-only) that calls `detachAmenity({ target_type: "hotel", target_id: hotelId, amenity_id })` and invalidates `["hotels", hotelId, "amenities"]`. Empty state: "No amenities yet."

**Attach-amenity dialog** (admin-only): an "Add Amenity" button opens a `<Dialog>` that lists the dictionary via `listAmenities()` (optionally filtered by a category `<Select>`); selecting one calls `attachAmenity({ target_type: "hotel", target_id: hotelId, amenity_id })`, invalidates `["hotels", hotelId, "amenities"]`, and shows a success toast. The dialog also offers a "Create new amenity" sub-form (name + category + optional icon) calling `createAmenity` then immediately attaching it. `attach_amenity` is idempotent server-side (re-attach is a no-op, HTL-002), so a double-click cannot create duplicate chips.

**404 / flag-off behavior**: if `getHotel` returns 404 (hotel not found OR flag off), render a centered error card — "Hotel not found or hotel management is not enabled." — with a "Back to Hotels" button.

**Loading state**: header `<Skeleton>` while `getHotel` loads; chip skeletons while `listAmenitiesForHotel` loads.

### 5.3 `property_type`-style label maps for amenity categories

The seven `AmenityCategory` literals (`connectivity`, `wellness`, `parking`, `dining`, `family`, `accessibility`, `general`) need human-readable labels. A local constant map is defined in the component file: `{ connectivity: "Connectivity", wellness: "Wellness", parking: "Parking", dining: "Dining", family: "Family", accessibility: "Accessibility", general: "General" }`. No i18n key required for MVP (§10 Open Question #4).

### 5.4 Star-rating display

`star_rating` is an integer 1–5. The display renders that many filled `Star` lucide icons (and 5 − rating muted/empty stars), with an `aria-label={`${star_rating} stars`}` for accessibility. A small local `<StarRating value={n} />` helper component (defined in the page file, not forked) handles both the card grid and the detail header — no external rating library.

### 5.5 Status filter and archived hotels

The grid filter defaults to `status="active"`. Setting it to `"archived"` shows archived hotels (with a muted overlay or "Archived" ribbon). **Archived hotels do NOT show a "Restore" button in MVP**: `HotelUpdateIn` (HTL-001 §model) does not include a `status` field, and `PUT /ui/hotels/{id}` therefore cannot flip status. Restore would require a dedicated endpoint not in HTL-003 scope. Archive is one-way in the MVP UI (§10 Open Question #1). (Note: HTL-001's service `archive_hotel` sets `status="archived"` via the dedicated `DELETE /ui/hotels/{id}` path; there is no symmetric un-archive route.)

### 5.6 Amenity chip grouping

`listAmenitiesForHotel` returns `AmenityAssociation[]` already hydrated with `name`/`category`/`icon` (HTL-002 `list_amenities_for` batched-hydrates each `AMEN#` child row from the `hotel_amenities` `META` rows). The FE groups them client-side by `category`; no extra fetch. Chips within a category sort by `name`.

### 5.7 Pagination — hotel card grid

`listHotels` is cursor-paginated (HTL-003 over `GSI_OWNER`, newest-first). For MVP the grid does a single-page fetch with `limit=50` (sufficient for a single hotelier's portfolio). If the response carries a non-null `cursor`, a "Load more" button at the bottom triggers a follow-up fetch with the next cursor (or `useInfiniteQuery`). "Load more" is acceptable over infinite scroll for MVP.

### 5.8 Photo URL input parsing

The "New Hotel" / "Edit Hotel" dialog accepts photos as a single multiline text field (one URL per line, commas also accepted), parsed on submit to `photo_urls: string[]`. No client-side URL validation beyond non-empty trim — the gallery simply renders whatever URLs are stored, with broken-image fallback (`onError` → placeholder).

### 5.9 Non-admin sessions

For `role=USER` sessions, all mutation controls ("New Hotel", "Edit", "Archive", "Add Amenity", chip "×") are hidden via the `isAdmin` flag (§7.3). Read-only browsing (card grid, detail page, amenity chips, photo gallery) works for any authenticated session because the GET endpoints use `require_ui_session` (HTL-003). This prevents confusing 403s.

### 5.10 Idempotent create feedback

`create_hotel` is idempotent on `(owner_sub, name)` (HTL-001) and `create_amenity` is idempotent on `name` (HTL-002). A double-submit returns the existing row without error; the FE disables the submit button while pending and invalidates the list query, so the existing card simply reappears — no duplicate, no error toast.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no dev-mode branches in backend

HTL-004 is a frontend + tests ticket. Its only backend interaction is through the HTL-003 router and HTL-001/002 service functions, all of which enforce SECOPS-007 (no `if S.dev_mode` branch in business logic; the same `T.*` handles in both environments — moto intercepts boto3 in dev, real DynamoDB in prod) per the HTL "Cross-cutting constraints" and the `app/services/inventory.py:27-28` template. The frontend has no concept of dev mode — it calls the same `/ui/hotels*` endpoints in both environments.

### 7.2 SECOPS-007 — hermetic pytest does not use `dev_mode`

`tests/test_htl_hotels_amenities.py` toggles `S.hotel_pms_enabled` via `object.__setattr__` but never sets `S.dev_mode`. All service calls go through the same DynamoDB code path with moto intercepting boto3 — identical to the dev/prod parity approach in every existing hermetic test (`tests/test_gap_0286_0287_kyc_partner_api.py`, etc.).

### 7.3 Security — admin-only mutations

All create/update/archive (hotels) and create/attach/detach (amenities) operations are gated by `require_admin_or_root_csrf` at the HTL-003 router layer (`app/auth/policy.py:100`) — the same auth split as `app/routers/inventory.py:48,65,81`. The FE hides mutation controls from non-admin sessions using `getRoleFromAccessToken(useAuthStore(s => s.accessToken))` (`frontend/src/lib/adminCapabilities.ts:22`; pattern `TicketsPage.tsx:43-44`) — NOT a non-existent `role` field on `useAuthStore`. Example: `const role = getRoleFromAccessToken(useAuthStore(s => s.accessToken)); const isAdmin = role === "admin" || role === "root";`. The CSRF token is auto-injected as `X-CSRF-Token` from the `ui_csrf` cookie by `client.ts:181` on every mutating call.

### 7.4 Money-safety — HTL-004 does not touch billing

HTL-004 is a pure hotel-listing + amenity-management UI. It does not display or handle payments, ledger entries, or any monetary value. No mutation here touches `billing_shared.py` (`new_ledger_entry` `:224`, `settle_or_reverse_ledger` `:262`, `apply_balance_delta` `:83`, `compute_due` `:158`). Folios, deposits, and stay pricing are explicitly out of scope (gap analysis §C / §B) and are future net-new tickets. `hotels.ts` never imports from `api/endpoints/billing.ts`, and the HTL services it calls never import `billing_shared`.

### 7.5 Idempotency

The "New Hotel" dialog calls `createHotel` once per submit; the backend `create_hotel` is idempotent on `(owner_sub, name)` (HTL-001) — a double-submit returns the existing hotel. `attachAmenity` is idempotent (re-attach writes no duplicate child row, HTL-002). The UI disables submit buttons while `useMutation.isPending`, but backend idempotency is the safety net for races.

### 7.6 Audit trail

Backend mutations emit best-effort audit events via `_audit()` (the `app/services/inventory.py:92-98` wrapper, copied into `hotel_pms.py` per HTL-001/002): `hotel.created`, `hotel.updated`, `hotel.archived`, `hotel.amenity.created`, `hotel.amenity.attached`, `hotel.amenity.detached`. HTL-004 adds no frontend audit emission — the backend is the authoritative audit source.

## 10. Open Questions / Assumptions

1. **No "un-archive / restore" path — `HotelUpdateIn` does NOT include `status`.** HTL-001's `HotelUpdateIn` is a partial over the persisted fields *minus* `status` (status is changed only by the dedicated `archive_hotel` / `DELETE /ui/hotels/{id}` path). A restore via `PUT … {status:"active"}` would be rejected (the field is not in the model). **Assumption**: MVP omits the restore UI and treats archive as one-way; a future `POST /ui/hotels/{id}/restore` endpoint (not in HTL-003 scope) would be required. The TypeScript `HotelUpdateIn` in §3.1 correctly omits `status`.

2. **Photo upload vs. URL strings.** HTL-001 stores `photo_urls` as a list of URL strings; there is no hotel photo-upload endpoint in the HTL cluster. **Assumption**: the MVP dialog accepts URL strings (multiline input) and the gallery renders them with broken-image fallback. A real uploader (reusing `filemanager.py` / the S3 mock, like the newsfeed/file picker) is a future ticket.

3. **`list_hotels` response shape is `{items, count, cursor}`.** Per the HTL-003 spec, `list_hotels` returns the `host_inventory.list_hosts` `{items, count, cursor}` shape (CLAUDE.md) — NOT a `{hotels: [...]}` envelope and NOT a bare array. `HotelListOut` in §3.1 uses `items`. **If** the implemented HTL-003 router instead returns `{hotels: [...]}` (PROP-005 used `properties`), the FE type + `HotelsPage` must read `.hotels` — the spec assumes `items` per the HTL-003 ticket text. Confirm against the implemented router.

4. **`i18nKey` for the sidebar nav item.** The nav items carry an optional `i18nKey` (`Sidebar.tsx:87`). **Assumption**: add `"nav.hotels"` to the translation file (`public/locales/en/translation.json` or equivalent) if one exists; otherwise the `label` string ("Hotels") is the fallback (the field is optional in the `NavItem` interface).

5. **`Hotel` lucide icon vs. `Building2`.** `frontend/node_modules/lucide-react/dist/esm/icons/hotel.js` exists, so `Hotel` is the chosen nav icon (more apt than the `Building2` used for "Organizations"). **Assumption**: importing `Hotel` from `lucide-react` resolves; if a stricter icon allowlist exists, fall back to `Building2` (already imported at `Sidebar.tsx:51`).

6. **Amenity category label map.** The seven category literals need display labels. **Assumption**: a local component-level map provides them (§5.3); no i18n key required for MVP.

7. **Admin-only controls derive role from the JWT.** `useAuthStore` has no `role` field; role is decoded via `getRoleFromAccessToken(accessToken)` (`frontend/src/lib/adminCapabilities.ts:22`, pattern `TicketsPage.tsx:43-44`). **Confirmed** against the codebase — do NOT read a `role` property off the store.
