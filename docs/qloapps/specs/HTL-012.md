# HTL-012 — Availability read/calendar API + booking-time availability check + router

**Type**: Feature | **Priority**: P1 | **Estimate**: 2d
**Source**: `docs/qloapps/AVAILABILITY_INVENTORY_TICKETS.md` §HTL-012 + "Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §B

---

## 1. Summary & Goal

HTL-012 lands the two *read-side* primitives at the heart of a hotel PMS — the per-date availability **calendar** and the booking-time **availability check** — and exposes the entire hotel-availability service layer over HTTP via a new `hotel_availability_router` (prefix `/ui/hotels`), registered in `app/main.py` immediately adjacent to `inventory_router` (`app/main.py:311,877`). The ticket delivers exactly **8 endpoints** and **2 net-new service functions** on `app/services/hotel_availability.py`.

The two service additions are:

1. **`availability_calendar(hotel_id, start_date, end_date) -> dict`** — the hotel-wide availability calendar across **all** room types for a date range. It queries the `GSI_HOTEL_DATE` index (PK=`hotel_id`, SK=`date` `between(start, end)`) declared by HTL-010, groups the rows by `room_type_id`, and returns `{"hotel_id", "start_date", "end_date", "room_types": {room_type_id: [AvailabilityDayOut, ...]}}`. This is a pure GSI aggregation — **no full table scan** — and is the data source for the FE calendar grid (HTL-013).

2. **`check_availability(hotel_id, room_type_id, checkin, checkout, rooms_needed) -> dict`** — the booking-time check. It calls `get_availability(...)` (HTL-010) for the stay span `[checkin, checkout)` (checkout exclusive) and answers a single question: is `available >= rooms_needed` on **every** night of the stay? The answer is the **intersection across the whole span** — a room type is bookable for a stay **iff every single night** has enough rooms. This is the structural distinction the OFBiz scalar inventory counter cannot express (`docs/ofbiz/specs/OFB-003.md`): a scalar `(sku, location)` row has *one* number and no concept of "every night across a span" (`QLOAPPS_GAP_ANALYSIS.md:58-60`). It returns `{"available": bool, "rooms_needed": int, "per_night": [{"date", "remaining", "sufficient"}, ...], "min_remaining": int}` where `min_remaining` is the binding (smallest) night.

> **Forward reference (HTL-017).** The intersection-across-the-span check is the reusable primitive the stay-search engine (HTL-017, a separate Tier-2 cluster — `QLOAPPS_GAP_ANALYSIS.md:47,140,176`) calls **per candidate room type** to filter search results. HTL-012 answers only "are there rooms?" — the summed multi-night **price** half (`QLOAPPS_GAP_ANALYSIS.md:58-60`) lives in the rate-plan cluster and is explicitly out of scope here.

The router is a thin, policy-correct HTTP façade. Beyond delegating to the service layer it contributes three non-trivial concerns: an **auth split** (reads → `require_ui_session`; mutations → `require_admin_or_root_csrf`), a **literal-before-dynamic route declaration order**, and a **flag-gated 404 short-circuit** via `_require_enabled()`. With `HOTEL_PMS_ENABLED=false` (the default) the router is still mounted but every handler is a silent 404 no-op, and the platform is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Service layer is foundational on HTL-010/011

HTL-012 assumes both predecessor tickets are merged:

- **HTL-010** (`docs/qloapps/AVAILABILITY_INVENTORY_TICKETS.md` §HTL-010) — the `hotel_availability` DynamoDB table (PK=`availability_pk` = composite `"{hotel_id}#{room_type_id}"`, SK=`DATE#{YYYY-MM-DD}`), the `GSI_HOTEL_DATE` index (PK=`hotel_id`, SK=`date`, both `S`; `attr_types={"updated_at": "N"}`), the `HOTEL_PMS_ENABLED` master flag plus `hotel_availability_table_name` / `hotel_hold_ttl_seconds` settings, the `T.hotel_availability` table handle, and the `_flag_on()` / `_require_enabled()` / `_audit()` / `_availability_pk()` / `_date_sk()` / `_date_range()` / `_available()` helpers. Critically it provides `get_availability(hotel_id, room_type_id, checkin, checkout) -> list[dict]` — the per-date rows for the stay span `[checkin, checkout)` with missing dates surfaced as **zeroed virtual rows** (`available = 0`), and `set_total_rooms` / `get_day`. The Pydantic models `AvailabilityDayOut` / `AvailabilitySetIn` / `AvailabilityDayIn` are defined in `app/models.py` by HTL-010.
- **HTL-011** (`docs/qloapps/AVAILABILITY_INVENTORY_TICKETS.md` §HTL-011) — the hold lifecycle (`hold_rooms`, `release_hold`, `expire_due_holds`) and the per-date controls (`set_overbooking_allowance`, `set_min_max_availability`), plus the `GSI_HOLD_EXPIRY` index (`attr_types={"expires_at": "N"}`) and the `HoldRoomsIn` / `HoldOut` / `OverbookingSetIn` / `MinMaxSetIn` Pydantic models. HTL-012's router exposes these mutation services over HTTP.

No hotel-availability router of any kind exists today. `grep -rn "hotel_availability_router\|ui/hotels" app/` returns no results, and `app/routers/hotel_availability.py` does not exist. The HTL-010/011 service functions are not yet reachable over HTTP.

### 2.2 Canonical router idiom — `app/routers/inventory.py`

`app/routers/inventory.py` is the exact structural template (the cross-cutting constraints mandate mirroring it "at every level"):

`hotel_availability_router` mirrors this pattern at every level.

### 2.3 Auth dependencies

- **`require_ui_session`** (`app/services/sessions.py:330`) — async FastAPI `Depends`; validates the cookie-based UI session or a Bearer JWT, and returns a `dict` carrying `user_sub`, `role`, etc. Used for all read (GET) endpoints.
- **`require_admin_or_root_csrf`** (`app/auth/policy.py:100-106`) — async FastAPI dependency; calls `enforce_cookie_csrf(request)` (`app/auth/policy.py:71-97`) then `require_roles(user, {Role.ADMIN, Role.ROOT})` (`app/auth/policy.py:106`); raises HTTP 403 on CSRF failure, on missing role, or on role mismatch. Used for all mutation (PUT/POST) endpoints.
- **`AuthenticatedUser`** dataclass (`app/auth/deps.py:126`) — the type returned by `require_admin_or_root_csrf`; carries `.sub` (the `user_sub`), `.role`, and `.admin_profile`.

### 2.4 Route-ordering constraint (FastAPI path-param capture)

FastAPI matches routes **in declaration order**. The `/ui/hotels/{hotel_id}/availability/...` surface mixes three literal-segment routes — `/availability/calendar`, `/availability/check`, and `/availability/holds/{hold_id}/release` — with a dynamic `/availability/{room_type_id}` capture. If `/availability/{room_type_id}` is declared **before** the literal routes, FastAPI silently captures `calendar`, `check`, or `holds` as a `room_type_id` path param and routes the request to the `get_availability` handler — which then reads a non-existent room type and returns a misleading sold-out / empty result rather than the intended calendar/check/release behaviour.

CLAUDE.md documents this exact class of bug for two existing cases:

- KYC: `/templates` declared before `/{case_id}` (CLAUDE.md §"KYC template-signature endpoints").
- Audit export: `/schedules` declared before `/{export_id}` (CLAUDE.md §"Scheduled audit export reports").

…and the open-property precedent is `/portfolio/occupancy` declared before `/{property_id}` (`docs/open-property/specs/PROP-004.md` §2.4, `docs/open-property/PROPERTY_UNITS_TICKETS.md` §PROP-004). HTL-012 declares the three literal routes **before** the dynamic `/availability/{room_type_id}` route. This is the single most important implementation detail of the router — a wrong order appears to work for every other endpoint but silently breaks `/availability/calendar` and `/availability/check`.

### 2.5 `main.py` registration adjacent to `inventory_router`

`app/main.py:311` imports `inventory_router`; `app/main.py:877` includes it. `hotel_availability_router` is imported on the line immediately after the `inventory_router` import (`:312`) and included on the line immediately after `app.include_router(inventory_router)` (`:878`). This keeps the commerce/ERP/PMS vertical routers grouped together and follows the established pattern for flag-gated additive routers (the same placement open-property's PROP-004 uses, `docs/open-property/specs/PROP-004.md` §2.5).

### 2.6 The span-intersection primitive the gap analysis demands

`QLOAPPS_GAP_ANALYSIS.md:58-60` records that "a stay-search engine (date-range + occupancy → available room types …)" and "a multi-night price computation across a check-in→check-out span … are the heart of a hotel PMS and are net-new." The OFBiz contrast row (`docs/ofbiz/specs/OFB-003.md`, scalar `(sku, location)` inventory) has **no date dimension** — there is no "every night", there is one number. `check_availability`'s "every night across the span" is therefore a genuinely net-new primitive, not a port. HTL-012 delivers the availability half; the summed-price half is a separate rate-plan cluster ticket.

## 3. Data Model

HTL-012 introduces **no new DynamoDB tables, no new GSIs, no new DynamoDB attributes, and no new Pydantic models**. The `hotel_availability` table (PK=`availability_pk`, SK=`sk`), the `GSI_HOTEL_DATE` / `GSI_HOLD_EXPIRY` indexes, and the `AvailabilityDayOut` / `AvailabilitySetIn` / `AvailabilityDayIn` / `HoldRoomsIn` / `HoldOut` / `OverbookingSetIn` / `MinMaxSetIn` models were all declared by HTL-010/011. This section documents the models that flow through the router and the **shape of the two net-new service return values** (which are returned as plain dicts, not Pydantic models — see §4.3/§4.4).

### 3.1 Models flowing through the router

| Endpoint | Request body model | Response shape |
|---|---|---|
| `GET /ui/hotels/{hotel_id}/availability/calendar` | — (query `start_date`, `end_date`) | `dict` — calendar projection (§3.2) |
| `GET /ui/hotels/{hotel_id}/availability/check` | — (query `room_type_id`, `checkin`, `checkout`, `rooms_needed`) | `dict` — check projection (§3.3) |
| `GET /ui/hotels/{hotel_id}/availability/{room_type_id}` | — (query `checkin`, `checkout`) | `List[AvailabilityDayOut]` (the span rows) |
| `PUT /ui/hotels/{hotel_id}/availability/{room_type_id}/total-rooms` | `AvailabilitySetIn` | `List[AvailabilityDayOut]` |
| `POST /ui/hotels/{hotel_id}/availability/{room_type_id}/hold` | `HoldRoomsIn` | `HoldOut` |
| `POST /ui/hotels/{hotel_id}/availability/holds/{hold_id}/release` | — | `HoldOut` |
| `PUT /ui/hotels/{hotel_id}/availability/{room_type_id}/overbooking` | `OverbookingSetIn` | `List[AvailabilityDayOut]` |
| `PUT /ui/hotels/{hotel_id}/availability/{room_type_id}/min-max` | `MinMaxSetIn` | `List[AvailabilityDayOut]` |

`AvailabilityDayOut` (HTL-010) carries all persisted fields (`hotel_id`, `room_type_id`, `date`, `total_rooms`, `booked`, `held`, `overbooking_allowance`, `min_availability`, `max_availability`, `updated_at`) plus the derived `available` (`= total_rooms + overbooking_allowance - booked - held`, per HTL-010's `_available()`).

### 3.2 `availability_calendar` return shape

```jsonc
{
  "hotel_id": "h_paris_01",
  "start_date": "2026-07-01",
  "end_date":   "2026-07-03",
  "room_types": {
    "rt_deluxe":   [ {AvailabilityDayOut for 07-01}, {…07-02}, {…07-03} ],
    "rt_standard": [ {AvailabilityDayOut for 07-01}, {…07-02}, {…07-03} ]
  }
}
```

`room_types` is a map keyed by `room_type_id`; each value is a date-ordered list of `AvailabilityDayOut` for the requested range. Dates with no seeded row simply do not appear in that room type's list (the calendar grid in HTL-013 fills gaps as zero/sold-out on render — `availability_calendar` does **not** synthesise virtual zero rows; only `get_availability` does, for the stay-check span). Because `GSI_HOTEL_DATE`'s SK is the ISO `date` (lexical == chronological), the `between(start, end)` query returns rows date-ordered for free; the service groups them in a single pass.

### 3.3 `check_availability` return shape

```jsonc
{
  "available": false,            // true iff EVERY night has remaining >= rooms_needed
  "rooms_needed": 2,
  "per_night": [
    {"date": "2026-07-01", "remaining": 5, "sufficient": true},
    {"date": "2026-07-02", "remaining": 1, "sufficient": false},   // binding night
    {"date": "2026-07-03", "remaining": 4, "sufficient": true}
  ],
  "min_remaining": 1             // = min(remaining) across per_night (the binding constraint)
}
```

`available` is the AND-reduction of every `sufficient` flag (the **intersection** across the whole span). `min_remaining` is `min(remaining for each night)`. A missing/zeroed night (`get_availability` surfaces it as `available = 0`) forces `sufficient = false` for that night ⇒ `available = false`.

### 3.4 Query parameters

- **`/availability/calendar`** — `start_date: str`, `end_date: str` (both `YYYY-MM-DD`, required). 422 if either is malformed or `end_date < start_date` (validated in the service via the HTL-010 `_date_range` helper / date parsing).
- **`/availability/check`** — `room_type_id: str` (required), `checkin: str`, `checkout: str` (both `YYYY-MM-DD`, required), `rooms_needed: int = 1` (≥ 1; 422 otherwise). `checkout` must be strictly after `checkin` (a zero-night span is 422).
- **`/availability/{room_type_id}`** — `checkin: str`, `checkout: str` (`YYYY-MM-DD`, required).

No request body for any GET endpoint. The PUT/POST endpoints carry the HTL-010/011 Pydantic bodies (§3.1).

## 4. API / Service Design

### 4.1 Service additions: `app/services/hotel_availability.py`

Two net-new functions are appended to the HTL-010/011 service module. Both call `_require_enabled()` first (the flag-off 404 contract, `app/services/inventory.py:54-56` analogue). Neither contains an `if S.dev_mode` branch (SECOPS-007).

```python
def availability_calendar(hotel_id: str, start_date: str, end_date: str) -> dict:
    """Hotel-wide availability calendar across ALL room types for a date range.

    Pure GSI_HOTEL_DATE aggregation (no scan). Rows grouped by room_type_id.
    """
    _require_enabled()
    _validate_date_range(start_date, end_date)   # 422 on malformed / end < start
    room_types: dict[str, list[dict]] = {}
    last_key = None
    while True:
        kwargs = dict(
            IndexName="GSI_HOTEL_DATE",
            KeyConditionExpression=Key("hotel_id").eq(hotel_id)
                & Key("date").between(start_date, end_date),
        )
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key
        resp = T.hotel_availability.query(**kwargs)
        for item in resp.get("Items", []):
            rt = item.get("room_type_id")
            room_types.setdefault(rt, []).append(_day_out(item))
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
    for rt in room_types:                         # date-ordered within each room type
        room_types[rt].sort(key=lambda d: d["date"])
    return {
        "hotel_id": hotel_id,
        "start_date": start_date,
        "end_date": end_date,
        "room_types": room_types,
    }


def check_availability(
    hotel_id: str, room_type_id: str, checkin: str, checkout: str, rooms_needed: int = 1,
) -> dict:
    """Booking-time check: is `available >= rooms_needed` on EVERY night of [checkin, checkout)?

    The answer is the intersection across the whole span. A single insufficient
    (or missing/zeroed) night ⇒ available = False. min_remaining = binding night.
    """
    _require_enabled()
    if rooms_needed < 1:
        raise HTTPException(status_code=422, detail="rooms_needed must be >= 1")
    rows = get_availability(hotel_id, room_type_id, checkin, checkout)  # HTL-010; [checkin, checkout)
    per_night: list[dict] = []
    for row in rows:
        remaining = _to_int(row.get("available"))
        per_night.append({
            "date": row.get("date"),
            "remaining": remaining,
            "sufficient": remaining >= rooms_needed,
        })
    available = bool(per_night) and all(n["sufficient"] for n in per_night)
    min_remaining = min((n["remaining"] for n in per_night), default=0)
    return {
        "available": available,
        "rooms_needed": rooms_needed,
        "per_night": per_night,
        "min_remaining": min_remaining,
    }
```

- `_day_out(item)` is the HTL-010 projection helper that maps a stored row to the `AvailabilityDayOut`-shaped dict with the derived `available` recomputed (analogous to `inventory._record_out`, `app/services/inventory.py:101-115`).
- `_validate_date_range` (HTL-010 helper, or a small local guard) raises `HTTPException(422)` for a malformed `YYYY-MM-DD` or `end_date < start_date`.
- `_to_int` is the HTL-010/inventory Decimal→int coercion helper (`app/services/inventory.py:67-73`) — DynamoDB returns numerics as `Decimal`; `remaining`, `min_remaining`, and `rooms_needed` must be plain `int` in the response.
- The calendar query loops on `LastEvaluatedKey`: per the CLAUDE.md gotcha "DDB FilterExpression doesn't reduce page size" / the 1MB page limit, a wide date range across many room types can exceed one page; the loop guarantees completeness. No `FilterExpression` is used — the `GSI_HOTEL_DATE` key condition is exact, so every returned row belongs in the result.

`check_availability` deliberately delegates the per-night sourcing to `get_availability` (HTL-010) rather than re-querying — `get_availability` already (a) restricts to the stay span `[checkin, checkout)` with **checkout exclusive** (the guest does not occupy a room the night of departure), and (b) surfaces never-seeded dates as zeroed virtual rows. `check_availability` adds only the per-night sufficiency reduction. This keeps the span/checkout-exclusion/zero-virtual logic single-sourced.

## 5. Detailed Behavior & Edge Cases

### 5.1 Route-ordering correctness — literal before dynamic

The router declares `get_availability_calendar` (`/availability/calendar`), `check_availability` (`/availability/check`), and `release_hold` (`/availability/holds/{hold_id}/release`) **before** `get_room_type_availability` (`/availability/{room_type_id}`). FastAPI matches in declaration order; without this, a request to `/ui/hotels/h1/availability/calendar?start_date=…&end_date=…` would bind `room_type_id="calendar"` and dispatch to `get_room_type_availability`, which would then call `get_availability(h1, "calendar", …)` and return zeroed virtual rows for a phantom room type — a silent, misleading bug that passes every other endpoint's tests. The `/availability/holds/{hold_id}/release` route is two literal segments deep (`holds` + `release`) so it cannot collide with the single-segment `/{room_type_id}`, but it is declared with the other literals for clarity and defence-in-depth. This is the same gotcha as KYC `/templates`-before-`/{case_id}` and audit-export `/schedules`-before-`/{export_id}` (CLAUDE.md), and open-property `/portfolio/occupancy`-before-`/{property_id}` (`docs/open-property/specs/PROP-004.md` §5.1).

### 5.2 Checkout night is excluded from the span

`check_availability` and `get_room_type_availability` operate on `[checkin, checkout)` — checkout exclusive. A guest checking out on `2026-07-03` does **not** occupy a room that night, so `2026-07-03` is not part of the stay span. Consequence (and acceptance criterion): **a stay whose checkout date is itself sold-out is STILL bookable**, because the checkout night is never inspected. This exclusion lives entirely in `get_availability` (HTL-010, the `between(DATE#checkin, DATE#checkout-1day)` key query); `check_availability` inherits it by delegating.

### 5.3 The intersection / binding-night semantics

`available` is `all(sufficient for every night) and per_night is non-empty`. A single insufficient night flips the whole stay to unbookable — this is the intersection across the span (`AVAILABILITY_INVENTORY_TICKETS.md` §HTL-012). `min_remaining = min(remaining)` is the **binding constraint** — the smallest per-night remaining, which is the room count that gates the entire stay. If the caller passes `rooms_needed=2` and the binding night has `remaining=1`, then `available=false` and `min_remaining=1` tells the caller exactly how short the stay is at its tightest point.

### 5.4 Missing / never-seeded night ⇒ sold out

A date that was never seeded by `set_total_rooms` has no DynamoDB row. `get_availability` (HTL-010) surfaces it as a **zeroed virtual row** (`available = 0`) rather than omitting it or erroring (the `inventory.get_or_zero` analogue, `app/services/inventory.py:158-173`). `check_availability` therefore sees `remaining = 0` for that night ⇒ `sufficient = false` ⇒ `available = false`. This is the safe default: an unknown date reads as sold-out, never as a phantom availability.

### 5.5 `availability_calendar` does not synthesise virtual rows

Unlike the stay-check path, the calendar projection returns only the rows that actually exist in `GSI_HOTEL_DATE` for the range — a never-seeded date simply does not appear in that room type's list. The FE grid (HTL-013) renders missing cells as zero/sold-out. This keeps the calendar a faithful read of persisted state (and avoids fabricating a potentially huge dense matrix of virtual rows over a long range × many room types). The contract difference between the two reads is intentional and documented here so HTL-013 renders gaps correctly.

### 5.6 Empty / degenerate ranges and spans

- `availability_calendar` with a range that has no seeded rows returns `{"hotel_id", "start_date", "end_date", "room_types": {}}` — an empty map, HTTP 200, no error.
- `check_availability` where `get_availability` returns an empty list (which would only happen for a zero-night `[checkin, checkin)` span) returns `{"available": false, "rooms_needed": …, "per_night": [], "min_remaining": 0}` — `available` is `false` because `per_night` is empty (a zero-night stay is not bookable). The router/service rejects a non-increasing span (`checkout <= checkin`) with 422 before reaching this branch.
- Malformed `YYYY-MM-DD` query params ⇒ 422 (service date validation).

### 5.7 409 on hold conflict propagates unchanged

`POST /availability/{room_type_id}/hold` delegates to `hold_rooms` (HTL-011), which raises `HTTPException(409)` when any night of the span lacks capacity, after compensating-rollback of the earlier nights it already incremented. The router does not catch or remap this — the 409 propagates to the client, and no partial hold persists.

### 5.8 Decimal coercion in responses

DynamoDB returns numerics as `Decimal`. Every integer-semantics field in the responses (`remaining`, `min_remaining`, `rooms_needed`, and the `AvailabilityDayOut` numeric fields `total_rooms` / `booked` / `held` / `overbooking_allowance` / `available` / `updated_at` / etc.) must be plain `int`. The service-layer `_day_out` / `_to_int` helpers (HTL-010, modelled on `app/services/inventory.py:67-73,101-115`) coerce before returning dicts; the `AvailabilityDayOut` / `HoldOut` Pydantic models coerce again on field assignment. No extra coercion is needed in the router.

### 5.9 Flag-off behaviour

When `HOTEL_PMS_ENABLED=false` (the default), every handler's first statement `_require_enabled()` delegates to `ha._require_enabled()` (HTL-010), which raises `HTTPException(404, "Hotel PMS is not enabled")`. The router is still mounted via `app.include_router(hotel_availability_router)` — the flag check is at the handler level, not the mount level (identical to `inventory_router`, `app/routers/inventory.py:32-33,38`). With the flag off the platform is byte-for-byte unchanged; no DynamoDB reads or writes occur.

### 5.10 CSRF on mutation endpoints

`require_admin_or_root_csrf` (`app/auth/policy.py:100-106`) calls `enforce_cookie_csrf(request)` (`app/auth/policy.py:71-97`) before the role check. For cookie-authenticated browser requests: both `x-csrf-token` header and `ui_csrf` cookie must be present and match. For Bearer-token API clients (no `ui_session` cookie): CSRF is not applicable and `enforce_cookie_csrf` returns early (`app/auth/policy.py:87-89`). Mutation endpoints are therefore reachable by Bearer-auth API clients without a CSRF header — consistent with every other admin endpoint on the platform.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/routers/hotel_availability.py` and the two new service functions contain **no** `if S.dev_mode` branch. The same handler/service code runs in dev (moto-intercepted boto3 / local DynamoDB) and prod (real DynamoDB) — the same `T.hotel_availability` handle in both environments (the cross-cutting "Dev/prod parity" constraint, mirroring `app/services/inventory.py:27-29`). The `app/core/dev_s3.py` in-process moto interception is transparent to this router (no S3 is touched here at all). `grep -n "dev_mode" app/routers/hotel_availability.py` must return nothing.

### 7.2 Idempotency

- **`GET /availability/calendar`, `GET /availability/check`, `GET /availability/{room_type_id}`** — pure reads; naturally idempotent, no mutation.
- **`PUT /availability/{room_type_id}/total-rooms`, `/overbooking`, `/min-max`** — absolute SETs over a date range; repeated identical calls converge to the same persisted state (`updated_at` advances each call — not idempotent in timestamp, acceptable).
- **`POST /availability/{room_type_id}/hold`** — each successful call creates a distinct `hold_id`; not idempotent by design (two hold requests are two holds). A conflicting hold raises 409 with full compensating rollback (no partial state).
- **`POST /availability/holds/{hold_id}/release`** — idempotent: the HTL-011 status-CAS (`status = active` guard) makes a double-release a no-op that returns the already-terminal `HoldOut`.

### 7.3 Security

- **Mutation auth**: all PUT/POST endpoints require `require_admin_or_root_csrf` — role `ADMIN` or `ROOT` plus CSRF for cookie-auth clients.
- **Read auth**: GET endpoints require `require_ui_session` — any authenticated user (USER, ADMIN, ROOT). No per-hotel ownership enforcement at the router layer for reads (single-platform deployment assumption; see §10.1).
- **CSRF**: `enforce_cookie_csrf` (`app/auth/policy.py:71-97`) validates `x-csrf-token` header == `ui_csrf` cookie for all non-GET cookie-auth requests; Bearer-auth (API-key) clients are exempt (`app/auth/policy.py:87-89`).
- **Path traversal**: `hotel_id`, `room_type_id`, `hold_id` are FastAPI path parameters constrained by URL encoding; no filesystem paths or shell commands are involved — no traversal risk. The composite `availability_pk = "{hotel_id}#{room_type_id}"` is built server-side by HTL-010's `_availability_pk`; a `#` inside a supplied `hotel_id`/`room_type_id` only mis-partitions that caller's own writes, never another's (it cannot escape the key namespace).
- **No public exposure yet**: per the ticket, `GET:/ui/hotels/...` read routes are added to API-key route exemptions only if a public booking surface needs them — that is deferred to the storefront cluster and is **not** in scope for HTL-012.

### 7.4 Money-safety

HTL-012 does **not** touch any billing table, billing service, or payment provider. The router imports only `hotel_availability`, the HTL-010/011 Pydantic models, and the auth dependencies — no `billing_shared`, `new_ledger_entry`, `compute_due`, `apply_balance_delta`, or any Stripe/PayPal/CCBill client. `check_availability` answers "are there rooms?" only; the monetary "what does it cost?" half (summed multi-night/occupancy price) is a separate rate-plan cluster ticket (`QLOAPPS_GAP_ANALYSIS.md:58-60,140`) and will route every monetary row through `billing_shared.new_ledger_entry` when built. HTL-012 has zero financial invariants to enforce.

### 7.5 Audit trail

The router does not call `_audit()` directly. The two net-new functions are **reads** and emit no audit events (consistent with `inventory.get_inventory` / `get_availability`, which do not audit). The mutation endpoints' audit events (`hotel.availability.set_total`, `hotel.hold.created`, `hotel.hold.released`, `hotel.availability.set_overbooking`, `hotel.availability.set_min_max`) are emitted by the HTL-010/011 service functions via the best-effort `_audit()` lazy-import wrapper (modelled on `app/services/inventory.py:92-98`); audit failure never propagates to the HTTP caller.

## 10. Open Questions / Assumptions

### 10.1 Multi-tenant hotel isolation on GET endpoints

Read endpoints do not enforce that the caller's `user.sub` matches an owner of `hotel_id`. Any authenticated user with a valid session can read any hotel's calendar/availability by ID.

**Assumption**: single-platform deployment where admins/root operate the same hotel group. If multi-tenant isolation is required (a hotelier on tenant A cannot read tenant B's availability), an ownership check must be added to the read handlers (fetch a hotel-ownership record, compare to `session["user_sub"]`, raise 403/404 on mismatch) — a non-breaking additive change. Note the QloApps codebase has no hotel-ownership table yet; that is a Tier-1 prerequisite tracked separately.

### 10.2 `availability_calendar` virtual-row contract vs `get_availability`

`availability_calendar` returns only persisted rows (gaps absent, §5.5) whereas `check_availability`/`get_availability` synthesise zeroed virtual rows for missing nights (§5.4). The asymmetry is deliberate: the calendar is a faithful read for grid rendering, the stay-check must treat unknown nights as sold-out for booking safety.

**Assumption**: HTL-013's grid renderer fills absent calendar cells as zero/sold-out client-side. If the product later wants a dense server-side matrix, `availability_calendar` can synthesise virtual rows over the full range × room-type cross product — an additive follow-up.

### 10.3 Calendar page-size / range cap

`availability_calendar` loops on `LastEvaluatedKey` to assemble a complete result, but a pathologically wide range (years) × many room types could assemble a very large payload.

**Assumption**: callers request bounded ranges (a month or two for a grid view). A hard server-side cap on `(end_date - start_date)` (e.g. ≤ 370 days, 422 otherwise) can be added as a non-breaking guard if abuse is observed.

### 10.4 `check_availability` is a non-locking read

`check_availability` is a point-in-time read with no reservation. Between the check and a subsequent `hold_rooms`, capacity can change (another booker). This is correct and intentional — the **authoritative** atomicity is the per-night conditional decrement in `hold_rooms` (HTL-011, the `available >= :q` CAS, `app/services/inventory.py:362-372` analogue), which is the single point that resolves the oversell race. `check_availability` is an advisory pre-flight that powers the calendar and stay-search (HTL-017) UX; it does not and must not lock.

### 10.5 `available` for a zero-night span

A degenerate `[checkin, checkin)` (zero nights) yields `per_night == []` and `available == False` (§5.6). The router rejects `checkout <= checkin` with 422 before this branch is reached, so the empty-`per_night` path is defensive only.

**Assumption**: a stay must be ≥ 1 night; the 422 guard is the primary defence and the `False` fallback is belt-and-braces.
