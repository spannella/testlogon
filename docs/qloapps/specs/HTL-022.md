# HTL-022 — Front-desk query service: arrivals / departures / in-house / occupancy snapshot

**Type**: Feature | **Priority**: P1 | **Estimate**: 2d
**Source**: `docs/qloapps/FRONT_DESK_TICKETS.md` §HTL-022 + "Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C row "Front desk (arrivals/departures/in-house, walk-in, assign room, check-in/out, room-move)"

---

## 1. Summary & Goal

HTL-022 delivers the **read-only front-desk query service** — the four operational "today"
views every hotel front desk needs, expressed as a thin layer of GSI-backed queries over the
existing reservation and room entities. It owns **no durable record** and adds **no DynamoDB
table**: it composes queries over the HTL-018 `hotel_reservations` table (a forward dependency
in the separate Tier-2 reservations cluster, `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md`
§HTL-018) and the HTL-006 `hotel_rooms` table (`docs/qloapps/specs/HTL-006.md`).

The deliverables are four service functions in a **new** `app/services/hotel_front_desk.py`:

1. **`arrivals_today(hotel_id, *, date=None, ...)`** — every reservation arriving today (its
   `checkin == date`) that is `confirmed` and not yet checked in. Sourced from the HTL-018
   hotel+check-in-date GSI. Paginated `{rows, count, cursor}`.
2. **`departures_today(hotel_id, *, date=None, ...)`** — every reservation departing today (its
   `checkout == date`) that is still `checked_in`. Paginated `{rows, count, cursor}`.
3. **`in_house(hotel_id, *, ...)`** — every guest currently `checked_in`, regardless of date,
   from the HTL-018 hotel+status GSI. Paginated `{rows, count, cursor}`.
4. **`occupancy_snapshot(hotel_id, *, date=None)`** — the live occupancy snapshot for `date`:
   physical rooms total / occupied / available / out-of-service + occupancy rate +
   arrivals/departures/in-house counts. Pure GSI aggregation.

Every entrypoint is gated by the master flag `HOTEL_PMS_ENABLED` (default `false`, landed in
HTL-010/HTL-001) via `_require_enabled()` → **404 when off**, mirroring the
`INVENTORY_RESERVATIONS_ENABLED` contract at `app/services/inventory.py:50-56`. Every query
goes through a GSI — **no full table scan anywhere**. There is no `if S.dev_mode` branch
(SECOPS-007). With the flag off the platform is byte-for-byte unchanged.

The conceptual analogue is the OFBiz order-management console's status buckets (we re-skin
status-bucketed lists), and the open-property `portfolio_occupancy_rollup`
(`docs/open-property/specs/PROP-003.md` §4.1) supplies the `occupied / max(total, 1)`
divide-by-zero-safe occupancy-rate idiom we copy. The **contrast**: these rows are
reservations (with an occupancy/room dimension), not orders, and not rental units.

Gap analysis row: `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C row "Front desk
(arrivals/departures/in-house, walk-in, assign room, check-in/out, room-move) — **MISSING**".

## 2. Context & Current State

### 2.1 What HTL-018 and HTL-006 land (prerequisite state)

HTL-022 builds on two upstream tickets and queries their tables/GSIs without modifying either.

- **HTL-018** (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md` §HTL-018, lines 184–320):
  establishes the `hotel_reservations` DynamoDB table (PK=`reservation_id`, SK=`META` for the
  header; child `HIST#{ts:020d}#{event_id}` rows added by HTL-019), the `T.hotel_reservations`
  handle, `S.hotel_reservations_table_name`, the `create_reservation` service, and **three
  GSIs** declared in `scripts/local-ddb-init.py`
  (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:226-248`):
  - `GSI_HOTEL_ARRIVALS` — PK=`hotel_id`, SK=`checkin` (`S`, `"YYYY-MM-DD"`) — "the arrivals
    board … the front-desk-console data source"
    (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:227-229`).
  - `GSI_GUEST` — PK=`guest_party_id`, SK=`created_at` (`N`) — a guest's booking history.
  - `GSI_HOTEL_STATUS` — PK=`hotel_id`, SK=`status` (`S`) — "a hotel's reservations bucketed by
    lifecycle status (in-house / confirmed / departed)"
    (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:232-233`).

  The reservation `status` literal set is `confirmed | checked_in | checked_out | cancelled |
  no_show` (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:220`), initial `confirmed`. The
  header carries `checkin` (inclusive first night, `:211`), `checkout` (exclusive departure
  day, `:212`), `nights` (`:213`), `assigned_room_ids` (`L`, empty `[]` until check-in,
  `:210`), `adults`/`children`/`rooms`/`total_cents`/`currency`/`version` (`:214-222`).

- **HTL-006** (`docs/qloapps/specs/HTL-006.md`): establishes the `hotel_rooms` table
  (PK=`hotel_id`, SK=`ROOM#{room_id}`), the `T.hotel_rooms` handle, and two GSIs
  (`docs/qloapps/specs/HTL-006.md:250-253`):
  - `GSI_ROOMTYPE` — PK=`room_type_id`, SK=`created_at` (`N`).
  - `GSI_HK_STATUS` — PK=`hotel_id`, SK=`housekeeping_status` (`S`) — "the HTL-007 board fast
    path, no partition scan" (`docs/qloapps/specs/HTL-006.md:254`).

  Each `ROOM#` row carries `status ∈ {available, out_of_service}`
  (`docs/qloapps/specs/HTL-006.md:235`) and `housekeeping_status ∈ {clean, dirty, inspected,
  out_of_service}` (`:236`). Both are always set, so every room projects into `GSI_HK_STATUS`
  (`docs/qloapps/specs/HTL-006.md:600-615`).

### 2.2 GSI-name reconciliation between the FRONT_DESK ticket and the HTL-018 source

The HTL-022 ticket prose (`docs/qloapps/FRONT_DESK_TICKETS.md:86-92`) refers to the arrivals
index as `GSI_HOTEL_CHECKIN` and posits a departures index `GSI_HOTEL_CHECKOUT`. The
**authoritative HTL-018 schema** — the standalone `docs/qloapps/specs/HTL-018.md:218-233`
(which mirrors its source-cluster table owner
`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:226-248`) — names the arrivals index
**`GSI_HOTEL_ARRIVALS`** (PK=`hotel_id`, SK=`checkin`, `docs/qloapps/specs/HTL-018.md:222`),
declares only `GSI_HOTEL_ARRIVALS` / `GSI_GUEST` / `GSI_HOTEL_STATUS`
(`docs/qloapps/specs/HTL-018.md:220-224`), and declares **no checkout index**. To avoid forking the reservation schema (cross-cutting constraint "Reuse
primitives, never fork" / "No NEW table"), HTL-022 aligns to the HTL-018 source of truth:

- **Arrivals** → `GSI_HOTEL_ARRIVALS` (PK=`hotel_id`, SK=`checkin`). The FRONT_DESK ticket's
  `GSI_HOTEL_CHECKIN` is the same index under its HTL-018 name.
- **In-house** → `GSI_HOTEL_STATUS` (PK=`hotel_id`, SK=`status`). Identical in both sources.
- **Departures** → there is **no `checkout` GSI in HTL-018**. HTL-022 therefore derives
  departures from `GSI_HOTEL_STATUS` (`status == "checked_in"`) and filters
  `checkout == date` in-memory (the partition of in-house reservations for a single hotel is
  small and bounded by physical room count — see §5.4). Whether HTL-018 should add a
  `GSI_HOTEL_CHECKOUT` index for a pure index-side departures query is recorded as Open
  Question §10.1; if HTL-018 adds it, `departures_today` switches to that index with no API
  change. This keeps HTL-022 within "no NEW table / no schema fork" while honouring the
  ticket's stated departures view.

### 2.5 Cursor pagination (reused from cursor.py:94,103)

`app/core/cursor.py:94` (`encode_cursor`) and `:103` (`decode_cursor`) implement the v2
HMAC-signed cursor over a DynamoDB `LastEvaluatedKey`. `encode_cursor` returns `None` when
DynamoDB returns no `LastEvaluatedKey` (`app/core/cursor.py:95-96`: `if not last_evaluated_key:
return None`). `decode_cursor` returns `None` for a missing, malformed, or tampered cursor
(`app/core/cursor.py:104-105` and the HMAC check at `:110-113`), so passing `cursor=None` or a
bad token simply starts a fresh page — no 422. The three HTL-022 list queries use these helpers
for `GSI_HOTEL_ARRIVALS` / `GSI_HOTEL_STATUS` pagination.

### 2.6 `now_ts()` and today-date derivation

`app/core/time.py:2-3` defines `now_ts() -> int` (integer Unix seconds). The default `date` for
all four queries is "today", derived as
`datetime.fromtimestamp(now_ts(), tz=timezone.utc).strftime("%Y-%m-%d")`. The `checkin` /
`checkout` columns are `"YYYY-MM-DD"` strings whose lexical order equals chronological order
(`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:211-212`), so an equality match on the
derived today-string is correct and timezone-stable in UTC (Open Question §10.2 covers the
hotel-local-timezone refinement).

### 2.7 The `{items, count, cursor}` list contract

CLAUDE.md documents `host_inventory.list_hosts` returning `{"hosts": [...], "count", "cursor"}`,
and the HTL-006 `list_rooms` returns `{"rooms": [...], "count", "cursor"}`
(`docs/qloapps/specs/HTL-006.md:433-435`). HTL-022's three list queries use the same envelope,
keyed **`rows`** (the front-desk row projection): `{"rows": [...], "count": int, "cursor": str |
None}`. Because each query uses a true DynamoDB GSI cursor (`ExclusiveStartKey`) rather than a
full in-memory load, `count` is the **page-level** count (items returned in the current page
after any in-memory filter) — identical to the PROP-003 `count` semantics
(`docs/open-property/specs/PROP-003.md` §5.2), not the global total of `list_hosts`.

### 2.8 The occupancy-rate divide-by-zero guard (reused from PROP-003)

`portfolio_occupancy_rollup` (`docs/open-property/specs/PROP-003.md` §4.1) computes
`occupancy_rate = occupied / max(unit_count, 1)`. HTL-022's `occupancy_snapshot` copies this
exact guard: `occupancy_rate = rooms_occupied / max(rooms_total, 1)`, so a hotel with zero
rooms yields `0.0` with no `ZeroDivisionError`.

### 2.9 Nothing else exists today

`grep -rn "hotel_front_desk\|arrivals_today\|departures_today\|occupancy_snapshot" app/`
returns no results — `app/services/hotel_front_desk.py` is entirely new. No existing service has
a front-desk console concept (gap analysis §C marks it MISSING).

## 3. Data Model

HTL-022 introduces **no new table, no new GSI, and no new DynamoDB attribute**. It reads the
schema declared by HTL-018 and HTL-006. This section documents which GSIs are exercised and the
read patterns, plus the three new read-only Pydantic models.

### 3.1 Table: `hotel_reservations` (reused from HTL-018)

**Primary key**: `reservation_id` (S, PK) / `sk` (S, SK; `META` for the header).

**Row shape consumed by HTL-022 (the `META` header)**

| Attribute | DDB Type | Used by HTL-022 |
|---|---|---|
| `reservation_id` | S | row id |
| `hotel_id` | S | GSI partition (arrivals / in-house) |
| `checkin` | S `"YYYY-MM-DD"` | `GSI_HOTEL_ARRIVALS` sort key; arrivals match |
| `checkout` | S `"YYYY-MM-DD"` | departures match (in-memory filter over in-house) |
| `status` | S | `GSI_HOTEL_STATUS` sort key; arrivals (`confirmed`) / in-house (`checked_in`) |
| `room_type_id` | S | `FrontDeskRow.room_type_id` |
| `guest_party_id` | S | `FrontDeskRow.guest_sub` (opaque guest fk) |
| `assigned_room_ids` | L | `FrontDeskRow.assigned_room_ids`; occupancy "occupied rooms" set |
| `nights` | N | `FrontDeskRow.nights` (denormalized; recomputed if absent) |
| `adults` / `children` | N | `FrontDeskRow.occupancy_adults` / `occupancy_children` |
| `total_cents` | N | `FrontDeskRow.total_cents` |

**GSIs exercised**

| Index | PK | SK | Used by |
|---|---|---|---|
| `GSI_HOTEL_ARRIVALS` | `hotel_id` (S) | `checkin` (S) | `arrivals_today` — `checkin == date`, filter `status == "confirmed"` |
| `GSI_HOTEL_STATUS` | `hotel_id` (S) | `status` (S) | `in_house` (`status == "checked_in"`); `departures_today` (`status == "checked_in"` then in-memory `checkout == date`) |

No `attr_types` change — both SKs are `S` (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:229,233`).

### 3.2 Table: `hotel_rooms` (reused from HTL-006)

**Primary key**: `hotel_id` (S, PK) / `sk` (S, SK; `ROOM#{room_id}`).

**GSI exercised**

| Index | PK | SK | Used by |
|---|---|---|---|
| `GSI_HK_STATUS` | `hotel_id` (S) | `housekeeping_status` (S) | `occupancy_snapshot` — `rooms_out_of_service` count |

`rooms_total` (all non-archived `ROOM#` rows) is read via the `hotel_rooms` PK query
(`Key("hotel_id").eq(hotel_id) & Key("sk").begins_with("ROOM#")`,
`docs/qloapps/specs/HTL-006.md:419`) — itself a partition query, **not** a table scan.

### 3.3 New Pydantic models (`app/models.py`)

Three new read-only response models, all additive — no existing model is modified.

**`FrontDeskRow`** — a reservation projection for a console row:

```python
    checkout: str              # "YYYY-MM-DD"

    occupancy_children: int

```

**`FrontDeskListOut`** — the paginated list envelope:

```python
class FrontDeskListOut(BaseModel):
    rows: List[FrontDeskRow]
    count: int
    cursor: Optional[str] = None
```

**`OccupancySnapshotOut`** — the live occupancy snapshot:

```python
class OccupancySnapshotOut(BaseModel):
    hotel_id: str
    date: str                  # "YYYY-MM-DD" the snapshot is computed for
    rooms_total: int
    rooms_occupied: int
    rooms_available: int
    rooms_out_of_service: int
```

`guest_party_id` (HTL-018) maps to `FrontDeskRow.guest_sub`; the model field is named

## 4. API / Service Design

### 4.1 Service module (`app/services/hotel_front_desk.py`)

A **new** module. Module-level imports mirror `app/services/inventory.py:30-41`
(`boto3.dynamodb.conditions.Key`, `botocore.exceptions.ClientError`, `fastapi.HTTPException`,
`app.core.settings.S`, `app.core.tables.T`, `app.core.time.now_ts`,
`app.core.cursor.encode_cursor`/`decode_cursor`). No `if S.dev_mode` branch anywhere
(SECOPS-007, §7.1).

Module helpers (copied from `app/services/inventory.py`):

```python
def _flag_on() -> bool:
    return bool(getattr(S, "hotel_pms_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Hotel PMS is not enabled")

def _audit(event: str, user_sub: str, **fields) -> None:   # used by HTL-023, not the queries
    try:
        from app.services.alerts import audit_event
        audit_event(event, user_sub or "system", None, **fields)
    except Exception:
        pass

def _to_int(value, default: int = 0) -> int:               # cf. inventory.py:67-73
    try:
        return default if value is None else int(value)
    except (TypeError, ValueError):
        return default

def _today() -> str:
    from datetime import datetime, timezone
    return datetime.fromtimestamp(now_ts(), tz=timezone.utc).strftime("%Y-%m-%d")

def _days_between(checkin: str, checkout: str) -> int:
    from datetime import date
    try:
        a = date.fromisoformat(checkin); b = date.fromisoformat(checkout)
        return max((b - a).days, 0)
    except Exception:
        return 0
```

#### 4.1.1 `_row_from_reservation`

```python
def _row_from_reservation(item: dict) -> dict:
```

Projects a `hotel_reservations` `META` item into a `FrontDeskRow`-shaped dict. Coerces `Decimal`
numerics to `int` via `_to_int` (`nights`, `adults`, `children`, `total_cents`); computes
`nights = _days_between(checkin, checkout)` when the stored `nights` is absent/zero; normalizes
`assigned_room_ids` to a `list[str]`; sets `guest_sub = item.get("guest_party_id", "")` and
`guest_name = item.get("guest_name") or guest_sub`.

#### 4.1.2 `arrivals_today`

```python
def arrivals_today(hotel_id: str, *, date: Optional[str] = None,
                   cursor: Optional[str] = None, limit: int = 50) -> dict:
```

1. `_require_enabled()`.
2. `date = date or _today()`; `limit = max(1, min(int(limit), 200))`;
   `esk = decode_cursor(cursor)`.
3. Query `GSI_HOTEL_ARRIVALS`:
   `IndexName="GSI_HOTEL_ARRIVALS"`,
   `KeyConditionExpression=Key("hotel_id").eq(hotel_id) & Key("checkin").eq(date)`,
   `FilterExpression=Attr("status").eq("confirmed")`,
   `Limit=limit`, plus `ExclusiveStartKey=esk` when not `None`.
   (A reservation arriving today that is not yet checked in is `confirmed`,
   `docs/qloapps/FRONT_DESK_TICKETS.md:115-119`.)
4. `rows = [_row_from_reservation(i) for i in resp.get("Items", [])]`.
5. `next_cursor = encode_cursor(resp.get("LastEvaluatedKey"))`.
6. Return `{"rows": rows, "count": len(rows), "cursor": next_cursor}`.

GSI-backed, no scan.

#### 4.1.3 `departures_today`

```python
def departures_today(hotel_id: str, *, date: Optional[str] = None,
                     cursor: Optional[str] = None, limit: int = 50) -> dict:
```

1. `_require_enabled()`; `date = date or _today()`; `limit` clamp; `esk = decode_cursor(cursor)`.
2. Query `GSI_HOTEL_STATUS`:
   `IndexName="GSI_HOTEL_STATUS"`,
   `KeyConditionExpression=Key("hotel_id").eq(hotel_id) & Key("status").eq("checked_in")`,
   `FilterExpression=Attr("checkout").eq(date)`,
   `Limit=limit`, plus `ExclusiveStartKey=esk` when not `None`.
   (A reservation still in-house and due to depart today is `checked_in` with `checkout ==
   date`, `docs/qloapps/FRONT_DESK_TICKETS.md:120-123`.) See §2.2 for why this derives from the
   status index rather than a non-existent checkout index, and §5.4 for the FilterExpression
   pagination loop.
3. `rows`, `next_cursor`, return — same shape as `arrivals_today`.

GSI-backed, no scan.

#### 4.1.4 `in_house`

```python
def in_house(hotel_id: str, *, cursor: Optional[str] = None, limit: int = 50) -> dict:
```

1. `_require_enabled()`; `limit` clamp; `esk = decode_cursor(cursor)`.
2. Query `GSI_HOTEL_STATUS`:
   `IndexName="GSI_HOTEL_STATUS"`,
   `KeyConditionExpression=Key("hotel_id").eq(hotel_id) & Key("status").eq("checked_in")`,
   `Limit=limit`, plus `ExclusiveStartKey=esk` when not `None`.
   (Every guest currently checked in regardless of date,
   `docs/qloapps/FRONT_DESK_TICKETS.md:124-126`.)
3. `rows`, `next_cursor`, return — same shape.

GSI-backed, no scan. No `date` parameter (in-house is date-independent).

#### 4.1.5 `occupancy_snapshot`

```python
def occupancy_snapshot(hotel_id: str, *, date: Optional[str] = None) -> dict:
```

1. `_require_enabled()`; `date = date or _today()`.
2. **Physical rooms total** — query the `hotel_rooms` PK with
   `Key("hotel_id").eq(hotel_id) & Key("sk").begins_with("ROOM#")`, looping `LastEvaluatedKey`
   to exhaustion (a hotel may have hundreds of rooms; the loop is bounded by room count).
   `rooms_total = len(room_items)`.
3. **Out-of-service rooms** — query `GSI_HK_STATUS` with
   `Key("hotel_id").eq(hotel_id) & Key("housekeeping_status").eq("out_of_service")`, looping
   `LastEvaluatedKey`. `rooms_out_of_service = count`. (Index-side, no scan,
   `docs/qloapps/specs/HTL-006.md:600-615`.)
4. **Occupied rooms** — collect the distinct union of `assigned_room_ids` across all
   `checked_in` reservations for the hotel (drain `GSI_HOTEL_STATUS`,
   `status == "checked_in"`, accumulating `assigned_room_ids` into a `set`).
   `rooms_occupied = len(distinct_assigned_room_ids)`.
5. `rooms_available = max(rooms_total - rooms_occupied - rooms_out_of_service, 0)` (clamped ≥ 0,
   `docs/qloapps/FRONT_DESK_TICKETS.md:132`).
6. `occupancy_rate = rooms_occupied / max(rooms_total, 1)` (0..1, no divide-by-zero, §2.8).
7. **Counts** — `arrivals_count = arrivals_today(hotel_id, date=date)["count"]`,
   `departures_count = departures_today(hotel_id, date=date)["count"]`,
   `in_house_count` = the count drained in step 4. (For a hotel whose arrivals/departures span
   more than one page, see §5.6 for the count-vs-page caveat and the drain-to-total option.)
8. Return the full `OccupancySnapshotOut` dict (`hotel_id`, `date`, the room tallies,
   `occupancy_rate`, the three counts).

Pure GSI aggregation — no scan.

## 5. Detailed Behavior & Edge Cases

### 5.1 `arrivals_today` excludes already-checked-in and terminal reservations

The `FilterExpression=Attr("status").eq("confirmed")` means a reservation whose `checkin ==
date` but whose status has already moved to `checked_in` (early check-in), `cancelled`, or
`no_show` is **not** returned by arrivals. This is intentional: the arrivals view is the
"still-expected-to-arrive" worklist (`docs/qloapps/FRONT_DESK_TICKETS.md:115-119`). An already
checked-in same-day guest appears in `in_house`, not `arrivals`.

### 5.2 `date` defaults to today; explicit `date` overrides

When `date is None`, all four functions derive today via `_today()`
(`datetime.fromtimestamp(now_ts(), tz=timezone.utc).strftime("%Y-%m-%d")`, §2.6). An explicit
`date="YYYY-MM-DD"` overrides it — enabling "tomorrow's arrivals" / "yesterday's departures"
look-ahead/look-back views. The string is matched against the `checkin` / `checkout` columns
directly (lexical == chronological for ISO dates). A malformed `date` simply matches no rows
(empty `rows`) rather than erroring — the service does not validate the date format (Open
Question §10.4 covers whether to 422 a malformed `date`).

### 5.3 Empty hotel / no matching reservations

`arrivals_today` / `departures_today` / `in_house` on a hotel with no matching reservations
return `{"rows": [], "count": 0, "cursor": None}`. `occupancy_snapshot` on a hotel with no rooms
returns `rooms_total=0`, `rooms_occupied=0`, `rooms_available=0`, `rooms_out_of_service=0`,
`occupancy_rate=0.0` (no `ZeroDivisionError`, §2.8), and the three counts as computed.

### 5.4 `departures_today` FilterExpression does not reduce page size

`departures_today` queries `GSI_HOTEL_STATUS` (`status == "checked_in"`) with a
`FilterExpression` on `checkout == date`. Per the CLAUDE.md gotcha "DDB FilterExpression doesn't
reduce page size", DynamoDB fetches up to `Limit` items **before** applying the filter, so a
single `query()` page may return fewer than `limit` departures even when more exist on a later
page. For a single hotel the `checked_in` partition is bounded by physical room count (a hotel
cannot have more guests in-house than rooms), so a single page of `limit ≤ 200` typically covers
it; for completeness the implementation accumulates filtered items across pages via
`LastEvaluatedKey` until it reaches `limit` matches or exhausts the partition — the
`host_inventory.list_hosts` precedent (`docs/qloapps/specs/HTL-006.md:178-187`). The returned
`cursor` is the `LastEvaluatedKey` at the point `limit` matches were collected (or `None` at
partition end).

### 5.5 `occupancy_snapshot` occupied-rooms set is distinct across reservations

`rooms_occupied` counts **distinct** room ids in the union of `assigned_room_ids` across all
`checked_in` reservations (`docs/qloapps/FRONT_DESK_TICKETS.md:130-132`). A reservation that
spans multiple rooms (`rooms > 1`) contributes each of its assigned room ids; two reservations
never share a physical room id (the assignment is exclusive per HTL-019/HTL-023), so the union
deduplication is defensive but correct. A `checked_in` reservation with an empty
`assigned_room_ids` (checked in unassigned — HTL-023 `walk_in_booking` allows this) contributes
zero to `rooms_occupied` (its rooms are not yet physically allocated).

### 5.6 `occupancy_snapshot` counts vs paginated list counts

`arrivals_count` / `departures_count` in the snapshot are computed by calling
`arrivals_today(date=date)` / `departures_today(date=date)` and reading their `count`, which is
the **first page** count (page-level, §2.7). For hotels whose same-day arrivals/departures
exceed one page (`> limit`), the snapshot count understates the true total. The snapshot
implementation passes `limit=200` to these inner calls and, for the in-house count (step 4),
drains all pages to a true total. Driving `arrivals_count` / `departures_count` to a true total
(by draining their pages) is a small, safe refinement recorded as Open Question §10.5; for MVP
the single-page (≤ 200) count is accurate for any realistically-sized single hotel.

### 5.7 Missing `guest_name` on the reservation header

HTL-018's reservation header carries only the opaque `guest_party_id`
(`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:208`), not a denormalized guest display
name. `_row_from_reservation` sets `guest_name = item.get("guest_name") or guest_sub` — so until
a guest-profile join (Contacts / OBP `CUS` / open-property `TEN`) lands, `guest_name` falls back
to the opaque id. This keeps the query service self-contained (no cross-entity fan-out per row);
the join is a follow-up (§10.3).

### 5.8 Decimal coercion

DynamoDB returns numeric attributes as `boto3.dynamodb.types.Decimal`. `_row_from_reservation`
coerces `nights`, `occupancy_adults`, `occupancy_children`, `total_cents` to `int` via
`_to_int`. `occupancy_rate` is a Python `float` computed in the service layer — it never comes
from DynamoDB. `rooms_total` / `rooms_occupied` / `rooms_available` / `rooms_out_of_service` /
the three counts are computed as plain Python `int`s.

### 5.9 Cursor tampering / malformed cursor

`decode_cursor` returns `None` for an invalid or tampered cursor token (HMAC verification fails,
`app/core/cursor.py:110-113`). All three list functions treat a `None` decoded cursor as the
start of pagination: a fresh query from the beginning of the GSI. No 422 is raised for a bad
cursor; pagination silently restarts — the established platform pattern
(`docs/open-property/specs/PROP-003.md` §5.10).

### 5.10 No write path — the query service is pure read

None of the four functions write to DynamoDB. Unlike PROP-003's `compute_property_occupancy`
(which best-effort writes back a derived `occupancy_status`), `occupancy_snapshot` is a pure
read aggregation — it does **not** persist the snapshot anywhere. Re-running any function with
the same inputs and unchanged data produces identical output. (The write path — walk-in /
assign-room / room-move with version-gated CAS — is HTL-023's deliverable in the same module.)

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`hotel_front_desk.py` must contain **no** `if S.dev_mode` branch. The same DynamoDB GSI queries
run in dev (boto3 intercepted by moto in-process at startup via `app/core/dev_s3.py`) and in
prod (real DynamoDB) on the identical `T.hotel_reservations` / `T.hotel_rooms` handles. This
mirrors the explicit cross-cutting constraint (`docs/qloapps/FRONT_DESK_TICKETS.md:59-61`) and
the `app/services/inventory.py:27-29` precedent (its module docstring: "SECOPS-007 parity:
identical code in dev … and prod … no `dev_mode` branch"). A `grep -n "dev_mode"
app/services/inventory.py` confirms the only hit is that docstring.

### 7.2 Idempotency

All four functions are pure read/aggregate operations with **no side effects** — no
`put_item`/`update_item`/`delete_item` anywhere. Re-running any function with the same inputs and
unchanged underlying data yields identical output. Pagination is deterministic for a stable
dataset (the GSI cursor is a function of the data, not of call count). There is nothing to make
idempotent because nothing is written.

### 7.3 Security — ownership & authorization

- **Auth boundary** (HTL-024): all four read endpoints use `require_ui_session`
  (`app/services/sessions.py:330`) — a valid UI session is required; no service-layer ownership
  check on reads, consistent with HTL-006's read endpoints
  (`docs/qloapps/specs/HTL-006.md:687-690`) and the single-platform-deployment assumption. The
  mutation endpoints (HTL-023, exposed by HTL-024) use `require_admin_or_root_csrf`
  (`app/auth/policy.py:100`) — `role ∈ {ADMIN, ROOT}` plus CSRF for cookie-auth.
- **Hotel scoping**: every query is partition-scoped to the `hotel_id` path parameter (the GSI
  PK), so a query can only ever return reservations/rooms for that one hotel. A caller cannot
  enumerate another hotel's reservations through these endpoints by construction.
- **No PII fan-out per row**: `_row_from_reservation` projects only the opaque `guest_party_id`
  (as `guest_sub`); it does not join to a guest profile, so the query service never exposes
  guest contact PII (the guest-name join, when it lands, must respect the same auth boundary —
  §10.3).

### 7.4 Money-safety

HTL-022 is a pure read/aggregation ticket. It does **not** touch the billing ledger
(`billing_shared.new_ledger_entry`, `settle_or_reverse_ledger`, `apply_balance_delta`,
`compute_due`), the `billing` table, or any payment provider (Stripe/PayPal/CCBill). The
`total_cents` it surfaces on a `FrontDeskRow` is read straight from the reservation header (set
at create time by HTL-018 from `compute_stay_price`,
`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:217`) and is display-only — HTL-022 never
re-computes a price or writes a money field. This ticket has zero financial invariants to
enforce. (Folio charges and deposits are Tier-3 clusters that go through the ledger
primitives.)

### 7.5 Audit trail

The four query functions are **read-only and emit no audit events** (CLAUDE.md/inventory
precedent: only mutations audit). The `_audit()` wrapper is present in the module solely for
HTL-023's mutating actions (`hotel.frontdesk.walk_in` / `assign_room` / `change_room` /
`room_move`), which extend the same file. A read of an operational dashboard does not warrant an
audit row.

## 8. Backward Compatibility & Migration

### 8.1 Additive-only changes

HTL-022 adds:
- One new service module `app/services/hotel_front_desk.py` (four query functions + helpers).
- Three new read-only Pydantic models (`FrontDeskRow`, `FrontDeskListOut`,
  `OccupancySnapshotOut`) to `app/models.py` — additive; no existing model modified.
- (HTL-024) four new read endpoints to `app/routers/hotel_front_desk.py` — not part of HTL-022
  directly, specified here as the consumer surface.

No existing endpoint, service function, DynamoDB table, GSI, or Pydantic model is altered.

### 8.2 No DynamoDB migration required

HTL-022 introduces **no new table and no new GSI**. It consumes GSIs declared by HTL-018
(`GSI_HOTEL_ARRIVALS`, `GSI_HOTEL_STATUS`) and HTL-006 (`GSI_HK_STATUS`). No `TableDef` entry,
no `attr_types` change, no `CreateTable`/`UpdateTable` in dev or prod. The schema dependency is
entirely satisfied by the upstream tickets. (If HTL-018 later adds a `GSI_HOTEL_CHECKOUT` index
per Open Question §10.1, `departures_today` switches to it with no HTL-022 API change and no
migration owned by HTL-022.)

### 8.3 Rollback

With `HOTEL_PMS_ENABLED=false`, the four query functions are dormant (every entrypoint 404s).
Rolling back HTL-022 reverts the new `hotel_front_desk.py` module and the three Pydantic models.
Because no DynamoDB schema is touched, no schema rollback is needed. A partial rollback (keep
HTL-018/HTL-006 deployed, revert only HTL-022) is safe — the upstream tables are unaffected.

### 8.4 Forward-compatibility with HTL-023

HTL-023 (the action service) **extends the same `hotel_front_desk.py` module** in place,
reusing `_require_enabled()`, `_audit()`, and `_row_from_reservation()`. HTL-022 deliberately
lands `_audit()` (unused by the queries) so HTL-023 adds only its mutating functions. The module
is structured so HTL-023 is purely additive (`docs/qloapps/FRONT_DESK_TICKETS.md:199-237`).

   `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:226-248`) declares **no** checkout index. **Assumption (MVP)**: `departures_today` derives departures
   from `GSI_HOTEL_STATUS` (`status == "checked_in"`) + in-memory `checkout == date` filter
   (§2.2, §5.4) — staying within "no new table / no schema fork". If a pure index-side
   departures query is wanted, HTL-018 should add `GSI_HOTEL_CHECKOUT` (PK=`hotel_id`,
   SK=`checkout`); `departures_today` then switches to it with no API change. This is an HTL-018
   schema decision, not an HTL-022 one.

2. **Today derived in UTC vs hotel-local timezone.** `_today()` uses UTC. A hotel in a far
   timezone could see "today's arrivals" roll over at the wrong local wall-clock moment.
   **Assumption (MVP)**: UTC is acceptable; a per-hotel timezone field (read from the HTL-001
   hotel `META` row) refining `_today()` is a non-breaking follow-up.

3. **`guest_name` join.** HTL-018 stores only the opaque `guest_party_id`; `FrontDeskRow.
   guest_name` falls back to that id. **Assumption**: a guest-profile join (Contacts / OBP
   `CUS` / open-property `TEN`) is a follow-up; until then the FE shows the opaque id (or HTL-018
   denormalizes a `guest_name` onto the header at create time). The join must respect the same
   auth boundary (§7.3).

4. **Malformed `date` validation.** A malformed `date` matches no rows (empty result) rather
   than erroring. **Assumption**: silent-empty is acceptable; if a 422 on a bad `date` is
   preferred, add an ISO-format check in the router (HTL-024) — not the service.

5. **Snapshot arrivals/departures counts page-level vs total.** `arrivals_count` /
   `departures_count` read the first-page `count` (`limit=200`); for hotels exceeding one page
   they understate the total (§5.6). **Assumption**: ≤ 200 covers any realistic single hotel;
   draining to a true total is a small follow-up if needed.

6. **`occupancy_snapshot` cost (multiple GSI drains).** The snapshot drains
   `GSI_HOTEL_STATUS` (for occupied + in-house), `GSI_HK_STATUS` (out-of-service), and the
   `hotel_rooms` partition (total), plus two inner list calls (arrivals/departures). For a
   single hotel this is a handful of bounded partition queries. **Assumption**: acceptable for
   MVP; a cached snapshot (write-back to a `META`-style row, à la PROP-003) is a follow-up if
   the dashboard is polled at high frequency.

7. **ROOT/cross-hotel scoping on reads.** Reads are `require_ui_session` only (no per-hotel
   ownership check), consistent with HTL-006. **Assumption**: single-platform deployment;
   per-hotel read authorization (a user may only view hotels they manage) is a future
   multi-tenant refinement (matches HTL-006 §10 Open-Q 1).
