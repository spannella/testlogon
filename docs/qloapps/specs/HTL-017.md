# HTL-017 — Stay-search engine (read-only): `search_stays` (dates + occupancy → available room types + total price)

**Type**: Feature | **Priority**: P1 | **Estimate**: 2d
**Source**: `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md` §HTL-017 + "Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C (Stay-search engine)

---

## 1. Summary & Goal

HTL-017 lands the **stay-search engine** — the single net-new booking primitive the gap analysis flags as "the heart of a hotel PMS": *date-range + occupancy → available room types (per-date availability intersection across the span) + summed multi-night/occupancy price* (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:57-61,138`). It delivers exactly **one public service function** — `search_stays(...)` — plus its supporting span-validation helper and three Pydantic models (`StaySearchIn`, `StayRoomTypeResult`, `StaySearchResult`), all in the new service file `app/services/hotel_reservations.py` (the home of the HTL-017..HTL-019 reservation cluster logic).

`search_stays` is **read-only**. It answers one question — *"which room types can I book for this stay, and what does each cost?"* — by **pure composition over two existing forward-dep primitives**:

1. **availability** — `check_availability(hotel_id, room_type_id, checkin, checkout, rooms_needed)` (HTL-012, `docs/qloapps/specs/HTL-012.md` §4.1) — the per-date availability **intersection across the whole span** (`{"available": bool, "rooms_needed", "per_night": [...], "min_remaining": int}`). A room type is bookable for a stay **iff every single night** has `available >= rooms`.
2. **price** — `compute_stay_price(hotel_id, room_type_id, checkin, checkout, adults, children, rooms)` (HTL-015, the rate-plan price engine; forward ref — `docs/qloapps/RATE_PLANS_TICKETS.md`) — the deterministic multi-night/occupancy price (`-> StayPriceResult{per_night, total_cents, currency, applied_rule_ids}`).

It performs **zero DynamoDB writes**: no `hold_rooms`, no `put_item`, no reservation creation (that is HTL-018). The candidate room types come from the HTL-005 room-type lister (`hotel_pms.list_room_types(hotel_id)`, `docs/qloapps/specs/HTL-005.md` §4.1.3) and — for a city search — the HTL-001 hotels lister (`hotel_pms.list_hotels(city=...)`, forward ref). HTL-017 never re-implements availability, pricing, room-type enumeration, or hotel resolution — it **composes by id**.

Like every HTL ticket, HTL-017 is **additive + flag-gated, default OFF**: `search_stays` calls `_require_enabled()` (the verbatim `app/services/inventory.py:54-56` 404 contract) first, so with `HOTEL_PMS_ENABLED=false` the entrypoint is a silent HTTP 404 no-op and the platform is byte-for-byte unchanged. The HTTP surface (`POST /ui/hotel-search`) and the frontend results page are later tickets (HTL-020 router, HTL-021 frontend). HTL-017 ships **service layer only**.

## 2. Context & Current State

### 2.1 Gap — no stay-search engine exists today

`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:57-61` records the two concepts that "defeat every existing primitive": a **per-date remaining-rooms inventory** (the existing OFB-003/004 inventory is a single scalar stock counter with no date dimension) and a **multi-night price computation across a check-in→check-out span** (the existing cart total is a naive line-item sum; pricing rules discount a cart total, not a stay). The §C "Booking + reservations + front desk" tier (`:135-141,174-178`) names the **Stay-search engine** as MISSING: "date-range + occupancy → available room types (per-date availability intersection across span) + summed multi-night/occupancy price." HTL-017 is precisely this function. `grep -rn "search_stays\|hotel_reservations" app/` returns no results today — neither the service file nor the function exists.

### 2.2 The two halves already exist as forward-dep primitives

The gap-analysis line splits cleanly into two already-specified primitives that HTL-017 composes but never re-implements:

- **Availability half — HTL-012** (`docs/qloapps/specs/HTL-012.md` §1, §4.1). `check_availability` is the "intersection across the whole span": `available = all(sufficient for every night) and per_night non-empty`, with `min_remaining = min(remaining)` the binding night. A missing/never-seeded night is surfaced by HTL-010's `get_availability` as a **zeroed virtual row** (`available = 0`) ⇒ `sufficient = false` ⇒ `available = false` (HTL-012 §5.4). Checkout is **exclusive** (`[checkin, checkout)`, HTL-012 §5.2). HTL-012 §11.3 already names HTL-017 as a downstream consumer: "`check_availability` called per candidate room type to filter search results — the reusable span-intersection primitive."
- **Price half — HTL-015** (forward ref, `docs/qloapps/RATE_PLANS_TICKETS.md`). `compute_stay_price(hotel_id, room_type_id, checkin, checkout, adults, children, rooms, advance_days=None) -> StayPriceResult` is the deterministic multi-night price engine. Per the parent doc (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:25-27,166-168`): a room type with no rate plan still prices off `base_nightly_rate_cents` (the HTL-005 field, `docs/qloapps/specs/HTL-005.md` §3.1), and a LOS (length-of-stay) min/max-nights rule rejection raises `HTTPException(422, "stay too short/long")`.

### 2.3 The candidate-enumeration forward-deps (HTL-005 / HTL-001)

- **HTL-005** `list_room_types(hotel_id, *, status="active", cursor=None, limit=50) -> dict` (`docs/qloapps/specs/HTL-005.md` §4.1.3) returns `{"room_types": [...RoomTypeOut...], "count": int, "cursor": str | None}` — newest-first, `active`-only by default, `META`-row excluded. Each `RoomTypeOut` carries `room_type_id`, `name`, `base_nightly_rate_cents`, `max_occupancy`, `base_occupancy_adults`, `base_occupancy_children`, etc.
- **HTL-001** `list_hotels(city=...)` (forward ref, `docs/qloapps/HOTELS_AMENITIES_TICKETS.md`) resolves hotels in a city. HTL-017 calls it only on the `city` branch.

HTL-017 treats both as **opaque calls** — it does not assume their internal storage. The parent doc (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:128-134`) specifies the resolution branch: `hotel_id` given → that one hotel's room types; `city` given → resolve hotels in that city then their room types; both absent → 422.

## 3. Data Model

HTL-017 introduces **no DynamoDB table, no GSI, no new DynamoDB attribute** — it is a pure read-only composition. It owns no persisted state. The reservation **table** (`hotel_reservations`) is HTL-018's deliverable (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md` §HTL-018); `search_stays` never touches it. This section documents only the three Pydantic I/O models that flow through the function/router.

### 3.1 `StaySearchIn` — request payload (`app/models.py`)

```python
class StaySearchIn(BaseModel):
    hotel_id: Optional[str] = None     # one of hotel_id | city required (else 422)
    city: Optional[str] = None
    checkin: str                       # "YYYY-MM-DD" (inclusive — first night)
    checkout: str                      # "YYYY-MM-DD" (exclusive — departure day, not a night)
    adults: int = Field(ge=1)
    children: int = Field(default=0, ge=0)
    rooms: int = Field(default=1, ge=1)

    @model_validator(mode="after")
    def _check_target(self) -> "StaySearchIn":
        if not (self.hotel_id or self.city):
            raise ValueError("one of hotel_id or city is required")
        return self
```

The `checkout > checkin` span check is **not** a Pydantic field validator (it needs date parsing and produces a 422 with a specific message); it is enforced in the service via `_validate_span` (§4.2). The model-level `_check_target` validator gives an early 422 at the router edge; the service re-checks defensively (§4.3 step 1).

### 3.2 `StayRoomTypeResult` — one available room type (`app/models.py`)

HTL-017 does not re-compute price independently; it copies `compute_stay_price(...).per_night` verbatim into the result (acceptance criterion, `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:163-164`).

### 3.3 `StaySearchResult` — the full search response (`app/models.py`)

### 3.4 `NightLineOut` (HTL-015 shape — referenced, not defined here)

`NightLineOut` is defined by HTL-015 in `app/models.py` (the rate-plan cluster). HTL-017 imports/references it; it is the per-night line of `StayPriceResult.per_night` (e.g. `{date, base_cents, applied_cents, rule_id?}` — exact fields per HTL-015). HTL-017 must **not** redefine it; if HTL-015 has not yet landed when HTL-017 is implemented standalone, HTL-017 may type `per_night` as `List[dict]` and tighten it to `List[NightLineOut]` once HTL-015 merges (a non-breaking additive tightening — see §10.3).

### 3.5 No persisted numeric coercion at this layer

Because `search_stays` performs no DynamoDB reads of its own, it does **not** itself coerce `Decimal`→`int`. The forward-dep functions it calls (`check_availability`, `compute_stay_price`, `list_room_types`) already coerce their numerics to plain `int` at their own service boundaries (HTL-012 §5.8, HTL-005 §5.8). HTL-017 consumes already-coerced values; the `StayRoomTypeResult`/`StaySearchResult` integer fields coerce again on field assignment as a belt-and-braces guard.

### 4.2 Span-validation helper

```python
def _validate_span(checkin: str, checkout: str) -> int:
    """Parse the YYYY-MM-DD span, enforce >= 1 night, return the night count.

    nights = count of dates in [checkin, checkout) (checkout exclusive).
    """
    try:
        ci = date.fromisoformat(checkin)
        co = date.fromisoformat(checkout)
    except (ValueError, TypeError):
        raise HTTPException(status_code=422, detail="checkin/checkout must be YYYY-MM-DD")
    nights = (co - ci).days
    if nights < 1:
        raise HTTPException(status_code=422, detail="checkout must be after checkin")
    return nights
```

`date.fromisoformat` rejects non-ISO strings (e.g. `"2026-7-1"`) with a 422. `nights` is the count of dates in `[checkin, checkout)` — the same checkout-exclusive convention as HTL-012 (`docs/qloapps/specs/HTL-012.md` §5.2). A zero- or negative-night span is 422.

### 4.3 `search_stays`

```python
def search_stays(
    *,
    hotel_id: str | None = None,
    city: str | None = None,        # one of hotel_id | city is required (else 422)
    checkin: str,                   # "YYYY-MM-DD" (inclusive — first night)
    checkout: str,                  # "YYYY-MM-DD" (exclusive — departure day, not a night)
    adults: int,
    children: int = 0,
    rooms: int = 1,
) -> StaySearchResult:
    """Read-only stay search. Pure composition over HTL-012 + HTL-015 — no DDB writes."""
```

**Flow** (per `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:123-150`):

1. **`_require_enabled()`** — flag-off 404 before any work.
2. **Validate**: `nights = _validate_span(checkin, checkout)` (≥ 1 night, ISO format). Validate `adults >= 1`, `children >= 0`, `rooms >= 1` (422 otherwise — also enforced by `StaySearchIn` at the router edge). Require `hotel_id or city`; both absent → `HTTPException(422, "one of hotel_id or city is required")`.
3. **Resolve candidate (hotel_id, room_type) pairs**:
   - `hotel_id` given → `hotel_pms.list_room_types(hotel_id)["room_types"]`, each paired with `hotel_id`.
   - else `city` given → `hotel_pms.list_hotels(city=city)` → for each resolved hotel, `list_room_types(hid)["room_types"]`, paired with that `hid`.
   - (Both absent already rejected in step 2.) An empty candidate set is **not** an error → returns an empty `results` list.
4. **For EACH candidate room type, compose the two forward-deps**:
   - **availability**: `avail = ha.check_availability(hid, rt_id, checkin, checkout, rooms_needed=rooms)` (HTL-012). If `not avail["available"]` → **skip** the room type (some night of the span is sold out — the intersection-across-the-span check, the distinction the OFBiz scalar counter cannot express, `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:57-61`).
   - **price**: `price = rate_plans.compute_stay_price(hid, rt_id, checkin, checkout, adults, children, rooms)` (HTL-015). Wrapped in `try/except HTTPException` keyed on **422** (LOS rule rejection — "stay too short/long"): a 422 from the price engine **excludes** that room type (caught + skipped, not propagated — a room type with an incompatible min/max-nights rule is simply not a search result). Any non-422 HTTPException re-propagates. The call NEVER mutates state.
5. **Build a `StayRoomTypeResult`** per surviving room type:
   `{hotel_id=hid, room_type_id=rt_id, name=rt["name"], available=True, min_remaining=avail["min_remaining"], rooms=rooms, per_night=price.per_night, total_cents=price.total_cents, currency=price.currency, applied_rule_ids=price.applied_rule_ids}`.
6. **Sort** `results` by `total_cents` **ascending** (cheapest first), with a **deterministic tiebreak by `room_type_id`** (`key=lambda r: (r.total_cents, r.room_type_id)`).
7. **Return** `StaySearchResult{checkin, checkout, nights, adults, children, rooms, results, result_count=len(results)}`.

**Pure composition**: no DDB writes, no `hold_rooms`, no holds, no audit event. The only state-touching calls are the read-only forward-deps' own internal reads.

## 5. Detailed Behavior & Edge Cases

### 5.1 No availability for any room type

Every candidate room type whose `check_availability(...)["available"]` is `False` is skipped. If **all** candidates are sold out (or there are no candidates), `results == []` and `result_count == 0` — HTTP 200, not an error. This is the safe default: a fully-booked hotel returns an empty result set, never an error.

### 5.2 Partial-span sold-out → room type excluded (the core primitive)

A room type available on every night **except one** is **excluded** — `check_availability` returns `available=False` because its `available` flag is the AND-reduction of every night's `sufficient` flag (HTL-012 §3.3, §5.3). This is the **intersection across the whole span**: a single sold-out night flips the entire stay to unbookable. This is precisely the distinction a scalar `(sku, location)` inventory counter cannot express (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:57-61`; OFBiz contrast, HTL-012 §2.6) — it has one number and no concept of "every night across a span." `min_remaining` (the binding night) is carried into the result **only** for surviving (available) room types, where it equals the smallest per-night remaining and is `>= rooms`.

### 5.3 Missing/never-seeded night → counts as sold out

A date never seeded by `set_total_rooms` has no DynamoDB row; HTL-010's `get_availability` surfaces it as a zeroed virtual row (`available = 0`), so `check_availability` sees `remaining = 0` ⇒ `sufficient = false` ⇒ `available = false` for that span (HTL-012 §5.4). HTL-017 inherits this transitively: a room type with a gap in its availability calendar over the requested span is excluded from search results. HTL-017 adds no special-casing for missing nights — it trusts the HTL-012 contract.

### 5.4 Checkout night is excluded from the span

`search_stays` passes `checkin`/`checkout` straight through to `check_availability` and `compute_stay_price`, both of which operate on `[checkin, checkout)` (checkout exclusive — the guest does not occupy a room the night of departure, HTL-012 §5.2). Consequence: a stay whose checkout date is itself sold out is **still bookable** — the checkout night is never inspected. The exclusion lives in HTL-010/012/015; HTL-017 does not re-implement it.

### 5.5 LOS-rule rejection excludes one room type without erroring the whole search

`compute_stay_price` raises `HTTPException(422, "stay too short/long")` when the stay violates a room type's length-of-stay (min/max-nights) rule (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:142-144,166-167`). `search_stays` catches the **422** from the price call and **skips** that room type — it does NOT propagate the error and abort the whole search. Other room types still return. This is the only HTTPException `search_stays` catches; a non-422 price error (e.g. an unexpected 500) re-propagates. A room type with **no rate plan** does **not** raise — it prices off `base_nightly_rate_cents` (the HTL-015 contract, `docs/qloapps/specs/HTL-005.md` §3.1) and appears in results.

### 5.6 `hotel_id` and `city` both absent → 422

`search_stays` requires exactly the disjunction "`hotel_id` or `city`." Both absent → `HTTPException(422, "one of hotel_id or city is required")` (also caught earlier by the `StaySearchIn._check_target` model validator at the router edge). If **both** are supplied, the precedence is `hotel_id` wins (the more specific target) — `city` is ignored. This precedence is documented as an assumption (§10.2).

### 5.7 `checkout <= checkin` → 422

`_validate_span` raises `HTTPException(422, "checkout must be after checkin")` for a zero- or negative-night span, and `HTTPException(422, "checkin/checkout must be YYYY-MM-DD")` for a malformed date, before any forward-dep call. A stay must be ≥ 1 night.

### 5.8 Occupancy exceeds a room type's max → handled by HTL-015, not duplicated here

A requested occupancy (`adults + children`) exceeding a room type's `max_occupancy` (HTL-005 §3.1) is a **pricing/eligibility** concern owned by `compute_stay_price` (HTL-015), which either prices an extra-guest supplement or rejects with a 422 (per the HTL-015 contract). HTL-017 does **not** independently re-validate occupancy against `max_occupancy` — doing so would fork the eligibility logic. If HTL-015 rejects an over-occupancy stay with a 422, §5.5's catch-and-skip applies and that room type is silently excluded; if HTL-015 prices a supplement, the room type appears with the higher `total_cents`. Single-sourcing this in HTL-015 keeps occupancy rules in one place.

### 5.9 Cheapest-first ordering with deterministic tiebreak

Results are sorted by `total_cents` ascending. Two room types with the **same** total are ordered by `room_type_id` ascending (a stable, deterministic tiebreak) so the result order is reproducible across calls — important for the FE results list and for hermetic test assertions. `result_count == len(results)` always holds.

### 5.10 `search_stays` performs zero DDB writes

Acceptance criterion (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:169-170`): no `hold_rooms`, no `put_item`, no reservation creation. `search_stays` is a non-locking advisory read — between a search and a later `create_reservation` (HTL-018), capacity can change. The **authoritative** binding check + atomic hold is in `create_reservation`/`hold_rooms` (HTL-018/HTL-011), not here. `search_stays` powers the search UX; it does not and must not lock (HTL-012 §10.4, same philosophy).

### 5.11 Pagination of candidate room types

`list_room_types` paginates (`{items, count, cursor}`, HTL-005 §4.1.3). For a single hotel with more room types than one page, `search_stays` should loop on the `cursor` to enumerate **all** active room types before composing (so a room type on page 2 is not silently dropped) — the same completeness discipline as HTL-012's calendar `LastEvaluatedKey` loop (HTL-012 §4.1). For the `city` branch, the hotels list is likewise paginated; a bounded result is assumed for MVP (§10.5). MVP scale (tens of room types per hotel) makes a single page typical, but the loop guarantees correctness.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_reservations.py` (and `search_stays` specifically) must contain **no** `if S.dev_mode` branch. `search_stays` issues no DynamoDB call of its own; the forward-dep functions it composes (`check_availability`, `compute_stay_price`, `list_room_types`, `list_hotels`) **already own any mock/real divergence internally** (each uses the same `T.*` handles in dev (moto) and prod (real DynamoDB) — HTL-012 §7.1, HTL-005 §7.1). HTL-017 calls them **identically** in both environments (cross-cutting constraint, `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:76-79`). Acceptance: `grep -n "dev_mode" app/services/hotel_reservations.py` returns nothing (or only a docstring).

### 7.2 Idempotency

`search_stays` is a **pure read** — naturally idempotent. Re-running it with identical inputs yields identical output, modulo concurrent availability/price changes in the underlying tables (which is correct — the search reflects current state). It writes nothing, so there is no idempotency-key, conditional-put, or replay concern. Two concurrent searches never interfere.

### 7.3 Security

- **Auth (router, HTL-020)**: `POST /ui/hotel-search` uses `require_ui_session` (`app/services/sessions.py:330`) — any authenticated user. A search is a read; no CSRF/admin gate (it creates no state). This matches the auth-split read side (`app/routers/inventory.py:48` GET → `require_ui_session`).
- **No ownership check at the service layer**: any authenticated user may search any hotel/city by id (single-platform deployment assumption, consistent with HTL-012 §10.1 / HTL-005 §7.3). Multi-tenant isolation is a non-breaking additive follow-up (§10.1).
- **Flag-off is 404, not 401/403**: a probe against a disabled vertical learns only "not found" — no entity-existence leak.
- **Input safety**: `hotel_id`, `city`, `checkin`, `checkout` are validated/parsed; date strings are parsed with `date.fromisoformat` (no injection surface — no SQL, no shell, no filesystem path). `hotel_id`/`city`/`room_type_id` flow only into the forward-dep DDB key conditions, which are exact-match key expressions (no scan filter injection).

### 7.4 Money-safety — read-only, no ledger interaction

`search_stays` is **read-only** and issues **no** Stripe/PayPal/CCBill call and writes **no** ledger entry (cross-cutting "No money fork", `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:80-83`). It surfaces `total_cents` for **display only** — the figure comes verbatim from `compute_stay_price(...).total_cents` (HTL-015); search does not re-compute or persist any monetary value. All money stays in integer cents (the money-as-cents convention); there is no float money field. The binding charge (when a reservation is later created and paid) routes through `billing_shared.new_ledger_entry` in a Tier-3 ticket (HTL-033), never through search. HTL-017 has zero financial invariants to enforce — it does not import `billing_shared` or any payment primitive.

### 7.5 Audit trail

`search_stays` emits **no** audit event (it is a read; consistent with `inventory.get_inventory` and HTL-012's two read functions). The `_audit()` wrapper is present in `hotel_reservations.py` for the HTL-018/019 mutation functions that share the file; HTL-017 does not call it.

## 8. Backward Compatibility & Migration

### 8.1 Additive-only changes

HTL-017 adds:
- One new file `app/services/hotel_reservations.py` with the flag/audit scaffolding, `_validate_span`, and `search_stays` (additive).
- Three Pydantic models to `app/models.py`: `StaySearchIn`, `StayRoomTypeResult`, `StaySearchResult` (additive; no existing model modified). `NightLineOut` is referenced from HTL-015, not redefined.

No existing endpoint, service function, DynamoDB table, GSI, or Pydantic model is modified. With `HOTEL_PMS_ENABLED=false` (the default), `search_stays` 404s — the running platform is byte-for-byte unchanged and produces zero DynamoDB traffic.

### 8.2 No DynamoDB migration

HTL-017 creates no table, no GSI, no `attr_types` change. `search_stays` reads only through the forward-dep functions, which use the tables provisioned by HTL-010/011 (availability) and HTL-001/005 (hotels/room-types). `just restart` in dev requires nothing new for HTL-017 itself.

### 8.3 Production deployment sequence

1. Deploy the upstream clusters (HTL-001/005/010/011/012/015) with `HOTEL_PMS_ENABLED=false` — their tables/indexes are provisioned; all service entrypoints 404.
2. Deploy HTL-017 with the flag still `false` — `search_stays` is defined but 404s.
3. Enable `HOTEL_PMS_ENABLED=true` once the upstream tables/indexes are verified healthy — `search_stays` (and the HTL-020 `/ui/hotel-search` endpoint) become live.

Zero-downtime; full rollback at any step by toggling the flag.

### 8.4 Rollback

The fast operational rollback is `HOTEL_PMS_ENABLED=false` — `search_stays` 404s with no redeploy. A code rollback reverts the two file changes (`hotel_reservations.py`, the three `models.py` additions). Because HTL-017 owns no persisted state, there is no data to migrate or drop on rollback.

### 8.5 Forward-dep ordering

HTL-017 is a **consumer** of HTL-012 (`check_availability`), HTL-015 (`compute_stay_price`), and HTL-005/001 (`list_room_types`/`list_hotels`). It can be **merged** before those clusters land (its hermetic tests patch the collaborators, §9.1), but it cannot **run live** until they do. The parent doc's dependency order (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:663-686`) places HTL-017 first in the reservation cluster (read-only, composes forward-deps), sharing `hotel_reservations.py` + the span-validation helper with HTL-018.

## 10. Open Questions / Assumptions

1. **Multi-tenant hotel/city isolation.** `search_stays` does not enforce that the caller owns the searched hotel/city. Any authenticated user may search any hotel by id. **Assumption**: single-platform deployment (one operator), consistent with HTL-012 §10.1 and HTL-005 §7.3. Multi-tenant isolation (filter candidates by an ownership record, 403/empty on mismatch) is a non-breaking additive follow-up; the QloApps codebase has no hotel-ownership table yet (Tier-1 prerequisite).

2. **`hotel_id` + `city` both supplied — precedence.** The spec resolves on `hotel_id` and ignores `city` when both are present (the more specific target wins, §5.6). **Assumption**: this precedence is acceptable; an alternative (422 "supply exactly one") could be enforced in `StaySearchIn` if the product prefers strictness — a non-breaking validator change.

3. **`NightLineOut` typing before HTL-015 merges.** `StayRoomTypeResult.per_night` is typed `List[NightLineOut]` (the HTL-015 shape). If HTL-017 is implemented before HTL-015 lands, `per_night` is temporarily typed `List[dict]` and tightened once HTL-015 merges. **Assumption**: the tightening is a non-breaking additive change (the serialized JSON is identical); the model reconciliation happens at HTL-015 merge time.

4. **`searched_at` timestamp.** §2.6 notes `search_stays` MAY stamp an informational `searched_at = now_ts()` on `StaySearchResult`. **Assumption**: omitted from the v1 model to keep the result minimal; it is an additive field if the FE wants a "results as of" label. The function is read-only either way.

5. **City-search result cap.** The `city` branch enumerates all hotels in a city × their room types, which could assemble a large result for a dense city. **Assumption**: callers request bounded cities and the cursor loops complete; a hard cap on candidate count (or a `limit` on `StaySearchResult.results`) is a non-breaking guard if abuse is observed. MVP scale (a handful of hotels per operator) makes this a non-issue.

6. **Occupancy eligibility ownership.** §5.8 delegates `adults + children` vs `max_occupancy` entirely to `compute_stay_price` (HTL-015). **Assumption**: HTL-015 owns occupancy pricing/rejection; HTL-017 does not duplicate the check. If HTL-015's contract changes (e.g. it returns an "ineligible" flag rather than a 422), HTL-017's catch-and-skip logic (§5.5) must reconcile — tracked at HTL-015 merge.

7. **Non-locking advisory read.** `search_stays` does not lock inventory; capacity can change between search and `create_reservation` (HTL-018). **Assumption**: this is correct — the authoritative atomicity is `hold_rooms`'s per-night conditional decrement (HTL-011/HTL-018), not the search (§5.10, HTL-012 §10.4).
