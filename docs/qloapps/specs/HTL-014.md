# HTL-014 — Rate-plan model + table + flag

**Type**: Feature | **Priority**: P1 | **Estimate**: 1.5d
**Source**: `docs/qloapps/RATE_PLANS_TICKETS.md` §HTL-014 + "Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §B

---

## 1. Summary & Goal

HTL-014 is the foundational, net-new ticket of the **price half** of the Hotel-PMS Tier-1 spine (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:122,134-136`). It lands exactly four deliverables and nothing more:

1. The `hotel_rate_plans` DynamoDB table — PK=`hotel_id#room_type_id`, SK=`META` for the plan header and SK=`RULE#{kind}#{rule_id}` for per-rule child rows co-located on the same partition — with its two GSIs (`GSI_HOTEL`, `GSI_ROOM_TYPE`) and the mandatory `attr_types={"created_at": "N"}` numeric-sort-key declaration.
2. The `hotel_rate_plans_table_name` setting wire + the `T.hotel_rate_plans` table handle. (The master `HOTEL_PMS_ENABLED` flag / `S.hotel_pms_enabled` setting already exists — it was added by HTL-001 and is reused by HTL-005; see §2.2 / §6.1.)
3. The `app/services/hotel_rate_plans.py` service: `create_rate_plan`, `get_rate_plan`, `add_rule`, `list_rules`, `update_rule`, `delete_rule`, `update_rate_plan`, `deactivate_rate_plan`, plus the five pure per-kind config validators.
4. The Pydantic I/O models in `app/models.py`: `RatePlanIn`, `RatePlanOut`, `RatePlanUpdateIn`, `RatePlanRuleIn`, `RatePlanRuleOut`.

A rate plan binds to exactly **one room type** (`hotel_id#room_type_id`) and holds a `base_nightly_rate_cents` (defaulting from the HTL-005 room type's `base_nightly_rate_cents` at create time) plus a set of **stay-dimension rule rows** of five kinds: `season`, `occupancy`, `los`, `advance`, `weekend`.

**Net-new, contrasted not reused.** testlogon already has two pricing layers — OFB-019/020 cart pricing rules (`app/services/pricing_rules.py`, `docs/ofbiz/specs/OFB-019.md`) and PRD-012 per-product price components (`docs/ofbiz/specs/PRD-012.md`) — and **neither has a per-night-of-stay or guest-occupancy dimension** (`docs/qloapps/RATE_PLANS_TICKETS.md:24-46`). HTL-014 lands the data model + rule rows; HTL-015 lands the deterministic multi-night summation engine that consumes them; HTL-016 the router/quote endpoint + frontend + tests. This ticket carries over only the **ideas** from OFB-019 — deterministic rule-evaluation **ordering** (`docs/ofbiz/specs/OFB-019.md:484-489`) and the **money-as-cents** integer convention — and never calls `pricing_rules.compute_discount` / `apply_stacking` (those operate on a cart, not a stay; `docs/qloapps/RATE_PLANS_TICKETS.md:48-53`).

With `HOTEL_PMS_ENABLED=false` (the default), every `hotel_rate_plans.py` entrypoint raises HTTP 404 before touching DynamoDB and the platform is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Gap — no nightly rate-plan model exists today

`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §B records the entire stay-dimension pricing cluster as **MISSING**:

- "Occupancy-based pricing (extra-adult/child surcharge) — **MISSING** … no guest-count dimension; OFB-019 tiers are on cart qty/total" (`:80`).
- "Length-of-stay (min/max nights, stay discounts) — **MISSING** … no nights concept" (`:81`).
- "Advance-purchase / last-minute / weekend-vs-weekday rates — **MISSING** … no lead-time or day-of-week pricing rule type" (`:82`).
- "Seasonal / date-range pricing — **PARTIAL** … PRD-012 `set_price_component`/`resolve_effective_price` returns ONE effective price as-of an instant, not a per-night rate across a span" (`:79`).

The headline names the two concepts that "defeat every existing primitive": a per-date remaining-rooms inventory (the sibling availability cluster, not this file) and "a **multi-night price computation across a check-in→check-out span**" (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:56-60`). HTL-014 lands the model that the HTL-015 span-summation engine reads.

### 2.2 Feature flag already exists (HTL-001)

The cross-cutting constraint mandates a single master flag `HOTEL_PMS_ENABLED` shared across the whole Hotel-PMS vertical (`docs/qloapps/RATE_PLANS_TICKETS.md:57-58`). That flag **already exists** — HTL-001 added `S.hotel_pms_enabled` (env `HOTEL_PMS_ENABLED`, default `false`) and `S.hotels_table_name` to `app/core/settings.py` (`docs/qloapps/specs/HTL-005.md:33`). HTL-014 **reuses** it; it adds only the new table-name setting (§4.1). The flag contract mirrors `INVENTORY_RESERVATIONS_ENABLED` exactly.

### 2.3 Flag-gate pattern to reuse (`app/services/inventory.py:50-56`)

`app/services/inventory.py` is the canonical flag-gate template:

```python
# inventory.py:50-56
def _flag_on() -> bool:
    return bool(getattr(S, "inventory_reservations_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Inventory reservations are not enabled")
```

HTL-014 copies this verbatim, reading `S.hotel_pms_enabled`, raising `HTTPException(status_code=404, detail="Hotel PMS is not enabled")`. The 404-on-off (not 403) is deliberate: the entity simply does not exist when the vertical is disabled (`docs/qloapps/specs/HTL-005.md:52`).

### 2.4 Audit wrapper to reuse (`app/services/inventory.py:92-98`)

```python
# inventory.py:92-98
def _audit(event: str, user_sub: str, **fields: Any) -> None:
    try:
        from app.services.alerts import audit_event
        audit_event(event, user_sub or "system", None, **fields)
    except Exception:
        pass
```

`hotel_rate_plans.py` copies this verbatim. Every mutation emits a best-effort audit event; failure is swallowed and never propagates.

### 2.5 Header + child-row idiom to reuse (`app/services/inventory.py:59-60`)

`inventory.py:59-60` co-locates child rows on the parent partition via an `sk` prefix helper:

```python
# inventory.py:59-60
def _location_sk(location_id: str) -> str:
    return f"LOC#{location_id}"
```

HTL-014 applies the same idiom: one `META` header row plus per-rule `RULE#{kind}#{rule_id}` child rows on a single `hotel_id#room_type_id` partition, enabling a cheap single-partition `begins_with(sk, "RULE#")` scan of all rules for a room type. This is the same shape HTL-005 uses for `ROOMTYPE#{room_type_id}` child rows on the `hotels` partition (`docs/qloapps/specs/HTL-005.md:71,106`) and PROP-001/002 use for `UNIT#{unit_id}` rows.

### 2.6 Structural analogue, contrasted: OFB-019 `PricingRules` (`docs/ofbiz/specs/OFB-019.md:580-593`)

The OFB-019 `PricingRules` table is the structural shadow — a `pk`/`sk` header + `rule_config` (M) child config, with a numeric-GSI `attr_types={"GSI1SK": "N", "created_at": "N"}` declaration (`docs/ofbiz/specs/OFB-019.md:580-593`). HTL-014's `TableDef` mirrors that shape. But the **field set differs fundamentally**: OFB-019 `rule_config` shapes are `tiered`/`bulk`/`conditional` keyed on **cart quantity** and **cart total** (`docs/ofbiz/specs/OFB-019.md:128-158`) — "there is no 'night', 'check-in', 'occupancy', or 'length-of-stay' concept anywhere" (`docs/qloapps/RATE_PLANS_TICKETS.md:32-34`). A rate plan binds to a **room type** and carries **stay-dimension** rule kinds. The only carry-overs are the rule-ordering idea (OFB-019 §5.4, `docs/ofbiz/specs/OFB-019.md:484-489` — ascending `priority`, lowest evaluated first) and the money-as-cents convention.

PRD-012's `resolve_effective_price` (`docs/ofbiz/specs/PRD-012.md:319-362`) is the second contrast: it returns ONE effective price as-of a single `as_of` instant — never a per-night rate summed across a span.

### 2.7 ID and primitive reuse

- `now_ts()` (`app/core/time.py:2`) → integer Unix seconds for `created_at` / `updated_at`. The whole file is two lines: `import time` then `def now_ts() -> int: return int(time.time())`.
- `rate_plan_id = "rp_" + uuid4().hex[:12]`; `rule_id = uuid4().hex` (non-deterministic — matches the FAC `create_location` / HTL-005 `room_type_id` id contract, `docs/qloapps/specs/HTL-005.md:114,264`). The plan **header** is keyed by the composite `hotel_id#room_type_id` PK + `META` SK, so plan creation is idempotent on (hotel, room_type) via a conditional put regardless of the random `rate_plan_id` convenience copy.
- `encode_cursor` / `decode_cursor` (`app/core/cursor.py:94,103`) — used by HTL-016's hotel-level rate-plan listing over `GSI_HOTEL`, not by HTL-014's per-partition `list_rules` (a single-partition query, no pagination needed at the rule level).

### 2.8 Dependency — HTL-005 room types (`docs/qloapps/specs/HTL-005.md`)

HTL-014 depends on **HTL-005**, which supplies the bound room type and its `base_nightly_rate_cents`. HTL-005 stores room types as `ROOMTYPE#{room_type_id}` child rows on the `hotels` table (PK=`hotel_id`, SK=`ROOMTYPE#{id}`), with `room_type_id = uuid4().hex` and a `base_nightly_rate_cents` `N` field (`docs/qloapps/specs/HTL-005.md:106,114,122,199`). `create_rate_plan` defaults its `base_nightly_rate_cents` from this room type's value at create time via `hotel_pms.get_room_type(hotel_id, room_type_id)` (`docs/qloapps/specs/HTL-005.md:275-279`) — a lazy import (avoid a hard module dependency / circular import), best-effort, falling back to the caller-supplied value. The rate plan stores its OWN copy: subsequent room-type rate edits do NOT retroactively mutate the plan (the plan is the authoritative price source for HTL-015).

### 2.9 What does NOT exist yet

`grep -rn "hotel_rate_plans\|HOTEL_RATE_PLANS\|RatePlanIn\|RatePlanRuleIn\|compute_stay_price" app/` returns nothing. No `hotel_rate_plans` table, no rate-plan service, no rate-plan Pydantic models. The `hotel_pms_enabled` flag and `hotels_table_name` setting exist (HTL-001); `hotel_rate_plans_table_name`, `T.hotel_rate_plans`, the `TableDef`, the service, and the models are all introduced by HTL-014.

## 3. Data Model

### 3.1 Table: `hotel_rate_plans`

Single DynamoDB table. PK=`hotel_id#room_type_id` (the composite of the bound hotel + room type), SK=`META` for the plan header and SK=`RULE#{kind}#{rule_id}` for per-rule child rows — header + children co-located on one partition (`docs/qloapps/RATE_PLANS_TICKETS.md:66-70,117-119`), the same idiom as inventory `LOC#` rows (`app/services/inventory.py:59-60`).

**Primary key**

| Key | Type | Value |
|---|---|---|
| `hotel_id#room_type_id` | S (PK) | Composite of the bound hotel + room type (literal `"#"` join) |
| `sk` | S (SK) | `"META"` (plan header) or `"RULE#{kind}#{rule_id}"` (rule child row) |

**META item (plan header)**

| Attribute | DDB Type | Notes |
|---|---|---|
| `hotel_id#room_type_id` | S | PK; composite of the bound hotel + room type |
| `sk` | S | `"META"` |
| `rate_plan_id` | S | `"rp_" + uuid4().hex[:12]` (convenience copy; the partition key is authoritative) |
| `hotel_id` | S | Denormalized for the `GSI_HOTEL` projection |
| `room_type_id` | S | Denormalized; the bound bookable room type (for `GSI_ROOM_TYPE`) |
| `name` | S | Human label (e.g. `"Standard Flexible"`); 1–200 chars |
| `base_nightly_rate_cents` | N | Plan base nightly rate in **cents**; defaults from the room type's `base_nightly_rate_cents` at create time; `ge=0` |
| `base_occupancy` | N | Adults included in the base rate before extra-adult surcharge; default `2`; `ge=1` |
| `currency` | S | ISO 4217; default `"USD"` |
| `active` | BOOL | Default `true` |
| `created_at` | N | `now_ts()` (`app/core/time.py:2`) |
| `updated_at` | N | `now_ts()`; restamped on every header/rule mutation of the plan |
| `created_by` | S | `user_sub` of the creating admin |

**RULE item (per-rule child row, SK=`RULE#{kind}#{rule_id}`)**

| Attribute | DDB Type | Notes |
|---|---|---|
| `hotel_id#room_type_id` | S | PK (same partition as the plan META) |
| `sk` | S | `"RULE#{kind}#{rule_id}"`; `rule_id = uuid4().hex` |
| `rule_id` | S | Convenience copy of the id |
| `kind` | S | One of `season` \| `occupancy` \| `los` \| `advance` \| `weekend` |
| `rule_config` | M | Per-kind config map (see §3.2) |
| `priority` | N | Default `500`; lower evaluated first (the OFB-019 §5.4 ordering idea, `docs/ofbiz/specs/OFB-019.md:484-489`) |
| `created_at` | N | `now_ts()` |
| `updated_at` | N | `now_ts()` |
| `created_by` | S | `user_sub` of the creating admin |

> The RULE rows carry `created_at` so they participate in the `GSI_HOTEL` / `GSI_ROOM_TYPE` indexes sparsely; the listing GSIs are primarily driven by META rows. The `GSI` partition keys (`hotel_id`, `room_type_id`) are present on both META and RULE rows.

### 3.2 Rule-config payloads (`rule_config` map)

| `kind` | `rule_config` shape | Semantics |
|---|---|---|
| `season` | `{start_date:"YYYY-MM-DD", end_date:"YYYY-MM-DD", mode:"absolute"\|"delta", value_cents:int}` | Per-night: for nights whose date ∈ `[start_date, end_date]`, `absolute` → override the night rate to `value_cents`; `delta` → add `value_cents` (may be negative) |
| `occupancy` | `{extra_adult_cents:int, extra_child_cents:int}` | Per-night surcharge: `max(0, adults - base_occupancy) * extra_adult_cents + children * extra_child_cents` |
| `los` | `{min_nights:int, max_nights:int\|null, discount_type:"percentage"\|"fixed_cents", discount_value:int}` | Whole-stay: rejects stays shorter than `min_nights` / longer than `max_nights`; applies the discount to the stay subtotal when `nights ∈ [min,max]` |
| `advance` | `{days_before_checkin:int, comparator:"gte"\|"lte", mode:"percentage"\|"fixed_cents", value:int}` | Whole-stay: when `advance_days` satisfies the comparator vs `days_before_checkin`, modify the stay subtotal (advance-purchase = `gte` discount; last-minute = `lte` delta) |
| `weekend` | `{dow:[int,...], mode:"absolute"\|"delta", value_cents:int}` | Per-night: for nights whose ISO weekday (Mon=1..Sun=7) ∈ `dow`, override (`absolute`) or add (`delta`) `value_cents` |

Money fields are **integer cents** throughout (OFB-019 / PRD-012 convention, `docs/qloapps/RATE_PLANS_TICKETS.md:79-80`). `value_cents` / `delta` / `discount_value` may be negative **only** in `delta` modes; `absolute` / rate fields are `ge=0`. This is enforced per-kind in the service validator (§4.4), not only at the Pydantic edge, so direct service callers and tests are also guarded.

### 3.3 GSIs

| Index name | PK | SK | Purpose |
|---|---|---|---|
| `GSI_HOTEL` | `hotel_id` (S) | `created_at` (N) | List a hotel's rate plans newest-first (admin rate-plan listing — HTL-016 `GET /ui/hotels/{hotel_id}/rate-plans`) |
| `GSI_ROOM_TYPE` | `room_type_id` (S) | `created_at` (N) | Fetch the rate plan(s) for a room type (the path HTL-015's quote / HTL-017's stay-search calls) |

Both GSIs project all attributes (`ALL`). `created_at` is the numeric sort key on both → it **MUST** appear in `attr_types` (§3.4).

### 3.4 `attr_types`

`attr_types={"created_at": "N"}` — mandatory. Per the CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha and the cross-cutting constraint (`docs/qloapps/RATE_PLANS_TICKETS.md:71-75`): omitting it stores `created_at` as String → `ValidationException` when `GSI_HOTEL` / `GSI_ROOM_TYPE` are queried with an integer `created_at`. OFB-019's `TableDef` is the precedent (`{"GSI1SK": "N", "created_at": "N"}`, `docs/ofbiz/specs/OFB-019.md:589`).

### 3.5 TableDef (append in `scripts/local-ddb-init.py`)

Follows the existing `TableDef(...)` form (cf. OFB-019 `PricingRules` def, `docs/ofbiz/specs/OFB-019.md:580-593`):

```python
TableDef(
    _resolve_table_name(S.hotel_rate_plans_table_name, "hotel_rate_plans"),
    "hotel_id#room_type_id",
    "sk",
    gsi=[
        {"index_name": "GSI_HOTEL",     "partition_key": "hotel_id",     "sort_key": "created_at"},
        {"index_name": "GSI_ROOM_TYPE", "partition_key": "room_type_id", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

`kind` and the per-kind `mode` / `comparator` / `discount_type` literals are constrained as enumerated in §3.2. Numeric fields returned from DynamoDB as `Decimal` are coerced to `int` before model construction (§5.7).

### 4.3 Service: `app/services/hotel_rate_plans.py` (new file)

Modeled on `app/services/inventory.py`. No `if S.dev_mode` branch anywhere (SECOPS-007, §7.1). Money is always integer cents. Nothing random in pricing math; nothing env-tunable in the math (rate values live in DDB rule rows, not settings — `docs/qloapps/RATE_PLANS_TICKETS.md:223-224`).

**Module-level helpers** (copied from inventory.py):

**`create_rate_plan`**

```python
def create_rate_plan(
    hotel_id: str,
    room_type_id: str,
    *,
    name: str,
    base_nightly_rate_cents: int | None = None,
    base_occupancy: int = 2,
    currency: str = "USD",
    user_sub: str,
) -> dict:
```

- `_require_enabled()` first.
- If `base_nightly_rate_cents is None`, default from the room type via a lazy import of `hotel_pms.get_room_type(hotel_id, room_type_id)` (`docs/qloapps/specs/HTL-005.md:275-279`); best-effort `try/except` → fall back to `0` if the room type cannot be read (the model edge already requires either a caller value or a room type). The plan stores its own copy (§2.8).
- Derives `rate_plan_id = "rp_" + uuid4().hex[:12]`.
- Builds the META item: PK=`_pk(...)`, `sk="META"`, all header attributes, `active=True`, `created_at=now_ts()`, `updated_at=now_ts()`, `created_by=user_sub`.
- `T.hotel_rate_plans.put_item(Item=item, ConditionExpression="attribute_not_exists(#pk) AND attribute_not_exists(sk)")` (alias `#pk` → `"hotel_id#room_type_id"` since the key name contains `#`). On `ConditionalCheckFailedException`, read and return the existing META via `get_rate_plan(hotel_id, room_type_id)` — **idempotent** on (hotel_id, room_type_id) (§5.1).
- `_audit("hotel.rate_plan.created", user_sub, hotel_id=hotel_id, room_type_id=room_type_id, rate_plan_id=rate_plan_id)`.
- Returns the coerced item dict.

**`get_rate_plan`**

```python
def get_rate_plan(hotel_id: str, room_type_id: str) -> dict | None:
```

- `_require_enabled()`. `T.hotel_rate_plans.get_item(Key={"hotel_id#room_type_id": _pk(...), "sk": "META"})`. Returns the coerced item or `None`. Never raises 404 — the caller/router maps `None` → 404 (mirrors `inventory.get_inventory` / `hotel_pms.get_room_type`, `docs/qloapps/specs/HTL-005.md:279`).

**`add_rule`**

```python
def add_rule(
    hotel_id: str, room_type_id: str, *,
    kind: str, rule_config: dict, priority: int = 500, user_sub: str,
) -> dict:
```

- `_require_enabled()`.
- Validate the parent plan exists via `get_rate_plan(...)` → `HTTPException(404, "rate plan not found")` if missing.
- Dispatch to the per-kind validator (§4.4); a validation failure raises `HTTPException(422, ...)` **before** any write.

- `_audit("hotel.rate_plan.rule.added", user_sub, hotel_id=hotel_id, room_type_id=room_type_id, kind=kind, rule_id=rule_id)`.
- Returns the coerced rule dict.

**`list_rules`**

```python
def list_rules(hotel_id: str, room_type_id: str) -> list[dict]:
```

- `_require_enabled()`.

### 4.4 Per-kind config validators (pure, deterministic)

Five module-level pure functions, each raising `HTTPException(422, ...)` on a malformed config and returning `None`/the normalized config on success. **No DDB access, no randomness, no time** — pure validation.

- `_validate_season_config` — `start_date` / `end_date` are valid `YYYY-MM-DD` and `start_date <= end_date`; `mode ∈ {"absolute","delta"}`; `value_cents` is int (`ge=0` for `absolute`, any int for `delta`).
- `_validate_occupancy_config` — `extra_adult_cents`, `extra_child_cents` are ints `ge=0`.
- `_validate_los_config` — `min_nights >= 1`; `max_nights is None or max_nights >= min_nights`; `discount_type ∈ {"percentage","fixed_cents"}`; `discount_value >= 0` (`<= 100` when `percentage`).
- `_validate_advance_config` — `days_before_checkin >= 0`; `comparator ∈ {"gte","lte"}`; `mode ∈ {"percentage","fixed_cents"}`; `value` is int (`ge=0` for `percentage`/`fixed_cents` discount or surcharge as specified by the mode; the sign is interpreted by HTL-015).
- `_validate_weekend_config` — `dow` is a non-empty list of ints each ∈ `1..7`; `mode ∈ {"absolute","delta"}`; `value_cents` int (`ge=0` for `absolute`, any int for `delta`).

A `_VALIDATORS = {"season": _validate_season_config, ...}` dispatch map drives `add_rule` / `update_rule`; an unknown `kind` raises `HTTPException(422, "unknown rule kind")`.

> **HTL-014 ships only validation + storage.** The actual per-night / whole-stay arithmetic that consumes these configs is `compute_stay_price`, owned by HTL-015 (`docs/qloapps/RATE_PLANS_TICKETS.md:256-383`). HTL-014 stores well-formed rule rows; HTL-015 reads them via `get_rate_plan` + `list_rules`.

### 4.5 Router / auth (HTL-016 — referenced, not owned)

The HTTP surface is HTL-016's deliverable. For completeness: reads → `require_ui_session` (`app/services/sessions.py:330`); mutations → `require_admin_or_root_csrf` (`app/auth/policy.py:100`) — the identical split to `app/routers/inventory.py:38,48,65,81` (`docs/qloapps/RATE_PLANS_TICKETS.md:81-84`). ## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent plan creation (one plan per room type)

`create_rate_plan` uses a conditional put (`attribute_not_exists` on the composite PK + `sk`). If two callers race for the same (hotel_id, room_type_id) META, exactly one write wins; the loser catches `ConditionalCheckFailedException` and reads back the existing META via `get_rate_plan`, returning the **same** `rate_plan_id` as the winner. A caller may call `create_rate_plan` twice with the same (hotel, room_type) and receive the same plan both times with no error (acceptance criterion, `docs/qloapps/RATE_PLANS_TICKETS.md:232-233`). The random `rate_plan_id` is a convenience copy only — the partition key is authoritative, so the random suffix does not break idempotency.

### 5.2 META and RULE rows co-locate; `list_rules` excludes META

All rows for a (hotel, room_type) share one partition. `list_rules` queries `begins_with(sk, "RULE#")`, which never matches the literal `"META"` SK, so the header row is excluded by construction (acceptance criterion, `docs/qloapps/RATE_PLANS_TICKETS.md:234-235`). Results are sorted by `priority` (then `kind`, `rule_id`) so the ordering is deterministic regardless of DynamoDB's natural `sk` (lexicographic) order.

### 5.3 Per-kind config validation rejects malformed configs before any write

Each `_validate_*_config` runs before the `put_item` / `update_item`. Rejected: bad date range (`start_date > end_date`), `dow` outside `1..7`, `max_nights < min_nights`, `min_nights < 1`, unknown `mode`/`comparator`/`discount_type`, non-int money fields, negative money in a non-`delta`/non-discount field, `percentage` > 100 (acceptance criterion, `docs/qloapps/RATE_PLANS_TICKETS.md:236-238`). Validation is pure and deterministic — same input always yields the same accept/reject.

### 5.4 `delete_rule` no-raise contract

`delete_rule` returns `False` for an unknown rule and never raises (acceptance criterion, `docs/qloapps/RATE_PLANS_TICKETS.md:239`; mirrors `host_inventory.delete_host`). This lets a router DELETE handler return a clean 200/204 idempotently even if the rule was already gone.

### 5.5 Negative money only in `delta`/discount modes

`absolute` season/weekend `value_cents`, `base_nightly_rate_cents`, occupancy surcharges, and LOS `fixed_cents` discounts are `ge=0`. Only `delta` modes (`season`/`weekend`) allow a negative `value_cents` (a per-night discount). The validators enforce this per-kind so a direct service caller cannot persist a negative absolute rate. HTL-015 additionally floors each computed night at 0 — but HTL-014's job is to never let a structurally invalid rate row land.

### 5.6 `base_nightly_rate_cents` default sourcing

When the caller omits `base_nightly_rate_cents`, the service reads it from the HTL-005 room type at create time (§2.8). The read is best-effort: if HTL-005 is not yet deployed or the room type is missing, the create still succeeds with a `0` default (the model edge normally requires either a caller value or an existing room type, so this fallback is a defensive belt-and-braces). The plan's stored copy is authoritative thereafter; the rate plan never re-reads the room type on subsequent gets.

### 5.7 Decimal coercion

`base_nightly_rate_cents`, `base_occupancy`, `priority`, `created_at`, `updated_at`, and the numeric values inside `rule_config` are stored as `N` and returned by boto3 as `Decimal`. The service coerces them to `int` (via `_to_int`) before returning, so `RatePlanOut` / `RatePlanRuleOut` validate and round-trip cleanly (same requirement as HTL-005 §2.7, `docs/qloapps/specs/HTL-005.md:79`, and the CLAUDE.md `MessageEncryptionEnvelope Decimal coercion` pattern).

### 5.8 Flag-off behavior

When `HOTEL_PMS_ENABLED=false` (default), every `hotel_rate_plans.py` entrypoint (`create_rate_plan`, `get_rate_plan`, `add_rule`, `list_rules`, `update_rule`, `delete_rule`, `update_rate_plan`, `deactivate_rate_plan`) raises `HTTPException(404, "Hotel PMS is not enabled")` before touching DynamoDB (acceptance criterion, `docs/qloapps/RATE_PLANS_TICKETS.md:230-231`). The `hotel_rate_plans` table may or may not exist — the flag check runs first.

### 5.9 `update_rate_plan` with empty kwargs

If `kwargs` is empty, the service still stamps `updated_at=now_ts()` — giving callers a way to bump the timestamp without a data change (matches the PROP-001 §5.9 / §10 decision). Routers driving via `RatePlanUpdateIn` send at least one field anyway.

### 5.10 One plan per room type (scope)

The composite PK `hotel_id#room_type_id` + `META` SK enforces at most one rate plan per room type. The `GSI_HOTEL` / `GSI_ROOM_TYPE` indexes therefore return at most one META per room type. If the product later needs multiple named plans per room type (e.g. "Flexible" vs "Non-refundable"), that is an additive change to the SK scheme (e.g. `META#{rate_plan_id}`) — documented as an open question (§10).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_rate_plans.py` contains **no** `if S.dev_mode` branch (acceptance criterion, `docs/qloapps/RATE_PLANS_TICKETS.md:242`). The same `T.hotel_rate_plans` boto3 path runs in dev (moto intercepts boto3 in-process) and prod (real DynamoDB) — identical to `app/services/inventory.py` (no `dev_mode` branch anywhere) and the cross-cutting constraint (`docs/qloapps/RATE_PLANS_TICKETS.md:85-89`).

### 7.2 Idempotency

`create_rate_plan` is idempotent on (hotel_id, room_type_id) via the conditional-put + read-back-on-collision pattern (§5.1). `update_rate_plan` / `deactivate_rate_plan` / `update_rule` are unconditional (idempotent in result, not in `updated_at`). `delete_rule` is idempotent (returns `False` on a second delete, never raises). `add_rule` mints a fresh `rule_id` each call, so two identical `add_rule` calls create two distinct rule rows — this is intentional (mirrors OFB-019 rule creation, `docs/ofbiz/specs/OFB-019.md` §7.2 "rule creation is intentionally non-idempotent"); callers dedupe.

### 7.3 Security

Mutations are restricted at the HTL-016 router layer to `require_admin_or_root_csrf` (`app/auth/policy.py:100`); reads to `require_ui_session` (`app/services/sessions.py:330`). The service layer itself does not enforce ownership — appropriate for a single-operator hotel deployment (mirrors PROP-001 §7.3). Multi-tenant hotel isolation, if needed, is a router-layer ownership check — documented in §10. The service never logs secrets; audit events carry only ids and kinds.

### 7.4 Money-safety

All money is **integer cents** (OFB-019 / PRD-012 convention). HTL-014 stores rate values; it performs **no** arithmetic and touches **no** billing/ledger primitive (`billing_shared.new_ledger_entry` etc. are not imported). The per-kind validators reject negative money in non-`delta`/non-discount fields so a structurally invalid rate can never land. The negative-total guard (flooring a stay at `>= 0`) is HTL-015's responsibility (the OFB-019 §7.4 guard idea, `docs/ofbiz/specs/OFB-019.md:635-637`) — HTL-014 only ensures the inputs are well-formed. No financial invariant settles in this ticket.

### 7.5 Audit trail

Every mutation emits a best-effort `_audit()` event (copied from `inventory.py:92-98`): `hotel.rate_plan.created`, `hotel.rate_plan.updated`, `hotel.rate_plan.deactivated`, `hotel.rate_plan.rule.added`, `hotel.rate_plan.rule.updated`, `hotel.rate_plan.rule.deleted`. Audit failure is swallowed and never propagates.

## 10. Open Questions / Assumptions

1. **HTL-005 availability at build time.** `create_rate_plan` defaults `base_nightly_rate_cents` from the HTL-005 room type via a lazy `hotel_pms.get_room_type` import. **Assumption**: HTL-005 lands first (it is the declared dependency); if HTL-005 is not yet merged, the best-effort `try/except` falls back to `0` and the caller must pass an explicit `base_nightly_rate_cents`. Confirm HTL-005's exported function name is `get_room_type(hotel_id, room_type_id)` (verified at `docs/qloapps/specs/HTL-005.md:275`).
2. **One plan per room type.** The composite PK + `META` SK enforces a single rate plan per room type (§5.10). **Assumption**: one plan per room type is sufficient for MVP. Supporting multiple named plans (Flexible / Non-refundable) is an additive SK-scheme change (`META#{rate_plan_id}`) and a forward concern.
3. **`occupancy`/`los`/`advance` cardinality.** §3.2 treats `occupancy` as effectively a single rule per plan (HTL-015 reads "the single `occupancy` rule if present", `docs/qloapps/RATE_PLANS_TICKETS.md:306`). HTL-014 does **not** enforce cardinality at write time — a caller could add two `occupancy` rules. **Assumption**: HTL-015 deterministically picks the lowest-`priority` `occupancy`/`los`/`advance` rule; HTL-014 stores whatever is added. A future hard cardinality guard in `add_rule` is an open option.
4. **`update_rate_plan` empty kwargs.** Stamps `updated_at` silently rather than 422-ing (§5.9). **Assumption**: matches PROP-001's decision; routers send at least one field.
5. **Multi-tenant hotel isolation.** The service does not enforce that the caller owns the hotel. **Assumption**: single-operator deployment; cross-hotel isolation, if needed, is a router-layer ownership check (mirrors PROP-001 §10).
6. **`advance` value sign convention.** §3.2 says `gte` = discount, `lte` = delta. **Assumption**: the stored `value` is a magnitude and HTL-015 applies the sign per comparator/mode; the validator only enforces type + range, leaving sign interpretation to the engine (documented so HTL-015 and HTL-014 agree).
