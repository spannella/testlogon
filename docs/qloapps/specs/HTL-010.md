# HTL-010 — Per-date availability inventory model + table

**Type**: Feature | **Priority**: P1 | **Estimate**: 2d
**Source**: `docs/qloapps/AVAILABILITY_INVENTORY_TICKETS.md` §HTL-010 + "Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §B

---

## 1. Summary & Goal

HTL-010 is the P1 foundational ticket for the QloApps hotel-PMS availability vertical. It lands exactly four deliverables: (1) the `hotel_availability` DynamoDB table with its `GSI_HOTEL_DATE` index and correct `attr_types`, (2) the master `HOTEL_PMS_ENABLED` feature flag with a `_flag_on()` / `_require_enabled()` 404 contract, (3) the seed/set + read service `app/services/hotel_availability.py` (`set_total_rooms`, `get_day`, `get_availability`) plus the derived-`available` computation, and (4) the Pydantic I/O models (`AvailabilityDayOut`, `AvailabilitySetIn`, `AvailabilityDayIn`).

The distinctive net-new primitive is the **per-room-type per-DATE remaining-rooms** row: one DynamoDB item per `(hotel_id, room_type_id, calendar_date)`, so the same room type can be sold-out on `2026-07-04` and wide-open on `2026-07-05`. This is the dimension the OFBiz scalar inventory record (`app/services/inventory.py`, `(sku, location)` → `on_hand`/`reserved`/`available`) has **no concept of** (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:83` — "inventory (OFB-003) is `(sku, location)` scalar `on_hand`/`reserved` — no date dimension; the distinctive hotel primitive"). We **reuse the conditional-update idiom and the flag/audit/table scaffolding** from `inventory.py` but **NOT the data model**: we add a DATE key.

Without HTL-010, no other HTL ticket (HTL-011 block/hold + overbooking/min-max, HTL-012 read/calendar API + booking-time check, HTL-013 frontend grid + tests) can be implemented. With HTL-010 merged but `HOTEL_PMS_ENABLED=false` (the default), the platform is byte-for-byte unchanged: no new HTTP surface is exposed (the router lands in HTL-012) and existing behaviour is entirely unaffected — every `hotel_availability.py` entrypoint short-circuits to 404 before touching DynamoDB.

### 2.2 The structural analogue we CONTRAST (not reuse): OFBiz scalar inventory

The closest artefact is the OFBiz inventory + soft-reservation pair (`app/services/inventory.py`, OFB-003/004). ### 2.5 Derived-counter recompute pattern to reuse

`available` is never an authoritative stored field that can drift — it is recomputed from authoritative inputs on every read/mutation. `app/services/inventory.py:101-115` (`_record_out`) and `:131` (`_persist`) compute `available = on_hand - reserved` each time. HTL-010's `_available(item)` is the date-keyed analogue: `available = total_rooms + overbooking_allowance - booked - held` (`docs/qloapps/AVAILABILITY_INVENTORY_TICKETS.md:110`; the sellable-clamp line `max(0, available - min_availability)` is at `:113`).

### 2.6 Zeroed-virtual-record pattern to reuse

`app/services/inventory.py:158-173` (`get_or_zero`) returns a zeroed virtual record for an absent SKU rather than `None`/an error. HTL-010's `get_availability` reuses this: a never-seeded date surfaces as a zeroed virtual row (`available = 0`) so it reads as **sold-out, not an error** — the correct semantic for a hotel calendar (an un-loaded date has no inventory and is unbookable).

### 2.7 Preserve-on-set pattern to reuse

`app/services/inventory.py:185-206` (`set_on_hand`) sets the absolute `on_hand` while **preserving** the existing `reserved` (read-merge: read the row, keep `reserved`/`reorder_point`, overwrite `on_hand`). HTL-010's `set_total_rooms` does the date-keyed read-merge equivalent per date: it overwrites `total_rooms` while preserving any existing `booked`/`held`/`overbooking_allowance`/`min_availability`/`max_availability` on that date-row.

## 3. Data Model

### 3.1 Table: `hotel_availability`

Single DynamoDB table. The composite partition key co-locates **all of a room type's calendar days on one partition** so a per-room-type date-range read is a single cheap `begins_with(sk, "DATE#")` / `between(...)` query — the header+child idiom from `docs/open-property/PROPERTY_UNITS_TICKETS.md` and the FAC `LOC#`-child pattern (`docs/ofbiz/specs/OFB-003.md`).

**Primary key**

| Key | Type | Value |
|---|---|---|
| `availability_pk` | S (PK) | `"{hotel_id}#{room_type_id}"` composite (one partition per room type) |
| `sk` | S (SK) | `"DATE#{YYYY-MM-DD}"` — ISO calendar date; **lexical order == chronological order**, so `between`/`begins_with` range queries are date-ordered for free |

**Date-row attributes**

| Attribute | DDB Type | Constraints / Notes |
|---|---|---|
| `availability_pk` | S | PK = `"{hotel_id}#{room_type_id}"` composite |
| `sk` | S | `"DATE#{YYYY-MM-DD}"` |
| `hotel_id` | S | Owning hotel id (convenience copy for the `GSI_HOTEL_DATE` PK + projections) |
| `room_type_id` | S | Owning room type id (convenience copy; opaque — HTL-005 FK, not enforced here) |
| `date` | S | `YYYY-MM-DD` (convenience copy of the SK date; the `GSI_HOTEL_DATE` sort key) |
| `total_rooms` | N | Physical rooms of this type sellable on this date; set by `set_total_rooms` |
| `booked` | N | Rooms consumed by confirmed reservations; default `0` (advanced by the reservation cluster HTL-018, forward ref — HTL-010 never writes it after seed) |
| `held` | N | Rooms held by active (TTL) holds; default `0` (managed by HTL-011 `hold_rooms`/`release_hold`) |
| `overbooking_allowance` | N | Extra rooms sellable beyond `total_rooms`; default `0` (set by HTL-011) |
| `min_availability` | N | Optional floor: stop selling once sellable drops to this; default `0` (set by HTL-011) |
| `max_availability` | N | Optional cap on sellable rooms for this date; optional/absent by default (set by HTL-011) |
| `updated_at` | N | `now_ts()` — integer Unix seconds (`app/core/time.py:2`), stamped on every mutation |

**Derived (computed, not stored authority)**

`available = total_rooms + overbooking_allowance - booked - held`, recomputed on every read/mutation exactly like `available` in `app/services/inventory.py:101-115,131`. For **sell decisions** the sellable count is `max(0, available - min_availability)` where `min_availability` reserves a hold-back floor (HTL-011 enforces the floor in its hold condition; HTL-010 only computes and surfaces the raw `available`). HTL-010 persists no `available` column — it is computed in `_available(item)` and returned on `AvailabilityDayOut`. (The optional persisted-`available` projection for the GSI calendar is deferred to HTL-012's read path; HTL-010 keeps `available` purely derived to avoid drift, matching `inventory.py`.)

**GSI**

| Index name | PK | SK | Purpose |
|---|---|---|---|
| `GSI_HOTEL_DATE` | `hotel_id` (S) | `date` (S) | Hotel-wide availability calendar across ALL room types for a date range (HTL-012 `availability_calendar`) without scanning each room type's partition separately. `date` is `S` (lexical==chronological) so `between(start, end)` is date-ordered — **no numeric `attr_types` entry needed for the index sort key**. |

Projection: `ALL`.

**`attr_types`**: `{"updated_at": "N"}` — mandatory per CLAUDE.md DynamoDB numeric-GSI rule. `updated_at` is declared numeric for any freshness/admin sort path; `date` (the GSI sort key) is `S` and needs no entry. Omitting `attr_types` for `updated_at` would store it as String → `ValidationException` on integer comparisons.

> **HTL-011 will add a second GSI** (`GSI_HOLD_EXPIRY`, PK=`gsi_expiry_pk` / SK=`expires_at` N, `attr_types={"expires_at": "N"}`) and the `HOLD#{hold_id}` meta rows to this **same** `TableDef`. The two tickets' `local-ddb-init.py` changes must be reconciled into a single `TableDef` with both GSIs and merged `attr_types={"updated_at": "N", "expires_at": "N"}` (`docs/qloapps/AVAILABILITY_INVENTORY_TICKETS.md:242-246`). HTL-010 ships only `GSI_HOTEL_DATE`.

**TableDef** (appended in `scripts/local-ddb-init.py` inside `_table_defs()` after the last existing entry, following the `inventory`/`reservations` `TableDef` style at `scripts/local-ddb-init.py:2456-2478` and `docs/ofbiz/specs/OFB-003.md` §3.1 — note OFB-004 §3.1 is "No new tables", so the table-shape reference is OFB-003):

```python
TableDef(
    _resolve_table_name(S.hotel_availability_table_name, "hotel_availability"),
    "availability_pk",
    "sk",
    gsi=[
        {"index_name": "GSI_HOTEL_DATE", "partition_key": "hotel_id", "sort_key": "date"},
    ],
    attr_types={"updated_at": "N"},

```

**Module-level helpers**

```python
def _flag_on() -> bool:
    return bool(getattr(S, "hotel_pms_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Hotel PMS is not enabled")

def _audit(event: str, user_sub: str, **fields: Any) -> None:        # copy of inventory.py:92-98
    try:
        from app.services.alerts import audit_event
        audit_event(event, user_sub or "system", None, **fields)
    except Exception:
        pass

def _availability_pk(hotel_id: str, room_type_id: str) -> str:
    return f"{hotel_id}#{room_type_id}"

def _date_sk(date: str) -> str:
    return f"DATE#{date}"

def _to_int(value: Any, default: int = 0) -> int:                    # copy of inventory.py:67-73
    try:
        return default if value is None else int(value)
    except (TypeError, ValueError):
        return default

def _date_range(start: str, end: str) -> list[str]:
    """Inclusive list of YYYY-MM-DD strings from start..end."""
    from datetime import date, timedelta
    d0, d1 = date.fromisoformat(start), date.fromisoformat(end)
    if d1 < d0:
        raise HTTPException(status_code=422, detail="end_date must be >= start_date")
    out, cur = [], d0
    while cur <= d1:
        out.append(cur.isoformat())
        cur += timedelta(days=1)
    return out

def _available(item: dict) -> int:                                    # date-keyed analogue of _record_out
    return (_to_int(item.get("total_rooms")) + _to_int(item.get("overbooking_allowance"))
            - _to_int(item.get("booked")) - _to_int(item.get("held")))

def _row_out(item: dict) -> dict:
    return {
        "hotel_id": item.get("hotel_id"),
        "room_type_id": item.get("room_type_id"),
        "date": item.get("date"),
        "total_rooms": _to_int(item.get("total_rooms")),
        "booked": _to_int(item.get("booked")),
        "held": _to_int(item.get("held")),
        "overbooking_allowance": _to_int(item.get("overbooking_allowance")),
        "min_availability": _to_int(item.get("min_availability")),
        "max_availability": (None if item.get("max_availability") is None
                             else _to_int(item.get("max_availability"))),
        "available": _available(item),
        "updated_at": _to_int(item.get("updated_at")),
    }

def _zero_row(hotel_id: str, room_type_id: str, date: str) -> dict:   # analogue of get_or_zero
    return {
        "hotel_id": hotel_id, "room_type_id": room_type_id, "date": date,
        "total_rooms": 0, "booked": 0, "held": 0, "overbooking_allowance": 0,
        "min_availability": 0, "max_availability": None, "available": 0, "updated_at": 0,
    }
```

**`set_total_rooms(hotel_id, room_type_id, start_date, end_date, total_rooms, *, user_sub) -> list[dict]`**
- Calls `_require_enabled()` first; validates `total_rooms >= 0` (else 422).
- For each `date` in `_date_range(start_date, end_date)`: `get_item` the existing date-row (read-merge), **preserve** any existing `booked`/`held`/`overbooking_allowance`/`min_availability`/`max_availability`, overwrite `total_rooms`, stamp `updated_at = now_ts()`, `put_item` the full row (with `availability_pk`, `sk=DATE#{date}`, the three convenience copies `hotel_id`/`room_type_id`/`date`). This is the `set_on_hand` preserve-on-set shape (`inventory.py:185-206`) applied per date.
- Emits **one** `_audit("hotel.availability.set_total", user_sub, hotel_id=..., room_type_id=..., start_date=..., end_date=..., total_rooms=...)` per range.
- Returns the list of `_row_out(...)` rows written (newest semantics N/A — chronological order of the range).

**`get_day(hotel_id, room_type_id, date) -> dict | None`**
- `_require_enabled()`; `get_item(Key={"availability_pk": _availability_pk(...), "sk": _date_sk(date)})`; returns `_row_out(item)` or `None`.

**`get_availability(hotel_id, room_type_id, checkin, checkout) -> list[dict]`**
- `_require_enabled()`; computes the **stay span** `[checkin, checkout)` — checkout **exclusive** (the guest does not occupy a room the night of departure, `docs/qloapps/AVAILABILITY_INVENTORY_TICKETS.md:177-180`). The span nights are `_date_range(checkin, checkout_minus_one_day)`; if `checkout <= checkin` → 422.
- One `Key` query on the partition with `KeyConditionExpression=Key("availability_pk").eq(pk) & Key("sk").between(_date_sk(first_night), _date_sk(last_night))` (date-ordered for free).
- Builds a `{date: row}` map from the query result, then returns the rows **for every night of the span in order**, surfacing **missing dates as zeroed virtual rows** (`_zero_row(...)`, `available = 0`) so a never-seeded night reads as sold-out, not an error (`get_or_zero` analogue, `inventory.py:158-173`).

All entrypoints call `_require_enabled()` first, before any DynamoDB access.

> `check_availability` (span-intersection booking check) and `availability_calendar` (GSI hotel-wide aggregation) are **HTL-012** service additions — they compose `get_availability` / `GSI_HOTEL_DATE`. They are out of scope for HTL-010.

## 5. Detailed Behavior & Edge Cases

### 5.1 Date-range seed writes exactly one row per date

`set_total_rooms("h1", "rt1", "2026-07-04", "2026-07-06", 10, user_sub="admin")` writes exactly **3** `DATE#`-keyed rows (`DATE#2026-07-04`, `DATE#2026-07-05`, `DATE#2026-07-06`) on the single partition `availability_pk="h1#rt1"`. `_date_range` is inclusive of both endpoints. A single-day range (`start_date == end_date`) writes one row.

### 5.2 Re-set preserves booked/held/overbooking/min/max

Re-running `set_total_rooms` for a date that already has a row is a **read-merge**: `total_rooms` is overwritten with the new value, but `booked`/`held`/`overbooking_allowance`/`min_availability`/`max_availability` are read from the existing row and re-written unchanged (mirrors `set_on_hand` preserving `reserved`, `inventory.py:185-206`). This means an admin can raise/lower `total_rooms` without clobbering live holds (`held`) or confirmed reservations (`booked`). A row that does not yet exist is created with the defaults (`booked=0`, `held=0`, `overbooking_allowance=0`, `min_availability=0`, `max_availability` absent).

### 5.3 `_available` computation and the min-floor

`_available(item) = total_rooms + overbooking_allowance - booked - held`. With `total_rooms=10`, `overbooking_allowance=2`, `booked=3`, `held=1` → `available = 8`. The **sellable** count (used by HTL-011's hold condition and HTL-012's check) is `max(0, available - min_availability)`; HTL-010 surfaces only the raw `available` on `AvailabilityDayOut` and never persists it (no-drift, matches `inventory.py`). `available` may be **negative** if `booked + held` exceeds `total_rooms + overbooking_allowance` (e.g., a `total_rooms` reduction after rooms were already booked); the field is returned as-is (a negative value is a meaningful over-committed signal), not clamped at the model layer.

### 5.4 Never-seeded date reads as a zeroed virtual row

`get_availability` returns one row per span night; a night with no stored DynamoDB row is surfaced as `_zero_row(...)` with `available=0`. A never-seeded date therefore reads as **sold-out (0 available)**, not as a 404/error — the correct hotel semantic (an un-loaded calendar day has no inventory and is unbookable). `get_day` (single date) returns `None` for an absent date (caller decides; the span reader is the one that zero-fills).

### 5.5 Checkout-night exclusion (the span is `[checkin, checkout)`)

`get_availability(h, rt, "2026-07-04", "2026-07-07")` returns nights `2026-07-04`, `2026-07-05`, `2026-07-06` — **three nights**, departure date `2026-07-07` **excluded**. A guest checking out on the 7th does not occupy a room that night. This is why HTL-012's `check_availability` can report a stay bookable even when the checkout date itself is sold-out. A same-day `checkin == checkout` (zero nights) is rejected `422` (a stay must be ≥ 1 night).

### 5.6 Date validation and lexical ordering

Dates are validated `YYYY-MM-DD` at the Pydantic layer (regex + `date.fromisoformat`) and re-validated in `_date_range`/the service (`date.fromisoformat` rejects `2026-02-30`). Because ISO `YYYY-MM-DD` strings sort lexically in chronological order, the SK `DATE#{date}` `between(...)` query returns nights in date order with no client-side sort — the same "lexical==chronological" property that makes `GSI_HOTEL_DATE` (sort key `date` as `S`) date-ordered for free.

### 5.7 Decimal coercion

`total_rooms`, `booked`, `held`, `overbooking_allowance`, `min_availability`, `max_availability`, `updated_at` are stored `N` and returned by boto3 as `Decimal`. `_to_int(...)` (copy of `inventory.py:67-73`) coerces every numeric to plain `int` in `_row_out`; `AvailabilityDayOut` integer fields would coerce `Decimal` automatically, but the service does the explicit coercion so callers (and `_available`) always see `int`.

### 5.8 Composite PK collision safety

`availability_pk = "{hotel_id}#{room_type_id}"` uses `#` as the separator. If a `hotel_id` or `room_type_id` could itself contain `#`, two distinct `(hotel, room_type)` pairs could collide on one partition. HTL-005 ids are sha256-hex / uuid-hex (no `#`); HTL-010 documents the constraint and assumes `#`-free ids (see §10-Q4). The `DATE#` SK prefix is fixed and never user-supplied.

### 5.9 Empty / large ranges

A range whose `end_date < start_date` raises `422` (`_date_range`). A very large range (e.g., a 2-year seed = 730 rows) issues 730 `get_item` + `put_item` round-trips in the simple loop; this is acceptable for an admin seed action and matches the `inventory.set_on_hand` per-record write model. A `batch_writer` optimization (and a read-merge `BatchGetItem`) is a noted follow-up (§10-Q5) — not required for correctness.

### 5.10 Flag-off behavior

When `HOTEL_PMS_ENABLED=false` (default), **every** `hotel_availability.py` function raises `HTTPException(404, "Hotel PMS is not enabled")` via `_require_enabled()` **before** touching DynamoDB. The `hotel_availability` table may or may not exist — the flag check runs first. The HTL-012 router (not shipped here) delegates to `_require_enabled()` so its handlers 404 identically while remaining mounted (platform byte-for-byte unchanged).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_availability.py` contains **no** `if S.dev_mode` branch. The same DynamoDB code path runs in dev (boto3 intercepted by moto in-process) and prod (real DynamoDB) via the identical `T.hotel_availability` handle. This mirrors the contract at `app/services/inventory.py:27-29` (no `dev_mode` branch anywhere in that file) and the cross-cutting constraint at `docs/qloapps/AVAILABILITY_INVENTORY_TICKETS.md:65-67`.

### 7.2 Idempotency

`set_total_rooms` is **idempotent in result** on `(hotel_id, room_type_id, range, total_rooms)`: re-running with the same `total_rooms` produces the same final `total_rooms` per date and preserves `booked`/`held` (idempotent in data, not in `updated_at` — `updated_at` is re-stamped each call). It uses a `put_item` after a read-merge (no conditional put needed — the row is overwritten wholesale and the merge preserves the live counters). `get_day` / `get_availability` are pure reads (trivially idempotent). HTL-010 exposes **no** delete — a never-deleted calendar matches `inventory.py` (which also has no row delete).

### 7.3 Security — auth split (enforced by the HTL-012 router)

HTL-010 ships **no** router. When HTL-012 mounts `hotel_availability_router`, reads (`get_day`/`get_availability`/calendar/check) use `require_ui_session` (`app/services/sessions.py:330`) and **mutations** (`set_total_rooms`, holds, overbooking, min/max) use `require_admin_or_root_csrf` (`app/auth/policy.py:100`, requires `role ∈ {ADMIN, ROOT}` + cookie CSRF) — identical to `app/routers/inventory.py` (reads on `require_ui_session`, mutations on `require_admin_or_root_csrf`). The service layer does **not** itself enforce ownership/role (admin reads are unrestricted at the service layer, matching `inventory.get_inventory`); the router is the enforcement point.

### 7.4 Money-safety

HTL-010 does **not** touch any billing table, ledger entry, wallet, or payment primitive. `billing_shared` (`new_ledger_entry`, `settle_or_reverse_ledger`, `apply_balance_delta`) is not imported or called. Availability is a non-monetary inventory count; money paths become relevant only in the reservation/folio clusters (Tier-2/Tier-3, forward refs). There are no financial invariants to enforce here. Holds (HTL-011) are non-monetary room counters, not deposits.

### 7.5 Audit trail

Every mutation emits a best-effort audit event via the `_audit()` wrapper (copy of `inventory.py:92-98`): `hotel.availability.set_total` (one per `set_total_rooms` range). Audit failure (exception from `audit_event`) is swallowed and never propagates. HTL-011 adds `hotel.hold.created`/`hotel.hold.released`/`hotel.availability.set_overbooking`/`hotel.availability.set_minmax`.

## 10. Open Questions / Assumptions

1. **Room-type FK enforcement.** HTL-010 stores `room_type_id` as an opaque string and does **not** check it against the HTL-005 room-type table at the service layer (DynamoDB has no referential integrity; the cost of a per-call existence read is unwarranted for a seed action). **Assumption**: the router/UI passes valid HTL-005 `room_type_id`s; a seed against a non-existent room type silently creates orphan availability rows (harmless — they read as inventory for an id nothing references). A defensive `get_room_type(...)` existence check in the HTL-012 router is an optional additive extension.
2. **Persisted vs derived `available`.** HTL-010 keeps `available` purely derived (no stored column) to avoid drift, matching `inventory.py`. HTL-012's calendar projection may choose to persist `available` for a cheaper GSI read. **Assumption**: derived-only is correct for HTL-010; persistence (if any) is HTL-012's decision and must keep the recompute-on-mutation invariant.
3. **Negative `available`.** `_available` returns negative when over-committed (e.g., `total_rooms` lowered below `booked+held`). **Assumption**: surface the negative value unclamped (a meaningful over-commit signal); sell decisions clamp at `max(0, ...)` in HTL-011/012, not here.
4. **`#` separator in composite PK.** `availability_pk="{hotel_id}#{room_type_id}"` assumes neither id contains `#`. HTL-005 ids are hex (sha256/uuid). **Assumption**: ids are `#`-free; if a future id scheme allows `#`, switch to a length-prefixed or URL-encoded join.
5. **Bulk-write optimization.** `set_total_rooms` does a per-date `get_item`+`put_item` loop. For large ranges a `BatchGetItem` read-merge + `batch_writer` write would cut round-trips. **Assumption**: the simple loop is acceptable for an admin seed (matches `inventory.set_on_hand`'s per-record model); batching is a non-breaking follow-up.
6. **`hotel_hold_ttl_seconds` ownership.** Declared in HTL-010's settings block but consumed only by HTL-011. **Assumption**: declaring it now (single-owner settings group) is preferable to a later edit to the same block.
