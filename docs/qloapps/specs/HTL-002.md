# HTL-002 — Amenity/feature catalog — reusable dictionary + many-to-many attach

**Type:** Feature | **Priority:** P1 | **Estimate:** 1.5d
**Source:** `docs/qloapps/HOTELS_AMENITIES_TICKETS.md` §HTL-002 + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A row 4

---

## 1. Summary & Goal

HTL-002 lands the reusable **amenity/feature catalog** for the QloApps hotel-PMS vertical and the **many-to-many association** that attaches an amenity to **hotels** and (forward-compat) **room types**. It ships exactly three things on top of HTL-001's `hotels` table and `HOTEL_PMS_ENABLED` master flag:

1. A new global `hotel_amenities` DynamoDB table holding the shared amenity dictionary (one canonical "Free WiFi" row, not one per hotel), with a single `GSI_CATEGORY` GSI for category-grouped listing.
2. Five service functions appended to `app/services/hotel_pms.py` (the module HTL-001 creates): `create_amenity`, `list_amenities`, `attach_amenity(target_type, target_id, …)`, `detach_amenity`, `list_amenities_for` — plus an internal `_target_partition` resolver.
3. The Pydantic I/O models in `app/models.py`: `AmenityIn`, `AmenityOut`, `AmenityAttachIn`, `AmenityAssociationOut`.

The associations themselves are **child rows co-located on the target's partition** — an `AMEN#{amenity_id}` row written onto the `hotels` partition (HTL-001) for a hotel target, and onto the future room-types partition for a `room_type` target (zero schema change here). No new table is needed for the *associations*; only the dictionary gets its own table.

Gap analysis §A row 4 records this as **MISSING**: "Hotel features / amenities catalog (wifi/pool/parking attached to hotels+room types)" — "no amenities catalog; catalog `attributes` map is free-form; PRD-006 feature/feature-category is the generic (unimplemented) analogue" (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:72`).

With `HOTEL_PMS_ENABLED=false` (the default), every amenity service entrypoint raises HTTP 404 via the shared `_require_enabled()` before touching DynamoDB, and the platform is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Gap — no amenity catalog exists today

`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:72` records row 4 as **MISSING**: there is no amenity dictionary, no amenity-to-hotel link, and no amenity Pydantic models. The only adjacent structure is the generic catalog item's **free-form `attributes` map** (`catalog.py`, gap-analysis `:72`) — an untyped key/value bag with no shared taxonomy and no many-to-many attach. An amenity is a *facility dictionary entry* (`"Free WiFi"`, category `connectivity`) attachable to many hotels and room types — a different shape entirely.

### 2.2 PRD-006 is the unimplemented generic analogue — contrasted, not reused

`docs/ofbiz/specs/PRD-006.md` (the OFBiz `ProductFeature` / `ProductFeatureCategory` / `ProductFeatureAppl` triad) is the closest *generic* shadow, and the gap analysis explicitly names it as such (`:72`, `:124`). **HTL-002 contrasts it, it does not reuse it**, for three concrete reasons grounded in the PRD-006 spec:

- **PRD-006 is unimplemented.** PRD-006 §2.2 states plainly: *"`T.product_depth` and `S.product_depth_enabled`/`S.product_depth_features_enabled` do not yet exist in the live codebase (PRD-002 has not shipped)"* (`docs/ofbiz/specs/PRD-006.md` §2.2 verification note). There is no live `product_features.py` table or service to extend.
- **PRD-006 features are product-variant axes, not facility dictionaries.** PRD-006 features model selectable *variant* axes ("Color"→"Red", "Size"→"XL") with a signed `price_delta_cents` and `position` (`docs/ofbiz/specs/PRD-006.md` §1, items 1–2). An amenity carries no price delta and no ordered value-set; it is a flat dictionary entry with a category and an optional icon.
- **PRD-006's link is product→category; ours is amenity→(hotel | room_type).** PRD-006 attaches a *category* to a product via an `FTAPPL#{fc_id}` row on `T.product_depth` (`docs/ofbiz/specs/PRD-006.md` §1 item 4). HTL-002 attaches an *amenity* to a hotel or room type via an `AMEN#{amenity_id}` row on the *target's* partition — a true symmetric many-to-many across two target types.

We reuse the PRD-006/FAC co-located child-row *idiom* (`CHILD#{id}` rows on a parent partition), never the PRD-006 semantics or table.

## 3. Data Model

Two storage artefacts: (1) a small **global** `hotel_amenities` table for the shared dictionary, and (2) **association child rows** co-located on the *target's* partition (the existing `hotels` partition for hotel targets — no new table).

### 3.1 Storage decision (justified)

**Why a separate global table for the dictionary (not child rows on a hotel):** amenities are *shared across all hotels and room types* — "WiFi" is one canonical dictionary entry, not a per-hotel row. Co-locating the dictionary under a hotel would force duplication and make "rename the amenity globally" impossible (`docs/qloapps/HOTELS_AMENITIES_TICKETS.md:206–210`). The dictionary therefore lives in its own tiny table, global (not owner-scoped).

**Why the *associations* are child rows on the target partition (not rows in the amenity table):** the dominant read is "list amenities for *this* hotel/room type" (HTL-004 detail page renders amenity chips), which must be a single-partition query. An attach writes an `AMEN#{amenity_id}` child row onto the *target's* META partition — the exact FAC `LOC#{location_id}` / PROP `UNIT#{unit_id}` co-located child-row idiom (`docs/ofbiz/specs/FAC-001.md` §3; `docs/qloapps/HOTELS_AMENITIES_TICKETS.md:212–219`). For a hotel target this row lands on the existing `hotels` partition from HTL-001, so **no new attach table is needed for hotels**; room-type targets land on the future room-types partition (same code).

### 3.2 Table: `hotel_amenities` (the dictionary)

Single DynamoDB table. PK=`amenity_id`, SK=`META` — the dictionary entry. Global, **not** owner-scoped, since amenities are platform-shared.

**Primary key**

| Key | Type | Value |
|---|---|---|
| `amenity_id` | S (PK) | `sha256(f"amenity\|{name}".encode()).hexdigest()[:32]` — idempotent per name, dedupes "WiFi" across callers |
| `sk` | S (SK) | `"META"` (dictionary entry) |

**Header (dictionary) row attributes**

| Attribute | DDB Type | Constraints / Notes |
|---|---|---|
| `amenity_id` | S | PK; derived deterministically from `name` (see above) |
| `sk` | S | Always `"META"` for the dictionary entry |
| `name` | S | Display name, e.g. `"Free WiFi"`; non-empty |
| `category` | S | Literal: `connectivity` \| `wellness` \| `parking` \| `dining` \| `family` \| `accessibility` \| `general` |
| `icon` | S | Optional lucide icon name for the FE chip (empty string if unset — DynamoDB cannot store `None`) |
| `created_at` | N | `now_ts()` — integer Unix seconds (`app/core/time.py:2`) |

**GSI**

| Index name | PK | SK | Purpose |
|---|---|---|---|
| `GSI_CATEGORY` | `category` (S) | `created_at` (N) | List amenities grouped by category for the FE picker (HTL-004); a `Scan` is used only when listing *all* categories at once |

Projection: `ALL`.

**`attr_types`**: `{"created_at": "N"}` — mandatory per the CLAUDE.md DynamoDB numeric-GSI rule. Omitting it stores `created_at` as a String and any integer-keyed `GSI_CATEGORY` query throws `ValidationException` at runtime (`scripts/local-ddb-init.py:34` documents the override; CLAUDE.md "DynamoDB numeric GSI sort keys").

**TableDef** (to be appended in `scripts/local-ddb-init.py` inside `_table_defs()`, after the HTL-001 `hotels` entry, following the existing `inventory` TableDef style at `scripts/local-ddb-init.py:2456-2464` — note there is NO live `facilities` table in `local-ddb-init.py`; `facilities` is a docs-only FAC-001 concept):

```python
TableDef(
    _resolve_table_name(S.hotel_amenities_table_name, "hotel_amenities"),
    "amenity_id",
    "sk",
    gsi=[
        {"index_name": "GSI_CATEGORY", "partition_key": "category", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

### 3.3 Association child row (co-located on the target's partition)

Written onto the **target's** partition. PK is the *target's* PK attribute (e.g. `hotel_id` for a hotel target — the same partition as the target's HTL-001 `META` row). **No new table** for hotel targets.

| Attribute | DDB Type | Constraints / Notes |
|---|---|---|
| `<target_pk>` | S | The target's PK value (e.g. `hotel_id`); same partition as the target `META` row |
| `sk` | S | `AMEN#{amenity_id}` (co-located child row) |
| `amenity_id` | S | Convenience copy of the referenced dictionary id |
| `target_type` | S | Literal: `hotel` \| `room_type` (forward-compat) |
| `created_at` | N | `now_ts()` — integer Unix seconds |

> `list_amenities_for(target)` is a single-partition query `Key(target_pk).eq(target_id) & Key("sk").begins_with("AMEN#")` followed by a batched read of the referenced `hotel_amenities` `META` rows to hydrate name/category/icon — **never** a scan of the target partition's other children (`META`, future room-type rows, etc.) (`docs/qloapps/HOTELS_AMENITIES_TICKETS.md:249–252`).

### 3.4 Pydantic models (`app/models.py`)

All literals match the table above. `category` and `target_type` are constrained to their literal sets so an invalid value is rejected with a `422` by FastAPI before any service call.

**`_amenity_id` helper**

```python
def _amenity_id(name: str) -> str:
    import hashlib
    return hashlib.sha256(f"amenity|{name}".encode()).hexdigest()[:32]
```

**`create_amenity`**

```python
def create_amenity(*, name: str, category: str, icon: str | None = None, user_sub: str) -> dict:
```

- Calls `_require_enabled()`.
- Derives `amenity_id = _amenity_id(name)`.
- Builds the item: `{amenity_id, sk:"META", name, category, icon: icon or "", created_at: now_ts()}`.
- `T.hotel_amenities.put_item(Item=item, ConditionExpression="attribute_not_exists(amenity_id)")`. On `ConditionalCheckFailedException`, reads and returns the existing dictionary row (`get_item(Key={"amenity_id":amenity_id,"sk":"META"})`) — **idempotent on `name`**.
- `_audit("hotel.amenity.created", user_sub, amenity_id=amenity_id, name=name)`.
- Returns the item dict.

**`list_amenities`**

```python
def list_amenities(*, category: str | None = None) -> list[dict]:
```

- Calls `_require_enabled()`.
- If `category` given: `T.hotel_amenities.query(IndexName="GSI_CATEGORY", KeyConditionExpression=Key("category").eq(category))` — **GSI query, not a scan**.
- If `category` is `None`: list all dictionary entries (a `Scan` filtered to `sk == "META"`; acceptable — the dictionary is tiny and global).
- Returns the rows sorted by `name` ascending.

**`_target_partition` (internal resolver)**

```python
def _target_partition(target_type: str, target_id: str) -> tuple[Any, str, str]:
    if target_type == "hotel":
        return (T.hotels, "hotel_id", target_id)
    # room_type partition is resolved by the future Room Type cluster — until then:
    raise HTTPException(status_code=422, detail="unsupported target_type")
```

Returns `(table_handle, pk_attr_name, pk_value)`. `room_type` is accepted by the model surface (forward-compat) but raises `422` at the service layer until the Room Type cluster wires its partition — **no schema change required when it does**.

**`attach_amenity`**

```python
def attach_amenity(*, target_type: str, target_id: str, amenity_id: str, user_sub: str) -> dict:
```

- Calls `_require_enabled()`.
- Validates the amenity dictionary entry exists: `T.hotel_amenities.get_item(Key={"amenity_id":amenity_id,"sk":"META"})` → 404 if absent.
- Resolves `(table, pk_attr, pk_val) = _target_partition(target_type, target_id)` and validates the target exists: `table.get_item(Key={pk_attr: pk_val, "sk": "META"})` → 404 if absent.
- Writes the association child row onto the target partition: `{pk_attr: pk_val, "sk": f"AMEN#{amenity_id}", "amenity_id": amenity_id, "target_type": target_type, "created_at": now_ts()}` via `put_item(..., ConditionExpression="attribute_not_exists(sk)")`. On `ConditionalCheckFailedException` (already attached), return the existing child row — **idempotent re-attach**.
- `_audit("hotel.amenity.attached", user_sub, amenity_id=amenity_id, target_type=target_type, target_id=target_id)`.
- Returns the association row dict.

**`detach_amenity`**

```python
def detach_amenity(*, target_type: str, target_id: str, amenity_id: str, user_sub: str) -> bool:
```

- Calls `_require_enabled()`.
- Resolves the target partition, `delete_item(Key={pk_attr: pk_val, "sk": f"AMEN#{amenity_id}"})`.
- Returns `True` if a row was deleted, `False` for a missing association — **never raises** (mirrors the `host_inventory.delete_host` no-raise contract, CLAUDE.md). Implementation uses `ReturnValues="ALL_OLD"` and checks whether `Attributes` was returned.
- `_audit("hotel.amenity.detached", user_sub, amenity_id=amenity_id, target_type=target_type, target_id=target_id)`.

**`list_amenities_for`**

```python
def list_amenities_for(*, target_type: str, target_id: str) -> list[dict]:
```

- Calls `_require_enabled()`.
- Resolves the target partition; single-partition query `Key(pk_attr).eq(pk_val) & Key("sk").begins_with("AMEN#")`.
- Collects the referenced `amenity_id`s, batch-hydrates each from `hotel_amenities` `META` (`batch_get_item` keyed on `{amenity_id, sk:"META"}`), and returns `AmenityAssociationOut`-shaped dicts (hydrated `name`/`category`/`icon` + `target_type` + `created_at` from the association row).
- Never returns the target `META` row (the `begins_with("AMEN#")` prefix excludes it).

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent amenity creation (name collision)

`create_amenity` uses a conditional put (`attribute_not_exists(amenity_id)`) where `amenity_id` is `sha256("amenity|{name}")[:32]`. Two callers creating `"Free WiFi"` derive the same id; exactly one write wins, the loser catches `ConditionalCheckFailedException` and reads back the existing row. Both calls return the same `amenity_id` with no error. This is the FAC-001 facility-create contract applied to the dictionary (`docs/qloapps/HOTELS_AMENITIES_TICKETS.md:269–272`).

### 5.2 Name-based dedup is intentional and global

Because `amenity_id` derives from `name` only (not owner), the dictionary is naturally deduped platform-wide: "WiFi" is one row regardless of which admin creates it. Two amenities with *different* names but the same intent (e.g. `"WiFi"` and `"Free WiFi"`) are two distinct dictionary entries — name normalization (case/whitespace) is out of scope (see §10).

### 5.3 Idempotent re-attach

`attach_amenity` writes the `AMEN#{amenity_id}` child row with `attribute_not_exists(sk)`. Re-attaching the same amenity to the same target catches `ConditionalCheckFailedException` and returns the existing association row — **no duplicate child row, no error**. The association is keyed solely by `(target_pk, AMEN#{amenity_id})`, so it is naturally a set membership.

### 5.4 Attach validation: unknown amenity vs unknown target

`attach_amenity` performs two existence checks before writing: the amenity dictionary entry (404 `"amenity not found"` if absent) and the target `META` row (404 `"target not found"` if absent). This prevents dangling associations that reference a non-existent dictionary entry or a non-existent hotel. Both checks run after `_require_enabled()`.

### 5.5 Detach of a missing association does not raise

`detach_amenity` returns `False` (never raises) when no `AMEN#{amenity_id}` row exists on the target partition — mirroring the `host_inventory.delete_host` no-raise contract (CLAUDE.md). This makes detach idempotent: calling it twice (or on a never-attached amenity) is a safe no-op. The HTL-003 router can map a `False` return to a `200 {"detached": false}` body rather than a 404.

### 5.6 `list_amenities_for` never leaks non-amenity rows

The query uses `Key("sk").begins_with("AMEN#")`, so the target `META` row and any future room-type child rows on the same partition are excluded. Hydration is a batched read of `hotel_amenities` `META` rows — never a scan of the target partition's other children (`docs/qloapps/HOTELS_AMENITIES_TICKETS.md:249–252, 300–301`).

### 5.7 Stale association after dictionary entry change

Because the association row stores only `amenity_id` (a convenience copy) and hydrates name/category/icon at read time from the `hotel_amenities` `META`, a global rename of an amenity (a future `update_amenity`, out of scope here) automatically propagates to every hotel that has it attached — the rationale for the dictionary-in-its-own-table decision (§3.1). If a dictionary entry is ever hard-deleted (out of scope), `list_amenities_for` simply omits the unresolvable id from its hydrated output (a missing `batch_get_item` key is skipped, not an error).

### 5.8 `room_type` target — accepted, deferred at the service layer

`target_type="room_type"` is a valid `AmenityAttachIn`/`AmenityAssociationOut` literal (forward-compat), but `_target_partition` raises `422 "unsupported target_type"` until the Room Type cluster wires its partition. This is deliberate: the model/service *surface* is room-type-ready so the future cluster attaches amenities with zero schema change (`docs/qloapps/HOTELS_AMENITIES_TICKETS.md:28–30, 303–304`).

### 5.9 Decimal coercion

`created_at` is stored as DynamoDB `N` and returned by boto3 as `Decimal`. Service functions coerce with `int(item["created_at"])` before returning; `AmenityOut.created_at` / `AmenityAssociationOut.created_at` typed `int` coerce a `Decimal` automatically.

### 5.10 `icon` is optional but never `None` in DynamoDB

DynamoDB cannot store a `None` Map/scalar value. `create_amenity` writes `icon or ""`. On read, `AmenityOut.icon` maps an empty string to an empty string (the FE treats `""` as "no icon"); callers wanting `None` semantics may post-process. (`docs/open-property/specs/PROP-001.md` §5.2 documents the same `None`-not-storable constraint for Map fields.)

### 5.11 `list_amenities()` with no category does a Scan — by design

Listing all amenities across all categories is a `Scan` filtered to `sk == "META"`. This is acceptable because the dictionary is a *small global* table (a handful to low-hundreds of rows), unlike the per-hotel partitions which always use the GSI or a single-partition query. The category-filtered path always uses `GSI_CATEGORY` (a query, never a scan), satisfying the acceptance criterion (`docs/qloapps/HOTELS_AMENITIES_TICKETS.md:296`).

### 5.12 Flag-off behavior

With `HOTEL_PMS_ENABLED=false` (default), every amenity entrypoint calls HTL-001's `_require_enabled()` first, which raises `HTTPException(404, "hotel PMS not enabled")` before any DynamoDB access. The `hotel_amenities` table may or may not exist — the flag check runs before any table touch (`docs/qloapps/HOTELS_AMENITIES_TICKETS.md:305`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

The amenity additions to `app/services/hotel_pms.py` contain **no** `if S.dev_mode` branch. The same DynamoDB code path runs in dev (boto3 intercepted by moto in-process) and prod (real DynamoDB) against the same `T.hotel_amenities` / `T.hotels` handles. This mirrors the cross-cutting constraint (`docs/qloapps/HOTELS_AMENITIES_TICKETS.md:59–61`) and the `app/services/inventory.py` precedent (no `dev_mode` branch anywhere in that file; module docstring `app/services/inventory.py:27–28`).

### 7.2 Idempotency

- `create_amenity` is idempotent on `name` via conditional put + read-back-on-collision.
- `attach_amenity` is idempotent on `(target, amenity)` via `attribute_not_exists(sk)` + read-back.
- `detach_amenity` is idempotent: a missing association returns `False`, never raises.
- `list_amenities` / `list_amenities_for` are read-only and naturally idempotent.

### 7.3 Security — auth split + ownership

Reads (`list_amenities`, `list_amenities_for`) are gated by `require_ui_session` (`app/services/sessions.py:330`) at the HTL-003 router; mutations (`create_amenity`, `attach_amenity`, `detach_amenity`) require `require_admin_or_root_csrf` (`app/auth/policy.py:100–106`), which enforces `role ∈ {ADMIN, ROOT}` and cookie-based CSRF for non-bearer requests. The amenity *dictionary* is intentionally global (platform-shared, not owner-scoped) — any admin may create/list dictionary entries. The *target* existence check in `attach_amenity` ties an association to a real hotel; cross-tenant hotel-ownership enforcement (an admin attaching to a hotel they don't own) follows the same single-platform assumption as PROP-001 §7.3 / §10 and is a router-layer concern, not introduced here.

### 7.4 Money-safety

HTL-002 touches **no** billing table, ledger entry, or payment primitive. An amenity is a free-text facility dictionary entry with no price field (explicitly contrasted with PRD-006's `price_delta_cents`, §2.2). `billing_shared` (`new_ledger_entry`, `apply_balance_delta`, etc.) is not imported or called. There are no financial invariants to enforce.

### 7.5 Audit trail

Every amenity mutation emits a best-effort audit event via HTL-001's `_audit()` wrapper (copied from `app/services/inventory.py:92–98`): `hotel.amenity.created`, `hotel.amenity.attached`, `hotel.amenity.detached`. Audit failure is swallowed and never propagates to the caller.

## 8. Backward Compatibility & Migration

### 8.1 Additive-only changes

HTL-002 adds:
- One new settings key (`hotel_amenities_table_name`) to `app/core/settings.py` (additive).
- One new attribute (`hotel_amenities`) to the `Tables` dataclass + one new wire in `T = Tables(...)` (`app/core/tables.py`, additive).
- One new `TableDef` (`hotel_amenities`) in `scripts/local-ddb-init.py` (additive).
- Five service functions + one helper appended to `app/services/hotel_pms.py` (additive; HTL-001's module).
- Four Pydantic models to `app/models.py` (additive).

No existing file is modified in a breaking way. No existing endpoint, service function, DynamoDB table, or model is altered. The `hotels` table from HTL-001 gains a new *child-row prefix* (`AMEN#`) that did not exist before — additive within the partition; existing `META` rows are untouched.

### 8.2 Table creation in dev

`just restart` runs `scripts/local-ddb-init.py` → `_table_defs()` → creates all tables, including the new `hotel_amenities`. No manual migration step in dev.

### 8.3 Production deployment

In production, the `hotel_amenities` table must be created (`CreateTable`) before the new code is deployed. Because `HOTEL_PMS_ENABLED` defaults to `false`, the code can be deployed first (all amenity entrypoints return 404) and the flag enabled once the table is verified. No data migration is required — both the new table and the `AMEN#` child-row space start empty.

### 8.4 Rollback

Revert the five additive changes (settings, tables, local-ddb-init, hotel_pms.py amenity functions, models) and (in prod) drop the `hotel_amenities` table; orphaned `AMEN#` child rows on the `hotels` partition are harmless data that the reverted reader never queries. A partial rollback is safe: keep the code, set `HOTEL_PMS_ENABLED=false` — every amenity entrypoint 404s.

## 10. Open Questions / Assumptions

1. **Amenity name normalization / dedup.** `amenity_id` derives from the raw `name`, so `"WiFi"`, `"wifi"`, and `"  WiFi  "` produce three distinct dictionary entries. **Assumption**: no case/whitespace normalization at this layer — callers (the HTL-004 picker) supply canonical names. If product wants stricter dedup, normalize `name` (`strip().lower()`-keyed id) in `_amenity_id` — a non-breaking change to the derivation (but it would re-id existing rows, so do it before any data exists).
2. **`update_amenity` / `delete_amenity`.** Not in HTL-002 scope. A global rename/recategorize would be additive (`update_amenity` on the `META` row, auto-propagating via read-time hydration, §5.7). A hard delete must consider orphaned `AMEN#` associations (the reader already tolerates a missing dictionary entry, §5.7). **Assumption**: create/list/attach/detach are sufficient for the MVP.
3. **Category extensibility.** The seven-literal category set is hardcoded in the model. New categories require a model change (a non-breaking additive literal). **Assumption**: the seven literals cover the MVP amenity taxonomy.
4. **Hotel-ownership on attach.** `attach_amenity` validates the target *exists* but not that the calling admin *owns* it (single-platform assumption, same as PROP-001 §10). **Assumption**: single-operator deployment; cross-tenant isolation is a router-layer follow-up if needed.
5. **`detach` HTTP mapping.** `detach_amenity` returns `False` for a missing association. **Assumption**: the HTL-003 router maps `False` to `200 {"detached": false}` (idempotent), not `404` — consistent with the no-raise contract (§5.5).
6. **`room_type` partition resolver.** `_target_partition` raises `422` for `room_type` until the Room Type cluster ships. **Assumption**: the future cluster adds the `(T.room_types, "room_type_id", id)` branch with zero change to attach/detach/list-for logic.
