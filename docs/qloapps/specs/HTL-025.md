# HTL-025 — Public hotel / room-type browse API — published hotels only, no auth

**Type**: Feature | **Priority**: P1 | **Estimate**: 1.5d
**Source**: `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md` §HTL-025 + the "Cross-cutting constraints" header + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C row 4 ("Booking-engine storefront — PARTIAL", `:95`)

---

## 1. Summary & Goal

HTL-025 lands the **read-only, unauthenticated storefront "shop window"** of the QloApps booking-engine vertical: the first screen a guest sees before they pick dates. It is the foundational ticket of the public booking funnel cluster (HTL-025 browse → HTL-026 search/quote → HTL-027 cart/checkout → HTL-028 confirmation, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:16`). It ships exactly three things on top of HTL-001 (Hotel entity) and HTL-005 (Room Type entity):

1. **A new service module `app/services/hotel_storefront.py`** with two public, no-auth, read-only entrypoints — `public_get_hotel(hotel_id)` and `public_list_room_types(hotel_id)` — plus the `_flag_on()` / `_require_enabled()` 404 gate and the `_audit()` lazy-import wrapper, copied verbatim from `app/services/inventory.py:50-56,92-98`.
2. **Three output-only Pydantic models in `app/models.py`** — `PublicHotelOut`, `PublicRoomTypeOut`, `PublicRoomTypeListOut` — each a deliberately narrowed *storefront projection* that exposes only guest-safe fields and never leaks `owner_sub`, raw `status`, audit metadata, or any other internal attribute.
3. **No new DynamoDB table.** Both functions read the existing HTL-001 `hotels` `META` row and the HTL-005 `ROOMTYPE#{id}` child rows on the same `hotels` partition (`T.hotels`, wired by HTL-001). No new GSI, no schema change.

This ticket is the **structural twin** of the public calendar booking-link read path (`app/routers/calendar.py` `public_router`, `:88`; handlers `get_booking_link` / `list_booking_openings` take no auth dependency, `:1946-1974`): an unauthenticated read where **publication of the resource is the access gate, not a session**. The contrast is the field set — calendar models a *time slot*; HTL-025 models a *hotel + bookable nightly product* (star rating, occupancy, bed type, nightly rate). The structural shadow on the data side is the open-property storefront and the ECM availability-projection (`docs/ofbiz/specs/ECM-005.md` §1); the funnel shape is the QloApps public booking engine (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:95`).

With the master flag `HOTEL_PMS_ENABLED=false` (the default), both entrypoints raise HTTP **404** via `_require_enabled()` before touching DynamoDB and the platform is byte-for-byte unchanged. The router that exposes these functions over HTTP (`booking_engine_router`, `GET /booking-engine/hotels/{hotel_id}` + `.../room-types`, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:283-284`) is **HTL-027's** deliverable; HTL-025 ships the service + models that the router and HTL-026 `quote_stay` both consume.

## 2. Context & Current State

### 2.1 Gap — no hospitality storefront exists today

`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C row 4 (`:95`) records the booking-engine storefront as **PARTIAL**: "public booking-link reserve (`calendar.py:1946-2043`) + ECM storefront availability/checkout specs + real cart; **no date+occupancy room-type search funnel**." There is no public hotel-browse surface, no `hotel_storefront` service file, and no public hotel/room-type Pydantic projection. testlogon has **no hospitality storefront** (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:10`); the closest analogues are the calendar public booking-link reserve flow (`app/routers/calendar.py:1946-2043`) and the ECM storefront availability-projection (`docs/ofbiz/specs/ECM-005.md` §1).

### 2.2 The data — HTL-001 hotels + HTL-005 room types already exist (hard deps)

HTL-025 reads, never writes. It depends entirely on two upstream tickets being merged:

- **HTL-001** (`docs/qloapps/specs/HTL-001.md`) created the `hotels` table (PK=`hotel_id`, SK=`META` for the hotel header), the `S.hotel_pms_enabled` / `S.hotels_table_name` settings, the `T.hotels` handle (`app/core/tables.py`), and the hotel `META` row carrying `owner_sub`, `name`, `description`, `star_rating`, `address`, `check_in_time`, `check_out_time`, `policies`, `contact`, `photo_urls`, `status` (`active` | `archived`, default `active`), `created_at`, `updated_at` (HTL-001 §3.1, `:100-118`).
- **HTL-005** (`docs/qloapps/specs/HTL-005.md`) added `ROOMTYPE#{room_type_id}` child rows on the **same** `hotels` partition (PK=`hotel_id`, SK=`ROOMTYPE#{id}`, HTL-005 §3.1, `:103-126`), the `GSI_HOTEL_ROOMTYPES` index (PK=`hotel_id`, SK=`created_at` numeric, HTL-005 §3.2), and the `list_room_types` read pattern (`begins_with(sk, "ROOMTYPE#")` on the hotel partition, or the ordered GSI fast path, HTL-005 §4.1.3, `:282-310`). Each room-type row carries `name`, `description`, `base_occupancy_adults`, `base_occupancy_children`, `max_occupancy`, `bed_type`, `size_sqft`, `base_nightly_rate_cents`, `photo_urls`, `status`, `created_at`, `updated_at`.

HTL-025 **reuses these read access patterns**; it adds no table, no GSI, no settings key, no schema change.

### 2.3 Publication is the access gate, not a session

The cross-cutting constraint (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:33-40`) states the browse endpoints are unauthenticated and mirror `app/routers/calendar.py` `public_router` (no auth dependency): **only published hotels are readable; publication is the access gate, not a session.** The structural precedent is `_load_booking_link` (`app/routers/calendar.py:289-298`) — the public booking-link read where the *existence/visibility of the link* is the entire access control: an unauthenticated caller may read a booking link, but only because the link itself was published. HTL-025 applies the same principle: an unauthenticated caller may read a hotel, but only a **published** one.

> **Publication ↔ HTL-001 `status` reconciliation.** The HTL-025 ticket text references both `status == "published"` and `published == True` (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:99-103`). HTL-001's hotel `META` row, however, carries a `status` of `active` | `archived` (HTL-001 §3.1, `:116`; §5.6, `:394-396`) — there is **no** `published` field today. HTL-025 reconciles this with a single `_is_published(item)` predicate (§3.4) that treats a hotel as publicly visible when it is **not archived and not draft** — concretely `status == "active"` (the HTL-001 published-equivalent state) **OR** `published is True` if a future ticket adds an explicit `published` flag. `archived` and any `draft` state are **never** publicly exposed. The predicate is defined once so a later "publish/unpublish" lifecycle ticket can extend it without touching the two entrypoints. This single point of reconciliation is flagged in §10 as the design assumption.

## 3. Data Model

HTL-025 adds **no DynamoDB table, no GSI, no attribute, no settings key**. It reads the existing HTL-001 / HTL-005 rows and projects a guest-safe subset. The only net-new artefacts are three output-only Pydantic models.

### 3.1 Read access patterns (existing rows, no schema change)

| Read | Key / Index | Source ticket |
|---|---|---|
| Hotel header | `get_item(Key={"hotel_id": hid, "sk": "META"})` — strongly-consistent point read | HTL-001 §3.1 (`:97-99`) |
| Room types for a hotel | `query(Key={"hotel_id": hid} + begins_with(sk, "ROOMTYPE#"))` on the base partition (co-reads nothing extra beyond the partition), or the `GSI_HOTEL_ROOMTYPES` ordered fast path | HTL-005 §4.1.3 (`:282-310`), §3.2 |

`public_list_room_types` uses the **base-partition `begins_with(sk, "ROOMTYPE#")` query** (HTL-005 §3.1 note, `:153-155`) rather than the GSI, because: (a) the storefront returns *all* published room types for a single hotel (no pagination required at the shop-window scale of tens of types per hotel), and (b) the base query never surfaces the `META` row when filtered by `begins_with("ROOMTYPE#")`, avoiding the `META`-in-GSI filtering HTL-005 §5.2 has to do. (If a future high-cardinality hotel needs paging, switch to the `GSI_HOTEL_ROOMTYPES` ordered path + cursor — additive, §10.)

### 3.2 `PublicHotelOut` — storefront-safe hotel projection (`app/models.py`)

Exposes only the guest-facing fields. **Never** includes `owner_sub`, raw `status`, `created_at`, `updated_at`, or any future internal admin attribute.

```python
class PublicHotelOut(BaseModel):
    hotel_id: str
    name: str
    description: str = ""
    star_rating: int
    check_in_time: str
    check_out_time: str
    address: Address                      # reuses the HTL-001 Address model
    amenities: List[str] = []             # HTL-002 amenity labels attached to the hotel
    photos: List[str] = []                # maps from the HTL-001 `photo_urls` field
    policies: HotelPolicies               # reuses the HTL-001 HotelPolicies model
    contact: HotelContact                 # reuses the HTL-001 HotelContact model
```

Notes:
- `Address`, `HotelPolicies`, `HotelContact` are reused from HTL-001 (`docs/qloapps/specs/HTL-001.md` §3.2, `:150-179`) — `PublicHotelOut` does **not** redefine them.
- `photos` projects the stored `photo_urls` field (renamed at the projection boundary to the storefront vocabulary the ticket uses, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:104`).
- `amenities` is a list of human-readable amenity labels resolved via HTL-002 `list_amenities_for("hotel", hotel_id)` (`docs/qloapps/specs/HTL-002.md` §1; the `AMEN#{amenity_id}` child rows on the `hotels` partition). When HTL-002 is not yet merged the projection emits `[]` (best-effort; see §5.6).

### 3.3 `PublicRoomTypeOut` / `PublicRoomTypeListOut` — storefront-safe room-type projection

```python
class PublicRoomTypeOut(BaseModel):
    room_type_id: str
    name: str
    description: str = ""
    occupancy_adults: int                 # maps from base_occupancy_adults
    occupancy_children: int               # maps from base_occupancy_children
    max_occupancy: int
    bed_type: str
    size_sqft: int
    amenities: List[str] = []             # HTL-002 amenity labels attached to the room type
    photos: List[str] = []                # maps from the HTL-005 photo_urls field
    base_rate_cents: int                  # maps from base_nightly_rate_cents
    currency: str = "usd"

class PublicRoomTypeListOut(BaseModel):
    room_types: List[PublicRoomTypeOut]
    count: int
```

Notes:
- `occupancy_adults` / `occupancy_children` project HTL-005's `base_occupancy_adults` / `base_occupancy_children`; `base_rate_cents` projects `base_nightly_rate_cents` (the integer cents money field, HTL-005 §3.1, `:122`). The storefront vocabulary matches the ticket (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:108-110`).
- `PublicRoomTypeListOut` uses the `{items, count}` shape (here `{room_types, count}`) — the CLAUDE.md `host_inventory.list_hosts` convention referenced by the ticket (`:111-113`). No `cursor` field at the shop-window scale (all published room types are returned; §3.1).
- `currency` defaults `"usd"`. If HTL-005 room-type rows do not persist a currency (HTL-005 §3.1 has no currency attribute — it carries cents only), the projection defaults to `S`-configurable platform currency or `"usd"`; the value is informational at this layer (no money is moved). Flagged in §10.
- **No raw `status`, no `created_at`/`updated_at`, no `hotel_id` echo on each room type** (the hotel id is already the request context).

### 3.4 `_is_published(item)` predicate (single reconciliation point)

```python
def _is_published(item: dict | None) -> bool:
    if not item:
        return False
    status = (item.get("status") or "").lower()
    if status in ("archived", "draft"):
        return False
    if item.get("published") is False:        # explicit unpublish, if a future ticket adds it
        return False
    return status == "active" or item.get("published") is True
```

Defined **once** in `hotel_storefront.py`. Both entrypoints call it; a future publish/unpublish lifecycle ticket extends only this function. `archived` (HTL-001 §5.6) and any `draft` state are never publicly visible.

#### 4.1.1 `public_get_hotel`

```python
def public_get_hotel(hotel_id: str) -> dict:
```

**Behavior**:
1. `_require_enabled()` (first statement — 404 when the flag is off, before any DDB read).
2. `item = T.hotels.get_item(Key={"hotel_id": hotel_id, "sk": "META"}).get("Item")` — strongly-consistent point read of the HTL-001 hotel header.
3. If `item is None` **or** `not _is_published(item)` → `raise HTTPException(status_code=404, detail="Hotel not found")`. **A non-existent, archived, or draft hotel is indistinguishable to the caller** — both yield the same 404, leaking nothing about an unpublished hotel's existence (§7.3).
4. Resolve attached amenity labels best-effort: `amenities = _amenities_for("hotel", hotel_id)` (§5.6) — `[]` on any error or if HTL-002 is absent.
5. Build the **storefront-safe projection** — copy ONLY the allow-listed fields (`hotel_id`, `name`, `description`, `star_rating`, `check_in_time`, `check_out_time`, `address`, `policies`, `contact`, `photos ← photo_urls`, `amenities`), coercing `star_rating` via `_to_int`. The projection is constructed field-by-field from an **allow-list**, never `**item` — so a newly added internal attribute can never accidentally leak (§7.3, §5.5).
6. Best-effort `_audit("hotel.storefront.viewed", "anon", hotel_id=hotel_id)` — low-cardinality, no PII, swallowed on failure.
7. Return the projected `dict` (the router wraps it in `PublicHotelOut`).

Takes **no `user_sub`** — it is a public read.

#### 4.1.2 `public_list_room_types`

```python
def public_list_room_types(hotel_id: str) -> dict:
```

**Behavior**:
1. `_require_enabled()`.
2. Verify the parent hotel is published: call `public_get_hotel(hotel_id)` (reuses the 404 gate) — if the hotel is missing/archived/draft this raises 404 **before** any room-type read, so room types of an unpublished hotel are never enumerable (§5.1).
3. Query the room-type child rows on the hotel partition:
   ```python
   resp = T.hotels.query(
       KeyConditionExpression=Key("hotel_id").eq(hotel_id) & Key("sk").begins_with("ROOMTYPE#"),
   )
   rows = resp.get("Items", [])
   ```
   (paginate via `LastEvaluatedKey` if a hotel ever exceeds one page — bounded by the per-hotel room-type count, §3.1.)
4. Filter to **published/bookable** room types only: keep rows where `_is_published(row)` — i.e. drop `status == "archived"` (and any `draft`). Unpublished/archived room types never appear (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:112-113`).
5. Project each surviving row to the **allow-listed** `PublicRoomTypeOut` shape (field-by-field, never `**row`), coercing numerics via `_to_int`, mapping `base_occupancy_adults → occupancy_adults`, `base_occupancy_children → occupancy_children`, `base_nightly_rate_cents → base_rate_cents`, `photo_urls → photos`, resolving per-room-type `amenities` best-effort.
6. Sort by `name` (stable, display-friendly; the storefront has no chronological semantics) — or by ascending `base_rate_cents` if product prefers price-ordered results (§10).
7. Return `{"room_types": [...], "count": len(projected)}` (the `PublicRoomTypeListOut` shape, §3.3). No `cursor`.

Both functions are **read-only**, take no `user_sub`, and call `_require_enabled()` first.

### 4.2 Router endpoints (HTL-027's deliverable — previewed for contract)

HTL-025 ships only the service. The public `booking_engine_router` (declared in HTL-027, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:283-284`) exposes:

| Method | Path | Auth | Service call | Response model |
|---|---|---|---|---|
| GET | `/booking-engine/hotels/{hotel_id}` | none (public) | `public_get_hotel(hotel_id)` | `PublicHotelOut` |
| GET | `/booking-engine/hotels/{hotel_id}/room-types` | none (public) | `public_list_room_types(hotel_id)` | `PublicRoomTypeListOut` |

No auth dependency on either handler — exactly like `get_booking_link` (`app/routers/calendar.py:1946-1957`). **FastAPI literal-before-dynamic ordering** (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:62-66`): HTL-027 declares the literal `/booking-engine/search` (HTL-026) and `/booking-engine/cart` routes **before** any `/booking-engine/hotels/{hotel_id}` dynamic route, mirroring the KYC `/templates`-before-`/{case_id}` and audit-export `/schedules`-before-`/{export_id}` gotcha (CLAUDE.md). The router maps the service's `HTTPException(404)` straight through.

## 5. Detailed Behavior & Edge Cases

### 5.1 Unpublished hotel → room types are not enumerable

`public_list_room_types` calls `public_get_hotel` first (step 4.1.2 §2), which 404s for a missing/archived/draft hotel **before** any room-type query runs. An attacker cannot enumerate the room inventory (and thus the nightly rates) of a hotel that has not been published. This is the storefront analogue of the booking-link gate: no link → no openings.

### 5.2 Published hotel with zero published room types

Returns `{"room_types": [], "count": 0}` — not an error. A hotel may be published (visible in the shop window) before any room type is published; the storefront shows the hotel with an empty room list.

### 5.3 Archived/draft room type under a published hotel

Filtered out by `_is_published(row)` in step 4 of `public_list_room_types`. The hotel is visible but the archived room type is invisible — it does not contribute to `count` and never appears in `room_types`. `get_room_type` (HTL-005) would still return it to an authenticated admin; the storefront simply never surfaces it.

### 5.4 Decimal coercion

`star_rating`, `base_nightly_rate_cents → base_rate_cents`, `occupancy_adults`, `occupancy_children`, `max_occupancy`, `size_sqft` are stored as DynamoDB `N` and returned as `Decimal`. Every projection coerces them to plain `int` via `_to_int` before building the `dict`, so the `Public*Out` models validate and JSON-serialize as integers (not `Decimal` strings). Money stays integer cents — there is no float field anywhere.

### 5.5 Allow-list projection — `**item` is forbidden

Both projections are built field-by-field from a fixed allow-list. The service **never** does `PublicHotelOut(**item)` or `{**item, ...}` — a stored `META` row carries `owner_sub`, raw `status`, `created_at`, `updated_at`, and may later gain internal-only attributes; copying the whole item would leak them. The allow-list is the single enforcement point, and the §9 no-leak test asserts forbidden keys are absent from the output.

### 5.6 Amenity resolution is best-effort and HTL-002-optional

`_amenities_for(target_type, target_id)` lazily imports HTL-002's `list_amenities_for` (`docs/qloapps/specs/HTL-002.md` §1) inside a `try/except`, mapping the association rows to human-readable labels. If HTL-002 is not yet merged, the import fails and the helper returns `[]`. Amenity resolution **never** fails a browse read — a missing amenity catalog yields an empty `amenities` list, not a 500. (HTL-002 is listed as a dependency, §11, but the browse path degrades gracefully without it.)

### 5.7 Flag-off behavior

With `HOTEL_PMS_ENABLED=false` (default), both entrypoints raise `HTTPException(404, "Hotel PMS is not enabled")` as their first statement, before any DDB access. The `hotels` table may or may not exist — the flag check runs first, so a flag-off platform never reads it. The router (HTL-027) maps this to a 404, so an unauthenticated probe against a disabled vertical learns only "not found."

### 5.8 No write, no mutation, no PII

Neither function writes to DynamoDB, mutates session state, or returns guest PII (the storefront has no guests yet — that is HTL-027 checkout). The only side effect is the best-effort low-cardinality `hotel.storefront.viewed` audit (no `user_sub`, no IP, no PII — just `hotel_id`). Rate-limiting of the public read is HTL-026/HTL-027's concern (the search endpoint fans out to the engine); the simple point/partition reads here are cheap, but HTL-027 may add a per-client rate-limit at the router edge (reusing `app/services/rate_limit.py` `_bucket_limit`, §10).

### 5.9 Non-existent hotel id

`public_get_hotel("does-not-exist")` → `get_item` returns no `Item` → `_is_published(None)` is `False` → `HTTPException(404, "Hotel not found")`. Identical 404 to the archived/draft case (§5.3) — no existence oracle.

### 5.10 Currency on room types

If HTL-005 room-type rows do not persist a `currency` attribute (they store cents only, HTL-005 §3.1), `PublicRoomTypeOut.currency` defaults to the platform currency (or `"usd"`). ## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_storefront.py` must contain **no** `if S.dev_mode` branch. The identical `T.hotels.*` code path runs in dev (boto3 intercepted by moto in-process) and prod (real DynamoDB). This matches the cross-cutting constraint (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:58-61`: "Zero `if S.dev_mode` branches in business logic; the same `T.*` handles in both environments") and the precedent `app/services/inventory.py` (no `dev_mode` branch). The `T.hotels` handle is identical in both environments — only the boto3 endpoint differs (moto vs real DDB), resolved transparently by `_safe_table` (`app/core/tables.py`). Acceptance: `grep "dev_mode" app/services/hotel_storefront.py` returns nothing.

### 7.2 Idempotency

Both functions are **read-only** and therefore trivially idempotent — repeated calls with the same `hotel_id` return the same projection (the underlying rows do not change as a result of the read). There is no write, no conditional put, no ledger entry. The only side effect is the best-effort audit, which is not a state mutation.

### 7.3 Security — no leak of internal fields, no existence oracle

- **No internal-field leak.** Both projections are built from a fixed **allow-list** (§5.5), never `**item`. `owner_sub`, raw `status`, `created_at`, `updated_at`, audit metadata, and any future internal attribute are structurally excluded. The §9 no-leak test asserts the forbidden keys are absent from the serialized output — this is the ticket's headline security invariant ("must not leak owner_sub or internal fields"; acceptance "Neither function exposes internal fields", `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:128`).
- **No existence oracle.** A missing, archived, or draft hotel all yield the same `404 Hotel not found` (§5.3, §5.9). An unauthenticated caller cannot distinguish "no such hotel" from "exists but unpublished" — so an unpublished hotel's existence (and its rates) leak nothing.
- **Publication is the only gate.** No session, no Bearer token, no CSRF (these are read GETs). Access control is entirely "is the resource published" — the calendar booking-link model (`app/routers/calendar.py:289-298`).
- **Flag-off is 404, not 401/403** (§5.7) — a disabled vertical leaks nothing.
- **No PII.** The storefront returns hotel/room metadata only; no guest data exists at this funnel step. The audit event carries no `user_sub`/IP/PII.

### 7.4 Money-safety — no ledger interaction

HTL-025 does **not** touch any billing table, ledger entry, or payment primitive. It does not import or call `billing_shared.new_ledger_entry`, `settle_or_reverse_ledger`, `apply_balance_delta`, or `compute_due`; it does not access `T.billing`; it invokes no Stripe/PayPal/CCBill SDK. `base_rate_cents` is surfaced as an **informational** integer-cents value only — the cross-cutting "checkout reuses the cart→order→payment money path" constraint (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:46-53`) applies to HTL-027 checkout, not to this read-only browse layer. All money values stay integer cents; there is no float field. There are no financial invariants to enforce here.

| Event | When | Fields |
|---|---|---|
| `hotel.storefront.viewed` | `public_get_hotel` success | `hotel_id` only (low-cardinality, no PII, no `user_sub`) |

Emitted best-effort via the `_audit()` wrapper (copied from `inventory.py:92-98`); an `audit_event` exception is swallowed and never fails the read. `public_list_room_types` does not separately audit (the parent `public_get_hotel` call already records the view).

Rolling back HTL-025 means reverting the two file changes (`hotel_storefront.py`, the three models in `models.py`). Because the flag defaults `false` and nothing else references the new service until HTL-027/HTL-026 land, a partial rollback is also safe: keep the code deployed with `HOTEL_PMS_ENABLED=false` — both entrypoints 404 and no data is read. ## 10. Open Questions / Assumptions

1. **`published` vs `status` reconciliation.** HTL-001 carries `status` (`active` | `archived`), not a `published` flag (§2.3). **Assumption**: a hotel/room type is publicly visible iff `_is_published(item)` is true — concretely `status == "active"` (HTL-001's published-equivalent) or an explicit `published is True` if a future "publish/unpublish" ticket adds the field. `archived` and `draft` are never exposed. The predicate is the single reconciliation point; a lifecycle ticket extends only `_is_published` (§3.4).
2. **No-leak is enforced by allow-list, never `**item`.** **Assumption**: the projection copies a fixed allow-list field-by-field; the §9 no-leak tests are the enforcement guard. A reviewer must reject any future `PublicHotelOut(**item)` shortcut.
3. **Amenity catalog (HTL-002) may not be merged when HTL-025 lands.** **Assumption**: `amenities` resolution is best-effort and degrades to `[]` when HTL-002 is absent (§5.6); the browse read never depends on the amenity catalog being present.
4. **Room-type `currency`.** HTL-005 stores cents only (no currency attribute). **Assumption**: `PublicRoomTypeOut.currency` defaults to the platform currency / `"usd"`; the authoritative charge currency is resolved at HTL-027 checkout. If a per-hotel currency is required, add it to HTL-001/HTL-005 and project it through (additive).
5. **No pagination at the shop-window scale.** **Assumption**: `public_list_room_types` returns *all* published room types for a hotel (tens at MVP scale, §3.1). If a hotel ever exceeds one DDB page, switch to the `GSI_HOTEL_ROOMTYPES` ordered path + cursor — additive, no contract change beyond adding a `cursor` field.
6. **Result ordering.** **Assumption**: room types are sorted by `name` for a stable display order. If product prefers price-ordered ("cheapest first") browse results, sort by ascending `base_rate_cents` — a one-line change with no schema impact.
7. **Rate-limiting the public browse read.** **Assumption**: the cheap point/partition reads here need no rate-limit; the fan-out `quote_stay` search (HTL-026) and checkout (HTL-027) own per-client rate-limiting via `app/services/rate_limit.py` `_bucket_limit`. If browse abuse is observed, HTL-027 can add a router-edge bucket keyed on `request.client.host` without changing the service.
8. **Audit cardinality.** **Assumption**: `hotel.storefront.viewed` carries only `hotel_id` (low-cardinality, no PII, no `user_sub`/IP). If per-view analytics are wanted, that belongs in a dedicated metrics pipeline, not the audit log.
