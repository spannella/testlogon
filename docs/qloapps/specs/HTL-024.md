# HTL-024 — Router `/ui/hotels/{hotel_id}/front-desk` + FrontDeskPage FE + tests

**Type**: Feature | **Priority**: P1 | **Estimate**: 3d
**Source**: `docs/qloapps/FRONT_DESK_TICKETS.md` §HTL-024 + "Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C row "Front desk (arrivals/departures/in-house, walk-in, assign room, check-in/out, room-move)"

---

## 1. Summary & Goal

HTL-024 is the **delivery ticket** for the front-desk vertical: it exposes the HTL-022
(query) and HTL-023 (action) service layer over HTTP through a new
`hotel_front_desk_router`, registers it in `app/main.py`, and ships the React/TypeScript
**FrontDeskPage** console plus the full test suite (hermetic pytest + Playwright E2E) that
validates the whole HTL-022..HTL-024 stack end-to-end.

The router is modeled **exactly** on `app/routers/inventory.py` — the same single-`APIRouter`
declaration, the same module-level `_require_enabled()` short-circuit delegating to the
service (`app/routers/inventory.py:31-33`), and the same auth split (reads on
`require_ui_session` / `app/services/sessions.py:330`; mutations on
`require_admin_or_root_csrf` / `app/auth/policy.py:100`). Eight endpoints are delivered under
the static `/ui/hotels/{hotel_id}/front-desk/...` path tree:

1. `GET .../front-desk/arrivals` — today's arriving (`confirmed`) reservations (HTL-022
   `arrivals_today`).
2. `GET .../front-desk/departures` — today's departing (`checked_in`) reservations (HTL-022
   `departures_today`).
3. `GET .../front-desk/in-house` — every currently `checked_in` reservation (HTL-022
   `in_house`).
4. `GET .../front-desk/occupancy` — the live occupancy snapshot (HTL-022
   `occupancy_snapshot`).
5. `POST .../front-desk/walk-in` — walk-in create+check-in (HTL-023 `walk_in_booking`).
6. `POST .../front-desk/reservations/{reservation_id}/assign-room` — set physical room(s)
   (HTL-023 `assign_room`).
7. `POST .../front-desk/reservations/{reservation_id}/change-room` — swap the assignment set
   (HTL-023 `change_room`).
8. `POST .../front-desk/reservations/{reservation_id}/room-move` — relocate a checked-in
   guest (HTL-023 `room_move`).

Every handler calls `_require_enabled()` as its first statement; with the master flag
`HOTEL_PMS_ENABLED` off (the default) every endpoint returns **404** and the platform is
byte-for-byte unchanged. The router is **always mounted** (just as `inventory_router` is at
`app/main.py:877`) — the flag check lives in the handler, not the registration.

The frontend deliverable is `frontend/src/pages/hotels/FrontDeskPage.tsx`: a console with
**arrivals / departures / in-house tabs built on the ticket-board pattern** (each tab is a
status-bucketed column of reservation cards — a re-skin of the
`frontend/src/pages/tickets/TicketKanbanBoard.tsx` column layout and the backend
`default_board_columns` shape at `app/services/tickets.py:60-70`), an occupancy-snapshot
summary strip at the top, a walk-in dialog (React Hook Form + Zod), and per-reservation-card
assign-room / change-room / room-move actions. Plus TypeScript types, an API-endpoint
wrapper, a lazy route in `frontend/src/App.tsx`, and a "Front Desk" sidebar nav item in
`frontend/src/components/layout/Sidebar.tsx`.

Gap analysis row (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:94`): "Front desk
(arrivals/departures/in-house, walk-in, assign room, check-in/out, room-move) — **MISSING** …
no front-desk console; calendar admin views + PROP occupancy roll-up are adjacent, no
room-assignment/check-in actions." HTL-024 lands the HTTP + UI surface that closes it.

**HTL-024 introduces no new DynamoDB table, no new GSI, and no new DynamoDB attribute** — it
is a thin HTTP + UI façade over an already-complete service layer (HTL-022/023), itself a
query/action layer over the HTL-018 `hotel_reservations` and HTL-006 `hotel_rooms` tables.
There is no `if S.dev_mode` branch anywhere (SECOPS-007).

### 2.1 The service layer is complete after HTL-022/023 (this ticket's hard prerequisites)

HTL-024 assumes both predecessor tickets in the front-desk cluster have merged into

  HTL-007 `set_room_housekeeping_status` collaborators, and emit `hotel.frontdesk.*` audit

HTL-024 adds **no service logic** — it only delegates. It defines `_require_enabled()` in the
router as a one-line delegation to `hotel_front_desk._require_enabled()`, exactly as
`app/routers/inventory.py:31-33` delegates to `inv._require_enabled()`.

### 2.4 Auth dependencies

- **`require_ui_session`** (`app/services/sessions.py:330`) — FastAPI `Depends`; validates a
  cookie-based UI session or a Bearer JWT and returns a `dict` with `user_sub`, `role`, etc.
  Used for the four GET reads. Read handlers pull `session["user_sub"]` (the
  `inventory_router` reads do not need it for inventory lookups, but the front-desk reads do
  not either — the partition key is `hotel_id` from the path; `session` is consumed purely
  for authentication).
- **`require_admin_or_root_csrf`** (`app/auth/policy.py:100-106`) — async FastAPI dependency;
  runs `enforce_cookie_csrf(request)` then `require_roles(user, {Role.ADMIN, Role.ROOT})`,
  raising **403** on missing/mismatched CSRF, on missing role, or on a non-admin role. Used
  for all four POST mutations.
- **`AuthenticatedUser`** dataclass (`app/auth/deps.py:126-128`) — the return type of
  `require_admin_or_root_csrf`; carries `.sub` (the `user_sub` passed to the service),
  `.role`, `.admin_profile`.

This is the **identical** split `app/routers/inventory.py` uses (storefront reads on the
session dep, admin mutations on the CSRF dep) — required by the cross-cutting constraints
(`docs/qloapps/FRONT_DESK_TICKETS.md:52-58`).

### 2.5 Route-ordering constraint (FastAPI path-param capture)

FastAPI matches routes in **declaration order**. If the dynamic
`/{hotel_id}/front-desk/reservations/{reservation_id}/...` routes were declared before the
literal sub-routes, FastAPI would still route correctly here because the differentiating
segment (`arrivals` vs `reservations`) sits one level below `front-desk` — but the ticket and
the cross-cutting "literal-before-dynamic" convention require the literal routes
(`arrivals`, `departures`, `in-house`, `occupancy`, `walk-in`) to be declared **before** the
`/reservations/{reservation_id}/...` group regardless, to keep the file legible and immune to
any future refactor that collapses a segment. This is the same class of bug CLAUDE.md
documents for KYC (`/templates` before `/{case_id}`), audit-export (`/schedules` before
`/{export_id}`), open-property PROP-004 (`/portfolio/occupancy` before `/{property_id}`,
`docs/open-property/specs/PROP-004.md` §2.4), and HTL-012 (`/availability/calendar` before
`/availability/{room_type_id}`). Because this router shares the `/ui/hotels` prefix with the
HTL-012 `hotel_availability_router`, the static `/front-desk/` segment keeps the two route
trees disjoint (`docs/qloapps/FRONT_DESK_TICKETS.md:354-356`).

| Endpoint | Query params |
|---|---|

### 4.1 Router file: `app/routers/hotel_front_desk.py` (new)

```python
"""Hotel front-desk router (QloApps hotel vertical, HTL-024).

Additive + flag-gated (``HOTEL_PMS_ENABLED``, default OFF). Every handler
calls ``_require_enabled()`` first; when the flag is off all endpoints return
404 and the platform is byte-for-byte unchanged (mirrors
app/routers/inventory.py:31-33).

Auth split (mirrors app/routers/inventory.py:37,48,65,81):
  * Read endpoints  → ``require_ui_session``        (any authenticated user)
  * Write endpoints → ``require_admin_or_root_csrf`` (ADMIN | ROOT + CSRF)
"""
from __future__ import annotations

from typing import Optional

from fastapi import APIRouter, Depends

from app.auth.deps import AuthenticatedUser
from app.auth.policy import require_admin_or_root_csrf
from app.models import (
    AssignRoomIn,
    FrontDeskActionOut,
    FrontDeskListOut,
    OccupancySnapshotOut,
    RoomMoveIn,
    WalkInBookingIn,
)
from app.services import hotel_front_desk as fd
from app.services.sessions import require_ui_session

hotel_front_desk_router = APIRouter(prefix="/ui/hotels", tags=["hotel-front-desk"])


def _require_enabled() -> None:
    fd._require_enabled()
```

### 4.2 Endpoint specifications (declaration order — literal before dynamic)

All eight handlers are declared in the order below. The five literal sub-routes
(`arrivals`, `departures`, `in-house`, `occupancy`, `walk-in`) come **before** the three
`/reservations/{reservation_id}/...` dynamic routes.

---

#### `GET /ui/hotels/{hotel_id}/front-desk/arrivals`  *(literal — declared first)*

```python
@hotel_front_desk_router.get(
    "/{hotel_id}/front-desk/arrivals", response_model=FrontDeskListOut
)
async def get_arrivals(
    hotel_id: str,
    date: Optional[str] = None,
    cursor: Optional[str] = None,
    limit: int = 50,
    session=Depends(require_ui_session),
) -> FrontDeskListOut:
    _require_enabled()
    result = fd.arrivals_today(hotel_id, date=date, cursor=cursor, limit=limit)
    return FrontDeskListOut(**result)
```

- Auth: `require_ui_session`. Service: HTL-022 `arrivals_today` — `GSI_HOTEL_ARRIVALS`,
  `checkin == date`, filtered `status == "confirmed"`. Response `{rows, count, cursor}`.

```typescript
import { api } from "@/api/client";
import type {
  FrontDeskList, OccupancySnapshot, WalkInBookingIn,
  AssignRoomIn, RoomMoveIn, FrontDeskActionOut,
} from "@/api/types";

const base = (hotelId: string) => `/ui/hotels/${hotelId}/front-desk`;

export const getArrivals = (hotelId: string, params?: { date?: string; cursor?: string; limit?: number }) =>
  api.get<FrontDeskList>(`${base(hotelId)}/arrivals`, paramsToQuery(params));

export const getDepartures = (hotelId: string, params?: { date?: string; cursor?: string; limit?: number }) =>
  api.get<FrontDeskList>(`${base(hotelId)}/departures`, paramsToQuery(params));

export const getInHouse = (hotelId: string, params?: { cursor?: string; limit?: number }) =>
  api.get<FrontDeskList>(`${base(hotelId)}/in-house`, paramsToQuery(params));

export const getOccupancy = (hotelId: string, date?: string) =>
  api.get<OccupancySnapshot>(`${base(hotelId)}/occupancy`, date ? { date } : undefined);

export const walkIn = (hotelId: string, body: WalkInBookingIn) =>
  api.post<FrontDeskActionOut>(`${base(hotelId)}/walk-in`, body);

export const assignRoom = (hotelId: string, reservationId: string, body: AssignRoomIn) =>
  api.post<FrontDeskActionOut>(`${base(hotelId)}/reservations/${reservationId}/assign-room`, body);

export const changeRoom = (hotelId: string, reservationId: string, body: AssignRoomIn) =>
  api.post<FrontDeskActionOut>(`${base(hotelId)}/reservations/${reservationId}/change-room`, body);

export const roomMove = (hotelId: string, reservationId: string, body: RoomMoveIn) =>
  api.post<FrontDeskActionOut>(`${base(hotelId)}/reservations/${reservationId}/room-move`, body);

function paramsToQuery(p?: Record<string, unknown>) {
  if (!p) return undefined;
  return Object.fromEntries(
    Object.entries(p).filter(([, v]) => v !== undefined).map(([k, v]) => [k, String(v)])
  );
}
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `FrontDeskPage.tsx` — layout

`useParams<{ hotelId: string }>()` extracts `hotelId`. The page is composed of three blocks:

**(a) Occupancy summary strip** (top, always rendered). `useQuery({ queryKey:
["frontDesk", hotelId, "occupancy", todayStr], queryFn: () => getOccupancy(hotelId) })`.
Renders a row of metric cards (shadcn/ui `Card`): Rooms Occupied / Available /
Out-of-Service, Occupancy Rate (`(rate * 100).toFixed(1) + "%"`), and the three counts
(Arrivals / Departures / In-House). On loading → `Skeleton`s; on 404 (flag off) → the inline
"Hotel PMS is not enabled on this platform." callout, which becomes the **only** content (no
broken partial render — PROP-005 §5.1).

**(b) Arrivals / Departures / In-House tabs** (shadcn/ui `Tabs`). Each `TabsContent` renders
a single status-bucketed **column** re-skinned from `TicketKanbanBoard.tsx:31-78`: a column
header with the count `Badge`, then a vertical stack of reservation `Card`s. Each card shows
`guest_name`, the `room_type_id`, `checkin → checkout` (with `nights`),
`occupancy_adults`/`occupancy_children`, a `status` `Badge`, and the `assigned_room_ids` chips
(or an "Unassigned" badge when empty). The three tabs drive the three list queries (§4.5).
No drag-and-drop (§2.8).

**(c) Per-card action menu** — each card carries a `Button`/dropdown exposing **Assign Room**
(shown when `assigned_room_ids` is empty), **Change Room** (shown when assigned), and **Move
Room** (shown on In-House cards only, since a move requires `status == "checked_in"`). Each
opens a dialog (§5.3).

**(d) Walk-in** — a top-right "Walk-in" `Button` opens the walk-in dialog (§5.2).

### 5.2 Walk-in dialog (RHF + Zod → `walkIn`)

```typescript
const walkInSchema = z.object({
  room_type_id: z.string().min(1, "Room type is required"),
  checkin: z.string().min(1),    // date input "YYYY-MM-DD"
  checkout: z.string().min(1),
  guest_name: z.string().min(1, "Guest name is required"),
  occupancy_adults: z.coerce.number().int().min(1).default(1),
  occupancy_children: z.coerce.number().int().min(0).default(0),
  total_cents: z.coerce.number().int().min(0).optional(),
});
```

On submit: `useMutation({ mutationFn: (d) => walkIn(hotelId, d), onSuccess })` →
`toast.success("Walk-in checked in")`, close dialog, invalidate the In-House/occupancy/arrivals
keys (§4.5). On API error → `toast.error(err.detail)` (e.g., a 409 oversell from the inner
`create_reservation`, surfaced verbatim). The submit button is disabled while
`mutation.isPending` (idempotency belt-and-braces, §7.5).

### 5.3 Assign / Change / Move dialogs (optimistic-concurrency `version`)

Each dialog loads the hotel's rooms (HTL-006 `GET /ui/hotels/{hotelId}/rooms`) into a
shadcn/ui `Select`/multi-select. **Assign / Change** submit `{ assigned_room_ids, version }`
where `version` is read from the card's reservation row; **Move** submits
`{ from_room_id, to_room_id, version }` (`from_room_id` pre-filled from the card's current
assignment). On success → invalidate the affected tab + occupancy; on a **409**
(`"Reservation was modified concurrently"`, HTL-023 §2.7) → `toast.error` instructing the
agent to refresh, then auto-invalidate the tab so the card reloads the fresh `version`. On a
**404** from `room_move` (unassigned `from_room_id`) → `toast.error("Room not currently
assigned")`.

### 5.4 `date` defaulting and timezone

The summary strip and arrivals/departures tabs default `date` to today, computed FE-side as
`new Date().toISOString().slice(0, 10)` (UTC) to match the server's `now_ts()`-derived UTC
today (HTL-022 §2.6). A `date` picker lets the agent view a future arrivals board; changing it
changes the query key so React Query refetches. Hotel-local-timezone refinement is Open
Question §10.2 (inherited from HTL-022).

### 5.5 Empty states

Each tab renders an empty card ("No arrivals today.", "No departures today.", "No guests
in-house.") when its `rows` is empty. The occupancy strip renders zeros cleanly on a
zero-room hotel (the service's divide-by-zero guard yields `occupancy_rate = 0.0`, HTL-022
§2.8).

### 5.6 Pagination

Each list query fetches one page (`limit=50`). If `cursor` is returned, a "Load more" button
appends the next page (single extra `useQuery` with the cursor) — MVP, matching PROP-005 §5.7.
The occupancy strip's counts come from `occupancy_snapshot` (its own aggregation), independent
of tab pagination.

### 5.7 Admin-gated controls

The Walk-in / Assign / Change / Move controls are mutations → `require_admin_or_root_csrf`
(403 for USER sessions). The page **hides** these controls for non-admin sessions, decoding
role from the JWT via `getRoleFromAccessToken(useAuthStore(s => s.accessToken))` from
`@/lib/adminCapabilities` (the established pattern — PROP-005 §7.3 / `TicketsPage`), not a
`role` field on `useAuthStore` (which exposes only `accessToken`/`userId`/`isAuthenticated`).
Read tabs remain visible to any authenticated user.

### 5.8 Route-ordering correctness (server-side)

The `/front-desk/arrivals`, `/departures`, `/in-house`, `/occupancy`, and `/walk-in` literal
routes are declared before the `/front-desk/reservations/{reservation_id}/...` dynamic routes
(§4.2). A request to `GET .../front-desk/arrivals` therefore resolves to `get_arrivals`, not to
a `reservation_id == "arrivals"` capture. A test asserts this (§9.1 #flag/ordering).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — no dev-mode branches

HTL-024 adds zero `if S.dev_mode` branches. The router is pure delegation; the service layer
(HTL-022/023) already enforces SECOPS-007 (same `T.*` handles in both environments, moto
intercepting boto3 in dev). The FE has no dev-mode concept — it calls the same endpoints in
both environments. Cross-cutting constraint `docs/qloapps/FRONT_DESK_TICKETS.md:60-64`.

### 7.2 SECOPS-007 — hermetic pytest uses no `dev_mode`

`tests/test_htl_front_desk.py` toggles `S.hotel_pms_enabled` via `object.__setattr__` but
never sets `S.dev_mode`. All reads/writes go through the same DynamoDB code path with moto
intercepting boto3 (§9.1), identical to every existing hermetic test.

### 7.3 Security — admin-only mutations + CSRF

All four POST mutations are gated by `require_admin_or_root_csrf` (`app/auth/policy.py:100`):
`enforce_cookie_csrf(request)` (403 on missing/mismatched `x-csrf-token`) then
`require_roles(user, {ADMIN, ROOT})` (403 for USER). The four GET reads accept any
authenticated UI session (`require_ui_session`). This is the exact `inventory_router` split.
Bearer-auth callers skip CSRF (CLAUDE.md auth note). The FE additionally hides mutation
controls for non-admin sessions (§5.7) to avoid confusing 403s, but the backend is the
authoritative gate.

### 7.4 Money-safety

HTL-024 touches **no** billing code. `walk_in_booking` delegates to HTL-018
`create_reservation`, which owns the total computation / availability decrement (HTL-023 §1) —
HTL-024 never recomputes a total, never writes a ledger entry, and never imports
`billing_shared`. `total_cents` is a pass-through display value. The assign/change/move
mutations move physical rooms only; no money moves. The version-gating (§7.5) guards against
double-assignment, not double-charge (there is no charge here).

### 7.5 Idempotency & optimistic concurrency

- **Walk-in**: the inner HTL-018 `create_reservation` is idempotent on its own key (HTL-018);
  the FE disables the submit button while `isPending` (§5.2) as belt-and-braces. A double-POST
  resolves to one reservation.
- **Assign / change / move**: each carries the reservation `version`; the HTL-023
  `update_item` guards `ConditionExpression="version = :v"` and bumps `ADD version :one`, so a
  stale second writer gets **409** and the FE refetches the fresh version (§5.3). This is the
  single-winner CAS idiom (HTL-023 §2.6/2.7, modeled on `app/services/inventory.py:434-453`).

### 7.6 Audit trail

The HTL-023 actions emit `hotel.frontdesk.walk_in` / `.assign_room` / `.change_room` /
`.room_move` via the service `_audit()` wrapper (HTL-023 §2.5). HTL-024 adds no router-side
audit — the service is the authoritative source. The four reads emit nothing (read-only,
HTL-022 §2.4).

6. `date` defaults to today when omitted (assert against a `now_ts`-patched fixed clock).
7. Explicit `date` param returns that date's arrivals.

*Departures query*
8. Seed `checked_in` reservations with `checkout == today` + a `checked_in` with a later
   checkout + a `confirmed` due today → `get_departures` returns only `checked_in` +
   `checkout == today`.

*In-house query*
9. Seed mixed-status reservations → `get_in_house` returns every `checked_in` regardless of
   date, via `GSI_HOTEL_STATUS`.

*Occupancy snapshot*
10. `rooms_occupied` = distinct in-house `assigned_room_ids` count; `rooms_out_of_service`
    from `GSI_HK_STATUS`; `occupancy_rate ∈ [0, 1]`.
11. Zero-room hotel → `occupancy_rate == 0.0`, no `ZeroDivisionError`.

*Walk-in*
12. `walk_in` handler calls the patched `create_reservation` then `check_in` (assert call
    order + args); the patched `check_in` returns a `checked_in` reservation; response is a
    `FrontDeskActionOut` shape ending `checked_in`.

*Assign / change / room-move*
13. `assign_room` with the current `version` writes `assigned_room_ids` and bumps `version`;
    the affected room's HK status flips through the patched
    `set_room_housekeeping_status` (assert it was called).
14. `assign_room` with a **stale** `version` → `HTTPException(409)`.
15. `change_room` swaps the assignment set (version-gated; 409 on stale).
16. `room_move` with an unassigned `from_room_id` → `HTTPException(404)`.
17. `room_move` on a non-`checked_in` reservation → `HTTPException(409)`.

*Route ordering (literal before dynamic)*
18. `GET .../front-desk/arrivals` resolves to `get_arrivals` (assert the response is the
    arrivals list shape, not a `reservation_id == "arrivals"` capture) — call the mounted
    router via the route table, or assert the route declaration order in
    `hotel_front_desk_router.routes`.
19. `POST .../front-desk/walk-in` resolves to `walk_in`, not captured by
    `/reservations/{reservation_id}/...`.

## 10. Open Questions / Assumptions

1. **Hotel selection / sidebar hotel id.** The sidebar nav item hard-codes
   `/hotels/default/front-desk` (§4.7) pending a hotel-selector / hotel-list page (a separate
   hotel-entity FE ticket). **Assumption**: single-hotel deployments in MVP; the route param
   makes multi-hotel forward-compatible. A hotel switcher is out of scope.
2. **Timezone.** "Today" is UTC (FE `toISOString().slice(0,10)`, service `now_ts()`-derived,
   HTL-022 §2.6). A hotel-local-timezone refinement (per-hotel `check_in_time`/tz) is deferred
   — inherited Open Question from HTL-022 §10.2.
3. **`HotelRoom` type reuse.** §3.3 defines a FE `HotelRoom` mirror of HTL-006 `RoomOut`. If
   HTL-006's FE ticket already added a room type to `types.ts`, reuse it and drop the
   duplicate. **Assumption**: HTL-006 has no FE ticket yet, so HTL-024 defines the minimal
   subset it needs.
4. **Departures index.** HTL-022 derives departures from `GSI_HOTEL_STATUS` +
   in-memory `checkout == date` filter (no `GSI_HOTEL_CHECKOUT` in HTL-018, HTL-022 §2.2). If
   HTL-018 later adds a checkout GSI, `departures_today` switches transparently — no HTL-024
   API change.
5. **Walk-in `201` on idempotent replay.** The handler returns `201` even when the inner
   `create_reservation` returns an existing reservation (idempotent), matching PROP-004's
   create-idempotency note. **Assumption**: callers treat `201` idempotently.
6. **Read auth breadth.** Reads accept any authenticated UI session (single-platform
   assumption, mirroring `inventory_router` reads + PROP-004 §2.3). Per-hotel staff scoping is
   a future multi-tenant ticket.
