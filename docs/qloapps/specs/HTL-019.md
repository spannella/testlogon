# HTL-019 — Reservation lifecycle state machine + append-only history + `modify_reservation`

**Type**: Feature | **Priority**: P0 | **Estimate**: 3d
**Source**: `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md` §HTL-019 + "Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C (Reservation lifecycle)

---

## 1. Summary & Goal

HTL-019 lands the **reservation lifecycle state machine** — the verbs that move a reservation through
`confirmed → checked_in → checked_out` plus the terminal `cancelled` / `no_show` exits, an **append-only
status-history trail**, and `modify_reservation` (change dates / room type → re-check availability + re-price).
It extends the **existing** `app/services/hotel_reservations.py` file landed by HTL-017 (`search_stays`) and
HTL-018 (`create_reservation` + the `hotel_reservations` table) — it ships **no new table** and **no new flag**.

The implementation is a **near-verbatim clone of three proven patterns**, specialized to the hotel domain:

1. The OFBiz **order state machine** — a module-level transition-allowlist dict + a single
   `transition_*` entry point that validates a legal edge in Python, then performs an **optimistic-concurrency
   conditional `update_item`** on the header (`docs/ofbiz/specs/ORD-005.md` §4.1.2, §4.1.6).
2. The OFBiz **append-only HIST rows** co-located on the entity's own partition
   (`docs/ofbiz/specs/ORD-001.md` §3.2; ORD-005 §3.3 — `SK = HIST#{ts:020d}#{event_id}`).
3. The KYC **`version = :expected_version`** counter CAS (`app/services/kyc_cases.py:228`) — the
   spec-chosen concurrency predicate (a numeric `version` bumped on each transition, unlike ORD-005 which CASes
   on the `lifecycle_status` string; the parent doc mandates `version`,
   `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:66-68,222`).

The five public functions HTL-019 delivers:

- **`transition_reservation(reservation_id, target_status, *, actor, reason="", assigned_room_ids=None)`** — the
  single transition entry point. Validates the edge against `_RESERVATION_TRANSITIONS`, applies the per-target
  side-effects (assign physical rooms on check-in; release physical rooms to housekeeping on check-out;
  **release the HTL-011 hold on cancel / no-show**), performs the `version`-gated conditional `update_item`,
  appends a HIST row, audits, and returns the updated header.
- **`modify_reservation(reservation_id, *, checkin=None, checkout=None, room_type_id=None, adults=None,
  children=None, rooms=None, actor)`** — re-dates / re-rooms a **confirmed** reservation: re-checks
  availability (HTL-012), swaps the hold new-before-old (HTL-011), re-prices (HTL-015), bumps `version`,
  appends a `modified` HIST row.
- **`list_reservation_history(reservation_id, *, cursor=None, limit=50)`** — reads the `HIST#` child rows
  newest-first.
- **`_record_history(...)`** — the internal append-only HIST writer (the ORD-006 `_append_history_row`
  analogue), best-effort, idempotent via `attribute_not_exists(sk)`.

The hard invariants: **exactly one winner** on a concurrent transition (the `version` CAS), **inventory is
released back across the span on cancel / no-show** (so the room-nights become sellable again), and **no money
fork** — cancel / no-show release held inventory and record the transition but issue **no refund** and write
**no ledger entry**; the cancellation/no-show **refund + penalty** engine is **HTL-033** (Tier-3 forward ref).
With `HOTEL_PMS_ENABLED=false` (the default) every entrypoint raises HTTP 404 before any DynamoDB access and
the platform is byte-for-byte unchanged.

### 2.3 The ORD state-machine idiom reused

ORD-005 (`docs/ofbiz/specs/ORD-005.md`) is the closest existing pattern. HTL-019 clones its three structural
pieces:

- **The transition-allowlist dict** (`ORD-005 §4.1.2`): `TRANSITIONS: dict[str, set[str]]`, terminal states as
  empty sets, validated in Python before any DDB round-trip (`ORD-005 §5.2`, §5.8 "terminal protection is
  correct-by-construction"). HTL-019's `_RESERVATION_TRANSITIONS` is the hotel-domain specialization.
- **The conditional-update CAS** (`ORD-005 §4.1.6`): a single `update_item` with a `ConditionExpression`
  guarding the current state, catching `ConditionalCheckFailedException` → a typed 409 conflict. HTL-019 guards
  on **`version = :expected_version`** (the KYC predicate, `app/services/kyc_cases.py:228`) rather than ORD's
  `lifecycle_status = :current_status`, per the parent doc.
- **The append-only HIST row + best-effort ordering** (`ORD-005 §3.3, §4.1.6 step 6`,
  `docs/ofbiz/specs/ORD-001.md` §3.2): the HIST write happens **after** the CAS-protected header update; a HIST
  failure does **not** roll back the state change (best-effort, matching the platform audit convention,
  CLAUDE.md). `event_id = sha256(...)[:16]` (the ORD-005 §4.1.3 hash-prefix idiom) gives a deterministic id so a
  replayed write with `attribute_not_exists(sk)` is a silent no-op (no duplicate history).

### 2.4 The LSE transition-allowlist shape

The open-property **LSE** lease (`docs/open-property/specs/LSE-001.md` §4.1, referenced by id from the parent
doc, `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:348-349`) provides the `_LEASE_TRANSITIONS` allowlist
shape — a plain `dict[str, set[str]]` of legal next states. HTL-019's `_RESERVATION_TRANSITIONS` is the same
shape, specialized to the five hotel states. (LSE CASes on `status`; HTL-019 CASes on `version` — that is the
one deliberate divergence, taken from KYC/ORD's numeric counter, `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:68`.)

### 2.5 The version-counter CAS (KYC)

`app/services/kyc_cases.py:228` (verified) is the canonical numeric-`version` optimistic-concurrency predicate:

```python

```

with the `ConditionalCheckFailedException` detector at `app/services/kyc_cases.py:113` (verified):

### 2.6 The HTL-011 hold lifecycle (release on cancel / no-show)

HTL-011 (`docs/qloapps/specs/HTL-011.md` §4.3) provides `release_hold(hold_id, *, reason, user_sub,
terminal_status)` — an **idempotent** status-CAS terminal flip of the `HOLD#{hold_id}` meta row that decrements
`held` back on exactly the dates the hold touched (its authoritative `dates` undo list, HTL-011 §5.8). Replays
after the terminal flip are no-ops (HTL-011 §5.6); a missing hold → 404. HTL-019's cancel / no-show transitions
call `release_hold(item["hold_id"], reason=target, user_sub=actor, terminal_status="released")` so the
date-keyed room-nights become sellable again. **HTL-019 does not call `hold_rooms` on a lifecycle transition** —
the hold is the booking (placed at create time, HTL-018 §5/`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:284-289`);
it is released only on cancel / no-show. `modify_reservation` is the one HTL-019 verb that places a fresh hold
(swapping the span). HTL-011 §11.2 already names HTL-018 (and transitively HTL-019) as the downstream consumer
of the hold lifecycle.

### 2.7 The HTL-012 / HTL-015 re-check-and-re-price forward-deps (modify)

`modify_reservation` re-validates the **new** span against the same two forward-deps `create_reservation`
(HTL-018) uses at book time:

- **HTL-012** `check_availability(hotel_id, room_type_id, checkin, checkout, rooms_needed)` — the per-date
  availability **intersection across the span** (`{available, rooms_needed, per_night, min_remaining}`;
  `docs/qloapps/specs/HTL-012.md` §4.1). A `not available` new span → 409 (no change applied).
- **HTL-015** `compute_stay_price(hotel_id, room_type_id, checkin, checkout, adults, children, rooms) ->
  StayPriceResult{per_night, total_cents, currency, applied_rule_ids}` — the deterministic multi-night/occupancy
  price engine (forward ref, `docs/qloapps/RATE_PLANS_TICKETS.md`). `modify_reservation` re-prices the new span
  and writes the new `total_cents`. **No money movement** — any price *delta* settlement is HTL-033 (forward ref).

### 2.8 The HTL-006 physical-room status forward-dep (check-in / check-out)

`transition_reservation`'s check-in / check-out side-effects flip individual **physical room** occupancy /
housekeeping status via the HTL-006 room service (forward ref,
`docs/qloapps/ROOMTYPES_ROOMS_HOUSEKEEPING_TICKETS.md`): `hotel_pms.set_room_status(room_id, "occupied")` on
check-in, and a housekeeping flip (`"dirty"` / `"vacant"`) on check-out. Both are **best-effort** (`try/except`,
never roll back the transition) — the same best-effort side-effect pattern as the EC2/K8s host-inventory hooks
(CLAUDE.md "EC2 host-inventory lifecycle (GAP-0223/0224)" / "K8s pod host-inventory lifecycle (GAP-0226/0227)":
"registration/cleanup failure must NOT roll back launch/termination"). HTL-006 is unbuilt; HTL-019's hermetic
tests patch `set_room_status` at the `hotel_reservations` namespace (§9.1).

## 3. Data Model

HTL-019 introduces **no new table, no new GSI, no new flag, no new top-level partition**. It (a) **mutates** the
HTL-018 `META` header (the `status`, `version`, `assigned_room_ids`, `total_cents`, span/occupancy fields, and
`updated_at`), and (b) **appends** child `HIST#` rows on the **same** reservation partition.

### 3.1 Header (`META`) fields HTL-019 writes

These columns already exist on the HTL-018 header (§2.2); HTL-019 is the owner that transitions them:

| Attribute | DDB Type | HTL-019 writer | Notes |
|---|---|---|---|
| `status` | S | every `transition_reservation` | `confirmed` → `checked_in` → `checked_out`, or `confirmed` → `cancelled` / `no_show`. Re-projects `GSI_HOTEL_STATUS`. |
| `version` | N | every `transition_reservation` / `modify_reservation` | `version = version + 1` inside the CAS-guarded write |
| `assigned_room_ids` | L | `transition_reservation(→ checked_in)` | the physical room ids (`len == rooms`); empty `[]` otherwise |
| `checkin` / `checkout` / `nights` | S / S / N | `modify_reservation` | the new span (re-validated via HTL-012, re-priced via HTL-015) |
| `room_type_id` | S | `modify_reservation` | the new room type (when changed) |
| `adults` / `children` / `rooms` | N | `modify_reservation` | the new occupancy |
| `total_cents` / `currency` | N / S | `modify_reservation` | from `compute_stay_price(...)` on the new span |
| `hold_id` | S | `modify_reservation` (new hold), unchanged on lifecycle transitions | swapped to the new HTL-011 hold on a successful modify |
| `updated_at` | N | every write | `now_ts()` |

`booked` is **not** written here — it is owned by the availability cluster; HTL-019 only manipulates the **hold**
(`held`) via `release_hold` / `hold_rooms`. `total_cents` is touched only by `modify_reservation` (a re-price);
a plain lifecycle transition never changes the money figure.

### 3.2 Append-only history child row (`HIST#`)

Co-located on the reservation's own partition (the ORD `ORDER`/`HIST#` idiom, `docs/ofbiz/specs/ORD-001.md`
§3.2, ORD-005 §3.3) — sparse to the three header GSIs (no `hotel_id` / `guest_party_id` / `status` attrs on the
HIST row, so it never appears in `GSI_HOTEL_ARRIVALS` / `GSI_GUEST` / `GSI_HOTEL_STATUS`):

| Attribute | DDB Type | Notes |
|---|---|---|
| `reservation_id` | S (PK) | same partition as the `META` header |
| `sk` | S (SK) | `"HIST#{ts:020d}#{event_id}"` — zero-padded `ts` sorts chronologically; `event_id` disambiguates same-second events |
| `event_id` | S | `sha256(f"{reservation_id}|{from_status}|{to_status}|{actor}")[:16]` — the ORD-005 §4.1.3 hash-prefix idiom |
| `from_status` | S | the status before the transition (e.g. `confirmed`) |
| `to_status` | S | the status after (e.g. `checked_in`, or `modified` for a `modify_reservation` event) |
| `actor` | S | the `user_sub` (or `"system"`) driving the transition |
| `reason` | S | human-readable note (may be empty) |
| `ts` | N | `now_ts()` at write time |

The HIST row is written with `ConditionExpression="attribute_not_exists(sk)"` (ORD-005 §7.2 HIST idempotency) —
a replayed write with the same `event_id`+`ts` fails silently, never duplicating history. There is **no numeric
GSI** on the HIST `sk` (it is queried by `begins_with(sk, "HIST#")` on the base partition, not via an index), so
**no `attr_types` change** is required by HTL-019 (the CLAUDE.md numeric-GSI rule does not apply — `HIST#` is a
String sort key on the base table).

### 3.3 The transition graph (`_RESERVATION_TRANSITIONS`)

Module-level data in `app/services/hotel_reservations.py` — the LSE allowlist shape + the ORD terminal-empty-set
idea (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:351-361`):

```python
_RESERVATION_TRANSITIONS: dict[str, set[str]] = {
    "confirmed":   {"checked_in", "cancelled", "no_show"},
    "checked_in":  {"checked_out"},
    "checked_out": set(),   # terminal
    "cancelled":   set(),   # terminal
    "no_show":     set(),   # terminal
}
```

- `confirmed → checked_in` — guest arrived; **assign physical rooms**.
- `confirmed → cancelled` — guest cancelled before arrival; **release held inventory** (HTL-011).
- `confirmed → no_show` — guest never arrived by end of arrival day; **release held inventory** (HTL-011); the
  no-show *fee* is HTL-033 (forward ref).
- `checked_in → checked_out` — departure; **release physical rooms** back to housekeeping (HTL-006).
- `checked_out` / `cancelled` / `no_show` — terminal (empty sets). Any outbound attempt fails the
  `target not in _RESERVATION_TRANSITIONS.get(current, set())` membership check (`target not in set()` is always
  `True`) → 409 with **zero DDB writes** (correct-by-construction, ORD-005 §5.8). `.get(current, set())` returns
  an empty set for an unknown/stale status string, producing a clean 409 rather than a `KeyError` (ORD-005 §5.2).

### 4.1 Module-level additions

```python
import hashlib

_RESERVATION_TRANSITIONS: dict[str, set[str]] = {       # §3.3
    "confirmed":   {"checked_in", "cancelled", "no_show"},
    "checked_in":  {"checked_out"},

    "cancelled":   set(),

_TERMINAL_STATES = frozenset({"checked_out", "cancelled", "no_show"})


def _is_conditional_conflict(exc) -> bool:
```

### 4.2 `_record_history` — the append-only HIST writer

```python
def _record_history(reservation_id, from_status, to_status, *, actor, reason="", ts=None) -> None:
    """Best-effort append of a HIST# child row on the reservation partition (ORD-006 analogue)."""
    ts = ts or now_ts()
    event_id = _hist_event_id(reservation_id, from_status, to_status, actor)
    try:
        T.hotel_reservations.put_item(
            Item={
                "reservation_id": reservation_id,
                "sk": f"HIST#{ts:020d}#{event_id}",
                "event_id": event_id,
                "from_status": from_status,
                "to_status": to_status,
                "actor": actor or "system",
                "reason": reason or "",
                "ts": int(ts),
            },
            ConditionExpression="attribute_not_exists(sk)",   # idempotent replay → silent no-op
        )
    except Exception:
        pass   # HIST failure never rolls back the transition (ORD-005 §4.1.6 step 6, best-effort)
```

### 4.3 `transition_reservation` — the single transition entry point

```python
def transition_reservation(
    reservation_id: str,
    target_status: str,
    *,
    actor: str,
    reason: str = "",
    assigned_room_ids: list[str] | None = None,   # required on → checked_in
) -> dict:
```

**Flow** (mirrors ORD-005 §4.1.6, specialized; `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:370-421`):

1. **`_require_enabled()`** — flag-off 404 before any work.
2. **Read current** — `item = get_reservation(reservation_id)`; `None` → `HTTPException(404)`. Read
   `current = item["status"]`, `expected_version = int(item["version"])`.
3. **Validate edge** — `if target_status not in _RESERVATION_TRANSITIONS.get(current, set()):
   raise HTTPException(409, detail={"code": "invalid_status_transition", "from": current, "to": target_status})`.
   Validated in **Python before any DDB call** (ORD-005 §5.2) — an illegal edge (incl. any outbound from a
   terminal state, §3.3) has **zero DDB cost and zero writes**.
4. **Per-target side-effects** — computed before the conditional write, applied within / around it:
   - **`→ checked_in`** — **assign physical rooms**. `assigned_room_ids` is **required**
     (`None`/empty → `HTTPException(422, "assigned_room_ids required for check-in")`) and
     `len(assigned_room_ids)` must equal `int(item["rooms"])`
     (`HTTPException(422, "assigned_room_ids must match rooms")` otherwise). The list is `SET` on the header in
     the CAS write (step 5). **Best-effort** flip each physical room `occupied` via HTL-006:
     ```python
     for rid in assigned_room_ids:
         try:
             hotel_pms.set_room_status(rid, "occupied")
         except Exception:
             pass   # never roll back the check-in
     ```
   - **`→ checked_out`** — **release physical rooms** back to housekeeping. Best-effort flip each
     `item.get("assigned_room_ids", [])` to `"dirty"` (housekeeping) via HTL-006 (`try/except`). The held
     room-night inventory was consumed by the completed stay; **checkout does NOT call `release_hold`** (the
     hold is the booking; it is released only on cancel / no-show,
     `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:397-398`).
   - **`→ cancelled` or `→ no_show`** — **release held inventory** (HTL-011) so the date-keyed `held` counts are
     decremented back across the span and the room-nights become sellable again:
     ```python
     hold_id = item.get("hold_id")
     if hold_id:
         try:
             ha.release_hold(hold_id, reason=target_status, user_sub=actor, terminal_status="released")
         except Exception:
             pass   # release failure must NOT block cancel/no-show; HTL-011 TTL sweep is the backstop
     ```
     **No refund / penalty / ledger entry** — HTL-033 (forward ref) owns the money. HTL-019 releases inventory
     and records the transition only (cross-cutting "no money fork",
     `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:80-83`, ORD-001 §5.6 invariant).
5. **`version`-gated conditional `update_item`** on the `META` header (the KYC/ORD CAS,
   `app/services/kyc_cases.py:228`, ORD-005 §4.1.6):
   ```python
   set_parts = ["#status = :target", "version = version + :one", "updated_at = :now"]
   values = {":target": target_status, ":one": 1, ":now": now_ts(), ":ver": expected_version}
   names = {"#status": "status"}
   if target_status == "checked_in":
       set_parts.append("assigned_room_ids = :rooms_assigned")
       values[":rooms_assigned"] = list(assigned_room_ids or [])
   try:
       T.hotel_reservations.update_item(
           Key={"reservation_id": reservation_id, "sk": "META"},
           UpdateExpression="SET " + ", ".join(set_parts),
           ExpressionAttributeNames=names,
           ExpressionAttributeValues=values,
           ConditionExpression="version = :ver",
           ReturnValues="ALL_NEW",
       )
   except ClientError as exc:
       if _is_conditional_conflict(exc):
           raise HTTPException(409, detail={"code": "concurrent_update"}) from exc
       raise
   ```
   A concurrent writer that bumped `version` first wins; the loser's condition fails →
   `HTTPException(409, {"code": "concurrent_update"})` (ORD-005 §5.6 "single winner").
   `#status` is an `ExpressionAttributeName` because `status` is a DynamoDB reserved word (the KYC/ORD pattern,
   `app/services/kyc_cases.py` `update_item` block).
6. **Append-only history** — `_record_history(reservation_id, current, target_status, actor=actor,
   reason=reason)` (§4.2) — best-effort, after the CAS write (ORD-005 §4.1.6 step 6).
7. **Audit** — best-effort `_audit("hotel.reservation.status_changed", actor, reservation_id=reservation_id,
   from_status=current, to_status=target_status)`.
8. **Return** the updated header (re-read via `get_reservation`, or deserialize `ReturnValues="ALL_NEW"`;
   the re-read avoids `Decimal`/projection edge cases — ORD-005 §10 assumption 5).

### 4.4 `modify_reservation` — re-date / re-room → re-check availability + re-price

```python
def modify_reservation(
    reservation_id: str,
    *,
    checkin: str | None = None,
    checkout: str | None = None,
    room_type_id: str | None = None,
    adults: int | None = None,
    children: int | None = None,
    rooms: int | None = None,
    actor: str,
) -> dict:
```

**Flow** (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:436-449`):

1. **`_require_enabled()`**; `item = get_reservation(reservation_id)`; `None` → 404. **Reject non-confirmed**:
   `if item["status"] != "confirmed": raise HTTPException(409, detail={"code": "not_modifiable", "status":
   item["status"]})` — a checked-in / checked-out / terminal reservation cannot be re-dated.
   `expected_version = int(item["version"])`.
2. **Compute the new effective values** — each field defaults to the current header value when the arg is `None`:
   `new_checkin`, `new_checkout`, `new_room_type_id`, `new_adults`, `new_children`, `new_rooms`. Validate the new
   span: `new_nights = _validate_span(new_checkin, new_checkout)` (HTL-017 helper → 422 on a malformed / ≤ 0-night
   span). If the effective values are identical to the current header (a no-op modify), the function may
   short-circuit and return the unchanged header (§5.7).
3. **Re-check availability for the NEW span** — `avail = ha.check_availability(item["hotel_id"],
   new_room_type_id, new_checkin, new_checkout, rooms_needed=new_rooms)` (HTL-012). `if not avail["available"]:
   raise HTTPException(409, detail={"code": "no_availability"})` — **before** swapping any hold (no inventory
   touched on an unavailable modify).
4. **Swap the hold — new-before-old (never an un-held window)** — place the **new** hold first; on success
   release the **old** hold; on a new-hold failure keep the old hold and raise
   (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:441-443`):
   ```python
   try:
       new_hold = ha.hold_rooms(item["hotel_id"], new_room_type_id, new_checkin, new_checkout,
                                quantity=new_rooms, user_sub=actor)   # HTL-011
   except HTTPException as exc:
       if exc.status_code == 409:
           raise HTTPException(409, detail={"code": "no_availability"}) from exc   # old hold intact
       raise
   new_hold_id = new_hold["hold_id"]
   old_hold_id = item.get("hold_id")
   ```
   The old hold is released only **after** the CAS write succeeds (step 6), so a CAS conflict leaves the old hold
   intact and best-effort-releases the *new* hold to avoid orphaning it (§5.8).
5. **Re-price the new span** — `price = rate_plans.compute_stay_price(item["hotel_id"], new_room_type_id,
   new_checkin, new_checkout, new_adults, new_children, new_rooms)` (HTL-015) → `new_total_cents`,
   `new_currency`. **No money movement** — any price *delta* settlement is HTL-033 (forward ref).
6. **`version`-gated conditional `update_item`** (same `version = :expected_version` CAS as §4.3 step 5) writing
   `checkin`, `checkout`, `nights`, `room_type_id`, `adults`, `children`, `rooms`, `total_cents`, `currency`,
   `hold_id = new_hold_id`, `version = version + 1`, `updated_at = now_ts()`. On
   `ConditionalCheckFailedException` → best-effort release the **new** hold, then
   `HTTPException(409, {"code": "concurrent_update"})`.
7. **Release the old hold** (best-effort, after the CAS succeeds) — `if old_hold_id and old_hold_id !=
   new_hold_id: try: ha.release_hold(old_hold_id, reason="modified", user_sub=actor,
   terminal_status="released") except Exception: pass`.
8. **Append-only history** — `_record_history(reservation_id, "confirmed", "modified", actor=actor,
   reason="dates/room modified")`; **audit** `_audit("hotel.reservation.modified", actor,
   reservation_id=reservation_id, ...)`; return the updated header.

## 5. Detailed Behavior & Edge Cases

### 5.1 Legal transitions bump `version` and write a HIST row

Each of the four legal transitions (`confirmed→checked_in`, `confirmed→cancelled`, `confirmed→no_show`,
`checked_in→checked_out`) succeeds, bumps `version` by exactly 1 in the CAS write, and appends one `HIST#` child
row. The header `status` is the legacy snapshot (re-projecting `GSI_HOTEL_STATUS`); the HIST trail is the
append-only audit. Acceptance: after `confirmed→checked_in`, the header has `status="checked_in"`,
`version=2` (was `1` at create), `assigned_room_ids` populated, and one `HIST#` row with
`from_status="confirmed"`, `to_status="checked_in"`.

### 5.2 Illegal transitions raise 409 with zero DDB writes

`checked_out→confirmed`, `confirmed→checked_out` (must check in first), any outbound from `cancelled` /
`no_show` / `checked_out` (terminal, empty sets) — all fail the `target not in _RESERVATION_TRANSITIONS.get(
current, set())` membership check **in Python before any DDB call** (ORD-005 §5.2, §5.8). The response is
`HTTPException(409, {"code": "invalid_status_transition", "from": current, "to": target})`; no `update_item`, no
HIST row, no audit. The header is byte-for-byte unchanged.

### 5.3 Check-in requires `assigned_room_ids` with `len == rooms`

`→ checked_in` with `assigned_room_ids=None` or `[]` → `HTTPException(422, "assigned_room_ids required for
check-in")`. With a list whose length ≠ `item["rooms"]` → `HTTPException(422, "assigned_room_ids must match
rooms")`. Both are validated **before** the CAS write (no partial state). On success the list is `SET` on the
header and each room is best-effort flipped `occupied` via HTL-006 (a `set_room_status` failure on one room never
rolls back the check-in — the EC2/K8s best-effort pattern, CLAUDE.md). The room-assignment list is the only
header field (besides `status`/`version`/`updated_at`) a check-in writes.

### 5.4 Check-out releases physical rooms but NOT the hold

`checked_in → checked_out` best-effort flips each `assigned_room_ids` entry to `"dirty"` (housekeeping) via
HTL-006 and does **not** call `release_hold` — the held room-nights were consumed by the completed stay; the hold
is the booking and is released only on cancel / no-show (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:397-398`).
A check-out never decrements `held`. (The hold's own TTL is moot post-stay; the operational lifecycle of a
consumed hold beyond checkout is an HTL-018/033 concern, not HTL-019's — §10.4.)

### 5.5 Cancel / no-show release held inventory; no money

`→ cancelled` and `→ no_show` call `ha.release_hold(item["hold_id"], reason=target, user_sub=actor,
terminal_status="released")` (HTL-011) so the date-keyed `held` counts are decremented back across the span and
the room-nights become sellable again. The release is **best-effort** (`try/except`) — a release failure must
**not** block the transition; HTL-011's TTL sweep (`expire_due_holds`, HTL-011 §4.4) is the backstop that
eventually reclaims a stuck hold. **No ledger entry is written and no refund is issued** — `billing_shared`
(`new_ledger_entry`, `settle_or_reverse_ledger`) is not imported; the cancellation/no-show **refund + penalty**
engine is HTL-033 (forward ref). A reservation with an empty/absent `hold_id` (defensive) skips the release and
still transitions. Idempotency: a replayed cancel (already `cancelled`) fails the edge check at §5.2 (409
invalid_status_transition, since `cancelled` is terminal) — it never double-releases; and even if `release_hold`
itself were re-invoked it is idempotent (HTL-011 §5.6).

### 5.6 Concurrent transitions — exactly one winner

Two concurrent `transition_reservation` calls for the same `reservation_id`, both reading
`expected_version=1`, both targeting `checked_in`: both attempt `update_item` with
`ConditionExpression="version = :ver"` (`:ver=1`). DynamoDB serializes writes — the first bumps `version` to `2`
and wins; the second's condition (`version == 1`) now fails → `ConditionalCheckFailedException` →
`HTTPException(409, {"code": "concurrent_update"})`. Exactly **one** HIST row is written (the loser never reaches
step 6). This is the ORD-005 §5.6 "single winner" guarantee with the KYC numeric-`version` predicate.

### 5.7 `modify_reservation` only on a confirmed reservation

A modify on a `checked_in` / `checked_out` / `cancelled` / `no_show` reservation → `HTTPException(409, {"code":
"not_modifiable", "status": ...})` — a guest already in-house or a terminal booking cannot be re-dated. A modify
with all args `None` (or args equal to the current header) is a no-op: the function may short-circuit and return
the unchanged header without swapping the hold or bumping `version` (an optional optimization; the safe default
is to still re-validate and re-price the identical span, which is harmless but consumes a hold swap — see §10.2).

### 5.8 `modify_reservation` hold swap is new-before-old (no un-held window)

`modify_reservation` places the **new** hold (HTL-011 `hold_rooms`) **before** releasing the **old** hold, so the
reservation is never momentarily un-held. If the new `hold_rooms` 409s (the new span is sold out), the old hold
stays intact and the function raises 409 `no_availability` — the reservation keeps its original confirmed span.
If the new hold succeeds but the `version` CAS then fails (a concurrent transition raced), the function
best-effort releases the **new** hold (to avoid orphaning the room-nights it just held) and raises 409
`concurrent_update` — the old hold is untouched, so the reservation is still validly held on its original span.
The old hold is released (best-effort) only **after** the CAS write commits the new span.

### 5.9 `modify_reservation` re-prices the new span

After the hold swap, `compute_stay_price` (HTL-015) re-prices the **new** span/room-type/occupancy and the CAS
write persists the new `total_cents`/`currency`. The price figure is recomputed verbatim from HTL-015 (not
re-derived). **No money moves** — a price delta (the guest now owes more / less) is settled by HTL-033 (forward
ref); HTL-019 writes no ledger entry. Acceptance: after a modify that lengthens the stay, `total_cents` equals
the patched `compute_stay_price(...).total_cents` for the new span.

### 5.10 History is newest-first and idempotent

`list_reservation_history` returns events newest-first (`ScanIndexForward=False` over the zero-padded `ts` SK).
`_record_history` writes with `attribute_not_exists(sk)`, so a replayed transition that somehow re-enters step 6
with the same `event_id`+`ts` is a silent no-op — no duplicate HIST row (ORD-005 §7.2). The `event_id` is
deterministic on `(reservation_id, from_status, to_status, actor)`; a distinct same-second event with a different
`actor` gets a distinct `event_id` and its own row.

### 5.11 Decimal coercion

`version`, `nights`, `adults`, `children`, `rooms`, `total_cents`, `created_at`, `updated_at`, `ts` are DDB `N`,
returned by boto3 as `Decimal`. The service coerces via `int(...)` before use (`expected_version =
int(item["version"])` in particular — the CAS value must be an int, not a Decimal, to match the stored numeric)
and before returning; `ReservationHistoryEntry`/`ReservationOut` `int` fields coerce on assignment as a guard
(the platform Decimal-coercion convention, ORD-005 §10 assumption 5, PROP-001 §5.4).

### 5.12 Missing reservation / missing hold

`transition_reservation` / `modify_reservation` / `list_reservation_history` on a missing `reservation_id`
(no `META` row) → `HTTPException(404)` (via `get_reservation` returning `None`). A reservation whose `hold_id` is
absent/empty (defensive — should not occur post-HTL-018) skips the cancel/no-show release and still transitions
(the transition is the authoritative state change; the hold release is the best-effort side-effect).

### 5.13 Flag-off behavior

When `HOTEL_PMS_ENABLED=false`, every HTL-019 function raises `HTTPException(404, "Hotel PMS is not enabled")`
via the shared `_require_enabled()` **before** any DDB access or forward-dep call. The HTL-020 lifecycle
sub-routes (which call these) 404 too. The platform is byte-for-byte unchanged.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_reservations.py` (HTL-019 additions) contains **no** `if S.dev_mode` branch. The transition
logic, the `version`-gated conditional `update_item`, the HIST append, and the audit emission are identical in dev
(DynamoDB Local / moto in-process, port 8001) and prod (real DynamoDB) — the same `T.hotel_reservations` handle
in both (`app/core/tables.py`, wired from `S.hotel_reservations_table_name`). The forward-deps HTL-011/012/015/006
**already own any mock/real divergence internally** (each uses the same `T.*` handles in dev (moto) and prod) —
HTL-019 calls them **identically** in both environments (cross-cutting constraint,
`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:76-79`). Acceptance: `grep -n "dev_mode"
app/services/hotel_reservations.py` returns nothing (or only a docstring).

### 7.2 Idempotency

- **`transition_reservation`** is naturally idempotent against replay through the state machine itself: a
  replayed cancel (already `cancelled`) fails the edge check (409 `invalid_status_transition`, terminal) — it
  never re-runs the side-effect. A replayed legal transition that lost the `version` race gets 409
  `concurrent_update`. The HIST write's `attribute_not_exists(sk)` guarantees at-most-one history row per
  `(from, to, actor, ts)` event (ORD-005 §7.2).
- **`release_hold`** (the cancel/no-show side-effect) is itself idempotent via HTL-011's status-CAS (HTL-011
  §5.6) — even a double-invocation never double-restores `held`.
- **`modify_reservation`** is **not** idempotent on its arguments (each successful modify mints a fresh
  `hold_id` and bumps `version`); a retried modify with the same args re-validates, swaps holds again, and bumps
  `version` again. Callers needing exactly-once must dedupe on the returned `version`. (The `version` CAS still
  guarantees no two concurrent modifies both commit — exactly one winner.)
- **`list_reservation_history`** is a pure read — naturally idempotent.

### 7.3 Security

- **Auth (router, HTL-020)**: all four lifecycle sub-routes + `modify_reservation` (PUT) are **mutations** →
  `require_admin_or_root_csrf` (`app/auth/policy.py:100`, verified) — role ∈ {ADMIN, ROOT} + cookie-CSRF.
  `list_reservation_history` (GET) is a **read** → `require_ui_session` (`app/services/sessions.py:330`,
  verified). The mutation handlers derive `actor` from the authenticated session (`ctx["user_sub"]`) — never a
  client-supplied field — so the HIST `actor` and the audit `actor` are always a valid Cognito sub (the ORD-005
  §7.3 `actor`-from-session pattern).
- **No service-layer ownership check**: the service does not verify the caller owns `hotel_id` (single-operator
  deployment assumption, consistent with HTL-011 §7.4 / HTL-017 §7.3 / PROP-001 §7.3). The HTL-020 router may add
  a `hotel_id`-scoped ownership / path-match check (the reservation's `hotel_id` must match the `{hotel_id}` path
  param → 404 on mismatch); multi-tenant isolation is a non-breaking additive follow-up (§10.1).
- **Flag-off is 404, not 401/403**: a probe against a disabled vertical learns only "not found" — no
  entity-existence leak (HTL-017 §7.3).
- **DynamoDB injection safety**: `UpdateExpression` / `ExpressionAttributeNames` / `ExpressionAttributeValues`
  reference all attributes by placeholder; no user value is interpolated into the expression string (the
  `app/services/kyc_cases.py` `update_item` pattern). `target_status` is constrained to the four literals by
  `ReservationTransitionIn` at the router edge and re-validated against `_RESERVATION_TRANSITIONS` in the service.

### 7.4 Money-safety — no money fork

HTL-019 issues **no** Stripe/PayPal/CCBill call and writes **no** ledger entry. `billing_shared`
(`new_ledger_entry`, `settle_or_reverse_ledger`, `apply_balance_delta`) and `refund_payment`
(`app/routers/billing.py`) are **not imported or called** anywhere in the HTL-019 additions. Cancel / no-show
**release held inventory only**; check-out releases physical rooms only; modify re-prices `total_cents` for
**display/record** but moves no money. The cancellation/no-show **refund + penalty** and any modify price-delta
settlement are **HTL-033** (Tier-3 forward ref), which routes through `refund_payment` /
`settle_or_reverse_ledger` — never a parallel mechanism (cross-cutting "no money fork",
`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:80-83`; ORD-001 §5.6 invariant). All money figures stay in
integer cents (the money-as-cents convention); there is no float money field. HTL-019 has **zero financial
invariants to enforce** — its hard invariant is the **state-machine + inventory-release correctness** (one
winner per transition; held inventory decremented at most once per cancel via HTL-011's idempotent
`release_hold`).

### 7.5 Audit trail

Every HTL-019 mutation emits a best-effort `_audit(...)` (the shared HTL-017 wrapper, itself copied from
`app/services/inventory.py:92-98`): `hotel.reservation.status_changed` (with `from_status`/`to_status`) on every
transition, and `hotel.reservation.modified` on a modify. Audit failure is swallowed and never propagates
(ORD-005 §7 best-effort). The HIST trail (§3.2) is the durable, queryable in-table record; the audit event is the
cross-cutting `T.alerts` emission.

  `ReservationHistoryEntry`) (additive; no existing model modified).

No existing endpoint, service function, DynamoDB **table**, **GSI**, **flag**, or Pydantic model is altered.
HTL-019 adds **no new table**, **no new GSI**, **no `attr_types` change** (the `HIST#` sort key is a base-table
String key, not a numeric GSI key — §3.2), and **no new settings**. With `HOTEL_PMS_ENABLED=false` (the default),
every HTL-019 function 404s — the running platform is byte-for-byte unchanged and produces zero DynamoDB traffic.

### 8.2 No DynamoDB migration

The `hotel_reservations` table (with its three GSIs + `attr_types={"created_at": "N"}`) is provisioned by HTL-018.
HTL-019 writes only child `HIST#` rows + header column updates on that existing table — no schema change, no new
index, no `attr_types` addition. `just restart` in dev requires nothing new for HTL-019 itself.

### 8.3 Production deployment sequence

1. Deploy the upstream clusters (HTL-001/005/006/010/011/012/015) + HTL-018 (the reservation table) with
   `HOTEL_PMS_ENABLED=false` — tables/indexes provisioned; all entrypoints 404.
2. Deploy HTL-019 with the flag still `false` — the lifecycle functions are defined but 404.
3. Enable `HOTEL_PMS_ENABLED=true` once the upstream tables/indexes are verified — the lifecycle (and the HTL-020
   sub-routes) become live.

Zero-downtime; full rollback at any step by toggling the flag.

### 8.4 Rollback

The fast operational rollback is `HOTEL_PMS_ENABLED=false` — every HTL-019 function 404s with no redeploy. A code
rollback reverts the two file changes (`hotel_reservations.py` additions, the three `models.py` additions).
HTL-019 owns no table and no flag, so there is nothing to drop. Any HIST rows already written remain on the
reservation partitions (sparse, ignored when the flag is off) — harmless; they are co-located children of headers
that are themselves invisible when the vertical is disabled.

### 8.5 Forward-dep ordering

HTL-019 is a **consumer** of HTL-011 (`release_hold`/`hold_rooms`), HTL-012 (`check_availability`), HTL-015
(`compute_stay_price`), and HTL-006 (`set_room_status`), and a **dependent** of HTL-018 (the reservation table +
`version` header + `hold_id` + `get_reservation`). It can be **merged** before the forward-dep clusters land (its
hermetic tests patch those collaborators, §9.1), but it cannot **run live** until they do. The parent doc's
dependency order (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:663-686`) places HTL-019 after HTL-018 (the
lifecycle needs the `version` header + `hold_id`) and before HTL-020 (the router).

## 10. Open Questions / Assumptions

1. **Multi-tenant `hotel_id` isolation.** The service does not check the caller owns `hotel_id`, nor that the
   reservation's `hotel_id` matches the HTL-020 `{hotel_id}` path param. **Assumption**: single-operator
   deployment (consistent with HTL-011 §10.4, HTL-017 §10.1, PROP-001 §10.2). A router-layer
   `item["hotel_id"] != path_hotel_id → 404` check and an owner check are non-breaking additive follow-ups for a
   multi-landlord SaaS.

2. **No-op modify behavior.** §5.7 leaves it optional whether `modify_reservation` with args equal to the
   current header short-circuits (return unchanged, no hold swap) or re-validates + re-prices the identical span
   (a harmless but wasteful hold swap). **Assumption**: short-circuit on a true no-op (all effective values equal
   the header) to avoid an unnecessary `hold_rooms`/`release_hold` round-trip; the implementer may simplify to
   always-process if the equality check is deemed not worth the branch.

3. **Confirm endpoint.** The parent doc (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md:515`) lists a
   `POST .../confirm` route as a no-op/idempotent confirm (a `confirmed` reservation is already confirmed;
   reserved for a future `draft → confirmed` step). **Assumption**: HTL-019's `_RESERVATION_TRANSITIONS` has no
   `draft` state and no inbound edge to `confirmed` (it is the create-time initial state); the confirm route is
   HTL-020's idempotent header-return, not an HTL-019 transition. A future `draft` pre-state is a non-breaking
   additive graph extension.

4. **Hold lifecycle after check-out.** §5.4 leaves the consumed hold un-released on check-out (the hold is the
   booking). **Assumption**: a consumed hold's `held` count remaining on the availability rows post-stay is
   correct (the room was occupied for those nights); whether a separate "settle hold → booked" verb should run at
   check-in (atomically `held -= q; booked += q`, the `inventory.commit_reservation` analogue,
   `app/services/inventory.py:456`, HTL-011 §10.3) is an HTL-018/HTL-011 question, not HTL-019's — HTL-019
   manipulates only the hold's terminal release on cancel/no-show.

5. **No-show timing automation.** `→ no_show` is a manual admin/system transition; HTL-019 does not auto-detect a
   no-show at end-of-arrival-day. **Assumption**: a scheduled "auto-no-show overdue arrivals" sweep (the
   `start_*_task` background-loop pattern, CLAUDE.md) is a separate front-desk/Tier-3 ticket; HTL-019 ships only
   the manual transition verb.

6. **`modify_reservation` partial vs full re-validation.** §4.4 re-checks availability + re-prices on **every**
   modify (even an occupancy-only change that does not alter the span). **Assumption**: always re-validating is
   the safe default (occupancy can affect price and even availability via per-occupancy room caps); a future
   optimization could skip `check_availability` when only `adults`/`children` change and the span/room_type are
   unchanged — a non-breaking refinement.

7. **History pagination cap.** `list_reservation_history` paginates via `encode_cursor`/`decode_cursor`
   (`app/core/cursor.py:94,103`). **Assumption**: a reservation accrues few HIST rows (≤ a handful of lifecycle
   events + modifies), so a single page (`limit=50`) is typical; the cursor loop guarantees completeness if a
   reservation is modified many times.

### 11.4 Contrasts (analogues, not dependencies)

| Analogue | Relationship |
|---|---|
| OFBiz **ORD** order lifecycle (`docs/ofbiz/specs/ORD-005.md`) | The structural template (transition graph + conditional-update CAS + HIST rows). **Differences**: ORD CASes on the `lifecycle_status` **string**; HTL-019 CASes on a numeric **`version`** counter (the KYC predicate, per the parent doc). ORD's terminal states are `cancelled`/`returned`; HTL-019's are `checked_out`/`cancelled`/`no_show`. | open-property **LSE** lease (`docs/open-property/specs/LSE-001.md` §4) | Lease `draft→active→ended` is a date-bounded tenancy state machine; HTL-019 reuses its allowlist **shape** but specializes to a room-night reservation (a lease is a months-long tenancy with informational rent; a reservation is a multi-night stay with physical-room assignment + an inventory hold to release). LSE CASes on `status`; HTL-019 on `version`. |
| KYC case state machine (`app/services/kyc_cases.py`) | Source of the numeric-`version` CAS predicate + the `ConditionalCheckFailedException` detector; not a domain dependency. |
