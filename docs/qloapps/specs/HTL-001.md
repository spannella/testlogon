# HTL-001 — Hotel entity — model, table, master flag

**Type**: Feature | **Priority**: P1 | **Estimate**: 1.5d
**Source**: `docs/qloapps/HOTELS_AMENITIES_TICKETS.md` §HTL-001 + the "Cross-cutting constraints" header + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A (rows 1 & 4)

---

## 1. Summary & Goal

HTL-001 is the P1 foundational ticket for the QloApps hotel-PMS hospitality vertical. It lands exactly three deliverables: (1) the `hotels` DynamoDB table with its two GSIs and the correct `attr_types`, (2) the `HOTEL_PMS_ENABLED` master feature flag with a `_flag_on()` / `_require_enabled()` 404 contract, and (3) the four service functions — `create_hotel`, `get_hotel`, `update_hotel`, `archive_hotel` — plus the Pydantic I/O models (`HotelIn`, `HotelOut`, `HotelUpdateIn`), the nested `HotelPolicies` / `HotelContact` models, and a shared `Address` model.

The Hotel entity is genuinely net-new: the gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §A) records the hospitality spine as **MISSING** — testlogon has no hospitality domain at all. The closest structural artefact is the open-property **Property** entity (`docs/open-property/specs/PROP-001.md`) and behind it the OFBiz **Facility** header (`docs/ofbiz/specs/FAC-001.md` §3). **HTL-001 reuses that table-shape and service idiom but NOT the semantics**: a Property carries rental real-estate fields (`address`/`property_type`/`occupancy_status`); a Hotel carries hospitality fields — `star_rating`, `check_in_time`/`check_out_time`, `policies` (cancellation/pet/smoking/children), `contact`, `photo_urls` — that no existing model has.

Without HTL-001 in place, no downstream HTL ticket (HTL-002 amenity catalog, HTL-003 router, HTL-004 frontend) can be implemented. With HTL-001 merged but `HOTEL_PMS_ENABLED=false` (the default), the platform is byte-for-byte unchanged: no new HTTP surface is exposed (the router is HTL-003's deliverable), and every service entrypoint 404s before touching DynamoDB.

The closest structural shadow is the open-property **Property** entity and the OFBiz **Facility** header (`docs/ofbiz/specs/FAC-001.md` §3) — a header entity (`*_id`, SK=`META`) co-located with child rows on the same partition. **The table shape is reused; the field set is not.** A `facilities` Facility models a warehouse with `LOC#{location_id}` child rows mapping to inventory bins (`docs/ofbiz/specs/FAC-001.md` §3, derivation at `:310` and `:83`); a `properties` Property models a rental building with dwelling Units. ### 2.6 TableDef pattern and `attr_types` requirement

`scripts/local-ddb-init.py:28–35` defines the `TableDef` dataclass; the file-level comment at `:34` reads: *"Override attribute types (default 'S'). Use for numeric keys, e.g. {'created_at': 'N'}"*. CLAUDE.md "DynamoDB numeric GSI sort keys" documents that omitting `attr_types` for a numeric GSI sort key causes DynamoDB to store the value as String, leading to `ValidationException` on integer queries at runtime. The `created_at` field is `N` (Unix integer from `now_ts()` at `app/core/time.py:2`) and is the sort key of both GSIs, so it **must** be declared in `attr_types`.

The existing `inventory` TableDef at `scripts/local-ddb-init.py:2457–2462` is the structural template (PK + GSI on `status`/numeric sort key); the `returns` TableDef at `:2483–2492` shows the `GSI_STATUS` (PK=`status`, SK=`created_at`) + `attr_types={"created_at": "N"}` shape HTL-001 mirrors.

## 3. Data Model

### 3.1 Table: `hotels`

Single DynamoDB table. The PK/SK design follows the FAC-001 `facilities` header+child idiom (`docs/ofbiz/specs/FAC-001.md` §3) and the PROP-001 `properties` analogue: a `META` row holds the hotel header, and child `AMEN#{amenity_id}` rows (added by HTL-002) co-locate on the same partition, enabling a cheap single-partition query for all rows of a hotel.

**Primary key**

| Key | Type | Value |
|---|---|---|
| `hotel_id` | S (PK) | `sha256(f"{owner_sub}\|{name}".encode()).hexdigest()[:32]` |
| `sk` | S (SK) | `"META"` (hotel header row) |

**Header row attributes**

| Attribute | DDB Type | Constraints / Notes |
|---|---|---|
| `hotel_id` | S | PK; derived deterministically (see §2.4) |
| `sk` | S | Always `"META"` for the hotel header |
| `owner_sub` | S | `user_sub` of the owning hotelier/admin |
| `name` | S | Human-readable hotel name; non-empty |
| `description` | S | Free-text description; may be empty string |
| `star_rating` | N | Integer 1–5 (validated `ge=1, le=5` in the Pydantic model) |
| `address` | M | Map: `{line1, line2?, city, region, postal_code, country}` |
| `check_in_time` | S | `"HH:MM"` 24h string; default `"15:00"`; validated `^([01]\d\|2[0-3]):[0-5]\d$` |
| `check_out_time` | S | `"HH:MM"` 24h string; default `"11:00"`; same pattern |
| `policies` | M | Map: `{cancellation_text: S, pet_policy: S, smoking: bool, children: bool}` |
| `contact` | M | Map: `{phone: S, email: S, website: S}` |
| `photo_urls` | L | List of photo URL strings; may be empty list |
| `status` | S | `active` \| `archived`; defaults `"active"` at create |
| `created_at` | N | `now_ts()` — integer Unix seconds (`app/core/time.py:2`) |
| `updated_at` | N | `now_ts()` — updated on every `update_hotel` / `archive_hotel` call |

**GSIs**

| Index name | PK | SK | Purpose |
|---|---|---|---|
| `GSI_OWNER` | `owner_sub` (S) | `created_at` (N) | List a hotelier's hotels newest-first — the primary list path (HTL-003 `list_hotels`) |
| `GSI_STATUS` | `status` (S) | `created_at` (N) | Admin listing by active/archived state |

Both GSIs project all attributes (`ALL` is the default for the moto/local create path; the `TableDef` GSI dicts carry only `index_name`/`partition_key`/`sort_key`, matching the existing entries at `scripts/local-ddb-init.py:2461,2489`).

**`attr_types`**: `{"created_at": "N"}` — mandatory per the CLAUDE.md DynamoDB numeric-GSI rule; omitting it causes `ValidationException` at runtime when `GSI_OWNER` or `GSI_STATUS` is queried with an integer `created_at` value.

**TableDef** (to be appended in `scripts/local-ddb-init.py` inside `_table_defs()`, following the `inventory`/`returns` pattern at `:2457–2462,2483–2492`):

```python
TableDef(
    _resolve_table_name(S.hotels_table_name, "hotels"),
    "hotel_id",
    "sk",
    gsi=[
        {"index_name": "GSI_OWNER",  "partition_key": "owner_sub", "sort_key": "created_at"},
        {"index_name": "GSI_STATUS", "partition_key": "status",    "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

Note: HTL-002 does NOT add a third GSI to this `TableDef` — its amenity-association rows are written as `AMEN#{amenity_id}` child rows on the existing `hotels` partition (a single-partition `begins_with("AMEN#")` query), and its dictionary lives in a separate `hotel_amenities` table with its own `GSI_CATEGORY`. So the HTL-001 `hotels` TableDef is final as written; HTL-002 only appends a new `hotel_amenities` TableDef.

**`create_hotel`**

```python
def create_hotel(
    owner_sub: str,
    *,
    name: str,
    description: str = "",
    star_rating: int = 3,
    address: dict,
    check_in_time: str = "15:00",
    check_out_time: str = "11:00",
    policies: dict | None = None,
    contact: dict | None = None,
    photo_urls: list[str] | None = None,
) -> dict:
```

- Calls `_require_enabled()`.
- Derives `hotel_id = _hotel_id(owner_sub, name)`.
- Builds the full item dict: all header attributes, `status="active"`, `created_at=now_ts()`, `updated_at=now_ts()`, `policies={}`/`contact={}` defaulted, `photo_urls=[]` defaulted.
- Calls `T.hotels.put_item(Item=item, ConditionExpression="attribute_not_exists(hotel_id)")`. On `ConditionalCheckFailedException`, reads and returns the existing item via `get_hotel(hotel_id)` — **idempotent** on (owner_sub, name). This mirrors the FAC facility-create contract (`docs/ofbiz/specs/FAC-001.md` §3 `:310`, `:481`).
- Emits `_audit("hotel.created", owner_sub, hotel_id=hotel_id, name=name)`.
- Returns the item dict (numeric fields coerced via `_to_int`).

**`get_hotel`**

```python
def get_hotel(hotel_id: str) -> dict | None:
```

- Calls `_require_enabled()`.
- `T.hotels.get_item(Key=_meta_key(hotel_id))`.
- Returns the coerced item or `None` if absent.

**`update_hotel`**

```python
def update_hotel(hotel_id: str, *, user_sub: str, **kwargs) -> dict:
```

- Calls `_require_enabled()`.
- Reads existing item; raises `HTTPException(404, "Hotel not found")` if absent.
- Filters `kwargs` to the allowed field set (`name`, `description`, `star_rating`, `address`, `check_in_time`, `check_out_time`, `policies`, `contact`, `photo_urls`), dropping `None` values.
- Builds an `UpdateExpression` `SET` over the supplied fields plus mandatory `updated_at=now_ts()`, using `ExpressionAttributeNames` for any reserved words (e.g. `#name`, `#status`).
- Calls `T.hotels.update_item(Key=_meta_key(hotel_id), ...)`.
- Emits `_audit("hotel.updated", user_sub, hotel_id=hotel_id, fields=list(kwargs.keys()))`.
- Re-reads and returns the updated item.

**`archive_hotel`**

```python
def archive_hotel(hotel_id: str, *, user_sub: str) -> dict:
```

- Calls `_require_enabled()`.
- Sets `status="archived"`, `updated_at=now_ts()` via `update_item` over `_meta_key(hotel_id)` (`SET #status = :s, updated_at = :u`).
- Emits `_audit("hotel.archived", user_sub, hotel_id=hotel_id)`.
- Returns the updated item.

Note: `list_hotels` (the `GSI_OWNER` query returning `{items, count, cursor}`) is a thin HTL-003 service addition per the HOTELS ticket; it is NOT an HTL-001 deliverable. HTL-001 ships only the four CRUD-style functions above.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent creation (owner+name collision)

`create_hotel` uses a DynamoDB conditional put (`attribute_not_exists(hotel_id)`). If two concurrent callers race for the same (owner_sub, name), exactly one write wins. The loser catches `ConditionalCheckFailedException` (via `botocore.exceptions.ClientError` with `error.response["Error"]["Code"] == "ConditionalCheckFailedException"`) and reads back the existing row — returning the same `hotel_id` as the winner. A caller may call `create_hotel` twice with identical arguments and receive the same `HotelOut` both times with no error. This is identical to the FAC facility-create and PROP-001 property-create contracts.

### 5.2 `address`, `policies`, `contact` stored as DynamoDB Maps (`M`)

These three dicts are stored as nested DynamoDB Maps. On read, boto3 returns them as Python dicts with the same keys. `HotelOut` serializes them via the `Address` / `HotelPolicies` / `HotelContact` models. Callers must not pass `None` values inside a Map — DynamoDB cannot store `None` as a Map value; omit the key or pass an empty string. (The Pydantic models default the optional sub-fields to `""` / `None`-omitted to satisfy this.)

### 5.3 `photo_urls` as List (`L`)

Stored as a DynamoDB List of strings. An empty list `[]` is a valid stored value and round-trips correctly (DynamoDB stores `[]` as an empty `L` attribute).

### 5.4 Numeric fields and Decimal coercion

`star_rating`, `created_at`, `updated_at` are stored as DynamoDB `N` and are returned by boto3 as `Decimal`. Service functions coerce them with `_to_int(...)` before returning. `HotelOut` integer fields typed as `int` also coerce automatically from `Decimal` at the Pydantic boundary, but the service layer normalizes first so raw dict consumers (the hermetic tests) see plain `int`.

### 5.5 `star_rating` and time-string validation live in the Pydantic layer

`star_rating` is constrained `ge=1, le=5` and `check_in_time`/`check_out_time` against `^([01]\d|2[0-3]):[0-5]\d$` in `HotelIn` / `HotelUpdateIn` (§3.2). An out-of-range rating or a malformed time string raises a Pydantic `ValidationError` → FastAPI returns **422** at the router boundary (HTL-003). The service functions accept already-validated values; they do not re-validate (the router's request model is the validation gate). A direct service caller (e.g. a test) passing `star_rating=7` is not blocked by the service — the constraint is a model-level contract, matching how `inventory.py` trusts its router-validated inputs.

### 5.6 `status` default and lifecycle

`status` is always `"active"` at create. `archive_hotel` flips it to `"archived"`. There is no "reactivate" function in HTL-001 (an admin can call `update_hotel(..., status="active")` only if `status` is added to the allowed-field set — it is **not** in the HTL-001 allow-list, deliberately, to keep archive a one-way audited transition; reactivation is a §10 open question).

### 5.7 `archive_hotel` is not a hard delete

`archive_hotel` sets `status="archived"`; no `delete_item` is issued. The hotel remains queryable via `get_hotel(hotel_id)` and appears in `GSI_STATUS` queries for `status="archived"`. Hard deletion is out of scope — it would have to cascade to HTL-002 `AMEN#` association child rows (and future Room Type / reservation rows), which HTL-001 has no knowledge of.

### 5.8 Flag-off behavior

When `HOTEL_PMS_ENABLED=false` (default), every call to any `hotel_pms.py` function raises `HTTPException(404, "Hotel PMS is not enabled")` before touching DynamoDB. The `hotels` table may or may not exist in DynamoDB — the flag check runs before any table access, so a flag-off platform never reads or writes the table even if it was created.

### 5.9 `update_hotel` with no changed fields

If `kwargs` is empty after filtering `None`s, the service still stamps `updated_at=now_ts()` (a single-field `SET updated_at = :u` update). This is intentional — it lets callers force a timestamp refresh. Raising 422 on empty kwargs is the documented alternative (§10). The router (HTL-003) always sends at least one field via `HotelUpdateIn` anyway.

### 5.10 `name` uniqueness scope

`hotel_id` is derived from (owner_sub, name). Two different hoteliers may have hotels with the same name — `owner_sub` disambiguates. A single hotelier cannot have two active hotels with the same name; the second `create_hotel` call returns the existing hotel (idempotent). Renaming a hotel via `update_hotel(name=...)` does **not** re-derive `hotel_id` (the PK is immutable once written) — the `hotel_id` stays bound to the original (owner_sub, original-name) tuple. A subsequent `create_hotel` with the new name would mint a different `hotel_id` (documented in §10).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_pms.py` must contain **no** `if S.dev_mode` branches. The same DynamoDB code path runs in dev (boto3 intercepted by moto in-process) and prod (real DynamoDB). This mirrors the explicit contract in `docs/qloapps/HOTELS_AMENITIES_TICKETS.md` §"Cross-cutting constraints" ("Zero `if S.dev_mode` branches in business logic; the same `T.*` handles in both environments") and the precedent in `app/services/inventory.py:27–28` (no `dev_mode` branch anywhere in that file). The `hotels` table handle (`T.hotels`) is identical in both environments — only the boto3 endpoint differs (moto vs real DDB), resolved transparently by `_safe_table` (`app/core/tables.py:65`).

### 7.2 Idempotency

`create_hotel` is idempotent on (owner_sub, name) via the conditional put + read-back-on-collision pattern, anchored on the deterministic `hotel_id = sha256(f"{owner_sub}|{name}")[:32]`. `update_hotel` and `archive_hotel` are unconditional — re-running them with the same payload produces the same final state (idempotent in result, not in `updated_at`, which advances on each call). The service deliberately exposes no `delete_hotel` function, preventing accidental data loss.

### 7.3 Security — ownership enforcement

`get_hotel` does not enforce that the caller owns the hotel (admin reads are unrestricted at the service layer). The HTL-003 router restricts mutations (`create`, `update`, `archive`) to `require_admin_or_root_csrf` (`app/auth/policy.py:100`), which requires `role ∈ {ADMIN, ROOT}` and a valid cookie CSRF token. This is appropriate for the initial single-platform vertical (one operator = one hotelier). For a multi-tenant hotelier scenario (a different hotelier cannot read/mutate another's hotels), an ownership check (`item["owner_sub"] != caller_sub → 403`) belongs in the HTL-003 router layer — flagged in §10. `owner_sub` is captured server-side from `user.sub` (never client-supplied), so even at the service layer a created hotel is correctly attributed.

### 7.4 Money-safety

HTL-001 does **not** touch any billing table, ledger entry, or payment primitive. The `billing_shared` money primitives (`new_ledger_entry`, `settle_or_reverse_ledger`, `apply_balance_delta`) are not imported or called. Money paths become relevant only in the far-downstream reservation/folio/deposit clusters (Tier 1+ in the gap analysis), which are explicitly out of scope here (`docs/qloapps/HOTELS_AMENITIES_TICKETS.md` lines 26–28). This ticket is purely a data-model + service foundation — there are no financial invariants to enforce.

### 7.5 Audit trail

Every service mutation emits a best-effort audit event via the `_audit()` wrapper (copied from `app/services/inventory.py:92–98`). Events: `hotel.created`, `hotel.updated`, `hotel.archived`. Audit failure (an exception from `audit_event`) is swallowed and never propagates to the caller. Reads (`get_hotel`) do not audit.

### 8.4 Rollback

Rolling back HTL-001 requires reverting the file changes (settings, tables, local-ddb-init, `hotel_pms.py`, `models.py`) and, in production, dropping the `hotels` table. Because the flag defaults to `false`, a partial rollback is also safe: keep the code deployed but ensure `HOTEL_PMS_ENABLED=false` — all service entrypoints 404 and no data is read or written.

## 10. Open Questions / Assumptions

1. **Existing `Address` model?** Verified (§2.7) that no plain `Address` model exists in `app/models.py` — only `AddressBase` (`:1411`, uses `state` not `region`, all-optional fields) and KYC/mailing variants. **Assumption**: add a new `Address` model with required `line1`/`city`/`region`/`postal_code`/`country`. If a future ticket introduces a colliding `Address`, rename to `HotelAddress` to avoid the clash.

2. **Multi-tenant hotelier isolation.** The current design lets any admin/root read any hotel via `get_hotel(hotel_id)`; the HTL-003 router does not enforce `user.sub == item["owner_sub"]`. For a single-platform deployment (one operator = one hotelier) this is fine. **Assumption**: single-platform deployment; cross-hotelier isolation deferred. If needed, add the ownership check in the HTL-003 router layer.

3. **`update_hotel` with empty kwargs.** **Assumption**: stamp `updated_at` silently (§5.9). The alternative — raise `HTTPException(422, "No fields to update")` — was considered and rejected because the router always sends at least one field via `HotelUpdateIn`.

4. **Renaming a hotel does not re-derive `hotel_id`.** `update_hotel(name=...)` changes only the `name` attribute; the PK stays bound to the original (owner_sub, original-name) hash (§5.10). **Assumption**: this is acceptable — the `hotel_id` is an opaque stable identifier and the deterministic derivation is only a creation-time idempotency device, not an ongoing invariant.

5. **`status` not in the `update_hotel` allow-list.** Archive is a one-way audited transition via `archive_hotel`; there is no reactivation path in HTL-001. **Assumption**: reactivation (`archived → active`) is a deliberate non-feature for now; if the product needs it, add an explicit `reactivate_hotel` function (audited) rather than allowing `status` through the generic update allow-list.

6. **`star_rating` / time validation lives only in the Pydantic layer.** A direct service caller can pass an out-of-range rating; only the router request model enforces 422. **Assumption**: this matches the `inventory.py` precedent (the service trusts router-validated inputs); tests cover both the model-level rejection and the service happy path.
