# HTL-031 — Deposit / partial payment policy + folio payment recording + folio PDF

**Type**: Feature | **Priority**: P1 | **Estimate**: 2.5d
**Source**: `docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md` §HTL-031 (`:325-459`) + "Cross-cutting constraints" (`:50-99`) + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §D (guest folio / booking invoice, `:101`) + Tier-3 cluster (`:150-156`)

---

## 1. Summary & Goal

HTL-031 adds the **money-movement layer** on top of the HTL-029 guest folio. It
ships five tightly-scoped deliverables, every one of which **reuses an existing
money primitive and never forks billing** (the cluster's absolute rule,
`docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md:73-78`):

1. **Deposit policy** — additive attributes on the folio `META` row
   (`deposit_policy_kind` ∈ `none|pct|fixed`, `deposit_pct_bps`,
   `deposit_fixed_cents`) plus a pure `compute_deposit_amount(folio) -> int`
   (the bps idiom from `S.invoices_tax_bps`, `invoices.py:306`). No new table.
2. **Atomic deposit hold** — `take_deposit(reservation_id, *, amount_cents=None,
   user_sub)` debits the guest wallet, writes an escrow sentinel row, and writes
   the paired ledger row in **one** `transact_write_items` (the TBT-001/003
   escrow pattern, `docs/ticket-bounty/specs/TBT-003.md` §"Atomic
   transact_write_items"). Insufficient balance → nothing written; a replay →
   already-held (the `attribute_not_exists(pk)` idempotency guard).
3. **`record_folio_payment(reservation_id, *, amount_cents, method, reference="",
   user_sub)`** — the RNT-002 thin wrapper over `new_ledger_entry`
   (`docs/open-property/specs/RNT-002.md` §4.1, `billing_shared.py:224`). One
   `hotel_payment` ledger row per call; `method="wallet"` deducts via the single
   `apply_wallet_delta` (`billing_shared.py:185`); external/cash methods are
   informational (no wallet move — RNT-002 §5.10 posture).
4. **Balance-due-on-arrival** — pure
   `balance_due_on_arrival(folio) = charges_total_cents - payments_total_cents -
   deposit_held_cents`, surfaced on `FolioOut` as `balance_due_on_arrival_cents`.
5. **Folio PDF** — `render_folio_pdf(reservation_id) -> bytes | None` assembles
   `get_folio` into the `invoices._render_invoice_lines` record shape and renders
   via the **dependency-free** `invoices._render_pdf` (`invoices.py:103,150`) — no
   new PDF dep (SECOPS-007 parity, mirrors `receipts.py`). Stored/served via the
   same S3 path the invoice PDF uses (`invoices._store_pdf` /
   `download_invoice_pdf`, `invoices.py:195,442`).

All five live in the **existing** `app/services/hotel_folios.py` (the HTL-029
file) — HTL-031 adds functions, no new service file. Pydantic models
(`DepositPolicyIn`, `TakeDepositIn`, `FolioPaymentIn`) and three additive
`FolioOut` fields go in `app/models.py`. The whole vertical stays gated behind the
**reused** `HOTEL_PMS_ENABLED` master flag (HTL-001; **no new flag**); with it off
every entrypoint 404s before touching DynamoDB and **no folio/ledger/escrow row is
ever written** (`docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md:52-60`).

The gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:101`) records the guest
folio / booking invoice as **PARTIAL**: "`invoices.py` (FIN-001: invoice#, line
items, tax, S3 PDF, `deposit` type); **no folio/running-stay-balance entity**."
HTL-029 landed the entity; HTL-031 lands the deposit/partial-payment money flow
the gap calls for — *reusing* the FIN-001 `deposit` invoice type and S3 PDF, the
TBT escrow hold, and the RNT-002 `record_payment` wrapper rather than building any
new money machinery.

## 2. Context & Current State

### 2.1 Gap — folio money flow is unbuilt; the primitives all exist

HTL-029 (`docs/qloapps/specs/HTL-029.md` §2.8) deliberately writes **no money
rows**: it seeds `payments_total_cents=0` and `deposit_held_cents=0` on the `META`
row and tracks `charges_total_cents` only. It never imports `billing_shared` and
records the cluster intent verbatim: "the actual payment rows are
`new_ledger_entry` ... on `T.billing` ... and the deposit hold is the TBT escrow
`transact_write_items` — both **HTL-031's** deliverables"
(`docs/qloapps/specs/HTL-029.md:196-198`). HTL-031 is exactly that follow-on.

The gap is *purely additive plumbing* — every money primitive HTL-031 needs is
already shipped and tested:

- **Single-entry ledger** — `new_ledger_entry(*, key_name, key_value, entry_type,
  amount_cents, state, reason, meta=, extra=) -> (sk, item)`
  (`app/services/billing_shared.py:224`). It **builds** the item (carrying
  `ts`, `entry_id=ulidish()`, `ledger_date` for `GSI_LEDGER_DATE`,
  `:253`) but does **not** write — the caller persists it via `ddb_put(T.billing,
  item)` (the RNT-002 contract, `docs/open-property/specs/RNT-002.md:276`; the
  stripe call-site precedent, `app/routers/billing.py:1126-1136`).
- **Atomic wallet debit** — `apply_wallet_delta(table, pk, delta_cents)`
  (`billing_shared.py:185`); for a withdrawal it uses
  `ConditionExpression="wallet_balance_cents >= :needed"` and raises
  `ConditionalCheckFailedException` on insufficient balance (`:203-212`).
- **Balance counters** — `apply_balance_delta(table, pk, {field: delta})`
  (`billing_shared.py:83`) atomically `if_not_exists`-`ADD`s onto the `BALANCE`
  row; `compute_due(balance_item)` (`:158`) derives `due_settled_cents`.
- **`user_pk(sub) -> "USER#{sub}"`** (`billing_shared.py:23`).
- **`deposit` invoice type** — already in `invoices.VALID_TYPES` (`invoices.py:33`)
  with the full `create_invoice` / `create_invoice_safe` path
  (`invoices.py:272,373`) that renders + stores an S3 PDF.
- **Dependency-free PDF** — `_render_pdf(lines)` (`invoices.py:103`) +
  `_render_invoice_lines(record)` (`invoices.py:150`) + `_store_pdf` (`:195`) +
  `download_invoice_pdf` / `_fetch_pdf` (`:442,204`).
- **Atomic multi-item write** — `transact_write_items` via the TBT-003 `_transact_client`
  / `_to_ddb_item` helpers (`group_treasury.py:716-740,47-53`,
  `docs/ticket-bounty/specs/TBT-003.md` §"Atomic transact_write_items precedent").

### 2.2 The escrow decision (TBT-001) — held vs. earned

A deposit is **held**, not yet **earned**. The cluster picks the TBT escrow option
over a bare ledger debit precisely to preserve that distinction
(`docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md:381-386`): the escrow sentinel makes a
later release/refund-at-checkout (a cancellation-cluster concern) a
`status`-guarded flip via `settle_or_reverse_ledger` (`billing_shared.py:262`),
exactly the TBT-006/007 model. TBT-001 §3.2 (`docs/ticket-bounty/specs/TBT-001.md:24-26`)
establishes that the escrow record is **co-located on `T.billing`** keyed
`pk=<DOMAIN>#{id}`, `sk="ESCROW"` — never a new money table. HTL-031 follows that
exactly with `pk=FOLIO_DEPOSIT#{reservation_id}`, `sk="ESCROW"`.

**Decision (recorded): escrow `transact_write_items`, NOT a plain ledger debit.**
Justification: (a) it preserves the held/earned semantics the cancellation cluster
needs; (b) it is replay-safe via `attribute_not_exists(pk)` on the escrow Put
(idempotent — no double-hold); (c) the wallet debit, escrow put, and paired ledger
row commit **atomically** so insufficient balance leaves nothing written; (d) it
reuses an existing, tested pattern (TBT-003) verbatim — no new money mechanism.

### 2.3 `record_folio_payment` reuses RNT-002 (no escrow)

A **payment** (deposit-applied, partial, or balance-at-checkout) is *settled*
immediately and is the RNT-002 `record_payment` case, not the escrow case
(`docs/open-property/specs/RNT-002.md` §4.1, `:227-298`). RNT-002 is a thin
`new_ledger_entry(state="settled")` wrapper + `apply_balance_delta` counter bump +
audit, with `method` informational for non-wallet methods (RNT-002 §5.10,
`:599-604`). HTL-031 mirrors that with one addition: `method="wallet"` actually
moves money via `apply_wallet_delta` (RNT-002 has no online provider; the hotel
guest may pay from their platform wallet).

### 2.4 `new_ledger_entry` builds, the caller writes — and the `key_name`/`pk` split

Critical reuse detail: `new_ledger_entry` returns `(sk, item)` and does **not**
write (`billing_shared.py:259`). Every call-site does `ddb_put(T.billing, item)`
(`app/routers/billing.py:1136`; RNT-002 `:276`). On the `T.billing` table the
hash attribute is `pk` (`billing_shared.ddb_get`/`ddb_put` key on `{"pk", "sk"}`,
`:27-36`), so `new_ledger_entry` is called with `key_name="pk",
key_value=user_pk(guest_sub)` and the wallet/escrow rows likewise key on `pk`.
`hotel_folios` keys on `reservation_id`/`sk` — **a different table** — so the folio
`META` counters are bumped with `update_item` on the `hotel_folios` handle, while
all money rows land on `T.billing`. HTL-031 never confuses the two partitions.

### 2.5 The HTL-029 folio entity (dependency) — extended in place

HTL-029 (`docs/qloapps/specs/HTL-029.md` §3) defines `hotel_folios`
(PK=`reservation_id`, SK=`META` header + `LINE#{line_id}` rows) with the
`META` counters HTL-031 bumps: `charges_total_cents`, `payments_total_cents` (`0`),
`deposit_held_cents` (`0`), `status`, `currency`, `guest_sub`, `hotel_id`. HTL-031
adds the deposit-policy attributes to the same `META` row (additive — no schema
change, §3.1) and reads the folio via the HTL-029 `get_folio(reservation_id)`
(`docs/qloapps/specs/HTL-029.md` §4.4), which authoritatively recomputes
`charges_total_cents` from the line rows and derives `balance_due_cents`.

### 2.6 Flag / audit / coerce idioms (reused from HTL-029)

`hotel_folios.py` already carries `_flag_on()` / `_require_enabled()` (the
`inventory.py:50-56` 404 contract with `hotel_pms_enabled` and the message
`"Hotel PMS is not enabled"`, `docs/qloapps/specs/HTL-029.md` §4.1), the `_audit()`
lazy-import wrapper (`inventory.py:92-98`), and `_to_int(...)` Decimal coercion
(`inventory.py:67`). HTL-031's new functions reuse all three verbatim — no new
helpers except the escrow `_transact_client` / `_to_ddb_item` borrowed from
`group_treasury.py` (§4.3).

### 2.7 What does NOT exist yet

`grep -n "take_deposit\|record_folio_payment\|render_folio_pdf\|compute_deposit_amount\|deposit_policy_kind"
app/services/hotel_folios.py app/models.py` returns nothing (HTL-029 ships only
`open_folio`/`add_line_item`/`get_folio`/`close_folio`). `grep -n
"DepositPolicyIn\|TakeDepositIn\|FolioPaymentIn" app/models.py` returns nothing.
No `FOLIO_DEPOSIT#` partition is written anywhere. HTL-031 introduces all of it,
additively, all gated behind the existing flag.

## 3. Data Model

HTL-031 adds **no new table**. It adds additive attributes to the existing
`hotel_folios` `META` row, writes money rows on the existing `T.billing` table, and
creates `deposit`-type invoices on the existing `T.invoices` table.

### 3.1 Deposit-policy attributes on the folio `META` row (`hotel_folios`)

Additive to the HTL-029 `META` header (PK=`reservation_id`, SK=`META`). All three
default-absent → treated as `none` by `compute_deposit_amount` (§4.1):

| Attribute | DDB Type | Constraints / Notes |
|---|---|---|
| `deposit_policy_kind` | S | `none` \| `pct` \| `fixed` (default `none` when absent). |
| `deposit_pct_bps` | N | Basis points (used when kind=`pct`); the bps idiom of `ticket_bounty_fee_bps` (TBT-001 §4.1) and `S.invoices_tax_bps` (`invoices.py:306`). `0`..`10_000`. |
| `deposit_fixed_cents` | N | Cents (used when kind=`fixed`); `ge=0`. |

HTL-029's existing `META` counters are the ones HTL-031 mutates:
`payments_total_cents` (bumped by `record_folio_payment`), `deposit_held_cents`
(bumped by `take_deposit`). No GSI change; `GSI_FOLIO_HOTEL` (HTL-029 §3.1) is
untouched (the new attributes are not GSI keys).

### 3.2 Escrow sentinel row (`T.billing`)

One row per reservation, co-located on `T.billing` (TBT-001 §3.2; never a new money
table). Keyed on the table's `pk`/`sk`:

| Attribute | DDB Type | Notes |
|---|---|---|
| `pk` | S | `FOLIO_DEPOSIT#{reservation_id}` (the escrow partition — distinct from the guest's `USER#{guest_sub}` money partition). |
| `sk` | S | `"ESCROW"` (fixed literal — exactly one escrow row per reservation). |
| `reservation_id` | S | Convenience copy. |
| `guest_sub` | S | The guest whose wallet was debited. |
| `hotel_id` | S | Denormalized for scoping. |
| `amount_cents` | N | Held amount. |
| `currency` | S | From the folio. |
| `status` | S | `"held"` (a later release/refund flips it via `settle_or_reverse_ledger`, cancellation cluster). |
| `ledger_sk` | S | The paired `LEDGER#{ts}#{entry_id}` sk (for release/audit join). |
| `created_at` | N | `now_ts()`. |

**Sparse to `GSI_LEDGER_DATE`** — it sets **no** `ledger_date`, so the platform
financial scan (`scripts/local-ddb-init.py:72`, `app/services/platform_financial_dashboard.py`)
never buckets the escrow sentinel (TBT-001 §"Verification" row 12,
`docs/ticket-bounty/specs/TBT-001.md:415`).

### 3.3 Deposit ledger row (`T.billing`) — via `new_ledger_entry`

Built by `new_ledger_entry(key_name="pk", key_value=user_pk(guest_sub),
entry_type="hotel_deposit", amount_cents, state="held",
reason=f"Hotel deposit — reservation {reservation_id}", extra={...})`
(`billing_shared.py:224`). Lands at `pk=USER#{guest_sub}`,
`sk=LEDGER#{ts}#{entry_id}`. Carries `ledger_date` (set by `new_ledger_entry:253`)
so it **does** appear in the dashboard, and `provider="wallet"` (FIN-013/GAP-0203
attribution, `billing_shared.py:235-238`) so the provider breakdown buckets it
correctly:

```
extra = {"reservation_id": reservation_id, "hotel_id": hotel_id,
         "provider": "wallet", "escrow_state": "held"}
```

### 3.4 Payment ledger row (`T.billing`) — via `new_ledger_entry`

`new_ledger_entry(key_name="pk", key_value=user_pk(guest_sub),
entry_type="hotel_payment", amount_cents, state="settled",
reason=f"Hotel payment — reservation {reservation_id}", extra={...})`:

```
extra = {"reservation_id": reservation_id, "hotel_id": hotel_id,
```

### 3.5 `deposit`-type invoice (`T.invoices`)

`take_deposit` creates a `deposit` invoice via `invoices.create_invoice_safe(...)`
(the `deposit` type already in `VALID_TYPES`, `invoices.py:33`; the safe wrapper
never raises, `:373`) for the deposit-receipt PDF — reusing FIN-001 wholesale,
no new invoice code.

## 4. API / Service Design

All functions are added to the **existing** `app/services/hotel_folios.py`. Every
entrypoint calls `_require_enabled()` **first** (404 when the flag is off, before
any table access). **No `if S.dev_mode` branch anywhere** (SECOPS-007, §7.1).

### 4.1 `compute_deposit_amount(folio: dict) -> int` (pure)

```python
def compute_deposit_amount(folio: Dict[str, Any]) -> int:
    kind = folio.get("deposit_policy_kind", "none")
    charges = _to_int(folio.get("charges_total_cents"))
    if kind == "pct":
        return charges * _to_int(folio.get("deposit_pct_bps")) // 10_000
    if kind == "fixed":
        return _to_int(folio.get("deposit_fixed_cents"))
    return 0
```

Mirrors the FIN-001 tax computation `amount * bps // 10_000` (`invoices.py:306`).
Pure, deterministic, no DDB. Integer floor division (banker-floor; never a float).

### 4.2 `set_deposit_policy(reservation_id, *, kind, pct_bps=0, fixed_cents=0, user_sub) -> dict`

1. `_require_enabled()`.
2. Validate `kind in {"none","pct","fixed"}` (422 — also enforced by
   `DepositPolicyIn.Literal`); `0 <= pct_bps <= 10_000` (422);
   `fixed_cents >= 0` (422).
3. **Conditional** `update_item` on the `META` row
   (`Key={"reservation_id": rid, "sk": "META"}`):
   `UpdateExpression="SET deposit_policy_kind = :k, deposit_pct_bps = :p,
   deposit_fixed_cents = :f, updated_at = :t"`,
   `ConditionExpression="attribute_exists(sk) AND #s = :open"`
   (`#s` → `status`, `:open="open"`). Missing folio → `ConditionalCheckFailed` →
   **404** `"Folio not found"`; closed folio → **409** `"Folio is closed"`
   (distinguished by a prior `get_item` existence check — §5.8).
4. `_audit("hotel.folio.deposit_policy_set", user_sub, reservation_id=..., kind=...,
   pct_bps=..., fixed_cents=...)`.
5. Return `get_folio(reservation_id)` (HTL-029 §4.4).

### 4.3 `take_deposit(reservation_id, *, amount_cents=None, user_sub) -> dict`

The **atomic deposit hold** — the TBT-003 escrow pattern
(`docs/ticket-bounty/specs/TBT-003.md` §"Atomic transact_write_items").

1. `_require_enabled()`.
2. `folio = get_folio(reservation_id)` → **404** `"Folio not found"` if `None`;
   **409** `"Folio is closed"` if `folio["status"] == "closed"`.
3. Resolve `amount = _to_int(amount_cents) if amount_cents is not None else
   compute_deposit_amount(folio)`. Reject `amount <= 0` → **422**
   `"Deposit amount must be positive"` (a `none`-policy folio with no override
   yields `0` → 422; the router surfaces "set a deposit policy first"). Reject
   `amount > folio["balance_due_cents"]` → **422** `"Deposit exceeds balance due"`
   (never hold more than owed).
4. Pre-compute the ledger row (so its `sk`/`ts` are known for the escrow's
   `ledger_sk` back-reference):
   ```python
   guest_sub = folio["guest_sub"]; currency = folio["currency"]
   led_sk, led_item = new_ledger_entry(
       key_name="pk", key_value=user_pk(guest_sub),
       entry_type="hotel_deposit", amount_cents=amount, state="held",
       reason=f"Hotel deposit — reservation {reservation_id}",
       extra={"reservation_id": reservation_id, "hotel_id": folio["hotel_id"],
              "provider": "wallet", "escrow_state": "held"},
   )
   ```
5. **One `transact_write_items`** (3 items, ≤ 25; via `_transact_client()` +
   `_to_ddb_item(...)`, copied from `group_treasury.py:716-740,47-53`,
   `docs/ticket-bounty/specs/TBT-003.md` §232-242), atomically:

   **(a) Wallet debit** — `Update` on `pk=USER#{guest_sub}` / `sk=WALLET`:
   ```
   UpdateExpression:  SET wallet_balance_cents = wallet_balance_cents + :neg, updated_at = :t
   ConditionExpression: wallet_balance_cents >= :amt
   values: {":neg": -amount, ":amt": amount, ":t": ts}
   ```
   The same guard as `apply_wallet_delta` (`billing_shared.py:203-212`) expressed
   as a transact Update item. No wallet row, or balance < amount → condition fails
   → whole transact rolls back → **402** `"Insufficient wallet balance"`.

   **(b) Escrow put** — `Put` on `pk=FOLIO_DEPOSIT#{reservation_id}` / `sk=ESCROW`
   (the §3.2 item), `ConditionExpression="attribute_not_exists(pk)"`
   (idempotency — a second `take_deposit` fails here → already-held).

   **(c) Ledger put** — `Put` of `led_item` (§3.3),
   `ConditionExpression="attribute_not_exists(sk)"` (belt-and-suspenders — the
   `ulidish()` sk is unique).

6. **Error handling** (mirrors TBT-003 `:401-419`):
   ```python
   except ClientError as exc:
       if exc.response["Error"]["Code"] == "TransactionCanceledException":
           reasons = exc.response.get("CancellationReasons", [])
           if reasons and reasons[0].get("Code") == "ConditionalCheckFailed":
               raise HTTPException(402, "Insufficient wallet balance")   # item (a)
           if len(reasons) > 1 and reasons[1].get("Code") == "ConditionalCheckFailed":
               raise HTTPException(409, "Deposit already held")          # item (b)
       raise
   ```
7. **After the transact succeeds** (best-effort, outside the atomic boundary —
   different table, cannot be in the same transact, TBT-003 §"Step 8"
   `:426-461`): bump the folio `META`
   `deposit_held_cents` atomically:
   ```python
   T.hotel_folios.update_item(
       Key={"reservation_id": reservation_id, "sk": "META"},
       UpdateExpression="ADD deposit_held_cents :amt SET updated_at = :t",
       ExpressionAttributeValues={":amt": amount, ":t": now_ts()},
   )
   ```
   then create the deposit-receipt invoice:
   ```python
   invoices.create_invoice_safe(
       user_sub=guest_sub, invoice_type="deposit", amount_cents=amount,
       line_items=[{"description": f"Deposit — reservation {reservation_id}",
                    "quantity": 1, "amount_cents": amount}],
       ledger_entry_id=led_item["entry_id"], currency=currency,
   )   # never raises (:373); :289 idempotency on ledger_entry_id
   ```
8. `_audit("hotel.folio.deposit_held", user_sub, reservation_id=...,
   amount_cents=amount, ledger_sk=led_sk)`.
9. Return `get_folio(reservation_id)` (now with `deposit_held_cents` bumped).

### 4.4 `record_folio_payment(reservation_id, *, amount_cents, method, reference="", user_sub) -> dict`

The RNT-002 thin wrapper (`docs/open-property/specs/RNT-002.md` §4.1).

1. `_require_enabled()`.
2. `folio = get_folio(reservation_id)` → **404** if `None`; **409** if `closed`.
3. Validate `amount_cents >= 1` (**422**); `method in _PAYMENT_METHODS`
   (`{"wallet","card_external","cash","check","bank_transfer","deposit_applied"}`,
   **422** — also enforced by `FolioPaymentIn.Literal`).
4. Build + persist **one** ledger row (the §3.4 row):
   ```python
   guest_sub = folio["guest_sub"]; currency = folio["currency"]
   led_sk, led_item = new_ledger_entry(
       key_name="pk", key_value=user_pk(guest_sub),
       entry_type="hotel_payment", amount_cents=amount_cents, state="settled",
       reason=f"Hotel payment — reservation {reservation_id}",
       extra={"reservation_id": reservation_id, "hotel_id": folio["hotel_id"],
              "method": method, "reference": reference,
              "provider": "wallet" if method == "wallet" else method},
   )
   ```
5. **Wallet move (only `method == "wallet"`)** — `apply_wallet_delta(T.billing,
   user_pk(guest_sub), -amount_cents)` (`billing_shared.py:185`), the **only**
   wallet write path; raises `ConditionalCheckFailedException` on insufficient
   balance → caught → **402** `"Insufficient wallet balance"` **before** the
   ledger row is written (order: wallet-debit first, then `ddb_put` the ledger row,
   so a failed wallet move leaves no orphan ledger row — §5.4). For
   external/cash/check/bank_transfer/deposit_applied: **no** wallet move (RNT-002
   §5.10 informational posture, `:599-604`).
6. `ddb_put(T.billing, led_item)` — the single ledger write
   (`billing_shared.py:32`; the RNT-002 `:276` / stripe `app/routers/billing.py:1136`
   precedent).
7. Bump the BALANCE counter: `apply_balance_delta(T.billing, user_pk(guest_sub),
   {"payments_settled_cents": amount_cents}, currency=currency)`
   (`billing_shared.py:83`).
8. Bump the folio `META` `payments_total_cents` atomically:
   ```python
   T.hotel_folios.update_item(
       Key={"reservation_id": reservation_id, "sk": "META"},
       UpdateExpression="ADD payments_total_cents :amt SET updated_at = :t",
       ExpressionAttributeValues={":amt": amount_cents, ":t": now_ts()},
   )
   ```
9. `_audit("hotel.folio.payment_recorded", user_sub, reservation_id=...,
   amount_cents=amount_cents, method=method, reference=reference, ledger_sk=led_sk)`.
10. Return `get_folio(reservation_id)` (with the new `balance_due_cents`).

### 4.5 `balance_due_on_arrival(folio: dict) -> int` (pure)

```python
def balance_due_on_arrival(folio: Dict[str, Any]) -> int:
    return (_to_int(folio.get("charges_total_cents"))
            - _to_int(folio.get("payments_total_cents"))
            - _to_int(folio.get("deposit_held_cents")))
```

The held deposit is **credited** against the arrival balance even though it is not
yet settled (it will be applied at check-in/checkout). Surfaced on `FolioOut` as
`balance_due_on_arrival_cents`; computed by `get_folio` after it has resolved the
header counters (§5.6).

## 5. Detailed Behavior & Edge Cases

### 5.1 `take_deposit` is atomic — insufficient balance writes nothing

The wallet debit (item a), escrow put (item b), and ledger put (item c) commit in
**one** `transact_write_items`. If the guest's `wallet_balance_cents < amount` (or
no wallet row exists), item (a)'s `ConditionExpression` fails →
`TransactionCanceledException` → the **entire** transaction rolls back: no wallet
change, **no** escrow row, **no** ledger row (`docs/ticket-bounty/specs/TBT-003.md`
§"No wallet row at all", `:493`). The caller gets **402**. A test asserts the
wallet balance is unchanged and `T.billing` has no `FOLIO_DEPOSIT#` /
`hotel_deposit` row after a 402.

### 5.2 `take_deposit` is idempotent — no double-hold

The escrow Put carries `ConditionExpression="attribute_not_exists(pk)"`. A second
`take_deposit` for the same `reservation_id` fails item (b) →
`TransactionCanceledException` with `CancellationReasons[1].Code ==
"ConditionalCheckFailed"` → caught → **409** `"Deposit already held"`. The wallet
is **not** debited a second time (the whole transact rolls back), so a deposit can
never be taken twice — no double-charge. (A release/refund-then-re-hold is a
cancellation-cluster concern that would first flip the escrow `status`.)

### 5.3 `take_deposit` rejects over-hold and non-positive amounts

`amount > balance_due_cents` → **422** (never hold more than owed). `amount <= 0`
(a `none`-policy folio with no override, or `pct`-on-zero-charges) → **422**. The
guard runs *before* the transact, so no money moves on a rejected amount.

### 5.4 `record_folio_payment` — wallet move is exactly once, no double-debit

For `method="wallet"`, the **single** `apply_wallet_delta(..., -amount_cents)`
deducts exactly `amount_cents` once (the atomic `update_item`, not a
read-modify-write, `billing_shared.py:206-212`). The wallet debit runs **before**
`ddb_put(led_item)`, so an insufficient-balance failure (402) leaves **no** ledger
row and **no** counter bump. `record_folio_payment` is intentionally **not**
dedup-keyed (each call is a distinct payment event — RNT-002 §7.5,
`docs/open-property/specs/RNT-002.md`); two calls record two payments. A test
asserts the wallet drops by exactly `amount_cents` per call (no double-debit) and
that for non-wallet methods the wallet is untouched (informational ledger only —
RNT-002 §5.10).

### 5.5 Non-wallet methods are informational

`method in {card_external, cash, check, bank_transfer, deposit_applied}` writes the
`hotel_payment` ledger row + bumps `payments_total_cents` + the BALANCE counter,
but moves **no** wallet money — the guest paid out-of-band (front-desk cash, an
external card terminal) or applied an already-held deposit. `deposit_applied` is
the front-desk action of crediting the held deposit toward the stay at checkout;
HTL-031 records it as a payment but does **not** auto-release the escrow (the
escrow `status` flip is the cancellation/checkout cluster's job — §10 Q2).

### 5.6 `balance_due_cents` vs. `balance_due_on_arrival_cents`

`get_folio` (HTL-029 §4.4) derives `balance_due_cents = charges_total_cents -
payments_total_cents`. HTL-031 adds `balance_due_on_arrival_cents =
charges_total_cents - payments_total_cents - deposit_held_cents` (§4.5) — the held
deposit is credited even though unsettled. Both can be **negative** (overpayment /
deposit larger than the stay) and HTL-031 does **not** clamp them (a clamp would
hide a refund-due; the cancellation cluster reads the negative balance —
`docs/qloapps/specs/HTL-029.md:561-569`).

### 5.7 Flag-off behavior

With `HOTEL_PMS_ENABLED=false` (default): `set_deposit_policy`, `take_deposit`,
`record_folio_payment` raise `HTTPException(404, "Hotel PMS is not enabled")`
before any table access; `render_folio_pdf` returns `None`;
`compute_deposit_amount` / `balance_due_on_arrival` are pure and never called
through a router when off. **No folio, ledger, escrow, wallet, balance, invoice, or
audit row is written.** The platform is byte-for-byte unchanged
(`docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md:52-60`).

### 5.8 404 vs. 409 disambiguation

`take_deposit` / `record_folio_payment` load the folio via `get_folio` first
(`None` → 404; `status=="closed"` → 409) before any money move. `set_deposit_policy`
uses a conditional `update_item` and disambiguates a `ConditionalCheckFailed` by a
prior `get_item` existence probe (absent → 404; present-but-closed → 409) — the
HTL-029 `close_folio` `:516-518` disambiguation idiom.

### 5.9 Folio PDF tax handling

A folio's tax/fee is carried as explicit `tax`/`fee` `LINE#` rows (HTL-029 §3.1,
`line_type` literal) already summed into `charges_total_cents`. So the PDF sets
`record["tax_cents"] = 0` and `record["total_cents"] = charges_total_cents` — the
tax line already appears as a line item; double-counting it as a `Tax:` subtotal
would inflate the total. (This differs from `invoices.create_invoice`, which adds
`S.invoices_tax_bps` tax *on top* of `amount_cents` — the folio already has tax in
its lines.)

### 5.10 Escrow row is sparse to the financial dashboard

The `FOLIO_DEPOSIT#` escrow sentinel sets **no** `ledger_date`, so it is omitted
from `GSI_LEDGER_DATE` and never appears in the platform financial scan
(`app/services/platform_financial_dashboard.py`; TBT-001 verification row 12). The
paired **ledger** row *does* carry `ledger_date` (set by `new_ledger_entry:253`)
and `provider="wallet"`, so the dashboard sees the deposit once, attributed
correctly.

### 5.11 Decimal coercion

DDB returns `N` as `Decimal`. `compute_deposit_amount`, `balance_due_on_arrival`,
and all reads coerce via `_to_int` (HTL-029 §2.4) before arithmetic / before
populating `FolioOut`/PDF, so no `Decimal` leaks into the response or the PDF
`_money` formatting.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`hotel_folios.py`'s HTL-031 functions contain **no** `if S.dev_mode` branch. The
same DynamoDB code path runs in dev (boto3 intercepted by moto in-process) and prod
(real DynamoDB); the escrow `transact_write_items` runs against moto in dev and
real DynamoDB in prod (the `_transact_client` reads endpoint/region/creds from
`T.billing.meta.client`, so DynamoDB Local is used automatically in dev —
`docs/ticket-bounty/specs/TBT-003.md` §234-236). The folio PDF reuses the
dependency-free `invoices._render_pdf` (`invoices.py:103`) — identical bytes in dev
and prod (no `reportlab`/system deps, mirrors `receipts.py`). S3 is moto in-process
in dev, real S3 in prod, same `_store_pdf` call (`invoices.py:195`).

### 7.2 Idempotency

- **`take_deposit`** is idempotent on `reservation_id` via the escrow Put's
  `attribute_not_exists(pk)` guard (§5.2) — a replay → 409, no double-hold, no
  double-debit. The deposit invoice is idempotent on `ledger_entry_id`
  (`invoices.create_invoice` `:289,301-303`).
- **`set_deposit_policy`** is naturally idempotent (a re-set with the same values
  is a no-op-equivalent write).
- **`record_folio_payment`** is intentionally **not** idempotent — each call is a
  distinct payment event (RNT-002 §7.5). The wallet deduction is exactly the
  recorded amount, once, per call (a single `apply_wallet_delta` with the
  conditional guard, §5.4) — no over-deduction.
- **`render_folio_pdf`** is a pure read-render (trivially idempotent).

### 7.3 Security — auth split + ownership

HTL-031 ships **service only**; the HTL-032 router enforces auth (cluster
"Auth split", `docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md:82-85`): reads
(`render_folio_pdf`, folio GET) via `require_ui_session`
(`app/services/sessions.py:330`); mutations (`set_deposit_policy`, `take_deposit`,
`record_folio_payment`) via `require_admin_or_root_csrf` (`app/auth/policy.py:100`)
— identical to `app/routers/inventory.py:48,65,81`. Hotel staff (admin/root) take
deposits and record payments; a guest reads only their own folio/PDF (the router
checks `folio["guest_sub"] == caller.sub`, the HTL-029 §10 Q3 contract). Money
amounts are **server-validated**: `take_deposit` clamps to `<= balance_due_cents`
and `record_folio_payment` accepts only the explicit `amount_cents` (no
client-controlled wallet pk — `guest_sub` comes from the folio, never the request).

### 7.4 Money-safety — the single ledger mechanism

- **Every monetary attribute is integer cents** — `amount_cents`,
  `deposit_held_cents`, `payments_total_cents`, `deposit_pct_bps`,
  `deposit_fixed_cents`, `balance_due_on_arrival_cents` — matching `invoices._money`
  (`invoices.py:146`) and `billing_shared.py`. No float ever touches money;
  `compute_deposit_amount` uses integer floor division (`* bps // 10_000`).
- **No double-charge** — `take_deposit` is atomic + idempotent (§5.1, §5.2);
  `record_folio_payment`'s wallet move is exactly once per call (§5.4).
- **One refund/ledger mechanism, never forked** — every money move is
  `new_ledger_entry` (`billing_shared.py:224`) + `ddb_put`, `apply_wallet_delta`
  (`:185`), `apply_balance_delta` (`:83`), or the escrow `transact_write_items`
  (TBT-003). **No bespoke `put_item` constructs a ledger row** and **no
  `delete_item` is ever called on a ledger/escrow row** (a release/refund — out of
  scope, cancellation cluster — would reuse `settle_or_reverse_ledger`,
  `billing_shared.py:262`, and `refund_payment`, `billing.py:1287`, never a delete).
- **Atomicity across tables** — the wallet/escrow/ledger rows are one transact
  (all on `T.billing`); the folio `META` counter bump and invoice creation are
  best-effort *after* the transact (a different table cannot join a
  `transact_write_items`, TBT-003 §510), so a crash between them leaves the money
  authoritative (transact committed) and the denormalized counter recoverable
  (`get_folio` could re-derive `deposit_held_cents` from the escrow row — §10 Q3).

### 7.5 Audit trail

Every mutation emits a best-effort audit event via `_audit()` (HTL-029 §2.3):
`hotel.folio.deposit_policy_set`, `hotel.folio.deposit_held`,
`hotel.folio.payment_recorded`. Audit failure is swallowed and never propagates
(the lazy-import + bare-`except` contract, `inventory.py:92-98`).

**Test cases**

1. **`compute_deposit_amount`** — `pct` (bps=2000 on charges=30000) → 6000;

## 10. Open Questions / Assumptions

1. **Deposit method.** HTL-031 assumes the deposit is held from the guest's
   **platform wallet** (the `apply_wallet_delta`-style transact debit). **Assumption**:
   a guest who pays a deposit by external card has the front desk seed wallet
   balance first, or the deposit is recorded as a `record_folio_payment` with
   `method="card_external"` (informational) instead of an escrow hold. Online-card
   deposit capture (a Stripe PaymentIntent → escrow) is a forward extension reusing
   the `_fraud_gate` + provider path (`app/routers/billing.py`), out of scope here.

2. **`deposit_applied` does not auto-release the escrow.** Recording a
   `method="deposit_applied"` payment registers the credit but does **not** flip the
   `FOLIO_DEPOSIT#` escrow `status` (§5.5). **Assumption**: escrow release/settle
   (held → earned) is the cancellation/checkout cluster's job via
   `settle_or_reverse_ledger`. HTL-031 only *takes* and *records*; it never
   *releases*. (A naive double-credit — applying the deposit as a payment AND later
   releasing the escrow as revenue — must be avoided by the checkout cluster; noted
   for that ticket.)

3. **Counter authority on partial-crash.** `take_deposit` bumps `META`
   `deposit_held_cents` *after* the transact (different table, §7.4). **Assumption**:
   a crash between the transact and the counter bump leaves the escrow row
   authoritative; `get_folio` could optionally re-derive `deposit_held_cents` from
   the `FOLIO_DEPOSIT#` escrow row (as HTL-029's `get_folio` re-derives
   `charges_total_cents` from line rows, §5.4 of HTL-029) — a hedge worth adding in
   HTL-032 if the counter ever drifts. HTL-031 keeps the denormalized counter as the
   fast path.

4. **No platform-wide default deposit policy.** Deposit policy is per-folio
   (§3.1). **Assumption**: a global `S.hotel_default_deposit_pct_bps` applied at
   `open_folio` time is a forward extension; HTL-031 requires `set_deposit_policy`
   (or a `take_deposit` `amount_cents` override) per reservation.

5. **Folio PDF "invoice number".** `render_folio_pdf` uses `folio["folio_id"]` as
   the PDF's `invoice_number` field (a running-balance document, not a finalized
   invoice). **Assumption**: a *finalized* folio invoice (monotonic
   `_next_invoice_number`, FIN-001) is produced only at folio close (HTL-032 /
   checkout), via `invoices.create_invoice(invoice_type="shop"|"deposit", ...)`;
   the running PDF is a statement, not a numbered invoice.

6. **No `void`/negative payment.** HTL-031 ships no payment reversal (a refund is
   the correct accounting primitive, owned by the cancellation/refund cluster via
   `refund_payment` / `settle_or_reverse_ledger`). **Assumption**: corrections are
   reversals in a later ticket, never a `delete_item` on a `hotel_payment` row
   (§7.4).
