# HTL-027 — Public booking cart + checkout → reservation

**Type**: Feature | **Priority**: P0 | **Estimate**: 3d
**Source**: `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md` §HTL-027 + "Cross-cutting constraints" (`:24-71`) + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C (Booking-engine storefront, `:95`)

---

## 1. Summary & Goal

HTL-027 lands the **transactional spine** of the public booking funnel — the step that turns a
price quote into money and a confirmed room-night reservation. The gap analysis flags the
booking-engine storefront as **PARTIAL** (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:95`): "public
booking-link reserve (`calendar.py:1946-2043`) + ECM storefront availability/checkout specs +
real cart; no date+occupancy room-type search funnel." HTL-025/026 land the read-only browse +
search/quote surface; **HTL-027 lands the write path**: select room-nights into a booking cart →
collect guest details (create/reuse a Contact) → check out through the **existing**
cart→order→payment money path → on payment success create the reservation (HTL-018) and **hold
inventory** for the booked room-nights.

It ships exactly four deliverables:

1. **Five booking-cart service functions** in `app/services/hotel_storefront.py` (the module
   HTL-025 created): `create_booking_cart`, `add_room_to_cart`, `set_guest_details`,
   `get_booking_cart`, `checkout_booking_cart`. Each is a thin hospitality layer over the
   **existing** shop-cart primitives (`app/services/shoppingcart.py` `get_cart:237`,
   `add_item:311`, `purchase_cart:474`) and `commerce_order_service`
   (`app/services/commerce_order_service.py`) — the money path is **not forked**.
2. **The new public `booking_engine_router`** (`prefix="/booking-engine"`, no `/ui` prefix, no
   session dependency) — declared in the new `app/routers/booking_engine.py`, mounting all eight
   storefront endpoints (the three HTL-025/026 reads + the five HTL-027 cart/checkout writes).
3. **Registration in `app/main.py`** next to the other public routers — `calendar_public_router`
   / `calendar_public_event_router` (`app/main.py:60-61` import, `:595-596` include).
4. **Pydantic I/O models** in `app/models.py`: `BookingCartOut`, `AddRoomToCartIn`,
   `GuestDetailsIn`, `BookingCheckoutIn`, `BookingCheckoutResult`.

This is the reserve-on-checkout analogue of ECM-005's reservation-adjusted availability
(`docs/ofbiz/specs/ECM-005.md` §1) and clones the public booking-link reserve idiom
(`reserve_booking_slot`, `app/routers/calendar.py:1977-2043`: re-check → 409 → put → audit) —
but the terminal action is a multi-night room reservation + inventory hold, not a calendar event.

Like every HTL ticket, HTL-027 is **additive + flag-gated, default OFF**. Every service
entrypoint and every router handler calls `_require_enabled()` (the verbatim
`app/services/inventory.py:54-56` 404 contract, copied into `hotel_storefront.py` by HTL-025)
first, so with `HOTEL_PMS_ENABLED=false` (the default) all eight endpoints are silent HTTP-404
no-ops, the router is mounted but inert, and the platform is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Gap — there is a real cart and a real money path, but no booking funnel

The gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:95`) records the booking-engine storefront
as **PARTIAL** — the cart→order→payment money path, the public-booking-link reserve pattern, and
the ECM availability/checkout specs all exist, but nothing wires a *date+occupancy room-type
search → room-night cart → guest details → checkout → reservation + inventory hold* funnel.
Guests are already **HAVE (as person)** via Contacts (`:96`), to be reused (not re-modeled).

The two halves HTL-027 composes already exist:

- **The shop cart + money path.** `app/services/shoppingcart.py` is a fully working cart on the
  `shopping_cart` table (PK `USER#{user_sub}`, SK `CART#{cart_id}` / `CART#{cart_id}#ITEM#{sku}`,
  `shoppingcart.py:30-39`). `get_cart` (`:237`) reads a cart, `add_item` (`:311`) adds a line,
  `purchase_cart` (`:474`) settles a cart through `commerce_order_service.create_order_from_line_items`
  (`:580-594`, `commerce_order_service.py:132`) and is **already idempotent** on
  `(user_sub, cart_id)` via a canonical idempotency key (`_cart_purchase_idempotency_key:194`) and
  a `status == OPEN` conditional `update_item` (`:621-642`) — a re-run returns the original order
  with no second charge. HTL-027 reuses this verbatim.
- **The reservation + hold primitives.** HTL-018 `create_reservation(...)`
  (`docs/qloapps/specs/HTL-018.md` §4.2) re-checks availability (HTL-012), computes the stay price
  (HTL-015), **holds the room-nights** via HTL-011 `hold_rooms` (`docs/qloapps/specs/HTL-011.md`
  §4 line 208), then writes the `META` header with `status="confirmed"`, `version=1`, and the
  stored `hold_id`. The hold *is* the inventory-hold half — HTL-018 already calls `hold_rooms`
  before the header write (`docs/qloapps/specs/HTL-018.md` §5.1). HTL-027 therefore gets
  "inventory held on payment success" **for free** by calling `create_reservation` per line.

### 2.2 The public-router contract (the calendar `/booking` precedent)

The unauthenticated booking funnel mirrors `app/routers/calendar.py` `public_router`
(`prefix="/booking"`, `:88`), whose handlers take **no auth dependency**: `get_booking_link`
(`:1946`), `list_booking_openings` (`:1960`), `reserve_booking_slot` (`:1977`). Ownership of a
public resource is the resource id itself (the opaque `link_id`, resolved via `_load_booking_link`),
not a session. HTL-027's `booking_engine_router` is a parallel public router with its own prefix;
ownership of a booking cart is the opaque, hard-to-guess `booking_cart_id` (same posture). The
public routers register **separately** in `main.py` next to `calendar_public_router` /
`calendar_public_event_router` (`app/main.py:60-61` import, `:595-596` include) — NOT under
`/ui/*` (those carry `require_ui_session`).

### 2.3 The reserve-on-checkout idiom to clone (`reserve_booking_slot`)

`reserve_booking_slot` (`app/routers/calendar.py:1977-2043`) is the structural template for
`checkout_booking_cart`: it (1) loads the public resource, (2) re-checks availability at
reserve-time — `_calendar_openings` + `_slot_in_openings` — and **raises 409 if the slot is no
longer available** (`:1990-1991`), (3) `put_item`s the terminal record, (4) emits an audit event
(`:2035`). HTL-027's checkout re-validates every cart line via `quote_stay` (HTL-026) and 409s on a
sell-out between add and checkout (the same `:1990-1991` 409), settles the money path, then on
success creates the reservation + holds inventory, then audits — the hotel analogue of the same
four steps.

### 2.4 Flag/audit scaffolding — already present from HTL-025

The `HOTEL_PMS_ENABLED` master flag (`S.hotel_pms_enabled`, env `HOTEL_PMS_ENABLED`, default
`false`) and the `_flag_on()` / `_require_enabled()` 404 contract were landed by HTL-001
(`docs/qloapps/specs/HTL-001.md` §6, settings at `app/core/settings.py:251` per HTL-001 §2.7) and
copied verbatim into `app/services/hotel_storefront.py` by HTL-025 (per
`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:93-95`). The canonical source is
`app/services/inventory.py:50-56`:

```python
def _flag_on() -> bool:
    return bool(getattr(S, "hotel_pms_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Hotel PMS is not enabled")
```

The `_audit()` lazy-import wrapper (`app/services/inventory.py:92-98`) is likewise present from
HTL-025. HTL-027 **reuses** these — it does not re-define them. `checkout_booking_cart` emits
`hotel.booking.created` through the existing `_audit`.

### 2.5 The quote/availability re-check primitive (HTL-026 `quote_stay`)

HTL-026 `quote_stay(*, hotel_id, checkin, checkout, adults, children, rooms) -> dict`
(`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:160-172`) validates the hotel is published, validates
`checkout > checkin` (400 otherwise), and delegates to HTL-017 `search_stays` for the per-date
availability intersection + summed multi-night price, returning the storefront quote shape
(`results: [{room_type, available_rooms, per_night, total_price_cents, currency}]`, room types with
zero availability excluded). HTL-027 calls `quote_stay` at **two** points: at add-time
(`add_room_to_cart`, to lock the authoritative price + confirm availability — never trusting a
client-supplied price) and at checkout-time (`checkout_booking_cart`, as the final guard against a
sell-out). HTL-027 never re-implements availability or pricing — it composes by id.

### 2.6 The rate-limit bucket to reuse

The DDB rate-limit bucket `_bucket_limit(user_sub, sid, max_n, win)`
(`app/services/rate_limit.py:60`) is reused on the cart-mutation + checkout paths. Because the
endpoints are unauthenticated, the "subject" is the request client host (`request.client.host`),
exactly as HTL-026's search handler keys its bucket
(`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:184-193`). On bucket exhaustion the handler raises
**429** with `Retry-After`. The bucket is **fail-open** (`_bucket_limit` returns `True` when the
sessions table is unavailable, `rate_limit.py:60-61`) so a backing-store hiccup never blocks a
booking.

### 2.7 The fraud gate (when a charge happens)

The cart money path settles real money through `purchase_cart` → `commerce_order_service`. The
charge surface in the existing codebase already runs a fraud gate: `_fraud_gate(user_id, amount,
entry_type, req=..., enforce_block=...)` (`app/routers/billing.py:118-167`) runs a synchronous
freeze check (`fd.is_frozen` → 403, `:134-139`) plus `fd.evaluate_transaction` (→ 403 on
`action == "block"` when `enforce_block`, `:150-164`), gated by `FRAUD_DETECTION_ENABLED` /
`FRAUD_BLOCK_ENABLED` (CLAUDE.md "Billing charge paths are gated", GAP-0207). HTL-027's checkout
runs `_fraud_gate` **before** settling the cart when the booking results in an actual charge (§5.7,
§7.4) — the guest's `guest_party_id` (the Contact) is the fraud subject.

### 2.8 Guests reuse Contacts — but the public funnel has no logged-in owner

`set_guest_details` "creates or reuses a Contact" for the guest by email
(`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:252-255`; gap analysis §C row 5 "Guests / customers …
reuse"). **Important nuance discovered in code:** the current `contacts` table
(`app/routers/contacts.py:14`) is a *user↔user contact-list* keyed `owner_id` / `contact_id`
(`:101-110`), requiring an authenticated `require_ui_session` owner (`:85`) and modeling "Alice's
saved contact Bob," not a standalone guest-person record with an email lookup. The public booking
funnel has **no logged-in owner**. HTL-027 therefore resolves the guest as an **opaque
`guest_party_id`** (the HTL-018 §2.7 contract — an opaque FK to a person, no FK validation), minted
deterministically from the guest email so a repeat guest reuses the same id:
`guest_party_id = "guest_" + sha256(email_normalized).hexdigest()[:24]` (the
`commerce_order_service.py:67` `sha256(...)[:32]` derivation idiom). The guest name/email/phone/
address snapshot is stamped on the booking-cart parent row; the `guest_party_id` is what flows into
`create_reservation` and the `GSI_GUEST` booking-history index (`docs/qloapps/specs/HTL-018.md`
§3.1). Whether a platform-owned "guest Contact" row is *also* written is deferred to §10 (the
current contacts table cannot store an unauthenticated guest without a schema change owned by a
separate guest-CRM ticket).

### 2.9 What does NOT exist yet

`grep -rn "booking_engine\|create_booking_cart\|checkout_booking_cart\|BookingCartOut" app/`
returns nothing. `grep -n "hotel_storefront" app/core/tables.py app/core/settings.py` returns
nothing (HTL-025 is unbuilt, confirming HTL-027 is correctly sequenced behind it). HTL-027 adds the
five service functions onto HTL-025's `hotel_storefront.py`, the new
`app/routers/booking_engine.py`, the `main.py` registration, and the five Pydantic models. **No new
DynamoDB table** — the booking cart IS a shop cart on the existing `shopping_cart` table, with
hotel/stay/guest metadata stamped on the cart rows.

## 3. Data Model

### 3.1 No new table — the booking cart rides the `shopping_cart` table

HTL-027 introduces **no new DynamoDB table** (cross-cutting constraint
`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:270-272`: "The booking cart is the same `carts` table
the shop uses … booking metadata rides on the cart rows"). The booking cart is a standard shop cart
on the `shopping_cart` table (`S.shopping_cart_table_name`, `app/core/settings.py:811`; PK
`USER#{user_sub}`, SK `CART#{cart_id}` / `CART#{cart_id}#ITEM#{sku}`, `shoppingcart.py:30-39`),
created via `shoppingcart.start_cart` (`:256`). The booking funnel stamps extra attributes:

**Booking-cart parent row** (the `type="cart"` row written by `start_cart`, then patched by
`create_booking_cart` / `add_room_to_cart` / `set_guest_details` via `T.shopping_cart.update_item`).
New booking attributes (additive — existing shop carts never carry these):

| Attribute | DDB Type | Notes |
|---|---|---|
| `booking_cart_id` | S | `uuid4().hex` minted by `create_booking_cart`; the public, opaque cart handle (the ownership gate, §2.2). Stored alongside the shop cart's own `cart_id` |
| `booking_hotel_id` | S | The hotel this booking cart is for (one cart = one hotel; validated published at create) |
| `booking_kind` | S | Constant `"hotel_booking"` — discriminates a booking cart from a generic shop cart (so the shop UI never shows it and vice-versa) |
| `guest_party_id` | S | Opaque guest FK (§2.8), set by `set_guest_details` |
| `guest_snapshot` | M | `{name, email, phone, address?}` set by `set_guest_details` |
| `booking_owner_sub` | S | The synthetic owner sub the shop cart is keyed under (§3.2) |

**Booking-line item rows** (the `type="item"` rows written by `shoppingcart.add_item`). Each
room-night selection is **one cart line** (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:236-237`).
The stay metadata rides on the line payload (`add_item` passes through arbitrary payload keys,
`shoppingcart.py:339-364`), stored under a `scope`/`rental_metadata`-style map so it round-trips:

| Line attribute | Source | Notes |
|---|---|---|
| `sku` | derived | `f"ROOMNIGHT#{room_type_id}#{checkin}_{checkout}"` — deterministic per (room-type, span) so re-adding the same selection updates qty, not a duplicate line (`add_item` get-then-merge, `shoppingcart.py:317-337`) |
| `name` | room type | `f"{room_type_name} — {checkin}→{checkout} ({nights}n)"` (display) |
| `quantity` | `rooms` | number of rooms of this type |
| `unit_price_cents` | `quote_stay` | **server-derived** `total_price_cents` for ONE room across the span (never client-supplied, §5.3) |
| `booking_meta` (map) | `quote_stay` | `{room_type_id, checkin, checkout, adults, children, rooms, nights, currency}` — carried so checkout can re-quote + call `create_reservation` per line |

`shoppingcart.add_item` computes `line_total_cents = unit_price_cents * quantity` (the cart's
existing line math, `shoppingcart.py` `_validate_commercial_item_payload`), so the cart total is
the sum of room-night line totals — no bespoke pricing in `hotel_storefront.py`.

### 3.2 The synthetic cart owner (`booking_owner_sub`)

The shop cart is keyed by `USER#{user_sub}` (`shoppingcart.py:30-31`), but the public funnel has no
logged-in user. `create_booking_cart` keys the cart under a **synthetic owner sub** derived from the
`booking_cart_id`: `booking_owner_sub = f"booking_guest:{booking_cart_id}"`. This (a) makes
`get_cart(booking_owner_sub, cart_id)` resolvable from only the public `booking_cart_id` (the
service recomputes the owner from the id), (b) namespaces guest carts away from real users'
`USER#{sub}` partitions, and (c) keeps `purchase_cart`'s `(user_sub, cart_id)` idempotency key
(`shoppingcart.py:194`) stable across checkout retries for the same booking cart. The mapping
`booking_cart_id → (booking_owner_sub, cart_id)` is fully derivable (no extra index needed): both
the synthetic owner and the underlying `cart_id` are stored on the parent row and recomputable from
`booking_cart_id`.

## 4. API / Service Design

### 4.1 Service module: `app/services/hotel_storefront.py` (extended in place)

HTL-027 extends the file HTL-025 created. The flag/audit scaffolding (`_flag_on`,
`_require_enabled`, `_audit`), `public_get_hotel`, `public_list_room_types` (HTL-025), and
`quote_stay` (HTL-026) are already present. HTL-027 adds the five cart/checkout functions plus tiny
helpers (`_booking_owner_sub`, `_guest_party_id`, `_resolve_booking_cart`, `_booking_cart_out`).
The forward-dep services it composes are imported at **module level** on the `hotel_storefront`
namespace so the hermetic tests can patch the symbols (the KYC GAP-0262 patch-collaborators
pattern, `tests/test_gap_0262_0264_kyc_template_endpoints.py`): `shoppingcart` (`start_cart`,
`add_item`, `get_cart`, `purchase_cart`), `commerce_order_service` (transitively via
`purchase_cart`), and `create_reservation` + the inventory-hold (HTL-018, which itself calls HTL-011
`hold_rooms`). **No `if S.dev_mode` branch anywhere** — SECOPS-007 (§7.1).

**Helpers**

```python
def _booking_owner_sub(booking_cart_id: str) -> str:
    return f"booking_guest:{booking_cart_id}"

def _guest_party_id(email: str) -> str:
    import hashlib
    norm = (email or "").strip().lower()
    return "guest_" + hashlib.sha256(norm.encode()).hexdigest()[:24]

def _resolve_booking_cart(booking_cart_id: str) -> dict:
    """Load the booking-cart parent row from the public id (404 if absent / not a booking cart)."""
    owner = _booking_owner_sub(booking_cart_id)
    cart = shoppingcart.get_cart(owner, booking_cart_id)        # raises 404 (shoppingcart.py:241)
    if cart.get("booking_kind") != "hotel_booking":
        raise HTTPException(status_code=404, detail="Booking cart not found")
    return cart
```

Note `booking_cart_id` IS the underlying shop `cart_id` (one uuid, used for both) — so
`get_cart(owner, booking_cart_id)` resolves directly; no separate mapping row is needed.

### 4.2 `create_booking_cart`

```python
def create_booking_cart(*, hotel_id: str) -> dict:
    """Mint a booking cart for a published hotel."""
```

1. `_require_enabled()` — 404 when off, before any DDB.
2. `public_get_hotel(hotel_id)` (HTL-025) — validates the hotel is **published** (404 otherwise,
   the publication gate is the public-access control, `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:39`).
3. Mint `booking_cart_id = uuid4().hex`; `owner = _booking_owner_sub(booking_cart_id)`.
4. `cart = shoppingcart.start_cart(owner)` — but `start_cart` mints its own `cart_id`
   (`shoppingcart.py:257`). **Implementation note:** either (a) call `start_cart` then patch the
   parent row to also carry our `booking_cart_id`, OR (b) write the parent row directly with
   `T.shopping_cart.put_item` using `booking_cart_id` as the `cart_id` (preferred — keeps one uuid).
   The spec uses (b): one uuid is both `booking_cart_id` and the shop `cart_id`.
5. Patch booking metadata onto the parent row (`booking_cart_id`, `booking_hotel_id=hotel_id`,
   `booking_kind="hotel_booking"`, `booking_owner_sub=owner`) via `T.shopping_cart.update_item`.
6. `_audit("hotel.booking.cart_created", "system", booking_cart_id=booking_cart_id, hotel_id=hotel_id)`.
7. Return `_booking_cart_out(cart)`.

### 4.3 `add_room_to_cart`

```python
def add_room_to_cart(*, booking_cart_id: str, hotel_id: str, room_type_id: str,
                     checkin: str, checkout: str, adults: int = 1,
                     children: int = 0, rooms: int = 1) -> dict:
    """Re-quote (price + availability) and add one room-night selection as a cart line."""
```

1. `_require_enabled()`.
2. `cart = _resolve_booking_cart(booking_cart_id)`; assert `cart["booking_hotel_id"] == hotel_id`
   (one cart = one hotel; 409 / 422 on mismatch).
3. **Re-quote** — `quote = quote_stay(hotel_id=hotel_id, checkin=checkin, checkout=checkout,
   adults=adults, children=children, rooms=rooms)` (HTL-026). This locks the **authoritative**
   price + confirms availability at add-time — the price is **never** client-supplied (the same
   principle as `reserve_booking_slot` re-checking openings,
   `app/routers/calendar.py:1989-1991`). Find the `results` entry for `room_type_id`; if absent
   (zero availability across the span) → `HTTPException(409, {"code": "no_availability"})`.
4. Derive the line payload: `sku = f"ROOMNIGHT#{room_type_id}#{checkin}_{checkout}"`,
   `unit_price_cents = result["total_price_cents"] // rooms` (per-room span total; or carry the
   per-room total directly from `quote_stay`), `quantity = rooms`, plus the `booking_meta` map
   (§3.1). The price is the engine's output, surfaced verbatim.
5. `shoppingcart.add_item(_booking_owner_sub(booking_cart_id), booking_cart_id, payload)`
   (`shoppingcart.py:311`) — get-then-merge so re-adding the same (room-type, span) updates qty.
6. Return `_booking_cart_out(_resolve_booking_cart(booking_cart_id))` (re-read for the updated
   line set + total).

def set_guest_details(*, booking_cart_id: str, name: str, email: str,

### 4.5 `checkout_booking_cart`

```python
def checkout_booking_cart(*, booking_cart_id: str, payment_method_token: str | None = None,
                          idempotency_key: str | None = None, req=None) -> dict:
    """Final-guard availability, fraud-gate, settle the money path, then on success
    create one reservation per line + hold inventory."""
```

1. `_require_enabled()`.
2. `cart = _resolve_booking_cart(booking_cart_id)`; require a `guest_party_id` is set
   (`set_guest_details` ran) → 422 `guest_required` otherwise; require ≥1 line → 422 `empty_cart`.
3. `owner = _booking_owner_sub(booking_cart_id)`; `lines = shoppingcart.list_items(owner, booking_cart_id)`.
4. **Final availability re-validation** — for every line, call `quote_stay(...)` with the line's
   `booking_meta` (hotel/room-type/dates/occupancy) and confirm the room type is still in `results`
   with `available_rooms >= rooms`. A sell-out between add and checkout →
   `HTTPException(409, {"code": "no_availability", "room_type_id": ...})` — the
   `reserve_booking_slot:1990-1991` 409, **before** any charge or write. (The price is *not*
   silently re-priced at checkout — a frozen quote is the booking contract, HTL-018 §5.6; a
   material price drift is a §10 open question.)
5. **Idempotency short-circuit** — if `cart["status"] == "PURCHASED"`, return the recorded result
   (re-read `last_order_id` + stored `reservation_ids`) **without** charging or creating a second
   reservation (the §7.2 no-double-charge invariant). `purchase_cart` itself also short-circuits a
   purchased cart (`shoppingcart.py:483-492`), but HTL-027 must additionally guard the
   reservation-creation side so a retry never mints a second reservation/hold.
6. **Fraud gate (when a charge happens)** — if the booking total is > 0 and a charge will settle,
   run `_fraud_gate(guest_party_id, total_cents, "credit", req=req)`
   (`app/routers/billing.py:118`) — freeze check + `evaluate_transaction` block → 403, gated by
   `FRAUD_DETECTION_ENABLED` (§7.4). Runs **before** `purchase_cart`.
7. **Settle the money path (UNFORKED)** —
   `result = shoppingcart.purchase_cart(owner, booking_cart_id, idempotency_key=idempotency_key)`
   (`shoppingcart.py:474`). This creates the order via
   `commerce_order_service.create_order_from_line_items` (`:580`) and flips the cart to `PURCHASED`
   under a `status == OPEN` conditional (`:621-642`) — idempotent on `(owner, cart_id)`. `order_id =
   result["order_id"]`. **No forked payment path** (acceptance criterion,
   `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:312-313`).
8. **On payment success (and ONLY then) — per-line reservation + inventory hold.** For each line,
   call HTL-018 `create_reservation(hotel_id=..., guest_party_id=cart["guest_party_id"],
   room_type_id=..., checkin=..., checkout=..., adults=..., children=..., rooms=..., user_sub="system")`
   (`docs/qloapps/specs/HTL-018.md` §4.2). `create_reservation` **internally** holds inventory via
   HTL-011 `hold_rooms` before writing the `META` header (HTL-018 §5.1) — so HTL-027 gets the
   per-date room-night hold "for free." Collect `reservation_ids`. (Edge: a 409 from
   `create_reservation` here — a night sold out in the TOCTOU window after step 4 — is the §5.6
   "money settled but a room sold out" case; see §5.6 for the compensation policy.)
9. **Persist `reservation_ids` on the cart** — `update_item` the parent row with `reservation_ids`
   + `booking_confirmed_at = now_ts()` so a checkout retry (step 5) returns the same ids.
10. `_audit("hotel.booking.created", "system", booking_cart_id=booking_cart_id,
    order_id=order_id, reservation_ids=reservation_ids, total_cents=total_cents)`.
11. Return `BookingCheckoutResult(reservation_ids=..., order_id=order_id,
    total_price_cents=total_cents, currency=..., confirmation={...})`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Price + availability are locked server-side at add-time (never trust the client)

`add_room_to_cart` (§4.3) calls `quote_stay` (HTL-026) and writes the engine's
`total_price_cents` as the line price. The `AddRoomToCartIn` model has **no** price field. A
client cannot inject a discounted price; the line `unit_price_cents` is always the rate engine's
output. This is the `reserve_booking_slot:1989-1991` re-check principle applied to price, and the
acceptance criterion "client-supplied price is never trusted (re-quoted server-side)"
(`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:317-318`).

### 5.2 A booking cart is one hotel

`create_booking_cart` stamps `booking_hotel_id`; `add_room_to_cart` rejects (422/409) a line for a
different hotel. A guest booking two hotels uses two booking carts. This matches the storefront
funnel (search is per-hotel) and keeps `create_reservation` (one `hotel_id` per call) clean. A
multi-hotel "trip cart" is out of scope (§10).

### 5.3 One line per (room-type, span); re-add updates quantity

The line `sku = f"ROOMNIGHT#{room_type_id}#{checkin}_{checkout}"` is deterministic, so
`shoppingcart.add_item`'s get-then-merge (`shoppingcart.py:317-337`) increments `quantity` on a
re-add of the same selection rather than creating a duplicate line. Two different spans of the same
room type are two distinct lines.

### 5.4 Final availability guard at checkout — two distinct 409 sources

A sell-out can 409 at two checkout points:
- **§4.5 step 4** — `quote_stay` no longer lists the room type / `available_rooms < rooms`. Raises
  `409 {"code": "no_availability"}` **before** any charge or reservation write (the read-only
  pre-guard).
- **§4.5 step 8** — `create_reservation` itself 409s because a night sold out in the TOCTOU window
  after step 4 but before the per-line `hold_rooms` (HTL-018 §5.2 — `hold_rooms` is the
  authoritative atomic check and rolls itself back). This is the post-charge edge handled in §5.6.

### 5.5 On payment success and ONLY then — reservation + hold

`create_reservation` (and its internal `hold_rooms`) runs **after** `purchase_cart` returns a
settled order (§4.5 step 8). A failed/declined payment means `purchase_cart` does not return a
successful order (or raises), so step 8 is never reached: **no reservation is created and no
inventory is held** (acceptance criterion `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:314-316`).
Conversely the cart status flips to `PURCHASED` only inside `purchase_cart`'s conditional
(`shoppingcart.py:621-642`), so the "did the charge settle?" signal is the order existing — not a
separate flag HTL-027 maintains.

### 5.6 The "charge settled but a room sold out at hold-time" edge (post-step-7 409)

If a per-line `create_reservation` 409s in step 8 *after* `purchase_cart` already settled (a TOCTOU
sell-out that beat the step-4 pre-guard), the money has been captured but a room cannot be held.
HTL-027's policy: (a) any reservations already created for *earlier* lines stand and are returned;
(b) for the failed line, the booking is partially fulfilled — the handler records the failed
`room_type_id` in `confirmation.partial_failures` and emits
`_audit("hotel.booking.partial_hold_failure", ...)`; (c) the refund/compensation for the
unfulfilled line routes through the **existing** `refund_payment` (`app/routers/billing.py:1287`,
per the cross-cutting "no money fork" constraint) and is a Tier-3 follow-up — HTL-027 does **not**
fork a bespoke refund. Because step 4 is a tight pre-guard and `create_reservation` holds before it
writes (no orphan reservation), this edge is rare; it is documented, audited, and never silently
double-books. The simpler alternative (best-effort `purchase_cart` reversal) is a §10 open question.

### 5.7 Checkout is idempotent and never double-charges

A retried `checkout_booking_cart` for a `PURCHASED` cart short-circuits in §4.5 step 5, returning
the stored `order_id` + `reservation_ids` **without** a second charge or a second reservation.
This composes two guards: (a) `purchase_cart`'s own `status == OPEN` conditional + idempotency key
(`shoppingcart.py:194,621-642`) prevents a second order/charge; (b) HTL-027's `reservation_ids`
persistence (§4.5 step 9) prevents a second `create_reservation`/`hold_rooms`. See §7.2.

### 5.8 Flag-off behavior

When `HOTEL_PMS_ENABLED=false` (default), every service function and every router handler raises
`HTTPException(404, "Hotel PMS is not enabled")` via `_require_enabled()` before touching DynamoDB,
the cart, the rate-limit bucket, or any forward-dep service. All eight endpoints 404; the router is
mounted but inert (acceptance criterion `docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:321`).

### 5.9 The guest is opaque; no FK validation; no logged-in owner

`guest_party_id` is derived from the guest email and stored verbatim — no existence check against
any person store (§2.8, HTL-018 §5.10). The cart is keyed under the synthetic
`booking_guest:{booking_cart_id}` owner (§3.2), so the funnel works with zero authentication. A
returning guest (same email) reuses the same `guest_party_id`, so their reservations all land on
the one `GSI_GUEST` partition (booking history, HTL-018 §3.1).

### 5.10 Rate-limit fail-open

`_bucket_limit` returns `True` when the sessions table is unavailable (`rate_limit.py:60-61`), so a
backing-store hiccup never blocks a cart mutation or checkout (the HTL-026 fail-open posture). The
checkout cap is deliberately tighter (default 20/hour/client vs 120 for cart mutations) because
checkout touches the money path.

### 5.11 Empty / guest-less checkout

`checkout_booking_cart` 422s on an empty cart (`empty_cart`) or a cart with no `guest_party_id`
(`guest_required`) — before any charge — so the funnel can only settle a complete booking.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_storefront.py` (HTL-027 additions) and `app/routers/booking_engine.py` contain
**no** `if S.dev_mode` branch. The same code path runs in dev (moto intercepts boto3 in-process;
stripe-mock settles the cart) and prod (real DynamoDB; real Stripe), per the cross-cutting parity
constraint (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:58-61`) and the `app/services/inventory.py`
precedent (no `dev_mode` branch anywhere in that file). The reused `purchase_cart` /
`commerce_order_service` money path is already dev/prod-identical, and `create_reservation` /
`hold_rooms` own any mock/real divergence internally — HTL-027 calls them identically in both envs.

### 7.2 Idempotency — and no double-charge

Checkout is idempotent on the booking cart, with **two composed guards**:
1. **No double-order / no double-charge** — `purchase_cart` short-circuits a `PURCHASED` cart
   (`shoppingcart.py:483-492`) and flips status under a `status == OPEN` conditional `update_item`
   keyed on the canonical `cart_purchase:{owner}:{cart_id}` idempotency key
   (`shoppingcart.py:194,542,621-642`). A retried checkout returns the original order — the money
   path is settled exactly once.
2. **No second reservation / no second hold** — HTL-027 persists `reservation_ids` on the parent
   row (§4.5 step 9) and short-circuits in step 5 when the cart is already `PURCHASED`, so a retry
   never mints a second reservation or a second `hold_rooms` (HTL-011 `hold_rooms` is itself
   non-idempotent, `docs/qloapps/specs/HTL-011.md` §10 — guarding it here is mandatory).

`create_booking_cart` / `add_room_to_cart` / `set_guest_details` are simple state mutations
(re-running produces the same final state; `add_room_to_cart` get-then-merges by deterministic sku,
§5.3).

### 7.3 Security — unauth by design, opaque-id ownership, storefront-safe projection

All eight endpoints are unauthenticated (the public-funnel contract,
`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:297-301`). Ownership of a booking cart is the opaque,
hard-to-guess `booking_cart_id` (`uuid4().hex` → the synthetic `booking_guest:{id}` partition,
§3.2) — the same posture as the public booking-link `link_id`
(`app/routers/calendar.py:289-298,1946`). Reads return only the storefront-safe `BookingCartOut`
projection (§4.7) — `booking_owner_sub`, the raw shop `cart_id`, and internal txn/idempotency
fields are never exposed. Only **published** hotels are bookable (`public_get_hotel` 404s an
unpublished hotel — the publication gate is the access control,
`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:39`). The mutation + checkout paths are rate-limited per
client (429, §4.8) so the unauthenticated surface cannot be hammered.

### 7.4 Money-safety — no fork, fraud-gated charge, no double-charge, integer cents

- **No money fork.** Checkout settles exclusively through `shoppingcart.purchase_cart` →
  `commerce_order_service` (the existing path) — HTL-027 issues **no** direct Stripe/PayPal/CCBill
  call and writes **no** bespoke ledger entry (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:46-53`).
  Any refund/compensation (§5.6) routes through the existing `refund_payment`
  (`app/routers/billing.py:1287`).
- **Fraud-gated charge.** When the booking total > 0 and a charge will settle, `_fraud_gate`
  (`app/routers/billing.py:118-167`) runs **before** `purchase_cart` (§4.5 step 6): a frozen
  account or a `block` action → 403, gated by `FRAUD_DETECTION_ENABLED` / `FRAUD_BLOCK_ENABLED`
  (CLAUDE.md GAP-0207). The subject is the guest's `guest_party_id`.
- **No double-charge.** The §7.2 idempotency guards guarantee the cart settles exactly once across
  retries; the §5.5 "reservation only after settle" ordering guarantees a declined charge creates
  no reservation/hold.
- **Integer cents end-to-end.** The line `unit_price_cents` / `line_total_cents`, the cart total,
  `total_price_cents`, and the HTL-018 `total_cents` are all integer cents (the `shoppingcart`
  `_ddb_int` pattern, `:46`; HTL-015 `total_cents` is `int`) — no float-rounding money bug.

### 7.5 Audit trail

Every mutation emits a best-effort `_audit(...)` event (the `inventory.py:92-98` wrapper, present
from HTL-025): `hotel.booking.cart_created`, `hotel.booking.guest_set`, `hotel.booking.created`,
and (edge) `hotel.booking.partial_hold_failure`. The reused `purchase_cart` /
`commerce_order_service` (`commerce_order_created`, `commerce_order_service.py:106`) and
`create_reservation` / `hold_rooms` (`hotel.reservation.created` / `hotel.hold.created`,
`docs/qloapps/specs/HTL-018.md` §7.5, HTL-011 §4) emit their own events, so the order, reservation,
and inventory-hold sides of a booking are each independently audited. Audit failure is swallowed
and never propagates.

### 8.3 Production deployment

Because `HOTEL_PMS_ENABLED` defaults to `false`, HTL-027 can be deployed first (all eight endpoints
404) and the flag flipped after the upstream hotel/room-type/availability/rate-plan/reservation
tables are created + verified. No data migration is needed.

### 8.4 Rollback

Rolling back HTL-027 requires reverting the four file changes (settings, hotel_storefront.py
additions, booking_engine.py, main.py registration, models). A partial rollback is also safe: keep
the code deployed but ensure `HOTEL_PMS_ENABLED=false` — all eight endpoints 404 and no cart,
reservation, hold, or charge is touched. Because HTL-027 never forks the money path, a rollback has
no bespoke financial side effects; any in-flight holds self-expire via HTL-011's TTL sweep
(`docs/qloapps/specs/HTL-011.md` §4).

### 9.3 Acceptance criteria (from the ticket)

- A guest can: create a booking cart → add a room-night selection (price + availability locked at
  add-time via `quote_stay`) → set guest details (Contact created/reused) → checkout → receive
  `reservation_ids` + an order/confirmation
  (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:308-311`).
- Checkout settles through the existing `shoppingcart.purchase_cart` → `commerce_order_service`
  money path — NOT a forked payment path (`:312-313`).
- On payment success (and only then) `create_reservation` (HTL-018) is called per room-type line
  and per-date inventory is held; a failed/declined payment creates no reservation and holds no
  inventory (`:314-316`).
- A sell-out between add and checkout → 409; unpublished hotel → 404; client-supplied price is
  never trusted (re-quoted server-side) (`:317-318`).
- `booking_engine_router` imported + `include_router`'d in `app/main.py` next to the public
  routers; literal `/search` and `/cart` declared before dynamic `/{hotel_id}` (`:319-320`).
- All 8 endpoints 404 when `HOTEL_PMS_ENABLED=false` (handler no-op, router still mounted) (`:321`).
- Cart-mutation + checkout endpoints are rate-limited per client (429 on exhaustion) (`:322`).
- No `if S.dev_mode` branch in `hotel_storefront.py` / `booking_engine.py` (SECOPS-007).

## 10. Open Questions / Assumptions

1. **Guest "Contact" persistence vs. opaque `guest_party_id`.** The ticket says
   `set_guest_details` "creates or reuses a Contact"
   (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:252-255`). The current `contacts` table
   (`app/routers/contacts.py:14,85,101-110`) is a *user↔user contact-list* keyed
   `owner_id`/`contact_id` requiring an authenticated `require_ui_session` owner — it **cannot**
   store a standalone unauthenticated guest-person with an email lookup without a schema change.
   **Assumption (this spec):** the guest is resolved as an opaque, email-derived `guest_party_id`
   (HTL-018 §2.7 opaque-FK precedent) + a `guest_snapshot` on the cart, which is exactly what
   `create_reservation` + the `GSI_GUEST` booking-history index consume. A platform-owned
   "guest CRM" Contact row (with its own table or a relaxed `contacts` schema) is a separate
   ticket; if landed, `set_guest_details` upserts that row and stores its id as `guest_party_id`
   with no caller-visible change.

2. **HTL-001 hotel `status` (`active|archived`) vs HTL-025 publication gate
   (`published`/`status=="published"`).** HTL-001 (`docs/qloapps/specs/HTL-001.md` §3) models hotel
   `status` as `active|archived` with no `published` field; HTL-025
   (`docs/qloapps/BOOKING_STOREFRONT_TICKETS.md:97-101`) gates public reads on
   `status == "published"` / `published == True`. **Assumption:** the publication gate is HTL-025's
   contract (a `published` flag or a `published` status value added by HTL-025/HTL-003), and HTL-027
   delegates the gate entirely to `public_get_hotel` — it does no independent publication check. The
   exact field is reconciled when HTL-025 lands.

3. **`create_booking_cart` cart-id reuse.** §4.2 uses one uuid as both `booking_cart_id` and the
   shop `cart_id` (writing the parent row directly rather than via `start_cart`, which mints its
   own id). **Assumption:** writing the parent row directly (mirroring `start_cart`'s item shape,
   `shoppingcart.py:261-273`) is acceptable; the alternative (call `start_cart`, then map its
   `cart_id`) needs an extra mapping field but is otherwise equivalent.

4. **Post-charge sell-out compensation (§5.6).** The "charge settled but a room sold out at
   hold-time" edge is documented + audited, with refund deferred to the existing `refund_payment`
   as a Tier-3 follow-up. **Assumption:** an automatic best-effort refund/`purchase_cart` reversal
   is NOT in HTL-027 scope (it would fork compensation logic); the tight step-4 pre-guard makes the
   edge rare. If the product needs auto-refund, it routes through `refund_payment`
   (`app/routers/billing.py:1287`) — never a bespoke path.

5. **Frozen price at checkout vs. drift re-quote.** §4.5 step 4 re-validates *availability* at
   checkout but does **not** silently re-price (a frozen quote is the booking contract, HTL-018
   §5.6). **Assumption:** if the rate engine returns a materially different price at checkout, the
   booking proceeds at the locked add-time price; surfacing a "price changed, confirm?" step is a
   frontend (HTL-028) / product decision, not a backend requirement.

6. **Multi-hotel / multi-room-type "trip cart".** A booking cart is one hotel (§5.2); a reservation
   is one room type (HTL-018 §5.5). A multi-hotel or grouped multi-room-type booking is two carts /
   two reservations. **Assumption:** a unified "trip cart" is an explicit future ticket, not
   HTL-027 scope.

7. **Rate-limit subject = client host.** Per HTL-026, the unauth bucket subject is
   `request.client.host`. **Assumption:** this is acceptable behind the platform's normal proxy
   setup (the same assumption HTL-026 makes); a shared-NAT false-positive is mitigated by the
   fail-open bucket and generous defaults.
