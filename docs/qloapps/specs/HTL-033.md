# HTL-033 — Cancellation / no-show policy engine (refund computation + side-effect engine)

**Type**: Feature · **Priority**: P1 · **Estimate**: 2d
**Cluster**: HTL Tier-3 — Cancellation/no-show policy engine + Hotel KPI reports + tax/currency wiring
**Source**: `docs/qloapps/CANCELLATION_REPORTS_TICKETS.md` → `### HTL-033`; gap analysis `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §D.

---

## 1. Summary & Goal

QloApps ([Qloapps/QloApps](https://github.com/Qloapps/QloApps)) ships a hotel
cancellation / no-show **policy engine**: a guest who cancels far enough before arrival is
refunded in full; cancelling inside the penalty window forfeits a percentage (or a fixed
fee) of the booking; a guest who simply never arrives is charged a no-show fee. testlogon
has **no such engine today** — `grep -rn "compute_cancellation_refund\|apply_no_show" app/`
returns nothing, and HTL-019 (`docs/qloapps/specs/HTL-019.md:46`) deliberately does **no
money movement** on its `confirmed → cancelled` / `confirmed → no_show` transitions, leaving
"the cancellation/no-show **refund + penalty** engine [as] **HTL-033**".

This ticket lands exactly that engine in a **new** service `app/services/hotel_cancellation.py`.
It owns two things only:

1. **The math** — `compute_cancellation_refund(reservation, policy, now)`: a pure,
   deterministic function that maps `(days-to-checkin, policy)` → `{base_cents,
   penalty_cents, refundable_cents, days_to_checkin}`. No DDB, no side effects.
2. **The orchestration** — `apply_cancellation(...)` and `apply_no_show(...)`: idempotent
   side-effect drivers that release held inventory (HTL-011) and post **exactly one** money
   row each through the **single platform refund/ledger mechanism** that
   `refund_payment` (`app/routers/billing.py:1287`) and RMA `refund_return`
   (`docs/ofbiz/specs/OFB-010.md` §4) already use — **never** a parallel hotel refund rail.

**Out of scope** (forward refs): the cancellation-policy entity persistence + reservation
cancel/no-show *router wiring* is **HTL-034**; the engine here consumes an
already-resolved `policy` dict and an already-loaded `reservation` dict supplied by the
HTL-034 caller, and **does not mutate reservation status** (that FSM transition is HTL-019).
The engine returns the ledger SK so HTL-034 can back-write the idempotency token onto the
reservation header.

**Goal:** money-safe, idempotent, flag-gated, dev/prod-identical cancellation/no-show
settlement, reusing every existing money and inventory primitive without forking any of them.

### 2.1 Gap — no cancellation refund/penalty engine exists

### 2.2 The ONE refund mechanism (never fork)

`refund_payment` at `app/routers/billing.py:1287` is the canonical platform refund. Its
money sequence (`:1306-1324`) is:

```python

    key_name="pk", key_value=pk,
```

RMA `refund_return` (`docs/ofbiz/specs/OFB-010.md` §4, implemented at
`app/services/returns_rma.py:444`) posts the **same** triple: one
`type="adjustment", reason="refund"` ledger entry with a `provider` stamp (for FIN-013

(`docs/ofbiz/specs/OFB-010.md:113-141`) documents the exact item shapes.

HTL-033 emits the **identical** sequence. It never calls Stripe (OFB-010 §7,
`docs/ofbiz/specs/OFB-010.md:309` — RMA refunds post only to the internal billing ledger;
a real off-session processor reversal is a future sub-flag concern, OFB-010 Open-Q #1).

### 2.4 Inventory release reused (HTL-011)

HTL-011 (`docs/qloapps/specs/HTL-011.md` §4.3, `:245-256`) provides
`release_hold(hold_id, *, reason="released", user_sub="system", terminal_status="released")`
— an **idempotent** status-CAS terminal flip of the `HOLD#{hold_id}` meta row that
decrements `held` back on exactly the dates the hold touched
(`docs/qloapps/specs/HTL-011.md:13,375`). Replays after the terminal flip are no-ops; a
missing hold → 404. HTL-019's cancel/no-show transitions already call
`release_hold(item["hold_id"], ...)` (`docs/qloapps/specs/HTL-019.md:139-144`).

**HTL-033's `apply_cancellation` calls `release_hold` for the reservation's `hold_id`**
(best-effort; release failure must NOT block the refund). `apply_no_show` does **not**
release — the night was held and forfeited.

### 2.5 Reservation dict shape consumed (HTL-018/019 forward dep)

The engine reads (never writes) these reservation fields (per
`docs/qloapps/CANCELLATION_REPORTS_TICKETS.md` HTL-033 dependencies + HTL-019 §2.2):
`total_cents` (paid/owed room-night base), `check_in_ts`, `check_out_ts`, `user_sub`,
`currency`, `hold_id`, `ledger_sk` (original charge ledger SK, if paid through the standard
path), `reservation_id`, `hotel_id`, and optionally `provider`, `rate_plan_id`,
`cancellation_ledger_sk`, `no_show_ledger_sk` (the idempotency tokens HTL-034 back-writes).

### 2.6 Deposit interaction (HTL-031 forward dep)

HTL-031 (`docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md:325`) introduces a **deposit hold**
escrow row (`pk=FOLIO_DEPOSIT#{reservation_id}`, `sk=ESCROW`, `status="held"`) and folio
payments. Where a reservation carries a folio with a held deposit, the *refund base* the
engine credits is `reservation["total_cents"]` (the paid/owed room base passed in by the
caller); HTL-031 §"Why escrow" notes that release/refund-at-checkout of the held deposit is
"a cancellation-cluster concern" — a `status`-guarded flip via `settle_or_reverse_ledger`.
HTL-033's `apply_cancellation` therefore additionally, **best-effort**, reverses a held
deposit escrow row when the caller passes `deposit_escrow_sk` (see §5.6). This keeps the
held/earned distinction without forking billing (HTL-031 §"Why escrow, not a plain debit").

## 3. Data Model

### 3.1 No new DynamoDB table, GSI, or partition

HTL-033 adds **no** table and **no** `attr_types` entry (the cross-cutting constraint:
"This cluster adds no new tables, so no new `attr_types`"). It reads a policy dict + a
reservation dict supplied by HTL-034 and writes **only** to the existing `billing` table
via the shared primitives. The cancellation policy is persisted by HTL-034 as a
`CANCELPOLICY#{policy_id}` child row on the `hotels` partition — outside this ticket.

### 3.2 The policy input dict (shape owned by HTL-034; treated as input here)

| Field | Type | Notes |
|---|---|---|
| `free_until_days_before` | int | cancel ≥ this many days before check-in → full refund, zero penalty (default `0` = no free window) |
| `penalty_pct` | int | penalty as integer percent `[0,100]` of the refundable base, inside the penalty window |
| `penalty_fixed_cents` | int | alternative fixed penalty in cents; when `> 0` takes precedence over `penalty_pct` |
| `no_show_fee_cents` | int | charge applied on no-show (default `0`) |

The engine reads these defensively (`policy.get(key, default)`); an absent key uses its
default, so the *implicit zero-penalty default policy* (`{}`) yields `penalty=0`,
`no_show_fee=0` — a missing policy never throws.

### 3.3 The refund ledger row written (canonical shape — OFB-010 §3)

`apply_cancellation` writes **exactly one** row via `new_ledger_entry`
(`billing_shared.py:224`) on `pk=user_pk(reservation["user_sub"])`:

```
pk            = "USER#{user_sub}"
sk            = "LEDGER#{ts}#{entry_id}"     # minted by new_ledger_entry
type          = "adjustment"
reason        = "refund"
state         = "settled"
amount_cents  = refundable_cents             # > 0 (zero refunds write NO row, §5.5)
ledger_date   = "YYYY-MM-DD"                 # FIN-013 dashboard bucket (auto)
provider      = provider                     # FIN-013/GAP-0203 attribution
reservation_id, hotel_id                     # extra pass-through
meta          = {"reason": "hotel_cancellation", "reservation_id": ...}
```

Then `apply_balance_delta(T.billing, pk, {"payments_settled_cents": -refundable_cents},
currency=reservation.get("currency","usd"))` and, if `reservation.get("ledger_sk")`,
`settle_or_reverse_ledger(T.billing, "pk", pk, reservation["ledger_sk"], "reversed")`.

### 3.4 The no-show fee ledger row written

`apply_no_show` writes **exactly one** charge/debit via `new_ledger_entry`:

```
type          = "charge"
reason        = "no_show_fee"
state         = "settled"
amount_cents  = no_show_fee_cents            # > 0 (fee==0 writes NO row)
provider      = provider
reservation_id, hotel_id                     # extra pass-through
```

Then `apply_balance_delta(T.billing, pk, {"payments_settled_cents": +no_show_fee_cents},
currency=...)`. No Stripe SDK call (internal ledger only — OFB-010 §7).

### 4.2 `compute_cancellation_refund` — pure, deterministic, no DDB

```python
def compute_cancellation_refund(reservation: dict, policy: dict, now: int | None = None) -> dict:
    """Pure. now defaults to now_ts(). No DDB, no side effects, no flag check."""
    base = max(0, int(reservation.get("total_cents") or 0))
    check_in_ts = int(reservation["check_in_ts"])
    now = now if now is not None else now_ts()
    days_to_checkin = max(0, (check_in_ts - now) // 86400)

    free_until = int(policy.get("free_until_days_before", 0) or 0)
    if days_to_checkin >= free_until:
        penalty = 0
    elif int(policy.get("penalty_fixed_cents", 0) or 0) > 0:
        penalty = min(base, int(policy["penalty_fixed_cents"]))
    else:
        penalty = (base * _clamp(int(policy.get("penalty_pct", 0) or 0), 0, 100)) // 100

    penalty = _clamp(penalty, 0, base)               # never refund a negative
    refundable = max(0, base - penalty)
    return {"base_cents": base, "penalty_cents": penalty,
            "refundable_cents": refundable, "days_to_checkin": days_to_checkin}
```

Note `compute_cancellation_refund` is intentionally **not** flag-gated — it is a pure
helper with no I/O; the 404 gate lives on the side-effect entrypoints (a pure compute that
404s would be surprising to test in isolation, and the HTL-034 router always gates first).

### 4.3 `apply_cancellation` — idempotent side-effect driver

```python
def apply_cancellation(reservation: dict, policy: dict, *, actor_sub: str,
                       provider: str = "stripe", now: int | None = None,
                       deposit_escrow_sk: str | None = None) -> dict:
    _require_enabled()                                                   # 404 when flag off
    rid = reservation["reservation_id"]

    # (1) Idempotency guard — stored single-write token (OFB-010 §5).
    if reservation.get("cancellation_ledger_sk"):
        return {"reservation_id": rid, "penalty_cents": 0, "refundable_cents": 0,
                "refund_ledger_sk": reservation["cancellation_ledger_sk"],
                "released_nights": 0, "idempotent": True}

    quote = compute_cancellation_refund(reservation, policy, now)
    pk = user_pk(reservation["user_sub"])
    currency = reservation.get("currency", "usd")

    # (2) Release per-date availability (HTL-011) — best-effort, must NOT block refund.
    released = 0
    hold_id = reservation.get("hold_id")
    if hold_id:
        try:
            from app.services.hotel_availability import release_hold
            release_hold(hold_id, reason="cancelled", user_sub=actor_sub,
                         terminal_status="released")
            released = 1
        except Exception:
            pass

    # (3) Reverse a held deposit escrow row, if any — best-effort (HTL-031 forward dep).
    if deposit_escrow_sk:
        try:
            settle_or_reverse_ledger(T.billing, "pk", pk, deposit_escrow_sk, "reversed")
        except Exception:
            pass

    # (4) Post EXACTLY ONE refund ledger row — the shared mechanism, never forked.
    refund_sk = None
    refundable = quote["refundable_cents"]
    if refundable > 0:                                                   # zero → no row (§5.5)
        refund_sk, led_item = new_ledger_entry(
            key_name="pk", key_value=pk,
            entry_type="adjustment", amount_cents=refundable, state="settled",
            reason="refund",
            meta={"reason": "hotel_cancellation", "reservation_id": rid},
            extra={"provider": provider, "reservation_id": rid,
                   "hotel_id": reservation.get("hotel_id", "")},
        )
        ddb_put(T.billing, led_item)
        apply_balance_delta(T.billing, pk,
                            {"payments_settled_cents": -refundable}, currency=currency)
        if reservation.get("ledger_sk"):
            try:
                settle_or_reverse_ledger(T.billing, "pk", pk,
                                         reservation["ledger_sk"], "reversed")
            except Exception:
                pass                                                     # OFB-010 §5 missing-linkage

    _audit("hotel.reservation.cancelled", actor_sub, reservation_id=rid,
           penalty_cents=quote["penalty_cents"], refundable_cents=refundable,
           provider=provider)
    return {"reservation_id": rid, "penalty_cents": quote["penalty_cents"],
            "refundable_cents": refundable, "refund_ledger_sk": refund_sk,
            "released_nights": released, "idempotent": False}
```

### 4.4 `apply_no_show` — idempotent fee charge

```python
def apply_no_show(reservation: dict, policy: dict, *, actor_sub: str,
                  provider: str = "stripe", now: int | None = None) -> dict:
    _require_enabled()
    rid = reservation["reservation_id"]

    if reservation.get("no_show_ledger_sk"):                              # idempotency guard
        return {"reservation_id": rid, "no_show_fee_cents": 0,
                "no_show_ledger_sk": reservation["no_show_ledger_sk"], "idempotent": True}

    fee = max(0, int(policy.get("no_show_fee_cents", 0) or 0))
    pk = user_pk(reservation["user_sub"])
    currency = reservation.get("currency", "usd")

    fee_sk = None
    if fee > 0:                                                          # fee==0 → no row
        fee_sk, led_item = new_ledger_entry(
            key_name="pk", key_value=pk,
            entry_type="charge", amount_cents=fee, state="settled", reason="no_show_fee",
            meta={"reason": "hotel_no_show", "reservation_id": rid},
            extra={"provider": provider, "reservation_id": rid,
                   "hotel_id": reservation.get("hotel_id", "")},
        )
        ddb_put(T.billing, led_item)
        apply_balance_delta(T.billing, pk,
                            {"payments_settled_cents": fee}, currency=currency)

    _audit("hotel.reservation.no_show", actor_sub, reservation_id=rid,
           no_show_fee_cents=fee)
    return {"reservation_id": rid, "no_show_fee_cents": fee,
            "no_show_ledger_sk": fee_sk, "idempotent": False}
```

### 4.5 The engine does NOT mutate reservation status

There is no `update_item` on the reservation in this file. HTL-019 owns the FSM transition
(`confirmed → cancelled` / `confirmed → no_show`, `docs/qloapps/specs/HTL-019.md:30-33`);
HTL-034's router calls the HTL-019 transition **first** (single-writer `version` CAS), and
only on a *successful* (non-replay) transition calls the matching engine function, then
back-writes the returned `refund_ledger_sk` / `no_show_ledger_sk` onto the reservation
header. The engine returns the SK precisely so HTL-034 can persist the idempotency token.

### 4.6 No router in this ticket

HTL-033 ships **service-only**. The four endpoints (GET/PUT cancellation-policy, POST
cancel, POST no-show) and their `require_ui_session` / `require_admin_or_root_csrf` auth
split land in HTL-034. The engine functions are plain callables, not FastAPI handlers.

## 5. Detailed Behavior & Edge Cases

### 5.1 Refund tiers by days-to-checkin

With `policy = {free_until_days_before: 7, penalty_pct: 50, no_show_fee_cents: 5000}` and
`base = total_cents = 20000`:

| days-to-checkin | branch | `penalty_cents` | `refundable_cents` |
|---|---|---|---|
| 14 (≥ 7) | free window | `0` | `20000` (full refund) |
| 7 (== free_until, boundary) | free window (`>=`) | `0` | `20000` |
| 6 (< 7) | penalty window, `penalty_pct=50` | `10000` | `10000` |
| 0 (same-day) | penalty window | `10000` | `10000` |

The boundary is inclusive of the free window (`days_to_checkin >= free_until` →
zero penalty), per the acceptance criterion "a cancel `>= free_until_days_before` days out
returns `penalty_cents=0`".

### 5.2 `penalty_fixed_cents` precedence over `penalty_pct`

When `penalty_fixed_cents > 0` it wins regardless of `penalty_pct`
(`policy = {free_until_days_before: 7, penalty_pct: 50, penalty_fixed_cents: 3000}`,
`base=20000`, days=3 → `penalty=3000`, `refundable=17000`). A `penalty_fixed_cents` larger
than `base` is clamped to `base` (`min(base, penalty_fixed_cents)`) → `refundable=0` (never
a negative refund).

### 5.3 Clamping invariants

`penalty_pct` is clamped to `[0,100]` (`_clamp`); `penalty` is clamped to `[0, base]`;
`refundable = max(0, base - penalty)`. A pathological `penalty_pct=150` behaves as `100`
(zero refund). A pathological negative penalty/fee is clamped to `0`.

### 5.4 `days_to_checkin` flooring

`days_to_checkin = max(0, (check_in_ts - now) // 86400)`. Integer floor division: a
check-in 6 days + 23 hours away is `6` days (still inside a 7-day free window → penalty).
A check-in **in the past** (negative delta) floors to `max(0, …) = 0` → same-day / past
treated as the deepest penalty tier. Tests pass an explicit `now` for determinism.

### 5.5 Zero-refund / zero-fee → no ledger row (no pollution)

If `refundable_cents == 0` (full penalty, or `base == 0`), `apply_cancellation` writes
**no** ledger row, applies **no** balance delta, and returns `refund_ledger_sk=None` — the
OFB-010 §5 zero-amount guard ("no zero-credit pollution"). Likewise `apply_no_show` with
`no_show_fee_cents == 0` writes nothing and returns `no_show_ledger_sk=None`. The audit
event still fires (records the decision even when no money moved).

### 5.6 Held-deposit reversal (HTL-031 interaction)

When the caller passes `deposit_escrow_sk` (the `sk` of the HTL-031
`FOLIO_DEPOSIT#{reservation_id}` escrow row), `apply_cancellation` flips it to
`state="reversed"` via `settle_or_reverse_ledger` **best-effort** — release/refund of a
held deposit at cancel is "a cancellation-cluster concern" (HTL-031 §"Why escrow"). This is
idempotent (a second flip is a harmless no-op) and never blocks the refund. When no
deposit is held, `deposit_escrow_sk` is omitted and the block is skipped.

### 5.7 Idempotency — no double refund

Two layers, exactly as the cluster constraint requires:

1. **FSM layer (HTL-034 caller)**: the HTL-019 `version`-gated conditional `update_item`
   (`docs/qloapps/specs/HTL-019.md:135`) is the single-writer token. A replayed transition
   (status already terminal) returns `None`, so HTL-034 never calls the engine a second time
   (OFB-010 §5 single-writer pattern).
2. **Engine layer (this ticket)**: even if invoked twice, the
   `reservation.get("cancellation_ledger_sk")` / `no_show_ledger_sk` stored-token guard
   short-circuits before any ledger write and returns `idempotent: True`. A second
   `apply_cancellation` for the same reservation posts **no** second `LEDGER#` row, applies
   **no** second balance delta. This mirrors OFB-010 §5 (the status field as a single-use
   token; no separate `CONSUMED#` row needed).

### 5.8 Inventory-release failure never aborts the refund

The `release_hold` call is wrapped in `try/except` (the EC2/K8s host-inventory best-effort
pattern, CLAUDE.md). A 404 (missing hold), an already-released hold (idempotent no-op,
HTL-011 §5.6), or any exception is swallowed; `released_nights` reflects success/failure but
the refund proceeds. Audit failure is likewise swallowed (`_audit` wrapper).

### 5.9 No-show releases no inventory

`apply_no_show` deliberately does **not** call `release_hold` — the room-night was held and
the guest forfeited it (the fee compensates for the unsold, unreleased night). Releasing on
no-show would wrongly return the night to inventory after the sell window closed.

### 5.10 Currency propagation

`apply_balance_delta` is always called with `currency=reservation.get("currency","usd")` —
the reservation's own currency, never a hard-coded `"usd"` (OFB-010 §5 order-currency
propagation, `docs/ofbiz/specs/OFB-010.md:272`).

### 5.11 `provider` attribution

`provider` defaults to `"stripe"` but the HTL-034 caller passes
`reservation.get("provider", "stripe")` (OFB-010 Open-Q #2). The `provider` field is set on
both the refund and the no-show ledger rows via `extra` so FIN-013/GAP-0203 buckets them
correctly (else the dashboard attributes them to `"unknown"`).

### 5.12 Flag off → 404

`apply_cancellation` / `apply_no_show` call `_require_enabled()` first; with
`HOTEL_PMS_ENABLED` off they raise `HTTPException(404)` before any compute or DDB access —
the platform is byte-for-byte unchanged. `compute_cancellation_refund` is pure and not
gated (it touches nothing); the router (HTL-034) gates the read paths.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`hotel_cancellation.py` contains **no** `if S.dev_mode` branch (acceptance criterion). The
billing primitives (`new_ledger_entry`, `ddb_put`, `apply_balance_delta`,
`settle_or_reverse_ledger`) operate identically against DynamoDB Local (dev, `DDB_ENDPOINT_URL`
port 8001) and real DynamoDB (prod) — the same `T.billing` handle in both
(OFB-010 §7, `docs/ofbiz/specs/OFB-010.md:307`). There is **no** Stripe API call in either
entrypoint (internal ledger only — a processor-level reversal is a future sub-flag, OFB-010
Open-Q #1), so there is no provider-mock divergence between environments.

### 7.2 Idempotency (two layers — §5.7)

- **Stored-token guard**: `cancellation_ledger_sk` / `no_show_ledger_sk` short-circuit before
  any write (the engine layer).
- **Single-writer FSM**: the HTL-019 `version` CAS at the HTL-034 caller (the transition
  layer). Either layer alone prevents a double refund; together they are belt-and-braces.
- **`settle_or_reverse_ledger` is idempotent**: re-flipping an already-`reversed` row is a
  harmless `update_item` (OFB-010 §5, `docs/ofbiz/specs/OFB-010.md:139-141`).

### 7.3 Security — auth + ownership

The engine functions are not directly reachable — HTL-034 mounts the routes with the
cluster auth split: reads → `require_ui_session` (`app/services/sessions.py:330`); mutations
(cancel/no-show/policy PUT) → `require_admin_or_root_csrf` (`app/auth/policy.py:100`),
identical to `app/routers/inventory.py:48,65,81`. HTL-034 enforces hotel ownership before
calling the engine. `actor_sub` is threaded into every `_audit` event for an immutable
who-did-what trail.

### 7.4 Money-safety (paramount)

- **One mechanism, never forked**: every money move is `new_ledger_entry` +
  `apply_balance_delta` (+ best-effort `settle_or_reverse_ledger`) — the identical sequence
  as `refund_payment` (`billing.py:1306-1324`) and `refund_return` (OFB-010 §4). No bespoke
  `put_item` of a ledger row, no `delete_item` on a ledger row, anywhere in the path.
- **Integer cents only**: `penalty_cents`, `refundable_cents`, `no_show_fee_cents` are all
  `int`; `//` floor division; no floats.
- **No negative / over-refund**: `penalty` clamped to `[0, base]`, `refundable = max(0, …)`,
  fee clamped to `>= 0`. A refund never exceeds the booking base.
- **Exactly one row per outcome**: a single ledger write per `apply_*` call (or zero when
  the amount is zero — §5.5). The stored-token guard makes a second call write nothing.
- **No double-refund**: enforced at both the FSM and engine layers (§5.7).

### 7.5 Audit trail

`hotel.reservation.cancelled` (with `penalty_cents` / `refundable_cents` / `provider`) and
`hotel.reservation.no_show` (with `no_show_fee_cents`) fire on every settlement, even
zero-money outcomes. Audit failure is swallowed (`_audit` best-effort wrapper,
`inventory.py:92-98`) and never aborts the refund.

## 8. Backward Compatibility & Migration

### 8.1 Additive-only — no behavior change with the flag off

HTL-033 adds one new file and imports only existing primitives. No existing function is
modified. With `HOTEL_PMS_ENABLED=false` (the default), every engine entrypoint 404s before
touching anything; `compute_cancellation_refund` is unreferenced until a flag-on caller
invokes it. The platform is byte-for-byte unchanged. `grep` for the new symbols returns only
the new file + its test.

### 8.2 No DDB migration

No new table, GSI, `attr_types`, or partition. The refund/no-show rows are ordinary
`billing`-table ledger items (same shape `refund_payment` / RMA already write); no schema
change in dev (`scripts/local-ddb-init.py` unchanged) or prod.

### 8.3 Forward-compatible reservation fields

`cancellation_ledger_sk` / `no_show_ledger_sk` are *read* by the engine but *written* by
HTL-034. Pre-HTL-033 reservations simply lack them (→ `None` → not idempotent-short-circuited
on first cancel, which is correct: they have never been cancelled). No backfill needed.

### 8.4 Rollback

Setting `HOTEL_PMS_ENABLED=false` instantly disables the engine (every entrypoint 404s).
Already-posted refund/no-show ledger rows are valid platform ledger entries and need no
cleanup. Reverting the file removes the engine with zero residue.

## 9. Test Plan

### 9.1 Hermetic pytest — `tests/test_htl_033_cancellation.py`

Offline, no live stack, no real AWS, no network, no Stripe. Pattern (per cross-cutting
"Hermetic offline tests" + PROP-001 §9.1, `docs/open-property/specs/PROP-001.md:432-487`):
a moto-backed `billing` table bound to the frozen `T.billing` handle via
`object.__setattr__`; the billing-shared primitives operate against that same handle;
frozen `S.hotel_pms_enabled` toggled via `object.__setattr__`; engine functions called
directly (they are plain callables, not coroutines — for the HTL-034 router tests a fresh
`asyncio.new_event_loop()` is used). `release_hold` is patched at the
`hotel_cancellation` namespace (no live `hotel_availability`); `_audit` is a no-op.

**Setup block**

```python
import boto3, pytest
from moto import mock_aws
from unittest.mock import patch

@pytest.fixture(autouse=True)
def setup(monkeypatch):
    with mock_aws():
        ddb = boto3.resource("dynamodb", region_name="us-east-1")
        billing = ddb.create_table(
            TableName="billing",
            KeySchema=[{"AttributeName": "pk", "KeyType": "HASH"},
                       {"AttributeName": "sk", "KeyType": "RANGE"}],
            AttributeDefinitions=[{"AttributeName": "pk", "AttributeType": "S"},
                                  {"AttributeName": "sk", "AttributeType": "S"}],
            BillingMode="PAY_PER_REQUEST",
        )
        from app.core import tables as T_mod
        from app.services import hotel_cancellation as svc
        object.__setattr__(T_mod.T, "billing", billing)
        object.__setattr__(svc.S, "hotel_pms_enabled", True)
        yield billing
```

Helper: `_ledger_rows(billing, sub)` queries `pk=USER#{sub}`, returns items with
`sk.startswith("LEDGER#")`; `RES = {"reservation_id":"r1","hotel_id":"h1","user_sub":"u1",
"currency":"usd","total_cents":20000,"check_in_ts":<fixed>,"check_out_ts":<+2d>,"hold_id":"hold1"}`.

**Test cases**

1. **Flag-off 404**: `object.__setattr__(svc.S, "hotel_pms_enabled", False)`; assert
   `apply_cancellation(RES, {}, actor_sub="a")` raises `HTTPException(404)` and **no**
   ledger row is written. (`compute_cancellation_refund` does NOT 404 — assert it returns a
   dict even with the flag off.)
2. **Free-window full refund**: `policy={free_until_days_before:7,penalty_pct:50}`,
   `now = check_in_ts - 14*86400`. `compute_cancellation_refund` → `penalty_cents=0,
   refundable_cents=20000, days_to_checkin=14`.
3. **Boundary (`days == free_until`)**: `now = check_in_ts - 7*86400` → `penalty_cents=0`
   (inclusive free window).
4. **Penalty-window pct**: `now = check_in_ts - 3*86400` → `penalty_cents=10000,
   refundable_cents=10000`.
5. **`penalty_fixed_cents` precedence**: `policy={free_until_days_before:7,penalty_pct:50,
   penalty_fixed_cents:3000}`, days=3 → `penalty_cents=3000, refundable_cents=17000`.
6. **Fixed > base clamps to base**: `penalty_fixed_cents:99999`, base=20000 →
   `penalty_cents=20000, refundable_cents=0`.
7. **pct clamp**: `penalty_pct:150` → behaves as 100 → `refundable_cents=0`.
8. **`apply_cancellation` posts exactly one refund row**: days=3, pct=50 → assert exactly
   one `type="adjustment", reason="refund"` row with `amount_cents=10000`,
   `provider="stripe"`, `reservation_id="r1"`; assert the BALANCE row
   `payments_settled_cents` decremented by `10000`; assert `release_hold` was called once
   with `hold_id="hold1", terminal_status="released"` (patched mock); returned
   `released_nights==1`.
9. **Zero-refund → no row**: full penalty (`penalty_fixed_cents>=base`) → `apply_cancellation`
   writes **no** ledger row, `refund_ledger_sk is None`, balance unchanged; audit still fires.
10. **Idempotency / no double refund**: call `apply_cancellation` once (capture
    `refund_ledger_sk`), set `RES["cancellation_ledger_sk"]=that_sk`, call again → returns
    `idempotent=True`, **still exactly one** refund row in the table (no second write).
11. **Original-charge reversal**: set `RES["ledger_sk"]` to a pre-seeded `state="settled"`
    charge row; after `apply_cancellation` that row is `state="reversed"`.
12. **`apply_no_show` posts the fee**: `policy={no_show_fee_cents:5000}` → exactly one
    `type="charge", reason="no_show_fee"` row, `amount_cents=5000`, BALANCE
    `payments_settled_cents` incremented by `5000`; `release_hold` **not** called.
13. **No-show fee==0 → no row**: `policy={}` → no row, `no_show_ledger_sk is None`.
14. **No-show idempotency**: set `RES["no_show_ledger_sk"]`, re-call → `idempotent=True`,
    no second row.
15. **release-hold failure best-effort**: patch `release_hold` to raise → `apply_cancellation`
    still posts the refund row, `released_nights==0`, no exception propagates.
16. **Currency propagation**: `RES["currency"]="eur"` → `apply_balance_delta` called with
    `currency="eur"` (spy the call).
17. **Past check-in floors to 0 days**: `now = check_in_ts + 86400` → `days_to_checkin==0`
    (deepest penalty tier), no crash.

## 10. Open Questions / Assumptions

1. **Real processor reversal vs internal ledger only.** Following OFB-010 (§7, Open-Q #1),
   HTL-033 posts only the internal billing-ledger refund — it does **not** call
   `stripe.Refund.create`. **Assumption**: an actual off-session processor reversal (to
   move money back at Stripe/PayPal/CCBill) is a separate future sub-flag concern, out of
   scope here. The `provider` stamp makes a later reconciliation worker possible.
2. **`provider` source.** **Assumption**: the HTL-034 caller passes
   `reservation.get("provider", "stripe")`. If the reservation never records a provider, the
   refund defaults to `"stripe"` for FIN-013 bucketing (OFB-010 Open-Q #2).
3. **Refund base = `total_cents`.** **Assumption**: `reservation["total_cents"]` is the
   paid/owed room-night base the refund credits. Where HTL-031 deposits + folio payments
   diverge from `total_cents`, HTL-034 supplies the correct base (and `deposit_escrow_sk`);
   the engine treats whatever base it is handed as authoritative.
4. **Penalty applied to gross base, not net-of-deposit.** **Assumption**: `penalty_pct`
   applies to the full `total_cents`, and the held deposit is reversed separately (§5.6).
   If product wants penalty-on-net, that is a policy-shape change in HTL-034, not an engine
   change.
5. **`days_to_checkin` granularity is whole days, floored.** **Assumption**: hour-level
   precision is unnecessary for cancellation tiers (the QloApps model is days-based).
6. **No-show fee is not idempotent across *separate* fee events** — but is idempotent on
   *replay* of the same no-show (the stored `no_show_ledger_sk` guard). **Assumption**: a
   reservation has at most one no-show event (enforced by the HTL-019 terminal status).
