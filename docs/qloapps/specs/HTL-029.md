# HTL-029 — Guest folio entity — model, table, flag, open/add-line/get/close service

**Type**: Feature | **Priority**: P1 | **Estimate**: 2d
**Source**: `docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md` §HTL-029 + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §D rows 1-2 (`:101-102`) + Tier-3 cluster (`:150-156`)

---

## 1. Summary & Goal

HTL-029 lands the **guest folio** entity — the running stay balance for one hotel
reservation. It ships exactly three deliverables: (1) the `hotel_folios` DynamoDB
table — PK=`reservation_id`, SK=`META` for the folio header plus co-located child
`LINE#{line_id}` rows for line items, with one GSI (`GSI_FOLIO_HOTEL`) and the
correct `attr_types` for its numeric sort key; (2) the core folio service
`app/services/hotel_folios.py` (new) with `open_folio`, `add_line_item`,
`get_folio`, and `close_folio`; and (3) the Pydantic I/O models `FolioLineIn`,
`FolioLineOut`, `FolioOut` in `app/models.py`.

A folio accumulates **charges** — room-nights seeded from the HTL-018 reservation,
add-ons (HTL-030), taxes/fees — as `LINE#` rows, and tracks a derived
`balance_due_cents = charges_total_cents - payments_total_cents`. Payments
(deposits + partials + balance) are recorded by HTL-031 as `new_ledger_entry`
rows on the **existing** `T.billing` partition and roll up into
`payments_total_cents`; the folio PDF (HTL-032) is an `invoices._render_pdf`
render. HTL-029 is the **lowest-net-new** Tier-3 work because every money movement
reuses primitives that already exist — `invoices.py` line items
(`app/services/invoices.py:218-245`), the `billing_shared.py` single-entry ledger,
and the `inventory.py` flag/audit/coerce idioms.

The gap analysis (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:101`) records the guest
folio / booking invoice as **PARTIAL**: "`invoices.py` (FIN-001: invoice#, line
items, tax, S3 PDF, `deposit` type); **no folio/running-stay-balance entity**."
HTL-029 lands exactly that missing entity. Without it, HTL-030 (add-on SKU → folio
line), HTL-031 (deposit/partial payment recording), and HTL-032 (router + folio
PDF) have no folio to attach to. With HTL-029 merged but `HOTEL_PMS_ENABLED=false`
(the default), the platform is byte-for-byte unchanged: every service entrypoint
404s before touching DynamoDB and **no folio/ledger row is ever written**.

## 2. Context & Current State

### 2.1 Gap — no running-stay-balance entity exists today

The gap analysis §D (`docs/qloapps/QLOAPPS_GAP_ANALYSIS.md:101-102`) records two
adjacent PARTIAL rows:

- **Guest folio / booking invoice** (`:101`): "`invoices.py` (FIN-001: invoice#,
  line items, tax, S3 PDF, `deposit` type); no folio/running-stay-balance entity."
- **Service / ancillary add-ons on a booking** (`:102`): "catalog + cart provide
  products; no 'attach add-on to a booking' link" — HTL-030's gap, layered atop
  HTL-029.

The Tier-3 cluster description (`:150-152`) frames HTL-029 precisely: "**Guest
folio**: open-stay running-balance entity accumulating room-nights + add-ons + tax
atop `invoices.py` line-items."

The codebase today has **no** `hotel_folios` table, **no**
`S.hotel_folios_table_name` setting, **no** `T.hotel_folios` handle, and **no**
folio Pydantic models. The closest structural artefacts are forward-design-only:

- **`invoices` invoices** — a `pk`/`sk` (`sk="INV#{number}"`) record with a
  `line_items` list of `{description, quantity, amount_cents}`
  (`app/services/invoices.py:218-245`), a `deposit` type already in `VALID_TYPES`
  (`invoices.py:33`), tax (`tax_cents`/`S.invoices_tax_bps`, `invoices.py:306`),
  and an S3 PDF rendered by the dependency-free `_render_pdf` /
  `_render_invoice_lines` (`invoices.py:103,150`). HTL-029 reuses the **line-item
  shape** but not the model: an invoice is a *finalized*, immutable document with a
  monotonic number; a folio is a *mutable, running* balance that accumulates lines
  during a stay and is rendered to a PDF (an invoice) only at HTL-032 close.
- **Header+child partition idiom** — the PROP-002 `UNIT#{unit_id}` /
  FAC-001 `LOC#{location_id}` co-located-child pattern
  (`docs/open-property/PROPERTY_UNITS_TICKETS.md` §PROP-002, `docs/ofbiz/specs/FAC-001.md` §3):
  a `META` header row plus typed child rows on one partition, queryable in a single
  partition `query`. HTL-029 reuses the **shape** (`META` + `LINE#{line_id}`).


DynamoDB returns `N` attributes as `Decimal`; every monetary/numeric field
(`charges_total_cents`, `payments_total_cents`, `amount_cents`, `quantity`,
`unit_price_cents`, `created_at`, `updated_at`, `closed_at`) is coerced with
`_to_int` before being returned. This mirrors `invoices._coerce_int`
(`invoices.py:60`) and `catalog.ddb_to_int` (`catalog.py:71`).

### 2.5 ID derivation — folio keyed on `reservation_id` (idempotent); lines non-deterministic

The folio header row is keyed on the **reservation_id PK** itself (one folio per
reservation), so `open_folio` is idempotent without a separate id derivation: a
conditional `attribute_not_exists(sk)` put on the `META` row makes the second
`open_folio` a no-op that returns the existing folio (§5.1). A convenience
`folio_id = "fol_" + uuid4().hex` is stored for display, but the canonical key is
`reservation_id`.

Line rows use a non-deterministic `line_id = uuid4().hex` (the LSE/HTL-018
non-deterministic-id precedent, `docs/qloapps/specs/HTL-018.md` §2.4) — a folio may
legitimately hold many identically-priced lines (e.g. three nights of a Deluxe
King), so a line is NOT idempotent on its arguments. Each `add_line_item` always
appends a fresh `LINE#` row.

### 2.6 The HTL-018 reservation (dependency) — passed in, not read here

HTL-018 (`docs/qloapps/specs/HTL-018.md` §3.1) defines the `hotel_reservations`
table (PK=`reservation_id`, SK=`META`) carrying the fields `open_folio` seeds from:
`hotel_id`, `guest_party_id`, `room_type_id`, `checkin` (`YYYY-MM-DD`, inclusive),
`checkout` (`YYYY-MM-DD`, exclusive), `nights` (count of `[checkin, checkout)`),
`total_cents` (from `compute_stay_price`), `currency`, and `rooms`
(`docs/qloapps/specs/HTL-018.md` §3.1 attribute table). **HTL-029 does not read the
reservation table** — per the cluster constraint
(`docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md` §HTL-029 "open_folio"), the HTL-032
router resolves the reservation via the Tier-2 service and passes the reservation
**dict** into `open_folio(reservation, *, user_sub)`. This keeps the cluster from
defining or coupling to the reservation table (`reservation_id` is referenced only).

> **Guest-sub vs. guest_party_id.** HTL-018's reservation carries `guest_party_id`
> (an opaque person FK → Contacts / OBP `CUS` / open-property `TEN`,
> `docs/qloapps/specs/HTL-018.md` §2.7). The folio's `guest_sub` is the *billing
> identity* — the `user_sub` whose `pk=USER#{guest_sub}` `T.billing` partition all
> HTL-031 folio money rows land on. The HTL-032 router supplies `guest_sub`
> (resolving the party→user mapping); `open_folio` denormalizes whatever the
> caller provides as `guest_sub` (falling back to `guest_party_id` if the caller
> passes only that — see §10 Q1).

### 2.8 Money — single-entry ledger lives elsewhere (HTL-031), never forked here

HTL-029 writes **no** money rows. It only tracks `payments_total_cents` as a
denormalized roll-up counter on the `META` row (bumped by HTL-031's `record_payment`
via `apply_balance_delta`-style atomic `ADD`). The actual payment rows are
`new_ledger_entry` (`app/services/billing_shared.py:224`) on `T.billing`

constraint is absolute: "**ONE refund/ledger mechanism — never fork billing.** ...
No bespoke `put_item` ever constructs a ledger row." HTL-029 honors this by never
importing `billing_shared` at all (§7.4).

## 3. Data Model

### 3.1 Table: `hotel_folios`

Single DynamoDB table. The PK/SK design follows the PROP-002 `UNIT#{unit_id}` /
FAC-001 `LOC#{location_id}` header+child idiom
(`docs/open-property/PROPERTY_UNITS_TICKETS.md` §PROP-002, `docs/ofbiz/specs/FAC-001.md` §3):
a `META` row holds the folio header and child `LINE#{line_id}` line-item rows
co-locate on the same `reservation_id` partition, enabling a cheap single-partition
query for a folio and all its lines.

**Primary key**

| Key | Type | Value |
|---|---|---|
| `reservation_id` | S (PK) | The HTL-018 reservation id (forward dep — referenced, never defined here). One folio per reservation. |
| `sk` | S (SK) | `"META"` (folio header row); child line rows use `"LINE#{line_id}"` |

**Folio header row attributes** (SK=`META`)

| Attribute | DDB Type | Constraints / Notes |
|---|---|---|
| `reservation_id` | S | PK. The HTL-018 reservation id. |
| `sk` | S | Always `"META"` for the folio header. |
| `folio_id` | S | Convenience id `"fol_" + uuid4().hex` (display only; canonical key is `reservation_id`). |
| `hotel_id` | S | Denormalized from the reservation for scoping/auth + the `GSI_FOLIO_HOTEL` index (HTL-001 hotel FK). |
| `guest_sub` | S | The guest's billing `user_sub` (the `pk=USER#{guest_sub}` `T.billing` partition all HTL-031 folio money rows land on). |
| `currency` | S | ISO 4217 lowercase, e.g. `"usd"` (from the reservation; money-as-cents). |
| `status` | S | `open` → `closed` (folio lifecycle; default `open`). |
| `charges_total_cents` | N | Denormalized running sum of all `LINE#` `amount_cents` (maintained on `add_line_item`; **also** recomputed authoritatively by `get_folio` from the line rows — §4.5). |
| `payments_total_cents` | N | Denormalized running sum of payments recorded against the folio (`0` here; maintained by HTL-031 `record_payment`). |
| `deposit_held_cents` | N | Amount currently held in escrow (`0` here; maintained by HTL-031). |
| `closed_at` | N | `now_ts()` when closed (absent while open). |
| `created_at` | N | `now_ts()` |
| `updated_at` | N | `now_ts()`; bumped on every `add_line_item` and `close_folio`. |

**Folio line row attributes** (SK=`LINE#{line_id}`, `line_id = uuid4().hex` —
non-deterministic, §2.5)

| Attribute | DDB Type | Constraints / Notes |
|---|---|---|
| `reservation_id` | S | PK (same partition as the `META` row). |
| `sk` | S | `"LINE#{line_id}"` |
| `line_id` | S | Convenience copy of the id. |
| `line_type` | S | `room_night` \| `addon` \| `tax` \| `fee` (constrained literal). |
| `description` | S | Human-readable, e.g. `"Deluxe King — 2026-07-04"` or `"Breakfast x2"`. |
| `quantity` | N | `ge=1`, defaults `1`. |
| `unit_price_cents` | N | Per-unit price in cents (`ge=0`). |
| `amount_cents` | N | `quantity * unit_price_cents` (computed at add time; the canonical line total). |
| `sku` | S | Catalog `item_id` for `addon` lines (HTL-030); `""` for non-addon lines. |
| `created_at` | N | `now_ts()` |

**GSIs**

| Index name | PK | SK | Purpose |
|---|---|---|---|
| `GSI_FOLIO_HOTEL` | `hotel_id` (S) | `created_at` (N) | List a hotel's folios newest-first (front-desk folio list / HTL-032 read path). **Sparse**: only the `META` row carries `hotel_id`, so `LINE#` rows never pollute the index. |

Projects all attributes (`ALL`).

> **Note.** Per-folio line rows stay queryable by the `hotel_folios` PK
> (`Key={"reservation_id": rid}` + `begins_with(sk, "LINE#")`) for the folio
> detail view (`get_folio`); the GSI above is the hotel-scoped folio-list fast path
> only.

**`attr_types`**: `{"created_at": "N"}` — mandatory for the single numeric GSI sort
key (`GSI_FOLIO_HOTEL` SK), per the CLAUDE.md "DynamoDB numeric GSI sort keys"
gotcha and the cluster constraint (`docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md`
"`attr_types` for numeric GSI keys"): omitting it stores `created_at` as String →
`ValidationException` when `GSI_FOLIO_HOTEL` is queried with an integer value.

**TableDef** (appended in `scripts/local-ddb-init.py` inside `_table_defs()`, after
the last existing entry, following the `TableDef` dataclass at
`scripts/local-ddb-init.py:29-36` and the `_resolve_table_name` helper at `:38-39`):

```python
TableDef(
    _resolve_table_name(S.hotel_folios_table_name, "hotel_folios"),
    "reservation_id",
    "sk",
    gsi=[
        {"index_name": "GSI_FOLIO_HOTEL", "partition_key": "hotel_id", "sort_key": "created_at"},
```

### 4.2 `open_folio(reservation, *, user_sub) -> dict`

Seeds a new folio from an HTL-018 reservation dict.

1. `_require_enabled()`.
2. Extract `reservation_id`, `hotel_id`, `currency` (default `"usd"`), and
   `guest_sub` (the caller-supplied billing user_sub; fall back to
   `reservation.get("guest_party_id")` — §10 Q1) from the **passed-in reservation
   dict** (never read the reservation table — §2.6).
3. Mint `folio_id = "fol_" + uuid4().hex`, `created_at = updated_at = now_ts()`.
4. Build the `META` header item: `charges_total_cents=0`, `payments_total_cents=0`,
   `deposit_held_cents=0`, `status="open"`.
5. **Idempotent put** — `T.hotel_folios.put_item(Item=meta,
   ConditionExpression="attribute_not_exists(sk)")`. On
   `ConditionalCheckFailedException`, the folio already exists → fall through to
   step 7 (read-back) **without** re-seeding lines.
6. **Seed room-night lines** (only on a fresh create): for the reservation's stay,
   append one `room_night` `LINE#` row per night via `add_line_item`. The simplest
   correct seeding derives `nights = _to_int(reservation.get("nights"))` and
   `total_cents = _to_int(reservation.get("total_cents"))`; the per-night unit price
   is `total_cents // nights` for the first `nights-1` nights and the remainder for
   the last night (so the lines sum **exactly** to `total_cents` — no rounding drift,
   §5.6). Each line is `line_type="room_night"`,
   `description=f"{room_type_id} — {checkin}..{checkout} night {i+1}"`,
   `quantity=1`, `unit_price_cents=<per-night>`. Each `add_line_item` call atomically
   bumps `charges_total_cents` (§4.3), so after seeding the header counter equals
   `total_cents`.
7. `_audit("hotel.folio.opened", user_sub, reservation_id=..., folio_id=...,
   hotel_id=..., total_cents=...)`.
8. Return `get_folio(reservation_id)` (the assembled folio dict).

> Seeding via `add_line_item` (not bespoke `put_item`) routes the room-night lines
> through the **single** charge-bump write path — no duplicated total math.

### 4.3 `add_line_item(reservation_id, *, line_type, description, quantity=1, unit_price_cents, sku="", user_sub) -> dict`

Appends a line and atomically bumps the header charge total.

1. `_require_enabled()`.
2. Validate `line_type in _LINE_TYPES` (422 otherwise — also enforced by the
   `FolioLineIn` `Literal`), `quantity >= 1` (422), `unit_price_cents >= 0` (422).
3. Read the `META` row (`Key={"reservation_id": rid, "sk": "META"}`); **404** if
   absent (`"Folio not found"`); **409** if `status != "open"`
   (`"Folio is closed"`).
4. Mint `line_id = uuid4().hex`; `amount_cents = quantity * unit_price_cents`;
   `created_at = now_ts()`.
5. `T.hotel_folios.put_item(Item=line_row)` (the `LINE#{line_id}` row).
6. **Atomically** bump the header via `update_item` on the `META` row:
   `UpdateExpression="ADD charges_total_cents :amt SET updated_at = :t"`,
   `:amt = amount_cents`, `:t = now_ts()` — no read-modify-write race (the
   `apply_wallet_delta` atomic-`ADD` precedent, `billing_shared.py:185-211`).
   `ADD` creates the counter if missing (it never is — `open_folio` seeds `0`).
7. `_audit("hotel.folio.line_added", user_sub, reservation_id=..., line_id=...,
   line_type=line_type, amount_cents=amount_cents)`.
8. Return the created line dict (the `FolioLineOut` shape, numbers `_to_int`-coerced).

### 4.4 `get_folio(reservation_id) -> dict | None`

The folio detail read — source of truth for `charges_total_cents` /
`balance_due_cents`.

1. `_require_enabled()`.
2. Single-partition `query(KeyConditionExpression=Key("reservation_id").eq(rid))`
   — paginate via `LastEvaluatedKey` if a folio ever exceeds 1MB of lines (defensive;
   real folios are tiny). Split items: the `sk == "META"` row is the header; every
   `sk` `begins_with "LINE#"` is a line.
3. If no `META` row → return `None`.
4. **Authoritatively recompute** `charges_total_cents = sum(_to_int(li["amount_cents"])
   for li in lines)` from the line rows (the denormalized header counter is a fast
   path; `get_folio` is the source of truth — §5.4).
5. Derive `balance_due_cents = charges_total_cents -
   _to_int(meta["payments_total_cents"])`.
6. Sort lines by `created_at` ascending (deterministic display order — `LINE#`
   `uuid4` SKs are not chronological, the same non-chronological-SK caveat as the
   messaging table; sort after fetch).
7. Assemble and return the folio dict: header fields (`_to_int`-coerced numbers) +
   the recomputed `charges_total_cents` + derived `balance_due_cents` +
   `line_items: [FolioLineOut...]`.

### 4.5 `close_folio(reservation_id, *, user_sub) -> dict`

Closes an open folio (an admin action — no zero-balance guard here, §5.5).

1. `_require_enabled()`.
2. **Conditional** `update_item` on the `META` row:
   `UpdateExpression="SET #s = :closed, closed_at = :t, updated_at = :t"`,
   `ConditionExpression="#s = :open"`, `ExpressionAttributeNames={"#s": "status"}`,
   `:closed="closed"`, `:open="open"`, `:t=now_ts()`. This flips `open → closed`
   exactly once; a replay (already `closed`) raises
   `ConditionalCheckFailedException`, caught and treated as a no-op idempotent
   success (§5.7). A missing `META` row also fails the condition → **404**
   (`"Folio not found"`) distinguished by a prior existence check or by inspecting
   the error.
3. `_audit("hotel.folio.closed", user_sub, reservation_id=...)`.
4. Return `get_folio(reservation_id)` (the updated folio dict).

All four entrypoints call `_require_enabled()` **first**, before any table access.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent `open_folio` (one folio per reservation)

`open_folio` writes the `META` row with `ConditionExpression="attribute_not_exists(sk)"`.
A second `open_folio(reservation, ...)` with the same `reservation_id` catches
`ConditionalCheckFailedException` and returns the existing folio via `get_folio` —
the same `folio_id`, **without re-seeding room-night lines** (which would double the
charges). Two calls return the same folio with no error and no duplicate lines. This
is the FAC/PROP/HTL-001 conditional-put-then-read-back idempotency contract.

### 5.2 `add_line_item` on an unknown folio → 404

If no `META` row exists for `reservation_id`, `add_line_item` raises
`HTTPException(404, "Folio not found")` before any `put_item`. No orphan `LINE#`
row is written.

### 5.3 `add_line_item` on a closed folio → 409

If the `META` row's `status == "closed"`, `add_line_item` raises
`HTTPException(409, "Folio is closed")`. A closed folio is immutable — no further
charges may be added (a re-open is a HTL-031/cancellation-policy concern, out of
scope). No `LINE#` row is written and `charges_total_cents` is unchanged.

### 5.4 Authoritative charge total vs. denormalized counter

`charges_total_cents` is maintained two ways: (a) the `META` counter, bumped
atomically by every `add_line_item` `ADD` (a cheap fast path for the folio-list
view); and (b) recomputed by `get_folio` as `sum(line.amount_cents)` from the line
rows (the source of truth). They should always agree, but `get_folio` recomputing
from the lines is the authoritative value returned — a hedge against a partial
write (a `LINE#` put that succeeded while its header `ADD` failed mid-call). This is
the invoices-style "render from line items" posture (`invoices._render_invoice_lines`
sums `line_items`, `invoices.py:177-184`).

### 5.5 `balance_due_cents` can be negative (overpayment)

`balance_due_cents = charges_total_cents - payments_total_cents`. After HTL-031
records a deposit/partial, `payments_total_cents > 0`. If payments exceed charges
(an overpayment / deposit larger than the stay), `balance_due_cents` is **negative**
— a credit the guest is owed. HTL-029 does not clamp it (a clamp would hide a
refund-due; the cancellation/refund cluster reads the negative balance). In HTL-029
proper (no payments recorded yet), `payments_total_cents == 0`, so
`balance_due_cents == charges_total_cents >= 0`.

### 5.6 Room-night seeding sums exactly to `total_cents` (no rounding drift)

Per-night unit price = `total_cents // nights` for the first `nights-1` nights and
`total_cents - (nights-1) * (total_cents // nights)` for the last night. This
guarantees `sum(line.amount_cents) == total_cents` exactly — the
banker-remainder-on-last-line idiom — so the seeded `charges_total_cents` equals the
reservation `total_cents` with no off-by-cents drift. For `nights == 0` (defensive —
HTL-018 enforces `nights >= 1`, `docs/qloapps/specs/HTL-018.md` §2.5), seed a single
`room_night` line of `total_cents` and skip the division.

### 5.7 `close_folio` is idempotent under replay

The conditional `SET status="closed" WHERE status="open"` flips exactly once. A
replay (folio already `closed`) raises `ConditionalCheckFailedException`, which
`close_folio` catches and returns the already-closed folio — idempotent success, not
an error. This is the ORD/KYC conditional-state-transition idiom
(`docs/qloapps/specs/HTL-018.md` §3.1 `version` CAS analogue, without a version bump
— closing is a single terminal flip).

### 5.8 Decimal coercion on read

DynamoDB returns `N` attributes as `Decimal`. Every numeric field
(`charges_total_cents`, `payments_total_cents`, `deposit_held_cents`,
`balance_due_cents`, `amount_cents`, `quantity`, `unit_price_cents`, `created_at`,
`updated_at`, `closed_at`) is coerced with `_to_int` before being returned, so
`FolioOut` / `FolioLineOut` receive plain `int`s. `FolioOut.closed_at` is
`Optional[int]` — absent while open.

### 5.9 Line-row vs. header-row disambiguation in `get_folio`

`get_folio`'s single-partition query returns the `META` row plus all `LINE#` rows.
Disambiguation is purely by `sk`: `sk == "META"` is the header; `sk.startswith("LINE#")`
is a line. No other `sk` prefix exists on the `hotel_folios` partition in HTL-029
(HTL-031 records payments on `T.billing`, **not** here — §2.8).

### 5.10 Sparse `GSI_FOLIO_HOTEL` — line rows excluded

Only the `META` row carries `hotel_id`; `LINE#` rows do not. Because a GSI item is
written only when its partition-key attribute is present, `LINE#` rows are absent
from `GSI_FOLIO_HOTEL` — a hotel-scoped folio-list query (`hotel_id` PK) returns
only `META` folio headers, never line clutter. This sparse-GSI pattern mirrors
HTL-018's `GSI_GUEST` (only `META` rows carry `guest_party_id`).

### 5.11 Flag-off behavior

When `HOTEL_PMS_ENABLED=false` (default), every `hotel_folios.py` entrypoint raises
`HTTPException(404, "Hotel PMS is not enabled")` before touching DynamoDB. The
`hotel_folios` table may or may not exist — the flag check runs first. No folio,
line, ledger, or audit row is written.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/services/hotel_folios.py` contains **no** `if S.dev_mode` branch. The same
DynamoDB code path runs in dev (boto3 intercepted by moto in-process) and prod (real
DynamoDB). This mirrors the cluster cross-cutting constraint
(`docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md` "Dev/prod parity (SECOPS-007)") and the
precedent of `app/services/inventory.py` (no `dev_mode` branch anywhere). The folio
PDF (HTL-032) reuses the dependency-free `invoices._render_pdf` (`invoices.py:103`)
— no `reportlab`/system deps, identical bytes in dev and prod (mirrors
`receipts.py`).

### 7.2 Idempotency

- **`open_folio`** is idempotent on `reservation_id` (one folio per reservation) via
  the conditional `attribute_not_exists(sk)` put + read-back-on-collision (§5.1).
  Critically, the second call does **not** re-seed room-night lines.
- **`add_line_item`** is intentionally **not** idempotent — each call appends a
  fresh non-deterministic `LINE#{uuid}` row (§2.5). A folio may legitimately hold
  many identical lines.
- **`close_folio`** is idempotent under replay (conditional `open → closed` flip;
  replay is a no-op success, §5.7).
- **`get_folio`** is a pure read (trivially idempotent).

### 7.3 Security — auth split + ownership

HTL-029 ships **service only**; the HTL-032 router enforces auth (the cluster
constraint "Auth split"): reads via `require_ui_session`
(`app/services/sessions.py:330`), mutations (`open`, `add-line`, `close`) via
`require_admin_or_root_csrf` (`app/auth/policy.py:100`) — identical to
`app/routers/inventory.py:48,65,81`. Hotel staff (admin/root) manage folios; a guest
reads only their own (the router checks `folio["guest_sub"] == caller.sub` for
guest reads — §10 Q3). `add_line_item` never trusts a client-supplied
`amount_cents` it doesn't compute — `amount_cents = quantity * unit_price_cents` is
server-derived; HTL-030's add-on path further resolves `unit_price_cents` from the
catalog server-side (anti-tamper, the `unlock_post` PM-validation posture).

### 7.4 Money-safety

- **Every monetary attribute is integer cents** — `charges_total_cents`,
  `payments_total_cents`, `deposit_held_cents`, `balance_due_cents`,
  `amount_cents`, `unit_price_cents` — matching `invoices._money` (`invoices.py:146`)
  and `billing_shared.py`. No floats ever touch money.
- **`amount_cents = quantity * unit_price_cents`** is integer arithmetic; room-night
  seeding distributes `total_cents` with the remainder on the last night so lines sum
  **exactly** to the reservation total (§5.6) — no rounding drift.
- **`charges_total_cents` is bumped atomically** via DynamoDB `ADD` (§4.3) — never a
  read-modify-write that could lose a concurrent line under a race.
- **HTL-029 writes no money rows and never forks billing.** It does not import
  `billing_shared`; `payments_total_cents` is a counter HTL-031 bumps via the
  existing ledger primitives (`new_ledger_entry`, `billing_shared.py:224`;
  `apply_balance_delta`, `:83`). No bespoke `put_item` constructs a ledger row and no
  `delete_item` is ever called on one (the cluster's absolute "ONE refund/ledger
  mechanism" rule).

### 7.5 Audit trail

Every service mutation emits a best-effort audit event via the `_audit()` wrapper
(copied from `inventory.py:92-98`): `hotel.folio.opened`, `hotel.folio.line_added`,
`hotel.folio.closed`. Audit failure (an `audit_event` exception) is swallowed and
never propagates to the caller (the lazy-import + bare-`except` contract).

## 10. Open Questions / Assumptions

1. **`guest_sub` source.** The folio's `guest_sub` is the *billing* `user_sub` (the
   `pk=USER#{guest_sub}` `T.billing` partition for HTL-031), whereas HTL-018's
   reservation carries `guest_party_id` (an opaque person FK,
   `docs/qloapps/specs/HTL-018.md` §2.7). **Assumption**: the HTL-032 router supplies
   `guest_sub` explicitly (resolving party→user); `open_folio` reads
   `reservation.get("guest_sub")` and falls back to
   `reservation.get("guest_party_id")` only if absent. If party and billing-user are
   never the same identity, the fallback is a placeholder the router must override.

2. **Room-night seeding granularity.** HTL-029 seeds one `room_night` line **per
   night** (so a 3-night stay shows 3 lines, matching a hotel folio's
   per-night display). An alternative is a single aggregate room-night line of
   `total_cents`. **Assumption**: per-night lines (the folio-UX norm); the
   remainder-on-last-night split (§5.6) keeps the sum exact. Date-labeled
   descriptions require the reservation `checkin`/`room_type_id`, which are present in
   the passed dict.

3. **Guest read ownership.** `get_folio` does not enforce ownership at the service
   layer (admin reads are unrestricted). **Assumption**: the HTL-032 router enforces
   `folio["guest_sub"] == caller.sub` for guest (`require_ui_session`) reads and lets
   admin/root read any folio (the inventory/PROP precedent). Multi-tenant hotel
   isolation (one hotel's staff cannot read another hotel's folios) is a router
   concern (`folio["hotel_id"]` scoping), out of HTL-029 scope.

4. **`close_folio` with a non-zero balance.** `close_folio` does **not** require a
   zero `balance_due_cents` — closing is an admin action (cluster constraint,
   `docs/qloapps/FOLIOS_PAYMENTS_TICKETS.md` §HTL-029 "close_folio"). **Assumption**:
   a zero-balance-on-close guard, if desired, is a HTL-031 / cancellation-policy
   concern. HTL-029 closes regardless of balance.

5. **Tax/fee lines.** `line_type` includes `tax` and `fee`, but HTL-029 does not
   auto-compute them (no `S.invoices_tax_bps` application at seed time). **Assumption**:
   tax/fee lines are added explicitly via `add_line_item` (by the front desk or a
   later HTL ticket); auto-tax atop `S.invoices_tax_bps` (`invoices.py:306`) is a
   forward extension, not HTL-029.

6. **No `delete_line_item`.** HTL-029 ships no line-removal function (a void/credit
   is the correct accounting primitive, owned by the cancellation/refund cluster via
   `settle_or_reverse_ledger`, `billing_shared.py:262`). **Assumption**: lines are
   append-only in HTL-029; corrections are made by adding an offsetting negative-amount
   line in a later ticket, never by deleting a `LINE#` row.
