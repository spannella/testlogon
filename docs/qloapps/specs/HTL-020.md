# HTL-020 — Routers: `/ui/hotel-search` + `/ui/hotels/{hotel_id}/reservations` + lifecycle sub-routes + registration

**Type**: Feature | **Priority**: P1 | **Estimate**: 1.5d
**Source**: `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md` §HTL-020 + "Cross-cutting constraints" + `docs/qloapps/QLOAPPS_GAP_ANALYSIS.md` §C (Reservation Lifecycle + Front Desk)

---

## 1. Summary & Goal

HTL-020 exposes the entire HTL-017/018/019 reservation service layer over HTTP by introducing one new file — `app/routers/hotel_reservations.py` — declaring a single `hotel_reservations_router` (prefix `/ui`, tag `hotel-reservations`) and registering it in `app/main.py` immediately after `inventory_router` (`app/main.py:877`). The ticket delivers exactly **11 endpoints**: the stay-search funnel (`POST /ui/hotel-search`), reservation CRUD-ish operations (`POST`/`GET` list, `GET` one, `GET .../history`, `PUT` modify), and five lifecycle action sub-routes (`confirm`, `check-in`, `check-out`, `cancel`, `no-show`).

No new DynamoDB tables, GSIs, or settings keys are introduced here — the `hotel_reservations` table, its three GSIs, the `HOTEL_PMS_ENABLED` master flag, and every Pydantic I/O model were landed by HTL-017 (`docs/qloapps/specs/HTL-017.md`), HTL-018, and HTL-019 (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md` §HTL-018, §HTL-019). HTL-020 is a thin, policy-correct HTTP façade over an already-complete service layer.

The router contributes four non-trivial concerns beyond plain delegation:

1. **Auth split** — reads use `require_ui_session` (`app/services/sessions.py:330`); mutations and all five lifecycle sub-routes use `require_admin_or_root_csrf` (role `∈ {ADMIN, ROOT}` + cookie CSRF, `app/auth/policy.py:100`). This is the identical split used by `app/routers/inventory.py` (reads at `:37`/`:48` use `require_ui_session`; mutations at `:65`/`:81` use `require_admin_or_root_csrf`).
2. **Route-declaration order (literal-before-dynamic)** — the literal `/ui/hotel-search` route and every literal lifecycle sub-route (`.../confirm`, `.../check-in`, `.../check-out`, `.../cancel`, `.../no-show`, `.../history`) must be declared **before** the bare dynamic `GET`/`PUT` `/ui/hotels/{hotel_id}/reservations/{reservation_id}` so FastAPI does not capture `check-in` (etc.) as a `{reservation_id}` value — the same gotcha CLAUDE.md documents for KYC `/templates`-before-`/{case_id}` and audit-export `/schedules`-before-`/{export_id}`.
3. **Feature-flag short-circuit** — every handler calls `_require_enabled()` first; when `HOTEL_PMS_ENABLED=false` (the default) every endpoint returns HTTP 404 and the platform is byte-for-byte unchanged.
4. **Typed-error → HTTP mapping** — the HTL-018/019 service functions raise `HTTPException` with structured `detail` dicts (`409 invalid_status_transition`, `409 concurrent_update`, `409 no_availability`, `422 ...`, `404 ...`); the router lets these propagate unchanged, adding only the `get_*` `None → 404` guards (the `inventory.py:101-105`/`:118-120` 404-on-`None` idiom).

With the flag off the router is still mounted (exactly as `inventory_router` is always mounted at `app/main.py:877`) but every handler is a silent 404 no-op. No existing endpoint, table, model, or behavioral contract is modified.

- **HTL-019** (`docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md` §HTL-019, spec `docs/qloapps/specs/HTL-019.md` — forward ref) — the `_RESERVATION_TRANSITIONS` state machine, `transition_reservation(reservation_id, target_status, *, actor, reason, assigned_room_ids)`, `modify_reservation(...)`, and `list_reservation_history(reservation_id)` service functions; `ReservationTransitionIn` / `ReservationModifyIn` / `ReservationHistoryEntry` models.

One function in the table below — `list_reservations` — is a HTL-018-layer lister that HTL-020 calls but that the §HTL-018 description does not name explicitly. It is treated here as a HTL-018 deliverable that HTL-020 depends on (see §10.3); it paginates `GSI_HOTEL_ARRIVALS` / `GSI_HOTEL_STATUS` and returns the `{reservations, count, cursor}` shape (the `host_inventory.list_hosts` `{items, count, cursor}` convention, CLAUDE.md).

No hotel-reservation router exists today. `grep -rn "hotel_reservations_router\|ui/hotel-search\|hotels/.*reservations" app/` returns no results, and `app/routers/hotel_reservations.py` does not exist (only `app/routers/inventory.py` and `app/routers/host_inventory.py` are present in the commerce/ops router group).

### 2.2 Canonical router idiom — `app/routers/inventory.py`

`app/routers/inventory.py` is the exact template to follow:

- **Router declaration** (`:29`): `inventory_router = APIRouter(prefix="/ui/inventory", tags=["inventory"])` — a single `APIRouter` with a `/ui/` prefix and a single tag.
- **Local `_require_enabled()` wrapper** (`:32-34`): a module-level function delegating to `inv._require_enabled()`. Every handler calls this as its first statement (`:38`, `:50`, `:67`, `:83`, ...).
- **Auth split**: GET endpoints use `session=Depends(require_ui_session)` (`:37`, `:48`); mutation endpoints use `user: AuthenticatedUser = Depends(require_admin_or_root_csrf)` (`:65`, `:81`).
- **`None → 404` guard**: reads that return `None` from the service raise `HTTPException(404, ...)` (`:101-105` for `get_inventory`, `:118-120` for `get_reservation`).
- **`main.py` import + registration**: imported as `from app.routers.inventory import inventory_router` (`app/main.py:311`); included via `app.include_router(inventory_router)` (`app/main.py:877`).

`hotel_reservations_router` mirrors this pattern at every level. The one structural divergence is the prefix: `inventory_router` prefixes `/ui/inventory`, but HTL-020 spans two path families (`/ui/hotel-search` and `/ui/hotels/{hotel_id}/reservations/...`) that do not share a common second segment, so the router prefix is the bare `/ui` and each handler carries its full sub-path (see §4.1).

### 2.3 Auth dependencies

- **`require_ui_session`** (`app/services/sessions.py:330`) — async FastAPI `Depends`; resolves an API-key principal, cookie UI session, or Bearer JWT; returns a `dict` with `user_sub`, `session_id`, `role`, `ip`, `tenant_id`. Used for read (GET) and the read-only `POST /ui/hotel-search` funnel. The handler reads `session["user_sub"]`.
- **`require_admin_or_root_csrf`** (`app/auth/policy.py:100`) — async FastAPI dependency; calls `enforce_cookie_csrf(request)` (`:71`) then `require_roles(user, {Role.ADMIN, Role.ROOT})` (`:105`); raises HTTP 403 on missing/mismatched CSRF (`:94-96`), on missing role, or on role mismatch. Returns an `AuthenticatedUser`. Used for `create_reservation`, `modify_reservation`, and all five lifecycle sub-routes. The handler reads `user.sub` for `actor` / `user_sub`.
- **`AuthenticatedUser`** dataclass (`app/auth/deps.py`) — the type returned by `require_admin_or_root_csrf`; carries `.sub` (the `user_sub`), `.role`, `.admin_profile`.

### 2.4 Route-ordering constraint (FastAPI path-param capture)

FastAPI matches routes in declaration order. Within the `/ui/hotels/{hotel_id}/reservations/...` family, the literal sub-routes (`/confirm`, `/check-in`, `/check-out`, `/cancel`, `/no-show`, `/history`) are `{hotel_id}/reservations/{X}/literal` shaped and the bare detail routes are `{hotel_id}/reservations/{reservation_id}`. A request to `.../reservations/res_abc/check-in` is a four-segment path under `/ui/hotels/.../reservations` and does not collide with the three-segment `.../reservations/{reservation_id}` — they differ in length. The real risk is `.../reservations/{reservation_id}` being declared before `.../reservations/{reservation_id}/history` (etc.); because the sub-route paths are strictly longer, FastAPI's longest-match-wins still routes correctly, but the **safe, documented practice is declaration order: literal/longer before bare dynamic, always** — identical to:

- KYC: `GET /v1/kyc/cases/templates` declared **before** `/{case_id}` (CLAUDE.md §"KYC template-signature endpoints").
- Audit export: `/schedules` declared **before** `/{export_id}` (CLAUDE.md §"Scheduled audit export reports").

The independent `POST /ui/hotel-search` literal has no `{hotel_id}` ambiguity (it is a distinct path family) but is still declared at the top of the router for clarity. HTL-020 declares (in order): `/ui/hotel-search`; the `/ui/hotels/{hotel_id}/reservations` collection POST + GET; then every `.../{reservation_id}/...` sub-route (`/history`, `/confirm`, `/check-in`, `/check-out`, `/cancel`, `/no-show`); then the bare `.../{reservation_id}` GET + PUT last. This is the single most subtle implementation detail of the ticket.

### 2.5 `main.py` registration adjacent to the hotel routers

`app/main.py:311` imports `inventory_router`; `:877` includes it (`app.include_router(inventory_router)`). HTL-020's `hotel_reservations_router` is imported directly after the inventory/host-inventory router imports (`~:311`) and included directly after `inventory_router` (`~:877`), grouping the hotel-PMS vertical routers together. The cluster doc names the HTL-008 hotels router, the HTL-012 availability router, and the HTL-016 rate-plans router as the intended adjacency anchors; those are sibling-cluster forward refs (`docs/qloapps/HOTELS_AMENITIES_TICKETS.md`, `docs/qloapps/AVAILABILITY_INVENTORY_TICKETS.md`, `docs/qloapps/RATE_PLANS_TICKETS.md`) and may not be merged when HTL-020 lands — so the concrete, verified insertion anchor is `inventory_router` at `app/main.py:877` (cf. ORD-001 §4.2 router-gate, the LSE router plan). If the sibling hotel routers are present, place HTL-020's include adjacent to them; otherwise adjacent to `inventory_router`.

### 2.6 Pagination + list-response shape

`list_reservations` uses `encode_cursor` (`app/core/cursor.py:94`) / `decode_cursor` (`app/core/cursor.py:103`) — the same HMAC-signed opaque cursor every paginated lister uses; a tampered cursor silently restarts from the beginning (per `decode_cursor`). The list endpoint returns `{reservations: [...], count: int, cursor: str | None}`, mirroring the `host_inventory.list_hosts` `{items, count, cursor}` convention noted in CLAUDE.md. The cursor encode/decode lives in the service; the router passes `cursor` and `limit` through transparently.

## 3. Data Model

HTL-020 introduces **no new DynamoDB tables, no new GSIs, no new DynamoDB attributes, and no new Pydantic models**. The `hotel_reservations` table (PK=`reservation_id`, SK=`META`/`HIST#{ts:020d}#{event_id}`) and its three GSIs (`GSI_HOTEL_ARRIVALS` PK=`hotel_id` SK=`checkin`; `GSI_GUEST` PK=`guest_party_id` SK=`created_at` numeric, `attr_types={"created_at": "N"}`; `GSI_HOTEL_STATUS` PK=`hotel_id` SK=`status`) were declared by HTL-018 in `scripts/local-ddb-init.py`. The Pydantic request/response models were defined by HTL-017/018/019 in `app/models.py`. This section documents which models flow through each endpoint.

### 3.1 Models flowing through the router

| Endpoint | Request body model | Response model |
|---|---|---|
| `POST /ui/hotel-search` | `StaySearchIn` | `StaySearchResult` |
| `POST /ui/hotels/{hotel_id}/reservations` | `ReservationCreateIn` | `ReservationOut` |
| `GET /ui/hotels/{hotel_id}/reservations` | — (query params) | `{reservations: List[ReservationOut], count: int, cursor: str \| None}` |
| `GET /ui/hotels/{hotel_id}/reservations/{reservation_id}/history` | — | `List[ReservationHistoryEntry]` |
| `POST /ui/hotels/{hotel_id}/reservations/{reservation_id}/confirm` | — | `ReservationOut` |
| `POST /ui/hotels/{hotel_id}/reservations/{reservation_id}/check-in` | `ReservationTransitionIn` | `ReservationOut` |
| `POST /ui/hotels/{hotel_id}/reservations/{reservation_id}/check-out` | `ReservationTransitionIn` (or none) | `ReservationOut` |
| `POST /ui/hotels/{hotel_id}/reservations/{reservation_id}/cancel` | `ReservationTransitionIn` (or none) | `ReservationOut` |
| `POST /ui/hotels/{hotel_id}/reservations/{reservation_id}/no-show` | `ReservationTransitionIn` (or none) | `ReservationOut` |
| `PUT /ui/hotels/{hotel_id}/reservations/{reservation_id}` | `ReservationModifyIn` | `ReservationOut` |
| `GET /ui/hotels/{hotel_id}/reservations/{reservation_id}` | — | `ReservationOut` |

`ReservationTransitionIn` (HTL-019) carries `target_status`, `reason?`, and `assigned_room_ids?`. For the lifecycle sub-routes the `target_status` is fixed by the route (e.g. `check-in` → `"checked_in"`), so the router ignores any `target_status` in the body and passes the route-fixed literal to `transition_reservation`; the body supplies `reason` and (for check-in) `assigned_room_ids`. The `confirm` sub-route takes no body (it is a no-op idempotent confirm — see §5.4). The `check-out`/`cancel`/`no-show` sub-routes accept an optional body solely for `reason`.

### 3.2 Query parameters

`GET /ui/hotels/{hotel_id}/reservations` accepts:
- `status: Optional[str] = None` — one of the five lifecycle literals (`confirmed`, `checked_in`, `checked_out`, `cancelled`, `no_show`); when present, the service queries `GSI_HOTEL_STATUS` (PK=`hotel_id`, SK=`status`); 422 if an unrecognized value is supplied. When omitted, the service queries `GSI_HOTEL_ARRIVALS` (PK=`hotel_id`, SK=`checkin`).
- `checkin_from: Optional[str] = None` / `checkin_to: Optional[str] = None` — `YYYY-MM-DD` arrival-date window; bounds the `GSI_HOTEL_ARRIVALS` SK range (the arrivals-board query). Invalid date format → 422 (raised by the service).
- `cursor: Optional[str] = None` — opaque HMAC-signed pagination token (`encode_cursor`/`decode_cursor`, `app/core/cursor.py:94,103`); a tampered token silently restarts from the beginning.
- `limit: int = 50` — page size; capped server-side (200) by the service.

No query parameters on `POST /ui/hotel-search` (the search criteria are in the `StaySearchIn` body), the single-reservation `GET`, the `.../history` `GET`, the `PUT`, or the lifecycle sub-routes.

## 4. API / Service Design

### 4.1 Router file: `app/routers/hotel_reservations.py` (new file)

```python
"""Hotel reservation router (QloApps hotel-PMS vertical, HTL-020).

Additive + flag-gated (``HOTEL_PMS_ENABLED``, default OFF). Every handler
calls ``_require_enabled()`` first; when the flag is off all endpoints return
404 and the platform is byte-for-byte unchanged.

Auth split (mirrors app/routers/inventory.py:37,48,65,81):
  * Read endpoints           → ``require_ui_session``        (any authenticated user)
  * Write/lifecycle endpoints → ``require_admin_or_root_csrf`` (ADMIN | ROOT + CSRF)

Read-only stay-search (``POST /ui/hotel-search``) is POST-with-body (the search
funnel) but uses the read auth dependency — it performs zero DDB writes.
"""
from __future__ import annotations

from typing import Optional

from fastapi import APIRouter, Depends, HTTPException

from app.auth.deps import AuthenticatedUser
from app.auth.policy import require_admin_or_root_csrf
from app.models import (
    ReservationCreateIn, ReservationModifyIn, ReservationOut,
    ReservationTransitionIn, StaySearchIn, StaySearchResult,
)
from app.services import hotel_reservations as svc
from app.services.sessions import require_ui_session

hotel_reservations_router = APIRouter(prefix="/ui", tags=["hotel-reservations"])


def _require_enabled() -> None:
    svc._require_enabled()
```

The prefix is `/ui` (not `/ui/hotels`) because the `POST /ui/hotel-search` funnel and the `/ui/hotels/{hotel_id}/reservations/...` family do not share a second path segment. Each handler declares its full sub-path.

### 4.2 Endpoint specifications (declaration order)

All 11 endpoints are listed below **in declaration order**. The order is non-negotiable: `/ui/hotel-search` first, then the reservations collection, then the `.../{reservation_id}/...` literal sub-routes, then the bare `.../{reservation_id}` GET + PUT last (literal-before-dynamic, §2.4).

---

#### `POST /ui/hotel-search`  *(declared first — independent literal path)*

```python
@hotel_reservations_router.post("/hotel-search", response_model=StaySearchResult)
async def hotel_search(body: StaySearchIn, session=Depends(require_ui_session)) -> StaySearchResult:
    _require_enabled()
    result = svc.search_stays(
        hotel_id=body.hotel_id, city=body.city,
        checkin=body.checkin, checkout=body.checkout,
        adults=body.adults, children=body.children, rooms=body.rooms,
    )
    return StaySearchResult(**result)
```

- Auth: `require_ui_session` — read-only; the search funnel must be reachable by any authenticated user (a guest-facing search). POST-with-body purely because the criteria are a structured object, not because it mutates state.
- Service: `search_stays` (HTL-017) — pure composition over HTL-012 `check_availability` + HTL-015 `compute_stay_price`; **zero DDB writes**. Raises `HTTPException(422)` when both `hotel_id` and `city` are absent, or `checkout <= checkin`; the handler lets these propagate.

---

#### `POST /ui/hotels/{hotel_id}/reservations`  *(collection — create)*

```python
@hotel_reservations_router.post("/hotels/{hotel_id}/reservations", response_model=ReservationOut, status_code=201)
async def create_reservation(
    hotel_id: str, body: ReservationCreateIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> ReservationOut:
    _require_enabled()
    item = svc.create_reservation(
        hotel_id=hotel_id, guest_party_id=body.guest_party_id,
        room_type_id=body.room_type_id, checkin=body.checkin, checkout=body.checkout,
        adults=body.adults, children=body.children, rooms=body.rooms,
        deposit_cents=body.deposit_cents, user_sub=user.sub,
    )
    return ReservationOut(**item)
```

- Auth: `require_admin_or_root_csrf` (`app/auth/policy.py:100`).
- `hotel_id` is taken from the path (authoritative); a `hotel_id` in the body, if any, is ignored in favor of the path param.
- Service: `create_reservation` (HTL-018) — re-checks availability at book time (`409 no_availability` if sold out), prices via HTL-015, holds inventory via HTL-011 `hold_rooms` **before** the header `put_item` (a `409` from `hold_rooms` leaves no header written), then writes the `META` header with `status="confirmed"`, `version=1`, `hold_id`. The `409` errors propagate to the client unchanged.

---

#### `GET /ui/hotels/{hotel_id}/reservations`  *(collection — list)*

```python
@hotel_reservations_router.get("/hotels/{hotel_id}/reservations")
async def list_reservations(
    hotel_id: str,
    status: Optional[str] = None,
    checkin_from: Optional[str] = None,
    checkin_to: Optional[str] = None,
    cursor: Optional[str] = None,
    limit: int = 50,
    session=Depends(require_ui_session),
) -> dict:
    _require_enabled()
    return svc.list_reservations(
        hotel_id=hotel_id, status=status,
        checkin_from=checkin_from, checkin_to=checkin_to,
        cursor=cursor, limit=limit,
    )
```

- Auth: `require_ui_session`.
- Service: `list_reservations` (HTL-018 lister, §10.3) — `status` present → `GSI_HOTEL_STATUS`; absent → `GSI_HOTEL_ARRIVALS` (optionally bounded by `checkin_from`/`checkin_to`). Returns `{reservations, count, cursor}`. Invalid `status` → 422 (service-raised, propagated).

---

#### `GET /ui/hotels/{hotel_id}/reservations/{reservation_id}/history`  *(literal sub-route — declared before bare `{reservation_id}`)*

```python
@hotel_reservations_router.get("/hotels/{hotel_id}/reservations/{reservation_id}/history")
async def reservation_history(hotel_id: str, reservation_id: str, session=Depends(require_ui_session)) -> list:
    _require_enabled()
    existing = svc.get_reservation(reservation_id)
    if existing is None or existing.get("hotel_id") != hotel_id:
        raise HTTPException(status_code=404, detail="Reservation not found")
    return svc.list_reservation_history(reservation_id)
```

- Auth: `require_ui_session`.
- Service: `list_reservation_history` (HTL-019) — `begins_with(sk, "HIST#")` newest-first. The handler first 404s on a missing reservation or a `hotel_id` mismatch (the row exists but belongs to a different hotel — §5.5).

---

#### `POST /ui/hotels/{hotel_id}/reservations/{reservation_id}/confirm`  *(literal sub-route)*

```python
@hotel_reservations_router.post("/hotels/{hotel_id}/reservations/{reservation_id}/confirm", response_model=ReservationOut)
async def confirm_reservation(
    hotel_id: str, reservation_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> ReservationOut:
    _require_enabled()
    existing = svc.get_reservation(reservation_id)
    if existing is None or existing.get("hotel_id") != hotel_id:
        raise HTTPException(status_code=404, detail="Reservation not found")
    return ReservationOut(**existing)
```

- Auth: `require_admin_or_root_csrf`.
- No-op / idempotent confirm: a reservation is created `confirmed`, so this returns the current header unchanged. Reserved for a future `draft → confirmed` step (§5.4). It does **not** call `transition_reservation` (there is no `confirmed → confirmed` edge in `_RESERVATION_TRANSITIONS`).

---

#### `POST /ui/hotels/{hotel_id}/reservations/{reservation_id}/check-in`  *(literal sub-route)*

```python
@hotel_reservations_router.post("/hotels/{hotel_id}/reservations/{reservation_id}/check-in", response_model=ReservationOut)
async def check_in_reservation(
    hotel_id: str, reservation_id: str, body: ReservationTransitionIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> ReservationOut:
    _require_enabled()
    existing = svc.get_reservation(reservation_id)
    if existing is None or existing.get("hotel_id") != hotel_id:
        raise HTTPException(status_code=404, detail="Reservation not found")
    item = svc.transition_reservation(
        reservation_id, "checked_in",
        actor=user.sub, reason=body.reason or "",
        assigned_room_ids=body.assigned_room_ids,
    )
    return ReservationOut(**item)
```

- Auth: `require_admin_or_root_csrf`.
- Service: `transition_reservation(..., "checked_in", assigned_room_ids=...)` (HTL-019). Missing `assigned_room_ids` (or `len != rooms`) → `HTTPException(422)`; an illegal edge (e.g. already `checked_out`) → `409 invalid_status_transition`; a concurrent writer → `409 concurrent_update`. All propagate unchanged.

---

#### `POST /ui/hotels/{hotel_id}/reservations/{reservation_id}/check-out`  *(literal sub-route)*

```python
@hotel_reservations_router.post("/hotels/{hotel_id}/reservations/{reservation_id}/check-out", response_model=ReservationOut)
async def check_out_reservation(
    hotel_id: str, reservation_id: str, body: ReservationTransitionIn | None = None,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> ReservationOut:
    _require_enabled()
    existing = svc.get_reservation(reservation_id)
    if existing is None or existing.get("hotel_id") != hotel_id:
        raise HTTPException(status_code=404, detail="Reservation not found")
    item = svc.transition_reservation(
        reservation_id, "checked_out",
        actor=user.sub, reason=(body.reason if body else "") or "",
    )
    return ReservationOut(**item)
```

- Auth: `require_admin_or_root_csrf`. Service: `transition_reservation(..., "checked_out")` (HTL-019) — releases physical rooms best-effort; does **not** call `release_hold` (the hold is the consumed booking). Illegal edge → `409`.

---

#### `POST /ui/hotels/{hotel_id}/reservations/{reservation_id}/cancel`  *(literal sub-route)*

Identical shape to `check-out`, passing `"cancelled"`. Illegal edge (e.g. cancelling a `checked_out` reservation) → `409 invalid_status_transition`.

#### `POST /ui/hotels/{hotel_id}/reservations/{reservation_id}/no-show`  *(literal sub-route)*

Identical shape, passing `"no_show"`. Service releases held inventory via HTL-011 `release_hold` (best-effort); no penalty/fee is charged here (HTL-033). Illegal edge → `409`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Route-ordering correctness — literal sub-routes before bare `{reservation_id}`

The router declares (in order): `/hotel-search`; `/hotels/{hotel_id}/reservations` (POST + GET); the six `.../{reservation_id}/...` literal sub-routes (`/history`, `/confirm`, `/check-in`, `/check-out`, `/cancel`, `/no-show`); then the bare `.../{reservation_id}` GET + PUT last. While FastAPI's longest-match routing means a four-segment `.../check-in` request would not actually be captured by the three-segment `.../{reservation_id}`, declaration order is the documented safe practice (CLAUDE.md KYC `/templates`-before-`/{case_id}`, audit-export `/schedules`-before-`/{export_id}`). The test plan asserts the ordering by index in `hotel_reservations_router.routes` (§9 case 14).

### 5.2 `POST /ui/hotel-search` is POST-with-read-auth

`/ui/hotel-search` uses POST (the search criteria are a structured `StaySearchIn` body, not query params) but `require_ui_session` read auth and performs **zero DDB writes**. This is a deliberate funnel design: the search must be reachable by any authenticated user, and POST avoids encoding a complex criteria object in the query string. It never holds inventory or creates a reservation (that is the separate `POST .../reservations` mutation, admin-gated).

### 5.3 `hotel_id` path param is authoritative

For every `/ui/hotels/{hotel_id}/...` endpoint the path `hotel_id` is authoritative. On create, a `hotel_id` in the body (if the model has one) is ignored in favor of the path. On every read/transition/modify, the handler verifies the resolved reservation's stored `hotel_id` equals the path `hotel_id` and 404s on mismatch (§5.5) — so a reservation under hotel A cannot be read or driven through `/ui/hotels/B/reservations/{id}`.

### 5.4 `confirm` is an idempotent no-op

A reservation is created `status="confirmed"` (HTL-018). The `confirm` sub-route therefore returns the current header unchanged — it does **not** call `transition_reservation` (no `confirmed → confirmed` self-edge exists in `_RESERVATION_TRANSITIONS`; calling it would 409). The route is reserved for a future `draft → confirmed` first step (per the §HTL-020 endpoint table). It is admin-gated for symmetry with the other lifecycle actions.

### 5.5 `hotel_id` / `reservation_id` mismatch → 404, not 403

`get_reservation` is keyed only on `reservation_id` (PK), so a valid `reservation_id` resolves regardless of the path `hotel_id`. Every reservation-scoped handler re-checks `existing.get("hotel_id") == hotel_id` and 404s (not 403) on mismatch — the row is treated as nonexistent under the wrong hotel, mirroring `inventory.py:118-120`'s `user_sub`-ownership 404 (it 404s rather than 403 to avoid leaking the existence of a reservation under another hotel).

### 5.6 Typed-error → HTTP mapping (no re-wrapping in the router)

The HTL-018/019 service functions raise `HTTPException` with structured `detail` dicts. The router does **not** catch or re-wrap them — they propagate to FastAPI's exception handler unchanged:

| Service condition | HTTP | `detail` |
|---|---|---|
| Reservation not found / wrong hotel | 404 | `"Reservation not found"` (router-raised guard) |
| Sold out at book time | 409 | `{"code": "no_availability"}` |
| Sold-out span on `hold_rooms` | 409 | (from HTL-011) |
| Illegal lifecycle edge / terminal state | 409 | `{"code": "invalid_status_transition", "from", "to"}` |
| Concurrent transition (version CAS lost) | 409 | `{"code": "concurrent_update"}` |
| `check-in` without `assigned_room_ids` / wrong count | 422 | `"assigned_room_ids required for check-in"` |
| `modify` on a non-`confirmed` reservation | 409 | `"only confirmed reservations may be modified"` |
| Search: both `hotel_id`+`city` absent, or `checkout<=checkin` | 422 | (from HTL-017) |
| Invalid `status` query filter | 422 | (from HTL-018 `list_reservations`) |

The router adds only the `get_*` `None`/mismatch → 404 guards.

### 5.7 Flag-off behavior

When `HOTEL_PMS_ENABLED=false` (the default), every handler calls `_require_enabled()` which delegates to `svc._require_enabled()` (HTL-017), raising `HTTPException(404, "Hotel PMS is not enabled")` before any service work, DDB read, or DDB write. The router remains mounted via `app.include_router(hotel_reservations_router)` — the flag check is at the handler level, not the mount level (identical to `inventory_router`, always mounted at `app/main.py:877`). With the flag off the platform is byte-for-byte unchanged.

### 5.8 `cancel` / `no-show` reflect released inventory; no money movement

A successful `cancel` or `no-show` returns 200 + the updated `ReservationOut` with the terminal `status`; the released hold is reflected by a subsequent HTL-012 availability query (the room-nights become sellable again). The router writes **no ledger entry, issues no refund, and charges no penalty** — HTL-033 (Tier-3, forward ref) owns refund/penalty, and any future refund must route through `refund_payment` (`app/routers/billing.py`) / `settle_or_reverse_ledger`, never a parallel mechanism (cross-cutting "no money fork", ORD-001 §5.6).

### 5.9 Decimal coercion in response models

`ReservationOut` numeric fields (`nights`, `adults`, `children`, `rooms`, `total_cents`, `deposit_cents`, `version`, `created_at`, `updated_at`) must be plain `int`, not `Decimal`, in the response. The HTL-018 service-layer projection handles `Decimal → int` coercion before returning the dict; the Pydantic model additionally coerces on assignment. No coercion is needed in the router.

### 5.10 Empty / no-match lists are 200, not 404

`GET .../reservations` for a hotel with no reservations returns `{"reservations": [], "count": 0, "cursor": None}` with HTTP 200 (not 404). `.../history` for a reservation with only the initial `confirmed` event returns that single entry. A 404 from the list/history endpoints means only "reservation not found" (history) or never (list — an unknown `hotel_id` simply returns an empty page).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 — zero `dev_mode` branches

`app/routers/hotel_reservations.py` contains **no** `if S.dev_mode` branches. The router imports no dev-mode helpers and calls no mock paths; the same handler code runs in dev (moto-intercepted DynamoDB, `app/core/dev_s3.py`) and prod (real DynamoDB). This mirrors the cross-cutting constraint ("Zero `if S.dev_mode` branches in business logic", `docs/qloapps/STAY_SEARCH_RESERVATIONS_TICKETS.md` §"Dev/prod parity") and the precedent of `app/routers/inventory.py` (no `dev_mode` branch in that file). Any mock/real divergence in availability/pricing/holds is owned internally by the HTL-011/012/015 services — HTL-020 calls them identically in both envs.

### 7.2 Idempotency

- `POST /ui/hotel-search` — read-only; trivially idempotent (no state).
- `POST /ui/hotels/{hotel_id}/reservations` — **not** idempotent by design: `reservation_id = "res_" + uuid4().hex[:16]` is non-deterministic (a guest may genuinely book the same span twice, HTL-018). Two identical POSTs create two reservations + two holds. The binding check (re-check availability + atomic `hold_rooms`) is the safety mechanism, not request idempotency.
- Lifecycle sub-routes (`check-in`/`check-out`/`cancel`/`no-show`) — idempotent in the strong sense via the state machine: re-issuing a transition that has already been applied hits the empty-target-set / illegal-edge check and returns `409 invalid_status_transition` (terminal states reject all outbound edges). Exactly one HIST row per successful transition (the `version` CAS guarantees one winner).
- `confirm` — idempotent no-op: always returns the current header (§5.4).
- `PUT .../{reservation_id}` (modify) — final-state idempotent for the spatial fields; `updated_at`/`version` advance each call (not timestamp-idempotent, acceptable).

### 7.3 Security

- **Mutation/lifecycle auth**: all POST (except `/hotel-search`) and PUT endpoints require `require_admin_or_root_csrf` (`app/auth/policy.py:100`) — role `ADMIN` or `ROOT` plus CSRF for cookie-auth clients. CSRF (`enforce_cookie_csrf`, `app/auth/policy.py:71`) validates `x-csrf-token` header == `ui_csrf` cookie for non-GET cookie-auth requests; Bearer-token API clients are exempt (consistent with every other admin endpoint).
- **Read auth**: GET endpoints + `POST /ui/hotel-search` require `require_ui_session` (`app/services/sessions.py:330`) — any authenticated user.
- **Hotel-scoping**: every reservation-scoped handler enforces `existing["hotel_id"] == path hotel_id` and 404s on mismatch (§5.5), preventing cross-hotel reservation reads/drives.
- **Path traversal**: `hotel_id` / `reservation_id` are FastAPI path parameters, URL-encoded; no filesystem paths or shell commands are involved.

### 7.4 Money-safety

HTL-020 touches **no** billing table, billing service, or payment provider. `app/routers/hotel_reservations.py` imports only `hotel_reservations` (the service), the Pydantic models, and the two auth dependencies — never `billing_shared`, `refund_payment`, `new_ledger_entry`, `settle_or_reverse_ledger`, or any Stripe/PayPal/CCBill client. `cancel`/`no-show` release **held inventory only**; the refund + penalty machinery is HTL-033 (forward ref), which must route through `refund_payment` (`app/routers/billing.py`) / `settle_or_reverse_ledger` — never a parallel mechanism (ORD-001 §5.6). HTL-020 has zero financial invariants to enforce.

### 7.5 Audit trail

The router does **not** call `_audit()` directly — audit events (`hotel.reservation.created`, `hotel.reservation.status_changed`, etc.) are emitted by the HTL-018/019 service functions via the best-effort `_audit()` lazy-import wrapper (modeled on `app/services/inventory.py:92-99`). Audit failure never propagates to the HTTP caller.

## 8. Backward Compatibility & Migration

### 8.1 Additive-only changes

HTL-020 adds:
- **One new file**: `app/routers/hotel_reservations.py` — additive; no existing router file is modified.
- **Two lines in `app/main.py`**: one import (~`:311`, adjacent to the inventory router import) and one `include_router` (~`:877`, adjacent to the `inventory_router` include) — additive; downstream include line numbers shift by one (a line-number shift, not a behavioral change).

No existing endpoint, service function, DynamoDB table, Pydantic model, or configuration key is modified. With `HOTEL_PMS_ENABLED=false` (the default), every new handler returns 404 and produces zero DynamoDB traffic.

### 8.2 No DynamoDB migration

HTL-020 uses the `hotel_reservations` table declared by HTL-018 in `scripts/local-ddb-init.py`. No new `TableDef`, no new GSI, no `attr_types` change. `just restart` in dev recreates the table from the HTL-018 `TableDef` automatically.

### 8.3 Production deployment sequence

1. Deploy HTL-017/018/019 code with `HOTEL_PMS_ENABLED=false` — creates the `hotel_reservations` table via infra provisioning; service functions exist but are unreachable over HTTP.
2. Deploy HTL-020 code with the flag still `false` — router mounted, all handlers 404.
3. Enable `HOTEL_PMS_ENABLED=true` (after the HTL-011/012/015 forward-dep clusters are deployed + their flags on) once the `hotel_reservations` table is verified healthy — all 11 endpoints become live.

Each step is zero-downtime and fully reversible by toggling the flag.

### 8.4 Rollback

Reverting HTL-020 requires removing `app/routers/hotel_reservations.py` and reverting the two `app/main.py` lines. A faster operational rollback is setting `HOTEL_PMS_ENABLED=false` — the router stays mounted but every handler 404s, disabling the feature without redeployment.

## 10. Open Questions / Assumptions

### 10.1 Read endpoints are not guest-scoped

`GET .../reservations` and `GET .../reservations/{id}` enforce hotel-scoping (§5.5) but not guest-scoping — any authenticated user with a valid session can read any reservation under a hotel they query. **Assumption**: a single-platform front-desk deployment where reads are operator-facing. If guest self-service (a guest viewing only their own bookings) is required, a `guest_party_id`-scoped read (querying `GSI_GUEST`) is an additive follow-up, not a change to HTL-020's admin/operator surface.

### 10.2 `POST /ui/hotel-search` read auth + POST verb

Using POST with `require_ui_session` (read auth) for a read-only operation is a deliberate funnel design (§5.2). **Assumption**: search must be reachable by any authenticated user and the criteria object is too rich for the query string. If search must be fully public (pre-login booking engine), a separate unauthenticated public router is a future ticket (the booking-engine storefront, out of scope per the cluster doc).

### 10.3 `list_reservations` is treated as a HTL-018 deliverable

The §HTL-018 description does not name `list_reservations` explicitly, but the §HTL-020 endpoint table requires `GET /ui/hotels/{hotel_id}/reservations` to paginate `GSI_HOTEL_ARRIVALS` / `GSI_HOTEL_STATUS`. **Assumption**: `list_reservations(*, hotel_id, status, checkin_from, checkin_to, cursor, limit) -> {reservations, count, cursor}` is a HTL-018-layer lister (the two GSIs exist for exactly this query). If it is not delivered by HTL-018, HTL-020 must add it to `app/services/hotel_reservations.py` (a small additive service function reusing `encode_cursor`/`decode_cursor`). Either way the router code is unchanged.

### 10.4 `confirm` is a placeholder

`confirm` is currently an idempotent no-op (§5.4) because reservations are born `confirmed`. **Assumption**: a future `draft` state (cart-hold before commitment) will give `confirm` real `draft → confirmed` semantics; the route is reserved now to avoid a later breaking path change. Until then, callers may treat `confirm` as "fetch the (already-confirmed) reservation."

### 10.5 Optional bodies on `check-out`/`cancel`/`no-show`

These three sub-routes accept an optional `ReservationTransitionIn` body solely for `reason` (their `target_status` is route-fixed, `assigned_room_ids` is irrelevant). **Assumption**: making the body optional (`ReservationTransitionIn | None = None`) is acceptable so callers can fire the action with no payload. If a mandatory cancellation `reason` is later required for audit/compliance, the model can require it without changing the route shape.
