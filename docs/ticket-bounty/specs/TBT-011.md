## 1. Summary & Goal

TBT-011 closes the bounty milestone by delivering a full test suite that proves every money invariant,
state-machine transition, and security gate defined in TBT-001 through TBT-010. Two test layers are required:

1. **`tests/test_ticket_bounties.py`** — hermetic offline pytest suite. Uses moto-bound frozen table handles
   and route-handler coroutines called directly (no TestClient, which is broken in this env). Covers all
   happy paths, sad paths, and concurrency races.

2. **`frontend/e2e/ticket-bounties.spec.ts`** — end-to-end Playwright spec. Drives the full user
   journey (bounty board → claim → submit → admin approve) against the live dev stack, verifying that
   wallet balances change correctly and the UI reflects every state.

The goal is not to re-test the service primitives (billing_shared, fraud_detection, etc.) which have
their own suites; it is to assert the *composition* — that the bounty service orchestrates those
primitives in the correct order, with correct amounts, and that no money leaks or double-charges
can occur.

|---|---|---|

| `ticket_id` | S | Back-reference |
| `poster_sub` | S | User who posted the bounty |
| `amount_cents` | N | Held amount (original posted amount) |
| `currency` | S | |
| `status` | S | `held` \| `released` \| `refunded` |
| `created_at` | N | Unix ts |
| `ledger_sk` | S | `sk` of the corresponding audit ledger entry (`LEDGER#{ts}#{entry_id}`) |
| `released_to` | S | Assignee `user_sub`; set on approve |
| `released_by` | S | Admin `user_sub`; set on approve |
| `released_at` | N | Unix ts; set on approve |

The escrow `put_item` uses `ConditionExpression="attribute_not_exists(pk)"` — the
idempotency guard that prevents double-escrow on network retry. This is the correct guard
because `pk=BOUNTY#{bounty_id}` is globally unique (the bounty id is derived deterministically
from `ticket_id`), so `attribute_not_exists(pk)` ensures exactly one escrow row per bounty.
This matches TBT-003 §3 and §5 step (b) exactly. (Earlier drafts incorrectly cited
`attribute_not_exists(sk)` here — the SK-based form from `group_treasury.py:604` guards ledger entries
whose SKs embed a random ulidish; the escrow Put uses the PK guard per TBT-003.)

## 5. Detailed Behavior & Edge Cases

### Bounty state machine

```
          post_bounty
 (none) ─────────────► funded ──claim──► claimed ──submit──► submitted
                          │                 │                      │
                          │ cancel          │ unclaim              │ approve ──► paid_out (terminal)
                          ▼                 ▼                      │ reject  ──► claimed (back)
                       cancelled ◄──────── funded ◄───────────────┘
                       (terminal)
```

Admin cancel is allowed in `funded`, `claimed`, `submitted`. Poster can only self-cancel while
`funded` and `claimed_by_sub` is absent. `paid_out` and `cancelled` are terminal; any
state-transition attempt returns 409.

### `post_bounty` — atomic escrow hold

1. Validates `amount_cents` within `[S.ticket_bounty_min_cents, S.ticket_bounty_max_cents]`.
2. Loads ticket; enforces owner check; enforces `bounty_status` is absent/`none`.
3. Calls `_fraud_gate(poster_sub, amount_cents, "bounty_hold", tx_id=ticket_id, enforce_block=True, req=request)`.
4. Computes `bounty_id = hashlib.sha256(f"bounty:{ticket_id}".encode()).hexdigest()[:24]`.
5. Issues a single `transact_write_items` with three operations:
   - **Update** `pk=USER#{poster}` / `sk=WALLET`: `SET wallet_balance_cents = wallet_balance_cents - :amt`
     with `ConditionExpression="wallet_balance_cents >= :amt"`. On `TransactionCanceledException`
     with `ConditionalCheckFailed` on this item → raise 402 "insufficient balance".
   - **Put** `pk=BOUNTY#{bounty_id}` / `sk=ESCROW` with `ConditionExpression="attribute_not_exists(pk)"`.
     On `ConditionalCheckFailed` for this item → the bounty was already posted (idempotent replay);
     return the existing ticket state without error.
   - **Put** ledger debit entry (pre-built via `new_ledger_entry`).
6. Updates ticket META via `TicketStore._apply_header_update_once` to set bounty fields and
   `gsi_bounty_pk="BOUNTY#OPEN"` / `gsi_bounty_sk=created_at`.
7. Emits `audit_event("bounty_posted", poster_sub, ...)`.

**Insufficient balance**: `TransactionCanceledException` is inspected; the `CancellationReasons`
list identifies which condition failed by position. Position 0 = wallet, position 1 = escrow.
Only a wallet condition failure → 402; an escrow condition failure → idempotent.

### `claim_bounty` — single-winner conditional

Uses `T.tickets.update_item` with
`ConditionExpression="attribute_not_exists(claimed_by_sub) AND bounty_status = :funded"`.
A `ConditionalCheckFailedException` means either already claimed (409 "already claimed") or not
funded (409 "ticket not claimable"). After claiming: sets `claimed_by_sub`, `claimed_at`,
`assigned_to_sub`, `bounty_status="claimed"`, ticket `status="in_progress"`, clears
`gsi_bounty_pk`/`gsi_bounty_sk` (so the ticket drops off the board).

**Race**: two simultaneous `claim_bounty` calls for the same ticket: DynamoDB's conditional
write is serialized server-side; exactly one wins, the other receives `ConditionalCheckFailedException`
and the service returns 409. No retry loop — caller re-presents the ticket.

### `unclaim_bounty` — abandonment (D4: manual unclaim, no auto-refund)

Enforces `claimed_by_sub == claimer_sub` (403 if not). Sets `bounty_status="funded"`, clears
`claimed_by_sub`/`claimed_at`/`assigned_to_sub`, re-sets `gsi_bounty_pk="BOUNTY#OPEN"` /
`gsi_bounty_sk=created_at` so the ticket reappears on the board. Escrow row is untouched.

### `approve_bounty` — release escrow → assignee credit

1. Loads `BOUNTY#{bounty_id}/ESCROW`; requires `status=="held"` (409 if already released or refunded).
2. Computes `fee_cents = amount_cents * S.ticket_bounty_fee_bps // 10000` (default 0 with D1).
   `net_cents = amount_cents - fee_cents`.
3. **Credit assignee**: `new_ledger_entry(key_name="pk", key_value=USER#{assignee}, entry_type="credit",
   state="settled", amount_cents=net_cents, reason="bounty_payout", meta={...})`.
4. **Credit assignee wallet**: `apply_wallet_delta(T.billing, USER#{assignee}, +net_cents)`.
5. **Settle escrow audit entry**: `settle_or_reverse_ledger(T.billing, "pk", USER#{poster},
   escrow_row["ledger_sk"], "settled_released")`.
6. **Update escrow row**: `status="released"`, `released_to`, `released_by`, `released_at`, `fee_cents`.
   Uses `ConditionExpression="#s = :held"` for idempotency — a replayed approve is a no-op.
7. Updates ticket META: `bounty_status="paid_out"`, ticket `status="paid_out"`, `bounty_paid_at`.
8. Sends notification to assignee via `alerts.audit_event` / alert.
9. Emits `audit_event("bounty_released", admin_sub, ...)`.

**No `write_tip_ledger` call.** The poster's wallet was debited once at `post_bounty`; calling
`write_tip_ledger` here would debit them a second time (it always debits `tipper_user_id`).

**Idempotency**: the `ConditionExpression="status = :held"` on the escrow `update_item`
means a second `approve_bounty` call sees `status="released"` and the condition fails; the
service returns the current ticket state without re-crediting the assignee.

### `cancel_bounty` — refund to poster

Permission check: poster can cancel only when `bounty_status=="funded"` and unclaimed. Admin can
cancel in `funded`, `claimed`, `submitted`. Nobody can cancel `paid_out` or `cancelled` (409).

Refund flow (mirrors `billing.py:1286–1345`):

1. Build refund ledger entry: `new_ledger_entry(key_name="pk", key_value="USER#{poster}",
   entry_type="adjustment", amount_cents=escrow["amount_cents"], state="settled",
   reason="bounty_refund", meta={"bounty_id": ..., "reason": reason})`.
2. Issue `transact_write_items`:
   - **Update** escrow row: `status="refunded"`, `refunded_at`, `refund_ledger_sk`.
     `ConditionExpression="#s = :held"` — if already refunded, the transaction fails and the
     service returns a 409-idempotent no-op.
   - **Put** refund ledger entry.
   - **Update** poster wallet: `wallet_balance_cents += amount_cents` (unconditional, always
     safe for a credit).
3. After transaction: `settle_or_reverse_ledger(..., escrow["ledger_sk"], "reversed")`.
4. Updates ticket META: `bounty_status="cancelled"`, clears `gsi_bounty_pk`/`gsi_bounty_sk`,
   sets `bounty_cancelled_at`.
5. Notifies poster (and claimant if `claimed_by_sub` was set).
6. Emits `audit_event("bounty_cancelled", actor_sub, ...)`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

**SECOPS-007 parity**: no `dev_mode` branch anywhere in the bounty service. `T.billing`
interactions go through the same DynamoDB table whether moto (dev) or real DynamoDB (prod).
The fraud-detection module (`billing.py:118–175`) already short-circuits cleanly when
`FRAUD_DETECTION_ENABLED=0` — no new bypass needed.

**Idempotency**:
- `post_bounty`: `attribute_not_exists(pk)` on the escrow `Put` in the `transact_write_items`
  call (TBT-003 §3 and §5 step b). A duplicate post (network retry after
  a timeout) finds the escrow row already present, the condition fails, and the transaction is
  cancelled. The service detects this by inspecting
  `CancellationReasons[1].Code == "ConditionalCheckFailed"` and returns the current ticket state
  without re-debiting.
- `approve_bounty`: `ConditionExpression="#status = :held"` on the escrow update. Second
  call finds `status="released"`, condition fails, service returns no-op.
- `cancel_bounty`: `ConditionExpression="#status = :held"` on the escrow update in the
  `transact_write_items`. Second call finds `status="refunded"`, service returns 409.
- `claim_bounty`: `attribute_not_exists(claimed_by_sub)` conditional enforces single-winner.

**Money-safety invariants**:
- Poster debited exactly once: the `transact_write_items` at `post_bounty` atomically debits
  the poster wallet and creates the escrow row. Subsequent approve/cancel never debit the poster.
- Assignee credited exactly once: the approve path uses a conditional update on the escrow row
  (`status: held → released`); replays cannot credit twice.
- Full refund: cancel credits the poster's wallet exactly the `amount_cents` from the escrow
  row (no haircut by default; fee logic applies only at payout).
- No negative wallet: `apply_wallet_delta` for withdrawals enforces
  `wallet_balance_cents >= :needed` (billing_shared.py:209); the bounty hold uses the same
  condition inside the `transact_write_items`.

**Security**:
- Frozen/fraud-blocked poster → `_fraud_gate` raises 403 before the `transact_write_items`
  is attempted (billing.py:134–164).
- Only the ticket owner may post a bounty (service enforces `owner_sub == poster_sub`).
- Only the claimant may submit or unclaim (service enforces `claimed_by_sub == actor_sub`).
- Only admins/root may approve or reject (router enforces `_is_admin_actor`).
- Admin or owner (only while unclaimed) may cancel.
- `paid_out` and `cancelled` escrows are permanently terminal — no backdoor path reachable.

## 8. Backward Compatibility & Migration

With `TICKET_BOUNTIES_ENABLED=false` (the default):

- `_TICKET_STATUSES` and `_STATUS_TRANSITIONS` in `tickets.py` are unchanged.
- `create_ticket` writes no new attributes (bounty fields are absent).
- `get_ticket` projection returns no new keys (absent DDB attrs map to `None` defaults in
  `TicketOut`; callers that don't know about `bounty_id` etc. see only the fields they
  already expect).
- All eight bounty endpoints return 404 immediately via `_require_bounties_enabled()`.
- No DynamoDB table changes are required for the flag-off path; the sparse `ByBounty` GSI
  is added to the `tickets` `TableDef` in `scripts/local-ddb-init.py` (and dev stacks gain
  it after `just restart`), but the GSI is never populated while the flag is off.

**No migration for existing tickets**: bounty fields are absent on old META rows; the sparse
`gsi_bounty_pk`/`gsi_bounty_sk` index keys are written only when a bounty is posted
(`bounty_status="funded"`), so pre-existing tickets never appear in the bounty board index.

## 10. Open Questions / Assumptions

1. **D1 — Fee default 0%**: Spec assumes `ticket_bounty_fee_bps=0`. If product decides to enable
   a fee, the `approve_bounty` fee path is already coded; the test parametrizes over both.

2. **D2 — Wallet-only funding**: Spec assumes `post_bounty` debits the poster's DynamoDB
   wallet balance only. Card-at-post-time is explicitly out of scope for v1 (per ticket).

3. **D3 — Any owner may post**: No role restriction beyond ownership. Bounded by min/max +
   fraud gate. Assumed correct per the ticket spec.

4. **D4 — Manual unclaim, no idle sweep**: `unclaim_bounty` returns the ticket to the board with
   escrow held. Idle-sweep (auto-refund after N days) is a follow-up; no timer is implemented here.

5. **`transact_write_items` in `FakeBillingTable`**: The fake must accurately simulate
   `TransactionCanceledException` with a `CancellationReasons` list in the same position-indexed
   shape as the real DynamoDB response. The positions must match the `TransactItems` list order:
   index 0 = wallet update, index 1 = escrow put, index 2 = ledger put.

6. **`paid_out` ticket status**: `paid_out` must be added to `_TICKET_STATUSES` by TBT-004 for the
   projection to be valid; the test suite asserts it appears in `get_ticket` response `status`.
   This spec assumes TBT-004 is merged before TBT-011 tests run.

7. **`pending_approval` status**: similarly added by TBT-004. Submit sets `ticket.status =
   "pending_approval"` (not `"done"`); the test suite verifies the gate behavior.

8. **Route declaration order in `tickets.py`**: `GET /tickets/bounties/open` must appear before
   the `GET /tickets/{ticket_id}` route. If this is wrong, the E2E `GET /tickets/bounties/open`
   will return 404 or a 422 (unrecognised ticket_id format). The test suite should assert
   the correct HTTP status as an early smoke-check.

9. **`cancelled` as a ticket `status`**: TBT-004 adds `cancelled` as a reachable status value for
   bountied tickets. It must be appended to `_TICKET_STATUSES` (not `_STATUS_TRANSITIONS` —
   it is a terminal state reachable only through the bounty cancel endpoint, not via
   `update_status`). The test validates that `update_status(..., "cancelled")` raises an error
   while the bounty cancel endpoint succeeds.
