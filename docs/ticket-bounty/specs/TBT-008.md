## 1. Summary & Goal

TBT-008 delivers the **public bounty board** and **per-ticket amount visibility**. Both are read-only query surfaces that depend entirely on data infrastructure established by earlier tickets (TBT-002 adds the sparse `ByBounty` GSI and `bounty_amount_cents` projection; TBT-005 writes the claim/unclaim transitions that add and remove tickets from the board). TBT-008's own scope is:

1. A service function `list_open_bounties(cursor, limit)` that queries the `ByBounty` sparse GSI to return only funded, unclaimed tickets with their amount, subject, labels, and `created_at`.
2. Verification that the single-ticket detail projection (already extended by TBT-002) exposes `bounty_amount_cents` and `bounty_status` to **any authenticated viewer**, not just the owner — so a user browsing the board can open a ticket and see the amount before claiming.
3. A `GET /tickets/bounties/open` router endpoint (declared **before** any `/{ticket_id}` dynamic segment, for FastAPI path-match ordering) backed by the service function.
4. The companion frontend types and API wrapper added to `frontend/src/api/endpoints/tickets.ts` and `frontend/src/api/types.ts`.

Nothing in this ticket posts, claims, approves, or moves money. All state-mutating paths are in TBT-003 through TBT-007. TBT-008 is a read path that makes the board functional.

## 2. Context & Current State

### Ticket system single-table design

The ticket service (`app/services/tickets.py`) uses `T.tickets` with a single-table layout. Every ticket occupies a DynamoDB partition `pk=TICKET#{ticket_id}` (`tickets.py:164`). The META row (`sk="META"`) holds all header fields. The projection function `get_ticket` (`tickets.py:522-566`) reads the META row and then prefix-scans MSG and ACT rows in the same partition.

`_query_headers_by_index` (`tickets.py:584-601`) is the generic GSI-paged query helper: it takes an `index_name`, a partition key value, a key expression, a `limit`, and an opaque base64 cursor, and returns `(items, next_cursor)`. All existing `list_*` methods reuse it (e.g., `list_tickets` at `tickets.py:614-645`). The bounty board query fits the same pattern with no new plumbing.

No `ByBounty` GSI exists today. TBT-002 adds it. TBT-008 queries it.

### ByBounty sparse GSI (established by TBT-002)

TBT-002 sets `gsi_bounty_pk="BOUNTY#OPEN"` and `gsi_bounty_sk=created_at` (integer) on the ticket META row only when `bounty_status == "funded"`. When a ticket is claimed (TBT-005), `gsi_bounty_pk` and `gsi_bounty_sk` are removed from the META row so the ticket drops off the board. When unclaimed, those attributes are restored. Non-bounty tickets never carry these attributes (sparse index). The `gsi_bounty_sk` is a numeric sort key, so `scripts/local-ddb-init.py` must declare `attr_types={"gsi_bounty_sk": "N"}` for the `ByBounty` GSI entry.

### Ticket projection (established by TBT-002)

TBT-002 extends `get_ticket` (`tickets.py:522-566`) to include:
- `bounty_amount_cents: int | None`
- `bounty_currency: str | None`
- `bounty_status: str | None` — one of `none | funded | claimed | submitted | paid_out | cancelled`
- `bounty_id: str | None`
- `claimed_by_sub: str | None`
- `claimed_at: int | None`
- `bounty_funded_at: int | None`
- `bounty_submitted_at: int | None`
- `bounty_paid_at: int | None`
- `bounty_cancelled_at: int | None`

All are additive; tickets without a bounty return all as `None`.

### Access control today

The `_can_access_ticket` helper (`tickets.py (router):339-340`) permits access to a ticket if `user.sub == ticket["owner_sub"]` or if the caller is an admin/root. This restricts who can call `GET /tickets/{ticket_id}`. For the bounty board to be useful — anyone browsing open bounties must be able to open the detail — the access check for `GET /tickets/{ticket_id}` must be widened when the ticket has `bounty_status="funded"` (or any public bounty state). TBT-008 documents this required widening.

### Router ordering constraint

`app/routers/tickets.py:25` registers the router with prefix `/tickets`. FastAPI matches routes in declaration order. The existing admin summary endpoint is declared as `GET /tickets/admin/summary` (`tickets.py (router):887`) — a literal path segment — before `GET /{ticket_id}` at line 900. Similarly, `GET /tickets/bounties/open` must be declared **before** any `GET /tickets/{ticket_id}` (dynamic) segment, otherwise `bounties` would be consumed as a `ticket_id`. The existing code already has the `admin/summary` endpoint declared before `GET /{ticket_id}`, so the pattern is established.

### Frontend baseline

`frontend/src/api/endpoints/tickets.ts` exports typed wrappers for all ticket endpoints. `frontend/src/api/types.ts` defines the `Ticket` interface (currently without bounty fields). Neither file has any bounty-related code. The `api` client in `frontend/src/api/client.ts` is the shared axios instance; all wrappers use it.

## 3. Data Model

TBT-008 introduces **no new DynamoDB tables and no new rows**. It is purely a query over structures established by TBT-002.

### ByBounty GSI on T.tickets (established by TBT-002, queried here)

**Table:** `T.tickets` (name from `S.tickets_table_name`, default `"tickets"`)  
**GSI name setting:** `S.tickets_bounty_index_name` (new in TBT-001/002, default `"bounty-open-created_at-index"` per TBT-002)

| Attribute | Value when funded | Value when not funded / claimed |
|---|---|---|
| `gsi_bounty_pk` (S) | `"BOUNTY#OPEN"` | absent (sparse) |
| `gsi_bounty_sk` (N) | `created_at` (integer Unix seconds) | absent (sparse) |

`ScanIndexForward=False` on the GSI query gives newest-first ordering (largest `created_at` first).

The `attr_types` declaration in `scripts/local-ddb-init.py` for this GSI entry must be:

```python
{"index_name": S.tickets_bounty_index_name, "partition_key": "gsi_bounty_pk", "sort_key": "gsi_bounty_sk"}
```

with the enclosing `TableDef` carrying `attr_types={"gsi_bounty_sk": "N"}`.

### Projected attributes returned by the board query

The GSI stores only the META row attributes. `_query_headers_by_index` returns those raw header dicts; `_assemble_headers` then calls `get_ticket` per item to hydrate messages and activities. For the board list endpoint, a lightweight projection is preferred (skip MSG/ACT assembly). Section 4 describes the `_assemble_bounty_headers` variant.

### No changes to T.billing

TBT-008 does not read or write `T.billing`. Escrow records (`pk=BOUNTY#{bounty_id}`, `sk=ESCROW`) are established by TBT-003; TBT-008 does not expose them through the board API.

## 4. API / Service Design

### 4.1 Service function — `list_open_bounties`

**File:** `app/services/tickets.py`  
**Class:** `TicketStore` (the `STORE` singleton)

```python
def list_open_bounties(
    self,
    *,
    limit: int = 25,
    cursor: str | None = None,
) -> dict[str, Any]:
    """
    Query the ByBounty sparse GSI for funded+unclaimed tickets.
    Returns {"bounties": [<lightweight dict>, ...], "next_cursor": str | None}.
    """
```

**Implementation steps:**

1. `_require_bounties_enabled()` (raises `HTTPException(404)` when `S.ticket_bounties_enabled` is false).
2. `page_limit = max(1, min(int(limit or 25), 100))`.
3. Call `_query_headers_by_index` with:
   - `index_name=S.tickets_bounty_index_name`
   - `pk="BOUNTY#OPEN"`
   - `key_expr="gsi_bounty_pk = :pk"`
   - `limit=page_limit`
   - `cursor=cursor`
4. For each raw header dict returned, call `_project_bounty_header(row)` (see below) instead of the full `get_ticket` round-trip to avoid N MSG/ACT queries per board page.
5. Return `{"bounties": projected_list, "next_cursor": next_cursor}`.

**`_project_bounty_header(row: dict) -> dict`** — lightweight projection from the raw GSI header row:

```python
def _project_bounty_header(self, row: dict[str, Any]) -> dict[str, Any]:
    return {
        "ticket_id": row.get("ticket_id", ""),
        "subject": row.get("subject", ""),
        "owner_sub": row.get("owner_sub", ""),
        "status": row.get("status", "open"),
        "labels": list(row.get("labels") or []),
        "created_at": int(row.get("created_at", 0) or 0),
        "updated_at": int(row.get("updated_at", 0) or 0),
        "bounty_amount_cents": int(row.get("bounty_amount_cents") or 0),
        "bounty_currency": row.get("bounty_currency", "usd"),
        "bounty_status": row.get("bounty_status"),
        "bounty_id": row.get("bounty_id"),
        "bounty_funded_at": row.get("bounty_funded_at"),
    }
```

This avoids `get_ticket`'s two additional `query()` calls (MSG/ACT prefix scans) per ticket on every board page load. If `space_id` is needed by the frontend it can be added to this projection without a back-end re-fetch.

### 4.2 Access widening for GET /tickets/{ticket_id}

**Current check** (`app/routers/tickets.py:339-340`):
```python
def _can_access_ticket(request, user, ticket) -> bool:
    return user.sub == ticket["owner_sub"] or _is_admin_actor(request, user)
```

**Required change** — any authenticated user may view a ticket that is in a public bounty state:

```python
_PUBLIC_BOUNTY_STATUSES = {"funded", "claimed", "submitted"}

def _can_access_ticket(request, user, ticket) -> bool:
    if user.sub == ticket["owner_sub"] or _is_admin_actor(request, user):
        return True
    if ticket.get("bounty_status") in _PUBLIC_BOUNTY_STATUSES:
        return True
    return False
```

This is the minimum change needed so a user who spots a bounty on the board can open it and read the subject, description, and amount before deciding to claim. `paid_out` and `cancelled` bounties remain owner/admin-only since they carry completed financial details. Note: `"pending_approval"` is a **ticket** `status` value (set by TBT-004 when a claimant submits), not a `bounty_status` value; the `bounty_status` for a ticket-in-pending-approval is `"submitted"`, which is already covered above.

## 5. Detailed Behavior & Edge Cases

### 5.1 Board membership invariants

A ticket appears on the bounty board if and only if its META row on `T.tickets` carries `gsi_bounty_pk="BOUNTY#OPEN"`. This attribute is:

- **Set** by `post_bounty` (TBT-003) when escrow is confirmed: `bounty_status` flips to `"funded"`.
- **Removed** by `claim_bounty` (TBT-005) when a user wins the conditional claim: `bounty_status` flips to `"claimed"`, GSI attrs removed.
- **Restored** by `unclaim_bounty` (TBT-005) when the claimant releases the ticket: `bounty_status` returns to `"funded"`, GSI attrs restored.
- **Removed permanently** by `cancel_bounty` (TBT-007) and `approve_bounty` (TBT-006) when the bounty reaches a terminal state.

Because GSI projection happens at write time in DynamoDB, the board reflects the state of `gsi_bounty_pk` as of the last META row update. There is no eventual consistency window beyond standard DynamoDB replication (typically single-digit milliseconds for the same region).

### 5.2 Race between board read and claim

A user calls `GET /tickets/bounties/open`, receives ticket `T`, and then calls `POST /tickets/T/bounty/claim`. Between the list response and the claim attempt, another user may have already claimed `T`. TBT-005's conditional-put ensures exactly one winner; the loser gets 409. The board list does not need to be transactional — stale reads are tolerable (the claim itself is the single-winner gate). No special handling is needed in TBT-008.

### 5.3 Amount always visible before claiming

`GET /tickets/{ticket_id}` returns `bounty_amount_cents` and `bounty_status` as part of the `TicketOut` projection added by TBT-002. After the access-widening change in section 4.2, any authenticated user can open a ticket with `bounty_status` in `{funded, claimed, submitted}` and read the amount. This satisfies the acceptance criterion "Amount is visible on the ticket detail before claiming." (A ticket in the pending-approval state has `bounty_status="submitted"`, which is included.)

### 5.4 Pagination correctness

The `ByBounty` GSI uses `created_at` (integer) as the sort key with `ScanIndexForward=False` (newest first). DynamoDB's cursor-based pagination (`ExclusiveStartKey`) is deterministic: a page boundary is stable as long as no items are inserted or deleted mid-pagination with a `created_at` between the last returned item and the boundary key. Since bounties are funded once (monotonically increasing `created_at`), new bounties appear at the front of the list (not mid-pagination); their arrival does not corrupt a cursor pointing into older items.

However: if a ticket is **claimed** while a client is paginating, it disappears from the GSI (sparse index). The DynamoDB `Limit` parameter is applied to the number of items scanned, not returned, so a sparse deletion mid-page can return fewer items than `limit` without it indicating end-of-results. The service must NOT treat `len(items) < limit` as exhaustion; it must always use `LastEvaluatedKey` presence to determine whether there is a next page. `_query_headers_by_index` already handles this correctly (`tickets.py:596-600`).

### 5.5 Empty board

When no funded tickets exist, the GSI query returns an empty `Items` list and no `LastEvaluatedKey`. The endpoint returns `{"bounties": [], "next_cursor": null}` — a valid 200.

### 5.6 Flag-off behavior

When `S.ticket_bounties_enabled` is `false`, `_require_bounties_enabled()` raises `HTTPException(status_code=404)`. The board endpoint returns 404. The `_can_access_ticket` widening for bounty statuses is harmless when the flag is off because no ticket will ever carry a non-null `bounty_status` (the data was never written). To be safe, the widening check can be made conditional on `S.ticket_bounties_enabled`:

```python
if S.ticket_bounties_enabled and ticket.get("bounty_status") in _PUBLIC_BOUNTY_STATUSES:
    return True
```

`_PUBLIC_BOUNTY_STATUSES = {"funded", "claimed", "submitted"}` — `"pending_approval"` is deliberately excluded because it is a ticket `status` value, not a `bounty_status` value. A ticket with ticket status `pending_approval` has `bounty_status="submitted"`, which is already in the set.

### 5.7 Limit clamping

`limit` is clamped to `[1, 100]` at both the router (Pydantic `ge=1, le=100`) and the service (`max(1, min(limit, 100))`). The default is 25.

### 5.8 Interaction with space-scoped tickets

A ticket may belong to a `space_id`. Space membership controls ticket visibility for non-public tickets through a separate access path. For bounty-board purposes: the `ByBounty` GSI indexes any funded ticket regardless of `space_id`. A ticket in a private space can therefore appear on the public board. This is by design — the bounty poster chose to post a monetary reward, which implicitly invites claimants who may not be space members. The claim endpoint (TBT-005) does not require space membership. If the product decides that private-space tickets should not appear on the public board, a `FilterExpression` on `space_id IS NULL` could be added to `list_open_bounties`, but that is out of scope for TBT-008.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 parity

TBT-008 is a read-only DynamoDB query. There is no `dev_mode` branch, no mock path, and no AWS service call beyond DynamoDB. The same code runs against moto in dev and real DynamoDB in prod. No divergence exists.

### Idempotency

`list_open_bounties` is a pure read. Calling it multiple times returns the current state of the board; no state is mutated. The endpoint is naturally idempotent.

### Security

- Auth: `require_ui_session` ensures a valid authenticated session for every request to `/tickets/bounties/open`. Anonymous access is not supported.
- No CSRF risk: `GET` endpoints are exempt from CSRF checks in `require_ui_session` (`app/auth/deps.py`).
- The board exposes only funded/unclaimed tickets and their subject, labels, amount, and created timestamp. It does not expose private messages, activity history, or owner PII beyond `owner_sub` (already present on all ticket list responses).
- The access widening in `_can_access_ticket` is deliberately scoped to a finite set of public `bounty_status` values (`funded`, `claimed`, `submitted`). `paid_out` and `cancelled` tickets remain owner/admin-only. This prevents a user from reading sensitive resolution details (e.g., payout amounts to specific assignees) without authorization. `"pending_approval"` is excluded from the set because it is a ticket status, not a `bounty_status` — a ticket in the pending-approval state already has `bounty_status="submitted"` which grants access.

### Money-safety

TBT-008 involves no money movement, no escrow reads, and no billing table access. It cannot trigger double-charge, incorrect balance, or refund issues. All money invariants are enforced by TBT-003, TBT-006, and TBT-007.

## 8. Backward Compatibility & Migration

### With `TICKET_BOUNTIES_ENABLED=false` (default)

- `GET /tickets/bounties/open` returns 404.
- `_can_access_ticket` has a guard on `S.ticket_bounties_enabled`, so existing ticket visibility is unchanged.
- The `ByBounty` GSI exists on the table (added by TBT-002 schema migration) but is never populated; it has zero items. Presence of an empty GSI does not affect any existing query.
- `TicketOut` has `bounty_*` fields (additive, all `None`) from TBT-002. Existing API consumers that ignore unknown fields are unaffected. Existing consumers that use strict deserialization (e.g., the frontend's `Ticket` interface) receive `undefined` for the new optional fields.

### DynamoDB table migration

TBT-002 adds the `ByBounty` GSI to `scripts/local-ddb-init.py`. In dev, `just restart` recreates the table with the new GSI. In prod, an `UpdateTable` operation on the `tickets` table is required to add the GSI before any bounty endpoint is deployed. DynamoDB backfills GSI entries asynchronously; since no existing META rows carry `gsi_bounty_pk`, the backfill is a no-op (sparse index starts empty). No data migration is needed.

### Frontend backward compatibility

The `Ticket` interface gains optional fields with `?`. All existing destructuring and rendering code that does not reference bounty fields is unaffected. The new `listOpenBounties` wrapper is only called from the Bounty Board page (TBT-010), which does not exist yet.

## 10. Open Questions / Assumptions

**OQ-1 — Private-space ticket visibility on the public board.**  
This spec assumes any funded ticket appears on the board regardless of `space_id`. If the product decides private-space tickets should require space membership to view, a `FilterExpression` exclusion needs to be added to `list_open_bounties` and the access-widening logic in `_can_access_ticket` must also check space membership. Deferred to product review.

**OQ-2 — `owner_sub` exposure on the board.**  
The board item projection includes `owner_sub` (a user sub string). This is already exposed on all ticket list responses to authenticated users. Assumed acceptable; if user sub leakage is a concern, replace with a display name or anonymize it. Deferred to product.

**OQ-3 — Board sort key: `created_at` vs. `bounty_amount_cents`.**  
The spec follows the ticket description and uses `created_at` as the `ByBounty` GSI sort key (newest bounties first). An alternative is to allow sort-by-amount. DynamoDB GSIs only support one sort key; sort-by-amount would require a second GSI or in-memory sorting after fetching. Assumed `created_at` (newest-first) for v1. If product wants amount-sorted board, this is a new GSI. Deferred.

**OQ-4 — Bounty amount range filtering.**  
The board returns all funded bounties. No server-side filter by amount is specified. If a client-side amount filter is sufficient for v1, no API change is needed. Deferred.

**OQ-5 — Assumption: `_require_bounties_enabled()` defined in TBT-001.**  
This spec assumes TBT-001 defines `_require_bounties_enabled()` in `app/services/ticket_bounties.py` and that the function is imported into the router in TBT-009. If the helper is defined inline in the router file instead, TBT-008's router usage is the same.

**OQ-6 — Open Decision D3 (who may browse the board).**  
Open Decision D3 recommends "any owner" for posting but is silent on who may browse the public board. This spec assumes any authenticated user may call `GET /tickets/bounties/open` — consistent with the ticket description "a user looks at it to assign themselves." If browsing is restricted to specific roles or subscription tiers, the `require_ui_session` dependency must be augmented accordingly.
