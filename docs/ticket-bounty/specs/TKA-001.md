# TKA-001 — Attachment presign + store

**Milestone:** 2 — Ticket file attachments
**Type:** Feature | **Priority:** P1 | **Estimate:** 1.5 days
**Status:** Design — 2026-06-11

---

## 1. Summary & Goal

Add the ability for ticket owners and assignees to attach files to a ticket. The flow mirrors the messaging image-upload pattern: the client first calls a presign endpoint to obtain a time-limited S3 PUT URL, uploads the file directly to S3, then calls a confirm endpoint to record attachment metadata in DynamoDB. The feature is entirely additive and is gated behind `S.ticket_attachments_enabled` (default **off**). With the flag off, the ticket system is byte-for-byte unchanged.

This ticket covers only the two-step "presign + store" flow. Listing, download-URL generation, and deletion are addressed in TKA-002; the frontend and full test suite are in TKA-003.

## 2. Context & Current State

### Existing ticket system

`app/services/tickets.py` owns the single-table `T.tickets` store. The tickets table uses a `pk`/`sk` composite key:

- META row: `pk=TICKET#{ticket_id}`, `sk=META` (`app/services/tickets.py:164-169`, `441-476`)
- Message rows: `pk=TICKET#{ticket_id}`, `sk=MSG#{ts:013d}#{message_id}` (`:172-173`)
- Activity rows: `pk=TICKET#{ticket_id}`, `sk=ACT#{ts:013d}#{activity_id}` (`:176-177`)

`_query_partition_prefix` (`:514-520`) fetches all rows under a ticket by `begins_with(sk, prefix)`, making it trivial to add a new `ATTACHMENT#` prefix into the same partition without any schema change.

`get_ticket` (`:522-566`) builds the projection by querying `MSG#` and `ACT#` prefixes. Attachment rows will be queried with the same helper in TKA-002 and optionally included in the projection there.

The existing `TicketOut` Pydantic model (`app/routers/tickets.py:58-73`) and `TicketListItemOut` (`:91-110`) do not reference attachments today. Adding an `attachments` field is deferred to TKA-002 so this ticket remains narrowly scoped.

### Auth helpers (tickets router)

`app/routers/tickets.py` exposes these reusable helpers:
- `_is_admin_actor(request, user)` (`:224-225`) — true for ADMIN/ROOT or api-key with `tickets:admin` scope
- `_is_admin(user)` (`:207-208`) — strict role check
- `_can_access_ticket(request, user, ticket)` (`:339-340`) — true when `user.sub == ticket["owner_sub"]` or admin (**does NOT currently check `assigned_to_sub`**; TKA-001 extends the auth check to also allow the assignee, but does so inline in the endpoint handler — it does not modify `_can_access_ticket` itself, as that would widen access for all existing ticket endpoints)
- All endpoints use `Depends(require_ui_session)` + `Depends(get_authenticated_user)` (`:591`, `:617`, etc.)

### Messaging presign precedent

`app/routers/messaging.py:8407-8423` is the reference implementation:

```
POST /conversations/{cid}/images/presign
  → key = f"{cid}/{user_id}/{now_ts()}_{uuid_hex}_{filename}"
  → dev: /mock/s3/{bucket}/{key}  (S.dev_mode)
  → prod: s3.generate_presigned_url(ClientMethod="put_object", Params={Bucket, Key, ContentType}, ExpiresIn=900)
  → returns PresignOut(upload_url, bucket, key, content_type)
```

`PresignOut` (`:1925-1929`) carries `upload_url`, `bucket`, `key`, `content_type`. The client then uses `bucket` + `key` in a follow-up call (`CreateImageMessageIn`, `:1932-1950`) to confirm the upload and write the metadata row.

`S3_BUCKET_IMAGES` (`:207`) is the messaging bucket. For ticket attachments the bucket is `S.filemgr_bucket` (`app/core/settings.py:946`, env `FILEMGR_BUCKET`, default `""`). Ticket attachments are stored on the same bucket as the file manager — this is consistent with the license-agreement service which resolves its bucket via `_bucket()` (`app/services/license_agreements.py:73-75`): `S.license_agreements_bucket or S.filemgr_bucket or "filemgr"`. The license-agreement service falls through to `S.filemgr_bucket` when `S.license_agreements_bucket` is unset; ticket attachments use `S.filemgr_bucket` directly (no separate `ticket_attachments_bucket` setting).

### Validation precedent

`app/services/license_agreements.py:40-90` provides:
- `ALLOWED_MIME_TYPES` (`:40-45`): `application/pdf`, `image/png`, `image/jpeg`, `image/webp`
- `_MAGIC_BYTES` (`:47-52`): byte-header signatures per type
- `MAX_FILE_SIZE = 20 * 1024 * 1024` (`:53`): 20 MB cap
- `_sanitize_filename(name)` (`:78-82`): strips path separators, caps at 200 chars
- `_validate_magic_bytes(mime_type, head)` (`:85-90`): checks first 8 bytes

For ticket attachments we extend `ALLOWED_MIME_TYPES` to also allow `text/plain` and common office formats (`application/msword`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `application/vnd.ms-excel`, `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`). Magic-byte validation is applied only for the types that have known signatures; unknown-signature types (plain text, .docx, .xlsx) pass through the size check only. **Note:** this diverges from `license_agreements.py`, where `_validate_magic_bytes` (`:85-90`) returns `False` for any type without a registered signature and the caller (`upload_agreement_document`, `:130`) treats `False` as a hard rejection — meaning `license_agreements.py` only accepts the four types with known signatures. The ticket attachment service intentionally relaxes this: it will call `_validate_magic_bytes` only when the declared type has a known signature, and skip the check for `text/plain` / `.docx` / `.xlsx`.

## 3. Data Model

### Table: `T.tickets`

Attachment metadata is stored **in the same `T.tickets` table** as all other ticket rows, under the ticket's partition. No new table is needed.

#### Attachment row

| Attribute | Type | Value / Notes |
|---|---|---|
| `pk` | S | `TICKET#{ticket_id}` |
| `sk` | S | `ATTACHMENT#{attachment_id}` |
| `entity_type` | S | `"ticket_attachment"` |
| `ticket_id` | S | |
| `attachment_id` | S | `att_{uuid4().hex[:12]}` |
| `bucket` | S | value of `S.filemgr_bucket` at presign time |
| `s3_key` | S | `tickets/{ticket_id}/attachments/{attachment_id}/{safe_filename}` |

#### Endpoint 1 — Presign

```
POST /tickets/{ticket_id}/attachments/presign
```

**Auth:** `Depends(require_ui_session)` + `Depends(get_authenticated_user)`. Caller must be the ticket owner or assignee (checked via `_can_access_ticket` `:339-340`, extended to also allow `user.sub == ticket["assigned_to_sub"]`).

**Request body (Pydantic `TicketAttachmentPresignIn`):**

```python
class TicketAttachmentPresignIn(BaseModel):
    filename: str = Field(..., min_length=1, max_length=255)
    content_type: str = Field(..., max_length=128)
    filesize: int = Field(..., ge=1)
```

**Success response 200 (`TicketAttachmentPresignOut`):**

```python
class TicketAttachmentPresignOut(BaseModel):
    attachment_id: str
    upload_url: str   # /mock/s3/... in dev, presigned PUT URL in prod
    bucket: str
    key: str
    content_type: str
```

**Errors:**
- 404 — flag off (`ticket_attachments_not_enabled`) or ticket not found
- 400 — unsupported `content_type` (`attachment_mime_type_not_allowed`) or `filesize > ticket_attachments_max_bytes` (`attachment_too_large`)
- 403 — caller is not owner or assignee

**Handler logic (synchronous `def`):**

1. `_require_enabled()` — 404 if flag off.
2. Load ticket via `_ticket_or_404(ticket_id)` (`:332-336`).
3. Auth: `user.sub == ticket["owner_sub"] or user.sub == ticket.get("assigned_to_sub") or _is_admin_actor(request, user)` — else 403.
4. Validate `content_type in ALLOWED_MIME_TYPES` — else 400.
5. Validate `filesize <= S.ticket_attachments_max_bytes` — else 400.
6. Call `ticket_attachments.presign_attachment(ticket_id=..., filename=..., content_type=..., filesize=...)` which:
   a. Generates `attachment_id = f"att_{uuid4().hex[:12]}"`.
   b. Sanitizes filename.
   c. Builds `key = f"tickets/{ticket_id}/attachments/{attachment_id}/{safe_filename}"`.
   d. In dev (`S.dev_mode`): `upload_url = f"/mock/s3/{S.filemgr_bucket}/{quote(key, safe='/')}"`.
   e. In prod: `s3.generate_presigned_url("put_object", Params={Bucket, Key, ContentType}, ExpiresIn=S.ticket_attachments_presign_ttl_seconds)`.
   f. Returns dict with `attachment_id`, `upload_url`, `bucket`, `key`, `content_type`.
7. Return `TicketAttachmentPresignOut(**result)` — HTTP 200.

```python
class TicketAttachmentOut(BaseModel):
    attachment_id: str
    ticket_id: str
    filename: str
    filesize: int
    mime_type: str
    s3_key: str
    bucket: str
    uploader_sub: str
    created_at: int
    status: str
```

**Errors:**
- 404 — flag off or ticket not found
- 400 — mime type not allowed; filesize exceeds cap; `key` does not start with expected prefix (key-ownership guard); magic-byte mismatch; duplicate `attachment_id`
- 403 — caller is not owner/assignee/admin
- 409 — per-ticket attachment cap reached

**Handler logic:**

1. `_require_enabled()`.
2. Load and auth-check ticket.
3. Call `ticket_attachments.add_attachment(...)` which:
   a. Re-validates `content_type in ALLOWED_MIME_TYPES` and `filesize <= max`.
   b. **Key prefix guard**: verifies `key.startswith(f"tickets/{ticket_id}/attachments/{attachment_id}/")` — rejects a caller who substitutes a key from another ticket.
   c. If `head_bytes_b64` provided, decode + validate magic bytes.
   d. Count existing active attachments: `len(_query_partition_prefix(ticket_id, "ATTACHMENT#"))` — 409 if at cap.
   e. `T.tickets.put_item(Item={...}, ConditionExpression="attribute_not_exists(sk)")` — idempotent guard; a second PUT with the same `attachment_id` raises `ConditionalCheckFailedException` → 409 `attachment_already_exists` (the idempotency case, not an error from a retry standpoint: the caller can re-confirm the existing row is present).
   f. Emit `audit_event("ticket_attachment_added", uploader_sub, ...)` (fire-and-forget, mirrors ticket activity audit).
   g. Return attachment dict.
4. Return `TicketAttachmentOut(**result)` — HTTP 201.

## 5. Detailed Behavior & Edge Cases

### Key-ownership guard (security invariant)

The `key` field in the confirm body is verified to start with `tickets/{ticket_id}/attachments/{attachment_id}/`. This prevents a malicious caller from:
- Submitting another user's presigned key (different `ticket_id` in the path).
- Submitting a key from a different feature's S3 namespace.

The guard is enforced in the service layer (`add_attachment`), not only in the router, so it applies even if the service is called programmatically.

### Idempotent re-confirm

`T.tickets.put_item(ConditionExpression="attribute_not_exists(sk)")` ensures the attachment row is written exactly once. If the client retries the confirm call after a network timeout, the second call raises `ConditionalCheckFailedException`. The service catches this and re-reads the existing row — if `uploader_sub` and `key` match, it returns the existing row (200, not 201). If they differ, it returns 409 `attachment_already_exists`.

### Per-ticket cap

Before writing, count existing `ATTACHMENT#*` rows for the ticket (using `_query_partition_prefix`). If the count equals `S.ticket_attachments_max_per_ticket` (default 20), return 409 `attachment_cap_reached`. The query page-loops until `LastEvaluatedKey` is exhausted (consistent with the CLAUDE.md note: FilterExpression does not reduce page size, so a count-based cap must loop).

### Filesize trust model

The `filesize` field in both presign and confirm is client-declared. The server uses it for the `≤ max` guard only. The actual object size is not read back from S3. This matches the messaging presign pattern (`:8407-8423`) — a heavyweight `HeadObject` round-trip would add latency and cost for every confirm call. Magic-byte validation (when `head_bytes_b64` is provided) gives a lightweight content-type check without reading the full object.

### Presign TTL expiry

The presigned URL expires after `S.ticket_attachments_presign_ttl_seconds` (default 900 s). After expiry, the S3 PUT will return 403. The client must re-call presign to get a fresh URL. The confirm endpoint has no TTL check — it writes metadata as long as the DDB row doesn't already exist. This is consistent with the messaging pattern (there is no server-side tracking of issued presign tokens for image uploads).

### Flag toggled off mid-flight

If the flag is turned off after a presign is issued but before confirm is called, the confirm endpoint returns 404 (`ticket_attachments_not_enabled`). The presigned URL remains valid at S3 but the metadata row is never written. This is safe — the orphan object will age out of S3 via a lifecycle rule (outside scope of this ticket; a standard bucket policy).

### Ticket deleted before confirm

`_ticket_or_404` in the confirm handler ensures the ticket still exists before writing the attachment row. If the ticket was deleted between presign and confirm, the endpoint returns 404. The presigned PUT URL is now an orphan — same lifecycle-rule handling as above.

### Bucket not configured

If `S.filemgr_bucket` is `""` (default when env var is unset), `presign_attachment` raises `HTTPException(500, "attachment_bucket_not_configured")`. This surfaces a misconfiguration clearly rather than silently writing an attachment row with an empty bucket field.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### Dev/prod parity

The presign handler branches only on `S.dev_mode` to choose between a `/mock/s3/...` relative URL and a real presigned URL — exactly as `messaging.py:8412-8422`. The confirm handler (`add_attachment`) writes to DynamoDB (moto in dev, real DDB in prod) with no `dev_mode` branch. The S3 `put_object` is performed by the client, not the server, so there is no server-side S3 write path to branch on. This is full SECOPS-007 parity.

### Idempotency

- **Presign:** Generates a new `attachment_id` and URL on every call. Re-calling presign for the same ticket is safe (creates a new attachment slot; the old presigned URL may be abandoned).
- **Confirm:** `attribute_not_exists(sk)` conditional put guarantees the DDB row is written at most once per `attachment_id`. Retries by the same caller receive the existing row.

### Security

- **Key-ownership guard** prevents cross-ticket and cross-user key injection (described in §5).
- **Allowlist** rejects unknown MIME types; **magic-byte check** (optional) rejects declared-type spoofing.
- **Auth on both endpoints**: presign and confirm both require the caller to be the ticket owner, assignee, or admin. An adversary who intercepts a presigned URL cannot register metadata for a ticket they don't own (the confirm call enforces the same auth).
- **Bucket scope**: all keys are prefixed `tickets/{ticket_id}/attachments/{attachment_id}/` — unrelated objects in the filemgr bucket are not reachable via ticket attachment endpoints.

### Money-safety

This ticket involves no money movement. No ledger entries, no wallet debits, no billing interactions. Money-safety constraints from the cross-cutting section do not apply to TKA-001.

## 8. Backward Compatibility & Migration

### With flag off

`_require_enabled()` returns 404 for both new endpoints. No existing endpoint is modified. The `T.tickets` table schema is unchanged — no new GSIs, no new table. `TicketOut` does not gain an `attachments` field in this ticket (that is TKA-002). Existing ticket reads, writes, and all 42 ticket E2E tests in `frontend/e2e/tickets.spec.ts` are unaffected.

### With flag on

`T.tickets` already stores heterogeneous row types (META, MSG, ACT) under the same partition. Adding `ATTACHMENT#` rows is purely additive. `get_ticket` (`:522-566`) does not query `ATTACHMENT#` rows (deferred to TKA-002), so `TicketOut` is unchanged and all existing callers continue to work.

### DynamoDB: no migration required

The `ATTACHMENT#{attachment_id}` sort key uses string comparison. There are no numeric GSI sort keys involved in this ticket, so no `attr_types` additions are needed in `scripts/local-ddb-init.py`. The existing `tickets` table definition at `:695-711` is unchanged.

### Settings

New `S.*` fields with defaults mean `app/core/settings.py` loads without error on existing deployments. No `.env.local` edits are required unless operators want to enable the feature or tune limits.

10. **Magic-byte mismatch**: `content_type="image/png"` but `head_bytes_b64` encodes bytes that start with `%PDF` → 400 `attachment_magic_byte_mismatch`.
11. **Idempotent re-confirm**: call confirm twice with the same `attachment_id` → first 201, second returns existing row (no duplicate DDB row).
12. **Assignee can attach**: assign ticket to user B, call presign as B → 200 (not 403).
13. **Admin can attach**: call presign as admin user → 200.
14. **Per-ticket cap**: create `ticket_attachments_max_per_ticket` attachments, attempt one more confirm → 409 `attachment_cap_reached`.
15. **`_query_partition_prefix` isolation**: confirm that `get_ticket` does NOT include `ATTACHMENT#` rows in the `messages` or `activity` arrays (TKA-002 concern, but assert it does not regress in TKA-001).

All tests are synchronous (service functions are not async). Route handlers in `app/routers/tickets.py` are also synchronous `def` functions (`:591-592`), so they are called directly without `asyncio.run`.

## 10. Open Questions / Assumptions

1. **Allowed MIME types for ticket attachments**: The spec extends the license-agreement set to include office/text formats. Product should confirm whether ZIP, CSV, or other formats are required. The allowlist in `app/services/ticket_attachments.py` is the single source of truth and can be adjusted without a schema change.

2. **Magic-byte validation is optional (client-supplied)**: The presign flow is a pure URL redirect — the server never sees the file bytes. Clients that want server-side content-type validation must send `head_bytes_b64` in the confirm body. This is a deliberate trade-off (no server-side S3 read). A future enhancement could do a `HeadObject` + range-GET on the S3 key after upload, but that adds latency and is left as a follow-up.

3. **`S.filemgr_bucket` default is `""`**: In dev, `setup_ubuntu.sh` / `local-stack-up.sh` must ensure `FILEMGR_BUCKET` is set (or the 500 error will surface on the first presign). Confirm with the infra team that `.env.local.example` addition is sufficient (it is, based on how other S3-dependent features behave in this codebase).

4. **Orphan S3 objects**: Objects uploaded via presigned URLs that are never confirmed (no metadata row in DDB) are orphans. A lifecycle rule on `S.filemgr_bucket` with a 24-hour expiry on the `tickets/` prefix would clean these up. This is an infrastructure concern outside this ticket's scope.

5. **Multipart upload**: `generate_presigned_url("put_object", ...)` supports single-part uploads only. Files larger than 5 GB require multipart. Given the 20 MB cap (`ticket_attachments_max_bytes`), this is not a concern for v1.

6. **D3 (Open Decision — who may attach)**: The ticket file is independent of the bounty Open Decisions. The spec permits owner + assignee + admin. If product decides attachments should be broader (any authenticated user can attach to any open ticket), the `_can_attach` guard in §4 is the only change required.
