# TBT-005 — Self-claim (any user assigns themselves)

**Milestone:** 1 — Escrow & bounty foundation  
**Type:** Feature | **Priority:** P0 | **Estimate:** 1.5 days  
**Dependencies:** TBT-003 (escrow service), TBT-004 (bounty state machine)

---

## 1. Summary & Goal

TBT-005 introduces the **self-claim and self-unclaim paths** for bounty tickets: any authenticated user may atomically claim a funded, unclaimed bounty ticket and assign themselves as the worker, and may later release it back to the open board. This is distinct from the admin-only `assign_ticket` path (`app/services/tickets.py:807`) that already exists. The key invariants are:

- Exactly one winner per race: two simultaneous claims produce one `claimed` and one 409.
- Escrow is untouched by claim and unclaim; money moves only at post time (TBT-003) and payout/cancel time (TBT-006/007).
- The bounty board (TBT-008) immediately reflects claim/unclaim via the sparse `ByBounty` GSI.
- With `TICKET_BOUNTIES_ENABLED=false`, every byte of the existing ticket system is unchanged.

## 2. Context & Current State

### Ticket system

The ticket service (`app/services/tickets.py`) uses a single-table design on `T.tickets` (`app/core/tables.py:392`). Each ticket occupies a DynamoDB partition keyed `pk=TICKET#{ticket_id}` (`tickets.py:164-165`). The META row (`sk=META`) holds all header fields; MSG and ACT rows live in the same partition. The projection function `get_ticket` (`tickets.py:522-566`) reads the META row plus prefix-scanned MSG/ACT items.

The `_TICKET_STATUSES` tuple (`tickets.py:15-29`) and `_STATUS_TRANSITIONS` dict (`tickets.py:30-40`) define valid statuses and transitions today: `open`, `in_progress`, `waiting_on_user`, `done`, `code_complete`, `qa_in_progress`, `qa_approved`, `blocked`, `deploying`, `deployed`, `investigating`, `analyzing`, `tickets_created`. None of the bounty lifecycle statuses (`claimed`, `pending_approval`, `paid_out`, `cancelled`) exist yet; TBT-004 adds them.

The `assign_ticket` service method (`app/services/tickets.py:807-849`) is admin-only at the router level (`app/routers/tickets.py:913-935`; `_is_admin_actor` at `app/routers/tickets.py:224-225` checks for admin role or `tickets:admin` API key scope). It uses a read-modify-write pattern (`_apply_header_update_once`, `app/services/tickets.py:792-805`) that calls `_conditional_update_meta` (`app/services/tickets.py:723`) which performs a conditional update on `version`. There is no self-assign path today.

Existing GSIs on `T.tickets` (`scripts/local-ddb-init.py:695-711`; the `gsi=[...]` list at lines 699-710):

| GSI | Partition key attr | Sort key attr |
|---|---|---|
| owner index (`S.tickets_owner_index_name`) | `gsi1pk` (`OWNER#{sub}`) | `gsi1sk` |
| status index (`S.tickets_status_index_name`) | `gsi2pk` (`STATUS#{status}`) | `gsi2sk` |
| assignee index (`S.tickets_assignee_index_name`) | `gsi3pk` (`ASSIGNEE#{sub}`) | `gsi3sk` |
| space, space+status, space+assignee, member-spaces, jira indices | various | various |

No `ByBounty` GSI exists yet; that is added in TBT-002.

### Billing / wallet primitives

`T.billing` (`app/core/tables.py:333`) uses `pk`/`sk` as keys. The wallet row for a user sits at `pk=USER#{sub}`, `sk=WALLET` (`billing_shared.py:173`). `apply_wallet_delta` (`billing_shared.py:185-213`) conditionally withdraws (requires `wallet_balance_cents >= needed` via a `ConditionExpression`) and creates the row on deposit via `if_not_exists`.

The escrow sentinel row (`pk=BOUNTY#{bounty_id}`, `sk=ESCROW`) is placed on `T.billing` by TBT-003, co-located with the ledger. TBT-005 only reads the escrow row (to verify it is in `status="held"`); it does not move money.

The atomic escrow pattern from `group_treasury.py:716-751` — constructing a low-level DynamoDB client from the resource's credentials/endpoint and calling `transact_write_items` via `_batch_transact` — is reused by TBT-003 and is the approved precedent for all multi-item atomicity in this codebase.

### Settings and flags

`S.ticket_bounties_enabled` (env `TICKET_BOUNTIES_ENABLED`, default `false`) is added by TBT-001 to `app/core/settings.py`. The helper pattern is `_bounties_enabled() -> bool` + `_require_bounties_enabled()` raising HTTP 404, mirroring `app/services/inventory.py:50-56`.

### Router auth helpers

`_is_admin_actor(request, user)` (`tickets.py:224-225`) returns `True` for ADMIN/ROOT role or `tickets:admin` API key scope. `require_ui_session` (imported from `app/services/sessions`) is the standard cookie/bearer auth dependency.

## 3. Data Model

### 3.1 Ticket META row additions (on `T.tickets`)

These are additive fields on the existing `pk=TICKET#{ticket_id}`, `sk=META` row. They are absent (never written) for non-bounty tickets, preserving byte-for-byte compatibility when the flag is off.

| Attribute | Type | Written by | Description |
|---|---|---|---|
| `bounty_id` | String | TBT-003 | `sha256(f"bounty:{ticket_id}")[:24]` — deterministic |
| `bounty_amount_cents` | Number | TBT-003 | Posted amount in cents |
| `bounty_currency` | String | TBT-003 | e.g. `"usd"` |
| `bounty_status` | String | TBT-003..007 | `none\|funded\|claimed\|submitted\|paid_out\|cancelled` |
| `bounty_funded_at` | Number | TBT-003 | Unix timestamp |
| `claimed_by_sub` | String | **TBT-005** | `claimer_sub` on claim; removed on unclaim |
| `claimed_at` | Number | **TBT-005** | Unix timestamp of claim; removed on unclaim |
| `gsi_bounty_pk` | String | TBT-003, **TBT-005** | `"BOUNTY#OPEN"` when `bounty_status=="funded"`; removed otherwise |
| `gsi_bounty_sk` | Number | TBT-003, **TBT-005** | `created_at` (numeric) when on board; removed otherwise |

**Sparse `ByBounty` GSI** (added by TBT-002 / `scripts/local-ddb-init.py`):

```
index_name: S.tickets_bounty_index_name  (default "bounty-open-index")
partition_key: gsi_bounty_pk  (String)
sort_key:      gsi_bounty_sk  (Number → attr_types={"gsi_bounty_sk": "N"})
```

The numeric sort key requires `attr_types={"gsi_bounty_sk": "N"}` in the `TableDef` for `T.tickets`. Missing this causes `ValidationException` at runtime (see CLAUDE.md "DynamoDB numeric GSI sort keys").

Only tickets with `bounty_status=="funded"` carry `gsi_bounty_pk`/`gsi_bounty_sk`. Claiming clears both attrs (REMOVE), so claimed tickets instantly drop off the board. Unclaiming re-sets them, returning the ticket to the board.

### 3.2 Escrow row (on `T.billing`, written by TBT-003, read by TBT-005)

```
pk=BOUNTY#{bounty_id}, sk=ESCROW
{
  ticket_id, poster_sub, amount_cents, currency,
  status: "held" | "released" | "refunded",
  created_at, ledger_sk (audit debit ledger entry sk on T.billing)
}
```

TBT-005 reads this row to assert `status=="held"` before completing the claim. It does not mutate the escrow row.

### 3.3 No new tables

Both the escrow sentinel and bounty ledger entries live on the existing `T.billing` table (`pk`, `sk` as keys; `billing_table_name` from `S`). No table provisioning changes beyond the `ByBounty` GSI on `T.tickets`.

## 4. API / Service Design

### 4.1 Service functions (in `app/services/ticket_bounties.py`)

#### `claim_bounty(ticket_id: str, claimer_sub: str) -> dict[str, Any]`

**Preconditions** (each raises HTTP on violation):

1. `_require_bounties_enabled()` → HTTP 404 if flag off.
2. `STORE.get_ticket(ticket_id)` — HTTP 404 if not found.
3. `ticket["bounty_status"] == "funded"` — HTTP 409 `bounty_not_funded` if not (covers not-yet-funded, already claimed, submitted, paid-out, cancelled).
4. Escrow exists and `status == "held"` (read `T.billing`, `pk=BOUNTY#{bounty_id}`, `sk=ESCROW`) — HTTP 409 `escrow_not_held` on mismatch (defensive guard; TBT-003 should always set this).

**Single-winner write** — performed as a DynamoDB `update_item` with `ConditionExpression`:

```python
T.tickets.update_item(
    Key={"pk": _ticket_pk(ticket_id), "sk": "META"},
    UpdateExpression=(
        "SET claimed_by_sub = :claimer, claimed_at = :ts, "
        "assigned_to_sub = :claimer, assigned_by = :claimer, assigned_at = :ts, "
        "bounty_status = :claimed, #status = :in_progress, "
        "updated_at = :ts, version = version + :one, "
        "gsi2pk = :gsi2pk, gsi2sk = :gsi2sk, "
        "gsi3pk = :gsi3pk, gsi3sk = :gsi3sk, gsi1sk = :gsi1sk "
        "REMOVE gsi_bounty_pk, gsi_bounty_sk"
    ),
    ConditionExpression="attribute_not_exists(claimed_by_sub) AND bounty_status = :funded",
    ExpressionAttributeNames={"#status": "status"},
    ExpressionAttributeValues={
        ":claimer": claimer_sub,
        ":ts": ts,
        ":claimed": "claimed",
        ":funded": "funded",
        ":in_progress": "in_progress",
        ":one": 1,
        ":gsi2pk": _status_index_pk("in_progress"),
        ":gsi2sk": _updated_index_sk(ts, ticket_id),
        ":gsi3pk": _assignee_index_pk(claimer_sub),
        ":gsi3sk": _updated_index_sk(ts, ticket_id),
        ":gsi1sk": _updated_index_sk(ts, ticket_id),
    },
)
```

The `ConditionExpression="attribute_not_exists(claimed_by_sub) AND bounty_status = :funded"` is the **single-winner gate**: if two requests race, exactly one wins; the loser gets `ConditionalCheckFailedException` → HTTP 409 `already_claimed`.

The REMOVE clause for `gsi_bounty_pk` and `gsi_bounty_sk` atomically removes the ticket from the bounty board in the same operation. DynamoDB does not allow `NULL` values as GSI key attributes, so REMOVE is required (not SET to None).

> **RISK — space GSI staleness**: The `_conditional_update_meta` path (used by `assign_ticket`, `add_message`, `update_status`) also updates `gsi_space_assignee_pk`/`gsi_space_sk`/`gsi_space_status_pk` etc. for space-assigned tickets (`app/services/tickets.py:757-775`). The claim/unclaim `update_item` above omits these space GSI keys. For tickets that belong to a space (`space_id` set), the `gsi_space_assignee` index entry will remain stale (pointing to `ASSIGNEE#unassigned`) after a claim, and space-based "assigned to me" views will miss the claimed ticket. The implementer must either (a) include the space GSI updates in the claim/unclaim `update_item` (reading `space_id` from the pre-checked ticket and conditionally including the space GSI SET/REMOVE clauses), or (b) document this as a v1 limitation. The same omission applies to `assigned_admin_sub`, `last_message_at`, and `last_message_by_role`, which `_conditional_update_meta` always writes but the claim path does not.

**Activity row** — after the update, write an activity row (matching the pattern from `assign_ticket` at `app/services/tickets.py:838-848`, which includes `ticket_id` and `activity_id`):

```python
_act_id = f"act_{uuid.uuid4().hex[:12]}"
T.tickets.put_item(Item={
    "pk": _ticket_pk(ticket_id),
    "sk": _act_sk(ts, _act_id),
    "entity_type": "ticket_activity",
    "ticket_id": ticket_id,
    "activity_id": _act_id,
    "activity_type": "bounty_claimed",
    "actor_sub": claimer_sub,
    "assignee_sub": claimer_sub,
    "created_at": ts,
})
```

**Audit** — `audit_event("bounty_claimed", claimer_sub, None, ticket_id=ticket_id, bounty_id=bounty_id)`.

**Returns** — `STORE.get_ticket(ticket_id)` (full projection including new bounty fields from TBT-002).

#### `unclaim_bounty(ticket_id: str, claimer_sub: str) -> dict[str, Any]`

Reverts the claim, returning the ticket to the bounty board. Escrow stays held.

**Preconditions:**

1. `_require_bounties_enabled()`.
2. `ticket = STORE.get_ticket(ticket_id)` — HTTP 404 if absent.
3. `ticket["bounty_status"] == "claimed"` — HTTP 409 `not_claimed`.
4. `ticket["claimed_by_sub"] == claimer_sub` — HTTP 403 `not_claimant` (only the current claimant can unclaim; admins use cancel/TBT-007).

**Write:**

```python
T.tickets.update_item(
    Key={"pk": _ticket_pk(ticket_id), "sk": "META"},
    UpdateExpression=(
        "SET bounty_status = :funded, #status = :open, "
        "gsi_bounty_pk = :bounty_open, gsi_bounty_sk = :created_at, "
        "assigned_to_sub = :none, assigned_by = :none, assigned_at = :none, "
        "updated_at = :ts, version = version + :one, "
        "gsi2pk = :gsi2pk, gsi2sk = :gsi2sk, "
        "gsi3pk = :gsi3pk, gsi3sk = :gsi3sk, gsi1sk = :gsi1sk "
        "REMOVE claimed_by_sub, claimed_at"
    ),
    ConditionExpression="claimed_by_sub = :claimer AND bounty_status = :claimed",
    ExpressionAttributeNames={"#status": "status"},
    ExpressionAttributeValues={...},
)
```

The `ConditionExpression="claimed_by_sub = :claimer AND bounty_status = :claimed"` ensures only the current claimant succeeds and that the ticket has not already been un-claimed or moved forward. A concurrent `unclaim` or a `submit_bounty` call on the same ticket will cause one to lose with `ConditionalCheckFailedException` → HTTP 409.

Restores `gsi_bounty_pk = "BOUNTY#OPEN"` and `gsi_bounty_sk = ticket["created_at"]` (numeric, preserving original board position). Resets ticket status to `open` and clears `assigned_to_sub`, `assigned_by`, `assigned_at`. Removes `claimed_by_sub` and `claimed_at` with REMOVE clause.

> **RISK — space GSI staleness (same as claim)**: The unclaim `update_item` must also reset `gsi_space_assignee_pk` to `_space_assignee_index_pk(space_id, "unassigned")` (and related space GSI attrs) when the ticket has a `space_id`, otherwise the space-assignee index remains pointing to the former claimant after unclaim. The implementer must read `space_id` from the pre-checked ticket header and conditionally include these in the `ExpressionAttributeValues`.

**Activity row** — `activity_type="bounty_unclaimed"` (include `ticket_id` and `activity_id` fields to match the `assign_ticket` pattern at `app/services/tickets.py:838-848`).

**Audit** — `audit_event("bounty_unclaimed", ...)`.

**Returns** — `STORE.get_ticket(ticket_id)`.

### 4.2 Router endpoints (in `app/routers/tickets.py`)

Both endpoints are declared under the existing `router` (`APIRouter(prefix="/tickets", ...)`). The bounty-specific routes should be grouped after the existing assign/status endpoints, before the admin endpoints.

#### `POST /tickets/{ticket_id}/bounty/claim`

```python
@router.post("/{ticket_id}/bounty/claim")
async def claim_bounty_endpoint(
    ticket_id: str,
    req: Request,
    ctx=Depends(require_ui_session),
) -> TicketEnvelope:
    _require_bounties_enabled()
    claimer_sub = ctx["user_sub"]
    try:
        ticket = claim_bounty(ticket_id=ticket_id, claimer_sub=claimer_sub)
    except TicketBountyError as e:
        _raise_bounty_error(e)
    if not ticket:
        _raise(404, "ticket_not_found", "Ticket not found")
    return _wrap_ticket(ticket)
```

**Auth:** `require_ui_session` — any authenticated user (no admin check). The service layer enforces the bounty state preconditions.

**Errors:**

| HTTP | Code | Trigger |
|---|---|---|
| 404 | `feature_disabled` | flag off |
| 404 | `ticket_not_found` | ticket absent |
| 409 | `bounty_not_funded` | `bounty_status != "funded"` |
| 409 | `already_claimed` | conditional write conflict (race) |
| 409 | `escrow_not_held` | escrow row missing or not `held` |

#### `POST /tickets/{ticket_id}/bounty/unclaim`

```python
@router.post("/{ticket_id}/bounty/unclaim")
async def unclaim_bounty_endpoint(
    ticket_id: str,
    req: Request,
    ctx=Depends(require_ui_session),
) -> TicketEnvelope:
    _require_bounties_enabled()
    claimer_sub = ctx["user_sub"]
    try:
        ticket = unclaim_bounty(ticket_id=ticket_id, claimer_sub=claimer_sub)
    except TicketBountyError as e:
        _raise_bounty_error(e)
    if not ticket:
        _raise(404, "ticket_not_found", "Ticket not found")
    return _wrap_ticket(ticket)
```

**Auth:** `require_ui_session`. Service enforces that the caller is the current claimant.

**Errors:**

| HTTP | Code | Trigger |
|---|---|---|
| 404 | `feature_disabled` | flag off |
| 404 | `ticket_not_found` | ticket absent |
| 409 | `not_claimed` | `bounty_status != "claimed"` |
| 403 | `not_claimant` | caller is not `claimed_by_sub` |
| 409 | `unclaim_conflict` | conditional write conflict (concurrent state change) |

## 5. Detailed Behavior & Edge Cases

### 5.1 Claim — state machine

Valid pre-claim states: `bounty_status="funded"`, ticket status `open`. After claim: `bounty_status="claimed"`, ticket status `in_progress`, `assigned_to_sub=claimer_sub`, `gsi_bounty_pk`/`gsi_bounty_sk` removed. The `gsi3pk` transitions from `ASSIGNEE#unassigned` to `ASSIGNEE#{claimer_sub}`, making the ticket appear in the claimant's assigned-to list.

### 5.2 Unclaim — state machine

Valid pre-unclaim state: `bounty_status="claimed"`, caller == `claimed_by_sub`. After unclaim: `bounty_status="funded"`, ticket status `open`, `assigned_to_sub=None`, `gsi3pk` resets to `ASSIGNEE#unassigned`, `gsi_bounty_pk`/`gsi_bounty_sk` restored. The `created_at` value used for `gsi_bounty_sk` is re-read from the ticket's `created_at` field, preserving original board sort order.

### 5.3 Race condition — two simultaneous claims

Both callers read `bounty_status="funded"` and no `claimed_by_sub`. Both attempt the `update_item` with `ConditionExpression="attribute_not_exists(claimed_by_sub) AND bounty_status = :funded"`. DynamoDB serializes these server-side; exactly one succeeds. The loser receives `ConditionalCheckFailedException` → HTTP 409 `already_claimed`. The poster's wallet is never affected. The escrow row is untouched by either call.

### 5.4 Race condition — claim vs. cancel (TBT-007)

If an admin triggers `cancel_bounty` concurrently with a user `claim_bounty`, both attempt to update `bounty_status` from `funded`. The cancel path (TBT-007) uses a different `ConditionExpression` gated on `bounty_status="funded"` with `attribute_not_exists(claimed_by_sub)`. Whichever DynamoDB call lands first wins; the other fails. Since cancel moves `bounty_status` to `cancelled` and claim checks `bounty_status=funded`, a claim after cancel fails at the pre-read check or at the conditional write.

### 5.5 Claiming a non-bounty ticket

A ticket with no `bounty_status` attribute (or `bounty_status="none"`) is not on the bounty board. Attempting to claim it fails at precondition step 3 (`bounty_status != "funded"`) → HTTP 409 `bounty_not_funded`. The endpoint is entirely separate from the admin-only assign endpoint, so non-bounty ticket assignment is unaffected.

### 5.6 Claiming one's own ticket (Open Decision D3)

Per D3, any owner may post a bounty. The service does **not** block the poster from claiming their own ticket. This is a deliberate product choice — the fraud gate at post time provides the economic disincentive, and the admin approval gate (TBT-006) prevents self-payment. If the product team decides otherwise, a single guard `if claimer_sub == ticket["owner_sub"]: raise TicketBountyError(403, "cannot_self_claim_own_bounty", ...)` is the change.

### 5.7 Abandonment / idle (Open Decision D4)

Per D4 (manual unclaim for v1), there is no automatic expiry. A claimant can remain claimed indefinitely without unclaiming. An idle-sweep (auto-unclaim after N days with no `submit_bounty`) is deferred to a follow-up ticket. The `unclaim_bounty` function here is the mechanism that sweep would call.

### 5.8 Version counter

Both `claim_bounty` and `unclaim_bounty` increment `version` by 1 in the same `update_item` (`version = version + :one`). This keeps the version counter consistent with the optimistic-locking pattern used by `_conditional_update_meta` (`app/services/tickets.py:723`). The pre-read check is not needed for the claim path (the `ConditionExpression` on `claimed_by_sub` and `bounty_status` is the race guard); the version increment is a side-effect rather than the guard. This is safe because the single field being contended is `claimed_by_sub`, not version.

### 5.9 GSI key consistency

DynamoDB does not allow `NULL` values as GSI partition or sort keys. The REMOVE clause in the claim update correctly removes `gsi_bounty_pk` and `gsi_bounty_sk` rather than setting them to None. The unclaim update sets them to non-null strings/numbers.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### Dev/Prod parity

- All DynamoDB writes go through `T.tickets` and `T.billing` which in dev resolve to DynamoDB Local (port 8001) and in prod to real AWS DynamoDB. No `dev_mode` branch is needed or permitted.
- `claim_bounty` and `unclaim_bounty` make no S3, Stripe, Cognito, or external HTTP calls. The `transact_write_items` client pattern from `group_treasury.py` is not needed here because both claim and unclaim are single `update_item` operations (no multi-table atomicity required). If multi-table atomicity were needed (e.g., simultaneously writing an activity row atomically), the `_transact_client()` / `_batch_transact()` helpers from `group_treasury.py:716-751` provide the model.
- Audit events use `app/services/alerts.audit_event`, which writes to `T.alerts` (DDB-backed in both envs).

### Idempotency

- `claim_bounty` is idempotent on retry by the same caller only if the first call succeeded and the condition is still true. If the first call succeeded, a retry by the same claimer gets `ConditionalCheckFailedException` on `attribute_not_exists(claimed_by_sub)` (the field now exists) → 409. Callers must treat 409 `already_claimed` as "check the ticket state and proceed accordingly" rather than a hard failure.
- No deterministic ID is needed for the claim write itself (it is a direct field update, not a new entity). The activity row uses `uuid4().hex[:12]`, consistent with the existing activity-row pattern (`tickets.py:840-843`).

### Security

- The claim endpoint requires `require_ui_session` — no unauthenticated access. The claimer identity is extracted from the session, never from the request body, preventing impersonation.
- There is no financial movement in TBT-005; the escrow row (TBT-003) is read-only here. The fraud gate (`_fraud_gate`) is run by TBT-003 at bounty post time, not at claim time — claiming a bounty costs the claimer nothing.
- The claim operation does not expose the poster's wallet balance or any payment metadata to the claimer.

### Money-safety invariants for TBT-005 specifically

- **No money moves on claim/unclaim.** The poster's wallet balance and the escrow `BOUNTY#{bounty_id}/ESCROW` row are read-only from the perspective of TBT-005.
- **Escrow status read**: reading `status=="held"` before claim is a defensive guard. The only code that flips `status` to `released` or `refunded` is TBT-006 and TBT-007 respectively, both requiring admin or owner authorization.
- **No double-assign**: the `attribute_not_exists(claimed_by_sub)` condition prevents two simultaneous writes; once set, `claimed_by_sub` cannot be overwritten by another claim (only unclaim clears it, and unclaim requires the same sub).

## 8. Backward Compatibility & Migration

### Flag-off behavior

With `TICKET_BOUNTIES_ENABLED=false` (the default):

- `_require_bounties_enabled()` raises HTTP 404 at the top of both the claim and unclaim endpoints.
- No code in `create_ticket`, `assign_ticket`, `update_status`, `add_message`, `list_tickets`, or `get_ticket` is modified. The `_TICKET_STATUSES` tuple and `_STATUS_TRANSITIONS` dict (`tickets.py:15-40`) are unchanged.
- The bounty-related fields (`bounty_status`, `claimed_by_sub`, etc.) are never written to `T.tickets` when the flag is off. Existing ticket projections return exactly the same JSON as today.
- The `ByBounty` GSI on `T.tickets` (added in TBT-002) is a sparse GSI — it contains only rows that have `gsi_bounty_pk` set, which is never written when the flag is off. The GSI therefore has zero entries when the feature is off and adds no overhead to reads.

### Migration steps

No data migration is required. The `ByBounty` GSI is added to `scripts/local-ddb-init.py` by TBT-002. In development, `just restart` recreates the table with the new GSI. In production, an `UpdateTable` call adds the GSI asynchronously; because it is sparse (no existing rows carry `gsi_bounty_pk`), the backfill completes instantly and there is no throughput spike.

The `tickets_bounty_index_name` setting name must be added to `app/core/settings.py` by TBT-001/TBT-002 before TBT-005 is deployed, because `list_open_bounties` (TBT-008) references it.

## 9. Test Plan

### 9.1 Hermetic pytest (`tests/test_ticket_bounties.py`, claim/unclaim section)

Tests use moto-backed in-memory DynamoDB bound to frozen `T.tickets` and `T.billing` via `object.__setattr__`, and route handlers called directly as coroutines (TestClient is broken in this environment per CLAUDE.md). `S.ticket_bounties_enabled` is toggled via `object.__setattr__(S, "ticket_bounties_enabled", True)` in a fixture.

**Setup fixture**: creates a ticket in `T.tickets` with `bounty_status="funded"`, `bounty_id`, `gsi_bounty_pk`, `gsi_bounty_sk`, and writes the corresponding `BOUNTY#{bounty_id}/ESCROW` row to `T.billing` with `status="held"`.

**Test cases for `claim_bounty`:**

1. **Happy path** — claimer != poster; ticket transitions from `funded`/`open` to `claimed`/`in_progress`; `claimed_by_sub` set; `gsi_bounty_pk` and `gsi_bounty_sk` removed; `assigned_to_sub` equals claimer; `gsi3pk` equals `ASSIGNEE#{claimer}`; version incremented; activity row written with `activity_type="bounty_claimed"`.

2. **Double-claim race** — call `claim_bounty` twice concurrently (or sequentially after the first succeeds); second call receives HTTP 409 `already_claimed`.

3. **Claim non-funded ticket** — ticket has `bounty_status="none"` (no bounty); expect 409 `bounty_not_funded`.

4. **Claim already-claimed ticket** — ticket has `bounty_status="claimed"`; expect 409 `bounty_not_funded` (or `already_claimed` depending on pre-read check ordering).

5. **Claim when flag off** — `S.ticket_bounties_enabled = False`; expect HTTP 404.

6. **Claim non-existent ticket** — expect HTTP 404 `ticket_not_found`.

7. **Claim with escrow in wrong state** — escrow row `status="refunded"`; expect HTTP 409 `escrow_not_held`.

**Test cases for `unclaim_bounty`:**

8. **Happy path** — claimant unclaims; `bounty_status` reverts to `"funded"`, ticket status to `"open"`, `claimed_by_sub` removed, `gsi_bounty_pk`/`gsi_bounty_sk` restored to original values, `assigned_to_sub` cleared, `gsi3pk` reset to `ASSIGNEE#unassigned`, version incremented.

9. **Wrong caller** — non-claimant calls unclaim; expect HTTP 403 `not_claimant`.

10. **Ticket not in claimed state** — `bounty_status="funded"` (unclaimed); expect 409 `not_claimed`.

11. **Flag off** — expect HTTP 404.

12. **Claim → unclaim → re-claim** — full round-trip; a different user claims after unclaim; both callers see correct state at each step.

### 9.2 E2E Playwright (`frontend/e2e/ticket-bounties.spec.ts`, claim section)

These tests are part of the broader TBT-011 test suite.

1. **Claim via UI** — Alice (poster) funds a bounty; Bob (non-poster) sees the ticket on the bounty board (`GET /tickets/bounties/open`); Bob clicks Claim; ticket disappears from board; Bob's ticket list shows the ticket in `in_progress`.

2. **Only one winner** — two page contexts race to claim the same ticket; one succeeds, the other sees an error toast.

3. **Unclaim returns to board** — Bob unclaims; ticket reappears on the bounty board; another user can then claim.

4. **Board visibility** — after claim, the ticket does not appear in `GET /tickets/bounties/open`; after unclaim, it does.

## 10. Open Questions / Assumptions

1. **Can the poster claim their own bounty?** (Open Decision D3) — The spec permits it (no owner-check guard). Confirm with product. If blocked, add: `if claimer_sub == ticket["owner_sub"]: raise TicketBountyError(403, "cannot_self_claim_own_bounty", "Poster cannot claim their own bounty")`.

2. **Admin unclaim** — The `unclaim_bounty` function currently requires `claimer_sub == claimed_by_sub`. Admins who want to forcibly unclaim a ticket mid-flight should use `cancel_bounty` (TBT-007), which also triggers a refund. There is no "admin force-unclaim without refund" path. Confirm this is the desired behavior.

3. **Claim count limit** — No limit on how many bounty tickets a user may hold simultaneously as claimed. If required (e.g., max 3 active claims), add a GSI query on `gsi3pk=ASSIGNEE#{sub}` filtered by `bounty_status="claimed"` before writing. Deferred for v1.

4. **Partial state between pre-read and write** — The service reads the ticket header (`STORE.get_ticket`) for precondition checks, then fires the conditional `update_item`. Between read and write, the escrow could transition from `held` to `refunded` (via a concurrent admin cancel). The `ConditionExpression` on `bounty_status=funded` catches this scenario at the write level because a cancel also sets `bounty_status="cancelled"`. The escrow read in step 4 is a belt-and-suspenders guard, not the primary race protection.

5. **`TicketOut` model rebuild** — If `TicketOut` is defined before the bounty fields are added and used in a `model_rebuild()` pattern (as `ConversationOut` requires per CLAUDE.md), a second `model_rebuild()` must be called after adding the optional bounty fields. Verify the `TicketOut` model in `app/routers/tickets.py:58-73` does not require forward-reference rebuilding. Current inspection shows no forward refs; additive optional fields are safe.

6. **`gsi_bounty_sk` type in update expression** — The `created_at` value written to `gsi_bounty_sk` is a Python `int`. DynamoDB boto3 resource layer accepts `int` and serializes it as Number. Confirm the `_FloatSafeTable` proxy (`app/core/tables.py:29-62`) does not coerce integers to strings (it only coerces `float` → `Decimal` via `_to_decimal` at line 11-26; `int` passes through unchanged — confirmed safe).
