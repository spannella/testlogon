# TBT-004 — Bounty state machine (gates existing transitions)

**Milestone:** 1 — Escrow & bounty foundation
**Priority:** P0
**Estimate:** 1.5 days
**Dependencies:** TBT-002 (bounty fields + sparse `ByBounty` GSI on `T.tickets`)

---

## 1. Summary & Goal

TBT-004 introduces the bounty-aware state machine that intercepts and gates status
transitions for tickets that carry a funded bounty. It does so surgically, without
touching the existing ticket transition table that non-bounty tickets have relied on
since the system was first written.

The primary behavioral goal is that when a claimant marks their work done on a
bountied ticket the system routes that transition to `pending_approval` rather than
the normal `done` status. Only an admin-triggered approval (TBT-006) can advance from
`pending_approval` to `paid_out`. The statuses `paid_out` and `cancelled` become
reachable exclusively through dedicated bounty endpoints and never through the generic
`PATCH /tickets/{id}/status` endpoint.

The scope of this ticket is the state machine itself: the module-level data structures
(`_BOUNTY_TRANSITIONS`, the expansion of `_TICKET_STATUSES`), the gate logic inside
`update_status`, and the validation helpers. Actual money movement lives in TBT-003
(hold), TBT-006 (release), and TBT-007 (cancel/refund). The bounty router endpoints
that expose the new statuses as HTTP operations are wired in TBT-009.

## 2. Context & Current State

### 2.1 Existing ticket status machine

`app/services/tickets.py:15-40` defines:

```python
_TICKET_STATUSES = (
    "open", "in_progress", "waiting_on_user", "done", "code_complete",
    "qa_in_progress", "qa_approved", "blocked", "deploying", "deployed",
    "investigating", "analyzing", "tickets_created",
)

_STATUS_TRANSITIONS: dict[str, tuple[str, ...]] = {
    "open": ("in_progress", "done", "blocked"),
    "in_progress": ("waiting_on_user", "done", "open", "code_complete", "blocked"),
    "waiting_on_user": ("in_progress", "done", "open"),
    "done": ("open",),
    "code_complete": ("done", "in_progress", "open", "qa_in_progress"),
    "qa_in_progress": ("qa_approved", "in_progress", "code_complete", "open"),
    "qa_approved": ("done", "in_progress", "open"),
    "blocked": ("open", "in_progress"),
}
```

The `update_status` method (`tickets.py:913-976`) calls `_coerce_status` (`:228-232`),
validates the status against `_TICKET_STATUSES`, then validates the transition against
`_STATUS_TRANSITIONS.get(current_status, ())`. The entire path is stateless with
respect to bounty: it reads only the ticket `status` field and the two module-level
maps.

### 2.2 TicketStore and update patterns

`TicketStore` (`tickets.py:244`) wraps `T.tickets`. Conditional updates use
`_conditional_update_meta` (`:723-790`) which CAS-updates the META row using
`ConditionExpression="#version = :expected_version"`. `_apply_header_update_once`
(`:792-805`) performs a single read-then-CAS (no retry loop): it reads the current
ticket once, calls `_conditional_update_meta`, and raises `TicketStateError` on
conflict without retrying.

`TicketStateError` (`:158-161`) carries a detail dict with a `code` key. The router
maps `code="ticket_update_conflict"` to HTTP 409; all other `TicketStateError` codes
(e.g. `invalid_ticket_status`, `invalid_ticket_status_transition`) map to HTTP 400.
This is implemented by `_ticket_state_http_status` (`app/routers/tickets.py:348-351`).

### 2.3 What TBT-002 adds (prerequisite)

TBT-002 extends the META row with optional fields including `bounty_status: str|None`
(values: `none|funded|claimed|submitted|paid_out|cancelled`) and adds the sparse
`ByBounty` GSI (`gsi_bounty_pk="BOUNTY#OPEN"`, `gsi_bounty_sk=created_at` numeric).
The `get_ticket` projection (`get_ticket` at `tickets.py:522-566`; there is no
separate `_ticket_out` helper — the projection is inlined in `get_ticket`) is extended
to surface these fields. TBT-004 reads `bounty_status` from the projected ticket dict and routes
transitions accordingly.

### 2.5 How `_is_admin_actor` is defined

## 3. Data Model

TBT-004 introduces no new DynamoDB tables or GSIs. All data mutations are on existing
rows in `T.tickets`.

### 3.1 Extended META row (via TBT-002)

The ticket META row (`pk=TICKET#{ticket_id}`, `sk=META`) gains the following optional
attributes, written by TBT-003 at bounty-post time and updated by TBT-004 state
transitions:

| Attribute | Type | Written by | Purpose |
|---|---|---|---|
| `bounty_status` | `S` | TBT-003 / TBT-004 | Current bounty lifecycle state |
| `bounty_id` | `S` | TBT-003 | Link to `BOUNTY#{id}/ESCROW` in `T.billing` |
| `bounty_amount_cents` | `N` | TBT-003 | Amount held in escrow |
| `bounty_currency` | `S` | TBT-003 | Currency code |
| `claimed_by_sub` | `S` | TBT-005 | Sub of the user who claimed the bounty |
| `claimed_at` | `N` | TBT-005 | Unix timestamp of claim |
| `bounty_funded_at` | `N` | TBT-003 | Unix timestamp of escrow hold |
| `bounty_submitted_at` | `N` | TBT-004 | Unix timestamp of submit-for-approval |
| `bounty_paid_at` | `N` | TBT-006 | Unix timestamp of payout |
| `bounty_cancelled_at` | `N` | TBT-007 | Unix timestamp of cancellation |
| `gsi_bounty_pk` | `S` | TBT-003 / TBT-004 | Sparse bounty board index key |
| `gsi_bounty_sk` | `N` | TBT-003 / TBT-004 | Numeric sort key (`created_at`) |

The `gsi_bounty_pk` / `gsi_bounty_sk` pair is only present when
`bounty_status == "funded"` (the open board). TBT-004 clears these attributes (via
`REMOVE`) when the ticket transitions away from `funded` (i.e., on `claimed`,
`cancelled`), and they are never re-added by TBT-004 (re-listing on unclaim is handled
by TBT-005).

The `gsi_bounty_sk` is numeric. Per the CLAUDE.md DynamoDB gotchas, it must be
declared with `attr_types={"gsi_bounty_sk": "N"}` in `scripts/local-ddb-init.py` (this
declaration is part of TBT-002's delivery, but TBT-004 authors must verify it is in
place before running tests).

### 3.2 Activity row for bounty transitions

Each state transition driven by TBT-004 also writes a `ticket_activity` row
(`pk=TICKET#{id}`, `sk=ACT#{ts}#{activity_id}`) with `activity_type` set to
`"bounty_status_changed"`, `actor_sub`, and both old and new `bounty_status` values.
This reuses the same write path used by `update_status` at `tickets.py:965-975` and
keeps the ticket activity feed informative without requiring a schema change.

## 4. API / Service Design

### 4.1 New module-level constants in `app/services/tickets.py`

```python
# Bounty lifecycle statuses added to the base set (flag-gated at runtime):
_BOUNTY_STATUSES = (
    "claimed",
    "pending_approval",
    "paid_out",
    "cancelled",
)

# Separate transition map: applied ONLY when a ticket has an active bounty.
# Keys are bounty_status values; values are allowed next ticket statuses.
# Note: paid_out and cancelled are terminal and have no outgoing transitions
# here — they are only reachable via dedicated bounty endpoints (TBT-006/007).
_BOUNTY_TRANSITIONS: dict[str, tuple[str, ...]] = {
    "funded":           ("in_progress",),    # claim → in_progress (TBT-005)
    "claimed":          ("pending_approval",),  # submit → pending_approval (TBT-004 gate)
    "pending_approval": ("in_progress",),    # reject → back to in_progress (TBT-006)
    # paid_out and cancelled are terminal; no outgoing paths through generic update_status
}
```

`_TICKET_STATUSES` is extended to include the four new values when the flag is on.
However, because the set is a module-level tuple used in validation, the safest
approach is to always include the four new statuses in `_TICKET_STATUSES` but gate
their *reachability* through the transition checks. This means:

- `_TICKET_STATUSES` gains `"claimed"`, `"pending_approval"`, `"paid_out"`,
  `"cancelled"` unconditionally (they are valid status strings the validator accepts).
- `_STATUS_TRANSITIONS` does NOT include entries for these four statuses.
- The `_BOUNTY_TRANSITIONS` map provides the allowed routing for bountied tickets only.
- With the flag off, no ticket can ever reach these statuses (no code path writes them).

### 4.2 Gate logic in `TicketStore.update_status`

The gate is inserted as an early check in `update_status` between the existing
`_coerce_status` call and the `_STATUS_TRANSITIONS` lookup (`:913-935`):

```python
def update_status(
    self,
    *,
    ticket_id: str,
    actor_sub: str,
    status: str,
    is_admin: bool = False,   # NEW: caller passes True when _is_admin_actor
) -> dict[str, Any] | None:
    requested_status = _coerce_status(status)
    if requested_status not in _TICKET_STATUSES:
        raise TicketStateError({...})

    ts = now_ts()
    cur = self.get_ticket(ticket_id)
    if not cur:
        return None

    current_status = cur.get("status", "open")
    bounty_status  = cur.get("bounty_status")  # None for non-bounty tickets

    # --- TBT-004: bounty gate ---
    if bounty_status and S.ticket_bounties_enabled:
        return self._update_status_bounty(
            ticket_id=ticket_id,
            cur=cur,
            actor_sub=actor_sub,
            requested_status=requested_status,
            bounty_status=bounty_status,
            current_status=current_status,
            ts=ts,
            is_admin=is_admin,
        )
    # --- end bounty gate ---

    # Existing non-bounty path unchanged below:
    allowed_next = _STATUS_TRANSITIONS.get(current_status, ())
    ...
```

The `is_admin` parameter is threaded through from the router endpoint so the service
never re-derives auth.

### 4.3 `_update_status_bounty` helper

```python
def _update_status_bounty(
    self,
    *,
    ticket_id: str,
    cur: dict[str, Any],
    actor_sub: str,
    requested_status: str,
    bounty_status: str,
    current_status: str,
    ts: int,
    is_admin: bool,
) -> dict[str, Any] | None:
```

Full behavior is described in Section 5. In summary:

1. Block direct transitions to `paid_out` or `cancelled` via this path (always 409
   with `code="bounty_terminal_via_dedicated_endpoint"`).
2. If `requested_status == "done"` and actor is the claimant (non-admin): reroute to
   `pending_approval`, set `bounty_status="submitted"`, write `bounty_submitted_at`.
3. Validate the requested ticket status against `_BOUNTY_TRANSITIONS[bounty_status]`.
4. Call `_apply_header_update_once` with the merged update (ticket status + bounty
   fields + GSI keys).
5. Write the `bounty_status_changed` activity row.

### 4.4 Service function signatures summary

All new functions live in `app/services/tickets.py` (inside `TicketStore`) or as
module-level helpers:

| Symbol | Signature |
|---|---|
| `_BOUNTY_STATUSES` | `tuple[str, ...]` (module constant) |
| `_BOUNTY_TRANSITIONS` | `dict[str, tuple[str, ...]]` (module constant) |
| `TicketStore.update_status` | Extended with `is_admin: bool = False` parameter |
| `TicketStore._update_status_bounty` | Private helper, see above |

### 4.5 Router changes in `app/routers/tickets.py`

The existing `POST /tickets/{ticket_id}/status` endpoint passes `is_admin` to the service.
The endpoint is `router.post` (NOT `router.patch`) at `app/routers/tickets.py:991`:

```python
@router.post("/{ticket_id}/status")
def set_ticket_status(         # NOTE: sync def, not async
    ticket_id: str,
    body: TicketStatusReq,
    request: Request,
    _ctx: dict[str, str] = Depends(require_ui_session),  # unused directly; auth gate only
    user: AuthenticatedUser = Depends(get_authenticated_user),  # NOTE: parameter is 'user', not 'actor'
) -> TicketEnvelope:
    _require_bounties_enabled_if_bounty_status(body.status)  # guard: block writing paid_out/cancelled via this endpoint
    try:
        result = STORE.update_status(
            ticket_id=ticket_id,
            actor_sub=user.sub,      # NOTE: user.sub, not ctx["user_sub"]
            status=body.status,
            is_admin=_is_admin_actor(request, user),  # NEW
        )
    except TicketStateError as exc:
        raise HTTPException(status_code=_ticket_state_http_status(exc), detail=_ticket_state_error(exc))
        # NOTE: HTTP status is 409 only for ticket_update_conflict; 400 for all other TicketStateError codes
    if result is None:
        _raise(404, "ticket_not_found", f"Ticket {ticket_id} not found")
    return _wrap_ticket(result)
```

`TicketStatusReq` (`app/routers/tickets.py:186-188`) already restricts `status` to a
`Literal` set. TBT-004 does NOT expand this Literal — `paid_out` and `cancelled` must
never be writable via the generic status endpoint. The Pydantic model remains unchanged.

## 5. Detailed Behavior & Edge Cases

### 5.1 Bounty state machine diagram

```
              ┌─────────────────────────────────────────────────┐
              │ bounty_status                                    │
              │                                                  │
  [TBT-003]   │  none ──► funded ──► claimed ──► submitted      │
              │                │         │            │          │
              │                │         │    [TBT-004 gate]     │
              │                │         │            │          │
              │           cancel(TBT-007)│       pending_approval│
              │                         │            │           │
              │                    unclaim(TBT-005)  ├─ reject(TBT-006) ──► claimed
              │                                      │           │
              │                                 approve(TBT-006) │
              │                                      │           │
              │                                  paid_out [terminal]
              │                                                   │
              │          cancel(TBT-007, admin only after claim)  │
              │                       └─► cancelled [terminal]   │
              └─────────────────────────────────────────────────┘
```

The parallel ticket `status` (the column shown in the Kanban board) mirrors the
bounty lifecycle as follows:

| bounty_status | ticket status |
|---|---|
| `funded` | `open` (unchanged from before posting) |
| `claimed` | `in_progress` (set by TBT-005 claim) |
| `submitted` | `pending_approval` (set by TBT-004 gate) |
| `paid_out` | `paid_out` (set by TBT-006) |
| `cancelled` | `cancelled` (set by TBT-007) |

### 5.2 The `done` → `pending_approval` reroute

When a user calls `PATCH /tickets/{id}/status` with `status="done"` on a ticket where
`bounty_status == "claimed"` and the caller is the `claimed_by_sub` (non-admin), the
service intercepts the transition and instead:

- Sets `ticket.status = "pending_approval"`.
- Sets `ticket.bounty_status = "submitted"`.
- Writes `bounty_submitted_at = now_ts()`.
- Clears the `ByBounty` GSI keys if present (they were already cleared at claim time
  by TBT-005, so this is defensive).
- Writes activity row `bounty_status_changed` with `from="claimed"`, `to="submitted"`.

An admin calling `done` on a `pending_approval` ticket (e.g., after the reject/re-work
loop brings it back to `claimed`) follows the same path: if `bounty_status == "claimed"`,
`done` always routes to `pending_approval`.

The router's `TicketStatusReq` Literal today accepts `"done"` (`tickets.py:187`). That
does not change — the reroute happens entirely in the service layer, invisible to the
caller.

### 5.3 Blocking `paid_out` and `cancelled` via the generic endpoint

Both statuses are added to `_TICKET_STATUSES` (so validation passes), but
`_STATUS_TRANSITIONS` has no outgoing edges for them and the bounty gate explicitly
raises:

```python
if requested_status in ("paid_out", "cancelled"):
    raise TicketStateError({
        "code": "bounty_terminal_via_dedicated_endpoint",
        "message": "Use the dedicated bounty approve/cancel endpoints.",
        "requested_status": requested_status,
    })
```

This guard fires before any transition lookup, ensuring they can never be reached via
`PATCH /tickets/{id}/status` regardless of who calls it.

### 5.4 Flag-off invariant

When `S.ticket_bounties_enabled` is `False`:

- No ticket ever has `bounty_status` set (TBT-003 is gated).
- The `_update_status_bounty` branch inside `update_status` is never entered because
  `bounty_status` is always `None` for every ticket.
- The Kanban board never shows `paid_out`, `cancelled`, `pending_approval`, or
  `claimed` columns because no ticket reaches those statuses.
- The existing `_STATUS_TRANSITIONS` table is used verbatim for every call.

The `_TICKET_STATUSES` tuple change (adding the four new values) is the only
modification that takes effect unconditionally. This is safe because `_TICKET_STATUSES`
is only used as a validation allowlist; being in the set does not make a status
reachable — it only prevents a `KeyError` if one somehow does appear.

### 5.5 Admin transitions on bountied tickets

When `is_admin=True` the bounty gate permits the following additional moves:

- `pending_approval → in_progress`: the reject path (TBT-006 `reject_bounty` calls
  `update_status(status="in_progress", is_admin=True)` after reverting `bounty_status`
  to `"claimed"`).
- Admins may never write `paid_out` or `cancelled` via `update_status` (see 5.3);
  they must use the dedicated endpoints.

Non-admins on a `pending_approval` ticket may not advance or retreat the ticket status
at all (any requested status raises `invalid_bounty_transition`).

### 5.6 Race conditions

Two concurrent `submit` calls on the same `claimed` ticket both attempt:

```python
_conditional_update_meta(
    ticket_id=ticket_id,
    expected_version=V,
    values={..., ":status": "pending_approval", ":bounty_status": "submitted", ...}
)
```

The CAS on `version` (`:792-805`) means only one succeeds. The other raises
`TicketStateError(code="ticket_update_conflict")` → HTTP 409 at the router.

This is the same protection already in place for concurrent `update_status` calls on
non-bounty tickets. No additional locking is required.

### 5.7 Transition from `pending_approval` back to `claimed` (reject path)

`reject_bounty` in TBT-006 updates `bounty_status` back to `"claimed"` on the escrow
row, then calls `update_status(status="in_progress", is_admin=True)`. The bounty gate
sees `bounty_status="claimed"` and `requested_status="in_progress"`:

`_BOUNTY_TRANSITIONS["claimed"] = ("pending_approval",)` — `in_progress` is NOT in
this set. So the gate must additionally allow `in_progress` when the admin calls reject
and `current_status == "pending_approval"`. The implementation handles this as a
special admin-privileged edge:

```python
if is_admin and current_status == "pending_approval" and requested_status == "in_progress":
    # This is the reject path — bounty_status was already reverted by the caller
    pass  # allow through
```

This is the only admin-specific carve-out inside `_update_status_bounty`.

### 5.8 `_conditional_update_meta` and bounty field write

TBT-004 extends the `_values` dict passed to `_conditional_update_meta` with bounty
fields. The update expression uses `SET` for string/numeric bounty fields and `REMOVE`
for clearing GSI attributes. The existing `_conditional_update_meta` at `:723-790`
already handles mixed SET/REMOVE expressions for space GSI keys; TBT-004 follows the
same pattern for `gsi_bounty_pk` / `gsi_bounty_sk`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### 7.1 SECOPS-007 parity

TBT-004 is a pure DynamoDB state machine with no external calls and no `dev_mode`
branching. The identical code path executes whether the process runs against DynamoDB
Local (moto) or production DynamoDB. There is no mock/real switch.

### 7.2 Idempotency

The `_conditional_update_meta` CAS on `version` makes all transitions idempotent with
respect to concurrent re-sends. A second identical transition request after the first
succeeds will observe that `version` has advanced and `bounty_status` / `status` have
already been updated; it will return the current state (via `get_ticket`) without
raising an error. The router returns HTTP 200 with the current ticket snapshot.

### 7.3 `paid_out` and `cancelled` are write-protected

Neither status can be written by `update_status`. The only path to `paid_out` is
`approve_bounty` (TBT-006) which writes it directly to the META row outside of
`update_status`. The only path to `cancelled` is `cancel_bounty` (TBT-007). This
design ensures that the escrow-release and refund operations (which move money) always
co-occur with the status flip.

### 7.4 Money-safety

TBT-004 itself moves no money. Its responsibility is that no transition can set a
ticket to `paid_out` without the escrow actually being released (TBT-006 handles the
atomic release). By blocking the generic endpoint from writing `paid_out`, TBT-004
prevents an admin from manually flipping a ticket `paid_out` without triggering the
payout.

### 7.5 Auth enforcement

The `is_admin` parameter is derived from `_is_admin_actor(request, actor)` in the
router, which checks both role (`Role.ADMIN` / `Role.ROOT`) and API key capability
`tickets:admin`. The service never re-derives auth from the session; it trusts the
caller to pass `is_admin` correctly. This matches the existing `_is_admin_actor`
pattern in `app/routers/tickets.py:224-225`.

## 8. Backward Compatibility & Migration

### 8.1 Non-bounty tickets

The existing `_STATUS_TRANSITIONS` map is untouched. Non-bounty tickets (where
`bounty_status is None`) bypass `_update_status_bounty` entirely. The addition of four
new values to `_TICKET_STATUSES` does not affect non-bounty behavior because:

- The validation at `update_status:915-920` only checks membership (not reachability).
- Non-bounty callers requesting `"paid_out"` or `"cancelled"` will pass the membership
  check but then be blocked by the terminal-status guard (which fires before the
  transition lookup) and receive HTTP 409.

In practice no caller today ever requests these status strings, so the guard is
defensive only.

### 8.2 Existing callers of `update_status`

`app/routers/messaging.py` does **NOT** call `STORE.update_status`. The `TicketStore.add_message`
method (`tickets.py:851`) handles the status side-effect of a new message internally (it
calls `_apply_header_update_once` directly with `_next_status_for_message` logic). The
known external callers of `STORE.update_status` are:
- `app/routers/tickets.py:1003` — the main status endpoint
- `app/routers/ticket_boards.py:484` — Kanban board status drag
- `app/routers/ticket_spaces.py:399` — space ticket status
- `app/services/payment_incident_ticket_sync.py:95` — incident-sync automation
- `app/routers/kyc_cases.py:784` — KYC case close
- `app/services/agent_pr_integration.py:203` — agent PR integration

All of these operate on tickets that never have `bounty_status` set in the current
codebase (none are bounty-aware), so the gate is a no-op for them. When TBT-004 is
implemented, each caller must pass the new `is_admin` parameter or accept the default
`is_admin=False`.

### 8.3 No database migration required

TBT-004 adds no new table rows, no new GSIs, and no new required attributes. The
`ByBounty` GSI and the four new status values that appear on the META row are written
for the first time only by TBT-003 (at bounty-post time). Tickets created before
TBT-003 is deployed have no `bounty_status` field, and the gate branch is never taken.

### 8.4 `TicketStatusReq` Literal is not expanded

`app/routers/tickets.py:186-188` defines:
```python
class TicketStatusReq(BaseModel):
    status: Literal["open", "in_progress", "waiting_on_user", "done", "reopened"]
```

This Pydantic Literal is NOT expanded to include the new bounty statuses. `paid_out`
and `cancelled` are intentionally unreachable via `POST /tickets/{ticket_id}/status`.

## 10. Open Questions / Assumptions

**D1 — Fee (resolved for this ticket):** TBT-004 does not deal with fee arithmetic.
The `_BOUNTY_TRANSITIONS` map has no fee-related logic. The decision that fee defaults
to 0% (`ticket_bounty_fee_bps=0`, Open Decision D1 recommendation) is relevant only
to TBT-006 (approve / release escrow).

**D2 — Wallet funding (resolved for this ticket):** TBT-004 does not deal with funding
source. The escrow hold in TBT-003 uses wallet balance (D2 recommendation: wallet-only
for v1). TBT-004 only transitions state.

**D3 — Who may submit:** The current design gates the `done → pending_approval` reroute
on the caller being the `claimed_by_sub`. Admins can also trigger this path (they pass
`is_admin=True`). An admin submitting on behalf of the claimant is permitted. Assumed
acceptable.

**D4 — Abandonment after claim (manual unclaim):** TBT-004 does not implement unclaim
— that is TBT-005. TBT-004 only blocks invalid transitions from `claimed` state (e.g.,
a non-claimant calling `done`). The question of whether the original poster can
"force-unclaim" by cancelling mid-flight is answered by TBT-007 (admin-cancel from any
non-terminal state).

**Assumption A1:** `bounty_status` is stored as a plain string attribute directly on the
ticket META row (not in a nested map), consistent with the other ticket scalar fields.
The `_ticket_out` projection at `tickets.py:528-566` surfaces it as a top-level key.

**Assumption A2 (CORRECTED — refactoring required):** The `_conditional_update_meta`
helper (`tickets.py:723-790`) uses a **hardcoded** `names` dict
(`tickets.py:724-745`) and a **hardcoded** `set_parts` list (`tickets.py:748-753`).
Adding bounty fields (`bounty_status`, `bounty_submitted_at`, `gsi_bounty_pk`,
`gsi_bounty_sk`) requires explicitly adding entries to both `names` and either
`set_parts` or the REMOVE logic. This is **not** a no-op extension — the method
must be refactored to accommodate the new attributes. The SET/REMOVE pattern for
optional GSI keys already present for space attributes (`gsi_space_pk` etc.) is the
correct model to follow, but the implementation requires code changes to
`_conditional_update_meta` itself.

**Assumption A3:** TBT-002's addition of `ByBounty` GSI to `scripts/local-ddb-init.py`
(with `attr_types={"gsi_bounty_sk": "N"}`) is complete and deployed before TBT-004
tests are run.
