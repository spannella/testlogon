# TBT-010 — Frontend — Bounty UI

## 1. Summary & Goal

TBT-010 delivers the complete React/TypeScript user interface that exposes the bounty subsystem to every user role. When `TICKET_BOUNTIES_ENABLED` is on, the UI adds:

- Bounty amount badge and status chip on every ticket card and detail view
- "Post Bounty" form for ticket owners
- "Claim" button on funded, unclaimed bounties visible on the ticket detail and the new Bounty Board page
- "Submit for Approval" for the active claimant
- Admin approval and rejection actions for `pending_approval` tickets
- "Cancel & Refund" for the poster (while unclaimed) and for admin/root in any non-terminal state
- A standalone `/bounties` page (Bounty Board) listing `GET /tickets/bounties/open`

All bounty UI is hidden behind a compile-time feature flag (`VITE_TICKET_BOUNTIES_ENABLED=false` default). The flag is checked before any component is rendered or any API call is made; removing or disabling the flag returns the ticket pages to their exact current state.

## 3. Data Model

TBT-010 is a pure frontend ticket. It reads the data model defined by TBT-001 through TBT-009 but adds no new DDB rows or indexes of its own. For completeness, the fields the frontend consumes are:

### Extended `Ticket` TypeScript interface (additive)

```typescript
// All fields are optional/nullable — absent on non-bounty tickets.
bounty_amount_cents?: number | null;
bounty_currency?: string | null;
// bounty_status values per TBT-004/006/009: "funded"|"claimed"|"submitted"|"paid_out"|"cancelled"
// "pending_approval" is the TICKET status (ticket.status field), NOT a bounty_status value.
// When a claimant submits, bounty_status → "submitted" and ticket.status → "pending_approval".
bounty_status?: BountyStatus | null;
bounty_id?: string | null;
claimed_by_sub?: string | null;
claimed_at?: number | null;
bounty_funded_at?: number | null;
bounty_submitted_at?: number | null;
bounty_paid_at?: number | null;
bounty_cancelled_at?: number | null;
```

### Bounty Board response type

`GET /tickets/bounties/open` returns: *(no `/ui` prefix — the tickets router has prefix `/tickets`, not `/ui/tickets`)*

```typescript
interface BountyBoardItem {
  ticket_id: string;
  subject: string;
  bounty_amount_cents: number;
  bounty_currency: string;
  bounty_status?: "funded"; // always "funded" on the board; included to match TBT-009 Python model
  labels: string[];
  created_at: number;
}

interface BountyBoardEnvelope {
  items: BountyBoardItem[];
  next_cursor?: string | null;
}
```

This is a sparse projection from the `ByBounty` GSI on `T.tickets` (defined in TBT-002: `gsi_bounty_pk="BOUNTY#OPEN"`, `gsi_bounty_sk=created_at`, `attr_types={"gsi_bounty_sk":"N"}`). Only funded+unclaimed tickets are indexed there; the board never shows claimed, submitted, paid_out, or cancelled items.

## 5. Detailed Behavior & Edge Cases

### 5.1 BountyBadge component

`BountyBadge` receives a `Ticket` and renders nothing if `!ticket.bounty_status || ticket.bounty_status === "none"`. When a bounty is present it renders two chips side by side:

- **Amount chip**: `$X.XX` formatted from `bounty_amount_cents / 100` in `bounty_currency`. Use `Intl.NumberFormat` with the currency.
- **Status chip**: A shadcn `Badge` with variant per status:
  - `funded` → `secondary` (blue-ish)
  - `claimed` → `outline` (grey)
  - `submitted` → `default` (yellow)
  - `pending_approval` → `default` (amber)
  - `paid_out` → success green (custom className)
  - `cancelled` → destructive (red)

This component is inserted into `TicketsPage.tsx` alongside the existing status badge (TicketsPage.tsx, in the ticket list card and the detail panel). It is only rendered when `isTicketBountiesEnabled()` returns true.

### 5.2 PostBountyDialog

Visible only when:
1. `isTicketBountiesEnabled()` is true
2. Current user `userId === ticket.owner_sub`
3. `ticket.bounty_status` is absent/null (bounty not yet posted) OR `ticket.bounty_status === "cancelled"` (re-post is allowed by the backend after cancel)
4. Ticket `status === "open"`

The form contains:
- Amount input (number, min 1.00, max derived from `S.ticket_bounty_max_cents` — fetched from a new `GET /ui/config/ticket-bounties` config endpoint or hardcoded to 100,000.00 for v1; see Section 10 for open decision on config endpoint)
- Currency select (default "usd"; v1 only USD supported)
- Wallet balance display: reads `queryClient.getQueryData(["billing", "wallet"])?.wallet_balance_cents`. Shows "Insufficient balance" validation inline if `amount_cents > wallet_balance_cents`.
- Submit button calls `postBounty` mutation; on success: `queryClient.invalidateQueries(["tickets", "detail", ticketId])` and `queryClient.invalidateQueries(["billing", "wallet"])`.

Error handling:
- HTTP 402 ("insufficient balance" from the service) → toast "Insufficient wallet balance".
- HTTP 403 ("account frozen" or fraud-blocked) → toast "Transaction blocked. Contact support."
- HTTP 409 (bounty already funded, idempotent double-post) → silently refresh ticket detail; treat as success.

### 5.3 BountyActionsPanel

This component mounts inside the ticket detail panel (below the existing message thread) whenever `isTicketBountiesEnabled()` and `ticket.bounty_status != null && ticket.bounty_status !== "none"`. It renders the contextually appropriate action buttons based on `ticket.bounty_status`, `currentUserSub`, and `isAdmin`.

State machine view (what the panel shows per actor per state):

| `bounty_status` (from ticket) | Owner (non-admin) | Any other user | Claimant | Admin/Root |
|---|---|---|---|---|
| `funded` | "Cancel & Refund" | "Claim Bounty" | — | "Claim Bounty" + "Cancel & Refund" |
| `claimed` | — | — | "Submit for Approval" + "Release Claim" | "Cancel & Refund" |
| `submitted` | — | — | (waiting — `ticket.status` is `"pending_approval"`) | "Approve" + "Reject" + "Cancel & Refund" |
| `paid_out` | (read-only — shows paid timestamp) | (read-only) | (read-only) | (read-only) |
| `cancelled` | (read-only — can re-post) | — | — | (read-only) |

> **CORRECTED**: "`pending_approval`" is `ticket.status` (the helpdesk status field), **not** a `bounty_status` value. The panel reads `ticket.bounty_status === "submitted"` to enter the admin-review state. The earlier draft listed "`submitted` / `pending_approval`" as two separate bounty_status rows — that was wrong. There is only one row: when `bounty_status === "submitted"`, the ticket status field happens to be `"pending_approval"`.

Determining "claimant": `ticket.claimed_by_sub === currentUserSub`.

Each button calls its respective API wrapper mutation. On success, each mutation invalidates:
- `["tickets", "detail", ticketId]`
- `["tickets"]` list (for status badge updates in the sidebar)
- `["billing", "wallet"]` on cancel (refund) and approve (credit)
- `["bounties", "open"]` on claim, cancel (which removes/adds the ticket from the board)

**"Cancel & Refund" confirmation dialog**: Because this involves money, the cancel action must be confirmed. A small `AlertDialog` (shadcn) asks "Cancel bounty and return $X.XX to your wallet?" with "Confirm" / "Cancel" buttons. This applies to both owner-cancel and admin-cancel.

**"Reject" form**: Rejection requires a `reason` string. A small inline textarea or `Dialog` collects the reason before calling `rejectBounty`.

### 5.4 BountyBoardPage — `/bounties`

Route: `/bounties` (lazy-loaded). Added to `frontend/src/App.tsx` inside the existing `<Route element={<ProtectedRoute><AppShell /></ProtectedRoute>}>` container (`App.tsx:316`) alongside the existing `/tickets` and `/tickets/boards` routes (`App.tsx:382–384`). The route inherits auth protection from its parent — **individual routes are not separately wrapped in `ProtectedRoute`** in this codebase's pattern.

The page uses `useInfiniteQuery` with `listOpenBounties` to paginate the board. Each item shows:
- Subject (link to `/tickets` with the ticket selected, or a separate detail route)
- Bounty amount badge (`BountyBadge` restricted to the amount chip only)
- Labels (rendered as small pills, same style as `TicketsPage`)
- "Posted" timestamp (`fmt(item.created_at)`)
- "Claim" button — calls `claimBounty(item.ticket_id)` mutation; on success navigates to `/tickets` with the ticket selected (or to the board detail if the ticket belongs to a board)

The page renders a "No open bounties" empty state when `items.length === 0`.

Pagination: a "Load more" button appears when `next_cursor` is present. Uses `fetchNextPage` from `useInfiniteQuery`.

The page header has a "Post a bounty" secondary call-to-action (deep link to `/tickets` with create-ticket intent); this is a convenience link, not a standalone flow.

### 5.5 TicketsPage and BoardDetailPage integration

In `TicketsPage.tsx`, the ticket list item cards gain the `BountyBadge` as an additional inline element after the existing status badge (gated on `isTicketBountiesEnabled()`).

In the ticket detail panel:
- If the selected ticket has `bounty_status`, `BountyActionsPanel` renders below the message input area.
- `PostBountyDialog` trigger button ("+ Post Bounty") appears in the detail header toolbar if the current user is the owner and no funded bounty exists.

In `BoardDetailPage.tsx` and `BoardKanban.tsx`, the `BountyBadge` component is inserted into each ticket card render.

### 5.6 Navigation

Add a "Bounty Board" nav entry in `AppShell` sidebar (or `Header` nav) gated on `isTicketBountiesEnabled()`. This prevents the route from appearing in navigation when the feature is off.

### 5.7 Edge cases

**Race on claim**: Two users click "Claim" simultaneously. The second caller receives HTTP 409 from the backend conditional put. The frontend handles 409 on claim as: "This bounty was just claimed by someone else." + invalidate ticket detail to show the updated state.

**Claimant's "Release Claim" (unclaim)**: Renders as a secondary/outline button distinct from "Submit for Approval". Requires a confirmation dialog: "Release your claim? The bounty will return to the board." Calls `unclaimBounty`.

**Admin approves already-paid bounty (idempotent)**: HTTP 409 "already paid out" → toast "Bounty already paid." + refresh.

**Cancelling a paid_out bounty**: HTTP 409 "already paid out" → toast "Cannot cancel after payout."

**Wallet balance display in PostBountyDialog**: The `["billing", "wallet"]` query may not be in cache (user never visited Billing page). The dialog triggers a `useQuery` for wallet balance on mount; shows a spinner in the balance line while loading. If the query fails, balance display is omitted (does not block the form — the server is the authoritative insufficient-balance guard).

**Amounts display**: Always display in the ticket's `bounty_currency`. If `bounty_currency` is absent, default to "USD". Format: `$1,234.56` for USD. Future currencies are formatted via `Intl.NumberFormat(undefined, { style: "currency", currency })`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### Dev/prod parity

The frontend makes no `dev_mode` check. All API calls go through the same Axios instance (`api/client.ts`) that attaches CSRF tokens and handles 401 → logout. Error handling is uniform across environments. There is no mock response path in the frontend for bounty operations; the dev stack runs the real backend with moto-backed DynamoDB.

### Money-safety in the UI

The frontend is NOT the authoritative guard on money operations. Every guard listed here is defense-in-depth only — the backend service layer enforces all invariants:

- **Insufficient balance**: shown as inline validation in `PostBountyDialog` to reduce round-trips, but the server enforces the conditional `wallet_balance_cents >= :needed` via `apply_wallet_delta` (billing_shared.py:185–213; the `ConditionExpression` is at billing_shared.py:209). Note: `post_bounty` uses `transact_write_items` (not `apply_wallet_delta` directly) with an equivalent inline `ConditionExpression` — `apply_wallet_delta` is the standalone `update_item` version of the same guard.
- **Frozen account**: the `_fraud_gate` check in `billing.py:118–175` always runs server-side on `post_bounty`; the frontend surfaces the resulting 403 as a toast.
- **Double-debit prevention**: the frontend does not debit anything. All wallet operations are server-side atomics. The UI only invalidates the `["billing", "wallet"]` cache after a confirmed server response.
- **Idempotent mutations**: all bounty POST mutations are safe to retry. The server uses `attribute_not_exists(pk)` conditional puts and deterministic `bounty_id` (SHA-256 of `bounty:{ticket_id}`). If the frontend fires a mutation twice due to a network retry, the second call returns 409 which the UI treats as success + refresh.

### CSRF

All non-GET API calls include the CSRF token via the `api()` fetch wrapper in `api/client.ts` (client.ts:179–181 — `getCookie("ui_csrf")` + `headers.set("X-CSRF-Token", csrf)`). **The client does not use Axios** — it wraps the native `fetch` API. No special handling is needed for bounty endpoints.

### Authorization UI cues

The frontend hides action buttons that the current user is unauthorized to perform (e.g., "Approve" is only shown when `isAdmin`). This is a UX convenience — the backend enforces auth independently via `_is_admin_actor` (`app/routers/tickets.py:224`) and session ownership checks. If a user crafts a direct POST, the server returns 403.

## 8. Backward Compatibility & Migration

With `VITE_TICKET_BOUNTIES_ENABLED=false` (the default):

- `frontend/src/api/endpoints/tickets.ts`: the new type declarations (`BountyStatus`, extended `Ticket` interface, new API functions) are present in the bundle but unused. - No DynamoDB schema changes are needed for this ticket (those are in TBT-001, TBT-002).
- No existing E2E tests are affected. Existing `frontend/e2e/tickets.spec.ts` (42 tests, sections 52–57) continues to pass unchanged because the bounty flag defaults off.

## 10. Open Questions / Assumptions

**A1 — Config endpoint for min/max amounts.** The `PostBountyDialog` needs to know `ticket_bounty_min_cents` and `ticket_bounty_max_cents` for client-side validation. Two options:
- (Recommended v1) Hardcode `min=100`, `max=10000000` as UI constants matching the server defaults. If the operator changes the env vars, the server enforces the limits with 400; the UI shows the server error message.
- (Follow-up) Add `GET /ui/config/ticket-bounties` returning `{ min_cents, max_cents, fee_bps }` and fetch it once on page load with a stale-while-revalidate query.

**A2 — Ticket detail routing.** Currently `TicketsPage` is a split-panel where `selectedId` drives the detail view. Clicking a Bounty Board item should navigate to `/tickets` and select that ticket. The simplest approach is to navigate to `/tickets?selected={ticket_id}` and have `TicketsPage` read the query param on mount to set `selectedId`. Confirm the routing approach with the team.

**A3 — Re-post after cancel.** The ticket spec (TBT-004) allows `cancelled → funded` for a re-post. The `PostBountyDialog` trigger renders when `bounty_status === null || bounty_status === "cancelled"`. This assumes the backend allows re-posting (the `attribute_not_exists(pk)` guard on the escrow row would need the old escrow row to not block re-post). Clarify with TBT-003 implementer whether re-post generates a new `bounty_id` or reuses the old one.

**A4 — D1 (fee display).** At 0% default fee, the payout display in the approve panel simply shows the full posted amount. If `ticket_bounty_fee_bps` is non-zero in future, the "Approve" dialog should surface `net = amount - fee` to the admin before confirmation. This is a follow-up for when D1 is resolved as non-zero.

**A5 — D4 (unclaim) button label.** The spec calls this "unclaim / abandonment". The UI labels it "Release Claim" to emphasize voluntary release rather than failure. Confirm label with product/design.
