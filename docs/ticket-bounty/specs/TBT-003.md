**Milestone:** 1 — Escrow & bounty foundation
**Type:** Feature | **Priority:** P0 | **Estimate:** 2 days
**Depends on:** TBT-001 (feature flag, settings, escrow table decision), TBT-002
(bounty fields + projection)

## 1. Summary & Goal

This ticket implements the escrow-hold operation that funds a ticket bounty. When
a ticket owner posts a bounty, two things must happen atomically: the poster's
wallet is debited for the bounty amount, and an escrow record is written to
`T.billing`. Neither can succeed without the other. If the wallet balance is
insufficient, nothing is written. If the escrow record already exists (replay or
double-post), the operation is a no-op that never double-debits.

The deliverable is a new service module `app/services/ticket_bounties.py`
containing `post_bounty(...)` plus its supporting helpers. No endpoint is wired
in this ticket — that is TBT-009. No state-machine changes are needed here — the
post operation simply sets `bounty_status="funded"` on the ticket META row (a
field introduced in TBT-002) and populates the sparse ByBounty GSI keys.

## 2. Context & Current State

### Ticket META row and partition layout

`create_ticket` (`app/services/tickets.py:411-512`) writes the META row as
`pk=TICKET#{ticket_id}`, `sk="META"`. All subsequent ticket items (messages at
`MSG#`, activities at `ACT#`) live in the same partition. Helper
`_ticket_pk(ticket_id)` (`tickets.py:164`) produces `TICKET#{ticket_id}`.

The `version` field (`tickets.py:550`) is an optimistic-concurrency integer.
`_apply_header_update_once` (`tickets.py:792-805`) uses it for CAS updates via
`_conditional_update_meta` (`tickets.py:723-790`), which executes an
`update_item` conditional on `version = :expected_version`. TBT-003 will update
the META row using a separate `update_item` (after the atomic transaction
completes) to set the bounty fields introduced by TBT-002.

The projection function `get_ticket` (`tickets.py:522-566`) reads the META item
and assembles a dict. It already returns any attribute stored on the row; TBT-002
added `bounty_amount_cents`, `bounty_status`, `bounty_id`, etc. to that
projection. By the time TBT-003 ships, those fields will be readable.

### Billing table and wallet primitives

The billing table (`T.billing`, `app/core/tables.py:333`) uses `pk`/`sk` as its
primary key. The table name is `S.billing_table_name` (default `"billing"`,
`app/core/settings.py:348`). The GSI `GSI_LEDGER_DATE` (`scripts/local-ddb-init.py:71-77`)
partitions by `ledger_date` / `sk`.

All wallet reads and writes use these helpers from
`app/services/billing_shared.py`:

- `get_wallet_balance(table, pk)` (`billing_shared.py:176-182`) — returns
  `{"wallet_balance_cents": int, ...}` from `pk / WALLET` row; returns `0` if
  the row is absent.
- `apply_wallet_delta(table, pk, delta_cents)` (`billing_shared.py:185-213`) —
  for negative `delta_cents` (withdrawal) issues an `update_item` with
  `ConditionExpression="wallet_balance_cents >= :needed"`. On
  `ConditionalCheckFailedException` this signals insufficient balance.
- `new_ledger_entry(key_name, key_value, entry_type, amount_cents, state, reason, meta, extra)` (`billing_shared.py:224-259`) — builds a ledger item
  with deterministic `sk=LEDGER#{ts}#{ulidish()}`, sets `ledger_date` for
  `GSI_LEDGER_DATE`, and returns `(sk, item)`.
- `settle_or_reverse_ledger(table, key_name, key_value, ledger_sk_value, new_state)` (`billing_shared.py:262-274`) — updates a ledger item's `state` attribute
  in place; used by `refund_payment` (`app/routers/billing.py:1323-1324`).
- `ulidish()` (`billing_shared.py:216-217`) — time-prefixed random ID for
  ledger entry de-duplication.
- `user_pk(user_id)` (`billing_shared.py:23-24`) — produces `USER#{user_id}`.

### Atomic transact_write_items precedent

`app/services/group_treasury.py` demonstrates the canonical pattern for atomic
multi-item DynamoDB writes in this codebase. The `_escrow_transact_items`
function (`group_treasury.py:631-693`) builds a list of low-level `{"Update": {...}}`
and `{"Put": {...}}` dicts, and `_batch_transact` (`group_treasury.py:743-751`)
calls `_transact_client().transact_write_items(TransactItems=items)`. The
`_transact_client` helper (`group_treasury.py:716-740`) constructs a plain
`boto3.client("dynamodb", ...)` by reading the endpoint, region, and credentials
from `T.billing.meta.client` — it does NOT call `transact_write_items` on
`.meta.client` directly (that would go through the high-level resource
serializer). This ensures DynamoDB Local is used in dev and real AWS in prod —
no `S.dev_mode` branch.

Items must be serialized to AttributeValue maps via `_to_ddb_item` (using
`TypeSerializer`, `group_treasury.py:47-53`) before passing to the low-level
client, since the high-level resource serializer does not participate in
`transact_write_items` calls made through the raw client.

The cap of 25 items per `transact_write_items` call
(`group_treasury.py:32-37`) applies here, but TBT-003's transaction has only
three items (wallet debit + escrow put + ledger put), well within limit.

### Fraud gate

`_fraud_gate(user_id, amount_cents, entry_type, tx_id, req, enforce_block)`
(`app/routers/billing.py:118-175`) calls `fd.is_frozen(user_id)` first (403 if
frozen), then `fd.evaluate_transaction(...)`. On `action="block"` it raises HTTP
403 when `enforce_block=True`. The function is module-level in `billing.py`;
TBT-003 will import it directly. It accepts an optional `Request` for IP
extraction; passing `None` is safe (IP will be omitted from the fraud record).

### Existing ticket GSIs and the ByBounty sparse index

`scripts/local-ddb-init.py:695-711` currently declares ten GSIs on the tickets
table. TBT-002 adds an eleventh: `ByBounty` with
`partition_key="gsi_bounty_pk"`, `sort_key="gsi_bounty_sk"` (numeric,
`attr_types={"gsi_bounty_sk": "N"}`). TBT-003 sets these GSI keys on the ticket
META row as part of funding — this is what places the ticket on the bounty board.

## 3. Data Model

### Escrow record on `T.billing`

The escrow record is a single item co-located with all other billing rows. Using
`T.billing` (per TBT-001's decision) means refund and audit queries stay on one
table with no new DDB table or provisioning change.

```
pk  = "BOUNTY#{bounty_id}"
sk  = "ESCROW"
```

Attributes written at hold time:

| Attribute | Type | Notes |
|---|---|---|
| `pk` | S | `BOUNTY#{bounty_id}` |
| `sk` | S | `"ESCROW"` |
| `bounty_id` | S | deterministic (see §4) |
| `ticket_id` | S | FK to tickets table |
| `poster_sub` | S | user who funded the bounty |
| `amount_cents` | N | integer, validated within min/max |
| `currency` | S | always `"usd"` for v1 |
| `status` | S | `"held"` on creation |
| `created_at` | N | `now_ts()` |
| `ledger_sk` | S | sk of the audit ledger entry, for `settle_or_reverse_ledger` |
| `ledger_date` | S | UTC date string, for `GSI_LEDGER_DATE` visibility |

The escrow row is protected at write time by
`ConditionExpression="attribute_not_exists(pk)"` (idempotency guard). Status
transitions to `"released"` (TBT-006 approve) or `"refunded"` (TBT-007 cancel)
are written by subsequent tickets.

### Audit ledger entry on `T.billing`

A single ledger entry records the debit for audit, payout-balance calculation,
and platform financial dashboard:

```
pk  = "USER#{poster_sub}"
sk  = ledger_sk(ts, entry_id)       # e.g. "LEDGER#1749000000#<ulidish>"
```

Fields populated by `new_ledger_entry(...)` (`billing_shared.py:224`):

| Attribute | Value |
|---|---|
| `entry_id` | `ulidish()` — time-prefixed random |
| `type` | `"debit"` |
| `amount_cents` | bounty amount |
| `state` | `"pending"` — transitions to `"settled_released"` (approve) or `"reversed"` (cancel) |
| `reason` | `"bounty_escrow"` |
| `meta` | `{"bounty_id": ..., "ticket_id": ..., "escrow_state": "held"}` |
| `ledger_date` | UTC date string from `ledger_date_for_ts(ts)` |

The `ledger_sk` value (the `sk` of this item) is stored on the escrow row so
later operations can call `settle_or_reverse_ledger` without re-querying.

### Ticket META row mutation (post-transaction)

After the atomic transaction succeeds, a separate `update_item` on `T.tickets`
sets the bounty fields introduced by TBT-002:

| Attribute | Value |
|---|---|
| `bounty_id` | deterministic id |
| `bounty_amount_cents` | N |
| `bounty_currency` | `"usd"` |
| `bounty_status` | `"funded"` |
| `bounty_funded_at` | `now_ts()` |
| `gsi_bounty_pk` | `"BOUNTY#OPEN"` — places ticket on the board |
| `gsi_bounty_sk` | `created_at` (numeric integer) — sort key for the ByBounty GSI |

The `gsi_bounty_sk` must be stored as a DynamoDB Number type, which requires
`attr_types={"gsi_bounty_sk": "N"}` in the `TableDef` (TBT-002). Passing an
integer value through `_FloatSafeTable` (`app/core/tables.py:41-49`) is
sufficient — no extra serialization is needed.

The version is not incremented here (this is a meta-annotation, not a status
transition), but the standard optimistic-lock field `updated_at` is refreshed.

## 4. API / Service Design

### New module: `app/services/ticket_bounties.py`

#### Module-level helpers

```python
def _bounties_enabled() -> bool:
    return bool(getattr(S, "ticket_bounties_enabled", False))

def _require_bounties_enabled() -> None:
    if not _bounties_enabled():
        raise HTTPException(status_code=404, detail="Ticket bounties are not enabled")
```

Pattern mirrors `app/services/inventory.py:50-56`. `HTTPException` is imported
from `fastapi`.

#### `_bounty_id(ticket_id: str) -> str`

```python
import hashlib

def _bounty_id(ticket_id: str) -> str:
    return hashlib.sha256(f"bounty:{ticket_id}".encode()).hexdigest()[:24]
```

Deterministic, stable across replays. The 24-character hex prefix gives 96 bits
of uniqueness — sufficient given the one-bounty-per-ticket invariant.

#### `_transact_client() -> Any`

Mirrors `group_treasury._transact_client()` exactly: derives endpoint, region,
and credentials from `T.billing.meta.client`, returns a plain
`boto3.client("dynamodb", ...)`. This ensures DynamoDB Local is used in dev
with no `S.dev_mode` branch (SECOPS-007 parity).

#### `_to_ddb_item(item: dict) -> dict`

Uses `boto3.dynamodb.types.TypeSerializer` to serialize a plain Python dict to
AttributeValue form. Matches `group_treasury._to_ddb_item()` exactly.

#### `post_bounty` — main entry point

```python
def post_bounty(
    *,
    ticket_id: str,
    poster_sub: str,
    amount_cents: int,
    currency: str = "usd",
    request: Optional[Request] = None,
) -> dict[str, Any]:
    ...
```

**Returns:** the updated ticket dict (result of `TicketStore.get_ticket`), with
bounty fields populated.

**Raises:**
- `HTTPException(404)` — bounties disabled or ticket not found
- `HTTPException(400)` — amount out of range, wrong currency, ticket not `"open"`
- `HTTPException(409)` — ticket already has a funded bounty, or poster is not the owner
- `HTTPException(402)` — insufficient wallet balance (ConditionalCheckFailed)
- `HTTPException(403)` — account frozen or fraud-blocked

### No new Pydantic request/response models in this ticket

The `post_bounty` function returns a plain dict that the router (TBT-009) will
wrap in `TicketEnvelope`. Request validation (amount range, currency) is done
inside the service; the router passes the raw fields through. This keeps the
service hermetically testable without HTTP plumbing.

## 5. Detailed Behavior & Edge Cases

### Step-by-step execution of `post_bounty`

**Step 1 — Feature gate**

```python
_require_bounties_enabled()
```

Raises `HTTPException(404)` if `S.ticket_bounties_enabled` is falsy. This is the
first check so flag-off behavior is identical to "endpoint not found".

**Step 2 — Load and validate the ticket**

```python
store = TicketStore()          # or import module-level STORE
ticket = store.get_ticket(ticket_id)
if not ticket:
    raise HTTPException(404, "Ticket not found")
if ticket["owner_sub"] != poster_sub:
    raise HTTPException(403, "Only the ticket owner may post a bounty")
if ticket["status"] != "open":
    raise HTTPException(400, "Bounty may only be posted on open tickets")
if ticket.get("bounty_status") not in (None, "cancelled"):
    raise HTTPException(409, "Ticket already has an active bounty")
```

`bounty_status=None` means no bounty ever posted. `bounty_status="cancelled"`
means a previous bounty was refunded and a new one may be posted (poster paid
back in full). Any other existing bounty_status (funded/claimed/submitted/
paid_out) is a conflict.

**Step 3 — Amount validation**

```python
if amount_cents < S.ticket_bounty_min_cents:
    raise HTTPException(400, f"Minimum bounty is {S.ticket_bounty_min_cents} cents")
if amount_cents > S.ticket_bounty_max_cents:
    raise HTTPException(400, f"Maximum bounty is {S.ticket_bounty_max_cents} cents")
if currency != "usd":
    raise HTTPException(400, "Only USD bounties are supported in v1")
```

`S.ticket_bounty_min_cents` defaults to `100` (1 USD) and
`S.ticket_bounty_max_cents` defaults to `10_000_000` (100,000 USD) per TBT-001.

**Step 4 — Fraud and freeze gate**

```python
from app.routers.billing import _fraud_gate   # lazy import avoids circular dep
_fraud_gate(poster_sub, amount_cents, "bounty_hold", tx_id=ticket_id,
            req=request, enforce_block=True)
```

`is_frozen` is checked inside `_fraud_gate`; a frozen account raises HTTP 403
immediately. A fraud `"block"` action with `enforce_block=True` also raises 403.
A fraud `"flag"` is logged and allowed through (the bounty proceeds but is
flagged for review).

**Step 5 — Build the bounty_id**

```python
bounty_id = _bounty_id(ticket_id)
```

Deterministic. If `post_bounty` is called twice for the same ticket (network
retry, client double-submit), the same `bounty_id` is produced each time.

**Step 6 — Build transaction items**

Three items for the `transact_write_items` call:

**(a) Wallet debit** — `Update` item on `USER#{poster_sub}` / `WALLET`:

```
UpdateExpression:
  SET wallet_balance_cents = wallet_balance_cents + :neg_amount, updated_at = :t
ConditionExpression:
  wallet_balance_cents >= :amount
ExpressionAttributeValues:
  {":neg_amount": -amount_cents, ":amount": amount_cents, ":t": ts}
```

This is the same guard used by `apply_wallet_delta` (`billing_shared.py:203-213`)
expressed as a `transact_write_items` Update item rather than a standalone
`update_item`. If `wallet_balance_cents` is missing (no wallet row exists), the
condition fails immediately → 402.

**(b) Escrow put** — `Put` item at `BOUNTY#{bounty_id}` / `ESCROW`:

```
Item: {pk, sk, bounty_id, ticket_id, poster_sub, amount_cents, currency,
       status: "held", created_at, ledger_sk: <pre-computed>, ledger_date}
ConditionExpression: attribute_not_exists(pk)
```

`attribute_not_exists(pk)` is the idempotency guard. If a `BOUNTY#{bounty_id}`
row already exists (prior successful transaction that updated the ticket), the
transaction will fail with `TransactionCanceledException` with reason
`ConditionalCheckFailed` on this item. The caller should treat this as a 409 and
return the existing ticket state.

**(c) Ledger entry put** — `Put` item at `USER#{poster_sub}` / `ledger_sk(ts, entry_id)`:

```
Item: built by new_ledger_entry(key_name="pk", key_value=user_pk(poster_sub),
      entry_type="debit", amount_cents=amount_cents, state="pending",
      reason="bounty_escrow", meta={"bounty_id": ..., "ticket_id": ...,
      "escrow_state": "held"})
ConditionExpression: attribute_not_exists(sk)
```

Using `attribute_not_exists(sk)` on the ledger entry is belt-and-suspenders;
since `ledger_sk` embeds a `ulidish()` (time + random), collisions are
practically impossible, but the guard makes the item idempotent if the same
`ts` and `entry_id` are somehow replayed.

All three items are serialized with `_to_ddb_item(...)` and passed to:

```python
_transact_client().transact_write_items(TransactItems=[item_a, item_b, item_c])
```

**Step 7 — Handle transaction errors**

```python
from botocore.exceptions import ClientError

try:
    _transact_client().transact_write_items(TransactItems=[...])
except ClientError as exc:
    code = exc.response["Error"]["Code"]
    if code == "TransactionCanceledException":
        reasons = exc.response.get("CancellationReasons", [])
        # item (a) wallet check failed → 402
        if reasons and reasons[0].get("Code") == "ConditionalCheckFailed":
            raise HTTPException(402, "Insufficient wallet balance")
        # item (b) escrow already exists → 409 (idempotent replay)
        if len(reasons) > 1 and reasons[1].get("Code") == "ConditionalCheckFailed":
            # Re-read and return the existing ticket (idempotent success)
            return store.get_ticket(ticket_id) or {}
    raise
```

The `CancellationReasons` list from DynamoDB Local (moto) and real DynamoDB
both include one reason per transaction item in declaration order. Item index 0
is the wallet Update; index 1 is the escrow Put.

**Step 8 — Update ticket META row**

After the transaction succeeds, update the ticket:

```python
ts = now_ts()
T.tickets.update_item(
    Key={"pk": _ticket_pk(ticket_id), "sk": "META"},
    UpdateExpression=(
        "SET bounty_id = :bid, bounty_amount_cents = :amt, bounty_currency = :cur, "
        "bounty_status = :bs, bounty_funded_at = :fat, updated_at = :t, "
        "gsi_bounty_pk = :gbpk, gsi_bounty_sk = :gbsk"
    ),
    ExpressionAttributeValues={
        ":bid": bounty_id,
        ":amt": amount_cents,
        ":cur": currency,
        ":bs": "funded",
        ":fat": ts,
        ":t": ts,
        ":gbpk": "BOUNTY#OPEN",
        ":gbsk": int(ticket["created_at"]),
    },
)
```

`gsi_bounty_sk` is set to the ticket's original `created_at` (integer) so the
bounty board sorts tickets by when they were originally opened, not when the
bounty was posted. The `_FloatSafeTable` wrapper handles float-to-Decimal
coercion (`app/core/tables.py:41-49`), but since `created_at` is already an
integer, no coercion is needed.

Note: this `update_item` is intentionally outside the atomic transaction. A crash
between step 6 and step 8 leaves funds debited but the ticket not reflecting
"funded". Recovery: `post_bounty` called again produces the same `bounty_id`,
hits the `attribute_not_exists(pk)` guard on the escrow Put (item b), treats it
as an idempotent success, and immediately calls this `update_item` to converge
the ticket state. The escrow record's presence is the authoritative signal that
funds were taken.

**Step 9 — Audit event**

```python
from app.services.alerts import audit_event
audit_event("bounty_posted", poster_sub, request,
            ticket_id=ticket_id, bounty_id=bounty_id, amount_cents=amount_cents)
```

Best-effort; wrapped in `try/except` so an alert write failure does not roll
back the escrow.

**Step 10 — Return**

```python
return store.get_ticket(ticket_id) or {}
```

### Edge cases and invariants

**Double-post / replay:** Same ticket posted twice. Second call hits
`attribute_not_exists(pk)` on the escrow Put → `TransactionCanceledException`
with reason index 1 being `ConditionalCheckFailed` → 409 / idempotent return of
existing ticket. Wallet is debited exactly once.

**Insufficient balance:** `wallet_balance_cents >= :amount` fails on item (a) →
`TransactionCanceledException`, reason index 0 → HTTP 402. Nothing written.

**No wallet row at all:** The wallet Update requires an existing row
(`wallet_balance_cents >= :amount` with no `if_not_exists`). If the row is
absent, DDB raises `ConditionalCheckFailed`. This is the correct behavior: a
poster with no wallet has zero balance, so 402 is the right response.

**Concurrent posts (race):** Two simultaneous `post_bounty` calls for the same
ticket produce the same `bounty_id`. The transaction that executes second loses
on `attribute_not_exists(pk)` → 409. The winner is the first transaction to
commit. Exactly one debit occurs.

**Ticket status changes between load and transaction:** `post_bounty` reads the
ticket at step 2 (status check) and the transaction fires at step 6. If the
ticket transitions between steps 2 and 6, the escrow record is still created
correctly. The business invariant ("bounty only on open tickets") is best-effort
at service level and enforced at step 2. A more strict design could add the
ticket's `bounty_status` as a fourth transaction item (conditional check on the
ticket table), but since the tickets and billing tables are separate DynamoDB
tables, `transact_write_items` cannot span them. Step 2's pre-check is the
practical guard.

**Cancelled-then-repost:** `bounty_status="cancelled"` is allowed at step 2.
This means a poster who cancelled a previous bounty (and was fully refunded) can
post a new bounty on the same ticket. Because `_bounty_id` is derived purely from
`ticket_id`, the same `bounty_id` would be generated. The old escrow row (at
`BOUNTY#{bounty_id}/ESCROW`) will still exist with `status="refunded"`, which
will cause the idempotent guard (`attribute_not_exists(pk)`) to fire on the new
post attempt.

**Resolution:** When `bounty_status="cancelled"` is detected at step 2, a
variant bounty_id must be produced to avoid the stale-row collision:

```python
repost_count = ticket.get("bounty_repost_count", 0) + 1
bounty_id = _bounty_id(f"{ticket_id}#repost#{repost_count}")
```

`bounty_repost_count` is an integer attribute on the ticket META row, incremented
at step 8 when the new bounty is funded. The zero case (first post) uses the
original `_bounty_id(ticket_id)` formula unchanged (backward compatible).

**Payout hold seconds:** `S.ticket_bounty_payout_hold_seconds` (default 0,
TBT-001) is not used in TBT-003. It applies at approval time (TBT-006) as a
minimum time between escrow creation and release.

**Fee:** `S.ticket_bounty_fee_bps` (default 0, Open Decision D1) is not applied
at hold time. The full `amount_cents` is debited from the poster. Fee is
calculated and deducted only at payout time (TBT-006), so the escrow amount
always equals what the poster paid.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 parity

There is no `S.dev_mode` branch anywhere in `ticket_bounties.py`. The same code
path runs against:
- DynamoDB Local (port 8001) in dev, populated by moto when running tests.
- Real AWS DynamoDB in production.

The `_transact_client()` helper derives its endpoint and credentials from
`T.billing.meta.client` at call time (`group_treasury.py:716-740` precedent),
ensuring local vs. remote is determined entirely by the environment's
`DDB_ENDPOINT_URL` setting.

### Idempotency

Three layers of idempotency:

1. **Deterministic bounty_id** — same `ticket_id` always produces the same
   `bounty_id` (for the first post). No random component means retries produce
   the same key.
2. **`attribute_not_exists(pk)` on the escrow Put** — only one escrow row per
   `bounty_id` can ever exist. A second commit attempt for the same `bounty_id`
   will fail the transaction; the service returns the existing ticket state (409
   with idempotent body).
3. **`attribute_not_exists(sk)` on the ledger Put** — the ledger entry's `sk`
   includes a `ulidish()` component which is computed before the transaction is
   built. Since the same `entry_id` is pre-computed for a given call invocation,
   replays within a single request lifetime are safe.

For end-to-end client-level idempotency: a client that gets a network timeout
should simply retry `post_bounty`. The worst outcome is a 409 indicating the
bounty was already funded.

### Security

- **Ownership check:** Only the ticket's `owner_sub` may call `post_bounty`.
  Verified at step 2 before any money moves (403 on mismatch).
- **Fraud gate:** `_fraud_gate` (`billing.py:118-175`) runs before any DynamoDB
  writes. Frozen accounts are blocked unconditionally. Fraud-blocked accounts
  are blocked when `enforce_block=True`.
- **Wallet isolation:** The poster's wallet is the only billing row modified. No
  other user's balance is touched by `post_bounty`.
- **No provider SDK calls:** `post_bounty` is a pure DynamoDB operation. It does
  not invoke Stripe, PayPal, or CCBill. Funds come from the poster's pre-loaded
  wallet balance (Open Decision D2 — wallet-only for v1).

### Money-safety invariants

1. **Poster debited exactly once:** The `attribute_not_exists(pk)` guard on the
   escrow row makes double-debit physically impossible within a single
   `transact_write_items` call.
2. **Atomicity:** Wallet debit and escrow creation happen in one
   `transact_write_items` call. A partial failure leaves either both committed
   or neither.
3. **Escrow as authoritative source:** The escrow row at `BOUNTY#{bounty_id}/ESCROW`
   with `status="held"` is the single authoritative record that funds are locked.
   All later operations (approve, cancel) gate on this row's status.
4. **No double-charge at payout:** TBT-006 credits the assignee directly via a
   new ledger entry of type `"credit"`. It does NOT call `write_tip_ledger`
   (which would debit the poster again). The poster's debit ledger entry from
   TBT-003 is settled (not reversed) at payout, reflecting that the money was
   legitimately spent.

## 8. Backward Compatibility & Migration

### Flag off

When `TICKET_BOUNTIES_ENABLED=false` (the default), `_require_bounties_enabled()`
raises HTTP 404 before any DynamoDB access. The tickets table, billing table, and
all existing endpoints are completely unchanged:

- `_TICKET_STATUSES`, `_STATUS_TRANSITIONS` (`tickets.py:15-40`) — not touched
  by TBT-003.
- `create_ticket`, `get_ticket`, `update_status`, `assign_ticket`
  (`tickets.py:411, 522, 913, 807`) — not touched.
- `TicketOut` (`app/routers/tickets.py:58-73`) — additive optional fields added
  by TBT-002 are absent from existing rows; they serialize as `None` or are
  dropped. **Note:** `TicketOut` lives in the router module, not the service
  module; throughout this spec other `tickets.py` references mean
  `app/services/tickets.py`.
- The billing table gains new row types (`BOUNTY#.../ESCROW`, new ledger entries
  with `reason="bounty_escrow"`) only when bounties are enabled and a bounty is
  posted. No existing billing rows are mutated.

### Schema migration

No DynamoDB table or GSI changes are required in TBT-003 itself. The ByBounty
GSI is declared in TBT-002. The escrow row type is new but uses the existing
`T.billing` table (pk/sk schema). In dev, `just restart` recreates all tables;
in production, no `UpdateTable` is needed for TBT-003 (the GSI was already
applied for TBT-002).

### Forward compatibility

The `bounty_repost_count` attribute written at step 8 (re-post after cancel) is
new but optional. Existing code that reads the ticket dict ignores unknown keys.
`TicketOut` will add it as an optional field in TBT-002's extension.

## 10. Open Questions / Assumptions

**D1 (fee, default 0%):** This spec assumes `ticket_bounty_fee_bps=0` for the
hold operation. The full `amount_cents` is debited at post time. Fee math at
payout is TBT-006's responsibility.

**D2 (wallet-only funding):** `post_bounty` only accepts wallet balance. There
is no card-charge path. Adding a card path would require Stripe/PayPal integration
and 3DS handling, deferred to v2.

**D3 (any owner):** Any ticket owner may post a bounty, gated only by min/max and
fraud checks. No additional role or KYC tier check is applied in v1.

**D4 (manual unclaim):** Not applicable to TBT-003. The escrow holds funds
indefinitely until TBT-006 (approve) or TBT-007 (cancel) releases them.

**Assumption — ticket and billing tables are separate:** `transact_write_items`
cannot span two DynamoDB tables. The wallet debit + escrow write are both on
`T.billing` (atomic). The ticket META update is a separate non-transactional
`update_item` on `T.tickets`. Recovery on crash between the two is handled by
the idempotent re-post path.

**Assumption — `_fraud_gate` importable from `billing.py`:** The function is
module-level in `app/routers/billing.py` (`billing.py:118`). A lazy import
inside `post_bounty` (`from app.routers.billing import _fraud_gate`) avoids
circular dependencies since `ticket_bounties.py` is a service module that
`billing.py` does not import.

**Open — maximum repost count:** The `bounty_repost_count` scheme allows
unlimited cancels and reposts. A product decision may want to cap this (e.g., 3
reposts) to prevent abuse. For v1, no cap is enforced.

**Open — currency support:** Only `"usd"` is supported (validated at step 3).
Multi-currency is a future concern.
