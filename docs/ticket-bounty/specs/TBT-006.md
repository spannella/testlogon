# TBT-006 — Submit-for-approval + admin approve → release escrow → assignee

**Type:** Feature | **Priority:** P0 | **Estimate:** 2 days
**Milestone:** Milestone 1 — Escrow & bounty foundation
**Dependencies:** TBT-003 (escrow row written), TBT-005 (claim/unclaim state established)

---

## 1. Summary & Goal

TBT-006 adds the two-step resolution path for a ticket bounty: a claimant marks
their work done ("submit for approval"), which gates the ticket in a
`pending_approval` state until an admin reviews and either approves or rejects.
On approval the escrowed funds are released: a credit entry is written to the
assignee's billing ledger (making the net amount immediately withdrawable via
the existing `get_available_balance` payout pathway), the escrow record is
settled, and the ticket transitions to the `paid_out` terminal state. On
rejection the ticket returns to `in_progress`/`claimed` so the claimant can
continue working.

The poster is never charged again. The full amount leaves the poster's wallet
exactly once, at escrow time (TBT-003). Release is a credit-only operation on
the assignee's ledger; `write_tip_ledger` is explicitly not used here.

## 2. Context & Current State

### Ticket status machine

`app/services/tickets.py:15-40` defines `_TICKET_STATUSES` (a tuple of
strings) and `_STATUS_TRANSITIONS` (a dict mapping each status to the tuple of
statuses it may advance to). Today's set: `open`, `in_progress`,
`waiting_on_user`, `done`, `code_complete`, `qa_in_progress`, `qa_approved`,
`blocked`, `deploying`, `deployed`, `investigating`, `analyzing`,
`tickets_created`. The statuses `pending_approval`, `paid_out`, and `cancelled`
do not yet exist.

All status mutations go through `TicketStore._conditional_update_meta` (`tickets.py:723`),
which issues a `version`-gated DynamoDB `update_item` — an optimistic-lock
single-writer pattern. `_apply_header_update_once` (`tickets.py:792`) wraps it with a
read-then-write that raises `TicketStateError` (code `"ticket_update_conflict"`)
on `ConditionalCheckFailedException` — it does **not** retry automatically;
callers must implement their own retry loop if needed.

The `TicketStore.update_status` method (`tickets.py:913`) validates against
`_STATUS_TRANSITIONS` and raises `TicketStateError` on invalid transitions. The
generic status endpoint in `app/routers/tickets.py` calls this method;
`pending_approval` and `paid_out` must never be reachable through that generic
path.

### Escrow record (written by TBT-003)

`BOUNTY#{bounty_id}/ESCROW` in `T.billing` (the "billing" DynamoDB table,

(default **604800 — 7 days**, not 0; `settings.py:1651`) — only credits where
`ts + hold_period <= now_ts()` count as "available". A new `type="credit"` ledger
entry on the assignee's partition with `ts` at approval time will be **held** for
7 days by default before the assignee can withdraw it (unless `PAYOUT_HOLD_PERIOD_SECONDS`
is overridden). Section 5.6 must be updated accordingly.

## 3. Data Model

### 3.1 New fields on the ticket META row (`T.tickets`)

TBT-002 establishes these additive optional fields on `pk=TICKET#{ticket_id}`,
`sk=META`. TBT-006 reads and writes the following subset:

| Attribute | Type | Written by | Meaning |
|---|---|---|---|
| `bounty_status` | S | TBT-003/005/006 | `funded` → `claimed` → `submitted` → `paid_out` |
| `bounty_id` | S | TBT-003 | `sha256("bounty:{ticket_id}")[:24]` |
| `bounty_amount_cents` | N | TBT-003 | Original escrowed amount |
| `claimed_by_sub` | S | TBT-005 | Assignee (= `assigned_to_sub`) |
| `bounty_submitted_at` | N | TBT-006 `submit_bounty` | Unix timestamp of submission |
| `bounty_paid_at` | N | TBT-006 `approve_bounty` | Unix timestamp of payout |

`bounty_status` progression specific to TBT-006:
- `claimed` → `submitted` (by claimant, via `submit_bounty`)
- `submitted` → `paid_out` (by admin, via `approve_bounty`)
- `submitted` → `claimed` (by admin, via `reject_bounty`)

### 3.2 Escrow record (`T.billing`, `pk=BOUNTY#{bounty_id}`, `sk=ESCROW`)

Written by TBT-003. TBT-006 updates `status` and adds release/reject fields:

**On `approve_bounty`:**
```
status           = "released"
released_to      = assignee_sub
released_by      = admin_sub
released_at      = now_ts()
payout_ledger_sk = <assignee credit ledger sk>
fee_cents        = fee (0 by default, see D1)
net_cents        = net payout amount
```
Update uses `ConditionExpression="escrow_status = :held"` (attribute alias for
`status`) to guard idempotency — a second `approve_bounty` call finds
`status="released"` and returns the existing ticket without re-crediting.

**On `reject_bounty`:** no escrow row change; escrow stays `status="held"`.

### 3.3 New assignee credit ledger row (`T.billing`, `pk=USER#{assignee_sub}`)

Written by `approve_bounty` using `new_ledger_entry`:
```python
sk, item = new_ledger_entry(
    key_name="pk",
    key_value=f"USER#{assignee_sub}",
    entry_type="credit",
    amount_cents=net_cents,
    state="settled",
    reason="bounty_payout",
    meta={
        "bounty_id": bounty_id,
        "ticket_id": ticket_id,
        "fee_cents": fee_cents,
        "approved_by": admin_sub,
    },
)
```
`state="settled"` ensures `get_available_balance` includes this entry (it is not
filtered out, unlike `state="reversed"` entries which are excluded). However, the
**hold period still applies**: `get_available_balance` (`creator_payouts.py:129`) tests
`ts + hold_period <= now` for every credit regardless of `state`. With the default
`S.payout_hold_period_seconds = 604800` (7 days), the credit will not count toward
`available_cents` until 7 days after `approve_bounty` runs. Operators can set
`PAYOUT_HOLD_PERIOD_SECONDS=0` to remove the hold. See §5.6 for the full discussion.

### 3.4 Poster's audit ledger row (existing, mutated)

The escrow debit entry written by TBT-003 has `state="pending"`. On approval:
```python
settle_or_reverse_ledger(T.billing, "pk", poster_pk, escrow_row["ledger_sk"], "settled_released")
```
The state `"settled_released"` is a custom terminal state meaning "held funds
disbursed to assignee" — distinct from `"settled"` (normal payment), `"reversed"`
(refund), and existing states. It is informational only; `get_available_balance`
filters on `state != "reversed"` so this entry (a debit) is not summed there.

### 3.5 GSI notes

No new GSIs are introduced by TBT-006. The `ByBounty` sparse GSI
(`gsi_bounty_pk` / `gsi_bounty_sk`) established in TBT-002 has its partition
key cleared when `bounty_status` transitions out of `funded` (done in TBT-005
at claim time). By `submitted` state the ticket is already off the open board.
`attr_types={"gsi_bounty_sk": "N"}` must be declared in
`scripts/local-ddb-init.py` for that GSI (established by TBT-002 — no change
required in TBT-006 itself).

## 4. API / Service Design

### 4.1 Service layer — `app/services/ticket_bounties.py`

This file is introduced by TBT-003; TBT-006 adds three functions to it.

---

#### `submit_bounty(ticket_id: str, claimer_sub: str) -> dict`

```python
def submit_bounty(ticket_id: str, claimer_sub: str) -> dict[str, Any]:
```

1. `_require_bounties_enabled()` — raises HTTP 404 if `S.ticket_bounties_enabled` is False.
2. Load ticket from `STORE.get_ticket(ticket_id)` — 404 if missing.
3. Assert `ticket["bounty_status"] == "claimed"` — 409 `bounty_wrong_state` otherwise.
4. Assert `ticket["claimed_by_sub"] == claimer_sub` — 403 `not_claimant` otherwise.
5. Update ticket META row via `STORE._apply_header_update_once` with additional fields
   `bounty_status="submitted"`, `bounty_submitted_at=now_ts()`, and ticket
   `status="pending_approval"`. The `pending_approval` status must be added to
   `_TICKET_STATUSES` in `tickets.py` (TBT-004 work, but this function depends on it).
6. Write an activity row: `entity_type="ticket_activity"`, `activity_type="bounty_submitted"`,
   `actor_sub=claimer_sub`.
7. Return the updated ticket dict.

**Note:** `pending_approval` is not reachable via the generic `update_status`
endpoint. Only this function writes it. The `_BOUNTY_TRANSITIONS` guard (TBT-004)
ensures the generic path cannot override it.

---

#### `approve_bounty(ticket_id: str, admin_sub: str, request: Request) -> dict`

```python
async def approve_bounty(
    ticket_id: str,
    admin_sub: str,
    request: Request,
) -> dict[str, Any]:
```

**Preconditions (all raise before any money moves):**
1. `_require_bounties_enabled()`.
2. Load ticket — 404 if missing.
3. Assert `ticket["bounty_status"] == "submitted"` — 409 `bounty_wrong_state`.
4. Load escrow row: `T.billing.get_item(Key={"pk": f"BOUNTY#{bounty_id}", "sk": "ESCROW"})` — 409 if missing.
5. Assert `escrow["status"] == "held"` — if `"released"`, this is a replay; return the existing ticket (idempotent no-op).
6. Resolve assignee: `assignee_sub = ticket["claimed_by_sub"]`. If None → 409 `no_claimant`.

**Fee computation (Open Decision D1 — default 0%):**
```python
fee_bps = S.ticket_bounty_fee_bps  # default 0
amount_cents = int(escrow["amount_cents"])
fee_cents = amount_cents * fee_bps // 10000
net_cents = amount_cents - fee_cents
```
With default `fee_bps=0`: `fee_cents=0`, `net_cents=amount_cents`.

**Atomic release — `transact_write_items` (5 items, well within the 25-item cap):**

Using the same low-level client pattern as `group_treasury._batch_transact`
(`:743-751`), call `transact_write_items` with:

1. **Update escrow row** (`ConditionExpression="escrow_status = :held"` guard):
   SET `status="released"`, `released_to`, `released_by`, `released_at`,
   `payout_ledger_sk`, `fee_cents`, `net_cents`.

2. **Credit assignee wallet** (unconditional deposit):
   `update_item` on `pk=USER#{assignee_sub}`, `sk=WALLET`,
   `wallet_balance_cents = if_not_exists(..., 0) + net_cents`.
   The assignee's wallet need not pre-exist; `if_not_exists` initialises it.

3. **Write assignee credit ledger entry**:
   `put_item` with the item from `new_ledger_entry(entry_type="credit",
   state="settled", reason="bounty_payout", ...)`.

4. **Settle the poster's escrow audit entry** (state `"pending"` → `"settled_released"`):
   `update_item` on `pk=USER#{poster_sub}`, `sk=escrow["ledger_sk"]`,
   SET `state = "settled_released"`.

5. **Update ticket META** (`ConditionExpression="#version = :v"` optimistic lock):
   SET `bounty_status="paid_out"`, `bounty_paid_at=ts`, `status="paid_out"`,
   `updated_at=ts`, version increment.

If the `transact_write_items` call raises `TransactionCanceledException` with
`CONDITIONAL_CHECK_FAILED` on item 1 (escrow guard), re-read the escrow row: if
it is already `"released"`, return the existing ticket (idempotent replay). All
other cancellation reasons are re-raised as HTTP 500.

**Post-transaction (best-effort, outside the transaction):**
- Write an activity row: `activity_type="bounty_approved"`, `actor_sub=admin_sub`.
- If `fee_cents > 0`: write a platform fee ledger entry (same convention as tip-fee
  split — `new_ledger_entry` on `pk="PLATFORM#ESCROW"`, `entry_type="credit"`,
  `reason="bounty_fee"`).
- `audit_event("bounty_released", admin_sub, request, ticket_id=ticket_id, bounty_id=bounty_id, net_cents=net_cents)`.
- Send an in-app notification to the assignee: `alerts.send_alert(assignee_sub, event="bounty_awarded", ...)`.

Return the updated ticket dict (re-read via `STORE.get_ticket`).

---

#### `reject_bounty(ticket_id: str, admin_sub: str, reason: str) -> dict`

```python
def reject_bounty(
    ticket_id: str,
    admin_sub: str,
    reason: str,
) -> dict[str, Any]:
```

1. `_require_bounties_enabled()`.
2. Load ticket — 404 if missing.
3. Assert `ticket["bounty_status"] == "submitted"` — 409 `bounty_wrong_state`.
4. No money moves. Escrow stays `status="held"`.
5. Update ticket META: `bounty_status="claimed"`, `status="in_progress"`, `updated_at=ts`, version increment. Use `STORE._apply_header_update_once` with these fields; the bounty-specific fields are passed via a second `update_item` call that also writes `bounty_reject_reason` and `bounty_rejected_at`.
6. Write activity row: `activity_type="bounty_rejected"`, `actor_sub=admin_sub`, with `reason` in metadata.
7. `audit_event("bounty_rejected", admin_sub, None, ticket_id=ticket_id, reason=reason)`.
8. Send notification to the claimant: `send_alert(claimant_sub, event="bounty_rejected", ...)`.
9. Return updated ticket.

## 5. Detailed Behavior & Edge Cases

### 5.1 State transition summary for TBT-006

```
(TBT-005) claimed  --[submit_bounty by claimant]--> submitted
                                                        |
                                               +--------+--------+
                                               |                 |
                              [approve_bounty]              [reject_bounty]
                                    v                            v
                               paid_out (terminal)       in_progress / claimed
```

The ticket's `status` field (the plain ticket lifecycle, separate from
`bounty_status`) mirrors the bounty state:
- `submit_bounty` → ticket `status` = `"pending_approval"`
- `approve_bounty` → ticket `status` = `"paid_out"`
- `reject_bounty` → ticket `status` = `"in_progress"` (claimant resumes work)

Neither `pending_approval` nor `paid_out` is reachable via the generic
`update_status` endpoint. They are added to `_TICKET_STATUSES` (so the
validation doesn't reject them), but are **absent** from `_STATUS_TRANSITIONS`
(so no generic transition can reach them). The bounty-specific endpoints are the
sole writers.

### 5.2 Error → HTTP code mapping

| Error condition | HTTP | `code` in response |
|---|---|---|
| Feature flag off | 404 | `feature_disabled` |
| Ticket not found | 404 | `ticket_not_found` |
| `bounty_status` not in expected state | 409 | `bounty_wrong_state` |
| Escrow row missing | 409 | `escrow_not_found` |
| `claimed_by_sub` != caller (submit) | 403 | `not_claimant` |
| Non-admin calling approve/reject | 403 | `forbidden` |
| No claimant on approval | 409 | `no_claimant` |
| DDB optimistic lock race | 409 | `version_conflict` (retry) |
| `TransactionCanceledException` (non-idempotent) | 500 | `escrow_release_failed` |

### 5.3 Money invariants

- **Poster is debited exactly once.** The wallet debit happens in TBT-003's atomic
  `transact_write_items`. `approve_bounty` never touches the poster's wallet
  balance — it only updates the state of the escrow audit ledger entry.
- **Assignee is credited exactly once.** The `transact_write_items` in
  `approve_bounty` uses the escrow row's `ConditionExpression="status = :held"`
  as the idempotency gate. If the transaction commits, the escrow transitions to
  `"released"` and the assignee credit is written atomically. A retry/duplicate
  call finds `status="released"` (via item 1 failing) and short-circuits without
  writing a second credit.
- **No partial release.** Because all five mutations are inside a single
  `transact_write_items` call, either all succeed or none do. The wallet credit,
  ledger entry, and escrow status flip are atomic.
- **Net amount consistency.** `net_cents = amount_cents - fee_cents` where
  `fee_cents = amount_cents * ticket_bounty_fee_bps // 10000`. With the default
  `fee_bps=0`, `net_cents == amount_cents` exactly. Integer arithmetic is used
  throughout; no floating-point.

### 5.4 Race conditions

- **Double-approve race:** Two concurrent admin `approve_bounty` requests — the
  first `transact_write_items` wins (escrow `status="held"` condition); the
  second gets `TransactionCanceledException` due to the condition failure on item 1.
  The handler re-reads the escrow row, finds `status="released"`, and returns the
  existing ticket without error.
- **Approve while claimant is re-submitting:** If a concurrent `submit_bounty`
  is in flight while `approve_bounty` runs, the ticket version optimistic lock
  (item 5 of the transaction) prevents a stale read from succeeding. One will win;
  the other gets `ConditionalCheckFailed` and must retry.
- **Admin approves after another admin rejects-then-claimant-resubmits:** The
  `bounty_status != "submitted"` precondition check prevents approving a ticket
  not in `submitted` state. The sequence reject → claimant-work → resubmit
  returns `bounty_status` to `"submitted"`, at which point approval is valid again.

### 5.5 `reject_bounty` escrow state

Rejection does not move money. The escrow row stays at `status="held"`. The claimant
resumes work (`bounty_status="claimed"`, ticket `status="in_progress"`) and may
resubmit. Only an explicit `cancel_bounty` (TBT-007) refunds the escrow and returns
funds to the poster.

### 5.6 Payout visibility

The `net_cents` credit with `state="settled"` and `type="credit"` is included in
`creator_payouts.get_available_balance` immediately (`:84-138`): the query
filters on `type="credit"` and `state != "reversed"` with `amount_cents > 0`.
The assignee can initiate a payout request for the bounty amount subject to
`S.payout_hold_period_seconds` (default **604800 s = 7 days**; `settings.py:1651`).
With the default hold period the credit is only "available" after 7 days; setting
`PAYOUT_HOLD_PERIOD_SECONDS=0` in the deployment removes the hold.

## 6. Feature Flag & Config

All functions in `ticket_bounties.py` begin with `_require_bounties_enabled()`,
which is defined in the same file as:

```python
def _require_bounties_enabled() -> None:
    if not S.ticket_bounties_enabled:
        raise HTTPException(status_code=404, detail={"code": "feature_disabled",
            "message": "Ticket bounties are not enabled."})
```

Settings (`app/core/settings.py`):

| Setting attribute | Env var | Default | Notes |
|---|---|---|---|
| `ticket_bounties_enabled` | `TICKET_BOUNTIES_ENABLED` | `False` | Master gate; all endpoints 404 when off |
| `ticket_bounty_fee_bps` | `TICKET_BOUNTY_FEE_BPS` | `0` | Basis points; 0 = full payout, no platform fee (D1) |
| `ticket_bounty_min_cents` | `TICKET_BOUNTY_MIN_CENTS` | `100` | Minimum bounty ($1.00) |
| `ticket_bounty_max_cents` | `TICKET_BOUNTY_MAX_CENTS` | `10_000_00` | Maximum bounty ($10,000) |

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

**Dev/prod parity:** `ticket_bounties.py` contains no `if S.dev_mode` branches.
The `transact_write_items` call must follow `group_treasury._transact_client`
(`group_treasury.py:716-740`) exactly — build a fresh `boto3.client("dynamodb")`
from `T.billing.meta.client`'s endpoint/region/credentials and pass raw
`AttributeValue` maps. Do **not** call `T.billing.meta.client.transact_write_items`
directly (the resource client carries a type serialiser that corrupts already-
serialised AttributeValue maps). The `T.billing` table is the same "billing"
DynamoDB table in both environments (`settings.py:348`).

**Idempotency:**
- `approve_bounty`: escrow row `ConditionExpression` on `status="held"` is the
  idempotency gate. A second call that finds `status="released"` returns the
  current ticket without writing any ledger entries. The assignee credit ledger
  entry is written once, inside the same atomic transaction.
- `submit_bounty`: the claimant can only submit when `bounty_status="claimed"`;
  after submission it is `"submitted"`. A duplicate call returns 409
  `bounty_wrong_state`. The optimistic version lock prevents a double-write race.
- `reject_bounty`: idempotent via the precondition check (`bounty_status=="submitted"`
  required); a duplicate rejection on a ticket already back to `"claimed"` returns
  409.

**Security:**
- `submit_bounty` verifies `claimed_by_sub == caller_sub` before proceeding —
  a different user cannot submit on another user's claimed ticket.
- `approve_bounty` and `reject_bounty` gate on `_is_admin_actor(request, user)`,
  which requires `Role.ADMIN` or `Role.ROOT` or the `tickets:admin` API key scope
  (`:224-225`). Regular users cannot approve or reject.
- The `bounty_id` embedded in the escrow key is computed as
  `sha256("bounty:{ticket_id}")[:24]` — deterministic and non-guessable relative
  to arbitrary strings. The escrow row is keyed under `BOUNTY#<bounty_id>` in
  `T.billing`, inaccessible to end-users through any public API.

**Money-safety:**
- The 5-item `transact_write_items` is atomic — partial escrow release is
  impossible.
- `write_tip_ledger` is never called; the poster is debited only once at TBT-003
  escrow time.
- If `apply_wallet_delta` for the assignee credit is in the transaction and it
  fails for any reason, the entire transaction rolls back — no funds leak.
- Platform fee (if `fee_bps > 0`) is recorded as a best-effort `new_ledger_entry`
  on `pk="PLATFORM#ESCROW"` outside the main transaction, so a fee-write failure
  does not block the payout. This is acceptable because the fee amount at default
  is 0 and at non-zero rates the escrow release (the critical money-safety path)
  has already committed.

## 8. Backward Compatibility & Migration

With `TICKET_BOUNTIES_ENABLED=0` (the default):

- All three new endpoints (`/bounty/submit`, `/bounty/approve`, `/bounty/reject`)
  return HTTP 404 immediately via `_require_bounties_enabled()`. No ticket data
  is read or written.
- The new statuses `pending_approval` and `paid_out` are added to
  `_TICKET_STATUSES` (so the validation tuple accepts them), but no ticket will
  ever have these statuses while the flag is off. Existing tickets in `open`,
  `in_progress`, `done`, etc. are completely unaffected.
- `TicketOut` gains nullable optional fields (`bounty_amount_cents`, etc.) with
  default `None`. The current `TicketOut` model (`tickets.py:58-73`) has no
  `model_config` set and does not use `exclude_none=True`. Pydantic v2 includes
  `None` fields in JSON output by default unless the model uses
  `model_config = ConfigDict(exclude_none=True)`. Implementors should add
  `model_config = ConfigDict(exclude_none=True)` to `TicketOut` or wrap the
  new fields in `Optional` with `Field(default=None, exclude=None)` to avoid
  polluting existing API responses with null fields.
- `_STATUS_TRANSITIONS` (`:30-40`) is unchanged — no new entries are added. The
  new bounty statuses are reachable only through dedicated service functions.
- The `T.tickets` and `T.billing` DynamoDB tables require no schema migration.
  New attributes are additive; DynamoDB's schema-less partition model means
  existing rows gain no new attributes until a bounty-specific write touches them.
  The `ByBounty` GSI (TBT-002) is sparse — non-bounty tickets never appear in it
  regardless.

**No DynamoDB table creation is needed for TBT-006 itself.** The `T.billing` and
`T.tickets` tables already exist. The `ByBounty` GSI on `T.tickets` is
established in TBT-002.

## 10. Open Questions / Assumptions

**D1 — Platform fee (default 0%).** This spec assumes `ticket_bounty_fee_bps=0`
throughout. The fee arithmetic is implemented and tested at non-zero values
(`test_fee_nonzero`), but the default is 0% — the poster pays X and the assignee
earns X. Changing the fee requires only an env-var change, no code change.

**D2 — Wallet-only funding.** Approval releases funds from the wallet-backed
escrow. There is no fresh card charge at approval time. This follows the
wallet-only recommendation in the open decisions.

**D3 — Any ticket owner may post a bounty.** The approve/reject endpoints in
TBT-006 do not restrict which user owns the ticket — any user who owns a ticket
(and who posted the bounty at TBT-003 time) may see their bounty paid out on
admin approval.

**D4 — Manual unclaim only.** The `reject_bounty` path returns the ticket to
`in_progress`/`claimed` without forcing the claimant off the ticket. The
claimant may voluntarily call `unclaim_bounty` (TBT-005) to release the claim.
There is no auto-refund timer; idle-sweep is a post-v1 follow-up.

**Assumption:** `pending_approval` and `paid_out` are added to `_TICKET_STATUSES`
by TBT-004 before TBT-006 ships. TBT-006 depends on `pending_approval` being a
valid value so `_conditional_update_meta` does not reject it.

**Assumption:** The `ByBounty` sparse GSI and bounty fields on the META row are
established by TBT-002 before TBT-006 runs in production.

**Assumption:** The `transact_write_items` call in `approve_bounty` does not
exceed the 25-item DynamoDB cap. The transaction has exactly 5 items (escrow
update, assignee wallet credit, assignee ledger entry, poster ledger state
update, ticket META update). This is well within the limit.

**Open:** Should `reject_bounty` notify the poster (ticket owner) as well as the
claimant? The current design only notifies the claimant. The poster is the
escrow funder and may want visibility, particularly if the rejection is for
quality reasons that imply the bounty will expire unclaimed.
