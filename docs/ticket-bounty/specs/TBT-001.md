# TBT-001 — Feature flag, settings & escrow table decision

**Milestone:** 1 — Escrow & bounty foundation
**Type:** Chore | **Priority:** P0 | **Estimate:** 1 day
**Depends on:** none (this is the foundation ticket)
**Required by:** TBT-002..TBT-011, TKA-001 (settings/flag pattern), and every
downstream bounty/attachment service and router.

---

## 1. Summary & Goal

This ticket lays the foundation for the entire Ticket Bounties feature
(`TBT`/`TKA`). It is deliberately small and contains **no money-moving code and
no endpoints** — its only job is to establish three things the rest of the
milestone depends on:

1. **A master feature flag** `S.ticket_bounties_enabled` (env
   `TICKET_BOUNTIES_ENABLED`, default **off**) plus four bounded settings that
   the escrow service will read: `ticket_bounty_min_cents` (default `100`),
   `ticket_bounty_max_cents` (default `100_000_00` = $100,000),
   `ticket_bounty_fee_bps` (default **0** — Open Decision D1), and
   `ticket_bounty_payout_hold_seconds` (default `0`).
2. **The escrow record's storage home.** The decision recorded here is to
   **reuse the existing `T.billing` table** (single-table) with a sentinel row
   keyed `pk=BOUNTY#{bounty_id}`, `sk="ESCROW"`. The escrow record is co-located
   with the per-user ledger entries (`pk=USER#{sub}`, `sk=LEDGER#…`) so refund,
   release, and audit queries all stay on one table with no new table and no new
   GSI.
3. **Two gate helpers** `_bounties_enabled()` / `_require_bounties_enabled()`
   that mirror the proven `inventory.py` pattern, so every downstream endpoint
   returns `404` when the flag is off.

With the flag off (the default), this ticket is inert: the new settings parse at
import but are read by nobody, there are no DynamoDB schema changes, and the
ticket + billing systems behave byte-for-byte as today. The goal is to make
TBT-002..011 a series of additive, independently reviewable changes behind one
switch.

## 2. Context & Current State

### 2.1 The Settings dataclass (frozen) — `app/core/settings.py`

The application configuration is a single frozen dataclass instantiated once as
the module singleton `S` (`app/core/settings.py:6-7`, `@dataclass(frozen=True)` /
`class Settings:`). Because it is **frozen**, fields cannot be mutated at runtime;
tests override fields via `object.__setattr__(S, "field", value)`. Every field is
a class-level default read from the environment at import time.

**Boolean flag precedent** (mirror for `ticket_bounties_enabled`):

```
# app/core/settings.py:432
ticket_boards_enabled: bool = os.environ.get("TICKET_BOARDS_ENABLED", "false").lower() == "true"
```

A second common idiom is `os.environ.get(...) not in ("0", "false", "False")`
(e.g. `broadcast_tipping_enabled`, `:557`). For a **default-OFF** flag the
`.lower() == "true"` form is the safer choice (anything but the literal `true` is
off) and matches the sibling `ticket_boards_enabled`, so TBT-001 mirrors that line.

**Integer `_cents` precedent** (mirror for the `_cents`/`_bps`/`_seconds` ints):

```
# app/core/settings.py:558-559
broadcast_tip_min_cents: int = int(os.environ.get("BROADCAST_TIP_MIN_CENTS", "100"))
broadcast_tip_max_cents: int = int(os.environ.get("BROADCAST_TIP_MAX_CENTS", "100000"))
```

**Integer `_seconds` precedent**: `session_challenge_ttl_seconds: int =
int(os.environ.get("SESSION_CHALLENGE_TTL_SECONDS", "300"))` (`:97`). These
precedents cover every shape TBT-001 needs (`bool`, `int` cents/bps/seconds).

### 2.2 The gate-helper pattern — `app/services/inventory.py:50-56`

The inventory service (another additive, flag-gated feature) is the canonical
template:

```python
# app/services/inventory.py:50-56
def _flag_on() -> bool:
    return bool(getattr(S, "inventory_reservations_enabled", False))


def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Inventory reservations are not enabled")
```

Note the defensive `getattr(S, "...", False)` (fail-closed if the attribute is
absent) and the `HTTPException(404)` so a flag-off endpoint is indistinguishable
from a non-existent route. TBT-001 copies this, renaming to `_bounties_enabled` /
`_require_bounties_enabled`.

### 2.3 The billing table and ledger conventions — `app/services/billing_shared.py`

The billing table is reached via the `T.billing` handle:

- `app/core/tables.py:81` — `billing: Any` (the handle is declared on the `T` dataclass)
- `app/core/tables.py:333` — `billing=_safe_table(S.billing_table_name)` (wired from settings)
- `app/core/settings.py:348` — `billing_table_name: str = os.environ.get("BILLING_TABLE_NAME", os.environ.get("DDB_TABLE", "billing"))`

The table's key schema is `pk` (HASH) / `sk` (RANGE) with a single GSI:

```
# scripts/local-ddb-init.py:67-77
TableDef(
    _resolve_table_name(S.billing_table_name, "billing"),
    "pk",
    "sk",
    gsi=[{
        "index_name": "GSI_LEDGER_DATE",
        "partition_key": "ledger_date",
        "sort_key": "sk",
    }],
    attr_types={"ledger_date": "S"},
)
```

The partition is shared across row "kinds": user balance/ledger rows use
`pk=USER#{user_id}` (`billing_shared.py:23-24`, `user_pk()`), payment methods use
`sk=PM#…`, the balance summary uses `sk=BILLING`, and ledger rows use
`sk=LEDGER#{ts}#{entry_id}` (`billing_shared.py:220-221`, `ledger_sk()`).

`new_ledger_entry(...)` (`billing_shared.py:224-259`) builds a ledger item with a
caller-supplied `key_name`/`key_value` (the `pk` attribute name + value),
`sk=ledger_sk(...)`, `type`, `amount_cents`, `state`, `reason`, and — for the GSI
— a denormalized `ledger_date` (`:253`, via `ledger_date_for_ts`, `:10-13`).
`settle_or_reverse_ledger(...)` (`:262-274`) flips a ledger row's `state` via
`update_item`. These are the primitives TBT-003 (escrow), TBT-006 (release), and
TBT-007 (refund) reuse — TBT-001 only proves the sentinel row co-exists cleanly.

## 3. Data Model

### 3.1 The escrow sentinel row (decision, not yet written here)

TBT-001 only **decides and documents** the row shape; the row is first written by
TBT-003's `post_bounty`. The decision is:

| Attribute | Value | Notes |
|---|---|---|
| `pk` | `BOUNTY#{bounty_id}` | Sentinel partition, one per bounty. `bounty_id = sha256(f"bounty:{ticket_id}")[:24]` (deterministic — TBT-003). |
| `sk` | `"ESCROW"` | Fixed literal — exactly one escrow row per bounty partition. |
| `ticket_id` | `str` | Back-reference to the ticket META row. |
| `poster_sub` | `str` | The user whose wallet was debited. |
| `amount_cents` | `int` | Held amount. |
| `currency` | `str` | e.g. `"usd"`. |
| `status` | `"held"` → `"released"` / `"refunded"` | Escrow lifecycle (TBT-006/007). |
| `created_at` | `int` (`now_ts()`) | |
| `ledger_sk` | `str` | The `sk` of the paired audit ledger entry (TBT-003 step 4c). |

Release/refund add `released_to`/`released_by`/`released_at` or
`refunded_at`/`refund_ledger_sk` (TBT-006/007). All are plain top-level
attributes — no nested maps required.

### 3.2 Why `T.billing` and not a new table

1. **Co-location with the ledger.** Every money movement for a bounty is a
   `new_ledger_entry` on `T.billing` keyed `pk=USER#{sub}`. Homing the escrow
   record on the same table means refund/audit reconciliation never joins across
   tables — a single `query` on `pk=BOUNTY#{bounty_id}` reads the escrow row, and
   the paired ledger `sk` it stores points back into the same table.
2. **No new infra.** A new table means a new `TableDef`, a new `T.*` handle, a new
   `*_table_name` setting, and a prod provisioning step. The sentinel row needs
   none of that — the existing `pk`/`sk` schema already accepts it.
3. **Single-table is the house style.** The codebase routinely overloads one
   partition with multiple `sk` kinds (`PM#`, `BILLING`, `LEDGER#` on `T.billing`;
   `META`/`MSG#`/`ACT#` on `T.tickets`). `BOUNTY#…/ESCROW` is the same pattern.

### 3.3 No GSI / no schema change / `attr_types` N/A

The only index on `T.billing` is `GSI_LEDGER_DATE`, keyed on the **string**
`ledger_date` attribute (`scripts/local-ddb-init.py:72-76`). The escrow sentinel
row does **not** set `ledger_date`, so it is **sparse to that GSI** and never
appears in the platform-financial-dashboard date scan (its paired ledger entries
carry `ledger_date` and *do* show up). Because no new GSI and no numeric GSI sort
key are introduced, the `attr_types={"field":"N"}` requirement called out in
CLAUDE.md **does not apply** to TBT-001 — the billing `TableDef` is unchanged. The
bounty board's `BOUNTY#OPEN` sparse index (TBT-002/008) lives on `T.tickets`, not
here, and is out of scope.

## 4. API / Service Design

### 4.1 Settings fields (exact)

Added to the `Settings` dataclass in `app/core/settings.py` (grouped under a
`# Ticket bounties (TBT-001)` comment, placed near the existing ticket settings
around line 432 for discoverability):

```python
# Ticket bounties (TBT-001) — additive, default OFF.
ticket_bounties_enabled: bool = (
    os.environ.get("TICKET_BOUNTIES_ENABLED", "false").lower() == "true"
)
ticket_bounty_min_cents: int = int(os.environ.get("TICKET_BOUNTY_MIN_CENTS", "100"))
ticket_bounty_max_cents: int = int(os.environ.get("TICKET_BOUNTY_MAX_CENTS", "10000000"))
ticket_bounty_fee_bps: int = int(os.environ.get("TICKET_BOUNTY_FEE_BPS", "0"))
ticket_bounty_payout_hold_seconds: int = int(
    os.environ.get("TICKET_BOUNTY_PAYOUT_HOLD_SECONDS", "0")
)
ticket_bounty_max_reposts: int = int(os.environ.get("TICKET_BOUNTY_MAX_REPOSTS", "3"))
```

| Field | Type | Env var | Default | Meaning |
|---|---|---|---|---|
| `ticket_bounties_enabled` | `bool` | `TICKET_BOUNTIES_ENABLED` | `False` | Master switch. Off → all bounty endpoints 404. |
| `ticket_bounty_min_cents` | `int` | `TICKET_BOUNTY_MIN_CENTS` | `100` ($1.00) | Lower bound for a posted bounty. |
| `ticket_bounty_max_cents` | `int` | `TICKET_BOUNTY_MAX_CENTS` | `10_000_000` ($100,000) | Upper bound. |
| `ticket_bounty_fee_bps` | `int` | `TICKET_BOUNTY_FEE_BPS` | `0` | Platform fee in basis points. **0 = no fee** (Open Decision D1): poster pays X, worker earns X. |
| `ticket_bounty_payout_hold_seconds` | `int` | `TICKET_BOUNTY_PAYOUT_HOLD_SECONDS` | `0` | Optional delay before an approved payout settles (reserved for a future hold-period; 0 = immediate). |
| `ticket_bounty_max_reposts` | `int` | `TICKET_BOUNTY_MAX_REPOSTS` | `3` | Max times a poster may cancel-and-repost a bounty on the same ticket (abuse guard; Open Decision D5). TBT-003 enforces it against `bounty_repost_count` (TBT-002). |

> Default literal `"10000000"` equals the ticket's `100_000_00`. Underscore
> grouping is fine in the source default (`"10000000"` is parsed by `int`), but
> the env-var string must be plain digits.

### 4.2 Gate helpers (exact signatures)

These live in the bounty service module `app/services/ticket_bounties.py` (the
module is *created* by TBT-003; TBT-001 may introduce just these two helpers as
the module's first content, or — to keep TBT-001 import-light — place them in
`app/routers/tickets.py` alongside the existing ticket router and re-export. The
recommended home is the service module, matching `inventory.py`):

```python
from fastapi import HTTPException
from app.core.settings import S

def _bounties_enabled() -> bool:
    return bool(getattr(S, "ticket_bounties_enabled", False))

def _require_bounties_enabled() -> None:
    if not _bounties_enabled():
        raise HTTPException(status_code=404, detail="Ticket bounties are not enabled")
```

- `_bounties_enabled() -> bool` — pure read, no side effects; safe to call in
  projection/UI-config paths.
- `_require_bounties_enabled() -> None` — raises `HTTPException(404)` when off;
  every bounty endpoint (TBT-009) calls it as its first statement.

The `404` (not `403`) is deliberate: a disabled feature should be
indistinguishable from a route that does not exist, mirroring
`inventory._require_enabled` (`inventory.py:54-56`).

## 5. Detailed Behavior & Edge Cases

- **Flag off (default) → endpoints 404.** Because every TBT-009 handler calls
  `_require_bounties_enabled()` first, an off flag yields `404` with detail
  `"Ticket bounties are not enabled"` before any auth, ticket lookup, or money
  logic runs. No bounty rows are ever written.
- **Settings validation timing.** The settings themselves are not *validated* at
  import (mirroring every other `int(...)` setting — a malformed env var raises
  `ValueError` at import, which is the existing fail-fast behavior for the whole
  dataclass). The *semantic* min/max validation (`min_cents <= amount <=
  max_cents`) happens in TBT-003's `post_bounty`, not in TBT-001. TBT-001's
  contract is only that the four numbers load with the documented defaults.
- **`min > max` misconfiguration.** TBT-001 does not guard against `MIN_CENTS >
  MAX_CENTS`; TBT-003's amount check would then reject every bounty (a safe,
  closed failure). Documented as an assumption, not enforced.
- **`getattr` fail-closed.** `_bounties_enabled()` uses `getattr(S,
  "ticket_bounties_enabled", False)`, so a stale/partial `S` defaults to OFF.
- **Fee 0 edge.** With `fee_bps=0`, TBT-006's `fee = amount * 0 // 10000 = 0`, so
  `net = amount` and no fee ledger entry is written — the intended D1 default.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

- **SECOPS-007 parity.** There is **no `dev_mode` branch** anywhere in this
  ticket. The gate helpers, settings, and escrow-row decision are identical in
  dev (moto / local DDB) and prod (real DDB). The same `T.billing` handle, same
  `pk`/`sk` schema, and same flag evaluation run in both environments. The escrow
  row is a real DynamoDB item in both.
- **Idempotency.** TBT-001 introduces no writes, but enables the idempotency
  substrate: `bounty_id` is deterministic (`sha256(ticket_id)`), so
  `pk=BOUNTY#{bounty_id}` is stable — letting TBT-003 use a conditional
  `attribute_not_exists(pk)` put for replay-safe `post_bounty`, and TBT-006/007
  use `status`-guarded updates for exactly-once release/refund.
- **Security.** Off-by-default is the security posture: an unreviewed,
  money-moving feature ships dormant. The `404`-on-disabled behavior avoids
  leaking the existence of an unreleased feature. No secrets, no PII, and no new
  network surface are introduced by TBT-001. The `fee_bps` default of 0 means
  the platform takes nothing without an explicit operator decision (D1).

## 8. Backward Compatibility & Migration

- **Ticket system unchanged (flag off).** TBT-001 adds no ticket fields, no new
  statuses, and no router changes. `create_ticket` / `_ticket_out` /
  `update_status` (`app/services/tickets.py`) are untouched by this ticket. The
  bounty fields are added additively in TBT-002 and only populated when the flag
  is on and an owner posts a bounty.
- **Billing system unchanged (flag off).** No new ledger rows, no balance-math
  change, no GSI change. The `BOUNTY#…/ESCROW` partition simply never appears
  while the flag is off. Existing `pk=USER#…` ledger queries are unaffected (a
  `BOUNTY#` pk never matches a `USER#` pk).
- **No migration / backfill.** Reusing `T.billing` with a new `pk` prefix needs
  zero data migration — the table already accepts arbitrary `pk`/`sk`. Enabling
  the flag in prod is a config change, not a schema change.
- **Rollback.** Flip `TICKET_BOUNTIES_ENABLED=false`. Already-written escrow rows
  remain inert (endpoints 404) and in-flight money stays reconcilable via the
  co-located ledger rows; a flag flip should still follow a drain of in-flight
  bounties (downstream runbook concern).

## 9. Test Plan

Hermetic, offline pytest (`tests/test_tbt_001_settings_flag.py`), no moto needed
for the settings/gate assertions (the gate helpers only read `S`):

1. **Flag defaults off.** With the env var unset, assert
   `S.ticket_bounties_enabled is False` and `_bounties_enabled() is False`.
2. **Settings defaults load.** Assert `min_cents == 100`, `max_cents ==
   10_000_000`, `fee_bps == 0`, `payout_hold_seconds == 0`, each an `int`.
3. **404 when off.** `object.__setattr__(S, "ticket_bounties_enabled", False)`;
   assert `_require_bounties_enabled()` raises `HTTPException(status_code=404)`
   with the documented detail; restore in `finally`.
4. **Passes when on.** `object.__setattr__(S, "ticket_bounties_enabled", True)`;
   assert `_bounties_enabled() is True` and `_require_bounties_enabled()` returns
   `None`; restore.
5. **Env override parsing.** `monkeypatch.setenv("TICKET_BOUNTY_FEE_BPS", "250")`
   + a fresh `Settings()`; assert the field reads `250`.
6. **`getattr` fail-closed.** `_bounties_enabled()` against an `S`-like object
   lacking the attribute returns `False`.

No E2E is required (no endpoint exists yet); the bounty E2E suite is TBT-011.

- **Assumption:** the `T.billing` table's `pk`/`sk` are generic strings (verified
  — `scripts/local-ddb-init.py:69-70`), so a `BOUNTY#` prefix is accepted with no
  schema change.
- **Assumption:** the gate helpers live in `app/services/ticket_bounties.py`
  (created by TBT-003); if TBT-001 must merge strictly first, they ship as a tiny
  standalone module that TBT-003 extends. The signatures are fixed either way.
- **Open:** whether `ticket_bounty_payout_hold_seconds` is wired in v1 or left a
  reserved `0`. Recommendation: ship the setting, defer the hold logic; a `0`
  value is a no-op in TBT-006.
