# TBT-007 — Cancel + refund → poster (any non-paid_out state)

**Milestone:** 1 — Escrow & bounty foundation
**Type:** Feature | **Priority:** P0 | **Estimate:** 1.5 days
**Dependencies:** TBT-003 (escrow service + `post_bounty`), which itself depends on TBT-001 (flag/settings) and TBT-002 (ticket bounty fields).

---

## 1. Summary & Goal

This ticket implements the **cancel-bounty-and-refund** path for the ticket bounty system. Any bounty that has been escrowed but not yet paid out must be fully refundable — to the poster — in a single atomic operation that:

1. Puts funds back in the poster's wallet.
2. Marks the escrow record as `refunded`.
3. Flips the ticket to `bounty_status="cancelled"` and `status="cancelled"`.
4. Clears the bounty board index.
5. Notifies the poster (and any active claimant).
6. Emits an audit event.

The operation is **idempotent**: a second cancel request on an already-cancelled bounty is a no-op (conditional on `escrow.status == "held"`). The one hard guard is `paid_out`: a bounty whose escrow has already been released to the assignee can never be refunded.

## 2. Context & Current State

### Ticket state machine

`app/services/tickets.py:15-40` defines the current status set in `_TICKET_STATUSES` (lines 15-29; 13 statuses, no `"cancelled"`) and the allowed transitions in `_STATUS_TRANSITIONS` (lines 30-40). Today `"cancelled"` does not exist in either structure; TBT-004 adds it, together with the bounty-specific `_BOUNTY_TRANSITIONS` map that gates bounty state changes to dedicated bounty endpoints.

The `update_status` method (`tickets.py:913`) enforces `_STATUS_TRANSITIONS` exclusively and has no bounty awareness (`tickets.py:913-935`). TBT-007 must never call `update_status` for the cancel transition; it drives ticket status directly.

### Ticket META row shape

`create_ticket` (`tickets.py:411-512`) writes the ticket header to `T.tickets` at `pk=TICKET#{ticket_id}` (via `_ticket_pk`, `tickets.py:164-165`), `sk=META` (via `_meta_item_key`, `tickets.py:168-169`). TBT-002 extends this row with the bounty fields (`bounty_id`, `bounty_status`, `bounty_amount_cents`, `bounty_currency`, `claimed_by_sub`, `gsi_bounty_pk`, `gsi_bounty_sk`). TBT-007 consumes and clears those fields.

The `gsi2pk` key format is `STATUS#{status}` (`_status_index_pk`, `tickets.py:184-185`); the `gsi2sk` format is `UPDATED#{updated_at:013d}#TICKET#{ticket_id}` (`_updated_index_sk`, `tickets.py:192-193`).

The existing GSIs on `T.tickets` (`scripts/local-ddb-init.py:695-711`) are: owner (gsi1), status (gsi2), assignee (gsi3), space, space+status, space+assignee, member spaces, jira workspace, jira issue, jira sync state. TBT-002 adds a sparse `ByBounty` GSI (`gsi_bounty_pk` / `gsi_bounty_sk`). Cancel must remove the two GSI attributes from the ticket META so the board no longer surfaces the cancelled bounty.

### Billing / escrow primitives

`app/services/billing_shared.py` provides the four money primitives used here:

- `apply_wallet_delta(table, pk, delta_cents, *, currency="usd")` (`billing_shared.py:185-213`): for a positive delta (refund), creates the wallet row if absent and increments atomically.
- `new_ledger_entry(*, key_name, key_value, entry_type, amount_cents, state, reason, meta, extra)` (`billing_shared.py:224-259`): mints a `LEDGER#ts#entry_id` sk item; calls `ulidish()` internally; returns `(sk, item)`. **Note:** the field stored in DDB is `"type"` (not `"entry_type"`) — see `billing_shared.py:247`.
- `settle_or_reverse_ledger(table, key_name, key_value, ledger_sk_value, new_state)` (`billing_shared.py:262-275`): flips the `state` field on an existing ledger row.
- `ulidish()` (`billing_shared.py:216-217`): time-ordered unique id used for `entry_id`; called internally by `new_ledger_entry`, not passed as a parameter.

The **refund pattern** is `refund_payment` in `app/routers/billing.py:1286-1344`. It writes `new_ledger_entry(entry_type="adjustment", state="settled", reason="refund")` (`billing.py:1306-1315`) then calls `settle_or_reverse_ledger(..., "reversed")` on the original charge ledger entry (`billing.py:1323-1324`). TBT-007 mirrors this exact two-step sequence for the escrow case.

### Atomic escrow write precedent

`app/services/group_treasury.py` establishes the `transact_write_items` pattern (low-level boto3 client with `TypeSerializer`) for multi-item atomic writes on `T.billing`. The relevant pieces: `TypeSerializer` instantiation at `group_treasury.py:40`, `_to_ddb_item` serializer helper at `group_treasury.py:47-53`, low-level client factory `_transact_client()` at `group_treasury.py:716-740`, and the commit function `_batch_transact` at `group_treasury.py:743-751`. The cancel refund must protect against: (a) concurrent approve racing with cancel; (b) double-refund. Both are defeated by a conditional `ConditionExpression="escrow_status = :held"` on the escrow row inside the transaction.

### Auth helper

`_is_admin_actor(request, user)` in `app/routers/tickets.py:224-225` returns `True` for ADMIN/ROOT roles (via `_is_admin`, `tickets.py:207-208`) or an API key with `tickets:admin` scope (via `_has_api_key_scope`, `tickets.py:216-221`). This is the right check for the "admin may cancel any non-paid_out bounty" gate. The tickets router accesses the user sub as `user.sub` (from `AuthenticatedUser`), **not** `ctx["user_sub"]`.

### Fraud gate

`_fraud_gate` (`billing.py:118-175`) applies only to **charge** paths. A refund/cancel is not a charge and therefore does NOT call `_fraud_gate`. The constraint from the cross-cutting rules applies to `post_bounty` (TBT-003), not to cancel.

### Notification helper

In-app notifications use `write_alert(user_sub, *, event, outcome, title, details, ...)` (`app/services/alerts.py:356`). There is **no** `send_alert` function in alerts.py; the correct function is `write_alert`. Alert delivery (SSE push, webhook fanout) is handled internally by `write_alert`.

## 4. API / Service Design

### Service function: `cancel_bounty`

Location: `app/services/ticket_bounties.py` (new file, established by TBT-003).

```python
async def cancel_bounty(
    ticket_id: str,
    actor_sub: str,
    reason: str,
    *,
    is_admin: bool,
    request: Request | None = None,
) -> dict[str, Any]:
    ...
```

**Parameters:**

- `ticket_id`: the ticket being cancelled.
- `actor_sub`: the calling user's `user_sub`.
- `reason`: caller-provided text; stored on the escrow row and ledger meta.
- `is_admin`: `True` when the caller passes the `_is_admin_actor` check; drives the permission gate.
- `request`: forwarded FastAPI `Request` for audit logging (IP capture); may be `None` in tests.

**Return value:** The updated ticket dict (same shape as `TicketStore.get_ticket`), suitable for wrapping in `TicketEnvelope`.

**Raises:**

| Condition | Exception / HTTP |
|---|---|
| Feature flag off | `HTTPException(404)` via `_require_bounties_enabled()` |
| Ticket not found | `HTTPException(404)` |
| Bounty field absent (`bounty_id` is None) | `HTTPException(409, "ticket_has_no_bounty")` |
| `bounty_status == "paid_out"` | `HTTPException(409, "bounty_already_paid_out")` |
| `bounty_status == "cancelled"` | returns current ticket (idempotent no-op) |
| Actor is not poster AND not admin | `HTTPException(403, "forbidden")` |
| Poster tries to cancel after claimed | `HTTPException(403, "poster_cannot_cancel_after_claim")` |
| DDB `ConditionalCheckFailedException` on escrow | idempotent: re-load and return current state |

### Router endpoint

Location: `app/routers/tickets.py` (extend existing router).

```
POST /tickets/{ticket_id}/bounty/cancel
```

Auth: `Depends(require_ui_session)` (standard cookie/bearer, CSRF enforced for cookie callers).

```python
class CancelBountyReq(BaseModel):
    reason: str = Field("", max_length=500)

class CancelBountyOut(BaseModel):
    ok: bool
    ticket: TicketOut

@router.post(
    "/{ticket_id}/bounty/cancel",
    response_model=CancelBountyOut,
    responses=_error_responses(),
)
async def cancel_bounty_endpoint(
    ticket_id: str,
    body: CancelBountyReq,
    request: Request,
    ctx=Depends(require_ui_session),
    user: AuthenticatedUser = Depends(get_authenticated_user),
):
    _require_bounties_enabled()
    is_admin = _is_admin_actor(request, user)
    ticket = await cancel_bounty(
        ticket_id=ticket_id,
        actor_sub=user.sub,  # tickets router uses user.sub, not ctx["user_sub"]
        reason=body.reason,
        is_admin=is_admin,
        request=request,
    )
    return CancelBountyOut(ok=True, ticket=TicketOut.model_validate(ticket))
```

### Service internals — step-by-step

```
cancel_bounty(ticket_id, actor_sub, reason, is_admin, request):

1. _require_bounties_enabled()

2. ticket = TicketStore(T.tickets).get_ticket(ticket_id)
   if not ticket → HTTPException(404)

3. bounty_id = ticket.get("bounty_id")
   if not bounty_id → HTTPException(409, "ticket_has_no_bounty")

4. Load escrow: T.billing.get_item(Key={"pk": f"BOUNTY#{bounty_id}", "sk": "ESCROW"})
   if not found → HTTPException(409, "escrow_not_found")  # shouldn't happen if TBT-003 ran

5. escrow_status = escrow["escrow_status"]
   if escrow_status == "released" (paid_out path):
       → HTTPException(409, "bounty_already_paid_out")
   if escrow_status == "refunded":
       → return TicketStore(T.tickets).get_ticket(ticket_id)  # idempotent

6. Permission gate:
   poster_sub = escrow["poster_sub"]
   bounty_status = ticket.get("bounty_status")  # "funded"|"claimed"|"submitted"|"pending_approval"
   is_poster = (actor_sub == poster_sub)
   if not is_admin and not is_poster:
       → HTTPException(403, "forbidden")
   if is_poster and not is_admin and bounty_status != "funded":
       # poster can only self-cancel while unclaimed
       → HTTPException(403, "poster_cannot_cancel_after_claim")

7. Compute refund:
   amount_cents = int(escrow["amount_cents"])
   ts = now_ts()
   # Note: do NOT call ulidish() separately — new_ledger_entry calls it internally.
   refund_ledger_sk_val, refund_ledger_item = new_ledger_entry(
       key_name="pk",
       key_value=f"USER#{poster_sub}",
       entry_type="adjustment",
       amount_cents=amount_cents,
       state="settled",
       reason="bounty_refund",
       meta={
           "bounty_id": bounty_id,
           "ticket_id": ticket_id,
           "refund_reason": reason,
           "refunded_by": actor_sub,
       },
   )

8. Atomic transact_write_items on low-level T.billing client:
   (a) UPDATE escrow row:
       Key={"pk": f"BOUNTY#{bounty_id}", "sk": "ESCROW"},
       UpdateExpression="SET escrow_status=:refunded, refunded_at=:ts, refund_ledger_sk=:rsk, refunded_by=:by, refund_reason=:reason",
       ConditionExpression="escrow_status = :held",
       ExpressionAttributeValues={":held": "held", ":refunded": "refunded", ...}
   (b) PUT refund_ledger_item (the adjustment entry computed in step 7)
   (c) UPDATE poster wallet:
       Key={"pk": f"USER#{poster_sub}", "sk": "WALLET"},
       UpdateExpression="SET wallet_balance_cents = if_not_exists(wallet_balance_cents, :z) + :amt, updated_at=:ts",
       ExpressionAttributeValues={":z": 0, ":amt": amount_cents, ":ts": ts}
   On ConditionalCheckFailedException:
       re-fetch escrow; if now "refunded" → idempotent return; else re-raise as 409.

9. settle_or_reverse_ledger(T.billing, "pk", f"USER#{poster_sub}", escrow["ledger_sk"], "reversed")
   (best-effort: swallow exceptions — the wallet has already been credited)

10. Update ticket META on T.tickets:
    SET bounty_status="cancelled", status="cancelled", bounty_cancelled_at=ts,
        gsi2pk=_status_index_pk("cancelled"), gsi2sk=_updated_index_sk(ts, ticket_id),
        updated_at=ts
    REMOVE gsi_bounty_pk, gsi_bounty_sk
    (Clears the ByBounty GSI + flips status GSI)

11. Write activity row:
    pk=TICKET#{ticket_id}, sk=ACT#{ts:013d}#{activity_id}
    entity_type="ticket_activity", activity_type="bounty_cancelled",
    actor_sub=actor_sub, created_at=ts

12. Notify:
    # alerts.send_alert does NOT exist — use write_alert (alerts.py:356).
    write_alert(poster_sub, event="bounty_cancelled", outcome="info",
                title="Bounty refunded", details={ticket_id, amount_cents, reason})
    if ticket.get("claimed_by_sub"):
        write_alert(claimed_by_sub, event="bounty_cancelled_claimant", outcome="info",
                    title="Active bounty cancelled", details={ticket_id})
    (Both best-effort, wrapped in try/except)

13. audit_event("bounty_cancelled", actor_sub, request,
        bounty_id=bounty_id, ticket_id=ticket_id, amount_cents=amount_cents,
        reason=reason, is_admin=is_admin)

14. return TicketStore(T.tickets).get_ticket(ticket_id)
```

## 5. Detailed Behavior & Edge Cases

### Permission matrix

| Actor | Bounty state | Allowed? |
|---|---|---|
| Poster | `funded` (unclaimed) | Yes |
| Poster | `claimed` / `submitted` / `pending_approval` | No — 403 |
| Admin/Root | `funded` | Yes |
| Admin/Root | `claimed` | Yes |
| Admin/Root | `submitted` | Yes |
| Admin/Root | `pending_approval` | Yes |
| Anyone | `paid_out` | No — 409 |
| Anyone | `cancelled` | No-op (idempotent return) |
| Non-poster, non-admin | any | 403 |

This reflects the cross-cutting rule from the ticket spec: "Poster cancels while `funded` & unclaimed; OR an admin/root cancels in ANY state except `paid_out`/`cancelled`."

### Race: concurrent cancel + approve (TBT-006)

Both TBT-006 (`approve_bounty`) and TBT-007 (`cancel_bounty`) issue a conditional write on the escrow row with `ConditionExpression="escrow_status = :held"`. Exactly one will win the DDB conditional check; the loser receives `ConditionalCheckFailedException`. The cancel handler re-fetches and checks the new `escrow_status`:

- If `"released"` → the approval won → return 409 "bounty already paid out".
- If `"refunded"` → the cancel already completed (concurrent duplicate) → idempotent return.

### Race: concurrent double-cancel

Two simultaneous cancel requests both have `escrow_status = "held"`. The conditional update in step 8(a) ensures exactly one succeeds. The loser gets `ConditionalCheckFailedException`, re-fetches, finds `escrow_status = "refunded"`, and returns the current ticket state (idempotent).

### Poster cancels while claimant is active

If a claimant (from TBT-005) holds the ticket (`bounty_status = "claimed"`), the poster alone cannot cancel — they receive 403 "poster_cannot_cancel_after_claim". An admin can still force-cancel, in which case both the poster and the claimant are notified. The claimant loses their in-progress work but is never charged (they never held funds).

### Poster cancels after submit (pending_approval)

Submitting does not change escrow ownership; funds remain `status="held"`. A poster without admin rights cannot cancel at this point — only an admin can. This prevents gaming: a poster cannot retract a bounty the moment a claimant submits their work.

### Money invariants

- Poster's wallet credit equals the original `amount_cents` exactly — no fee is deducted on refund (fee is only applicable on payout per D1; cancel is always full refund).
- The poster is never debited twice: TBT-003 debits once; TBT-007 credits once. No call to `write_tip_ledger` is made.
- The adjustment ledger entry (`entry_type="adjustment"`, `state="settled"`) and `settle_or_reverse_ledger(..."reversed"...)` on the original debit entry provide a complete, auditable money trail identical to `refund_payment` (`billing.py:1306-1324`).

### What happens to the claimant's work

TBT-007 does not destroy messages or activity. The ticket status moves to `"cancelled"` but all historical messages/activities remain in DynamoDB under `pk=TICKET#{ticket_id}`. The claimant simply loses a live bounty; there is no financial impact on them.

### `bounty_status="none"` tickets

If a regular (non-bounty) ticket somehow reaches this endpoint, step 3 returns 409 "ticket_has_no_bounty" (no `bounty_id` in the META row), and no money moves.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### Dev/prod parity

There is **no `dev_mode` branch** in `cancel_bounty`. All DynamoDB writes (escrow update, ledger entry, wallet credit, ticket META update) execute through the same code path in both environments. In dev, `T.billing` and `T.tickets` are backed by DynamoDB Local (port 8001); in prod they are real DynamoDB tables. The `boto3` call surface is identical. moto handles the test environment.

### Idempotency

The idempotency key for the refund is the escrow row's `escrow_status` attribute:

- First call: conditional `escrow_status = "held"` → succeeds → writes ledger + wallet + ticket.
- Second call: conditional fails → re-fetch finds `escrow_status = "refunded"` → returns ticket state immediately without any writes.

This means even if the client retries after a network timeout (after the DDB write succeeded but before the HTTP response arrived), the second call returns the correct final state and writes nothing.

### Preventing double-credit

The `transact_write_items` in step 8 groups the escrow update, the ledger entry write, and the wallet credit in one atomic operation. If the transaction commits, all three are guaranteed. If it fails, none is applied. The `settle_or_reverse_ledger` call in step 9 is outside the transaction but is best-effort (it only flips a state label; the real money has already moved atomically).

### Authorization

The permission gate (step 6) checks both `is_poster` and `is_admin` before any money moves. A regular non-poster user who guesses a `ticket_id` always receives 403 before any DDB read on the escrow row (the ticket read happens first, but the escrow load and write only proceed after authorization).

The endpoint uses `require_ui_session`, which enforces CSRF for cookie-authenticated callers and validates a Cognito JWT for bearer-auth callers (`app/auth/deps.py`). No dev-mode header bypass is available when `COGNITO_USER_POOL_ID` is set (per CLAUDE.md note).

### Audit trail

Every successful cancel produces:

1. An `"adjustment"` ledger entry (`state="settled"`) on the poster's billing partition.
2. The original debit ledger entry flipped to `"reversed"`.
3. An `audit_event("bounty_cancelled", ...)` row in `T.alerts`.
4. A `bounty_cancelled` activity row in the ticket's partition.

All four survive independently; none is lost even if the HTTP response is dropped.

### Fraud gate not applied to refunds

`_fraud_gate` (`billing.py:118-175`) checks account freeze and evaluates the transaction for fraud signals. It applies to **charge** events (debit from wallet). A cancel/refund is a **credit** back to the poster and is not a fraud-risk charge path. The cancel endpoint does NOT call `_fraud_gate`. (Frozen accounts can still receive refunds — the freeze prevents new charges, not fund returns.)

## 8. Backward Compatibility & Migration

### Flag-off: zero impact

With `TICKET_BOUNTIES_ENABLED=false` (the production default), `cancel_bounty` is unreachable from the router (endpoint returns 404). The ticket service (`tickets.py`), its `_TICKET_STATUSES` tuple, and `_STATUS_TRANSITIONS` dict are **byte-for-byte unchanged** from today's `main` branch. Existing helpdesk/support ticket flows are entirely unaffected.

TBT-004 adds `"cancelled"` to `_TICKET_STATUSES` and to `_BOUNTY_TRANSITIONS`, but the non-bounty `_STATUS_TRANSITIONS` map does not include `"cancelled"` as a reachable state. A non-bounty ticket can never be moved to `"cancelled"` through `update_status`, because `"cancelled"` is only reachable via the bounty cancel endpoint, which is 404 when the flag is off.

### No DynamoDB schema migration required

The escrow rows (`BOUNTY#{bounty_id}/ESCROW`) are new rows introduced by TBT-003. No existing rows are altered. The `gsi_bounty_pk` / `gsi_bounty_sk` attributes on ticket META rows are written only by TBT-003 and cleared by TBT-007 — they are never present on pre-bounty tickets.

The `ByBounty` sparse GSI (added by TBT-002 to `scripts/local-ddb-init.py`) requires a `just restart` in dev to recreate the table. In prod it requires an `UpdateTable` + async backfill before the bounty endpoints are deployed.

### `TicketOut` model (additive)

`TicketOut` in `app/routers/tickets.py:58-72` gains optional bounty fields (TBT-002). All new fields carry `None` defaults, so existing serialized tickets and existing API consumers that don't know about bounties continue to work unchanged (Pydantic ignores extra fields on deserialization, and `None` fields are excluded from responses by `model_config = {"exclude_none": True}` if that's the project convention).

## 10. Open Questions / Assumptions

1. **D1 (fee=0% default, from Open Decisions):** Cancel always refunds the full `amount_cents`. Since `ticket_bounty_fee_bps` defaults to 0 (D1), no fee was ever deducted from the poster at post time, so the full amount is correct in all cases. If fee > 0 is adopted in future, the cancel refund should still return the full posted amount (the fee is only taken on successful payout), which this design already does.

2. **D2 (wallet funding):** The refund credits the poster's wallet (`pk=USER#{poster_sub}`, `sk=WALLET`). This is symmetric with the debit at post time. If D2 is revisited to allow card-funded bounties in future, the cancel path would need to optionally route through the provider's refund API (similar to `refund_payment`). For v1 (wallet-only), `apply_wallet_delta` is sufficient.

3. **D3 (any owner):** The permission check (`is_poster and bounty_status == "funded"`) allows any ticket owner to self-cancel their own unclaimed bounty, consistent with D3's "any owner" recommendation.

4. **D4 (manual unclaim):** An active claimant who wants to abandon the work calls `unclaim_bounty` (TBT-005), which returns the ticket to `funded` and makes it self-cancellable by the poster again. TBT-007 does not implement unclaim.

5. **Partial refunds:** Not supported. Cancel is always full-amount. Partial bounty reductions are a future feature.

6. **Claimant notification delivery:** *(Pass-3 update: `alerts.send_alert` does not exist; the correct call is `write_alert`, already corrected in §12 row 27 and in the §4 pseudocode.)* `write_alert` stores the alert in DDB and delivers it in-app via SSE for any event string; `"bounty_cancelled_claimant"` requires no pre-registration. Email/SMS/push delivery of this event is a v1 nice-to-have — it requires adding the event to `ALERT_EVENT_TYPES` and wiring user preferences, deferred to TBT-009 or a follow-up ticket.

7. **`status="cancelled"` in existing ticket board queries:** The existing `list_tickets` and board queries use `gsi2pk=STATUS#<status>`. Adding `"cancelled"` as a reachable status means an admin's ticket list with no status filter may eventually include cancelled tickets. The filtering is caller-optional; this is acceptable.
