# TKA-002 — Attachment list / get-download / delete + projection

**Milestone:** 2 — Ticket file attachments
**Type:** Feature | **Priority:** P1 | **Estimate:** 1 day
**Status:** Design — 2026-06-11

---

## 1. Summary & Goal

TKA-001 defined the presign + store flow and the `ATTACHMENT#{attachment_id}` DDB row schema. TKA-002 completes the attachment feature by adding the remaining three read/write operations:

1. **List** — `GET /tickets/{id}/attachments` returns all active attachment metadata for a ticket.
2. **Download URL** — `GET /tickets/{id}/attachments/{aid}/download` returns a time-limited presigned GET URL (prod) or a `/mock/s3/…` URL (dev) so the caller can fetch the file from S3.
3. **Delete** — `DELETE /tickets/{id}/attachments/{aid}` soft-deletes the metadata row and performs a best-effort S3 object removal. Only the original uploader or an admin may delete.
4. **Projection** — `get_ticket` (and therefore `GET /tickets/{id}`) gains an `attachments` array carrying all active attachment metadata, so a single GET of the ticket detail returns everything the UI needs.

All four changes are strictly additive and remain entirely gated on `S.ticket_attachments_enabled` (default **off**, introduced in TKA-001). With the flag off, every new endpoint returns 404 and `TicketOut.attachments` is always `[]`. Existing ticket behaviour is byte-for-byte unchanged.

## 2. Context & Current State

### Existing ticket data layer

`app/services/tickets.py` owns the single-table `T.tickets` store (handle wired at `app/core/tables.py:140` struct field and `:392` instantiation). The partition structure is:

- META row: `pk=TICKET#{ticket_id}`, `sk=META` (`app/services/tickets.py:164-169` — `_ticket_pk` + `_meta_item_key`)
- Message rows: `sk=MSG#{ts:013d}#{message_id}` (`app/services/tickets.py:172-173` — `_msg_sk`)
- Activity rows: `sk=ACT#{ts:013d}#{activity_id}` (`app/services/tickets.py:176-177` — `_act_sk`)
- Attachment rows (added by TKA-001): `sk=ATTACHMENT#{attachment_id}`, `entity_type="ticket_attachment"`

`_query_partition_prefix(ticket_id, sk_prefix)` (`app/services/tickets.py:514-520`) fetches all rows under a ticket by `begins_with(sk, prefix)` with `ScanIndexForward=True`; no `LastEvaluatedKey` pagination loop. TKA-001 uses this to count existing attachments before writing a new one. TKA-002 uses the same helper to list them.

`get_ticket` (`app/services/tickets.py:522-566`) builds the ticket projection by:
1. `get_item` on the META row
2. `_query_partition_prefix(ticket_id, "MSG#")` for messages
3. `_query_partition_prefix(ticket_id, "ACT#")` for activities

It currently returns a dict that omits `ATTACHMENT#` rows entirely. TKA-002 adds a fourth query inside `get_ticket` (or its caller) to include `attachments`.

### S3 delete pattern

DDB soft-delete (flip `status` field) is the primary action. S3 `delete_object` is called best-effort in a `try/except` block — a failure to delete the S3 object must never roll back the DDB soft-delete. This mirrors the file-manager delete pattern and the cross-cutting constraint that storage cleanup is never a correctness invariant.

## 4. API / Service Design

### Service additions: `app/services/ticket_attachments.py`

All four functions are **synchronous** — consistent with the rest of the ticket service layer (`app/services/tickets.py:807` `assign_ticket`, `:851` `add_message`, `:913` `update_status`, all `def` not `async def`, verified) and the router's `def` endpoints (verified: all route handlers in `app/routers/tickets.py` are plain `def`).

#### 4.1 `list_attachments`

```python
def list_attachments(ticket_id: str) -> list[dict[str, Any]]:
    """
    Return all active attachments for a ticket, sorted by created_at ascending.
    Uses _query_partition_prefix(ticket_id, "ATTACHMENT#") then filters status=="active".
    Returns a list (never None); empty list when no attachments exist.
    Decimal fields (filesize, created_at) are coerced to int before return.
    """
```

Implementation sketch:
1. Call `_query_partition_prefix(ticket_id, sk_prefix="ATTACHMENT#")` — returns all rows including soft-deleted.
2. Filter to `item.get("status") == "active"`.
3. Coerce `filesize` and `created_at` to `int` (DynamoDB returns `Decimal` for numeric attributes).
4. Sort by `created_at` ascending (consistent with message ordering).
5. Strip internal DDB attributes (`pk`, `sk`) before returning.
6. Return list (empty list if none).

#### 4.2 `get_attachment`

```python
def get_attachment(ticket_id: str, attachment_id: str) -> dict[str, Any] | None:
    """
    Point-read a single attachment row.
    Returns None if not found or status=="deleted".
    """
```

Implementation: `T.tickets.get_item(Key={"pk": f"TICKET#{ticket_id}", "sk": f"ATTACHMENT#{attachment_id}"})`. Returns `None` if the item is absent or `status == "deleted"`.

#### 4.3 `get_download_url`

```python
def get_download_url(ticket_id: str, attachment_id: str) -> str:
    """
    Generate a presigned GET URL (prod) or /mock/s3/... URL (dev) for the attachment.
    Raises LookupError if attachment not found or deleted.
    Raises HTTPException(500) if bucket is empty.
    """
```

Implementation:
1. Call `get_attachment(ticket_id, attachment_id)` — raise `LookupError` if `None`.
2. Extract `bucket` and `s3_key` from the row.
3. Guard: `if not bucket: raise HTTPException(500, "attachment_bucket_not_configured")`.
4. If `S.dev_mode`: return `f"{S.public_base_url}/mock/s3/{bucket}/{quote(s3_key, safe='/')}"`.
5. Else: `s3_client().generate_presigned_url("get_object", Params={"Bucket": bucket, "Key": s3_key}, ExpiresIn=S.ticket_attachments_download_ttl_seconds)`.

Uses `app.core.aws_clients.s3_client()` — no new boto3 instantiation.

#### 4.4 `delete_attachment`

```python
def delete_attachment(
    ticket_id: str,
    attachment_id: str,
    actor_sub: str,
) -> dict[str, Any]:
    """
    Soft-delete an attachment:
      1. update_item sets status="deleted", deleted_at=now_ts(), deleted_by=actor_sub.
         ConditionExpression: attribute_exists(sk) AND #status = :active
         → ConditionalCheckFailedException if not found or already deleted → 404.
      2. Best-effort S3 delete_object (try/except, failure is logged but not raised).
      3. Emits audit_event("ticket_attachment_deleted", actor_sub, ...).
      4. Returns the updated attachment dict (with status="deleted").
    """
```

The conditional `update_item` prevents a double-delete race from corrupting the row (second call sees `status != "active"` and raises `ConditionalCheckFailedException`). The router maps this to a 404 (`attachment_not_found`) — idempotent from the caller's perspective.

#### Endpoint 1 — List attachments

```
GET /tickets/{ticket_id}/attachments
```

**Auth:** `Depends(require_ui_session)` + `Depends(get_authenticated_user)`. Caller must pass `_can_access_or_work_ticket` (owner, assignee, or admin) — same extended guard introduced by TKA-001; analogous to the base `_can_access_ticket` used in the existing `GET /{ticket_id}` (`app/routers/tickets.py:907-910`).

**Response 200:** `TicketAttachmentListEnvelope`

**Errors:** 404 (flag off or ticket not found), 403 (not owner/admin).

**Handler:**
1. `_require_attachments_enabled()` — 404 if flag off.
2. `ticket = _ticket_or_404(ticket_id)`.
3. `if not _can_access_ticket(request, user, ticket): _raise(403, ...)`.
4. `rows = ticket_attachments.list_attachments(ticket_id)`.
5. Return `TicketAttachmentListEnvelope(attachments=[TicketAttachmentOut.model_validate(r) for r in rows])`.

#### Endpoint 2 — Download URL

```
GET /tickets/{ticket_id}/attachments/{attachment_id}/download
```

**Auth:** Same as list — owner or admin.

**Response 200:** `TicketAttachmentDownloadOut`

**Errors:** 404 (flag off, ticket not found, or attachment not found/deleted), 403.

**Handler:**
1. `_require_attachments_enabled()`.
2. `ticket = _ticket_or_404(ticket_id)`.
3. Auth check.
4. `try: url = ticket_attachments.get_download_url(ticket_id, attachment_id)` — catches `LookupError` → 404 `attachment_not_found`, `HTTPException(500)` re-raised.
5. Load attachment metadata via `ticket_attachments.get_attachment(ticket_id, attachment_id)` for `filename` and `mime_type`.
6. Return `TicketAttachmentDownloadOut(download_url=url, expires_in_seconds=S.ticket_attachments_download_ttl_seconds, filename=att["filename"], mime_type=att["mime_type"])`.

#### Endpoint 3 — Delete attachment

```
DELETE /tickets/{ticket_id}/attachments/{attachment_id}
```

**Auth:** `Depends(require_ui_session)` + `Depends(get_authenticated_user)`. Caller must be the original uploader (`user.sub == attachment["uploader_sub"]`) or an admin.

**Response 204:** No body.

**Errors:** 404 (flag off, ticket not found, attachment not found/deleted), 403 (not uploader/admin).

**Handler:**
1. `_require_attachments_enabled()`.
2. `ticket = _ticket_or_404(ticket_id)`.
3. Auth: load attachment first — `att = ticket_attachments.get_attachment(ticket_id, attachment_id)` → 404 if `None`.
4. `if user.sub != att["uploader_sub"] and not _is_admin_actor(request, user): _raise(403, ...)`.
5. `ticket_attachments.delete_attachment(ticket_id, attachment_id, actor_sub=user.sub)` — catches `ConditionalCheckFailedException` → 404 `attachment_not_found` (already deleted or race).
6. Return `Response(status_code=204)`.

Note: `_can_access_ticket` is NOT sufficient for delete — the owner of the ticket is not necessarily the uploader, and allowing the ticket owner to delete another user's attachment would be unexpected. Admin can always delete. Uploader can always delete their own.

#### Projection: `get_ticket` extended

`app/services/tickets.py:522-566` is modified to query `ATTACHMENT#` rows and include them:

```python
def get_ticket(self, ticket_id: str) -> dict[str, Any] | None:
    header = self._table.get_item(Key=_meta_item_key(ticket_id)).get("Item")
    if not header:
        return None
    messages   = self._query_partition_prefix(ticket_id=ticket_id, sk_prefix="MSG#")
    activities = self._query_partition_prefix(ticket_id=ticket_id, sk_prefix="ACT#")
    raw_atts   = self._query_partition_prefix(ticket_id=ticket_id, sk_prefix="ATTACHMENT#")
    attachments = [
        {
            "attachment_id": item["attachment_id"],
            "ticket_id":     item["ticket_id"],
            "filename":      item.get("filename", ""),
            "filesize":      int(item.get("filesize", 0) or 0),
            "mime_type":     item.get("mime_type", ""),
            "s3_key":        item.get("s3_key", ""),
            "bucket":        item.get("bucket", ""),
            "uploader_sub":  item.get("uploader_sub", ""),
            "created_at":    int(item.get("created_at", 0) or 0),
            "status":        item.get("status", "active"),
        }
        for item in raw_atts
        if item.get("status") == "active"
    ]
    return {
        # ... existing keys unchanged ...
        "attachments": attachments,
    }
```

This change is inside the `TicketStore` class, not the router. `get_ticket` has no concept of the flag — the projection is always computed. The router's `_wrap_ticket` calls `TicketOut.model_validate(ticket)`, which maps `attachments` to the new `TicketOut.attachments` field (default `[]` when the flag is off and no rows exist).

Flag-gating note: when `ticket_attachments_enabled` is `False`, no attachment rows exist in DDB (the TKA-001 endpoints are 404-gated), so the `raw_atts` query always returns `[]`. The projection adds zero overhead. When the flag is on, the extra query cost is proportional to the attachment count, which is bounded by `S.ticket_attachments_max_per_ticket` (default 20).

## 5. Detailed Behavior & Edge Cases

### Soft-delete vs. physical delete

`delete_attachment` writes `status="deleted"` via `update_item` with a condition on `status == "active"`. The S3 object is then deleted best-effort:

```python
try:
    s3_client().delete_object(Bucket=att["bucket"], Key=att["s3_key"])
except Exception as exc:
    logger.warning("s3 delete failed for attachment %s: %s", attachment_id, exc)
```

A DDB soft-delete without an S3 delete leaves an orphan object. This is acceptable — correctness is defined by DDB state; S3 is the backing store. A lifecycle rule on `S.filemgr_bucket` (out of scope) handles orphans. The `deleted` row remains for audit; a future hard-purge job could use it.

### Concurrent delete race

If two callers attempt to delete the same attachment simultaneously:
- First call: `update_item` with condition `status = "active"` succeeds → returns 204.
- Second call: condition fails → `ConditionalCheckFailedException` → router returns 404 `attachment_not_found`.

This is correct (idempotent from the first caller's perspective; the second caller is told the attachment is gone).

### `list_attachments` pagination

The `_query_partition_prefix` helper (`:514-520`) uses `KeyConditionExpression` with `begins_with` and `ScanIndexForward=True`, but does **not** paginate via `LastEvaluatedKey`. Per the CLAUDE.md note: "DynamoDB fetches up to 1MB before applying FilterExpression." For attachment rows, each row is small (~300 bytes) and the cap is 20 per ticket (at most ~6 KB total), so a single page is always sufficient. No pagination loop is needed.

If `S.ticket_attachments_max_per_ticket` is raised to a large value in the future, the `list_attachments` implementation should be reviewed — the `_query_partition_prefix` loop-less query could silently miss rows beyond 1 MB. A comment in the service marks this assumption.

### Cap check must exclude deleted rows

TKA-001's `add_attachment` count check (before writing a new row) uses `_query_partition_prefix`. With soft-delete in place, that count must filter to `status == "active"` rows only — otherwise a ticket that hit the 20-attachment cap and deleted some attachments could never add new ones. The TKA-001 spec must be updated (or the TKA-002 implementation confirms this correctness note when landing the service module).

### Download URL for deleted attachment

`get_download_url` calls `get_attachment`, which returns `None` for `status == "deleted"` rows. The router maps `LookupError` to 404. A deleted attachment's S3 object may or may not still exist (best-effort delete), but the endpoint never reveals a download URL for a deleted attachment.

### `TicketOut.attachments` field and `TicketListItemOut`

`TicketListItemOut` (`app/routers/tickets.py:91-110`, verified) is used for list responses. It does include `messages: list[TicketMessage] = []` and `activity: list[TicketActivity] = []` as fields that default to empty (verified: lines 106-107). Attachments are similarly **not** added to `TicketListItemOut` in TKA-002 — list responses would need to query attachment rows for every ticket in the page, which is N extra DDB queries. The attachment array is available only on the single-ticket detail (`GET /{ticket_id}`). The frontend fetches attachments via `GET /{ticket_id}` or via `GET /{ticket_id}/attachments` for a dedicated view.

### Flag toggled off with existing attachments

If `ticket_attachments_enabled` is turned off after attachments have been uploaded, the three attachment endpoints all return 404. The `get_ticket` projection query still runs (no flag check inside `get_ticket`) but returns the attachment rows in the dict. However, because the flag is off, `TicketOut` would still have `attachments: list[TicketAttachmentOut] = []` — wait: the projection returns the data, and `model_validate` will populate the field. This is a conscious choice: existing attachment data is preserved and surfaced even when the flag is off, so that re-enabling the flag does not require re-upload. Operators who want to hide attachments while the flag is off can do so at the UI level (TKA-003 gates the attachment UI on the same flag).

If the product requirement is to hide attachment data when the flag is off, `get_ticket` can check `S.ticket_attachments_enabled` before appending the `attachments` key. This is noted as an open question in §10.

### Auth on download vs. access-ticket

`GET /tickets/{ticket_id}/attachments/{aid}/download` requires the same access as the ticket itself (`_can_access_ticket`). The assignee (`assigned_to_sub`) is not in `_can_access_ticket` today (`:339-340`). Per TKA-001, the assignee may upload attachments — they should also be able to download. The TKA-002 endpoints use the same extended auth logic introduced in TKA-001:

```python
def _can_access_or_work_ticket(request, user, ticket) -> bool:
    return (
        user.sub == ticket["owner_sub"]
        or user.sub == (ticket.get("assigned_to_sub") or "")
        or _is_admin_actor(request, user)
    )
```

This helper is introduced in TKA-001 (for presign/confirm) and reused here for list, download, and delete.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### Dev/prod parity

The only `S.dev_mode` branch is inside `get_download_url`, which returns a `/mock/s3/…` URL in dev instead of a real presigned URL — exactly the same branch as `app/services/license_agreements.py:168-174`. All DDB reads and writes go through `T.tickets` (moto in dev, real DDB in prod) with no branch. The S3 `delete_object` call in `delete_attachment` is best-effort in both environments. Full SECOPS-007 parity.

### Idempotency

- **List:** Pure read; inherently idempotent.
- **Download URL:** Generates a fresh presigned URL on every call; idempotent (repeated calls return fresh, independently valid URLs; no state is written).
- **Delete:** `update_item` with `ConditionExpression = "attribute_exists(sk) AND #status = :active"`. The first call transitions `active → deleted`. A second call fails the condition and returns 404. This is idempotent from the client's perspective — both calls confirm the attachment is gone.

### Security

- **Access control on list and download:** only the ticket owner, assignee, or admin can list or download attachments. An adversary cannot enumerate or download attachments from a ticket they don't own.
- **Access control on delete:** only the uploader or admin can delete. A ticket owner who did not upload an attachment cannot delete it (the ticket owner may not even know the uploader's identity on a bounty ticket with a different assignee).
- **No download of deleted attachments:** `get_attachment` returns `None` for `status=="deleted"`, so the download endpoint always returns 404 for deleted rows.
- **S3 key scoping:** `get_download_url` uses the `s3_key` stored at upload time, which is always of the form `tickets/{ticket_id}/attachments/{attachment_id}/{safe_filename}`. The endpoint never accepts a caller-supplied key — the key comes from the authoritative DDB row.

### Money-safety

This ticket involves no money movement. The bounty Open Decisions (D1 fee, D2 wallet funding, D3 owner, D4 unclaim) do not apply to TKA-002. No ledger entries, no wallet deltas, no billing interactions.

## 8. Backward Compatibility & Migration

### With flag off

`_require_attachments_enabled()` returns 404 for all three new endpoints. `TicketOut.attachments` defaults to `[]` and `get_ticket` returns an empty `attachments` list (no `ATTACHMENT#` rows exist in DDB). All existing ticket endpoints, the existing 42 ticket E2E tests in `frontend/e2e/tickets.spec.ts` (`app/routers/tickets.py:901-910` verified), and all unit tests in `tests/test_ticketing_routes.py` (40 tests) are unaffected.

### `TicketOut` extension is additive

Adding `attachments: list[TicketAttachmentOut] = []` to `TicketOut` is strictly additive. Existing callers of `TicketOut.model_validate(ticket)` receive the new field with value `[]`. API consumers already using `GET /tickets/{id}` will see the new field in the JSON response only after the code is deployed; the field is `[]` until attachments are uploaded. No breaking change.

### `get_ticket` projection change

The additional `_query_partition_prefix(ticket_id, "ATTACHMENT#")` call inside `get_ticket` is the most significant backward-compatibility concern. It adds one DDB query per `get_ticket` call. For tickets with no attachments (all existing tickets at deploy time), the query returns an empty list immediately (no items to scan). The performance impact is negligible — one extra DDB round-trip of ~1 ms. The change is in the service layer, so all callers (router, tests, background jobs) pick it up automatically.

### DynamoDB: no migration required

No new tables. No new GSIs. No `attr_types` additions. The existing `tickets` table definition at `scripts/local-ddb-init.py:695-711` is unchanged (verified). `just restart` is not required for DDB-schema reasons.

## 10. Open Questions / Assumptions

1. **Attachment visibility when flag is off**: The spec currently leaves `get_ticket` unchecked for the flag — existing attachment rows are included in the projection even when `ticket_attachments_enabled=False`. This means any data uploaded while the flag was on remains visible after the flag is toggled off. If product requires strict hiding, add `if not S.ticket_attachments_enabled: return []` at the top of the projection's attachment section in `get_ticket`. The trade-off: this adds a settings check inside every `get_ticket` call (cheap, but a branch).

2. **`TicketListItemOut` attachments**: List responses do not include attachments (§5 explains why — N+1 DDB queries). If the ticket list UI needs to show "has attachments" indicators without fetching each ticket individually, a Boolean `has_attachments: bool` field on `TicketListItemOut` could be derived cheaply from the META row if we store an `attachment_count` counter there (incremented/decremented in `add_attachment`/`delete_attachment`). This is a follow-up enhancement, not required for v1.

3. **Assignee auth on download/list**: TKA-001 extended `_can_access_ticket` to include `assigned_to_sub`. TKA-002 depends on that extension. If TKA-001 did not land that change (due to scope creep), TKA-002 must introduce `_can_access_or_work_ticket` itself. The spec assumes TKA-001 already provides the extended predicate.

4. **S3 delete on disable**: If `ticket_attachments_enabled` is turned off permanently and the operator wants to purge all attachment data, a one-time admin script would need to scan all `ATTACHMENT#` rows across all ticket partitions and delete the S3 objects. There is no built-in purge in this ticket — that is an operational concern.

5. **`_query_partition_prefix` cap**: As noted in §5, the `list_attachments` query is loop-less and safe only because the per-ticket cap (default 20) keeps the total row size well under 1 MB. If `TICKET_ATTACHMENTS_MAX_PER_TICKET` is raised above ~3,000 (at ~300 bytes/row), the query could silently truncate. A comment in `list_attachments` documents this assumption; a future change to `_query_partition_prefix` that adds pagination would fix it universally.

6. **Download URL expiry disclosure**: The `expires_in_seconds` field in `TicketAttachmentDownloadOut` tells the client how long the URL is valid. In dev mode the `/mock/s3/…` URL never expires, but `expires_in_seconds` is still populated with `S.ticket_attachments_download_ttl_seconds` for consistency. This is not a security issue (dev URLs are not real AWS presigned URLs).
