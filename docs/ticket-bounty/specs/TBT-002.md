# TBT-002 — Ticket bounty fields + projection (additive)

**Milestone:** 1 — Escrow & bounty foundation
**Type:** Feature | **Priority:** P0 | **Estimate:** 1 day
**Depends on:** TBT-001 (feature flag, settings, escrow table decision)
**Required by:** TBT-003 (atomic hold), TBT-004 (state machine), TBT-008 (bounty board)

## 1. Summary & Goal

This ticket adds the bounty data fields to the ticket META row and surfaces them
in every ticket projection response. It also declares the sparse `ByBounty` GSI
on the `tickets` table so the bounty board (TBT-008) can query funded+unclaimed
tickets cheaply without scanning.

No money moves in this ticket. It is purely additive schema and projection work.
With `TICKET_BOUNTIES_ENABLED=false` (the default) all new fields are absent from
every read and write path — the ticket system is byte-for-byte unchanged.

## 2. Context & Current State

### Ticket META row

`create_ticket` (`app/services/tickets.py:411-512`) writes a single META row with
`pk=TICKET#{ticket_id}`, `sk="META"` and a fixed set of header attributes. The
relevant current attributes are:

- `status` — one of `_TICKET_STATUSES` (`app/services/tickets.py:15-29`), currently
  has no bounty-related values.
- `assigned_to_sub` / `assigned_admin_sub` — set by `assign_ticket`
  (`app/services/tickets.py:807`), which is today an admin-only operation
  (enforced at `app/routers/tickets.py:921`).
- `version` — an optimistic-concurrency integer incremented by
  `_conditional_update_meta` (`app/services/tickets.py:746`: `:next_version = expected_version + 1`),
  orchestrated via `_apply_header_update_once` (`app/services/tickets.py:792`; used by
  `update_status` at `app/services/tickets.py:913`).
- No bounty fields exist on the item today.

The header is written with a comprehension that strips `None` values
(`app/services/tickets.py:476`), so any new field set to `None` at creation time
will simply be absent from DynamoDB — no schema migration is needed for existing rows.

### Ticket projection (`get_ticket`)

`get_ticket` (`app/services/tickets.py:522-566`) reads the META item, then queries
the `MSG#` and `ACT#` sk-prefixes, and assembles a plain dict. Every caller
(router, service) reads through this function. Fields not present in the dict are
absent from the response.

The router-level `TicketOut` Pydantic model (`app/routers/tickets.py:58-73`)
currently has no optional bounty fields. It does not declare `model_config =
ConfigDict(extra="ignore")`, but the Pydantic v2 default behaviour (verified:
`pydantic==2.6.4`) is to silently ignore extra keys — so extra dict keys returned
by `get_ticket` are silently dropped without any config needed. This means we can
add new keys to `get_ticket`'s return dict now, and they will be silently ignored
by older callers until `TicketOut` is extended (both steps happen in this ticket).

## 3. Data Model

### 3.1 New fields on the ticket META row (`pk=TICKET#{id}`, `sk=META`)

All fields below are **absent** (not written) when the bounty feature is off or
when a ticket carries no bounty. DynamoDB stores only what is written; the
`{k: v for k, v in header.items() if v is not None}` filter at `tickets.py:476`
ensures absent fields remain absent on existing rows.

| Field | Type | Written when | Description |
|---|---|---|---|
| `bounty_amount_cents` | `int` | bounty posted (TBT-003) | Escrowed amount in cents |
| `bounty_currency` | `str` | bounty posted | ISO 4217 code (e.g. `"usd"`) |
| `bounty_status` | `str` | bounty posted | Lifecycle value; see §3.2 |
| `bounty_id` | `str` | bounty posted | Deterministic 24-hex id (sha256 of `"bounty:{ticket_id}"`) |
| `claimed_by_sub` | `str` | claim accepted (TBT-005) | `user_sub` of claimant |
| `claimed_at` | `int` | claim accepted | Unix timestamp (seconds) |
| `bounty_funded_at` | `int` | bounty posted | Unix timestamp |
| `bounty_submitted_at` | `int` | claimant submits (TBT-006) | Unix timestamp |
| `bounty_paid_at` | `int` | admin approves (TBT-006) | Unix timestamp |
| `bounty_cancelled_at` | `int` | cancel/refund (TBT-007) | Unix timestamp |
| `bounty_repost_count` | `int` | bounty (re)posted (TBT-003) | Number of times this ticket's bounty has been posted; starts `0`, incremented each re-post after a cancel. **Tracked but NOT enforced in v1** — per decision D3 (`docs/CROSS_TICKET_AUDIT.md` §D3, no repost cap) it is not checked against `S.ticket_bounty_max_reposts`. Resolves the TBT-003↔TBT-002 plan-gap — TBT-002 is authoritative for ticket META fields, so the field is declared here and surfaced in `_ticket_out` + `TicketOut`. |
| `gsi_bounty_pk` | `str` | `bounty_status=="funded"` only | Sparse index pk: `"BOUNTY#OPEN"` |
| `gsi_bounty_sk` | `int` | `bounty_status=="funded"` only | Sparse index sk: `created_at` (N) |

**Sparse index invariant:** `gsi_bounty_pk` / `gsi_bounty_sk` are set exactly
when `bounty_status == "funded"` (ticket is on the board, unclaimed). They are
cleared (set to `None`, which DynamoDB omits) when a ticket is claimed, cancelled,
paid out, or the bounty is removed. This keeps non-bounty tickets completely out
of the GSI — a full-table scan would find zero non-bounty items in the index.

### 3.2 `bounty_status` lifecycle values

```
none (absent)  →  funded  →  claimed  →  submitted (pending_approval)
                     ↓            ↓               ↓
                 cancelled    cancelled       paid_out | back to claimed (reject)
```

Valid values: `"funded"`, `"claimed"`, `"submitted"`, `"paid_out"`, `"cancelled"`.
The absence of `bounty_status` on a ticket means it has no bounty at all.
Terminal values: `"paid_out"`, `"cancelled"`.

This ticket is responsible only for **declaring** the values and including them
in the projection. The transitions and writes are owned by TBT-003 through TBT-007.

### 3.3 New GSI — `ByBounty` on `T.tickets`

**Purpose:** enables the bounty board query (`list_open_bounties`, TBT-008) to
retrieve all funded+unclaimed bounties by recency without a table scan.

| Property | Value |
|---|---|
| Index name | `S.tickets_bounty_index_name` (env `TICKETS_BOUNTY_INDEX_NAME`, default `"bounty-open-created_at-index"`) |
| Partition key | `gsi_bounty_pk` (String) |
| Sort key | `gsi_bounty_sk` (Number — Unix timestamp) |
| Projection | `ALL` (ticket subject, labels, status, and bounty fields are all needed) |

### 4.4 Helper functions added to `app/services/tickets.py`

Two small pure helpers support later tickets without coupling them to
implementation details of the META row:

```python
def _set_bounty_gsi_keys(
    item: dict[str, Any], *, funded: bool, created_at: int
) -> dict[str, Any]:
    """Return a copy of `item` with gsi_bounty_pk/sk set or cleared.

    Called by TBT-003 (post_bounty), TBT-005 (claim, unclaim), TBT-007 (cancel).
    `funded=True` → sets the sparse index keys; `funded=False` → sets them to
    None (omitted by the `{k:v if v is not None}` filter on put_item).
    """
    if funded:
        item["gsi_bounty_pk"] = "BOUNTY#OPEN"
        item["gsi_bounty_sk"] = created_at
    else:
        item["gsi_bounty_pk"] = None
        item["gsi_bounty_sk"] = None
    return item


def bounty_id_for_ticket(ticket_id: str) -> str:
    """Deterministic 24-hex bounty id. Used by TBT-003 and TBT-007."""
    import hashlib
    return hashlib.sha256(f"bounty:{ticket_id}".encode()).hexdigest()[:24]
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behavior

When `S.ticket_bounties_enabled` is `False`:

- `get_ticket` still returns the bounty fields (they will all be `None` because
  no bounty data is ever written with the flag off). This is safe — adding `None`
  fields to the dict is additive and harmless.
- `TicketOut` serializes all bounty fields as `null` in JSON. Clients ignoring
  unknown / null fields are unaffected.
- The sparse GSI exists in the table schema but has zero items in it (no row ever
  writes `gsi_bounty_pk` with the flag off).
- Crucially, no ticket can reach any bounty state because the endpoints that write
  bounty data (TBT-003 onwards) all call `_require_bounties_enabled()` and return
  404 when the flag is off.

### 5.2 Non-bounty tickets

For tickets that have never had a bounty posted (the vast majority), `get_ticket`
returns `bounty_status: None`, `bounty_amount_cents: None`, etc. Clients MUST
treat a `null` `bounty_status` as "no bounty" and not render any bounty UI.

### 5.3 Backward compatibility with existing serialization

`get_ticket` currently returns a dict with no bounty keys at all (the keys simply
do not exist). After this change it returns the keys with `None` values. Any code
that previously used `"bounty_status" in ticket_dict` as an existence check would
need updating, but a search of the codebase confirms no such checks exist yet —
all bounty consumers are new (TBT-003+).

### 5.4 `int()` coercion for DynamoDB Decimal

DynamoDB returns numbers as `Decimal`. Any timestamp or cent field read back must
be coerced to `int` to avoid Pydantic validation errors. The pattern `int(header["field"]) if header.get("field") is not None else None` is established at
`app/services/tickets.py:536-540` and must be followed for all new numeric fields.

### 5.5 Sparse GSI semantics

DynamoDB only indexes a row into a GSI when both the GSI partition key and the
GSI sort key are present and non-null on the item. Setting `gsi_bounty_pk=None`
(or omitting it) removes the item from the index on the next write. This is the
mechanism used throughout the codebase (e.g. `gsi_space_pk` is set to `None` for
tickets without a space at `app/services/tickets.py:469`).

The `gsi_bounty_sk` sort key is a numeric Unix timestamp. DynamoDB Local will
reject queries against a String-typed sort key using numeric comparisons, which
is why the `attr_types={"gsi_bounty_sk": "N"}` declaration is non-negotiable.
Omitting it causes `ValidationException` at runtime (CLAUDE.md: "DDB numeric GSI
sort keys" gotcha).

### 5.6 GSI propagation latency

GSI writes in DynamoDB are eventually consistent (typically sub-second). The
bounty board query (TBT-008) uses `ConsistentRead=False` (GSIs do not support
strong reads) and may miss a very recently posted bounty for a brief window. This
is acceptable for a board listing; claiming (TBT-005) uses a conditional
`update_item` on the base table (strongly consistent) as the authoritative
single-winner gate.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

**SECOPS-007:** There is no `dev_mode` branch in any code touched by this ticket.
`get_ticket` reads from DynamoDB; in dev it reads from DynamoDB Local (moto);
in prod it reads from real DynamoDB. The `TableDef` change in `local-ddb-init.py`
applies to both environments (prod uses `UpdateTable` + backfill at deploy time;
dev recreates the table on `just restart`).

**No money movement here.** TBT-002 is schema and projection only. The money-
safety constraints (atomic escrow, no double-charge, `_fraud_gate`, `is_frozen`)
are enforced in TBT-003 and later.

**Idempotency:** `get_ticket` is a pure read; it is inherently idempotent.
`create_ticket` already guards against double-creation at `tickets.py:431-433`
(`if existing: return existing`). No new write paths are introduced here.

**Information security:** Bounty fields (`bounty_amount_cents`, `claimed_by_sub`,
etc.) are returned by `get_ticket` to any caller that can already read the ticket.
Existing ticket visibility rules (owner sees own ticket; admin sees all) are
unchanged and continue to gate access at the router layer. No bounty field
requires elevated privilege to *read* — the amount is intentionally public (the
bounty board shows it). Claim identity (`claimed_by_sub`) is a user sub, which
is already a non-PII identifier used throughout the ticket system (e.g.
`owner_sub`, `assigned_to_sub`).

## 8. Backward Compatibility & Migration

### Existing tickets (no bounty)

No migration is required. Existing ticket META rows in DynamoDB carry none of the
new fields. `get_ticket` uses `.get(field)` with a `None` default for every new
field, so existing rows return `bounty_status: None`, etc. The `{k: v if v is not
None}` write filter means we never write `None`-valued fields back to DynamoDB
when updating existing tickets through the existing code paths.

### GSI backfill

Adding a new GSI to an existing DynamoDB table is an online operation (`UpdateTable`
in prod). DynamoDB backfills the new GSI from the base table asynchronously; since
no existing items carry `gsi_bounty_pk`, the backfill is instantaneous (zero items
to index). There is no risk of spurious rows appearing in the new index.

In dev, `just restart` drops and recreates all tables via `local-ddb-init.py`,
so the new GSI is present from first boot after the change lands.

### Flag rollout

- **Flag off (default):** Zero behavior change. The new Pydantic fields serialize
  as `null` in all ticket responses, which is additive and safe for all existing
  frontend consumers (React Query shapes use TypeScript optionals; `null` fields
  are ignored until bounty UI is rendered by TBT-010).
- **Flag on:** Bounty endpoints become reachable; the sparse GSI starts receiving
  writes when bounties are posted. Toggling the flag off again after bounties have
  been posted does not corrupt data — it only prevents new bounties; existing bounty
  data is still projected correctly.

## 9. Test Plan

### 9.1 Hermetic pytest unit tests (`tests/test_tbt002_bounty_fields.py`)

All tests use moto-backed DynamoDB, with `T.tickets` patched via

— route handlers are called directly as coroutines on a fresh
`asyncio.new_event_loop()`.

**Test cases:**

1. **Non-bounty ticket projection** — create a ticket with `create_ticket`;
   call `get_ticket`; assert all bounty fields (`bounty_status`, `bounty_amount_cents`,
   etc.) are `None` in the returned dict.

2. **Bounty field round-trip** — directly write a META row with all bounty fields
   set (simulating TBT-003's output); call `get_ticket`; assert each field is
   correctly projected with `int` coercion (e.g. `bounty_amount_cents` returns

3. **`TicketOut` serialization — no bounty** — construct `TicketOut(**ticket_dict)`

4. **`TicketOut` serialization — with bounty** — construct `TicketOut(**ticket_dict)`
   with bounty fields populated; assert all fields serialize correctly.

5. **`gsi_bounty_pk` / `gsi_bounty_sk` absent on non-bounty ticket** — query the
   moto GSI with `gsi_bounty_pk="BOUNTY#OPEN"`; assert zero items returned for
   a freshly created non-bounty ticket.

6. **Sparse GSI populated when `bounty_status="funded"`** — directly write a META
   row with `gsi_bounty_pk="BOUNTY#OPEN"` and `gsi_bounty_sk=<ts>` (integer);
   query the GSI; assert the item is found.

7. **Sparse GSI absent when `bounty_status="claimed"`** — write a row with
   `gsi_bounty_pk=None` (omitted); query GSI; assert zero items.

8. **`bounty_id_for_ticket` determinism** — call twice with the same `ticket_id`;
   assert both calls return the same 24-character hex string.

9. **`_set_bounty_gsi_keys` with `funded=True`** — assert `gsi_bounty_pk` and
   `gsi_bounty_sk` are set on the returned dict.

10. **`_set_bounty_gsi_keys` with `funded=False`** — assert `gsi_bounty_pk` and
    `gsi_bounty_sk` are `None` in the returned dict (and therefore omitted by the
    write filter).

11. **Flag off — projection unchanged** — with `S.ticket_bounties_enabled=False`,
    a ticket that somehow has `bounty_status="funded"` written (direct DDB write)
    still projects the bounty fields correctly (the projection does not gate on the

## 10. Open Questions / Assumptions

1. **`TicketListItemOut` bounty fields scope** — this spec includes only
   `bounty_amount_cents` and `bounty_status` on the list model to avoid
   transmitting all timestamps in list responses. If the board page (TBT-010)
   needs additional fields (e.g. `bounty_id` for the claim endpoint URL), they
   can be added additively here without breaking anything.

2. **`bounty_status` as a ticket-level field vs. `status`** — the design keeps
   `bounty_status` as a separate field on the META row, parallel to the main
   `status`. This avoids touching `_TICKET_STATUSES` and `_STATUS_TRANSITIONS`
   in this ticket (those are owned by TBT-004). The implication is that a ticket
   can have `status="in_progress"` and `bounty_status="claimed"` simultaneously,
   which is correct. Downstream rendering (TBT-010) displays both status chips
   independently.

3. **Assumption: `attr_types` key already accepted by `TableDef`** — confirmed at
   `local-ddb-init.py:34-35`: `attr_types: Dict[str, str] = field(default_factory=dict)`.
   Adding `attr_types={"gsi_bounty_sk": "N"}` to the tickets `TableDef` is valid
   without any changes to the `TableDef` dataclass.

4. **Assumption: existing frontend** — the React `TicketOut` type in
   `frontend/src/api/types.ts` will be extended by TBT-010, not this ticket. Until
   TBT-010 lands the frontend silently ignores the new `null` fields (TypeScript
   optional fields with no UI rendering).

5. **Open Decision D3 (who may post)** — any ticket owner bounded by min/max and
   the fraud gate. This ticket only stores `bounty_amount_cents` and surfaces it;
   the ownership check is enforced by TBT-003 and TBT-009.
