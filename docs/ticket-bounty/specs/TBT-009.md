**Type:** Feature | **Priority:** P0 | **Estimate:** 1.5 days

## 1. Summary & Goal

This ticket wires the eight bounty service functions produced by TBT-003 through TBT-008 into the existing `app/routers/tickets.py` FastAPI router. Every endpoint must be guarded by `_require_bounties_enabled()` so the entire surface is a 404 dead-zone when `S.ticket_bounties_enabled` is `False`. The router enforces all auth/ownership rules inline (no new auth middleware), maps the service layer's domain errors to the correct HTTP status codes, and follows every convention already established in `app/routers/tickets.py`: `require_ui_session` + `get_authenticated_user` dependency injection, the `_is_admin_actor` / `_is_admin` helpers, `_raise` for structured error responses, and `_wrap_ticket` for the response envelope.

A concrete secondary goal is route-ordering safety: `GET /tickets/bounties/open` must be declared **before** `@router.get("/{ticket_id}")` (line 900 of `app/routers/tickets.py`) so FastAPI does not capture the literal segment `bounties` as a path parameter.

## 2. Context & Current State

### Existing ticket router conventions (all must be preserved)

`app/routers/tickets.py` uses a consistent structure throughout:

- **Auth**: every handler has `_ctx: dict = Depends(require_ui_session)` (imported from `app.services.sessions` at `tickets.py:19`) plus `user: AuthenticatedUser = Depends(get_authenticated_user)` (`tickets.py:13`). No raw `Request` object is used for auth; the `Request` is only passed to `_emit_ticket_alerts` and audit helpers.
- **Admin check**: `_is_admin_actor(request, user)` (`tickets.py:224`) returns `True` for ADMIN/ROOT roles or for API-key principals with scope `tickets:admin`. `_is_admin(user)` (`tickets.py:207`) checks role only (no API-key fallback), used when the action must be a human admin.
- **Structured errors**: `_raise(status_code, code, message, details=...)` (`tickets.py:194`) raises `HTTPException` with a nested `{"error": {"code":..., "message":..., "details":...}}` body. `_error_responses()` (`tickets.py:198`) provides standard 400/403/404/409 response schemas for OpenAPI.
- **Ticket fetch**: `_ticket_or_404(ticket_id)` (`tickets.py:332`) calls `STORE.get_ticket` and raises 404 if absent.
- **Access check**: `_can_access_ticket(request, user, ticket)` (`tickets.py:339`) grants access to the ticket's `owner_sub` or any admin actor.
- **Response envelope**: `_wrap_ticket(ticket)` (`tickets.py:232`) wraps a dict into `TicketEnvelope(ticket=TicketOut.model_validate(...))`.
- **Route order**: literal-segment routes (`/admin/summary` at `tickets.py:887`, `/admin/kyc-sync-*` starting at `tickets.py:587`) are all declared before the `/{ticket_id}` wildcard at `tickets.py:900`. The `bounties/open` endpoint must follow this same pattern.

### Current `TicketOut` model (app/routers/tickets.py:58-72)

The existing `TicketOut` Pydantic model does not yet carry bounty fields. TBT-002 adds the optional bounty fields to the DynamoDB projection (the return-value dict inside `TicketStore.get_ticket()` at `app/services/tickets.py:528-566`) and to `TicketOut`. There is no separate `_ticket_out` helper function — the projection is built inline in `get_ticket()`. By the time TBT-009 is implemented, those fields (`bounty_amount_cents`, `bounty_currency`, `bounty_status`, `bounty_id`, `claimed_by_sub`, etc.) will be present in `TicketOut` as optional/nullable fields. TBT-009 must not re-add them.

Note: Pydantic v2's `model_validate` ignores extra keys by default, so before TBT-002 lands, `_wrap_ticket` drops the bounty dict fields silently rather than erroring. After TBT-002 adds the fields to `TicketOut`, they are serialized automatically.

### Existing tickets table GSIs (scripts/local-ddb-init.py:695-711)

The `tickets` table currently has ten GSIs: `gsi1pk/sk` (owner), `gsi2pk/sk` (status), `gsi3pk/sk` (assignee), `gsi_space_pk/sk`, `gsi_space_status_pk/sk`, `gsi_space_assignee_pk/sk`, `gsi_member_pk/sk`, `gsi_jira_workspace_pk/sk`, `gsi_jira_issue_pk/sk`, `gsi_jira_sync_state_pk/sk`. TBT-002 adds the `ByBounty` GSI (`gsi_bounty_pk` / `gsi_bounty_sk`); TBT-009 consumes it via `list_open_bounties` (implemented in TBT-008 service layer).

### Billing table (T.billing, S.billing_table_name "billing")

Escrow rows (`pk=BOUNTY#{bounty_id}`, `sk=ESCROW`) and their ledger entries live on `T.billing` (`app/core/tables.py:81` declaration, `:333` assignment). The `_fraud_gate` function called by `post_bounty` is defined in `app/routers/billing.py:118-175` as a module-level function. **Important distinction**: `new_ledger_entry`, `settle_or_reverse_ledger`, and `apply_wallet_delta` live in the shared service `app/services/billing_shared.py` and can be imported cleanly. `_fraud_gate` lives in a *router* module — importing it from `app.routers.billing` into a service is an architectural anti-pattern and risks circular imports in the future. The recommended approach (see Assumption A1) is to call `app.services.fraud_detection.is_frozen` and `app.services.fraud_detection.evaluate_transaction` directly from `post_bounty`, replicating the five-line gate inline, rather than importing a private router function.

### State machine additions (TBT-004 dependency)

TBT-004 extends `_TICKET_STATUSES` in `app/services/tickets.py:15-29` (currently 13 statuses: `open`, `in_progress`, `waiting_on_user`, `done`, `code_complete`, `qa_in_progress`, `qa_approved`, `blocked`, `deploying`, `deployed`, `investigating`, `analyzing`, `tickets_created`) with `claimed`, `pending_approval`, `paid_out`, `cancelled` and adds a `_BOUNTY_TRANSITIONS` map. Neither `_BOUNTY_TRANSITIONS` nor any of these four bounty statuses exist yet in the codebase. TBT-009's endpoints must never call `STORE.update_status` directly for bounty-specific transitions — that path would bypass the `_BOUNTY_TRANSITIONS` gate. All status-changing calls go through the dedicated bounty service functions.

## 5. Detailed Behavior & Edge Cases

### 5.1 Route declaration order

`GET /bounties/open` must be declared in `tickets.py` **above** `@router.get("/{ticket_id}")` (currently line 900). If declared after, FastAPI matches `bounties` as the `ticket_id` path parameter and routes to `get_ticket`, returning 404. The existing `GET /admin/summary` (line 887) is a canonical precedent: it appears before `/{ticket_id}` for the same reason.

Similarly, the new `POST /{ticket_id}/bounty/approve` (and all other `/{ticket_id}/bounty/*` variants) must be declared before the general `POST /{ticket_id}/status` (line 991) for clarity, though FastAPI handles these correctly because the path segments differ.

### 5.2 Ownership and role checks (per endpoint)

**POST `/{ticket_id}/bounty` (post_bounty)**
Caller must be the ticket's `owner_sub`. Check: `if user.sub != ticket["owner_sub"]: _raise(403, "bounty_forbidden", "only the ticket owner may post a bounty")`. Admin actors are NOT permitted to post on someone else's behalf (Open Decision D3: any owner, bounded by fraud gate).

**POST `/{ticket_id}/bounty/claim` (claim_bounty)**
Any authenticated user may claim. No ownership restriction beyond the single-winner conditional (handled in service). The router does not need an ownership check here — the service's `attribute_not_exists(claimed_by_sub)` conditional enforces single-winner.

**POST `/{ticket_id}/bounty/unclaim` (unclaim_bounty)**
Caller must be `ticket["claimed_by_sub"]`. Check: `if user.sub != ticket.get("claimed_by_sub"): _raise(403, "not_claimant", "only the current claimant may unclaim")`. Admin may not unclaim on behalf of a user via this endpoint — use `cancel_bounty` instead.

**POST `/{ticket_id}/bounty/submit` (submit_bounty)**
Same as unclaim: caller must be `claimed_by_sub`.

**POST `/{ticket_id}/bounty/approve` and `/reject` (admin only)**
`if not _is_admin_actor(request, user): _raise(403, "admin_role_required", "admin role required")`. API-key principals with scope `tickets:admin` are also permitted (this is the existing `_is_admin_actor` behavior at line 224). Approve and reject are among the highest-value operations; consider whether `_is_admin` (role check only, no API-key) should be used instead — given the money movement, using `_is_admin` (not `_is_admin_actor`) is safer and consistent with the money-moving intent. The spec recommends `_is_admin(user)` (role check only) for approve/reject to prevent an API-key actor from unilaterally releasing escrow.

**POST `/{ticket_id}/bounty/cancel`**
Two permitted actors:
1. The poster (`user.sub == ticket["owner_sub"]`) while `bounty_status == "funded"` (unclaimed). The service enforces the state check; the router passes `is_admin=False`.
2. Any admin actor (`_is_admin_actor(request, user)`) in any state except `paid_out`. The router passes `is_admin=True`.
Logic: `is_poster = (user.sub == ticket["owner_sub"]); is_admin_actor = _is_admin_actor(request, user); if not is_poster and not is_admin_actor: _raise(403, ...)`.

### 5.3 Double-ticket-fetch avoidance

Several endpoints need the ticket for both the auth check and the service call. The service functions re-fetch the ticket internally (they need the current version for optimistic locking), so calling `_ticket_or_404` in the router is acceptable for the auth check even though the service does its own fetch. This is consistent with the existing `assign_ticket` handler (line 930) which calls `_ticket_or_404` then immediately calls `STORE.assign_ticket`. The cost is one extra `get_item` — acceptable for correctness.

### 5.4 HTTP 402 for insufficient balance

FastAPI's default status codes do not include 402 ("Payment Required"). Use `HTTPException(status_code=402, detail={"error": {"code": "insufficient_balance", "message": "insufficient wallet balance"}})`. The `_raise` helper in tickets.py accepts arbitrary status codes. This must be exposed in `_error_responses()` by adding `402: {"model": ErrorEnvelope, "description": "Insufficient balance"}`.

### 5.5 Concurrent claim race

Two simultaneous `POST /{id}/bounty/claim` requests both pass the router auth check (any authenticated user). Both call `claim_bounty`. The service uses a DynamoDB conditional `update_item` with `ConditionExpression="attribute_not_exists(claimed_by_sub)"`. One request's write succeeds; the other gets `ConditionalCheckFailedException` → the service raises `BountyAlreadyClaimedError` → the router returns HTTP 409 `{"error": {"code": "bounty_already_claimed", "message": "this bounty has already been claimed"}}`. The losing request's caller gets a clear, actionable error.

### 5.6 Approve idempotency

If `approve_bounty` is called twice (e.g., network timeout causing a retry), the service reads `BOUNTY#{id}/ESCROW` and checks `status == "held"`. On the second call the status is already `"released"`, so the service returns a no-op (or raises `BountyWrongStateError` with code `bounty_already_released`). The router returns 409 on the second call. The assignee is credited exactly once.

### 5.7 Cancel-after-paid_out guard

If an admin attempts `POST /{id}/bounty/cancel` after the bounty is `paid_out`, the service reads the escrow row and finds `status == "released"`. It raises `BountyAlreadyPaidOutError`. The router returns 409 `{"error": {"code": "bounty_already_paid_out", "message": "cannot cancel a paid-out bounty"}}`. No money moves.

### 5.8 `bounties/open` list pagination

`list_open_bounties` queries the `ByBounty` GSI (`gsi_bounty_pk = "BOUNTY#OPEN"`) newest-first (`ScanIndexForward=False`). The router passes through `cursor` and `limit` query parameters. Consistent with the existing tickets list pattern (`list_tickets`, line 867), the router validates `limit` with `Query(default=25, ge=1, le=100)`. The cursor is an opaque base64-encoded string. The `TicketStore` class in `app/services/tickets.py` exposes instance methods `_encode_cursor` / `_decode_cursor` (lines 568-582) — the bounty service should replicate the same base64-urlsafe JSON encoding idiom inline rather than calling those private instance methods. The router file itself uses `_encode_unified_cursor` / `_decode_unified_cursor` (lines 280-295) for multi-source cursors; a simpler single-key cursor suffices for the bounty board.

### 5.9 Alerts and audit events

After each successful mutation the router calls `_emit_ticket_alerts` (`tickets.py:362`) and/or `audit_event` for the bounty-specific events. Suggested events:
- `post_bounty`: `bounty_posted`, recipients `[ticket["owner_sub"]]`
- `claim_bounty`: `bounty_claimed`, recipients `[ticket["owner_sub"], claimer_sub]`
- `unclaim_bounty`: `bounty_unclaimed`, recipients `[ticket["owner_sub"]]`
- `submit_bounty`: `bounty_submitted`, recipients `[ticket["owner_sub"]]` + any assigned admin
- `approve_bounty`: `bounty_awarded`, recipients `[assignee_sub]`
- `reject_bounty`: `bounty_rejected`, recipients `[ticket.get("claimed_by_sub")]`
- `cancel_bounty`: `bounty_cancelled`, recipients `[ticket["owner_sub"]] + ([ticket.get("claimed_by_sub")] if any)`

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security & Money-safety

### SECOPS-007 parity
There is no `dev_mode` branch anywhere in the bounty router or service. DynamoDB Local (port 8001) is the moto-backed store in dev; the exact same code paths write to AWS DynamoDB in prod. `apply_wallet_delta` (`billing_shared.py:185-213`) works identically against both targets because the boto3 endpoint is configured via `DDB_ENDPOINT_URL` at startup. `T.billing.meta.client.transact_write_items(...)` also inherits the same endpoint — see `group_treasury.py:717-740` for the client-construction pattern that shows why the low-level client always reaches the correct target (dev or prod) without a `dev_mode` branch.

### Fraud gate
`post_bounty` must run a fraud gate before the wallet debit. The canonical implementation is `_fraud_gate` at `app/routers/billing.py:118-175`, which calls `fraud_detection.is_frozen(user_id)` then `fraud_detection.evaluate_transaction(...)` (`app/services/fraud_detection.py:428` and `:262`). Because importing a private function from a router module into a service is an anti-pattern, the bounty service should call the `fraud_detection` service functions directly (`from app.services import fraud_detection as fd`) replicating the same five-line gate, or extract the check to a shared helper. The gate must run synchronously before any DynamoDB write: a frozen account raises `HTTPException(403)` before any write; a fraud-blocked account (`action=="block"`) also raises 403. No network calls occur that could time out and leave money in an intermediate state.

### Atomic escrow (no partial writes)
`post_bounty` uses `T.billing.meta.client.transact_write_items(...)` — the same pattern used by `app/services/refund_requests.py:292` and the helper `_batch_transact` at `app/services/group_treasury.py:743-751`. The private function `_batch_transact` cannot be imported across modules (it is an internal helper to `group_treasury.py`); the bounty service should call `T.billing.meta.client.transact_write_items(TransactItems=[...])` directly (serialising items via the DynamoDB low-level format) following the `refund_requests.py` precedent. The wallet debit, the `BOUNTY#{id}/ESCROW` put, and the audit ledger entry are a single atomic operation. If any of the three writes fail (including the `wallet_balance_cents >= :needed` conditional on `apply_wallet_delta`), the entire transaction is rolled back by DynamoDB — the wallet is never debited without creating the escrow record.

### No double-charge
The poster's wallet is debited once, atomically with the escrow row creation. `approve_bounty` credits the assignee directly (`new_ledger_entry(USER#{assignee}, type="credit", ...)` + `apply_wallet_delta(T.billing, USER#{assignee}, +net)`) and updates the escrow row to `status="released"`. `write_tip_ledger` is never called — that function debits the tipper, which would erroneously charge the poster a second time.

### Idempotency
- `post_bounty`: deterministic `bounty_id = sha256(f"bounty:{ticket_id}".encode()).hexdigest()[:24]`; the escrow `Put` uses `ConditionExpression="attribute_not_exists(pk)"` — a second call with the same `ticket_id` fails the conditional and raises 409 "already funded" before attempting the wallet debit. The wallet is never double-debited. Note: `apply_wallet_delta` for withdrawals uses `ConditionExpression="wallet_balance_cents >= :needed"` (`billing_shared.py:209`) — an insufficient-balance condition raises `ConditionalCheckFailedException` which maps to HTTP 402.
- `claim_bounty`: `ConditionExpression="attribute_not_exists(claimed_by_sub)"` on the ticket META update; at most one writer wins.
- `approve_bounty`: escrow status checked for `"held"` before credit; second approve returns 409, no second credit.
- `cancel_bounty`: escrow status checked for `"held"` before refund; second cancel returns a no-op (409), no second refund.

### One refund mechanism
`cancel_bounty` refunds exclusively via `new_ledger_entry(type="adjustment", state="settled", reason="bounty_refund")` + `settle_or_reverse_ledger(escrow audit entry → "reversed")` + `apply_wallet_delta(USER#{poster}, +amount)`, all in one `transact_write_items`. **Important balance-column distinction**: `apply_wallet_delta` (`billing_shared.py:185-213`) credits `wallet_balance_cents` on the `WALLET` sk row — the same column that was debited when the bounty was posted. This is the correct return path. By contrast, `refund_payment` in `billing.py:1287` uses `apply_balance_delta` to adjust `payments_settled_cents` on the `BALANCE` sk row (a Stripe payment accounting column) — that path is structurally similar but operates on a different balance column and must NOT be used for wallet-funded bounty refunds. No bespoke refund logic is introduced beyond what `billing_shared.py` already provides.

### CSRF
All endpoints are POST/GET on a router that already has `Depends(require_ui_session)`. The `require_ui_session` dependency (`sessions.py:330`) enforces CSRF for cookie-auth non-GET requests. Bearer-auth requests skip CSRF. No changes are needed to the auth layer.

## 8. Backward Compatibility & Migration

### Flag-off guarantees
With `TICKET_BOUNTIES_ENABLED` unset or `"false"` (the default):
- All eight new endpoints return 404 immediately (first line of each handler calls `_require_bounties_enabled()`).
- No new DynamoDB writes are attempted.
- `_TICKET_STATUSES` additions (`claimed`, `pending_approval`, `paid_out`, `cancelled`) added by TBT-004 are present in the tuple but unreachable through any publicly accessible path when the flag is off (the generic `POST /{id}/status` endpoint only allows `TicketStatusReq` literals: `"open"|"in_progress"|"waiting_on_user"|"done"|"reopened"`, at `tickets.py:187`, unchanged).
- Existing helpdesk/support ticket flows, KYC-ticket sync, Jira sync, and all E2E tests that do not import bounty endpoints are completely unaffected.
- `TicketOut` gains optional nullable bounty fields (TBT-002), so serialization of existing tickets without bounty data is unchanged (all new fields default to `None` and are omitted from the JSON via `model_config = ConfigDict(exclude_none=True)` or equivalent).

### DynamoDB schema migration
The `ByBounty` GSI (TBT-002) is a sparse secondary index. Existing rows that do not carry `gsi_bounty_pk` are simply not indexed — DynamoDB sparse GSIs only index rows that contain the key attributes. No backfill is needed. In prod, the GSI is added via `UpdateTable` before deploying the code; because it is sparse and initially empty, the backfill is instantaneous.

### No existing test regression
All existing `frontend/e2e/tickets.spec.ts` tests (42 tests, sections 52-57) and `frontend/e2e/helpdesk-extra.spec.ts` tests (section 58) are unaffected. The router file gains new handlers that are gated by `_require_bounties_enabled()` and positioned after the existing handlers in the file (except for `GET /bounties/open`, which must be before `GET /{ticket_id}`).

## 10. Open Questions / Assumptions

**D1 — Platform fee (resolved: 0% default)**
`ticket_bounty_fee_bps = 0` → assignee earns the full posted amount. Fee logic is a no-op at zero but the code path exists; changing to a non-zero fee only requires updating the env var. The router does not need to know the fee value — that is service-layer logic in `approve_bounty`.

**D2 — Funding source (resolved: wallet-only)**
`post_bounty` debits `USER#{poster}/WALLET` via `apply_wallet_delta`. No card-charge path. If the poster's wallet is insufficient they receive 402. Fresh-card top-up before posting is handled by the existing wallet deposit endpoints (not in scope for this ticket).

**D3 — Who may post bounties (resolved: any owner)**
No role restriction beyond owning the ticket. The fraud gate and min/max amounts bound abuse. If a role restriction is needed later, it is a one-line check added to the `post_bounty` handler.

**D4 — Assignee abandonment (resolved: manual unclaim, no auto-refund)**
`unclaim_bounty` re-adds the ticket to the bounty board. Escrow stays held. An idle-sweep that auto-refunds after N days is a follow-up; TBT-009 does not implement it.

**Assumption A1**: The fraud gate. `_fraud_gate` is defined in `app/routers/billing.py:118-175` as a module-level function that wraps `app.services.fraud_detection`. Importing a private router function into a service module is an architectural anti-pattern (services should not depend on routers). The recommended approach is to import `app.services.fraud_detection as fd` directly in `app/services/ticket_bounties.py` and call `fd.is_frozen(poster_sub)` then `fd.evaluate_transaction(user_id=poster_sub, amount_cents=amount_cents, entry_type="bounty_hold", tx_id=ticket_id, ip_address=ip)` — identical logic to `_fraud_gate`, without the router dependency. If the project later decides to centralize the fraud gate, it should be extracted to `app/services/fraud_check.py` (not living in the billing router). No circular-import issue arises with the direct `fraud_detection` import since `billing.py` does not import `ticket_bounties.py`.

**Assumption A2**: `TicketOut` will carry the bounty fields (nullable) by the time this ticket is merged. If TBT-002 is not yet merged, `_wrap_ticket` will silently drop the extra fields; the router code does not need to change, but the response will not include bounty data until TBT-002 lands.

**Assumption A3**: The `BountyBoardEnvelope` / `BountyBoardItem` models are sufficient for the frontend. If TBT-010 needs the full `TicketOut` shape on the board, `list_open_bounties` can return `TicketListEnvelope` (same type as `list_tickets`) with no router changes — the service just returns richer dicts.

### Money-invariant summary

| Invariant | Design | Risk |
|---|---|---|
| No double-charge | Wallet debit atomic with escrow put (single `transact_write_items`); idempotent via `attribute_not_exists(pk)` conditional | LOW — conditional enforced by DynamoDB |
| Single refund | Refund path: `apply_wallet_delta(+amount)` only; guarded by `status=="held"` check before any refund write | LOW — escrow status gate prevents double-refund |
| Correct balance column | Bounty debit/refund via `apply_wallet_delta` (`WALLET` sk) NOT `apply_balance_delta` (`BALANCE` sk) | RISK if implementer copies `refund_payment` (Stripe path) verbatim |
| No payout double-credit | `approve_bounty` credits assignee; gated by escrow `status=="held"`; second approve sees `status=="released"` → 409 | LOW |
| `write_tip_ledger` not used | Tip ledger debits the tipper — using it for payout would debit poster again | MUST NOT be used for bounty payout |
